Before you start: scope, honesty and safety

What "any hardware" really means

No one learns every machine. What transfers is a method: master one architecture deeply (here x86-64 on QEMU, then one real PC), and learn to read specifications and datasheets well enough that a new platform becomes a checklist: CPU manual, boot firmware and handoff, memory map, interrupt controller, timer, console, storage, then everything else. Track D turns that checklist into practice on ARM64 and RISC-V.

The expanded page makes the method explicit for any device you can see: section 5 is a step-by-step procedure from "a device on the table" to a tested driver, section 6 catalogs every device class with its standard and reference drivers, and sections 7–12 and 16 add file systems, user space up to self-hosting, more CPU architectures, SoC platforms, virtualization and open GPU documentation.

Two independent lines of work

Line 1 (Tracks A–D, optional G): firmware, kernel, drivers. Runs in an emulator first, real hardware later.

Line 2 (Tracks E–F): GPU kernels with CUDA and HIP, then multi-GPU and multi-node. This runs on Linux or Windows with the vendor's driver, not on your own kernel. The two lines share only the foundations, so you can alternate between them.

The bigger version: building an OS for any hardware you see. The goal "an OS from scratch for any hardware" is reached in layers, not all at once: one architecture deeply (Tracks A–C), the universal method and the hardware catalog (sections 5–6) so that every new device becomes a procedure, a complete operating system around the drivers (file systems in section 7, user space and self-hosting in section 8), more instruction sets and SoC platforms (Track D, sections 10–11), virtual hardware (section 12), and GPUs (Tracks G and section 16). The honest limits stay the same everywhere: some hardware is undocumented, some depends on signed vendor firmware, and some is locked; the method tells you which, early, and the page says so wherever it applies.

Honest scope statement about GPUs. CUDA kernels run on NVIDIA's driver and CUDA runtime; HIP kernels run on AMD's amdgpu kernel driver and the ROCm user-space stack (HIP on NVIDIA hardware maps to CUDA). Writing a GPU driver from scratch, one that brings up the GPU's firmware, memory manager, command processors and display engine, is a separate, research-level, multi-year effort. AMD publishes a large share of its hardware documentation and its whole Linux driver stack is open source; NVIDIA publishes its open-gpu-kernel-modules, but much of the GPU's programming interface stays vendor-controlled and relies on signed firmware (the GSP). Track G is therefore an optional reading-and-experiment track with a realistic target: understanding, plus a working driver for a simple virtual display device, not a replacement for amdgpu.

Safety box: read this twice.

  • Develop all firmware and kernels in QEMU first, using OVMF (EDK II's UEFI firmware for virtual machines) for UEFI work, with KVM acceleration on a Linux host if available (WHPX/Hyper-V acceleration exists on Windows hosts but is less convenient for low-level debugging; plain TCG emulation is the most predictable for early milestones).
  • Only after a milestone passes in QEMU, move to a dedicated spare machine or development board whose disk contents you do not need. Boot your work from a USB stick or a separate disk first.
  • Never flash self-built firmware onto a machine you depend on. Firmware milestones that reach real flash chips need a board with a documented recovery path (for example a coreboot-supported board), an external SPI flash programmer with a test clip, and a verified backup image of the original flash.
  • Expect that a bad driver can corrupt disks (wrong LBA, wrong DMA address) or, in rare cases, upset a device's state. Disconnect disks you care about while testing storage drivers on real hardware.
  • Do GPU experiments on a machine whose data you do not need; driver crashes, hangs and forced resets are normal while learning, and long benchmarks stress power and cooling.

0 · How to use this page (you and an agent)

The page is written for two readers at once: you, the learner, and an AI coding agent pairing with you. The agent follows the runbook in section 19; you follow the reading lists and own every design decision. The rhythm is the same for both.

1 · Pick exactly one milestoneNever two at once. Its ID (for example B4) goes in the branch name, the log entry and the commit message.
↓
2 · Read the named spec sections firstThe agent names the document and section title; you read it and write three to five sentences in your own words in the log. No implementation before this.
↓
3 · Write the planA short design note: data structures, the order of hardware steps, what can fail, how the acceptance test will observe success.
↓
4 · Write the test harness first where possibleHost-side unit tests for pure logic (allocators, parsers, checksums); a QEMU run script with a timeout and serial-log checks for anything touching hardware.
↓
5 · Build in small stepsEach step boots. Keep the previous milestone's tests green.
↓
6 · Acceptance test passes in QEMUAll listed tests, run from a clean build. The agent never marks a milestone done with a test skipped, weakened or "to be added later".
↓
7 · Commit and logOne git commit (or a small series) tagged with the milestone ID; a short written log entry; optionally a real-hardware run noted separately.

Suggested repository layout (described, not prescribed)

  • docs/log/ one dated entry per working session: milestone, spec sections read, decisions, what broke, how it was fixed, test result, commit ID.
  • docs/design/ one note per subsystem (memory map, page-table layout, interrupt vectors, driver model, locking rules). The agent updates it whenever a decision changes.
  • docs/specs.md-style index (any format) listing every specification used, with the edition you downloaded and the sections used per milestone.
  • boot/ UEFI loader (Track A); kernel/ arch-independent core; kernel/arch/x86_64, later arch/aarch64 and arch/riscv64; drivers/ one folder per device class; user/ user-space programs; tests/ host unit tests and QEMU test scenarios; tools/ image builders and run scripts.
  • gpu/ a separate project (or repository) for Tracks E and F, with one folder per kernel family and a benchmark harness.

How acceptance tests work for kernel code

  • Serial output is the oracle. The kernel prints structured lines on the emulated 16550 UART; QEMU writes them to a file or to the terminal; the harness checks for expected lines and for the absence of "PANIC".
  • Pass/fail exit. QEMU's isa-debug-exit device lets the kernel end the run with a chosen exit status, so a test run is a normal process that passes or fails in CI.
  • Timeouts. Every QEMU test has a wall-clock limit; a hang is a failure, not "probably fine".
  • Determinism. Fixed QEMU machine type, memory size, CPU count and firmware build per test; the harness records them in the log.
  • Debugger reproducibility. Every failing test can be re-run with QEMU's GDB stub enabled and the CPU halted at start, so the failure can be stepped through.
  • Real hardware runs are recorded as extra evidence, never as a replacement for the QEMU test.

Universal definition of done (every milestone): (1) all acceptance tests listed for the milestone pass from a clean build; (2) earlier milestones' tests still pass; (3) the design note is updated; (4) the log entry names the spec sections used; (5) no compiler warnings at the agreed warning level; (6) the commit is tagged with the milestone ID; (7) you can explain, without notes, every hardware register the milestone touches.

1 · Foundations (prerequisites)

Budget two to four months part-time. Much of this you may already know from C++ work; the parts that are usually new are the memory model at the hardware level, linking, ELF, and reading assembly fluently.

1.1 C++ for systems programming

Language topics

  • Object representation: size, alignment, padding, standard-layout and trivially-copyable types, bit-fields (and why hardware register layouts should not rely on them).
  • The C++ memory model: data races, happens-before, the atomic memory orders, fences; why volatile is not a synchronization tool but is still used for memory-mapped device registers (each access must happen, in order, with the right width).
  • Undefined behaviour that bites kernels: strict aliasing, signed overflow, misaligned access, lifetime of objects created in raw memory (placement new, start of lifetime).
  • Inline assembly as a topic: what the compiler needs to know (inputs, outputs, clobbers, memory barriers), and why most of it should live in a few small wrapper functions.
  • Compile-time techniques useful for drivers: constexpr register descriptions, strong types for physical vs virtual addresses, static assertions on structure offsets taken from specs.

Linking and binaries

  • Compilation units, symbols, relocations, sections, segments; the difference between the linker's view (sections) and the loader's view (program headers).
  • Linker scripts: placing the kernel at a higher-half virtual address, aligning sections to pages, exporting section boundaries as symbols.
  • ELF: file header, program headers, section headers, symbol tables, relocation types for x86-64; dynamic vs static linking; position-independent code.
  • PE/COFF: the format of UEFI applications and of Windows binaries such as bootmgfw.efi and ntoskrnl.exe, which you have seen in traces.
  • DWARF debug information: what GDB needs to show source lines and variables in your kernel.

1.2 C++ inside a kernel (topics, no code)

  • Freestanding environment: the C++ standard defines a freestanding implementation; only the freestanding headers are guaranteed (type traits, limits, atomics, initializer lists and a few others); everything else, including most of the standard library, is unavailable unless you port or write it.
  • No exceptions, no RTTI by default: both need runtime support (unwinding tables, an unwinder, type-info objects). Disable them through compiler options; only implement support later if you have a reason.
  • Your own operator new and delete (all overloads, including sized and aligned forms) backed by your kernel heap; a policy for allocation failure in contexts where you cannot sleep.
  • Global constructors: the compiler emits a table of initializer functions (the init_array section on ELF); your early init code must call them, in order, after the heap and console exist, or you must avoid non-trivial globals entirely.
  • The Itanium C++ ABI: name mangling, vtable layout, guard variables for function-local statics, the handful of runtime support functions the compiler expects (pure-virtual call handler, guard acquire/release, destructor registration).
  • Calling convention: the System V AMD64 ABI (registers, stack alignment, the red zone and why kernels disable it, the kernel code model).
  • Floating point and SIMD: kernels usually forbid the compiler from using SSE/AVX registers in kernel code, or must save and restore extended state (the XSAVE family) on every context switch.
  • A cross compiler: a GCC built for the x86_64-elf target (the OSDev wiki "GCC Cross-Compiler" page), or Clang with an explicit target triple and the LLD linker. Never use the host compiler's default target for kernel code.
  • Freestanding helpers you must supply: memory copy/set/compare functions, a formatted print, a panic routine, assertions, a stack-protector failure handler if you enable the stack protector, sanitizer runtime hooks if you enable sanitizers (a kernel undefined-behaviour sanitizer is a worthwhile later goal).

1.3 Computer architecture

  • "Computer Systems: A Programmer's Perspective" (Bryant, O'Hallaron): data representation, machine-level programs, the memory hierarchy, linking, exceptional control flow, virtual memory, system-level I/O, concurrency. Do its labs (data, bomb, attack, cache, shell, malloc).
  • "Computer Organization and Design" (Patterson, Hennessy) for pipelines and caches; "Computer Architecture: A Quantitative Approach" (Hennessy, Patterson) later.
  • "A Primer on Memory Consistency and Cache Coherence" (Sorin, Hill, Wood; second edition with Nagarajan) for the hardware view of memory ordering.
  • Caches, TLBs, write-combining and uncacheable memory types (the MTRRs and the PAT on x86), DMA and cache coherence, interrupts as hardware events.

1.4 Assembly at reading level

  • x86-64: Intel SDM Volume 1 (basic architecture) and Volume 2 (instruction reference) for lookup; AMD64 Architecture Programmer's Manual Volumes 1 and 3. Learn to read both Intel and AT&T syntax because GCC tools default to AT&T.
  • ARM64: Arm's "Learn the architecture" guides and the Arm Architecture Reference Manual for A-profile (A64 instruction set chapters) for lookup; the Procedure Call Standard for the Arm 64-bit Architecture (AAPCS64).
  • Practice: read compiler output for your own small functions at several optimization levels (Compiler Explorer is the standard tool); read disassembly of a Windows driver in a debugger to connect to your trace work.

2 · TRACK A — Firmware and boot

Goal of the track: understand, and then build, everything between power-on and the first instruction of your kernel. Your Windows boot traces start roughly where this track ends (the Windows Boot Manager and winload have already run when kernel-mode ETW logging begins), so this track also explains the part of boot that traces cannot show.

2.1 From power-on to the boot loader (x86 PC)

  1. Power sequencing: the platform's power-management controller and the chipset bring rails up; on modern PCs the security processor (Intel CSME or AMD PSP) runs before the main CPU and, on AMD, even loads the first firmware stages.
  2. Reset vector: the bootstrap processor starts in real mode at the reset vector near the top of the 32-bit address space, which the chipset maps to the SPI flash. Other cores wait.
  3. Microcode: early firmware loads a CPU microcode update (Intel SDM Volume 3 describes the microcode update facility; AMD delivers microcode in the firmware image as well).
  4. Cache-as-RAM: before DRAM works, firmware uses the CPU cache as temporary memory for a stack.
  5. Memory initialization ("training"): vendor silicon code (Intel FSP, AMD AGESA or AMD openSIL) trains the DRAM. This step is the main reason firmware is hard to write from scratch for real PCs.
  6. Chipset and CPU init: PCH/FCH configuration, PCI Express root ports, multiprocessor initialization, SMM (System Management Mode) setup.
  7. Device discovery: PCI enumeration, option ROMs (UEFI drivers stored on add-in cards, such as a graphics card's GOP driver).
  8. Tables for the OS: ACPI tables, SMBIOS tables, the memory map.
  9. Boot device selection: UEFI boot variables (BootOrder, Boot####) choose a boot loader on an EFI System Partition; legacy BIOS reads the first sector of a disk.
  10. OS loader: on Windows, bootmgfw.efi (Windows Boot Manager) then winload.efi, which loads ntoskrnl.exe, the HAL and the boot-start drivers you see in DRIVERS.html, then calls ExitBootServices and jumps to the kernel.

2.5 Security and hidden components

  • Secure Boot (UEFI Specification, "Secure Boot and Driver Signing"): Platform Key (PK) owns the platform; Key Exchange Keys (KEK) authorize changes to the databases; db lists allowed signers or hashes; dbx lists revoked ones. Linux distributions boot through shim, a small loader signed by Microsoft's UEFI CA that carries the distribution's key and supports Machine Owner Keys (MOK). For your own loader in QEMU, simply leave Secure Boot off; later, enroll your own PK/KEK/db in OVMF and sign your loader (the sbsigntools package is the usual tool) as an exercise.
  • Measured boot: each stage hashes the next into TPM Platform Configuration Registers; the TCG PC Client Platform Firmware Profile Specification defines what is measured and the event log format.
  • Hardware roots of trust: Intel Boot Guard and AMD Platform Secure Boot (topics) verify the firmware itself, which is one reason you cannot simply flash your own firmware on most retail PCs.
  • Microcode: loaded by firmware and often again by the OS early in boot.
  • Embedded Controller (EC): a small microcontroller on laptops handling keyboard matrix, battery, fans, lid, power button; the OS talks to it through the ACPI EC interface (ACPI Specification, "ACPI Embedded Controller Interface Specification" chapter). The Chromium EC project is an open-source EC firmware you can read.
  • Intel CSME / AMD PSP (topics): independent security processors with their own firmware, present on almost all modern PCs. Read about them; do not try to modify them.
  • SMM: a CPU mode entered through System Management Interrupts, used by firmware for platform services; important for understanding unexplained pauses and some security issues.

The ExitBootServices rule. The memory map key changes whenever memory is allocated. The loader must get the memory map, call ExitBootServices with that key, and retry by getting the map again if the call fails; after success no boot service may be used (no printing through the console protocol, no allocation). This is the most common first bug.

4 · TRACK C — Drivers and buses: from a specification to a driver

Goal of the track: learn to turn a controller specification into a working driver, starting with the devices QEMU emulates faithfully and ending on your spare PC. Each driver is a separate milestone; the method is always the same.

4.1 The method (use it for every device)

  1. Identify the device: PCI vendor and device ID and class code (from your C1 enumerator, or from Device Manager / lspci on the host), or the ACPI hardware ID (_HID) for platform devices.
  2. Find the controller specification: the interface standard (AHCI, NVMe, xHCI, HD Audio, virtio) if one exists; otherwise the vendor's datasheet or programmer's reference manual. If none is public, the Linux driver becomes the de facto documentation (read it, cite it in the log, do not copy it).
  3. Read the register map: which BAR, register offsets and widths, reset values, read/write semantics (read-only, write-1-to-clear, reserved bits that must be preserved).
  4. Read the initialization sequence: the specification's "initialization" or "programming model" section, step by step, including required delays and timeouts.
  5. Configuration space: enable memory space decoding and bus mastering in the PCI command register; walk the capability list (power management, MSI, MSI-X, PCI Express capability); for PCIe, the extended capability list.
  6. MMIO vs port I/O: map MMIO BARs uncached in your page tables; use port I/O only for legacy devices; every register access through a small typed accessor with the right width and ordering.
  7. DMA: allocate physically contiguous, correctly aligned buffers below any address limit the device has; understand cache coherence on your platform; with an IOMMU (Intel VT-d, AMD-Vi) the device sees I/O virtual addresses that you must map.
  8. Interrupts: legacy INTx through the IOAPIC (routing from ACPI _PRT), then MSI or MSI-X (preferred: one vector per queue).
  9. Power states: device D-states (D0–D3), link states (ASPM) as topics; most early drivers keep devices in D0.
  10. Write the driver against the spec, test on QEMU, then on real hardware, where errata and firmware quirks appear; record every quirk with its source.

This is the short form. Section 5 expands it into the universal method for any device, including identification on every bus, the order in which to look for documentation, lawful observation when there is none, and a full design and test checklist.

5 · The universal method: from a device you see to a working driver

Track C taught the method on devices that were chosen for you because their specifications are public and QEMU emulates them. This section turns that method into a procedure you can apply to any device you meet: a card in a slot, a chip on a laptop motherboard, a USB gadget, a block on an SoC. It has five stages: identify the device, find documentation in a fixed order, observe a working driver lawfully if there is no documentation, design the driver, and test it. The hardware catalog (section 6), the platform notes (section 11) and the agent rules (section 19.5) all plug into this procedure.

What the method promises, stated honestly. It always tells you what a device is and where the knowledge about it lives. It cannot make undocumented hardware documented. Every device ends up in one of six outcomes, and knowing which one early is most of the skill:

  1. An open class standard applies (NVMe, AHCI, xHCI, HD Audio, USB HID, virtio...): a class driver works, possibly with a few quirks.
  2. The vendor publishes documentation (datasheet, programmer's reference manual, technical reference manual): you write the driver from the documents.
  3. Only open-source drivers exist (Linux, BSD): they are executable documentation; you read them, write your own understanding down, and implement it.
  4. Nothing public exists, but a working driver does: lawful observation of that driver (stage c) is slow but possible.
  5. The device depends on signed vendor firmware: you can only drive it through the interface its firmware offers, and only if you may redistribute or load that firmware.
  6. The device is locked (fused secure boot, encrypted firmware interfaces, no working driver to observe): record it as out of reach and move on.

5.2 Stage (b): find documentation, always in this order

  1. An open standard for the device's class. If the class code, USB interface class or ACPI _CID says the device follows a standard, a class driver works and the vendor's own documentation is only needed for quirks. Examples: PCI class 01 08 02 is an NVMe controller, 01 06 01 an AHCI SATA controller, 0C 03 30 an xHCI USB controller (0C 03 20 EHCI, 0C 03 10 OHCI, 0C 03 00 UHCI), 04 03 an HD Audio controller; vendor ID 1AF4 marks virtio devices; USB interface class 03 is HID, 08 mass storage, 02 and 0A communications (CDC), 01 audio, 0E video, 09 hub, 0B smart card, E0 wireless controller (Bluetooth), FF vendor-specific (no class driver).
  2. The vendor's public documents: datasheet, programmer's reference manual (PRM), technical reference manual (TRM) for SoCs, application notes, and the errata document (Intel calls it a "specification update", Arm a "Software Developer Errata Notice", NXP a "chip errata"). Some vendors require a free registration; some require an NDA, which is normally out of reach for an individual and must never be used for open work.
  3. The Linux driver and its devicetree binding, as executable documentation. Write what you learn in your own words in the design note.
  4. BSD drivers (FreeBSD, OpenBSD, NetBSD): often smaller and simpler, under permissive licences, and occasionally written from documentation the Linux authors did not have. OpenBSD drivers are particularly compact to read.
  5. Vendor SDKs, board-support packages and reference code: microcontroller HALs and register headers, vendor U-Boot and Linux trees, Android kernel trees, firmware source drops. Quality varies; register headers are the most valuable part.
  6. Everything else: community wikis (linux-sunxi, OSDev), other open systems (Haiku, ReactOS, SerenityOS, Redox, Zephyr, NuttX), and QEMU's device model if QEMU emulates the device (a readable description of what the emulator's authors believe the hardware does; useful, but second-hand).

5.5 Stage (e): the test plan

  • Emulation first when QEMU models the device (or a close relative). If it does not, a small QEMU device model written from your specification is a strong test of the specification itself (an advanced but very instructive exercise).
  • Host unit tests for every pure function: descriptor parsing, divider calculations, report-descriptor parsers, protocol state machines.
  • Trace replay: feed recorded captures (USB pcap files, mmiotrace logs, logic-analyser exports) into your protocol state machine on the host and check its decisions.
  • Real hardware matrix: every machine and every revision you have; record subsystem IDs and firmware versions with each result.
  • Fault injection: unplug during transfer, cable pulls, timeouts, corrupted descriptors, IOMMU faults, interrupts arriving before initialization completes, suspend and resume in the middle of I/O.
  • Soak: long runs (hours) with throughput and error counters logged.
  • Reference comparison: the same workload on Linux or Windows on the same machine: throughput, latency, and the device's own statistics registers.
  • Regression: the emulator part runs in the harness on every commit; real-hardware runs are recorded in the log as separate evidence (as everywhere on this page).

5.6 Three worked examples (in words)

Example 1 — a PCI Express Ethernet card (an Intel I210-family controller)

  1. Identify. Device Manager shows a hardware ID with VEN_8086 (Intel) and the device's ID, a subsystem ID naming the card maker, and a compatible ID with class 02 00 00 (network controller, Ethernet). The PCI ID Repository names the chip. The Intel INF lists sibling IDs, showing that one programming model covers a family of controllers. The boot trace shows Intel's NDIS miniport loading early.
  2. Find documentation. There is no class standard for Ethernet controllers on PCI (unlike NVMe for storage), so step 2 applies: Intel publishes the I210 datasheet publicly (tier 2). The Linux igb driver and FreeBSD's Intel Ethernet driver are the second reference; the datasheet's specification update lists errata.
  3. Observe? Not needed. Optionally, an mmiotrace of the igb driver's probe on Linux gives a reference initialization order to compare with your reading of the datasheet.
  4. Design. Bind by vendor and device ID; BAR0 is the register space; MSI-X with separate vectors for receive queues, transmit queues and "other" causes (link change). Initialization: global device reset through the control register and wait for completion; mask interrupts; read the MAC address from the NVM; reach the PHY through the MAC's MDIO interface (IEEE 802.3 clause 22 registers) and start auto-negotiation; set up receive and transmit descriptor rings (base, length, head, tail) using the datasheet's descriptor formats; enable receive and transmit; handle link-status-change interrupts. DMA is 64-bit capable; buffers come from your DMA API (IOMMU-mapped after C7). No firmware download is needed (contrast with many Wi-Fi chips). Error handling: transmit-hang detection with a reset path.
  5. Test. Recent QEMU versions include an igb (82576) model, a close relative, for the first runs; then the real card: DHCP, the C9 TCP echo test, a 1 GiB transfer with checksum, cable unplug and replug, throughput compared with Linux on the same machine, interrupt counts per vector.

Example 2 — a USB device (a USB-to-serial adapter)

  1. Identify. VID and PID from Device Manager or lsusb, and, most importantly, the interface class. Two very different cases follow.
  2. Find documentation. If the interface class is 02 (CDC, with a data interface of class 0A), the device follows the USB-IF "Class Definitions for Communications Devices" and its PSTN subclass (abstract control model): write one class driver and every such adapter works (tier 1). If the class is FF (vendor-specific), as on many popular adapter chips (FTDI, Silicon Labs CP210x, WCH CH34x, Prolific PL2303 families), check the vendor's application notes and datasheets (coverage of the vendor requests varies by vendor), then the Linux drivers (ftdi_sio, cp210x, ch341, pl2303) and the FreeBSD drivers (uftdi, uslcom, uchcom, uplcom).
  3. Observe if needed. Pass the adapter to a Windows VM with the vendor driver, capture with Wireshark on the host (usbmon or USBPcap), change the baud rate, parity and flow-control settings one at a time, and record which vendor control request (request type, request number, value, index, data) each change produces. Data travels on bulk endpoints; modem-status lines often arrive on an interrupt endpoint or as a header inside bulk packets. Write this down as your specification.
  4. Design. A USB class or vendor driver on your C8 stack: match by interface class or by VID/PID table; claim the interfaces; set up the bulk and interrupt endpoints; implement line coding and flow control; connect to the TTY layer from C2; handle disconnect in the middle of a transfer.
  5. Test. QEMU's usb-serial device emulates an FTDI-style adapter for the first runs; on hardware, a loopback wire between TX and RX: 1 MiB with checksum at several baud rates; compare captured traffic from your driver with the vendor driver's capture; unplug mid-transfer and confirm clean recovery.

Example 3 — an SoC peripheral described by a devicetree (the I2C controller of a Raspberry Pi 4 and a temperature sensor)

  1. Identify. In the devicetree the firmware passes, the I2C controller node has a compatible list naming the Broadcom BCM2835-family I2C controller, a reg property, an interrupts property (a GIC SPI on the Pi 4), a clocks reference and pinctrl references; you add (or find) a child node for a sensor, for example a TI TMP102 with compatible "ti,tmp102" at its I2C address.
  2. Find documentation. The binding for the controller in the Linux devicetree bindings documentation; the "BSC" (Broadcom Serial Controller) chapter of "BCM2711 ARM Peripherals" (tier 2); the GPIO chapter for the pin alternate functions; NXP UM10204 for the bus protocol; the TMP102 datasheet; the Linux i2c-bcm2835 driver and FreeBSD's BCM2835 BSC driver as cross-checks.
  3. Observe? Not needed; a logic analyser is used for verification, not discovery.
  4. Design. A platform driver bound by compatible. Translate the reg address through the parent buses' "ranges" properties: the Broadcom documents give peripheral addresses in the VideoCore bus address space, which differs from the ARM physical address your MMU must map; this translation is a classic first bug. Select the pins' alternate function (pinctrl), obtain the input clock rate (from the clock node or the firmware's mailbox property interface), compute the divider for 100 kHz, handle the FIFO, the "transfer done", "acknowledge error" and "clock-stretch timeout" status bits, and the interrupt. Instantiate child devices from the controller's child nodes; the sensor driver reads the temperature register and converts it as the datasheet specifies.
  5. Test. Host unit tests for the divider calculation and the transfer state machine against the datasheet's status-bit description (and in QEMU if your QEMU version emulates this board's I2C controller); on the board: the logic analyser's I2C decoder shows the expected address, register and data bytes at the configured speed; the temperature agrees with a reference thermometer within the sensor's stated accuracy; a transfer to an absent address returns a "no acknowledge" error instead of hanging.

6.2 How to use the catalog with a new machine

  1. Run M1 (identify every device). For each device, find its row here.
  2. If the row's class has an open standard and you already have the class driver, test it and record quirks.
  3. If not, follow the row's "Open documentation" column into stage (b) of section 5; if the column says "members only" or "NDA", go straight to the open drivers in the next column.
  4. Add a line to your design log for each device: class row, tier, driver status. That list is your real-hardware roadmap for the machine.

6.3 Catalog milestones (Track C continued)

C14 HID over I2C: the laptop touchpad hard
Goal
On a laptop (Intel or AMD), make the touchpad work through three cooperating drivers: the I2C controller (DesignWare-compatible on most such laptops), the GPIO controller delivering its interrupt, and an HID-over-I2C class driver feeding your input layer.
Read
Microsoft "HID over I2C Protocol Specification"; ACPI Specification sections on I2cSerialBusV2 and GpioInt resources and on _DSM; the touchpad's device entry in the laptop's DSDT disassembled with iasl; the USB-IF HID class definition (report descriptors) and HID Usage Tables (digitizer page); Linux i2c-designware, pinctrl driver for the platform and i2c-hid as references; NXP UM10204.
Build
ACPI resource parsing for serial-bus and GPIO resources; the I2C controller driver; a GPIO interrupt path; the HID-over-I2C protocol (descriptor fetch, report reads, reset); a report-descriptor parser shared with C8's USB HID (the parser must not care which bus delivered the report).
Accept
  • Host unit tests: your report-descriptor parser decodes descriptors dumped from three different real touchpads and keyboards (collected under Linux) identically to Linux's parsed view.
  • On the laptop: pointer motion, button clicks and two-finger contact reports arrive in your input layer; the interrupt counter grows only while the pad is touched.
  • A deliberate wrong I2C address produces a reported "no acknowledge" error, not a hang.
C15 Processor idle, frequency and thermal management medium
Goal
Your kernel saves energy and respects thermal limits: idle states chosen by a simple governor, frequency control through HWP, CPPC or ACPI P-states, and thermal-zone monitoring with a critical shutdown.
Read
Intel SDM Volume 3 power and thermal management chapter (MWAIT hints, HWP, thermal status MSRs, RAPL energy counters) or the AMD equivalents; ACPI Specification sections on processor power states (_CST, _LPI), performance control (_PSS, _PCT, _PPC, _CPC) and thermal zones; Linux kernel documentation "CPU Performance Scaling" and "CPU Idle Time Management" for the concepts.
Build
An idle governor choosing between halt and deeper states from expected idle length; a frequency driver; a thermal driver reading zones through your C10 AML interpreter; statistics per CPU (time in each state, frequency residency measured with the APERF/MPERF ratio).
Accept
  • In QEMU: an idle kernel keeps host CPU usage near zero (halt-based idle works) and wakes for timers on time (B8 tests still pass).
  • On the spare PC: package energy measured through the RAPL counters at idle drops by a margin you set in the plan when deeper idle states are enabled; requested frequency changes are visible in the measured effective frequency.
  • A simulated critical trip point (test build) triggers an orderly shutdown with file systems synced.

7 · File systems in breadth

Track B gave your kernel a VFS, FAT32 (B15) and ext2 (B16). And it has to survive the power being cut at any moment. This section adds the breadth and the discipline of crash consistency.

7.2 Crash consistency: the discipline

  • The problem: one logical operation (append a block to a file) changes several on-disk structures (data block, inode, bitmap). A power cut between those writes leaves the disk inconsistent. Disks and controllers may also reorder writes in their caches.
  • Ordering tools from the device: cache flush commands (NVMe Flush, ATA FLUSH CACHE, SCSI SYNCHRONIZE CACHE), Force Unit Access (FUA) writes, and the device's atomic-write guarantees (usually one sector; check the NVMe atomic-write fields). Without flushes, no file system is crash-safe.
  • Strategies: run a checker after the crash (fsck, as in FAT and ext2); journaling (write intent to a log first, then in place; metadata-only "ordered" mode or full data journaling, as in ext3/ext4, NTFS and XFS); soft updates (carefully ordered writes, as in FreeBSD's UFS); copy-on-write (never overwrite live data; switch a root pointer atomically, as in ZFS, btrfs, APFS); log-structured designs (F2FS, and the original Sprite LFS).
  • Checksums catch silent corruption (metadata checksums in ext4, everything in ZFS and btrfs).
  • What applications are promised: fsync and fdatasync semantics, rename atomicity, directory fsync; many applications get these wrong, which the research below documents.
  • Testing: cut the power in an emulator at random points (stop QEMU abruptly with the disk cache mode set so that unflushed writes can be lost), record and replay write streams (Linux's dm-log-writes is the classic tool), and use the fstests (xfstests) suite's crash and consistency tests as inspiration.

Reading: OSTEP chapters "Crash Consistency: FSCK and Journaling", "Log-structured File Systems", "Data Integrity and Protection" and "Flash-based SSDs"; Tweedie, "Journaling the Linux ext2fs Filesystem"; McKusick and Ganger, "Soft Updates: A Technique for Eliminating Most Synchronous Writes in the Fast Filesystem" (USENIX 1999); Rosenblum and Ousterhout, "The Design and Implementation of a Log-Structured File System"; Pillai et al., "All File Systems Are Not Created Equal: On the Complexity of Crafting Crash-Consistent Applications" (OSDI 2014); Mohan et al., "Finding Crash-Consistency Bugs with Bounded Black-Box Crash Testing" (CrashMonkey, OSDI 2018); Giampaolo, "Practical File System Design with the Be File System"; Carrier, "File System Forensic Analysis" (on-disk layouts of FAT, NTFS, ext and UFS).

9.2 ARM64 essentials

  • Exception levels: EL0 (user), EL1 (kernel), EL2 (hypervisor), EL3 (secure monitor, usually Trusted Firmware-A). Your kernel normally starts at EL2 or EL1; if at EL2, drop to EL1 or use VHE (topic).
  • Exception vectors: a vector table base register per level, with entries per exception type and source; syndrome registers describe the cause.
  • MMU: translation tables with configurable granule (4 KiB, 16 KiB, 64 KiB), two table base registers (lower and upper address ranges), memory attributes through the MAIR register, explicit barriers and TLB maintenance instructions, cache maintenance for DMA on non-coherent devices.
  • GIC: distributor, redistributors (GICv3), CPU interface through system registers; SGIs, PPIs, SPIs, LPIs (with the ITS for MSIs).
  • Generic timer: a system counter and per-CPU timers with interrupt as a PPI.
  • PSCI for CPU on/off, system reset and power off; SMCCC for calling firmware.
  • Devicetree vs ACPI: embedded boards describe hardware in a Flattened Devicetree (Devicetree Specification); servers following the Arm SBSA (Server Base System Architecture) and BSA (Base System Architecture) with the BBR (Base Boot Requirements) use UEFI and ACPI, like PCs.
  • UEFI on ARM: QEMU's virt machine can run EDK II's ArmVirtPkg firmware (packaged by distributions under names such as AAVMF or QEMU_EFI), so your Track A loader can be ported with an AArch64 build.
  • Reading: Arm "Learn the architecture" guides (exception model, memory management, generic timer, GIC); Arm Trusted Firmware-A documentation; Linux arch/arm64.

9.3 RISC-V essentials

  • Privilege modes: M (machine, firmware), S (supervisor, your kernel), U (user); H extension for hypervisors.
  • SBI: the RISC-V Supervisor Binary Interface Specification defines calls from S-mode into M-mode firmware (timer, IPIs, remote fences, hart state management, system reset, debug console); OpenSBI is the reference implementation.
  • Interrupts: CLINT (or ACLINT) for software and timer interrupts, PLIC for external interrupts; the newer AIA (Advanced Interrupt Architecture) with APLIC and IMSIC.
  • Paging: Sv39, Sv48 (and Sv57) page-table formats, the satp register, sfence.vma for TLB invalidation.
  • Boot: OpenSBI then U-Boot (often with U-Boot SPL before it on real boards) or EDK II; the kernel receives the hart ID and a devicetree pointer.
  • Reading: RISC-V Instruction Set Manual Volume II; SBI Specification; PLIC Specification; RISC-V ELF psABI; xv6-riscv source and book (the best compact RISC-V kernel to read).

9.4 Boards

  • Raspberry Pi 4 / 5: the boot starts in the SoC's own boot ROM and firmware (on the Pi 4 and Pi 5 a bootloader in SPI EEPROM, plus firmware files on the boot partition and a config.txt file), which then loads your kernel image at a documented address with a devicetree. Documentation: Raspberry Pi's official documentation, "BCM2711 ARM Peripherals" (Pi 4) and "RP1 Peripherals" (Pi 5). A community UEFI firmware exists for the Pi 4 (the Pi Firmware Task Force project) if you want the UEFI path. A USB-to-serial adapter on the UART pins is essential.
  • RISC-V boards: StarFive VisionFive 2 (JH7110 SoC) and similar boards ship with OpenSBI and U-Boot; use the vendor's JH7110 documentation and the board's devicetree; mainline Linux and U-Boot support help as references.
  • QEMU virt machines (aarch64 and riscv64) are the first target in both cases: well-documented devices, virtio, and GDB support.

10.2 Architecture-neutrality checklist

Every item below has broken some kernel during a port. Before X1 or X2, review your arch layer against it and fix what you can in advance.

  • Pointer and long width: 32-bit targets break code that stores pointers in 64-bit integers carelessly, or assumes all physical memory is directly mapped.
  • Endianness: device registers and on-disk formats have a defined byte order; every access must say which (FAT and ext2 are little-endian, network headers are big-endian, the devicetree blob is big-endian).
  • Page and cache-line sizes: never hard-code 4 KiB or 64 bytes in core code.
  • Memory ordering: x86 is strongly ordered (TSO); Arm, RISC-V, Power and MIPS are weakly ordered. C++ atomics with the correct memory orders, plus explicit barriers around device access, are mandatory.
  • Atomics: load-linked/store-conditional versus compare-and-swap; 64-bit atomics may be missing on 32-bit CPUs.
  • Alignment: some CPUs fault on misaligned access, especially to device memory.
  • Instruction and data cache coherence: loading code (exec, modules, JIT) needs explicit instruction-cache maintenance on most non-x86 CPUs.
  • MMU model: hardware page walks with different table formats, hashed page tables (Power), or software TLB refill (MIPS, LoongArch, OpenRISC).
  • Interrupt and timer abstraction: your interfaces from Track B must not assume an APIC.
  • System-call entry, context switch, FPU and vector state: one small file per architecture; lazy versus eager saving of large vector registers.
  • ABI details: argument registers, stack alignment, TLS register, relocation types, the start-up code of user programs.
  • Boot protocol and hardware description: UEFI and ACPI, devicetree, or both.

11 · Platforms and SoCs

11.3 Arm SystemReady, EBBR and why they make "any Arm board" easier

  • The problem they solve: without a standard, every Arm board needs a board-specific kernel image and board-specific boot instructions.
  • Arm SystemReady is Arm's compliance programme: a certified system boots generic, unmodified operating-system images through UEFI. Historically it had bands named SystemReady SR (servers: SBSA hardware, UEFI and ACPI per the BBR), SystemReady ES (embedded servers: BSA hardware, UEFI and ACPI) and SystemReady IR (IoT: UEFI as defined by EBBR, typically provided by U-Boot, with a devicetree); Arm has since reorganised the bands, so read Arm's current SystemReady requirements document for today's names.
  • EBBR (Embedded Base Boot Requirements, an open specification maintained by Arm and the community) defines the subset of UEFI that U-Boot-based boards provide, plus where the devicetree comes from.
  • BSA and SBSA (Base System Architecture, Server Base System Architecture) define the hardware minimum (GIC, generic timer, UART, watchdog, PCIe behaviour); BBR defines the firmware side. The Arm SystemReady Architecture Compliance Suites (ACS) test both.
  • Consequence for you: on a SystemReady board, your AArch64 UEFI loader (A1–A3 rebuilt for AArch64) boots without board-specific code, finds ACPI tables or a devicetree through the UEFI configuration table, and your kernel discovers everything from them. D10 uses exactly this.
  • RISC-V analogues: the RISC-V Boot and Runtime Services (BRS) specification and the RVA23 application profile aim at the same "one image boots everywhere" goal; EDK II and U-Boot provide UEFI on RISC-V today. Check their ratification status when you start.

11.5 SoC bring-up checklist (extends the checklist in 9.1)

  1. Serial console first: find the debug UART pins, use a 3.3 V USB-to-serial adapter (never 5 V), confirm the boot ROM's or U-Boot's output.
  2. Recovery path: know how to recover from a bad image (SD card swap, FEL, mask-ROM mode, uuu) before writing anything to on-board storage.
  3. Boot a known-good stack (vendor or mainline U-Boot and Linux), dump its devicetree and kernel log: this is your reference.
  4. Read the devicetree top to bottom: memory, CPUs, interrupt controller, timer, UART, clocks, resets, pinctrl, regulators, then devices.
  5. Bring up in order: memory map and MMU, interrupt controller, timer, UART driver, then (trusting firmware-enabled clocks at first) GPIO with a heartbeat LED, then storage, USB (often DWC2 or DWC3), Ethernet (often Synopsys or Cadence MAC plus an MDIO PHY), display last.
  6. Clocks and resets: add drivers only when a device needs a clock or reset the firmware left off; record each in the design log.
  7. DMA: check every device for coherency ("dma-coherent" in the devicetree) and handle caches accordingly.
  8. Errata: read the SoC and core errata documents before chasing "impossible" bugs.

12 · Virtualization

Much of the "hardware" your OS will ever run on is virtual: QEMU on your desk, Hyper-V under Windows, KVM and Xen in clouds. Virtualization matters in two directions. As a guest, your OS should detect the hypervisor and use paravirtual clocks and devices instead of slow emulated ones. As a host, your kernel can itself become a hypervisor: the most demanding test of your understanding of the CPU, because you must emulate or pass through everything a guest expects.

12.1 Concepts

  • Trap and emulate and the Popek and Goldberg requirements for virtualizable architectures; why classic x86 did not meet them, and how binary translation (early VMware) and paravirtualization (early Xen) worked around it.
  • Hardware-assisted virtualization: a new CPU mode or privilege level for the hypervisor, a control structure per virtual CPU, and "VM exits" for the events the hypervisor chooses to intercept.
  • Nested paging (Intel EPT, AMD NPT, Arm stage-2 translation, RISC-V G-stage translation): the hardware walks the guest's page tables and then the hypervisor's, a two-dimensional walk whose cost is why TLBs and large pages matter even more in VMs.
  • I/O virtualization: emulated devices (QEMU's e1000, AHCI), paravirtual devices (virtio, VMBus, Xen PV), device pass-through with the IOMMU (VFIO), and SR-IOV virtual functions.
  • Interrupt and timer virtualization: virtual APICs (Intel APICv and posted interrupts, AMD AVIC), virtual GIC interfaces and GICv4 direct injection, RISC-V AIA guest interrupt files; TSC offsetting and scaling, the Arm virtual timer.
  • Nested virtualization: a hypervisor running as a guest of another hypervisor; this is how you will develop yours (KVM on Linux supports nested VMX and SVM; Hyper-V supports nested virtualization for its guests).
  • Confidential computing (Intel TDX, AMD SEV-SNP, Arm CCA) as a topic: guests protected even from the hypervisor.

13.2 Topics in the order you will meet them

  1. Programming model: host and device code, kernels, grids/blocks/threads, memory spaces (global, shared/LDS, constant, local, registers), synchronization within a block, asynchronous launches, error checking after every API call and every launch.
  2. Memory coalescing: how a warp's or wavefront's addresses combine into memory transactions; structure-of-arrays vs array-of-structures; alignment and vectorized loads.
  3. Occupancy and latency hiding: registers, shared memory and block size; when higher occupancy does not help; instruction-level parallelism.
  4. Bank conflicts: shared memory / LDS access patterns, padding and swizzling.
  5. Parallel primitives: reductions (tree, warp/wave shuffles, atomics), scans (Blelloch, decoupled look-back as used in CUB), histograms, radix sort, stream compaction.
  6. Tiling and GEMM: block tiling, register tiling, double buffering, asynchronous copies to shared memory, the CUTLASS hierarchy (threadblock, warp, instruction-level tiles) and its CuTe layout algebra.
  7. Mixed precision: FP32, TF32, FP16, BF16, FP8 and integer formats; accumulation precision; numerical error and how to set test tolerances.
  8. Streams, events and graphs: concurrency between copies and kernels, pinned host memory, CUDA Graphs / HIP graphs to cut launch overhead.
  9. Unified / managed memory: page migration, prefetching and its costs.
  10. Profiling and the roofline model: arithmetic intensity, memory-bound vs compute-bound, reading Nsight Compute's and ROCm Compute Profiler's speed-of-light and memory charts.
  11. Reading PTX and SASS (cuobjdump, nvdisasm) and AMD ISA (the assembly emitted by the AMDGPU back end; ROCm's disassembly tools); recognize spills, uncoalesced loads, bank-conflict-prone patterns, matrix instructions.
  12. HIP portability: HIP API equivalents of the CUDA runtime, hipify-perl and hipify-clang, warp-size-dependent code, 64-bit lane masks on wave64, differences in atomics and memory model details.
  13. Higher-level kernel languages: Triton (Python-embedded, tile-based; supports NVIDIA and AMD GPUs) as a productivity comparison.

13.4 How performance acceptance tests work

  • Correctness first: compare against a CPU reference or the vendor library with a tolerance justified by the precision (relative error, or ULP-based for FP32; looser for FP16/BF16 with FP32 accumulation). Test odd sizes (not multiples of the tile), tiny sizes, and large sizes.
  • Measurement protocol: warm-up runs, then the median of at least 20 timed runs using device events; fixed clocks if your driver allows it (record the setting); report GB/s or TFLOP/s and the percentage of the reference.
  • Reference: the vendor library on the same GPU, same data type, same sizes, measured by the same harness. Peak numbers from datasheets are context, not the target.
  • Targets are yours to set: each milestone says "reaches X % of the reference"; write X in the plan before you start (sensible first targets are often in the 50–80 % range for GEMM and 80–95 % of measured copy bandwidth for memory-bound kernels, but your GPU decides). The agent never lowers X after the fact without your explicit approval and a log entry.
  • Explain the gap: every performance milestone ends with a profiler-backed explanation of the remaining gap (memory throughput, issue stalls, occupancy, instruction mix).

  • F4–F8: two machines with GPUs and a network. Plain Ethernet with TCP works for correctness; InfiniBand or RoCE NICs with GPUDirect RDMA are needed for the real performance picture. Cloud instances with RDMA networking are the practical route for most learners.

15 · TRACK G (optional, advanced) — Toward your own GPU driver

Scope, stated plainly. A full driver for a modern discrete GPU is one of the largest pieces of software in an operating system: the Linux amdgpu driver alone is millions of lines (much of it generated register headers) and is maintained by a large team at AMD with hardware documentation and firmware engineers to ask. nouveau, the community NVIDIA driver, was built over many years largely by reverse engineering and still depends on NVIDIA-signed firmware for recent GPUs. What is realistic for one person: understand the architecture of a GPU driver, read the real ones, probe a real GPU read-only from your own kernel, and write a complete driver for a simple virtual GPU (virtio-gpu, and the Bochs/QEMU standard display device). CUDA and HIP will keep running on the vendor's driver.

16 · Open GPU documentation beyond AMD and NVIDIA

Track G centres on AMD and NVIDIA because those are the GPUs of Tracks E and F. For the goal of driving any hardware, the other GPU families matter as much: integrated graphics in most PCs and nearly every SoC carry an Intel, Arm Mali, Qualcomm Adreno, Broadcom VideoCore, Imagination PowerVR, Vivante or Apple GPU. Their documentation situations differ enormously, from vendor-published manuals to pure reverse engineering. This section maps them and says which are realistic targets for one person.

Display and 3D are separate problems. A GPU driver has a display (mode-setting) half and a rendering/compute half. On SoCs they are often entirely different blocks from different vendors (for example a Rockchip display controller with an Arm Mali GPU), and the display side is usually far better documented and needs no firmware. Getting pixels on a screen natively is therefore the realistic first goal on almost every platform.

16.2 Kernel-side reading for any GPU

  • Linux DRM documentation (in the kernel documentation tree): "DRM Internals", "Kernel Mode Setting (KMS)" (CRTCs, planes, encoders, connectors, atomic mode setting), "DRM Memory Management" (GEM, TTM), the GPU scheduler, "Buffer Sharing and Synchronization" (dma-buf, dma-fence), "Userland interfaces", and the per-driver chapters (i915, xe, amdgpu, panfrost, msm, vc4, v3d, etnaviv).
  • Mesa documentation: the source-tree layout, Gallium, the NIR compiler intermediate representation, and the per-driver pages; the freedreno and Panfrost projects' published notes on their reverse-engineering methods.
  • Talks and write-ups from the reverse-engineering projects (Panfrost, freedreno, Asahi Linux, etnaviv) are the best explanation of how undocumented GPUs were understood, and they apply the observation techniques of 5.3 at scale.

16.3 Which targets are realistic for a hobby GPU driver

  1. virtio-gpu (G2): complete and fully specified; done in Track G.
  2. Native display on an Intel integrated GPU from the PRMs: reading EDID, taking over the pipe that the firmware's GOP configured, changing the scanout address and then the mode. Documented, no firmware needed on older generations, and every Intel laptop is a test machine (G5).
  3. A SoC display controller on a board with a public TRM (NXP i.MX LCDIF, TI DSS) or a well-studied one (Raspberry Pi's HVS through the vc4 driver, Allwinner DE2 through linux-sunxi).
  4. Broadcom VideoCore IV 3D on a Raspberry Pi 3: the one embedded 3D core with a vendor-published architecture guide, a small open driver, and no firmware dependency for 3D (G6).
  5. An Intel GPU's copy or render engine on an older generation, from the PRMs, where command submission does not need GuC firmware.
  6. Mali Midgard/Bifrost through Panfrost, or Vivante through etnaviv: feasible as study and porting projects, using the open Mesa compilers rather than writing your own shader compiler.
  7. Hard or out of reach for one person: modern NVIDIA (GSP firmware), Apple AGX (everything undocumented), current Adreno and CSF-based Mali (firmware plus undocumented interfaces), current AMD beyond what amdgpu already does.

In every case the shader compiler is a project of its own; reusing Mesa's compilers through a port of the user-space driver is the realistic path once your kernel has a DRM-like interface.

17 · TRACK H — Device firmware: the microcontrollers inside the hardware

What this track adds. Track A is system firmware: the UEFI/BIOS that boots the PC. But almost every device you met in the driver list has its own small computer inside, running its own firmware: the laptop's Embedded Controller (battery, keyboard, fans, power button), the touchpad, USB devices, the SSD controller, Wi-Fi and Bluetooth chips, the GPU's power and security processors, and on servers the BMC. These are mostly microcontrollers (Arm Cortex-M, RISC-V, older 8051-class cores) running bare-metal code or a small real-time OS. Here you learn to write that kind of firmware on development boards you can freely reflash, and how the host's driver talks to it.

Honest scope. The firmware of commercial SSD controllers, Wi-Fi chips, GPUs and most touchpads is proprietary and signed: you can study how it is loaded and how the driver talks to it, but you cannot rewrite it. The open, learnable parts are: microcontroller firmware on development boards, open Embedded Controller firmware (Chromium EC), open BMC firmware (OpenBMC), USB device firmware, and research SSD platforms. Use development boards and a debug probe; never reflash the EC or BMC of a machine you depend on.

17.2 What to learn

  • Microcontroller architecture: Armv7-M and Armv8-M Architecture Reference Manuals; the Cortex-M Technical Reference Manuals; the NVIC interrupt controller, SysTick, the MPU, low-power modes. RISC-V microcontrollers use the privileged specification from Track D.
  • Bare-metal C++ on a microcontroller: the vector table, the reset handler, start-up code and the linker script (flash vs RAM), the same freestanding C++ rules as the kernel, plus very small memory budgets. Arm CMSIS (Cortex Microcontroller Software Interface Standard) for the core headers.
  • Peripherals and buses: GPIO, timers, UART, I2C (NXP's "I2C-bus specification and user manual", UM10204), SPI, SMBus (System Management Bus Specification), ADC, DMA.
  • A real-time OS: Zephyr RTOS and FreeRTOS: their schedulers, drivers and device-tree-based configuration, which mirrors Track D.
  • Debugging: JTAG and SWD (Arm Debug Interface Architecture Specification), a debug probe, OpenOCD or pyOCD, GDB on the target.
  • Updating safely: bootloaders on microcontrollers, A/B images, signed images (MCUboot), rollback protection.
  • Boards to use: any well-documented board, for example the Raspberry Pi Pico (RP2040/RP2350, with full public datasheets), an STM32 Nucleo board (ST's reference manuals), or a RISC-V microcontroller board.
  • Books: "The Definitive Guide to ARM Cortex-M3 and Cortex-M4 Processors" (Joseph Yiu); "Making Embedded Systems" (Elecia White).

19 · Agent instructions (runbook for an AI coding agent)

This section is addressed to the AI coding agent that pairs with the learner. Follow it literally. When the learner's instructions conflict with this runbook, ask the learner which one wins and record the answer in the log.

19.1 Setup (once)

  1. Confirm the host. Record the operating system, CPU, available virtualization acceleration (KVM, WHPX/Hyper-V, or none) and GPUs. If the host is Windows, propose WSL2 or a Linux virtual machine for the toolchain and explain the trade-off (nested virtualization, GDB access) before choosing.
  2. Install and pin the toolchain: cross compiler (x86_64-elf GCC or Clang/LLD), binutils, build system, QEMU, OVMF, GDB, image tools. Write the versions into the log. Make the installation scripted and repeatable.
  3. Create the repository with the layout in section 0, a README stating the current milestone, the log folder and the design folder; first commit.
  4. Create the test harness skeleton: host unit tests; a QEMU runner with timeouts, serial-log capture, isa-debug-exit result codes and a "debug" mode that starts QEMU halted with the GDB stub.
  5. Ask the learner which tracks to run (line 1, line 2, or both alternating) and which real hardware is available (spare PC, boards, GPUs, second node). Record it.

19.2 For every milestone

  1. One milestone at a time. Do not start code for the next milestone until the current one is done, committed and logged. Do not combine milestones to "save time".
  2. Name the reading. List the exact documents and section titles needed (for example "Intel SDM Volume 3, chapter 'Interrupt and Exception Handling', section on the IDT"). Never invent section numbers, page numbers or titles; if unsure, say "the section on X in document Y" and ask the learner to locate it.
  3. Ask the learner to read first. Wait until the learner confirms they have read the sections and has written a short summary in the log. Answer questions about the text, quoting the spec's own terms.
  4. Explain every new spec concept you use, with the document and section title it comes from, before the code that depends on it. Each register, field and bit used in code gets a comment naming its source document and section title.
  5. Write the plan before the code: a short design note covering data structures, hardware sequence, failure modes, and exactly how the acceptance tests will observe success. The learner approves the plan.
  6. Tests first where possible. Pure logic (allocators, parsers, checksums, protocol state machines) gets host unit tests before implementation. Hardware-facing code gets the QEMU scenario and expected serial output written first.
  7. Small steps that boot. Each intermediate step builds and boots; run the full regression suite of earlier milestones regularly and always before declaring done.
  8. Never skip, weaken or postpone an acceptance test. If a test cannot pass (missing hardware, emulator limitation), stop, explain, and let the learner decide; record the decision. Do not mark the milestone done without the learner's explicit approval of any change to its tests.
  9. Never flash firmware to real hardware, never write to a real disk the learner has not explicitly designated as disposable, never run GPU or network stress tests on machines the learner has not designated. Firmware work stays in QEMU unless the learner has a recovery path (external programmer, backup image) and explicitly asks.
  10. Stop and ask on ambiguity: when the spec is ambiguous, when QEMU and the spec disagree, when real hardware differs from the spec, or when a design decision affects later milestones. Present options with consequences.
  11. Keep the design log current: every decision, every quirk (with its source), every deviation from the spec, every known limitation.
  12. Debug with evidence. When something fails, gather evidence first (serial log, QEMU interrupt and exception logging, GDB backtrace, register dump, profiler report) and state a hypothesis before changing code. Record the root cause in the log.
  13. Prefer clarity over cleverness in kernel code: small functions, typed wrappers for register access, no hidden global state, explicit locking rules written next to the data they protect.
  14. Respect licences. Reading Linux, EDK II, coreboot, Mesa or vendor code is encouraged; copying code requires checking the licence with the learner and recording the origin.
  15. Real hardware is a separate step. After the QEMU acceptance test passes, offer a real-hardware run if the learner has designated hardware; record its results separately and never replace a QEMU test with a hardware observation.

19.3 Definition of done (check every item)

  1. All listed acceptance tests pass from a clean checkout and clean build, run by the harness, with output saved in the log.
  2. All earlier milestones' tests still pass.
  3. No compiler warnings at the agreed level; static analysis (if configured) clean; sanitizers clean in host tests.
  4. Design note updated; spec sections used are listed in the log entry.
  5. For performance milestones (Tracks E and F): the reference measurement, your measurement, the target X agreed beforehand, the achieved percentage, and a profiler-backed explanation of the gap are recorded.
  6. The learner can explain the code and the hardware behaviour; the agent asks three short questions about the milestone and records the learner's answers.
  7. Commit tagged with the milestone ID; the README's "current milestone" updated to the next one.

19.4 Log entry template (fields)

  • Date and session length
  • Milestone ID and step
  • Documents and section titles read (with edition)
  • Learner's summary of the reading (3–5 sentences)
  • Plan or changes to the plan
  • What was built; what failed; root cause; fix
  • Tests run and results (pass/fail counts, performance numbers)
  • Open questions for the next session
  • Commit ID

19.5 When the learner points at a new piece of hardware

Use these rules whenever the learner says "make this work", whether "this" is a card, a laptop, a board, a USB gadget or a chip on a schematic. They follow the universal method of section 5 step by step. Numbering continues from 19.3.

  1. Open a device record before anything else. Create a design-log entry named after the device with the fields: identification, class and catalog row, documentation tier, documents found, observation needed (yes/no), design note, test plan, status. Never start driver code for a device without this record.
  2. Identify (stage a). Ask the learner for, or collect with the learner's permission, every identifier the machine offers: Windows Device Manager hardware and compatible IDs and the INF name; Linux PCI and USB listings with numeric IDs, ACPI table dumps or the devicetree; the boot-trace driver name if the device appears there; CPU identification registers for CPUs. Resolve names with the PCI and USB ID databases, the ACPI ID registry, and the devicetree bindings. Record every ID exactly as read.
  3. Classify. Find the device's row in the hardware catalog (section 6). If the class code, interface class or compatible ID matches an open class standard, say so first: a class driver may already exist in the learner's kernel.
  4. Find documentation in the fixed order (stage b): open class standard; vendor datasheet, programmer's or technical reference manual and errata; the Linux driver and its devicetree binding; BSD drivers; vendor SDKs and other open systems. Name each document by its real title and issuing body; if you are unsure of an exact title, say "the vendor's datasheet for this chip" and ask the learner to locate it. Never invent titles, section numbers, register names or URLs.
  5. Assign the documentation tier (1–6) and tell the learner what it implies for effort and risk, including when the honest answer is "tier 6: out of reach". Get the learner's decision to proceed, to choose a different device, or to stop.
  6. Never use NDA, leaked or confidential material, even if the learner has it; ask the learner to confirm the origin of any document that is not obviously public.
  7. Observation (stage c) only with explicit approval. Before any reverse engineering, present the legal and licence note of 5.3, ask the learner to confirm it is lawful where they live, and record the confirmation. Prefer observing behaviour (MMIO traces, USB captures, logic-analyser traces, read-only register dumps) over disassembling vendor code. Write the resulting specification in your own words; never paste vendor or GPL code into the learner's project without the licence check of rule 19.
  8. Read-only first on real hardware. Until the design note is approved, only read registers the documentation or an open driver says are safe to read. Never write to PMICs, SPI flash, EEPROMs (including memory-module SPD), fuses, or unknown registers; never change voltages or clocks outside documented ranges.
  9. Design (stage d). Fill every row of the 5.4 table in the design note: bus binding, resources, initialisation sequence, register model, interrupts, DMA and cache coherency, power states, error handling, hot-plug, upper interface, trust, observability. Each register used gets its source document and section title. The learner approves the note.
  10. Test plan (stage e) before code. Write the 5.5 test plan: emulator tests (or a reason why none exist), host unit tests, trace-replay tests, the real-hardware matrix, fault injection, soak, and comparison with a reference OS. Acceptance tests are fixed here and follow rule 13 (never weakened later without the learner's approval).
  11. Emulate before touching the device when QEMU models it or a close relative; otherwise build the host-side tests and, for complex devices, propose writing a QEMU model from the specification as a separate step.
  12. Record quirks with evidence: every difference between documentation and hardware gets an entry with the observation, the board or revision (subsystem IDs, firmware versions), and the workaround.
  13. Close the record: status (working, partial, unsupported with reason), tests and results, and a one-paragraph summary the learner can reuse for the next device of the same class.

19.6 Rules for the expanded tracks

  1. File systems (section 7): power-cut and corruption tests run only on disk images or disks the learner has designated as disposable; never run a write-capable driver for NTFS, ext4 or exFAT on a disk holding the learner's data; FS6 stays read-only.
  2. User space (section 8): record the system-call ABI decision (own ABI or Linux-compatible) before U1; ported software keeps its licence files and the recipe records the source, version and patches; never claim POSIX conformance beyond the test subsets that actually passed.
  3. SoCs (section 11): before writing anything to on-board storage (eMMC, SPI flash, boot partitions), confirm the board's recovery path (SD boot, USB recovery mode) works; never burn fuses or enable secure-boot locks.
  4. Other architectures (section 10): a port is only done when the same arch-neutral tests pass unchanged; any change to arch-neutral code is logged as a bug fix or design change.
  5. Virtualization (section 12): hypervisor development happens inside nested virtualization or on a designated test machine, never on the learner's main host; a hypervisor bug that crashes the host is treated as a test failure to analyse, not something to retry blindly.
  6. GPUs (sections 15 and 16): display experiments on real hardware start read-only (state dumps) and only change scanout or modes after the learner approves; never load GPU firmware whose redistribution licence has not been checked.

ACPI
Advanced Configuration and Power Interface: tables and bytecode through which firmware describes the platform and its power management to the OS.
ACS / AER / DPC
PCI Express Access Control Services (which devices may talk to each other directly), Advanced Error Reporting, and Downstream Port Containment (isolating a failed link).
AHCI
Advanced Host Controller Interface: the standard register interface for SATA controllers.
ALSA / ASoC
Linux's sound architecture and its System-on-Chip layer, which splits SoC audio into codec, CPU interface (I2S) and machine drivers.
AML / ASL
ACPI Machine Language (bytecode in the DSDT/SSDTs) and ACPI Source Language (its human-readable form).
AP / BSP
Application processor / bootstrap processor: the BSP runs firmware and early kernel code; APs are started later.
APIC, local APIC, IOAPIC, x2APIC
x86 interrupt controllers: one local APIC per CPU (timer, IPIs, interrupt acceptance), IOAPICs routing device interrupts, x2APIC as the MSR-based mode of the local APIC.
APLIC / IMSIC
The two parts of the RISC-V Advanced Interrupt Architecture: a wired-interrupt controller and a per-hart controller for message-signalled interrupts.
BAR
Base Address Register: PCI configuration field giving the address range of a device's registers or memory.
BDS
Boot Device Selection, the UEFI PI phase that chooses and launches a boot option.
Bank conflict
Two or more threads of a warp/wavefront accessing different addresses in the same shared-memory/LDS bank, which serializes the accesses.
BL31 / BL32 / BL33
Trusted Firmware-A stage names: the EL3 runtime, the secure payload (for example OP-TEE) and the non-secure firmware (for example U-Boot).
Block cache
Kernel cache of disk blocks shared by file systems.
Boot ROM
Code fixed in an SoC at manufacture that runs first after reset and loads the next stage from a boot medium, often with a USB recovery mode.
Bus bandwidth (busbw)
The nccl-tests metric that normalizes collective throughput so that it can be compared with link bandwidth.
Cache-as-RAM
Using the CPU cache as memory before DRAM is initialized during early firmware.
CAN
Controller Area Network: a robust multi-drop bus used in vehicles and industry, standardised as ISO 11898.
CCID
The USB class for smart-card readers.
CDNA / RDNA
AMD's GPU architecture families for compute accelerators (Instinct) and for graphics (Radeon).
Class code
The three-byte PCI field (base class, subclass, programming interface) that says what kind of device a function is and, for standard interfaces, which programming model it follows.
Clean-room implementation
Reimplementation in which one party writes a specification from observation and another implements from that specification only.
Coalescing
Combining the memory accesses of a warp/wavefront into few wide transactions.
Collective
A communication operation involving a whole group of processes or GPUs (all-reduce, all-gather, reduce-scatter, broadcast).
Common clock framework
Linux's model of an SoC's clock tree (rates, parents, gating), the usual reference for clock drivers.
Compatible string
The devicetree property ("vendor,device", most specific first) used to match a device node to a driver.
Compute Unit (CU)
AMD's basic GPU core block, comparable to NVIDIA's SM.
Connection manager (USB4)
The software or firmware that discovers USB4 and Thunderbolt routers and sets up tunnels for PCIe, DisplayPort and USB 3.
coreboot
Open-source firmware that initializes hardware and then runs a payload (for example SeaBIOS, an EDK II payload or LinuxBoot).
CPPC
Collaborative Processor Performance Control: an ACPI interface through which the OS requests abstract performance levels from the platform.
cpufreq / cpuidle
Linux's frameworks for choosing CPU frequency and idle-state depth; good conceptual references for your own power management.
CPUID / MIDR / misa
The CPU identification mechanisms of x86, Arm (Main ID Register) and RISC-V (machine ISA register, with mvendorid, marchid and mimpid).
Crash consistency
The property that a file system returns to a valid state, without losing synced data, after a power cut at any moment.
CRC32
The checksum used in GPT headers and partition arrays.
CSI-2 / DSI
MIPI Alliance serial interfaces for cameras (CSI-2) and displays (DSI); specifications are for members only.
DART
The IOMMU used in Apple Silicon SoCs, documented by Asahi Linux.
Device Manager hardware ID
The identifier strings Windows builds from bus IDs (for example from PCI vendor and device IDs) and matches against INF files to choose a driver.
Device record
On this page: the design-log entry the agent opens for every new device (identification, tier, documents, design, tests, status).
Devicetree
A data structure describing hardware for platforms without ACPI, passed by firmware to the kernel.
DMA
Direct Memory Access: a device reading or writing memory without the CPU.
Documentation tier
On this page: the 1–6 scale from "open class standard" to "locked" that predicts the effort a device will need (section 5.2).
Doorbell
A device register written by the driver to say "new work is in this queue" (NVMe, xHCI, GPUs).
DRAM training
Firmware calibration of the memory interface timing and voltages at boot, done before any RAM can be used.
DRM / KMS
Linux's Direct Rendering Manager (GPU memory, command submission) and Kernel Mode Setting (display configuration).
DSDT / SSDT
Differentiated / Secondary System Description Tables: ACPI tables containing AML.
DXE
Driver Execution Environment, the UEFI PI phase where most firmware drivers run.
EBBR
Embedded Base Boot Requirements: the UEFI subset and devicetree rules that let generic OS images boot on embedded Arm (and RISC-V) boards.
EC
Embedded Controller: a microcontroller on laptops for battery, keyboard, fans and power events, reached through ACPI.
ECAM
Enhanced Configuration Access Mechanism: memory-mapped PCI Express configuration space, described by the ACPI MCFG table.
EDID / DisplayID
VESA data structures in which a monitor describes its supported modes and properties.
EDK II / TianoCore
The open-source reference implementation of UEFI and PI; OVMF is built from it.
eDP
Embedded DisplayPort: the VESA standard for internal laptop panels.
ELF
Executable and Linkable Format, the object and executable format used by your kernel and user programs.
eMMC
Embedded MultiMediaCard: soldered flash storage with an MMC interface, standardised by JEDEC.
EPT / NPT
Intel Extended Page Tables and AMD Nested Page Tables: hardware second-stage translation from guest-physical to host-physical addresses.
Errata
A vendor's list of known deviations between hardware and its documentation, with workarounds (Intel "specification update", Arm "Software Developer Errata Notice").
Exception level (EL0–EL3)
ARM64 privilege levels: user, kernel, hypervisor, secure monitor.
exFAT
Microsoft's FAT successor for large removable media; its specification was published openly in 2019.
ExitBootServices
The UEFI call by which the OS loader takes ownership of the machine; boot services are gone afterwards.
FADT
Fixed ACPI Description Table: power-management hardware blocks and pointers to other tables.
FEL
The USB recovery mode in Allwinner boot ROMs, used with the sunxi-tools.
Fence (GPU)
An object signalled when the GPU finishes a piece of work, used for synchronization.
Freestanding
A C++ implementation without a hosted OS: only a minimal set of standard headers is guaranteed.
FullMAC / SoftMAC
Wi-Fi designs in which the 802.11 MAC layer runs in the chip's firmware (FullMAC) or in the host driver (SoftMAC).
GDT
Global Descriptor Table: x86 segment descriptors; in long mode mainly code/data privilege and the TSS.
GIC
Arm Generic Interrupt Controller.
GMBUS
The I2C controller inside Intel display engines used to read monitor EDID over DDC.
GOP
Graphics Output Protocol: UEFI's framebuffer interface.
GPT
GUID Partition Table, the UEFI partitioning scheme.
GPUDirect P2P / RDMA
NVIDIA technologies for direct GPU-to-GPU transfers and for network adapters accessing GPU memory directly.
GSP
GPU System Processor: a microcontroller in recent NVIDIA GPUs running NVIDIA firmware that handles much of GPU initialization and management.
GuC / HuC / DMC
Firmware-driven microcontrollers in Intel GPUs: command submission scheduling, media authentication, and display power management.
H extension
The RISC-V hypervisor extension adding HS, VS and VU modes and G-stage translation.
HBM
High Bandwidth Memory: stacked DRAM used on data-center GPUs.
HHDM / direct map
A region of kernel virtual address space mapping all physical memory at a fixed offset.
HID over I2C
Microsoft's protocol that carries USB-style HID reports over I2C, used by most laptop touchpads and touchscreens.
HIP
AMD's C++ GPU programming interface, closely mirroring the CUDA runtime, part of ROCm.
HOB
Hand-Off Block: data structures passed from PEI to DXE describing memory and resources.
Hot-plug
Adding or removing a device while the system runs (PCIe, USB, Thunderbolt); drivers must cope with a device disappearing at any moment.
HPET
High Precision Event Timer.
HWP
Intel Hardware P-states: the processor chooses its own frequency within limits set by the OS.
I2C / SMBus / I3C
Two-wire low-speed buses for sensors, EEPROMs and controllers; SMBus is a stricter subset of I2C, I3C a faster MIPI successor.
I2S
A serial bus for digital audio samples between an SoC and an audio codec.
IDT
Interrupt Descriptor Table: x86 table of interrupt and exception handlers.
INF file
The Windows driver-package description listing supported hardware IDs, services and settings.
Infinity Fabric / xGMI
AMD's interconnect; xGMI links connect AMD Instinct GPUs directly to each other.
InfiniBand / RoCE
High-performance networks offering RDMA; RoCE carries RDMA over Ethernet.
IOMMU
A unit translating and restricting device DMA addresses (Intel VT-d, AMD-Vi, Arm SMMU).
IORT
The Arm ACPI table that describes how devices connect to SMMUs and interrupt translation services.
IPI
Inter-Processor Interrupt.
ISO 9660 / UDF
File systems for optical media and installer images (ECMA-119 and ECMA-167 with the OSTA UDF specification).
IST
Interrupt Stack Table: x86-64 TSS entries that give certain exceptions a known-good stack.
Itanium C++ ABI
The C++ ABI used by GCC and Clang on x86-64, ARM64 (with small variations) and RISC-V: mangling, vtables, runtime support functions.
ITS
Interrupt Translation Service: the GICv3 component that turns device MSI writes into interrupts (LPIs).
JEDEC
The standards body for memory (DDR, LPDDR, SPD), flash storage (eMMC, UFS) and related interfaces.
Journaling
Writing intended changes to a log before applying them in place, so that a crash can be repaired by replaying or discarding the log.
KVM
Linux kernel virtualization support that lets QEMU run guests at near-native speed.
kvmclock
KVM's paravirtual clock: time information the hypervisor keeps up to date in guest memory.
LDS
Local Data Share: AMD's on-chip shared memory per CU.
Limine
A boot loader and boot protocol popular for hobby and research kernels.
Long mode
x86-64's 64-bit operating mode.
MADT
Multiple APIC Description Table: lists CPUs and interrupt controllers.
MBR
Master Boot Record: the legacy first sector of a disk with boot code and four partition entries.
MCFG
ACPI table giving ECAM base addresses for PCI Express configuration space.
MDIO / MII / RGMII
The Ethernet PHY management bus and the family of MAC-to-PHY data interfaces.
MFMA / WMMA
AMD matrix instructions (MFMA on CDNA, WMMA on RDNA3+); WMMA is also the name of NVIDIA's warp-level matrix API.
MMIO
Memory-mapped I/O: device registers accessed through memory addresses.
mmiotrace
A Linux tracing feature that logs every memory-mapped register access made by a driver.
MSI / MSI-X
Message Signalled Interrupts: a device raises an interrupt by writing to a special address.
MSR
Model-Specific Register (x86): CPU control registers accessed with dedicated instructions.
musl / newlib / mlibc
C libraries commonly ported to new operating systems (Linux-ABI oriented, embedded oriented, and designed for hobby systems respectively).
NCCL / RCCL
NVIDIA Collective Communications Library and its ROCm counterpart.
Nested virtualization
Running a hypervisor as a guest of another hypervisor.
NVLink / NVSwitch
NVIDIA's GPU interconnect and the switch chip that connects many GPUs all-to-all.
NVMe
NVM Express: the queue-based interface for PCIe SSDs.
Occupancy
Active warps/wavefronts on an SM/CU relative to the maximum, limited by registers, shared memory and block size.
OP-TEE
An open-source trusted OS running in the Arm TrustZone secure world.
OpenSBI
Reference implementation of the RISC-V SBI running in M-mode.
Option ROM
Firmware stored on an add-in card (for example a GPU's UEFI GOP driver).
OVMF
Open Virtual Machine Firmware: EDK II's UEFI build for QEMU and other virtual machines.
Panfrost / freedreno / etnaviv
Open drivers, largely based on reverse engineering, for Arm Mali, Qualcomm Adreno and Vivante GPUs.
PAT / MTRR
x86 mechanisms that set memory caching types (write-back, write-combining, uncached).
PCR
Platform Configuration Register: TPM register extended with hashes during measured boot.
PEI
Pre-EFI Initialization: the UEFI PI phase that initializes memory.
PHY
The physical-layer chip or block that converts a controller's digital signals to the electrical signals of a link (Ethernet, USB, PCIe, MIPI).
PI
UEFI Platform Initialization: the specification of firmware internals (SEC, PEI, DXE, BDS...).
Pin control (pinmux)
Selecting which internal function drives each SoC pin and setting its electrical properties.
PLIC / CLINT / ACLINT / AIA
RISC-V interrupt controllers: external interrupts (PLIC, APLIC), core-local timer and software interrupts (CLINT, ACLINT), and the Advanced Interrupt Architecture with MSI support (IMSIC).
PLT / GOT
Procedure Linkage Table and Global Offset Table: the indirection tables through which dynamically linked code reaches functions and data in shared libraries.
PM4
The packet format for AMD GPU command processors.
PMIC
Power-management IC: the chip that supplies and sequences a board's voltages, usually controlled over I2C or SPI.
POSIX
IEEE Std 1003.1 / The Open Group Base Specifications: the standard Unix-like system interfaces, shell and utilities.
PRM / TRM
Programmer's Reference Manual / Technical Reference Manual: the vendor documents that describe a chip's registers and programming model.
PSCI
Arm Power State Coordination Interface: firmware calls for CPU on/off, reset and power-off.
PTX / SASS
NVIDIA's virtual instruction set and the real machine code it is compiled to.
RCU
Read-Copy-Update: a synchronization technique letting readers run without locks while writers publish new versions.
RDMA
Remote Direct Memory Access: a NIC reads or writes a remote machine's memory without that machine's CPU.
Regulator
A controllable voltage supply (often inside a PMIC) that a driver must enable before its device works.
Reset vector
The address at which a CPU starts executing after reset.
Rock Ridge / Joliet
Extensions to ISO 9660 for Unix attributes and long names (Rock Ridge) and Unicode names (Joliet).
ROCm
AMD's open-source GPU compute platform (driver interfaces, runtime, compilers, libraries, tools).
RSDP / XSDT
ACPI root pointer and the extended root table listing all other ACPI tables.
SBI
RISC-V Supervisor Binary Interface: calls from the kernel to M-mode firmware.
SCMI
Arm System Control and Management Interface: messages through which an OS asks a system control processor's firmware for clocks, resets, power and performance changes.
SDHCI
The SD Association's standard register interface for SD and eMMC host controllers.
SEC
Security phase: the first UEFI PI phase after reset.
Secure Boot (PK, KEK, db, dbx)
UEFI signature verification of boot components using the Platform Key, Key Exchange Keys, the allowed database and the forbidden database.
Self-hosting
An OS that can build its own compiler, user space and kernel from source while running on itself.
shim
A small first-stage UEFI loader signed by Microsoft's UEFI CA, used by Linux distributions to boot under Secure Boot.
SIPI
Startup Inter-Processor Interrupt, part of the INIT-SIPI-SIPI sequence that starts x86 APs.
SM
Streaming Multiprocessor: NVIDIA's basic GPU core block.
SMBIOS
System Management BIOS: firmware tables describing the machine's hardware inventory.
SMM
System Management Mode: a special x86 CPU mode used by firmware, invisible to the OS.
SMMU
Arm System Memory Management Unit: Arm's IOMMU architecture (SMMUv3 on current systems).
SMP
Symmetric multiprocessing: the kernel runs on all CPUs.
SoC
System on a chip: CPU cores, memory controller and many peripherals on one die, typical of phones and single-board computers.
SPCR / DBG2
ACPI tables (Microsoft specifications) that name the serial console and debug port of a machine.
SPL / TPL
U-Boot's small early stages (secondary and tertiary program loaders) that run from on-chip SRAM and initialise DRAM.
SR-IOV
Single Root I/O Virtualization: a PCIe device presents lightweight virtual functions that can be assigned to virtual machines.
Subsystem ID
The PCI subsystem vendor and device IDs identifying the board or laptop maker's variant of a chip, used for quirks.
Sv39 / Sv48
RISC-V page-table formats with 39-bit and 48-bit virtual addresses.
System V ABI
The calling convention and binary interface used on x86-64 Unix-like systems and by most hobby kernels.
SystemReady
Arm's compliance programme for systems that boot generic OS images through UEFI.
Tensor Core / Matrix Core
GPU units executing small matrix multiply-accumulate operations at high throughput.
TF-A
Trusted Firmware-A: the reference secure-world firmware for Arm A-profile systems (PSCI, secure monitor).
Thermal zone
A region with a temperature sensor and trip points at which cooling or shutdown is triggered (ACPI or devicetree described).
TIS / CRB
The two TPM 2.0 host interfaces (FIFO-based TIS and Command Response Buffer) defined by the TCG PC Client Platform TPM Profile.
TLB shootdown
Invalidating stale translations on other CPUs after a page-table change, usually with IPIs.
TLFS
Microsoft's Hypervisor Top Level Functional Specification for Hyper-V guests.
TLS (thread-local storage)
Per-thread variables, located through a thread pointer register and laid out by the dynamic linker.
TPM
Trusted Platform Module: a security chip (or firmware) providing keys, random numbers and PCRs.
TSC
Time-Stamp Counter: x86 per-CPU cycle-based counter; "invariant" when its rate is constant.
TSS
Task State Segment: in x86-64, holds the stack pointers for privilege changes and the IST.
U-Boot
The most widely used open boot loader on embedded and SoC boards; also implements a UEFI subset.
UCSI
USB Type-C Connector System Software Interface: how an OS talks to the Type-C and Power Delivery controller.
UEFI
Unified Extensible Firmware Interface: the firmware interface used by modern PCs and many servers.
UFS
Universal Flash Storage: JEDEC's high-speed flash storage interface carrying SCSI commands.
Unwinder
Runtime code that walks stack frames using unwind tables, needed for C++ exceptions and backtraces.
USB4 / Thunderbolt
Tunnelling interconnects carrying USB, PCIe and DisplayPort over one cable.
usbmon / USBPcap
USB capture facilities on Linux and Windows whose captures Wireshark can decode.
UVC / UAC
USB Video Class and USB Audio Class: standard class protocols for webcams and audio devices.
V4L2
Video4Linux2: Linux's video capture and camera interface.
VBE
VESA BIOS Extensions: the legacy BIOS interface for graphics modes and linear framebuffers.
VFIO
Linux's framework for giving a device directly to user space or a virtual machine under IOMMU protection.
VID / PID
USB vendor ID (assigned by USB-IF) and product ID (chosen by the vendor).
virtio
OASIS standard for paravirtual devices (block, network, GPU) used by QEMU and other hypervisors.
VFS
Virtual File System: the kernel layer that lets many file systems share one interface.
VM exit
A transfer of control from a guest to the hypervisor caused by an intercepted event.
VMBus
Hyper-V's channel-based bus for paravirtual devices.
VMCS / VMCB
The per-virtual-CPU control structures of Intel VT-x and AMD-V.
VMX / SVM
Intel's and AMD's hardware virtualization extensions (VT-x and AMD-V).
Warp / wavefront
Group of GPU threads executing in lock step: 32 on NVIDIA; 64 on AMD CDNA; 32 or 64 on AMD RDNA.
Watchdog
A timer that resets the system unless software periodically services it.

The ACPI Watchdog Action Table describing a platform watchdog (Microsoft specification).

Xen's paravirtual devices and the mechanism by which guests share memory pages with each other.
