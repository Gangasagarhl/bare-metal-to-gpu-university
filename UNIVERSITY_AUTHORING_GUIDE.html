This document is not the university. It is the complete instruction set that Claude agents follow to build one: HTML lecture chapters, labs, forensic labs, exams and big projects that take a learner from "I have never programmed" to the skills of a senior engineer who can build an operating system for any hardware (from PCs and boards to distributed computers in server rooms), write GPU kernels in CUDA C++ and in ROCm/HIP, and build the software stacks of robots and drones. Honesty first: what this university can and cannot promise

The promise, stated kindly and truthfully. No curriculum by itself can guarantee that someone becomes a "senior engineer". Seniority is not a certificate. It is deep knowledge plus years of building, debugging, reviewing and owning real systems together with other people: shipping things that others depend on, being woken by an incident and fixing it, explaining a design to a sceptical colleague, mentoring a beginner, and being wrong in public and learning from it.

What a university can do is give the learner the knowledge, the habits and a very large amount of realistic practice. That is why this one is built around practice: every chapter has a lab, every course has forensic labs (diagnosing real-looking broken systems from evidence), exams that test doing rather than remembering, projects, design reviews and post-mortems, and the final years are mostly mega projects. A learner who completes it honestly will be ready to grow into a senior engineer much faster, and will have a portfolio that proves it. The last step still happens in real teams on real systems.

Hallucination: the honest engineering view. Agents that write chapters can produce text that sounds right and is wrong: an API name that does not exist, a register that belongs to another chip, a version number that was never released, a performance figure from nowhere. No wording in a prompt can eliminate this. "Please do not hallucinate" does not work on its own. Hallucination can only be made rare by a process: read the official source first and write down what it says (the source dossier), tag every claim with its source, compile and run every code listing with a named toolchain and paste the real output, have an independent agent fact-check against the sources, and keep a corrections log for whatever still slips through. Section 3 is that process, and it is the most important section of this guide.

Safety: read before any robot, drone, firmware or GPU lab.

  • Robots and drones can hurt people. Propellers cut skin and eyes; motors pinch fingers and can start unexpectedly; robot arms move with force. Every physical lab starts in a simulator; real hardware only after the simulator lab passes. Remove propellers for all bench tests; use a physical kill switch or arming switch; keep a clear zone around the vehicle.
  • LiPo batteries (lithium polymer) can catch fire if punctured, over-charged, over-discharged, short-circuited or charged unattended. Use a charger made for LiPo, a fire-resistant charging bag or container, never charge unattended, store at the storage voltage the battery maker documents, and dispose of damaged batteries according to local rules. The chapter quotes the battery and charger manufacturers' instructions, never numbers from memory.
  • Young learners (levels L0–L2) do physical labs only with adult supervision, at low voltages, with kits designed for their age. No mains-voltage work at any level of this university.
  • Drone flights are regulated in most countries (registration, where and how high you may fly, line of sight, flying near people or airports). Before any outdoor flight lab, the chapter tells the learner to read the current rules of their national aviation authority and to fly only where allowed, with permission of the land owner, and supervised. Agents never write rule details (heights, weights, distances) from memory: they cite the authority's current document or say "check your national aviation authority's current rules".
  • Firmware and bricking: develop firmware and kernels in QEMU with OVMF first (curriculum safety box); move to spare hardware only after the emulator milestone passes; never flash a machine the learner depends on; keep a recovery path (SD-card boot, USB recovery mode, external SPI programmer with a backup image).
  • GPU labs need a GPU. CUDA labs need an NVIDIA GPU; ROCm/HIP labs need an AMD GPU that appears in the ROCm documentation's compatibility list (HIP can also compile for NVIDIA GPUs, which is enough to learn the syntax but not AMD-specific performance). A cloud GPU instance is an acceptable alternative. Every GPU lab states its hardware requirement at the top, and labs that can run without a GPU (reading profiler output, forensic labs on recorded traces) say so.

1 · Purpose, audience, honest promise, how to use this guide

1.1 Purpose

The owner wants a "high-tech university" made of HTML pages, built by Claude agents, such that a kid who goes through it chapter by chapter, with labs, forensic labs, exams and big projects, can grow into a senior engineer able to do five things:

  1. Build an operating system for any hardware: normal PCs, development boards and SoCs, and distributed computers made of many servers.
  2. Write GPU kernels with CUDA in C++.
  3. Write GPU kernels with ROCm/HIP.
  4. Build a robot's OS and software stack so that it can perform activities.
  5. Build a drone's OS and flight software.

Along the way the learner must understand how hardware works (so that operating systems and kernels make sense), learn CUDA programming in C++ in detailed sub-chapters, meet real-life kid analogies everywhere, see the right pictures at the right places, have every jargon term explained in simple words with an analogy, get explicit transitions from one technology to the next, and read nothing invented: agents read the official documents before writing.

1.2 The two audiences of this guide

The owner (a human)

  • Reads sections 1, 2, 5 and 11 to understand what will be built.
  • Pastes the master prompt (section 15) into a Claude agent to start, and the per-chapter prompt to produce individual chapters.
  • Approves the plan the Dean agent proposes (which faculties first, how many chapters per batch).
  • Decides the open questions agents escalate: conflicting sources, safety calls, hardware purchases, whether a chapter may ship with an "untested on hardware" note.
  • Spot-checks published chapters with the QA record beside them (every chapter links to its record).

The agents (Claude instances)

  • Read this whole guide before their first task, and the sections named in their role card (section 12) before every task.
  • Read the Systems Curriculum sections that their course maps to (each course card in section 5 names them).
  • Follow the anti-hallucination protocol (section 3) literally: no dossier, no writing; no run, no code; no fact-check, no publishing.
  • Use the chapter template (section 7), the analogy maps (section 8), the diagram rules (section 9), the jargon rules (section 10) and the style guide (section 13) exactly.
  • Stop and ask the owner whenever this guide, the curriculum and the sources disagree, or a safety question arises.

2.3 Level rules every agent applies

  1. State the level in the chapter front matter (one of L0–L5, or a range of two adjacent levels such as L1–L2 when a chapter serves both).
  2. Never jump more than one level between consecutive chapters of a course. If a jump is needed, insert a bridge chapter (section 6).
  3. Prerequisites are explicit: chapter ids and course codes, never "you should know some C++".
  4. L0–L2 chapters pass the reading-level checks of 10.4 before publication.
  5. From L3 upwards, the analogy is still first: every chapter opens with a story hook and every major section opens with one analogy sentence, then the precise engineering text follows.
  6. Each level has a "can do" exam: the practical exams of the courses at that level test the "Can do" column of the table above.

3 · Anti-hallucination protocol (the most important section)

This section is the process that keeps the university true. It is written as rules with numbers so that agents, QA records and corrections logs can cite them ("violates AH-12"). Every role in section 12 must know it. The Fact-Checker's checklist (3.7) is built from it.

The three laws (short form; everything else in this section is detail):

  1. No dossier, no writing. A chapter is written only from a source dossier produced by reading the official documents first.
  2. No run, no code. A code listing ships only after it was compiled and run with the toolchain named in the dossier, and its output is pasted from that run.
  3. No independent check, no publishing. A chapter is published only after an independent Fact-Checker agent has checked every tagged claim against the dossier and the sources, and the QA record is complete.

3.1 The source hierarchy (AH-1 to AH-6)

When two sources could support a claim, use the highest tier available. When they disagree, the higher tier wins unless the dossier records a reason (for example a vendor errata document that corrects its own manual; the errata is part of tier 1).

3.2 "Read before write": the source dossier (AH-7 to AH-14)

For every chapter, the Source Researcher agent produces a source dossier before anyone writes a sentence of the chapter. The dossier is a separate HTML file (university/_dossiers/<chapter-id>.dossier.html) that the chapter links from its front matter. It is the only material the Author may use for technical claims.

  • AH-7 No outline, draft, diagram, lab or exam question for a chapter exists before its dossier is approved at gate G1 (12.3).
  • AH-8 Every document entry records: document title exactly as printed on the document; issuing body or authors; version or edition exactly as shown on the document (for example the version string on the title page or in the page footer; if none is shown, write "no version shown" and the date the agent accessed it); section titles and numbers used, as printed; short notes paraphrased in the Researcher's own words; quotes of at most two lines, in quotation marks, with the section; date accessed; how it was accessed (URL opened in this session, local PDF provided by the owner, printed book); and the tier (3.1).
  • AH-9 The dossier lists, per planned chapter section, the facts it may contain, each fact with a dossier fact id (F1, F2…) and its source entry. The Author's claim tags refer to these ids.
  • AH-10 The dossier contains a "not found" list: facts the outline wanted but the sources did not support. These may appear in the chapter only inside an "unverified" box (AH-17).
  • AH-11 The dossier records the toolchain versions the Lab Engineer actually has installed (compiler, CUDA Toolkit, ROCm, driver, ROS 2 distribution, PX4 or ArduPilot release, QEMU, simulator) as printed by the tools themselves (for example the version line printed by the compiler). The chapter's code must be built with exactly these.
  • AH-12 When the official document changes title or structure between versions, the dossier records the title of the version read. Example observed while writing this guide: the NVIDIA page at the long-standing "CUDA C++ Programming Guide" address showed the title "CUDA Programming Guide" with a version 13.x number in October 2026. The dossier records what the page shows, and the chapter cites that.
  • AH-13 Quotes stay short (two lines or less) and are used only when the exact wording matters (a definition, a rule, a warning). Everything else is paraphrased. Licensed text is never copied in bulk.
  • AH-14 The dossier is reviewed at gate G1 by the Fact-Checker (completeness: does every outline item have a source?) before the Author starts.

3.3 Claim tagging (AH-15 to AH-16)

  • AH-15 Every technical statement in a chapter carries a source tag: a small superscript link to the chapter's Sources list, showing the dossier document id and section, for example <sup class="src"><a href="#src-D1">D1 §2.3</a></sup>. It is small and unobtrusive (hidden in plain sight) but always inspectable: the learner can click it and the Fact-Checker can verify it. Kid-level chapters (L0–L1) may group tags at the end of a paragraph rather than after each sentence.
  • AH-16 What counts as a "technical statement": any fact about hardware, software behaviour, an API, a number, a standard, a protocol, history, a person's work, or a performance property. Analogies, encouragement, exercise instructions and the chapter's own definitions of its exercises do not need tags. When in doubt, tag.

3.4 Forbidden content and the "unverified" box (AH-17 to AH-20)

AH-17 Forbidden unless the dossier contains the fact with its source:

  • Invented or "probable" API names, function signatures, flags, command-line options, environment variables, configuration keys, ROS 2 parameter names, PX4/ArduPilot parameter names, MAVLink message names.
  • Invented register names, bit positions, addresses, opcodes, instruction mnemonics.
  • Invented numbers: sizes, counts, latencies, bandwidths, clock rates, power figures, prices, dates.
  • Invented version numbers and release names.
  • Invented URLs (see AH-30) and invented document titles, section numbers or page numbers.
  • Invented performance figures ("this kernel is 10× faster") that were not measured in this university's own lab run, recorded in the QA record.
  • Invented quotes and invented attributions ("as Linus Torvalds said…").
  • Padding that pretends to knowledge: "it is believed", "experts say", "typically around", "studies show", "it is well known that". Either cite, or do not say it.

AH-18 When a fact cannot be verified but the chapter genuinely needs to mention it, write it inside an unverified box with the document to check. Never guess. Never silently drop a needed fact either: the box tells the learner and the next agent exactly what is missing.

  • AH-20 Hedging words do not replace verification. "Usually", "often", "about" are allowed only when the source itself says so (and the tag points to where).

3.5 Hardware numbers (AH-21 to AH-23)

  • AH-21 Numbers about hardware (core counts, SM or CU counts, memory sizes, bandwidths, clock rates, cache sizes, register-file sizes, TDP, sensor ranges, motor ratings, battery ratings) come only from the vendor's specification sheet or manual for a named product ("NVIDIA <exact product name> datasheet", "the <exact IMU part number> datasheet, section …"), recorded in dossier part F.
  • AH-22 Never write "typical" values that are not attributed to a named product and its document. If the chapter wants to give a sense of scale to a kid, use a named product with its tagged number, or the learner's own measurement from the lab ("run deviceQuery and write your GPU's number here").
  • AH-23 Measured numbers (bandwidth from a lab run, a kernel's time, a control loop's jitter) are labelled as measurements: which machine, which tool, which version, which date, and they live in the QA record. They are never presented as the product's specification.

3.6 Code rules (AH-24 to AH-29)

  • AH-24 Every code listing in a chapter, lab, exam answer key or project starter kit is compiled and run by the Lab Engineer/Tester agent with the exact toolchain recorded in dossier part E. The build command shown in the chapter is the one that was actually used, written in the form the official documentation gives (for example nvcc file.cu -o file for CUDA, hipcc file.cpp -o file for HIP, colcon build for a ROS 2 workspace), with any extra flags the run needed.
  • AH-25 Output is pasted from the real run, unedited except for trimming, which is marked with "[…]". Machine-specific lines (paths, user names) may be replaced with placeholders, marked as such. The QA record stores the full log.
  • AH-26 No listing ships untested. If the required hardware is not available, the chapter shows a clearly marked "untested on hardware" note and gives the simulator or emulator result instead (QEMU for kernels and firmware; Gazebo or another named simulator for robots; PX4 or ArduPilot SITL for drones; a HIP build for the NVIDIA back end when only an NVIDIA GPU exists, with the AMD run marked untested). The note names what is untested and what would be needed.
  • AH-27 Every listing compiles without warnings at the warning level recorded in the dossier, passes the sanitizer or checker that exists for it (AddressSanitizer and UndefinedBehaviorSanitizer for host C++; Compute Sanitizer for CUDA; the corresponding ROCm tooling for HIP where available), and checks every API error code (CUDA and HIP calls are wrapped in an error check; the exemplar in section 14 shows the pattern).
  • AH-28 Listings are complete enough to build (no "…" inside code that is presented as buildable). Fragments are allowed if labelled "fragment, not buildable alone" and if the complete file is in the lab folder and was built.
  • AH-29 Every API, type, macro and flag used in a listing appears in the dossier with its documentation source. The Fact-Checker compares the listing's identifiers against the dossier (checklist item FC-9).

3.7 Independent Fact-Checker pass, Editor pass and the QA record (AH-30 to AH-36)

The Fact-Checker is a different agent instance from the Author, started with no access to the Author's reasoning: it sees only the draft, the dossier, the sources and this guide. It checks; it does not rewrite. Its findings go back to the Author, who fixes and resubmits.

Fact-Checker checklist (FC items, copied into every QA record)

  1. FC-1 Every technical statement has a source tag (AH-15).
  2. FC-2 Every tag resolves to a dossier fact and that fact really appears in the cited section of the cited document (open the document; do not trust the dossier blindly for at least a random 25 % sample, and for 100 % of numbers, names and code identifiers).
  3. FC-3 Every source is tier 1–5 and appropriate for the claim (AH-1, AH-2).
  4. FC-4 Document titles, versions and section titles are written exactly as the dossier recorded them from the document.
  5. FC-5 No forbidden content (AH-17): scan for API names, flags, registers, numbers, versions, URLs, performance figures, quotes, and padding phrases.
  6. FC-6 Hardware numbers only from named spec sheets (AH-21 to AH-23).
  7. FC-7 Every unverified item is in an unverified box and listed in the QA record (AH-18, AH-19).
  8. FC-8 Every code listing has a Lab Engineer run log in the QA record with the toolchain of dossier part E; output in the chapter matches the log (AH-24, AH-25).
  9. FC-9 Every identifier in every listing (functions, types, macros, constants, flags, parameters, topics, message names) appears in the dossier with a source (AH-29).
  10. FC-10 Every URL in the chapter was opened by an agent in a recorded session and loaded (AH-30).
  11. FC-11 Diagrams: labels match the text's terms; nothing in a diagram contradicts the text or the sources (9.4).
  12. FC-12 "Where the analogy breaks" exists and is correct: the analogy does not smuggle in a false technical claim (section 8).
  13. FC-13 Quiz answers, lab expected observations and forensic-lab answer keys are consistent with the sources and with the Lab Engineer's runs.
  14. FC-14 Safety boxes present wherever the safety rules of the "Honesty first" section apply; hardware requirements stated for GPU labs.
  15. FC-15 Cross-references (chapter ids, course codes, curriculum section ids and milestone ids) exist and point to the right place.
  • AH-30 URL policy. A chapter (and this guide) contains a URL only if an agent actually opened it in a recorded session and it loaded with the expected content. Otherwise the document is cited by title and issuing body only. URLs from memory are forbidden even when they "look right". The QA record lists every URL with the date it was opened and the session or run id.
  • AH-31 The Editor pass comes after the fact-check: voice, structure, reading level for L0–L2 (10.4), template compliance (section 7), analogy rules (8.2). The Editor must not change technical content; any change that touches a tagged sentence goes back to the Fact-Checker for that sentence.

  • AH-33 A chapter is published only with a filled QA record: all gates passed, named agents and run ids, dates, the FC checklist with results, the Lab Engineer logs, the list of unverified boxes and owner approvals, the list of URLs opened.
  • AH-34 If the Fact-Checker finds more than three factual errors in one draft, the draft goes back to the dossier stage: errors of that density mean the Author wrote beyond the dossier.
  • AH-35 The Author never "fixes" a Fact-Checker finding by removing the tag while keeping the claim.
  • AH-36 Agents never mark their own work as checked. Author, Fact-Checker and Editor are distinct agent runs.

3.8 The corrections log (AH-37 to AH-39)

  • AH-37 Every chapter has a public corrections log at the end of its QA record and linked from the chapter footer: date, chapter version, what was wrong, what it now says, the source that proves the correction, who found it (learner, owner, agent), and which other chapters were checked for the same error.

3.9 Agent self-check before handing anything over

Each agent runs this list on its own output before handing it to the next gate. It does not replace the Fact-Checker; it reduces rework.

  1. Did I use anything not in the dossier? (If yes: add it to the dossier with a source, or remove it, or put it in an unverified box.)
  2. Did I write any name, number, version, flag, register or URL from memory?
  3. Can every code identifier be found in the dossier?
  4. Did I paste output that I did not see in a real run log?
  5. Did I use a hedge word to cover uncertainty?
  6. Does every analogy have its "where it breaks" note?
  7. Did I name the hardware requirement and the safety rules for every lab?

3.10 Why this works (and its limits)

The process attacks each way an invented fact can enter: memory is replaced by reading (dossier), unsupported sentences become visible (tags), code is grounded in execution (runs), a second agent with no stake checks (fact-check), and residual errors are captured and propagated (corrections log). It does not make errors impossible: a dossier can misread a source, a document can itself be wrong, a run can pass by luck. That is why the corrections log and re-verification exist, and why the university tells learners openly: check the source yourself when it matters. Teaching learners to do that is part of becoming a senior engineer.

5.2 Credits, years and semesters

  • One credit hour = about 30 hours of total learner work (reading, labs, forensic labs, quizzes, project time). A 4-credit course is therefore about 120 hours. The curriculum's timeline ranges (18.1) were used to size the L3–L4 courses; they are estimates, not promises, and the course page says so.
  • Semester = a planning unit of about 15–18 credits for a full-time learner; part-time learners take half. Kids in the Foundation year go at their own pace, in short sessions.
  • Year 0 is the Foundation year (L0–L1). Years 1–5 build to L4. Years 6–7 are the advanced year and the residency (L4–L5), dominated by mega projects.
  • Honest pacing note (on every course page): a full-time adult learner might move through Years 1–6 in five to eight years; a kid starting at 11 who studies part-time grows with the school over their teenage years and continues into university age. Nobody is "late".

6 · Transitions from one technology to the next

Learners get lost not inside a technology but between technologies: the day C++ becomes CUDA, the day one GPU becomes eight, the day the simulator becomes a real robot. The university handles every such step twice: a dedicated bridge chapter (BR-01 to BR-10) placed exactly where the step happens, and a mandatory Transition box in every chapter that introduces something new relative to an earlier technology.

6.1 The Transition box (required in chapters)

Every chapter has a Transition box (template position 13, 7.3). It answers four questions in this order, each in one to three sentences, with source tags for every technical claim:

  1. Where you came from: the earlier technology or chapter (by id).
  2. What carries over: knowledge and habits that still apply unchanged.
  3. What changes: the differences that will bite, most dangerous first.
  4. What comes next: the next chapter and how today's idea will be used there.
Transition box (example from F6-04)

Where you came from: SP102 taught you functions and std::vector on the CPU. What carries over: the same C++ syntax, types and functions; host code is ordinary C++. What changes: the kernel runs on the GPU and cannot read your std::vector directly; data must be in GPU memory first; a launch returns before the GPU finishes; errors arrive as return codes you must check. What comes next: F6-05 shows how to check every call and find bugs with Compute Sanitizer.

(Source tags omitted in this guide's example; in a chapter each claim is tagged.)

6.2 The ten bridges

Each bridge chapter follows the full chapter template, is at most one level above the chapters before it, has its own lab, and is listed as a prerequisite of the first chapter after the step.

BR-01 From C++ to CUDA C++: the same language, a second place to run L2
Placement
Between SP203 and CU201 (prerequisite of F6-01).
Carries over
C++ syntax, types, functions, templates (within the limits CUDA documents for device code), headers, build discipline, testing habits, RAII for host-side resources.
Changes
Two processors and two memories (host and device); function execution-space qualifiers; the execution configuration of a launch; explicit allocation and copies (or managed memory with its own costs); asynchronous execution; error handling through return codes and a "last error"; many standard-library facilities and exceptions are not available in device code (the dossier cites the Programming Guide's C++ language support section for the exact list); a new compiler driver (nvcc) that splits host and device code.
Traps
Reading results before the GPU finished; forgetting the bounds check; passing a host pointer to a kernel; not checking errors so failures look like zeros.
Lab
Rewrite a CPU vector-add program step by step into CUDA C++, checking each step; deliberately break it three ways and read the errors.
BR-02 From CUDA to HIP: a second kitchen building with the same recipes L3
Placement
Before F7-01.
Carries over
The programming model (grids, blocks, threads, shared memory, streams, events); most runtime calls have HIP counterparts with similar names (each mapping cited from the HIP documentation's porting guide and API reference); kernel code is largely the same C++.
Changes
API prefixes and headers; the hipcc driver and the ROCm toolchain; the warp size is not a constant 32 (64 on CDNA; 32 or 64 on RDNA); lane masks become 64-bit; LDS instead of "shared memory" in AMD's documents; different profilers; hardware support listed in the ROCm compatibility matrix; HIP can also target NVIDIA through the CUDA back end.
Traps
Hard-coded 32; 32-bit ballot masks; tuning parameters copied from NVIDIA; assuming a CUDA library has a drop-in HIP equivalent without checking.
Lab
hipify a CU201 lab, run it on both back ends, fix the warp-size assumption planted in the starter code.
BR-03 From CPU threads to GPU warps and wavefronts L2–L3
Placement
Between F6-03 and F6-04 for readers coming from SP203; referenced again in F7-08.
Carries over
Data races, the need for synchronization, atomics, the idea of a memory model, Amdahl-style reasoning about serial parts.
Changes
CPU threads are few, heavy and scheduled by the OS; GPU threads are many and light, created by the launch and scheduled by hardware in groups (warps of 32 on NVIDIA, wavefronts of 64 on AMD CDNA); divergence inside a group costs time; there are no OS context switches per GPU thread; synchronization is cheap inside a block and expensive or unavailable across the whole grid; memory access patterns of the whole group matter (coalescing).
Traps
Using a mutex-like spin lock across threads of the same warp; expecting one GPU thread to be fast; ignoring divergence.
Lab
The same histogram written with std::thread and with CUDA; measure and explain the difference with the kitchen analogy and the profiler.
BR-04 From one GPU to many GPUs to many machines L4
Placement
Before F8-01.
Carries over
Kernels, streams and events; measurement protocol; roofline thinking applied to links instead of memory.
Changes
Data must move between devices over links of very different speeds (PCIe, NVLink, xGMI, network); topology decides performance; collectives replace point-to-point thinking; failures of one process stop everyone; time is dominated by communication unless overlapped.
Traps
Assuming all GPU pairs are equally connected; benchmarking with one message size; deadlocks from mismatched collective calls.
Lab
F1 peer bandwidth matrix, then predict a ring all-reduce time with the alpha-beta model before running it.
BR-05 From bare metal to an RTOS to Linux L3
Placement
Inside OS305 (between F3-38 and F3-39), referenced by RB304 and DN302.
Carries over
Interrupts, timers, drivers, memory maps, the debugger, the discipline of measuring timing.
Changes
Bare metal: one loop, you own everything. RTOS: tasks with priorities, a scheduler, kernel objects, deterministic timing, small memory, usually no MMU-based process isolation. Linux: processes with virtual memory, rich drivers and networking, much larger footprint, real-time behaviour only with configuration (PREEMPT_RT) and care.
Traps
Blocking calls inside interrupt handlers; priority inversion; assuming Linux is real-time by default; dynamic allocation in time-critical paths.
Lab
The same sensor-to-actuator loop implemented bare metal, on Zephyr or FreeRTOS, and on Linux with and without PREEMPT_RT; compare measured jitter.
BR-06 From x86 to ARM to RISC-V L4
Placement
Before F4-23.
Carries over
The arch-neutral kernel core; the platform checklist (curriculum 9.1); C++ code with correct atomics.
Changes
Privilege models (rings, exception levels, M/S/U modes); boot contracts (UEFI and ACPI, devicetree, SBI); interrupt controllers (APIC, GIC, PLIC/AIA); memory ordering (x86's strong ordering versus weakly ordered Arm and RISC-V); cache maintenance for DMA on non-coherent devices.
Traps
Missing barriers; hard-coded page sizes; assuming an APIC; endianness of device and on-disk data (curriculum 10.2).
Lab
Fill the checklist for the three QEMU machines and run the arch-neutral test suite on each.
BR-07 From a PC to an SoC board L4
Placement
Before F4-31; referenced by RB403 and DN302.
Carries over
Drivers written against specifications; the universal method; the devicetree knowledge from DR402.
Changes
No enumeration; boot ROMs and vendor boot chains; explicit clocks, resets, pins and regulators; non-coherent DMA; documentation quality varies by vendor (curriculum 11.1, 11.4).
Traps
A device that "reads zeros" because its clock is off; wrong bus-address translation; writing to on-board storage without a recovery path.
Lab
Boot a known-good image on the board, dump its devicetree, and write the bring-up plan before writing any code.
BR-08 From simulator to real robot or drone (sim-to-real) L3–L4
Placement
Before the first real-hardware lab of RB304 and DN401; revisited in F9-71.
Carries over

Changes

Description. 8.2 Analogy rules

  1. Analogy first. Introduce the analogy before the precise term, in the story hook or the first paragraph of the section.
  2. Map every part explicitly. Use a small mapping list or table: "helper = thread; row = warp; table = shared memory". No silent mappings.
  3. State where it breaks. Every chapter has the "Where the analogy breaks" section with at least two concrete points; the Fact-Checker checks they are correct (FC-12).
  4. Never let the analogy replace the precise definition. Every term the analogy introduces is followed by its precise, tagged definition.
  5. Keep the same analogy across a course (and across the faculty, as registered above). A chapter that needs a new mapping asks the Dean to register it.
  6. Age-appropriate. No violence, danger glorification, romance, fear, or adult themes; analogies a 10-year-old understands at L0–L1.
  7. Culturally neutral. Everyday activities common to many cultures (cooking, school, walking, cycling, friends sharing food); no religious or political content, no national sports or holidays, no brand names, no assumptions about family structure or wealth; names in stories are varied and not stereotyped.
  8. One analogy per idea per chapter. Do not mix worlds inside one explanation (no "the GPU kitchen's principal").
  9. Analogies carry no hidden technical claims. If the analogy implies a number or a behaviour ("the pantry is 100 times farther"), that claim must be tagged or removed.
  10. Engineer-level chapters keep it short: one paragraph, then the specification.

9 · Diagram and picture rules

9.1 Rules

  1. Inline SVG only. No external images, no bitmap files, no embedded data URIs of photos.
  2. No fabricated photos or realistic renderings of real products. A diagram may show a simplified block diagram of a named product only if it is derived from that vendor's own published block diagram, and the caption says "simplified, after <document title, section>".
  3. Theme-aware. Colours only through the SVG classes of the canonical style block (.sv-*, which use the CSS colour tokens), so light and dark modes both work. No hard-coded colours in SVG attributes.
  4. Numbered, captioned, described. Every figure is a <figure> with an id, an SVG with role="img", a <title> and a <desc> (the text alternative, describing what the diagram shows, not just its name), and a <figcaption> starting "Figure n."
  5. Labels match the text. The same words as the chapter (and the glossary). If the text says "shared memory", the diagram does not say "scratchpad".
  6. Placement. Directly after the paragraph that introduces the concept, and referenced from the text.
  7. Readable. Text in SVG at least 11px at the design width; the figure scrolls horizontally on phones rather than shrinking below that (the .svgbox wrapper with a minimum SVG width).
  8. Meaning never by colour alone. Use labels, shapes or patterns as well (dashed lines, icons, text).
  9. Truthful. No decorative diagrams. Every element represents something the text explains. Sizes and proportions do not suggest numbers they do not have (say "not to scale" when relevant).
  10. Sources. A diagram that encodes technical facts carries source tags in its caption, like text.

10 · Jargon rules

10.1 Rules in chapters

  1. Defined at first use, in place. A term appears in the chapter's Jargon box before (or at) its first use, and in the text its first occurrence is bold.
  2. Four parts, always in this order: simple words → analogy → precise definition → source tag.
  3. One meaning per word. Where a word has two meanings in the university ("kernel" in F3 and F6, "thread" on CPUs and GPUs, "shared memory" between processes and on a GPU), the glossary has separate entries with qualifiers ("kernel (GPU)", "kernel (operating system)") and every chapter that uses one meaning mentions the other once.
  4. Acronyms are expanded at first use in each chapter, even if expanded elsewhere.
  5. No undefined jargon in L0–L2 chapters. The Editor lists every technical word and checks it is defined in the chapter or in a prerequisite chapter's Jargon box (linked).
  6. Vendor terms are marked as vendor terms ("NVIDIA calls this a warp; AMD calls the similar group a wavefront").

10.4 Reading-level checks for L0–L2 chapters

  1. Short sentences. L0: average about 12 words, rarely over 18; L1: about 15; L2: about 20. The Editor reports the average and the longest sentences in the QA record.
  2. One idea per sentence at L0–L1.
  3. Everyday words first. Prefer "use" to "utilise", "start" to "initialise" in Layer 1 text; the technical word comes after it is defined.
  4. Paragraphs of at most four sentences at L0–L1.

11.2 Forensic lab template

A forensic lab gives the learner evidence from a broken or slow system and asks them to find the cause, as an engineer does with a boot trace, a crash dump or a profile. The idea comes from the project in which this university was conceived: analysing Windows boot traces (ETL files) to find which driver made a boot slow. Evidence packs are generated by the Lab Engineer from real runs (deliberately broken systems in emulators, simulators or on lab hardware), never invented by hand; the answer key records how the evidence was produced.

12.4 Working in parallel without contradictions

  1. Dependency order. Chapters are built in prerequisite order within a course; across courses, a chapter may start its dossier early but cannot pass G2 until its prerequisite chapters have passed G6 (so terms and analogies are settled).
  2. Shared registries are single sources of truth: the glossary, the analogy registry (section 8 and analogies.html), the style block, the source registry (section 4), the toolchain record (one per lab machine). Agents read them at the start of every task and never keep private copies.
  3. Write locks. Only the Integrator writes to the glossary and catalogue; only the Dean writes to the analogy registry and blueprint. Other agents submit proposals.
  4. Batching. The Dean assigns batches of related chapters (for example F6-01 to F6-04) to one Researcher–Author pair for consistency, and different batches to different pairs in parallel.
  5. Cross-chapter consistency search. Before publishing, the Integrator searches the whole site for each new glossary term and each numeric fact in the chapter, and flags conflicts.
  6. Same facts, same source. When two dossiers cover the same fact, the later Researcher reuses the earlier dossier's entry (with a fresh check of the source) rather than citing a different document.

12.7 When sources disagree

  1. Record the conflict in the dossier (part D) with both sources, their tiers and versions.
  2. Prefer the higher tier; within tier 1, prefer the more specific and more recent document (errata over the manual it corrects; the product datasheet over a family overview).
  3. If the conflict is about behaviour, the Lab Engineer tests it on the recorded hardware and toolchain; the chapter reports what was observed, labelled as an observation (AH-23), and cites both documents.
  4. If unresolved, the chapter presents both statements in an unverified box and the Dean escalates to the owner.
  5. Never silently pick one.

12.8 Re-verification when vendors update their documents

  • Every chapter records the document versions it used. On a schedule set by the owner (suggested: every six months for fast-moving areas such as CUDA, ROCm, ROS 2, PX4 and ArduPilot; yearly for specifications and textbooks), the Source Researcher re-opens each source and compares versions.
  • Triggers for immediate re-verification: a new major toolkit release (CUDA Toolkit, ROCm, a ROS 2 distribution, a PX4 or ArduPilot release), a renamed or restructured document (example observed while writing this guide: the CUDA programming guide's page title and structure changed), a learner's correction report, or a broken URL.
  • Re-verification re-runs the labs with the new toolchain where the chapter targets the current release, or pins the old release explicitly ("this chapter uses ROCm version X as recorded") where re-running is not possible; the catalogue shows "needs re-verification" until done.
  • Results go into the corrections log, even when nothing changed ("re-verified against version Y on date Z: no changes").

13 · Style guide

13.1 Voice

  • Warm, precise, encouraging. Speak to the learner as "you". Praise effort and method, not talent. Mistakes are normal and useful ("this error message is your friend").
  • Honest. Say when something is hard, when the university simplifies, when a fact is unverified, when hardware is required.
  • Never condescending. Simple does not mean childish; a 10-year-old can handle real ideas told clearly.
  • No hype. No "revolutionary", "blazing fast", "magic". Describe what happens and measure it.
  • Inclusive. Varied names and roles in stories; no assumptions about gender, culture, family or wealth.

13.3 Units and number formats

  • SI units with a space between number and unit: 3.3 V, 20 mA, 10 ms, 1 kHz, 25 °C.
  • Binary prefixes for memory sizes where the quantity is binary: KiB, MiB, GiB (as the curriculum does); decimal prefixes (kB, MB, GB) only where the source uses decimal units (storage capacities, network rates), and say which.
  • Bits versus bytes: b for bits, B for bytes; Gbit/s versus GB/s spelled out at L0–L2.
  • Thousands separators: commas in running text (10,000), none in code. Decimal point is a full stop.
  • Percentages written as "80 %" (as in the curriculum).
  • Ranges with an en dash: 2–4 hours.
  • Dates in ISO form: 2026-10-09.
  • Hexadecimal written 0x1F in text and code; binary 0b1010 where the language supports it, otherwise "1010 in binary".
  • Multiplication in prose with ×; in code with *.
  • Every hardware number follows AH-21 to AH-23.

13.4 Code style

  • Language version: the C++ standard version used by each listing is stated in the dossier and the build command (for example a -std= option); the default for host code is a recent ISO C++ standard supported by all recorded toolchains, chosen by the Dean.
  • Modern C++: RAII for every resource; containers and spans instead of raw arrays in host code; const by default; no using namespace std; in headers; no raw new/delete in learner-facing code except in the chapters that teach them; follow the C++ Core Guidelines where they apply.
  • CUDA and HIP conventions: kernels named with a verb in lowerCamelCase (vecAdd, as in the CUDA Programming Guide's example); device pointers prefixed d (dA) and host buffers h (hA); every runtime call checked through a small checking function; every launch followed by a check of the last error; bounds check in every kernel whose grid can exceed the data; index arithmetic that cannot overflow for the sizes used (state the limit or use 64-bit indices); no hard-coded warp size in portable code (use the documented built-in or query).
  • Freestanding and kernel code follows the curriculum's rules (1.2): no exceptions or RTTI, typed register wrappers, comments naming the specification and section for each register (curriculum rule 9).
  • Formatting: four-space indentation, braces on their own line for functions and on the same line for control statements (as in the exemplar), line length at most 100 characters; a single clang-format configuration file published by the Integrator.
  • Comments explain why, not what; the line-by-line table carries the "what" for learners.
  • Listings in HTML are escaped (&lt;, &gt;, &amp;) and placed in <pre><code>; the Integrator checks that the escaped listing matches the tested source file byte for byte after unescaping.

13.5 Naming

  • Chapter ids, course codes and file names exactly as in section 5 and 7.1.
  • Product and document names exactly as their owners write them (CUDA, ROCm, HIP, PX4, ArduPilot, ROS 2, NuttX, ChibiOS, Zephyr, FreeRTOS, MAVLink); trademarks are not decorated with symbols in running text.
  • Headings in sentence case.

13.6 Accessibility

  • Colour contrast aims at WCAG 2 level AA in both light and dark themes (the token palette of this guide is the starting point; the Accessibility reviewer checks new colours).
  • One h1 per page; headings never skip levels.
  • Every SVG has role="img", <title> and <desc>; every figure has a caption.
  • Tables have header cells; wide tables scroll inside .tw wrappers; no layout tables.
  • Link text says where it goes ("CUDA Programming Guide, section 2.3"), never "click here".
  • No meaning by colour alone; no information only on hover.
  • Text resizes without breaking layout; the page works at 320 px width.
  • Language attribute set; abbreviations expanded at first use.

13.7 No JavaScript

Chapters, labs, exams and all university pages contain no scripts, no event handlers and no interactive widgets. Answers are placed in separate sections or files instead of collapsible elements. If the owner later allows JavaScript, the Dean first updates this guide (which features, which pages, accessibility and offline behaviour), then the change is applied.

1 · Story hook

Analogy

Imagine a school kitchen that must make one million sandwiches before lunch. The head chef is brilliant. She can cook anything. But she has only two hands. One sandwich at a time, she would still be working next week.

Now imagine a huge hall next door, full of thousands of helpers. Each helper is not a great chef. Each one only knows how to follow a simple recipe card. But if every helper makes a few sandwiches at the same time, the million sandwiches are done before the bell rings.

A computer has both. The CPU is the head chef. The GPU is the hall of helpers. This chapter is about the hall.

2 · What you will be able to do

  • Explain, with the kitchen analogy and with precise words, why a GPU can finish some jobs much faster than a CPU.
  • Name the parts of the CUDA thread hierarchy: thread, block, grid, and explain what a warp is.
  • Compute which element of an array a given GPU thread works on.
  • Read, build and run a complete CUDA C++ vector-add program and explain every line.
  • Say where the kitchen analogy stops being true.
Jargon box
Thread (GPU)
Simple words: one worker on the GPU doing one small part of the job. Analogy: one kitchen helper. Precise: the smallest unit of execution in CUDA; each thread runs the kernel's code with its own built-in index variables such as threadIdx.D1 §2.3 Not the same as a CPU thread (see SP203).
Kernel (GPU)
Simple words: the instructions every GPU worker follows. Analogy: the recipe card handed to every helper. Precise: a function marked __global__ that is launched from the host and executed on the GPU by many threads in parallel.D1 §2.3 Not the same as an operating-system kernel (F3).
Block (thread block)
Simple words: a team of GPU workers that can share a table and wait for each other. Analogy: the helpers around one table. Precise: a group of threads identified by blockIdx, with blockDim threads, that can cooperate through shared memory and synchronization.D1 thread hierarchy
Grid
Simple words: all the teams working on one job. Analogy: every table in the hall for this order. Precise: the set of all thread blocks created by one kernel launch.D1 thread hierarchy
Warp
Simple words: a small group of GPU workers that always do the same step together. Analogy: a row of helpers who move in step. Precise: a group of 32 threads that NVIDIA GPUs schedule and execute together.D1 SIMT AMD's similar group is the wavefront (F7-08).

3 · The idea in pictures

4 · Layer 1 — the kid explanation

Some jobs are made of many small, similar pieces. Adding two long lists of numbers is like that. Each pair of numbers can be added on its own. Nobody has to wait for anybody else.

The CPU is great at hard, twisty jobs. The GPU is great at jobs with many similar pieces. So we give the GPU the long lists. We hand every helper the same recipe card: "take your number from list A, take your number from list B, add them, write the answer in list C".

How does a helper know which number is "theirs"? Every helper has a number, like a ticket. The helpers sit at tables. Each table has a number too. A helper works out their ticket from their table number and their seat number. You will do that calculation yourself in the worked example.

5 · Layer 2 — the student explanation

In CUDA, the function every GPU thread runs is a kernel, marked with __global__.D1 §2.3 When the host (the CPU side of the program) launches a kernel, it says how many blocks to create and how many threads each block has; together the blocks form the grid.D1 thread hierarchy Inside the kernel, each thread can read built-in variables: threadIdx.x (its position inside its block), blockIdx.x (its block's position in the grid) and blockDim.x (the number of threads per block).D1 §2.3 Combining them gives a unique global index:

int i = blockIdx.x * blockDim.x + threadIdx.x;

The CUDA Programming Guide's own vector-add example computes this index and then checks it against the vector length before touching memory, because the grid may contain more threads than there are elements.D1 §2.3 Threads are executed by the hardware in groups of 32 called warps.D1 SIMT

6 · Layer 3 — the engineer's depth

The GPU and CPU have separate memories in this model: the kernel can only use pointers to device memory, so the host allocates device buffers, copies inputs in, launches the kernel, and copies results out.D2 memory management Kernel launches are asynchronous with respect to the host; a later blocking call, such as a device-to-host copy, waits for the kernel to finish.D2 asynchronous execution Errors from a launch are reported through the runtime's error state, which is why the listing checks the last error immediately after the launch.D2 error checking

For the curious

The way a warp's memory requests combine into transactions (coalescing) decides how fast this kernel can run. That is F6-08's topic.

7 · How the hardware actually does it

The blocks of a grid are distributed over the GPU's streaming multiprocessors (SMs); each SM runs warps of threads and switches between warps that are ready, which hides the waiting time of memory accesses.D1 hardware implementation HW301 (F1-56, F1-57, F1-60) explains this hardware in depth. How many SMs your GPU has is printed by the device-query lab (F6-07) and stated in the vendor documentation for your exact product; this chapter does not quote a "typical" number (AH-22).

8 · Worked example

You want to add two arrays of n = 1000 numbers with 256 threads per block.

  1. Blocks needed: we round up, so that no element is left out: (1000 + 256 − 1) / 256 = 1255 / 256, which is 4 in integer division (4.90… rounded down). So 4 blocks.
  2. Threads created: 4 × 256 = 1024. That is 24 more than the 1000 elements.
  3. Thread 3 of block 2 computes i = 2 × 256 + 3 = 515, so it adds element 515.
  4. Thread 255 of block 3 computes i = 3 × 256 + 255 = 1023. Since 1023 is not less than 1000, the bounds check stops it: it does nothing. Without the check, it would write past the end of the arrays.

9 · Code walk-through

Listing 1 — vec_add.cu, written in the style of the CUDA Programming Guide's vector-add example (same index formula and bounds check), extended with allocation, copies, error checking and a correctness check.

#include <cstdio>
#include <cstdlib>
#include <vector>
#include <cuda_runtime.h>

__global__ void vecAdd(const float* A, const float* B, float* C, int n)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        C[i] = A[i] + B[i];
    }
}

static void check(cudaError_t err, const char* what)
{
    if (err != cudaSuccess) {
        std::fprintf(stderr, "%s failed: %s\n", what, cudaGetErrorString(err));
        std::exit(EXIT_FAILURE);
    }
}

int main()
{
    const int n = 1 << 20;
    const std::size_t bytes = n * sizeof(float);

    std::vector<float> hA(n), hB(n), hC(n);
    for (int i = 0; i < n; ++i) { hA[i] = 1.0f * i; hB[i] = 2.0f * i; }

    float *dA = nullptr, *dB = nullptr, *dC = nullptr;
    check(cudaMalloc(&dA, bytes), "cudaMalloc A");
    check(cudaMalloc(&dB, bytes), "cudaMalloc B");
    check(cudaMalloc(&dC, bytes), "cudaMalloc C");

    check(cudaMemcpy(dA, hA.data(), bytes, cudaMemcpyHostToDevice), "copy A to device");
    check(cudaMemcpy(dB, hB.data(), bytes, cudaMemcpyHostToDevice), "copy B to device");

    const int threadsPerBlock = 256;
    const int blocks = (n + threadsPerBlock - 1) / threadsPerBlock;
    vecAdd<<<blocks, threadsPerBlock>>>(dA, dB, dC, n);
    check(cudaGetLastError(), "kernel launch");

    check(cudaMemcpy(hC.data(), dC, bytes, cudaMemcpyDeviceToHost), "copy C to host");

    int errors = 0;
    for (int i = 0; i < n; ++i) {
        if (hC[i] != hA[i] + hB[i]) { ++errors; }
    }
    std::printf("checked %d elements, %d errors\n", n, errors);

    check(cudaFree(dA), "cudaFree A");
    check(cudaFree(dB), "cudaFree B");
    check(cudaFree(dC), "cudaFree C");
    return errors == 0 ? 0 : 1;
}

10 · Where the analogy breaks

  • Kitchen helpers can each decide to do something different; threads in a warp execute together, so if some must take a different branch, the others wait (divergence, F6-14).
  • Helpers can see and talk to the whole hall; threads can cooperate quickly only within their block (shared memory and barriers), not across the whole grid in a simple way (F6-12).
  • In a real hall, moving food from the main kitchen is quick; copying data between host and GPU memory can cost more time than the addition itself for a job this small (measured in F6-09).

16 · Summary

  • A CPU is a few strong workers; a GPU is many simple workers.
  • A kernel is run by many threads; threads form blocks; blocks form the grid.
  • Each thread computes blockIdx.x * blockDim.x + threadIdx.x and checks it against n.
  • Threads run in warps of 32 on NVIDIA GPUs.
  • Data must be copied to GPU memory and back; every call must be checked.
