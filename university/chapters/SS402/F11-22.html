Story hook

Arjun's neighbour Elena checks child car seats in a factory. One Saturday she shows him a seat from the production line. Under it is a small label with a code. "This code," she says, "tells me exactly which design this seat was built to, which batch of plastic it used, and which tests were run on seats from the same batch."

She opens a folder on her laptop. For one buckle she shows him the requirement ("opens with one hand, but not by a child's push"), the drawing that answers it, the test that checked it, the result, and the date. "Last month the buckle's spring changed," she says. "So last year's test does not count any more. We tested the new spring, and the label on new seats points to the new test."

Arjun asks whether anyone ever looks at all this. "Twice," Elena says. "The inspector looks before we may sell the seat. And if a child is ever hurt, someone will ask: which design was it, which test showed it was safe, and was that test about this seat? If I cannot answer in one minute, the folder failed, however good the seat is."

This chapter builds Elena's folder for the course robot: requirements traced to designs, tests and results, all tied to the build that is released, and a measure of how well the tests exercise the safety logic.

What you will be able to do

  • Distinguish verification from validation, and the kinds of evidence (review, analysis, test, simulation, field data) by what each can and cannot show.
  • Build a trace from hazard to safety goal, safety requirement, design element, test and result, and check it with the course's traceability tool.
  • Tie evidence to configuration: requirement revisions and build ids, so that stale evidence is found by a tool, not by luck.
  • Measure decision, condition and MC/DC coverage of a safety decision and find a minimal MC/DC test set.
  • Diagnose an evidence folder in which every test is green and the release is still not verified.
Jargon box
Verification
Simple words: checking that you built the thing the way the plan said. Analogy: measuring the buckle against its drawing. Precise: confirmation, by examination and provision of objective evidence, that the outputs of a lifecycle phase meet the requirements set for that phase (by review, analysis or test); answers "did we build it right?". D1
Validation
Simple words: checking that the plan itself was right, so the finished thing really keeps people safe in real use. Analogy: crash-testing the whole seat with a test dummy, not only measuring its parts. Precise: confirmation, by examination and provision of objective evidence, that the safety requirements are adequate and that the system as built achieves the safety goals in its intended environment and use; answers "did we build the right thing?". D1 D2
Safety requirement
Simple words: a sentence that says exactly what a safety function must do, so that someone can test it. Analogy: "the buckle opens with one hand, but not by a child's push". Precise: a requirement derived from the hazard analysis that a safety function or measure must meet, stated so that it is verifiable (what, when, how fast, with what integrity); refined from top-level safety goals to functional and then technical requirements allocated to design elements. D2
Traceability
Simple words: links that let you follow any safety requirement to the part that does it and the test that checked it, and back. Analogy: the seat's label leading to its design and its tests. Precise: the documented, bidirectional relationship between hazards, safety goals, safety requirements, design elements, code, test cases and test results; it shows that every requirement is implemented and verified and that nothing in the design or the tests lacks a reason. D3
Configuration of evidence
Simple words: every test result says exactly which version of the robot and which version of the requirement it is about. Analogy: the test of the new spring counts; last year's test does not. Precise: the identification of each verification result with the configuration items it applies to (software build identifier, hardware revision, requirement revision, tool versions), so that evidence is valid only for the released configuration and becomes stale when any of those changes. D1
Decision and condition coverage
Simple words: did the tests make each yes/no decision come out both yes and no, and did each small part of the decision take both values? Analogy: testing the buckle both closed and open, and each of its two catches both pressed and not. Precise: decision coverage requires every decision (a Boolean expression controlling a branch) to evaluate to both true and false; condition coverage requires every condition (a Boolean operand without Boolean operators) to take both values; neither implies the other. D3
MC/DC (modified condition/decision coverage)
Simple words: for each part of a decision, there are two tests that differ only in that part and give different answers, so you know that part really matters. Analogy: showing that pressing only the left catch, with everything else the same, changes whether the buckle opens. Precise: every entry and exit point invoked, every decision taking every outcome, every condition taking every outcome, and each condition shown to independently affect the decision's outcome (in the unique-cause form: by a pair of tests in which only that condition changes); for N independent conditions at least N + 1 tests. D3 R2
Independence of verification
Simple words: the person who checks is not the person who built it. Analogy: Elena checks seats; the people who designed them do not sign her report. Precise: separation between the people (or teams, or organisations) who produce an item and those who verify or assess it, graded by integrity level in the standards, so that the same misunderstanding does not enter both the design and its check. D1 D3

Terms from earlier chapters: hazard log (F11-19), course target and integrity level (F11-20), mutation testing (F4-18), unit test and regression test (F2-30), reproducible build (F9-67).

The idea in pictures

Figure 1 is the V shape that most safety standards draw in some form. The left side goes from hazards down to code; the right side goes from code back up to the system in use. Horizontal arrows are verification against the level opposite; the top arrow is validation. Traceability is the set of links that make the arrows checkable.

Figure 2 follows one trace chain from the course robot, from hazard H3 to the evidence file, and shows the two ways a chain breaks without any test failing: the requirement changes after its test was written, or the result belongs to another build.

Layer 1 — the kid explanation

Building a safe robot is not enough. You must be able to show that it is safe, and show it to someone who did not build it. So every promise about safety is written down as a sentence that can be tested. Then you keep links: from each danger to the promise, from the promise to the part of the robot that keeps it, and from that part to the test that checked it.

Each test result also says which version of the robot it was about. If you change the robot, old results may not count any more. A green tick for last month's robot says nothing about today's robot.

Last, you check your tests. A test that would pass even on a broken robot is not proof of anything. Good tests are the ones that would fail if something were wrong.

Layer 2 — the student explanation

Verification and validation. Verification asks whether each step's output meets that step's input: does the code do what the design says, does the design meet the safety requirement, does the test show it? Validation asks the harder question: are the safety requirements the right ones, and does the finished robot, in its real environment, actually achieve the safety goals? A robot can pass every verification and fail validation: if the hazard analysis missed teach mode (F11-19's forensic lab), every requirement can be met perfectly and the learner's fingers are still unprotected. Validation therefore includes tests of the whole robot in realistic use, and a review of the hazard log against what actually happens. D1 D2

Requirements that can be verified. "The arm must stop quickly when the e-stop is pressed" cannot be tested; "after an e-stop, the control thread brings the arm to rest before the safety relay removes drive power (200 ms), under the worst-case load defined in the test plan" can. Safety requirements are refined in levels: safety goals from the hazard log (SG1: the arm comes to rest after an e-stop before power is removed), functional requirements that say what the system does (SR2: the control thread reads the e-stop every cycle and ramps to rest), and technical requirements allocated to hardware and software elements. Each has an identifier and a revision number, and each revision is a new thing to verify. D2

Kinds of evidence. A review shows that competent people read the item against a checklist; it finds misunderstandings but proves nothing about behaviour. An analysis (a timing budget, a fault tree, a PFD calculation, a static check) shows a property for all cases covered by its model, and is only as good as the model. A test shows behaviour for the cases run, and says nothing about cases not run. A simulation is a test of a model, not of the robot (BR-08). Field data shows what happened in use, after the fact. A good safety argument combines them, and says which kind supports each claim; the safety case of F11-23 will check that a claim about the real robot is not supported only by a simulation. D1

Traceability. With requirements, designs and tests named, the links between them can be written down and checked by a program. Forward, from every hazard to the tests that cover it: is anything not implemented, not tested? Backward, from every test and design element to the requirement it serves: is anything there without a reason (an orphan test that verifies a requirement nobody has any more, or code no requirement asks for)? The course's checker, Listing 1, reads a small text format and reports the gaps. D3 R1

Evidence belongs to a configuration. A test result is a statement about one build of the software, on one hardware revision, against one revision of one requirement. The checker refuses evidence from another build and tests that verify an old revision of their requirement, because both are common, and both look exactly like good evidence in a folder of green ticks. Reproducible builds (F9-67) are what make the build identifier mean something. R1 R3

How thoroughly the tests exercise the logic. Requirements-based tests can still leave parts of the code untouched. Structural coverage measures that: statement coverage (every statement ran), decision coverage (every decision went both ways), condition coverage (every condition took both values), and MC/DC (each condition was shown to matter on its own). Listing 2 computes them for the course robot's drive-enable rule. Coverage is a check on the tests, not a goal in itself: a missing MC/DC pair usually means a missing requirement-based test, and the fix is to write that test from the requirement, not to add inputs until a number turns green. D3 R2

The rule is enable = !estop && wd_ok && (auto_mode || deadman): the arm's drive may be enabled only if the e-stop is not pressed, the watchdog is healthy, and either the robot is in automatic mode or a person holds the enabling (deadman) switch. Coverage and independence in the standards. From the author's memory, not checked in this build: DO-178C requires structural coverage analysis of the requirements-based tests, with statement coverage at level C, decision coverage added at level B and MC/DC added at level A, and requires that some verification objectives be met "with independence" at the higher levels; its definition of MC/DC allows forms other than unique cause (masking MC/DC is widely accepted, per guidance from certification authorities); and DO-330 covers the qualification of tools whose output is not otherwise verified. ISO 26262-6 recommends statement, branch and MC/DC coverage at the unit level with strength depending on the ASIL, and IEC 61508-3 has similar tables per SIL. The definitions in this chapter's Jargon box are paraphrases, not quotations. Check the current editions and the applicable authority guidance before relying on any of this. D1 D2 D3


Coverage of what, compiled by what. Listing 2 measures MC/DC of a Boolean expression from its truth table, which is the concept. Measuring it on real code needs a coverage tool and raises two questions this course can only name: does the compiled code have the same decision structure as the source (an optimiser can turn && into branch-free arithmetic, or split one decision into several), and is the coverage tool itself trustworthy? Both are why the standards care about the tools in the chain. GCC's own coverage instrumentation was not used in this build. D3


Tests that can fail. F11-21's watchdog suite showed each test killing a mutant. Coverage and mutation testing answer different questions: coverage says which parts of the logic the tests touched; mutation testing says whether the tests would notice if those parts were wrong. A suite can reach full MC/DC and still not check the outputs (every test "passes" because it asserts nothing). Safety evidence should show both, and the course's CT2 rule (F11-20) asks for both on the safety decision logic. R2


Regression and impact analysis. When anything changes, the trace tells you what to re-verify: every requirement whose design element changed, every test that depends on it, and every analysis whose model it touches. The forensic lab shows what happens without that discipline: a requirement was tightened (SR4 r2 to r3, a narrower watchdog window) and its test was never updated, so the test still verifies the old window. The checker found it because the test records which revision it verifies. Without revision numbers in the links, nothing would. R3


Independence. The person who writes a requirement and the test for it share their understanding of it, including their misunderstanding. Independent verification (a reviewer from another team, an independent test author) is the process measure against that common cause, the human version of F11-21's diversity. The course requires a learner from another team to sign the evidence index for CT2 functions, and the safety-case review of F11-23 is done by someone who did not write the case. D1



How the hardware actually does it


On real products, a large share of safety verification happens on hardware: hardware-in-the-loop rigs where the real controller runs against a simulated plant, fault injection on the target (pulling connectors, shorting signals to supply or ground, corrupting memory with a debugger, cutting power at chosen moments), and measurements with calibrated instruments (an oscilloscope on the e-stop contact and the drive enable gives the true press-to-disable time). Each of those results is evidence only with its configuration: the board revision, the firmware build, the instrument and its calibration date. Hardware revisions matter as much as software builds: a new batch of relays, a different encoder, or a re-routed cable can change a timing or a common cause. The course robot's T1 (the e-stop chain timed on the real robot) belongs here; it is the one requirement this build could not verify. D1 C1

Worked example


A. Find an MC/DC pair by hand. For deadman, look for two vectors that differ only in bit 3 and give different decisions. Enable needs estop = 0 and wd_ok = 1, and deadman matters only when auto_mode = 0. So the pair is (estop 0, wd_ok 1, auto 0, deadman 0) = v2 → 0 and (0, 1, 0, 1) = v10 → 1. For auto_mode the same reasoning gives v2 → 0 and v6 → 1 (deadman 0). Both pairs share v2, which is why five tests suffice for four conditions. R2


B. Why suite D misses two conditions. Its tests are v6, v7, v4, v10, v0, v15. For auto_mode it would need a pair differing only in bit 2 with different outcomes: (v6, v2) or (v14, v10). It has v6 and v10 but neither v2 nor v14. For deadman: (v10, v2), and v2 is missing. Adding v2 alone completes MC/DC: seven tests, two more than necessary, which is fine; MC/DC is about the pairs, not the count.


C. A trace query in your head. SR4 changes from revision 2 to 3. Which items must be re-verified? D4 (the watchdog class), T4 (its tests), the mutation run, the MC/DC suite if the enable rule uses the watchdog's state (it does: wd_ok), the timing budget of F11-21's Figure 1, and the safety-case claim that cites them. The list comes from following links, not from memory.

Where the analogy breaks


    

  • A child seat's design changes a few times a year. Robot software can change every day, so traceability and configuration of evidence must be automated, not kept by hand in a folder.
    • 

  • Elena's label points to tests of the same batch. Software has no batches: every copy of a build is identical, so one test result covers every robot running that build, and none running another.
    • 

  • A crash test can test the whole seat. There is no crash test for a robot's software that covers all inputs; structural coverage and analysis fill the gap only partly.
    • 

  • Elena's folder is checked by an inspector with legal authority. A learner's evidence index is checked by another learner; that is practice in independence, not certification.
    • 




Common mistakes and debugging


    

  • Results without a build id. Symptom: nobody can say which build a "PASS" was for. Fix: every test run records the build id and the requirement revision; the checker rejects results without them.
    • 

  • Requirement changed, test not. Symptom: a green test for a requirement that now says something else (forensic lab). Find it: revision numbers in the trace. Fix: impact analysis on every requirement change.
    • 

  • Coverage as a target. Symptom: tests with no assertions added to reach a coverage number. Fix: derive tests from requirements, use coverage to find missing requirements-based tests, and use mutation testing to check the tests' power.
    • 

  • Simulation evidence for a hardware claim. Symptom: "the e-stop stops the arm in 100 ms" supported by a simulator log. Fix: label each evidence item with its kind; claims about the robot need evidence from the robot (F11-23 checks this).
    • 

  • Orphan tests. Symptom: tests for requirements that no longer exist, giving a false sense of coverage. Fix: backward traceability; remove or re-link them.
    • 

  • One person writes requirement, code and test. Symptom: all three share the same misunderstanding. Fix: independent review of requirements and tests, graded by course target.
    •

Summary


    

  • Verification checks each step against its input; validation checks that the requirements and the finished system achieve the safety goals in real use.
    • 

  • Safety requirements must be verifiable, identified and revised in levels from safety goals down.
    • 

  • Evidence has kinds (review, analysis, test, simulation, field); each supports only certain claims.
    • 

  • Traceability links hazards, goals, requirements, design, tests and results both ways, and a program can check it.
    • 

  • Evidence belongs to a configuration: a result for another build or an old requirement revision is stale, however green.
    • 

  • Structural coverage up to MC/DC measures how well tests exercise decisions; mutation testing measures whether they would notice errors.
