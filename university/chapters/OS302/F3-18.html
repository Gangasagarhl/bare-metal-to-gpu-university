Story hook

It is six in the morning and the school is dark. The caretaker arrives first, switches on the lights and the heating and checks that the doors work. Then the person with the classroom keys lets the new principal in, hands over a sheet of paper that says which rooms exist and which are locked, and leaves. From that moment the principal is alone. There is no secretary yet, no timetable, no intercom. Before the first student arrives, the principal must find a desk to work at, wipe yesterday's writing off the blackboard, call the few assistants who must set up their tables before anything else happens, and get one way of speaking to the outside world working, even if it is only a hand-held radio to the caretaker's office.

This chapter is that first hour. Your kernel is the principal. The firmware and a loader have done their part; now your code owns the machine, with nothing underneath it: no operating system, no C library, no C++ runtime. You will make a 64-bit C++ kernel start, set up its own stack, clear its uninitialised data, run its global constructors, and print through the PC's serial port. When something goes wrong, it will say so in one clear line and stop.

What you will be able to do

  • Explain what "freestanding" means for C++ and list what a kernel must supply itself: the entry stub, the stack, BSS clearing, global constructors, the memory functions the compiler calls, and the ABI hooks such as __cxa_pure_virtual.
  • Read and write a linker script for a higher-half kernel whose code runs at 0xffffffff80000000 plus its physical address.
  • Follow a 32-bit entry stub as it builds boot page tables, enables long mode and jumps to the higher half.
  • Build the kernel with the freestanding compiler flags and prove with readelf that it needs no runtime library.
  • Use QEMU's isa-debug-exit device so that a kernel test passes or fails with an exit status a script can check.
  • Diagnose a kernel whose global objects are silently never constructed.
Jargon box
Kernel (operating system)
Simple words: the part of the operating system that runs with full control of the machine. Analogy: the principal. Precise: the privileged program that manages the CPU, memory and devices and offers services to other programs. Not the same as a "kernel (GPU)" in F6, which is a function launched on a GPU. D1
Freestanding implementation
Simple words: C++ without the operating system's help: only a small part of the standard library is guaranteed. Analogy: the principal on the first morning, with no secretary. Precise: an implementation in which a program may run without an operating system; only a limited set of headers is required, and program start-up and termination are implementation-defined. D8
Higher-half kernel
Simple words: a kernel whose addresses are at the very top of the virtual address space. Analogy: the staff rooms are on the top floor, far from the classrooms. Precise: a kernel linked at virtual addresses in the upper half of the canonical address space (here 0xffffffff80000000 + physical address), so that the lower half stays free for user programs. D1 R1
Long mode
Simple words: the CPU's 64-bit mode. Analogy: the school's full-day timetable, as opposed to the morning set-up hour. Precise: the x86-64 operating mode entered with paging enabled, PAE set and the long-mode-enable bit set in the EFER register; 64-bit code runs in its 64-bit sub-mode. D1
BSS
Simple words: the part of a program for variables that start at zero; the file does not store those zeros. Analogy: wiping the blackboard before the day starts. Precise: a section of type NOBITS that occupies memory but no file space; the loader or start-up code must fill it with zeros. D9
Global constructor
Simple words: code that sets up a global object before main (here kmain) runs. Analogy: the assistants who set up their tables before the first lesson. Precise: dynamic initialisation of objects with static storage duration; on ELF x86-64 the compiler places a pointer to each translation unit's initialisation function in .init_array, which start-up code must call. D3 R5
Multiboot
Simple words: an agreement between a loader and a kernel about how the kernel is found, loaded and started. Analogy: the sheet of paper the key holder hands to the principal. Precise: a boot protocol: the kernel image carries a header with a magic number and flags; the loader enters the kernel in 32-bit protected mode with a magic value in EAX and the address of an information structure in EBX. D2
Serial port (UART)
Simple words: the simplest way for a computer to send text, one bit after another over a wire. Analogy: the hand-held radio to the caretaker. Precise: a universal asynchronous receiver-transmitter; the PC's first one (COM1) is a 16550-compatible device at I/O port 0x3F8. D4
Panic
Simple words: the kernel's "I cannot continue" stop. Analogy: the principal closing the school and posting one clear notice on the door. Precise: a function that disables interrupts, prints the location and reason of a fatal error, and halts (here: ends QEMU with a failure status). R3

Layer 1 — the kid explanation

When you run a program on your laptop, a lot of helpers do work before your first line runs. They put the program in memory, give it a place to keep notes, clear its blank pages, and connect it to the screen. A kernel has no such helpers: it is the helper. So the first thing a kernel does is to do these jobs for itself.

Our kernel does them in a fixed order. It switches the processor into its 64-bit mode. It picks a piece of memory to use as its notebook (the stack). It wipes the variables that should start at zero. It lets every global object set itself up. Then it starts the real work and sends a line of text out of the serial port, which QEMU shows on your screen. If something is wrong, it prints one clear line saying where, and stops.

Analogy

The principal arrives with only a sheet of paper from the key holder. Before the first lesson: a desk (the stack), a clean blackboard (BSS), the assistants called in (constructors), and a radio that works (the serial port). If anything is badly wrong, the school closes with one notice on the door (the panic line).

Layer 2 — the student explanation

In SP301 you met the pieces separately: object files and relocations (F2-43), ELF (F2-44), linker scripts (F2-46), freestanding C++ (F2-48) and inline assembly wrappers (F2-49). Here they meet in one program.

Who loads us, and in what state

OS301 ends with a choice of loaders: your own UEFI loader from milestone A3, or Limine. This build of the course uses a third, smaller route for its labs: QEMU's built-in loader for the Multiboot protocol (version 1), selected with qemu-system-x86_64 -kernel. The reason is practical and is recorded as a decision for the course owner in NOTES.md: the labs must boot inside the build container with nothing but QEMU, and every later chapter needs a kernel that boots in one second. The kernel's C++ code does not depend on the loader; only boot.S does, and the chapter shows where an A3 or Limine entry would differ.

A Multiboot loader looks for a header in the first part of the image: a magic number, flags, and a checksum chosen so that the three add up to zero. Our image is a flat binary (not ELF), so the header also carries the addresses that tell the loader where to put the file and where to start: the "a.out kludge" fields. The loader enters _start in 32-bit protected mode, paging off, interrupts off, with the value 0x2BADB002 in EAX and the physical address of an information structure in EBX D2. The lab run printed both: magic=0x2badb002 info=0x9500 R2.

From 32 bits to 64 bits

64-bit code cannot run with paging off: long mode requires paging, and paging needs tables. So the stub's first job is to build page tables (Figure 2), then set three switches: PAE in CR4, long mode enable in the EFER register, and paging in CR0. A far jump through a code segment whose "long" bit is set lands in 64-bit code D1. One more jump moves execution from the identity-mapped copy at 1 MiB to the higher-half address the kernel was linked for.

The C++ runtime you must write

A hosted C++ program has its start-up code (in the C library and the compiler's support library) set up the stack, clear BSS and call constructors before main. Freestanding, that code is gone D8. Our kernel provides: an entry stub that sets a stack and clears BSS; a loop that calls every pointer in .init_array; memset, memcpy, memmove and memcmp (the compiler may emit calls to them even when you never write them); __cxa_pure_virtual and an empty __cxa_atexit (Itanium C++ ABI hooks) D3. Exceptions and run-time type information are switched off, so their support code is not needed.

Printing and failing

The serial port needs seven register writes to configure and a loop that waits for "transmitter empty" before each character D4. On top sits a small formatter, kformat.h, that understands the printf conversions the kernel uses; because it is pure logic, the same file is tested on the host against the C library's snprintf (R4). PANIC and KASSERT print PANIC at file:line: message and then end QEMU with the failure status through the isa-debug-exit device.

Layer 3 — the engineer's depth

The compiler flags, one by one

kbuild.sh (Listing 5) compiles every file with the same flags. Each has a reason:

  • -ffreestanding: no hosted assumptions; the compiler may not replace your loops with library calls it assumes exist, beyond the four memory functions (which is why cxxrt.cc defines them) D10.
  • -fno-exceptions -fno-rtti: no unwinder and no type-info tables; throw becomes a compile error, which is what a kernel wants.
  • -fno-threadsafe-statics: function-local statics are initialised without calls to __cxa_guard_acquire; the kernel has one CPU here, and later chapters that need such guards must provide them D3.
  • -mno-red-zone: the System V ABI lets leaf functions use 128 bytes below the stack pointer without moving it. An interrupt arriving in kernel mode pushes its frame exactly there, on the same stack, and would destroy that data; F3-19 makes this concrete D5.
  • -mcmodel=kernel: code and static data live in the top 2 GiB of the address space, so 32-bit sign-extended addresses reach them D5 D10. Our link address 0xffffffff80000000 is the bottom of that window.
  • -mgeneral-regs-only: the compiler uses no SSE or x87 registers. The interrupt entry code of F3-19 saves only general-purpose registers, and the FPU is not set up; floating-point state belongs to threads (OS303).
  • -fno-stack-protector -fno-pic: no canary calls into a library that is not there; no position-independent code, because the kernel is linked for one address.

Link: ld -nostdlib -static -T linker.ld, no libraries at all. objcopy -O binary turns the ELF file into the flat image that the a.out-kludge header describes. The ELF file is kept for readelf, nm, addr2line and the debugger.

The linker script and the two kinds of address

Every section has a virtual address (VMA, where the code expects to run) and a load address (LMA, where it is placed in physical memory). The .boot section has VMA = LMA = 1 MiB: it runs before the higher half exists. Every later section is placed at KERNEL_VMA + its physical address with AT(ADDR(.text) - KERNEL_VMA) D7. R1 shows the result in the program headers: a LOAD segment at virtual 0x0000000000100000, then segments at virtual 0xffffffff8010d000 with physical 0x10d000 R1.

The script exports symbols the code uses: __bss_start and __bss_end for clearing, __init_array_start and __init_array_end for constructors, and __load_end_phys and __bss_end_phys for the Multiboot header. Two details cost hours in this build and are worth knowing. First, QEMU's loader reads the file up to load_end_addr; if the flat image ends before that address the loader fails with a read error, so the script pads the last file-backed section to a page boundary (line 30). Second, the constructor list is placed inside .rodata, so it is found by name, not by luck; the forensic lab shows what happens when a script names the wrong section.

Boot page tables in six loops' worth of thought

The stub fills one PML4, two PDPTs and eight page directories (Figure 2). Each PD entry maps a 2 MiB page: physical address bits plus flags 0x83 (present, writable, page size) D1. The eight PDs cover 8 GiB. The PDPT for the direct map points at all eight; the identity entry PML4[0] shares that PDPT; the kernel's PDPT entry 510 points at the first PD only, giving 1 GiB at 0xffffffff80000000. Index arithmetic: 0xffffffff80000000 splits into PML4 index 511 and PDPT index 510, which you will verify by hand in F3-21. Because the stub runs in 32-bit mode, it writes each 64-bit entry as two 32-bit halves (lines 52–58); the high half matters only above 4 GiB.

Keeping two numbers safe across BSS clearing

The magic value and information address arrive in EAX and EBX. The stack lives in .bss, so pushing them would be erased by the clearing loop (this build's first version printed magic=0 for exactly that reason). The stub keeps them in R12 and R13, which the System V ABI says a called function must preserve, across both rep stosb and run_global_constructors, then passes them in EDI and ESI, the first two argument registers D5.

Constructors: .init_array, not .ctors

For each translation unit with dynamic initialisation, GCC on x86-64 Linux targets emits a function (here _GLOBAL__sub_I_kmain) and stores its address in .init_array D3 R5. Older toolchains used .ctors with a different order. The B1 probe object prints B1 ok from its constructor and sets value = 42; kmain prints the value, so a missing constructor is visible twice R2. Constructors run in link order across files, and the C++ standard leaves that order unspecified; a kernel must not let one global's constructor depend on another file's global. The probe calls serial::init() itself for that reason.

Pass and fail as exit codes

QEMU's isa-debug-exit device, placed at I/O port 0xF4, ends QEMU when written; the exit status is the written value shifted left by one, plus one. Writing 0x10 gives 33 and 0x11 gives 35, which the lab's logs record (R2, R3). Exit status 0 can therefore never mean "test passed", a property the curriculum's test harness relies on.

Not verified — check before relying on this

Written from memory and only partly confirmed by the runs: the Multiboot header field order, the flag bits 1 and 16, the magic values 0x1BADB002 and 0x2BADB002, and the information structure layout (check the Multiboot Specification version 1, D2; the run confirms only that QEMU accepted the header and filled mem_lower/mem_upper). The bit positions CR4.PAE = 5, CR0.PG = 31, EFER.LME = 8, the EFER MSR number 0xC0000080, the descriptor values 0x00AF9A000000FFFF and 0x00CF92000000FFFF, and the PDE flag value 0x83 (check the Intel SDM Vol. 3, D1; the run confirms that the combination works on QEMU 8.2.2). The 16550 register offsets and the divisor for 115200 baud (check the PC16550D datasheet, D4). The isa-debug-exit formula is confirmed only by the two exit codes observed (R2, R3); check the QEMU documentation (D6).

How the hardware actually does it

On a PC, the CPU starts in a 16-bit mode at the reset vector inside the firmware (F3-09). The firmware, legacy BIOS (SeaBIOS in QEMU) or UEFI, initialises memory and devices and runs a loader. A BIOS loader that speaks Multiboot switches to 32-bit protected mode and enters the kernel as described above D2. A UEFI loader such as your A3 loader is already in 64-bit mode with identity-mapped paging when it hands over; Limine enters in 64-bit mode with the kernel already mapped in the higher half and passes its information through request structures. In both cases the 32-bit part of boot.S (lines 20–80) disappears, and the rest (stack, BSS, constructors, kmain) stays the same.

The switch into long mode is a sequence the processor checks: paging must be off while EFER.LME is set; PAE must be on; setting CR0.PG then activates long mode in its compatibility sub-mode, and the far jump into a code segment with the L bit set enters 64-bit mode D1. The GDT used for that jump is the stub's own three-entry table; F3-19 replaces it with the kernel's real GDT and TSS.

The UART is a separate chip function on the platform (today inside the chipset or a Super I/O device). Writing a byte to the data register starts its transmission at the configured rate; the "transmitter holding register empty" bit in the line status register says when the next byte may be written D4. QEMU's model connects that byte stream to -serial stdio, which is how the lab captures output into .out files.

Watch out

Untested on hardware. Every run of this chapter used QEMU 8.2.2 with TCG in a cloud container without KVM. On a real PC you need a Multiboot-capable loader on a boot medium, a machine that still offers legacy BIOS boot (or a loader that provides Multiboot under UEFI), and a physical serial port or a USB-serial adapter wired to another computer. None of this was tried in this build. Follow the curriculum's safety rules for real machines: a spare computer, a boot medium you can erase, and no firmware flashing.

Worked example

Question: the lab printed .bss 0xffffffff8010f000-0xffffffff80114000. Which physical memory did the stub clear, how many bytes, and which Multiboot field told the loader about it?

  1. Physical = virtual − 0xffffffff80000000: 0x10f000 to 0x114000.
  2. Size: 0x114000 − 0x10f000 = 0x5000 = 20,480 bytes. Cross-check with R1's size output: bss 20480. The boot stack (16 KiB = 16,384 bytes) is most of it.
  3. The header's bss_end_addr field holds __bss_end_phys, which the linker set to 0x114000. A Multiboot loader zeroes from the end of the loaded file to that address D2; the stub clears again anyway, because the other routes (A3, Limine) may not.
  4. Evidence it worked: bss check: 0 0 0 0 in R2.

A second question the exam likes: why is the first LOAD segment of R1 marked RWE? Because .boot holds both the stub's code and its page tables, which the stub writes. After F3-21 the kernel no longer uses that region, and its own mappings give each section exactly one of read-only, read-write or execute.

Where the analogy breaks


    

  • The principal arrives as a person who already knows how to work. The kernel arrives as bytes in memory that cannot even use its own variables correctly until it has cleared BSS and run constructors; "being ready" is something the code must build.
    • 

  • The principal can ask the key holder a question later. The kernel cannot call back into the loader: the information structure is all it gets, and it must copy what it needs before reusing that memory (F3-20 reserves it).
    • 

  • The school has one building. The kernel sees the same physical memory through three virtual windows at once (Figure 2), which has no counterpart in a building.
    • 




Common mistakes and debugging


    

  • Linking without -mcmodel=kernel: relocation errors such as "relocation truncated to fit" for every global. The default model assumes the low 2 GiB.
    • 

  • Red zone left on: random corruption of local variables once interrupts arrive (F3-19). The symptom appears far from the cause.
    • 

  • Clearing BSS with the stack inside it while holding live values on the stack: this build's first version lost the Multiboot magic that way. Keep such values in callee-saved registers.
    • 

  • An image shorter than load_end_addr: QEMU stops with a read error before the kernel runs. Pad to a page, as line 30 of the script does.
    • 

  • Old tutorial linker scripts that collect .ctors: the link succeeds, the kernel boots, and globals stay zero. That is the forensic lab.
    • 

  • Silent hang: add -d int,cpu_reset -D qemu.log to the QEMU command and read the log; a triple fault shows as a CPU reset (F3-19 uses this).
    • 

  • Debugging with gdb: start QEMU with -s -S, then gdb k_b1.elf, target remote :1234. Break on kmain, not on _start: gdb sees the 32-bit stub through 64-bit eyes and disassembles it wrongly.
    • 




Transition box

Where you came from: OS301 (firmware, boot protocols, the A3 loader or Limine) and SP301 (linker scripts, ELF, freestanding C++, inline assembly wrappers). What carries over: the ELF view of a program, the linker as the tool that decides addresses, the rule that inline assembly lives in tiny wrappers (arch.h), and your habit of testing logic on the host first. What changes: nobody runs before your code; you write the start-up sequence, you own the stack, and a mistake now ends in a reboot rather than an error message. What comes next: F3-19 gives the kernel its own GDT, TSS and IDT, so that a mistake prints a report instead of rebooting the machine.

Summary


    

  • A freestanding kernel provides its own start-up: entry stub, stack, BSS clearing, constructors, memory functions and ABI hooks.
    • 

  • QEMU's Multiboot loader enters in 32-bit mode at 1 MiB; the stub builds 2 MiB-page tables, enables long mode and jumps to 0xffffffff80000000 + physical.
    • 

  • The linker script separates virtual and load addresses with AT(...) and exports the symbols the start-up code needs.
    • 

  • Kernel flags: no red zone, kernel code model, no SSE, no exceptions or RTTI, no stack protector.
    • 

  • Global constructors are pointers in .init_array; a script that collects .ctors silently loses them.
    • 

  • PANIC prints file, line and message and ends QEMU with status 35; a pass ends with 33.
    • 

  • readelf proves the kernel has no undefined symbols and no dynamic section.

Forensic lab answer key


Observation. The first line, B1 ok…, is missing, and probe.value=0 instead of 42. BSS is still zero, printing works, and the kernel passes its other checks: only dynamic initialisation is missing.


Hypotheses. QEMU never runs constructors in any case; the kernel does (R2), so QEMU is not involved. The compiler did emit a constructor: forensic_elf shows an .init_array section of 8 bytes whose entry addr2line names _GLOBAL__sub_I_kmain at b1_main.cc:48. The start-up loop walked an empty list: __init_array_start and __init_array_end are both ffffffff8010e2f8.


Root cause. The broken script collects .ctors between the two symbols; GCC put the pointer in .init_array, which the script no longer names, so the linker placed it as an orphan section after .data, outside the bounds the loop uses. No error, because orphan placement is legal.


Fix. Restore lines 26–27 of Listing 2: KEEP(*(SORT_BY_INIT_PRIORITY(.init_array.*))) and KEEP(*(.init_array)).


Prevention. A build check that the list is non-empty when the object files contain constructors (the mini-project), or --orphan-handling=error on the ld line so any unnamed section stops the link (check the option in the ld manual, D7), plus the B1 probe test in every boot.
