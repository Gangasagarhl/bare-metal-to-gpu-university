Story hook

On the first afternoon, the principal is writing at the desk when something goes wrong in a classroom. Nobody has said what to do in that case, so the student runs around the building, finds no one in charge of "accidents", and the whole school is evacuated. Nobody ever learns what happened.

The next morning the principal pins up a list on the office wall: for each kind of event, number 0 to 255, the name of the person who handles it and, for the worst ones, a separate staircase to use, because the usual one may be the very thing that collapsed. Accidents still happen. But now each one ends in a written report.

A kernel without an interrupt table is that school on the first afternoon: any exception becomes a triple fault and the machine resets with no message. This chapter writes the list (the IDT), gives the worst cases their own staircases (the IST stacks in the TSS), and turns every CPU exception into a readable report.

What you will be able to do

  • Build a 64-bit GDT with kernel and user code and data descriptors and a 16-byte TSS descriptor, and load it with a far return.
  • Explain what the TSS still does in 64-bit mode: privilege-level stacks and the Interrupt Stack Table (IST).
  • Write 256 interrupt entry stubs that give every handler the same frame layout, whether or not the CPU pushed an error code.
  • Decode a page-fault error code and the CR2 register.
  • Show that a kernel stack overflow ends in a readable double-fault report on its own stack instead of a reboot.
  • Read QEMU's interrupt log to reconstruct a triple fault exception by exception.
Jargon box
GDT (Global Descriptor Table)
Simple words: a table that describes the code and data "segments" the CPU may use. Analogy: the list of room types in the school: staff rooms and student rooms. Precise: a table of segment descriptors (8 bytes each, system descriptors 16 bytes in 64-bit mode) located by GDTR; in 64-bit mode code descriptors still set the mode (L bit) and the privilege level (DPL), while bases and limits are mostly ignored. D1
TSS (Task State Segment)
Simple words: a small structure that tells the CPU which stack to use when an interrupt arrives. Analogy: the noticeboard that says which staircase to take. Precise: in 64-bit mode, a 104-byte structure holding RSP0–RSP2 (stacks for privilege changes), IST1–IST7 (stacks selected by IDT gates) and the I/O permission bitmap base; loaded with ltr. D1
IDT (Interrupt Descriptor Table)
Simple words: the table of handlers, one per interrupt or exception number. Analogy: the list on the office wall: event number → who handles it. Precise: up to 256 16-byte gate descriptors located by IDTR; each holds a handler address, a code selector, a type (interrupt or trap gate), a DPL and an IST index. D1
Exception
Simple words: the CPU's own alarm when an instruction cannot be completed normally. Analogy: an accident in a classroom, reported by the room itself. Precise: a synchronous event generated by the processor (vectors 0–31), classified as a fault (restartable; the saved RIP points at the faulting instruction), a trap (the saved RIP points after it) or an abort. D1
Interrupt
Simple words: a signal that makes the CPU stop what it is doing and run a handler. Analogy: the doorbell. Precise: an asynchronous event from a device or another CPU, delivered through an interrupt controller with a vector number; handled through the same IDT as exceptions. D1
IST (Interrupt Stack Table)
Simple words: up to seven spare stacks the CPU can switch to for chosen interrupts. Analogy: the emergency staircase. Precise: seven 64-bit stack pointers in the TSS; a gate whose IST field is n (1–7) makes the CPU load RSP from ISTn unconditionally before pushing the frame. D1 R2
Double fault (#DF)
Simple words: the CPU's report that it failed while trying to report another fault. Analogy: the messenger trips on the stairs on the way to report the accident. Precise: exception 8, raised when a second exception occurs while delivering a first one in certain combinations (for example a page fault while delivering a page fault); an abort with error code 0. D1
Triple fault
Simple words: a failure while reporting a double fault; the CPU gives up and resets. Analogy: the school is evacuated and nobody writes a report. Precise: an exception during delivery of a double fault; the processor enters shutdown, which the platform turns into a reset. D1 R4
CR2
Simple words: the register that holds the address a page fault was about. Analogy: the room number on the accident report. Precise: control register 2, loaded by the processor with the linear address that caused a page fault. D1

In this course "kernel" always means the operating-system kernel; the F6 courses use "kernel (GPU)" for a function launched on a GPU, which is unrelated.

Layer 1 — the kid explanation

A computer's processor can get into trouble: dividing by zero, finding an instruction it does not know, touching memory that does not exist. When that happens it does not stop and freeze. It looks at a list that the operating system wrote in advance, finds the line for that kind of trouble, and runs the program written there. That list is called the interrupt descriptor table.

If the list is missing, or the program on it cannot even start, the processor tries once more, then gives up and restarts the whole computer. Our kernel writes the list for all 256 kinds of events, and for the very worst ones it keeps a spare stack ready, so it can always write a report.

Analogy

The list on the office wall (IDT) says who handles each numbered event; the noticeboard (TSS) says which staircase to take; for fire, there is a separate emergency staircase (IST) because the main one may be the thing on fire. When the doorbell (an interrupt) or an accident (an exception) happens, the school follows the list.

Layer 2 — the student explanation

Why a GDT still exists in 64-bit mode

Segmentation is mostly switched off in 64-bit mode: code and data segments have base 0 and no limit checks. But the CPU still reads two things from a code descriptor: whether it is a 64-bit segment (the L bit) and its privilege level (DPL), which is how the CPU knows whether it runs kernel code (ring 0) or user code (ring 3) D1. The GDT is also where the TSS descriptor lives. Our GDT has seven 8-byte slots: null, kernel code, kernel data, user data, user code, and a 16-byte TSS descriptor that takes two slots. The order of the user entries (data before code) is chosen for the syscall/sysret instructions of OS303, which compute selectors from a base D1.

The TSS: no task switching, only stacks

The 32-bit x86 used the TSS for hardware task switching. 64-bit mode dropped that; what remains is a list of stack pointers. RSP0 is loaded when an interrupt moves the CPU from ring 3 to ring 0 (OS303 sets it for each thread). The seven IST slots are used when an IDT gate asks for them, regardless of the current ring D1. We give three handlers their own 16 KiB stack: double fault (IST1), NMI (IST2) and machine check (IST3). These are the events that may arrive when the current stack cannot be trusted.

256 gates, one shape of frame

For some vectors the CPU pushes an error code, for others it does not. Handlers are easier to write if they all see the same frame, so each of the 256 stubs in isr.S pushes a dummy 0 when the CPU did not push one, then the vector number, then jumps to common code that saves every general-purpose register. The result is struct InterruptFrame, 22 words, which interrupt_dispatch receives by pointer. Exceptions 0–31 get a report; vectors 32–255 go to handlers registered by drivers (F3-24 and F3-25 use them).

Faults, traps and resuming

A fault saves the address of the instruction that failed, so returning re-executes it; that is what makes page faults useful for demand paging later. A trap saves the address of the next instruction: the breakpoint instruction int3 is a trap, so returning continues after it. Our test kernel shows both: the breakpoint resumes by itself; for the faults, a test-only "fixup" address tells the dispatcher where to continue, because re-executing a division by zero would fault forever D1 R2.

Layer 3 — the engineer's depth

Descriptor encodings, tested on the host

A code or data descriptor packs a 32-bit base, a 20-bit limit, an access byte (present, DPL, type) and four flag bits (granularity, size, L) into 8 bytes in a famously scattered layout. gdt.h builds it with a constexpr function; desc_host.cpp checks on the host that it reproduces the two values boot.S used in F3-18 (0x00af9a000000ffff and 0x00cf92000000ffff), that user code has DPL 3 and the L bit, and that a gate built for a known handler address, IST 1, type 0xE, present, decodes back to the same fields R1. This is the habit from SP courses: anything that is pure bit arithmetic is tested on the host first, under AddressSanitizer, where a mistake prints a message instead of rebooting a machine.

The 64-bit TSS descriptor is 16 bytes: the base address is split over bits 16–39 and 56–63 of the first quadword and all of the second; type 0x9 means "available 64-bit TSS"; ltr later marks it busy (type 0xB), which is why loading the same TSS twice faults D1. QEMU's log in R4 shows the loaded task register as TR =0028 ffffffff801210a0 00000067 00008900 DPL=0 TSS64-avl: selector 0x28, base, limit 0x67 = 103 = 104 − 1, the type nibble 9 R4.

Loading the GDT: the far return

lgdt only changes where the CPU will look next; CS still holds the old selector and the CPU's cached descriptor. In 64-bit mode there is no direct far jump with an immediate 64-bit target, so gdt.cc pushes the new code selector and a return address and executes lretq, which pops both and reloads CS D1. Then the data segment registers get the new data selector, and ltr loads the TSS selector.

The gate

Each 16-byte gate holds the handler address split into three parts, the code selector (0x08), the IST index (bits 32–34), the type (0xE: interrupt gate, which clears IF on entry; 0xF would be a trap gate, which leaves IF unchanged), DPL and the present bit D1. The lab prints gates 8 and 14 raw: idt[8] raw: low 80108e010008dd30 and idt[14] raw: low 80108e000008dd90 R2. Reading right to left: offset bits 0–15 dd30, selector 0008, IST byte 01 for gate 8 and 00 for gate 14, type and attributes 8e (present, DPL 0, type 0xE), offset bits 16–31 8010; the high quadword holds offset bits 32–63, ffffffff. So stub 8 is at 0xffffffff8010dd30 and stub 14 at ...dd90: six stubs of 16 bytes later, as designed.

The dispatcher's policy

Vectors 32 and up call a registered handler. For exceptions the policy is: a breakpoint is reported and resumed; a fault with a test fixup set is reported and resumed at the fixup; anything else switches the printer into panic mode, dumps the registers and control registers, and panics. Page faults are decoded: bit 0 present (0 = page not present, 1 = protection violation), bit 1 write, bit 2 user mode, bit 3 reserved bit set, bit 4 instruction fetch D1. The run shows error code 0x0 for a read of an unmapped address and 0x2 for a write, both with CR2 = 0x0000000400000000 (16 GiB, beyond the boot tables' 8 GiB) R2.

The general-protection test uses a non-canonical address. In 4-level paging, bits 63–48 of an address must all equal bit 47; 0x0000800000000000 breaks that rule, and such an access raises #GP, not #PF D1 R2.

The stack-overflow test, step by step

A guard page is an unmapped page below a stack, so running off the end faults instead of silently overwriting whatever lies below. Before F3-21 the kernel has only the boot tables with 2 MiB pages, so the test makes a 2 MiB guard: it clears entry 3 of the boot page directory (physical 6–8 MiB, in all three windows at once, because they share the directory), reloads CR3 to flush the TLB, and switches to a 16 KiB stack whose bottom is at physical 8 MiB. A recursive function with a 256-byte local array then runs downward until a write lands at 0xffff8000007fff.., the last bytes of the guard R2.

What happens next is the whole point of the IST (Figure 2). The write causes a page fault. To deliver it, the CPU must push the exception frame onto the current stack, which is in the guard, so the push faults too. A page fault during page-fault delivery is one of the combinations that become a double fault D1. If gate 8 uses the current stack, delivering the double fault faults again: triple fault. With IST1, the CPU first loads RSP from the TSS, pushes onto the good stack, and our handler prints the report. R2 shows the report with rsp ffff8000007fff30 (the broken stack, saved in the frame) and the frame itself at 0xffffffff80118ff0, inside the IST1 stack whose top is 0xffffffff801190a0.

QEMU's interrupt log

-d int makes QEMU print one block per delivered exception or interrupt: v= the vector, e= the error code, cpl= the privilege level, the RIP and the full register state; check_exception old: X new: Y lines show how QEMU combines a new exception with one being delivered. With -d cpu_reset a reset is logged too. In a normal boot of the B2 kernel the log has no v= line at all (R3), which is the third acceptance test: no hidden exceptions R3.

Not verified — check before relying on this

Written from memory and confirmed only as far as the runs go: the list of vectors with an error code (8, 10–14, 17, 21, 29, 30), the exception names for vectors 15–31, the gate layout and type values 0xE/0xF, the TSS layout (104 bytes, IST at offset 0x24), the TSS descriptor type values 0x9 and 0xB, the page-fault error-code bits 3 and 4, the canonical-address rule, the 16-byte stack alignment on entry and the double-fault combination table. Check them in the Intel SDM Vol. 3, "Interrupt and Exception Handling", "Task Management" and "Paging" (D1), and the AMD64 APM Vol. 2 (D2). The runs confirm: gates with type 0xE, IST 1 on gate 8, the TSS limit 0x67, error codes 0x0 and 0x2, and the #PF → #PF → #DF → triple-fault sequence on QEMU 8.2.2.

How the hardware actually does it

When an exception or interrupt is recognised, the processor reads the gate from the IDT, checks it (present, type, privilege), decides on a stack (IST if the gate says so; RSP0 from the TSS if the privilege level changes; otherwise the current stack), aligns RSP to 16 bytes, pushes SS, RSP, RFLAGS, CS and RIP, pushes an error code for the vectors that have one, clears IF for an interrupt gate, and loads CS:RIP from the gate D1. iretq reverses this, popping all five values, so the interrupted code continues with its own stack and flags.

Every step of that sequence can itself fail: a gate can be missing (#GP with an error code naming the IDT entry), the new stack can be unmapped (#PF), the code segment can be wrong. The processor's rules for what happens when the second failure occurs during the first are what the double-fault and triple-fault mechanisms are about. A triple fault puts the processor into shutdown; on a PC the chipset turns shutdown into a reset, and QEMU models that as a reset, which -no-reboot turns into "exit" D1 D3 R4.

NMI and machine check get IST stacks for a different reason: they can arrive at any instruction, including the few instructions in the system-call path where the kernel has not yet switched to its own stack (OS303). Using a known-good stack for them is the standard defence D4.

Watch out

Untested on hardware. All runs used QEMU 8.2.2 with TCG. TCG's checks of descriptor fields are not guaranteed to be as strict as a real processor's: a descriptor that QEMU accepts might fault on hardware. Before booting on a real machine, compare every descriptor bit with the SDM (the unverified box lists them) and keep the triple-fault test in your regression suite.

Worked example

Decode the double-fault report line cr0 0000000080000011 cr2 ffff8000007fff28 cr3 0000000000101000 cr4 0000000000000020 from R2.

  1. CR0 = 0x80000011: bit 31 (PG, paging on), bit 4 (ET), bit 0 (PE, protected mode). WP (bit 16) is not set yet; F3-21 sets it.
  2. CR2 = 0xffff8000007fff28: the address of the last page fault. Subtract the direct-map base: physical 0x7fff28, inside the guard region 0x600000–0x7fffff that the test printed. It is 8 bytes below the saved RSP ffff8000007fff30: the CPU's first push of the page-fault frame.
  3. CR3 = 0x101000: the boot PML4 (the first page after the multiboot header page at 1 MiB).
  4. CR4 = 0x20: only bit 5, PAE, as boot.S set it.

Conclusion: the second page fault happened while pushing, exactly the case that becomes a double fault. The handler is still running because gate 8 named IST1.

Where the analogy breaks


    

  • A school's emergency staircase is used by whoever is in danger. An IST stack is used by one handler, and if that handler can run twice at the same time (an NMI arriving during the NMI handler, for example), both use the same stack and the second overwrites the first; real kernels add extra care for that case.
    • 

  • The doorbell rings at the door; an exception is raised by the very instruction the CPU is executing. There is no "outside" visitor for #PF: the classroom reports on itself.
    • 

  • The list on the office wall can be read by anyone. The IDT is read by the processor, and it reads it at the moment of the event, so changing a gate while interrupts are enabled is a race.
    • 




Common mistakes and debugging


    

  • Wrong error-code list: one vector off and every handler after it sees a frame shifted by 8 bytes; RIP looks like a flags value. Check the stub table against the SDM.
    • 

  • Forgetting the far return after lgdt: works until something reloads CS (the first iretq), then faults with a confusing selector.
    • 

  • Loading the TSS twice: ltr on a busy TSS raises #GP.
    • 

  • No IST for #DF: stack overflows become silent reboots (the forensic lab).
    • 

  • Red zone: an interrupt in a leaf function corrupts its locals. F3-18's -mno-red-zone prevents it.
    • 

  • Reading the log: run with -d int,cpu_reset -D qemu.log -no-reboot, search for the last v= lines and the check_exception lines before "Triple fault". With -d int QEMU also logs every hardware interrupt once they are enabled (from F3-24 on), so filter by vector.
    • 




Transition box

Where you came from: F3-18, a kernel that boots, prints and panics, but whose any exception means a reset. What carries over: the build, the serial printer, PANIC, the pass/fail exit codes, and the boot page tables, which the overflow test edits. What changes: the kernel now owns its descriptor tables; every exception produces a report; the worst ones have their own stacks. What comes next: F3-20 reads the firmware's memory map and builds the physical memory manager, so that the kernel can stop using fixed arrays in BSS for everything.

Summary


    

  • The 64-bit GDT still matters for the L bit, privilege levels and the TSS descriptor.
    • 

  • The 64-bit TSS holds stacks only: RSP0–2 and IST1–7.
    • 

  • 256 stubs give every handler one frame layout; vectors with a CPU error code skip the dummy push.
    • 

  • Faults resume at the faulting instruction, traps after it; test fixups make faults resumable for testing.
    • 

  • Page-fault reports decode the error code and CR2.
    • 

  • A stack overflow without IST escalates #PF → #DF → triple fault; with IST1 on #DF it ends in a report.
    • 

  • QEMU's -d int,cpu_reset log reconstructs any exception chain.

Forensic lab answer key


Observation. Block 6: v=0e e=0002, a write page fault at RIP ffffffff8010f132 with SP ffff8000007fff30, inside the guard (physical 0x600000–0x7fffff). Then check_exception old: 0xe new 0xe: a second page fault while delivering the first, so block 7 is v=08, a double fault, still with SP ffff8000007fff30. Then check_exception old: 0x8 new 0xe and Triple fault.


Hypotheses. A broken #DF handler would have run and printed something; it never ran, because the failure happened while the CPU was pushing the #DF frame. A missing gate would show #GP (vector 0x0d) with an IDT error code; there is none. The double fault was delivered on the same broken stack: SP is unchanged between blocks 6 and 7.


Root cause. The IST slots are empty: the serial log says IST1 top 0x0000000000000000 and tss: ist1 0000000000000000, and gate 8 reads 80108e000008dd30 (IST byte 00) where the correct kernel has 80108e010008dd30. The kernel was built with B2_FORGET_IST, so gdt::init(false) and idt::init(false) were called.


Fix. Fill the IST pointers (lines 40–44 of gdt.cc) and set the IST field for vector 8 (line 129 of interrupts.cc), that is, call both with true.


Prevention. The B2 stack-overflow test in every regression run, plus a boot-time assertion that tss().ist[0] != 0 and that gate 8's IST field is 1.
