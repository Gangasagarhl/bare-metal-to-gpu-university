Story hook

Teachers do not ask the cupboard office for a whole cupboard when they need three pencils. The school keeps a stationery cupboard with labelled boxes: a box of small items, a box of medium ones, a box of large ones. Each box is filled from a full cupboard drawer when it runs empty. Big requests, a whole crate of paper, still go straight to the cupboard office.

The person who runs the stationery cupboard has one habit that saves the school more than once: every returned item is wrapped in bright tape before it goes back in its box. When someone hands out an item and the tape is torn, somebody has been using an item after returning it. One day the torn tape appears on an item that nobody returned at all, and the real culprit turns out to be the neighbour in the box.

This chapter builds the kernel's stationery cupboard: a heap with size classes on top of the frames of F3-20 and the mappings of F3-21, every form of C++ new and delete, containers that work in the kernel, and poisoning that catches writes to freed memory.

What you will be able to do

  • Design a size-class slab allocator: caches, slabs, free lists, and how free finds a block's slab without a header per object.
  • Add a large-allocation path that maps fresh pages with a guard page in front.
  • Provide every replaceable form of operator new and operator delete, including the aligned and nothrow forms, without exceptions.
  • Write kernel containers (a vector, an intrusive list, a hash map) that report allocation failure instead of throwing.
  • Catch use-after-free and double free with poisoning, and prove "no leak" with frame accounting after a million allocations.
  • Reason from a poison report back to the real bug when the report names an innocent object.
Jargon box
Kernel heap
Simple words: the part of the kernel that hands out memory of any size, like new does in programs. Analogy: the stationery cupboard. Precise: a general-purpose allocator for kernel objects, built on the physical memory manager and the kernel page tables, offering kmalloc/kfree and the C++ allocation functions. D1
Slab allocator
Simple words: an allocator that cuts larger pieces of memory into many equal objects. Analogy: a drawer divided into equal compartments. Precise: an object-caching allocator in which each cache holds slabs (contiguous memory blocks) divided into objects of one size; Bonwick's design adds constructors and per-CPU layers that this chapter leaves out. D1
Size class (cache)
Simple words: one fixed object size the heap serves, such as 64 bytes. Analogy: one labelled box. Precise: in this heap, one of eight caches for 16, 32, …, 2048 bytes, each a list of 16 KiB slabs; a request is served by the smallest class at least as large as the size and the alignment. R2
Poisoning
Simple words: filling freed memory with a known pattern so that later writes to it can be detected. Analogy: bright tape on every returned item. Precise: writing a constant byte (here 0xDE) over a freed object and verifying the pattern when the object is handed out again; a mismatch reports a write after free. R3
Use-after-free
Simple words: using memory after giving it back. Analogy: writing in an exercise book after returning it. Precise: an access through a pointer to an object whose storage has been released; undefined behaviour in C++, and a classic source of kernel memory corruption. D2
Replaceable allocation functions
Simple words: the versions of operator new and delete a program may define itself. Analogy: the school writing its own stationery rules. Precise: the global operator new, new[], delete and delete[] in their plain, sized, aligned (std::align_val_t) and nothrow forms, whose definitions a program may provide to replace the library's. D2
Intrusive list
Simple words: a linked list whose links are stored inside the objects themselves. Analogy: students holding hands in a line instead of being written on a list. Precise: a list in which each element contains its own link member, so insertion and removal need no allocation. R2
Memory leak
Simple words: memory that was taken and never given back. Analogy: pencils that never come back to the cupboard. Precise: allocated storage no longer reachable or no longer intended to be used but never freed; measured here as the difference in free frames before and after a workload. R2

As in the whole course, "kernel" means the operating-system kernel; the "kernel (GPU)" of F6 is a function launched on a GPU.

Layer 1 — the kid explanation

The memory manager of F3-20 lends memory in pieces of 4096 bytes or more. Most things a kernel creates are much smaller: a name of 20 letters, a list entry of 24 bytes. Giving each one a whole page would waste almost all of it. So the kernel takes a few pages, cuts them into equal small pieces, and lends those. There are boxes for 16-byte pieces, 32-byte pieces, and so on up to 2048 bytes. Anything bigger gets whole pages.

When a piece comes back, the kernel paints it with a special pattern. When it lends the piece again, it checks that the pattern is still there. If not, someone wrote into the piece after giving it back, and the kernel says so loudly.

Analogy

The stationery cupboard has labelled boxes for small, medium and large items, refilled from the cupboard office in whole drawers. Big orders go to the cupboard office directly. Every returned item is wrapped in bright tape; torn tape means trouble.

Layer 2 — the student explanation

Size classes and slabs

The heap has eight caches for 16, 32, 64, 128, 256, 512, 1024 and 2048 bytes. Each cache owns a list of slabs: 16 KiB blocks from the PMM (order 2, so 16 KiB-aligned), reached through the direct map. A slab starts with a small header and is otherwise cut into objects of the cache's size; free objects form a singly linked list whose links are stored inside the free objects themselves, like the PMM's lists in F3-20. Allocation pops the head of a slab's free list; free pushes the object back.

How does kfree(p) know which cache p belongs to, without a header in front of every object? The slab is 16 KiB-aligned, so rounding p down to 16 KiB gives the slab header, which names the cache. A magic number in the header catches pointers that never came from the heap. This is the reason slabs are aligned to their own size D1.

Alignment

Objects in a cache are aligned to the cache's size: the first object starts at the first multiple of the size after the header, and every object is one size further. So a request with alignment 256 is served by a cache of at least 256 bytes, even if the size is smaller. Larger alignments, up to a page, go to the large path, which returns page-aligned memory. The lab's operator test shows new Aligned256 landing on a multiple of 256 R2.

The large path

Requests above 2048 bytes get whole pages. The heap asks the environment for pages + 1, writes a header (magic and page count) into the first, and returns the address of the second. The kernel's environment does not take contiguous frames for this: it allocates frames one by one and maps them consecutively in a virtual region of its own (0xffffd00000000000), leaving an unmapped guard page before each block. A large buffer therefore needs no contiguous physical memory, and running off its beginning faults. The lab's new int[1000] (4,000 bytes) came back as 0xffffd000000bb000, page-aligned, in that region R2.

C++ allocation without exceptions

The C++ standard lists the replaceable global allocation functions: plain, array, aligned (with std::align_val_t) and nothrow forms of new, and the matching delete forms including sized ones D2. new.cc defines all of them on top of kmalloc/kfree. The kernel has no exceptions, so the throwing forms cannot throw std::bad_alloc; they panic with the size instead. The nothrow forms return nullptr, which kernel code that can handle failure uses. The test asks for 4 TiB with nothrow and gets 0x0000000000000000 R2. One surprise: std::nothrow is an object defined in the C++ runtime library, which the kernel does not link; the link fails until the kernel defines it itself (lines 12–14 of new.cc).

Containers that can fail

The standard containers throw on allocation failure and pull in parts of the library a freestanding kernel does not have. containers.h provides three small ones whose operations return false when memory runs out: KVector (a growable array), IntrusiveList (links inside the elements, so insertion never allocates: the shape of every run queue in OS303), and KHashMap (open addressing with 64-bit keys) R2.

Layer 3 — the engineer's depth

One allocator, two environments

heap.h knows nothing about the kernel. It receives an environment of six functions: get and put a slab, get and put pages, decide whether a pointer is large, and report an error. The kernel's environment (kheap.cc) uses the PMM, the page tables and PANIC. The host test's environment uses aligned_alloc and records reports instead of panicking. The same 278 lines therefore run under AddressSanitizer on the host, where any out-of-bounds access in the allocator's own bookkeeping is caught at once, and in the kernel R1. This is the curriculum's third acceptance test for B5, and in this build it found two real bugs before the kernel ever ran.

Poisoning in detail

New slabs are poisoned when they are cut into objects; freed objects are poisoned again, except their first 8 bytes, which hold the free-list link. alloc_small checks bytes 8 to size − 1 of the object it hands out; any byte that is not 0xDE produces a report naming the cache, the object, the offset and the value found (lines 233–239). free detects a double free cheaply: if the last byte is poison, it walks the slab's free list to confirm (the walk is slow but runs only in that suspicious case).

What poisoning cannot catch: a write after free that lands on the link bytes, a write that happens to store 0xDE, a read after free (reads change nothing), and a bug in an object that is never reused. Production kernels add more tools (red zones after each object, quarantines that delay reuse, a sanitizer for kernel memory) D3. The use-after-free test of the lab writes 'X' at byte 20 of a freed 48-byte object (in kmalloc-64); the next allocation of that size reports byte 20 = 0x58 R3.

The million-allocation stress test

The stress test keeps 4,096 slots. At each step it picks a slot at random: if it is full, it checks the pattern written at the first and last byte and frees it; otherwise it allocates a random size (2 bytes to 2 KiB, and 0.1 % between 4 KiB and 64 KiB) with a random alignment (1 to 256) and writes a pattern into both ends. After one million allocations it frees everything, returns empty slabs to the PMM (trim), and compares the PMM's free frames with the value before the test R2.

The comparison has one subtlety: the large path maps pages in a fresh virtual region, so it creates page-table pages, which F3-21's address space never frees. The test counts them and requires "free frames after + new table pages = free frames before". The run: 32,395 before, 32,374 after, 21 new table pages: no frame leaked, and 0 corrupted blocks R2. The bump pointer of the large region never reuses virtual addresses, so a dangling pointer to a freed large block faults instead of reaching a new owner; the region is 1 TiB, enough for a test, not for a kernel that runs for years (an extension).

Costs and choices

Worst-case internal waste is a little under half of each object (a 1,025-byte request takes 2,048), plus the header slot in each slab. One slab per cache is kept even when empty, to avoid handing a slab back and forth on alternating allocate and free. There is no lock: the heap is single-CPU and must not be called from interrupt handlers yet; OS303 adds per-CPU caches and a lock. Bonwick's design also caches constructed objects, which this heap does not D1.

Not verified — check before relying on this

The exact list of replaceable allocation functions and which forms a compiler calls for which expressions (for example, when sized delete is used, and that aligned forms are used for alignments above the default new alignment) is written from memory: check the C++ standard's [new.delete] and [expr.new] sections (D2). The statement that std::nothrow lives in libsupc++ comes from the link error seen in this build, not from the library documentation. The description of Linux's tools (KASAN, slab red zones) is from memory (D3).

How the hardware actually does it

The heap has no hardware of its own: it is pure bookkeeping over frames and mappings. Two hardware facts still shape it. First, caches and alignment: objects aligned to their size never straddle more cache lines than necessary, and two objects of different owners in one 64-byte line can make two CPUs fight over that line (false sharing, SP203); per-CPU caches in OS303 avoid it D4. Second, the large path's guard pages use the MMU of F3-21: an overrun before a large block hits an unmapped page and faults immediately, which no amount of software checking can match for speed.

The direct map uses 2 MiB pages for most of RAM, so small objects live in large pages and cost few TLB entries; the large path uses 4 KiB pages so that each block can have its own guard. That trade-off (TLB reach versus fine-grained protection) appears again in user-space allocators.

Watch out

Untested on hardware. Timing does not matter for correctness here, but the stress test's run time under TCG (about ten seconds) says nothing about real hardware speed; do not quote it as a performance figure.

Worked example

Which cache and which address does kmalloc(300, 256) use, and how does kfree find its way back?

  1. need = max(300, 256) = 300. Smallest class ≥ 300: 512 (kmalloc-512).
  2. The first object of a 512-byte slab starts at first_offset(512): the header is 40 bytes (sizeof(Slab): two 4-byte fields and four 8-byte pointers), rounded up to 512 → offset 512. Objects at 512, 1024, …, 15,872: 31 objects per slab.
  3. The address is the slab's base (a multiple of 16 KiB) + a multiple of 512: aligned to 256 as asked (and to 512).
  4. kfree(p): is_large(p) is false (not in 0xffffd…); p & ~0x3FFF is the slab header; its magic is 0x51AB51AB; its cache pointer names kmalloc-512; bytes 8 to 511 are poisoned and the object goes on the slab's free list.

Compare with the lab's new Aligned256 (300 bytes of data with alignas(256), so sizeof is 512): the run printed an address ending in …200, a multiple of 512 R2.

Where the analogy breaks


    

  • Tape on a returned pencil is on the pencil. Poison is in the memory that the next owner will use, and the free-list link occupies part of it, so the first bytes of a free object are not protected.
    • 

  • A stationery cupboard knows who took what. The heap does not record owners; a leak shows only as a count that does not return to its start value.
    • 

  • Boxes in a cupboard are separate. Objects in a slab are neighbours in memory, so one object's overrun is another object's corruption (the forensic lab).
    • 




Common mistakes and debugging


    

  • Slabs not aligned to their size: slab_of rounds to the wrong header; the magic check catches it.
    • 

  • Forgetting the sized and aligned delete forms: link errors, or the library's version being expected.
    • 

  • Counting leaks without trimming: empty slabs kept by the caches look like leaked frames.
    • 

  • Ignoring page-table pages in leak accounting: the large path creates tables that are never freed.
    • 

  • Allocating in an interrupt handler before the heap has a lock: the interrupted code may be in the middle of alloc.
    • 

  • Trusting the report's object: the poison report names the object where corruption was found, not where it was made. Look at neighbours and at the free-list links (the forensic lab).
    •

Summary


    

  • Eight size classes from 16 to 2048 bytes, each a list of 16 KiB slabs; larger requests get mapped pages after a guard page.
    • 

  • Slabs aligned to their size let free find the slab header by rounding down.
    • 

  • Alignment is served by choosing a class at least as large as the alignment.
    • 

  • All replaceable new/delete forms are defined; throwing forms panic, nothrow forms return nullptr.
    • 

  • Poisoning catches writes after free and double frees, not reads, and not writes to the link bytes.
    • 

  • Leak checks count frames after trimming, and account for page-table pages.
    • 

  • A poison report shows where corruption was found; the cause may be a neighbour's overrun.

Forensic lab answer key


Observation. Names 0–4 were allocated at …13c040, …080, …0c0, …100, …140, consecutive objects of one kmalloc-64 slab. The panic came during the next allocation (name 5) and names object …13c100, which is name 3, still in use; byte 8 of "pci-0000:00:1f.2-…" is the colon, 0x3a.


Hypotheses. The poison check is right: it found a byte that is not 0xDE in an object the free list handed out. Name 3 was never freed (the free loop comes after the panic point). So the free list itself must have pointed at name 3: corruption of a link.


Root cause. Name 3 has exactly 64 characters. copy_name allocates len bytes when len ≥ 64 (the comment's "at most 64" forgot the terminator) and copies len + 1. The 65th byte, the zero terminator, lands on byte 0 of the next object, …140, which was free: byte 0 is the low byte of its free-list link, which pointed to …180. Little-endian: the low byte 0x80 becomes 0x00, so the link now reads …100. Name 4 takes …140 (its poison is intact, bytes 8–63); the free-list head becomes …100; name 5's allocation returns name 3's memory, and the poison check finds name 3's text at byte 8 (bytes 0–7 are not checked, because they normally hold the link).


Fix. Allocate len + 1 bytes always: kmalloc(len + 1). Better, use a bounded copy with an explicit maximum and reject longer names.


Prevention. Red zones: a few guard bytes with a pattern after every object, checked at kfree (and periodically), report the overrun at the object that made it; the lab's step 4 builds it. The host test with AddressSanitizer would also have caught copy_name at the first long name, if the name code were tested on the host.
