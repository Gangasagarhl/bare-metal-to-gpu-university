Story hook

The school has two ways to tell everyone something: the noticeboard in the hall, which anyone walking past can read, and the loudspeaker, which reaches the caretaker's room even when nobody is in the hall. Messages carry a label (for your information, warning, emergency) so people know which ones to read first. Only one person may speak on the loudspeaker at a time; there is a key to the microphone.

One morning the fire alarm goes off while the deputy head is halfway through an announcement, holding the microphone key. The principal runs to the microphone to say "leave the building", finds it locked, and waits politely for the key. The school stands in silence, waiting for an announcement that never comes. Everyone agrees afterwards: in an emergency, nobody waits for the key.

This chapter builds the kernel's noticeboard (a text console drawn into a framebuffer), keeps the loudspeaker (the serial port of F3-18), adds message levels and a lock, prints a boot banner with the machine's name read from the firmware's SMBIOS tables, and makes sure that a panic speaks even when the lock is held.

What you will be able to do

  • Find QEMU's display device on PCI, set a 640 × 480 × 32 mode, and map its framebuffer write-combining.
  • Draw text with a bitmap font, scroll, and colour lines by log level.
  • Prove the screen is right with a screenshot test: replay the serial log on the host and compare the image pixel by pixel.
  • Parse SMBIOS entry points and structures of types 0, 1 and 2 for a boot banner, and show that QEMU's -smbios option changes it.
  • Design an output lock that interrupt handlers cannot deadlock on, and a panic path that never waits for it.
  • Diagnose a silent hang from a register dump, addr2line and a disassembly.
Jargon box
Framebuffer
Simple words: a block of memory whose bytes are the pixels on the screen. Analogy: the noticeboard: what you pin there is what people see. Precise: a region of (usually device) memory in which each pixel has a fixed position and format; in this lab, 640 × 480 pixels of 32 bits (0x00RRGGBB), one row after another, mapped from the display device's BAR0. D2
Bitmap font
Simple words: letters stored as little grids of on and off pixels. Analogy: stencils for the noticeboard. Precise: a table mapping each character to a fixed-size pixel pattern; this course draws its own 5 × 7 font in a 6 × 10 cell. R2
Log level
Simple words: a label saying how important a message is. Analogy: "for your information", "warning", "emergency" on a notice. Precise: an ordered severity (here Debug < Info < Warn < Error) attached to each message, used to filter output and to choose its colour. R1
SMBIOS
Simple words: tables in which the firmware describes the machine: maker, model, firmware version. Analogy: the plaque at the school gate. Precise: the DMTF System Management BIOS specification: an entry point (found by an anchor string, 32-bit "_SM_" or 64-bit "_SM3_") gives the address of a table of typed structures (type 0 firmware, type 1 system, type 2 baseboard, …), each a formatted area followed by strings. D3
Write-combining
Simple words: a way for the CPU to collect several writes and send them to a device together. Analogy: carrying a whole stack of notices to the board in one trip. Precise: a memory type in which writes may be buffered and merged before reaching memory, with weak ordering; selected for a page through the PAT (F3-21). D4
Deadlock
Simple words: waiting for something that will never happen, because the one who could make it happen is waiting too (or is you). Analogy: the principal waiting for the microphone key the deputy will never return. Precise: a state in which a set of execution contexts each wait for a resource held by another member of the set; here a CPU spinning for a lock it already holds. D5
Panic mode
Simple words: the kernel's emergency state, in which it only tries to report and stop. Analogy: the fire alarm rule: nobody waits for the key. Precise: in this kernel, a flag set once by the panic or fatal-exception path; from then on output ignores the output lock and the framebuffer switches to the panic screen. R3
Screendump
Simple words: a picture of the emulated screen, saved by QEMU. Analogy: a photograph of the noticeboard. Precise: the QEMU monitor command screendump FILE, which writes the display's current contents as an image (PPM by default). D6

As in the whole course, "kernel" means the operating-system kernel; the "kernel (GPU)" of F6 is a function launched on a GPU.

Layer 1 — the kid explanation

A screen is a big grid of coloured dots. The computer keeps one number for every dot in memory; change the number and the dot changes colour. To write a letter, the kernel looks up a tiny picture of the letter (five dots wide, seven tall) and colours those dots. When the screen is full, it moves every line up by one and writes at the bottom.

Every message has a label: debug, info, warning or error, and each label has its own colour. Only one part of the kernel may write at a time, so there is a lock. But when the kernel crashes, it ignores the lock: a crash report that waits politely is no use to anyone.

Analogy

The noticeboard is the screen, the loudspeaker is the serial port, the labels on notices are the levels, and the microphone key is the lock. In a fire, nobody waits for the key.

Layer 2 — the student explanation

Finding a framebuffer

The curriculum's milestone assumes a UEFI boot, where the firmware's Graphics Output Protocol hands the kernel a framebuffer address, its size and a pixel format D2. This course boots with Multiboot through QEMU's -kernel option (F3-18), which gives no framebuffer, so the kernel sets one up itself on QEMU's standard VGA device (-vga std). It scans PCI bus 0 for vendor 0x1234, device 0x1111 (the configuration mechanism of F1-45), reads BAR0 for the framebuffer's physical address, and programs the device's Bochs "DISPI" registers: width, height, 32 bits per pixel, enable with linear framebuffer R1. The lab's log: device at slot 2, BAR0 fd000000, DISPI id b0c5, mode 640 × 480 mapped at 0xffffe00000000000.

A console on pixels

Each character occupies a 6 × 10 cell: 5 × 7 pixels of glyph, a column and three rows of space. That gives 106 columns and 48 rows. The font is the university's own, drawn by hand in font5x7.h (lower-case letters use the upper-case shapes, a stated simplification). FbConsole keeps a cursor; put draws a cell; a newline at the last row copies every pixel row up by ten and clears the last text line. It is a header with no hardware in it, so the host checker can run the same code into an array.

Levels, prefixes and colours

klog(level, fmt, …) drops messages below the minimum level, takes the lock, sets the colour for the level (grey, light grey, yellow, red), prints a prefix (a sequence number [#0001] now, a timestamp once F3-25 provides a clock), the message and a newline, and releases the lock. All of it goes through kprint's fan-out of F3-18 to the serial sink and the console sink. The serial log is the record; the screen is for a human in front of the machine.

The SMBIOS banner

The boot banner names the machine from SMBIOS. The kernel scans 0xF0000–0xFFFFF on 16-byte boundaries for "_SM3_" (or "_SM_"), checks the entry point's checksum, and walks the structures. QEMU 8.2.2 with SeaBIOS provides a 3.0 entry point at 0xf52d0, eight structures, and the banner "Booted on: QEMU Standard PC (i440FX + PIIX, 1996)" with "Firmware: SeaBIOS, version 1.16.3-debian-1.16.3-2, date 04/01/2014". With -smbios "type=1,manufacturer=OS302 Lab,product=Kernel I Test Board" the banner says "Booted on: OS302 Lab Kernel I Test Board" R4. QEMU's pc machine has no type 2 structure, which the banner says plainly.

A lock interrupts cannot deadlock

Output from two places at once would interleave characters, so klog holds a lock. A plain spinlock (SP203) is not enough: if an interrupt handler logs while the code it interrupted holds the lock, the handler spins forever on its own CPU. So log_lock_acquire first saves the flags and clears the interrupt flag, then spins; log_lock_release restores the flags, turning interrupts back on only if they were on D5. Exceptions cannot be masked, though: a page fault inside a locked region reaches its handler with the lock held. That is the case the panic path must survive.

Layer 3 — the engineer's depth

The panic path

The rule: once the kernel decides it is dying, nothing on the reporting path may wait for anything. kprint_panic_mode() (F3-18's kprint.cc, lines 47–57) sets a flag once and calls the panic-screen hook; from then on kvprintf does not take the lock (line 61). The exception handler of F3-19 calls it for every non-recoverable exception before printing, and panic_at calls it as its second action, after cli. The panic screen clears the framebuffer to dark red (0xa01010) and writes "*** KERNEL PANIC: THE SYSTEM IS HALTED ***"; the report follows in white.

Ignoring the lock has a cost: if another CPU is printing at that moment, the outputs interleave, and a half-drawn console state (cursor, colours) may be inconsistent. On one CPU, the code that held the lock will never run again, so nothing is lost. With several CPUs (OS303), the panicking CPU must also stop the others (an inter-processor interrupt) before it trusts any shared state; Linux's panic path does both D7.

The acceptance test, "panicking while holding the log lock": the test kernel logs a warning, calls log_lock_acquire(), and executes ud2. The run prints the exception, the registers and "PANIC at ../F3-19/interrupts.cc:119: unhandled exception 6 (#UD invalid opcode)", then exits with status 35 R3. A deadlock would end at the 30-second time limit with 124.

Write-combining and the framebuffer

A framebuffer is device memory. Mapped uncached, every 4-byte pixel write is a separate bus transaction; mapped write-back, writes may sit in the cache and never reach the device in time. Write-combining collects writes into buffers and sends them in bursts, which suits a stream of pixels D4. The kernel reprograms PAT entry 4 to write-combining (the MSR changed from 0007040600070406 to 0007040100070406) and maps the framebuffer with the PAT bit set (F3-21's kPat4K). Under TCG, memory types are not modelled, so this setting has no visible effect in the lab: it is correct by reading, not by test.

The screenshot test

Pixel tests are fragile when the reference is a stored image: any font change breaks them. This lab builds the reference instead. The host program fbcheck reads QEMU's screendump (a PPM file), reads the serial log, replays every line after "console: started" through the same FbConsole and font with the same colours, and compares all 307,200 pixels. The run: 61 lines replayed, 0 pixels differ, a pixel-exact match R2. The replay works because the serial log and the screen receive the same characters from the same fan-out; a bug in the console (scrolling, wrapping, colours) shows as differing pixels, and the first difference is printed. The tolerance is zero; a real display path with scaling would need a documented tolerance, as the milestone allows.

The serial line, revisited

The serial sink is the 16550-compatible UART of F3-18, polled: each character waits until the transmitter holding register is empty. At 115,200 baud that is about 87 µs per character on a real line, so a 100-character log line costs nearly 9 ms of busy waiting: logging changes timing, which matters for the timer measurements of F3-25. The 16550's FIFO and an interrupt-driven, buffered sink are the usual fixes; a panic must still fall back to polling D1.

Not verified — check before relying on this

Written from memory and not checked against the documents: the Bochs/QEMU DISPI register numbers and ports (0x1CE/0x1CF, registers 0–4, enable bits 0x01 and 0x40) and the PCI ids 1234:1111 (the lab shows they work in QEMU 8.2.2, which is not a specification); the SMBIOS entry-point offsets (table address at 0x10 for "_SM3_", 0x18 for "_SM_", lengths at 0x0C and 0x16) and the string-number offsets of types 0, 1, 2 (D3); the PAT encoding of write-combining as 0x01 (D4); the UEFI GOP pixel-format names (D2); the 16550 timing figure (D1).

How the hardware actually does it

On real PCs booted through UEFI, the firmware's GOP driver has already set a mode and reports the framebuffer's base, size, resolution, pixels per scan line (often larger than the width: the pitch) and one of a few pixel formats (red-green-blue or blue-green-red with 8 bits each, a bit-mask format, or "blit only" with no framebuffer at all) D2. After the kernel exits boot services, it may only write pixels; changing the mode needs a real display driver (Track C and later). The DISPI interface used here exists only in emulators and some virtual machines.

A display controller scans the framebuffer out to the screen many times a second; the CPU's writes appear at the next scan, which can tear a scrolling image. Real consoles double-buffer or scroll by changing the scan-out start address. SMBIOS on real machines carries more structures (memory devices, processors, slots) and sometimes strings such as "To Be Filled By O.E.M.": a banner must cope with missing and placeholder strings D3.

Watch out

Untested on hardware. The framebuffer code works only with QEMU's standard VGA device; on real hardware, use the GOP framebuffer from the bootloader (Limine or UEFI) instead.

Worked example

Where does the character of column 10, row 3 start in the framebuffer, and how many bytes does one scroll move?

  1. Cell origin: x = 10 × 6 = 60, y = 3 × 10 = 30.
  2. Pixel index = y × pitch + x = 30 × 640 + 60 = 19,260; byte offset = 19,260 × 4 = 77,040 = 0x12CF0. Virtual address 0xffffe00000000000 + 0x12CF0.
  3. One scroll copies rows 10 to 479 into rows 0 to 469: (48 − 1) × 10 = 470 pixel rows × 640 pixels × 4 bytes = 1,203,200 bytes, then clears 10 rows (25,600 bytes).
  4. Which line is at the top after the lab's boot? The checker replays 61 lines ("console: started", 59 log lines, "B6 screen ready…"). Lines 1 to 47 fill rows 0 to 46; line 48 goes to row 47 and its newline scrolls once; every later line scrolls once more. After 61 lines: 61 − 47 = 14 scrolls, so the top row holds line 15, which is [#0014], and the bottom row is empty, waiting for the next line.

Check the last step against the zoomed picture in screen.out: the first two visible lines read "[#0014] [ INFO] SCRO" and "[#0015] [ INFO] SCRO" in the hand-drawn upper-case font R2. The three fb: lines never reach the screen: they are printed before the console exists.

Where the analogy breaks


    

  • A noticeboard keeps old notices; the console forgets lines that scroll off. Only the serial log is a record.
    • 

  • The deputy holding the microphone key could, in principle, come back. A CPU spinning for a lock it holds itself, with interrupts off, never lets the holder run again: the wait is provably endless.
    • 

  • Ignoring the key in a real fire has no cost. Ignoring the lock can garble output on a machine with other CPUs still running.
    • 




Common mistakes and debugging


    

  • Logging from an interrupt handler with a plain spinlock: a hang the first time an interrupt arrives during a log line.
    • 

  • Taking the lock on the panic path: the forensic lab.
    • 

  • Ignoring the pitch: on real displays a row can be longer than the width; the image slants.
    • 

  • Mapping the framebuffer write-back: pixels arrive late or in pieces on real hardware; under TCG, nothing shows the bug.
    • 

  • Trusting SMBIOS strings: string number 0 means "none"; strings may be missing or placeholders.
    • 

  • Comparing against a stored screenshot: one font change and every test fails; build the reference from the same code.
    • 

  • A silent hang: get the RIP from the QEMU monitor (info registers), then addr2line and objdump it.
    •

Forensic lab answer key


Observation. RIP = ffffffff80110ec2, which addr2line places in log_lock_acquire(), log.cc:53: the while loop with __atomic_exchange_n. HLT=0: the CPU is running. RFL = 00000002: IF (bit 9) is clear. The disassembly is the spin: mov %edx,%eax; xchg %eax,g_lock_word; test %eax,%eax; jne back to pause. RAX = 1: the last exchange returned 1, the lock is taken.


Hypotheses. A broken IDT would end in a triple fault and a reset (F3-19), not a CPU running in the log lock. An exception loop would show RIP in an exception stub and a growing count in an interrupt log. The evidence fits "waiting for a lock".


Root cause. The test took the log lock and executed ud2. The #UD handler's report calls kprintf, which takes the lock, already held by the same CPU, with interrupts off: no one can ever release it. In this kernel PANIC_KEEPS_LOCK compiled out the body of kprint_panic_mode (kprint.cc lines 49–56), so the handler's call to it did nothing and kvprintf still locked.


Fix. Remove -DPANIC_KEEPS_LOCK (in a real kernel: set the panic flag before the first print on every fatal path, and make kvprintf skip the lock in panic mode). The normal kernel does this and prints the full report (R3).


Prevention. Acceptance test 3, the B6_PANIC_TEST kernel, run on every build: it must exit with 35 within 30 seconds; a hang ends with 124 and fails the lab.
