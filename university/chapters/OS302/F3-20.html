Story hook

The caretaker leaves the principal a plan of the building: "rooms 1 to 40 usable; room 41 is the boiler, never enter; rooms 42 to 300 usable; the roof is under repair". The principal now has to hand out cupboards to teachers, every day, for years. Some teachers want one cupboard. The science teacher wants eight cupboards side by side, because the equipment does not fit in separate ones. Teachers return cupboards when they leave, but not always the way they borrowed them.

After a term, the school office notices something odd: every evening the list of free cupboards gets a little shorter, although every teacher swears they returned everything. One day the science teacher asks for two neighbouring cupboards and gets "none available", while the list still shows thousands of free ones. This chapter builds the cupboard office of your kernel, the physical memory manager, and then solves that mystery.

What you will be able to do

  • Read the firmware's memory map and explain each range type.
  • Normalise the map: round to pages, sort, merge, and subtract the kernel image, boot data and low memory.
  • Implement a bitmap allocator and a binary buddy allocator for 4 KiB frames, with contiguous, aligned allocations.
  • Account for every KiB of conventional memory: what the allocator manages and why the rest is not managed.
  • Test the allocator on the host against a reference model, and in QEMU with three memory sizes.
  • Diagnose a slow frame leak and the fragmentation it causes from allocator statistics over time.
Jargon box
Frame (physical page)
Simple words: one 4 KiB piece of real memory. Analogy: one cupboard. Precise: a naturally aligned 4 KiB block of physical address space, the unit the page tables map (larger page sizes are multiples of it). D1
Memory map (firmware)
Simple words: the firmware's list of which address ranges are RAM you may use and which are not. Analogy: the caretaker's room plan. Precise: a list of (base, length, type) entries delivered by the firmware or loader (BIOS E820 through Multiboot here, the UEFI memory map in A3); only "available" ranges may be used freely. D2 D3
Physical memory manager (PMM)
Simple words: the part of the kernel that hands out and takes back frames. Analogy: the cupboard office. Precise: an allocator over physical frames, built from the memory map, offering allocation of single frames and of contiguous, aligned runs. D4
Bitmap allocator
Simple words: one bit per frame: 1 used, 0 free. Analogy: a tick list with one box per cupboard. Precise: a frame allocator whose state is a bit array; allocation searches for a clear bit (or a run of them). D4
Buddy allocator
Simple words: an allocator that keeps memory in blocks of 1, 2, 4, 8… frames, splitting big blocks and joining neighbours back. Analogy: cupboards grouped in pairs, pairs of pairs, and so on; a returned cupboard rejoins its partner when the partner is free. Precise: a power-of-two allocator: a block of order k has 2^k frames and is aligned to 2^k frames; its buddy is found by flipping bit k of its frame number; freeing merges buddies recursively. D5 D6
Order
Simple words: the size class of a buddy block, as a power of two. Analogy: "a group of 2^order cupboards". Precise: the exponent k of a block of 2^k frames; this kernel uses orders 0 (4 KiB) to 10 (4 MiB). R2
Fragmentation (external)
Simple words: enough free memory in total, but not enough of it in one piece. Analogy: many free cupboards, none of them next to another free one. Precise: the state in which free memory is split into blocks smaller than a request, so the request fails although the free total exceeds it. D5 R4
Direct map
Simple words: a window in the kernel's address space where every physical address can be read at a fixed offset. Analogy: a master key that opens every cupboard by its number. Precise: a virtual range (here 0xffff800000000000 + physical) mapping all of RAM, used by the kernel to touch frames it does not otherwise map. R1

"Kernel" here is the operating-system kernel; "kernel (GPU)" in F6 names a GPU function, an unrelated meaning.

Layer 1 — the kid explanation

A computer's memory is a long row of bytes. The kernel cuts it into small pieces of 4096 bytes and lends them out: to page tables, to the heap, to programs. It must never lend a piece twice, and it must never lend a piece that belongs to someone else, like the firmware or the kernel's own code.

So the kernel first reads a list from the firmware that says which parts are free memory. It removes the parts it already uses. Then it keeps the rest in groups of 1, 2, 4, 8 and more pieces, so that it can quickly find a big group when someone needs many pieces side by side. When pieces come back, it joins neighbours into bigger groups again.

Analogy

The caretaker's plan (memory map) says which rooms exist and which are off limits. The cupboard office (PMM) lends cupboards (frames). It keeps them in pairs, pairs of pairs and so on, so that a teacher who needs eight side by side can get them at once. A cupboard returned next to its free partner is joined with it again.

Layer 2 — the student explanation

The map the firmware gives us

On a BIOS machine the firmware reports memory through a list of ranges (the E820 interface); a Multiboot loader copies that list into the information structure, with entries of base, length and type D2. Type 1 is available RAM; other types are reserved, ACPI tables that may be reclaimed after reading, ACPI non-volatile storage, or bad memory. A UEFI loader passes the UEFI memory map instead, with more types (boot services data, runtime services code and so on) that the kernel maps onto the same idea D3.

The lab prints QEMU's map for 128 MiB: available below 640 KiB, two reserved ranges below 1 MiB (the extended BIOS data area and the BIOS), available from 1 MiB to 128 KiB below 128 MiB, a 128 KiB reserved range at the top (where SeaBIOS keeps the ACPI tables, as F3-24 shows), the firmware's flash below 4 GiB, and one large reserved range at 0xfd00000000 R2. Note what is not in the list at all: the VGA hole at 640 KiB–768 KiB, the PCI device windows, the local APIC. "Not listed" is not "free".

Normalising

Maps can overlap, be unsorted, or start and end in the middle of a page. memmap.h rounds every available range inwards to whole pages (a partial page at the edge is not ours), sorts, and merges overlapping or touching ranges. Then it subtracts what the kernel keeps, rounding those ranges outwards: everything below 1 MiB (firmware data and the real-mode area, kept for later use such as starting other CPUs in OS304), the kernel image up to the end of BSS, the boot information and the map itself, and the allocator's own state.

First allocator: a bitmap

One bit per frame is the simplest correct allocator: start with all bits set ("used"), clear the bits of the usable ranges, and allocate by searching for a clear bit. bitmap_pmm.h does this and is tested on the host. It is easy to trust but slow to search, and finding 512 contiguous clear bits aligned to 2 MiB means scanning. The kernel therefore uses a buddy allocator, which the curriculum names as the second step D7.

The buddy allocator

Free memory is kept as blocks of 2^k frames, each aligned to its own size, on one list per order k. To allocate order k, take a block from list k; if it is empty, take a bigger block and split it in halves until one half has the right size, putting the other halves on their lists. To free, look at the block's buddy, the block of the same size that it was split from: its frame number is the block's frame number with bit k flipped. If the buddy is free and has the same order, unlink it and merge, then repeat one order higher D5. Figure 2 shows both directions. Allocation and free cost at most one step per order, and contiguous, aligned requests come for free: an order-9 block is 2 MiB and 2 MiB-aligned, exactly what a 2 MiB page or a DMA buffer needs.

Layer 3 — the engineer's depth

Where the allocator keeps its state

The free lists are doubly linked lists whose nodes live inside the free frames themselves: a free frame is not used by anyone, so its first 16 bytes can hold the next and previous pointers. The allocator reaches a frame's bytes through a "window", the kernel's direct map (0xffff800000000000 + physical) R1. In the host test the window is an ordinary array, so the same code runs on both sides. Besides the lists, the allocator keeps one state byte per frame: 0xFF for "not the head of a free block", or the order of the free block that starts there. Merging needs that byte: the buddy may be merged only if it heads a free block of the same order; a buddy that is free but part of a bigger or smaller block must not be touched.

With check_order on, the byte also records the order of each allocated block (0x80 | order). Then a free with the wrong order, or a second free of the same block, is refused. The lab kernel runs with checking on; the forensic driver runs with it off, which is the configuration in which its bug stays invisible.

How big is the state, and where does it go?

One byte per frame up to the highest usable address: for 128 MiB, 0x7fe0000 / 4096 = 32,736 frames, rounded to 32 KiB. The state needs memory before an allocator exists, so pmm.cc takes it from the first usable range big enough, then subtracts it from the map. For the 4 GiB machine the state is 1,280 KiB: the highest usable address is 5 GiB, because QEMU places 1 GiB above 4 GiB (R2). That is the price of a dense array: memory holes cost state bytes too. Larger kernels keep a per-frame structure as well (Linux's struct page) and handle sparse layouts with sections D8.

Adding a range

add_frames cuts each usable range into the largest aligned blocks that fit: at each position it tries order 10 and lowers the order while the position is not aligned or the block would run past the end. The 128 MiB machine's range runs from frame 0x11e to frame 0x7fe0: it begins with blocks of order 1, 5, 6, 7 and 9, continues with order-10 blocks and ends with blocks of order 9, 8, 7, 6 and 5. The lab's "free blocks by order" line at boot, 0 1 0 0 0 2 2 2 1 2 30, is exactly that count R2. Each block is released through the normal free path, so neighbours merge as they arrive.

Accounting: every KiB explained

The acceptance test asks that free memory after boot match "conventional memory minus the kernel within a documented tolerance". Rather than a tolerance, the kernel counts every subtraction and prints an equation that must hold exactly: conventional = managed + below 1 MiB + kernel + boot info + metadata + rounding. For 128 MiB: 130,559 = 129,800 + 636 + 88 + 0 + 32 + 3 KiB. The 3 KiB of rounding is the partial page at 0x9fc00 (639 KiB is not a whole number of pages); boot info is 0 because QEMU put it below 1 MiB, where it is already excluded. The same equation holds for 1 GiB and 4 GiB R2. The documented tolerance is therefore zero; the design note should say so.

Testing

The host test pmm_host.cpp checks normalisation and subtraction on hand-made maps; allocates every frame one by one and frees them all, checking that the free count and the shape of the free lists come back; and runs 200,000 random operations of random orders against a reference model (an owner number for every frame), checking at each allocation that the block is aligned and that none of its frames is already owned or outside the usable map, and at the end that the free count and the block shape come back R1. Under AddressSanitizer, an off-by-one in the window arithmetic is caught at once. In QEMU, the kernel repeats allocate-everything and free-everything, and allocates order 4 and order 9 to show alignment R2.

Not verified — check before relying on this

From memory, not from the documents: the Multiboot memory-map entry layout (a size field that does not count itself) and its type values 1–5 (Multiboot Specification, D2); the E820 interface and type meanings (ACPI Specification, "System Address Map Interfaces", D9); the UEFI memory types (UEFI Specification, D3); that the reserved range at 0xfd00000000 is QEMU's reservation for its own use on large address spaces (check the QEMU source or documentation, D10). The runs confirm only that QEMU 8.2.2 with SeaBIOS reported the ranges shown.

How the hardware actually does it

Physical memory has no "free" or "used" state in hardware: the memory controller answers any address that decodes to DRAM, and the platform's address decoders send other addresses to devices, firmware flash or nowhere D1. Which ranges are RAM is decided by the platform at boot: the firmware trains the memory, programs the decoders (including the PCI hole below 4 GiB, which is why QEMU's 4 GiB machine shows 3 GiB below and 1 GiB above 4 GiB), and reports the result in its memory map R2. Reading a reserved range may return device registers whose reads have side effects; writing it may change firmware state. That is why the allocator must take ranges only from the map's available type, and why F3-21 maps reserved ranges read-only or not at all.

DMA is the other hardware reason for contiguous allocation: many devices read and write physical addresses directly and need a buffer that is contiguous in physical memory, sometimes below a limit (for example 4 GiB for 32-bit DMA engines) D7. A buddy allocator can be split into zones by address for that purpose; this kernel has one zone and records the limit as an extension.

Watch out

Untested on hardware. On a real PC the memory map has many more entries, ranges may overlap, and some firmware reports ranges that are not page-aligned. The normaliser handles those cases in the host test, but no real firmware's map was read in this build. Never "test" an allocator on a real machine by writing to memory the map does not list as available.

Worked example

A free request: free(frame 0x7fc0, order 4) on the 128 MiB machine, after the lab's order-4 allocation at physical 0x7fc0000 (R2). Which blocks does the merge loop look at?

  1. Order 4: block 0x7fc0 (16 frames). Buddy = 0x7fc0 XOR 0x10 = 0x7fd0. When the order-4 block was split from a bigger one, 0x7fd0 stayed free at order 4, so merge: block 0x7fc0, order 5.
  2. Order 5: buddy = 0x7fc0 XOR 0x20 = 0x7fe0. Frame 0x7fe0 is physical 0x7fe0000, the start of the reserved ACPI range, and 0x7fe0 = 32,736 is also the number of frames the allocator tracks: the buddy lies outside the state array, so the loop stops (line 151). No merge.
  3. Result: one free block of order 5 at 0x7fc0 (128 KiB, 0x7fc0000–0x7fdffff), the end of the usable range. The allocation came from there in the first place: the order-4 list was empty, so alloc popped the block most recently pushed on the order-5 list (the one add_frames added last, at the end of the range) and split it.

Check: the run's line contiguous: order 4 (64 KiB) at 0000000007fc0000, aligned to its size: yes; 0x7fc0000 is a multiple of 0x10000.

Where the analogy breaks


    

  • A cupboard office can look inside a cupboard to see whether it is empty. The PMM cannot tell a used frame from a free one by its contents; only its own bookkeeping knows, which is why a wrong-order free corrupts it silently.
    • 

  • Cupboards are physically grouped in pairs. Frames are "paired" only by arithmetic (the XOR rule); nothing in the hardware groups them.
    • 

  • A teacher who keeps a cupboard too long is visible in the corridor. A leaked frame is invisible: it is neither on a free list nor owned by anyone.
    • 




Common mistakes and debugging


    

  • Trusting the map blindly: unsorted or overlapping entries, partial pages. Normalise first.
    • 

  • Forgetting to exclude the kernel or the boot information: the allocator hands out the page that holds your own code; the crash comes much later.
    • 

  • Merging with a buddy of a different order: the free lists end up with overlapping blocks. The state byte must equal the order.
    • 

  • Freeing with the wrong order: frames leak (smaller order) or blocks double-count (larger order). Record the order at allocation, at least in debug builds.
    • 

  • Touching a frame through a mapping that does not exist: before F3-21 only the boot direct map's 8 GiB are reachable; pmm.cc ignores RAM above that and says so.
    • 

  • Debugging: print the statistics line at intervals; a free count that falls while allocation and free counts stay equal is a size mismatch, not a missing free.
    • 




Transition box

Where you came from: F3-19, a kernel with exception reports but no memory management: every buffer was a static array. What carries over: the boot direct map, the panic and assertion machinery, and host testing of pure logic. What changes: memory becomes a resource the kernel hands out and takes back at run time; correctness now includes "never twice, never someone else's". What comes next: F3-21 uses these frames to build the kernel's own page tables, with permissions and guard pages, and replaces the boot tables.

Summary


    

  • The firmware's map lists RAM and reserved ranges; anything not listed as available is not ours.
    • 

  • Normalise: round available ranges inwards, kept ranges outwards; sort and merge.
    • 

  • A buddy allocator keeps aligned power-of-two blocks; the buddy of block f at order k is f XOR 2^k.
    • 

  • Free lists live inside free frames, reached through the direct map; one state byte per frame guards merging.
    • 

  • Exact accounting replaces a tolerance: every subtracted KiB is named.
    • 

  • A wrong-order free leaks frames silently and fragments memory; equal allocation and free counts do not prove there is no leak.
    •

Forensic lab answer key


Observation. Every 4,000 packets: free frames drop by exactly 4,000 (32,450 → 28,450 → … → 16,450), allocations and frees both grow by 4,000, and the order-0 free-block count grows by 4,000 while the large blocks disappear (order 10: 30 → 23 → 16 → 8 → 0).


Hypotheses. A missing free would make the free count lag the allocation count; they are equal, so every allocation was freed. Fragmentation by long-lived allocations would not lose exactly one frame per packet. A size mismatch fits: one frame lost per packet, and one new order-0 free block per packet.


Root cause. The driver allocates order 1 (8 KiB, lines 62 and 70) and frees order 0 (line 63, 74). The first frame of each pair goes back as an order-0 block; the second is never freed. The returned frame cannot merge, because its buddy is the lost frame (Figure 2, row 4). After 16,000 packets there are 16,000 free frames, all single, and no two of them are buddies: an order-1 request finds no block of order ≥ 1 and fails at packet 16,226, with roughly 16,200 frames still counted as free.


Fix. Free with the order used for allocation: one constant for both (kRxOrder = 1), or let the allocator remember the order. With pmm::init(info, true) (order checking on), the first wrong-order free would have returned false; checking the return value would have stopped the driver at packet 1.


Prevention. Keep order checking on in debug builds; assert on the return value of every free; and watch the statistic "free frames versus allocations minus frees", which must stay constant in a steady-state driver.
