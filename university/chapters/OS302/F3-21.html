Story hook

Every student in the school has a locker number. Locker 12 in class A is not the same cupboard as locker 12 in class B: the school keeps a map from locker numbers to real cupboards, and each class has its own page in it. The principal's own staff lockers are on every page, in the same place, but marked "staff only". Some cupboards are marked "look, don't touch". Below the staff lockers there is a deliberately empty cupboard number with no cupboard behind it: anyone who walks past the end of the row bumps into it and an alarm rings.

Looking a number up in the full map takes four steps through four binders, so the principal keeps a sticky note of the last few look-ups. Once, a cupboard was given to a new teacher, but the old note was still on the principal's desk. The old owner's last delivery went straight into the new teacher's cupboard. The map was right; the note was wrong.

This chapter builds that map for the kernel: its own page tables, with permissions and guard pages, an API to map and unmap, and the discipline of clearing the sticky note, the TLB. It also teaches the exam skill of this course: walking a translation by hand from a QEMU monitor dump.

What you will be able to do

  • Split a 64-bit virtual address into its four table indices and offset, and walk the tables by hand from CR3 to the byte, using QEMU's monitor.
  • Build an address-space object with map, unmap, protect and translate over frames from F3-20.
  • Give each kernel section exactly the rights it needs: code read and execute, read-only data read-only and not executable, data and BSS writable and not executable.
  • Explain NX, write protection in kernel mode (CR0.WP), global pages and the PAT, and test that they work.
  • Place a kernel stack above an unmapped guard page and show the overflow is caught.
  • Diagnose a stale TLB entry that writes into memory the page tables no longer map.
Jargon box
Page table
Simple words: the table the CPU uses to turn the addresses a program uses into real memory addresses. Analogy: the map of lockers: locker number to real cupboard. Precise: in x86-64 4-level paging, a hierarchy of 4 KiB tables of 512 eight-byte entries (PML4, PDPT, PD, PT) rooted at CR3; each entry holds a physical address and permission bits. D1
PML4
Simple words: the top-level page table. Analogy: the first binder of the locker map. Precise: the page-map level-4 table whose physical address is in CR3; indexed by virtual address bits 47–39. D1 R3
Page-table entry (PTE)
Simple words: one line of a page table: where the page is and what may be done with it. Analogy: one line of the locker map, with "staff only" and "look, don't touch" marks. Precise: a 64-bit entry: present, writable, user, write-through, cache-disable, accessed, dirty, page-size or PAT, global, the physical address bits, and NX in bit 63. D1 R1
TLB (translation lookaside buffer)
Simple words: the CPU's small cache of recent translations. Analogy: the principal's sticky note of recently looked-up lockers. Precise: a processor cache of virtual-to-physical translations and their rights; not kept coherent with the page tables by hardware, so software must invalidate entries it changes (invlpg, a CR3 write, or other mechanisms). D1 R4
NX (no-execute)
Simple words: a mark that says "this page holds data; never run it as code". Analogy: a "no experiments in this room" sign. Precise: bit 63 of a paging entry, honoured when EFER.NXE is set; an instruction fetch from such a page raises a page fault with the instruction-fetch bit set. D1 R2
Guard page
Simple words: an address deliberately left unmapped next to a stack or buffer, so running off the end faults. Analogy: the empty cupboard number at the end of the row that rings an alarm. Precise: an unmapped page adjacent to a region that grows; an access raises a page fault instead of corrupting the neighbouring memory. R2
Global page
Simple words: a translation the CPU keeps even when it switches to another program's tables. Analogy: the staff lockers that are on every class's page. Precise: a leaf entry with the G bit set, while CR4.PGE is enabled; such TLB entries survive CR3 writes and are removed with invlpg or by toggling CR4.PGE. D1
PAT (page attribute table)
Simple words: a table that lets each page choose how the CPU caches it. Analogy: a choice of delivery methods per cupboard: keep a copy on the desk, or always walk to the cupboard. Precise: an MSR with eight memory-type entries; the PAT, PCD and PWT bits of a leaf entry select one, giving write-back, write-through, write-combining, uncached and other types per page. D1
Virtual address space
Simple words: all the addresses a program can use, whether or not memory is behind them. Analogy: all the locker numbers that could exist. Precise: with 4-level paging, 48-bit canonical addresses: a lower half 0–0x00007fffffffffff and an upper half 0xffff800000000000–0xffffffffffffffff. D1

"Kernel" means the operating-system kernel here; F6 uses "kernel (GPU)" for code launched on a GPU, which is a different idea.

Layer 1 — the kid explanation

Programs do not use real memory addresses. They use made-up numbers, and the processor translates each one into a real address by looking it up in a map that the kernel wrote. The map also says what is allowed: some places may only be read, some may never be run as instructions, and some numbers lead nowhere on purpose, so a mistake is caught.

The processor keeps a small notebook of translations it used recently, so it does not have to read the whole map every time. When the kernel changes the map, it must also tell the processor to forget the old notebook entry, or the processor will keep using it.

Analogy

The map of lockers turns a locker number into a real cupboard, in four binders. Marks on each line say "staff only" or "look, don't touch". The principal's sticky note remembers recent look-ups; when a cupboard changes hands, the note must be torn off too.

Layer 2 — the student explanation

Splitting an address

With 4-level paging a virtual address has 48 meaningful bits. The low 12 bits are the offset inside a 4 KiB page. The next four groups of 9 bits are indices into the four tables: bits 47–39 for the PML4, 38–30 for the PDPT, 29–21 for the PD and 20–12 for the PT. 9 bits select one of 512 entries, and 512 entries of 8 bytes fill exactly one 4 KiB page D1. Bits 63–48 must copy bit 47, which is what makes an address "canonical"; that rule splits the space into a lower and an upper half with a hole between them (F3-19's #GP test used an address in the hole).

An entry in the PD can map a 2 MiB page directly (page-size bit set) instead of pointing to a PT; an entry in the PDPT can map 1 GiB the same way D1. The boot tables of F3-18 used only 2 MiB pages. The kernel's own tables use 4 KiB pages for its image (so each section can have its own rights) and 2 MiB pages for most of the direct map (fewer tables, fewer TLB entries).

Rights

Each entry carries permission bits, and the effective right is the most restrictive along the walk: an address is writable only if every level allows writing, user-accessible only if every level allows user access, executable only if no level sets NX D1. This kernel keeps intermediate entries permissive (present, writable, user) and puts every restriction in the leaf, so one place decides. Two switches make the rights bite in kernel mode: EFER.NXE turns on the NX bit, and CR0.WP makes the CPU honour read-only pages even for ring-0 writes. Without WP, the kernel could write to its own .rodata unnoticed.

The address-space object

AddressSpace owns one PML4 and offers map (one 4 KiB page), map_2m, unmap (clear the entry and invalidate the TLB entry), protect and translate (a software walk). Missing intermediate tables are allocated from the PMM and zeroed. The kernel builds its space once at boot, switches CR3 to it, and from then on the boot tables are no longer used. The address space for each user process arrives in OS303; it will share the kernel's upper half.

Why the TLB matters for correctness, not only speed

A walk costs up to four memory reads, so the CPU caches results in the TLB. The CPU does not watch the page tables for changes: if the kernel clears an entry and does nothing else, the old translation may stay in the TLB and keep working D1. So every change that removes or reduces rights must be followed by invlpg for that address (or a CR3 reload for non-global entries). On a multiprocessor, other CPUs' TLBs must be told too (a TLB shootdown, OS304). The forensic lab shows what one forgotten invlpg does.

Layer 3 — the engineer's depth

Building the kernel space

build_kernel_space in paging.cc does four things. First it enables the CPU features: EFER.NXE (bit 11), CR0.WP (bit 16), CR4.PGE (bit 7); R2 prints EFER d00, CR0 80010011, CR4 a0 R2. Then it maps the kernel image section by section from the linker symbols of F3-18, with the least rights each needs, all global. Then it builds the direct map from the firmware's map: available RAM read-write and NX, using 2 MiB pages wherever a 2 MiB-aligned run fits and 4 KiB pages at the edges; reserved ranges below 4 GiB (ACPI tables, BIOS) read-only and NX, because later chapters read tables there; reserved ranges above 4 GiB not at all. Finally it switches CR3. For 128 MiB this costs 62 large pages, 1,024 small ones and 10 table pages R2.

Two details came from failures in this build. The legacy BIOS area 0xE0000–0xFFFFF is where F3-23 and F3-24 search for the SMBIOS and ACPI entry points, but QEMU's map lists only 0xF0000–0xFFFFF as reserved; without an explicit read-only mapping, F3-23's SMBIOS scan page-faulted at 0xf0000 before the reserved range was mapped. And two map entries can share a partial page (available up to 0x9fbff, reserved from 0x9fc00): the second mapping attempt then hits an existing entry, so the code checks translate before mapping a 4 KiB edge page.

The walk in code

AddressSpace::entry(virt, level, create) walks from the PML4 down to the requested level, computing each index as (virt >> (12 + 9 × (level − 1))) & 511, allocating and zeroing missing tables when asked, and refusing to descend through a 2 MiB leaf. translate is the same walk without allocation; at a 2 MiB leaf it keeps 21 offset bits instead of 12. The test of acceptance criterion 2 maps 1,000 random pages in a 4 TiB test region and checks the software walk against the CPU in two ways: translate must return the frame the test mapped, and a load through the mapping must read the value the test wrote through the direct map. Both agreed 1,000 times; the page-table count rose from 13 (10 at boot, 3 for the kernel stack) to 1,904, because random addresses rarely share tables R2.

The four acceptance tests

  1. Write to .rodata: page fault, error code 0x3 = present + write: "protection violation, write, supervisor mode" R2. Without CR0.WP the write would succeed.
  2. Execute from data: a frame from the PMM gets the byte 0xC3 (ret) and is called through the direct map. Error code 0x11 = present + instruction fetch; RIP and CR2 both equal the page address R2. (The curriculum says "from the heap"; the heap arrives in F3-22 and uses the same NX direct map, so this is the same test.)
  3. Translate agrees with a manual walk for 1,000 random addresses, as above; the "manual walk" by a person is the monitor session in Figure 1.
  4. Access after unmap faults: the test writes through a fresh mapping, so its translation is certainly in the TLB, then unmaps and reads: error code 0x0, page not present. Only the invlpg in unmap makes that fault happen (the forensic lab removes it).

The guard page, now with 4 KiB granularity

F3-19 had to sacrifice 2 MiB of the boot map for its guard. Now the kernel maps a 16 KiB stack at 0xffffff0000001000 and leaves 0xffffff0000000000 unmapped. The overflow variant recurses until RSP reaches ffffff0000000f30 and CR2 reads ffffff0000000f28: inside the guard page; the double fault is reported on IST1 as in F3-19 R5. Every kernel thread in OS303 gets a stack built this way.

Memory types and the PAT

Each leaf entry selects one of the eight PAT entries through three bits: PWT (bit 3), PCD (bit 4) and the PAT bit (bit 7 in a 4 KiB PTE, bit 12 in a large-page entry) D1. The MSR's reset value, printed in R2 as 0007040600070406, holds one byte per entry, entry 0 in the low byte: 06 (write-back), 04 (write-through), 07 (uncached-minus), 00 (uncached), repeated. So ordinary pages (all three bits 0) are write-back; PCD + PWT selects entry 3, uncached, which F3-24 uses for device registers. Write-combining, which a framebuffer wants, is not among the reset entries; F3-23 rewrites entry 4 to write-combining (value 01) and selects it with the PAT bit alone. Different memory types for the same physical page through two mappings must be avoided; the direct map therefore does not cover device memory D1.

What this design does not do

Page-table pages are never freed: unmapping leaves empty tables in place (the 1,891 tables added by test 3 stay allocated; R2's final statistics show it). A user-process address space must reclaim them on exit (OS303). There is no PCID (process-context identifiers would let TLB entries of several address spaces coexist), no 1 GiB pages, and no 5-level paging, which the curriculum lists for awareness D1.

Not verified — check before relying on this

From memory, and confirmed only as far as the runs show: the bit positions EFER.NXE = 11, CR0.WP = 16, CR4.PGE = 7; the PAT MSR number 0x277 and its encoding (00 UC, 01 WC, 04 WT, 05 WP, 06 WB, 07 UC-); the PAT bit position 7 in a 4 KiB PTE and 12 in a 2 MiB entry; the rule that effective rights combine all levels; the behaviour of global entries on CR3 writes. Check them in the Intel SDM Vol. 3, "Paging" and "Memory Cache Control" (D1), and the AMD64 APM Vol. 2, "Page Translation and Protection" (D2). The runs confirm: QEMU 8.2.2 accepts the entries, faults with the decoded error codes, prints the PAT value above, and the monitor's walk agrees with the kernel's (R2, R3).

How the hardware actually does it

The page walker is a hardware unit in each core. On a TLB miss it reads the PML4 entry from memory (through the caches), then the PDPT entry, the PD entry and the PT entry, checks rights at every level, and fills the TLB with the result. It also sets the accessed bit in each entry it uses and the dirty bit in the leaf on a write, which is why the lab's entries end in …27 (accessed set) and the leaf in …163 (accessed and dirty) D1 R3. Processors also cache upper-level entries in paging-structure caches, which is another reason the SDM's invalidation rules must be followed exactly D1.

QEMU's TCG emulates the walk and keeps its own software TLB per CPU. It behaves like real hardware in the way that matters here: a translation it has cached stays in use until invlpg or a CR3 write, as the forensic lab shows R4. How long a real CPU keeps an entry depends on the model and on what else runs; the bug may hide on one machine and appear on another, which is why it must be prevented by discipline rather than found by testing.

Watch out

Untested on hardware. Real CPUs differ in TLB sizes and in which paging features they support (1 GiB pages, PCID, 5-level paging); query CPUID before using any of them. The stale-TLB behaviour on a particular real processor was not observed in this build.

Worked example

Exam P of this course: "walk a page-table translation by hand from a QEMU monitor dump". Here is the lab's dump (R3), solved the way the exam expects.

  1. Get CR3. info registers shows CR3=0000000000133000. The PML4 is at physical 0x133000 (the low 12 bits of CR3 hold flags, all zero here).
  2. Split the address 0xffffffff80114008. In binary the bits 47–39 are all ones: PML4 index 511. Bits 38–30: 0x80114008 has bit 31 set and bit 30 clear, and bits 32–38 are ones, so the 9-bit field is 1 1111 1110 = 510. Bits 29–21: 0x80114008 & 0x3FE00000 = 0, index 0. Bits 20–12: (0x114008 >> 12) & 511 = 0x114 = 276. Offset: 0x008.
  3. PML4 entry at 0x133000 + 8 × 511 = 0x133ff8: xp /1gx 0x133ff8 → 0x0000000000134027. Bit 0 set: present. Next table: 0x134000.
  4. PDPT entry at 0x134000 + 8 × 510 = 0x134ff0 → 0x135027. Bit 7 clear: not a 1 GiB page. Next: 0x135000.
  5. PD entry at 0x135000 + 0 → 0x136027. Bit 7 clear: not a 2 MiB page. Next: 0x136000.
  6. PT entry at 0x136000 + 8 × 276 = 0x1368a0 → 0x8000000000114163. Frame 0x114000; flags 0x163 = present (1), writable (2), accessed (0x20), dirty (0x40), global (0x100); bit 63 = NX; bit 2 clear = supervisor only.
  7. Physical address 0x114000 + 0x008 = 0x114008. Check: xp /1gx 0x114008 shows the kernel's value 0x5452414e534c4154, and gva2gpa agrees: gpa: 0x114008.

Note also that the result is consistent with the higher-half rule of F3-18: virtual 0xffffffff80114008 − 0xffffffff80000000 = physical 0x114008.

Where the analogy breaks


    

  • A locker map has one level; page tables have four, and the tables themselves are ordinary frames that the kernel must allocate, map and (in OS303) free.
    • 

  • A sticky note that disagrees with the map is visibly wrong. A stale TLB entry gives no sign at all: the software walk (Figure 1) says "not mapped" while the CPU still writes through the old translation.
    • 

  • "Look, don't touch" is a request; read-only pages are enforced by hardware, but only once CR0.WP is set for kernel code.
    • 




Common mistakes and debugging


    

  • Restrictive intermediate entries: a read-only PDPT entry silently makes a whole 1 GiB read-only. Keep restrictions in the leaves, or document them.
    • 

  • Forgetting EFER.NXE before setting bit 63: the CPU treats bit 63 as reserved and raises a page fault with the reserved-bit flag (0x8 in the error code).
    • 

  • Mapping MMIO through the write-back direct map: device registers cached; writes delayed or merged. Map devices separately and uncached (F3-24).
    • 

  • Changing an entry without invlpg: works in some runs, fails in others (the forensic lab).
    • 

  • Switching CR3 to tables that do not map the current code or stack: immediate triple fault. Map the kernel image and the stack before activate.
    • 

  • Debugging: the monitor's info mem and info tlb, xp and gva2gpa (Listing 4), and -d int for the faults. In gdb, monitor info mem works through the gdb stub.
    • 




Transition box

Where you came from: F3-20, frames handed out by a buddy allocator, reached through the boot direct map. What carries over: the higher-half layout and direct-map offset of F3-18, frames from the PMM (now also for page tables), the exception reports of F3-19 (every test here ends in one). What changes: the kernel owns its address space; rights are enforced per section; stacks have guard pages; TLB invalidation becomes part of every unmap. What comes next: F3-22 builds the kernel heap on top of frames and mappings, so that new and delete work in the kernel.

Summary


    

  • A virtual address splits into four 9-bit indices and a 12-bit offset; each level's entry address is table base + 8 × index.
    • 

  • Rights combine along the walk; keep restrictions in the leaves; NXE and WP make them apply to the kernel.
    • 

  • The kernel image is mapped per section with the least rights; the direct map is NX; device memory stays out of it.
    • 

  • Guard pages turn stack overflows into faults that the IST stack reports.
    • 

  • The TLB is not coherent with the tables: every unmap or rights reduction needs invlpg (and later a shootdown).
    • 

  • The QEMU monitor's info registers, xp, info mem and gva2gpa let you walk any translation by hand.
    •

Forensic lab answer key


Observation. In each round the driver's buffer frame and the new owner's frame are the same, 0x13f000: the PMM correctly reused the frame the driver had freed. The software walk says the buffer is not mapped. Yet the new owner's word reads bad0001, bad0002, bad0003: the driver's late write landed in it.


Hypotheses. A stale direct-map pointer would be possible, but the driver writes through buf, the unmapped address, as the code shows. The PMM did hand out the frame again, correctly, after the driver freed it; that is not a double allocation. A cached translation fits: the write used the old buf → 0x13f000 translation.


Root cause. The "cleanup" replaced unmap with unmap_no_flush: the entry was cleared but the TLB entry remained. The software walk reads the tables (correct); the CPU uses the TLB (stale). QEMU's TCG keeps its software TLB entry until invlpg or a CR3 write, like a real TLB may.


Fix. Line 104 of paging.cc: arch::invlpg(virt) in unmap. With it, the late write page-faults (error code 0x2, CR2 = the buffer address) and the new owner keeps 600d (second evidence file).


Prevention. Make invalidation part of the only public unmap and protect functions (remove unmap_no_flush from the API); on multiprocessors, batch invalidations with shootdowns in one function; keep the "access after unmap faults" test in the regression suite.
