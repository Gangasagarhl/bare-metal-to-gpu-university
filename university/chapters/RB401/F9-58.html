Story hook

Lina's grandmother asks for a cup of tea from the kitchen. Lina has a plan: go to the kitchen, pick up the cup, bring it to the sofa table, put it down. But plans meet the world. The kitchen door is shut today, so she goes round through the hall. The cup slips the first time she picks it up, so she tries again. And if her phone rings with bad news halfway there, she drops the errand and goes where she is needed, without finishing the walk to the kitchen first.

Lina does not think about how she organises all this. A robot must be told: in which order to do things, what to try when something fails, which conditions to keep checking while it acts, and how to stop an action cleanly when something more important comes up. Robots use two main tools for this: state machines and behaviour trees. This chapter builds the same fetch mission with both, then shows a bug that only behaviour trees with asynchronous actions can have: a robot that grabs at thin air.

What you will be able to do

  • Model a robot mission as a finite-state machine and as a behaviour tree, and compare them on the same runs.
  • Trace the ticks of a behaviour tree: statuses, which children are ticked, and when running actions are halted.
  • Choose between reactive and memory control nodes, and place conditions so that they are re-checked while actions run.
  • Implement asynchronous actions correctly (RUNNING until the result, haltable), and diagnose one that is not (forensic lab).
  • Plan the course project, a fetch-an-object task in simulation that combines navigation, manipulation and behaviour.
Jargon box
Finite-state machine (FSM)
Simple words: a robot is always in one of a few named situations, and rules say when it moves to another. Analogy: a trip has stages (setting off, riding, parking), and you move between them for clear reasons. Precise: a finite set of states, one of which is current, and transitions between states triggered by events or conditions, with actions on entry, during the state or on transitions. D2
Behaviour tree (BT)
Simple words: a tree of small behaviours, checked from the top many times a second, that decides what the robot does now. Analogy: a cyclist's habits checked in priority order every moment. Precise: a rooted tree whose leaves are conditions and actions and whose inner nodes are control nodes (sequence, fallback, parallel) and decorators; the root is ticked periodically and every node returns SUCCESS, FAILURE or RUNNING. D1
Tick
Simple words: one "check and act" pass through the tree. Analogy: one glance at the road. Precise: a call that propagates from the root to the children chosen by each control node, and returns a status upwards; ticks are issued at a fixed rate (here every 0.5 s). D1
Sequence node
Simple words: do these in order; stop at the first one that is not done. Analogy: unlock, mount, ride. Precise: ticks children left to right; returns FAILURE or RUNNING as soon as a child does, and SUCCESS if all succeed. D1
Fallback node (selector)
Simple words: try these in order; stop at the first one that works. Analogy: the short road, or else the long way round. Precise: ticks children left to right; returns SUCCESS or RUNNING as soon as a child does, and FAILURE if all fail. D1
Decorator
Simple words: a node with one child that changes how the child is run. Analogy: "try up to three times". Precise: a node with a single child that modifies its ticks or its status, such as retry, repeat, timeout or inverter. D1
Reactive and memory control nodes
Simple words: a reactive node re-checks everything from the start at every tick; a memory node carries on from where it was. Analogy: checking the traffic light again at every moment, or remembering that you already passed it. Precise: a reactive sequence restarts from its first child on every tick and halts a running child when an earlier one fails; a sequence with memory resumes at the running child and does not re-tick finished children. D1
Halt (preemption)
Simple words: telling a running action to stop because something else is now more important. Analogy: braking and turning back when the phone rings. Precise: a call from a parent to a RUNNING child that is no longer selected; the action must cancel its work (for example, cancel a navigation goal) and return to idle. D1

Layer 1 — the kid explanation

A robot doing a job needs a plan with "what if"s. A state machine is like a board game: the robot is always on one square, and rules say which square to move to next. A behaviour tree is like a list of habits the robot checks again and again, from most important to least: "battery low? go and charge. Otherwise, holding the cup? take it to Grandma. Otherwise, go and get it."

Both work. Trees make it easy to add a new "what if" in one place. Both need care with one thing: when the robot starts something slow, like driving across the house, it must wait until it has really arrived before doing the next thing.

Layer 2 — the student explanation

The mission and its small world

The lab's world (Listing 2, lines 9–33) is deliberately small: named places joined by routes of known length, a robot that moves 0.2 m per tick (0.4 m/s, a tick every 0.5 s), a battery that falls 0.25 % per tick while driving and 0.05 % per tick always, a kitchen door that is closed today, and a cup that slips on the first grasp. The mission: fetch the cup from the kitchen table and place it on the sofa table, unless the battery falls to 20 %, in which case go to the dock. Navigation and manipulation are reduced to their interfaces: "go to a place" takes many ticks and returns when there, "grasp" takes a tick and may fail. That is exactly how a behaviour layer sees F9-56 and F9-57. R1

As a state machine

Listing 3 writes the mission as a switch over nine states. Each moving state sends its goal on entry and waits for arrival; Grasp counts attempts; Place finishes. The battery rule is the interesting part: it must be checked in every state it guards (line 41: "this check must be repeated for every state it guards"). Run 1 (battery 60 %) ends in Done after 5 transitions at tick 79; run 2 (battery 26 %) leaves GoKitchenHall at tick 21 with the battery at 19.9 %, docks, and ends in Failed. R2

The root is ticked every 0.5 s until it returns SUCCESS or FAILURE. R1




Run 2 shows reactivity. At tick 20 the battery reaches 20.0 %; the reactive mission sequence ticks its condition first, gets FAILURE, and halts its running child; the halt travels down to the GoTo, which stops the robot. The root fallback then ticks its second child, GoTo(dock). Notice the last line: the tree returned SUCCESS, but the cup was not delivered. The root reports that one of its children succeeded, here docking. Whoever started the mission needs to know which: the state machine's "Failed" is more honest, and the tree should be fixed to say the same (check yourself, question 6). R1


Comparing them


Both produce the same behaviour on these runs (the state machine takes an extra tick per transition, so its timings differ by a few ticks). The difference shows when the mission grows. Adding "if a person is in the way, wait" to the state machine means a new transition from every moving state; in the tree it is one more condition in one reactive sequence. Conversely, a state machine makes "where is the robot in its mission" explicit in one variable, which is easy to log and to reason about, while a tree's "state" is spread over the running nodes. D1 D2



Layer 3 — the engineer's depth


Statuses, RUNNING and halting


The power of behaviour trees comes from three rules. A node may return RUNNING, meaning "not finished, tick me again". A parent that stops selecting a RUNNING child must halt it. And an action's work happens outside the tick: the tick only starts the work, polls it, and returns quickly. Together these make preemption clean: in run 2 the GoTo was stopped by the halt chain mission → fetch → reach the kitchen → GoTo, without any code in the GoTo knowing about batteries. The cost is that every asynchronous action must implement both halves correctly: RUNNING until the outcome is known, and a halt that really cancels. D1


Reactive or with memory?


The mission sequence is reactive because its condition must be re-checked while fetching. The fetch sequence has memory because its children are steps of a procedure: once the robot holds the cup, it must not re-run "reach the kitchen" on the next tick. Using a reactive sequence there would restart the walk to the kitchen every tick after the grasp; a memory sequence for the mission would never re-check the battery. Each sequence in a tree must be one or the other on purpose. D1 R1


Hierarchical state machines and statecharts


Flat state machines suffer from transition explosion, as the dashed arrows of Figure 2 show. Harel's statecharts add hierarchy (a superstate "Moving" with one "battery low" transition that applies to all its substates), concurrency (orthogonal regions) and history. A hierarchical state machine can express what this tree expresses; the choice is often about tooling and team habits. A common pattern is both: a small state machine for the robot's modes (idle, mission, charging, fault) and a tree inside the mission mode. D2 D4


Data between nodes


Real trees pass data between nodes: the goal pose from a perception node to a GoTo, the grasp pose to the arm. Libraries use a shared key–value store, often called a blackboard, with ports declared per node. The lab's tree avoids this by capturing the world by reference, which is fine for 15 nodes and becomes hard to follow at 150. D1 D3

How the hardware actually does it


On a robot, every action in a behaviour layer is a request to another program: a navigation goal, an arm trajectory, a gripper command, usually as a ROS 2 action with feedback, result and cancel. Three hardware facts follow. A halt must reach the hardware: cancelling a navigation goal must make the base stop, and the behaviour layer should confirm that it did. Actions take real time and can stop answering: every action needs a timeout and a defined result if the server disappears. And the behaviour layer is not a safety system: emergency stops, speed limits and safe states (RB403) work below it and independently of it, so that a bug in a tree cannot defeat them. D3


Safety
Faculty rule: test every mission in the simulator first, including the failure branches (low battery, failed grasp, blocked route). On a real robot, a hardware emergency stop independent of the software, a clear test area, speed limits from the safety case, and supervision for students below L3. A behaviour tree's "stop" is not an emergency stop.

Where the analogy breaks


    

  • Lina re-checks her priorities whenever something changes. A tree re-checks only what its reactive nodes tick, at its tick rate; a condition placed under a memory sequence is checked once.
    • 

  • Lina's habits are flexible. A tree's order is fixed by whoever wrote it; it has no notion of "more important" beyond left-to-right order and structure.
    • 

  • When Lina stops walking, she has stopped. When a tree halts an action, the robot stops only if the action's halt really reaches the motors.
    • 

  • Lina knows whether her errand succeeded. A tree's root status only says that some branch succeeded; deciding what counts as mission success is a design task.
    • 




Common mistakes and debugging


    

  • Asynchronous action returns SUCCESS when the request is sent. Symptom: following steps run while the robot is still moving; "no object within reach". Fix: RUNNING until the result; test that an action cannot succeed before its post-condition holds.
    • 

  • Halt does nothing. Symptom: after a higher-priority branch takes over, the old action keeps going (two goals fight). Fix: implement halt to cancel the request and wait for confirmation.
    • 

  • Condition under a memory node. Symptom: a safety-relevant check (battery, person nearby) is evaluated only once. Fix: put it in a reactive sequence above the actions it guards.
    • 

  • Reactive sequence over procedural steps. Symptom: the robot repeats early steps after finishing them. Fix: memory sequence for procedures.
    • 

  • Root SUCCESS taken as mission success. Symptom: dashboards show success for missions that were abandoned. Fix: make fallback branches that abandon the mission end in FAILURE, or report the outcome explicitly.
    • 

  • Ticks that block. Symptom: the whole tree freezes while one action waits. Cause: a tick that waits for an action to finish. Fix: start, return RUNNING, poll on later ticks.
    •

Summary


    

  • State machines make the current mode explicit; behaviour trees make priorities, alternatives and reactivity modular.
    • 

  • A behaviour tree is ticked repeatedly; nodes return SUCCESS, FAILURE or RUNNING; sequences stop at the first non-success, fallbacks at the first non-failure.
    • 

  • Reactive sequences re-check conditions and halt running actions; memory sequences carry procedures forward.
    • 

  • On the lab mission both designs behave alike; the tree's root SUCCESS after docking shows that mission success must be designed, not assumed.
    • 

  • An asynchronous action that returns SUCCESS when it sends its request breaks every sequence it is in: the forensic robot grasped at air for 2.5 s and reported success.
    • 

  • The behaviour layer is not a safety layer; emergency stops and safe states work below it.
    •
