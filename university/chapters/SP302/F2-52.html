Story hook

Nadia is preparing a banquet: one hundred plates, and each plate needs one spoon of every sauce from a long rack of sauce jars in the pantry. The pantry runner never brings a single jar; he always brings a whole tray of sixteen neighbouring jars and puts it on the shelf next to the stove, because the corridor is long and one trip for one jar would be a waste.

On the first evening Nadia works plate by plate: for plate one she needs jar 1 from tray 1, jar 1 from tray 2, jar 1 from tray 3… The shelf by the stove is small, so trays keep being sent back before she needs them again, and the runner walks the corridor for almost every spoon. On the second evening she works sauce by sauce: tray 1 arrives, she uses all sixteen jars on it for every plate, and only then asks for tray 2. The same plates, the same sauces, the same spoons. The second evening finishes long before the first.

Nothing about the cooking changed; only the order in which Nadia touched the jars. In this chapter you measure exactly that effect on a real machine, count it with a cache simulator, and learn the three ways engineers use caches deliberately: walk memory in the order it is stored, keep the working set small (blocking), and keep threads from fighting over the same tray.

What you will be able to do

  • Measure the latency of a dependent load as a function of working-set size on your own machine and explain the steps in the curve.
  • Predict the number of cache-line misses of a loop from its access pattern, and check the prediction with Cachegrind.
  • Restructure a loop nest (interchange, tiling) so that it uses every byte of each cache line it fetches, and measure the gain.
  • Diagnose false sharing between threads from timings and data layout, and fix it with padding and alignment.
  • Explain which cache facts in this chapter are measured, which are reported by the operating system, and which are not verified.
Jargon box
Cache line (recap)
Simple words: the block of neighbouring bytes a cache always moves as one piece. Analogy: the tray of sixteen jars. Precise: the unit of transfer and allocation of a cache, defined in F1-33; the build machine's kernel reports 64 bytes for the level-1 data cache (LEVEL1_DCACHE_LINESIZE), which is 16 floats. R1 D2
Pointer chasing
Simple words: following a chain where each step tells you where the next step is. Analogy: a treasure hunt in the pantry: each jar has a note with the shelf number of the next jar. Precise: a loop of the form i = next[i], in which every load's address depends on the previous load's value; loads cannot overlap, so the time per step approximates the load latency of the level of the memory hierarchy that holds the working set. D3 R2
Loop interchange
Simple words: swapping which loop is inside and which is outside, so memory is visited in the order it is stored. Analogy: Nadia's switch from plate-by-plate to sauce-by-sauce. Precise: a legal reordering of a loop nest's loops (allowed when it does not change the result) chosen so that the innermost loop has unit stride over the array's storage order. D3
Loop tiling (cache blocking)
Simple words: cutting a big job into small square pieces that fit on the shelf, and finishing each piece before starting the next. Analogy: working on one corner of the banquet table with the few trays that fit on the shelf. Precise: splitting the iteration space of a loop nest into blocks (tiles) whose data fits in a chosen cache level, so that lines brought in for one tile are reused before they are evicted. D3 R4
Cachegrind
Simple words: a tool that runs your program on a pretend computer and counts every cache hit and miss. Analogy: a clerk who writes down every trip of the pantry runner. Precise: a Valgrind tool that executes the program on a synthetic CPU, simulating the instruction cache, first-level data cache and last-level cache (with --cache-sim=yes) and attributing references and misses to functions and source lines; its counts are of its own cache model, not of the real hardware. D4 R3
False sharing (recap)
Simple words: two threads slow each other down because their separate variables sit on the same cache line. Analogy: two recipes printed on one sheet: two cooks keep taking the sheet from each other. Precise: defined in F1-36: coherence traffic caused by writes to different data that share a cache line. D2 R5

Layer 1 — the kid explanation

Analogy

The CPU is the head chef; the shelves near the stove are the caches; the pantry down the corridor is DRAM. Things always come from the pantry a whole tray at a time (a cache line). If you use everything on a tray before asking for the next one, the runner walks rarely. If you take one jar from each tray and move on, the runner walks for almost every jar, and the shelf fills with trays you barely used. And if two cooks keep writing on two recipes that are printed on the same sheet, the sheet travels between them all evening even though they never need each other's recipe.

So caches reward three habits: visit memory in the order it is stored, finish a small piece of work before starting the next, and give each thread its own trays. The rest of the chapter measures each habit.

Layer 2 — the student explanation

Know your machine — measured, not assumed

Every number about the caches of a real processor comes from that processor's documentation (guide AH-21) or from your own measurement. In this build no datasheet could be opened, so the chapter uses two kinds of numbers only. First, what the operating system reports: lscpu and getconf print the cache geometry the kernel knows (Listing 1's output) R1. On a virtual machine those values come from what the hypervisor presents and need not describe the physical chip. Second, what your program measures: the working-set sweep of Listing 3 R2. When the two disagree, the measurement describes what your program experiences.

The working-set sweep

Listing 3 builds a single random cycle through an array of indices (Sattolo's algorithm visits every slot exactly once before returning to the start), then follows it: i = next[i]. Because each address depends on the previous load, the processor cannot overlap the loads, and because the order is random, the hardware prefetcher cannot guess the next address D3. The time per step is therefore close to the latency of whichever level holds the array. Doubling the array from 4 KiB to 1 GiB traces the curve: flat while the set fits the level-1 cache, then a series of rises. In the recorded run the time per load stayed near its minimum up to 32 KiB, rose gradually up to 1 MiB, rose steeply from 2 MiB, and reached more than a hundred times the minimum beyond 16 MiB R2. The first two transitions sit near the reported L1 and L2 sizes. The last one does not match the reported L3 size: see the unverified box in "How the hardware actually does it".

Use every byte of every line

A 4096 × 4096 matrix of floats stored row by row occupies 64 MiB. Listing 2 sums it twice: row by row (inner loop over columns, consecutive addresses) and column by column (inner loop over rows, addresses 16 KiB apart). Each 64-byte line holds 16 floats R1. Row order uses all 16 floats of a line on consecutive steps; column order uses one float from a line and moves to a line 16 KiB away; by the time the walk returns for the neighbouring float, 4,096 other lines have been touched (256 KiB of lines, more than the reported L1d), so the line has probably been evicted. In the recorded run the column order took about nine times as long as the row order R3. Fixing it requires only loop interchange: put the loop over the contiguous index inside.

Count misses instead of guessing

Time tells you that something is slow; a miss count tells you why. The hardware counters that would count real misses are not available in the build container (F2-55 shows the evidence), so this course uses Cachegrind, which simulates a cache hierarchy while the program runs and attributes misses to functions D4. For a 1024 × 1024 matrix (1,048,576 floats) the worked example predicts 65,536 level-1 misses for row order and about 1,048,576 for column order; Cachegrind reported 65,538 and 1,048,577 R3. A simulator is still a model: it counts misses of its cache, configured from what the machine reported, not of the real one.

Keep the working set small: tiling

Some loops cannot be interchanged into perfect order. A matrix transpose reads in along rows and writes out down columns (or the reverse): one side always strides. Tiling solves it: process the matrix in b × b tiles. Inside a tile, the b lines of in and the b lines of out being touched fit in cache together, so each line fetched is fully used before it leaves D3. Listing 4 measures naive and tiled transposes for several tile sizes and checks every result against the naive one; in the recorded run every tiled version was correct and roughly three times faster than the naive version R4. The same idea, applied to matrix multiply, is step 3 of the SGEMM lab in F2-56, and on the GPU it becomes the tiling of CU302.

Give each thread its own lines

Coherence (F1-36) works on whole lines. When two cores write to different variables in the same line, each write must first take the line away from the other core D2. The forensic lab's program has four threads, each incrementing its own counter. Layout A packs the four counters next to each other (8 bytes apart, so in one or two 64-byte lines); layout B gives each counter its own 64-byte block with alignas(64). No thread ever reads another thread's counter, so there is no data race and the results are identical; only the layout differs R5.

Layer 3 — the engineer's depth

Latency, bandwidth and the prefetcher

The pointer chase measures latency because it allows only one outstanding miss. A sequential sum (Listing 2, row order) has independent addresses that the hardware can predict, so the prefetcher can fetch lines ahead and several misses can be in flight at once (memory-level parallelism, F1-32) D2. That is why the row-order sum of a 64 MiB matrix, which certainly does not fit the reported L1 or L2, costs about one nanosecond per element in the recorded run, while one random dependent load in a large working set costs hundreds R2 R3. In fact the row-order sum is not limited by memory at all: its float additions form one dependent chain (each addition needs the previous sum), which F2-53 breaks with SIMD. Keep both effects apart when you read a timing.

Pages and the TLB

A strided or random walk also changes page often. With 4 KiB pages, the column walk of a 4096-wide float matrix touches a new page on every step (each step is 16 KiB), and the random chase over hundreds of MiB touches pages at random; both need address translations that miss in the TLB (F1-38) D2. Part of the large-set latency in Listing 3 is therefore page-walk cost, not cache misses. Without hardware counters, this build cannot separate the two; huge pages (F1-38) are the experiment that would.

Choosing a tile size

The tile must be large enough that each line fetched is fully used (at least 16 floats wide for 64-byte lines) and small enough that all lines of one tile of in and out stay in the target cache together. For b = 32 that is 32 lines of each array, 2 × 32 × 64 B = 4 KiB, well inside the reported L1d; for b = 128 it is 16 KiB of data spread over 256 lines. In the recorded run all tile sizes from 8 to 128 helped; b = 16 was the slowest of them R4. Small differences between tile sizes are within the machine's spread (F2-51); do not over-interpret them. Set associativity (F1-33) adds a trap: a power-of-two row length (here 16 KiB) maps the lines of a column into few sets, so conflict misses can appear before capacity runs out.

Padding against false sharing, and its cost

Padding each hot per-thread variable to its own line removes the coherence traffic but multiplies the memory used by the variables (64 bytes for an 8-byte counter). C++17 added std::hardware_destructive_interference_size as a portable hint for this distance D5; this chapter's listing writes 64 because the kernel of the build machine reported a 64-byte line R1, and says so in a comment. The better fix, when possible, is not to share at all: let each thread accumulate in a local variable and combine at the end.

How the hardware actually does it

Caches are filled and evicted by hardware, line by line, without any instruction from the program (the registered analogy's "the chef does not choose") D2. A load that misses in L1 asks the next level, which may ask the next, until DRAM; the line is installed on the way back. Hardware prefetchers watch the stream of miss addresses and fetch lines ahead when they detect a pattern such as a constant stride D2 D3. Multicore coherence protocols such as MESI (F1-36) keep one writable copy of a line at a time, which is why writes to a shared line serialise between cores.

Not verified — check before relying on this

(1) The cache sizes in Figure 1 are what the virtual machine's kernel reported (lscpu: L1d 48 KiB per instance, L2 2 MiB per instance, L3 260 MiB, one instance); they were not checked against the processor's datasheet, and the CPU model string ("Intel(R) Xeon(R) Processor @ 2.10GHz") does not name a specific product. (2) In Listing 3 the latency rose steeply at 2–16 MiB, far below the reported 260 MiB L3. Possible explanations (the L3 is shared with other tenants, the virtual machine sees only part of it, TLB misses dominate, the reported value does not describe the cache this code uses) were not distinguished; doing so needs hardware counters or a huge-page experiment. (3) The prefetcher behaviour is described from textbooks (D2, D3), not from this processor's optimisation manual, which is the document to check (for Intel processors, the vendor's optimization reference manual, memory subsystem chapters).

Worked example

Predict the level-1 data-cache misses of sumRows and sumColumns for n = 1024, assuming 64-byte lines, a level-1 cache far smaller than the 4 MiB matrix, and that the matrix starts at the beginning of a line.

  1. Elements: 1024 × 1024 = 1,048,576 floats of 4 bytes = 4 MiB.
  2. Floats per line: 64 / 4 = 16.
  3. Row order: each line is loaded once and its 16 floats are used on 16 consecutive steps. Misses = 1,048,576 / 16 = 65,536.
  4. Column order: consecutive steps are 1024 × 4 = 4,096 bytes apart, so each step touches a new line. Before the walk comes back to the same line (one column later), it has touched 1,024 other lines (64 KiB). If those do not all stay in L1 (they did not in Cachegrind's model of a 48 KiB cache; associativity also maps lines 4 KiB apart into few sets), every load misses: about 1,048,576.
  5. Check against the tool: Cachegrind reported D1 read misses of 65,538 for sumRows and 1,048,577 for sumColumns R3. The two extra misses in each function are the vector's header and stack data, not the matrix.
  6. Instructions: the same tool counted about 2.6 million instructions for sumRows and about 6.3 million for sumColumns: the column version also does more index arithmetic per element. Both effects add up in the timing.

Where the analogy breaks


    

  • Nadia decides which trays to keep on the shelf. Caches decide by themselves, by a replacement policy, line by line; a program can only influence what stays by the order and amount of data it touches.
    • 

  • The runner in the story brings one tray per trip and waits. Real memory systems keep many misses in flight and prefetch ahead on patterns, so a sequential walk is far faster than "one trip per tray" suggests (Layer 3).
    • 

  • Shelves in a kitchen hold anything anywhere. A set-associative cache allows each line only in a few slots chosen by its address, so lines at power-of-two distances can push each other out while most of the cache is empty.
    • 

  • Two cooks sharing a recipe sheet could photocopy it. Cores can share a line freely while they only read it; the cost appears when at least one of them writes.
    •

Summary


    

  • Use only reported (kernel) or measured cache facts; on a virtual machine they may disagree, and the measurement describes what your code experiences.
    • 

  • A dependent random walk measures latency; a sequential walk is helped by the prefetcher and many misses in flight.
    • 

  • Caches move whole lines (64 bytes reported here): use every byte of a line before moving on. Loop interchange fixes most stride problems.
    • 

  • Predict miss counts with arithmetic and confirm them with Cachegrind, remembering that it simulates a model.
    • 

  • Tiling keeps the working set of a loop nest inside a cache when no loop order is perfect.
    • 

  • Threads writing to different variables in one line slow each other down (false sharing); pad, align or, better, accumulate locally.
    •

  7. False sharing: the four doubles occupy 32 consecutive bytes, one or two lines, and every thread writes its element in its inner loop. Fixes: accumulate in a local variable and write results[t] once at the end; or pad each element to its own line (alignas(64) struct).

Forensic lab answer key


Observation. In layout A the counters are 8 bytes apart (+0, +8, +16, +24): all four fit in 32 bytes, so they share one 64-byte line, or two if the array straddles a line boundary. In layout B they are 64 bytes apart: each has its own line. Layout A took several times as long as layout B in the recorded run (the printed ratio A / B).


Hypotheses. (1) The layouts make the threads share lines (false sharing). (2) The two runs did different amounts of work, or the machine was busier during run A. Against (2): the same runThreads function with the same iteration count is used for both; each result is a median of 11 runs; the difference is far larger than the spread measured in F2-51.


Root cause. Each increment is a write to the counter's line. Under a MESI-style protocol a core must hold the line exclusively to write it, so the four cores take the line from each other on almost every increment; the line moves between cores instead of staying in each core's L1. In layout B each core keeps its own line.


Fix and verification. Best: each thread increments a local variable and adds it to the shared total once at the end (no shared line in the loop). Alternatively pad to the line size as in layout B. Verify with the same program: the time for the fix should be close to layout B's, and the totals unchanged.


Data race? No: each counter is written by exactly one thread and read only after join, which synchronises; different objects in one line are different memory locations in the C++ memory model. False sharing is a performance problem, not a correctness one. How the evidence was produced: sharing.cc built with -O2 -pthread by run.sh; output unedited.
