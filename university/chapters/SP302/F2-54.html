Story hook

At Lucía's café, the kitchen is a row of stations: one cook cracks eggs, the next whisks, the next fries, the last plates. To keep every station busy, the first cook does not wait for the waiter to confirm each order: when a regular walks in, she starts the regular's usual dish at once. Most mornings that guess is right, and the dish is half-made when the order arrives.

On Monday the regulars come in the same order as always, and the guesses are almost never wrong. On Tuesday a tour group arrives, ordering at random from the menu. Half of the guesses are wrong; each wrong dish must be thrown out of every station it already reached, and the right dish started from the beginning. The kitchen is the same, the dishes are the same, the number of plates is the same, and Tuesday takes many times longer.

Processors guess branches in exactly this way. This chapter measures what a wrong guess costs on a real machine, shows how the same loop can be fast or slow depending only on the order of its data, and teaches three tools: arranging data so guesses are right, writing code without data-dependent jumps, and checking what the compiler did with your if.

What you will be able to do

  • Explain why a pipelined, speculative core predicts branches and what a misprediction costs.
  • Measure the effect of predictable and unpredictable data on the same loop, and estimate the cost of one misprediction on your machine.
  • Count branches and mispredictions per function with Cachegrind's branch simulation and relate them to the data.
  • Rewrite a data-dependent branch as branch-free code, and recognise when the compiler has already done it (conditional move).
  • Simulate 1-bit and 2-bit predictors on outcome patterns and predict their misses by hand.
Jargon box
Branch prediction (recap)
Simple words: the processor guesses which way an if will go, and starts working on that path before it knows. Analogy: starting the regular's usual dish before the order arrives. Precise: defined in F1-28: hardware that predicts the direction (and target) of a branch at fetch time, so the pipeline can keep fetching; the work on the predicted path is speculative. D1
Misprediction penalty (recap)
Simple words: the time lost when the guess was wrong. Analogy: throwing out the half-made dish from every station and starting the right one. Precise: the cycles between fetching down the wrong path and resuming on the correct one, during which the speculative work is discarded (F1-28); its size is processor-specific. D1
Data-dependent branch
Simple words: an if whose direction depends on the values being processed, not on the loop counter. Analogy: the guest's order. Precise: a conditional branch whose outcome is a function of loaded data; it is predictable only if the data has a pattern the predictor can learn. D1 R2
Branchless code
Simple words: code that computes both possibilities, or a mask, and picks the result with arithmetic instead of jumping. Analogy: preparing the plate so that it fits every order, with one ingredient switched on or off. Precise: code in which no conditional jump depends on the data; the selection is done with a conditional move / select instruction, masks (-(b >= 128) & b), or SIMD compare-and-blend. It trades possible mispredictions for always doing the work of both paths. D1 R3
If-conversion
Simple words: the compiler turning your if into branchless code by itself. Analogy: the translator rewriting "if the guest wants cheese, add cheese" as "add the cheese amount the guest asked for (possibly none)". Precise: a compiler transformation that replaces a conditional branch around simple code with predicated or conditional-move instructions; GCC's -fif-conversion and -fif-conversion2 passes do this and are switched off by the -fno- forms used in this chapter's "jump" build. D3 R3
Branch simulation (Cachegrind)
Simple words: a tool that pretends to be a branch predictor and counts its wrong guesses. Analogy: a clerk who notes every guess the first cook makes and whether it was right. Precise: with --branch-sim=yes, Cachegrind counts executed conditional branches (Bc) and their mispredictions (Bcm), and indirect branches (Bi, Bim), using its own simple predictor model, per function. D4 R4

Layer 1 — the kid explanation

Analogy

The kitchen is a row of stations, so the first cook must start the next dish before the current order is confirmed: she guesses. Regulars in their usual order make guessing easy; a tour group ordering at random makes every second guess wrong, and each wrong guess throws away the work of several stations. Mapping: stations = pipeline stages; guessing the usual dish = branch prediction; a guest's order = data that decides an if; throwing out the half-made dish = the pipeline flush.

So the same program can be fast or slow depending only on how predictable its decisions are. Two cures exist: make the decisions predictable (for example, sort the data first), or remove the decision (cook every plate the same way and leave out the ingredient by measure, not by choice).

Layer 2 — the student explanation

Why processors guess

A pipelined core fetches new instructions every cycle, long before earlier ones finish (F1-26). A conditional branch's direction is known only when it executes, several stages after it was fetched. Waiting would leave the front of the pipeline idle at every branch, and branches are frequent (every loop iteration has one). So the core predicts the direction, fetches and executes down the predicted path speculatively, and, if the prediction was wrong, discards that work and restarts at the correct address (F1-28, Figure 1) D1. A correct prediction costs (almost) nothing; a misprediction costs the penalty.

The same loop, two inputs

Listing 1 sums the bytes of an array that are at least 128. The bytes are random, so half pass the test. It runs the sum on two arrays with exactly the same bytes: sorted (all small bytes first, then all large ones) and shuffled (random order). The results printed are identical for both. In the "jump" build, where the if is a real conditional jump, the recorded run shows the shuffled array costing several times as much per element as the sorted one R2. With sorted data the branch goes the same way millions of times in a row and is predicted almost perfectly; with shuffled data its direction is a coin toss, and no predictor can do better than guessing D1.

Count, don't guess

Cachegrind's branch simulation counts the branches of each function and how many its model predictor gets wrong D4. Run on one MiB of each input (forensic evidence below), it reports for sumBranchy 2,097,153 conditional branches in both cases (two per element: the loop's own branch and the if), with 18 mispredictions on sorted data and 523,813 on shuffled data, about half of the 1,048,576 if branches R4. sumBranchless executes one conditional branch per element (the loop's) and almost no mispredictions on either input. The instruction counts are identical across inputs: the extra time is not extra work, it is discarded work.

Removing the branch

sumBranchless builds a mask that is all ones when the byte is at least 128 and zero otherwise (-static_cast<long>(b >= 128)) and adds mask & b. No jump depends on the data, so there is nothing to mispredict, and its time is the same for both inputs R2. The price is that every element now costs the "add" path, whether or not it was needed. For a cheap operation that is a good trade; for an expensive one (a function call, a division) it may not be.

The compiler may already have done it

The surprise of this lab is the "cmov" build: plain -O2. There, sumBranchy costs the same on sorted and shuffled data R2, because GCC replaced the if by a cmovs instruction (a conditional move, F1-31): the disassembly of the cmov build has no data-dependent jump at all R3. Only when if-conversion is switched off (-fno-if-conversion -fno-if-conversion2) does the source-level if become a jns jump, and the sorted/shuffled difference appears. Two lessons: the C++ if is not the machine's branch, so read the instructions before blaming the predictor; and the compiler's choice depends on its version, flags and cost model, so a small source change can bring the branch back.

Layer 3 — the engineer's depth

Estimating the penalty from two measurements

If two runs differ only in misprediction count, the time difference divided by the extra mispredictions estimates the cost of one misprediction in time on that machine. The worked example does this with the recorded numbers. Two cautions: the estimate includes everything a misprediction disturbs (for example, memory loads issued on the wrong path), and it is a time, not a cycle count, because the clock frequency during the run is unknown in this build (F2-51's unverified box) R2.

When branchless code is slower

A conditional move turns a control dependency (which the predictor can speculate past) into a data dependency (which must wait for its inputs). In the cmov build, sumBranchy runs at the same speed for both inputs, but on sorted data it is slower than the jump build's well-predicted branch, because every iteration's cmovs waits for the comparison and the addition of the previous sum R2 R3. The jump build, when predictions are right, lets the core run ahead speculatively. Branchless is the right choice for unpredictable conditions on cheap operations; a well-predicted branch can beat it. Measure both with your real data distribution.

What predictors can learn

Listing 3 runs two textbook predictors on recorded outcome patterns. A loop branch with a short, regular pattern (taken three times, then not taken) defeats the 1-bit predictor twice per period and the 2-bit counter once per period; the strictly alternating pattern defeats a 1-bit predictor every time and a 2-bit counter that starts in a weak state half the time; a random pattern defeats both, and on the recorded random pattern the 2-bit counter was even slightly worse than the 1-bit one R5. Real predictors also use the history of recent branches to choose among many counters, which lets them learn patterns like "alternate" and "taken three times, then not" D1; but no predictor learns a truly random condition. That is the property to design around.

Design patterns

  • Sort or partition first when the data will be processed several times: the one-time cost of sorting can pay for itself.
  • Separate the cases: split a mixed array into two arrays by condition once, then run a branch-free loop over each.
  • Use select-friendly code: std::min, std::max, the conditional operator on simple values, and masks; check that the compiler produced cmov or SIMD blends.
  • Move rare cases out of hot loops: error handling and unusual paths in separate, cold functions; GCC and Clang accept __builtin_expect and C++20 offers [[likely]] and [[unlikely]] to hint code layout D3 D5; these change layout, not the hardware predictor, and their effect must be measured.
  • Vectorise: SIMD code handles conditions with compare and blend per lane (F2-53, the clampAll loop): there is no per-element branch at all.

How the hardware actually does it

At fetch time the core looks up the branch's address in its prediction structures: a branch target buffer gives the target, and direction predictors built from counters like Figure 2's, indexed with the branch address and recent branch history, give the direction (F1-28) D1. Instructions on the predicted path are executed out of order and speculatively (F1-29); their results are held back until the branch resolves. On a misprediction, the speculative results are discarded, the front end is redirected, and the counters are updated D1.

Not verified — check before relying on this

The organisation of the build machine's branch predictor (table sizes, history length, predictor type), its pipeline depth and its misprediction penalty in cycles are not known from any document in this build, and its CPU model string does not identify a product. The per-misprediction time in the worked example is a measurement on a shared virtual machine, not a property of a processor. Cachegrind's branch simulator uses its own simple model (described in the Valgrind user manual's Cachegrind chapter, D4, not opened in this build); its misprediction counts show the pattern in the data but are not the hardware's counts. The documents to check for a real processor are the vendor's optimization reference manual (branch prediction sections) and, for counts, the hardware counters through perf (F2-55), which did not work in this build.

States before each outcome: 2 3 3 3 2 3 3 3; misses: 2. A 1-bit predictor (start "taken") misses whenever the outcome differs from the previous one: at positions 4 (N after T), 5 (T after N) and 8 (N after T), so 3 misses. Listing 3 prints exactly "23332333", 3 and 2 for this pattern R5.

Part B — estimate the time of one misprediction from the jump build's recorded output (branches_jump.out, 224 elements) R2:

  1. Recorded medians for sumBranchy: 0.560 ns per element (sorted) and 4.335 ns per element (shuffled).
  2. Difference: 4.335 − 0.560 = 3.775 ns per element.
  3. Extra mispredictions per element: on sorted data almost none; on shuffled data about one in two if branches (Cachegrind's model: 523,813 of 1,048,576, R4). So about 0.5 extra mispredictions per element.
  4. Time per misprediction ≈ 3.775 / 0.5 ≈ 7.6 ns on this machine in this run. Expressed in cycles it would need the clock frequency during the run, which this build could not observe; at an assumed frequency f (in GHz) it is 7.6 × f cycles.

Where the analogy breaks


    

  • The cook guesses from the guest's face; the processor guesses from the branch's address and the history of recent branch outcomes, with no idea what the data means.
    • 

  • In the kitchen, a wrong dish is visible and wasteful. In the processor, the discarded work is invisible to the program's results; only time is lost (security researchers have shown that speculative work can leave traces in caches, a topic for F11).
    • 

  • The café could ask guests to order in advance. A program cannot tell the hardware predictor the outcome; hints such as [[likely]] only change how the compiler lays out code.
    • 

  • The story suggests that guessing is always worth it. Branch-free code avoids guessing altogether, and is sometimes faster and sometimes slower (Layer 3).

Summary


    

  • Pipelined cores predict branch directions and execute speculatively; a misprediction throws away work and costs time.
    • 

  • A data-dependent branch is cheap when the data has a pattern and expensive when it is random: the same loop can differ several times in speed with the same values in a different order.
    • 

  • Count before you fix: Cachegrind's branch simulation gives branches and mispredictions per function (from its own model).
    • 

  • Branch-free code (masks, cmov, SIMD blends) removes mispredictions but always pays for the work and can add data dependencies.
    • 

  • The compiler may already have converted your if into a cmov; the disassembly decides, not the source.
    • 

  • Penalties and predictor designs are processor-specific: measure on your machine and check the vendor's manual.
    •

Forensic lab answer key


Observation. Same in both runs: total instructions (about 229.9 million), total branches (about 37.6 million), and per function the instruction counts (Ir: 6,815,581 and 7,340,042) and conditional branches (Bc: 2,097,153 and 1,048,577), and the result (100401614). Different: mispredictions of sumBranchy (Bcm): 18 on sorted versus 523,813 on shuffled data, about half of its 1,048,576 if branches. sumBranchless stays at 10 in both.


Theories. "Bigger files": ruled out, the instruction and branch counts are identical for the same size, and the size did not change. "Slower disk": the kernel reads no file and its time difference appears with identical in-memory data; a disk problem would not change mispredictions.


Root cause. The jns in sumBranchy (Listing 2, jump build) depends on each byte. Sorted input gives long runs of the same direction (predictable); arrival-order input gives a random direction, so about half the predictions fail, each costing a pipeline flush.


Fixes. Code: make the kernel branch-free (mask or cmov; the cmov build already shows equal times on both inputs, R2), verified by equal times on both inputs and equal results.
