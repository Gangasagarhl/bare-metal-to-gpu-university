Story hook

Ji-woo serves soup at a school canteen. At first she fills cups with an ordinary ladle: dip, pour, next cup. One day the kitchen buys a long ladle with eight spouts. Lined up under it, eight cups are filled with one pour. When the cups are already waiting in a row on the counter, the line moves almost eight times faster.

But the wide ladle has rules. The eight cups must stand in a row under the spouts. Every spout pours the same soup: it cannot give cup three a different dish. And it does not help when the soup pot is empty and Ji-woo is waiting for the next pot from the kitchen. Some jobs do not fit it at all: when a cup can only be filled after looking at what went into the previous cup, the eight spouts have nothing to do at the same time.

Modern processors have exactly such ladles: instructions that do the same operation on 4, 8 or 16 numbers at once. This chapter shows when the compiler uses them for you, how to see whether it did, how to use them explicitly, and the three things that stop them: dependencies, the order of floating-point additions, and memory that cannot deliver data fast enough.

What you will be able to do

  • Explain SIMD execution: vector registers, lanes, and one instruction operating on all lanes, and relate it to the GPU's SIMT model.
  • Read the compiler's vectorisation report and its generated instructions, and tell real vector arithmetic from scalar code that only looks vectorised.
  • Write an explicitly vectorised loop with AVX2 and FMA intrinsics, with a run-time CPU check and a scalar remainder loop.
  • Decide whether reordering a floating-point reduction is acceptable, and break a dependency chain with several accumulators.
  • Measure SIMD speed-ups in cache and in DRAM, and explain why they differ.
Jargon box
SIMD (single instruction, multiple data)
Simple words: one instruction that does the same thing to several numbers at once. Analogy: the eight-spout ladle. Precise: a form of data-level parallelism in which one instruction operates on all elements (lanes) of a vector register; on x86-64, the SSE, AVX/AVX2 and AVX-512 instruction families operate on 128-, 256- and 512-bit registers (4, 8 and 16 single-precision floats). D1 D5
Vector register and lane
Simple words: a wide register that holds several numbers side by side; each slot is a lane. Analogy: the row of cups under the spouts; each cup is a lane. Precise: an architectural register of 128 (xmm), 256 (ymm) or 512 (zmm) bits on x86-64; a lane is one element position. (HW301 uses "lane" for one thread of a GPU warp, F1-57; the idea is related, the mechanism differs.) D1
Auto-vectorisation
Simple words: the compiler rewriting your ordinary loop to use SIMD instructions. Analogy: the translator noticing that the recipe says "fill each cup" and writing "use the wide ladle". Precise: a compiler transformation (vectorisation, F1-31) that turns loop iterations into vector operations when it can prove this preserves the program's meaning; in GCC it is enabled at -O3 and, in a cheaper form, at -O2, and reported with -fopt-info-vec. D3 R2
Intrinsic
Simple words: a function that the compiler turns into one particular machine instruction. Analogy: writing "wide ladle" in the recipe yourself instead of hoping the translator does it. Precise: a compiler-provided function, declared in a header such as <immintrin.h>, that maps to a specific instruction; in GCC 13, _mm256_fmadd_ps is defined in fmaintrin.h as a call to the built-in __builtin_ia32_vfmaddps256. H1 D2
FMA (fused multiply-add)
Simple words: one instruction that computes a × b + c. Analogy: stirring while pouring, in one movement. Precise: an operation computing a × b + c with a single rounding at the end (IEEE 754 fusedMultiplyAdd); x86-64 provides it in the FMA extension (vfmadd…ps instructions). It counts as two floating-point operations in FLOP rates. D1 D4
Reduction
Simple words: combining many numbers into one, such as a sum or a maximum. Analogy: pouring all the cups back into one pot. Precise: a loop that accumulates values with an associative operation into a single result; vectorising it means keeping several partial results (one per lane) and combining them at the end, which changes the order of operations. D5
Floating-point reassociation
Simple words: adding the same float numbers in a different order, which can give a slightly different answer. Analogy: tipping sand and pebbles into a scale in a different order changes which grains the scale can still show. Precise: floating-point addition is commutative but not associative, because every addition rounds; (a + b) + c and a + (b + c) can differ. A compiler may reorder floating-point operations only when allowed (for example by -ffast-math or -fassociative-math in GCC). D4 D3 R4

Layer 1 — the kid explanation

Analogy

A SIMD instruction is a wide ladle with eight spouts. It fills eight cups in one pour, but only if the cups stand in a row (data next to each other in memory), only with the same soup for every cup (the same operation in every lane), and only if the pot is full (the data has arrived from memory). Mapping: ladle pour = one SIMD instruction; cups in a row = consecutive array elements in a vector register; same soup = same operation in every lane; empty pot = waiting for memory.

The translator (the compiler) often switches to the wide ladle by itself. Your job is to check that it did, to write loops it can switch, and to know when the ladle cannot help.

Layer 2 — the student explanation

What the machine offers

x86-64 processors have vector registers and instructions that treat a register as several lanes D1. Every x86-64 processor supports the 128-bit SSE2 instructions, so a compiler targeting plain "x86-64" can always use 4-float vectors. Wider vectors (AVX2: 256 bits, 8 floats; AVX-512: 512 bits, 16 floats) and FMA exist only on some processors, so the compiler uses them only if you tell it that the target has them (-march=…) or if the code asks for them per function and checks at run time D3. On the build machine, GCC reported that -march=native meant sapphirerapids with AVX2, FMA and AVX-512F enabled and a preferred vector width of 256 bits R1. That is GCC's reading of the virtual machine's CPU flags; it does not tell you which physical processor ran the code.

Let the compiler do it, then check

GCC tells you what its vectoriser did when you add -fopt-info-vec-optimized (loops it vectorised) or -fopt-info-vec-missed (loops it did not, with a reason) D3. Listing 1 holds five small loops; its reports for the baseline target and for -march=native are below it R2. Read them line by line, with the loop's line number:

  • Line 6, saxpy: vectorised, and "loop versioned for vectorization because of possible aliasing". The compiler cannot prove y and x do not overlap, so it emits a run-time check and two versions of the loop: a vector one for non-overlapping arrays and a fallback.
  • Line 14, sumInt: vectorised. Integer addition is associative, so partial sums in lanes give the identical result.
  • Line 23, sumFloat: reported as vectorised. Hold that thought: Layer 3 shows what that means.
  • Line 31, prefix: not vectorised. Each element needs the previous element's new value: a true dependency between iterations.
  • Line 38, clampAll: not vectorised for the baseline target ("control flow in loop"), but vectorised with -march=native. The if can be turned into a lane-wise select or a masked store when the target has the instructions for it.

The instructions are the proof

A report is a claim; the disassembly is the evidence. Two things identify real SIMD arithmetic: the register name (xmm 128-bit, ymm 256-bit, zmm 512-bit) and the instruction suffix (ps = packed single precision, all lanes; ss = scalar single, lane 0 only) D1. The saxpy disassembly shows both versions the report announced: a scalar loop with vfmadd213ss on xmm registers and a vector loop with vmovups, vfmadd213ps and vmovups on ymm registers R3. The compiler fused the multiply and the add into one FMA instruction in this build.

Or say it yourself: intrinsics

Listing 2's saxpyAvx2 writes the vector loop by hand. _mm256_set1_ps(a) puts a in all eight lanes; _mm256_loadu_ps loads eight consecutive floats (the u means the address need not be 32-byte aligned); _mm256_fmadd_ps(va, vx, vy) computes va × vx + vy per lane; _mm256_storeu_ps stores eight floats H1 D2. Two engineering details matter more than the intrinsics. First, the function carries [[gnu::target("avx2,fma")]], so only this function is compiled for AVX2, and main calls it only after __builtin_cpu_supports("avx2") and ("fma") return true: the program still runs on a processor without AVX2 D3. Second, a remainder loop handles the last n % 8 elements; without it the code reads and writes past the end of the arrays.

When SIMD pays, and when it does not

Listing 2 is built three ways: -O2 -fno-tree-vectorize (no auto-vectorisation), -O3 (baseline target, 16-byte vectors) and -O3 -march=native. For arrays of 4,096 floats, which stay in the level-1 cache between repetitions, the recorded runs show the vectorised saxpy several times faster than the scalar one, and the explicit AVX2 version among the fastest R5. For arrays of 16 M floats (64 MiB each), every version runs at a similar, much lower rate, because each element costs 12 bytes of memory traffic and memory cannot deliver them as fast as the vector unit can use them R5. SIMD multiplies the arithmetic rate; it does not make DRAM faster. F2-56 turns this observation into the roofline model.

Layer 3 — the engineer's depth

The reduction that was "vectorised" but not faster

The report says sumFloat was vectorised with 32-byte vectors. The instructions say what that means (forensic evidence below): the main loop loads eight consecutive floats per iteration but adds them with eight scalar vaddss instructions into one accumulator, in the original order R3. The compiler has kept the exact sequence of roundings of the source, as the C++ and IEEE 754 rules require without permission to reassociate D4; it has only unrolled the loop. The time per element is set by the latency of one floating-point addition, exactly as in F1-55's single dependent chain. Built with -ffast-math, the same function uses vaddps on a ymm accumulator: eight partial sums, combined at the end R3.

The timings confirm it: sumPlain costs about the same per element in all three builds, while sum8, which writes eight partial sums explicitly in ordinary C++, becomes several times faster as soon as the compiler may vectorise R5. Writing the accumulators yourself is the honest way to vectorise a reduction: you choose a new, deterministic order in the source, and every build computes the same result. -ffast-math instead allows many other transformations (it also assumes no NaNs or infinities occur, for example), which can change results elsewhere in the file; use it only with tests that would catch that D3.

How different are the results?

Listing 4 sums the same million floats 1/1, 1/2, …, 1/1,000,000 in two orders. The in-order float sum and the eight-lane float sum differ already in the second decimal place, and the eight-lane sum is closer to the double-precision reference R4. Neither order is "the right one": both are approximations with different rounding histories. What matters for engineering is that (1) the result is reproducible for a given build, (2) tests compare against a reference with a tolerance justified by the precision (MA302; the SGEMM check in F2-56 does this), and (3) changing the order is a decision, not an accident.

Aliasing, alignment and the remainder

The saxpy loop was versioned because float* y and float const* x may point into the same array; if they overlap with a small offset, eight-lane loads and stores would read values the scalar loop would already have changed. When you know they never overlap, you can say so to the compiler (GCC and Clang accept the non-standard __restrict__ qualifier), which removes the check D3. Unaligned loads (loadu) are used throughout this chapter; whether aligned data is faster on a given processor is a question for that processor's optimisation manual and for your measurement, not for this chapter. Every vector loop needs a plan for the last n % width elements: a scalar remainder (as here), masked operations (AVX-512 has mask registers), or padding the arrays.

Wider is not automatically faster

GCC's -march=native on the build machine preferred 256-bit vectors even though AVX-512 was enabled R1. In build 3 of Listing 2 the plain loop compiled with -march=native and the hand-written AVX2 loop gave different in-cache rates, and the hand-written loop was not the faster one in that run R5; repeat it on your machine before concluding anything (F2-51: the spread of a shared virtual machine is large). Reasons why wider vectors may not help include memory bandwidth (above) and processor-specific effects of 512-bit instructions documented in vendor optimisation manuals; this build did not investigate them (see the unverified box).

SIMD on the CPU, SIMT on the GPU

On a CPU, you (or the compiler) write vector instructions explicitly: one thread, wide registers. On an NVIDIA or AMD GPU, you write scalar code for one thread, and the hardware executes groups of threads (warps of 32 or wavefronts of 64) in lock-step, lane by lane (F1-57, BR-03). The same constraints reappear in another form: neighbouring lanes should access neighbouring data (coalescing), and lanes that take different branches cost time (divergence).

How the hardware actually does it

A SIMD instruction is decoded once and executed by a functional unit that is as wide as the vector, or by several units over consecutive cycles; the register file holds the architectural vector registers D5. The cost of the instruction in decode, issue and scheduling (F1-29) is paid once for all lanes, which is where the speed-up comes from. Loads and stores of a vector move 16, 32 or 64 contiguous bytes, which is why contiguous data (one or two cache lines per load, F2-52) suits SIMD and scattered data does not.

Not verified — check before relying on this

The number of vector execution units per core, their width, the latency and throughput of vaddps, vfmadd…ps and their 512-bit forms, and any clock-frequency change caused by wide vector instructions are processor-specific facts. None was taken from a document in this build: the CPU model string of the build machine does not name a product. Check the processor vendor's optimization reference manual and the instruction tables it points to for your exact processor, and measure peak FMA throughput yourself (Listing peak.cc of F2-56). The instruction-family facts in Figure 1 (register widths, the ps/ss suffixes) are from the Intel SDM (D1), title only and pending verification, and are consistent with the real disassembly in R3.

Worked example

How many instructions does the vector loop of saxpyAvx2 execute for n = 4,100, and how many elements does the remainder loop handle?

  1. Vector iterations: the loop runs while i + 8 ≤ n, stepping by 8: the last full block starts at i = 4,088 (4,088 + 8 = 4,096 ≤ 4,100; the next, 4,096 + 8 = 4,104, is too far). Iterations = 4,096 / 8 = 512.
  2. Remainder: i = 4,096 after the loop, so the scalar loop handles elements 4,096 to 4,099: 4 elements (4,100 mod 8 = 4).
  3. SIMD arithmetic instructions in the vector loop: one FMA per iteration = 512, plus 2 loads and 1 store per iteration = 1,536 memory instructions. A scalar loop would need 4,096 FMAs (or 4,096 multiplies and 4,096 adds) and 3 × 4,096 = 12,288 memory instructions for the same elements.
  4. FLOPs: saxpy does 2 floating-point operations per element (one multiply, one add, fused in one FMA): 2 × 4,100 = 8,200 FLOP. This is the count Listing 2 uses for its GFLOP/s column (2 / ns per element).
  5. Bytes: per element 4 (read x) + 4 (read y) + 4 (write y) = 12 bytes, so 49,200 bytes; the arithmetic intensity is 8,200 / 49,200 ≈ 0.17 FLOP per byte. Keep this number for F2-56: it predicts that saxpy on large arrays is limited by memory, which the 64 MiB measurement shows.

Where the analogy breaks


    

  • A real ladle with eight spouts pours the same amount into each cup. A SIMD instruction computes a different result in each lane (each lane has its own operands); what is shared is the operation, not the value.
    • 

  • Ji-woo can lift the ladle over any eight cups on the counter. A vector load takes consecutive elements from memory; collecting scattered elements (a "gather") is a separate, slower operation, and many loops cannot be vectorised because their data is not consecutive.
    • 

  • In the story, wider ladles are always better if the cups are ready. In processors, wider vectors can come with other costs (fewer units, frequency or power effects documented per processor), and a memory-bound loop gains nothing.
    • 

  • Soup does not care about the order it is poured in. Floating-point sums do: changing the order changes the rounding (Listing 4).
    •

Summary


    

  • SIMD instructions apply one operation to 4, 8 or 16 floats in xmm, ymm or zmm registers; ps means all lanes, ss one lane.
    • 

  • Let the compiler vectorise, then check its report (-fopt-info-vec) and, above all, the instructions.
    • 

  • Dependencies between iterations, branches the target cannot predicate, possible aliasing and non-contiguous data stop or complicate vectorisation.
    • 

  • Float reductions keep their source order unless you allow reassociation; write explicit partial sums to choose a new deterministic order.
    • 

  • Intrinsics give control; protect them with a per-function target attribute, a run-time CPU check and a remainder loop.
    • 

  • SIMD multiplies arithmetic throughput, not memory bandwidth: large-array loops with little arithmetic stay memory-bound (next stop: the roofline, F2-56).
    •

Forensic lab answer key


Observation. Strict build: the main loop (from the instruction after nopl to the backward jne) has eight vaddss instructions with memory operands at offsets 0, 4, 8 … 28 from the pointer, one add $0x20 (32 bytes = 8 floats per iteration), and all eight add into the same register %xmm0: one accumulator, eight floats per iteration, scalar arithmetic. Fast-math build: the main loop is a single vaddps (%rax),%ymm1,%ymm1 plus pointer update: eight lanes added in parallel into %ymm1; after the loop, vextractf128, vmovhlps, vshufps and further vaddps combine the eight partial sums.


Did the compiler lie? No. GCC transformed the loop to process a block of 8 floats per iteration (loads covering 32 bytes) but, without permission to reassociate, kept the additions in source order: an "in-order reduction". The report's "vectorized" describes the loop transformation, not lane-parallel arithmetic. The speed is set by the latency chain of scalar additions, so the job did not get faster.


Why the totals changed. With -ffast-math the additions are done in eight lanes and combined in a tree: a different rounding order (Figure 2). Listing 4 shows the size of such a change on comparable data. Neither total is exactly "correct"; both approximate the exact sum; the double-precision reference is closer to it.


Fix and test. Write the reduction with explicit partial sums (as sum8), which GCC vectorises without -ffast-math (R5 shows sum8 several times faster than sumPlain in builds 2 and 3); the result is identical in every build because the order is in the source. Update the regression test to compare against a double-precision reference with a justified tolerance, rather than bit-equality with an old order. How the evidence was produced: kernels.cc compiled by run.sh with -O3 -march=native and with -O3 -march=native -ffast-math, disassembled with objdump; unedited, first 40 lines of the function.
