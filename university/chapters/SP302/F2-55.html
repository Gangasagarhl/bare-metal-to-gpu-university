Story hook

The new owner of a busy restaurant wants to know why dinner service is slow. She has two ways to find out. She can stand at the pass and, every few minutes, glance at the kitchen and note what each cook is doing at that moment: "chopping", "waiting for the oven", "washing pans". After an evening of glances, the notes form a picture of where the time goes, without disturbing anyone. Or she can hire a clerk who follows the cooks and writes down every single action with its start and end time. The clerk's log is complete and exact, but the cooks, who must stop and spell out each step, work more slowly while being watched.

That evening the glances say "washing pans" a third of the time. Nobody had suspected the pans; everyone had blamed the oven. That is what profilers are for: to replace the team's opinion about where the time goes with evidence.

This chapter teaches both kinds of profiler with tools that work in the build container (gprof for sampling, Callgrind for instrumentation), records honestly what happened when we tried the kernel's own perf tool, and ends with the course's forensic case: a release that became markedly slower, two profiles, and a diff with four changes, only one of which matters.

What you will be able to do

  • Choose between a sampling and an instrumenting profiler for a question, and state each one's costs and blind spots.
  • Read a flat profile and a call-graph profile, distinguishing self cost from inclusive cost.
  • Profile a C++ program with gprof and Callgrind, restricting collection to the code you care about.
  • Diagnose a performance regression by comparing two profiles and a source diff, and confirm the cause with an experiment.
  • Explain what hardware performance counters measure and what you lose when they are not available.
Jargon box
Profiler (recap from SP202)
Simple words: a tool that tells you where a program spends its time (or another resource). Analogy: the owner's notes on what the kitchen is doing. Precise: a tool that attributes a cost (time, instructions, cache misses, allocations) to parts of a program (functions, lines, call paths), by sampling or by instrumentation. D1
Sampling profiler (recap from SP202)
Simple words: a profiler that looks at the program at regular moments and notes where it is. Analogy: the owner glancing at the kitchen every few minutes. Precise: a profiler that interrupts the program periodically (on a timer or a hardware counter overflow) and records the current instruction address (and possibly the call stack); a function's share of samples estimates its share of the cost. Low overhead, statistical, misses short rare events. D1 D3
Instrumenting profiler
Simple words: a profiler that adds counting code to every function or instruction so that nothing is missed (SP202 calls the instruction-counting kind an instruction-count profiler). Analogy: the clerk who logs every action. Precise: profiling by inserting code at compile time (gprof's -pg call counting) or at run time (Valgrind's dynamic binary translation in Callgrind) that counts events exactly; complete and deterministic, but it slows the program, often many times, and may change its behaviour. D3 D4
Self cost and inclusive cost
Simple words: self cost is what a function does itself; inclusive cost adds everything it calls. Analogy: the time the head cook spends cooking, versus that time plus all the jobs she hands to helpers. Precise: self (exclusive) cost is the cost of instructions inside the function's own body; inclusive cost is self cost plus the inclusive cost of its callees along the observed call graph. D4
Call graph
Simple words: the map of which function calls which. Analogy: the chain of who hands work to whom in the kitchen. Precise: a directed graph whose nodes are functions and whose edges are observed calls, annotated with call counts and costs; gprof and Callgrind both build one. D3 D4
Hardware performance counter
Simple words: a counter inside the processor that counts events such as cycles, instructions or cache misses. Analogy: a tally counter fixed to each oven door, clicking every time it opens. Precise: a programmable register in the CPU's performance monitoring unit that counts a selected micro-architectural event; Linux exposes counters through the perf_event_open system call, used by the perf tool. Availability inside virtual machines depends on the hypervisor. D5 R2
Performance regression
Simple words: a change that makes the program slower than before. Analogy: a new kitchen rule that adds a step to every dish. Precise: a measured, reproducible increase in a performance metric (time, instructions, memory) between two versions, under the same workload and environment. D1

Layer 1 — the kid explanation

Analogy

To find out where the kitchen's evening goes, you can glance in every few minutes and write down what each cook is doing (a sampling profiler), or you can have a clerk write down every action (an instrumenting profiler). Glancing is cheap but can miss a quick job; the clerk misses nothing but slows everyone down. Mapping: a glance = a sample of the program counter; the clerk = counting code added around every function or instruction; "washing pans a third of the time" = a function with a third of the samples.

The rule is to look before you change anything. People's guesses about where time goes are often wrong; a profile is evidence. And when something gets slower after a change, compare a profile from before with one from after: the part that grew is where to look.

Layer 2 — the student explanation

What we tried first, and what happened

On Linux, the usual first tool is perf, which samples using the processor's hardware counters D5. In this build container, perf stat -e task-clock -- true stopped with "WARNING: perf not found for kernel 6.18.44-fc" and exit code 2: the installed perf is a wrapper that needs a tool built for the running kernel R1. To check the counters themselves, Listing 1 calls the perf_event_open system call directly. Every hardware event (cycles, instructions, branch misses, cache misses) failed with errno 2; the software events task-clock and page-faults worked R2. So this chapter's evidence comes from tools that do not need hardware counters: gprof and Callgrind. Everything said about perf is untested on hardware in this build.

gprof: compile-time counting plus timer sampling

Compile and link with -pg; the program then counts calls to its own functions and samples its program counter on a timer while it runs, and writes gmon.out at exit. gprof -b -p prints the flat profile D3. On hotspot.cc (Listing 2: generate two million words, split them, count them in a std::map, sort the counts), the recorded flat profile gives splitWords half of 0.18 sampled seconds, countWords a third, generateText about a ninth R3. Two things in that output should make you cautious. Each sample is worth 0.01 seconds, so 18 samples in total: the percentages are coarse. And the call count printed for splitWords is 4,000,001, although the program calls it once; we have not established why (see the unverified box). A profile is evidence, but evidence must be read critically.

Callgrind: count every instruction

Callgrind runs the program on Valgrind's synthetic CPU and counts every executed instruction (Ir), attributing each to a function and each call to an edge of the call graph D4. The counts are exact and repeatable (run it twice and you get the same numbers, unlike timings) but they are instruction counts, not time: a cache miss and an addition both count as one instruction. On the same program, Callgrind gives the largest self cost to __memcmp_avx2_movbe in libc (21 %), followed by countWords (20 %), splitWords (17 %) and generateText (16 %) R4. gprof did not show memcmp at all: it profiles only code compiled with -pg, so time inside shared libraries does not appear in its table.

Reading self and inclusive columns

Self cost says where instructions execute; inclusive cost says which caller is responsible. memcmp's large self cost alone suggests "make memcmp faster", which is not in your power. The inclusive view (Figure 2) says that countWords is responsible for 43 % of the program, most of it in comparisons: each ++counts[w] walks a balanced tree and compares strings at every level R4. The fix is then in your code: a hash map, shorter keys, or counting on integer word ids. Read the self column to find where; read the inclusive column to find who asked.

A method, not a tool

  1. Write down the question ("why is the nightly report slower?") and the metric (time of the report step, median of 21 runs).
  2. Measure, with the F2-51 protocol, to confirm there is something to explain.
  3. Profile the whole program first, then restrict to the part that matters.
  4. Form one hypothesis from the profile, and test it with an experiment that could prove it wrong.
  5. Fix, then measure again with the same protocol.

This is the "scientific method" style of performance analysis described in performance texts (D1, pending verification D1); the forensic case applies it.

Layer 3 — the engineer's depth

The biases of each method

  • Sampling is statistical: with s samples, a function's share has an error of the order of the square root of its sample count; 18 samples cannot separate 30 % from 40 %. Run longer or sample faster. Samples can also be biased by when the timer can interrupt (skid: the reported instruction may be a few instructions after the one responsible) D1.
  • Instrumentation perturbs: -pg adds a call to a counting routine at every function entry, which inflates small functions; Valgrind executes every instruction through its translator, which made the one-run forensic profiles below take hundreds of milliseconds per step instead of tens (printed in orders_v1_cg.out and orders_v2_cg.out) R5. Exact counts of a slowed-down program.
  • Instruction counts are not time. Callgrind's Ir does not see cache misses, mispredictions or memory bandwidth unless you enable its simulators, and even then they are a model (F2-52, F2-54). A change that doubles instructions in a memory-bound loop may change time very little; a change that halves cache misses may not change Ir at all. Always confirm an instruction-count story with a timing.
  • Inlining moves cost. At -O2 the compiler inlines small functions into callers, so their cost appears under the caller's name. We used [[gnu::noinline]] on the functions we wanted to see; in real code, look at the disassembly or the profile at line level.

Restricting what you collect

Whole-program profiles are dominated by whatever the program does most, which in a benchmark is often the set-up. In the forensic programs, building 400,000 orders costs far more than the step being investigated. Callgrind's --toggle-collect='summarise*' collects only while summarise (and what it calls) runs, so the inclusive total is the cost of that step alone D4 R5. With perf, the equivalent is to measure a run that does only the work of interest, or to filter samples by function after recording.

What hardware counters would add

With hardware counters, perf stat reports cycles, instructions, branch mispredictions and cache misses for a real run at full speed, and perf record samples on any of these events, so you could ask "which functions cause the cache misses?" on the real hardware rather than Cachegrind's model D5. Instructions per cycle (IPC), computed from two counters, is the first number to look at: a low IPC suggests stalls (memory, mispredictions), a high one suggests the work itself is the cost. None of this could be run here; the box below says what to check.

How the hardware actually does it

A sampling profiler needs an interrupt. With a timer (gprof, or perf's software clock events), the operating system's timer interrupt fires, and the profiler records where the program was. With hardware counters, the performance monitoring unit is programmed to raise an interrupt when a counter overflows (for example every N cycles or every N cache misses), and the kernel records the instruction address, optionally with the call stack D5 D1. Instrumentation needs no hardware support: gprof's compiler-inserted calls run as ordinary code, and Valgrind translates the program's machine code into instrumented code on the fly D4. That is why Callgrind worked in a virtual machine where counters did not.

Worked example

From two profiles to a number. The forensic case's two Callgrind runs (Listings 3 and 4) count the instructions executed inside summarise for 400,000 orders R5:

  1. Totals: release 1, 70,529,774; release 2, 152,120,517. Ratio 152.1 / 70.5 ≈ 2.16; per order, 70,529,774 / 400,000 ≈ 176 instructions versus 152,120,517 / 400,000 ≈ 380.
  2. Rows present only in release 2 (self cost): _int_free 21,600,000; malloc 18,000,000; free 11,200,000; operator new 6,400,000; memcpy 4,400,000; arena free 1,200,000. Sum: 62,800,000, which is 157 instructions per order: one allocation, one copy and one release per order.
  3. Rows in both: _Hash_bytes 41,600,000 in both; isPremium self 19,512,896 in both. summarise self grows from 7,760,030 to 20,160,036 (+12.4 million, 31 per order).
  4. Check: 70.5 M + 62.8 M + 12.4 M ≈ 145.7 M; the remaining 6.4 M is in the small rows below the top 10 and the [???] stubs.
  5. Time, from the timed runs (F2-51 protocol, median of 21): 16.33 ms for release 1 and 26.40 ms for release 2, a factor of about 1.6 R6.

Lesson: the instruction count more than doubled, but the time grew by a smaller factor. Our hypothesis, not tested in this build: the added instructions (allocation, copying of recently used memory) run fast per instruction, while the unchanged hash-set probes, spread over a set of 5,000 heap-allocated names, wait on memory. The ticket says "2× regression"; the evidence says "2.2× instructions, 1.6× time on the build machine". Report both.

Where the analogy breaks


    

  • The owner's glances are random; a sampling profiler's timer is regular, and a program that does something periodic in step with the timer can fool it.
    • 

  • The clerk slows the cooks by a roughly fixed amount per action. Instrumentation slows different code by different amounts (small functions suffer most from -pg; Valgrind slows everything a lot), so even "exact" counts describe a distorted run.
    • 

  • In the kitchen, "where time goes" is one question. In a program it is several: instructions, time, cache misses, allocations. Each tool answers some of them.
    • 

  • A cook who works for another cook is visible. A function inlined into its caller disappears from the profile.
    •

Forensic lab answer key


Size of the regression. Time: 16.33 ms → 26.40 ms (median of 21), about 1.6× on the build machine (R6). Instructions inside summarise: 70,529,774 → 152,120,517, about 2.16× (R5). "2×" fits the instruction count; the time grew less. Results are identical (40,000 premium orders, same totals), so the work is the same.


New rows. _int_free, malloc, free, operator new, memcpy, arena free: 62.8 million instructions in total, about 157 per order. All are memory allocation and copying, once per order (for example 18,000,000 / 400,000 = 45 instructions per malloc call).


The cause. The isPremium parameter changed from std::string const& customer to std::string customer: every call now copies the customer name. The names are 30 characters ("customer-00012345@example-shop"), longer than the 15 characters std::string can hold inside the object in this library (H1), so each copy allocates heap memory, copies the characters and frees them when the parameter dies. The other three changes: the comment and the message text do not execute in the step; the rename i→k cannot change generated code. The profile confirms it: _Hash_bytes (41.6 M) and isPremium's self cost (19.5 M) are unchanged; only allocation rows and summarise's self cost grew.


Why under summarise. In the C++ calling convention used here, the caller constructs the by-value argument and destroys it after the call, so the copy, operator new, and free are reached from summarise's code, which is also where the inlined parts of the string copy constructor and destructor land (its self cost grew by 12.4 M). isPremium's inclusive cost is almost the same in both releases (62.77 M versus 62.76 M): the callee does the same work. Looking only at the function whose signature changed would have missed it; comparing the profiles found it.
