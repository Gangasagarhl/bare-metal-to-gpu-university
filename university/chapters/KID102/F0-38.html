Story hook

Analogy

It is game night. Grandma says: "I am thinking of a number from 1 to 100. Guess it! I will tell you if you are too low or too high."

Leila guesses 50. "Too high." She guesses 25. "Too high." Then 12. "Too low." Seven guesses later she has it, and she says: "I can always do it in seven!"

Her brother wants to play too, but Grandma has gone to bed. "Let's teach the computer to be Grandma," says Leila. "It picks a number, it gives hints, and it counts our guesses."

That is this chapter's project. It uses everything from this course: variables, decisions, a loop, functions, a test function and the debugger mindset. And it raises a new question: how does a computer, which always follows exact steps, "think of" a number?

What you will be able to do

  • Build a complete guessing game from small functions, each with one job.
  • Write a test function for the part that gives hints, and make main refuse to start the game if a test fails.
  • Explain what a pseudo-random number generator and a seed are, and why we fix the seed for a recorded run.
  • Explain why halving the possible numbers finds any secret from 1 to 100 in at most seven guesses, using a program as proof.
  • Plan your own course project and prepare for the practical exam.
Jargon box
Pseudo-random number generator
Simple words: A recipe that produces numbers that look random. Analogy: A very long, fixed shuffled list of numbers that you start reading at some place. Precise: An algorithm that produces a sequence of numbers from a starting value (the seed); the same seed gives the same sequence, as R3 shows with seed 2026. This course uses std::mt19937 with std::uniform_int_distribution. R3, D2
Seed
Simple words: The starting number for a pseudo-random number generator. Analogy: The page where you start reading the shuffled list. Precise: The value given to a generator when it is created; with seed 2026 the game's secret was 22 in every recorded run of this build (R1, R3). R1, R3

Layer 1 — the kid explanation

To teach the computer to be Grandma, split her job into small jobs. One job: pick a secret number. One job: compare a guess with the secret and say "Too low.", "Too high." or "Correct!". One job: keep asking for guesses and count them. Each small job becomes a function (F0-34).

Before you trust the hint job, test it. You know the right answers: 10 against a secret of 50 must be "Too low.". A test function checks these answers by itself, every time the program starts.

Now the tricky part: picking a number. A computer follows exact steps, so it cannot really "think of" a number. Instead, it uses a recipe that makes numbers that look random. The recipe needs a starting number, called the seed. Same seed, same numbers. Different seed, different numbers.

That sounds like a weakness, but it is useful. When we record a game for this book, we choose the seed ourselves. Then everyone who runs the program gets the same secret, and our recorded guesses still work. For real play, you would let the computer choose a seed that changes every time.

And Leila's claim, "always in seven"? If you always guess the middle, each hint throws away about half of the numbers. A program can try all 100 secrets and check her claim.

Layer 2 — the student explanation

The game (Listing 1) has five functions besides main: pick_secret, hint_for, play, check_hint and test_hint_for. main runs the tests first and ends with exit code 1 if any fail, so a broken hint function can never reach the player. In the recorded run the tests reported "test_hint_for: 0 failures". R1

To pick a secret, the program creates a pseudo-random number generator, std::mt19937, from the header <random>, and gives it a seed. A second object, std::uniform_int_distribution<int> with the limits 1 and 100, turns the generator's large numbers into a number from 1 to 100. R1, D1, D2

Listing 3 proves the "same seed, same number" rule on this machine: pick_secret(2026) called twice printed "22 22". It also used std::random_device to make five different seeds; those secrets are different in every run, so the output on this page shows one example and yours will differ. R3

Why fix the seed in the game? The game reads the guesses from the keyboard, and in the recorded run they came from a file: 50, 25, 12, 18, 21, 23, 22. Those guesses only make sense for one secret. With seed 2026 the secret was 22, the game said "Correct!" on guess 7, and anyone can repeat the run and get the same lines. A run that cannot be repeated cannot be checked. R1

The play function loops while (std::cin >> guess). The loop ends when the guess is correct (return tries;) or when the input runs out, for example at the end of the file; then it prints the secret and returns 0. That second exit matters: without it, a game with no correct guess could never end. R1, R4

Listing 2 checks Leila's claim. It plays against every secret from 1 to 100, always guessing the middle, (low + high) / 2, and moving low or high after each hint. It printed "Secret 22 needs 7 guesses." and "Most guesses ever needed: 7 (first for secret 2)". So seven guesses are always enough with this method, and sometimes seven are needed. R2

Layer 3 — the engineer's depth

Note

For the curious. Why seven? Each guess leaves at most about half: 100, then 50, 25, 13, 7, 4, 2, 1. Seven halvings get from 100 down to one number, because 2 multiplied by itself 7 times is 128, which is more than 100, while 6 times gives 64, which is less. For 1,000 numbers it would be 10 guesses, because 2 multiplied by itself 10 times is 1,024. Listing 2 confirms the 7 for this game; changing 100 to 1000 gave "Most guesses ever needed: 10". R2, R6

The name mt19937 names a well-known generator algorithm, the "Mersenne Twister". It is fully deterministic: it keeps a block of numbers in memory and mixes them with arithmetic each time you ask for a number. It is good for games and simulations, not for secrets such as passwords; that needs a generator designed for security. D1, D2

Not verified — check before relying on this

This build checked "seed 2026 gives 22" only with one toolchain (g++ 13.3.0 and its standard library). Whether another compiler's standard library gives the same secret for the same seed was not tested: the generator and the step that maps its output to 1–100 may be specified differently. Check the random number generation clause of ISO/IEC 14882 (the C++ standard) and record in the dossier which parts are fixed by the standard. Until then, the chapter only promises "same seed, same secret, same toolchain", which is what the comment on line 6 of Listing 1 says. R1, R3, D2

How the hardware actually does it

The processor has no dice. Every instruction it runs gives the same result for the same inputs (F0-29). The generator is ordinary arithmetic on numbers stored in memory, so a fixed seed leads to a fixed series of numbers, exactly as R3 showed. R3, D3

For a seed that changes, the program asks the outside world. std::random_device asks the system for a value that is hard to predict; in R3 it gave five different seeds and so five different secrets. R3, D2

Not verified — check before relying on this

Where the operating system on the build machine gets the values for std::random_device (for example timing of hardware events, or a special processor instruction) was not checked in this build. Check the documentation of the standard library and of Linux, and record the answer in the dossier.

Worked example

Plan the game before writing it, as an engineer would. Write each job as a function with a name, inputs and an output:

  1. pick_secret(seed) → a number from 1 to 100.
  2. hint_for(guess, secret) → "Too low.", "Too high." or "Correct!". Pure: no input, no output, so it is easy to test.
  3. play(secret) → the number of guesses, or 0 if the input ran out.
  4. test_hint_for() → the number of failures, using check_hint for each case.

Then work out the test answers by hand, before running anything: 10 against 50 is too low; 90 against 50 too high; 50 against 50 correct; and an edge case, 1 against 1 correct. Then predict the recorded game with secret 22 and the guesses 50, 25, 12, 18, 21, 23, 22: too high, too high, too low, too low, too low, too high, correct, so "You found it in 7 guesses.". The real run printed exactly that. R1

Where the analogy breaks


    

  • Grandma really thinks of a number. The program computes one from the seed; with the same seed, it always "thinks of" 22. R3
    • 

  • Grandma notices if Leila stops playing. The program only notices when the input ends; that is why play has a second way out. R1
    • 

  • Grandma might cheat or make a mistake on a bad day. A tested function gives the same hint for the same inputs every time, and if it is wrong, it is wrong every time, which is what makes tests useful. R1, R4
