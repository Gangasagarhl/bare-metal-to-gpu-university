Story hook

Analogy

Sofia hands her recipe card to cousin Tomás, the helper from F0-29 who rewrites recipes for Grandpa. Tomás hands it straight back with a note: "Line 7: I expected a full stop before 'std'."

Sofia's first feeling is panic. Her second feeling is annoyance: "Line 7 is fine!" Then she looks at line 6. "Put 3 apples in the bowl" has no full stop at the end. Tomás only noticed the problem when he reached the next line, because that is where the sentence suddenly made no sense.

Tomás is not angry, and he is not judging Sofia. He is telling her exactly where he got stuck. Sometimes his note is slightly off target, and sometimes one mistake makes him write three notes. But every note is a clue.

Real programmers see error messages every day, even after many years. The difference is that they read them calmly, from the top, like a detective. This chapter teaches you how.

What you will be able to do

  • Read a g++ message and name its parts: file, line, column, error or warning, and the description.
  • Find the real mistake, which may be on the line before the reported one.
  • Fix the first error first, and recognise follow-on errors that disappear with it.
  • Explain what the warning flags -Wall, -Wextra and -Werror do, using g++'s own help text.
  • Use the compiler's suggestions ("did you mean …?") as hints, not as orders.
Jargon box
Compiler error
Simple words: A message from the compiler that says it cannot build your program, and where it got stuck. Analogy: The helper saying: "I cannot rewrite this recipe; step 6 is missing its end." Precise: A diagnostic that stops compilation; g++ prints file:line:column: error: followed by a description and the source line with a marker (R2). R2, D2
Warning
Simple words: A message from the compiler that says "this is allowed, but it looks like a mistake". Analogy: The helper saying: "You bought pears but never used them. Did you mean to?" Precise: A diagnostic about legal but suspicious code, enabled by flags such as -Wall and -Wextra; with -Werror ("Treat all warnings as errors", R7) every warning stops the build (R5). R5, R7, D2
Follow-on error
Simple words: An extra error message caused by an earlier mistake, not by a new one. Analogy: One missing step that makes the next three steps confusing too. Precise: A diagnostic that appears only because the compiler was already confused by an earlier error; fixing the first error usually removes it, as in R3 and R6. R3, R6

Layer 1 — the kid explanation

When the compiler cannot understand your program, it does not build it. Instead it prints messages. They look scary at first: long lines, strange words, little arrows. But each message is a note from a helper, and it says where the helper got stuck.

Read the first message first. It has the file name, the line number and the position on the line. Go to that line. If it looks fine, look at the line right above it. Very often the mistake is a missing semicolon or a missing quote at the end of the line before.

One mistake can confuse the compiler so much that it prints several messages. Fix the first one, build again, and see what is left. Often the other messages disappear by themselves.

Some messages are warnings, not errors. A warning says: "This is allowed, but it looks like a mistake." In this course, we ask the compiler to treat every warning as an error. That sounds strict, but it catches many bugs before the program ever runs.

And the most important rule: an error message is not a bad mark. It is free help. Read it slowly. Be a detective.

Layer 2 — the student explanation

A g++ message starts with file:line:column:, then the kind (error, warning or note), then a description. Below it, g++ prints the source line with the line number and a marker (^~~~) under the place it means. Often the first line says which function the problem is in: "In function 'int main()'". R2, R3, D1

The compiler reports where it noticed the problem, which can be later than the mistake. In Listing 2 the semicolon is missing at the end of line 6, but the error is reported at line 7, column 5, where std appeared although a ; was expected. Then a second error followed: "'fruit' was not declared in this scope" at line 8, because line 7 was never understood as a declaration. Adding the ; fixes both. R2

A follow-on error is such a second message caused by the first mistake. Listing 3 shows another kind: apple is misspelled on line 8, and the compiler then also says "unused variable 'apples'", because the real apples is now never used. Fix the spelling and both messages go away. R3

Some messages contain suggestions. In Listing 3, g++ wrote "did you mean 'apples'?" and showed the corrected word. That suggestion was right. In F0-34, for a function used before its definition, g++ suggested "did you mean 'double'?", which was wrong. Suggestions are guesses based on spelling. R3, D1

Error messages use precise words for types. In Listing 4, the text "three" is described as const char*, which is how C++ sees a string literal here. You do not need to understand every word. "invalid conversion from … to 'int'" already says: "this kind of value does not fit into an int jar". R4, D1

Warnings are switched on with flags. g++'s own help describes them: -Wall "Enable most warning messages", -Wextra "Print extra (possibly unwanted) warnings", and -Werror "Treat all warnings as errors". With -Werror, the unused variable in Listing 5 stopped the build, and the message ends with the flag in square brackets: [-Werror=unused-variable]. R5, R7

Layer 3 — the engineer's depth

Note

For the curious. The square brackets at the end of a warning name the flag that controls it, such as [-Werror=parentheses] in F0-32 or [-Werror=uninitialized] in F0-30. That lets you look the warning up in the GCC manual by name. A line "cc1plus: all warnings being treated as errors" means the build failed only because of -Werror. R5, D2

The compiler is not the only tool that can complain. In SP101 you will meet the linker, which joins pieces of a program together and has its own messages, such as "undefined reference". They look different because a different tool prints them. D1, D2

Not every mistake produces a message. A program can compile perfectly and still be wrong: the loop that never ends (F0-33) and the missing name card (F0-35) compiled without a single warning. For those, you need tests and the debugger of F0-37.

How the hardware actually does it

Compiler errors happen before your program ever reaches the processor. The compiler is itself a program running on the processor, reading your text from top to bottom. When it cannot fit the next word into the rules of C++, it stops translating and writes messages instead. No executable is produced, so there is nothing for the processor to run. That is why a program with a compiler error can never cause a crash: it never starts. D2, D3

Worked example

We solve Listing 2 the detective way, step by step.

  1. Read only the first error. "missing_semicolon.cpp:7:5: error: expected ',' or ';' before 'std'". File: missing_semicolon.cpp. Line 7. Column 5.
  2. Go to the place. Line 7 is std::string fruit = "apples";. Column 5 is where std starts (the first four columns are spaces). The line looks correct.
  3. Read the description as a sentence. "Before 'std', I expected a ',' or a ';'." So something before std was not finished.
  4. Look one line up. Line 6 is int apples = 3 without a semicolon. Found it.
  5. Predict the effect of the fix. With the ; added, line 7 becomes a proper declaration, so the second error about fruit should disappear too.
  6. Fix and build again. The result is fixed.cpp, which built and printed "We have 3 apples.".

Both errors came from one missing character. The real messages are under Listing 2 below; the fixed program's run is under Listing 1. R1, R2

Where the analogy breaks


    

  • Tomás could read the whole card first and then point at the real mistake. The compiler reports where it got stuck while reading, which can be a line after the mistake (Listing 2). R2
    • 

  • Tomás writes one note per mistake. The compiler may write several messages for one mistake (follow-on errors), or one message for a line that is fine. R2, R3
    • 

  • Tomás would never refuse a recipe only because you bought pears you did not use. With -Werror, the compiler does exactly that, because we asked it to be that strict. R5
    • 

  • Tomás would also notice that "fill the bowl until exactly 20 spoons, 3 at a time" can never finish. The compiler checks the rules of the language, not whether your plan makes sense (F0-33).
    •
