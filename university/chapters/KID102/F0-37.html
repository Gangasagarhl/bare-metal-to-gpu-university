Story hook

Analogy

Malik is following a rice recipe with three steps. Something goes wrong: the kitchen fills with smoke, and he has no idea which step did it. Everything happened too fast.

Now imagine Malik had a pause button for the whole kitchen. Before each step, the whole kitchen freezes. The water stops in mid-air. Malik walks around, opens every jar, reads the timer, counts the cups. Then he presses "one more step" and watches exactly what that step does. Freeze again. Look again.

With that button, finding the smoky step would be easy. He would see the moment a jar holds something it should not, or the moment the recipe tries a fourth step that does not exist.

Real kitchens have no such button. But programs do. It is called a debugger, and in this chapter you will use a real one.

What you will be able to do

  • Build a program with debugging information and start it in the debugger gdb.
  • Set a breakpoint, run to it, print variables, and continue to the next stop.
  • Step through a program line by line with next, and into a function with step.
  • Find where a loop goes one step too far, both with the debugger and with printed trace lines.
  • Read a recorded debugger session as evidence and find a bug from it.
Jargon box
Debugger
Simple words: A program that runs your program one step at a time, so you can look inside. Analogy: A pause button for the kitchen: everything freezes and you can look into every jar. Precise: A tool (here GNU gdb 15.1) that starts or attaches to a program, stops it at chosen places and shows the values of its variables (R3, R5). R3, R5, D2 §5.1.1, §8.2
Breakpoint
Simple words: A place in your program where the debugger will pause. Analogy: A sticky note on step 9: "stop here and check". Precise: A location set with the gdb command break (help text: "Set breakpoint at specified location.", R5); the program stops each time it reaches that line (R4). R4, R5, D2 §5.1.1
Step
Simple words: Running exactly one more line of the program, then pausing again. Analogy: Doing one recipe step and freezing again. Precise: gdb's next runs one line and treats a function call as one line ("proceeding through subroutine calls"); step goes into the called function (R3, R5). R3, R5, D2 §5.2
Off-by-one error
Simple words: A loop that runs one time too many or one time too few. Analogy: Stirring 21 times when the recipe said 20. Precise: A bug where a boundary is wrong by one, for example i <= size() instead of i < size(); in R1 the loop reached i = 3 for a vector of size 3. R1, R4
Trace
Simple words: Extra printed lines that show what the program is doing, step by step. Analogy: The cook saying each step out loud while cooking. Precise: Output added only for debugging, such as [trace] i = 3, which shows the order of events and the values of variables (R2). R2

Layer 1 — the kid explanation

Some bugs are easy to see: the compiler points at them (F0-36). Others hide. The program builds, starts, and then does something wrong, too fast to watch. For those bugs you need to slow time down.

A debugger runs your program for you, but with a pause button. You tell it where to pause by setting a breakpoint, like a sticky note on one line: "stop here". When the program reaches that line, everything freezes. Then you can ask: what is in this jar? And that one?

From a pause you can go on in small or big steps. "Next" runs exactly one more line and freezes again. "Step" does the same, but if the line calls a function, it walks into the function with you. "Continue" runs on until the next sticky note.

The debugger does not fix anything by itself. It shows you the truth: the real values at the real moment. Your job is to compare them with what you expected. The first place where they differ is where the bug lives.

There is also a simple way without a debugger: add extra print lines that say what is happening. That is called a trace. It works everywhere, and you will try both.

Layer 2 — the student explanation

The debugger in this build is GNU gdb, version line "GNU gdb (Ubuntu 15.1-1ubuntu1~24.04.1) 15.1". It needs the program to be built with -g, which keeps the line numbers and variable names in the executable; the course flags already include -g (F0-29). R3, R5, D2 §4.1, D4 §3.10

You start gdb with the program: gdb ./steps_dbg. Then you type commands. gdb's own help describes the ones we use: break "Set breakpoint at specified location."; run "Start debugged program."; print "Print value of expression EXP."; next "Step program, proceeding through subroutine calls."; step "Step program until it reaches a different source line."; continue "Continue program being debugged, after signal or breakpoint." Most have one-letter short forms, such as b, r, p, n, s and c. R5

A breakpoint such as break steps.cpp:9 stops the program each time line 9 is about to run. At each stop, print i showed the counter: 0, 1, 2, and then 3. print steps.size() showed 3, and even the condition itself could be printed: print i <= steps.size() gave true when i was 3. That is the bug: the loop condition lets i reach 3. R4

To step through code, stop at the start of main (break main) and use next. In the session for Listing 3, next moved from line 11 to line 12; step on line 12 entered double_it and showed its parameter, number=3; next twice and the program was back in main at line 13 with plates equal to 6. R3

In our sessions, gdb did not wait for a person to type. The commands were stored in a small file and gdb ran them one by one (non-interactive mode, gdb -q -batch -x steps.gdb ./steps_dbg). With set trace-commands on, gdb printed every command with a + in front, so the transcript shows what was typed and what gdb answered. At your own keyboard you type the same commands after the (gdb) prompt. R3, R4

A trace is the no-debugger method: extra output lines such as [trace] i = 3. Listing 2 printed one before each step and showed the same story as gdb: i reached 3. R2

Layer 3 — the engineer's depth

Note

For the curious. Debuggers and sanitizers can get in each other's way. Our first attempt at the forensic session ended with "LeakSanitizer has encountered a fatal error" and the hint "LeakSanitizer does not work under ptrace (strace, gdb, etc)". The program's own output was lost. We switched leak checking off inside gdb only, with set environment ASAN_OPTIONS=detect_leaks=0, and the session worked. The runs without gdb keep every check. When a tool tells you how it fails, believe it and write it down. R9, D6

A debugger shows you a frozen moment, but it can also change it: gdb can assign a new value to a variable while the program is paused, or stop only when a condition is true (break 9 if i == 3, a form described in gdb's help for break: "[if CONDITION]"). You will use these in later courses. R5, D2 §17.1, §5.1.1

When the program was stopped by the exception, gdb reported "Program received signal SIGABRT, Aborted." and showed a library file that is not installed on the build machine ("No such file or directory"). That is normal: the stop happened inside library code, not yours. The command backtrace lists the chain of calls that led there, so you can walk back to your own line; its help text was not saved in this build, so this last point rests on the GDB manual (section 8.2, Backtraces). R4, D2 §8.2

How the hardware actually does it

A debugger is a program that controls another program, with help from the operating system. To make a breakpoint, the debugger places a special instruction at the start of the machine code for that line. When the processor reaches it, it stops your program and hands control to the debugger, which can then read your program's memory: that is how it finds the value of i. The -g information is the map from machine code back to your line numbers and variable names. The word "ptrace" in the LeakSanitizer hint above names the Linux facility for this kind of control. Its manual page says it lets one process "observe and control" another. It is "primarily used to implement breakpoint debugging". R9, D2 §5.1.1, §4.1, D5

Note

Two kinds of breakpoint. The GDB manual calls the usual kind a software breakpoint. gdb replaces the program's code at that place with a special instruction that hands control back to the debugger. When the program stops, gdb puts the original instructions back. A second command, hbreak, asks for a breakpoint built into the processor itself. That needs hardware support, which not every computer has. gdb can also choose between the two kinds by itself. Our recorded sessions used break only, and which kind gdb picked inside was not recorded. R3, D2 §5.1.1

Worked example

The debugger lab of this course: "find where a loop goes one step too far". We use the four questions of a detective.

  1. What did I expect? Three steps printed, then "The rice is ready.".
  2. What happened? Listing 1 printed the three steps, then stopped with std::out_of_range: "__n (which is 3) >= this->size() (which is 3)". "The rice is ready." never appeared. R1
  3. Where should I look? The message says index 3 was used on a vector of size 3. The only place that uses an index is line 9, inside the loop. So: break on line 9, and print i each time.
  4. What does the frozen program show? Stops 1 to 3: i = 0, 1, 2, and each "continue" printed one step. Stop 4: i = 3, and i <= steps.size() is true. Line 9 is about to call steps.at(3). R4

Conclusion: the condition i <= steps.size() allows one iteration too many. The valid indexes are 0 to 2, so the loop must stop when i reaches 3: i < steps.size(). Prediction for the fix: three steps, then "The rice is ready.", exit code 0. The real run of steps_fixed.cpp agreed. R6

Where the analogy breaks


    

  • A frozen kitchen stays frozen for ever. A paused program is waiting for the debugger; if you end the debugger, the program ends too (the sessions end with kill or by letting the program finish). R4
    • 

  • In the frozen kitchen you can see everything at once. In gdb you see only what you ask for: one print per variable. You must know what to look at, which is why you form a hypothesis first. R4
    • 

  • Freezing a kitchen would not change the soup. Running under a debugger can change how a program behaves: here the leak checker refused to work under gdb until we switched it off. R9
    •

Method hints


Compare "expected" and "observed" at every stop, not only at the end. The first stop where they differ points to the bug. Remember that gdb stops before the line it shows. State two hypotheses (for example "the input numbers are wrong" and "the total is not added up") and use the session to decide.



Mini-project
