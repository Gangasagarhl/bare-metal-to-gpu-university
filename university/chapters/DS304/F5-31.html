Story hook

Analogy

Lina moves into a brand-new house in a town where she knows nobody. The house is empty: no furniture, no instructions, not even her own address written down. She knows one thing: when you arrive, you shout "I'm new here!" in the street. The town hall answers: "Your address is 15 Station Road, and your starter parcel is called BOOTX64.EFI, at the depot at number 2." She walks to the depot, asks for the parcel by name, carries it home in small pieces and unpacks it; inside are the instructions for everything else. One day the depot clerk cannot find a parcel called bootx64.efi: on his shelf it is labelled BOOTX64.EFI, and he reads labels letter by letter.

A data centre installs and starts thousands of servers this way. A server with an empty disk (or a disk nobody trusts) asks the network for an address and a boot file, downloads it and runs it. That file then installs or starts the real operating system. In this chapter you build such a file, a UEFI program, and boot two virtual servers with it over QEMU's network. The program reports where it came from and the server's inventory from SMBIOS, and a small script turns the two reports into a table. That is the DS304 course project in miniature.

What you will be able to do

  • Explain the UEFI network boot sequence: boot option, DHCP with PXE options, TFTP download of the network boot program (NBP), start of the NBP; and where HTTP boot differs.
  • Build a UEFI application that is booted over the network and reads its own device path.
  • Collect a server inventory from SMBIOS and check it against an independent source (the virtual machine's configuration).
  • Recognise the byte-order trap in SMBIOS UUIDs.
  • Diagnose a PXE failure from a time-stamped console log and the boot server's configuration.
Jargon box
Network boot
Simple words: starting a computer from a file it fetches over the network instead of from its own disk. Analogy: Lina's starter parcel. Precise: a boot in which the firmware's boot manager selects a network boot option, obtains an address and a boot-file location from the network (DHCP), downloads the file (TFTP or HTTP) and executes it. D1 D2
PXE (Preboot Execution Environment)
Simple words: the long-established standard way for a computer's firmware to boot from the network. Analogy: the rule "shout 'I'm new here', then fetch the parcel from the depot". Precise: a specification, originally from Intel, that defines how a client's firmware uses DHCP (with PXE-specific options) to find a boot server and file, and TFTP to download it; UEFI firmware implements it as the PXE Base Code protocol for IPv4 and IPv6. D2 D1
TFTP
Simple words: a very simple file-download protocol, small enough to fit in firmware. Analogy: the depot that hands out parcels piece by piece, by exact name. Precise: the Trivial File Transfer Protocol over UDP: a read request names the file; the server sends numbered blocks, each acknowledged before the next; errors are sent as error packets with a code and a message; no authentication, no directory listing. D3
NBP (network boot program)
Simple words: the first program a computer downloads and runs when it boots from the network. Analogy: the starter parcel. Precise: the file named by the DHCP boot-file option and downloaded by the PXE client; on UEFI it is a UEFI application (in the lab, BOOTX64.EFI built from netboot.cc); in practice it is often a boot loader that fetches a kernel or an installer. D2 R2
HTTP boot
Simple words: network boot that downloads the boot file with the web's protocol instead of TFTP. Analogy: a courier with a van instead of carrying the parcel in pieces. Precise: a UEFI network boot method in which DHCP returns a URI and the firmware downloads the image over HTTP (or HTTPS), which is faster over long distances and can cross routers more easily than TFTP. D1
Device path (UEFI)
Simple words: a description, step by step, of where a device sits, like "root, then PCI slot 2, then the network card with this MAC". Analogy: directions to the depot: town, street, building. Precise: a sequence of variable-length nodes (type, subtype, 16-bit length, data) ending with an end node of type 0x7f, attached to a handle through the device path protocol; boot options and loaded images refer to devices with it. D1
Inventory
Simple words: the list of what a server is and has: maker, serial number, processors, memory. Analogy: the moving company's checklist. Precise: machine-readable facts used to identify and plan servers, here read from SMBIOS structures 0 (firmware), 1 (system, with serial number and UUID), 3 (chassis, asset tag), 4 (processor sockets) and 17 (memory devices), and checked against an independent record. D4

Terms from earlier chapters: DHCP (F5-06), UEFI application, OVMF, SMBIOS (F3-10, F3-12).

Layer 1 — the kid explanation

Usually a computer starts from its own disk. A server can also start with nothing on its disk at all. It calls out on the network: "I'm new, help!" A helper answers with an address for it and the name of a file to fetch. The server downloads that file and runs it.

In this chapter, the file is a small program you write. When it runs, it says where it came from and lists what the server is made of. Two pretend servers start this way, and you make a table of both.

Layer 2 — the student explanation

Why boot from the network

Analogy first: the town hall can set up a hundred new houses in a day because each house fetches the same parcel. Network boot lets operators install, reinstall, repair and run servers without touching their disks: a new rack is installed by switching it on; a server with a broken OS is reinstalled from the network; diskless servers run entirely from a network image; and the boot file is changed in one place for thousands of machines. D2 D6 Together with the BMC (F5-29), which can switch a server on and choose its next boot device, it gives fully remote control from power-on to running OS.

The sequence

Figure 1, step by step, with the lab's run as the example (R2):

  1. Boot option. The UEFI boot manager works through its boot options in order. OVMF created network options for the virtio network card: "UEFI PXEv4 (MAC:525400000701)" as Boot0001. Its device path is PciRoot(0x0)/Pci(0x2,0x0)/MAC(525400000701,0x1)/IPv4(…DHCP…), printed by OVMF itself. R2 D1
  2. DHCP. The firmware's PXE client broadcasts a DHCP discover with options that say "I am a PXE client of this architecture". A DHCP server that serves PXE answers with an address and the boot server and file name. The run shows the result: "Station IP address is 10.0.2.15", "Server IP address is 10.0.2.2", "NBP filename is BOOTX64.EFI". D2 R2
  3. TFTP. The client asks the TFTP server for the file by name, first for its size ("NBP filesize is 8192 Bytes"), then downloads it block by block. D3 R2
  4. Start. The firmware loads the file as a UEFI image and starts it, exactly as if it came from a disk; the loaded image remembers the device it came from. Our program prints that device's path and the inventory, then ends the virtual machine. D1

In QEMU, steps 2 and 3 are served by QEMU itself: its user-mode network backend has a built-in DHCP server, and the options tftp=dir and bootfile=f turn on a TFTP server for a directory and set the boot-file name in the DHCP answer (QEMU's help in R1). R1 In a data centre these are separate services on a provisioning network.

What happens after the NBP

Our NBP is the whole program. A real NBP is a boot loader (or a network-capable chain loader) that downloads a kernel and an initial RAM disk, often over HTTP, and the kernel then runs an installer or mounts its root file system from the network. D6 Server provisioning systems drive this: they map each server's MAC address or SMBIOS UUID to a role and serve a different configuration per server.

Inventory from SMBIOS

The NBP reads SMBIOS (F3-12) and prints "inventory: key=value" lines: firmware vendor and version (type 0), manufacturer, product, serial number and UUID (type 1), chassis serial and asset tag (type 3), the number of processor sockets (count of type 4) and memory (sum of type 17 sizes). D4 On a real server these come from the vendor's firmware and from the factory's records; on QEMU, from the -smbios, -smp and -m options (R1). report.py collects the lines from each console into one table (R3). Curriculum milestone B6 asks for exactly this round trip: "The banner prints QEMU's SMBIOS strings; overriding them with QEMU's SMBIOS options changes the banner accordingly." S1 The two servers with different options are that test.

Layer 3 — the engineer's depth

Reading the device path

Listing 1 asks the firmware for the loaded image of itself, then for the device path of the device it was loaded from, and decodes the nodes. D1 The run (R2) shows four nodes: type 2 subtype 1 (ACPI, the PCI root), type 1 subtype 1 (PCI device 0x02 function 0), type 3 subtype 11 (MAC address 525400000701) and type 3 subtype 12 (IPv4). They match OVMF's own text form of the boot option, PciRoot(0x0)/Pci(0x2,0x0)/MAC(525400000701,0x1)/IPv4(0.0.0.0,…,DHCP,…), node for node, which is the independent check for the node numbers written from memory. The IPv4 node's addresses are 0.0.0.0 in both: the node says "use DHCP", not which address DHCP gave. So the device path tells you which card and which protocol, and the console line "Station IP address is 10.0.2.15" tells you the address.

The UUID byte-order trap

Server A was given uuid=00112233-4455-6677-8899-aabbccddeeff. Listing 1 prints the 16 bytes of SMBIOS type 1's UUID field in storage order: 33221100 5544 7766 8899aabbccddeeff (spaces added). The first three groups are reversed byte by byte; the last two are not. Server B shows the same pattern (R2). R2 This matches the SMBIOS rule, from memory of D4 and pending verification, that the first three fields of the UUID are stored little-endian. D4 Consequence for inventory: a tool that prints the raw bytes as a UUID string reports a different identity than the one in the purchase records, the BMC's Redfish page or the provisioning database. The check in R4 keeps the difference visible ("NOT the same order") rather than hiding it; the mini-project asks you to convert it.

From two servers to a rack

The lab's QEMU network serves one machine per network. A rack of 40 servers changes the engineering:

  • Separation. Provisioning DHCP must answer only the provisioning network, or it competes with other DHCP servers; the BMCs are on the management network (F5-29). D6
  • Identity. The DHCP server decides per MAC address (or per architecture option, for mixed firmware) which file each server gets; the inventory (serial, UUID) links the MAC to the asset record.
  • Transport. TFTP sends one block at a time and waits for each acknowledgement; the larger the image and the longer the round trip, the slower it is. D3 The usual design downloads only a small first stage with TFTP and everything else with HTTP, or uses UEFI HTTP boot directly; in the forensic run, OVMF offers "HTTP Boot over IPv4" as its third option (R5). R5
  • Security. Plain PXE trusts the network: whoever answers DHCP decides what the server runs. Mitigations are an isolated provisioning network, UEFI Secure Boot (the NBP must be signed by a trusted key), HTTPS boot, and measured boot. D1 D6

The DS304 exam asks you to plan "the boot and management path for a rack of servers"; the list above and F5-29's warning box are the parts of that plan.

Not verified — check before relying on this

Written from memory and not confirmed by a run: the DHCP message names and the PXE options (client architecture, vendor class "PXEClient"); TFTP's block size, option negotiation (block size and transfer size) and error codes; HTTP boot's DHCP options and URI handling; the SMBIOS type 1, 3, 4 and 17 offsets used by Listing 1 (confirmed only by agreement with QEMU's options in R4) and the UUID byte-order rule; the device-path node type and subtype numbers (confirmed only by agreement with OVMF's text in R2); the meanings of the codes PXE-E23 and PXE-E16 beyond the text OVMF printed. Check them in the UEFI Specification, the PXE specification, the TFTP and DHCP RFCs and the SMBIOS Reference Specification. Not established in this build: why about 64 s pass between the failed PXEv4 attempt and the start of PXEv6 in R5 (the time-out behind it was not identified).

How the hardware actually does it

On a physical server, the network card's option ROM or the platform firmware's built-in network stack provides the UEFI network driver; the PXE client in the firmware uses it to send and receive frames, without any operating system. D1 The network card is a PCI device (in the lab, PCI device 2 on the root bus: QEMU's virtio-net-pci), and its MAC address is the identity the DHCP server sees. R2 The downloaded file goes into memory allocated by the firmware, is checked as a PE image (and, with Secure Boot, its signature), relocated and called. The switch port must forward the broadcast DHCP traffic during boot: switch features that delay a port's forwarding after link-up (for loop protection) can make the first DHCP attempts fail, which shows up as a slow or failed network boot on hardware but never in QEMU. D6 Untested on hardware in this build.

Watch out

Never start a DHCP or PXE server on a network you do not own: it can answer other computers' requests and make them boot or install whatever it serves. Keep provisioning networks separate, and test PXE configurations in QEMU's private user-mode network as this lab does. D6

Worked example

Predict server B's inventory from its QEMU options, then check it against R2 and R3.

  1. Options: -smp 4,sockets=1,cores=4 -m 1G, -smbios type=1,…,serial=SRV-B-0002,uuid=0f1e2d3c-4b5a-6978-8796-a5b4c3d2e1f0, -smbios type=3,serial=CH-B-02,asset=RACK1-U08, MAC 52:54:00:00:08:01.
  2. Sockets: one socket, so one type 4 structure: cpu.sockets=1. (Cores are inside the socket; Listing 1 counts sockets only.)
  3. Memory: 1 GiB = 1024 MiB in one type 17 structure: memory.mib=1024.
  4. UUID raw bytes: reverse the first three groups byte by byte: 0f1e2d3c → 3c2d1e0f, 4b5a → 5a4b, 6978 → 7869; keep 8796 a5b4c3d2e1f0. Prediction: 3c2d1e0f5a4b78698796a5b4c3d2e1f0.
  5. Device path: the same PCI position as server A (same machine type and card order), MAC node 525400000801.
  6. Check: R2 and R3 show exactly these values. The firmware lines (vendor "Ubuntu distribution of EDK II", version 2024.02-2ubuntu0.10) come from OVMF, not from our options, and match the toolchain record.

Where the analogy breaks


    

  1. Lina knows her own name; a booting server knows only its MAC address (and, if the firmware sends it, its UUID). The DHCP server decides everything else.
    2. 

  2. The town hall is trusted; a DHCP answer is not. Any machine on the network can answer; the analogy hides the security problem of Layer 3.
    3. 

  3. Lina carries pieces home in any order; TFTP blocks are numbered and acknowledged one by one, which is why TFTP is slow over long round trips.

Mini-project


The DS304 course project: network-boot your OS (your kernel from earlier courses, or Listing 1 as a stand-in) on two virtual servers and report their inventory from SMBIOS. Deliverables: a run script that boots both servers over the network without manual steps; an inventory table with at least serial number, UUID in standard text form, sockets, memory size and asset tag; checks that compare every value with the virtual machines' configuration; and a one-page plan for the same on a real rack (provisioning network, DHCP per MAC, BMC next-boot setting, security). Summary


    

  • UEFI network boot: a boot option for the network card → DHCP gives an address and a boot-file name → TFTP (or HTTP) downloads it → the firmware starts it like any UEFI image.
    • 

  • In the lab, OVMF booted BOOTX64.EFI (8192 bytes) from QEMU's built-in DHCP/TFTP on two servers.
    • 

  • The program's device path (ACPI root, PCI 2.0, MAC, IPv4) matched OVMF's own text; the IPv4 node records "DHCP", not the address.
    • 

  • Inventory from SMBIOS (types 0, 1, 3, 4, 17) matched the QEMU options for both servers; the raw UUID shows the first three fields byte-reversed.
    • 

  • TFTP names are exact: bootx64.efi is not BOOTX64.EFI; one wrong name cost more than a minute of fallbacks.
    • 

  • At rack scale: separate provisioning networks, per-MAC configuration, HTTP for large files, and signed images.

  1. DHCP succeeded ("Station IP address is 10.0.2.15", "Server IP address is 10.0.2.2", "NBP filename is bootx64.efi" at 7.4 s). TFTP failed: "NBP filesize is 0 Bytes", "PXE-E23: Client received TFTP error from server", and Boot0001 "Not Found".
    2. 

  2. H1: the TFTP server does not have the requested file. For: the directory holds BOOTX64.EFI, the request is bootx64.efi, and the server returned an error rather than a time-out. H2: TFTP is unreachable (firewall, wrong server). Against: an error packet came back from the server within milliseconds, so it was reachable and answered.

  3. The firmware moved to its next boot option, PXE over IPv6, which reported "No valid offer received" at 71.5 s (QEMU's user network gave no IPv6 boot offer), then to HTTP boot over IPv4 at 72.0 s. Each fallback has its own waiting; the 64 s before the IPv6 attempt's message was not explained in this build.
    4. 

  4. Root cause: the boot-file name in the DHCP configuration (bootfile=bootx64.efi) does not match the file name on the TFTP server (BOOTX64.EFI); this TFTP server compares names exactly. Smallest fix: set bootfile=BOOTX64.EFI (or add a file with the lower-case name).
