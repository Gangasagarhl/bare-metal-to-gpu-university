Story hook

Analogy

Sofia owns a cottage in a town far from hers. She cannot drive there whenever the heating fails. So her friend Tariq lives in the cottage's little gatehouse. Tariq has his own key, his own phone line and his own small battery lamp, so he answers even during a power cut or when the cottage is locked and dark. When Sofia phones, Tariq can read the thermometers, switch the cottage's power off and on, and read her the notebook where he writes down everything unusual. In the early years they agreed on a list of numbered codes: "06-01" means "tell me who you are". Later they switched to a written form with named boxes, sent by e-mail, which anyone can read without the code list.

Every server in a data centre has a Tariq: the baseboard management controller (BMC), a small computer on the main board that stays powered whenever the server is plugged in. Operators use it to switch servers on and off, read their sensors, read their event logs and reach their consoles from far away, also when the operating system has crashed or was never installed. The numbered codes are IPMI, the long-established message set; the written form is Redfish, the newer web interface. In this chapter you talk IPMI to a simulated BMC from a UEFI program, byte by byte through the KCS interface, until you ask it to switch your own virtual machine off, and it does. Then you walk a model of a Redfish service by following its links.

What you will be able to do

  • Explain what a BMC is, why it works when the host is off, and the difference between in-band and out-of-band management.
  • Encode and decode IPMI requests and responses (network function, command, completion code, data) and carry them over the KCS interface.
  • Use the IPMI functions an operator needs most: identify the BMC, read the chassis power state, read and write the system event log (SEL), and control power.
  • Describe Redfish's model (resources at paths, links, collections, actions) and discover a service from its root.
  • Diagnose a wrong-server power action from BMC audit logs and an automation log.
Jargon box
BMC (baseboard management controller)
Simple words: a separate small computer on a server's main board that can switch the server on and off and watch its health, even when the server is off. Analogy: Tariq in the gatehouse (in the F3 world of F3-42: the night watchman). Precise: a system-on-chip with its own processor, memory, firmware and network port, powered from standby power, that controls host power, reads sensors, drives fans, logs events and offers a remote console; reachable from the host (in band) and over the network (out of band). D1 D3 (Definition shared with the glossary entry of F3-42.)
In-band management
Simple words: the server's own operating system talks to its own BMC, from inside the box. Analogy: Sofia calling Tariq from inside the cottage. Precise: access to the management controller from the host through a host-side interface (KCS, SSIF or BT for IPMI; a host interface for Redfish); it needs a running host and host software, unlike out-of-band management (defined in OS305), which uses the BMC's own network connection and works whatever the host's state. D1 D2
IPMI
Simple words: an older standard set of messages for talking to a BMC. Analogy: the list of numbered phone codes. Precise: the Intelligent Platform Management Interface: request messages with a network function (netfn) and command number plus data, answered by a response with netfn + 1, the same command, a completion code and data; carried in band (for example the KCS interface) or out of band over the LAN. D1 L1 (Definition shared with F3-42.)
KCS interface
Simple words: the simplest way for the host's processor to pass IPMI messages to the BMC: two I/O registers and a byte-by-byte handshake. Analogy: a hatch in the gatehouse wall with one tray in each direction and a flag that says "tray full". Precise: Keyboard Controller Style interface: a data register and a status/command register; status bits OBF (output buffer full) and IBF (input buffer full) and a two-bit state (idle, read, write, error); control codes start and end a write phase and request each byte of the read phase. D1 R2
SEL (system event log)
Simple words: the BMC's diary of unusual events: a fan stopped, a temperature crossed a limit, the power went off. Analogy: Tariq's notebook. Precise: a non-volatile log of fixed-size records kept by the BMC, each with a record ID, a record type, a time stamp from the BMC's clock and, for system events, the generator, sensor type, sensor number, event type and event data; read and written with Storage commands. D1 R2
Completion code (IPMI)
Simple words: the first byte of every IPMI answer: 0 means "done", anything else says what went wrong. Analogy: Tariq's "yes, done" or "I don't know that code". Precise: a one-byte status in every IPMI response; 0x00 is success, and the Linux UAPI header in the build container names, among others, 0xC1 "invalid command" and 0xFF "unspecified". L1 D1
Redfish
Simple words: the newer way to manage servers, over the same web technology browsers use. Analogy: the written form with named boxes. Precise: a DMTF standard for management over HTTPS with JSON resources, which many BMCs offer beside or instead of IPMI. D2 (Definition shared with F3-42.)
Service root (Redfish)
Simple words: the one address a Redfish client must know; everything else is found from there. Analogy: the first page of the form book, listing all other forms. Precise: the top resource of a Redfish service, whose links lead to the collections of systems, chassis, managers and services; clients discover resources by following links rather than by building paths themselves. D2

Terms from earlier chapters: SMBIOS (F3-12), DHCP (F5-06), NUMA node (F5-28).

Layer 1 — the kid explanation

A server has a tiny helper computer inside it. The helper never sleeps while the server is plugged in. It watches the temperatures and the fans, writes down anything strange in its notebook, and can press the server's power button for you.

You can talk to the helper from inside the server or from far away over a separate network. There are two languages. The old one uses short number codes. The new one uses web pages with named fields. In this chapter you speak the old language one byte at a time, and you hear the helper answer.

Layer 2 — the student explanation

Why a second computer

Analogy first: Tariq answers even when the cottage is dark. A data centre has too many servers to visit, and the moments when management matters most are exactly the moments when the server's own software cannot help: it is switched off, it hangs during boot, its OS crashed, or it has no OS yet. The BMC solves this by being independent: its own processor and firmware, powered from the standby supply that is present whenever the power cord is in, with its own network connection. D1 D3 From there it can switch the host's main power on and off and reset it, read the sensors on the board (temperatures, voltages, fan speeds, power supplies), run the fans, record events, store inventory data (field-replaceable unit data, FRU), and redirect the host's console so that an operator sees the firmware screens remotely. D1 D2 F3-42 modelled a BMC from the firmware side; this chapter takes the operator's side.

IPMI messages

Every IPMI request has the same shape: a network function (netfn), which groups commands by area; a command number; and data. The response carries netfn + 1, the same command, a completion code and data. D1 The Linux UAPI header in the build container names, for example, netfn 0x06 / 0x07 as "App" request and response, command 0x01 as Get Device ID, netfn 0x0A / 0x0B as Storage, command 0x44 as Add SEL Entry, and completion code 0xC1 as "invalid command". L1 On the KCS interface, the first byte carries the netfn in its upper six bits and a logical unit number (LUN) in its lower two: netfn 0x06 with LUN 0 is the byte 0x18, and the response's 0x1C decodes as netfn 0x07. D1 R2

The commands an operator uses most, and the lab sends, are: Get Device ID (who are you, which firmware revision), Get Chassis Status (is the host powered), Get SEL Info, Add SEL Entry and Get SEL Entry (the event log), and Chassis Control (power off, on, cycle, reset). D1 Sensors are described by a sensor data record repository (SDR) and read one by one; thresholds on them generate the events that end up in the SEL. D1 F5-33 reads such a log during an incident.

Transports

The same messages travel over different paths. D1 S1

  • In band, from the host: the KCS interface (two I/O ports and a handshake, this chapter's lab), SSIF (over SMBus) and BT (block transfer). The host's OS has a driver for them; on Linux it is the IPMI driver whose header you see in L1. L1
  • Out of band, over the BMC's network port: IPMI over LAN, inside UDP packets with sessions and authentication defined by the specification. D1

How does the host find its BMC? The firmware describes it in SMBIOS structure type 38 (IPMI device information): the interface type, the IPMI version, the BMC's address on the internal management bus and the interface's base address. D4 Listing 1 reads that structure first; under QEMU it says "KCS, 2.0, BMC address 0x20, base 0xca3 with bit 0 set (I/O space)", which gives data port 0xca2 and status port 0xca3, matching QEMU's isa-ipmi-kcs default ioport=3234 (decimal 3234 = 0xca2). R1 R2

Redfish

Redfish replaces the numbered codes with resources: JSON documents at paths under one service root, served over HTTPS. D2 Resources link to each other; collections list their members as links; state changes go through actions (a POST to an action's target) or through updates of writable properties; the meaning of each property is defined by published schemas, and services can push events to subscribers. D2 The important habit is discovery: a client starts at the root and follows links; it does not assume that system "1" exists. Listing 2 is a model of exactly that habit, without HTTP.

Layer 3 — the engineer's depth

The KCS state machine in detail

The KCS status register has two flags and a state. IBF set means the BMC has not yet taken the last byte the host wrote; OBF set means the BMC has put a byte in the output register for the host. The state field (top two bits) says what the BMC thinks is happening: idle, read (it is sending a response), write (it is receiving a request) or error. D1 A request is written as: control code WRITE_START to the command register; every byte but the last to the data register; WRITE_END to the command register; the last byte to the data register. After each write the host waits for IBF to clear, checks that the state is still "write", and clears a stale OBF by reading the data register. The response is then read byte by byte: wait for OBF, read the byte, write the READ control code to the data register to ask for the next one; when the state becomes idle, one final byte is read and discarded. D1 Listing 1's transact implements this and returns a negative step number when the BMC does not follow it, so that a failure says where it happened.

This handshake was written from memory of the specification's KCS chapter; the run shows only that QEMU's model accepts it for eight requests of six kinds (R2). A real BMC may be stricter (timing, error recovery with the GET_STATUS/ABORT control code, which Listing 1 does not implement). Production drivers, such as Linux's, also handle interrupts instead of polling and retry after errors. D1

The SEL record, decoded from the run

Listing 1 adds a 16-byte record and reads it back. The request bytes are: record ID 0x0000 (the BMC assigns one), record type 0x02 (system event), four time-stamp bytes (the BMC fills them in), generator ID, event-message revision 0x04, sensor type, sensor number, event type and three bytes of event data. D1 The responses show what the BMC did with it (R2):

  • Get SEL Info before: version 0x51, 0 entries, 2048 bytes free; after: 1 entry, 0x07f0 = 2032 bytes free. One record costs 16 bytes, as expected.
  • Add SEL Entry returned record ID 0x0000; Get SEL Entry returned "next record ID" 0xffff (there is no next one) followed by the 16 stored bytes, with the time stamp filled in.
  • The time stamp is a 32-bit count of seconds. Convert it on Linux with date -u -d @<value> and compare it with the run record's date: line: in the run shown they agree within one second (the date: line is written immediately after QEMU ends), so QEMU's simulated BMC takes its clock from the host. A real BMC has its own clock, set by the host, by the network or by hand; a BMC clock that is wrong makes every incident timeline wrong (F5-33).

Reading completion codes, and the device ID surprise

Get Self Test Results returned completion code 0xC1, which L1 names "invalid command": QEMU's simulated BMC in this build does not implement that command. L1 R2 A management tool must treat this as "not supported", not as "self test failed". More surprising: the lab started the simulated BMC with device_id=0x42, a property QEMU's own help lists (R1), but Get Device ID reported 0x20, which is both the property's default in QEMU's help (R1: "default: 32", decimal 32 = 0x20) and the value the Linux header names as the default BMC slave address. L1 A second run during authoring with slave_addr=0x24 still reported 0x20, while SMBIOS type 38 followed the new address. Why the property does not reach the response was not investigated (QEMU's source file hw/ipmi/ipmi_bmc_sim.c would answer it; not opened). The lesson does not depend on the cause: compare what you configured with what the device reports, and keep the mismatch visible (the "NOTE" line of R3) instead of trusting either side.

Redfish design choices

Three properties of Redfish matter to an engineer. D2 First, it is self-describing: each resource names its type and schema version, so a client can check what it is reading. Second, it is discoverable: collections and links replace fixed numbering, which is why Listing 2's client starts at the root. Third, it uses ordinary web security (HTTPS, sessions, accounts and roles), which is easier to audit than IPMI over LAN's own session protocol. D2 D1 The cost is size: a JSON document and a TLS session instead of a few bytes, and schemas that vendors extend with their own properties ("OEM" sections) that portable tools must ignore. D2

Not verified — check before relying on this

All Redfish names in this chapter and in Listing 2 (the paths under /redfish/v1, @odata.id, Members, Links, Actions, PowerState, the action ComputerSystem.Reset and its ResetType values ForceOff and On, Thermal, ReadingCelsius) were written from memory of the DMTF Redfish specification and schemas, which could not be opened (the guide's registry records that the DMTF site returned "403 Forbidden"). Check each against the Redfish Specification and the ComputerSystem, Chassis and Thermal schemas of the version your BMC reports. The IPMI details not confirmed by L1 (the KCS control codes 0x61, 0x62, 0x68, the status bits, the Chassis netfn 0x00 and its commands 0x01 and 0x02, Get Self Test Results 0x04, Get SEL Info 0x40, Get SEL Entry 0x43, the SEL record layout, sensor type 0x01, and the SMBIOS type 38 offsets) were written from memory and are supported only by QEMU's acceptance in R2; check them in the IPMI v2.0 Specification and the SMBIOS Reference Specification.

How the hardware actually does it

A BMC is a system-on-chip with an embedded processor, its own DRAM and flash, Ethernet, many I2C/SMBus controllers, fan-tachometer and PWM blocks, analog inputs, GPIOs, and a host-facing bus through which the host sees KCS-style registers; on a server board it is wired to the voltage regulators, power supplies, temperature sensors, fans and the host's power and reset lines. D3 D5 F5-30 shows the memory map of one such chip as QEMU models it. When the host's OS writes to port 0xca3, the host's chipset forwards the cycle over that bus to the BMC, where the KCS block raises IBF and interrupts the BMC's firmware; the firmware reads the byte, clears IBF and, when the request is complete, executes it. For Chassis Control "power down", the BMC drives the host's power-control signals; the host loses power while the BMC keeps running. D1 D3 In QEMU, the "BMC" is a C model inside QEMU, and "power down" is QEMU ending the virtual machine: the run ends with QEMU's exit status 0 before Listing 1's "still running" line could print (R2).

Watch out

A BMC can switch off, reconfigure and reinstall the servers it manages, and it runs whether or not the host is up. Treat its network as the most privileged network you have: separate it from production and from the internet, control who can reach it, manage its accounts and firmware updates like those of any critical system, and log every action (the forensic lab shows why). D2 D6

Worked example

Decode the Get Chassis Status exchange from the run without looking at Listing 1's interpretation.

  1. Request bytes 0x00 0x01: the first byte is netfn << 2 | LUN, so netfn = 0x00 >> 2 = 0x00 (Chassis), LUN 0; command 0x01 (Get Chassis Status).
  2. Response bytes 0x04 0x01 0x00 0x61 0x00 0x00 0x00: 0x04 >> 2 = 0x01 = request netfn + 1, so it is the Chassis response; command 0x01 repeated; completion code 0x00, success.
  3. First data byte 0x61 = 0110 0001 in binary. Bit 0 is set: the system power is on. The other set bits (5 and 6) belong to the power-restore policy field and other flags of the specification's table, pending verification; Listing 1 decodes only bit 0. D1
  4. Now the SEL free space: before, bytes 6–7 of the response are 0x00 0x08, little-endian 0x0800 = 2048; after, 0xf0 0x07 = 0x07f0 = 2032. 2048 − 2032 = 16 bytes, one record.

The check script in R3 confirms the second computation mechanically.

Where the analogy breaks


    

  1. Tariq decides for himself; a BMC follows rules and firmware. It acts on thresholds and policies its firmware and configuration define (for example "power the host on when power returns"); it does not judge. Wrong configuration is obeyed faithfully.
    2. 

  2. Anyone who knows the phone number can call Tariq's line. Out-of-band access is a network service with accounts and protocols; who can reach it is decided by network design and access control, not by who knows the number.
    3. 

  3. The written form is not slower to fill in by hand only. Redfish's JSON and TLS cost more bytes and computation per request than IPMI's few bytes; the analogy suggests only convenience, not that cost.

Mini-project


Turn Listing 1 into a small in-band inventory tool: print, as key=value lines, the BMC's identity (Get Device ID), the chassis power state and the number of SEL entries, plus SMBIOS type 1 serial number; refuse any power action unless a serial number given on the command line (in a UEFI load option or a file on the ESP) equals the one in SMBIOS. Rubric: correct decoding with raw bytes kept in a debug mode (1); identity check implemented and tested with a wrong serial (1); every IPMI command used is cited with its specification section in a comment (1); error paths (no type 38, completion codes) tested (1); a short note compares the same tool done over Redfish (1).



Summary


    

  • A BMC is a separate computer on standby power that controls host power, reads sensors, keeps an event log and offers remote access, in band and out of band.
    • 

  • IPMI messages are netfn + command + data; responses carry netfn + 1 and a completion code (0x00 success, 0xC1 invalid command).
    • 

  • KCS carries them through two I/O ports with an IBF/OBF handshake; SMBIOS type 38 tells the host where the interface is.
    • 

  • In the lab, every reply matched the simulated BMC's configuration except the device ID (0x42 configured, 0x20 reported), and Chassis Control switched the VM off.
    • 

  • The SEL stores 16-byte records with the BMC's time stamp; the BMC's clock is evidence and can be wrong.
    • 

  • Redfish: JSON resources over HTTPS, discovered from one root by following links; actions change state; names must be checked in the DMTF schemas.
    • 

  • Before any destructive action, verify the identity the BMC reports.
    •

Answers to Check yourself


    

  1. It runs from standby power, which is present whenever the power cord is connected, and it has its own processor, firmware and network port; it drives the host's power-control signals itself.
    2. 

  2. 0x28 = 0010 1000: netfn = 0x28 >> 2 = 0x0A (Storage request), LUN 0. 0x2C >> 2 = 0x0B, the Storage response.
    3. 

  3. For IBF to clear (the BMC has taken the byte), then it checks the state is still "write" and clears a stale OBF. Writing before IBF clears would overwrite a byte the BMC has not read.
    4. 

  4. "Command not supported by this BMC" (0xC1, invalid command). Wrong: "self test failed", or decoding non-existent data bytes as a result.
    5. 

  5. In band: the host's OS uses a host interface to its own BMC; out of band: another computer reaches the BMC over its network port, independently of the host. Only out of band works when the host is off, hung, crashed or has no OS (for example to power it on or watch it boot).
    6. 

  6. The Get Device ID response's fourth data byte (0x03 → 0x07) and the decoded "firmware 7.0x14"; the first check fails because it expects 3.0x14 (update it to the new configuration).
    7. 

  7. Reading 200 temperatures every minute: out of band (Redfish, or IPMI over LAN), since it must not depend on the hosts' OSes, and in bulk from a management station. Power-cycle: also out of band, but first verify the identity the BMC reports (serial number) against the intended server, and that the server is drained.
    8. 

  8. Paths are not guaranteed: a system might be called "1", a serial number or something else, and there may be several; links from the root are the contract.
    9. 

  9. (b). The time stamp's correctness (a) needs a trusted clock; the sensor number (c) is whatever the writer put in the record; the power state (d) is a different command.
    10. 



Forensic lab answer key


    

  1. BMC 10.20.0.17 at 23:10:01, requested by user "automation" from 10.20.9.5 (the automation host): "ForceOff", then "host power state On -> Off".
    2. 

  2. H1: the automation targeted the wrong BMC. Supported: the script sent ForceOff to 10.20.0.17 for "rack1/r08", and 10.20.0.17's own reports give serial R07-0001; r08's BMC (10.20.0.18) received no power request. H2: r07 failed by itself (a crash, power loss) at the same moment. Against: the BMC log records a requested power-off, not a fault event, and monitoring shows r07 down from 23:10:08, seven seconds after the request.
    3. 

  3. The automation log's own lines: at 23:04 it polled "rack1/r08 via 10.20.0.17" and received serial "R07-0001"; at 23:10:01 the ForceOff reply carried "serial R07-0001" too. A check "reported serial must equal R08-…" before acting would have stopped it.
    4. 

  4. Root cause: the inventory file swaps the BMC addresses of r07 and r08. Immediate fix: power r07 back on through 10.20.0.17, correct the inventory, then perform the r08 maintenance through 10.20.0.18 after verifying its serial.
    5. 

  5. Prevention: verify identity (serial or UUID from the BMC, compared with the asset database) before every destructive action; generate the inventory from the BMCs themselves instead of editing it by hand; dry-run mode that prints the target identity; and an alert when the polled serial does not match the inventory.
    6. 



How the evidence was produced: power_audit.cpp simulates two BMCs and an automation script whose inventory maps rack1/r07 to 10.20.0.18 and rack1/r08 to 10.20.0.17 (swapped); the script logs the serials it receives but never compares them.
