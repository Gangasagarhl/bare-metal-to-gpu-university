Story hook

Analogy

Tariq (F5-29) has become a whole team: Ana reads the thermometers, Bo turns the fans, Chen answers the phone, Dita writes the diary. They work in shifts and never call each other. Instead, every reading, every fan setting and every alarm goes on one notice board in the gatehouse: Ana pins "kitchen 21 °C", Bo reads it and pins "fans 40 %", Chen answers callers only from what is on the board. One morning a new team member reads the instruction sheet, which spells a thermometer's name wrong. Her note never appears on the board. Bo, who has a rule "if a thermometer is missing, assume the worst", runs every fan at full speed. Nothing is broken, yet the cottage roars all day.

OpenBMC is an open-source firmware stack for BMCs: a Linux distribution where many small programs, each with one job, share state through objects on a message bus. That design is why OpenBMC is used and adapted by many server builders, and why its failures look the way they do: one misnamed entry in a configuration file can make a component silently absent and push another one into its safe mode. In this chapter you look at a BMC chip as QEMU models it, run your own program on it, and study the architecture with a small model you can run and break.

What you will be able to do

  • Describe the hardware a BMC firmware runs on, from QEMU's model of an AST2600 board: processor, DRAM, flash controller, UARTs, I2C, ADC, PWM, GPIO.
  • Explain OpenBMC's architecture: a Linux system built from layers, daemons that publish objects on D-Bus, configuration as data, and interfaces (Redfish, IPMI, web) as views of the bus.
  • Write and run a bare-metal program on an emulated BMC SoC in QEMU.
  • Trace a sensor reading from an ADC channel to a fan decision and a web answer through the bus, in a model.
  • Diagnose a "fans at full speed" incident caused by a configuration error, from journal and bus evidence.
Jargon box
OpenBMC
Simple words: free, open firmware for the little management computer in a server. Analogy: the gatehouse team and its rule book. Precise: an open-source Linux distribution for BMCs, hosted by the Linux Foundation, built with the Yocto Project's tools from layers (common code plus per-machine layers), in which management functions are separate services that communicate over D-Bus; it offers Redfish, IPMI and a web interface. D1 D4
BMC SoC
Simple words: the chip that is the BMC: a processor with all the controllers a server's management needs, on one piece of silicon. Analogy: the gatehouse itself, with its desk, phone and switches. Precise: a system-on-chip with one or more Arm cores, a DRAM controller, flash (SPI) controllers, Ethernet MACs, several UARTs, many I2C buses, ADC, PWM and fan-tachometer blocks, GPIOs and a host-facing interface (LPC or eSPI, with KCS registers); the Aspeed AST2600 is one such chip and QEMU models it. D2 R2
D-Bus
Simple words: a message system that lets programs on one computer offer objects, call each other's methods and announce changes. Analogy: the notice board. Precise: an inter-process communication system with a bus daemon, in which services own well-known names and export objects at paths; objects implement named interfaces with methods, properties and signals; clients read properties and subscribe to signals such as "properties changed". D3
Daemon
Simple words: a program that runs in the background and does one job for as long as the computer is on. Analogy: one team member on shift. Precise: a long-running process without a terminal, started and supervised by the init system (systemd in OpenBMC), restarted when it fails according to its unit's settings. D1 D5
Fail-safe fan mode
Simple words: when the fan controller cannot see a temperature it needs, it runs the fans fast to be safe. Analogy: Bo's rule: thermometer missing, assume the worst. Precise: a fan-control policy that, on missing, stale or invalid inputs, sets the fans to a configured safe output (in the model of this chapter, 100 %), trading noise, power and fan wear for thermal safety. D1
Configuration as data
Simple words: the same program works on many boards because a file tells it which sensors and fans exist. Analogy: the instruction sheet that names each thermometer. Precise: board-specific facts (sensor names, buses, addresses, scaling, thresholds, fan zones) kept in data files (OpenBMC uses JSON and YAML files, among others) read by generic daemons at start-up, so that a new board is mostly a new configuration. D1

Terms from earlier chapters: BMC, IPMI, Redfish (F3-42), I2C (HW204), KCS interface (F5-29).

Layer 1 — the kid explanation

The little helper computer inside a server needs a program, like your laptop does. OpenBMC is a free program for it that anyone can read.

Inside OpenBMC, many small helpers each do one job: one reads thermometers, one turns fans, one answers questions. They do not talk to each other. They put what they know on a shared board, and read from the board what they need. If one thermometer is missing from the board, the fan helper plays it safe and turns all fans to full speed.

Layer 2 — the student explanation

The chip

Analogy first: the gatehouse has a desk, a phone, a switchboard and wires to every thermometer. A BMC SoC is that gatehouse in silicon. QEMU 8.2.2 in this build lists 25 BMC machine models, from Aspeed AST1030/2500/2600 evaluation boards to boards named after server products of several companies, with processor cores from ARM926EJ-S to Cortex-A7 (R1). R1 The lab uses ast2600-evb. Its memory map (R2) shows what a BMC needs: DRAM at 0x80000000, a flash controller (aspeed.smc) for the firmware image, an Ethernet MAC for the management network, a system control unit (SCU) for clocks, resets and chip identification, an ADC for voltages and temperatures, GPIOs, a real-time clock, timers, many UARTs (one for the BMC's own console, others for the host's console), the LPC block that faces the host (where the KCS registers of F5-29 live) and I2C buses for sensors and power supplies. R2 D2

The software stack

On a real BMC, the boot path is: the SoC's boot ROM reads the flash; a bootloader (U-Boot in OpenBMC) initialises DRAM and starts the Linux kernel with a device tree that describes the board; the kernel mounts the root file system from flash; the init system (systemd) starts the services. D1 D5 OpenBMC's image is built with the Yocto Project's BitBake from layers: common recipes for all machines, plus a layer per vendor and per machine with the device tree, configuration files and any machine-specific services. D1 D4

Daemons and objects

The central design choice: each management function is a separate service, and services share state as objects on D-Bus rather than by calling each other. D1 A sensor service creates one object per sensor, for example at a path under /xyz/openbmc_project/sensors/temperature/, with a Value property; when the value changes, D-Bus delivers a "properties changed" signal to every service that subscribed. D3 A fan-control service reads the temperatures and writes fan targets; a logging service records events; the Redfish server, the IPMI daemon and the web interface answer requests by reading and writing objects. D1 So Redfish and IPMI are two views of the same objects, which is how one BMC can answer both F5-29 interfaces consistently.

Listings 2 and 3 model this design in about 200 lines of C++: a bus with objects, properties and watchers; four "daemons"; a configuration list. The model has no D-Bus, no processes and no real OpenBMC names beyond an imitation of its path style. Its purpose is the architecture, not the API.

Configuration as data

Because the daemons are generic, the board's facts live in configuration: which ADC channel or I2C address is which sensor, its scale, its thresholds, which fans cool which zone. D1 Adding a board means writing configuration rather than code; the cost is that a configuration mistake is not a compile error. It shows up at run time as a missing object, an error line in the journal, and some other daemon's reaction to the absence. The forensic lab is exactly that chain.

Layer 3 — the engineer's depth

Why a bus and not function calls

A bus decouples the services in three ways. D3 In time: a service can restart without the others noticing more than a short absence of its objects. In knowledge: fan control needs to know the names of the sensors it uses, not which program produced them, so a sensor can move from an ADC to an I2C chip without changing fan control. In number: any number of readers can watch a property, so adding a new interface (a Redfish feature, an SNMP agent) does not touch the producers. The costs are latency per message (a bus round trip instead of a function call), an extra failure mode (the bus daemon itself), and debugging that crosses process boundaries: the cause of a symptom is often in another service's log. D3 D1

Fail-safe as a design rule

Fan control faces a decision whenever an input is absent: keep the last output, use the remaining inputs, or go to the safe output. Running fans slowly with a hidden hot component risks hardware damage and thermal shutdowns (F5-33); running them fast costs power, noise and fan wear but nothing else. A BMC therefore treats "I cannot see sensor X" like "sensor X is very hot". D1 Listing 1's model does that on lines 163–168. The engineering consequence for operators: a server whose fans run at full speed while all visible temperatures are low has not got a thermal problem; it has an observability problem. Look for the missing input.

How the hardware actually does it

When Listing 4 stores a byte to address 0x1e784000, the Cortex-A7 core issues a write on the SoC's internal bus; the address decoder routes it to the UART block, whose transmit register queues the byte for the serial line. D2 In QEMU, the "address decoder" is the memory map of Figure 2: the write lands in QEMU's serial device model, which appends the byte to the file named by -serial file:. R2 R4 On a real board, firmware must first set up clocks, pin multiplexing and the UART's baud rate before characters come out right; QEMU's model does not need that, which is one reason a program that runs in QEMU can be silent on hardware. For sensors, a real BMC's ADC block converts the voltage on a pin to a count; a driver turns the count into millivolts or degrees with board-specific scaling (from the device tree or a configuration file); a daemon publishes the result on D-Bus. The fans are driven by PWM outputs and measured by tachometer inputs on the same SoC. D2 D1

Watch out

Writing BMC firmware to a real server's flash can leave it without working management, and fan-control or power-sequencing mistakes can overheat or damage hardware. Do the work of this chapter in QEMU. On real hardware, use only the vendor's supported update path and keep a recovery path (a second flash image or an external programmer) before experimenting. D1

Worked example

Follow cpu1's temperature through the model at t = 120 s in R3, computing each step yourself.

  1. Board: at t = 60 s the fan target was 37 %. The job starts at t = 120 s, so heat = 120. Target temperature for adc1 = 25 + 120 · (1 − 0.6 · 37/100) + 3 = 25 + 120 · 0.778 + 3 = 121.36 °C. (Listing 2, line 29; made-up physics.)
  2. The channel moves half way from its previous value each minute (line 30). Idle target with the fan at 30 %: 25 + 20 · (1 − 0.18) + 3 = 44.4 °C. From 35 °C: t = 0 s, 39.7 °C (R3 prints cpu1.Value=39.7); t = 60 s, 42.05 °C; t = 120 s, 42.05 + 0.5 · (121.36 − 42.05) = 81.7 °C, the value in R3.
  3. Sensor reader: raw = 817 (×10), published as 81.7 with scale 0.1 (Listing 1, lines 66 and 97).
  4. Threshold monitor: 81.7 ≥ 75 and < 90, level 1: "normal -> WARNING high" (lines 125–132).
  5. Fan control: hottest = 81.7; 30 + (81.7 − 40) · 3.5 = 175.95, clamped to 100 (line 170). Published Target = 100, and the bus monitor prints the change.

The order of lines in R3 at t = 120 s (two warnings, then the fan change) is the order of steps: poll() publishes, watchers react immediately, then step() runs.

Where the analogy breaks


    

  1. Team members read the whole board; daemons subscribe. A D-Bus client receives only the signals it asked for; nothing is "visible" to everyone by default.
    2. 

  2. A notice board has no owner; D-Bus names do. Each object is exported by one service, and only that service changes its properties (others call methods or set writable properties through it).
    3. 

  3. A human notices a misspelled name; a daemon does not. The forensic lab's error line is the only trace; nothing else complains.
