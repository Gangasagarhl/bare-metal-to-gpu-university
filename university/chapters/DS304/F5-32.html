Story hook

Analogy

Hiro owns a big old house in a busy town and turns it into a guesthouse. Each tenant gets a flat with a front door, a kitchen and a letterbox, and inside it feels like a whole house. Hiro keeps the keys, the boiler and the fuse box. Because most tenants are at work all day, he promises more hot-water capacity than the boiler could deliver if everybody showered at once, and it works, most days. One evening a tenant complains that her flat has become slow at everything: the kettle takes ages, but only for tea, not for washing up. She asks the right question: "Am I even in the house I rented, or did you move me to the old annex?"

Most servers in a data centre run virtual machines (VMs). A hypervisor on each physical server (the host) runs many guests, each believing it owns a computer. This chapter is about the operator's view: how guests find out they are virtual, how many VMs fit on a host, what "overcommit" buys and costs, how VMs move between hosts, and what happens when acceleration silently disappears. Your guest program asks the processor "who is my hypervisor?" in three different QEMU configurations, and a forensic lab finds out why a VM became about six times slower at floating point but much less at integers.

What you will be able to do

  • Describe the layers of a data-centre virtualization host: hardware, host kernel with hypervisor, a VM process per guest, virtual devices.
  • Detect a hypervisor from inside a guest with CPUID, and explain when the answer can be hidden or misleading.
  • Place VMs on hosts under vCPU overcommit, memory limits and NUMA locality, and explain why a VM may not fit although enough total capacity is free.
  • Explain live migration, device passthrough and the noisy-neighbour problem at an operator's level.
  • Diagnose a VM that runs without hardware acceleration from its start-up log and timing evidence.
Jargon box
vCPU
Simple words: a processor that a VM sees, which is really a share of a real processor. Analogy: a bed in a flat, which may share a room with others when the guesthouse is full. Precise: a virtual processor of a guest, in KVM-based hypervisors implemented as a thread of the VM's process that the host scheduler runs on a physical CPU (pCPU) and that enters guest mode to execute guest instructions. D1 D2
Overcommit
Simple words: promising VMs more processors or memory in total than the host really has, betting they will not all use it at once. Analogy: renting more beds than rooms. Precise: allocating virtual resources beyond the physical ones, expressed as a ratio (for example vCPUs per pCPU); CPU overcommit costs waiting time (steal time) when guests are busy together; memory overcommit needs reclaiming mechanisms (ballooning, page sharing, swapping) and risks severe slowdowns or failures when guests use what they were promised. D2 D3
TCG (Tiny Code Generator)
Simple words: QEMU's way of running a guest without hardware help: it translates the guest's instructions into the host's instructions in software. Analogy: a tenant whose every instruction is read aloud by an interpreter. Precise: QEMU's dynamic binary translator: guest code is translated block by block into host code and cached; it works on any host and for other architectures, but is slower than hardware-assisted virtualization, by an amount that depends strongly on the kind of instructions (R4, R5). D1 R5
Live migration
Simple words: moving a running VM to another host without switching it off. Analogy: moving a tenant to another guesthouse while she sleeps, so she wakes up in the same-looking flat. Precise: transferring a VM's memory, device state and vCPU state to another host while it runs: commonly pre-copy, which copies memory in rounds while the guest keeps writing, tracks dirtied pages, then pauses the guest briefly to copy the rest and resumes it on the destination. D4 D1
Device passthrough
Simple words: giving a VM a real device (a network card, a GPU) for itself instead of an imitation. Analogy: a flat with its own private entrance and its own boiler. Precise: assigning a physical PCI device or a virtual function of an SR-IOV device to a guest, with the IOMMU translating and confining the device's DMA to the guest's memory; fast and isolated, but it ties the VM to the host's hardware and complicates live migration. D2 D5
Noisy neighbour
Simple words: another VM on the same host that slows yours down by using shared parts heavily. Analogy: the tenant who takes hour-long showers. Precise: interference between co-located guests through resources the hypervisor does not partition fully: CPU time under overcommit, last-level cache, memory bandwidth, the inter-socket link, network and storage queues. D3 D6

Terms from earlier chapters: Hypervisor, Hypervisor-present bit, Hypervisor signature, Steal time, Balloon device (F4-38, DR404); virtio (DR301); IOMMU (HW204); NUMA node (F5-28); Packing and spreading (DS303).

Layer 1 — the kid explanation

A big computer can pretend to be many small computers at once. Each pretend computer is called a virtual machine, and it thinks it is a real one. A special program, the hypervisor, shares out the big computer's parts between them.

A virtual machine can ask the processor: "Am I real?" The processor usually answers honestly and even says the hypervisor's name. In this chapter you ask that question, and you find out what happens when the helper hardware is missing and everything must be done slowly in software.

Layer 2 — the student explanation

Why data centres virtualize

Analogy first: a guesthouse earns more from one building than a single tenant would pay. A data-centre server is big (F5-28: two sockets, many cores, much memory), while many services need a small part of it. Virtual machines let operators consolidate several services on one server, give each its own operating system and isolation, size each to its need, move it between hosts for maintenance, and create or delete it in minutes through software instead of a purchase. D2 D3 Containers (DS303) share one kernel and isolate less; VMs isolate whole operating systems and are often combined with containers (containers inside VMs).

The stack on one host

In a KVM-based host (Figure 1), the Linux kernel's KVM module uses the processor's virtualization extensions to run guest instructions directly on the real CPU in a special guest mode; whenever the guest does something the hypervisor must handle (an I/O access, some privileged instructions), the CPU leaves guest mode (a VM exit, F4-38) and KVM or the VM's user-space process deals with it. D1 D2 The VM process (QEMU, or another virtual machine monitor) provides the virtual devices, usually virtio (DR301) for disks and networks. Each vCPU is a thread; the host scheduler decides which pCPU runs it and when. Without KVM, QEMU can still run the same guest with TCG, translating every instruction in software. D1

How a guest knows

The x86 CPUID instruction answers questions about the processor. In a VM, the hypervisor controls the answers. By convention, bit 31 of ECX for leaf 1 says "a hypervisor is present", and leaf 0x40000000 returns a 12-character vendor signature (F4-38). D7 This build's results (R1–R3):

  • The build container itself: bit 1, signature "KVMKVMKVM". The container is a VM on a KVM-based hypervisor (which user-space monitor runs it was not identified).
  • Our UEFI program under QEMU TCG: bit 1, signature "TCGTCGTCGTCG".
  • The same under TCG with -cpu qemu64,hypervisor=off: bit 0, yet leaf 0x40000000 still returns "TCGTCGTCGTCG". A guest that trusts bit 31 sees bare metal; the signature is still there for anyone who asks. Software must check the bit first (Listing 2 does) and should treat both as hints, not proof.
  • KVM in QEMU: not possible here, "Could not access KVM kernel module: No such file or directory" (R3). The V1 milestone's QEMU/KVM case is therefore untested in this build, as are Hyper-V and bare metal.

Sizing and overcommit

Operators decide how many vCPUs and how much memory to promise per host. CPU overcommit is common because most VMs are idle most of the time; when several become busy together, their vCPUs wait for pCPUs, which the guest sees as steal time (DR404). Memory overcommit is riskier: memory a guest has touched cannot be shared out again without the guest's help (ballooning) or the host's tricks (merging identical pages, swapping), and running out is far more disruptive than waiting for a CPU. D2 D3 Add NUMA (F5-28): a VM whose vCPUs and memory sit on one node gets local latency; one spread over two nodes pays the remote factor on some of its accesses. The worked example combines all three rules.

Live migration and maintenance

To repair or update a host without stopping its guests, operators live-migrate them away. Pre-copy migration sends all guest memory while the guest runs, then resends pages the guest wrote meanwhile, round after round, until the remainder is small enough to send during a short pause. D4 A guest that writes memory faster than the network can send it never converges; migration then needs a longer pause, throttling of the guest, or another method. Passed-through devices (Figure 1, VM 3) hold state the hypervisor cannot copy, which is why such VMs are harder to migrate. D4 D5

Layer 3 — the engineer's depth

Where the cost of virtualization goes

With hardware assistance, ordinary computation in guest mode runs on the real CPU. The costs are concentrated: VM exits for I/O and certain instructions, address translation through two levels of page tables (guest and host, nested paging) on TLB misses, interrupts delivered through the hypervisor, and device emulation in the VM process. D1 D2 virtio reduces exits with shared-memory queues; passthrough removes the VM process from the data path. Without hardware assistance (TCG), every instruction is translated, and the cost depends on how well the host can express the guest instruction. The forensic lab measures this: on this build's machine, the same 200 million integer multiply-add steps took 0.29 s natively and about 0.53 s under TCG (about 1.8×), but the same 50 million double-precision steps took 0.13 s natively and about 0.80 s under TCG (about 6.4×) in the final run (R4, R5). TCG has to reproduce the guest's floating-point behaviour exactly; for integers it can map guest instructions to host ones more directly. Why the floating-point gap is this large in QEMU 8.2.2 was not investigated here (QEMU's source would tell). The lesson is in the shape: a VM without acceleration is not uniformly slower, so "everything is a bit slower" is not the symptom to look for. R4 R5

Note

These times were measured in a shared cloud container that is itself a virtual machine; the host loop timed with std::chrono, the guest loops from host-side time stamps on console lines, which include console output. They differ between runs: an earlier run during authoring gave 0.25 s and 0.09 s on the host and 0.31 s and 0.54 s in the guest (ratios about 1.2× and 5.7×). The integer ratio moved between 1.2× and 1.8×, the floating-point ratio stayed between 5.7× and 6.4×. Use the ratio between kinds of work, not the absolute numbers.

Placement is bin packing with extra rules

Placing VMs on hosts is a multi-dimensional bin-packing problem: each VM needs vCPUs and memory, each host node offers them, and rules add constraints (fit in one NUMA node, keep replicas on different hosts, keep some hosts empty for maintenance). D3 Exact solutions are expensive, so placers use heuristics; Listing 3 uses first-fit decreasing by memory, which places the largest memory requests first because memory is the resource that cannot be overcommitted here. Its result (Figure 2) shows fragmentation: 96 GiB and 24 vCPUs are free on hostB in total, but batch2 needs 24 vCPUs and 64 GiB on one node, and no node has both. Options are a different policy (spread instead of pack; DS303's two policies), relaxing the NUMA rule for that VM and accepting remote memory, a higher overcommit ratio, or another host. Each is a trade-off an operator decides explicitly. D3 R6

Isolation is not complete

The hypervisor partitions CPU time and memory capacity, but VMs on one host still share caches, memory bandwidth, the inter-socket link, the network card's queues and storage. A VM can be slowed by its neighbours without any change in its own configuration; its signs are steal time, lower instructions per cycle, and latency that varies with time of day. D3 D6 Mitigations: dedicated (pinned) pCPUs for latency-sensitive VMs, NUMA-aware placement, cache and bandwidth partitioning features where the processor has them, and placement rules that keep heavy VMs apart. Shared hardware is also a security boundary: side channels between VMs are a reason to separate tenants by host. D6

How the hardware actually does it

Intel VT-x and AMD-V add a guest mode to the processor: the hypervisor prepares a control structure per vCPU (VMCS or VMCB, DR404) that says which events cause exits, then executes an instruction that enters the guest; the CPU runs guest code at full speed until an event listed in the structure happens, saves the guest state and returns to the hypervisor. D7 D1 CPUID is one of the instructions that always exits under VT-x, which is how the hypervisor gets to answer it, and why it can set bit 31 and return a signature. Second-level address translation (EPT on Intel, NPT on AMD) lets the hardware walk the guest's page tables and the host's in one TLB fill. The IOMMU translates device DMA addresses so that a passed-through device can write only the guest's memory. D5 None of this was observable in the container (no /dev/kvm); the container's own CPUID answer shows that a KVM hypervisor below it intercepts CPUID. Untested on hardware.

Watch out

Guests on one host trust the hypervisor and the host completely: whoever controls the host can read every guest's memory. Keep the host management network as protected as the BMC network (F5-29), keep hypervisor and firmware updated, and place tenants that must not share hardware on different hosts. D6

Worked example

Place the eight VMs of consolidate.in by hand, then compare with Listing 3. Two hosts, each with two NUMA nodes of 16 pCPUs and 128 GiB; vCPU ratio 2.0 (32 vCPUs per node); memory not overcommitted; a VM must fit in one node. Sort by memory, largest first (ties keep file order): cache1 112, db1 96, db2 96, batch1 64, batch2 64, web1 16, web2 16, web3 16.

  1. cache1 (8, 112) → hostA node 0 (first node that fits). Node 0: 8 vCPU, 112 GiB.
  2. db1 (16, 96): hostA node 0 has 16 GiB left, no. hostA node 1: yes. Node 1: 16, 96.
  3. db2 (16, 96): hostA full for 96 GiB on both nodes; hostB node 0.
  4. batch1 (24, 64): hostA nodes have 16 and 32 GiB free, no; hostB node 0 has 32 GiB free, no; hostB node 1: yes (24 ≤ 32 vCPUs).
  5. batch2 (24, 64): memory fits only on hostB node 1 (64 free), but 24 + 24 = 48 > 32 vCPUs. hostB node 0 has 32 GiB: no. Not placed.
  6. web1, web2, web3 (4, 16 each): web1 → hostA node 0 (12 vCPU, 128 GiB: full); web2 and web3 → hostA node 1 (24 vCPU, 128 GiB).

This matches R6, including the exit status 3 that signals an unplaced VM to a calling script. Notice that the three small VMs filled the first host because first-fit looks at hosts in order: a "pack" policy. Try the check question on what changes if batch2 is allowed to span both nodes of hostB.

Where the analogy breaks


    

  1. A tenant can look out of the window; a guest sees only what the hypervisor shows. CPUID, devices and even time are the hypervisor's answers, and can be hidden or changed (R2).
    2. 

  2. Moving a sleeping tenant takes one trip; live migration copies memory repeatedly while the guest keeps changing it, and may not converge.
    3. 

  3. Hot water is one shared resource; a host has many (CPU time, caches, memory bandwidth, network queues), and they run out at different times.

Summary


    

  • A data-centre host runs many VMs: hypervisor in the host kernel (KVM), one VM process per guest, vCPUs as threads, virtio devices, optional passthrough through the IOMMU.

  • Guests detect a hypervisor with CPUID: the bit, then the signature. In this build: container "KVMKVMKVM"; QEMU guest "TCGTCGTCGTCG"; hypervisor=off hides the bit but not the signature.

  • Placement is bin packing with rules; free capacity in total does not mean room for one VM (Figure 2).
