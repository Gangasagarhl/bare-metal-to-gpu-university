Story hook

Before the fair, Lina practises. Not with real glasses in the crowded hall, but in an empty hallway with plastic cups full of water, while her friend Mateus plays the crowd: he moves chairs into her way and calls out "someone bumps your elbow, now!". If a cup falls, nothing breaks, and they try again.

The rehearsal is only useful if it is honest. Mateus learns one trick early: he says "step", waits until Lina has actually taken her step, and only then moves the next chair. If he rushed ahead while she was still thinking, chairs would appear in places she could never have reacted to, and they would both learn the wrong lesson. On another day, a new friend replaces Mateus and calls out the times in minutes while Lina expects seconds. Lina stumbles all over the hallway, and for a while everybody blames her balance.

In this chapter you meet the flight stack's rehearsal: software in the loop, where the real PX4 code runs on your computer and a simulator plays the world. You will see how PX4 is built for a board and for simulation, build your own two-process SITL in which a simulator and an autopilot step together in lockstep, and then investigate the day the new friend called out the wrong units.

What you will be able to do

  • Describe how PX4 is built: the build target that names a board and a configuration, what the build produces for a flight controller and for simulation, and how firmware reaches a board.
  • Explain SITL: which parts are real code, which are simulated, how they exchange sensor and actuator data, and what lockstep guarantees.
  • Build and run a two-process lockstep simulation and show that its result does not depend on how the operating system schedules the processes.
  • Compute the real-time factor of a simulation and predict what changes when lockstep is off.
  • Diagnose a simulation that "flies badly" because of a timestamp unit error at the simulator interface.
Jargon box
SITL (software in the loop)
Simple words: the real flight software runs on a normal computer and a simulator plays the drone and the world. Analogy: rehearsing the walk in the hallway with plastic cups. Precise: a test configuration in which the flight stack is compiled for the host operating system and exchanges sensor data and actuator commands with a physics simulator instead of hardware drivers; PX4 supports SITL with several simulators. D1
HITL (hardware in the loop)
Simple words: the real flight controller runs the real firmware, but its sensors are replaced by a simulator. Analogy: the real tray, in the hallway, with a friend shouting the bumps. Precise: a configuration in which the firmware runs on the flight-controller hardware and receives simulated sensor data (and sends actuator outputs) over a link to a simulator on a computer; it tests the firmware on its real processor and operating system without flying (F10-34). D1
Lockstep
Simple words: simulator and flight software take turns: the simulator waits for the answer before it moves time forward. Analogy: the coach says "step" and waits until you have stepped. Precise: a coupling in which simulated time advances only after the flight stack has processed the current sensor data and returned its actuator outputs, so that the result is independent of how fast either runs in wall-clock time. D1 R1
Real-time factor
Simple words: how many seconds of simulated time pass per second on the clock on the wall. Analogy: rehearsing in slow motion (below 1) or fast forward (above 1). Precise: simulated time elapsed divided by wall-clock time elapsed; with lockstep it can be any value without changing the result; without lockstep, a value below 1 means the simulation cannot keep up. D4
Build target (PX4)
Simple words: the name you give the build to say which board and which set of modules you want. Analogy: choosing which tray and which drinks before you start. Precise: a name passed to PX4's top-level build (a Makefile front end that drives CMake) that selects a vendor, a board and a configuration label; a SITL target selects the host platform instead of a board. D1 D2
Simulator interface (bridge)
Simple words: the piece of code that translates between the simulator's world and the flight stack's sensor and motor messages. Analogy: the friend who calls out the bumps: if he uses the wrong units, everything goes wrong. Precise: the module or plugin that converts simulator state into the flight stack's sensor topics (with timestamps) and actuator topics into simulator inputs, over a defined protocol; it replaces the hardware drivers in SITL. D1
Firmware image
Simple words: the single file that is written into the flight controller's memory. Analogy: the packed tray, ready to carry. Precise: the linked binary of PX4 and NuttX for one board, packaged with metadata, which a bootloader on the board writes into flash. D1

Related terms: simulated clock (sim time), real-time factor and physics step from RB303 (F9-44); deterministic simulation; the build ideas of SP202.

The idea in pictures

Layer 1 — the kid explanation

Testing a drone by flying it is slow and risky. So engineers first run the real flight program on a normal computer, and a second program pretends to be the drone, the air and the ground. The flight program gets pretend sensor readings, decides how fast each motor should spin, and the pretend world moves the pretend drone. That is software in the loop.

To make the rehearsal fair, the two programs take turns. The world says: "here is what your sensors feel at this instant". The flight program answers: "spin the motors like this". Only then does the world move on by a tiny step. Then it does not matter whether the computer is fast or slow: every run gives exactly the same flight.

The rehearsal also catches mistakes in how the two talk. If the world says "4" meaning milliseconds and the flight program hears microseconds, the flight program thinks time is passing a thousand times too slowly, and it flies very badly. In the lab you will find out how such a mistake looks from the inside.

Layer 2 — the student explanation

How PX4 is built

PX4 is built with CMake, driven by a top-level make front end. You name a build target that encodes the vendor, the board and a configuration label; the board's configuration selects which modules and drivers are compiled in, and for a NuttX board also the NuttX configuration. The result for a board is a firmware image for that board; the result for a SITL target is an executable for your computer's operating system. The build needs a host toolchain, a cross-compiler for the board's processor (for board targets), Python with some packages (for code generation, for example of the uORB message structs from their definition files), and the simulator you choose for SITL. D1 D2 PX4 publishes setup scripts and container images for the build environment; using them is the easiest way to get a toolchain that matches the release you build. The exact target names, scripts and versions change between releases; they are listed in the unverified box of Layer 3 and must be taken from the guide for your release.

Building is the first real-tool step of this course, and the build container used to write it had neither PX4 nor network access, so every PX4 command in this chapter is untested here. What the chapter can show with real runs is the mechanism SITL relies on, with a program small enough to read completely.

What runs in SITL

In SITL the PX4 executable contains the same estimator, controllers, commander, navigator, logger and MAVLink modules as the firmware; what changes is underneath (Linux or macOS instead of NuttX, F10-20) and at the edges: instead of sensor drivers, a simulator interface publishes the sensor topics from the simulator's data, and the actuator outputs go back to the simulator instead of to ESCs. A ground-station program can connect over MAVLink exactly as to a real vehicle. D1 This is why SITL is the first place to test a new module (F10-24), a parameter change, or a mission: if it is wrong in SITL, it is wrong on the vehicle. The converse does not hold (bridge BR-08): the simulator's sensors are cleaner, its timing is ideal, and its physics is a model.

A SITL you can read: Listing 1

Listing 1 builds a complete SITL in about 150 lines. runSitl creates a connected pair of local sockets and forks into two processes. The simulator process owns the physics of a vehicle that can only move up and down (mass, gravity, a thrust limit, the ground) and the clock. The autopilot process owns a small estimator (altitude from a noisy barometer, vertical speed from the difference of successive altitudes, both low-pass filtered) and a cascaded controller (altitude error → velocity setpoint → thrust with a hover feed-forward and an integrator, as in F10-16). Every 4 ms of simulated time the simulator sends a SensorMsg stamped with the simulated time and waits for the ActuatorMsg; only then does it integrate the physics for 4 ms (Figure 2). The setpoint is 0 m for the first second and 2 m after that. R1



The vehicle takes off at 1 s, climbs at about 1 m/s (the velocity setpoint is limited to ±1 m/s), approaches 2 m without a large overshoot and holds there; the thrust settles around the hover value 1.5 × 9.81 / 30 ≈ 0.49 (between 0.48 and 0.55 in the printed lines). The vertical-speed estimate wobbles by a few tenths of a metre per second at hover: that is the barometer's ±1 cm noise, differentiated over 4 ms and filtered. Both processes report 2,500 steps. R1


The lab's run.sh ran the same program three times and compared the outputs byte for byte: R2




Two processes, scheduled by Linux as it pleases, and identical results to the last digit, because neither process ever uses wall-clock time and the simulator never advances without the autopilot's answer. That is what lockstep buys you: a failing SITL test fails every time, and a fix can be verified by a single run.



Layer 3 — the engineer's depth


Whose clock?


In lockstep SITL there is exactly one clock: the simulator's. The flight stack must take all time from the timestamps it receives, never from the operating system's wall clock, or the two diverge as soon as the real-time factor is not 1. PX4 provides a time interface that, in lockstep SITL, is driven by the simulator's time (unverified box); code that reads the host clock directly breaks this. In Listing 1 the autopilot computes dt from the difference of two message timestamps (line 94), exactly the habit a flight-stack module needs. D1 R1



Real-time factor and what happens without lockstep


The real-time factor is simulated time per wall-clock time. With lockstep, it is simply as fast as the slower side allows, and it does not affect the result. Without lockstep, the simulator runs on its own timer and the flight stack runs on its own threads; if either cannot keep up, sensor messages arrive late or are skipped, control outputs arrive one or more steps late, and the closed loop sees a delay that the real vehicle may not have (or may have differently). The results then depend on the machine's load: a test that passes on a fast workstation fails on a busy CI server. The Worked example puts numbers on it. D1 D4



The protocol is an interface: units, frames, timestamps


Between simulator and flight stack, every field has a unit, a coordinate frame and a time base. Listing 1's SensorMsg says in comments: time in microseconds, altitude in metres, specific force in metres per second squared along "up". A real simulator interface carries IMU, magnetometer, barometer, GNSS and airspeed data, each with frame conventions (for example north-east-down versus east-north-up) that the interface converts. An error in any of them produces a vehicle that flies "badly" in a way that looks like a tuning problem. The forensic lab is the time-unit version of that failure; frame errors are the subject of the mini-project. D1 D3



What SITL tests, and what it does not


SITL exercises logic: modes, missions, failsafes (F10-35), parameter handling, estimator and controller behaviour against a model, and your own modules. It does not exercise the flight controller's timing (a PC is faster and runs a different scheduler), memory limits, drivers and buses, vibration, electromagnetic interference, or the gap between the simulator's physics and the real airframe. HITL moves the firmware onto the real processor and operating system; bench tests with propellers removed exercise drivers and outputs; only then does a supervised flight test follow (DN401). D1

How the hardware actually does it


In SITL there is no flight-controller hardware: the "sensors" are numbers computed by the simulator from its model state, and the "motors" are inputs to its physics. The real hardware path that SITL replaces is: sensor chips sampled over SPI or I2C by drivers at rates set by their configuration, timestamps taken from the flight controller's high-resolution timer at the moment of the sample, and outputs generated by timer peripherals as PWM pulses or digital ESC protocols (F10-10). Each of these has delays and noise the simulator leaves out or models only roughly. D1 On the build side, cross-compiling for a board means generating machine code for the board's processor architecture (for most current flight controllers an Arm Cortex-M core, as in F3-36) and linking it to the addresses of that chip's flash and RAM; flashing writes the image through a bootloader that already lives on the chip. Which core, how much flash and RAM, and which bootloader protocol a named board uses come from that board's documentation (AH-21). D1



Worked example


Task. A SITL setup has a 4 ms simulation step. Per step, the simulator needs 3 ms of wall-clock time and the flight stack 1 ms (measured, on some machine). (a) What is the real-time factor with lockstep? (b) Without lockstep, the simulator runs a timer at 4 ms of wall-clock time per step and the flight stack runs at its own rate; what happens when another job on the machine makes the simulator need 6 ms per step? (c) What does the Listing 1 autopilot compute for dt if the timestamps are sent in milliseconds instead of microseconds?


    

  1. (a) In lockstep, each step costs 3 + 1 = 4 ms of wall-clock time (the two sides take turns). Real-time factor = 4 ms simulated / 4 ms wall = 1.0. If both were twice as fast, it would be 2.0, with an identical result.
    2. 

  2. (b) The simulator falls behind: it can deliver only one step per 6 ms of wall time, so simulated time runs at 4/6 ≈ 0.67 of wall time. The flight stack, if it runs on wall time, now sees new sensor data only every 6 ms of its own time, believes time has advanced 6 ms while the simulation advanced 4 ms, and its outputs are applied late. The result depends on the load of the machine.
    3. 

  3. (c) Successive timestamps 4, 8, 12… are read as microseconds: dt = 4 × 10−6 s instead of 4 × 10−3 s, 1,000 times too small. The velocity estimate (Δaltitude / dt) becomes 1,000 times too large: a 1 cm noise step reads as 0.01 / 0.000004 = 2,500 m/s raw, about 250 m/s after the first filter step. The controller saturates its thrust at 0 or 1 on every swing of the noise. The forensic lab's evidence shows exactly that pattern (estimates of hundreds of metres per second, thrust 0.000 or 1.000, altitude stuck near the ground).
    4.

Where the analogy breaks


    

  • Plastic cups are lighter than glasses; a simulator's vehicle is whatever its model says. The rehearsal hides problems the model leaves out (vibration, delays, battery sag, wind), and can even create problems the real vehicle does not have. SITL success is necessary, not sufficient (BR-08).
    • 

  • Lina and Mateus share one sense of time; in SITL the flight stack has only the time it is told. If the messages carry the wrong time, the flight stack has no other clock to notice it by. R3
    • 

  • A rehearsal is never exactly the same twice; a lockstep SITL with fixed seeds is. That is a strength for debugging, and a weakness if you forget to vary noise and conditions in tests.
    • 




Common mistakes and debugging


    

  • Symptom: the vehicle in SITL oscillates or saturates although the same parameters work for others. Cause: a unit or frame error at the simulator interface. Find: print the first few sensor messages and the dt the stack computes; compare with the simulator's step. Fix: correct the interface, and add a startup check that rejects implausible dt.
    • 

  • Symptom: SITL results differ between runs or machines. Cause: lockstep off, or a module that reads the wall clock. Find: run three times and compare (as run.sh does). Fix: lockstep on; all time from the flight stack's time interface.
    • 

  • Symptom: the build fails with missing Python modules or a wrong compiler version. Cause: a hand-made environment that does not match the release. Fix: use the release's setup script or container image; record the versions in your lab notes.
    • 

  • Symptom: a module you added does not appear in SITL. Cause: it is not enabled in the SITL target's board configuration, or not started by the start-up script. Fix: see F10-24.
    • 

  • Symptom: SITL runs far slower than real time and the ground station shows a choppy vehicle. Cause: the simulator's rendering or physics is too heavy for the machine. Fix: with lockstep, results are still valid; run headless for automated tests.
    •

Summary


    

  • PX4 is built with CMake through a make front end; a build target names the board and configuration, or a SITL host target.
    • 

  • Board targets produce one firmware image (PX4 + NuttX) written by the board's bootloader; SITL targets produce a host executable.
    • 

  • In SITL the flight-stack modules are the same; a simulator interface replaces drivers and outputs.
    • 

  • Lockstep advances simulated time only after the flight stack has answered; results become independent of machine speed (three runs identical in this build).
    • 

  • All time in SITL comes from the simulator's timestamps; a unit error (ms read as µs) made dt 1,000 times too small and the velocity estimate absurd.
    • 

  • SITL tests logic against a model; timing, drivers, vibration and real physics need HITL, bench tests and supervised flights.
    • 

  • Every PX4 command in this chapter is untested in this build and listed in unverified boxes.

Forensic lab answer key


Observation. The dt column reads 0.000004 s from the second sample on (0.004000 in the reference). vz_est_mps shows values of tens to hundreds of metres per second with changing sign; thrust jumps between 0.000 and 1.000; alt_est_m stays at a few centimetres. The first line is identical in both logs (the first dt is a default).


Hypotheses. (a) Gains: unchanged and correct in the reference; gains cannot change dt. (b) Noise: the altitude column's scatter is similar to the reference at the start; noise cannot change dt. (c) Time base: confirmed by dt = 4 µs.


Root cause. The new bridge sends the timestamp in milliseconds in a field defined as microseconds: successive values 4, 8, 12… give dt = 4 µs, 1,000 times too small. Δaltitude / dt is 1,000 times too large, so centimetre noise becomes hundreds of metres per second of "velocity"; the velocity loop saturates the thrust at 0 or 1 on every swing; the vehicle bounces on the ground.


Why the teammate's check missed it. Altitude and acceleration values do not depend on the time base; only quantities computed from time differences do. Checking values without checking their timestamps misses the error.


Fix and prevention. Send microseconds (multiply by 1,000, or send the step counter times the step in µs). Checks: a startup check on the first timestamp differences (Check yourself 9); a CI test that flies a short SITL takeoff and asserts altitude reached, plus an assertion that the stack's measured loop rate equals the configured rate.


How the evidence was made. forensic_sitl.cpp calls runSitl(true); in sitl_core.h line 50 the simulator then sends tUs / 1000 in the microsecond field. Everything else is identical.
