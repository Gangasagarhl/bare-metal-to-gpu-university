Story hook

Lina is carrying a tray of six full glasses across a crowded school hall. Three things are happening in her body at once. Something deep inside keeps the tray level: every small tilt is felt and corrected, again and again, many times a second. A slower part of her decides the route: left around the table, wait for the door. And a third part chats with her friend Tomás, who is walking beside her. If Tomás asks a hard question at the moment the tray tips, the balance wins. Lina does not decide this; it is the rule her body follows. The chat waits, the route waits, the tray is saved.

A flight controller has the same three kinds of work: a fast loop that keeps the vehicle level, slower loops that decide where to go, and talk with the ground. On most flight controllers that run PX4, the rule that decides "which job gets the processor now" belongs to an operating system called NuttX. In this chapter you look at NuttX the way an engineer looks at a component they depend on: what it promises, how its tasks and priorities work, what it shares with Linux and what it does not, and where its promises end. Then you write a periodic task using only the standard calls NuttX is built around, and you study what happens when two tasks share one memory with no walls between them.

What you will be able to do

  • Explain what NuttX is as a real-time operating system: tasks and threads, fixed priorities, preemption, and its design goal of following the POSIX standard.
  • Write a periodic task with an absolute release time and pass its samples to another task through a message queue, using only POSIX calls, and measure its lateness.
  • Compare a flat build (one address space) with a build that protects memory, and predict what a buffer overflow does in each.
  • Place PX4 on top of NuttX: which parts of PX4 rely on which operating-system services, and why the same PX4 code also runs on Linux for simulation.
  • Diagnose a corrupted variable in a flat build from a link map, a memory dump and a timeline.
Jargon box
NuttX
Simple words: a small operating system for microcontrollers that tries to look like Unix to the programs on it. Analogy: the rule in Lina's body that decides which job gets her attention first. Precise: an open-source real-time operating system of the Apache Software Foundation that emphasises compliance with standards (POSIX and ANSI C) and a small footprint, and scales across microcontroller families; it is the operating system PX4 uses on most flight-controller boards. D2 D1
POSIX
Simple words: a standard list of operating-system calls (threads, files, clocks, queues) that many systems agree on. Analogy: a common sign language every helper in the building understands. Precise: the IEEE Std 1003.1 family, published by The Open Group as the Base Specifications: interfaces such as pthread_create, clock_nanosleep, mq_open and sem_post, with their required behaviour. D3
Task (NuttX) and thread (pthread)
Simple words: two names for a job the scheduler runs; a task is started on its own, a thread belongs to a task. Analogy: a helper with their own job card, and a second pair of hands working for the same helper. Precise: in NuttX a task is a schedulable entity with its own stack and its own resources (such as open files), created by NuttX's task-creation interface; a pthread is created by a task with pthread_create and shares its parent task's resources; both are scheduled by the same priority-based scheduler. The exact API names and resource-sharing rules are in the unverified box of Layer 3. D2
SCHED_FIFO
Simple words: the rule "the most urgent job runs, and keeps running until it waits or someone more urgent arrives". Analogy: the balance reflex: nothing interrupts it except something even more urgent. Precise: the POSIX first-in-first-out real-time scheduling policy: fixed priorities, preemption by higher priorities, and no time slicing among equal priorities. D3
Absolute release time
Simple words: "wake me at 10:00:04", not "wake me in 4 seconds". Analogy: stepping on the beat of music, not counting four steps after you last finished one. Precise: sleeping until a point on a clock (clock_nanosleep with TIMER_ABSTIME), so that the next release is the previous release plus the period, independent of how late the task woke or how long it worked. D3 R1
Lateness (release jitter)
Simple words: how much later than planned a periodic task actually starts. Analogy: how far off the beat Lina's step lands. Precise: the time from a job's planned release to the moment the task observes it is running; its worst value bounds the start of every job and adds to the response time. D4
Message queue (POSIX)
Simple words: a mailbox of fixed-size messages between tasks. Analogy: a small tray where one helper puts notes and another takes them, in order. Precise: a kernel object opened by name with mq_open, holding up to mq_maxmsg messages of at most mq_msgsize bytes; mq_send blocks when it is full and mq_receive blocks when it is empty (unless non-blocking mode is set). D3
Flat build and protected build
Simple words: in a flat build every task can write anywhere in memory; in a protected build the hardware stops writes outside allowed areas. Analogy: everyone carrying drinks on one shared tray, versus each helper with their own tray. Precise: NuttX build configurations that differ in memory protection: the flat build links the kernel and all applications into one address space with no protection; the protected build uses the microcontroller's memory protection unit (MPU) to separate kernel and user parts; a kernel build uses an MMU and separate address spaces. Build-mode names and requirements are in the unverified box. D2
NSH
Simple words: the text command line of NuttX. Analogy: a walkie-talkie into Lina's head: you can ask what each part of her is doing. Precise: the NuttShell, NuttX's shell application, which runs commands typed on a console and from start-up scripts; PX4 uses it as the console on its flight controllers. D2 D1

Related terms from earlier courses: RTOS, task (RTOS thread), fixed-priority preemptive scheduling, priority inversion and priority inheritance (OS305); POSIX; jitter (RB304). "Kernel" in this chapter means the operating-system kernel, not a GPU kernel (F6-01).

The idea in pictures

Layer 1 — the kid explanation

A flight controller has one small processor and many jobs. NuttX is the part that shares that processor fairly, but not equally: the most urgent job that is ready always runs first. Keeping level is more urgent than talking to the ground, so it always wins, the way Lina's balance always wins over her chat.

NuttX also tries hard to speak the same "language" as Linux and other Unix systems. A program asks it for a timer, a mailbox or a second thread with the same words it would use on a laptop. That is why the people who wrote PX4 can run the same code on a laptop to test it, and then on the flight controller to fly.

One thing is different from a laptop: on most small flight controllers, all the jobs share one memory with no walls. If one job writes too far, it can spoil another job's numbers, and nobody stops it. You will see exactly that happen in this chapter's lab.

Layer 2 — the student explanation

What NuttX promises

The NuttX documentation describes NuttX as a real-time operating system with an emphasis on standards compliance and small footprint, scalable from small to larger microcontrollers. Two promises matter most for a flight stack. First, scheduling is priority based and preemptive: the highest-priority ready task runs, and a task that becomes ready with a higher priority than the running one takes the processor at once. Second, the programming interface follows POSIX: threads, mutexes, semaphores, message queues, clocks and timers, files and file descriptors, with names and behaviour from the standard wherever NuttX implements them. D2 D3

You met fixed-priority preemptive scheduling in F3-39, where you built a kernel that did exactly that on an emulated Cortex-M3, and its blocking objects and priority inversion in F3-40. NuttX does the same job, with many more services and years of use. The rules you learned carry over unchanged: a task that never blocks starves every task below it; priorities follow urgency of deadlines, not amount of work; shared data needs a lock, and a lock shared across priorities needs priority inheritance or a design that avoids it. D4

Tasks, threads and their stacks

NuttX has two kinds of schedulable entity. A task is started on its own and owns resources such as its open files; a pthread is created by a task and shares that task's resources. Both have their own stack and their own priority, and the scheduler treats them alike. Every task and thread needs a stack whose size is chosen when it is created; there is no virtual memory to grow it on demand, so the size must cover the deepest call chain plus any interrupt frames that land on it. D2 PX4 starts its long-running modules as tasks with explicit priorities and stack sizes, and runs many smaller pieces of work inside a few shared threads called work queues (F10-21). D1

Watch out
"Compiles on Linux" does not mean "behaves the same on NuttX". The standard allows options (for example, which clocks exist, the range of priorities, whether a call is supported at all), and an RTOS may implement a subset. One address space


Linux gives each process its own virtual address space: a wild write in one process crashes that process and nothing else. On the microcontrollers of most flight controllers, NuttX is commonly built "flat": the kernel and every application are linked into one image and share one address space without protection. A bug in any task can overwrite any other task's data, the kernel's data, or a driver's buffer. NuttX also offers a protected build that uses the MPU to separate the kernel from user code, and a kernel build for processors with an MMU. D2 Listing 2 models the difference in a few lines: a logger copies a message into its 32-byte buffer without checking the length, and the rate controller's gains sit right behind the buffer, where a linker could well have put them. R2




In the flat model the 41-byte message spills 9 bytes into the gains: kp becomes a huge number, and the dump shows the bytes are the letters "emaining" of the logger's text. The rate controller would now command enormous corrections. In the protected model the first write outside the logger's region is refused, the logger is stopped, and the gains keep their values. Neither outcome is "good": in the protected build the logger stops logging. But the failure stays where the bug is, and it is reported. R2



Layer 3 — the engineer's depth


Scheduling policies, priorities and what "real-time" means here


POSIX defines SCHED_FIFO and SCHED_RR as fixed-priority policies: both preempt on priority; FIFO never time-slices among equal priorities, round-robin rotates them after a quantum. A conforming system reports its priority range through sched_get_priority_min and sched_get_priority_max; the standard guarantees a minimum span, not particular numbers. D3 The run above printed 1 and 99 for Linux in this container. NuttX has its own range; never copy priority numbers from one system to another, always compute them relative to the range the target reports, which is what a portable layer such as PX4's does. R1 D1


"Real-time" is a property of the whole system, not of the operating system alone. NuttX's scheduler gives a bounded, analysable rule. The response time of the rate loop still depends on the interrupt handlers that run above it, on the time interrupts are disabled inside drivers and the kernel, on locks shared with lower-priority tasks, and on the work the loop itself does. The analysis method is the one of F3-39 and RB304: list the tasks with their periods and worst-case execution times, add the blocking terms, compute response times, then measure on the target and compare. D4



Absolute releases and the cost of being late


Listing 1, lines 57–63, keeps a timespec called release, adds one period to it before each sleep, and sleeps until that absolute time. A wake-up that comes late does not move later releases: the next one is still exactly one period after the previous planned release. A loop that instead sleeps "4 ms from now" after its work accumulates the work time and every lateness into its period and drifts (the Worked example computes how much). The while (... == EINTR) loop around the sleep repeats it if a signal interrupts it; POSIX allows clock_nanosleep to return early with EINTR. D3


Lateness is measured right after the wake-up (lines 64–72). It includes the time the kernel needed to notice the timer expiry, the time to switch to the task, and any time other runnable work of higher or equal priority delayed it. On a microcontroller under NuttX, the same measurement with a hardware timer or a GPIO pin and a logic analyser gives the number you need for analysis; in this container it measures the cloud machine.



Message queues versus shared data


The queue in Listing 1 copies each 16-byte sample into kernel-owned storage and out again. That costs two copies and a system call per message, but it decouples the tasks: the consumer can be slow for up to eight messages (mq_maxmsg on line 129) before the producer blocks. Blocking a 250 Hz sensor task because a consumer is slow is usually the wrong failure; a flight stack prefers "the reader may miss old data, the writer never waits". That is the design of PX4's uORB, which keeps the newest message(s) per topic and lets each reader see what it missed (F10-22). D1 D3



Build modes and what protection costs


A flat build has no address translation and no protection checks: every access is a plain access, every system call is a function call, and task switches do not reconfigure memory hardware. That is cheap and simple, and it is why the flat build is the usual choice on small parts. The price is that one wrong pointer can corrupt anything (Figure 2). A protected build pays for reprogramming the MPU on switches and for crossing into the kernel on system calls, and it constrains how memory is laid out (MPU regions have hardware-defined sizes and alignments). D2 Which build a given PX4 board uses is part of its board configuration (F10-26).

How the hardware actually does it


The analogy's "body" is a microcontroller core with an interrupt controller and timers (HW204, F3-37). NuttX's notion of time comes from a hardware timer interrupt (a periodic tick, or a "tickless" one-shot timer reprogrammed for the next deadline), and its context switch uses the core's exception mechanism, on Armv7-M with the PendSV-style deferral you implemented in F3-39. D2 The memory protection of a protected build is a hardware unit in the core (the MPU) that the kernel programs with a small number of regions, each with a base, a size and permissions; an access outside the allowed regions raises a fault exception, which the kernel turns into an error report for the offending task. On a part without an MPU, there is no protected build. D2 D5 Clock rates, RAM sizes and MPU region counts are properties of the named microcontroller and come from its datasheet and reference manual (AH-21); this chapter names none.



Worked example


Task. A developer writes the 250 Hz sensor loop with a relative sleep: "do the work (0.15 ms), then sleep 4 ms". Each wake-up is also late by a measured 0.05 ms on average. How many samples does the loop produce in 10 s, and how far has it drifted from the 250 Hz grid by then? Compare with Listing 1's absolute releases.


    

  1. Period of the relative loop. One iteration takes 4 ms of sleep + 0.05 ms lateness + 0.15 ms work = 4.20 ms.
    2. 

  2. Samples in 10 s. 10,000 ms / 4.20 ms = 2,380.95, so 2,380 complete iterations, instead of 10,000 / 4 = 2,500. The loop runs at 1 / 4.20 ms ≈ 238.1 Hz, not 250 Hz.
    3. 

  3. Drift. After 2,380 iterations the relative loop is at 2,380 × 4.20 = 9,996 ms, while the 2,380th release on the grid is at 2,380 × 4 = 9,520 ms: 476 ms behind, growing by 0.20 ms every period.
    4. 

  4. Absolute releases. Release k is at k × 4 ms whatever happened before. Lateness and work affect each job's start and finish, but not the grid; in 10 s there are 2,500 releases, and as long as each job finishes before the next release (0.05 + 0.15 = 0.20 ms < 4 ms) none is skipped.
    5. 

  5. Why it matters downstream. An estimator that assumes 250 Hz but receives 238 Hz integrates with the wrong time step unless it uses the samples' own timestamps, and a controller tuned at one rate behaves differently at another (F10-17). Use absolute releases and carry timestamps in every message.
    6. 



The arithmetic is checked by the lab's step 3, where you change Listing 1 to a relative sleep and count samples for one second.

Where the analogy breaks


    

  • Lina's body runs her jobs truly in parallel; a single-core flight controller runs one task at a time. "Balance wins" means the balance task preempts the others between instructions, not that both run at once. Some newer processors have several cores; then NuttX's symmetric multiprocessing support and its own rules apply.
    • 

  • A reflex adapts its urgency; an RTOS priority is a number someone wrote down. If that number is wrong, NuttX will faithfully let the chat win over the balance. Priorities are a design decision you must analyse (F3-39).
    • 

  • Spilling a drink from a shared tray is visible at once; a memory overwrite may stay silent for minutes. In Listing 2 the damage appears only when the 40-character message arrives, long after boot. R2

Common mistakes and debugging


    

  • Symptom: a periodic loop runs slightly slower than its nominal rate and drifts against other loops. Cause: relative sleep. Find: log the release time of each job and plot its difference from k × period. Fix: absolute releases (Listing 1, lines 57–63).
    • 

  • Symptom: thread priorities seem to be ignored. Cause: attributes set without PTHREAD_EXPLICIT_SCHED, or the system refused the policy and the code did not check the return value. Find: print the policy each thread actually runs with (Listing 1 does). Fix: set explicit scheduling and check every return code.
    • 

  • Symptom: a variable of one module changes "by itself" in a flat build. Cause: an overflow or a stray pointer in another task. Find: look up the variable's neighbours in the link map; set a data watchpoint on its address in the debugger; read the bytes: text in a float is a strong clue. Fix: bounds-checked copies (snprintf, explicit lengths); for defence in depth, a protected build if the hardware and the flight stack support it.
    • 

  • Symptom: a task crashes or the system hard-faults only with certain inputs. Cause: stack overflow; a fixed stack that was enough for the usual path but not for a deep one. Find: the RTOS's stack-usage report (fill pattern, "high-water mark"), as in F3-36. Fix: measure the worst path, then size the stack with margin.
    • 

  • Symptom: a high-priority task waits for a long time on a lock. Cause: priority inversion (F3-40). Fix: priority inheritance on that lock, or keep high-rate work free of locks shared with slow tasks (uORB's design, F10-22).
    •

Summary


    

  • NuttX is the RTOS under PX4 on most flight controllers: fixed-priority preemptive scheduling, tasks and pthreads with fixed stacks, and a POSIX-style interface.
    • 

  • The POSIX interface is why the same flight-stack code also runs on Linux for simulation; options and limits still differ and must be checked per call.
    • 

  • Periodic work uses absolute releases; relative sleeps drift (4.20 ms instead of 4 ms per period in the Worked example).
    • 

  • Listing 1 delivered all 250 samples in order on the build container; its lateness numbers describe that machine only.
    • 

  • A flat build has one unprotected address space: an overflow in one task silently changes another task's data (kp became 1.7 × 1025 in Listing 2).
    • 

  • A protected build stops the faulting task instead, at a cost in speed and layout constraints, and only on hardware with an MPU.
    • 

  • Real-time is a property of the system: interrupts, locks, drivers and your own code all enter the response time.
    •

Answers to Check yourself


    

  1. Fixed-priority preemptive scheduling (the most urgent ready task runs at once) and a POSIX-style interface. It does not promise that your system meets its deadlines: that depends on priorities, execution times, interrupts and locks, which you must analyse and measure. (Also acceptable: it does not promise memory protection in a flat build.)
    2. 

  2. A task is started on its own and owns resources such as open files; a pthread is created by a task and shares that task's resources. For the scheduler both are entities with a priority, a stack and a state, scheduled by the same rule.
    3. 

  3. PX4 talks to the operating system through POSIX-style interfaces and a thin platform layer; Linux offers the same kind of interfaces, so the same source builds for both, with a simulator providing the sensor data on the laptop. Differences in timing, memory protection and options remain.
    4. 

  4. The thread inherits the creating thread's scheduling policy and priority, and the values set in the attributes are ignored, so the priorities you asked for silently do not apply.

Forensic lab answer key


Observation. Telemetry sends 10 packets per second for seconds 0–8, and 0 from second 9 on (total 90). At second 9 the logger wrote "GPS: 3D fix, 12 satellites, hdop". The dump shows 0x60 = 00 (the rate, which started at 10) and 0x61 = 5a (90: the sequence counter, consistent with 90 packets sent). The bytes 0x40–0x5f hold the end of that message ("…D fix, 12 satellites, hdop") with "hover\0" written over its beginning.


Hypotheses. (a) The telemetry task stopped running: ruled out because the model's task still reads its rate every second and the sequence counter is consistent; on the real system its CPU-load line would show it alive. (b) Its configuration (rate) changed: supported by 0x60 = 0. (c) The radio driver failed: ruled out by the radio's own counters in the scenario and by the dump.


Root cause. The message has exactly 32 characters; with its terminating zero it is 33 bytes. The buffer has 32 bytes, so the terminator lands on 0x60, telem_rate_hz, and sets it to 0. The logger's copy has no length check. The 30-character message at second 8 (31 bytes with the terminator) fit, so the bug stayed hidden until a message of exactly 32 or more characters appeared.


Fix and prevention. Copy with an explicit bound and always terminate inside the buffer (for example snprintf(line, sizeof line, "%s", text)), or keep the length with the data. Test: a unit test that logs messages of length 31, 32, 33 and 100 and checks a guard pattern placed after the buffer. Containment: canary bytes or a guard region after buffers in debug builds; a protected build where available; static analysis of string copies.


Alternative wrong answers. "The telemetry task crashed": the counter at 0x61 shows it ran exactly as many times as packets were sent; a crash would not zero the rate. "The radio failed": the radio's own counters were healthy and the firmware's rate variable is 0.


How the evidence was made. forensic_flat.cpp lays out a 32-byte buffer and a one-byte rate variable next to each other and copies each logger message with its terminator and no bound; nothing was edited by hand.
