Story hook

At the school fair, Lina's tray has become popular, and the teachers add a helper: Ana's only job is to watch Lina's tray and pin a note on the notice board whenever it tilts too far ("tray tilted past 30°, third time"). Ana does not touch the tray. She reads the notice "how is the tray held" that someone else keeps up to date, does her small calculation, and pins her own notice for whoever cares: the head teacher, the first-aid desk.

After lunch, the head teacher decides 30° is too generous and announces on the board: "settings changed: tray limit is now 20°". Ana's colleague at the next table, who follows the same instructions, keeps using 30° all afternoon. His notices say "no problems". He had been told the limit once, in the morning, and never looked at the "settings changed" notice again.

A PX4 module is such a helper: a small piece of code with one job, started from the shell, running on a work queue, reading topics, publishing its own topic, and reading its parameters, also when they change. In this chapter you write one, test it, and find the colleague's bug.

What you will be able to do

  • Design a small module: its job, the topics it subscribes to and publishes, its parameters, its rate and its work queue.
  • Implement the module's life cycle (start, run, status, stop), its periodic work and its parameter handling, in this course's miniature runtime.
  • Test the module with unit tests that call it directly and with a shell session, and read its topic like a listener would.
  • List the steps to add the same module to PX4 (source folder, build files, message definition, board configuration, start-up) and mark which you have verified.
  • Diagnose a module that ignores parameter changes.
Jargon box
Module (PX4)
Simple words: one program inside the flight stack with one job, which can be started and stopped from the shell. Analogy: one helper at the fair with one job. Precise: a unit of PX4 code with a command-line entry point (start, stop, status and its own commands), its own source folder and build description, that runs as a task or as work items on a work queue and communicates through uORB (F10-21). D1
Module life cycle
Simple words: what happens when a module starts, works, reports and stops. Analogy: the helper arrives, does the job, answers "how is it going?", leaves and clears the table. Precise: the sequence start (allocate, subscribe, register periodic work, read parameters), run (periodic or triggered work), status (print counters and state), stop (cancel work, release subscriptions and memory); PX4 provides base classes that implement the common parts (unverified box). D1
Scheduled work item
Simple words: a job that the system runs again and again at a fixed interval on a work queue. Analogy: "every ten seconds, look at the tray". Precise: a work item (F10-21) registered with an interval; the work queue thread calls its run function when the interval elapses, to completion, then waits for the next one. A work item can instead be triggered by a uORB publication. D1 R1
Module parameter
Simple words: a named setting of a module that the operator can change without rebuilding. Analogy: "tray limit is now 20°". Precise: a named, typed value stored in the parameter system, with a default, range and description, that a module reads at start and must re-read when the parameter system announces a change; PX4 announces changes on a topic. D1
Parameter update notification
Simple words: the message that says "some setting changed, check yours". Analogy: the "settings changed" notice. Precise: a publication on a dedicated topic each time any parameter changes; a module subscribes to it and, when it sees an update, reloads its parameters. In this course's runtime the topic is parameter_update_model. D1 R1
Listener
Simple words: a shell command that prints the latest message of a topic. Analogy: walking to the notice board and reading one notice. Precise: a tool that subscribes to a topic and prints its fields; PX4 provides one in its shell (unverified box); this course's shell provides listener tilt_status. D1
Edge-triggered event
Simple words: counting the moment something starts, not every moment it lasts. Analogy: counting how often the tray tipped too far, not how many seconds it stayed tipped. Precise: an event recorded on the transition of a condition from false to true; it needs the previous state to be stored. R1

Related terms: unit test, test harness, regression test, continuous integration; from this course work queue, uORB.

The idea in pictures

Layer 1 — the kid explanation

A flight controller is not one big program. It is many small helpers, each with one job: one reads the gyroscope, one estimates where the drone is, one steers, one writes the diary. They do not call each other; they pin notes on a notice board, and read the notes they need.

Writing your own helper means answering a few questions first. What is your job? Which notes do you need to read? Which note will you pin up? How often do you look? What settings can people change? Then you write the helper so that it can be started, asked "how are you doing?", and stopped cleanly.

The helper in this chapter watches how far the drone leans. If it leans more than a limit, it says so on its note and counts how many times it happened. And it keeps an eye on the "settings changed" notice, so that when someone changes the limit, it uses the new one at once.

Layer 2 — the student explanation

Design before code

A module is designed through its interfaces. For our example, tilt_guard:

QuestionAnswer for tilt_guardWhy
JobCompute tilt from vertical; flag and count excursions beyond a limit.One job, easy to test.
InputsThe attitude topic; the parameter update topic.Only what it needs.
OutputIts own topic tilt_status: time, tilt, limit, exceeded, count.Others can react; logs can record it (F10-25).
ParametersTG_MAX_TILT (degrees, default 30).Our own name, not a PX4 parameter.

Failure behaviourNo new attitude: publish nothing, count it.Silence is visible to a listener; a stale value is not.

The tilt from vertical, for roll φ and pitch θ, is the angle between the body's down axis and the world's down axis: cos(tilt) = cos φ · cos θ (yaw does not matter). D3 At φ = 25°, θ = 0, tilt is 25°; at φ = 20°, θ = 20°, cos(tilt) = 0.9397² = 0.8830 and tilt is 28.0°, more than either angle alone.

The course runtime

The build container has no PX4, so the module is written against this course's miniature runtime mini_px4.h (Listing 2): a simulated clock, uORB-like topics from F10-22's uorb_lite.h, a parameter store that publishes on a parameter update topic whenever a parameter is set, and a scheduler that calls work functions at fixed intervals. A "simulator" in runFor publishes a rocking attitude every 4 ms: roll 25·sin(πt) degrees, pitch 12·sin(πt + 1) degrees. The runtime is our own code and deliberately mirrors the shape of a PX4 module, not its API. R1

The module: Listing 1

The constructor subscribes to the two topics, reads the parameter once, and schedules run every 10,000 µs; the destructor cancels the schedule. That is the life cycle in RAII form: a module that exists is running, a destroyed module leaves nothing behind. run first checks the parameter update subscription and re-reads the parameter if anything changed, then takes the newest attitude (if none arrived since the last cycle it counts a "no data" cycle and returns without publishing), computes the tilt, detects false→true crossings, and publishes tilt_status. R1

From the course runtime to PX4


The concepts map one to one; the names and the build plumbing do not, and they are release-specific. Rules a flight-stack module must follow


    

  • Bounded run time. A work item runs to completion and delays everything behind it on its queue (F10-21). No blocking calls, no unbounded loops, no file input or output in run. Measure the worst case; choose the queue by priority need.
    • 

  • No dynamic allocation after start. Allocate at start; on a microcontroller, heap fragmentation and allocation failure are real (F10-20). Listing 1 allocates nothing in run.
    • 

  • Time from the flight stack's clock. Never from the host (F10-23); Listing 1 copies the attitude's timestamp into its output.
    • 

  • Parameters re-read on change. Every module with parameters subscribes to the update notification. The forensic lab is the failure.
    • 

  • Stale data is not data. Use the update check (update() returning false) or timestamps to detect missing input; publish nothing or publish a flag rather than repeat old values.
    • 

  • One owner per topic instance. Two modules publishing the same topic instance confuse every subscriber (F10-22).
    • 




Testing at three levels


Unit tests (Listing 4) call the module's run with chosen inputs: fast, deterministic, and they catch logic and parameter errors. SITL tests (F10-23) run the module inside the real flight stack with a simulated vehicle: they catch integration errors (topic names, scheduling, start-up). Bench tests on the flight controller, propellers removed, catch resource and timing problems: stack size, CPU load, queue latency on the real processor. Each level catches errors the others cannot; a module is not done until it has passed all three, in that order. D1 D2



How the hardware actually does it


On the flight controller, the module's run executes on a NuttX thread belonging to its work queue, at that queue's priority (F10-21); the interval is measured with the board's high-resolution timer, and the work queue thread is woken from a timer interrupt or from a uORB publication. Each work queue thread has a fixed stack, sized at build time: a module that puts large arrays on the stack in run can overflow it, and on a processor without memory protection between threads the overflow corrupts a neighbour silently (F10-20, flat build). The module's CPU share is run time × rate: Listing 1's computation is two cosines, one arccosine and a few comparisons, well under the rate loop's budget on any Cortex-M with a floating-point unit, but the actual number must be measured on the board (the course lab asks for it) and is not printed here. D1 Topics live in RAM, one buffer per queue entry per instance; a new topic with a small message costs little, but logging it at a high rate costs SD-card bandwidth (F10-25).



Worked example


Task. Predict, before running, three numbers in the shell session: (a) the number of tilt_guard cycles after 3 s; (b) the peak tilt during the first 3 s, to one decimal; (c) the number of exceed events in the 2 s after setting the limit to 20°.


    

  1. (a) The work is scheduled every 10 ms from start (time 0): runs at 10, 20, …, 3,000 ms: 300 cycles. Attitude arrives every 4 ms, so every 10 ms cycle has at least one new message: 0 without new data. Matches the output.
    2. 

  2. (b) Roll 25·sin(πt), pitch 12·sin(πt+1). Tilt is largest near the roll peaks. At t = 0.5 s: roll 25, pitch 12·sin(π/2 + 1) = 12·cos(1) = 6.48; cos(tilt) = cos 25° · cos 6.48° = 0.9063 × 0.9936 = 0.9005; tilt = 25.8°. A little later the pitch is larger and the roll still near 25: at t = 0.55, roll 24.69, pitch 12·sin(1.728 + 1) = 4.83 … smaller. Earlier: at t = 0.45, roll 24.69, pitch 12·sin(1.414 + 1) = 7.99; cos = 0.9086 × 0.9903 = 0.8998; tilt 25.9°. The peak is about 25.9°, in the printed output.
    3. 

  3. (c) From t = 3 to 5 s is one full period of the roll. The tilt exceeds 20° around each roll extreme (roll ±25°, one positive, one negative), so the condition goes false→true twice: 2 events. The output shows 2.
    4. 



The value of the exercise: if your prediction and the output differ, either the prediction or the module is wrong, and you learn which before flying.

Where the analogy breaks


    

  • A helper at the fair notices a new notice by chance; a module notices only if it checks. There is no "glance" in code: a module that does not poll the update topic, or is not triggered by it, never sees it. R3
    • 

  • Ana can take a break; a work item cannot. A module must return quickly every time; slowness delays every module behind it on its queue.
    • 

  • Notices on a board are read by people who understand them; topics are read by code that trusts their fields. A wrong unit or a stale value in a topic is believed by every reader (F10-22, F10-23).
    • 




Common mistakes and debugging


    

  • Symptom: a parameter change has no effect until reboot. Cause: no parameter update check. Find: change the parameter and read the module's topic or status. Fix: check the update topic in every cycle (Listing 1 lines 33–36) and test it (Listing 4 lines 59–67).
    • 

  • Symptom: the module's topic is never published in SITL. Cause: the module is not built (not in the board configuration) or not started. Find: try the start command; check the status command; list topics. Fix: enable it in the configuration; add it to the start-up script.
    • 

  • Symptom: the topic is published but always with the same value. Cause: the module republishes stale input. Find: compare timestamps of output and input. Fix: only publish after a successful update.
    • 

  • Symptom: events counted in the thousands. Cause: counting samples instead of edges. Fix: keep the previous state (Listing 1 lines 46–50).
    • 

  • Symptom: the rate controller's timing worsens after adding the module. Cause: the module runs on the rate loop's queue or takes too long. Find: the work queue status command; timing in the log. Fix: a low-priority queue; shorter run (F10-21).
    • 

  • Symptom: the board crashes after the module starts, only on hardware. Cause: stack overflow on the work queue thread. Fix: move large buffers into the object; measure stack use.
    •

Summary


    

  • A module has one job, defined by its inputs, its output topic, its parameters, its rate and its work queue.
    • 

  • Its life cycle is start (subscribe, read parameters, schedule), run, status and stop; RAII expresses it cleanly.
    • 

  • Every cycle: check parameter updates, take new input or publish nothing, compute, publish with the input's timestamp.
    • 

  • The lab module ran at 100 Hz (300 cycles in 3 s), saw a peak tilt of 25.9° and counted 2 events after the limit changed to 20°.

  • Without the parameter-update check the module kept 30° and counted 0 events; the unit test caught it, the merge should have been stopped.
