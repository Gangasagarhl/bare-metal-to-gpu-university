Story hook

The fair team has a notice board on the wall by the kitchen door. Tomás pins a note every time he refills a glass: "glass 3 refilled, 10:04:12". Aiko pins the route: "go left of the stage". Kwame pins the cash count. Nobody hands notes to anybody. Whoever needs to know something walks past the board and reads it. Each board space holds only a few notes: when a new one is pinned, the oldest in that space is taken down.

That works for the route. Lina only needs the newest route note; old ones are wrong anyway. It does not work for Kwame's job of counting how many glasses were sold. If Tomás pins a note per glass and Kwame passes the board only every few minutes, the space has been overwritten many times, and Kwame counts only the notes still hanging. His total is far too low, and nobody notices, because every note he read was correct.

PX4's modules talk through exactly such a board, called uORB. In this chapter you build a small working model of it, then measure what each kind of reader gets: the one who wants only the newest value, and the one who must not miss any.

What you will be able to do

  • Explain uORB's model: topics with fixed message types, publishers that never wait, subscribers that read when they run, queue length, multiple instances.
  • Implement a topic with a ring of the newest messages and a generation counter, and subscriptions that detect what they missed.
  • Choose between polling, larger queues and publication-triggered scheduling for a given reader, and compute the queue length it needs.
  • Verify a concurrent publish/subscribe implementation with invariants and ThreadSanitizer.
  • Diagnose an estimate that drifts because a reader of increments misses messages.
Jargon box
uORB
Simple words: PX4's notice board: modules post data there and read data from there. Analogy: the board by the kitchen door. Precise: PX4's asynchronous publish/subscribe messaging layer for communication between modules (and threads) inside one flight-stack instance; data is exchanged as fixed-size message structs on named topics. D1
Topic (uORB)
Simple words: one named kind of message, like "attitude" or "battery status". Analogy: one labelled space on the board. Precise: a named channel with exactly one message type, defined in a message definition file from which PX4's build generates a C++ struct; every message carries a timestamp. The ROS 2 topic of F9-37 is the same idea across processes and machines. D1
Publication and subscription
Simple words: the writer's handle and the reader's handle for a topic. Analogy: pinning a note; walking past and reading. Precise: a publication writes a new message to the topic without waiting for any reader; a subscription remembers which message it last read, can tell whether a newer one exists ("updated"), and copies it out. D1 R1
Queue length (uORB)
Simple words: how many of the newest messages the topic keeps. Analogy: how many notes fit in one board space before the oldest comes down. Precise: the size of a topic's ring of recent messages; with length 1, a reader sees only the latest message; with length n, a reader that falls fewer than n messages behind can still read every message in order. D1 R1
Generation counter
Simple words: a running number of how many messages were ever published on a topic. Analogy: the number written on each note: 1, 2, 3… Precise: a monotonically increasing count kept by the topic; a subscription compares its own position with it to decide whether it is up to date and how many messages were overwritten before it read them. R1 D1
Multi-instance topic
Simple words: several copies of the same topic, one per sensor of the same kind. Analogy: two spaces labelled "GPS", numbered 0 and 1. Precise: a topic that can be advertised more than once, each advertisement getting an instance index; subscribers choose the instance (for example the second IMU) and redundancy logic compares instances. D1
Latest-value semantics
Simple words: the reader only cares about the newest message. Analogy: Lina reading the newest route note. Precise: a usage in which missing intermediate messages is harmless because each message is a complete state (an attitude, a setpoint); contrast with messages that carry increments (an angle change since the last message), where every message matters. R2

Related terms: publish–subscribe, topic (ROS 2) and history and depth (QoS) from RB303; data race and mutex from SP203; work item from F10-21.

The idea in pictures

Layer 1 — the kid explanation

Inside PX4, modules never talk to each other directly. Each one pins its results on a notice board called uORB, under a label such as "attitude". Any module that needs the attitude reads it from the board when it is ready. The writer never waits for the readers, and a slow reader can never slow down the writer.

The board keeps only the newest few notes for each label. For many readers that is perfect: the controller wants the newest attitude, not an old one. But some readers must see every note, for example one that adds up small turns to know the total turn. If such a reader is too slow, it silently misses notes and its total comes out wrong. The art is to know which kind of reader you are writing.

Layer 2 — the student explanation

The uORB model

The PX4 Autopilot User Guide describes uORB as an asynchronous publish/subscribe API for communication between threads and modules. A topic has one message type, defined in a message definition file; the build generates a C++ struct for it, and every message has a timestamp field in microseconds. Publishers publish complete structs; subscribers check whether a newer message exists and copy it. Topics can keep a queue of more than one message, and some topics have several instances, for example one per IMU. Modules can be scheduled to run when a topic they subscribe to is published (F10-21). D1 The exact PX4 class and function names are in the unverified box of Layer 3; this chapter works with its own model, uorb_lite.h, whose every line you can read.

uorb_lite: a topic is a ring and a counter

In Listing 1, a Topic<T, Q> holds an array of Q messages and a 64-bit generation counter. publish writes message number g into slot g mod Q and increments g, under a mutex, and then calls any callbacks registered with onPublish. A Subscription keeps next_, the number of the next message it wants. update compares it with the topic's generation: if nothing new, it returns false; if the reader is more than Q behind, the overwritten messages are added to lost_ and the position jumps to the oldest message still in the ring; then one message is copied out and the position advances (Figure 1). A new subscription starts at the newest existing message, if any. These are this model's rules, chosen to match the behaviour the PX4 documentation describes; they are not PX4's code. R1 D1

Under real concurrency


Part 1 and 2 are single-threaded and repeatable. Listing 3 runs a publisher and a subscriber on two real threads. The publisher writes 200,000 messages as fast as it can; the subscriber reads whenever the scheduler lets it. Which messages the subscriber misses depends on timing and changes from run to run, so the program checks only invariants that must always hold: every message is either received or counted as lost; no message is torn (each carries a check value computed from its other fields); messages arrive in order; and the very last one is received. Layer 3 — the engineer's depth


Why "publishers never wait"


A flight stack has producers with hard timing (the IMU driver) and consumers with very different rates and urgencies (the rate controller at the IMU rate, the logger at a fraction of it, MAVLink streams at a few hertz). A blocking queue (F10-20) would let the slowest consumer stall the most critical producer. uORB's design inverts the responsibility: the publisher always succeeds, and each reader is responsible for running often enough or for asking for a queue long enough for its needs. The failure mode moves from "the system stalls" to "a reader silently misses data", which is safer for control but must be designed for. D1



How long must the queue be?


A reader of increments must read every message. If the publisher's period is Tp and the longest interval between two runs of the reader is Imax (its period plus its worst release jitter and response-time variation, F10-21), the reader finds at most ⌈Imax / Tp⌉ new messages, so the queue length must be at least that. With Tp = 1 ms and a 4 ms reader that is perfectly periodic, Q = 4 is just enough, which is why Listing 2's queue-4 reader lost nothing; any jitter would lose messages again. The Worked example adds jitter. Alternatives to a longer queue: trigger the reader on every publication (Part 2), or change the message so that missing one does not matter (publish the accumulated angle, or the increment since a timestamp that the reader also receives). R1



What a publication costs


Every publish copies the whole struct into the topic, and every read copies it out: the cost grows with message size and with the number of readers. Under a lock, the copy also determines how long other threads can be blocked by it; a long message on a busy topic is a blocking term for everyone who touches that topic (F10-21). Callbacks are called after the lock is released in Listing 1 (lines 26–38), because a callback that reads the topic would otherwise deadlock on the same mutex, and because work done under a lock lengthens everyone's blocking. Implementations may avoid the lock on the read path with sequence counters or per-slot generation checks; Listing 1 detects an overwrite between its two locked steps and counts it as lost (lines 104–110). R1 D4



Timestamps are part of the data


Because readers sample topics at their own rates, "the newest message" may be old by the time it is used. Every uORB message carries the time at which its data was valid, so that consumers can compute delays, detect stale data (a sensor that stopped publishing), and align data from different sources. A reader that ignores timestamps cannot distinguish "nothing changed" from "the publisher died". D1 The logger records these timestamps, which is what makes the analyses of F10-25 possible.



Instances and redundancy


With two IMUs, both drivers publish the same message type. Multi-instance topics keep them apart: each publication gets an instance index, and consumers subscribe to a specific instance or iterate over all. Redundancy logic (voting, failover when one instance stops or disagrees) is built on top: it compares instances and their timestamps. Part 3 of Listing 2 shows the basic property in the model: a subscription to an instance sees only that instance's messages. D1 R1



Inside one process; bridges outside


uORB connects modules inside one PX4 instance. Communication with the ground station uses MAVLink (F10-30), and communication with ROS 2 on a companion computer uses a bridge that maps selected uORB topics to DDS topics; the bridge's name and configuration have changed between PX4 releases (unverified box). The concepts you learned for ROS 2 topics (F9-37, F9-40) carry over: uORB's queue length plays the role of the history depth, and uORB has no reliability or durability settings because nothing crosses a network. How the hardware actually does it


On a flight controller, all modules share one physical memory (F10-20): a publication is a memory copy into a buffer owned by the uORB layer, plus bookkeeping, and a read is a copy out. Nothing travels on a bus or a network. On a single core, the "concurrency" of Listing 3 is interleaving: a higher-priority thread can preempt a lower one in the middle of a publish, which is why the copy must be protected (a lock, or briefly disabled preemption or interrupts) so that no reader sees half of an old message and half of a new one. The torn-message check in Listing 3 is the test for exactly that failure. D1 D4 On a multi-core processor (and on the PC of a SITL run), two threads can really run at the same time, and the memory model of the language and the processor (F2-35) decides what a reader may observe; the mutex in Listing 1 provides the needed ordering. Copy cost depends on the processor's memory system and the message size; measure it on the target if it matters.



Worked example


Task. A gyro topic is published at 1 kHz. A reader that integrates angle increments runs every 4 ms on a work queue, but its start can be delayed by up to 2 ms by higher-priority work (its worst waiting time from an analysis like F10-21's), while its earliest start is on time. What queue length guarantees that it never loses a sample? What angle error would queue length 4 cause in the worst case for a 90°/s turn lasting 2 s, if every period suffered the worst delay pattern?


    

  1. Longest interval between two reads. One run starts on time, the next as late as possible: Imax = 4 + 2 = 6 ms.
    2. 

  2. Messages in that interval. At most ⌈6 / 1⌉ = 6 publications. A queue of 6 guarantees no loss.
    3. 

  3. Loss with queue 4. In such an interval 6 messages arrive, 4 are still in the ring: 2 are lost. The next interval is then only 4 − 2 = 2 ms long (the run after a late run can be on time), with 2 messages, none lost. In the worst repeating pattern (on time, late, on time, late...), 2 messages are lost every 8 ms.
    4. 

  4. Angle error. A 2 s turn has 2,000 / 8 = 250 such pairs: 500 lost samples of 0.09°: 45° of a 180° turn, 25 %. With timestamps or accumulated angles the reader could detect or avoid the loss; with plain increments it cannot.
    5. 

  5. Choice. Queue 6 (or more, with margin), or a callback per publication, or publish accumulated angles. Each option has a cost: memory per topic, a wake-up per sample, a change of message definition.
    6. 



The model reproduces step 2's rule in its simplest form: with no jitter, queue 4 lost nothing and queue 1 lost three of four (Listing 2). Lab step 3 adds the jitter to the model and checks steps 3 and 4; a version of that check run while preparing this chapter (reads at 4, 10, 12, 18, 20 ms and so on, for 2 s) lost 498 of 2,000 samples with queue length 4 and none with 6, integrating 134.82° and 179.64° of 180° (the last few samples were published after the last read).

Where the analogy breaks


    

  • Reading a paper note leaves it on the board for everyone; so does reading a uORB topic, but each reader keeps its own place. Two readers of the same topic can be at different positions, one up to date and one far behind (Figure 1); a board has no idea who has read what.
    • 

  • Overwritten notes on a real board might be found in the bin; overwritten messages are gone. Only the counter remembers that they existed. A reader that does not check its lost count cannot know. R1
    • 

  • Pinning a note takes as long as it takes; a publication must be short and bounded. It runs inside time-critical code, and any lock it holds is a blocking term for other threads.
    • 




Common mistakes and debugging


    

  • Symptom: an integrated quantity (angle, distance, energy) is too small by a constant factor. Cause: a reader of increments loses messages. Find: compare publication rate and reader rate; count lost messages; check the queue length. Fix: longer queue, publication-triggered reading, or messages that carry accumulated values (forensic lab).
    • 

  • Symptom: a module uses a value that stopped changing long ago. Cause: the publisher stopped and the reader never checks timestamps. Fix: reject data older than a limit; report the stale topic.
    • 

  • Symptom: a module reads a topic in a loop and burns processor time. Cause: polling with no new data. Fix: check updated() first, or schedule on publication.
    • 

  • Symptom: deadlock when a callback reads the topic that called it. Cause: callbacks invoked while holding the topic's lock. Fix: call them after releasing it (Listing 1, lines 35–37).
    • 

  • Symptom: rare garbage values in one field. Cause: torn reads in a hand-written shared struct without the topic's protection. Find: a check word and ThreadSanitizer, as in Listing 3. Fix: share data only through the topic mechanism.
    •

Summary


    

  • uORB is PX4's in-process publish/subscribe layer: topics with one fixed message type each, with timestamps.
    • 

  • Publishers never wait; each subscriber reads when it runs and tracks its own position.
    • 

  • A topic keeps the newest Q messages; a reader more than Q behind loses messages, and only a counter can tell.
    • 

  • Latest-value readers are fine with Q = 1; readers of increments need Q ≥ ⌈longest read interval / publication period⌉, a callback per publication, or accumulated values.
    • 

  • Measured in the model: queue 1 read 250 of 1,000 and integrated 22.50° of 90°; queue 4 and a callback read all 1,000.
    • 

  • Concurrency was checked with timing-independent invariants and ThreadSanitizer (no race reported in this run).
    • 

  • Timestamps let readers detect delay and stale data; multi-instance topics carry redundant sensors.

Forensic lab answer key


Observation. During the turn (1.0–3.0 s) true yaw rises by 90.00° − 0.04° ≈ 89.96° in the window shown, the estimate by 22.50° − 0.05° = 22.45°: a ratio of almost exactly 1/4 (90.00 vs 22.50 at the end). gyro_delta: queue length 1, 4,000 published, 3,000 lost by the estimator's subscription. The estimator ran 1,000 times. heading: 1,000 published, 992 lost by the log reader.


Hypotheses. (a) Mis-scaled gyro: ruled out; the loss count accounts exactly for the factor (1,000 read of 4,000 = 1/4), and before the refactor the same gyro gave correct headings. (b) Dropped samples: confirmed by 3,000 lost. (c) Stale log values: ruled out; the final estimate itself is 22.50°, and the log reader always takes the newest heading.


Root cause. The gyro publishes increments at 1 kHz; the estimator runs every 4 ms and reads one message from a topic that keeps one: it sees 1 of 4 increments, so it integrates 1/4 of the rotation.


The heading losses. Not a bug: the heading is a complete state, and the log reader only needs the newest value every 0.5 s. Losses are harmful only for readers of increments.


Fixes. (1) Restore scheduling on every gyro publication. (2) Keep 250 Hz but give gyro_delta a queue of at least 4 plus margin for jitter, and drain it with a loop. (3) Publish the accumulated angle (or integrate in the driver over the reader's interval) so that the newest message suffices. Test: in SITL or in the model, turn 90° and assert the estimate within a tolerance; also assert that the estimator's lost count on gyro_delta is zero.


How the evidence was made. forensic_yaw.cpp: a 1 kHz publisher of yaw increments with queue length 1, an estimator that runs every 4 ms and reads once, and a log reader every 500 ms; nothing edited by hand.
