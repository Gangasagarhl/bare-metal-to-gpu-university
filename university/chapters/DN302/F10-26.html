Story hook

The school buys new trays for next year's fair. They look like the old ones, but the cup holders are in different places, one handle is lower, and the little bell that rings when a glass tips is screwed to a different corner. Lina knows how to walk with a tray. What she does not know is this tray.

So before carrying anything, Mateus draws the new tray on paper: every holder, every handle, the bell. He notices on the drawing that the bell has been screwed exactly where one cup holder sits; one of them must move. Then, with the real tray, they check each holder one by one with a plastic cup: "holder one, does a cup fit? yes. Holder two? yes." On the second prototype tray, two holders are labelled the wrong way round: the label "big glass" is on the small holder. Nothing breaks, but the check catches it.

Porting PX4 to a new flight controller is the same work. The flight stack is the same; the board is new. You describe the board (which pin does what, which chip sits on which bus), you check the description before building, and you bring the board up one device at a time, from the serial console to the last sensor.

What you will be able to do

  • List what a PX4 port consists of: the NuttX board support (clocks, pins, memory, console), the PX4 board configuration (modules, drivers, sensors, outputs), and the start-up configuration.
  • Write a board description from a schematic and check it for the common conflicts: pins used twice, shared chip selects or addresses, timer rate conflicts, missing console.
  • Plan a bring-up order and say what evidence each step must produce.
  • Interpret a first-boot log: sensor probes, identity registers, preflight results.
  • Diagnose swapped chip selects from the probe output alone.
Jargon box
Port (PX4 to a board)
Simple words: the work that makes the same flight software run on a new flight-controller board. Analogy: learning a new tray for the same walk. Precise: the board-specific code and configuration for a new flight controller: NuttX board support (clock tree, memory map, pin multiplexing, console, storage), PX4 board files (which drivers, modules and sensors, bus and output mapping), a bootloader, and start-up settings; PX4's generic code is not changed. D1 D2
Board description
Simple words: the written list of what is connected where on a board. Analogy: Mateus's drawing of the new tray. Precise: the set of definitions that map board functions to processor resources: which pin is which bus signal, chip select, timer channel or LED; which device sits at which chip select or address; which timer drives which output. In PX4 and NuttX it is spread over several C headers and configuration files (unverified box); in this course it is one text file. D1 R1
Chip select
Simple words: the wire that tells one chip on a shared SPI bus "this message is for you". Analogy: calling one person by name in a group. Precise: a per-device line, driven low by the controller during a transfer, that enables one device on an SPI bus; every device on a bus needs its own chip select. D4
WHO_AM_I register
Simple words: a register in a sensor chip that always returns the same identity number. Analogy: asking a cup holder "which size are you?". Precise: a read-only identification register found in many sensor chips, with a fixed value given in the chip's datasheet; drivers read it at probe time to confirm that the expected chip answers. Register name and value differ per chip (AH-21). D4
Probe
Simple words: the driver's first contact with its chip, to check it is there and is the right one. Analogy: checking each holder with a plastic cup. Precise: the driver step that talks to the device at the configured bus and select or address, reads its identity, and fails cleanly if the answer is wrong or missing, before configuring the device. D1
Timer group (PWM outputs)
Simple words: outputs that share one hardware timer and so must share one update rate. Analogy: cup holders that are fixed to one plate. Precise: the channels of one timer peripheral share its counter and period; each channel can have its own pulse width but not its own frequency. Outputs on one timer must use the same rate or protocol (F10-10). D4 R1
Bring-up
Simple words: getting a new board to work step by step, from the first sign of life. Analogy: trying the new tray with one plastic cup at a time. Precise: the ordered process of verifying a new board: power, clocks, debug and console, memory, storage, buses and devices, outputs, then the full software; each step with its own evidence (BR-07, DR403). D3

Related terms: bring-up, bring-up plan, board support layer, pin multiplexing, SPI, I2C, I2C address conflict, PWM, timer peripheral, Kconfig, linker script, boot loader (microcontroller).

The idea in pictures

Layer 1 — the kid explanation

A drone's brain is a small computer board. Many companies make such boards, and each one wires its parts a little differently: the motion sensor might be connected to one wire on this board and to another wire on that board. The flight program is the same for all of them, but it has to be told how this particular board is wired.

So the first job is writing a map of the board: "the motion sensor is here, the air-pressure sensor is there, motor 1 is on this pin". Then a checking program looks for mistakes in the map, like two things on the same pin.

Then the board is switched on for the first time, and each part is asked "who are you?". Every sensor answers with its own number. If the motion sensor answers with the air-pressure sensor's number, the map has the two mixed up, and it is much better to find that on the table than in the air.

Layer 2 — the student explanation

What a port consists of

PX4 runs on many flight controllers; most use microcontrollers from a few families that NuttX already supports (F10-20). When the processor is supported, porting means writing board files, not drivers: D1 D2

  • NuttX board support: the clock configuration (crystal, PLL, bus clocks), the memory layout (where flash and RAM are, how much is reserved for the bootloader), pin multiplexing for every used peripheral, the serial console, storage (SD card), LEDs, and a NuttX configuration selecting the drivers.
  • PX4 board configuration: which modules and drivers to build (Kconfig-style options), which sensor sits on which bus with which chip select or address and orientation, the mapping of outputs to timers and channels, the default parameters and start-up script for the board.
  • Bootloader: a build of PX4's bootloader for the board, so firmware can be flashed over USB.

The quickest route is to start from the files of an existing board with the same processor and similar sensors and change only what differs. The exact files are listed in the unverified box of Layer 3.

Describe the board, then check the description

Before any build, every pin and device of the schematic goes into a board description. Most first-boot failures are description errors: a pin used for two functions, two devices given the same chip select, two outputs on one timer asked to run at different rates. The course uses its own one-line-per-item format (documented in Listing 1, lines 6–11) and a checker that finds exactly these errors. Two errors, each a classic. Output 6 was put on the same timer as output 5 (TIM4) but at 400 Hz, while output 5 asks for 50 Hz (a servo, say); all channels of one timer share its period (F10-10), so one of them would silently get the wrong rate. And the red LED was given pin PB1, which the barometer's chip select already uses: blinking the LED would select the barometer in the middle of other bus traffic. First boot: probe every device


At start-up, each sensor driver probes its chip: it selects the device at the configured bus and chip select (or address), reads the identity register, and compares with the value from the chip's datasheet. Only if the value matches does it configure the chip and start publishing (F10-22). Then preflight checks decide whether the vehicle may arm. The course models this with a board whose wiring is fixed in code and a start-up that reads the description (Listing 3). In the model, a select line with no chip reads 0xff (an assumption of the model: the data line is pulled high). The first boot with the reviewed description: R3




Each probe line is evidence: the device, where it was looked for, what answered, and what was expected. The identity values in the model (0x47, 0x50, 0x12, 0x3d) are model values; real values come from each chip's datasheet.

Clocks, memory and the first sign of life


The two errors that stop a port before any sensor are a wrong clock configuration and a wrong memory layout. A wrong crystal frequency makes every derived clock wrong: the console prints garbage at the "right" baud rate, timers run fast or slow, USB does not enumerate. A wrong flash start address (forgetting the bootloader's reserved area) makes the bootloader jump into nothing. Both show no useful error; the evidence is the absence of a console. That is why the console comes first in the bring-up order, and why a debug probe (SWD) that can halt the processor and read registers is the essential tool of the first day (F3-36, BR-07). D3 D4



Sensor orientation and redundancy


A sensor that probes correctly can still be wrong: if its axes are rotated relative to the board and the rotation is not configured, the estimator receives roll as pitch. The test is physical: tilt the board nose down and check that the attitude shows nose down, then each other axis. Redundant sensors (two IMUs, as on the course model) protect against one failing; a lost probe should never be hidden by the other sensor: the course model warns "redundancy lost" exactly so that the bench test does not pass silently. D1 R3



Why check descriptions with a program


The course's checker (Listing 1) is about 110 lines and finds four classes of error. Real board files are spread over several files and two languages, which makes such checks harder but not less useful: a script that extracts pins, selects and timer assignments from the board files and checks them is a good mini-project, and a CI step that runs it on every change catches errors before anyone flashes a board. R1



How the hardware actually does it


On the microcontroller, each pin can serve one of several functions (GPIO, a bus signal, a timer channel), selected by pin multiplexing registers that the board support writes at start-up; two functions on one pin are impossible at the same time, which is why the checker forbids it. An SPI controller drives clock and data lines shared by all devices on the bus; each device has its own chip select, usually a GPIO driven by software before and after each transfer. A device whose chip select is never asserted never answers; on a bus with a pull-up on the data-in line, the controller then reads all ones (0xff), which is the course model's assumption and a common real symptom. An I2C device answers at its address; two devices with the same address on one bus collide. A timer peripheral counts at a clock derived from the system clock, resets at its period, and compares each channel's pulse width register against the count to produce PWM; the period is shared by all channels of that timer. D4 Exact pin functions, timer channels and identity values come from the processor's reference manual, the board's schematic and each chip's datasheet (AH-21); none were consulted in this build, and the model's pin names are illustrative.

Where the analogy breaks


    

  • A tray's mistakes are visible; a board's are not. A swapped chip select or a wrong clock looks exactly like a working board until something is measured. Only probes and measurements show it.
    • 

  • A cup that does not fit a holder just does not fit; a wrong device may answer. A swapped chip select gets an answer, just from another chip: the identity check is what turns that into an error. R4
    • 

  • Lina learns the new tray once; a port must work for every board of that design. Manufacturing variants (a different sensor fitted because of supply) need the probe to handle alternatives.

Common mistakes and debugging


    

  • Symptom: nothing on the console after flashing. Cause: wrong clock (crystal value), wrong console pins, wrong flash offset. Find: attach the debug probe, halt, read the program counter and clock registers. Fix: compare board files with the schematic and reference manual line by line.
    • 

  • Symptom: a sensor probe reads 0xff or 0x00. Cause: no chip answering: wrong chip select, chip not powered, bus pins wrong. Find: logic analyser on the bus during the probe. Fix: description or power rail.
    • 

  • Symptom: a probe reads another chip's identity. Cause: chip selects swapped in the description. Find: compare each probe's received value with the other devices' expected values. Fix: the forensic lab.
    • 

  • Symptom: a servo jitters or an ESC does not arm. Cause: outputs on one timer with different rates. Fix: regroup outputs by timer (Worked example).
    • 

  • Symptom: attitude shows roll when the board is pitched. Cause: sensor rotation not configured. Fix: set the rotation; repeat the tilt test per axis.
    • 

  • Symptom: "works on my board" but not on the second unit. Cause: a different sensor fitted, or a revision change. Fix: record the board revision; let drivers probe alternatives.
    •

Forensic lab answer key


Observation. imu0 (looked for at SPI1 PD7) read 0x50, expected 0x47; baro0 (at SPI1 PC2) read 0x47, expected 0x50. Both "another chip answered". imu1 and mag0 are ok. Result: 0 of 1 baro (arming refused), 1 of 2 IMU (redundancy lost).


Is the barometer bad? No. The value 0x50 is the barometer's identity, and it was read by the imu0 probe at PD7; the value 0x47 is the IMU's identity, read at PC2. Both chips answer correctly, just at each other's chip select.


Root cause. The tidied description swapped the two chip selects: spi SPI1 PD7 imu0 and spi SPI1 PC2 baro0, where the working description (and the wiring) has imu0 on PC2 and baro0 on PD7.


Failure versus warning. With no barometer the vehicle has no altitude source for the estimator: a hard failure. One of two IMUs missing still leaves one: degraded, so a warning. Without the warning the bench test would have looked like a single "baro" problem, the IMU half of the evidence would have been missed, and a new board would have been ordered for nothing.


Fix and prevention. Restore PC2 for imu0 and PD7 for baro0. Prevention: generate or check the description against the schematic's net list in CI; make the probe report whose identity a wrong answer matches (lab step 4); never accept a board-file change without a bench boot log showing all probes ok.


How the evidence was made. forensic_bringup.in is bringup.in with the chip selects of imu0 and baro0 swapped; the model's wiring (Listing 3 lines 16–25) is unchanged.
