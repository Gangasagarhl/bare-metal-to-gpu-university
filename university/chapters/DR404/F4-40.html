Story hook

So far you have been the guest principal. Now you are the real one. You hand the small school a written agreement: "You may teach, mark, open your own cupboards. Call me when you touch the building's bell, the boiler, or the front door; call me if you fall ill; call me when you want to leave." Then you let them work and wait at your desk. Every time they call, you note why in a ledger, handle it, and let them continue exactly where they stopped.

That agreement is a page of memory called the VMCB; the moment they call is a VM exit; and the ledger, counts of exits by reason, is the most useful debugging tool a hypervisor writer has. In this chapter your kernel becomes a hypervisor: it enables AMD's SVM extension, builds one virtual CPU, runs a small 64-bit guest that prints through an emulated UART, survives a guest's triple fault, and reports invalid guest states with the documented error code. At the end, the ledger catches a guest that wastes two seconds polling a timer: between 180,000 and 215,000 exits across this build's runs, against 268 for a guest that halts.

What you will be able to do

  • Implement SVM enablement, a VMCB with guest and host state, and a run loop that enters a guest and handles every exit.
  • Implement exit handlers for port I/O (with a 16550 output model and an 8254 model), CPUID, HLT, a hypercall and triple fault.
  • Explain a VM-entry failure from its documented error code, on AMD SVM and on Intel VMX.
  • Diagnose a slow guest from exit counts by reason and by port.
  • Evaluate what a run under QEMU's emulated SVM proves about real hardware, and what it does not.
Jargon box
SVM (AMD-V)
Simple words: AMD's processor extension for running virtual machines. Analogy: the building's rule book that lets a second school run inside it. Precise: Secure Virtual Machine: enabled by EFER.SVME; adds VMRUN, VMLOAD, VMSAVE, VMMCALL, STGI, CLGI and the VMCB; guest-mode execution ends in #VMEXIT with an exit code. D1 C1
VMX (VT-x)
Simple words: Intel's extension for the same purpose. Analogy: another building's rule book, with different forms. Precise: Virtual Machine Extensions: VMXON enters root operation; VMLAUNCH and VMRESUME enter non-root operation with a VMCS selected by VMPTRLD and accessed by VMREAD and VMWRITE. D2 C1
VMCB
Simple words: one page of memory that describes a virtual CPU to the processor. Analogy: the written agreement and the small school's state, on one sheet. Precise: virtual machine control block: a 4 KiB, page-aligned structure with a control area (intercepts, I/O and MSR bitmap addresses, ASID, exit code and information, event injection, nested paging) and a state-save area (segments, control registers, EFER, RIP, RSP, RAX and more). D1
VMCS
Simple words: Intel's counterpart of the VMCB. Analogy: the same agreement on the other building's forms, which only the clerk may read and write. Precise: virtual machine control structure, accessed only through VMREAD and VMWRITE with field encodings; its layout in memory is not architectural. D2
Intercept
Simple words: a rule saying "this event must stop the guest and call the hypervisor". Analogy: "call me when you touch the bell". Precise: a control bit in the VMCB (or an execution control in the VMCS) that turns an instruction, register access, exception or interrupt in guest mode into a VM exit. D1 D2
I/O permission map (IOPM)
Simple words: a table with one bit per I/O port, saying which ports the guest may not touch directly. Analogy: the list of doors with an alarm. Precise: on SVM, a physically contiguous bitmap whose address is in the VMCB; a set bit makes IN or OUT to that port exit with code IOIO when the IOIO intercept is on. D1
Exit code and exit information
Simple words: the number that says why the guest stopped, and the details that go with it. Analogy: the line in the ledger: "rang the bell, east wing, 10:42". Precise: on SVM, EXITCODE in the VMCB (names from SVM_EXIT_*: 0x7B IOIO, 0x72 CPUID, 0x78 HLT, 0x7F SHUTDOWN, 0x81 VMMCALL, 0x400 NPF, −1 ERR) with EXITINFO1 and EXITINFO2; on VMX, the exit reason (basic reason in bits 15:0) and the exit qualification. D3 R6
VM-entry failure
Simple words: the processor refuses to start the guest because its described state breaks a rule. Analogy: the agreement is not signed properly, so the small school is not let in. Precise: on SVM, VMRUN performs consistency checks and on failure exits immediately with EXITCODE = −1 (SVM_EXIT_ERR, "invalid_guest_state" in Linux's table); on VMX, VMLAUNCH/VMRESUME either fail as an instruction (with a VM-instruction error number) or the entry fails after loading and exits with bit 31 of the exit reason set (basic reason 33 for invalid guest state). D3 D2 R3
ASID
Simple words: a number tagging the guest's TLB entries so they are not mixed with the host's. Analogy: a coloured sticker on every key copy, one colour per school. Precise: address space identifier in the VMCB; ASID 0 belongs to the host, and VMRUN rejects it for a guest. Intel's equivalent is the VPID. D1 R3
Global interrupt flag (GIF)
Simple words: an extra on/off switch for interrupts, above the usual one, used while switching between host and guest. Analogy: the real principal's "do not disturb" sign during the hand-over. Precise: an SVM flag cleared by CLGI and set by STGI; while it is clear, interrupts are held pending, so the hypervisor can enter and leave the guest atomically. D1

The idea in pictures

Layer 1 — the kid explanation

A hypervisor is a program that lets another operating system run on the processor almost by itself, but stops it whenever it does something important. Before starting the guest, the hypervisor fills in a form: "stop the guest if it talks to a device, if it asks the processor who it is, if it goes to sleep, or if it crashes." Then it says "go".

When the guest does one of those things, the processor freezes it, writes down why on the form, and wakes the hypervisor. The hypervisor does the job (for example, prints the letter the guest wanted to print), notes it in a tally, and says "go" again. The guest never notices it was stopped.

Layer 2 — the student explanation

Enabling SVM

The hypervisor first checks that the processor has SVM (CPUID 0x80000001, ECX bit 2) and that firmware has not locked it off (the SVMDIS bit of the VM_CR MSR). It then sets EFER.SVME, which makes the SVM instructions legal, and writes the physical address of a 4 KiB host-save area to the VM_HSAVE_PA MSR: VMRUN stores part of the host's state there. CPUID 0x8000000A describes the SVM implementation; QEMU's model reports revision 1, 16 ASIDs, and with +npt the nested-paging feature bit (R1). D1 R1

Describing the guest

The VMCB's state-save area gets a complete processor state: segment registers with their hidden attributes (a 64-bit code segment, flat data segments, a busy TSS), GDTR, IDTR, CR0, CR3, CR4, EFER, RFLAGS, RIP, RSP. The lab's first guests share the host's page tables (identity map of the first 4 GiB with 2 MiB pages) and run in long mode from the start, so the guest state is mostly a copy of the host's. The guest has no IDT on purpose: any exception becomes a triple fault, which is the cleanest way to test the triple-fault path. D1

The control area says what to intercept: external interrupts (so that the host keeps its timer), CPUID, HLT, I/O instructions, shutdown (triple fault), VMRUN and VMMCALL. It points to an I/O permission map with every bit set, so every port access exits. It gives the guest ASID 1. And it sets V_INTR_MASKING, which makes the host's interrupt flag, not the guest's, decide whether a physical interrupt stops the guest. D1

Running and handling exits

One VMRUN runs the guest until the next intercepted event. VMRUN saves and loads RAX, RSP and RIP through the VMCB but not the other general registers, so a small assembly routine loads them from a GuestRegs structure before VMRUN and stores them back after. The run loop then reads EXITCODE and dispatches:

  • IOIO (0x7B): decode port, direction and size from EXITINFO1 (Figure 2), emulate the device, write the result into the guest's RAX for an IN, and set the guest's RIP to EXITINFO2, which holds the address of the next instruction.
  • CPUID (0x72): execute CPUID on the host, edit the result (set the hypervisor-present bit, hide SVM, answer the 0x40000000 range with "DR404-tinyHV"), and advance RIP by 2.
  • HLT (0x78): advance RIP by 1 and wait, on the host, until the guest's next virtual timer tick.
  • VMMCALL (0x81): the hypercall. The DR404 interface has one call: RAX = 0 means "exit with the code in RBX". Advance RIP by 3.
  • SHUTDOWN (0x7F): the guest triple-faulted. Report it, destroy the guest, carry on.
  • −1 (SVM_EXIT_ERR): VMRUN refused the state. Report and stop.

Each handler is a few lines; R1 traces the first six exits of the "hello" guest, alternating a read of the UART's line-status register (port 0x3FD) and a write of a character to port 0x3F8. R1 D3

Device models

The UART model is only what the guest uses: transmit (collect characters into a line, print the line on the host console prefixed with guest|) and line status (always "transmitter empty"). The PIT model implements channel 0 in mode 2: writes to port 0x43 and 0x40 set a reload value and start time, a latch command freezes the current count, and reads of port 0x40 return the count, low byte then high. The count is computed from the host's TSC, so the virtual PIT runs at real speed even though no real PIT is involved. R4 R5

Layer 3 — the engineer's depth

Interrupts and the hand-over

The hypervisor's own 100 Hz timer must keep working while a guest runs. svm_run executes CLGI (global interrupt flag off: interrupts held pending), STI (host IF on), then VMRUN. In guest mode, with V_INTR_MASKING set and the INTR intercept on, a physical interrupt causes a #VMEXIT with code INTR. After the exit, STGI re-enables the global flag, the pending interrupt is taken by the host's own handler right there, and the loop continues. Without CLGI, an interrupt arriving between STI and VMRUN would be taken in the wrong place; without STGI the host would never take one. In the busy run, the report shows a handful of INTR exits for about 200 host ticks; our reading, not verified, is that most ticks arrive while the hypervisor is handling an I/O exit and are taken at STGI without an exit of their own. D1 R5

Halting without spinning

A HLT exit must not spin the host. handle_hlt computes the TSC value of the guest's next virtual PIT tick and halts the host CPU (sti; hlt; cli) until the host's own timer moves past it. If the guest halted with interrupts disabled or without programming the timer, nothing can ever wake it: the hypervisor stops it as "halted forever" instead of waiting eternally. F4-40's guests have no interrupt handlers, so a woken guest continues after its HLT; F4-41 adds real interrupt injection. R4

VM-entry failure: the documented error code

VMRUN checks the guest state before entering it, and refuses illegal combinations. On SVM, a refusal looks like an immediate exit with EXITCODE = −1, which Linux's header names SVM_EXIT_ERR and its table "invalid_guest_state". SVM gives no further code: the hypervisor must find which rule it broke by checking the state against the list of consistency checks in the APM. R3 breaks four rules on purpose (VMRUN intercept clear, ASID 0, EFER.SVME clear, CR0.NW set with CR0.CD clear) and QEMU's model refuses each one; then the same guest with a valid state runs normally, proving the host survived. D1 D3 R3

A finding of this build: QEMU 8.2.2 stores the failure code as 0x00000000FFFFFFFF, only the low 32 bits of −1. A hypervisor that compared the 64-bit field with −1 would not recognise the failure under QEMU; Listing 3 compares the low 32 bits. Whether real processors write all 64 bits has not been checked. R3

On Intel VMX the documentation is richer. A VMLAUNCH or VMRESUME can fail in two ways. If the checks on the VMX controls or the host-state area fail, the instruction itself fails ("VMfailValid") and the VM-instruction error field of the VMCS holds a number that the SDM lists with its meaning. If the checks on the guest state fail, or loading MSRs fails, the processor reports a "VM-entry failure" as a VM exit whose exit reason has bit 31 set: basic reason 33 means invalid guest state, 34 means MSR loading failed. Listing 6 decodes 0x80000021 and 0x80000022 with Linux's own table. D2 D3 R6

Not verified — check before relying on this

Not opened in this build: the AMD APM Vol. 2 (VMCB layout appendix, the list of VMRUN consistency checks, the IOIO EXITINFO1 format, the MSR numbers EFER 0xC0000080, VM_CR 0xC0010114 and VM_HSAVE_PA 0xC0010117, the intercept-bit order, the segment attribute format) and the Intel SDM Vol. 3 (the VMfailValid/VM-entry-failure distinction and the VM-instruction error numbers). Every VMCB offset and bit in Listing 1 and Listing 3 was written from memory; the runs prove only that QEMU 8.2.2's SVM model agrees with them. The exit-code and exit-reason numbers and names are verified against <asm/svm.h> and <asm/vmx.h>. Before running on hardware, check every offset against the APM's VMCB appendix, and check that real processors enforce the four checks R3 shows.

What the counts tell you

The hello guest causes 134 exits to print 66 characters: two per character (status, then data) plus one CPUID and one hypercall. A real 16550 driver that checks the status register before each byte costs twice what a paravirtual console would (one notification per line). The busy guest's report says more in three lines than any profiler: almost all exits are IOIO, on ports 0x43 and 0x40, in a ratio of 1 to 2: a latch command and two reads, repeated. That pattern is "polling the PIT". R1 R5

How the hardware actually does it

On an AMD processor, VMRUN is a single instruction that does what Figure 1 shows: it saves host state to the host-save area, loads the guest state from the VMCB, applies the control area (intercepts, ASID, event injection), and starts executing the guest. A #VMEXIT does the reverse, writing exit information into the control area. The VMCB is ordinary memory that the hypervisor reads and writes with normal instructions, but the processor may cache parts of it ("VMCB clean bits" let the hypervisor say which parts it has not changed). On Intel, the VMCS is opaque: its fields have encodings and are accessed with VMREAD and VMWRITE, and the processor may keep the active VMCS inside the CPU. D1 D2

Under QEMU TCG none of this is hardware. QEMU's CPU emulator implements SVM in software: VMRUN and #VMEXIT are emulated, and the guest's instructions are translated like any others. The logic the lab tests (which events exit, with which codes and information, which states VMRUN refuses) follows QEMU's model of the APM. The timings (milliseconds per run, CPU percentages) are properties of the emulator and say nothing about exit costs on silicon. R1

Untested on hardware

The hypervisor has run only under QEMU 8.2.2 TCG with -cpu qemu64,+svm,+npt. It has not run on an AMD processor, and there is no Intel VMX version: QEMU's TCG does not emulate VMX, and the build container has no KVM to nest under. The curriculum's milestone V2 says to "develop under nested virtualization on a Linux KVM host"; do that before claiming V2 on real hardware, and expect differences in the consistency checks and in fields QEMU does not model (for example the VMCB clean bits).

Safety

A hypervisor runs at the highest privilege the machine has. A bug in a VMCB or in the host-save area set-up can crash or hang the computer, and an IOPM that lets a guest touch real ports can reprogram real devices. Develop in QEMU or under nested virtualization; on real hardware, use a spare machine with nothing on its disks you need, and keep the IOPM fully set unless you deliberately pass a port through.

Worked example

1. A VM-entry failure, explained from its code (the exam's question P). The hypervisor prints: VMRUN refused the guest state: exit code ffffffff (SVM_EXIT_ERR, -1). Step 1, identify the code: EXITCODE is a 64-bit field; the low 32 bits are all ones, which is −1 as QEMU stores it (Listing 6 decodes it as "invalid_guest_state"). Step 2, the meaning: VMRUN's consistency checks failed; the guest never ran a single instruction (R3 shows 1 exit, 0 ms). Step 3, find the rule: SVM gives no detail, so compare the VMCB with the APM's list of checks; the hypervisor's own log line says which field was broken on purpose (ASID 0 in the second case: ASID 0 is the host's). Step 4, confirm the host survived: the last guest in R3, with a valid state, prints its message. On Intel the same situation reads differently: exit reason 0x80000021 = bit 31 (entry failure) + basic reason 33 (invalid guest state), and the SDM's chapter on VM entries lists the guest-state checks to compare against. R3 R6 D3

2. Counting the hello guest's exits. The guest prints "hello from a 64-bit guest\n" (26 characters), "my hypervisor says it is \"" (26), "DR404-tinyHV" (12) and "\"\n" (2): 66 characters. For each, puts reads port 0x3FD once (the model always says "ready") and writes port 0x3F8 once: 132 IOIO exits, 66 per port. Plus one CPUID (the signature) and one VMMCALL (the exit): 134, as R1 reports. R1

3. Counting the busy guest's PIT exits. guest_busy programs the PIT (one write to 0x43, two to 0x40), reads it once before the loop, then once per poll; each read is one write to 0x43 and two reads of 0x40. With N polls (the guest prints N), port 0x43 sees 1 + (N + 1) = N + 2 exits and port 0x40 sees 2 + 2(N + 1) = 2N + 4. Check this against R5: the counts in the output satisfy both formulas exactly, whatever N was in the run. R5

4. The triple-fault guest. It prints a 33-character line (66 IOIO exits) and executes ud2. The processor raises #UD; with IDTR limit 0 it cannot deliver it, which raises #DF; that cannot be delivered either, so the processor shuts down: on SVM, a SHUTDOWN exit (code 0x7F). R2: 66 IOIO + 1 SHUTDOWN = 67 exits; the next guest then runs normally. R2

Where the analogy breaks


    

  • The guest is frozen, not interrupted. A principal who calls the head teacher waits on the line and remembers the call. A guest at a VM exit is stopped between two instructions and does not know it was stopped; only time has passed.
    • 

  • The agreement is enforced by hardware, not trust. In a school, an agreement can be broken. In guest mode, an intercepted event always exits; the guest cannot opt out.
    • 

  • The real principal does the job by pretending. The head teacher really rings the bell. The hypervisor usually does not touch real hardware at all: the guest's "UART" and "PIT" exist only as a few variables in the hypervisor.
    • 




Common mistakes and debugging


    

  • Forgetting to advance RIP. Symptom: the same exit repeats forever (the run reaches "too many exits"). Fix: IOIO uses EXITINFO2; CPUID +2, HLT +1, VMMCALL +3 (when the processor provides no next-RIP field, as here).
    • 

  • Losing general registers. Symptom: the guest misbehaves after its first exit. Cause: VMRUN saves only RAX, RSP, RIP and a few others. Fix: Listing 2.
    • 

  • Comparing the failure code as 64-bit −1. Symptom under QEMU: "unhandled exit ffffffff". Fix: compare the low 32 bits (Listing 3, line 293), and test on hardware before relying on either.
    • 

  • VMRUN intercept clear. Symptom: VMRUN fails with −1 (R3, first case). The APM requires it set. Fix: always intercept VMRUN.
    • 

  • An IOPM with holes. Symptom: the guest reprograms the host's real PIT or PIC; the host's timer stops. Fix: start with every bit set (Listing 3, line 223) and open ports one by one, on purpose.
    • 

  • Waiting in HLT with interrupts off. Symptom: a guest that halts with IF = 0 hangs the host. Fix: detect it ("halted forever") and stop the guest.
    • 

  • Debugging blind. Print the raw fields of the first few exits (trace=6 in R1) and compare them with what you expect, before reading any more code.
    • 




Transition box

Where you came from: F4-39, where your kernel was the guest; F4-38's concepts; your own boot code, IDT, PIC and PIT. C1 What carries over: the boot path, console and interrupt code are reused unchanged; CPUID, port I/O and the PIT are the same devices seen from the other side. What changes: your kernel now owns a second processor state in a VMCB, every guest device access is a function call in your kernel, and "it crashed" becomes an exit code you can count. What comes next: F4-41 gives the guest its own memory through nested paging, injects real timer interrupts, and boots F4-39's kernel, unchanged, as the guest.

Summary


    

  • SVM is enabled by EFER.SVME after checking CPUID and VM_CR; VMRUN needs a host-save area.
    • 

  • One VMCB page describes a virtual CPU: what to intercept, and the guest's processor state.
    • 

  • The run loop is: load registers, CLGI, STI, VMRUN, STGI, save registers, count the exit code, handle it, repeat.
    • 

  • Handlers for IOIO, CPUID, HLT, VMMCALL and SHUTDOWN are short; device models (UART, PIT) live in the hypervisor.
    • 

  • A VM-entry failure on SVM is exit code −1 (QEMU stores 32 bits of it); on VMX, exit reason bit 31 plus a basic reason, or a VM-instruction error number.
    • 

  • Exit counts by reason and by port diagnose a slow guest: 180,000 to 215,000 PIT exits for a polled two-second wait, 268 exits for a halted one.
    • 

  • Everything here ran on QEMU's software model of SVM; untested on hardware.
