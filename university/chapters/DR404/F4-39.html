Story hook

In the rented wing of the big school, a new principal arrives. She has two choices. She can behave as if the wing were a whole school: ring her own bell by standing in the corridor and staring at the clock, ask the building for a fresh timetable every few minutes, and wonder why the caretaker looks tired. Or she can look at the door plate, see "Wing B — property of the main school", and adapt: borrow the building's clock instead of building her own, tell the caretaker when her rooms are empty so the heating can be turned down, and go to sleep in her office when nothing is happening, instead of pacing.

An operating system running in a virtual machine faces the same choice. Every busy loop it runs, every timer it polls, burns real CPU time that another guest could have used. This chapter turns your kernel into a good guest: it reads the door plate (the hypervisor-present bit and the hypervisor's signature), idles by halting, and keeps time with the help of the host. The lab measures the difference on a real emulator: an idle guest that halts costs a few per cent of one host CPU; the same guest polling a timer costs about 90 %.

What you will be able to do

  • Detect a hypervisor from inside a kernel through the CPUID hypervisor-present bit and the hypervisor leaf range, and name it from its signature.
  • Explain why a guest must halt when idle, never busy-poll a timer, and prefer paravirtual devices and clocks, using exit counts and host CPU time as evidence.
  • Measure the host CPU time an idle guest costs and compare two idle strategies.
  • Implement the reader side of a paravirtual clock record (version counter, scale and shift) and show why a careless reader can see time go backwards.
  • Evaluate which parts of milestone V1 a given kernel passes, and which need a KVM host to test.
Jargon box
Hypervisor-present bit
Simple words: a bit that a hypervisor sets in the CPU's self-description to say "you are in a virtual machine". Analogy: the door plate that says "Wing B, property of the main school". Precise: bit 31 of ECX returned by CPUID leaf 1; real processors return 0 there, and hypervisors that want to be found return 1 and then answer the leaf range starting at 0x40000000. D1 R1
Hypervisor signature
Simple words: a 12-character name returned by the CPU instruction that describes the processor, when the hypervisor answers it. Analogy: the name of the building's owner on the plate. Precise: the bytes of EBX, ECX and EDX returned by CPUID leaf 0x40000000, for example "KVMKVMKVM" followed by zero bytes for KVM and "TCGTCGTCGTCG" for QEMU without acceleration; EAX gives the highest hypervisor leaf. D2 R1
Paravirtual clock (kvmclock)
Simple words: a clock the hypervisor keeps up to date in the guest's memory, so the guest can read the time without asking. Analogy: the building's master clock, with a repeater in each wing. Precise: a per-virtual-CPU record (TSC value, system time at that value, a multiplier and shift to convert TSC ticks to nanoseconds, a version counter) that the guest registers through KVM-specific MSRs; the guest computes the time from the record and the TSC. D3 C1
Seqlock (version counter)
Simple words: a counter that the writer makes odd while it changes a record and even when it is done, so a reader can tell whether what it read was half-changed. Analogy: a "being updated" sign hung on the timetable board while the secretary rewrites it. Precise: a reader copies the version, the fields, then the version again, and retries if the version was odd or changed; the writer increments the version before and after the update. D3 R6
Steal time
Simple words: time when the guest's virtual CPU wanted to run but the host ran something else. Analogy: lesson time lost because the main school borrowed the room. Precise: a per-vCPU counter the hypervisor publishes (KVM's steal-time feature) so the guest's scheduler and accounting can tell real idle time from time taken away. D3 C1
Enlightenment
Simple words: a change in a guest OS that makes it aware of, and cooperate with, its hypervisor. Analogy: the guest principal reading the building's rules and following them. Precise: the use of paravirtual interfaces (clocks, end-of-interrupt shortcuts, TLB-flush hypercalls, synthetic timers) instead of emulated hardware; "Hyper-V enlightenments" is the name used for Hyper-V's set. C1 D4
Balloon device
Simple words: a device through which the host asks the guest to give back memory it is not using. Analogy: the guest school returning empty classrooms so the building can lend them elsewhere. Precise: virtio-balloon: the guest driver allocates pages ("inflates") and tells the host their addresses, which the host can then reclaim. D5 C1
vsock
Simple words: a socket connection between a guest and its host that needs no network set-up. Analogy: an internal phone line between the wing and the main office. Precise: the virtio-vsock device and its socket address family, addressing endpoints by context ID and port. D5 C1

Layer 1 — the kid explanation

When a program lives inside a pretend computer, it shares the real computer with other pretend computers. If it waits by running in circles, it uses up real time that others need. If it waits by sleeping, the real computer can do something else.

So a polite guest first checks whether it is inside a pretend computer. The processor has a "you are a guest" sign it can read. If the sign is there, the guest reads the name of its host and uses the shortcuts that host offers: a ready-made clock, simple devices, and a way to give back memory it does not need.

Layer 2 — the student explanation

Detection

On x86 the hypervisor answers the CPUID instruction on the guest's behalf (F4-40 intercepts it). By convention it sets bit 31 of ECX in leaf 1, which real processors leave at 0, and answers leaves starting at 0x40000000: EAX gives the highest hypervisor leaf, and EBX, ECX and EDX hold a 12-byte vendor signature. Under QEMU without acceleration the lab's kernel saw signature "TCGTCGTCGTCG" with maximum leaf 0x40000001; with the hypervisor-present bit hidden (-cpu qemu64,-hypervisor) it reported "none"; and a user program in the build container saw "KVMKVMKVM", the KVM signature defined in Linux's <asm/kvm_para.h>. D2 R1 R2 R5

The bit is a convention, not a guarantee. A hypervisor can hide itself (R2 is QEMU doing exactly that on request), and a bit can be set by a hypervisor you have never heard of. A good guest therefore treats an unknown signature as "some hypervisor": it still halts when idle and still distrusts timing loops, but uses no vendor-specific interface. C1

Idle: halt, do not poll

A native kernel that busy-waits only wastes its own CPU's power. A guest that busy-waits takes a host CPU away from every other guest and host task. Worse, the most tempting busy-wait in a hobby kernel, reading the PIT counter in a loop, is made of I/O instructions, each of which a hardware hypervisor must intercept and emulate: F4-40 counts between 180,000 and 215,000 such exits in two seconds for one guest. The rule in the curriculum's list of guest rules is short: halt when idle; never busy-poll the PIT. C1

The lab measures both strategies on the same kernel: 300 timer ticks (3 s at 100 Hz) waited by HLT cost the QEMU process between 0.1 and 0.25 s of host CPU (4–7 % of one CPU across this build's runs); the same wait by polling cost about 3 s (82–92 %). The poll loop ran about 15 million times to wait 300 ticks; the halt loop ran 300 times, once per interrupt. These figures come from QEMU's software emulation, where halting lets QEMU's thread sleep; on a hardware hypervisor HLT causes a VM exit and the hypervisor deschedules the vCPU, with the same effect on the host's load. R3 R4

Time: why the TSC is not enough

A native kernel calibrates the TSC against a known timer (Listing 1 counts TSC ticks over 0.2 s of PIT interrupts) and converts TSC deltas into nanoseconds. In a guest, both sides of the calibration are virtual: the PIT interrupts are delivered when the hypervisor decides, and the guest may be descheduled in the middle. This build's runs calibrated the same emulated TSC at values from 2,058,789,330 Hz to 2,117,315,250 Hz: a 3 % spread that would make a native kernel's clock drift by about a minute and a half per hour. The outputs below show the latest run's values; compare them. R3 R4

The cure is a paravirtual clock. Under KVM, the guest gives the hypervisor the guest-physical address of a small record per vCPU (through a KVM-specific MSR); the hypervisor fills in a TSC value, the system time in nanoseconds at that TSC value, and a multiplier and shift that convert TSC ticks into nanoseconds. To read the time, the guest reads the TSC, subtracts the recorded TSC value, scales the difference, and adds the recorded time. The hypervisor refreshes the record when it matters (after migration, after the vCPU moves to another host CPU, when the host's clock is adjusted), so the guest needs no calibration at all. The build container's own Linux kernel was offered exactly this clock: kvm-clock appears next to tsc among its clock sources, and the KVM feature leaf advertises CLOCKSOURCE2 and CLOCKSOURCE_STABLE_BIT. D3 R5

Devices: prefer paravirtual ones

The same container shows what a well-configured guest looks like from the inside: its disks are virtio-blk, its network is virtio-net, it has a balloon device to return memory, a vsock device to talk to its host, and a virtio-rng device to get entropy. Five of its ten virtio devices negotiated event-index notification suppression (the EVENT_IDX feature), which lets driver and device skip notifications the other side does not need. Each skipped notification is one fewer exit. R5 D5

Layer 3 — the engineer's depth

Reading a record the writer is changing

The paravirtual clock record is shared memory written by one party (the hypervisor) and read by another (the guest) without a lock: the hypervisor cannot wait for the guest. The protocol is a seqlock. The writer increments version (making it odd), writes the fields, and increments it again (even). The reader reads version, then the fields, then version again, and keeps the result only if both reads were equal and even; otherwise it retries. On real hardware the reader also needs read barriers between the steps so that the processor does not reorder the loads; the model in Listing 3 is single-threaded and replays one interleaving deterministically, so it shows the logic, not the memory ordering. D3 R6

R6 is the failure the protocol prevents. The host refreshes the record at TSC 1,000,000,000. A careless reader catches it half-written: the new TSC timestamp, but the old system time (0 ns). Its result, 238,095 ns, is earlier than the 475,714,285 ns it read a moment before: time went backwards by almost half a second. The careful reader sees version 3 (odd), rejects the copy, retries and gets 476,428,571 ns, after the earlier read. R6

Fixed-point scaling

Converting TSC ticks to nanoseconds with a division per read would be slow. The record therefore carries a 32-bit multiplier and a signed shift: ns = ((delta shifted by shift) × mul) >> 32. For a 2.1 GHz TSC, Listing 3 computes mul = 4,090,445,043 and shift = −1. Over one hour of ticks, the result is 713 ns short of exact arithmetic: about 0.2 parts per billion. The guest must still guarantee monotonicity across vCPUs: if two vCPUs' records disagree slightly, a thread that moves between them could see time go backwards. That is what KVM's stable bit (advertised in R5) is about, and why the curriculum's acceptance test for V1 requires 10 million reads "on all vCPUs, including while the host is loaded". R6 D3 C1

Not verified — check before relying on this

The layout and semantics of KVM's clock record (the fields version, tsc_timestamp, system_time, tsc_to_system_mul, tsc_shift, the formula with the shift applied before the multiplication, the MSR used to register the record, and the meaning of the stable bit) are written from memory of the Linux kernel's documentation "KVM-specific MSRs", which was not opened in this build. Listing 3 models them; it does not prove that KVM uses exactly these fields. The feature names CLOCKSOURCE, CLOCKSOURCE2 and CLOCKSOURCE_STABLE_BIT and their bit numbers are verified: they come from <asm/kvm_para.h> in this build and R5 decodes them. Before writing a kvmclock driver, read "KVM-specific MSRs" and "KVM CPUID bits" in the Linux kernel documentation.

Other hypervisors

Each hypervisor family has its own guest interfaces. The curriculum's table 12.3 lists them: Hyper-V publishes a reference TSC page and synthetic timers and offers VMBus devices, described in its Top Level Functional Specification; Xen publishes per-vCPU time information in shared memory and uses grant tables and event channels for its split drivers; VMware documents TSC frequency leaves and offers vmxnet3 and PVSCSI devices. A portable kernel keeps these behind one clock abstraction (B8's) and one device-discovery path, chosen by signature at boot. C1 D4

Not verified — check before relying on this

The signatures "Microsoft Hv", "XenVMMXenVMM" and "VMwareVMware", and the interfaces named in the paragraph above, are copied from the curriculum's table 12.3 (a map, AH-4); none was observed in this build. Listing 2 marks them "unverified signature" in its output names. Check them in the Hyper-V TLFS ("Hypervisor discovery"), the Xen public headers (arch-x86/cpuid.h) and VMware's open-vm-tools sources before relying on them.

Other rules of thumb

Prefer the x2APIC (MSR access, which hypervisors can accelerate) and the TSC-deadline timer (one MSR write per timer event, instead of reprogramming a counter); give the host free memory back through virtio-balloon or virtio-mem; feed your entropy pool from virtio-rng instead of timing jitter, which is less trustworthy inside a VM; and use vsock rather than a virtual network for host communication. Each rule removes either exits or wasted host resources. C1

How the hardware actually does it

CPUID is an unprivileged instruction, so in a hardware-assisted guest it must be intercepted to be virtualized; on Intel VMX, CPUID causes a VM exit unconditionally, and on AMD SVM the hypervisor sets the CPUID intercept bit in the VMCB (F4-40 does). The hypervisor then returns values of its choice: it sets the hypervisor-present bit, answers the 0x40000000 range, and hides features it does not want the guest to use (F4-40 hides SVM itself, so the guest cannot try to become a hypervisor). Under QEMU TCG there is no hardware interception at all: QEMU's CPU emulator computes the answer, which is why R1 shows TCG's own signature. D1 D6 R1

HLT is privileged; on a hardware hypervisor its intercept makes the vCPU exit, and the hypervisor marks the vCPU blocked until an interrupt is due for it, then lets the host scheduler run something else. That is the mechanism behind the near-zero idle cost the curriculum's acceptance test asks for. IN and OUT to the PIT are intercepted through the I/O permission bitmap (F4-40), and a timer emulated in a user-space VMM costs a further switch from the kernel to that process. D6 C1

Not verified — check before relying on this

"CPUID always exits on VMX" and the HLT-intercept behaviour of KVM are from memory of the Intel SDM Vol. 3 chapter "VMX Non-Root Operation" (instructions that cause VM exits unconditionally) and of KVM's design; not checked in this build. The DR404 hypervisor's CPUID and HLT intercepts on AMD SVM are verified in QEMU's model (F4-40, R2 of that chapter).

Worked example

1. Reading a signature by hand. Suppose CPUID 0x40000000 returns EBX = 0x4b4d564b, ECX = 0x564b4d56, EDX = 0x0000004d. x86 is little-endian, so the bytes of EBX in memory order are 4b 56 4d 4b: "KVMK". ECX gives 56 4d 4b 56: "VMKV". EDX gives 4d 00 00 00: "M" and three zero bytes. Together: "KVMKVMKVM" padded with zeros, the KVM signature. Listing 2 does the same with memcpy of the three registers in the order EBX, ECX, EDX. D2

2. What polling costs. R4: about 15 million poll iterations in 3 s; each iteration latches and reads the PIT through three port accesses (one OUT, two INs), about 45 million port accesses. Under a hardware hypervisor that intercepts the PIT ports, that would be 45 million VM exits for three seconds of "doing nothing". (F4-40's forensic lab measures the exit count of a smaller poll loop directly.) The halting guest's loop ran 300 times: one wake-up per tick. R4 R3

3. The scale for 2.1 GHz. We need ns = delta × 109 / (2.1 × 109) = delta × 0.476…. With shift = −1, delta is halved first, so mul/232 must be 0.952…; 0.952380952 × 4,294,967,296 ≈ 4,090,445,043, the value R6 prints. One second of ticks (2.1 × 109) gives 999,999,999 ns: the truncation loses at most one nanosecond per conversion plus the rounding of mul, 713 ns over an hour. R6

Where the analogy breaks


    

  • The door plate can lie, or be missing. A principal can trust the plate on the door. A guest cannot fully trust the hypervisor-present bit: a hypervisor can hide it (R2) or present another's signature. Detection is a hint for performance, never a security decision.
    • 

  • Sleeping is not "doing nothing" for the building. A principal asleep in her office costs nothing. A halted vCPU still holds memory, and each wake-up for a timer tick costs exits; a tickless guest kernel (one that programs the next timer event instead of ticking periodically) is better still.
    • 

  • The master clock is read, not asked. In a school, "using the building's clock" means walking to it. A paravirtual clock is a record in the guest's own memory, read without any exit; asking the hypervisor every time would defeat the purpose.
    • 




Common mistakes and debugging


    

  • Reading hypervisor leaves without checking the bit. Symptom: garbage "signatures" on bare metal. Cause: on real processors, leaves in the 0x40000000 range are not defined for this use. Fix: test CPUID.1:ECX[31] first (Listing 2, line 25).
    • 

  • Reading leaves beyond the maximum. Symptom: wrong feature bits on some hypervisors. Fix: compare with EAX of 0x40000000 (Listing 2, line 40).
    • 

  • Idling with interrupts disabled. Symptom: HLT never returns, or the vCPU is reported as "halted forever" by your hypervisor (F4-40 reports exactly that). Fix: sti; hlt as a pair, with the timer running.
    • 

  • Calibrating once and trusting it forever. Symptom: wall-clock drift of seconds per hour in a guest. Cause: a calibration taken while the vCPU was descheduled (compare the calibrated rates of R1 to R7). Fix: use the hypervisor's clock or its documented TSC frequency.
    • 

  • Ignoring the version counter. Symptom: rare time jumps backwards, worse under host load. Cause: a torn read of the clock record (R6). Fix: the seqlock loop, with barriers.
    • 

  • Measuring the guest's own idle time instead of the host's. A polling guest reports itself "idle". Measure from the host: process CPU time (cputime.py), or the hypervisor's exit counts.
    •

Summary


    

  • A guest finds its hypervisor through CPUID.1:ECX[31] and the 0x40000000 leaf range; the signature names it.
    • 

  • Detection is a performance hint; unknown hypervisors still get generic good behaviour.
    • 

  • Halt when idle: measured under QEMU TCG, a few per cent of one host CPU with HLT against about 90 % when polling the PIT.
    • 

  • Calibrating the TSC in a guest is unreliable (up to 3 % spread between runs); paravirtual clocks publish the conversion instead.
    • 

  • A paravirtual clock record is read with a seqlock; a torn read made time go backwards by almost half a second in the model.
    • 

  • Prefer paravirtual devices with notification suppression, balloon memory back, take entropy from virtio-rng, talk to the host over vsock.
    • 

  • The build container is a KVM guest with kvm-clock and virtio devices, a live example of these rules.
