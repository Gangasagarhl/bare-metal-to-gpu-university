Story hook

Imagine a large school that rents one wing to a second, smaller school. The small school has its own principal, its own timetable and its own classes. Its principal believes they run everything: they ring the bell, unlock rooms and call the caretaker. But the wing belongs to the large school, and so do the real bells, keys and caretaker. When the small school's principal reaches for the real bell, the large school's principal must step in, ring a bell that only the wing hears, and step back out, so quickly and so faithfully that the small school never notices.

That is a virtual machine. The small school is the guest operating system; the large school's principal is the hypervisor. The whole art is deciding which of the guest principal's actions may go straight through ("teach a lesson in your own room") and which must be caught and handled above ("ring the building's bell"). This chapter is about that decision: why it was hard on early x86 processors, how three generations of engineers solved it, and what it costs. And a surprise: the computer that built this chapter is itself a guest. You will see its hypervisor's name in a real run.

What you will be able to do

  • Explain trap-and-emulate and the Popek and Goldberg condition, and identify a sensitive instruction that is not privileged in a given instruction set.
  • Compare the three ways of virtualizing a processor that lacks the condition: binary translation, paravirtualization and hardware-assisted virtualization (VMX root and non-root, SVM guest mode, Arm EL2, RISC-V HS mode).
  • Compute the number of memory reads of a two-dimensional (nested) page walk for any number of guest and nested levels, and explain why large pages and TLBs matter more inside a virtual machine.
  • Classify I/O and interrupt virtualization techniques (emulated devices, paravirtual devices, pass-through with an IOMMU, virtual interrupt controllers) by what causes a VM exit.
  • Diagnose, from a monitor's trap log, a guest that loses updates because one sensitive instruction never traps.
Jargon box
Virtual machine (VM)
Simple words: a computer made of software, running on a real computer, that an operating system can use as if it were real. Analogy: the small school in the rented wing. Precise: an efficient, isolated duplicate of a real machine, in the words of Popek and Goldberg's definition: programs in it behave as on the real machine (equivalence), the monitor keeps control of the real resources (resource control), and most instructions run directly on the processor (efficiency). D1 D2
Hypervisor (virtual machine monitor, VMM)
Simple words: the program that creates virtual machines and stays in charge of the real hardware. Analogy: the large school's principal above the small school. Precise: the software that multiplexes the physical machine among virtual machines and handles the guest events it chooses to intercept; "type 1" hypervisors run on the hardware, "type 2" ones run as part of a host operating system (KVM makes the Linux kernel itself the hypervisor). D2 D8
Guest and host
Simple words: the guest is the operating system inside the virtual machine; the host is the real machine and the software that runs the virtual machine. Analogy: the rented wing and the building that owns it. Precise: guest software runs with the virtual machine's view of the CPU, memory and devices; host software (the hypervisor and, for type 2, its host OS) owns the physical resources. D2
Sensitive instruction
Simple words: an instruction whose effect depends on, or changes, who controls the machine. Analogy: touching the building's bell or master keys. Precise: an instruction that changes the processor's mode or the mapping of resources (control-sensitive) or whose result depends on them (behaviour-sensitive). Popek and Goldberg show that a machine can be virtualized by trap-and-emulate if every sensitive instruction is privileged. D1
Trap-and-emulate
Simple words: run the guest kernel with fewer rights; when it tries something only the real kernel may do, the processor stops it and the hypervisor does the job on its behalf. Analogy: the real principal steps in when the guest principal reaches for the real bell. Precise: deprivilege the guest kernel so that every privileged instruction traps to the monitor, which updates the virtual machine's state (a virtual interrupt flag, virtual control registers) and resumes the guest after the instruction. D1 D2
Binary translation
Simple words: rewrite the guest kernel's code on the fly so that the troublesome instructions are replaced before they run. Analogy: an assistant who reads the guest principal's notes before they are carried out and replaces "ring the bell" with "ask the real principal". Precise: the monitor translates guest kernel code into an instruction stream that is safe to run, emulating sensitive instructions in the translation; user-mode guest code runs directly. Early VMware used this on x86. D3
Paravirtualization
Simple words: change the guest operating system so that it asks the hypervisor directly instead of touching the hardware. Analogy: the guest principal is told about the arrangement and phones the real principal instead of reaching for the bell. Precise: a guest kernel ported to a virtual interface, using hypercalls and shared-memory devices instead of sensitive instructions and emulated hardware; early Xen required it for x86 guests. D4
Hypercall
Simple words: a call from the guest kernel to the hypervisor. Analogy: the phone line from the guest principal's desk to the real principal. Precise: a deliberate transfer of control from guest to hypervisor with arguments in registers, the virtual-machine counterpart of a system call (VMCALL on Intel VMX, VMMCALL on AMD SVM, HVC on Arm). D6 D7
Hardware-assisted virtualization
Simple words: processor features that let a guest kernel run at its usual privilege level while the hypervisor still catches what it must. Analogy: the building gives the small school its own copy of the office, and an alarm on the few doors that matter. Precise: a new processor mode for guests (VMX non-root operation on Intel, guest mode under SVM on AMD, EL1 under EL2 on Arm, VS mode under HS mode on RISC-V), a per-virtual-CPU control structure (VMCS, VMCB) that says which events to intercept, and VM exits and entries between guest and hypervisor. D6 D7 C1
VM exit and VM entry
Simple words: an exit is the moment the guest is stopped and the hypervisor runs; an entry is the moment the guest resumes. Analogy: the real principal stepping in, and stepping out again. Precise: a VM exit saves the guest's processor state in the control structure, loads the hypervisor's, and records the reason (exit reason on VMX, exit code on SVM) and qualifying details; a VM entry (VMLAUNCH/VMRESUME, VMRUN) does the reverse after checking the guest state. D6 D7 D10
Guest-physical address
Simple words: what the guest believes is a real memory address. Analogy: the room numbers on the small school's own floor plan, which the building translates to its real rooms. Precise: the address produced by the guest's own page tables; the hypervisor translates it to a host-physical address, in software (shadow page tables) or with nested paging. D2 D5
Nested paging (EPT, NPT, stage-2, G-stage)
Simple words: a second set of page tables, owned by the hypervisor, that the processor walks after the guest's own tables. Analogy: the building's master plan, consulted after the small school's floor plan. Precise: hardware translation of guest-physical to host-physical addresses through hypervisor-controlled tables (Intel extended page tables, AMD nested page tables, Arm stage-2 translation, RISC-V G-stage translation), which makes every guest page-table access itself a translated access: a two-dimensional walk. D5 C1
Shadow page tables
Simple words: page tables that the hypervisor builds by combining the guest's tables with its own, before nested paging existed. Analogy: the building's clerk keeps a merged copy of the small school's plan, with real room numbers, and must update it every time the school changes its plan. Precise: monitor-maintained tables mapping guest-virtual directly to host-physical addresses, kept consistent by write-protecting guest page tables and trapping changes and CR3 loads. D2 D3
Nested virtualization
Simple words: a hypervisor running inside a virtual machine, with its own guests. Analogy: the small school rents part of its wing to a third, even smaller school. Precise: running a hypervisor as a guest, with the outer hypervisor emulating the virtualization extensions for it; the usual way to develop a hypervisor (DR404's labs run theirs under QEMU's emulation instead). Layer 1 — the kid explanation

A computer can pretend to be several computers at once. Each pretend computer gets its own operating system, which believes it owns the whole machine. Underneath, one real program, the hypervisor, owns everything and shares it out.

Most of what the pretend computer does is harmless: adding numbers, reading its own memory. That runs at full speed on the real processor. But a few actions would affect everybody: switching interrupts off, changing the memory map, talking to a device. Those must be caught and done carefully by the hypervisor, for that one pretend computer only. The trick is to catch every one of those actions, and nothing more, because each catch costs time.

Layer 2 — the student explanation

The three requirements and the condition

Popek and Goldberg, in 1974, defined a virtual machine monitor by three properties: equivalence (a program runs in the VM as it would on the real machine, apart from timing and resource availability), resource control (the VM cannot use resources the monitor did not give it), and efficiency (a statistically dominant subset of instructions runs directly on the processor, without the monitor). They then proved a sufficient condition for building such a monitor on a "third generation" machine with a user mode and a supervisor mode: the set of sensitive instructions is a subset of the set of privileged instructions. If that holds, the monitor runs the guest kernel in user mode; every sensitive instruction traps because it is privileged, and the monitor emulates it on the virtual machine's state. That is trap-and-emulate. D1 D2

Two kinds of sensitivity matter. A control-sensitive instruction changes the processor's configuration or the allocation of resources: disabling interrupts, loading a page-table root, halting. A behaviour-sensitive instruction behaves differently depending on the configuration: an instruction whose result depends on the current privilege level or on where memory is mapped. Both must trap, because a guest kernel running deprivileged would otherwise see or change the real configuration instead of its virtual one. D1

Why classic x86 failed the condition

The 32-bit x86 architecture had instructions that were sensitive but not privileged. The best known is POPF: executed in ring 0 it loads the interrupt flag from the stack; executed at a lower privilege level it silently leaves the interrupt flag unchanged, and raises no exception. A guest kernel moved down to a lower ring that uses POPF to restore "interrupts off" therefore believes interrupts are off while the monitor never learns about it. Other examples discussed in the literature read state that reveals the real privilege level or the real descriptor tables (for example the selector of the code segment, or the descriptor-table base registers) without trapping. Three answers

Binary translation. The monitor never runs guest kernel code directly. It translates basic blocks of guest kernel code into a cache of safe code, replacing sensitive instructions with calls into the monitor or with inline emulation, and runs the translation. Guest user code, which cannot execute the problematic instructions meaningfully, runs directly. Adams and Agesen describe VMware's translator and compare it with the first hardware support; their measurements, which this chapter does not reproduce, are the classic evidence that the first generation of hardware support was not automatically faster. D3

Paravirtualization. The guest kernel is modified to run on a slightly different, virtualization-friendly interface: instead of POPF it calls the hypervisor (a hypercall) or writes a flag in memory shared with the hypervisor; instead of emulated disk and network controllers it uses shared-memory rings. Xen's original design took this route for x86 guests. Run 5 of R1 shows the idea: the same guest with HCALL in place of POPIF is correct, with 77 traps and 600 hypercalls. D4 R1

Hardware-assisted virtualization. The processor gains a second "world". Guest code runs in it at its normal privilege levels, so the guest kernel runs in its own ring 0 and POPF works on the guest's own flag. A control structure per virtual CPU, filled in by the hypervisor, lists the events that must leave that world: some instructions (CPUID, HLT, I/O instructions), accesses to some registers, exceptions, external interrupts. When one happens, the processor performs a VM exit into the hypervisor with a code that says why. Intel calls the extension VMX (marketed as VT-x) with the VMCS as control structure; AMD calls it SVM (AMD-V) with the VMCB; Arm builds it into the architecture as exception level EL2; RISC-V adds it as the H extension with HS, VS and VU modes. D6 D7 D11 D12 C1

Memory: from shadow tables to nested paging

A guest kernel builds page tables that map guest-virtual to guest-physical addresses, but guest-physical memory is itself an illusion: the hypervisor decides where each guest-physical page really is. Before hardware help, monitors built shadow page tables: tables from guest-virtual straight to host-physical, installed in the real CR3 while the guest runs. To keep them correct, the monitor write-protects the guest's tables and traps every change and every CR3 load, a large source of exits. D2 D3

Nested paging gives the hypervisor its own set of tables from guest-physical to host-physical, walked by the processor itself. The guest owns its CR3 and edits its tables freely, with no exits. The price is the walk: each guest table pointer is a guest-physical address that must itself be translated. With n guest levels and m nested levels, a TLB miss with nothing cached costs n × (m + 1) + m = (n + 1)(m + 1) − 1 reads: 24 for four by four, against four natively. That is why TLB reach, page-walk caches and large pages (in the guest and in the nested tables) matter more in virtual machines. D5 R2

Layer 3 — the engineer's depth

What an exit costs, and how to count exits

Every VM exit saves the guest's state, loads the hypervisor's, runs a handler and enters the guest again; with nested paging and tagged TLBs (VPID on Intel, ASID on AMD) the TLB need not be flushed, but the round trip is still far longer than the instruction that caused it. The engineering rule that follows is simple: count exits by reason. A guest that is slow under virtualization is usually slow because something it does often causes exits: polling a timer through port I/O, touching an emulated device register in a loop, executing CPUID inside a hot path, or taking page faults that the hypervisor must resolve. F4-40's forensic lab is exactly such a count. This chapter gives no exit latency in nanoseconds: that is a property of a named processor and must be measured on it (AH-21). D2 D6 D7

I/O virtualization: four rungs

Devices are virtualized in four ways, from slowest to fastest for the guest:

  1. Full emulation. The hypervisor (or a user-space VMM such as QEMU) models a real device, for example the e1000 network card or an AHCI controller, register by register. Every guest access to a register is an exit (an I/O instruction exit or a fault on an unmapped MMIO page). The guest needs no special driver.
  2. Paravirtual devices. The device is designed for virtual machines: requests travel in rings of descriptors in shared memory, and the guest notifies the device with one write per batch. The virtio family (DR301's F4-05) is the common standard; Hyper-V's VMBus and Xen's split drivers follow the same idea. Event-index notification suppression lets each side skip notifications the other does not need, saving exits.
  3. Pass-through. A physical device (or one of its functions) is given to the guest. Its registers are mapped straight into the guest; its DMA uses guest-physical addresses, so the IOMMU of DR302 (milestone C7) must translate them, with tables the hypervisor controls (VFIO in Linux). Interrupts must be remapped as well.
  4. SR-IOV. A device built to present many lightweight "virtual functions", each of which can be passed through to a different guest.

D2 D13 C1

Interrupts and time

A guest expects an interrupt controller and timers. The simplest hypervisor emulates them: guest writes to the local APIC or the PIC are exits, and the hypervisor injects virtual interrupts at the next VM entry (F4-41 does exactly this with a PIC model). Hardware then took over part of the work: Intel's APIC virtualization and posted interrupts, AMD's AVIC, Arm's virtual GIC CPU interface with list registers and direct injection in GICv4, and RISC-V AIA guest interrupt files let many interrupt deliveries and acknowledgements happen without exits. Time needs care too: a guest's view of the TSC can be offset and scaled by the hypervisor, Arm provides a virtual timer, and paravirtual clocks such as KVM's kvmclock let the guest compute time from a record the hypervisor keeps up to date (F4-39). Nested virtualization and confidential computing

When a hypervisor runs as a guest, its VMRUN or VMLAUNCH instructions must themselves exit to the outer hypervisor, which emulates them by running the inner guest directly on the hardware with merged control structures and merged nested page tables. The Turtles project described the design for x86; KVM supports nested VMX and SVM, and the curriculum's milestone V2 tells you to develop your hypervisor this way on a Linux KVM host. The build container of this university has no KVM device, so DR404's labs use QEMU's software emulation of SVM instead (F4-40). Confidential computing turns the trust relationship around: the guest's memory and register state are protected even from the hypervisor, which can still schedule the guest and handle a limited set of exits. It is listed here as a topic; this course builds nothing with it. D9 C1 R3

How the hardware actually does it

On Intel processors, software enters VMX operation with VMXON, becomes the hypervisor in "VMX root operation", and runs a guest in "VMX non-root operation" with VMLAUNCH or VMRESUME. The VMCS, a memory region read and written only through VMREAD and VMWRITE, holds the guest-state area, the host-state area, the execution controls (which instructions and events cause exits, I/O and MSR bitmaps, the EPT pointer), and the exit-information fields (exit reason, exit qualification). On AMD, EFER.SVME enables SVM; VMRUN takes the physical address of a VMCB, an ordinary 4 KiB page with a control area (intercept bits, exit code and exit information, nested-paging root) and a state-save area. Arm's EL2 has its own system registers (HCR_EL2 decides what traps; VTTBR_EL2 points to stage-2 tables). RISC-V's H extension adds hypervisor CSRs (hstatus, hedeleg, hideleg, hgatp for G-stage translation). D6 D7 D11 D12 C1

Worked example


1. Counting the traps of run 2 (R1). The guest kernel of Listing 1 executes one STI, then 300 iterations of CLI … STI, receives some timer interrupts, each ending in IRET, and finally HLT. All five are privileged, so under the monitor each traps once. R1 reports 75 interrupts. Traps = 1 + 300 + 300 + 75 + 1 = 677, which is the number printed. In run 5, CLI and STI inside the loop are replaced by hypercalls (2 × 300 = 600, as printed), and only STI, the 75 IRETs and HLT trap: 1 + 75 + 1 = 77. Paravirtualization did not remove the monitor's work; it turned 600 traps into 600 cheaper, explicit calls. R1


2. Explaining run 4's numbers. With POPIF ignored in user mode, the virtual interrupt flag set by the first STI is never cleared, so interrupts arrive inside the critical section. R1 shows 599 interrupts and a counter of 300,300 where 300 + 599 × 1000 = 599,300 was expected. The difference is 299,000: 299 of the handler's additions of 1000 were overwritten. Each lost one arrived between the guest's LOAD and STORE: the handler added 1000 to memory, then the interrupted code stored its stale value plus one on top. R1


3. A two-dimensional walk by hand. Take n = 4 guest levels and m = 4 nested levels (Figure 2). The guest CR3 holds a guest-physical address: 4 nested reads translate it, then 1 read fetches the guest's level-4 entry (5 reads). The entry holds the guest-physical address of the level-3 table: again 4 + 1 (10). Level 2: 15. Level 1: 20. The level-1 entry gives the guest-physical address of the data, which needs 4 more nested reads: 24. In general n(m + 1) + m = nm + n + m = (n + 1)(m + 1) − 1. For n = 4 and m = 3 (one nested level removed, as 2 MiB nested pages would) the count is 19; for five-level tables in both dimensions, 35. R2 confirms all five cases by counting reads on real tables. Where the analogy breaks


    

  • The real principal is not always called. In the school, the small school's principal must ask for anything that touches the building. With hardware assistance, the guest kernel changes its own interrupt flag, page tables and most control registers directly in guest mode; the hypervisor is involved only for the events it chose to intercept. The analogy registry already notes this: hardware support makes most actions direct, not relayed.
    • 

  • The guest cannot be "told" about the arrangement in general. A principal can be told about the arrangement. An unmodified guest operating system cannot: paravirtualization requires changing its source code, which is why hardware support, not paravirtualization, became the way to run arbitrary operating systems.
    • 

  • Room numbers are translated twice, at a cost the analogy hides. A floor plan read twice takes a moment; a nested page walk can cost six times the reads of a native one (24 against 4) on every TLB miss that nothing cached. Nothing in a school makes a lookup six times slower.
    • 




Common mistakes and debugging


    

  • "Hardware virtualization makes the guest as fast as native." Symptom: a guest that is much slower than the same OS on bare metal. Cause: exits (I/O polling, emulated devices, timer programming) or nested-walk costs. How to find it: count exits by reason (F4-40) and measure TLB misses where the tools allow it. Fix: paravirtual devices and clocks, fewer exits, large pages.
    • 

  • Confusing guest-physical and host-physical addresses. Symptom: a device under pass-through writes to the wrong memory, or an IOMMU fault (DR302's forensic lab "DMA to nowhere"). Cause: a guest-physical address given to hardware that expects a host-physical one, or the IOMMU not set up for the guest. Fix: the IOMMU tables must translate exactly what the guest believes is physical.
    • 

  • Assuming that "it traps" means "it is handled". Symptom (R1, run 4): the monitor's trap log looks normal, yet results are wrong. Cause: an instruction that should have trapped did not. How to find it: compare against a native run and list the sensitive instructions the guest uses. Fix: translate, paravirtualize, or use hardware support.
    • 

  • Benchmarking a VM on an emulator. QEMU's TCG emulates the CPU in software; timings there say nothing about virtualization overhead on hardware. Every number from this course's QEMU runs is labelled as a measurement on that emulator.
    •

Summary


    

  • A VM monitor needs equivalence, resource control and efficiency; trap-and-emulate works when every sensitive instruction is privileged.
    • 

  • Classic x86 had sensitive, unprivileged instructions such as POPF; a toy version loses 299,000 counts in R1.
    • 

  • Binary translation rewrites guest kernel code; paravirtualization changes the guest to make hypercalls; hardware assistance adds a guest mode with exits chosen by a control structure.
    • 

  • Shadow page tables trap guest table changes; nested paging lets the guest edit its tables freely but costs (n + 1)(m + 1) − 1 reads per uncached walk (24 for 4 × 4).
    • 

  • Devices are emulated, paravirtual, passed through with an IOMMU, or SR-IOV functions; interrupts and time need virtual controllers and paravirtual clocks.
    • 

  • Performance problems in VMs are found by counting exits by reason.
    • 

  • This build container is itself a KVM guest without nested virtualization; DR404's labs therefore use QEMU's emulation of SVM.
    •
