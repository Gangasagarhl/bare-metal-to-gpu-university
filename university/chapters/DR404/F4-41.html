Story hook

Until now the small school borrowed the main school's floor plan: its "room 12" was the building's room 12. That was fine while the small school was a single class run by the real principal's own staff. Now a whole school moves in, with its own floor plan numbered from room 1, and the main school must keep using its own rooms. The building needs a second plan, its own, that says where each of the guest school's rooms really is: "their room 1 is our room 600, their room 2 is our room 601, and their room 3000 does not exist: if they try to go there, call me."

That second plan is the nested page table. In this chapter the hypervisor of F4-40 gets one, plus a virtual interrupt controller and a timer that can wake a sleeping guest, and then it boots a real kernel: F4-39's good-guest kernel, built unchanged. The guest detects "DR404-tinyHV", calibrates its clock, idles with HLT, keeps a monotonic clock over 10 million reads, and, when told to read an address that its hypervisor never gave it, is stopped cleanly with a report of the nested page fault. The chapter also tells the story of a first attempt that crashed the host, and why.

What you will be able to do

  • Implement nested page tables that give a guest its own guest-physical address space, and load a kernel ELF file into it.
  • Implement a virtual interrupt controller and timer interrupt injection through the VMCB's event-injection field, and wake a halted guest.
  • Interpret a nested page fault report: the faulting guest-physical address and the error code.
  • Diagnose a host crash caused by a guest whose addresses were not translated, from QEMU's log, symbol tables and a probe.
  • Evaluate how virtual timer injection distorts a guest's view of time, using the guest's own calibration as evidence.
Jargon box
Nested page table (NPT) and nested CR3
Simple words: the hypervisor's page table that says where each guest "physical" page really is. Analogy: the building's master plan for the guest school's rooms. Precise: on AMD SVM, enabled by the VMCB's NP_ENABLE bit; its root is N_CR3, a host-physical address; entries use the long-mode page-table format and translate guest-physical to host-physical addresses for every guest memory access, including the guest's own page-table reads. Intel's equivalent is EPT, rooted at the EPT pointer. D1 D2
Nested page fault (NPF) and EPT violation
Simple words: the exit that happens when the guest touches guest-physical memory the hypervisor's table does not allow. Analogy: the guest school walks to "room 3000", which does not exist on the building's plan, and the real principal is called. Precise: SVM exit code 0x400 (SVM_EXIT_NPF) with the guest-physical address in EXITINFO2 and an error code in EXITINFO1; on VMX, basic exit reason 48 (EPT violation) with the address in a VMCS field and the access type in the exit qualification. D3 R5
Event injection
Simple words: the hypervisor makes the guest receive an interrupt or exception as if hardware had raised it. Analogy: the real principal rings the small school's bell for them. Precise: on SVM, writing a vector, a type (external interrupt, exception, software interrupt) and a valid bit into the VMCB's EVENTINJ field; the processor delivers the event through the guest's IDT at the next VMRUN. VMX uses the VM-entry interruption-information field. D1 R2
Virtual interrupt controller
Simple words: the hypervisor's imitation of the chip that hands interrupts to the processor. Analogy: the small school's own bell board, run by the real principal. Precise: a software model of an interrupt controller (here, the 8259 PIC's initialisation words, mask and end-of-interrupt) that decides when an injected interrupt is allowed; hardware assistance (APIC virtualization, AVIC, GICv4) moves part of this into the processor. C1
Guest-physical memory
Simple words: the memory the guest believes is its RAM, starting at address 0. Analogy: the guest school's rooms, numbered from 1 on its own plan. Precise: the address space produced by the guest's page tables and translated by the nested table; in the lab, guest-physical 0–32 MiB is one host buffer at host-physical 0x600000. R1
Lost ticks
Simple words: timer interrupts the guest should have received but did not, because it was not running at the time. Analogy: bells that rang while the small school's staff were out of the building. Precise: when a periodic virtual timer comes due while the vCPU is not running or cannot take interrupts, the hypervisor must either deliver the missed ticks later (catch-up) or drop them; either choice distorts a guest that counts ticks to measure time. D4 R3

The idea in pictures

Layer 1 — the kid explanation

A guest operating system thinks its memory starts at 0. The real memory at 0 belongs to the hypervisor. So the hypervisor keeps a second map that turns every guest address into a real one. The processor reads both maps by itself: first the guest's own map, then the hypervisor's. If the guest asks for an address the hypervisor never gave it, the processor stops it and tells the hypervisor exactly which address it wanted.

A real operating system also needs a clock that ticks. The hypervisor keeps an imaginary clock for the guest, and when it is time for a tick, it slips an interrupt into the guest right before letting it run again.

Layer 2 — the student explanation

Giving the guest its own memory

F4-40's guests used the host's own page tables, so every guest address was a host address: no isolation at all. Listing 1 gives the guest a 32 MiB buffer of host memory (2 MiB aligned, at host-physical 0x600000) and builds a nested page table that maps guest-physical 0–32 MiB onto it with sixteen 2 MiB pages. Every other guest-physical address is not present. Then it sets NP_ENABLE and N_CR3 in the VMCB. From now on, the guest's CR3 holds a guest-physical address, the guest's page-table entries hold guest-physical addresses, and the processor translates all of them through the nested table. D1 R1

Playing the boot loader

QEMU loaded F4-39's kernel with its Multiboot loader. Now the hypervisor must do that job. Listing 1's load_guest_elf copies the kernel's loadable segments to their physical addresses in guest RAM, zeroes their .bss, and looks up four symbols in the ELF symbol table. vcpu_init_guest_kernel writes a Multiboot information block with the guest's command line at guest-physical 0x9000, fills in the kernel's boot_magic and boot_info variables, builds an identity map of the guest's first 4 GiB in guest memory at 0x10000, and enters the kernel at its 64-bit entry point long_mode, in long mode with paging on. The next section explains why not at its 32-bit Multiboot entry. R1 shows the guest's own boot log, printed through the hypervisor's UART model: the F4-39 kernel finds "DR404-tinyHV". R1

Interrupts for the guest

F4-39's kernel programs the PIC and PIT, enables interrupts and calibrates its TSC by halting through 20 ticks. A hypervisor that only resumes the guest after HLT (as F4-40 did) never delivers the interrupt the guest is waiting for. Listing 2 adds three pieces: a virtual 8259 that follows the guest's initialisation words (to learn its vector base, 32) and its mask, and sees end-of-interrupt commands; an entry hook, run before every VMRUN, that injects IRQ 0 when a tick is due and the guest can take it; and a halt hook that sleeps on the host until the next tick. R2 shows the result: 221 HLT exits, about as many injected interrupts (221 or 222 in this build's runs: once in a while a tick falls due while the guest is running rather than halted), and one write to port 0x20 per injected interrupt plus one initialisation word. R2

Nested page faults

With the guest kernel's test=touch addr=1073741824, the guest reads one byte at guest-physical 1 GiB. Its own page tables map it (they identity-map 4 GiB), but the nested table does not. The processor stops the guest with exit code 0x400; EXITINFO2 is the guest-physical address, 0x40000000, and EXITINFO1 is the error code 0x100000004. The hypervisor reports both and stops the guest: V3's second acceptance test. R5 C1

Layer 3 — the engineer's depth

Reading the nested-page-fault error code

The low bits of EXITINFO1 follow the format of an ordinary page-fault error code: bit 0 set means the page was present (a protection violation), clear means not present; bit 1 set means a write; bit 2 set means a user-mode access. Bits above 31 add nested-paging information: one says the fault happened while the processor was translating the final guest-physical address, another that it happened while reading the guest's own page tables. R5's 0x100000004 decodes as: not present, read, user (nested walks are treated as user accesses), during the final translation. A fault with the "during the guest's page-table walk" bit would mean the guest's page tables themselves are outside guest RAM, a hypervisor bug rather than a guest bug. D1 R5

Not verified — check before relying on this

From memory of the AMD APM Vol. 2 ("Nested Paging" and the VMCB appendix), not opened in this build: the NPF error-code bits (bit 32 for a fault on the final translation, bit 33 for a fault during the guest's table walk; Listing 2 prints only bit 33), the rule that nested walks are user accesses (so every nested entry needs U/S), the EVENTINJ format (vector bits 7–0, type bits 10–8, valid bit 31), the NP_ENABLE and N_CR3 offsets, and the CPUID bit for nested paging (Fn8000_000A EDX bit 0). The exit code 0x400 is verified (<asm/svm.h>). The runs prove only that QEMU 8.2.2 behaves as these assumptions predict.

Why the guest is entered in long mode: a finding about QEMU

The natural design is to enter the kernel exactly as a Multiboot loader does: at _start, in 32-bit protected mode with paging off, EAX = 0x2BADB002, EBX = the information address. With paging off, every guest address is guest-physical and the nested table should translate it. Under QEMU 8.2.2 it did not. Listing 4 is a probe: a nested table with a 2 MiB hole at 48 MiB, and a guest that reads the hole twice. With guest paging on, the read causes a nested page fault, as expected. With guest paging off, the read succeeds: QEMU used the guest-physical address as a host-physical address. R6

The consequence for the 32-bit entry is drastic, and the forensic lab examines it: the guest's first instructions are fetched from host-physical 0x10000C, which is the hypervisor's own _start, and it clears the hypervisor's .bss. The workaround in Listing 1 is to enter the guest at long_mode with paging already on and page tables built by the hypervisor in guest memory; from then on every guest access is translated. The F4-39 kernel has this second entry point for exactly this purpose, so it still runs unchanged. R7

Not verified — check before relying on this

"Nested paging applies to every guest access, including when guest paging is disabled" is this course's reading of the AMD APM from memory; the APM was not opened in this build. R6 shows that QEMU 8.2.2's TCG model does not do it. Whether this is a QEMU limitation (our belief), a configuration QEMU does not support, or a misreading of the APM has not been settled. The Source Researcher should check the APM's nested-paging chapter, and the course owner may want to check a newer QEMU and real AMD hardware. Until then, enter guests with paging on, as Listing 1 does.

What the virtual timer does to the guest's clock

The guest calibrates its TSC exactly as on QEMU without a hypervisor: count TSC ticks over 20 PIT ticks. In this chapter's runs the result ranged from about 2.10 GHz to 2.48 GHz, while the hypervisor measured the same TSC at about 2.05 to 2.10 GHz. The guest is not lying; its ticks are late. Listing 2 injects a tick only at a VM entry after it is due, and when ticks were missed, it drops them and schedules the next one from "now". Every late or dropped tick lengthens the guest's 0.2 s window, so the guest overestimates the TSC rate: by up to about 10 % in most of this build's runs and by about 20 % in one (2.48 GHz). Compare the calibrated value in each output below with the host's. A guest that keeps time by counting ticks would run slow by the same amount. This is the "lost ticks" problem of virtual timekeeping, and the reason good guests use a paravirtual clock instead of calibrating (F4-39). R1 R2 R3 R4

From here to milestone V3

V3 asks for more than this lab built: your full B-track kernel as the guest, passing B1–B9 and B15's FAT32 tests on a virtio-blk device that the hypervisor emulates; CPUID and MSR filtering; a virtual local APIC timer. The pieces you would add are a virtio-blk device model (the device side of DR301's driver, served from a disk image), an MSR permission map with handlers, and either APIC emulation (exits on the APIC page through a nested page fault, then emulate the access) or x2APIC MSR exits. The structure of this chapter's hypervisor (hooks for I/O, entry, halt and exits) is designed to take them. C1

How the hardware actually does it

With nested paging on, the processor's page walker performs the two-dimensional walk of F4-38: each guest page-table reference is a guest-physical address translated through the nested table, and the final guest-physical address is translated again. TLB entries then cache the combined guest-virtual to host-physical translation, tagged with the guest's ASID, so a guest's TLB contents survive VM exits. The lab uses 2 MiB pages in both dimensions (the guest's identity map and the nested map), which shortens both dimensions of the walk by one level: by the formula of F4-38, (3 + 1)(3 + 1) − 1 = 15 reads instead of 24 on a miss with nothing cached. On Intel, EPT plays the same role, with its own entry format (read, write and execute bits, memory type) and its own exit (EPT violation, plus "EPT misconfiguration" for illegal entries). D1 D2 D5

Event injection is a processor feature: at VMRUN, after loading the guest state, the processor delivers the event in EVENTINJ through the guest's IDT exactly as if it had happened in the guest, then clears the valid bit. If delivery itself causes an exit (for example a nested page fault while pushing the interrupt frame), EXITINTINFO reports the event so that the hypervisor can re-inject it. D1

Untested on hardware

All runs are under QEMU 8.2.2 TCG with -cpu qemu64,+svm,+npt. No AMD or Intel hardware, no nested virtualization under KVM, no EPT version. The timing numbers (milliseconds, CPU percentages, calibrated TSC rates) are properties of the emulator. The QEMU behaviour in R6 may differ from hardware.

Safety

The forensic run in this chapter crashes its (emulated) host: a guest overwrites the hypervisor's memory. On real hardware the same bug could corrupt anything the host kernel owns, including disk buffers. Develop in QEMU or nested under KVM; on hardware, a spare machine with nothing you need on its disks.

Worked example

1. Where does guest-physical 0x1011EB live? R5's faulting instruction is at guest RIP 0x1011EB (the guest's page tables are an identity map, so that is also its guest-physical address). The nested PD entry is 0x1011EB >> 21 = 0, which maps guest 0–2 MiB to host 0x600000; the offset within the 2 MiB page is 0x1011EB. Host-physical = 0x600000 + 0x1011EB = 0x7011EB. The faulting data address 0x40000000 has PD index 0x40000000 >> 21 = 512: past the 512 entries of the only PD (indices 0–511), so the walk stops at PDPT index 1, which is not present. R5

2. Counting a halting guest's exits. R2 waits 200 ticks after a calibration that waits 20 ticks plus one to align: 221 HLT exits. Each wake-up is an injected interrupt whose handler sends one EOI to port 0x20; with the one ICW1 write at initialisation, port 0x20's count is the injected count plus one (check it in R2: 221 or 222 injected, 222 or 223 writes). Ports 0x21 and 0xA1 see the four initialisation and mask writes each; port 0x43 once and 0x40 twice (programming the PIT). The rest are UART output, two exits per character: about 445 characters in R2's run. Total about 1,350 exits for two seconds of idling, against roughly 140,000 to 175,000 for the polling guest of R4 (the count depends on the run). R2 R4

3. Decoding R5's error code. 0x100000004 = bit 32 + bit 2. Bit 0 = 0: not present. Bit 1 = 0: read. Bit 2 = 1: user access (nested walks count as user). Bit 32 = 1: fault on the final guest-physical address (unverified bit meaning, see the box). Bit 33 = 0: not during the guest's page-table walk. Conclusion: the guest read a guest-physical address the hypervisor never mapped; the guest's own tables are fine. R5

Where the analogy breaks


    

  • The building's plan is consulted for every step, not once. A school consults the master plan once to find a room. The processor consults the nested table for every guest table read, so the guest's own map lookup becomes many lookups (F4-38's two-dimensional walk).
    • 

  • The bell is rung only when someone is in. A real bell rings on time whether or not anybody hears it. A virtual tick can only be delivered when the guest runs and can accept it; late and lost ticks have no counterpart in the school.
    • 

  • "Room 3000 does not exist" is a policy, not a fact. The hypervisor could map it lazily on the first fault (as hypervisors do for memory they allocate on demand), or treat it as a device (MMIO emulation). The analogy suggests an error; the NPF is a general mechanism.
    • 




Common mistakes and debugging


    

  • Guest page tables holding host addresses. Symptom: NPFs at strange guest-physical addresses, or the "during the guest's walk" bit set. Fix: everything the guest sees (CR3, its table entries, GDTR base) holds guest-physical addresses.
    • 

  • Nested entries without U/S. Symptom: NPF with bit 0 set (present) on every access. Cause: nested walks are user accesses (unverified box). Fix: set U/S at every level (Listing 1, lines 60–63).
    • 

  • Injecting with the guest's IF clear, or while an interrupt is in service. Symptom: the guest takes an interrupt inside a critical section or recursively. Fix: check IF and the virtual PIC's state before every injection (Listing 2, line 54).
    • 

  • Never injecting. Symptom: the guest hangs in HLT during calibration. Fix: an entry hook, and a halt handler that sleeps until the next tick.
    • 

  • Trusting the guest's calibrated clock. Symptom: the guest's sense of time is off by tens of per cent. Fix: give the guest a paravirtual clock, or deliver missed ticks.
    • 

  • Entering a guest with paging off under QEMU 8.2.2 TCG. Symptom: the host crashes as soon as the guest runs. Fix: Listing 1's long-mode entry (Layer 3, R7).
    •

Summary


    

  • Nested paging (NP_ENABLE, N_CR3) translates every guest-physical address through a hypervisor-owned table; the guest owns its CR3 and tables.
    • 

  • The hypervisor plays the boot loader: ELF segments, Multiboot information, guest page tables, entry state.
    • 

  • Timer interrupts are injected through EVENTINJ at VM entry when the guest can take them; a virtual PIC tracks base, mask and EOI.
    • 

  • An unmapped guest-physical access is a nested page fault (exit 0x400) with the address in EXITINFO2: report it and stop the guest.

Forensic lab answer key


    

  1. The guest started at 0x10000C. The decoded block shows mov $0x200000,%edi and mov $0x2602000,%ecx: the hypervisor's own __bss_start and __bss_end, matching the hypervisor's _start, not the guest's (whose constants are 0x104000 and 0x113128). The guest is executing the hypervisor's code.
    2. 

  2. (a) Ruled out: the loader's lines show the segments copied into guest RAM, and with the 64-bit entry the same image runs (R1). (b) Ruled out: the instructions are not the guest's. (c) Confirmed: guest-physical 0x10000C was used as host-physical 0x10000C, where the hypervisor itself is loaded; R6 shows QEMU does not translate when guest paging is off.
    3. 

  3. The guest's rep stosb zeroes host-physical 0x200000–0x2602000: the hypervisor's whole .bss, including its page tables, IDT, VMCB and the guest RAM buffer. The guest also stores the magic into the hypervisor's boot_magic. An INTR exit (rip 0x100026, inside the rep stosb) returns to a host whose memory is gone: the host takes a cascade of exceptions (the check_exception lines) and triple-faults; QEMU resets (status 0).
    4. 

  4. Enter the guest with paging on, through tables in guest memory, so that all accesses are translated (Listing 1); or avoid the overlap so that untranslated accesses cannot reach host memory (for example, load the hypervisor at an address the guest never uses), which only hides the problem. Both should be combined with checking QEMU's or the hardware's behaviour first.
    5. 

  5. A probe like Listing 4 run before the first real guest: a nested table with a hole, read once with guest paging off and once on. It costs one boot of a 17-byte guest and settles the question for the platform being used.
