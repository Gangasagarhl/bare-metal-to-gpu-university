Story hook

Analogy

When Sipho joined the cycling club, the secretary gave him a small card for each notice board he wanted to follow: "route", "weather", "spare parts". Every time a new note went up on one of those boards, a copy arrived in his pigeonhole. He kept the cards in his wallet.

One Saturday he cleaned out his wallet and threw away a pile of old receipts. The "route" card was among them. Nothing happened at first; nobody told him. He just stopped getting route notes. The next week he rode the old route alone while the club rode the new one, and he could not understand why the pigeonhole had gone quiet. The board was still there. Amara still pinned the route every Friday. Only the card that connected Sipho to the board was gone.

In rclcpp, the C++ library for ROS 2, every subscription, publisher and timer is an object like that card, and your node must keep it. This chapter writes nodes in C++ and shows exactly what happens when a node throws its card away.

What you will be able to do

  • Write a node as a C++ class that owns its publisher, subscription and timer, in the shape of an rclcpp program, and explain each line.
  • Explain who owns what in an rclcpp program (shared pointers held by the node; the library keeps only weak references) and predict what happens when an owner goes away.
  • Use lambdas that capture this as callbacks safely, and say when such a capture becomes dangerous.
  • Describe how a ROS 2 C++ package is built (package manifest, CMake with ament, colcon) and which details must be checked in the ROS 2 documentation.
  • Diagnose a subscriber that hears nothing because its subscription object was destroyed.
Jargon box
rclcpp
Simple words: the C++ library you use to write ROS 2 nodes. Analogy: the club's rule book and forms, in C++. Precise: the ROS 2 client library for C++; it provides the node class, publishers, subscriptions, services, actions (through a companion library), timers, parameters, logging and executors, built on a common C layer (rcl) and the middleware interface (rmw). D1 D2
Timer (ROS 2)
Simple words: an alarm that calls your function again and again at a fixed period. Analogy: the club's bell every half hour. Precise: an entity created by a node with a period and a callback; when the period elapses, the timer becomes ready and an executor runs its callback; a wall timer measures time with the system's steady clock, other timers can follow the ROS clock (simulated time, F9-44). D2
Spin
Simple words: handing your program's thread to ROS 2 so that it can call your callbacks whenever something is ready. Analogy: sitting by the pigeonhole and reading each note as it arrives. Precise: running an executor's loop, which waits for ready entities (timers, subscriptions with messages, service requests) and executes their callbacks, until shutdown (F9-39). D2
Entity lifetime (rclcpp)
Simple words: a publisher, subscription or timer exists only as long as some part of your program keeps a pointer to it. Analogy: the card in Sipho's wallet. Precise: rclcpp returns entities as std::shared_ptr; when the last shared pointer is destroyed, the entity is destroyed and its callbacks no longer run; holding the pointers as node members ties the entities' lifetime to the node. D2 D3
Weak pointer
Simple words: a pointer that can look at an object without keeping it alive. Analogy: the secretary's list of members: having your name on the list does not keep you in the club. Precise: std::weak_ptr observes an object owned by std::shared_ptrs without contributing to its reference count; lock() returns a shared pointer if the object still exists, an empty one otherwise. D3
Package (ROS 2)
Simple words: a folder with your node's code plus two small files that say how to build it and what it needs. Analogy: a labelled toolbox with a packing list. Precise: the unit of building and release in ROS 2: a directory with a package manifest (package.xml) declaring name, version, licence and dependencies, and a build description (for C++, a CMakeLists.txt using ament's CMake functions). D1
Workspace and colcon
Simple words: a folder that holds several packages, and the tool that builds them all in the right order. Analogy: the club's workshop where all toolboxes are packed in order. Precise: a workspace is a directory with a source folder of packages; colcon is the ROS 2 build tool that discovers the packages, orders them by dependencies, builds each with its own build system, and produces a setup script that makes the results available to the shell. D1

Layer 1 — the kid explanation

In C++, a ROS 2 node is a class. When the node is built, it asks the library for the things it needs: a way to send messages, a way to receive them, an alarm clock. The library hands each one back like a membership card. Your node must keep every card. Then you hand your program over to the library, which watches the clocks and the incoming messages and calls your node's functions at the right moments. If your node loses a card, the library does not shout. That part of the node simply goes quiet.

Layer 2 — the student explanation

The shape of every rclcpp program

A ROS 2 C++ program has the same four steps in main: initialise the library (it reads command-line arguments and sets up the context); create one or more nodes, normally with std::make_shared; spin, which hands the thread to an executor that runs callbacks until the program is asked to stop; and shut down. Everything the node does happens inside callbacks that the executor calls: a timer callback when its period elapses, a subscription callback when a message has arrived, a service callback when a request has arrived. D1 D2

The build container has no ROS 2, so this chapter does two things. Listing 1 is built on mini_rclcpp.hpp, the university's small header that copies the shape of rclcpp (a Node base class, create_publisher, create_subscription, create_wall_timer, shared pointers, a spin function) with simulated time, so the ownership rules can be built and observed here. Listing 3 is the same talker written against the real rclcpp API from memory; it is shown inside an unverified box, and the build only proves that its headers are absent (R3). R1 R3

A node is a class

The recommended style in the ROS 2 tutorials is a class derived from the library's node class. The constructor passes the node's name to the base class and creates the node's entities; the entities are stored as members; the callbacks are member functions or lambdas. Listing 1's Talker creates a publisher on chatter with a queue depth of 10 and a timer of 500 ms whose callback publishes a counter. Listener creates a subscription on the same topic whose callback logs what it heard. D1 R1

Ownership: the node holds the cards

The create functions return std::shared_ptrs. The node keeps them as members; that is the only thing that keeps the entities alive. The library side keeps weak references, which let it find ready timers and subscriptions without owning them. In mini_rclcpp.hpp this is literal: the context stores std::weak_ptrs (lines 35–36) and every use starts with lock(), which fails once the owner is gone. R1 shows the consequence: when main destroys the listener node at 2.0 s, its subscription goes with it, and the talker's next message reaches "0 subscriber(s)". That is the correct, intended behaviour: a node's entities live exactly as long as the node. D2 D3 R1

The mistake that the forensic lab is about is the same mechanism in the wrong place. If the constructor stores the returned pointer in a local variable, the last owner is destroyed when the constructor returns, and the subscription with it. R2 shows a listener that announces "subscribed to chatter" and then never hears a message, while the talker reports "to 0 subscriber(s)" every time. There is no error message: from the library's point of view, a subscription was created and then legitimately destroyed. R2

Callbacks that capture this

The callbacks in Listing 1 are lambdas that capture this (SP102's lambda chapter), so they can call member functions and use members. That is safe because each lambda is stored inside an entity that the same node owns: the node, its entities and their callbacks are destroyed together. It becomes dangerous when a callback is stored somewhere that outlives the node, for example when you hand a lambda capturing this to an object owned by another node; then the callback can run after the node is gone and use a dangling pointer. Address Sanitizer reports such a use as a heap-use-after-free (SP202's F2-29). D3

Logging

rclcpp offers logging macros that take the node's logger and a format string, at levels from debug to fatal; the output carries the level, a timestamp and the node's name. Listing 1's log function prints the same three pieces, with simulated time. Prefer logging over printing to standard output, because the ROS 2 logging system can be configured per node, written to files and recorded. The exact macro names are in the unverified box below. D2

Building: packages, ament and colcon

A ROS 2 C++ node lives in a package: a directory with a manifest (package.xml) that names the package and its dependencies, and a CMakeLists.txt that uses ament's CMake functions to find dependencies, build executables and install them where the ROS 2 tools can find them. A workspace holds several packages under a source directory; the colcon tool builds them in dependency order and writes a setup script. Sourcing that script in a shell lets the ROS 2 command-line tools run your node by package name. All of this is ordinary CMake underneath (SP202's F2-26). D1

What the library holds, and why

The design choice, entities returned as shared pointers and observed weakly, has a reason: it makes destruction safe and predictable. If the library owned the entities, a node could not get rid of a subscription it no longer wants without asking the library; if the node held raw pointers, the library could call into freed memory. With shared ownership by the node and weak observation by the executor, an executor that is in the middle of collecting ready entities can lock its weak reference and keep the entity alive for the duration of one callback, even if the node drops it at the same moment from another thread. The model in mini_rclcpp.hpp takes the same lock() on every use (lines 41, 75, 129, 134, 141). D2 D3

Messages: copies, shared pointers and zero copy

Listing 1's publisher copies each message into every subscription's queue (line 77). Between processes a copy is unavoidable: the message is serialised into bytes (F9-40) and deserialised on the other side. Inside one process, rclcpp can pass a message between publisher and subscribers without serialisation if intra-process communication is enabled, and can avoid copies altogether when the publisher hands over a std::unique_ptr and the subscriber accepts ownership. For large messages (images, point clouds) this changes the cost of a topic by orders of magnitude; the exact conditions are documented by ROS 2 and must be checked for your distribution. D1 D2

Queues and depth

The number 10 in create_publisher(..., 10) and create_subscription(..., 10, ...) is the history depth: how many messages a queue keeps before the oldest are dropped. mini_rclcpp.hpp applies it on the subscription side (line 78: keep the newest depth). In ROS 2 that number is shorthand for a full quality-of-service profile whose other settings take defaults; F9-41 shows why those defaults matter. D2 R1

Components

Because a node is a class, it can be compiled into a shared library and loaded into a container process at run time instead of having its own main. ROS 2 calls such nodes components; loading several components into one process allows intra-process communication between them and reduces the number of processes on a small robot computer. A component is written exactly like Listing 1's classes, plus a registration macro and a constructor that takes node options; check the ROS 2 documentation's "Composition" pages for the exact form. D1

How the hardware actually does it

Nothing in this chapter touches robot hardware directly: a node is a user-space C++ object in an operating-system process (OS201). What matters at the hardware level is where the callbacks run and what they cost. Each callback runs on a CPU core in some executor thread (F9-39); a timer callback is woken by the operating system's timer mechanism, so its punctuality depends on the scheduler and on everything else running on that core; a subscription callback runs after the message's bytes have been received by the network stack or copied through shared memory and deserialised. A node that allocates memory in every callback (a new std::string per message, as Listing 1 does) also takes the allocator's locks and may page-fault; RB304 measures why real-time loops avoid that. D2

Worked example

Predict R1 from Listing 1 and mini_rclcpp.hpp, then check.

  1. main creates both nodes at simulated time 0. Talker's timer has period 500 ms, so its first deadline is 500 ms (line 109 of the header: nextMs = nowMs + periodMs).
  2. spin_for(2000) finds the earliest deadline, 500, sets the clock and runs the timer callback: count 0, "publishing 'hello 0' to 1 subscriber(s)" (one live subscription on chatter). The message is queued in the listener's subscription.
  3. Still at 500 ms, the spin loop runs every queued message: "I heard 'hello 0'". Same at 1000, 1500 and 2000 ms: four messages, four replies.
  4. listener.reset() destroys the last owner of the listener node; its member subscription_ is destroyed with it. The talker logs "listener node destroyed" at t = 2.000.
  5. spin_for(1000) runs the timer at 2500 and 3000 ms: "to 0 subscriber(s)". No reply lines.
  6. Total: 6 messages published, 4 heard. R1 shows exactly these 11 lines. R1

Where the analogy breaks


    

  • Sipho could ask the secretary for a new card and get it the same day. A destroyed subscription is gone; the node must create a new one, and messages published in between are lost unless the publisher keeps history for late joiners (F9-41).
    • 

  • A membership card belongs to one person. A std::shared_ptr may have many owners; the entity lives until the last owner lets go, so a copy of the pointer stored elsewhere can keep a subscription alive longer than you intended.
    • 

  • Sipho reads the notes when he chooses. Callbacks run when the executor chooses, on an executor thread; a callback that blocks delays others (F9-39).
    • 




Common mistakes and debugging


    

  • Entity stored in a local variable. Symptom: the callback never runs; no error (R2). Cause: the last shared pointer died at the end of the constructor. How to find it: check that every create_… result is assigned to a member; the publisher's subscription count is 0. Fix: store it in a member.
    • 

  • Node created but never spun. Symptom: timers never fire, subscriptions never deliver. Cause: nothing runs the callbacks. Fix: add the node to an executor and spin it.
    • 

  • Blocking inside a callback. Symptom: other callbacks of the node are late or never run. Cause: a single-threaded executor runs one callback at a time. Fix: keep callbacks short; move long work to an action or another thread (F9-39).
    • 

  • Lambda capturing this stored outside the node. Symptom: crash or AddressSanitizer "heap-use-after-free" after a node is destroyed. Fix: keep callbacks inside entities the node owns, or capture a weak_ptr to the node and lock it.
    • 

  • Forgetting to source the workspace. Symptom: the ROS 2 tools say the package is not found after a successful build. Fix: source the workspace's setup script in that shell (check the name in the documentation).
    •

Summary


    

  • An rclcpp program initialises, creates nodes, spins, and shuts down; all node work happens in callbacks.
    • 

  • A node is a C++ class that creates its publishers, subscriptions and timers in the constructor and stores them as members.
    • 

  • Entities are returned as shared pointers; the library observes them weakly; an entity lives as long as its last owner.
    • 

  • Storing an entity in a local variable destroys it at the end of the scope: the node silently stops hearing or ticking.
    • 

  • Lambdas capturing this are safe inside entities the node owns, and dangerous anywhere that outlives the node.
    • 

  • Real ROS 2 nodes are built as packages with a manifest, ament CMake and colcon; the exact API and commands must be checked in the documentation.
    •
