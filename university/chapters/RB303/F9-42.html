Story hook

Analogy

Before every club ride, Zanele, the ride leader, works through a checklist. Everyone is here. Each bicycle has been checked: tyres pumped to the pressure on its owner's card, saddle at the height on the card. Only when every bicycle is checked does anyone line up at the start, and only when everyone is at the start line does the group set off. At the end, bicycles are packed away in the reverse order.

One Saturday a new member, Felix, handed in his card with "tyre presure: 4.5". The volunteer pumping the tyres looked for the line "tyre pressure", did not find it, and pumped Felix's tyres to the club's default. Nobody said anything. Felix rode the whole day on soft tyres, slower than everyone, wondering why the ride felt twice as long as the map said.

A robot's start-up is the same checklist: which programs to start, with which settings, in which order, and only then "go". ROS 2 has launch files for the list, parameters for the settings, and lifecycle nodes for the order. This chapter builds all three and then finds Felix's misspelt card in a robot's odometry.

What you will be able to do

  • Declare parameters with a default, a type and a validity rule, override them from a parameter file, and reject invalid changes at run time.
  • Explain a lifecycle (managed) node's states and transitions, and why a robot brings nodes up in the order configure all, then activate all.
  • Read and write a launch description that starts nodes with names, namespaces, parameters and remappings, and say which details must be checked in the ROS 2 documentation.
  • Run the university's parameter and lifecycle model and predict its log line by line.
  • Diagnose a robot whose odometry is wrong by a constant factor because a parameter override was misspelt and silently ignored.
Jargon box
Parameter (ROS 2)
Simple words: a named setting of a node, such as a wheel's radius, that you can change without recompiling. Analogy: the saddle height on a member's card. Precise: a named, typed value owned by a node; a node declares the parameters it accepts (with defaults and optional descriptors such as ranges), values can be set at start-up from the command line, launch files or parameter files, and at run time through services, subject to the node's validation callback. D1
Parameter file
Simple words: a text file with the settings of one or more nodes. Analogy: the stack of members' cards. Precise: a YAML file that maps node names to parameter names and values, passed to nodes at start-up; values for parameters a node has not declared are not applied (unless the node allows undeclared parameters). D1
Launch file
Simple words: a file that starts a whole set of nodes with their settings in one command. Analogy: the ride leader's checklist. Precise: a description, written in Python, XML or YAML, of the processes to start (nodes with package, executable, name, namespace, parameters, remappings), plus arguments, conditions and event handlers; the ROS 2 launch system executes it. D2
Remapping
Simple words: renaming a topic or service from outside a node when you start it. Analogy: telling Felix "your 'route' board today is the one in the hall". Precise: a rule given at start-up that replaces a name the node uses with another name before resolution (F9-37), so that nodes written independently can be connected without changing their code. D2 D1
Lifecycle node (managed node)
Simple words: a node that starts in a "not ready" state and only begins working when told to, step by step. Analogy: a bicycle that goes from "checked" to "at the start line" to "riding". Precise: a ROS 2 node with a standard state machine (primary states Unconfigured, Inactive, Active, Finalized) whose transitions (configure, activate, deactivate, cleanup, shutdown) are requested from outside and executed through callbacks the node implements; publishers of a lifecycle node publish only in the Active state. D3
Lifecycle transition
Simple words: one step from one state to the next, which can succeed or fail. Analogy: "check the bike", "go to the start line". Precise: a named change between primary states; while it runs, the node is in an intermediate transition state, the node's callback decides success or failure, and an error leads to error processing. D3

Layer 1 — the kid explanation

A robot starts many programs at once. A launch file is the list: which programs, with which names and settings. The settings are called parameters, like the size of the wheels. Each program says which settings it accepts and what values are allowed. Some programs also follow a start-up checklist: first get ready, then wait, and only start working when everyone else is ready too. If you misspell a setting's name, the program may not notice. It just uses its default, and the robot is wrong in a quiet way.

Layer 2 — the student explanation

Parameters: declared, typed, validated

A node's behaviour depends on numbers that differ between robots: wheel radius, encoder resolution, publishing rate, sensor frame names. Hard-coding them means recompiling for every robot. ROS 2 parameters move them out of the code. A node declares each parameter it accepts with a name, a type and a default; values can then come from the command line, a launch file or a parameter file at start-up, and from other nodes or tools at run time through the node's parameter services. A node can register a callback that validates every attempted change and rejects invalid ones. D1

Listing 1 models this. OdomNode declares three parameters, each with a default and a rule (lines 30–32): wheel_radius must be positive, ticks_per_rev an integer of at least 1, publish_rate_hz an integer from 1 to 200. Overrides from the parameter file are applied only to declared names (lines 33–39). At run time, set checks type and rule before changing anything (lines 41–51). R1 shows the file's three values accepted, and two run-time changes rejected: "set publish_rate_hz=500 rejected: must be 1..200" and "set wheel_radius=-0.05 rejected: must be > 0 m". R1

Why "declared" matters

Declaration is what lets the node refuse settings it does not understand. It also creates the trap of the forensic lab. When an override's name matches no declared parameter, the value goes nowhere. The model prints one warning line and continues; the declared parameter keeps its default. With a default wheel radius of 0.10 m instead of the intended 0.05 m, every distance the odometry computes is exactly twice the truth (R2). Whether real ROS 2 warns at all in this case, and how loudly, must be checked (Layer 3's box). Either way, the robot runs. R2 D1

Lifecycle nodes

An ordinary node starts working as soon as it is constructed: it publishes, it subscribes, it may command motors. On a robot that is often wrong. The motor driver should not accept commands before its parameters are checked and the hardware is open; the controller should not run before the state estimator publishes; and an operator should be able to stop one part (deactivate) without killing its process. ROS 2's lifecycle nodes, also called managed nodes, give each node a standard state machine (Figure 1). A node starts Unconfigured. configure reads parameters and allocates resources; success leads to Inactive, ready but quiet. activate starts real work: Active. deactivate and cleanup go back; shutdown ends in Finalized. Each transition runs a callback the node implements, which can fail. D3

Listing 1's transition (lines 53–72) is the edge table of Figure 1: a transition is allowed only from its source state; configure calls onConfigure, which may refuse; a failed callback leaves the state unchanged. R1 shows the two protections a robot needs: "transition 'activate' not allowed in state unconfigured" (activation before configuration is refused), and "not active: 100 ticks ignored" (inputs do nothing until the node is active). R1

Bring-up order

With lifecycle nodes, a robot can be brought up in two waves: configure every node (each reads its parameters and checks its hardware), and only if all succeed, activate every node. If any configure fails, nothing has moved. Shutdown runs the other way: deactivate the controllers first, then the drivers. Someone has to request these transitions: a launch file with event handlers, a dedicated lifecycle manager node, or an operator. D3 D2

Launch files

A launch file describes what to start. In ROS 2 it can be written in Python, XML or YAML; the Python form is a function that returns a launch description, a list of actions such as "start this node". For each node the description gives the package and executable, a node name, a namespace (F9-37), parameter files or values, and remappings, which rename the node's topics from outside so that nodes written by different people can be connected without code changes. Parameters as configuration management

A robot's parameter files are its configuration, and they deserve the care of code: version control (SP202's F2-31), review, and a test that loads them. Three practices follow from the forensic lab. First, a node should print the effective value of every parameter once, at configure, as Listing 1's on_configure line does; that single line makes R2's fault visible. Second, defaults should be safe and obviously wrong rather than plausible: a wheel radius default of 0 that fails configure would have stopped the robot at start-up instead of letting it run with a factor-of-two error. Third, overrides for undeclared names should be treated as errors in your own start-up checks, whatever the framework does by default. R1 R2

Run-time changes and consistency

Changing a parameter while a node runs is convenient for tuning, and dangerous for values that other state depends on. Listing 1 copies wheel_radius into the odometry maths only in on_configure (lines 85–92), so a run-time change has no effect until the node is cleaned up and configured again. That is one consistent policy ("structural parameters change only through reconfiguration"); the other is to apply changes immediately in a validated callback. Mixing them without saying which applies to which parameter produces nodes whose reported parameters differ from what they use. D1 D3

Launch at scale

Large robots have launch files that include other launch files, take arguments (which robot, which map, simulation or hardware), and start nodes conditionally. Two engineering consequences: the effective configuration is computed at launch time, so it should be printed or recorded (F9-43 records it in a bag's metadata, where possible); and the launch system starts processes concurrently, so start-up order must come from lifecycle transitions or from nodes that wait for their inputs, never from the order of lines in a launch file. D2

How the hardware actually does it

Lifecycle states map naturally onto hardware: configure opens the device (a serial port, a CAN interface, RB201's F9-14) and checks that it answers; activate enables outputs (motor power, a sensor's streaming mode); deactivate disables them without closing the device; cleanup closes it. That split matters for safety: a motor driver in Inactive holds the hardware open but cannot move the robot, which is the state you want while the rest of the system starts or while an operator investigates. Parameters such as wheel radius and encoder resolution are physical facts about the robot; RB201's odometry chapter shows how to measure them, and those measured values, with their units and the date measured, are what belongs in the parameter file. D3

Safety

On a real robot, never activate a motor driver from a lab exercise without the faculty's rules: simulator first, an emergency stop within reach, a clear zone, speed limits configured, supervision below L3. A lifecycle node in Active means "may move".

Worked example

Predict R1's distances from the parameter file and the encoder ticks.

  1. Parameters: wheel_radius 0.05 m, ticks_per_rev 2048. One wheel revolution moves the robot 2π × 0.05 = 0.314159… m.
  2. The first 100 ticks arrive before activation: ignored (R1: "not active: 100 ticks ignored").
  3. After configure and activate, 6,519 ticks: 6,519 ÷ 2048 = 3.18311 revolutions; × 0.314159 = 1.0000 m. R1: "distance 1.000 m (ticks 6519)".
  4. Another 6,519 ticks: total 13,038: 2.000 m. R1 agrees.
  5. With the misspelt file (R2): radius stays 0.10, so each distance doubles: 2.000 m and 4.000 m. The ratio is exactly the ratio of the default to the intended radius, 0.10 ÷ 0.05 = 2. R1 R2

Where the analogy breaks


    

  • A volunteer reading "tyre presure" would probably ask. Software that ignores undeclared names does not ask; a misspelling is as silent as a missing line (R2).
    • 

  • Zanele's checklist is followed in order by one person. A launch file starts processes concurrently; order comes only from lifecycle transitions or from nodes waiting for their inputs, not from the order of lines.
    • 

  • A bicycle at the start line could still roll if pushed. An Inactive lifecycle node is defined to do nothing with its publishers; but that is a property of the code that implements it, so a careless node can still act in Inactive if its author ignores the state.
    • 

  • Members' cards are read once. Parameters can be changed while the robot runs, by anyone with access to the node's parameter services, which makes them a configuration and a security question (F11).
    • 




Common mistakes and debugging


    

  • Misspelt parameter name in a file. Symptom: behaviour as if the default were used; often a constant-factor error (R2). How to find it: the effective values printed at configure, or the framework's parameter listing for the node; compare with the file. Fix: correct the name; make start-up checks fail on undeclared overrides.
    • 

  • Wrong node name or namespace in the parameter file. Symptom: none of the file's values apply. Cause: the file addresses a node name that does not exist (for example without the namespace). Fix: match the fully qualified node name, or use the documented wildcard (check it).
    • 

  • Order assumed from the launch file. Symptom: occasional start-up failures ("no transform", "no map") that disappear on restart. Cause: processes start concurrently. Fix: lifecycle bring-up, or nodes that wait for their inputs.
    • 

  • Parameters changed at run time but used only at configure. Symptom: the parameter listing shows the new value; the behaviour does not change. Fix: document which parameters need reconfiguration, and enforce it (reject run-time changes to them).
    • 

  • Defaults that look plausible. Symptom: a node runs with a wrong value nobody set. Fix: safe, failing defaults for physical parameters that must be measured.
    •

Summary


    

  • Parameters move robot-specific numbers out of code; nodes declare them with types, defaults and validation.
    • 

  • Overrides for undeclared names are not applied; a misspelt name silently leaves the default in place.
    • 

  • Print effective parameter values at configure, and prefer failing defaults for physical quantities.
    • 

  • Lifecycle nodes have states Unconfigured, Inactive, Active, Finalized; work happens only in Active; transitions can fail.
    • 

  • Bring a robot up by configuring everything, then activating everything; bring it down in reverse.
