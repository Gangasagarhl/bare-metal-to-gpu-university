Story hook

Analogy

At six in the morning the school is dark. Before any teacher arrives, the caretaker, Mr Adeyemi, unlocks the outer door, switches on the lights floor by floor, checks the heating, and tests the fire alarm. Then he unlocks one classroom and the principal walks in and takes over the day. Nobody thanks the caretaker for this, and nobody sees him do it, but if he does not arrive, nothing else happens: the principal stands outside a locked door.

Every PC starts the same way. Between pressing the power button and seeing the first line from your operating system, a program you did not write runs alone on the machine: it finds the memory, starts the devices, picks a disk, and loads a boot loader. This chapter follows that program from its very first instruction. You will stop a virtual PC before it executes anything, read the processor's registers, step through the first eight instructions of a real firmware, and then, a few seconds later, find the page tables that the firmware itself built and walk one address through them by hand.

What you will be able to do

  • Draw the boot chain of an x86 PC from power-on to the kernel and name who owns the machine at each stage.
  • Explain the processor state at reset (real-address mode, the hidden base of CS, the reset vector 16 bytes below 4 GiB) and show it in GDB attached to QEMU.
  • Locate the first instruction inside a firmware image file and disassemble it as 16-bit code.
  • Find the page-table root of a running guest from the QEMU monitor and walk one translation by hand (milestone P3).
  • Diagnose a machine that shows nothing at all after power-on by checking the reset vector, before suspecting memory or the console.
Jargon box
Firmware
Simple words: the program stored on a chip on the motherboard that runs first when the machine is switched on. Analogy: the caretaker who opens the doors in the morning. Precise: software held in non-volatile memory (flash) on the platform that initialises the processor, memory and devices, describes the hardware to the operating system and loads an OS loader; on PCs it is UEFI firmware or, on older machines, a legacy BIOS. D3 D4
Reset vector
Simple words: the fixed address where the processor fetches its first instruction after reset. Analogy: the one door the caretaker always enters by. Precise: on x86, physical address FFFFFFF0h: the processor starts in real-address mode with CS selector F000h, a hidden CS base of FFFF0000h and IP 0000FFF0h; platform logic maps the top of the firmware flash there. D1 R3
Real-address mode (real mode)
Simple words: the old 16-bit way the processor starts, with no memory protection. Analogy: the building before any room has a lock. Precise: the 8086-compatible operating mode an x86 processor enters at reset: 16-bit instructions by default, addresses formed as segment base plus offset, no paging and no privilege checks. D1
Segment base (hidden part of a segment register)
Simple words: a starting address the processor keeps next to each segment register, which it adds to every offset. Analogy: the floor number added to every room number. Precise: the base field of a segment register's descriptor cache; in real mode loading a selector sets base = selector × 16, but after reset CS has selector F000h with base FFFF0000h until the first far jump reloads it. D1
Long mode
Simple words: the 64-bit mode the processor runs in once firmware or the OS has switched it on. Analogy: the full timetable in force, with every room numbered and locked. Precise: the x86-64 operating mode, active when EFER.LMA = 1, entered with paging enabled (CR0.PG), physical address extension (CR4.PAE) and EFER.LME set. D1 D2
Page table (and CR3)
Simple words: the tables that turn the addresses a program uses into real memory addresses; CR3 holds where the top table is. Analogy: the map of lockers: locker number to real cupboard. Precise: on x86-64 with 4-level paging, a tree of 4 KiB tables (PML4, PDPT, PD, PT) of 512 eight-byte entries; bits 47–39, 38–30, 29–21 and 20–12 of a virtual address index the four levels; an entry with the PS bit set in the PDPT or PD maps a 1 GiB or 2 MiB page directly. D1
OVMF
Simple words: a UEFI firmware built for virtual machines such as QEMU. Analogy: a caretaker trained for a model school instead of a real one. Precise: the "Open Virtual Machine Firmware" platform of the EDK II project, which builds UEFI firmware images for QEMU and other hypervisors; this course uses the build shipped in the Ubuntu package ovmf 2024.02-2ubuntu0.10. D7 R2
GDB stub (QEMU)
Simple words: a door in QEMU that lets the GDB debugger stop and inspect the virtual processor. Analogy: a window into the building that lets an inspector watch the caretaker from the first step. Precise: QEMU's implementation of the GDB remote serial protocol (-gdb tcp:…, with -S to hold the CPU at reset), through which GDB reads registers and memory and single-steps the guest. D5 D6

The idea in pictures

Figure 1 is the map for the whole course: eight stages from power-on to your kernel. The firmware owns the first five, the loader the next two, the operating system the last. Each later chapter of OS301 opens one or two boxes. This chapter covers stages 1 and 2 in detail and shows that the firmware is already deep into stages 3 to 5 a few seconds later.

Figure 2 zooms into stage 2. The processor computes the address of its first instruction from two parts, a segment base and an instruction pointer; the platform makes sure that address lands on the last 16 bytes of the firmware file.

Layer 1 — the kid explanation

When a computer is switched on, its memory is empty. The processor does not know where the operating system is, which disk it is on, or even how much memory there is. So the computer keeps a small program on a chip that never forgets, and the processor is built to start reading instructions at one fixed place on that chip. That program is the firmware, the caretaker. It turns things on in the right order, finds the memory, looks at the disks, and finds a boot loader. The boot loader brings the operating system into memory and gives it the keys. From then on the operating system, the principal, runs the day.

Layer 2 — the student explanation

An x86 processor that comes out of reset is in a defined state: most registers are zero, the instruction pointer holds 0000FFF0h, and the code segment register CS holds the selector F000h with a hidden base of FFFF0000h. The processor fetches from base plus offset, so the first instruction comes from physical address FFFFFFF0h, 16 bytes below 4 GiB.D1 The motherboard (here, QEMU's model of one) maps the firmware's flash chip so that its last byte sits at FFFFFFFFh; the last 16 bytes of the firmware file are therefore the first bytes executed.R2 R3

Sixteen bytes are not enough for a firmware, so the first instructions jump backwards into the rest of the image. At that moment there is no usable RAM on a real PC: the memory controller has not been programmed. The first phase of UEFI firmware, called SEC (security), sets up temporary memory (on real processors by using the cache as RAM), and hands over to PEI (pre-EFI initialisation), whose main job is to bring up the real memory. DXE (driver execution environment) then loads drivers for buses and devices and builds the description tables the OS will need; BDS (boot device selection) reads the boot options and starts a boot loader.D3 D4 On the way, the firmware switches the processor from 16-bit real mode to 32-bit protected mode and then to 64-bit long mode, with page tables of its own.

The boot loader is a program that the firmware loads from the disk. It reads the kernel file, prepares memory for it, and jumps to it. After that jump the firmware's boot-time services are gone and the kernel owns the machine. Chapters F3-10 to F3-15 follow these steps; this chapter stays at the very beginning and builds the tool skill you need for the rest of the course: watching a machine you did not write, from its first instruction, with GDB and the QEMU monitor (curriculum milestone P3).S1

Layer 3 — the engineer's depth

The reset state, register by register

The register dump in Listing 3's output (the first block of gdb_reset.out) is the processor state before the first instruction, as QEMU models it. Read it with the Intel SDM's description of the processor state after reset open next to it (Volume 3, the chapter on processor management and initialization).D1 The points to check:

  • EIP=0000fff0 and CS =f000 ffff0000 0000ffff 00009b00: QEMU prints selector, base, limit and attribute bits. The base is FFFF0000h, not F000h × 16 = F0000h. This is the one moment in the life of the machine when a real-mode segment register's base disagrees with its selector.R3
  • All data segments have base 0 and limit FFFFh: plain real mode.
  • CR0=60000010: bit 0 (PE, protection enable) and bit 31 (PG, paging) are 0; bits 29 and 30 (NW and CD, caching disabled) and bit 4 (ET) are 1.D1 R3
  • EDX=00060fb1: after reset, EDX holds a processor identification value (family, model, stepping) on Intel processors. The value is what QEMU's default CPU model reports, not a real chip's.D1
  • EFER=0000000000000000, CR3=00000000, CR4=00000000: no long mode, no paging tables.
  • A20=1: QEMU's view of the address line 20 gate. On the first PCs this line was held low for compatibility with the 8086's wrap-around at 1 MiB; it is a reason old boot code contains "enable A20" sequences (F3-10).D4

The first eight instructions of this OVMF build

The disassembly in Listing 1's output and the single steps in Listing 3's output tell one consistent story. Read them side by side:

  1. mov %cr0,%eax (3 bytes) copies CR0 into EAX. GDB's next stop is at IP FFF3h.
  2. test $0x1,%al tests bit 0, the PE bit. At reset PE is 0, so the zero flag is set.
  3. je 0xfffffffc is taken: the next stop is FFFCh, not FFF7h. The bytes from FFF7h to FFFBh (e9 2c ff ff ff) are never executed on this path; objdump shows them as a 16-bit jump followed by two bytes it cannot decode, which is what you get when you disassemble bytes that were written for another mode or are data.
  4. jmp 0xffffff10: a near jump backwards; IP becomes FF10h and CS is unchanged (still F000h, base FFFF0000h), so execution continues inside the top 64 KiB of the flash.
  5. mov $0x5042,%di: DI gets 5042h, which is the two ASCII characters "BP". The register dump after the eight steps shows EDI=00005042.
  6. jmp 0xffffff1a, then jmp 0xffffff15, then mov %eax,%esp (with an operand-size prefix, so all 32 bits): ESP becomes 60000010h, the CR0 value read in step 1. The final dump confirms ESP=60000010.

The code under test is so small that you can verify every effect in the registers.R1 R3 Why this firmware checks PE first, why it stores "BP" in DI, and why it parks a value in ESP are design choices of the EDK II reset-vector code; this build did not open that source.

Not verified — check before relying on this

The purpose of the first instructions (testing CR0.PE so that the same reset-vector code can also be entered in 32-bit mode; DI = "BP" as a boot-path marker; ESP used as a scratch register before any stack exists) was not checked against the EDK II source. Read the reset-vector module of the EDK II tree that matches the package version 2024.02-2ubuntu0.10 (D7) before teaching any of these purposes. The instruction effects listed above are observed facts (R1, R3); only the purposes are open.

From real mode to long mode, seen from outside

Six seconds later the same virtual machine is a different machine. Listing 4 stops it and reads the control registers: CR0 = 0x80010033 (PE and PG set), CR4 = 0x00000668 (PAE set, 5-level paging off), EFER = 0xd00 (LME, LMA and NXE set).R4 Long mode is active, and long mode cannot be active without paging, so the firmware built page tables.D1 D2 The SDM describes the order of the switch: enable protected mode, enable PAE, load CR3, set EFER.LME, then set CR0.PG, after which the processor sets EFER.LMA.D1 You do not need to perform this switch yourself on UEFI machines: x86-64 UEFI firmware calls your loader in long mode with paging on (F3-10). You meet it again in F3-10's legacy path and in the kernel track.

The firmware's page tables

The walk in Listing 4 splits RIP = 0xecfe31e into the four 9-bit indices and the offset (PML4 0, PDPT 0, PD 118, PT 254, offset 0x31e), then reads one 8-byte entry per level with the monitor command xp (examine physical memory).D5 The PD entry has PS = 1, so it maps a 2 MiB page and the walk ends one level early: the physical address is the 2 MiB page base plus the low 21 bits of RIP. The result equals RIP: the firmware maps memory one to one (an identity map), and QEMU's own translator (gva2gpa) agrees.R4 In the analogy, the map of lockers says that locker 0xecfe31e is cupboard 0xecfe31e: a map that changes nothing, but must exist because the processor insists on one in long mode. Your own loader in F3-15 builds a richer map: the identity map for the moment of the switch, plus a higher-half map for the kernel.

Note what the entries say beyond the address. Each has P (present), RW (writable) and A (accessed) set, and the 2 MiB page also D (dirty). None has US (user) set: firmware code runs at the highest privilege, and nothing is mapped for user mode. None has NX set either, although EFER.NXE is on: in this firmware the page holding RIP is executable, as it must be.R4

How the hardware actually does it

On a real PC much happens before the reset vector, and none of it is visible in QEMU. Power supplies bring up their rails in a defined order; on many current platforms a separate security or management processor starts first, checks the firmware image and only then lets the main processor out of reset; the processor may load a microcode update; and the flash chip is reached over a serial bus through the platform controller hub, which presents it in the address range below 4 GiB.D4 On a multi-core processor one core is chosen as the bootstrap processor and starts at the reset vector; the others wait for a start-up message that the firmware sends later.D1 Memory is the hardest step: DRAM must be detected and trained (timings measured per module and channel) before it can hold a single byte, so early firmware runs from flash and from the processor's caches used as RAM.D3 D4

QEMU skips all of that. Its RAM works from the first instruction, it has no security processor, it emulates no DRAM training and no flash bus timing, and it maps the firmware file directly as a flash device (-drive if=pflash). OVMF, built for this environment, does not need to train memory; it asks QEMU how much RAM exists through a QEMU-specific interface.D5 D7 The reset state, the reset vector, the mode switches and the page tables are architectural and behave as on a real processor; the platform steps around them are not.

Not verified — check before relying on this

Untested on hardware: nothing in this chapter ran on a real PC. The statements about power sequencing, a security processor releasing the main processor from reset, microcode loading, the flash bus and DRAM training come from the title-only sources D3 and D4 and from the curriculum's boot-chain description (S1); none was observed. On a spare PC, the observable evidence is limited (no GDB at the reset vector without special debug hardware); the vendor's firmware documentation and the platform's datasheets must be checked before teaching any vendor-specific order of events. The claim that OVMF reads the RAM size through a QEMU-specific interface (fw_cfg) is from memory of D7 and was not checked.

Safety

Everything in this chapter runs inside QEMU and touches no real firmware. Never write a modified firmware image to the flash chip of a machine you depend on: a damaged reset vector, as in the forensic lab, leaves a real PC without any output and may need a hardware programmer to recover. Real-hardware firmware work belongs on a designated spare machine with a recovery path (guide 5.8, curriculum safety box).

Worked example

Problem. The firmware file is 3,653,632 bytes long and is mapped so that its last byte is at physical address FFFFFFFFh. (a) At which physical address does the file start? (b) Which file offset does the processor read first? (c) After the jump to IP FF10h with CS base FFFF0000h, which file offset is executed?

Solution.

  1. 4 GiB = 232 = 4,294,967,296. The file occupies the addresses from 232 − 3,653,632 to 232 − 1. 232 − 3,653,632 = 4,291,313,664 = FFC84000h. This matches Listing 2's output ("it starts at 0xffc84000").R2
  2. The first fetch is at FFFF0000h + FFF0h = FFFFFFF0h. Offset = FFFFFFF0h − FFC84000h = 37BFF0h = 3,653,616 = file size − 16: the 16th byte from the end, as Listing 2 prints.
  3. FFFF0000h + FF10h = FFFFFF10h; offset = FFFFFF10h − FFC84000h = 37BF10h = file size − F0h (240). Listing 1's run disassembles exactly those 16 bytes ("16 bytes at file offset size-0xf0" in its run record) and finds mov $0x5042,%di, the instruction GDB executes at FF10h.R1 R3

Check. The two independent views agree byte for byte: reset_bytes reads 0f 20 c0 a8 01 74 05 e9 2c ff ff ff e9 11 ff 90 from the file, and GDB's x/16xb 0xfffffff0 reads the same 16 bytes from the running virtual machine's physical address space.R2 R3

Where the analogy breaks


    

  1. The caretaker does not leave. The F3 map says it: firmware stays partly resident after the OS starts. UEFI runtime services, the ACPI tables and code that runs in system management mode remain, and the OS calls or tolerates them for the whole day (F3-12, F3-15).S2 D3
    2. 

  2. The caretaker builds part of the building. A real caretaker finds the rooms already there. Firmware must first make memory usable before it can store anything at all, and it decides where devices appear in the address space (PCI resources). The school has no counterpart for "the corridors exist only after the caretaker draws them".
    3. 

  3. There is no key handover ceremony in the processor. "Lets the principal in" suggests a negotiation. In reality the handover is a jump instruction; the processor does not know it happened. What makes it a handover is a convention (the boot protocol, F3-14) and one firmware call (ExitBootServices, F3-15).
    4. 

  4. The "one door" is fixed in silicon, and the building is mapped onto it. The caretaker chooses a door; the processor cannot. The platform must place the firmware where the processor will look.
    5. 




Common mistakes and debugging


    

  • Reading GDB's rip as a physical address. In real mode GDB shows 0xfff0; the fetch address is base + IP = FFFFFFF0h. Use monitor info registers for the base.
    • 

  • Computing the reset address as F000h × 16 + FFF0h = FFFF0h. That is the 1 MiB-area alias that the original 8086 used. After reset the CS base is FFFF0000h until the first far jump.D1
    • 

  • Disassembling 16-bit code as 32- or 64-bit. 0f 20 c0 decodes the same in both, but e9 11 ff is a 3-byte jump in 16-bit mode and the start of a 5-byte jump in 32-bit mode. Always pass -m i8086 for reset code. (GDB 15.1 in this build did not accept set architecture i8086 for this target; objdump was used instead.)
    • 

  • Using x instead of xp for page-table entries. x takes a virtual address; entries contain physical addresses.
    • 

  • Forgetting the PS bit. A walk that always goes down four levels reads a 2 MiB data page as if it were a page table and returns nonsense.
    • 

  • Attaching GDB too late. Without -S QEMU starts the CPU at once; by the time GDB connects the firmware is in long mode.
    • 

  • Writing to the firmware file QEMU is using. The code image is attached read-only (readonly=on); the variable store is a copy per run. Sharing one writable variable file between runs carries settings from one experiment into the next.
    •

Summary


    

  • The boot chain has eight stages: power, SEC, PEI, DXE, BDS (firmware), OS loader and handoff (loader), kernel (OS).
    • 

  • An x86 processor leaves reset in real mode with CS selector F000h, hidden CS base FFFF0000h and IP FFF0h; the first fetch is at FFFFFFF0h.
    • 

  • The platform maps the firmware flash so its last byte is at FFFFFFFFh; the last 16 bytes of the file are the first code. In this build: 0f 20 c0 …, a test of CR0.PE and a jump backwards.
    • 

  • GDB attached to qemu -S shows the reset state; GDB prints offsets, QEMU's monitor shows the segment bases.
    • 

  • A few seconds later the firmware runs in long mode with its own page tables (identity map with 2 MiB pages in this build), which you can walk by hand with xp.
    • 

  • QEMU models the architecture, not the platform: no power sequencing, security processor or DRAM training.
    • 

  • When a machine shows nothing at all, check the reset vector before the console or memory.

  1. Same size (3,653,632 bytes) and therefore the same start address FFC84000h; but the last 16 bytes are all 00 instead of 0f 20 c0 a8 01 74 05 e9 2c ff ff ff e9 11 ff 90. The reset vector was erased.
    2. 

  2. 00 00 is add %al,(%bx,%si) in 16-bit code, a 2-byte instruction; evidence 4 shows IP advancing by 2 each step: FFF0h, FFF2h, FFF4h … FFFEh. (Run objdump -m i8086 on the 16 zero bytes to confirm the decoding.)
    3. 

  3. After FFFEh the 16-bit IP wrapped to 0000h; CS was never reloaded, so its base is still FFFF0000h and the next fetch is at FFFF0000h + 0 = FFFF0000h, 64 KiB below the top: random firmware bytes that were never meant to be an entry point. The flags show Z and P set by the add instructions.
    4. 

  4. Ines: ruled out, because the same console configuration shows the shell with the healthy file (evidence 1), and GDB shows the processor never reached any code that could print. The memory hypothesis: ruled out because the failure happens at the first instruction, before any memory initialisation code could run; the processor executes garbage from the flash window, not from RAM.
    5.
