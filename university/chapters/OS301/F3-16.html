Story hook

Analogy

The caretaker will not let anyone into the building whose permission slip is not signed by someone on the list pinned in the staff room. The list itself can only be changed by the head of the school board, whose signature is also on file. A second, quieter rule: at the entrance lies a visitors' book in which every person who enters is written down, in order, in ink, on numbered pages. Nobody can stop a visitor with that book, but afterwards anyone can read it and see exactly who came in.

These are the two security mechanisms of the PC boot chain. Secure Boot stops: the firmware refuses to start a UEFI program whose signature does not match a certificate or hash in its database. Measured boot records: each stage hashes the next into a TPM register before running it, so that a remote party can later check what ran. In this chapter you read the Secure Boot state from the firmware, watch it refuse your unsigned program, sign the program yourself, byte by byte, with a test key the firmware trusts, and watch it run. Then you compute the measured-boot arithmetic for real files. The forensic lab: one character changed in a signed file.

What you will be able to do

  • Explain the Secure Boot key hierarchy (PK, KEK, db, dbx), setup mode and user mode, and where shim fits.
  • Read the Secure Boot state from a UEFI program, and predict what the firmware does with signed, unsigned and modified images.
  • Sign a PE32+ image with an Authenticode signature you construct yourself, and explain which bytes the signature covers.
  • Compute SHA-256 digests and PCR extends, and explain why the order of measurements matters.
  • Distinguish enforcement (Secure Boot) from attestation (measured boot), and explain what each one does not protect against.
Jargon box
Secure Boot (PK, KEK, db, dbx)
Simple words: the firmware feature that only starts programs signed by someone it trusts. Analogy: the caretaker who checks permission slips against the list in the staff room. Precise: UEFI image verification: before starting a UEFI image, the firmware checks its Authenticode signature (or its hash) against the allowed database db and the forbidden database dbx; db and dbx may be changed only with a signature from a Key Exchange Key (KEK), and the KEKs only with the Platform Key (PK). D1 S1
Setup mode and user mode
Simple words: whether the platform has an owner key yet. Analogy: a school without a head of the board accepts any new list; once one is appointed, only signed changes count. Precise: with no PK enrolled the platform is in setup mode (variable SetupMode = 1), the key variables can be written without authentication and images are not verified; enrolling a PK switches to user mode, where SecureBoot = 1 if verification is enabled. D1
Authenticode
Simple words: the signature format for Windows and UEFI program files. Analogy: the signed permission slip stapled to the back of the visitor's papers. Precise: a PKCS#7 SignedData structure, stored in the PE file's certificate table, whose signed content holds a hash of the image computed over the headers (excluding the checksum and the certificate-table entry) and the sections, but not over the certificate table itself. D2 D3
Measured boot
Simple words: each step of the boot writes a fingerprint of the next step into a tamper-proof log before running it. Analogy: the visitors' book in ink. Precise: each boot component measures (hashes) the next one and extends a TPM Platform Configuration Register with that digest, and appends an event to the event log; the PCR values can be reported, signed by the TPM, to a remote verifier (attestation). D4 S1
PCR extend
Simple words: the only way to change a TPM register: mix in a new value, never set it. Analogy: adding a line to the book; there is no eraser. Precise: PCRnew = H(PCRold ‖ digest) for the PCR bank's hash H (SHA-256 here); the final value depends on every digest and their order, and the register can only return to its initial value by a platform reset. D5
shim
Simple words: a small first loader that Linux distributions use to boot with Secure Boot on. Analogy: a visitor with a permission slip from the board who vouches for his own colleagues. Precise: a UEFI loader signed by Microsoft's UEFI CA, which is in db on most PCs; it carries the distribution's own certificate and supports Machine Owner Keys (MOK), and verifies the next stage (for example GRUB) itself. S1

Layer 1 — the kid explanation

Before the firmware starts a program from the disk, it can check a seal on it. The seal can only be made by someone with a secret key, and the firmware has a list of whose seals it accepts. If one letter of the program is changed, the seal no longer fits, and the firmware says "access denied". Separately, a special chip can keep a fingerprint diary of everything that started, so someone can check later what really ran.

Layer 2 — the student explanation

Secure Boot is configured by four variables in the firmware's non-volatile store. The PK belongs to the platform owner (on a retail PC, the manufacturer); the KEKs belong to parties allowed to update the databases (on most PCs, the manufacturer and Microsoft); db holds certificates and hashes of allowed images (on most PCs, Microsoft's Windows and third-party UEFI CAs); dbx holds revoked ones.S1 D1 Two read-only variables report the state: SetupMode (1 when no PK is enrolled) and SecureBoot (1 when verification is enforced).

A UEFI program is a PE32+ file (F3-10). Its signature lives in the certificate table, which is found through entry 4 of the optional header's data directories. The signature covers an Authenticode hash: a SHA-256 over the file with three pieces left out: the checksum field, the certificate-table directory entry, and the certificate table itself. That is why a signature can be added to a file without changing the hash it signs.D2 D3

Linux distributions boot under Secure Boot through shim, signed by Microsoft's UEFI CA, which carries the distribution's key. For your own loader the curriculum's advice is to leave Secure Boot off in QEMU, and later "enroll your own PK/KEK/db in OVMF and sign your loader (the sbsigntools package is the usual tool) as an exercise".S1 sbsigntools is not installed in this build, and neither are the usual tools for writing OVMF's variable store; the lab therefore uses the variable store the distribution ships with a test key already enrolled, and writes the signing program itself.

Measured boot does not stop anything. Each stage computes a digest of the next stage and extends a PCR in the TPM with it. Because extend is a hash of the old value and the new digest, the final PCR value is a commitment to the exact sequence of digests; a verifier who knows the expected components can recompute it from the event log and compare.D4 D5 No TPM is available in this build (no software TPM is installed), so the lab computes the arithmetic on real files and leaves the TPM itself untested.

Signing by hand

sign.py (Listing 2) produces an Authenticode signature without a signing tool, so every byte is visible. It works in four steps:

  1. Authenticode hash (lines 76–90): SHA-256 over the headers up to the checksum field, then from after the checksum to the certificate-table entry, then from after that entry to the end of the headers; then each section's raw data in file order; then any bytes after the last section that are not the certificate table.
  2. SpcIndirectDataContent (lines 95–98): a DER structure saying "this is a PE image" (an object identifier and an empty SpcPeImageData) followed by a DigestInfo: the SHA-256 algorithm identifier and the hash from step 1.
  3. PKCS#7 SignedData (lines 99–119): two signed attributes, the content type and the SHA-256 of the content from step 2 (its value bytes, without the outer tag and length); the RSA signature (PKCS#1 v1.5, SHA-256) over the DER-encoded set of those attributes; the signer's certificate; issuer and serial number to identify it.
  4. WIN_CERTIFICATE (lines 129–137): length, revision 0x0200, type 0x0002 (PKCS signed data), the PKCS#7 bytes, padded to 8 bytes, appended at an 8-byte-aligned end of the file; directory entry 4 set to its file offset and size.

The run (R5): the image hash, the certificate table at file offset 0x1000 with 1,664 bytes, and llvm-readobj now reporting CertificateTableSize: 0x680 (1,664). The proof that the format is right is the firmware's decision: the signed file ran under the snakeoil store, the same file without the signature was refused (R6).R5 R6

Not verified — check before relying on this

Every structure in sign.py was written from memory of D2, D3 and D6: the offsets of the checksum (optional header + 64) and the data directories (optional header + 112), the object identifiers, the layout of SpcPeImageData, and the rule that the message digest covers the content's value bytes. The firmware's acceptance shows that OVMF's verifier agrees with this encoding; it does not show that every detail matches the specifications, nor that other verifiers (Windows, shim, older firmware) accept it. Use sbsigntools for anything beyond this lab.

Measurement arithmetic and reproducible builds

measure (Listing 3) contains its own SHA-256 and computes, for three files (the OVMF code image, our UEFI program, the F3-14 kernel), each digest and the register after each extend, plus the register for the same files in reverse order (R7). run.sh checks every digest against sha256sum and the final register against a three-line Python loop; they agree (R8).R7 R8 The reverse order gives a different final value: a PCR records the sequence, not the set.

The lab also found something a measured-boot designer must know. An earlier version of run.sh gave loader.efi (the same source, compiler and flags) a different digest on every run. Step 5 isolates the cause: linking the same object file twice, 1.1 s apart, gives two files that differ in exactly one byte, at offset 129 (decimal, counted from 1, as cmp prints it), inside the PE header's TimeDateStamp; with lld-link's /Brepro option the two links are identical (R10). The main build now links with /Brepro, which is why the digests in this chapter are the same on every run.R10 A verifier that expects a PCR value computed from "the loader we built" must expect the exact bytes, so boot components should be built reproducibly.

Not verified — check before relying on this

Untested on hardware and untested with any TPM, real or emulated. From memory of D4 and D5, not opened: which PCR the firmware uses for which component (for example, UEFI applications measured into PCR 4 and Secure Boot policy into PCR 7), that UEFI applications are measured by their Authenticode hash rather than the plain file hash used in measure, and the event-log format. measure models only the extend operation with one SHA-256 bank.

How the hardware actually does it

Neither mechanism is enforced by the processor. Secure Boot is firmware code: the DXE image loader (F3-11) calls a verification library before starting an image. Its strength depends on the firmware being unmodified and on the variable store being writable only through authenticated paths: on PCs, SMM-protected flash, which is why QEMU needs smm=on and a secure flash device for the Secure Boot build. What protects the firmware itself is a separate, earlier root of trust, such as Intel Boot Guard or AMD Platform Secure Boot, which the curriculum names as topics.S1 The TPM is a separate chip (or a firmware TPM running in a protected processor) whose PCRs can only be extended, and reset only by a platform reset; it can sign a report of its PCRs ("quote") with a key that never leaves it.D5

Not verified — check before relying on this

Untested on hardware: all runs used QEMU 8.2.2 with the distribution's OVMF 2024.02 builds and no TPM. The descriptions of Boot Guard, Platform Secure Boot, firmware TPMs and quotes are from the curriculum's summary (S1) and memory of D5; none was observed here. Real PCs differ in which keys are in db by default and in how the firmware setup screen lets the owner change them.

Worked example

Problem. (a) Under the snakeoil store, sbstate reported the PK as 1,031 bytes. The PK is stored as one EFI_SIGNATURE_LIST holding one X.509 certificate. Our test certificate is 987 bytes in DER. Account for the remaining bytes. (b) The signed file is 1,664 bytes longer than the unsigned one (the certificate table's size), yet both have the same Authenticode hash (R9). Explain both facts. (c) The tampered file differs from the signed file in one byte. Which hashes change?

Solution. (a) 1,031 − 987 = 44 bytes. An EFI_SIGNATURE_LIST starts with a 28-byte header: the signature type GUID (16 bytes, here "X.509 certificate"), the list size, the header size and the signature size (4 bytes each). Each signature in the list then starts with a 16-byte owner GUID. 28 + 16 = 44.R6 (b) The unsigned file ended at 0x1000 (4,096 bytes), already 8-byte aligned, so no padding was added; the certificate table of 0x680 = 1,664 bytes was appended at 0x1000 (R5). The Authenticode hash leaves out the certificate-table directory entry (changed by signing) and the table itself (added by signing), so it is the same for both files: 3e39…46f9. The plain file hashes differ: 242f…9e67 and 040a…d308. (c) The changed byte is in a section, so the Authenticode hash changes (e018…a47d) and so does the plain hash (cf4e…ebab); the signature, which was over the old Authenticode hash, no longer matches.R9

Not verified — check before relying on this

The EFI_SIGNATURE_LIST layout (28-byte header, 16-byte owner GUID) is from memory of D1. The arithmetic matches the observed size exactly, which is consistent with that layout but does not prove it (a different 44-byte layout would also match).

Where the analogy breaks


    

  1. The caretaker cannot recognise faces. A permission slip in the school is checked by a person who might notice something odd; the firmware checks only mathematics. A signed program with a bug (or signed by a careless key holder) runs.
    2. 

  2. The visitors' book in a school can be read by anyone at the door. PCRs are only useful if someone checks them against expected values; on most machines nobody does, except for features such as disk encryption keys sealed to PCR values.
    3. 

  3. The board's list is not in the staff room. db and dbx live in the firmware's flash and are protected by firmware code; a firmware compromise bypasses them, which is why roots of trust below the firmware exist.
    4. 




Common mistakes and debugging


    

  • Expecting the plain OVMF build to enforce anything. It has no Secure Boot support; use the secboot build with smm=on and secure flash.
    • 

  • Thinking "Secure Boot is enabled" because keys exist. Check SecureBoot and SetupMode: in setup mode nothing is verified.
    • 

  • Changing a signed file after signing (patching a string, stripping symbols, adding a section). The Authenticode hash changes; sign as the last step.
    • 

  • Hashing the whole file to compare with a signature. The signature is over the Authenticode hash, which skips the checksum, the directory entry and the certificates.
    • 

  • Expecting identical builds to measure identically. Time stamps in PE headers (and other build metadata) change the digest; build reproducibly.
    • 

  • Treating measured boot as protection. It records; something has to check the record.
    • 




Transition box

Where you came from: F3-10 (PE32+ programs), F3-11 (the DXE image loader), F3-15 (your loader). What carries over: the format knowledge (PE headers, data directories), the habit of checking every claim against a run, and the CRC and checksum ideas of F3-13, now with cryptographic hashes and signatures that an attacker cannot recompute without the key. What changes: the question is no longer "does it boot?" but "who decided that it may boot, and how would anyone know what booted?". Lab


Goal


The curriculum's exercise: "enroll your own PK/KEK/db in OVMF and sign your loader … as an exercise".S1 In this build: observe the Secure Boot states, sign a program with a key the firmware trusts, and compute measured-boot values.


Hardware and software needed


clang 18.1.3 and lld-link, Python 3.13 with python3-cryptography (50.0.1 in this build, R5), llvm-readobj 18.1.3, QEMU 8.2.2, the ovmf package 2024.02 with its secboot code and ms and snakeoil variable stores, and its test key files PkKek-1-snakeoil.pem and .key.


Safety


Never change Secure Boot keys on a real PC as part of this lab: a mistake can leave a machine that refuses its own operating system, and on some laptops the firmware's own option ROMs (graphics) are verified against db too, so removing Microsoft's certificate can leave no display. The snakeoil key is public test material: never trust it on a real machine.

Expected observations


The four rows of the table in Layer 3 (R1–R3, R6); the signed program prints SecureBoot = 1; every digest equals sha256sum's; the reverse order gives a different register; links differ only at offset 129 without /Brepro (R10).


Verification


run.sh exits 0 only if: the plain build's program printed the variables, the ms store refused it, the snakeoil store refused the unsigned and tampered files and ran the signed one with SecureBoot = 1, every digest matched sha256sum, the final register matched Python's, and the /Brepro links were identical.

  • The Secure Boot build does not start at all → missing smm=on or the secure flash option.

    • 

  • sign.py says "already signed" → start from the unsigned file.

Forensic lab


Scenario: "One character". A team boots its signed tool on test machines with Secure Boot on. Before a demonstration, Ana corrects a typo in the tool's start message, a one-character change, directly in the .efi file with a hex editor, "to avoid a rebuild". The machines now refuse to start it. Her colleague suspects the test key has expired; another suspects the hex editor corrupted the file.


Evidence pack. (1) The original signed file booting. (2) The edited file booting. (3) The Authenticode hashes and plain hashes of the unsigned, signed and edited files, and the bytes that differ between signed and edited.






Compare with the original signed file's boot in the code walk-through (sb_snakeoil_signed).

    2. 

  2. Which hash did the signature cover, and did it change?

  3. Evaluate the two hypotheses (expired key; corrupted file).
    4. 

  4. Why are the unsigned and signed files' Authenticode hashes equal while their plain hashes differ?

Method hints. cmp -l prints a 1-based decimal offset and the two byte values in octal. Convert both. Then decide which of the three hashes in the pack the firmware compares with the signature.



Mini-project


Write verify.py, the other half of sign.py: parse the WIN_CERTIFICATE and the PKCS#7 structure of a signed file, recompute the Authenticode hash, compare it with the one inside SpcIndirectDataContent, check the message-digest attribute, and verify the RSA signature with the certificate inside. Rubric: reports OK for signed.efi (1); reports which check fails for tampered.efi (hash mismatch) and for a file with one byte changed inside the signature (signature check) (2); never crashes on a truncated certificate table (fuzz it with 1,000 random truncations) (1); a paragraph on what this verifier does not check that the firmware does (db, dbx, certificate chains) (1).



Summary


    

  • Secure Boot: PK controls KEK, KEK controls db and dbx; images are verified against db and dbx at load time; SetupMode and SecureBoot report the state.
    • 

  • Authenticode: PKCS#7 SignedData in the PE certificate table, over a hash that skips the checksum, the certificate directory entry and the certificate table.
    • 

  • Observed: plain OVMF has no Secure Boot; the secboot build with an empty store is in setup mode; with keys enrolled, unsigned and modified programs get "Access Denied"; our hand-made signature with the enrolled test key ran.
    • 

  • Measured boot: PCR ← H(PCR ‖ digest); the final value commits to every component and their order; it records, it does not stop.
    • 

  • Reproducible builds matter for measurement: a linker time stamp alone changed our program's digest.

Answers to Check yourself


    

  1. PK: changed by the PK holder (the platform owner). KEK: changed with the PK. db and dbx: changed with a KEK (or the PK). In setup mode (no PK), they can be written without authentication.
    2. 

  2. No Platform Key is enrolled, so images are not verified: Secure Boot is not in force, whatever else is stored.
    3. 

  3. The Authenticode hash excludes the certificate-table directory entry and the certificate table, the two things that signing changes (and the checksum, which tools may recompute).
    4. 

  4. The variable store holds the keys; if the operating system or any program could write the flash directly, it could put its own certificate in db. SMM-only write access (secure flash) lets the firmware enforce the authenticated-update rules.
    5. 

  5. Secure Boot refuses to start images not allowed by db and dbx; it does not stop a signed but vulnerable program, or an attacker who has modified the firmware. Measured boot records digests of what ran in PCRs; it does not stop anything, and is useless if nobody checks the values.
    6. 

  6. (b) and (d). (a) and (c) touch only the excluded fields; (d) changes TimeDateStamp in the COFF header, which is hashed.
    7. 

  7. Firmware (db: Microsoft UEFI CA) → shim, signed by Microsoft, carrying the distribution's certificate → the distribution's boot loader and kernel, signed with the distribution's key and verified by shim (and by the next stage for the kernel). The owner can add keys through MOK.
    8. 

  8. A different PCR value: the rebuilt loader has a different time stamp, so a different digest, so every extend after it differs. The verifier reports an unknown boot even though the source did not change.
    9. 



Forensic lab answer key


    

  1. One byte, at 1-based offset 3753 (byte 3752 = 0xEA8): octal 66 → 67, the character "6" → "7", turning "F3-16" into "F3-17" in the message text.
    2. 

  2. The Authenticode hash. It changed from 3e39…46f9 to e018…a47d, so the signature (over 3e39…) no longer matches the file, and the firmware refused it: "Access Denied".
    3. 

  3. Expired key: rejected; the original signed file with the same key ran under the same firmware, and the certificate's validity runs to 2053 (notAfter in R5). Whether OVMF checks validity periods at all was not tested. Corrupted file: partly right but misleading; the editor did exactly what was asked, one byte, and that is enough.
    4. 

  4. Signing changed only the certificate-table directory entry and appended the table; both are excluded from the Authenticode hash, both are included in a plain hash.
    5. 

  5. Change the source, rebuild, and sign again as the last step. Rule: signed artefacts are never edited; signing is the final build step, and the signing key is used by the build, not by hand on edited binaries.
    6. 



How the evidence was produced: run.sh step 4 changed the byte with a one-line Python command (the "hex editor") and booted the result under the snakeoil store.
