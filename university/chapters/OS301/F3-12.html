Story hook

Analogy

On her first morning, a new principal finds a folder on her desk from the caretaker: a floor plan with every room, which rooms have a projector, where the fuse boxes are, which doorbells ring in which office, and a page with the building's make and year. She will never walk every corridor to check; she trusts the folder. If a page is wrong, she will send a class to a room that does not exist.

An operating system starts in the same position. It cannot ask the motherboard how many processors exist, where the interrupt controllers are, or which address range holds PCI configuration space; there is no general hardware question for that. The firmware writes the answers into tables in memory, and the OS reads them. On PCs those tables are ACPI (for configuration and power) and SMBIOS (for inventory). In this chapter your UEFI program finds them through the configuration table, checks every checksum, decodes the processor list, the interrupt controllers, the timer and the PCI Express window, and compares all of it with how you configured QEMU. Then you measure when the firmware handed control to you, and use that timeline to find where a slow boot loses its time.

What you will be able to do

  • Find the ACPI RSDP and the SMBIOS entry point through the UEFI configuration table by GUID.
  • Walk RSDP → XSDT → individual ACPI tables, verify checksums, and decode the MADT, HPET, MCFG and FADT fields an early kernel needs.
  • Read SMBIOS structures (type, handle, formatted area, string set) and connect them to the machine's configuration.
  • Test firmware tables against an independent source of truth (the QEMU command line).
  • Build a boot timeline from console time stamps and the processor's time-stamp counter, and locate a delay in it; explain what a firmware performance data table (FPDT) would add, and why this build could not use one.
Jargon box
ACPI
Simple words: the standard set of tables (and a small program language) through which firmware describes a PC's devices and power controls to the OS. Analogy: the floor plan and fuse-box pages of the inventory folder. Precise: the Advanced Configuration and Power Interface: a root pointer (RSDP), system description tables with a common 36-byte header and a byte checksum, fixed tables such as FADT, MADT, HPET and MCFG, and the DSDT/SSDT definition blocks containing AML bytecode the OS interprets. D2
RSDP and XSDT
Simple words: the first pointer and the table of contents of the ACPI tables. Analogy: the folder's cover page and its index. Precise: the Root System Description Pointer (signature "RSD PTR ", checksums over its first 20 bytes and, for revision 2 and later, over its full length) holds the physical address of the Extended System Description Table, whose body is an array of 64-bit physical addresses of the other tables. D2 R1
MADT
Simple words: the ACPI table that lists the processors and interrupt controllers. Analogy: the page saying which doorbell rings in which office. Precise: the Multiple APIC Description Table (signature "APIC"): the local APIC address followed by variable-length entries (processor local APIC, I/O APIC, interrupt source override, NMI and others). D2
SMBIOS
Simple words: the firmware's inventory of the machine: maker, model, firmware version, processor sockets, memory modules. Analogy: the page with the building's make and year. Precise: the System Management BIOS structure table: typed structures (type, length, handle, formatted area) each followed by a set of zero-terminated strings ending in an extra zero, found through a 32-bit or 64-bit ("_SM3_") entry point. D3
Configuration table (UEFI)
Simple words: a list in the system table that pairs a GUID with the address of a table. Analogy: the folder's sticky tabs, each with a code. Precise: the array of EFI_CONFIGURATION_TABLE entries (vendor GUID, pointer) referenced by the EFI system table, through which firmware publishes the ACPI RSDP, SMBIOS entry points and other tables. D1
Time-stamp counter (TSC)
Simple words: a counter inside the processor that increases steadily; reading it twice tells how much time passed. Analogy: the school clock read at two moments. Precise: a 64-bit counter read with RDTSC; on current processors it increments at a constant rate, which must be calibrated against a known timer before converting counts to seconds. D4
FPDT
Simple words: an ACPI table in which firmware records how long its own boot steps took. Analogy: the caretaker's time sheet for the morning round. Precise: the Firmware Performance Data Table, which points to performance records with time stamps for points such as the end of reset, the OS loader's load and start, and ExitBootServices entry and exit; tools that draw boot timelines (for example on Windows) read it. D2

Layer 1 — the kid explanation

Before the operating system starts, the firmware writes a description of the computer into memory: how many processors, where the clocks and doorbells are, who made the machine, how much memory there is. It leaves a small sign telling where that description starts. The operating system finds the sign, follows it, and reads. Each page of the description has a little check number at the end, so that the reader can tell if a page was damaged.

Layer 2 — the student explanation

A UEFI program finds the firmware's tables in the configuration table: an array of (GUID, pointer) pairs reached from the system table. The ACPI 2.0 GUID leads to the RSDP; the SMBIOS 3 GUID leads to the 64-bit SMBIOS entry point.D1 A legacy BIOS kernel would instead search for the "RSD PTR " signature in fixed low-memory areas; UEFI makes that search unnecessary.D2

The RSDP leads to the XSDT, a list of 64-bit addresses of the other tables. Every ACPI table starts with the same 36-byte header: a 4-character signature, the total length, a revision, a checksum byte chosen so that all bytes of the table add up to zero modulo 256, and OEM identifiers.D2 An early kernel needs four tables: the MADT ("APIC") to find the processors and interrupt controllers (B7), the HPET table for a reliable timer (B8), the MCFG table for the memory-mapped PCI Express configuration space (C-track drivers), and the FADT ("FACP"), which points to the DSDT, the block of AML bytecode describing devices and power methods. Interpreting AML is a large job (real kernels embed an interpreter); reading the fixed tables is a small one, and that is what this chapter does.

SMBIOS is different in purpose: it is inventory, not configuration. Each structure has a type (0 firmware, 1 system, 4 processor, 17 memory device, 127 end of table…), a length for its formatted part, and a handle, followed by its strings. Management software and your kernel's "about this machine" line read it; no driver should configure hardware from it.D3

Both table sets stay in memory after the handoff, in ranges that the memory map marks as ACPI reclaim, ACPI NVS or runtime-services data. That is why your loader passes only two addresses to the kernel, the RSDP and the SMBIOS entry point (milestone A3), and keeps those ranges out of the kernel's free memory.S1

Layer 3 — the engineer's depth

Trusting a table: checksums and a second source

Listing 1 verifies three kinds of checksum: the RSDP's 20-byte checksum and its extended checksum over its full 36 bytes (revision 2), every ACPI table's whole-table checksum, and the SMBIOS 3 entry point's checksum over its own length. All were "ok" in this build (R1). A checksum only proves that the table was not damaged after the firmware wrote it; it says nothing about whether the firmware told the truth. For that you need an independent source of truth. Here it is the QEMU command line: -smp 2 must give two processor entries in the MADT, and -smbios type=1,manufacturer=OS301-Lab,product=Tables-Demo must appear in SMBIOS type 1. Both checks pass (R2).R1 R2 On real hardware the second source is the board's documentation, a different OS's view, or the hardware itself (for example, starting each processor listed and seeing it answer).

Reading the MADT entries

The MADT body starts at offset 44 with the 32-bit local APIC address (here 0xfee00000) and a flags word, then a sequence of entries, each starting with a type byte and a length byte. Listing 1 decodes three types: 0 (processor local APIC: processor UID, APIC ID, flags; bit 0 = enabled), 1 (I/O APIC: ID, address 0xfec00000, first global system interrupt 0), and 2 (interrupt source override: the ISA IRQ 0 timer arrives on GSI 2; IRQs 5, 9, 10 and 11 have flags 0x000d). The one entry of type 4 (length 6) is not decoded.D2 R1 A kernel that ignores the override for IRQ 0 programs the I/O APIC pin 0 for the timer and never sees a timer interrupt: a classic Track B bug.

Not verified — check before relying on this

Written from memory of the ACPI Specification (D2), not opened: the field offsets of the RSDP (revision at 15, XSDT address at 24, length at 20), of the generic header and of the MADT, HPET (base address at 44), MCFG (allocation entries from 44) and FADT (DSDT at 40, X_DSDT at 140) tables; the meaning of the MADT entry types 0, 1, 2 and 4 (type 4 is believed to be "local APIC NMI"); the meaning of the override flags 0x000d (believed: polarity active high, trigger level); and the meaning of WAET (believed: "Windows ACPI Emulated devices Table") and BGRT (boot graphics resource table). The decoded values are self-consistent (checksums, the HPET and I/O APIC addresses QEMU uses, the ECAM range that F3-10's memory map reserves at 0xe0000000), which makes gross offset errors unlikely; it does not verify meanings. The SMBIOS offsets (type 17 size at 0Ch, device locator string at 10h) are from memory of D3, likewise.

Who wrote which table

The OEM fields tell a story. Every table except one carries the OEM ID "BOCHS ", the historic name QEMU's ACPI generator uses; the BGRT carries "INTEL ". F3-11's module list contains both QemuFwCfgAcpiPlatform and BootGraphicsResourceTableDxe: the likely reading is that OVMF installs the tables QEMU generated (received through QEMU's firmware-configuration interface) and adds a BGRT of its own (EDK II's default OEM ID). On a real PC the board vendor's firmware writes them all.R1 D5 The same distinction explains why SeaBIOS and OVMF disagree on the ECAM address (F3-10): the address is a firmware decision, and the MCFG table is how the firmware tells the OS what it decided.

Where the tables live is also visible. The RSDP and XSDT (0xf77e014, 0xf77d0e8) and the other ACPI tables fall inside the range that F3-10's memory map (same memory size, one processor) types as ACPI reclaim memory (0xf76d000, 18 pages); the SMBIOS 3 entry point at 0xf586000 falls inside runtime-services data (0xf4ed000, 256 pages). Your own run's addresses can differ; check them against your own map.R1 R4

Time stamps, the TSC and the missing FPDT

The course card's second forensic task is an "ETL-style boot timeline": a firmware performance data table dump compared with a healthy one. Listing 1 searched the XSDT for an FPDT and printed "not in the XSDT": this OVMF build does not publish one (R1). Rather than invent one, this chapter builds the timeline from two real clocks: the host time stamp that the harness puts in front of every console line (--stamp), and the TSC value Listing 1 reads as its first action. The TSC advanced by about 2.0 to 2.1 × 109 counts per host second in these runs (for example 4,150,777,498 counts at 2.025 s); that ratio is a property of QEMU on this container, not of any processor.R3 F3-15's loader goes one step further and records its own FPDT-like points (kernel file read, before and after ExitBootServices, kernel entry) in the boot information it passes to the kernel.

Not verified — check before relying on this

The content of an FPDT (record types, which boot points it time-stamps, nanosecond units) and how Windows boot-tracing tools (ETW/ETL) consume it are from memory of D2 and of the curriculum's mention of ETW; nothing was observed, because the table is absent in this firmware. A firmware build with FPDT support (EDK II has performance infrastructure that can be enabled at build time; F3-17) is needed to do the card's original task. Decision recorded for the owner in NOTES.md.

How the hardware actually does it

None of these tables is read from hardware registers. On a real PC, platform firmware assembles them from what it knows: compiled-in board descriptions, what it discovered (processor count after starting the cores, memory size after training, PCI resources it assigned) and what the silicon vendor's code provides. Then it computes the checksums and installs pointers in the configuration table.D2 D6 The addresses inside the tables (local APIC at 0xfee00000, I/O APIC at 0xfec00000, HPET at 0xfed00000) are where the hardware's registers respond; the tables tell the OS where to look, and the OS then talks to the hardware directly (Track B). In QEMU those devices are emulated at those addresses. The TSC is real processor hardware; under QEMU's emulation (TCG) its value is produced by QEMU, which is why its rate here says nothing about a real processor.D4

Not verified — check before relying on this

Untested on hardware: no real machine's tables were read. Real firmware tables are known to contain errors that operating systems work around (quirk tables); check each field you rely on against a second source. On a spare PC, the same UEFI program from a USB stick prints that machine's tables; compare with the output of an OS tool that dumps ACPI tables, and record both. The statement that the TSC runs at a constant rate on current processors is from memory of D4 and must be checked per processor family (CPUID flags) before a kernel relies on it.

Worked example

Problem. The XSDT has length 84. How many table addresses does it hold? Then check the SMBIOS type 17 entry against the QEMU command line.

Solution. The XSDT body follows the 36-byte header and holds 8-byte addresses: (84 − 36) / 8 = 6. Listing 1 printed six entries: FACP, APIC, HPET, MCFG, WAET, BGRT (R1). For the memory device, Listing 1 printed "size field 0x0100" for "DIMM 0". If the field counts MiB (its top bit clear), 0x100 = 256 MiB: the -m 256M given to QEMU.R1 The unit is from memory of D3 (see the unverified box): run the lab with -m 512M and see whether the field becomes 0x0200, which tests the unit claim without the specification.

Check by arithmetic. The RSDP's extended checksum covers 36 bytes; the run says "extended checksum (36 bytes) ok". A byte sum of zero over 36 bytes is a constraint on all of them: change any single byte, and the sum changes by that byte's difference (mod 256), which is non-zero, so a single-byte error is always detected. Two errors can cancel.

Where the analogy breaks


    

  1. The folder contains a program. The DSDT is not a page of text but AML bytecode that the OS must execute to learn about devices and to switch power states. No inventory folder asks the principal to run its pages.
    2. 

  2. The folder is written for one reader at a time but read by several. Firmware runtime code, the OS and management controllers may all depend on these tables; some ACPI regions (NVS) are firmware working memory that the OS must never reuse, a "page you may read but not throw away or write on".
    3. 

  3. Nobody checks the folder against the building for you. A principal can walk the corridors; an OS often cannot verify a table independently and must trust it, which is why wrong tables cause real bugs.
    4. 




Common mistakes and debugging


    

  • Using the ACPI 1.0 RSDP and the 32-bit RSDT when an XSDT exists. The configuration table here offers both GUIDs; prefer the 2.0 one and the XSDT.
    • 

  • Checksumming the RSDP over 36 bytes only, or 20 only. Revision 2 has two checksums with two lengths; check both.
    • 

  • Walking MADT entries without guarding against length 0. Infinite loop on a damaged table.
    • 

  • Treating SMBIOS as configuration. It is inventory written for humans and management tools; strings and sizes can be wrong or missing ("(none)").
    • 

  • Dereferencing table addresses after the handoff without a mapping. Inside the kernel, physical addresses need the direct map; F3-15 passes the RSDP as a physical address for that reason.
    • 

  • Treating host time stamps as hardware time. They measure QEMU in a shared container. Repeat runs and compare positions in the sequence, not absolute values.
    • 




Transition box

Where you came from: F3-11 showed the DXE phase that produces these tables, and F3-10 the system table and memory types. What carries over: the configuration table is reached from the system table; the types ACPI reclaim, ACPI NVS and runtime-services data in the memory map are where these tables live; GUIDs are names. What changes: you now parse data structures defined by two more specifications (ACPI, SMBIOS) and verify them against an independent source, which is the habit a kernel author needs. What comes next: F3-13 leaves memory for the disk: the MBR and GPT layouts, the EFI system partition, and a verifier that checks a disk image as strictly as you checked these tables.

Lab


Goal


Read the firmware's tables from a UEFI program, verify them, and test them against QEMU's configuration; prepare the RSDP and SMBIOS fields of milestone A3's boot information.S1


Hardware and software needed


clang 18.1.3 with LLD 18.1.3, QEMU 8.2.2, OVMF 2024.02-2ubuntu0.10 in this build (R1); the shared headers efi.hpp and console.hpp from F3-10; no real PC.


Safety


The program only reads memory. On a spare PC it is safe to run from a USB stick; do not modify ACPI tables on a machine you depend on.


Steps


    

  1. Build Listing 1, copy it to esp/EFI/BOOT/BOOTX64.EFI, and boot with -smp 2 and the -smbios option from the run record.
    2. 

  2. Repeat with -smp 4 and -m 512M; record what changes in the MADT and SMBIOS output and what does not.
    3. 

  3. Write the four checks of run.sh step 3 for your own configuration and run them on both outputs.
    4. 

  4. Find each table's address in your memory map (Listing 1 of F3-10, same QEMU options) and record its memory type.
    5. 

  5. Boot three times plainly and three times with -boot menu=on,splash-time=3000 using qemu_run.py --stamp; tabulate the time of "BdsDxe: starting" and the program's run time.
    6. 



Expected observations


Two processor entries become four; the memory-device size field doubles if the unit is MiB; checksums stay "ok"; the RSDP stays at revision 2; the table addresses can move. In the timed runs, the boot-option start moves later by roughly the configured wait, while the program's own run time stays below a fifth of a second (R3).


Verification


All four checks print PASS for both configurations; your step-4 table types every address; your step-5 table gives the mean and the spread of both configurations. (A3's acceptance item "the kernel prints the RSDP signature and revision … the test compares them with QEMU's configuration" reuses these checks in F3-15.)


Troubleshooting


    

  • No ACPI line at all → the RSDP GUID did not match: compare efi.hpp's GUID bytes with your firmware's configuration table output.
    • 

  • "checksum BAD" on every table → your u32 length read is wrong (endianness) or you sum the wrong range.
    • 

  • The program does not start by itself → the file must be at \EFI\BOOT\BOOTX64.EFI on a FAT disk.

Forensic lab


Scenario: "Boot got slow after a settings change". The lab machines of a school's robotics club used to reach the club's boot program in about two and a half seconds. After a technician "standardised" the virtual-machine settings, they take more than five. The technician says the new program version is slower; the club's student lead, Aroha, says the program has not changed. The course card asks for an FPDT comparison; this firmware publishes no FPDT (see Listing 1's output), so the evidence is a console timeline with host time stamps plus the processor's time-stamp counter at the program's entry, three boots per configuration.

Method hints. Separate "before our program" from "inside our program". A delay before the first line you control is not in your code. Host time and TSC are two clocks; check that they agree on order and roughly on proportion before trusting either. Look at the full run record for each configuration's command line.



Mini-project


Write acpidump.efi: a UEFI program that copies every ACPI table (including the DSDT) to files on the ESP through the Simple File System protocol, one file per table named by signature, and a host-side C++ tool that re-validates each file's checksum and prints the header. Rubric: files are byte-identical across two boots of the same configuration (1); the host tool runs under the course flags with no sanitizer errors (1); a table changed by one byte is detected (1); the program handles a missing XSDT by falling back to the RSDT, tested by explaining how you would test it (1); the report compares two QEMU configurations table by table (1).



Summary


    

  • UEFI publishes the ACPI RSDP and the SMBIOS entry points in the configuration table, by GUID.
    • 

  • ACPI: RSDP → XSDT → tables with a common 36-byte header and a zero byte-sum; the MADT (processors, I/O APIC, overrides), HPET, MCFG and FADT→DSDT are what an early kernel reads first.
    • 

  • SMBIOS: typed structures with string sets; inventory, not configuration.
    • 

  • Checksums detect damage, not falsehood; test tables against an independent source (here the QEMU command line: 2 CPUs, our SMBIOS strings).
    • 

  • OEM IDs and memory types show who wrote a table and where it lives (ACPI reclaim, runtime-services data).
    • 

  • This OVMF has no FPDT; a timeline built from console time stamps and the TSC still locates a delay (about 3.2 s before BDS starts the boot option, with an unchanged program).

Answers to Check yourself


    

  1. System table → configuration table entry with the ACPI 2.0 GUID → RSDP → XSDT → the entry whose table signature is "APIC".
    2. 

  2. That the bytes of the table were not changed (by most damage) since the checksum was computed. It does not prove that the content is true (the firmware may describe the machine wrongly) or that two compensating errors did not occur.
    3. 

  3. The interrupt source override (MADT type 2) for ISA IRQ 0 → GSI 2. A kernel that ignores it programs the I/O APIC input 0 for the timer and never receives timer interrupts (or receives them on an unexpected vector).
    4. 

  4. Memory-mapped configuration space (ECAM) sits at an address the firmware chose (0xe0000000 under OVMF, 0xb0000000 under SeaBIOS in this build); nothing in the processor or the PCI devices reveals it. The MCFG table is where the firmware records that choice, with the segment and bus range.
    5. 

  5. The MADT processor entries (count and the enabled flag) and your kernel's own parsing of them (wrong entry walk, stopping at the first unknown type); then whether your kernel starts the other processors at all, which is separate from detecting them.
    6. 

  6. The string index for the product would be 0 or point to a default chosen by QEMU or OVMF; Listing 1 prints "(none)" for index 0. Run it to find out which, and record the observation.
    7. 

  7. The GUID lookup, the RSDP and XSDT walk, the checksum and header code and the SMBIOS walk carry over. The x86 MADT entries (local APIC, I/O APIC) are replaced by Arm interrupt-controller entries (GIC structures) in the MADT on Arm; look up their layout in the ACPI Specification, section on the MADT, rather than guessing.
    8. 

  8. The tables stay in memory the firmware has reserved for them (ACPI reclaim and NVS, runtime-services data); the kernel can reach them through its direct map. Copying would require knowing all table lengths and sub-tables in the loader, and the NVS region must stay where it is anyway because firmware code uses it.
    9. 



Forensic lab answer key


    

  1. Old settings: boot option started at 2.023, 2.504 and 2.823 s, mean 2.45 s; program run times 0.084, 0.069 and 0.092 s (from the entry line to "done"). New settings: 5.925, 5.444 and 5.502 s, mean 5.62 s; run times 0.139, 0.087 and 0.148 s.
    2. 

  2. Not meaningfully: the program runs in under 0.15 s in all six boots, while the boot option starts about 3.2 s later on average. Aroha is right; the technician's explanation does not fit the timeline.
    3. 

  3. Before "BdsDxe: starting Boot0001": in the firmware, before BDS starts the boot option (DXE/BDS). The TSC at entry is a second, independent clock: the new configuration's entry values (12.3, 11.1 and 11.4 × 109) are more than twice the old ones (4.2, 5.1 and 5.8 × 109), so the firmware itself experienced the extra time; it is not an artefact of the host time stamps.
    4. 

  4. The difference of means (about 3.2 s) is close to the configured 3,000 ms. It need not match exactly: the spread between boots of the same configuration is itself about 0.8 s (2.02 to 2.82 s) in this shared, emulated container, and the menu wait may add its own set-up time. Exact semantics of splash-time must be checked in the QEMU documentation (D8 of F3-10).
    5. 

  5. Records for the end of reset, the OS loader's LoadImage and StartImage, and ExitBootServices entry and exit would bracket the firmware phase and the loader directly, in firmware time units. This OVMF build publishes no FPDT (Listing 1 prints "not in the XSDT"); a firmware built with performance recording would be needed (F3-17).
