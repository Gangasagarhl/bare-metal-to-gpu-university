Story hook

Analogy

At the end of the caretaker's shift, he hands the building to the new principal. He will only leave if she shows him the latest room plan, the one with today's stamp on it, because he will never be back to tell her what changed. If, between printing the plan and showing it, someone books one more room, the stamp is out of date: the caretaker refuses and stays. A principal who does not look at his answer waits in the corridor for ever, and the visitors see only the school's logo on the door.

This chapter is the course project. Your loader, written in C++, reads the kernel of F3-14 from the disk of F3-13, maps it at its higher-half address with the right permissions, collects the boot information, and performs the most delicate step of the whole boot: it asks the firmware to leave (ExitBootServices), with a key that proves it has seen the final memory map, and jumps. A test then reads the running machine from the outside, through QEMU's monitor, and checks every acceptance item of milestone A3. In the forensic lab, a loader with one extra line hangs "after the logo"; you find out why from its serial output and a time line.

What you will be able to do

  • Implement a UEFI loader that loads an ELF64 kernel from the ESP, builds four-level page tables and jumps to the kernel with the OS301 protocol.
  • Apply the ExitBootServices rule: get the final map, call with its key, retry on failure, and use no boot service after success.
  • Build page tables with an identity map, a direct map of physical memory and a higher-half kernel mapping whose W and NX bits follow the ELF flags.
  • Verify a running machine from outside: walk its page tables through the QEMU monitor and compare the framebuffer with a screen dump.
  • Diagnose a hang at the handoff from serial output and time stamps, and tell a stale map key from other causes.
Jargon box
ExitBootServices
Simple words: the call in which the loader tells the firmware "I take over now; stop your services". Analogy: the caretaker's handover at the end of the shift. Precise: the UEFI boot service ExitBootServices(ImageHandle, MapKey); if MapKey is the key of the current memory map, the firmware ends boot services and returns success, after which only runtime services may be used; otherwise it returns an error and boot services remain partly available. D1 S1
Memory map key
Simple words: a number the firmware gives with each memory map; it changes whenever memory is allocated or freed. Analogy: today's stamp on the room plan. Precise: the MapKey output of GetMemoryMap, identifying the state of the memory map at that moment; ExitBootServices accepts only the key of the current map. D1
Page-table entry (PTE) bits
Simple words: the switches in each page-table entry that say whether the page exists, may be written, and may hold code. Analogy: the signs on a classroom door: "open", "staff may rearrange", "no lessons held here". Precise: in x86-64 four-level paging, bit 0 Present, bit 1 Read/Write, bit 7 Page Size (2 MiB or 1 GiB page at levels 2 and 3), bit 63 Execute-Disable (honoured when EFER.NXE = 1); the physical address of the next table or the page is in bits 12 to 51. D3
Identity map
Simple words: a mapping where every virtual address equals the physical address. Analogy: the room numbers on the plan are the numbers on the doors. Precise: page-table entries mapping virtual address v to physical address v; the loader needs it because the instruction after mov cr3 is fetched at the same (identity-mapped, under the firmware) address. D3
Graphics Output Protocol (GOP)
Simple words: the firmware's description of the screen: where its memory is and how big it is. Analogy: the caretaker's note about the notice board: where it hangs and how many rows it has. Precise: the UEFI protocol giving the current mode's resolution, pixel format, pixels per scan line, and the framebuffer's physical base and size; the framebuffer stays valid after ExitBootServices. D1

Layer 1 — the kid explanation

The loader carries the kernel into memory, writes its note (F3-14), and builds a new map of addresses for the kernel. Then comes the handover. The firmware will only stop and leave if the loader shows it the newest list of who uses which memory. The loader asks for the list, and immediately, without changing anything, says "here is your list, you can go now". If the firmware says "that list is old", the loader asks again and tries again. When the firmware has gone, the loader cannot ask it for anything any more; it switches to the new map and jumps into the kernel.

Layer 2 — the student explanation

The loader is an ordinary UEFI application (F3-10) with seven steps, numbered in the comments of Listing 1:

  1. Find the volume. The Loaded Image protocol says which device the loader was loaded from; that device's Simple File System protocol opens its root directory.
  2. Read and check the kernel. The whole \kernel.elf is read into memory and checked with F3-14's elf::check before anything else happens. A bad file ends here with a message and a return to the firmware: the A3 rule "print a clear error and return to firmware instead of jumping".S1
  3. Place the kernel. One physically contiguous block of zeroed pages for the kernel's whole span; each segment's file bytes are copied in. The zero-fill of .bss is free because the pages were zeroed.
  4. Fill the boot information (all of F3-14's fields except the memory map, which must be the final one): RSDP and SMBIOS 3 addresses from the configuration table (F3-12), the framebuffer from GOP, the command line from \cmdline.txt.
  5. Build page tables: the kernel's pages with W and NX from the ELF flags; a direct map and an identity map of physical memory with 2 MiB pages; a stack.
  6. Hand over: get the memory map, call ExitBootServices with its key, retry on failure. After success, convert the map into the OS301 format.
  7. Jump: enable NX in EFER, disable interrupts, load CR3, load the stack pointer, put the BootInfo address in RDI, jump to the entry point.

The ExitBootServices rule in the curriculum's words: "The memory map key changes whenever memory is allocated. The loader must get the memory map, call ExitBootServices with that key, and retry by getting the map again if the call fails; after success no boot service may be used (no printing through the console protocol, no allocation). This is the most common first bug."S1 Listing 1 obeys it in three ways: every allocation the loader needs (including space for the final map, with room for 16 more entries) happens before the loop; the loop contains only GetMemoryMap and ExitBootServices; and after the loop, output goes to the serial port by direct port I/O, not through the console protocol.

Layer 3 — the engineer's depth

Why the key exists

The firmware owns memory until ExitBootServices. Its own drivers allocate and free memory while the loader runs (timers fire, a USB or network driver may react), and every allocation by the loader changes the map too. The memory map the kernel receives must describe memory exactly as the firmware leaves it, because the kernel will treat every range marked "boot services data" or "conventional" as free. If the map were one allocation out of date, a page the kernel thinks is free might hold the firmware's last data structure or, worse, a page the firmware still uses for a runtime service. The map key turns "is this map current?" into one comparison inside the firmware.D1

Three consequences shape the code. First, the buffer for the final map must exist before the final GetMemoryMap: allocating it afterwards changes the map you received a moment earlier. Listing 1 asks for the size first, adds room for 16 descriptors, and allocates both the raw buffer and the OS301 range array (lines 232–242). Second, the descriptor size is whatever GetMemoryMap says, never sizeof (F3-10). Third, the conversion of the raw descriptors into MemoryRange entries happens after ExitBootServices (lines 321–327), because it writes into memory already allocated and calls nothing.

Not verified — check before relying on this

From memory of the UEFI Specification (D1), not opened: after a failed ExitBootServices, the firmware may already have shut down part of its services, and the loader should call nothing but GetMemoryMap and ExitBootServices (some editions also allow the memory-allocation services) before trying again. Listing 1 follows the stricter reading in its normal build, except on its give-up path after four failures (line 315), which prints through the console. The forensic build prints through the console after a failure, which is a second rule violation; it worked on this OVMF build (R6). The status values 0x8000000000000001 (EFI_LOAD_ERROR) and 0x8000000000000002 (EFI_INVALID_PARAMETER, returned for a stale key) are also from memory of D1.

Building the page tables

The loader runs under the firmware's page tables: on x86-64 UEFI, long mode with an identity map.S1 It builds its own in pages it allocates as LoaderData, so they appear in the final memory map as loader memory, which the kernel must keep until it builds its own tables.

  • Kernel (lines 221–231): for each page of each segment, pte_slot walks PML4 → PDPT → PD → PT, creating missing tables with Present and Writable set, and the leaf entry gets Present, Writable only if the segment has W, and NX unless it has X. Permissions are decided at the last level, because the processor combines all levels: a page is writable only if every level allows writing, and executable only if no level sets NX.D3
  • Direct map (lines 243–267): the loader scans the map for the highest address of any RAM range, takes at least 4 GiB (the framebuffer and PCI windows live below 4 GiB), and builds one PDPT plus one page directory per GiB, each with 512 entries of 2 MiB pages (bit 7). The same PDPT is placed in PML4 entry 0 (identity map) and entry 256 (0xffff800000000000, the direct map).
  • Stack: 16 pages, used through the direct map.

The switch (lines 333–347) has an ordering constraint. After mov cr3, the next instruction is fetched through the new tables at the same virtual address as before, a low identity-mapped firmware address; without PML4 entry 0 the processor would fault on the next fetch, and with no interrupt handler of ours that ends in a triple fault and a reset. EFER.NXE is set before the switch, because with NXE off, bit 63 of an entry is a reserved bit and a page-table walk that meets it faults.D3 The stack pointer is set to the top minus 8, as if a call had pushed a return address, because the System V ABI expects RSP + 8 to be a multiple of 16 at a function's first instruction.D4

Not verified — check before relying on this

The PTE bit positions (0, 1, 7, 63), the address mask, the EFER MSR number 0xC0000080 and NXE as bit 11, the reserved-bit behaviour with NXE off and the permission-combining rule are from memory of the Intel SDM (D3), not opened. Evidence that the bits we wrote mean what we think: QEMU's monitor reports these entries, and a3_test.py decodes them with the same positions and finds what the ELF flags require (R2); this is consistent, not independent, because both sides use our reading of D3. The ABI stack-alignment rule is from memory of D4.

Testing from outside the machine

A kernel that prints "my pages are correct" proves little: the claim and the check would both be ours. a3_test.py (Listing 2) instead pauses the machine and asks QEMU, which implements the hardware, what is there. It reads CR3 from info registers, walks the four levels with xp (read physical memory) for every page of every PT_LOAD segment listed in the ELF file itself, and compares the W and NX bits with the segment flags. It compares the framebuffer base the kernel printed with the VGA device's BAR0 from info pci, and the reported size and pattern with a screendump image. All ten checks passed (R2).R2

One acceptance sentence was implemented with a difference worth stating. A3 says the kernel "as its first act, writes a known pattern to the framebuffer". The kernel stub prints "kernel entered" first and paints the framebuffer last (F3-14, Listing 1, lines 171–176); the test checks the painted pattern, not its order. The order was chosen so that the serial port shows how far the kernel got even if the framebuffer address were wrong; NOTES.md records this as a decision for the course owner.

How the hardware actually does it

ExitBootServices is not a hardware event: no signal changes on any pin. The firmware stops its timer interrupts and its drivers' activity, marks its boot-services memory as no longer its own, and returns; the processor continues in the same mode with the same page tables.D1 The hardware events in this chapter are the three instructions at the end. wrmsr to EFER turns on the interpretation of bit 63. mov cr3 makes the processor use a new top-level table and flushes the translations it cached (except global ones, which we do not use). jmp to a higher-half address is the first instruction fetch through the kernel mapping; if any level of that walk were wrong, this would be the faulting instruction.D3

The kernel's physical address in the run, 0xe753000 (about 231 MiB on a 256 MiB machine), is an observation about this OVMF: AllocatePages with AllocateAnyPages returned memory near the top of RAM. The loader does not depend on it; the kernel is position-independent in physical memory because the page tables decide where its virtual addresses point.R2

Not verified — check before relying on this

Untested on hardware: every run in this chapter used QEMU 8.2.2 (q35, std VGA, AHCI) with the distribution's OVMF (2024.02). Real firmware differs in how often its drivers allocate memory (more chances for a stale key), in the framebuffer format and pitch, and in memory above 4 GiB; the "at least 4 GiB" direct map would need to cover the real top of RAM, which the loop at lines 244–250 computes but which was only exercised with 256 MiB.

Worked example

Problem. For the lab machine (256 MiB of RAM, kernel of 3 pages at 0xffffffff80000000), compute (a) the PML4, PDPT, PD and PT indices of the kernel's first address and of the BootInfo's direct-map address if it is at physical 0xe756000; (b) how many 4 KiB pages of page tables the loader allocates; (c) the time spent in the handoff, from the TSC readings.

Solution. (a) An index is 9 bits: PML4 = bits 47–39, PDPT = 38–30, PD = 29–21, PT = 20–12. For 0xffffffff80000000: bits 47–39 are all ones → 511; bits 38–30 = 0b111111110 → 510; bits 29–21 = 0; bits 20–12 = 0. For 0xffff800000000000 + 0xe756000: PML4 = 256 (bit 47 set, the others zero); PDPT = 0 (below 1 GiB); PD = 0xe756000 >> 21 = 0x73 = 115; it is a 2 MiB page, so there is no PT level, and the offset in the page is 0xe756000 − 0x73 × 0x200000 = 0x156000.

(b) PML4: 1. Kernel path: a new PDPT, PD and PT (PML4 entry 511 was empty): 3. Direct map: 4 GiB → 1 PDPT and 4 PDs: 5. Total 9 pages = 36 KiB. The identity map costs nothing extra: it reuses the direct map's PDPT.

(c) From R2: before ExitBootServices +14,995,966, after +17,173,164: 2,177,198 ticks, which at the rate measured in F3-12 (about 2.0 to 2.1 × 10^9 ticks per host second) is about 1.0 to 1.1 ms, including one GetMemoryMap. From then to "kernel entered", +17,812,228: 639,064 ticks, about 0.3 ms, almost all of it the two serial lines printed at polling speed. The second healthy run (R7) gives 1,718,670 and 396,548 ticks: same order, different values. Treat these as observations of one emulator on one host, not as properties of UEFI.R2 R7

Where the analogy breaks


    

  1. The stamp is not a date. A map key is an opaque number; the firmware compares it for equality. Nothing about "older" or "newer" can be read from it.
    2. 

  2. The caretaker does not entirely leave. Runtime services (variables, time, reset) stay in memory and can still be called after the handover; the analogy's caretaker who "never comes back" overstates it.
    3. 

  3. Refusing is the friendly outcome. In the story the refusal is the problem; in UEFI, the refusal is the protection, and the bug is the loader that ignores it.
    4. 




Common mistakes and debugging


    

  • Printing between GetMemoryMap and ExitBootServices. Console output can allocate. Print before, or after through the serial port.
    • 

  • Allocating the final map's buffer after getting its size. The allocation changes the map; allocate with spare room first.
    • 

  • Ignoring ExitBootServices' status. The machine continues with firmware still running and the jump may even "work", until a firmware timer fires into memory the kernel has reused.
    • 

  • Using boot services after success. Console, allocation and file calls are gone; on some firmware they appear to work, on others they hang.
    • 

  • No identity map at the CR3 switch. Triple fault and reset immediately after mov cr3; QEMU with -no-reboot exits instead, and -d int shows the faults.
    • 

  • NX bits with EFER.NXE off. Reserved-bit page fault on the first fetch through the kernel mapping.
    • 

  • Passing the BootInfo in RCX. The loader is compiled with the Microsoft convention, the kernel with System V: be explicit, as the "D" constraint at line 346 is.
    • 




Transition box

Where you came from: F3-10 (the first UEFI application and the memory map), F3-12 (RSDP and SMBIOS), F3-13 (the disk), F3-14 (ELF, the protocol, the kernel stub). What carries over: all of them are now parts of one program; the map you printed in F3-10 is now the map you hand over. What changes: for the first time a program you wrote owns the machine with nobody underneath: no firmware services, no operating system, no debugger except the emulator's. What comes next: F3-16 asks whether the firmware should run your loader at all: Secure Boot checks a signature on loader.efi, and measured boot records a hash of it in the TPM.

Summary


    

  • The A3 loader: find the volume, read and check the kernel, copy it, fill the boot information, build page tables, exit boot services with the map key, jump.
    • 

  • The ExitBootServices rule: allocate everything first; in the loop, only GetMemoryMap and ExitBootServices; retry on failure; after success, no boot service at all.
    • 

  • Page tables: leaf entries carry W and NX from the ELF flags; one PDPT serves as identity map (PML4[0]) and direct map (PML4[256]); EFER.NXE before CR3.
    • 

  • Test from outside: QEMU's monitor (registers, physical memory, PCI, screen dump) gives evidence the kernel cannot fake.
    • 

  • A stale map key gives EFI_INVALID_PARAMETER (from memory of D1); a loader that does not retry hangs "after the logo". Whether a given allocation changes the key depends on the firmware: a 64-byte pool allocation did not here, a page allocation did.
    •

Answers to Check yourself


    

  1. Get the memory map, call ExitBootServices with the key that came with it, without allocating in between; if it fails, get the map again and retry; after success, use no boot service.
    2. 

  2. Allocating changes the memory map and its key; the map you received would no longer be the final one.
    3. 

  3. Right after mov cr3, the processor fetches the next loader instruction at its current low address through the new tables; that address must be mapped. The kernel can remove the identity map later.
    4. 

  4. Leaf: Present, not Writable, NX clear. Intermediate: Present and Writable, NX clear. The processor combines the levels (writable only if all allow it, no-execute if any sets NX), so permissive intermediate entries let each leaf decide for its own page.
    5. 

  5. A kernel with wrong page tables could also print wrong claims about them; QEMU reads the tables the processor actually uses (CR3 and physical memory), an independent observer.
    6. 

  6. (a), (c), (e). AllocatePages (b) and ConOut (d) are boot services.
    7. 

  7. 64 GiB → gib = 64 → 64 page-directory pages (plus one PDPT), 256 KiB, within the 512 GiB limit at line 252. The loop takes the highest end of every RAM-type range, so it would reach 64 GiB if the map lists RAM up to there; device windows above 4 GiB are left out by type.
    8. 

  8. The last line "loader: jumping to the kernel" and nothing more: the fetch after mov cr3 faults, no handler exists, a triple fault follows; with -no-reboot QEMU exits.

Forensic lab answer key


    

  1. Healthy: "kernel: halting" at 2.239 s, under 2 ms after "exiting boot services" (2.237 s). Build 1: the same, at 2.339 s. Build 2: the last line is at 2.559 s, 3 ms after "exiting boot services" (2.556 s), and then nothing until the harness stopped QEMU 25 s after start.
    2. 

  2. 0x8000000000000002 is an error (top bit) with code 2, EFI_INVALID_PARAMETER (from memory of D1); for ExitBootServices it means the map key was not the current one. The key 0x91a came from a GetMemoryMap that preceded the planted AllocatePages.
    3. 

  3. Build 2's AllocatePages changes the memory map (a new LoaderData page), so the key is stale; the call fails, and the planted code prints and spins instead of retrying: "stuck after the logo". Build 1's 64-byte AllocatePool did not make ExitBootServices fail on this firmware. The hypothesis: OVMF served the pool request from a pool page it had already allocated, so the map (and the key) did not change. The rule is not "small allocations are safe": another firmware, or the same one with a fuller pool, may change the key for build 1 too.
    4. 

  4. Rejected: the healthy loader on the same firmware boots (evidence 1), and the failure follows the code change, not the firmware. The status names the cause.
    5. 

  5. Remove the allocation from the loop (allocate the log buffer before the final GetMemoryMap), and keep the retry so that any stale key, from the loader or from a firmware driver, is survived. Rule: between the final GetMemoryMap and ExitBootServices, call nothing; always handle ExitBootServices' status with a retry.
    6.
