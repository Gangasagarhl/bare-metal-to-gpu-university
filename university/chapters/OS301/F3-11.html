Story hook

Analogy

The caretaker's morning is not one job but a round with a fixed order: first the front door and the alarm panel, then the boiler room so the building has heat, then every classroom and corridor light, and last the board in the hall where the day's timetable is pinned. Each step needs the one before it. Nobody switches on classroom lights before the power is on.

UEFI firmware has the same kind of round, with names: SEC, PEI, DXE and BDS. In F3-09 you watched the first eight instructions; in F3-10 you were a guest that the firmware called at the end. This chapter opens the firmware file itself. You will write a tool that lists every module inside OVMF and sorts them by phase, unpack the compressed part of the image, and watch the processor move from the flash chip into RAM during the first second. Then you will meet a firmware image that is broken in a way that its own volume checksums do not notice.

What you will be able to do

  • Name the PI phases SEC, PEI, DXE and BDS (and the later TSL, RT and AL), what each must achieve, and what it hands to the next.
  • Explain the PI firmware storage format: firmware volumes, firmware files with a type and a GUID, and sections (compressed, user-interface name, volume-in-a-section).
  • List the modules of a real firmware image by phase with your own C++ tool, including the volumes packed inside an LZMA-compressed section.
  • Observe the processor's mode and memory region over time from the QEMU monitor, and connect what you see to the phases.
  • Diagnose a firmware image that hangs before printing anything, using a byte comparison, the module list and the CPU samples together.
Jargon box
PI (Platform Initialization)
Simple words: the standard for how UEFI firmware itself is built inside: its phases and its module formats. Analogy: the written order of the caretaker's morning round. Precise: the UEFI Forum's Platform Initialization Specification, which defines the boot phases (SEC, PEI, DXE, BDS and later ones), the interfaces between modules in each phase, and the firmware storage format; the UEFI Specification defines what the OS loader sees, PI defines how the firmware gets there. D1
SEC (security phase)
Simple words: the first firmware code after reset; it sets up temporary memory and finds the next phase. Analogy: the front door and the alarm panel. Precise: the phase that handles the reset, establishes a temporary memory store (cache-as-RAM on real processors), may act as the root of trust, and passes control and a description of the temporary memory to the PEI core. D1
PEI (pre-EFI initialization)
Simple words: the phase that makes the real memory work. Analogy: the boiler room: nothing else is usable until it runs. Precise: a small dispatcher (the PEI core) that runs PEI modules (PEIMs) in dependency order, with interfaces called PPIs; its main duties are initialising permanent memory and describing the platform in hand-off blocks (HOBs) for DXE. D1
HOB (hand-off block)
Simple words: a small record that PEI leaves for DXE: "here is memory", "here is a firmware volume". Analogy: a note pinned on the boiler-room door for whoever comes next. Precise: an entry in the HOB list, a sequence of typed, length-prefixed records built during PEI (resource descriptors, memory allocations, firmware-volume locations, GUID-identified data) and passed to the DXE core. D1
DXE (driver execution environment)
Simple words: the phase where most firmware drivers run and the UEFI services appear. Analogy: switching on every classroom and corridor. Precise: the phase in which the DXE core builds the UEFI boot and runtime services, and a dispatcher loads DXE drivers from firmware volumes in dependency order; drivers install protocols for buses and devices and produce tables such as ACPI and SMBIOS. D1
BDS (boot device selection)
Simple words: the phase that picks what to boot and starts it. Analogy: the timetable board. Precise: the phase that connects consoles and boot devices, reads the boot variables (BootOrder, Boot####), and loads and starts a boot option, falling back to defaults; in EDK II it is a DXE driver, BdsDxe. D1 D2
Firmware volume (FV), firmware file (FFS) and section
Simple words: the boxes inside a firmware image: volumes hold files, files hold sections. Analogy: cupboards, folders in the cupboards, pages in the folders. Precise: an FV is a region with a header (signature "_FVH", length, header checksum) holding firmware files; each file has a 24-byte header with a GUID name, a type (SEC core, PEI core, PEIM, DXE core, driver, application, raw, volume image…) and a size; a file's data is a series of sections, some of which contain code, a user-interface name, compressed data or a whole nested volume. D1

Layer 1 — the kid explanation

The firmware is not one program but a box of many small programs, and it starts them in four rounds. Round one, very short, runs straight from the chip and prepares a tiny scratch space. Round two gets the big memory working. Round three starts dozens of little helpers, one for each kind of device: the disk, the keyboard, the screen, the network. Round four looks at the list of things you can boot and starts one. Each round leaves notes for the next.

Layer 2 — the student explanation

The PI Specification splits the firmware's work by what is available. In SEC nothing is: there is no RAM, so code runs from flash and the first job is temporary memory for a stack. On real processors that memory is the cache, configured so that it does not write back to the (not yet working) DRAM.D1 D3 SEC finds the PEI core and calls it.

In PEI there is a little temporary memory, and the PEI core runs small modules (PEIMs) in an order decided by their dependencies. The modules talk to each other through PEIM-to-PEIM interfaces (PPIs). The single most important PEIM on a real board initialises the DRAM. Once permanent memory works, PEI copies what it needs there and records what it learnt in HOBs: where the memory is, where the firmware volumes are. The last PEIM to run, the DXE initial program load, starts the DXE core and passes it the HOB list.D1

In DXE memory is plentiful. The DXE core creates the UEFI boot services and runtime services you used in F3-10, then dispatches DXE drivers from the firmware volumes, again in dependency order. Drivers install protocols (interfaces identified by GUIDs) on handles: PCI buses, disk controllers, file systems, consoles, the graphics output. Drivers also publish the ACPI and SMBIOS tables of F3-12. When nothing more can be dispatched, BDS runs: it connects consoles and boot devices, reads the boot variables and starts a boot option. Your loader runs in the phase the PI Specification calls the transient system load (TSL); after ExitBootServices the OS runs in the runtime (RT) phase.D1 D2

All these modules are stored in one image with a standard layout: firmware volumes contain firmware files, each with a GUID and a type that says which phase it belongs to, and files contain sections. A section can hold code (a PE32 or TE image), a human-readable name, or another volume, possibly compressed. Your tool in this chapter reads exactly that layout.

Layer 3 — the engineer's depth

Reading the storage format

Listing 1 (fvscan.cc) looks for volumes by their signature: the four bytes "_FVH" at offset 40 of a volume header, preceded at offset 32 by the volume's 64-bit length. It checks the header checksum: the 16-bit words of the header, added together, must give zero.D1 Inside a volume, files start on 8-byte boundaries; each file header is 24 bytes: a 16-byte GUID name, an integrity-check field, the type at byte 18, attributes, a 24-bit size at bytes 20–22 and a state byte. A file whose 24 header bytes are all FFh marks the start of erased flash: the end of the volume's contents. Sections follow the file header, 4-byte aligned, each with a 24-bit size and a type byte; type 15h is the user-interface section (the module name in UCS-2), 17h a volume image, and 02h a GUID-defined section whose GUID says how to decode it.D1

Not verified — check before relying on this

The volume-header offsets (length at 32, "_FVH" at 40, header length at 48, extended-header offset at 52), the 24-byte file header and its field positions, the large-file and large-section size escapes (FFFFFFh), the file-type numbers (01h raw … 0Dh MM core, F0h pad), the section-type numbers (02h, 15h, 17h), the alignment rules and the GUID of the LZMA decompression section (ee4e5898-…) were written from memory of the PI Specification, Volume 3 ("Firmware Storage"), which could not be opened. The evidence that they are right for this image is indirect: with them, the tool finds 127 named modules whose names match the boot messages of later chapters (BdsDxe, Shell), every header checksum is zero, and the walk ends exactly at the end of every volume (R1). A wrong rule for a case this image does not contain would not show up. Check every field against D1 before reusing the tool on other firmware.

What is inside this OVMF

Listing 1's output on OVMF_CODE_4M.fd (R1) gives the structure of Figure 2. Three observations are worth stating carefully, each with its evidence:

  1. Only SEC is stored uncompressed. The volume at 0x348000 holds SecMain (type SECURITY_CORE, 41,534 bytes) and a 2,504-byte RAW file. Everything else is inside one LZMA-compressed section of 1,495,727 bytes that unpacks to 16,122,000 bytes. Something must unpack it before PEI can run; since SEC is the only code stored in the clear, SEC (or code it calls) must do it.R1
  2. The reset vector is a file. Listing 3's output shows that the RAW file is the last file of the SEC volume, occupies file offsets 0x37B638–0x37BFFF, and ends exactly at the end of the image: the 16 bytes F3-09 disassembled are its last 16 bytes.R2 A firmware build tool must therefore place this file last in the last volume, so that it ends at 4 GiB.
  3. Phases map to volumes. The first unpacked volume holds PeiCore and 13 PEIMs (among them PlatformPei, CpuMpPei, the TPM-related Tcg2Pei, and DxeIpl, the DXE initial program load). The second holds DxeCore, 109 drivers and two applications, UiApp (the setup menu) and Shell, the UEFI Shell that ran your A1 program in F3-10. BdsDxe, the BDS phase, is one of the 109 drivers.R1

Two names appear twice, CpuMpPei and CpuDxe, with different GUIDs and sizes. The tool reports what it finds; why this build carries two modules with the same user-interface name is a question for the build description (the FDF file of OvmfPkg, D4), not something the binary answers. It is the extension task of the lab.

The phases in time

Listing 2 (sample.py) asks QEMU every 5 ms for the registers and prints a line whenever the processor mode or the memory region of the next instruction changes. In this build's run (R3): real mode at FFFFFFF0h at the first sample; long mode, still executing from flash, about 6 ms later; and the first instruction in RAM above 1 MiB at about half a second. The healthy run did not catch the 32-bit protected-mode stage, while the forensic run, which starts identically, did: a 5 ms sampling interval misses stages that last less than that. Sampling shows what is true at the sampled moments, never what happened between them.R3 R5

Three cross-checks tie the samples to the phases and to F3-10's memory map (all addresses from this build's runs, same 256 MiB machine):

  • The long stretch executing from flash in long mode is SEC (and its decompression work): only SEC is uncompressed, so only SEC can run from flash.
  • The first RAM address, 0x82257d, lies in the range 0x810000–0x8fffff, which F3-10's memory map reports as ACPI NVS memory (descriptor 7). The firmware placed early code there and later protected that range from the OS.R3 R6
  • The final RIP, 0xecfe372, lies in descriptor 103 of F3-10's map (BootServicesCode at 0xecfe000, 0x17 pages): DXE driver code, which is what boot-services code is. The 16 bytes there begin with eb dd, a short jump 35 bytes backwards: the firmware is in a waiting loop.R3 R6
Not verified — check before relying on this

Not checked in the EDK II source (D4): that OVMF's SEC decompresses the main volume itself; that the RAM range at 0x820000 holds the unpacked PEI volume; that this is why the memory map marks it ACPI NVS (a common reason is S3 resume, which needs PEI again); and which loop runs at 0xecfe372. The observations (addresses, modes, types) are from the runs; the explanations are the most likely ones, not verified ones.

Why the phases exist

The split is not arbitrary. SEC exists because the first code runs with no memory at all and must be tiny and trusted. PEI exists because memory initialisation needs code that runs without a heap, in a few KiB of cache, and that code should be as small as possible. DXE can then be written like ordinary C with a memory allocator, and can be large: in this OVMF, the DXE volume is about 16 times the size of the PEI volume (0xE80000 versus 0xE0000).R1 BDS is separated so that the policy "what to boot" can change without touching the drivers. The same split appears in other firmware with other names: coreboot's bootblock, romstage, ramstage and payload follow the same logic of "no memory, then memory, then devices, then boot" (F3-17).D3 D5

How the hardware actually does it

The phases are software; what forces them is hardware. On a real PC the processor's caches can be configured as a small writable memory before DRAM works (cache-as-RAM, or "no-evict" mode), and SEC sets that up; the DRAM controller needs per-board training code, provided by the silicon vendor and run in PEI; and multi-core processors start their other cores only when firmware sends start-up messages, a job of a CPU module such as the CpuMpPei and CpuDxe found in this image.D3 D6 QEMU needs none of that: RAM works from the first cycle, and OVMF's platform module (PlatformPei) learns the memory size from QEMU instead of training anything. That is why OVMF can afford to keep almost everything compressed and unpack it into RAM early.D4

Not verified — check before relying on this

Untested on hardware: no real board's firmware was examined. A vendor image is often protected, signed or encrypted in parts, may use other compression, and contains silicon-vendor modules whose names reveal little. The statements about cache-as-RAM, memory training in PEI and AP start-up come from title-only sources (D3, D6) and must be checked there before teaching them as fact. Never read or write the flash of a machine you depend on with tools that were not made for that board.

Worked example

Problem. Using only Listing 1's output (R1), estimate (a) the compression ratio of the main volume, (b) the share of the unpacked data used by the two inner volumes, and (c) the size of the largest DXE driver and why that driver might be large.

Solution. (a) 16,122,000 / 1,495,727 ≈ 10.8: the compressed section is about 9 % of its unpacked size. (b) The first inner volume starts at offset 0x80 of the unpacked data and is 0xE0000 = 917,504 bytes long, so it ends at 0xE0080; the second starts at 0xE0090 (16 bytes later) and is 0xE80000 = 15,204,352 bytes long, so it ends at 0xF60090. In decimal, 0xF60090 = 15 × 1,048,576 + 6 × 65,536 + 144 = 16,122,000: exactly the unpacked size. The two volumes fill the section; only the first 0x80 bytes and the 16-byte gap are something else (headers of the enclosing file and section, and alignment). (c) Scanning the DRIVER lines, the largest is TlsDxe with 918,910 bytes, larger than the UEFI Shell (885,078 bytes); a TLS implementation carries a cryptographic library, which is large code. The reason is an inference from the name; confirming it means reading the module's build description (D4).R1

Check. Keep hexadecimal and decimal side by side: 0xE0000 + 0xE80000 = 0xF60000 = 16,121,856, and 16,122,000 − 16,121,856 = 144 = 0x80 + 0x10, the offset of the first volume plus the gap. Both ways give the same answer.

Where the analogy breaks


    

  1. The round is not strictly one room after another. PEI and DXE dispatch modules by dependency, not by a fixed list: a module runs when the interfaces it needs exist. A caretaker's round is a fixed route.
    2. 

  2. Earlier rounds do not always finish. On resume from sleep (S3), firmware runs SEC and PEI again and then jumps back to the OS without DXE; the "morning round" restarts halfway.D1
    3. 

  3. The caretaker builds the boiler before using it. In PEI the code that brings up memory runs without that memory. There is no school equivalent of "heat the building with a boiler that does not exist yet".
    4. 

  4. Some notes stay pinned after the caretaker leaves. HOBs end with DXE, but runtime services, ACPI tables and system-management code continue under the OS.
    5. 




Common mistakes and debugging


    

  • Searching for "_FVH" at offset 0. The signature is at offset 40 of the header, not its start.
    • 

  • Treating a header checksum of "ok" as "the volume is intact". It covers the header only (forensic lab).
    • 

  • Stopping at the first all-FFh GUID. Pad files have one; check the whole 24-byte header for erased flash.
    • 

  • Ignoring alignment. Files are 8-byte aligned and sections 4-byte aligned; forgetting to round up makes the next header read from the wrong place.
    • 

  • Reading time from sampling as duration. Sample times are host wall-clock times under QEMU's emulation (the run record says so); they show order, not the speed of any PC.
    • 

  • Expecting a debug log from a release build. The distribution's OVMF prints nothing on QEMU's debug console in this build; phase transitions must be inferred (this chapter) or come from a debug build (F3-17).
    •

Summary


    

  • PI firmware runs in phases: SEC (no memory; temporary RAM), PEI (memory initialisation; HOBs), DXE (drivers, UEFI services, tables), BDS (choose and start a boot option); then TSL (your loader), RT (the OS) and AL.
    • 

  • Firmware images are volumes of files of sections; file types say which phase runs a module; sections hold code, names, compressed data or nested volumes.
    • 

  • In this OVMF only SEC and the reset-vector file are stored uncompressed; PEI and DXE are in one LZMA section that unpacks to about 10.8 times its size.
    • 

  • Sampling the CPU from the QEMU monitor shows real mode, then long mode from flash, then execution in RAM; short stages can fall between samples.
    • 

  • Addresses from samples can be matched to F3-10's memory map: DXE driver code is boot-services code.
    • 

  • A volume header checksum covers only the header; damage inside a compressed section passes it and stops the boot before any output.
    •

  4. Because right after reset there is no working RAM; code that initialises memory must run with only flash and a few KiB of temporary memory, without a heap. PEI is the small, constrained environment for that job; DXE's large drivers with allocators can only run once memory works.
