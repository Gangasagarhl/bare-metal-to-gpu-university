Story hook

Analogy

The old school building had one caretaker routine, written on a card forty years ago: unlock the front door, switch on the hall lights, walk to room 1, open it. Whoever taught in room 1 had to know the building's quirks by heart. The new building has a front desk with a directory, a set of tools on loan (keys, a ladder, the floor plan) and a written list of every room and what it is for; when the principal arrives, the caretaker hands over the list, takes back the tools, and leaves only a small office open for emergencies.

PCs have both buildings. For decades the firmware was the BIOS: a 16-bit program that loaded the first 512 bytes of a disk to a fixed address and jumped there, offering services through software interrupts. Today's PCs run UEFI firmware, which loads real executable files from a file system, calls them in 64-bit mode, and offers its services through tables of function pointers. In this chapter you write a program for each: a boot sector in assembly that runs under SeaBIOS and asks for the BIOS memory map, and a UEFI application in C++ that runs under OVMF and prints the UEFI memory map. Then you compare what the two firmwares told you about the same virtual machine.

What you will be able to do

  • Compare the legacy BIOS boot path and the UEFI boot path: processor mode, how the first program is found and loaded, how services are reached, and how memory is described.
  • Build a PE32+ UEFI application in C++ with clang and lld-link, without EDK II, and run it in QEMU with OVMF (milestone A1, route (b)).
  • Read a UEFI memory map: descriptor size and version, memory types, attributes, and which types the OS may reuse after ExitBootServices.
  • Write a 512-byte boot sector that loads a second sector through the BIOS disk services and prints the E820 memory map (milestone A5).
  • Diagnose a legacy disk that the BIOS refuses to boot by reading the firmware's own debug log.
Jargon box
BIOS (legacy)
Simple words: the original PC firmware, which starts in 16-bit mode and loads the first sector of a disk. Analogy: the old caretaker's routine on a card. Precise: the IBM PC-compatible Basic Input/Output System: firmware that initialises the platform, loads sector 0 of the boot device to 0000:7C00h, jumps to it in real mode, and provides services through software interrupts (INT 10h video, INT 13h disk, INT 15h system, among others). D4 D6
UEFI
Simple words: the modern PC firmware standard; it starts programs stored as files and offers them services in tables. Analogy: the new front desk with a directory and tools on loan. Precise: the Unified Extensible Firmware Interface, a specification of the interface between firmware and OS loaders: a system table with boot services and runtime services, protocols identified by GUIDs, a boot manager driven by variables, and PE32+ images as the executable format. D1
Boot services and runtime services
Simple words: two groups of firmware functions: one usable only while booting, one that stays available to the OS. Analogy: the tools on loan and the small office that stays open. Precise: function tables reached from the EFI system table; boot services (memory allocation, protocol lookup, image loading, ExitBootServices) end when the loader calls ExitBootServices; runtime services (variables, time, reset) remain callable by the OS. D1
Memory map (UEFI) and E820
Simple words: the firmware's list of which physical address ranges are RAM and which are reserved. Analogy: the written list of every room and what it is for. Precise: UEFI's GetMemoryMap returns an array of descriptors (type, physical start, number of 4 KiB pages, attributes) plus a map key; the legacy equivalent is the list returned entry by entry by INT 15h with EAX = E820h (base, length, type). D1 D6
PE32+
Simple words: the 64-bit Windows executable file format, which UEFI also uses for its programs. Analogy: the standard form every visitor must fill in at the desk. Precise: the Portable Executable format with the optional-header magic 0x20B (64-bit); UEFI images use it with subsystem values for applications and drivers. D1 D7 R1
Boot sector (MBR boot code)
Simple words: the first 512 bytes of a disk, which an old BIOS loads and runs. Analogy: the instructions taped inside the door of room 1. Precise: sector 0 of a disk; a legacy BIOS checks that bytes 510 and 511 are 55h and AAh, loads the sector to physical address 7C00h and jumps to it with the boot drive number in DL. D4 D6
GUID
Simple words: a 128-bit number used as a name that nobody else will pick by accident. Analogy: a unique room code that cannot be confused with another school's. Precise: a globally unique identifier; UEFI names protocols, configuration tables and variable namespaces with GUIDs. D1

Layer 1 — the kid explanation

There are two kinds of caretaker in PCs. The old kind reads the first little piece of a disk, puts it at one fixed place in memory and runs it; that piece must know everything else by itself. The new kind, UEFI, understands files: it opens a folder on the disk, finds a program with a known name, and runs it. While that program runs, the caretaker lends it tools: "give me memory", "print this", "read that file", "what does the memory look like?". When the operating system is ready to take over, it gives the tools back.

Layer 2 — the student explanation

Legacy BIOS. After the platform is initialised, the BIOS reads sector 0 of the first bootable disk into memory at 7C00h and checks the last two bytes for the signature 55h AAh. If they match, it jumps to 0000:7C00h in real mode with the boot drive number in DL.D4 D6 The 512 bytes must do everything themselves: set up segments and a stack, read more sectors through INT 13h, ask for the memory map through INT 15h function E820h, and eventually switch the processor to protected and long mode. The BIOS's services are available only in real mode; once the OS switches modes it stops using them.D4 Our boot sector (Listing 3) does the first steps and prints to the serial port.

UEFI. UEFI firmware reads a FAT file system on the disk and loads a PE32+ executable: either the one named by a boot option stored in a firmware variable, or, for removable media and disks without options, a default file path.D1 It calls the image's entry point in long mode with two arguments: a handle that identifies the image and a pointer to the EFI system table. The calling convention on x86-64 is the Microsoft x64 one (arguments in RCX and RDX), which is why this course compiles UEFI code with clang for the x86_64-unknown-windows target: the compiler then uses that convention and lld-link writes a PE32+ file.D1 D7 From the system table the program reaches the console, the boot services (memory, protocols, images, ExitBootServices) and the runtime services (variables, time, reset). Our program (Listing 1) prints a greeting, asks for the memory map, prints every descriptor and the totals per type, and returns to the firmware.

Why both matter. New PCs boot with UEFI; many have removed the compatibility support module (CSM) that let UEFI firmware boot legacy disks. But old code and old documentation are full of 7C00h, INT 13h and E820, and QEMU still boots legacy disks with SeaBIOS by default. Milestone A5 exists so that you can read that history; A1 is where the course's own loader begins.S1

Layer 3 — the engineer's depth

Choosing a route for A1

The milestone offers three routes: (a) an EDK II module built with the EDK II build system, (b) a minimal header set with clang targeting the Windows-style UEFI triple and LLD producing PE32+ directly, or (c) gnu-efi with a conversion step.S1 This course takes route (b), for three reasons that you should record in your own design log if you choose it too: the build container has clang 18 and lld but no EDK II tree; the whole toolchain is two commands, which fits on one line of a run record; and every declaration your program depends on is in one file you can read (efi.hpp). The price is that nobody checked that file against the specification for you. The milestone also asks you to wrap the C interfaces in small C++ classes, with no exceptions and no RTTI: Console (Listing 2) is that wrapper.

What the build produces

The build record (R1) shows the file is COFF-x86-64 with optional-header magic 0x20B (PE32+), subsystem IMAGE_SUBSYSTEM_EFI_APPLICATION (0xA), entry point at relative address 0x1000 and a preferred image base of 0x140000000.R1 The firmware does not have to load the image at that base; it relocates it using the file's base-relocation data, which lld-link emits for this target.D7 The compile flags matter: -ffreestanding (no hosted C library assumed), -fno-exceptions -fno-rtti (no runtime support for either exists), -mno-red-zone (firmware interrupt handlers may write below the stack pointer, so the 128-byte red zone of the System V ABI is unsafe; the Microsoft x64 ABI has none anyway), -fno-stack-protector (no guard symbol to link against).D1 The linker flags name the subsystem, the entry symbol and say "no default libraries".

GetMemoryMap, carefully

Three rules from Listing 1 are worth memorising, because F3-15 depends on them:

  1. Ask for the size first. Called with a zero-sized buffer, GetMemoryMap fails with EFI_BUFFER_TOO_SMALL and writes the size it needs.D1
  2. Allocate with spare room. Allocating the buffer can split a free range and add a descriptor; the listing adds room for four more descriptors.
  3. Step by the descriptor size the firmware returns, never by sizeof. The specification allows the firmware's descriptor to be larger than the structure your header declares, so that the structure can grow.D1 In this build the firmware reported 48 bytes, version 1, while the five fields of MemoryDescriptor occupy 40 bytes (4 + 4 bytes padding + 4 × 8).R2 Stepping by 40 would have read garbage from the second descriptor onwards.

The memory types fall into three groups for an OS. Free after ExitBootServices: conventional memory, loader code and data (yours), boot-services code and data. Keep: runtime-services code and data (the firmware still runs there), ACPI NVS, reserved, MMIO, unusable. Free after reading: ACPI reclaim memory holds the ACPI tables; the OS may reuse it after it has parsed them (F3-12).D1 Listing 1 prints "conventional" and a conservative "usable after ExitBootServices" (the first group only).

The attribute column also tells a story: 0x000000000000000f on RAM ranges sets four caching-capability bits (uncacheable, write-combining, write-through, write-back), and 0x800000000000000f on the runtime ranges adds bit 63, EFI_MEMORY_RUNTIME: "this range must be mapped by the OS if it wants to call runtime services".D1 R2

Not verified — check before relying on this

Written from memory and not checked against the UEFI Specification (D1), which could not be opened: the layouts and slot orders in efi.hpp (EFI_SYSTEM_TABLE, EFI_BOOT_SERVICES, EFI_RUNTIME_SERVICES, EFI_MEMORY_DESCRIPTOR, the protocol structures and the GUID values); the meaning of the attribute bits 0–3 and 63; the rule that loader and boot-services memory become free after ExitBootServices; the Microsoft x64 calling convention requirement; and the default removable-media path (shown working in F3-13, but its exact wording in D1 is unchecked). What the runs show is narrower: OVMF 2024.02-2ubuntu0.10 ran code built on these declarations and returned plausible values (R2, R3). A wrong slot in a table that happens not to be called would not show up. Check every structure in D1's sections "EFI System Table", "Boot Services" (memory allocation services), "Simple Text Output Protocol" and "Image Entry Point" before reusing the header.

The legacy path in 1,024 bytes

Listing 3 is two sectors. Stage 1 (sector 0) zeroes the segment registers, puts the stack below its own code at 7C00h, saves DL, programs the 16550 UART of COM1 at I/O port 3F8h, prints a greeting, checks for the extended disk services (INT 13h AH = 41h, BX = 55AAh) and reads sector 1 to 7E00h with AH = 42h and a 16-byte disk address packet. Stage 2 calls INT 15h with EAX = E820h, EDX = "SMAP" and ECX = 24 in a loop, printing base, length and type, until EBX returns 0; then it writes 10h to the isa-debug-exit port F4h, which makes QEMU exit with status (10h << 1) | 1 = 33.D6 D8 R4 The milestone's next step (switch to protected and long mode) is left to the mini-project.

Not verified — check before relying on this

The BIOS service numbers and register conventions in Listing 3 (INT 13h AH = 41h and 42h, the disk-address-packet layout, INT 15h EAX = E820h with the "SMAP" signature, the 24-byte buffer, the meaning of EBX = 0 and of type 1 and 2), the 16550 register offsets, and the isa-debug-exit formula were written from memory. The run shows they work with SeaBIOS 1.16.3 and QEMU 8.2.2 (R4); they were not checked against the documents named in D4, D6 and D8, and other BIOSes may differ (for example in how they report the last entry).

How the hardware actually does it

Neither path is hardware in the strict sense: both are firmware conventions on top of the same processor. What the processor contributes is the reset state of F3-09 and the mode switches. In this build both firmwares ran in QEMU's q35 machine with 256 MiB of RAM, and both read QEMU's description of the machine through QEMU's firmware configuration interface: SeaBIOS's log says so ("Found QEMU fw_cfg", followed by "qemu/e820" lines with QEMU's own RAM and reserved ranges).R6 On a real PC, the firmware builds the memory map from what the memory controller and the platform report after memory training, and the BIOS or UEFI implementation is the board vendor's. The two firmwares here also placed PCI Express configuration space differently (SeaBIOS: "q35 mmconfig at 0xb0000000"; OVMF: a reserved range at 0xe0000000, which F3-12 confirms from the ACPI MCFG table), a reminder that the firmware, not the processor, decides much of the address map.R2 R6

Not verified — check before relying on this

Untested on hardware: no program of this chapter ran on a real PC. On a spare PC, A1's application runs from a USB stick formatted FAT32 at the default removable path (F3-13); a legacy boot sector needs a machine whose firmware still offers legacy (CSM) boot, which many current machines do not. Whether a given machine has a serial port, and on which port, must be checked in its documentation; without one, the UEFI program's console output still appears on screen, but the boot sector's serial output does not.

Safety

QEMU first. A boot sector written to the wrong disk overwrites that disk's partition table: never run dd towards a device name you have not checked twice, and never on a machine you depend on. Use a spare USB stick on a spare machine for the optional hardware step.

Worked example

Problem. With -m 256M, Listing 1 reports "usable after ExitBootServices KiB: 255776", while QEMU was given 256 MiB = 262,144 KiB. Account for every missing KiB using the totals and the descriptor list of the 256 MiB run.

Solution. Missing: 262,144 − 255,776 = 6,368 KiB. Not counted as usable, from the totals: RuntimeServicesCode 1,024 KiB + RuntimeServicesData 2,324 KiB + ACPIReclaim 72 KiB + ACPINVS 2,052 KiB = 5,472 KiB. The type "Reserved" has a large total (12,845,568 KiB), but most of it lies above RAM (descriptor 130 at 0xfd00000000, 0x300000 pages = 12 GiB, and descriptor 128 at 0xe0000000, 256 MiB); only descriptor 117, 0x80 pages = 512 KiB at 0xf6ed000, is inside RAM. 5,472 + 512 = 5,984 KiB. The remaining 384 KiB: descriptors 1 and 2 jump from 0xa0000 (end of descriptor 1: 0x1000 + 0x9f pages × 4 KiB) to 0x100000. That range, 0xa0000–0xfffff, is the legacy VGA and ROM area, and the map does not list it at all: 0x60000 bytes = 384 KiB. 5,984 + 384 = 6,368 KiB. Every KiB is accounted for.R2

Second part. Conventional memory alone is 212,020 KiB, 50,124 KiB (48.9 MiB) short of 256 MiB, and exactly the same 48.9 MiB short at 512 MiB (R3). The difference between conventional and usable is boot-services memory and loader memory (39,460 + 3,400 + 888 + 8 = 43,756 KiB): the firmware's own drivers, the UEFI Shell (loaded as loader code) and our program. That memory is in use while the program runs, and free once an OS has called ExitBootServices.R2 R3

Where the analogy breaks


    

  1. The "tools on loan" are code running on the same processor. A boot service is not a person doing work in parallel; when your program calls AllocatePool, your program's thread of execution runs the firmware's code and returns. There is no second worker.
    2. 

  2. The caretaker can still be inside the building after the handover. Runtime services stay, and firmware code in system management mode can run at any time without the OS seeing it (F3-12, F3-16). "Takes back the tools and leaves" is only true for boot services.
    3. 

  3. The old building's card is not simpler for the reader. The legacy path looks smaller, but it hands the boot sector a machine in 16-bit mode with no file system, no memory allocator and a 512-byte limit; all of that complexity moves into the boot loader.
    4. 




Common mistakes and debugging


    

  • Compiling UEFI code for the Linux target. clang++ --target=x86_64-linux-gnu uses the System V calling convention and writes ELF; the firmware's calls would pass arguments in the wrong registers, and the file would not load at all. Use the Windows target and lld-link.
    • 

  • Forgetting \r. The UEFI console moves to the next line on \n without returning to column 0; output becomes a staircase.
    • 

  • Stepping by sizeof(MemoryDescriptor). See rule 3. Symptom: plausible first line, garbage afterwards.
    • 

  • Missing a slot in a function table. Every slot after the missing one calls the wrong function. Symptom: a call that does something unrelated, or an exception dump with a strange instruction pointer.
    • 

  • Expecting a hosted C++ runtime. No std::vector, no new, no global constructors unless you call them; the compiler may still emit calls to memset and memcpy (F3-15 has to provide them).
    • 

  • Boot sector: wrong org, or relying on DS. Strings print as garbage. Set the segment registers yourself.
    • 

  • Boot sector: a disk image of exactly 1,024 bytes. In this build SeaBIOS could not read such a small image; padding it to 1 MiB with truncate fixed it (see the comment in run.sh).
    • 




Transition box

Where you came from: F3-09 followed the processor from reset to the firmware's long-mode page tables, and SP301 taught C++ close to the bytes. What carries over: the reset state and real mode of F3-09 are exactly the environment the boot sector runs in; the long-mode, identity-mapped environment F3-09 observed is the one a UEFI application is called in.D1 What changes: you now write code that the firmware runs: a freestanding C++ program with no C++ runtime, calling the firmware through tables of function pointers, built for a different executable format and calling convention than your Linux programs. What comes next: F3-11 opens the firmware itself: how OVMF is organised into SEC, PEI, DXE and BDS modules, and how to list them from the firmware file.

Forensic lab


Scenario: "The old disk image does nothing". Kofi keeps a legacy boot-sector demo for a history lesson. Summary


    

  • A legacy BIOS loads 512 bytes ending in 55 AA to 7C00h and runs them in real mode; services are software interrupts (INT 13h disk, INT 15h E820 memory map).
    • 

  • UEFI loads a PE32+ file from a FAT file system, calls it in long mode with an image handle and a system-table pointer, and offers boot services, runtime services and GUID-named protocols.
    • 

  • Route (b) of A1: clang for x86_64-unknown-windows plus lld-link, freestanding C++ without exceptions or RTTI, and one hand-written header that must be checked against the specification.
    • 

  • GetMemoryMap: ask for the size, allocate with spare room, step by the returned descriptor size (48 bytes here, not 40).
    • 

  • While a UEFI program runs, much RAM is boot-services or loader memory; after ExitBootServices the OS may reuse it. In this build every KiB between "usable" and the RAM size was accounted for.
    • 

  • When a legacy disk does not boot, the firmware's debug log says why ("not a bootable disk" = missing signature).
    •

Those pages are not "conventional" (free) at that moment, although an OS may reuse them after ExitBootServices. The constant 48.9 MiB at both sizes shows it is a fixed cost of the running firmware, not a fraction of RAM.
