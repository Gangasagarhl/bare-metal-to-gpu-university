Story hook

Analogy

The school keeps its room plan in two places: one copy behind the front entrance and one by the back door, each with a check number at the bottom. One morning the caretaker finds coffee spilled on the front copy; the check number no longer matches. He walks to the back door, reads the second copy, and redraws the front one from it. Then, one summer, the school gets an extension. Nobody moves the back-door copy: it now hangs in the middle of the new corridor, and the plan still says the building ends there.

A disk is the same kind of building. Before any file can be found, the firmware must know where the partitions are, and it reads that from a table at a fixed place. Old PCs used a 64-byte table inside the first sector (the MBR); UEFI uses the GUID Partition Table (GPT), which keeps two copies with CRC32 check values, one at each end of the disk. In this chapter you build a bootable GPT disk image with a script that needs no root rights, write a verifier in C++ that checks every field and both check values independently of the tools that made the image, damage one byte and watch OVMF repair it, and then meet the "extension" problem: an image copied to a larger disk.

What you will be able to do

  • Draw the layout of an MBR disk and of a GPT disk sector by sector, including the protective MBR and the backup structures.
  • Build a reproducible GPT image with an EFI System Partition (FAT32) and your loader at the removable-media default path, without root rights (milestone A2).
  • Verify a disk image with your own tool: protective MBR, both GPT headers, both CRC32 values, the partition GUIDs and the presence of the loader file in the FAT32 file system.
  • Observe how firmware treats a damaged primary header, and explain why the backup header exists.
  • Diagnose and repair a GPT image whose backup header is not at the end of the disk.
Jargon box
MBR partition table
Simple words: the old partition table: four entries inside the first 512-byte sector of a disk. Analogy: a room plan small enough to fit on the front door. Precise: four 16-byte entries at offset 446 of sector 0 (type byte, 32-bit starting LBA, 32-bit sector count and legacy CHS fields), followed by the 55h AAh signature; 32-bit LBAs limit it to 232 sectors. D1 D4
GPT (GUID Partition Table)
Simple words: the modern partition table, stored twice on the disk with check values. Analogy: the room plan kept at the front entrance and at the back door. Precise: the UEFI partitioning scheme: a header at LBA 1 (signature "EFI PART", CRC32 of itself and of the entry array, its own and the alternate header's LBA, usable range, disk GUID) and an array of partition entries (type GUID, unique GUID, first and last LBA, attributes, UTF-16 name), mirrored by a backup array and backup header at the end of the disk. D1
Protective MBR
Simple words: a fake MBR on a GPT disk that tells old tools "this disk is in use". Analogy: a sign on the front door: "plan inside, do not draw a new one". Precise: an MBR in sector 0 of a GPT disk whose single partition entry has type EEh, starts at LBA 1 and covers the disk (or as much as 32 bits allow). D1
EFI System Partition (ESP)
Simple words: the partition, formatted FAT, where UEFI firmware looks for boot loaders. Analogy: the key cabinet by the entrance where the person who unlocks the classroom keeps the keys. Precise: a partition with the type GUID C12A7328-F81F-11D2-BA4B-00A0C93EC93B and a FAT file system that UEFI firmware must be able to read; it holds boot loaders, including the removable-media default \EFI\BOOT\BOOTX64.EFI on x86-64. D1
CRC32
Simple words: a 32-bit check value computed from a block of bytes; a changed byte gives a different value. Analogy: the check number at the bottom of the room plan. Precise: a cyclic redundancy check; the variant used by GPT is the reflected CRC with polynomial EDB88320h, initial value FFFFFFFFh and final inversion; it detects all single-bit and single-byte errors but is not a cryptographic protection. D1 R2
LBA (logical block address)
Simple words: a sector's number on the disk, counting from 0. Analogy: the room number. Precise: the index of a logical block (here 512 bytes) in a linear numbering of the device; byte offset = LBA × block size. D1

Layer 1 — the kid explanation

A disk is a very long row of numbered boxes, each holding 512 bytes. To use it for several things, you write a plan at the start: "boxes 2048 to 133119 belong to the boot area, the rest to the system". Old computers wrote a tiny plan in the very first box. New computers write a bigger plan in box 1, with a check number, and a copy of the same plan in the very last box. If one copy is damaged, the computer reads the other. In the boot area there is a small file system, like a library with folders, and in one known folder the firmware finds the boot loader.

Layer 2 — the student explanation

MBR. The first sector holds boot code, then at offset 446 four partition entries of 16 bytes, then the signature 55h AAh at 510.D4 Each entry has a type byte and 32-bit fields for the first sector and the number of sectors. With 512-byte sectors, 32 bits address at most 232 × 512 bytes = 2 TiB, and four entries are all there is (extended partitions work around that with a chain of further tables).

GPT. UEFI defines a table without those limits. LBA 1 holds a header: the signature "EFI PART", a revision, the header size (92 bytes), a CRC32 of the header, the LBA of this header and of the other copy, the first and last LBA usable by partitions, a disk GUID, and where the entry array is, how many entries it has, how large each is, and the CRC32 of the array.D1 The array (here 128 entries of 128 bytes, LBAs 2–33) describes each partition by a type GUID, a unique GUID, 64-bit first and last LBAs, attribute bits and a UTF-16 name. The last LBA of the disk holds a backup header, and the 32 sectors before it a backup array. LBA 0 keeps a protective MBR with one entry of type EEh, so that MBR-only tools see the disk as occupied.D1 R2

ESP. One partition has the EFI System Partition type GUID and a FAT file system (FAT32 here). UEFI firmware includes a FAT driver (the Fat module of F3-11's list) and, when no boot option says otherwise, looks for a file at a default path that depends on the architecture: \EFI\BOOT\BOOTX64.EFI on x86-64.D1 Put your loader there and OVMF starts it with no boot-menu interaction, as this chapter's boot shows ("BdsDxe: starting Boot0001 "UEFI QEMU HARDDISK…"" followed by A1's greeting).R4

Layer 3 — the engineer's depth

Building without root

Formatting a partition usually means attaching a disk device, which needs administrator rights. Listing 1 avoids that: truncate creates a sparse 128 MiB file; sgdisk writes the protective MBR, both GPT headers and both entry arrays directly into the file; mkfs.fat formats a separate 64 MiB file as FAT32; mmd and mcopy (mtools) create directories and copy files into that FAT image without mounting it; and dd … seek=2048 conv=notrunc places the FAT image at partition 1's first sector.D5 Fixed GUIDs and a fixed FAT volume ID make two builds byte-identical, which matters when a CRC or a hash of the image appears in a test or a report (F3-16).

sgdisk's verification after the build reports "No problems found" and a free segment of 2,014 sectors: LBAs 34–2047, the alignment gap before partition 1 (2048 − 34 = 2,014). It also warns that partition 2 does not end on a 2048-sector boundary: partition 2 fills the disk to the last usable LBA, 262,110, which is not a multiple of 2048 minus one. Neither is an error for this purpose.R3

Not verified — check before relying on this

The sgdisk, mkfs.fat and mtools options in Listing 1 (--clear, --disk-guid, --new=1:2048:+64M, --typecode=1:EF00, --change-name, --partition-guid, -e, -v, -p; mkfs.fat -F 32 -n -i; mmd -i, mcopy -i) were written from memory. They ran without error with the versions in the run record (GPT fdisk 1.0.10, dosfstools 4.2-1.1build1, mtools 4.0.43-1build1) and produced the layout the verifier reads back (R1–R3), but their documented meaning was not checked in the manuals (D5), which are not installed in the build container. The type codes EF00 and 8300 are sgdisk's short names; the verifier shows the GUIDs they produced.

Verifying independently

The milestone asks for "a small host-side C++ tool that verifies the image independently".S1 Independence is the point: if the same library builds and checks an image, a misunderstanding in that library passes both. Listing 2 implements CRC32 itself, reads every field by offset, and checks five things: the protective MBR (signature, type EEh, start LBA 1); each header (signature, revision 1.0 and size 92, its CRC32 computed with the CRC field zeroed, its own and the alternate LBA, the entry-array CRC32); that both arrays have the same CRC; the partitions (an ESP exists); and, through the FAT32 structures, that \EFI\BOOT\BOOTX64.EFI exists. It found the file with 9,216 bytes at cluster 5, the size of A1's memmap.efi.R2

Not verified — check before relying on this

The field offsets in Listing 2 were written from memory of the UEFI Specification's GPT chapter and the Microsoft FAT32 specification (D1, D2), which could not be opened: the header fields at 8, 12, 16, 24, 32, 40, 48, 56, 72, 80, 84, 88; the entry fields at 0, 16, 32, 40, 56; the MBR entry at 446; the FAT32 boot-sector fields at 11, 13, 14, 16, 36, 44 and 82; the directory-entry fields at 11, 20, 26, 28 and the long-name attribute 0Fh. The evidence they are right: the computed CRC32 values equal the values sgdisk stored in both headers and both arrays, every LBA agrees with sgdisk's own listing, and the file lookup finds the file mtools wrote, with the right size (R2, R3). The CRC variant is the common reflected CRC-32; that GPT uses exactly this variant is confirmed only by the matching values.

What the firmware did with a damaged header

The run changed one byte of the primary header (offset 512 + 56, the first byte of the disk GUID) from AAh to 00h. The verifier fails exactly one check, the primary header's CRC32 (stored 0x767635b5, computed 0x897ae2ed), and lists the partitions from the backup header instead; the disk GUID it prints from the damaged primary begins 0a530100 instead of 0a5301aa.R4 OVMF then booted the damaged image normally, and afterwards the same verifier passed on the same file: the primary header's CRC and disk GUID were back to their original values. The firmware had not only fallen back to the backup header, it had rewritten the primary from it.R4 That is the milestone's "observe it", with evidence before and after.

Watch out

Firmware that writes to a disk during boot is useful here and surprising elsewhere: a forensic copy of a disk must be attached read-only, or the act of booting it changes the evidence. QEMU's -drive …,readonly=on or a copy is the minimum; a hardware write blocker is the standard for real disks.

How the hardware actually does it

A disk controller knows nothing about partitions: it reads and writes numbered blocks. In QEMU the image file is presented through an emulated SATA controller (the device path in the boot line: PciRoot(0x0)/Pci(0x1F,0x2)/Sata(0x0,0xFFFF,0x0)), and OVMF's drivers stack on top of it: the SATA controller driver, the ATA bus, a block-I/O protocol, then the partition driver (which parses the MBR or GPT and creates one block device per partition) and the FAT driver (a simple-file-system protocol on the ESP).R4 D3 F3-11's module list names those drivers: SataController, AtaAtapiPassThruDxe, AtaBusDxe, PartitionDxe, DiskIoDxe, Fat. On real disks two physical facts matter that a file does not show: many current drives use 4096-byte physical sectors (with 512-byte logical sectors or natively), which is one reason partitions start at multiples of 2048 sectors (1 MiB); and USB sticks and SSDs remap blocks internally, so "LBA 262143" is a logical address, not a place on the medium.D4

Not verified — check before relying on this

Untested on hardware: the milestone's optional item "The same image boots a spare PC from a USB stick" was not done (no hardware in this build). To do it: write the image with dd to a spare stick whose device name you have checked twice, then expect the same grown-disk situation as the forensic lab (the stick is larger than 128 MiB); run sgdisk -e on the stick or build the image at the stick's size. Some PCs show the stick only in a boot menu, and machines with Secure Boot enabled refuse an unsigned loader (F3-16). The statements about 4096-byte physical sectors and internal remapping are from memory of D4.

Safety

The lab writes only to files. Writing an image to a device overwrites that device's partition table and data: identify the device by size and model (lsblk) before every dd, never write to a disk of a machine you depend on, and keep a spare stick for this course.

Worked example

Problem. For a 128 MiB image with 512-byte sectors, 128 entries of 128 bytes, and the backup structures at the end: compute (a) the number of LBAs, (b) the LBAs of the entry arrays, (c) the first and last usable LBA. Then check against the verifier.

Solution. (a) 128 MiB / 512 B = 134,217,728 / 512 = 262,144 LBAs, numbered 0 to 262,143. (b) The array is 128 × 128 = 16,384 bytes = 32 sectors. Primary: LBAs 2–33 (after the protective MBR at 0 and the header at 1). Backup: the 32 sectors before the backup header at 262,143, so 262,111–262,142. (c) First usable: 34 (after the primary array). Last usable: 262,110 (before the backup array).

Check. The verifier printed "usable LBAs 34..262110" and "entries at LBA 262111" for the backup header, and sgdisk printed "First usable sector is 34, last usable sector is 262110".R2 R3 For the grown image (192 MiB = 393,216 LBAs), the same arithmetic gives a backup header at 393,215 and last usable LBA 393,182, exactly what the verifier reports after the repair with sgdisk -e.R5

Where the analogy breaks


    

  1. The copies are not identical. The two GPT headers differ on purpose (each records its own position and the other's), so their CRCs differ (0x767635b5 and 0xfbf3d7eb here); only the entry arrays are the same. Two paper copies of a plan would be identical.
    2. 

  2. Nobody "reads" the plan; programs parse it. A smudged paper plan can still be understood; a GPT with one wrong byte fails its CRC and is rejected entirely. Robustness comes from the second copy, not from tolerance.
    3. 

  3. The "building" can be copied onto a bigger plot. Disks are copied block by block onto other disks; school buildings are not. The extension problem of the forensic lab exists only because images move between devices of different sizes.
    4. 




Common mistakes and debugging


    

  • Computing the header CRC with the CRC field in place. Zero bytes 16–19 first, then compute over the header size (92), not the whole sector.
    • 

  • Computing the array CRC over only the used entries. It covers all entries (count × size), used or not.
    • 

  • Printing GUIDs byte by byte. The first three fields are little-endian; the type GUID of the ESP looks wrong if printed in byte order.
    • 

  • Writing the FAT image without conv=notrunc. dd truncates the disk file after the copy and the backup GPT disappears.
    • 

  • Assuming the ESP must be the first partition. It need not be; firmware finds it by type GUID.
    • 

  • Upper/lower case on FAT. 8.3 directory entries store names in upper case; BOOTX64 EFI with a space, not a dot.
    • 

  • Booting a forensic image read-write. The firmware may repair (change) it, as observed in this chapter.
    •

Mini-project


Turn gptcheck into gptfix: when the primary header is invalid and the backup is valid (or the reverse), rebuild the damaged copy from the good one (including the "my LBA" and "alternate LBA" swap, the entries LBA and both CRCs), and when the backup is not at the end, move it there. Summary


    

  • MBR: four 16-byte entries at offset 446 of sector 0, 32-bit LBAs (2 TiB with 512-byte sectors), signature 55 AA.
    • 

  • GPT: protective MBR at LBA 0, header at LBA 1, entry array after it, and a backup array and header at the end; CRC32 on headers and arrays; GUIDs for disk, partition types and partitions.
    • 

  • The ESP is a FAT partition with a known type GUID; on x86-64 the removable-media default loader is \EFI\BOOT\BOOTX64.EFI.
    • 

  • A reproducible image can be built without root: truncate, sgdisk, mkfs.fat on a separate file, mtools, dd with notrunc.
    • 

  • Verify with an independent tool; in this build OVMF fell back to the backup header and rewrote the damaged primary.
    • 

  • An image copied to a larger disk keeps its backup in the middle: it boots, but tools and resizing fail until the backup is moved to the end.
