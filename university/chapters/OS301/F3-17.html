Story hook

Analogy

Three schools hire caretakers from the same agency. All three wear the same uniform and open the building the same way. But one carries a key ring for a strong room and checks permission slips; another never opens the computer lab and has a sealed envelope for the head; the third carries a notebook and writes down every door he opens, all morning. The difference is not in the person: it is in the job description the agency wrote for each school.

Every UEFI firmware you have used in this course is an OVMF binary built by the distribution from the EDK II source tree, with a particular set of build options. Milestone A4 asks you to build OVMF and coreboot yourself and watch the PI phases happen in a debug log. This build container has neither source tree, nor internet access to fetch them, so this chapter does two things honestly. First, what can be done for real: compare three packaged OVMF builds module by module to see what build options change in a binary, and compare what the packaged SeaBIOS and OVMF write to the firmware's debug port. Second, what A4 involves, written as a plan and marked as untested. The forensic lab: Secure Boot "configured" on a firmware that cannot enforce it.

What you will be able to do

  • Explain how an EDK II platform build is described (platform description, flash description, module descriptions) and what a build option changes.
  • Compare two firmware binaries module by module and attribute the differences to features (Secure Boot, SMM, network boot, confidential computing).
  • Tell a release build from a debug build by its behaviour on the debug port.
  • Separate what a firmware's code can do from what its variable store configures.
  • Plan milestone A4: an OVMF debug build, a small DXE driver of your own, and a coreboot build with a payload, with the acceptance tests the curriculum sets.
Jargon box
EDK II
Simple words: the open-source code base from which most UEFI firmware, including OVMF, is built. Analogy: the agency's book of standard procedures from which each caretaker's job description is assembled. Precise: the reference implementation of the UEFI and PI specifications, organised in packages (MdePkg, MdeModulePkg, OvmfPkg and others) of modules, built by its BaseTools build command from a platform description. D1 S1
Platform and flash description (DSC, FDF)
Simple words: two text files that say which modules go into a firmware and where in the flash image they are placed. Analogy: the job description (what he does) and the floor plan of his key cabinet (where each key hangs). Precise: the DSC file lists the modules to build, the libraries they use and the build-time settings (PCDs); the FDF file lists the firmware volumes and which built modules go into each; each module has its own INF description. D1
Debug build and release build
Simple words: two versions of the same firmware: one talkative and larger, one quiet and smaller. Analogy: the caretaker with the notebook, and the one without. Precise: build targets of EDK II (-b DEBUG or -b RELEASE); in a debug build the DEBUG and ASSERT macros produce output and checks, on OVMF written to an I/O port that QEMU can capture; in a release build they compile to nothing. D1
System Management Mode (SMM)
Simple words: a hidden processor mode where firmware code runs out of sight of the operating system. Analogy: a locked office in the school that only the caretaker can enter, even after he has handed over the building. Precise: an x86 operating mode entered through a System Management Interrupt, running code from protected memory (SMRAM) that the operating system cannot read or write; PI calls the software model for it MM (Management Mode), and its modules have the file types MM and MM_CORE. D2 S1
Payload (coreboot)
Simple words: the program coreboot starts after it has set up the hardware: the part that actually finds and boots an operating system. Analogy: a caretaker who only unlocks the gates and switches on the heating, then hands over to a receptionist who takes visitors to their rooms. Precise: a program loaded by coreboot's last stage (ramstage), for example SeaBIOS, an EDK II payload (a UEFI implementation) or LinuxBoot; coreboot's stages are bootblock, romstage, postcar and ramstage. S1

Layer 1 — the kid explanation

Firmware is a program like any other: people write it, and a computer builds it from its source. When it is built, a list says which parts to put in: the part that checks signatures, the part that talks to the network, the part that writes a diary. Different lists give different firmware from the same source. We cannot build one here, but we can open three finished ones and compare their parts lists.

Layer 2 — the student explanation

An EDK II platform such as OVMF is described by text files. The platform description (.dsc) names every module and library to build and sets build-time options; the flash description (.fdf) says which firmware volumes the image contains and which modules go into each; each module has an .inf file naming its sources and dependencies. The build command of BaseTools reads them, compiles every module for its phase (SEC, PEI, DXE, MM), wraps each one in an FFS file with its sections (F3-11), and assembles the volumes into an image.D1 For OVMF, build options switch features on and off: Secure Boot, SMM, TPM support, network boot, the UEFI shell, debug output.

coreboot divides the work differently. Its own stages only initialise the hardware: the bootblock runs from the reset vector, romstage brings up memory, postcar tears down cache-as-RAM, ramstage enumerates devices and writes tables (ACPI, SMBIOS); then it loads a payload, which provides the interface an operating system boots from: SeaBIOS for a legacy BIOS interface, an EDK II payload for UEFI, or LinuxBoot.S1

Without the sources, two experiments remain. fvscan from F3-11 lists every module in a firmware image with its type and name; fvdiff.py (Listing 1) compares two such lists. Applied to the three OVMF builds the distribution ships, it shows what the build options did. And QEMU's isa-debugcon device captures what a firmware writes to I/O port 0x402, the port OVMF's debug builds and SeaBIOS use for their logs.

Layer 3 — the engineer's depth

What the Secure Boot build adds

The Secure Boot build has 137 named modules against the plain build's 127: 18 only in the Secure Boot build, 8 only in the plain one (R2).R2 The 18 fall into three groups. SMM infrastructure: PiSmmIpl (loads the SMM core), PiSmmCore (type MM_CORE), PiSmmCpuDxeSmm, SmmAccess2Dxe, SmmControl2Dxe, SmmAccessPei, CpuIo2Smm, CpuHotplugSmm, SmmLockBox, CpuS3DataDxe. Variables served from SMM: VariableSmm, FvbServicesSmm and SmmFaultTolerantWriteDxe (all type MM), with VariableSmmRuntimeDxe as the non-SMM front end and PeiVariable, FaultTolerantWritePei for reading variables before DXE. Secure Boot policy: SecureBootConfigDxe and FirmwareSecvarUpdater. The 8 modules only in the plain build are their non-SMM counterparts (VariableRuntimeDxe, FvbServicesRuntimeDxe, FaultTolerantWriteDxe, EmuVariableFvbRuntimeDxe) plus the UEFI Shell and three of its dynamic commands.

This is F3-16's requirement made visible: Secure Boot's keys are only worth something if nothing but authenticated code can write the variable store, so the Secure Boot build moves the variable driver and the flash driver into SMM, where the operating system cannot reach them, and needs QEMU's smm=on and secure flash. The shell is removed because a shell built into the firmware would be a signed-by-definition program that can start anything.

Not verified — check before relying on this

The roles given to each module are inferred from their names and from memory of the PI Specification (D2) and the EDK II tree (D1); none of their sources was available. "The shell is removed because …" is our explanation of an observed difference, not a documented reason; the build files would show whether it is a policy or a side effect of a build option. Which build options produced these binaries (for example SECURE_BOOT_ENABLE, SMM_REQUIRE) is also from memory: the distribution's build recipe was not available.

What the AMD SEV build removes

OVMF.amdsev.fd, a build for AMD's memory-encrypted virtual machines, has 97 named modules: 31 of the plain build's are missing and 3 are new (R3).R3 Missing: the entire network stack (SnpDxe, MnpDxe, Ip4Dxe/Ip6Dxe, Udp, Tcp, Dhcp, Dns, the web-protocol and TLS drivers, IScsiDxe, UefiPxeBcDxe, VirtioNetDxe), the shell, VirtioFsDxe and VirtioSerialDxe, and the Intel TDX modules (TdxDxe, TdTcg2Dxe). New: Grub (an application: a boot loader built into the firmware), SecretPei and SecretDxe. The pattern fits a build whose purpose is a small, measurable firmware for a confidential virtual machine: fewer modules means less code to trust, and the boot loader is part of the measured image instead of being read from a disk the host controls.

Not verified — check before relying on this

The purpose of the AMD SEV build, and the roles of SecretPei, SecretDxe and the built-in Grub, are our interpretation of the module names (memory of OvmfPkg's AmdSev platform, D1), not read from any document in this build. AMD SEV itself is not explained in this course.

Release and debug builds on the debug port

With QEMU's debug console attached to port 0x402, the packaged SeaBIOS wrote 110 lines in 6 s, starting with its version and the compiler it was built with: "SeaBIOS (version 1.16.3-debian-1.16.3-2)", "BUILD: gcc: (Ubuntu 13.2.0-7ubuntu1) 13.2.0 binutils: (GNU Binutils for Ubuntu) 2.41", then the hardware it found, including QEMU's E820 map (R6). The packaged OVMF wrote 0 bytes in 8 s (R6).R6 The version text does not appear as one string in the SeaBIOS binary, only as the format strings "SeaBIOS (version %s)" and "BUILD: %s" (R4): the values are filled in at run time, which is why the run, not strings, is the evidence.

Milestone A4's acceptance starts with "The OVMF debug log shows the transitions from SEC to PEI to DXE to BDS".S1 The empty debug port is the reason A4 requires your own build: the distribution's OVMF is a release build (or one with debug output switched off), and no option at run time turns the log on. F3-11 had to infer the phases by sampling the instruction pointer for the same reason.

How the hardware actually does it

On real hardware a firmware build ends in a flash chip on the main board. The differences this chapter found in software, such as SMM-protected variables, have hardware counterparts: SMRAM is memory the chipset hides from everything but SMM, and the flash chip can be configured so that only SMM code may write it. On most retail PCs a further root of trust verifies the firmware itself before running it, which is one reason, as the curriculum notes, you cannot flash your own firmware on most retail PCs; coreboot supports a list of boards where this is possible.S1 Port 0x402 is a QEMU convention for debug output; real boards use a serial port, a POST-code display at port 0x80, or a debug probe.

Not verified — check before relying on this

Untested on hardware. The SMRAM and flash-protection mechanisms are from memory of D2 and the Intel SDM, the port-0x80 POST code convention from general knowledge; none was observed in this build. Never write firmware to a real board's flash as part of this course without a hardware programmer and a backup of the original image: a failed flash can leave a board that does not start at all.

Worked example

Problem. From R2's per-type table, check that the "only in" lists account for every change in the counts, type by type.

Solution. For each type, B − A must equal (only in B) − (only in A).

  • APPLICATION: 1 − 2 = −1; only in B: none; only in A: Shell. 0 − 1 = −1. ✓
  • DRIVER: 109 − 109 = 0; only in B: 7 (CpuS3DataDxe, FirmwareSecvarUpdater, PiSmmIpl, SecureBootConfigDxe, SmmAccess2Dxe, SmmControl2Dxe, VariableSmmRuntimeDxe); only in A: 7 (the eight A-only modules minus Shell). 7 − 7 = 0. ✓
  • MM: 7 − 0 = 7; only in B: 7 MM modules. ✓ MM_CORE: 1 − 0 = 1; PiSmmCore. ✓
  • PEIM: 16 − 13 = 3; only in B: FaultTolerantWritePei, PeiVariable, SmmAccessPei. ✓
  • Totals: 137 − 127 = 10 = 18 − 8. ✓

The same check for R3: DRIVER 79 − 109 = −30, and the A-only list has 31 entries of which one is the application Shell, so 30 drivers; B-only drivers: SecretDxe; 1 − 30 = −29, not −30. The difference is a module that appears in both builds but with a different count: fvdiff.py compares names, not counts. In this case one driver name appears once more in the plain build than in the AMD SEV build. Finding which is the extension in the lab; it shows why a comparison tool must state what it compares.R2 R3

Check APPLICATION for R3: 2 − 2 = 0; A-only Shell, B-only Grub: 1 − 1 = 0. ✓ PEIM: 13 − 13 = 0; B-only SecretPei, A-only none: 1 − 0 = 1, not 0. Again one PEIM name appears with different counts; the same extension finds it.

Where the analogy breaks


    

  1. A job description can be read. A firmware binary's "job description" (the DSC and FDF) is not in the binary; we reconstructed it from the modules present, which is inference.
    2. 

  2. The agency's caretakers are separate people. The three OVMF builds share most of their code byte for byte; a bug in a shared module is in all three.
    3. 

  3. A notebook does not change the work. A debug build is larger and slower, and its ASSERT checks can stop a boot that a release build would continue; it is not the same firmware with a diary added.
    4. 




Common mistakes and debugging


    

  • Expecting a debug log from a packaged OVMF. It writes nothing to port 0x402 (R6); build your own debug build.
    • 

  • Choosing Secure Boot by the variable store alone. The code image decides whether Secure Boot can be enforced (see the forensic lab).
    • 

  • Mixing a code image and a variable store from different builds or versions. The variable store's format and layout are part of the build; pair them as shipped.
    • 

  • Forgetting smm=on for an SMM build. The Secure Boot build needs it, and secure flash, as F3-16 showed.
    • 

  • Comparing names only. Two modules with the same name can differ; and one name can appear more than once (worked example).
    • 

  • Building coreboot with the host compiler. coreboot builds its own cross tool chain for reproducible results; use it.

Summary


    

  • EDK II builds a platform from a DSC (modules, options), an FDF (volumes, placement) and INF files (modules); build options switch features in and out of the binary.
    • 

  • Comparing packaged OVMF builds: the Secure Boot build adds SMM and SMM-based variable services (+18, −8 modules); the AMD SEV build drops the network stack and the shell and adds a built-in GRUB (−31, +3).
    • 

  • The packaged OVMF writes nothing to the debug port; SeaBIOS writes its version, compiler and hardware findings. A4's debug log needs your own build.
    • 

  • The code image decides whether Secure Boot can be enforced; the variable store decides which keys are trusted.
    • 

  • coreboot separates hardware initialisation (bootblock, romstage, postcar, ramstage) from the payload that boots the operating system.
    • 

  • Building OVMF and coreboot from source was not possible in this build; the A4 plan is untested.
