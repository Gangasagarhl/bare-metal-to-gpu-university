Story hook

Analogy

A new principal arrives on the first day of term. The person who unlocks the classroom for her does not only open the door: he hands over a folder. On the first page, a printed checklist that both of them signed weeks ago: "keys to rooms 1 to 30; the room plan; the fire-drill schedule; the timetable; the list of rooms that are closed for repair". If he hands over a folder in last year's format, or with pages missing, she must notice at once, before she sends anyone anywhere.

A boot loader and a kernel have the same problem. The loader puts the kernel in memory, sets the processor up in an agreed state, and jumps; the kernel's first instruction can only rely on what was agreed. That agreement is a boot protocol. This chapter takes two halves of the problem. First, the kernel file: the ELF format, which segments must be loaded where with which permissions, and how a loader must check a file before it trusts any of its numbers. Second, the hand-over: you design the OS301 boot protocol, a versioned boot-information structure, and compare it with a protocol that QEMU itself speaks, Multiboot, by booting a small Multiboot kernel. The forensic lab shows what happens when a kernel and a loader do not speak the same protocol.

What you will be able to do

  • Explain the jobs of a boot loader: find and load the kernel, gather boot information, set up the processor state, hand over.
  • Read an ELF64 executable's header and program headers, and say what a loader does with each PT_LOAD segment (copy, zero-fill, map with its flags).
  • Link a freestanding C++ kernel in the higher half with one segment per permission set.
  • Design a versioned boot-information structure and the rules that let loader and kernel evolve separately.
  • Write and test an ELF checker that never reads outside the file, whatever the file contains.
  • Compare boot protocols (Multiboot, Limine, the Linux x86 boot protocol, your own) by entry state and what they hand over.
Jargon box
Boot loader
Simple words: the program that loads the operating system's kernel into memory and starts it. Analogy: the person who unlocks the classroom and lets the principal in. Precise: software started by the firmware (here a UEFI application) that locates the kernel image and its inputs, loads them, collects platform information, puts the processor in the state the kernel's boot protocol requires and transfers control to the kernel's entry point. D1 S1
Boot protocol
Simple words: the written agreement between a loader and a kernel about how the kernel is started and what it receives. Analogy: the handover checklist both have signed. Precise: a specification of the kernel image format the loader accepts, the processor state at entry (mode, paging, registers, stack, interrupts) and the format and location of the information passed (memory map, framebuffer, firmware tables, command line, modules). D3 S1
ELF
Simple words: the standard file format for programs and kernels on Linux and many other systems. Analogy: a packing list on the box that says which item goes on which shelf. Precise: the Executable and Linkable Format: an ELF header (magic, class, data encoding, type, machine, entry point, table offsets) followed by a program-header table for loading and a section-header table for linking and debugging. D2
PT_LOAD segment
Simple words: one piece of the file that the loader must put in memory. Analogy: one line of the packing list: "these items, to that shelf, in a locked or open cupboard". Precise: a program-header entry of type PT_LOAD giving the file offset and size (p_offset, p_filesz), the virtual address and memory size (p_vaddr, p_memsz; the bytes beyond p_filesz are zero, which is how .bss is stored) and the permission flags R, W, X. D2
Higher-half kernel
Simple words: a kernel linked to run at very large virtual addresses, leaving the low addresses for programs. Analogy: the staff offices on the top floor, the classrooms below. Precise: a kernel whose virtual addresses lie in the upper part of the canonical address space (here from 0xffffffff80000000, the range the x86-64 "kernel" code model assumes), mapped there by page tables regardless of where it sits in physical memory. D4
Boot information structure
Simple words: the record the loader fills in and passes to the kernel. Analogy: the folder handed over with the keys. Precise: a data structure in memory, whose address is passed to the kernel at entry, holding the hand-over data of a boot protocol; in OS301 it is os301::BootInfo, which starts with a magic number, a version and its own size. S1

Layer 1 — the kid explanation

The kernel is stored on the disk as a file with a packing list at the front: "these bytes are code and go here; these are words and go there; this space must be empty". The boot loader reads the list, puts every piece in its place, and writes a note for the kernel: how much memory there is, where the screen is, what the user typed. Then it jumps into the kernel and hands it the note. The kernel and the loader agreed in advance what the note looks like, so the kernel can read it.

Layer 2 — the student explanation

A loader has four jobs.S1 Find and load: read the kernel file (and a command line and an initial RAM disk if the protocol has them) from a file system the firmware can read, here the ESP. Gather: collect what the kernel cannot easily find after the firmware's services are gone: the final memory map, the framebuffer set up by the firmware, the addresses of the ACPI and SMBIOS tables (F3-12). Prepare: build the page tables the kernel expects, a stack, and put the processor in the agreed mode. Hand over: exit the firmware's boot services (F3-15) and jump to the entry point with the agreed registers.

The kernel file is an ELF executable. Its header says it is 64-bit, little-endian, for x86-64, and where the entry point is. Its program headers list the PT_LOAD segments: for each, where the bytes are in the file, how many to copy, where they go in virtual memory, how much memory to reserve (the extra is zero, which is how uninitialised globals in .bss cost no file space), and the permissions.D2 A loader never needs the section headers; they are for linkers and debuggers.

The boot protocol fixes the rest. Different loaders and kernels speak different protocols. Multiboot (GNU) puts a magic header in the kernel and enters it in 32-bit protected mode without paging, with a magic value in EAX and a pointer to an information structure in EBX. The Limine protocol hands over a higher-half kernel in long mode, with a memory map, framebuffer, RSDP, SMP information and a direct map of physical memory. The Linux x86 boot protocol has its own header and, on UEFI machines, an EFI stub that makes the kernel itself a UEFI application.D3 S1 Milestone A3 asks you to design your own; this chapter does it, and F3-15 implements the loader side.

Layer 3 — the engineer's depth

Building a kernel the loader can map

The kernel stub (Listing 1) is freestanding C++ compiled with flags that each answer a question about the environment: -ffreestanding -nostdlib (no C library), -fno-exceptions -fno-rtti (no runtime support), -fno-pic -fno-pie (absolute addresses: the kernel runs where it was linked), -mcmodel=kernel (code and data live in the top 2 GiB of the address space, so 32-bit sign-extended addresses reach them), -mno-red-zone (interrupt handlers will later run on the same stack and would overwrite the 128-byte red zone below RSP), -mgeneral-regs-only (no SSE: the kernel has not enabled the floating-point state yet).D4 The linker script (Listing 2) places .text, .rodata and .data+.bss in three PT_LOAD segments with flags 5 (R+X), 4 (R) and 6 (R+W), each starting on a new 4 KiB page, and discards notes and unwind tables. readelf confirms the result: three LOAD headers at 0xffffffff80000000, ...1000 and ...2000, file offsets 0x1000, 0x2000, 0x3000, and the third with file size 4 and memory size 0x10 (R1).R1

Why one segment per permission set and one page each? Page tables assign permissions per page. If code and writable data shared a page, that page would have to be both writable and executable, and F3-15's acceptance test ("writable and executable permissions match the ELF segment flags") could not pass.S1 The two volatile globals in Listing 1 exist only to give the stub a real .data and .bss: without volatile, the compiler folded them into constants in this build and the data segment disappeared.

Checking before trusting

Every number in an ELF header is an instruction to the loader: "read here", "copy this many", "jump there". A loader that obeys them blindly can be made to read outside the file, write over itself or the firmware, or jump into data. elf::check (Listing 3) is written so that it never reads outside [data, data + size), whatever the bytes say, and refuses anything outside the protocol: wrong magic, class, data encoding, type or machine; a program-header table outside the file; a segment whose file bytes are outside the file; a segment below the higher half, larger in file than in memory, or wrapping around the address space; a segment not page-aligned; overlapping segments (compared on page-rounded ranges, because they will be mapped by page); no PT_LOAD; or an entry point outside every executable segment.D2 The same header file is compiled into the host test bench (Listing 4, with AddressSanitizer and UBSan) and into F3-15's UEFI loader: the code that is tested is the code that runs.

The test bench runs nine named damage cases and 200,000 random ones (one to eight random bytes changed in the first 512 bytes). Each named case gives the expected reason; in the random run, 123,791 copies were rejected and 76,209 accepted, with no sanitizer report.R3 "Accepted" does not mean "correct": the first 512 bytes include the padding between the program headers (which end at byte 232) and the code at 0x1000, and fields the check does not use (for example the section-header offset). The check guarantees that loading is memory-safe and stays within the protocol; it cannot guarantee that the kernel's bytes are the right ones. That is the job of a signature (F3-16).

Designing a versioned boot-information structure

Milestone A3 lists what the structure must contain: the final memory map, the framebuffer (base, size, width, height, pitch, pixel format), the RSDP physical address, the SMBIOS entry point, the kernel's physical and virtual load addresses, a command line and an optional initial RAM disk.S1 os301::BootInfo (Listing 5) has all of them plus a boot timeline of four TSC readings (the FPDT-like record F3-12 asked for) and the number of ExitBootServices attempts. The design decisions are the part worth copying:

  • Magic, version, size first. A kernel can recognise a structure that is not a BootInfo at all (magic), refuse a loader that is older than it needs (version), and know how many bytes the loader actually wrote (size), so a newer kernel can run on an older loader if it checks size before reading newer fields.
  • Append-only. Fields are only ever added at the end. A field is never reused for a new meaning; a version number goes up when a field is added.
  • Fixed-width types and explicit padding. uint32_t and uint64_t only, and a pad field, so the layout is the same for every compiler that follows the x86-64 ABI, and the loader (compiled for the Windows target by clang) and the kernel (compiled for the kernel model by g++) agree.
  • Physical addresses for firmware objects, virtual for things the kernel walks. The RSDP and SMBIOS addresses are physical (the kernel reaches them through the direct map, direct_map_base + physical); the memory-map pointer is already a direct-map virtual address, ready to use.
  • A copied memory map. The UEFI descriptors are copied into a fixed MemoryRange format, so the kernel does not depend on the firmware's descriptor size (F3-10's rule 3).

Compare Multiboot's information structure in the lab's run: a flags word says which fields are valid (0x24f here: memory sizes, boot device, command line, memory map, boot-loader name, and others), and a pointer in EBX locates it.R4 That is a different answer to the same question: flags per field instead of version plus size.

How the hardware actually does it

The processor knows nothing about ELF, protocols or loaders. It sees a jump to an address, and a page-table walk for every instruction fetch and data access after it. What the hardware enforces is the permissions the loader writes into the page-table entries: a write to a page without the W bit faults; an instruction fetch from a page with NX set faults (if EFER.NXE is on).D5 That is why the protocol's "map each segment with its flags" is a real protection and not a convention: a kernel bug that writes into its own code faults immediately instead of corrupting it silently. The calling convention that puts the BootInfo pointer in RDI is also only a convention between two pieces of software; the processor does not check it. A loader that puts the pointer in RCX (the Microsoft x64 convention the loader itself is compiled with) hands the kernel garbage.D4

Not verified — check before relying on this

Untested on hardware: the kernel stub and the Multiboot comparison kernel ran only in QEMU 8.2.2. The page-permission semantics stated here (W, NX, EFER.NXE) are from memory of D5 and are tested in F3-15 only as page-table contents read through QEMU's monitor, not as faults. The descriptions of the Limine protocol and the Linux x86 boot protocol in Layer 2 are taken from the curriculum's summary table (S1), not from the protocols' own documents (D3), which were not opened; check them there before designing against them.

Worked example

Problem. From the program headers of kernel.elf (R1), compute: (a) how many 4 KiB pages the loader must allocate for the whole kernel; (b) for each page, the W and NX bits it must have; (c) how many bytes the loader copies and how many it zero-fills.

Solution. (a) Segments start at ...0000, ...1000, ...2000 and are 0x53c, 0x2ec and 0x10 bytes in memory: each fits in one page, and they are consecutive, so the span is 0x3000 bytes = 3 pages (elfinfo: "span 0x3000 bytes"). (b) Page 0 (R-X): W = 0, NX = 0. Page 1 (R--): W = 0, NX = 1. Page 2 (RW-): W = 1, NX = 1. (c) Copied: 0x53c + 0x2ec + 0x4 = 1,340 + 748 + 4 = 2,092 bytes. Zero-filled within segments: 0x10 − 0x4 = 12 bytes. The rest of each page is unused; a careful loader zeroes whole pages anyway, so that no old memory contents leak into the kernel.R1 R2

Check. F3-15's acceptance test reads these exact bits from the running machine's page tables: "segment at 0xffffffff80000000 (R-X): every page has W=0, NX=0", and the same for the two others.R6

Where the analogy breaks


    

  1. The principal cannot ask questions. At entry the kernel has no channel back to the loader; anything missing from the folder is missing for good once boot services are gone. A human handover allows "where is the key to room 12?".
    2. 

  2. The checklist is enforced by nobody. Two people who signed a checklist can point at it; a loader and a kernel that disagree about one field offset do not notice, they misbehave. That is why the structure carries magic, version and size.
    3. 

  3. The person who unlocks the classroom may be the principal. Linux's EFI stub makes the kernel its own loader; there is no second person.
    4. 




Common mistakes and debugging


    

  • Loading by sections instead of segments. Section headers can be stripped; segments are what the loader must honour.
    • 

  • Forgetting to zero-fill p_memsz − p_filesz. Globals in .bss start with whatever was in memory. The kernel stub prints its .bss word to catch this.
    • 

  • Overflowing checks. offset + size > file_size wraps for huge values; write size > file_size - offset after checking offset ≤ file_size.
    • 

  • Code and data in one page. The permissions cannot be right; give each permission set its own page in the linker script.
    • 

  • Building the kernel with the red zone or SSE. Fine until the first interrupt or the first floating-point instruction; then random corruption or a fault.
    • 

  • Changing a field's meaning without a version change. An old kernel reads the new meaning and nobody notices.
    • 

  • Different struct layouts in loader and kernel. Two compilers, two targets: use fixed-width types, explicit padding, and print sizeof on both sides once (the kernel prints the size it received).
    • 




Transition box

Where you came from: F3-13 put a loader on a bootable disk; F3-12 found the firmware tables; F3-10 printed the memory map; SP301 covered object files and linking. What carries over: the memory map, RSDP and SMBIOS addresses are exactly the fields of the boot information; the ELF linking of SP301 now decides page permissions; the habit of checking every number before trusting it (checksums, CRCs) becomes "check every ELF field before obeying it". What changes: you now design an interface between two programs that never run at the same time, and must make it evolve safely. What comes next: F3-15 writes the loader that implements the protocol: it reads the kernel from the ESP, builds the page tables, exits boot services with the map key, and jumps.

Summary


    

  • A loader finds and loads the kernel, gathers what the kernel will need, prepares page tables and processor state, and hands over; the boot protocol says how.
    • 

  • ELF: header plus program headers; each PT_LOAD is copied (p_filesz), zero-filled (to p_memsz) and mapped at p_vaddr with its R/W/X flags.
    • 

  • Link the kernel in the higher half with one segment per permission set on its own page, using the kernel code model, no red zone and no SSE.
    • 

  • Check every ELF number before obeying it, with checks that cannot overflow; test the check with named and random damage under the sanitizers; "accepted" means memory-safe, not correct.
    • 

  • OS301 protocol v1: long mode, loader page tables (kernel, direct map, identity), interrupts off, boot services exited, RDI = BootInfo (296 bytes: magic, version, size first; fields only appended).
    • 

  • Different loaders speak different protocols: QEMU's -kernel boots a Multiboot kernel and refuses the OS301 kernel.
    •
