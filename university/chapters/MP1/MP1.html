Story hook

For three years Mei-Ling has been principal of a practice school: two training buildings where every door, bell and timetable behaves exactly as the handbook says. She wrote her own rule book there, page by page, and ran a drill for every page.

Now the district gives her two real schools. The first is a small village school with a caretaker she has never met: he opens the doors his own way and hands her a building plan at the gate. The second is a large city school with many classrooms, where nobody hands her the rule book at the door: it arrives by courier on the first morning, and the courier only comes if she has arranged the delivery in advance.

She makes three promises before she leaves. The same rule book will work in both schools, and where it cannot, she will write the difference down on one page. Every drill she ever ran will be run again, in both practice buildings, before any change goes into the book. And she will time the morning opening in each school with the same stopwatch, so that she can compare her mornings with those of the principal who ran the school before her.

This handbook is those three promises, turned into a project.

What you will be able to do

  • Run the kernel you wrote in OS302–OS304 and DR402 as one regression matrix on x86-64 and AArch64 in QEMU, with host-stamped serial logs, a baseline and a written quarantine rule (milestone 1, R1).
  • Bring up the same AArch64 image on a real SoC board through the standard boot chain, and the same x86-64 image on a server through UEFI network boot, with every difference between platforms kept in one platform difference record (milestones 2 and 3).
  • Deliver a shell and user programs over the network, from your own TCP/IP stack to a client on another machine (milestone 4).
  • Measure a boot timeline of your kernel and of Linux on the same hardware with one method, and explain the differences from evidence (milestone 5).
  • Diagnose a regression or a slow boot from stamped logs and run records, and write it up as a blameless incident report.
  • Lead the project through gates R0–R4: prepare the evidence each gate asks for, collect written approval, and defend the result.
Jargon box
Regression matrix
Simple words: the full list of "this kernel, on this machine, with this many CPUs, running this test" combinations that must pass before a change is accepted. Analogy: the drill timetable: every drill, in every building, with every class size. Precise: a versioned file of rows, each naming an architecture, an emulator or machine configuration, a time limit and a pass rule (exit status and a required serial line); the harness runs every row from a clean build and the verdict is the conjunction of the counted rows. This project's own definition, built on the curriculum's acceptance-test rules. D2 R3
Regression baseline
Simple words: the saved results of the last run everyone agreed was good, so a new run can be compared with it row by row. Analogy: last term's drill record, kept on file. Precise: the results file of an accepted matrix run; a row that passed in the baseline and does not pass now (or is missing) is a regression, whatever the overall count says. This project's own definition. R8
Host-side timestamping
Simple words: writing down the time on the computer that runs the test whenever a line of boot output arrives. Analogy: one stopwatch held by the inspector, not by each school. Precise: the harness reads the guest's serial output line by line and records, for each line, the host's monotonic clock relative to the start of the run; stage durations are differences between these stamps. It measures arrival at the host, so it includes the serial path; it does not need the guest's clocks to be calibrated or comparable between operating systems. R4
Platform difference record
Simple words: one page listing every way your kernel is built or started differently on each machine, and why. Analogy: the one page Mei-Ling adds to the rule book: "in the village school, the bell is a hand bell". Precise: a design note, kept under version control with the matrix, with one row per difference (image, build option, boot path, command line, devicetree or ACPI source, driver set) and its reason; the MP1 rubric's first criterion is graded against it ("one kernel image or a documented minimal difference"). D1
Remote shell
Simple words: typing commands on one computer and having them run on another, over the network. Analogy: the office window, but reached by telephone from another building. Precise: a user-space server on your OS that accepts a TCP connection, runs the shell of B18 with its standard input and output connected to the connection, and returns the output; the MP1 card accepts it, or a file service, as milestone 4. D1 D2

Terms from earlier chapters, used without redefinition: boot timeline and device record (F4-14, F4-20), generic kernel image (F4-37), network boot and PXE (F5-31), PSCI, isa-debug-exit, flaky test, quarantine, design-review gate, entry criteria and final defence (F12-29, F12-30). Layer 1 — the kid explanation

A computer does not care that your kernel worked yesterday on a pretend computer. On a real board, the caretaker (firmware) opens different doors, hands you a different building plan, and the clock ticks at its own speed. On a real server, many teachers (CPUs) start at once, the rule book comes over the network, and the storeroom (the disk) is a fast machine with its own rules. MP1 is the year in which your kernel leaves the practice school. You keep it honest with three habits: run every old drill again in both practice buildings before every change; write every difference between schools on one page; and time every morning with the same stopwatch. That is all the analogy you need; the rest of this handbook is engineering.

Regression discipline: what the 20 % criterion actually rewards

The curriculum's rules for kernel tests are short, and the harness implements each of them: serial output is the oracle; the run ends with a pass or fail exit; every test has a wall-clock limit and "a hang is a failure, not 'probably fine'"; the configuration is fixed and recorded per test; a failing test can be re-run with the debugger stub; real-hardware runs are extra evidence, "never as a replacement for the QEMU test". D2 On top of them, a mega project needs four disciplines that a single chapter lab does not:

  1. Two-part pass rules. An exit status alone is not a verdict on AArch64, where the kernel ends every run with PSCI SYSTEM_OFF and QEMU exits 0 either way; the required line is what fails the run. The regression run R7 shows this case: row mp1-a64-smp4 failed with exit status 0. R7
  2. A baseline, compared row by row. "9 of 11 passed" hides which two failed. The compare step names regressions by row and treats a missing row as a regression, because a matrix that silently loses rows is the failure the forensic lab is about. R8
  3. Quarantine with a rule. A row whose result changes without a code change is a flaky test (F12-10). The starter matrix runs the OS303 B9 test (~os303-threads) in quarantine: it checks that 100 threads' counters stay within a max/min ratio of 2.00 after a fixed time, a timing property that depends on how the host schedules QEMU's TCG thread. The recorded attempts below ran the unchanged kernel eight times: five on an otherwise idle host, then three while three other QEMU runs loaded the host, as parallel CI jobs do. Compare the ratios of the two groups: the verdict of this row depends on the host, not only on the code. R6 Quarantine is not deletion: the row still runs, it still reports, and it has an owner, a reason and a review date; the fix (a bound derived from a model of TCG scheduling, or a run under KVM) is a milestone-1 task.
  4. Cost per commit. The matrix must be fast enough to run on every commit. In the recorded run, the four MP1 rows and the two DR402 rows each took well under a second, and three OS303 rows took tens of seconds (the seconds column of R3). Long stress sizes (B11's full counts, B13's hour of fuzzing) belong in a nightly matrix with the same harness. R3



Measuring a boot with one stopwatch


Your kernel and Linux keep time differently, and on x86-64 your starter kernel has no calibrated clock at all: it prints raw time-stamp-counter ticks, because calibration is B8's job (F3-25). The AArch64 port can convert, because the generic timer's frequency register gives the counter's rate. D5 R5 Comparing two operating systems through their own clocks would compare their clock code as well. Host-side timestamping avoids that: the harness stamps each line when it reaches the host. Its limits must be stated with every result: the stamp includes the serial path (a slow UART or a buffered console delays it), it starts when the host starts QEMU or powers the machine, not at the reset vector, and on real hardware the host must read the serial line directly, not through a buffering tool. The design rule for milestone 5 is "same machine, same power state, same stamping path, several runs, median and spread", the protocol of F12-13.

UEFI network boot of your own loader


F5-31 booted a UEFI program over the network in QEMU: OVMF's boot manager chose its network boot option, obtained an address and a boot file name by DHCP, fetched the file by TFTP and started it; the chapter also observed that OVMF offers HTTP boot as another option. D8 For MP1, your A3 loader is that network boot program. Two design points follow. Second, the boot server is part of the system under test: its configuration files go into the repository next to the matrix, and its version is recorded in the log.

A remote shell is a security decision


A remote shell runs commands for whoever connects. On a lab network that only your machines reach, an unauthenticated shell is an acceptable first step; anywhere else it is an open door. Write the threat note at R2: which network the server listens on, who can reach it, what a connected client can do (your kernel probably has no users or permissions yet), and what you will not do (connect it to a shared or public network). A file service raises the same questions for reads and writes. The F11 courses (SS301, SS401) cover threat models; MP1 needs only the honest note and the isolation.

Worked example


A worked example of the whole regression loop, from the starter lab's recorded runs. Suppose a teammate wants to save memory and changes the number of CPUs the kernel can track from 16 to 2. On their laptop they run the kernel once, with one CPU, and it passes.


Step 1: the baseline. The full matrix before the change, eleven rows, ten counted and one quarantined. R3




Step 2: the change, built and run on the MP1 rows. build_all.sh .build_bug -DMP1_MAX_CPUS=2, then the four MP1 rows. R7




Read the two failed rows carefully. The x86-64 row failed on its exit status: the kernel wrote the fail code to isa-debug-exit and QEMU exited 35 instead of 33. The AArch64 row exited 0, the same status as a pass, because the kernel always ends with PSCI SYSTEM_OFF; it failed only because the line MP1 END pass=… fail=0 was not printed. With an exit-status-only rule, this regression would have reached the baseline on AArch64.


Step 3: the comparison. R8




Step 4: the arithmetic of the matrix. The change fails exactly the rows where the firmware lists more CPUs than the kernel tracks. The test is listed == want && listed <= kMaxCpus (Listing 2, line 69): with kMaxCpus = 2, a row with -smp 1 gives 1 == 1 and 1 ≤ 2, true; a row with -smp 4 gives 4 == 4 but 4 ≤ 2 is false. A matrix with only one CPU count per architecture could not have caught this change; that is why each architecture has rows at 1 and at 4 CPUs, and why milestone 3 adds a row at the server's real count.


Step 5: what goes into the log. The run ids, the two failing rows, the root cause in one sentence ("MP1_MAX_CPUS lowered below the CPU count of the 4-CPU rows"), the decision (revert), and the new baseline only after the revert's run is green. The baseline file never moves because a row failed; it moves when the owner accepts a run.

Where the analogy breaks


    

  • A rule book cannot run. Mei-Ling's rule book is read by people who understand intentions; your kernel is executed by a CPU that does exactly what the bytes say. "The same rule book in both schools" sounds easy because people adapt; one kernel image on two machines is hard because nothing adapts unless you wrote the code that adapts (devicetree and ACPI parsing, feature checks).
    • 

  • Drills do not interfere with each other; regression rows can. Two drills in two buildings are independent. Two QEMU rows on one CI host share CPU time, and the quarantined row of this lab changes its verdict with host load (R6). The analogy hides the fact that the test environment is part of the test.
    • 

  • One stopwatch is not neutral. The inspector's stopwatch suggests the measurement is free. Host-side stamps include the serial path, the emulator's buffering and the harness's own reading loop; on hardware, a slow UART at the start of boot adds its own delay to every line. The method note must say what the stamp includes.
    • 

  • The courier never brings the wrong book. A network boot can: DHCP answers from another server on a shared network, an old image in the boot server's folder, a cached file in the firmware. That is why the network boot runs only on an isolated lab network, and why the kernel prints its own build identity first.
    • 

  • A real school's principal is not a stranger. On the server the "previous principal" is Linux, and comparing your boot with Linux is not a contest about who is better: Linux brings up far more hardware and does far more work. The comparison is honest only when it says, stage by stage, what each system did.

Forensic lab


The incident. Three weeks into milestone 2, a teammate notices that the AArch64 rows of the CI dashboard now take about three seconds each instead of a fraction of a second. Every row is green. The commit history of the period has a "tidy-up" of the matrix file ("shorten QEMU options"), a change to the scheduler and a new driver for the board. Nobody connects the slow rows with any of them, and the board boots "a bit slower than before" too. You are asked to find out why, and to make sure it cannot go unnoticed again.

    3.

    4.

Summary


    

  • MP1 turns the earlier courses into one operating system on two real machines: a board through the standard boot chain and a server through network boot, with SMP, storage, networking and a service a client can use.
    • 

  • The regression matrix is the project's spine: every acceptance test is a row with an exit status and a required line, run from a clean build on every change and compared with a baseline by name.
    • 

  • "One kernel image" is graded against a platform difference record: every difference is written down with a reason.
    • 

  • Flaky rows are quarantined explicitly, with an owner and a date; host load can change a timing-dependent verdict.
    • 

  • Boot times are measured with one host-side stamp for every system, and compared stage by stage with Linux on the same hardware.
    • 

  • Gates R0–R4 decide when to move on; on real hardware the owner's supervision and sign-off come first.
