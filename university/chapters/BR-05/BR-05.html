Story hook

Three schools have the same small duty: every period, on the minute, someone must look at the thermometer in the science room and set the heater. Late is bad; very late is worse.

The first school is a one-room school. Ms Okafor teaches, marks, sweeps and also checks the heater, all from one list she repeats all day. When she starts marking a long essay right before the minute, the heater waits until she finishes. A kind parent installs a doorbell that rings on the minute; now, whatever she is doing, she stops, sets the heater, and goes back. Nobody else works in the building, so nobody else can delay her.

The second school has several groups and a timetable with a rule on the hall door: the more urgent group always goes first. The heater duty becomes the most urgent group. It is on time as long as everyone follows the rule; a group that locks the door from the inside while it works breaks the rule for everyone.

The third school is a large campus: a principal, an office with a window, classrooms with locks, buses, a library, visitors. It can do far more than the other two. But the principal sometimes holds a long assembly that nobody may interrupt, and the heater duty waits outside like everyone else, unless the school adopts a stricter rulebook.

This bridge is the walk from the first school to the third. The duty stays the same; who decides when it runs changes. You will run the same heater loop in all three, measure how late it is, and meet the four traps that catch people on the way.

What you will be able to do

  • Explain what carries over from bare metal to an RTOS to Linux (interrupts, timers, drivers, memory maps, the debugger, measuring timing) and what changes, most dangerous change first.
  • Run one sensor-to-actuator control step unchanged in three worlds (a superloop, a timer interrupt, an RTOS task, a Linux thread) and show with a checksum that only the timing differs.
  • Measure actuation lateness and jitter in each world and compare them fairly, each against its own period, with the limits of an emulator and of a shared virtual machine stated.
  • Demonstrate the four traps on running systems: a blocking wait in an interrupt handler, priority inversion, a Linux kernel that is not real-time, and allocation in the time-critical path; and fix each one.
  • Diagnose a jitter regression from a context-switch log and a lateness histogram.
  • Choose between the three worlds for a given job, and say what must be measured on real hardware before the choice is final.
Jargon box
Superloop
Simple words: firmware whose main is one endless loop that does every job in turn. Analogy: Ms Okafor's single list, repeated all day. Precise: a bare-metal program structure in which all application work runs in one loop in thread context (often woken by a timer tick or other interrupts that only set flags or count); a job's start time depends on how long every job before it in the loop takes. D3 R1
Actuation lateness
Simple words: how long after the planned moment the output was actually written. Analogy: how many seconds after the minute the heater was set. Precise: in this lab, for step k with release time k·T: (time stamp taken right after the actuator write) − k·T. It includes the wake-up delay and the time of the step itself; its spread (maximum minus minimum) is reported as the jitter of the loop. R1 R5 Jitter in general is defined in F9-45.
Interrupt context
Simple words: the state the processor is in while it runs an interrupt handler; there is no task to put to sleep. Analogy: answering the doorbell: you cannot go home and come back tomorrow while standing at the door. Precise: code running as an exception or interrupt handler (Handler mode on Armv7-M), entered by hardware on top of whatever code was interrupted; it cannot block, because blocking means "switch to other work until an event", and the interrupted work, or anything of lower or equal priority, cannot run until the handler returns. D1 D4 R3
Interrupt lock (interrupts-disabled section)
Simple words: a stretch of code during which the processor ignores interrupts. Analogy: a group that locks the hall door from the inside: nobody can enter, not even the most urgent group. Precise: code between disabling and re-enabling interrupts (on Armv7-M, cpsid i and cpsie i, which set and clear PRIMASK); interrupts that arrive meanwhile stay pending, so the tick and the scheduler are delayed by the whole length of the section. Kernels use short ones internally; their longest one is a blocking term in every task's response time. D1 D7 R2
Memory protection unit (MPU)
Simple words: a small hardware guard that can forbid code from touching some memory regions, without translating addresses. Analogy: "staff only" signs that the building enforces, on a building with one set of room numbers. Precise: an optional Armv7-M unit that checks every access against a few programmable regions with permissions and raises a fault on a violation; unlike an MMU it has no page tables and no separate address spaces, so tasks still share one memory map. D1 D2
Memory footprint
Simple words: how much memory a piece of software needs to run. Analogy: how many rooms and cupboards a school needs. Precise: for firmware, the sizes of code (.text, in flash) and data (.data and .bss, in RAM) reported by the linker or a size tool; for a Linux process, its virtual size (all mappings) and its resident set (pages in RAM), reported in /proc/self/status as VmSize and VmRSS, plus the kernel and libraries it relies on. D6 R9

Terms used without repeating them: interrupt handler (ISR), interrupt latency, hardware timer and memory map (HW204); RTOS, task, priority inversion, priority inheritance and kernel object (OS305, defined in F3-39 and F3-40, which follow this bridge); process, scheduler and preemption (OS201); virtual memory and page fault (HW203); heap (SP201); jitter, PREEMPT_RT, wake-up latency and locked memory (RB304).

Layer 1 — the kid explanation

A heater, a motor or a robot arm needs a small job done again and again at exact moments: read a sensor, decide, set the output. The question of this chapter is who makes sure that job happens on time.

On bare metal, you do. Your program is the only thing running. If your loop is busy with something long, the job waits. A timer interrupt, like a doorbell, can pull the processor away from the long thing at the right moment, so the job is on time again.

With an RTOS, a small helper program, the kernel, does the deciding. You write each job as its own task and give it a number for how urgent it is. The kernel always runs the most urgent task that is ready. If everyone follows the rules, the urgent job is on time every time.

With Linux, a big operating system does the deciding. It can do much more: files, networks, many programs, protection between them. But it was built to be fast on average, not on time every time. With the right settings and a special version, it gets much closer to "on time".

The job itself, the code that reads, decides and writes, stays the same in all three. You will prove that by running exactly the same code in all of them.

One control step, three worlds

The lab's control step (Listing 1) is a proportional-integral controller holding a simulated heater plate at 40 °C: read the temperature, compute the heater command, apply it. It is plain integer C++ with no library, so the same header compiles for the Cortex-M3 and for the PC. R8 Every world of the lab prints its own checksum; all of them are 0x941c0934 (the last line of the comparison table). The logic carried over exactly. Everything that differs below is timing.

Each world runs 1,000 steps, one per period, and a housekeeping job of 1.5 periods every tenth period. For every step it records the actuation lateness: the time stamp right after the actuator write minus the time the step was due. The spread of lateness is the loop's jitter.

World 1: bare metal, two ways

Superloop (Listing 5). The timer interrupt only counts periods. main waits for the next count, runs the step, and every tenth period runs housekeeping inline. Housekeeping takes 1.5 periods, so the step after it starts half a period late: R1



Ninety-nine of 1,000 steps were late by half a period, always the step after housekeeping (11, 21, 31 ...). The other 901 were on time to within one emulated clock. In a superloop, a job's lateness is the sum of the jobs ahead of it; you could split housekeeping into slices by hand, which turns the loop into a hand-written scheduler. D3


Interrupt-driven (Listing 6). The same step moves into the timer's handler; main keeps only housekeeping. The hardware now preempts housekeeping at every period: R1




Lateness is one emulated clock for all 1,000 steps: jitter zero at this resolution. This is the best a single processor can do, and it is how many small products work. It has a price that grows with the program: everything in a handler runs at interrupt priority, may not wait for anything (trap 1), and shares data with main under the rules of F3-37 (ring buffers, volatile, short critical sections).



World 2: an RTOS

Layer 3 — the engineer's depth


The changes, most dangerous first


    

  1. Someone else decides when your code runs. On bare metal, lateness is a property of your loop and your handlers, and you can read it off the code (Figure 2, rows a and b). On an RTOS it is a property of the whole task set: priorities, execution times, blocking and the kernel's own interrupt locks (row d); response-time analysis in F3-39 turns that into arithmetic. On Linux it also depends on the kernel's preemption model, on drivers, on interrupts of devices you did not write, on other processes and, on a virtual machine, on the hypervisor. D5 D7
    2. 

  2. Blocking becomes possible, and with it new failure modes. A task can wait on a mutex or a queue; a handler still cannot (trap 1). Waiting on a shared resource opens the door to priority inversion (trap 2).
    3. 

  3. Memory stops being one flat array you own. On the RTOS, every task needs its own stack, sized by measurement (stack painting, F3-36), and a stack overflow corrupts a neighbour silently unless an MPU region guards it. On Linux, memory is virtual: a page you touch for the first time costs a page fault, and memory you allocate may come from the kernel at the moment you ask (trap 4). D1 D6
    4. 

  4. Protection grows. Bare metal and a typical microcontroller RTOS run all code in one address space: a wild pointer in the logger can overwrite the controller. Linux puts each process in its own address space and checks every access with the MMU, so a crash stays inside its process. D9 Some RTOSes use the MPU to separate tasks or user threads, with a few regions instead of page tables (unverified box). D4
    5. 

  5. The footprint and the toolchain grow. From kilobytes and one linker script to a kernel, a C library, shared libraries, a root file system and a build system that produces all of them.
    6. 




Trap 1: blocking calls inside interrupt handlers


Listing 8 is a realistic mistake. The timer handler runs the control step and logs each command into an eight-entry ring buffer that main empties to the UART. main is busy with a ten-period job, so the buffer fills. logBlocking then waits for a free slot. The only code that frees slots is main, which is exactly the code the handler interrupted: it cannot run until the handler returns. Nothing at the same or lower priority runs again: R3




The run log records exit code 124: the emulator was stopped by the 10-second limit; the firmware was alive, spinning in a handler, and nothing else could execute. On a real board a watchdog (F1-48) would reset it, and the field report would say "random reboots". The fix keeps the handler non-blocking: try, and count what was dropped. R3




Twelve of sixty entries were dropped, and the program says so. Whether dropping is acceptable is a design decision; a bigger buffer, a faster consumer, or logging only changes are the usual answers. On an RTOS the same rule holds: a handler is not a task, so it may not call anything that blocks. Kernels make this explicit with separate non-blocking variants of their calls for interrupt context (FreeRTOS) or by allowing only a zero timeout from a handler (Zephyr), per their documentation as remembered (unverified box). D4 On Linux, a driver's interrupt handler may not sleep either; PREEMPT_RT runs most handlers as kernel threads, which changes what may sleep and where (RB304, F9-47). D5



Trap 2: priority inversion


Once tasks share a lock, a high-priority task can wait for a low-priority one, and a medium-priority task that needs no lock can stretch that wait without bound. F3-40 shows it on uRTOS; Listing 11 shows the same thing on Linux, because the rule "the most urgent ready thread runs" is the rule of SCHED_FIFO too. All threads are pinned to one CPU. L (priority 10) takes the mutex and needs 20 ms of CPU inside it; 5 ms later, H (30) wants the mutex and M (20) starts 100 ms of unrelated work: R7




H waited about 116 ms: the 15 ms left of L's critical section plus all of M's work, which has nothing to do with H. With the mutex created with the priority-inheritance protocol, L runs at H's priority while H waits, M cannot preempt it, and H waits only for the critical section: R7 D6 D7




POSIX names PTHREAD_PRIO_NONE as the default protocol, so the slow behaviour is what you get unless you ask. D6 On bare metal this trap does not exist in this form, because there are no blocking locks; its cousin is a long interrupt lock, which delays everything (the forensic lab).

Trap 4: dynamic allocation in time-critical paths


On the microcontroller the course's firmware is linked without any library, so it has no heap at all. Listing 9 puts a new[] into the timer handler, and the linker refuses: R4




That is the safest form of the rule: the mistake cannot ship. With a C library and a heap linked in, it would build, and then the allocator's time would depend on the heap's history, it could fail when memory is fragmented, and a general-purpose allocator may not be safe to call from a handler at all. RTOSes therefore offer static allocation of their objects and fixed-size memory pools (unverified box). D3 D4

Comparing worlds honestly


Three cautions make the comparison table meaningful. First, units: emulated clocks are not microseconds. The emulator runs with -icount shift=0, so its virtual time advances by a fixed amount per instruction, and its processor clock runs many instructions per tick of SysTick (F3-39 measured that ratio). The control step, a few dozen instructions, therefore costs about one emulated clock; a real core needs many cycles, plus interrupt entry, flash wait states and bus contention. D8 D2 What the emulator shows faithfully is structure: the superloop's half-period lateness and the forensic build's 0.4 period come from the code, not from the hardware model, and would appear on any chip. Second, the Linux numbers are from a virtual machine shared with other work; they change from run to run, and they are not this kernel's or this processor's specification (AH-23). Third, 1,000 samples say little about the worst case: a one-in-a-million delay needs millions of samples, hours of running and the worst load you can create, which is why F9-48 records long histograms. D7



Choosing a world


The worlds are not a ladder of quality but of capability. A motor current loop, a battery protector or a USB keyboard is often best on bare metal or a small RTOS: small, analysable, nothing else running. A product that needs networking, a file system, a camera driver or ROS 2 needs Linux, and gets its hard real-time part either from PREEMPT_RT with careful configuration or from a microcontroller beside it. Robots and drones commonly split the work that way; F9-51, F9-66 and DN302's F10-20 (NuttX, an RTOS with a POSIX interface) take the decision further. C1



How the hardware actually does it


All three worlds rest on the same few hardware mechanisms. A timer counts processor or reference clocks and raises an interrupt when it wraps; on Armv7-M the SysTick counter is part of every core, which is why this lab can use it in every build. The interrupt controller (the NVIC on Cortex-M) compares priorities in hardware and makes the core stack eight registers and fetch the handler's address from the vector table; disabling interrupts with PRIMASK leaves them pending until re-enabled, which is the mechanism behind the forensic lab. D1 D2 An RTOS adds no hardware: it uses the same timer as its tick and the same exception machinery for its context switch (PendSV and SVC on Cortex-M, F3-39). Linux on an application processor uses an MMU: page tables translate every virtual address and carry permissions, a TLB caches translations, and a missing translation raises a page fault that the kernel serves. D9 That machinery is what gives processes isolation and what makes a first touch of memory slow. On a real board, measure time with a cycle counter or by toggling a GPIO pin at release and at actuation and watching both on an oscilloscope or logic analyser; a measurement that includes the hardware is the only one that counts for the product.



Worked example


Task. A team moves the lab's loop to a product with a period of 2 ms. The housekeeping job grows to 2.5 ms of work every 20 ms. For each structure, predict the worst actuation lateness from the structure alone (ignore the step's own time and the kernel's few clocks), then say what to measure.


    

  1. Superloop. Housekeeping starts right after the step at release r and runs to r + 2.5 ms. Releases at r + 2 ms and r + 4 ms: the first is served at r + 2.5 ms, 0.5 ms late; the second is on time. Worst lateness 0.5 ms = 0.25 period. (In the lab: 1.5 periods of housekeeping gave exactly 0.5 period; check that the same reasoning reproduces it: 1.5 − 1 = 0.5.)
    2. 

  2. Housekeeping longer than two periods. If it grew to 4.5 ms, the releases at +2 ms and +4 ms would both be waiting when it ends. A loop that serves one step per pass would run them back to back, the first 2.5 ms late; the plant would see two commands within microseconds and then a normal step. The loop structure decides whether that is "late" or "skipped", and you must choose it deliberately (F9-45).
    3. 

  3. Timer interrupt or RTOS task with the highest priority. Housekeeping is preempted at every release, so its length does not matter. Worst lateness = interrupt latency + (for the RTOS) tick handling and context switch + the longest interrupt lock anywhere in the system. In the lab that was 1 and 6–8 emulated clocks. R1
    4. 

  4. RTOS with an interrupt lock in housekeeping. If housekeeping holds interrupts off for 1.2 ms and the lock can begin right before a release, the worst lateness is about 1.2 ms = 0.6 period. In the lab, the lock began at 10.5 and ended at 11.4, so the step was 0.4 period late, not 0.9: the worst case needs the lock to start right before a release. R2 A design review should find every interrupt lock and its longest path.
    5. 

  5. Linux. No structural prediction is possible from the application alone. Predict only "lateness at least the wake-up latency of this kernel on this hardware under the worst load" and measure it with a long histogram (F9-48). The recorded run's worst SCHED_FIFO step (about 1.2 ms) would already be more than half of a 2 ms period on this virtual machine. R5
    6. 



What to measure on the real product: the step's execution time (worst of many runs), interrupt latency and the longest interrupt lock (RTOS), and for Linux the wake-up latency histogram with the real load, before and after PREEMPT_RT.

Where the analogy breaks


    

  • The doorbell in the one-room school is heard at once; a real interrupt is not. Interrupt entry takes cycles, can wait for a higher-priority handler or an interrupt lock, and on a real chip depends on the instruction being executed and the memory system. The emulator hides most of this (one clock in world 1b). D2 R1
    • 

  • The campus principal's "long assembly" sounds like a person's choice; in Linux it is many small things. Non-preemptible kernel sections, interrupt handlers, other devices' drivers and, on a virtual machine, the hypervisor all add delay, none of them deliberately. D5
    • 

  • Classrooms with locks suggest the RTOS school has none. Some RTOSes do protect tasks with an MPU; what they usually lack is separate address spaces (each class seeing its own room numbers), not all protection. D1 D4
    • 

  • The story's schools differ in size; real systems may combine them. One product can have a Linux processor and a microcontroller with an RTOS on the same board, talking over a bus, each doing what it is good at (F9-51).
    • 




Common mistakes and debugging


    

  • Symptom: firmware freezes after a few seconds; with a watchdog, it resets "at random". Cause: a handler waits for something only lower-priority code can provide (trap 1). Find it: halt in the debugger; the program counter is inside a handler (Handler mode, IPSR non-zero on Armv7-M), in a loop. Fix: non-blocking calls in handlers; move the waiting part into a task. R3 D1
    • 

  • Symptom: a high-priority task's response time is sometimes much longer than its own work plus every critical section. Cause: priority inversion through a mutex without inheritance (trap 2). Find it: a timeline of who ran while the task was blocked (switch log, a trace); a medium-priority task appears inside the wait. Fix: mutexes with priority inheritance; keep critical sections short. R7
    • 

  • Symptom: a Linux control loop is fine on the bench and misses deadlines when the robot also records video. Cause: default scheduling policy, no PREEMPT_RT, memory not locked (trap 3). Find it: a latency histogram under the real load, compared with an idle one (F9-48); uname -v and the kernel configuration. Fix: real-time policy and priority, mlockall, PREEMPT_RT, CPU isolation, or move the loop to a microcontroller. R5 R6
    • 

  • Symptom: the loop's execution time has rare long outliers and page faults appear during the loop. Cause: allocation or first-touch memory in the loop (trap 4). Find it: count minor faults around the loop (getrusage), and time the step separately from the wake-up. Fix: allocate and touch everything before the loop; lock memory. R5
    • 

  • Symptom: ld.lld: error: undefined symbol: __aeabi_uldivmod when building firmware. Cause: a 64-bit division on a 32-bit core needs a compiler helper function, and -nostdlib links no helper library. This happened while writing Listing 3, with a 64-bit sum. Fix: use 32-bit arithmetic where the range allows, or link the compiler's helper library deliberately (compiler helper functions, F4-30). R4
    • 

  • Symptom: a SCHED_FIFO program behaves exactly like a normal one. Cause: the policy call failed (no permission) and the error was not checked, or helper threads inherited a policy you did not intend. Fix: check every return code, as Listings 10 and 11 do, and set helper threads' policy explicitly.
    • 

  • Symptom: measured lateness differs by exactly one period from what you expect. Cause: the time base: a tick counted twice or not at all at a boundary. Find it: F3-39 Layer 3, "time stamps you can trust".
    •

Forensic lab answer key


Observation. Steps 11, 21, 31, ... (one in ten, 99 of 1,000) are late by 10,020 clocks = 0.4008 period; all others by 6–8 clocks. In the switch log, control should start at 11.0002 as in rtos.out; instead it starts at 11.4006. Between 10.0004 and 11.4006 housekeeping runs without interruption although control was released at 11.0.


Hypotheses. (a) Swapped priorities would make control wait until housekeeping finishes (11.501), not 11.4, and both builds create the tasks with the same priorities (Listing 7, lines 94–95). (b) A lost tick would shift all later releases by a period and show late_by_a_period_or_more or a lateness near a whole period; neither appears. (c) Fits: the tick of 11.0 was taken at 11.4, so interrupts were disabled.


Root cause. With BR05_LONG_CRITICAL=1, housekeeping (released at 10) runs 0.5 period of preemptible work (10.0004 to about 10.5), then disables interrupts and works 0.9 period (about 10.5 to 11.4), then re-enables them. The SysTick interrupt of 11.0 stays pending until 11.4; the handler makes control ready, PendSV switches, and the step completes at 11.4008: 0.4 period late. R2


Longer lock. With a lock longer than one period, SysTick wraps twice while one interrupt is pending; the kernel counts one tick instead of two, so its time base falls behind real time, every later release shifts, and lateness measured with the kernel's own clock is wrong (F3-39 Layer 3).


Fix and prevention. Protect the log copy with a mutex (or copy in small chunks with very short interrupt locks, or hand the data over through a queue), so that the scheduler and the tick keep running. Prevention: a rule that interrupt locks are short and reviewed; a test that measures the longest interrupts-disabled interval (for example by instrumenting cpsid/cpsie pairs or with a trace tool) and a lateness test like this lab's in CI that fails above a threshold.


How the evidence was made. run.sh built Listing 7 twice, once with -DBR05_LONG_CRITICAL=1; both ran in QEMU with the same settings. Nothing was edited by hand.
