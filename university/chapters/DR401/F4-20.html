Story hook

The school moves into a new building. On the first morning the head does not start lessons. She walks the corridors with a clipboard and a watch: are the lights on, is the phone line working, which rooms are there, which have a teacher assigned, which are locked. At every door she writes the time. When she reaches the old porter's lodge and nobody answers the knock, she knocks once, listens, writes "empty" and moves on. Her deputy, last year, knocked on the same kind of door for an hour, because the old building's porter always answered eventually.

A first boot on a real PC is that walk. Your kernel passed every test in QEMU; now it meets a machine whose firmware, devices and timings you did not choose. The goal on the first day is not to run everything. It is to learn as much as possible from one boot, safely, with a log you can read afterwards, and to keep going past the doors that do not answer.

What you will be able to do

  • Prepare a real-hardware session that follows the curriculum's safety box: a designated spare machine, disks you may erase, a recovery path, firmware left alone.
  • Choose a log path that works before anything else does: serial (built-in, PCIe card, USB adapter) or a network log sender.
  • Structure a bring-up kernel as stamped stages that each report and go on, so one boot gives a full picture.
  • Read the machine's identity from SMBIOS and use it to key quirks.
  • Produce C12's device report: every PCI function with "driver bound / no driver", named from the PCI ID database.
  • Compare boot timelines and find the stage that regressed.
  • Recognise the "absent legacy device looks busy" trap and write presence checks.
Jargon box
Bring-up
Simple words: the first boots of your system on a new machine, done to find out what works. Analogy: the head's first walk through the new building. Precise: a staged boot that records CPU, memory map, firmware tables and devices and binds what it can, with every step logged; C12's goal is "Boot your loader and kernel on the spare machine; inventory its devices; make storage, network and input work on the real controllers." C1
Log path
Simple words: the wire your kernel's messages travel on, so you can read them on another computer. Analogy: the phone line from the new building to the old office. Precise: C12 asks for "A serial or network log path for debugging (a USB-to-serial adapter, a PCIe serial card, or a network log sender after C9)"; the ACPI SPCR and DBG2 tables name a machine's console and debug ports. C1
SMBIOS
Simple words: tables in the firmware where the machine says its own make, model and firmware version. Analogy: the plaque at the building's entrance. Precise: the DMTF System Management BIOS tables: an entry point ("_SM_" or "_SM3_") and typed structures (type 0 firmware, type 1 system, …), each with a formatted area and a set of strings. D1 R2
DMI quirk
Simple words: a fix that applies only on machines with a certain maker and model name. Analogy: "in this building, the third-floor door sticks: push hard". Precise: a quirk table entry keyed by SMBIOS strings (system or baseboard maker, product, version, firmware version); the curriculum names Linux's DMI-based quirks as the reference. C1
Boot timeline
Simple words: how long each step of the boot took. Analogy: the times on the head's clipboard. Precise: per-stage durations from a time source (here time-stamp counter ticks, not converted to seconds), compared between boots; C12's last acceptance line asks you to compare yours with a Windows boot trace of the same machine. C1
Presence check
Simple words: making sure a device is there before waiting for it. Analogy: knocking once and listening before waiting at a door. Precise: a read whose "nothing here" value is known (on this lab's machine, 0xFF from an unclaimed I/O port) tested before any wait loop that the absent value would keep busy. R3

The idea in pictures

Layer 1 — the kid explanation

When you take your program to a real computer for the first time, you want three things. First, a way to hear it talk: a cable to another computer that writes down everything it says. Second, a list it makes of everything it finds, with a clock time next to each step, so you can see where it got slow. Third, good manners: before waiting for a part to answer, check that the part is there at all. And one rule above all: use a computer whose disks nobody needs, because a program that is still learning can break things.

Layer 2 — the student explanation

C12 is the milestone where QEMU stops being the whole world. Its acceptance tests are concrete: a device report printed on real hardware, every device named from the PCI ID database; a root file system mounted from a real AHCI or NVMe disk you are allowed to erase, passing the 1 GiB I/O test; DHCP and the TCP echo test on the real NIC; and a boot timeline compared with a Windows boot trace of the same machine. C1

The safety box comes first. Only after a milestone passes in QEMU, move to "a dedicated spare machine or development board whose disk contents you do not need. Boot your work from a USB stick or a separate disk first." Expect that a bad driver can corrupt disks, and "Disconnect disks you care about while testing storage drivers on real hardware." C1

Then the log path. A PC that has a COM port gives you the B6 serial console; many current PCs have none on the back panel, so C12 lists a PCIe serial card, a USB-to-serial adapter, or a network log sender once C9 works. C1 A USB adapter needs your USB stack (C8) before it can carry anything, so a PCIe serial card or a header on the board is the earlier path.

Then the kernel itself. The lab's bring-up kernel runs stages in a fixed order — console, cpu, memory, smbios, acpi, legacy, pci — stamps each with time-stamp counter ticks, and never stops at a failure: "A stage that fails prints why and the boot goes on: a bring-up log should show everything that can be learned in one boot." L1

Layer 3 — the engineer's depth

Why this order

Each stage depends only on the stages before it. The console needs nothing and makes everything else visible. CPU identification needs only CPUID. The memory map comes from the loader (here the Multiboot information structure: flags bit 0 gives lower and upper memory sizes, bit 6 a map of ranges) and decides where everything later may live. D2 SMBIOS and ACPI are read-only firmware tables. Legacy probes touch I/O ports. PCI comes last because binding a driver is the first step that changes device state. A hang is then attributed to the last stage that started and did not end.

The machine's name for itself

SMBIOS is how quirks find their machine. The curriculum's identification table lists, for "The machine as a whole", the SMBIOS system and baseboard maker, product name and version and the firmware vendor and version, with Linux's DMI-based quirk tables as the reference. C1 The lab reads the entry point in 0xF0000–0xFFFFF, tests its checksum, walks the structures and prints types 0 and 1. To check the parser without trusting it, the boot gives QEMU its own strings (-smbios type=1,manufacturer=DR401-lab,product=spare-pc,version=1) and the kernel must print exactly those; it does. R2 On a UEFI machine the entry point is found through the EFI configuration table rather than by scanning; this lab boots with SeaBIOS only. D1

Not verified — check before relying on this

The SMBIOS entry-point offsets (smbios4.cc lines 3–8) and the Multiboot information offsets (f420_main.cc lines 35–38) were written from memory of the specifications, which were not opened. The checksum test and the -smbios cross-check pass, and the memory map's ranges add up to plausible totals (130559 KiB usable on a 128 MiB guest), which supports the offsets used; offsets the lab never reads are untested. The location of the SMBIOS entry point on UEFI machines is from memory.

The absent device that looks busy

Old code often waits for a legacy controller with a loop like "while status bit 1 is set, wait". On a machine where nothing answers that port, the read returns all ones (0xFF on this lab's machine), bit 1 is always set, and the loop waits until its limit — or forever, if it has none. R5 The lab shows both: on q35 with the PS/2 controller present the status reads 0x1c and the wait ends after 70550 ticks; with i8042=off the presence check reads 0xff, says "absent, skipped", and the stage takes 1127682 ticks. R2 R3 Without the check, the same stage runs into its 4,000,000,000-tick limit. R4 The rule generalises: before any wait, know what "not there" reads as, and test for it. On ACPI machines the firmware also says which legacy devices exist (the DSDT's PNP0303 object for the keyboard controller, F4-14). C1

Not verified — check before relying on this

The i8042 status bit meaning (bit 1, "input buffer full") is from memory, and "an unclaimed I/O port reads 0xFF" is what QEMU does in this build; on a real PC the value depends on the chipset. Some machines emulate an i8042 in firmware (for USB keyboards) and some have none; whether a given PC does is something to observe on that PC, not to assume. The ACPI FADT also has a boot-architecture flag for the 8042, recalled from memory and not used in this lab.

Comparing timelines

timeline.py reads the "end <stage> ticks N" lines of two logs and flags a stage that grew more than 10 times and by more than 100,000,000 ticks. L3 Both conditions matter: in this build, whole boots under TCG vary by a factor of about two from run to run (the normal comparison in the saved run shows ratios from 0.8 to 2.0, and an earlier run of the same lab, log not kept, showed 0.4 to 1.0), so a ratio alone would flag noise in short stages, and an absolute growth alone would flag a stage that is slow in both. R4 C12 asks for the same kind of comparison against a Windows boot trace of the same machine: there, the per-driver times from the trace and the per-stage times from your log are in different units and granularity, so compare order and outliers, not totals. C1

How the hardware actually does it

A real PC differs from q35 in ways that matter on day one. The firmware is a vendor's UEFI, not SeaBIOS; the machine has dozens of PCI functions (F4-14's build VM alone shows 11, and a laptop more); devices are behind bridges, some powered down by firmware; the console may not exist. The curriculum's bring-up guidance for real controllers adds: read the machine's own ACPI tables first (dump them under Linux or Windows and disassemble the DSDT with iasl), the datasheets for its NIC and storage controllers, the Linux drivers for those devices, and your Windows boot trace. C1

The safe order on the spare machine:

  1. Boot Linux from a USB stick on the spare PC; save lspci -nnvv, the ACPI tables, dmidecode output and the kernel log: these are your reference answers.
  2. Boot your kernel from a USB stick with only the log path and read-only stages enabled (as in this lab): nothing is written to any device.
  3. Compare the device report line by line with the Linux reference (F4-14's method).
  4. Enable one driver at a time, storage last, and only on a disk designated as disposable, with other disks disconnected. C1
Safety

Use only a designated spare machine whose disks you may erase, and boot from a USB stick or a separate disk first. Disconnect disks you care about while testing storage drivers. Never flash self-built firmware onto a machine you depend on: firmware work needs a documented recovery path, an external SPI flash programmer with a test clip and a verified backup of the original flash. The runbook adds: never write to a real disk not explicitly designated as disposable, and record real-hardware results separately — a hardware observation never replaces a QEMU test. C1 A USB-to-serial adapter on a board's UART pins must match the pins' voltage (the curriculum: "use a 3.3 V USB-to-serial adapter (never 5 V)" for SoC boards); a PC's back-panel COM port uses RS-232 levels, which need an RS-232 adapter, not a logic-level one.

Not verified — check before relying on this

Untested on hardware: no real PC was available, and the build container lacks the tools to make a bootable USB image (no grub-mkrescue or xorriso), so steps 1–4 above and the C12 acceptance tests on real hardware were not run. The RS-232 level remark is general knowledge, not from a document opened in this build.

Where the analogy breaks


    

  • An empty room is quiet; an absent device can answer. The port returns a value (0xFF here) that looks like a device saying "busy". R3
    • 

  • The head can walk back. A kernel that hangs in a stage gives no second chance in that boot; that is why the log path comes first and every wait is bounded.
    • 

  • The plaque can be wrong. SMBIOS strings are written by the maker and are sometimes placeholders; a quirk keyed on them must use the exact strings read, and a generic string matches many machines. C1

Forensic lab answer key


Observation. timeline.py flags "legacy": 1127682 ticks before, 4000915102 after (×3547.9); all other stages are between 0.3 and 0.8, inside the run-to-run variation. The after log's legacy stage says "i8042: waiting for input buffer empty, stopped after ticks 4000185716" — the full 4,000,000,000-tick limit plus the loop's last pass.


Root cause. The build defines F420_NO_PRESENCE_CHECK (lines 173–177): the code waits for status bit 1 to clear without first reading whether a controller is there. On i8042=off the port reads 0xFF (as boot_nops2.out shows), so bit 1 never clears and the wait runs to its limit. On a machine with the controller (boot.out, status 0x1c) the wait ends after 70550 ticks, so the removal is invisible there: that is why it looked redundant.


Why the boot still passes. The wait is bounded and the stage does not treat the timeout as an error; it reports and goes on. Bounding saved the boot; the regression is still real: about two seconds of host time per boot in this build, and on real hardware an unbounded copy of the same loop would hang.


Fix and verification. Restore the presence check (the normal build), and report a timeout as an error line. Verify: timeline.py boot_nops2.out <new boot> exits 0, and the legacy stage reads "absent, skipped".


Wrong answers and why. "Everything else got faster (PCI ×0.3), so the change also sped up the boot": run-to-run variation of TCG emulation, below both thresholds, not an effect of the change. "The SMBIOS change": the strings differ only because boot_nops2 sets none; the stage time is unchanged. "Raise the limit": the device is absent; any limit is wasted time.
