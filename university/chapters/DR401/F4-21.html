Story hook

A visitor at the school sits in room 2C at the end of a long corridor. She never walks to the office. When she has something to say she presses a bell button; the bell rings on the office's bell board, and the clerk at the board tells the office "room 2C rang". Someone from the office then walks down the corridor, knocks on 2C and collects a note. The notes are written in a private shorthand, but on the first day she handed over a card explaining it: "first three marks: buttons; next two numbers: across and down".

Three people must do their jobs for one note to arrive: the corridor runner (who knows how to knock and what silence means), the bell-board clerk (who knows which wire is which room's bell and says which one rang) and the interpreter (who reads the card and turns marks into meaning). If any of them does it wrong, the office hears nothing — or hears the bell ringing forever.

That is a laptop touchpad. This chapter builds all three parts against a model, because a touchpad is the first device in this course where no single driver is enough.

What you will be able to do

  • Name the three drivers a HID-over-I2C touchpad needs and what each does, from the catalog row and C14.
  • Read where each driver gets its facts: ACPI (I2cSerialBusV2, GpioInt, _DSM) for addresses and lines, the device's HID descriptor for registers, its report descriptor for the meaning of reports.
  • Parse a HID report descriptor into fields with bit offsets, and self-check it.
  • Drive the HID-over-I2C sequence against a model: descriptor fetch, report-descriptor fetch, reset, power on, input reads on interrupt.
  • Handle "no acknowledge" as a reported error, not a hang.
  • Explain why a level-triggered interrupt that is never serviced looks like an interrupt storm.
Jargon box
HID over I2C
Simple words: a way for an input device to send keyboard and mouse style messages over a small two-wire bus. Analogy: the visitor in room 2C and her notes. Precise: Microsoft's "HID over I2C Protocol Specification": a device on an I2C bus exposes a HID descriptor at a register named by ACPI (_DSM), from which the host learns the registers for the report descriptor, input, output and commands; ACPI identifies it with compatible ID PNP0C50. D1 C1
Report descriptor
Simple words: the card a HID device hands over describing what its messages mean. Analogy: the shorthand card. Precise: a byte string of items (main, global, local; each a one-byte prefix with tag, type and size, then 0, 1, 2 or 4 data bytes) defined by the USB-IF HID class definition; the same descriptor format is used on USB, I2C and other transports. D2
Input report
Simple words: one message from the device: button states and positions packed into bits. Analogy: one note from room 2C. Precise: a byte string whose fields the report descriptor locates by bit offset and size; on HID over I2C it is read from the input register and starts with a 2-byte length. D1
NACK
Simple words: on I2C, the silence that means "nobody here" or "not now". Analogy: knocking on a door and hearing nothing. Precise: the receiver leaves the acknowledge bit high after an address or data byte; an I2C controller driver reports it as an error (the lab's model returns -ENXIO, which this course recalls, unverified, as the value Linux I2C drivers use for an address NACK); C14 requires that "A deliberate wrong I2C address produces a reported "no acknowledge" error, not a hang." D3 C1
Level-triggered interrupt
Simple words: an interrupt that keeps firing as long as the signal stays on. Analogy: a bell that rings as long as the button is held. Precise: the interrupt condition is the line's level, not its change; the device holds the line asserted until the cause is cleared (for a HID-over-I2C device, until the host reads the pending report), so a handler that does not clear the cause is called again at once. D1
GpioInt resource
Simple words: the line in the ACPI table that says which GPIO pin carries a device's interrupt. Analogy: the bell board's wiring chart: which bell is room 2C. Precise: an ACPI resource descriptor in a device's _CRS naming a GPIO controller, pin, trigger mode and polarity; with I2cSerialBusV2 (controller, address, speed) it is how the touchpad's ACPI object tells the OS how to reach it. D4 C1

The idea in pictures

Layer 1 — the kid explanation

A touchpad is a small helper inside the laptop that talks over two tiny wires. It cannot talk whenever it likes: it has a separate "ring" wire, and when your finger moves it pulls that wire to say "I have news". The computer then asks "what is it?" over the two wires and gets a short message. To understand the message, the computer read a description card from the touchpad at the start: which bits are buttons, which are across and down. Three programs share the work: one for the wires, one for the ring, one for the messages. If the message program forgets to ask, the touchpad keeps ringing.

Layer 2 — the student explanation

The catalog row says it plainly: "Most laptop touchpads are HID over I2C behind a DesignWare I2C controller with a GPIO interrupt: three drivers (I2C, GPIO, HID) must cooperate." The ACPI object has compatible ID PNP0C50 and a _DSM that gives the HID descriptor address. C1

C14 asks you to build: "ACPI resource parsing for serial-bus and GPIO resources; the I2C controller driver; a GPIO interrupt path; the HID-over-I2C protocol (descriptor fetch, report reads, reset); a report-descriptor parser shared with C8's USB HID (the parser must not care which bus delivered the report)." C1

The order of work follows the dependencies. ACPI first: without the I2C address and the GPIO pin nothing else can start. Then the I2C controller driver, testable alone by reading a register of any device on the bus (and by getting NACK from an empty address). Then the HID-over-I2C driver's probe, which only needs I2C: read the 30-byte HID descriptor, then the report descriptor. Then reset and power on. Last, the GPIO interrupt path, which turns "the line is asserted" into a call to the HID driver's handler.

The lab cannot do any of this on a laptop, and QEMU has no HID-over-I2C device (F4-19's list of 426 device types has none). R5 So it builds the two parts that can be tested on the host — C14's first acceptance line is itself a host unit test — and a model of the rest: a bus that answers NACK for empty addresses, a touchpad model with registers, and a level-triggered line.

Layer 3 — the engineer's depth

Report descriptors, item by item

A report descriptor is a sequence of short items. The prefix byte holds a 4-bit tag, a 2-bit type (main, global, local) and a 2-bit size code (0, 1, 2 or 4 data bytes); 0xFE starts a long item. Global items (usage page, logical minimum and maximum, report size, report ID, report count, push, pop) set state that lasts; local items (usage, usage minimum and maximum) apply to the next main item only; main items (input, output, feature, collection, end collection) consume the state. Each input item adds report size × report count bits to its report. D2 The lab's parser does exactly that and nothing more: it tracks bit offsets per report ID, names usages on the Generic Desktop, Button, Keyboard and LED pages, and says "constant" for padding.

Not verified — check before relying on this

The item tags and their numbers (hid_parse.cc lines 61–111), the page and usage numbers (lines 121–137) and the rule that a 1-byte logical maximum of 0xFF after a minimum of 0 should be read unsigned are from memory of the HID class definition and usage tables, which were not opened. The parser agrees with itself on three descriptors and catches one inconsistency (below); it has not been compared with Linux's parsed view, which is what C14's first acceptance line requires.

Descriptors from a real program

C14's host test wants descriptors "dumped from three different real touchpads and keyboards (collected under Linux)". C1 No such dumps exist in this build, so the lab takes the next real thing it has: the descriptors compiled into the QEMU program, found by their shape (Usage Page Generic Desktop, a Usage, Collection Application) and walked item by item until the collections close. It finds three complete descriptors — a tablet (absolute pointer), a keyboard and a mouse with a report ID — and one candidate whose collections do not close within 1024 bytes. R1

The self-check then finds something real: the keyboard descriptor's input report adds up to 34 bits, not a whole number of bytes. The item list shows why: at offset 46 the bytes are "95 06", then "06 75 08". 0x06 is a Usage Page item with two data bytes, so it swallows "75 08" (which would have been Report Size 8), and the key array is counted as 6 fields of the previous size, 3 bits. R2 Removing that one byte gives 64 bits, 8 bytes (checked in this build, Check yourself question 7). Either the program file really contains a stray 0x06 at that point, or the extraction picked up bytes that are not one descriptor; this build cannot tell, because it has no USB stack in a guest to see which bytes QEMU actually sends.

Not verified — check before relying on this

Whether QEMU 8.2.2's USB keyboard really presents a 64-byte descriptor with an extra 0x06, and what a host does with it, is unresolved. Do not cite this as a QEMU bug. Check it by dumping the descriptor a Linux guest receives (its HID report-descriptor file in sysfs or debugfs) and comparing; until then the course uses the tablet descriptor, which passes the self-check, for the touchpad model. The incomplete mouse candidate at offset 13113712 is likewise unexplained.

The HID-over-I2C sequence

As this course remembers the protocol: the host writes the 16-bit HID descriptor register number (from _DSM) and reads 30 bytes, in one transfer with a repeated START. The descriptor gives, as 16-bit little-endian fields, its own length (30), the protocol version (0x0100), the report descriptor's length and register, the input register and maximum input length, the output register and length, the command and data registers, and vendor, product and version IDs. The host reads the report descriptor the same way. It sends RESET through the command register; the device answers by asserting its interrupt and offering an input read of length 0. It sends SET_POWER (on). From then on, every interrupt is answered by a plain read of up to the maximum input length: 2 bytes of length, then the report. D1

Not verified — check before relying on this

Everything in the paragraph above — the descriptor's field order, the command register's layout (register, then a low byte with the power state, then the opcode), opcodes 1 (RESET) and 8 (SET_POWER), the zero-length reset answer and the 2-byte length prefix — is from memory of Microsoft's "HID over I2C Protocol Specification", not opened in this build. The model and the driver were written from the same memory, so their agreement proves consistency, not correctness. Check every field against the specification and against Linux's i2c-hid driver before using it on a laptop.

Why level-triggered matters

The model's interrupt line is asserted while a report is pending and released when the host has read it. With a level-triggered GPIO interrupt the handler is called on every tick the line is asserted. A handler that reads the report clears the cause: 7 touches, 7 interrupts, 7 reports. A handler that does not read leaves the line asserted forever: from the first touch on, every tick is an interrupt. R3 R4 That is why C14's acceptance says "the interrupt counter grows only while the pad is touched". C1

How the hardware actually does it

On a laptop, the touchpad's ACPI object sits under an I2C controller's object in the DSDT. Its _CRS holds an I2cSerialBusV2 resource (which controller, the 7-bit address, the bus speed) and a GpioInt resource (which GPIO controller, which pin, edge or level, polarity); its _DSM, called with the HID-over-I2C identifier, returns the HID descriptor register. C1 D4 You read all of these from the machine's own DSDT with iasl (C10's AML interpreter evaluates them at run time). The I2C controller on most such laptops is DesignWare-compatible, with Linux's i2c-designware as the reference driver; the GPIO controller is the platform's pin controller (Linux's pinctrl drivers). C1

Two practical rules from the catalog apply. I2C has no enumeration: the address comes from ACPI, devicetree or the schematic, so scanning addresses is guessing, and on a shared bus it can disturb devices. And "a device whose clock or reset is off reads as all zeros or hangs the bus. First bring-up rule: keep what the firmware enabled and do not gate unknown clocks". C1

Safety

Do not write to I2C addresses you have not identified: the same controllers can reach SPD EEPROMs on memory modules ("read-only, never write them"), battery and charger chips and sensors. Do not reprogram GPIO pins you do not own: a pin configured as an output can fight another driver. Work on a laptop designated as a spare. C1

Not verified — check before relying on this

Untested on hardware: no laptop, no DesignWare I2C controller and no GPIO controller were available. The ACPI resource names come from the curriculum; their binary layouts were not used in this build. The "_DSM returns the HID descriptor register" detail is the catalog's; the _DSM identifier itself is not given here.

Worked example

Task. From the tablet descriptor (80 bytes), find where X, Y and button 1 live in an input report.

  1. Collections. Application Mouse, then Physical Pointer. R2
  2. First input item. Usage Page Button, usages 1..3, logical 0..1, count 3, size 1: bits 0–2.
  3. Padding. count 1, size 5, constant: bits 3–7.
  4. X and Y. Usage Page Generic Desktop, usages X and Y, logical 0..32767, size 16, count 2, absolute: X at bits 8–23, Y at 24–39.
  5. Wheel. relative, 8 bits: bits 40–47. Total 48 bits, 6 bytes, no report ID.
  6. On the wire. A HID-over-I2C input read is 2 length bytes plus the report: 8 bytes, which is the model's maximum input length. A touch at (1000, 2000) reads 08 00 00 e8 03 d0 07 00; the driver's decode gives x 1000, y 2000, button 0 (R3's event 0).

Where the analogy breaks


    

  • The bell-board clerk cannot stop the ringing. With a level-triggered line, only clearing the cause (reading the report) stops the interrupt; the GPIO driver cannot fix a missing read. R4
    • 

  • Silence is not always "nobody here". On I2C a NACK can also mean a busy device or a byte it refuses; the driver reports it and decides, it does not assume. D3
    • 

  • The card can be wrong. A report descriptor is data from the device; the lab found one whose fields do not add up to whole bytes. A parser must check, not trust. R2

Forensic lab answer key


Observation. 180 interrupts in 200 ticks, 173 of them on ticks with no touch, 0 reports read. The first touch is at tick 20; from tick 20 to tick 199 is 180 ticks: an interrupt on every one. Probe, reset and power-on traces are identical to the passing run.


Root cause. The handler (irq, lines 173–176) returns without reading under F421_NO_READ. The model keeps its interrupt line asserted while a report is pending (line 62), so the level-triggered line is never released, and every tick calls the handler again. The reset answer was read by the setup code in main (line 228), not by the handler, which is why reset looked fine.


Why not the GPIO driver. The GPIO side does what it should: it reports a line that is asserted. Switching to edge-triggered would hide the storm — one interrupt at the first touch — and lose every report after it, because the line would never be released to make a new edge.


Fix and verification. Read the input register in the handler (the normal build): 7 interrupts, 0 on idle ticks, 7 reports, PASS. The test: the model run with an idle-interrupt counter, which is C14's "grows only while the pad is touched" in host form.


Wrong answers and why. "Disable the interrupt after the first one": no more reports either. "Add a delay in the handler": slows the storm, does not end it. "The touchpad is faulty": the model, which behaves correctly with the right handler, shows the same storm.
