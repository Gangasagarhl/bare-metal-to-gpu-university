Story hook

Before an important visit, the office rehearses. A colleague plays the visitor and follows a script of what the visitor will probably say; the interpreter practises. Then the office plays back the recording of an earlier, real visit, line by line, to check that the interpreter would still say the same things. Then it tries the awkward cases: the visitor who does not answer, the visitor who leaves early, the one who speaks so fast that every phrase arrives twice.

One year the rehearsal had a flaw that nobody saw. The checklist said: "the interpreter answers every question". It did not say "correctly". A new interpreter, very confident, answered every question instantly, without waiting for the visitor to finish. Every rehearsal passed. At the real visit, the interpreter answered the visitor's questions before hearing them, and repeated the visitor's first words back as the answer.

This chapter writes the test plan of the universal method for the F4-17 driver, runs every category of it that the build can run, and then asks the uncomfortable question every test plan needs: would these tests notice if the driver were wrong?

What you will be able to do

  • Write a test plan with the curriculum's eight categories, before the tests, with acceptance criteria fixed.
  • Compile a kernel driver unchanged for the host through small shims, and test it against a model written from the observed specification, with sanitizers on.
  • Record a driver's register accesses in the emulator and replay them to the host build (trace replay).
  • Inject faults (stuck device, removal returning all ones, removal returning zeros, a status that never clears) deterministically with a fake clock.
  • Measure a test suite's strength with a mutation: a deliberately broken driver must fail it.
  • Explain what each category can and cannot prove, and what a real-hardware matrix records.
Jargon box
Test plan
Simple words: the list of tests a driver must pass, written before the tests are. Analogy: the rehearsal programme agreed before rehearsing. Precise: the document of stage (e): emulator tests (or why none exist), host unit tests, trace-replay tests, the real-hardware matrix, fault injection, soak and reference comparison, each with its acceptance criterion; criteria are fixed there and not weakened later without the learner's approval. C1
Test shim
Simple words: a small stand-in for the kernel functions a driver calls, so the same driver code runs in a normal program. Analogy: the colleague who plays the office during a rehearsal. Precise: host implementations of mmio_read32, rdtsc, the PCI accessors and printing, sending device accesses to a model and giving a deterministic clock. R1
Device model
Simple words: a program that behaves like the device, for testing. Analogy: the colleague playing the visitor from a script. Precise: here, a host class implementing the observed specification's behaviour of each register, with switches that inject faults; it models what was observed, not what a datasheet promises. R1
Trace replay
Simple words: playing a recorded conversation with the device back to the driver and checking it says the same things. Analogy: replaying last year's real visit line by line. Precise: every read returns the recorded value, every write must equal the recorded offset and value; any difference is a mismatch. C1 R3
Mutation testing
Simple words: break the driver on purpose and check that the tests notice. Analogy: sending a deliberately bad interpreter to the rehearsal. Precise: a mutant is a copy of the code with one small change (here, the busy-wait removed); a suite that passes on a mutant is too weak to protect against that kind of bug. R6
Soak test
Simple words: run the driver for a long time and count errors. Analogy: a full-day rehearsal, not five minutes. Precise: long runs (the curriculum says hours) with throughput and error counters logged; this build's soak is 20,000 operations in the emulator. C1 R5

The idea in pictures

Layer 1 — the kid explanation

Before you trust a program that talks to a part, you test it in many ways. You make a pretend part out of software that behaves like the real one, and you check the program's answers against answers you already know. You make the pretend part misbehave on purpose: it never finishes, or it disappears, and you check that the program notices and stops nicely. You play back a recording of the program talking to the real part. And then you do something sneaky: you break the program on purpose and see whether your tests catch it. If they do not, your tests were not good enough.

Layer 2 — the student explanation

The curriculum lists eight kinds of test for stage (e): emulation first; host unit tests for every pure function; trace replay; a real-hardware matrix; fault injection; soak; reference comparison; and regression ("the emulator part runs in the harness on every commit; real-hardware runs are recorded in the log as separate evidence"). C1 The runbook adds two rules: the plan is written before the code, and its acceptance tests are never weakened later without the learner's approval. C1

The lab's plan, test_plan.txt, gives each test an ID, what it checks, how success is observed, where it runs and its status. Of its 19 rows, 16 are marked "run" in this build; the real-hardware matrix (H1) is "not applicable" (no real 1234:11e8 exists outside the emulator), the soak row (S1) points to 20,000 operations in the emulator instead of hours, and G1 states the regression rule. L1

The host tests need the driver to run outside the kernel. The driver is not changed: two small headers in a host/ folder replace the kernel's k4.h and pci4.h, a model of the device answers its register accesses, and a fake clock advances by 1,000 ticks every time the driver reads the time, so that "wait 50,000,000 ticks" takes 50,000 reads and no real time. The pattern: every category proves agreement with something. The model, the emulator and the recording are all second-hand descriptions of the device; only the real-hardware matrix compares with the device itself, which is why the curriculum keeps those runs as separate evidence. C1

The model must say where it guesses

The model implements the observed specification. Where the specification is silent, the model has to choose, and says so in a comment: F4-16 saw IRQ_RAISE and IRQ_ACK used with one value only, so "RAISE ORs bits in, ACK clears the bits written" is "the model's guess". COMPUTE reading N while busy was observed (the busy-wait mutant depends on exactly that). L2 A test that passes only because of a guessed behaviour is weaker evidence than one that passes on observed behaviour; mark which is which.

Golden traces and timing

The golden trace is recorded while the emulator runs the F4-17 kernel; the replay makes the host build of the same driver produce the same writes in the same order. Polls are a problem for any replay: the number of STATUS reads depends on timing. Here the replay serves each read from the recording, so the driver polls exactly as many times as it did when recorded, and the fake clock keeps the deadline far away. The recording itself is not stable: the poll counts differ between runs (15 polls, one per computation, in the recording whose replay is shown; 27312 in F4-17's saved run; every new run differs again). R3 R2 So the plan says the golden trace is re-recorded "only when the driver's access sequence is changed on purpose", and comparisons between recordings fold polls, as F4-16's diff does. L1

Testing the tests

One mutant was made by replacing the busy-wait's exit test with an unconditional break: the driver no longer waits for the device to finish. R6 On the model, which returns N while busy, the mutant returns n instead of n!. The weak suite (T1, and "compute returns Ok") passes on it; the full suite fails it in three tests: T4 (values: 13 wrong), T5 (a stuck device no longer times out) and T9 (counters: 100 polls instead of 400). R6 One mutant is a spot check, not a measurement; tools exist that generate many mutants automatically, and the extension asks you to try more by hand.

How the hardware actually does it

None of the host tests touch hardware: the shim's mmio_read32 is a function call into the model. That is the point and the limit. The real access is a bus transaction with posting, ordering, and a device that takes physical time; F4-17's posted-write discussion applies only on the emulator and real hardware rows. R1

In the emulator, each access traps into QEMU's device model, which runs the device's logic in software; QEMU's edu model finishes a factorial on its own schedule, which is why poll counts vary. On real hardware, a soak would also expose temperature, power-state transitions and interference from other devices on the bus, none of which an emulator has. C1

Not verified — check before relying on this

That QEMU's edu device computes in a separate thread with a delay (the reason poll counts vary) is from memory of its source, which was not opened in this build; the variation itself is observed (R2, R3). Automatic mutation-testing tools are mentioned by kind only; none was installed or run.

Where the analogy breaks


    

  • A stand-in visitor can improvise; a model only does what you wrote. A colleague playing a visitor may surprise the interpreter. A model never does anything its author did not think of, so model tests cannot find misunderstandings of the device; only the emulator and real hardware can. L2
    • 

  • Rehearsals take real time; host tests do not. The fake clock makes a 50,000,000-tick timeout happen in microseconds, which is what lets the suite test timeouts on every commit. R1
    • 

  • Nobody sends a bad interpreter to a rehearsal on purpose. Mutation testing does exactly that, and it is the only check in this chapter that measures the tests rather than the driver. R6
    •

Forensic lab answer key


Observation. The CI log: T1 and T4w pass, "2 of 2 tests passed", exit 0. The field log: compute(0) = 0, and compute(1) to compute(14) return n itself, which is right only for 1 and 2 (1! = 1, 2! = 2); 13 problems, exit code 35. The counters read "computes 15 polls 15": exactly one STATUS read per computation, against 27312 polls for 15 computations in F4-17's saved normal run. Taken alone the poll count is weak evidence: the normal driver's golden recording in this build also needed one poll per computation, because the device happened to finish before the first read. The values are the decisive evidence; the poll count is the clue that points at the busy-wait.


Root cause. The shipped driver's busy-wait exits after the first STATUS read whatever it says (mutation.out: "break; // MUTANT: busy-wait removed"). It reads COMPUTE before the device has finished. What a busy device returns there is the argument N in this saved run (as F4-16 observed and F4-18's model assumes); compute(0) = 0 is N too. Which reads land while the device is still busy is decided by timing, so another run can show different wrong values: one more reason never to read a result before the busy bit clears.


Why CI passed. (1) The CI suite checks that compute returns Ok, not what it returns. (2) It has no timing-sensitive test: no stuck-device test (T5) and no counter test (T9). The full suite fails the mutant in T4 (13 wrong values), T5 (no timeout on a stuck device) and T9 (100 polls instead of 400). R6


Process rule. Ship only on the full acceptance suite of the plan, and run the mutation check whenever the suite changes; a suite that passes a mutant must be strengthened before it gates anything (runbook: acceptance tests are fixed in the plan and never weakened without approval).


Wrong answers and why. "The device is slow in the field": the device answered N, which only happens while busy; the driver read too early. "A compiler optimisation removed the loop": the source line itself is changed. "The emulator's edu model is broken": the original driver gets n! on the same emulator.
