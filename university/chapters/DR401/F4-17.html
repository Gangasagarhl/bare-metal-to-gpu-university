Story hook

Before a long visit, the office asks the interpreter for a written plan. Who meets the visitor at the gate, and how do they recognise each other? Which rooms will the visitor use, and who must unlock them? In what order are the first introductions made? What does the interpreter do if the visitor falls ill, or leaves without saying goodbye? Who is told, and how? The office will not let the visit start until every question has an answer, even if the answer is "we do not know yet, so we will not do that part".

One interpreter's plan said: "if the visitor stops answering, wait until they answer again". On the second day the visitor went home at lunch, without a word. The interpreter waited in the empty room all afternoon, and in the evening reported that the visit was going well, because nothing had gone wrong in the room. A second interpreter's plan said "wait for an answer, but not longer than ten minutes", and handled the same departure correctly. A third plan, written after the first two, added one line: "after every answer, check that you are still talking to the same visitor", because on the third day an empty chair had been mistaken for a visitor who had nothing to say.

This chapter writes that plan for a device: the design note, with every row of the curriculum's design table answered and every register traced to the document it came from. Then it writes the driver from the note and tests what happens when the device leaves without saying goodbye.

What you will be able to do

  • Answer every row of the curriculum's design table (5.4) for a device: bus binding, resources, initialization, register model, interrupts, DMA and coherency, power, error handling, hot-plug, upper interface, trust, observability.
  • Trace every register a driver touches to a document and section (or an observation), and check this mechanically.
  • Write a probe that proves the device is present and behaves as specified before claiming it.
  • Bound every wait with a timeout, and distinguish "busy", "done" and "gone".
  • Inject a removal fault and show that the driver stops cleanly.
  • Explain why "not busy" can be a lie, using this build's finding about what an emulated BAR reads when decoding is switched off.
Jargon box
Design note
Simple words: the written plan for a driver, made before the code. Analogy: the interpreter's plan for the visit. Precise: one entry per row of the curriculum's table 5.4, each with its answer and "where found"; plus a register table giving every register's source document and section title; approved by the learner before driver code (runbook). C1
Probe
Simple words: the driver's first meeting with a device: check it really is what it claims, then take charge of it. Analogy: the greeting at the gate. Precise: the driver-model function called after a match; it claims resources, runs the initialization sequence and a self-test, and returns an error (leaving the device unbound) if any check fails. R1
Surprise removal
Simple words: a device disappears while the driver is using it. Analogy: the visitor who goes home at lunch without a word. Precise: on PCI Express, reads after removal return all ones (the curriculum's 5.4 "Error handling" row); in this build's emulator, a BAR whose memory decoding is off reads 0 instead, which a status poll can mistake for "done". C1 R3
Bounded wait
Simple words: waiting for a device, but never forever. Analogy: "wait ten minutes, then report". Precise: a poll or sleep loop with a deadline (here in time-stamp-counter ticks), whose expiry is a distinct, reported error; the curriculum asks for "timeouts on every wait". C1
Posted write
Simple words: a write the CPU sends without waiting to hear that it arrived. Analogy: a note pushed under the door. Precise: PCI memory writes are posted: they may still be on their way when the next instruction runs; a read from the same device forces earlier writes to complete first, which is why drivers "read back to flush" when order matters. C1 D2
Register table
Simple words: the list of every register the driver uses, with where each fact came from. Analogy: the plan's list of rooms, each with who holds its key. Precise: the part of the design note that M2's acceptance test checks: "Each register the driver touches is listed in the design note with its document and section title." C1

The idea in pictures

Layer 1 — the kid explanation

Before you write a program that talks to a part, you write a plan on paper. How will you find the part? Which parts of it will you use? What do you say first? How do you know it understood you? What will you do if it takes too long to answer, or if someone unplugs it in the middle? For each answer, you write down where you learned it. Only when every question has an answer do you write the program, and the program follows the plan, step by step.

Layer 3 — the engineer's depth

A probe that proves

F4-01 taught that a driver must greet its device before claiming it. Here the greeting has four parts, each from the specification: the BAR has the observed size; the ID register reads the one value ever observed (any other value is "a revision we have never observed": refuse rather than guess); the CHECK register returns the inverse of a pattern; and the interrupt-status path raises and clears. R1 Refusing an unknown ID looks strict. It is right for a device you learned by observation: your specification covers only the revision you watched.

"Busy", "done" and "gone"

The compute loop reads STATUS until bit 0 clears. Three outcomes must be told apart: busy (keep polling), done (read the result), gone (stop). The curriculum's error-handling row gives one rule for "gone": on real PCI Express, reads after surprise removal return all ones. C1 The driver checks for that value first. Then the lab's fault injection switched the device's memory decoding off between two computations, and this build found something the rule does not cover: in QEMU, reads of the BAR with decoding off return 0, not all ones. R3 Zero has bit 0 clear, so the loop sees "done" and reads a "result" of 0. Version 1 of the driver did exactly that for every remaining computation (the forensic lab). The fix is to confirm, after every computation, that the ID register still reads the observed value; zero or anything else means gone. R2

Not verified — check before relying on this

"Reads after surprise removal return all ones" is the curriculum's statement (C1) and the PCI Express behaviour as remembered (D2, not opened); it was not observed in this build, which has no hot-plug hardware. "Reads with memory decoding off return 0" was observed only in QEMU 8.2.2 on this machine (R3); what a real device or chipset returns for an access to an address nobody decodes depends on the platform. The ID re-check is useful whichever is true.

Choosing a deadline

The note gives 50,000,000 time-stamp-counter ticks per computation and says it was "chosen for the emulator; to be re-measured on real hardware". The design value must be far above the longest normal wait and short enough that a stuck device is reported quickly. The F4-18 soak run measured the normal case: 20,000 computations, no timeouts. R5 On real hardware, deadlines belong in time units, converted from a measured counter frequency (F4-22 measures one), never in loop iterations.

Posted writes and read-back

PCI memory writes are posted: the CPU does not wait for them. A read from the same device cannot pass earlier writes to it, so reading back is how a driver makes sure a write has arrived before it relies on the effect. D2 The edu4 driver always reads the register that shows the effect (CHECK after writing CHECK, IRQ_STATUS after RAISE and ACK, STATUS after COMPUTE), so ordering is never assumed. On x86 with uncached MMIO mappings, the CPU also keeps the accesses in program order; on other architectures you need explicit barriers (curriculum 5.4, "Register model"). C1

Not verified — check before relying on this

The PCI ordering rule (a read does not pass a posted write in the same direction) and the x86 statement about uncached MMIO ordering are from memory of D2 and of the Intel SDM's memory-ordering chapter; neither was opened in this build, and the emulator cannot show reordering. Check before writing a driver for another architecture.

Switching things off on purpose

The note switches bus mastering off. The device has registers (0x80–0x98) whose purpose is unknown; if one of them started a DMA transfer, a device without bus mastering cannot write to memory. A design note is also the place for these defensive decisions, with the reason. R4

How the hardware actually does it

Bit 1 of the PCI command register (memory space) tells a function to respond to memory accesses in its BARs; bit 2 (bus master) allows it to start its own memory transactions. With memory space off, the function ignores accesses to its BAR addresses. What the CPU then reads depends on what else answers at that address: on real PCI Express, an access that nobody claims is completed by the root complex with an error status, which the CPU sees as all ones; in QEMU 8.2.2 the read returned 0. L1 R3 The bit names come from <linux/pci_regs.h> (PCI_COMMAND_MEMORY, PCI_COMMAND_MASTER), the behaviour of real hardware from memory (see the unverified box above).

The compute itself happens inside the device: the driver's write starts it, the device sets the busy bit, and clears it when the result register holds the answer. The F4-16 trace showed the busy bit set right after the write and clear one to several reads later; F4-18's model records that the result register reads N while busy, as observed. R6

Where the analogy breaks


    

  • A visitor who leaves is gone; a device that leaves may keep "answering". The empty chair in the story is silent. A device whose decoding is off still produces values when read: 0 in QEMU, all ones on real PCI Express. A driver must tell "answer" from "noise that looks like an answer". R3
    • 

  • A plan can be vague; a register table cannot. "Meet the visitor at the gate" is enough for people. A design note must say which offset, which width, which bit, and where each fact came from. C1
    • 

  • Plans are agreed once. A design note changes every time evidence contradicts it, as the error-handling row did in this chapter; the change and its evidence go into the note. R4

Forensic lab answer key


Observation. compute(0) to compute(3) are correct. After "fault injection: memory decoding switched off", compute(4) to compute(14) all return 0 and are flagged "DIFFERS"; 11 problems; exit code 35. The final dump shows "id=0x00000000 status=0x00000000" and "polls 15" for 15 computations, against 27312 polls in the normal run of the saved build (poll totals vary from run to run with emulator timing; after decoding is switched off every status read returns 0, "not busy", so each computation costs one poll).


Root cause. With decoding off, every read of the BAR returns 0 in this emulator. STATUS = 0 means "not busy" to the loop, so it exits immediately (hence the low poll count and no timeout) and reads the "result", 0. The version-1 error rule tested only for all ones, the value the curriculum gives for surprise removal on PCI Express, so it never fired. The ID register, which can never legitimately read 0, shows the truth.


Fix and verification. After each computation, re-read the ID and treat any value other than the observed one as gone (lines 70–74 of edu4.cc without F417_V1). This works whether the platform returns all ones (≠ ID) or zeros (≠ ID). Verification: the removal run stops at compute(4) with "device gone", "gone 1", one problem (R2). Update the note's error-handling row with the evidence (done in design_note.txt).


Wrong answers and why. "The device computed 0": 4! is 24, and the ID read 0 too. "A timeout is too long": no timeout was involved, the loop exited at once. "Add a delay before reading the result": the device is not answering; delays change nothing.
