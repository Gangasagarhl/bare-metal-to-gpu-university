Story hook

Reception has filled in the visitor card. Now someone must understand the visitor. The office has a rule for where to look, always in the same order. First: does the visitor speak a language the school already teaches? Then any French teacher can help, and there is a printed phrasebook. If not: did the visitor's own school send a letter explaining their customs? If not: is there a teacher somewhere who once worked with a visitor from that school and wrote notes? If not: is there anyone at all who can talk with the visitor, so that the office can listen in and learn? And sometimes the honest answer is: this visitor speaks only through a sealed envelope that nobody is allowed to open.

A new office assistant skipped the order. A visitor arrived, the assistant found an old notebook in a drawer with some phrases that seemed to work, and spent a week learning from it. On Friday the head of languages walked past, glanced at the visitor's badge and said: "Her school publishes a full guide for visitors. It is on the shelf behind you."

Stage (b) of the universal method is that office rule. The order is fixed because the cheapest, most reliable source is checked first, and because the place where you stop decides how much work the driver will be. This chapter turns the rule into a procedure your tools can run, and ends with an unknown device where the shelf behind you matters.

What you will be able to do

  • Search for documentation in the curriculum's fixed order: class standard, vendor documents, Linux driver and binding, BSD drivers, vendor SDKs, everything else.
  • Assign each device one of the six tiers and say what it implies for effort, risk and your plan.
  • Recognise a class match from a PCI class code, a USB interface class or an ACPI compatible ID, and know when a class match is only a start (quirks).
  • Read what a boot trace, Windows hardware IDs and an INF file tell you about a device and its driver.
  • Apply the licence and NDA rules: never use NDA or leaked material; record where every piece of knowledge came from.
  • Produce the device record and tier for an unknown device from a hardware-ID list, an INF excerpt and a boot trace.
Jargon box
Documentation tier
Simple words: a number from 1 to 6 saying how much is known about programming a device, and where it comes from. Analogy: phrasebook, letter from the visitor's school, a colleague's notes, nobody, a sealed envelope. Precise: the curriculum's table 5.2: 1 open class standard, 2 public vendor documentation, 3 documentation only under NDA, 4 open driver only, 5 only a closed driver, 6 locked. C1
Class driver
Simple words: one driver that works for every device following a published standard. Analogy: a French teacher who can help any French-speaking visitor. Precise: a driver bound by class code, interface class or compatible ID rather than by vendor and device ID, for example NVMe (PCI class 01 08 02) or USB HID (interface class 03); vendor-specific differences are handled as quirks. C1 R1
Quirk
Simple words: a known difference between what a device should do and what it does, with its workaround. Analogy: "this visitor nods when they mean no". Precise: a table entry keyed by IDs, subsystem IDs, revision or firmware version (or SMBIOS strings for whole machines) that changes driver behaviour for that device; the runbook asks for evidence with every entry. C1
Errata document
Simple words: the vendor's list of known mistakes in a chip. Analogy: the visitor's school writing "our guide is wrong on page 12". Precise: a document published per chip and stepping (Intel "specification update", Arm "Software Developer Errata Notice", NXP "chip errata"); read with the datasheet. C1
NDA documentation
Simple words: documents you may only read after signing a secrecy contract. Analogy: a letter marked "for staff of the partner school only". Precise: tier 3; for an individual it is the same as tier 4, and the runbook forbids using NDA or leaked material even when the learner has it. C1
INF file
Simple words: the text file that tells Windows which devices a driver package serves. Analogy: an interpreter's business card listing every language they speak. Precise: a driver package's setup information file: its models section lists every hardware ID the package supports, and it names the service (.sys) it installs, registry parameters and often firmware files. C1
Boot trace
Simple words: a time-stamped log of what started during boot, including which driver took which device. Analogy: the morning register of which interpreter met which visitor, and when. Precise: in the curriculum, a Windows performance trace whose driver-load events give .sys names, order and timing; in this lab, the kernel's own log with a time-stamp-counter value per line. C1 R1

The idea in pictures

Layer 1 — the kid explanation

When you find a part you do not know, you look for its instructions, and you always look in the same order. First you check whether it is a common kind of part with a public rulebook everyone uses. Then whether the company that made it wrote instructions. Then whether someone else wrote a program for it that you can read. If nobody wrote anything and you cannot read anyone's program, you can still watch a program that works with the part and take notes. And sometimes the part is locked, and the right thing is to write "locked" and choose another part. You give each part a number from 1 to 6 for how easy it will be, and you never use secret papers someone was not allowed to give you.

Layer 2 — the student explanation

The curriculum fixes the search order. C1

  1. An open standard for the device's class. If the PCI class code, USB interface class or ACPI _CID says the device follows a standard, a class driver works and the vendor's own documents are needed only for quirks. The curriculum's examples: PCI 01 08 02 NVMe, 01 06 01 AHCI, 0C 03 30 xHCI (20 EHCI, 10 OHCI, 00 UHCI), 04 03 HD Audio; vendor 1AF4 marks virtio; USB interface classes 03 HID, 08 mass storage, 02 and 0A communications, 01 audio, 0E video, 09 hub, 0B smart card, E0 Bluetooth, FF vendor-specific.
  2. The vendor's public documents: datasheet, programmer's reference manual (PRM), technical reference manual (TRM) for SoCs, application notes, and the errata document.
  3. The Linux driver and its devicetree binding, read as executable documentation, with its git history and mailing-list discussions.
  4. BSD drivers, often smaller and under permissive licences.
  5. Vendor SDKs, board-support packages and reference code; register headers are the most valuable part.
  6. Everything else: community wikis, other open systems, and QEMU's device model if QEMU emulates the device ("useful, but second-hand").

Where the search stops gives the tier, and the tier gives the plan: tier 1 means "write the class driver once, collect quirks"; tier 2 "follow the datasheet's initialization chapter, keep the errata at hand"; tier 3 "for you, the same as tier 4"; tier 4 "read the drivers, write your own specification, implement from it"; tier 5 "stage (c) observation; publish your specification, not their code"; tier 6 "record it as unsupported, with the reason, and move on". C1

The lab runs this as a procedure. The kernel's boot log binds every PCI function it can by exact ID, then vendor, then class, and says "NO DRIVER" for the rest: two functions on the lab machine, 00:02.0 (1234:11e8) and 00:1f.3 (the SMBus controller). R1 A second program reads one record per device with what you found in each step and prints the tier; it refuses to give a tier when a step has not been searched. R3

Layer 3 — the engineer's depth

A class match is a start, not an end

A class code is a promise the vendor makes: "this function follows that standard". Drivers trust it because the alternative, one driver per chip, does not scale. But the promise has edges. A standard has optional features and versions; the device may implement them badly; and a class code can be generic (00 ff 00, "unclassified", for both the virtio RNG and the edu device in our lab) or even vendor-defined (the build VM's virtio balloon reports class ff ff 00). R1 R5 That is why the match table of Listing 1 tries the exact ID first, then the vendor, then the class: the most specific knowledge wins, and quirks attach to IDs. The virtio RNG shows the vendor rule doing work the class could not: its class says nothing, its vendor 1AF4 says "virtio". R1

Two lists of six

The curriculum describes the six outcomes twice, and the two lists are not in the same order. The introduction to section 5 lists: (1) open class standard, (2) vendor publishes documentation, (3) only open-source drivers, (4) nothing public but a working driver to observe, (5) depends on signed vendor firmware, (6) locked. The tier table of 5.2 lists: (1) class standard, (2) public vendor documentation, (3) NDA only, (4) open driver only, (5) only a closed driver, (6) locked. C1 This course uses the table's numbering everywhere, because M1's acceptance test says "a tier from 5.2". The first list's "signed vendor firmware" outcome has no number of its own in the table; this course records it as tier 6 when the firmware's host interface is undocumented and the firmware cannot lawfully be loaded, and otherwise by the tier of that host interface's documentation (often 2 or 4). The owner has been asked to settle this (NOTES.md).

What Windows already knows

On a machine with Windows, Device Manager's Details tab shows the device's "Hardware Ids", "Compatible Ids", "Inf name" and "Matching device Id"; the matching ID says which ID the installed driver claimed, and "a class-code match means a class driver is in use". The INF file lists every hardware ID the package supports; sibling IDs show which chips share one programming model; the service name connects to the .sys file in the boot trace. C1 None of this is a programming document. It answers "which driver, from whom, for which family", which tells you where to search in steps 2–5.

Not verified — check before relying on this

The forensic exhibit's list of Windows hardware and compatible IDs is formatted by mk_evidence.py from the device's real IDs, following the forms the curriculum gives (PCI\VEN_xxxx&DEV_xxxx&SUBSYS_xxxxxxxx&REV_xx and PCI\CC_xxxxxx). The full list of forms and their order (most specific first) were written from memory of Microsoft's documentation on PCI identifier strings, which was not opened in this build, and no Windows machine was available to compare. The INF excerpt is constructed for the lab and is not any vendor's file; its section names follow the general INF layout as remembered, also unchecked.

Licences, NDAs and the record of where knowledge came from

Reading GPL-licensed code to understand hardware is normal practice; copying it brings the GPL's obligations into your project. NDA material is out: the runbook forbids it even when the learner has it, and asks the learner to confirm the origin of any document that is not obviously public. Every fact in a design note carries its source (F4-17 enforces this per register). C1

What you can find without a network

This build had no network. What it did have is instructive: the ID databases (pci.ids 2024.03.31, usb.ids 2024.03.18, pnp.ids), the Linux user-space headers with register and protocol names (pci_regs.h, serial_reg.h, virtio_pci.h, hid.h, i2c.h and others), and the QEMU packages, whose documentation folder holds only a copyright file and a changelog. R4 The headers are a genuine step-3 source (they are part of Linux), and the earlier chapters used them for every register offset they could. The emulator's own description of a device is a step-6 source, available here through the monitor's info qtree. R6

How the hardware actually does it

Documentation tiers are about people, but binding is about hardware fields. A class driver can bind only because the device carries a class code in read-only configuration space, set by the vendor at manufacture (or by firmware on some SoCs and chipsets that can change it, for example a SATA controller switching between IDE, AHCI and RAID modes, where the programming interface byte changes with the mode). The class code in our lab's AHCI controller, 01 06 01, is exactly the curriculum's example, and the match table binds it. R1 C1

Not verified — check before relying on this

The statement that firmware can change a SATA controller's programming interface (IDE, AHCI and RAID modes with different class bytes) is from memory and was not observed in this build; QEMU's ICH9 AHCI function has a fixed class. Check a chipset datasheet (tier 2 for Intel PCH SATA) before relying on it.

USB works the same way one level down: a device can have several interfaces, each with its own class, so a webcam with a microphone binds the video class driver to one interface and the audio class driver to another. ACPI's _CID does the job for platform devices: PNP0C50 says "HID over I2C", whatever the _HID. C1

Worked example

Task. Assign tiers to the e1000 (00:01.0) and the SMBus controller (00:1f.3) of the lab machine.

  1. e1000, 8086:100e, class 02 00 00. Step 1: Ethernet controllers on PCI have no class standard (the curriculum says so in worked example 1), and class 02 00 00 is in no row of the standards table. Step 2: Intel publishes the 8254x Software Developer's Manual (catalog row "Ethernet: Intel controllers": public). Stop: tier 2. First document: the SDM and its specification update. C1 R3
  2. SMBus, 8086:2930, class 0c 05 00. Step 1: SMBus is a bus standard, but the controller's register interface is not standardized by a class code (the curriculum lists none for 0c 05). Step 2: the catalog says "the Intel PCH SMBus controller is described in the PCH datasheets": tier 2. C1 Plan: datasheet. Safety note for the record: SPD EEPROMs sit on this bus; read-only.
  3. Check with the tool. tier.out prints "tier 2: the vendor publishes documentation" for both. R3

Check. Neither device was bound in the boot trace (the e1000 was, by ID; the SMBus controller was not), but binding and tier are separate questions: tier says how to learn to drive it, binding says whether this kernel already does. R1

Where the analogy breaks


    

  • A phrasebook does not lie. A class standard can be implemented badly; tier 1 still needs quirks, and they are keyed by IDs, subsystem IDs and revisions you recorded in F4-14. C1
    • 

  • Listening in is not always allowed. Watching an interpreter at work is harmless at school. Observing a closed driver touches licences and local law; F4-16 starts with that note, and the runbook requires the learner's confirmation first. C1
    • 

  • Notes from a colleague can be copyrighted. An open driver is "executable documentation", but its code carries a licence; you write your understanding in your own words. C1
