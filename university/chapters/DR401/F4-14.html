Story hook

A school's reception desk receives visitors all day. Before anyone calls an interpreter, the receptionist does one thing for every visitor: fills in a visitor card. Name, who sent them, which language they speak, which document proved it. Some visitors hand over a passport with a number printed by a government. Some carry a badge from their own school. A delegation of six arrives together and the group leader signs in for everyone, so the card must say "group of six", not "one visitor". And a few visitors carry no papers at all: the only way to know who they are is the guest list the head teacher wrote the week before.

One Monday a new receptionist decides that the group leader's card is enough. Nobody notices for a week, until a parent asks why her daughter, the fourth member of a visiting choir, has no record of ever entering the building. The building was full of people the office did not know about. Every later decision (which interpreter, which room, who is still inside when the fire alarm rings) was made from a list that was wrong at the first step.

A kernel meets hardware the same way. Before any driver is chosen, every device must be identified: read its identifiers, write them down exactly, and find what they mean. This chapter teaches that first stage of the universal method for every kind of bus you will meet, on three machines you can run today, and shows what happens when the sign-in sheet skips the fourth member of the choir.

What you will be able to do

  • List what identifies a device on PCI and PCI Express, USB, ACPI, devicetree, x86 CPUs and the machine as a whole, and say who assigns each identifier.
  • Read a PCI function's vendor, device, subsystem, revision and 3-byte class code with configuration mechanism #1, and find multi-function devices correctly.
  • Find the hardware IDs and compatible IDs an ACPI DSDT declares without an AML interpreter, and the compatible strings of a devicetree blob.
  • Name each device from the local ID databases (pci.ids, pnp.ids), and say plainly when a database does not know it.
  • Check your kernel's device list against an independent list (the emulator's own, or Linux's) and treat any difference as a bug until explained.
  • Open a device record (runbook 19.5) with every identifier written exactly as read.
  • Diagnose a device report that silently misses devices.
Jargon box
Device record
Simple words: the card you fill in for one device before writing any driver code. Analogy: the visitor card at reception. Precise: a design-log entry with the fields identification, class and catalog row, documentation tier, documents found, observation needed, design note, test plan and status; the runbook forbids driver code for a device without one. C1
Vendor ID and Device ID
Simple words: two numbers every PCI device answers with: who made it, and which product it is. Analogy: the country on a passport and the passport number. Precise: 16-bit fields at configuration offsets 0x00 and 0x02; vendor IDs are assigned by PCI-SIG to members, device IDs are chosen by the vendor; a read of 0xFFFF from the vendor field means no function answered. C1 L3 D2
Subsystem ID
Simple words: a second pair of numbers naming the board or laptop maker's variant of a chip. Analogy: the school badge a visitor wears in addition to the passport. Precise: Subsystem Vendor ID and Subsystem ID at offsets 0x2C and 0x2E of a type-0 header; quirks and firmware choices are often keyed on them. C1 L3
Class code
Simple words: three bytes saying what kind of device this is, independent of who made it. Analogy: "this visitor speaks French" rather than "this visitor is Ms Dupont". Precise: base class, subclass and programming interface in configuration bits 31:8 of offset 0x08, defined by the PCI Code and ID Assignment Specification; for example 01 08 02 is an NVMe controller. C1 D1
Multi-function device
Simple words: one PCI device slot that contains several separate functions, each with its own IDs. Analogy: the delegation that signs in as a group. Precise: a device whose function 0 has bit 7 of the header-type register set; functions 1–7 must then be probed too. L3 R5
Hardware ID (_HID) and compatible ID (_CID)
Simple words: the names firmware gives devices that cannot announce themselves. Analogy: the head teacher's guest list. Precise: ACPI objects in the device's namespace scope: _HID names the device (a PNP ID such as PNP0501 or an ACPI ID such as ACPI0013), _CID lists IDs of standards it is compatible with. C1 D3
Compatible string
Simple words: the devicetree's way of naming a device, as text. Analogy: a list of languages, the best-spoken first. Precise: the compatible property, a list of "vendor,device" strings, most specific first; a driver binds to the first entry it knows. C1 D4
ID database
Simple words: a file that turns numbers into names. Analogy: the directory of countries and schools at reception. Precise: community-maintained lists such as pci.ids (used by lspci) and usb.ids, and the registry of PNP and ACPI vendor prefixes (pnp.ids locally); they are a lookup aid, not a specification. L1 L2

The idea in pictures

Layer 1 — the kid explanation

Every part inside a computer has a name tag, but the name tags are written in different ways. Some parts shout two numbers when you ask: "I am maker 8086, product 100E". Some parts never say anything, and the only way to know they are there is a list that the computer's firmware wrote down when the computer was built. Before you can talk to a part, you walk around the whole machine and write every name tag down on a card, exactly, even the ones you do not understand yet. Then you look the numbers up in a big directory. If the directory says "unknown", you write "unknown" on the card. You never guess, and you never skip a part because it stands next to one you already wrote down.

Layer 2 — the student explanation

The curriculum's table 5.1 lists what identifies a device on each kind of bus and who assigns each identifier. C1 Four families matter most on a PC and on boards:

  • Self-describing buses. PCI, PCI Express and USB devices answer questions about themselves. A PCI function has a 256-byte configuration space (4096 bytes on PCI Express) that starts with the vendor ID, device ID, command and status registers, the revision and class code, and the header type. L3 A USB device sends descriptors with a vendor ID (VID), product ID (PID), device class and per-interface classes. C1
  • Firmware-described devices. On a PC, the serial ports, the PS/2 controller, the battery, the touchpad and many more are not on a bus that can enumerate; the ACPI tables name them with _HID and _CID objects and list their resources in _CRS. On Arm and RISC-V boards the same job is done by the devicetree's compatible property. C1
  • The CPU itself. On x86 the CPUID instruction gives a vendor string, family, model and stepping, and a bit saying whether you run under a hypervisor. R6
  • The machine as a whole. SMBIOS tables name the maker, product and firmware version. Linux and Windows key their quirk tables on these strings. You will read them in F4-20. C1

Two rules make the method reliable. First, record every identifier exactly as read, including the ones that look unimportant (revision, subsystem): the runbook says so, and later chapters will show why. C1 Second, never trust your own list until it agrees with an independent one. In this chapter's lab the kernel's PCI list is compared, field by field, with the list QEMU itself reports for the machine it emulates, and the Linux view of the build machine is compared with the bytes of its own DSDT. R2 R4

Names come last. The ID databases turn numbers into names, but they are community lists, not specifications: they can be out of date or silent. The lab shows both cases: the build machine's host bridge, device 8086:0d57, is not in the installed pci.ids, and neither is the emulated device 1234:11e8. R3 R4 "Not in the database" is a fact for the device record, not a reason to stop.

Layer 3 — the engineer's depth

PCI: the whole identity, and the trap of function 0

A PCI function's identity is seven numbers: vendor, device, subsystem vendor, subsystem, revision, and the three class bytes. The class code answers "which standard might apply" (stage b, F4-15); vendor and device answer "which exact chip"; the subsystem pair answers "whose board"; the revision answers "which stepping", which is where errata live. C1 Our kernel reads all seven with the offsets of Linux's user-space header <linux/pci_regs.h> rather than numbers typed from memory. L3

Enumeration walks bus, device and function. A device (slot) can hold up to eight functions; the header-type register of function 0 has bit 7 set when the others exist (the header defines it as PCI_HEADER_TYPE_MFD). L3 On the emulated q35 machine, slot 0x1f is such a device: function 0 is the LPC bridge (8086:2918), function 2 the AHCI SATA controller (8086:2922), function 3 the SMBus controller (8086:2930), and their header-type byte reads 0x80. R1 A report that stops after function 0 loses the disk controller and the SMBus controller. That is this chapter's forensic case.

Base address registers (BARs) are part of identification too: the size of BAR0 is a fingerprint (the edu device's BAR0 is 1 MiB, the e1000's 128 KiB in our run) and the design note of F4-17 needs it. Sizing a BAR means writing all ones and reading back which bits stick; our kernel switches decoding off in the command register while it does so, so the device never answers at a half-written address. R1 L3

ACPI: IDs inside bytecode

The DSDT is not a table of devices but a program in AML bytecode, which an OS normally runs with an interpreter (milestone C10). For identification you can do without: Name(_HID, …) compiles to a NameOp byte followed by the four-character name and a value, which is either a 32-bit compressed EISA ID or a string. A byte-pattern scan finds most IDs; IDs computed by methods (rare for _HID, more common for _CID packages) need the interpreter, and the scanner says so instead of guessing. D3 R4

Two ID shapes exist: a PNP ID is three letters and four hexadecimal digits (PNP0501, the 16550-compatible serial port); an ACPI ID is four letters or digits and four hexadecimal digits (ACPI0013). The vendor prefix of a PNP ID can be looked up in the local pnp.ids file; four-character ACPI prefixes are in the UEFI Forum's registry, which this build could not open. Linux also creates IDs of its own (LNXSYSTM for the namespace root, LNXSYBUS for \_SB_ and \_TZ_) that appear in no table, and the lab's comparison flags them as "not in the DSDT". R4 L2

Not verified — check before relying on this

The AML encodings used by acpi_ids.cpp (NameOp 0x08, DWordPrefix 0x0C, StringPrefix 0x0D), the EISA ID compression (three 5-bit letters, then four hexadecimal digits) and the two ID shapes were written from memory of the ACPI Specification (D3), which was not opened in this build. They are cross-checked, not proven: on the build machine every _HID that Linux lists and that is not a Linux-made ID was found by the scanner with the same spelling (R4), and on QEMU's own DSDT the scanner finds the IDs the curriculum names for the same devices (PNP0501, PNP0303, PNP0A08). An ID shape that is legal but rare would not have been exercised. Check against D3 before relying on the scanner for a real machine.

Devicetree: one blob, many names

A devicetree blob (DTB) is a flattened tree of nodes with properties. Identification reads compatible (most specific first), then reg and interrupts for the resources. Boards repeat devices: QEMU's AArch64 virt machine has 32 virtio,mmio transport nodes, and a report that prints all of them hides the interesting ten. The lab's parser groups alike nodes and prints 56 nodes, 48 with a compatible property. R5

The CPU is whatever the machine presents

The same container produced two CPU identities in this build. The Linux host reports "GenuineIntel", family 6, model 207, with the hypervisor bit set and the hypervisor signature "KVMKVMKVM". The lab kernel running under QEMU with TCG on that same host reports "AuthenticAMD", family 0x0f, model 0x6b: QEMU's default emulated CPU model, not the host's. R6 R1 CPU identification identifies the CPU the software sees; on a virtual machine that is a configuration choice of the hypervisor.

Buses that cannot identify

I2C devices have only a 7-bit address, SPI devices nothing; HD Audio codecs, Ethernet PHYs and SPI NOR flash have ID registers you read with the bus's own commands. C1 For them, identification comes from the platform description (an ACPI I2cSerialBusV2 resource, a devicetree child node) or from the schematic. F4-21's touchpad is the canonical case: the ACPI device with compatible ID PNP0C50 tells you that a HID-over-I2C device exists, and its resources say at which address and interrupt. C1

How the hardware actually does it

PCI configuration mechanism #1. On a PC, the CPU writes a 32-bit address to I/O port 0xCF8 (enable bit 31, bus in bits 23:16, device 15:11, function 10:8, register 7:2) and reads or writes the data at port 0xCFC. The host bridge turns this into a configuration transaction on the bus. When no function exists at an address, the read completes with all ones, so a vendor ID of 0xFFFF means "nobody there". D2 PCI Express adds a memory-mapped way to reach the same space (ECAM), whose base is in the ACPI MCFG table; our report lists an MCFG table on q35. R1

Not verified — check before relying on this

The CONFIG_ADDRESS bit layout and the "all ones when absent" rule above are from memory of the PCI Local Bus Specification (D2, not opened). The lab checks them indirectly: a kernel built on them produced a list of 10 functions identical, field by field, to QEMU's own list (R2). That proves the layout is right as QEMU implements it; real chipsets were not tested.

ACPI tables in memory. Firmware leaves a Root System Description Pointer (RSDP, signature "RSD PTR ") in the BIOS area; it points to the RSDT, which lists the other tables, among them the FADT (signature FACP), which points to the DSDT. Every table carries a checksum: all its bytes sum to zero modulo 256. Our kernel checks every one before trusting it. R1 D3 (The RSDP scan ranges and the FADT offset of the DSDT pointer are from memory, in the same unverified state; the checksums passing on every table is the cross-check.)

The devicetree blob starts with a header (magic number, total size, offsets of the structure and strings blocks, version) and then a stream of 32-bit big-endian tokens: begin node, property, end node, end. The lab dumps QEMU's own DTB for the virt machine with -machine dumpdtb=… and walks it; the walk "ended cleanly on END". R5 D4

Worked example

Task. Open the device record for the function at 00:02.0 of the lab's q35 machine.

  1. Read the kernel's line. "pci 00:02.0 id 1234:11e8 sub 1af4:1100 rev 10 class 00 ff 00 hdr 00", then "bar0 mem32 base 0xfea00000 size 0x00100000". R1
  2. Check it independently. QEMU's own list has the same IDs, subsystem, class and BAR size for 00:02.0: "match". R2
  3. Look up the name. pci.ids (version 2024.03.31, 2378 vendors) has no vendor 1234 and therefore no device 11e8: "(vendor 1234 not in pci.ids)". R3
  4. Read the class. 00 ff 00 is "Unclassified device" in the same file: the class code promises no standard. R3
  5. Write the record. Identification: PCI 1234:11e8, subsystem 1af4:1100, revision 0x10, class 00 ff 00, header type 0 (single function), BAR0 32-bit memory, 1 MiB. Class and catalog row: none matches (F4-19 confirms: "unclassified"). Tier: not yet known (F4-15). Name: unknown in pci.ids.

Check. Every field came from a run and was confirmed by a second, independent view. Nothing in the record is a guess. The F4-15 forensic lab continues from exactly this record.

Where the analogy breaks


    

  • One passport office versus many. A visitor's passport number comes from one government. A PCI device's vendor ID comes from PCI-SIG, its device ID from the vendor, its class from a specification, its name from a community database that may not know it at all (1234:11e8, 8086:0d57 in this build). C1 R3
    • 

  • Visitors do not change passports depending on who asks. A CPU does: the same host presented itself as GenuineIntel to Linux and as AuthenticAMD to the emulated machine running on it. Under virtualization, identity is configuration. R6 R1
    • 

  • The guest list is code. A head teacher's list is plain text. ACPI's list is bytecode: an ID can be computed by a method, and only an interpreter can say what it is. The scanner of Listing 4 reports such cases instead of guessing. D3

Answers to Check yourself


    

  1. Vendor ID, device ID, subsystem vendor ID, subsystem ID, revision ID, and the class code's three bytes (base class, subclass, programming interface). The class code answers "which standard might apply".
    2. 

  2. A configuration read to an address where no function exists completes with all ones, so 0xFFFF in the vendor field is "nobody answered". Treating it as a vendor would create phantom devices at every empty address, 32 per bus.
    3. 

  3. Only a device with several functions sets the multi-function bit; probing functions 1–7 of other devices wastes time and, on devices that ignore the function number, produces seven ghost copies. Probing only function 0 of a multi-function device loses real functions (the forensic case).
    4. 

  4. As a compressed EISA ID (DWord) or as a string. The scanner cannot find an ID returned by a method or built at run time, or one inside a package (several _CIDs), unless the pattern happens to match.
    5. 

  5. "ELAN0001" is an ACPI ID shape (four characters, four hex digits); it names the specific device, and its prefix is in the UEFI Forum's PNP ID and ACPI ID registry. "PNP0C50" is a PNP ID; it says the device is compatible with HID over I2C, so a class driver can bind (F4-21); its prefix PNP is in pnp.ids.
    6. 

  6. "AuthenticAMD", family 0x0f, model 0x6b: the record describes the q35 machine as its software sees it. The host's identity belongs in the record of the build machine. Both should note "virtual: configured by the hypervisor".
    7. 

  7. Nine functions; QEMU's list also has nine, and the comparison prints "identical" (checked in this build: "9 functions in QEMU's list, 9 in the kernel's report: identical"). Both views lose the device together, which is why an independent list checks enumeration, not completeness of your configuration. The slot numbers of the devices added after it shift down by one.
    8. 

  8. Because the IDs themselves are the identity; the database is a community convenience that lags behind hardware. The record says "unknown in pci.ids version X", and stage (b) continues from the IDs and class.
    9. 

  9. I2C (address only) and SPI (nothing). The identification comes from the platform description (ACPI I2cSerialBusV2 resources, devicetree child nodes) or from the schematic; some chips have an ID register you can read once you know the address.

Forensic lab answer key


Observation. The report lists 8 functions; QEMU lists 10. Missing: 00:1f.2 (8086:2922, class 01 06, the AHCI controller) and 00:1f.3 (8086:2930, class 0c 05, the SMBus controller). Both are functions 2 and 3 of slot 0x1f. The report's line for 00:1f.0 shows "hdr 80": bit 7 of the header type, the multi-function bit, is set.


Root cause. pci4.cc line 68, active under F414_FUNC0_ONLY, continues to the next slot right after function 0. The idea "function 0 is the device" is true for single-function devices, which are the majority of slots in the test machine, so the bug is invisible except on multi-function devices.


Why no error. A missing function is not a failure from the kernel's point of view: nothing it read was wrong. Storage and SMBus drivers never saw a device to bind. Only an independent list shows the absence.


Fix and verification. Remove the early continue; probe functions 1–7 when PCI_HEADER_TYPE_MFD is set (lines 70–77). Verification: the normal build's report has 10 functions and qmp_compare.out says "identical" (R1, R2). Test to keep: compare.py in the harness, failing the build on any difference.


Wrong answers and why. "The AHCI controller is broken": QEMU lists it, so it exists. "The kernel needs ECAM to see functions above 0": mechanism #1 reaches all eight functions (the normal build finds them). "A driver match problem": matching happens after enumeration, and the functions are not in the list at all.
