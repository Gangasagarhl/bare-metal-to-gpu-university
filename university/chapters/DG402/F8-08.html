Story hook

In the chain of kitchen halls, the delivery vans load only at the loading dock behind each hall. The ingredients, though, live in the pantry deep inside, where the cooks work. For years every hall did the same dance: a helper carried the crate from the pantry to the dock, the van drove it to the next hall, and a helper there carried it from the dock into that hall's pantry.

Then the delivery company announced a new crew: they recognise pantry crates and fetch them themselves, sometimes straight from pantry to pantry. Halls that had signed up for the new crew found their deliveries much quicker. One hall, run by Ingrid, signed the same contract but saw no change at all. Her deliveries arrived intact and on time by the old schedule, every single one. Only when someone compared her delivery times with the time of "walk to the dock, drive, walk from the dock" did the truth come out: her contract had never been activated, and her helpers were still carrying every crate by hand, quietly and correctly.

Correct but slow is the hardest kind of bug to see. This chapter teaches you how to ask an MPI library whether it can take GPU memory directly, how to stage correctly when it cannot, and how to read the logs that tell you which one actually happened.

What you will be able to do

  • Explain what a GPU-aware (CUDA-aware or ROCm-aware) MPI library does with a device pointer, and the three paths a GPU buffer can take between ranks.
  • Query an MPI library for GPU support at compile time and at run time, and read its build configuration (ompi_info, the transport modules installed).
  • Write a halo exchange with device buffers that uses device pointers when the library supports them and stages correctly through pinned host memory when it does not.
  • Measure the cost of staging with a latency and bandwidth benchmark, and predict it with the alpha-beta model.
  • Diagnose the course forensic case "Staging through host memory": find, from benchmark results and logs, that the library was built without GPU support.
Jargon box
GPU-aware MPI (CUDA-aware, ROCm-aware)
Simple words: an MPI library that accepts the address of GPU memory in its send and receive calls and moves the data itself. Analogy: the delivery crew that recognises pantry crates and fetches them. Precise: an MPI implementation that detects device pointers passed as buffers (for NVIDIA GPUs through CUDA's unified virtual addressing and pointer-attribute queries) and moves the data with GPU-capable transports: peer copies or inter-process handles inside a node, GPUDirect RDMA or pipelined staging between nodes. Support is a build-time property of the library (and of its transport layer). The MPI Standard itself does not mention GPUs. D2 D5 C1
Host staging
Simple words: copying GPU data into ordinary computer memory, sending that, and copying it back into the other GPU. Analogy: carrying the crate from the pantry to the loading dock and back in at the other end. Precise: a device-to-host copy into a (preferably pinned) host buffer, a host-to-host MPI transfer, and a host-to-device copy at the receiver; done by the application when the library is not GPU-aware, or by the library internally (often in pipelined chunks) when no direct GPU path exists. C1 D2
Unified virtual addressing (UVA)
Simple words: host and GPU memory share one range of addresses, so a pointer alone tells you where the memory is. Analogy: every crate in every room has a unique shelf number, so the crew knows from the number whether it is in the pantry or on the dock. Precise: a CUDA feature in which host and device allocations of a process occupy one virtual address space; cudaPointerGetAttributes returns a cudaPointerAttributes whose type is one of cudaMemoryTypeUnregistered, cudaMemoryTypeHost, cudaMemoryTypeDevice or cudaMemoryTypeManaged (enum in the installed driver_types.h). H2 D5
MCA parameter (Open MPI)
Simple words: a named setting of Open MPI that you can read and change without recompiling. Analogy: a switch on the delivery company's control panel. Precise: a parameter of Open MPI's Modular Component Architecture, set with mpirun --mca <name> <value> or the environment, and listed with its value, source and help text by ompi_info; read-only parameters such as mpi_built_with_cuda_support report how the library was built. D2 R2
UCX (Unified Communication X)
Simple words: a communication library that many MPI libraries use underneath to reach the network and the GPUs. Analogy: the company that owns the vans and the road permits, hired by the delivery service. Precise: an open-source communication framework with transports for shared memory, TCP, InfiniBand/RoCE verbs and GPU memory, loaded as modules; Open MPI can use it as its point-to-point layer (this build was configured --with-ucx, R2). D4 R2
OSU Micro-Benchmarks
Simple words: a standard set of small MPI test programs that measure latency and bandwidth between ranks. Analogy: timing a test parcel of each size between two halls. Precise: a benchmark suite from Ohio State University (curriculum reading-list item 83) whose point-to-point and collective tests can place buffers in host or device memory; milestone F4 asks for their device-buffer results "logged next to host-buffer results". D3 C1

Layer 1 — the kid explanation

Inside each kitchen hall, the food is in the pantry, and the vans only load at the dock. If the delivery crew does not know about pantries, a helper must carry each crate out to the dock first, and another helper carries it back in at the other end. That works, but it adds two walks to every delivery.

A smarter crew knows what a pantry crate looks like. You hand them the pantry shelf number, and they work out the fastest way: straight across a corridor to a pantry in the same building, or with a special van that can load right inside the pantry.

The catch is that you must know which crew you hired. If you hand a pantry shelf number to the old crew, they go to the dock, find nothing there, and get confused. So before you hand over a pantry number, you ask: "are you the smart crew?" If not, you carry the crate to the dock yourself.

Layer 2 — the student explanation

What "GPU-aware" means

MPI calls take a buffer address. Without GPU support, the library assumes that address is host memory and lets the CPU read or write it, through memcpy, through the kernel's socket calls or through a network card registration. A device pointer from cudaMalloc is not host memory, so passing it to such a library is an error, and what happens next depends on the code path. D2 D5 A GPU-aware library checks each buffer: with CUDA's unified virtual addressing, the pointer's value alone identifies host or device memory, and the runtime call cudaPointerGetAttributes reports which (the installed header lists the memory types). H2 For device memory it uses a path that can reach the GPU (Figure 1, B and C). D2 The MPI Standard does not define any of this; it is an implementation feature, so you must ask the library you have. D1

Asking Open MPI

Open MPI answers in three places, and this build gives the same answer in all three (Listing 1 and the build report):

  • Compile time. The header mpi-ext.h includes Open MPI's "cuda" extension, whose generated header defines MPIX_CUDA_AWARE_SUPPORT. In this installation the line reads #define MPIX_CUDA_AWARE_SUPPORT 0. H1
  • Run time. The same header declares int MPIX_Query_cuda_support(void); Listing 1 prints its value, 0 (R1). H1 R1 The run-time answer matters because one compiled program may meet a different library at run time (a container image, a module system).
  • Build report. ompi_info lists the read-only parameters mpi_built_with_cuda_support and opal_built_with_cuda_support, both false, with the help text "Whether CUDA GPU buffer support is built into library or not", and the full configure command line (R2). R2

Staging correctly


When the library is not GPU-aware, the application stages (Figure 1, A): copy the outgoing data from the device into a host buffer, call MPI on the host buffer, copy the received data back into device memory. Listing 3 does this for the halo exchange of F8-07 with three rules: D5


    

  1. Use pinned host memory for the staging buffers (cudaMallocHost). Pageable memory forces the driver to copy through its own pinned staging area first (the installed CUDA header says pageable copies use "staging memory for DMA transfer", as quoted in the glossary entry from F1-62), adding a hidden third copy. H2
    2. 

  2. Order the work. The kernel that produced the boundary cells must have finished before the device-to-host copy, and the host-to-device copy must have finished before the next kernel reads the halos. Listing 3 uses the default stream and cudaDeviceSynchronize (line 152) for clarity; F8-11 replaces that with streams and events.
    3. 

  3. Decide once, log it. Listing 3 decides "aware" or "staged" at start-up from MPIX_Query_cuda_support() and prints the decision. The forensic lab is about the day nobody read that line.
    4. 



On a GPU-aware library the same program passes dU + 1 directly (lines 124–127). Even then MPI is not stream-aware: an MPI call on a device buffer does not wait for kernels you launched, so the program must synchronize (or wait on an event) before handing the buffer to MPI, exactly as before a host copy. D2


What staging costs


In the alpha-beta model, a staged message of m bytes costs one device-to-host copy, one transfer and one host-to-device copy: tstaged ≈ (αc + m/βc) + (αn + m/βn) + (αc + m/βc), where c is the copy and n the network or shared-memory transport. For small m the two extra αc terms dominate; for large m the two extra m/βc terms do. D7 Listing 2 measures the shape of this on the CPU: in its "staged" mode every transfer is preceded and followed by a memcpy through a separate bounce buffer. Both buffers are host memory here, so the copies are CPU copies, not PCIe transfers: this is a model of the structure, not a GPU measurement. In this run the ratio staged/direct stays near 1 up to 32 KiB and grows to 1.45 at 128 KiB, 2.31 at 2 MiB and 3.35 at 8 MiB (R4). R4




The numbers are noisy (other jobs share this container's CPUs) and they are CPU numbers. What carries over to real GPUs is the method: run the same benchmark with host buffers and with device buffers and log them side by side, as milestone F4 requires; if the device curve equals "host curve plus two copies", the library or the application is staging. C1



Layer 3 — the engineer's depth


One analogy sentence: a crew that recognises pantry crates still needs a road, a door and a key for every pantry, and each of those is a separate piece of software that must be built and configured. GPU awareness is a property of a whole stack, not of one library.


The stack that must agree


    

  • The MPI library must be built with GPU support (in Open MPI, a configure option naming the CUDA installation; for ROCm, the corresponding option or a GPU-aware UCX). D2
    • 

  • The transport layer (UCX, libfabric, or the library's own transports) must be built with its GPU modules, or device buffers fall back to staging or fail. D4
    • 

  • The GPU driver and the network driver must support the direct path: peer access between GPUs in a node (F8-04), and for GPUDirect RDMA a kernel module that lets the network card's driver register GPU memory (F8-09). D6
    • 

  • The topology decides whether the direct path is fast: a network card and a GPU behind the same PCIe switch behave differently from a pair whose traffic crosses the CPU's root complex (F8-04). D6
    • 



Other MPI libraries expose the same capability with different switches and queries (MVAPICH, MPICH with its GPU support, vendor MPIs); their documentation is the source for each, never the Open MPI names above. D2


Asking for what was not built


Open MPI has a writable parameter mpi_cuda_support next to the read-only mpi_built_with_cuda_support (R2). Setting the writable one cannot add what the build left out. The lab runs Listing 1 with --mca mpi_cuda_support 1 on this library: each process prints Open MPI's own help message, "The user requested CUDA support with the --mca mpi_cuda_support 1 flag but the library was not compiled with any support." (the same text is in the installed help file help-mpi-runtime.txt), and both processes then die with a segmentation fault; mpirun reports exit code 139 (R3). R3 H1 The crash after the message was not investigated further (the backtrace has no symbols); the lesson is the message, which names the cause in one sentence.




Semantics you must keep in mind


    

  • No stream ordering. MPI calls are not enqueued on CUDA streams; synchronize the producing stream (or an event) before the call, and do not launch a consumer kernel before the receive has completed. D2
    • 

  • Managed memory (cudaMallocManaged) is reported as cudaMemoryTypeManaged (H2) and may be handled differently from plain device memory by different libraries; check the library's documentation before passing it. H2
    • 

  • Which GPU. A rank must select its device (cudaSetDevice) before allocating or calling MPI on device buffers; Listing 3 uses rank % devices, which is wrong when ranks of several nodes are numbered consecutively but each node has its own GPUs. F8-10 uses a node-local rank from MPI_Comm_split_type.
    • 

  • Collectives on device buffers are allowed by GPU-aware libraries, but the library may implement the reduction arithmetic on the CPU (staging the data) or on the GPU; NCCL and RCCL (F8-06) are built for device-resident collectives and are often used alongside MPI for exactly that reason. D2 D8
    •

How the hardware actually does it


A staged message crosses the PCIe link between GPU and host twice per side (out of the sender's GPU, into the receiver's), each time carried by a DMA engine on the GPU (the copy engines of F6-29) into or out of pinned host memory, plus the transfer between host buffers by the CPU (shared memory) or the network card (F1-52). D5 Inside one node, a GPU-aware library can instead map the peer GPU's memory (inter-process handles) and let a GPU copy engine move the data directly over PCIe or NVLink, as your peer-copy matrix in F8-04 measured. D5 Between nodes, GPUDirect RDMA lets the network card read the sender's GPU memory and write the receiver's directly over PCIe, so host memory is not touched at all; F8-09 covers what that requires. D6 None of these hardware paths exists in the build container: no GPU, no RDMA device. The CUDA listing is built for real and its run stops at the runtime's own error.



Worked example


Predict the staging penalty, then compare with R4. Take Listing 2's 2 MiB row (2,097,152 bytes). The direct one-way time measured 225.33 µs (R4), so the transport moved about 2,097,152 / 225.33 µs ≈ 9.3 GB/s. The staged mode adds per one-way trip one copy on the sending side and one on the receiving side (rank 1 even does two, Listing 2 lines 37–38, because it stages both its receive and its reply). If a CPU memcpy of 2 MiB took about as long as the transfer itself (both are memory copies on this machine), two extra copies would roughly triple the time; the measurement says 521.55 µs, a ratio of 2.31. At 8 KiB the ratio is 1.01: the copies are tiny compared with the per-message cost.


The same reasoning for a GPU, with symbols instead of numbers (no GPU was available to measure): for m bytes, tstaged − tdirect ≈ 2αc + 2m/βc. With your own measured αc and βc from the CU201 bandwidth lab (F6-09), write the predicted penalty for 8 KiB and 8 MiB into your lab record before running the OSU benchmarks; at small sizes expect the 2αc term to dominate, at large sizes the 2m/βc term. F8-09 adds pipelining, which hides most of the copy time for large messages.

Where the analogy breaks


    

  • The old crew does not just "get confused"; the program fails. Handing a device pointer to a library that is not GPU-aware is an invalid memory access by the CPU, which can crash or silently read something else. The story's gentle confusion understates it.
    • 

  • "Smart crew" is not one switch. The analogy suggests one contract. In reality the MPI library, its transport layer, both drivers and the topology must all support the direct path; any missing piece silently turns path C into path B or A (Layer 3).
    • 

  • Carrying crates is not always the slow option. For tiny messages the per-message costs dominate and staging adds little (ratio 1.01 at 8 KiB in R4); for some topologies a pipelined staged path can rival a direct one (F8-09). The story suggests the walk is always the problem.
    • 

  • Pantry and dock are separate rooms; UVA addresses are not. With unified virtual addressing, host and device addresses come from one address range; the "where is it" question is answered from the pointer value by the runtime, not by the shape of a crate.
    •

Summary


    

  • GPU-aware MPI accepts device pointers and chooses a GPU-capable path; the MPI Standard does not define it, so you query the library.
    • 

  • Open MPI answers at compile time (MPIX_CUDA_AWARE_SUPPORT), at run time (MPIX_Query_cuda_support()) and in ompi_info; this build says no in all three (R1, R2).
    • 

  • Support needs the whole stack: MPI build, transport modules, drivers and topology; "built with UCX" is not "built with GPU support" (R2).
    • 

  • Without support, stage: pinned host buffers, D2H, MPI, H2D, with the kernel finished before the copy.
    • 

  • MPI is not stream-aware: synchronize before handing a device buffer to MPI, aware or not.
    • 

  • Staging costs about 2αc + 2m/βc per message: invisible for small messages, large for big ones (R4, CPU model).
    • 

  • Log the chosen path and benchmark host and device buffers side by side: "correct but slow" is found only by comparison.
    •

Answers to Check yourself


    

  1. The compile-time macro MPIX_CUDA_AWARE_SUPPORT in Open MPI's extension header (0 here, H1); the run-time function MPIX_Query_cuda_support() (0, R1); ompi_info's read-only parameters mpi_built_with_cuda_support/opal_built_with_cuda_support (false, R2). The configure line and the transport modules are supporting evidence (no CUDA option, no CUDA module).
    2. 

  2. Recognising a device pointer needs the GPU runtime: with UVA the runtime knows which address ranges are device allocations, and a pointer-attribute query asks it. A library built without GPU support does not link against or call the GPU runtime, so it has no way to ask and treats every buffer as host memory.
    3. 

  3. (c). A program compiled against a CUDA-aware header can be run with a different, non-aware library (containers, modules): that is why the run-time query exists. (a) is false: R3 shows the library refusing because support was not compiled in. (b) is false: MPI does not see streams. (d) is false: the extra cost is 2αc + 2m/βc, small for small messages (R4: ratio about 1 at 8 KiB).
    4. 

  4. Aware library: MPI may read the boundary cells before the kernel has written them, sending stale values; the result is wrong without an error (a race). Not aware: the D2H cudaMemcpy on the default stream waits for the preceding kernel on the same (legacy default) stream, so the staged path happens to stay correct, which hides the bug until the program moves to an aware library or to non-default streams.
    5. 

  5. 1 KiB: a ratio near 1, because per-message costs dominate and two 1 KiB copies are tiny. 16 MiB: a ratio of about 2–4, because both extra copies scale with size and are comparable to the transfer itself on this machine; the exact value is noisy (R4 has 2.31 at 2 MiB and 3.35 at 8 MiB). Run it to see.
    6. 

  6. (1) Is this MPI build ROCm-aware? Its documentation names the query or build report (and for Open MPI over UCX, whether UCX was built with ROCm support). (2) Do the transports have GPU modules for AMD GPUs (UCX module list, library build report)? (3) Does the driver and network stack allow direct access to GPU memory, and is the topology good (ROCm documentation on GPU-aware networking; the topology tools of F8-04)? If any answer is no or unknown, stage.
    7. 

  7. Δt ≈ 2αc + 2m/βc (one D2H and one H2D, each with a fixed cost and a size-proportional cost). At 8 KiB the 2αc term dominates; at 8 MiB the 2m/βc term does.
    8. 

  8. Pinned memory is about correctness of the method and avoiding a hidden copy, not about the size here: with pageable memory the copy is still correct but goes through the driver's own staging buffer (H2), and asynchronous copies from pageable memory do not overlap. For four doubles it is only slower, not wrong; for large halos the hidden copy matters, and the habit should be right from the start.

Forensic lab answer key


Observation. E1: the staged/direct ratio is between 0.89 and 1.04 from 8 B to 32 KiB, then 1.45 at 128 KiB, 1.67 at 512 KiB, 2.31 at 2 MiB and 3.35 at 8 MiB. Small messages pay only the fixed costs, which are small for in-memory copies; large messages pay copies proportional to size. A ratio rising from 1 towards 3 is what one copy before and one after the transfer (more on rank 1, which stages both directions) produce when a copy costs about as much as the transfer.


Hypotheses. H1: the application stages because it decided the library is not aware (tested by E2's first line and E3). H2: the library is aware but stages internally because no direct transport exists (tested by E4: a CUDA-aware build with no GPU transport module would show built-with-CUDA true). H3: the direct path exists but is slow because of topology (tested by a topology view; it would not explain a "not aware" probe).


Root cause. E2's first line, "halo path: staged", shows the application chose path A. E3 shows why: compile-time MPIX_CUDA_AWARE_SUPPORT = 0, run-time MPIX_Query_cuda_support() = 0. E4 confirms from the library itself: mpi_built_with_cuda_support:value:false, with the help text "Whether CUDA GPU buffer support is built into library or not". H2 is ruled out (the library is not CUDA-aware at all) and H3 is irrelevant until the library can take device pointers.


Missing option. The configure command line in E4 lists --with-ucx, --with-verbs, --with-libfabric, --with-psm2 and others, but no option naming CUDA. GPU support must be enabled in the MPI library at configure time (for Open MPI an option naming the CUDA installation; the exact spelling is in the Open MPI installation documentation, unverified here) and in the transport layer: the UCX module list in E4 has libuct_cma, libuct_ib, libuct_rdmacm and a ROCm perftest module, but no CUDA transport module. "Built with UCX" only says which transport layer is used; UCX itself must be built with its CUDA support, and Open MPI must be built with CUDA support too.


E5. It proves the diagnosis a second way: Open MPI itself states that the library "was not compiled with any support". It is not a fix because a run-time parameter cannot add code that was not compiled; here the processes even crashed afterwards (exit code 139).


Fix and verification. Build UCX with CUDA support and Open MPI with CUDA support against that UCX (or install vendor packages built that way), in a separate prefix. Verify: (1) the probe prints 1 and 1; (2) ompi_info shows built_with_cuda_support true and the CUDA option in the configure line, and the UCX module folder contains a CUDA transport module; (3) the device-buffer benchmark no longer follows "host plus two copies", and Listing 3 prints "halo path: aware" and the same hash.


Prevention. Make the application fail loudly (or at least warn on every rank) when it expected a GPU-aware library and the run-time query says no, controlled by a configuration flag; add an image acceptance test that runs the probe and a device-buffer benchmark and compares it with a stored baseline. How the evidence was produced: real runs in this build of Listings 1–3 and ompi_info on a stock Open MPI 4.1.6 package built without CUDA support; E1 is a CPU model of staging (memcpy through a bounce buffer), not a GPU measurement.
