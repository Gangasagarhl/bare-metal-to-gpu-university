Story hook

The chain of kitchen halls has grown: half the halls are now in a second building across town. Inside one building, crates move along corridors. Between buildings they travel by road, and the road is slower and has a gate at each end.

The town's delivery couriers already work the way you learned in DS401: each hall gives a courier the key to one labelled shelf, and the courier fills or empties that shelf without bothering the cooks. But the shelves are on the loading dock, and the food lives in the pantry. So for every delivery, a helper still carries the crate from pantry to dock, the courier drives it across town, and another helper carries it from the dock into the far pantry.

Joon-ho, the head of logistics, asked for something bolder: give the courier a key to a shelf inside the pantry. Then the crate goes from pantry to pantry with no helper walking at all. It needs the pantry's owner, the courier company and the building manager to agree, and it needs the pantry to be close enough to the road door. When all of that is true, the deliveries become as fast as the road allows. When one of them is missing, the couriers quietly go back to the loading dock, and nobody notices unless they measure.

What you will be able to do

  • Explain how data move between GPUs in two nodes over an RDMA network, with and without GPUDirect RDMA, and what each piece of hardware and software contributes.
  • Predict the time of a staged, a pipelined staged and a GPUDirect RDMA transfer with the alpha-beta model, and identify which term limits each.
  • Verify a two-node environment in the order the milestone prescribes: devices, raw RDMA bandwidth with perftest, library bandwidth with nccl-tests or rccl-tests, then your own code.
  • Determine which transport an MPI job actually used from the library's own verbose log, and recognise a fallback to TCP.
  • Diagnose a two-node job that silently ran over TCP because the RDMA devices were not visible to it.
Jargon box
RDMA (remote direct memory access)
Simple words: one computer's network card reads or writes another computer's memory directly, without the other computer's CPU copying anything. Analogy: the courier with the key to one labelled shelf (DS401's mapping). Precise: network transfers that the network adapter performs by DMA to and from registered memory regions, posted through verbs on queue pairs, over InfiniBand or RoCE; first defined in F1-53 and treated in depth in F5-34 to F5-38. D1 D2
GPUDirect RDMA
Simple words: the network card reads and writes GPU memory directly, so GPU data cross the network without a stop in the computer's main memory. Analogy: the courier with a key to a shelf inside the pantry. Precise: a mechanism with which a PCIe network adapter performs DMA to and from GPU device memory (first defined in F1-53); it requires support in the GPU, the GPU driver, a kernel component that lets the network driver register GPU memory, the network adapter and its driver, and a suitable PCIe topology. The CUDA 12.0 runtime exposes the per-device attribute cudaDevAttrGPUDirectRDMASupported, commented "Device supports GPUDirect RDMA APIs, like nvidia_p2p_get_pages". D3 H1
Pipelined staging
Simple words: moving a big GPU buffer through host memory in pieces, so the copy of one piece overlaps the network transfer of the previous one. Analogy: a bucket chain: while one crate is on the road, the next is being carried to the dock. Precise: splitting a message into chunks and running the three stages (device-to-host copy, network transfer, host-to-device copy) concurrently on different chunks; for k chunks the time is about the first chunk's three stages plus (k − 1) times the slowest stage. D4 R6
BTL (byte transfer layer, Open MPI)
Simple words: the part of Open MPI that actually moves bytes over one kind of path: shared memory, TCP, or a network card. Analogy: the kind of vehicle a parcel travels in: corridor trolley, road van, courier. Precise: an Open MPI component framework whose components (this build lists ofi, openib, tcp, vader, self) are selected per peer at start-up; the verbose log reports the choice as "Using <name> btl for send to …". Open MPI can instead use UCX through a different layer for the same job. D4 R3
perftest
Simple words: a set of small programs that measure raw RDMA latency and bandwidth between two machines. Analogy: timing an empty courier run before loading real crates. Precise: the RDMA performance tests distributed with the rdma-core ecosystem (for example ib_write_bw), introduced in F5-37; milestone F5 requires raw bandwidth "within 10 % of the NIC's line rate" before any GPU test. D2 C1

Layer 1 — the kid explanation

When two halls are in different buildings, every crate must cross the road. The road has a gate at each end, and opening a gate takes a moment no matter how small the crate is. Big crates also take longer to drive. That is the same "fixed cost plus cost per size" you have used since F8-03.

If the courier can only load on the dock, someone must carry the crate from the pantry to the dock first, and from the dock into the far pantry at the end. A clever team does this as a bucket chain: while one batch is on the road, the next batch is being carried out. The road never waits for long.

The cleverest arrangement is a courier with a key to the pantry itself. Then nobody carries anything to the dock. But that only works if every owner agrees and the pantry door is near the road. So the first job in a new building is always to check: which doors are open, and which road are we really using?

Layer 2 — the student explanation

The pieces between two GPUs

Between a GPU in node A and a GPU in node B there are, in order: the GPU's memory and its PCIe link; a PCIe switch or the CPU's root complex; the RDMA network adapter on its own PCIe link; the network (InfiniBand, or Ethernet with RoCE, F5-35) and its switches; and the same chain mirrored in node B (Figure 1). D1 C1 RDMA lets the adapter move data between registered memory and the wire without the CPU copying (F5-36). Without GPUDirect RDMA, the only memory the adapter can register is host memory, so GPU data must first be copied there: the staged path of F8-08, now with a real network in the middle. With GPUDirect RDMA, the adapter can register GPU memory and transfer it directly. D3

Three paths in one model

Listing 4 puts the three paths into the alpha-beta model, with parameters for the copy (αc, βc), the network (αn, βn), the rate at which the adapter can read GPU memory (βg) and a chunk size for pipelining:

  • staged: t = 2(αc + m/βc) + (αn + m/βn);
  • pipelined, k = ⌈m/chunk⌉ chunks: t = 2c1 + n1 + (k − 1)·max(c1, n1), with c1 and n1 the per-chunk copy and network times;
  • GPUDirect RDMA: t = αn + m/min(βn, βg).

The parameters in two_node_model.in are invented teaching values labelled TN-2 (they describe no real product, AH-22): copies at 8 µs + 20 GB/s, network at 4 µs + 20 GB/s, the adapter reading GPU memory as fast as the network, and 512 KiB chunks. R6



Read the table by size. For small messages GPUDirect wins by removing two fixed copy costs: 4 µs against 20 µs at 8 bytes, a factor of 5. For large messages serial staging approaches three times the direct time (two copies and one transfer at equal bandwidths), while pipelining brings it down to about the time of the slowest stage plus the pipe's fill: at 64 MiB, 4,443.87 µs pipelined against 3,359.44 µs direct and 10,086.33 µs serial (R6). R6 This is why a GPU-aware MPI without GPUDirect RDMA still pipelines its staging, and why the benefit of GPUDirect RDMA is largest for small and medium messages. D4 On real hardware every parameter is a measurement: copies from the CU201 bandwidth lab, the network from perftest, βg from a GPU-buffer RDMA test, all on your machines.

Layer 3 — the engineer's depth


One analogy sentence: the pantry key works only if four owners each sign, and the courier only takes the shortcut if it is actually shorter. In engineering terms, GPUDirect RDMA is a chain of software and hardware conditions, and the topology decides whether it helps.

How the hardware actually does it


An RDMA write from node A to node B starts when A's adapter reads a work request from its queue, then reads the source data by DMA over PCIe, packetises it and sends it; B's adapter receives the packets, checks the memory key and writes the data by DMA into the target memory region, then signals completion (F5-36). D1 D2 With GPUDirect RDMA the DMA reads and writes target addresses in a GPU's memory aperture on PCIe instead of host memory: the adapter does the same work, but the PCIe transactions go to the GPU (directly through a shared PCIe switch, or through the root complex), and host memory and CPU caches are not involved. D3 Two hardware facts follow: the GPU-side PCIe link and any switch between GPU and adapter become part of the network path (the topology matrix of F8-04 matters again), and writes arriving in GPU memory must become visible to kernels in the right order, which is what the CUDA attributes about flushing and ordering of GPUDirect RDMA writes describe (H1). None of this hardware exists in the build container.



Worked example


One 4 MiB message, TN-2 parameters (m = 4,194,304 bytes; 1 GB/s = 1,000 bytes per µs, so 20 GB/s = 20,000 bytes per µs):


    

  1. Copy: 8 + 4,194,304/20,000 = 8 + 209.7152 = 217.7152 µs. Network: 4 + 209.7152 = 213.7152 µs.
    2. 

  2. Serial staging: 2 × 217.7152 + 213.7152 = 649.1456 µs. Listing 4 prints 649.15 (R6).
    3. 

  3. Pipelined, chunk 524,288 bytes: k = 8. Per chunk, copy c1 = 8 + 26.2144 = 34.2144 µs, network n1 = 4 + 26.2144 = 30.2144 µs. Fill: 2 × 34.2144 + 30.2144 = 98.6432; then 7 × max(34.2144, 30.2144) = 239.5008. Total 338.144 µs; Listing 4 prints 338.14.
    4. 

  4. GPUDirect RDMA: 4 + 209.7152 = 213.7152 µs; printed 213.72. Ratio staged/direct 3.04.
    5. 



A two-node all-reduce. Two nodes with one GPU each all-reduce 64 MiB with a ring (F8-02): 2(P − 1) = 2 steps, each sending S/P = 32 MiB. With GPUDirect RDMA each step costs 4 + 33,554,432/20,000 = 1,681.72 µs, so the all-reduce costs 3,363.44 µs, ignoring the reduction arithmetic. F8-10's model prints exactly this inter-node term, 3,363.4 µs, for 2 nodes and 64 MiB. Note what the pipeline taught: with staging the per-step cost would be the pipelined figure for 32 MiB, and the copies would also compete with the reduction kernels for the GPU's copy engines.

Where the analogy breaks


    

  • "Key to the pantry" sounds like a security decision only. GPUDirect RDMA is mainly a hardware-path question: the adapter's DMA to GPU memory crosses PCIe switches whose placement determines speed. A key does not get faster with a shorter corridor; DMA does.
    • 

  • The bucket chain implies free helpers. Pipelined staging uses the GPU's copy engines, host memory bandwidth and, for the reduction in a collective, GPU compute: resources the training step also needs. The story's extra helpers cost nothing; the real ones compete.
    • 

  • The road is not one road. A network is links and switches shared by many jobs; congestion, routing and the adapter's own limits change βn from one measurement to the next. One road with one speed is the model, not the network.
    • 

  • "Quietly going back to the dock" is literal, not a metaphor. Libraries do fall back without errors (R3, R4 show the selection; R7 shows a missing-device environment). The story makes it sound unusual; in practice it is the default failure mode.
    •

The two-node all-reduce is far slower than their single-node results suggested, and a quick ping-pong between the two nodes shows a per-message cost in the microseconds and a bandwidth far below the fabric's line rate. The job ran without a single error. They send you the ping-pong results, the transport log of the job, and the output of two checks run inside the job's container.


Evidence pack. All items are real outputs of this build. In this one-machine stand-in, E2 and E4 come from a run with TCP forced by an option; on Leila's cluster TCP was the only transport the job could find. E1 and E3 are the shared-memory baseline from the same machine, standing in for "what a fast path looks like".

Summary


    

  • Between nodes, GPU data either stage through host memory or travel by GPUDirect RDMA, with the network adapter reading and writing GPU memory directly.
    • 

  • In the alpha-beta model, GPUDirect saves the copies' fixed costs (large factor for small messages) and their bandwidth costs; pipelined staging recovers much of the large-message gap (R6, invented TN-2 values).
    • 

  • GPUDirect RDMA needs GPU, drivers, a peer-memory kernel component, the adapter, the library and the topology to agree; the CUDA attribute is only the GPU's part (H1).
    • 

  • Verify in the milestone's order: devices, perftest, library, your code; each step predicts the next.
    • 

  • Find the transport per peer in the library's log; a fallback to TCP produces no error (R3, R4).
    • 

  • Run device checks inside the job's environment: containers without RDMA device files look exactly like E5 and E6.

  2. For small messages the time is mostly fixed costs: staging adds two copy α's (16 µs in TN-2) to a network α of 4 µs, so removing them gives a factor near 5. For large messages time is mostly bytes over bandwidth; pipelined staging overlaps the copies with the network so it costs about the slowest stage plus one fill, close to the direct time; GPUDirect still removes the fill and frees the copy engines, but the factor is smaller (64 MiB: 4,443.87 versus 3,359.44 µs, R6).

  5. With βg = 5 GB/s the direct path costs 4 + m/5,000 µs. Pipelined staging's steady state costs one chunk per max(c1, n1), about m/20,000 per byte plus overheads, so for large messages (from roughly a megabyte, where the fill and the extra α's become small compared with m/5,000 − m/20,000) pipelined staging wins; for small messages the direct path still wins by its smaller fixed cost. Forensic lab answer key


Observation. 8-byte one-way time 0.27 µs on the fast path (E1) versus 8.19 µs in the slow job: a factor of about 30. At the largest sizes, 1,646.52 µs versus 3,129.69 µs for 8 MiB: about 2. The fixed per-message cost is what changed most, the signature of a different software path rather than a slower wire.


Transport. E4: "mca: bml: Using tcp btl for send to [[…],1] on node vm" (and to rank 0). The initialised components were tcp and self; no RDMA-capable transport was initialised (E3 shows vader for the same-machine fast path; an RDMA BTL or UCX would appear on a working cluster).


Hypotheses. No device visible: tested by E5 and E6, confirmed (no list, errno 38; no /sys/class/infiniband, no /dev/infiniband). Excluded by configuration: would show a device in E5 but still no RDMA transport in E4; not the case here. Fabric down: would show a device with a port state other than active in Listing 2's output; the container cannot even see a device. Library built without RDMA support: ompi_info on this build lists openib and was configured --with-verbs and --with-ucx (F8-08, R2 there), so support is built in; it had nothing to use.


Root cause. The job's container has no RDMA device files and no InfiniBand sysfs entries, so libibverbs finds no device, every RDMA transport disqualifies itself at start-up, and the library falls back to the transport that always works: TCP. Fallback is by design and silent.


Fix and verification. Run the job with the RDMA devices and sysfs entries exposed to the container (the cluster's container runtime documents how). Then, in order: (1) Listing 2 inside the job lists the adapters with port state active; (2) perftest inside the job reaches the line rate within 10 %; (3) the MPI transport log no longer says tcp for inter-node peers. Only then re-run the all-reduce.


Prevention. A pre-flight line such as "run Listing 2; abort the job if it exits non-zero" at the top of every multi-node script, plus logging the transport per peer in every performance run. How the evidence was produced: real runs of Listings 1 and 2 and of shell checks in this one-machine build; E2 and E4 come from forcing TCP with --mca btl tcp,self, standing in for the cluster job's fallback.
