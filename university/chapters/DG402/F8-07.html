Story hook

Four kitchen halls stand in a row along one street. Each hall cooks one stretch of a very long banquet table: hall 0 the first quarter, hall 1 the second, and so on. Every few minutes each hall must taste the dish at the edge of its neighbour's stretch, because the seasoning on one plate depends on the plates next to it. So the halls send small parcels to each other: "here is my last plate, send me your first one".

For weeks this worked. Then Malik, who runs hall 1, decided to send bigger samples: a whole tray instead of one spoon. That evening every hall stood at its door holding a tray, waiting for the neighbour to come and take it before going inside to receive anything. Nobody moved. The street was silent until the night manager came by and sent everyone home.

Small parcels had been left on the doorstep; big ones needed the neighbour to open the door. The recipe on the wall had always said "send, then receive". It had never been safe; it had only been lucky. This chapter is about the delivery rules between halls, the Message Passing Interface, and about that evening, which is this chapter's forensic lab.

What you will be able to do

  • Write MPI programs with point-to-point (MPI_Send, MPI_Recv, MPI_Sendrecv, MPI_Isend, MPI_Irecv, MPI_Waitall) and collective operations, and check each result against a value you can compute by hand.
  • Implement a halo exchange for a decomposed 1-D stencil and prove with a hash that it gives bit-identical results on 1, 2 and 4 processes (milestone F4's acceptance test, host part).
  • Explain the difference between what the MPI Standard guarantees and what one MPI library happens to do, using eager and rendezvous protocols and the library's own eager limits.
  • Diagnose a head-to-head deadlock from a hang trace and the library's configuration, and fix it with MPI_Sendrecv or non-blocking calls.
  • Estimate the communication cost of a halo exchange with the alpha-beta model of F8-03.
Jargon box
MPI (Message Passing Interface)
Simple words: a standard set of library calls that lets many separate programs, often on different computers, send each other data and compute together. Analogy: the delivery rules every kitchen hall in the chain agrees to follow. Precise: a library interface specified by the MPI Forum in "MPI: A Message-Passing Interface Standard"; processes have private memory and exchange data only through explicit calls (point-to-point, collective, one-sided); implementations include Open MPI, MPICH and MVAPICH. The library used here reports MPI API version 3.1.0. D1 R1
Rank (MPI)
Simple words: the number of one process in the job, counted from zero. Analogy: the hall's number on the delivery list. Precise: the integer that identifies a process within a communicator, 0 to size − 1, returned by MPI_Comm_rank (first defined in F5-22). D1
Communicator (MPI)
Simple words: a named group of processes that talk to each other; every MPI call says which group it is about. Analogy: the delivery list a parcel is addressed within; the same hall can be on several lists with a different number on each. Precise: an opaque object (MPI_Comm) that combines a group of processes with a communication context, so messages and collectives in one communicator never match those in another; MPI_COMM_WORLD contains all processes started together. D1
Point-to-point communication (MPI)
Simple words: one process sends a message to one other process. Analogy: one labelled parcel from one hall to one other hall. Precise: a send and a receive matched by communicator, source rank and tag; the data are described by (buffer address, count, datatype). D1
Non-blocking operation (MPI)
Simple words: a call that starts a transfer and returns at once; you ask later whether it has finished. Analogy: handing a parcel to the delivery desk and getting a ticket, instead of waiting at the door. Precise: MPI_Isend, MPI_Irecv (and non-blocking collectives such as MPI_Iallreduce) return an MPI_Request; the buffer must not be reused (send) or read (receive) until MPI_Wait/MPI_Test or their "all/some" forms report completion. D1
Halo exchange
Simple words: each process keeps a copy of the cells at its neighbours' edges and refreshes those copies every step. Analogy: tasting the edge plate of the neighbouring hall's stretch of table. Precise: in a domain decomposition, ghost (halo) cells around each subdomain hold copies of neighbouring subdomains' boundary values; before each stencil update the boundary values are sent to the neighbours and the halos filled from them (milestone F4's "halo-exchange (stencil) example"). C1
Eager and rendezvous protocols
Simple words: two ways a library delivers a message: small ones are pushed to the receiver straight away; large ones wait until the receiver is ready. Analogy: small parcels left on the doorstep; big ones only handed over when the neighbour opens the door. Precise: implementation protocols, not MPI Standard terms: in an eager send the data travel with the first packet and are buffered at the receiver if no receive is posted; in a rendezvous send a first fragment announces the message and the bulk moves only after the receiver has matched it. Open MPI's per-transport parameter btl_<name>_eager_limit sets the switch-over size ("Maximum size (in bytes, including header) of 'short' messages"). D2 R3
Safe MPI program
Simple words: a program that finishes no matter how much the library is willing to buffer. Analogy: a delivery plan that works even if no hall ever leaves anything on a doorstep. Precise: the MPI Standard allows a standard-mode MPI_Send to return either after buffering the data or only after a matching receive has started; a program whose completion depends on buffering is called unsafe. D1

Layer 1 — the kid explanation

In the chain of kitchen halls, no hall can look into another hall's pantry. If hall 2 needs to know what hall 1 has, hall 1 must pack a parcel, write hall 2's number on it and hand it to the delivery service. That is message passing: the only way to share is to send.

Every parcel has a label: who sent it, who should get it, and a small tag that says what it is ("left edge plate", "right edge plate"). The receiver asks for a parcel with a particular label, and the service hands over the matching one.

Some jobs need every hall at once: "add up everybody's leftovers and tell everyone the total". The delivery rules have ready-made jobs for that, called collectives, so nobody has to plan the trips by hand.

One rule is easy to forget. A small parcel can be left on the doorstep, but a big one is handed over only when the receiver opens the door. If two neighbours both insist on handing over a big parcel before they open their own door, they wait for each other forever.

Layer 2 — the student explanation

The programming model

An MPI job is a set of processes started together (here by mpirun -np N), usually running the same program. Each process has its own address space; nothing is shared implicitly. Each process learns its rank and the number of processes from the communicator MPI_COMM_WORLD and decides from its rank which part of the work to do. D1 This is the same SPMD idea (single program, multiple data) you met with GPU threads in F6-02, with two differences that matter: ranks are whole processes, possibly on different machines, and the only way to share data is an explicit call. D1

Every data argument in MPI is a triple: a buffer address, a count and a datatype (MPI_INT, MPI_DOUBLE, MPI_CHAR, or derived types for strided data). The count is in elements, not bytes. A point-to-point message also carries the destination or source rank, a tag (a non-negative integer you choose) and the communicator; a receive matches a send when communicator, source and tag match, with wildcards MPI_ANY_SOURCE and MPI_ANY_TAG available on the receive side. Messages between one pair of ranks in one communicator do not overtake each other. D1 All of these names appear in the installed mpi.h of Open MPI 4.1.6, which is what the compiler checked. H1

Blocking, combined and non-blocking point-to-point

  • MPI_Send / MPI_Recv are blocking: MPI_Send returns when the send buffer may be reused, which may be before or after the receiver got the data; MPI_Recv returns when the data are in the receive buffer. D1
  • MPI_Sendrecv performs a send and a receive as one call, and the library arranges them so that a ring or pairwise exchange of MPI_Sendrecv calls cannot deadlock on buffering. Listing 1 uses it for a ring; Listing 2 uses it for the halo exchange. D1
  • MPI_Isend / MPI_Irecv start an operation and return a request; MPI_Waitall completes a set of requests. Posting receives before sends is a good habit: an incoming message then has a destination waiting for it. D1
  • MPI_PROC_NULL as a source or destination turns the operation into a no-op that completes at once. It removes the "if I am at the edge" branches from the halo exchange (Listing 2, lines 67–68). D1

The halo exchange


Listing 2 simulates heat spreading along a rod of 1,000 cells for 500 steps with the explicit update u′i = ui + r(ui−1 − 2ui + ui+1), r = 0.25. Each rank owns a contiguous block of cells plus one halo cell on each side (Figure 1). Before each update it sends its first owned cell to the left neighbour and its last owned cell to the right neighbour, and fills its own halos from theirs. The decomposition changes who computes a cell, never what is computed: each cell's new value uses the same three operands in the same order. That is why the final grids on 1, 2 and 4 ranks must be bit-identical, and the run shows the same FNV-1a hash 9fef6c9047951684 for all three (R2). R2 This is the acceptance test of milestone F4, "The stencil gives the same answer on 1, 2 and 4 ranks", with host buffers; F8-08 moves the grid to the GPU. C1





Layer 3 — the engineer's depth


One analogy sentence: the delivery rules say what must arrive, not how the van is loaded, and production code must work for every way of loading it. At this level you read the MPI Standard for the guarantees and the library's documentation and configuration for the behaviour you observe, and you keep the two apart.


Send modes and what "safe" means


The Standard defines four send modes: standard (MPI_Send), buffered (MPI_Bsend, using a buffer you attach), synchronous (MPI_Ssend, completes only after the matching receive has started) and ready (MPI_Rsend, legal only if the receive is already posted). For standard mode it leaves the choice to the implementation: the call may copy the message into a system buffer and return, or wait for the receiver. D1 A program that only completes because the library buffered is unsafe, and the Standard's point-to-point chapter discusses exactly the pattern of Listing 3. A practical test is to replace MPI_Send by MPI_Ssend during development: a safe program still completes; an unsafe one hangs at once, at every size. D1


Eager and rendezvous in one library


Open MPI moves point-to-point messages through a layer of transports, each a component of its "byte transfer layer" framework: vader (shared memory between processes on one machine), tcp, self (a process sending to itself), and others that need hardware. D2 R3 Each transport has an eager limit. On this build, ompi_info prints 4,096 bytes for vader and 65,536 bytes for tcp, both described as "Maximum size (in bytes, including header) of 'short' messages". R3




Below the limit a message is sent eagerly and the receiver buffers it if no receive is posted yet; above it the sender first announces the message and the payload moves after the receiver matches it. D2 The trade-off is memory and copies versus a round trip: eager costs a buffer and an extra copy at the receiver but no handshake; rendezvous costs one extra message latency but lets the payload go straight into the user's buffer, which on RDMA hardware can be a zero-copy transfer (F5-38). D2 The exact protocol variants, fragment sizes and pipeline thresholds are the library's business and vary by transport and version; read them from ompi_info --param btl <name> --level 9 on the machine you use.


How collectives are implemented


The Standard specifies what a collective computes, not how. An MPI library chooses an algorithm (ring, recursive doubling, binomial tree, Rabenseifner's reduce-scatter plus all-gather…) per call from message size and process count; the papers on collective optimisation in MPICH describe the cost of each in the alpha-beta model you used in F8-03. D3 Open MPI's choice lives in its coll framework (components such as tuned, libnbc for non-blocking collectives, and han, a hierarchical one you will meet in F8-10). R3 D2 Two consequences matter for GPU work: a floating-point reduction may not be bitwise reproducible across process counts or library versions, because the summation order changes; and a mismatch in collective call order between ranks is not detected by the Standard's rules and usually shows up as a hang.


Errors and checking


Every MPI function returns an error code, and Listing 1 checks each one, as the university's code rules require (AH-27). Know, though, that the default error handler on MPI_COMM_WORLD is MPI_ERRORS_ARE_FATAL: an error aborts the job before your check runs, unless you install MPI_ERRORS_RETURN with MPI_Comm_set_errhandler. D1 Deadlocks are not errors to the library: they produce no message at all, only silence, which is why the forensic lab's evidence is a trace that stops.

How the hardware actually does it


On one machine, the vader transport moves a message through memory shared between the two processes: the sender's CPU copies the data into a shared region and the receiver's CPU copies it out, or, for large messages, one process copies directly from the other's address space with a kernel-assisted single copy. The parameter btl_vader_single_copy_mechanism reports "cma" on this build, which names Linux cross-memory attach. R3 D2 Either way the CPU cores of the two ranks move the bytes, which you will see again in F8-11 when "overlap" on a CPU turns out not to overlap. Between machines, tcp hands the bytes to the operating system's network stack and the network card (F1-52), with system calls and copies on both sides (F5-34); RDMA transports let the network card read and write registered memory directly (F5-36, and F8-09 for GPU memory). The MPI program is the same in every case: that is the point of the interface, and the reason performance must be measured per transport.


Not verified — check before relying on this
The two-copy and single-copy mechanisms of the shared-memory transport are described from memory; this build observed only the parameter value "cma" (R3). Check the Open MPI documentation for the version in use, and the Linux documentation of process_vm_readv and process_vm_writev, before relying on the description.



Worked example


Decomposition. 1,000 cells on P = 3 ranks (a count the lab did not run; try it in Lab step 3): base = ⌊1000/3⌋ = 333, extra = 1000 mod 3 = 1. Rank 0 gets 334 cells starting at 0 (cells 0–333); rank 1 gets 333 starting at 1·333 + 1 = 334 (cells 334–666); rank 2 gets 333 starting at 2·333 + 1 = 667 (cells 667–999). Listing 2, lines 53–56 and 91–94, compute exactly these numbers.


First step at the edge of the hot band. Before step 1, u398 = u399 = 0 and u400 = u401 = 100. Then u′399 = 0 + 0.25·(0 − 0 + 100) = 25 and u′400 = 100 + 0.25·(0 − 200 + 100) = 75. With 4 ranks, cells 399 and 400 both belong to rank 1 (cells 250–499), so no message is involved; cell 499 needs cell 500 from rank 2's first owned cell, which arrives through exchange 1 of Figure 1.


Messages and bytes. Each step every interior rank makes two MPI_Sendrecv calls, each sending one 8-byte double and receiving one; edge ranks send one real message (the other partner is MPI_PROC_NULL). On P ranks that is 2(P − 1) messages per step: 6 for 4 ranks, 3,000 in 500 steps. With the alpha-beta model of F8-03, an 8-byte message costs about α; an interior rank spends about 2 · 500 · α = 1,000α waiting for halos over the run, independent of the grid size. With the α that F8-03 measured between two processes on this kind of container (its ping-pong listing), that is well under a millisecond: the stencil here is limited by computation, and on a real cluster with large grids the halo size (one cell in 1-D, a whole face in 3-D) decides the balance. Write your own α into the formula in Lab step 4.

Where the analogy breaks


    

  • Parcels on the doorstep are not free and not unlimited. An eagerly sent message occupies buffer memory at the receiver until it is matched; many unexpected messages from many ranks can exhaust it. The doorstep picture suggests a pile that can always grow.
    • 

  • Halls do not choose their own parcel size limit; the transport does. In the story, Malik's "bigger samples" broke the street. In MPI the same program crosses the limit at 4,096 bytes on one transport and 65,536 on another on this very machine (R3–R5): the limit is a property of the library and the path, and it changes when the job moves to another network.
    • 

  • A delivery service carries parcels; MPI carries typed data. The count and datatype describe the data; the library may convert, pack or split it. A parcel analogy hides that sending 1,000 MPI_DOUBLE is not the same call as sending 8,000 MPI_CHAR on a heterogeneous system.
    • 

  • Collectives are not a manager who collects everything. There is no central hall; collectives are distributed algorithms whose steps are ordinary messages between ranks (rings, trees), as in F8-02.
    •

Transition box

Where you came from: in F8-01 to F8-06 the GPUs of one machine exchanged data through NCCL or RCCL calls and your own ring, with one process or thread per GPU; F5-22 started MPI programs on a cluster. What carries over: the collectives and their algorithms, the alpha-beta model for predicting time, the habit of checking results against a closed form, and the rule that every participant must call the same collective in the same order. D1 D3 What changes: the participants are separate processes that may sit on different machines, so there is no shared memory and no peer access: every byte moves through an explicit call; correctness can depend on buffering that the Standard does not promise, so a program that passes on one transport can hang on another; and the library, not you, picks transports and algorithms, so you must read its configuration (R3) to explain what you measure. D1 D2 What comes next: F8-08 puts the buffers in GPU memory and asks whether the MPI library can read them directly or must stage them through host memory.

Summary


    

  • MPI processes share nothing; data move only through explicit calls described by (buffer, count, datatype) and matched by (communicator, source, tag).
    • 

  • Blocking, combined (MPI_Sendrecv) and non-blocking (MPI_Isend/MPI_Irecv + wait) point-to-point calls cover most exchange patterns.
    • 

  • Collectives involve every rank of a communicator, in the same order on every rank; the library chooses the algorithm.
    • 

  • A halo exchange keeps neighbour copies current; a correct one gives bit-identical results for every rank count (R2).
    • 

  • Standard-mode sends may or may not buffer; a program that depends on buffering is unsafe.
    • 

  • Eager and rendezvous are library protocols; this build's limits are 4,096 bytes (shared memory) and 65,536 bytes (tcp), and the unsafe exchange hangs exactly there (R3–R5).
    • 

  • Read the library's configuration with ompi_info before explaining any measurement.

Forensic lab answer key


Observation. E1's last line is "naive 4096 bytes: entering exchange"; the last completed size is 2,048. E2's last line is "naive 65536 bytes: entering exchange"; the last completed size is 32,768. Both logs end with "entering" and never "done": the processes are inside the exchange. Both runs were stopped by the 15 s limit (exit code 124), not by a crash.


Hypotheses. A crashed peer would make mpirun report a process failure, not a timeout. A network failure is ruled out because both ranks are on one machine and the hang moves with the transport's configuration. An infinite loop in user code is ruled out because rank 0 printed "entering" and the only code between "entering" and "done" is the two MPI calls. A deadlock between the two blocking sends fits every line.


Root cause. E3: the shared-memory transport's eager limit is 4,096 bytes and the tcp transport's is 65,536 bytes, both including the message header. A 4,096-byte payload plus header exceeds 4,096, so in E1 it is sent with the rendezvous protocol: MPI_Send waits until the peer posts a matching receive. Both ranks are inside MPI_Send, so neither reaches MPI_Recv: a cycle of waits (Figure 2). In E2 the same happens one step later in the series because the tcp limit is larger: 32,768 + header fits, 65,536 + header does not.


Standard. The program is erroneous in the Standard's sense of an unsafe program: its completion depends on system buffering of standard-mode sends, which the Standard does not guarantee. It is not "a bug in Open MPI".


Fix. E4 uses MPI_Sendrecv (Listing 3, lines 26–27), which the library executes without requiring buffering, so it completes at every size on every transport. Equivalent fixes: post MPI_Irecv first, then MPI_Send, then wait; or order the calls by rank parity (even ranks send first, odd ranks receive first).


Prevention. Develop and test with MPI_Ssend in place of MPI_Send (a compile-time switch), which removes buffering from the picture and makes the unsafe pattern hang at the first size; and include message sizes above every transport's eager limit in the test suite. How the evidence was produced: real runs of Listing 3 in this build with the default transports, with --mca btl tcp,self, and in fixed mode; each naive run was stopped by timeout -k 5 15.
