Story hook

In a corner of the great kitchen hall stands a machine that the helpers rarely use. You lay a small tray of numbers on its left side and another on its top, and in one push it multiplies the whole tray and adds the result into a third tray. A row of helpers working by hand needs many steps for the same tray.

The machine is picky. It takes only trays of certain sizes. It takes only certain kinds of numbers: short ones in, longer ones out. And every helper of the row must hand in their part of the tray in exactly the place the machine expects: if Aiko puts her numbers where Tomás's should go, the machine still runs, quickly and silently, and the answer is wrong.

Last week a team in the hall swore they were using the machine. Their dishes came out right, but slowly. When someone finally looked at the list of steps the helpers really followed, the machine was not in it at all. This chapter is about that machine on AMD GPUs: the matrix cores, their MFMA instructions, the rocWMMA library, and how to prove from the disassembly that you really use them.

What you will be able to do

  • Explain what one MFMA instruction computes, which wave holds which operands, and which AMD targets have it.
  • Write a small FP16-input, FP32-accumulate GEMM with a compiler builtin for MFMA, and state exactly which part of it is unverified.
  • Prove from the ISA that the matrix instructions are in the inner loop, and read their accumulator registers (AGPRs or VGPRs).
  • Justify an E7 tolerance from FP16 and BF16 input rounding and FP32 accumulation.
  • Compare the MFMA route with rocWMMA and with CUDA WMMA, and choose between them.
  • Diagnose "matrix cores unused" from build logs, macros and disassembly.
Jargon box
Matrix core
Simple words: a part of an AMD GPU that multiplies small blocks of numbers in one instruction. Analogy: the tray machine in the corner of the hall. Precise: AMD's name for the matrix-multiply units of its CDNA (Instinct) GPUs, used through MFMA instructions; RDNA3 GPUs have WMMA instructions instead. NVIDIA's comparable units are tensor cores. D2 C1
MFMA
Simple words: the instruction that tells the matrix core to multiply-add a tray. Analogy: one push of the machine. Precise: "matrix fused multiply-add": a wave-wide instruction D = A × B + C on fixed block shapes and types, named like v_mfma_f32_32x32x8f16 (FP32 result, a 32 × 32 × 8 block, FP16 inputs); in HIP reachable through clang builtins such as __builtin_amdgcn_mfma_f32_32x32x8f16. D2 R2
Fragment (operand layout)
Simple words: each thread's share of the small matrices, in the order the machine wants. Analogy: which helper puts which numbers where on the tray. Precise: the mapping from (lane, register element) to (row, column) of A, B and C for one matrix instruction; documented per instruction in the ISA guide and the AMD Matrix Instruction Calculator, and hidden by rocWMMA's fragment types. D2 D4
AGPR (accumulation register)
Simple words: a special register where the matrix machine keeps its running sums. Analogy: a separate tray rack next to the machine. Precise: accumulation VGPRs of CDNA GPUs, written a[...] in the ISA; the compiler placed the MFMA accumulator in AGPRs for gfx908 and, inside a loop, for gfx90a (R2, R3). R2 R3 C1
rocWMMA
Simple words: a library that lets you use the matrix machine without knowing where each number goes. Analogy: a tray holder that puts every helper's numbers in the right place for you. Precise: AMD's C++ header library of wave-level matrix multiply-accumulate with fragment types, modelled on CUDA's WMMA API (F6-26); names to be checked in its documentation (unverified box). D3
Mixed precision
Simple words: short numbers in, longer numbers for the sums. Analogy: small trays in, a big tray for the results. Precise: FP16 or BF16 inputs with FP32 accumulation; the error comes mainly from rounding the inputs (unit roundoff 2−11 for FP16, 2−8 for BF16) and from the FP32 sums (2−24 per addition). D6 R5

The idea in pictures

Figure 1 shows one v_mfma_f32_32x32x8f16: a whole wave of 64 lanes hands in a 32 × 8 block of A and an 8 × 32 block of B, and receives a 32 × 32 block of D = A × B + C. The counts per lane follow from the builtin's types, which the compiler checked: 4 FP16 values of A, 4 of B and 16 FP32 values of C per lane (64 × 4 = 256 = 32 × 8; 64 × 16 = 1,024 = 32 × 32).

Figure 2 shows the decision every matrix-core kernel goes through at compile time, and where it can silently go wrong: the forensic lab of this chapter.

Layer 1 — the kid explanation

A matrix multiply is many small multiplications added together. A row of helpers can do it by hand, one multiply-add at a time. The matrix core is a machine that does a whole block of them in one go, if you give it numbers in exactly the shape and order it wants.

Two things make it tricky. First, it wants short numbers (half precision) in and gives longer numbers out, so you must check that the small rounding errors are acceptable. Second, it will not tell you if you forgot to use it. The program is still correct, only slower. So you check the list of instructions the compiler produced.

Layer 2 — the student explanation

What one MFMA does

An MFMA instruction is executed by a whole wave. For v_mfma_f32_32x32x8f16 the wave multiplies a 32 × 8 FP16 block by an 8 × 32 FP16 block and adds the product into a 32 × 32 FP32 block. D2 In HIP 5.7 (clang 17) the builtin __builtin_amdgcn_mfma_f32_32x32x8f16(a, b, c, cbsz, abid, blgp) takes a vector of 4 _Float16 for A, the same for B, and a vector of 16 float for C, and returns the new 16 floats; Listing 1 passes 0 for the last three arguments, which select broadcast variants described in the ISA guide. R2 D2

Which targets have it

The targets run compiles one call of this builtin for five targets (R2): gfx908 and gfx90a accept it as v_mfma_f32_32x32x8f16; gfx942 accepts it and prints the mnemonic v_mfma_f32_32x32x8_f16; gfx1030 and gfx1100 reject it with "needs target feature mai-insts". RDNA3 (gfx1100) has its own matrix instruction, which the wmma_rdna3 run shows as v_wmma_f32_16x16x16_f16 on a wave of 32 (R4). R2 R4 So a "matrix-core kernel" is per architecture family: CDNA uses MFMA, RDNA3 uses WMMA, older RDNA has neither, and NVIDIA uses its own MMA instructions (F6-26).

The operand layout, and what is unverified

Every lane must place its 4 + 4 inputs and read its 16 outputs according to the instruction's layout. Listing 1 keeps that mapping in six small functions (lines 18–23) and states that it is assumed, not verified, in this build.

The program's own test will also catch a wrong layout on hardware: it compares every element of C with a CPU reference and prints the first five mismatches.

Where the accumulators live

The compiler's choice of registers is visible in the ISA. For a single call, gfx908 put C in AGPRs (a[0:15], .agpr_count: 16), while gfx90a and gfx942 used ordinary VGPRs (v[0:15], .agpr_count: 0) (R2). Inside Listing 1's K loop on gfx90a, the compiler placed the accumulator in AGPRs (a[0:15], .agpr_count: 16, .amdhsa_accum_offset 28) and initialised them with v_accvgpr_write_b32 (R3). R2 R3 The curriculum's vocabulary table describes "accumulation registers on CDNA"; how the AGPR and VGPR files share the register budget on gfx90a is in the ISA guide and the LLVM AMDGPU user guide, and matters for occupancy (F7-10). C1 D5

rocWMMA and CUDA WMMA

Writing layouts by hand is error-prone and not portable across instruction shapes. CUDA's answer is the WMMA API in mma.h: fragment types, load_matrix_sync, mma_sync, store_matrix_sync. The cuda_wmma run builds such a kernel for sm_80 in this build and finds 10 HMMA.16816.F32 instructions in its SASS (R6). H1 R6 rocWMMA is AMD's library in the same style. D3

Not verified — check before relying on this

rocWMMA is not installed in this build. The chapter assumes, from the curriculum's description and the author's memory, that it offers a namespace rocwmma with fragment, fill_fragment, load_matrix_sync, mma_sync and store_matrix_sync mirroring CUDA's names, with block sizes and types restricted per architecture. Check every identifier, the supported block sizes and types for your GPU, and the header to include in the rocWMMA documentation for your ROCm version before porting cuda_wmma.cu.inc.

Layer 3 — the engineer's depth

An E7 tolerance from first principles

E7 asks for "Error versus an FP64 reference within a tolerance justified from FP16/BF16 input rounding." C1 Rounding a real number to FP16 introduces a relative error of at most u16 = 2−11 (round to nearest, 11-bit significand), to BF16 at most 2−8. D6 A product of two rounded inputs has relative error at most 2u + u2. The product of two FP16 numbers is exact in FP32 (11 + 11 = 22 significand bits ≤ 24), so the only further error is the FP32 summation, at most about K·2−24 relative to S = Σ|akbk|. D7 Bound: |error| ≤ (2u + u2 + K·2−24)·S.

Listing 2 measures the worst observed error over 200 random dot products for K = 64, 512 and 4,096, in three variants (R5): FP16 inputs summed in FP64, FP16 inputs summed in FP32, and BF16 inputs summed in FP32. All observed errors lie below the bounds it prints; the first two columns agree to three digits, which says that for these sizes input rounding dominates and FP32 accumulation adds little; BF16 errors are roughly eight times larger, matching the ratio of the unit roundoffs (2−8 / 2−11 = 8). R5 Use the bound, not the observation, as the test tolerance; quote S, not |result|, as the scale.

Not verified — check before relying on this

Listing 2 assumes the matrix instruction computes the exact products and adds them in FP32 one by one. Real MFMA hardware may add groups of products in a different order or with different intermediate precision, and may treat denormals and rounding modes in its own way. The ISA guide's MFMA chapter (D2) describes this; it was not opened in this build. The bound above holds for the model; recheck it against the documented behaviour of your instruction.

From one instruction to a fast kernel

Listing 1 is correctness-first: one wave per 32 × 32 tile, operands loaded from global memory as single 16-bit values (global_load_ushort, 6 per iteration in R3) and no LDS. In its inner loop, address arithmetic outnumbers the single v_mfma. A fast kernel combines everything of F7-16 with the matrix instruction: block tiles staged in LDS with wide loads, several MFMA tiles per wave (so one wave reuses its A fragment across several B fragments), double buffering, and an LDS layout that delivers fragments without bank conflicts. Composable Kernel and hipBLASLt do this (F7-18, F7-19); E7's second acceptance test compares your kernel with hipBLASLt half-precision GEMM. C1

The instruction's throughput per clock, its latency in cycles and the number of independent MFMAs needed to keep the unit busy are hardware facts of each GPU; they belong in your dossier from the ISA guide or the vendor's tuning guide, not in this chapter.

How the hardware actually does it

The MFMA instruction is issued once for the wave, like any vector instruction, but executed by the matrix unit; its sources are VGPRs (A and B) and AGPRs or VGPRs (C), and its result goes to AGPRs or VGPRs (R2, R3). D2 On gfx908 the accumulator must be in AGPRs in the code this compiler produced; on gfx90a both appear, depending on the code. Moving values between the two files costs instructions (v_accvgpr_write_b32 to initialise, reads at the end). The s_nop just before the MFMA in R3 is one of the waits the compiler inserts between dependent instructions; the required wait states for MFMA are listed in the ISA guide and handled by the compiler, which is a good reason not to write MFMA kernels in inline assembly.

Worked example

How many MFMAs for a 4096 × 4096 × 4096 FP16 GEMM? Each 32x32x8 instruction does 32·32·8 = 8,192 multiply-adds = 16,384 FLOP. The GEMM does 2·40963 = 137,438,953,472 FLOP. Instructions: 137,438,953,472 / 16,384 = 8,388,608 MFMAs, i.e. (4096/32)·(4096/32)·(4096/8) = 128 · 128 · 512 = 8,388,608. Each 32 × 32 output tile needs 512 of them in sequence, which is exactly Listing 1's K loop with K = 4,096.

A tolerance for K = 520 (Listing 1's test). Listing 1's inputs are multiples of 1/64 between −0.78 and 0.78, so they are exact in FP16 and only the FP32 sum rounds: tolerance K·2−24·S = 520 · 5.96 × 10−8 · S ≈ 3.1 × 10−5·S per element. With random inputs that must be rounded to FP16, add 2·2−11 + 2−22 ≈ 9.8 × 10−4, which dominates.

Reading the layout (as assumed). Lane 37, element 2 of A: row 37 mod 32 = 5, k = 4·⌊37/32⌋ + 2 = 6, so A[5][6]. Element 13 of C in lane 37: row 8·3 + 4·1 + 1 = 29, column 5. If the layout were wrong, the program's test would report mismatches such as row 29, column 5 first.

Where the analogy breaks


    

  • The tray machine sits in a corner, separate from the helpers. Matrix cores are part of each compute unit and are driven by an instruction in the same wave's instruction stream, with operands in the wave's own registers.
    • 

  • "One push" suggests one cycle. An MFMA has a latency of many cycles and the compiler must keep enough independent work around it; the number is in the ISA guide, not in the story.
    • 

  • In the story, wrong placement is a helper's mistake that someone might notice. With a wrong operand layout nothing fails: the instruction runs and produces a wrong matrix; only a full comparison with a reference shows it.
    • 

  • The story's machine takes "short numbers". Several formats exist (FP16, BF16, FP32, integer types and others per generation), each with its own instruction names and shapes; the story hides that you choose the format.
    • 




Common mistakes and debugging


    

  • Symptom: "needs target feature mai-insts". Cause: compiling an MFMA builtin for a target without matrix-core instructions (gfx1030, gfx1100 in R2). Fix: a per-target path (WMMA on RDNA3, FMA fallback elsewhere) guarded correctly.
    • 

  • Symptom: fast enough? correct, but no faster than FMA code. Cause: the matrix path is not compiled in (the forensic lab). How to find it: grep -c v_mfma on the disassembly for every target you ship. Fix: correct the guard; add the grep to CI.
    • 

  • Symptom: wrong results in a regular pattern of rows. Cause: wrong operand layout. How to find it: fill A with the identity and B with distinct values; print C. Fix: take the layout from the ISA guide or the Matrix Instruction Calculator.
    • 

  • Symptom: E7 tolerance test fails by a small margin. Cause: tolerance relative to |result| instead of S, or inputs not FP16-exact in the CPU reference. Fix: derive the tolerance as in Layer 3.
    • 

  • Symptom: occupancy dropped after adding MFMA tiles. Cause: AGPR plus VGPR use. How to find it: .agpr_count, .vgpr_count, accum_offset in the metadata. Fix: fewer accumulator tiles per wave, or accept it after measuring.
    •

Summary


    

  • An MFMA instruction is a wave-wide D = A × B + C on a fixed block shape and type; v_mfma_f32_32x32x8f16 holds 4 + 4 FP16 inputs and 16 FP32 accumulators per lane.
    • 

  • MFMA exists on CDNA targets (gfx908, gfx90a, gfx942 in this build); RDNA3 has WMMA; gfx1030 has neither.
    • 

  • The operand layout decides correctness; it is unverified here and must come from the ISA guide or the Matrix Instruction Calculator.
    • 

  • Accumulators can live in AGPRs; the metadata shows .agpr_count and accum_offset.
    • 

  • E7 tolerance: (2u + u2 + K·2−24)·Σ|ab|, with u = 2−11 (FP16) or 2−8 (BF16).
    • 

  • The disassembly is the only proof that matrix cores are used; check it for every target you ship.

Forensic lab answer key


Observation. Built for gfx942, linGemm contains 2 v_fma_mix_f32 (mixed-precision FMAs, the fallback loop) and 0 v_mfma. Built for gfx90a from the same source, it contains v_mfma_f32_32x32x8f16. For gfx942 the compiler defines __gfx942__ (R7).


Root cause. Line 14: the guard tests __gfx908__, __gfx90a__ and __gfx940__, but the Makefile builds for gfx942, where only __gfx942__ is defined. The preprocessor silently takes the #else branch. The fallback is correct, so every test passes: only performance and the disassembly reveal it.


Wrong answers and why. "gfx942 has no MFMA": the targets run compiles the builtin for gfx942 (R2). "Wrong target in the Makefile": the target is right; the source does not recognise it.


Fix. Add __gfx942__ (and check the full list of CDNA targets in the HIP documentation), or better, test a feature rather than a list of names where the toolchain offers one. Prevention: make the fallback an explicit, named choice, and add #error for unknown AMD targets in performance-critical files; add a CI step that greps the disassembly for v_mfma per target (the mini-project). How the evidence was produced: slow_gemm.hip.inc built with --cuda-device-only -S for both targets; macros from -dM -E.
