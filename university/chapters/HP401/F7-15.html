Story hook

At closing time the great kitchen hall counts what it used today. Every helper has a little tally of onions peeled. Yusuf, a new helper, suggests that everyone walk to one shared counter and click it once per onion. The queue at the counter reaches the door.

Old Marisol shows the hall's way. Each row of helpers first adds up its own tallies by passing numbers sideways, neighbour to neighbour, until the last helper of the row holds the row's total. Then each table adds its rows. Only one number per table goes to the counter. The next morning the same trick, with one twist, tells every helper where to put their onions on a long shelf: everyone needs the sum of all tallies before theirs, a running total.

Marisol does not invent the trick anew each day. She takes the hall's recipe book down from the shelf, written by the people who built the hall, and follows the page called "sum" or "running total". This chapter is about that trick (reduction and scan), about the recipe books on AMD GPUs (rocPRIM and hipCUB), and about the subtle way that the same recipe gives a slightly different answer in a different hall.

What you will be able to do

  • Write a wave-width-agnostic block reduction and block scan in HIP that is correct on wave64 (CDNA), wave32 (RDNA) and warp32 (NVIDIA), and read in the AMD ISA what the compiler made of it.
  • Explain the two-phase temporary-storage calling pattern of device-wide primitives (CUB, hipCUB, rocPRIM) and use it correctly.
  • Explain single-pass scan with decoupled look-back and trace it by hand for a few tiles.
  • Justify a tolerance for floating-point reductions from the order of operations, and explain why two correct GPUs can disagree.
  • Measure (on an AMD GPU) your reduction and scan against hipCUB/rocPRIM, as the E3 and E4 acceptance tests require.
  • Diagnose a "wrong on AMD" report that is really a wrong test.
Jargon box
Reduction
Simple words: combining many values into one, such as a sum or a maximum. Analogy: every row adds its tallies, then every table, until one number is left. Precise: applying an associative binary operator (sum, max, min, logical or) over a sequence to produce one value; on a GPU done as a tree inside waves, then across waves, then across blocks. D5 H2
Scan (prefix sum)
Simple words: a running total: each output is the sum of the inputs before it. Analogy: each helper learns how many onions all the helpers before them peeled, so they know where their onions go on the shelf. Precise: an inclusive scan's i-th output includes the i-th input; an exclusive scan's does not (CUB's header comment defines both this way). H2
rocPRIM
Simple words: AMD's library of ready-made parallel building blocks for HIP. Analogy: the AMD hall's own recipe book. Precise: a ROCm library of device-wide, block-level and wave-level primitives (reduce, scan, sort, histogram and others) written for AMD GPUs. D3
hipCUB
Simple words: a library with CUB's names, so code written for CUB ports easily. Analogy: a translated copy of the NVIDIA hall's recipe book whose pages point at the AMD book. Precise: a thin HIP wrapper that exposes a CUB-style interface; on AMD it calls rocPRIM, on NVIDIA it calls CUB (see the unverified box in Layer 2 for the details this build could not check). D3
Temporary storage (two-phase call)
Simple words: scratch memory that a library routine needs, which you must give it. Analogy: before cooking, you ask the recipe how many bowls it needs, fetch them, then cook. Precise: device-wide primitives take a pointer and a size; called with a null pointer they only write the required size; called again with an allocation of that size they do the work. H2
Decoupled look-back
Simple words: a way for each block of a scan to find the total of all earlier blocks without a second pass over the data. Analogy: each table posts a note "my own total is ready" or "my running total is ready"; a table looks at the notes of the tables before it and stops at the first running total. Precise: the single-pass prefix-scan algorithm of Merrill and Garland in which every tile publishes its aggregate and later its inclusive prefix, and successors accumulate predecessors' values until they meet an inclusive prefix; CUB's device scan header says its device-wide scan implements it. D4 H2
Run-to-run determinism
Simple words: getting exactly the same bits every time you run the same thing on the same machine. Analogy: the same hall, same rows, same order of adding: the same total to the last digit. Precise: CUB's header promises it for floating-point sums on the same GPU, and warns that devices with a different compute capability may give different results because tile sizes differ. H2

Layer 1 — the kid explanation

A reduction is adding up a long list. A scan is writing down the running total after each item. Both look like jobs for one person with a pencil. On a GPU they are jobs for a whole hall: the helpers of a row pass numbers sideways, so after a few passes the last helper of the row has the row's total. Then the tables add their rows. Then one number per table goes on.

Because this pattern is needed everywhere (counting, sorting, packing results without gaps), the people who build the GPU write it once, very carefully, and put it in a library. On AMD GPUs that library is rocPRIM, and hipCUB gives it the same names as NVIDIA's CUB. You still learn to write the pattern yourself, because you need to understand what the library does, check it, and sometimes fuse it into your own kernel.

Layer 2 — the student explanation

Inside a wave: shuffles

Within a wave, lanes exchange registers with cross-lane operations (F7-12). In HIP 5.7, __shfl_up(var, delta, width) returns the value of the lane delta below, with width defaulting to warpSize, and in device code warpSize is defined as the constant __AMDGCN_WAVEFRONT_SIZE, which the compiler sets per target (64 for gfx90a, 32 for gfx1100, as the isa_scan run shows). H1 R3 An inclusive scan in a wave takes log2(warpSize) steps: at step d = 1, 2, 4, … every lane with index ≥ d adds the value d lanes below (the Hillis–Steele pattern taught in F6-15). D5 A reduction is the same with __shfl_down, ending with the total in lane 0.

The loop bound must be warpSize, never 32. Code written for 32 lanes and run on wave64 silently scans each half separately; that is the forensic lab of HP301. Listing 1 uses warpSize everywhere and sizes its LDS array for the narrowest wave (32 lanes), so the same source works for 64-lane and 32-lane waves.

Inside a block: one value per wave in LDS

After the wave scan, the last lane of every wave holds the wave's total. It writes it to an LDS array, the block synchronises, wave 0 scans that small array, the block synchronises again, and every lane adds the scanned total of the waves before it. With 256 threads that is four totals on wave64 and eight on wave32: in the generated code, the gfx90a build has 6 + 2 = 8 ds_bpermute_b32 instructions and the gfx1100 build 5 + 3 = 8 (R3). R3

Across blocks: the device-wide primitives

A block cannot see another block's LDS, and blocks have no cheap barrier across the grid (F6-12). Device-wide reduction therefore uses either a second kernel over the block totals, atomics, or a single pass in which blocks communicate through global memory. Writing this well, for every size, type and GPU, is the work a library does. CUB, installed in this build as version 2.0.1, documents the calling convention in its headers: every device-wide algorithm takes d_temp_storage and temp_storage_bytes; when d_temp_storage is null, the call only writes the required size and does no work. H2 Listing 2 uses exactly this with cub::DeviceReduce::Sum and cub::DeviceScan::ExclusiveSum; it was built for real and printed CUB_VERSION 200001 before stopping at the first allocation (R2). R2

Port Listing 2 to hipCUB by changing the include, namespace and runtime calls, build it, and record the header version you used.

Floating point: the order is part of the answer

Integer addition is associative, so every order gives the same sum. Floating-point addition rounds after every operation, so the order changes the result (MA302; IEEE 754 defines each operation's rounding, not the order a program chooses). D6 A GPU reduction adds in an order set by the grid size, the block size and the wave width. Listing 3 replays four such orders on the CPU for the same 16,777,216 floats: wave width 32 and 64 with 1,024 blocks give different last digits, and so do different block counts; the integer sums forwards and backwards agree exactly (R4). R4 CUB's header states the consequence for libraries: results are reproducible run to run on the same GPU, but may differ on a GPU of another compute capability because tile sizes differ. H2 The test of a float reduction is therefore a tolerance, never equality with a "golden" number from another GPU.

Layer 3 — the engineer's depth

Single-pass scan with decoupled look-back

The classic device scan is three passes: reduce each tile, scan the tile totals, then scan each tile again with its offset. That reads the input twice. CUB's header describes its device scan as single-pass: about 2n data movement (n reads, n writes), achieved by decoupled look-back. H2 Each tile keeps a status word: X (nothing yet), A (aggregate of this tile only) or P (inclusive prefix up to and including this tile). A tile reduces its data, publishes A, then reads its predecessors from the nearest backwards: it adds every A it sees, keeps going, and stops at the first P. It then publishes P = (sum found) + (own aggregate) and writes its outputs. D4 Because many tiles publish A early, a tile rarely waits for the full chain; that is the "decoupling".

Listing 4 models this on the CPU with a scheduler that gives one step at a time to a random live tile, so tiles really interleave. It passes the E4 size list (1, 2k−1, 2k, 2k+1 and a large size) for random, sorted, reverse-sorted and all-equal inputs, and reports how many status words each tile read and how often a tile had to wait on an X (R5). R5 The model's scheduler is deliberately pessimistic: every tile may start at any time. On a GPU, tiles that wait on a predecessor which has not been scheduled yet could wait forever; the paper's answer is to hand out tile numbers in the order blocks actually start (a global counter), rather than to use blockIdx.x. D4

Watch out

A look-back scan relies on the status word and its value becoming visible together, in order, to other blocks. That needs the memory-model guarantees of the platform (fences or atomics with the right ordering). The CPU model in Listing 4 does not test this at all, because it runs on one thread. Do not write your own look-back scan for production without reading the HIP documentation on memory fences and the paper; use the library.

A tolerance you can defend

For a sum computed as a tree whose longest chain of additions has depth d, the first-order error bound is |error| ≤ d · u · Σ|xi|, with u = 2−24 for FP32 round-to-nearest. D7 Listing 3 prints this bound for each order: 16,777,216 for the sequential float loop (a useless bound, and indeed its error is the largest of the GPU-like orders), and depths around 600–1,100 for the GPU orders. The observed errors are far below the bounds because random signs cancel; the bound is what you can prove, not what you will see. E3's acceptance test asks for "your stated tolerance" against a Kahan-summed reference: state it from this bound, relative to Σ|x|, not relative to the result (whose size can be close to zero). C1

Library or own kernel?

Use the library for stand-alone reductions, scans, sorts and histograms: it is tuned per architecture and tested on sizes you would forget. Write your own when the primitive is a small step inside a larger kernel (a block scan inside a stream-compaction kernel, a wave reduction inside a softmax): then you want a block-level or wave-level primitive, which rocPRIM and CUB also offer, or your own Listing 1. In both cases the E3/E4 rule holds: measure against the library on the same GPU with the same harness (F7-19). C1

How the hardware actually does it

The isa_scan run shows what the compiler made of __shfl_up for both AMD targets: ds_bpermute_b32, a cross-lane permute that goes through the LDS hardware without allocating LDS, preceded by index arithmetic and followed by a wait on lgkmcnt (F7-13). R3 D2 Because warpSize is a compile-time constant on AMD, the loop is fully unrolled: six permute steps on gfx90a, five on gfx1100. The two __syncthreads() became two s_barrier. The kernel uses 32 bytes of LDS (eight int slots) on both targets. The vendor ISA guide (D2) also describes DPP (data-parallel primitives) modifiers that let some cross-lane moves happen inside a VALU instruction; whether rocPRIM uses them for its wave scans on your GPU is something to read in its source, not to assume.

Worked example

A wave scan by hand (8 lanes for readability; a real wave has 32 or 64). Inputs: 3, 1, 4, 1, 5, 9, 2, 6.

StepRuleLanes 0–7 after the step
startown value3, 1, 4, 1, 5, 9, 2, 6
d = 1lane ≥ 1 adds the old value of lane − 13, 4, 5, 5, 6, 14, 11, 8
d = 2lane ≥ 2 adds the old value of lane − 23, 4, 8, 9, 11, 19, 17, 22
d = 4lane ≥ 4 adds the old value of lane − 43, 4, 8, 9, 14, 23, 25, 31
exclusiveinclusive − own input0, 3, 4, 8, 9, 14, 23, 25

Three steps for 8 lanes; log2 64 = 6 steps for wave64. "Old value" matters: all lanes read before any writes, which the shuffle guarantees because every lane's __shfl_up happens in the same instruction.

A look-back by hand (Figure 2). Tile aggregates 10, 7, 5, 8. Tile 0 publishes P 10. Tile 1 reads P 10, publishes P 17. Tile 2 has published only A 5 when tile 3 looks back: tile 3 adds 5, moves to tile 1, reads P 17, adds it and stops. Its exclusive prefix is 5 + 17 = 22 (check: 10 + 7 + 5 = 22) and it publishes P 22 + 8 = 30.

Temporary storage. Listing 2 queries both algorithms and allocates the larger size once, so one buffer serves both calls. This is safe only because the calls run one after the other on the same stream.

Where the analogy breaks


    

  • Helpers passing numbers "sideways" suggests a walk along the row taking time per step. A shuffle moves all 64 values at once in one instruction; what costs time is the number of steps (log2 of the width), not the distance.
    • 

  • The recipe book suggests the library always gives the same answer. For floating point it gives a reproducible answer on the same GPU, and possibly a different one on another (H2): the book's page depends on the hall.
    • 

  • In the story, tables wait politely for earlier tables. On a GPU, a block that waits for a block which has not started can wait forever; real look-back scans number their tiles in start order to avoid that (D4).
    • 

  • "Recipe book written by the builders" hides that rocPRIM and CUB are open-source projects with versions and bugs; you record the version you used like any other dependency.
    • 




Common mistakes and debugging


    

  • Symptom: the sum is right on NVIDIA and about half (or garbage) on CDNA. Cause: a shuffle loop that starts at 16 or uses % 32. How to find it: grep for literal 32 and 16 near shuffles (F7-20 has a scanner). Fix: warpSize, and LDS arrays sized for the narrowest wave.
    • 

  • Symptom: a library call returns success but the output is unchanged. Cause: only the size query was made (null temporary storage). How to find it: count the calls: each algorithm is called twice. Fix: allocate and call again.
    • 

  • Symptom: random wrong results when two library calls overlap. Cause: one temporary buffer shared by calls on different streams. Fix: one buffer per stream, or order the streams with events.
    • 

  • Symptom: a float test fails "only on the new GPU". Cause: an equality test against a number recorded on another GPU. How to find it: compare the difference with the bound of Layer 3. Fix: a tolerance relative to Σ|x| (the forensic lab).
    • 

  • Symptom: integer sum overflows for large inputs. Cause: 32-bit accumulator. Fix: accumulate in 64 bits; CUB lets the output type differ from the input type (check hipCUB's equivalent).
    •

Summary


    

  • Reduction and scan are trees: inside a wave with shuffles, across waves through LDS, across blocks through global memory.
    • 

  • Use warpSize: on AMD it is a per-target compile-time constant (64 for gfx90a, 32 for gfx1100), and the compiler unrolls accordingly.
    • 

  • Device-wide library calls follow the two-phase convention: size query with a null pointer, then the real call.
    • 

  • Single-pass scan with decoupled look-back reads the input once; tiles publish A, then P, and look back to the first P.
    • 

  • Float reductions depend on the order; test them with a tolerance relative to Σ|x|, never equality across GPUs.
    • 

  • rocPRIM and hipCUB were not available in this build: their identifiers are in an unverified box to check against their documentation.

Forensic lab answer key


Observation. The two results differ by 31.248283 − 31.248207 = 0.000076. Their errors against the Kahan reference (31.249278) are −0.000994 and −0.001070: both are of the same size, the AMD-order result is not noticeably worse, and both are about 10−10 of Σ|x| (8,387,434.698), far inside the bound of about 549.


Root cause. The test is wrong, not the GPU: it requires bit-equality with a value produced by a different order of additions on another GPU. The wave width (32 versus 64) changes the shuffle tree, so the last digits change. CUB documents that float results may differ across devices with different tile sizes (H2).


Wrong answers and why. "hipCUB is buggy": both orders are equally close to the reference; a bug would show an error far larger than the bound or a dependence on the input pattern. "Use double on AMD": changes the numbers but not the principle; the test would still compare across orders.


Fix. |got − ref| ≤ d · 2−24 · Σ|x| with a Kahan or double reference computed on the host, and d from the launch configuration (or a documented, slightly larger constant). Prevention: float tests never compare against numbers recorded on a GPU; every tolerance is written down with its derivation. How the evidence was produced: Listing 3, seed 2026, uniform values in [−1, 1).
