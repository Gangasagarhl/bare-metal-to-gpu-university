Story hook

The great kitchen hall has a sister hall in another town, built by a different company. The recipe cards are written in the same language, and almost every card works in both halls. But the sister hall's rows have sixty-four helpers instead of thirty-two, its tables are a different size, and its tray machine takes different trays.

Priya copied her best card from the first hall to the second without changing anything. The food came out right. It was just strangely slow, and when she walked through the sister hall she saw why: at every table, one row of sixty-four helpers was working with only thirty-two pairs of hands busy, the other half standing still, because the card said "one row of thirty-two per table".

Writing one set of recipe cards that is correct in both halls is portability. Writing cards that are also fast in both halls is performance portability, and it is the last skill of this course: one source tree, two vendors, and an honest table that shows how close to each vendor's own library you got.

What you will be able to do

  • Build one HIP source for AMD wave64, AMD wave32 and NVIDIA warp32, and list the code objects inside an AMD binary.
  • Explain which macros exist in the host pass and in each device pass, and where per-target tuning decisions must therefore be made.
  • Write warp-size-independent kernels with 64-bit lane masks and a per-platform ballot wrapper.
  • Scan a code base for warp-size assumptions and fix them.
  • Produce the E9 table: each kernel's percentage of the vendor library on both GPUs, with one sentence per kernel on why it differs.
  • Diagnose a kernel that is correct on both vendors but leaves half of each AMD wave idle.
Jargon box
Performance portability
Simple words: one program that is not only correct but also reasonably fast on different GPUs. Analogy: one set of recipe cards that works well in both halls. Precise: the property that a single source achieves a stated fraction of each platform's achievable performance (here: the vendor library on each GPU), measured per kernel; correctness portability is the weaker property of correct results everywhere. C1
Host pass and device pass
Simple words: the compiler reads a HIP file several times: once for the CPU part and once for each GPU target. Analogy: the same card read once by the hall manager and once by each kind of row. Precise: in single-source GPU compilation the host code is compiled once and the device code once per offload target, each pass with its own predefined macros (for example __gfx90a__ and __HIP_DEVICE_COMPILE__ only in the gfx90a device pass). R1 D1
Fat binary (code object bundle)
Simple words: one program file that carries machine code for several GPUs. Analogy: one recipe folder with a card for each kind of hall. Precise: an executable whose GPU section bundles one code object per offload target (listed in this build as hipv4-amdgcn-amd-amdhsa--gfx90a and --gfx1100), from which the runtime loads the one matching the GPU. R2 D2
Lane mask (64-bit)
Simple words: a number with one bit per lane of a wave, saying which lanes answered "yes". Analogy: a row of 64 hands, each up or down. Precise: in HIP, __ballot returns unsigned long long; on wave64 all 64 bits are used, so storing it in 32 bits loses lanes 32–63 (F7-12). H1
Tuning table
Simple words: the chosen block sizes and tile sizes for each GPU, kept in one place. Analogy: a small sheet per hall saying how big the trays and rows should be. Precise: per-device parameters selected at run time from device properties (or per device pass for device-only constants), with the measured evidence for each choice. C1
Idle lanes
Simple words: parts of a wave that have nothing to do. Analogy: helpers in a row standing still. Precise: lanes whose bit in the execution mask is off for an instruction; a workgroup of 32 work-items on a wave64 target occupies one wave with at most 32 active lanes. R5 D3

Layer 1 — the kid explanation

A program that is correct on two kinds of GPU is a good start. A program that is fast on both is harder, because the GPUs are built differently: different row sizes, different tables, different special machines. So you keep one recipe, but you let a few numbers change per GPU: how many helpers per table, how big the trays are.

Then you check how close you came to each GPU maker's own best recipe. You write that down in a table for both GPUs, with a sentence explaining every difference.

Layer 2 — the student explanation

Three builds of one source

Listing 1 is one HIP file. With hipcc --offload-arch=gfx90a --offload-arch=gfx1100 it becomes one executable whose GPU section contains two code objects, one per target, which the fatbin run lists with the LLVM offload bundler (R2). R2 With nvcc -x cu -D__HIP_PLATFORM_NVIDIA__ the same file builds for sm_80 through HIP's NVIDIA headers, which map HIP calls to the CUDA runtime (F7-07); its SASS contains VOTE.ANY, POPC and a 64-bit atomic reduction (RED.E.ADD.64) for the ballot, the popcount and the atomicAdd (R4). R4 Both builds' runs stop at the first runtime call: no GPU here.

What each pass knows

The macros run prints the predefined macros of each pass (R1). The hipcc host pass defines __HIP_PLATFORM_AMD__ and also __AMDGCN_WAVEFRONT_SIZE 64, but no __gfx…__ macro and no __HIP_DEVICE_COMPILE__. The gfx90a device pass adds __gfx90a__ and __HIP_DEVICE_COMPILE__ with wave size 64; the gfx1100 device pass adds __gfx1100__ with wave size 32. For CUDA, __CUDA_ARCH__ is undefined in the host pass and 800 in the sm_80 device pass. R1 Three rules follow:

  • Device code may specialise on target macros or on warpSize, which in HIP 5.7 device code is the per-pass constant __AMDGCN_WAVEFRONT_SIZE. H1
  • Host code must not use __AMDGCN_WAVEFRONT_SIZE or target macros to size launches: the host pass is compiled once for all targets, and in this build it saw 64 although the binary also contained a wave32 target.
  • Host decisions that depend on the GPU are made at run time from hipDeviceProp_t (warpSize, multiProcessorCount, gcnArchName), as Listing 1's pickTuning does. H1

A portable ballot

HIP's __ballot returns a 64-bit mask on AMD (H1). The first version of Listing 1 used it directly on both platforms. Built through HIP 5.7's NVIDIA path for sm_80, it failed: nvcc warned that __ballot is deprecated and "not valid on compute_70 and above", and ptxas stopped with "Instruction 'vote' without '.sync' is not supported on .target sm_70 and higher" (R3). R3 Listing 1 therefore wraps the ballot: __ballot_sync(0xFFFFFFFFu, p) on NVIDIA, __ballot(p) on AMD, both returned as unsigned long long. This is the honest shape of portable code: a small, named, tested per-platform layer, not #if scattered through kernels.

Watch out

The full mask 0xFFFFFFFFu in the NVIDIA branch asserts that all 32 lanes of the warp reach the ballot, which is true in Listing 1 (no early return before it). In code with divergent paths the mask must name exactly the participating lanes; see the CUDA Programming Guide's warp vote functions and F6-15. The literal is also exactly what the hazard scanner of Listing 2 flags: here it is deliberate and inside the NVIDIA-only branch.

Finding hidden assumptions

BR-02 lists the traps: hard-coded 32, 32-bit ballot masks, tuning parameters copied from NVIDIA. C2 Listing 2 is a small scanner that reads a source file and flags lines matching seven patterns. On a hipified reduction (hazards.in) it flags 8 lines: the WARP_SIZE 32 constant and its two uses, a shuffle tree starting at 16, lane and warp indices computed with % 32 and / 32, a ballot stored in unsigned int, and a 0xffffffff mask (R6). R6 A scanner finds patterns, not bugs; every hit is read by a person.

Where performance differs, and what to parameterise

Everything in this course that made a kernel fast was architecture-dependent: the wave width (shuffle steps, wave totals, idle lanes), LDS size and banks (tile shapes and padding), registers per lane (thread tiles and occupancy), and the matrix instructions (MFMA on CDNA, WMMA on RDNA3, MMA on NVIDIA, each with its own shapes). C3 A portable code base makes these explicit:

  • Device constants derived from warpSize or from per-pass macros, in one header (the F7-15 project).
  • A tuning table selected at run time per device (block size, grid size, tile instance), with the measurement that justifies each entry.
  • Algorithm variants where one source cannot be fast everywhere (a matrix-core path per family, a fallback that fails loudly when a matching target is unknown; the F7-17 forensic lab).
  • Libraries where they exist: hipCUB, rocPRIM, rocBLAS and hipBLASLt (and, on NVIDIA, CUB and cuBLAS) carry their own tuning.

How the hardware actually does it

When an AMD binary starts, the HIP runtime finds the GPU's target name and loads the matching code object from the bundle; a bundle without a matching target cannot run on that GPU. D1 Within the running kernel, a workgroup is split into waves of the target's width (F7-08). A workgroup of 32 work-items on a wave64 target therefore occupies one wave in which at most 32 lanes are active; the metadata of Priya's kernel in the forensic lab shows exactly this combination (.max_flat_workgroup_size: 32, .wavefront_size: 64) (R5). R5 D3 On NVIDIA the same 32-thread block fills its warp completely, which is why such code can look fine there.

Worked example

Lane utilisation of a block size. Active lanes / allocated lanes per workgroup = B / (⌈B/W⌉ · W) for block size B and wave width W.

Block size BW = 32W = 64
3232/32 = 100 %32/64 = 50 %
9696/96 = 100 %96/128 = 75 %
192100 %192/192 = 100 %
256100 %100 %

Rule: choose block sizes that are multiples of 64 when the code may run on wave64; they are then also multiples of 32. This is a lane count, not a speed: whether 50 % lane use halves the speed depends on what limits the kernel (a memory-bound kernel may lose less), and is measured.

Which pass sees what. A host-side const int threads = 4 * __AMDGCN_WAVEFRONT_SIZE; in a binary built for gfx90a and gfx1100 gives 256 in the host pass (R1 shows the host pass sees 64), which is a whole number of waves on both targets by luck; a host-side waves = threads / __AMDGCN_WAVEFRONT_SIZE gives 4, wrong for gfx1100 (8 waves). Use prop.warpSize at run time instead.

Where the analogy breaks


    

  • "Sister hall built by another company" suggests two fixed designs. AMD alone has wave64 CDNA, RDNA with wave32 and wave64, and different matrix instructions per generation; "two vendors" is at least three or four targets.
    • 

  • Idle helpers in the story are visibly wasted. Idle lanes do not always cost time in proportion: a kernel limited by memory bandwidth may lose little; only measurement tells.
    • 

  • The story's recipe cards are read the same way in both halls. A HIP file is read several times by the compiler, and the "manager's" reading (the host pass) does not know which hall it is in (R1).
    • 

  • In the story, comparing with each hall's master team is natural. The two reference libraries differ in maturity per operation and data type, so a lower percentage on one vendor may reflect the reference as much as your kernel; the explanation sentence must say which.
    • 




Common mistakes and debugging


    

  • Symptom: correct on NVIDIA, wrong counts on AMD. Cause: ballot in 32 bits, or lane maths with 32. How to find it: Listing 2; per-lane debug output on wave64. Fix: 64-bit masks, warpSize.
    • 

  • Symptom: build error through the NVIDIA path about vote without .sync. Cause: legacy warp function on sm_70+ (R3). Fix: a platform wrapper with the _sync variant.
    • 

  • Symptom: "no kernel image" or similar error on a new AMD GPU. Cause: its target is not in the bundle. How to find it: list the bundle as in the fatbin step; compare with rocminfo. Fix: add --offload-arch for it.
    • 

  • Symptom: correct everywhere, slow on AMD only. Cause: block sizes or tiles tuned for 32 lanes; a matrix path not compiled for the target. How to find it: metadata (.max_flat_workgroup_size, .wavefront_size), v_mfma count. Fix: multiples of 64; per-target paths that fail loudly.
    • 

  • Symptom: host code computes the wrong number of waves for one target. Cause: host use of __AMDGCN_WAVEFRONT_SIZE. Fix: prop.warpSize.

Forensic lab answer key


Observation. The kernel promises at most 32 work-items per workgroup (__launch_bounds__(kThreads) → .max_flat_workgroup_size: 32) and is compiled for 64-lane waves (.wavefront_size: 64) (R5). The launch uses kThreads = 32.


Root cause. Each workgroup is a single wave64 with at most 32 active lanes: 50 % lane utilisation in every vector instruction, plus a workgroup's worth of LDS (1,024 bytes for the 256 bins) and setup per 32 work-items. On NVIDIA a 32-thread block fills one warp exactly, so the same constants look fine there.


Wrong answers and why. "LDS atomic contention": possible as a second factor, but it would affect both vendors and is not what the metadata shows; a profiler's LDS counters would decide. "Too few workgroups": the grid size is a parameter (blocks) and is not shown to be small.


Fix. kThreads = 256 (a multiple of 64), which also changes the strides of the bin loops (they use kThreads, so they stay correct) and the launch bounds; rerun the histogram tests and remeasure on both GPUs. Prevention: none of Listing 2's seven rules flags this file, because the 32 hides behind the name kThreads (rule 6 only matches a literal 32 in the launch); add a rule for named constants set to 32 and for block sizes that are not multiples of 64 (lab step 4); in review, check .max_flat_workgroup_size against .wavefront_size. How the evidence was produced: half_lanes.hip.inc compiled for gfx90a with --cuda-device-only -S.
