Story hook

Every year the great kitchen hall holds a friendly contest: who can make a hundred pastries fastest? The hall's own master pastry team sets the reference time, and every apprentice table writes its time as a percentage of the master's.

This year Sam's table reported 360 % of the master's speed, more than three times faster than the people who designed the hall. Everyone was excited, except old Ines. She asked two questions. "Did you time the master team on its first batch of the morning, while it was still taking out its trays and lighting its ovens?" And: "Did you time yourselves the same way, the same number of times?" Sam went quiet. When both teams were timed the same way, after warming up, Sam's table was at 96 %. Still very good, and true.

This chapter is about the master team of AMD GPU matrix multiplication, rocBLAS and hipBLASLt, and about Ines's two questions, which turn a percentage into a fact.

  • Diagnose a benchmark report whose percentage is impossible.
Jargon box
BLAS
Simple words: a standard list of linear-algebra routines with standard names and arguments. Analogy: the hall's standard recipe names that every team understands. Precise: Basic Linear Algebra Subprograms: level 1 (vector), level 2 (matrix-vector) and level 3 (matrix-matrix, including GEMM) routines with column-major storage and leading-dimension arguments; vendor libraries (cuBLAS, rocBLAS) implement this interface for GPUs. D3 H1
rocBLAS
Simple words: AMD's BLAS library for its GPUs. Analogy: the master pastry team. Precise: the ROCm implementation of BLAS for AMD GPUs, used through a handle and BLAS-style calls (exact names in the unverified box). D1
hipBLASLt
Simple words: AMD's flexible matrix-multiply library with many options. Analogy: the master team's special kitchen for unusual orders. Precise: a ROCm library for GEMM with descriptors for operation and matrix layouts, extra epilogue operations, workspace, and algorithm selection by heuristics; modelled on NVIDIA's cuBLASLt, whose installed header in this build declares cublasLtMatmul, cublasLtMatmulDescCreate, cublasLtMatrixLayoutCreate and cublasLtMatmulAlgoGetHeuristic. D2 H2
Leading dimension
Simple words: the distance in memory between the start of one column and the next. Analogy: the length of a shelf, even if only part of it holds the tray you use. Precise: in column-major storage, element (i, j) of X is at X[i + j · ldX] with ldX ≥ the number of rows; it lets a routine work on a sub-matrix. D3
Percentage of reference
Simple words: how fast your kernel is compared with the library, as a percentage. Analogy: your table's time compared with the master team's. Precise: 100 · treference / tyours (equivalently the ratio of FLOP/s), both measured with the same harness, data type, sizes and GPU; the target X is written before measuring. C1
Warm-up
Simple words: running something a few times before you start timing it. Analogy: letting the ovens heat up before the stopwatch starts. Precise: untimed runs that absorb one-time costs (library initialisation, workspace allocation, code loading, cache and clock state) so that timed runs measure the steady state; required by the curriculum's protocol. C1

Layer 1 — the kid explanation

To know whether your matrix multiply is fast, you compare it with the best one you can get on the same GPU: the vendor's library. You do not compare with the number on the box, because that number is a ceiling, not something any real program reaches.

Comparing is only fair if you measure both the same way. Both get a few practice runs first. Both are timed many times, and you take the middle value. Then the percentage means something.

Layer 2 — the student explanation

Why the library is the reference

The curriculum's rule for every Track E performance milestone: "Reference: the vendor library on the same GPU, same data type, same sizes, measured by the same harness. Peak numbers from datasheets are context, not the target." Targets are written as "reaches X % of the reference", with X chosen before measuring and never lowered afterwards without the owner's approval. C1 For GEMM on AMD the reference is rocBLAS for FP32 (E6) and hipBLASLt or rocBLAS for mixed precision (E7). The library has been tuned per GPU by its authors, so "X % of rocBLAS on this GPU" is a hard, reproducible yardstick; a datasheet peak is neither measured nor reachable.

Column-major, and the transpose trick

BLAS routines use column-major storage: element (i, j) of an m-row matrix X is X[i + j·ldX]. D3 C++ programs usually store row-major. A row-major M × K array, read as column-major, is the K × M transpose. Since (A·B)T = BT·AT, you can compute a row-major C = A·B by asking the column-major routine for CT = BT·AT: pass B first, then A, swap M and N, and use the row lengths (N for B and C, K for A) as leading dimensions. No copies, no transposes. Listing 1 does this with a small column-major GEMM written in the BLAS argument order and checks every element against the row-major definition: 0 mismatches (R1). R1 Listing 2 makes the same call to cuBLAS (cublasSgemm, which the installed cuBLAS 12.0.2 header maps to cublasSgemm_v2); it built and linked in this build and stopped at the first allocation (R2). What the "Lt" libraries add

The installed cuBLASLt header shows the structure hipBLASLt follows: a matmul descriptor (operation, compute type, epilogue), one layout object per matrix (type, rows, columns, leading dimension, order), a preference object whose CUBLASLT_MATMUL_PREF_MAX_WORKSPACE_BYTES attribute defaults to 0, "no workspace allowed", a heuristic query that returns candidate algorithms, and cublasLtMatmul, which takes the chosen algorithm and a workspace. Epilogues such as CUBLASLT_EPILOGUE_BIAS fuse a bias addition into the GEMM. H2 Two consequences for benchmarking follow directly: the workspace you allow changes which algorithms are eligible (so record it), and the heuristic's choice is part of what you measure (so record which algorithm ran, if the library tells you).

The protocol

Curriculum 13.4: "warm-up runs, then the median of at least 20 timed runs using device events; fixed clocks if your driver allows it (record the setting); report GB/s or TFLOP/s and the percentage of the reference." C1 GEMM performs 2·M·N·K floating-point operations, so TFLOP/s = 2MNK / (t · 1012). Listing 3 implements the protocol on the CPU (there is no GPU here; on a GPU you replace the steady clock by HIP events around the launch): it warms up twice, times 20 runs, takes the median of the even count as the mean of the two middle values, and prints GFLOP/s and the percentage.

Layer 3 — the engineer's depth

A reference is only a reference when it is built like one

Listing 3 was run twice in this build, and the two runs teach the first lesson of benchmarking. Built by the lab runner with sanitizers and without optimisation, the naive loop and the "reference" loop (unit-stride inner loop) take about the same time, and "mine" even reached 105.4 % (R3). Built with -O2 and no sanitizers, the reference was about twice as fast and "mine" reached 52.3 % of it (R4). R3 R4 Neither number says anything about a GPU; both are measurements of this container's CPU in one run (AH-23). The lesson: build flags, sanitizers, debug modes and clocks are part of the experiment and go in the report.

Traps that inflate a percentage

  • Cold reference. Timing the library's first call, which includes one-time setup (the forensic lab: R5 against R6).
  • Different work. Different sizes, transposes, data type, α/β (β ≠ 0 reads C), or a different compute type (FP32 accumulation versus FP16).
  • Different timing. Host timer around an asynchronous launch without synchronisation; one kernel timed with events, the other with a wall clock that includes the copy.
  • Wrong FLOP count. M·N·K instead of 2·M·N·K, or counting padded sizes for your kernel only.
  • Cherry-picked sizes. One size where your kernel happens to win; E6 asks for 4096 and two more sizes you choose. C1
  • Incorrect fast kernel. A kernel that skips work is fast. Correctness against the library within tolerance comes first.

Explaining the gap

"Explain the gap: every performance milestone ends with a profiler-backed explanation of the remaining gap (memory throughput, issue stalls, occupancy, instruction mix)." C1 For GEMM on AMD, the usual evidence is: does the reference use MFMA where your kernel uses FMAs (disassembly, F7-17); VGPR/AGPR use and occupancy of both (metadata and the profiler, F7-14); LDS bank conflicts; and the share of time in the main loop versus edges for small sizes. Profile the library's kernel too: profilers show its kernel name and resources like yours.

How the hardware actually does it

Why does a first call cost more? A GPU library's first call typically has to load code objects for the GPU, select a kernel, and allocate workspace; the GPU's clocks may also need time to rise from idle. Which of these apply to rocBLAS or hipBLASLt, and how large they are, is not documented in anything this build opened; the forensic lab demonstrates the mechanism with a CPU stand-in whose first call allocates and zero-fills a 64 MiB workspace (R5). R5 On the GPU, time with events recorded on the same stream as the kernel (F6-06, HIP equivalents in F7-03), and synchronise on the stop event before reading the elapsed time.

Where the analogy breaks


    

  • The master team in the story is the fastest possible. A vendor library is very good but not a ceiling: for particular shapes, fused operations or data layouts, your kernel may legitimately beat it; then explain why, with evidence.
    • 

  • The contest suggests one number. Performance depends on size, type and layout; the reference is a curve, and E6 asks for at least three sizes.
    • 

  • "Ovens heating up" makes warm-up sound like a physical effect only. Much of a library's first-call cost is software (loading code, choosing kernels, allocating workspace), which a well-written harness also excludes.
    • 

  • In the story both teams cook the same pastry. A GPU library may choose a different algorithm (and, for mixed precision, a different accumulation) than your kernel; "the same work" must be checked in the call's arguments.
    • 




Common mistakes and debugging


    

  • Symptom: library result is the transpose of what you expect, or garbage. Cause: row-major data passed as column-major without the transpose trick, or wrong leading dimensions. How to find it: test with a small non-square example like Listing 1. Fix: B first, swap M and N, leading dimensions = row lengths.
    • 

  • Symptom: impossible percentage (well above 100 %). Cause: unequal protocol (forensic lab), or different work. Fix: one harness function used for both sides; print the arguments of both calls.
    • 

  • Symptom: percentages change a lot between runs. Cause: too few runs, clocks not fixed, other load on the GPU. Fix: at least 20 runs, median, record clock settings; report the spread too.
    • 

  • Symptom: hipBLASLt returns "not supported" or no algorithm. Cause: workspace 0, or a type/layout combination it does not support. Fix: allow workspace (record how much); check its documentation.
    • 

  • Symptom: your FP16 kernel "beats" the FP16 reference. Cause: the reference accumulates in FP32, yours in FP16 (less work, worse accuracy). Fix: same compute type; tolerance test first (F7-17).
    •

Forensic lab answer key


Observation. "mine" is timed 20 times and the median is reported; "library" is timed exactly once, and that once is its first call (R5).


Root cause. The single library call includes the one-time creation and zero-filling of a 64 MiB workspace; Sam's kernel gets no such cost and its median is taken over warm runs. The arithmetic is identical, so the true ratio is near 100 %. The corrected harness (warm-up twice, median of 20 for both) reported "mine = 98 % of the library" in the Lab Engineer's run (R6); the exact value changes from run to run.


Wrong answers and why. "Sam's kernel is faster": both sides run the same function mine. "The library does more arithmetic": it does the same arithmetic plus one-time setup, which a warm-up removes.


Fix. Use one measurement function for both sides with warm-up runs and the median of at least 20 (Listing 3's medianSeconds). Prevention: the harness exposes only measure(callable); a report is rejected if the run counts differ; the self-test of the mini-project. How the evidence was produced: cold_ref.cpp and cold_ref_fixed.cpp in the lab folder.
