Story hook

The great kitchen hall has a famous cookbook. It does not contain one recipe for pastries. It contains a recipe pattern, with blanks: how big a tray each table takes, how many pastries each helper holds, whether the trays may be only partly full. Filling in the blanks gives one concrete recipe, and the book's editors have already filled in hundreds of combinations that work in this hall.

Before a dinner, the head of the hall asks each filled-in recipe: "can you do tonight's order?" Some answer "yes", some "no, my trays must be full and tonight's order does not fill them". She cooks with one that said yes. A new cook, Ana, skipped the question and always took the recipe with the biggest trays, because it was the fastest last week. Most nights the food was fine. Some nights it was quietly wrong.

AMD's Composable Kernel (CK) is such a book of recipe patterns for GPU kernels. This chapter teaches you to read it: the tile hierarchy, the template parameters, the instances, and the "can you do this?" check that you must never skip.

What you will be able to do

  • Explain how a tile-based template library turns one kernel template into many instances, and what each level of the tile hierarchy maps to on an AMD GPU.
  • Read an instance's template parameters and predict its threads, LDS bytes, workgroup count and tile utilisation for a shape.
  • Use compile-time checks and run-time "is this argument supported?" checks correctly, and write a dispatcher over a list of instances.
  • Read the compiler metadata of several instances and connect it to their parameters.
  • Navigate an unfamiliar template library methodically, and record what you verified.
  • Diagnose wrong results caused by an instance used outside its supported shapes.
Jargon box
Composable Kernel (CK)
Simple words: AMD's library of kernel "patterns" from which many fast kernels are made. Analogy: the cookbook of recipe patterns with blanks. Precise: a ROCm C++ template library for performance-critical GPU operations (GEMM and others), in which kernels are composed from tile-level building blocks and instantiated for chosen parameters; its exact structure and names are in its documentation (unverified box in Layer 2). D1 C1
Instance
Simple words: one fully filled-in version of a kernel template. Analogy: one filled-in recipe. Precise: a template specialisation with every tuning parameter fixed (tile sizes, thread tile, padding, data types, layouts), compiled into its own kernel with its own register and LDS use. R4
Tuning parameter
Simple words: a number you choose that changes speed but not the answer. Analogy: the size of the trays. Precise: a compile-time constant such as block tile BM × BN × BK or thread tile TM × TN; for valid inputs every choice computes the same mathematical result, with different resource use and speed. D2
Argument support check
Simple words: asking an instance whether it can handle this exact problem before running it. Analogy: "can you do tonight's order?" Precise: a run-time predicate on the problem (sizes, strides, alignment) that an instance evaluates because its kernel assumes properties (for example K a multiple of BK) it does not check inside the loop; CK exposes such a check per instance (name to verify). D1
Tile hierarchy
Simple words: the work split into nested blocks: for the grid, a workgroup, a wave, one instruction, one lane. Analogy: the hall, a table, a row, one push of the tray machine, one helper's hands. Precise: the decomposition of a GEMM into block tiles (workgroups), wave tiles (waves) and instruction tiles (one MFMA or FMA group), with per-lane fragments; the same idea as CUTLASS's threadblock, warp and instruction tiles. D2 C1
Padding specialisation
Simple words: an instance variant that can handle sizes that do not fill the last tile. Analogy: a recipe that allows partly full trays. Precise: a compile-time choice that adds bounds checks or zero-filling along one dimension (M, N or K), costing some instructions but supporting any size along it. R2

Layer 1 — the kid explanation

Writing one fast GEMM kernel by hand takes days, and the best tile sizes differ for every GPU and every matrix shape. So library authors write the kernel once as a pattern with blanks, and fill in the blanks many times. Each filled-in version is a separate kernel. A small program picks the right one for your problem.

Each filled-in version only works for some problems. If you use it for a problem it was not made for, it may give a wrong answer without any error. That is why you always ask it first: "can you do this?"

One template, many kernels

Listing 1 (mini_ck.hpp) defines GemmPolicy<BM, BN, BK, TM, TN, PadK>. From the six parameters it derives the thread count (BM/TM)·(BN/TN) and the LDS bytes 4·BK·(BM + BN), and it rejects impossible combinations at compile time with static_assert: the thread tile must divide the block tile, the workgroup must be a whole number of 64-lane waves and at most 1,024 threads, and the LDS tile must fit the 65,536-byte per-workgroup limit that the compiler enforced in F7-16. R2 Listing 3 asks for 64 × 40 tiles with 4 × 4 thread tiles: 160 threads, two and a half waves, and the build fails with the policy's own message (R3). R3 Rejecting a bad instance at compile time is cheap and certain; this is the first kind of check.

The run-time support check

The second kind of check depends on the problem. The fastest kernels avoid bounds checks inside their inner loop; an instance without K padding assumes that K is a multiple of BK. isSupported(M, N, K) returns false otherwise. Listing 2 asks four instances about three shapes (R2): for K = 40 the two instances without padding answer "not supported", and the two with padding run and give 0 wrong elements. For every supported pair the result is correct. R2

A dispatcher

Listing 4 compiles three instances of a real HIP kernel template driven by the same policies and launches the first instance that supports the problem, as a library dispatcher does (launch<P> returns an error for an unsupported shape, and the caller tries the next). The instances_isa run shows that each instance really is its own kernel with its own resources: 116, 70 and 94 VGPRs; 16,384, 8,192 and 12,288 bytes of LDS; all with a maximum workgroup size of 256 (R4). R4 The LDS figures are exactly the policy's formula; the VGPR figures grow with the thread tile (64, 16 and 8 accumulators).

Layer 3 — the engineer's depth

The parameter space and its cost

Six parameters with a few values each already give dozens of instances; real libraries add data types, layouts (row- or column-major for each operand), padding per dimension, pipeline variants, MFMA shapes and epilogues (bias, activation). Each instance is compiled separately, so build time and binary size grow with the number of instances, which is why libraries ship a curated subset and let you build more. D2 For MP4 this means: do not try every combination; start from instances that the library itself uses for similar shapes, and measure.

Choosing an instance

Listing 2's table shows two effects that decide speed before any measurement. Tile utilisation: for M = 200, N = 72 only 43.9 % of the computed block-tile area is useful with 64 × 64 or 128 × 128 tiles, and 50.2 % with 32 × 64; for M = N = 96, 32 × 64 tiles use 75.0 % against 56.2 % for 64 × 64 (R2). Workgroup count: the 128 × 128 instance makes only 2 workgroups for 200 × 72 and 4 for 256 × 256, far too few to fill a GPU with many compute units (look up your count with rocminfo). R2 Profiling tools (CK's profiler, unverified box) automate the final choice by timing; your harness of F7-19 does the same.

How to read an unfamiliar template library

  1. Start from a client example that builds and runs; record the commit.
  2. Find the instance type it uses; write out every template argument with its meaning (as in Listing 2's names).
  3. Find the argument check and read every condition: these are the instance's assumptions.
  4. Find the kernel entry point and follow it down one level at a time (grid → workgroup → wave → instruction), noting where LDS is allocated and where the MFMA (or WMMA) is issued.
  5. Compile one instance with --save-temps or -S and match the metadata (VGPRs, AGPRs, LDS) and the inner loop to what you read (F7-13).
  6. Write down what you verified and what you assumed; the rest goes in an unverified box, exactly as in this chapter.

This is the same method as reading CUTLASS (F6-27); the curriculum lists both libraries for the E6 and E7 reading. C1

How the hardware actually does it

An instance is an ordinary kernel when it reaches the GPU: a code object with its kernel descriptor (register counts, LDS size, workgroup size limit) and its machine code. D3 The hardware knows nothing of templates or policies. That is why the metadata in R4 is enough to compare instances' resource use without a GPU, and why two instances of the "same" kernel can have very different occupancy: the VGPR counts 70 and 116 give different numbers of resident waves on the same compute unit (F7-10). R4 The __launch_bounds__(P::threads) in Listing 4 becomes .max_flat_workgroup_size: 256, which lets the compiler budget registers for exactly that size.

Worked example

Reading an instance. Gemm<32x64x32, 2x4, PadK> for M = N = 96, K = 40:

QuestionComputationAnswer
Threads(32/2) · (64/4)256 = 4 waves of 64
LDS4 · 32 · (32 + 64)12,288 bytes (R4)
Supported?PadK is trueyes, for any K
Workgroups⌈96/32⌉ · ⌈96/64⌉ = 3 · 26
Tile use96·96 / (6 · 32 · 64)9,216 / 12,288 = 75.0 % (R2)
k-tiles⌈40/32⌉2, the second with 8 valid k and 24 zero-filled

The same problem with Gemm<64x64x16, 4x4> (no PadK): 40 mod 16 = 8, so isSupported is false. Without the check, the third k-tile would read 8 values past each row of A and past the last row of B.

Where the analogy breaks


    

  • A cookbook's recipes are read by people who notice nonsense. Instances are executed blindly: an unpadded instance on a bad K computes garbage at full speed with no error.
    • 

  • "Filled-in recipes" suggests choosing is cheap. Each instance costs compile time and binary size; libraries cannot ship every combination, and the one you need may have to be built.
    • 

  • The story's editors "know the hall". A library's pre-made instances were tuned for the GPUs and shapes its authors chose; on your GPU and shapes the best one must be measured.
    • 

  • Recipes in a book are independent. CK's building blocks are shared C++ templates: a change in one block changes many instances at once, which is why you record the exact commit you read.
    • 




Common mistakes and debugging


    

  • Symptom: correct for "nice" sizes, wrong for others, no error. Cause: instance used without its support check. How to find it: list failing shapes and look for a divisibility pattern (the forensic lab). Fix: always check; fall back to a padded instance.
    • 

  • Symptom: a long template error at build time. Cause: a parameter combination the library rejects (like Listing 3). How to find it: the first "static assertion failed" line and its message. Fix: respect the documented constraints.
    • 

  • Symptom: the "fastest" instance is slow for small problems. Cause: too few workgroups or poor tile utilisation (Listing 2). Fix: select by shape, then measure.
    • 

  • Symptom: binary size and build time explode. Cause: instantiating every combination. Fix: a curated list, built per target.
    • 

  • Symptom: you cannot find where the MFMA is issued. Cause: many template layers. Fix: compile one instance to assembly and search for v_mfma, then walk back up the call chain.

Summary


    

  • Template libraries like CK write a kernel once and instantiate it for many tuning parameters; each instance is a separate kernel.
    • 

  • Compile-time checks reject impossible instances; run-time support checks reject problems an instance cannot handle. Never skip the second.
    • 

  • Instance resources (VGPRs, LDS, workgroup size) are visible in the compiled metadata without a GPU.
    • 

  • Tile utilisation and workgroup count decide a lot before any measurement; the final choice is measured.
    • 

  • CK's own structure and names were not verified in this build: read its documentation and source with the six-step method and record the commit.

Forensic lab answer key


Observation. Failing: K = 72, 100, 33, 24. Passing: K = 512, 64, 96, 16. Every failing K is not a multiple of 16; every passing K is. M and N vary independently (130 × 250 passes although neither is a multiple of 128), and failing shapes have every element wrong, with worst relative errors around 0.1–0.3 (R5).


Root cause. The 128 × 128 × 16 instance has no K padding: its isSupported requires K % 16 == 0, and Ana's dispatcher never asks. For K = 72 the fifth k-tile covers k = 64–79; the kernel reads 8 elements past the end of each row of A (the next row's values) and rows of B past K (in the replay, wrapped to the start of B; on a GPU, whatever memory follows). These products are added into every output.


Why every element. Every element of C sums over all k, including the invalid ones, so every element gets garbage terms.


Wrong answers and why. "Edge handling in M or N": 130 × 250 passes. "Tolerance too tight": errors of 10 % to 30 % of Σ|ab| are many orders of magnitude above any FP32 rounding bound.


Fix. Call isSupported and fall back to a PadK instance. Prevention: the dispatcher must be the only way to launch; tests include K values that are not multiples of every BK in the instance list; the support check is part of code review. How the evidence was produced: nightly.cpp, deterministic inputs, host replay of the instance.
