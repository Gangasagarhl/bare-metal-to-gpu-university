Story hook

The great kitchen hall has an order for a mountain of small pastries. Each pastry needs one ingredient from a long shelf of fillings and one from a long shelf of doughs, and every filling goes with every dough. The first night, every helper walks to the far pantry for each filling and each dough they use. The path is jammed and most helpers stand in the queue.

The second night, Chidi's table works differently. The table fetches one short stretch of fillings and one short stretch of doughs and lays them on the table in the middle. Every helper at the table then makes many pastries from what is already in front of them, holding a few of the pastries they are building in their own hands. Only when the table's stretch is used up does the table fetch the next stretch, and everyone waits until the new ingredients are all laid out, and also until everyone has finished with the old ones, before anything on the table is replaced.

That second "wait" is easy to forget, and forgetting it ruins pastries only sometimes. This chapter is about the table (the LDS), the stretches (tiles), the hands (registers) and both waits, for a matrix multiply on an AMD GPU.

What you will be able to do

  • Write an SGEMM kernel in HIP with LDS block tiling and register tiling that is correct for any M, N and K.
  • Compute for a tile shape its LDS bytes, global arithmetic intensity, LDS reads per FMA and accumulator registers, and check them against the compiler's metadata.
  • Read the AMD ISA of the inner loop: LDS read widths, packed FMAs, barriers, VGPR count and spills.
  • Explain why both barriers of the tile loop are needed, and diagnose a kernel that lost one.
  • Run the E6 step table on an AMD GPU against rocBLAS (lab steps 6–8).
Jargon box
GEMM
Simple words: multiplying two matrices and adding the result into a third. Analogy: every filling goes with every dough. Precise: general matrix-matrix multiply, C ← α·A·B + β·C, with A of size M × K, B of size K × N and C of size M × N; SGEMM is the FP32 version. It performs 2·M·N·K floating-point operations. D5 D6
LDS (Local Data Share)
Simple words: AMD's fast memory that the threads of one workgroup share. Analogy: the table in the middle of the row group. Precise: on-chip, banked memory allocated per workgroup, declared in HIP with __shared__; the AMD name for what CUDA calls shared memory (F7-11). Not the same as shared memory between processes. D1 D2
Block tile (LDS tiling)
Simple words: the part of A and B that one workgroup copies to LDS before using it many times. Analogy: the stretch of fillings and doughs laid on the table. Precise: a BM × BK slice of A and a BK × BN slice of B staged in LDS so that each element loaded from global memory serves BN (for A) or BM (for B) multiply-adds. D5
Register tiling (thread tile)
Simple words: each thread computes a small block of outputs, not one. Analogy: each helper holds several pastries in their hands at once. Precise: each thread keeps a TM × TN block of C in registers and, per k step, reads TM values of A and TN values of B from LDS for TM·TN FMAs. D5
Arithmetic intensity
Simple words: how much arithmetic you do per byte you fetch. Analogy: pastries made per trip to the pantry. Precise: floating-point operations divided by bytes moved between two levels of memory (here global memory to LDS); the quantity on the x-axis of the roofline model. D7
Write-after-read hazard (on a tile)
Simple words: overwriting a value that someone has not finished reading. Analogy: clearing the table while a helper is still reaching for a filling. Precise: in a tiled loop, a thread storing the next tile into LDS before all threads have finished reading the current one; the barrier at the end of each iteration prevents it. D1

The idea in pictures

Figure 1 is the tiling diagram of guide 9.2 for this kernel: tiles of A and B move from global memory into LDS once per k-step of the tile loop, and each thread moves values from LDS into registers and multiplies them into its 4 × 4 block of C.

Layer 1 — the kid explanation

In a matrix multiply, every number of A is used many times and every number of B is used many times. If each helper fetches every number from the far pantry each time, the pantry path is full and the helpers wait. So a group fetches a piece of A and a piece of B once, puts them on its table, and everyone uses them many times. Each helper also builds several results at once in their hands, so every number they pick up from the table is used more than once.

Two waits keep it safe: nobody starts using the table before it is fully set, and nobody clears the table before everyone has finished with it.

Layer 2 — the student explanation

Why naive GEMM is starved

In sgemmNaive each thread computes one element of C. Every k step loads one float of A and one of B (8 bytes) for one FMA (2 FLOP): 0.25 FLOP per byte from global memory, as Listing 2 prints (R4). R4 Caches catch some reuse, but the kernel's design does not guarantee any. GEMM itself does 2·M·N·K operations on M·K + K·N inputs, so its potential reuse grows with the matrix size; tiling is how a kernel collects it. D5

LDS tiling

sgemmLds is F6-22's kernel in HIP: a 16 × 16 workgroup loads a 16 × 16 tile of A and of B into LDS, synchronises, does 16 multiply-adds per thread from LDS, synchronises, and moves on. Each element loaded from global memory now serves 16 FMAs: per k-tile the workgroup loads (16 + 16) × 16 floats and does 16 × 16 × 16 FMAs, which is 4 FLOP per byte (Listing 2). R4 In HIP the declaration is the same __shared__ as in CUDA; AMD's documents call the memory LDS. D1

The cost moved: each FMA now needs two LDS reads (2.000 in Listing 2's "LDS rd/FMA" column). LDS is fast but not free; the next step attacks that ratio.

Register tiling

sgemmLdsReg has a 64 × 64 block tile, BK = 16, 256 threads, and each thread owns a 4 × 4 block of C in registers. Per k step a thread reads 4 values of A and 4 of B from LDS and does 16 FMAs: 0.5 LDS reads per FMA. The global intensity rises to 16 FLOP per byte, because each loaded element serves 64 FMAs. R4 The A tile is stored transposed (As[k][m]), so the four A values a thread needs for one k are contiguous, and padded by four floats per row. The compiler turned these reads into ds_read_b128 and ds_read_b96 (several floats per instruction), and the 256 FMAs per k-tile into 98 packed v_pk_fma_f32 (two FMAs each) plus 60 v_fmac_f32: 98 × 2 + 60 = 256 (R5). R5

Edges

The E6 acceptance test includes "sizes not multiples of the tile". Listing 1 guards every load (out-of-range elements become 0 in LDS, which adds nothing) and every store, so one kernel serves all shapes. Listing 3 replays the register-tiled kernel on the CPU, thread by thread and phase by phase, for square, tall-skinny, short-wide and odd shapes, and finds 0 wrong elements for all of them (R6). R6 This proves the index logic, not the GPU run, which is untested here.

Both barriers

Every iteration of the k loop has two barriers. The first (after the loads) makes the tile complete before anyone reads it. The second (after the compute) makes sure nobody overwrites the tile with the next one while another wave is still reading it: a write-after-read hazard. In HIP, __syncthreads() waits for all threads of the workgroup and makes their LDS writes visible to each other. D1 In the ISA of sgemmLdsReg they are the two s_barrier (R5). The forensic lab is about the second one.

Layer 3 — the engineer's depth

The tile budget

A tile shape trades four resources against each other. Listing 2 computes them for four shapes (R4): LDS bytes per workgroup (limits how many workgroups can share a compute unit), global FLOP per byte (how far the kernel is from being memory-bound), LDS reads per FMA (pressure on LDS bandwidth) and accumulator registers per thread (VGPR pressure, hence occupancy). Bigger tiles raise both intensities but need more registers and give fewer workgroups: 4,096 workgroups for a 4096 × 4096 C with 64 × 64 tiles, 1,024 with 128 × 128. A GPU with many compute units needs enough workgroups to fill them; the compute-unit count of your GPU comes from rocminfo or hipDeviceProp_t::multiProcessorCount, not from this chapter. H1

What the compiler reports

Without a GPU you can still read each kernel's resource use from the code object metadata (the LLVM AMDGPU back end emits it; D3). D3 For gfx90a the resources run shows: sgemmNaive 11 VGPRs and no LDS; sgemmLds 34 VGPRs and 2,048 bytes of LDS; sgemmLdsReg 76 VGPRs and 8,448 bytes, and no spills (R3). R3 The LDS figures match Listing 2's formula exactly. The 16 accumulators are only part of the 76 VGPRs: the A and B values for one k step, addresses and loop state take the rest.

How many waves can be resident per SIMD with 76 VGPRs, and how many workgroups per CU with 8,448 bytes of LDS, depends on the register file and LDS sizes of your GPU (F7-10, F7-11).

Beyond this kernel

The E6 step table continues: vectorised global loads (four floats per thread per instruction), double buffering (two LDS buffers so the next tile loads while the current one is used, which also changes the barrier pattern), tuned tile sizes per GPU, and finally the matrix cores (F7-17), where FP32 SGEMM can use FP32 matrix instructions on CDNA if the ISA guide lists them for your GPU. Each step is a measured row in your table against rocBLAS (F7-19); a step that does not help on your GPU is recorded too. C1

How the hardware actually does it

The inner loop of sgemmLdsReg as compiled for gfx90a (R5) is almost pure LDS reads and FMAs: ds_read_b128 brings four floats per lane from LDS into four VGPRs, and v_pk_fma_f32 performs two FP32 FMAs on pairs of registers. R5 D2 The loads of the tiles from global memory appear as global_load_dword inside small loops (the compiler did not unroll the strided load loops), and stores to LDS as ds_write_b32. The barrier is s_barrier, preceded by s_waitcnt so that outstanding LDS operations are complete (F7-13). In sgemmLds the compiler chose v_pk_mul_f32 and separate v_add_f32 rather than fused multiply-adds (visible if you rebuild with -S): the rounding differs slightly from an FMA, one more reason to test with a tolerance.

Where the analogy breaks


    

  • The table suggests a passive surface. LDS is banked (F7-11): lanes of one wave reaching into the same bank at different addresses are served one after another, so the layout on the "table" matters, which the story does not show.
    • 

  • "Holding pastries in their hands" suggests a helper can hold as many as they like. Every accumulator is a VGPR; more registers per thread means fewer waves resident (F7-10), and too many means spills to slow memory.
    • 

  • In the story, a helper who finishes early simply waits. On a GPU, a wave that does not wait at the second barrier really does overwrite LDS that other waves are still reading; the result is not "a bit late" but wrong.
    • 

  • The pantry trip in the story has a fixed cost. Real global loads pass through caches and are combined per wave (coalescing), so the "one trip per element" picture of the naive kernel overstates its traffic; that is why intensity here is defined by the kernel's design, not by measured traffic.
    • 




Common mistakes and debugging


    

  • Symptom: correct for 512 × 512 × 512, wrong for 1000. Cause: loads or stores not guarded. How to find it: run the E6 shape list; print wrong indices modulo the tile size. Fix: zero-fill out-of-range loads, guard stores.
    • 

  • Symptom: wrong only sometimes, at "random" places; correct when K ≤ BK. Cause: the second barrier is missing. How to find it: count s_barrier in the ISA (the forensic lab). Fix: restore it, or double-buffer.
    • 

  • Symptom: a compile error "local memory (…) exceeds limit (65536)". Cause: tile too large for one workgroup on this target (R7). Fix: smaller BK or BM/BN, or less padding.
    • 

  • Symptom: a bigger thread tile makes the kernel slower. Cause: VGPR use rose (check vgpr_count, vgpr_spill_count), occupancy fell or registers spilled. Fix: read the metadata after every change; record it in the E6 table.
    • 

  • Symptom: results differ from the CPU in the last bits. Cause: different rounding (FMA versus multiply then add) and order. Fix: a tolerance from the K·u·Σ|a||b| bound, as Listing 1 uses.
    •

Summary


    

  • Naive GEMM does 0.25 FLOP per byte from global memory; LDS tiling raises it to BM·BN/(2(BM+BN)) FLOP per byte.
    • 

  • Register tiling cuts LDS reads per FMA to (TM+TN)/(TM·TN) and turns into wide ds_read and packed FMAs on gfx90a.
    • 

  • The code-object metadata gives LDS bytes, VGPRs and spills without a GPU; check every change against it.
    • 

  • clang 17 limited one gfx90a workgroup to 65,536 bytes of LDS; hardware sizes come from the ISA guide (unverified here).
    • 

  • Guard loads and stores for any M, N, K; test the E6 shape list.
    • 

  • Both barriers of the tile loop are needed; a missing second one corrupts results only for K > BK and only on some schedules.

Forensic lab answer key


Observation. In the replay of Kai's kernel, every failing shape is wrong exactly in rows 16–63 of each 64-row block tile; rows 0–15 are correct; the shape with K = 16 passes. The compiler shows one s_barrier in kaiGemm against two in sgemmLdsReg; registers and LDS size are otherwise identical (R8).


Root cause. The second __syncthreads() at the end of the k loop is missing. Wave 0 (threads 0–63, tRow 0–3, which own rows 0–15) finishes its compute and starts loading the next k-tile while waves 1–3 still read the current one. In the load loops, threads 0–63 store As for m = 0–3, 16–19, 32–35, 48–51 and Bs rows k = 0, 4, 8, 12 (all 64 columns). Waves 1–3 read all Bs rows, so all their outputs (rows 16–63) are corrupted; wave 0 itself read the tile before overwriting it.


Why the tests misled. K = 16 has one k-tile, so there is no next tile. On a GPU the schedule varies; a printf changes timing and can hide the race. That is exactly why the replay chooses one legal schedule deliberately.


Wrong answers and why. "Missing edge guard": edge bugs depend on M and N, not on K, and would hit the last block tiles, not rows 16–63 of every tile. "LDS too small": the metadata shows the same 8,448 bytes as Listing 1.


Fix. Restore the barrier after the compute loop. Prevention: test shapes with several k-tiles; count barriers in the ISA in code review; for races, consider a race checker where the ROCm tools offer one, and a CPU replay with adversarial schedules like Listing 3. How the evidence was produced: kai_kernel.inc is Listing 1's kernel minus that line; the replay is tiled_replay.cpp mode 2.
