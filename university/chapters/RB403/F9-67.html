Story hook

Before a long ride, Kofi prepares his bicycle on the kitchen floor. He chooses what goes on: lights yes, the heavy rack no, a bell because the route goes through a town. He writes on a card which cable runs to which brake and which switch turns on which light, because last year a mechanic swapped two cables and the rear brake worked the front wheel. He packs the toolkit, ticks every item on his list, and takes one short test ride round the block, timing how long it takes him to get going.

The next morning his friend borrows the card and builds an identical bicycle. It works, because everything that mattered was written down: the parts list, the cable plan, the checklist. Nothing depended on Kofi remembering.

A robot's OS image is that prepared bicycle. The kernel configuration is the parts list. The devicetree is the cable plan. The image file with its manifest is the packed toolkit with the ticked list. The boot in QEMU is the ride round the block, timed. This chapter builds all of it for the course robot.

What you will be able to do

  • Resolve a kernel-style configuration with defaults, ranges and dependencies, and detect options that are silently dropped.
  • Write the devicetree of a robot board, including the robot's own wiring (which input is the e-stop), and explain what belongs in a devicetree and what does not.
  • Build a reproducible robot image: kernel, devicetree, configuration and a checksum manifest, packed into a GPT disk image with boot, spare and log partitions.
  • Boot the image in QEMU, read its driver-binding log, and measure its boot stages over several boots.
  • Design the image to refuse to arm when a safety input is missing, and diagnose an image that refuses.
Jargon box
Robot OS image
Simple words: one file that holds everything the robot computer needs to start: the kernel, the description of the board, the settings and the programs. Analogy: the bicycle prepared and packed, with its ticked checklist. Precise: a versioned, reproducibly built artefact (here a GPT disk image) containing the kernel image, the board's devicetree blob, the resolved build configuration, the root file system (in a Linux image), and a manifest of checksums; written to the robot's boot medium or delivered as an update. C1 R4
Kernel configuration
Simple words: the list of choices made before building the kernel: which drivers and features go in, and with which settings. Analogy: the parts list for the bicycle. Precise: the set of option values (booleans, numbers, strings, "built in" or "module") that selects code and constants at build time; in Linux it is described by Kconfig files (types, defaults, dependencies) and stored as a .config file; in this course's image by mkconfig.py's rules and robot.config. D2 R1 (Kconfig in Zephyr: OS305.)
Driver binding
Simple words: matching each device described for the board with the program that knows how to drive it. Analogy: giving each cable on the plan to the person who knows that brake. Precise: for devicetree platforms, the kernel walks the nodes, skips those whose status is not "okay", and calls the probe function of the driver whose match table contains one of the node's compatible strings; unmatched nodes stay unbound and are listed. D1 (DR403's F4-35 built a driver model.)
Kernel command line (bootargs)
Simple words: a line of text the loader hands to the kernel at start, with settings that can change without rebuilding. Analogy: a note taped to the handlebar for today's ride. Precise: a string passed by the boot loader, on devicetree systems in the /chosen node's bootargs property, parsed by the kernel and by components that look for their own keys; QEMU's -append option sets it in direct kernel boot. D1 D4 R5
Image manifest
Simple words: a list inside the image of every file and its fingerprint, so anyone can check that nothing changed. Analogy: the ticked checklist packed with the toolkit. Precise: a file listing each artefact of the image with a cryptographic hash (here SHA-256), checked before boot or before an update is accepted; it detects corruption, not tampering, unless it is itself signed. D6 R4
Reproducible build
Simple words: building the same sources twice gives exactly the same bytes. Analogy: the friend builds the identical bicycle from the card. Precise: a build whose output depends only on its declared inputs (sources, configuration, toolchain version), not on time, paths or the machine; verified by building twice and comparing hashes. R3
Boot stage time stamp
Simple words: a note of the time at which each step of starting up finished. Analogy: timing how long until the bicycle is rolling. Precise: a value of a monotonic counter recorded at the end of each start-up stage (here the Arm architectural counter, which counts from reset), printed in the boot log so that boot time can be measured and attributed to stages. D3 R6

Terms used from earlier courses: devicetree, DTB and compatible string (DR402, F4-31); Kconfig and A/B update (OS305); GPT (OS301).

Layer 1 — the kid explanation

To start, a robot computer needs a package with everything in it: the main program, a map of which wire goes where, and a list of settings. Engineers build that package with tools, so that building it twice gives exactly the same result. They put a list of fingerprints inside, so the robot can check that nothing got damaged. And they make the robot check one important thing before it moves: can it see its emergency stop button? If not, it refuses to move at all.

Layer 2 — the student explanation

An OS image has four kinds of content, and each has its own tool and its own way of going wrong. C1

The kernel, built from a configuration. A kernel is configured before it is compiled: which drivers are included, which features, which constants. Linux describes its options in Kconfig files, each with a type, a default, and dependencies; the resolved choice is the .config file, and the build turns it into C preprocessor symbols. The course image uses a miniature of the same idea: mkconfig.py holds the rules, robot.config the choices, and the tool writes robot_config.h. Two properties matter for a robot: the configuration is a file under version control (so a reviewer can see that the e-stop requirement is on), and every dropped option is reported (so nobody believes a feature is in that is not). D2 R1

The devicetree. On an SoC board the kernel learns the hardware from the devicetree (DR403, F4-31). A robot adds its own wiring: which GPIO line is the e-stop, which bus the motor controller sits on, which camera is fitted. That belongs in the devicetree because it is a fact about the hardware of this robot. Software policy (control period, gains, which nodes start) does not; it belongs in the configuration or in the middleware's parameters (F9-68). D1

Drivers. At boot, the kernel binds drivers to devicetree nodes by compatible and status. A node can end in three states: bound, disabled in the tree, or without a driver in this image. The course image prints all three, because the forensic lab's fault is visible only in that list. D1 R5

The packed image. The files go into a disk image with a partition table: a boot partition that the loader reads, a second slot for updates, and a partition for logs that survives updates. A manifest of checksums lets the boot step, the update process and you confirm that the files are the ones that were built. R4 D6

The course board in this build is QEMU's Arm virt machine, because the build container has no robot computer. The image is the course's own bare-metal kernel from DR403, extended into a robot image, not Linux: the container has no Linux kernel source. Everything that would be different with a Linux image is marked, and Layer 3 maps each step onto its Linux counterpart. D4

Layer 3 — the engineer's depth

Kofi's card was worth more than his memory because his friend could check it. Everything below is about making the image checkable: by a reviewer, by a tool, and by the robot itself.

Configuration: rules, choices, and silent drops

The resolved configuration of the lab, and a variant that switches the real-time clock driver off while still asking for RTC time stamps: R1





The variant asks for CONFIG_ROBOT_RTC_TIMESTAMPS=y, but that option depends on CONFIG_ROBOT_DRIVER_PL031, which the same file sets to n. The tool drops the request and says so. A tool that dropped it silently would leave a log reader believing the robot's logs carry wall-clock times when they do not (F9-70). Two design rules follow for any robot configuration. First, a safety requirement must not depend on anything that can be switched off without notice: in the course rules, CONFIG_ROBOT_REQUIRE_ESTOP_TO_ARM has no dependency, so switching off the GPIO driver leaves the requirement on and the image refuses to arm instead of arming without an e-stop. Second, the configuration that was actually built (the resolved file, not the request) goes into the image, so the robot can report it. R1


Not verified — check before relying on this
For Linux, the author recalls that the Kconfig tools (for example make olddefconfig) resolve a .config by applying defaults and that an option whose dependencies are not met is not set, without an error; that configuration fragments are merged with a script in the kernel tree (scripts/kconfig/merge_config.sh), which warns when a requested value did not survive; and that the real-time preemption model is selected by CONFIG_PREEMPT_RT. None of this was checked in this build. Read the Linux kernel documentation "Kconfig Language" and "Kconfig make config" and the real-time preemption pages for your kernel version, and check every requested value against the final .config in your image build (the lab's extension does that for the course image).



The robot's devicetree

    •

    • 

  • The robot node. /robot has compatible = "course,robot-board" and estop-gpios = <&gpio 3 0>: a reference to the GPIO controller's phandle, the line number, and flags. The -gpios suffix and the "phandle, line, flags" layout follow the common GPIO binding convention; the "course," prefix is this course's own, not a registered vendor prefix.
    • 

  • Why line 3. QEMU's own tree for virt has a gpio-keys node whose poweroff key is line 3 of the PL061 (read with the F4-31 tool in this build), and QEMU's monitor command system_powerdown presses it. The lab uses that key as the e-stop button (F9-69).

Not verified — check before relying on this
The GPIO binding convention (a property named <name>-gpios holding a controller phandle and as many cells as the controller's #gpio-cells, and the flag value 0 meaning active high) is from the author's memory of the Linux devicetree bindings documentation ("GPIO properties"), not opened in this build. The course image reads only the phandle and the line; it ignores the flags cell and uses its own boolean estop-active-high. Driver binding, read from the boot log


The boot of the packed image, after checking the files against the manifest: R5




Read it top to bottom. The three file checks pass. The console comes up from /chosen. The time base is the architectural counter, 62,500,000 Hz on this QEMU machine, counting since reset. The options line shows the resolved configuration that was compiled in. The binding list has the three bound drivers and the disabled camera. The RTC gives wall-clock seconds (on QEMU, the host's clock). The e-stop is resolved to line 3 and reads "released". The bootargs set 500 cycles; the loop runs and the image ends itself through semihosting with exit code 0. The last line is the host's wall-clock time for the whole QEMU process, which includes QEMU's own start-up. R5 D3


On Linux, the same three outcomes appear in different places: bound devices under /sys/bus/platform/drivers/…, the "deferred" and unbound devices in debug files and the kernel log, and disabled nodes simply absent. Your image's test (lab step 5) should turn that information into a list and compare it with the expected list, so that a missing driver fails the test instead of the robot. D2

Boot time, measured and attributed


Five boots of the same image with one control cycle each, stage times from the image's own counter (emulated time since reset) and the host's wall-clock time per QEMU process: R6




Three habits matter more than the numbers, which are QEMU's and change at every run. Measure several boots and report the spread, not one value. Attribute time to stages; a total says nothing about what to fix. And measure from a defined origin: here the counter starts at reset, so "console up" includes everything before kmain; on Linux the kernel log's time stamps also start near the kernel's own start, so firmware and boot-loader time must be measured separately (with a GPIO toggle and a logic analyser, or the boot loader's own time stamps). On a robot the requirement is usually not "fast" but "bounded and known": the robot must not be armed by a supervisor that assumes it is ready (F9-68). R6 D3



Packing, checking and updating


The disk image and its contents: R4




The layout plans for three operations a robot image must survive. Boot: partition 1 is a FAT file system, which most boot loaders read; it holds exactly the files the loader needs. Update: partition 2 is an empty slot of the same purpose; an A/B scheme writes the new image into the inactive slot, boots it on trial, and falls back if it does not confirm itself healthy (OS305 did this for a microcontroller with MCUboot). Logs: partition 3 is never rewritten by an update, so evidence from before an update survives it (F9-70). The manifest detects corruption; it does not stop a deliberate change, because anyone who can change a file can change the manifest. Signing the manifest (and verifying the signature in the boot chain) is F11's subject. D6 C2


The kernel image is reproducible in this build: two builds in separate folders gave identical bytes. The disk image is not: the FAT directory records the time of each copy (visible in the mdir listing), and the GPT has random GUIDs. That is why the manifest hashes the payload files, which are reproducible, rather than the disk image. R3 R4

How the hardware actually does it


On a real SoC board the path from power-on to kmain is the Arm boot chain of DR403 (F4-32): a boot ROM inside the SoC loads a first stage from the boot medium in a vendor-specific layout, the first stage initialises DRAM, secure firmware and a boot loader follow, and the boot loader reads the kernel and the devicetree from a file system on the boot medium, places the devicetree's address in x0 and jumps to the kernel. QEMU's direct boot skips everything before the last step: it places the image and the DTB in RAM itself. That is why the lab's boot starts in "stage 0" with the loader's work already done, and why its times say nothing about firmware time on hardware. C1 D4


The architectural counter used for the time stamps is a system-wide counter that runs at a fixed frequency reported by CNTFRQ_EL0; QEMU's virt machine reported 62,500,000 Hz in this build. On hardware the frequency is set by the SoC and its firmware, and the counter may not start exactly at power-on, so the "since reset" origin must be checked against the board's documentation. D3 R5


Safety
Writing an image to a real robot computer's storage can leave it unbootable. Follow curriculum section 11.5: serial console first, a recovery path (SD-card swap, the SoC's USB recovery mode, or an external programmer with a backup image) before writing to on-board storage, and never on a machine you depend on. Test a new image in QEMU or on a bench board before it goes into the robot, and never boot a new image on a robot whose wheels or arm can move: put it on blocks, or disconnect motor power at the hard-wired e-stop chain. C1


Not verified — check before relying on this
Untested on hardware. The image ran only in QEMU 8.2.2 (machine virt, acpi=off, Cortex-A53). It was not written to an SD card or eMMC, not booted by a real boot loader, and not run on a robot computer. The QEMU behaviours relied on (direct kernel boot with -kernel, -dtb replacing the generated tree, -append setting /chosen/bootargs) were observed in the runs; their documentation (QEMU System Emulation User's Guide) was not opened.



Worked example


A. Resolve robot_nortc.config by hand. The file sets CONFIG_ROBOT_DRIVER_PL031=n and CONFIG_ROBOT_RTC_TIMESTAMPS=y; everything else takes the defaults of RULES. Walk the rules in order: the three numbers take their defaults 1000, 500, 300 (in range). DRIVER_PL061 defaults to y. DRIVER_PL031 = n (given). RTC_TIMESTAMPS = y requested, depends on DRIVER_PL031, which is n: dropped to n, with a message. ESTOP = y by default, depends on DRIVER_PL061 = y: kept. REQUIRE_ESTOP_TO_ARM = y, no dependency. The tool's output (mkconfig_drop.out above) matches line by line.


B. The disk layout in numbers. truncate -s 32M makes 32 MiB = 33,554,432 bytes = 65,536 sectors of 512 bytes. Partition 1 starts at sector 2048 (2048 × 512 = 1,048,576 bytes = 1 MiB, the dd seek=1 with bs=1M) and has +8M = 16,384 sectors, so it ends at 2048 + 16,384 − 1 = 18,431. Partition 2 starts at the next aligned sector, 18,432, and has 12 MiB = 24,576 sectors: end 18,432 + 24,576 − 1 = 43,007. Partition 3 starts at 43,008 and takes the rest up to the last usable sector, 65,502, because the backup GPT occupies the final 33 sectors (65,536 − 33 = 65,503 is the first of them): 65,502 − 43,008 + 1 = 22,495 sectors ≈ 11.0 MiB. All match mkimage.out. R4 D5


C. The control period in counter ticks. Line 188 of Listing 2 computes the period as 1000 µs × 62,500,000 Hz / 1,000,000 = 62,500 ticks. The image uses integer arithmetic only, because it is compiled with -mgeneral-regs-only (no floating-point registers in the kernel).

Where the analogy breaks


    

  • A bicycle's cable plan describes one bicycle, and a mechanic can see the cables. A devicetree can describe a board correctly and still be wrong for this robot (the forensic lab), and nothing visible tells you; only the boot log does.
    • 

  • Kofi's friend built an identical bicycle by reading a card. An identical image needs identical inputs, including the toolchain version and every build flag; the disk image in this lab is not even byte-identical between builds because of time stamps, while its payload is.
    • 

  • A test ride round the block tests the whole bicycle. A QEMU boot tests the image's software against an emulated board: it says nothing about the real boot ROM, firmware, clocks, or the motor controller.
    • 

  • Packing a toolkit does not change the bicycle. Configuration choices change the code that exists in the kernel; a dropped option is not a missing tool in the bag but a missing part on the bicycle.
    • 




Common mistakes and debugging


    

  • Believing the requested configuration. Symptom: a feature "is enabled" but does not work. Cause: its dependency was off and the option was dropped. Find it: compare the request with the resolved file (mkconfig_drop.out). Fix: fix the dependency; make the tool fail on drops in release builds.
    • 

  • Software settings in the devicetree. Symptom: a control gain change requires a new devicetree. Cause: policy put where hardware facts belong. Fix: hardware wiring in the tree; parameters in the configuration or middleware.
    • 

  • A node silently disabled by a merged board file. Symptom: a device's driver never probes. Find it: the "disabled in the devicetree" lines of the boot log. Fix: the forensic lab.
    • 

  • No console, no clue. Symptom: QEMU exits with code 4 and prints nothing. Cause: stdout-path names a node that does not exist or is disabled. Find it: the documented exit codes of Listing 2. Fix: correct the path; keep exit codes for every pre-console failure.
    • 

  • sgdisk -q wrote nothing. Seen in this build: with -q, sgdisk 1.0.10 returned 0 and left no partition table. Find it: always print the partition table after creating it (mkimage.out does). Fix: drop -q and discard the messages instead.
    • 

  • Hashing the disk image. Symptom: "the image changed" although nothing was rebuilt. Cause: file-system time stamps and GUIDs. Fix: hash the payload files; record the disk image's hash only as the hash of that particular artefact.
    • 

  • Booting a new image on a robot that can move. Never. Blocks under the wheels or motor power off at the e-stop chain.
    •

Mini-project


Image metadata and a self-report. Make the image able to answer "what are you?": put the resolved configuration, the manifest and a build-info file in the boot partition, embed the configuration's SHA-256 in the kernel at build time (a generated header), and make the kernel print it and compare it with a hash of the robot.cfg it finds through a second /chosen property set by the loader. Summary


    

  • An image holds the kernel (built from a configuration), the board's devicetree, the resolved configuration and a manifest, packed into a disk image with boot, spare and log partitions.
    • 

  • Configuration tools apply defaults and dependencies; dropped options must be reported, and safety requirements must not depend on optional features.
    • 

  • The devicetree holds hardware facts, including the robot's own wiring such as the e-stop input; software policy does not belong there.
    • 

  • Drivers bind by compatible and status; the boot log should list bound, disabled and unmatched nodes, and a test should compare it with an expected list.
    • 

  • Boot time is measured over several boots, attributed to stages, from a defined origin.
    • 

  • Payload files are reproducible and hashed; the disk image is not byte-reproducible because of time stamps and GUIDs.
    • 

  • A missing safety input must stop the robot from arming; in this build the course image did exactly that.

Forensic lab answer key


How the evidence was produced. robot_forensic.dts is robot.dts with the GPIO controller's status changed from "okay" to "disabled" (and its first comment line). The same kernel image was booted with the release-2 DTB (R7). The difference between the two trees:




Root cause. The merged board file disabled the PL061 GPIO controller. The binder therefore skipped it ("/pl061@9030000 disabled in the devicetree: skipped"); find_estop_line found the /robot node and its phandle, but the controller it names has no bound driver, so it returned −1 ("e-stop: no usable input"); with CONFIG_ROBOT_REQUIRE_ESTOP_TO_ARM=y the image refused to arm and exited with 6.


Other hypotheses and why they are ruled out. "The PL061 driver is configured out": the log would say "driver not configured", not "disabled in the devicetree", and the options line shows e-stop support on. "The /robot node or its property is missing or mistyped": the diff shows /robot unchanged, and the only change is the controller's status. "The e-stop button is pressed": the log never reached a reading of the line.


Right behaviour. Yes: refusing to arm is the fail-safe default. An image that armed would run the robot with no software e-stop monitoring; the hard-wired chain would still cut motor power, but the software would not know it had happened, would keep commanding motion, and would surprise everyone when power returned.


Fix and prevention. Set the controller's status back to "okay" (or, if the vendor disabled it because those pins now serve another function, move the e-stop to an available input and update estop-gpios). Prevention: the expected-bindings test of lab step 5 in the image build (it fails on "pl061 disabled"), and a review rule that any change to a node referenced by /robot needs the safety owner's approval.
