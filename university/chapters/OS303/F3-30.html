Story hook

A new class is moving into a room. The caretaker receives a room plan: "desks along the window wall, bookshelf by the door, whiteboard at the front". A good caretaker reads the whole plan first and refuses it if the bookshelf is drawn in the corridor, if two desks occupy the same spot, or if the plan says "and also bring in the school's safe". Furniture is carried in only when somebody first needs it, and on the first morning a folder waits on the teacher's desk: the class list and a note on where things are.

The head of year opens ten classes at once, and at the end of the day waits at her desk until each class reports how its day went: ten different reports. When a class leaves, its room must be cleared completely, so that the next class finds it empty. One caretaker forgot to take the empty shelf brackets down. After a thousand classes, there were no brackets left in the school.

That forgetful caretaker is this chapter's forensic case, recorded in a kernel log. The chapter builds the careful one: an ELF loader that trusts nothing in the file, demand paging, the initial stack with arguments and the auxiliary vector, spawn, exit and wait, and the course project: an init that starts ten programs, and a fuzzer that throws thousands of broken programs at the exec path.

What you will be able to do

  • Validate an ELF64 executable completely before loading it, with checks that cannot be fooled by integer wrap-around.
  • Load program segments lazily: map each page on its first page fault, with file bytes, zero fill and the right permissions.
  • Build the initial user stack: argc, argv, envp and the auxiliary vector, 16-byte aligned, as the System V ABI describes.
  • Implement spawn, exit and wait with a process table, zombies, orphans and reaping.
  • Prove the B13 acceptance tests: init with ten children and ten statuses, memory back at the baseline after 10,000 exec/exit cycles, and malformed ELF files rejected without kernel faults.
  • Find a slow memory leak from frame statistics and page-table arithmetic.
Jargon box
Process
Simple words: a running program with its own memory. Analogy: a class with its own room. Precise: here a struct Process: a pid, an address space (its own PML4), the ELF image it runs, one user thread, a parent, an exit status and a wait queue for its children. D3 R2
ELF loader
Simple words: the kernel code that reads a program file and sets up memory so the program can run. Analogy: the caretaker with the room plan. Precise: code that validates the ELF header and program headers, creates mappings for every PT_LOAD segment (file bytes up to p_filesz, zeros up to p_memsz, permissions from p_flags) and starts a thread at e_entry. D1
Program header (segment)
Simple words: an entry in an ELF file saying "put these bytes at this address with these permissions". Analogy: one line of the room plan. Precise: a 56-byte ELF64 record with type, flags, file offset, virtual address, file size and memory size; the loader acts only on type PT_LOAD and refuses PT_INTERP and PT_DYNAMIC. D1 R1
Demand paging
Simple words: mapping a page only when the program first touches it. Analogy: carrying furniture in when someone first needs it. Precise: the page-fault handler checks that the faulting user address belongs to a segment or the stack of the current process and is not yet mapped, maps a zeroed frame filled with the file's bytes, and restarts the instruction. D3 R2
Auxiliary vector
Simple words: a list of facts the kernel leaves for a new program, after its arguments. Analogy: the note in the first-day folder. Precise: (type, value) pairs on the initial stack after envp's NULL, ending with AT_NULL; this kernel passes AT_PHDR, AT_PHENT, AT_PHNUM, AT_PAGESZ and AT_ENTRY. D2
Initial process stack
Simple words: what the stack holds when a program's first instruction runs. Analogy: the first-day folder itself. Precise: at RSP: argc, argv[0..argc−1], NULL, envp[...], NULL, auxv pairs, AT_NULL; strings above; RSP 16-byte aligned. D2
Spawn
Simple words: create a new process running a given program, in one step. Analogy: opening a new class in a new room with a given plan. Precise: this kernel's system call 3: validate and load an ELF file from the boot modules, build its stack, create its thread; returns the child's pid. It replaces Unix's fork followed by exec. R2
Zombie process
Simple words: a process that has finished but whose parent has not yet asked for its status. Analogy: a class that left, whose report still waits on the head of year's desk. Precise: a Process with exited set, kept in the process table only for its pid and status until wait reaps it. D3
Orphan process
Simple words: a process whose parent exited first. Analogy: a class whose head of year went home early. Precise: here a child whose parent pointer was cleared in process_exit; nobody will wait for it, so it reaps itself when it exits (Unix instead re-parents it to init). R2
Init process
Simple words: the first user program, which starts the others. Analogy: the head of year who opens the classes. Precise: in this lab u_init.elf, started by the kernel; it spawns ten children and waits for all of them. C1
Fuzzing
Simple words: testing with huge numbers of random or mutated inputs. Analogy: handing the caretaker thousands of scribbled room plans. Precise: here mutation fuzzing: random byte changes, bit flips, boundary values and truncations of a valid ELF file, checked by invariants (no kernel fault, no accepted file that breaks the loader's promises, memory back at the baseline). R3

The idea in pictures

Layer 1 — the kid explanation

Analogy

Each class gets its own room set up from a plan. The caretaker checks the plan before moving anything, carries furniture in only when it is needed, and leaves a folder with the class list on the desk. The head of year opens classes and, at the end of the day, collects each class's report. When a class leaves, everything in its room goes back to the store, down to the last bracket.

A program on disk is just a file. The kernel turns it into a running process: it checks the file carefully, gives the program its own memory, puts the program's arguments where it can find them, and starts it. When the program finishes, the kernel cleans up after it and tells whoever started it how it ended.

Layer 2 — the student explanation

Where programs come from. This kernel has no file system yet (B14 adds one). The user programs are passed by QEMU as Multiboot modules (-initrd a.elf,b.elf,…), and the kernel keeps them in memory by name. spawn("u_child.elf", argv) looks the name up and loads that file.

Validate everything first. An ELF file is a header followed by tables of offsets and sizes, every one of them chosen by whoever made the file. SP301's ELF chapter (F2-44) read such files on the host; here a mistake is a kernel bug. elf_check (Listing 1) checks the magic number, class (64-bit), byte order, version, type (an executable, not a shared object), machine (x86-64) and the header sizes; that the program headers lie inside the file; that there is no interpreter or dynamic section (only static programs are supported); and for every PT_LOAD segment that its file part lies inside the file, its memory part inside the user range, that file size ≤ memory size, that its address and offset agree modulo 4096, that no two segments overlap, and finally that the entry point is inside an executable segment. Every comparison is written so that no sum can wrap past 264 (the pattern of F3-29's user_range_ok). Only a file that passes every check is loaded.

A new address space. The process gets a fresh top-level page table. Entry 0 is copied from the kernel's (the shared, supervisor-only kernel half); entry 1, the user half, starts empty.

Demand paging. No segment page is mapped at spawn time. When the program first touches a page, the CPU raises a page fault; vm_handle_fault checks that the address is in the user half, that the page belongs to a segment or to the 64 KiB stack, and maps a zeroed frame into which map_program_page copies the file bytes that belong there. Bytes between p_filesz and p_memsz (the .bss) stay zero. A page is writable if it belongs to the stack or to a segment with the write flag.

The initial stack. A program's _start expects to find its arguments on the stack. build_stack maps the top stack page at spawn time and writes, as Figure 2 shows: the argument strings at the very top, then (16-byte aligned) argc, the argv pointers, a NULL, an empty envp ended by NULL, and the auxiliary vector, which tells the program where its program headers are (AT_PHDR, AT_PHENT, AT_PHNUM), the page size (AT_PAGESZ) and its entry point (AT_ENTRY) D2. u_args prints all of it; its _start address equals the AT_ENTRY value R2.

Spawn, exit, wait. process_spawn adds the process to the process table under proc_lock and creates its thread, which enters ring 3 with F3-29's enter_user. process_exit (from the exit system call, a fatal user fault, or a kill) frees the address space, reaps already-exited children, orphans the living ones, stores the status and wakes the parent; the process becomes a zombie. process_wait sleeps on the parent's wait queue until some child has exited, takes its status and reaps it. The init test program spawns ten children, each of which exits with status 10 + its argument, and waits for all of them; the run shows ten distinct statuses R2.

Killing. process_kill sets a flag on the process's thread; the kernel acts on it at the user/kernel boundary (on return from an interrupt or a system call), so a process is never killed in the middle of kernel code that holds a lock. u_spin loops forever in ring 3; after 20 ticks the test kills it and its status is 0x1FF ("killed by the kernel").

Layer 3 — the engineer's depth

Why lazy loading, and what it costs

Demand paging means that a program's pages are read only if used: u_nop touches one code page and one stack page, whatever its file contains. It also simplifies spawn: no loop over segments, no partial failure halfway through mapping. The price is that errors move: a segment that is too large for memory fails on the first touch, as a page fault that cannot be satisfied, not at spawn time. This kernel accepts that because segments are limited to the user range by elf_check. A real kernel also reads file pages through a page cache and shares read-only pages between processes running the same program; here each process copies its pages from the in-memory module.

One detail of map_program_page deserves attention: a page can contain bytes of two segments (the end of one, the start of the next) when a linker packs them. The function copies the bytes of every segment that intersects the page and makes the page writable if any of them is writable. The ELF specification allows this kind of sharing at page boundaries D1; giving the whole page the union of the permissions is what simple loaders do, and it is a small weakening of protection worth knowing about.

Exit frees everything, in the right order

process_exit runs on the exiting thread, in its own address space. Before freeing the page tables it switches CR3 to the kernel's (line 223); otherwise the CPU would be walking tables that are being freed. It frees, for the user half only, every mapped frame, every page table, page directory and page-directory-pointer table, then the PML4 (lines 75–103). Entry 0 is the kernel half, shared by everyone, and must never be freed. Only after that does it take proc_lock to update the table and wake the parent. The thread itself then exits like any kernel thread and is reaped by F3-26's zombie reaping.

No TLB shootdown is needed for the user pages: a process has one thread, every CPU it ran on loaded another CR3 when it switched away (a CR3 load drops the non-global entries; F3-28's check-yourself question 8), and the exiting CPU has just loaded the kernel's CR3. With several threads per process on several CPUs, freeing would require a shootdown to every CPU that has the address space loaded.

Zombies, orphans and the lost-wake-up rule again

process_wait holds proc_lock, scans for an exited child, and if there is none but there are living children, sleeps on the parent's wait queue with F3-27's WaitQueue::sleep(proc_lock), which releases the lock only after the thread is queued. process_exit sets exited and wakes the queue under the same lock, so a child that exits between the scan and the sleep cannot be missed. When a parent exits before its children, they become orphans; Unix re-parents them to init, which must reap them. This kernel marks them so they reap themselves at exit: simpler, and enough as long as nobody needs their status.

In the recorded run, init's ten children were reaped in reverse order (status 19 first) R2. Nothing in the ABI promises an order: here all ten had exited before init's first wait, the process table is a list with new processes at the head, and wait takes the first exited child it finds.

Spawn instead of fork

Unix creates processes with fork (copy the caller) and exec (replace the copy's program). That design needs copy-on-write page tables to be cheap and raises questions about threads, locks and file descriptors at the moment of the copy. The curriculum lists fork "as a topic" for B13 C1; this kernel creates a process directly from a program file and arguments, like POSIX posix_spawn or Windows' process creation D4. Building fork on top of this kernel is a good extension once copy-on-write exists.

Fuzzing the exec path: what the two fuzzers prove

The B13 test wants "1 hour of fuzzing through the exec path" C1. This lab fuzzes at two levels. In the kernel, test_fuzz mutates u_child.elf 3000 times (mostly in the first 256 bytes, where the headers are), passes each mutant through the real exec path and runs whatever loads, with a 30-tick limit. The invariants are: no kernel fault, every mutant either rejected or run to an exit or a kill, and memory back at the baseline. In this build 1,877 mutants were rejected for 16 different reasons and 1,123 ran (most exited normally, 14 were killed by a CPU exception in ring 3, none hit the time limit) R3. On the host, elf_fuzz.cpp compiles the very same elf_check.h under AddressSanitizer and UBSan and mutates a minimal hand-built ELF 200,000 times, copying each mutant into an exactly-sized heap block so that any read past its end is caught; it then re-checks every accepted file against the loader's promises (segments inside the file and the user range, entry inside an executable segment). No sanitizer report and no broken promise R4. Neither is an hour of coverage-guided fuzzing: they are a few minutes of blind mutation, and the NOTES list the gap.

What this chapter does not do

  • Processes with multiple threads (B13's goal names them): one thread per process here.
  • A file system: programs are Multiboot modules (B14 brings a RAM disk and a VFS).
  • Environment variables: envp is always empty.
  • Dynamic linking: PT_INTERP and PT_DYNAMIC are rejected.

How the hardware actually does it

The hardware knows nothing about processes or ELF. What it provides: a page-table root per address space (CR3), the user/supervisor and write bits checked on every access, a page fault with the faulting address in CR2 and an error code saying whether the page was absent (bit 0 clear) or protected, and the ability to restart the faulting instruction after the handler returns. Demand paging is built entirely from those: the handler maps the page and returns, and the CPU re-executes the instruction as if nothing happened D5. A CR3 write switches address spaces and drops the TLB's non-global entries; F3-26's scheduler writes CR3 at a switch only if it differs.

Worked example

Loading u_child.elf by hand. From readelf (Listing 3 output): the entry point is 0x80_0040_1019; three PT_LOAD segments: offset 0 → 0x80_0040_0000 (0x120 bytes, R), offset 0x1000 → 0x80_0040_1000 (0x5d bytes, R E), offset 0x2000 → 0x80_0040_2000 (0x54 bytes, R); and a GNU_STACK header, which the loader skips because its type is not PT_LOAD. The checks: each vaddr ≡ offset (mod 4096) — 0x...0000 and 0, 0x...1000 and 0x1000, 0x...2000 and 0x2000: yes. No overlap: [0x...0000, 0x...0120), [0x...1000, 0x...105d), [0x...2000, 0x...2054). The entry 0x...1019 lies in the R E segment: 0x1019 − 0x1000 = 0x19 < 0x5d. The program headers start at file offset 64, which lies inside the first segment (offset 0, file size 0x120), so AT_PHDR = 0x80_0040_0000 + 64 = 0x80_0040_0040, exactly the value u_args printed for its own (equally laid out) file R2.

First instruction. The thread enters ring 3 at 0x80_0040_1019 with RSP pointing at argc. The fetch faults (page not present); vm_handle_fault finds the page inside the R E segment, maps a frame, copies 0x5d bytes from file offset 0x1000, and the fetch is restarted. u_child then reads argv[1][0], on the already-mapped stack page; computes 10 + n and calls exit. Its read-only data page is touched only if a string is used.

The stack of u_args. argv strings: "u_args.elf" (11 bytes with NUL), "hello" (6), "world" (6) = 23 bytes, placed downwards from 0xFF_FFFF_F000: "world" at …EFFA, "hello" at …EFF4, "u_args.elf" at …EFE9 — the addresses u_args printed. Words: argc 1 + argv 3 + NULL 1 + envp NULL 1 + auxv 12 = 18 words = 144 bytes. 0xFF_FFFF_EFE9 − 144 = 0xFF_FFFF_EF59, rounded down to 16: 0xFF_FFFF_EF50 = RSP. argv is at RSP + 8 = 0xFF_FFFF_EF58, the value printed R2.

Where the analogy breaks


    

  • The room is an illusion. A process's "room" is a set of page-table entries; the same physical frame can appear in two rooms, or in none, and the kernel's rooms are visible (but locked) in every process.
    • 

  • Furniture appears at the first touch, invisibly. The program never sees demand paging; a caretaker carrying desks in mid-lesson would be noticed.
    • 

  • The head of year cannot hear a class end. A parent learns about a child's exit only by asking (wait); there is no notification unless the kernel adds one (signals, which this kernel does not have).
    • 

  • A rejected plan has no owner to complain to. The loader returns an error code to whoever called spawn; it cannot ask the file's author what was meant.
    • 




Common mistakes and debugging


    

  • offset + filesz > size. Wraps for huge values and accepts a segment that reads far past the file. Use the subtraction form after checking offset ≤ size; the host fuzzer finds the sum form within seconds (try it).
    • 

  • Forgetting .bss. Copying p_memsz bytes from the file reads past the segment; copying p_filesz into a non-zeroed frame leaves garbage in .bss.
    • 

  • A misaligned initial stack. RSP must be a multiple of 16 at _start; compiled code that uses aligned SSE stores would crash (this kernel's programs use no SSE, so the bug would hide until they do).
    • 

  • Freeing the address space while it is loaded. Switch CR3 first.
    • 

  • Freeing only the leaves. Page tables are memory too: the forensic case.
    • 

  • A missing wake-up in exit. The parent sleeps forever; with F3-27's wait queue and the same lock in exit and wait, it cannot happen here.
    • 

  • Debugging method for leaks. Print frames, heap objects, threads and processes at regular intervals in a loop; a constant slope means a fixed number of objects per cycle; divide, then list the objects a cycle allocates and find the ones with that count.
    • 




Transition box

Where you came from: F3-29 ran single user programs in ring 3 through a system-call ABI with checked copies. What carries over: threads and wait queues (F3-26, F3-27), the per-CPU area and IPIs (F3-28), enter_user, the exception table and user_range_ok's no-wrap pattern (F3-29), page tables (F3-21) and SP301's knowledge of ELF. What changes: programs are files the kernel validates and loads lazily into their own address spaces; processes have parents, statuses, zombies and orphans; init starts the others; the exec path survives thousands of malformed files. What comes next: OS304 gives the kernel storage (curriculum B14 onward): a virtual file system, an initial RAM disk and a block cache, then FAT32 and ext2, so that init can start programs from files instead of boot modules.

Mini-project (course project B13)


Init launches ten programs; fuzzing the exec path. The course project extends this chapter's lab into a small, honest system test.


    

  1. Make u_init read a list of programs and arguments from a boot module inittab.txt (a text file passed with -initrd), start them, and print a table "pid, program, status" sorted by pid.
    2. 

  2. Add a u_crash child that dereferences a null pointer and one that runs forever, and make init kill the latter after a time limit by a new system call kill(pid) (update the ABI table of F3-29).
    3. 

  3. Build a fuzzing corpus: the host fuzzer writes 1,000 mutants that its checker accepts into files, which become boot modules; the kernel runs each through the exec path. Run the kernel fuzzer for as long as your machine allows and report runs per minute under TCG (and KVM if you have it).
    4. 

  4. Run everything on 1 and 4 CPUs and record every run with qemu_step.
    5. 



Rubric (20 points). inittab parsing with errors reported, not crashed (3); kill system call with permission rule (parent only) and an updated ABI table (3); status table correct for normal exits, faults and kills (3); corpus fuzzing with the accepted-mutant corpus and a recorded duration (4); memory back at baseline after each phase, on 1 and 4 CPUs (4); a one-page report stating what was and was not tested, with the gap to "1 hour" quantified (3).



Summary


    

  • The loader validates the whole ELF file first: header, program headers inside the file, PT_LOAD segments inside the file and the user range, aligned, non-overlapping, entry executable; no interpreter. No sum can wrap.
    • 

  • Segments are loaded on demand by the page-fault handler: zeroed frame, file bytes, permissions. The top stack page is built at spawn: argc, argv, envp, auxv, 16-byte aligned.
    • 

  • Spawn, exit and wait use a process table, zombies, orphans and the wait-queue discipline of F3-27; kills act at the user/kernel boundary.
    • 

  • Exit frees the user half's frames and its page tables after switching to the kernel's CR3.
    • 

  • Init reaped ten children with ten statuses; 10,000 exec/exit cycles left memory at the baseline; 3,000 kernel and 200,000 host mutants caused no fault. The hour of fuzzing and multi-threaded processes were not done; nothing was tested on hardware.
    •

Answers to Check yourself


    

  1. The loader copies p_filesz bytes and zero-fills up to p_memsz; a file part larger than the memory part would write file bytes beyond the segment's memory, into whatever is mapped (or not) there. It is never valid.
    2. 

  2. Offset 64 lies inside the segment (offset 0), so AT_PHDR = 0x80_0060_0000 + 64 = 0x80_0060_0040, provided the segment's file size is at least 64 + phnum × 56.
    3. 

  3. Good answers mention: a failure halfway would require undoing partial allocations (page tables, frames, a process entry) on every error path, which is where leaks and double frees hide; validating first makes the error path trivial (return an error, nothing to free) and keeps hostile data away from the allocator.
    4. 

  4. CR3 points at the PML4 the CPU uses for every access, including the kernel's own code and stack (through the shared entry 0). Freeing it, or the tables below it, while loaded means the CPU may walk freed frames that are reused for something else.
    5. 

  5. Both the scan and the sleep happen with proc_lock held, and WaitQueue::sleep releases it only after the thread is on the queue; the exiting child needs proc_lock to set exited and wake the queue, so it either runs before the scan (and is found) or after the parent is queued (and wakes it).
    6. 

  6. In the middle of kernel code the thread may hold locks or be halfway through updating a structure; killing it there would leave them locked or inconsistent. At the boundary it holds nothing and its kernel state is clean.
    7. 

  7. Strings: "dddd" 5, "ccc" 4, "bb" 3, "a" 2 = 14 bytes (placed in reverse order: the last argument highest), lowest string at 0xFF_FFFF_F000 − 14 = 0xFF_FFFF_EFF2. Words: 1 + 4 + 1 + 1 + 12 = 19 words = 152 bytes; 0xFF_FFFF_EFF2 − 152 = 0xFF_FFFF_EF5A; rounded down to 16: 0xFF_FFFF_EF50.
    8. 

  8. It copies the bytes of both segments into one frame and maps it writable (the union of permissions), executable bits aside — so the code bytes on that page are writable from ring 3. A program (or an attacker controlling its input) could then modify its own code on that page; strict loaders refuse such files or map the page with the intersection, at the cost of breaking some linkers' output.
    9. 

  9. Coverage feedback (so that mutants that reach new checks are kept), a corpus of real executables from several linkers as seeds, a faster loop (KVM, or the host harness for the validator), and invariants that are checked automatically (sanitizers on the host, memory statistics and the absence of kernel faults in the kernel), plus a record of what was covered — not just the elapsed time.
    10. 



Forensic lab answer key


Observation. Free frames fall from 64,749 to 59,749 after 1000 cycles and by exactly 5,000 per 1000 cycles after that, down to 14,749 after 10,000: 5 frames per cycle, constant. Heap objects, threads and processes stay at the baseline, so Process objects, thread stacks and control blocks are freed; only raw frames leak.


Frames per cycle. One PML4; for 0x80_0040_1000: PML4 index (0x80_0040_1000 >> 39) & 511 = 1, PDPT index (>> 30) & 511 = 0, PD index (>> 21) & 511 = 2; for 0xFF_FFFF_E000: PML4 index 1, PDPT index 511, PD index 511. Same PML4 entry, so one PDPT; two PDPT entries, so two page directories; two PD entries in different directories, so two page tables. Tables below the PML4: 1 + 2 + 2 = 5. Leaves: the stack page (built at spawn) and the code page (demand-faulted), plus the PML4 itself.


Match. The leak is exactly the 5 paging-structure frames below the PML4. Leaves and the PML4 are still freed (otherwise the count would be 7 or 8).


Root cause. In the forensic build, process.cc lines 90–100 (#ifndef BUG_LEAK_PAGE_TABLES around frame_free of the page table, the page directory and the PDPT) are compiled out: free_address_space frees the leaves and the PML4 but not the intermediate tables.


Survival time. About 64,000 free frames at 5 per spawn: about 12,800 spawns, about 13 seconds at one spawn per millisecond.


Fix and prevention. Free every level, as the normal build does. Keep the exec/exit loop with its per-1000 statistics in the test suite: a constant slope finds a 5-frame leak that a single spawn would never show, and dividing the slope by the cycle count names the culprit.
