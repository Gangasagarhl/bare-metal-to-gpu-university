Story hook

A teacher on homework duty sits with one student at a time. When Amara gets stuck, she closes her notebook, the teacher writes "page 14, line 3" on a bookmark, and moves to Kwame, opens his notebook at his bookmark and carries on exactly where they left off. Each student keeps their own notebook; the teacher only needs the bookmark to pick up the thread.

The system works well until Lior arrives. Lior never says "I am stuck". He keeps talking, happily, for the whole afternoon, and the teacher never reaches anyone else. The school's fix is simple and slightly rude: every ten minutes a bell rings, and when it rings the teacher puts a bookmark in whatever notebook is open and moves to the next student in the queue, whether the student likes it or not.

This chapter builds that teacher, those notebooks, those bookmarks and that bell inside the kernel of OS302: kernel threads with their own stacks, a context switch of fourteen instructions, a run queue, an idle thread, and preemption driven by the local APIC timer of F3-25.

What you will be able to do

  • Explain what a kernel thread is made of (a control block, a kernel stack, saved registers) and why only the callee-saved registers need saving in a voluntary switch.
  • Write a context switch in a few lines of assembly and build the first stack frame of a thread that has never run.
  • Build a run queue, an idle thread that halts the CPU, sleep and wake on timer ticks, and round-robin preemption from the timer interrupt.
  • Place every kernel stack in its own slot with an unmapped guard page, and free a dead thread's stack safely (never on that stack).
  • Prove the three B9 acceptance tests in QEMU: fairness for 100 threads, preemption of an infinite loop, and 100,000 create/exit cycles with no leak.
  • Diagnose a kernel stack overflow from a double-fault dump, CR2 and addr2line.
Jargon box
Kernel thread
Simple words: a piece of kernel work that can be paused and resumed, with its own place to keep its unfinished business. Analogy: a student with a notebook. Precise: an independently scheduled flow of execution in kernel mode, made of a control block (here struct Thread) and a private kernel stack; while it is not running, its register state is saved on that stack. D3 R2
Kernel stack
Simple words: the scratch memory a thread uses for function calls inside the kernel. Analogy: the student's own notebook. Precise: a region of kernel memory used as the call stack while the thread runs in ring 0; in this kernel 16 KiB (four 4 KiB pages) per thread, mapped in a slot of the stack area that starts at 4 GiB. R2
Guard page
Simple words: an empty, unmapped page placed just below a stack so that running off the end crashes loudly instead of silently overwriting something. Analogy: a sheet in the notebook that tears if you write on it. Precise: a page of virtual addresses with no translation; any access raises a page fault, so a stack overflow is detected at its first byte. D1 R3
Context switch
Simple words: stopping one thread and starting another on the same CPU. Analogy: bookmark one notebook, open the next at its bookmark. Precise: saving the register state of the running thread and loading the saved state of another; in this kernel, pushing the callee-saved registers, swapping the stack pointer and popping them (switch.S). D2
Callee-saved register
Simple words: a register that a function promises to give back unchanged. Analogy: the pages you must leave as you found them. Precise: in the System V AMD64 ABI, RBX, RBP, R12–R15 (and RSP) must be preserved across a call; the caller cannot assume anything about the others. D2
Run queue
Simple words: the line of threads that are ready to run and waiting for a CPU. Analogy: the queue of students waiting for the teacher. Precise: a data structure holding the threads in state Ready; here one global FIFO list protected by one spinlock. D3
Idle thread
Simple words: the thread a CPU runs when nobody else is ready; it sleeps until something happens. Analogy: the teacher marking papers until a hand goes up. Precise: a per-CPU thread that never blocks, which loops on "look for work, then sti; hlt"; it is never put in the run queue. D1
Preemption
Simple words: taking the CPU away from a thread that did not offer it. Analogy: the bell. Precise: a switch forced from outside the running code, here at the end of the timer interrupt handler, when the thread's time slice is used up and no spinlock is held. D3
Time slice (quantum)
Simple words: how long a thread may run before the next one gets a turn. Analogy: ten minutes between bells. Precise: in this kernel one timer tick, 10 ms of the calibrated APIC timer at 100 Hz (kTickHz, kQuantumTicks). R2
Interrupt stack table (IST)
Simple words: a list of spare stacks the CPU can switch to for chosen interrupts, even in kernel mode. Analogy: an emergency notebook kept in the teacher's drawer. Precise: seven stack pointers in the 64-bit TSS; an IDT gate with a non-zero IST index makes the CPU load that stack before pushing the interrupt frame. D1
Double fault
Simple words: the CPU's "I failed to report a fault" fault. Analogy: the fire alarm going off while you were calling about the first fire. Precise: exception 8, raised when the CPU cannot deliver certain exceptions (here: a page fault whose frame cannot be pushed because the stack itself is unmapped). D1
Zombie (thread)
Simple words: a finished thread whose memory has not been cleaned up yet. Analogy: a student who has gone home but whose notebook is still on the desk. Precise: a thread in state Dead that is still on the zombies list; its stack can be freed only by another thread, because a thread cannot free the stack it is running on. R2

"Thread" here is a CPU thread in the operating-system kernel. GPU threads (F6) are a different thing with the same name, and "kernel" here means the operating-system kernel, not a GPU kernel.

Layer 1 — the kid explanation

Analogy

One teacher, many students, each with a notebook. To switch, the teacher bookmarks the open notebook and opens the next one at its bookmark. Students who are stuck put up their hand and wait (blocked); students who are ready queue up (ready). A bell every ten minutes makes sure a chatterbox cannot keep the teacher forever. When nobody needs help, the teacher rests until a hand goes up.

A computer's processor can only follow one list of instructions at a time. To do many jobs "at once", the kernel lets each job run for a short while, then saves exactly where it was and lets the next one run. It saves so carefully that each job never notices it was paused.

Layer 2 — the student explanation

The kernel of OS302 runs one flow of code from kmain to the end. A kernel thread lets it run several. Each thread is a struct Thread (its name, its state, the saved stack pointer, links into lists) plus a private kernel stack. While a thread is not running, everything it needs to continue is on that stack.

The switch. Switching from thread A to thread B happens inside a normal C++ function call: switch_context(&A->rsp, B->rsp). The ABI already says which registers a callee must preserve: RBX, RBP and R12–R15 (plus RSP) D2. The compiler assumes every other register may be destroyed by any call, so it has already saved whatever it needed. switch_context therefore pushes only those six registers, stores RSP into A's control block, loads B's saved RSP, pops B's six registers and returns. The return lands in B's copy of the code that called switch_context some time ago. That is the whole trick: a switch is a function call that returns into a different thread.

The first switch into a new thread. A thread that has never run did not call switch_context, so thread_alloc builds by hand the frame that a call would have left: six register slots (with the entry function in R12 and its argument in R13) and a return address pointing at thread_start. The first switch into it pops those values and "returns" into thread_start, which enables interrupts and calls the entry function. If the function returns, thread_start calls thread_exit.

The run queue and the policy. Ready threads wait in a first-in, first-out list. schedule() takes the current thread, puts it at the back of the list if it is still runnable, takes the first thread from the front and switches to it. That is round robin D3. If nobody is ready, the CPU runs its idle thread, which executes sti; hlt: enable interrupts and halt until the next one.

Preemption. If threads called thread_yield() politely, that would be enough (cooperative scheduling). The B9 tests contain a thread in an infinite loop that never yields. So the timer interrupt of F3-25 now ends with a decision: when the running thread has used its time slice (one 10 ms tick here), the handler sets need_resched, and after the interrupt work is done, trap_dispatch calls schedule(). The interrupted thread's registers are already saved in the trap frame on its stack, so switching away from inside the handler is safe: when the thread is switched back in, it finishes the handler and returns from the interrupt as if nothing had happened. Listing 7, a host model, shows the difference in numbers: with cooperative scheduling one spinner keeps the CPU for all 40 slices; with a quantum of 2 the other two jobs finish at slices 8 and 16 R4.

Sleeping. thread_sleep_ticks(n) records a wake tick, marks the thread Blocked, puts it on a sleep list and switches away. CPU 0's timer handler moves every sleeper whose time has come back to the run queue. Blocked threads use no CPU time.

Ending. thread_exit() marks the thread Dead and switches away for the last time. It cannot free its own stack: it is standing on it. The scheduler puts it on a zombie list, and thread_reap_zombies(), called later by some other thread, unmaps the stack pages, returns the frames and frees the control block.

Layer 3 — the engineer's depth

The scheduler lock is handed across the switch

The run queue is shared by every CPU (from F3-28 on), so it is protected by one spinlock, g_sched. The delicate moment is the switch itself. Thread A puts itself on the run queue and then switches away. If A released the lock before switching, another CPU could take A from the queue and start running it while A's registers are still being pushed onto A's stack: two CPUs on one stack. The lab kernel therefore keeps the lock held through switch_context and lets the thread that switches in release it: either in finish_switch() right after switch_context returns (thread.cc line 152), or in thread_start/idle_loop for a thread's first run. xv6 uses the same handover in its scheduler D4. For this reason g_sched is excluded from the lock-order checker of F3-27: it is acquired by one thread and released by another, which the checker cannot model.

Where preemption is allowed

Preemption happens only at the end of trap_dispatch and only if three conditions hold (trap.cc lines 113–116): a reschedule was requested, this CPU holds no spinlock (preempt_count == 0), and it is not nested inside another interrupt handler (irq_depth == 0). Switching away while holding a spinlock would leave other CPUs spinning until the holder is scheduled again; switching inside a nested handler would leave the outer handler half done. Every Spinlock::lock() increments preempt_count and every unlock() decrements it, so the rule costs one counter. Linux uses the same idea under the same name D6.

The idle thread and the lost-wake-up window

The idle loop disables interrupts, calls schedule() to run anything that is ready, then executes sti; hlt. The pair matters. If the code enabled interrupts, checked "anything ready?", and then halted, an interrupt arriving between the check and the halt could make a thread ready and the CPU would still go to sleep until the next tick. The x86 sti instruction delays interrupt delivery until after the following instruction, so sti; hlt enters the halt with no window D1. That property is register-level behaviour from memory: see the unverified box in the hardware section.

Stack slots and guard pages

Kernel stacks do not come from the heap of F3-22. They live in a dedicated stack area starting at 4 GiB (above the identity map of the first 4 GiB). Slot s covers five pages starting at 0x1_0000_0000 + s × 0x5000: the lowest page is never mapped (the guard page), and the four pages above it are mapped to freshly allocated frames when the thread is created (thread_alloc, lines 88–92). A thread that writes below its stack touches the guard page and faults immediately, instead of overwriting another thread's stack or a heap object. Freeing a stack unmaps the four pages and then calls tlb_shootdown() (F3-28), so that no CPU keeps a cached translation to frames that are about to be reused.

What a stack overflow looks like

A page fault in kernel mode does not switch stacks: the CPU pushes its exception frame onto the current stack. If the current stack pointer is already inside the guard page, that push faults too. The CPU gives up on the page fault and raises a double fault. If the double fault also used the broken stack, the third fault would reset the machine (a triple fault, F3-19). So idt_init marks vector 8 to use IST1, a 4 KiB emergency stack per CPU (cpu.cc line 36). The forensic lab of this chapter is exactly this sequence, recorded.

Reaping, leaks and the 100,000-cycle test

The third B9 test creates and finishes 100,000 threads and requires frames, heap objects, stack slots and the thread count to return to the baseline C1. Two details made it pass. First, a warm-up of 100 threads runs before the baseline is taken: the stack area's own page tables are created on first use and never freed, which is fine, but they must exist before the baseline. Second, zombies are reaped in thread_create and in the test's snapshot, never with interrupts disabled, because freeing a stack calls a TLB shootdown that waits for other CPUs to answer an interrupt (F3-28).

What this scheduler deliberately leaves out

  • Priorities. B9 says "a simple round-robin policy, then priorities" C1. This chapter stops at round robin; priorities are the mini-project.
  • Floating-point and SIMD state. The kernel is compiled with -mgeneral-regs-only, and user programs in F3-29 and F3-30 are too, so no thread ever has SSE or x87 state to save. A real kernel must save it (FXSAVE/XSAVE) on switches between user threads D1.
  • One global run queue. Per-CPU queues with work stealing come later (B11 allows "a global queue first").
  • No higher-half kernel. OS302 linked its kernel at the top of the address space. The OS303 teaching kernel is a fresh, smaller kernel loaded at 1 MiB and identity-mapped, so that one build serves all five chapters; the ideas are unchanged.

How the hardware actually does it

Three pieces of hardware behaviour carry the whole chapter. The interrupt frame: when an interrupt arrives in 64-bit mode the CPU pushes SS, RSP, RFLAGS, CS and RIP (plus an error code for some exceptions) and jumps through the IDT; through an interrupt gate it also clears RFLAGS.IF, so the handler starts with interrupts disabled D1. trap.S pushes the general registers on top, which forms the TrapFrame of cpu.h. The timer: the local APIC timer of F3-25, calibrated here against PIT channel 2, interrupts each CPU 100 times per (guest) second on vector 32 R2. The halt: hlt stops the CPU until the next interrupt.

Not verified — check before relying on this

Written from memory and not checked against the Intel SDM or AMD64 APM in this build: the 64-bit interrupt frame layout (SS, RSP, RFLAGS, CS, RIP, error code); interrupt gates clearing IF; vector 8 = double fault and the "contributory/page fault" rules that turn a fault during delivery into a double fault; the TSS layout with IST1–IST7 at the offsets in cpu.h; the IDT gate type 0x8E; the one-instruction interrupt shadow after sti; the PIT input clock of 1 193 182 Hz and port numbers 0x42, 0x43, 0x61 in lapic.cc; the Multiboot v1 magic numbers in boot.S; that a local APIC keeps at most one pending interrupt per vector, so missed timer ticks are not delivered one by one. The QEMU runs prove that these values work on QEMU 8.2.2's TCG model of a PC, and nothing more. The Source Researcher must confirm each against the SDM Vol. 3 ("Interrupt and Exception Handling", "Task Management", "Instruction Set Reference" for STI/HLT), the 8254 PIT datasheet and the Multiboot Specification (D1, D7, D8).

Note

Untested on hardware: every run in this chapter is QEMU 8.2.2 in TCG mode (software emulation) in the build container, which has no KVM. The "seconds" of the tests are guest timer ticks, not wall-clock seconds: under TCG, guest time and host time drift apart, which is why fairness is measured in ticks.

Worked example

Building the first frame of a thread in slot 1. The forensic run below crashed in a thread whose stack slot was 1, so take that slot. Slot 1 starts at 0x1_0000_0000 + 1 × 5 × 0x1000 = 0x1_0000_5000. The guard page is 0x1_0000_5000–0x1_0000_5fff; the stack pages are 0x1_0000_6000–0x1_0000_9fff; kstack_top = 0x1_0000_a000. The crash dump of the forensic run prints exactly these ranges R3.

thread_alloc then writes seven 8-byte words downwards from the top:

AddressValuePopped by switch_context as
0x1_0000_9ff8address of thread_startreturn address of ret
0x1_0000_9ff00RBP
0x1_0000_9fe80RBX
0x1_0000_9fe0entry function fnR12
0x1_0000_9fd8argument argR13
0x1_0000_9fd00R14
0x1_0000_9fc80R15 ← t->rsp

The first switch_context into this thread loads RSP = 0x1_0000_9fc8, pops R15, R14, R13, R12, RBX, RBP (RSP is now 0x1_0000_9ff8), and ret pops thread_start into RIP, leaving RSP = 0x1_0000_a000, the very top. thread_start calls finish_switch (the scheduler lock is released), enables interrupts, moves R13 into RDI (the first argument register) and calls R12. One detail: the ABI wants RSP to be a multiple of 16 plus 8 at function entry (right after a call pushed its return address); thread_start is entered by ret with RSP a multiple of 16, and its call pushes 8 bytes, so fn starts correctly aligned D2. Notice also that RSI in the crash dump of the forensic run is 0x1_0000_9fc8: the value switch_context received as the new thread's stack pointer when the crashing thread was first switched in.

The fairness bound. The B9 test leaves the choice of bound to the student C1. With 100 threads and a 10 ms quantum, each thread gets one slice per round of 100 ticks, so in about 500 ticks each thread gets about five slices; one extra or one missing slice is a 20 % difference. The bound "every counter non-zero and max/min ≤ 2" allows for that and for slices that are cut short by interrupts, while still failing a scheduler that starves anybody. In this build the measured ratio was well inside it (Listing 6 output) R2.

Where the analogy breaks


    

  • The teacher is a student too. The kernel's scheduler is not a separate person: it is code that runs on the very CPU it manages, on the stack of whichever thread called it. That is why the handover of the scheduler lock across the switch is needed; a real teacher never has this problem.
    • 

  • Bookmarks are not enough for every notebook. A bookmark records one page. A context switch must record every register the thread may still need, and which registers those are is a contract (the ABI), not common sense. A preempted thread is saved twice: its full register set in the trap frame, then six registers by switch_context.
    • 

  • Students know when they are interrupted. A preempted thread does not. Nothing in its code marks the place; any instruction can be the last before a switch, which is why shared data needs the locks of F3-27.
    • 

  • The "ten minutes" are not ten minutes. Under emulation the tick is guest time; the teacher's clock and the wall clock do not agree.
    • 




Common mistakes and debugging


    

  • Saving the wrong registers. Forgetting one callee-saved register gives bugs that appear only when the compiler happens to keep a value there across the call. Compare switch.S with the ABI list, and check that pushes and pops are in mirror order.
    • 

  • Releasing the scheduler lock before the switch. Works on one CPU, corrupts stacks on several: two CPUs run the same thread. Symptom: random crashes with RSP inside another thread's slot.
    • 

  • Freeing a thread's stack in thread_exit. The function is still running on that stack; the next push lands in a freed (or unmapped) page. Use a zombie list.
    • 

  • Calling schedule() with a spinlock held. Another thread then spins for a lock whose owner is not running. The preempt_count check prevents this for preemption; for explicit calls, F3-27's lockup detector reports it.
    • 

  • Enabling interrupts too early in a new thread. thread_start must release the scheduler lock before sti; otherwise the timer interrupt can try to reschedule while the lock is still held by this CPU.
    • 

  • A red zone in kernel code. Without -mno-red-zone, leaf functions may keep data below RSP, and an interrupt frame pushed there overwrites it.
    • 

  • Debugging method. When a thread misbehaves, call sched_dump() (it prints every thread, its state, its last CPU and how often it ran) and boot QEMU with -d int to see interrupts and exceptions as they are delivered; for crashes, take the RIP and the backtrace to addr2line -f -i -e kernel.elf.
    • 




Transition box

Where you came from: OS302 ended with a kernel that boots, handles exceptions, manages memory, has a heap, a console, the local APIC and timers (F3-18 to F3-25) — one flow of code. What carries over: the IDT and trap frame, the frame allocator and kmap_page, the APIC timer and its calibration, the panic path that never waits for the console lock. What changes: the kernel now runs many threads, each with its own stack and guard page, switched by a timer-driven round-robin scheduler; every shared structure from here on can be touched by two threads "at once". What comes next: F3-27 makes that safe: spinlocks that respect interrupts, sleeping mutexes, semaphores and condition variables built on this chapter's wait queues, and a checker that catches lock-order inversions before they deadlock.

Summary


    

  • A kernel thread is a control block plus a private kernel stack; while it is not running, its state is on that stack.
    • 

  • A context switch is a function call that returns into a different thread: push the six callee-saved registers, swap RSP, pop, return. A new thread gets a hand-made frame that "returns" into thread_start.
    • 

  • Round robin keeps a FIFO of ready threads; the idle thread halts with sti; hlt; sleepers are woken by the tick.
    • 

  • Preemption happens at the end of the timer interrupt, only with no spinlock held and no nested handler. The scheduler lock is handed from the outgoing to the incoming thread.
    • 

  • Stacks live in slots with unmapped guard pages; an overflow becomes a double fault on IST1 with CR2 inside the guard page. Dead threads are reaped by other threads.
    • 

  • In this build all three B9 tests passed under QEMU TCG, and the forensic overflow was caught and located by addr2line; nothing was tested on hardware.
    •

Answers to Check yourself


    

  1. RBX is callee-saved: the code that called switch_context may keep a value in it and expects it back. RAX is caller-saved (and holds return values): the compiler has already saved anything it needed from it before the call. Saving it would be harmless but useless.
    2. 

  2. Slot 3 starts at 0x1_0000_0000 + 3 × 0x5000 = 0x1_0000_f000; guard page 0x1_0000_f000–0x1_0000_ffff; stack 0x1_0001_0000–0x1_0001_3fff; top 0x1_0001_4000; initial t->rsp = top − 7 × 8 = 0x1_0001_3fc8.
    3. 

  3. Good answers say: while the old thread's registers are being saved it is already on the run queue; if the lock were free, another CPU could pick that thread and start running on its stack at the same time. Holding the lock until the switch is complete, and letting the new thread (which knows the switch is complete) release it, closes the window.
    4. 

  4. An interrupt between schedule finding nothing and hlt could make a thread ready (say, a timer wake-up); the CPU would then halt anyway and the thread would wait for the next interrupt: a lost wake-up of up to one tick. sti as the instruction right before hlt closes the window because interrupts are recognised only after the next instruction (see the unverified box).
    5. 

  5. In ring 0 the CPU pushes the page-fault frame on the current stack, which is the guard page; the push faults during delivery, so the CPU raises a double fault. If the double fault were also delivered on that stack, it would fault a third time and reset the machine; IST1 gives it a known-good stack.
    6. 

  6. The cooperative policy lets the running job keep the CPU until it yields. "editor" yields after slice 1, then "spinner" runs and never yields, so slices 2 to 40 all go to it. Yielding is only as good as the worst job's manners.
    7. 

  7. A reschedule was requested (otherwise there is nothing to do); preempt_count == 0 (otherwise other CPUs spin on a lock whose owner is switched out, and on one CPU the next thread to take that lock spins forever); irq_depth == 0 (otherwise an outer handler is left half-finished and its interrupt source may stay unacknowledged).
    8. 

  8. Ticks are counted by CPU 0's timer interrupt, so while interrupts are masked no ticks happen and no sleeper is woken; the thread wakes only some ticks after interrupts are enabled again, and the ticks missed while they were masked are not made up (pending timer interrupts are not queued one by one; see the hardware section's unverified box for this kind of detail). Sleeping guarantees "at least", never "exactly"; a long interrupts-off section delays every sleeper, and the tick counter itself loses time.
    9. 

  9. The stack area's page tables (one page table per 2 MiB of stack area, and its parents) are allocated the first time a slot in that range is used and are kept on purpose. Without the warm-up the baseline would be taken before they exist and the comparison would report a "leak" of those few frames. It is not cheating as long as the warm-up is bounded and the test then runs 100,000 more cycles with constant memory, which is what B9 asks.

Forensic lab answer key


Observation. The dump says "double fault (vector 8)" in thread 3 'parser'. The thread's stack is 0x1_0000_6000–0x1_0000_9fff and its guard page 0x1_0000_5000–0x1_0000_5fff; CR2 = 0x1_0000_5f68 is inside the guard page, and so is RSP = 0x1_0000_5f70. RIP = 0x101cc0 resolves to parse_group, test_threads.cc:134 (scratch[0] = s[0]); the backtrace repeats return address 0x101d01 (line 136, the recursive call) and ends in parser_thread (line 144).


Hypotheses. A bad pointer would give a page fault with a CR2 far from the stack, not 8 bytes below RSP; a corrupted return address would show a backtrace into nonsense; a stack overflow predicts CR2 and RSP inside the guard page and a deep repetition in the backtrace. Only the last fits.


Root cause. Each call reserves 0x800 bytes (Evidence 3: sub $0x800,%rsp): the compiler inlined one level of recursion into the other, so each real frame holds two 1 KiB scratch buffers (at -0x800 and -0x400 from RBP) plus the saved RBP and return address, about 2 KiB for two levels. The 16 KiB stack holds about 8 such frames, about 16 levels, minus the frames below the parser. Depth 7 fits; depth 39 does not. The sub moved RSP into the guard page; the next store, at RIP 0x101cc0, faulted with CR2 = RSP. The CPU then tried to push the page-fault frame at RSP − 8 = 0x1_0000_5f68, which faulted again: that second fault is the one CR2 now records, and it turned into a double fault delivered on IST1.


Fix. Do not put kilobyte buffers on a kernel stack: allocate the scratch buffer once (heap or caller), make the parser iterative, and reject input deeper than a fixed limit with an error.


Prevention. Keep guard pages (they turned silent corruption into a precise report); compile the kernel with -Wframe-larger-than=512 (GCC option) so a 2 KiB frame is a build error; add a depth limit to every recursive kernel function; and keep this forensic test in the lab so the double-fault path itself stays tested.
