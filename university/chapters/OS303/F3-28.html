Story hook

For years the school had one teacher on duty. Now the principal hires seven more. On the first morning the principal phones each new teacher at home: "wake up" (they get dressed), then "come in through the side door at number 8" (they arrive, twice in case the first call was missed). Each new teacher finds a desk with a drawer of their own, a copy of the timetable, and a pad of sticky notes for the locker numbers they look up most.

Two problems appear in the first week. The locker map changes, and the principal updates the big map in the office, but teachers keep using their sticky notes and send students to lockers that are now somebody else's. The principal learns to phone every teacher, "tear up your note for locker 1407", and to wait until each has said "done".

The second problem is at the school bank, where two tellers move money between the accounts of Alice and Bob. With one teacher on duty, transfers happened one after another and never collided. With eight, a teller holding Alice's ledger waits for Bob's, while another holds Bob's and waits for Alice's. The bank froze on the first busy day. Its log, recorded in this build, is the course's forensic case "Works on 1 CPU, hangs on 8".

What you will be able to do

  • Find every processor in the ACPI MADT, starting from the RSDP, with checksums.
  • Start application processors with INIT-SIPI-SIPI and a real-mode trampoline that climbs to long mode and calls C++.
  • Give each CPU its own GDT, TSS, double-fault stack, idle thread and APIC timer, and reach its data in one instruction through the GS base.
  • Send inter-processor interrupts for rescheduling and for TLB shootdown, and prove with a test that no CPU keeps a stale translation.
  • Run the B11 acceptance tests for 1, 2, 4, 8 and 16 CPUs in QEMU and re-run the B10 producer/consumer test on 8 CPUs.
  • Diagnose an SMP deadlock from a lock-order report and per-CPU lockup logs (the model for exam P).
Jargon box
SMP (symmetric multiprocessing)
Simple words: several CPUs sharing one memory and running one kernel. Analogy: several teachers in one school, one timetable. Precise: a system in which all processors have equal access to memory and devices and any of them can run any kernel or user code. D1
Bootstrap processor (BSP)
Simple words: the one CPU that starts running at power-on. Analogy: the principal, first in. Precise: the processor selected by the hardware to execute the firmware and the boot loader; all others wait. D1
Application processor (AP)
Simple words: every other CPU, asleep until the kernel wakes it. Analogy: the new teachers at home. Precise: a processor that stays in a wait-for-SIPI state after reset until the BSP sends it the start-up sequence. D1
INIT-SIPI-SIPI
Simple words: the three messages that wake an AP and tell it where to start. Analogy: "wake up", then "come in at side door 8", said twice. Precise: an INIT inter-processor interrupt, a delay, then two start-up IPIs whose vector field gives the 4 KiB page at which the AP starts executing in real mode (vector 0x08 = address 0x8000 in this kernel). D1
Trampoline
Simple words: a small piece of start-up code copied below 1 MiB, where a CPU in 16-bit mode can reach it. Analogy: the side door and the staircase to the staff room. Precise: code that takes an AP from real mode through protected mode to long mode with the BSP's page tables, then jumps to the kernel's C++ entry (trampoline.S). R2
Per-CPU data
Simple words: variables that exist once per CPU, so each CPU has its own copy. Analogy: each teacher's desk drawer. Precise: here the Cpu structure (current thread, idle thread, tick count, preemption count, GDT, TSS, double-fault stack); each CPU's GS base register points at its own, and %gs:0 holds its address. R2
GS base
Simple words: a register that adds an offset to every memory access that uses the GS segment. Analogy: "your drawer" means a different drawer for each teacher. Precise: in 64-bit mode, the base of the GS segment, set through a model-specific register; mov %gs:0, %rax reads the first 8 bytes of this CPU's Cpu. D1
Inter-processor interrupt (IPI)
Simple words: an interrupt one CPU sends to another. Analogy: the principal phoning a teacher. Precise: a message sent by writing the local APIC's interrupt command register (ICR): destination APIC id, vector or special type (INIT, SIPI). This kernel uses vector 0xF0 for TLB shootdown and 0xF1 for "reschedule". D1
TLB shootdown
Simple words: telling every CPU to forget a translation that was just removed. Analogy: phoning every teacher to tear up one sticky note. Precise: after changing or removing a page-table entry, invalidating it locally (invlpg) and sending an IPI to every other CPU that may cache it, whose handler invalidates it too; the initiator waits until all have acknowledged before the old frame may be reused. D1 R3
Stale TLB entry
Simple words: an old translation a CPU still uses after the page table changed. Analogy: an out-of-date sticky note. Precise: a TLB entry that no longer matches the page tables; the CPU keeps using it until it is invalidated or evicted, so reads and writes reach the old frame. R3
ABBA deadlock
Simple words: one CPU holds A and waits for B while another holds B and waits for A. Analogy: two students each holding a book the other needs. Precise: a deadlock whose wait-for graph is a two-lock cycle; possible whenever two code paths take the same two locks in opposite orders and can run in parallel. D4 R4

The idea in pictures

Layer 1 — the kid explanation

Analogy

A computer with several CPUs is a school with several teachers. Only the principal is awake at first; the principal has to phone each teacher to come in. Each teacher gets their own desk drawer for their own things. When the locker map changes, every teacher must throw away their old notes. And rules that never mattered with one teacher ("take Alice's book, then Bob's") suddenly matter, because now two teachers can do it at the same moment, in opposite orders.

More CPUs means more work done at the same time, but also more ways for things to go wrong at the same time. Code that was "safe because only one thing happens at once" stops being safe.

Layer 2 — the student explanation

Finding the CPUs. The firmware lists the processors in the ACPI MADT (F3-24 parsed it for interrupt controllers). acpi.cc finds the RSDP by scanning for the signature "RSD PTR " in the EBDA and in 0xE0000–0xFFFFF, follows it to the RSDT (or XSDT), finds the table with signature APIC, and walks its entries. Type 0 entries are processors: an ACPI processor id, a local APIC id and a flags word whose bit 0 means "enabled" D2. With -smp 8, QEMU's firmware listed eight enabled processors with APIC ids 0–7, one I/O APIC and five interrupt source overrides R1.

Starting an AP. After reset, each AP waits. The BSP sends it an INIT IPI, waits 10 ms, then a start-up IPI (SIPI) whose 8-bit vector says where to start: page 0x08, address 0x8000, twice D1. The AP starts in 16-bit real mode, so its first code must be below 1 MiB: the kernel copies the trampoline there. The trampoline repeats in a few lines what OS301's boot path did: load a GDT, enter protected mode, enable PAE, load the BSP's page tables (the low memory is identity-mapped, so the code at 0x8000 stays reachable), enable long mode and paging, load a stack and call ap_entry. The BSP fills four variables at the end of the trampoline before each start: CR3, the stack, the entry function and a pointer to the AP's Cpu. It then polls the AP's online flag for up to one second.

Making the AP a full member. ap_entry gives the AP its own GDT and TSS (each CPU needs its own TSS: it holds this CPU's double-fault stack and, from F3-29, its ring-0 stack pointer), loads the shared IDT, sets the GS base to its Cpu, initialises its local APIC, turns its start-up code into its idle thread, enables SYSCALL (F3-29), starts its timer at 100 Hz and sets online. From then on it runs F3-26's idle loop and takes threads from the global run queue.

Per-CPU data. Many kernel variables are really "this CPU's": the current thread, the idle thread, the tick count, preempt_count, irq_depth. They live in one Cpu object per CPU. The GS base register of each CPU points at its own object, and the first field of the object is its own address, so this_cpu() is a single mov %gs:0, %rax R2.

IPIs. A CPU can interrupt another by writing the local APIC's interrupt command register. The kernel uses two vectors. 0xF1, "reschedule": sched_make_ready sends it to an idle CPU so that a newly ready thread does not wait for that CPU's next tick. 0xF0, "TLB shootdown".

TLB shootdown. Each CPU caches translations in its own TLB. When the kernel removes a mapping (a thread's stack in thread_reap_zombies, the probe page of the test), invalidating the entry on the current CPU is not enough: the others may still hold it and keep using the old frame, even after that frame has been given to someone else. tlb_shootdown invalidates locally, interrupts every other online CPU, and waits until each has invalidated the page too. The B11 test pins one probe thread on each CPU, lets every CPU read a page, unmaps it, shoots it down, and checks that every CPU's next read faults. In this build, with the shootdown, all 8 CPUs faulted with zero reads after the shootdown completed; with the shootdown switched off, only the unmapping CPU faulted and the others went on reading the freed frame millions of times R3.

Locks under real parallelism. The B10 producer/consumer test now runs with 4 producers and 4 consumers on 8 CPUs, and the scheduler hands threads to all CPUs. F3-27's locks did not change, but code that only ever ran one thread at a time now really runs in parallel. The forensic case shows what that means for code that was "tested".

Layer 3 — the engineer's depth

Writing position-dependent code at a fixed address

The trampoline is linked into the kernel image (somewhere above 1 MiB) but runs at 0x8000. Every absolute address inside it is therefore written as 0x8000 + (label − tramp_start), and the variables are patched at their copied location (patch(), smp.cc lines 31–34). The far jumps load code selectors from the trampoline's own four-entry GDT; once in 64-bit mode, ap_entry loads the kernel's real per-CPU GDT through cpu_setup. The AP initially runs on a 16 KiB static boot stack (ap_boot_stacks), which becomes the stack of its idle thread; unlike thread stacks it has no guard page, a simplification worth remembering when reading a crash on an idle thread.

One AP at a time

The BSP starts the APs one after another, re-patching the same trampoline variables and waiting for each to come online before starting the next. Starting all at once with a broadcast INIT-SIPI-SIPI is faster but needs one stack per AP chosen by the AP itself (for example by its APIC id), and it starts processors the MADT marks as disabled. The sequential version is slower and much easier to debug: if an AP never comes online, the log names it (line 84 of smp.cc).

The hazard of per-CPU data: moving while you read

this_cpu() returns a reference to the current CPU's object. If the thread is preempted right after that and continues on another CPU, the reference now points at the old CPU's data. Reading a counter for a log line is harmless; changing preempt_count or the run queue through it would corrupt another CPU's state. The kernel touches per-CPU fields that matter only with interrupts disabled or a spinlock held (both prevent preemption), which is the rule Linux states for its per-CPU variables too D5. The test code that prints this_cpu().id from a teller thread is exactly the harmless case.

Why the shootdown needs interrupts enabled

The initiator spins until every other CPU has answered its IPI. If two CPUs started shootdowns at the same time with interrupts disabled, each would wait for the other to handle an interrupt it can never take: a deadlock. The lab avoids it twice: shoot_lock serialises shootdowns, and tlb_shootdown asserts that interrupts are enabled, so a CPU waiting for the lock or for answers can still answer someone else's IPI (line 120). This is also why F3-26's zombie reaping is skipped when interrupts are off. A two-second timeout turns a lost IPI into a panic instead of a hang. Real kernels batch shootdowns, send them only to CPUs that may have used the address space, and use PCID or ASIDs to avoid flushing more than needed D3; none of that is done here.

The scheduler on several CPUs

F3-26's design was already SMP-ready: one global run queue under one lock, the lock handed over across the switch, rq_pop_for honouring pinned threads, and sched_make_ready waking one idle CPU with an IPI. The test prints the set of CPUs on which 32 short, sleeping threads ran; in the passing runs of this build the mask was never "all eight" (the recorded run shows 0x3, CPUs 0 and 1; an earlier run showed 0x87) R2. With a single queue and threads that sleep for one tick, whichever CPU is awake when a thread becomes ready takes it; that is correct, just not balanced. The check is informational in this lab, and balancing is left to per-CPU queues with work stealing.

What was re-run, and at what size

B11 asks that "B10 tests pass on 8 CPUs, 100 runs in a row, under KVM and TCG" C1. The build container has no KVM, so only TCG was run. Under TCG with 8 emulated CPUs, contention on the single buffer mutex is very slow: while this lab was being developed, a 10-million-item run on 8 CPUs (before adaptive spinning was added to the mutex) did not finish within a 5-minute limit, and it was not repeated afterwards. The test therefore takes its sizes from the kernel command line: by default one run of 200,000 items followed by 20 runs of 10,000 items, all of which passed in this build R2. items=10000000 runs=100 on the command line gives the curriculum's sizes; running them, and running under KVM, is left to a machine that has KVM. The NOTES file lists this as a decision for the course owner.

How the hardware actually does it

Each CPU core has a local APIC, reached at a physical address given by the IA32_APIC_BASE MSR (QEMU reports 0xFEE00000 in the MADT R1). Writing the high half of the interrupt command register sets the destination APIC id; writing the low half sends the IPI. The low half's fields select the delivery mode (fixed vector, INIT, start-up) and, for a start-up IPI, the vector that names the start page. A "delivery status" bit stays set while the previous IPI is still being sent D1. invlpg removes the TLB entry for one page on the executing CPU only; there is no x86 instruction (before recent extensions) that invalidates another CPU's TLB, hence IPIs. The GS base is a model-specific register written with wrmsr; F3-29 uses its partner, the "kernel GS base" MSR, with swapgs.

Not verified — check before relying on this

Written from memory and not checked against the documents in this build: the ICR low values 0x4500 (INIT, level assert) and 0x4600 | page (start-up), the ICR offsets 0x300/0x310 and the delivery-status bit 12; the IA32_APIC_BASE MSR number 0x1B; IA32_GS_BASE 0xC0000101 and IA32_KERNEL_GS_BASE 0xC0000102; EFER 0xC0000080 with LME bit 8; CR4.PAE bit 5; the trampoline's GDT descriptor values; the 10 ms and 200 µs delays of the MP initialization example; that a SIPI vector names a 4 KiB page below 1 MiB; the RSDP layout (revision at offset 15, RSDT address at 16, XSDT at 24), the EBDA pointer at 0x40E, the MADT header (local APIC address at 36, entries from 44) and the layouts of entry types 0, 1 and 2. They work on QEMU 8.2.2's TCG model with its SeaBIOS-provided ACPI tables, as the runs below show; that proves nothing about real machines. Check against the Intel SDM Vol. 3 ("Multiple-Processor Management", "Advanced Programmable Interrupt Controller (APIC)"), Vol. 4 (MSRs) and the ACPI Specification ("ACPI Software Programming Model", MADT) (D1, D2).

Note

Untested on hardware, and not under KVM: QEMU TCG emulates all CPUs in software, and its timing is nothing like real hardware's. On real machines, x2APIC mode, more than 255 CPUs, and firmware that lists disabled or "online capable" processors all need handling this kernel does not have.

Worked example

Reading the MADT of the 8-CPU machine. The madt run printed the RSDP (revision 0, so there is no XSDT and the RSDT is used), the RSDT with two tables (FACP and APIC) and the MADT entries R1. The MADT is 176 bytes. Its entries start at offset 44, so there are 132 bytes of entries: 8 processor entries of 8 bytes (64), one I/O APIC entry of 12 bytes, five interrupt source overrides of 10 bytes (50) and one entry of type 4 of 6 bytes: 64 + 12 + 50 + 6 = 132. The arithmetic checks, which is a good sign that the entry walk (e += t[e + 1]) is right. The override "IRQ 0 → GSI 2" says that the old timer IRQ 0 arrives at I/O APIC input 2, which F3-24 had to know.

The trampoline's addresses. tramp_gdt_ptr is assembled with the value 0x8000 + (tramp_gdt − tramp_start). If tramp_gdt is at offset 0x70 from tramp_start (the exact offset depends on instruction sizes; read it from nm kernel.elf), the AP loads its GDT from 0x8070, where the copy really is, and not from the kernel's link address above 1 MiB, which in real mode it could not even reach with a 16-bit offset.

The shootdown counts. In the recorded smp8 run, cpu0 read the probe page 76,897 times before the unmap and 0 times after the shootdown completed; all eight CPUs then faulted R3 (your counts will differ). In the recorded noshootdown run, cpu1 read the page 14,013 times before the unmap and 2,380,217 times after "the shootdown completed" — which in this run means "after tlb_shootdown returned having flushed only cpu0" — and never faulted. Every one of those reads used a translation to a frame that the kernel had already returned to the free list.

Where the analogy breaks


    

  • Teachers do not share a brain. Teachers who disagree can talk. CPUs share memory but each sees writes through its own caches and store buffers; agreement comes only from the hardware's coherence protocol and the memory orders of F3-27.
    • 

  • A sticky note is visible; a TLB entry is not. No instruction lists what another CPU's TLB holds. The kernel must assume any CPU that ever ran with an address space may hold any of its translations.
    • 

  • Phoning a teacher does not stop them. An IPI interrupts the target at its next instruction boundary, unless it has interrupts disabled; then the call waits, and so does the caller.
    • 

  • The side door is a real address. "Door 8" is literally physical page 8 (0x8000): the start-up message can only name a page below 1 MiB, which is why the trampoline is copied there.
    • 




Common mistakes and debugging


    

  • An AP never comes online. Usually the trampoline uses a link-time address instead of a 0x8000-relative one, or a variable was not patched. Boot with -d int,cpu_reset and look for the AP's triple fault; check the trampoline with objdump -m i8086 for the real-mode part.
    • 

  • Sharing one TSS or one boot stack between CPUs. Two CPUs on one stack corrupt each other within microseconds; loading a TSS that another CPU loaded faults because it is marked busy.
    • 

  • Starting the AP's timer before the scheduler knows the CPU. The first tick calls schedule() with no current thread.
    • 

  • Forgetting the shootdown when freeing a page. Nothing fails at once: another CPU keeps writing into a frame that now belongs to someone else. The noshootdown run shows how quiet this is.
    • 

  • Shooting down with interrupts disabled. Two simultaneous initiators deadlock. Keep the assertion.
    • 

  • "It passed on one CPU." Code that takes two locks in data-dependent order passes every single-CPU test. Read the LOCKDEP lines even in passing runs.
    • 

  • Debugging method for SMP hangs. With QEMU's monitor, info cpus shows each vCPU's RIP; addr2line them. Better: rely on the lockup detector, whose report has the same information plus the locks.
    • 




Transition box

Where you came from: F3-26 and F3-27 built threads, a scheduler and locks, tested on one CPU. What carries over: the global run queue and its lock handover, the IPI-ready sched_make_ready, ticket spinlocks, the order checker and the lockup detector; F3-24's MADT and local APIC; F3-21's page tables. What changes: all CPUs run; each has its own GDT, TSS, GS base, idle thread and timer; page unmapping now requires a shootdown; and bugs that need two CPUs at once become real. What comes next: F3-29 adds the boundary between kernel and user code: ring 3 segments, SYSCALL and SYSRET, swapgs with the per-CPU area built here, SMEP and SMAP, and a kernel that no longer trusts the pointers it is given.

Summary


    

  • The MADT lists the processors; the BSP starts each AP with INIT, SIPI, SIPI and a trampoline at 0x8000 that climbs to long mode and calls ap_entry.
    • 

  • Every CPU gets its own GDT, TSS, double-fault stack, GS base, idle thread and timer; the IDT and page tables are shared. %gs:0 is this CPU's Cpu.
    • 

  • IPIs reschedule idle CPUs and shoot down TLB entries. Unmapping a page is complete only after every CPU has invalidated it; without that, other CPUs keep using a freed frame (recorded).
    • 

  • Per-CPU data may only be changed while the thread cannot move to another CPU.
    • 

  • The CPU count matched the MADT for 1–16 CPUs; producer/consumer and shootdown passed on 8 emulated CPUs at reduced sizes, TCG only; nothing was tested on hardware or under KVM.
    • 

  • Code with two locks in data-dependent order passes on one CPU and deadlocks on eight; the lock-order checker had already warned in the passing run.

Answers to Check yourself


    

  1. The AP starts in 16-bit real mode, where an address is segment × 16 + offset and only the first MiB (plus a little) is reachable; the start-up IPI's 8-bit vector names a 4 KiB page number (vector × 0x1000), so the start address is necessarily a page boundary below 1 MiB.
    2. 

  2. 0x8000 >> 12 = 0x08, so the low ICR word is 0x4608: delivery mode start-up with vector 0x08, naming page 8, address 0x8000 (values from memory; see the unverified box).
    3. 

  3. Good answers say: every CPU has its own TLB and may hold the old translation; it will keep using it, reading or writing the old frame, until the entry is evicted or invalidated on that CPU. Only that CPU can invalidate its own entries, so it must be asked (IPI) and the initiator must wait for the answer before reusing the frame.
    4. 

  4. The initiator waits for other CPUs to handle an interrupt. If another CPU is itself waiting (for the shootdown lock, or for answers to its own shootdown) with interrupts disabled, it never answers, and both wait forever. With interrupts on, waiting CPUs still answer.
    5. 

  5. The GS base cannot be read as a normal memory value without an MSR read; storing the object's own address at offset 0 lets mov %gs:0, %rax produce a normal pointer to it in one instruction, which C++ can then use like any pointer.
    6. 

  6. Four processor entries instead of eight removes 4 × 8 = 32 bytes: 176 − 32 = 144 bytes. If the printout differs, the other entries differ (count them with the walk); the prediction is only as good as its assumption.
    7. 

  7. (a) transfer takes the first lock with lock_irqsave(), so the timer cannot interrupt (and preempt) a teller between the two locks; (b) with one CPU nothing else runs in parallel. So each transfer completes before another starts, and no teller ever holds one lock while another holds the other.
    8. 

  8. Only a CPU that still has the process's CR3 loaded, or ran it and has not loaded another CR3 since (a CR3 load flushes non-global entries, and this kernel uses no PCID; register-level detail from memory, D1). Here a process has one thread: every CPU it ran on before loaded a different CR3 when it switched away (schedule_locked writes CR3 whenever it differs), and process_exit loads the kernel's CR3 on the exiting CPU before freeing anything. So no CPU can hold a stale user entry, and no shootdown is needed. With several threads per process running on several CPUs at once, it would not be safe.
    9. 

  9. With one global queue, any awake CPU takes the next ready thread, so a correct scheduler can legitimately leave some CPUs idle for short sleeping threads; a hard check would fail randomly (it did, during development) without indicating a bug.
    10. 



Forensic lab answer key


Observation. Evidence 1 passed (balances total 2,000,000) but starts with a LOCKDEP report: "acquiring 'account:alice' while holding 'account:bob' … earlier: 'account:alice' was held while acquiring 'account:bob'". Evidence 2 has the same kind of report (on cpu2 in the recorded run), then a lockup: cpu2 holds 'account:alice' and waits for 'account:bob', cpu3 holds 'account:bob' and waits for 'account:alice', and cpu0, cpu1 and cpu4–cpu7 wait for one of the two holding nothing. (Which two CPUs form the cycle changes from run to run.) addr2line puts both addresses in transfer(): one at test_smp.cc:166 and one at line 167.


Wait-for graph. Figure 3: cpu2 → bob → cpu3 → alice → cpu2. A cycle of two CPUs; the other six are victims queued behind the two locks.


Why the addresses coincide. Both orders come from the same line of code, to_lock.lock() inside transfer; only the arguments differ. The checker compares lock classes (names), which is why it can see an inversion that no code review of a single line would show.


Lines. The recorded addresses are return addresses of the lock() calls. 0x106306 follows from_lock.lock_irqsave() on line 165, so it maps to line 166; 0x10630e follows to_lock.lock() on line 166, so it maps to 167.


Why one CPU never deadlocked. See answer 7: interrupts are off between the two locks, and nothing else runs in parallel.


Root cause. transfer(from, to) locks the source first. Tellers with even i transfer alice→bob, odd ones bob→alice, so the two orders occur in parallel on 8 CPUs.


Fix. Impose one global order: lock the two accounts in a fixed order (by account number, name or address) regardless of the direction of the transfer, as lockorder.cpp's ordered() does in F3-27. Concurrency between transfers on other accounts is unchanged.


Prevention. Treat every LOCKDEP report as a test failure (make lockdep_reports() > 0 fail the test even when the run completes), and run the test suite with several CPUs in CI. The passing single-CPU run already contained the warning.
