Story hook

On a building site, the plumber finishes the pipes on Monday. On Tuesday the plasterers arrive and close the walls. If a pipe leaks, nobody will see it until the paint bubbles in March, and then the walls must be opened again.

So the site has an inspector. Every evening, before anybody may build on top of today's work, she checks it: the pipes are pressure-tested, the wiring is tested with a meter, the stairs are measured. She writes "pass" or "fail" in the site book. A trade may start only when the work under it has passed.

One autumn the inspector is replaced by a cheaper service. Its reports are always "pass". In spring, the third floor's heating does not work. The site book says the pipes were tested every day. They were not: the new service checked only that the plumber had written "done" on the door.

Continuous integration is the evening inspection of software. This chapter builds one for a kernel, a GPU program and a robot controller, and then shows how a pipeline can say "pass" every day while the thing it guards is broken.

What you will be able to do

  • Design a CI pipeline in stages (host tests, freestanding build, emulator tests, harness self-tests, GPU build, GPU run, robot simulation) and justify their order.
  • Implement the curriculum's acceptance-test rules for kernel code: serial output as the oracle, pass/fail through QEMU's isa-debug-exit device, a wall-clock limit on every run, a fixed and recorded machine.
  • Prove that a harness can fail: run planted panics, hangs and empty runs and require the harness to report each as a failure.
  • Handle stages that cannot run on a given runner (no GPU, no robot) as "skipped", never as "passed", and say what evidence is missing.
  • Diagnose a pipeline that reports success for a broken commit, from its script and its log alone.
Jargon box
CI pipeline
Simple words: the list of checks a computer runs, in order, on every change before the change is accepted. Analogy: the inspector's evening round: pipes first, then wiring, then stairs. Precise: an ordered set of stages (build, tests, analyses) run automatically for each commit or merge request; each stage has a pass, fail or skipped result, a failing stage stops the pipeline, and the overall result gates the merge. D1 R1
isa-debug-exit
Simple words: a pretend device in QEMU that a kernel can write a number to, which makes QEMU stop with an exit status. Analogy: the plumber flips a green or red card that the inspector can read from the road. Precise: a QEMU device on the ISA I/O port bus (here at port 0xf4); a write of value v ends the emulator with exit status (v << 1) | 1, as observed in this build (0x10 gave 33, 0x11 gave 35); the status is therefore always odd, and the harness must map one chosen value to "pass". D2 D3 R2
Wall-clock limit (test timeout)
Simple words: the most time a test may take; if it takes longer, it has failed. Analogy: the inspector does not wait all night for a pressure test to finish. Precise: a limit on real elapsed time enforced from outside the test (here by timeout, exit status 124 when it fires); the curriculum's rule: "a hang is a failure, not 'probably fine'". D2 R1
Harness self-test
Simple words: a test that is supposed to fail, run to prove that the harness notices failures. Analogy: the inspector checks her gauge on a pipe with a known leak. Precise: a deliberately failing case (panic, hang, no tests run) executed through the real harness in CI, with the stage passing only if every such case is reported as a failure; it protects the oracle itself from regressions. Related to mutation testing. R1
Skipped (test result)
Simple words: "this check did not run here", reported as its own result, never as a pass. Analogy: "lift not inspected: lift engineer absent", written in the site book in red. Precise: a third verdict next to pass and fail, for tests whose preconditions (a GPU, a robot rig) are absent; the pipeline's summary names every skipped stage so that missing evidence stays visible, and a policy decides where the skipped test must still run before release. D2 R1
pipefail (shell option)
Simple words: a shell setting that makes a chain of commands joined by | fail if any command in the chain fails. Analogy: the report says "fail" if any trade failed, not only the last one to sign. Precise: in bash, set -o pipefail makes the exit status of a pipeline the status of the last command that failed (or 0 if all succeeded); without it the status is that of the last command only, so qemu ... | tee log reports tee's success. D4 R6

Layer 1 — the kid explanation

Analogy

The evening inspection. Mapping: each day's work = a commit; the inspector's round = the pipeline; pressure-testing the pipes = running the tests; "nobody builds on work that failed" = a failing pipeline blocks the merge; the inspector testing her own gauge on a known leak = the harness self-tests; "lift not inspected" in red = a skipped stage; the cheap service that read the "done" sign on the door = a pipeline that checks the wrong thing.

When many people change the same program, a mistake by one person can break everyone's work. So every change is checked by a computer before it joins the rest, every time, in the same way. That is continuous integration.

A kernel is hard to check because it runs on a whole computer, not inside one. So we start a pretend computer, an emulator, and let the kernel run tests inside it. The kernel writes its results on a pretend cable, and at the end it presses a pretend button that says "all good" or "something failed".

The most important rule: the checker must be able to say "fail". If it cannot notice a crash, or if it waits forever when the kernel freezes, it is worse than no checker, because everybody trusts it.

Layer 2 — the student explanation

Analogy

The inspector checks the cheap things first (are the pipes connected?) and the expensive things later (a pressure test). If the pipes are not connected, there is no point in the pressure test.

The rules from the curriculum

Curriculum section 0 states how acceptance tests work for kernel code. Quoted, because the lab implements each sentence: D2

  • "Serial output is the oracle. The kernel prints structured lines on the emulated 16550 UART; QEMU writes them to a file or to the terminal; the harness checks for expected lines and for the absence of "PANIC"."
  • "Pass/fail exit. QEMU's isa-debug-exit device lets the kernel end the run with a chosen exit status, so a test run is a normal process that passes or fails in CI."
  • "Timeouts. Every QEMU test has a wall-clock limit; a hang is a failure, not "probably fine"."
  • "Determinism. Fixed QEMU machine type, memory size, CPU count and firmware build per test; the harness records them in the log."
  • "Real hardware runs are recorded as extra evidence, never as a replacement for the QEMU test."

Section 5.5 adds the rule for drivers: "Regression: the emulator part runs in the harness on every commit; real-hardware runs are recorded in the log as separate evidence". D2

The test kernel

Listing 2 (kmain.cc) is a small Multiboot kernel built only for tests. QEMU loads it with -kernel and passes the -append string as its command line; the kernel reads the command line from the Multiboot information and runs the tests it names. Each test prints one structured line, KTEST <name> ok or KTEST <name> FAILED, on COM1. At the end it prints KTEST summary N passed M failed and writes 0x10 (all passed) or 0x11 (something failed) to the isa-debug-exit port. A failed assertion prints a PANIC line and writes 0x11.

The real test is the frame allocator of Listing 1 (bitmap.hpp), the kind of allocator milestone B3 asks for. It is pure logic, so the same header is tested twice: on the host with AddressSanitizer and UBSan, including the B3 test "random allocate/free sequences against a reference model" (Listing 5), and inside the kernel. Host first: bugs in logic are found in a second with a full debugger and sanitizers; the kernel run then proves it works freestanding, compiled with kernel flags, on the emulated machine.

The harness and its verdict

Listing 3 (qemu_test.sh) boots the kernel once, under timeout, with a fixed machine (-machine q35 -m 64M -smp 1), the serial port written to a file, and the debug-exit device at port 0xf4. Its verdict rule is the bottom row of Figure 1. A pass needs two independent signals: the exit status 33 and the summary line with 0 failures. Either alone can lie: a kernel that crashes in the summary code could still have written 0x10 earlier; a log can contain "0 failed" from a previous run if it is not deleted first (line 11 deletes it).

The harness must fail when it should

Stage 4 of Listing 4 (ci.sh) runs three kernels that must fail: one that panics on a wrong assertion, one that halts with interrupts off and never ends, and one with an empty command line, so that no test runs. The stage passes only if the harness reports all three as failures. In this build it did: the panic gave "FAIL (PANIC in the serial log; QEMU exit status 35)", the hang gave "FAIL (no result within 10 s: a hang is a failure)", the empty run gave "FAIL (QEMU exit status 35; last serial line: KTEST summary 0 passed 1 failed)". R1 The third case matters as much as the others: a typing mistake in the command line (test=bitmpa) would otherwise run nothing and pass.

GPU and robot stages


GPU code needs a GPU to run, and CI runners often have none. The pipeline still checks what it can on every commit: that the CUDA code compiles with warnings as errors, and that the produced machine code contains the kernel function (stage 5, cuobjdump lists _Z6vecAddPKfS0_Pfi). Stage 6 asks the CUDA runtime for devices; when there are none, the program exits with 77 and the pipeline reports the stage as SKIPPED, by name, in the final line. Layer 3 — the engineer's depth


Analogy
A site book full of "pass" is worth exactly as much as the inspector's method. Engineers audit the method, not the book.


Ordering stages: cost, information, and dependency


Order stages by three questions. Dependency: nothing can be emulated before it builds. Cost: host tests take seconds; a QEMU boot takes longer; a GPU or HIL runner is a scarce machine; cheap stages first save expensive ones. Information: a host test failure points at one function with a sanitizer report; a QEMU failure says "something in the kernel"; run the most precise check first, so the failure message is the most useful one. The harness stage comes after the QEMU stage here so that a harness change is tested on the same kernel image the real tests used. A real pipeline can run independent stages in parallel (the GPU build does not depend on the kernel), which most CI services support; their configuration languages are not covered here (see the unverified box).


The oracle: exit status and log, both


Why not only the exit status? The kernel writes it, so a kernel bug can write the wrong one. Why not only the log? Logs are text; a pattern can match old or partial text, and a missing line is easy to miss. Using both gives two independent witnesses that must agree. The structure of the log lines matters: KTEST <name> ok is easy to match exactly; free text such as "bitmap seems fine" is not. Line 20 of Listing 3 anchors the summary pattern at the start of a line (^KTEST summary), so a test that prints the word "summary" in its own output cannot fake it.


Choosing the time limit


A limit that is too short makes a slow but correct run fail on a loaded runner (a flaky test, F12-10); a limit that is too long wastes a runner for every hang. Measure the normal duration on the runner, under load, and set the limit at a generous multiple of it; record the limit in the verdict line (Listing 3 prints it). The hang self-test uses a shorter limit (10 s) than the real tests (20 s) because it can only end by the limit. The limit is enforced from outside the emulator: timeout sent signal 15 (SIGTERM) and QEMU printed "terminating on signal 15 from pid ... (timeout)" before the harness recorded the hang. R1 A kernel cannot be trusted to enforce its own time limit, for the same reason it cannot be trusted to write its own exit status alone.


Determinism and the record


The curriculum asks for a fixed machine type, memory size, CPU count and firmware build per test, recorded in the log. D2 The verdict line records the first three; the run record of this build adds the QEMU version (8.2.2) and the firmware package (SeaBIOS 1.16.3-2), because a different firmware or QEMU version can change what a kernel sees at boot. R1 Emulation with TCG (no hardware acceleration) is the most predictable choice for early milestones, as the curriculum notes. D2 The section 0 rule on debugger reproducibility ("Every failing test can be re-run with QEMU's GDB stub enabled and the CPU halted at start") is a lab step below: a failing CI run is only useful if a developer can repeat it on their own machine, with the same command line, and step through it.


Skips are evidence that is missing


A skipped stage is not a pass. The pipeline prints "PASS with skipped stages: gpu-run" so the gap is visible in every summary. The policy that turns skips into evidence belongs in the test plan (curriculum 5.5): which machine runs the GPU tests, how often (every commit on a GPU runner, nightly, or before a release), and who looks at the result. The curriculum's definition of done rules out the dangerous version: "The agent never marks a milestone done with a test skipped, weakened or "to be added later"." D2 A skip on a commit is acceptable; a skip at the milestone gate is not.


What a GPU-less runner can still check


    

  • The code compiles for every target architecture in the support matrix, with warnings as errors (stage 5).
    • 

  • The produced binary contains the kernels you expect (stage 5, cuobjdump); a refactoring that silently removed a kernel or changed its signature shows up as a changed name.
    • 

  • The host-side logic (sizes, launch configuration, the CPU reference used by the GPU tests) is tested with ordinary host tests and sanitizers.
    • 

  • Not checkable without a GPU: correctness of the device code, races on the device (F0-80 uses the GPU sanitizers for that), performance. These are the gpu-run stage's job on a runner with a GPU.

Robots in CI


For robots the ladder of F12-07 maps onto CI frequencies: SIL scenarios on every commit (stage 7 here), PIL with an emulator on every commit or nightly, HIL on a rig as a scheduled job or a release gate, field tests as planned events. A HIL rig in CI is a physical machine that moves; it needs the same safety rules as a lab bench, and an unattended job must not be able to command motion beyond what the rig is built to contain.

The isa-debug-exit formula is inferred from two observed values (0x10 to 33, 0x11 to 35); D3 must confirm it. The 16550 transmitter-empty bit used by putc is from memory of the datasheet (D6).



How the hardware actually does it


On a real PC, a write to an I/O port with the out instruction goes to whatever device decodes that port. Under QEMU with TCG, the guest's instructions are translated into host code; an out to port 0xf4 becomes a call into QEMU's device model, and the isa-debug-exit device's handler ends the QEMU process with the computed status. D3 No such device exists on a real PC: the same kernel on hardware would write to an unused port and continue, so a hardware run needs another way to end (here the cli; hlt loop after the write) and another way to report (a person or a script reading the serial line). The serial port is the emulated 16550: putc waits until bit 5 of the line status register (port 0x3f8 + 5) says the transmitter can take a byte, then writes the byte to port 0x3f8; QEMU's model is ready at once and writes the byte to the log file. D6 On real hardware the same loop waits for the bits to leave the wire at the configured baud rate, which this kernel never sets; that is one reason the hardware run is untested.


Watch out
Untested on hardware. Every kernel run in this chapter ran in QEMU 8.2.2 with TCG and SeaBIOS; no physical PC booted this kernel. The CUDA program was compiled and its machine code inspected, but it never ran on a GPU: the runtime reported "no CUDA-capable device is detected". R1 R9 The robot stage is simulation only.

Where the analogy breaks


    

  • An inspector looks at the real house; CI looks at a model of the machine. QEMU is not a PC. A kernel can pass every emulated test and fail on hardware (timing, firmware quirks, devices QEMU models differently). That is why the curriculum records real-hardware runs as separate evidence, and why this chapter's hardware column says "untested".
    • 

  • An inspector comes once a day; CI runs on every change. The value of CI comes from the small size of each change: when a test fails, the cause is in the last commit, not in a week of work. Running the pipeline nightly over many commits loses that and turns every failure into a bisect.
    • 

  • An inspector can use judgement; a pipeline cannot. Anything a script does not check, it does not see: the forensic lab's pipeline "checked" a log for one good line. A human inspector who saw "PANIC" on the page would have stopped.
    • 




Common mistakes and debugging


    

  • Symptom: CI passes although the kernel panicked. Cause: the stage's status comes from the last command of a pipeline (| tee), or the check looks only for a good line. How to find it: run the harness self-tests; read the stage's script for | without pipefail. Fix: set -o pipefail, check for PANIC, require the exit status.
    • 

  • Symptom: a CI job runs for hours and is killed by the service. Cause: no time limit around QEMU. Fix: timeout on every emulator run, with a limit recorded in the log.
    • 

  • Symptom: passes locally, fails in CI (or the reverse). Cause: a different QEMU, firmware or machine type; a different compiler; files left in the working tree. How to find it: compare the recorded versions and machine lines. Fix: pin and record versions; build from a clean tree (curriculum: "pass from a clean build").
    • 

  • Symptom: a test "passes" that never ran. Cause: a misspelt test name, an empty selection, a skipped stage counted as success. Fix: count "no test selected" as a failure (kmain.cc 158–161); report skips by name.
    • 

  • Symptom: QEMU reboots forever after a crash. Cause: a triple fault resets the emulated machine. Fix: -no-reboot, and a time limit.
    • 

  • Symptom: a failure in CI cannot be debugged. Cause: the command line and versions are not recorded. Fix: print the full QEMU command, and keep the serial log as a CI artifact; re-run locally with the GDB stub.
    •

Lab


Course lab: a CI pipeline running QEMU kernel tests with timeouts (curriculum section 0).


Goal. Run the pipeline, extend the test kernel with a new test, prove the harness catches two new failure kinds, and repeat a failing run under the debugger.


Hardware and software needed. A Linux machine with g++ (with 32-bit multilib support for -m32), ld.lld, qemu-system-x86_64, and optionally nvcc and cuobjdump (stage 5; without them the stage fails, so remove it and record that you did). This build used g++ 13.3.0, LLD 18.1.3, QEMU 8.2.2 with SeaBIOS 1.16.3-2, CUDA 12.0. Folder university/labs/F12-09; from the repository root run university/labs/run_lab.sh university/labs/F12-09.


Safety
This lab runs only in an emulator; nothing touches real hardware. If you later boot the test kernel on a spare PC, follow the curriculum's real-hardware rules: a machine whose data you do not need, disks you care about disconnected, and the QEMU test kept as the primary evidence. If you add a HIL stage for a robot, the rig must contain any motion it can command, with an emergency stop, and the job must not run unattended on a robot that can leave the bench (BR-08).

Summary


    

  • CI checks every change automatically, in ordered stages, cheapest and most precise first; a failing stage stops the pipeline.
    • 

  • Kernel tests follow curriculum section 0: serial lines as the oracle, a pass/fail exit through isa-debug-exit (status (v << 1) | 1: 33 for pass, 35 for fail here), a wall-clock limit on every run, a fixed and recorded machine.
    • 

  • Pass requires two signals that agree: the exit status and the summary line, with no PANIC.
    • 

  • Prove the harness can fail: a panic, a hang and an empty run must each be reported as failures (R1).
    • 

  • Test pure logic on the host first (with sanitizers), then the same code in the kernel.
    • 

  • Without a GPU, check compilation and the machine code; report the run as SKIPPED by name; a skip is missing evidence.
    • 

  • A pipe without pipefail can turn a failing kernel into a green pipeline (R6).

Forensic lab answer key


How the evidence was produced. run.sh built the kernel with ci.sh, then ran ci_broken.sh, which boots it with test=all,panic; its output was captured unchanged except for path cleaning. The same commit was then run through qemu_test.sh (R7). R6 R7


Observation. The kernel ran the bitmap and selfcheck tests (both ok), then panicked: "PANIC: assertion failed: b.free_count() == 127 at kmain.cc:150". The stage printed "CI stage qemu: PASS". From panic (kmain.cc line 61), the kernel wrote 0x11, so QEMU exited with status 35; R7 shows exactly that status for the same command line.


Hypotheses. (1) QEMU's status was lost: line 11 tests $? after a pipeline qemu ... | tee. Supported. (2) The log check looks for a good line instead of a complete result: line 14 greps "KTEST bitmap ok". Supported. (3) The check runs on an old log: excluded, tee rewrites serial_ci.log on each run. (4) The kernel wrote the wrong exit code: excluded by R7 (status 35).


Root cause. Without pipefail the status of the pipeline on lines 8–10 is tee's, and tee succeeded, so $? was 0 at line 11. Line 14 then found "KTEST bitmap ok", which the kernel printed before the panic, and declared PASS. Neither check could see the panic, and the script never looks for "PANIC" or for the summary line. Two further defects did not cause this failure but would cause others: no time limit (a hanging kernel would block the job until the CI service killed it, reported as an infrastructure error, not a test failure), and the machine is not recorded.


Fix and verification. Replace the stage with qemu_test.sh: status checked directly, PANIC and the anchored summary checked, a time limit, the machine recorded. On the same commit it reports "FAIL (PANIC in the serial log; QEMU exit status 35)" and exits 1 (R7). Keep the fix tested: the harness self-test stage (panic, hang, empty run) fails the pipeline if any later change makes the harness blind again (R1). If a pipe is wanted for live output, add set -o pipefail as ci.sh does (line 11).


Scope. Since the stage was introduced, any commit whose kernel panicked after printing "KTEST bitmap ok", hung after it, or failed another test, passed. To find affected commits: re-run the fixed harness on every commit of the three weeks (the kernel builds are reproducible from the commits), or bisect for the first commit with the panic; then check what was merged on top of it.
