Story hook

Lina inspects the doors of a new school building. The checklist from the builder says: "door 12 closes; door 31 closes; door 7 closes". Each line is true. But there are 140 doors, and the checklist names twelve.

Lina writes a different kind of rule: "every door, when pushed shut from any angle, closes and latches". Then she walks the corridors and tries doors at random, from strange angles, some of them twice. On door 88 the rule breaks: pushed from wide open, it bounces back. Lina tries again, less and less wide, until she finds the smallest push that still fails. That small push goes into the report, because the carpenter can fix it in a minute.

On the last day, Lina's young cousin visits. He leans on handrails, slams cupboards, hangs on door handles and sits on a window sill. Nobody would write any of that on a checklist. In ten minutes he finds a rail that wobbles.

Lina's rule-plus-random-doors is property-based testing. Her cousin is a fuzzer. This chapter teaches you to do both on code, and to keep the smallest failing case forever.

What you will be able to do

  • Write properties (round trip, agreement with a model, "never crashes") and test them on generated inputs with a seeded generator.
  • Explain shrinking, and use it to turn a random 442-byte failure into a 256-byte one you can understand.
  • Build and run a coverage-guided fuzzer with sanitizers, and explain why feedback finds bugs that blind random testing does not.
  • Diagnose a fuzzer crash report: the faulting line, the input field responsible, the fix, and the regression test.
  • Decide where generated inputs belong in a test strategy: which code to fuzz, with which oracle, for how long, in CI or overnight.
Jargon box
Property-based testing
Simple words: instead of checking a few chosen examples, you write a rule that must hold for every input, and the computer tries many random inputs. Analogy: "every door closes", tried on many doors. Precise: a testing method in which a property (a predicate over inputs and outputs) is checked on many inputs produced by a generator; a failing input is reported together with the seed that reproduces it, and is usually shrunk. Popularised by the QuickCheck library for Haskell. D1 R1
Generator (test input)
Simple words: the part that invents test inputs. Analogy: Lina's way of choosing which door to try next and how wide to open it. Precise: a function from a pseudo-random source and a size parameter to an input value; its distribution decides which inputs are likely, and therefore which bugs can be found. Not the CMake generator of F2-26. D1
Shrinking
Simple words: making a failing input smaller and smaller while it still fails. Analogy: pushing the door less and less wide until the smallest failing push is found. Precise: after a property fails, repeatedly replacing the failing input by a "smaller" candidate (fewer elements, smaller values) that still fails, until no candidate fails; the result is a local minimum, not necessarily the smallest failing input. D1 R1
Model-based testing
Simple words: comparing your clever code with a simple version that is obviously right. Analogy: checking the automatic door against a plain hinged door that does the same job. Precise: a property of the form "for every sequence of operations, the system under test returns the same results as a reference model"; here a ring buffer against std::deque. Related to the reference model of F1-14. D1 R2
Round-trip property
Simple words: if you pack something and unpack it, you get back what you started with. Analogy: taking a door off its hinges and putting it back: it must close as before. Precise: for an encoder e and decoder d, d(e(x)) = x for every valid x; one of the most productive properties for parsers, serialisers and compressors. D1

Also used: fuzzing (F2-44), coverage-guided fuzzing and corpus (F11-09; here: a fuzzer that keeps inputs which reached new code, and its collection of such inputs), AddressSanitizer and UBSan (F2-29), seed and pseudo-random number generator (F0-38), test oracle and regression test.

The idea in pictures

Figure 1 shows the two loops of this chapter side by side. Both generate inputs. They differ in the oracle and in what they learn from each run: property-based testing checks a rule and shrinks a failure; a coverage-guided fuzzer checks "no sanitizer report" and keeps inputs that reached new code.

Layer 1 — the kid explanation

Analogy

A checklist names a few doors; a rule covers all of them. Mapping: the rule "every door closes" = a property; trying random doors = generating inputs; finding the smallest failing push = shrinking; the clumsy visitor = a fuzzer; remembering which rail creaked = coverage feedback; the inspector's report with the exact door and push = a saved failing input that becomes a regression test.

A normal test checks examples you chose. You can only choose examples you thought of. Bugs live in the examples you did not think of.

So you write a rule instead: "unpacking what I packed gives back the original". The computer then invents hundreds of inputs and checks the rule on each. When the rule breaks, the computer makes the input smaller and smaller, until it is as simple as it can be while still breaking the rule.

A fuzzer is even simpler and even more stubborn. The idea is old: an early study fed random characters to standard UNIX programs and watched many of them crash or hang. D2 A fuzzer feeds a program millions of strange inputs, and watches only for crashes and memory errors. A clever fuzzer notices when an input made the program do something new, and keeps playing with that input. That is how it gets past checks that a blind fuzzer would never pass.

Layer 2 — the student explanation

Analogy

Lina's rule is only as good as her choice of doors and angles. A generator that never opens a door wide never finds door 88.

A property-based harness in 70 lines

Listing 1 (pbt.hpp) is the whole harness. for_all creates a std::mt19937_64 from the seed, asks the generator for inputs of growing size (small first, line 41), and checks the property on each. On the first failure it shrinks: it asks the generator's shrink function for smaller candidates and moves to the first one that still fails, again and again, until none fails (lines 48–58). It prints the seed, so the exact run can be repeated. A generic helper, remove_chunks, proposes the same vector with a half, a quarter, ... down to single elements removed.

A round trip finds a boundary nobody wrote down

Listing 2 is a run-length encoder: each run of equal bytes becomes a pair (count, value), both one byte. encode_v1 has a bug that no example test in its file would show: a count is a byte, so the 256th equal byte wraps the count to 0. Listing 3 checks the round-trip property decode(encode(x)) == x on byte strings built from a few long runs. The run: encode_v1 failed on run 83 of 200 with a 442-byte input (59 sevens, 285 zeros, 98 bytes of 255), and six shrink steps later the report said [0*256] (256 bytes): 256 equal bytes. The fixed encode, which starts a new pair at 255, passed all 200 runs. R1 The shrunk input is the specification of the bug: "a run of 256".

No sanitizer complained about the wrap. Incrementing a std::uint8_t from 255 converts the value 256 back to an unsigned 8-bit type, which C++ defines as arithmetic modulo 256, so it is not undefined behaviour. D7 Sanitizers find undefined behaviour; properties find wrong answers. You need both.

Model-based: a ring buffer against a deque

Listing 4 tests a ring buffer of capacity 4 (the kind a driver or a sensor task keeps) against std::deque limited to 4 elements: for any sequence of push and pop operations, both must give the same answers. The generator makes sequences of up to 40 operations. The run: failure on run 91 with 13 operations, shrunk to 10: push(0) push(0) pop pop push(0) pop push(0) push(12) pop pop. R2 Read it as a story: the read position walks to slot 3, wraps, and the planted bug sends it to slot 1 instead of 0, so the last pop returns an old 0 instead of 12. The shrinker kept 12 because with all values 0 the stale value looks correct; that detail tells you the bug returns a wrong slot, not a wrong count.

Fuzzing a parser, blind and guided

Listing 5 is a parser for a binary sensor frame: magic bytes S P, a type, a length, the payload, a checksum. It has a planted bug: a type-2 (text) payload is copied into a 32-byte array with the length from the frame. Listing 6 is the university's mutation fuzzer. It starts from one dull input (hello) and mutates it (flip a bit, set a byte, insert, erase, append a chunk). In blind mode it always mutates the starting input. In guided mode it keeps every input that reached a code block not seen before, and mutates those.

The runs, same seed and the same budget of 300,000 executions: blind mode found nothing. R3 Guided mode added an input starting with S at execution 2114, S P at 3631, S P 01 at 18528, S P 02 at 20584, and at execution 38745 AddressSanitizer reported a stack-buffer-overflow: a write of 48 bytes in memcpy called from parse_frame at pkt.cc:32. The fuzzer's death callback printed the input: 53 50 02 30 ..., 60 bytes. R4 Each comparison in the parser is a separate code block, so each correct byte is a step the fuzzer can see and keep; the worked example computes why that matters.

After the crash

The crash becomes a regression test (Listing 7) with the crash's essential shape (type 2, length 48) and its neighbours at the boundary (32, 31, 0). Against the old parser it fails with the same AddressSanitizer report; against the fixed parser it passes. Layer 3 — the engineer's depth

Analogy

An inspector with a good rule and a bad way of choosing doors finds nothing. The craft is in both.

Where properties come from

Writing properties is a skill with a small set of patterns:

  • Round trip: decode(encode(x)) = x; parse(format(x)) = x. Parsers, serialisers, compressors, protocol encoders (Listing 3).
  • Model or oracle: the fast implementation agrees with a slow, obvious one: a ring buffer and a deque; a GPU kernel and a CPU reference within a justified tolerance (F0-80, curriculum 13.4); a frame allocator and a set, which is the B3 acceptance test "random allocate/free sequences against a reference model". D6
  • Invariants: after any sequence of operations, the free count equals the number of frames minus those in use; a sorted output is sorted and a permutation of the input.
  • Metamorphic relations: when no oracle exists, relate two runs: scaling all distances by 2 must not change whether the robot meets S1 when the speeds are scaled too; adding a no-op must not change the result.
  • "Does not crash": the weakest property and the fuzzer's default oracle, made strong by sanitizers, which turn silent memory errors and undefined behaviour into reported failures (F2-29).

Generators decide what can be found

The RLE bug needs a run of at least 256 equal bytes. A generator of uniformly random bytes almost never produces two equal neighbours, let alone 256; Listing 3's generator draws a few values from a four-value alphabet and long run lengths that grow with the size parameter, so long runs are common. Ask of every generator: what is the probability that it produces the boundary I fear? The lab asks you to measure it by changing the generator. Growing size (small inputs first) has two benefits: small failures are found first and are easy to read, and fast early runs catch shallow bugs cheaply. D1

Shrinking is greedy, and that is fine

Our shrinker takes the first smaller candidate that still fails. That finds a local minimum, not a global one: the ring-buffer result kept the value 12 because the only value-shrink it tries is 0. A shrinker that also tried halving would report push(1) or similar. Real libraries invest heavily in shrinking because a short counterexample is what a human can debug. D1 Shrinking must preserve the generator's own invariants: shrinking a list of operations by deleting one is safe because any sequence is valid; shrinking a frame by deleting a byte breaks its length field, which is why fuzzers rarely shrink structurally.

How coverage feedback works here

GCC's -fsanitize-coverage=trace-pc inserts a call to __sanitizer_cov_trace_pc into every basic block of the instrumented file. D3 Listing 6 defines that function (lines 100–104): it hashes the caller's return address into a 4096-entry table of "seen" flags. run_one copies the table before an execution and counts entries that became set; a positive count means new coverage. Only pkt.cc is instrumented, so the fuzzer's own code does not pollute the signal. The hash can collide: two blocks can share an entry, so a new block can occasionally be missed; a bigger table makes that rarer. Production fuzzers record edges (pairs of blocks) and hit counts, not only blocks, and add comparison tracing and dictionaries to get past magic values faster. D4 D5

Where fuzzing pays, and how long to run it

Fuzz code that parses data from outside your trust boundary: sensor frames, network packets, file formats (the ELF reader of F2-44), firmware tables, USB descriptors (curriculum 5.5 lists corrupted descriptors under fault injection). D6 Curriculum milestone P2's acceptance test sets a duration: "Malformed inputs (truncated file, bad offsets) are rejected without crashing; a fuzzing run of at least an hour finds nothing." D6 A practical split: a short, seeded, deterministic fuzz run in every CI build (it catches regressions in seconds and never flakes), and long runs on a schedule, with the corpus saved between runs. Every crash becomes a regression test in the ordinary suite, so the fix is protected even when the fuzzer is not running.

Properties and fuzzing for kernels, GPUs and robots

Kernel code that is pure logic (allocators, parsers of ACPI or devicetree blobs, page-table builders) can be compiled for the host and tested with properties and sanitizers there, the "host first" rule of curriculum section 0 (F12-09 does this with a frame allocator). GPU kernels get model-based properties against a CPU reference with justified tolerances. Robot controllers get metamorphic and invariant properties over simulated scenarios: the scenario matrix of F12-07 is a hand-made generator; a seeded random one, with shrinking toward the simplest failing world, is the next step.

How the hardware actually does it

AddressSanitizer is how a fuzzer "sees" a memory error that would otherwise corrupt silently. The compiler surrounds stack variables with poisoned red zones and checks every memory access against a shadow map (one shadow byte per 8 bytes of memory, as the report's legend says in F2-29's runs); memcpy is intercepted and checked over its whole range. D3 In R4 the report says the 48-byte write started inside the 40-byte object f (a Frame: two 4-byte integers and a 32-byte array) and ran into the red zone after it; the object belongs to the frame of run_one, the caller, because that is where f was declared. R4 Without ASan the same write would overwrite the caller's other variables or its return address, and the program might crash later in an unrelated place, or not at all. Coverage instrumentation, similarly, is extra code: a call in every basic block. Fuzzing measures an instrumented program, as coverage measurement did in F2-30.

Worked example

Task. Estimate why blind mutation of hello found nothing in 300,000 executions, while guided fuzzing reached the bug.

  1. What the bug needs. Byte 0 = S, byte 1 = P, byte 2 = 2, byte 3 (length) above 31, and at least length + 5 bytes in total.
  2. Blind, optimistic bound. Even if every input had three fully random leading bytes, the chance of exactly S, P, 2 is 1 / 2563 = 1 / 16,777,216, about 6.0 × 10−8. Over 300,000 executions the expected number of hits is 300,000 × 6.0 × 10−8 ≈ 0.018. In reality it is far smaller: a blind mutation changes at most four bytes of hello, so all three bytes must be hit at once and set to the right values.
  3. Guided. Each correct byte is a new code block (the comparisons at pkt.cc lines 14, 17 and the type branches), so the fuzzer keeps each partial success. It needs roughly "one byte right" at a time: probabilities of the order of 1 / 256 times the chance of choosing that position and that mutation, instead of the product of all three. The run needed 2114, then 1517 more, then about 15,000, then about 2,000 executions for the four steps (R4).
  4. Conclusion. Feedback turns a product of small probabilities into a sum of moderate ones. The length and size conditions were then satisfied by the "append a chunk" mutation within about 18,000 more executions.

The 300,000 and the execution counts are from the runs; the probabilities are computed here by hand from the frame format. Run the lab with other seeds: the counts change, the pattern does not.

Where the analogy breaks


    

  • A building has 140 doors; a parser has more inputs than atoms. Lina could, in principle, try every door. A 60-byte frame has 25660 possible values. Generated testing is sampling, never exhaustive; "200 runs passed" means "no counterexample found in this sample", nothing more (R1's fixed encoder).
    • 

  • The cousin gets tired; a fuzzer does not, but it can get stuck. A fuzzer runs millions of executions without tiring, yet it can plateau for hours behind a check it cannot pass (a checksum, a cryptographic signature). Engineers then help it: dictionaries, a fuzzing build that skips the checksum, or a structure-aware generator.
    • 

  • A wobbly rail is visible; a memory error often is not. The cousin sees the rail move. Without AddressSanitizer, the 48-byte overflow of R4 might not crash at all. The oracle (sanitizers, properties) is half of the method; the analogy has no equivalent.
    • 




Common mistakes and debugging


    

  • Symptom: a property never fails although you know there is a bug. Cause: the generator cannot produce the triggering input (uniform bytes never make long runs). How to find it: print a histogram of a generated feature (run lengths, sequence lengths). Fix: bias the generator toward boundaries and structure.
    • 

  • Symptom: a failure seen in CI cannot be reproduced. Cause: unseeded generator, or the seed was not printed. Fix: seed explicitly, print the seed on every failure, accept a seed from the command line (F12-10's forensic lab is this bug).
    • 

  • Symptom: the property itself is wrong (fails on correct code, or is a tautology such as encode(x) == encode(x)). Fix: check the property against a planted bug, as this chapter does, and against the fixed code.
    • 

  • Symptom: the fuzzer finds a crash but you have no input. Cause: the process aborted before saving it. Fix: a death callback (Listing 6, lines 34–41) or write each input to a file before running it.
    • 

  • Symptom: fuzzer progress lines vanish when it crashes. Cause: stdout to a pipe is block-buffered, and an abort does not flush it (this happened while building the lab). Fix: line buffering or explicit flushes (Listing 6, line 117).
    • 

  • Symptom: a fuzzer reaches no new coverage after the first seconds. Cause: magic values, checksums, or the instrumentation is missing from the target file. How to find it: print the corpus growth; check that the target object contains calls to the coverage hook (nm shows it as undefined). Fix: seed inputs that pass the checks; a fuzzing build that disables the checksum.
    •

Mini-project


Generated tests for the mega project (course project, part 3). Pick two components of your mega project: one parser or protocol handler, and one stateful component (allocator, queue, scheduler, state machine). Write a property-based test with a model for the stateful one, and a seeded fuzz target with a sanitizer oracle for the parser. Run each with a fixed budget in CI and a longer one overnight; record what they found.


Rubric. Properties are meaningful (not tautologies) and seen failing on a planted bug (3). Generators reach the boundaries, with evidence (2). Fuzz target instrumented, sanitizers on, inputs saved on failure (2). Findings turned into regression tests, or an honest report that nothing was found and how long was spent (3).



Summary


    

  • Property-based testing checks a rule on many generated inputs and shrinks failures; a 442-byte failure became [0*256] (R1).
    • 

  • Useful properties: round trip, agreement with a model, invariants, metamorphic relations, "never crashes" with sanitizers.
    • 

  • The generator decides what can be found; design it for the boundaries you fear.
    • 

  • Coverage feedback turns a product of tiny probabilities into a staircase of small steps: guided fuzzing found the overflow at execution 38745, blind fuzzing found nothing in 300,000 (R3, R4).
    • 

  • Sanitizers are the fuzzer's eyes: ASan reported a 48-byte write into a 40-byte object at pkt.cc:32.
    • 

  • Every failure becomes a regression test that includes the boundary's neighbours (R5, R6); then fuzz again (R7).
    • 

  • Print and accept seeds; short deterministic runs in CI, long runs on a schedule.
    •

Forensic lab answer key


How the evidence was produced. The guided run of minifuzz (seed 1, 300,000 executions) against the planted bug in pkt.cc, with ASAN_OPTIONS=print_legend=0; paths were made relative by run.sh; nothing else was changed. R4


Observation. A 48-byte write by memcpy, called from parse_frame at pkt.cc:32, into the stack object f (bytes 48–88 of the frame of run_one, so 40 bytes long), declared at minifuzz.cc:48. The input starts 53 50 02 30: S, P, type 2 (text), length 0x30 = 48; the input is 60 bytes, enough for 48 payload bytes and a checksum position.


Hypotheses. "Checksum wrong": the checksum is computed after the copy (lines 37–41), so it cannot be involved in an overflow at line 32. "Harness bug": the write is inside parse_frame, into an object of the correct type passed by the harness; the harness only passes f. "Length trusted": line 32 copies len bytes into f.text, which is 32 bytes; nothing checks len against it. The evidence supports the last.


Root cause. The length check on line 21 only ensures the input holds the payload; it does not ensure the payload fits the destination. With len = 48, memcpy writes 48 bytes into a 32-byte array that sits 8 bytes into a 40-byte struct, so it writes past the end of f. The checksum is verified last, after the damage.


Fix and verification. Refuse a text that does not fit with its terminator before copying (pkt_fixed.cc: if (len >= sizeof f.text) return false;). The regression test with lengths 48, 32, 31 and 0 fails on the old parser with the same ASan report and passes on the fixed one; fuzzing the fixed parser with the same seed and budget finds no crash. R5 R6 R7 A better design also verifies the checksum before using the payload.


Severity and prevention. Yes: a corrupted or malicious frame on the serial line reaches this code. Without ASan the write would silently overwrite the caller's stack (other variables, possibly a return address): wrong behaviour later, a crash elsewhere, or an exploitable bug. Process: fuzz every parser of external input in CI with a short seeded run and overnight with a long one; review rule "every copy is bounded by the destination size"; keep the regression test.


Wrong answers and why. "Disable the fuzzer, it is noisy": the bug exists without the fuzzer. "Increase the array to 64 bytes": the length field can say 255; the bound must come from the destination.
