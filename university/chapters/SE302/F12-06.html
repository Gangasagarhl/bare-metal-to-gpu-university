Story hook

Amara's team is building a house. Every brick that arrives is checked: is it the right size, is it cracked? Every beam is measured. Those checks are quick and cheap, and they happen hundreds of times a day.

But the bricks were all perfect, and the first rain still came through the wall. The bricks were fine; the joint between the wall and the window frame was not. The bricklayers had measured in centimetres and the window maker in inches. Each team had checked its own work against its own drawings, and each was right on its own.

So the site also needs a second kind of check, where two pieces meet. And once the house stands, someone must walk through it in the rain, turn on every tap and close every door. That walk is slow and can only be done a few times. If you only did that walk, you would find leaks, but you would not know which brick, joint or pipe caused them.

Software teams face the same choice every day: how many checks of each kind, and where. This chapter is about choosing them on purpose.

What you will be able to do

  • Explain unit, integration and system tests, what each can and cannot see, and why their costs differ.
  • Measure what a test suite really catches by planting bugs (mutants) and recording which level kills each one.
  • Diagnose a test suite that is expensive and still blind to a whole class of bugs, from its mutation report.
  • Design a test portfolio for a small system: which checks at which level, with a written reason for each.
  • Write the first section of a test plan in the form of curriculum section 5.5, with acceptance tests fixed before code.
Jargon box
Test pyramid
Simple words: a picture that says: write many small, fast tests, fewer tests that join parts together, and only a few tests of the whole system. Analogy: check every brick, many joints, and walk through the finished house a few times. Precise: a heuristic for the shape of a test portfolio, with test levels ordered by scope; the narrow, cheap, precise levels at the wide base and the broad, slow, ambiguous levels at the narrow top. It is a starting shape, not a law. D1 D3
Integration test
Simple words: a test that runs two or more real parts together and checks that they agree. Analogy: checking the joint between the wall and the window frame. Precise: a test whose scope covers the interface between units (data formats, units of measure, call order, error conventions) with the real implementations on both sides, in contrast to a unit test, which isolates one unit. D5 R1
System test (end-to-end test)
Simple words: a test of the whole thing doing its job, judged by what a user would see. Analogy: walking through the finished house in the rain. Precise: a test that exercises the complete system (here, the closed control loop with a simulated world) against its requirements, observing only externally visible behaviour. D5 R1
Test oracle
Simple words: the rule that decides whether a result is right. Analogy: the drawing the inspector compares the wall with. Precise: the mechanism that judges an observed outcome as pass or fail: an expected value, a requirement such as "never closer than 0.35 m", a reference model, or a property; in curriculum section 0 the oracle for kernel tests is the serial output. D2
Test double
Simple words: a stand-in for a real part, used only in tests. Analogy: a wooden frame standing in for the window while the wall is built. Precise: an object or function that replaces a real dependency in a test; kinds include fakes (a working light implementation), stubs (fixed answers) and mocks (which also check how they were called). In this chapter the simulated world is a test double for the real corridor. Not to be confused with the RPC stub of F5-09, which is production code. D1
Contract test
Simple words: a test both sides of an interface agree on, so neither can change the deal alone. Analogy: one shared drawing of the window opening, signed by the bricklayers and the window maker. Precise: a test that checks a property of an interface (here: "the parser returns metres") and is run against every implementation and by every consumer of that interface. D1
Hermetic test
Simple words: a test that brings everything it needs and touches nothing outside itself. Analogy: testing a door in the workshop, not in a house where people walk through it. Precise: a test that depends only on inputs it controls (no network, shared files, real clock or shared state), so its result depends only on the code under test. D1

This chapter also uses terms defined earlier: unit test and regression test (F2-30), continuous integration (F2-26), and mutation testing (F4-18).

Layer 1 — the kid explanation

Analogy

A building site has three kinds of inspection. Brick checks: many, quick, and when one fails you know exactly which brick is bad. Joint checks: fewer, where two teams' work meets. The walk-through: slow, rare, and the only check that notices that the house as a whole does what people need. Mapping: brick = unit; joint = interface between units; walk-through = system test; the drawing an inspector compares with = test oracle.

A test is a small program that runs your code and says "pass" or "fail". Tests come in sizes. A small test checks one function. A medium test checks that two parts work together. A big test runs the whole system and checks that it does its job.

Small tests are fast, and when one fails it points at the broken function. Big tests are slow, and when one fails it only says "something is wrong somewhere". But only big tests can see problems that come from timing, from many parts together, or from the world around the program.

So a good team writes many small tests, a fair number of medium tests, and a few big ones. Then it checks its own work: it breaks the code on purpose, and looks at which tests notice. A test that never fails, whatever you break, is not protecting anything.

Layer 2 — the student explanation

Analogy

Before choosing inspections, the site manager lists what can go wrong: cracked bricks, mismatched measurements, leaks that only show in a storm. Each kind of defect has a cheapest place to catch it.

The system under test

The lab uses one small system all through this course. A delivery robot drives along a corridor toward a shelf. A range sensor sends text packets such as R 1500 (1500 millimetres). Unit 1, the parser, turns a packet into metres. Unit 2, the governor, turns a distance into a speed limit: 0 at or below 0.5 m, 1.0 m/s at or above 1.0 m, and a straight line in between. The control loop applies the limit to a motor that can change speed by at most 2 m/s² (Listing 1). The requirements of the whole system are written in portfolio.hpp: S1, never closer to the shelf than 0.35 m; S2, at the end stopped (below 0.02 m/s) within 0.65 m; S3, never faster than 1.0 m/s. R1

Three levels, three kinds of evidence

  • Unit tests call one unit with chosen inputs and compare with values from its specification. The parser gets 7 checks (typical, boundary, invalid), the governor 6. On the correct system they cost 7 and 6 function calls. R1 A failure names the unit and the input.
  • Integration tests send real packets through the real parser into the real governor and check the speed: R 4000 → 1.0, R 750 → 0.5, R 300 → 0, and an unparsable packet → 0 (the controller's fail-safe rule). They see the interface: units, formats, error conventions. R1
  • The system test runs the closed loop for 20 simulated seconds from 4 m and checks S1–S3. It sees timing and dynamics: how stale the reading is, how fast the motor reacts. It cost 2000 simulation steps. A failure says "the robot came too close", not why. R1

Measuring a suite by breaking the code

How do you know a suite is good? Coverage tells you which lines ran (F2-30), not whether a wrong result would be noticed. A stronger measure: plant a bug (a mutant) and see whether any test fails ("kills" it). F4-18 did this for a driver. D4 The lab plants five realistic bugs and runs all levels against each (Listing 2, output below Figure 1):

  • M1 deletes the governor's upper clamp; far from the shelf it commands more than 1.0 m/s. Killed by the governor's unit tests, by integration and by the system test.
  • M2 changes the parser to return millimetres, and its author changed the parser's own unit tests to millimetres too. Both units pass their own tests. Only integration and system tests kill it: this is the window-frame joint of the story hook.
  • M3 makes the control loop act on a reading that is 0.6 s old. The functions are untouched, so unit and integration tests pass. Only the system test kills it: the robot stops too close.
  • M4 makes the parser read malformed digits as 0 mm. The integration test sends one malformed packet, but 0 mm also means "stop", so the speed is the same as the fail-safe answer. Only the parser's unit test bad("R ") kills it.
  • M5 types the stop distance as 0.05 m. Killed by three levels.

The run's verdict: the correct system passes every level, and every mutant is killed by at least one level; but no level alone kills all five. R1

Why a pyramid

Three arguments make the base wide. Cost: in this lab one system run did 2000 simulation steps against 6–8 calls for the small levels; with a real simulator or real hardware the gap is far larger, and every test runs on every change. Diagnosis: a failed unit test names the unit; a failed system test starts an investigation. Determinism: small tests have fewer moving parts, so fewer ways to be flaky (F12-10). D1 Two arguments keep the top from disappearing. Some bugs exist only in the whole (M3). And the requirements are written about the whole system, so the final evidence must be about the whole system too.

Layer 3 — the engineer's depth

Analogy

A good site manager does not ask "how many inspections?" but "which defect does each inspection exist to catch, and is that the cheapest place to catch it?"

Start from failure modes, not from levels

The pyramid is a description of a healthy result, not a design method. The design method is: list the ways the system can fail, then for each one choose the cheapest test that can observe it. Curriculum section 5.5 is exactly such a list for a driver: emulator tests, host unit tests for every pure function, trace replay, a real-hardware matrix, fault injection, soak, reference comparison, and regression on every commit. D2 For our robot, the failure modes and their cheapest observer are:

Failure modeCheapest observerWhy not lowerWhy not higher
Arithmetic or boundary error inside a unit (M1, M5)Unit test—Higher levels also catch it (R1) but cannot say where
Malformed input accepted (M4)Unit test with invalid inputs—Higher levels could not see it: the wrong answer equals the fail-safe one
Two units disagree on a contract (M2)Integration or contract testEach unit is right by its own specificationThe system test catches it too, at 2000 steps instead of 8 calls
Timing, staleness, dynamics (M3)System test in simulationThe functions are correct; the loop around them is notReal hardware adds risk and cost; use it to confirm the model (F12-07)

Notice row two. It is tempting to think that higher levels "include" lower ones, because they run more code. They run more code but observe less: the system test watches the robot's distance, and a parser that turns garbage into 0 mm makes the robot stop exactly as the fail-safe rule would. The observation point decides what a test can catch, not the amount of code it runs. R1

Scope, size and the cost model

Two different axes are often mixed up. Scope is how much of the code is meant to be validated (one unit, an interface, the whole). Size is what resources a test needs: one process or several, a network, a disk, real time, real hardware. "Software Engineering at Google" separates these two axes for this reason. D1 A system test can be small in size (our 2000-step simulation runs in one process with no I/O), and a unit test can be large (a driver unit test that needs a real device). Size is what drives cost and flakiness; scope is what drives what the test can find.

A simple cost model makes the trade-off explicit. Let a level have n tests, each costing c (machine time per run) and each failing for reasons other than a bug with probability f (flakiness). Per commit the suite costs about n·c, and the chance of at least one false alarm is 1 − (1 − f)n. Large tests have large c and large f; a top-heavy suite pays both on every commit. F12-10 works this formula with numbers.

Beyond the pyramid

  • Contract tests sit between levels. M2 survived both unit suites because each side's tests encoded its own belief. A contract test ("for R 1500, the parser returns 1.5, in metres") belongs to the interface, not to either side, and both teams run it. It costs one call and kills M2. The lab asks you to add it.
  • Simulation and hardware-in-the-loop tests extend the top: the same system test against a better world model, then against real hardware (F12-07).
  • Property-based tests and fuzzing widen the base: instead of 7 hand-chosen parser inputs, millions of generated ones (F12-08).
  • Static checks sit below the base: warnings as errors and sanitizers (F2-27, F2-29) catch whole classes of bugs before a test runs.
  • Mutation analysis is a test of the tests. Real mutation tools generate many mutants automatically; the lab's five are written by hand to stand for realistic mistakes. D4

From portfolio to test plan

Curriculum section 0 says to write the test harness first where possible, and that the acceptance tests of a milestone are fixed in advance and never weakened later without the learner's explicit approval. D2 A test plan therefore records, before code: the failure modes; the level and observer for each; the acceptance criteria (numbers such as 0.35 m are written here, not discovered later); what runs on every commit and what runs less often; and what cannot be tested yet and why. The course project and the practical exam both ask for this document.

How the hardware actually does it

Test levels map onto hardware in a way that explains their cost. A unit test runs a few functions in one process: the instructions and data fit in the CPU caches, and nothing waits for a device (F1-32). An integration test of a driver may need a device model or an emulator (curriculum 5.5 puts emulation first when QEMU models the device). D2 A system test of a robot needs either a simulator, which must step a physical model many times per simulated second (2000 steps for 20 s here), or the real robot, which runs in real time, needs a person nearby for safety, and can be damaged. The higher you go, the more the test waits for something other than the CPU: emulated devices, simulated physics, real motors. That waiting is what makes the top of the pyramid expensive, and it is also where timing bugs such as M3 live.

Worked example

Task. Check by hand that the integration test R 750 → 0.5 kills M2 but the parser's unit test is("R 1500", 1.5 * s) does not.

  1. Correct system. The parser turns R 750 into 750 / 1000 = 0.75 m. The governor: 0.75 is between 0.5 and 1.0, so the limit is 1.0 × (0.75 − 0.5) / (1.0 − 0.5) = 0.25 / 0.5 = 0.5 m/s. The test expects 0.5: pass.
  2. M2. The parser returns 750 (millimetres). The governor sees 750, which is at least 1.0, so it returns 1.0 m/s. Expected 0.5: the integration test fails, M2 is killed.
  3. M2's own unit test. For M2 the scale s is 1000 (its author wrote the tests in millimetres), so the check is "parse(R 1500) = 1.5 × 1000 = 1500". M2 returns 1500: pass. The parser's unit suite cannot kill M2, because it tests the parser against the parser's own (changed) belief.
  4. Cost of the fix. A contract test "parse(R 1500) = 1.5 metres", owned by the interface, costs one call and kills M2 at the base of the pyramid.

The program confirmed steps 1–3: the M2 row shows unit-P pass, integr. FAIL. R1

Where the analogy breaks


    

  • Software tests are re-run on every change; inspections are not. A brick is inspected once. A unit test runs thousands of times over the life of the code, so its cost and its flakiness are multiplied by every commit. That multiplication, more than the cost of one run, is why the base must be cheap.
    • 

  • A house's parts do not change their meaning silently. A brick does not become a different size because someone edited a line elsewhere. In software, M2 changed what a number means with no visible change at the interface (still a double). Contract tests exist because types do not carry units unless you make them.
    • 

  • The walk-through sees more than our system test. A person walking through a house notices things nobody listed. A system test only checks the requirements someone wrote (S1–S3); it would not notice a robot that wobbles, unless a requirement says so.
    • 




Common mistakes and debugging


    

  • Symptom: the suite takes a long time and still lets bugs through. Cause: an inverted pyramid ("ice-cream cone"): many slow system scenarios that all observe the same thing. How to find it: a mutation report per test (the forensic lab). Fix: push each check down to the cheapest level that can observe its failure mode; keep a few system tests per requirement.
    • 

  • Symptom: every unit suite is green, the integrated system is wrong. Cause: each side tests its own belief about an interface (M2). Fix: a contract test owned by the interface; types that carry units (a Metres type instead of double).
    • 

  • Symptom: a system test fails and nobody can say why. Cause: a failure mode with no lower-level test. Fix: reproduce it in the system test, then write the smallest test that fails for the same reason, and keep both (regression test).
    • 

  • Symptom: a test fails on correct code. Cause: a wrong oracle (expected value, or a requirement threshold nobody wrote down). How to find it: run the suite on the known-good variant first, as Listing 3 does (line 27). Fix: derive expected values from the specification by hand (the worked example), never by copying the program's output.
    • 

  • Symptom: a mutant survives every test. Cause: either a missing test, or an "equivalent mutant" that does not change observable behaviour. Fix: decide which, in writing; if the behaviour matters, add the observer (M4 needs a unit test because no higher level can see it).
    •

Summary


    

  • Unit, integration and system tests observe different things; in the lab each level caught a bug the others could not (R1).
    • 

  • A level's power comes from where it observes, not how much code it runs: M4 was invisible above the unit level.
    • 

  • Unit suites encode their authors' beliefs; contract tests protect interfaces between teams (M2).
    • 

  • Timing and dynamics bugs exist only in the whole system (M3), so the top of the pyramid never disappears.
    • 

  • The pyramid shape follows from cost per commit, diagnosis and determinism; it is a heuristic, not a law.
    • 

  • Measure a suite by the mutants it kills; an expensive suite can still be blind (R2).
    • 

  • A test plan fixes failure modes, levels, oracles and acceptance criteria before code (curriculum 0 and 5.5).

Forensic lab answer key


How the evidence was produced. suite_report.cpp runs an inverted suite (one governor unit test, twelve system scenarios from 1.5 m to 7.0 m) against the five mutants of portfolio.hpp; nothing was edited by hand. R2


Observation. One run costs 24001 units of work; 24000 of them are the twelve system scenarios (2000 steps each), 1 is the unit test. Every scenario kills exactly M1, M2, M3 and M5; the unit test kills M1. M4 is never killed.


Hypotheses. "Each start distance tests something different" is refuted for these mutants: all twelve rows kill the identical set. "Most scenarios are redundant" is supported: one scenario kills everything the other eleven kill. (Redundant for these mutants; a different mutant could separate them, so keep one or two distances that matter physically, such as starting inside the ramp.)


Root cause. No test observes the parser's output on invalid input. M4's wrong value (0 mm) produces the same speed as the fail-safe rule, so no system scenario, however many, can see it (Layer 3, row two).


Fix. For example: the parser's 7 unit checks (kill M4), the governor's 6 (kill M1, M5), the 4 integration packets (kill M2), one or two system scenarios (kill M3). Work per run from R1: 7 + 6 + 8 + 2000 (or 4000) = 2021 (or 4021), against 24001 now, and five of five mutants killed.


Prevention. Run a mutation report like Listing 3 in CI (nightly if it is slow) and fail when a mutant survives without a written reason; review new tests by asking which failure mode they observe.


Wrong answers and why. "Buy a faster CI machine": the suite would be faster and exactly as blind. "Add more start distances": more of the same observation cannot see M4.
