Story hook

The new school has smoke alarms in every room. In week one, the alarm in room 14 beeps during a maths lesson. Everybody files out; there is no smoke. In week two it beeps again; no smoke. By week four, when it beeps, the teacher says "it's that alarm again" and carries on.

In week six the alarm in room 14 beeps, and this time there is a small fire in the store room behind it. The class keeps working for three minutes before somebody smells it.

Nobody decided to ignore fires. They learned, one false alarm at a time, that this alarm did not mean anything. The alarm was not wrong every time; it was wrong sometimes, and that was enough to make it useless.

A test that sometimes passes and sometimes fails on the same code is that alarm. This chapter shows where such tests come from, how to measure them, how to find the cause, and why "re-run it and move on" is how teams learn to ignore fires.

What you will be able to do

  • Recognise a flaky test, and name its common causes: timing assumptions, order dependence and shared state, data races, hidden randomness, and environment.
  • Measure flakiness with repeat runs, and compute how many runs you need to see a rare failure or to trust a fix.
  • Diagnose a flaky test from CI history: reproduce it deterministically, then find whether the bug is in the test or in the code.
  • Fix the common causes: wait for events instead of sleeping, isolate state, remove races (with ThreadSanitizer's help), and print and accept seeds.
  • Set a team policy for retries and quarantine that does not hide real failures.
Jargon box
Flake rate
Simple words: how often a flaky test fails on code that has not changed. Analogy: how many false beeps the alarm gives per week. Precise: the estimated probability p that one run of a test fails, measured as failures ÷ runs over repeated runs of one fixed commit in one fixed environment; it depends on the machine and its load, so it is recorded together with them. D2 R1
Repeat run (stress run)
Simple words: running the same test many times on the same code to see whether it ever fails. Analogy: lighting a candle under the alarm a hundred times to see whether it always beeps. Precise: executing a test n times on one commit, often with load, shuffled order or different CPU counts, to estimate its flake rate or to gain confidence in a fix; the number of runs follows from the rate you want to detect (worked example). R2
Order-dependent test
Simple words: a test whose result depends on which tests ran before it. Analogy: an alarm that only works if the alarm next door was tested first. Precise: a test that reads state another test leaves behind (globals, caches, files, a database, environment variables), so it passes or fails depending on the execution order; a failure of test isolation. Shuffling the order with a printed seed exposes it. D2 R1
Automatic retry (test rerun)
Simple words: when a test fails, run it again and accept the result if it passes the second time. Analogy: when the alarm beeps, wait to see if it beeps again before leaving. Precise: a CI policy that re-executes failing tests and reports a pass if a retry passes; it hides a failure of probability p with probability about 1 − p, so it hides real intermittent bugs as well as test defects, and must be recorded and counted when used at all. D1 R5
Quarantine (flaky test)
Simple words: moving a flaky test out of the blocking suite while it is fixed, with a name, an owner and a date. Analogy: taping a note on the alarm "under repair, fire warden checks room 14 by hand until Friday". Precise: a recorded exclusion of a known-flaky test from the merge gate; it keeps running and reporting outside the gate, has an owner and a deadline, and returns to the gate only after a repeat run shows the fix. For curriculum acceptance tests it is a weakening and needs the learner's approval. D1 D3

Also used: flaky test (F10-33), test isolation (F2-30), data race, race condition, condition variable and ThreadSanitizer (TSan) (F2-35, F2-37), seed, bisect.

The idea in pictures

Figure 1 is the triage path for a test that failed once. The first question is never "does it pass if I re-run it?" but "can I make it fail again on purpose?": a failure you can reproduce is an ordinary bug.

Layer 1 — the kid explanation

Analogy

The alarm that beeps for no reason. Mapping: the alarm = a test; a beep without smoke = a test failing on correct code; silence with smoke = a test passing on broken code; "it's that alarm again" = re-running until green; taping a "being repaired, checked by hand" note on it = quarantine; lighting a candle under it a hundred times = a repeat run.

A good test says the same thing every time you run it on the same code. A flaky test sometimes says "pass" and sometimes "fail", and nothing in the code changed.

That happens when the test depends on something it does not control: how fast the computer is today, which test ran right before it, two parts of the program racing each other, or a dice roll it did not write down.

The worst thing about a flaky test is not the wasted time. It is that people stop believing failures. Then, one day, a real failure looks exactly like the flaky ones, and nobody looks.

Layer 2 — the student explanation

Analogy

To fix the alarm you must first find out why it beeps: dust, a low battery, steam from the kitchen. Each cause has its own repair.

Two shapes, run 200 times

Listing 1 (flaky_suite.cpp) contains three tests and runs each 200 times on the same code.

  • async_wait_sleep starts a worker thread that takes 0–4 ms (the stand-in for I/O), sleeps 2 ms "which should be enough", and checks that the worker is done. Whether it is depends on the worker's duration that run and on the scheduler.
  • order_dependent assumes it starts with an empty cache. Another test, fills_cache, leaves an entry in the same global cache. The order of the two is shuffled per run, as a test runner with random order would.
  • async_wait_fixed is the first test repaired: it waits for the worker's signal on a condition variable, with a deadline of 5 s, far above the worker's time.


Both broken tests failed in roughly half of the runs and are FLAKY; the repaired one never failed. R1 The exact count for async_wait_sleep changes from one run of the lab to the next (it depends on the scheduler); the count for order_dependent does not, because the order comes from a seeded generator. That difference is itself a clue: a flake rate that is stable under repetition points at hidden but reproducible randomness, not at timing.

That is the key property of a race detector: it reports the race that could happen, not only the one that did. A flaky test in multithreaded code is a reason to run it under ThreadSanitizer before anything else.


Why "re-run it" is the wrong first move


A retry policy asks: "does it pass if we try again?" For a test that fails with probability p, a single retry passes with probability 1 − p, whatever the cause. It cannot tell a bad test from an intermittent bug in the product. The forensic lab is a team that re-ran a failing test for months; the cause was a real bug in the code under test, with a reproducible input, hidden because the test did not print its seed.

Kernels, GPUs and robots


In kernel tests under QEMU, a fixed sleep becomes a too-tight time limit: an emulator on a loaded CI runner can be several times slower than on a quiet laptop, so the limit must be measured on the runner and generous (F12-09). Multi-CPU kernel tests (-smp 4) add real nondeterminism in interrupt and scheduling order; that is a reason to run them many times, not a reason to accept occasional failures. GPU tests become flaky when a tolerance is too tight for a reduction whose summation order changes between runs (atomics, different grid sizes): either make the order deterministic or justify the tolerance (curriculum 13.4, F0-80). Robot simulation tests become flaky when the simulator runs in real time on a loaded machine; a lockstep simulation (F10-33) or a simulated clock removes that.


A policy that does not hide fires


    

  • Every failure is recorded, including those a retry passed; a dashboard counts failures per test and per commit, so a flake rate can be computed from history.
    • 

  • Retries, if used at all, are visible. "Passed on retry" is a separate result, and a test that needs retries gets an owner.
    • 

  • Quarantine has an owner and a deadline, and the quarantined test keeps running outside the gate. A quarantined test that nobody fixes is a deleted test with extra steps.
    • 

  • Acceptance tests of the curriculum are never quarantined silently. The agent rule is: "Never skip, weaken or postpone an acceptance test. If a test cannot pass (missing hardware, emulator limitation), stop, explain, and let the learner decide; record the decision." D3
    • 

  • A fix is verified by a repeat run long enough to detect the old flake rate with the confidence you choose (worked example), on the machine where it failed.
    • 



Some acceptance tests in the curriculum are repeat runs by design: in milestone FS2 (the journal), the power-cut harness must pass "in all 500 runs". D3 Such a test turns flakiness into a measured, required property.

How the hardware actually does it


Why does g_events = g_events + 1 lose counts? On x86-64 the compiler at -O0 emits a load of the value into a register, an add, and a store. Two cores can each load the same old value, add one, and store the same new value: one increment is lost. Each core works on its own cached copy of the line, and the cache-coherence protocol gives the line to one core at a time, but it does not make the load–add–store sequence atomic (F2-38; cache coherence). D5 How often the overlap happens depends on how many cores run the threads at the same time, how long each thread runs before the other starts, and the machine's load; that is why the same binary failed in every run at one time and passed in every run at another on this build machine (R3). In C++ the program has a data race, and its behaviour is undefined; "a lost count" is what this machine happened to do. D5 ThreadSanitizer does not need the overlap to happen: it instruments every memory access and records, per location, which thread accessed it and whether the accesses are ordered by synchronisation; two unordered accesses, one a write, are reported. D4


Timing flakiness has a hardware story too: a 2 ms sleep is a request to the operating system's scheduler, which wakes the thread at or after that time, later if the CPU is busy. Under a sanitizer, or on a loaded CI runner with more jobs than CPUs, "after" can be much later; the worker's own sleep can also overrun. A test that compares two such times is comparing two random numbers.



Worked example


Task. A test failed once last week. (a) If its flake rate is p = 0.1, how likely is it that 10 runs all pass? (b) After a fix, how many consecutive passing runs do you need to be 95 % sure the old 1 % flake is gone? (c) A suite has 200 tests, each with a flake rate of 0.5 %; how often is the whole suite green on a correct commit?


    

  1. Model. Runs are independent with failure probability p. n runs all pass with probability (1 − p)n.
    2. 

  2. (a) (1 − 0.1)10 = 0.910 = 0.3487. One time in three, ten runs look perfect while a 10 % flake remains. R2
    3. 

  3. (b) We want (1 − p)n ≤ 1 − 0.95 = 0.05: if the fix did nothing, n passing runs should be unlikely. n ≥ ln 0.05 / ln 0.99 = (−2.9957) / (−0.01005) = 298.1, so n = 299. Listing 3 prints 299 for 95 % and 459 for 99 %. R2
    4. 

  4. (c) 0.995200 = e200 · ln 0.995 = e200 · (−0.0050125) = e−1.0025 ≈ 0.367. About one green suite in three, with no bug at all. (Computed by hand here, not by a listing.)
    5. 

  5. Conclusions. Rare flakes need hundreds of runs to rule out; a handful of green re-runs proves little. And small flake rates add up across a suite, which is why each flaky test must be fixed, not tolerated: the suite's credibility is the product of its tests'.
    6. 



The independence assumption is optimistic: flaky failures cluster (a loaded runner, a bad hour), so in practice you also vary the conditions between runs.

Where the analogy breaks


    

  • A false alarm is harmless in itself; a flaky test can be the only witness of a real bug. The race test fails because the product is wrong; the alarm beeping "for no reason" was, this time, the reason. Never assume the test is the broken part.
    • 

  • An alarm's false-beep rate is a property of the alarm; a flake rate is a property of the test, the code and the machine together. The race test failed in all 20 runs at one time and passed in all 20 at another, on the same machine (R3). Quote flake rates with their environment.
    • 

  • You cannot replay a fire; you can replay a test. With a printed seed, a fixed order and a recorded environment, most "random" failures become deterministic. The analogy suggests helplessness where engineering offers control.
    • 




Common mistakes and debugging


    

  • Symptom: "it passed on re-run, so it's flaky", and the ticket is closed. Cause: treating flakiness as a diagnosis. Fix: follow Figure 1: reproduce, classify, decide whether the bug is in the test or the product.
    • 

  • Symptom: a sleep is increased from 2 ms to 20 ms and the flake "goes away". Cause: the race between test and code is still there, now rarer (and the suite slower). Fix: wait for the event with a deadline (Listing 1, lines 60–63).
    • 

  • Symptom: a test fails only in the full suite, never alone. Cause: order dependence or shared state. How to find it: run the suite with shuffled order and a printed seed; then bisect the list of tests that run before it. Fix: isolate the state.
    • 

  • Symptom: a multithreaded test fails a few times a month. Cause: a data race or atomicity bug, often in the product. How to find it: ThreadSanitizer (R4); repeat runs on more CPUs and under load. Fix: synchronisation, then a repeat run sized by the worked example.
    • 

  • Symptom: a random-input test fails once and can never be reproduced. Cause: the seed was not printed. Fix: print it on every failure and accept it as input (Listing 4).
    • 

  • Symptom: a quarantined test is still quarantined a year later. Cause: no owner, no deadline. Fix: both, recorded; review quarantines at a fixed interval.
    •

Troubleshooting.


    

  • The race test always passes on your machine → you may have one CPU, or the threads may not overlap; run it 1,000 times, add load, or raise the count; TSan finds it regardless.

Forensic lab


Scenario. For two months, the sensor team's CI has shown test_average_batch failing now and then. Each time, somebody re-ran the job, it went green, and the pull request was merged. The test is now on the team's "known flaky" list. A new team member, Amira, is asked to "make it stop failing". She replays the CI history of one unchanged commit: 400 CI runs, the failing runs, and what each re-run showed. The test draws a random batch of sensor readings and checks that their average lies between the smallest and the largest reading. You have the replay program (the test exactly as it ran in CI) and its output.


Evidence pack.






Questions.


    

  1. Observation: how many of 400 runs failed, which re-runs passed, and what value did the failing test print?
    2. 

  2. Hypotheses: list three possible explanations (timing, environment, a real bug for some inputs) and say what in the evidence supports or excludes each.
    3. 

  3. Root cause: which input makes the test fail, why does the average print as -nan, and why did the comparison then fail? Is the bug in the test or in the code under test?

Summary


    

  • A flaky test passes and fails on the same code; its real cost is that people stop believing failures.
    • 

  • Main causes: timing assumptions, order and shared state, data races, hidden randomness, environment. Each has a way to expose it and a fix.
    • 

  • Reproduce first: same seed, order, commit and machine. A retry that passes is not a diagnosis.
    • 

  • ThreadSanitizer reports a race even in a run where the result was right (R4).
    • 

  • Repeat runs are sized by arithmetic: 299 runs for 95 % confidence against a 1 % flake (R2); ten green runs prove little.
    • 

  • Flakiness can be a real product bug: an empty batch gave 0/0 = NaN, hidden for months by re-runs (R5); the fix changed the code and made the seed visible (R6).
    • 

  • Quarantine needs an owner and a deadline; acceptance tests are never weakened without approval.

Forensic lab answer key


How the evidence was produced. forensic_history.cpp replays the test as written, seeding its generator with CI run numbers 1–400, and a re-run with the number + 1000 (as a CI service would assign a new number); it was compiled and run by run_lab.sh with ASan and UBSan. R5 Nothing was edited.


Observation. 3 of 400 runs failed (runs 111, 185, 199). Each printed "average -nan not within the readings". Re-runs 1185 and 1199 passed; re-run 1111 failed again with the same message.


Hypotheses. Timing: excluded; the test has no threads and no clocks, and the failure value is the same every time. Environment: excluded for the same reason; the replay reproduces it on one machine. A real bug for some inputs: supported; the printed value is NaN, which only arises from an operation such as 0/0.


Root cause. Line 26 draws the batch size as rng() % 100, which can be 0. average (line 19) then divides 0.0 by 0.0, which gives NaN under IEEE 754 floating-point arithmetic (printed as -nan by this C library); every comparison with NaN is false, so the check on line 34 fails. The test happened to find a real bug: average has no defined behaviour for an empty batch, and code that calls it with no readings (a sensor dropout) would receive NaN. The test's own defect is that it hid its seed, so nobody could replay it. UBSan did not report the division in this build (see the unverified box).


Re-runs explained. A re-run used a new number, so a new seed and a new batch size; it fails only if that size is also 0, probability about 1/100. Run 1111 was that coincidence. Expected failures in 400 runs: 400 × 1/100 = 4; observed 3, consistent. The "flakiness" was a deterministic bug behind a random input.


Fix and verification. average returns std::optional and no value for an empty batch; a permanent test for the empty case; the random test prints its seed and replays it from the command line (Listing 4). Replaying the same 400 seeds: 0 failures, and the empty-batch test passes. R6 The callers of average must now handle "no value"; the compiler forces them to.


Prevention. Retrying without recording turned a real failure into folklore. A policy that records every failure, requires a seed in every random test, and gives every flaky test an owner who must reproduce it (Figure 1, step 1) would have found this on the first day.


Wrong answers and why. "Seed the generator with a constant so it always passes": the empty batch would never be tested again, and the product bug would remain. "Make the batch size at least 1": the same, for the test; the product would still return NaN for real empty input.
