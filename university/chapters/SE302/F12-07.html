Story hook

Before the heating goes into the new house, Tomás tests the boiler controller in the workshop. He cannot wait for winter, and he cannot test it in a house that does not exist yet. So he builds a test rig: a box with a heater, a fan and a thermometer that pretends to be the house. The controller is wired to the rig, and the rig is told: "it is minus ten outside, the windows are open".

The controller passes every test on the rig. Then, in the real house, the rooms overshoot and become too hot every morning. Tomás finds out why: the real thermometer sits behind a thick wall and reports the temperature several minutes late. The rig's thermometer answered instantly. The controller was fine for the world the rig described, and wrong for the world that exists.

Nobody blamed the rig for being a rig. The mistake was that nobody had asked, "what does the real thermometer do that our rig does not?" This chapter is about building such rigs for robots, kernels and controllers, and about asking that question before the field does.

What you will be able to do

  • Explain software-in-the-loop, processor-in-the-loop and hardware-in-the-loop testing, and what each one makes real.
  • Build a scenario matrix that sweeps the properties of the simulated world (latency, noise, start conditions) and reports which scenarios break the requirements.
  • Run the same controller source on a second instruction set (AArch64 under QEMU user-mode emulation) in a closed loop with a simulator, and compare the runs line by line.
  • Diagnose "green CI, broken robot" from a CI log and a field log: find the property of the world that the simulation left out.
  • Decide which tests belong in simulation, which on a hardware rig, and which only in a supervised field test, and write the reasons in a test plan.
Jargon box
Software in the loop (SIL, SITL)
Simple words: your real control code, built for your computer, driving a simulated robot. Analogy: the controller's program running on a laptop wired to the rig. Precise: as defined in F10-33: the production software compiled for a development computer, in a closed loop with a simulator that replaces sensors and actuators. D1
Processor-in-the-loop (PIL)
Simple words: the control code built for the robot's own kind of processor, still driving a simulated robot. Analogy: the real controller's chip on a bench, wired to the rig, but not yet in its box. Precise: a closed-loop test in which the controller is compiled with the target's compiler for the target's instruction set and executed on that processor (or, as in this chapter, on an emulator of it), while the plant remains simulated; it checks compilation, numerics and the interface, not real-time behaviour. D1 R5
Hardware in the loop (HIL, HITL)
Simple words: the real robot computer with its real software, connected to a simulated robot body. Analogy: the finished boiler controller in its box, wired to the rig. Precise: as defined in F9-71 and F10-34: the target hardware runs the production software and exchanges signals or messages over its real interfaces with a real-time simulation of the plant. D1
Simulation fidelity
Simple words: how much of the real world the simulator includes, and how accurately. Analogy: whether the rig's thermometer is slow like the real one. Precise: the set of physical effects a simulation models (dynamics, delays, noise, saturation, quantisation, failures) and the accuracy of their parameters; a test result is only valid for the effects modelled. Fidelity is chosen per question: more is not always better if it costs speed or determinism. D2
Scenario matrix
Simple words: the same test run in many versions of the world, one for every combination of the things that may differ. Analogy: testing the boiler with cold and mild weather, open and closed windows, slow and fast thermometers. Precise: a set of system-test runs over the cross product of chosen world parameters (here latency × noise × start distance), each judged against the requirements, so the boundary of safe operation becomes visible. R1
Data age
Simple words: how old a reading is when the controller uses it. Analogy: the thermometer behind the thick wall. Precise: as in F10-34: current time minus the time stamp of the newest reading the controller has received; it adds directly to the loop's delay. Here it is computed from the field log as receive time minus capture stamp. R3
Field test
Simple words: testing the real robot in the real place where it will work, with people watching. Analogy: the first winter morning in the finished house. Precise: a supervised test of the complete physical system in its operating environment; it produces evidence nothing else can, at the highest cost and risk, and therefore comes last, after simulation and bench tests pass (BR-08). D2

Also used: lockstep simulation (F10-33), sim-to-real gap (F9-22), system test and test double (F12-06).

Layer 1 — the kid explanation

Analogy

The test rig pretends to be the house. The controller cannot tell the difference, so you can test it any day, in any weather you invent. Mapping: rig = simulator; controller on a laptop wired to the rig = software in the loop; the real controller in its box wired to the rig = hardware in the loop; the first winter in the real house = field test; the slow thermometer behind the wall = sensor latency.

Robots are expensive, slow to test and can hurt people. So we test their software in a simulator first. The simulator pretends to be the robot and its world. The robot's program reads pretend sensors and drives pretend motors.

A simulator only knows what you told it. If the real sensor is slow and the simulated one is instant, the simulator will happily say "all fine". The test was honest about the world it was given; the world was wrong.

So good teams do two things. They test in many pretend worlds: slow sensors, noisy sensors, fast starts and slow starts. And they climb a ladder: simulator, then the real computer with a pretend robot, then the real robot, slowly and with someone watching.

Layer 2 — the student explanation

Analogy

Tomás's first question for any rig: "what does the real house do that my rig does not?" Write the answer down; it is the list of tests you still owe.

A world model you can turn knobs on

Listing 1 (wallsim.hpp) is the university's tiny world: the robot of F12-06 on a straight corridor. It has knobs: start distance, sensor latency, sensor noise, motor acceleration, duration and a random seed. The sensor's readings travel through a queue (line 70); with latency L, the controller receives the reading measured L seconds ago, with its original time stamp (lines 75–81). Noise is uniform and comes from std::mt19937 with a fixed seed, so every run is repeatable. R1

The scenario matrix

One system test checks one world. A scenario matrix checks many. Listing 2 runs the unchanged controller in 24 worlds: latency 0–500 ms, noise 0 or ±20 mm, start at 2 or 4 m. Every world with latency up to 300 ms passes; every world with 400 ms or more fails requirement S1 (closest approach at least 0.35 m), with closest approaches between 0.305 m and 0.189 m. Noise makes little difference here; start distance makes none. R1 The matrix turns "the test passed" into a map: the controller is safe in this model for latency up to somewhere between 300 and 400 ms, and the next question becomes "what is the real latency?"

The ladder: SIL, PIL, HIL, field

  • SIL (Listing 2): the controller is ordinary C++ built for this computer and called as a function. Fast, deterministic, thousands of scenarios per minute. It can only find what the model contains.
  • PIL (Listings 3–5): the controller becomes its own program, built for AArch64 with the cross compiler, run under QEMU's user-mode emulator, and connected to the simulator through two named pipes. The simulator sends R <mm> packets, the controller answers C <speed>. The run with the x86-64 build and the run with the AArch64 build produced identical logs, line by line. R5 R6 R7 R8 This checks that the code compiles for the target, behaves the same there, and speaks the protocol. It does not check timing: the simulator waits for each answer (lockstep), so a slow controller would look exactly like a fast one.
  • HIL: the real robot computer, with its operating system, drivers and buses, against a simulator that runs in real time. Now a slow controller is a late controller, and the loop sees it. Untested in this build (no robot computer).
  • Field test: the real robot in the real corridor, supervised, after everything below passes (BR-08). D2 Untested in this build.

What goes into CI

SIL scenarios are cheap and deterministic: they run on every commit. PIL needs a cross compiler and an emulator: it can run on every commit too, as it did in this build in a few seconds. HIL needs a rig and a person to maintain it: in most teams a scheduled job, or a gate before a release. Field tests are planned events with a checklist. Curriculum section 0 states the principle for kernels, and it holds for robots: real-hardware runs are recorded as extra evidence, never as a replacement for the emulated test. D2 F12-09 builds such a pipeline.

Layer 3 — the engineer's depth

Analogy

A rig is a promise: "for the effects I model, the controller is safe". The engineer's job is to know exactly which effects those are, and to measure the real ones.

Fidelity is a list, not a level

"High-fidelity simulator" means nothing until you list the effects. BR-08 lists what changes from simulation to a real robot: noise, delays, friction, vibration, battery sag, calibration errors, unmodelled dynamics, timing jitter, and physical danger. D2 Turn that list into a table in your test plan: for each effect, is it modelled, with what parameter value, from what measurement? Our model has latency and noise but no friction, no battery sag, no quantisation of the range sensor and no jitter in the control period. Each "no" is a known gap, and the plan says how it will be covered (a later model, a bench measurement, the HIL rig, or an accepted risk).

Why latency matters so much

A delay in a feedback loop does not change the loop's gain, but it adds phase lag that grows with frequency, and so it reduces the margin before the loop overshoots or oscillates. D3 F10-19 worked this out for a drone's rate loop. In our robot the effect is simpler to see: during the latency the robot keeps driving at the old command. At cruise speed 1 m/s, every extra 0.1 s of latency is 0.1 m driven blind. The sweep shows exactly that: from 300 ms upward, each 100 ms more latency moved the closest approach about 0.1 m closer (0.401, 0.305, 0.205 m). R1

Determinism and what lockstep hides

The world uses a seeded std::mt19937 and converts its integers to noise with our own arithmetic (line 74). The C++ standard specifies the Mersenne Twister engine's algorithm and parameters, so its sequence is the same on every conforming implementation; the algorithms of the standard distributions (such as std::normal_distribution) are not specified, so two standard libraries may turn the same engine output into different numbers. D5 For a simulation that must replay identically on another machine or in a bug report, that difference matters. Lockstep coupling adds the other half of determinism: simulated time stops while the controller computes, so results do not depend on the host's speed. R8 The price is that lockstep cannot find timing bugs in the controller itself. A test that must find them has to run in real time, which is what HIL is for.

What PIL can and cannot tell you

PIL caught nothing in this build: both builds gave identical commands. That is a real result, not a wasted run: it says the controller's arithmetic and protocol handling did not change across instruction sets with these compilers and flags. Differences that PIL exists to catch include: a different long or pointer size on the target, different floating-point contraction into fused multiply-add (F6-04 met this for GPUs), uninitialised memory that happens to be zero on one platform, and endianness in a binary protocol. Our protocol is text and our long is 64 bits on both targets, so several of these could not occur. An emulator models the instruction set, not the board: memory timing, caches, interrupts from real devices and the real-time behaviour of the target's operating system are all absent. D4

Building a HIL rig (design notes)

A HIL rig for this robot would put the real robot computer on a bench, running its real image (F9-67 builds one; F9-70 covers its logs), with the motor driver's interface connected to a simulator computer instead of motors, and the range sensor replaced by the simulator producing readings with the measured latency and noise. Its design questions are: which interface is cut (messages on the robot's bus, or electrical signals at the connectors); how the simulator keeps real time and logs its own lateness; how both clocks are aligned for the logs; and how the rig fails safe if the simulator stops. The drone versions of these questions are worked in F10-34.

Not verified — check before relying on this

Robotics and drone toolchains (ROS 2 with a physics simulator, PX4 and ArduPilot SITL and HITL) have their own documented ways to run these tests; no such tool exists in this build, and no command line, parameter or message name of theirs is given here. Check the ROS 2 documentation and the PX4 Autopilot User Guide or the ArduPilot documentation for the release recorded in your dossier (and see F10-33, F10-34, F9-44). The statements about delay and phase lag (D3) and about the C++ standard's random-number specification (D5) are from those documents' titles only, pending verification at dossier gate G1.

How the hardware actually does it

In the PIL runs, the AArch64 controller is a real AArch64 executable: readelf reports class ELF64 and machine AArch64. R5 qemu-aarch64 translates its instructions into x86-64 instructions and passes its system calls (here: reading and writing the pipes) to the host's Linux kernel. D4 That is why it can share named pipes with an ordinary x86-64 program. On a real robot computer, the same reads and writes would go to the target's own kernel, its own scheduler and, in HIL, to a real bus or serial link with its own delays. Those delays are exactly the "latency" knob of the simulator, and on real hardware they are not a parameter you choose: they are a property you measure, with time stamps at both ends on one clock (F9-48). The field log of the forensic lab contains such stamps: the sensor's capture time and the controller's receive time.

Worked example

Task. The field log says the sensor's readings arrive 0.45 s after capture. Using only the latency sweep (R1), predict how close the robot came to the shelf, and the largest latency that still meets S1. Then check against the runs.

  1. Read the trend. From R1: 300 ms → 0.401 m, 400 ms → 0.305 m, 500 ms → 0.205 m. Each 100 ms costs about 0.1 m, matching "1 m/s × 0.1 s" from Layer 3. A line through these points is closest ≈ 0.70 m − L × (1 m/s) for L from 0.3 to 0.5 s.
  2. Predict the field. L = 0.45 s: 0.70 − 0.45 = 0.25 m. Below 0.35 m: S1 violated.
  3. Largest safe latency. 0.70 − L ≥ 0.35 gives L ≤ 0.35 s. The sweep agrees: 300 ms passes, 400 ms fails.
  4. Check. The field log's tape measure gives 253 mm, and the fixed controller's table gives 0.253 m for the old controller at 450 ms. R3 R4 The prediction was within a few millimetres.

The line is a fit to this model's runs, not a law of robots: it holds while the robot cruises at 1 m/s into the ramp. Its value is that it turns "latency is bad" into a number you can write into a requirement: "end-to-end data age at most 0.30 s, measured".

Where the analogy breaks


    

  • A rig's thermometer can be swapped for the real one; a simulator's sensor cannot. In the workshop, Tomás could bolt the real slow thermometer onto the rig. A simulator can only contain a model of the sensor, with parameters someone measured or guessed. The model's latency of 0.45 s in the forensic lab is a number; the real sensor's latency varies, and its distribution is what you must measure.
    • 

  • Software rigs run thousands of winters a day. A heating rig tests one scenario at a time in real time. A SIL scenario matrix runs 24 worlds in well under a second here (R1), so the economics are different: in simulation, breadth is cheap and you should use it.
    • 

  • The house does not change when the controller changes. A robot's behaviour changes the world it then senses (it approaches the shelf faster, so the readings change faster). Closed-loop effects like this are why a recorded sensor log cannot replace a closed-loop simulation: replaying yesterday's readings ignores today's commands.
    • 




Common mistakes and debugging


    

  • Symptom: simulation green, robot misbehaves. Cause: an effect missing from the model, often a delay. How to find it: compare a field log's time stamps (capture versus receive) with the simulator's parameters; make a fidelity table. Fix: model the measured effect, sweep it past the measured value, and fix the controller (the forensic lab).
    • 

  • Symptom: the closed-loop PIL run hangs. Cause: an answer left in an output buffer, or pipes opened in a different order on each side. How to find it: the timeout fires; run each side by hand with a terminal. Fix: flush after each message (Listing 3, line 22); one fixed open order (Listing 4, lines 36–37).
    • 

  • Symptom: a simulation run cannot be reproduced on a colleague's machine. Cause: an unseeded generator, a standard distribution whose algorithm differs between libraries, or wall-clock time inside the model. Fix: seed every generator and record the seed; convert engine output yourself (line 74); use simulated time only.
    • 

  • Symptom: PIL shows tiny numeric differences between targets. Cause: floating-point contraction or different library functions on the target. How to find it: diff the logs and find the first differing line. Fix: decide whether the difference matters for the requirement; compare with a tolerance justified by the numerics (F0-80) or fix the compiler flags for both builds.
    • 

  • Symptom: a HIL test passes on the bench and fails in the field. Cause: the rig's real-time simulator was itself late, or its clock differed from the robot's. Fix: make the simulator log its own lateness; align clocks before comparing logs.
    •

Forensic lab


Scenario: "Green CI, broken robot". The team's CI runs a simulation test of the robot on every commit, and it has been green for weeks. During the first warehouse trial, the robot stopped much closer to a shelf than allowed; Priya, the safety officer, measured the gap with a tape measure. The robot did not touch the shelf, but it broke requirement S1, and the trial was stopped. The team lead says "the controller passed CI, so the hardware must be faulty". You have the CI test, its log, and the robot's own log from the trial.

Summary


    

  • A simulation test is valid only for the effects it models; list them in a fidelity table.
    • 

  • A scenario matrix turns one pass into a map of where the controller is safe (24 worlds; safe up to 300 ms latency in this model, R1).
    • 

  • Latency in a feedback loop costs margin; here each 0.1 s at 1 m/s cost about 0.1 m (R1, worked example).
    • 

  • SIL tests logic and dynamics; PIL tests the target build and protocol (identical logs on x86-64 and emulated AArch64, R8); HIL adds real time and real interfaces; the field adds everything else.
    • 

  • Lockstep makes simulation reproducible and hides controller timing; real-time tests need HIL.
    • 

  • "Green CI, broken robot" is usually a missing effect in the model, found from time stamps, not from the controller code.

Forensic lab answer key


How the evidence was produced. ci_sim.cpp is the default world (latency 0, noise 0) from 3.0 m. field_log.cpp is the same simulator and controller with latency_s = 0.45, noise ±3 mm and seed 7; every second control tick is printed while the robot moves, plus the first tick after it stops, and the "tape measure" is the simulator's true final distance. Nothing was edited by hand. R2 R3


Observation. From t_rx = 0.50 s on, every line has stamp = t_rx − 0.45 s: the readings are 0.45 s old. The command first drops below 1000 mm/s at t_rx = 2.70 s, when the reading is 996 mm; but that reading was captured at 2.25 s, and the robot has driven about 0.45 m at 1000 mm/s since. The robot stopped with the tape measure at 253 mm, below the 350 mm of S1.


Hypotheses ruled out. Weak brakes: the wheel speed falls by about 200 mm/s every 0.1 s (1000 → 891 → 695 → 495 against commands 991 → 795 → 585 → 396), which is the 2 m/s² limit of the motor model: the motor does what it is told as fast as it can, and it is told late. Noise: consecutive readings change smoothly by about 100 mm per 0.1 s at 1 m/s, with only a few millimetres of scatter. Sensor offset: the stopped reading (447 mm at t_rx 3.25 s) was captured at 2.80 s while the robot was still moving; there is no steady difference between readings and true distance once the age is accounted for. Latency remains, and it is proven by the stamps.


Root cause. The CI simulation used the default latency_s = 0; the real sensor path delivers readings 0.45 s late. The controller, safe up to about 0.35 s of latency (R1, worked example), is unsafe at 0.45 s. Predicted closest approach 0.70 − 0.45 = 0.25 m; observed 253 mm.


Fix and verification. Controller: use the stamp; subtract the distance driven since the reading (Listing 1, line 40, compensate = true). CI: a scenario matrix that sweeps latency up to the measured value and requires a pass there. Listing 6 does both; the compensating controller meets the requirements at 0, 150, 300 and 450 ms (closest 0.471 m at 450 ms) and the program exits 0. It still fails at 600 ms (0.289 m): a margin probe that tells the team how much more latency the fix tolerates. R4






Prevention. A fidelity table in the test plan with "sensor latency: measured on the bench before the trial, value, method"; a requirement on end-to-end data age; the latency axis in the CI matrix; and the field-test checklist requiring the bench measurement before any trial.


Wrong answers and why. "The hardware is faulty": the brakes and sensor behave as modelled once the stamps are read. "Re-run CI": the simulation is deterministic; it will be green forever. "Lower the maximum speed": it would reduce the distance driven blind, but it hides the cause, and no test would then protect against a future increase in latency.
