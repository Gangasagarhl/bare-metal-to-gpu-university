Story hook

Next door to the data-centre building, the second building has a graphics wing. Kofi works there. On his first morning he counts the rows of helpers, as Amara taught him: 32. In the afternoon a different recipe card arrives, and the same helpers line up in rows of 64. Nobody moved a table. The building can arrange the same people both ways.

Kofi asks the head of the wing which length is better. "It depends on the card," she says. "When every helper does the same thing, long rows mean fewer row instructions to hand out. When the card says if your bowl is red, do this, otherwise do that, a long row is more likely to contain both colours, and then the whole row has to walk through both halves of the card." Kofi writes that down. Then he finds a card from the library that will not even let itself be printed for rows of 64 in this wing.

This chapter is about that graphics wing: RDNA GPUs, where a kernel can be compiled for wave32 or wave64, what the choice changes in the machine code, what it costs when lanes disagree, and what this build's HIP version allows.

What you will be able to do

  • Explain what wave32 and wave64 mean on RDNA targets, and which one the compiler of this build picks by default for gfx1030 and gfx1100.
  • Read the differences between the wave32 and wave64 versions of one kernel: vcc_lo versus vcc, s_and_saveexec_b32 versus _b64, the .wavefront_size metadata.
  • Compute with a counting model how the probability that a wave diverges grows with its width, and what that does to lane efficiency.
  • Recognise a data layout whose branch pattern is aligned to 32 lanes, so that it never diverges in wave32 and always diverges in wave64.
  • State what the HIP 5.7 headers do when asked for wave64 on an RDNA target, and where to check whether a newer HIP behaves differently.
Jargon box
RDNA
Simple words: AMD's family of graphics GPUs (the "graphics wing"), next to CDNA for data centres. Analogy: the graphics wing of the second building. Precise: AMD's GPU architecture line for graphics products; in the LLVM target names of this build, the gfx10 (for example gfx1030) and gfx11 (for example gfx1100) targets are RDNA targets; the generations are documented in the RDNA ISA reference guides. D4 D5
Wave32 / wave64
Simple words: compiling a kernel so that its waves have 32 lanes, or 64 lanes. Analogy: short rows or long rows of the same helpers. Precise: the wavefront size of a compiled kernel, fixed at compile time and recorded in the kernel metadata as .wavefront_size; RDNA targets support both, CDNA targets use 64. In this build's compiler, gfx1030 defaults to 32 and the option -mwavefrontsize64 selects 64 (R2). D4 R2
vcc_lo, exec_lo
Simple words: the low 32-bit halves of two mask registers, used by wave32 code. Analogy: the left half of a row's attendance sheet, all that a short row needs. Precise: VCC (vector condition code) and EXEC are 64-bit registers made of two 32-bit halves; wave32 code uses only vcc_lo and exec_lo, wave64 code uses the full vcc and exec (R2, R4). D4 R2
Workgroup Processor (WGP)
Simple words: on RDNA, a block made of two compute units that work together. Analogy: two neighbouring sections of the graphics wing sharing some equipment. Precise: the curriculum's vocabulary table (13.1) says that on RDNA, CUs pair into Workgroup Processors; what exactly is shared, and how the workgroup is placed on it, is to be read in the RDNA ISA guide (pending, D4). D4
Divergence probability
Simple words: the chance that the lanes of one wave disagree about a branch. Analogy: the chance that a row contains at least one red bowl. Precise: for lanes that take a rare side independently with probability p, a wave of w lanes runs the rare side with probability 1 − (1 − p)w; this is the model of Listing 1 (R1), an arithmetic fact about the model, not a hardware measurement.

The idea in pictures

Figure 1 shows the same 64 work-items running a branch whose condition alternates every 32 work-items (part 2 of Listing 1). Compiled for wave32, the 64 work-items form two waves; each wave agrees with itself, so each runs one side of the branch with all lanes on. Compiled for wave64, they form one wave that contains both kinds of lane, so it runs both sides, each time with half of the EXEC mask switched off.

Layer 1 — the kid explanation

In the graphics wing, the same helpers can stand in short rows of 32 or long rows of 64. Each row still moves together: one instruction, every helper in the row. Long rows need half as many instructions to be handed out for the same number of helpers. That is good when everybody does the same thing.

But a row has only one card in front of it. If some helpers must stir and others must chop, the row does the stirring first, with the choppers standing still, and then the chopping, with the stirrers standing still. A long row is more likely to contain both kinds of helper. So the long row wins when the work is uniform, and the short row wins when the work is mixed. The building lets each recipe choose.

Layer 2 — the student explanation

Who chooses the width, and when

The wavefront size is a property of the compiled kernel, not of the GPU at run time. F7-08 showed that the compiler fixes warpSize per target. For RDNA targets there is a second input: a compiler option. The w32_w64 step of the lab compiled one small kernel for gfx1030 twice: without options, the kernel metadata says .wavefront_size: 32; with -mwavefrontsize64 it says .wavefront_size: 64 (R2). R2 The RDNA ISA guides describe both modes as supported by the hardware (pending, D4); the CDNA targets of F7-08 compiled as wave64 by default in this build. D4

The width is decided once per kernel, so it must be the same in every place that depends on it: warpSize in device code, the host's prop.warpSize, the lane masks and the per-wave buffers. A program that mixes a wave64 kernel with host code that assumes the device's default width would compute wrong buffer sizes; F7-08's rule "ask, never assume" still holds, but on RDNA "the device" is not the whole answer: the compiled kernel decides. D1

What HIP 5.7 allows

The hip_w64 step asked hipcc to compile Listing 3 (an ordinary HIP program) for gfx1030 with -mwavefrontsize64. The compile stopped with an error that the HIP header itself raises: "HIP is not supported on the specified GPU ARCH with wavefront size 64" (R3). The line that raises it is in hip/hip_runtime.h of HIP 5.7, guarded by the condition __HIP_DEVICE_COMPILE__ && !__GFX8__ && !__GFX9__ && __AMDGCN_WAVEFRONT_SIZE == 64: wave64 is accepted for gfx8 and gfx9 targets (gfx90a is a gfx9 target) and refused for every other target. H1 R3 So in this build's HIP, RDNA kernels written with the HIP headers are wave32 kernels.

The wave64 build of the w32_w64 step worked because Listing 2 does not include the HIP headers at all: it uses compiler builtins (__builtin_amdgcn_workitem_id_x) and the __attribute__((global)) spelling, so that the compiler alone decides. That is a teaching device for reading machine code, not a way to write production HIP.

Not verified — check before relying on this

Wave64 HIP on RDNA in newer ROCm versions. The refusal above is a fact about HIP 5.7's header. Whether later HIP versions accept -mwavefrontsize64 for RDNA targets, and whether the ROCm documentation recommends either width for RDNA, could not be checked in this build. Check: the HIP Programming Guide (hardware implementation, warp size) and the ROCm compatibility matrix for your ROCm version (D1, D8); then repeat the hip_w64 step with your toolchain and record the result.

What divergence costs at each width

HW301 (F1-57) established the rule: a wave runs a side of a branch if at least one of its lanes needs it, and the lanes that do not need it are masked off but still occupy their slots. D2 Listing 1 turns the rule into arithmetic. If each lane needs a rare side of cost e independently with probability p, a wave of w lanes runs it with probability 1 − (1 − p)w. Every lane of that wave pays e, whatever it needed. Part 1 of the output gives, for a common side of 10 model instructions and a rare side of 100: at p = 0.01, a wave32 wave diverges 27.5 % of the time and a wave64 wave 47.4 %; lane efficiency (useful lane-slots over spent lane-slots) is 29.3 % in wave32 and 19.2 % in wave64 (R1).

The model also shows when width does not matter. At p = 0 nothing diverges. At p = 0.2 or 0.5 practically every wave of either width runs both sides, and both efficiencies are equal (27.3 % and 54.5 %, R1). The width matters most in between, where rare events are rare enough that a short wave often escapes them and a long wave seldom does.

Note

Two meanings of "kernel" and "thread". As in every chapter of this faculty: the kernel is the GPU function, not the operating-system kernel of F3; a work-item is not an operating-system thread (BR-03).

Layer 3 — the engineer's depth

In the analogy: the head of the wing can only hand out one card per row at a time, and the attendance sheet in front of each row has room for 64 names; a short row uses only its left half.

The two compiled versions side by side

The w32_w64 output contains the same kernel twice. The instruction sequence is identical in shape: one scalar load of n, the index computation (v_lshl_add_u32 v0, s6, 8, v0, that is workgroup_id × 256 + workitem_id), a compare, an EXEC-mask branch around the body, a load, the arithmetic, a store (R2). Four things differ, and all of them are about masks:

  1. The bounds check v_cmp_gt_i32_e32 writes its 1-bit-per-lane result into vcc_lo (wave32) or vcc (wave64). R2
  2. The branch into the body saves and narrows EXEC with s_and_saveexec_b32 s0, vcc_lo or s_and_saveexec_b64 s[0:1], vcc: the saved copy needs one scalar register or a pair. R2 D4
  3. The 64-bit address addition uses vcc_lo or vcc as its carry: v_add_co_u32 v0, vcc_lo, s0, v0. Even carries are per-lane bits, so their register follows the width. R2
  4. The inner if became a select, v_cndmask_b32_e64 v2, -v2, v3, vcc_lo: both results are computed and each lane picks one. The compiler chose not to branch at all, so this kernel has no divergence cost from the inner branch at either width. R2

The metadata lines confirm the rest: .vgpr_count: 4 and .sgpr_count: 9 in both builds (R2). In this small kernel the width changed no register count; F7-10 explains why it can matter for occupancy, because a wave64 wave holds each VGPR for 64 lanes.

A 64-bit ballot on a 32-lane wave

Listing 3 stores one __ballot per wave. In HIP 5.7, __ballot returns unsigned long long and is implemented as __builtin_amdgcn_uicmp(predicate, 0, ICMP_NE): a compare whose per-lane result bits form the mask. H1 The ballot_isa step compiled it for gfx90a and gfx1100 (R4):

  • gfx90a (wave64): v_cmp_lt_f32_e64 s[0:1], 0, v2 writes the 64-bit mask into a scalar register pair; s_bcnt1_i32_b64 s0, s[0:1] counts its bits; v_pk_mov_b32 moves both halves into VGPRs for the 8-byte store global_store_dwordx2. R4
  • gfx1100 (wave32): v_cmp_lt_f32_e64 s0, 0, v0 writes a 32-bit mask into one scalar register, and s_mov_b32 s1, 0 sets the upper half to zero. The count is still s_bcnt1_i32_b64 s4, s[0:1], and the store is still 8 bytes (global_store_b64). The program's 64-bit type survives; the upper 32 bits are always zero. R4

Three more gfx1100 details are visible. v_cmpx_eq_u32_e32 0, v3 compares and writes EXEC in one instruction, replacing gfx90a's compare plus s_and_saveexec_b64. v_dual_mov_b32 v5, s1 :: v_dual_mov_b32 v6, s4 encodes two moves in one instruction. And the kernel ends with s_sendmsg sendmsg(MSG_DEALLOC_VGPRS) before s_endpgm. R4 The run step also removed s_delay_alu lines, which the gfx1100 assembly contains, to keep the comparison readable; they are scheduling hints for the hardware. What each of these instructions does precisely is defined in the RDNA3 ISA guide (pending, D4). D4

Choosing a width: a decision procedure

  1. If the code is HIP and the toolchain is HIP 5.7, there is no choice on RDNA: wave32 (R3).
  2. Where both widths are available, compile both and compare the resource reports and the ISA (the w32_w64 method).
  3. Estimate divergence: find each data-dependent branch, estimate the probability that a lane takes the rare side, and use Listing 1's formula. Check for alignment patterns (part 2): a condition that changes every 32 work-items is free in wave32 and costs both sides in wave64.
  4. Measure on the GPU with the profiler of F7-14 (for example the ratio of active lanes per instruction, if your profiler version reports it), never with this model alone.

How the hardware actually does it

The EXEC register has 64 bits on every target in this chapter; wave32 code uses its low half, exec_lo, as the compiled code shows (s_mov_b32 s4, exec_lo in R4). R4 D4 A vector instruction operates on the lanes whose EXEC bit is set; scalar instructions run once per wave and manipulate masks, counters and addresses (F7-08, F7-10). D4 The width is recorded in the code object (.wavefront_size) so that the runtime and the hardware dispatch the kernel's waves accordingly (pending, D5). D5

Not verified — check before relying on this

How an RDNA SIMD executes a wave64 instruction (for example, in how many passes over how many lanes), how many cycles a wave32 versus a wave64 vector instruction occupies the SIMD, how many SIMDs an RDNA CU or WGP has, how workgroups are placed in a WGP, and how this affects LDS and caches: none of this could be read from a document in this build, and no measured timing exists. Check: the RDNA2 or RDNA3 ISA reference guide (introduction and program-state chapters) and the architecture whitepaper of the named product (D4, D6); measure with the profiler (F7-14).

Worked example

Task. A particle kernel runs a cheap update (10 model instructions) for every particle and an expensive collision handler (100 model instructions) for particles that hit a wall. One particle in a thousand hits a wall in each step, independently. (a) What share of waves runs the collision handler in wave32 and in wave64? (b) What lane efficiency does each width give? (c) The team sorts particles so that wall-hitting particles sit next to each other. Which width benefits more from the sorting?

  1. (a) p = 0.001. Wave32: 1 − 0.99932 = 1 − 0.9685 = 3.2 %. Wave64: 1 − 0.99964 = 1 − 0.9380 = 6.2 %. Listing 1 prints 3.2 % and 6.2 % (R1).
  2. (b) Useful work per lane: 10 + 100 × 0.001 = 10.1. Spent per lane, wave32: 10 + 100 × 0.0315 = 13.15, efficiency 10.1 / 13.15 = 76.8 %. Wave64: 10 + 100 × 0.0620 = 16.20, efficiency 10.1 / 16.20 = 62.3 %. Listing 1 prints 76.8 % and 62.3 % (R1).
  3. (c) Sorting turns independent lanes into groups. If the wall-hitters fill whole waves, only those waves run the handler, and the efficiency approaches 100 % at either width. The width that was further from 100 % gains more: wave64, which lost 37.7 points against wave32's 23.2. This is the reasoning of part 2 turned around: alignment can make divergence worse (when the pattern is 32-aligned and the wave is 64) or remove it (when the data are grouped to whole waves).

Where the analogy breaks


    

  • The helpers do not rearrange themselves during the day. The width is fixed when the kernel is compiled; a running kernel cannot switch from 32 to 64 (R2: the width is in the code object's metadata). R2
    • 

  • A long row is not two short rows standing side by side. A wave64 wave has one program counter and one 64-bit EXEC mask; two wave32 waves have two of each and can be at different places in the program (Figure 1). D4
    • 

  • "Walking through both halves of the card" is not always what happens. The compiler can turn a short if into a select (v_cndmask_b32) with no branch at all (R2); then both sides are computed by every lane regardless of the width.
    •

Forensic lab answer key


Observation. Width 32: 0 of 32 waves diverge; width 64: 16 of 16 waves diverge (R1). The two compiled versions differ only in mask registers and metadata (R2).


Hypotheses. (a) Against: R2 shows the same instructions in both widths; the branch around the body is present in both. (b) Not supported: the evidence contains nothing about memory, and the speed-up appears per lane in a branch-bound part. (c) Supported: the team's condition is 32-aligned, exactly part 2 of the model.


Root cause. In wave64, every wave contains one even and one odd tile, so every wave runs both classification paths with half its lanes masked; in wave32, each wave runs one path. Per lane, the CDNA version spent the cost of both sides; the RDNA version spent one.


Fix and verification. Make the tiles 64 pixels wide on CDNA, or reorder work so that the condition depends on (i / warpSize) % 2; then 0 of 16 waves diverge (answer 6). Verify with the profiler's lane-activity metric on the GPU (F7-14).


Prevention. A design note: "branch conditions must be aligned to warpSize, not to 32", and a unit test that runs Listing 1's counting on the real index pattern for both widths. How the evidence was produced: the Lab Engineer ran Listing 1 and the w32_w64 step; the team, the tiles and the workstation are a scenario.
