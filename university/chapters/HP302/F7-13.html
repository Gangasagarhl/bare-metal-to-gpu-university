Story hook

Recipe cards in the second building are written in the house language: short lines, one action each, with the counter or hand named in every line. "Fetch four jars from the pantry into hands 4 to 7." "Wait until the pantry jars have arrived." "Multiply hands 4 and 5 by hands 8 and 9, two at a time." Most cooks never read these cards; they write recipes in the common language and let the translator produce the house version.

Ravi reads them anyway. When a recipe is slow, the common-language version tells him what the cook wanted; the house version tells him what the helpers actually do. Today he is looking at a card for a dot product. The cook wrote a*b + c and expected a single "multiply-add" step; the house card has a multiply and a separate add. The cook used an atomic add at the end and expected one step; the house card has a small loop that tries, checks and tries again. Each surprise has a reason, and each reason can be changed.

This chapter teaches you to read AMD's house language for your own kernels: where the assembly comes from, how a code object is organised, how to read a kernel from its first scalar load to s_endpgm, how to annotate an inner loop line by line, and how to confirm a prediction by changing one thing.

What you will be able to do

  • Produce AMD assembly and code objects for any kernel without a GPU, and list the code objects inside a HIP executable.
  • Decode instruction names: prefix (s_, v_, ds_, global_, buffer_), operation, data type, encoding suffix (_e32, _e64), operands.
  • Read a kernel's prologue: kernel-argument loads from the kernarg pointer, the workgroup id in an SGPR, the work-item id in v0.
  • Annotate an inner loop line by line, identifying global loads and their width, LDS and cross-lane accesses, waits, the FMA instructions, the EXEC-mask loop control and any spills (curriculum E10).
  • Read the kernel descriptor and the metadata (register counts, LDS and scratch sizes, kernel-argument size, wave size) and relate them to F7-10's occupancy.
  • Predict the effect of a source or option change on the ISA, make it, and check it with an instruction census.
Jargon box
AMD ISA (GCN/CDNA/RDNA)
Simple words: the machine language of AMD GPUs, the instructions the hardware runs. Analogy: the house language of the second building's recipe cards. Precise: the instruction set documented per generation in AMD's ISA reference guides (for gfx90a, the MI200 / CDNA2 guide); the LLVM AMDGPU back end emits it as assembly text and as binary in a code object. D2 D5
Code object
Simple words: the file that holds a GPU's compiled kernels for one target. Analogy: the bound book of house-language cards for one building. Precise: an ELF file for the AMD GPU architecture (in this build: "ELF 64-bit LSB shared object, AMD GPU architecture version 1"), with one function symbol per kernel, one 64-byte .kd object per kernel (the kernel descriptor), and metadata in an ELF note; a HIP executable bundles one code object per --offload-arch target (R4, R7). D5 R4
Kernel descriptor
Simple words: a small block of settings the hardware reads before it starts a kernel. Analogy: the header card of a recipe: how many hands, how much table, where the first line is. Precise: a 64-byte structure (<kernel>.kd in R4) that the assembler builds from the .amdhsa_* directives: LDS and scratch sizes, kernel-argument size, user SGPR count, VGPR and SGPR allocation, accumulation offset, floating-point modes (R5). D5 R5
Kernarg segment
Simple words: the memory block that holds a kernel's arguments. Analogy: the order slip clipped to the recipe card. Precise: a buffer whose address the kernel receives in an SGPR pair; the kernel reads its arguments with scalar loads at fixed offsets; its size is .kernarg_segment_size (28 bytes for dot(), R4). D5
s_waitcnt
Simple words: the instruction where a wave waits for earlier memory operations to finish. Analogy: "wait until the pantry jars have arrived." Precise: waits until the counter of outstanding vector-memory operations (vmcnt) or of LDS, scalar-memory and message operations (lgkmcnt) falls to the given value; AMD code issues loads early and waits only before the first use (F1-60). D2
Encoding suffix (_e32, _e64)
Simple words: a tag that tells which of two binary forms an instruction uses. Analogy: a short card and a long card for the same step. Precise: the 32-bit and 64-bit encodings of vector instructions; in R4, v_mov_b32_e32 v2, 0 is 4 bytes and an instruction with a 32-bit literal such as s_and_b32 s6, s12, 0xffff is 8; the 64-bit form allows more operands, for example a compare result written to an SGPR pair instead of VCC (F7-09). R4 D2

Layer 1 — the kid explanation

You write a recipe in your own words. A translator turns it into very short lines that the helpers follow exactly. Reading those short lines is like reading the real instructions on the helpers' cards: you see every fetch from the pantry, every wait, every multiplication.

Sometimes the translator does something you did not expect. It might do two multiplications in one line, or turn one "add to the shared tally" into "try, check, try again". Reading the short lines is how an engineer finds out what the GPU is really asked to do, and then changes the recipe or the translator's settings on purpose.

Layer 2 — the student explanation

Getting the code

The lab used three commands, all without a GPU (R1, R4, R7). hipcc … --cuda-device-only -S dot.hip -o dot.s writes the device assembly for the --offload-arch target. hipcc … --cuda-device-only --no-gpu-bundle-output -c dot.hip -o dot.co writes the code object as an ELF file, which llvm-objdump -d disassembles and llvm-readelf -s / -n lists. A normal build with two --offload-arch options produces an executable whose bundle contains a host entry and one device entry per target; roc-obj-ls lists them (R7). R7 HP301 (F7-06) showed the bundle from the build side; the curriculum also names hipcc --save-temps, which keeps all intermediate files including the assembly. D1

Reading instruction names

An AMD instruction name is built from parts. Take v_add_co_u32_e32 v12, vcc, s0, v4 from R1: v_ = vector (per lane); add_co = add with carry-out; u32 = unsigned 32-bit; _e32 = the 32-bit encoding; operands: destination v12, carry-out vcc, sources s0 (a scalar, the same for all lanes) and v4. The prologue: where the arguments come from

dot(const float4* a, const float4* b, float* result, int n4) has 8 + 8 + 8 + 4 = 28 bytes of arguments, and the metadata says .kernarg_segment_size: 28 (R4). The first lines of R1 load them through the SGPR pair s[6:7]: s_load_dwordx4 s[0:3], s[6:7], 0x0 brings a and b (offsets 0 and 8), s_load_dwordx2 s[10:11], s[6:7], 0x10 brings result (offset 16), s_load_dword s9, s[6:7], 0x18 brings n4 (offset 24) (R1). R1 So s[6:7] is the kernarg pointer, and the arguments are laid out in order with natural alignment.

Two more loads use s[4:5]: offset 0x4 (s_load_dword s12, then masked to 16 bits with 0xffff and multiplied by s8) and offset 0xc (s_load_dword s8, added to i on every loop iteration). The code uses them as blockDim.x and as the grid-stride gridDim.x × blockDim.x; s8 before that is the workgroup id, and v0 on entry is threadIdx.x (R1). R1

Not verified — check before relying on this

That s[4:5] holds the address of the dispatch packet, that its offset 4 is the 16-bit workgroup size in X and offset 12 the grid size in X (in work-items), that s[0:3] before the first instruction held the private-segment buffer descriptor, and that s8 is the first system SGPR after 8 user SGPRs (.amdhsa_user_sgpr_count 8, R5): these readings are consistent with every use in R1 but were not read in a document in this build. Check: LLVM "User Guide for AMDGPU Backend", sections on the kernel descriptor, initial kernel execution state and the HSA dispatch packet (D5); the HSA Platform System Architecture specification for the packet layout (D11).

E10 summary for this loop. Global loads: two per iteration, 16 bytes each (dwordx4). LDS: none in the loop; six ds_bpermute_b32 after it for the wave sum (lines 51–86, F7-12). Synchronization: no barrier; two s_waitcnt per iteration. FMA: none; two packed multiplies and four adds. Spills: none (.vgpr_spill_count: 0, R4). R1 R4

Two details deserve attention. First, the loop is controlled by EXEC, not by a scalar counter: each lane has its own i, so lanes leave the loop at different iterations, and the wave loops until its last lane is done (F1-57's divergence, applied to a loop). Second, the register s[4:5], which held the dispatch-packet pointer in the prologue, is reused as the "done" mask once its two loads were issued (line 15, s_mov_b64 s[4:5], 0): register names in assembly are storage, not variables. R1

Predict, change, confirm

Milestone E10 asks for one predicted change. The lab made three, each from a question raised by the annotation:

  1. "Why no FMA?" Prediction: writing the arithmetic as a chain of fmaf calls (dotFma) gives four fused multiply-adds per iteration and fewer instructions. Result: v_fmac_f32_e32 v2, v4, v8 four times, no v_pk_mul and no v_add_f32 in the loop; the census counts 21 loop instructions against 23 (R2, R3). R2 R3 The two versions round differently: dotFma rounds once per multiply-add, dot once per multiply and once per add (MA302). D12
  2. "Will -ffp-contract=fast do the same?" Prediction: the compiler might contract a*b + c into FMAs. Result: no change in the loop (2 v_pk_mul_f32, 0 FMA, 4 v_add_f32, R6). With this compiler and these flags, the packed multiply was chosen before contraction could apply; the explicit fmaf is the reliable way. R6
  3. "Why is the atomic a loop?" The end of dot() (lines 95–103) is a loop around global_atomic_cmpswap … glc: load, add, compare-and-swap, retry while another wave changed the value. Prediction: -munsafe-fp-atomics replaces it with a hardware float add. Result: global_atomic_cmpswap 1 → 0, global_atomic_add_f32 0 → 1 (R6). R6
Not verified — check before relying on this

What "unsafe" means in -munsafe-fp-atomics. The option changed the instruction (R6), but what the hardware float atomic does differently from the compare-and-swap loop (for example with denormals or on particular memory types), and on which memory it is supported, were not read in a document in this build. Do not enable it without checking: HIP Programming Guide, section on atomics and the unsafe floating-point atomics option, and the CDNA2 ISA guide for global_atomic_add_f32 (D1, D2). The "profiler confirmation" part of E10 needs a GPU (F7-14).

The code object, the descriptor and the metadata

The code_object step shows the ELF view (R4). dot is a 524-byte FUNC symbol in section 7 and dot.kd a 64-byte OBJECT in section 6. The disassembly prints each instruction with its address and encoding: s_load_dword s12, s[4:5], 0x4 is 8 bytes (C0020302 00000004), v_mov_b32_e32 v2, 0 4 bytes (7E040280), s_and_b32 s6, s12, 0xffff 8 bytes because the literal 0xffff follows the instruction word. R4 The branch s_cbranch_execz 33 at address 0x1A40 targets dot+0xc8: 0x1A40 + 4 + 33 × 4 = 0x1AC8 = 0x1A00 + 0xC8, so the branch offset counts 4-byte words from the next instruction — arithmetic you can check on the listing.

The metadata gives the facts that F7-10's calculator needs: .vgpr_count: 16, .agpr_count: 0, .sgpr_count: 17, .group_segment_fixed_size: 0 (no LDS), .private_segment_fixed_size: 0 (no scratch), .max_flat_workgroup_size: 1024 (no launch bounds, so the 128-VGPR cap of F7-10 applies), .wavefront_size: 64 (R4). The kernel descriptor directives (R5) repeat some of them in the form the hardware reads: .amdhsa_next_free_vgpr 16, .amdhsa_accum_offset 16 (where AGPRs would start), .amdhsa_next_free_sgpr 13, .amdhsa_user_sgpr_count 8, .amdhsa_kernarg_size 28, .amdhsa_ieee_mode 1. R5

Not verified — check before relying on this

The metadata's .sgpr_count (17) is larger than the descriptor's .amdhsa_next_free_sgpr (13). The difference is presumably registers the hardware reserves in addition (such as VCC), but which ones, and how the descriptor's fields are encoded in the 64 bytes, was not read in a document in this build. Check: LLVM AMDGPU user guide, "Kernel Descriptor" and "Code Object Metadata" sections (D5).

A census for every kernel

Reading 100 lines by eye is possible; reading a 3,000-line kernel is not. Listing 2 counts instruction classes per kernel and per loop (a loop is a label that a later branch jumps back to). For dot() it reports 100 instructions, of which 58 are vector ALU, 6 LDS/cross-lane, 3 vector memory, 10 waits; the main loop has 23 (R3). Run it on the kernels of F7-10 and it finds the spills ("scratch (spill)" class); on HP401's GEMM it will find v_mfma. A census does not replace reading; it tells you where to read. R3

How the hardware actually does it

To start a kernel, the runtime writes a dispatch packet into a queue; the packet points at the kernel descriptor in the loaded code object and at the kernarg buffer. D5 D11 The hardware allocates the resources the descriptor asks for (VGPRs, SGPRs, LDS, scratch; F7-10, F7-11), initialises the requested SGPRs (user SGPRs such as the kernarg pointer, then system SGPRs such as the workgroup id) and VGPRs (the work-item ids), sets EXEC for the wave's active lanes, and starts fetching instructions at the kernel's entry. D5 Scalar instructions execute once per wave in the scalar unit; vector instructions in the SIMD for all lanes whose EXEC bit is set; memory instructions are issued and counted, and s_waitcnt stalls the wave until the counts fall (F1-60). D2 s_endpgm ends the wave and frees its resources. D2

Not verified — check before relying on this

The exact initial register state (which SGPRs and VGPRs are set, in which order, for which descriptor bits), the queue and packet formats, and the instruction issue rules (how many instructions of which types a CU issues per cycle) were not read in a document in this build. Check: D5 (initial kernel execution state), D11 (dispatch packet), D2 (instruction issue and dependency rules).

Worked example

Task. Using only R1, R4 and R5, answer: (a) how many bytes does one iteration of dot()'s loop load per wave, and per instruction of the loop? (b) What is the loop's ratio of floating-point operations to loaded bytes? (c) Which resource would limit occupancy, by F7-10's model?

  1. (a) Two global_load_dwordx4 per lane = 32 bytes per lane; per wave of 64 lanes, 2,048 bytes. The loop has 23 instructions (R3), so about 89 bytes per instruction issued.
  2. (b) Per lane and iteration: 4 multiplies and 4 adds = 8 floating-point operations for 32 bytes: 0.25 FLOP per byte. A kernel is memory-bound when its intensity lies below the machine's ridge point (SP302's roofline model); F7-14 shows how to compute the ridge point for the lab GPU from its documented peaks and place this kernel on it. D13
  3. (c) .vgpr_count: 16, no LDS, no scratch (R4): ⌊512 / 16⌋ = 32 → 8 waves per SIMD. Nothing limits it but the wave slots.

Where the analogy breaks


    

  • The house card is not a translation line by line. One source line became twelve instructions (the loop header and address arithmetic), and four multiplies became two (packed). Do not look for a one-to-one mapping (R1).
    • 

  • The card names storage, not ingredients. s[4:5] is first a pointer and later a lane mask (R1); a register is a place, not a variable.
    • 

  • Not every line is an action on food. s_waitcnt, EXEC updates and branches are control, not work; in dot()'s loop, 5 of 23 instructions are scalar control (one EXEC update, one branch, one scalar mask operation, two waits; R3).
    •

Forensic lab answer key


Observation. Loop: v_pk_mul_f32 ×2 and v_add_f32 ×4 replaced by v_fmac_f32 ×4; 23 → 21 instructions (R2, R3). Atomic: global_atomic_cmpswap loop replaced by one global_atomic_add_f32 (R6).


Hypotheses. (a) Supported: FMA rounds once per multiply-add instead of twice; results can differ in the last digits, deterministically. (b) Possible: both atomic forms add per-wave partial sums in the order the waves arrive, which is not fixed; the evidence shows the instruction changed, not that the order did. (c) The packed multiply rounds each product like a scalar multiply (D2); it is not a new source of difference.


Run-to-run variation. The atomic accumulation: floating-point addition is not associative, and the arrival order of waves can vary between runs with either atomic form. The FMA change gives a different but repeatable result.


On the GPU. Time four builds (each change alone and both) under the profiler (F7-14); for digits, run each build several times and compare with a high-precision CPU reference.


Prevention. Tests compare with a reference within a tolerance derived from the length of the sum and the precision (MA302), never bit-exact; reproducibility, if required, needs a fixed reduction order (for example per-wave results written to memory and summed in a second pass).
