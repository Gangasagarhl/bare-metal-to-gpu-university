Story hook

In the second building, every helper has two hands, and the hall manager has noticed something odd. A recipe card that asks each helper to hold eight things at once fills the hall with rows. A card that asks each helper to hold a hundred things leaves most of the hall empty, because each row needs so many hands that only a few rows fit at the counters. And a card that asks for two hundred things is worse than that: the helpers start putting bowls down on a shelf in the far pantry and walking back for them.

Wei, who writes recipe cards, wants to know the rule. How many rows fit, for a card that needs so many hands? What is on the row's shared notepad, which only needs one copy per row? And can she tell the building in advance "my workgroups are small", so that it lets each helper hold more?

This chapter answers Wei with the compiler's own reports. AMD GPUs have two kinds of registers: vector registers (VGPRs), one copy per lane, and scalar registers (SGPRs), one copy per wave. The number of VGPRs a kernel needs decides how many waves fit on a SIMD, its occupancy. You will build a calculator that reproduces every occupancy figure the compiler reported in this build, and use it to find why a kernel lost occupancy.

What you will be able to do

  • Distinguish VGPRs (per lane), SGPRs (per wave) and, on gfx90a, AGPRs (accumulation registers), and say which values the compiler puts in each.
  • Read the compiler's resource report (-Rpass-analysis=kernel-resource-usage): VGPRs, SGPRs, AGPRs, scratch size, spills, occupancy.
  • Compute occupancy in waves per SIMD from VGPR count and LDS size with this build's model of gfx90a, and name the limiting resource.
  • Explain why the default maximum workgroup size of 1,024 caps a gfx90a kernel at 128 VGPRs, and what __launch_bounds__ changes in HIP 5.7.
  • Recognise spills in AMD assembly (buffer_store_dword … Spill) and spills to AGPRs (v_accvgpr_write), and choose between spilling and losing occupancy.
  • Diagnose a VGPR-limited kernel from a resource report and its ISA, and fix it.
Jargon box
VGPR (vector general-purpose register)
Simple words: a register that holds one value for every lane of a wave. Analogy: one hand of every helper in the row. Precise: a 32-bit register of the vector register file with one copy per lane; v_ instructions read and write VGPRs; a kernel's VGPR count is fixed at compile time and reported as .vgpr_count and in the resource report. D2 D5 R1
SGPR (scalar general-purpose register)
Simple words: a register that holds one value for the whole wave. Analogy: the row's shared notepad. Precise: a 32-bit register of the scalar register file, one copy per wave; s_ instructions operate on SGPRs; values that are the same for every lane (kernel-argument pointers, uniform loop counters, data loaded with s_load) live there. D2
AGPR (accumulation register)
Simple words: on CDNA targets such as gfx90a, a second set of per-lane registers made for matrix instructions. Analogy: a tray each helper can also hold, meant for the matrix machine. Precise: accumulation VGPRs (a0, a1, …) used as operands of MFMA instructions and readable with v_accvgpr_read, writable with v_accvgpr_write; the compiler also uses them as spill space (R3). On gfx90a the compiler counts them together with VGPRs for occupancy (R2). D2 R2 R3
Occupancy (AMD)
Simple words: how many waves can be resident on one SIMD at the same time. Analogy: how many rows fit at one counter. Precise: the number of waves per SIMD that the scarcest resource allows: wave slots, VGPRs (allocated in granules), LDS per workgroup, and further limits; the compiler reports it as "Occupancy [waves/SIMD]". D2 R1
Spill (AMD)
Simple words: a value the compiler could not keep in a register, so it stores it in memory and loads it back. Analogy: a bowl put down on a shelf in the far pantry. Precise: the compiler stores the register to the wave's private scratch memory (in this build's gfx90a code, buffer_store_dword marked "Folded Spill") and reloads it ("Folded Reload"); the resource report gives the count ("VGPRs Spill") and the bytes per lane ("ScratchSize"). D5 R3
__launch_bounds__ (HIP)
Simple words: a promise you write on a kernel about the largest workgroup you will launch, and optionally how many waves you want per SIMD. Analogy: telling the building "my groups are small", so it can give each helper more hands. Precise: in HIP 5.7, __launch_bounds__(N) expands to __attribute__((amdgpu_flat_work_group_size(1, N))), and __launch_bounds__(N, M) adds amdgpu_waves_per_eu(M); the second argument therefore means "waves per execution unit", not CUDA's "minimum blocks per multiprocessor". H1 D1

The idea in pictures

Figure 1 shows the vector register file of one SIMD as the compiler of this build models it for gfx90a: a budget of 512 registers per lane, shared by the waves resident on that SIMD, allocated in granules of 8. A kernel that needs 64 registers lets 8 waves fit (the wave-slot limit); one that needs 128 lets 4 fit; one that needs 262 (256 VGPRs plus 6 AGPRs) leaves room for only 1. The SGPRs are drawn separately: one set per wave, not per lane.

Layer 1 — the kid explanation

Each helper has hands to hold things while cooking. The more things a recipe asks each helper to hold, the more hands each row needs. A counter has only so many hands' worth of space. So a recipe that needs many hands lets fewer rows work at the counter at once.

Some things are the same for every helper in a row, like the page number of the recipe. Nobody needs to hold that in their own hand: one notepad per row is enough. A clever cook writes the shared things on the notepad and keeps hands free for the things that differ between helpers.

When a recipe needs more hands than there are, helpers put things down on a far shelf and fetch them back later. That keeps more rows at the counter, but all the walking takes time. Choosing between "fewer rows" and "more walking" is the question of this chapter.

Layer 2 — the student explanation

Two register files

Every AMD instruction you have read so far starts with v_ or s_. A v_ instruction works on vector registers: v_add_u32 v0, s8, v0 adds, in every active lane, a scalar to that lane's own v0. An s_ instruction works on scalar registers once for the whole wave: s_mul_i32 s8, s8, s4 multiplies the workgroup id by the workgroup size (F7-09, R4 there). D2 The compiler decides, for each value, whether it can be the same in every lane ("uniform") and puts uniform values in SGPRs.

The taps_isa step shows this in Listing 3, a filter with 32 taps. Every work-item uses the same taps, so the compiler loaded them with two scalar loads, s_load_dwordx16 s[0:15], … and s_load_dwordx16 s[16:31], …: 32 floats, one copy per wave, in 32 SGPRs. Each work-item's input window is different, so it came with vector loads, global_load_dwordx4 v[24:27], …: 16 bytes per lane per instruction (R4). R4 A value in an SGPR costs one register per wave; the same value in a VGPR would cost one register per lane, that is, 64 copies on gfx90a.

The compiler's resource report

You do not need a GPU to learn a kernel's register use. With -Rpass-analysis=kernel-resource-usage, the compiler of this build prints one block of remarks per kernel: SGPRs, VGPRs, AGPRs, ScratchSize (bytes per lane), Occupancy (waves per SIMD), SGPRs Spill, VGPRs Spill and LDS Size (bytes per workgroup) (R1). R1 The same numbers are in the code object's metadata (.vgpr_count, .sgpr_count, F7-13) and in the profiler's kernel table on a GPU (F7-14; the exact columns depend on the profiler version, D7). D5 D7

Listing 2 creates register pressure on purpose: each work-item keeps K running values that all stay live across a loop. The resources step reports, for accum<K> with the default launch bounds: K = 8 needs 26 VGPRs and gets occupancy 8; K = 64 needs 68 and gets 7; K = 96 needs 110 and gets 4; from K = 128 on, the VGPR count stops at exactly 128 and the compiler starts to spill (5 spills at K = 128, 406 at K = 200, 487 at K = 256) (R1).

A calculator that agrees with the compiler

Listing 1 computes occupancy with three rules: (1) at most 8 waves per SIMD; (2) VGPRs are allocated in granules of 8 out of a budget of 512 per lane, so waves by VGPR = ⌊512 / roundUp(VGPRs, 8)⌋; (3) waves by LDS = (65,536 / LDS per workgroup) × (waves per workgroup) / 4 SIMDs. The result is the minimum. The occ_check step fed it the compiler's own VGPR and LDS numbers for all fourteen kernels of Listing 2: every prediction matches the compiler's figure (R2), and F7-11 adds seven more LDS cases that also match. R2

Layer 3 — the engineer's depth

In the analogy: the building must be sure that a whole group of rows fits at once before it lets any row of that group start, so the size of the biggest group you might send decides how many hands each helper may have.

Why 128 VGPRs: the default workgroup size

A workgroup must be resident on one CU in its entirety, because its waves can meet at a barrier (F7-08, F7-11). D2 When a kernel has no launch bounds, the compiler must allow the largest workgroup, 1,024 work-items (the metadata records .max_flat_workgroup_size: 1024, F7-13 R3). On gfx90a that is 1,024 / 64 = 16 waves, spread over 4 SIMDs: 4 waves per SIMD must fit at once. With the 512-register budget, each wave may use at most 512 / 4 = 128 VGPRs. That is exactly where accum<K> stopped (R1). The compiler does not choose a lower occupancy for a large kernel; it must keep the possibility of a 1,024-item workgroup, so it spills instead.

accumLB<K> differs only by __launch_bounds__(256). A workgroup of at most 256 work-items is 4 waves, one per SIMD, so a single wave may use the whole budget. The compiler then used 142 VGPRs at K = 128 (occupancy 3, no spill), 214 at K = 200 (occupancy 2), and 256 VGPRs plus 6 AGPRs at K = 256 (occupancy 1, no spill) (R1, R2). R1 In HIP 5.7, __launch_bounds__(256) is amdgpu_flat_work_group_size(1, 256) (H1): it is a promise. Launching that kernel with 512 work-items breaks the promise; what happens then must be checked in the HIP documentation (D1). H1

What a spill looks like

The spill_isa step counts the evidence in the assembly (R3):

  • accum<128>: 5 stores marked "Spill" and 13 loads marked "Reload", for example buffer_store_dword v0, off, s[12:15], 0 offset:12 ; 4-byte Folded Spill. The four SGPRs s[12:15] hold the descriptor of the wave's scratch buffer; offset:12 is the slot in each lane's private area. The report says ScratchSize 24 bytes per lane. R3 R1
  • accum<256>: 487 spill stores and 491 reloads, 976 bytes of scratch per lane (R1, R3). Scratch is private memory in device memory behind the caches, so every reload that misses is a trip to the far pantry. D2
  • accumLB<256>: no spill stores, but 2 v_accvgpr_write and 6 v_accvgpr_read: the compiler parked values in AGPRs (v_accvgpr_write_b32 a0, v6) instead of memory (R3). On gfx90a, AGPRs that a kernel uses count against the same budget (262 total, R2).

Spill or lose occupancy?

There is no rule that higher occupancy is faster. HW301 (F1-60) showed that latency is hidden by enough independent work in flight, from more waves or from more independent instructions per wave. D9 A kernel with occupancy 2 and no spills may beat the same kernel with occupancy 4 and 406 spills, or it may not. The compiler reports cannot decide this; a measurement can (F7-14). What the reports do tell you is the shape of the choice: accum<200> (occupancy 4, 812 bytes of scratch per lane) against accumLB<200> (occupancy 2, no scratch).

The second argument of __launch_bounds__ lets you push the compiler the other way. In HIP 5.7 it becomes amdgpu_waves_per_eu(M) (H1). The forensic_fix step compiled Listing 3's 32-output filter with M = 6 and M = 8: with 6 the compiler fitted the kernel into 80 VGPRs (occupancy 6, no spill); with 8 it used 64 VGPRs and spilled 22 registers into 92 bytes of scratch per lane (R5). R5 Asking for occupancy you cannot afford buys it with spills.

Watch out

The second argument means something else in CUDA. In CUDA, __launch_bounds__(maxThreads, minBlocks) names a minimum number of resident blocks per multiprocessor (D10). HIP 5.7 maps the same position to amdgpu_waves_per_eu, a number of waves per SIMD (H1). A hipified kernel with __launch_bounds__(256, 2) asks AMD for 2 waves per SIMD, not 2 workgroups per CU. Recompute the value for AMD rather than copying it. H1 D10

SGPRs and occupancy

Every kernel in this chapter's reports used between 16 and 64 SGPRs (R1, R5, R7), and none of their occupancy figures needed an SGPR rule to be reproduced (R2; the forensic kernels by the same arithmetic in the answer key). SGPRs are also allocated per wave and have a per-SIMD budget; on some targets they can limit occupancy. D2 This chapter's calculator ignores them; that is a known gap, listed in the unverified box above.

How the hardware actually does it

When a workgroup is dispatched, the hardware allocates for each of its waves a block of VGPRs in the register file of the SIMD that receives the wave, a block of SGPRs, and, if the kernel needs it, LDS for the workgroup and scratch space in memory. D2 The sizes come from the kernel descriptor that the compiler wrote into the code object (.amdhsa_next_free_vgpr, .amdhsa_next_free_sgpr, .amdhsa_accum_offset, F7-13). D5 A wave whose registers cannot be allocated waits until a resident wave finishes; nothing is swapped out. Each register stays with its wave from its first instruction to s_endpgm, which is why switching between resident waves costs nothing (F1-60). D9

Not verified — check before relying on this

The size of the register file of a gfx90a SIMD in bytes, how AGPRs and VGPRs share it, the SGPR budget per SIMD, whether allocation granules differ between VGPRs and AGPRs, and how many cycles a scratch access takes were not read in a document in this build; Figure 1 and Listing 1 use the compiler's model. Check: CDNA2 ISA guide, chapters on the register files and on scratch (private) memory (D2); LLVM AMDGPU user guide, sections on the kernel descriptor and on register allocation (D5).

Worked example

Task. Before writing code, a team plans six kernels for gfx90a, all with workgroups of 256 (four waves): A uses about 24 VGPRs; B 64; C 65; D 100; E 40 VGPRs and a 16 KiB LDS tile; F 40 VGPRs and a 24 KiB tile. Predict each occupancy and its limiter.

  1. A: roundUp(24, 8) = 24; 512 / 24 = 21.3 → capped at 8 wave slots. Limiter: wave slots.
  2. B: 64 → 512 / 64 = 8. Still 8: exactly at the edge.
  3. C: 65 → rounded to 72; 512 / 72 = 7.1 → 7. One register more than B costs one wave per SIMD.
  4. D: 100 → 104; 512 / 104 = 4.9 → 4. Limiter: VGPRs.
  5. E: VGPRs allow 8; LDS: 65,536 / 16,384 = 4 workgroups per CU × 4 waves = 16 waves / 4 SIMDs = 4. Limiter: LDS.
  6. F: 65,536 / 24,576 = 2.67 → 2 workgroups × 4 waves / 4 SIMDs = 2. Limiter: LDS.

Listing 1 prints the same six results (R6). The lesson of B and C: occupancy falls in steps. Read the step edges for your target (here, by the same formula, at most 64, 72, 80, 96, 128, 168 and 256 registers give 8, 7, 6, 5, 4, 3 and 2 waves) and aim slightly below one.

Where the analogy breaks


    

  • Hands are not handed out one at a time. Registers are allocated in granules (8 in this build's model): a 65th register costs as much as 72 (worked example, R6).
    • 

  • The notepad is not free either. SGPRs are a per-wave resource with their own budget; a "row notepad" in the analogy sounds unlimited, but it is not (D2).
    • 

  • The far shelf is not always far. A spill to an AGPR (v_accvgpr_write, R3) stays in the register file; only spills to scratch memory are trips to the pantry. And a scratch reload may be served by a cache.
    • 

  • The building does not check the size of the groups when they arrive. The register budget is fixed when the kernel is compiled, from the launch bounds; a launch that breaks the promise is not rescued by a re-allocation (D1).
    •

Summary


    

  • VGPRs hold one value per lane; SGPRs one value per wave; uniform data (kernel arguments, shared taps) goes to SGPRs via s_load.
    • 

  • gfx90a also has AGPRs; the compiler counts them with VGPRs for occupancy and can spill into them.
    • 

  • The compiler's resource report gives VGPRs, SGPRs, scratch, spills and occupancy without a GPU.
    • 

  • This build's gfx90a model: occupancy = min(8, ⌊512 / roundUp(VGPRs, 8)⌋, LDS limit); it matched all compiler figures.
    • 

  • Default bounds (1,024 work-items) cap gfx90a kernels at 128 VGPRs; __launch_bounds__(256) lifts the cap and lowers occupancy.
    • 

  • In HIP 5.7, __launch_bounds__'s second argument is waves per SIMD; forcing too many waves buys occupancy with spills.
    •

Answers to Check yourself


    

  1. (a) SGPR: a kernel argument is the same for every lane (in R4 the pointers arrive in s[16:19] and s[20:21]). (b) VGPR: each lane loads its own element. (c) SGPR: blockIdx.x and blockDim.x are the same for the whole wave (s_mul_i32 s8, s8, s4 in F7-09's R4). (d) SGPR, if t is a uniform loop counter: R4 shows the taps loaded with s_load_dwordx16. A common wrong answer is "every variable of a kernel is per lane": that is the source-level view, not the compiler's.

Forensic lab answer key


Observation. fir<16>: 62 VGPRs, 48 SGPRs, no scratch, occupancy 8. fir<32>: 84 VGPRs, 60 SGPRs, no scratch, occupancy 5. Instructions 488 → 896; multiply-adds 231 → 541; vector loads 12 → 16; scalar loads 6 in both (R7).


Hypotheses. (a) Ruled out: ScratchSize 0 and VGPRs Spill 0 in both. (b) Not needed: the calculator reproduces occupancy 5 from VGPRs alone (roundUp(84, 8) = 88; 512 / 88 = 5.8 → 5), and the SGPR increase (48 → 60) follows from the extra address and tap registers. (c) Confirmed: 62 is below the 64 edge (8 waves); 84 is above the 80 edge (6 waves).


Root cause. win[OUT + TAPS − 1] and acc[OUT] are fully unrolled per-lane arrays: each element is a VGPR. Doubling OUT grows the window from 47 to 63 values and the sums from 16 to 32. The taps stay in SGPRs because they are uniform, which is why they did not grow the VGPR count.


Fix and verification. Fix 1: return to OUT = 16 (62 VGPRs, occupancy 8). Fix 2: keep OUT = 32 and add __launch_bounds__(256, 6): the forensic_fix step gives 80 VGPRs, occupancy 6, no spill (R5). Asking for 8 instead gives 64 VGPRs but 22 spills and 92 bytes of scratch per lane (R5): a worse trade. A third option, more structural: slide the window through LDS or registers so that fewer values are live at once. Which fix is fastest must be measured on the GPU (F7-14); the compiler report only predicts occupancy and spills.


Prevention. A CI step that runs the resource report for every kernel and fails when occupancy drops or ScratchSize becomes non-zero compared with a stored baseline. How the evidence was produced: the Lab Engineer compiled Listing 3 for gfx90a and ran the census in run.sh; the team, the slowdown and the profiler table are a scenario, because no GPU was available.
