Story hook

A row of 64 helpers is filling jars. Only some helpers have something worth keeping, and the keepers must put their jars on a shelf in order, with no gaps. Nobody may walk to the table; the row can only pass things along the row and raise hands.

Ana, the row leader, has a trick. "Everyone who has a jar to keep, raise your hand." She writes down who raised a hand: one tick per helper, 64 ticks in a long line. Each keeper then counts the raised hands to their left: that count is their place on the shelf. It works perfectly, until a new leader copies the trick onto a notepad with room for only 32 ticks. The 32 helpers on the right still count "the hands to my left", but on a sheet that ends at helper 31; they all get the same number, put their jars in the same place, and all but one jar are lost.

This chapter is about passing values along a wave and raising hands in it: shuffles, ballots, lane masks and population counts, why on AMD wave64 every mask is 64 bits, and what the hardware really does when you call __shfl_down.

What you will be able to do

  • Use HIP's cross-lane functions (__shfl, __shfl_down, __shfl_xor, __ballot, __popcll, __lane_id) in code that works for any warpSize.
  • Simulate a wave in lock step to predict the result of a shuffle reduction, a butterfly and a ballot-based compaction.
  • Explain how HIP 5.7 implements shuffles on AMD (ds_bpermute_b32 with a byte address) and ballots (a vector compare into a 64-bit scalar register pair).
  • Find a 32-bit mask truncation with a compiler warning, and predict exactly which lanes it breaks.
  • Count cross-lane instructions in the ISA for wave64 and wave32 and relate the count to log2(warpSize).
Jargon box
Shuffle (__shfl family)
Simple words: each lane reads a value from another lane of the same wave, without going through memory the program can see. Analogy: passing a bowl a fixed number of places along the row. Precise: in HIP 5.7, __shfl(var, srcLane, width), __shfl_down(var, delta, width), __shfl_up and __shfl_xor(var, laneMask, width), with width defaulting to warpSize; on AMD they are implemented with __builtin_amdgcn_ds_bpermute(index << 2, var); a lane whose source would fall outside its width-sized segment gets its own value back. H1 D1
Ballot
Simple words: every lane answers yes or no, and the wave gets one number whose bits are the answers. Analogy: raising hands; the leader writes one tick per helper. Precise: HIP 5.7's __ballot(predicate) returns unsigned long long, bit l set if lane l is active and its predicate is non-zero; it is __builtin_amdgcn_uicmp(predicate, 0, ICMP_NE), a vector compare whose per-lane results form the mask. H1 D2
Lane mask
Simple words: a number with one bit per lane, saying which lanes are meant. Analogy: the line of ticks, one per helper. Precise: a bit set indexed by lane; on wave64 it needs 64 bits (unsigned long long or uint64_t); EXEC, VCC and ballot results are lane masks; HIP 5.7 provides __lanemask_lt(), __lanemask_gt() and __lanemask_eq() returning uint64_t. H1
Population count (__popcll)
Simple words: how many bits of a number are 1. Analogy: counting the raised hands. Precise: HIP 5.7's __popcll(unsigned long long) is __builtin_popcountll; __popc(unsigned int) counts 32 bits only. In this build's gfx90a code it became s_bcnt1_i32_b64 on a scalar mask and v_bcnt_u32_b32 (twice) on a per-lane mask (R3). H1 R3
Stream compaction (wave-level)
Simple words: packing the lanes that keep a value into consecutive places, with no gaps. Analogy: keepers putting jars on the shelf in order. Precise: each keeping lane writes to slot = popcount(ballot & lanemask_lt), the number of keeping lanes below it; the count of kept values is popcount(ballot). R1
ds_bpermute_b32
Simple words: the AMD instruction that lets each lane fetch a 32-bit value from any lane of its wave. Analogy: each helper names the helper whose bowl they want, and the table's machinery hands the bowls over. Precise: a "backward permute" instruction of the LDS hardware that takes a per-lane byte address (lane index × 4) and returns the source lane's value, without allocating LDS memory; HIP 5.7 builds every __shfl variant on it (H1, R3). H1 D2

The idea in pictures

Figure 1 follows a ballot-based compaction through one 64-lane wave, with the predicate "lane % 3 == 0" of Listing 1. The ballot is one 64-bit mask, 0x9249249249249249, with 22 bits set. Lane 36 keeps its value; it masks the ballot with "all lanes below me" and counts 12 bits: its slot is 12. If the mask had been stored in 32 bits, lane 36 would count only the 11 bits of lanes 0–31 and get slot 11, like every keeping lane from 33 up.

Layer 1 — the kid explanation

Helpers in a row can do two things without walking to the table. They can pass a bowl a fixed number of places along the row, all at the same moment. And they can raise hands, so that the leader writes one tick per helper on a long line of paper.

Passing bowls lets a row add up all its numbers quickly: pass half-way along and add, then a quarter, then an eighth, until the first helper holds the total. Raising hands lets every helper find out how many others said yes, and how many of them stand to their left. For a row of 64 helpers, the line of ticks must have 64 places. A sheet with 32 places forgets half the row.

Layer 2 — the student explanation

Shuffles

A shuffle reads a register of another lane in the same wave. HIP 5.7 offers four forms, each with an optional width that defaults to warpSize: __shfl (from a given lane), __shfl_up and __shfl_down (from delta lanes below or above) and __shfl_xor (from lane l XOR mask). H1 The AMD side of HIP 5.7 has no _sync variants and no member mask; the NVIDIA side of the same installation defines __shfl_down(...) as __shfl_down_sync(0xffffffff, ...), a full 32-lane mask (nvidia_hip_runtime_api.h). H1 HP301 (F7-07) showed what hipify does with CUDA's _sync shuffles. D1 One detail of the HIP 5.7 code matters for algorithms: in __shfl_down, a lane whose source self + delta lies outside its width-sized segment receives its own value back. H1 Listing 1's shflDown models exactly that rule.

The tree reduction of F7-08 uses __shfl_down with d = warpSize / 2, …, 1: after log2(warpSize) steps lane 0 holds the total. Listing 1 shows the result for 1, 2, …, 64: 2,080 with offsets from 32, and 528 with offsets copied from 32-lane code (R1). The butterfly with __shfl_xor and masks 32, 16, …, 1 gives every lane the total (2,080 in lanes 0, 37 and 63, R1), which saves a broadcast when all lanes need the result.

Ballots, masks and counts

A ballot returns one bit per lane. In HIP 5.7 its type is unsigned long long on every target (F7-09 showed the upper half is zero on wave32). H1 Combined with a mask of "lanes below me" and a population count, it gives each lane its rank among the lanes that said yes. Listing 2's compaction does exactly this: keep = __ballot(in[i] > 0), below = keep & ((1ull << lane) - 1ull), slot = __popcll(below). HIP 5.7 also offers __lanemask_lt(), which returns the same "lanes below me" mask intersected with the active lanes. H1

Every type in this chain must be 64 bits wide on wave64: the variable that holds the ballot, the constant 1ull (a plain 1 << lane is an int shift, undefined for lane ≥ 32), and the count (__popcll, not __popc). Listing 1 prints what happens when only the variable is wrong: the 64-bit mask 0x9249249249249249 has 22 bits set; kept in 32 bits it becomes 0x49249249 with 11 (R1). The compaction slots of lanes 36, 39, 42 and 45 become 11, 11, 11, 11 instead of 12, 13, 14, 15 (R1).

Layer 3 — the engineer's depth

In the analogy: the row does not really pass bowls hand to hand; each helper writes the number of the helper whose bowl they want, and the table's machinery delivers all bowls at once.

What __shfl_down becomes

HIP 5.7 defines __shfl_down(int var, unsigned int lane_delta, int width) as: self = __lane_id(); index = self + lane_delta; if (self & (width - 1)) + lane_delta >= width then index = self; return __builtin_amdgcn_ds_bpermute(index << 2, var). H1 The ops_isa step shows the compiled form of Listing 2's waveSum on gfx90a (R2):

  • v_mbcnt_lo_u32_b32 and v_mbcnt_hi_u32_b32: the lane id (F7-08).
  • v_and_b32_e32 v0, 63, v1: self & (width − 1) with width 64.
  • v_cmp_gt_u32_e32 vcc, 32, v0, v_cndmask_b32_e64 v3, 0, 1, vcc, v_lshlrev_b32_e32 v3, 5, v3: "is my source inside the wave? then add 32, else add 0", without a branch.
  • v_add_lshl_u32 v3, v3, v1, 2: (delta + self) × 4, the byte address.
  • ds_bpermute_b32 v3, v3, v2, then s_waitcnt lgkmcnt(0) and v_add_u32: fetch, wait, add. R2

The pattern repeats with 48, 56, 60, 62 as the comparison limit (that is, 64 − delta for delta = 16, 8, 4, 2) and finally v_cmp_ne_u32_e32 vcc, 63, v0 with v_addc_co_u32, which adds the carry bit as the +1 for delta = 1 (R2). The compiler interleaves the address computation of the next step with the wait of the current one. R2

The ops_count step counts the cross-lane instructions of the same kernel for both widths: 6 ds_bpermute_b32 on gfx90a and 5 on gfx1100, that is log2(64) and log2(32) steps; both mbcnt halves on wave64, only the low one on wave32; s_and_saveexec_b64 against _b32 (R3). R3 Because __shfl_down goes through ds_bpermute, a shuffle reduction uses the LDS hardware and waits on lgkmcnt like an LDS access (F7-11), even though no LDS memory is allocated. D2

What __ballot becomes

In R2 there is no instruction called "ballot". The compare v_cmp_lt_i32_e32 vcc, 0, v2 (in[i] > 0) writes its 64 result bits into VCC, and the rest of the code uses VCC as the ballot (R2). R2 The per-wave count __popcll(keep) is one scalar instruction, s_bcnt1_i32_b64 s0, vcc. The per-lane count __popcll(below) is computed in VGPRs, because below differs per lane: v_lshlrev_b64 v[6:7], v1, -1 builds the "lane and above" mask, two v_not_b32 invert it, two v_and_b32 with vcc_lo and vcc_hi apply the ballot, and two v_bcnt_u32_b32 count the halves and add them (R2). The 64-bit mask costs two 32-bit vector instructions per step on gfx90a.

Other cross-lane mechanisms

The AMD ISA has further ways to move data between lanes, which the compiler may use for other code or which libraries use explicitly: reading one lane's value into a scalar register, modifiers that let a vector instruction take an operand from a neighbouring lane within a row of lanes, and ds_swizzle. None of them appeared in this chapter's kernels. D2

How the hardware actually does it

Each lane's registers live in the VGPR file of the wave's SIMD (F7-10). A lane cannot address another lane's VGPR in an ordinary vector instruction; data crosses lanes through dedicated paths: the LDS crossbar for ds_bpermute and ds_permute, the scalar unit for values made uniform, and operand-routing modifiers. D2 A ballot needs no crossing at all: a vector compare already produces one bit per lane, and the hardware writes the bits into a scalar register pair (VCC or an SGPR pair) that the scalar unit can test and count. D2 R2 Inactive lanes (EXEC bit 0) contribute 0 to a compare's result, which is why __lanemask_lt() in HIP 5.7 ANDs with __ballot64(1), the mask of active lanes. H1

Not verified — check before relying on this

Whether inactive lanes really produce 0 bits in a VOPC compare result on gfx90a, what ds_bpermute_b32 returns for a source lane that is inactive, and its latency and throughput compared with an LDS read, were not read in a document in this build. Check: CDNA2 ISA guide, VOPC and LDS chapters (D2). Until then, write code that does not depend on values from inactive lanes.

Worked example

Task. A wave64 holds the values l + 1 in lane l (Listing 1). (a) After the first step of a __shfl_down reduction with d = 32, what do lanes 0, 31, 32 and 63 hold? (b) After all six steps, what does lane 0 hold? (c) Why does the second half of the wave hold "garbage", and does it matter? (d) With the predicate lane % 3 == 0, which slot does lane 63 get, and how many values does the wave keep?

  1. (a) Lane l < 32 reads lane l + 32 and adds: lane 0 holds 1 + 33 = 34; lane 31 holds 32 + 64 = 96. Lanes 32–63 have no source inside the wave and get their own value back (H1), so they double: lane 32 holds 33 + 33 = 66, lane 63 holds 128.
  2. (b) The steps fold 32, 16, 8, 4, 2, 1 lanes; lane 0 ends with the sum of all 64 values, 64 × 65 / 2 = 2,080 (R1).
  3. (c) Lanes whose sources were out of range doubled their own values, and lanes above 0 accumulated partial sums of different subsets. Only lane 0's result is defined as the total; the code must read it from lane 0 (Listing 2 line 29) or use the butterfly, in which every lane ends with 2,080 (R1).
  4. (d) Keeping lanes are 0, 3, …, 63: 22 of them (popcount 22, R1). Lane 63 has 21 keeping lanes below it: slot 21. The wave keeps 22 values in slots 0–21.

Where the analogy breaks


    

  • Bowls are not passed one place at a time. A shuffle by 32 lanes costs the same single ds_bpermute_b32 as a shuffle by 1 (R2); the "distance" along the row is free.
    • 

  • A helper who has nobody to take from does not end up empty-handed. In HIP 5.7 an out-of-range shuffle returns the lane's own value (H1), which is why the upper lanes double their values in the worked example.
    • 

  • Raising hands is not a separate event. The ballot is the side effect of a compare that the code needed anyway (VCC in R2); there is no extra "vote" instruction.
    •

Summary


    

  • HIP 5.7 shuffles (__shfl, _up, _down, _xor) take a width defaulting to warpSize; out-of-range lanes get their own value.
    • 

  • On AMD they compile to ds_bpermute_b32 with a byte address; a full reduction needs log2(warpSize) of them.
    • 

  • __ballot returns 64 bits; it is a compare's VCC; __popcll counts it (s_bcnt1_i32_b64).
    • 

  • Compaction: slot = __popcll(ballot & lanemask_lt); every type in the chain must be 64-bit.
    • 

  • A 32-bit ballot variable compiles silently with -Wall -Wextra; -Wshorten-64-to-32 catches it.

Forensic lab answer key


Observation. With the 32-bit mask, lanes 33, 36, 39, 42, 45 (and all keeping lanes above) get slot 11 instead of 11, 12, 13, 14, 15, …; the count is 11 instead of 22 (R1).


Hypotheses. (a) Against: the error is deterministic and appears in a host simulation with no memory race at all. (b) For: the 32-bit lines reproduce both symptoms, and the build with -Wshorten-64-to-32 points at a 64-to-32 conversion of __ballot (R5). (c) Against: a wrong shuffle offset changes sums, not slots or counts; the reduction lines are not involved.


Root cause. unsigned int mask = __ballot(…) (Listing 3, line 8): HIP's ballot is 64-bit on wave64, the variable 32-bit. "About half": the keeping lanes are spread evenly over the wave, so the upper half's are lost from the count; the colliding writes to slot 11 explain the "neighbour's value" symptom (the last writer wins).


Fix and verification. unsigned long long (or uint64_t) for the mask, 1ull in the shift, __popcll for the counts. The simulator's "64-bit mask" slot line and "popcount 22" are the expected behaviour; on a GPU, compare against a CPU compaction.


Prevention. Build: -Wshorten-64-to-32 -Werror for all device code (R4 shows the default warnings are silent). Testing: run wave-level unit tests compiled for a wave64 target and in a host simulator such as Listing 1, with predicates that set bits in both halves. How the evidence was produced: the Lab Engineer ran Listing 1 and compiled Listing 3 twice; the particle filter is a scenario.
