Story hook

The second building has three kinds of observers. The first stands at the door with a clipboard and writes down when each order started and finished, and how many times each recipe was cooked. The second sits next to one table for one recipe and counts everything: jars fetched, drawers opened, rows waiting, hands idle. The third films the whole street: the head chef in the restaurant across the road, the order runners, the kitchen hall, all on one timeline.

Kwame's dinner service is slow, and he wants to call the second observer straight away to count the jars. His mentor stops him. "First ask the one with the film. If the hall stands empty half the evening because the orders arrive one by one, counting jars inside the hall will not help you." Kwame watches the film. The hall is busy for a moment, then idle while the head chef waits for each dish before writing the next order. The fix is in the restaurant, not in the hall.

This chapter is about AMD's three observers: rocprofv3 (traces and counters), ROCm Compute Profiler (per-kernel analysis) and ROCm Systems Profiler (the whole-program timeline). This build had no GPU and none of these tools installed, so the chapter is honest about that: it teaches the measurement protocol, the arithmetic every profiler view is built on, the static facts you can get without a GPU, and how to read a timeline, with models whose numbers are labelled invented. Every tool command is in a box that says it was not run here.

What you will be able to do

  • Choose the right observer for a question: timeline (Systems Profiler), kernel list and counters (rocprofv3), per-kernel analysis and roofline (Compute Profiler).
  • Time a kernel correctly with HIP events, following the curriculum's measurement protocol (warm-up, median of at least 20 runs).
  • Compute derived metrics from raw totals: achieved bandwidth, FLOP/s, arithmetic intensity, the roofline bound and the percentage of it.
  • Read a kernel timeline: GPU busy share, gaps, launch-bound sequences, and their host-side causes.
  • Combine static facts from the compiler (registers, LDS, scratch, occupancy) with measured ones to explain a gap, as every performance milestone requires.
  • Complete the AMD hardware passport and tuning notes for the lab GPU (course project).
Jargon box
rocprofv3
Simple words: AMD's command-line profiler that records which kernels and API calls ran, for how long, and selected hardware counters. Analogy: the observer at the door with a clipboard. Precise: the ROCm profiling tool named in the curriculum's vocabulary table (with its predecessor rocprof) for traces and counters; its options and output formats are documented in the ROCm profiler documentation (D7). Not installed in this build (R1). D7 R1
ROCm Compute Profiler
Simple words: AMD's tool for a deep look at single kernels: how close they come to the hardware's limits, and where they wait. Analogy: the observer who sits at one table and counts everything. Precise: the per-kernel performance analysis tool, formerly named Omniperf, with speed-of-light, memory-chart and roofline views built from hardware counters (D7). Not installed in this build (R1). D7
ROCm Systems Profiler
Simple words: AMD's tool for one timeline of the whole program: CPU threads, API calls, copies and kernels. Analogy: the observer who films the whole street. Precise: the system-wide tracing and sampling profiler, formerly named Omnitrace, whose timeline shows host and device activity together (D7). Not installed in this build (R1). D7
Hardware performance counter
Simple words: a counter inside the GPU that counts events, such as instructions issued or bytes read. Analogy: a tally clicker fixed to a drawer or a door. Precise: a hardware register in a GPU block that counts a selectable event while a kernel runs; profilers read them per kernel and compute derived metrics from them; which counters exist depends on the GPU (D7, D2). D7
Derived metric
Simple words: a number a profiler computes from raw counts and time, such as GB/s. Analogy: "jars per minute", from "jars" and "minutes". Precise: a formula over counters and duration: bandwidth = bytes / time, FLOP/s = operations / time, arithmetic intensity = operations / bytes; Listing 2 implements these (R4).
Kernel trace / timeline
Simple words: the list of kernels with start and end times, drawn on a time axis. Analogy: the film of the street, frame by frame. Precise: a record of each dispatch's start and end timestamps (and, in a systems profiler, of host API calls and threads), from which busy time, gaps and overlap are read; Listing 3 produces one from a model (R5).

Layer 1 — the kid explanation

When cooking is slow, you can watch in three ways. You can note when each dish started and finished. You can sit at one table and count every jar and every wait. Or you can film the whole street, the restaurant and the kitchen together.

Start with the film: it shows whether the kitchen is busy at all. If it is idle half the time, the problem is outside, in how orders arrive. If it is always busy, pick the slowest dish and count everything at its table: is it waiting for jars from the pantry, or for the cooks' hands? The numbers you count only make sense next to the best the kitchen could ever do, so you always compare with that.

Timing before profiling

A profiler changes what it measures: it intercepts calls, and counter collection can replay a kernel several times. D7 The headline number of a performance milestone is therefore measured by your own harness, with the curriculum's protocol (13.4), quoted verbatim: "warm-up runs, then the median of at least 20 timed runs using device events; fixed clocks if your driver allows it (record the setting); report GB/s or TFLOP/s and the percentage of the reference." C1 Listing 1 does that for a scaling kernel with HIP events: three warm-up launches, 20 timed launches between hipEventRecord calls, sort, median of the middle two, bandwidth = 2 × n × 4 bytes / median. D1 In this build it stopped at its first call (no device, R2); its output line is a format, not a result.

What you know before you run

Some columns of a profiler's kernel table are static: they come from the code object, not from the run. The resources step printed them for Listing 1's kernel without a GPU: 13 SGPRs, 4 VGPRs, no AGPRs, no scratch, occupancy 8 waves per SIMD, no LDS (R3). R3 F7-10 to F7-13 showed how to read these and the ISA. A profile should never surprise you about them; if the profiler shows other register counts, you are profiling a different build.

The arithmetic behind the views

Every per-kernel view is built from a few totals: duration, bytes moved to and from DRAM, floating-point operations. Listing 2 computes the derived metrics for four kernels from invented totals (its input file says so in its first line) and a machine with invented roofs: achieved GB/s, achieved GFLOP/s, arithmetic intensity (FLOP per byte), the roofline at that intensity, min(compute roof, memory roof × intensity), and the percentage of it (R4). R4 With these invented values, scale (0.125 FLOP/byte) is memory-bound at 89.5 % of its roof; dot_fma reaches 74.6 % against dot_naive's 55.9 % with the same intensity; gemm_tiled (128 FLOP/byte) is compute-bound at 42.9 % (R4). On a GPU, the totals come from counters and the roofs from the product's documented peaks or from measured micro-benchmarks; record which (curriculum 13.4: "peak numbers from datasheets are context, not the target"). Layer 3 — the engineer's depth

In the analogy: before counting jars at one table, check on the film whether the hall is busy; before believing the count, check that the counter was not watching a rehearsal.

A workflow that ends in an explanation

  1. Timeline first. Measure GPU busy share and look for gaps between kernels (Listing 3's analysis). If the busy share is low, the problem is on the host or in synchronization: Listing 3's version A loses half the span to a synchronize after each launch (50.3 % busy, R5); version C, with tiny kernels, is launch-bound (60.2 % busy, R5). Fixes are on the host: queue work, fuse small kernels, use graphs (curriculum 13.2). R5
  2. Kernel list. Sort kernels by total time (calls × duration). Profile the top ones only.
  3. Static facts. For each top kernel: registers, LDS, scratch, occupancy (F7-10, F7-11), and the ISA census of its loop (F7-13). Predict its limiter before measuring.
  4. Roofline. Place the kernel: below the memory roof and far from it means latency or access-pattern problems (coalescing, bank conflicts); near the memory roof means the algorithm must move fewer bytes; near the compute roof means better instructions (FMA, packed or matrix instructions, HP401).
  5. Counters for the hypothesis. Collect only the counters that test your prediction (LDS bank conflicts for F7-11's transpose; scratch traffic for F7-10's spills; active lanes for F7-09's divergence), and confirm or reject it: this is E10's "confirm the predicted effect in the profiler".
  6. Write the explanation. Curriculum 13.4: "every performance milestone ends with a profiler-backed explanation of the remaining gap (memory throughput, issue stalls, occupancy, instruction mix)". C1

How profiles mislead

  • Replay. When more counters are requested than the hardware can collect at once, a profiler can run the kernel several times; a kernel that changes its own input (an in-place update, an atomic accumulation) then sees different data in each pass. D7
  • Serialisation. Per-kernel tools may serialise kernels that would otherwise overlap; do not read overlap from them, read it from the timeline. D7
  • Clocks. GPU clocks vary with load and temperature; the protocol says to fix them if the driver allows and to record the setting (C1). Compare runs only at the same setting.
  • Cold runs. The first launch includes code-object loading and other one-time work; Listing 1's warm-up excludes it.
  • Units. Decimal GB (109 bytes) and binary GiB (230) differ by 7.4 %; Listing 1 prints "decimal GB" so nobody has to guess (guide 13.3). G1

How the hardware actually does it

GPU blocks (the CUs' instruction and memory units, the LDS, the caches, the memory controllers) contain counters that a profiler can program to count selected events while a kernel runs, and read afterwards; the driver and the ROCm runtime provide the interfaces through which profiling tools configure counters and receive timestamps of dispatches and copies. D7 D2 Timestamps of a kernel's start and end come from the GPU's own clock and are converted to host time by the runtime; that is what the event-based timing of Listing 1 uses as well. D1 Sampling-based tools (as in ROCm Systems Profiler) periodically record where the host threads are, which is how the timeline shows host-side causes of GPU gaps. D7

Worked example

Task. Using Listing 2's invented machine (memory roof 1,000 GB/s, compute roof 20,000 GFLOP/s): (a) at what intensity does a kernel stop being memory-bound? (b) A kernel moves 64 MiB and performs 227 FLOP in 100 µs. Compute its intensity, achieved GFLOP/s, roof and percentage. (c) The team halves its DRAM traffic by caching a tile in LDS, with the same FLOP and time 70 µs. What changes?

  1. (a) Ridge = 20,000 / 1,000 = 20 FLOP per byte (R4 prints "ridge 20.00").
  2. (b) 64 MiB = 67,108,864 bytes. Intensity = 134,217,728 / 67,108,864 = 2.0 FLOP/byte. GFLOP/s = 134,217,728 / 100 × 10−6 / 109 = 1,342.2. Roof = min(20,000, 1,000 × 2.0) = 2,000 GFLOP/s. Percentage: 67.1 %. Achieved bandwidth: 67,108,864 / 100 µs = 671.1 GB/s.
  3. (c) Bytes 33,554,432: intensity 4.0, roof 4,000; GFLOP/s = 134,217,728 / 70 µs = 1,917.4; percentage 47.9 %. The kernel got faster (100 → 70 µs) while its percentage of roof fell, because the roof rose more than the speed. A percentage of roof is a diagnosis, not a score; the time and the gap explanation are what the milestone reports. (Lab Engineer's arithmetic; add both lines to metrics.in and run Listing 2 to check.)

Where the analogy breaks


    

  • Observers change what they observe. A person with a clipboard does not slow the kitchen; a profiler can (interception, replay, serialisation, D7). Headline times come from your own harness.
    • 

  • The film is not continuous. A systems profiler records events and samples, not every moment; short events between samples can be missed (D7).
    • 

  • Counting jars does not tell you the best possible evening. The roof in Figure 2 is a model limit; a real kernel may be bounded by something the roofline does not draw (latency, LDS throughput, instruction issue).

Forensic lab answer key


Observation. Version A: span 3,980, busy 2,000 = 50.3 %, every gap 20 (R5). Version B: span 2,000, busy 100 %, no gaps.


Hypotheses. (a) Excluded by the evidence: kernel durations are the same in A and B (20 each); the difference is all in the gaps. (b) Supported: the gaps appear only when the host waits after each launch. (c) Not the main cause here: with kernels of 20 and launch calls of 5, B is not launch-bound; version C shows what launch-bound looks like (60.2 % busy with 3-unit kernels).


Root cause. With a synchronize after every launch, the next step's preparation (15) and launch call (5) start only when the kernel has finished, so the GPU waits 20 units before each kernel. A faster GPU makes kernels shorter but the gaps stay, so the busy share gets worse: "slower than the old one" can be the host loop's effect on a faster GPU.


Fix and verification. Remove the per-launch hipDeviceSynchronize(); synchronize once, or only where the host needs results; check errors with hipGetLastError() after launches instead. The timeline should then look like B: kernels back to back, busy share near 100 %. Verify on the GPU with ROCm Systems Profiler.


Prevention. Host-code rule: no synchronization inside launch loops without a stated reason. Performance test: report GPU busy share from a timeline, not only kernel durations. How the evidence was produced: the Lab Engineer ran Listing 3 (a model with invented durations); the team, their GPU and their trace are a scenario.
