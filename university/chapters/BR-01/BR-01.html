Story hook

Lina has learned to run a busy kitchen. In SP203 she put several cooks in one kitchen, gave them one key to the spice cabinet, and learned that two cooks writing on the same order slip ruin the order. Her recipes are written in one language that every cook in the kitchen reads.

Today the school opens a great hall next door, full of helpers. Lina is delighted: the recipes do not need a new language. A recipe card for the hall is written in the same words, with the same measures and the same steps.

But by lunchtime she has met four surprises. The helpers cannot reach her pantry; the hall has its own, and someone must carry ingredients over and carry the dishes back. Every recipe now needs a label saying who may cook it: the chef, the hall, or both. When she hands the order slip to the hall, the hall starts work and she is back in her kitchen before a single dish is ready. And the hall never shouts when something goes wrong: if she does not walk to the pass and ask, she may serve an empty tray and never learn why.

This chapter is that first day in the hall. The language stays; the place to run changes.

What you will be able to do

  • Explain what carries over unchanged from C++ to CUDA C++ and what changes, most dangerous change first.
  • Rewrite a CPU vector-add program into CUDA C++ in five steps, compiling and checking after every step.
  • Mark functions with the execution-space specifiers __host__, __device__ and __global__, and predict which calls the compiler will refuse.
  • Write a checked launch: execution configuration, bounds check, the last-error check and a synchronising call, with device memory owned by an RAII class.
  • Read the messages of nvcc and the list of tools it runs, and say which part of your file became host code and which became device code.
  • Diagnose the four classic traps: reading results too early, a missing bounds check, a host pointer passed to a kernel, and unchecked errors that look like zeros.
Jargon box
Host code and device code
Simple words: the part of your program that runs on the CPU, and the part that runs on the GPU. Analogy: the pages of the recipe book that the head chef cooks from, and the recipe cards that go to the hall. Precise: in a CUDA C++ source file, functions are compiled for the host, for the device or for both, according to their execution-space specifiers; nvcc compiles the device part in a separate pass in which the macro __CUDA_ARCH__ is defined. D1 D3 R3 R7 "Host" and "device" themselves are defined in F6-01.
Execution-space specifier
Simple words: a word in front of a function that says where it may run. Analogy: a label on each recipe: "chef only", "hall only", or "both". Precise: __host__ (callable and run on the host; the default for an unmarked function), __device__ (run on the device, callable from device code) and __global__ (a kernel: run on the device, launched from the host); __host__ __device__ compiles one function for both. In the installed headers they are macros that expand to a compiler attribute. D1 H1 The bridge card calls them "qualifiers"; the CUDA documentation's own word is to be confirmed from D1 (see Sources).
nvcc
Simple words: the program you run to build CUDA C++; it calls several other tools for you. Analogy: a translator who splits the recipe book, rewrites the hall's cards for the hall, hands the chef's pages to the chef's usual translator, and binds everything back into one book. Precise: NVIDIA's CUDA compiler driver: for a .cu file it runs a preprocessor, a front end (cudafe++) that separates host and device code, the device compiler (cicc, which writes PTX), the PTX assembler (ptxas), fatbinary, and the host compiler and linker (here gcc/g++). D3 R7 A compiler driver in general is defined in F7-06 and F3-54.
Device pointer and host pointer
Simple words: an address in the GPU's memory, and an address in the CPU's memory. Both look like ordinary pointers. Analogy: a shelf number in the hall's pantry, and a shelf number in the chef's pantry; the note does not say which pantry it means. Precise: cudaMalloc returns a pointer to device memory that kernels may use; a std::vector's data() is a host pointer. Both have the C++ type float*, so the compiler cannot tell them apart. H1 R10
Last error
Simple words: the runtime's memory of the most recent thing that went wrong, which you must ask for. Analogy: a note pinned at the pass between kitchen and hall; nobody reads it to you. Precise: cudaGetLastError "Returns the last error that has been produced by any of the runtime calls in the same instance of the CUDA Runtime library in the host thread and resets it to cudaSuccess"; cudaPeekAtLastError returns it without resetting. A launch returns no value, so this is how its error reaches you. H1
Synchronising call
Simple words: a call that makes the CPU wait until the GPU has finished what it was given. Analogy: the chef walks to the pass and waits until the hall hands back the tray. Precise: cudaDeviceSynchronize "Blocks until the device has completed all preceding requested tasks" and returns an error if one of them failed; a cudaMemcpy from device to host also returns "only once the copy has completed". H1 CU303 calls these host synchronisation points (F6-32).
Managed memory
Simple words: memory that the CPU and the GPU can both use through the same pointer, moved for you behind the scenes. Analogy: a shared pantry whose shelves a porter moves between the two buildings when someone reaches for them. Precise: memory from cudaMallocManaged, whose pointer "is valid on the CPU and on all GPUs in the system that support managed memory"; the Unified Memory driver migrates it and tries to "prevent excessive page faults", which is where its costs come from. H1 Taught in F6-31; this bridge uses explicit copies.
Port (of a program)
Simple words: the same program, changed so that it runs somewhere new. Analogy: the same dish, rewritten for a different kitchen. Precise: a version of a program adapted to a new platform or programming model, with its behaviour checked against the original; here, from host-only C++ to host plus device CUDA C++. (The word is a general engineering term; it carries no CUDA-specific claim.)

Layer 1 — the kid explanation

You already know how to write a recipe in C++. You can name ingredients (variables), write steps (functions), repeat steps (loops), and check that the dish came out right (tests). None of that is thrown away. CUDA C++ is still C++.

What is new is a second building. The CPU is the head chef in the kitchen. The GPU is the great hall next door, with thousands of helpers. They do not share a pantry. If the helpers are to add two long lists of numbers, someone must first carry the lists into the hall's pantry, and later carry the answers back.

Every recipe now gets a label. "Chef only" recipes stay in the kitchen. "Hall" recipes, the recipe cards, are handed to the helpers. Some easy recipes, like "add two numbers", can carry both labels, so the chef and the helpers use exactly the same one.

When the chef hands the order to the hall, she does not stand there waiting. She walks back to her kitchen at once. That is fast, but it means she must not taste the dish before the hall has finished. And the hall never shouts about problems. The chef has to walk to the pass and ask: "did that work?" If she forgets, she may serve an empty plate and think it is the answer.

Layer 2 — the student explanation

The analogy in one sentence: the same recipe language, a second kitchen with its own pantry, labels on recipes, and orders that are answered only when you ask. Now the precise version, in two parts: what carries over, and what changes.

What carries over

C++ syntax, types and functions. A .cu file is C++ source. This build proved it the bluntest way possible: Listing 1, a plain C++ program, was copied unchanged into a .cu file and built with nvcc; it printed exactly what the g++ build printed. R1 R2 Inside the kernel, too, you write ordinary declarations, arithmetic, if statements and calls; Listing 5's kernel is four lines of familiar C++. D1

Templates. A function template can be marked __host__ __device__ and a kernel can be a template; Listing 5 uses both, and the compiler instantiates them for float exactly as F2-14 taught. The host binary even carries the instantiated name vecAdd<float> (R8). The words "within the limits CUDA documents" matter: everything a device-side template calls must itself be available in device code, which is the next section's subject. D1 R8

Headers and the build discipline of SP202. Listing 3 is an ordinary header with #pragma once, included by two programs. The lab builds every listing with all warnings turned into errors (-Werror all-warnings, the nvcc spelling of F2-27's -Werror), and the CPU listings with AddressSanitizer and UndefinedBehaviorSanitizer (F2-29). R5 R12

RAII for host-side resources. Device memory is a resource like a file descriptor (F2-11): acquired by cudaMalloc, released by cudaFree. Listing 3's DeviceBuffer owns one allocation, frees it in its destructor, and deletes its copy operations so that two owners can never free the same memory (F2-10). The object lives on the host; only the pointer it holds refers to the device. H1 D5

Testing habits. Every step of the port ends the same way as Listing 1: compare every element with a CPU computation and turn the count of mismatches into the exit status. In Listing 5 the CPU reference even calls the very same add function that the kernel calls. R5 Host code may still throw and catch exceptions (F2-16); Listing 3 does, and you will see in a moment why device code may not.

What you learned in SP203, re-used. A launch behaves like F2-41's asynchronous task: it starts work elsewhere and returns at once, and you must wait for it before you use its result. The difference is that there is no std::future to hold: you wait with a synchronising call. H1 And the warning of F2-35 still applies: reading memory that another processor may be writing, without the right waiting, gives you no guarantee about what you read.

What changes, most dangerous first

1. Two processors and two memories. The host is the CPU with its memory; the device is the GPU with its own memory. A kernel works on device memory, so the host allocates device buffers, copies inputs in, launches, and copies results back. D1 Pointers to the two memories have the same C++ type, so mixing them up is not a compile error (trap 3 below). R10

2. Asynchronous execution. The installed runtime header says it in one line: "Kernel launches are asynchronous with respect to the host." H1 The launch statement returns when the work is queued; the next host line may run while the GPU is still busy. A device-to-host cudaMemcpy "returns only once the copy has completed", and cudaDeviceSynchronize blocks until all earlier work is done. H1

3. Errors through return codes and a "last error". Runtime functions return a cudaError_t. A launch returns nothing, so you fetch its error with cudaGetLastError, which returns the last error of the runtime in this host thread and resets it. H1 Errors that happen inside a running kernel cannot be known at launch time; they are reported by a later call that waits, such as cudaDeviceSynchronize. H1 If you ignore all of this, nothing stops your program: it carries on with whatever is in its host buffers (trap 4, real output below). R11

4. Function execution-space specifiers. Every function is compiled for the host, the device, or both. An unmarked function is a host function, and a kernel may not call it: the compiler says "calling a __host__ function ... from a __global__ function ... is not allowed". D1 R9 The fix is a specifier, not a rewrite: __host__ __device__ in front of add makes one function usable on both sides (Listing 2).

5. The execution configuration of a launch. A kernel is not called like a function. It is launched with an execution configuration between triple angle brackets, vecAdd<<<blocks, threadsPerBlock>>>(...), which says how many blocks of how many threads to create. D1 Calling a kernel without it is a compile error ("a __global__ function call must be configured"), and putting a configuration on a host function is one too ("a host function call cannot be configured"). R15 Because the block count is rounded up, the grid usually has more threads than elements, and each thread must check its index: the bounds check (trap 2).

6. Explicit allocation and copies, or managed memory with its own costs. In this bridge and in CU201 every byte crosses between the memories by a cudaMemcpy that you write, so you can see it and later time it. The alternative, managed memory from cudaMallocManaged, gives one pointer valid on the CPU and on supporting GPUs; the header warns that the driver migrates such memory and works to "prevent excessive page faults", so the copies have not disappeared, they have become invisible. H1 F6-31 measures that cost.

7. A smaller C++ in device code. Device code supports much of the language but not all of it, and many standard-library facilities are not available there. D1 This build tested a handful of cases for real. An exception in a kernel is refused: "device code does not support exception handling" (R9). std::vector's member functions, std::string's constructor and an ordinary helper function are host functions, so a kernel may not call them (R15). Listing 6 below probes four more lines. The exact list of what is supported is in the Programming Guide's C++ language support section, which this build could not open.

Layer 3 — the engineer's depth


One analogy sentence: the translator splits the book, translates each half for its own kitchen, and binds both into one volume. Now the evidence.


The two roads, from the tool list


nvcc --dryrun lists the commands nvcc would run without running them ("Do not execute the compilation commands generated by nvcc. Instead, list them.", R16). This build ran it on Listing 5 and reduced each command to one line: the tool, the file it reads, the file it writes, and two facts from its command line. R7




Read it as two roads. Step 1 preprocesses the .cu file without __CUDA_ARCH__, and cudafe++ (step 2) turns that text into a host-only C++ file, .cudafe1.cpp, which gcc compiles in step 7. Step 3 preprocesses the same .cu file again, this time with __CUDA_ARCH__ defined, and cicc (step 4) turns it into PTX; ptxas (step 5) assembles the PTX into a cubin for the target sm_52, and fatbinary (step 6) packs both. Steps 8–11 are the device link and the final host link. R7 Step 7's command line also defines __CUDA_ARCH__, but it compiles a file that was preprocessed in step 1, so its #ifdefs were already decided; Listing 2's run, which printed "host pass" from main(), agrees with that reading. R3 That interpretation is ours, from the evidence; the NVCC document (D3) is the authority on the trajectory.


Two consequences matter every day. First, a __host__ __device__ function is compiled twice, once per road, so it must be valid C++ for both; code under #ifdef __CUDA_ARCH__ is seen by one road only. Second, the device road compiles for a target. With no option this nvcc chose sm_52 (visible in the file names); real projects choose their targets with the architecture options that F6-07 and F6-34 discuss. R7 D3


What the executable carries




cuobjdump finds device images inside the host executable: cubin ELF files for sm_52 and one PTX file. nm shows the host side of the kernel: a symbol for vecAdd<float> and a __device_stub__ function. Our reading, from the names and from F6-07's fatbinary chapter: when the host executes the launch statement, it calls host code that hands the kernel's arguments and configuration to the runtime; the kernel's instructions themselves are the device images. R8 D3 This is why a launch can be "asynchronous": on the host it is a call into a library that queues work.


RAII, exceptions and the two sides


Listing 3 throws on the host and never on the device, and that is a design decision, not an accident. The host may throw because host code is ordinary C++ (F2-16). The destructor of DeviceBuffer must not throw, because it can run during stack unwinding; it therefore reports a failed cudaFree on stderr instead. D5 H1 Device code may not throw at all (R9), so kernels signal problems in data: an error flag in device memory, or a count the host reads back. CU201 keeps its own style, which prints and exits (F6-05); both are valid as long as no call goes unchecked.


Index width


The built-in variables are structures of unsigned int: the installed headers declare threadIdx and blockIdx as uint3 and blockDim as dim3, both with members unsigned int x, y, z. H1 A product of two unsigned int values wraps around (F2-02 and MA102), so Listing 5 widens to std::size_t before it multiplies. Listing 10 shows the difference with real numbers in the Worked example. Whether a grid that large can be launched on your GPU is a device limit you read from the device query (F6-07), not from this chapter.



How the hardware actually does it


In the hall analogy the two pantries are two buildings; in hardware, on a GPU card, they are two separate memories joined by a link. The CPU's memory sits next to the CPU; the GPU's global memory sits on the card; on a PCIe card, copies between them cross the PCIe link, which F1-62 models and F6-09 measures. D1 D4 The CPU does not execute kernels: it places requests in a queue that the GPU works through, which is the mechanism behind "asynchronous with respect to the host" (F6-28 shows the queues, called streams, in detail). H1 D4 On the GPU, the blocks of the grid are spread over the streaming multiprocessors, which run their threads in warps (F1-55, F1-56, F6-01). How many there are, how wide the link is and how fast the copies go are properties of your exact product: read them from its documentation and from your own measurements, never from a chapter (guide AH-21 to AH-23).

Where the analogy breaks


    

  • A label on a recipe is advice; a specifier is a rule. A chef could ignore a "hall only" label. The compiler cannot: a kernel that calls a host function does not build (R9). And the label decides how the recipe is translated, not only who reads it: a __host__ __device__ function is compiled twice. R9
    • 

  • A shelf note in the wrong pantry is useless, but nobody notices. In a kitchen, a helper handed a note for the chef's pantry would say "that shelf is not here". The compiler says nothing: host and device pointers have the same C++ type, and the mistake compiled with zero warnings (R10). What happens at run time depends on the system and was not observable in this build.
    • 

  • The chef walking away is not the same as the hall being slow. "Asynchronous" says when the host call returns, not how fast the GPU is. A launch may return long before the kernel finishes or start long after the launch line; the host simply does not wait (H1).
    • 

  • One translator, not two. The analogy has one translator splitting the book, but nvcc really calls a whole team of tools, including your ordinary host compiler (Figure 2).

Common mistakes and debugging


The bridge card names four traps. Each one below has a real run where this build allows it, and a clear note where it does not.



Trap 1: reading results before the GPU finished


Symptom. Results that are old, partly old, or "fine on my machine". Cause. The host reads a buffer the GPU is still writing, or will write later. With explicit copies, as in Listing 5, the device-to-host cudaMemcpy waits for you (H1), so the trap needs one of three things: reading hC before the copy back, an asynchronous copy (F6-28), or managed memory read by the host right after a launch. H1 Listing 8 is a CPU model of the third case. It is the university's own teaching model, not CUDA: its launch() only queues the work, which then runs inside synchronize().

Summary


    

  • CUDA C++ is C++: a plain C++ program built with nvcc unchanged gave the same output.
    • 

  • Host code keeps everything you know: templates, headers, exceptions, RAII, tests and sanitizers.
    • 

  • There are two processors and two memories; pointers to both have the same type, so the compiler cannot catch a swap.
    • 

  • __host__, __device__ and __global__ say where a function runs; a kernel may not call a host-only function.
    • 

  • A kernel is launched with an execution configuration; rounded-up grids need a bounds check in every kernel.
    • 

  • Launches return before the work is done; read results only after a waiting call.
    • 

  • Errors arrive as return codes and as a last error you must fetch; unchecked failures look like zeros.
    • 

  • Device code is a smaller C++: no exceptions, many standard-library facilities unavailable; check the Programming Guide for the exact list.
    • 

  • nvcc splits one file into a host road and a device road and joins them in one executable.
    •

Hypotheses. (a) Each fix introduced a new bug. (b) The compiler reports problems in stages, so problems that were there from the start appear only once earlier ones are gone. (c) The compiler is broken.


Evidence-based conclusion. The lines that fail in build 3 (18 and 21) are identical in forensic_port.cu and forensic_port3.cu; Kwame's fixes touched only line 28 (build 1's error) and line 19 (build 2's error). So the problems in build 3 were present in build 1: hypothesis (b). Figure 2 and R7 show why stages are plausible: the configuration error is about the host side of the file, and the device compiler (cicc) reports device-code errors; this build's messages arrived one stage at a time. (That the exact staging is a property of the toolchain is our reading of the evidence; D3 is the authority.) The root cause is one misunderstanding: Kwame wrote the kernel as host C++, taking std::vector references, calling an unmarked helper, throwing an exception, and calling the kernel like a function. Kernels take device pointers and sizes, call only device-callable functions, signal problems through data, and are launched with a configuration.


Wrong answers and why. "The fixes broke it": refuted by the unchanged lines 18 and 21. "nvcc is broken": the same compiler builds Listing 5 cleanly (R5). "Just add --expt-relaxed-constexpr": the refused functions are not constexpr, and even if the code compiled, the vectors' data would still be in host memory (trap 3).


Fix and verification. Listing 5: template <typename T> __global__ void vecAdd(const T* a, const T* b, T* c, std::size_t n), a __host__ __device__ helper, if (i < n) instead of a throw, DeviceBuffers with copies, and vecAdd<<<blocks, threadsPerBlock>>>(dA.get(), dB.get(), dC.get(), n) followed by the two checks. Verified in this build: it compiles without warnings (R5); its GPU run is untested on hardware.


Prevention. Port in small checked steps, as in this chapter: step 3 (specifiers, kernel written but not launched) would have shown the device-code errors before any launch existed. How the evidence was produced: three real builds of the three files in this build's container with the lab's nvcc command; the files were written to contain the mistakes; nothing in the output was edited.
