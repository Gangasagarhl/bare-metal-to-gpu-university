Story hook

Mei runs a row of kitchen helpers in the great hall. At the end of every shift she wants to know one thing: how many plates came out burnt. Her method is quick. She asks the whole row "is your plate burnt?", every helper with a burnt plate raises a hand, and the helper at the start of the row counts the hands on a tally card with 32 boxes, one box per helper. Then she adds the row's number to the shift total. Rows in her hall have 32 helpers, so the card always fits.

The company opens a second kitchen building across the road, and Mei's recipe cards go there unchanged. The recipes cook perfectly: same steps, same plates. But the evening report says fewer burnt plates than the bins show. Tunde, the shift lead over there, walks the hall and finds out why. His rows have 64 helpers. Mei's card still has 32 boxes, so only the first 32 hands of each row are ever written down. And because her card says "the helper at seat 0, 32, 64 and so on counts", each long row has two counters, both reading the same short card. On a night when every plate is burnt, the two half-counts happen to add up to the right answer, and nobody notices anything for weeks.

This bridge is about moving recipes into that second building: almost everything carries over, a few things change, and a small number of hidden numbers on the cards turn into quiet, wrong answers.

What you will be able to do

  • Map a CUDA C++ program to HIP: headers, the cuda→hip runtime names (checked against the installed HIP header, not memory), and the kernel code that stays the same.
  • Port a CU201 lab with a translator, build the result for both HIP back ends (AMD through clang, NVIDIA through nvcc) and read each build's messages as evidence.
  • Find and fix the four traps of this step: a hard-coded 32, a 32-bit ballot mask, tuning parameters copied from NVIDIA, and a library assumed to have a drop-in HIP twin.
  • Prove a warp-size fix without a GPU: from the AMD assembly (lane test and population count) and from a lock-step CPU model with data that makes the bug visible.
  • Explain which tools, documents and hardware lists change when you cross from the CUDA world to the ROCm world, and what you must check before trusting a result from either.
Jargon box
HIP
Simple words: a way to write GPU programs in C++ that can be built for AMD GPUs and for NVIDIA GPUs from one source. Analogy: the shared cookbook language both kitchen buildings can read. Precise: AMD's C++ runtime API and kernel language whose host functions mirror the CUDA runtime with a hip prefix and whose kernels use CUDA's __global__, threadIdx and <<<…>>> syntax (full entry in F7-01). D1 R3
ROCm
Simple words: AMD's whole software stack for computing on its GPUs. Analogy: the second kitchen building with its staff and equipment. Precise: AMD's open GPU-computing platform (driver, runtimes, compiler, libraries, tools); HIP is its programming interface; supported GPUs and operating systems are listed per version in its compatibility matrix. D2
hipcc
Simple words: the command that compiles a HIP program by calling the real compiler for you. Analogy: the prep chef who translates a card for the stoves of one building. Precise: HIP's compiler driver: on the AMD platform it runs clang with one --offload-arch per GPU target; on the NVIDIA platform it runs nvcc (this build: clang 17.0.6 and nvcc 12.0). D1 R2
Wavefront
Simple words: AMD's name for the group of GPU threads that move together, like NVIDIA's warp. Analogy: a row of helpers; 64 long in the second building's CDNA halls. Precise: the unit of SIMT execution on AMD GPUs; 64 lanes on CDNA targets such as gfx90a, 32 or 64 on RDNA targets; the built-in warpSize gives the width the code was compiled for (64 for gfx90a and 32 for gfx1030 in this build). D4 D5 R12
Ballot and lane mask
Simple words: a vote where every lane answers yes or no, and the answer comes back as one bit per lane. Analogy: raising hands in a row (the analogy of F6-15), with a tally card of one box per seat. Precise: CUDA's __ballot_sync(mask, p) returns an unsigned int with bit k set when lane k's predicate is true; HIP 5.7's AMD header declares unsigned long long __ballot(int), a 64-bit lane mask. D3 H1
LDS (Local Data Share)
Simple words: AMD's name for the fast on-chip memory that CUDA calls shared memory. Analogy: the table in the middle of a row group (the same table, a different name on the building's floor plan). Precise: the on-chip memory of an AMD compute unit that backs a workgroup's __shared__ variables; HIP code still writes __shared__, and the AMD assembly accesses it with ds_ instructions. D4 R18
Warp-size-agnostic code
Simple words: GPU code that gives the right answer whatever the number of lanes in a warp or wavefront. Analogy: a recipe card that says "the first helper of each row counts" instead of "the helper at seat 0, 32, 64…". Precise: code that takes the group width from warpSize (or a host query of the device property), stores lane masks in 64 bits, and keeps tuning values that depend on the width in per-target tables. C1 R12
Drop-in equivalent (library)
Simple words: a library you can swap in by renaming calls, without changing what the program means. Analogy: the second building's own spice mix: maybe the same, maybe not; you taste before you serve. Precise: a claim, to be checked per function and per version, that a library on one platform offers the same functions, arguments, data layouts and results as one on another; a renaming translator cannot establish it. D8 R17

Layer 1 — the kid explanation

You already know how to write recipe cards for the NVIDIA kitchen hall in CUDA. HIP lets you write the same cards for a second building, AMD's. The cooking steps do not change. The names of the tools change a little: cudaMalloc becomes hipMalloc, the header has a new name, and a different prep chef, hipcc, prepares the card. Most of a port is renaming, and a translator program can do most of the renaming for you.

The dangerous part is not the renaming. It is the numbers you wrote on the card without noticing that they described the old building: "a row has 32 helpers", "my tally card has 32 boxes", "use rows of 32 because that was fastest over there". Those numbers still compile in the new building. They just give the wrong count, or a slower kitchen. Your job in this bridge is to find those numbers, replace them with questions ("how long is a row here?"), and prove the fix with evidence, even without a GPU.

Layer 2 — the student explanation

As in the story, HIP is the shared cookbook language and ROCm is the second building (F7-01 uses the same picture). This section takes the bridge card's three lists in turn: what carries over, what changes, and the traps.

What carries over

The programming model. HIP reproduces the CUDA runtime's model: a host program allocates device memory, copies data, launches kernels over a grid of blocks of threads, orders work in streams, times it with events and reads error codes after every call. D1 D3 Everything CU201 taught about the index formula (F6-02), memory spaces (F6-03), the bounds check (F6-04), checking every call and launch (F6-05) and timing with events (F6-06) applies unchanged. The kernel of this bridge's starter, Listing 1, is F6-04's SAXPY with one extra statistic; its only lines that do not survive the port are the two vote lines.

Most runtime calls, by name. The installed HIP release contains a header for its NVIDIA back end in which every HIP function is written in terms of a CUDA function. Reading that header gives the map this HIP version really uses, with line numbers. For the 17 runtime names that Listing 1 and CU201's timing chapter use, R3 found the CUDA counterpart of each: 16 differ only by the prefix (hipMalloc → cudaMalloc at line 1495, hipEventElapsedTime → cudaEventElapsedTime at line 2471, and so on), and one does not: hipHostMalloc wraps cudaHostAlloc (line 1528). H3 R3 The HIP documentation's porting guide and API reference are where these mappings are documented for each release; the header shows what one installed release does. D1

Kernel code is largely the same C++. The translator changed 18 of the 97 lines of Listing 1 (R4), and every changed line was in host code or the include; the kernel's body was untouched by renaming. What changes

API prefixes and headers. #include <cuda_runtime.h> becomes #include <hip/hip_runtime.h>; types and constants change with the functions (cudaError_t → hipError_t, cudaSuccess → hipSuccess, cudaMemcpyHostToDevice → hipMemcpyHostToDevice). D1 R4

The driver and the toolchain. You build with hipcc. On the AMD platform it runs clang and produces machine code per named GPU target (--offload-arch=gfx90a in this lab); on the NVIDIA platform it runs nvcc (selected here with HIP_PLATFORM=nvidia). D1 R2 This build reported HIP version: 5.7.31921-0, clang 17.0.6 and hipconfig --platform: amd (R2). F7-01 and F7-06 show the full command lines.

The warp size is not a constant 32. NVIDIA's warp is 32 threads. D3 AMD's wavefront is 64 lanes on CDNA and 32 or 64 on RDNA. D4 D5 In HIP 5.7, warpSize is declared as static constexpr int warpSize = __AMDGCN_WAVEFRONT_SIZE; (line 86 of the AMD warp-functions header), so it is a compile-time constant per target; the assembly in R12 shows it became 64 for gfx90a and 32 for gfx1030, and the code-object metadata says .wavefront_size: 64 and 32. H2 R12 On the NVIDIA back end the PTX reads it from the special register WARP_SZ instead (R13). R13

Lane masks become 64-bit. A mask has one bit per lane, so a 64-lane wavefront needs 64 bits. HIP 5.7 declares unsigned long long int __ballot(int predicate) and a 64-bit population count __popcll. H1 The CUDA vote __ballot_sync, which takes a participation mask and returns 32 bits, does not exist in HIP 5.7 for AMD: the build of the translated file stopped with use of undeclared identifier '__ballot_sync' (R5). R5 D3

"Shared memory" is called LDS in AMD's documents. The source keyword stays __shared__; AMD's ISA and architecture documents call the on-chip memory behind it the Local Data Share. D4 R18 shows both names on one kernel: ds_write_b32, s_barrier, ds_read_b32 and a group_segment_fixed_size of 1024 bytes on AMD; .shared, st.shared, bar.sync and ld.shared in PTX. R18 When you read an AMD tuning document, translate "LDS" back to the table in the middle of the row group.

Different profilers. NVIDIA's correctness and performance tools are Compute Sanitizer, Nsight Systems and Nsight Compute D9; AMD's are the rocprof family (rocprofv3/rocprof, ROCm Compute Profiler, ROCm Systems Profiler) D2. Hardware support is a list. The four traps

Trap 1: hard-coded 32. threadIdx.x & 31, % 32, / 32, a shuffle loop starting at 16, an array of 32 per-lane slots: each is correct for 32-lane warps and wrong for 64-lane wavefronts, and the compiler accepts every one of them. In Listing 1 the leader test (threadIdx.x & 31) == 0 picks lanes 0 and 32 of each 64-lane wavefront, so each wavefront gets two leaders. The assembly of the naive port shows the test as v_and_b32_e32 v0, 31, v0 (R12). R12

Trap 2: 32-bit ballot masks. Writing unsigned int mask = __ballot(p); compiles silently with this build's default flags and keeps only lanes 0–31 (R7). Asked with -Wshorten-64-to-32, clang says exactly what happened: implicit conversion loses integer precision: 'unsigned long long' to 'const unsigned int' (R8). R7 R8 In the naive port's assembly the population count is the 32-bit s_bcnt1_i32_b32 s0, vcc_lo: it counts only the low half of the 64-bit vote register (R12).

Trap 3: tuning parameters copied from NVIDIA. A block size, a tile size or a per-warp work split chosen on an NVIDIA GPU encodes 32 lanes and that GPU's resources. Listing 4's table (R15) is the arithmetic for the first of these: a block of 32 threads fills one warp but only half of a 64-lane wavefront (32 idle lanes); 96 and 160 threads waste 32 lanes per block on wave64; 64, 128, 192 and 256 fit both. R15 Shared-memory/LDS sizes, register budgets and occupancy also differ per GPU and are measured, not copied (HP302, F7-10).

Trap 4: assuming a CUDA library has a drop-in HIP equivalent. A translator renames what it knows. R17 ran the university's teaching translator on a program that calls cuBLAS: it reported CUDA-looking identifiers NOT translated: 0, and the output still included cublas_v2.h and called cublasSgemm; the AMD build then failed inside the CUDA headers. R17 R16 shows that this container has cuBLAS, CUB and Thrust and none of rocBLAS, hipBLAS, hipCUB, rocPRIM or rocThrust. R16 Whether an AMD library exists for your call, with the same arguments, layouts and results, is a question for that library's documentation and a test, every time. D8

Layer 3 — the engineer's depth

Why the model ports and the numbers do not

The CUDA programming model is defined without a warp width in most of its rules: a kernel is a function over a grid of blocks, threads in a block share memory and barriers, blocks are independent. D3 HIP adopts those rules. D1 The width enters only where code reaches below the block into the lock-step group: votes, shuffles, lane indices, "warp-synchronous" tricks, and tuning. The curriculum's vocabulary table says it in one line: "never hard-code 32 in portable code". C1 A practical audit therefore searches a CUDA code base for exactly those places: literals 32, 31, 16 and 0xffffffff near threadIdx, lane, warp, shfl or ballot; every _sync warp intrinsic; every mask variable's type; and every constant tuned on a GPU. The teaching translator of F7-04 prints such lines (R4 flagged line 22) but cannot judge them. R4

The vote, precisely, on each back end

On NVIDIA, __ballot_sync(mask, p) evaluates p for the lanes named in mask and returns a 32-bit value with bit k set for lane k; the lanes named in the mask must all reach the call. D3 In PTX it is vote.sync.ballot.b32 (R13). In HIP 5.7 on AMD, __ballot(p) is implemented as __builtin_amdgcn_uicmp(predicate, 0, ICMP_NE), a compare across the wavefront that yields a 64-bit scalar value, and there is no participation-mask argument. H1 Two consequences matter for a port:

  • The result type differs (32 versus 64 bits), so the variable that receives it must be 64 bits in portable code. On wave32 targets the upper 32 bits are simply zero: in the gfx1030 assembly the fixed kernel builds the high half as s_mov_b32 s1, 0 and counts it with s_bcnt1_i32_b64 s0, s[0:1] (R12). R12
  • The calling convention differs (mask argument or not), so one spelling does not compile on both back ends in HIP 5.7. The non-sync __ballot does compile on the NVIDIA back end, but it is CUDA's own deprecated function: nvcc warned __ballot() is deprecated in favor of __ballot_sync() and ptxas warned that vote without .sync is deprecated (R9). R9 H4 Listing 2 therefore wraps the vote in a four-line function selected by the platform macro: __ballot on AMD, __ballot_sync(0xffffffffu, p) on NVIDIA. The literal 0xffffffffu is correct there because that branch only compiles for 32-lane warps and every lane of the (full) warp reaches the call.
Not verified — check before relying on this

Whether newer HIP releases than 5.7 provide __ballot_sync or other _sync warp functions on AMD, and with which mask type, was not checked: only the HIP 5.7.1 headers installed here were read. Check D1 (HIP documentation, the section on warp cross-lane functions, for the ROCm version recorded in your dossier) before choosing between a platform switch like Listing 2's and a single spelling.

The leader test and the compiler's own aggregation

Both versions elect leaders and do an atomicAdd. The AMD assembly shows something extra that is worth reading slowly (R12): after the leader test, the compiler counts the active leader lanes with s_bcnt1_i32_b64 s1, s[2:3] (a population count of the execution mask), multiplies by the value with s_mul_i32 s0, s0, s1, and lets one lane do a single global_atomic_add. R12 Because the vote result is the same for every lane, adding it once per leader equals adding it times the number of leaders. In the naive port that number is 2 on a full wavefront (lanes 0 and 32), so the assembly literally computes 2 × popcount(low 32 bits): the double counting of Figure 2, visible without a GPU. In the fixed code the leader test is v_and_b32_e32 v0, 63, v0 on gfx90a (the compiler turned % warpSize with the constant 64 into a mask of 63), so there is one leader. R12 H2

Note

Reading the assembly this way is an interpretation of this build's listing in the light of the ISA guide's general description of scalar, vector and execution-mask instructions (D4, pending verification). The CPU model (Listing 3, R14) is the independent check: its "naive port, W = 64" rows equal 2 × the low-half counts by construction, and its totals are wrong in exactly the cases the assembly predicts.

Why the bug survives tests

R14 is the uncomfortable part. With all results negative and n = 1,048,576, the naive port is correct: each full wavefront has 32 negative lanes in its low half, two leaders each add 32, total 64. R14 With n = 1,000,003 the same data set is off by 3 (1,000,006 versus 1,000,003), only because the last wavefront is partial. With the lab's mixed data it is off by 78 of 537,300 at n = 1,048,576 — small enough to look like noise. With negatives only in lanes 32–63 it returns 0. A port test must therefore use data that differs between the two halves of a wavefront, sizes that are not multiples of 64, and an exact reference; the E1 milestone's "bit-exact against a CPU reference … including non-multiple-of-block sizes" is the right habit, applied to the count as well as to y. How the hardware actually does it

On an AMD GPU a wavefront runs on a SIMD unit of a compute unit; a vector instruction operates on all lanes at once under a 64-bit execution mask (EXEC on wave64), and scalar instructions run once per wavefront on scalar registers. D4 A vote is therefore cheap and natural on this hardware: a vector compare writes one bit per lane into a 64-bit scalar register pair (vcc in R12), and counting the yes votes is one scalar instruction (s_bcnt1_i32_b64). R12 When C++ stores that pair in a 32-bit variable, the compiler simply uses the low register (vcc_lo) — the hardware did not lose the upper lanes; the program did. On RDNA in wave32 mode the same compare fills a 32-bit register (vcc_lo, exec_lo in the gfx1030 listing). D5 R12 On NVIDIA, a warp of 32 threads executes in SIMT fashion and vote.sync.ballot.b32 produces the 32-bit mask. D3 D10 R13 The LDS is on-chip memory per compute unit that the workgroup allocates (the group_segment_fixed_size of 1024 bytes in R18 is 256 four-byte integers), reached with ds_ instructions. D4 D6 R18 HP302 (F7-08 to F7-13) goes through each of these units in depth.

Worked example

Question. One block of 256 threads runs the naive port on gfx90a (wavefronts of 64). Every thread's result is negative except threads 32–63 and 160–191. How many does each version count, and what is right?

  1. Group the threads. 256 / 64 = 4 wavefronts: threads 0–63, 64–127, 128–191, 192–255 (lanes are consecutive threadIdx.x values in a one-dimensional block D3).
  2. Right answer. 256 − 32 − 32 = 192 negatives.
  3. Naive port, wavefront 0. Negatives in lanes 0–31 only (32 to 63 are not negative). Kept low half: popcount 32. Leaders: lanes 0 and 32 (threads 0 and 32). Contribution 2 × 32 = 64. True value 32.
  4. Wavefront 1 (threads 64–127): all 64 negative. Low half popcount 32, two leaders: 64. True 64.
  5. Wavefront 2 (threads 128–191): lanes 0–31 (threads 128–159) negative, lanes 32–63 (threads 160–191) not. Contribution 2 × 32 = 64; true 32.
  6. Wavefront 3: all negative: 64; true 64.
  7. Naive total 64 + 64 + 64 + 64 = 256; right answer 192. Fixed total: one leader per wavefront adds popcount of 64 bits: 32 + 64 + 32 + 64 = 192.
  8. CUDA original on 32-lane warps (8 warps): 32 + 0 + 32 + 32 + 32 + 0 + 32 + 32 = 192, correct — which is why the bug never showed on NVIDIA.

The rule behind it: the naive port counts 2 × (low-half negatives) per full wavefront. Check it against R14. The worked block is the pattern of R14's fourth data set, "negative except i % 128 in 32–63", repeated: at n = 1,048,576 there are 4,096 such blocks, and R14 prints 1,048,576 (= 4,096 × 256) for the naive port against the reference 786,432 (= 4,096 × 192). Its "negative only in lanes 32–63" rows are the extreme case: low halves have no negatives, so the naive count is 0. R14

  • "Same recipes" hides that HIP is mostly CUDA's own vocabulary. The second building did not invent a neutral language; HIP follows the CUDA runtime name by name (R3), which is why porting is easy and why CUDA habits, including the 32, come along unnoticed.
    • 

  • A row of helpers does not "notice" a short tally card. In the story Tunde finds the problem by walking the hall. A GPU never reports a truncated mask: the hardware computed all 64 bits correctly (R12) and the program threw half away. Only a test with the right data, or a compiler warning you asked for (R8), will tell you.
    • 

  • The second building is not always a different building. HIP on the NVIDIA back end runs in NVIDIA's kitchen through CUDA (R6, R11). "It runs in HIP" says nothing about AMD hardware.
    • 

  • Row length belongs to the stove model, not to the company. AMD's gfx1030 compiled with 32 lanes in this build (R12); the width is a property of the compile target, and one AMD executable can carry code objects with different widths.
    •

Summary


    

  • The CUDA programming model carries over to HIP: grids, blocks, threads, shared memory, streams, events, the kernel syntax and the habit of checking every call.
    • 

  • Most runtime calls differ only by the prefix (16 of 17 here, R3); some do not (hipHostMalloc wraps cudaHostAlloc), so check the header or the porting guide, not memory.
    • 

  • The warp size is a property of the compile target: 64 on gfx90a, 32 on gfx1030, 32 on NVIDIA; read warpSize and never write 32 in portable code.
    • 

  • Lane masks are 64-bit; HIP 5.7's __ballot returns unsigned long long, and __ballot_sync does not exist for AMD in that version.
    • 

  • A 32-bit mask and a & 31 leader together double-count the low half and drop the high half of every wavefront, and uniform test data can hide it completely (R14).
    • 

  • Without a GPU you can still prove a lane-width fix: AMD assembly (R12), PTX (R13), a narrowing warning (R8) and a lock-step CPU model (R14).
    • 

  • Tuning values and library equivalences are measured and checked per platform, never copied; a translator's silence is not evidence (R17).
    • 

  • Everything GPU-side in this chapter is untested on hardware; builds, generated code and CPU models are real.
    •

Forensic lab answer key


Observation. Leader test: v_and_b32_e32 v0, 31, v0 followed by v_cmp_eq_u32_e64 s[0:1], 0, v0 — lanes whose threadIdx.x & 31 is 0. Vote count: s_bcnt1_i32_b32 s0, vcc_lo — population count of the low 32 bits of the 64-bit compare result vcc. Leader count: s_bcnt1_i32_b64 s1, s[2:3] after s_mov_b64 s[2:3], exec, then s_mul_i32 s0, s0, s1 and one global_atomic_add (R12). Evidence 2: the narrowing warning on line 21 (R8).


Hypotheses. (1) Floating-point differences changing signs: ruled out as the main cause because the AMD assembly uses a fused multiply-add (v_fmac_f32, R12), matching the CPU reference's std::fma and the NVIDIA build; and sign changes would not depend on lane position. (2) Lane-width assumption: supported by the 31 mask, the 32-bit popcount and the narrowing warning. (3) Atomic race: ruled out — the atomic is a hardware atomic add and the compiler even merges the leaders into one; a race would not explain agreement on NVIDIA.


Root cause. On wave64, lanes 0 and 32 of every wavefront are leaders; each adds the number of negatives among lanes 0–31; lanes 32–63 are never counted. Count per full wavefront = 2 × (low-half negatives). On data where both halves have the same number of negatives this equals the truth, which is exactly the test suite's "all negative, n = 1,048,576" case (R14, ok). On mixed production data it is close but wrong (R14: 537,222 instead of 537,300).


Fix and verification. Listing 2: 64-bit LaneMask, __popcll, leader threadIdx.x % warpSize == 0, platform wrapper for the vote. Evidence this week: clean build with -Wshorten-64-to-32 on both back ends; assembly with & 63 and s_bcnt1_i32_b64 … vcc; the model's "fixed, W = 64" rows all ok. The AMD GPU run stays an open item in the report.
