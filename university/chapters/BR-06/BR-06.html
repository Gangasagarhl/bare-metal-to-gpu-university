Story hook

Analogy

Before Ms Okafor opens her second school, the school board sends her on a week of visits to three schools in three countries. She brings her timetable, her rules for settling quarrels and her lesson plans. On the first evening she notices that none of them needed changing: they never mention a building.

Everything else is different. In the first school, the staff rooms are numbered 0 to 3 and the principal holds the key to room 0. In the second, the rooms are numbered the other way round, and there is an extra room above the principal's for an inspector. In the third, the caretaker keeps the top room for himself and lets the principal in one floor lower. Each caretaker hands over the building in a different way: one gives a thick folder of forms, two leave a folded plan of the building on the desk. The doorbells are wired to different panels. And in two of the schools, notes pinned on the noticeboard by one teacher can be read by another teacher in a different order from the one in which they were pinned, unless the writer adds a "read the earlier notes first" stamp.

On the last day Ms Okafor writes one page: what stayed the same, what changed, and the four mistakes she almost made. This chapter is that page for kernels.

What you will be able to do

  • Explain what carries over from an x86-64 kernel to AArch64 and RISC-V (the arch-neutral core, the platform checklist, C++ code with correct atomics) and prove it by running one test suite, unchanged, on all three.
  • Compare the three privilege models (rings, exception levels, M/S/U modes), boot contracts (Multiboot or UEFI with ACPI, the arm64 Image contract with a devicetree, OpenSBI with SBI) and interrupt controllers (APIC, GIC, PLIC and ACLINT), using what each machine reported about itself in this build.
  • Predict which reorderings a strongly ordered (x86) and a weakly ordered (Arm, RISC-V) CPU allow, show the barriers a compiler emits for each C++ memory order on each CPU, and explain why an emulator is not evidence about hardware ordering.
  • Decide when a driver must clean or invalidate caches around DMA, and why buffers must not share a cache line with other data.
  • Diagnose the four bridge traps from real evidence: a missing barrier, a hard-coded page size, an assumed APIC and the byte order of device and on-disk data.
Jargon box
Boot contract
Simple words: the promise between whoever starts your kernel and your kernel: where it is loaded, in which CPU mode it starts and which register holds what. Analogy: how the caretaker hands over the building on the first morning: a folder of forms, or a plan left on the desk. Precise: the entry state defined by a boot protocol document, for example the Multiboot Specification (eax = 0x2BADB002, ebx = information structure, 32-bit protected mode), the Linux arm64 booting document (x0 = devicetree address) or the SBI specification's convention used by OpenSBI (a0 = hart ID, a1 = devicetree address, S-mode). Privilege level, exception level, privilege mode
Simple words: three families' names for "how much is this code allowed to do". Analogy: student areas and staff-only rooms; some buildings have an inspector's room above the principal's. Precise: x86 has rings 0–3, with the current privilege level in the low two bits of CS; AArch64 has exception levels EL0 (user) to EL3 (secure monitor), readable from CurrentEL at EL1 and above; RISC-V has U, S and M modes (plus the H extension), with M reserved for firmware. Strongly and weakly ordered CPUs
Simple words: whether other cores see one core's memory accesses in the order the program wrote them. Analogy: notes on the noticeboard read in the order they were pinned, or not (a proposed mapping, see the notes). Precise: x86 follows total store order (TSO): only a later load may complete before an earlier store to a different address. Arm and RISC-V are weakly ordered: loads and stores to different addresses may be reordered unless an acquire, release or fence instruction forbids it. D1 D2 D3 D4
Page granule
Simple words: the size of the smallest page an MMU translates. Analogy: the size of one locker on the locker map: the same map with bigger lockers has fewer of them. Precise: on AArch64 the kernel chooses a translation granule of 4, 16 or 64 KiB among those the CPU implements; the page size of a port is a fact the arch layer reports, not a constant of the core. Plain char signedness
Simple words: whether the C++ type char holds −128..127 or 0..255. Analogy: two schools that agree on the alphabet but not on whether the last letters count as "minus". Precise: the language leaves it to the platform's ABI; this build's toolchains make plain char signed on x86-64 and unsigned on AArch64 and RISC-V Linux (R3). D15 R3
Cache-maintenance instruction
Simple words: an instruction that tells the data cache to write a line back to memory, or to forget it. Analogy: before the delivery truck takes boxes from the storeroom, someone must carry the boxes still on the classroom tables to the storeroom. Precise: clean (write back a dirty line), invalidate (discard a line) and clean-and-invalidate, by address: DC CVAC, DC IVAC, DC CIVAC on AArch64; cbo.clean, cbo.inval, cbo.flush from the Zicbom extension on RISC-V. Needed around DMA when a device is not cache-coherent. D3 D13 R10
Entry probe
Simple words: this chapter's tiny kernel that only prints what it found when it was started. Analogy: the principal's first walk round a new building with a notebook. Precise: a freestanding image per machine (probe_core.cc, unchanged, plus one arch layer) that prints its privilege level, the registers of the boot contract and the devicetree magic, then powers the machine off through that machine's own mechanism. Layer 2 — the student explanation

What carries over

The arch-neutral kernel core. Your OS303 kernel already separates two kinds of code. Formatted output, the frame allocator's bookkeeping, the scheduler's queues, the file systems: these talk about ideas, not about a machine. They are compiled again for each CPU, but they are not edited. In this chapter the same rule is applied to a tiny kernel: probe_core.cc is compiled for a 32-bit x86 Multiboot image, an AArch64 Image and two RISC-V images, and every probe log records the same SHA-256 prefix for it. What changes, most dangerous first

Memory ordering. x86 keeps almost every order your program wrote: only a later load can overtake an earlier store. Arm and RISC-V allow far more reordering. Code with plain variables or memory_order_relaxed where an acquire or release was needed can work for years on x86 and corrupt data on Arm. This is the most dangerous change because nothing fails at build time and the failure is rare. D1 D2 D3 D4

Cache maintenance for DMA. On a typical PC, devices that read and write memory see what the CPU caches hold. On many Arm and RISC-V systems on a chip, some devices do not: the driver must clean the cache before a device reads a buffer and invalidate it before the CPU reads what a device wrote. A missing clean sends stale data; a buffer that shares a cache line with other data can be overwritten after the device wrote it. D1 R10

Interrupt controllers. The PC's local APIC and IOAPIC become a GIC on Arm and a PLIC with an ACLINT (or the newer AIA) on RISC-V. Different registers, different numbering, different ways to acknowledge an interrupt. Core code that "knows" the APIC address faults on the other machines. D1 R8

Boot contracts. On the PC your kernel was started by UEFI (or a Multiboot loader) and learned about the machine from ACPI tables. On the two new machines it is started with a devicetree address in a register, by QEMU's loader on AArch64 and by OpenSBI on RISC-V. D5 D6 D7 R1

Privilege models. Rings become exception levels or modes. The idea of user and kernel privilege carries over; the number of levels, who sits above the kernel, and the instructions to move between levels do not. D2 D3 D4

Four traps sit across these changes, and each one gets a real run in this chapter: a missing barrier, a hard-coded page size, an assumed APIC, and the byte order of device and on-disk data. D1

Layer 3 — the engineer's depth

Privilege models

The x86 privilege level of running code is the current privilege level (CPL), held in the low two bits of the CS selector; kernels use ring 0 and ring 3 only. AArch64 numbers its exception levels upward: EL0 for applications, EL1 for an OS kernel, EL2 for a hypervisor, EL3 for the secure monitor; an exception can only be taken to the same or a higher level, and each level from EL1 up has its own vector base register (VBAR_ELx) and syndrome registers (ESR_ELx, FAR_ELx, ELR_ELx). RISC-V has three modes: M (machine) for firmware, S (supervisor) for the kernel, U (user), with machine-level CSRs such as misa, mstatus and medeleg inaccessible from S-mode. M-mode firmware decides which traps it delegates to S-mode through medeleg and mideleg. D2 D3 D4

The probes ask each CPU instead of trusting these sentences. On x86, CS&3 is 0. On AArch64, CurrentEL says EL1 under -M virt and EL2 when the same image runs with virtualization=on; the arch layer then installs its vector table in VBAR_EL2 as well, and leaves through smc instead of hvc. On RISC-V there is no "current mode" register an S-mode kernel can read, so the probe tests a consequence: reading the machine-level CSR misa traps with scause 2 behind OpenSBI, and succeeds when QEMU starts the image with -bios none. OpenSBI's own banner, kept in the run record, reports "Domain0 Next Mode : S-mode" and the delegation masks it set. R1

Boot contracts

A boot contract fixes three things: the CPU state at entry, where the image is loaded, and where the hardware description is. The x86 probe uses Multiboot because QEMU's -kernel loader accepts a 32-bit Multiboot ELF directly: the image carries a 12-byte header (magic 0x1BADB002, flags, checksum), and the loader enters in 32-bit protected mode with paging off, eax = 0x2BADB002 and ebx pointing to an information structure. There is no devicetree: a PC describes itself through firmware tables (E820 or the UEFI memory map, ACPI's MADT and others, OS301 and F3-24). The AArch64 probe begins with the 64-byte arm64 Image header (a branch, a text offset, the image size, flags, the magic "ARM\x64"); QEMU then loads it at RAM base plus the text offset and passes the devicetree's physical address in x0, with x1 to x3 zero. The RISC-V probe is entered by OpenSBI, which runs in M-mode at the start of RAM and jumps to 0x80200000 in S-mode with a0 = hart ID and a1 = devicetree address. D6 D7 D5 D9 R1

Firmware services also change. A PC kernel powers off and starts CPUs through ACPI and the local APIC (INIT-SIPI-SIPI, F3-28); an AArch64 kernel calls PSCI through hvc or smc (the probe uses PSCI SYSTEM_OFF, function 0x84000008); a RISC-V S-mode kernel calls SBI with ecall (the probe uses the System Reset extension, ID 0x53525354). Each run record shows the machine exiting after that call, which is evidence that the call worked. A real kernel reads the PSCI conduit from the devicetree's /psci node (F4-24) and starts RISC-V harts through SBI HSM (F4-29). D8 D5 R1

Interrupt controllers

Row 4 of the checklist changes the most code. On the PC, each CPU has a local APIC at a fixed physical window (0xfee00000 in QEMU's memory map) and external interrupts are routed through an IOAPIC (0xfec00000); MSIs are writes into the APIC window. On QEMU's AArch64 virt machine with GICv3, a distributor at 0x8000000 routes shared peripheral interrupts and one redistributor per CPU (from 0x80a0000) handles private ones; the CPU interface is reached through system registers, not memory. On RISC-V virt, a PLIC at 0xc000000 routes external interrupts to harts and an ACLINT at 0x2000000 provides software interrupts and the machine timer; QEMU can also model the newer AIA (APLIC and IMSIC), as F4-23's variants run shows. Interrupt numbering, priority, acknowledgement and end-of-interrupt differ in every case, so the kernel's interrupt interface (Track B) must speak of "an interrupt line and a handler", never of APIC vectors. Memory ordering

Three rules matter for a port. Sequential consistency (SC) is the rule a programmer imagines: the steps of all threads interleave, each thread's steps in program order. Total store order (TSO), the x86 rule in simplified form, adds a first-in-first-out store buffer per core: a store waits in the buffer while later loads of the same core go to memory, so a later load can complete before an earlier store, and nothing else is reordered. A weakly ordered CPU may also reorder two stores, two loads, or a load and a later store, as long as they touch different addresses, unless the program forbids it. Arm and RISC-V are weakly ordered; their official models (the Arm memory model in the Arm ARM, RVWMO in the RISC-V Unprivileged manual) are more subtle than this summary. D2 D3 D4 D1

The program ordering_model.cpp turns the three rules into an enumerator and prints every outcome each rule allows for the SB and MP tests of Figure 3 (R6). TSO allows SB's (0,0) and forbids MP's (1,0); the weak rule allows both; seq_cst on SB and release/acquire on MP forbid them under every rule. That is the whole porting lesson in four lines: code that relies on MP ordering without saying so is correct on x86 and wrong on Arm and RISC-V. R6

The compiler implements C++'s memory orders differently on each CPU (R5). On x86-64, a release store and an acquire load are plain mov instructions: TSO already gives those orders, so a missing release costs nothing visible on x86, which is exactly why the bug hides there. A seq_cst store becomes xchg, the instruction that drains the store buffer. On AArch64, release becomes stlr and acquire ldar; relaxed accesses are plain str/ldr. On RISC-V, GCC brackets plain sw/lw with fences: fence rw,w before a release store, fence r,rw after an acquire load, and full fence rw,rw around seq_cst accesses. R5 D3 D4

Device registers add a second ordering problem. Writes to memory-mapped registers must reach the device in program order and after the memory writes they announce (a descriptor before the doorbell). C++ atomics order memory for other CPUs, not for devices; a driver uses the kernel's I/O accessors, which contain the architecture's barriers (dmb/dsb on Arm; fence with the I and O bits, such as fence w,o, on RISC-V). DR402's forensic lab "works on x86, corrupts on ARM" is this case. D3 D4 R10

Cache maintenance for DMA

A write-back data cache holds the newest copy of a line until it writes it back. A coherent device's accesses are checked against the caches (snooped), so it always sees the newest data. A non-coherent device sees memory only. Curriculum 11.1 states the consequence for SoCs: many devices are not coherent, so drivers clean and invalidate around DMA or use uncached buffers. The rule of thumb: before a device reads a buffer (transmit), clean the buffer's lines; before the CPU reads what a device wrote (receive), invalidate them, and do not touch them while the device owns the buffer. Buffers for non-coherent DMA must start and end on cache-line boundaries, because invalidating or writing back a line also affects whatever else lives in it. D1 D3 D13

dma_cache_model.cpp shows each rule as an outcome (R10): without a clean, the non-coherent device transmits the old bytes; without an invalidate, the CPU reads the old bytes after a receive; and when a counter shares the receive buffer's cache line, the line's later write-back destroys the device's data. cachemaint.S assembles the real instructions for each CPU. Page sizes

Curriculum 9.2 lists the AArch64 translation granules: 4, 16 and 64 KiB. The granule is chosen by the kernel among those the CPU implements, so a 64 KiB-page AArch64 kernel is as legitimate as a 4 KiB one; RISC-V Sv39 and x86-64 use 4 KiB base pages with larger leaf pages above them. Byte order

All three CPUs of this course run little-endian in this build (R3), and that is the trap: byte order is a property of each data format, not of the CPU. The devicetree blob is big-endian; ext2 and FAT on disk are little-endian; network headers are big-endian; modern virtio is little-endian even on big-endian CPUs. A little-endian kernel that reads the DTB with a pointer cast gets every number byte-swapped (the probe prints 0xedfe0dd0 for the magic on all three machines), and a correct-looking ext2 reader with a struct cast fails the day it runs on a big-endian CPU (the forensic lab, on s390x). How the hardware actually does it

Store buffers. A core does not wait for each store to reach its cache: the store enters a store buffer and the core continues. On x86 the buffer drains in program order and loads check it first for their own address, which yields TSO. Weakly ordered cores add more freedom: stores may leave the buffer out of order, loads may be satisfied early and out of order, and the coherence protocol may make a store visible to some cores before others in models without multi-copy atomicity. Barriers and acquire/release instructions limit that freedom by making the core wait (for the buffer to drain, or for earlier loads to complete). This is why a barrier costs time on Arm and RISC-V and why x86 code that "needs no barriers" is not portable. D2 D3 D4 D14

Worked example

Task. From the probe runs (R1) and the APIC trap run (R8), decode four register values by hand: x86 cr0 = 0x11, RISC-V misa = 0x80000000001411ad, AArch64 ESR = 0x96000010, and the native-order DTB magic 0xedfe0dd0.

Step 1: cr0 = 0x11. In binary, 0x11 = 0001 0001: bits 0 and 4 are set. Bit 0 is PE (protected mode enable) and bit 4 is ET; bit 31, PG (paging), is clear. So the Multiboot loader entered the probe in 32-bit protected mode without paging, as the contract promises. D2 D6

Step 2: misa = 0x80000000001411ad. The top two bits (63:62) are 10, so MXL = 2: a 64-bit hart. The low 26 bits name extensions, bit 0 = A, bit 1 = B, … bit 25 = Z. 0x1411ad = 0x100000 + 0x40000 + 0x1000 + 0x100 + 0x80 + 0x20 + 0x8 + 0x4 + 0x1, which sets bits 20, 18, 12, 8, 7, 5, 3, 2 and 0: U, S, M, I, H, F, D, C, A. Sorted, that is "ACDFHIMSU": base integer I, M, A, F, D, C, plus the hypervisor extension H, plus S-mode and U-mode support. OpenSBI's banner in R1 independently prints "Boot HART Base ISA : rv64imafdch". D4 R1

Step 3: ESR = 0x96000010. The exception class is bits 31:26: 0x96000010 >> 26 = 0x25 (0x96 = 1001 0110, the top six bits 100101 = 37 = 0x25): a data abort taken without a change of exception level. Bit 25 (IL) is 1: a 32-bit instruction. The low six bits, 0x10, are the data fault status code for a synchronous external abort: the bus refused the access, as opposed to a translation fault (the MMU is off). FAR = 0xfee00030 is the address the core code read. D3 R8

Step 4: 0xedfe0dd0. The blob's first four bytes are d0 0d fe ed (the big-endian encoding of 0xd00dfeed). A little-endian load puts the first byte in the lowest position: 0xed fe 0d d0 read from the most significant end, 0xedfe0dd0. Every number in the DTB would be byte-swapped the same way, which is why F4-23's parser reads through be32. D10 R1

Where the analogy breaks


    

  • The principal changes too. In the story only the buildings differ. In a port the CPU itself changes: different instructions, different registers, a different exception model. The arch layer is not a new set of notes about a building; it is new code in a new instruction set (Listings 3 to 8).
    • 

  • Noticeboards are not reordered by anyone. A note pinned first is on the board first. In a weakly ordered CPU, no person reorders anything: store buffers, caches and the interconnect let accesses become visible in another order, and only barriers restore it. The proposed noticeboard mapping explains the symptom, not the mechanism (Figure 3).
    • 

  • Visiting is not enough. Ms Okafor could see the three buildings. For memory ordering, looking proves little: x86 never shows MP reordering, and the emulator showed reorderings that Arm hardware forbids (R4). Only the architecture's rules, applied to your code, decide.
    • 

  • Some differences are not in any building. Byte order belongs to data formats, not to machines: three little-endian CPUs can still read big-endian devicetree numbers wrongly (R1).
    • 




Common mistakes and debugging


The four traps of this bridge come first, each with a real run; then the smaller mistakes.


Trap 1: missing barriers


Symptom. A producer/consumer path (a ring of descriptors, a flag and a buffer, a lock-free queue) works on every PC and loses or corrupts data on an Arm or RISC-V board, rarely and under load. Cause. The code relied on TSO: plain or relaxed accesses where the algorithm needs a release on the publishing store and an acquire on the consuming load (or a device barrier before a doorbell write). On x86, R5 shows release and relaxed compile to the same mov, so no x86 test can find the bug. How to find it. Review every flag, index and pointer that publishes data to another CPU or a device, and ask "which order does this rely on, and who guarantees it?". Use the model (R6) to check the pattern; run litmus-style stress tests on real hardware, not under an emulator (R4). Fix. std::atomic with release/acquire (or the kernel's ordered I/O accessors for devices); never volatile as a substitute. R4 R5 R6


Trap 2: hard-coded page sizes


Symptom. On an AArch64 kernel configured for 16 or 64 KiB pages: the frame allocator believes it has four or sixteen times too many frames, mappings start at addresses the MMU cannot map, and "page base" computations point into the middle of pages. Cause. A constant 4096 (or a shift of 12) in core code. How to find it. grep for 4096, 0x1000, 0xfff and >> 12 outside the arch layer; run the core's tests with the page size as a parameter. Fix. Ask the arch layer. The run below computes the same three answers both ways for the three AArch64 granules: R7

Trap 3: assuming an APIC


Symptom. The kernel prints its first lines on AArch64 or RISC-V, then stops; with an exception handler installed, it reports a synchronous external abort (AArch64) or a load access fault (RISC-V) at an address near 0xfee00000. Cause. Core code that reads or writes the PC's local APIC directly (timer setup, end-of-interrupt, CPU ID). How to find it. The exception report's address names the APIC window; addr2line on the pc names the core function that made the access (R8 prints probe_core.cc:67 for both faulting machines, a line inside probe_main: shared code, not an arch file). Fix. An interrupt-controller interface in the arch layer (curriculum 10.2: "your interfaces from Track B must not assume an APIC"), with APIC, GIC and PLIC drivers behind it. Trap 4: endianness of device and on-disk data


Symptom. Absurd sizes or a "bad magic" from a parser that worked elsewhere: the devicetree magic read as 0xedfe0dd0 on all three little-endian machines (R1), or an ext2 volume refused by a big-endian machine (the forensic lab, R11). Cause. A pointer cast or memcpy into a struct reads bytes in the CPU's order, not the format's. How to find it. Compare the raw bytes (od -t x1) with the value your code printed: a byte-swapped number is the signature. Test parsers on a big-endian CPU under QEMU user mode, as the forensic lab does. Fix. Named accessors (le16, le32, be32) for every field of every external format; no structs laid over external bytes. R1 R11 D1


Smaller mistakes


    

  • Assuming plain char is signed. Symptom: a loop while ((c = getchar()) != EOF) with char c never ends on AArch64 or RISC-V; byte comparisons with negative constants never match. Cause: plain char is unsigned there (R3). Fix: int for getchar results, unsigned char for bytes.
    • 

  • Installing exception vectors for one level only. Symptom: the AArch64 kernel hangs silently when started at EL2 (a board's firmware, or virtualization=on). Cause: only VBAR_EL1 set. Fix: as in Listing 4, or drop to EL1 at entry as F4-24 does.
    • 

  • Calling firmware through the wrong conduit. Symptom: PSCI calls fault or do nothing. Cause: hvc where the firmware listens on smc (the probe needed smc at EL2). Fix: read the /psci node's method (F4-24).
    • 

  • Trusting an emulator for ordering or coherence. Symptom: "tested on QEMU" code fails on hardware. Cause: QEMU's DMA is coherent and its ordering follows its host (R4). Fix: mark such tests untested on hardware and run them on a board.

  • Privilege models differ in names, number of levels and who sits above the kernel: ring 0, EL1 (or EL2), S-mode behind M-mode firmware.
    • 

  • Boot contracts differ: Multiboot or UEFI with ACPI tables on the PC; a devicetree address in x0 (AArch64) or a1 (RISC-V, with the hart ID in a0).
    • 

  • Interrupt controllers differ completely: APIC and IOAPIC, GIC, PLIC with ACLINT or AIA; core code must not know any of them.
    • 

  • x86 is strongly ordered (TSO), Arm and RISC-V weakly: release and acquire are free on x86 and real instructions elsewhere, so missing ones only show up on the weak CPUs.
    • 

  • Emulators do not reproduce a CPU's ordering or a non-coherent device; such behaviour must be reasoned from the architecture and tested on hardware.
    • 

  • Non-coherent DMA needs clean before the device reads, invalidate before the CPU reads, and buffers that own their cache lines.
    • 

  • Page size and byte order are facts of the platform and the data format, never constants of the core.
