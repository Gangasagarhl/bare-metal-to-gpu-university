Story hook

A visiting speaker arrives at the school office. The secretary never lets a visitor wander in. First she asks for a short card: "Who are you, and how much can you carry in one trip?" Then she gives the visitor a temporary badge number. Then she asks for the full CV: what talks they can give, which rooms they need, how often they want the microphone. She reads it, finds the matching kind of room ("ah, a keyboard teacher: we have a standard room for those"), assigns it, and from then on asks the visitor every ten minutes: "anything to say?" The visitor speaks only when asked.

A USB device meets a PC in exactly that way. The PC (the host) asks every question; the device answers with prepared tables called descriptors; the PC assigns an address, picks a configuration, finds a class driver it already has, and then polls the device regularly. In this chapter you write the device side of a USB keyboard, with its descriptors, its answers to standard requests, and one interrupt endpoint, and you test it against a model host that logs every packet like a protocol analyser. Then you read a broken descriptor set and find the single number that makes a PC ignore the device.

What you will be able to do

  • Describe the USB device model: host-driven transfers, endpoints, endpoint 0 control transfers with SETUP, data and status stages, and the interrupt transfer type.
  • Build the descriptor set of a HID boot keyboard (device, configuration, interface, HID class and endpoint descriptors, a report descriptor and strings) and compute wTotalLength by hand.
  • Walk through an enumeration packet by packet and explain each request, the address change and the data toggles.
  • Send key presses as boot-protocol reports and decode them on the host side.
  • Diagnose a device that enumerates but gets no driver, from a packet log.
  • Plan the hardware part of H3: which documents, which tools, what counts as a clean enumeration.
Jargon box
USB device stack
Simple words: the firmware that makes a microcontroller behave as a USB device. Analogy: the visitor's folder of prepared answers and the habit of answering only when asked. Precise: device-side software layered over the chip's USB device controller: endpoint 0 request handling (standard, class and vendor requests), descriptor storage, and class drivers (HID, CDC, mass storage) that feed data endpoints; TinyUSB is an open example. D1 D4
Control transfer (SETUP, data, status)
Simple words: a question-and-answer exchange on endpoint 0. Analogy: the secretary's form: question, the visitor's written answer, a stamp that closes the exchange. Precise: a transfer of three stages: a SETUP stage carrying an 8-byte request (bmRequestType, bRequest, wValue, wIndex, wLength), an optional data stage in the direction given by bmRequestType, and a status stage in the opposite direction with a zero-length packet. D1 R1
Device descriptor
Simple words: the 18-byte identity card of a USB device. Analogy: the visitor's short card. Precise: the first descriptor a host reads: USB version, device class, maximum packet size of endpoint 0, vendor and product IDs, device release, string indices and the number of configurations. D1 D3
Configuration descriptor and wTotalLength
Simple words: the full CV, with a number on the first line saying how long it is. Analogy: "this CV has 34 pages": if the number is wrong, the secretary stops reading early. Precise: a 9-byte header followed by all interface, class-specific and endpoint descriptors of that configuration; its wTotalLength field is the length of the whole set, which the host uses to read it in a second request. D1 R2
Endpoint
Simple words: a numbered mailbox inside the device, with a direction. Analogy: the pigeon-hole the secretary checks every ten minutes. Precise: a uniquely addressable source or sink of data in a device, identified by number and direction (bit 7 of bEndpointAddress: 1 = IN, device to host); each has a transfer type (control, interrupt, bulk, isochronous) and a maximum packet size. D1
HID (human interface device) class
Simple words: the standard way keyboards, mice and similar devices talk, so the PC needs no special driver. Analogy: "a keyboard teacher: we have a standard room for those". Precise: a USB device class (interface class 3) whose devices describe their data format in a report descriptor and send reports over an interrupt IN endpoint; operating systems ship a generic driver for it. D2
Report descriptor
Simple words: a small program-like table that tells the PC what each byte of a report means. Analogy: the legend of a map. Precise: a sequence of HID items (usage page, usage, logical minimum and maximum, report size and count, input/output/feature, collections) that defines the layout and meaning of the device's reports. D2
Boot protocol keyboard report
Simple words: the fixed 8-byte message a simple keyboard sends. Analogy: a pre-printed form even a substitute teacher can read. Precise: a report of one modifier byte (Ctrl, Shift, Alt, GUI bits), one reserved byte and six key-usage bytes, defined so that BIOS/UEFI firmware can use a keyboard without parsing report descriptors. D2 R1
Data toggle (DATA0/DATA1)
Simple words: a one-bit sequence number on each data packet. Analogy: alternating red and blue envelopes: a repeated colour means "you already have this one". Precise: data packets alternate between the DATA0 and DATA1 packet IDs per endpoint, so that a receiver can detect a retransmission after a lost handshake; a SETUP stage always uses DATA0, and the data stage of a control transfer starts with DATA1. D1

From F1-46 (HW204), used without repeating: USB host and host controller, hub, endpoint, transfer types, descriptor, enumeration, device class, SETUP packet.

The idea in pictures

Layer 1 — the kid explanation

When you plug a keyboard into a computer, the computer has never met it before. So it interviews it. "Who are you? How big are your messages?" Then it gives the keyboard a number, like a badge. Then it asks for the keyboard's full description: "I am a keyboard. I have one mailbox for key presses. Check it every few moments."

The computer already knows how to talk to keyboards, so it needs nothing new installed. From then on it keeps asking "any keys?" and the keyboard answers with a short message: which keys are down right now. When you let go, the keyboard sends "no keys down".

The keyboard never starts a conversation. It only answers. That one rule makes USB simple for the device and puts the computer in charge.

Layer 2 — the student explanation

The device side of USB

USB is host-centred: the host schedules every transaction, and a device transmits only when the host addresses one of its endpoints. D1 A device therefore does not run a protocol loop of its own; its firmware reacts to events raised by the chip's USB device controller: bus reset, a SETUP packet received on endpoint 0, an IN token for an endpoint, a transfer completed. That makes a USB stack a natural user of the interrupt patterns of F3-37: the controller's interrupt handler reads which event happened, and short handlers fill or empty endpoint buffers. D4 D5

Every device has endpoint 0, a bidirectional control endpoint used for configuration. Our keyboard adds one more: endpoint 1 IN, an interrupt endpoint. "Interrupt" in USB does not mean a hardware interrupt to the PC: it means "poll me regularly, with a bounded delay". D1

Control transfers on endpoint 0

Every configuration request is a control transfer. The host sends a SETUP packet of 8 bytes; the first request in this chapter's log is 80 06 00 01 00 00 08 00:

  • 80 = bmRequestType: bit 7 = 1 (device to host), type standard, recipient device;
  • 06 = bRequest: GET_DESCRIPTOR;
  • 00 01 = wValue, little-endian 0x0100: descriptor type 1 (device) in the high byte, index 0 in the low byte;
  • 00 00 = wIndex 0; 08 00 = wLength 8: "send at most 8 bytes". D1 R1

The device answers in the data stage, split into packets of at most its endpoint-0 packet size, and the host closes the transfer with a zero-length packet in the opposite direction (status stage). For a request without data, such as SET_ADDRESS, the device sends the zero-length status packet. A device that does not support a request answers with a STALL handshake, and well-behaved hosts carry on. D1

Read it with Figure 1 beside it. The host first asks for only 8 bytes of the device descriptor, at address 0: it does not yet know the device's endpoint-0 packet size, and byte 7 of the descriptor is exactly that (08). It then assigns address 5. Note that the status stage of SET_ADDRESS is still at address 0, and the next packet is at address 5: the device must switch address only after the status stage completes, which is why Listing 1 keeps a pendingAddress_. D1 Then come the full device descriptor (18 bytes in three packets: 8 + 8 + 2), the configuration header (9 bytes, to learn wTotalLength = 0x0022 = 34), the full configuration set (34 bytes in five packets), and a string. The host walks the configuration set, finds interface class 3 (HID) with one HID descriptor and one IN endpoint, selects configuration 1, sends the HID class request SET_IDLE, and fetches the 63-byte report descriptor. R1



Key presses


After configuration the host polls endpoint 0x81. The device answers each poll with one report if it has one, or NAK ("nothing now") if not. A boot-keyboard report has 8 bytes: modifiers, a reserved byte, then up to six key codes. The key "h" is HID usage 0x0B (keyboard usages for letters start at 0x04 for "a"), so the first report is 00 00 0b 00 00 00 00 00; the next report, all zeros, means "all keys released". Without the release report the host would see "h" held down and repeat it. D2 The model host turns the reports into the text "hi" after 47 packets in total. R1



Layer 3 — the engineer's depth


Descriptors are bytes on the wire, not C++ structs


Listing 2 starts with four static_assert lines. Three confirm that the kernel header's structs have the wire sizes (18, 9, 8). The fourth records a trap: sizeof(usb_endpoint_descriptor) is 9, but an endpoint descriptor on the wire is 7 bytes (USB_DT_ENDPOINT_SIZE). The header's struct carries two extra fields used only by audio-class endpoints. D3 R1 Firmware that sends sizeof bytes inserts two stray bytes into the configuration set, and every descriptor after them is misparsed. Listing 1 therefore appends every descriptor with an explicit wire length. The same discipline covers byte order: multi-byte fields are little-endian on the wire. The host and Cortex-M are both little-endian, so le16 is the identity here; on a big-endian core it would swap bytes, and keeping the call documents the rule (F2-24).



Reading the report descriptor


The report descriptor is a list of short items, each a prefix byte (tag, type and size) followed by 0–4 data bytes. The first items, 05 01 09 06 a1 01, read: usage page Generic Desktop, usage Keyboard, start an application collection. Then 05 07 (usage page Keyboard/Keypad), usages 0xE0 to 0xE7 (the eight modifier keys), each 1 bit, 8 of them: the modifier byte. Then one 8-bit constant field (the reserved byte), five 1-bit LED outputs plus 3 bits of padding (the output report the host sends to light Caps Lock), and six 8-bit key-code fields with usages 0 to 0x65, and c0 to end the collection. D2 The bytes in Listing 1 were written from the author's memory of the HID specification's boot-keyboard example and are in the unverified box: the model host does not parse them, so the run does not check them.



Boot protocol and report protocol


The interface descriptor declares subclass 1 (boot interface) and protocol 1 (keyboard). That promise lets simple hosts, such as PC firmware before the operating system starts, use the keyboard with the fixed 8-byte format without parsing the report descriptor; a full host parses the descriptor and may switch the device to report protocol with the HID request SET_PROTOCOL. A boot keyboard must therefore send the same 8-byte layout in both protocols, or support the switch. D2 This model does not implement SET_PROTOCOL or GET_REPORT, so it would STALL them; a real stack must answer every request that its class requires.



Polling, latency and what the model hides


The endpoint descriptor's bInterval sets the maximum polling interval; at full speed it counts frames. A key press is therefore seen by the host up to one interval late, and the device must keep the report until the host collects it. D1 The model polls instantly and has no frames, no bit timing, no CRCs, no handshake losses, and no retries, so toggle errors and timeouts cannot occur in it. It also enumerates in one fixed order; real host stacks differ (some reset the device twice, some ask for 64 bytes of the device descriptor first, some read the string descriptors early) and a device must answer any order. D1 D5



Vendor and product IDs


The device descriptor carries a vendor ID and a product ID that host software uses to choose drivers. Real products need IDs assigned through the USB organisation's process or a vendor's sub-licence; Listing 1 uses the placeholder 0xFFFF:0x0305, which this build did not check against any registry. D1 Because the keyboard is matched by its interface class (HID), not by its IDs, the generic driver binds whatever the IDs are; that is the meaning of "without a custom driver" in H3.



From the model to firmware: TinyUSB, then your own


H3 asks for the keyboard "first with TinyUSB, then with your own minimal stack". C1 TinyUSB, an open USB stack, separates a chip-specific device-controller driver from class drivers; the application supplies descriptors through callbacks and pushes reports. D4 Your own minimal stack is KeyboardDevice::setup, statusStageDone and interruptIn from Listing 1, connected to the chip's controller: the SETUP-received interrupt passes the 8 bytes to setup; the answer is copied into the endpoint-0 buffer in packets of bMaxPacketSize0; the status-complete interrupt calls statusStageDone, which is where the address register is written; and the endpoint-1 buffer is filled from interruptIn when the previous report has been collected. D5 Those connections depend on the chip's USB peripheral chapter and were not written or run here.

How the hardware actually does it


A full-speed USB link is a differential pair (D+ and D−) plus power and ground. A device announces itself and its speed by a pull-up resistor on one data line; the host's port detects it and signals a bus reset by driving both lines low for a while. D1 Inside the microcontroller, a USB device controller handles everything below the transaction: NRZI encoding and bit stuffing, the CRCs, the packet IDs, the handshakes and, for most controllers, the data toggles. It owns a small packet memory with one buffer (or two, for double buffering) per endpoint, and raises interrupts such as "reset", "SETUP received" and "transfer complete on endpoint n". D5 USB also needs an accurate clock: full speed allows only a small frequency error, which is why many chips require a crystal or a clock-recovery feature for USB; your chip's reference manual says which. D5 The model in this chapter starts above all of that, at the level of complete packets.

Where the analogy breaks


    

  • A visitor can raise a hand; a USB device cannot. Even "interrupt" endpoints wait to be polled. (USB has a remote-wakeup signal for suspended devices, a narrow exception.) D1
    • 

  • A secretary reads a CV with judgement; a host stack parses bytes. One wrong length field and it stops reading or misreads everything after it (forensic lab).
    • 

  • The interpreter in guide 8 is the driver on the PC; for a HID device, the interpreter already works at the school. The device must describe itself well enough for a generic driver; no new interpreter is hired.
    • 




Common mistakes and debugging


    

  • Symptom: the PC reports "device descriptor request failed". Cause: no answer on endpoint 0 at all: wrong clock, no pull-up, controller not enabled, wrong bMaxPacketSize0. Check: a protocol analyser shows whether the device NAKs, STALLs or is silent.
    • 

  • Symptom: enumeration fails right after SET_ADDRESS. Cause: address applied before the status stage completed. Fix: apply it in the status-complete event.
    • 

  • Symptom: the device enumerates but no driver binds, or the PC shows an unknown device. Cause: wrong wTotalLength, wrong class codes, extra bytes from sizeof on a struct, or a missing HID descriptor. Check: walk the configuration set by bLength as Listing 1 does (forensic lab).
    • 

  • Symptom: a key repeats forever. Cause: no release report. Fix: always queue the all-zeros report after a press.
    • 

  • Symptom: works with one operating system, not another. Cause: different enumeration order or an unsupported class request answered wrongly. Fix: STALL unknown requests; answer GET_DESCRIPTOR with any wLength by truncating.

Transition box

Where you came from: F1-46 showed USB from the host's side (host controller, hubs, enumeration); F3-37 taught interrupt-driven drivers on the microcontroller. What carries over: short handlers that react to controller events, ring buffers for data that waits, byte-exact layouts and the static_assert habit, testing against a known answer. What changes: the device is now the passive side of a protocol owned by someone else; correctness means answering every request the way the specification and real hosts expect, in any order; and there is a large stack between your code and the bytes. What comes next: this chapter closes the bare-metal part of the course. Bridge BR-05 follows: from one loop with handlers, to an RTOS with tasks and priorities (F3-39, F3-40), and later to Linux. A USB stack is one of the first things people move into its own RTOS task.

Safety
A USB port supplies power. On a real board, never connect the board's supply to the USB 5 V line from another source at the same time unless the board's schematic shows that this is allowed; do not short D+ or D− to a supply; use a powered hub with over-current protection between your experiments and your PC's port where possible. Use a board you are allowed to reflash and keep its recovery path (a USB bootloader in ROM, or a debug probe), because a firmware that breaks USB can also break USB-based flashing. Safety rules.

Summary


    

  • USB is host-driven; a device answers on endpoint 0 (control) and on its own endpoints, here one interrupt IN endpoint polled by the host.
    • 

  • Control transfers have SETUP, optional data and status stages; the 8-byte SETUP packet says what is wanted.
    • 

  • Enumeration: 8 bytes of the device descriptor, SET_ADDRESS (applied after status), full device descriptor, configuration header, full configuration set by wTotalLength, strings, SET_CONFIGURATION, class requests.
    • 

  • A HID boot keyboard sends 8-byte reports (modifiers, reserved, six usages) and a release report; generic drivers bind by interface class.
    • 

  • Descriptors are bytes on the wire: use explicit wire lengths, not sizeof (9 versus 7 for an endpoint).
    • 

  • One wrong wTotalLength hides the HID and endpoint descriptors and the device gets no driver.
    • 

  • H3 on real hosts, with TinyUSB and an analyser, is untested in this build.

Forensic lab answer key


Observation. The configuration header says 09 02 12 00: wTotalLength = 0x0012 = 18, instead of 0x0022 = 34. The host then requests 18 bytes and receives the configuration and interface descriptors only (8 + 8 + 2 bytes). Its walk finds one interface of class 3, but 0 HID descriptors and 0 endpoints, and it gives up: "ENUMERATION FAILED".


Hypotheses. (a) Wrong class: no, class 3 is reported. (b) Wrong packet size: no, the early transfers succeed with 8. (c) Wrong total length: yes, 18 = 9 + 9. (d) Missing descriptors: the log cannot tell the difference, because the host never asks beyond 18 bytes; the source (countClassDescriptors = false, used in Listing 1 lines 149–151) shows that the descriptors are still appended to the set but not counted. The device stores 34 bytes and announces 18.


Why the name appears. The device descriptor and the string descriptors are separate requests and are correct; the operating system lists the device, but without an interface that describes an endpoint it has nothing to bind the HID driver to.


Why unit tests passed. Each descriptor was correct on its own; only the sum in the header was wrong. Tests that do not walk the assembled set as a host does cannot see it.


Fix and prevention. Compute wTotalLength from the bytes actually appended (config_.size() after assembly) and patch it into bytes 2–3, rather than summing a separate list. Test: an enumeration test like Listing 2 in CI, plus an assertion that walking the set by bLength ends exactly at wTotalLength.


How the evidence was made. forensic.cpp builds the same KeyboardDevice with countClassDescriptors = false and runs the same model host; nothing was edited by hand.
