Story hook

The school is getting a new timetable. The old way: the caretaker wipes the board in the only classroom and starts writing the new timetable on it. Halfway through, the power goes off for the night. In the morning nobody knows what to do: the old timetable is gone and the new one is half-written. The whole school stands in the corridor.

The new way: the school has two classrooms. The new timetable is written in the empty one while the old one stays in use. Only when the new timetable is complete, and signed by the principal, does the person who unlocks the classrooms open the new room. The first day is a trial: if the classes report "all fine" by evening, the new room becomes the official one; if not, everyone goes back to the old room the next morning. A power cut can now only cost a day of preparation, never the school day itself.

In this chapter you build both ways on a model of a microcontroller's flash memory, cut the power at every single flash operation of an update, and count how many devices survive. Then you replay one night of a simulated fleet of 1,000 devices, the course's forensic case "The update that bricked half the fleet", and you build a real two-slot boot loader that runs on the emulated board.

What you will be able to do

  • Explain why erase-then-write updates of a single image can leave a device unbootable, and how A/B slots with an atomic "switch" step prevent it.
  • Implement a test-and-confirm update: write the inactive slot, mark it pending, trial-boot it once, keep it only if the application confirms.
  • Use a hash for integrity and a digital signature for authenticity, and explain what each protects against; refuse downgrades.
  • Build a boot loader that validates two slots and starts an application from a different address by moving the vector table (VTOR) and the stack pointer.
  • Prove H4's acceptance tests with a power-cut sweep and a wrong-key test.
  • Investigate a fleet incident from logs and identify the design decision that caused it.
Jargon box
Boot loader (microcontroller)
Simple words: a small program that runs first, checks the real firmware and starts it. Analogy: the person who unlocks the classroom and lets the principal in, after checking the appointment letter. Precise: firmware placed at the reset vector that selects, validates and starts an application image stored elsewhere in flash, and on many designs also installs updates; it is rarely updated itself, so its correctness matters more than any application's. D1 D3
Image slot
Simple words: a fixed area of flash that can hold one complete firmware image. Analogy: one classroom. Precise: a flash partition sized for an image (header, code and data, metadata such as signatures), addressed by the boot loader; designs have one slot (overwrite in place) or two (primary/secondary, A/B). D1
A/B update
Simple words: write the new firmware next to the old one, then switch. Analogy: prepare the second classroom while the first is in use. Precise: an update scheme with two image slots in which the running image is never modified; the new image is written to the other slot, and a small, atomic state change makes the boot loader select it. D1 R1
Test and confirm (trial boot)
Simple words: the new firmware gets one try; it must say "I'm fine" or the old one comes back. Analogy: the trial day in the new classroom. Precise: the boot loader starts a newly installed image once, marked as on trial; the image must mark itself confirmed (after self-tests) before the next reset, otherwise the boot loader reverts to the previous image. D1 R1
Cryptographic hash (SHA-256)
Simple words: a 32-byte fingerprint of data; change one bit and the fingerprint changes completely. Analogy: a seal across every page of the timetable. Precise: a function from any byte string to a fixed-size digest, designed so that finding two inputs with the same digest, or an input for a given digest, is infeasible; SHA-256 (FIPS 180-4) gives 256 bits. It detects accidental and deliberate changes, but anyone can compute it, so it does not prove who made the image. D5 R3
Digital signature (Ed25519)
Simple words: proof that the image was approved by whoever holds a secret key. Analogy: the principal's signature, which the door-keeper checks against a sample kept in the office. Precise: a value computed from the image with a private key that anyone holding the matching public key can verify, and nobody without the private key can produce; Ed25519 is one signature scheme (RFC 8032). The boot loader stores only the public key. D6 R1
Anti-rollback (downgrade protection)
Simple words: refusing to install an older version, even a correctly signed one. Analogy: last year's timetable, still signed, must not come back. Precise: a check that an image's version (or security counter) is at least a stored minimum, which is raised when a newer image is confirmed; it stops an attacker from installing an old, signed image with a known vulnerability. D1 R1
Bricked device
Simple words: a device that no longer starts and cannot fix itself. Analogy: the school standing in the corridor with no timetable. Precise: a device whose boot path finds no runnable image and offers no recovery that works in the field, so it needs physical intervention (a debug probe, a factory programmer) or replacement. R2
VTOR (vector table offset register)
Simple words: the register that tells the core where the vector table is. Analogy: moving the card on the door to the new classroom. Precise: an Armv7-M system control register at 0xE000ED08 holding the base address of the active vector table; a boot loader writes the application's table address there before jumping, so that the application's interrupts reach its own handlers. D2 R3
MCUboot
Simple words: an open-source secure boot loader for microcontrollers. Analogy: a professional door-keeper service that many schools hire. Precise: a boot loader project that validates signed images in primary and secondary slots and supports several upgrade strategies (including swapping slots with test-and-confirm, and overwrite), used with Zephyr and other RTOSes; its image format and tools are outside this build's verification. D1

The idea in pictures

Layer 1 — the kid explanation

Devices like smart thermostats get new firmware over the internet. Writing new firmware takes time, and the power can go off in the middle. If the device had only one copy and was halfway through replacing it, it would have no working program at all. It would be "bricked": as useful as a brick.

The safe way is to keep two places for firmware. The new firmware goes into the empty place while the old one keeps working. Only when the new one is completely written and checked does the device switch. If the power goes off during writing, the old firmware is still there.

The device also checks a signature, a kind of secret stamp that only the real maker can produce. Firmware without the right stamp is refused, so a stranger cannot put their own program on your device.

Layer 2 — the student explanation

Why updates are dangerous: flash

A microcontroller's flash can change bits only from 1 to 0 when programming; returning them to 1 needs an erase, and erases work on whole sectors, much larger than a program page (HW205). D4 So replacing an image is a long series of operations: erase sector, erase sector, …, program page, program page, …. Listing 1 models exactly that: a flash of 0xFF bytes, sector erase (4 KiB in the model), page program (256 bytes, an AND with the old contents), and a power cut that can stop any operation halfway, leaving a half-erased sector or a half-written page. The model's sizes are chosen for teaching; real parts have their own, in their datasheets. R1

Two designs

Single slot (SingleSlot in Listing 1): erase the only slot, write the new image, and at boot accept it if its CRC matches. Simple and small. From the first erase until the last page is written, the device holds no complete image.

A/B with test and confirm (ABSlots):

  1. The running application writes the new image into the other slot. The running slot is never touched.
  2. When the whole image is written, it writes a small state record: "the other slot is pending". This record is the single switch of the update. It exists in two copies in two different sectors, each with a sequence number and a CRC; a new record always goes to the copy that is not the newest, so a cut while writing it destroys at most the older copy, and the boot loader uses the newest valid one.
  3. At the next reset, the boot loader sees "pending", checks the new image (CRC, Ed25519 signature with its built-in public key, version not below the stored minimum), marks it "tried" and starts it once.
  4. The application runs its self-tests and calls confirm: the record now says "the new slot is active", and the minimum version is raised to the new version.
  5. If the image fails a check, it is refused. If the device resets during the trial without confirming, the boot loader sees "tried but not confirmed" and reverts to the old slot. D1 R1

The H4 acceptance tests

H4's acceptance test is: "An update with a wrong signature is refused; power loss during an update (simulated) leaves the old image running." C1 Listing 2 runs both, plus a never-confirmed image and a downgrade, then injects a power cut at each flash operation of an update in turn, for both designs:



Test 2: the image signed with "someone else's key" is written into slot B, marked pending, and refused at boot; v1 keeps running. Test 3: v2 runs once on trial; the application "crashes" before confirming; the next boot reverts to v1. Test 4: after v2 was confirmed, a correctly signed v1 is refused because the stored minimum version is now 2. The sweep is the heart of it: an A/B update is 29 flash operations, and a cut at any one of them leaves v1 running; the single-slot update is 27 operations, and a cut at any one of them bricks the device. Layer 3 — the engineer's depth


Integrity, authenticity and freshness


Three different questions, three different checks. Is the image intact? A CRC catches random damage; a cryptographic hash such as SHA-256 also catches deliberate changes, as long as the reference digest itself is trusted. Did the vendor make it? Only a signature answers that: anyone can compute a new hash for a modified image and write it into the header, as the on-target loader of Listing 6 would accept. Is it current? A signature does not expire; an old signed image with a known flaw stays valid forever unless the device refuses versions below a stored minimum. D1 D6 The host model performs all three (CRC, Ed25519, minimum version); the on-target loader performs only the integrity check with SHA-256. Making the target verify the Ed25519 signature needs a signature-verification library compiled for Cortex-M; this build did not have one and did not write one. That is the main gap between this lab and a secure boot loader, and the lab's extension. 



The hand-over to the application


Listing 6's jumpTo does three things in a fixed order: write the application's vector-table address to VTOR, execute dsb and isb so that the write takes effect before any later instruction, then load the main stack pointer from word 0 of the application's table and branch to word 1. D2 It is the reset sequence of F3-36, done by software. A production boot loader does more before jumping: disable every interrupt and peripheral it enabled (an interrupt arriving after VTOR changes would otherwise call an application handler before the application has initialised its data), clear pending interrupts, and restore the clocks to the state the application expects. D1 D3 VTOR's alignment requirements depend on the number of vectors; the 0x100 offset used here satisfies them for this table size (unverified box).



The one atomic step


Every safe update design reduces "switch to the new image" to one write that is atomic in practice: either the old record or the new record is valid afterwards, never neither. Listing 1 does it with two copies, a sequence number and a CRC (torn copies fail the CRC and are ignored). Real designs use the same ideas with different details: magic values written last, trailers at the end of a slot, or flags that can only be programmed from 1 to 0 so that a half-done write cannot set a flag back. D1 D4 The sweep in Listing 2 is the test that matters for any such design: cut the power at every operation and check that every outcome is a bootable device.



How MCUboot does it


MCUboot is the boot loader the curriculum names for H4. Its design matches this chapter's in outline: a primary and a secondary slot; images with a header, a signed hash and metadata in TLV (type-length-value) records; a host tool that signs images; upgrade strategies that either swap the slots (with test-and-confirm and revert) or overwrite the primary slot; and optional downgrade prevention with a security counter. D1 MCUboot's swap strategies copy the new image into the primary slot so that the application always runs from the same address, which is why they need extra space or extra sectors and a recovery procedure that survives a power cut in the middle of the swap. This chapter's design runs each image in place in its own slot instead, which avoids the copy but needs two builds of every image (one per slot address), as Listing 7 is built twice. D1 R3

Keys and what they cost to get wrong


The private key is the device fleet's master key: whoever holds it can install anything on every device. It belongs in a signing service or a hardware security module, never in a repository. The public key is compiled into the boot loader, so changing it requires a boot-loader update, which the boot loader itself cannot safely perform without a further mechanism; key rotation and revocation therefore have to be designed before the first device ships. D1 D3 The lab's keys are derived from fixed text seeds so that runs repeat; that is acceptable only for teaching.



How the hardware actually does it


Flash cells store charge on a floating gate; programming adds charge (bits go from 1 to 0) a page at a time, erasing removes it for a whole sector, and both take far longer than a read and need a stable supply. D4 A brown-out during an operation leaves the affected cells in an undefined state, which is what Listing 1's "half erased, half written" models. The microcontroller's flash controller exposes erase and program commands through registers, often requires the code that issues them to run from RAM (because the flash cannot be read while it is being written, on many parts), and may offer write protection for the boot-loader sectors so that application bugs cannot destroy the boot loader. D3 D7 Some chips add a hardware root of trust: a boot ROM that verifies the boot loader itself. In the emulator, slot images were placed in memory by QEMU's generic loader device; no flash controller was programmed. R3



Worked example


Task. Count the flash operations of an A/B update in Listing 1's model and find which cut is the most dangerous.


    

  1. Image size. v2 = 16-byte header + 6,200-byte payload + 64-byte signature = 6,280 bytes, as printed. R1
    2. 

  2. Erases. Sectors of 4,096 bytes: ⌈6,280 / 4,096⌉ = 2 erase operations.
    3. 

  3. Programs. Pages of 256 bytes: ⌈6,280 / 256⌉ = 25 (24 full pages = 6,144 bytes, plus 136 bytes).
    4. 

  4. State record. One erase of the record's sector plus one program: 2.
    5. 

  5. Total. 2 + 25 + 2 = 29, as printed. The single-slot update is 2 + 25 = 27 (no record). R1
    6. 

  6. The dangerous cut. For A/B, operations 1–27 touch only slot B: harmless. Operation 28 erases the sector holding the older record copy: harmless. Operation 29 programs the new record: a half-written record fails its CRC, and the older copy still says "v1 active". Every cut is harmless; the sweep confirmed all 29. For the single slot, operation 1 already destroys the only image's first sector.
    7. 

  7. A design error to avoid. If the record were a single copy erased and rewritten in place, a cut at the erase (operation 28) would leave no valid record at all. The boot loader would then fall back to its default, and whether that default is safe becomes the question. Two copies remove the question.

Where the analogy breaks


    

  • A classroom does not half-exist; a flash sector can. A power cut during an erase leaves a sector partly erased, which no analogy of rooms captures; the design must treat every partially written area as garbage, which is what CRCs and hashes are for.
    • 

  • A door-keeper can recognise a forged signature by eye; a boot loader recognises only mathematics. If the private key leaks, every forgery is perfect. Security rests on the key, not on the door-keeper's vigilance.
    • 

  • The trial day is decided by people; confirmation is decided by the application's own self-test. A new image that confirms too early (before checking that it can, for example, still download the next update) defeats the mechanism.
    • 




Common mistakes and debugging


    

  • Symptom: devices brick after a power cut during updates. Cause: erase-then-write of the only image, or a single-copy state record. Test: a cut at every flash operation (Listing 2).
    • 

  • Symptom: after an update, the application crashes on its first interrupt. Cause: VTOR not set; interrupts still go to the boot loader's table. Check: read 0xE000ED08 in the debugger.
    • 

  • Symptom: an attacker installs a modified image. Cause: only a hash or CRC is checked, or the signature does not cover the header. Fix: sign header and payload; verify in the boot loader.
    • 

  • Symptom: a buggy new version keeps running after a field failure. Cause: confirmation at the start of the application instead of after self-tests. Fix: confirm only after the application has proved it can still update.
    • 

  • Symptom: an old, vulnerable version is reinstalled. Cause: no downgrade protection. Fix: minimum version or security counter, raised on confirm.
    • 

  • Symptom: the boot loader jumps into garbage on a fresh board. Cause: erased flash (0xFF) or empty memory taken as a header. Fix: check magic, sizes and hash before reading anything else (Listing 6).
    •

Summary


    

  • Flash updates are long sequences of erases and page writes; a power cut can stop any of them halfway.
    • 

  • Single slot, erase then write: a cut at any of the 27 operations bricked the device (27 of 27).
    • 

  • A/B with test and confirm: write the other slot, flip one double-buffered state record, trial-boot once, confirm or revert: a cut at any of the 29 operations left v1 running (29 of 29).
    • 

  • Hash = integrity; signature = authenticity; minimum version = freshness. All three are needed.
    • 

  • H4: wrong signature refused and power loss survived, met in the host model; the emulated boot loader validated slots with SHA-256 and handed over with VTOR.
    • 

  • Simulated fleet: 496 of 1,000 devices bricked with the single-slot design; the same night with A/B left those 496 on v1, ready to retry, and none bricked.
    • 

  • MCUboot implements the same ideas with its own formats and strategies; all its details are unverified here.

Answers to Check yourself


    

  1. From the first erase until the last page is written, the only slot contains neither the old image nor a complete new one. The CRC then correctly says "invalid", but there is nothing valid to boot instead: detection without an alternative.
    2. 

  2. Writing the state record that marks the new slot pending. It is made atomic in effect by keeping two copies in two sectors, each with a sequence number and a CRC, and always writing the copy that is not the newest: after a cut, either the old or the new record is valid.
    3. 

  3. A hash in the header proves the payload has not changed since the hash was computed, but anyone can compute a hash for a modified payload and write it in. A signature proves that the holder of the private key approved exactly these header and payload bytes; without the key, nobody can produce a valid one.
    4. 

  4. So that the application's exceptions and interrupts use the application's own vector table. Without it, the first interrupt goes to the boot loader's handler (or its default handler), which knows nothing about the application.
    5. 

  5. One possible answer: 256 − 32 = 224 KiB for slots and records. In five years, 100 KiB × 1.15 ≈ 161 KiB, so two equal slots (A/B) of up to 112 KiB minus one or two sectors for records would not hold it; options: a compressed or delta update, or an overwrite-with-download-buffer scheme with a recovery image, or a larger part. State the trade-off: A/B is the safest but needs two full slots. Any answer that sizes slots with a growth margin and explains its failure behaviour is acceptable.
    6. 

  6. pending = 1 and tried = 1 without a later confirm: the boot loader saw a trial that never confirmed and set pending back to 0, keeping active = A.

Forensic lab answer key


Observation. Bricked devices are exactly those that started between 01:40 and 02:00: 132 + 126 + 120 + 118 = 496, 100 % of each of those windows. No device started between 02:00 and 02:10 (they waited for power and started at 02:10, which is why the 02:10–02:15 window holds 375). Devices that started after 02:10 all run v2.


Hypotheses. (a) Faulty firmware: ruled out, because 504 devices run v2 normally and the bricked ones are determined by start time alone, which has nothing to do with hardware revisions. (c) Network corruption would appear as failed checks at random times, spread over all windows; the logs show bricking only in the windows overlapping the cut, and "power lost at operation n" for each bricked sample. (b) Power cut: yes.


Root cause. A 20-minute update that started between 01:40 and 02:00 was still running at 02:00, so every such update was interrupted. With the single-slot design (erase the only image, then write), every interruption point leaves no valid image: the device is bricked, whatever the operation number (6, 9, 19 in the samples). "Half the fleet" is a coincidence of the start-time spread, not a property of the bug: the fraction is the share of devices whose update window overlapped the cut.


The replay. The same 496 devices end on v1, "update to retry": the cut stopped them before the state record was written, so the boot loader kept the untouched slot A. That is correct: the update did not complete, and the device kept working. Operations must re-push firmware 2 to these devices (and should stagger updates away from planned outages).


Why the CRC did not help. It detected the damage correctly but the design had no second image to fall back to.


Prevention. The replay changes: (1) A/B slots with a double-buffered state record, (2) signature verification, (3) test and confirm with downgrade protection. (1) alone prevents the bricking; (2) and (3) protect against malicious and faulty images, which this incident did not involve.


How the evidence was made. fleet.cc drew each device's start time from a fixed-seed generator, converted the overlap with the power cut into a flash operation number, and ran the same device model (ota.h) used in the lab. Nothing was edited by hand.
