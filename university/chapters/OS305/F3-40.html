Story hook

The science lab has one key. The youngest class borrows it for a slow experiment. Halfway through, the final-year exam group arrives: they need the lab now, and wait at the door. Nothing wrong yet; the young class will finish soon. But then the bell rings for a long assembly of the middle years, which by the timetable outranks the youngest class. The young class is sent to the assembly, still holding the key. The exam group, the most urgent people in the school, waits for the whole assembly. Their exam starts late.

The fix the school adopted is simple: whoever holds the lab key while someone more urgent is waiting gets that person's "urgent" badge until they return the key. The young class now outranks the assembly, finishes, hands back the key, and the exam group goes in. In this chapter that story happens in firmware, with a sensor task, a logger task, a long computation and one I2C bus: you measure the sensor missing its deadline, then switch priority inheritance on and measure it meeting every one. Then you map the small kernel you wrote onto the two RTOSes that the curriculum names, Zephyr and FreeRTOS.

What you will be able to do

  • Use a mutex and a message queue between RTOS tasks, and say which kernel object fits which sharing problem.
  • Explain blocking and wake-up inside a kernel: the Blocked state, wait lists and who runs next.
  • Demonstrate priority inversion on a running system and remove it with priority inheritance, with measured response times as evidence.
  • Add a sensor task with a measured deadline to an RTOS application (the course's practical exam).
  • Map uRTOS's tasks, tick, mutex and queue to Zephyr's and FreeRTOS's concepts, configuration systems and build flows, knowing which names you must still check.
Jargon box
Kernel object
Simple words: something the RTOS gives tasks to cooperate with: a mutex, a queue, a semaphore, an event flag, a timer. Analogy: the school's shared things with rules attached: the lab key, the pigeon-holes, the bell. Precise: a kernel-managed data structure with operations that may block the calling task and wake others, implemented with interrupts disabled (or a kernel lock) so its state changes are atomic with respect to the scheduler. D3 D4
Blocked state
Simple words: a task that waits for something other than time. Analogy: the exam group standing at the locked door. Precise: the scheduling state of a task waiting on a kernel object (a mutex to be released, a message to arrive); it is not eligible to run until the object's operation wakes it. In uRTOS v2: State::Blocked with waitingOn naming the object. R1
Message queue (RTOS)
Simple words: a kernel-owned mailbox of fixed-size messages between tasks. Analogy: pigeon-holes with a rule: a reader with nothing to read waits by them. Precise: a bounded FIFO of fixed-size items whose send and receive operations can block (receive when empty, send when full, depending on options) and wake the waiting task; the usual way to pass data from a producer task (or interrupt) to a consumer task without sharing variables. D3 D4
Priority inversion
Simple words: an urgent task waits for a less urgent one, and a middle task delays them both. Analogy: the exam group waits for the young class, which is stuck in the middle years' assembly. Precise: a situation in which a high-priority task is blocked on a resource held by a low-priority task, which in turn is preempted by medium-priority tasks that do not need the resource; the high-priority task's blocking time then depends on the medium tasks' execution and is unbounded in general. D1 R2
Priority inheritance
Simple words: while you hold what an urgent task needs, you become as urgent as it. Analogy: lending the young class the exam group's badge until they return the key. Precise: a mutex protocol in which the owner's effective priority is raised to the highest priority of the tasks blocked on the mutex, and restored when it unlocks; it bounds the blocking time to the length of the owner's critical section (per resource, for non-nested use). D1 R1
Devicetree (Zephyr)
Simple words: a text file that describes the board's hardware, from which Zephyr generates configuration for its drivers. Analogy: the school's building plan that every new staff member receives. Precise: a hierarchical description of hardware (nodes, compatible strings, registers, interrupts, pin assignments) in devicetree source; Zephyr compiles it at build time into C macros that drivers and applications use, the same format the Linux kernel reads at boot on many Arm systems (Track D). D3
Kconfig
Simple words: the list of on/off and number settings that choose which RTOS features are built. Analogy: the school's policy checklist: "do we run a canteen? how many classrooms?". Precise: the configuration language (from the Linux kernel) that Zephyr uses for build-time options such as enabling a subsystem or setting the tick rate; FreeRTOS uses a header, FreeRTOSConfig.h, for the same purpose. D3 D4

From SP203, used without repeating: mutex, critical section, deadlock, producer/consumer, condition variable. From F3-39: task, response time and deadline.

The idea in pictures

Layer 1 — the kid explanation

When tasks share something, like the wires to a sensor, only one may use it at a time. They take turns with a lock: take the lock, use the thing, give the lock back. A task that finds the lock taken waits.

Here is the trap. A slow, unimportant task takes the lock. An important task comes and waits for it. Then a medium task, which does not even need the lock, pushes the slow task aside because it is more important than the slow one. Now the important task is waiting for the medium task, which has nothing to do with it.

The cure: while the slow task holds a lock that an important task is waiting for, it is treated as important too. It finishes quickly, gives the lock back, and the important task goes on. Real RTOSes, like Zephyr and FreeRTOS, do this for you if you choose the right kind of lock.

Layer 2 — the student explanation

Two kernel objects

uRTOS version 2 (Listings 1 and 2) adds a third task state, Blocked, and two objects. Both are built from the same three internal helpers: irqOff/irqRestore make an operation atomic with respect to the tick and to other tasks; blockOn(object) marks the current task Blocked on an object and requests a switch; wakeOne(object) makes the most urgent task blocked on it Ready. R1

  • Mutex. lock takes it if it is free; otherwise the caller blocks and retries when woken. unlock frees it, wakes the most urgent waiter and asks the scheduler to choose again. A mutex has an owner: only the task that locked it may unlock it, which is what makes priority inheritance possible.
  • Queue. Eight 32-bit messages in a ring. send never blocks (it fails when full) so that it could also be called from an interrupt handler; receive blocks the caller while the queue is empty; tryReceive never blocks.

Use a mutex to protect a resource that must be used by one task at a time for a while (a bus, a peripheral, a data structure being updated). Use a queue to hand data from one task to another: the producer does not wait for the consumer, and the two never share a variable. Disabling interrupts is the third tool, for a few instructions only (F3-37). D3 D4

The application: a sensor task with a deadline

Listing 3 has three tasks (Figure 2):

  • sensor, priority 3, released every 5 ticks from tick 1: locks the bus mutex, reads the emulated temperature sensor over I2C with the driver of F3-37, unlocks, filters for 0.3 tick, sends the reading to the queue. Its deadline is 2 ticks after each release.
  • compute, priority 2, every 10 ticks from tick 1: 3 ticks of computation, no shared objects.
  • logger, priority 1, every 10 ticks from tick 0: prints the queued readings, then locks the bus for 1.5 ticks to write a log record to an imagined slow I2C memory.

This is the course's practical exam in miniature: "add a sensor task to an RTOS application with a measured deadline". The sensor task measures its own response time from its release to the end of its job and counts misses. C1

First run: inheritance off



Every odd-numbered sensor job takes 3.80 ticks and misses its 2-tick deadline; every even one takes 0.30 and is fine. Read the first row of the timeline with Figure 1: L runs from 0 (holding the bus from about 0.0), at tick 1 the sensor and compute are released, the sensor blocks on the mutex, and compute, more urgent than the logger, runs for three ticks (CCCC|CCCC|CCCC). Only at tick 4 does the logger finish its critical section (LL), unlock, and let the sensor run (S). The sensor was not waiting for the logger's short critical section; it was waiting for compute, a task it shares nothing with. That is priority inversion. R2 The jobs released at ticks 6 and 16 do not meet the logger in its critical section, so they take only their own 0.30 tick.



Second run: inheritance on




Now the logger, while the sensor is blocked on the mutex it owns, runs at priority 3. Compute cannot preempt it; the logger finishes its critical section at 1.5 (LLLL|LL), unlocks, its priority drops back to 1, and the sensor runs at once (S), followed by compute. Worst sensor response: 0.80 ticks, the time from its release to the end of the logger's remaining critical section plus its own work: 0.5 + 0.3. No deadline is missed. R1 The readings are 23.50 °C: the sensor was set to 23.75 °C, and this application does not configure 12-bit resolution (compare F3-37).



The same ideas in Zephyr and FreeRTOS


uRTOS's pieces have direct counterparts in both production RTOSes, as the curriculum's H4 asks ("the same functions on Zephyr (or FreeRTOS)"). C1 The concepts transfer exactly: tasks or threads with fixed priorities and preemption, a tick, sleeping until an absolute time, mutexes with priority inheritance, message queues, and interrupt-safe variants of the functions an interrupt handler may call. D3 D4 What differs is packaging. FreeRTOS is a small kernel distributed as a few C files plus a port layer per processor; you add it to your own build, configure it in FreeRTOSConfig.h, and bring your own drivers. Zephyr is a complete RTOS project with its own build system, Kconfig for features, devicetree for hardware, and a large set of drivers and subsystems; an application is a small directory built against it. Layer 3 — the engineer's depth


How long can the sensor be blocked?


With inheritance, the sensor can be blocked at most once per job for the length of one lower-priority critical section on a mutex it uses: here the logger's 1.5-tick section, of which at most 1.5 remains when the sensor arrives. The RTA of F3-39 gets a blocking term: R = C + B + interference, with B = 1.5 for the sensor. Worst case: 0.3 (own work, plus the brief bus read) + 1.5 = 1.8 < 2, met, if the sensor arrives right after the logger locked. In the lab the sensor arrived 1.0 tick into the section, so it measured 0.8. Without inheritance, B includes every medium-priority job that can run during the inversion, here compute's 3 ticks, which is why the measurement was 3.8. D1 R1 R2


A deadline that depends on the sensor's arrival phase relative to the logger is a warning: the lab's measurement, taken at one phase, is not the worst case. Measuring the worst case means arranging the worst phase on purpose (lab step 3), or using the analysis.



What uRTOS's inheritance does not handle


uRTOS v2's inheritance is the simplest correct form for one mutex at a time. It does not handle: a task holding two mutexes (on unlock it drops to its base priority even if a waiter on the other mutex still needs the boost); chains (A waits for B, which waits on another mutex held by C: C must inherit A's priority transitively); or a waiter that times out (the owner's boost should then be recomputed). Production kernels handle these cases, each in its own way. D1 D3 An alternative protocol, the priority ceiling (each mutex has a fixed priority equal to its most urgent user, and a task that locks it runs at that priority at once), prevents inversion and also some deadlocks, at the cost of knowing every user in advance. D1



Kernel objects and interrupts


An interrupt handler must never block: it has no task context to put to sleep. In uRTOS that is why Queue::send never blocks. Production RTOSes make the rule explicit: FreeRTOS offers separate "from ISR" functions, and Zephyr allows only non-blocking calls (a zero timeout) from interrupt context, according to their documentation as the author remembers it (unverified box). D3 D4 The pattern from F3-37, "the handler acknowledges and hands data on, slow work happens elsewhere", becomes "the handler sends to a queue (or gives a semaphore) and a task does the work". Bridge BR-05 lists "blocking calls inside interrupt handlers" as its first trap. C1

What the objects cost




The mutex's lock is 0x66 = 102 bytes and unlock 0x2c = 44 bytes; the whole queue about 0x48 + 0x30 + 0x70 = 280 bytes. The image grew from F3-39's 3,784 bytes of code to 4,008 including the I2C driver. Small kernels are small; their RAM cost is dominated by task stacks. R1



How the hardware actually does it


A mutex in a single-core RTOS needs no special hardware: the kernel makes its operations atomic by disabling interrupts (PRIMASK on Cortex-M) for a few instructions, which also stops the tick and therefore preemption. D2 On multicore microcontrollers (some recent parts have two cores, and Zephyr supports symmetric multiprocessing on some of them), disabling interrupts on one core does not stop the other, and kernels use spinlocks built on exclusive load/store instructions, as in F2-38. D2 D3 The I2C bus that the mutex protects is real shared hardware: if two tasks interleaved their bit-banging, the bus would see an illegal sequence and the sensor would answer garbage or hold SDA low. The mutex protects the bus transaction as a whole, from START to STOP.

Where the analogy breaks


    

  • A badge is visible to everyone; inheritance is invisible. Nothing in the code of the logger says it may run at priority 3; a timeline or a debugger is needed to see it.
    • 

  • A class can be told to hurry; a task cannot. Inheritance does not make the critical section shorter, it only stops others from stretching it. The worst case is still the whole critical section (Layer 3).
    • 

  • Two students each holding a book the other needs (guide 8's deadlock) is a different failure: inheritance does not prevent deadlock; lock ordering or the priority-ceiling protocol does (F2-40).
    • 




Common mistakes and debugging


    

  • Symptom: an urgent task misses deadlines only when a certain unrelated task is busy. Cause: priority inversion. Check: a timeline: the urgent task blocked on a lock while a medium task runs. Fix: a mutex with inheritance (not a binary semaphore, which has no owner), and short critical sections.
    • 

  • Symptom: the system freezes when an interrupt fires. Cause: a blocking call in an interrupt handler. Fix: use the interrupt-safe, non-blocking variant and defer work to a task.
    • 

  • Symptom: a queue silently loses data. Cause: send failed because the queue was full and the return value was ignored. Fix: check it, count failures, size the queue from producer and consumer rates.
    • 

  • Symptom: a priority looks reversed after moving code from FreeRTOS to Zephyr (or back). Cause: opposite numeric conventions (Table 1, unverified). Fix: define priorities by name in one header.
    • 

  • Symptom: two tasks deadlock on two mutexes. Cause: locking in different orders. Fix: one global lock order (F2-40).
    •

Summary


    

  • Kernel objects (mutex, queue) let tasks share resources and pass data; they block and wake tasks inside the kernel.
    • 

  • Priority inversion: a high-priority task waits for a lock held by a low-priority task that a medium-priority task preempts. Measured: 3.80-tick responses and 4 misses of 8.
    • 

  • Priority inheritance lends the owner the waiter's priority until unlock. Measured: worst 0.80 tick, no misses; analysed worst case 1.8 ticks.
    • 

  • Blocking adds a term B to the response-time analysis; inheritance bounds it to one critical section.
    • 

  • Handlers must not block; production RTOSes provide interrupt-safe calls.
    • 

  • Zephyr and FreeRTOS provide the same concepts; their APIs, priority conventions and build flows differ, and every name in Table 1 is unverified here.

Forensic lab answer key


Observation. The jobs released at ticks 1, 11 (and 21, 31) take 3.80 ticks and miss the 2-tick deadline; those at 6, 16, 26, 36 take 0.30. In the timeline the sensor does not appear between tick 1 and 4.5; compute runs from 1 to 4 (CCCC|CCCC|CCCC), the logger from 4 to 4.5. The build ran with "priority inheritance OFF".


Hypotheses. (a) Slow bus: the sensor's own job is 0.30 tick when it is not blocked, so no. (b) Overload: U = 0.3/5 + 3/10 + 1.5/10 + (printing) ≈ 0.06 + 0.3 + 0.15 = 0.51, far from 1, and idle time is visible in the timeline; no. (c) Yes: the sensor waits for the bus mutex held by the logger while compute, which shares nothing, runs.


Root cause. Unbounded priority inversion: the bus mutex has no priority inheritance. Timeline: 0–1 logger (locks the bus at about 0.0); 1.0 sensor and compute released, sensor blocks on the mutex, compute preempts the logger; 1–4 compute; 4–4.5 logger finishes its section and unlocks; 4.5–4.8 sensor; response 3.8.


Why every second job. The logger holds the bus only in ticks 0–1.5 of every 10; only the sensor jobs released at 1, 11, 21, 31 fall into that window. Those at 6, 16, ... find the bus free.


Fixes. (1) Configuration: use a mutex with priority inheritance (the lab's app.out shows 0.80 and no misses); ship this first, it is a one-line change with a measured effect. (2) Design: shorten the logger's critical section (chunked writes) and/or move the log memory to a different bus; this also reduces the worst-case blocking under inheritance (1.8 ticks leaves only 0.2 of margin).
