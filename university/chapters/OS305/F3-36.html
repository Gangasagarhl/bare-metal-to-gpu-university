Story hook

At six in the morning the school is dark. Amira, the caretaker, is the first to arrive. On the front door hangs a small card with two lines: where to put her coat, and which room to go to first. She follows it. In that room she unlocks a cabinet and copies the day's timetable onto the big whiteboard, wipes every other whiteboard clean, and walks the corridors switching on the lights in each room that needs them. Only then does she unlock the classroom for the day's work to begin.

A microcontroller starts every morning in exactly that way, and in this course there is nobody to do it for you: no operating system, no vendor framework, no hidden library. You write the card on the door (the vector table), the caretaker's round (the start-up code) and the plan of the building (the linker script), all in C++. At the end of this chapter the emulated chip prints a banner, blinks an LED, reports how much of its memory you used, and a debugger stops it inside its very first function. That is milestone H1 of the curriculum.

What you will be able to do

  • Build a freestanding C++ firmware image for an Armv7-M microcontroller with your own linker script, vector table and start-up code, and no vendor framework.
  • Explain what the core does at reset and what the start-up code must do before main (copy .data, zero .bss, run global constructors), and what breaks when a step is missing.
  • Report an image's flash and RAM use from the linker's symbols and from llvm-size, and check that it fits a chip's budget.
  • Drive a UART and an LED register from C++ through a small board-support layer, and confirm each register write with an emulator trace.
  • Stop the firmware in its reset handler with a debugger connected to a GDB-protocol stub (H1 acceptance), and read the vector table from memory.
  • Diagnose a firmware that "works" but whose global objects were never constructed, from symbols, disassembly and a register trace.
Jargon box
Firmware
Simple words: the program that lives permanently inside a device and runs it. Analogy: the caretaker who opens the building every morning and, in a small school, also runs the whole day. Precise: software stored in a device's non-volatile memory (flash on a microcontroller) and executed directly by its processor from reset, here without any operating system underneath it. D3
Start-up code
Simple words: the first code that runs, which prepares memory so that normal C++ works. Analogy: the caretaker's morning round before the first lesson. Precise: the reset handler and its helpers: copy initial values of .data from flash to RAM, zero .bss, run the constructors listed in .init_array, then call main. D2 D5
Constructor table (.init_array)
Simple words: a list of functions that set up global C++ objects before main. Analogy: the list of rooms whose lights must be switched on before school opens. Precise: an array of function pointers that the compiler emits in a section named .init_array, one per translation unit with dynamically initialised globals; a hosted C++ run-time calls them before main, and on bare metal your start-up code must. D4 D5 R1
Thumb bit
Simple words: the lowest bit of a code address on Cortex-M, which must be 1. Analogy: a tick on the room card that says "speak the school's language here". Precise: Armv7-M executes only the Thumb instruction set; addresses loaded into the program counter from the vector table or by a branch-and-exchange carry bit 0 = 1 to mark Thumb state, so a function at 0x84 appears as 0x85 in the vector table. D1 R1
Semihosting
Simple words: a way for firmware to ask the debugger or emulator for a service, such as "stop now and report success". Analogy: the caretaker phoning the head office from the school's single telephone. Precise: an Arm convention in which the target executes a special breakpoint (bkpt 0xab on Armv7-M) with an operation number in r0 and an argument in r1, and the host side (debugger or emulator) performs the operation; here it is used only for SYS_EXIT. D6 R1
Board support layer (BSP)
Simple words: the small file that knows the addresses of one board's devices. Analogy: the building plan pinned in the caretaker's office: which switch is which. Precise: the code that maps a specific board's peripherals (base addresses, register layouts, pin choices) to functions the application calls; vendor kits ship large ones, this course writes a minimal one (board.h). D3
Memory budget
Simple words: how much flash and RAM your program may use, and how much it does use. Analogy: the number of cupboards and desks the school has, against how many the timetable needs. Precise: flash use = code + read-only data + constructor table + the stored initial values of .data; RAM use = .data + .bss + the stack (and heap, if any); both must be at most the chip's sizes from its datasheet. D4 R1

Terms from HW303 used without repeating them: vector table, reset handler, linker script, freestanding, section, VMA and LMA.

Layer 1 — the kid explanation

A microcontroller is a whole small computer on one chip: a processor, memory that keeps your program when the power is off, memory for working, and little helpers for talking to lights, buttons and other chips. Nothing else is there. No screen, no keyboard, no operating system.

When the power comes on, the processor does one fixed thing: it reads two numbers from the very start of its memory. The first says where its scratch pad (the stack) begins. The second says where the first instruction is. Then it starts running there.

That first code has to tidy up before the real program starts: copy starting values into the working memory, clear the rest, and prepare any objects the program needs. Then it calls your program. Your program can then talk to a light by writing a number into a special memory address, and to a computer by sending letters through a serial line.

Layer 2 — the student explanation

What the core does at reset

On an Armv7-M core (Cortex-M3 and its relatives), reset is described by data, not code: the core reads word 0 of the vector table into the main stack pointer and word 1 into the program counter, then starts executing. D1 D2 No instruction has run before that, so the stack pointer is valid from the first instruction of the reset handler, and the reset handler can be an ordinary C++ function. The remaining words are the addresses of handlers for faults, system exceptions and interrupt requests, which F3-37 uses.

The debugger session of this lab shows the contract from outside. With the core held at reset, the first two words of memory are 0x20010000 and 0x00000085, and the core's registers already hold sp = 0x20010000 and pc = 0x00000084: the same address without its Thumb bit. R2

The plan of the building: the linker script

The compiler turns each source file into an object file full of sections (.text for code, .rodata for constants, .data for initialised variables, .bss for zero-initialised ones). It does not know where any of them will live. The linker script (Listing 1) tells the linker two facts about the chip, its memory regions, and one policy, which section goes where. D4 This course's script declares 256 KiB of code memory at 0x00000000 and 64 KiB of RAM at 0x20000000. Those origins come from the emulator's own memory tree, printed by its monitor:



The memory at 0 is RAM in the emulator (named ssram1); this course calls it "flash" and never writes to it from the firmware, so the image would behave the same on a chip whose code memory really is flash. The sizes were chosen to be small on purpose, so that the budget check is meaningful. R1


The script also defines symbols that the start-up code needs: where the stored .data values start in flash (__data_load), where .data and .bss are in RAM, where the constructor table begins and ends, and where the stack's top and limit are. The .data section is placed with > RAM AT > FLASH: its run address (VMA) is in RAM, its load address (LMA) is in flash. D4 An ASSERT turns "global variables have grown into the stack" into a link error instead of a mysterious crash.

Layer 3 — the engineer's depth


Which C++ works on bare metal


The build uses -ffreestanding -fno-exceptions -fno-rtti -nostdlib. Freestanding means the compiler may not assume a hosted library; the C++ standard guarantees only a small set of headers for freestanding implementations, and this toolchain's Arm target provides the C headers stdint.h and stddef.h but no C++ library headers at all, which is why the code uses uint32_t from stdint.h and builds its own number printing. D5 R1 Exceptions need an unwinder and tables; run-time type information needs type descriptors; both cost flash and need run-time support that this image does not have, so they are switched off. D3 What remains is most of the language: classes, constructors, templates, constexpr, references, namespaces, static_assert. Listing 3 uses static_assert(offsetof(UartRegs, bauddiv) == 0x10) so that a wrong register layout is a compile error, not a silent write to the wrong address.


-nostdlib also means no compiler run-time library. Two consequences appeared while writing the labs of this course: a 64-bit division generated a call to a helper function that does not exist in the image, which failed at link time, so the code keeps arithmetic in 32 bits; and a global object whose constructor only stored constants was turned by the optimiser into initialised data, with no constructor at all. That second effect is why the Led constructor in Listing 4 writes to a hardware register: a constructor with a visible side effect must run. R1



Registers, volatile and the optimiser


Every device register is reached through a volatile reference (board::reg) or a struct of volatile fields (UartRegs). Without it, the compiler may merge the two writes of an on/off pair, or read the UART's "transmit full" bit once and loop forever on the cached value. D2 volatile keeps every access and its order with respect to other volatile accesses; it does not make an access atomic, and it says nothing about ordering with interrupts, which is F3-37's topic. (See also F1-41.)



Budgets and what grows them


The linker's --gc-sections removes any section nothing refers to. The vector table and the constructor table are referenced by nobody in the program (the hardware reads one, the start-up loop walks the other by symbol), so the script wraps both in KEEP; without it the vector table vanishes and the chip boots from garbage, the forensic case of F1-74. D4 The map file shows what remains, with the size of each piece (excerpt from firmware.map.txt, saved by the lab script):




Three things are worth seeing. main() is 0x50a bytes (1,290), most of the image, because board.h's functions are inlined into it at -Os. The strings take 0x131 bytes (305). And the global led0 occupies one byte: the optimiser saw that its only member is either 0 or 1 and shrank it. Your source code is a description; the map file is what was built. R1


The stack has no automatic size check on this core: it grows down from __stack_top, and if it passes __stack_limit it silently overwrites .bss. The 4 KiB here is a reservation for the linker's ASSERT, not a protection. Armv8-M cores add a stack-limit register, and a memory protection unit can place a guard region below the stack; both are beyond this chapter. D1 D2



What a real chip adds before main


The emulated board starts with a working clock and code memory that answers at full speed. A real microcontroller adds steps the vendor's start-up file usually hides: configuring flash wait states before raising the clock, starting an oscillator and a PLL, enabling the clocks of the peripherals you use (F1-75), and deciding about the watchdog, which on some chips starts by itself and resets the chip unless the firmware feeds it. D3 D9 Which of these your chip needs, and in which order, is in its reference manual; none of it was exercised in this build.

How the hardware actually does it


On a real Cortex-M microcontroller, code memory is on-chip flash connected to the core's instruction and data buses through a bus matrix; SRAM sits on another port, and peripherals on a slower peripheral bus behind a bridge. D2 When reset is released, the core's reset logic performs two bus reads at the vector-table address (address 0 on Armv7-M unless the chip remaps it) and loads the results into the stack pointer and the program counter; this happens in hardware before the first instruction. D1 Writing a peripheral register, such as the LED word at 0x40028000, is a store instruction whose address falls in the peripheral region: the bus matrix routes it to the peripheral's bus interface, and the peripheral latches the value into a flip-flop that drives a pin (F1-41, F1-76). D2 The SysTick timer is part of the core, not a vendor peripheral: a 24-bit down-counter with a reload register, whose "counted to zero" flag the delay loop polls. D1 In the emulator all of this is C code inside QEMU; the bus is a function call and the LED is a line in a trace.

Where the analogy breaks


    

  • A caretaker can improvise; the core cannot. If the card on the door is wrong (a vector-table entry without the Thumb bit, or a stack pointer outside RAM), the core does not ask; it faults on the first instruction or the first push. D1
    • 

  • Whiteboards are blank in the morning; RAM is not. After power-on SRAM holds unpredictable values, and after a reset it still holds the previous run's values. That is why the zeroing loop exists, and why a forgotten initialiser can "work" after a warm reset and fail after a cold start. D3
    • 

  • In a small school the caretaker runs the day; in a large one she hands over. On a PC, firmware hands over to a bootloader and an operating system and stays partly resident. In this chapter nothing takes over: the firmware is the whole system until power-off.
    • 




Common mistakes and debugging


    

  • Symptom: nothing at all happens; the debugger shows a HardFault or a lockup at the first instruction. Cause: vector table missing (removed by --gc-sections), not at address 0, or reset entry without the Thumb bit. Check: memory read 0x0 must show a RAM address and an odd code address.
    • 

  • Symptom: an initialised global has a wrong value at start. Cause: .data not copied, or LOADADDR wrong. Check: stop at main and print it, as Listing 5 does.
    • 

  • Symptom: a global object is "all zeros" although its constructor sets fields. Cause: constructors not run. Check: llvm-nm shows a non-empty range between __init_array_start and __init_array_end; break on the _GLOBAL__sub_I_... function. (Forensic lab.)
    • 

  • Symptom: output stops in the middle of a word, or garbage on the serial line. Cause: wrong baud divider or clock; on hardware, also the wrong pins or a missing common ground. Fix: recompute the divider from the clock the chip really runs at (F1-75).
    • 

  • Symptom: random corruption of globals after the program grows. Cause: the stack has grown into .bss. Fix: raise __stack_size and fill the stack area with a known pattern at start to measure its high-water mark.
    • 

  • Symptom: "undefined symbol: __aeabi_uldivmod" or similar at link time. Cause: 64-bit division or other operations that need the compiler's run-time library, which -nostdlib leaves out. Fix: use 32-bit arithmetic, or link the run-time library deliberately.
    • 




Transition box

Where you came from: in HW303 you saw a microcontroller's memory map, a reset handler and a debugger from the hardware side; in SP201 you learned where C++ objects live (stack, static storage) and when their lifetime begins. What carries over: every SP201 rule about object lifetime still holds; the start-up code is the part of the language run-time that makes it true. Addresses, sections and the debugger are the same as in HW303. What changes: there is no operating system to load the program, zero its memory or call its constructors: you write that code; there is no printf, no heap and no exceptions unless you build them; and the output of a test is a UART line and an exit code rather than a terminal. What comes next: F3-37 replaces the polling loops with interrupts, adds a timer tick and an I2C driver that reads a temperature sensor (H2). Later, at bridge BR-05, the single loop of this chapter becomes a set of tasks under a scheduler.

Summary


    

  • At reset an Armv7-M core loads SP from word 0 and PC from word 1 of the vector table; no code runs before that.
    • 

  • The linker script places code and constants in flash, .data in RAM with its initial values stored in flash, .bss in RAM only, and defines the symbols the start-up code uses.
    • 

  • Start-up code copies .data, zeroes .bss, runs .init_array, then calls main; on bare metal you write it.
    • 

  • Freestanding C++ keeps classes, templates and constexpr; it drops exceptions, RTTI and the library unless you provide them.
    • 

  • Budget: flash = .text + stored .data (1,948 bytes here); RAM = .data + .bss + stack (12 + 4,096 bytes here).
    • 

  • H1 was met in emulation: banner, breakpoint in Reset_Handler (LLDB), size report; hardware is untested.
    • 

  • A missing constructor loop produces a firmware that prints normally and whose objects silently stay zero.

Answers to Check yourself


    

  1. The main stack pointer from word 0 and the program counter from word 1 of the vector table (at address 0 here). Because the stack pointer is valid before the first instruction, the reset handler can use the stack like any function. (Per the Armv7-M manual; unverified in this build, but the session shows both values loaded.)
    2. 

  2. At the breakpoint, the .data copy has run (41 from flash) but main has not yet executed ++bootCount. The report is printed after the increment.
    3. 

  3. .data variables have non-zero starting values that must survive power-off, so they are stored in flash (LMA) and copied to RAM (VMA), where the program changes them. .bss variables all start at zero, so storing their values would waste flash; the start-up code writes zeros over the range instead.
    4. 

  4. The core loads 0x84 into the PC with bit 0 = 0, which asks for the Arm (non-Thumb) state that Armv7-M does not support; the core takes a fault at once (a UsageFault escalated to HardFault on the first instruction; per the Armv7-M manual, not run in this build). Wrong answer: "it works, the address is the same" — the bit is not part of the address, it is a state flag.
    5. 

  5. Flash: 30,100 + 900 = 31,000 ≤ 32,768: fits (1,768 bytes left). RAM: 900 + 5,200 + 2,048 = 8,148 ≤ 8,192: fits, with only 44 bytes to spare, so any growth or a deeper call chain overflows. A common error is to forget the stored copy of .data in the flash sum.
    6. 

  6. With --gc-sections, the linker removes sections that nothing refers to. Code in .text is referenced from the reset handler's call chain; the vector table and the constructor table are read by hardware or walked through symbols, which the linker does not count as references.
    7. 

  7. (a) and (b) yes; (c) no. volatile keeps accesses and their order; it does not make a read-modify-write atomic with respect to interrupts (F3-37).
    8. 

  8. The link fails with the script's message "RAM overflow: .data + .bss collide with the stack": with a 64 KiB stack, __stack_limit becomes 0x20000000, below __bss_end.
    9. 



Forensic lab answer key


Root cause. broken_startup.cc no longer contains the constructor loop. The constructor table still exists (__init_array_start = 0x76c, __init_array_end = 0x770: one pointer, to _GLOBAL__sub_I_main.cc at 0x5ea), but nothing calls it; the disassembly of Reset_Handler shows only the copy and zero loops. So led0 stays as .bss left it: all zero. Its member mask_ is 0, so led0.on() writes 0, and the LED never lights. The trace has six writes, all 0x0 (no constructor write, and every "on" writes 0); the working image has seven, alternating 0 and 1. constructors = 0 in the console and exit code 1 confirm it.


Ruling out the hypotheses. Broken LED: the emulator has no LED fault, and the register received 0, not 1. .bss not zeroed: constructorsRun printed 0, and the zero loop is visible in the disassembly. .data not copied: bootCount = 42.


Why no warning. Removing a loop is valid code; the compiler cannot know that the start-up code must call .init_array. "blink 1, 2, 3" prints because printing does not depend on led0. The 40 bytes saved are the loop and its constants (1,948 → 1,908 bytes).


Fix and prevention. Restore the loop. Prevention: keep a start-up self-check like Listing 4's (a global object whose constructor sets a witness), and make the firmware signal failure visibly at boot (for example a fast LED pattern or a UART line the test rig checks); add a CI step that fails if __init_array_end > __init_array_start and the reset handler has no loop over it.


How the evidence was made. The Lab Engineer copied startup.cc to broken_startup.cc without the constructor loop and ran the same build, boot and trace steps in run.sh; nothing was edited by hand.
