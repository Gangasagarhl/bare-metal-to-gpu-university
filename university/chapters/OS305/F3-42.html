Story hook

The school office never touches the boiler. When the head teacher wants to know how warm the building is, the clerk writes a note, puts it in the caretaker's in-tray at the hatch, waits until the caretaker has picked it up, and then waits until an answer lies in the out-tray. The caretaker does the actual work: reads the boiler gauge, rings the bell, locks the doors at night.

One week a new clerk starts. To save time, she waits only until the note has gone from the in-tray, then takes whatever paper is in the out-tray. Most days the caretaker is quick and the answer is already there. Some days he is busy for a minute; the paper in the out-tray is then the answer to the previous question. The head teacher reads "boiler at 119 %" and calls the heating company.

Your laptop has a caretaker too: a small microcontroller called the Embedded Controller, with its own firmware, which owns the keyboard, the battery, the fans and the lid. The operating system talks to it through exactly such a hatch: two one-byte registers. A server has a night watchman: the BMC, a separate computer that stays on when the server is off. This chapter follows a key press and a battery reading from the EC's firmware into the operating system, talks to a model BMC, and investigates a battery indicator that shows 119 %.

What you will be able to do

  • Name the firmware that runs beside the main processor in a laptop (EC) and in a server (BMC), what each one owns, and how the host reaches it.
  • Trace a battery reading and a key press hop by hop, from the EC's firmware loop through the ACPI EC interface to the operating system's driver.
  • Explain the EC's status/command and data registers and the IBF/OBF handshake, and find a handshake bug from a trace.
  • Describe a BMC: standby power, in-band and out-of-band access, IPMI-style requests with completion codes, and why it is a security boundary.
  • Read unfamiliar firmware by building a hop map with a source for every hop: the H5 method.
Jargon box
Embedded Controller (EC)
Simple words: a small computer inside a laptop that looks after the keyboard, battery, fans and lid. Analogy: the school caretaker. Precise: a microcontroller on the motherboard with its own firmware, running whenever the board has power (including in sleep states), which scans the keyboard matrix, talks to the battery and charger over SMBus, controls fans and power sequencing, and exposes data and events to the operating system through the ACPI Embedded Controller interface. D1 C1
ACPI EC interface
Simple words: the agreed way for the operating system to ask the EC for a byte or give it one. Analogy: the hatch with an in-tray and an out-tray. Precise: a pair of one-byte I/O registers, a status/command register and a data register, with commands such as read, write and query, and status bits for "input buffer full", "output buffer full" and "event pending"; the platform's ACPI tables tell the OS where the registers are and what the EC's bytes mean. D1
IBF and OBF (input/output buffer full)
Simple words: two flags: "the EC has not yet taken your byte" and "the EC has put a byte for you". Analogy: a note still in the in-tray; a paper waiting in the out-tray. Precise: status bits that synchronise the two sides: the host must wait for IBF clear before writing and for OBF set before reading; reading the data register clears OBF. D1 R1
SCI event and query (QR_EC)
Simple words: the EC's way of saying "something happened, ask me what". Analogy: the caretaker rings the office bell; the clerk comes to the hatch and asks. Precise: the EC sets an event bit and raises a system control interrupt; the OS sends the query command, receives an event number and runs the ACPI method that the platform's tables associate with that number. D1
AML (ACPI Machine Language)
Simple words: small programs, supplied by the laptop maker, that the operating system runs to learn what the EC's bytes mean. Analogy: the instruction sheet pinned beside the hatch. Precise: bytecode in the platform's ACPI tables, interpreted by the OS; for the EC it defines fields in the EC's address space and methods such as battery status and event handlers, so the same OS driver works on laptops with different EC layouts. D1
SMBus
Simple words: a slow two-wire bus that the EC uses to talk to the battery. Analogy: the caretaker's walkie-talkie to the boiler room. Precise: the System Management Bus, a two-wire bus derived from I2C with defined transactions and timeouts; smart batteries report remaining capacity, full capacity, voltage and more over it. D3
BMC (baseboard management controller)
Simple words: a separate small computer on a server's main board that can switch the server on and off and watch its health, even when the server is off. Analogy: the night watchman with his own keys and phone line. Precise: a system-on-chip with its own processor, memory, firmware and network port, powered from standby power, that controls host power, reads sensors, drives fans, logs events and offers a remote console; reachable from the host (in band) and over the network (out of band). D4 C1
IPMI
Simple words: an older standard set of messages for talking to a BMC. Analogy: the watchman's fixed list of radio codes. Precise: the Intelligent Platform Management Interface: request messages with a network function (netfn) and command number plus data, answered by a response with netfn + 1, the same command, a completion code and data; carried in band (for example the KCS interface) or out of band over the LAN. D4 D5
Redfish
Simple words: the newer way to manage servers, over the same web technology browsers use. Analogy: the watchman now also answers e-mail with a fixed form. Precise: a DMTF standard for management over HTTPS with JSON resources, which many BMCs offer beside or instead of IPMI. D6
Out-of-band management
Simple words: managing a machine through a path that does not need the machine's own operating system. Analogy: phoning the watchman instead of the school office. Precise: access to a management controller over its own network port or a dedicated channel, independent of host power and host software; it works on a crashed or powered-off host, and it is also an attack surface that bypasses the host's defences. D4

From earlier chapters: polling (HW204), I2C transactions (F3-37), interrupts and their acknowledgement (F3-37).

The idea in pictures

Layer 1 — the kid explanation

Your laptop has more than one computer inside. Besides the big processor that runs your programs, there is a tiny one that is always awake, even when the laptop sleeps. It notices when you press a key, checks how full the battery is, turns the fan on when things get warm and wakes the laptop when you open the lid.

The big processor asks the tiny one questions through a very small window: one number at a time. It must wait politely: first until the tiny computer has taken the question, then until the answer is there. If it grabs too early, it gets an old answer, and the battery might show 119 %.

Big servers in data centres have a helper computer too, called a BMC. It has its own network cable, so a person far away can switch the server on, see how hot it is, or restart it when it is stuck.

Layer 2 — the student explanation

The EC's firmware loop

An EC is a microcontroller running firmware of the kind you wrote in F3-36 to F3-40: a main loop or a small RTOS, interrupts, bus drivers. Listing 1 models one: on every pass it scans the keyboard matrix (a key must be seen in three consecutive scans before it counts: debouncing), every 100 passes it reads the battery's remaining and full capacity over SMBus into its own RAM, and when the host has written a byte it serves the host interface, on some passes but not every pass, because the firmware has other work. D2 R1 The curriculum names the Chromium EC project as open EC firmware to read; its real structure (tasks, host commands, board files) is the subject of the lab's reading part and is not described from memory here. C1 D2

A battery reading, hop by hop

The operating system's battery driver does not know where this laptop's EC keeps the battery numbers. The laptop maker's ACPI tables say so: AML code describes fields in the EC's address space and battery methods that read them. When the AML needs a byte, the OS's EC driver performs one read transaction on the two registers: wait until IBF is clear, write the read command (RD_EC, 0x80) to the command register, wait until IBF is clear, write the address to the data register, wait until OBF is set, read the data register. A 16-bit value takes two transactions: D1 R1



Read the trace: 224 + 121 × 256 = 31,200 mWh remaining of 48,000 mWh: 65 %. Between writing the address (t=203) and reading the data (t=210), the EC needed seven passes of its loop; a driver that read at once would have got the old byte. The last line is the model's stress test: 1,000 reads with the correct handshake, none wrong. R1



A key press, hop by hop


A key press does not travel through the ACPI EC registers at all. The EC's scan finds the key, debounces it (here at t=234, three passes after the press), converts row and column into a scan code and puts it into the keyboard port, raising the keyboard interrupt; the OS's keyboard driver takes it from there, as if a separate keyboard controller were attached. In the model the scan code is 0x10 + row × 16 + column, 53 for row 2, column 5; real scan codes come from the keyboard's scan-code set and the EC firmware's key table. R1 D1



Events: the lid


For changes the OS did not ask about (lid closed, AC adapter plugged in, battery low), the EC sets SCI_EVT in its status register and raises a system control interrupt. The OS sends the query command (QR_EC, 0x84) and receives an event number, here 0x51; the platform's AML defines a method for each number, conventionally named after it (_Q51), which tells the OS what happened. In the output, the status register reads 0x20: bit 5, SCI_EVT. D1 R1



The server's BMC


A BMC is a whole computer, with an Arm processor, memory, flash and a network port; open BMC firmware (OpenBMC) is a Linux distribution. D4 C1 Listing 3 models the part the host and the administrator see: IPMI-style requests.




With the host off, the administrator asks for the device identity over the LAN; the BMC answers, because it runs on standby power. A Chassis Control request powers the host on. From the running host, the OS reads the CPU temperature in band through KCS. The response's network function is the request's plus one (0x06 → 0x07, 0x04 → 0x05), and every response carries a completion code: 0x00 success, 0xC1 "invalid command" (both taken from the Linux IPMI header in the build container), 0xCB for a sensor that does not exist (recalled, unverified). Meanwhile the BMC runs its own control loop: after ten passes with the host on, the CPU is at 60 °C and the BMC has raised the fan to 2,700 rpm, without any request from the host. R3 D5



Layer 3 — the engineer's depth


Why a separate controller at all


The keyboard, the power button and the battery charger must work when the main processor is off, asleep or crashed: pressing the power button is how the main processor gets turned on. So these jobs go to a small, always-powered microcontroller with its own firmware, which also sequences the main power rails. D1 D2 The ACPI EC interface is deliberately minimal (two byte registers, three commands) so that one OS driver serves every laptop, and the board-specific meaning lives in AML supplied with the board. The price is speed: every byte costs several register accesses and waits, which is acceptable for battery levels read every few seconds and the reason fast paths (the keyboard) use other channels. D1



Handshakes and the meaning of a status bit


The two flags answer different questions. IBF clear: "the EC has taken the last byte you wrote; you may write another". OBF set: "a byte for you is in the data register". After the address byte, IBF clears as soon as the EC's firmware picks the byte up, which may be before it has produced the answer. Listing 1 models that: in a quarter of reads the result is delayed by one or two passes (lines 111–117). A driver that waits for the wrong flag works on most reads and fails when the EC is busy, which makes the bug rare, load-dependent and hard to reproduce: the shape of most driver bugs at hardware boundaries. R1 R2 Real EC drivers add timeouts (an EC that never answers must not hang the OS), may use the EC's interrupt instead of polling, and serialise all transactions, because the two registers are shared by every user. D1



The BMC as a security boundary


A BMC can power the host on and off, mount virtual media, show the console and update the host's firmware, independently of the host's operating system. Whoever controls the BMC controls the server; and the BMC is reachable over a network. Management ports therefore go on a separate, restricted network, default credentials must be changed, and the BMC's own firmware needs the signed, verified update path of F3-41. D4 D6 In band, the host OS reaches the BMC through a small register interface (KCS: keyboard controller style, named after the same keyboard-controller heritage as the EC) or over SMBus (SSIF); out of band, through IPMI over LAN or Redfish over HTTPS. Redfish replaces IPMI's numeric commands with a tree of JSON resources (systems, chassis, managers), which is easier to extend and to secure with standard web practice. D5 D6


The emulator used in this course can model BMC chips: QEMU 8.2.2 lists 24 BMC machines (output in the lab). Booting a BMC firmware image on one of them is the next step for a learner who wants to read OpenBMC running; this build had no image and did not do it. R4

How the hardware actually does it


On a PC, the EC's two registers appear to the main processor as two I/O ports on the low-pin-count or eSPI bus between the chipset and the EC; the EC's firmware sees the other side as a peripheral with its own interrupt: "the host wrote a byte". D1 D2 The battery pack contains its own gauge chip that answers SMBus transactions; the EC is the SMBus master. D3 The keyboard matrix is a grid of row and column wires: the EC drives one column at a time and reads the rows, the scanning you could build with F3-37's timer and GPIO. A BMC is a separate chip with its own DRAM and flash, connected to the host by a low-speed bus for KCS, often by PCIe for video, and by its own Ethernet port or a shared one. D4 All of this is described here from sources not opened during the build; none of it was observed on a real board. The models of Listings 1–3 run on the build machine's processor, not on a microcontroller.



Worked example


Task. Turn the first two transactions of the battery trace into the percentage the user sees, and count the register accesses.


    

  1. Low byte. Transaction 1 reads address 0x10: the data register gives 224 = 0xE0. R1
    2. 

  2. High byte. Transaction 2 reads address 0x11: 121 = 0x79.
    3. 

  3. Combine. 0x79E0 = 121 × 256 + 224 = 31,200 mWh, the value the model's battery reported over SMBus.
    4. 

  4. Full capacity. Two more transactions (not printed) give 48,000 mWh = 0xBB80: bytes 0x80 = 128 and 0xBB = 187.
    5. 

  5. Percentage. 31,200 × 100 / 48,000 = 65 % (integer division, as printed).
    6. 

  6. Cost. Each transaction is 3 register writes or reads plus at least 3 status polls; one percentage needs 4 transactions: 12 data accesses and, in this run, dozens of status reads. That is why the EC interface is used for slow data only.
    7. 

  7. Sensitivity. If the high byte of the remaining capacity were wrongly 224 (the low byte read twice), the value would be 0xE0E0 = 57,568 and the percentage 119 %. Keep this number: it appears in the forensic lab.
    8.

Where the analogy breaks


    

  • A caretaker reads the note and decides; the EC follows its firmware exactly. It never guesses what the OS meant; a malformed transaction gives a wrong answer, not a question back.
    • 

  • The hatch is shared by everyone in the office. In the analogy each clerk can see who is at the hatch; in the OS, two threads using the EC registers at once corrupt each other's transactions unless the driver serialises them.
    • 

  • A night watchman can be trusted or not; a BMC is software with bugs. It needs updates, and its network port is an entry point into the whole server.
    • 




Common mistakes and debugging


    

  • Symptom: occasional absurd values (119 %, 174 %) from the EC. Cause: reading before OBF is set, or two transactions interleaved. Check: trace the handshake; compare with the order in Listing 1.
    • 

  • Symptom: the OS hangs while reading the battery. Cause: polling a status bit with no timeout on an EC that stopped answering. Fix: a timeout and an error path.
    • 

  • Symptom: lid or AC events are missed. Cause: the SCI is acknowledged without sending the query, or only one event is queried when several are queued. Fix: query until SCI_EVT clears (Listing 1, line 102).
    • 

  • Symptom: a BMC command "does nothing". Cause: the completion code was not checked. Fix: treat every non-zero completion code as an error and print it.
    • 

  • Symptom: a management port reachable from the general network. Cause: deployment, not code. Fix: a separate management network, changed credentials, signed BMC firmware.

Summary


    

  • A laptop's EC and a server's BMC are separate processors with their own firmware, powered when the host is off.
    • 

  • The OS reaches the EC through two byte registers: wait IBF clear, write command, wait IBF clear, write address, wait OBF set, read data.
    • 

  • Battery readings go EC RAM → EC registers → OS EC driver → AML battery method → battery driver; key presses go EC scan → keyboard port → keyboard driver; events go SCI → query → AML _Qxx.
    • 

  • In the model, the correct handshake gave 0 wrong reads in 1,000; a driver that waits for IBF only showed 119 %, 174 %, 94 %, 64 %.
    • 

  • A BMC answers IPMI-style requests in band and out of band, runs its own control loops, and is a security boundary.
    • 

  • H5 is built here on a model; naming real source files and specification sections is still open.

Forensic lab answer key


Observation. 20 readings: 65 % five times, 94 % eight times, 64 % three times, 119 % three times, 174 % once (count them in the output; the true value, 65 %, is present). The trace: "write address" at t=524, "read data register" at t=526, two passes later, and the second read follows its address after one pass; in ec_sim.out the correct driver waited seven passes (t=203 → t=210). The second byte read is 224, the same as the first.


Hypotheses. (a) A faulty gauge would give wrong but plausible values, and the EC's RAM would hold them; the values here are combinations of the correct bytes 224, 121, 128 and 187. (b) The EC firmware was not changed, and the same EC model with the old driver read 1,000 values correctly. (c) Fits: the driver reads before the EC has produced the byte.


119 %. The high byte of the remaining capacity was the stale low byte 224: 0xE0E0 = 57,568 mWh; 57,568 × 100 / 48,000 = 119. Similarly 94 %: the high byte of the full capacity was the stale low byte 128, 0x8080 = 32,896, and 31,200 × 100 / 32,896 = 94. 64 %: the low byte of the remaining capacity was the stale 187 from the previous reading's last byte, 0x79BB = 31,163, 64 %. 174 % is consistent with the remaining capacity's bytes both arriving one transaction late (121, then 224: 0xE079 = 57,465) and the full capacity's high byte stale (32,896): 57,465 × 100 / 32,896 = 174; its trace was not printed, so this is an inference, not an observation.


The bug and the fix. Listing 1, line 155: waitIbfClear() where the read must wait for OBF (waitObfSet(), line 153). IBF clear means the EC has taken the address, not that the answer is ready. Fix: wait for OBF, with a timeout.


Why it passed tests. When the EC answers in the same pass that it takes the address, the two conditions coincide and the bad driver reads correctly (question 7). In the model, three quarters of reads are like that; a test against an idle EC, or with few reads, sees nothing wrong.


How the evidence was made. forensic.cpp runs the EC model of Listing 1 with the driver option that waits for IBF only, prints the percentage every 30 simulated seconds, and keeps the trace of the first reading that is not 65 %. Nothing was edited by hand.
