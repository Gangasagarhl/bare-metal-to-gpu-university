Story hook

Amira, the caretaker, used to walk to the front door every few minutes to see whether anyone was waiting. She spent most of her day walking, and still made visitors wait. Now the school has doorbells: one at the front door, one at the delivery gate, one at the kitchen. When a bell rings, a light comes on in the office panel showing which door. She finishes the sentence she is writing, notes where she was, answers that door, switches the light off, and returns to her sentence.

A microcontroller works the same way. Peripherals ring bells called interrupts; an interrupt controller lights the right lamp and decides which bell is answered first; the core saves its place, runs a short handler, and goes back. In this chapter you replace the polling loops of F3-36 with interrupts for a timer and a serial port, write an I2C driver, and read a temperature sensor whose value you set yourself, so you know what the right answer is. You will also see two classic interrupt bugs happen in front of you: a bell that rings forever because nobody switches its light off, and a visitor left outside because the light was switched off at the wrong moment.

What you will be able to do

  • Trace an interrupt from the device through the NVIC and the core to the handler and back, naming each enable, pending and acknowledge step.
  • Measure which interrupt line a peripheral uses, instead of trusting a table, and connect IRQ numbers to exception numbers and vector-table slots.
  • Write interrupt handlers that acknowledge the device in the right order, and share data with main safely through a single-producer, single-consumer ring buffer.
  • Implement an I2C controller driver (START, address, read/write bit, ACK, repeated START, STOP) and test it twice: against a simulated bus with a logic-analyser check, and against an emulated sensor.
  • Verify a sensor reading against a known value, and explain what a real logic-analyser timing check would add.
  • Diagnose an interrupt storm and a lost interrupt from traces and console output.
Jargon box
NVIC (Nested Vectored Interrupt Controller)
Simple words: the interrupt controller built into every Cortex-M core. Analogy: the office panel of lamps, one per doorbell, with a rule for which lamp wins. Precise: the Armv7-M interrupt controller, memory-mapped from 0xE000E100, with per-line enable (ISER/ICER), pending (ISPR/ICPR), active and priority registers; it presents the highest-priority pending enabled interrupt to the core, which fetches the handler address from the vector table ("vectored") and may pre-empt a lower-priority handler ("nested"). D1 D2
Exception number and IRQ number
Simple words: two ways of counting the same interrupt. Analogy: room 24 on the school plan is "the eighth classroom". Precise: on Armv7-M, exception numbers 1–15 are the core's own (reset, faults, SVCall, PendSV, SysTick) and external interrupt n has exception number 16 + n, which is also its vector-table word index; the active exception number is readable in the IPSR register. D1 R1
Acknowledge (clear at the source)
Simple words: telling the device "I have seen your interrupt" so it stops asking. Analogy: switching off the doorbell's lamp after opening the door. Precise: a write to the peripheral's interrupt-clear register (often write-1-to-clear) that de-asserts its interrupt request; on a level-sensitive line, a handler that returns without it is entered again at once. D2 R3
Interrupt storm
Simple words: an interrupt that fires again and again so fast that nothing else runs. Analogy: a doorbell stuck down: the caretaker never gets back to her desk. Precise: a condition in which an interrupt source stays asserted (for example, never acknowledged) so the core re-enters its handler continuously and lower-priority code, including main, is starved. R3
Lost interrupt
Simple words: an event that happened but whose interrupt never ran its handler. Analogy: the caretaker switches off the lamp after closing the door, at the very moment a second visitor rings: that ring is erased. Precise: a race in which a new event's pending flag is cleared by software that meant to clear an older one, or arrives while the source is masked and is not latched; the data waits, but no interrupt announces it. R4
Ring buffer (SPSC)
Simple words: a circular queue between one writer and one reader. Analogy: a pigeon-hole rack by the door: the caretaker puts letters in, the teacher takes them out, each moving only their own marker. Precise: a fixed array with a head index written only by the producer (here the interrupt handler) and a tail index written only by the consumer (here main); with single-word index stores and correct ordering of data and index, it needs no lock on a single core. D3 D4
I2C transaction
Simple words: one conversation on the two-wire bus, from "start" to "stop". Analogy: knocking, saying the room number and "I want to tell you" or "I want to ask you", then talking, with a nod after every sentence. Precise: a START condition (SDA falls while SCL is high), a byte of 7-bit address plus R/W bit, an ACK bit from the addressed target, data bytes each followed by ACK or NACK, optionally a repeated START to change direction, and a STOP (SDA rises while SCL is high). D5 R2
Repeated START
Simple words: starting a new conversation without letting go of the bus. Analogy: "and now a question" without leaving the room. Precise: a START condition sent instead of a STOP, so that the controller keeps the bus while switching from writing a register pointer to reading that register. D5
Bit-banging
Simple words: making a bus protocol by switching pins in software. Analogy: tapping Morse code by hand instead of using a telegraph machine. Precise: driving and sampling the lines of a serial protocol directly from software through GPIO-like registers, so timing is set by the code; the alternative is a dedicated controller peripheral that generates the waveform. D3

From HW204, used without repeating: interrupt, interrupt handler, pending, masked, in service, edge- and level-triggered, I2C, open-drain, ACK and NACK, write-1-to-clear.

Layer 1 — the kid explanation

Imagine waiting for a friend by looking out of the window every minute. You get nothing else done. A doorbell is better: you do your homework, and when it rings, you go to the door. An interrupt is a doorbell for the processor. A timer can ring it a hundred times a second, a serial port can ring it when a letter arrives.

When the bell rings, the processor marks its place, runs a small piece of code called a handler, and goes back to what it was doing. The handler must do one important thing: tell the device "I heard you". If it forgets, the bell keeps ringing and the processor never gets back to its homework.

I2C is a way for one chip to talk to many small chips over only two wires. Each small chip has a number, its address. The main chip says the number, asks a question ("what is the temperature?"), and the small chip answers, one bit at a time, while the main chip keeps the beat on the clock wire.

Layer 2 — the student explanation

Which bell is which: measuring the IRQ map

Every interrupt-capable peripheral is wired to one input of the NVIC, its IRQ number. The chip's reference manual has a table of them. This course measures them instead, because a wrong line in a table produces an interrupt that never arrives. Listing 2 enables all 16 lines, defines all 16 handlers as one shared function that reads the active exception number from the IPSR register, and then makes each peripheral raise its interrupt in turn. D1



Timer 0 is IRQ 8 and the UART's receive interrupt is IRQ 0 on this emulated board. External interrupt n is exception 16 + n, so the timer's handler address sits in vector-table word 24 and the UART's in word 16: Irq8_Handler and Irq0_Handler in F3-36's start-up file. R1



Three switches must all be on


An interrupt reaches its handler only if three enables agree: the peripheral's own interrupt-enable bit (the timer's CTRL bit 3, the UART's CTRL bit 3 for receive), the NVIC line's enable bit (a write of 1 << n to ISER0 at 0xE000E100), and the core's global mask (interrupts are enabled after reset unless software sets PRIMASK). D1 D6 "My interrupt never fires" means one of these three is off, or the handler's name does not match its vector (F1-77). Listing 3, lines 119–124, turns on all three for both devices.



Two handlers and a buffer


The timer handler (lines 97–101) acknowledges the timer by writing 1 to its INTCLEAR register, then increments ticks. main uses ticks to wait: "wait until ticks has grown by 10", sleeping with wfi between interrupts so the core does nothing while it waits.


The UART receive handler (lines 103–112) clears the UART's receive-interrupt flag, then moves every waiting byte into a 16-byte ring buffer. main takes bytes out and executes them as commands: s scans the I2C bus, r reads the temperature, c sets 12-bit resolution, w waits ten ticks, t prints the tick count, q quits. The handler never prints and never talks to I2C: it does the minimum and leaves the slow work to main. D3


The ring buffer is safe without a lock because each index has one writer: only the handler writes head_, only main writes tail_, and each is a single aligned 32-bit store, which the core performs in one access. The data byte is written before the index that publishes it; the empty asm volatile("" ::: "memory") statements stop the compiler from moving the plain buffer accesses across the volatile index accesses, which volatile alone does not forbid. D4 D3 On a single core with no data cache, that is enough; with two cores you need atomics with acquire and release ordering (F2-38).



The I2C driver


I2C has two lines, SCL (clock) and SDA (data), both open-drain with pull-up resistors: any device can pull a line low, nobody drives it high (F1-47). Data may change only while SCL is low; a change of SDA while SCL is high is a control signal, START when SDA falls and STOP when it rises. Layer 3 — the engineer's depth


What the core does on entry and return


On Armv7-M, interrupt entry is done by hardware: the core pushes r0–r3, r12, LR, PC and xPSR onto the current stack (the registers a C function may change), loads the handler address from the vector table, writes a special EXC_RETURN value into LR, and starts the handler. D1 D2 That is why a handler can be a plain C++ function with no special attribute: the procedure-call standard's caller-saved registers are already saved, and the function's own prologue saves the rest if it uses them. When the handler returns by branching to EXC_RETURN, the core recognises the value, pops the eight registers and resumes. If another interrupt is pending at that moment, the core can go straight to its handler without popping and pushing again (tail-chaining). D2 F1-77 showed these values inside a SysTick handler in a debugger.



Priorities and nesting


Each interrupt has a priority; on Cortex-M a smaller number means more urgent. A pending interrupt pre-empts the running handler only if its priority is strictly more urgent; equal priorities wait their turn, which makes handlers of equal priority mutually exclusive. D1 How many priority bits exist is chosen by the chip designer (the unused low bits read as zero), so code should use the CMSIS-style "shift into the top bits" convention rather than raw small numbers. D2 D6 This chapter leaves all priorities at their reset value 0. F3-39 sets SysTick and PendSV priorities on purpose; there the order matters.



Acknowledge order and the lost interrupt


The first version of this lab's UART handler drained the receive buffer and then cleared the receive-interrupt flag. It worked in most runs. In some, the console stopped answering in the middle of the command string. The evidence (app_race.cc, run many times in a row):




The sequence is: the handler reads the last waiting byte; the loop finds the buffer empty; a new byte arrives and sets the flag; the handler then clears the flag, erasing the new byte's announcement. The byte sits in the UART, no interrupt will ever report it, and because this UART holds one byte, the next byte cannot arrive either. main sleeps in wfi forever. (The "0.00 C" in that output is not part of the bug: the race runs do not set the sensor's temperature.) R4 The fix in Listing 3 is the order: clear the flag first, then drain. A byte arriving after the clear sets the flag again and the handler runs once more; a byte arriving before the clear is found by the drain loop. The rule generalises: acknowledge, then service, then re-check. During development of this lab, batches of 20 runs of the old handler stopped between 0 and 8 times. Races hide; run a suspected race many times and count. R4


Watch out
On a real chip the write that clears a device's flag travels through the bus and may complete after the handler has already returned, so the core sees the old request still asserted and enters the handler a second time. The common remedy is a data synchronisation barrier (dsb) after the clearing write, or a read-back of the register. The emulator completes writes at once, so this effect cannot be seen here. Check your chip's documentation before relying on either remedy. D2



Sharing anything bigger than one word


ticks = ticks + 1 in a handler is safe because only the handler writes ticks. If main also wrote it, its load–add–store could be interrupted between the load and the store, and the handler's increment would be lost (the lost update of F2-35, with an interrupt in place of a second thread). The tools are: disable interrupts around the critical section (cpsid i / cpsie i, or better, save and restore PRIMASK so the code nests); Armv7-M's exclusive load/store instructions, which std::atomic uses; or a design with one writer per variable, as in the ring buffer. D1 D4 Disabling interrupts adds latency to every interrupt in the system, so keep such sections to a few instructions.



What the bit-banged driver leaves out


Listing 1 is correct for the emulated bus, which has no timing. A real bus adds four things the driver does not handle yet. Timing: each half-period must respect the minimum high and low times and the set-up and hold times for the chosen speed (the wait() hook is where they go). Clock stretching: a target may hold SCL low to make the controller wait, so after releasing SCL the controller must wait until SCL really is high. Arbitration: with two controllers, one may lose the bus. Bus recovery: a target reset in the middle of a byte can hold SDA low forever; the usual cure is clocking SCL until SDA is released, then sending STOP. D5 Most microcontrollers also have an I2C controller peripheral that generates the waveform in hardware and raises interrupts per byte; a driver for it is a state machine driven by those interrupts. How the hardware actually does it


A peripheral's interrupt output is a wire into the NVIC. The NVIC samples each line every core clock; on Cortex-M a line held high keeps its interrupt pending, and a short pulse also sets the pending bit, which stays set until the handler starts or software clears it. D1 A priority comparator picks the most urgent pending enabled line and compares it with the current execution priority; if it wins, the core's exception logic stacks registers on the bus while fetching the vector in parallel, so the handler's first instruction runs a small, fixed number of cycles after the request, given in the core's technical reference manual. D2 On the I2C side, each line is a wire with a pull-up resistor; a device "outputs 0" by turning on a transistor to ground and "outputs 1" by turning it off. Rise time therefore depends on the resistor and the wire's capacitance, which is why a bus that works on the bench fails with a long cable, and why the specification bounds the bus capacitance. D5 In the emulator the NVIC is a C model, the I2C bus is a function call per byte, and the "wires" have no capacitance at all.

Where the analogy breaks


    

  • A caretaker hears a doorbell once; a level-sensitive interrupt "rings" as long as the device's flag is set. Acknowledging is not courtesy, it is what stops the ringing (forensic lab). D1
    • 

  • The caretaker decides calmly which door to answer; the NVIC decides in hardware within cycles, by number only. It knows nothing about which job matters more today; you encode that once in priority registers.
    • 

  • A visitor who is not answered rings again; a lost interrupt does not. If the flag is cleared at the wrong moment, the device waits silently forever (Layer 3). R4
    • 




Common mistakes and debugging


    

  • Symptom: the interrupt never fires. Cause: one of the three enables is off, the IRQ number is wrong, or the handler's name does not match the vector. Check: read the peripheral's flag (it should be set), the NVIC pending register (set?) and enable register, and the vector-table word 16 + n in the debugger.
    • 

  • Symptom: main stops making progress as soon as interrupts are on. Cause: a handler that does not acknowledge its device. Check: break in the handler; if it hits again immediately after returning, it is a storm (forensic lab).
    • 

  • Symptom: received characters go missing or the console freezes under load. Cause: clearing the flag after draining (lost interrupt), a buffer that is too small, or a handler that does slow work. Check: count dropped bytes, as Listing 3 does; run the test many times.
    • 

  • Symptom: every I2C transfer NACKs. Cause: the 8-bit address passed as 7-bit, missing pull-ups on a real board, wrong pins. Check: scan the bus; on hardware, measure that idle SCL and SDA are high.
    • 

  • Symptom: the temperature is plausible but steps in 0.5 °C. Cause: the sensor's power-on resolution. Fix: configure it, and verify by reading back the configuration register.
    • 

  • Symptom: a variable shared with a handler "never changes" in main. Cause: not volatile (or not atomic), so the compiler kept it in a register.
    •

Summary


    

  • An interrupt flows device → NVIC → core → handler → acknowledge → return; three enables (peripheral, NVIC line, core mask) must all be on.
    • 

  • IRQ n is exception 16 + n and vector-table word 16 + n; on this emulated board, timer 0 is IRQ 8 and UART 0 receive is IRQ 0 (measured).
    • 

  • Acknowledge at the source, and in the right order: clear, then service, then re-check. A missing acknowledge causes a storm; a late one can lose an interrupt.
    • 

  • Share data between a handler and main with one writer per variable, volatile plus compiler barriers on a single core, or atomics and short critical sections.
    • 

  • An I2C read: START, address+W, pointer, repeated START, address+R, data with ACKs, NACK, STOP; the driver was tested on a simulated bus (47 clocks) and against an emulated sensor set to 23.75 °C.
    • 

  • H2: the known-value check passed in emulation; the logic-analyser timing check is untested on hardware.

Forensic lab answer key


Observation. Exception 24 (IRQ 8, timer 0) is acknowledged several hundred thousand times in 2 s (the exact count differs per run); exception 16 (IRQ 0, UART receive) only a handful of times. The console printed only the banner and was stopped by the time limit (exit code 124).


Root cause. The removed line wrote 1 to the timer's INTCLEAR register: the acknowledge step of Figure 1. Without it, the timer's interrupt flag stays set, the request line stays asserted, and the moment Irq8_Handler returns, the NVIC finds IRQ 8 pending again and the core re-enters the handler (with tail-chaining, possibly without ever returning to main). main gets almost no instructions, so it never takes the bytes out of the ring buffer and never answers a command. The few UART interrupts still occur (both have priority 0; the core takes the lower-numbered exception when both are pending) and fill the ring buffer, but nothing consumes it.


Hypotheses. (a) UART broken: no, exception 16 is taken; the bytes arrive. (b) I2C scan hangs: the scan never starts; no "scan:" line, and the trace shows the processor busy in exception 24. (c) Starvation by the timer: yes.


Why the linter was wrong. It treats a write that is never read back as dead. Device registers have side effects; a write-1-to-clear register is the extreme case: its whole purpose is the side effect. Such writes must go through volatile, and tools that do not understand that must be told.


Fix and prevention. Restore reg(kTimer0 + 0x0C) = 1; at the start of the handler with the comment "acknowledge: W1C, side effect only, do not remove". Test: a CI run in the emulator with a time limit that fails if the console does not answer within the limit (exactly how this evidence was produced), or a counter of handler entries per tick that must equal 1.


How the evidence was made. app_v2.cc is app.cc with the one line removed; run.sh built it and ran QEMU for 2 s with NVIC tracing. Nothing was edited by hand.
