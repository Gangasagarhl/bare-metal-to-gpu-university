Story hook

The castle hires an inspector who does nothing but hand the gate clerk strange documents all day: a visitor list with a torn corner, one with a length that says "three hundred names" above two names, one that is all blank, one with a smudge where the count should be. For each, the inspector watches whether the clerk stumbles — writes off the edge of the slate, reads a page already wiped, freezes in a loop. Most documents are rejected cleanly. Once in a while the clerk trips, and the inspector keeps the exact document that did it, then trims it down to the few marks that matter, so the fault can be reproduced and fixed. That inspector is a fuzzer, and the watcher on the clerk's pen is a sanitizer.

In this chapter you build both — the university's own small coverage-guided fuzzer and the sanitizer builds it drives — and turn them on two real parsers: the ELF reader from SP301 and a MAVLink-style frame scanner. You will find a planted bug in each within a few inputs, shrink the crashing input, read the sanitizer report, fix the code, and then watch the fixed parser survive tens of thousands of inputs with nothing found.

What you will be able to do

  • Build a program with AddressSanitizer, UndefinedBehaviorSanitizer and coverage instrumentation, and explain what each adds.
  • Explain coverage-guided fuzzing: a corpus, mutation, an edge bitmap, and keeping inputs that reach new code.
  • Run a fuzzer against a parser, find a crash, and read the saved crashing input and its sanitizer report.
  • Minimise a crashing input to the few bytes that matter and turn it into a regression test.
  • Fix the bug and show, by fuzzing the fixed build, that the finding is gone.
  • Apply the method to a new parser (the course project and milestone P2).
Jargon box
Fuzzing
Simple words: testing a program by feeding it huge numbers of random or damaged inputs and watching for crashes. Analogy: handing the clerk thousands of torn and smudged documents. Precise: automated generation of inputs (here by mutating valid seeds) run against a target built with sanitizers, so that any memory error or undefined behaviour is detected and the input saved. D1
Coverage-guided fuzzing
Simple words: a fuzzer that keeps inputs which make the program run new code. Analogy: keeping any document that makes the clerk open a drawer never opened before. Precise: fuzzing that measures which edges of the target's control-flow graph each input exercises and adds inputs that reach new edges to the corpus, so mutation is steered toward unexplored code. D1
Corpus
Simple words: the set of interesting inputs the fuzzer keeps and mutates. Analogy: the stack of documents worth copying and altering again. Precise: the collection of seed inputs plus every input retained for reaching new coverage; mutations are drawn from it. D1
Edge / coverage bitmap
Simple words: a table that records which jumps in the code have run. Analogy: a checklist of every drawer in the office, ticked when opened. Precise: an array indexed by a hash of each control-flow edge; the compiler's -fsanitize-coverage instrumentation sets an entry when that edge executes. D2
Test-case minimisation
Simple words: shrinking a crashing input to the smallest that still crashes. Analogy: trimming the document to the few marks that trip the clerk. Precise: delta debugging — repeatedly removing parts of the input, keeping any removal that preserves the crash — to produce a small, readable reproducer. D1
Sanitizer
Simple words: a checker built into the program that reports its own memory and undefined-behaviour mistakes as it runs. Analogy: the watcher on the clerk's pen. Precise: compiler instrumentation (-fsanitize=address for out-of-bounds and use-after-free; -fsanitize=undefined for undefined behaviour) with a runtime that aborts and prints a diagnostic on a violation. D3

The idea in pictures

Figure 1 shows the fuzzing loop: pick an input from the corpus, mutate it, run it against the sanitized target, and either save a crash or (if it reached new edges) keep it in the corpus.

Layer 1 — the kid explanation

Two tools work together. A sanitizer is a watcher the compiler builds into your program; the moment the program touches memory it should not, the watcher stops it and prints exactly what went wrong and where. A fuzzer is a machine that throws millions of weird inputs at the program to try to make that happen. On their own, random inputs rarely find deep bugs; so a smart fuzzer watches which parts of the code each input runs and keeps the inputs that reach new parts, slowly working its way in. When the watcher finally shouts, the fuzzer saves the exact input, and you shrink it to the few bytes that matter so the bug is easy to see and fix.

Layer 2 — the student explanation

You already build with sanitizers (SP202): -fsanitize=address adds red zones around allocations and a quarantine for freed memory, catching out-of-bounds and use-after-free; -fsanitize=undefined catches undefined behaviour such as signed overflow and out-of-range shifts. A sanitizer only reports a bug an input actually triggers, so you need inputs that trigger bugs — that is the fuzzer's job. D3

Pure random fuzzing is weak against structured input: a random blob almost never looks like a valid ELF file, so it is rejected at the magic check and never reaches the interesting code. Coverage-guided fuzzing fixes this. The target is compiled with -fsanitize-coverage, which calls a small function on every control-flow edge; that function sets a byte in an edge bitmap. The fuzzer starts from a valid seed, mutates it, runs it, and if the run set any new bitmap byte, keeps the mutated input in the corpus. Over time the corpus accumulates inputs that reach deeper code, and mutation explores from there. D1 D2

The lab's fuzzer runs each input in a forked child so a crash kills only the child; the parent saves the input and the child's sanitizer report and continues (or stops at the first crash, to minimise and fix). The edge bitmap lives in shared memory so the parent can read the coverage a child produced even after it exits — the same shared-bitmap idea real fuzzers use. R6

Layer 3 — the engineer's depth

A coverage-guided fuzzer is a feedback loop over the target's control-flow graph. Instrumentation (-fsanitize-coverage=trace-pc here; production tools use inline 8-bit counters) marks edges; the fuzzer treats "reached a new edge" as progress and retains the input that did so. This turns an astronomically unlikely random hit into a guided search: to pass the ELF magic check, one byte-flip that happens to produce 0x7f 'E' 'L' 'F' is retained because it reaches new code, and all later mutations build on it. The lab shows the signature of this: fuzzing the fixed ELF reader grows the edge count as the corpus learns the format (46 to 51 edges in the recorded run), while the buggy reader is caught so quickly — within ten executions from the seed — that the corpus never grows (R3, R5). D1 R3 R5

The sanitizer is the oracle: it decides what counts as a bug. Without it, a fuzzer only sees hard crashes (a segfault that happens to hit an unmapped page); with it, an out-of-bounds read of one byte into valid heap — which would silently succeed in production and leak data — becomes a clean, located report. This is why the rule is "no run, no code" and "fuzz the sanitized build". The lab's ELF bug is an unbounded string read; a plain build might never crash on the crashing input, but under AddressSanitizer it is a heap-buffer-overflow READ at a named line (R7). D3 R7

Minimisation (delta debugging) matters more than it looks. A fuzzer-found input is a mutated seed full of irrelevant bytes; the bug depends on a few. The lab's minimiser trims the ELF crash from 203 bytes to 168 and the MAVLink crash from 12 bytes to 2 (R4, R9) — and two bytes, 0xFE followed by a non-zero length, is the whole bug: a start marker and a length claiming payload that is not there. A two-byte reproducer becomes a one-line regression test that will fail forever if the bug returns. The honest limit: this teaching fuzzer is mutation-only with a coarse bitmap and no dictionary or structure awareness, so it finds shallow parser bugs fast but would struggle with inputs gated on checksums or magic constants; production tools (libFuzzer, AFL++) add exactly those features, and the method is identical. D1 R4 R9

How the hardware actually does it

Coverage instrumentation is just extra instructions: at each edge the compiler emits a call that writes one byte. There is no special hardware here, though some processors offer branch-trace facilities (Intel PT) that production fuzzers can use instead of compile-time instrumentation to fuzz uninstrumented binaries. The lab uses the compiler route, which is portable and exact. D2 The fork-per-input design rests on the operating system's copy-on-write fork: the child shares the parent's pages until it writes, so a fork is cheap, and the shared-memory bitmap (an mmap with MAP_SHARED) is one region both processes write, so a child's coverage survives its exit. AddressSanitizer's own machinery — shadow memory, red zones, quarantine — is software over ordinary memory; the processor enforces nothing about "a buffer", which is exactly why the sanitizer must. D3 R6

Worked example

Take the MAVLink-style scanner. A frame is a start byte 0xFE, a length byte, four header bytes, then that many payload bytes, then two checksum bytes. The buggy scanner reads the length and then computes a checksum over the header and payload — six plus len bytes — without first checking that the buffer actually holds them. Seed the fuzzer with one valid frame. Within three executions it mutates the length byte to a value larger than the bytes present; the checksum loop walks off the end of the heap copy; AddressSanitizer reports a heap-buffer-overflow READ in toy_sum and the fuzzer saves the 12-byte input (R8). The minimiser then removes everything that does not matter and lands on two bytes: 0xFE and a non-zero length (R9). Reading those two bytes, the bug is obvious: a start marker and a claim of payload that is not there. The fix is one line — before touching the payload, require size - pos ≥ header + len + checksum — after which the fuzzer runs ~18,000 inputs in thirty seconds with nothing found (R10). R8 R9 R10

Where the analogy breaks


    

  • The inspector tries documents blindly; a coverage-guided fuzzer learns. It remembers which inputs opened new drawers and builds on them, so it is a guided search, not random trial. The "random documents" picture undersells it. D1
    • 

  • A tripping clerk is obvious; a silent over-read is not. Many real bugs do not crash on their own; the sanitizer is what makes the stumble visible. Without it the inspector would see nothing. D3
    • 

  • "Finds nothing" is not "no bugs". A clean fuzzing run means the fuzzer, with this coverage and this time, found nothing — not that the parser is proven safe. The castle inspector who finds no fault today has not certified the gate. D1
    • 




Common mistakes and debugging


    

  • Symptom: the fuzzer runs for ages and finds nothing, even on buggy code. Cause: no sanitizer (so silent bugs are invisible) or no coverage (so it never reaches deep code). How to find it: check the build flags; print the edge count and watch it grow. Fix: build the target with -fsanitize=address,undefined and -fsanitize-coverage, and start from a valid seed.
    • 

  • Symptom: the fuzzer dies on the first crash and loses progress. Cause: running the target in-process. How to find it: the whole process aborts. Fix: run each input in a forked child (as the lab does) so a crash kills only the child.
    • 

  • Symptom: a crash reproduces sometimes but not always. Cause: uninitialised memory or address-dependent behaviour, or a non-fixed RNG. How to find it: fix the fuzzer's seed; replay the saved input with repro. Fix: use the saved input file, not a re-generated one; add the minimised input as a regression test.
    •

  • Sanitizers are the oracle (they decide what is a bug and locate it); fuzzers are the input generator (they trigger bugs).
    • 

  • Coverage-guided fuzzing keeps inputs that reach new edges, so it learns structured formats a random fuzzer never would.
    • 

  • The loop is: mutate a corpus input, run the sanitized target (in a forked child), save crashes, keep new-coverage inputs.
    • 

  • Minimise a crashing input to the bytes that matter and make it a regression test.

  • Fix the bug, then re-fuzz the fixed build to show the finding is gone — but "finds nothing" is not "proven safe".

  2. Structured input is gated: a random blob fails the first check (magic, length) and never reaches deep code. Coverage guidance keeps any mutation that reaches a new edge — such as one that happens to form valid magic — so the fuzzer accumulates inputs that penetrate the format and explores from there.
