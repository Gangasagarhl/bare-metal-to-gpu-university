Story hook

Even a castle with a careless clerk can be made hard to rob. Put a thin wax seal between each order and the one below it, so a clerk who scribbles too far breaks the seal and the guard refuses the order (a stack canary). Forbid the guards from ever acting on instructions written in the visitors' own notebooks (no-execute pages). Move the rooms around every night so a thief who learned yesterday's map arrives at the wrong door (address randomisation). And post an inner rule that the castle staff never follow orders found in a visitor's bag, nor rummage in it, unless a specific procedure says to (SMEP and SMAP in the kernel). None of these fixes the clerk; each makes a surviving mistake far harder to turn into a robbery.

This chapter is about defence in depth for compiled programs and kernels: the mitigations that sit under your code so that a bug which slipped past F11-08 and F11-09 is more likely to become a clean crash than a working exploit. You will set each one, watch it fire, and read it out of a real binary.

What you will be able to do

  • Explain what a stack canary, non-executable memory (NX/W^X), ASLR, SMEP and SMAP each defend against, and which exploit link each one breaks.
  • Trigger a stack-protector abort and an NX fault on your own machine and read them.
  • Observe ASLR by seeing addresses change between runs of the same binary.
  • Read a binary's hardening flags (PIE, non-executable stack, RELRO) from its ELF program headers.
  • Describe how SMEP and SMAP protect a kernel from user memory, and why user pointers must still be validated (B12).
Jargon box
Stack canary
Simple words: a secret value placed between a buffer and the saved return address, checked before returning. Analogy: a wax seal that breaks if the clerk writes too far. Precise: a random value (__stack_chk_guard) the compiler stores on the stack with -fstack-protector; the function checks it before returning and calls __stack_chk_fail (aborting) if it changed. D1
NX / W^X
Simple words: memory is either writable or executable, never both; data pages cannot run as code. Analogy: guards never act on notes in visitors' notebooks. Precise: the no-execute page bit (x86-64 XD bit 63 of a page-table entry, honoured when EFER.NXE is set); an instruction fetch from a non-executable page faults. W^X is the policy of never mapping a page writable and executable at once. D2
ASLR
Simple words: the program's stack, heap and code sit at different addresses each run. Analogy: the rooms are rearranged every night. Precise: Address Space Layout Randomisation — the kernel loads the stack, the heap, shared libraries and (for a position-independent executable) the program itself at randomised base addresses, so an attacker cannot know a target address in advance. D3
PIE
Simple words: a program built so it can be loaded at any address. Analogy: a building with no fixed street number. Precise: a Position-Independent Executable (ELF type ET_DYN) whose code uses relative addressing, letting the loader place it at a random base — the prerequisite for ASLR of the main program. D4
SMEP
Simple words: the CPU refuses to run user-page code while in kernel mode. Analogy: staff never follow instructions written in a visitor's notebook. Precise: Supervisor Mode Execution Prevention (CR4 bit 20): an instruction fetch at privilege level 0 from a user page faults. D2
SMAP
Simple words: the CPU refuses kernel reads and writes of user pages, except in an explicitly opened window. Analogy: staff do not rummage in a visitor's bag unless the copy procedure is open. Precise: Supervisor Mode Access Prevention (CR4 bit 21): data accesses at privilege level 0 to user pages fault unless RFLAGS.AC is set, which stac sets and clac clears. D2

The idea in pictures

Figure 1 shows a stack frame with a canary between the buffer and the saved return address: an overflow that reaches the return address must first pass through, and change, the canary.

Layer 1 — the kid explanation

You cannot promise a big program has no bugs. So you add layers that make a bug hard to use. A canary is a secret number tucked in just before the return address; if an overflow stomps toward the return address, it changes the secret, and the program notices and stops. No-execute says data can be written or run, never both, so an attacker who drops code into a buffer cannot run it. Address randomisation moves everything around each run, so an attacker who needs to know where something is must guess, and usually guesses wrong. Inside the operating system, two more rules (SMEP and SMAP) stop the kernel from being tricked into running or reading a program's own memory. Each layer is cheap and each breaks a different step of an attack.

Layer 2 — the student explanation

Recall the stack exploit chain from F11-07: overflow a buffer, overwrite the saved return address, jump to attacker code. Each mitigation breaks one link.

  • Stack canary (-fstack-protector): detects the overwrite. The compiler stores a secret below the buffer and checks it before ret; a contiguous overflow that reaches the return address must change the canary, so the check fails and the program aborts with "stack smashing detected". The lab shows this abort (R1). D1 R1
  • NX / W^X: blocks jumping to injected code. Data pages are non-executable, so even if the attacker places code in a buffer, fetching an instruction from it faults. The lab calls a byte of data as a function and gets a segmentation fault (R3). D2 R3
  • ASLR (with PIE): hides the address the attacker needs. Stack, heap, libraries and the PIE program itself load at random bases each run, so a hard-coded address is wrong. The lab prints stack, heap and code addresses across three runs and they differ (R4). D3 R4

Because NX blocks running injected code, real attacks turned to return-oriented programming — stitching together existing code fragments — which in turn needs to know addresses, which ASLR denies. The defences interlock. For kernels, SMEP and SMAP add two more: the processor refuses to execute user-page code in kernel mode (SMEP) and refuses to read or write user pages except in an explicitly opened window (SMAP), so a kernel bug cannot be steered into running or trusting user memory. You built these in OS303 (F3-29). D2

Layer 3 — the engineer's depth

Mitigations are probabilistic and composable, not proofs. A stack canary defends the return address but not a function pointer overwritten before the canary, and not a non-contiguous write that skips it; -fstack-protector-strong protects more functions than the default heuristic, at a small cost. NX forces attackers to reuse existing executable code (return-oriented programming), which is why control-flow integrity and shadow stacks exist as the next layer. ASLR's strength is its entropy: too few random bits and an attacker brute-forces the base; a non-PIE executable leaves the main program at a fixed address even when libraries move, which is why PIE matters. None of these removes the bug; they raise the cost and, crucially, convert many silent corruptions into loud crashes you can detect and alert on. D1 D3

You can read most of a binary's posture straight from its ELF program headers, which is what tools like checksec do. A PT_GNU_STACK segment with the X flag means an executable stack (bad); without it the stack is non-executable. PT_GNU_RELRO marks the region made read-only after relocation, which protects the Global Offset Table; combined with "bind now" it closes a classic GOT-overwrite path. ELF type ET_DYN (rather than ET_EXEC) marks a PIE. The lab's own reader and readelf agree: the weakly built binary has an executable stack and is not a PIE; the hardened one has a non-executable stack, is a PIE, and carries RELRO (R5). D4 R5

SMEP and SMAP are architectural, enforced by the processor given the right CR4 bits (B12). SMEP (CR4.20) faults on a supervisor instruction fetch from a user page; SMAP (CR4.21) faults on a supervisor data access to a user page unless RFLAGS.AC is set, which the kernel sets briefly with stac around a deliberate user copy and clears with clac. They do not remove the need to validate user pointers: SMAP stops an accidental access, but a system call that takes a pointer and length from a user program must still check that the range is a user range and copy it through a fault-tolerant routine — otherwise a malicious program can hand the kernel a kernel address or an unmapped one. The OS303 lab shows exactly this: with SMAP on, a bug that trusts a user pointer faults in the kernel; the correct kernel validates the range and returns an error instead. SMEP, SMAP and user-pointer validation are three layers for the same goal. D2 D5

How the hardware actually does it

These are hardware features the processor enforces on every access, which is why they are cheap. The no-execute bit is bit 63 of each page-table entry; when EFER.NXE is set, an instruction fetch from a page with that bit raises a page fault with the instruction-fetch error bit, so the data page in the lab's NX demo cannot be run (R3). D2 R3 SMEP and SMAP are CR4 bits the kernel sets once at boot; thereafter the page-walk hardware checks the user/supervisor bit of every page against the current privilege level and the AC flag, and faults without the kernel executing a single extra instruction per access. The stack canary is not hardware — it is compiler-emitted loads, a compare and a conditional call to __stack_chk_fail — which is why it costs a few instructions per protected function. ASLR is the kernel choosing random load bases using the per-page translation the MMU already does; the running code is identical, only its base differs, which is why a PIE can run anywhere. D3

Worked example

Run the lab's canary.cc: a function copies an unbounded string into char buf[16]. Give it a forty-byte string. Built with -fstack-protector-all, the copy overruns the buffer, overwrites the canary and the saved return address, and on return the function's epilogue reloads the canary, finds it changed, and calls __stack_chk_fail: the program prints "*** stack smashing detected ***" and aborts with SIGABRT (exit 134) before any attacker-chosen address can be used (R1). Built with -fno-stack-protector, there is no check; the corrupted return address is loaded on ret and the program jumps to a bad address, giving a segmentation fault (exit 139) — or, with a cleverly chosen string, silent corruption (R2). The difference is the whole value of the mitigation: with it, the overflow is a clean, detectable abort; without it, it is an uncontrolled jump the attacker might steer. R1 R2

Where the analogy breaks


    

  • A wax seal stops one path; a canary guards one slot. The canary protects the saved return address, not a function pointer overwritten before it or a write that skips over it. The seal image suggests a wall; it is one checkpoint. D1
    • 

  • Rearranging rooms nightly still leaves the same building. ASLR moves bases, not contents; a leak of one address can de-randomise the rest, and too little entropy can be brute-forced. The analogy hides that the map is still internally fixed. D3
    • 

  • "Guards ignore the visitor's notebook" is not "the bag is safe". SMAP stops accidental kernel access to user memory, but the kernel still must validate any user pointer it is asked to use; the analogy makes the rule sound total when deliberate, checked access is still needed. D5
    • 




Common mistakes and debugging


    

  • Symptom: an overflow that should abort just runs. Cause: the stack protector was off (-fno-stack-protector) or the function was not covered by the default heuristic. How to find it: check the build flags; disassemble and look for __stack_chk_fail. Fix: use -fstack-protector-strong (or -all for sensitive code).
    • 

  • Symptom: a binary you shipped reports an executable stack in a scan. Cause: a -z execstack flag or an assembly file without a .note.GNU-stack marker. How to find it: readelf -lW and look at GNU_STACK flags (RWE vs RW). Fix: remove -z execstack; add the non-exec stack note to assembly.
    • 

  • Symptom: the kernel crashes when a system call is given a crafted pointer. Cause: a user pointer trusted without validation (SMAP stops accidental access, not this). How to find it: the fault's address is a user or kernel address from the call; see F3-29. Fix: validate the range and copy through a fault-tolerant routine.
    •

Summary


    

  • Hardening is defence in depth: each mitigation breaks one link of an exploit chain, turning many silent corruptions into clean crashes.
    • 

  • Stack canary detects a return-address overwrite; NX/W^X blocks running injected code; ASLR (with PIE) hides needed addresses.
    • 

  • SMEP and SMAP stop a kernel from executing or reading user memory; user pointers must still be validated (B12).
    • 

  • A binary's posture — PIE, executable stack, RELRO — is readable straight from its ELF program headers.
    • 

  • Mitigations are probabilistic and composable; they raise cost and detectability but do not remove the bug.

Answers to Check yourself


    

  1. Stack canary breaks the "overwrite return address" link (it detects the overwrite before ret). NX breaks the "jump to attacker code" link (it refuses to execute injected data). ASLR breaks the attacker's need to know the target address (it randomises bases).
    2. 

  2. NX made injected code non-runnable, so attackers reused existing executable code fragments (gadgets) ending in ret — return-oriented programming. Control-flow integrity and hardware shadow stacks target that by constraining where returns and indirect calls may go.
    3. 

  3. ASLR randomises load bases, but a non-PIE main program is ET_EXEC and must load at its fixed link address. Only a position-independent executable (ET_DYN) can be placed at a random base, so without PIE the program's own code stays at a known address.
    4. 

  4. (c). (a) a canary detects a contiguous overwrite of the return address, not all overflows; (b) SMAP stops accidental access but user pointers still need validation; (d) ASLR changes only the base, not the code.
    5. 

  5. SMAP faults on a supervisor-mode data access to a user page when RFLAGS.AC is clear. The kernel does a legitimate user copy by briefly setting AC with stac around a fault-tolerant copy routine and clearing it with clac.
    6. 

  6. PIE is missing. Adding it costs recompiling with -fPIE -pie (a small code-size/indirection cost); it lets ASLR randomise the main program's base, so its code and data addresses are no longer fixed and known to an attacker.
    7. 

  7. With -fstack-protector-all: the canary changes, the check fails, and the program aborts with "stack smashing detected" (exit 134). With -fno-stack-protector: no check, the corrupted return address is used and the program segfaults (exit 139). The logs confirm both.
    8.
