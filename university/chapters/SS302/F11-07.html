Story hook

At the castle gate a guard reads orders from a slate: sixteen boxes for a visitor's name, then one box that says let in: yes or no. A clerk copies each name onto the slate. One morning a visitor gives a name far longer than sixteen letters. The clerk, told only "copy the name", keeps writing past the sixteenth box and over the let in box, turning its no into a yes. Nobody checked a password. Nobody lied about who they were. A length that was too long, copied by a clerk who never counted, opened the gate.

That is the whole of this chapter. Most attacks on programs written in C and C++ are not clever tricks with secret knowledge; they are ordinary memory bugs — writing past the end of a buffer, using memory after it is freed, trusting a number that wrapped around — that an attacker arranges to land on something that matters. You will make three of them happen on your own machine, watch the sanitizer catch them, and see why the next three chapters exist.

What you will be able to do

  • Explain how an out-of-bounds write, a use-after-free and an integer overflow each turn into a change the program never intended.
  • Describe the path from "a buffer is one byte too small" to "the attacker chose what the program does next".
  • Run a program under AddressSanitizer and UndefinedBehaviorSanitizer and read the report it prints.
  • Distinguish a bug the sanitizer catches from the same bug running silently in a production build.
  • Apply the idea to a new case: given a struct layout, say which field an overflow would reach.
Jargon box
Memory safety
Simple words: every read and write touches only memory the program is allowed to touch, and only while it is valid. Analogy: writing only inside your own boxes on the slate, and only while the slate is yours. Precise: the property that a program has no out-of-bounds access, no use of freed or uninitialised memory, and no type-confused access; C and C++ do not guarantee it, so the programmer must. D1
Buffer overflow
Simple words: writing more into a fixed-size area than it holds, so the extra spills into whatever is next. Analogy: writing a name past its boxes onto the next field. Precise: a write (or read) beyond the bounds of an array or allocation; the neighbouring bytes may be another variable, a saved return address, heap metadata or a function pointer. D2
Use-after-free
Simple words: using a pointer to memory that has already been given back. Analogy: reading orders off a slate that was already wiped and handed to someone else. Precise: dereferencing a pointer after the object it referred to has been freed or has ended its lifetime; the memory may now hold something else, so the read or write is attacker-influenceable. D1
Integer overflow
Simple words: a number grows past the biggest its type can hold and wraps to a small one. Analogy: a tally sheet that only has three digits rolling from 999 back to 000. Precise: an arithmetic result outside the representable range of the type; for unsigned types it wraps modulo 2n, for signed types it is undefined behaviour. A size computed this way can be far too small. D3
Exploit
Simple words: an input crafted so that a bug does something useful for an attacker. Analogy: a name chosen precisely so the overflow lands on the let in box. Precise: an input or sequence of inputs that drives a vulnerability to a goal — changing data, redirecting control flow, or leaking memory — rather than merely crashing. D1
Sanitizer
Simple words: a checker the compiler builds into the program so it reports its own memory mistakes as it runs. Analogy: an inspector watching the clerk, who shouts the moment a pen leaves the boxes. Precise: compiler instrumentation (here -fsanitize=address and -fsanitize=undefined) with a runtime that detects out-of-bounds access, use-after-free, and undefined behaviour and prints a diagnostic. D4

The idea in pictures

Figure 1 shows the first demo's memory: a sixteen-byte name field with an is_admin flag right after it, inside one small struct on the stack. A copy that does not stop at sixteen writes the overflow straight onto the flag.

Layer 1 — the kid explanation

A program keeps its information in boxes called memory. Each box has a number, and the program is supposed to write only in the boxes it set aside for a job. A buffer overflow is when it writes past the last box of one job into the boxes of the next job. If the next box happened to hold "is this user an administrator?", the overflow can switch it on. The program did not decide to make the visitor an administrator; a careless copy did.

There are a few ways to make this kind of mess. You can write past the end (overflow). You can keep using a box after you gave it back (use-after-free). You can let a counter roll over so you ask for far too few boxes and then write too many things into them (integer overflow). An attacker's craft is choosing exactly what to write and where, so the accident lands on something that helps them.

Layer 2 — the student explanation

C++ gives you direct, unchecked access to memory, which is why it is fast and why it is dangerous. An array write such as a.user[i] = c does no bounds check: if i is 16 and the array has 16 elements, the write goes to whatever memory follows. D1 Whether that memory is another local variable, the function's saved return address, or metadata the allocator keeps, depends on layout — and attackers study layout. The accident is always the same; the consequence is chosen.

Three families cover most of what you will meet:

  • Spatial errors: reading or writing outside an object's bounds (overflow, under-read, off-by-one). D2
  • Temporal errors: using memory outside its lifetime (use-after-free, double free, use of a dangling pointer or iterator). D1
  • Type and value errors that lead to the first two: integer overflow in a size, a signed/unsigned mix-up, an uninitialised length. D3

The worst consequence is control-flow hijack: overwriting a value the processor will later load into the instruction pointer — a saved return address, a function pointer, a C++ virtual-table pointer — so that the attacker chooses the next instruction. The second demo does this with a function pointer; the castle guard now follows the attacker's orders.

Layer 3 — the engineer's depth

An exploit is a chain, and every link is a specific fact about the target. A classic stack chain reads: (1) an unchecked copy into a stack buffer; (2) the buffer sits below the saved return address; (3) the attacker writes a chosen address there; (4) on ret the processor jumps to it. Each defence in F11-10 breaks one link — a stack canary detects step 3, a non-executable stack blocks jumping to injected code, address randomisation hides the address needed in step 3. Because the links are independent, defences stack: break any one and the chain fails, which is why real systems use several at once. D5

Not every memory bug is exploitable, and honest engineering does not pretend otherwise. A read one byte past a buffer may only crash; a write the attacker fully controls, to a location they choose, is a "write-what-where" and is usually serious. Triage asks: read or write? how much of the offset and the value does the attacker control? what lives at the target? Sanitizers answer the first questions precisely — the report says READ or WRITE, the size, and the faulting address relative to the object — which is why they are the first tool you reach for. D4

One limit matters from the start: a sanitizer reports what it can see. AddressSanitizer places red zones around allocations, so it catches a write that leaves an object, but not a write that stays inside one correctly sized object yet lands on the wrong field — the is_admin case of demo 1 (Figure 1). There, a different check saves you: UndefinedBehaviorSanitizer knows the static array bound char[16] and flags the index 16 (R3). Use both, and know what each one sees. D4 R3

How the hardware actually does it

The processor has no idea what a "buffer" is. It executes loads and stores to addresses and jumps to whatever address is in the instruction pointer; the meaning of a region as "a name" or "a return address" lives only in the compiler's plan. That is exactly why overwriting the bytes of a return address works: to the processor they were never special, so a ret happily loads the attacker's value and jumps there. D5 The hardware defences you meet later add meaning the processor does enforce: a no-execute bit per page (so a jump into data faults), and supervisor-mode checks (so the kernel cannot be tricked into running or reading user pages) — all in F11-10. The integer overflow of demo 3 is pure hardware arithmetic: a 32-bit multiply keeps only the low 32 bits, and 0x40000001 × 4 keeps 0x4, so the program asks the allocator for four bytes (R5). D3 R5

Worked example

Take demo 1's struct: struct Account { char user[16]; int is_admin; };. On this platform sizeof(Account) is 20: sixteen bytes of name, then four bytes of flag, with no padding because int's four-byte alignment is already met at offset 16. A copy of a name that is exactly twenty bytes long writes indices 0 through 19. Indices 0–15 fill the name; indices 16–19 are the four bytes of is_admin. Twenty bytes of 'A' (0x41) make is_admin read as 0x41414141 = 1,094,795,585, which is nonzero, so if (a.is_admin) is true. The lab's plain build prints exactly that number and "ADMIN ACCESS GRANTED" (R2). Crucially, twenty bytes is in bounds of the struct: the write never leaves the 20-byte object, so there is no heap or stack red zone to trip — the corruption is of the wrong field, not of the wrong allocation. A twenty-one-byte name would leave the object and AddressSanitizer would catch that. The attacker picks twenty. R2

Where the analogy breaks


    

  • The slate's boxes are not labelled in memory. The processor does not know which bytes are "the name" and which are "the flag"; that meaning exists only in the compiler's layout. A guard can see the let in box; the hardware cannot. D5
    • 

  • A castle has a handful of gates; a program has thousands. Every input — a file, a packet, a device register, an environment variable — is a potential entrance. The analogy undercounts the attack surface. D1
    • 

  • Overflows can reach backwards and sideways, not just forward. Depending on layout and the bug, a write can land before an object or on allocator metadata, not only on the next field. The tidy left-to-right picture is one case of many.
    • 




Common mistakes and debugging


    

  • Symptom: "it worked for me" — the bug does nothing in a normal build. Cause: the corruption landed on padding or unused memory this time. How to find it: build with -fsanitize=address,undefined and run your tests and fuzzer (F11-09). Fix: treat any sanitizer report as a real bug, even if the program "seemed fine".
    • 

  • Symptom: a crash with a corrupted backtrace or a jump to a nonsensical address. Cause: a saved return address or function pointer was overwritten. How to find it: the AddressSanitizer report names the overflowed object and the write size; a debugger shows the clobbered frame. Fix: bound the copy; the defences of F11-10 turn a silent hijack into a clean abort.
    • 

  • Symptom: AddressSanitizer says nothing but the value is wrong. Cause: an intra-object overwrite (demo 1) or an uninitialised read — ASan does not model either. How to find it: add UndefinedBehaviorSanitizer and MemorySanitizer-style thinking; prefer bounded types so the case cannot arise. Fix: std::array/std::span with checked indices, covered in F11-08.
    •

Summary


    

  • Most attacks on C/C++ programs are ordinary memory bugs aimed on purpose at something that matters.
    • 

  • Spatial (out-of-bounds), temporal (use-after-free) and value (integer-overflow) bugs are the main families.
    • 

  • The worst outcome is control-flow hijack: overwriting a return address or function pointer so the attacker chooses the next instruction.
    • 

  • An exploit is a chain of specific facts about the target; defences (F11-10) each break one link.
    • 

  • Sanitizers catch most of these and classify them, but each has blind spots: ASan sees out-of-allocation writes, UBSan sees known-bound index errors; use both.
    • 

  • Not every bug is exploitable; triage asks read-or-write, how much the attacker controls, and what is at the target.
    •
