Story hook

The castle does not trust any single guard to be careful on any single day. Instead it builds carefulness into the routine: a checklist every guard follows, a second guard who reads the first one's work, and a locked rule that an order with any crossing-out is refused, not quietly accepted. The point is not that people stop making mistakes — they do not — but that a mistake must pass several independent checks before it reaches the gate, and most do not survive even the first.

A coding standard is that routine for software: a short set of rules, enforced by tools that run automatically, so that the dangerous constructs of F11-07 are caught at build time by the compiler and the analyser, not in production by an attacker. This chapter turns the lessons of F11-08 and F11-09 into a standard a team can apply, and shows the tools catching the bugs for you.

Jargon box
Coding standard
Simple words: a written set of rules for how code must be written, so dangerous constructs are avoided or flagged. Analogy: the guards' checklist that every order must satisfy. Precise: a documented rule set (here the SEI CERT C++ standard and the C++ Core Guidelines) with rationale and, where possible, automated enforcement. D1
Static analysis
Simple words: checking code for mistakes without running it. Analogy: a second guard reading the order before it is acted on. Precise: tools (here clang-tidy) that inspect source or the compiler's representation to find rule violations and likely bugs, reporting them with file, line and a rule name. D2
Warnings as errors
Simple words: make the build fail on any compiler warning. Analogy: refusing an order that has any crossing-out, not filing it anyway. Precise: the -Werror option, usually with a chosen warning set (-Wall -Wextra -Wconversion …), so a warning stops the build and must be fixed. D3
Narrowing conversion
Simple words: putting a value into a type too small or of the wrong sign, silently changing it. Analogy: copying a four-digit number into a three-box field. Precise: an implicit conversion that may lose value or change sign (e.g. uint32_t to short); flagged by -Wconversion/-Wsign-conversion. D3
Linter
Simple words: a tool that flags suspicious or non-conforming code. Analogy: the colleague who points at the smudge before you hand the order over. Precise: a static-analysis tool with configurable check sets (clang-tidy groups: cert-*, bugprone-*, clang-analyzer-*) run in the editor and in CI. D2
Continuous integration (CI)
Simple words: a system that builds and checks every change automatically. Analogy: the gate that no order reaches without passing the checklist. Precise: an automated pipeline that, on each change, compiles with warnings-as-errors, runs the analyser, the tests under sanitizers, and a short fuzzing pass, failing the change if any step fails. D1

The idea in pictures

Figure 1 shows the secure-coding pipeline as a series of gates a change must pass, each catching a different class of problem.

Layer 1 — the kid explanation

People are careful most of the time, but "most of the time" is not good enough when one slip can open the gate. So instead of hoping everyone is careful, you write down the rules and let machines check them on every change. The compiler can be told to refuse to build if it sees anything suspicious. A separate tool reads the code and points at known-bad patterns. The tests run with the watchers from F11-09 turned on. A fuzzer throws odd inputs at it. And finally a person reads it, because some mistakes are about meaning, not syntax. Each layer catches different things, and a mistake has to slip past all of them to survive.

Layer 2 — the student explanation

A coding standard for C++ security has two well-known sources: the SEI CERT C++ Coding Standard (rules such as "do not use atoi, which cannot report errors" and "do not access freed memory") and the C++ Core Guidelines (prefer bounded types, RAII, no raw owning pointers — the content of F11-08). Rules are only as good as their enforcement, so each layer of Figure 1 automates part of it. D1

  • Compiler, warnings as errors. Turn on -Wall -Wextra -Wconversion -Wsign-conversion -Wshadow and -Werror. Now a narrowing conversion — a 32-bit device length stored in a short — fails the build instead of silently truncating. The lab shows the same file building quietly without these flags (storing 70000 as 4464) and failing to build with them (R3). D3 R3
  • Static analyser. clang-tidy with cert-* and bugprone-* checks reads a careless parser and reports four problems — atoi that cannot report errors, an assignment inside an if, an uninitialised read, and a double free — none of which stop the compiler (R1). The same checks on the standard-conforming rewrite report nothing (R2). D2 R1 R2
  • Sanitized tests and fuzzing. The input-triggered bugs that survive static analysis are caught by the tools of F11-09.
  • Human review. Design and logic — is this the right check, in the right place, with the right error? — is where a reviewer adds what tools cannot.

Layer 3 — the engineer's depth

The value of a standard is in making the safe thing the default and the unsafe thing loud. Each layer has a precise role and a precise cost. Compiler warnings are free and instant but shallow: they catch narrowing, unused results, shadowed names and obvious type errors, and with -Werror they cannot be ignored under deadline pressure. Static analysis is deeper and still cheap: clang-tidy's clang-analyzer-* checks do path-sensitive reasoning (it can see that a pointer is null on one branch and dereferenced later), while cert-* and bugprone-* encode specific rules; the cost is false positives, managed by choosing check sets and annotating intentional exceptions. The lab's careless file trips exactly the kinds of rules a real standard names: an error-silent conversion (CERT ERR34-C), an assignment-in-condition (a bugprone check), and an uninitialised-value use found by the path-sensitive analyzer (R1). D2 R1

Some domains add a further standard. Safety-critical C and C++ (automotive, aerospace) use rule sets such as MISRA, enforced by qualified tools, and forbid whole language features; the functional-safety course (SS402) treats these at the concept level. For general systems code, the combination in Figure 1 — Core Guidelines content enforced by the compiler and clang-tidy, backed by sanitized tests and fuzzing, gated in CI, and finished by human review — is the practical standard, and it is exactly the pipeline the university's own chapters are built to pass. The discipline that makes it work is non-negotiable gates: a warning that can be ignored will be, so -Werror and a failing CI on any finding are what give the rules teeth. D1 D4

Code review deserves its own discipline. A security review reads for the things tools miss: is untrusted input validated before use (F11-12); is every length and index bounded; who owns each resource; what happens on the error path; is the check in the right place and does it fail closed? The course practical is exactly this — review a provided parser against a checklist — and it is a skill, not a formality: reviewers find different bugs than fuzzers, and the two together find more than either alone. D1

How the hardware actually does it

This chapter is about process, not hardware, and it says so plainly: no processor enforces a coding standard. The connection to hardware is indirect but real — the rules exist because the hardware will faithfully execute the consequences of a bug (the overflow and the hijack of F11-07), and the mitigations of F11-10 are hardware features a standard tells you to enable. A coding standard therefore includes build settings that turn on hardware defences (non-executable stack, PIE for ASLR) as surely as it includes source rules; the two meet in the compiler and linker flags your CI enforces. D3

Worked example

Take the lab's narrowing.cc: a function stores a 32-bit unsigned device length in a short. A length of 70000 does not fit in a 16-bit signed type; the stored value becomes 4464 (70000 modulo 65536, interpreted as signed). Built with only -Wall -Wextra, this compiles without complaint and prints "device said 70000, we stored 4464" — a silent, dangerous truncation of a value that controls how much the program will read or write. Built with -Wconversion -Wsign-conversion -Werror, the same line fails to compile: "conversion from 'uint32_t' to 'short int' may change value" (R3). The lesson is mechanical and absolute: the warning set and -Werror turn a latent bug into a build failure the author must address, which is the whole purpose of a coding standard. The fix is to use a type wide enough (or to validate and reject the value), as the standard-conforming good.cpp does — and clang-tidy then reports nothing on it (R2). R2 R3

Where the analogy breaks


    

  • A checklist is finite; code is not. A coding standard cannot list every mistake; analysers have false negatives (missed bugs) and false positives (noise). The checklist image suggests completeness it does not have. D2
    • 

  • A second guard reads the same order; a reviewer reads changing code. Review scales poorly with size and fatigue, which is why tools do the mechanical part and humans focus on design and untrusted-input handling, not on counting brackets. D1
    • 

  • "Refuse any crossing-out" sounds absolute; warnings need curation. Blindly enabling every warning or check produces noise that teams learn to ignore, which is worse than fewer, enforced rules. The standard is a chosen set, kept meaningful.
    • 




Common mistakes and debugging


    

  • Symptom: a narrowing or sign bug ships despite "we have warnings on". Cause: the relevant warnings (-Wconversion, -Wsign-conversion) were not enabled, or -Werror was not set. How to find it: build the file with the full set and read the diagnostics. Fix: add the warnings and -Werror in the build and CI.
    • 

  • Symptom: the analyser is "always red", so the team ignores it. Cause: too many checks enabled, including noisy or stylistic ones. How to find it: count findings per check. Fix: curate the check set to high-value rules (cert-*, bugprone-*, clang-analyzer-*), fix or suppress with justification, and gate CI on zero new findings.
    • 

  • Symptom: a bug tools cannot see (wrong check, wrong place) reaches production. Cause: no human security review of untrusted-input handling. How to find it: post-incident review shows a missing or misplaced validation. Fix: add a review checklist (validate before use, bound every length, fail closed) — the course practical.
    •

Summary


    

  • A coding standard makes carefulness part of the routine, enforced by tools, not left to individual memory.
    • 

  • The pipeline is layered: compiler (warnings as errors), static analyser, sanitized tests, fuzzing, human review.
    • 

  • Each gate catches a different class; most mistakes stop at the compiler or analyser, cheaply and instantly.
    • 

  • -Werror and a failing CI on any finding are what give the rules teeth.
    • 

  • Sources are the SEI CERT C++ standard and the C++ Core Guidelines; safety-critical domains add rule sets like MISRA (SS402).
    • 

  • Human review focuses on what tools miss: untrusted-input validation, ownership, error paths, and whether a check is in the right place and fails closed.
