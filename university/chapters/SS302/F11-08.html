Story hook

The castle keeps a ledger of visitors. A page has room for a fixed number of lines; a clerk must never write below the last line onto the next page, and must never read a line from a page that has been torn out and reused for something else. Two rules, kept by discipline, prevent most of the trouble in the whole castle: stay inside the page (bounds), and only read a page while it is still this ledger's page (lifetime). A third rule keeps the first two honest: every page has exactly one owner who decides when it is torn out, so no two clerks disagree about whether it still exists (ownership).

Chapter F11-07 showed how breaking these rules becomes an attack. This chapter is the defence: how modern C++ lets you keep bounds, lifetimes and ownership by construction, so the bug cannot be written, not merely caught later.

What you will be able to do

  • Carry a length with every pointer using std::span and check bounds once, at the edge.
  • Explain object lifetime and name the moment a pointer, reference, iterator or string_view becomes dangling.
  • Choose an ownership model — single owner (unique_ptr), shared owner (shared_ptr), or a non-owning view — and say who frees what.
  • Diagnose a use-after-free and a reallocation-dangling bug from an AddressSanitizer report.
  • Apply RAII so that every resource is released exactly once, on every path, including exceptions.
Jargon box
Bounds
Simple words: the first and last valid positions of an array or buffer. Analogy: the top and bottom lines of a ledger page. Precise: the half-open range [0, size) of valid indices of a contiguous object; an access outside it is undefined behaviour in C++. D1
Lifetime
Simple words: the time between when an object is created and when it is destroyed. Analogy: while the page belongs to this ledger. Precise: the interval from the completion of an object's constructor (or its storage's allocation for trivial types) to the start of its destructor or the release of its storage; access outside it is undefined. D1
Ownership
Simple words: whose job it is to free a resource. Analogy: the one clerk who may tear out a page. Precise: the responsibility for releasing a resource exactly once; expressed in C++ by the type that holds it (a value, a unique_ptr, a shared_ptr), not by convention. D2
RAII
Simple words: tie a resource to an object so it is freed when the object goes out of scope. Analogy: the page is torn out automatically when its folder is closed. Precise: Resource Acquisition Is Initialisation — acquire in the constructor, release in the destructor, so every path (including exceptions) releases exactly once. D2
std::span
Simple words: a pointer and a length travelling together, without owning the data. Analogy: a bookmark that also says how many lines the section has. Precise: a non-owning view over a contiguous sequence, carrying a pointer and a size; operator[] is unchecked but size() lets the callee check once. D1
Dangling pointer
Simple words: a pointer to something that no longer exists. Analogy: a bookmark in a page that has been torn out. Precise: a pointer, reference, iterator or view whose referent's lifetime has ended; using it is undefined behaviour and a frequent root of use-after-free. D1

Layer 1 — the kid explanation

Two habits stop most memory trouble. First, stay inside: never write or read past the end of an array. If you keep the length next to the pointer, you can always check. Second, do not keep stale notes: if you remember where something was, and then it moves or is thrown away, your note is wrong — using it reads whatever is there now. Third, give every thing one owner who decides when it is freed, so two parts of the program never disagree about whether it still exists. In C++ you can make the compiler and the types do this bookkeeping for you, which is far safer than remembering it yourself.

Layer 2 — the student explanation

Bounds. A raw pointer has no length; a function that takes (int* p, size_t n) trusts the caller to pass a matching n, and many bugs are a wrong n. std::span<T> binds the pointer and the length into one value, so the length cannot be lost or mismatched; the callee checks i < s.size() once. For owning storage, std::vector::at() checks and throws, and std::array has a compile-time size. D1

Lifetime. Every pointer-like thing can dangle: a pointer or reference to a local that has returned, an iterator or pointer into a container that has reallocated (Figure 1), a std::string_view onto a temporary string that has been destroyed. The rule is to keep a view only as long as you can prove the owner outlives it; when in doubt, copy the value out. D1

Ownership. Decide, for every resource, who frees it. A single owner uses std::unique_ptr; transferring ownership is std::move, after which the old owner is null. Shared ownership uses std::shared_ptr with reference counting, at the cost of the count and the risk of cycles. A part that only looks uses a non-owning raw pointer, a reference, or a span — and must not outlive the owner. The bug is almost never "a raw pointer exists"; it is "two owners" (double free) or "a view outlived its owner" (use-after-free). D2

Layer 3 — the engineer's depth

The C++ Core Guidelines frame these as three profiles — bounds, lifetime and type safety — each a checkable subset of the language. The bounds profile bans pointer arithmetic and unchecked indexing in favour of spans and ranges; the lifetime profile tracks which pointers may dangle and flags escapes; the type profile bans unsafe casts and unions. Enforcement is partial and tool-assisted (a static analyser applies the rules), which is why they are "profiles" you opt into, not language rules. D3 The engineering point is leverage: a function that takes a span instead of (ptr, len) removes a whole class of caller mistakes at no run-time cost, because the span is just the pointer and the length you were passing anyway. D1

Lifetime is the subtler half, because a dangling view is often correct for a while — it worked in testing because the owner happened to still be alive. The reallocation case (Figure 1) is the archetype: the pointer is valid right up to the push_back that overflows capacity, then silently invalid. The discipline is to treat container mutation as invalidating all views into it (the standard specifies exactly which operations invalidate which iterators and pointers), and either re-acquire the view after mutation or copy the value out first. The lab's fixed version does the latter; AddressSanitizer confirms the buggy version reads freed memory (R2) and the fixed version is clean (R1). D1 R1 R2

Ownership through unique_ptr also makes exceptions safe for free: RAII releases on every path out of a scope, including the one an exception takes, so there is no "leak on error" path to forget. Freestanding and kernel code (curriculum 1.2) often forbids exceptions and the heap, so the same ideas appear as fixed-capacity containers and explicit owning handles; the principle — one owner, release in a destructor — is unchanged. D2

How the hardware actually does it

There is no hardware "bounds" or "lifetime"; the processor reads and writes addresses. span and unique_ptr compile to the same loads, stores and one free you would write by hand — the safety is in which code the compiler is allowed to emit, not in a run-time guard (except the explicit checks of at()). D1 A use-after-free is dangerous precisely because the freed bytes are real memory the allocator will hand to the next request; the hardware will happily read or write them. AddressSanitizer adds the missing notion of lifetime in software: it quarantines freed regions and poisons their shadow so a later access is caught, which is why the lab can show the bug at all. On a real deployment there is no such quarantine, and the read returns whatever the allocator reused the bytes for. D4

Worked example

Consider a function that returns the address of a reading so a caller can "watch" it: int* watch = &readings[0];. The vector holds two elements with some capacity; printing *watch is fine. Then a loop does readings.push_back(i) a thousand times. The first push that exceeds capacity allocates a larger block, copies the two elements plus the new one, and frees the old block — the block watch points into. Every later push_back is irrelevant to watch; the damage is done at the first reallocation. Reading *watch afterwards is a heap-use-after-free, and AddressSanitizer prints READ of size 4 with the freed-region note (R2). The fix is one of: copy the value out before growing (int first = readings[0];), reserve enough capacity up front so no reallocation happens, or re-index (readings[0]) after growth instead of holding a pointer. The lab's safe.cpp uses the copy-out and reserve forms and runs clean (R1). R1 R2

Where the analogy breaks


    

  • A torn-out page is visibly gone; freed memory is not. The allocator keeps the bytes and reuses them, so a stale pointer reads plausible-looking data, not a blank. That is what makes use-after-free exploitable rather than merely wrong. D4
    • 

  • A ledger page does not move while you read it; a vector's storage does. The most common dangling bug is not "freed" but "moved": a growing container relocates its storage, silently invalidating every pointer and iterator into it. D1
    • 

  • "One owner" is a type, not a note in the margin. In C++ ownership is encoded in the type (unique_ptr vs a raw view), so the compiler moves it for you; the ledger analogy makes it sound like a rule people remember, which is exactly the fragile version this chapter replaces.
    • 




Common mistakes and debugging


    

  • Symptom: a value read through a pointer is garbage after a container grew. Cause: a pointer or iterator kept across a reallocation. How to find it: AddressSanitizer names a heap-use-after-free with "freed by" at the reallocation. Fix: copy the value out, reserve first, or re-index after mutation.
    • 

  • Symptom: a double free or "corrupted" allocator message. Cause: two owners of the same resource (a raw pointer deleted while a smart pointer also owns it). How to find it: ASan reports "attempting double-free" with both frees. Fix: one owner only; hand out non-owning views, never a second owner.
    • 

  • Symptom: a string_view or span reads freed bytes. Cause: the view outlived the temporary or local it viewed. How to find it: ASan stack-use-after-scope or heap-use-after-free. Fix: keep the owner alive for the view's whole use, or store a value.
    •

Summary


    

  • Three disciplines prevent most memory bugs: stay in bounds, respect lifetimes, give each resource one owner.
    • 

  • std::span carries a length with the pointer so the bound is checked once and cannot be mismatched.
    • 

  • Pointers, references, iterators and views dangle when their referent ends — including when a container reallocates and moves its storage.
    • 

  • Ownership is a type: unique_ptr for one owner, shared_ptr for shared, a non-owning view for lookers.
    • 

  • RAII releases on every path, including exceptions, so there is no leak-on-error path to forget.
    • 

  • These choices cost nothing at run time (beyond explicit checks); the safety is in the code the compiler may emit.
    •
