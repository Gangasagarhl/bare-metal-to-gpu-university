Story hook

A delivery arrives at the castle with its own paperwork: "this crate contains two hundred items; unpack them onto shelf seven." A careless quartermaster reads "two hundred" and starts counting items off the crate — but the crate holds three, and the fourth count reaches past the crate into the next delivery, and the next. The paperwork was written by the sender, who may be careless or hostile, yet it was obeyed as if it were the castle's own count. The rule the castle learns the hard way: numbers that come with the goods are claims, not facts. Check them against what actually arrived before acting.

Devices and networks are exactly this: a USB stick, a network packet, a sensor, a radio link all hand your program lengths, counts, indices and offsets that an attacker may control. This chapter is the discipline for the whole boundary — treat every device-provided value as untrusted — and it ties together the bugs of F11-07, the safe patterns of F11-08, and the finding and hardening of F11-09 and F11-10, applied where they matter most.

What you will be able to do

  • Identify the untrusted values a device or protocol hands you: lengths, counts, indices, offsets, descriptor contents.
  • Validate every such value against what was actually received, in the overflow-safe form, before using it.
  • Explain why hardware channels (DMA) need the IOMMU as well as software checks (the runbook "Trust" row).
  • Diagnose an over-read caused by a trusted length from a sanitizer report.
  • Apply the validate-at-the-boundary rule to a parser and turn malformed inputs into clean rejections.
Jargon box
Untrusted input
Simple words: data from outside your program that an attacker might control. Analogy: paperwork written by whoever sent the crate. Precise: any value crossing a trust boundary — a file, a network packet, a device register or descriptor, a user-space pointer — that must be validated before use because its source is not under your control. D1
Trust boundary
Simple words: the line between code you control and data you do not. Analogy: the castle gate, where outside paperwork meets inside rules. Precise: the interface at which data of lower trust enters a higher-trust component; all validation must happen on the inside of it, once, before the data is used. D1
Descriptor
Simple words: a small record a device gives describing itself or its data. Analogy: the crate's paperwork. Precise: a device-supplied structure (e.g. a USB configuration descriptor with a wTotalLength, or a DMA descriptor with address and length fields) whose every field is attacker-influenceable and must be bounded. D2
DMA
Simple words: a device reading or writing memory directly, without the CPU copying each byte. Analogy: a courier allowed into the storeroom to fetch goods himself. Precise: Direct Memory Access — a device transfers data to/from memory over the bus; a malicious or buggy device can read or overwrite memory it was not meant to unless constrained. D3
IOMMU
Simple words: a guard between devices and memory that limits which memory a device may touch. Analogy: a gatekeeper at the storeroom with a list of shelves each courier may use. Precise: an input–output memory management unit that translates device addresses through per-device tables and blocks accesses without a mapping, containing a malicious device's DMA. D3
Fail closed
Simple words: when input is invalid, reject it and stop, rather than guessing. Analogy: refuse the crate whose paperwork does not match, do not unpack it anyway. Precise: a design in which an unexpected or malformed input leads to a safe refusal (error returned, operation aborted), never to undefined behaviour or a best-effort continue. D1

The idea in pictures

Figure 1 shows the lab's bug: a configuration descriptor claims a wTotalLength larger than the bytes actually received, and a parser that trusts it walks off the end of the buffer.

Layer 1 — the kid explanation

When a program talks to a device or a network, the other side sends not just data but numbers that describe the data: "there are two hundred items", "the name is at position fifty", "skip forward thirty bytes". A careless program believes those numbers and uses them to decide where to read and write — and if the number is wrong (by accident or on purpose), the program reads or writes somewhere it should not. The rule is simple and strict: never trust a number that came from outside. Check it against what you actually received before you use it, and if it does not fit, refuse the whole thing.

Layer 2 — the student explanation

The curriculum's universal method has a "Trust" row that states the rule for drivers: treat device-provided values — lengths, indices, descriptor contents — as untrusted, and remember that external devices (malicious USB, Thunderbolt/USB4) can attack through DMA and malformed descriptors, so enable the IOMMU. The same rule covers network packets and any protocol you parse. D1

Concretely, at every trust boundary, for every value that came from outside:

  • Lengths and sizes: check against the bytes actually received, in the overflow-safe form off <= size && len <= size - off (never off + len <= size, which can wrap — F2-44). Also bound them to a sane maximum (F11-07). D4
  • Indices: check i < count before use; a device can send an index past the array.
  • Offsets: check they land inside the buffer and that what they point to also fits.
  • Counts and loop bounds: a descriptor claiming a huge count or a zero advance can cause an over-read or a non-terminating loop; bound both.

The lab shows this with a USB-configuration-style descriptor. The buggy parser trusts wTotalLength and each descriptor's bLength and advances through them; given a four-byte blob that claims a total of two hundred, it reads past the end and AddressSanitizer reports a heap-buffer-overflow (R2, Figure 1). The fixed parser checks that wTotalLength is within the received bytes and that each bLength is at least its header and fits, and it rejects malformed blobs cleanly (R3). D2 R2 R3

Layer 3 — the engineer's depth

Validation must happen once, on the inside of the boundary, and the validated result must be the only thing the rest of the code sees — otherwise a value is checked in one place and used unchecked in another (a time-of-check/time-of-use gap). For a parser that means: copy or bound the input up front, carry lengths with pointers (a span, F11-08), and make every advance a checked step. The discipline pairs with F11-09: a boundary parser is exactly the thing to fuzz, because its whole job is to survive hostile input, and the lab's descriptor parser, the ELF reader and the MAVLink scanner are all the same shape — read a length, bound it, advance. D4

Software checks are necessary but not sufficient when a device can touch memory directly. A device doing DMA writes to physical memory over the bus; no amount of pointer validation in the driver constrains where the device itself writes. That is why the "Trust" row also says to enable the IOMMU: it sits between devices and memory and only permits a device to access memory the kernel explicitly mapped for it, so a malicious USB4/Thunderbolt device or a compromised peripheral cannot read secrets or overwrite kernel memory by DMA. The driver still validates descriptor contents (the device can lie about lengths and indices in the rings it shares), and the IOMMU contains the hardware channel; both layers are needed, as you saw building drivers in DR302. D3

Two further boundaries reuse the same rule. User-space pointers into a kernel (B12) are untrusted input: a system call's pointer and length must be range-checked and copied through a fault-tolerant routine, with SMAP as the hardware backstop (F11-10, F3-29). And protocol input from a radio or network — the MAVLink scanner of F11-09 — is untrusted in the same way: a length byte on the wire is a claim about bytes that may not be there. The unifying idea is that "device", "network" and "user space" are all just sources outside your trust boundary, and one rule covers them: validate against reality, bound to a maximum, fail closed. D1 D5

How the hardware actually does it

A memory-mapped device register is just an address; reading it returns whatever the device drives onto the bus, which the device chooses, so a value read from a register is as untrusted as a byte from the network — the hardware gives you no guarantee about it (F2-50). D2 For DMA, the device is a bus master: it issues its own memory transactions, and without an IOMMU those go to physical addresses the device names, anywhere in memory. The IOMMU is real hardware — a translation unit on the path from device to memory — that the kernel programs with per-device page tables; a device transaction to an unmapped address faults instead of succeeding, which is what contains a malicious device. The software lesson and the hardware lesson meet here: validate the numbers the device puts in the descriptors you read, and use the IOMMU to bound the memory the device can reach on its own. D3

Worked example

Take the lab's descriptor blob 04 02 c8 00: a four-byte configuration header with bLength 4, bDescriptorType 2, and wTotalLength = 0x00c8 = 200. Four bytes were received; the paperwork claims two hundred. The buggy parser reads wTotalLength, sets its loop limit to 200, and begins reading descriptor headers at offset 4 — which is already the end of the received data. Its first read of a byte at or past offset 4 is out of bounds, and AddressSanitizer reports a heap-buffer-overflow READ in parse_config (R2). The fixed parser first checks wTotalLength <= size (200 > 4, so it rejects) and would also check each descriptor's bLength is at least the two-byte header and that pos + bLength <= size; given the hostile blob it returns "rejected: malformed descriptor" without reading anything out of bounds (R3). On a well-formed blob — header plus two two-byte descriptors, wTotalLength 8 — the fixed parser accepts and reports two descriptors (R4). The whole difference is three bounds checks on values that came from the device. R2 R3 R4

Where the analogy breaks


    

  • A crate is physically bounded; a descriptor's claim is not. The paperwork can claim any number; nothing physical stops a length field from naming megabytes. That is exactly why the check must be explicit in software. D2
    • 

  • A quartermaster can see the crate is empty; a DMA device bypasses the gate entirely. A courier allowed into the storeroom (DMA) does not hand over paperwork to check — it fetches memory itself, which is why the IOMMU, not just descriptor validation, is needed. D3
    • 

  • "Refuse the crate" is clean at a gate; a device may keep sending. Failing closed on one bad descriptor is right, but a real driver must also handle a device that floods, stalls or disappears — robustness beyond a single rejection (the driver design note of DR302). 
    • 




Common mistakes and debugging


    

  • Symptom: an over-read or crash when a device sends a short or crafted transfer. Cause: a length or count from the device used without checking against the bytes received. How to find it: AddressSanitizer names a heap-buffer-overflow in the parser; the input has a length field larger than the data. Fix: check len <= size - off and bound to a maximum before use.
    • 

  • Symptom: a parser loops forever on some device input. Cause: an advance taken from the device that can be zero (a descriptor of length 0). How to find it: a timeout; the loop position never changes. Fix: require each advance to be at least the header size, and fail closed otherwise.
    • 

  • Symptom: validation exists but the bug still happens. Cause: a time-of-check/time-of-use gap — the value is checked once and re-read or re-used unchecked. How to find it: trace every use of the device value. Fix: validate once at the boundary and pass only the validated result inward (a bounded span).
    •

Summary


    

  • Every value from a device or network — length, count, index, offset, descriptor content — is untrusted and must be validated before use.
    • 

  • Validate once, on the inside of the trust boundary, in the overflow-safe form, bounded to a sane maximum, and fail closed.
    • 

  • The descriptor-length bug is the archetype: a parser that trusts wTotalLength or bLength walks off the received bytes.
    • 

  • Software validation does not constrain DMA; the IOMMU bounds the memory a device can touch directly, and both layers are needed.
    • 

  • "Device", "network" and "user space" are all sources outside the trust boundary; one rule covers them.
    • 

  • Boundary parsers are the prime target to fuzz (F11-09) and to review (F11-11); this discipline ties the course together.
