Story hook

Last term, Ngozi's team wrote a recipe card for the great kitchen hall that came close to the hall's own master team: their matrix multiply reached the percentage of the vendor library they had promised in MP3. This term the same card goes to the second building. The language of the card is the same. The rows are not: sixty-four helpers instead of thirty-two on the building's big machines, tables of a different size, and a tray machine that only takes its own trays.

The first week goes well. One copy of the card, a few lines changed, and every dish comes out right in both buildings. Then Ngozi's teammate Tomás tries the card on the second building's other kind of hall, the one with rows of thirty-two, using a smaller table setting he picked for it. Every dish is wrong, yet nothing looks broken: no smoke, no shouting, just plausible-looking plates with the wrong taste. Nobody had changed the recipe. They had only changed which table setting the card was used with.

This project is that semester: one recipe for both buildings, every MP3 test passing in the second building, tuning for its rows, tables and tray machine against its own master team, and an honest report of how close you got in each building, and why.

What you will be able to do

  • Build one source tree for AMD (several gfx targets in one binary) and NVIDIA (through HIP's NVIDIA path), with exactly one file that knows the platform.
  • Prove that every MP3 correctness test passes on an AMD GPU, for every kernel instance your tuning table can select, not only the one your development GPU uses.
  • Tune for AMD hardware (wave64, LDS, MFMA matrix instructions) towards targets frozen at gate R1, against rocBLAS and hipBLASLt measured by your own harness.
  • Explain each kernel's percentage of the vendor library on both GPUs, with profiler and ISA evidence for every reason, in a portability report whose every claim carries a tag.
  • Lead your project through review gates R1, R2 and R4 with packets of rerunnable evidence, and write an incident report when something breaks.
Jargon box
Device key
Simple words: the short name your program uses to look up the settings for the GPU it found. Analogy: the name on the door of the hall, used to find that hall's sheet of table sizes. Precise: in this project, the AMD target name taken from hipDeviceProp_t::gcnArchName up to the first colon, or sm_XY built from major and minor on HIP's NVIDIA path, where the installed HIP 5.7 headers do not fill gcnArchName. H1 R1
Fail-loud dispatch
Simple words: if the program meets a GPU it has no settings for, it stops and says so instead of guessing. Analogy: a helper who finds no sheet for this hall asks, instead of using another hall's sheet. Precise: a run-time selection of a kernel instance from a table keyed by device key, in which a missing key, a wave width that differs from the table, or an LDS need above the device limit ends the program with an error that names the problem; there is no default row. R1
Portability report
Simple words: the final document that says, kernel by kernel, how close you came to each vendor's library on each GPU, and why. Analogy: one table comparing your card with each building's master team. Precise: the MP4 deliverable required by the card: "each kernel's percentage of the vendor library on both GPUs, with reasons", produced from raw benchmark records by a generator, with every number labelled by GPU, driver and toolkit versions and every reason tagged with its evidence. C2 C1
Portability gap
Simple words: how much worse your kernel does, relative to the vendor library, on one GPU than on the other. Analogy: the card is nearly as good as the master team in one building but much further behind in the other. Precise: for kernel k and size n, the difference (in percentage points) between its percentage of the vendor library on the NVIDIA GPU and on the AMD GPU; it compares two ratios, each against its own platform's library, so it says nothing about which GPU is faster. C1
Targets digest
Simple words: a short fingerprint of the target numbers, written down when the reviewers approve them, so any later change shows. Analogy: the inspector's stamp on the plan, which no longer matches if someone redraws a wall. Precise: the first 16 hexadecimal digits of the SHA-256 of the canonical JSON of targets_percent, recorded at R1; report.py warns whenever the current targets do not match it, enforcing curriculum 13.4's rule that targets are never lowered without the owner's approval and a log entry. R9 C1
Packed FP32 FMA
Simple words: one instruction that does two single-precision multiply-adds at once. Analogy: one helper stirring two pots with two hands in one movement. Precise: v_pk_fma_f32, which the compiler emitted for gfx90a and gfx942 in this build alongside scalar v_fmac_f32; its operand pairs indicate two FP32 lanes of work per instruction; the ISA reference guide's description is title only here (D3). R3 D3
Dual-issue pair (gfx11)
Simple words: on the newer AMD design, two simple instructions written on one line that are issued together. Analogy: two helpers in a row given one combined instruction. Precise: an assembly line of the form v_dual_fmac_f32 … :: v_dual_fmac_f32 …, emitted for gfx1100 in this build; when pairing is allowed is defined by the RDNA3 ISA guide (title only, D3). Counting instructions on gfx11 must count both halves. R3 D3
Static instruction count
Simple words: how many times an instruction appears in the compiled program text, not how often it runs. Analogy: counting the steps written on the card, not the steps the helpers actually did. Precise: a count over the assembly of one kernel; it equals the work per loop iteration only when the loop body is fully unrolled, and is a check of code generation, not a performance measurement (dynamic counts come from the profiler, D5). R3
Drift check
Simple words: a test that fails when your copy of something no longer matches the original. Analogy: comparing your copy of the master card with the original before every service. Precise: an automated comparison between data copied from another component (here MP3's shape matrix) and its source, run in the lab so that the copy cannot silently diverge. R8

Terms from earlier chapters used here: performance portability, tuning table, instance (kernel template), percentage of reference, fat binary (F7-20, F7-19, F7-18); rocBLAS, hipBLASLt, MFMA (F7-17); LDS, wave64 and wave32, VGPR (HP302); unit roundoff, justified test tolerance (MA302, F6-25); mutation testing; design-review gate, entry criteria, gate outcome, review packet, independent reviewer (F12-29); blameless post-mortem (F12-18); claims ledger.

M1 — one source tree building for both vendors

Entry criteria. MP3's GEMM kernels and harness exist and pass MP3's suite on the NVIDIA GPU (or, for a learner who took only MP3's GEMM part, MP3 milestones 1–3 are signed). The HP401 labs F7-16, F7-17 and F7-20 have been run. An AMD machine (or cloud instance) has been chosen and its ROCm compatibility recorded (unverified box below).

Tasks.

  1. Run the starter lab (section Lab). It is a scaled-down M1: one SGEMM, three instances, four tuning rows, three builds.
  2. Move each MP3 kernel into the tree: hipify it (F7-04), then remove every warp-size assumption, keep lane masks 64-bit, and make every loop stride and launch size come from the instance's own constants, never from a literal.
  3. Split each kernel as Listing 2 and Listing 3 do: the per-work-item work in MP4_HD functions, the kernel a thin wrapper with the barriers. This is what lets one text run on AMD, on NVIDIA and in the CPU emulator.
  4. Write the tuning table with one row per device key you will ever run on, and fail loudly on any other.
  5. Set up CI: build the fat binary and the NVIDIA path, run the CPU suite, the drift check, the hazard scan and the ISA summary (the starter lab's run.sh is the seed).
  6. Write the R1 packet (gate R1 below), including the targets file.

Evidence that M1 is done. CI logs showing the bundle listing with every AMD target you named, the NVIDIA-path build, the CPU suite passing for every instance with the seeded faults caught, zero unexplained hazard-scan hits, and the ISA summary per target. The program run on each GPU prints its device key and the instance it chose.

M2 — all MP3 correctness tests pass on AMD

Entry criteria. R1 passed; targets frozen; M1 evidence green.

Tasks. Run MP3's full correctness suite on the AMD GPU for every instance in the tuning table (not only the one the table selects for that GPU), in every MP3 precision; then on the NVIDIA GPU through HIP's NVIDIA path. Use the same tolerance header and the same shapes as MP3 (the drift check proves it). Run the AMD address-sanitizer support that your ROCm version documents (unverified box) on the smallest shapes. Keep MP3's seeded faults and add one per new instance family.

Evidence. One table per GPU: kernel × instance × precision × shapes passed, worst error over bound, with the GPU, driver and toolkit lines printed by the tools themselves. A skipped case is not a pass.

Curriculum E9's first acceptance test, verbatim: "All E1–E8 correctness tests pass on an AMD GPU (and, through HIP's NVIDIA back end, on an NVIDIA GPU)." For MP4 the E1–E8 tests are MP3's suite. C1

M3 — AMD-specific tuning to pre-set targets

Entry criteria. M2 passed on the AMD GPU; the reference libraries installed and their versions recorded; the harness measures your kernel and the library with the same protocol (warm-up, then the median of at least 20 timed runs with device events, fixed clocks if the driver allows it and the setting recorded) C1.

Tasks. One documented step at a time, each with its own row in a speed table, its resources from the ISA summary, and a profiler capture:

  • Wave64. Workgroup sizes that are whole waves on every target; work per work-item re-chosen for 64-lane waves; cross-lane code with 64-bit masks (F7-08, F7-12).
  • LDS. Tile depth and padding re-chosen against the LDS banking and size documented for your GPU (F7-11, F7-16); bank-conflict counters before and after.
  • Registers and occupancy. VGPR count per instance from the metadata, occupancy from the profiler (F7-10); never trade a spill for occupancy without measuring.
  • MFMA. The mixed-precision GEMM on matrix instructions; the disassembly must show v_mfma in the inner loop (curriculum E7) and the result must pass MP3's FP16/BF16 tolerance (F7-17).
  • Instances, not one kernel. Add instances where one shape class needs it (tall-skinny, short-wide); the tuning table records which instance wins for which GPU, and why, with the measurement id.

Evidence. Raw benchmark records (CSV) for own kernel and library at the three R1 sizes; the speed table per step; the ISA summary per step; profiler exports for the final instance; the report's verdict per target. Curriculum E6/E7's acceptance wording applies: "your kernel reaches X % of cuBLAS/rocBLAS SGEMM on your GPU" and "Reaches X % of cuBLAS/hipBLASLt half-precision GEMM; the disassembly shows the matrix instructions in the inner loop." C1

Layer 3 — the engineer's depth

Targets, references and the measurement protocol

MP4 inherits MP3's rule: targets are written before the work and frozen at R1; "the agent never lowers X after the fact without your explicit approval and a log entry" C1. The reference is "the vendor library on the same GPU, same data type, same sizes, measured by the same harness"; peak numbers from data sheets are context, not the target C1. For MP4 that means rocBLAS for FP32 GEMM and hipBLASLt for the mixed-precision GEMM on the AMD GPU, and MP3's cuBLAS/cuBLASLt references on the NVIDIA GPU. The curriculum offers a starting range ("sensible first targets are often in the 50–80 % range for GEMM ... but your GPU decides") C1; your R1 reviewers decide with your F7-16/F7-17 results in hand. The starter lab's targets.json has every target null until R1, and report.py prints "targets not frozen yet" until a digest is recorded (R9).

How to analyse portability

A percentage of the vendor library is a ratio against a different denominator on each GPU, so the portability gap of a kernel has three possible sources, and the report must say which: (1) your kernel uses one GPU's resources worse than the other's (tile sizes, wave width, LDS layout, missing matrix path); (2) the two libraries differ in how close they come to their own hardware for that operation, type and size; (3) the measurement differs (clocks, warm-up, timer, data). Evidence for (1) is the ISA summary and profiler counters of your kernel per target; for (2), the library's own kernel resources and counters, captured by the same profiler; for (3), the environment lines and the protocol in the raw records. A reason without one of these is an opinion, and the report generator does not print opinions: it prints numbers, and you add tagged sentences.

Claim tags in your report

Tag every factual sentence of the report and the slides, as this handbook does. Use one prefix per kind of evidence: M a raw measurement record (file and row), P a profiler export, I an ISA summary or disassembly excerpt, T a test log, D a vendor document you opened (title, version, section), G a gate record. A sentence such as "i1 loses to i0 on gfx942 because the compiler kept 96 of 256 multiplies unfused" needs an I tag for the instruction counts and an M tag for the loss; without the M tag it is a hypothesis and must be written as one. The claims ledger of F12-30 collects them for R4.

Risks and safety

Safety

Read the university's safety rules, in particular "GPU labs need a GPU" and the firmware rules. MP4 has no moving parts, but real-hardware steps can damage machines and budgets: installing GPU drivers and ROCm on a computer the learner depends on can leave it without a working display or boot; do it on a dedicated machine or a cloud instance, with a recovery path. Fixing clocks or changing power limits needs administrator rights and the machine owner's approval; record the setting and restore it. Never flash GPU firmware for this project. On shared or cloud machines, follow the owner's supervision rules: who may install, who approves spending, and when long benchmark runs may occupy the GPU. Learners below L3 do not administer GPU machines alone.

How the hardware actually does it

The same source becomes different machine code per target, and the starter lab's ISA summary (Listing 10) shows how. All three AMD targets kept LDS exactly as the instance arithmetic predicts (8448, 6272 and 6400 bytes) and reported their wave width in the kernel metadata: 64 for gfx90a and gfx942, 32 for gfx1100 R3. No instance spilled registers. The FP32 kernels contain no v_mfma, as expected: matrix instructions appear only when you write the mixed-precision path, and HP401's run showed that the 32×32×8 FP16 MFMA builtin compiles for gfx908, gfx90a and gfx942 but is refused for gfx1030 and gfx1100 ("needs target feature mai-insts"), where gfx1100 has v_wmma_f32_16x16x16_f16 instead R10. On a CDNA GPU your M3 matrix path is MFMA; an RDNA3 row in your report needs a WMMA path or an honest "no matrix path".



Three things in this table matter for M3. First, how the FP32 multiply-adds are encoded differs: gfx90a and gfx942 use packed v_pk_fma_f32 (counted as two) next to scalar v_fmac_f32, and gfx1100 uses dual-issue pairs. Second, for instance i1 on gfx90a and gfx942, 96 of the 256 multiplies per stage were not fused (v_pk_mul_f32 followed by separate adds), while gfx1100 and NVIDIA's sm_80 (256 FFMA, 0 FMUL) fused all of them R3 R4. Unfused operations round twice, so bitwise results may differ between targets and from MP3's NVIDIA results; MP3's tolerance covers both orders and roundings, which is why MP4 compares against a bound, never against golden values (F6-25). Why the compiler chose this for one instance is a question for M3, to be answered with the ISA guide and a measurement, not assumed. Third, VGPR counts per lane differ by target (74, 76 and 54 for i0); what that means for occupancy depends on each GPU's register file and wave slots, which you take from the ISA guide of your GPU (D3) and confirm in the profiler (D5).

Worked example


1. Resources of an instance, before the compiler confirms them


For an instance with block tile BM × BN, stage depth BK, work-item tile TM × TN and padding PAD:


    

  • work-items = (BM / TM) · (BN / TN); for i2 (32, 64, 16, 4, 4, 4): 8 · 16 = 128.
    • 

  • LDS bytes = 4 · (BK · (BM + PAD) + BK · BN); for i0: 4 · (16 · 68 + 16 · 64) = 4 · 2112 = 8448; for i1 (128, 64, 8, 8, 4, 4): 4 · (8 · 132 + 8 · 64) = 4 · 1568 = 6272; for i2: 4 · (16 · 36 + 16 · 64) = 4 · 1600 = 6400.
    • 

  • multiply-adds per work-item per stage = BK · TM · TN = 256 for all three; FMAs per LDS read = TM · TN / (TM + TN) = 2.00 for i0 and i2, 32 / 12 = 2.67 for i1.
    • 



The suite prints the same numbers from the code (R1), the compiler reports .group_segment_fixed_size 8448, 6272 and 6400 on all three AMD targets, and FMA + MUL = 256 per kernel wherever the stage loop was fully unrolled (R3). Three independent routes agree, which is what an R1 reviewer wants to see before trusting the instance table.


2. Lane use of each tuning row


Lane use = B / (⌈B / W⌉ · W) for B work-items and wave width W (F7-20). Every row of the starter table has B = 256 or 128 and W = 64 or 32, so every row is 100 % (suite output, R1). A row giving gfx90a an instance of 96 work-items would be 96 / 128 = 75 %; the suite rejects rows whose work-items are not a whole number of waves.


3. A report row, from records to a sentence


Percentage of library = tref / town · 100, since both do the same 2MNK operations. In the fixture records (invented numbers that test the generator, not measurements), the AMD row at 4096 has town = 100.0 ms and tref = 75.0 ms: 75.0 %, which meets a fixture target of 70 %; the NVIDIA row has tref = 60.0 ms: 60.0 %, below 70 % R9. The portability gap is 60.0 − 75.0 = −15.0 points (the kernel does relatively worse on NVIDIA). The sentence you would then owe is of the form "at 4096 the kernel reaches 75.0 % of rocBLAS [M…] but 60.0 % of cuBLAS [M…] because …", where the reason needs I and P tags on both GPUs.

Where the analogy breaks


    

  • "Two buildings" suggests two designs. The starter table alone has three AMD targets with two wave widths and different FMA encodings (R3), plus the NVIDIA GPU; MP4's "both vendors" is four or more targets.
    • 

  • A master team in the story is one fixed yardstick. A vendor library selects among many kernels per shape and type, and its quality differs per operation and version; the percentage can exceed 100 % at some sizes and that is a finding to explain, not a victory.
    • 

  • The story's wrong dishes taste wrong at once. A GPU kernel reading stale LDS returns plausible numbers (the forensic lab's C[0] values look normal); only a test against a bound finds it.
    • 

  • The inspector checks the building. Gate reviewers check evidence about a program, and the evidence can be rerun: a reviewer who reruns the suite learns more than one who reads a summary.
    • 




Common mistakes and debugging


    

  • Symptom: correct on the development GPU, wrong on another GPU with plausible values. Cause: an instance never tested, often with a literal stride or size. How to find it: run the suite for every instance (Listing 8); compare the instance per row. Fix: derive every stride from the instance; test every instance in CI.
    • 

  • Symptom: "no tuning row" on a new machine. Cause: its device key is new (or has a feature suffix your parser did not expect). Fix: add a row with evidence after measuring; never add a default.
    • 

  • Symptom: bitwise differences between AMD and NVIDIA results. Cause: different fusion and summation (R3, R4). Fix: none needed if inside MP3's bound; never compare against golden values from the other GPU.
    • 

  • Symptom: no v_mfma in the "matrix" kernel. Cause: the matrix path is not compiled for this target (wrong __gfx*__ guard, the F7-17 forensic case). Fix: a per-target path that fails loudly when no matrix path exists.
    • 

  • Symptom: a percentage that jumps between runs. Cause: clocks, warm-up, or the library choosing a different kernel. Fix: the 13.4 protocol, environment lines, the library's kernels in the profiler.
    • 

  • Symptom: drift check fails after MP3 changed. Fix: update shapes.hpp and rerun; the check exists so that this is loud.
    •

Forensic lab answer key


Observation. Only i2 fails: 4095 of 4096 elements at 64×64×64 and 1023 of 1023 at 33×31×65; i0 and i1 (256 work-items) have 0 bad elements (R5). The C[0] values (−1.107581 and +0.726167 instead of +0.053156 and +1.894725) are ordinary-looking numbers, not −7 and not NaN: the kernel wrote every output, from wrong inputs.


Hypotheses. "Wave32 breaks it": ruled out, the CPU emulator has no waves and still fails for i2 only. "LDS too small on gfx1100": ruled out, the failure occurs on the CPU, and i2 needs 6400 bytes, less than i0. "i2 is wrong": partly right, but the production kernel with i2 passes all 12 shapes in the suite (R1); the difference is the loader.


Root cause. The loaders in mutantStride256 step by the literal 256 instead of Cfg::THREADS. With 128 work-items, work-item t writes elements t, t+256, … only: for i2's A stage (BM·BK = 512 elements) indices 128–255 and 384–511 are never written, and for the B stage (BK·BN = 1024) indices 128–255, 384–511, 640–767 and 896–1023. Those LDS cells keep values from an earlier stage or workgroup, so results are plausible but wrong. On a GPU, LDS holds whatever was there before.


Why CI stayed green. The gfx90a, gfx942 and sm_80 rows select i0 (256 work-items), for which the literal happens to equal the instance's work-items; only the gfx1100 row selects i2, and CI never ran on that GPU or for that instance.


Fix and verification. Use Cfg::THREADS as the stride (as Listing 2 does); rerun the CPU suite for every instance (all pass, R1) and the GPU suite on gfx1100. Prevention. CI runs the CPU suite for every instance in kInstances; the hazard scanner gains a rule for literal loop strides in device code (F7-20's rules look for 32-lane assumptions and flagged nothing here, R6); a static_assert or review question "does any constant in the kernel assume a workgroup size?"; at R1, every tuning row's instance must have passing evidence. How the evidence was produced. forensic_stride.cpp runs the seeded loader through the F6-21 emulator for each instance (R5).
