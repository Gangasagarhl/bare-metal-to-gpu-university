Story hook

Amara has rewritten every card in the shared cookbook language. The second building will not be ready for another month, but her own building can read the shared language too: its prep chef translates each card back into the old building's words and cooks it on the old stoves. So she tests every card at home. Everything tastes right. She signs the cards off and sends them across the road.

The note comes back the next day, from Ines, the second building's head cook: "Card 17, the sauce: the card says pass the spoon along the row, sixteen places, then eight, four, two, one, and the first helper in every row puts the total in the pot. In your building a row is 32, so that reached everyone. Ours are 64. The spoon never crossed the middle of the row, and only the first helper of each row poured. Half the sauce never got into the pot. The card was correct for your building. It was never correct for ours." This chapter is about what testing at home can and cannot prove.

What you will be able to do

  • Build and run HIP code through HIP's NVIDIA back end, and show from the executable and the generated code that it is a CUDA program underneath.
  • State exactly what a passing run on NVIDIA proves about a HIP port, and what it cannot prove.
  • Explain how warpSize and the shuffle functions are defined on each back end in your HIP version, and read the consequences in PTX and AMD ISA.
  • Diagnose a reduction that is correct on NVIDIA and wrong on AMD from per-lane outputs, and fix it without hard-coding a lane count.
  • Apply curriculum E9's acceptance test to your E1–E5 ports on the back ends you have, marking the rest untested on hardware.
Jargon box
NVIDIA back end (of HIP)
Simple words: the way of building HIP code so that it runs on NVIDIA GPUs, by turning it into CUDA. Analogy: the first building's prep chef cooking a shared-language card on the old stoves. Precise: HIP's NVIDIA platform: hipcc runs nvcc (R1); HIP's headers map every HIP name onto CUDA (F7-03); the result is an ordinary CUDA fat binary linked to the CUDA runtime (R8). D1 R1 R8
warpSize (HIP)
Simple words: the number of lanes in the warp or wavefront the kernel runs on, readable inside a kernel. Analogy: how long a row of helpers is in the building where the card is cooked. Precise: a built-in available in device code; in HIP 5.7 on AMD it is static constexpr int warpSize = __AMDGCN_WAVEFRONT_SIZE; (a compile-time constant per target: 64 for gfx90a, 32 for gfx1030 in R2), and on NVIDIA it is CUDA's warpSize, which PTX reads from the special register WARP_SZ (R4). H1 R2 R4
Shuffle (cross-lane exchange)
Simple words: every lane reads a value from another lane of the same warp or wavefront in one step. Analogy: passing the spoon along the row. Precise: HIP's __shfl_xor(var, lane_mask, width = warpSize) returns var from lane self ^ lane_mask; on AMD it is built on ds_bpermute, on NVIDIA HIP defines it as __shfl_xor_sync(0xffffffff, …) (R5). H1 R5
Butterfly reduction
Simple words: adding up the values of a group by exchanging with partners at distance 16, 8, 4, 2, 1 (or 32 first, for 64 lanes), so that every lane ends with the total. Analogy: pairs of helpers swapping and adding, then pairs of pairs, until the whole row knows the sum. Precise: a reduction over 2^k lanes with k steps of v += shfl_xor(v, 2^j); it covers exactly the lanes reachable by the offsets used, so its first offset must be half the group size. D3 R6
Untested on AMD hardware
Simple words: an honest label for a result that was only checked on NVIDIA or only compiled for AMD. Analogy: "tasted at home only" written on the card. Precise: the university's AH-26 marking, which the F7 faculty requires when the NVIDIA back end replaces an AMD GPU for a lab (guide 5.12, hardware requirement).

The idea in pictures

Figure 1 is the course's forensic case in one picture: a butterfly reduction whose first offset is 16, on a 32-lane warp and on a 64-lane wavefront. With 32 lanes the offsets 16, 8, 4, 2, 1 connect every lane to every other. With 64 lanes they never connect the two halves: lanes 0–31 end with the sum of their half, lanes 32–63 with the sum of theirs, and a single leader per wavefront adds only one half to the total.

Layer 1 — the kid explanation

HIP code can be built for NVIDIA GPUs too. Then HIP becomes CUDA again: every HIP word is turned into its CUDA word, and the program runs exactly like a CUDA program. That is useful. If you only have an NVIDIA GPU, you can still check that your HIP port works.

But it checks the port in the old building. In the old building a row of helpers is always 32 long. If your program quietly assumes "rows of 32", the old building will never notice, because there the assumption is true. In the new building many rows are 64 long, and the same program gives the wrong answer without any error message.

So you use the NVIDIA back end for what it is good at: checking that the HIP calls are right and that the program works with 32 lanes. And you use two other checks for the rest: compiling for AMD, which needs no GPU and catches leftover CUDA words; and running on an AMD GPU, which is the only way to prove the program is right with 64 lanes. When you have no AMD GPU, you write "untested on AMD hardware" next to the result.

Layer 2 — the student explanation

Building for NVIDIA

Two ways were used in this course. With hipcc: HIP_PLATFORM=nvidia hipcc -std=c++17 -x cu file.hip (this container also needed CUDA_PATH=/usr, F7-01). With HIP_PLATFORM=nvidia, hipcc runs /usr/bin/nvcc -Wno-deprecated-gpu-targets -lcuda -lcudart -L/usr/lib64 -std=c++17 -x cu plus your file (R1). R1 With CMake: compile the .hip file as CUDA (F7-06, Listing 3). In both cases nvcc compiles the file, HIP's headers detect nvcc and select their NVIDIA implementation, and every HIP call becomes an inline call to CUDA (F7-03). D1 H2 nvcc options pass through: -arch=sm_80, -gencode …, -ptx, -cubin all worked in this build (R4, R7, R8).

What you get: a CUDA program

The executable is indistinguishable in structure from one built by nvcc from CUDA source. R8 lists the GPU code inside two executables built with the same -gencode options, one from vec_add.hip through the NVIDIA back end, one from saxpy.cu with plain nvcc: the same entries, sm_80 and sm_86 machine code plus sm_86 PTX. R8 One difference is visible: the HIP build lists the shared library libcudart.so.12, because hipcc passes -lcudart; the plain nvcc build lists none, so it carries the CUDA runtime inside the executable. Either way, the runtime underneath is NVIDIA's: error names are CUDA's (cudaErrorNoDevice in R9 and R10), and NVIDIA's tools (cuobjdump, Compute Sanitizer, the Nsight profilers) work on it as on any CUDA program. D2

The generated code is CUDA's too. F7-05's vecAdd, built this way, becomes the PTX and SASS of R7: the index with mad.lo.s32, the bounds check as a predicate %p1 and a branch, and in SASS a predicated @P0 EXIT. R7 Compare with the AMD ISA of the same source in F7-05: the work is the same, the machines are not.

What a passing NVIDIA run proves

If the HIP port builds and passes its correctness tests on an NVIDIA GPU through the NVIDIA back end, you know: the HIP calls are used correctly (they become the CUDA calls you trust), memory is allocated, copied and freed correctly, launches are configured correctly, and the algorithm is correct for 32-lane warps. You do not know: whether the source compiles for AMD (leftover CUDA names compile on NVIDIA: F7-03, R5 there), whether the algorithm is correct for 64-lane wavefronts, whether AMD-specific intrinsics are used correctly, or anything about AMD performance. warpSize on each back end

The fix for hidden lane counts is the built-in warpSize, but its nature differs by back end, and it is worth seeing the difference in generated code. On AMD, HIP 5.7 declares static constexpr int warpSize = __AMDGCN_WAVEFRONT_SIZE; (R5, line 86): the compiler knows the value for each target and writes it as a constant. Listing 4's kernel out[0] = warpSize; became v_mov_b32_e32 v1, 64 for gfx90a and v_mov_b32_e32 v1, 32 for gfx1030, with matching .wavefront_size metadata (R2). R2 On NVIDIA the same kernel's PTX reads mov.u32 %r1, WARP_SZ; (R4): a value PTX leaves to the hardware, not a literal. R4 D4 Consequence for code: a loop for (offset = warpSize / 2; …) is fully unrolled into a known number of shuffles on AMD and stays a loop in NVIDIA's PTX. R3 counts exactly that: the fixed kernel has 6 shuffles for gfx90a (offsets 32 to 1), 5 for gfx1030 (16 to 1), and a single shuffle inside a loop in the sm_80 PTX. R3

Layer 3 — the engineer's depth

The shuffle in two headers

R5 prints both definitions of __shfl_xor in this HIP version. AMD (amd_warp_functions.h lines 403–408): the source lane is self ^ lane_mask, replaced by self if it falls outside the caller's width-sized segment (index >= ((self + width) & ~(width - 1))), and the value moves with __builtin_amdgcn_ds_bpermute(index << 2, var). NVIDIA (nvidia_hip_runtime_api.h line 558): #define __shfl_xor(...) __shfl_xor_sync(0xffffffff, __VA_ARGS__). R5 H1 Three consequences:

  1. The HIP form has no mask argument, and on NVIDIA it supplies the full 32-lane mask 0xffffffff; all 32 lanes must therefore reach the shuffle together, as CUDA's _sync rules require. D4
  2. The default width is warpSize, so on gfx90a a shuffle can reach any of 64 lanes; whether it does depends only on the offsets your loop uses.
  3. Lane masks that come back from votes (__ballot) are 64-bit on AMD: unsigned long long int __ballot(int predicate) (R5, line 715). Storing one in an unsigned int, as CUDA code often does with __ballot_sync's 32-bit result, drops lanes 32–63. F1-57 introduced this; HP302 (F7-08 onward) measures it.

Writing lane-count-independent code

The rules that make a kernel correct on 32 and 64 lanes, each tied to this chapter's evidence:

  • Start butterflies and tree loops at warpSize / 2, never at 16 (Listing 2 versus Listing 1; R6 shows both totals).
  • Choose leaders and lane ids with warpSize: threadIdx.x % warpSize == 0, lane = threadIdx.x % warpSize, warp = threadIdx.x / warpSize.
  • Size per-warp shared-memory arrays from blockDim.x / warpSize (or a maximum that covers the smallest lane count), not from blockDim.x / 32.
  • Keep lane masks in 64-bit types (unsigned long long or uint64_t) in portable code, and count bits with 64-bit population counts.
  • Make block sizes a multiple of 64 where the algorithm needs whole wavefronts.
  • Test with per-lane outputs. A single total hides which lanes went wrong; writing every lane's value (Listing 1's lanes array) shows the pattern of the bug at once.

These are the curriculum's own requirements written as code rules: E3 accepts a reduction only if "The same source runs correctly with wave64 on AMD (no hidden 32-lane assumption)", and guide 13.4 forbids a hard-coded warp size in portable code. Curriculum, track E.

Not verified — check before relying on this

Newer HIP versions may add _sync warp functions with 64-bit masks and may change how warpSize is declared (for example, no longer a compile-time constant). The definitions in this chapter are those of the installed HIP 5.7.1 headers (R5). Check the HIP documentation's warp cross-lane functions section and the release notes of your HIP version (D1) before relying on warpSize being usable in constant expressions.

How the hardware actually does it

On an NVIDIA GPU a shuffle is one SIMT instruction (SASS SHFL, from PTX shfl.sync) that moves 32-bit values between the 32 lanes of a warp through the register file's crossbar; lanes outside the warp are not reachable. D4 On AMD CDNA hardware the HIP shuffle is ds_bpermute_b32, an LDS-unit instruction that lets each of the wavefront's 64 lanes read a value from any lane, addressed by a byte index (hence index << 2 in the header); it uses the LDS hardware's crossbar without allocating LDS memory. D5 H1 R3 shows the instruction counts: five ds_bpermute_b32 for the ported loop on both AMD targets, six for the fixed loop on gfx90a. The hardware is capable of crossing the middle of a 64-lane wavefront; the ported loop never asks it to. A wrong answer on AMD here is not a hardware or compiler bug; it is an algorithm written for a 32-lane machine.

Not verified — check before relying on this

The descriptions of SHFL and of ds_bpermute_b32's use of the LDS crossbar are from memory of D4 and D5, not from opened documents, and nothing was run on either GPU. The instruction names and counts are this build's real compiler output (R3).

Worked example

Question. Listing 1 sums one block of 64 threads with inputs 1, 2, …, 64 (expected 64 × 65 / 2 = 2080). Predict every lane's value after the loop and the total, on a 32-lane warp machine and on gfx90a, for the ported loop (first offset 16) and for the fixed loop (first offset warpSize / 2).

  1. 32 lanes, ported. Offsets 16, 8, 4, 2, 1 form a complete butterfly over 32 lanes: every lane of warp 0 ends with 1 + … + 32 = 32 × 33 / 2 = 528; every lane of warp 1 with 33 + … + 64 = 2080 − 528 = 1552. Leaders are threads 0 and 32 (% warpSize with 32): total 528 + 1552 = 2080. Correct.
  2. 64 lanes, ported. The same offsets stay within lanes 0–31 and within 32–63 (an XOR with a value below 32 never changes bit 5 of the lane number). So lanes 0–31 hold 528, lanes 32–63 hold 1552, exactly as on 32 lanes. But now there is one leader, thread 0 (% 64): total 528. Wrong by 1552.
  3. Fixed, 32 lanes. warpSize / 2 = 16: identical to step 1. 2080.
  4. Fixed, 64 lanes. Offsets 32, 16, 8, 4, 2, 1: a complete butterfly over 64 lanes. Every lane holds 2080; one leader adds 2080. Correct.

Check. R6, the university's lane model running the same loop with HIP 5.7's __shfl_xor rule, prints exactly these values for all four cases (lane tables and totals 2080, 528, 2080, 2080). Note the per-lane tables of cases 1 and 2 are identical: the lanes did the same thing on both machines; only the number of leaders changed. That is why the evidence must include per-lane values and the leader rule, not only the total.

Where the analogy breaks


    

  • "Testing at home" sounds like a weaker version of the real test. It is a different test: it can find bugs the AMD run would also find (API misuse), and it is blind to a whole class (lane-count assumptions), however carefully it is done.
    • 

  • The second building's rows are not always 64. gfx1030 compiled to 32 lanes (R2), so a 32-lane assumption can pass on some AMD GPUs too. "Works on my AMD GPU" is also a statement about one lane count.
    • 

  • In the kitchen, Ines could see the unstirred half. On the GPU nothing is visible: no error, no warning, a plausible number. Only a test against a reference, or per-lane outputs, reveals it.

Summary


    

  • HIP's NVIDIA back end is CUDA: hipcc runs nvcc, HIP names become CUDA calls, the executable is a CUDA fat binary using the CUDA runtime and tools.
    • 

  • A pass on NVIDIA proves the API use and the algorithm for 32 lanes; it does not prove AMD compilation, wave64 correctness or AMD performance.
    • 

  • In HIP 5.7, warpSize is a per-target compile-time constant on AMD (64 for gfx90a, 32 for gfx1030) and PTX's WARP_SZ on NVIDIA.
    • 

  • HIP's __shfl_xor has no mask; on NVIDIA it expands to __shfl_xor_sync(0xffffffff, …); on AMD it uses ds_bpermute over the whole wavefront.
    • 

  • A butterfly starting at 16 leaves a 64-lane wavefront in two halves; with one leader per wavefront the total loses one half. Start at warpSize / 2.
    • 

  • Per-lane outputs make lane-count bugs visible; totals hide them.
    • 

  • Nothing ran on a GPU in this build: lane values are from the university's model, and GPU results are untested on hardware on both vendors.

Forensic lab answer key


Observation. The two lane tables are identical: lanes 0–31 hold 528, lanes 32–63 hold 1552 on both machines. The totals differ: 2080 on the 32-lane machine, 528 on the 64-lane machine (R6). The ported kernel compiles to 5 ds_bpermute_b32 on gfx90a (R3), one per offset 16, 8, 4, 2, 1; gfx90a's wavefront is 64 lanes (R2).


Hypotheses. (1) AMD shuffle bug: ruled out; the lane values on 64 lanes are exactly what the header's rule gives for these offsets, the same as on 32 lanes. (2) Lost atomics: ruled out; the total equals exactly lane 0's value, one leader's contribution. (3) 32-lane assumption: confirmed. (4) Uninitialised total: ruled out; the total equals a lane value exactly, and the host sets it to 0 (hipMemset).


Root cause. Line 21 starts the butterfly at 16, so offsets never reach across lane 31/32 on a 64-lane wavefront; line 27's leader rule (% warpSize, correctly ported) makes one leader per 64 lanes. Lane 0 holds only the half-sum 1 + … + 32 = 528, and that is the total.


Fix. for (int offset = warpSize / 2; offset > 0; offset /= 2) (Listing 2). New 64-lane table: every lane 2080 (R6, fourth block); shuffles on gfx90a: 6 (R3, wave_sum_fixed.hip gfx90a … 6).


Prevention. Without an AMD GPU: AMD compile in CI, the grep rules of Layer 3, shuffle counts per target in CI (a wave64 target must show log2(64) = 6), and a lane-model or unit test with 64 lanes. With one: run the correctness tests on a wave64 target (E3's acceptance line). How the evidence was produced: the university's lane model (R6) implementing HIP 5.7's __shfl_xor rule, plus real compiler output (R2, R3, R5). No GPU was used; the scenario's partner output is represented by the model's 64-lane block.
