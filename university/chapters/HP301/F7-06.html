Story hook

For one dish, Amara hands the prep chef a card and says "for the gfx90a stoves, please". For a whole menu, that does not scale: forty cards, two buildings, several stove models, cards that share sub-recipes. So the kitchen writes a plan of work: which cards exist, which depend on which, which stove models each must be prepared for. Every evening the plan is followed the same way, by anyone.

One Monday, Sipho, new on the team, follows the plan exactly and the dishes fail at the stove in hall B. The plan was fine. But on the line "prepare for these stove models", Sipho left the box empty, and the prep chef, asked for no model in particular, quietly prepared everything for an older model nobody in the building uses. Nobody noticed until the stove refused the card. This chapter is about the prep chef (hipcc), the plan of work (CMake), and that empty box.

What you will be able to do

  • Explain what hipcc does on each platform, and print the exact command it runs.
  • Build a multi-file HIP program in which only the GPU file is compiled as HIP and the rest is ordinary C++.
  • Write a CMake project that builds the same source tree for AMD (with an explicit list of GPU targets) and for HIP's NVIDIA back end.
  • Prove which GPU targets an executable contains, and diagnose a build that silently used a default target.
  • Read a CMake failure message and decide whether the installation or the project is at fault.
Jargon box
Compiler driver
Simple words: a command that decides which real compiler and which options to use, then runs them for you. Analogy: the prep chef who decides how to prepare a card for a given stove. Precise: a program such as hipcc (or nvcc, or clang++ itself) that turns one command line into a sequence of tool invocations; HIPCC_VERBOSE=1 makes hipcc print the command it runs (R1). D1 R1
--offload-arch
Simple words: the option that names the GPU model to make machine code for. Analogy: the stove-model box on the plan of work. Precise: a clang option for HIP (and CUDA) offloading; each occurrence adds one GPU target and one code object to the output; without it, this build's toolchain chose gfx906 (R2, R6). D2 R2
GPU_TARGETS (CMake)
Simple words: the CMake setting that lists the AMD GPU models a project is built for. Analogy: the stove-model box itself. Precise: a cache variable defined by the installed hip CMake package (hip-config-amd.cmake lines 69–70, default empty, initialised from AMDGPU_TARGETS); for each entry the package adds --offload-arch= to the hip::device target's compile and link flags (lines 121–125). H1
hip::device
Simple words: a ready-made CMake bundle of the flags and libraries needed to compile GPU code with HIP. Analogy: the prep chef's standard kit, handed to any card that needs a stove. Precise: an imported interface target created by find_package(hip); linking a target to it adds -x hip, the --offload-arch list, --hip-link and the HIP runtime library (R4). D1 R4
Imported target (CMake)
Simple words: a name in CMake that stands for something already installed, with its flags attached. Analogy: a labelled box of tools the kitchen bought rather than built. Precise: a CMake target that is not built by the project but carries usage requirements (include directories, compile options, link libraries) to whatever links to it; defined by a package's config file. D3

Layer 1 — the kid explanation

A big program is many files. Building it means compiling each file and joining the results. For a HIP program, only the files with GPU code need the special treatment: they must be compiled once for the CPU and once for every GPU model you name. Ordinary C++ files can be compiled the ordinary way.

hipcc is the helper that knows the special treatment. You can watch what it does by asking it to print its command: on AMD it calls the clang compiler with options such as --offload-arch=gfx90a; on NVIDIA it calls nvcc.

For more than a few files, you write a plan of work for CMake, which then runs the right commands for every file, every time. The most important line in that plan for HIP is the list of GPU models. If you leave it empty, the tools pick a model by themselves, without telling you, and the program will not run on your GPU. So you always write the list, and you always check the finished program to see which models are inside.

Layer 2 — the student explanation

What hipcc runs

With HIPCC_VERBOSE=1, hipcc prints the command it executes. On the AMD platform, in this build, compiling the kernel file printed (R1):

/usr/bin/clang++-17 --offload-arch=gfx90a -mllvm -amdgpu-early-inline-all=true -mllvm -amdgpu-function-calls=false -std=c++17 -O2 -Iproj/src -c -x hip proj/src/saxpy_kernel.hip -o "k.o"

So hipcc's work on AMD is small: it adds -x hip (treat the file as HIP), passes your options through, and adds two LLVM options that ask the AMDGPU back end to inline device functions. R1 On the NVIDIA platform it printed /usr/bin/nvcc -Wno-deprecated-gpu-targets -lcuda -lcudart -L/usr/lib64 -std=c++17 -x cu … (F7-07, R1 there). Because hipcc mostly forwards to clang, you can build HIP code with clang++ -x hip --offload-arch=… directly; that is what CMake does in R4. D1 D2

Not verified — check before relying on this

What the two -mllvm options do exactly, and whether hipcc adds them in other versions, was not checked in a document; they were printed by this build's hipcc 5.7 (R1). See the HIP documentation's compiler section (D1) and the LLVM AMDGPU user guide (D2).

Split the program: GPU file and host files

The project of this chapter has three source files (Listings 1 and 2). saxpy.h declares one function, saxpyOnGpu, using only standard C++ types. saxpy_kernel.hip defines the kernel and that function with all HIP calls. main.cpp is ordinary C++ that calls the function and checks the result. This split has three effects: host files compile with any C++ compiler and flags (including sanitizers and warnings you use elsewhere); the HIP-specific part is small and in one place; and the same split works for both back ends, because only the GPU file changes how it is compiled. It is also the "common interface for CUDA and HIP back ends" that curriculum E1 asks the harness to have. Curriculum, track E.

CMake with the installed hip package

Listing 3 is the project file. On the AMD path it uses find_package(hip), which loads the HIP package's configuration files installed with HIP (here under /usr/lib/x86_64-linux-gnu/cmake/hip/) and defines imported targets including hip::device. H1 The GPU file is marked LANGUAGE CXX and linked to hip::device; the package then adds -x hip and one --offload-arch per entry of GPU_TARGETS to its compile line, and --hip-link, the --offload-arch list and libamdhip64 to the link line, all visible in R4. The C++ compiler must be clang (here clang++-17), because only clang understands -x hip.

On the NVIDIA path the same file enables CMake's CUDA language and compiles the .hip file as CUDA with nvcc. Nothing else is needed, because HIP's own header selects the platform: hip/hip_common.h defines __HIP_PLATFORM_NVIDIA__ when it sees nvcc's macro __NVCC__ (lines 44–52), and __HIP_PLATFORM_AMD__ when clang compiles HIP (lines 31–40). H2 R8 shows nvcc's command line and the single sm_80 code object in the result. R8 R9 One source tree, one CMake file, two back ends, chosen with -DHIP_BACKEND=NVIDIA.

Always set the target list, always check it

The package defines GPU_TARGETS with an empty default (H1). With it empty, CMake's build in this container produced an executable containing only a gfx906 code object (R6), and hipcc without --offload-arch did the same (R2). No warning was printed in either case. Two rules follow: set GPU_TARGETS (or --offload-arch) explicitly from the target names of the GPUs you will use (F7-02), and list the bundle of every executable you hand to someone else.

Reading the compile line CMake produced

R4's first line contains -D__HIP_PLATFORM_AMD__=1 -D__HIP_PLATFORM_HCC__=1 -x c++ -O3 -DNDEBUG -std=gnu++17 … -x hip --offload-arch=gfx90a --offload-arch=gfx1030. Three details: the two platform macros come from hip::device (the second is an older name kept for compatibility; HIP's header would also define the first by itself, H2); -x c++ comes from CMake's C++ rules and is overridden by the later -x hip (clang applies the last -x before the file); and -std=gnu++17 (not c++17) is CMake's default when CMAKE_CXX_EXTENSIONS is not turned off. R4 D3 The main file's line has none of the HIP flags: it is plain C++. The link line ends with --hip-link --offload-arch=gfx90a --offload-arch=gfx1030; the device code objects are bundled at link time, which is why the link must see the same target list as the compile.

Kernels in libraries

The kernel lives in a static library (libkernels.a) and is launched from a function in the same file. That is the simplest arrangement. A kernel called from another file, or device functions shared across files, need relocatable device code (-fgpu-rdc for clang/hipcc, -rdc=true for nvcc) and a device link step; without it the device code of each file is complete on its own. D1 D2 Keep each kernel and its launcher together and you avoid the question.

How the hardware actually does it

Why does the target list matter so much? Because a code object contains machine instructions for one GPU target, and targets differ in their instruction encodings and features (for example the wavefront size, 64 for gfx90a and 32 for gfx1030 in this build's compiler output, F7-07). D2 When a program starts, the HIP runtime looks at the GPU's target and searches the executable's bundle for a matching code object; if there is none, there is nothing the GPU could execute, and the kernel cannot be launched. D1 NVIDIA's fat binaries offer an escape hatch that AMD bundles in this build did not contain: PTX, which the driver can compile for a newer GPU at run time (cuobjdump lists it in F7-07). On the AMD path you build for every target you will run on.

Not verified — check before relying on this

The exact error a HIP program reports on a GPU whose target is missing from the bundle was not observed (no GPU in this build); check the HIP documentation's error list (D1) and record the message the first time you see it. Whether AMD offers a target-independent form of code objects in newer ROCm versions is not covered here; check D2 for "generic" targets.

Worked example

Question. A project is configured with -DGPU_TARGETS="gfx90a;gfx1030". Without running anything, predict: (a) the --offload-arch options on the kernel's compile line, (b) on main.cpp's compile line, (c) on the link line, and (d) the entries roc-obj-ls lists for the executable.

  1. Kernel compile. The kernel library links hip::device; the package's loop over GPU_TARGETS (H1 lines 121–125) adds one compile flag per entry: --offload-arch=gfx90a --offload-arch=gfx1030, in list order.
  2. main.cpp. The executable links only kernels, and kernels links hip::device as PRIVATE, so compile flags do not propagate: no --offload-arch, no -x hip.
  3. Link. Link requirements of a static library's private dependencies still reach the final link (a static library has no link step of its own), so the executable's link line gets --hip-link, both --offload-arch flags and libamdhip64.
  4. Bundle. Host plus two code objects: three entries.

Check against R4. Kernel line: --offload-arch=gfx90a --offload-arch=gfx1030 ✓. main.cpp line: no HIP flags ✓. Link line: libamdhip64.so.5.7.31921 --hip-link --offload-arch=gfx90a --offload-arch=gfx1030 ✓. Bundle: host-x86_64-unknown-linux--, …gfx1030, …gfx90a ✓. Step 3 relies on CMake's rule for private dependencies of static libraries (D3, pending verification); R4 confirms it for this case.

  • A prep chef asked for "no model" would ask back. The toolchain did not: with no target given, it chose gfx906 silently (R2, R6). Tools are less helpful than the worst prep chef.

Forensic lab answer key


Observation. R6: GPU_TARGETS:STRING= (empty) and a bundle with host-x86_64-unknown-linux-- and hipv4-amdgcn-amd-amdhsa--gfx906 only. R3/R4: configure with -DGPU_TARGETS='gfx90a;gfx1030', compile and link lines with both --offload-arch flags, bundle with gfx1030 and gfx90a. R2: hipcc without options also gave gfx906.


Hypotheses. (1) Broken ROCm on the cluster: contradicted by the hand build working on the same nodes. (2) Wrong target in the CI executable: confirmed by R6's bundle, which has no gfx90a code object. (3) Different HIP versions: not supported; the logs show the same toolchain line.


Root cause. The CI clean-up removed -DGPU_TARGETS=… from the configure command. The hip package's default is empty (H1), and the toolchain then built for gfx906 without a warning (R6). The gfx90a nodes find no matching code object and cannot launch the kernel.


Why the hand build works. It was configured with an explicit target list containing gfx90a (or with hipcc and --offload-arch=gfx90a).


Fix and prevention. Restore -DGPU_TARGETS="gfx90a" (plus any other targets in use); make the CMake file stop at configure when the list is empty (if(NOT GPU_TARGETS) message(FATAL_ERROR …)); add the bundle check of the lab extension to CI. How the evidence was produced: real configure, build and bundle listings in this build, with the target list deliberately left out.


Wrong answers. "Reinstall ROCm on the cluster": the hand build works there. "The GPU is not in the compatibility matrix": the hand build runs on it.
