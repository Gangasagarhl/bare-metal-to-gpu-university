Story hook

Before Amara can cook a single dish in the second kitchen building, someone has to open it. The keys must work, the gas must be connected, the stoves must be a model the building's maintenance company actually services, and Amara's name must be on the staff list or the door stays locked. On the first morning, Tomás from maintenance walks through the building with a clipboard. He does not cook anything. He checks: is the stove on the list of models we support? Is the gas line connected? Can the cooks open the stove room? Does the stove answer when you turn the knob?

Halfway down the list he finds the problem that would have ruined Friday: the stove in hall B is a newer model that is not on the maintenance list for this year's equipment. It might work. Nobody promises that it will. Tomás writes it down, with the list's date, and the team decides before the first recipe card is printed. This chapter is Tomás's clipboard for ROCm.

What you will be able to do

  • Describe the layers that must all be present before a HIP program can use an AMD GPU: the GPU, the kernel driver, the device files, the user-space runtimes and the compiler.
  • Check a machine's readiness with a script that reads, never changes, and reports PASS, FAIL or INFO for each layer.
  • Find your GPU's target name (gfx…) and decide whether it is on the compatibility matrix for the ROCm version you install, recording the matrix's version and date.
  • Build a device-report program and list which GPU targets an executable contains, so that "built for my GPU" is shown, not assumed.
  • Write an environment record (curriculum E1) that another engineer could use to reproduce your results.
Jargon box
Compatibility matrix (ROCm)
Simple words: AMD's table of which GPUs, Linux versions and kernels a given ROCm release supports. Analogy: the maintenance company's list of stove models it services this year. Precise: a document in the ROCm documentation, published per ROCm version, listing supported GPU architectures and products, operating systems and related requirements; "supported" is a statement by the vendor, not a guarantee that unlisted hardware fails. D2
Kernel driver (amdgpu, KFD)
Simple words: the part of the operating system that owns the GPU and lets programs use it safely. Analogy: the gas line and the building's maintenance staff. Precise: the Linux kernel's amdgpu DRM driver, together with its compute part (often called KFD, the Kernel Fusion Driver), which exposes the device file /dev/kfd used by the ROCm runtime and render nodes under /dev/dri/. Not to be confused with a GPU kernel (F6-01). D2 D3
Device file
Simple words: a special file through which a program talks to a driver. Analogy: the locked door of the stove room; you need the right key (permission) to go in. Precise: a character or block special file under /dev; the ROCm runtime opens /dev/kfd and a render node such as /dev/dri/renderD128, and the file permissions decide which users may do so. D3 D2
HSA runtime (ROCr)
Simple words: the low-level library that finds the GPUs and hands them work; the HIP runtime sits on top of it. Analogy: the building's shift supervisor who knows which stoves are lit. Precise: AMD's implementation of the Heterogeneous System Architecture runtime API (library libhsa-runtime64), which discovers "agents" (CPUs and GPUs) through the kernel driver; rocminfo prints what it finds. D2 R1
Agent (HSA)
Simple words: a processor the runtime can give work to: a CPU or a GPU. Analogy: a station on the shift supervisor's board. Precise: an HSA term for a device that can execute or dispatch work; each GPU agent has a name that is its GPU target, such as gfx90a. D2 D5
Environment record
Simple words: a written list of exactly what software and hardware produced a result. Analogy: Tomás's signed clipboard page, with the date. Precise: in this university, the OS, kernel release, ROCm/HIP and CUDA versions printed by the tools, GPU name and target, and the compatibility-matrix version consulted; required by curriculum E1 and by AH-11 for every measured result. R5

The idea in pictures

A HIP program on AMD reaches the GPU through a stack of layers, and every layer must be present. Figure 1 shows the stack from your program down to the GPU, and marks which layers existed in this build's container. The top three layers are user-space libraries you install as packages; the bottom layers belong to the operating system and the machine. When a layer is missing, the error appears at the first layer above it that notices, which is usually far from the cause.

Figure 2 turns the stack into a checklist you walk from the GPU upward. Each step has one question and one piece of evidence. The order matters: there is no point in debugging a HIP program while the kernel driver is not loaded.

Layer 1 — the kid explanation

A GPU is a big machine, and your program cannot touch it directly. Between them stand several helpers, one on top of the other. The operating system has a driver that owns the GPU, like the maintenance team that owns the gas line. The driver opens a door, a special file, through which other programs may ask for the GPU. Above that, two libraries do the asking for you: one that finds the GPUs, and the HIP library your program calls.

Each of those helpers has to be there, and the GPU itself has to be one the helpers know how to serve. AMD publishes a list for each version of ROCm saying which GPUs and which versions of Linux it supports. Checking compatibility means walking the list from the bottom up: is my GPU on the list, is the driver running, may I open the door, does the library see the GPU, and was my program built for exactly this GPU?

If you skip the walk, the error you get will appear at the top, in your program, even when the problem is at the bottom. That is why this chapter spends its time on checking, and why you write down what you found.

Layer 2 — the student explanation

The parts of an installation

A ROCm installation for HIP development has two halves. Kernel side: the amdgpu driver with its compute interface, which creates /dev/kfd and the render nodes /dev/dri/renderD*. User side: the HSA runtime (libhsa-runtime64), the HIP runtime (libamdhip64), the compiler (clang with the AMDGPU back end, driven by hipcc), the device libraries linked into every kernel (rocm-device-libs), the code-object manager (libamd-comgr) and tools such as rocminfo. D2 D3 In this build only the user side was present, installed as Ubuntu packages under /usr; Listing 2 (R5) prints the exact package versions. Notice that they are not all the same version: HIP, the HSA runtime and rocminfo are 5.7.1, while the code-object manager and device libraries carry 6.0 snapshot versions. Your environment record must list each one, because "ROCm 5.7" does not describe this machine completely.

The user-side packages do not need a GPU to be installed or to compile. That is why this build could compile every HIP listing of the course. Running needs the kernel side and the GPU.

The compatibility matrix

ROCm supports a specific list of GPU architectures and Linux distributions per release, published as a compatibility matrix and as system-requirement pages in the ROCm documentation. D2 Three facts about the list shape your checking:

  1. It is per version. A GPU supported by one ROCm release may be dropped or added in another, so the question is always "supported by ROCm x.y?" and the record names x.y.
  2. It names architectures and products. The compiler and runtime work with the target name (gfx90a, gfx1030); the matrix and the shop work with product names. Your dossier links the two for your GPU, from the vendor's document, not from memory. D5
  3. Unlisted is not the same as broken. An unlisted GPU may work, partly work or fail; the vendor does not promise any of these. For coursework you use a listed GPU, so that a failure is your bug and not an unsupported configuration.
Not verified — check before relying on this

This chapter does not name any supported GPU, distribution or kernel version, because the compatibility matrix could not be opened in this build (no internet) and the list changes with each ROCm release. Before buying, renting or installing, open the ROCm documentation's compatibility matrix and system-requirements page for the ROCm version you will install (D2), copy the supported GPU targets for your card into supported_targets.txt, and write the document's title, ROCm version and the date you read it in the file's source: line. The descriptions of /dev/kfd, render nodes and the need for group membership (commonly the video and render groups) are from the course card and memory, not an opened document: check D2's "prerequisites" or "post-install" section and D3.

Finding your GPU's target

On a working installation rocminfo prints one block per agent, and the name of each GPU agent is its target. D2 Listing 1 extracts every gfx… word from rocminfo's output. A program can also ask: hipGetDeviceProperties fills a hipDeviceProp_t whose gcnArchName field holds the target name on AMD (Listing 4 prints it). D1 H1 The target you find is the one you pass to --offload-arch; the bundle listing (Listing 3) then proves that the executable carries code for it.

Ways to install

The ROCm documentation describes several installation methods: AMD's package repositories for supported distributions (with a helper installer), and the distribution's own packages where a distribution ships ROCm. D2 This build used the second kind: the Ubuntu 24.04 "noble" universe archive (R5). Distribution packages and AMD's packages differ in version, file locations (/usr here, /opt/rocm in AMD's layout according to D2) and in which components are included. Pick one method per machine and record it; mixing them is a common source of version mismatches.

Not verified — check before relying on this

No installer command is given in this chapter, on purpose: the package names, repository setup and installer options change between ROCm releases and could not be checked in this build. Follow the ROCm installation guide for your ROCm version and distribution (D2) step by step, and paste the commands you actually ran into your environment record. The statement that AMD's own packages install under /opt/rocm is from memory; this build's hipconfig --rocmpath printed /usr (R5).

Safety

Installing a kernel driver changes how your machine boots. Do it on a machine you are allowed to change, with backups of your work, and with a way back (a second boot entry or a rescue medium). Do not install a GPU card into a computer without following the computer's and the card's own manuals for power and handling; ask a supervisor if you have not done it before. The checks in this chapter only read and are safe to run anywhere.

Targets, code objects and "it runs on my GPU"

The compiler emits one code object per --offload-arch, and the runtime loads the code object whose target matches the GPU. D5 D1 If no code object matches, the program builds and starts, and the launch fails at run time. This makes step 6 of Figure 2 a build-time check that you can do without the GPU: list the bundle and look for your target (R3). The LLVM AMDGPU user guide also describes target features written after the name (such as :xnack+ or :sramecc-) that further restrict which GPU configurations a code object runs on; HP302 returns to them. D5

A practical rule for a course machine: build for exactly the targets you have, plus any your teammates have, and check them all in the bundle. Building for many targets increases build time and executable size, which the lab lets you see.

How the hardware actually does it

When a HIP program starts on AMD, the HSA runtime opens /dev/kfd and asks the kernel driver which GPUs exist; each becomes an agent. To run a kernel, the runtime places a dispatch packet in a queue in memory that the GPU's command processor reads; the packet points to the code object's kernel descriptor and arguments. D2 D5 The kernel driver's job is to give the process those queues and the GPU memory mappings safely. This is why the absence of the driver is total: without /dev/kfd there is no queue and no agent, and the runtime cannot even enumerate the hardware (R1). The GPU and the CPU talk across PCI Express (F1-44 on DMA, F4-01 on driver stacks). HP302 opens the GPU side of this path.

Not verified — check before relying on this

The description of user-mode queues, dispatch packets and the command processor is a conceptual summary written from memory of the HSA model, not from an opened document. Check the ROCm documentation's runtime overview (D2) and the LLVM AMDGPU user guide's sections on code objects and kernel descriptors (D5) before teaching it in detail.

Worked example

Situation. Lucía has a Linux workstation with an AMD GPU and wants to run the course labs. She runs check_rocm.sh and gets this (constructed for the example from the script's real messages):

  • PASS hipcc found, PASS /dev/kfd exists, PASS render nodes: /dev/dri/renderD128
  • FAIL rocminfo lists no GPU agent
  • INFO this user's groups: lucia

Step 1 — read upward from the bottom. The driver layer passes: the device files exist. The runtime layer fails: rocminfo sees no GPU agent. Between them is exactly one layer of Figure 1: permission to open the device files.

Step 2 — form hypotheses. (a) Lucía's user may not open /dev/kfd or the render node. (b) The GPU is not supported by this ROCm version, so the runtime ignores it. (c) The runtime and driver versions do not fit together.

Step 3 — test the cheapest first. Her groups line lists only her own group. Compare with ls -l /dev/kfd /dev/dri/renderD128: the group owner of each file tells you which group needs membership. If her user is not in it, hypothesis (a) explains the evidence. Running rocminfo as a user who is in the group (or after adding her and logging in again) tests it.

Step 4 — if the agent appears, continue the walk. Copy the agent's gfx name, check it against the matrix for her ROCm version (step 2 of Figure 2), build with --offload-arch set to it, and list the bundle (step 6).

Check. The reasoning used only what each line can prove: device files present (driver loaded), no agent (runtime cannot use them), groups (who may open them). The exact group names and the command to add a user to a group are in D2 (see the unverified box in Layer 2).

Where the analogy breaks


    

  • A maintenance list is about safety and service; the compatibility matrix is about testing and support. An unlisted GPU is not dangerous; it is untested by the vendor for that release. The analogy suggests a stove that might explode; the real risk is wasted days on bugs nobody will fix.
    • 

  • Tomás checks once; you check per version. A new ROCm release can change the matrix, the package layout and the default behaviour. The check is repeated whenever any layer changes, including a kernel update by the operating system.
    • 

  • In a building the gas line is visible. A missing kernel driver is invisible until a program asks: the libraries install and the compiler works without it (this whole course was compiled that way).
    •

Forensic lab answer key


Observation. Kernel side: FAIL /dev/kfd missing, FAIL no /dev/dri/renderD* render nodes, FAIL rocminfo lists no GPU agent; its first line: ROCk module is NOT loaded, possibly no GPU devices (R1). User space: PASS hipcc found: HIP version: 5.7.31921-0 (R1); HIP runtime version 50731921 (R2); packages present (R5). Device query: hipErrorNoDevice (R2).


Hypotheses. (1) Kernel driver not loaded or not installed: device files missing, rocminfo's message. (2) No GPU in the machine or not visible (for example a virtual machine without the card passed through): also consistent with missing device files. (3) Permissions: ruled out, because the files do not exist at all. (4) A HIP bug: the HIP runtime correctly reports what the layers below it provide.


Root cause. The kernel side of Figure 1 is missing: no /dev/kfd, no render nodes, driver module not loaded. Hypotheses (1) and (2) cannot be separated from these files alone; lspci on the server (not in the pack) would show whether an AMD GPU is on the bus. In this build's container the truth is (2): there is no GPU.


The version call. It is evidence that the user-space libraries load, nothing about the kernel side; it does not support a HIP bug.


Fix and prevention. Check the hardware is present (lspci), check the kernel and OS are on the matrix for the ROCm version, install or load the driver per D2, re-run the checklist until it passes, then run the device report. Every support request includes the environment record and the checklist output. How the evidence was produced: real runs in this build's container (no GPU, no driver); nothing was injected.


Wrong answers. "Reinstall HIP": the user side is fine. "Add the user to the video group": the files to open do not exist. "Use the NVIDIA back end": changes the vendor, does not fix the AMD server.
