Story hook

On her second day in the new kitchen building, Amara asks for "the walk-in" and gets a blank look. Here it is called "the cold room". The blast chiller is "the quick-cooler". The order spike is "the rail". Almost everything works exactly as in her old building; only the words differ, and most of them differ in a predictable way: the old building put "C-" in front of every station name, this one puts "H-". C-grill is H-grill, C-pass is H-pass.

Ravi, who has worked in both buildings, gives her a folded card: the old name on the left, the new name on the right, and a star next to the handful that are not only the letter swapped. "Learn the stars," he says. "And when in doubt, do not trust the card. Ask the building." He points at the station labels on the wall: the building's own signs, which are what the staff actually read. This chapter makes that card, and reads the building's own signs to check it.

What you will be able to do

  • Map the CUDA runtime calls, types and constants you used in CU201 to their HIP names, and name the ones that differ by more than the prefix.
  • Read the map that a given HIP version really uses, from HIP's own NVIDIA back-end header, with a small script.
  • Explain how each back end implements a HIP call: an inline wrapper around the CUDA call on NVIDIA, a function of the HIP runtime library on AMD.
  • Port a CU201-style host program by hand, checking every call, and show that an unported name or an unchecked result is caught at build time.
  • Diagnose a half-finished port that builds on the NVIDIA back end and fails on AMD.
Jargon box
Runtime API (HIP, CUDA)
Simple words: the functions your CPU code calls to use the GPU: get a device, allocate, copy, launch, wait, check errors. Analogy: the names of the stations and tools in a kitchen building. Precise: a C-style host API; CUDA's is declared in cuda_runtime_api.h, HIP's in hip/hip_runtime_api.h, which mirrors CUDA's with the prefix hip and HIP's own types (hipError_t, hipDeviceProp_t). D1 D4 H1
API mapping
Simple words: the list of which HIP name stands for which CUDA name. Analogy: Ravi's folded card. Precise: a correspondence between CUDA runtime identifiers and HIP identifiers; documented by AMD in the HIP porting guide and HIPIFY tables, and implemented concretely by HIP's NVIDIA back-end header, where each HIP name is defined in terms of a CUDA name (R1). D1 D2 R1
Inline wrapper
Simple words: a tiny function whose whole job is to call another function and translate the answer. Analogy: a sign on the wall that says "H-pass: this is the C-pass". Precise: in HIP's NVIDIA back end, an inline static function such as hipFree, whose body is return hipCUDAErrorTohipError(cudaFree(ptr)); (header line 1511). H2
Error-code conversion
Simple words: turning one runtime's error number into the other's. Analogy: translating the old building's alarm codes into the new building's. Precise: on the NVIDIA back end, hipCUDAErrorTohipError (line 561) maps cudaError_t values to hipError_t, and hipErrorToCudaError (line 971) maps back, for example to ask CUDA for an error's name. H2
[[nodiscard]]
Simple words: a C++ mark that makes the compiler warn when you ignore what a function returns. Analogy: a kitchen ticket that must be signed off, or the manager hears about it. Precise: a C++17 attribute; HIP 5.7 declares hipError_t with it (typedef enum __HIP_NODISCARD hipError_t, hip_runtime_api.h lines 206 and 218), so every HIP call whose result is ignored produces a warning on both back ends (R6). D5 H1 R6

The idea in pictures

Figure 1 follows one call, hipMalloc, through both back ends. Your source is the same; what the name means is decided by the header the back end includes. On NVIDIA, the name is an inline wrapper that calls cudaMalloc and converts the error code. On AMD, the name is a function of the HIP runtime library libamdhip64, which talks to the ROCm stack of F7-02. Both paths return a hipError_t, so your checking code is the same.

Layer 1 — the kid explanation

When you wrote CUDA programs, you called functions such as cudaMalloc to get GPU memory and cudaMemcpy to copy into it. HIP has a function for almost each of these, and for most of them the name is the same with cuda replaced by hip: hipMalloc, hipMemcpy. That is Ravi's card.

A few names differ by more than the swap. The pinned-memory allocator cudaHostAlloc is called hipHostMalloc in HIP, and cudaFreeHost is hipHostFree. Those are the starred names on the card, and a port that swaps letters blindly gets them wrong.

Ravi also said: ask the building. The HIP package contains a file in which every HIP name for NVIDIA is written out in terms of its CUDA name. That file is the building's own sign. In this chapter you read it with a small program, so your card is not from memory but from the version you actually installed.

Kernel code and the launch

The kernel side needs almost no mapping: __global__, __device__, __shared__, threadIdx, blockIdx, blockDim, gridDim, __syncthreads() and atomicAdd are spelled the same in HIP. D1 The triple-angle-bracket launch is accepted by both back ends (every listing of this course uses it). HIP also offers a macro form, hipLaunchKernelGGL(kernel, grid, block, sharedBytes, stream, args...), defined in both back ends' headers (amd_detail/amd_hip_runtime.h line 234, nvidia_detail/nvidia_hip_runtime.h line 39); you will meet it in code ported by older tools. H1 The exceptions are warp-level intrinsics, which are the subject of F7-04 and F7-07: on NVIDIA, HIP's __shfl_xor is a macro for __shfl_xor_sync(0xffffffff, ...), a 32-lane mask written into the header. H2

The checking pattern carries over, and gets help

The CU201 rules stay: check the return value of every call, read the last error after every launch, and synchronise (or do a blocking copy) before trusting a kernel's result. In HIP 5.7 the compiler helps with the first rule: hipError_t is declared [[nodiscard]], so ignoring a HIP call's result produces a warning from hipcc on AMD and from nvcc and the host compiler on the NVIDIA back end (Listing 3, R6). H1 R6 A launch with <<<…>>> returns nothing, so no warning can catch an unchecked launch; that one stays your discipline. Listing 3 also shows why the rule exists: with every result ignored, the program printed sum of 256 ones = 0 and exited with code 0 on a machine without a GPU (R7).

Layer 3 — the engineer's depth

How the two back ends implement the same name

NVIDIA. hip/hip_runtime_api.h includes nvidia_detail/nvidia_hip_runtime_api.h when __HIP_PLATFORM_NVIDIA__ is defined. In that header, constants and types are macros or typedefs onto CUDA's (#define hipMemcpyHostToDevice cudaMemcpyHostToDevice, line 83; typedef cudaStream_t hipStream_t, line 417), and functions are inline wrappers that call CUDA and convert the result (hipMalloc, line 1495). H2 Nothing of HIP remains in the executable except those inlined calls: Listing 2 built this way links the CUDA runtime, not a HIP library (F7-07 shows the library list).

AMD. The same header declares the functions as ordinary external functions (hipError_t hipMalloc(void** ptr, size_t size);, line 2786), implemented in libamdhip64, the HIP runtime. H1 There is no CUDA anywhere on this path. A CUDA name left in the source has no declaration and the build fails (Listing 4, R4).

This asymmetry is the root of the most common porting accident: the NVIDIA back end compiles anything CUDA compiles, because the CUDA headers are included underneath. A leftover cudaStreamCreate builds and runs on NVIDIA (R5) and stops the AMD build (R4). Test the AMD build of every port, even when you have no AMD GPU: compiling is enough to find leftovers.

HIP's own types: same name, different contents

hipError_t is an enumeration defined by HIP (hip_runtime_api.h line 218), not a typedef of cudaError_t. On NVIDIA every wrapper converts with hipCUDAErrorTohipError, and hipGetErrorName converts back with hipErrorToCudaError before asking CUDA (line 1876). H2 Consequences: never compare a HIP result with a numeric CUDA code; never assume two runtimes use the same numbers for the same condition; print the name of the error. The name you print on NVIDIA is CUDA's (R3: cudaErrorNoDevice), on AMD it is HIP's (R2: hipErrorInvalidDevice).

hipDeviceProp_t is HIP's own struct (line 96–162 of hip_runtime_api.h). On NVIDIA, hipGetDeviceProperties calls cudaGetDeviceProperties and copies the fields one by one into HIP's struct (line 1979 onward). H1 H2 A field that exists only on one vendor (such as gcnArchName) is then empty or meaningless on the other; F7-02's device report prints both kinds and you interpret per back end.

Same name is not same behaviour

A mapping says which call to use; it does not promise identical behaviour. Flags, default values, the behaviour of the default stream, the size limits of memory and the meaning of device attributes are documented per runtime. D1 D4 One small visible example in this build: hipHostMallocDefault is 0x0 in the AMD headers (hip_runtime_api.h line 607) and cudaHostAllocDefault on NVIDIA (nvidia_hip_runtime_api.h line 362); the constants agree in meaning by design, but they are two definitions maintained separately. H1 H2

Not verified — check before relying on this

Whether every HIP call used in this course behaves identically to its CUDA counterpart on AMD (stream ordering of the default stream, synchronisation implied by hipMemcpy, the flags accepted by hipHostMalloc, the behaviour of hipMallocManaged on GPUs without page-fault support) could not be checked: the HIP API reference (D1) was not opened and no AMD GPU was available. Before relying on a behaviour, read the call's entry in D1 for your HIP version and test it on your GPU. The number of mapped names (665) is what Listing 1's simple parser found in this header; it is not an official count and may miss names defined in other ways.

How the hardware actually does it

The API names change; the hardware actions behind them do not change in kind. hipMalloc reserves GPU memory and maps it into the GPU's address space; hipMemcpy between host and device is carried out by DMA across the bus (F1-44); pinned host memory (hipHostMalloc) is host memory that the operating system will not move, so the DMA engine may read it directly; a kernel launch places a dispatch packet in a queue that the GPU reads (F7-02). D1 D3 Events are timestamps the GPU writes when the queue reaches them, which is why hipEventElapsedTime measures GPU-side time. The details (how many copy engines, how the queues are scheduled, how memory is mapped) are hardware- and driver-specific and are not the same on the two vendors; HP302 and the profiling chapters measure them.

Not verified — check before relying on this

The descriptions of DMA, pinned memory and event timestamps above are conceptual and from the CUDA and HIP programming guides as remembered, not opened (D1, D4); they were not observed in this build. Listing 2's timing line was never printed (no GPU).

Worked example

Task. Port this CU201-style fragment to HIP by hand, using only the map, and list every change:

cudaStream_t s; cudaStreamCreate(&s); float* h; cudaHostAlloc((void**)&h, bytes, cudaHostAllocDefault); … cudaMemcpyAsync(d, h, bytes, cudaMemcpyHostToDevice, s); … cudaFreeHost(h); cudaStreamDestroy(s);

  1. Types: cudaStream_t → hipStream_t (prefix only, R1 line 417).
  2. Streams: cudaStreamCreate → hipStreamCreate; cudaStreamDestroy → hipStreamDestroy (prefix only).
  3. Pinned memory: cudaHostAlloc → hipHostMalloc (starred: name differs, R1 line 1528); flag cudaHostAllocDefault → hipHostMallocDefault (starred, H1 line 607); cudaFreeHost → hipHostFree (starred, R1 line 1636).
  4. Copies: cudaMemcpyAsync → hipMemcpyAsync; cudaMemcpyHostToDevice → hipMemcpyHostToDevice (prefix only).
  5. Checks: the original ignores every result. With hipError_t declared [[nodiscard]], each of the six calls would now warn (R6); wrap each in check(…, "what").

Count. 9 identifiers change: 5 by prefix only, 3 starred names plus 1 starred flag (4), and every call gains a check. Check against a real program: Listing 2 is exactly this pattern, ported the same way; it compiled on both back ends (R2, R3) and, as a further check, contains no CUDA identifier (the AMD build would have failed, as Listing 4 shows).

Where the analogy breaks


    

  • Ravi's card translates words; the NVIDIA back end does not translate, it forwards. On NVIDIA, a HIP call is the CUDA call plus an error conversion (H2); there is no second set of stations. Only on AMD is there a second building behind the name.
    • 

  • Same station name, same station? In the kitchen, the cold room and the walk-in are the same kind of room. In the APIs, the same name can carry different limits, defaults and behaviour (Layer 3); the card tells you what to call, not how it behaves.
    • 

  • The building's signs are versioned. A kitchen's labels rarely change; the header is one version of HIP. Re-run Listing 1 when you upgrade.
    •

Summary


    

  • The HIP runtime API mirrors the CUDA runtime: most names differ only by the prefix; a few are "starred" (hipHostMalloc, hipHostFree).
    • 

  • Read the map of your HIP version from its NVIDIA back-end header (Listing 1) rather than from memory.
    • 

  • On NVIDIA a HIP call is an inline wrapper around the CUDA call; on AMD it is a function of libamdhip64.
    • 

  • hipError_t and hipDeviceProp_t are HIP's own types; print error names, never compare numbers across runtimes.
    • 

  • The NVIDIA back end compiles leftover CUDA names; the AMD build rejects them. Build both.
    • 

  • HIP 5.7 marks hipError_t [[nodiscard]]: unchecked calls warn; unchecked launches still need your discipline.
    • 

  • Same name does not guarantee same behaviour: read D1 per call; nothing here ran on a GPU.

Forensic lab answer key


Observation. R4: leftover.hip:28:5: error: unknown type name 'cudaStream_t', 1 error generated when compiling for gfx90a. R5: the NVIDIA build succeeded (exit code 0).


Hypotheses. (1) ROCm installation problem: ruled out: the compiler ran and diagnosed a source line; an installation fault would fail on the header or the toolchain, not on one identifier. (2) Leftover CUDA name: confirmed by the message and by the comment on line 28. (3) Wrong header: the file includes hip/hip_runtime.h (line 3), the right one.


Root cause. On the NVIDIA back end, HIP's header includes the CUDA runtime headers (Figure 1), so cudaStream_t and cudaStreamCreate are declared and the code compiles; on AMD no CUDA header exists, so the name is unknown. CI built only the NVIDIA back end and could not see it.


Why no nodiscard warning on line 29. cudaStreamCreate returns cudaError_t, CUDA's type, which this CUDA version does not mark [[nodiscard]]; the warning comes from HIP's hipError_t. And the AMD build stopped at line 28 before reaching it.


Fix and prevention. hipStream_t stream; and check(hipStreamCreate(&stream), "hipStreamCreate"); (and destroy it at the end). Add an AMD compile job to CI (hipcc with --offload-arch; no GPU needed), plus a grep for cuda identifiers. How the evidence was produced: real builds in this build; the leftover lines were written deliberately into leftover.hip.


Wrong answers. "Reinstall ROCm": the compiler worked. "Use the NVIDIA back end on AMD too": impossible; the NVIDIA back end needs NVIDIA's runtime and GPU.
