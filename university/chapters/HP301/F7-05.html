Story hook

The first dish Amara cooks in the second building is the simplest on the menu: two bowls of numbers, add them pairwise, put the results in a third bowl. A million and three pairs. She hands out the recipe card to tables of 256 helpers, rows of 64 at each table, and every helper works out "my pair is table number times 256 plus my seat number".

The kitchen manager, Kwame, watches the last table. Only 67 of its 256 helpers have a pair to add; the other 189 seats have numbers beyond the end of the bowls. The card says "if your number is past the last pair, do nothing". Kwame wants to see how the second building's stoves handle that line: does each helper think about it, or does the row decide together? He asks for the card as the stove actually reads it, the machine's own instructions. This chapter reads them.

What you will be able to do

  • Write a complete HIP vector add with checked calls, a bounds check and a CPU comparison, and explain every line.
  • Compute the grid for any n and block size, and say exactly which threads, wavefronts and lanes of the last block do work.
  • Produce and read the AMD GPU assembly of a kernel: scalar versus vector registers, the execution mask, memory instructions and the kernel's resource metadata.
  • Show from the assembly alone whether a kernel has a bounds check, without running it.
  • Compare the same kernel's AMD assembly with NVIDIA PTX and SASS from HIP's NVIDIA back end.
Jargon box
AMD GPU assembly (ISA)
Simple words: the GPU's own instructions, written as text, that the compiler produced from your kernel. Analogy: the recipe card as the stove reads it. Precise: the AMDGPU instruction set (here for gfx90a, a CDNA2 target) as emitted by clang's AMDGPU back end; obtained in this build with hipcc --save-temps, which keeps the .s file. D2 D5 R2
Scalar register (SGPR)
Simple words: a register that holds one value for the whole wavefront. Analogy: the number written on the table, the same for every helper at it. Precise: a 32-bit register named s0, s1, …; used for values uniform across the wavefront (kernel arguments, block index, pointers); the metadata field .sgpr_count counts them. D2 R2
Vector register (VGPR)
Simple words: a register that holds a separate value for each lane. Analogy: each helper's own hands. Precise: a register named v0, v1, …, with one 32-bit element per lane of the wavefront; per-thread values such as threadIdx.x and i live here; .vgpr_count counts them. D2 R2
Execution mask (EXEC)
Simple words: a row of on/off switches, one per lane, saying which lanes take part in the next vector instruction. Analogy: the helpers in a row who raise their hand for this step. Precise: a 64-bit register on wave64 targets; an if on a per-lane condition becomes a compare that writes a lane mask (vcc) and s_and_saveexec_b64, which restricts EXEC; s_cbranch_execz skips code when no lane is left. D2 R2
Kernel arguments segment (kernarg)
Simple words: the small block of memory where the kernel's arguments are placed for it to read. Analogy: the slip clipped to the recipe card with today's quantities. Precise: a memory region whose address the kernel receives in an SGPR pair; arguments sit at fixed offsets (here a at 0, b at 8, c at 16, n at 24 = 0x18) and the metadata field .kernarg_segment_size is 28 bytes. D5 R2

The idea in pictures

Figure 1 is the thread hierarchy of this chapter's launch, with the index formula, as in F6-02, now with the AMD level between block and thread: the wavefront. The vector has 1,000,003 elements; blocks have 256 threads; on gfx90a each block is four wavefronts of 64 lanes.

Figure 2 shows what the bounds check becomes on AMD hardware for the last block: not a branch per thread, but a mask per wavefront. Wavefronts whose mask is all zeros skip the body entirely.

Layer 1 — the kid explanation

Vector add is the "hello" of GPU programming: add two long lists of numbers pairwise. Every GPU thread adds one pair. Each thread works out which pair is its own from two numbers it is given: which block it belongs to, and its seat in the block. The program on the CPU side gets memory on the GPU, copies the two lists in, starts the kernel, copies the answer back and checks it against an answer computed on the CPU.

The HIP version is the CUDA version with the names changed, as you saw in F7-03. What is new in this chapter is that you also look at the instructions the compiler made for the AMD GPU. They show two kinds of registers: some hold one number for the whole row of 64 helpers, some hold a number for each helper. They also show how "if my number is past the end, do nothing" works: the row switches off the helpers who have nothing to do, and if nobody in the row has anything to do, the row skips the work completely.

Three readings above come from memory of the AMDGPU calling convention, not from an opened document: that s[4:5] holds the dispatch-packet pointer and offset 4 holds the work-group size, that s[6:7] holds the kernarg-segment pointer, and that the work-group id arrives in s8 and the work-item id in v0. They are consistent with the code (the 0x18 offset matches n's position, the 0xffff mask matches a 16-bit field), but check them in the LLVM AMDGPU user guide's sections on the kernel descriptor, initial kernel execution state and the HSA dispatch packet (D5) before teaching them as fact.

Layer 3 — the engineer's depth

Uniform and divergent values

The compiler decides for every value whether it is the same in all lanes of a wavefront (uniform) or may differ (divergent). Uniform values go to SGPRs and scalar instructions, executed once per wavefront; divergent ones to VGPRs and vector instructions. D5 D2 In R2 you can follow the split exactly: blockIdx.x * blockDim.x and every kernel argument are scalar (s_mul_i32, s_load_*); from the moment threadIdx.x enters (v_add_u32), everything is vector. This is the hardware reason behind a CUDA habit: compute what is the same for the whole block outside the per-thread part, and the compiler can keep it in scalar registers. NVIDIA's SASS for the same kernel has a related idea, uniform registers (UR4 in F7-07's R7), but the split is less visible. R6

Masks instead of branches

On a SIMT machine, a per-lane if cannot send different lanes of one wavefront to different instructions at the same time. AMD's ISA makes this explicit: the compare writes a 64-bit lane mask, s_and_saveexec_b64 turns off the lanes that fail, and the body runs for the rest; a real branch (s_cbranch_execz) is taken only when the whole wavefront agrees (all lanes off). D2 That is why the mask is 64 bits wide on this target, and why code that stores lane masks in 32-bit integers loses half of them (F7-07, HP302). NVIDIA's PTX for the same if uses a predicate and a branch (setp.ge.s32 %p1, @%p1 bra), and its SASS a predicated exit (@P0 EXIT) (R6); the hardware masking is hidden from the instruction text. D3

Resource metadata and why it matters later

The metadata fields are the compiler's statement of what one wavefront of this kernel needs: SGPRs, VGPRs, scratch, kernel-argument bytes, wavefront size. The number of VGPRs per lane, together with LDS use and the block size, limits how many wavefronts can be resident on a compute unit at once (occupancy), which is HP302's topic. D2 For vecAdd the counts are small (8 VGPRs, 13 SGPRs) and no scratch is used (.private_segment_fixed_size: 0); a non-zero scratch size would mean registers spilled to memory, which is the first thing to check when a kernel is unexpectedly slow. The forensic lab below uses the same fields to compare two builds.

Not verified — check before relying on this

How SGPR and VGPR counts translate into occupancy on gfx90a (register-file size per SIMD, allocation granularity) is not stated here because it is a hardware number not printed by any program in this build; HP302 takes it from the CDNA2 ISA reference (D2) and measures it.

How the hardware actually does it

An AMD compute unit runs wavefronts on SIMD units; each vector instruction operates on all lanes whose EXEC bit is set, reading per-lane operands from VGPRs, while scalar instructions run once on a separate scalar unit and read SGPRs. D2 D4 Memory instructions are issued per wavefront: the 64 addresses of a global_load_dword are combined by the memory system, so neighbouring lanes reading neighbouring words (as here, a[i] with consecutive i) is the coalesced pattern of F6-08. The two counters in R2, lgkmcnt (scalar and LDS loads) and vmcnt (vector memory), are how the program waits for loads that are still in flight: the GPU does not stall at the load, it stalls at the s_waitcnt that needs the result, and meanwhile other wavefronts can run (latency hiding, F1-57). HP302 studies all of this with measurements.

Worked example

Question. For n = 1,000,003 and block = 256 on gfx90a: how many blocks are launched, how many threads are idle, and for each wavefront of the last block, how many lanes are active after the bounds check and does it execute the body?

  1. Blocks. grid = (1,000,003 + 255) / 256 = 1,000,258 / 256 = 3907.26…, which integer division rounds down to 3907. Check: 3906 × 256 = 999,936 is less than 1,000,003, and 3907 × 256 = 1,000,192 is not, so 3907 blocks are exactly enough.
  2. Threads launched. 3907 × 256 = 1,000,192; idle threads = 1,000,192 − 1,000,003 = 189.
  3. Last block. It is block 3906, covering i from 3906 × 256 = 999,936 to 1,000,191. Valid i are 999,936 … 1,000,002: 67 threads (threadIdx.x 0–66). 67 + 189 = 256. ✓
  4. Wavefronts. Wavefront 0 (threadIdx.x 0–63): 64 active, body runs. Wavefront 1 (64–127): 64, 65, 66 active = 3 lanes, body runs with 61 lanes masked. Wavefronts 2 and 3: 0 active, s_cbranch_execz jumps to .LBB0_2. That is Figure 2.
  5. Same on NVIDIA. Warps of 32: warps 0 and 1 full, warp 2 (64–95) has 3 active lanes, warps 3–7 have none and take the @P0 EXIT in every thread.

Check. The arithmetic was verified as integer arithmetic in the text; the instructions that implement step 4 are in R2. On a GPU, Listing 1 prints grid=3907 block=256, which you can compare (untested here).

Where the analogy breaks


    

  • Helpers who "do nothing" still sit in the row. In the kitchen an idle helper could leave; on the GPU, masked lanes of an active wavefront occupy their lane for every instruction the wavefront issues. Only a whole wavefront with no active lanes skips the work.
    • 

  • The number on the table is not written once by a person. The scalar registers are filled by hardware and by scalar loads the compiler places; "uniform" is a property the compiler proves, not a choice of the helpers.
    • 

  • Tables of 256 do not exist as furniture. A block is a scheduling group; on gfx90a it is four wavefronts that may run on different SIMD units of one compute unit (D2), not a physical table of 256 seats.
    •

Forensic lab answer key


Observation. R3 has no s_load_dword s1, s[6:7], 0x18 (it never loads n), no v_cmp_gt_i32, no s_and_saveexec_b64, no s_cbranch_execz and no .LBB0_2 label. Its metadata: .sgpr_count: 16 (A: 13), .vgpr_count: 5 (A: 8); kernarg size 28 and wavefront size 64 are the same. Both run records stopped at hipMalloc.


Hypotheses. (1) Same work, scheduled differently: would still contain the compare and mask. (2) Less work: the compare is gone, and n is never read. The missing instructions decide for (2).


Root cause. Build B's kernel has no bounds check: c[i] = a[i] + b[i]; without if (i < n). (The source confirms it: vec_add_b.hip differs from Listing 1 only in lines 19–21 and the comment line.)


Consequence. For n = 1,000,003, threads with i = 1,000,003 … 1,000,191 (189 threads) read past the end of a and b and write past the end of c: out-of-bounds global memory accesses, which may corrupt other allocations, fault, or appear to work. The colleague used n = 2^20, a multiple of 256, so no thread was out of range.


Fix and prevention. Restore if (i < n). Review rule: a kernel launched with a ceiling-division grid must contain a bounds check, visible as a compare and an EXEC restriction in the ISA. Test sizes always include non-multiples of the block size (E1's own rule) and run under the address sanitizer on hardware. "Fewer registers" is not evidence of better code when the work differs. How the evidence was produced: real compiler output for both files in this build; the bounds check was removed deliberately in vec_add_b.hip.


Wrong answers. "B is better because it uses fewer VGPRs": it does less work. "Both runs failed the same way, so they are equivalent": both runs failed for lack of a GPU, which says nothing about the kernels.
