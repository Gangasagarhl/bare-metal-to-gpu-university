Story hook

Amara has two hundred recipe cards to rewrite for the second building. Ravi's card of names (F7-03) works, but by card thirty she is making typos. So the company hires two translators. The first, Noor, is fast: she reads each card as plain text and swaps every old station name she finds for the new one, all two hundred cards in an evening. The second, Viktor, is slow: he reads each card as a cook would, understands which word is a station, which is an ingredient and which is part of a note, and only then rewrites it. He needs the old building's full manual on his desk to do it.

In the morning both piles are back, and both translators have attached the same kind of note to a few cards: "This card says pass the bowl along the row of 32 helpers. I translated the words. I cannot tell whether your rows are 32 long in the new building. Check it yourself." This chapter is about Noor, Viktor, and that note.

What you will be able to do

  • Explain the difference between a text-based translator (hipify-perl) and a compiler-based translator (hipify-clang), and choose between them for a given code base.
  • Run a translation on a CUDA program, read its report of changed lines and untranslated identifiers, and review the diff line by line.
  • Build the result for both back ends and decide, from the build messages, what still needs a human.
  • Identify what no renaming tool can fix: 32-lane assumptions, 32-bit lane masks, warp intrinsics without a direct counterpart, and tuning numbers.
  • Port the curriculum E1–E5 programs and verify them against their correctness tests (E9, first part).
Jargon box
HIPIFY
Simple words: AMD's tools that rewrite CUDA source code into HIP source code. Analogy: the translators who rewrite the recipe cards overnight. Precise: a project in the ROCm software with two translators, hipify-perl and hipify-clang, that replace CUDA identifiers, headers and some constructs with HIP equivalents and report what they could not translate. D2
hipify-perl
Simple words: the fast translator that swaps names in the text. Analogy: Noor, who reads the cards as plain text. Precise: a Perl script that applies pattern-based replacements to the source text; it does not parse C++ and does not need the CUDA headers. D2
hipify-clang
Simple words: the careful translator that first understands the code as a compiler does. Analogy: Viktor, who needs the old building's manual on his desk. Precise: a Clang-based tool that parses the CUDA source into a syntax tree (so it needs the CUDA headers and the same include paths and macros as a real compile), and rewrites the identifiers it resolves. D2 D5
Translation unit
Simple words: one source file together with everything it includes, as the compiler sees it. Analogy: one recipe card with all the sub-recipes it refers to clipped to it. Precise: the unit of compilation in C++ after preprocessing; a compiler-based translator works per translation unit, with that unit's macros and include paths. D5
Warp intrinsic
Simple words: a built-in function that lets threads of one warp or wavefront exchange values directly. Analogy: passing a bowl along the row of helpers. Precise: device functions such as CUDA's __shfl_down_sync(mask, v, delta) and HIP's __shfl_down(v, delta, width); their lane counts and mask widths differ between vendors, so a correct translation needs a human decision (F7-07). D1 D4 R5

The idea in pictures

Figure 1 is the porting loop this chapter teaches. A translator produces a HIP file and a report; you review both; you build for both back ends; each failure or warning sends you back to the source with a specific question. The loop ends only when both builds are clean and the correctness tests pass on a GPU. The translator is the cheapest step of the loop, and the only one that a tool can do alone.

Figure 2 shows the difference between the two translators on one line. A text translator sees characters; a compiler-based translator sees what each name is after the preprocessor and the C++ parser have run.

Layer 1 — the kid explanation

Changing cuda to hip by hand in a big program is slow and easy to get wrong. So AMD made tools that do it for you, called HIPIFY. There are two. One is quick and reads your program as plain text, swapping every name it knows. The other reads your program the way the compiler does, so it knows what each word means before changing it. The careful one needs more setup: it must be able to find the CUDA files your program uses.

Both tools only change names. They cannot know that your program quietly assumes that 32 threads move together. That assumption is written in numbers like 32, 16 and 31, not in names, and on many AMD GPUs it is wrong because 64 threads move together. So after any tool, you read what it changed, build for both kinds of GPU, and test. The tool does the typing; you do the thinking.

In this build the real HIPIFY tools were not installed. Instead you will use a tiny translator the university wrote, toyhipify.py, that works like the quick tool. It is small enough to read completely, so you can see exactly what "swapping names" can and cannot do.

Layer 2 — the student explanation

What a translator changes

A CUDA-to-HIP translator changes three kinds of thing: headers (cuda_runtime.h → hip/hip_runtime.h), runtime identifiers (functions, types, constants: the map of F7-03) and, for some constructs, syntax (older tool versions replaced <<<…>>> launches with hipLaunchKernelGGL). D2 Kernel code is mostly left as it is, because the HIP kernel language spells CUDA's built-ins the same way. The output of a run is a .hip (or .cpp) file plus statistics: how many names were converted and which were not. D2

In this build, toyhipify.py (Listing 1) did the first two for SAXPY, curriculum E1's program: 12 of 61 lines changed, 0 untranslated names, 0 lane warnings (R1). The diff in R1 is exactly the map of F7-03 applied to a real file: the header line, cudaError_t, cudaSuccess, cudaGetErrorString, cudaMalloc, cudaMemcpy with its direction constants, cudaGetLastError, cudaFree. The result built for AMD (R2) and for NVIDIA (R3) with no change by hand. R1 R2 R3

Reviewing the result

The report and the diff are where your work begins. For each translated file:

  1. Untranslated identifiers. Every name left with a cuda prefix or a _sync warp intrinsic is a decision for you: is there a HIP equivalent with different arguments, a library replacement, or nothing? In R4, toyhipify.py flagged __shfl_down_sync on line 20. R4
  2. Lane-count suspects. Numbers 32, 16, 31 and the mask 0xffffffff near warp-related code are suspects. R4 flagged lines 20 and 22. A tool can point at them; it cannot decide them.
  3. Strings and comments. The toy translator changed the message string "cudaMalloc dX" into "hipMalloc dX" (R1). Here that is welcome; in a string that is parsed by something else (a file name, a log key that monitoring depends on) it would be a bug.
  4. Build both back ends. The AMD build is the strict one (F7-03): R5 shows the AMD compiler rejecting __shfl_down_sync and suggesting __shfl_down, while the NVIDIA build accepted the same file (R6).

Layer 3 — the engineer's depth

Why text replacement is both useful and limited

C++ names are resolved after preprocessing, by scope, overloading and templates. D5 A text translator works before all of that. It is right when a CUDA name appears literally in the source, which covers most host code in course-sized programs: R1 needed no manual fix. It is fragile when names are built or hidden:

  • Token pasting. #define CU(f, ...) cuda##f(__VA_ARGS__) produces cudaMalloc only after preprocessing; the text contains cuda##f. (toyhipify.py would report a bare cuda identifier.)
  • Your own names that look like CUDA's. A variable called cudaStatus is not a runtime name; a translator that matched prefixes instead of whole names would rename it. toyhipify.py replaces whole identifiers from a table only (Listing 1, lines 69–78), so it would leave it and report it.
  • Conditional code. Code under #ifdef branches that are not active on the translating machine is invisible to a compiler-based tool for that run, and visible (but not understood) to a text tool.

A compiler-based translator handles the first two by seeing the resolved declarations, at the cost of needing a working CUDA compile environment per translation unit, and it handles the third only for the macro settings it was given. D2 D5 In practice: text pass first to see the size of the job, compiler pass on the files that matter, human review on everything both report.

Warp intrinsics: where a name map stops working

CUDA's warp shuffles since the _sync versions take an explicit 32-bit lane mask: __shfl_down_sync(0xffffffff, v, delta). D4 HIP 5.7's AMD headers offer __shfl_down(var, lane_delta, width = warpSize) without a mask (amd_detail/amd_warp_functions.h line 308, quoted by the compiler in R5). H1 R5 The translation is therefore not a rename: the mask argument has to go, and the decision whether the loop around it covers 32 or 64 lanes has to be made. In warp_sum.cu (Listing 3) the loop starts at offset 16 and the leader test is threadIdx.x % 32; both encode "32 lanes". Renaming would produce a program that compiles on AMD and gives a wrong sum on 64-lane hardware; F7-07 shows that failure lane by lane.

Not verified — check before relying on this

Later HIP versions may provide _sync variants of the warp functions, possibly with 64-bit masks; this build's HIP 5.7 for AMD did not (R5). Check the HIP documentation's section on warp cross-lane functions (D1) for your version before choosing between rewriting to __shfl_down and keeping _sync forms.

Libraries and what else translators touch

CUDA libraries (cuBLAS, cuRAND, CUB, Thrust and others) have AMD-side counterparts with their own names and sometimes their own interfaces (the hip- and roc- libraries), and HIPIFY's tables include many library calls. D2 D3 The curriculum's trap list says it plainly: do not assume "a CUDA library has a drop-in HIP equivalent without checking" (guide 6.2, BR-02). The E1–E5 programs of this course use only the runtime, so their ports do not depend on libraries; HP401 treats rocPRIM, hipCUB and rocBLAS.

How the hardware actually does it

A translator works on text and never sees hardware, which is exactly why it cannot fix hardware assumptions. The assumption in warp_sum.cu lives in the machine: on NVIDIA GPUs a warp is 32 threads that execute together; on AMD CDNA GPUs such as gfx90a a wavefront is 64 lanes (the compiler set .wavefront_size: 64 for gfx90a in this build, F7-05). D4 D6 A shuffle moves register values between lanes of one such group without going through memory; on AMD the HIP header implements __shfl_down and __shfl_xor with the LDS-permute instruction ds_bpermute_b32, which appears in this build's AMD assembly (F7-07, R3 there). H1 The loop bound decides how many lanes take part; the hardware decides how many lanes there are. Only you can make them agree.

Worked example

Task. Predict toyhipify.py's report for warp_sum.cu (Listing 3) before running it: lines changed, untranslated identifiers, lane-warning lines.

  1. Lines changed. Count lines containing a mapped name or the header: line 2 (header), 7 (cudaError_t), 9 (cudaSuccess), 10 (cudaGetErrorString), 33, 34 (cudaMalloc), 35 (cudaMemcpy, cudaMemcpyHostToDevice), 36 (cudaMemset), 38 (cudaGetLastError), 40 (cudaMemcpy, cudaMemcpyDeviceToHost), 42, 43 (cudaFree). That is 12 lines. (The comment on line 1 mentions "CUDA" in capitals and is left alone: the translator skips text after //.)
  2. Untranslated. __shfl_down_sync on line 20 is not in the header-derived table (the header maps __shfl_down to it on NVIDIA, not the other way) and matches the _sync rule: 1 identifier.
  3. Lane warnings. The rule needs a suspicious number and a warp-related word on the same code line. Line 19 has 16 but its warp-related word "lanes" is in the comment, which is cut off: no warning. Line 20 has 0xffffffff and shfl: warning. Line 22 has 32 and threadIdx: warning. Total 2.

Check against the run (R4): lines changed: 12 of 45, CUDA-looking identifiers NOT translated: 1 (line 20), lines that may assume 32 lanes: 2 (lines 20 and 22). Prediction confirmed. Note what the prediction exposed: line 19 (offset = 16) is a real 32-lane assumption that the heuristic missed. A report is a list of places to look, not a list of all problems.

Where the analogy breaks


    

  • Noor and Viktor understand cooking; the tools do not understand your algorithm. Even hipify-clang understands C++ declarations, not intent: it knows __shfl_down_sync is a function, not that your loop assumes 32 lanes.
    • 

  • A recipe card translated wrongly is visible on the plate; a port translated wrongly may still compile and run. SAXPY needed no human change; warp_sum would, after a rename, compile on AMD and print a wrong sum. The tests, not the translation, decide.
    • 

  • Viktor needs only the manual; hipify-clang needs a whole working CUDA compile setup (headers, include paths, macros) for each file, which can be harder to obtain than the analogy suggests.

Forensic lab answer key


Observation. R4: CUDA-looking identifiers NOT translated: 1, line 20: __shfl_down_sync; lines that may assume 32 lanes (check by hand): 2, lines 20 and 22. R5: gen/warp_sum.hip:20:14: error: use of undeclared identifier '__shfl_down_sync'; did you mean '__shfl_down'?, 1 error generated when compiling for gfx90a. R6: NVIDIA build succeeded.


Hypotheses. Installation: ruled out; the compiler ran, found the AMD header and even suggested a declared function. Translator: it did what it promised and reported line 20. Source: the CUDA source uses a mask-taking intrinsic and three 32-lane assumptions: confirmed.


Root cause. "0 conversion errors" counts names the tool tried and failed to convert; an intrinsic it does not map, or a number such as 16, is not a conversion error. The NVIDIA CI compiles CUDA names through HIP's header, so it could not see the problem.


Question 4. With offsets 16, 8, 4, 2, 1 inside a 64-lane wavefront, __shfl_down only moves values within distance 31, so lane 0 ends with the sum of lanes 0–31 = 32, and lane 32 with the sum of lanes 32–63 = 32. The leader test threadIdx.x % 32 == 0 makes lanes 0 and 32 of each wavefront leaders, so both add 32: the block total is 256 and the sum is n. The answer looks right by accident, because there are two leaders per wavefront. The same program with leader test threadIdx.x % warpSize == 0 (a common half-fix) would give 128 per block, half of n. F7-07 shows exactly this half-fix lane by lane. (Arithmetic from the code; the lane behaviour of __shfl_down at the edge of the wavefront is from the header and was modelled, not run on a GPU.)


Prevention. The PR template requires: the translator report with every flagged line answered; an AMD compile log; a grep for 32|16|31|0xffffffff in device code with each hit justified; and correctness results on AMD hardware (or an explicit "untested on AMD hardware"). How the evidence was produced: real translator run and real builds in this build; the 32-lane assumptions were written deliberately into warp_sum.cu.


Wrong answers. "Add -x cu to the AMD build": that selects the CUDA language for nvcc, not for clang's AMD path. "Use the NVIDIA back end on AMD": impossible.
