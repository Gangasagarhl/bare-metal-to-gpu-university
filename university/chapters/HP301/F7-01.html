Story hook

Amara runs the evening shift in a great kitchen hall. Her recipe cards are written for this hall: "fetch from pantry shelf C, use the blue stove, rows of 32 helpers". One day the company opens a second kitchen building across the road. The building has its own pantries, its own stoves of a different make, its own supervisors, and its rows of helpers are 64 long. Amara is asked to cook the same menu there by Friday.

She could rewrite every card by hand. Instead she notices that most of each card is the cooking itself: chop, mix, heat, plate. Only a few words name the building: which pantry, which stove, how long a row is. So she writes the cards once more in a shared cookbook language that both buildings' prep chefs can read, and she asks each building's prep chef to translate the card for the stoves there. The first card she tries comes back from the new building with a note: "Cooked fine. But your card says every row has 32 helpers. Ours have 64. Half your sauce was never stirred." This chapter is about that shared cookbook language, the second building, and that note.

What you will be able to do

  • Explain what HIP is and what ROCm is, and which of the two you are using when you write, build and run a GPU program.
  • Describe the two back ends of HIP: the AMD path (hipcc driving clang for a named GPU target) and the NVIDIA path (hipcc driving nvcc).
  • Build one HIP source file for both back ends and tell from the program's own output and from the executable which back end produced it.
  • List the contents of a HIP executable for AMD (host code plus one code object per GPU target) with a bundle-listing tool.
  • Name the differences between CUDA and HIP that bite first, starting with the lane count of a warp or wavefront.
Jargon box
HIP
Simple words: a way of writing GPU programs in C++ that can be built for AMD GPUs and for NVIDIA GPUs from the same source. Analogy: the shared cookbook language both kitchen buildings can read. Precise: AMD's C++ runtime API and kernel language (the expansion "Heterogeneous-compute Interface for Portability" is used in AMD's documents; check D1); its host API mirrors the CUDA runtime API with a hip prefix, and its kernel language uses the same __global__, threadIdx and <<<...>>> syntax as CUDA C++. The installed Ubuntu package describes itself as "C++ Runtime API and Kernel Language for AMD and NVIDIA GPUs". D1 H1
ROCm
Simple words: AMD's whole software stack for computing on its GPUs: drivers, runtimes, compilers, libraries and tools. Analogy: the second kitchen building itself, with its staff and equipment. Precise: the AMD open software platform for GPU computing, documented by AMD with its own installation guide and compatibility matrix; HIP is one part of it (the programming interface); rocminfo, the HSA runtime and the device libraries used in this build are others. D2 H1
hipcc
Simple words: the command you use to compile a HIP program; it calls the real compiler for you. Analogy: the prep chef who translates a card for the stoves of the building it will be cooked in. Precise: HIP's compiler driver; on the AMD platform it runs clang with HIP options and an --offload-arch per GPU target; on the NVIDIA platform it runs nvcc. This build's hipcc printed both command lines (R4, F7-06). D1 R4
HIP platform (back end)
Simple words: which vendor's GPU a HIP build is for. Analogy: which building the card is translated for. Precise: the choice between HIP's AMD implementation (ROCm runtime, clang) and its NVIDIA implementation (headers that wrap the CUDA runtime, nvcc); visible in the macros __HIP_PLATFORM_AMD__ and __HIP_PLATFORM_NVIDIA__ and selected in this build with the environment variable HIP_PLATFORM. D1 R1 R3
GPU target (gfx name)
Simple words: the exact family of AMD GPU the machine code is made for, written like gfx90a. Analogy: the model of stove the card is written for. Precise: the processor name passed to --offload-arch; the compiler emits one code object per target, and that code object runs only on GPUs of that target (F7-02 checks yours). D5 R2
Offload bundle (fat binary)
Simple words: one executable file that carries the CPU program and the GPU programs together. Analogy: a recipe binder with the head chef's card and one card per stove model. Precise: the container clang writes into a HIP executable: a host entry (host-x86_64-unknown-linux) and one device code object per target (hipv4-amdgcn-amd-amdhsa--gfx90a), listed in this build by roc-obj-ls. D5 R2
Wavefront
Simple words: AMD's name for the group of GPU threads that move together, like NVIDIA's warp. Analogy: a row of helpers, 64 long in the second building's main halls. Precise: the unit of SIMT execution on AMD GPUs; 64 lanes on CDNA targets such as gfx90a, 32 or 64 on RDNA; inside a HIP kernel the built-in warpSize holds the value for the compiled target (64 for gfx90a and 32 for gfx1030 in this build's compiler output, F7-07). Defined first in F1-57. D1 R5

The idea in pictures

Figure 1 is the map of the whole course. One HIP source file goes to hipcc. Which way it then goes depends on the HIP platform. On the AMD path, clang compiles the host part for the CPU and the kernels for each named GPU target, and packs everything into one bundle that the ROCm runtime loads. On the NVIDIA path, hipcc hands the same file to nvcc, and HIP's own headers turn every hip call into a CUDA runtime call. Layer 1 — the kid explanation

A GPU program is a recipe card that thousands of helpers follow at once. You learned to write such cards for one kitchen building, NVIDIA's, in the language CUDA. Now there is a second building, AMD's. Its stoves are different, its rows of helpers can be 64 long instead of 32, and its staff use different names for some tools.

HIP is a way to write the card once so that both buildings can cook from it. Most of the card does not change at all: the cooking steps are the same. What changes are the words that name the building's tools: cudaMalloc becomes hipMalloc, cudaMemcpy becomes hipMemcpy. A prep chef called hipcc reads your card and prepares it for whichever building you choose.

ROCm is the second building itself: its drivers, its compiler, its runtime, its tools. When people say "it runs on ROCm", they mean "it runs in AMD's building". When they say "it is written in HIP", they mean "the card is in the shared language". You will meet both words in every chapter of this course.

Layer 2 — the student explanation

What HIP is, and what stays the same

HIP has two halves, exactly as CUDA does. The runtime API is a set of host functions for devices, memory, streams, events and errors; its names follow the CUDA runtime with the prefix hip instead of cuda. The kernel language is C++ with the same execution-space qualifiers (__global__, __device__), the same built-in indices (threadIdx, blockIdx, blockDim, gridDim) and the same triple-angle-bracket launch. D1 Listing 1 below compiles unchanged for both back ends in this build, which is evidence that the CUDA-style syntax is accepted by both compilers for this program (R1, R3).

So everything you learned in CU201 carries over: the thread hierarchy and the global index formula (F6-02), the memory spaces (F6-03), the habit of checking every call and every launch. HIP calls AMD's "shared memory" by the same keyword, __shared__; AMD's hardware documents call the memory behind it the Local Data Share (LDS). D1 D6

What ROCm is

ROCm is the platform around HIP on AMD GPUs: kernel driver, runtime libraries, compiler, math and communication libraries, profilers and diagnostic tools. D2 In this build the pieces installed were Ubuntu packages: hipcc, libamdhip64 (the HIP runtime for AMD GPUs), libhsa-runtime64 (the HSA runtime the HIP runtime sits on), rocm-device-libs (device-side libraries linked into every kernel), libamd-comgr (the code object manager) and rocminfo. Their versions are in the lab record (R6). H1 A full ROCm installation from AMD contains more: libraries such as rocBLAS and rocPRIM, profilers, and the kernel driver for the GPU. Which pieces you need depends on what you build; F7-02 treats installation.

Two back ends

HIP is not only an AMD thing. Its NVIDIA back end is a set of headers in which every hip function is a small inline wrapper around the CUDA function of the same meaning; hipcc then calls nvcc. D1 H2 You will read those headers in F7-03; for example, line 1495 of the installed nvidia_hip_runtime_api.h defines hipMalloc as a call to cudaMalloc whose error code is converted to a hipError_t. H2

The AMD back end works differently. There is no translation into another vendor's API: the HIP runtime library (libamdhip64) talks to the ROCm stack directly, and the kernels are compiled by clang's AMDGPU back end into machine code for one or more named GPU targets. D1 D5 Listing 2's output (R2) shows the result: one file holding host code and a gfx90a code object.

What differs, most dangerous first

  1. The lane count. A warp on NVIDIA GPUs has 32 threads; an AMD wavefront has 64 on CDNA targets and 32 or 64 on RDNA targets. D1 D4 Code that writes 32 where it means "one warp" compiles and runs on AMD and gives wrong answers. In this build, the HIP compiler turned warpSize into the constant 64 for gfx90a and 32 for gfx1030 (R5). F7-07 works through a real case.
  2. Lane masks. Votes and masks have one bit per lane, so on 64-lane hardware they are 64 bits wide. HIP's __ballot returns unsigned long long in the installed AMD header. H3 A port that stores it in a 32-bit integer silently loses half the lanes (F1-57).
  3. Names that do not map one to one. Most runtime names differ only by the prefix, but some do not (hipHostMalloc wraps cudaHostAlloc), some CUDA functions have no HIP counterpart in a given version, and libraries have their own names. H2 F7-03 and F7-04.
  4. Hardware support is a list. ROCm supports specific GPUs and Linux distributions, listed in AMD's compatibility matrix for each ROCm version. D2 F7-02.
  5. Different tools. Profilers, debuggers and sanitizers have different names and options (HP302).

Layer 3 — the engineer's depth

The programming model is shared; the machine is not

HIP deliberately reproduces the CUDA runtime's programming model: a host thread enqueues work on a device; kernels are launched over a grid of blocks of threads; memory is allocated, copied and freed by explicit calls; work is ordered in streams and timed with events; errors are returned as codes and a sticky last error. D1 D4 That is why porting is mostly renaming. But the model leaves some numbers to the hardware: the width of the lock-step group, the size and banking of shared memory, register-file sizes, how many blocks fit on one compute unit. Code that only uses the model ports cleanly; code that builds a hardware number into its algorithm does not. The curriculum's 13.1 vocabulary table puts it in one line: "never hard-code 32 in portable code". Curriculum, track E.

What happens at compile time on each back end

On the AMD platform hipcc is a thin driver over clang. In this build it printed its real command: /usr/bin/clang++-17 --offload-arch=gfx90a -mllvm -amdgpu-early-inline-all=true -mllvm -amdgpu-function-calls=false ... -x hip (R4, recorded in F7-06). Clang compiles each translation unit twice: once for the host and once per --offload-arch; the device passes produce code objects for the AMDGPU targets, and the link step packs them with the host code. D5 Without --offload-arch, this build's hipcc chose gfx906 by itself (R4 of F7-06), which is rarely what you want; F7-06 makes that a forensic case.

On the NVIDIA platform hipcc ran /usr/bin/nvcc -Wno-deprecated-gpu-targets -lcuda -lcudart -L/usr/lib64 -std=c++17 -x cu plus your file. Everything after that is CUDA: nvcc splits host and device code, PTX and SASS are produced as in CU201, and the HIP headers make the hip names resolve to CUDA. D1 R7 Two consequences matter for porting. First, anything CUDA accepts also compiles on the NVIDIA back end, including leftover CUDA names, so a port can "build fine" on NVIDIA and still fail on AMD (forensic lab of F7-03). Second, the runtime underneath is NVIDIA's, so error names printed on the NVIDIA back end are CUDA's: in R3, hipGetErrorName printed cudaErrorNoDevice.

Which platform am I on?

Three places tell you, and they can disagree. hipconfig --platform reports the installation's default (amd in this build). R6 The environment variable HIP_PLATFORM overrides it for one hipcc invocation (R3 used HIP_PLATFORM=nvidia). Inside the program, the macros __HIP_PLATFORM_AMD__ and __HIP_PLATFORM_NVIDIA__ tell the code which one compiled it, and Listing 1 prints that. D1 R1 R3 The only reliable answer about a given executable is the executable itself: its printed platform line, or for AMD builds its bundle listing (R2).

Not verified — check before relying on this

The expansion of the name HIP, the list of ROCm components, and the statement that a full ROCm install includes the kernel driver are written from the course card and the registry, not from an opened document. Check D1 (HIP documentation, introduction) and D2 (ROCm documentation, "what is ROCm" and installation overview) for the ROCm version in your dossier. The environment variable CUDA_PATH=/usr used in this build's NVIDIA-back-end commands was needed because this container's CUDA is installed in /usr rather than where hipcc looks by default (hipcc first failed with "/usr/local/cuda/bin/nvcc: not found"); on a standard CUDA install you may not need it. Check D1's NVIDIA-platform build instructions.

How the hardware actually does it

The two buildings are different machines that agree on a programming model. An NVIDIA GPU groups threads into warps of 32 and runs them on streaming multiprocessors; an AMD GPU groups them into wavefronts and runs them on compute units (CUs). D4 D6 On AMD hardware each wavefront has vector registers (one value per lane) and scalar registers (one value per wavefront), and an execution mask chooses which lanes take part in each vector instruction. You can already see these in this build's compiler output: in F7-05's assembly for gfx90a, addresses are computed in scalar registers (s0, s1, …), per-thread values in vector registers (v0, v1, …), and the bounds check becomes a 64-bit mask operation (s_and_saveexec_b64). D6 R8 The same source on NVIDIA becomes PTX with a predicate and a branch (F7-07). Same recipe; different stove. HP302 is the course on AMD hardware in depth.

Worked example

Question. You build hello_hip.hip twice, once with the defaults and once with HIP_PLATFORM=nvidia, and run both on a machine without a GPU. Predict, for each run: the platform line, the error name, and how many entries roc-obj-ls lists for the AMD build compiled with --offload-arch=gfx90a.

  1. Platform line. The default platform here is amd (R6), so the first build defines __HIP_PLATFORM_AMD__; the second defines __HIP_PLATFORM_NVIDIA__. Listing 1's preprocessor branch prints one of the two lines.
  2. Error name. hipGetDeviceCount is the first call that needs a device. On AMD, the HIP runtime reports its own code; on NVIDIA, the wrapper calls cudaGetDeviceCount, and hipGetErrorName asks CUDA for the name (H2, line 1876: it returns cudaGetErrorName(hipErrorToCudaError(error))). So the second run prints a CUDA error name.
  3. Bundle entries. One host entry plus one code object per --offload-arch: 1 + 1 = 2.

Check against the runs. R1: built for platform: AMD (ROCm back end) and hipErrorNoDevice (no ROCm-capable device is detected). R3: built for platform: NVIDIA (CUDA back end) and cudaErrorNoDevice (no CUDA-capable device is detected). R2: two entries, host-x86_64-unknown-linux-- and hipv4-amdgcn-amd-amdhsa--gfx90a. Prediction confirmed in all three parts.

Where the analogy breaks


    

  • The "shared cookbook language" is mostly CUDA's own words with a new prefix. A real shared language would be neutral; HIP follows the CUDA runtime closely (D1, H2). That makes porting easy and also means CUDA habits, good and bad, come along.
    • 

  • A recipe card can be read in any kitchen; a compiled AMD code object cannot. The machine code for gfx90a is for that target only. The analogy's "card" is the source; the executable is a binder of stove-specific cards, and a stove whose card is missing cannot cook at all (F7-02, F7-06).
    • 

  • On the NVIDIA path, there is no second building. HIP on NVIDIA runs in NVIDIA's own kitchen through CUDA; only the card's words differ (H2). "Running HIP" does not by itself mean "running on AMD".
    • 

  • Rows of helpers are not a fixed 64 in the second building. RDNA targets use 32 by default in this build's compiler output (R5); the lane count belongs to the target, not to the vendor.
    •

Summary


    

  • HIP is a C++ runtime API and kernel language that mirrors CUDA's; ROCm is AMD's GPU software platform, of which HIP is one part.
    • 

  • hipcc is a driver: on AMD it runs clang with one --offload-arch per GPU target; on NVIDIA it runs nvcc and HIP's headers wrap CUDA calls.
    • 

  • An AMD HIP executable is a bundle: host code plus one code object per target (roc-obj-ls lists it).
    • 

  • The executable tells you its platform; the installation default does not.
    • 

  • Most porting is renaming; the dangerous part is hidden hardware numbers, first of all the lane count (32 versus 64) and 32-bit lane masks.
    • 

  • Nothing in this chapter ran on a GPU: builds, listings and runtime errors are real; GPU results are untested on hardware.

Answers to Check yourself


    

  1. HIP: a C++ GPU runtime API and kernel language that mirrors CUDA and builds for AMD and NVIDIA. ROCm: AMD's software platform for GPU computing (drivers, runtimes, compiler, libraries, tools), of which HIP is one part. hipcc: HIP's compiler driver, which runs clang (AMD) or nvcc (NVIDIA).
    2. 

  2. (c), shown by H2 line 1495. (a) is false: the NVIDIA back end runs on NVIDIA GPUs (R3). (b) is false: a code object is for its target only. (d) is false: it reports the installation default; the environment variable can override it per build, and only the executable shows what built it.
    3. 

  3. On the NVIDIA back end hipGetErrorName is a wrapper that converts the HIP error back to a CUDA error and calls cudaGetErrorName (H2 line 1876), so CUDA's names appear.
    4. 

  4. Most of a CUDA program is the shared programming model (indices, launches, memory calls) and C++, and HIP mirrors those names. Not the whole story because some algorithms build hardware numbers into the code (lane count, mask width, tuning sizes), some names do not map one to one, and libraries and tools differ.
    5. 

  5. Three: one host entry and two code objects (…gfx1030, …gfx90a). F7-02's R3 shows exactly that.

Forensic lab answer key


Observation. Line 1 differs: built for platform: AMD (ROCm back end) versus built for platform: NVIDIA (CUDA back end). Line 2 is the same (HIP headers: version 5.7). Line 3 differs in the error's name and text: hipErrorNoDevice (no ROCm-capable device is detected) versus cudaErrorNoDevice (no CUDA-capable device is detected) (R1, R3).


Hypotheses. (1) Two back ends: supported by both differing lines. (2) Two HIP versions: ruled out by the identical header-version line. (3) Two machines with different GPUs: cannot explain the platform line, which is decided at compile time by the macros, not by the machine.


Root cause. The second executable was built with HIP_PLATFORM=nvidia; it runs on the CUDA runtime and its errors are CUDA's. The claim "AMD works" rests on an NVIDIA-back-end build and is unsupported. The default build is the AMD one; R2 shows it carries a gfx90a code object only.


What would prove AMD readiness without a GPU. Nothing proves it runs correctly; a GPU run is needed. Without one you can show that it builds for AMD and which targets it contains (bundle listing), and that the lab GPU's target is among them (F7-02).


Prevention. Every result records the build command, HIP_PLATFORM, the target list and the program's own platform line (the mini-project's passport). How the evidence was produced: real builds and runs in this build (HIP 5.7.31921, nvcc 12.0); nothing was injected, the two builds differ only in HIP_PLATFORM.


Wrong answers. "Both failed the same way, so they are equivalent": the error is the same kind (no device) but from different runtimes. "The header version differs": it does not.
