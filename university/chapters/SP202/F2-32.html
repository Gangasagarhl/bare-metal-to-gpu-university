Story hook

The translator returns a recipe with a note that runs to three pages. A junior cook panics and puts it in a drawer. The head chef reads it differently. She skips to the line that mentions her recipe, step 9. Then she reads the one sentence that says what is wrong: "The tool in step 9 needs a tray you can jump around in; this recipe uses a chain of bowls." Everything else is the translator explaining how she got there.

The head chef also reads the translation itself now and then, to see what the cooks will really do. Sometimes it is cleverer than the original: "divide into 8 portions" became "halve, halve, halve".

This chapter teaches you to read the compiler's long notes, its translation (assembly), the names it writes into object files, and its reports about what it optimised.

What you will be able to do

  • Triage a long template error: find your own line ("required from here") and the one error line that matters.
  • Compare how g++ and clang++ present the same error.
  • Produce and read assembly for small functions at -O0 and -O2, in AT&T and Intel syntax.
  • Explain why x / 8 compiles to different instructions for unsigned and int.
  • Demangle symbol names with nm -C and c++filt.
  • Ask the compiler which loops it vectorised and why it refused others.
Jargon box
Instantiation context
Simple words: the chain of "this template was used from there" lines that leads from an error inside a library back to your own code. Analogy: the translator's note "this problem comes from step 9 of your recipe". Precise: when an error occurs inside a template instantiation, GCC prints "In instantiation of …" and "required from …" lines, ending with "required from here" at the user's code; Clang prints "note: in instantiation of … requested here". R1 R3
Assembly output
Simple words: the compiler's translation of your code into processor instructions, as readable text. Analogy: the translated recipe the cooks really follow. Precise: the output of -S (stop after generating assembly); x86-64 assembly is printed in AT&T syntax by default in GCC and Clang, or Intel syntax with -masm=intel. D1 R5
Strength reduction
Simple words: the compiler replacing an expensive operation with a cheaper one that gives the same result. Analogy: "divide into 8" becomes "halve three times". Precise: an optimisation that replaces, for example, division by a power of two with a shift (plus a correction for signed values), or a multiplication with additions and shifts. D6 R4
Name mangling
Simple words: the compiler's way of writing a C++ function name plus its parameter types as one plain symbol. Analogy: a coded label on a jar that includes what goes inside. Precise: see the glossary entry from SP101; on Linux, g++ follows the Itanium C++ ABI, for example square(int) → _Z6squarei. R6 D3
Demangling
Simple words: turning a mangled symbol back into the readable C++ name. Analogy: decoding the jar's label. Precise: done by c++filt, by nm -C, and by debuggers and sanitizers when they print function names. R6
Optimisation report
Simple words: messages in which the compiler tells you what it optimised, and what it could not, and why. Analogy: the translator's note "I combined steps 3 and 4; I could not combine 7 and 8 because 8 needs 7's result". Precise: GCC -fopt-info-<group>-<kind> (for example -fopt-info-vec-optimized), Clang -Rpass=, -Rpass-missed= and -Rpass-analysis= remarks. R7 R8 D1 D2

The idea in pictures

Figure 1 shows how to read a template error. The compiler reports the problem where it was detected, deep inside the library, and then lists how it got there. You read two lines: the "required from here" line (your code) and the "error:" line (the reason).

Layer 1 — the kid explanation

A compiler talks to you in several ways. When something is wrong, it prints messages. Sometimes they are very long, because the mistake shows up deep inside code someone else wrote. The trick is to find the line that mentions your file, and the line that says error:. Those two usually tell the whole story.

The compiler can also show you its translation: the list of simple steps the processor will do. You do not need to read every program this way. But reading a few small ones teaches you what the computer really does, and sometimes it is surprising: the compiler finds shortcuts you did not write.

And if you ask, the compiler will tell you which loops it managed to speed up, and which it could not, with a reason.

Layer 2 — the student explanation

Triage a template error

sort_list.cpp (Listing 1) calls std::sort on a std::list. g++ produced 24 lines of messages. R2 A filter for the two important kinds of line gave:

  • sort_list.cpp:9:14: required from here: the line in your code that started the problem.
  • stl_algo.h:1948:50: error: no match for 'operator-' (operand types are 'std::_List_iterator<int>' and …): the reason.

So: on line 9, std::sort tried to subtract two list iterators, and list iterators cannot be subtracted. std::sort needs random-access iterators (it jumps to the middle); a list can only step one element at a time. The fix is the list's own member function waiting.sort(), or a std::vector. D5 The rest of the messages ("note: candidate: … reverse_iterator", "template argument deduction/substitution failed") list the operator- versions the compiler tried and why each did not fit. They are correct, but not needed here. R1

clang++ reported the same problem as error: invalid operands to binary expression, with "note: in instantiation of function template specialization 'std::sort<std::_List_iterator<int>>' requested here" pointing at sort_list.cpp:9:10, and found a second error at another line of the library ("2 errors generated"). R3 When one compiler's message is hard to read, try the other.

Read the translation

g++ -S -o - file.cc prints assembly instead of building an object file. The lab adds two options that remove noise (-fno-asynchronous-unwind-tables removes unwind directives, -fcf-protection=none removes control-flow-protection instructions) and filters out assembler directives. R4 D1 For square (Listing 3):

  • At -O0: 7 instructions. The function saves the frame pointer, stores the argument %edi on the stack, loads it back into %eax, multiplies (imull %eax, %eax), restores, returns. Every variable lives in memory, as in F1-31.
  • At -O2: 3 instructions: imull %edi, %edi, movl %edi, %eax, ret. The argument arrives in %edi and the result leaves in %eax, by the calling convention; nothing touches memory. R4 D4

AT&T syntax writes the source first and the destination last (movl %edi, %eax copies edi into eax), with % on registers and $ on constants. Intel syntax (-masm=intel) reverses the order and drops the sigils: sar eax, 3. R5 Know both; documentation and tools use both.

Names in object files

nm explore.o listed four symbols such as _Z6squarei and _Z11divide_by_8j; nm -C printed square(int) and divide_by_8(unsigned int), and echo _Z6squarei | c++filt printed square(int). R6 You can read the pattern: _Z, the name's length (6), the name (square), then the parameter types (i = int, j = unsigned int). Mangled names appear in linker errors ("undefined reference to …"); c++filt turns them back into C++.

Layer 3 — the engineer's depth

  • Division by 8. For unsigned, the compiler emitted one shift right (shrl $3) at both levels. For int it emitted four instructions at -O2: testl %edi, %edi, leal 7(%rdi), %eax, cmovns %edi, %eax, sarl $3, %eax. R4 C++ integer division rounds toward zero, but an arithmetic shift rounds toward minus infinity; for negative x, adding 7 first fixes the difference. cmovns ("move if not sign") keeps the original x when it is not negative. D5 D4 No division instruction appears. If you know a value is never negative, saying so with an unsigned type is information the compiler can use.
  • Range check without branches. x >= 10 && x < 20 became, at -O2, subl $10, %edi, cmpl $9, %edi, setbe %al in g++, and addl $-10, cmpl $10, setb in clang++. R4 Both subtract 10 and do one unsigned comparison (setbe = "set if below or equal", unsigned): values below 10 wrap around to huge unsigned numbers and fail the test. At -O0 the same function had two compares and three jumps. Two compilers, two different but equivalent instruction sequences.
  • Vectorisation reports. For saxpy (each element independent), g++ -O3 -fopt-info-vec-optimized reported "loop vectorized using 16 byte vectors" (four floats at once) and "loop versioned for vectorization because of possible aliasing". R7 "Versioned" means the compiler generated two versions and a run-time check: x and y might point into the same array, in which case the safe scalar loop runs. clang++ at -O2 reported "vectorized loop (vectorization width: 4, interleaved count: 2)". For running_sum, clang++ explained "Backward loop carried data dependence": each y[i] needs y[i - 1], which is computed in the previous step. g++ said "couldn't vectorize loop" with a less direct reason. R8 R7 Vectorisation itself (see the glossary entry) returns in the hardware and GPU courses; here the point is that you can ask.
  • Online and local exploration. Many engineers use a website called Compiler Explorer to see assembly for many compilers side by side. The lab's explore commands do the same thing locally, with the compilers installed on your machine, which also means the result matches what your build really uses.

How the hardware actually does it

The assembly you read is one step from the machine: the assembler turns each line into a few bytes of machine code, which the processor fetches, decodes and executes (F1-23 to F1-25). D4 Registers such as %edi and %eax are storage inside the processor; %edi is the 32-bit lower half of the 64-bit register %rdi, which is why leal 7(%rdi), %eax can use the 64-bit name while working on a 32-bit value. D4 A shift by 3 is a cheap operation for the processor; a general integer division is one of its slower operations, which is why compilers work hard to avoid it when the divisor is a constant. D6 This build did not time either instruction; F2-33 measures programs, not single instructions.

Worked example

Task. Check by hand that the -O2 code for divide_by_8_signed gives the C++ answer for x = -9 and x = 17. R4

  1. C++: -9 / 8 = −1.125, rounded toward zero = −1. 17 / 8 = 2.125 → 2. D5
  2. x = -9: testl sees a negative value (sign flag set). leal 7(%rdi) gives −2 in %eax. cmovns does nothing (the sign is set), so %eax stays −2. sarl $3: −2 / 8 = −0.25, and an arithmetic shift rounds toward minus infinity: −1. Correct.
  3. Without the correction, sarl $3 on −9 would give −1.125 rounded down = −2: wrong. That is why the extra instructions exist.
  4. x = 17: not negative, so cmovns copies 17 into %eax (overwriting 24). sarl $3: 17 / 8 = 2.125 → 2. Correct.

The lab asks you to confirm this by running a small test program with both values.

Where the analogy breaks


    

  • The translator is never vague. A human's long note may ramble. The compiler's long error is a precise log of what it tried; every line is true, only most are not needed.
    • 

  • The translation is not the recipe rearranged. A human translator keeps the steps in order. The optimiser removes, merges and reorders steps freely, as long as the visible result is the same (the two-compare in_range became one, R4).
    • 

  • Different translators, different good translations. g++ and clang++ produced different, equally correct instruction sequences for in_range and square (R4). There is no single "right" assembly.
    • 




Common mistakes and debugging


    

  • Symptom: you read the first line of a long error and are lost in library code. Cause: the first line is where the error was detected. Fix: search for "required from here" (g++) or "requested here" (clang++), then the "error:" line.
    • 

  • Symptom: the assembly is full of .cfi_ and other dot-lines. Cause: assembler directives. Fix: -fno-asynchronous-unwind-tables and a filter as in the lab (R4).
    • 

  • Symptom: the function you want is missing from -O2 assembly. Cause: it was inlined into its caller or removed as unused (dead code elimination). Fix: compile the function alone in a file, as explore.cc does, or make it non-static.
    • 

  • Symptom: a linker error shows _Z… names. Fix: pipe it through c++filt; compare the parameter types with your declaration.
    • 

  • Symptom: you conclude "the compiler did not vectorise" from -O2 g++ output. Cause: this lab asked g++ for its report at -O3, not -O2; what is vectorised depends on the level, the compiler and its version. Fix: ask for the report at the level you build with, and check the manual of your version.
    •

Forensic lab answer key


Observation. g++: orders.cpp:17:26:   required from here (twice). clang++: orders.cpp:17:17: note: in instantiation of member function 'std::vector<std::unique_ptr<Order>>::push_back' requested here. Both name line 17, open_orders.push_back(order);. R9 R10


Hypotheses. (1) A broken library installation. (2) Wrong use of the library in Wei's code. (3) A compiler bug. Evidence: two different compilers fail at the same line of Wei's code with consistent reasons, and both use the library successfully elsewhere (all other labs). That rules out (1) and (3) in practice.


Root cause. push_back(order) with a named variable chooses the push_back(const value_type&) overload (the g++ chain shows it: push_back(const value_type&)), which must copy the unique_ptr. A unique_ptr owns its object alone, so its copy constructor is deleted: unique_ptr(const unique_ptr&) = delete;, shown by "note: declared here" at unique_ptr.h:522. R9 D5


Fix. open_orders.push_back(std::move(order)); — ownership moves into the vector. Afterwards order is empty (null). The fixed program printed "1 open order(s); order is empty after the move" and "first: noodle soup for table 4", under ASan and UBSan. R11 (Creating the pointer directly in the call, open_orders.push_back(std::make_unique<Order>(...)), also works.)


Prevention. "A unique_ptr cannot be copied, only moved; if you see 'use of deleted function … unique_ptr(const unique_ptr&)', you tried to copy one. Find 'required from here' to see where, and use std::move if you mean to give the ownership away."


Wrong answers and why. "Go back to raw pointers": the error is the type system catching a real ownership mistake; with raw pointers, the same code compiles and two owners might delete the order. "Use shared_ptr": it compiles, but changes the design to shared ownership without a reason.
