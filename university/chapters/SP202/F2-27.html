Story hook

The restaurant's recipes are written in Sofia's language, and the kitchen works in another. A translator rewrites each recipe for the cooks. She is careful and literal: whatever the recipe says, she translates. But sometimes she writes a small note in the margin. "Step 4 says to add the salt to the empty pot. Did you mean the soup pot?" "This step uses a jug that was put away in step 2."

A busy chef could ignore the notes. The translation is still done, and the cooks will still cook. Most evenings nothing happens. Then one evening, a customer gets a soup with no salt at all, because step 4 really did put it into the wrong pot.

Your compiler is that translator. Its margin notes are called warnings. This chapter teaches you to switch on more of them, to read them, and to let them stop the build, because each one is a free review of your code by a very patient expert.

What you will be able to do

  • Explain the difference between a compiler error and a warning, and why a program with warnings can still be wrong when it runs.
  • Choose a warning set (-Wall, -Wextra, -Wpedantic, -Wconversion, -Wshadow) and ask the compiler which warnings each flag really enables.
  • Read a warning: file, line, column, the message, and the flag named in brackets.
  • Fix the cause of a warning instead of silencing it, and recognise the rare case where a targeted suppression is right.
  • Compare what two compilers and two optimisation levels report for the same file.
  • Diagnose a wrong result from a build log full of ignored warnings.
Jargon box
Diagnostic
Simple words: any message the compiler prints about your code: an error, a warning or a note. Analogy: anything the translator writes in the margin. Precise: a message with a location (file:line:column), a kind (error, warning, note) and text; GCC and Clang add the controlling option in brackets, for example [-Wshadow]. D1 R1
Warning
Simple words: a message about code that is allowed but looks suspicious. The program is still built. Analogy: the translator's margin note. Precise: a non-fatal diagnostic; see the glossary entry from F0-36. D1
Warning flag
Simple words: a compiler option that switches one warning, or a group of warnings, on or off. Analogy: telling the translator which kinds of notes you want. Precise: a -W<name> option; -W<name> enables, -Wno-<name> disables; group flags such as -Wall ("Enable most warning messages.") and -Wextra ("Print extra (possibly unwanted) warnings.") enable sets of warnings. R4 D1
Warnings as errors (-Werror)
Simple words: an option that makes every warning stop the build. Analogy: the head chef's rule: no recipe goes to the cooks while it has margin notes. Precise: GCC and Clang option that turns warnings into errors, so the compile fails; the template's UNI_WERROR option adds it (F2-26). D1 R6
Shadowing
Simple words: declaring a new variable with the same name as one that already exists, so the old one is hidden. Analogy: two jars labelled "salt" on two shelves; you reach for the wrong one. Precise: a declaration in an inner scope that hides an entity with the same name in an enclosing scope; -Wshadow "Warn[s] when one variable shadows another". R4 D3
Implicit conversion
Simple words: the compiler changing a value from one type to another without you writing it, sometimes losing part of it. Analogy: the translator rounding "2½ cups" to "2 cups" without telling you. Precise: a conversion inserted by the language rules (for example double to int, which drops the fraction, or int to an unsigned type); -Wconversion is described by g++ as "Warn for implicit type conversions that may" (the help line is cut there; the full text is in the manual). R4 D3
Uninitialised variable
Simple words: a variable you read before you gave it a value. It holds whatever was in that memory before. Analogy: a jar you never filled, still holding yesterday's leftovers. Precise: an automatic variable read before any value was stored in it; reading such an indeterminate value is undefined behaviour in C++ (F2-23). D3

Layer 1 — the kid explanation

When the compiler finds something it cannot translate, it stops. That is an error, and you met many of them in F0-36. When it finds something it can translate but that looks like a mistake, it prints a warning and carries on. Your program is built anyway.

That is the danger. A warning that scrolls past is easy to ignore, and the program may even seem to work. But a warning often points at the exact line where a bug lives: a value you forgot to set, a number that loses its fraction, a test that compares in the wrong way.

So engineers do three things. They ask for more warnings than the compiler gives by default. They read every warning and fix its cause. And they set the build to fail on any warning, so that nobody can ignore one by accident. Warnings are not insults. They are free advice.

Layer 2 — the student explanation

Reading a warning

Every diagnostic from g++ and clang++ has the same shape: file:line:column: kind: message [option], often followed by the source line with a marker under the exact spot. D1 D2 For example, from the forensic build: invoice.cc:23:16: warning: declaration of 'rate' shadows a previous local [-Wshadow], followed by a note: pointing to line 21, "shadowed declaration is here". R7 The option in brackets tells you which flag produced it, and therefore where to read about it.

Which flags turn on which warnings

Do not guess what a group flag contains: ask the compiler. g++ -Q --help=warnings prints every warning with its state for the flags you give. R4 In this build, with no flags, -Wreturn-type carried no "[disabled]" mark (and it did report bug 1), while -Wparentheses, -Wsign-compare, -Wuninitialized, -Wmaybe-uninitialized and -Wunused-variable were "[disabled]". Adding -Wall enabled all five of them. -Wconversion, -Wfloat-conversion and -Wshadow stayed "[disabled]" even with -Wall -Wextra: you must ask for them by name. R4 That matches the experiment of Figure 1: the double-into-int bug and the shadowed variable were reported only when -Wconversion and -Wshadow were added. R1

The university template uses -Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wsign-conversion with -Werror (F2-26, Listing 1). -Wpedantic "Issue[s] warnings needed for strict compliance to" the standard, so non-standard extensions are reported; -Wsign-conversion covers conversions between signed and unsigned types. R4

The five bugs

bugs.cc (Listing 1) compiles, and the run printed 1 2 … 400 0 where the right answers are 1 2.5 2 2000 1 (the third number was a large meaningless value read from an uninitialised variable). R5 Each wrong value matches a warning:

  • Missing return (line 10): grade(30) would fall off the end of a function that must return int; using that value is undefined behaviour. -Wreturn-type, on even without flags in g++. R1 D3
  • double into int (line 16): total += x converts 2.5 to int each time, dropping the fraction, so the average became 2. -Wfloat-conversion (part of -Wconversion). R1
  • Uninitialised count (line 23): the result started from whatever was in memory. Reported by clang at -O0 (-Wuninitialized) and by g++ only at -O2 (-Wmaybe-uninitialized). R2 R3
  • Shadowed factor (line 36): the inner int factor = 10; is a new variable; the outer one stays 2, so scale(200) returned 400. -Wshadow. R1
  • Assignment in a condition (line 44): if (x = 0) stores 0 and tests 0, which is false, so is_zero(0) returned false. -Wparentheses, in -Wall. R1

The fixed file (Listing 2) builds with no warnings under both compilers, at -O0 and -O2, with the template's full set and -Werror, and prints 1 2.5 2 2000 1. R6

Why make warnings errors

A warning that does not stop the build is a request for attention that a busy person can postpone forever. The forensic lab below is a real case: four warnings in a build log, one of them pointing exactly at the reported bug, all ignored. R7 With -Werror, the first warning stops the build, so the code base stays at zero warnings and every new warning is noticed by the person who caused it. The template turns it on by default; the option exists so you can switch it off for one experiment, not for good.

Layer 3 — the engineer's depth

  • Some warnings need the optimiser. g++ at -O0 printed 3 warnings for bugs.cc with -Wall, and 4 at -O2; the extra one was 'count' may be used uninitialized [-Wmaybe-uninitialized], although -Q --help=warnings showed -Wuninitialized enabled in both cases. R3 R4 The GCC manual explains that these warnings depend on data-flow analysis done during optimisation. D1 Practical rule: build at least one CI configuration with optimisation and warnings on, as the template's Release build does.
  • Two compilers see different things. clang++ reported the uninitialised variable at -O0, and reported two -Wsign-conversion warnings (it includes them in -Wconversion) that g++ did not show for the same flags. R2 Building with both is one of the cheapest bug-finding steps you can add to CI.
  • Suppress narrowly, never globally. When a warning is truly a false alarm, prefer a code change that states your intent: static_cast<double>(xs.size()) (Listing 2, line 23) says "I know this converts". For an unused parameter, delete its name or mark it [[maybe_unused]]. Third-party headers can be included as system headers (CMake's target_include_directories(... SYSTEM ...) form, R8) so their warnings do not hide yours. Do not add -w or -Wno-... to a whole project. D1 R8
  • Warnings are version-dependent. A new compiler version can add warnings, so a project with -Werror can stop building after an upgrade (the "works on my machine" of F2-26 in another form). That is a feature: the new warnings are new reviews. Record the compiler version, and upgrade deliberately.
Not verified — check before relying on this

The descriptions of warning flags quoted here are the one-line help texts that g++ 13.3.0 printed (g++ --help=warnings, R4); the full explanations (which exact warnings -Wall and -Wextra enable in other versions, how -Wmaybe-uninitialized depends on optimisation, how Clang groups -Wconversion) belong in the GCC manual's "Warning Options" and the Clang manual's diagnostics reference for your installed versions. They were not opened in this build.

How the hardware actually does it

Warnings are produced entirely by the compiler, before any hardware runs your code. But several of the bugs in this chapter are about how values are stored in hardware. An int on this machine holds whole numbers only, so storing 2.5 into it keeps 2 (MA102). An uninitialised local variable is a slot in the function's stack frame that still holds bytes left by an earlier function call; that is the likely reason the third value in the run was a large, meaningless number. R5 D4 And if (x = 0) compiles to a store and a test of the stored value, which the processor executes faithfully: it does what was written, not what was meant.

Task. Triage the four warnings of the forensic build (Evidence 1 below) against the bug report "orders of 10 or more items never get the 10 % discount". For each, decide: could it explain the symptom?

  1. 14:42 unused parameter 'with_tax' [-Wunused-parameter]. A parameter nobody uses cannot change the discount. Harmless for this bug (but worth removing). R7

Where the analogy breaks


    

  • The translator never fixes anything. A human translator might quietly correct an obvious slip. The compiler never does: it translates exactly what you wrote, even if (x = 0), and only notes its doubt.
    • 

  • Silence is not approval. A recipe without margin notes from a good translator is probably fine. A program with zero warnings can still be badly wrong: in Figure 1, g++ with -Wall -Wextra said nothing about three of the five bugs. R1 Warnings are one check among several (sanitizers in F2-29, tests in F2-30).
    • 

  • Two translators, two sets of notes. Real kitchens have one translator; you can (and should) ask two compilers, and they disagree about what is worth noting (R2).
    • 




Common mistakes and debugging


    

  • Symptom: a build log with dozens of warnings that "have always been there". Cause: no -Werror, so warnings accumulated and nobody reads them. How to find it: count them: grep -c warning: build.log. Fix: fix them one flag at a time, then turn on -Werror so the count stays at zero.
    • 

  • Symptom: a warning disappears after adding a cast, but the result is still wrong. Cause: the cast silenced the message without fixing the logic (for example static_cast<int>(x) where a double was needed). Fix: ask what the warning was about; change the type, not the message.
    • 

  • Symptom: Debug build clean, Release build fails with -Werror. Cause: warnings such as -Wmaybe-uninitialized appear only with optimisation (R3). Fix: fix the code; the Release build found a real problem.
    • 

  • Symptom: after a compiler upgrade, new warnings stop the build. Cause: new versions add or extend warnings. Fix: fix them, record the new version; do not pin an old compiler to avoid them.
    • 

  • Symptom: warnings from a library's headers flood your build. Cause: the library is included as a normal include folder. Fix: include it as a system include folder (R8), keep your own code at full warning level.
    •
