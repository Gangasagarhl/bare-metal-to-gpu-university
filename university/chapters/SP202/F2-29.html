Story hook

Every dish this week has come out fine. But once in a while, on busy nights, a customer finds something strange on the plate. Nobody can reproduce it at a quiet lunch. The head chef decides on a practice service with an inspector standing beside every cook. The inspector does not taste the food. She watches hands: every reach into a container, every pour, every jar that is thrown away and then, oddly, picked up again.

On the second practice dish she stops the kitchen. "That cook reached into a pan that was washed and put away two minutes ago." The dish would have looked fine. The mistake was real anyway.

Sanitizers are that inspector, built into your program by the compiler. They make the program slower and bigger, so you do not ship them. But in development and tests, they catch memory mistakes and undefined behaviour at the moment they happen, even when the output looks right.

What you will be able to do

  • Build a program with AddressSanitizer, UndefinedBehaviorSanitizer and LeakSanitizer, and with Valgrind's Memcheck as a second opinion.
  • Read a sanitizer report: the kind of error, the access, where it happened, and where the memory was allocated and freed.
  • Explain how shadow memory and redzones let AddressSanitizer catch an out-of-bounds read.
  • Recognise what each tool cannot see (for example, reads inside a vector's spare capacity).
  • Diagnose a heap-use-after-free caused by keeping a reference into a vector that grows.
Jargon box
Sanitizer
Simple words: a checker the compiler builds into your program, so the program reports its own mistakes while it runs. Analogy: the food-safety inspector at a practice service. Precise: a compiler instrumentation mode, enabled with -fsanitize=<name> in GCC and Clang, with a runtime library that checks operations and prints a report. D1 D2
Instrumentation
Simple words: extra checking code that the compiler adds around your own code. Analogy: the inspector's checklist stapled to every recipe step. Precise: compiler-inserted code (for example, a check before every memory load and store) that calls into a runtime library; it changes the program's size and speed but not its intended behaviour. D1
AddressSanitizer (ASan)
Simple words: the sanitizer for memory mistakes: reading outside an array, using freed memory. Analogy: the inspector watching every reach into a container. Precise: see the glossary entry from SP101; -fsanitize=address. D3
Shadow memory
Simple words: a separate, smaller area of memory where ASan writes down which bytes of your memory you are allowed to touch. Analogy: a floor plan with every shelf marked "in use" or "off limits". Precise: in ASan, one shadow byte describes 8 application bytes: 00 means all 8 are addressable, 01–07 that only the first 1–7 are, and other values mark kinds of forbidden memory such as heap redzones (fa) and freed memory (fd). R2 D3
Redzone
Simple words: a small forbidden gap that ASan puts around each block of memory. Analogy: a strip of red tape on the counter around each tray: touching it is a violation. Precise: poisoned bytes placed by ASan's allocator before and after each allocation, so that an access right past the end lands in poisoned memory (legend: "Heap left redzone: fa"). R2
Heap-use-after-free
Simple words: using memory after it has been given back. Analogy: reaching into a pan that was already washed and put away. Precise: a read or write through a pointer or reference to a heap block that has been deallocated; undefined behaviour; ASan reports it with the stacks of the access, the free and the allocation. R9 D5
Iterator invalidation
Simple words: when a container changes, pointers, references and iterators to its elements can stop being valid. Analogy: the restaurant moves the spice rack to a bigger shelf; your note "third jar from the left on the old shelf" now points at nothing. Precise: rules in the C++ standard library that say which operations invalidate which references; for std::vector, an insertion that exceeds the capacity reallocates storage and invalidates all of them. D5 R9
UndefinedBehaviorSanitizer (UBSan)
Simple words: the sanitizer that reports operations the C++ rules leave undefined, such as signed overflow or too-large shifts. Analogy: the inspector who knows the rule book, not only the containers. Precise: -fsanitize=undefined; it prints "runtime error:" with file, line and column and, by default, continues; -fno-sanitize-recover=all makes the first report stop the program. R4 D1
Memory leak
Simple words: memory that the program took and never gave back, and can no longer reach. Analogy: trays carried into the storeroom and forgotten there every night. Precise: heap blocks still allocated at exit with no pointer to them from the program's live data; ASan's LeakSanitizer reports them at exit as "direct" or "indirect" leaks. R5 D2
Memcheck (Valgrind)
Simple words: a tool that runs an unchanged program inside a simulator that checks every memory access. Analogy: inspecting through a camera instead of standing in the kitchen: no change to the cooks, but everything slower. Precise: Valgrind's default tool, "a memory error detector" (its banner); it needs no recompilation, but runs the program on a synthetic CPU. R3 D4

The idea in pictures

Figure 1 explains the most important line of the first ASan report in this chapter. The vector holds five ints, 20 bytes. ASan's shadow memory says, 8 bytes at a time, what may be touched. The read of readings[5] lands at byte 20, the first byte that is not part of the vector's block.

Layer 1 — the kid explanation

Some bugs do not crash and do not print anything wrong, at least not today. A program might read one number past the end of a list, and by luck that spot holds a zero. The answer looks right. Tomorrow, on another computer, it may not.

A sanitizer is a guard the compiler adds to your program. Before every reach into memory, the guard checks a map: is this spot really yours? If not, the program stops at once and prints a report: what went wrong, on which line, and where that memory came from.

The guard makes the program slower, so you use it while you build and test, not in the final product. It is like practising with an inspector watching, so that the real service goes well.

Layer 2 — the student explanation

The bug that printed the right answer

overflow.cc (Listing 1) has a loop condition i <= readings.size(), so it reads readings[5], one past the end. Built normally, it printed sum = 150: the correct sum of the five readings. R1 The extra read happened to find a 0. This is undefined behaviour (F2-23): the result is right by luck, and no test that only checks output would catch it.

Built with -fsanitize=address, the same program stopped with ERROR: AddressSanitizer: heap-buffer-overflow and exit code 1. R2

Reading an ASan report

Read the report in four blocks, top to bottom: R2

  1. What: heap-buffer-overflow, then READ of size 4: one int was read where it should not be.
  2. Where: a stack trace; the first frame in your code is sum_readings ... overflow.cc:9, called from main ... overflow.cc:17.
  3. Whose memory: "0 bytes after 20-byte region", "allocated by thread T0 here", with a stack ending in main ... overflow.cc:16: the vector created on line 16.
  4. The map: the shadow bytes and their legend (Figure 1). You rarely need it, but it explains the verdict.

The SUMMARY: line repeats the kind and the first location. For a use-after-free, the report adds a third stack, "freed by thread T0 here", which is often the most useful one (the forensic lab).

Undefined behaviour

ub.cc (Listing 2) computes 13! in an int and shifts a 32-bit value by 32. Built normally it printed 13! = 1932053504 (13! is 6,227,020,800, which does not fit in 32 bits) and mask(32) = 4294967295. R4 With -fsanitize=undefined it printed two reports, signed integer overflow: 479001600 * 13 cannot be represented in type 'int' at ub.cc:8:16 and shift exponent 32 is too large for 32-bit type 'unsigned int' at ub.cc:15:16, then kept running and exited with code 0. Note that mask(32) printed 0 in that build, not 4294967295: undefined behaviour can give different results in different builds. With -fno-sanitize-recover=all, the first report stopped the program with exit code 1. R4 Use that form in tests, so a report fails the test.

Leaks

leak.cc (Listing 3) links two shared_ptr objects in a cycle: each keeps the other's count above zero, so neither is ever destroyed. The program printed its message, then LeakSanitizer (part of ASan on Linux in this build) reported two "Indirect leak of 64 byte(s)" with the allocation lines 14 and 15, "128 byte(s) leaked in 2 allocation(s)", and exit code 1. R5 The fix is a non-owning std::weak_ptr for the back link (Listing 5); fixed.cpp was built by the lab runner with -fsanitize=address,undefined and ran clean. R11

Layer 3 — the engineer's depth

  • How ASan works. The compiler inserts a check before each memory access: compute the shadow address of the target, load the shadow byte, and report if it forbids the access. The runtime replaces malloc/new and free/delete so that each block gets redzones, and freed blocks are kept poisoned for a while ("quarantine") so use-after-free lands on fd bytes. D3 The lab shows the visible effects: operator new from asan_new_delete.cpp in every allocation stack, and the shadow legend. R2
  • What ASan cannot see by default. reserve.cc reserves 8 ints, pushes 5 and reads v[6]. That is past size() but inside memory the vector owns. Plain ASan was silent and the program printed v[6] = -1094795586. R6 With libstdc++'s annotation macro -D_GLIBCXX_SANITIZE_VECTOR, the vector tells ASan which part of its capacity is in use, and ASan reported container-overflow at reserve.cc:12, "24 bytes inside of 32-byte region". R6 Lesson: a silent sanitizer is evidence, not proof. Unit tests (F2-30) and .at() or a debug-mode library cover other cases.
  • Memcheck as second opinion. Valgrind found the same overflow in the unmodified binary, "Invalid read of size 4 ... 0 bytes after a block of size 20 alloc'd", but the program still ran to the end, printed sum = 150 and exited with code 0; only "ERROR SUMMARY: 1 errors" shows it. R3 In CI, use its option that makes errors change the exit code (check valgrind --help for --error-exitcode). Memcheck is useful when you cannot recompile, for example a library you only have as a binary.
  • Reproducible stacks. Add -fno-omit-frame-pointer and -g, and avoid high optimisation in sanitizer builds; in this build the "freed by" stack of the forensic case was incomplete until -fno-omit-frame-pointer was added (recorded in SP202 NOTES.md). R9 D1

How the hardware actually does it

Why did the unsanitized overflow read not crash? The processor checks memory permissions per page through the memory management unit, and pages are 4 KiB on this kind of machine; the heap block of 20 bytes sits inside a mapped page together with other data. D6 Reading 4 bytes past it is a legal access as far as the hardware is concerned, so there is no fault, only a wrong (here, lucky) value. A segmentation fault happens only when an access reaches an unmapped page, as with the null-pointer read at address 0x20 in F2-28. That gap between "bad for the program" and "bad for the hardware" is exactly what sanitizers fill in, with a byte-level map maintained in software. In the forensic case, the busy-day run did crash (exit status 139) while the quiet day did not: why it crashed instead of printing garbage depends on how the allocator reused the freed block, which this build did not investigate. R8

Worked example

Task. From the UBSan line ub.cc:8:16: runtime error: signed integer overflow: 479001600 * 13 cannot be represented in type 'int', check the numbers and explain the printed value 1932053504. R4

  1. 12! = 479,001,600, so the failing step is result *= 13 with k = 13. This matches the report.
  2. The true product is 479,001,600 × 13 = 6,227,020,800.
  3. The largest 32-bit signed int is 2,147,483,647 (MA102), so the product does not fit: undefined behaviour.
  4. What the machine did in this build: it kept the low 32 bits. 6,227,020,800 − 232 = 6,227,020,800 − 4,294,967,296 = 1,932,053,504. That is the printed value.
  5. Fix: use a 64-bit type (std::int64_t, Listing 5): 13! = 6227020800. R11

Step 4 explains this run; it is not a promise. The compiler may assume that signed overflow never happens and transform the code on that basis (F2-23).

Where the analogy breaks


    

  • The inspector changes the kitchen. A real inspector only watches. A sanitizer changes the program: different memory layout, extra code, slower. A bug that depends on layout or timing can appear or disappear under it (compare mask(32): 4294967295 plain, 0 with UBSan, R4).
    • 

  • She only sees what is cooked today. A sanitizer checks the paths your run actually takes. A bug on a path no test runs is invisible, like the busy-day path of the forensic lab when only quiet days are tested (R8).
    • 

  • Some rooms have no inspector. Memory inside a vector's spare capacity is "the vector's own" to ASan unless the library annotates it (R6).
    • 




Common mistakes and debugging


    

  • Symptom: the sanitizer build passes; the release build crashes. Cause: the failing input or path was not exercised under the sanitizer. Fix: run the same tests, with the same inputs, in the sanitizer configuration; add the failing input as a test.
    • 

  • Symptom: UBSan prints errors but the test still passes. Cause: UBSan recovers by default (R4). Fix: -fno-sanitize-recover=all.
    • 

  • Symptom: the report's stacks stop after one or two frames. Cause: frame pointers omitted. Fix: -fno-omit-frame-pointer -g.
    • 

  • Symptom: a link error mentioning sanitizer symbols. Cause: -fsanitize=... was given when compiling but not when linking. Fix: pass it to both (the template's uni_flags adds it to compile and link options; F2-26).
    • 

  • Symptom: "incompatible" error. Cause: ASan and TSan in one build (R7). Fix: separate CI configurations.
    •

Summary


    

  • Sanitizers are compiler-added checks: ASan for memory, UBSan for undefined behaviour, LeakSanitizer for leaks, TSan for data races.
    • 

  • A correct-looking output can hide an out-of-bounds read; ASan stops at it (R1, R2).
    • 

  • Read reports top-down: kind, access, your first frame, allocation and free stacks.
    • 

  • ASan's shadow memory marks every 8 bytes as usable, partly usable or forbidden.
    • 

  • Use -fno-sanitize-recover=all, -g and -fno-omit-frame-pointer in test builds.
    • 

  • A silent sanitizer is not proof: it sees only executed paths and memory it knows about.
    •

Forensic lab answer key


Observation. heap-use-after-free, READ of size 4 at menu.cc:24 (the printf of special; 4 bytes is the int price_cents, "32 bytes inside of 40-byte region"). Freed by std::vector<Dish>::_M_realloc_insert ← push_back ← main at menu.cc:21; allocated by the same path from line 16. R9


Hypotheses. (1) The extra dishes overwrite the first dish. (2) Long names overflow a buffer. (3) The reference special becomes invalid when the vector grows. (4) A printing bug with many lines. Evidence: the quiet day is fine (R8); ASan says the memory was freed during a push_back, which rules out (1), (2) and (4) and supports (3).


Root cause. special (line 17) is a reference to the first element inside the vector's storage. When a push_back needs more capacity than the vector has, the vector allocates a bigger block, moves the elements, and frees the old block (_M_realloc_insert → _M_deallocate in the "freed by" stack). The reference still points into the freed block: iterator invalidation. On the quiet day no push_back happens after line 17, so nothing is freed.


Fix. (a) Copy the dish: const Dish special = menu.front(); (Listing menu_fixed.cpp, verified for 0 and 8 extra dishes under ASan and UBSan, R10). (b) Read menu.front() after the vector stops growing, or store an index instead of a reference.
