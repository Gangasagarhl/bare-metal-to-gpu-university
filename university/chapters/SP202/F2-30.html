Story hook

A new dish has four parts: a sauce, a purée, a crisp, and the fish. If the head chef only tastes the finished plate, and it is wrong, she has to guess which part failed. So the kitchen tastes each part on its own, before plating: the sauce for salt, the purée for texture, the crisp for crunch. Each tasting takes seconds, and when one fails, everyone knows exactly where to look.

There is a second rule in good kitchens: every tasting starts from a clean spoon. If you taste the sauce with the spoon you used a moment ago for the purée, the sauce will seem wrong when it is fine.

Unit tests are those tastings for code. This chapter builds them with the university's tiny harness, uses them to drive a design, measures what they reach, and shows what happens when they share a spoon.

What you will be able to do

  • Write unit tests with the university harness uni_test.h and run them through CTest.
  • Choose test cases: typical values, boundaries, invalid inputs.
  • Use the red–green–refactor cycle of test-driven development.
  • Measure line coverage with gcov and explain why 100 % coverage does not mean "no bugs".
  • Combine tests with sanitizers so a hidden bug fails the run.
  • Diagnose a test that fails in the full run but passes alone.
Jargon box
Unit test
Simple words: a small program that checks one piece of your code on its own. Analogy: tasting the sauce before it goes on the plate. Precise: see the glossary entry from SP101; in this course, a function registered with UNI_TEST. R2
Test case
Simple words: one situation you check: an input and the result you expect. Analogy: "the sauce, tasted for salt". Precise: a named check or group of checks with given inputs and expected outputs; in uni_test.h, one UNI_TEST function containing one or more CHECKs. R2 D1
Test harness
Simple words: the small framework that finds your tests, runs them and reports the result. Analogy: the tasting station with clean spoons and a checklist. Precise: code that registers test cases, runs them (optionally filtered), reports pass or fail per case, and returns an exit code; uni_test.h is 82 lines and returns 0 only if at least one test ran and none failed. R1
Test-driven development (TDD)
Simple words: writing a failing test first, then the code that makes it pass, then tidying up. Analogy: deciding how the sauce must taste before you cook it. Precise: a practice of short cycles "red" (a new test fails), "green" (the simplest code that passes), "refactor" (improve the code with tests still passing). D1 R3
Regression test
Simple words: a test added after a bug, so the same bug can never come back unnoticed. Analogy: after a customer found a bone, "check for bones" is added to every tasting. Precise: a test that reproduces a fixed defect and is kept in the suite to detect its reintroduction (a "regression"). D1
Code coverage
Simple words: how much of your code the tests actually ran. Analogy: which pots the tasting spoon has been in at least once. Precise: a measurement by an instrumented build; line coverage is the share of executable lines run at least once; GCC's --coverage and gcov report "Lines executed: …% of N". R5 D2
Test isolation
Simple words: each test must work the same whether it runs alone, first, last or with others. Analogy: a clean spoon for every tasting. Precise: the property that no test depends on state left by another (global variables, files, environment); tests that break it pass or fail depending on order. R7 R8

Layer 1 — the kid explanation

A unit test is a tiny program that asks one question about your code and checks the answer. "If I give parse_duration the text 45s, do I get 45?" If yes, the test passes. If not, it fails and says which line.

You write many small tests, each about one thing: normal inputs, inputs at the edges, and silly inputs that must be refused. Then you run them all, every time you change anything. It takes a second. If one fails, you know at once what you broke.

Good tests are like fair judges. Each one judges by itself. A test that only passes when another test ran first is a judge who was told the answer by someone else.

Layer 2 — the student explanation

The harness

Professional projects use frameworks such as GoogleTest or Catch2 D3; this course uses an 82-line header, uni_test.h (Listing 1), so that nothing is hidden. It is byte for byte the file in the template's tests/ folder. R1 It does four things:

  • UNI_TEST(name) defines a function and registers it in a list, using a static object whose constructor runs before main (lines 75–78).
  • CHECK(expr) evaluates a condition; if it is false, it prints file:line: CHECK failed: expr, counts the failure and continues, so one run shows every failed check (lines 36–42, 80).
  • run_all runs every registered test whose name contains the first command-line argument (the filter), printing [ RUN ] and [ OK ] or [ FAIL ] (lines 50–71).
  • It returns 0 only if at least one test ran and none failed (line 70), so CTest and CI can rely on the exit code.

Choosing test cases

The function under test is parse_duration (Listing 2): it turns "1h30m" into 5400 seconds, and refuses anything that breaks its rules. The tests in Listing 3 are grouped in four cases: R2

  • Typical values, one per unit (single_units) and combined (combined_units).
  • Boundaries: zero ("0s") and a large value in one unit ("90m").
  • Invalid inputs, one per rule: empty text, a number without unit, a unit without number, an unknown unit, a repeated unit, the wrong order, a sign. Each comment says which rule the check covers.

A useful habit: read the function's specification (the comment at the top of duration.h) and write at least one check per sentence. The full run passed all four cases with exit code 0, under the lab runner's ASan and UBSan build. R2

Red, green, refactor

The first version, duration_v1.h, accepted one number and one unit. The combined_units tests were written before combining was implemented. Run against v1, they failed: three CHECK failed lines (test file lines 14, 15 and 16), [ FAIL ] combined_units, 4 test(s) run, 1 failed, exit code 1. R3 That is the red step, and it is useful evidence: it proves the tests can fail. A test you have never seen fail may not be testing anything. Then duration.h was written until all four cases passed (green); refactoring would follow with the tests as a safety net. D1

Running tests: filter, CTest, CI

The filter runs a subset: ./test_duration invalid ran only invalid_inputs, "1 test(s) run, 0 failed". R4 In the template, add_test registers the test program with CTest, and ctest --output-on-failure runs it and reports "100% tests passed"; ci.sh runs CTest in a debug-asan and a release configuration (F2-26). R10 Remember the trap from F2-26: without enable_testing(), CTest found no tests and still exited 0.

Layer 3 — the engineer's depth

  • Coverage: a floor, not a ceiling. Built with --coverage, the four test cases executed every line of duration.h: gcov reported "Lines executed:100.00% of 28", and no line was marked unexecuted. R5 Yet a probe with the input "99999999999999999999s", built with UBSan, reported duration.h:22:29: runtime error: signed integer overflow: 999999999999999999 * 10 cannot be represented in type 'long int', and the function returned a value instead of refusing. R6 Every line was run; not every value was. Coverage tells you what is certainly untested (lines with 0 executions); it cannot tell you what is tested well.
  • Tests plus sanitizers. The overflow above produced no wrong-looking output; only UBSan saw it. That is why the template runs its tests in a sanitizer configuration, and why the lab runner builds every lab program with -fsanitize=address,undefined (F2-29). The fix (a limit check before multiplying) and its regression test are the lab's step 4.
  • Isolation and order. Static registration runs tests in the order they appear in the file, every time. That makes order-dependence reproducible but also hidden: if a test leaks state into a later one, the suite fails the same way each run, and the failure is blamed on the innocent later test. The forensic lab is that case. R7 Larger frameworks offer options to shuffle the order to expose this (check the documentation of the framework you use). D3
  • What a unit is. A unit is a piece small enough to test without its surroundings: a function or a class, with no network, disk or clock. Code that reads files or the time is easier to test if those are passed in (a string instead of a file, a time value instead of reading the clock), which is also better design.

How the hardware actually does it

A test result travels as a number: the value main returns. On Linux, the process exit status is passed from the program's exit system call to the parent process (the shell, CTest), which waits for the child and reads its status (F0-36 introduced the exit code). D4 CTest's verdict "Passed" or "Failed" comes from that number unless a property such as PASS_REGULAR_EXPRESSION says otherwise (F2-26, R10). Coverage needs help from the compiler: --coverage adds counters to the program, increments them as code runs, and writes them to .gcda files at exit, which gcov reads. D2 R5 Like sanitizers, coverage is instrumentation: the measured program is not the same machine code as the shipped one.

Worked example

Task. Design tests for a new rule: "a duration may have an optional d (days) unit before h". Write the cases before the code.

  1. Typical: "1d" → 86400 (24 × 3600). "1d2h" → 86400 + 7200 = 93600.
  2. Boundary: "0d" → 0. "1d0h0m0s" → 86400.
  3. Invalid: "2h1d" (wrong order) → no value. "1d1d" (repeated) → no value.
  4. Existing behaviour unchanged: keep every existing test; they now protect against breaking the old rules.
  5. Red: run the tests against the current duration.h. Predict: the four valid-d checks fail (unknown unit gives no value), and the two invalid ones already pass. Write the code until all pass.

The arithmetic is done here by hand (86400 = 24 × 3600); the lab asks you to run it.

Where the analogy breaks


    

  • Tasting is about the actual food; a test is about chosen inputs. Tasting the sauce checks this batch. A unit test checks the function on the inputs you thought of, and says nothing about others (R6).
    • 

  • A test can be wrong. A taster with a cold still tastes something. A test with a wrong expected value passes wrong code or fails right code; that is why each test should be seen failing once (the red step).
    • 

  • Tests are code you keep. Tastings vanish after service. Tests stay in the repository, run thousands of times, and need the same care as the code they test.
    • 




Common mistakes and debugging


    

  • Symptom: a new test passes the first time you run it, before you wrote the code. Cause: it tests nothing, or the feature already existed. Fix: make it fail on purpose (change the expected value) to prove it can.
    • 

  • Symptom: one failed check stops the rest of the test. Cause: using assert or abort instead of a recording check. Fix: use CHECK, which continues (Listing 1, lines 36–42).
    • 

  • Symptom: the suite passes locally and fails in CI, or the other way round. Cause: tests depend on order, time, files or environment. How to find it: run each test alone with the filter, then in the full run, and compare (the forensic lab).
    • 

  • Symptom: 100 % coverage but bugs found later. Cause: coverage measures lines run, not values tried (R5, R6). Fix: add boundary and invalid inputs, run tests under sanitizers.
    • 

  • Symptom: floating-point checks fail by tiny amounts. Cause: comparing with ==. Fix: CHECK_NEAR(a, b, tolerance) with a tolerance you can justify.
    •

Forensic lab answer key


Observation. price_with_default_vat fails at order.cc:29: price_with_vat(1000) == 1200. It runs second, after price_with_reduced_vat. Alone it passes. R7 R8


Hypotheses. (1) Random flakiness (timing, uninitialised memory). (2) Order dependence through shared state. (3) A different build in CI. Evidence: the harness always runs tests in file order, so the full run is deterministic; the failure is the same each time in CI; the build is the same binary in both evidence runs. (2) remains.


Root cause. price_with_reduced_vat sets the single shared settings().vat_percent to 10 and never restores it. The next test computes 1000 + 1000 × 10 / 100 = 1100, not 1200. Alone, the setting still has its initial value 20.


Fix. Restore shared state at the end of the test that changes it, even if a check fails: the RAII guard in order_fixed.cpp saves the settings in its constructor and restores them in its destructor. Verified: all three tests pass in the full run, under ASan and UBSan. R9 Also run the single test again.


Prevention. Rule: a test leaves no trace (test isolation). Design: pass the VAT rate (or a Settings object) into price_with_vat instead of reading a global, so tests cannot interfere. "Re-run until green" is never a fix: here it would never turn green, and with real flakiness it hides the problem.


Wrong answers and why. "Reorder the tests so the default-VAT test runs first": the bug stays and returns with the next new test. "Make the expected value 1100": the test then asserts the wrong price.
