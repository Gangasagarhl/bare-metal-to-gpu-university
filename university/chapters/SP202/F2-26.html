Story hook

Every morning before lunch service, the kitchen of a busy restaurant runs on a prep plan pinned to the wall. It says which dishes need which components: the soup needs stock and chopped onions, the stock needs bones and water, the salad needs washed leaves. Lina, the sous-chef, does not start from zero every day. She checks what is already in the fridge and still fresh, and only prepares what is missing or has changed. When the supplier delivers new tomatoes, she remakes the tomato sauce and every dish that uses it, and nothing else.

One day a new cook, Kofi, joins. Lina does not explain the kitchen by talking for an hour. She hands him the prep plan. Kofi follows it and, by eleven o'clock, his station looks exactly like hers. The plan is written down, so it works the same for everyone.

A C++ project with ten files is a small kitchen. A project with a thousand files, three compilers and two kinds of build (one for debugging, one for speed) is a big one. This chapter is about the written prep plan of a C++ project: the build system, and the one this university uses, CMake. By the end you will have built the university template repository, the starting point of every later C++ lab.

What you will be able to do

  • Explain what a build system does that a single compiler command does not: dependencies, incremental rebuilds and repeatable settings.
  • Write a CMakeLists.txt with a library, an executable, a test program, include directories, a language standard and build options.
  • Run the three CMake steps (configure, build, test) out of source, and read what each one prints.
  • Predict which files are recompiled after a change, and check the prediction against the build output.
  • Diagnose a "works on my machine" failure from two build logs by comparing compiler versions and flags, one variable at a time.
  • Set up the university template repository with its CI script and tests (the course lab).
Jargon box
Build system
Simple words: a program that knows how all the files of a project fit together and runs the right compiler commands, in the right order, only when needed. Analogy: the kitchen's prep plan on the wall. Precise: a tool that reads a description of build targets, their sources and their dependencies, and executes the commands that bring outdated outputs up to date (here CMake generating Makefiles for GNU Make). D1 D3
CMake
Simple words: a tool that reads your project description and writes the detailed build instructions for another tool. Analogy: the person who turns the menu into a prep plan for this particular kitchen. Precise: a build-system generator: it reads CMakeLists.txt, detects the compiler (configure step), writes native build files for a chosen generator (generate step) and can drive the build and the tests; version 3.28.3 in this build. D1 R1
Target
Simple words: one thing the build makes, such as a program or a library. Analogy: one dish or one component on the prep plan. Precise: a named build product created by add_executable or add_library, with its own sources and its own properties (include directories, compile options, linked libraries). D1 R7
Generator (CMake)
Simple words: the kind of build instructions CMake writes. Analogy: writing the prep plan in the language of this kitchen's staff. Precise: the back end that CMake writes files for; in this build the default "Unix Makefiles" generator, whose build ran /usr/bin/gmake. D1 R9
Build type
Simple words: a named set of compiler settings, such as one for debugging and one for speed. Analogy: a practice service (slow, everything checked) versus the real dinner service. Precise: the value of CMAKE_BUILD_TYPE on single-configuration generators, with typical values Debug, Release, RelWithDebInfo and MinSizeRel; in this build Debug added -g and Release added -O3 -DNDEBUG. R7 R4 R9
Out-of-source build
Simple words: putting everything the build makes in a separate folder, so your source folder stays clean. Analogy: preparing on a separate counter, not on top of the recipe book. Precise: a build tree (here build/, chosen with -B) separate from the source tree (chosen with -S); several build trees with different settings can share one source tree. D1 R6
Incremental build
Simple words: rebuilding only what changed and what depends on it. Analogy: remaking the tomato sauce and the dishes that use it, nothing else. Precise: a build in which each output is regenerated only if one of its recorded inputs is newer than it; in this build, touching src/stats.cpp recompiled that one file and relinked the library and both programs. D3 R3
Compilation database
Simple words: a file listing the exact compiler command used for every source file. Analogy: a photocopy of every instruction given to every cook. Precise: compile_commands.json, written by CMake when CMAKE_EXPORT_COMPILE_COMMANDS is on; it contains "the exact compiler calls for all translation units of the project in machine-readable form". R7 R4
CTest
Simple words: CMake's test runner: it runs every test you listed and reports which passed. Analogy: the head chef's tasting round before service. Precise: the test driver shipped with CMake (ctest), which runs the tests declared with add_test after enable_testing() and reports pass or fail per test. R7 R5
Continuous integration (CI)
Simple words: building and testing every change automatically, the same way every time. Analogy: every dish checked by the same checklist before it leaves the kitchen, even on a busy night. Precise: the practice of running a scripted, repeatable build and test (here ci.sh: a Debug build with sanitizers and a Release build, each tested) on every change, on a machine other than the developer's. R6 D4

Layer 1 — the kid explanation

When a program has one file, you can build it with one compiler command, as you did in F2-01. When it has many files, you must remember which files to compile, in which order, with which settings, and how to link them. If you forget one, the program is built from a mix of old and new parts. That mix can fail in strange ways.

A build system is a written plan for this. You describe your project once: "this library is made from these files; this program uses that library; these are the tests". The build system then works out the commands. When you change one file, it remakes only what depends on that file. It is fast, and it never forgets a step.

The plan also makes your build the same for everyone. Your classmate, your teacher and the test computer all follow the same written plan. If the build works for you but not for them, the plan helps you find out why: you compare what the plan did on each machine.

Layer 2 — the student explanation

Targets and their properties

A CMake project is described in a file called CMakeLists.txt. Its central idea is the target: a library made with add_library, or a program made with add_executable. In the CMake 3.28.3 reference that the tool prints itself, add_library "Add[s] a library to the project using the specified source files", and add_executable does the same for an executable. R7 Each target carries its own properties: where its headers are (target_include_directories), which compiler options it needs (target_compile_options) and what it links against (target_link_libraries). D1 R7

Properties can travel. When stats_cli links stats, it also receives the include directory that stats declared as PUBLIC. The reference says libraries following PUBLIC "are linked to, and are made part of the link interface", those following PRIVATE "are linked to, but are not made part of the link interface", and those following INTERFACE are only passed on. R7 That is why the template can give every target the same warning flags with a single line each: the flags live on an interface library, uni_flags, which "does not compile sources and does not produce a library artifact on disk" but carries properties to whoever links it. R7

Configure, build, test

You run CMake in three steps (Figure 1). The configure step, cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug, read the project, identified the compiler as "GNU 13.3.0" and wrote the build files into build/. R1 The build step, cmake --build build, compiled three source files, made the static library libstats.a and linked two programs. R2 The test step, ctest --test-dir build, ran the two tests and printed "100% tests passed, 0 tests failed out of 2". R5

Keep the build folder separate from your sources (an out-of-source build). You can then have several build folders from one source tree, for example build/debug-asan and build/release, which is exactly what the template's ci.sh does. R6 Deleting a build folder is always safe; the next configure recreates it.

What gets rebuilt

Running the build a second time with no change printed only "Built target" lines: nothing was compiled. After touch src/stats.cpp (which changes only the file's modification time), the build recompiled stats.cpp, re-made libstats.a and relinked stats_cli and test_stats; main.cpp and test_stats.cpp were not recompiled. R3 Make decides this by comparing modification times of each output with its inputs. D3 The inputs include headers: the compile commands carry -MD -MT ... -MF ...d options, which ask the compiler to write a list of the headers each source file included, so that a change to stats.h rebuilds all three objects. R9 D2

Build types and options

The build type selects a set of flags. The CMake reference describes CMAKE_BUILD_TYPE as specifying "the build type on single-configuration generators", with typical values Debug, Release, RelWithDebInfo and MinSizeRel, and warns that the default "is often an empty string". R7 In this build, the Debug compile command contained -g, and the Release command contained -O3 -DNDEBUG. R4 R9 -DNDEBUG switches off assert (F2-08), so a Release build does not run your assertions: test both builds.

Your own switches are made with option(), which provides "a boolean option that the user can optionally select". R7 The template has two: UNI_WERROR (on by default: warnings stop the build, F2-27) and UNI_SANITIZE (off by default: AddressSanitizer and UndefinedBehaviorSanitizer, F2-29). You set them at configure time, for example -DUNI_SANITIZE=ON.

Layer 3 — the engineer's depth

  • Generators. CMake does not build anything itself. The "Unix Makefiles" generator wrote Makefiles, and cmake --build ran /usr/bin/gmake, as the verbose log shows ("Run Build Command(s): ... /usr/bin/gmake -f Makefile"). R9 Other generators (for example Ninja, also installed in the container but not used here) write other build files from the same CMakeLists.txt; multi-configuration generators keep several build types in one build folder and ignore CMAKE_BUILD_TYPE. R7 D1
  • The language standard as a requirement. CMAKE_CXX_STANDARD 20 with CMAKE_CXX_STANDARD_REQUIRED ON and CMAKE_CXX_EXTENSIONS OFF produced -std=c++20 on every compile command (not -std=gnu++20), so GNU-only language extensions are not silently accepted. R4 R7
  • Reproducibility. A build is reproducible when the same sources and the same recorded tools give the same result. The configure log names the compiler and its version; record it. In the forensic lab below, the only difference that mattered between two machines was the compiler version, and the configure log's first line showed it. R1 R9
  • Host and target builds. The curriculum's P1 milestone asks for "a build system with separate host and target configurations". D4 The template is the host half. The lab also compiles one freestanding file (no C or C++ library, no exceptions, no RTTI) and checks it with readelf: "Class: ELF64", "Machine: Advanced Micro Devices X86-64", and nm -u listed 0 undefined symbols, so the object needs nothing from the host C library. R8 The real target build uses a cross compiler and a linker script; that is F2-46 and F2-48 in SP301.
Not verified — check before relying on this

This chapter quotes only the parts of the CMake reference that cmake --help-command, --help-variable and --help-property printed in this build (CMake 3.28.3, run record cmake_help.log). Statements about other generators, multi-configuration builds, CMake presets and the exact default flags that CMake adds for each build type on other compilers were not checked; read the CMake documentation for your installed version ("cmake-generators", "cmake-buildsystem", "CMAKE_<LANG>_FLAGS_<CONFIG>") before relying on them. The "Unix Makefiles" and Release flags shown here are what this build produced, not a promise for other machines.

How the hardware actually does it

A build is a lot of separate programs run one after another or side by side: the compiler for each source file, then the archiver for the library, then the linker for each program (F2-01). Independent compiles can run on different CPU cores at the same time; ci.sh asks for two parallel jobs with --parallel 2. The build tool can do this safely only because the dependency graph (Figure 2) tells it which steps are independent. D3 R6 Deciding what is outdated needs only the file system's modification times, which the operating system stores with every file; no file contents are compared. D3 This build did not measure how long compiles take on this machine: the CMake logs report only the configure time (for example "Configuring done (0.3s)").

  4. You edit CMakeLists.txt. The next cmake --build first re-runs the configure step: the verbose log shows the check "cmake ... --check-build-system CMakeFiles/Makefile.cmake" at the start of every build. R9 What is rebuilt then depends on which flags changed.

Where the analogy breaks


    

  • A cook notices a missing step; Make does not. If a dependency is not recorded (for example a generated header that no rule mentions), the build happily links old and new parts together. The plan is only as good as what it lists. D3
    • 

  • Freshness is a timestamp, not a smell. Lina checks whether the sauce is still good. Make only compares modification times: a file copied with its old time, or a clock that jumps backwards, can make a changed file look up to date. When in doubt, delete the build folder. D3
    • 

  • CMake does not cook. In the kitchen, the person with the plan also cooks. CMake only writes the plan (the Makefiles); GNU Make runs it, and the compiler and linker do the work. R9
    • 




Common mistakes and debugging


    

  • Symptom: fatal error: uni/stats.h: No such file or directory in a new program. Cause: the target does not link stats, so it never receives the PUBLIC include folder. How to find it: look at its line in compile_commands.json: there is no -I.../include. Fix: target_link_libraries(new_target PRIVATE stats), not a hand-written -I.
    • 

  • Symptom: your change has no effect. Cause: you ran an old program from another build folder, or you edited a copy. How to find it: run the build and read whether your file appears in a "Building CXX object" line. Fix: one build folder per configuration, and run programs from it.
    • 

  • Symptom: a test passes although the program crashed or returned an error. Cause: a PASS_REGULAR_EXPRESSION test ignores the exit code (R7). Fix: make the program print its result only on success, or add a separate test that checks the exit status.
    • 

  • Symptom: CI is green, but your failing test never ran. Cause: add_test without enable_testing(). In this build, such a project printed "No tests were found!!!" and ctest still returned exit status 0, although its only test program returns 1 (R10, below). How to find it: read the test count in the CI log, not only the exit status. Fix: enable_testing() before add_test; make CI fail when the number of tests is zero.
    • 

  • Symptom: "works on my machine, fails in CI". Cause: a different compiler, standard library, build type or flag. How to find it: compare the first lines of both configure logs and the compile commands; change one difference at a time (forensic lab). Fix: make the code correct for both; record the tool versions.
    • 

  • Symptom: strange behaviour after moving the project folder or changing the compiler. Cause: the build folder caches the old configuration. Fix: delete the build folder and configure again.
    •

Summary


    

  • A build system turns a description of targets and dependencies into the right commands, and reruns only what is outdated.
    • 

  • CMake configures (detects the compiler, writes build files), builds (through a generator such as Make) and tests (through CTest).
    • 

  • Targets carry properties; PUBLIC and INTERFACE properties travel to targets that link them.
    • 

  • Build types select flags: here Debug added -g, Release -O3 -DNDEBUG.
    • 

  • Keep builds out of source; delete the build folder when in doubt.
    • 

  • The template's ci.sh builds and tests two configurations with one command.
    • 

  • "Works on my machine" is solved by comparing the logs and changing one variable at a time.

Forensic lab answer key


Observation. Evidence 1: "The CXX compiler identification is GNU 12.4.0", /usr/bin/g++-12 ... -g -std=c++20 -Wall -Wextra, build succeeds, program prints checksum("packer") = 3299101830. Evidence 2: "GNU 13.3.0", /usr/bin/g++-13 ... -Werror -O3 -DNDEBUG -std=c++20 -Wall -Wextra, and the first error: checksum.h:5:6: error: 'uint32_t' in namespace 'std' does not name a type; did you mean 'wint_t'?, followed by 'checksum' was not declared in this scope in main.cpp. Differences: compiler version (12.4.0 versus 13.3.0), build type (Debug versus Release: -g versus -O3 -DNDEBUG), and -Werror. R9


Hypotheses. (1) The newer compiler's headers differ. (2) The Release flags change what compiles. (3) -Werror turns a warning into an error. Hypothesis 3 is ruled out at once: the message says error:, not a warning promoted by -Werror (that would name a -W option in brackets).


Root cause, proven by experiment. With g++ 13 and Mei's Debug flags, the same error appears (wom_ci_debug); with g++ 12 and the CI's Release and -Werror flags, the build succeeds (wom_dev_release). R9 So the compiler version alone decides. The header uses std::uint32_t but includes only <string>; the type is declared in <cstdint>. With GCC 12's standard library, <string> happened to include it indirectly; with GCC 13's it did not, so the code was always relying on an accident. (Which header includes which other header is a detail of each library version, not a promise; check the release documentation of the GCC 13 standard library before quoting the exact change.) The second error is a follow-on error: the declaration failed, so checksum was never declared.


Fix and verification. Add #include <cstdint> to checksum.h (include what you use). The fixed header built and printed the same checksum with both compilers and the CI flags (wom_fixed). R9


Prevention. CI builds every change before it is merged; record the compiler version in the README and in the configure log; build with more than one compiler (both are cheap in CI); treat "works on my machine" as a hypothesis to test, not a conclusion.


Wrong answers and why. "Remove -Werror from CI": the failure is an error, not a warning, and wom_ci_debug fails without -Werror. "Pin CI to GCC 12": hides the missing include until the next upgrade. "The optimiser broke it": an optimisation level cannot make a type undeclared, and the isolating experiment shows Release flags work with g++ 12.
