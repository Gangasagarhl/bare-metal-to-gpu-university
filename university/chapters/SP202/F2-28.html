Story hook

A dish comes back from a customer: the sauce is wrong. The head chef tastes it and frowns. She could stand at the pass and guess what happened, or she could do something only a kitchen in a training school can do: replay the order and freeze the whole kitchen at any moment she chooses. "Stop when the sauce goes into the pan. What is in the pan? Show me the jar the cook used. Now go on, but stop again the moment anybody touches the salt."

A real restaurant cannot freeze time. A program can. A debugger is the tool that freezes your running program wherever you ask, shows you every value it holds, and lets it go on one step at a time. Engineers who learn it stop guessing and start looking.

What you will be able to do

  • Build a program with debug information and start it under GDB or LLDB.
  • Stop a program with a breakpoint on a function or a line, and with a watchpoint on a variable.
  • Inspect arguments and local variables, print expressions, and step with next, step and finish.
  • Read a backtrace after a crash and find the first frame that is your own code.
  • Explain why an optimised build is harder to debug.
  • Diagnose a crash that happens only on another machine, by reproducing it with that machine's input.
Jargon box
Debugger
Simple words: a program that runs your program and can pause it to show what is inside. Analogy: the head chef who can freeze the kitchen. Precise: see the glossary; GDB and LLDB are the two used here. D1 D2
Debug information
Simple words: extra data the compiler puts in the program so a debugger can show source lines and variable names instead of raw addresses. Analogy: labels on every pot and jar, saying which recipe step filled it. Precise: tables that map machine addresses to files and lines and describe variables and types, produced with -g; on Linux usually in the DWARF format. D3 R2
Breakpoint
Simple words: a place in the code where the debugger pauses the program. Analogy: "freeze the kitchen when the sauce goes in the pan". Precise: see the glossary; GDB: "Set breakpoint at specified location." R5
Watchpoint
Simple words: a pause that happens when a chosen variable changes, wherever in the code that is. Analogy: "freeze the moment anybody touches the salt". Precise: GDB: "Set a watchpoint for EXPRESSION." The debugger stops after a write that changes the value and prints the old and new values. R5 R2
Stepping
Simple words: letting the paused program run for exactly one more source line. Analogy: unfreeze the kitchen for one recipe step, then freeze again. Precise: GDB next ("Step program, proceeding through subroutine calls."), step ("Step program until it reaches a different source line.", entering called functions) and finish ("Execute until selected stack frame returns."). R5
Backtrace
Simple words: the list of function calls that led to where the program is now, newest first. Analogy: the chain of orders: the waiter asked the sauce cook, who asked the prep cook, who reached for the empty jar. Precise: GDB: "Print backtrace of all stack frames, or innermost COUNT frames." Frame #0 is the current function, each higher number is its caller. R5 R7
Signal (operating system)
Simple words: a message the operating system sends to a program, for example "you touched memory you may not use". Analogy: the fire alarm going off in the kitchen. Precise: an asynchronous notification to a process on POSIX systems; a program that reads an unmapped address receives SIGSEGV and, by default, is terminated. D4 R7
Segmentation fault
Simple words: the crash you get when a program uses a memory address it is not allowed to use. Analogy: reaching for a shelf that is not there. Precise: the termination caused by SIGSEGV; bash reported it as "Segmentation fault" and the exit status 139 in this build. R6 D4

Layer 1 — the kid explanation

When a program gives a wrong answer, you could add print statements and run it again and again. That works, but it is slow, and you have to guess where to look. A debugger is better: it runs your program and can stop it anywhere.

You tell it "stop when you reach this function", and it does. Now the program is frozen. You can ask: what is in this variable? How long is this list? Then you let it run one line, and look again. You can also say "stop whenever this variable changes", and the debugger catches the exact moment.

When a program crashes, a debugger shows you where it was and which functions called which to get there. That list is the backtrace. It is like footprints leading back from the accident to where it started.

Layer 2 — the student explanation

Build for debugging

Compile with -g (debug information) and -O0 (no optimisation) while you debug. D1 In the template, the Debug build type does this: CMake used -g for Debug (F2-26). Then start the debugger with the program: gdb ./streak or lldb ./streak. In the lab, the commands are kept in a file and run in batch mode (gdb -q -batch -x session.gdb ./streak), so the session is repeatable and its transcript is real. R2

A session, step by step

The program streak.cc (Listing 1) should report the longest run of rising temperatures. For the week 3 4 5 2 3 4 5 6 the answer is 4 (2→3→4→5→6), but it printed longest rise: 2. R1 Here is what the GDB session did, command by command (Listing 2, transcript below it): R2

  1. break longest_rise, run: the program stopped at line 9, the first line of the function. GDB showed the argument: "std::vector of length 8".
  2. info args printed all eight temperatures; the input is right, so the bug is in the function.
  3. watch best, continue: the first stop was best going from a meaningless value (-16568, it was not yet initialised) to 0 on line 9. The second stop was best changing from 0 to 2, with the program about to run line 18 (run = 0;) after the fall from 5 to 2.
  4. info locals at that moment: i = 3, best = 2, run = 2. So far, correct.
  5. No more change of best follows. To see the end, the watchpoint is deleted and a breakpoint set on line 21 (return best;). There, print run gave 4 and print best gave 2.

That is the bug, seen directly: the last rising run (4) is still in run when the loop ends, but best is updated only when a fall happens. The fix (Listing 3) compares after every step; it printed 4, and 0 for a falling list and an empty list. R9 The LLDB session did the same with LLDB's commands and found the same values (run = 4, best = 2 at line 21). R3

After a crash

When a program crashes under the debugger, it stops at the crash. backtrace then shows how it got there. The rule from Figure 1: read from the top down until you reach a file you wrote, select that frame with frame N, and look at its variables. In the forensic case, frame 3, info locals showed port = 0x0: a null pointer, dereferenced on line 40. R7

Layer 3 — the engineer's depth

  • Optimised code lies a little. The same program built with -g -O2 behaved differently in the debugger: a breakpoint on line 21 was accepted but never hit, and the first stop on line 13 showed i = 1, best = 0, run = 0 although ++run is the line being run. R4 The optimiser merges, moves and removes code, so source lines and variables no longer map one to one onto machine instructions. Debug at -O0 when you can; when a bug appears only at -O2, expect <optimized out> values and jumping line numbers, and read the assembly (F2-32). D1
  • Hardware watchpoints. GDB printed "Hardware watchpoint 2: best". R2 Watching a variable by single-stepping the program and comparing after each instruction would be very slow; processors provide a small number of debug registers that trap on a write to an address, and debuggers use them when they can. D5 Watchpoints on local variables end when the function returns.
  • Addresses before and after run. GDB placed breakpoint 1 "at 0x127a" before the program started, and breakpoint 3 "at 0x555555555300" after; LLDB reported the same function offset 0x127a. R2 R3 The program is position-independent: the operating system chose where to load it, and the debugger converts. Under a debugger on Linux, address randomisation is usually switched off so that addresses repeat between runs. D1
  • Batch scripts and core files. A session file (-x session.gdb, -s session.lldb) makes debugging repeatable and reviewable, which is how this chapter's transcripts were produced. When a program crashes on a machine you cannot reach, a core file (a snapshot of its memory at the crash) can be opened later with gdb program core; core files were not produced in this build. D1
Not verified — check before relying on this

The claims about how breakpoints and watchpoints are implemented (debug registers, the number available, trap instructions), about address randomisation being disabled by GDB by default, and about core files come from the titles of the GDB manual and the Intel architecture manual, which were not opened in this build. The lab only shows what GDB printed ("Hardware watchpoint", the two forms of the breakpoint address). The LLDB commands frame select, next, step and finish were not run.

How the hardware actually does it

A stopped program is a process that the operating system has paused; on Linux, the debugger controls it through a system interface that lets it read and write the paused program's memory and registers. D4 When the debugger prints a local variable, it reads the bytes at a known offset in the current stack frame, and the debug information tells it which offset and which type. That is why the uninitialised best printed as -16568 in GDB and -16520 in LLDB: the debugger faithfully decoded whatever bytes were left in that stack slot. R2 R3 The crash itself is a hardware event: the processor could not translate address 0x20 (a small offset from a null pointer, where port->value would live) to a mapped page, so it raised a fault, and the kernel turned that into the signal SIGSEGV. R7 D4

Worked example

Task. Without running anything, predict what the GDB watchpoint on best will report for the input 3 4 5 2 3 4 5 6, then compare with the transcript.

  1. Line 9 sets best = 0: one change, from whatever was in memory to 0.
  2. i = 1 (4 > 3): run = 1. i = 2 (5 > 4): run = 2. No change to best.
  3. i = 3 (2 < 5): the else branch. run (2) > best (0), so best = 2: second change. Then run = 0.
  4. i = 4 to 7: all rises, run goes 1, 2, 3, 4. No fall, so best never changes again.
  5. Loop ends; return best returns 2, while run holds 4.

Compare. The transcript shows exactly two watchpoint stops (garbage→0, 0→2 with i = 3), and at line 21 run = 4, best = 2. R2 When a prediction and a debugger disagree, the debugger is right about what happened, and your mental model needs fixing.

Where the analogy breaks


    

  • Freezing changes nothing. A frozen kitchen would spoil the food. A paused single-threaded program loses nothing: it continues exactly as if it had never stopped. (With several threads or real hardware timers this is no longer true; that is F1-30's territory.)
    • 

  • The debugger can change the food. A debugger can also write variables and call functions in the stopped program. The head chef only inspects; the debugger can alter the evidence. Use that power carefully.
    • 

  • Labels can be missing. In a kitchen, the jars are there whether labelled or not. Without -g, the debugger still stops the program, but shows addresses instead of names, and an optimised build has "labels" that are partly wrong (R4).
    • 




Common mistakes and debugging


    

  • Symptom: "No symbol table is loaded" or no line numbers. Cause: built without -g. Fix: rebuild with -g (CMake: -DCMAKE_BUILD_TYPE=Debug).
    • 

  • Symptom: a breakpoint never hits, or values show as <optimized out>. Cause: optimised build (R4). Fix: rebuild at -O0, or use -Og (an optimisation level aimed at debugging; check your compiler's manual) D1.
    • 

  • Symptom: stepping disappears into library headers (basic_string.h). Cause: step enters every call, including the standard library. Fix: use next to go over calls, and finish to get out of one.
    • 

  • Symptom: after a crash the backtrace starts in code you did not write. Cause: the crash happened in a library called with bad data. Fix: walk down the frames to your first one (Figure 1); the bad data came from there.
    • 

  • Symptom: "it works under the debugger". Cause: the input, environment or timing differs. Fix: give the debugger exactly the failing input (run < config_new.in, R7), and suspect uninitialised memory or data races (F2-29).
    • 




Transition box

Where you came from: F2-27 used the compiler to find bugs before the program runs; F1-31 read assembly, including function calls and their stack frames. What carries over: reading a diagnostic location (file:line), and the stack frame picture, which is now something you can look at in a real program. R7 What changes: you now inspect a running program instead of reading source and guessing; the evidence is the program's real state, and an optimised build makes that evidence harder to read. R4 What comes next: F2-29 adds sanitizers, which watch every memory access for you and stop at the first bad one, even when there is no crash.

Troubleshooting.


    

  • GDB says "ptrace: Operation not permitted" → the system restricts debuggers (common in containers); ask the machine's administrator, or run the program directly under GDB rather than attaching to a running process. (Not seen in this build.)
    • 

  • LLDB cannot show std::vector contents → its C++ library formatters may not match your standard library; GDB showed them in this build (R2).
    • 

  • The watchpoint triggers inside library code → you are watching memory that a library function writes; that is real information, look at the backtrace.
    •

Forensic lab answer key


Observation. Frame #3 port_of at config.cc:40, return std::stoi(port->value);; info locals gives port = 0x0. The crash itself is in frame #0 inside basic_string.h with this=0x20, a small offset from the null pointer. R7


Hypotheses. (1) The input file differs (most likely: written by hand). (2) A different compiler or library version on the server. (3) A hardware or operating system difference. Evidence: in this lab, Evidence 1 and 2 were produced on one machine with one build; only the input file differed, and the crash appeared. So (2) and (3) are not needed to explain it.


Root cause. The server's file says Port=8080 with a capital P (print settings[1].key gives "Port"). Keys are compared exactly, so find(settings, "port") returns nullptr, and port_of dereferences it without checking.


Fix. Make "not found" impossible to ignore: return std::optional<std::string> and check it in main, printing config error: no 'port' setting (keys are case-sensitive) and exiting with code 2. Verified with both files: 8080 for Priya's, a clear error and exit code 2 for the server's. R8 (Whether keys should be case-insensitive is a product decision; the crash is a bug either way.)


Prevention. A unit test for port_of with a missing key (F2-30), and building tests with AddressSanitizer and UndefinedBehaviorSanitizer (F2-29), which report a null dereference with a clear message.


Wrong answers and why. "The new server's compiler is broken": the crash reproduces on Priya's machine with the server's file. "std::stoi has a bug": frame #0 is in the library, but the bad pointer was passed in from frame #3.
