Story hook

The kitchen's best soup changed last month, and since then customers say it is not as good. Nobody remembers exactly what changed. Was it the new stock? The shorter simmer? The cheaper onions? The old recipe card was thrown away when the new one was written.

A better kitchen keeps a recipe book where nothing is ever erased. Every change is a new dated page that says who changed what and why. When the soup goes wrong, the chef can open the page from before, compare the two, and even try the page halfway between them.

Git is that recipe book for code. This chapter puts the university template under git, makes a bad change on purpose, and lets git find it for you, with a binary search over history that runs your tests at each step.

What you will be able to do

  • Create a repository, stage files and make commits with clear messages.
  • Read history with git log, git show and git diff.
  • Use branches, merge them, and resolve a merge conflict by hand.
  • Find the commit that broke a test with git bisect run and undo it with git revert.
  • Tag a milestone and prove that a clean clone builds and passes its tests with one command.
  • Explain what a commit hash is, and check one by hand.
Jargon box
Version control
Simple words: a system that keeps every saved version of your files, with who changed what, when and why. Analogy: the recipe book where no page is ever erased. Precise: software that records snapshots of a set of files as a history, so any version can be restored, compared or combined; git is a distributed version control system: every copy holds the whole history. D1
Repository
Simple words: a project folder plus its full history. Analogy: the whole recipe book, all pages. Precise: in git, the working files plus a .git directory holding objects (file contents, folder listings, commits) and references (branches, tags). D1 R8
Staging area
Simple words: the list of changes you have chosen to put in the next commit. Analogy: the tray of corrected recipe cards waiting to be bound into the book. Precise: git's index; git add copies the current content of files into it; git status --short shows A for added and ?? for untracked files. R1 D2
Commit
Simple words: one saved snapshot of the whole project, with a message. Analogy: a new dated page in the recipe book. Precise: a git object that names a tree (the snapshot), zero or more parent commits, an author, a committer, times and a message. R8
Commit hash
Simple words: the long hexadecimal name of a commit, computed from its content. Analogy: a fingerprint of the page: change one letter and the fingerprint changes. Precise: the SHA-1 hash (40 hex digits; abbreviated to 7 in --oneline) of the object's type, size and content; in this build git hash-object of hello\n equalled sha1sum of blob 6\0hello\n. R8 D3
Branch
Simple words: a named line of work, so you can try something without disturbing the main version. Analogy: a test kitchen working on a copy of a recipe. Precise: a movable reference to a commit; a new commit on a branch moves it forward. D1
Merge
Simple words: combining the work of two branches. Analogy: copying the test kitchen's improvements into the main recipe book. Precise: creating a commit with two parents whose tree combines the changes made on both sides since their common ancestor. R6 R8
Merge conflict
Simple words: when two branches changed the same lines differently, and git cannot decide which to keep. Analogy: two chefs rewrote the same step in different ways; the head chef must choose. Precise: a merge stops with CONFLICT (content), writes both versions between <<<<<<<, ======= and >>>>>>> markers, and waits for you to edit, git add and commit. R6
Bisect
Simple words: letting git find the commit that broke something by testing the commit halfway, then halfway again. Analogy: opening the recipe book in the middle of the suspect month and tasting that version. Precise: git bisect does a binary search between a known good and a known bad commit; git bisect run <script> runs a script at each step, treating exit status 0 as good and other statuses as bad. R4 D2
Revert
Simple words: undoing an old commit by adding a new commit that does the opposite. Analogy: a new page that says "go back to the old stock", instead of tearing out a page. Precise: git revert creates a commit applying the inverse of a given commit's changes; history is kept. R5
Tag
Simple words: a permanent name for one commit, such as a milestone. Analogy: a bookmark labelled "the version we served at the opening". Precise: a reference to an object that does not move; an annotated tag (git tag -a) is itself an object with a message. R7 D2
Clone
Simple words: a full copy of a repository, history included. Analogy: a second complete recipe book for a second kitchen. Precise: git clone copies all objects and creates a working tree from the default branch. R7

Layer 1 — the kid explanation

When you work on a project, you change files again and again. Without a record, yesterday's working version is gone forever. Git keeps a record. Each time you are happy with a step, you make a commit: a snapshot of every file, with a short message like "add the README".

Later you can look back at every snapshot, see exactly what changed between two of them, and go back to any one. You can also start a branch, a side road where you try an idea. If the idea works, you merge it back. If not, you drop the branch, and the main road was never touched.

And when something breaks, git can help you find which snapshot broke it. It checks the one in the middle, then the middle of the half that is broken, and so on. Even with a thousand snapshots, that takes about ten checks.

Reading history

The lab then makes four more commits: a README, a "faster" median, a shorter output line in the program, and a CI change. Three commands read history: R2

  • git log --oneline: one line per commit, newest first, with the abbreviated hash.
  • git show --stat HEAD~2: one commit's author, date, message and which files changed (src/stats.cpp | 9 ++++-----). HEAD~2 means "two commits before the current one".
  • git diff HEAD~3 HEAD~2 -- src/stats.cpp: the exact lines changed, - removed, + added. Here the diff shows the sort and the even-count average removed, and nth_element with return xs[mid]; added.

Layer 3 — the engineer's depth

  • Content-addressed objects. Git stores everything as objects named by the SHA-1 of their content: blobs (file contents), trees (folder listings: mode, type, hash, name) and commits. git cat-file -p HEAD showed the merge commit's tree, its two parent lines, author, committer and message; git cat-file -p 'HEAD^{tree}' listed blobs and subtrees, with mode 100755 for the executable ci.sh. R8 Because a commit names its tree and parents by hash, its own hash covers the entire history behind it: change any old file and every later hash changes.
  • Bisect's cost. Each step halves the range of candidate commits, so n commits need about log2 n tests. Here 4 candidate commits after the good one needed 2 test runs. R4 This only works if every commit builds and tests on its own, which is one reason to commit small, complete steps. The script's exit status 125 tells bisect to skip a commit that cannot be tested (Listing 1, lines 4–5). D2
  • Revert versus rewriting history. git reset and git rebase can remove or rewrite commits. On a branch others have cloned, that breaks their copies; revert is the safe undo for shared history. D1
  • Reproducible hashes. The lab sets author, committer and dates to fixed values, so the hashes in this chapter are the same each time it runs (R2–R8). In real work, hashes depend on who committed and when; never assume two people's commits will match.
Not verified — check before relying on this

The meaning of exit status 125 in git bisect run (skip this commit) is from the title of the git documentation (D2); no commit in this lab failed to build, so the skip path was not exercised. The P1 acceptance test asks for a second machine or container: the clone in R7 ran in the same container as the original, so that part is untested. Git's move from SHA-1 to SHA-256 object names is mentioned in its documentation (D2); this build used the default SHA-1 format only.

How the hardware actually does it

Git is ordinary user software, but its central idea rests on a hardware-friendly operation: a hash function reads bytes and mixes them into a fixed-size number (160 bits for SHA-1, shown as 40 hexadecimal digits; MA102). D3 Comparing two whole files then becomes comparing two 20-byte numbers. The objects live as files on disk under .git/objects, compressed D1; the working tree is a normal folder. The executable bit you saw (100755 for ci.sh) is a file permission the operating system stores with the file, and git records it in the tree. R8 When git bisect moves between commits, it rewrites your working files on disk, which is why the build script uses a separate build folder (build/bisect) and why CMake must rebuild everything that changed.

Worked example

Task. Show that git's name for the file content hello plus a newline is a SHA-1 hash you can compute without git.

  1. The content is 6 bytes: h e l l o \n.
  2. Git hashes a header plus the content: the type blob, a space, the size in decimal (6), a zero byte, then the content: blob 6\0hello\n. D1
  3. Compute with git: printf 'hello\n' | git hash-object --stdin printed ce013625030ba8dba906f756967f9e9ca394464a.
  4. Compute without git: printf 'blob 6\0hello\n' | sha1sum printed the same 40 digits. R8
  5. The same check on a real file: git hash-object README.md and git rev-parse HEAD:README.md both gave 76b342fb…: the README in the commit is byte for byte the one on disk.

So a commit hash is not a random serial number: it is a checksum of the content, and anyone can recompute it.

Where the analogy breaks


    

  • Pages are whole books. A recipe book page holds one change. A git commit records a snapshot of the whole project; the "change" you see is computed by comparing two snapshots.
    • 

  • Every kitchen has the whole book. A restaurant has one recipe book. With git, every clone is complete, and kitchens exchange pages; there is no single master copy unless the team agrees on one (a shared server).
    • 

  • Pages can be rewritten. The recipe book never erases. Git can rewrite unpublished history (rebase, reset); it is safe only before others have copied it.
    • 




Common mistakes and debugging


    

  • Symptom: the build folder or binaries show up in git status. Cause: no .gitignore entry. Fix: add build/ to .gitignore before the first commit (the template has it, R1).
    • 

  • Symptom: one huge commit "various fixes". Cause: committing everything at the end of the day. Fix: stage related changes together (git add file, or git add -p in a terminal) and commit each step; bisect and revert work only as well as the commits are small.
    • 

  • Symptom: bisect blames a commit that only changed documentation. Cause: the test is flaky or depends on something outside the repository (F2-30). Fix: make the test deterministic first.
    • 

  • Symptom: after a conflict, the program does not compile: <<<<<<< in the source. Cause: markers left in the file. Fix: search for them before git add (grep -n '<<<<<<<', as in R6), then build and test before committing the merge.
    • 

  • Symptom: "works for me, fails on a clean clone". Cause: a needed file is untracked or ignored, or a path outside the repository is used. Fix: the clean-clone test of R7, in CI.
    •

Answers to Check yourself


    

  1. git add copies the current content of files into the staging area; git commit records a snapshot of what is staged as a new commit.
    2. 

  2. The commit two steps before the current one, following first parents (HEAD~1 is the parent).
    3. 

  3. Each test halves the candidates: 4 → 2 → 1. For 1,000 candidates about 10 tests (210 = 1,024).
    4. 

  4. Revert adds a commit; everyone's copies stay consistent and the record of the mistake remains. Deleting (rewriting) changes hashes of later commits, and others who cloned the old history get conflicting copies.
    5. 

  5. Two parents. In R8, git cat-file -p HEAD showed two parent lines; in R6 the graph showed two lines joining.
    6. 

  6. Usually keep both lines (both sides wanted a new source file), in a sensible order, then build and test. Choosing one side would drop the other's file.
    7. 

  7. The commits before the change keep their hashes; your new commit gets a new hash, and so would every commit made after it. If instead you amended an old commit, that commit and all later ones would get new hashes. Run it to see.
    8. 

  8. Your working folder can contain untracked or ignored files, local build output and settings that the repository does not. A clean clone has only what is committed, which is what another person or machine will get.

Observation. median_even_count_averages_middle_pair fails at test_stats.cpp:23: *uni::median({4.0, 1.0, 3.0, 2.0}) near 2.5. The median of 1, 2, 3, 4 is (2 + 3) / 2 = 2.5. R3


Hypotheses. "docs: add README": cannot change code behaviour. "stats: faster median with nth_element": touches median directly ("nobody touched the median" is wrong). "app: shorter output": changes the program's printout; could break stats.cli, but that test passed. "ci: build with 4 jobs": changes the build, not the result.


Root cause. Bisect named 1d441cc as first bad commit in 2 steps. R4 Its diff removes the even-count branch return (xs[mid - 1] + xs[mid]) / 2.0; and returns xs[mid] after nth_element; for 4 values that is the third smallest (3), not the average of the middle pair. R2

Prevention. The author should have run ./ci.sh before committing; CI should run on every proposed change before it is merged into main, so a red commit never lands. A performance change also needs a measurement (F2-33) to show it is faster at all.
