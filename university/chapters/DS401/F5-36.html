Story hook

Amara and Wei agree on rules before the courier from F5-34 may carry anything. Amara labels a shelf "Wei's notes" and makes two keys: one she keeps for herself, and one key card she sends to Wei, which lets a courier put things on that shelf and nowhere else. Both of them put two trays on their hall table, "to send" and "to receive", and register the pair with the courier company under a number. They phone each other once, slowly, to swap tray numbers and the first parcel number. Only then do the couriers start.

From now on, Wei writes a slip ("put this note on Amara's shelf, key card 0x1101"), drops it in his "to send" tray and rings the courier's bell. Later he finds a receipt in his receipts box: done, or a reason why not. If Wei sends a letter that Amara must read rather than a shelf delivery, Amara must have put an empty envelope in her "to receive" tray first, or the courier has nowhere to put it.

The rules are the verbs interface. The trays are a queue pair, the labelled shelf is a memory region, the key card is a remote key, the receipts box is a completion queue. This chapter writes the program, line by line.

What you will be able to do

  • Explain the verbs objects (device context, protection domain, memory region, completion queue, queue pair, address vector) and how they depend on each other.
  • Write and explain line by line a reliable-connection ping-pong over libibverbs, including the out-of-band exchange and the queue-pair state transitions (the course's practical exam).
  • Register memory with the right access flags and use local and remote keys correctly in work requests.
  • Predict the completions of SEND/RECV and RDMA WRITE, including receiver-not-ready, remote access errors and flushed work requests.
  • Diagnose a stalled replica from a completion log: find the first error, not the loudest one.
Jargon box
Verbs
Simple words: the list of operations a program can ask an RDMA adapter to do, and the C library that offers them. Analogy: the courier company's rulebook and forms. Precise: the abstract interface the InfiniBand architecture defines between a consumer and a channel adapter; on Linux it is implemented by the rdma-core library libibverbs (header infiniband/verbs.h, functions prefixed ibv_) with per-device user-space providers. D1 D3
Protection domain (PD)
Simple words: a group that memory regions and queue pairs belong to; a queue pair can only use memory of its own group. Analogy: one household's key ring: keys from another household's ring do not open your shelves. Precise: a verbs object (struct ibv_pd, from ibv_alloc_pd) that associates queue pairs, memory regions and other objects; the adapter allows a work request to use a memory region only if both belong to the same protection domain. D1 D3
lkey and rkey
Simple words: two numbers you get when you register memory: one you use yourself, one you give to the other side. Analogy: Amara's own key, and the key card she posts to Wei. Precise: the local key, placed in a scatter/gather element to let the local adapter access the region, and the remote key, sent to a peer and carried in the RETH of RDMA READ/WRITE so the remote adapter can check access; both are fields of struct ibv_mr. D1 D3
Access flags
Simple words: what a registered region allows: may the adapter write into it locally, may remote peers write or read it. Analogy: what the key card permits: put things on the shelf, or also take them. Precise: bits of enum ibv_access_flags passed to ibv_reg_mr: in the installed header IBV_ACCESS_LOCAL_WRITE = 1, IBV_ACCESS_REMOTE_WRITE = 2, IBV_ACCESS_REMOTE_READ = 4, IBV_ACCESS_REMOTE_ATOMIC = 8, among others. D3 D1
Work request (WR) and scatter/gather element (SGE)
Simple words: a slip that tells the adapter what to do (send, receive, write) and where the bytes are. Analogy: the slip Wei puts in his "to send" tray. Precise: struct ibv_send_wr or struct ibv_recv_wr posted with ibv_post_send/ibv_post_recv; it carries a 64-bit wr_id chosen by the program, an opcode (send queue only), flags, and a list of struct ibv_sge entries (address, length, lkey). D3
Work completion (WC)
Simple words: the receipt for a finished work request, with "success" or an error. Analogy: the receipt in the receipts box. Precise: struct ibv_wc returned by ibv_poll_cq, carrying the wr_id, a status from enum ibv_wc_status (IBV_WC_SUCCESS, IBV_WC_REM_ACCESS_ERR, IBV_WC_RNR_RETRY_EXC_ERR, IBV_WC_WR_FLUSH_ERR, …), the opcode and the byte count. D3
Queue-pair state machine
Simple words: a queue pair moves through steps (reset, initialised, ready to receive, ready to send) before it can be used, and falls into an error step when something goes wrong. Analogy: registering the trays, swapping numbers on the phone, then opening for business. Precise: the states of enum ibv_qp_state (IBV_QPS_RESET, INIT, RTR, RTS, SQD, SQE, ERR), changed with ibv_modify_qp and an attribute mask naming which fields of struct ibv_qp_attr are valid. D1 D3
Receiver not ready (RNR)
Simple words: a SEND arrived but the other side had not posted a receive buffer. Analogy: a letter arrives and Amara has no empty envelope in her "to receive" tray. Precise: the responder's negative acknowledgement for a SEND that finds no posted receive work request; the requester retries after a timer, up to the queue pair's RNR retry count, and then completes the work request with IBV_WC_RNR_RETRY_EXC_ERR. D1 D3
Out-of-band exchange
Simple words: swapping the connection details over some other channel before RDMA can be used. Analogy: the one slow phone call to swap tray numbers. Precise: transfer of queue-pair number, first PSN, LID and/or GID (and, for one-sided operations, buffer address, length and rkey) through a channel that already works, such as a TCP socket, before the queue pairs are moved to RTR and RTS; the rdma-cm library (librdmacm) automates this. D4 R1

Terms from earlier: Memory region and registration, queue pair, completion queue (CQ, RDMA) (HW205); one-sided operation and kernel bypass (F5-34); LID and GID, PSN and path MTU (F5-35).

Layer 1 — the kid explanation

Analogy

Mapping (proposed): protection domain = a household's key ring; memory region = a labelled shelf; lkey = the household's own key; rkey = the key card given to a friend; access flags = what the key card allows; queue pair = the pair of trays "to send" and "to receive", registered under a number; work request = a slip in a tray; doorbell = the courier's bell; completion queue = the receipts box; the out-of-band exchange = the one slow phone call before the couriers start; receiver not ready = a letter arrives and there is no empty envelope in the "to receive" tray.

Before any parcel moves, both friends do slow, careful set-up: label shelves, make keys, set out trays, swap numbers by phone. After that, sending is fast: write a slip, ring the bell, later check the receipts box. Two kinds of delivery exist. A letter ("SEND") needs the friend to have set out an empty envelope first, and both friends get a receipt. A shelf delivery ("RDMA WRITE") only needs the key card; the friend at home gets no receipt and is not disturbed.

Layer 2 — the student explanation

The objects, in the order you create them

Listing 1 creates every object in the order of Figure 1 D3 D1:

  1. Device list and context. ibv_get_device_list returns a NULL-terminated array of devices ("Return a NULL-terminated array of IB devices", the header's comment) and the count; ibv_open_device opens one and returns a struct ibv_context D3.
  2. Port and address. ibv_query_port fills struct ibv_port_attr (LID, active MTU, link layer); ibv_query_gid reads one entry of the port's GID table, selected by an index D3. On RoCE the GID is derived from an IP address of the interface, and several GIDs (for example for RoCE v1 and v2, IPv4 and IPv6) can exist; choosing the index is part of the configuration (see the unverified box below).
  3. Protection domain. ibv_alloc_pd.
  4. Memory region. ibv_reg_mr(pd, addr, length, access) registers an application buffer and returns struct ibv_mr with lkey and rkey D3. Registration pins the pages and gives the adapter their translations, so it is slow and is done once, ahead of time (F5-38) D4.
  5. Completion queues. ibv_create_cq(context, cqe, cq_context, channel, comp_vector): the header's comment explains each parameter, including that cqe is the "Minimum number of entries required for CQ" and that the channel "May be NULL if completion events will not be used" D3. Listing 1 polls, so it passes NULL.
  6. Queue pair. ibv_create_qp(pd, &init_attr) with the two CQs, the capacities of the send and receive queues and the transport type IBV_QPT_RC. The new QP's number is in qp->qp_num D3.

Connecting two queue pairs

A reliable-connection QP talks to exactly one remote QP. Before it can, each side must know the other's QP number, first PSN and address (LID on InfiniBand, GID on RoCE) D1. RDMA cannot carry these yet, so Listing 1 exchanges them over a TCP connection (lines 266–268): the out-of-band exchange. Then each side moves its QP through the states of Figure 2 D3:

  • RESET → INIT: which partition-key index and port to use, and which remote accesses the QP allows (qp_access_flags; 0 in Listing 1, because a ping-pong with SEND/RECV needs no remote access).
  • INIT → RTR (ready to receive): the remote QP number, the PSN the remote side will start with, the path MTU, and the address vector (ah_attr); with a non-zero GID, is_global = 1 and the GRH fields. A QP in RTR can receive.
  • RTR → RTS (ready to send): our own first PSN, the transport timeout, the retry counts, and the number of outstanding RDMA READs it may issue.

Every call names the fields it sets with the attribute mask, a bitwise OR of enum ibv_qp_attr_mask values such as IBV_QP_STATE (bit 0), IBV_QP_AV (bit 7) and IBV_QP_PATH_MTU (bit 8) D3. A missing bit means the field is ignored; a required one that is missing makes ibv_modify_qp fail.

Not verified — check before relying on this

The numbers in toRtr and toRts (min_rnr_timer = 12, timeout = 14, retry_cnt = 7, rnr_retry = 7, hop_limit = 1, max_dest_rd_atomic = max_rd_atomic = 1) were written by the author from memory of common examples. They compile (the fields exist in the installed header, D3), but their meanings are encoded: timeout and min_rnr_timer select time values from tables, and a retry count of 7 may have a special meaning for RNR retries. Check ibv_modify_qp(3) in the rdma-core documentation and the QP attribute tables of the InfiniBand specification (D1, D2) before using them, and choose the GID index for RoCE v2 from your system's GID table (how to list it is in the rdma-core documentation, not verified here).

Posting work and reaping completions

A work request names its buffers through scatter/gather elements: address, length and the lkey of the region that contains them (Listing 1, lines 169 and 183). A SEND (IBV_WR_SEND) consumes one receive request that the peer posted earlier; an RDMA WRITE (IBV_WR_RDMA_WRITE) also names a remote address and the peer's rkey in wr.rdma. The flag IBV_SEND_SIGNALED asks for a completion entry D3. The header's comment on ibv_post_send states the buffer rule in one line: "If IBV_SEND_INLINE flag is set, the data buffers can be reused immediately after the call returns" D3; without that flag, the buffer belongs to the adapter until the completion arrives.

ibv_poll_cq(cq, n, wc) returns how many completions it wrote into wc, 0 if none, a negative value on error; per the header comment, a non-negative return smaller than n means the CQ was emptied D3. Each completion carries the wr_id you chose and a status. Check the status of every completion: an error does not come back from ibv_post_send (that only checks that the request was well formed and the queue had room); it comes back later, in the CQ D1.

The rules, demonstrated by a model you can run

The build has no RDMA device: Listing 1 compiles and links against rdma-core 50.0 but stops at ibv_get_device_list with 0 devices and errno 38 ("Function not implemented") R1 R2. To watch the rules act, Listing 2 (verbs_model.hpp) is the university's own toy verbs model: in-process objects with the same names, the access-flag bits of the real header and the status names of enum ibv_wc_status, but executing the chapter's simplified reading of the rules. Its run (R3) shows five scenes:

  1. A QP cannot jump from RESET to RTS, and a SEND posted in INIT is rejected.
  2. An RDMA WRITE into B's region (registered with access 0x3 = LOCAL_WRITE | REMOTE_WRITE) succeeds; only A gets a completion; B's memory changes although B's program did nothing.
  3. A SEND that finds a RECV posted by B: both A and B get a completion.
  4. A SEND with no RECV posted: receiver not ready, retried, then RNR_RETRY_EXC_ERR; the QP goes to ERR and the RDMA WRITE queued behind it completes with WR_FLUSH_ERR.
  5. An RDMA WRITE of 64 bytes at offset 1000 of a 1024-byte region: REM_ACCESS_ERR, QP to ERR, the next request flushed.
Not verified — check before relying on this

The model is the author's reading of rules that were not checked against the specification in this build: exactly which transitions are legal from which states (the model allows only RESET→INIT→RTR→RTS, any→RESET, any→ERR), that receive requests may be posted in INIT, that posting to a QP in ERR is accepted and then flushed, that a remote access violation is reported to the requester as IBV_WC_REM_ACCESS_ERR, and what happens to the responder's QP after such an error (the model leaves it alone). The status names are real (D3); the behaviour must be checked in D1 and D2 and on hardware.

Layer 3 — the engineer's depth

Transport types and what they cost

The installed header lists the QP types IBV_QPT_RC, IBV_QPT_UC, IBV_QPT_UD, IBV_QPT_RAW_PACKET and the XRC types D3. Reliable connection (RC) gives ordered, acknowledged delivery and all operations (SEND, RDMA READ and WRITE, atomics) between two QPs. Unreliable datagram (UD) lets one QP send to many peers with an address handle per destination, but only SENDs of at most one MTU and without acknowledgement. Unreliable connection sits between D1. The engineering consequence is the connection-scaling problem: with RC, N processes that all talk to each other need on the order of N² QPs in total, each with state that the adapter must cache; designs reduce this with shared receive queues, XRC, UD for control traffic, or a dynamically connected transport some vendors offer (vendor documentation, not verified here) D4.

Registration, keys and security

An rkey is a capability: anyone who knows it and can reach a connected QP in the same protection domain can access the region with the rights its flags give, until it is deregistered D1. Rules that follow:

  • Register with the least access the protocol needs, but no less: a region that peers write into with RDMA WRITE needs IBV_ACCESS_REMOTE_WRITE, and the adapter itself needs IBV_ACCESS_LOCAL_WRITE to write received data (the header shows IBV_ACCESS_REMOTE_WRITE is bit 1 and IBV_ACCESS_LOCAL_WRITE bit 0) D3. The forensic lab is about getting this wrong.
  • Advertise the address, length and rkey of a region to a peer only through a trusted channel, and invalidate (deregister, or use memory windows) when the peer should lose access.
  • Do not deregister or free memory while a peer may still write to it: the peer's next WRITE gets an error (good) or, if the memory was re-registered and the key reused, lands in new data (bad). HW205's "stale key" forensic lab showed this (F1-53).
  • Registration cost grows with the region's size (pages to pin and translate), so programs register pools at start-up and carve buffers from them. Registered memory counts against the process's locked-memory limit (F5-38 prints it) D4.
  • Process creation: the header warns that unless ibv_fork_init() succeeded, "libibverbs data structures are not fork()-safe and the effect of an application calling fork() is undefined" D3. Fork before opening devices, or not at all.

Flow control is your job

The kernel's TCP never refuses a message for lack of a receive buffer; it buffers. With SEND/RECV, the receiver must have posted enough receive requests before messages arrive, or the sender suffers RNR retries and eventually an error that breaks the connection D1. Protocols built on verbs therefore use credits: the receiver tells the sender how many receives it has posted, and the sender never exceeds that. Listing 1 avoids the problem by design (one message in flight, and the barrier at line 276 after both sides posted a receive). The same reasoning applies to completion queues: a CQ smaller than the number of completions that can be outstanding overflows, which is an error; size it as the sum of the queues that report into it.

Building protocols from one-sided operations

RDMA WRITE into a ring buffer on the peer is the fastest way to move data, but the peer learns nothing. Three standard patterns, each with a trade-off D4:

  • Write, then a flag. Write the payload, then write a flag or a sequence number; the receiver polls the flag. Correct only if the second write cannot become visible before the first; check the ordering guarantees for RC and the adapter's documentation, and remember the receiver's CPU caches (HW205).
  • RDMA WRITE with immediate. IBV_WR_RDMA_WRITE_WITH_IMM writes the data and consumes a posted receive at the target, producing a completion with 32 bits of immediate data D3.
  • Write, then SEND. A SEND after the WRITE on the same RC QP arrives after it; the SEND's completion tells the receiver that the write is in place.

The course project (replicated log append, F5-38) is built from these patterns.

Note

Connection management libraries exist so that programs do not have to write the out-of-band exchange, the GID choice and the state transitions themselves: rdma-cm (librdmacm, installed in the build as the package librdmacm1t64, R2) resolves an IP address to a device, port and GID and drives the transitions. Its header was not installed (no librdmacm-dev), so it is not used here; Listing 1 does everything by hand on purpose, because the exam asks you to explain each step.

How the hardware actually does it

Posting a work request writes a descriptor into the send or receive queue, which lives in memory mapped for the process, and then writes a doorbell register in a page of the adapter's PCIe space mapped into the same process (kernel bypass, F5-34) D4. The adapter fetches the descriptor by DMA, translates the SGE's address with the memory region identified by the lkey, reads the data by DMA, and runs the transport of F5-35. On the responder, the adapter finds the QP from the BTH, checks the PSN, and for an RDMA WRITE looks up the rkey from the RETH in its table of regions, checks the access flags and the bounds and the protection domain, translates the address, and writes by DMA. Completions are written by DMA into the CQ's ring in host memory; ibv_poll_cq reads them there, which is why the header can make it a static inline call through the context's operation table D3.

The installed provider list shows where this device-specific code lives: /usr/lib/x86_64-linux-gnu/libibverbs holds one user-space driver per adapter family, including librxe-rdmav34.so for Soft-RoCE (rxe) and libsiw-rdmav34.so for software iWARP R2. The kernel half of those drivers was not available in the build container (no /lib/modules, no /sys/class/infiniband).

Worked example

Predict every completion of this sequence on QP A (connected to QP B, both RTS), then check against the model's rules. B has registered region L (1024 bytes, access 0x3) and region I (256 bytes, access 0x1), and has posted no receive. A posts, in order: (1) RDMA WRITE 14 bytes to L+0 with L's rkey; (2) SEND 9 bytes; (3) RDMA WRITE 14 bytes to L+0.

  1. WR 1: rkey valid, REMOTE_WRITE set (0x3 & 0x2 ≠ 0), 0 + 14 ≤ 1024: success; completion at A only.
  2. WR 2: SEND needs a receive request at B; none is posted: receiver not ready; after the RNR retries, RNR_RETRY_EXC_ERR; A's QP goes to ERR.
  3. WR 3: queued behind a failed request on a QP in ERR: WR_FLUSH_ERR, although by itself it would have succeeded.

Scenes 2 and 4 of R3 show exactly these completions (wr 2 SUCCESS; wr 4 RNR_RETRY_EXC_ERR; wr 5 WR_FLUSH_ERR) R3. Two lessons: a flush error is a consequence, never a cause, so look for the first non-flush error; and after any error the QP is useless until it is reset and reconnected, so the RNR mistake also cost the WRITE behind it.

Access-flag arithmetic. A region registered with IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_READ has flags 1 + 4 = 5 = 0x5. It allows remote reads but not remote writes (0x5 & 0x2 = 0). A region printed as "access 0x1" allows neither.

Where the analogy breaks


    

  • A friend whose letter finds no envelope would wait or leave a note. An RDMA SEND without a posted receive is retried a fixed number of times and then breaks the connection: there is no buffering at the receiver.
    • 

  • A household's keys stay valid until you change the lock. An rkey is valid exactly as long as its registration; deregistering is "changing the lock", and a re-registration may produce a different key.
    • 

  • Trays on a hall table hold any number of slips. Queues have fixed capacities chosen at creation (max_send_wr, max_recv_wr); posting beyond them fails at once.
    • 

  • A courier who finds a problem with one parcel still delivers the others. After one error the QP goes to the error state and every later request is flushed, as R3 and the forensic lab show.
    • 

  • The phone call to swap numbers happens once in the story. Real systems need it again after every reconnect, with new PSNs, and the exchange channel must itself be reliable and authenticated.
    •

Transition box

Where you came from: F5-35 read the packets (BTH, RETH, AETH); F5-09 and DS201 programmed sockets; SP201 taught RAII. What carries over: request ids (now wr_id), checking every error, RAII for every handle, an explicit protocol for the bytes you exchange, and the PSNs and keys you decoded on the wire D3. What changes: most dangerous first: errors arrive later in a completion queue, not as return values; a buffer belongs to the adapter until its completion; the receiver must post buffers in advance; one error breaks the connection and flushes everything behind it; and set-up (registration, out-of-band exchange, state transitions) is explicit and slow D1. Summary


    

  • A verbs program creates, in order: device context, protection domain, memory regions, completion queues, queue pairs; RAII destroys them in reverse order.
    • 

  • Memory registration returns an lkey (used in your SGEs) and an rkey (given to peers, carried in the RETH); access flags decide what peers may do.
    • 

  • Connecting an RC queue pair needs an out-of-band exchange (QP number, PSN, LID/GID) and three transitions: INIT, RTR, RTS, each with an attribute mask.
    • 

  • SEND needs a receive posted in advance and completes at both ends; RDMA WRITE completes only at the requester; the target program learns nothing unless the protocol tells it.
    • 

  • Errors arrive as completion statuses; after the first error the QP is in ERR and later requests are flushed: find the first error.
    • 

  • A buffer belongs to the adapter until its completion (unless sent inline); a receive buffer must exist before the message.
    • 

  • Listing 1 compiled against rdma-core 50.0 but is untested on hardware; the rules were demonstrated with the university's toy model.

Answers to Check yourself


    

  1. Device list (none) → context (a device from the list) → PD (context) → MR (PD and a buffer) → CQs (context) → QP (PD, CQs). The address vector is part of the QP's attributes, set in RTR.
    2. 

  2. QP number, first PSN, LID and GID (and for one-sided operations the buffer address, length and rkey). RDMA needs a connected QP to send anything, and connecting needs exactly these values: a chicken-and-egg problem solved with a channel that already works (TCP, or rdma-cm).
    3. 

  3. INIT: port and P_Key index (which port and partition the QP uses), access flags (what remote peers may do). RTR: destination QP number and RQ PSN (to accept the peer's packets), path MTU and address vector (where and how big). RTS: SQ PSN (our numbering), timeout and retry counts (what to do when ACKs do not come).
    4. 

  4. The lkey authorises the local adapter to use a region named in your own SGEs; it never leaves the host. The rkey authorises a remote adapter's requests; you send it to the peer, and it travels in the RETH of each RDMA READ or WRITE request (F5-35, Figure 2: "Remote Key").
    5. 

  5. 0x5 & 0x2 = 0: no REMOTE_WRITE, so the WRITE fails with REM_ACCESS_ERR at A; A's QP goes to ERR and the next request completes with WR_FLUSH_ERR (as in scene 5 and the forensic lab).
    6. 

  6. The first SEND consumes the only receive; the others arrive before the server re-posts: receiver not ready, retries, and if the server is slower than the retries, RNR_RETRY_EXC_ERR and a broken connection. Fixes: post at least as many receives as the client may have in flight (and size max_recv_wr for it), and use credits so the client never sends more than the server has posted; a shared receive queue helps with many clients.
    7. 

  7. A receive completion (the pong) can be in the CQ before the send completion of our own ping. A single-CQ loop waiting for the send's wr_id would read and discard the pong's completion, then wait forever for it. With one CQ per queue each wait consumes only completions of its own kind.
    8. 

  8. After its completion has been polled (signalled sends), or after a later signalled completion on the same queue if it was unsignalled. The header: "If IBV_SEND_INLINE flag is set, the data buffers can be reused immediately after the call returns."
    9. 

  9. 0x7 = 1 + 2 + 4 = LOCAL_WRITE, REMOTE_WRITE, REMOTE_READ; not REMOTE_ATOMIC (8).
    10. 



Forensic lab answer key


Observation. The first error is "qp 0x102: error REM_ACCESS_ERR on wr 201 -> state ERR": QP 0x102 is the leader's QP to F2, wr 201 its first append. wr 202, 203 and 204 complete with WR_FLUSH_ERR: three of the four errors are consequences. All four of F1's writes succeed R4.


Decoding. F1 advertised access 0x3 = IBV_ACCESS_LOCAL_WRITE (1) | IBV_ACCESS_REMOTE_WRITE (2); F2 advertised 0x1 = IBV_ACCESS_LOCAL_WRITE only D3. Addresses, lengths and rkeys are otherwise consistent: the leader used F2's own rkey 0x1201 and offsets inside the 2048-byte region.


Hypotheses. (1) Faulty adapter: against it, the error is a specific remote-access status on the very first request and the other QP on the same leader adapter works; a hardware fault would not choose the follower whose registration changed. (2) Wrong rkey sent by the leader: ruled out, the leader used 0x1201, F2's advertised rkey. (3) Out-of-bounds write: ruled out, offsets 0–255 inside 2048 bytes. (4) F2's region does not allow remote writes: consistent with access 0x1 and with the upgrade date (the region was re-registered with tighter flags).


Root cause. F2's new build registers its log region with IBV_ACCESS_LOCAL_WRITE only; one-sided appends need IBV_ACCESS_REMOTE_WRITE. The first WRITE fails with a remote access error, the leader's QP to F2 enters the error state, and every later append is flushed.


Fix. Register the log region with IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE (least privilege means "no REMOTE_READ", not "no REMOTE_WRITE"). The leader's QP 0x102 must be reset and reconnected (new out-of-band exchange, new PSNs), then the missing entries 1–4 re-sent. Prevention. At connection set-up, the leader checks each follower's advertised access value against the operations it will use and refuses to start with a clear message; an integration test appends one entry to every follower after each upgrade.


How the evidence was produced. replog_fault.cpp on the toy model: F2's region registered with LOCAL_WRITE only (line 21), four RDMA WRITEs per follower; output unedited.
