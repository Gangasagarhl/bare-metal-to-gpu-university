Story hook

Wei wants to know how fast the new courier is. On Monday he times one letter to Amara and back: 2 hours. On Tuesday the same trip takes 9 hours, because the courier was stuck behind a parade. On Wednesday he sends a whole lorry of parcels and divides the number of parcels by the time: 40 parcels per hour. Which number is "the speed of the courier"?

None of them alone. One trip tells you almost nothing; many trips, sorted, tell you the usual time (the median) and the bad days (the tail). A single letter measures delay; a lorry-load measures throughput; they answer different questions. And if the courier was new on Monday and still learning the route, Monday should not count at all.

The RDMA community's standard tool, the perftest suite, is built on exactly these rules. This chapter learns the rules on a harness we can run, then applies them to a case where an RDMA fabric was measured slower than TCP.

What you will be able to do

  • Design a latency and a bandwidth measurement with warm-up, enough iterations, fixed message sizes and percentile reporting.
  • Run a perftest-style harness and interpret its minimum, median, 99th percentile and maximum, and its message rate (the course goal "measure with perftest") D4.
  • Fit the alpha–beta model to latency medians and say when the fit is meaningless.
  • Plan a perftest run on RDMA hardware (what to fix, what to record) and read its output columns, knowing which flags this build could not check.
  • Explain an "RDMA slower than TCP" result from a configuration dump: path MTU and the missing lossless setting.
Jargon box
perftest
Simple words: a set of small programs that measure how fast RDMA is between two machines. Analogy: the courier company's official stopwatch kit. Precise: an open-source benchmark suite distributed with or alongside rdma-core: one program per operation and metric (for example ib_write_lat, ib_write_bw, ib_send_lat, ib_send_bw, ib_read_lat, ib_read_bw), each run as a server on one host and a client on the other. D1 R4
Latency test and bandwidth test
Simple words: a latency test sends one message and waits for the answer, many times; a bandwidth test sends many messages without waiting and counts bytes per second. Analogy: one letter there and back, versus a lorry-load. Precise: a latency test is a ping-pong with one message in flight, reporting one-way latency as half the round-trip time; a bandwidth test keeps a window of messages in flight in one direction and reports bytes delivered divided by elapsed time, and the message rate. D1 R1
Message rate
Simple words: how many messages per second can be sent, whatever their size. Analogy: parcels per hour, not kilograms per hour. Precise: messages completed per second in a bandwidth test (bandwidth divided by message size); for small messages it, not bytes per second, is the limiting figure. R1
Goodput
Simple words: the useful bytes delivered per second, not counting headers or bytes sent twice. Analogy: the letters that arrived the first time, not the envelopes or the repeats. Precise: application payload delivered once divided by time, or as a fraction of the bytes the link carried; it falls with per-packet header overhead (small path MTU) and with retransmission. R2

Terms from earlier: median and percentile and warm-up run (MA202); tail latency (DS201: the slowest few percent, such as p99 or the maximum; for a step that waits for many messages, the tail sets the step time); alpha–beta model (HW301); path MTU, lossless traffic class and PFC, go-back-N (F5-35); queue pair (HW205).

Layer 1 — the kid explanation

Analogy

Mapping (proposed): latency test = time one letter there and back, many times, and halve it; bandwidth test = time a lorry-load and divide; warm-up = the courier's first trips, not counted; the median = the usual trip; the 99th percentile = the parade days; goodput = letters that arrived the first time, not counting envelopes or repeats.

To know how fast something is, you time it many times, throw away the first few, sort the times, and say "usually this, on a bad day that". You measure one letter and a lorry-load separately because they answer different questions. And you write down everything about the test (which courier, which road, what day) so someone else can repeat it.

Layer 2 — the student explanation

Seven rules of a network benchmark

  1. One question per test. Latency (one message in flight) and bandwidth (many in flight) are different experiments. A bandwidth test's per-message time is not a latency.
  2. Fixed message size per run, swept over a list. Small messages show per-message cost; large messages show the bandwidth limit. Listing 1 uses 2 B to 64 KiB for latency and 64 B to 1 MiB for bandwidth.
  3. Warm up. Listing 1 runs 200 untimed round trips before 2000 timed ones (lines 105–111).
  4. Report a distribution. Minimum (the best the system can do), median (the usual), p99 and maximum (the tail) (MA202). Never only a mean: one stall of 400 µs moves a mean of 2000 samples by 0.2 µs, invisible, while the maximum shows it.
  5. Repeat the whole run. Listing 1 repeats each bandwidth test three times and prints the minimum, median and maximum of the three (lines 179–184). Two runs of the same program in this build (R1, sanitizer build and -O2 build) differ, as the worked example shows.
  6. Hold everything else constant and record it. Machine, CPU and core placement, kernel, driver and firmware versions, MTU, adapter settings, compiler and flags, the exact command. The run logs in this chapter (R1–R4) record what the build could record.
  7. Know what the clock measures. Listing 1 measures round-trip time with a monotonic clock on one machine and halves it, which assumes the two directions are symmetric; it never compares clocks of two machines.

What perftest numbers do and do not tell you


    

  • A latency test with one message in flight measures adapter, PCIe and wire latency plus polling; it says nothing about how a real application with many outstanding operations behaves.
    • 

  • Results depend on settings that must be recorded: path MTU, message size, inline sends, which CPU core and which NUMA node the process runs on relative to the adapter (F5-38), whether the CPU's frequency scaling is active, and the RoCE GID index (v1 or v2) D2.
    • 

  • A perftest run between two hosts on an idle fabric shows the best case. The forensic lab of this chapter is about a fabric where incast makes the result much worse; a benchmark that never creates congestion would miss it.
    • 

  • The no-hardware-numbers rule (AH-23): a perftest result is recorded with machine, adapter, firmware, driver, perftest version and command line, or it is not quoted.
    • 




Layer 3 — the engineer's depth


The alpha–beta fit, and when it lies


The alpha–beta model says a message of n bytes takes t(n) = α + n/β: a fixed cost α plus n bytes at bandwidth β (HW301). Listing 1 fits it by least squares to the six medians (lines 160–172). The -O2 run printed α = 12.88 µs and 1/β = 0.2767 ns/byte (β = 3614 MB/s); the sanitizer run printed α = 19.95 µs and 1/β = 0.2110 ns/byte (β = 4739 MB/s) R1. Three things are wrong with taking these at face value:


    

  • The fitted α (12.88 µs) is six times the measured 2-byte median (2.09 µs). The intercept absorbs the scheduling noise of the 64 B to 4 KiB medians; it is not a per-message cost.
    • 

  • The least-squares fit on linear sizes 2, 64, …, 65536 is dominated by the largest size: the 65536-byte point alone almost decides the slope.
    • 

  • The two runs disagree by 55 % on α. A model parameter that changes that much between runs is not a property of the system.
    • 



Better practice: fit minima or medians of many repeated runs; use sizes spaced evenly where you need the parameters (small sizes for α, large sizes for β); report the residuals; and check the fitted β against the separately measured bandwidth table (here 2868.6 MB/s median at 1 MiB, R1). On RDMA hardware the same method gives the α and β that collective-communication models need (F5-38 and DS402) D2.


Bandwidth, message rate and the window


The bandwidth table shows the second limit: message rate. At 64 bytes the -O2 run delivered 77.1 MB/s, which is 1.205 million messages per second; at 1 MiB it delivered 2868.6 MB/s but only 0.003 million messages per second (R1). For small messages the cost per message (here, a system call and a TCP segment) limits throughput; for large ones the cost per byte. RDMA adapters move the per-message cost into hardware, which is why message rate is one of their headline figures; perftest bandwidth programs report it alongside bytes per second D1.


A bandwidth test needs enough messages in flight to cover the path's bandwidth-delay product: at rate B and round-trip time R, at least B × R bytes must be outstanding, or the sender waits for completions and the test measures latency instead. Listing 1 lets the TCP socket buffers provide the window; perftest programs have a parameter for the number of outstanding work requests (tx depth; not verified here) D1.


Why RoCE can be slower than TCP: the fabric model


RDMA is fast when its assumptions hold: large enough path MTU and a fabric that does not drop packets. Listing 2 is the university's RoCE path model: it reads a configuration dump (fabric_model.in) and predicts goodput for a long stream of RDMA WRITE packets with three mechanisms:


    

  1. Header overhead per packet: 58 bytes (Ethernet 14 + IPv4 20 + UDP 8 + BTH 12 + ICRC 4, as counted in F5-35, line 48). At path MTU 1024 the payload share is 1024 / 1082 = 94.6 %; at 4096 it is 98.6 %.
    2. 

  2. Drops in a lossy class during incast: when more than one sender converges (incast > 1) and the QP's traffic is not in a lossless class with PFC, each packet is dropped with a fixed probability (0.002 in the dump, a chosen parameter) (lines 65–72).
    3. 

  3. Go-back-N recovery: after a drop, the responder discards the out-of-sequence packets that follow, and the requester resends everything from the lost PSN; the model counts a whole bandwidth-delay window (131072 bytes in flight) as resent per drop (lines 75–78). With PFC on, the same event is counted as a pause and nothing is lost (line 74).
    4. 



The result (R2): pair A-B (path MTU 4096, PFC on) 98.6 %; pair C-D (path MTU 1024, PFC off) 76.9 %, with 46238 packets resent after 379 NAKs. With smaller packets, more packets fit in the window (122 at MTU 1024 versus 32 at MTU 4096), so each drop costs more resends; the two misconfigurations multiply. TCP, by contrast, recovers from loss with selective acknowledgement and congestion control designed for lossy networks (DS201), which is how a TCP benchmark on the same hosts can beat a RoCE benchmark on a lossy fabric.


Not verified — check before relying on this
The model is a teaching model, not a simulator of any product. Not modelled: the throughput lost while PFC pauses a sender (counted, not charged), PFC side effects such as head-of-line blocking and pause storms, ECN-based congestion control in the adapter, retransmission timeouts, adapters that implement selective repeat instead of go-back-N, and the actual drop behaviour of any switch. The loss probability 0.002 and the in-flight bytes 131072 were chosen for the lab and were not measured anywhere. That go-back-N is the recovery of RC on RoCE, and that some adapters offer better recovery, is after D1 and D2 (pending verification).



How the hardware actually does it


A perftest latency program on hardware, as described in D1 and D2 (pending verification): both sides register a buffer, connect an RC QP, and the client posts an operation and busy-polls the CQ (or, for RDMA WRITE latency, polls a byte in its own buffer that the server's WRITE changes). Timing comes from the CPU's cycle counter or a monotonic clock; per-iteration times are sorted for the percentiles D1. Small messages may be sent inline (data copied into the work request by the CPU, saving the adapter's DMA read), which lowers latency; the maximum inline size depends on the adapter D2.


On the fabric, the switch decides what happens under congestion. With PFC enabled for a priority, a switch port whose buffer for that priority fills sends a pause frame upstream for that priority only; the upstream port stops sending that priority; nothing is dropped. Without it, the buffer overflows and packets are dropped, and RoCE's transport recovers end to end (F5-35) D3. Both the switch and every host must agree which DSCP value or VLAN priority carries RoCE, and the switch must map it to the lossless priority: in the forensic dump, C-D's QPs use DSCP 26 and the switch's lossless DSCP is 26, but PFC on that class is off.


Not verified — check before relying on this
Untested on hardware. No RDMA adapter, switch or perftest binary was available. The descriptions above (polling method of the WRITE latency test, inline sends, pause behaviour) are the chapter's reading of D1–D3 and must be checked against the perftest source and documentation, the adapter's manual and the switch's configuration guide for the versions in use. To test: two RoCE hosts on a switch with configurable PFC; run ib_write_bw with and without PFC on the RoCE priority while a third and fourth host send to the same receiver, and compare with the model.

Where the analogy breaks


    

  • A courier's round trip is the same distance both ways. A network path need not be symmetric; RTT / 2 is a convention, not a measurement of one direction.
    • 

  • Timing a lorry-load ignores what happens to the letters. A bandwidth test of RDMA WRITE says nothing about whether the receiving program noticed the data.
    • 

  • "Bad days" for a courier are rare and random. Tail latency in computers is often systematic (a timer interrupt every few milliseconds, a garbage collector, another tenant on the machine) and can be removed once found.
    • 

  • Warm-up for a courier happens once. On a computer, "cold" can return: after a page is swapped out, after the CPU lowers its frequency when idle, after another program evicts the caches.
    •

Summary


    

  • Latency (one message in flight, RTT / 2) and bandwidth (many in flight, bytes per second, message rate) are separate tests.
    • 

  • Warm up, fix the size, sweep sizes, report min/median/p99/max, repeat whole runs, record everything, measure the release build.
    • 

  • In this build the minimum latency was stable while small-message medians varied with scheduling; an alpha–beta fit of those medians gave an α of 12.88 µs in one run and 19.95 µs in another: not quotable.
    • 

  • perftest applies the same protocol to RDMA operations; it was not installed here, and its flags are listed as unverified.
    • 

  • RoCE needs a large enough path MTU and a lossless class: the model shows a pair with path MTU 1024 and PFC off at 76.9 % of fair-share goodput, versus 98.6 % when both are fixed.

Forensic lab answer key


Observation (the diff). A-B: Ethernet MTU 9000, RoCE path MTU 4096, PFC on for the lossless class. C-D: Ethernet MTU 1500, path MTU 1024, PFC off. Same QP DSCP (26), same switch lossless DSCP (26), ECN off on both, incast 4 on both R2.


Mechanisms. (1) Path MTU 1024: 58 bytes of headers per 1024 bytes of payload, 94.6 % payload share versus 98.6 %. Path MTU 1024 is forced by Ethernet MTU 1500: the next RDMA MTU, 2048, needs an IP packet larger than 1500 bytes (F5-35's table: 1024 is the largest path MTU that fits Ethernet MTU 1500) R3. (2) PFC off: the RoCE traffic is marked for the lossless class (DSCP 26) but the class is not lossless, so during incast the switch drops; each drop triggers go-back-N. The model counts 379 NAKs and 46238 resent packets (379 × 122). Goodput = 200000 × 1024 / (246238 × 1082) = 76.9 %.


Hypotheses. H1: lossy class plus go-back-N under incast (strong: the C-D benchmark ran under incast, A-B with PFC does not lose; model: PFC on alone raises C-D to 94.6 %). H2: small path MTU (real but smaller: MTU 4096 alone gives 93.0 %, and it also reduces the go-back-N window). H3: "RoCE is inherently slower than TCP" (against: A-B is faster than TCP on the same fabric). H4: wrong DSCP marking (ruled out: QP DSCP equals the switch's lossless DSCP on both pairs).


Separating experiment. Model: the whatif lines (93.0 % MTU only, 94.6 % PFC only, 98.6 % both). Real fabric: rerun the C-D benchmark without the incast senders (if it then matches A-B apart from header overhead, losses are the cause); then enable PFC on the RoCE priority on C-D's switch ports and rerun under incast; then raise the Ethernet MTU on C, D and the switch ports and rerun. Watch the adapters' retransmission and out-of-sequence counters and the switch's drop and pause counters (counter names depend on the products, not verified).


Recommendation. Do not revert: fix the configuration. First enable PFC (and preferably ECN-based congestion control, D2) for the RoCE priority on C, D and their switch ports, matching A-B; then raise the Ethernet MTU to 9000 end to end so the path MTU can be 4096. Confirm with the same incast benchmark and with zero drops on the lossless priority. Add the configuration diff to the cluster's acceptance test.
