Story hook

Wei and Amara live in different towns and keep a shared notebook: every evening Wei sends Amara the day's new lines. Each note goes through the post office. Wei walks to the counter and waits his turn. The clerk copies the note onto the office's own form, stamps it, sorts it and sends it. In Amara's town another clerk takes it out of the bag, copies it into an envelope, and knocks on Amara's door. Amara stops cooking, opens the door, reads the note and copies the lines into her notebook. The road between the towns is fast; most of the waiting happens at the counters and at the door.

One day Amara gives a courier service a key that opens one shelf in her hall, and only that shelf. Now Wei hands his note to the courier at his own front door. The courier drives straight to Amara's house, checks the key against the shelf, and puts the note on it. Nobody copies the note on the way. Amara is not interrupted; she looks at the shelf when she wants to.

The post office is the operating system's network stack. The courier with the key to one shelf is an RDMA network card. This chapter measures what the counters cost, and asks when a courier is worth its price.

What you will be able to do

  • Explain where the time and the CPU work go when a message travels through the kernel's TCP stack: system calls, copies, protocol processing, and waking a sleeping thread.
  • Explain the three ideas RDMA combines: the transport protocol runs in the network card, the application talks to the card without a system call (kernel bypass), and the card moves data straight to and from application memory (zero copy).
  • Measure the cost of the kernel path on your own machine with a ping-pong over TCP and a polled shared-memory mailbox, and count system calls with strace.
  • Decide when RDMA is worth its costs (memory registration, connection state, network configuration, programming effort) and when a tuned TCP path is enough.
  • Diagnose a "TCP is too slow, we need RDMA" complaint whose real cause is in the application's use of TCP.
Jargon box
Kernel bypass
Simple words: a program talks to the network card directly instead of asking the operating system for every message. Analogy: handing the note to the courier at your own door instead of queuing at the post-office counter. Precise: a design in which the operating system sets up access once (memory, queues, permissions) and the application then submits and completes data transfers by reading and writing queue memory and device registers mapped into its address space, with no system call on the data path. D2 D3
Zero copy
Simple words: the bytes go from your memory to the wire, and from the wire into the other program's memory, without being copied into another buffer on the way. Analogy: nobody copies Wei's note onto a form; the courier carries the original. Precise: a transfer in which the device reads the payload by DMA directly from the sender's application buffer and writes it by DMA directly into the receiver's application buffer, so the CPU makes no intermediate copy; the buffers must stay valid and resident until the transfer completes. D2 D1
Transport offload
Simple words: the network card itself does the work of a protocol like TCP: numbering packets, acknowledging, resending. Analogy: the courier service, not Wei, makes sure the note arrives and fetches a receipt. Precise: implementing the reliable transport (segmentation, sequence numbers, acknowledgements, retransmission, ordering) in the network adapter's hardware and firmware instead of in the host operating system; InfiniBand and RoCE define such a transport. D1
One-sided operation
Simple words: an operation where only one computer's program takes part; the other computer's card does the work alone. Analogy: the note lands on Amara's shelf while Amara keeps cooking. Precise: an RDMA READ or RDMA WRITE (and atomic operations), which name a remote address and a remote key; the target adapter executes it against registered memory without the target application posting a request or receiving a completion. Two-sided operations (SEND matched with a posted RECEIVE) involve both programs. D1 D2
System call cost
Simple words: the time a program loses each time it asks the operating system to do something. Analogy: the wait at the counter, however short the road. Precise: the time and CPU work of entering the kernel, doing the requested work (here: copying bytes and running the protocol), and returning; plus, when a thread must wait, the cost of putting it to sleep and waking it up. Measured in this chapter as a difference between two paths, not as a property of any product. R1 R3
Nagle's algorithm
Simple words: a rule inside TCP that holds back a small piece of data while an earlier small piece is still waiting for its acknowledgement, so it can send them together. Analogy: the clerk keeps your second short note until the first one's receipt comes back, to save stamps. Precise: a sender-side TCP rule that delays sending a less-than-full segment while previously sent data is unacknowledged; combined with a receiver that delays its acknowledgements, a write-write-read pattern can stall for the delayed-ACK time; disabled per socket with the TCP_NODELAY option. D4 D5 R4

Terms from earlier courses used here: RDMA (remote direct memory access), queue pair, completion queue and InfiniBand and RoCE (HW205, F1-53); DMA, descriptor ring and doorbell register (F1-52); polling (HW204); median and percentile (MA202). "Kernel" in this course means the operating-system kernel, not a GPU kernel.

Layer 1 — the kid explanation

Analogy

Mapping, proposed for the F5 analogy registry (NOTES.md): the town post office = the operating system's network stack; queuing at the counter = a system call; copying the note onto the office's form = copying bytes into a kernel buffer; the knock on Amara's door = waking a sleeping program; the courier service = an RDMA network card; the key that opens only one shelf = a remote key for one registered memory region; checking the shelf = polling; the courier's receipt to Wei = a completion. The registered F5 warnings still hold: letters can be delayed, and the road can be cut.

Sending a message through the operating system is safe and flexible: the post office checks everything, and any program can use it. But every message pays at the counter twice, once in each town, and is copied twice. For long letters, the road is the slow part. For short notes sent thousands of times a second, the counters are the slow part.

RDMA moves the post-office work into the courier service, which is a special network card. After a careful set-up, the program hands work to the card directly, the card picks up the bytes from the program's own memory, and the other card puts them on the agreed shelf. Nothing is copied, nobody queues, and the other program is not interrupted. The price: someone has to hand out keys, keep the shelves reserved, and build roads where couriers never lose a parcel.

Layer 2 — the student explanation

What happens to one TCP message

In DS201 (F5-04, F5-05) you used TCP through sockets. TCP runs in the operating-system kernel: the kernel keeps each connection's send and receive buffers, its sequence numbers and its timers D4. For one small request and its reply between two programs, the following work happens, all of it on CPUs:

  1. System call to send. The sender calls send; the CPU enters the kernel D5.
  2. Copy 1. The kernel copies the bytes from the application's buffer into kernel memory attached to the socket. The application may reuse its buffer as soon as send returns, which is only possible because of this copy D4.
  3. Protocol processing. The kernel builds TCP and IP headers, keeps the data for possible retransmission, and hands a descriptor to the network driver, which rings the NIC's doorbell (F1-52) D4.
  4. Receive side. The receiving NIC writes the packet into a kernel buffer by DMA and raises an interrupt (or the kernel polls it); the kernel processes the IP and TCP headers and places the data in the socket's receive buffer D4.
  5. Wake-up. The receiving thread is usually asleep inside recv. The kernel marks it runnable; the scheduler must run it on a CPU.
  6. Copy 2. recv copies the bytes from the kernel buffer into the application's buffer and returns D5.

The reply repeats all six steps in the other direction. The lab counts this: with both programs as threads of one process on the loopback interface, the TCP path made 12,800 sendto and 12,831 recvfrom system calls for 3,200 round trips at each of two sizes, that is, two system calls per message per side, four per round trip R3. The shared-memory path made none on its data path: its whole run, start-up included, made 97 system calls R3.

What RDMA changes

RDMA (remote direct memory access) combines three ideas, each of which removes one part of the kernel path D1 D2:

  • Transport offload. The reliable transport (packet sequence numbers, acknowledgements, retransmission) is defined by the InfiniBand architecture and executed by the adapter, not by the host's kernel D1. Steps 3 and 4 move off the CPU.
  • Kernel bypass. After a set-up phase that does use the kernel (opening the device, registering memory, creating queues), the application submits work by writing work requests into queues and ringing a doorbell, and learns about finished work by reading a completion queue. The installed rdma-core header shows that ibv_post_send, ibv_post_recv and ibv_poll_cq are static inline functions that call the device's operations directly from the application D3; whether a particular provider makes a system call inside them is a property of that provider (see the unverified box below). Steps 1, 5 and the system-call part of 6 go away.
  • Zero copy. The adapter reads the payload by DMA from the application's registered buffer and the remote adapter writes it by DMA into the remote application's registered buffer D2. Copies 1 and 2 go away. The price is that the buffer must stay registered and resident (pinned) and must not be reused until the adapter reports completion.

On top of these, RDMA offers one-sided operations: an RDMA WRITE or RDMA READ names a remote address and a remote key, and the remote adapter executes it without the remote application doing anything for that transfer D1. This is the courier putting the note on the shelf while Amara keeps cooking. The remote application only learns that data arrived if it looks (polls a flag in memory) or if the sender also sends a message that consumes a receive request (F5-36).

Not verified — check before relying on this

That the data-path verbs of a given provider (for example a particular vendor's user-space driver, or the Soft-RoCE driver) execute without any system call, and exactly what the kernel does at set-up time, was not checked in this build: no RDMA device was available and the rdma-core documentation and provider sources were not opened. Check the rdma-core documentation and the provider's source for the rdma-core version recorded in the dossier (the build had the Ubuntu packages libibverbs-dev and ibverbs-providers version 50.0-2ubuntu0.2, R2 of F5-36), and trace a real run with strace on hardware.

Layer 3 — the engineer's depth

Where the benefit comes from, and how big it can be

Treat the time of one operation as a sum: t = thost,send + twire + thost,recv + tapp. RDMA shrinks the host terms; it does nothing for the wire term (signals still travel at the speed the cable allows, and switches still forward) and nothing for the application's own work. The same Amdahl-style reasoning you used for parallel speed-up (SP203, HW301) bounds the gain: if the host network stack is 40 % of a request's time, removing all of it makes the request at most 1/0.6 ≈ 1.67 times faster. Measure the split before buying hardware. The lab's two paths are a crude but honest split: on the build machine, at least 3.65 us of a 4.13 us minimal TCP round trip was host path R2; for a service whose handler takes 500 us, removing that is invisible.

The gain has three different faces, and a design should say which one it wants:

  • Latency for small messages: fewer and cheaper steps per message. This is where Figure 2's gap matters.
  • CPU efficiency for large transfers: with transport offload and zero copy, the CPUs at both ends spend almost nothing per byte, so they are free for the application. In the lab, the CPU copies 64 KiB several times per round trip; at high rates, those copies consume memory bandwidth and cores.
  • Tail latency and jitter: a busy-polling receiver never sleeps, so the "wake the thread" step (35.40 us median versus 4.13 us minimum for TCP in R2) disappears. This is mostly a property of polling, not of RDMA; it costs a CPU core that spins (F5-38 measures the trade-off).

What RDMA costs

Every item below is a reason a team may stay with TCP. Each returns in a later chapter.

  • Memory registration. Buffers must be registered with the adapter before use; registration pins pages and fills the adapter's translation tables, and it is slow compared with a single transfer, so applications register large pools once and reuse them D2 (F5-36, F5-38).
  • Connection state. A reliable connection is a queue pair at each end with its own state in the adapter; many-to-many communication among thousands of processes means many queue pairs D1. Datagram transports and shared receive queues exist to limit this (F5-36).
  • The network must cooperate. InfiniBand is a separate fabric with its own switches and a subnet manager. RoCE runs on Ethernet but expects the network to be configured so that RDMA traffic is rarely dropped, because the adapter's recovery after a drop is expensive (F5-35, and the course's forensic lab in F5-37) D1 D2.
  • Security and isolation. A remote key is a capability: whoever holds it and can reach the queue pair can write that memory region. Keys, protection domains and access flags must be designed, not copied from examples (F5-36).
  • Programming effort. The application now manages buffers, queues, completions and flow control (a SEND that finds no posted receive at the target is an error condition, not a wait), the work the kernel did for you before.
  • Observability. Tools that watch the kernel (strace, socket statistics, packet capture on the host) see little of the data path; you need adapter counters and switch telemetry instead.

Alternatives on the same spectrum

Kernel bypass and zero copy are not unique to RDMA. User-space packet-processing frameworks poll NIC rings from user space without a transport in hardware; the Linux kernel itself offers zero-copy send and receive paths for sockets in some cases; shared memory between processes on one machine (your mailbox) is the extreme case of both. Which one to use depends on whether the peer is on the same machine, whether you control the network, and whether you need a reliable transport in hardware. These alternatives are named here only as directions for reading; their interfaces were not opened in this build, and F5-38 compares the ideas with code you can run.

How the hardware actually does it

An RDMA adapter is a PCIe device (F1-45) built around the same structures as the NIC of F1-52: queues of descriptors in host memory, doorbell registers that the host writes to say "new work", DMA engines that read and write host memory, and completion entries written back to host memory. Two differences make kernel bypass possible D1 D2. First, the queues and a doorbell page belong to one application: the kernel maps them into that process's address space at set-up, so the process can post work with ordinary memory writes. Second, the adapter keeps its own table of registered memory regions with their keys, permissions and address translations, so it can check every access and translate application virtual addresses to physical pages without asking the CPU. The transport state of each connection (next packet sequence number, unacknowledged packets, retry counters) lives in the adapter too.

Not verified — check before relying on this

Untested on hardware. Nothing in this chapter ran on an RDMA adapter: the build container has none (no /sys/class/infiniband, and ibv_get_device_list returned 0 devices, R1 of F5-36). The description of where queues, doorbells and translation tables live is the chapter's reading of the InfiniBand architecture's model of a channel adapter, written without opening the specification; how a specific adapter implements it (on-chip caches of translations, how many queue pairs it holds before performance drops, how its doorbells are mapped) is in that adapter's programming documentation, not checked here.

Worked example

How much does one trip through the kernel cost on the build machine, and what would removing it buy a key-value service?

  1. Per round trip. Minimum TCP round trip 4.13 us, minimum mailbox round trip 0.48 us R2. Difference: 4.13 − 0.48 = 3.65 us. The minimum is the right statistic here: it is the round trip in which no thread had to be woken, so it isolates the system calls, copies and protocol work.
  2. Per system call. strace counted 4 system calls per round trip on the TCP path (12,800 sendto for 3,200 round trips × 2 sizes × 2 sides = 12,800) R3. 3.65 us / 4 ≈ 0.91 us per send-or-receive, including its copy and its share of the protocol work. (strace itself slows each call down, so its timing columns are not used.)
  3. Per message rate. A single thread that does nothing but these system calls could not exceed 1 / 3.65 us ≈ 274,000 round trips per second on this machine, before doing any useful work.
  4. For a service. Suppose a key-value store answers a GET in 2 us of CPU work and the network round trip outside the hosts takes 3 us. Through TCP at the best case: 3.65 + 2 + 3 = 8.65 us. With the host path removed entirely: 2 + 3 = 5 us, a factor of 1.73. If the GET takes 200 us of work, the same change gives 206.65 / 203 ≈ 1.02: not worth a new network.
  5. The median view. With the median instead of the minimum, the TCP path took 35.40 us against 0.64 us R2: almost all of the typical cost was waking sleeping threads. A TCP service that busy-polls its sockets would recover much of that without RDMA; a fair comparison changes one thing at a time.

The "2 us" and "3 us" in step 4 are invented inputs for the exercise, not measurements; only the 3.65 us comes from the run.

Where the analogy breaks


    

  • A courier who finds the shelf full or the key wrong can phone Wei. An RDMA WRITE that breaks the rules fails at the sender with an error completion, and the connection stops working until it is reset (F5-36); there is no conversation.
    • 

  • In the story Amara "notices the note when she looks". With RDMA she also has to know when the whole note has arrived: data written by a one-sided operation gives the target program no signal, so protocols write a flag last or send a separate message (F1-53, F5-36).
    • 

  • Post offices in the story are slow because clerks are slow. The kernel is not slow at any one step; its cost is many small steps per message, each fast, plus the copies, and the cost depends on message size, CPU and load in ways the story cannot show. Measure it (Figure 2).
    • 

  • Couriers can drive on any road. RoCE needs the Ethernet network to be configured for it, and InfiniBand needs its own network; the "road" is part of the design (F5-35).
    • 

  • Amara's key opens one shelf forever. Real remote keys are valid until the region is deregistered, and a stale key held by a peer is a real bug class (HW205's "stale key" forensic lab, F1-53).
    •

Summary


    

  • A TCP message pays, on each side, system calls, a copy, protocol processing on the CPU and usually a thread wake-up; on the build machine this was at least 3.65 us per 64-byte round trip, and the median was dominated by wake-ups.
    • 

  • RDMA combines transport offload, kernel bypass and zero copy, and adds one-sided operations that do not involve the target program.
    • 

  • RDMA helps small-message latency, CPU cost per byte and jitter; it does nothing for the wire or the application's own work: apply Amdahl-style reasoning before deciding.
    • 

  • Its costs are memory registration and pinning, connection state in the adapter, a network configured for it, key management, and more complex programs.
    • 

  • Busy polling removes wake-ups but spends a core; removing the kernel does not remove copies.
    • 

  • Measure the build you ship, on a recorded machine, with minima, medians and tails; one number is not a measurement.
    • 

  • Before blaming TCP, check how the application uses it: a write-write-read pattern with Nagle's algorithm can cost tens of milliseconds.
    •

Forensic lab answer key


Observation. Per request the client makes two sendto calls, 8 bytes ("REQ…") then 56 bytes, and one recvfrom of 8 bytes. In requests 2 and 3, the server's recvfrom(5, …) first returns only the 8 header bytes, and the next recvfrom that completes with the 56 body bytes resumes after 0.041713 s and 0.043288 s R4. The client's second sendto returned at once: the body was accepted by the client's kernel but not delivered for about 42 ms.


Hypotheses. (1) The kernel's TCP path is slow: ruled out, the same machine does a full 64-byte round trip in microseconds (R2), and request 1 took 0.277 ms. (2) The server is slow to process: ruled out, the server's call is blocked waiting for bytes, not working. (3) The client's TCP holds back the second small segment while the first is unacknowledged (Nagle's algorithm), and the server's TCP delays its acknowledgement of the header because it has no reply to piggy-back it on yet (delayed ACK); the body leaves only when the delayed ACK timer fires D4. This matches the gap and the configuration line TCP_NODELAY=0. (4) Request 1 escapes because no earlier data was unacknowledged when its body was written, or because the receiver acknowledged promptly at the start of the connection (the exact rule for the first segments is in D4 and the Linux tcp(7) page, not verified here).


Root cause. The client writes one logical message with two system calls, and the socket uses the default TCP_NODELAY=0: the write-write-read pattern meets Nagle's algorithm and delayed acknowledgements.


Fix and verification. Either send header and body in one call (writev, or build the message in one buffer), or set TCP_NODELAY on the client socket. Both were run R4:






The median fell from 43.975 ms to 0.033 ms and 0.031 ms respectively. Prevention. A latency test in CI with an alert on the median; a code-review rule "one message, one write"; set TCP_NODELAY on request-reply sockets as F5-09's library and Listing 1 do.


Reply to the design document. "The 44 ms is a delay caused by how the client writes to TCP, not by the TCP stack; with one write per request the same service answers in about 31 us on the same machine. Re-measure the host-path share after this fix before considering RDMA."
