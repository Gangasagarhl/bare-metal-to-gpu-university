Story hook

Amara's town post office is careful: every letter is handed over the counter, the clerk copies the address into a ledger, puts the letter into the office's own bag, and later hands it to the courier. It is safe and fair to everyone, and it takes a clerk's time for every letter. The courier from F5-34 skips all of it: he has a key to Amara's shelf and takes the letter himself. No counter, no clerk, no second bag.

But the courier only works if two things hold. The shelf must not move while he has the key (if Amara rearranges her house, he takes the wrong thing). And someone must notice when a parcel arrives. Amara can stand at the window all day watching for the courier, which is quick and tiring, or nap and ask to be woken, which is restful and slow. Her neighbour tried to have both by napping "for one second" between looks out of the window. It did not work the way he expected.

This chapter measures each of these ideas on one computer, where it can be run, and then sets the course project.

What you will be able to do

  • Measure what a kernel data path costs in system calls and copies, and what a shared-memory bypass path saves, with strace and a timing harness.
  • Explain zero copy and why it requires registered (pinned) memory, and check a process's locked-memory limit.
  • Choose an idle policy (busy poll, block, spin-then-sleep) and predict its latency and CPU cost.
  • Diagnose a "kernel bypass made it slower" case from latency, CPU and system-call evidence.
  • Plan the course project: an RDMA-based replicated log append benchmark with a correct protocol and an honest measurement.
Jargon box
Data path and control path
Simple words: the data path is the work done for every message; the control path is the set-up done once or rarely. Analogy: handing over each letter, versus signing up with the courier company. Precise: in kernel-bypass designs the control path (opening the device, registering memory, creating and connecting queue pairs) goes through the kernel with system calls, while the data path (posting work requests, ringing doorbells, polling completions) runs in user space without system calls. D1 R2
Locked-memory limit (RLIMIT_MEMLOCK)
Simple words: the most memory a process is allowed to pin so that it cannot be swapped or moved. Analogy: how many shelves you may bolt to the wall. Precise: the per-process resource limit that bounds memory locked with mlock and, on Linux, memory pinned by RDMA registration for unprivileged processes; read with getrlimit(RLIMIT_MEMLOCK) (soft and hard values). D2 R3
Idle policy
Simple words: what a program does while it waits for the next message: keep checking, or sleep. Analogy: stand at the window, or nap and ask to be woken. Precise: the choice between busy polling (lowest latency, one core fully used), blocking on a notification such as a completion channel, eventfd or futex (no CPU while idle, a wake-up latency per message), and hybrids that spin for a bounded time and then block; a timed sleep in a polling loop is a poor hybrid because sleep durations are not precise. R4 D2
Registration cache
Simple words: a library's memory of which buffers are already registered, so it does not register them again. Analogy: a list of shelves that already have a courier key. Precise: a cache in communication libraries (MPI implementations, UCX, NCCL) mapping user buffers to existing memory regions, to avoid the cost of ibv_reg_mr per message; it must be invalidated when memory is freed or remapped. D3
Replicated log append
Simple words: adding a record to the end of a log that is kept as identical copies on several machines. Analogy: Amara writes each diary entry and posts copies to two friends; an entry counts once most of the copies have arrived. Precise: the leader writes entry i to the log of each follower, and the entry is committed when a quorum (for example, a majority including the leader) has stored it; the operation underneath primary-backup replication and consensus protocols (DS301). D4

Terms from earlier: kernel bypass, zero copy and system call cost (F5-34); system call and context switch (OS201); SPSC ring buffer and false sharing (SP203); polling (HW204); adaptive spinning (OS303); pinned (page-locked) memory (HW301); NUMA (HW203); memory region and registration (HW205); quorum and primary-backup replication (DS301).

Layer 1 — the kid explanation

Analogy

Mapping (proposed): kernel = the post office counter and its clerk; system call = queuing at the counter; kernel copy = the clerk putting your letter into the office's own bag; kernel bypass = the courier collects from your shelf with his key; zero copy = he takes the original, not a photocopy; pinned memory = a shelf bolted to the wall; RLIMIT_MEMLOCK = how many shelves you may bolt down; busy polling = standing at the window; blocking = napping and asking to be woken; "sleep 1 µs between looks" = a nap that always lasts much longer than you asked.

Going through the counter costs a little every time; skipping it saves that every time. But skipping it means you must be ready yourself: your shelf must stay put, and you must keep watching for the courier, because no clerk will come and wake you. Watching all the time is quick but tiring; napping is restful but slow. There is no free choice, only a trade.

Layer 2 — the student explanation

What the kernel path costs, measured

Listing 1 sends 64-byte messages between two processes on one machine, first through a Unix-domain socket pair, then through two shared-memory rings (Listing 1's header, spsc_ring.hpp, is the SPSC ring of SP203 placed in memory mapped with MAP_SHARED before fork). It measures 20000 ping-pongs and a stream of 200000 messages one way. The -O2 build printed R1:



Running each path under strace -f -c counts the system calls of both processes (R2). The socket path made 240003 write and 240005 read calls: one per message per direction (20000 + 20000 for the ping-pong, 200000 for the stream, plus a final byte and a few at start-up). The ring path made 79 system calls in total, all for start-up (loading, mmap, clone for the fork, two write calls for the printed lines) and none per message:






That is kernel bypass on one machine: the control path (create the shared mapping, fork) uses the kernel once; the data path (copy into a slot, publish with an atomic store, poll with an atomic load) never does. On the stream test the ring delivered 56.49 million messages per second against 0.87 million for the socket: a factor of about 65, because each socket message costs two system calls and two copies through a kernel buffer, while a ring message costs one 64-byte copy and two atomic operations.


The ping-pong medians need care. The -O2 run's socket median was 24.27 µs; the sanitizer run (R1, ring_ipc.out) printed 4.50 µs for the same path, although sanitizers only add work. As in F5-37, small-message socket latency here is dominated by whether the sleeping peer process is woken on an idle CPU or must be scheduled; the ring's ping-pong (0.75 µs and 1.13 µs) is stable because neither process ever sleeps. The figure to quote is the system-call count, which does not depend on scheduling.


Zero copy and why memory must be pinned


A socket write copies the user's bytes into kernel memory, so the application may reuse its buffer at once. A zero-copy interface instead passes a descriptor (address and length) and lets the device read the bytes where they are (F5-34). Listing 2 shows what the copy costs on this machine: handing over 500 messages of 1 MiB took 31.55 ms with a copy each time (16.62 GB/s of copying) and 0.49 ms by descriptor (the "device" here touches one byte per 4 KiB page) R3:




Zero copy has two conditions. First, the device must be able to find the buffer's physical pages and they must not move or be swapped out while the device uses them: this is what registration does for RDMA, by pinning the pages and giving the adapter their translations (F5-36; HW301 for the GPU equivalent) D1. Pinned memory counts against the process's locked-memory limit; in the build container that limit is 8388608 bytes (8 MiB) soft and hard, and mlock of 1 MiB succeeded (R3). The process ran as user id 0, which may be allowed to exceed the limit; an ordinary user registering more than 8 MiB would need the limit raised by the administrator D2. Second, the application must not touch the buffer until the device is done: the buffer-ownership rule of F5-36 (a buffer belongs to the adapter until its completion).


Not verified — check before relying on this
That RDMA registration by an unprivileged process is charged against RLIMIT_MEMLOCK, how privileged processes are treated, and whether on-demand paging (ODP, a feature of some adapters that avoids pinning) changes this, were not checked: they need the Linux kernel's RDMA documentation and the adapter's manual (D1, D2). The build only shows the limit's value and that mlock works (R3). How the limit is raised for a service (shell limits, service manager settings, container runtime settings) varies and is not shown here.


Who notices the message: idle policies


Without the kernel on the data path, nobody wakes a waiting process when a message arrives. The program must look. Three policies:


    

  • Busy poll: check in a tight loop. Lowest latency; one core at 100 % even when idle. The ring path of Listing 1 and waitOne in F5-36 do this.
    • 

  • Block on a notification: ask the kernel to wake you (for verbs, a completion channel; for shared memory, an eventfd or a futex). No CPU while idle; each wake-up costs a system call and a scheduling delay, the very costs bypass was meant to remove.
    • 

  • Spin, then block: poll for a bounded time (a few microseconds, or about the expected message gap), then arm the notification and block. Good latency under load, low CPU when idle (adaptive spinning, OS303).
    • 



A fourth, tempting policy, "poll, and sleep a little when empty", is the subject of the forensic lab.



Layer 3 — the engineer's depth


Why the ring is correct and fast


The ring (header lines 17–61) has one producer and one consumer. The producer writes a slot and then stores head with release order (line 48); the consumer loads head with acquire order (line 55) and only then reads the slot. Release/acquire guarantees the consumer sees the slot's bytes written before the index that publishes them (SP203). head, tail and the slots are each aligned to 64 bytes (lines 19–21) so the producer's and the consumer's index writes do not share a cache line (false sharing). The atomics must be lock-free (line 23), or two processes could not share them through plain memory. An RDMA adapter uses the same pattern with different actors: the program writes a descriptor and then a doorbell; the adapter writes a completion entry and then makes it visible, and ibv_poll_cq reads it D1.


Why "sleep 1 µs" is not 1 µs


A timed sleep is a system call (clock_nanosleep in R4's strace), which deschedules the thread and sets a timer; when the timer fires, the thread must be scheduled again. The forensic program's server asked for 1 µs and the run shows the consequence: 10932 clock_nanosleep calls in a run with 2000 requests (2000 of them are the client's deliberate 200 µs pauses between requests, line 145; the rest are the server's idle sleeps), a median round trip of 40.78 µs instead of 1.09 µs, and a p99 of 2105 µs R4.


Not verified — check before relying on this
The reasons a 1 µs sleep lasts tens of microseconds were not measured in this build: Linux's timer slack (a per-thread allowance that lets the kernel delay timer expiry to batch wake-ups; the author recalls a default of 50 µs for normal threads, adjustable with prctl(PR_SET_TIMERSLACK)), the scheduler's wake-up latency, and the CPU's idle-state exit latency. Check prctl(2) and the kernel's timer documentation for the version in use, and measure the actual sleep length on your machine (lab step 4).


The same trade-offs on an RDMA adapter


    

  • Polling the CQ gives the lowest latency (the F5-36 ping-pong polls); completion channels (ibv_create_comp_channel, ibv_req_notify_cq, ibv_get_cq_event, all declared in the installed header) give interrupt-driven waiting at the cost of a system call and a wake-up per event, and need the "arm, then poll again" sequence to avoid losing a completion that arrived while arming D1 D2.
    • 

  • Registration cost moves the copy's cost to set-up time. Programs register pools once; libraries keep a registration cache; a cache that misses on every message (fresh buffers from the allocator each time) can make RDMA slower than copying into a pre-registered bounce buffer for small messages D3.
    • 

  • NUMA placement: the adapter sits on one CPU socket's PCIe lanes; a buffer or a polling thread on the other socket adds an interconnect hop to every DMA and every poll (NUMA, HW203).
    • 

  • Zero copy across the whole path needs the data to be produced in registered memory: copying it there first is a copy again. For GPUs, GPUDirect RDMA registers GPU memory so the adapter reads it directly (milestone F5; DS402) D3.
    • 



Other kernel-bypass systems


RDMA is one of several designs that move the data path to user space: user-space packet processing frameworks that map a NIC's descriptor rings into a process and poll them, user-space storage drivers that poll NVMe queues, and io_uring, which keeps the kernel but replaces per-operation system calls with shared submission and completion rings. All of them share this chapter's structure: shared rings, descriptors instead of copies, pinned or registered memory, and an explicit idle policy D2. (Names given from general knowledge; their documentation was not opened in this build.)



How the hardware actually does it


On one machine, Listing 1's bypass works because both processes' page tables map the same physical pages (MAP_SHARED) and the CPU's cache coherence makes a store on one core visible to a load on another. The cost of a ring message is a 64-byte copy and the transfer of a few cache lines between cores. An RDMA adapter extends this across machines: the doorbell page of the adapter is mapped into the process; registered pages are translated by the adapter's own tables; DMA reads and writes go over PCIe into host memory and become visible to the CPU through the platform's coherence for device writes D1.


Not verified — check before relying on this
Untested on hardware. No RDMA adapter was available; every RDMA statement in this chapter is the author's reading of D1–D3 (title only) and the installed header. The one-machine measurements (R1–R4) are real but are about shared memory between processes, not about RDMA. To test the RDMA side: on two RDMA hosts, run the F5-36 ping-pong with polling and with a completion channel, and record latency and CPU use for both, with the adapter's NUMA node and the polling core recorded.



Worked example


How much CPU does a message cost on each path, and what does it buy? From R1 and R2 (-O2):


    

  1. Socket stream: 0.87 million messages/s, each with one write by the sender and one read by the receiver: 1.74 million system calls per second across two processes, about 1.15 µs of wall time per message. strace attributed 1.43 s to 240003 writes (about 6 µs each under tracing; strace itself slows every call, so this is an upper bound, not a cost).
    2. 

  2. Ring stream: 56.49 million messages/s: 17.7 ns per message, which is a 64-byte copy, an acquire load and a release store on each side, and the transfer of cache lines between cores.
    3. 

  3. Ratio: 56.49 / 0.87 ≈ 65. For 64-byte messages, almost all of the socket path's cost is per message, not per byte.
    4. 

  4. The price: both ring processes spin. In the stream test this costs nothing extra (they are busy anyway); in a service with requests 200 µs apart (forensic lab) a spinning server burns 97 % of a core to answer in 1.09 µs.
    5. 



Will this registration fit? A service wants to register 64 send buffers and 64 receive buffers of 64 KiB each, as an ordinary user, under the container's limit of 8388608 bytes. 128 × 65536 = 8388608 bytes: exactly the limit, so any other locked memory (or a second region) makes registration fail. Raise the limit or register one pool and carve buffers from it with headroom.

Where the analogy breaks


    

  • A courier with a key can take anything from the shelf. A memory region's access flags restrict what a remote adapter may do, and its bounds are checked on every operation (F5-36).
    • 

  • "Bolting a shelf to the wall" sounds permanent. Pinning lasts until deregistration or munlock; the danger is the opposite of the analogy: forgetting to release it, until the limit is reached.
    • 

  • Standing at the window costs only the watcher's time. A spinning core also costs power, heat and a core another program could have used, and on a shared machine it can slow its neighbours.
    • 

  • On one machine, "bypass" in Listing 1 means no kernel at all. With RDMA the kernel is still on the control path (device open, registration, QP creation), and the adapter, not another process, does the work at the other end.
    •

Forensic lab


Scenario — "kernel bypass made it slower". A team replaced the socket transport of an internal two-process service with shared-memory rings ("version 2"), after a benchmark showed ring round trips under 1 µs. To avoid one core spinning at 100 % all day, a reviewer asked for "a tiny sleep when there is no work", and the server now sleeps 1 µs whenever its request ring is empty. In production, where requests arrive about every 200 µs, latency did not improve as promised: the median is tens of microseconds and the tail is in milliseconds. The ticket asks whether shared memory "is just slower on this hardware".

DS401 course project: an RDMA-based replicated log append benchmark


Goal. Build a leader and two followers that replicate an append-only log with one-sided RDMA WRITEs, and measure append latency (request to commit) and throughput honestly. The protocol of Figure 3 is a suggested starting point.


Functional requirements.


    

  1. Each follower registers a log ring with IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE and sends its address, length and rkey to the leader out of band; the leader checks the advertised access before the first append (F5-36's forensic lesson).
    2. 

  2. The leader appends fixed-size entries (header with term, index, length and a checksum; payload 64 B to 64 KiB) by RDMA WRITE into the next free slot of each follower, then signals the entry index (RDMA WRITE WITH IMMEDIATE, or a SEND on the same RC queue pair).
    3. 

  3. Followers acknowledge the highest index stored and return credits (free slots); the leader never writes into a slot whose credit it has not received.
    4. 

  4. An entry is committed when a majority (2 of 3 copies, counting the leader's) holds it; the leader reports commit latency per entry.
    5. 

  5. Every completion's status is checked; on an error the leader logs the first error, marks the follower down, resets and reconnects its queue pair, and resends missing entries from the follower's last acknowledged index.
    6. 

  6. A baseline implementation of the same protocol over TCP (DS201 sockets) on the same hosts.
    7. 



Quality requirements. Followers' logs are byte-identical to the leader's for all committed entries (checked by a test); the measurement follows F5-37 (release build, warm-up, percentiles, repetitions, recorded configuration dump including path MTU and lossless settings); the raw fabric is verified first with perftest (curriculum milestone F5 acceptance test: raw RDMA bandwidth within 10 % of the adapter's line rate, recorded).


Constraints. Hardware: three hosts with RDMA adapters on one InfiniBand or RoCE network, or three hosts or virtual machines with Soft-RoCE (results then labelled "Soft-RoCE"). Without either, the model track: implement the protocol on the toy verbs model of F5-36 (correctness and fault tests) and on the shared-memory rings of this chapter (one process per node, for timing), graded on correctness and analysis with every number labelled "model" or "shared memory, not RDMA". Time: about 30 hours.


Deliverables. Code with build instructions; tests (byte-identical logs, a follower that stops consuming makes the leader stall rather than overwrite, a follower registered without REMOTE_WRITE is refused at set-up, a killed follower is caught up after restart); a report of at most six pages with plots of commit latency percentiles and appends per second against entry size, batch size and number of followers, RDMA against TCP; a five-minute demo.


Milestones. M1 (week 1): the F5-36 ping-pong runs on the project hosts, and perftest results are recorded. M2 (week 2): one follower, RDMA WRITE plus signal plus acknowledgement, with credits. M3 (week 3): two followers, majority commit, error handling and catch-up. M4 (week 4): benchmarks, TCP baseline, report and demo.

Forensic lab answer key


Observation. As deployed (-O2): minimum round trip 0.98 µs (the ring path works when the server happens to be awake), median 40.78 µs, p99 2104.99 µs, server at 19 % of one core R4. The sanitizer build shows the same pattern (median 65.42 µs, p99 3880.11 µs, 17 %). strace: 10932 clock_nanosleep calls dominate; 2000 are the client's 200 µs pauses, about 8900 are the server's idle sleeps. There are no read/write calls on the data path.


Hypotheses. H1 hardware or shared memory slow: against, the minimum is 0.98 µs and the busy-polling variant on the same machine gives a median of 1.09 µs (R4, bypass_spin.out, below); R1's ring ping-pong median was 0.75 µs. H2 measurement error: against, the minimum and the spin variant use the same clock and code. H3 the idle policy: for, the median is far above the minimum, the tail is in milliseconds, and the only system call in the steady state is the sleep. H3 explains everything.


Mechanism. Requests arrive every 200 µs, so the server is almost always idle when a request comes and is inside a sleep. sleep_for(1 µs) is a clock_nanosleep system call: the thread is descheduled and is woken by a timer, later than asked (timer slack, wake-up and idle-exit latency; see the unverified box in Layer 3). The request waits for the sleep to end; occasionally the thread is not rescheduled for milliseconds (the p99). Bypass removed the kernel from the data path; the sleep put it back, with a timer in front.


Fix. Replace the sleep by spin-then-block: spin for a bounded time after each request, then block on an eventfd (or futex) that the client signals only when the server is blocked; or dedicate a core and busy-poll if the latency target justifies 100 % of a core. Prove it with the lab-step-5 curve at the production request gap: median and p99 near the busy-poll values, idle CPU near the block-only value.
