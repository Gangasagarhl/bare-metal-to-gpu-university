Story hook

Amara's team is building a house. Joon lays pipes, Farah runs the electric cables, and Amara plans the order of work. For three weeks everything goes well: each of them finishes their own part early. Then the day comes to close the kitchen wall. Joon's pipe runs exactly where Farah's cable box was supposed to go. Nobody was wrong in their own room. They were wrong between the rooms.

They agree on two new habits. First, before anyone builds, they draw where every pipe and cable crosses from one person's work into another's, with sizes, and they test those crossings first. Second, they finish one small room completely, with water from the tap, light from the switch and a door that closes, before they finish anything else. If the first room works end to end, the others are mostly repetition. If it does not, they learn it in week two instead of week ten.

This chapter is about running your final mega project, MP8, the way that team learned to build houses: crossings first, one working room early, and an honest record of how far along you really are.

What you will be able to do

  • Write an MP8 plan in which every milestone has an acceptance test, a three-point estimate, explicit dependencies and its review gate.
  • Identify the interfaces between the components you bring from earlier mega projects, and write a contract and a contract test for each before integrating.
  • Plan a walking skeleton: the thinnest end-to-end path through all components, working early.
  • Track plan against actual every week and re-forecast the end date from evidence, using Listing 1.
  • Diagnose hidden work and undeclared dependencies from a team's plan and its weekly log.
Jargon box
Mega project
Simple words: a long project that joins several things you built before into one system. Analogy: a whole house built by several trades. Precise: in this university, one of the eight capstones MP1–MP8: one to two semesters, alone or in a small team, with milestones, deliverables, a grading rubric and the review gates R0 to R4; each reuses curriculum milestones as building blocks and adds integration, scale and real-world constraints D1 §11.6.
Integration milestone
Simple words: a step whose test only passes when two or more parts work together. Analogy: the day the kitchen wall is closed over pipes and cables. Precise: an MP8 milestone that the learner defines and has approved at R1 D1 §11.6, MP8, whose acceptance test exercises a path crossing at least one interface contract between components; course definition.
Interface contract
Simple words: a written agreement about exactly what passes between two parts. Analogy: the drawing of where each pipe crosses the wall, and how wide it is. Precise: a versioned specification of the messages or calls between two components: names, types, units, ranges, ordering, error and timeout behaviour, and what happens with unknown fields; it is part of the design document and is owned by both sides; course definition, extending the design-document sections of F12-02.
Contract test
Simple words: a test that checks one side keeps the agreement, without the other side running. Analogy: checking the hole in the wall with the agreed pipe size before the plumber arrives. Precise: an automated test that feeds a component inputs (or reads its outputs) exactly as the contract specifies, including the edge cases the contract names (units, limits, unknown fields), so that both components can be tested separately and integration failures become contract violations with a named owner; course definition.
Walking skeleton
Simple words: the thinnest version of the whole system that works from end to end. Analogy: one finished room with water, power and a door, before the others. Precise: an early milestone in which every component exists (real or stubbed behind its contract) and one representative request travels the complete path and is checked by an automated end-to-end test; later milestones replace stubs with real components without changing the path; course definition (the term is used in software practice; no source opened in this build defines it, see the unverified box in Layer 2).
Hidden work
Simple words: work that is really happening but is not in the plan. Analogy: moving a pipe that nobody wrote on the job list. Precise: effort spent on a task that has no milestone, estimate or acceptance test in the plan, usually discovered as time a planned milestone spent blocked; it makes the plan's critical path and forecasts wrong; course definition, detected by Listing 1 from blocked lines.
Re-forecast
Simple words: a new estimate of the end date, made from how the project has really gone so far. Analogy: after three rooms took longer than planned, you expect the next rooms to take longer too. Precise: in Listing 1, a forward pass over the dependency graph in which finished milestones take their actual durations and unfinished ones their likely estimate multiplied by the observed ratio of actual to likely; a simple model with stated assumptions, not a prediction method validated by a source (Layer 3).

Terms from earlier chapters used here: critical path, three-point estimate and slack (F12-23); design document (F12-02); threat model (SS401); acceptance test (curriculum section 0); post-mortem and game-day (SE402, F12-18).

Layer 1 — the kid explanation

Analogy

Mapping (F12; proposed in NOTES.md): the house = the mega project; Joon's pipes and Farah's cables = components from earlier projects; the drawing of where pipes and cables cross the walls = interface contracts; checking each hole with the agreed pipe before the plumber comes = a contract test; the first finished room = the walking skeleton; moving a pipe nobody wrote on the list = hidden work; the inspector's visits = review gates (next chapter, F12-29).

Big projects rarely fail inside one person's part. They fail where the parts meet. So you write down the meeting points first, test them first, and make one thin path through everything work early. Then you keep an honest list of what is done, what is late and what nobody planned, and you change the plan when the list says so.

Layer 2 — the student explanation

What MP8 asks for

The MP8 card in the guide fixes the frame; you fill in the content D1 §11.6. Its milestones are: a proposal combining at least two goal areas; a design document and threat model, reviewed; integration milestones defined by you and approved at R1; an incident game-day and post-mortem; a public defence. Its deliverables are all of those plus a retrospective on what you would do differently. Its rubric weights technical depth (25 %), integration quality (20 %), evidence and testing (20 %), leadership and communication (20 %) and reflection (15 %). It passes through all five gates, R0 to R4, and a gate is passed only with written reviewer approval D1 §11.6.

Two things follow. First, most of the plan is yours to write: the card names only the frame, so the R1 review will judge whether your integration milestones are the right ones. Second, 40 % of the grade (integration quality plus leadership and communication) is about the parts between components and between people, which is exactly where the story hook's team failed.

Choosing the combination

The card's examples join two finished mega projects, for instance a drone ground station backed by the consensus-replicated service of MP2, or a robot whose perception kernel is your own CUDA or HIP code D1 §11.6. Choose with three questions:

  • What is new? MP8 is graded on integration. If the plan is "run MP2 and MP7 side by side", nothing is integrated. Name the new behaviour that only exists because the parts work together (in the worked example: an operator's mission survives the crash of a store replica).
  • What can you test without hardware you do not have? Every component should have a path that runs in an emulator or simulator, so that acceptance tests run in CI. Real hardware is a separate, later step (the curriculum's runbook rule) D2 §19.2.
  • What would you cut first? Write the cut list in the proposal. Scope is the only safe variable: acceptance tests are never skipped, weakened or postponed without explicit approval and a log entry D2 §0, §19.2.

Milestones that can be tested

The curriculum's rhythm applies unchanged: one milestone at a time, its ID in the branch name, log entry and commit; read first, plan second, tests before code where possible; done only when every listed acceptance test passes from a clean build and earlier milestones' tests still pass D2 §0, §19.3. For MP8 that means each line of the plan carries a test name that someone else could run. "Integration mostly working" is not a milestone; skeleton_end_to_end_with_stubs is, if the test exists.

Order the milestones so that risk is retired early. Contracts (M2) come before integration because they are cheap to change on paper and expensive to change in code. The walking skeleton (M3) comes before the real components are finished because it finds the mismatches that contracts missed. The riskiest behaviour (failover in the worked example) gets its own milestone with its own matrix of tests, before the game-day.

Contracts first

For every arrow that crosses between components, write a contract in the design document: the fields, their types and units, valid ranges, ordering and duplication rules, what happens with an unknown field or a newer version, timeouts and retries, and who owns changes. Then write contract tests on both sides. In the worked example, C-tel fixes that telemetry carries a sequence number and that a gap is reported, never silently filled; C-store fixes when a write counts as acknowledged. The final chapter of this course (F12-30) shows what happened when that second sentence was not tested.

Units deserve a special warning. A contract that says "timeout: 500" without a unit is two contracts, one per reader. SE301's design-document chapter made the same point with typed units (F12-02).

The walking skeleton

The skeleton is the thinnest end-to-end path: one waypoint written, stored and read back, with an automated test, and with stubs behind each contract where the real component is not ready. It forces every build system, configuration file, start-up order and contract to exist in week four instead of week ten. Later milestones replace stubs one at a time; after each replacement the skeleton test must stay green, which is the curriculum's "keep the previous milestone's tests green" applied to a whole system D2 §0.

The log, the design notes and the weekly review

Keep the curriculum's repository habits: a dated log entry per working session with milestone, documents read, decisions, what broke, root cause, fix, tests and commit; one design note per subsystem, updated whenever a decision changes D2 §0, §19.4. Add two MP8 files: the plan (Listing 1's input, kept in the repository) and a risk register (risk, likelihood and impact as judgements, the milestone that retires it, the owner).

Once a week, update the plan with done and blocked lines, run Listing 1, and write three sentences in the log: the forecast, what changed it, and what you will do about it. Blocked time is the most valuable line in the log. A milestone that waited three days on something is telling you about a dependency, and if that something is not in the plan, it is hidden work.

Layer 3 — the engineer's depth

The plan as a graph

A plan with dependencies is a directed graph. Listing 1 orders it topologically (Kahn's method: repeatedly take a milestone whose dependencies are all placed; anything never placed is in a cycle, which the program reports and stops on). A forward pass gives each milestone its earliest start, the latest finish among its dependencies, and its earliest finish, start plus duration. A backward pass from the end gives each milestone its latest finish that does not delay the end. Slack is latest minus earliest finish; milestones with zero slack form the critical path, whose length is the planned end R1. The method is arithmetic on the graph and is derived here; F12-23 introduced it with estimates.

Listing 1 runs the forward pass three times, with optimistic, likely and pessimistic durations. The resulting range (day 35 to 87 for the worked example) is wide on purpose and has no probability attached: every milestone at its pessimistic value at once is unlikely. F12-23's Monte Carlo schedule gives percentiles instead; use it for the R1 plan, and use Listing 1 for the weekly check, where the questions are simpler (is the graph sound, what is critical now, what does the evidence say about the end).

Re-forecasting from evidence

Listing 1's tracking section computes the ratio r of the summed actual durations to the summed likely estimates of the finished milestones, then a forward pass in which finished milestones take their actual length and the others their likely estimate times r. For the worked example after five weeks, r = 26 / 20 = 1.30 and the forecast end is day 66.3 against a likely plan of 51 R1.

The model's assumptions are part of its output and must be stated with it: the remaining work will be misjudged by the same factor as the finished work; the remaining estimates were made with the same habits; and the graph is complete. Early in a project, r rests on two or three milestones and moves a lot; the first milestones (proposal, design) are also of a different kind from the later ones (code, tests). Use the forecast as a signal to talk, not a date to promise.

Not verified — check before relying on this

How well a ratio-based re-forecast predicts the real end of student or professional projects is not established by any source opened in this build. Listing 1 implements the model; the chapter makes no claim about its accuracy. A dossier should look for evidence in the estimation literature named in SE404's sources (for example "The Mythical Man-Month" D3) before this method is presented as more than a disciplined signal.

What the graph does not know: people

The forward pass assumes that milestones without a dependency between them run in parallel. In the worked example M4 (store) and M5 (telemetry) both start on day 26. That is true for a team of two. For a learner working alone, the two are sequential, and the real end is later by the shorter of the two. Before trusting the critical path, add the resource dependencies: if the same person does M4 and M5, make one depend on the other in the plan, and rerun. The R1 reviewer should ask "who does each milestone?" for every pair that the plan runs in parallel.

Hidden work and undeclared dependencies

Two kinds of evidence in the log reveal a plan that does not describe the project. A milestone blocked by another milestone that is not among its dependencies is an undeclared dependency: the graph is wrong, so the critical path may be wrong. A milestone blocked by something that is not in the plan at all is hidden work: effort is being spent with no estimate and no test, so it will never be "done", and it is invisible to the forecast. Listing 1 checks both from the blocked lines (lines 96–115). The fix for both is the same: add the missing work as a milestone with a test and an estimate, correct the dependencies, and rerun. The forensic lab is a project where this was not done.

Managing scope without weakening tests

When the forecast slips past the R4 date, there are three honest levers: add time (if the calendar allows), reduce scope (cut a feature from the proposal's cut list, with the reviewers' agreement), or reduce risk (a spike that removes an uncertainty). There is one dishonest lever, which is to weaken a test or skip one, and the curriculum forbids it without explicit approval and a log entry; performance targets are not lowered after the fact either D2 §13.4, §19.2. Cutting scope is recorded at the next gate as a change to the approved plan.

How the hardware actually does it

In a mega project, hardware enters as constraints on the plan rather than as mechanisms to explain. Three of them shape every MP8 plan.

  • Emulator first, hardware as a separate milestone. Each component's acceptance tests run in QEMU or a simulator; a real-hardware run is recorded as extra evidence and never replaces the emulated test D2 §0, §19.2. In the plan, every hardware run is its own milestone with its own estimate, because hardware brings work the emulator does not: flashing, recovery paths, cabling, supervision, and quirks.
  • Access is a dependency. A GPU, a board or a robot kit that is shared, booked or still to be bought is a dependency with a date, and belongs in the graph. A milestone that needs it cannot start earlier, whatever the code says.
  • Safety gates come from the hardware. If MP8 includes a robot or a drone, MP6's and MP7's R3 safety checks apply before any real run (e-stop, clear zone, supervision, propellers removed for bench tests, battery handling per the maker's instructions, current aviation rules recorded) D1 §11.6, Honesty first. Plan time for them; they are not optional when late.

The build container of this university has no GPU, board, robot or drone. Listing 1 is a planning tool and needs none; the MP8 plans in this chapter are examples, and their hardware milestones are untested in this build by construction.

Worked example

Task. Plan the ground-station MP8 of Figure 1 at R0, then re-forecast it after five weeks.

Step 1 — milestones with tests. Nine milestones, each with an acceptance test name, a three-point estimate in working days (the team's judgements) and dependencies. M2 (contracts and their tests) is a separate milestone; M3 is the walking skeleton; M4 (store on three replicas) and M5 (telemetry replay from MP7's SITL logs) can run in parallel because two people work on them.

Listing 2 — mp8plan.in: the plan and the progress after five weeks.



Step 2 — run Listing 1 and read the checks. "no problems found": every milestone has a test, the estimates are ordered, and the graph has no cycle R1.


Step 3 — read the schedule. The likely end is day 51, the range 35 to 87. The critical path is M0 M1 M2 M3 M4 M6 M7 M8; only M5 has slack, one day. Check by hand: 4 + 10 + 6 + 6 + 9 + 8 + 3 + 5 = 51. M5 finishes on 26 + 8 = 34 and M6 cannot start before M4 finishes on 35, so M5's slack is 1.


Step 4 — gates. R2 falls after M4 on day 35, R3 after M6 on day 43, R4 on day 51. The team books reviewers for those weeks now.


Step 5 — five weeks later. M0, M1 and M2 are done in 5, 13 and 8 days. The ratio is (5 + 13 + 8) / (4 + 10 + 6) = 1.30. The forecast end is day 66.3: 26 days spent, then M3 7.8, M4 11.7, M6 10.4, M7 3.9 and M8 6.5, which sum to 66.3 R1.


Step 6 — decide and record. Fifteen days over the likely plan is too much to absorb silently. The log entry: "Forecast day 66 against 51; all three finished milestones ran 25–33 % over; the design milestone ran over because the threat model took longer than planned. Options: cut the operator map view (on the R0 cut list) to save about 5 days; ask at R2 whether R4 can move. No test is changed." That entry is what R2 will read.


Step 7 — add the people. Amara asks who does M4 and M5. If Joon does both, M5 must follow M4, and the plan gets one more line of dependency; rerunning shows a later end. The team keeps the two-person split and writes the name next to each milestone.

Where the analogy breaks


    

  • Software components can be stubbed. A house cannot have a pretend plumber whose pipes carry pretend water so the electrician can test the kitchen. A software component can be replaced by a stub that honours its contract, which is what makes the walking skeleton possible in week four. The analogy understates how early integration can start.
    • 

  • Software contracts change more easily, and that is a danger. Moving a pipe in a finished wall is visibly expensive; changing a field's unit in a message is one line of code and silently breaks the other side. The analogy suggests that crossings are hard to change; in software they are easy to change and hard to change safely, which is why contracts are versioned and tested.
    • 

  • One person may be all the trades. In a house, plumbing and wiring are done by different people at the same time. A learner doing MP8 alone does every trade, one after another, so the "parallel" milestones of the plan are not parallel (Layer 3).
    •

Transition box

Where you came from: SE404 taught estimating, trade-offs under uncertainty, mentoring and communicating (F12-23 to F12-27), and two of MP1–MP7 gave you finished systems with their own tests. What carries over: the curriculum's milestone rhythm (read, plan, test first, small steps, done only when the acceptance tests pass) D2 §0; three-point estimates and the critical path; design documents with alternatives; threat models. Mini-project


One contract, tested on both sides. Take the riskiest interface of your MP8. Write its contract (fields, types, units, ranges, ordering, unknown fields, versioning, timeouts, ownership) as a one-page section of your design document, then write contract tests on both sides that run without the other component. Include at least one test for a sentence that is easy to forget (units, a gap, an unknown field, an acknowledgement rule). Rubric: contract complete and unambiguous, units everywhere (30 %); tests on both sides, runnable in CI without the other component (30 %); at least one easy-to-forget case tested and justified (20 %); the contract is versioned, with an owner and a change rule (20 %).

Forensic lab answer key


How the evidence was produced. mp8plan_team.in was written to reproduce a plan in which the interface contracts were never made a milestone: the work happened inside M4, M5 and the waiting time of M3. It was run through Listing 1 by run.sh R2.


Observation. The checks print three problems: M3 has no acceptance test (test:tbd); M3 waited 11 days and M5 3 days on "M2", which is not a milestone in the plan. M4 and M5 ran 67 % and 75 % over their likely estimates.


Root cause. M2, the agreement and testing of the telemetry and store contracts, is hidden work: it is being done (the week-4 log entry), it blocks integration, and it has no milestone, estimate or test. Without a test it can never be finished, so M3 can never start; and M3 itself has no test, so it could never be finished either. The team's forecast of day 60 counts M4 and M5 as if their overruns were their own work and has no place for M2 at all.


Corrected plan. Add M2 with a contract-test milestone, make M4 and M5 depend on it, give M3 a test. With M2's actual 11 days recorded, Listing 1 forecasts day 72.3 against a likely plan of 49 R3:




(The corrected forecast keeps M4's and M5's actual durations as recorded; part of their overrun was probably M2 work as well, so the true overrun of M4 and M5 is smaller and the ratio may be pessimistic. That is a judgement to write next to the forecast, not to hide.)


What should have happened. In week 2, the first blocked day on the contracts should have become a milestone with a test. R1 should have refused a plan in which an integration milestone has test:tbd and in which no milestone covers the contracts named in the design document. Wrong answer to rule out: "the team is slow" — the finished milestones' overruns are largely explained by work that was not in the plan; the plan, not the people, was wrong.


Prevention. Run Listing 1 in CI on the plan file with the weekly blocked lines, failing on any PROBLEM; at R1, check that every contract in the design document has a milestone and a test.
