Story hook

Amara, Kenji and Lucía have been hired to renovate an old house. Nobody who built it is still around, and there are no drawings. On the first morning a tap in the upstairs bathroom drips, and the owner asks them to fix it.

Kenji goes straight to the bathroom and starts opening the wall behind the tap. By lunch he has found three pipes, two of which go nowhere he can see, and he is not sure which one to cut. Lucía does something that looks slower. She walks through every room with a notebook. She draws the floor plan: where the doors are, which walls carry the roof, where the water comes in from the street, where the main pipe climbs to the first floor. She marks the rooms that look newer than the rest. It takes her an hour, and she has not touched a single pipe.

After lunch Lucía's drawing shows that the drip has nothing to do with the bathroom wall. The main pipe runs through the cupboard next door, and a joint there leaks along the outside of the pipe down to the tap. Amara finds it in ten minutes with the drawing in her hand. The drawing is a map of a house nobody explained to them. This chapter is about drawing that map for a large program you did not write, before you open any of its walls.

What you will be able to do

  • Explain why a first map of an unfamiliar codebase comes before reading any function in detail, and which five questions the map answers.
  • Produce a first map of a large codebase within an hour by measuring it: size and areas, entry points, hub modules, the outline of one file, and one path confirmed by running the code.
  • Find the code that produced a given log line by searching for its constant fragments, and decide between several candidates with a probe instead of a guess.
  • Judge the limits of a map: heuristics that miscount, calls made by name at run time, generated code, and the version the map belongs to.
  • Write the map so that every step names the real file, directory or document section where it happens, as curriculum milestone G1 requires.
Jargon box
Codebase map
Simple words: a short written description of a large program: what its parts are, how big they are, where it starts, what everything depends on, and how one request flows through it. Analogy: the floor plan you sketch on your first walk through an old house. Precise: in this course, a document of one to three pages, tied to one exact version of the code, that records (1) size and areas with numbers, (2) entry points, (3) hub modules, (4) the outline of the files on the path you care about and (5) at least one path traced end to end, where every step names the real file and line, directory or document section; curriculum milestone G1 asks for such "a written architecture map" with that naming rule in its acceptance test D2.
Entry point (codebase map)
Simple words: a place where the program starts running when someone uses it. Analogy: a door into the house. Precise: a function or file that the outside world calls first: a main function, a script that can be run directly, a system call handler, a request handler a framework calls, a callback a scheduler starts. Not the same as the ELF entry point of SP301 (the address where a loaded program starts), although a program's ELF entry point is one of its entry points in this wider sense. In the Python library mapped here, files that can be run directly contain a __main__ guard or are named __main__.py D4.
Hub module (fan-in)
Simple words: a part of the program that very many other parts use. Analogy: the main pipe every room is connected to. Precise: a module with high fan-in, the number of other files that import or include it; measured here by counting, for each top-level module name, the files containing an import or from line naming it (R1). A change to a hub affects many callers; a hub is also a good place to start reading, because its interface is the vocabulary of the whole codebase.
Format string (of a log line)
Simple words: the fixed text of a message with holes in it, filled in when the message is printed. Analogy: the shape of a stamp; the ink colour changes, the shape does not. Precise: a string such as "code %d, message %s" whose conversion specifications are replaced by values at run time; the printed log line is the format string with the holes filled, often after several functions have each added their own part. Python's % operator on strings works this way, and the server mapped here uses it to build its log lines D4.
Instrumentation probe
Simple words: a few lines you add, temporarily, to a program so that it tells you what it is doing at one point. Analogy: opening one small inspection hatch in a wall instead of knocking the wall down. Precise: code inserted without changing the program's behaviour (here, a subclass that overrides one method, prints where it was called from, and calls the original) to turn a question about the running program into an observation; Listing 2 is one. Not the same as a driver's probe function in DR301 or a hardware debug probe in HW303.
Static and dynamic evidence
Simple words: what you learn by reading the code versus what you learn by running it. Analogy: reading the floor plan versus turning on the tap and watching where the water goes. Precise: static evidence comes from the source without executing it (search results, outlines, import counts); dynamic evidence comes from an execution (logs, traces, a probe's output, a stack sample). Static evidence shows what can happen; dynamic evidence shows what did happen in one run. A map uses both and says which is which.
Dispatch by name
Simple words: the program builds the name of the function to call from data, while it runs, so no line of the source calls that function by its name. Analogy: a doorbell panel where the visitor types the flat number; no wire runs from the street to one particular flat. Precise: a call through a run-time lookup (in Python, getattr(self, 'do_' + self.command) in the request handler mapped here; in C, a table of function pointers; in C++, a virtual call or a registry keyed by a string) D4. Text search for callers of such a function finds none (R4).

Terms from earlier courses used here: entry point (SP301, the ELF meaning), system call and strace (OS201), stack (call stack) (SP201), design document (SE301).

Layer 1 — the kid explanation

Analogy

Mapping (F12 world; proposed in NOTES.md): the old house = a large codebase you did not write; the floor plan sketched on the first walk = the codebase map; the size of each room = lines of code per area; a door = an entry point; the main pipe every room connects to = a hub module; a mark on a wall = a log line; finding the tool that made the mark = finding the code that printed the line; opening a small inspection hatch = adding a probe. The registered F12 warning about blueprints applies here too: software changes more often than houses, so a map belongs to one version and must be kept alive D3.

When a program is too big to read, you do not start at the first line of the first file. You walk through it quickly, measure it, and draw a plan. The plan says which parts are big, where the program starts, and which parts everything else uses. Then you pick one question and follow one path, and you check that path by running the program, not only by reading it.

A log line is a mark the program left behind. To find the code that made it, you look for the parts of the line that never change, because the parts that change (the time, a number, a file name) were filled in while the program ran.

Layer 2 — the student explanation

Why a map comes first

Reading time is the scarce resource. The library mapped in this chapter has 294,774 lines of Python in 591 files (R1) R1; an operating system kernel or a flight stack is larger and spread over several languages. Reading line by line, you would spend weeks before you could say anything useful, and you would forget the first file before you reached the last. A map turns the codebase into a small number of named parts, each with a size, a role and a few connections, so that every later hour of reading is spent on a part you chose on purpose.

The habit is the one the curriculum asks for before any milestone: name the documents and sections first, read them, write a few sentences in your own words, and only then plan D2. In an unfamiliar codebase, the code itself is the main document, and the map is your "few sentences" about it.

Five questions, five measurements

A first map answers five questions. Each has a cheap measurement that gives a first answer in minutes; Listing 1 makes the first four for a Python tree, and Listing 2 makes the fifth.

  1. What is here, and how big is it? Count files and lines per language. For the Python library: 591 files and 294,774 lines (R1). Size tells you how much you will never read, which is most of it.
  2. Where is the weight? Count lines per top-level area and rank them. In R1, 43.1 % of the lines are files directly in the top folder, and the largest folder is encodings/ with 11.0 % in 122 files R1. The biggest single file, pydoc_data/topics.py with 13,902 lines, is a clue in itself: a file that large in a library is often data that happens to be stored as code, and its name says so. Ranking prevents a common mistake, which is to assume the area you have heard of is where the code is.
  3. Where does execution start? Find the entry points. In Python, a file that can be run directly contains a __main__ guard, and a package that can be run with python -m contains __main__.py; R1 finds 81 files of the first kind and nine packages of the second, among them asyncio, unittest and venv R1. In a kernel the entry points are the boot path, the system call table, interrupt handlers and the module initialisation functions (OS303, DR301); in a ROS 2 system they are the nodes' main functions and the callbacks an executor calls (RB303).
  4. What does everything depend on? Count fan-in. In R1 the most-imported modules are sys (212 files), os (159) and codecs (104) R1. The hubs are the vocabulary of the codebase: once you know their interfaces, every other file reads faster.
  5. What does one request do? Pick one question that matters to you, find the entry point it starts from, and follow one path through the code to where the answer is. Then confirm the path by running the program with a probe or a trace, because reading tells you what can happen and running tells you what did.

The first four questions take minutes with a tool; the fifth takes the rest of the hour. The output is a page of notes with numbers, file names and line numbers, tied to the version you mapped (here, the standard library of Python 3.13.16, the version printed by the interpreter in the run logs) R2.

Finding the code behind a log line

A log line is the most common starting point in real work: a user sends you one line from a log, and you must find out what the program was doing. The method has four steps.

  1. Split the line into fixed and variable parts. In 127.0.0.1 - - [10/Oct/2026 02:30:57] code 404, message File not found, the address, the date and the number 404 were filled in at run time. The fixed parts are - - [, code, , message and perhaps File not found.
  2. Search for each fixed fragment separately. Searching for the whole line finds nothing, because the whole line never appears in the source; the search session R4 shows zero hits for it R4. Searching for code %d, message finds the one call that formats the middle part, and searching for - - [ finds the one function that adds the prefix.
  3. Walk the callers upward until you reach an entry point, using the map to know when you have arrived.
  4. When several candidates remain, run the program with a probe instead of choosing the most plausible one. In the forensic lab, the message File not found is passed at two different lines; the log line is identical for both; only a run can say which one produced a given line.

Layer 3 — the engineer's depth

Every measurement is a heuristic: know how it lies

Listing 1 counts what it can see with simple text rules, and each rule fails in a way you should be able to name before you trust the number.

  • Fan-in counts imports, not use. codecs is the third hub in R1 (104 files) R1. Counting its importers per area (R5, below) shows that 96 of the 104 are in encodings/, the family of codec definitions, and only eight are anywhere else R5. The hub ranking is inflated by one large family of near-identical files. The fix is to look at who imports a hub before concluding that it is central to the part you care about.
  • Text rules see text. A line inside a documentation string that starts with "import " is counted as an import. Imports made inside functions, or made by name at run time (Python's importlib, C's dlopen), are counted wrongly or not at all. A precise tool would parse the language; a first map does not need precision, it needs the right order of magnitude and a note of the rule used.
  • Lines are not complexity. 13,902 lines of generated text data in pydoc_data/topics.py weigh more than typing.py (3,846 lines) in R1, although nobody would read them first R1. Generated files, vendored copies of other projects and tests distort size; a map lists them as such.

Where static search goes blind: calls by name


The request handler mapped here never calls do_GET by that name. It builds the name from the request at run time, mname = 'do_' + self.command, and fetches the method with getattr D4. The search session confirms the consequence: searching the library for do_GET finds three definitions (in http/server.py, xmlrpc/server.py and pydoc.py) and no call R4. Searching for the construction itself, 'do_' +, finds the dispatcher in http/server.py and a different family of the same trick in cmd.py and pdb.py (R4).


Every large codebase has such places, and they are where maps go wrong. In C, a structure full of function pointers (a driver's operations table, a file system's operations) is the same pattern; in C++, virtual functions and registries keyed by strings; in a robot or drone stack, a callback registered with a publish–subscribe system and called by an executor or a work queue (RB303, F9-39; DN302, F10-21). The rule: when a caller cannot be found by search, look for the registration (where the function is put into a table, passed as a callback, or named in a configuration), and confirm with a dynamic observation. The probe of Listing 2 prints the chain send_head <- do_GET <- handle_one_request <- handle, which no search produced (R3) R3.



The build system is a map someone else already drew


A large compiled project decides in its build files which sources become part of a given product. Reading those files early answers "is this file even used in my configuration?", which no amount of reading the file itself can answer. The kernel of OS303 has one build script; real projects have layers of them, often with configuration options that switch whole directories on or off. A map belongs to one version


Every number and line number in this chapter belongs to the Python 3.13.16 library as installed in the build container; another release would give other numbers, and some line numbers would move. Write the version (a release number, a tag, or a commit identifier) at the top of every map, and when you cite a line, cite it as "file:line at version X". The rule is the same as the registered warning for blueprints, "software blueprints change more often; keep them alive" D3, and the same as AH-12 for documents: record what the version you read actually showed.



A time budget and a written output


This course's rule for a first map: one hour, five questions, one page, before reading any function in depth. The hour is a budget, not a measurement of how long mapping takes; its purpose is to stop the two failures of the story, opening the first wall you see (Kenji) and drawing the house forever without fixing the tap. If you cannot answer a question in the hour, write "unknown" and the reason; an honest gap in the map is more useful than a guess.


The map is written for someone else, so it follows the curriculum's naming rule for architecture maps: "Each step in both paths names the real source directory or document section where it happens; the learner explains both paths aloud without notes." That sentence is the acceptance test of milestone G1, written for maps of GPU drivers D2; this course applies it to every map, including the course project.



Reading as the first step of changing


The course's third chapter, F12-22, follows D1 on changing code you did not write: you will need to find the places where the behaviour you want to change can be observed and where the code can be cut apart for testing. Those places come from the map: the entry points tell you where tests can call in, the hubs tell you what a change will ripple into, and the traced path tells you which functions a change must keep working D1.

How the hardware actually does it


The library mapped in this chapter never touches hardware directly: it calls the operating system through the C library and system calls (OS201, F3-07). That boundary is itself a line on the map. When the forensic server writes its log line, the Python code at line 611 calls sys.stderr.write D4, and below that the interpreter eventually issues a write system call; from there on, the path belongs to the kernel and its drivers. You can watch that boundary with strace (OS201), and F12-21 follows a read across it, down through the kernel's file system and block layers to the driver of a disk and to a command an emulated NVMe controller receives.


In systems code the map is shaped by the hardware. A kernel tree is organised around architectures, buses and device classes; a flight stack around sensors, estimators and actuators; a GPU driver around the engines of the GPU (curriculum Track G, 15.1, lists them for a GPU driver) D2. When you map such a codebase, draw the hardware too: which device each driver area serves is often the fastest way to explain why an area exists.

Where the analogy breaks


    

  • Houses do not call rooms by name at run time. A pipe that runs from the street to the kitchen is visible on the plan. A call made through getattr, a function-pointer table or a callback registry is not; the plan of a program can be correct and still miss the connection that matters (Layer 3). The probe, which has no real counterpart in a house walk, is how you close that gap.
    • 

  • Programs change every day. A house plan stays valid for decades; a codebase map is valid for one version, and line numbers move with the next commit. A map without a version is closer to a rumour than a plan.
    • 

  • Size is not visible from the doorway. You can see at a glance that a hall is bigger than a cupboard; in code, a 13,902-line file of data and a 3,846-line file of dense logic look alike in a file list (R1). Measuring replaces the glance, and measuring needs rules whose errors you know.
    • 

  • A program can have hundreds of doors. A house has a few entrances; the library mapped here has 81 runnable files and every public function is a door for some caller (R1). A map lists the doors that matter for its question, not all of them.
    •

Mini-project


Start the course project: a written map of one large open-source subsystem. Choose a subsystem of a large open-source project you can obtain as source on your own computer (the build container had none, so this choice is yours and goes in your project notes): for example the block layer or one file system of the Linux kernel, the sensor pipeline of PX4, or the publish–subscribe path of ROS 2's client library. Rubric: every item has evidence and a version-qualified location (30 %); the five questions are answered or honestly marked unknown with a reason (25 %); the measurements' heuristics and their known errors are stated (20 %); one path is confirmed dynamically (15 %); the map fits on one page and a peer can follow it (10 %).



Summary


    

  • Map before details: the code is too large to read, so decide by measurement what to read.
    • 

  • Five questions: size, areas, entry points, hubs, one path; the first four are measured in minutes, the fifth is traced and confirmed by running.
    • 

  • Every measurement is a heuristic; state its rule and how it lies (imports are not use; lines are not complexity).
    • 

  • Log lines are assembled from format strings: search for fixed fragments, not whole lines.
    • 

  • Calls made by name are invisible to search; find the registration and confirm with a probe.
    • 

  • When several call sites remain, decide with dynamic evidence, never by plausibility.
    • 

  • A map belongs to one version and names file:line or a document section for every step (the G1 rule).
    • 

  • Write unknowns on the map; an honest gap tells the next reader where to look.

Forensic lab answer key


How the evidence was produced. run.sh started python3 -m http.server (Python 3.13.16) on the loopback address in an empty temporary folder and made two GET requests, for /nope.txt and /missing-dir/; it kept the server's standard error without the start-up banner (R2) R2. Nothing was broken on purpose: the "fault" is that the requested paths do not exist in the folder the server serves.


The search session (real, R4):




Observation. Two requests, each producing an error line followed by a request line; all four share the prefix "address - - [date]". The error lines are identical apart from the date.


Writer and formats. log_message (line 590) writes every line, with the prefix format at line 611. The text after the date in lines 1 and 3 is "code %d, message %s", passed by send_error at line 481 through log_error (571). Lines 2 and 4 come from log_request (560), called by send_response at line 516. The second definition of log_request in xmlrpc/server.py is a different server class and is ruled out because the evidence comes from http.server.


Which call site. "File not found" is passed at lines 743 and 748 of send_head. Line 743 runs when the translated path ends with "/"; line 748 when opening the file fails. The probe (R3) shows /nope.txt → line 748 and /missing-dir/ → line 743 R3.


Order. send_error logs the error first (line 481), then calls send_response, which logs the request (line 516); hence error line, then request line.


Colleague's claim. The server was asked for paths that do not exist in the folder it serves. Next checks: the folder the server was started in (or its --directory option), and the exact paths users requested (a trailing "/" on a file name gives the line-743 case). Wrong answers to rule out: "the disk is failing" (an I/O error would not take the trailing-slash path, and both requests failed in different branches); "permissions" (possible for line 748 in general, but the probe run with an empty folder reproduces the same lines without any permission problem, so the evidence does not require it).


Prevention. Make messages distinct per call site ("not found: path ends with /" versus "not found: cannot open"), or log the translated filesystem path in the team's own handler subclass; then one search finds one line. Add a test that requests both kinds of missing path and checks the messages.
