Story hook

The old house has a family living in it, and they want a new bathroom without moving out. Before anyone lifts a tool, Amara goes from room to room with a camera and a notebook. She flips every switch and opens every tap, and writes down what each one does, including the odd ones: the hall switch also turns on the porch light; the kitchen tap runs warm for a minute before it runs hot. "Those are probably mistakes," says Kenji. "Maybe," says Amara. "But somebody might be using them. Write them down first; decide later."

Next she finds the place where the bathroom's cables meet the rest of the house and puts in a junction box, so the bathroom can be switched off and tested alone without cutting into any other room. The new bathroom is built as a new room next to the old one, with its own tested wiring, and joined to the house at that box.

A week later a helper "tidies" the wiring in the hall while the others are out. Everything still works when he tests the hall light. That evening the family comes home in the dark: the porch light no longer comes on with the hall switch. Amara's notebook shows exactly which behaviour changed, and that it was there on the first day. This chapter is about changing code that people still live in.

What you will be able to do

  • Explain why changes to code without tests are risky, and the principle "record what it does before you change what it does".
  • Write a characterization test: a golden master of today's behaviour, including the odd behaviours, hidden state and call order.
  • Create a seam with the smallest mechanical edit, so that a hidden input (here, the clock) can be controlled by a test.
  • Refactor under the golden master, keeping every output identical, and add a feature as new, separately tested code beside the old.
  • Diagnose a "harmless cleanup" from a characterization diff, and decide for each changed behaviour whether it is a bug fix or a broken contract.
Jargon box
Legacy code
Simple words: code that people depend on but nobody fully understands, and that has no tests to tell you when you break it. Analogy: an old house a family still lives in. Precise: in this course, code that is in use (other code, tools or people depend on its behaviour) and whose behaviour is not pinned down by tests or a specification, so that a change cannot be checked against anything; age is not the criterion. D1 is the course card's reference for working with such code D1; the definition here is this course's working definition, to be compared with D1's at the fact-check.
Characterization test
Simple words: a test that writes down what the code does today, right or wrong, so you notice when that changes. Analogy: photographing and testing every room, switch and tap before you touch anything. Precise: a test whose expected values are taken from running the existing code, not from a specification; it asserts "unchanged", not "correct". Listing 4 is one: it records twelve inputs and outputs of the legacy formatter (R3) R3.
Golden master
Simple words: the saved output of a characterization test that later versions are compared with. Analogy: the photo album from the first day. Precise: a recorded set of outputs for a fixed, ordered set of inputs and controlled conditions (here: the same calls in the same order and a fixed clock), compared line by line against a new version; a difference is a behaviour change to be explained. Listing 6 compares the refactored formatter with it (R4); the forensic lab compares a cleanup with it (R5).
Seam
Simple words: a place where you can change what the code uses, without changing the code itself at that place. Analogy: a junction box where one cable can be disconnected to test a room alone. Precise: a point in a program where a dependency can be replaced from outside: a function pointer or virtual function (an object seam), a different definition chosen at link time (a link seam), a macro (a preprocessor seam). Listing 3's diff creates one: the clock is read through a function pointer that a test can point to a fixed clock (R1) R1. The names of the seam kinds are recalled from D1 (see the unverified box in Layer 2).
Hidden input
Simple words: something that changes what a function returns, but is not one of its arguments. Analogy: the porch light that depends on the hall switch, which nobody mentions. Precise: any state a function reads besides its parameters: a global or static variable, the clock, the environment, a file, a device register, the order of earlier calls. Hidden inputs make the same call return different results (R2) and must be controlled before behaviour can be recorded R2.
Sprout
Simple words: writing a new feature as new code next to the old code, with its own tests, and calling it from one place. Analogy: a new room built beside the old one and joined at one door. Precise: a change technique in which new behaviour is implemented in a new function or class, developed with tests, and invoked from the legacy code at a single point, so that the untested code changes by as little as possible; cellVolts in Listing 5 is sprouted, and its call is guarded so that the old behaviour is unchanged when the feature is not used (R4). The name is recalled from D1.
Behaviour-preserving refactoring
Simple words: changing how the code is written without changing anything it does. Analogy: rewiring a room so that every switch still does exactly what it did. Precise: a change of structure after which every observable output is identical for every recorded input; checked here by comparing with the golden master (12 of 12 identical, R4). A change that alters any recorded output is not a refactoring, whatever its commit message says.

Terms from earlier chapters used here: unit test and regression test (SP202); acceptance test and traceability (SE301); codebase map (F12-20); request path (F12-21).

Layer 1 — the kid explanation

Analogy

Mapping (F12 world; proposed in NOTES.md, except the registered code-review row): an old house people still live in = legacy code; photographing and testing every room first = a characterization test; the photo album = the golden master; a junction box that lets you test one room alone = a seam; the porch light that comes on with the hall switch = a quirk someone may rely on; a new room built beside the old one = a sprouted feature; the helper's "tidying" = a refactoring that changed behaviour; a second carpenter checking your joints = code review (registered) D3.

When code has no tests, you cannot tell whether your change broke something. So before you change it, you write down what it does today, by running it on many inputs and keeping the answers. That list is your safety net. Every time you change the code, you run the same inputs again and compare.

Sometimes you cannot write the list, because the code gives a different answer each time, for example because it reads the clock. Then you make the smallest possible change that lets a test control the clock. After that, you can record, change and compare, one small step at a time.

Layer 2 — the student explanation

The legacy dilemma

To change code safely you want tests; to put tests around code that was not written for them you often have to change it. The way out is to make the first changes so small and so mechanical that they cannot plausibly change behaviour, use them only to make the code testable, and then write tests before anything else changes. This course's version of the rule: record what it does before you change what it does, and change structure and behaviour in separate steps, never in the same commit.

The lab's legacy code is a status-line formatter from an old ground-station tool (Listing 1). It takes a string such as V=12.34;I=1.5;T=30 and returns a line such as 12.3V 1.5A 30C @7. Its rules were never written down, and two other tools parse its output. You have been asked to add a "volts per cell" figure to the line, and the team would like the code to be less fragile afterwards.

Step 1: try to pin it down, and fail

The first attempt at a test calls the function twice with the same input, one second apart. The outputs differ: the line ends in the seconds of the current minute (R2) R2. No expected value can be written for a function that reads the clock. A second hidden input is visible in Listing 1 itself: the global g_lastVolts, which makes the result depend on earlier calls.

Step 2: make a seam with the smallest edit

The diff of Listing 3 is the whole change: one function that reads the clock as before, one function pointer that points to it by default, and one call that goes through the pointer instead of calling the clock directly (R1) R1. For every existing caller nothing changes: the pointer points to the same clock. For a test, the pointer can point to a function that always returns the same time. The pointer points to our own small function rather than directly to the standard library's std::time, so that the seam does not depend on taking the address of a library function.

Three properties make this a safe first edit: it is mechanical (no logic was touched), it is small enough to review completely in a minute, and it preserves every signature, so no caller has to change. The global state is left as it is; it does not prevent recording, because a characterization test can control it by making the same calls in the same order.

Step 3: characterize

Listing 4 points the seam at a fixed clock and runs twelve inputs, in a fixed order, printing input and output (R3) R3. The inputs (Listing 2b) were chosen to touch every branch visible in Listing 1 and the edges of each condition: no V field, an empty value, an unknown key, a negative current, a temperature exactly at 60 and one degree above, a temperature below zero, an empty line, and a negative voltage. The output is the golden master. Reading it, you learn things nobody had written down:

  • V=11.86 prints as 11.8V: the voltage is cut to one decimal, not rounded.
  • I=2.25 prints as 2.2A: the current is formatted with %.1f, and in this build's C library that printed 2.2 for 2.25. Why is a question for the C library's documentation; for the golden master it is enough that it is today's behaviour.
  • A line without a V field, or with an empty V=, or an empty line, prints the previous line's voltage.
  • 60 °C is not "HOT"; 61 °C is.
  • V=-0.5 prints 0.-5V. That is certainly a bug, and it is recorded anyway.

The last point is the heart of characterization: the test records the bug, and it does not fix it. Fixing it is a behaviour change, to be decided separately (step 6 of Figure 2) after asking the tools that parse the line.

Step 4 and 5: refactor, then sprout

Listing 5 is the refactored formatter. Parsing and formatting are separate functions, the remembered voltage is a member of a Formatter object instead of a global, the clock is a constructor argument instead of a global pointer, and absent fields are std::optional instead of a sentinel value of −999. Every quirk is kept deliberately, with a comment where it would be tempting to "fix" it. Listing 6 runs the legacy code and the new code on the same inputs in the same order and compares: 12 of 12 lines identical (R4) R4.

Only then is the feature added. cellVolts is new code with its own tests, called from one place in format, and only when the caller asks for it with a cell count; without a cell count, the output is unchanged. Listing 6 checks both: the four new-feature checks pass, and the golden master comparison was made with the feature off (R4).

Layer 3 — the engineer's depth

Choosing characterization inputs

A golden master is only as good as its inputs. Sources of inputs, in the order this course recommends:

  1. The branches you can see. Read the code once for its conditions and write one input for each side of each condition, and one at each boundary (60 and 61 °C, 10.49 V against the 10.5 V limit).
  2. Real inputs from the field. Logs and recorded traffic contain the inputs that actually occur, including the odd ones; F12-21's traces are a source. In the lab, the empty line and the unknown key stand for this kind of input.
  3. Generated inputs. A property-based or fuzz generator (SE302, F12-08) can produce thousands of inputs, all compared with the legacy code as the oracle. This finds differences no human thought of; it needs the hidden inputs controlled first, or every comparison fails.

Order and state are part of the input. The legacy formatter's output for I=0.5;T=35 depends on the call before it; a golden master that sorts or shuffles its inputs records a different behaviour from the one in production. Listing 2b's comment says "IN ORDER" for this reason.

What a golden master can and cannot tell you

  • It detects change, not error. A difference means "the behaviour changed"; whether that is good is a separate question. In the forensic lab, one of the seven differences is arguably an improvement and two are clearly regressions (R5).
  • It covers only its inputs. Twelve lines cannot prove that no other input changed. The cleanup of the forensic lab passed the three unit tests that came with the code; a golden master with too few inputs could have passed it too.
  • It freezes formatting. Some recorded details are accidents nobody depends on (perhaps the clock suffix). If the golden master makes every harmless change painful, people will stop running it. Decide, with the consumers, which parts of the output are contract and which are not, and compare only the contract; write that decision down.
  • It must be regenerated deliberately. When a behaviour change is accepted, the golden master is regenerated in the same commit, and the diff of the golden master is part of the review. A golden master regenerated without review is a test that has been switched off.

Bug or contract?

Every recorded quirk raises the question "does anyone depend on this?". Use the map and the traces of F12-20 and F12-21 to find who consumes the output: which tools parse the line, which tests or dashboards read it, which people read it at night when something is wrong. Then classify each behaviour change:

This is the engineer's equivalent of Amara's "write them down first; decide later". The deciding is not the author's alone: it belongs in review, with the golden master diff in front of the reviewer (SE301, F12-04).

Separate structure from behaviour

The course's rule for every legacy change: one commit (or series) that changes structure with the golden master identical, then separate commits that each change one behaviour, each with its golden master diff and the reason. The rule makes review possible (a reviewer can trust "identical" and spend attention on the behaviour commits) and makes bisecting possible (a regression found later points to one behaviour commit). The curriculum's definition of done states the same principle for milestones: earlier milestones' tests still pass D2. The forensic lab's commit violated it: "tidy formatStatus: no globals, proper rounding, simpler checks" is three behaviour changes inside one refactoring.

Legacy code in systems software

In drivers, kernels and flight stacks, the odd line in old code is often a hardware workaround: a delay after a register write, a retry for a device that sometimes answers late, a field set to a value the specification does not require. Such lines look exactly like the quirks of this chapter, and "tidying" them is the classic way to break a device that nobody on the team owns any more. Characterize them the same way, with the device as part of the test: in an emulator, record the device-side trace (the QEMU trace events of F12-21) before and after the change, and compare the command sequences as a golden master. Where a line exists only for real hardware that you do not have, the honest result is "untested on hardware", and the line stays until someone with the hardware can test it.

How the hardware actually does it

The hidden input this chapter removes is time, and time comes from hardware. In the legacy formatter, std::time asks the operating system for the current calendar time, which the kernel keeps from a hardware clock source and an initial value read from a real-time clock at boot (DR301, F4-04, RTC and wall-clock time) D4. A test cannot control that hardware; it can only replace the function that asks for it. That is what the seam does, and the same reasoning applies to every hardware-dependent input of legacy systems code: a sensor value, a device register, a timer, an interrupt's arrival time. Put each behind a seam, give it a fake in tests and the real thing in production, and record the code's behaviour against the fake.

The seam itself has a cost in hardware terms: the call now goes through a function pointer, an indirect call, where before it was a direct call. For a status line printed a few times per second this is irrelevant; for code on a fast path (an interrupt handler, a per-packet function), measure before and after, as SE401 teaches, rather than assume either way.

Worked example

Task. Add "volts per cell" to the status line of Listing 1 without breaking the two tools that parse it, and leave the code less fragile than you found it. This walks the six steps of Figure 2 with the lab's real outputs.

Step 1 — map and trace. Find who calls formatStatus and who reads its output. In the scenario: the ground-station tool calls it once per telemetry line; a log viewer and a parser tool read the lines. Write the consumers down; they will be asked in step 6.

Step 2 — the seam. Try a test; it fails because of the clock (R2: the same input gave lines ending in different seconds) R2. Make the edit of Listing 3 (R1): two added lines, one changed line. Review it alone and commit it alone: "seam for the clock; no behaviour change".

Step 3 — characterize. Write the inputs (Listing 2b) and Listing 4; run it; keep the output (R3) as the golden master. Read every line and write down every rule it reveals, in particular the five listed in Layer 2.

Step 4 — refactor. Write Listing 5. Run Listing 6: "golden master: 12 of 12 lines identical" (R4) R4. If a line had differed, the refactoring would be wrong, however much cleaner it looked; fix it until the comparison is identical.

Step 5 — sprout. Write cellVolts with its tests first (12.6 V over 3 cells is 4.2 V; 0 cells returns the pack voltage), then call it from one place, only when a cell count is given. Run Listing 6 again: four new checks pass, and the 12 old lines are still identical (R4).

Step 6 — decide. Write a short note to the consumers listing the quirks found in step 3, and ask about two: may 0.-5V become -0.5V, and may a missing voltage print as unknown instead of the previous value? Each accepted change becomes its own commit with its golden master diff.

Result. Three or more commits instead of one, each small and reviewable: the seam; the refactoring (golden master identical); the feature (old outputs identical); then one per accepted behaviour change.

Where the analogy breaks


    

  • A photograph cannot be re-run; a golden master can. Amara's photos show one moment; a characterization test is executed again after every change, on the same inputs, and compares automatically. That is its whole value.
    • 

  • Houses do not have infinitely many rooms. You can test every switch in a house; you cannot run every input of a function. A golden master is a sample, and "12 of 12 identical" says nothing about the thirteenth input.
    • 

  • The junction box changes the house; the seam should not change the program. Installing a box is visible building work. A good seam leaves every existing caller's behaviour exactly the same (the diff of R1 adds no logic), and can be verified to do so.
    • 

  • Nobody photographs time. In a house, hidden inputs are wires in walls. In code they include time, earlier calls and the environment, which a camera cannot see; finding them needs the attempt of Listing 2, or reading the code for globals and system calls.

Transition box

Where you came from: F12-20 mapped a codebase you did not write and F12-21 traced requests through it; SE302 (F12-06) and SP202 taught you to write tests for code designed with them in mind. What carries over: the map's entry points and consumers, the traces as a source of real inputs, unit tests and sanitizers, and the definition of done's rule that earlier tests stay green D2. What changes: most dangerous first, the expected values of your tests now come from the code itself, not from a specification, so a passing test means "unchanged", never "correct"; the code was not designed to be tested, so your first edits must be tiny and mechanical; and every quirk may be somebody's contract, so behaviour changes become decisions with consumers, not private improvements. Summary


    

  • Legacy code, in this course: code people depend on whose behaviour no test or specification pins down.
    • 

  • Record what it does before you change what it does: a characterization test and its golden master.
    • 

  • Hidden inputs (state, time, environment) must be controlled first; a seam made with the smallest mechanical edit does it without changing callers.
    • 

  • Characterization records bugs too; fixing them is a separate, reviewed decision.
    • 

  • Refactor under the golden master until it is identical; sprout new features as new, tested code called from one place.
    • 

  • Separate structure from behaviour in different commits; review every golden master diff.
    • 

  • Passing old unit tests proves little: the forensic cleanup passed 3 of 3 and changed 7 of 12 golden master lines (R5).
    • 

  • In systems code, odd lines may be hardware workarounds; characterize them with the device (or its emulator) in the loop.

Forensic lab answer key


How the evidence was produced. status_cleanup.hpp was written for this lab to reproduce a typical tidy-up that mixes refactoring with three behaviour changes; cleanup_check.cpp ran the three original unit tests and the golden master comparison against the seamed legacy code, with the same fixed clock (R5) R5.


Observation. 3 of 3 unit tests pass; 5 of 12 golden master lines identical, 7 changed.


Grouped by rule. (a) Rounding instead of truncation (line 31, std::lround): 11.86 → 11.9 instead of 11.8; 10.49 → 10.5 instead of 10.4; 9.99 → 10.0 instead of 9.9. (b) No remembered voltage (line 15, volts = 0.0): I=0.5;T=35, V=;I=1 and the empty line now print 0.0V and LOW instead of the previous voltage. (c) HOT threshold (line 37, >= 60): 60C is now 60C HOT. The negative-voltage line 0.-5V is unchanged (rounding −5.0 still gives −5), and so is the current formatting.


Why the unit tests missed it. Their inputs (12.0 V, 10.0 V, 12.5 V; 30 °C and 70 °C; a V field in every line) are exactly the cases where old and new rules agree: one-decimal voltages are unaffected by truncation versus rounding, every input has a V field, and no temperature is at 60.


The reports explained. "Jumps to zero": telemetry lines without a voltage field (or with an empty one) now print 0.0V … LOW instead of repeating the last voltage (rule b). "Warnings appear and disappear": every such line also carries LOW, and a voltage slightly below 10.5 V now rounds up to 10.5V while still flagged LOW (rule a), so the parser sees flags that do not match the printed value; at 60 °C, HOT appears where it did not before (rule c).


The inconsistent line. 10.5V … LOW: the displayed value is 10.5, the LOW rule is "below 10.5", so the line contradicts itself. The flag uses the unrounded value and the display the rounded one. A person reading the log sees a warning for a voltage that, as printed, is at the limit.


Decisions. (a) Rounding: a defensible fix of display precision, but it must be negotiated with the parser owner and the LOW rule must use the same value as the display; revert for now, reintroduce alone. (b) Dropping the remembered voltage: a regression for the operator (and possibly a safety issue in a battery display); revert. If "unknown" is wanted, print it explicitly (for example ?.?V) after agreement, never 0.0. (c) HOT at 60: a contract change; ask the consumers and the requirement's owner; revert until decided.


What the commit should have been. One refactoring commit (no globals in the structure, but the remembered value kept, as Listing 5 does) with "golden master: 12 of 12 identical"; then separate commits for each rule change, each with its golden master diff. Process change: run the golden master comparison in CI on every change to the formatter, and require the golden master diff in the review when it changes. Wrong answer to rule out: "the parser is buggy" — the parser's input changed; the evidence shows exactly which lines.
