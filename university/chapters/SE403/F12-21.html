Story hook

The drip in the old house is fixed, and now the owner has a new complaint: the shower upstairs is weak in the morning and fine in the afternoon. Kenji wants to replace the shower head. Lucía takes her floor plan from the first day and does something else: she follows the water, joint by joint, from the shower back to the street.

At every joint she writes three things in her notebook. What the pipe is made of, and who is responsible for it: the house's own copper, a plastic section someone added later, the city's main after the meter. How wide it is: wide pipes, narrow pipes, a tank in the attic where water waits before it falls to the bathroom. And what changes there: at the tank, the water no longer comes when you open the tap, it comes from what is stored, and the tank refills on its own schedule.

The tank is the answer. In the morning, everyone showers at once, the tank empties faster than its float valve refills it, and the shower gets only what trickles through. Nothing is broken; one joint changes the timing of everything after it. A request in a computer travels the same way, through joints that change its size, its owner and its timing. This chapter follows three of them: a read() down to a disk command, a sensor sample up to an estimator, and the estimator's output out to a ROS 2 node.

What you will be able to do

  • Trace a read() from a C++ call through the C++ library, the system call, the file system and block layers and the driver, to the command a disk controller receives, naming the evidence for each hop.
  • Choose the right evidence at each boundary: a system call tracer at the user–kernel boundary, kernel stack samples inside the kernel, device-side trace events at the device, per-hop timestamps in a publish–subscribe pipeline.
  • Explain how a request changes shape at each hop (buffered, split, queued, sampled, dropped) using real runs as evidence.
  • Find the hop that adds latency or loses messages in a sensor-to-estimator-to-ROS 2 pipeline from per-hop traces.
  • Plan the source-reading part of a trace in Linux, PX4 and ROS 2 trees, and record which hops you verified and how.
Jargon box
Request path
Simple words: the list of every place one request passes through, from where it starts to where it is answered. Analogy: the pipe from the shower back to the street, with every joint written down. Precise: the ordered sequence of hops (functions, modules, processes, devices) that handle one request, each recorded with its location in a named version of the code or document and with the evidence that the request passed there; the answer usually travels back by a different route (a return, an interrupt, a callback), which is part of the path. This course writes request paths in the format of curriculum milestone G1 D7.
Hop
Simple words: one step of a request path where something about the request changes. Analogy: a joint where the pipe changes size, material or owner. Precise: a point on a request path where ownership, representation, size or timing of the request changes: a library call becomes a system call, a file offset becomes a disk block, a request waits in a queue, a message is copied into another process. Hops are where requests are buffered, split, merged, delayed or dropped, and therefore where bugs and latency hide.
Kernel stack sample
Simple words: a snapshot of which kernel functions a thread is inside at one moment, from the innermost outwards. Analogy: a photograph of the pipe joints the water is passing through right now. Precise: the list of return addresses on a task's kernel stack, resolved to function names, as Linux prints it in /proc/<pid>/task/<tid>/stack (readable by root in this build, R2); many samples of a busy thread show its kernel call chains and how often each occurs. A sample is statistical evidence: a hop that is fast is seen rarely R2 D2.
Direct I/O (O_DIRECT)
Simple words: asking the operating system to read from the disk itself every time, without keeping a copy in memory. Analogy: drawing water straight from the main instead of from the attic tank. Precise: a flag to open() on Linux that asks for transfers between the user buffer and the device without the page cache, with alignment requirements on buffer, offset and length that the open(2) manual page describes D2; used in Listing 2 so that every read() reaches the block layer (R2).
Block layer (blk-mq)
Simple words: the part of the kernel that collects disk requests from file systems and hands them to disk drivers. Analogy: the manifold where pipes from many rooms join before the main. Precise: the Linux subsystem between file systems and block device drivers; its multi-queue design (blk-mq) keeps software and hardware queues and calls the driver's queue function to dispatch each request D1; in this build's kernel the observed chain enters it at blk_finish_plug and leaves it at the driver's virtio_queue_rq (R2).
Trace event (QEMU)
Simple words: a message an emulator prints each time something chosen happens inside the emulated hardware. Analogy: a water meter at the street that writes down every litre that passes. Precise: a named probe point in QEMU's device models, enabled with -trace <name>, that prints the event's fields when it fires; this build used pci_nvme_admin_cmd, pci_nvme_io_cmd and pci_nvme_read of QEMU 8.2.2's NVMe controller (R3) R3 D4.
Message age
Simple words: how old the measurement inside a message is when someone uses it. Analogy: how long the water has been in the pipes when it comes out of the shower. Precise: the time between the sample's measurement and its use at a given hop; the sum of the latencies the hops before it added. A periodic hop (one that runs on a timer and reads the newest message) adds between zero and one period, depending on phase, and can skip messages (R4, R5) R4 R5.

Terms from earlier chapters used here: system call and strace (OS201); virtual file system (VFS) and block cache (OS304); virtio, notification (virtio), NVMe, submission queue and doorbell register (DR301); uORB, topic (uORB) and queue length (uORB) (DN302); executor (ROS 2), rmw and DDS (RB303); codebase map and instrumentation probe (F12-20). "Kernel" in this chapter always means the operating system kernel, not a GPU kernel (CU201).

Layer 1 — the kid explanation

Analogy

Mapping (F12 world; proposed in NOTES.md): the water = the request; following the pipe from the shower back to the street = tracing the request path; a joint where the pipe changes size, material or owner = a hop; the attic tank = a buffer or queue where requests wait; the float valve that refills the tank on its own schedule = a periodic task; the house's pipes, the city's main = code owned by different teams (your program, the kernel, a driver, the device); the water meter at the street = a device-side trace. The analogy is a single pipe; Layer 3 and "Where the analogy breaks" say where real requests behave differently.

A request is like water in a pipe: it starts at one end and must reach the other. To understand why it is slow, or why it sometimes never arrives, you follow it, joint by joint, and write down what happens at each joint.

At some joints the request changes shape. A small read becomes a big one because a library reads ahead. A sample waits until a timer wakes up the next module. A message is dropped because a newer one replaced it before anyone looked. Each joint needs its own way of looking: a tool that watches the doorway between your program and the operating system, a snapshot of the operating system's own steps, and a recorder inside the device.

Layer 2 — the student explanation

The method: one request, hop by hop, with evidence

Start from the map of F12-20: you know the entry point and roughly which areas the request crosses. Then, for each hop, record four things: the hop's name (function, module, process, device), its location (file and line, directory, or document section at a stated version), what changes there (size, ownership, timing, representation), and the evidence that this request really passed there. Hop 1–2: from in.read() to the system call

Listing 1 calls in.read() four times on a 22,000-byte file, asking for 16, 16, 12,000 and 20,000 bytes. Run under strace, the kernel sees four read() calls with different sizes: 8191 bytes, then 3841, then 20,000 (of which 9968 arrive), then a read that returns 0 at the end of the file (R1) R1. The two 16-byte reads produced one system call between them; the 12,000-byte read was served partly from what the first system call had already brought in (8191 − 32 = 8159 bytes) and partly by a second call for the remaining 3841; the 20,000-byte read went to the kernel directly. The request changed shape at the first hop, inside the C++ library, before the kernel saw anything.

This is why a trace must start where the request starts. If you began at the kernel, you would see a read() of 8191 bytes and look for code asking for 8191 bytes; there is none in Listing 1. The size 8191 is a property of this C++ library's file buffer in this build, observed, not documented here; another library or version may choose another size, which is exactly the kind of fact a trace records with its version.

Hops 3–6: inside the kernel

Listing 2 reads a file with O_DIRECT in one thread while another thread samples that thread's kernel stack. The most frequent chain in the recorded run is the one in which the reader waits for its I/O, ending in blk_io_schedule; below it, from the outside in: the system call entry (entry_SYSCALL_64_after_hwframe, do_syscall_64, x64_sys_call, __x64_sys_read), the generic read (ksys_read, vfs_read), the file system (ext4_file_read_iter) and its direct-I/O path (iomap_dio_rw, __iomap_dio_rw) (R2) R2. A rarer chain continues further: blk_finish_plug and the block layer's dispatch functions, ending in the virtio block driver's virtio_queue_rq and virtqueue_notify (R2). In development runs of this build, such a chain sometimes had an interrupt-entry frame on top, because an interrupt arrived while the driver was running; the recorded run may or may not show one.

Read the chain as the layers of OS201 and OS304. The system call enters the kernel (OS303, F3-29); vfs_read is the virtual file system, which hands the request to the file system that owns the file (F3-31) D1; the file system turns a file offset into blocks on the device; the block layer queues the request and calls the driver; the driver tells the device. The program found the device and driver behind the file through sysfs: block device 254:0, named vda, driver virtio_blk (R2), the device family of F4-05.

With an ordinary open(), a second read of the same data would usually be answered from the page cache and never reach the block layer, which is why Listing 2 uses O_DIRECT D2. Choosing the request so that it reaches the hop you want to see is part of the method.

Hop 7: the device receives a command

The build machine's disk is virtio, not NVMe, and its kernel has no nvme_queue_rq in its symbol table (R2). To see the device side of an NVMe read, the lab boots QEMU with an emulated NVMe controller and asks QEMU to print every command that controller receives. The host software in this run is QEMU's x86 firmware (SeaBIOS 1.16.3, as it printed on its debug console), which initialises the controller and reads sector 0 of the disk to boot from it (R3) R3. The trace shows the controller's view: administrative commands first (QEMU names them NVME_ADM_CMD_IDENTIFY, NVME_ADM_CMD_CREATE_CQ and NVME_ADM_CMD_CREATE_SQ, followed by a long series of further Identify commands), which is the firmware setting up a completion queue and a submission queue for I/O, and then one I/O command, opc 0x2, which QEMU names NVME_NVM_CMD_READ, for namespace 1, one block of 512 bytes at LBA 0. Then the boot sector ran and ended QEMU with exit status 3, which the lab expects when the sector writes 1 to QEMU's exit device (R3).

This is the same command sequence the NVMe driver of F4-07 issues from your own kernel: create the queues, write a command into the submission queue, ring the doorbell, wait for the completion D9. The opcode value and the command layout are defined by the NVMe specifications (D3, title only); the trace is the controller model's own report of what it received D3.

From a sensor driver to an estimator, and out to ROS 2

A flight stack's request path does not start with a call; it starts with a measurement. In PX4, modules exchange data through uORB topics, which DN302 described as a notice board where each reader sees the newest note (F10-22) D9. The course's model, Listing 3, follows one accelerometer sample through four hops: a driver publishes it, a sensors module reads it and publishes a processed version, an estimator reads that and publishes its state, and a bridge forwards the state to a ROS 2 node. Every message carries a list of the hops it passed, with times, so the trace is part of the data.

In the triggered configuration (R4), each module runs when its input is published: the sample is 280 µs old when the estimator finishes and 450 µs old when the ROS 2 listener's callback runs, every time R4. The bridge forwards only one estimator output in five because it runs every 5000 µs while the estimator produces one every 1000 µs; the model reports this as 12 outputs not forwarded, by design. The 20 µs the bridge adds is luck of phase: its timer happens to fire 20 µs after the estimator finishes. A periodic hop can add anything from zero to one full period.

The ROS 2 side has its own layers. A message published by a node passes through the client library, a middleware interface and a DDS implementation before another node's executor calls its callback (RB303, F9-39, F9-40) D6. The model collapses all of that into one "ros2_listener" hop of fixed latency; a real trace would split it.

Layer 3 — the engineer's depth

Where requests change shape

Every hop in this chapter's runs changed the request in one of a few ways, and the same few appear in every system you will trace:

  • Buffering and read-ahead: four C++ reads became four system calls of other sizes (R1). Effect: the size and number of requests below the hop differ from those above it.
  • Caching: a read answered from memory never reaches the device; O_DIRECT was needed to make every read visible below the file system (R2).
  • Queueing and batching: the block layer collects requests and dispatches them later; the chain in R2 shows dispatch happening when the request's "plug" is finished, inside blk_finish_plug, rather than at the moment the file system created the request. The blk-mq documentation describes the queues; the details of plugging are a point to check in it (D1) D1.
  • Translation: a file offset became a block address, and a block request became a device command in the device's own format (R3).
  • Sampling and dropping: a periodic reader of a newest-only topic adds up to one period of age and skips everything published in between (R5).

When you write a request path, note the transformation at each hop. A bug report almost always describes the request at one end ("my read is slow", "the estimator is late") and the cause at a hop in the middle.

Sampling evidence and its traps

Stack sampling is statistics, not a trace. In the recorded run the waiting chain dominates because the reader spends most of its time asleep, waiting for the device; the dispatch chain that reaches the driver was caught in only a few samples, and Listing 2 had to keep sampling until it saw one (it stops after six seconds and says so if it never does) (R2). Three consequences:

  • Absence is not evidence. A hop missing from the samples may be fast, not absent. submit_bio exists in this kernel (R2), yet neither printed chain contains it; the direct-I/O path reached dispatch through the plug instead. Whether a function was skipped or only missed by sampling is a question for the source (D1) or for a real tracer.
  • Frequency is time, not importance. The most frequent chain is where the thread waits, which is exactly what you want for a latency question and exactly wrong for a "which code ran" question.
  • One sample is a hint. Interrupt frames can sit on top of a chain (seen in development runs of Listing 2), and a stack read from a running thread is a snapshot that may change while it is read. Confirm every hop with a second kind of evidence: the source at the stated version, or a tracer when one is available.

Reading the Linux source for the same path

The course card asks you to trace a read() to an NVMe command in Linux source. The build container had no kernel source, so this part could not be done here; the runs above give you the function names of one real kernel to search for. The plan:

  1. Obtain the source of the kernel version you trace (write it at the top of your map; here, R2 printed 6.18.44 for the running kernel, whose exact source the build container did not have).
  2. For each function name in R2, find its definition and write down file and line. Then read only enough of each function to find the call to the next name.
  3. Where the next call goes through a pointer (the file system's read operation, the driver's queue operation), find the table that installs it, as in F12-20, Layer 3.
  4. For the NVMe driver, find the function that turns a block request into an NVMe command and the place where the doorbell is written, and compare the fields with R3 and with F4-07.

Writing the path down

The written trace is a table with one row per hop, in the G1 format: each step names the real source directory, file and line or document section D7; plus two columns this chapter adds, "what changes here" and "evidence (static or dynamic, which run)". The worked example below is one such table. A row whose evidence is only "I read the code" is a hypothesis; mark it so, and try to give it a dynamic confirmation.

How the hardware actually does it

The last software hop of a disk read is a write to a device register. In R2's driver chain, virtqueue_notify is the virtio driver telling the device that new work is in a queue in memory (R2) R2; in virtio, that notification is a write to a device register, as DR301 described (F4-05) D9. In development runs of Listing 2 a frame named iowrite16 appeared above virtqueue_notify, consistent with such a register write; it is not in every run. NVMe works the same way in principle: the driver places a command in a submission queue in host memory and writes the new tail index to the queue's doorbell register; the controller then fetches the command by DMA, moves the data, and writes a completion entry, after which an interrupt (or polling) tells the driver it is done (DR301, F4-07) D9 D3. R3 is that fetch, seen from the controller's side: one Read command with its namespace, block count and starting LBA.

Two consequences for tracing. First, the request crosses from the CPU's instruction stream to a separate machine at the doorbell write; from there on, kernel tools see only the completion, and the device's own view needs device-side evidence (an emulator's trace, a bus analyser, the controller's log). Second, the answer comes back asynchronously: the thread that issued the read sleeps (the dominant chain of R2 ends in blk_io_schedule) and is woken by the completion path, which runs in interrupt context, on a different stack. A request path is a loop, not a line.

Watch out

R3's NVMe controller is emulated. It shows the commands the NVMe model in QEMU 8.2.2 received from SeaBIOS; it says nothing about a real NVMe drive's timing, firmware or command handling. Real-drive behaviour is untested in this build.

Where the analogy breaks


    

  • Requests are copied, split and merged; water is not. One C++ read became part of one system call, another became two (R1); a block layer can combine requests. A pipe carries the same water from end to end.
    • 

  • Newest-only topics throw old data away. A tank keeps all its water; a topic that keeps only the newest message overwrites the previous one if nobody read it, and the model counted 10 of 20 samples lost that way (R5). There is no water equivalent of an overwrite.
    • 

  • The answer comes back by another route. Water does not return to the street; a read's data and completion come back through an interrupt and a wake-up on a different stack, and a ROS 2 reply would be a separate message. A complete trace follows the way back too.
    • 

  • You cannot see some joints at all. In a house you can always open the wall. In this build, the kernel's tracing tools were missing (R6), the device was emulated (R3), and PX4 and ROS 2 were not installed; the method had to say which joints were seen and which were only reasoned about.

Forensic lab answer key


How the evidence was produced. run.sh ran Listing 3 with uorb_polled.in: "sensors polled 2500", bridge every 5000 µs, run 20,000 µs (R5) R5. The fault injected is the scheduling change of the sensors module from triggered (each publication) to a 2500 µs timer; the configuration line at the top of the evidence says so, and a careful learner uses it as confirmation, not as the starting point.


Observation. Before: accel_driver 50, sensors 30, estimator 200, dds_bridge 20, listener 150 µs; age at estimator 280 µs; 20 of 20 samples used. After: sensors 950, dds_bridge 2100; age at estimator 700..1200 µs; 8 estimator outputs; 10 samples overwritten before the sensors module read them.


Cause and inherited change. The sensors hop is the cause: it now runs every 2500 µs (at 500, 3000, 5500, … µs) and reads the newest sample, which is 450 or 950 µs old at that moment (published 50 µs after samples taken every 1000 µs). The estimator is unchanged (200 µs). The bridge did not change either; its 2100 µs is inherited: the estimator now finishes at times such as 3200 µs, so when the bridge runs at 5300 µs the newest estimator output is 2100 µs old.


Why the listener always shows +950. The bridge samples the estimator's outputs every 5000 µs, and with these periods it always picks an output whose sensors hop was the 950 µs case; the 450 µs cases exist (the estimator range 700..1200 includes them: 450 + 50 + 200 = 700, 950 + 50 + 200 = 1200) but are never forwarded. A periodic hop downstream hides variation upstream; look at every hop's own range, not only the end-to-end lines.


Lost samples. Between two polls 2500 µs apart, two or three samples are published on a newest-only topic; the poll sees only the last one. Over the run, 10 samples were overwritten unseen, and 8 reached the estimator instead of 20. The estimator integrates fewer, older measurements.


Fix and verification. Restore triggering on publication (configuration "sensors triggered") or, if a timer is required, poll faster than the driver publishes and read all queued samples (a queue length greater than one, F10-22). Verify by re-running: per-hop sensors latency 30 µs, age at estimator 280 µs, 0 samples overwritten (R4). Wrong answers to rule out: "the bridge is broken" (its configuration and its own work are unchanged; its latency follows the estimator's phase); "the estimator got slower" (its hop is 200 µs in both runs).


Prevention. A test that runs the pipeline and asserts per-hop budgets (sensors ≤ a stated bound, age at estimator ≤ a stated bound, zero overwritten samples) would have failed on the refactoring; carrying per-hop timestamps in messages in the real system makes the same check possible in the field.
