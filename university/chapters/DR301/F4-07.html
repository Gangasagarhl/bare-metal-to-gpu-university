Story hook

After the old logistics company of F4-06, with its gates and forms inherited from another century, the school tries a new supplier built for speed. There is no access road and no form in a foreign language. There are pairs of trays: an order tray and a receipt tray. The school drops orders of exactly 64 bytes into the order tray and presses a bell with the tray's new count; the supplier puts 16-byte receipts into the receipt tray and the school presses another bell to say how far it has read. The school can set up one tray pair per teacher, so nobody waits for anybody.

One detail is clever. Receipts are never wiped from the tray. Instead, in each round the supplier writes receipts in a different ink colour, so the school knows a receipt is new because its colour matches this round's colour. Forget about the colour and you will happily read last round's receipts as if they were new. This chapter builds an NVMe driver with admin and I/O queue pairs, PRP lists, Identify and namespaces, runs the random test with 1, 4 and 8 queue pairs, reads the course project's root file system from a second namespace, and shows exactly what happens to a driver that forgets the colour.

What you will be able to do

  • Bring up an NVMe controller: read CAP, disable, set up the admin queue pair, enable with the right entry sizes, wait for ready.
  • Issue admin commands: Identify Controller, the active namespace list, Identify Namespace, Set Features (number of queues), Create and Delete I/O queues.
  • Submit and complete I/O through submission queues, completion queues, doorbells and the phase tag.
  • Describe data with PRP entries and PRP lists for 1, 2 and more pages.
  • Use several I/O queue pairs and match completions to commands by command identifier.
  • Read a root file system from an NVMe namespace (the course project), and diagnose a driver that reads stale completions.
Jargon box
NVMe (NVM Express)
Simple words: the standard way a computer talks to fast flash SSDs on PCI Express. Analogy: the new supplier's tray system. Precise: a host controller interface with memory-resident submission and completion queues, doorbell registers, and admin and I/O command sets; on PCI, class code 010802h with registers in BAR0. D1 D2
Submission queue (SQ)
Simple words: a ring of commands the driver writes for the controller. Analogy: the order tray. Precise: a circular array of 64-byte entries in host memory; the driver owns the tail and advances it by writing the SQ tail doorbell; the controller consumes from the head. D1
Completion queue (CQ)
Simple words: a ring where the controller reports finished commands. Analogy: the receipt tray. Precise: a circular array of 16-byte entries (result, SQ head, SQ ID, command identifier, status with phase tag); the controller produces at the tail, the driver consumes at the head and reports it through the CQ head doorbell. D1
Doorbell register
Simple words: a register the driver writes to say "new orders up to here" or "I have read up to here". Analogy: the bells on the trays (not the faculty's doorbell analogy for interrupts, which ring the other way, from device to CPU). Precise: per queue, a tail doorbell for an SQ and a head doorbell for a CQ, at BAR0 offset 1000h + (2y or 2y + 1) × (4 << CAP.DSTRD). D2
Phase tag
Simple words: one bit in each completion that flips every time the controller goes round the queue. Analogy: this round's ink colour. Precise: bit 0 of the completion entry's status word; the controller writes the inverse of the previous value at that slot on each pass, starting from 1 on the first pass over a zeroed queue; an entry is new when its phase equals the phase the driver expects for the current pass. D1
PRP (physical region page) entry
Simple words: a pointer to one memory page of a command's data. Analogy: a shelf number on the order. Precise: a 64-bit physical address; a command carries PRP1 and PRP2; for data spanning more than two pages, PRP2 points to a page-aligned list of further PRP entries. D1
Namespace
Simple words: one "disk" inside an NVMe controller. Analogy: one of the supplier's warehouses. Precise: a quantity of non-volatile memory addressed by logical blocks, with its own size and LBA format, identified by a namespace ID (NSID) that every I/O command names. D1
Command identifier (cid)
Simple words: a number the driver puts on each command so it can recognise the answer. Analogy: the order number printed on the receipt. Precise: a 16-bit field in command dword 0, copied into the completion entry; unique among the commands outstanding on one SQ. D1

Layer 1 — the kid explanation

A fast SSD and the computer share two lists in memory: one for jobs and one for "done" notes. The computer writes a job, rings a bell, and goes on with other work. The SSD does the job and writes a "done" note. The notes are never erased; instead the SSD writes them in a different colour each time it starts the list again from the top, so the computer can tell new notes from old ones. The computer can have many pairs of lists, one for each of its helpers.

Layer 2 — the student explanation

An NVMe controller is PCI class 010802h with its registers in BAR0. CAP describes it (the maximum queue size, the doorbell stride, how long to wait for ready, the page sizes it supports). The driver disables the controller (CC.EN = 0, wait until CSTS.RDY = 0), writes the admin queues' sizes and addresses (AQA, ASQ, ACQ), enables it with the entry sizes it will use (64-byte commands, 16-byte completions), and waits for CSTS.RDY = 1. D1 R2

Everything else is commands. Admin commands go to queue 0: Identify (with a "CNS" value saying what to identify), Set Features, Create and Delete I/O queues. I/O commands go to the I/O queues: Read (02h), Write (01h), Flush (00h). Each command names a namespace, a starting LBA and a block count, and points at its data with PRP entries. D1 D3

Milestone C6 asks for "controller reset and enable sequence, queue memory, PRP lists, completion handling with MSI-X per queue (after C7, start polled), namespace block devices". This chapter's driver is polled, as the milestone allows until C7. Its acceptance tests compare Identify with QEMU's configuration, run the 1 GiB random test with 1, 4 and 8 queues, and ask for the root file system on NVMe, which is also this course's project. D7

Layer 3 — the engineer's depth

Reset and enable

R2's CAP is 0x004018200f0107ff. MQES (bits 15:0) = 7FFh: queues may hold up to 2048 entries (the field is zero-based). Bit 16 (CQR) = 1: queues must be physically contiguous. TO (bits 31:24) = 0Fh: wait up to 15 × 500 ms = 7500 ms for ready changes. DSTRD (bits 35:32) = 0: doorbells 4 bytes apart. CSS (bits 44:37): bit 0 set, the NVM command set. MPSMIN (bits 51:48) = 0 and MPSMAX (bits 55:52) = 4: pages from 4 KiB to 64 KiB. VS = 1.4.0. D1 R2

CC.EN = 0 resets the controller's queues; the driver must wait for CSTS.RDY to clear before touching AQA, ASQ and ACQ, and after setting EN it must wait for RDY to be set, watching CSTS.CFS (controller fatal status) and the timeout. CC also carries IOSQES = 6 and IOCQES = 4 (log2 of 64 and 16), the memory page size (0 = 4 KiB) and the command set (0 = NVM); a controller does not accept I/O queue creation unless IOSQES and IOCQES are set. D1

The rule that queue creation fails without IOSQES/IOCQES and the behaviour of the CQ head doorbell beyond posted entries are from memory only.

Admin commands and Identify

An admin command is a 64-byte entry: dword 0 holds the opcode (bits 7:0) and the CID (bits 31:16), then the NSID, PRP1 and PRP2, and command dwords 10–15. Identify with CNS = 1 returns the controller's 4 KiB data structure; CNS = 2 returns the list of active namespace IDs; CNS = 0 with an NSID returns that namespace's structure. R2: vendor 0x1b36, serial "DR301NVME0001" and MDTS 5 (both from QEMU's command line), model "QEMU NVMe Ctrl", firmware "8.2.2". D1 R2

One field is easy to misread: NN, "number of namespaces", is 256 in R2 although the controller has two. NN is the highest namespace ID the controller supports, not the count of namespaces in use; the active namespace list (CNS 2) gives the real ones: 1 and 2. The lab's first version printed "nn 256" as the namespace count; comparing with the configuration caught it. D1 R3

Identify Namespace gives NSZE (size in blocks) and the LBA formats: FLBAS bits 3:0 select one of the LBAF entries, whose bits 23:16 (LBADS) are log2 of the block size. R2: namespace 1 has 2097152 blocks of 512 bytes; namespace 2 (the root image, configured with logical_block_size=4096) has 512 blocks of 4096 bytes. R2

I/O queues and doorbells

Set Features with feature 07h asks for a number of I/O queues (zero-based counts in dword 11); the answer in completion dword 0 says how many the controller allows: R2 asked for 8 pairs and was allowed 64. Create I/O Completion Queue comes before the SQ that uses it, with the queue ID and zero-based size in dword 10 and "physically contiguous" plus interrupt settings in dword 11 (here PC = 1, interrupts off: polled). Deleting is the other way round: SQs first, then their CQs. The trace in R6 shows exactly this order. D1 R6

The submission path: write the entry at the tail, advance the tail modulo the size, barrier, write the tail to the SQ's doorbell. The completion path: read the entry at the head; if its phase bit equals the expected phase, it is new: copy it, advance the head (flipping the expected phase on wrap-around), write the head to the CQ's doorbell so the controller can reuse the slot. The completion also reports the SQ head, which tells the driver how many SQ slots the controller has freed; the lab's driver never has more commands in flight than an SQ has entries, so it does not need to track it. D1 D2

PRPs

PRP1 points to the first page of the data (it may have an offset; the lab keeps buffers page-aligned). If the data ends within the second page, PRP2 points to that page. If it needs more, PRP2 points to a PRP list: a page of 64-bit page addresses for the rest. The prp test in R2 covers all three cases (4, 8 and 64 KiB) and checks the data read back with a hash. MDTS = 5 limits one transfer to 25 × 4 KiB = 128 KiB with these page settings, so the lab's 64 KiB maximum is within it. D1 R2

Several queues, and command identifiers

The random test sends slot s to I/O queue (s mod n) + 1 and polls all queues in turn. The CID encodes the slot in its low 5 bits and a sequence number above, so a completion names its slot and a stale completion (a CID no longer in flight) can be recognised. In a real kernel each CPU would own one queue pair and submit without locks; the curriculum's test asks for "1, 4 and 8 queues on 8 CPUs". This lab kernel has one CPU, so it exercises the controller's queue handling but not per-CPU submission (see the box in the lab section). D7

Interrupts later

NVMe is designed for MSI-X with one vector per completion queue, so that each CPU's completions interrupt that CPU. This driver turns INTx off and polls, as C6 permits until C7 (MSI and MSI-X, DR302). D7

How the hardware actually does it

A real NVMe SSD has its controller on the drive, attached by PCI Express lanes; the queues are in host memory and the drive reads commands and writes completions by DMA, with the doorbell writes as its only signal from the CPU. Behind the controller, the drive's firmware (its flash translation layer) maps logical blocks to flash pages, does wear levelling and garbage collection, and decides when data written to its cache is durable, which is what Flush is for. The test machine's Windows driver list (DRIVERS.html, List 2) shows stornvme, Microsoft's NVMe driver, and nvmedisk, with "yes-on device" firmware. D1 D8

In the lab, QEMU's nvme device plays the controller and image files play the flash. R6 shows something a real machine does too: the firmware (here SeaBIOS) used the controller before the kernel, created its own queues and enabled it; the kernel's first job is to disable it and start clean. R6

Not verified — check before relying on this

The description of SSD firmware (flash translation, wear levelling, garbage collection, cache and flush semantics) is general knowledge from memory, not from a source opened in this build. No physical NVMe device was used; queue counts, timeouts and transfer limits differ per drive and must be read from CAP and Identify.

Worked example

A read command. Read 8 blocks (4 KiB) at LBA 8000 of namespace 1 into a page at 0x150000, CID 0x0123: dword 0 = 0x01230002 (CID in bits 31:16, opcode 02h); NSID = 1; PRP1 = 0x150000, PRP2 = 0; dword 10 = 8000 = 0x1F40 (LBA bits 31:0), dword 11 = 0 (bits 63:32); dword 12 = 7 (block count, zero-based). D3

Doorbell addresses. With DSTRD = 0 the stride is 4 bytes. Queue 0 (admin): SQ tail at 1000h, CQ head at 1004h. I/O queue 3: SQ tail at 1000h + 6 × 4 = 1018h, CQ head at 1000h + 7 × 4 = 101Ch. D2

A PRP list. 64 KiB at buffer 0x200000 is 16 pages: PRP1 = 0x200000; PRP2 = the address of the list, whose 15 entries are 0x201000, 0x202000, …, 0x20F000. D1

Reading the CIDs in the trace. R6's kernel part starts with CIDs 63, 95, 127: in binary 1 11111, 10 11111, 11 11111. The low 5 bits are 31 (the admin slot) and the sequence number above them counts 1, 2, 3. R6

Where the analogy breaks


    

  • Ink colours suggest many colours. The phase is one bit: two "colours", alternating. Any scheme with more state would need more bits per entry.
    • 

  • Trays per teacher, but one school building. Queue pairs per CPU avoid locks in the driver, but the controller still serves all queues; how it arbitrates between them (round robin or weighted) is its business. The analogy suggests completely independent suppliers.
    • 

  • The bell carries a number. A doorbell write is not just "ring": it states the new tail or head index. Writing a wrong number (for example, a head beyond what the controller produced, as the forensic build does) is an error the analogy does not suggest.
    • 




Common mistakes and debugging


    

  • Touching AQA/ASQ/ACQ while the controller is enabled. Symptom: the admin queue is not where the controller thinks; the first command never completes. Disable and wait for RDY = 0 first.
    • 

  • Sizes not zero-based. Symptom: queue creation fails with an invalid-size status, or the queue is one entry larger than its memory.
    • 

  • Ignoring the phase tag. Symptom: stale completions, then a hang after the first wrap (forensic lab).
    • 

  • Not zeroing a CQ before creating it. Symptom: garbage with phase bit 1 is taken as the first completions.
    • 

  • Reading NN as the namespace count. Symptom: the driver probes 256 namespaces and fails on the first missing one.
    • 

  • A PRP list that crosses a page. Symptom: transfers above a certain size corrupt data. A list page holds 512 entries; longer lists chain with the last entry.
    • 

  • Reusing a CID still in flight on the same SQ. Symptom: completions credited to the wrong request.
    • 




Transition box

Where you came from: F4-05's virtqueues and random test, F4-06's command structures and the habit of comparing with the device's configuration, F1-50 (HW205), where NVMe queues were introduced from the hardware side. What carries over: commands in memory, a write to start, completion matching, publication order, the host checks. What changes: no legacy protocol and no link to train; completions are recognised by a phase bit instead of an index the device publishes; queues are created by commands and can be many, one per CPU. Next: DR302 starts with milestone C7: MSI and MSI-X (so each queue can interrupt its own CPU) and the IOMMU (so devices reach only the memory you map for them). This is the last chapter of DR301; the course project below completes it.

Safety
"Expect that a bad driver can corrupt disks (wrong LBA, wrong DMA address)... Disconnect disks you care about while testing storage drivers on real hardware." (curriculum safety box). NVMe adds a trap: the system disk of most modern PCs is an NVMe SSD, often the only one. Never boot a test kernel with write tests on a machine whose NVMe drive holds anything you want; the lab's namespace 1 is an image file the script deletes.

Not tested in this build
Two parts of C6 are only partly met. Troubleshooting. "no NVMe controller": the device is missing or the machine is pc with the controller on a bridge (use q35). Timeout after CC.EN = 1: CSTS.CFS set, or AQA/ASQ/ACQ written while enabled. Queue creation fails: IOSQES/IOCQES not in CC, or the size above MQES. Hang after exactly n commands on a queue of n entries: the phase tag.

Mini-project and course project


Course project: the root file system on NVMe in QEMU. The lab reads a read-only archive. The project makes it a real root: put the NVMe driver under your kernel's block-device interface (B14) as one block device per namespace, put an ext2 file system on namespace 2 (built on the host with mke2fs, or by your own mkfs), mount it as / through your VFS, and read /etc/hostname and run /bin/init from it when your kernel has user space. Then run the random test with 1, 4 and 8 queues with one queue pair per CPU on your SMP kernel (8 CPUs in QEMU), with each CPU submitting only to its own queue.


Rubric (20 points): the root mounts from NVMe and the host's file list and hashes match the kernel's (6); per-CPU queues on 8 CPUs, random test passes with 1, 4 and 8 queues, checked by the host (5); writes through the file system survive a reboot (Flush before shutdown) and the host's e2fsck -n is clean (4); the phase-tag, CID and PRP rules covered by host-side unit tests of your queue code (3); every register and field you used cited to a section of D1–D3 after reading them (2).



Summary


    

  • NVMe is class 010802h with registers in BAR0; CAP describes queue limits, timeout, doorbell stride and page sizes.
    • 

  • Bring-up: disable and wait, admin queues in AQA/ASQ/ACQ, enable with entry sizes, wait for ready.
    • 

  • Identify Controller, the active namespace list and Identify Namespace describe the device; NN is the highest namespace ID, not a count.
    • 

  • I/O queues are created by admin commands, CQ before SQ; commands are 64 bytes, completions 16 bytes; doorbells carry indices.
    • 

  • A completion is new when its phase bit equals the expected phase; the phase flips on every wrap.
    • 

  • PRP1, PRP2 or a PRP list describe the data; MDTS limits a transfer.
    • 

  • The course project's root file system can live on an NVMe namespace and be checked file by file against the host.

Answers to Check yourself


    

  1. MQES = FFFh → 4096 entries; TO = 28h = 40 → 20000 ms; DSTRD = 0 → 4-byte stride (bits 35:32 of 0x00000020 in the high dword are 0; the 20h is bit 37, CSS bit 0, the NVM set).
    2. 

  2. Creating an SQ names the CQ its completions go to, so the CQ must exist; deleting a CQ while an SQ still posts to it would leave completions with nowhere to go.
    3. 

  3. Stride 4 << 2 = 16 bytes. SQ 5 tail: 1000h + 10 × 16 = 10A0h; CQ 5 head: 1000h + 11 × 16 = 10B0h.
    4. 

  4. Three pages: PRP1 = the buffer, PRP2 = the address of a PRP list holding buffer + 4 KiB and buffer + 8 KiB.
    5. 

  5. Driver and controller go round the queue in lockstep entry by entry: the controller writes entry i of pass k with phase k mod 2 (inverted), and the driver reads entry i of the same pass; tracking its own head's wraps gives the driver exactly the phase of the pass it is reading, without seeing the controller's position.
    6. 

  6. That namespace IDs go up to 256; Identify with CNS 2 (the active namespace list) gives the IDs in use, here 1 and 2.
    7. 

  7. MDTS = 0 means no limit reported by the controller; the driver must still limit transfers to what its PRP lists and buffers can describe, and to what the namespace's size and the block layer allow.
    8. 

  8. The slot index finds the request in one step, and the sequence number makes a CID different from the previous use of the same slot, so a stale completion for an old use of the slot is detected.
    9. 

  9. A successful write may still sit in the drive's volatile cache; Flush makes the controller commit it to non-volatile media, which a file system needs before it records that the data is safe (for example before a journal commit or a clean unmount).
    10. 



Forensic lab answer key


    

  1. QEMU completed 17 commands (17 pci_nvme_rw_cb lines); the driver counted 16 stale completions (only the first five are printed) and then waited 2000 ms for a completion that it never accepted.
    2. 

  2. 0x0100 = binary 1 00000 000: slot 0 (low 5 bits), sequence 8. Slot 0 is waiting for CID 0x0300 (sequence 24), the 17th I/O command. "SQ head 1" is the SQ head the controller reported when it completed the first I/O command: this is the pass-1 entry for the first command, read a second time.
    3. 

  3. The I/O CQ has 16 entries. Commands 1–16 filled pass 1 with phase 1, and the driver consumed them correctly (it expected 1). Command 17 is the first of pass 2, where new entries have phase 0; the driver still expects 1 and the old entries all have phase 1.
    4. 

  4. No: the controller completed 17 commands, one per command submitted. The driver read 16 old entries a second time.
    5. 

  5. After reading all 16 old entries the driver is back at entry 0, which now holds the real completion of command 17 with phase 0; a driver that wants phase 1 never takes it, and no other entry changes, so it times out.
    6. 

  6. Each stale read advanced the CQ head and wrote it to the CQ head doorbell, telling the controller that entries were consumed that it had not produced in this pass. The specification treats such a doorbell value as invalid (from memory, unverified); a real controller may report an error or behave unpredictably. QEMU tolerated it here (CSTS = 0x1, no fatal status).
    7. 

  7. Any test that runs more commands on a queue than it has entries: the chapter's random test (4000 operations on 64-entry queues) or simply a long sequential read. Kofi's desk tests stayed within one pass.
