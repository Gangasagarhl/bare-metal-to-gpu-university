Story hook

Until now every visitor to the school has handed things over at the front desk, one at a time: a byte through the UART's window, a scan code through the keyboard's hatch, a date read card by card off the hall clock. That works for letters. It does not work for furniture. When the school orders a hundred boxes of books, nobody wants the secretary to carry them in one by one.

So the school does what every real school does: it fills in delivery notes, pins them to an order board, and the delivery truck comes, reads the notes, drives the goods straight to the shelves the notes name, and writes in the receipt book what it delivered. The secretary only checks the receipt book. This chapter builds that arrangement for two virtual devices, a disk and a network card, using the cleanest interface there is for it: virtio. By the end your kernel will have written and checked four thousand random blocks of a 1 GiB disk at two queue depths, and sent an ARP request that you can see in a packet capture.

What you will be able to do

  • Find a modern virtio device's register blocks by walking its PCI vendor-specific capabilities.
  • Bring up a device through the status handshake: reset, acknowledge, driver, feature negotiation, features OK, driver OK.
  • Build a split virtqueue (descriptor table, available ring, used ring) and explain who writes which part.
  • Write a virtio-blk driver with up to 32 requests in flight and a virtio-net driver with receive and transmit queues.
  • Prove a block driver correct with a reproducible random-I/O test whose result the host checks independently.
  • Diagnose a driver whose device reports success for every request while the data is wrong.
Jargon box
DMA (direct memory access)
Simple words: a device reading or writing the computer's memory itself, without the CPU copying each byte. Analogy: the delivery truck driving the goods to the shelf. Precise: memory transactions started by a device (a PCI bus master) at addresses the driver gave it; the CPU only sets up the transfer and learns when it is done. D4
virtio
Simple words: a family of devices designed for virtual machines, with one shared way of talking to all of them. Analogy: suppliers who all accept the same order form. Precise: the OASIS "Virtual I/O Device (VIRTIO)" standard: common device status and feature negotiation, virtqueues for data, and transports (PCI, MMIO, channel I/O) that carry them. D1
virtqueue
Simple words: the queue in shared memory through which a driver hands buffers to a virtio device and gets them back. Analogy: the order board plus the receipt book. Precise: in the split layout, a descriptor table, an available ring written by the driver and a used ring written by the device. D1
Descriptor (virtio)
Simple words: one entry saying "here is a buffer, this long". Analogy: a delivery note naming a shelf and how much fits on it. Precise: a 16-byte entry: 64-bit physical address, 32-bit length, flags NEXT (another descriptor follows) and WRITE (the device writes this buffer), and the index of the next descriptor. D1
Feature negotiation
Simple words: device and driver agreeing which optional abilities they will both use. Analogy: the supplier lists the services it can offer; the school ticks the ones it will use. Precise: the driver reads the device's 64 feature bits, writes back a subset it understands, and sets FEATURES_OK; the device confirms by keeping the bit set. D1
Device status (virtio)
Simple words: a byte both sides use to record how far start-up has got. Analogy: the stamps on a supplier's contract: seen, assigned, terms agreed, active. Precise: a register in the common configuration with bits ACKNOWLEDGE (1), DRIVER (2), DRIVER_OK (4), FEATURES_OK (8), NEEDS_RESET (0x40) and FAILED (0x80); writing 0 resets the device. D1
Notification (virtio)
Simple words: the driver telling the device "look at the queue, there is new work". Analogy: phoning the depot. Precise: a write of the queue index to the queue's notify address, at notify-capability offset + queue_notify_off × notify_off_multiplier; also called a kick. D1

Layer 1 — the kid explanation

When a computer wants a lot of data from a disk, it does not ask for it one letter at a time. It writes little notes in its own memory: "please put block number 500 here, in this box". Then it pokes the disk to say "there are new notes". The disk reads the notes, puts the data straight into the boxes, and writes "done" in a list. The computer looks at the list and knows the data is there. Sending a message on the network works the same way, with notes that say "please send what is in this box".

Layer 2 — the student explanation

Virtio devices were designed for virtual machines, where the "hardware" is a program on the host. Because the designers could choose freely, the interface is simple and regular, which makes it the best first DMA driver. All virtio devices share one start-up procedure and one queue format; only the meaning of the buffers differs between a disk and a network card. D1

On PCI, a modern virtio device has vendor ID 0x1AF4 and device ID 0x1040 plus its type: 0x1042 for block, 0x1041 for network (R2 found both). Its registers are not at fixed places: the device's PCI capability list contains vendor-specific entries that say "the common configuration is at offset X of BAR Y", and likewise for notifications, interrupt status and device-specific settings. D1 R2

Start-up is a handshake through the device-status byte: reset, acknowledge, announce a driver, agree on features, confirm, set up the queues, and declare the driver ready. A queue is three tables in the driver's memory: descriptors that describe buffers, an available ring where the driver lists new requests, and a used ring where the device lists finished ones. The driver tells the device about new requests by writing to a notify address; the device tells the driver about finished ones by writing to the used ring (and, if the driver wants, by an interrupt; this chapter polls instead). D1

A virtio-blk request is a chain of three buffers: a 16-byte header (read or write, and the sector), the data, and a status byte the device fills in. A virtio-net packet is one buffer with a 12-byte header in front of the Ethernet frame; queue 0 receives and queue 1 transmits. Milestone C4 asks for exactly these: the generic transport, virtqueues, a block device and a network device. D1 D8

Layer 3 — the engineer's depth

The transport: capabilities and the common configuration

The driver enables memory decoding and bus mastering in the PCI command register first; without bus mastering the device cannot do DMA at all, and the failure is silent (requests never complete). It then walks the capability list from F4-02. Each vendor capability (ID 0x09) carries a type at byte 3, a BAR number at byte 4 and a 32-bit offset at byte 8; the notification capability adds a 32-bit multiplier at byte 16. The common configuration is a 56-byte structure: feature selectors and windows, the queue count, the status byte, and a "queue window" (queue_select chooses which queue the following fields describe). D1 R5

Feature bits are 64 bits read through a 32-bit window: write 0 to the selector and read the low half, write 1 and read the high half. Bit 32, VERSION_1, marks a modern device; a driver that does not accept it is talking the legacy protocol, with different layouts. The driver must accept only bits it understands. After writing its subset it sets FEATURES_OK and reads the status back: a device that cannot work with the subset clears the bit, and the driver must give up. D1

All the numbers were compared with the Linux UAPI headers installed on the build machine (38 values, 0 differences, R5) and the devices worked in QEMU 8.2.2 (R2); two independent implementations agreeing is evidence, not the specification. The handshake order and the rule "read FEATURES_OK back" are from memory only.

Split virtqueues

The descriptor table is an array of 16-byte descriptors. A request that needs several buffers links them with NEXT and the next index, forming a chain; the chain's first index (the head) identifies the request. The available ring holds flags, idx and an array of heads: the driver writes the head at ring[idx % size] and then increments idx. The used ring holds flags, idx and an array of (id, len) elements: the device writes the head it finished and the number of bytes it wrote into device-writable buffers, then increments its idx. Both indices are free-running 16-bit counters; only the array position is reduced modulo the queue size. D1

Ownership is the rule that makes this safe without locks: the driver writes descriptors and the available ring and only reads the used ring; the device does the opposite. Two orderings matter. The driver must write the ring entry before the new idx (otherwise the device may read a stale head), and must read the used element only after it has seen the new used idx. On x86, ordinary stores are seen by other agents in program order and loads are not reordered with older loads, so a compiler barrier suffices in this lab; on weakly ordered processors, Linux's virtio code uses real memory barriers at the same places. D2 D9

Not verified — check before relying on this

The x86 ordering statement is from memory of the Intel SDM's memory-ordering section (D9), and it holds for normal write-back memory, which is what the rings are here. The claim that Linux places barriers at these points is from memory of drivers/virtio/virtio_ring.c (D2), not opened during this build. The lab passed in QEMU with TCG on one virtual CPU, which does not exercise reordering at all: the lab cannot show that the barriers are sufficient. Also from memory of D1 only: the alignment rules for the three ring areas, the meaning of the available ring's flag bit 0, and that the used element's len counts the bytes written into device-writable buffers.

The available ring's flags bit 0 asks the device not to interrupt; this driver sets it because it polls (interrupts and MSI-X come in DR302, milestone C7). The ring layout requires the descriptor table to be 16-byte aligned, the available ring 2-byte aligned and the used ring 4-byte aligned in the modern layout; the lab puts the table and the used ring on 4 KiB boundaries, which satisfies stricter legacy rules as well. D1

virtio-blk

Every request is header + data + status. The header is {type, reserved, sector}; type 0 reads (IN, from the device's point of view the data goes in to the driver), type 1 writes. Sectors are always 512 bytes in this header, whatever the disk's logical block size. The status byte is 0 for OK, 1 for an I/O error and 2 for unsupported. The data descriptor of a read must carry WRITE, because the device writes it; the status descriptor always carries WRITE. The capacity, in 512-byte sectors, is the first 64-bit field of the device configuration. D1 R5

Several requests may be in flight, and the device may finish them in any order. The driver therefore keeps a table from head index to request (here: to a slot with its own buffer, header and status byte), and the test never has two requests on the same block in flight at once, because their order of completion is not defined.

virtio-net

The network device needs buffers before any packet arrives, so the driver posts receive buffers (device-writable) to queue 0 at start-up and gives each back after reading it. Transmit buffers go to queue 1 and are device-readable. Each packet starts with a virtio-net header; with VERSION_1 negotiated it is 12 bytes (R5), and with no offloads negotiated it is all zeros on transmit. The driver accepts only the MAC feature, so it can read the MAC address from the device configuration. D1 R5

Proving a block driver correct

"The reads returned no errors" proves nothing: Section "Forensic lab" shows a driver for which every request succeeds and nearly every read is wrong. The test in iotest.cc writes a pattern that depends on the block number and a per-block generation counter, so every read has a known expected content, including "all zero" for never-written blocks. It is driven by a seeded xorshift generator, so the host can replay the same sequence and check the disk image after QEMU exits, an independent check that does not trust the kernel's own reading code. The curriculum's test is "random-read and random-write test over 1 GiB with checksum, with queue depth 1 and 32"; the lab runs 4000 operations at each depth, chosen uniformly over the 262144 blocks of 4 KiB, and compares the full contents instead of a checksum. D8 R2 R3

How the hardware actually does it

In this lab the "device" is code inside the QEMU process. A write to the notify address is an MMIO access that QEMU intercepts; QEMU then reads the guest's rings from the guest's memory, which for QEMU is ordinary host memory, performs the read or write on the image file, writes the data into the guest buffers and updates the used ring. That is DMA in effect: the guest CPU never copies the data. With KVM, the notify write causes an exit from the guest to the hypervisor, which is why virtio drivers try to batch requests and kick once per batch; mechanisms that avoid even that (event index suppression, the vhost kernel back-end, devices implemented in hardware) are beyond this chapter. D1 D7

On a real PCIe device, DMA is a bus-master memory read or write request travelling up through the root complex to the memory controller. The addresses the driver puts in descriptors are physical (here: paging is off, so virtual = physical); with an IOMMU, they become I/O-virtual addresses that the IOMMU translates, which is milestone C7. D4 D8

Not verified — check before relying on this

That KVM exits on the notify write, that vhost and hardware virtio implementations exist, and what they do, are from the author's general knowledge, not from a source opened in this build. Nothing in this chapter ran on physical hardware or under KVM (the build container has no KVM).

Worked example

Decoding the feature offer. R2 shows the block device offering 0x10130006e54. Write it in binary and list the set bits: 2, 4, 6, 9, 10, 11, 13, 14, 28, 29, 32, 40. Looking each number up in the installed Linux headers (<linux/virtio_blk.h>, <linux/virtio_ring.h>, <linux/virtio_config.h>, D3) gives: SEG_MAX, GEOMETRY, BLK_SIZE, FLUSH, TOPOLOGY, CONFIG_WCE, DISCARD, WRITE_ZEROES (device-specific, bits below 24), INDIRECT_DESC, EVENT_IDX (ring features), VERSION_1 and RING_RESET (transport features). The driver asked for nothing optional, so it accepted only bit 32: 0x100000000. The network device offered 0x10130bf8024, which includes MAC (bit 5); the driver accepted MAC and VERSION_1: 0x100000020 = bit 32 + bit 5. R2 D3

Where the queue lives. R2's line virtio queue 0: size 128 (device max 256), desc 0x136000 avail 0x136800 used 0x137000. The device offered 256 entries; the driver wrote 128, the size of its arrays. Descriptor table: 128 × 16 = 2048 bytes, so the available ring follows at 0x136000 + 0x800 = 0x136800. The available ring needs 2 + 2 + 128 × 2 + 2 = 262 bytes, and the used ring is aligned up to the next 4 KiB: 0x137000. R2

A request in numbers. Block 1000 (4 KiB blocks) is sector 1000 × 8 = 8000. A read of it is: header {0, 0, 8000} (16 bytes, device-readable), data (4096 bytes, NEXT | WRITE = 3), status (1 byte, WRITE = 2). When the device completes it, the used element's len counts the bytes it wrote: 4096 + 1. D1

The ARP request. 42 bytes: destination ff:ff:ff:ff:ff:ff, source 52:54:00:12:34:56, EtherType 0x0806, then hardware type 1, protocol 0x0800, lengths 6 and 4, operation 1, sender MAC and IP 10.0.2.15, target MAC zero, target IP 10.0.2.2 (QEMU's user-mode network gateway). The device receives 12 + 42 = 54 bytes. R4 shows the request and the reply exactly as tshark decodes them. D6 R4

Where the analogy breaks


    

  • A truck that is not there. In this lab the "device" is a program on the same machine, and its "truck" is a memory copy by the host. The analogy suggests distance and travel time that do not exist here, which is why virtio is fast in a VM and why the emulated timings in R2 say nothing about real disks.
    • 

  • The truck reads the notes whenever it likes. A real delivery company waits for the phone call; a virtio device may look at the available ring at any moment, even before the kick. That is why the order of writes (entry before index) matters and why the analogy's "fill in the note, then pin it up" must be taken literally.
    • 

  • Delivery notes are reused at once. The school keeps old delivery notes; the driver recycles descriptors as soon as the device returns them. A descriptor freed too early (before the used ring says so) is a bug the analogy does not warn about.
    • 




Common mistakes and debugging


    

  • Bus mastering not enabled. Symptom: the first request never completes; the used idx stays 0. Check the PCI command register.
    • 

  • WRITE flag missing on a read's data buffer. Symptom: status OK, data unchanged (forensic lab).
    • 

  • Index published before the entry. Symptom: rare, load-dependent wrong requests; often invisible on x86 and in emulation.
    • 

  • Comparing ring indices modulo the size. Symptom: the driver stops after 65536 or after size requests. The indices are free-running 16-bit counters; only the array position is reduced.
    • 

  • Accepting all offered features. Symptom: the device changes behaviour (for example, event-index notification rules, a different header size) and the driver hangs. Accept only what you implement.
    • 

  • Forgetting to post receive buffers. Symptom: the transmit works (the capture shows the request) but nothing is ever received.
    • 

  • Two requests on one block in flight. Symptom: the random test reports a few bad reads that move from run to run. The test or the block layer must order them.
    • 




Transition box

Where you came from: F4-02's capability walk and BAR sizing, F4-03's PIT clock, F3-31 (OS304), where a kernel gets a block-device interface on a RAM disk (if you have taken it), and F1-50 and F1-52 (HW205), where queues, doorbells and descriptor rings were introduced from the hardware side. What carries over: matching devices by ID, the driver-model shape (probe, then use), printing raw values, host-side tests. What changes: data no longer passes through registers: the driver writes descriptions of memory and the device moves the data itself, so correctness now depends on memory layout, ownership and ordering, and the proof of correctness has to look at the data. Next: F4-06 drives AHCI, a real hardware interface with the same ideas (command lists, physical region descriptors, a status register) and much more ceremony, and runs the same test on it.

Safety
The curriculum's warning applies from this chapter on: "Expect that a bad driver can corrupt disks (wrong LBA, wrong DMA address)... Never point the -drive file= option at a real disk device or at an image you want to keep.

Summary


    

  • A modern virtio-pci device is found by its vendor capabilities; the common configuration carries status, features and the queue window.
    • 

  • Start-up is a handshake: reset, ACKNOWLEDGE, DRIVER, feature subset, FEATURES_OK (read back), queues, DRIVER_OK.
    • 

  • A split virtqueue is a descriptor table and an available ring written by the driver, and a used ring written by the device; write order and ownership make it safe.
    • 

  • virtio-blk requests are header + data + status chains; virtio-net packets carry a 12-byte header and need receive buffers posted in advance.
    • 

  • A block driver is proved by checking data, not status: a seeded random test checked by the kernel and again by the host.
    • 

  • A missing WRITE flag gives success statuses and wrong data: the device can only write where the driver allows.

Forensic lab answer key


    

  1. The trace shows every request completed with status 0 (8000 completion events for 8000 operations), and the kernel saw status 0 too (0 errors); but nearly every read fails the content check: 1999 of 2000 at depth 1 and most of the depth-32 reads, and the run fails (exit code 3).
    2. 

  2. Write requests never needed the WRITE flag on the data descriptor (the device reads that buffer), so writes are unchanged; only reads require the device to write into the buffer, and without the flag that buffer is device-readable only.
    3. 

  3. The buffer still holds what the slot held before: the pattern of the last block written through that slot. The device did not overwrite it. (A likely mechanism in QEMU is that it sees no device-writable data buffer, so it transfers zero bytes and still completes with status 0; this is inferred from the evidence, not checked in QEMU's source.)
    4. 

  4. At depth 1 every request uses slot 0. The first read happened before slot 0 had ever been used for a write, so its buffer was still the zero-filled static memory, and the block expected was never written (zero): the check passed by accident.
    5. 

  5. From the device's point of view the request was well formed: it read nothing into a buffer it was not allowed to write, which is not an error. The used element's len field should have shown it: for a correct read it counts the bytes written into device-writable buffers, 4097 (data + status); here only the status byte was writable, so it should be 1. The lab does not print len, so this is a prediction to check (lab step: print it). A driver that compares len with the expected length notices.
    6. 

  6. Any test that reads data back and compares it, like the chapter's random test; Tomás's test checked writes and statuses only. The used ring's len field should reveal it without any content check (a prediction: the lab does not print it).
    7.
