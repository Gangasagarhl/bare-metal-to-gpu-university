Story hook

In F4-01 the school office kept a list of visitors written by someone else in advance, and half of it was wrong. A better school puts a sign-in book at every entrance. Each visitor writes their own name, where they come from, what they are here for, and which rooms they will need. The office no longer guesses: it walks to every entrance, reads every book, and sends an interpreter for each line. If an entrance opens onto a second building, the office walks through and reads the books there too.

PCI is that sign-in system. Every device on a PCI or PCI Express bus carries a small block of memory, its configuration space, in which it says who made it, what kind of device it is, how much address space it needs, and which optional features it has. In this chapter your kernel reads every one of those blocks on QEMU's q35 machine, works out where each device's registers are, follows bridges to buses behind them, and hands the result to the driver model of F4-01. Then it compares its list, line by line, with the list QEMU itself prints.

What you will be able to do

  • Read PCI configuration space through the legacy I/O ports 0xCF8/0xCFC and through ECAM, and find the ECAM window in the ACPI MCFG table.
  • Enumerate every function on every bus, including multi-function devices and buses behind PCI-to-PCI bridges.
  • Size a BAR by writing all ones, and decode I/O, 32-bit and 64-bit memory BARs correctly.
  • Walk the capability list and the PCI Express extended capability list, and name the capabilities that matter to drivers (MSI, MSI-X, PCI Express, power management).
  • Bind drivers by vendor/device ID or by class code, as real kernels do for standard interfaces such as AHCI and NVMe.
  • Verify an enumerator against an independent listing (QEMU's own) and explain every difference.
Jargon box
Configuration space
Simple words: a small block of registers every PCI device has, which describes the device and controls its basic behaviour. Analogy: the visitor's own line in the sign-in book. Precise: 256 bytes per function in conventional PCI (4096 bytes in PCI Express), starting with a standard header (vendor ID, device ID, command, status, class code, header type, BARs, capability pointer, interrupt line and pin). D1 D2
Bus, device, function (BDF)
Simple words: the three numbers that address one PCI function, written bb:dd.f. Analogy: building, entrance, line in the book. Precise: an 8-bit bus number, a 5-bit device number and a 3-bit function number; a physical device may implement up to eight functions. D1
ECAM
Simple words: a way to read configuration space as ordinary memory. Analogy: a photocopy of every sign-in book laid out on one long table. Precise: the Enhanced Configuration Access Mechanism of PCI Express: a memory window in which each function's 4 KiB configuration space is at base + (bus << 20 | device << 15 | function << 12); its base and bus range come from the ACPI MCFG table. D2 D3
BAR (base address register)
Simple words: a register in which a device says how big a window of addresses it needs, and the firmware or OS writes where that window is. Analogy: "this visitor needs a room of this size"; the office writes in the room number. Precise: a configuration register at 0x10–0x24 (type 0 header) describing one I/O or memory region; low bits encode the type (I/O, 32-bit or 64-bit memory, prefetchable); the size is found by writing all ones and reading back which address bits are writable. D1
Class code
Simple words: three bytes that say what kind of device it is, regardless of who made it. Analogy: "here for: a lesson on mass storage". Precise: base class, subclass and programming interface at configuration offset 0x09–0x0B, for example 01.06.01 (mass storage, SATA, AHCI 1.0) or 01.08.02 (mass storage, non-volatile memory, NVM Express). D1
PCI-to-PCI bridge
Simple words: a device that connects a second PCI bus behind it. Analogy: a door to a second building with its own entrances. Precise: a function with a type 1 header holding primary, secondary and subordinate bus numbers and the address ranges it forwards; PCI Express root ports and switch ports appear to software as such bridges. D1 D2
Capability list
Simple words: a chain of optional feature descriptions inside configuration space. Analogy: extra pages stapled to the sign-in line: "also speaks sign language", "has a phone". Precise: a linked list starting at the pointer at offset 0x34 (when status bit 4 is set), each entry an ID byte and a next pointer; PCI Express adds an extended list at offset 0x100 with 16-bit IDs, reachable only through ECAM. D1 D2
MCFG table
Simple words: the firmware table that tells the OS where ECAM is. Analogy: the note saying which table the photocopies are on. Precise: an ACPI table (signature "MCFG") defined by the PCI Firmware Specification, listing for each PCI segment group the ECAM base address and the range of bus numbers it covers. D3

Layer 1 — the kid explanation

Many helpers in a computer sit on a shared road called PCI. Each helper keeps a little card that says who made it, what kind of helper it is, and how much space it needs to work. When the computer starts, the operating system walks along the road and reads every card. Some cards say "there is another road behind me"; the operating system walks that road too. At the end it has a full list, and it gives each helper a translator that knows its kind.

Layer 2 — the student explanation

Every PCI function has a configuration space. Its first 64 bytes form a standard header: vendor and device ID at offsets 0 and 2, the command register at 4 (bits that switch on I/O decoding, memory decoding and bus mastering), status at 6, revision and class code at 8–0xB, header type at 0xE (0 for normal devices, 1 for bridges, bit 7 for multi-function), six BARs at 0x10–0x24, the capability pointer at 0x34, and the interrupt line and pin at 0x3C and 0x3D. A read of the vendor ID that returns 0xFFFF means no function is there, the same "all ones" signature as in F4-01. D1

Enumeration is a loop: for bus 0, for each of 32 devices, read function 0's vendor ID; if a device is present and its header type has the multi-function bit, also try functions 1 to 7; if a function is a bridge, read its secondary bus number and scan that bus the same way. Each function found is reported to the driver model with its IDs, class code and resources. Drivers match by exact vendor and device ID when they handle one chip (the e1000), by vendor alone when one vendor's interface covers many devices (virtio), and by class code when the interface is a standard (AHCI, NVMe, xHCI, HD Audio). D1 D4

The BARs tell the driver where the device's registers are. Firmware (SeaBIOS in QEMU, or UEFI) has already written addresses into them; the kernel reads them back and also needs each region's size, which the device announces in a roundabout way: write all ones to the BAR, read it back, and the bits that stayed zero are the size bits. The low bits of a BAR are not address bits: bit 0 says I/O or memory, bits 2–1 say 32-bit or 64-bit memory, bit 3 says prefetchable. A 64-bit BAR uses the next BAR for its upper 32 bits. Getting this wrong is the forensic lab of this chapter.

Configuration space has two doors. The old one, two I/O ports at 0xCF8 (address) and 0xCFC (data), reaches only the first 256 bytes of each function. The PCI Express door, ECAM, maps each function's full 4 KiB into physical memory, which is how the kernel reaches the extended capability list at 0x100. The firmware tells the kernel where the ECAM window is through the ACPI MCFG table. The lab kernel uses ECAM when MCFG exists (q35) and falls back to the ports when it does not (the older pc machine), exactly as milestone C1 asks.

Layer 3 — the engineer's depth

Finding MCFG

The kernel finds ACPI's root pointer (RSDP) by scanning the BIOS area 0xE0000–0xFFFFF on 16-byte boundaries for the signature "RSD PTR " with a valid checksum; on a UEFI system the firmware passes the RSDP address in its configuration table instead (F3-12, F3-15). The RSDP points to the RSDT (32-bit entries) or, from revision 2, the XSDT (64-bit entries); each entry points to a table with a 36-byte common header. MCFG's entries start at offset 44 and are 16 bytes each: 64-bit base address, segment group, start bus, end bus. QEMU's q35 firmware gave one entry, base 0xb0000000, buses 0–255 (R2). The ECAM address for bus b is computed relative to the entry's start bus, a detail that matters on machines whose segments start above bus 0. D3 D5 R2

Bridges and bus numbers

A type 1 header has three bus numbers: primary (the bus the bridge sits on), secondary (the bus directly behind it) and subordinate (the highest bus number reachable behind it). Configuration cycles for buses in the range secondary..subordinate are forwarded through the bridge. Someone has to assign those numbers: on a PC the firmware does it during boot, and the lab enumerator trusts the result (it follows the secondary number if it is larger than the current bus). A kernel that supports hot-plug or runs on firmware that does not number bridges must assign numbers itself, depth first, and reprogram each bridge's forwarding windows; that is the mini-project. PCI Express makes every link a point-to-point connection, so each root port and each switch downstream port is a bridge with exactly one device behind it, but the software model is unchanged. D1 D2

BAR sizing, precisely

For each BAR: switch off I/O and memory decoding in the command register (otherwise the device decodes the temporary all-ones address and may claim accesses meant for something else), save the BAR, write 0xFFFFFFFF, read the result, restore the saved value, and restore the command register at the end. For a memory BAR, clear the four low type bits of the read-back value; the remaining value is a mask whose lowest set bit is the size: size = ~mask + 1. For a 64-bit BAR (type bits 2–1 equal to 10b), the same is done to the next BAR, which holds address and mask bits 63–32, and the two are combined before inverting. For an I/O BAR, the low two bits are cleared and the result is limited to 16 bits on x86. A read-back of 0 means the BAR is not implemented. Bridges have only two BARs; their remaining header space holds bus numbers and forwarding windows. D1

Watch out

Writing the command register as a 16-bit value through a 32-bit configuration access also writes the status register next to it, and most status error bits are write-1-to-clear. Writing back the status bits you read clears any error the device had recorded. Listing 2 does this knowingly (comment at line 84); a production kernel writes zero to the status half or uses a true 16-bit access.

Capabilities

If status bit 4 is set, offset 0x34 points to the first capability. Each capability starts with an ID byte and a next-pointer byte; the list ends at pointer 0. The IDs a driver writer meets first: 0x01 power management, 0x05 MSI, 0x09 vendor-specific (virtio uses five of them to locate its register structures, F4-05), 0x10 PCI Express, 0x11 MSI-X. Extended capabilities (PCI Express only) start at 0x100 with a 32-bit header: ID in bits 15–0, version in bits 19–16, next offset in bits 31–20. The lab's root port shows extended IDs 0x0001 (advanced error reporting) and 0x000d (access control services) in R2. MSI and MSI-X are only listed here; DR302 (F4-08) programs them. D1 D2 R2

Not verified — check before relying on this

The header offsets, command bits, BAR type bits and capability IDs were written from memory of the PCI Local Bus Specification (D1) and agree with Linux's <linux/pci_regs.h> in the build container (Listing 6, R7: 28 values, no difference). The ECAM bit layout, the extended capability header format and the names of extended capabilities 0x0001 and 0x000d are from memory of the PCI Express Base Specification (D2) and are confirmed only by QEMU's model behaving as expected (the extended list walk terminates and the ECAM reads return the same IDs as the port reads). The MCFG entry layout and offset 44 are from memory of the PCI Firmware Specification (D3), confirmed only by QEMU's table parsing correctly. The RSDP search area is from memory of the ACPI Specification (D5).

Binding by class, and what Windows and Linux do

Standard interfaces are bound by class code: any function with class 01.06.01 is an AHCI controller and any with 01.08.02 is an NVMe controller, whoever made it. Linux PCI drivers list such class entries in their ID tables; Windows' in-box storage miniports (storahci, stornvme) are matched through compatible IDs derived from the class code, while a vendor's own driver (amdsata in the project's DRIVERS.html test boot) matches a more specific hardware ID and therefore wins. Your model's rule, "the first driver whose table matches and whose probe returns 0", is simpler; if you want "more specific wins", sort candidates by match quality before probing. D4 D6 D7

How the hardware actually does it

A configuration read is a special bus transaction. On conventional PCI, the host bridge turns the value at 0xCF8 into a type 0 configuration cycle (for bus 0, with a dedicated select line for the target device) or a type 1 cycle (for other buses, which bridges convert into type 0 cycles on their secondary bus). On PCI Express the root complex sends configuration request packets, routed by bus and device number, to the right link; an ECAM memory access inside the window is converted by the root complex into such a request. When no function answers, the request completes with an "unsupported request" status and the root complex returns all ones to the CPU. Devices get their BAR windows decoded by the bridges above them, which forward a memory or I/O transaction only if its address falls into the window programmed into that bridge. D1 D2

QEMU emulates these structures in software; the lab cannot show timing or electrical behaviour. Real machines also have devices that need quirks (wrong class codes, BARs that must not be sized while in use, functions that are hidden). The curriculum's universal method (section 5) handles those through the documentation tiers; on QEMU none appeared.

Worked example

Sizing three BARs from raw reads. The lab kernel printed the raw values for the e1000 and the NVMe controller (R2), and Listing 5 recomputes them on the host (R3).

  1. e1000 BAR0: original 0xfe680000, after ones 0xfffe0000. Bit 0 = 0: memory. Bits 2–1 = 00: 32-bit. Bit 3 = 0: not prefetchable. Mask = 0xfffe0000 (low four bits already 0). As a 32-bit value, ~mask = 0x0001ffff, +1 = 0x20000: 128 KiB at 0xfe680000.
  2. e1000 BAR1: original 0x0000c081, after ones 0xffffffc1. Bit 0 = 1: I/O. Clear bits 1–0: 0xffffffc0. ~mask + 1 = 0x40; address 0xc080: 64 ports from 0xc080.
  3. NVMe BAR0: original 0xfe6a0004, after ones 0xffffc004. Bits 2–1 = 10: 64-bit, so BAR1 is the upper half: original 0x00000000, after ones 0xffffffff. Combined mask = 0xffffffff_ffffc000; ~mask + 1 = 0x4000: 16 KiB at 0x00000000_fe6a0000.

QEMU's own listing agrees: e1000 "BAR0: 32 bit memory at 0xfe680000 [0xfe69ffff]" (end − start + 1 = 0x20000), "BAR1: I/O at 0xc080 [0xc0bf]", NVMe "BAR0: 64 bit memory at 0xfe6a0000 [0xfe6a3fff]" (R4). R2 R3 R4

A configuration address. The AHCI controller is 00:1f.2 and its ABAR is BAR5 at offset 0x24 (F4-06). Legacy: 0x80000000 | (0 << 16) | (31 << 11) | (2 << 8) | 0x24; 31 << 11 = 0xF800, 2 << 8 = 0x200, total 0x8000FA24. ECAM: (31 << 15) | (2 << 12) = 0xF8000 + 0x2000 = 0xFA000, plus 0x24, plus the base: 0xB00FA024 (Figure 2).

Where the analogy breaks


    

  • Visitors write their own line, but the office writes the room numbers. A BAR is half description (its size and type, fixed by the device) and half assignment (its address, written by firmware or the OS). The sign-in book has no part that the office fills in and the visitor then obeys.
    • 

  • Reading a sign-in book has no side effects; sizing a BAR does. While all ones are in a BAR, the device would answer at a nonsense address if decoding were on. A book never moves the visitor to another room while you read it.
    • 

  • The building behind a door must be numbered first. Bus numbers are assigned by software (firmware or kernel), and until a bridge's numbers are set, nothing behind it can be reached. Buildings have their names before anyone arrives.
    • 




Common mistakes and debugging


    

  • Treating the upper half of a 64-bit BAR as a BAR. Symptom: phantom regions at address 0 with size 0x10, and drivers mapping the wrong registers on machines that place BARs above 4 GiB. This is the forensic lab.
    • 

  • Sizing with decoding on. Symptom: rare hangs or a device answering for another's addresses during boot, usually not on QEMU. Clear the command bits first.
    • 

  • Scanning functions 1–7 of single-function devices. Symptom: the same device listed eight times. Check the multi-function bit.
    • 

  • Expecting extended capabilities through the ports. Symptom: offset 0x100 reads wrap around to offset 0 or return garbage. Use ECAM.
    • 

  • Including the expansion ROM in comparisons. QEMU lists the e1000's option ROM as BAR6 with an all-ones address (R4); it lives at configuration offset 0x30, not among BARs 0–5, and the kernel does not size it. compare.py leaves it out on purpose.
    • 

  • Trusting the interrupt line register. It is a scratch byte firmware writes for the legacy PIC; with the IOAPIC or MSI it may be meaningless. F4-03 and F4-06 use it only because the lab kernel keeps the PIC.
    • 




Transition box

Where you came from: F4-01, where devices came from a hand-written table and probe had to prove presence; HW204 F1-45, where PCI Express was links, lanes and packets; OS301 F3-12, where ACPI tables were things firmware hands over. What carries over: the driver model, unchanged; the all-ones signature of "nobody there"; ACPI's table walk. What changes: devices describe themselves; resources (BARs, interrupt pins) come from the device and the firmware, not from constants; matching can be by class instead of by name; the kernel must follow bridges. What comes next: F4-03 turns two legacy devices, the UART and the i8042, into interrupt-driven drivers; F4-05 uses the vendor-specific capabilities found here to locate virtio's registers.

Summary


    

  • Every PCI function describes itself in configuration space: IDs, class code, header type, BARs, capabilities, interrupt pin.
    • 

  • Configuration space is reached through ports 0xCF8/0xCFC (256 bytes) or through ECAM (4 KiB, base from ACPI MCFG).
    • 

  • Enumeration scans buses, devices and functions and follows bridges through their secondary bus numbers.
    • 

  • BAR sizing writes all ones with decoding off; type bits decide I/O, 32-bit or 64-bit (two registers) memory.
    • 

  • Drivers bind by exact ID, by vendor, or by class code for standard interfaces; the F4-01 model works unchanged.
    • 

  • An independent listing (QEMU's) turns enumeration into a test with a verdict.
