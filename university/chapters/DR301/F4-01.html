Story hook

A school receives visitors all day long: a delegation from a partner school abroad, an inspector, a parent who speaks only Portuguese, a deaf guest who signs. The principal cannot learn every language. Instead the school keeps a list of interpreters. When a visitor signs in at reception, the office looks up an interpreter who claims that language, and the interpreter walks over and says a few words first, to check that the visitor really speaks it. Only then does the interpreter stay with the visitor for the rest of the day, translating every request in both directions, handling the misunderstandings, and telling the office when the visitor leaves.

Sometimes the sign-in book is wrong. Someone wrote "Room 2: visitor from Lyon" in the morning, but nobody came. An interpreter who skips the first greeting will spend the day translating for an empty chair, and will report everything as fine. This chapter is about the interpreters of a kernel, its drivers, and about the small set of rules that lets a kernel add, match, start and remove them without knowing any device in advance. You will build those rules, write a first driver for the PC's serial port against them, and watch what happens when a driver forgets to greet its visitor.

What you will be able to do

  • Define a driver by what it does: it owns a device's registers, interrupts and memory, translates kernel requests into register sequences, and reports errors upward.
  • Draw the driver stack from an application down to the device, and say which layer owns which decision.
  • Build a driver model with devices, drivers, match tables, probe and remove, and explain why binding is a separate step from discovery.
  • Write a typed register-access layer in C++ in which a write to a read-only register or a wrong-width access fails at compile time.
  • Write a probe function that proves a device is present before claiming it, and a remove that leaves it quiet.
  • Check register constants written from memory against an independent source (here Linux's user-space headers), and say what such a check proves and what it does not.
  • Diagnose a driver that "works" on a device that is not there.
Jargon box
Device driver
Simple words: the part of the kernel that knows how to talk to one kind of device. Analogy: an interpreter for a visitor who speaks another language. Precise: kernel code that owns a device's resources (register ranges, interrupt lines, DMA memory), implements a subsystem's interface (block, character, network, input) on top of the device's programming interface, and handles its errors and lifecycle. D2 D3
Driver model
Simple words: the kernel's rules for which driver serves which device. Analogy: the office's list of interpreters and the rule for assigning them. Precise: the data structures and procedures that record discovered devices, registered drivers and the bindings between them, and that call each driver's probe and remove at the right moments. D2 D3
Probe
Simple words: the driver's first contact with a device it might serve; it may say no. Analogy: the interpreter's first greeting. Precise: a driver callback invoked when a device matches one of the driver's IDs; it checks the device, acquires its resources, initialises it and returns success (the driver now owns the device) or an error (the device stays unbound). D3
Match table
Simple words: the list of device identities a driver says it can handle. Analogy: the languages an interpreter lists on the office board. Precise: an array of identifiers (PCI vendor/device IDs or class codes, ACPI or devicetree compatible strings) that the driver model compares with a device's identity before calling probe. D3
Platform device
Simple words: a device that cannot announce itself, so the kernel learns about it from a table or a convention. Analogy: a visitor written into the sign-in book in advance by someone else. Precise: a device at fixed addresses known from firmware tables (ACPI, devicetree) or platform convention (the PC's legacy I/O ports), as opposed to a device on a bus that can be enumerated, such as PCI. D3
Register map
Simple words: the list of a device's control and status boxes and where each one is. Analogy: the visitor's phrasebook: which word means what. Precise: the offsets, widths, reset values, field layouts and access rules (read-only, write-only, read/write, write-1-to-clear) of a device's registers, as given by its specification or datasheet. D1
Write-1-to-clear (RW1C)
Simple words: a status bit you switch off by writing a 1 to it. Analogy: pressing the lit button on a call panel to say "seen". Precise: an access rule in which writing 1 to a bit clears it and writing 0 leaves it unchanged, so software can acknowledge some events without losing others that arrived meanwhile. D4
Port I/O
Simple words: x86's separate small address space for devices, reached with special instructions. Analogy: the internal phone numbers of the school, separate from street addresses. Precise: a 64 Ki-entry I/O address space accessed with the IN and OUT instructions; legacy PC devices such as the 16550 UART at 0x3F8 live there (F1-41). D5

The idea in pictures

Figure 1 is the driver stack (guide 9.2). Read it from the top: a program asks for something through a system call, a subsystem turns the request into an operation on a class of devices, a driver turns that into register reads and writes on one device, and the bus carries those accesses to the device. Interrupts and completed data travel the other way. Figure 2 shows the driver model of this chapter: devices on one side, drivers on the other, and the binding in between.

Layer 1 — the kid explanation

A computer has many helpers: a keyboard, a disk, a network card, a clock. Each helper speaks its own small language made of numbers written into little boxes. The operating system does not learn all those languages. For each helper it uses a translator program called a driver. The driver knows which box to fill with which number to make the helper do something, and it knows how to read the helper's answers.

Before a driver starts translating, it checks that the helper is really there, by saying something and waiting for the right reply. If nobody answers, the driver says "not here" and the operating system leaves that spot empty.

Layer 2 — the student explanation

A device presents a programming interface: a set of registers at some addresses, possibly an interrupt line, possibly the ability to read and write main memory itself (DMA). The device's specification or datasheet describes that interface: which register is at which offset, which bits mean what, what to write in which order to start an operation, and how the device reports completion and errors. A driver is the code that implements one device's programming interface on one side and one of the kernel's internal interfaces on the other. The 16550 UART driver of this chapter offers "write a string" upward and performs "wait until the Line Status Register says the transmitter is empty, then write one byte to the Transmitter Holding Register" downward. D1 D3

Three questions shape every driver model, in Linux, in Windows and in your kernel. How does the kernel learn that a device exists? Some buses can be asked: PCI devices answer configuration reads with their vendor and device IDs (F4-02). Others cannot: nothing on a PC announces that a serial port lives at I/O port 0x3F8; the kernel learns it from a firmware table or from convention, and such devices are called platform devices. Which driver serves which device? Each driver publishes a match table, and the model compares identities. When does a driver own a device, and when does it let go? The model calls probe when a driver might take a device and remove when it must give it back, for example when the device is unplugged or the driver is unloaded. D2 D3

Discovery and binding are separate on purpose. The bus reports what might be there; the driver decides whether it is there and whether it can handle it. A table entry for COM2 says only that a PC usually has a second serial port at 0x2F8. On QEMU's machine with one serial port, nothing answers there, and the driver's probe must notice. The lab shows both cases.

Registers deserve their own layer of code. A driver that writes outb(0x3F8 + 3, 0x80) in twenty places is hard to read and easy to get wrong. The lab's reg.h turns each register into a C++ type that carries its offset, width and access rule. A read of a write-only register or a plain write to a read-only one becomes a compile-time error, and the same driver code can run against a fake bus on the host for testing. This is the register-access layer that the course's practical exam asks you to write for a new device.

Layer 3 — the engineer's depth

What a driver owns

A driver's responsibilities go beyond translation (the analogy's limit, see below). It owns resources: register windows (I/O port ranges or memory-mapped BARs), interrupt lines or message-signalled vectors, DMA buffers and descriptor rings, and timers for timeouts. It owns state: whether the device is initialised, which requests are in flight, which errors have occurred. It owns policy for errors: retry, reset the device, report an I/O error upward, or give up and mark the device dead. And it owns ordering: which register writes must happen before which, and which memory writes must be visible to the device before a doorbell write (F4-05 to F4-07). D2 D3

The model in Linux and in Windows

Linux describes the same three objects with struct device, struct device_driver and struct bus_type; a bus type has a match function and calls the driver's probe on a match, and PCI drivers carry an ID table of vendor, device and class entries. Windows uses device objects stacked into a device stack (a physical device object created by the bus driver, a functional device object created by the function driver, and optional filter objects), with the Plug and Play manager matching hardware IDs from the bus driver against the INF files of installed drivers and loading the driver on demand. The project's DRIVERS.html shows this from the outside: in the test machine's boot trace, pci, disk and storage drivers start early as boot-start drivers, and most others start "on demand" once Plug and Play finds their hardware. Your C1 model needs the same lifecycle, without the generality. D2 D3 D6

Probe: prove, acquire, initialise, publish

A good probe has four steps in this order. Prove the device is the one expected: for a platform device, a harmless read-write test of a register that has no side effects; for a PCI device, the IDs already prove it, but the revision or a capability may still rule it out. Acquire the resources and record them so that remove can release exactly what was taken. Initialise the device into a known state: reset it if the specification provides a reset, then program it. Publish the service upward (register a TTY, a block device, a network interface) only when everything else succeeded, because the moment it is published other code can call it. If any step fails, undo the earlier ones and return an error; the device stays unbound and the next matching driver may try. D3

The 16550 probe in Listing 4 proves presence twice. First it writes two complementary values to the scratch register at offset 7, which the datasheet describes as a register with no effect on the UART; reading back the same values rules out an empty bus, where reads on QEMU return all ones (the forensic lab shows this). Then it enables the internal loopback mode of the Modem Control Register, sends one byte and checks that the receiver got it, which proves that the transmit and receive paths work without sending anything on the wire. D1 R2 R4

Remove: leave the device quiet

remove is the reverse of probe and is easy to forget because the lab rarely unloads anything. It must stop the device from generating interrupts and DMA (a device that writes into memory after its buffers were freed corrupts whatever owns them next; DR302 has a forensic lab on exactly that), release resources, and forget per-device state. The UART driver disables the UART's interrupts by clearing the Interrupt Enable Register. The lab kernel unbinds and rebinds the RTC driver to show that the cycle works.

A register layer that refuses mistakes

Listing 1 encodes three facts in each register's type: the value type (uint8_t for the UART, uint32_t for AHCI and NVMe), the offset, and an access rule. read<R>() refuses write-only registers; write<R>() refuses read-only and write-1-to-clear registers; clear<R>() is the only way to touch a write-1-to-clear register; set_field<F>() performs a read-modify-write of one field and keeps the other bits. A Bus type supplies the actual access, so the same RegBlock works with I/O ports, with memory-mapped registers through volatile pointers, or with a fake bus on the host that logs every access (Listing 6). Reading the 16550's registers 0 and 1 shows why types help: offset 0 is three registers (receive buffer when read, transmit holding when written, divisor latch low when the DLAB bit of the Line Control Register is set). Three types with three access rules make each use explicit at the call site. D1

Two warnings about read-modify-write. It is wrong for write-1-to-clear status registers: reading a status register with bits 0 and 2 set and writing the value back with one more bit changed clears both pending events. That is why set_field calls write, which refuses RW1C registers at compile time. And it is wrong for registers whose read has side effects, such as the 16550's receive buffer, where a read removes a byte from the FIFO. The layer cannot know about side effects of reads; the comments in the register map must say it. D4

Error values and what they mean

The lab model returns negative error numbers named after POSIX errors (-E_NODEV "no such device", -E_IO, -E_BUSY, -E_TIMEDOUT), with values chosen by us. What matters is the contract: zero means "I own it now", a negative value means "I do not, and here is why", and the model records the value so a person can see it in the table (R2 prints -19 for COM2). The model's NOT_TRIED marks devices for which no driver's table matched, which is different from "a driver tried and failed".

How the hardware actually does it

On a PC, the CPU reaches devices in two ways (F1-41). Port I/O uses the IN and OUT instructions on a separate 16-bit address space; the chipset routes each port number to a device, and legacy devices (the 16550 UARTs, the i8042 keyboard controller, the CMOS RTC, the PIT) live there at fixed numbers. Memory-mapped I/O uses ordinary loads and stores to physical addresses that the chipset routes to a device instead of RAM; PCI devices are mostly reached this way through their BARs (F4-02). Reads from a port or address that no device decodes do not fault on a PC: the bus returns all ones, which is why 0xFF and 0xFFFFFFFF are the classic signature of "nothing there". The lab shows QEMU returning 0xff for every register of the absent COM2. D5 R4

The 16550 itself is a register file of eight byte-wide registers. When the CPU writes the Transmitter Holding Register, the UART moves the byte to its shift register and clocks it out one bit at a time at the rate set by the divisor (the input clock divided by 16 times the divisor); the Line Status Register's "transmitter holding register empty" bit tells software when it may write the next byte. In QEMU the serial port model passes each byte to the host side of -serial immediately, so the lab measures nothing about real baud rates. D1

They agree with Linux's <linux/serial_reg.h> as installed in the build container (Listing 7, R5: 33 values, no difference), which is an independent second source but not the datasheet; the run proves they work on QEMU 8.2.2's model only. Port numbers 0x3F8, 0x2F8, 0x60/0x64, 0x70/0x71, 0x378 are PC convention from memory; a real kernel takes them from ACPI (F3-24).

Worked example

Binding COM1, step by step. Follow the lab kernel through R2. The platform table adds five devices; three drivers register. bind_all takes com1 (compatible ns16550) and compares it with uart16550's table: one row, platform bus, ns16550: a match, so it calls uart_probe.

  1. Write 0x5A to SCR (port 0x3F8 + 7 = 0x3FF), read it back: 0x5A. Write 0xA5, read back 0xA5. Two complementary patterns rule out a stuck bus (all ones or all zeros) and a single stuck bit.
  2. Save MCR, write MCR = 0x10 (loop bit), drain any old received byte, write 0xAE to THR, poll LSR bit 0 (data ready), read RBR: 0xAE. Restore MCR.
  3. Program the line: IER = 0; LCR = 0x80 (DLAB on); DLL = 1, DLM = 0 (divisor 1: the highest standard rate); LCR = 0x03 (8 data bits, no parity, 1 stop bit, DLAB off); FCR = 0x07 (FIFOs on and cleared); MCR = 0x03 (DTR, RTS).
  4. Record the state, set d.priv, return 0. The model sets d.driver.

Now check R2's dump line for COM1: LSR=0x60 is bits 5 and 6 (transmitter holding register empty, transmitter empty), so the port is idle; IIR=0xc1 has bit 0 set (no interrupt pending) and bits 7–6 set (FIFOs enabled); MCR=0x03 is DTR and RTS as programmed; SCR=0xa5 is the last scratch value of the probe. Every number is explained by a line of Listing 4. For COM2 the same probe reads back 0xFF from SCR on its first test and returns -E_NODEV: the table shows -19. For lpt1, no driver lists pc-parallel, so the table says "no matching driver". D1 R2

A field write by hand. Listing 6 sets the 3-bit field SPEED at bits 4–6 of a control register holding 0x101 to 5. Mask: ((1 << 3) - 1) << 4 = 0x70. Clear the field: 0x101 & ~0x70 = 0x101. Insert: (5 << 4) & 0x70 = 0x50. Result: 0x101 | 0x50 = 0x151, bits 0 and 8 untouched. R3 prints 0x00000151 and the mask 0x00000070. R3

Where the analogy breaks


    

  • An interpreter only translates; a driver also manages. A driver allocates memory the device writes into, owns an interrupt line, enforces ordering between memory and register writes, and decides when to reset the device. No interpreter rebuilds the visitor after a misunderstanding.
    • 

  • Visitors talk back on their own; devices mostly do not. A device acts only on what its registers say. If a driver stops writing, a UART simply goes quiet; there is no visitor who notices the interpreter has left.
    • 

  • An interpreter for an empty chair notices; a driver may not. Reads from an absent device return plausible-looking values (all ones) and writes vanish without error. The forensic lab is about exactly this.
    • 

  • Interpreters are people; drivers run with the kernel's full rights. A bug in one driver can overwrite any memory of the kernel. The analogy hides that the interpreter carries the school's master key.
    • 




Common mistakes and debugging


    

  • Claiming in probe before proving. Symptom: a device table that shows a driver bound to something absent, everything "works", nothing happens. Check: dump the status registers right after probe; all 0xff means nobody is there (forensic lab).
    • 

  • Read-modify-write on a write-1-to-clear register. Symptom: interrupts lost under load, because acknowledging one event cleared another. Check: grep for |= on status registers; use clear<R>().
    • 

  • Forgetting the DLAB bit. Symptom: garbage on the serial line or an IER full of nonsense, because offsets 0 and 1 meant the divisor latch. Check: LCR bit 7 must be 0 after initialisation.
    • 

  • Publishing before initialising. Symptom: rare crashes at boot when another part of the kernel uses the device during probe. Check: the publish step is the last line of probe.
    • 

  • No remove. Symptom: after unbinding, interrupts arrive for a device nobody owns; the interrupt controller masks the line or the kernel spins. Check: unbind and rebind in a test, as the lab does.
    • 

  • Constants written from memory. Symptom: works on QEMU, fails on a real chip. Check: compare against a second source (Listing 7) and against the datasheet before real hardware.
    • 




Transition box

Where you came from: OS302, where your kernel booted, printed through COM1 with a few direct outb calls (F3-18), and learned interrupts and the APIC (F3-19, F3-24); HW204, where buses, port I/O and MMIO were hardware ideas (F1-40, F1-41). What carries over: the freestanding C++ kernel, the serial oracle and isa-debug-exit, the habit of writing a host test first. What changes: devices are no longer hard-wired into the kernel. They are discovered, matched to drivers by identity, probed and removed; registers are reached through a typed layer, not through bare port numbers; every constant has a second source or an unverified box. What comes next: F4-02 replaces the hand-written platform table with a real bus, PCI, whose devices describe themselves.

Summary


    

  • A driver implements a device's programming interface downward and a subsystem's interface upward, and owns the device's resources, ordering and errors.
    • 

  • The driver stack runs application → system call → subsystem → driver → bus → device; requests go down, interrupts and completions come up.
    • 

  • A driver model separates discovery from binding: buses report devices, drivers publish match tables, probe proves, acquires, initialises and publishes, remove undoes it all.
    • 

  • Reads of absent devices on a PC return all ones and writes vanish silently; a probe that does not prove presence binds to nothing.
    • 

  • A typed register layer turns access-rule mistakes into compile errors and lets driver logic run against a fake bus on the host.
    • 

  • Constants written from memory are checked against a second source and marked unverified until the specification is read.
    •

  1. Differences: in the table, COM2 is bound to uart16550 with probe 0 (R2: (none), -19); COM1's dump shows SCR=0x00 instead of 0xa5; there is a new dump line for COM2 with every register 0xff; and a new "writing a test line through com2".

  2. (b). An idle real 16550 cannot show LSR = 0xff (bit 7 would mean an error in the FIFO, bits 1–4 errors and a break) nor IIR = 0xff (bits 5–4 are not set on a 16550).
