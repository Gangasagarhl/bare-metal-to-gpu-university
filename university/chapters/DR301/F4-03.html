Story hook

The interpreter of F4-01 had a bad habit: every few seconds she walked to the visitor and asked "did you say something?". It worked, but she did nothing else all day, and when the visitor spoke quickly she missed words between two visits. The school fixes this with a doorbell. The visitor presses it when there is something to say; the interpreter comes, writes everything down in a notebook as fast as possible, and goes back to her other work. Later she reads the notebook at her own pace. When she has an answer to deliver, she leaves it in a second notebook, and the visitor's side rings again whenever it is ready for more.

There is one rule that the school secretary enforces strictly: after answering the bell, the interpreter must tell the secretary "done". Until she does, the secretary holds back that bell and every bell of lower importance. This chapter builds both doorbell drivers of the old PC, the serial port and the PS/2 keyboard and mouse controller, makes 64 KiB pass through the serial port without losing a byte, and shows what one forgotten "done" does to a keyboard.

What you will be able to do

  • Program the legacy 8259 interrupt controllers and the PIT, install interrupt handlers, and send end-of-interrupt correctly for both controllers.
  • Write an interrupt-driven 16550 driver with receive and transmit rings, using the FIFO trigger level, the interrupt identification register and on-demand transmit interrupts.
  • Initialise the i8042 controller with its self-tests, reset the keyboard and the mouse, decode scan codes and 3-byte mouse packets.
  • Build a single-producer, single-consumer ring that is safe between an interrupt handler and normal code on one CPU.
  • Write a line discipline with echo and backspace.
  • Test input drivers automatically by injecting keys and mouse moves through QEMU's monitor and by feeding a serial port from a host program, with checksums.
  • Diagnose a missing end-of-interrupt from interrupt counters and an emulator trace.
Jargon box
8259 PIC
Simple words: the PC's original interrupt controller chip, two of them chained. Analogy: the school secretary who decides which bell to pass on first. Precise: a programmable interrupt controller with eight request lines, an interrupt mask register (IMR), an interrupt request register (IRR) and an in-service register (ISR); the PC chains a slave to the master's line 2, giving 15 usable lines, and both must be remapped so their vectors do not overlap CPU exceptions. D3
End-of-interrupt (EOI)
Simple words: the message a handler sends to the interrupt controller to say "I am done with this one". Analogy: telling the secretary "done" after answering the bell. Precise: a command (for the 8259, writing 0x20 to its command port) that clears the highest-priority in-service bit, allowing that line and lines of lower priority to be delivered again; slave lines need an EOI at both controllers. D3
FIFO trigger level
Simple words: how many received bytes the UART collects before it rings. Analogy: the visitor waits until there are 14 words to say before pressing the bell. Precise: the 16550's receive FIFO raises the "received data available" interrupt when it holds at least the programmed number of bytes (1, 4, 8 or 14); a "character timeout" interrupt reports fewer bytes that have waited for a while. D1
Ring buffer (SPSC)
Simple words: a circular queue where one side only writes and the other side only reads. Analogy: the interpreter's notebook, written by one hand and read by another. Precise: a fixed array with a producer index and a consumer index, each written by only one party; with one producer and one consumer it needs no lock, only the right ordering of the data write before the index update. D5
i8042
Simple words: the PC's keyboard and mouse controller. Analogy: a receptionist who collects the keyboard's and mouse's messages and passes them through one window. Precise: a controller with a data port (0x60) and a status/command port (0x64) that connects up to two PS/2 devices, raises line 1 for the keyboard and line 12 for the mouse, and can translate the keyboard's scan code set 2 into set 1. D2
Scan code
Simple words: the number a keyboard sends for a key going down or coming up. Analogy: the key's seat number, not its letter. Precise: a byte sequence identifying a key position and a make (press) or break (release) event; in set 1 a break is the make code with bit 7 set, in set 2 a break is 0xF0 followed by the make code. D2
Line discipline
Simple words: the layer that turns key presses into finished lines of text. Analogy: the interpreter writing a sentence, crossing out a wrong word, and handing it over only at the full stop. Precise: the TTY component that buffers input in canonical mode, applies editing characters (erase, kill), echoes, and delivers a line to the reader when a line terminator arrives. D6

The idea in pictures

Layer 1 — the kid explanation

A keyboard does not wait to be asked. When you press a key, it rings a little bell inside the computer. The processor stops what it is doing for a moment, runs a tiny piece of code that writes the key down in a notebook, and goes back to work. Later the rest of the program reads the notebook. After each ring the code must say "done", or the bell stays silent forever.

Layer 2 — the student explanation

Polling, as in F4-01, wastes the CPU and loses data when the device is faster than the polling loop. Interrupts reverse the direction: the device signals when it needs attention. On a PC with legacy devices, each device drives one interrupt request line; the 8259 PIC turns the highest-priority pending line into a vector number for the CPU; the CPU saves its state and jumps to the handler from the interrupt descriptor table (F3-19); the handler services the device, sends an EOI to the PIC, and returns. D3 D4

A handler must be short and must leave the device in a state where it will interrupt again. For the 16550 that means reading the interrupt identification register (IIR) until it says "no interrupt pending", servicing each cause it reports: received data (read bytes until the line status register says the FIFO is empty), transmitter empty (write the next bytes), line status (read the line status register) or modem status (read the modem status register). Each read is what clears the cause in the chip. For the i8042, each interrupt means one byte is waiting in the data port; reading it clears the condition. D1 D2

Between the handler and the rest of the kernel sits a ring buffer. The handler is the producer for received data and the consumer for data to send; normal code is the other side. Because each index has a single writer, the ring needs no lock on one CPU, only the guarantee that the byte is written before the index that publishes it.

The i8042 carries the keyboard and the mouse. The keyboard sends scan codes: one or more bytes per key press and per release. The controller normally translates the keyboard's native set 2 into the older set 1, in which a release is the press code with bit 7 set. The mouse sends 3-byte packets: buttons and sign bits, then X movement, then Y movement. A line discipline above the keyboard driver collects characters, handles backspace and delivers a finished line on Enter, which is what a shell reads.

Layer 3 — the engineer's depth

The 8259 pair and the PIT

At reset the master PIC delivers its lines as vectors 8–15, which collide with CPU exceptions in protected mode, so the kernel reprograms both PICs with four initialisation words each: ICW1 (start, ICW4 follows), ICW2 (vector base: 32 for the master, 40 for the slave), ICW3 (the master has a slave on line 2; the slave's cascade identity is 2), ICW4 (8086 mode). The interrupt mask register then enables only the lines with handlers. The priority scheme in the default mode is fixed: line 0 highest; the whole slave sits at the priority of master line 2. EOI is non-specific (0x20 to the command port) and clears the highest in-service bit; a slave line needs an EOI at the slave and then at the master. The PIT's channel 0 is programmed in mode 2 with divisor 1193, which gives about one interrupt per millisecond from its input clock; the lab kernel uses that tick as its monotonic clock. D3 D7

Note

The legacy PIC is a decision for this lab, not a recommendation. A modern x86 kernel masks the 8259 entirely, routes legacy lines through the IOAPIC using ACPI's interrupt source overrides, and acknowledges at the local APIC; PCI devices then move to MSI or MSI-X (F4-08). Your B7 kernel already has that path (F3-24). The drivers in this chapter do not change: only irq.cc does. The decision is recorded in NOTES.md.

The 16550 in interrupt mode

Interrupt-driven operation needs four things set. The FIFO control register enables the FIFOs, clears them and selects the receive trigger level (14 bytes in the lab, bits 7–6 = 11b). The modem control register sets OUT2, which on PC serial hardware connects the UART's interrupt output to the bus; without it the UART never interrupts. The interrupt enable register selects causes: received data available (bit 0) always, transmitter holding register empty (bit 1) only while there is something to send. And the PIC line is unmasked after the handler is installed. D1

The transmit side has a classic subtlety. The "transmitter empty" interrupt fires when the transmitter becomes empty, and also, on enabling, if it already is. If the driver left it enabled with nothing to send, the UART would interrupt continuously. So the driver turns it on when it puts the first byte into an empty ring (uart_irq_putc) and off when the handler finds the ring empty. Both places change IER and a flag, so the normal-code side does it with interrupts disabled. On each transmit interrupt the handler writes up to 16 bytes, the FIFO depth, which divides the number of transmit interrupts by up to 16. D1

The receive trigger trades interrupts against latency and overrun risk. With trigger 14 the UART interrupts when 14 bytes are waiting; at that point only two more bytes fit before an overrun. On QEMU the bytes arrive as fast as the emulator delivers them, and R3 shows no overrun and no ring drop, with the ring's high-water mark well below 4096. On a real 16550 at a high bit rate, a handler delayed by other interrupts could lose bytes at trigger 14; a lower trigger or hardware flow control (RTS/CTS) is the remedy. D1 R3

The i8042 and its devices

The controller has a status register (bit 0: output buffer full, a byte is waiting at port 0x60 for the CPU; bit 1: input buffer full, the controller has not yet taken the last byte the CPU wrote; bit 5: the waiting byte came from the second port), a configuration byte (bit 0 and 1: interrupts for port 1 and 2; bits 4 and 5: clocks of port 1 and 2 disabled; bit 6: translation), and commands written to port 0x64: 0x20/0x60 read/write the configuration byte, 0xAA self-test (answer 0x55), 0xAB/0xA9 port tests (answer 0), 0xAD/0xAE and 0xA7/0xA8 disable/enable ports, 0xD4 "send the next data byte to the second port". Bytes written to port 0x60 go to the keyboard; the devices answer commands with ACK 0xFA, and a reset (0xFF) with 0xAA after their self-test (the mouse adds its ID byte). The mouse starts reporting only after 0xF4. D2

The initialisation order matters, and the lab found out the hard way: enabling a port with 0xAE/0xA8 clears that port's clock-disable bit in the configuration byte, so writing back an old copy of the configuration byte afterwards disables the ports again and no interrupt ever arrives. The driver re-reads the byte before setting the interrupt bits (Listing 3, lines 102–107). This is the kind of ordering rule that a register map alone does not show. R2

Mouse packets are re-synchronised with bit 3 of the first byte, which is always 1: if a byte is lost, the decoder drops bytes until it sees a plausible first byte. The X and Y movements are 9-bit two's complement values whose sign bits are bits 4 and 5 of the first byte. D2

Not verified — check before relying on this

Written from memory and confirmed only by QEMU 8.2.2's models answering as expected (R2, R3): the 8259 initialisation words, priority and EOI rules (check the Intel 8259A datasheet, D3); the PIT mode and the input clock behind divisor 1193 (8254 datasheet, D7); the i8042 command, status and configuration bits and the device command and answer values (the OSDev wiki pages named in the curriculum, D2, and better the controller's own documentation if you can find it); the 16550 FIFO trigger encoding and OUT2's role on PC hardware (PC16550D datasheet, D1). The UART constants also agree with Linux's serial_reg.h (F4-01, R5 there). The direction of the mouse's Y axis relative to QEMU's mouse_move is an observation of R2 (monitor −5 became +5), not a documented fact.

Rings, volatile and ordering

The ring in Listing 4 keeps free-running indices (they only grow; the slot is index mod N, N a power of two), so "full" is head − tail == N and "empty" is head == tail without a wasted slot. Each index is written by one side only. volatile stops the compiler from keeping an index in a register across a loop; the empty asm volatile("" ::: "memory") stops it from moving the byte store after the index store. That is enough on one CPU because the interrupt and the normal code run on the same CPU, which sees its own stores in order. With two CPUs, the same ring needs atomic indices with release and acquire ordering (SP203, F3-27). D5

Testing input without a person

The curriculum's acceptance tests are automatic. QEMU's monitor command sendkey presses and releases a key on the emulated keyboard, and mouse_move/mouse_button generate mouse events; the lab drives the monitor through QMP's human-monitor-command from a Python script (Listing 6) and compares the shell's line with the typed text. QEMU's trace event ps2_put_keycode logs every scan code byte the emulated keyboard produced, an independent record of what the driver should have seen. For the serial port, a host program connects to COM2 through a socket, sends 64 KiB, reads the echo and compares checksums on both sides. D8 R2 R3

How the hardware actually does it

On an original PC, each ISA device drove its interrupt line high to request service, and the 8259 detected a rising edge. Edge triggering explains a classic failure: if a device keeps its line high because the handler did not clear the cause, there is no new edge and no further interrupt. On a modern PC there are no physical 8259 chips or ISA lines; the chipset emulates the legacy controllers and the "devices" (the i8042 is usually emulated by the embedded controller, and the UART, if present, sits in a Super I/O chip). The project's DRIVERS.html notes for the test machine that its PS/2 port is emulated by the embedded controller and that the touchpad behind it has its own firmware. The keyboard itself contains a microcontroller that scans the key matrix and sends codes over a two-wire synchronous serial link clocked by the device. D3 D2 D9

In QEMU, all of this is software: the 16550 model hands bytes to and from a host character device, and the PS/2 model queues scan codes generated by the monitor. Timing in the lab is emulated (TCG), so the milliseconds printed in R3 describe the emulator on a busy build machine, not a UART at any bit rate.

Worked example

Following the letter "h". The script sends sendkey h. QEMU's keyboard model produces set 2 make code 0x33, then (on release) 0xF0 0x33: the first three lines of the trace in R2. The controller translates: set 1 make 0x23, break 0xA3. Each byte raises line 1. The handler reads port 0x60 (status bit 0 was set) and pushes the byte into the keyboard ring; EOI. In get_key, 0x23 has bit 7 clear (a press), code 0x23, and kLower[0x23] is 'h'; the line discipline stores and echoes it. 0xA3 is the release, ignored by the test. Count the interrupts: 23 keys typed (including shift-d, which presses Shift around D) produced 75 set 2 bytes (R2 trace count) and 50 line-1 interrupts after translation; check the 50 yourself in the exercise. R2

Decoding a mouse packet. mouse_move 10 -5 produced a packet that the driver printed as dx=10 dy=5. The bytes were first byte 0x08 (bit 3 always set, no buttons, sign bits 4 and 5 clear), X = 0x0A = 10, Y = 0x05 = 5. Had Y been −5, byte 0 would have had bit 5 set and Y would have been 0xFB: 251 − 256 = −5. Then mouse_button 1 and mouse_button 0 produced two packets with zero movement and the left button bit set and cleared. Nine bytes, nine line-12 interrupts: irq12=9 in R2's status line. R2

The paste in numbers. R3: 65536 bytes received, FNV-1a 7c0c9dc5 on the kernel side and on the host side, the echo identical, no overruns, no ring drops. The number of interrupts printed is several times smaller than the number of bytes received plus sent, because each receive interrupt drains up to a FIFO's worth and each transmit interrupt refills up to 16 bytes. R3

Watch out
One of about ten runs of the paste test in this build, made while other emulators were running on the same machine, stalled with nothing received; it could not be reproduced afterwards, even under deliberate CPU load. The cause is not known (candidates: the feeder and QEMU's socket set-up racing, or a lost receive interrupt). run.sh therefore records a failed first attempt in paste.out and tries once more, and the kernel prints the UART registers if no byte arrives for 10 s. If you see the diagnostic line, you have evidence for the investigation; NOTES.md keeps this open.



Where the analogy breaks


    

  • A doorbell rings once; an interrupt line can stay asserted. A level-triggered line keeps requesting until the device's cause is cleared; an edge-triggered one may never ring again if the cause is left set. A doorbell has neither problem.
    • 

  • The secretary blocks more than one bell. A missing EOI blocks this line and every lower-priority line, including all slave lines behind line 2. No school secretary would stop passing on unrelated visitors because one interpreter forgot to report back.
    • 

  • Visitors do not lose words if the notebook is full; UARTs do. A full FIFO overwrites or drops data with only a status bit as trace (overrun). The analogy suggests the visitor would wait.
    • 




Common mistakes and debugging


    

  • No EOI, or EOI only to the master for a slave line. Symptom: one interrupt and then silence, often for several devices. Check the per-line counters (forensic lab).
    • 

  • Forgetting OUT2. Symptom: the 16550 never interrupts although IER is set. Check MCR bit 3.
    • 

  • Leaving THRE interrupts on. Symptom: the CPU spends all its time in the UART handler; the system feels frozen. Check that IER bit 1 is cleared when the ring empties.
    • 

  • Servicing one IIR cause and returning. Symptom: lost interrupts under load. Loop until IIR bit 0 is 1.
    • 

  • Writing back a stale i8042 configuration byte. Symptom: the keyboard never interrupts after an apparently good initialisation. Re-read before writing.
    • 

  • Unmasking line 12 but not line 2. Symptom: the mouse is silent, the keyboard works.
    • 

  • Doing work in the handler. Symptom: overruns at high rates. Move decoding and echo out of the handler, as the lab does.
    • 




Transition box

Where you came from: F4-01's polled UART driver; F3-19 and F3-24, where your kernel took exceptions and timer interrupts; F1-42 and F1-43, where interrupts and interrupt controllers were hardware. What carries over: the register layer and the UART register map; the driver model; the serial log as the oracle. What changes: the device decides when the driver runs; driver code splits into a handler that must be short and normal code that consumes rings; every handler owes an EOI; tests inject input from outside the guest. What comes next: F4-04 reads a device whose registers change on their own (the RTC), where the problem is not "when" but "a consistent snapshot".

Summary


    

  • Interrupts let devices signal; the 8259 pair maps lines to vectors after remapping, enforces priority and needs an EOI per interrupt (both controllers for slave lines).
    • 

  • An interrupt-driven 16550 needs FIFOs, OUT2, IER and an unmasked line; the handler loops over IIR causes; transmit interrupts are enabled only while data waits.
    • 

  • The i8042 initialisation is an ordered sequence of self-tests, resets and configuration writes; re-read the configuration byte before changing it.
    • 

  • Handlers and normal code meet in single-producer, single-consumer rings that need ordering but no lock on one CPU.
    • 

  • Input drivers are tested automatically: monitor key injection with an emulator trace, and a host-fed serial port with checksums.
    • 

  • A missing EOI silences the line and everything below it in priority; per-line counters reveal it.
    •
