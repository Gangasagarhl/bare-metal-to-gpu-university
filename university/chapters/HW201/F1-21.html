Story hook

Analogy

Ana, the head chef, hands the builder two documents. One is a recipe: "first chop, then fry, then plate". It is a list of steps, done one after another. The other is the floor plan of a new kitchen: "here is the stove, here is the sink, this counter connects them". Nothing on a floor plan happens "first". Everything on it exists at the same time, all day.

The builder who reads the floor plan as a recipe ends up with a very strange kitchen.

A hardware description language is a floor plan, written in text that looks like a recipe. Its lines look like a program, with if, begin and end, but most of them describe parts that exist side by side and work all at once. This chapter teaches you to read Verilog as a floor plan: which lines become flip-flops, which become gates, which exist only in the simulator, and how three different tools read the same text.

What you will be able to do

  • Read a Verilog module: its ports, parameters, wires and registers, and its always blocks.
  • Tell from the code which signals become flip-flops and which become combinational logic.
  • Explain the difference between blocking (=) and non-blocking (<=) assignments and use each correctly.
  • Separate the synthesisable design from simulation-only testbench code.
  • Read the reports of a simulator, a lint tool and a synthesis tool on the same file.
  • Diagnose a delay line that does not delay (the forensic lab).
Jargon box
Hardware description language (HDL)
Simple words: a text language for describing circuits. Analogy: the floor plan, written in words. Precise: a language such as Verilog or VHDL whose descriptions can be simulated and synthesised into hardware; most statements describe hardware that runs concurrently. D1 D3
Module
Simple words: one named block of hardware with inputs and outputs. Analogy: one station on the floor plan, with its doors. Precise: the Verilog unit of design: a port list, declarations and statements; modules are instantiated inside other modules to build a hierarchy. D3
Port
Simple words: a named connection into or out of a module. Analogy: a door of the station. Precise: a module's interface signal, declared input, output or inout with a width. D3
Always block
Simple words: a piece of Verilog that runs again whenever something it waits for happens. Analogy: a standing instruction: "whenever the bell rings, do this". Precise: a procedural block with an event control; always @(posedge clk) describes edge-triggered storage, always @(*) describes combinational logic. D3 D1
Blocking assignment
Simple words: =: the new value is used by the very next line. Analogy: passing a plate hand to hand along a line of cooks in one go. Precise: a procedural assignment that completes before the next statement executes; the right style for combinational always @(*) blocks. D3 D1
Non-blocking assignment
Simple words: <=: every right-hand side is read first, and all the left-hand sides change together afterwards. Analogy: at the bell, every cook hands their plate to the next station at the same moment. Precise: a procedural assignment whose update is scheduled after all right-hand sides in the time step are evaluated; the right style for clocked always @(posedge clk) blocks, matching the behaviour of flip-flops. D3 D1
Parameter
Simple words: a named number you can change when you use the module. Analogy: "this counter is N metres long" on the plan. Precise: a module constant, such as a width, that each instance can override. D3
Lint tool
Simple words: a program that reads code and points out suspicious lines. Analogy: an inspector who reads the floor plan before anything is built. Precise: a static checker that reports problems such as width mismatches, unused signals and inferred latches without simulating. D4
Synthesis tool
Simple words: a program that turns HDL into a list of gates and flip-flops. Analogy: the builder turning the plan into real stations. Precise: a tool that maps a synthesisable HDL description to a netlist of cells of a target technology. D5 D1
Synthesisable subset
Simple words: the parts of the language that can become real hardware. Analogy: plan notes a builder can build; "paint it later" is not one. Precise: the constructs a synthesis tool accepts; delays such as #5, $display and most initial blocks are for simulation only. D1

The idea in pictures

Layer 1 — the kid explanation

When you write a computer program, the computer does your lines one after another, like following a recipe.

A hardware description language looks a bit like a program, but it is really a drawing made of words. It says: "here is a box that adds, here is a row of flip-flops, connect this wire to that one." All the parts it describes are there at the same time and all work at once, like all the lamps in a house being on together.

Three kinds of helper programs read these word-drawings. A simulator pretends to be the circuit and shows what it would do. A lint tool reads it like a teacher with a red pen and points at lines that look wrong. A synthesis tool turns it into a real list of gates and flip-flops that could be built.

Learning to read one well means asking, for every line: "what part does this make?"

Layer 2 — the student explanation

The shape of a module

Every Verilog file in this course has the same shape D3: module name #(parameters) (ports);, then declarations, then statements, then endmodule. Read it in that order.

  1. Ports tell you the interface: names, directions and widths. [WIDTH-1:0] means bits WIDTH−1 down to 0.
  2. Parameters are numbers fixed when the module is used; program_counter #(.WIDTH(8)) builds an 8-bit version.
  3. Declarations: wire is a connection driven by something (a gate, an assign, a module output). reg is a variable assigned inside an always block. Despite its name, a reg does not always become a register D1 D3.
  4. Statements are of four kinds you have already used: assign (continuous, combinational), always @(*) (combinational), always @(posedge clk) (flip-flops), and instances of other modules.

Which lines become flip-flops?

Ask one question for each reg: is it assigned in an always @(posedge clk) block? If yes, it is stored in flip-flops, one per bit, and changes only at the edge D1. If it is assigned in always @(*) and gets a value on every path, it is combinational. If it is assigned in always @(*) but some path leaves it unassigned, it becomes a latch, as F1-16's forensic lab showed D1.

The if chain inside a clocked block becomes multiplexers in front of the flip-flops: in Listing 1, "reset wins over load wins over inc" is the order of the multiplexers. The synthesis report confirms it: 8 flip-flops for 8 bits, plus multiplexers and the gates of the +1 adder R3.

Blocking and non-blocking

In a clocked block, a <= b; means "at this edge, a takes the value b had before the edge". All flip-flops sample at the same instant, so this is how real flip-flops behave, and the order of lines does not matter D1 D3. In a clocked block, a = b; means "a takes b's value now, and the next line already sees the new a". Line order then changes the hardware. Figure 2 and the forensic lab show the result.

Two rules cover this course D1:

  • Clocked block (always @(posedge clk)): use <= only.
  • Combinational block (always @(*)): use = only, and assign every output on every path.

Design code and testbench code

A testbench (HW102 introduced them) uses things no hardware can do: #5 delays, initial blocks that run once, $display, $finish, tasks that wait for clock edges. These belong to the simulation world only D1. A synthesis tool will reject them or ignore them. When you read a file, first decide which world it belongs to; then read it with that world's rules.

Layer 3 — the engineer's depth

The simulation scheduler. A Verilog simulator keeps a queue of events per time step. Blocking assignments update at once; non-blocking updates are collected and applied after all the right-hand sides in that step have been read D3. That is why non-blocking assignments in different always blocks on the same clock never race each other, whereas blocking assignments can produce results that depend on which block the simulator happens to run first D3 D1.

Simulation and synthesis can disagree. A simulator runs the text; a synthesis tool infers hardware from it. Code with an incomplete sensitivity list, delays, or races may behave one way in simulation and another way once built D1. Using @(*), the two assignment rules and a lint tool removes most such mismatches. Checking a synthesised netlist against the original description (equivalence checking, or simulating the netlist) closes the gap in industry flows D5.

Reading a synthesis report. Yosys names its generic cells by function. In Listing 1's report, $_SDFFE_PP0P_ is read as: a D flip-flop (DFF) with a synchronous reset (S) and an enable (E), positive clock edge, active-high reset, reset value 0, active-high enable D5. The tool folded "reset → 0" and "hold when nothing applies" into the flip-flop cell itself; the multiplexers that remain choose between jump_to and pc + 1 R3.

Not verified — check before relying on this

The reading of the cell name $_SDFFE_PP0P_ letter by letter is from the Yosys manual's naming scheme as recalled, which this build did not open; the cell counts themselves are from the real run. Behaviour of other synthesis tools, and of other Yosys versions (this build: "Yosys 0.33 (git sha1 2584903a060)"), may differ.

Other languages. VHDL is the other long-established HDL, with stricter typing; SystemVerilog extends Verilog with features mostly for verification D1. The reading questions in this chapter (which parts are storage, which are logic, which are simulation-only) apply to all of them.

How the hardware actually does it

The hardware never "runs" Verilog. The synthesis tool reads the text once and produces a netlist: a list of cells and the wires between them (F1-11 introduced netlists) D5. For a chip, later tools place those cells on silicon and route the wires; for an FPGA (F1-22), they map the cells to lookup tables and flip-flops and produce a configuration file D1. From then on there is no program counter stepping through your always block: all of Listing 1's 33 cells work at the same time, every cycle R3. That is the floor plan becoming a kitchen.

Where the analogy breaks


    

  • A floor plan has no timing. Verilog does: the clock edge and the two kinds of assignment decide when values move. The floor plan analogy explains "everything exists at once"; it says nothing about "everything moves at the bell".
    • 

  • Builders refuse impossible plans; simulators do not. A simulator will happily run testbench-style code inside a design. Only synthesis (or lint) tells you that a line cannot become hardware.
    • 

  • Recipes are not all wrong. Inside one always @(*) block, statements are evaluated in order with =, recipe-style, to compute one combinational result. The result is still a circuit that exists all the time.

Summary


    

  • An HDL describes hardware that exists all at once; read it as a floor plan, not a recipe.
    • 

  • A reg assigned in always @(posedge clk) is flip-flops; in always @(*) with every path assigned, it is logic; otherwise a latch.
    • 

  • Clocked blocks use <=; combinational blocks use =.
    • 

  • Testbench constructs (delays, initial, $display) are simulation-only.
    • 

  • Simulator, lint tool and synthesis tool answer different questions; use all three.
    • 

  • Count flip-flops in the synthesis report and compare with your intent.

Forensic lab answer key


Observation: in Priya's version, out equals in right after the same edge (0 edges late, as if there were one register) R6; the correct version delivers the value of edge n−2 R5. Synthesis: 4 flip-flops instead of 12 R6. Hypotheses: (1) the testbench is wrong: ruled out, since the correct version passes the same testbench; (2) the module has fewer stages than written: confirmed by the flip-flop count. Root cause: lines 13–15 use blocking =. At an edge, stage1 = in updates stage1 at once; stage2 = stage1 then reads the new stage1, which is in; out = stage2 reads that too. All three get the input value at the same edge; stage1 and stage2 are only intermediate names, and the tool keeps only one 4-bit register, for out. Why the simulator was silent: it is legal Verilog with a well-defined meaning; it is not the meaning Priya wanted. The lint tool checks style rules as well as legality, and its rule BLKSEQ ("Blocking assignment '=' in sequential logic process") points at exactly lines 13, 14 and 15 R7. Fix: use <= on all three lines (Listing 5).
