Story hook

Analogy

Every order in the restaurant has a status card on the board: ordered, cooking, plating, served. Rosa, the expediter, follows a small rule card. "At each ring of the bell, look at the order's status and at what is happening. If it is cooking and the timer has run six rings, move it to plating. Otherwise leave it where it is."

Rosa never needs to remember the whole history of the order. The status card says everything that matters. And the board tells the waiters what to do: an order at plating means "come to the pass now".

That is a finite state machine: a handful of named situations, one of which is current, a rule for moving between them at each clock edge, and outputs decided by the current situation. Traffic lights, vending machines, and the control unit of a processor are all built this way. In this chapter you design them from a description in words, the way the course's practical exam asks.

What you will be able to do

  • Turn a description in words into states, a state diagram, a state table and Verilog.
  • Explain the three parts of a state machine: next-state logic, state register and output logic.
  • Tell a Moore machine from a Mealy machine and say when each answers.
  • Build and test a traffic-light controller with a self-checking testbench that checks safety rules.
  • Diagnose a state machine whose state register is too narrow for its states (the forensic lab).
Jargon box
Finite state machine (FSM)
Simple words: a circuit that is always in one of a few named situations and moves between them by rules. Analogy: the order's status card and Rosa's rule card. Precise: a sequential circuit with a finite set of states, a state register holding the current state, next-state logic that computes the next state from the current state and inputs, and output logic. D5 “Finite State Machines (FSMs)”
State
Simple words: the situation the machine is in right now. Analogy: the word on the status card. Precise: the value held in the state register; it summarises everything about past inputs that the machine needs for its future behaviour. D5 “Finite State Machine (FSM)”
State diagram
Simple words: a drawing with a circle for each state and an arrow for each move. Analogy: the flow chart pinned beside the order board. Precise: a directed graph whose nodes are states and whose edges are transitions, labelled with the input conditions that cause them (and, for Mealy machines, the outputs). D5 “Moore FSM Example”, “Mealy FSM Example”
State table
Simple words: the same information as the diagram, written as a table. Analogy: Rosa's rule card. Precise: a table listing, for each current state and input combination, the next state (and outputs). D5 “FSM Design Procedure”
Next-state logic
Simple words: the part that decides where to go next. Analogy: Rosa reading her rule card. Precise: combinational logic computing the next state from the current state and the inputs; it is stored into the state register at the clock edge. D5 “Finite State Machines (FSMs)”
Moore machine
Simple words: a state machine whose outputs depend only on the state. Analogy: the waiters look only at the status card, not at what Rosa is hearing. Precise: an FSM whose outputs are a function of the current state alone; outputs change only after a clock edge. D5 “Finite State Machines (FSMs)”
Mealy machine
Simple words: a state machine whose outputs also look at the inputs right now. Analogy: a waiter who reacts to the status card and to the customer's wave at the same time. Precise: an FSM whose outputs are a function of the current state and the current inputs; it can respond in the same cycle, at the cost of outputs that follow input changes between edges. D5 “Mealy FSM Example”
State encoding
Simple words: the bit pattern chosen for each state. Analogy: a numbered status card instead of a word. Precise: an assignment of binary codes to states; binary encoding uses ⌈log2(number of states)⌉ flip-flops, one-hot encoding uses one flip-flop per state. D5 state-encoding slides W1
Illegal state
Simple words: a bit pattern in the state register that is not one of your states. Analogy: a status card with a word that is not on the rule card. Precise: a code the state register can hold but the design never meant to use; the designs in this course give it a defined next state through a default branch. D6 “Combinational Logic using case”

Layer 1 — the kid explanation

Many machines around you do things in steps. A traffic light goes green, then yellow, then red, and waits. A washing machine fills, washes, rinses, spins. Each step is a state, a situation the machine is in.

A finite state machine remembers only which state it is in now. That is its whole memory. At every clock tick it looks at its state and at its inputs (is a car waiting? has the timer run out?) and decides the next state. Then its outputs, like which lamps are on, follow from the state.

You can draw it: one circle per state and one arrow per move, with the reason written on the arrow. If you can draw it, you can build it from the parts you already know: flip-flops to hold the state, and gates to decide the next state and the outputs.

The nice part is that "finite" means you can check every case. A traffic light with six states has only six situations to think about, and you can make sure none of them ever shows green both ways.

Layer 2 — the student explanation

Three parts

An FSM has a state register of k flip-flops, next-state logic and output logic (Figure 1) D5 “Finite State Machines (FSMs)”. At each rising edge the register stores the next state; during the following cycle the logic computes the new next state and the outputs. A counter (F1-17) is the simplest FSM: its next-state logic is "+1" and its outputs are the state itself.

Moore and Mealy

In a Moore machine, outputs depend only on the state, so they change only right after a clock edge and stay steady for the whole cycle D5 “Finite State Machines (FSMs)”. In a Mealy machine, outputs depend on the state and the present inputs D5 “Mealy FSM Example”. A Mealy machine can therefore react within the same cycle in which an input arrives, and often needs fewer states, but its outputs can change (or glitch) whenever its inputs change. Both machines in this chapter are Moore machines: their outputs are decoded from the state only. The 101 detector, for example, says "found" during the cycle after the final 1 has been stored R1; a Mealy version could say it during the same cycle the final 1 is on the input.

From words to hardware: the method

This is the method the course's practical exam tests ("design an FSM from a word description"). It follows the usual textbook steps D5 “FSM Design Procedure”:

  1. Inputs and outputs. List them, with their meaning and timing ("sampled at the rising edge").
  2. States. Ask: what must the machine remember about the past to decide the future? Each distinct answer is a state. Name states by what they remember ("S10: the last two bits were 1, 0").
  3. Diagram. From every state, draw exactly one arrow for every input combination. Missing arrows are missing decisions.
  4. Table. Write the diagram as a state table and check it row by row against the words.
  5. Encoding. Choose codes. With n states, binary encoding needs ⌈log2 n⌉ bits: 4 states need 2 bits, 6 states need 3 W1. Check the register is wide enough for every code.
  6. Verilog. Write three blocks: next-state logic (always @(*) with a default), state register (always @(posedge clk) with reset), output logic.
  7. Test. Write a testbench that compares with an independent model, or checks properties that must always hold ("never green both ways").

States that last several cycles

A traffic light stays green for many clock cycles. Rather than one state per cycle, the design adds a small counter, timer, that counts cycles spent in the current state and is cleared whenever the state changes (Listing 3, line 49). The next-state logic then reads "if timer ≥ 5 and a car is waiting, go to yellow" D5 “Factored FSMs”. Strictly, the timer is part of the state (the full state is "state, timer"), but splitting it this way keeps the diagram readable.

Layer 3 — the engineer's depth

Encoding choices. Binary encoding uses the fewest flip-flops. One-hot encoding (one flip-flop per state, exactly one of them 1) uses more flip-flops but often simpler, faster next-state and output logic; synthesis tools may re-encode a state machine they recognise D5 state-encoding slides D3 fsm, fsm_recode.

Not verified — check before relying on this

Gray-style encodings, in which neighbouring states differ in one bit, are said to be useful when a state value is read in another clock domain (F1-18). No source opened in the verification pass covers this; check a digital-design textbook's section on clock-domain crossing before relying on it.

Illegal states. A 3-bit register for 6 states can hold 8 codes; codes 6 and 7 are illegal states. They should never occur, but a design that will run unattended should still say what happens if one does: Listing 3's default sends any unknown code to an all-red state D6 “Combinational Logic using case”. The forensic lab shows a worse problem: a register too narrow to hold some legal codes at all.

Verification by properties. A traffic light's specification is mostly about what must never happen. The testbench in Listing 4 checks three safety properties at every cycle instead of comparing with a fixed expected sequence R2. Formal tools go further: they try to prove such a property for all input sequences, not only the ones a testbench tries. The Yosys tool used in this course has a command, sat, that can attempt to prove that a signal always has a given value, and with temporal induction that it keeps it forever D3 sat.

The processor connection. HW202 designs the control unit of a processor (F1-25). When you get there, look for the three parts of Figure 1: a state register, next-state logic and output logic.

Not verified — check before relying on this

The traffic light here is a teaching example with made-up timings (6, 4, 2 and 1 clock cycles). Real traffic signals follow national road-traffic rules and standards (for example on minimum yellow and all-red times) and safety-critical engineering rules (SS402). This build opened none of them, and nothing in this chapter is a specification for real signals.

How the hardware actually does it

An FSM in silicon is exactly Figure 1: a few flip-flops plus gates. When the synthesis tool reads Listing 3, the state register becomes three flip-flops with a reset, and the case statements become gates (F1-21 shows such a report) D3 synth, proc. Any hardware that must follow a sequence of steps can be built this way. When one machine grows too large, the textbook's slides split it into several smaller FSMs that talk to each other ("factored FSMs") D5 “Factored FSMs”. In HW204 and the driver courses you will read device data sheets that describe a device's behaviour as states; the drivers you write mirror those state machines in software.

Worked example

From words: the 101 detector

Words: "One input bit in is sampled at each rising edge. Output found must be 1 during the cycle after the last three sampled bits were 1, 0, 1. Overlaps count: 10101 contains the pattern twice."

  1. What must be remembered? How much of the pattern has been seen so far: nothing (S0), "1" (S1), "1, 0" (S10), or the whole "1, 0, 1" (S101).
  2. Arrows. From S0: a 1 starts the pattern (S1); a 0 does not (S0). From S1: a 0 continues (S10); another 1 is still a usable first bit (S1). From S10: a 1 completes the pattern (S101); a 0 breaks it, and "0, 0" contains no useful start (S0). From S101: its last bit is a 1, so it can start the next pattern: input 0 gives "1, 0" (S10) and input 1 gives "1" (S1). This last pair of arrows is what makes overlaps count.
  3. Table:
StateMeaningin = 0in = 1found
S0 (00)nothing usefulS0S10
S1 (01)last bit 1S10S10
S10 (10)last bits 1, 0S0S1010
S101 (11)last bits 1, 0, 1S10S11
  1. Encoding: 4 states need 2 bits (22 = 4) W1; codes in brackets above.
  2. Trace on the bits 1, 0, 1, 0, 1: S0 → S1 → S10 → S101 (found) → S10 → S101 (found). Two detections, overlapping.

The traffic light

Words: "A main road (NS) and a side road (EW) cross. NS is green by default. When a car waits on EW (sensor car_ew) and NS has been green for at least 6 cycles, NS goes yellow for 2 cycles, then both roads are red for 1 cycle, then EW is green for 4 cycles, yellow for 2, all red for 1, and NS is green again. States: NS_GREEN, NS_YELLOW, ALL_RED_1, EW_GREEN, EW_YELLOW, ALL_RED_2. Six states need 3 bits W1. Figure 3 shows the diagram; Listing 3 is the Verilog.

Where the analogy breaks


    

  • Rosa can improvise; an FSM cannot. If something happens that the rule card does not mention, Rosa uses common sense. An FSM does exactly what its next-state logic says, including for inputs and states nobody thought about. That is why Step 3 of the method demands an arrow for every input in every state.
    • 

  • The status card holds a word; the state register holds bits. A word cannot be "too long for the card" without someone noticing. A state code that does not fit in the register is silently cut, as the forensic lab shows R3.
    • 

  • One order, one card; one machine, one state. Rosa tracks many orders at once with many cards. One FSM is in exactly one state at a time; many orders would need many FSMs (or a bigger state).

Transition box

Where you came from: F1-17 built counters (FSMs with "+1" as their only rule) and F1-18 fixed the rhythm with the clock. What carries over: one register on one clock, one step per edge, and combinational logic between edges that must finish within the period D5 “Synchronous Sequential Logic”. What changes: the next-state rule is now any logic you design from a description in words, so the hard part moves from building to specifying: naming states, covering every input in every state, and testing properties. What comes next: F1-20 stores not one state but many words, in SRAM and DRAM memory cells.

Summary


    

  • An FSM is a state register plus next-state logic plus output logic, all on one clock.
    • 

  • Moore outputs depend on the state only; Mealy outputs also on the current inputs.
    • 

  • Method: inputs and outputs → what must be remembered (states) → diagram with every arrow → table → encoding → three Verilog blocks → self-checking test.
    • 

  • n states need ⌈log2 n⌉ bits in binary encoding; check the register width.
    • 

  • Long-lasting states use a timer counter that is cleared on every state change.
    • 

  • Give every block a default and every illegal code a safe next state.
    • 

  • Test safety properties at every cycle, not only a fixed expected trace.

Forensic lab answer key


Observation: only states 0–3 appear; after reset the machine shows state 1 (NS yellow) instead of 5 (all red); from state 3 (EW green) it jumps to state 0 (NS green): EW goes green → red with no yellow and NS goes red → green with no all-red cycle, at cycles 8 and 37 R3. The compiler warns: "Port 6 (state) of traffic_bug expects 2 bits, got 3" R3. Hypotheses: (1) the testbench is too strict: ruled out, because the reference design passes the same testbench R2 and the violations are real safety problems; (2) the design cannot hold some states: confirmed. Root cause: traffic_bug.v still declares the old 2-bit widths: output reg [1:0] state and reg [1:0] next (Listing 3 has [2:0] on lines 11 and 26). Six states need 3 bits. Storing 4 (binary 100) keeps only 00, so EW_YELLOW becomes NS_GREEN; storing 5 (101) keeps 01, so the reset state ALL_RED_2 becomes NS_YELLOW. Fix: widen both declarations to [2:0]; the testbench then passes, as the reference does. Prevention: treat every compiler warning as an error (the lab script does this for its own designs); derive register widths from the number of states in one place; print the state in every testbench; check that every state appears at least once in a test (state coverage). How the evidence was made: Listing 3 with the two width declarations changed back to [1:0] and the module renamed, run with the unchanged testbench. Wrong answers: "the timer is wrong" (the timer works; the yellow state cannot exist at all); "the default branch is missing" (it is there, but codes 6 and 7 are not the problem: the register cannot hold codes 4 and 5).
