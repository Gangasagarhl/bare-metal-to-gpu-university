Story hook

Analogy

Ana orders a bicycle in a box. The box holds a parts list: frame, fork, handlebar, two wheels, cranks. For each part there is one line saying what it is attached to, where, and how it may move. The fork is hinged to the frame at the head tube and turns left and right. Each wheel spins on an axle at the end of the fork or the frame. The handlebar is clamped to the fork and does not move relative to it. With only this list and a spanner, Ana builds the bicycle. A mechanic in another town could draw the same bicycle from the same list without seeing it.

A robot description file is that parts list for a robot, written so that programs can read it. Every tool that draws the robot, simulates it, plans its motion or publishes its frames reads the same file. That is the strength of the file, and its danger too: one wrong line, such as a hinge placed on the wrong side, misleads all of those programs at once, and none of them complains.

What you will be able to do

  • Read a robot description in URDF: links, joints, origins, axes, limits and masses, and draw its link tree.
  • Compute a link's pose from the file by walking the tree and composing each joint's origin and motion (F9-23, F9-25).
  • Write a URDF of the course robot and verify it against the closed-form kinematics and against simulator ground truth.
  • Explain what SDF adds to URDF (worlds, several models, closed chains, sensors) and when each is used.
  • Diagnose a model file whose origin is wrong by comparing model predictions with an external measurement.
Jargon box
Robot description (model file)
Simple words: a text file that lists a robot's parts, how they are joined, and how much they weigh. Analogy: the bicycle's parts list with attachment instructions. Precise: a machine-readable description of a robot's kinematic tree (links and joints with their fixed offsets, axes and limits) and, optionally, inertial, visual and collision data; read by visualisers, simulators, planners and frame publishers. D1S1
URDF (Unified Robot Description Format)
Simple words: the XML format ROS uses for one robot's parts list. Analogy: a parts list that only allows a tree: every part hangs off exactly one other part. Precise: an XML format with a robot element containing link and joint elements; the joints must form a tree with one root link. Element names in this chapter are unverified (see the box in Layer 3). S1
SDF (Simulation Description Format)
Simple words: a richer XML format that can describe whole worlds for a simulator. Analogy: the plan for the whole bike shed, not only one bicycle. Precise: an XML format for worlds containing several models, lights and physics settings; models may include closed kinematic chains and sensors. Described conceptually only in this chapter (unverified). S2
Joint origin
Simple words: where the child part sits on the parent part when the joint is at zero. Analogy: "the fork is attached 5 cm in front of the frame's top, tilted back". Precise: the fixed transform Tparent,joint from the joint frame to the parent link frame, given as a translation xyz and a rotation rpy; the joint's motion is applied after it, about the joint's axis in the joint frame. D1S1
Roll–pitch–yaw (rpy)
Simple words: three angles that say how a part is turned: about x, about y and about z. Analogy: tipping a bicycle sideways (roll), nose up or down (pitch), and turning it left or right (yaw). Precise: in this chapter's reader, rotation R = Rz(yaw)Ry(pitch)Rx(roll) with angles in radians; that this matches URDF is an assumption (unverified box). D1S1
Joint type (revolute, continuous, prismatic, fixed)
Simple words: how a joint may move: turn with limits, turn for ever, slide, or not at all. Analogy: the fork (limited turn), a wheel (endless turn), a seat post (slide when loosened), the handlebar clamp (fixed). Precise: revolute: rotation about the axis within [lower, upper]; continuous: unlimited rotation; prismatic: translation along the axis; fixed: no motion, the origin alone. S1D1

The idea in pictures

Figure 1 is the link tree of the course robot, read from course_robot.urdf by this chapter's reader. Boxes are links, each with its own frame. Arrows are joints and point from parent to child. Each joint's label gives its type, axis and the main part of its origin. The arm hangs off the base through a fixed joint; the wheels hang off the base through continuous joints.

Layer 1 — the kid explanation

To describe a robot to a computer, you write a list. First the parts: the body, the wheels, each piece of the arm. Then, for every part except the body, one line saying which part it hangs from, where it is attached, which way it can turn, and how far.

The computer can then work out where every part is. It starts at the body and follows the list outwards: the arm is here on the body, the upper arm is here on the arm's base, turned this much, and so on, like following a family tree from grandparent to grandchild. Every part has exactly one parent, so the computer never gets lost.

Because every program reads the same list, a mistake in the list fools all of them. So you check the list against the real robot: you measure where the hand really is, and compare.

Layer 2 — the student explanation

Links and joints in the file

Listing 1 is the course robot as a URDF file. A link element names a rigid body and may hold its inertial data; here only the mass, in kilograms. A joint element names its type, its parent and child links, an origin with xyz (metres) and rpy (radians), an axis for moving joints, and a limit for revolute ones. These names come from the author's memory of URDF and must be checked (unverified box in Layer 3). The file's rules of meaning are what this chapter teaches, and Listing 2's reader implements them so that they can be tested. S1D1

From file to pose

For each joint, the reader builds the origin transform Torigin = (Rz(yaw)Ry(pitch)Rx(roll), xyz). The child link's pose in the parent is then D1B1

T_parent,child(q) = T_origin · Rot(axis, q) (revolute or continuous joint) T_parent,child = T_origin (fixed joint)

and a link's pose in the root is the product along the path from the root, as in F9-23's frame tree. For the tool: Tbase_link,tool = Tarm_mount · Tbase_yaw(q1) · Tshoulder(q2) · Telbow(q3) · Ttool_mount. This is F9-25's forward kinematics, now read from a file instead of written in code. D1

Verify the file

A model file is code, so it gets tests. Run R1 checks three things. The file's structure: one root, every joint names known links, no link has two parents. The arm's forward kinematics computed from the file against the closed form of F9-25 plus the mount offset (0.1, 0, 0.3), at 5,415 configurations; the largest difference is 1.11 × 10−16 m. And plain facts: total mass 6.50 kg; tool at the home pose at (0.7000, 0, 0.4000) m; wheel origins at y = ±0.150 m, unmoved when the wheels turn. R1

Watch out

Angles in the model file are radians. rpy="0 0 90" does not mean 90°: it means 90 rad, which is 14.32 turns and lands at 116.62° (run R2). The file is still valid, and nothing warns you. The forensic lab is this mistake.

URDF and SDF

URDF describes one robot as a tree. SDF describes worlds: several models, the ground, lights, physics settings, and models that can have closed chains (a four-bar linkage, a parallel gripper) and sensors with their own parameters. In the ROS world, robot descriptions for frame publishing and planning are usually URDF, often generated from a macro language; simulators often convert URDF to SDF or load SDF directly. This chapter's own simulators read the URDF subset of Listing 2. S1S2

Layer 3 — the engineer's depth

Joint frames and the axis. In URDF the joint frame coincides with the child link frame; the axis is expressed in that frame. So the origin decides where the hinge is and how the child is oriented at zero; the axis decides which way it turns. A hinge on the wrong side, or an axis with the wrong sign (F9-25's elbow flip), are both one-character errors. Writing an axis such as 0 -1 0 instead of rotating the frame is a legitimate choice that keeps link frames aligned with the base at the home pose, as the course robot does. S1D1

Inertial, visual, collision. A full link has inertial data (mass, centre of mass with its own origin, and the six independent entries of the inertia tensor, F9-28), visual geometry for drawing, and simpler collision geometry for contact and planning. Simulators need physically consistent inertia (positive definite, satisfying the triangle inequalities on the principal moments); a link with a zero or tiny inertia can make a simulation unstable. Collision shapes are usually simplified boxes, cylinders and convex meshes for speed. B1S1

What the tree cannot say. A tree has no closed loops, so parallel mechanisms are described in URDF by breaking a loop and adding a constraint elsewhere (in the simulator or controller); mimic relations, transmissions to motors and controller settings are extensions with their own elements. The wheels of a differential drive (F9-24) are continuous joints; the floor contact that makes them drive the robot is not in the URDF at all; the simulator provides it. S1S2

Models as the single source of truth. The same file feeds the frame publisher (F9-23's tf2 tree), visualisers, motion planners (RB401) and simulators. That is why the model must be verified against measurements of the real robot, and why it belongs in version control with its tests, like code. Calibration (F9-23) then corrects the measured offsets in the file. U1D1

Not verified — check before relying on this

URDF and SDF details in this chapter were written from the author's memory and were not checked against their specifications in this build. Specifically: (1) the element and attribute names robot, link, inertial, mass value, joint name type, parent link, child link, origin xyz rpy, axis xyz, limit lower upper, and the joint types revolute, continuous, prismatic, fixed; (2) the assumption that rpy is in radians and composes as R = Rz(yaw)Ry(pitch)Rx(roll) (fixed axes, roll first); (3) that the joint frame equals the child link frame and the axis is expressed in it; (4) whether a revolute joint also requires effort and velocity attributes in limit (our reader does not need them; standard tools may refuse the file without them); (5) everything said about SDF, which is described conceptually only; (6) the names of ROS 2 tools that read or check a URDF (frame publisher, file checker, macro language). The lab's files were read only by this chapter's own reader. Before RB401 uses them, a standard URDF parser must load course_robot.urdf, and the dossier must record the specification versions.

How the hardware actually does it

A model's numbers come from three places: the mechanical design (CAD drawings give link lengths, mount positions and estimated masses and inertias); measurement (a tape measure and scales for a kit robot; joint zero positions from the encoders, RB201); and calibration (F9-23: fitting offsets so that the model's predictions match an external measurement such as a camera or a tracker). The joint zero in the file must match the zero of the encoder and the motor driver; a few degrees of mismatch moves the tool by centimetres at full reach. Mass and inertia from CAD miss cables, glue and screws; F9-28's lab shows how such errors show up as gravity-compensation drift. U1D1

Not verified — check before relying on this

Untested on hardware. All dimensions, masses and limits in course_robot.urdf belong to the university's simulated course robot. They were not measured on the kit robot named in the dossier; whoever builds the kit must measure it, update the file, and rerun the lab's tests. The "tracker" in the forensic lab is a simulated ground truth, not a real tracking system.

Worked example

Where is the course robot's tool, in the base_link frame, at base_yaw = 90°, shoulder = 30°, elbow = −60°? Walk the tree of Listing 1.

  1. arm_mount (fixed): translate (0.1, 0, 0.3). The arm's base sits 0.1 m ahead of and 0.3 m above the base origin.
  2. base_yaw (revolute about z, origin 0): turn 90° about z. The arm's forward direction becomes +y of base_link.
  3. shoulder (origin (0, 0, 0.10), axis (0, −1, 0)): 0.10 m up, then turn 30° about −y, which raises the upper arm 30° above horizontal.
  4. elbow (origin (0.30, 0, 0), axis (0, −1, 0)): 0.30 m along the upper arm, then −60°: the forearm points 30° below horizontal.
  5. tool_mount (fixed, (0.30, 0, 0)): 0.30 m along the forearm.
  6. In the arm's vertical plane: reach = 0.30 cos 30° + 0.30 cos(−30°) = 0.5196 m, height above the shoulder = 0.30 sin 30° + 0.30 sin(−30°) = 0. In base_link: x = 0.1 + 0.5196 cos 90° = 0.1, y = 0.5196 sin 90° = 0.5196, z = 0.3 + 0.10 + 0 = 0.4 m.

Run R2 computes the same point from the file: (0.1000, 0.5196, 0.4000). It also checks the two rpy facts used in this chapter: a yaw of 90° turns the x axis to (0, 1, 0), and rpy (90°, 0, 90°) puts the child's z axis along the parent's x axis.

Where the analogy breaks


    

  • Ana's bicycle has a loop; a URDF cannot. A bicycle frame is a closed triangle and the chain forms a loop; URDF allows only trees. Loops need SDF or extra constraints. S2
    • 

  • Ana can see a mistake; programs cannot. A builder notices a fork put on backwards. A program reading rpy="0 0 90" accepts 90 radians without a word. Tests replace the eyes. R3
    • 

  • The parts list is not the bicycle. Real parts bend, wear and are assembled slightly off; the file holds nominal values until calibration corrects them. D1

Goal


Model the course robot in URDF; simulate it; verify its kinematics against simulator ground truth (course card). The simulator is the university's own: this chapter's reader drives the kinematics, and the base motion comes from F9-24's differential-drive simulator.


Hardware and software needed


A computer with a C++ compiler; this build used g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0 with the flags of the build command. Optional: the course kit robot, a tape measure and kitchen scales for step 6 (untested on hardware).

Steps 1–5 are software only. For step 6, switch the robot's power off and disconnect its battery before measuring it; support the arm so it cannot drop when its joints are unpowered; keep fingers out of the gear trains. Learners below L3 work with adult supervision.

Verification

  • Agreement everywhere except when the base turns → you composed the base pose on the wrong side of the chain.
