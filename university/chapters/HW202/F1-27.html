Story hook

The five-station row from the last chapter works beautifully for a while. Then a ticket arrives: "make the sauce", and right behind it, "pour the sauce over the fish". The sauce is still on the stove when the fish reaches the plating station. The plating cook stands there, waiting. Behind her, every station waits too.

Daniel, the head chef, watches for a few minutes. Then he changes one rule. "Don't wait for the sauce to be bottled and put on the shelf. As soon as it leaves the stove, hand the pot straight across the counter to whoever needs it." The waiting shrinks to almost nothing.

Almost. One kind of ticket still causes a pause: anything that needs an ingredient from the pantry. The pantry runner comes back one bell too late for the very next station, however fast the hand-over is. Daniel's fix for that is cleverer still: he reorders the tickets so that something else is cooked in that gap. This chapter is about those waits (hazards), the hand-over (forwarding), and the reordering trick. Its forensic lab is the course's classic: the slow loop.

What you will be able to do

  • Identify read-after-write data hazards in a U16 or real assembly sequence and say which stages are involved.
  • Explain forwarding (bypassing): which values are forwarded, from where, to where, and when it cannot help.
  • Calculate stall cycles with and without forwarding, and the cost of taken branches, from a pipeline diagram.
  • Remove a load-use stall by reordering instructions, and prove that the result is unchanged.
  • Diagnose "the slow loop": find the load-use hazard from a pipeline diagram and the assembly.
Jargon box
Data hazard (read after write, RAW)
Simple words: an instruction needs a result that an earlier instruction has not finished writing. Analogy: the fish reaches plating while the sauce is still on the stove. Precise: a dependence in which instruction j reads a register that an earlier instruction i writes, and j would read it in the pipeline before i has written it. D1 D3
Stall (bubble)
Simple words: making an instruction wait a cycle, with an empty slot moving down the pipeline instead. Analogy: a station that does nothing for one bell while the rest of the row moves on. Precise: holding an instruction (and those behind it) in place for a cycle while a no-operation, the bubble, is inserted into the next stage. D1
Forwarding (bypassing)
Simple words: giving a result straight to the next instruction that needs it, before it is written into the register. Analogy: handing the pot across the counter instead of bottling the sauce and shelving it first. Precise: extra datapath paths and multiplexers that deliver a result from the EX/MEM or MEM/WB pipeline register to the ALU inputs of a later instruction in EX, selected by a forwarding unit that compares register numbers. D1 D2
Load-use hazard
Simple words: using a value loaded from memory in the very next instruction. Analogy: the pantry runner comes back one bell too late for the next station. Precise: a RAW hazard where the producer is a load whose value exists only at the end of MEM, so a dependent instruction immediately after it must stall one cycle even with forwarding. D1 R1
Control hazard (branch hazard)
Simple words: not knowing which instruction comes next until a branch is decided. Analogy: the next ticket depends on a guest's answer that has not come back yet. Precise: a hazard caused by fetching instructions after a branch before the branch outcome and target are known; wrongly fetched instructions must be flushed. D1
Flush
Simple words: cancelling instructions that were started by mistake. Analogy: throwing away dishes started for the wrong ticket. Precise: turning instructions already in early pipeline stages into bubbles (their control signals set to zero) so they change no state. D1
Instruction scheduling
Simple words: putting instructions in a different order so the pipeline waits less, without changing the result. Analogy: cooking something else while the pantry runner is away. Precise: reordering independent instructions (by a compiler or by hardware) to separate producers from consumers, preserving all data dependences. D1 D3

Layer 1 — the kid explanation

In a pipeline, instructions overlap. That is the whole point. But sometimes an instruction needs the answer of the one right before it. In a pipeline, that answer is not written down yet when the next instruction wants to read it. This clash is called a hazard.

The simple fix is to wait. The second instruction stops for a few ticks until the first one has written its answer. The pipeline does not break, but it gets slower: empty slots, called bubbles, travel down the row.

The clever fix is forwarding. The answer exists as soon as the ALU has computed it, even before it is written into the register. So the hardware adds a short-cut wire that hands the fresh answer straight to the next instruction. Most waits disappear.

One wait stays: when the answer comes from memory. A value from memory arrives one step later than an ALU answer, so the very next instruction is still too early. The trick then is to put a different, useful instruction in between. Compilers do this all the time.

Branches cause a different problem. The pipeline fetches the next instructions before it knows whether the branch jumps. If it guessed wrong, it throws those instructions away. That costs cycles too.

Layer 2 — the student explanation

When does a RAW hazard happen?

In the five-stage pipeline, an instruction reads its source registers in ID and writes its destination in WB, three stages later. D1 If instruction i writes register r and one of the next instructions reads r, the reader's ID may come before i's WB. With the register file written in the first half of a cycle and read in the second half, a reader whose ID is in the same cycle as the writer's WB is safe; anything earlier is a hazard. D1 For adjacent instructions that means two stall cycles, for instructions two apart one stall cycle, and from three apart none. The real run of the sum program without forwarding shows exactly this: add r3, r3, r4 right after lw r4 shows ID id id EX, two stall cycles. R1

Write-after-read and write-after-write orderings cannot cause trouble in this simple pipeline, because instructions read in ID and write in WB in program order; they matter in the out-of-order processors of F1-29. D3

Forwarding

An ALU result exists at the end of EX, two cycles before WB. Forwarding sends it from the EX/MEM pipeline register directly to the ALU inputs of the next instruction, and from MEM/WB to the instruction after that. D1 D2 The forwarding unit's rule, in words: "if the instruction in EX/MEM writes a register (RegWrite = 1), its destination is not r0, and it equals a source of the instruction now in EX, select the EX/MEM value for that input; otherwise, check MEM/WB the same way; otherwise use the value read in ID". The newer producer (EX/MEM) wins when both match. D1 In the model, forwarding is line 86 of pipe.h: the reader's EX may start one cycle after the producer's EX. R1

The load-use hazard

A load's value exists only at the end of MEM, one stage later than an ALU result. An instruction immediately after the load reaches EX in the same cycle the load is in MEM, too early even for forwarding: the arrow in Figure 1c would point backwards in time. So the hazard detection unit stalls the dependent instruction for one cycle, then the value is forwarded from MEM/WB. D1 The model encodes this as line 84 of pipe.h. In the sum loop with forwarding, the only remaining data stall is exactly this one, once per iteration: 5 stall cycles in 5 iterations. R1

Scheduling away the stall

If an independent instruction is placed between the load and its use, the bubble is filled with useful work. In the sum loop, the two addi instructions do not depend on r4, so they can move up between lw and add (reordered.s). The result must not change, and the real runs on the U16 computer prove it: both versions output 29. R2 With forwarding, the reordered loop has no data stalls at all: 42 cycles instead of 47. R2 Compilers perform this kind of instruction scheduling for the pipelines they target. D1 D3

Control hazards

The model's pipeline keeps fetching the next instructions in order (it predicts "not taken") and decides branches at the end of EX. When a branch is taken, the two instructions fetched after it are flushed and the target is fetched in the next cycle: two lost cycles per taken branch. D1 R1 In the diagrams these are the rows marked (flushed), with xx cells. The sum loop's branch is taken four times, so 8 cycles are lost in every version. Deciding branches earlier (in ID) would halve that, at the cost of extra comparison hardware and new hazards in ID; predicting better is F1-28. D1

Layer 3 — the engineer's depth

  • Accounting identity. In the model, total cycles = instructions + 4 + data-stall cycles + branch cycles, and every real run satisfies it: 30 + 4 + 20 + 8 = 62, 30 + 4 + 5 + 8 = 47, 30 + 4 + 0 + 8 = 42. Checking the identity is a quick test of any hand-drawn diagram. R1 R2
  • Stores. A sw needs its data value in MEM, not EX, so a design can forward a load's result to a following store without a stall. The model is conservative and treats the store's data like an ALU input; the textbooks discuss the refinement. D1 R1
  • Interlocks versus exposed delays. The hardware stall for load-use is called an interlock. Some early pipelined ISAs instead made the delay part of the ISA: the instruction after a load must not use its result, and the compiler fills the slot. That leaks the microarchitecture into the ISA (F1-23), which later implementations then have to carry. D3
  • Forwarding costs. Each forwarding path adds wires and a wider multiplexer at the ALU inputs, on the critical path of EX. Deep or wide pipelines need many more paths, one reason they are expensive. D3
Not verified — check before relying on this

All stall and cycle counts in this chapter come from the five-stage model, not from a real processor. The load-use penalty, forwarding paths and branch handling of any real CPU are not stated; nothing could be measured on the build machine (the perf tool did not work in the container). The historical remark about ISAs with exposed load delays is from D3 as named (Appendix C located in the verification pass; the book's text not opened), and no ISA or processor is named for it.

How the hardware actually does it

The forwarding unit is a few comparators: 3-bit equality checks between the source fields carried in ID/EX and the destination fields in EX/MEM and MEM/WB, gated by those registers' RegWrite bits and a "not r0" check. Their outputs are the select inputs of the ALU input multiplexers in Figure 2. D1 D2 The hazard detection unit compares the sources of the instruction in ID with the destination of a load in ID/EX (MemRead = 1). On a match it does three things in the same cycle: it keeps the PC and IF/ID from loading (so the same instructions are fetched and decoded again), and it writes zeros into the control fields of ID/EX, which turns that slot into a bubble. A flush works the same way for the wrongly fetched instructions after a taken branch. D1 All of it is combinational logic plus write enables on pipeline registers: no instruction "waits" in any active sense.

Worked example

Task. Predict the cycles of the sum loop's first iteration without forwarding, then check against the real diagram.

  1. lw r4, 0(r1) (4th instruction): IF 4, ID 5, EX 6, MEM 7, WB 8.
  2. add r3, r3, r4 reads r4. Without forwarding it may read r4 in ID no earlier than r4's WB cycle 8. It enters ID in cycle 6, stalls in cycles 7 and 8, enters EX in cycle 9: two stall cycles.
  3. addi r1, r1, 1 does not read r4. It was fetched in cycle 6 but must wait in IF while add holds ID: IF 6, ID 9, EX 10.
  4. addi r2, r2, -1: IF 9, ID 10, EX 11, MEM 12, WB 13.
  5. bne r2, r0, loop reads r2, written in WB at cycle 13. It enters ID at cycle 11, stalls in 12 and 13, enters EX at 14: two more stall cycles. The branch is resolved at the end of cycle 14; the target lw is fetched in cycle 15.

The real run shows the same cells: add "IF ID id id EX", the first addi "IF if if ID", bne "IF ID id id EX", and two flushed fetches. R1 With forwarding, step 2 becomes one stall (load-use), step 5 becomes zero (ALU result forwarded from EX/MEM), and the iteration is 3 cycles shorter.

Where the analogy breaks


    

  • A cook can see the sauce is not ready; hardware must compare numbers. Hazard detection is not seeing: it is equality checks on 3-bit register numbers. Two instructions that touch the same memory word through different registers are not detected this way at all (in this pipeline, memory accesses happen in order in MEM, so it does not matter). D1
    • 

  • Handing a pot across is free; forwarding is not. Every path costs wires and multiplexer delay on the critical path. D3
    • 

  • Reordering tickets could change a dinner; reordering instructions must not change results. Only independent instructions may move. In the sum loop, moving add above lw would add the old r4: a wrong answer, not a faster one.
    • 




Common mistakes and debugging


    

  • Symptom: a hand-drawn diagram with forwarding still shows two stalls for ALU-to-ALU dependences. Cause: forgetting the EX/MEM path. How to find it: compare with the model's forward-mode output. Fix: an ALU result can be used in the next cycle's EX.
    • 

  • Symptom: a diagram with zero stalls after a load used immediately. Cause: forwarding "backwards in time". How to find it: draw the arrow; it must point right or straight down. Fix: one bubble.
    • 

  • Symptom: a reordered program prints a different answer. Cause: a moved instruction depended on one it jumped over. How to find it: list each instruction's sources and destination; check every pair that changed order. Fix: move only independent instructions. Always rerun the program (R2) after scheduling.
    • 

  • Symptom: counting r0 as a dependence. Cause: r0 is never written, so it never creates a hazard (line 51 of pipe.h drops it). Fix: ignore r0 sources.
    •

Summary


    

  • A RAW data hazard occurs when an instruction reads a register before an earlier instruction has written it.
    • 

  • Without forwarding, an adjacent dependence costs two stall cycles in the five-stage pipeline.
    • 

  • Forwarding passes results from EX/MEM and MEM/WB straight to the ALU inputs; ALU-to-ALU dependences then cost nothing.
    • 

  • A load used by the next instruction still costs one bubble: the load-use hazard.
    • 

  • Scheduling independent instructions between a load and its use removes that bubble; the result must be re-checked (both versions output 29).
    • 

  • Taken branches cost two cycles in the model (resolved in EX, two fetches flushed).
    • 

  • Cycles = instructions + 4 + stall cycles + branch cycles in every real run.

Forensic lab answer key


Root cause. In the loop, slt r5, r6, r4 uses r4 immediately after lw r4, 0(r1): a load-use hazard. With forwarding, it costs one bubble per iteration. The diagram shows slt as "IF ID id EX" in cycles 7–10 (the id in cycle 9), and the summary reports 8 data-stall cycles for 8 iterations.


Evidence. Forwarding summary: 55 instructions, 81 cycles, 8 data-stall cycles, 14 branch cycles. Identity: 55 + 4 + 8 + 14 = 81. The 14 branch cycles are 7 taken branches × 2 (the eighth time the loop exits). So the "extra" 22 cycles split into 8 (load-use) and 14 (branches); the ALU-to-ALU dependences (slt → add, addi r2 → bne) cost nothing with forwarding. (The first diagram, without forwarding, has 50 stall cycles: that core would be much slower, but Leila's core forwards.)


Fix. Move addi r1, r1, 1 between the load and the slt (forensic_fixed.s). Real runs: with forwarding, 73 cycles and 0 data-stall cycles (R3); the U16 computer prints out: 3 for both versions (answer_forensic, answer_forensic_fixed), so the result is unchanged.

Wrong answers and why. "The branch is the problem": it costs 14 cycles, which a predictor (F1-28) could reduce, but the question asks about the stall marked in the diagram, and the 8 data-stall cycles are exactly the load-use count. "Forwarding is broken": ALU-to-ALU pairs show no stall. Prevention: let the compiler schedule for the pipeline; review hot loops with a pipeline model or with the processor's documented latencies.
