Story hook

Amina's restaurant is opening branches in two other cities. Head office writes each recipe once, in plain words. Each branch's kitchen then rewrites it into its own ticket language: one kitchen calls the stations by numbers, another by colours, a third has extra stations the others lack. The dish should taste the same everywhere.

One day a branch's soup is reported as "suspiciously fast": it leaves the kitchen in no time. Amina reads that branch's tickets, not the head-office recipe, and finds the problem in a minute. The branch had noticed that nobody ever tasted the stock, so it had stopped making it. The recipe said "make stock"; the tickets did not.

Your C++ is the head-office recipe. The compiler rewrites it into the ticket language of each processor, and with optimisation it rewrites boldly. When a measurement looks strange, the truth is in the tickets: the assembly. This chapter teaches you to read it on three real instruction sets.

What you will be able to do

  • Produce the assembly of a C++ function for x86-64, ARM64 and RISC-V at several optimisation levels, with a recorded command.
  • Read small functions in each: find the arguments, the result, loads, stores, branches and loops.
  • Compare -O0, -O1, -O2 and -O3 output and explain the main differences.
  • Tell apart Intel and AT&T syntax for x86-64.
  • Diagnose a benchmark whose loop was removed by the optimiser.
Jargon box
Disassembler
Simple words: a program that turns machine code back into assembly text. Analogy: reading a kitchen's tickets aloud in words. Precise: a tool (here objdump -d) that decodes the instruction bytes in an object file or executable into mnemonics and operands, with addresses. D4
Optimisation level
Simple words: how hard the compiler tries to make the program fast or small. Analogy: how freely a branch may rewrite head office's recipe. Precise: a compiler option such as -O0 (no optimisation, code follows the source closely), -O1, -O2, -O2 (in GCC 13 "nearly all supported optimizations that do not involve a space-speed tradeoff") and -O3 (more loop transformations and a more generous vectorisation cost model); each enables a set of individual optimisation passes that the compiler's manual lists. D3 §3.11
Calling convention (ABI)
Simple words: the agreed rules for where a function finds its arguments and leaves its result. Analogy: every kitchen agreeing which shelf the order slip goes on. Precise: part of the application binary interface: which registers or stack slots carry arguments and return values, which registers a function must preserve, and stack alignment; different for each ISA and operating system (F2-47). D5
Stack frame
Simple words: a function's own scratch area in memory, made when it starts and removed when it returns. Analogy: a cook's cutting board, cleared after each dish. Precise: the region of the stack used by one function call for saved registers, local variables and spilled values, reached through the stack pointer or a frame pointer. D5
Conditional move / select
Simple words: an instruction that picks one of two values depending on a condition, with no jump. Analogy: handing over plate A or plate B without walking anywhere. Precise: x86-64 cmovcc, ARM64 csel: the result depends on the flags, and the program counter goes to the next instruction in all cases, so there is nothing to predict (F1-28). D1 D2
Vectorisation
Simple words: making one instruction work on several numbers at once. Analogy: one cook slicing four carrots with one stroke. Precise: transforming a loop to use SIMD instructions (for example the paddd instruction in this build's -O3 output, a packed add of 32-bit integers in a 128-bit register; its exact definition is in D1, not opened) that process several elements per instruction. D1 D3 §3.11 R3
Dead code elimination
Simple words: the compiler deleting work whose result is never used. Analogy: the branch that stopped making the stock nobody tasted. Precise: an optimisation that removes computations with no observable effect; C++ allows any transformation that preserves observable behaviour (the "as-if" rule), and elapsed time is not observable behaviour. D3 §3.11 D6 [intro.abstract]

The idea in pictures

Figure 1 shows one line of C++, return a + b;, as the three compilers translated it at -O2. The shape is the same everywhere: arguments arrive in registers, one instruction adds, the result leaves in a register. Only the names and the instruction differ.

Layer 1 — the kid explanation

When you write a program, a compiler translates it into the processor's own instructions. Different processors speak different instruction languages, so the same program becomes different lists of instructions on a phone and on a laptop.

You can ask the computer to show you that list. It looks strange at first, but it is made of the same few things everywhere: move a number into a register, add, compare, load from memory, store to memory, jump.

The compiler can translate carefully, word by word, or cleverly, rewriting to go faster. When it is clever, it may combine steps, use special instructions, or even remove work nobody looks at.

That last trick can fool you. If you time a loop whose answer you never use, the clever compiler may delete the loop, and the timer says it took no time at all. Reading the instruction list shows what really happened.

Layer 2 — the student explanation

Getting the assembly

Compile to an object file, then disassemble it: g++ -O2 -c funcs.cc -o funcs.o, then objdump -d --no-show-raw-insn -M intel -C funcs.o. -C turns mangled C++ names back into readable ones; -M intel chooses Intel syntax for x86-64. D4 objdump The same works with the cross-compilers aarch64-linux-gnu-g++ and riscv64-linux-gnu-g++ and their own objdump. R1 An online compiler explorer does the same in a browser; this build could not reach one, so every output here was produced locally and its command is in its log.

A reading method

  1. Find the function's label and its ret.
  2. Find the arguments. In this build's output: x86-64 reads the first two int arguments from edi and esi and returns in eax; ARM64 uses w0, w1 and returns in w0; RISC-V uses a0, a1 and returns in a0. R1 R5 R7 That is what the calling conventions prescribe: the System V AMD64 ABI passes integer arguments in rdi, rsi, rdx, rcx, r8, r9 in that order and returns in rax (the 32-bit names edi, esi, eax are the low halves); the AAPCS64 uses r0–r7 for arguments and results; the RISC-V convention uses a0–a7 and returns in a0 and a1. Each ABI also lists the registers a function must preserve: rbx, rbp, r12–r15; r19–r28; s0–s11. D5 §3.2.3
  3. Find the loop: a backward branch (target address lower than the branch's own address).
  4. Find memory accesses: brackets in Intel syntax, parentheses in RISC-V, [ ] with ldr/str on ARM64.
  5. Map back to the source line by line; expect reordering.

What optimisation changes

At -O0, GCC stores every argument and local variable on the stack and reloads it at each use: add is 10 instructions on x86-64, including two stores to the stack and two loads back. R2 That makes debugging easy and code slow. At -O2, add is lea eax,[rdi+rsi*1] and ret (after the endbr64 marker). R1 maxOf becomes branch-free with cmovge; sumArray walks a pointer instead of an index. R1 At -O3, GCC vectorised sumArray: the loop uses movdqu and paddd to add four integers per instruction, with extra code for the leftovers. R3 More instructions in the file does not mean slower: the vector loop runs a quarter as many iterations. The GCC manual describes -O0 as the default that makes "debugging produce the expected results", -O2 as "nearly all supported optimizations that do not involve a space-speed tradeoff", and -O3 as adding further loop transformations and a vectorisation cost model that uses a run-time check; which passes each level enables is GCC's own list. D3 §3.11

x86-64 can add straight from memory; ARM64 and RISC-V are load–store machines, like U16 (F1-23). ARM64 folded the pointer update into the load; RISC-V compares and branches in one instruction, like U16's bne. For maxOf, x86-64 used cmovge and ARM64 csel, while RISC-V used a branch, bge: the base RISC-V ISA has no conditional-move instruction. R1 R5 R7 D2

Intel versus AT&T syntax

The same x86-64 bytes can be printed two ways. Intel syntax puts the destination first: mov eax,esi. AT&T syntax, the GNU default, puts it last and decorates registers and constants: mov %esi,%eax, add $0x4,%rdi, and memory as (%rdi,%rsi,4) instead of [rdi+rsi*4]. D4 Compare the two -O2 outputs in the lab: every line matches. R4 Always check which syntax you are reading before deciding which operand is written.

Layer 3 — the engineer's depth

  • Two compilers, two answers. Clang 18.1.3 at -O2 also used a conditional move for maxOf, but cmovg with a different operand order, and it vectorised sumArray already at -O2 (its output is 54 lines against GCC's 30). R6 Optimisation levels are compiler-specific names, not standards. D3 §3.11
  • Width tricks. int is 32 bits but registers are 64. x86-64 writes to eax clear the upper half of rax; RISC-V uses addw and sext.w to keep 32-bit results sign-extended in 64-bit registers; ARM64 names the low half wn. D1 D2
  • Markers and padding. endbr64 is a control-flow-protection marker added because Ubuntu's GCC enables it by default; nop lines after ret are padding to align the next function. Neither is part of your algorithm. D1 D3
  • Signed overflow. The compiler may assume s += p[i] never overflows, because signed overflow is undefined in C++; that freedom is part of what allows reordering into vector lanes. D6 [expr.pre]
  • Object versus executable. Addresses in an object file start at 0 and calls are not yet resolved; in a linked executable (the forensic lab) they are final, and calls to shared libraries go through the @plt stubs, as the main of the forensic lab shows. R1 R8 F2-32 goes further with reading compiler output.

To test it you need an ARM64 or RISC-V machine; a first check is possible with the user-mode emulators qemu-aarch64 and qemu-riscv64 (QEMU 8.2.2, installed in the verification container but not used for these objects, which have no main).

How the hardware actually does it

Every line you read is an encoding the decoder of F1-25 turns into control signals. x86-64 instructions have variable length: in the -O2 output, addresses step by 2, 3, 4 or more bytes (for example lea at 4, ret at 7). ARM64 instructions are all 4 bytes: the addresses go 0, 4, 8. RISC-V instructions are 4 bytes, or 2 bytes when the compressed extension is used, which this toolchain did by default: addresses go 0, 2, 4. R1 R5 R7 D2 Fixed-length encodings make fetch and decode simpler; variable-length encodings save space but need more decode hardware, a trade-off you met for U16 in F1-23. The cross-compiled code was not run, so the claim that it behaves as read is untested on hardware.

Where the analogy breaks


    

  • A branch kitchen that skips the stock is breaking the recipe; a compiler that deletes unused work is not. C++ promises only the observable behaviour (output, volatile accesses, and so on), and time is not part of it. D6 [intro.abstract]
    • 

  • Ticket languages are invented per kitchen; ISAs are fixed, published contracts. The compiler chooses among the instructions the ISA offers; it cannot invent new ones (F1-23).
    • 

  • The tickets are not the whole kitchen. Assembly shows the instructions, not how the out-of-order core will schedule them (F1-29) or how long memory takes (F1-33). Reading assembly explains a measurement; it does not replace one.
    • 




Common mistakes and debugging


    

  • Symptom: reading mov %esi,%eax as "write esi". Cause: AT&T syntax puts the destination last. How to find it: look for % and $. Fix: choose -M intel, or read right to left.
    • 

  • Symptom: the function you want is missing from the output. Cause: it was inlined into its caller, or removed as unused. How to find it: search the caller; compile the function in its own file with -c. Fix: read it where it ended up, or mark it noinline for study only.
    • 

  • Symptom: mangled names such as _Z3addii. Cause: C++ name mangling. Fix: objdump -C or c++filt.
    • 

  • Symptom: drawing conclusions about speed from -O0 code. Cause: unoptimised code is dominated by stack loads and stores. Fix: study the level you ship.
    • 

  • Symptom: "the compiler is broken, my loop is gone". Cause: the loop's result was never used. How to find it: disassemble main. Fix: use the result (print it), and see the forensic lab.
    •
