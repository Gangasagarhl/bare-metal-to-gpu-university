Story hook

Every evening at the restaurant, the same regular, Mr Haddad, sits at table seven. When the waiter brings him the menu, the kitchen already knows: grilled vegetables, every time. So the grill cook starts the vegetables the moment Mr Haddad sits down, long before the waiter comes back with the order. On most evenings the plate is ready almost as soon as the order arrives.

Once a month, Mr Haddad surprises everyone and orders soup. The half-grilled vegetables go to the staff meal, and the soup is started late. Nobody minds: one wasted start a month is a small price for being early on all the other evenings.

But when a new guest sits at table seven, a guest who orders something different each time, the grill cook's habit backfires every other evening. The kitchen learns to stop guessing for that table. A processor faces the same choice at every branch, millions of times a second. This chapter is about how it guesses, how it learns, and how to tell from evidence when guessing is going wrong.

What you will be able to do

  • Explain why a pipeline must guess the outcome of a branch, and what a wrong guess costs.
  • Simulate static and dynamic predictors (always not taken, always taken, 1-bit, 2-bit saturating counter) on a branch outcome sequence and count mispredictions.
  • Calculate the cycles lost to mispredictions and their effect on CPI.
  • Describe the hardware tables behind prediction (branch history table, branch target buffer) at concept level.
  • Diagnose a loop that became slow because its data changed from sorted to unsorted.
Jargon box
Branch prediction
Simple words: guessing which way a branch will go before it is known, so the pipeline can keep going. Analogy: starting Mr Haddad's vegetables before he orders. Precise: a technique by which the processor chooses the next fetch address after a branch before the branch is resolved, and recovers (flushes) if the guess was wrong. D1 D2
Misprediction penalty
Simple words: the cycles thrown away when a guess is wrong. Analogy: the half-grilled vegetables plus the late soup. Precise: the number of cycles lost between fetching down the wrong path and resuming at the correct one; 2 cycles for a taken branch in the model of F1-27. D1 R1
Static prediction
Simple words: a fixed guessing rule that never changes. Analogy: "always start vegetables at table seven". Precise: a prediction that does not depend on run-time history, for example always not taken, or "backward branches taken, forward branches not taken". D1 D2
Dynamic prediction
Simple words: guessing based on what the branch did recently. Analogy: the cook remembering what table seven ordered last time. Precise: prediction using state updated at run time with each branch's actual outcome. D1
2-bit saturating counter
Simple words: a tiny counter from 0 to 3 that moves up when the branch is taken and down when it is not; 2 and 3 mean "guess taken". Analogy: the cook changes the habit only after being surprised twice in a row. Precise: a predictor state machine with four states (strongly/weakly not taken, weakly/strongly taken) that must mispredict twice in a row to change its prediction from a strong state. D1 D2
Branch history table (BHT)
Simple words: a small memory of predictors, one slot per branch (roughly). Analogy: a notebook with one line per table: "usually vegetables", "unpredictable". Precise: a table of prediction state (for example 2-bit counters) indexed by low-order bits of the branch's address; different branches can share an entry (aliasing). D1 D2
Branch target buffer (BTB)
Simple words: a memory that remembers where a branch jumped to last time. Analogy: knowing not only that table seven orders, but which dish. Precise: a cache indexed by the fetch address that supplies a predicted target address, so that a predicted-taken branch can be followed in the fetch stage before decoding. D2
Speculative execution
Simple words: doing work before knowing it is needed, and undoing it if not. Analogy: cooking for an order that has not arrived yet. Precise: executing instructions down a predicted path before the prediction is confirmed, without allowing them to change architectural state until it is (F1-29). D2

Layer 1 — the kid explanation

A branch is a fork in the road: "if this is true, go there; otherwise carry on". In a pipeline, the next instructions must be fetched before the branch has been worked out. So the processor has to guess which way the fork goes.

If the guess is right, nothing is lost. If it is wrong, the instructions started on the wrong road are thrown away, and the right ones are started late. That costs a few clock ticks each time.

The simplest guess never changes: for example "always carry on". Better guessers remember. A branch at the end of a loop jumps back almost every time, so "it jumped last time, it will jump again" is usually right. An even better guesser waits for two surprises in a row before changing its mind, so one odd case, like the loop's last turn, does not fool it twice.

Guessing only works when there is a pattern. If a branch depends on data that looks random, no memory helps, and the processor loses time on about half of those branches. Sometimes the fix is in the data, sometimes in the code.

Layer 2 — the student explanation

What prediction must achieve

In the five-stage model, a branch is resolved at the end of EX; the two instructions fetched behind it are flushed if the fetch went the wrong way, costing 2 cycles. R1 With the model's fixed rule "predict not taken", every taken branch is a misprediction. The cost in cycles is mispredictions × penalty, and the CPI contribution is that divided by the instruction count. D1 For the reordered sum loop of F1-27: 4 taken branches × 2 = 8 cycles, so 42 cycles in total; with a perfect predictor, 34 cycles (R1). The gap grows with the penalty, and longer pipelines resolve branches later, so better prediction matters more as pipelines get deeper. D2 R1

Static prediction

Static schemes need no memory. "Always not taken" is free to implement: keep fetching in order. "Always taken" needs the target address early. "Backward taken, forward not taken" uses the sign of the branch offset: loops branch backwards and are usually taken. D1 D2 On a loop branch that is taken three times and then not taken (Listing 1's pattern), "always taken" is right 30 of 40 times and "always not taken" only 10 of 40 times. R1

Dynamic prediction: 1-bit and 2-bit

A 1-bit predictor remembers the last outcome and predicts it again. On a loop it mispredicts twice per loop execution: on the exit (it predicted taken) and on the first iteration of the next execution (it remembers the exit). D1 The real run agrees: 20 mispredictions out of 40, pattern X..XX..XX..X. R1

A 2-bit saturating counter (Figure 1) changes its prediction only after two consecutive surprises from a strong state. On the same loop it mispredicts once per loop execution, on the exit. D1 D2 The run shows 12 mispredictions: one per execution for ten executions, plus two at the start while the counter warms up from "strongly not taken". R1 Over this short run "always taken" (10) still beats it, because the warm-up is a larger share of 40 branches; over a long run the counter converges to one miss per loop exit, the same as "always taken" on this pattern, while also adapting to branches that are mostly not taken, which "always taken" cannot.

Data-dependent branches

Some branches depend on data: if (value >= 128). If the data are sorted, the outcomes form long runs (N…N then T…T) and any dynamic predictor is nearly perfect. If the same values arrive in random order, the outcomes look random and a 2-bit counter is right only about as often as chance allows. The forensic lab measures exactly this with the same 64 values: 2 mispredictions sorted, 34 unsorted. R2 Two remedies exist: change the data order, or remove the branch. Compilers can turn a simple if into a conditional select instruction with no branch at all; the real x86-64 and ARM64 output in F1-31 does this for maxOf (cmovge, csel), while the RISC-V output in the same lab uses a branch. R3

Layer 3 — the engineer's depth

  • Tables and aliasing. Real predictors keep many counters in a branch history table indexed by low bits of the branch address. Two branches with the same low bits share a counter and can disturb each other (aliasing). D1 D2
  • Correlation. The outcome of one branch often depends on recent outcomes of others (if (x > 0) …; if (x > 5) …). Correlating or two-level predictors index their counters with a global history register of recent outcomes, combined with address bits; tournament predictors choose between a local and a global predictor per branch. D2
  • Targets. Predicting "taken" is useless without the target. A branch target buffer, looked up with the fetch address, supplies it in IF. Function returns are predicted with a return address stack, because one return instruction goes back to many call sites. D2
  • Recovery. Instructions fetched after a predicted branch must not change registers or memory until the prediction is confirmed. In the five-stage pipeline they cannot reach WB before the branch resolves in EX, so flushing is enough; in out-of-order machines (F1-29) a reorder buffer holds speculative results. D2

How the hardware actually does it

Each 2-bit counter is two flip-flops and a little logic: an incrementer and decrementer that saturate, exactly the state machine of Figure 1 (F1-19). A branch history table is a small memory array of such counters, read in the fetch stage with bits of the PC and written when the branch resolves (F1-20). D1 D2 Prediction happens in IF, before the instruction is even decoded, so the hardware must find out "is this a branch, and where does it go?" from tables looked up with the address alone; that is the BTB's job. When the branch resolves and disagrees, the flush logic of F1-27 cancels the younger instructions and the PC is loaded with the correct address. D2

Where the analogy breaks


    

  • A cook guesses per guest; a predictor guesses per table entry. Entries are chosen by address bits, so two unrelated branches can share one "notebook line" and confuse each other (aliasing). D1
    • 

  • Wasted vegetables are visible; wasted instructions must be invisible. A wrongly started instruction may never change registers or memory. The hardware guarantees that the architectural result is the same as without guessing; only time is lost. D2
    • 

  • A cook can ask the guest; the processor cannot ask the program. The only information is the address and the history of outcomes. That is why rearranging data or code can matter more than a cleverer predictor (forensic lab).
    • 




Common mistakes and debugging


    

  • Symptom: a 2-bit trace by hand differs from the program. Cause: letting the counter go beyond 0 or 3. How to find it: check each state stays in 0–3. Fix: saturate.
    • 

  • Symptom: "the 2-bit counter is worse than always-taken, so it is useless". Cause: judging from a short run that includes warm-up. How to find it: count mispredictions per loop execution after the first. Fix: compare steady states, and remember branches that are mostly not taken.
    • 

  • Symptom: blaming the predictor for a slow loop whose branch is perfectly regular. Cause: the cost is elsewhere (for example load-use stalls). How to find it: use the identity of F1-27 to split stalls from branch cycles. Fix: fix the larger term first.
    • 

  • Symptom: confusing "taken" with "true". Cause: compilers often invert conditions; a C++ if whose condition is true may compile to a branch that is not taken. How to find it: read the assembly (F1-31). Fix: reason about the branch instruction, not the source line.
    •

Summary


    

  • A pipeline fetches before branches resolve, so it must predict; wrong guesses cost the misprediction penalty.
    • 

  • Static predictors use fixed rules; dynamic predictors learn from each branch's history.
    • 

  • A 1-bit predictor misses twice per loop execution; a 2-bit saturating counter misses once in steady state.
    • 

  • In the model, perfect prediction would cut the reordered sum loop from 42 to 34 cycles.
    • 

  • Data-dependent branches are predictable only if the data have patterns: 2 versus 34 mispredictions for the same 64 values, sorted versus unsorted.
    • 

  • Branch-free code (conditional select) avoids the problem for simple cases.
    • 

  • Real predictors use tables, histories and target buffers; their details come only from vendor documents and measurement.

Forensic lab answer key


Root cause. The same 64 values (37 below 128 on both days: the first output line) arrive sorted yesterday and unsorted today. Sorted, the outcomes are 37 N then 27 T: the 2-bit counter misses only twice, when it switches at the boundary. Unsorted, the outcomes alternate irregularly (TNNTNTNNTTTN…), the counter keeps being pushed between states, and it misses 34 of 64. At 2 cycles each that is 68 lost cycles versus 4.


Evidence. "64 values, 37 of them below 128 (the same values on both days)" rules out more work; "mispredictions 2 of 64" versus "34 of 64"; the outcome strings show long runs versus short runs.


Fix. Data: sort upstream again (if sorting costs less than the misses, which must be measured). Code: remove the branch, for example count += (value >= 128);, which compilers can turn into a compare-and-set or conditional select without a branch; verify by reading the assembly (F1-31) and re-measuring.


How the evidence was made. The Lab Engineer generated 64 values with a fixed linear congruential generator, sorted a copy with insertion sort, and ran the same 2-bit counter on both. The "slowdown" is the model's misprediction count, not a time measured on hardware.


Wrong answers and why. "There are more values today": the count line says otherwise. "The predictor is broken": it is nearly perfect yesterday. Prevention: treat data order as part of the performance contract; benchmark with realistic data orders before changing them.
