Story hook

The restaurant has grown. On busy nights one cook at each station is not enough, so Amina hires a second grill cook and a second sauce cook. Now two tickets can move through the stations side by side. On the first busy night it works beautifully for a table of eight ordering eight separate salads. Then a table orders a soup that needs a stock, which needs roasted bones, which need the oven first. The second cooks stand around: every step waits for the one before it.

So Amina changes the rule. Cooks no longer take tickets strictly in order. They look along the rail and start any dish whose ingredients are ready, while the soup's long chain simmers. At the pass, though, Amina still sends plates out in ticket order, so the guests never notice the shuffle in the kitchen.

Modern processors do both of these things: they have several "cooks" per stage, and they work on whatever is ready. This chapter explains the ideas, measures them in a small model, and then shows them in a real program on the build machine, where the same additions run faster when written with four running sums instead of one.

What you will be able to do

  • Explain superscalar issue and out-of-order execution, and why both are limited by dependences between instructions.
  • Find the dependency chains in a short instruction sequence and estimate its best possible cycle count.
  • Calculate IPC (instructions per cycle) from a model run and compare machines.
  • Describe register renaming, the reorder buffer and in-order commit at concept level.
  • Diagnose a real loop whose speed is limited by one dependency chain, using its disassembly.
Jargon box
Superscalar
Simple words: a processor that can start more than one instruction in the same clock cycle. Analogy: two grill cooks working side by side. Precise: a processor that issues several instructions per cycle to several execution units; the maximum number is its issue width. D1 D2
Issue width
Simple words: how many instructions can start per cycle at most. Analogy: how many cooks stand at the station. Precise: the maximum number of instructions the issue logic can send to execution units in one cycle. D2
IPC (instructions per cycle)
Simple words: how many instructions finish per clock tick, on average. Analogy: plates out per bell. Precise: instructions completed divided by cycles; the reciprocal of CPI (F1-26). Above 1 is possible only on a superscalar processor. D1
Instruction-level parallelism (ILP)
Simple words: how many instructions in a program could run at the same time because they do not need each other's results. Analogy: eight separate salads versus one soup chain. Precise: the potential overlap among instructions of a single thread, limited by data dependences, control dependences and resources. D2
Dependency chain
Simple words: a line of instructions where each one needs the result of the one before. Analogy: bones → stock → soup. Precise: a path in the data-dependence graph; the longest path (sum of latencies) bounds the run time from below, however many units there are. D2
Out-of-order execution
Simple words: running instructions as soon as their inputs are ready, not strictly in program order. Analogy: cooks starting any dish whose ingredients are ready. Precise: dynamic scheduling in which instructions wait in a window (reservation stations or an issue queue) and are dispatched when their operands are available, while results are committed in program order. D1 D2
Register renaming
Simple words: giving each new result its own hidden register, so instructions that only reuse a register name stop blocking each other. Analogy: a fresh labelled pot per ticket instead of everyone sharing "pot 10". Precise: mapping architectural registers to a larger set of physical registers at decode, which removes write-after-read and write-after-write (name) dependences and leaves only true read-after-write dependences. D2
Reorder buffer (ROB)
Simple words: a queue that remembers the program order so results can be made official in that order. Analogy: Amina's ticket rail at the pass: plates leave in ticket order, whenever they were cooked. Precise: a circular buffer of in-flight instructions in program order; an instruction commits (updates architectural state) only when it reaches the head and has completed, which gives precise exceptions and lets mispredicted work be discarded. D2

Layer 1 — the kid explanation

A faster processor can try two tricks. The first is to do two or more instructions at the same moment, like two cooks at one station. The second is to not wait in line: if the next instruction is stuck waiting for something, start a later one that is ready.

Both tricks only help when instructions do not need each other. If every step needs the answer of the step before, extra cooks stand idle. Ten people cannot boil one egg faster.

So the shape of a program matters. Adding up a list into one total makes a long chain: each addition waits for the last. Adding into four separate totals and combining them at the end makes four short chains, and the processor can work on all four at once. The answer is the same; the speed is not.

The processor keeps a strict list of the program's order, and only makes results official in that order. That way, even though the work inside is shuffled, the program sees exactly what it asked for.

Layer 2 — the student explanation

From one instruction per cycle to several

The pipeline of F1-26 can at best finish one instruction per cycle: CPI 1, IPC 1. A superscalar processor fetches, decodes and issues several instructions per cycle, with several execution units. D1 D2 In Listing 1, sixteen independent additions (sequence A) take 16 cycles on a 1-wide machine and 8 cycles on a 2-wide one: IPC 2.00. R1 More width costs more hardware: more register file ports, more forwarding paths, and dependence checks between every pair of instructions issued together. D2

Dependences set the limit

Sequence B loads eight values and adds each into one running sum. The model gives loads and floating-point adds 3 cycles of latency. The eight additions form one chain of 8 × 3 = 24 cycles; with the first load, 27 cycles is the best any machine can do. The model agrees: 27 cycles on the 2-wide machine, in order or out of order. R1 Width does not help a chain. This is the most important idea in the chapter: the longest dependency chain bounds the time. D2

In order versus out of order

Sequence C has two chains (Figure 1). A 2-wide in-order machine still takes 30 cycles, because it must stop at the first instruction that is not ready, even when later instructions could go. An out-of-order machine with a window of 8 instructions takes 18 cycles: it issues loads and the other chain's additions while one chain waits. R1 Out-of-order execution finds the parallelism that the code's shape allows; it cannot invent parallelism that is not there (B stays at 27). D2

Sequence D, with four sums, takes 20 cycles out of order, not fewer than C. R1 Once the chains are short enough, another limit binds: only 2 instructions issue per cycle, and D has 19 instructions, two more combining additions than C. Every speed-up runs into the next bottleneck.

Keeping the program's meaning

Instructions may execute out of order, but the program must see results as if they ran in order. The reorder buffer holds instructions in program order; each one commits, making its result official, only when it reaches the head and has finished. D2 If an older instruction faults, or a branch was mispredicted (F1-28), everything younger in the buffer is discarded. This is how speculative execution stays invisible to the program, apart from time. D2

Layer 3 — the engineer's depth

  • Name dependences and renaming. Listing 1's out-of-order model refuses to issue an instruction that would overwrite a register an older, waiting instruction still needs (lines 34–42). Those write-after-read and write-after-write conflicts are about names, not data. Real out-of-order cores rename architectural registers onto a larger physical register file, so only true read-after-write dependences remain. D2
  • The pieces. A typical textbook out-of-order core has: a front end (fetch with branch prediction, decode, rename); an issue queue or reservation stations, where instructions wait for operands; execution units; a result bus that wakes up waiting instructions; and the reorder buffer for in-order commit. D2
  • Memory ordering. Loads and stores also need ordering checks: a load may not take a value from memory if an older store to the same address has not happened yet. Load/store queues track this. D2
  • Limits. Window size, issue width, number of units of each kind, branch mispredictions and cache misses (F1-33) all cap IPC. Static alternatives exist: VLIW machines leave scheduling to the compiler. D1 D2
  • Floating point and reordering. Floating-point addition is not associative under rounding, so a compiler may not turn one running sum into four on its own unless told that reassociation is allowed. The real disassembly below shows GCC 13.3.0 at -O2 kept the single chain in sumOne. D3 R3

How the hardware actually does it

Everything here is built from the registers, counters and memory arrays of F1-17 and F1-20. The rename table is a small register file indexed by architectural register number whose entries are physical register numbers; a free list hands out unused physical registers. D2 Each waiting instruction in the issue queue stores the tags of the physical registers it needs; when a unit finishes, it broadcasts its tag, and comparators in every queue entry mark matching operands ready. That broadcast-and-compare logic grows with width × window size, which is one reason real windows and widths are finite. D2 The reorder buffer is a circular queue with head and tail pointers, written at rename and read at commit (F1-17 counters). None of this changes the ISA: the same U16 or x86-64 program runs unchanged, faster or slower (F1-23).

Worked example

Task. Estimate the best cycle count of sequence C (two sums) by hand, then compare with the model.

  1. Chains. Each sum receives four additions: chain length 4 × 3 = 12 cycles. The final combining addition adds 3: 15 cycles of chain after the first value is available.
  2. First load. The first addition cannot start before its load finishes: 3 cycles. Lower bound from dependences: about 3 + 15 = 18 cycles.
  3. Issue limit. 17 instructions at 2 per cycle need at least 9 cycles to issue: not binding here.
  4. Model. The out-of-order run gives 18 cycles, IPC 0.94: the machine reached the dependence bound. R1
  5. In order. The 2-wide in-order run gives 30 cycles: it waits at every addition whose load or earlier addition is not done, even when the other chain could proceed. R1

The same reasoning for B gives 3 + 8 × 3 = 27 cycles, which is what every 2-wide machine in the model achieved. R1

Where the analogy breaks


    

  • Cooks can taste and improvise; units cannot. Each execution unit does one kind of operation with a fixed latency; the scheduling is mechanical, done every cycle by comparators. D2
    • 

  • A kitchen can always hire more cooks. Hardware cost grows faster than width: every extra issue slot needs more register ports, more bypass paths and more comparisons. D2
    • 

  • Guests never see a dish thrown away; programs never see a squashed instruction's result, but they can see its timing. That timing side channel of speculative execution is a security topic beyond this course.
    • 




Common mistakes and debugging


    

  • Symptom: expecting a 4-wide processor to run any loop 4 times faster. Cause: ignoring dependency chains. How to find it: draw the graph; find the longest chain. Fix: shorten chains (more accumulators, tree reductions) where correctness allows.
    • 

  • Symptom: splitting a floating-point sum changes the last digits. Cause: rounding depends on the order of additions. How to find it: compare with values whose sums are exact (Listing 2 uses halves for this reason). Fix: decide whether the change is acceptable; document it.
    • 

  • Symptom: a model run shows no gain from out-of-order execution. Cause: the window is too small, or all instructions are in one chain. How to find it: vary window on line 94. Fix: none needed: that is the lesson.
    • 

  • Symptom: a timing comparison flips between runs. Cause: noise on a shared machine. How to find it: repeat; use medians, as Listing 2 does. Fix: report the spread and the machine, never a single number (AH-23).
    •

Summary


    

  • Superscalar processors issue several instructions per cycle; IPC can exceed 1.
    • 

  • Out-of-order processors issue whatever is ready within a window, and commit in program order through a reorder buffer.
    • 

  • Register renaming removes name dependences; true read-after-write dependences remain.
    • 

  • The longest dependency chain bounds the time: in the model, one sum takes 27 cycles on any 2-wide machine; two sums take 18 out of order.
    • 

  • Once chains are short, other limits bind: four sums gave 20 cycles, not fewer.
    • 

  • On the build machine, four running sums ran faster than one in the logged run, and the disassembly shows why: one xmm0 chain versus four registers.
    • 

  • Real widths, windows and latencies must come from vendor documents and measurement.

Root cause. In sumOne, the hot loop (addresses 14c0–14d2) is two addsd xmm0, … per iteration: every addition reads and writes xmm0, so each must wait for the previous one's latency. The compiler unrolled by two but kept one chain, because reassociating floating-point additions would change rounding. In sumFour, the hot loop (1528–154a) adds into xmm0, xmm2, xmm1 and xmm3: four independent chains that an out-of-order core can overlap. Instruction count per element is similar, so "fewer instructions" does not explain it. R3


Ruling out memory. Both versions read the same 8 MB array in the same order, once per repetition; memory traffic is the same. A stronger test: rerun with a smaller array that fits in cache (F1-33); if the gap persists, the chain is the cause.
