Story hook

The restaurant opens a second kitchen line. Now there are two head chefs, each with their own stations and cooks, sharing one pantry. On the pantry door hangs a whiteboard: "lemons left: 12". The rule is simple: when you take a lemon, read the number, subtract one, write the new number.

One evening both chefs take a lemon at the same moment. Both read 12. Both write 11. Two lemons are gone, but the board says one. By the end of the night the board claims eight lemons, and the drawer is empty. Nobody broke a rule; the rule was not enough for two people at once.

Your computer has several cores: several "head chefs" sharing one memory. This chapter shows how a program uses them, why "add one to a shared number" goes wrong exactly like the lemon board, and how to prove it with a tool instead of hoping.

  • Calculate the speed-up limit of a partly parallel program with Amdahl's law.
  • Diagnose a data race with ThreadSanitizer.
Jargon box
Multicore processor
Simple words: one chip with several complete processors (cores) on it. Analogy: several head chefs, each with their own line, sharing a pantry. Precise: a chip containing two or more cores, each with its own pipeline and registers (and usually its own first-level caches), that share memory and usually some caches. D1 D2
Thread
Simple words: one running sequence of instructions inside a program; a program can have several. Analogy: one chef's list of tickets. Precise: an independent flow of control with its own registers, program counter and stack, sharing the address space of its process; the operating system schedules threads onto cores (F2-34, F3-03). D3 ch. 26
Interleaving
Simple words: one possible order in which the steps of several threads happen. Analogy: who reads the lemon board first. Precise: a total order of the memory operations of concurrent threads that respects each thread's own order; different runs can produce different interleavings. D2
Data race
Simple words: two threads touching the same memory at the same time, at least one writing, with nothing to keep them in order. Analogy: two chefs updating the lemon board at once. Precise: in C++, two conflicting accesses to the same memory location from different threads, at least one a write, not ordered by synchronisation and not both atomic; a program with a data race has undefined behaviour. D4 [intro.races]
Atomic operation
Simple words: an operation that happens all at once: no other thread can see it half done. Analogy: the pantry key: whoever holds it reads and writes the board before anyone else may. Precise: an operation on an atomic object that is indivisible with respect to other threads; for example std::atomic<long>::fetch_add, an atomic read-modify-write. D4
Cache coherence
Simple words: the hardware's way of making sure cores do not keep using old copies of a value another core changed. Analogy: when one chef changes the board, everyone else's photo of it is torn up. Precise: a protocol that keeps the private caches' copies of each memory location consistent, usually by invalidating other copies before a write; it orders accesses to one location but does not make a read-then-write sequence indivisible. D1 D2
Amdahl's law
Simple words: the part of a job that cannot be shared out limits how much faster more workers can make it. Analogy: one chef must still plate every dessert. Precise: if a fraction p of the run time can be spread perfectly over N processors, speed-up = 1 / ((1 − p) + p/N), never more than 1 / (1 − p). D1

Layer 1 — the kid explanation

For a long time, computers got faster mostly because each processor got faster. Then making one processor faster became very hard, so chip makers put several processors, called cores, on one chip instead.

Several cores only help if the work can be split. Adding up a million numbers splits well: give each core a quarter of the list, let each add its own quarter, then add the four answers.

The danger is sharing. If two cores both change the same number in memory, each does "read it, add one, write it back". If both read before either writes, one change is lost, like the lemon board.

The fix is to share less, and to share carefully. Give each core its own place to write, and when something truly must be shared, use a special instruction that does the whole "read, add, write" in one go, so no other core can sneak in between.

Layer 2 — the student explanation

Why multicore

Speeding up one core has limits you met in F1-26 to F1-29: deeper pipelines cost more per misprediction, and wider issue is limited by dependency chains. Raising the clock frequency raises power, and power turns into heat that must be removed. D1 D2 Since the mid-2000s, chip makers have used extra transistors largely to add cores instead, which moves the work of finding parallelism from the hardware to the programmer. D1 On the build container, std::thread::hardware_concurrency() printed 4. R1

The main thread waits with join; after join, the thread's writes are guaranteed visible. R1 The pattern "private work, private result, combine after join" avoids almost all sharing problems.

How an update is lost

count = count + 1 is three machine steps on a load–store machine: load, add, store (F1-23); on x86-64 too, the textbook shows it compiled to a load, an add and a store. D3 ch. 26 Listing 2 plays two cores' steps in a chosen order. In order AAABBB, memory ends at 2. In order ABABAB, both cores load 0, both compute 1, both store 1: one increment is lost. R2 The hardware did nothing wrong; every load returned the latest stored value. The problem is that the three steps are not one indivisible action. D2 D3 ch. 26

Coherence: necessary, not sufficient

Each core caches memory locally (F1-33). Without coherence, core 1 might read its own stale cached copy long after core 0 changed the value. A coherence protocol prevents that: before a core writes a cache line, the other cores' copies are invalidated, so their next read fetches the new value. D1 D2 Coherence makes every core agree on the order of writes to one location. It does not make load–add–store indivisible: the ABABAB interleaving is perfectly coherent and still loses an update. That needs atomic instructions or locks. D2

How much faster?

Amdahl's law: if a fraction p of the work can run in parallel on N cores, speed-up = 1 / ((1 − p) + p/N). D1 With p = 0.9 and N = 4: 1 / (0.1 + 0.225) ≈ 3.08. Even with infinitely many cores, at most 1 / 0.1 = 10. The serial part dominates quickly.

Layer 3 — the engineer's depth

  • Coherence protocols. Textbook protocols give each cached line a state such as Modified, Shared or Invalid (MSI, and variants such as MESI); small systems keep states consistent by snooping on a shared connection, larger ones by a directory. D1 D2 The memory chapters (F1-36) return to this with caches in full.
  • False sharing. Coherence works on whole cache lines. If two threads write different variables that sit in the same line, the line bounces between cores even though no data are shared. Listing 1's partial slots are adjacent; each thread writes its slot once, so it does not matter there, but a slot written in the inner loop would. This build did not measure the effect. D2
  • Memory consistency. Coherence concerns one location; the order in which a core's writes to different locations become visible to others is the memory consistency model, which differs between ISAs. C++ atomics with their memory orders hide those differences from portable code. D2 D4 F1-37 covers memory consistency; F2-35 and F2-38 cover data races and atomics in C++.
  • Hardware threads. Some cores run two or more threads at once, sharing one pipeline (simultaneous multithreading); the operating system then reports more "CPUs" than physical cores. The container's count of 4 does not say which. D2
Not verified — check before relying on this

This chapter did not measure any speed-up from threads: Listing 1 is built with AddressSanitizer for checking, not for timing, and the container's 4 visible CPUs may be shared or be hardware threads. How the hardware actually does it

Each core is a complete processor of the kind built in F1-24 to F1-29, with its own register file and program counter. Each private cache keeps, next to every line, a few state bits (the coherence state) and logic that reacts to messages on the shared connection: "someone wants to write this line: invalidate yours", or "someone wants to read it: send it if yours is modified". D1 D2 An atomic read-modify-write, such as the one fetch_add compiles to, gains exclusive ownership of the line and keeps it for the whole load–add–store, so no other core's write can come between. D2 On x86-64, GCC 13.3.0 at -O2 compiled the fetch_add of Listing 1 into one instruction with the lock prefix, lock add QWORD PTR [rax],0x1 (R4, below); what that prefix guarantees is the processor vendor's statement (Intel's manual, not opened here), so this chapter claims only what the disassembly shows; you can repeat the check on your own machine with the method of F1-31. Where the analogy breaks


    

  • Chefs can see each other; cores cannot. A chef would notice the other reaching for the board. Cores have no such awareness: unless the program uses atomics or locks, nothing orders their steps.
    • 

  • The pantry is not one shelf. Real memory is reached through private and shared caches; "the board" may exist as several copies that the coherence protocol keeps consistent. D1
    • 

  • A wrong lemon count is merely wrong; a C++ data race is undefined behaviour. The compiler may assume no race exists and transform the code in ways that make results even stranger than a lost update. D4
    • 




Common mistakes and debugging


    

  • Symptom: a shared counter is sometimes too low. Cause: a data race on ++counter. How to find it: build with -fsanitize=thread and run. Fix: per-thread counters combined after join, or std::atomic.
    • 

  • Symptom: the program prints the right answer, so "there is no race". Cause: races depend on timing; one good run proves nothing (the ThreadSanitizer run below printed 200000 and still reported a race). How to find it: use a race detector, not output. Fix: remove the race.
    • 

  • Symptom: volatile int counter still loses updates. Cause: volatile does not make operations atomic or ordered between threads. How to find it: ThreadSanitizer. Fix: std::atomic. D4
    • 

  • Symptom: eight threads are slower than four. Cause: more threads than hardware threads, contention on shared data, or false sharing. How to find it: measure with different counts, record the machine. Fix: match the count to the hardware; reduce sharing.
    • 

  • Symptom: terminate called without an active exception. Cause: a std::thread destroyed without join. Fix: join every thread (or use std::jthread).
    •

Summary


    

  • A multicore processor has several complete cores sharing memory; threads run on them.
    • 

  • Split work so each thread works on private data and writes its own result; combine after join.
    • 

  • count = count + 1 is load–add–store; interleaved on two cores, an update can be lost (ABABAB ended at 1, not 2).
    • 

  • Cache coherence keeps copies consistent but does not make read-modify-write indivisible; atomics or locks do.
    • 

  • Races depend on timing: the normal runs printed far fewer than 200,000, a different number each run, and ThreadSanitizer reported the race even in a run that printed the right total.
    • 

  • Amdahl's law: the serial fraction limits speed-up.
