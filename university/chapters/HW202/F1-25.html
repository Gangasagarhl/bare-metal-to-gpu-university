Story hook

At the restaurant, one person never cooks. Amina stands at the pass, between the ticket rail and the stations. She takes each ticket, reads the action word, and calls out: "Grill, on! Pantry, nothing for this one! Shelf, put it on board three!" She does not touch the food. She only turns each ticket into a set of short commands for the stations, and she does it the same way every time for the same action word.

One evening a new expediter takes over. He has a small mistake in his habits: on "STORE" tickets, he also shouts "put it on a board!". The pantry gets the right box, but a cook also drops a copy of the box's shelf number on a cutting board, on top of the ingredient that was there. Nobody notices until a dish comes out wrong much later. In this chapter you will build Amina for U16, test her against a table, and then find the new expediter's mistake.

What you will be able to do

  • Explain what a control unit does and why it is combinational logic in a single-cycle processor.
  • Derive the control signals of any U16 instruction from what the instruction must do.
  • Read and simulate a control unit written in Verilog, and compare it with a reference table automatically.
  • Compare hardwired and microprogrammed control at concept level.
  • Diagnose a faulty control unit from a test-bench table and predict the program bug it causes.
Jargon box
Control unit
Simple words: the part of the processor that reads the instruction's command and switches the datapath to do it. Analogy: Amina at the pass, calling out what each station must do for this ticket. Precise: logic that maps the instruction's opcode (and sometimes other fields) to the control signals that drive multiplexer selects, write enables and ALU operation inputs. D1 D2
Control signal
Simple words: a wire that tells one part of the datapath what to do right now. Analogy: one call such as "pantry, nothing for this one". Precise: a one-bit (or few-bit) signal such as RegWrite or AluSrcImm that selects a multiplexer input, enables a write or selects an ALU operation. D1
Write enable
Simple words: a signal that allows a storage element to change at the next clock edge. Analogy: permission to put something on a board. Precise: an input of a register, register file or memory that must be 1 for a write to happen at the clock edge; RegWrite and MemWrite are write enables. D2
Hardwired control
Simple words: control built directly as logic gates. Analogy: an expediter who knows every call by heart. Precise: a control unit implemented as combinational logic (or a finite state machine) generated from the signal table. D1
Microprogrammed control
Simple words: control that reads its calls from a small built-in table of steps. Analogy: an expediter who looks up each action word in a binder of call sequences. Precise: a control unit in which each instruction selects a sequence of microinstructions stored in a control memory; each microinstruction's bits are the control signals for one step. D1 D4
Test bench
Simple words: a piece of Verilog that tests another piece by giving it inputs and printing its outputs. Analogy: a practice evening where every action word is tried once. Precise: a non-synthesisable HDL module that instantiates the design under test, drives its inputs and observes its outputs in simulation (F1-21). D2 R2

The idea in pictures

Figure 1 shows the control unit as a box between the instruction's opcode and the datapath. Four wires go in; eleven control outputs (one of them three bits wide) come out. A small piece of extra logic combines two of them with the ALU's zero test to choose the next PC.

Layer 1 — the kid explanation

The datapath from the last chapter has many little switches: which value goes into the ALU, whether memory is read, whether a register is written. Something has to set all those switches for every instruction. That something is the control unit.

The control unit looks only at the command part of the instruction, the opcode. For each opcode it has a fixed answer: "for an add, write a register, use the register value, do not touch memory". For a store: "do not write a register, do write memory". It is like a lookup table: same command in, same switch settings out, every time.

Because it is a fixed table, it can be built from ordinary logic gates. You can also write it in a hardware language like Verilog, test every input, and compare the result with the table you wrote by hand. If one entry is wrong, programs will go wrong in strange ways, often far from where the mistake is.

Layer 2 — the student explanation

Deriving the signals

Each control signal answers one yes/no question about the instruction, and the answer follows from the instruction's meaning. D1 D2 For U16 (Listing 1, whose output is the reference table):

  • RegWrite — does the instruction change a register? Yes for add, sub, and, or, slt, addi, lw; no for sw, branches, out, halt.
  • AluSrcImm — is the ALU's second input the immediate? Yes for addi, lw, sw (address = register + offset).
  • ReadRdAsB — does read port B need the register named in the rd field? Yes for sw (the value to store), beq/bne (the second register to compare) and out.
  • MemRead / MemWrite — only lw reads data memory; only sw writes it.
  • MemToReg — does the written value come from memory? Only for lw.
  • ALU op — sub for sub, beq and bne (equality is "difference is zero"), the named operation for and/or/slt, and add otherwise.
  • BranchEq / BranchNe / Out / Halt — one instruction each (and Halt for the unused opcodes).

R1 In the single-cycle design these outputs depend only on the current opcode, never on earlier instructions, so the control unit is combinational logic: a truth table with 4 inputs and 12 output bits. D2

Values that do not matter

For some instructions a signal's value has no effect. When RegWrite is 0, MemToReg could be 0 or 1: nothing is written anyway. Textbooks mark such entries as "don't care" (X), which lets a logic designer pick whichever value makes the circuit smaller. D1 D2 U16's reference table writes 0 in those places, so the C++ table and the Verilog can be compared exactly; the Watch out box below explains why write enables can never be "don't care".

Watch out

Write enables (RegWrite, MemWrite) and anything that changes the PC are never "don't care". A wrong 1 there changes state that a later instruction will read. The forensic lab is this mistake.

Layer 3 — the engineer's depth

  • Two-level decoding. Textbook MIPS and RISC-V designs split control in two: a main decoder produces a short "ALU op class" from the opcode, and a separate ALU decoder combines that class with function fields of R-type instructions to pick the exact ALU operation. This keeps each decoder small. U16 has no function field, so one level is enough. D1 D2
  • From table to gates. Synthesis tools turn the table into gates automatically. Yosys turned Listing 2 into 30 generic cells (AND, OR, NOT, multiplexer and similar) in this build. That number belongs to yosys's generic cell library and this exact Verilog, not to any real chip. R3
  • Hardwired versus microprogrammed. A hardwired unit is the gate circuit itself. A microprogrammed unit stores, for each instruction, a sequence of control words in a small memory and steps through them; it was attractive for complex instructions that need many steps, because changing behaviour meant changing the stored table, not the gates. Single-cycle and pipelined designs for simple ISAs such as U16 use hardwired control. D1 D4
  • Control in a pipeline. In F1-26 the signals are computed in ID and then travel with the instruction through pipeline registers, so each stage uses the signals of the instruction currently in it, not of the newest one. D1
Not verified — check before relying on this

Whether any particular commercial processor uses microcode, and for which instructions, is not stated here: no vendor manual was opened in the build or in the verification pass, and the textbook description of microprogrammed control (D1, D4) rests on those books as named, their text not having been opened. Check the vendor's own architecture or optimisation manual for the named product before making such a claim (for x86-64: the Intel 64 and IA-32 Architectures Software Developer's Manual and the vendor's optimisation reference manual).

How the hardware actually does it

The four opcode bits fan out to a small network of gates. One way to picture it: a 4-to-16 decoder (F1-12) produces one line per opcode, and each control output is an OR of the lines of the opcodes that need it; RegWrite, for example, is the OR of the lines for opcodes 1–7. Synthesis then simplifies that network. D2 D3 The outputs reach the datapath's multiplexer select inputs and write enables. Because control is combinational, its delay adds to the critical path of F1-24: the multiplexers cannot settle before their select signals do.

Worked example

Task. Derive the control row for sw rd, imm(rs) and check it against the real table.

  1. What does sw do? memory[R[rs] + imm] = R[rd]. No register changes.
  2. RegWrite = 0 (no register changes).
  3. AluSrcImm = 1 (the ALU adds the immediate to compute the address); ALU op = add.
  4. ReadRdAsB = 1 (the value to store is in the register named by rd, read through port B).
  5. MemRead = 0, MemWrite = 1.
  6. MemToReg = 0 (don't care, since RegWrite = 0; the reference writes 0).
  7. BranchEq = BranchNe = Out = Halt = 0.

Row 8 of the real output reads "8 sw 0 1 1 0 1 0 0 0 0 0 add": identical. R1

Where the analogy breaks


    

  • Amina thinks; the control unit does not. An expediter can notice an odd ticket and ask. The control unit maps every 4-bit pattern to outputs, including unused ones; there is no judgement, only the table. R1
    • 

  • Calls happen one after another; control signals are all valid at once. Amina calls stations in turn. All control outputs are produced in parallel and must be stable before the clock edge. D2
    • 

  • A wrong call is usually noticed at once in a kitchen. A wrong control bit often produces no visible symptom until a later instruction reads the damaged state (forensic lab).
    • 




Common mistakes and debugging


    

  • Symptom: synthesis warns about an inferred latch, or simulation shows outputs keeping old values. Cause: some case branch does not assign every output. How to find it: look for outputs not set in a branch. Fix: assign defaults at the top of the always block (lines 12–14).
    • 

  • Symptom: a register changes after a store. Cause: RegWrite = 1 for sw. How to find it: diff the test-bench table against the reference. Fix: correct the row. (Forensic lab.)
    • 

  • Symptom: branches go the wrong way. Cause: ALU op for branches set to add instead of sub, so the zero test is wrong. How to find it: the ALU column for beq/bne rows. Fix: sub.
    • 

  • Symptom: diff reports every line different. Cause: column order or formatting differs, not the logic. How to find it: compare one line by eye. Fix: make the test bench print exactly the reference layout.
    •

Forensic lab answer key


Root cause. In control_bug.v line 23, the sw row sets reg_write = 1. A store therefore also writes register rd. With MemToReg = 0 the written value is the ALU result, which for sw is the address (rs + imm). So sw r3, 0(r1) stores r3 correctly in memory, then overwrites r3 with the address. The next additions start from that address: "the total jumps".


Evidence. The diff shows exactly one differing line: opcode 8, second column (RegWrite) 0 in the reference, 1 in Bo's version. Memory receives the right value (MemWrite and the data path are unchanged), which is why Bo saw a correct value in memory.


Fix. Remove reg_write = 1; from the 4'd8 line, as in Listing 2. Verify with the same diff ("no differences").


How the fault was made. The Lab Engineer copied Listing 2 and added reg_write = 1; to the sw line (and changed the header comment); run.sh generated the evidence with the same test bench.


Wrong answers and why. "The store address is wrong": AluSrcImm and ALU op for sw are unchanged, and memory holds the right value. "The add is broken": add's row matches. Prevention: run the exhaustive table comparison in continuous integration on every change to the control unit.
