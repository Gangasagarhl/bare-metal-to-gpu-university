Story hook

Yuki has recently started as a cook in a busy restaurant. On her first evening she notices something odd. The waiters never shout "make something nice with fish". They clip small tickets to a rail above the stove, and every ticket uses the same few words in the same order: an action, then where to put the result, then what to use. "GRILL 2 salmon", "PLATE 4 from-grill". The head chef reads each ticket and does exactly what it says, nothing more.

Yuki asks why the tickets are so strict. The head chef laughs. "Because then anyone can write them. The waiters, the owner, the new tablet system at the front desk. They all write the same language, and I never have to guess." Later Yuki learns that the restaurant across the street has a bigger kitchen with two stoves, but uses the very same ticket language. A waiter can move from one restaurant to the other and keep writing tickets the same way.

A processor works like that head chef. The list of words it understands, and the exact way each one is written, is called its instruction set architecture. This chapter is about that language: what is in it, how it is written as bits, and why three real families of processors chose different languages.

What you will be able to do

  • Explain what an instruction set architecture (ISA) is and why it separates software from the hardware that runs it.
  • Encode and decode instructions of the university's 16-bit teaching ISA, U16, by hand: opcode, register fields and signed immediate.
  • Write a short U16 program in assembly and in machine code, assemble it and run it.
  • Compare real x86-64, ARM64 and RISC-V machine code produced by real compilers, and point out fixed-length and variable-length encodings in it.
  • Diagnose a hand-encoded program that never stops by decoding its machine words field by field.
Jargon box
Instruction set architecture (ISA)
Simple words: the complete list of commands a processor understands, and the exact rules for writing each one. Analogy: the restaurant's ticket language that every waiter writes and the head chef reads. Precise: the interface between software and hardware: the instructions, their encodings, the registers and memory model visible to programs, and what each instruction does to that visible state. Different hardware designs can implement the same ISA. D1 D2
Instruction
Simple words: one command for the processor, such as "add these two numbers". Analogy: one ticket on the rail. Precise: one operation defined by the ISA, stored in memory as a binary pattern that the processor fetches, decodes and executes. D1
Machine code
Simple words: instructions written as the bit patterns the processor really reads. Analogy: the ticket written in the kitchen's short codes. Precise: the binary encoding of a program's instructions as defined by an ISA. D1
Assembly language
Simple words: machine code written with short words and numbers so people can read it. Analogy: the ticket read aloud: "grill two salmon". Precise: a textual form of machine instructions, one line per instruction, using mnemonics such as add and register names; an assembler translates it into machine code. D1 D3
Opcode
Simple words: the part of an instruction that says which command it is. Analogy: the action word at the start of a ticket. Precise: the field of an instruction encoding that selects the operation; in U16 it is bits 15–12. D1 R1
Register (CPU)
Simple words: a tiny, very fast storage place inside the processor that holds one value. Analogy: the chef's hands and cutting board. Precise: a named storage element that is part of the ISA's visible state; instructions name registers as sources and destinations. U16 has eight 16-bit registers, r0 to r7, and r0 always reads as 0. D1 R1 (The registers built from flip-flops in F1-17 are how hardware implements them.)
Immediate
Simple words: a small number written inside the instruction itself. Analogy: "add 2 pinches of salt": the 2 is on the ticket, not fetched from a shelf. Precise: a constant operand encoded in an instruction field; U16 stores it as a 6-bit two's-complement number, so it ranges from −32 to 31. D1 R1
Program counter (PC)
Simple words: the number that says which instruction comes next. Analogy: the clip on the ticket rail that marks the next ticket. Precise: a register holding the address of the instruction being fetched; it normally advances to the next instruction, and branches change it. D1
Assembler
Simple words: a program that turns assembly text into machine code. Analogy: the front-desk tablet that turns a spoken order into the kitchen's short codes. Precise: a translator from assembly language to machine code that also resolves labels into addresses or offsets. D3

Layer 1 — the kid explanation

A processor cannot understand English, or C++, or even "add five numbers". It understands a short, fixed list of tiny commands. Each command does one small thing: add two numbers, copy a number from memory, jump back to an earlier command. That list, together with the exact way each command is written, is the processor's language.

Think of the restaurant tickets. The head chef understands perhaps a dozen action words. A whole dinner for a big table is many tickets, each with one action. The waiter's job is to break a wish ("a birthday dinner for six") into those simple tickets. In a computer, the compiler is that waiter: it breaks your C++ into simple instructions.

Every instruction is stored as a row of bits. A few bits say which command it is; other bits say which registers to use, or hold a small number. The processor reads the bits, works out the command, and does it. Then it moves on to the next one, marked by a pointer called the program counter.

The best part of having a fixed language is freedom below it. A small, cheap processor and a huge, fast one can understand exactly the same instructions. They carry them out in different ways, like a small kitchen and a big kitchen reading the same tickets.

Layer 2 — the student explanation

What an ISA defines

An instruction set architecture is the part of a computer's design that a programmer, a compiler writer or an operating system writer must know. It defines the instructions, how each is encoded in binary, the registers that programs can name, how memory is addressed, and the effect of every instruction on that visible state. D1 D2 It deliberately leaves out how the effect is achieved: how many steps an addition takes inside, whether instructions overlap, how big the caches are. Those choices belong to the microarchitecture, the particular hardware design that implements the ISA. D1

This split is why one compiled program can run on a whole family of processors from different years: they implement the same ISA with different microarchitectures. D1 It is also why the next six chapters can build three very different U16 machines (single-cycle, pipelined, superscalar models) and run the same programs on all of them with the same answers.

U16: the university's teaching ISA

Real ISAs have hundreds of pages of rules. To learn the ideas, this course uses a tiny ISA designed for it, called U16, in the spirit of the small teaching machines in "The Elements of Computing Systems" and the MIPS and RISC-V subsets in the Patterson and Hennessy and Harris and Harris textbooks. D1 D2 D3 Everything about U16 is defined by our own code in Listing 1, so every statement about U16 in this course can be checked against a program that really ran. R1

  • Words and registers. Every instruction and every data value is 16 bits. There are eight registers, r0 to r7. Register r0 always reads 0, and writing to it has no effect; this gives programs a free constant zero. R1
  • Memory. Instructions live in an instruction memory; data lives in a separate data memory of 256 words, addressed by word number. Keeping the two apart (a "Harvard" arrangement) keeps the datapath of F1-24 simple. R1 D1
  • Load/store. Only lw (load word) and sw (store word) touch data memory. Arithmetic works only on registers. This is the load/store style used by RISC-V and ARM64; x86-64 also allows memory operands in arithmetic instructions, as you will see in the real compiler output below. D1 R3
  • Twelve instructions. add, sub, and, or, slt (set if less than) work on two registers; addi adds an immediate; lw and sw move data; beq and bne branch when two registers are equal or not equal; out sends a register to an output port; halt stops. R1

Encoding: from fields to a 16-bit word

Every U16 instruction has a 4-bit opcode in bits 15–12. R-type instructions then hold three 3-bit register numbers: the destination rd and the sources rs and rt. I-type instructions replace rt and the unused bits by a 6-bit signed immediate. Three bits are enough to name eight registers, because 23 = 8. Six bits in two's complement give the range −32 to 31 (F0-24). R1

Encoding is shifting each field into place and combining with OR; decoding is shifting back and masking, exactly the masks and shifts of F0-25. Lines 31–57 of Listing 1 do this. For example, add r3, r3, r4 has op = 1, rd = 3, rs = 3, rt = 4, so the word is (1 << 12) | (3 << 9) | (3 << 6) | (4 << 3) = 4096 + 1536 + 192 + 32 = 5856 = 0x16E0, which is what the lab run printed. R1

Branches use PC-relative offsets: bne r2, r0, loop stores the distance from the instruction after the branch to the label, not the label's address. In the sum program, the branch is at address 7 and loop is at address 3, so the offset is 3 − (7 + 1) = −5. R1 Real ISAs also use PC-relative branches, which lets code run correctly wherever it is placed in memory. D1

Layer 3 — the engineer's depth

Designing an ISA is a series of trade-offs that every later chapter will feel. D1 D2

  • Fixed versus variable length. Fixed-length instructions (U16's 16 bits; ARM64's 32 bits) make fetch and decode simple: the next instruction always starts a fixed distance away. Variable-length instructions (x86-64) can be denser but make finding instruction boundaries harder. RISC-V's base instructions are 32 bits, and an optional compressed extension adds 16-bit forms; the real RISC-V output in this chapter's lab contains both lengths. D4 D5 D6 R3
  • Field positions. U16 keeps rs in the same bits in every format, so the register file can start reading it before the opcode is fully decoded. RISC-V is designed with the same idea of keeping register fields in fixed places. D6 D2
  • Immediate width. Six bits are cheap but small: U16 needs two instructions to build the constant 50 (the forensic program of F1-27 does exactly that). Real ISAs offer wider immediates and special instructions to build large constants. D1
  • The zero register. U16's r0, like RISC-V's x0, always reads zero; it turns "copy" into add rd, rs, r0 and "unconditional branch" into beq r0, r0, label, so the ISA needs fewer opcodes. D6 D7 R1
  • Unused encodings. Opcodes 12–15 are unused in U16. Our machine treats them as halt (line 93 of Listing 1); a real ISA specifies what happens, usually an exception for an undefined instruction, which the operating system handles (F1-42). D1

What the opened documents do confirm: the RISC-V calling-convention document (D7) lists x0 as "zero", immutable; and the byte columns of R3 show 1- to 6-byte x86-64 instructions, 4-byte A64 instructions and 2- and 4-byte RISC-V instructions.

How the hardware actually does it

In hardware, decoding is wiring plus a little logic. The four opcode bits drive a decoder (F1-12) whose outputs become control signals; the three register fields go straight to the address inputs of the register file built from the registers of F1-17; the immediate bits go through a sign-extension circuit that copies bit 5 into the upper bits. D1 D2 Nothing "reads" the instruction the way you read a sentence: the bits are electrical signals that steer multiplexers and select ALU operations, all in parallel. F1-24 draws that datapath and F1-25 builds its control unit in Verilog.

Worked example

Task. Encode addi r2, r2, -1 and bne r2, r0, loop (at address 7, with loop at address 3) by hand, then decode the word 0xA43B to check.

  1. addi: fields. op = 6 (0110), rd = 2 (010), rs = 2 (010), imm = −1.
  2. Immediate in 6-bit two's complement. +1 is 000001; invert to 111110; add 1 to get 111111. So −1 = 111111.
  3. Join the fields. 0110 010 010 111111 → regroup into nibbles: 0110 0100 1011 1111 = 0x64BF.
  4. bne: fields. op = 10 (1010), rd = 2 (010), rs = 0 (000), offset = 3 − (7 + 1) = −5.
  5. −5 in 6 bits. +5 = 000101; invert: 111010; add 1: 111011.
  6. Join. 1010 010 000 111011 → 1010 0100 0011 1011 = 0xA43B.
  7. Decode check. 0xA43B: top nibble 1010 = 10 = bne; next three bits 010 = r2; next 000 = r0; last six 111011: bit 5 is 1, so the value is 59 − 64 = −5. Target = 7 + 1 + (−5) = 3. Correct.

Both words match the listing printed by the real run of Listing 2 (addresses 6 and 7). R1

Where the analogy breaks


    

  • A chef understands meaning; a processor only matches bits. A head chef would notice a ticket that says "grill 2 ice cream" and ask. A processor decodes 0x6481 as addi r2, r2, 1 without any idea that you meant −1. The forensic lab is exactly this failure. R2
    • 

  • A ticket language can grow overnight; an ISA cannot change freely. Old programs depend on every encoding, so ISAs are extended (new opcodes, new optional extensions) rather than changed, and unused encodings are reserved for that. D1 D6
    • 

  • "Different kitchens, same tickets" hides a cost. Two processors with the same ISA give the same results but not the same speed; how fast a program runs depends on the microarchitecture, which is the subject of the rest of this course. D1
    • 




Common mistakes and debugging


    

  • Symptom: a loop never ends. Cause: a negative immediate encoded as positive (for example 000001 instead of 111111). How to find it: disassemble the words and compare each with the intended instruction. Fix: encode negatives in two's complement in the field width. (Forensic lab, R2.)
    • 

  • Symptom: a branch lands one instruction off. Cause: offset counted from the branch itself instead of from the next instruction. How to find it: compute target = address + 1 + offset by hand. Fix: offset = target − (address + 1).
    • 

  • Symptom: the assembler reports "cannot assemble" for addi r1, r0, 40. Cause: 40 does not fit in −32…31. How to find it: check immediate ranges first. Fix: build the constant in two steps (addi r1, r0, 31 then addi r1, r1, 9). Note that the shown assembler masks the value to 6 bits silently in encodeI; the extension task asks you to add a range check.
    • 

  • Symptom: a result that should be stored is always 0. Cause: writing to r0. How to find it: look for rd = r0 in the disassembly. Fix: use another register (see the forensic lab of F1-24).
    •

Summary


    

  • An ISA is the contract between software and hardware: instructions, encodings, registers, memory and effects.
    • 

  • The microarchitecture is how one design implements the ISA; many designs can share one ISA.
    • 

  • U16 has 16-bit instructions with a 4-bit opcode, 3-bit register fields and a 6-bit signed immediate.
    • 

  • Encoding is shifting fields into place; decoding is shifting and masking; immediates use two's complement.
    • 

  • Branches store PC-relative offsets: target = address + 1 + offset in U16.
    • 

  • Real compiler output shows variable-length x86-64, fixed 4-byte ARM64, and mixed 2- and 4-byte RISC-V encodings.
    • 

  • The processor decodes bits, not intentions: a wrong bit is a different, valid instruction.

Forensic lab answer key


Root cause. Address 4 holds 0x6481, which decodes as addi r2, r2, 1 (immediate field 000001 = +1), while the comment says −1. The counter goes 7, 8, 9, …, so bne r2, r0 keeps branching. It would only reach 0 after wrapping around 16 bits, tens of thousands of iterations later; the 10,000-step limit stops it first.


Evidence. The listing line "4  0x6481  0110 010 010 000001  addi r2, r2, 1" against the comment "addi r2, r2, -1"; "stopped: step limit of 10000 reached"; no "out:" line.


Fix. −1 in six bits is 111111, so the word is 0110 0100 1011 1111 = 0x64BF. With that word the same program is cpu.in of F1-24, whose real run outputs 42.


How the fault was made. The Lab Engineer encoded the correct program and replaced the immediate field of the fourth word by the magnitude 1 instead of its two's complement.


Wrong answers and why. "The branch offset is wrong": 0xA43D decodes to bne r2, r0, -3, and 5 + 1 − 3 = 3 is the loop start, correct. "The add is wrong": it does not affect termination. Prevention: always assemble from text, or at least run the disassembler over hand-written words and diff it against the intended assembly.
