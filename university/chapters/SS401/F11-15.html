Story hook

Kofi's team is showing its delivery robot in the school hall. The robot drives where the team's laptop tells it, over the hall's Wi-Fi. Halfway through the demo, it turns away from the table it was driving to, speeds up, and heads for the stage steps. Kofi's teammate Mei presses the red stop button on the robot's back, and the motors go quiet.

Afterwards a classmate admits it: he had joined the same Wi-Fi, watched the frames the laptop sent, and sent one of his own, "to see what happens". Nothing in the robot checked who sent a command. In the castle of SS301, every guard checked the badge of the next person in the boot chain. Nobody had put a guard at the gate where commands come in.

The team was lucky twice: the stop button was wired to cut the motors without asking the software, and the stage was empty. This chapter is the threat model the team should have written before the demo, and the first mitigation it would have produced.

What you will be able to do

  • Draw the data-flow diagram of the course robot, with zones for the operator's laptop, the robot computer, the motor microcontroller, the vendor and the physical world, and enumerate its threats with the engine.
  • Rank the threats by the robot's assets, including "people nearby are not hurt", and say which ones become hazards.
  • Explain why the emergency stop and other safety functions must not depend on the parts of the system that the threat model exposes.
  • Implement and test message authentication with a freshness check on the command path, and show what each part stops.
  • Diagnose from a controller log a replay that a freshness check failed to stop.
Jargon box
Message authentication code (MAC)
Simple words: a short check value that only someone with the secret key can compute for a message. Analogy: a wax seal that only the castle's own ring can make. Precise: a value computed from a secret key and a message such that, without the key, producing a valid value for a new or changed message is infeasible; the receiver recomputes it and compares. It gives integrity and origin (from a holder of the key), not secrecy. Not the MAC (media access controller) of networking (HW205). D3
HMAC
Simple words: a standard way to build a MAC from a hash function. Analogy: the seal made by pressing the ring twice, in a fixed way. Precise: HMAC(K, m) = H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ m)), with the key padded to the hash's block size (hashed first if longer), ipad the byte 0x36 and opad the byte 0x5C repeated; with SHA-256 the block is 64 bytes and the output 32 bytes, often truncated. D3 R2
Replay attack
Simple words: sending again a real message that someone recorded earlier. Analogy: a sealed order from yesterday, handed to the guard again today. Precise: an attack in which a valid, authenticated message is captured and re-sent later or elsewhere; a MAC does not detect it, because the message really was produced by a key holder. D1 R3
Freshness check
Simple words: a test that a message is new, not a copy of an old one. Analogy: the guard keeps the number of the last order and refuses any order with a smaller number. Precise: a receiver-side rule using a monotonic counter, a timestamp or a challenge that the authenticated message must include, so that the receiver can refuse old or repeated messages; the receiver's state (last counter, last time) must survive anything that the attacker can trigger, including restarts. D1 R4
Defence in depth
Simple words: several independent protections, so that one failing is not the end. Analogy: the castle has a wall, a gate, guards and a keep. Precise: a design principle: layers of controls with different failure modes (authentication on the command path, a speed limit in the motor firmware, a hard-wired emergency stop), so that a single flaw does not lead directly to harm. D1

Layer 1 — the kid explanation

A robot is a house that can walk, so the burglar question has a new twist: someone may not want to take anything, only make the robot move. The robot listens for orders over the air. If it obeys any order that sounds right, anyone nearby can drive it. So each order gets a seal that only the real operator can make, and the robot checks the seal. That is still not enough: someone could record a real sealed order and play it again later. So each order also carries a number, and the robot refuses any number it has already seen. And because no lock is perfect, the big red stop button is wired straight to the motors, so it works even if every lock fails.

Layer 2 — the student explanation

The robot's diagram

Figure 1 has twelve elements and thirteen flows in six zones. The zones follow the rule of F11-14 (privilege, ownership, reachability): the operator's laptop is another machine on a shared network; the robot computer runs the navigation stack, the motor bridge and a service console; the motor microcontroller is a separate processor behind a serial link; the vendor's update server is someone else's system; and the physical world (sensors, wheels, a person standing at the robot) is outside everyone's control. D1 The engine reports nine crossing flows and 90 threats, of which only one has a claimed control: the signed update flow, which SS301 built and tested. R1

Assets, and the one that is not data

The robot's assets are: people nearby are not hurt; the robot moves only when its operator wants; the robot keeps doing its job; the camera stream and the map (they show the inside of a building); the keys it holds. The first two are what makes a robot's threat model different from a server's. A tampered velocity command is not a data-integrity problem; it is a possible collision. A threat whose result can hurt someone is also a hazard, and SS402 treats hazards with the methods of functional safety (F11-19). This course marks such threats in the threat table and makes sure that the protection against harm does not depend on the security controls alone. D1

The threats that come first

Boundary first, then by assets: the engine's first 71 threats are on elements and flows that touch a crossing (R1). Within them, the team ranks:

  1. The command path from the laptop: spoofing of the teleop app towards the navigation stack (T09, S on Navigation stack) and tampering of the command flow (T48). This is the hook's attack.
  2. The serial link to the motor microcontroller: tampering of wheel speeds (T57) and spoofing of the motor bridge (T15). If the robot computer is compromised by any route, the attacker controls the motors unless the firmware checks something itself.
  3. The service console: spoofing of the person at the robot (T37), elevation of privilege through the console (T26), tampering of the map and parameters through it (T88). Someone who can touch the robot for a minute can change its parameters, including speed limits.
  4. The sensors: spoofing of the lidar and camera (T33): objects placed or light shone to make the robot see what is not there. The navigation stack must treat sensor data as untrusted input (F11-12) and the safety functions must not rely on one sensor alone.
  5. Denial of service on Wi-Fi: the command flow blocked (T50). The robot must go to a safe state (stop) when commands stop arriving, which is a safety requirement as much as a security one.
  6. Updates: tampering of the update flow (T66) is claimed as mitigated by signatures (F11-04); the claim needs its test reference in the table (the SS301 lab's rejection test).

The T-numbers are those of the saved run. R1

The first mitigation: authenticated, fresh commands

For the command path the team chooses a message authentication code. The laptop and the robot share a secret key; every frame carries a tag computed from the key and the frame's text; the controller recomputes the tag and refuses frames whose tag does not match. A MAC answers spoofing and tampering of the flow: without the key, an attacker cannot produce a valid tag for a new or changed frame. D3 It does not answer replay: an old frame with its old tag is still valid. So every frame also carries a sequence number inside the authenticated text, and the controller refuses any number not larger than the last one it obeyed. Listing 6 shows the three policies side by side (Figure 2): with no check, 5 of 5 attacker frames are obeyed; with a MAC, 2 (the replays); with a MAC and the freshness check, none. R3

Layer 3 — the engineer's depth

HMAC, and why the lab's crypto is cross-checked

HMAC builds a MAC from a hash function H with block size B: pad or hash the key K to B bytes, then compute H((K ⊕ opad) ‖ H((K ⊕ ipad) ‖ m)), where ipad is the byte 0x36 and opad the byte 0x5C repeated B times. For SHA-256, B is 64 bytes and the output 32 bytes. D3 Listing 2 implements SHA-256 and HMAC-SHA-256 for teaching. The sources were not opened in this build, so the implementation's correctness is not taken from them: Listing 3 prints four values (two hashes, two HMACs, one with a key longer than the block so that the "hash the key first" branch runs), Listing 4 computes the same four values with Python's hashlib and hmac modules, and the lab fails unless the outputs are byte-for-byte identical. They are. R2 That proves agreement with an independent implementation for these inputs, which is strong evidence and not a proof of correctness for all inputs.

Watch out

Do not put teaching crypto in a product. Use a maintained library for your platform, and keep Listing 2 for understanding and for tests. The comparison function equalTags is written so that its running time does not depend on where the first difference is; whether a compiler preserves that property is not guaranteed by the C++ language, which is one more reason to use a library function made for it.

Truncated tags

The lab sends 8 of the 32 bytes of the HMAC. A random guess of an 8-byte tag is right with probability 1 in 264 per try; frame 4 of Listing 6 is such a guess and fails. Shorter tags save radio bandwidth and bytes on slow serial links, and the cost is a higher chance per forged frame; a receiver can also limit how many bad tags it accepts per second, which turns guessing into a slow, visible attack. The tag length is a design decision for the threat table, with its reason. D3

What the tag must cover

Frame 5 of Listing 6 takes the valid tag of frame 1 and attaches it to a forged body. It fails because the tag covers the whole body, including the sequence number and the speed. A common mistake is to authenticate only part of a message (the command name, not its arguments), or to leave fields that change the meaning outside the tag (a "target robot" field, a "units" field). Rule: everything the receiver acts on is inside the authenticated part. R3

Freshness: counters, time and challenges

There are three common ways to make a message fresh. A counter: the sender increments, the receiver keeps the last accepted value; cheap, but the receiver's state must survive restarts, and two senders need separate counters. A timestamp: the receiver accepts messages within a window of its own clock; needs synchronised clocks and still allows replay inside the window unless combined with a counter. A challenge: the receiver sends a random number and the sender includes it; strong but costs a round trip per exchange. D1 The controller in Listing 5 keeps its counter in RAM (line 35). The forensic lab shows what that costs. Two designs avoid it: store the counter in non-volatile memory (with care for wear and for power loss during the write), or derive a new session key at every connection, so that frames from an earlier session do not verify at all.

Keys

A MAC moves the problem to the key. One key for every robot means that one stolen robot (the attacker "someone with the robot on a bench for a day") opens every robot. Per-robot keys need provisioning (who puts the key in, when, and how it is recorded) and storage that resists reading out; SS301 discussed hardware places for keys (TPM, secure elements, TrustZone; F11-03, F11-05). Rotation needs a way to replace a key without a person at the robot, which is an update flow with its own row in the table. D1

Security and safety

Security controls fail in ways that safety cannot accept: keys leak, configurations are wrong, a bug opens a path. So the robot's protection against harm is layered (defence in depth): authenticated commands (security), a speed and acceleration limit inside the motor firmware that no command can raise (a safety mechanism that also limits what an attacker can do), a watchdog that stops the motors when no valid command arrived for a set time (safe state on denial of service), and a hard-wired emergency stop that removes motor power without any software in the path. The university's safety rules require a physical kill switch for every robot lab; this chapter adds the reason from the threat model: it is the one control the attacker on the network cannot reach. SS402 develops the safety side (F11-21). C1 D1

How the hardware actually does it

On the course robot the check of Listing 5 belongs in two places. On the robot computer, the process that receives teleop frames checks the MAC before passing a command to the navigation stack: that stops the attacker on the Wi-Fi. In the motor microcontroller's firmware, a second check (a MAC on the serial frames with a key that only the motor bridge and the firmware hold, or at least a speed limit and a heartbeat timeout) stops an attacker who has taken over the robot computer by another route. The second check costs processor time on a small microcontroller: an HMAC-SHA-256 over a short frame is a few compressions of SHA-256 (Listing 2 runs the compression once per 64-byte block, and HMAC adds two hashes), and whether that fits the control loop's period on your kit's microcontroller is something you measure, not assume. R2

The emergency stop must be wired so that it removes motor power or enables a hardware brake directly. A stop button read by software and forwarded as a "stop" command is a command like any other: it can be delayed, lost or overridden by the same attacker. Whether your kit's stop does that is in its wiring diagram and its documentation, which go in the dossier.

Safety

Robots move with force and can start unexpectedly. Run every lab of this chapter in the simulator first; move to the kit robot only after the simulator lab passes, with a tested physical kill switch, a clear zone around the robot, and supervision for learners below L3. Never test an attack on a robot that is near people or that you do not own. Test the emergency stop before every session.

Not verified — check before relying on this

Untested on hardware: no robot, microcontroller or serial link was available in this build. The check runs on the host only. The cost of HMAC on the kit's microcontroller, the serial frame format, and the kit's emergency-stop wiring were not checked; they belong in the kit's dossier entry.

Where the analogy breaks


    

  • A house does not move. The worst a burglar does is take things; the worst outcome for a robot is that it hurts someone. A robot's threat model therefore has hazards in it, and those need safety mechanisms that work even when the security model is wrong.
    • 

  • A house's attacker wants your things; a robot's attacker may want nothing. The hook's classmate wanted "to see what happens". Threats that bring no gain to the attacker still need decisions, because the harm does not depend on motive.
    • 

  • A wax seal can be inspected by eye; a MAC cannot. A tag looks like random hexadecimal whether it is right or wrong; only the key holder can check it. And unlike a seal, a MAC does not show who of the key holders made it: every robot and laptop with the shared key can make valid frames.
    • 

  • A guard remembers yesterday; a microcontroller forgets on restart. Unless its counter is stored, a restarted controller has no memory of which orders it has seen. That is the forensic lab.
    •

Answers to Check yourself


    

  1. "People nearby are not hurt", "the robot moves only when its operator wants" and "the robot keeps doing its job". Threats against them can cause physical harm, so they are hazards: they rank above data threats of similar likelihood, and they need a safety mechanism that does not depend on the security control.
    2. 

  2. Against forged and altered frames (Mac rejects frames 3, 4 and 5). Not against replays of genuine frames (Mac obeys 7 and 8), not against reading the frames (no secrecy), and not against blocking them.
    3. 

  3. The controller recomputes the tag over the received body (with sequence number 4 and speed 1.50), which differs from frame 1's body, so frame 1's tag does not match. The tag binds to the whole body.
    4. 

  4. A software stop travels the same paths as other commands: it can be delayed by a flooded network, ignored by a crashed or compromised computer, or overridden by the attacker's next frame. A hard-wired stop removes motor power without any of those parts, so it still works when the threat model's controls have failed.
    5. 

  5. Zones: tablet (operator's device), workshop network, arm controller, pendant (on a cable, in the operator's hand), world (people, workpieces). Threats: spoofed or tampered jobs from the network (security control: authenticated jobs with freshness; safety mechanism: speed and force limits in the controller, reduced speed when a person is in the cell); and the pendant being bypassed or spoofed (security: the pendant link is local and the controller accepts motion only with the pendant's enabling device; safety: the hard-wired stop on the pendant). Other good answers are possible if each has both kinds of control.
    6. 

  6. 1 in 264. Add a limit on bad tags (for example, after a few bad tags per second, ignore that link for a while and log it), so that guessing becomes slow and visible.
    7. 

  7. Checked in this build: no verdict changes (the guessed all-zero tag and the moved tag are still wrong at 2 bytes). But a 2-byte tag is guessed with probability 1 in 65,536 per try, which a script reaches in minutes. A few hand-picked frames cannot show the strength of a control; the tag length must be argued from the arithmetic and the attacker's rate.
    8. 

  8. If freshness came first, an attacker could send forged frames with huge sequence numbers; even though their tags are wrong, the receiver would have updated or compared its state on unauthenticated data. Checking the MAC first means only frames from a key holder can influence the freshness state.
    9. 

  9. T66 (update tampered with): "Claimed: signed updates". Before "mitigated", the row needs the reference to a test that runs: the SS301 lab's test where an update with a bad signature is refused, and the date and version it last ran.

Forensic lab answer key


Observation. Before the restart the controller obeyed seq 101–105 from 10.0.0.20. At 14:02:10 it restarted and its state was reset. The operator's laptop reconnected and started again at seq 1 (1, 2, 3 obeyed). At 14:06:44 a frame seq=104;cmd=drive;v=0.40;w=0.00 from 10.0.0.77 was obeyed. At 14:06:51 and 14:06:52 the operator's stops (seq 4 and 5) were rejected with "old seq 4 <= 104" and "old seq 5 <= 104".


Root cause. The frame at 14:06:44 is an exact copy of the operator's own frame from 14:01:30 (same body, seq 104): a replay of a recording made before the restart. Its tag is valid, because the operator's key really made it (the policy checks the MAC first; it was obeyed, so the tag matched). It was accepted because the controller's last sequence number lives in RAM (robotlink.h line 35) and was reset by the restart to -1; after the operator's 1–3, 104 was "fresh". Accepting it then moved the counter to 104, so every genuine operator frame with a smaller number was rejected: the attacker both drove the robot and locked the operator out.


Source address. It does not prove anything: on a shared network any device can send from any address, and the MAC, not the address, is the identity. The different address suggests a second device, consistent with a recording replayed by someone else.


Fixes and test. (1) Persist the last accepted sequence number across restarts (and make the operator continue from it), or (2) use a new session key per connection so frames of an earlier session fail the MAC. Test: restart the controller, replay a frame recorded before the restart, expect rejection; send the operator's next frame, expect it obeyed.


What stopped the robot. The hard-wired emergency stop. The threat table must list "replay after restart" as a threat with a test, and the incident confirms why the stop must be independent of the command path.


Wrong answers and why. "The key was stolen": no forged frame appears; the accepted frame is a byte-for-byte copy of a genuine one. "A bug in the MAC check": the check behaved as designed; the freshness state was the gap. "Block 10.0.0.77": addresses can be changed; it fixes nothing. How the evidence was produced: forensic.cpp feeds the listed frames to robot::Controller with policy MacFresh and calls restart() at 14:02:10; the scenario is synthetic.
