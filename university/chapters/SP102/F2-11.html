Story hook

Analogy

The kitchen has a tool wall: the big pot, the only mandoline, the key to the spice cabinet. The rule says: take a tool, use it, hang it back. Most days that works.

Then one evening Tariq takes the spice key, sees that the dish needs no spice after all, and hurries off to the next order. The key is in his apron pocket. Ten minutes later Mei needs saffron. The cabinet is locked, and the key is nowhere. "Someone else is using it," she thinks, and waits. Nobody is using it. Nobody will ever bring it back.

Lucía, the head chef, solves it for good: the tool wall now has a door, and anything you took from the wall is returned automatically when you leave the room, by whichever door you leave. You cannot forget, because returning is no longer your job.

That automatic return is called RAII. It is the most important habit in C++ systems programming, and this chapter builds it from the destructor of F2-10.

What you will be able to do

  • Explain what a resource is and why "acquire, use, release" by hand fails on early-return and error paths.
  • Write an RAII wrapper class for a Linux file descriptor: acquire in the constructor, release in the destructor, copying forbidden.
  • Measure a resource leak by counting a process's open file descriptors, and prove a fix with a test.
  • Recognise RAII types in the standard library (std::ofstream, std::lock_guard) and use them instead of manual release.
  • Diagnose "the file that stays locked" from a log and a list of open descriptors.
Jargon box
Resource
Simple words: Something your program borrows from the system and must give back. Analogy: A tool from the tool wall. Precise: Anything that must be acquired and later released: memory, open files, locks, network connections, GPU memory; if not released, it stays taken until the process ends. D1, D3
RAII (Resource Acquisition Is Initialisation)
Simple words: Tie a resource to an object: the object takes it when it is made and gives it back when it ends. Analogy: Borrowing a tool from the tool wall, which is returned automatically when you leave the room. Precise: The technique of acquiring a resource in a constructor and releasing it in the destructor of an owning object, so that the release happens on every path out of the owner's scope, including early returns and exceptions. D1, D3, R2
File descriptor
Simple words: A small number the operating system gives your program for each file it has open. Analogy: The number on the tag of a borrowed tool. Precise: On Linux and other POSIX systems, a non-negative integer returned by open() that indexes the process's table of open files; it stays valid until close() or the end of the process. D4, R5
Resource leak
Simple words: Taking a resource and never giving it back. Analogy: The spice key forgotten in an apron pocket. Precise: A resource acquired and never released while the program keeps running; leaks accumulate until acquisition fails (R5: Too many open files). R1, R5
Early return
Simple words: Leaving a function before its last line. Analogy: Leaving the room by the back door. Precise: A return statement before the end of a function body; any clean-up written after it does not run. R1
Lock (advisory file lock)
Simple words: A sign that says "I am using this; others must wait". Analogy: The single key to the spice cabinet. Precise: Here: a lock taken with Linux's flock() on an open file; it is held through that open file and released by flock(fd, LOCK_UN) or when the file is closed; "advisory" means only programs that also ask for the lock are stopped. D4, R6
Owner (of a resource)
Simple words: The one object responsible for giving a resource back. Analogy: The name written on the borrowing card. Precise: The object whose destructor releases the resource; with RAII each resource has exactly one owner at a time, which is why the wrapper forbids copying (F2-13 adds transfer of ownership by moving). D3

The idea in pictures

Figure 1 compares the two versions of the same function. With release by hand, the clean-up sits at the bottom, and the early-return path never reaches it. With RAII, every path out of the function goes through the closing brace, and the compiler places the destructor call there.

Layer 1 — the kid explanation

Some things in a computer are borrowed. When your program opens a file, the operating system lends it a numbered tag for that file. When your program locks something, it holds the only key. These borrowed things are called resources, and every one of them must be given back.

Giving back "by hand" means writing close at the end of the function. That works only if the program always reaches the end. Real functions have many exits: "nothing to do, leave now", "bad input, leave now", "an error happened, leave now". Every exit is a back door where the key can walk out in someone's pocket.

RAII is the automatic tool wall. You put the resource inside an object. The object's constructor borrows it; the object's destructor gives it back. And from F2-10 you know the destructor runs at the closing brace, whichever door you use. So the resource is always returned, and you never have to remember.

Layer 2 — the student explanation

Measuring a leak

On Linux every process can list its own open files in the folder /proc/self/fd; each entry is one file descriptor. The function open_file_count() in the listings counts those entries (the listing itself uses one descriptor while it reads the folder, which is why the count starts at 4: standard input, output, error, and the folder being read). D4, R1

Listing 1 appends orders to a file with the system calls open, write and close. For an empty order it returns early, between open and close. After six orders, three of them empty, the run printed open files at start: 4 and open files after 6 orders (3 empty): 7: exactly one leaked descriptor per early return. Nothing crashed and no warning appeared; the program simply holds three files it will never use again. R1

How long can that go on? Listing 5 lowers its own limit to 32 open files and then opens without closing. The run printed open failed after 29 leaked files: Too many open files. A leak is a slow failure: the program works for a while, then a completely unrelated open somewhere else fails. R5, D4

The RAII wrapper

Listing 2 puts the descriptor inside a class File with four parts. The constructor calls open and throws if it fails, so a File object always owns an open file (its invariant). The destructor calls close. Copying is deleted, because two objects closing the same descriptor would be the "closed twice" bug of F2-10. And a member function, write_line, does the work. D1, D3

Now append_order creates a local File f. The early return needs no extra code: f's destructor runs on the way out. The run printed open files after 6 orders (3 empty): 4. Opening a file that does not exist threw, main caught it (caught: File: cannot open no_such_folder/orders.txt), and the count at the end was still 4. R2

RAII is already everywhere in the standard library

You have used RAII types without knowing it. std::string and std::vector release their memory in their destructors. std::ofstream closes its file in its destructor, and std::lock_guard unlocks a mutex in its destructor. Listing 3 shows both: inside write_menu the count was 5, after it 4, and try_lock on the mutex succeeded, so the lock had been released at the closing brace. When a standard RAII type exists for your resource, use it; write your own wrapper only for resources the library does not cover, such as raw descriptors, device handles or, later, GPU memory. R3, D1, D2

Layer 3 — the engineer's depth

Design rules for a wrapper

  • One resource, one owner. A class that owns two resources needs care in its constructor: if the second acquisition throws, the destructor of the half-built object does not run (F2-10), and the first resource leaks. Give each resource its own small wrapper and make them members; already-constructed members are destroyed even when the constructor throws. D2, D3
  • Establish the invariant or throw. Listing 2 never holds an invalid descriptor, so its destructor need not check. MenuLock in Listing 4 chose differently: a failed lock is a normal outcome, so it records locked_ and its destructor checks. Both are valid; the invariant comment must say which. R2, R6
  • Release must not fail loudly. close can report an error, but a destructor must not throw (F2-10). If a caller needs to know whether data reached the disk, offer an explicit close() or flush() member that returns an error, and let the destructor be the safety net. D3, D4
  • Copy is forbidden; move comes next. A File cannot yet be returned from a function or stored in a std::vector. F2-13 adds move operations that transfer ownership. D1

Where RAII goes later in this university

The same pattern wraps a mutex in SP203, a CUDA device allocation and stream on the host side in BR-01 and CU201, and an MMIO mapping or a DMA buffer in the driver courses. The systems curriculum asks kernel code to wrap C interfaces in small C++ classes; RAII is how those classes release what they acquire. D5

How the hardware actually does it

A file descriptor is not a hardware object. It is an index into a table that the operating system kernel keeps for each process. open and close are system calls: the program asks the kernel, through a special instruction, to add or remove an entry. The kernel only frees the entry when the program asks, or when the whole process ends. That is why a leak is invisible to the program itself: the table lives in the kernel, not in your variables. D4

Listing 5 shows the table's behaviour directly. After lowering the limit to 32, the descriptors handed out went up to 31 (highest descriptor number handed out: 31), and the 30th open failed. The three missing numbers, 0, 1 and 2, are standard input, output and error, which every process starts with. In the forensic lab you will read the table itself, entry by entry. R5, R4

Not verified — check before relying on this

Details of flock (that the lock belongs to the open file description and is released when the last descriptor referring to it is closed; that a second open in the same process gets a separate lock) were observed in runs R4 and R6 but not read in the Linux man-pages during this build. Behaviour on other systems (for example Windows, where locking works differently) was not tested. Check the Linux man-pages for flock(2), open(2), close(2) and proc(5), and record the version in the dossier. R4, R6

Where the analogy breaks


    

  • A tool wall returns tools when you leave the room. RAII returns the resource when the owning object ends, which is at the end of the object's scope, not of the function or the program. An object created early in main holds its resource until main ends, even if you stopped using it long before; give such objects a smaller block. R3
    • 

  • A forgotten key can be found and brought back. A leaked descriptor cannot be recovered by the program: the variable holding the number is gone, and only the end of the process frees the entry (R4). R4, D4
    • 

  • The registered analogy says RAII "only works if every resource has an owner object". That is literal: a raw int fd or a raw pointer is not an owner, and RAII does nothing for it. R1
    •

Transition box

Where you came from: F2-10 showed that a destructor runs at the closing brace on every path, in reverse order. What carries over: constructors that establish an invariant, deleted copies, and tracing to see what really happens. What changes: the destructor now releases something outside your program (a kernel table entry, a lock), so a mistake is not a wrong number in a variable but a leak that shows up much later and somewhere else; and you must decide who owns each resource. R1, R5 What comes next: F2-12 explains references and const, which let functions use an owner's resource without copying the owner.

Method hints


Start from the symptom and go backwards: the refusal comes from the flock call failing, so ask what holds the lock. The descriptor list is the process's own view of its kernel table; compare it with the descriptors a healthy run should have (standard input, output, error, and the one the listing uses itself). Summary


    

  • A resource is anything acquired that must be released: files, locks, memory, connections.
    • 

  • Releasing by hand fails on early returns and errors; leaks show up later and elsewhere.
    • 

  • RAII: acquire in the constructor, release in the destructor; the compiler runs the destructor on every path.
    • 

  • A wrapper owns one resource, establishes its invariant or throws, deletes copying, and never throws from its destructor.
    • 

  • Use standard RAII types when they exist: std::string, std::vector, std::ofstream, std::lock_guard.
    • 

  • On Linux, /proc/self/fd lists a process's open descriptors: a leak meter and a forensic tool.
    •
