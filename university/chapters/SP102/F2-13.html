Story hook

Analogy

Grandmother Ngozi's recipe card for pepper soup hangs in the kitchen. Two cooks want it. For the first cook, Lucía makes a photocopy: now there are two cards, and each cook can scribble on their own. That took time at the copier, but nobody lost anything.

The second cook is moving to the new branch across town, and the old kitchen will not need the card any more. Making a photocopy and then throwing the original away would be silly. Lucía simply hands over the original card. It is quick, and afterwards the old hook is empty.

Now imagine the card was not a card but the only key to the spice cabinet. Photocopying a key is not allowed: two people would think they own the cabinet. But handing the key over is fine.

C++ has exactly these two operations. Copy makes an independent duplicate. Move hands the contents over and leaves the source empty. Some things, like the key (and the File of F2-11), may only be moved.

What you will be able to do

  • Explain the difference between copying and moving, and predict which one C++ uses for a given line.
  • Apply the rule of zero, and when needed the rule of five, to your own classes.
  • Make an RAII class movable but not copyable, so it can be returned from functions and stored in containers.
  • Explain why move operations should be noexcept, using a measurement of std::vector growth.
  • Diagnose a use-after-move bug from its output.
Jargon box
Copy
Simple words: Make a second, independent object with the same value. Analogy: A photocopy of the recipe card. Precise: Done by the copy constructor (T(const T&)) or copy assignment (T& operator=(const T&)); afterwards the two objects are equal and changing one does not change the other (R2). D1, R2
Move
Simple words: Hand the contents of an object over to another, leaving the first one empty or reusable. Analogy: Handing over the original card. Precise: Done by the move constructor (T(T&&)) or move assignment (T& operator=(T&&)), which may take resources from the source; the source stays a valid object, in a state each class documents (R7). D1, D2, R7
std::move
Simple words: A label that says "you may take this object's contents". Analogy: Writing "please take the original" on the card. Precise: A function in <utility> that only converts its argument to an rvalue reference so that a move operation can be chosen; it moves nothing by itself. D1, D2
Rvalue reference (T&&)
Simple words: A kind of reference that binds to things that are about to disappear or that were marked with std::move. Analogy: The tray marked "leftovers: take whatever you need". Precise: A reference type written T&&; overloads taking T&& are chosen for temporaries and for std::move(x), which is how the compiler picks moving over copying. D2
Moved-from state
Simple words: What is left in an object after its contents were moved away. Analogy: The empty hook where the card used to hang. Precise: The state of the source after a move; for standard library types, "valid but unspecified" (you may assign to it or destroy it, but should not rely on its value); your own classes should document it (our File: owns nothing). D2, D3
Rule of zero / rule of five
Simple words: Either write none of the copy, move and destructor functions, or think about all five. Analogy: Either follow the standard kitchen procedure fully, or write your own procedure for every step. Precise: Guidelines: let members that manage themselves (std::string, std::vector, RAII wrappers) give correct behaviour with no declarations (zero); if a class must declare any of destructor, copy constructor, copy assignment, move constructor, move assignment, it should declare or delete all five. D3
Copy elision
Simple words: The compiler building the result directly where it is needed, with no copy and no move. Analogy: Writing the card straight onto the cook's hook instead of writing it elsewhere and moving it. Precise: Since C++17, returning a temporary (return T(...);) used to initialise an object constructs it in place, without calling copy or move constructors (step 6 of R1 printed none). D2, R1

Layer 1 — the kid explanation

When you copy something in C++, you get a second one that is completely separate. Change the copy, and the original stays the same. For a list of a thousand dishes, copying means writing out all thousand again.

Sometimes you do not need the original any more. Then copying is wasted work. Moving says: "take what is inside; I am done with it". The new object takes over the contents, and the old one is left empty but still a proper object: you may fill it again or let it end.

Some things must never be copied, like the only key to a cabinet or an open file. Two owners would both try to give it back. Those things can still be moved: the key is handed over, and only one person has it at any time.

Layer 2 — the student explanation

Which operation runs?

Listing 1 gives a class Tray all four copy and move operations, each printing its name. The run R1 answers "which one runs?" line by line:

  • Tray b = a; printed copy constructor: a is a named object that is still needed, so it is copied.
  • Tray c = std::move(a); printed move constructor: std::move marks a as "may be taken from".
  • b = c; printed copy assignment: b already exists, so it is assignment, not construction.
  • b = make_tray(); printed move assignment: the function's result is a temporary that will disappear anyway, so moving from it is safe without writing std::move.
  • Tray d = make_tray(); printed nothing at all: the result was built directly in d (copy elision).

The final line, sizes: a=0 b=3 c=2 d=3, shows that a was left empty by the move. R1, D2

The rule of zero: usually, write nothing

Listing 2's Recipe holds a std::string and a std::vector and declares none of the copy or move operations. The compiler-generated ones copy or move each member, which is exactly right: the copy spicy got its own steps (4 after adding one, while the original kept 3), and moving spicy handed over all 4 steps. This is the rule of zero, and it is the right choice for most classes: build them from members that already manage themselves. R2, D3

The rule of five: a class that owns a raw resource

A class that owns something the compiler does not understand, such as the file descriptor of F2-11, needs its own destructor; then the generated copy would duplicate the descriptor and close it twice. So it must decide about all five operations. Listing 3's File: destructor closes; copying is deleted (Listing 4 shows File b = a; refused with use of deleted function 'File::File(const File&)'); the move constructor takes the descriptor and sets the source's to -1; move assignment closes its own file first, then takes the other's. Its invariant now reads "fd_ >= 0 owns a file; fd_ == -1 owns nothing", and the destructor checks which. R3, R4, D3

The run shows ownership moving and nothing leaking: five files in a vector made 5 open; moving logs[0] out left logs[0] owns a file: 0 and first owns a file: 1 with still 5 open; assigning a new file to first closed the old one first, so the count stayed 5; and after the block it was 0. R3

After a move

A moved-from object is still alive: its destructor will run, and you may assign a new value to it. What you should not do is read its old value. For standard library types the standard only promises a "valid but unspecified" state; with this library, R5 printed size 0 for a moved-from vector, but the forensic lab shows how relying on any value after a move goes wrong. For your own classes, document the moved-from state and test it, as the lab does. D2, R5, R7

Layer 3 — the engineer's depth

Why move operations should be noexcept

When a std::vector grows, it must transfer its elements to the new block. If moving an element could throw halfway, the old block would already be partly emptied and the vector could not undo the operation. So the library moves elements during growth only if the move constructor is declared noexcept (or if the type cannot be copied); otherwise it copies, which keeps the old block intact if something fails. D2, D1

Listing 6 measured this with 100 push_back calls. With a noexcept move constructor: 0 copies, 227 moves. Without noexcept: 127 copies, 100 moves. The 100 moves in both cases are the temporaries passed to push_back; the 127 are the elements carried over during growth (1 + 2 + 4 + 8 + 16 + 32 + 64 = 127 with this library's doubling), copied instead of moved when the move might throw. Mark your move operations noexcept whenever they cannot fail, which is the normal case for "take the pointer, leave -1 behind". R6, D3

Not verified — check before relying on this

The growth sequence 1, 2, 4, …, 64 is what libstdc++ of GCC 13.3 produced in R6; the C++ standard does not fix the growth factor. The rule "move if noexcept, else copy" is the behaviour of std::move_if_noexcept used by the standard containers' strong exception guarantee; check the exact wording in ISO/IEC 14882 (vector modifiers, and the description of move_if_noexcept). R6

Self-assignment

Move assignment of File checks this != &other. Without that check, f = std::move(f) would close its own descriptor and then take back the closed number. GCC 13 warns about obvious self-moves (Listing 7: moving 'dish' of type 'std::string' to itself [-Werror=self-move]), but a self-move through a second name, such as an element reached through two references, is not caught by the compiler; the lab tests it. R8, R7

Passing "sink" parameters

A constructor that stores a string, such as Recipe(std::string name, ...), can take it by value and then std::move it into the member. A caller passing a temporary pays one move; a caller passing a named string pays one copy (made at the call) and one move. This is the pattern used in Listings 1 and 2, and it improves on Stock in F2-09, which copied its by-value parameter a second time. D3, D1

How the hardware actually does it

Listing 5 shows what a move of a vector really costs. The vector object itself was 24 bytes on this machine: room for addresses and counts that describe a separate block of memory holding the 1,000 strings. The copy got a new block (copy uses the same block: 0); the move kept the original block (move uses the same block: 1). So the move transferred a few machine words from one 24-byte handle to another; the 1,000 strings in the block were not touched at all. A copy, by contrast, allocated a block and copied every string. R5

The same holds for File: moving copies one int and writes -1 into the source. The kernel's descriptor table (F2-11) is not involved at all, which is why R3's open-file count did not change when ownership moved. Moving is cheap exactly when an object is a small handle to something bigger or outside the program. R3

Note

A class whose members are plain values, such as two ints, gains nothing from moving: moving and copying both copy the same bytes. Moving matters for handles. D1

Where the analogy breaks


    

  • After handing over the original card, the hook is visibly empty. A moved-from C++ object is not necessarily empty: standard types promise only "valid but unspecified". Our own File promises "owns nothing" because we wrote that; R5's empty vector is this library's choice. D2, R5
    • 

  • std::move sounds like the act of handing over. It is only the label "you may take this"; if the receiving type has no move operations, a copy happens instead, and if nobody receives it, nothing happens at all. D2
    • 

  • A photocopy is always cheap to understand. Copying a C++ object runs code you may not see (a copy constructor), and for some classes copying is forbidden altogether (R4). R4

Summary


    

  • Copy makes an independent duplicate; move hands the contents over and leaves the source valid.
    • 

  • std::move only marks an object as movable; the move operation does the work.
    • 

  • Temporaries are moved from automatically; returning a temporary into a new object involves no copy or move (copy elision).
    • 

  • Rule of zero for most classes; rule of five for classes that own a raw resource.
    • 

  • RAII owners: delete copies, write noexcept moves, define the moved-from state, check self-move.
    • 

  • Moving a handle (vector, file) moves a few words, not the data; never read a moved-from object's old value.
