Story hook

Analogy

Three things go wrong in the kitchen on one evening. A ticket says "l2 dumplings": a smudged 12, or an L? The cook writes "unreadable" on the ticket and hands it back to the waiter, who asks the guest. The fridge is out of cream: the cook says "no cream" and the guest chooses another dessert. Then the pan catches fire. Nobody hands a note back for that. The cook pulls the alarm, every station shuts down its burners on the way out, and the manager at the door decides what happens next.

The kitchen has three ways to report a problem: a note saying what went wrong (an error code), a plate that may come back empty (std::optional), and the alarm to the manager (an exception). This chapter is about choosing between them.

What you will be able to do

  • Report failure with an error code, with std::optional, and with an exception, and say when each fits.
  • Write throw, try and catch, and trace stack unwinding, including which destructors run.
  • Explain what happens to an exception that nobody catches.
  • Use [[nodiscard]] so that ignored error codes become compiler errors.
  • Recognise the machine-code calls behind throw, and why kernels build without exceptions.
  • Diagnose a program that hides an error behind a default value.
Jargon box
Error code
Simple words: A returned value that says whether it worked, and if not, why. Analogy: A note handed back: "unreadable", "no cream". Precise: A return value (often an enum class) whose values name the outcomes; the result itself is returned separately, for example through a reference parameter. D3, R1
std::optional
Simple words: A box that holds either a value or nothing. Analogy: A plate that may come back empty. Precise: The class template std::optional<T> (header <optional>), which contains a T or is empty (std::nullopt); test it with if (o) and read it with *o or o.value_or(default). D2, R1
Exception
Simple words: A way to stop the normal work and jump to code that can handle the problem. Analogy: The alarm to the manager. Precise: An object thrown with throw; control leaves the current function and continues at the nearest matching catch handler of an enclosing try block. D1, D2
Stack unwinding
Simple words: On the way out, every function that is left behind tidies up. Analogy: Each station turns off its burners as the cooks leave. Precise: While an exception travels to its handler, the destructors of all automatic objects in the scopes it leaves run, in reverse order of construction (R2). D2, R2
std::terminate
Simple words: The emergency stop when nobody handles an exception. Analogy: The alarm rings and no manager answers: the building is evacuated. Precise: The function called when an exception is not caught (and in a few other cases); by default it calls std::abort, which ends the program with the signal SIGABRT (R3: exit code 134). D2, R3
[[nodiscard]]
Simple words: A label that says "do not ignore what this function returns". Analogy: A note stapled to the ticket that must be read. Precise: An attribute on a function or type; discarding the returned value causes a compiler warning, which -Werror turns into an error (R4). D2, R4
Exception safety
Simple words: What is still true about your objects after an exception went through. Analogy: After the alarm, are the stations safe and the stock lists correct? Precise: The basic guarantee: no leaks and every invariant holds; the strong guarantee: the operation either succeeds or changes nothing; no-throw: it never throws (noexcept). D3, D1

Layer 1 — the kid explanation

Sometimes a job cannot be done. The question is how to tell the person who asked for it.

For small, everyday problems, you just answer: "I could not read it" or "there is none left". The person who asked checks your answer and decides what to do. That is an error code, or an empty plate.

For big problems that stop everything, you ring the alarm. Everyone on the way stops what they are doing, tidies up their own place, and the alarm goes to someone whose job is to handle it. That is an exception. If nobody handles it, the whole program stops.

The worst choice is to say nothing and pretend: if you cannot read "l2" and just write 0, the guest gets no dumplings and nobody knows why. The forensic lab is about exactly that.

Layer 2 — the student explanation

Three ways, one job

Listing 1 reads a number of portions from text in three ways, with four inputs. Each way reports the same problems differently:

  • Error code (parse_code): returns an enum class ParseError and writes the number into a reference parameter. For "l2" it returned 2 (not_a_number), for "" 1 (empty), for "99999999999" 3 (out_of_range). The caller must check the code, and nothing forces it to. R1
  • Exception (parse_throw, using std::stoi): for "l2" and "" the library threw std::invalid_argument, for the too-large value std::out_of_range; the handlers caught them by const reference. This library's what() text was only stoi, which tells the user very little. R1, D2
  • std::optional<int> (parse_optional): either a value or empty. For "12" it held 12; for the three bad inputs it was empty. Simple to use, but the reason for the failure is lost. R1

How exceptions travel

Listing 2 shows throw leaving two functions at once. For 2 portions everything ran normally; for 6, fry threw std::length_error, the lines "frying" and "order done" were skipped, pan and stove were released in that order, and the catch in main printed the message. This is why RAII (F2-11) matters so much: with exceptions, any function call can be a way out of your function, and only destructors are sure to run on every way out. R2, D2

Catch by const reference (catch (const std::length_error& e)). Handlers are tried in order, and a handler for a base class such as std::exception also catches the classes derived from it, so put the specific handlers first. Throw objects of the standard exception types, or of types derived from them, not integers or strings. D3, D1

If no handler matches, the program ends. Listing 3 throws in main without a try: the run printed terminate called after throwing an instance of 'std::runtime_error' with the message, and the exit code was 134. No destructors are guaranteed to run in this case. R3, D2

Making error codes harder to ignore

The weakness of error codes is that callers forget to check them. Mark such functions [[nodiscard]]. In Listing 4 the caller ignored the result, and the build failed with ignoring return value of ... declared with attribute 'nodiscard' [-Werror=unused-result]. The forensic lab of F2-15 was the case where no such attribute protected the caller. R4

Layer 3 — the engineer's depth

std::expected (C++23)

std::expected<T, E> holds either a value or an error of type E: std::optional plus a reason. It is C++23, so this course's C++20 flags do not have it. The lab folder's run.sh built Listing 5 with -std=c++23, and it printed value 12 and error not a number: "l2". Many embedded and kernel codebases have their own type of this shape for the same reason. R5, D2

Exception guarantees

Each operation should promise one of three levels. Basic: after an exception, no resource leaks and all invariants hold, but values may have changed. Strong: it either succeeds or leaves everything as it was ("commit or roll back"). No-throw: it never throws; destructors, move operations and swap should be noexcept. F2-13 showed why: std::vector moves elements only if the move constructor is noexcept, because only then can it keep the strong guarantee when it grows. The "refuse without changing anything" rule of F2-09 is the strong guarantee. D1, D3

Destructors and noexcept

A destructor that throws while an exception is already unwinding the stack ends the program with std::terminate. Destructors are therefore noexcept by default (F2-10). A noexcept function that throws anyway also calls std::terminate. noexcept is a promise, not a filter. D2

How the hardware actually does it

The processor has no instruction for "throw". The compiler turns throw into calls to a support library, and it adds tables that let the program find handlers and clean-up code. The lab folder's run.sh built Listing 2 without sanitizers and listed every call in the machine code of fry: R7

  • __cxa_allocate_exception gets memory for the exception object; it does not live on the normal stack, because the stack is about to be unwound.

R7, D5


The normal path contains no exception work at all: no checks, no flags. The cost is paid when something is thrown (the unwinder searches tables and runs clean-up blocks) and in program size (the tables and clean-up code). This design keeps the success path fast and makes throwing slow, which is one reason exceptions are reserved for rare failures. D5, R7


A kernel has no unwinder unless you write one. The systems curriculum says so directly: "No exceptions, no RTTI by default: both need runtime support (unwinding tables, an unwinder, type-info objects)". With -fno-exceptions, a throw no longer compiles. Listing 6 failed with exception handling disabled, use '-fexceptions' to enable. Code you want to reuse in a kernel must therefore report errors with codes or std::expected-like types. D6, R6

Where the analogy breaks


    

  • A real alarm is heard by everyone at once. An exception goes only up the chain of callers, and only to the nearest matching handler; code elsewhere in the program never hears it. D2
    • 

  • In the kitchen, staff shut down their own stations because they were trained to. In C++, only objects with destructors clean up during unwinding. A raw open without a RAII wrapper is simply abandoned, as in F2-11's forensic lab. R2
    • 

  • An empty plate is obvious to a waiter. An empty std::optional is only obvious if the code checks it. value_or(0) turns it back into a silent plausible value (forensic lab). R8
    •

Transition box

Where you came from: F2-09 to F2-11 threw from constructors and relied on destructors; F2-15 used end() as a "not found" marker. What carries over: invariants and RAII are what make exceptions safe; "refuse without changing anything" is the strong guarantee. What changes: you now choose a strategy deliberately per kind of failure, and you write it into the interface (return type, [[nodiscard]], documented exceptions) instead of leaving it to the caller's luck. R2, R4, D3 What comes next: F2-17 writes small functions in place (lambdas): the predicates of F2-15, and callbacks that decide what to do when something fails.

Add std::optional<T> peek() const (empty when the buffer is empty), mark push and pop [[nodiscard]], and write a short design note: why the ring buffer reports "full" and "empty" by return values and never throws, which functions are noexcept (and for which T), and which exception guarantee push gives if copying T throws. Test that ignoring push's result no longer compiles, by keeping an expect-fail file as in Listing 4.


Rubric (course project default, guide 11.5): correctness and tests 35 %; engineering quality 20 %; measurement and evidence 20 % (recorded runs, including the expect-fail build); documentation and design notes 15 % (the error-handling note); presentation 10 %.



Summary


    

  • Error codes, std::optional and exceptions report failure in different ways; choose per kind of failure and put the choice in the interface.
    • 

  • An exception unwinds the stack: destructors of the scopes it leaves run in reverse order; uncaught, it ends the program (R3).
    • 

  • Catch by const reference, most specific first; throw standard exception types.
    • 

  • [[nodiscard]] makes ignored results a compile error under -Werror.
    • 

  • Never turn a failure into a plausible value.
    • 

  • throw becomes calls into a support library plus clean-up blocks; the normal path pays nothing. Kernels build without exceptions (R6, R7).
    •
