Story hook

Analogy

The restaurant has a cold shelf for soup. A card is taped to it: "Never fewer than 0 portions. Never more than 20. Only the soup cook moves portions on or off this shelf."

One busy evening, a helper named Kofi grabs portions straight from the shelf without telling the soup cook. The cook's notebook says 7 portions are left. The shelf really has none. A waiter promises soup to a table of nine, and there is nothing to serve.

The rule on the card was fine. The problem was that anyone could reach the shelf. The head chef, Lucía, fixes it the simple way: the shelf goes behind a counter, and every request goes through the soup cook, who checks the card before every move.

In C++, the shelf with its card and its one cook is a class. The card is the class's invariant. The counter is the word private. This chapter shows how to build all three and how to prove that the rule holds.

What you will be able to do

  • Explain what a class invariant is and write one down as a comment before you write the class.
  • Write a class with private data members, a checking constructor and member functions that keep the invariant true.
  • Explain why private turns "please follow the rule" into "the compiler enforces who may touch the data", and read the compiler error that proves it.
  • Use small classes as strong types so that the compiler refuses to mix up two numbers with different meanings.
  • Test a class's invariant after every operation and diagnose a broken invariant from a log.
Jargon box
Class
Simple words: Your own type that bundles data with the only functions allowed to change it. Analogy: A kitchen station: the shelf, its rule card and the one cook who works it. Precise: A user-defined type declared with class or struct, containing data members and member functions; with class the members are private unless marked otherwise. D1, D2
Object
Simple words: One real thing made from a class, with its own data. Analogy: One actual soup shelf, built to the station plan. Precise: A region of storage with a type and a lifetime; each object of class type has its own copy of the non-static data members. D2, R5
Data member
Simple words: A variable that lives inside each object. Analogy: The portions sitting on that shelf. Precise: A variable declared inside a class; every object has its own (here portions_ and capacity_). D2
Member function
Simple words: A function that belongs to a class and works on one object. Analogy: A task only the station's cook may do, such as "take portions". Precise: A function declared inside a class, called on an object (soup.take(4)); inside it, the members of that object are directly visible. D1, D2
Access specifier (public, private)
Simple words: Labels that say who may use a member. Analogy: The counter in front of the shelf: customers talk to the cook (public) but cannot reach the shelf (private). Precise: public members can be named anywhere; private members only inside the class's own member functions (and friends); the compiler rejects other uses, as R3 shows. D2, R3
Class invariant
Simple words: A rule about an object's data that is true whenever someone outside can look. Analogy: The rule card taped to the shelf. Precise: A condition on the data members that the constructor establishes and every public member function preserves; it may be broken briefly inside a member function but must hold again when the function returns. See also the general invariant of MA102. D1, D3
Constructor
Simple words: The special function that sets up a new object. Analogy: The set-up checklist done before the station opens. Precise: A member function with the class's name and no return type, run when an object is created; it should establish the invariant or refuse to create the object (here by throwing an exception, explained in F2-16). F2-10 covers constructors in depth. D1, D2
Strong type
Simple words: A tiny class that wraps one number so it cannot be confused with a different kind of number. Analogy: Putting grams on a scale and portions on a tally board, so nobody reads one as the other. Precise: A class such as Portions holding one int, with an explicit constructor, so that the compiler rejects passing a Grams where a Portions is required (R4). D3, R4

Layer 1 — the kid explanation

A struct from SP101 (F2-06) is like an open shelf. It groups things that belong together, such as a name and a number. But anyone can change anything on it. If one part of the program writes a wrong number, nothing stops it.

A class is a shelf with a rule card and a counter. You write the rule first, for example "portions are never below 0 and never above the capacity". Then you hide the data behind the counter with the word private. Finally you write the only ways in: functions such as "take 4 portions" or "add 5 portions". Each of these functions checks the rule before it changes anything.

When someone asks for 13 portions and there are only 10, the function says no and changes nothing. The rule stays true. When someone tries to reach behind the counter, the compiler itself refuses to build the program. You do not have to remember the rule at every place in your program; the class remembers it for you.

The rule card has a name: the invariant. "Invariant" means "does not vary": it is true when the object is made, and true again after every job the cook finishes.

Layer 2 — the student explanation

The problem: a struct cannot protect its own rule

Listing 1 stores soup stock in a plain struct. All members of a struct are public by default, so main can subtract 13 from 10 directly. The run printed soup: -3 of 20, rule holds: 0: the program kept running with a stock that cannot exist. A helper function rule_holds can detect the problem afterwards, but nothing prevents it. R1, D2

The fix: private data, public operations, one invariant

Listing 2 turns the struct into a class. Four decisions make it safe. First, the invariant is written as a comment above the class: 0 <= portions_ <= capacity_, and capacity_ > 0. Second, the data members are under private:, so only the class's own member functions can name them. Third, the constructor checks the starting values and refuses to create an object that would break the invariant. Fourth, every function that changes data checks first and either keeps the invariant or changes nothing and returns false. D1, D3

The run shows each decision working. take(13) with 10 portions was refused and the stock stayed at 10. add(15) with 6 of 20 was refused because only 14 fit. take(-2) was refused because a negative request would secretly add portions. A Stock("bread", 30, 20) was never created: the constructor threw std::invalid_argument and main printed construction refused: Stock: bad starting values for bread. Every line of the run ends with invariant holds: 1. R2

What private really means

Listing 3 tries soup.portions_ = -3; from main. The build failed with error: 'int Stock::portions_' is private within this context and a note pointing at the declaration. Access control is checked by the compiler when it reads your source; it is not a run-time lock. That is exactly what you want: a mistake is found before the program exists. R3, D2

In C++ the only difference between struct and class is the default access: public for struct, private for class. A common convention, recommended by the C++ Core Guidelines, is to use struct when the members can vary independently (no invariant) and class when there is an invariant to protect. D2, D3

Read-only member functions

Functions such as portions() const end with the word const. It promises that calling them does not change the object, which is why report can call them on a const Stock&. F2-12 explains references and const in full; for now, read const Stock& s as "look at the caller's stock without copying it and without changing it". D1, R2

Layer 3 — the engineer's depth

When the invariant must hold

An invariant does not have to be true at every instant. Inside take, between the check and the subtraction, the object is "in the middle of a job". The contract is that the invariant holds at the end of the constructor and at the end of every public member function, which are the only moments outside code can observe the object. This is why a class whose members can be set one by one through "setters" usually has no meaningful invariant: each setter would have to accept states that only make sense together. D1, D3

Three ways to refuse a bad request

Listing 2 uses two of them. A request that can fail in normal use (asking for more soup than there is) returns false and changes nothing. A request that should never happen (building a stock that cannot exist) throws an exception, so no broken object is ever created. A third option, stopping the program with an assertion (F2-08), fits checks of your own logic in tests. F2-16 compares these strategies properly; the rule of thumb here is "never leave the object half-changed". D1, D3

Strong types: invariants about meaning

Some rules are not about ranges but about meaning: 500 grams of flour is not 500 portions. Listing 4 wraps each in its own small class with an explicit constructor. Passing a Grams to serve(Portions) failed to compile with could not convert 'flour' from 'Grams' to 'Portions'. The systems curriculum asks for exactly this technique later, as "strong types for physical vs virtual addresses" in kernel code, where mixing two kinds of address is a classic bug. R4, D4

Note

The word explicit stops the compiler from converting a plain int into a Portions behind your back, so serve(500) would also be rejected. F2-10 shows the conversion rules for constructors. D2

How the hardware actually does it

The processor knows nothing about classes, private or invariants. Listing 5 shows what remains after compiling: sizeof(PlainPair) and sizeof(CheckedPair) both printed 8, which is two times sizeof(int) = 4 on this machine. The member functions did not make the object bigger. Each object holds only its data; the code of take exists once in the program and works on whichever object it is called for. R5

How does one copy of take know which object to change? The compiler passes the address of the object as a hidden extra argument, available inside the function as the pointer this. a.take(4) and b.take(1) call the same machine code with different addresses, which is why the run printed 6 for a and 2 for b. Access control leaves no trace at all in the machine code: it was checked at compile time and is gone. R5, D1, D2

Not verified — check before relying on this

How this is passed at machine level (which register) is fixed by the platform's calling convention, the System V AMD64 psABI together with the Itanium C++ ABI on this machine. That was not checked in this build; SP301 (F2-47) reads those documents. Sizes of int and of classes differ between platforms; the 4 and 8 above are this machine's numbers only. R5

Worked example

Design a class from a specification, the way the practical exam asks. Specification: "A restaurant table has a number and a fixed number of seats. Groups of guests sit down and leave. A table never holds more guests than seats."

  1. Write the invariant first. seats_ >= 1 and 0 <= guests_ <= seats_. A table with zero seats makes no sense, so it is part of the rule.
  2. Choose the data. number_, seats_, guests_, all private. Free seats are computed (seats_ - guests_), not stored, because a second stored number could disagree with the first.
  3. Constructor. Table(int number, int seats) sets guests_ to 0 and throws if seats < 1. Check: after it returns, 1 ≤ seats and 0 ≤ 0 ≤ seats. The invariant holds.
  4. Operations. seat(n): allowed only if 1 <= n <= seats_ - guests_; then guests_ + n <= seats_, so the invariant holds. leave(n): allowed only if 1 <= n <= guests_; then guests_ - n >= 0.
  5. Predict a test by hand. Table 4 with 6 seats: seat 4 → true, 2 free. Seat 3 → false, still 2 free. Leave 5 → false. Leave 4 → true. Table with 0 seats → exception.

The lab's reference solution table_lab.cpp runs exactly these cases and printed table tests: 0 failures. R6

Where the analogy breaks


    

  • A real counter stops people while the restaurant is open. private stops nobody at run time: it is a compile-time rule, and the machine code has no trace of it (Figure 2). A program can still damage an object's bytes through a bad pointer (F2-19); private protects against honest mistakes in source code, not against memory corruption. R3, D2
    • 

  • A real station has one cook. A class's member functions can be called by any number of callers, and in later courses by several threads at once (SP203); then two "cooks" can be inside take at the same time and the invariant needs a lock as well. D1
    • 

  • A rule card can be read by anyone. The invariant of a C++ class is only a comment unless you also write code that checks it, such as invariant_holds() and the tests of the lab. R6
    •

Summary


    

  • A class bundles data with the only functions allowed to change it.
    •

  • private is checked by the compiler; reaching private data from outside does not compile.
