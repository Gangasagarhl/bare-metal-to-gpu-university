Story hook

Analogy

The kitchen has a recipe card that says: "Stir-fry with ______. Heat oil, add ______, stir for four minutes, season." Kofi fills the blank with tofu on Monday, with mushrooms on Tuesday, with chicken on Wednesday. One card, three dishes. When the blank is filled, the card becomes a real recipe, and only then can anyone check that it makes sense: "stir-fry with ice cream" fails the moment someone tries it.

Above the pass hangs the order rail: a loop of four clips. New tickets go on the next free clip; the cooks always take the oldest ticket. When the last clip is reached, the next ticket goes back to the first clip, if it is free. Nobody ever moves the tickets along the rail. It works the same whether the clips hold paper tickets, numbers or names.

In C++ the card with a blank is a template, and the order rail is the ring buffer you will write as this course's lab: one piece of code that works for any type you fill in.

What you will be able to do

  • Write function templates and class templates, and explain how the compiler fills in the template parameters (deduction and instantiation).
  • Write a generic ring buffer RingBuffer<T, N> with an invariant, a static_assert and tests for several types.
  • Read template error messages, and use a C++20 concept to state what a type must support.
  • Show from the compiled object file that each instantiation is a separate function.
  • Diagnose a ring buffer that serves tickets out of order after wrap-around.
Jargon box
Template
Simple words: Code with a blank that the compiler fills in with a type or a number. Analogy: A recipe card "stir-fry with ______". Precise: A declaration introduced by template <...> that defines a family of functions or classes, parameterised by types or values. D1, D2
Template parameter
Simple words: The blank in a template. Analogy: The empty line on the card. Precise: A name declared in the template's parameter list: a type parameter (typename T) or a non-type parameter such as std::size_t N. D2
Instantiation
Simple words: The compiler writing the real code for one filled-in blank. Analogy: Writing out "stir-fry with tofu" as a real recipe. Precise: The generation of a concrete function or class from a template for specific arguments, for example larger<int>; each instantiation is separate code (R6 lists three). D2, R6
Template argument deduction
Simple words: The compiler working out what to put in the blank from the values you pass. Analogy: Seeing tofu in the pan and knowing which card version is meant. Precise: For a function template call without explicit arguments, the compiler deduces the template arguments from the argument types; conflicting deductions are an error (R2). D2, R2
Concept
Simple words: A named rule for what a type must be able to do. Analogy: A note on the card: "fill only with something that can be fried". Precise: A C++20 named set of requirements on template arguments, such as std::totally_ordered; a template constrained by a concept is not used for types that fail it, and the error says which requirement failed (R4). D2, R4
static_assert
Simple words: A check that runs while compiling. Analogy: The head chef refusing a card with an impossible blank before anyone cooks. Precise: A declaration static_assert(condition, message); if the constant condition is false, compilation fails with the message (R8). D2, R8
Ring buffer
Simple words: A queue in a fixed number of slots that wraps around from the last slot to the first. Analogy: The loop of clips on the order rail. Precise: A first-in, first-out buffer of capacity N stored in an array; a head index marks the oldest element and a count (or tail index) marks how many are stored; indices advance modulo N. D3, R7

The idea in pictures

Layer 1 — the kid explanation

Sometimes you write the same function three times: "the larger of two whole numbers", "the larger of two decimal numbers", "the later of two words in the dictionary". The steps are identical; only the kind of value changes. A template lets you write the steps once, with a blank for the kind of value. When you use it with whole numbers, the compiler writes the whole-number version for you.

The same works for a whole class. An order rail for numbers and an order rail for names follow the same rules: put the new one on the next free clip, take the oldest one first, wrap around at the end. So you write RingBuffer once, with two blanks: what it holds, and how many clips it has.

The compiler checks each filled-in version separately. If you fill the blank with something that cannot do what the steps need, such as comparing two orders that have no "smaller than", the compiler stops and tells you, before the program ever runs.

Layer 2 — the student explanation

Function templates

Listing 1 defines template <typename T> T larger(T a, T b). In larger(3, 8) the compiler deduces T = int from the arguments; in larger(2.5, 1.25), T = double; with two std::strings, T = std::string, where < compares alphabetically. The run printed 8, 2.5 and soup. R1, D2

Deduction must agree. larger(3, 2.5) asks for T = int from the first argument and T = double from the second; R2 shows deduced conflicting types for parameter 'T' ('int' and 'double'). You can always choose T yourself: larger<double>(3, 2.5) converts 3 to 3.0 and printed 3. R2, R1

Template errors and concepts

A template's body is checked for a type only when it is instantiated with that type. In Listing 3, larger(x, y) with a struct Order that has no < failed with In instantiation of 'T larger(T, T) [with T = Order]' and no match for 'operator<', pointing inside the template. For bigger templates such messages get long, because they report where in the template's code the type failed. R3, D2

C++20 lets you state the requirement up front with a concept. Listing 4 writes template <std::totally_ordered T>. Now the error is reported at the call: no matching function for call to 'larger(Order&, Order&)' with constraints not satisfied, followed by the chain of requirements that failed, ending in the required expression '(__t == __u)' is invalid. The message is longer here, but it names the broken requirement and points at the caller, not at the template's internals. R4, D2

A class template: the ring buffer

Listing 5 is the course's ring buffer: template <typename T, std::size_t N> class RingBuffer. T is the element type and N, a non-type template parameter, is the capacity, known at compile time. The data lives in a std::array<T, N> inside the object, so the buffer never allocates memory. The invariant is count_ <= N and head_ < N, with the oldest value at data_[head_]. push writes at (head_ + count_) % N and refuses when full; pop reads at head_, advances head_ modulo N, and refuses when empty. Both follow the rule of F2-09: refuse without changing anything. D3, R7

The test file instantiates RingBuffer<int, 4>, RingBuffer<std::string, 2> and RingBuffer<double, 8> and printed RingBuffer tests: 0 failures, including the wrap-around case of Figure 1. A static_assert(N > 0, ...) rejects a buffer with no room at compile time: RingBuffer<int, 0> failed with static assertion failed: RingBuffer needs room for at least one value and the comparison reduces to '(0 > 0)'. R7, R8

Note

Templates usually live entirely in header files, as ring_buffer.h does. The compiler needs the full template body wherever it instantiates it, which is in every .cpp file that uses it (F2-07 explained headers and source files). D1, D2

Layer 3 — the engineer's depth

Compile-time knowledge as a tool

Because N is a compile-time constant, capacity() can be static constexpr: the test uses RingBuffer<double, 8>::capacity() without any object. Facts known at compile time can be checked at compile time. The systems curriculum asks for exactly this in driver code: register descriptions as constexpr values and "static assertions on structure offsets taken from specs", so that a wrong layout fails the build instead of corrupting a device. static_assert(N > 0) is the same idea at small scale. R7, D4

What the ring buffer asks of T

Every template silently requires something of its parameters. RingBuffer value-initialises its array (data_{}), so T must be default-constructible; push and pop copy-assign, so T must be copy-assignable. A non-copyable File from F2-13 would therefore fail to instantiate push. Write the requirements in a comment, and from C++20 consider a concept such as std::copyable. A move-friendly version (push(T&&) moving the value in, pop moving it out) is a lab extension. D2, D3

Why "% N" and not a power of two trick

Some ring buffers require N to be a power of two so that "modulo N" becomes a bit mask (MA102's masks). That is a performance choice with its own invariant; this course's version keeps the general % so that any capacity works, and leaves measurement to SP302. D3

Not verified — check before relying on this

Whether a compiler turns % N into a mask or a cheaper sequence for a constant N was not inspected in this build. Read the generated assembly (SP202, F2-32 "Reading compiler output") before claiming any speed difference.

How the hardware actually does it

There are no templates in machine code. The compiler writes one ordinary function per set of template arguments it needs. The lab folder's run.sh compiled Listing 1 to an object file and listed its symbols with nm -C, keeping the lines for larger: R6



Three separate functions exist: larger<int>, larger<double>, and larger<std::string> (spelled out in full as std::__cxx11::basic_string<...>). The call larger<double>(3, 2.5) reused larger<double>, so there is no fourth. The letter W is nm's mark for a "weak" symbol: because every .cpp that uses larger<int> produces its own copy, the linker is allowed to keep just one. R6, D5


The ring buffer's storage is just as plain: a RingBuffer<int, 4> is an array of four ints and two std::size_t counters inside the object, wherever the object lives. Each different N is a different type with its own code, which is the price of knowing the capacity at compile time: many different capacities mean more machine code. D2, D1



Not verified — check before relying on this
The meaning of nm's symbol letter W (weak) and the linker's rule for merging identical template instantiations come from the GNU Binutils documentation and the ELF specification by title only; SP301 (F2-43, F2-44) reads them. D5

Where the analogy breaks


    

  • A cook reads the card with the blank and fills it in at the stove. The compiler fills in templates while compiling; at run time there is no template left, only the instantiated functions (R6). You cannot choose T from user input at run time. R6
    • 

  • One card in the kitchen stays one card. One template can become many separate functions in the program, one per type and per value of N, which makes the program larger. R6, D1
    • 

  • On a real rail you can see which clips are empty. The ring buffer cannot: a "free" slot still holds an old value (or a default one); only head_ and count_ say which slots are in use. That is why the invariant, not the slot contents, defines the buffer. R7

Transition box

Where you came from: F2-09 to F2-13 built classes for one specific type, with invariants, RAII and copy/move. What carries over: everything; a class template is a class with blanks, and it needs the same invariant, the same tests and the same decisions about copying. Summary


    

  • A template is code with blanks for types or values; the compiler instantiates it for each set of arguments.
    • 

  • Function template arguments are usually deduced; conflicts are errors; you can give them explicitly.
    • 

  • A template body is checked per instantiation; concepts state requirements and move errors to the call.
    • 

  • Non-type parameters such as N are compile-time values; static_assert checks them while compiling.
    • 

  • RingBuffer<T, N>: invariant count_ <= N, head_ < N; write at (head_ + count_) % N; always test the wrap-around.
