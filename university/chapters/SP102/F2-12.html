Story hook

Analogy

Jonas is cooking a big pot of stew. Mei wants to check the taste. There are three ways to let her.

He could ladle a bowl of stew for her. She can salt her bowl as much as she likes; the pot does not change. That is a copy, and for a big pot it is a lot of ladling.

He could say, "The pot on burner two, you may stir it." Now Mei works on the very same pot. If she adds salt, the stew is saltier for everyone. That is a reference: a second name for the same pot.

Or he could say, "The pot on burner two, look and taste, but do not add anything." That is a const reference: the same pot, no copy, and a promise not to change it.

One more thing can go wrong. If Mei writes "pot on burner two" on a note and comes back after the pot was moved to another burner, the note now points at an empty burner. That is a dangling reference, and in C++ nothing warns you before you taste.

What you will be able to do

  • Explain what a reference is and how it differs from a copy, and prove "same object" with a program.
  • Choose between passing by value, by reference and by const reference for each parameter, and justify the choice by cost and by intent.
  • Write const member functions and read the compiler errors that enforce const.
  • Recognise two ways a reference outlives its object (returning a local, holding a vector element across push_back) and diagnose one from an AddressSanitizer report.
Jargon box
Reference
Simple words: A second name for an object that already exists. Analogy: "The pot on burner two": not a bowl of stew, but a way to reach the pot itself. Precise: A declaration such as int& r = x; makes r an alias for the object x; it must be initialised, cannot be re-bound to another object, and every use of r uses x (R1 prints "same object: 1"). D1, D2, R1
Pass by value
Simple words: The function gets its own copy of the argument. Analogy: A bowl ladled from the pot. Precise: The parameter is a new object initialised from the argument (for class types, by the copy constructor); changes to it do not affect the caller (R1, R2). D2, R2
Pass by reference
Simple words: The function works on the caller's own object. Analogy: Stirring the actual pot. Precise: The parameter has reference type (T&) and is bound to the argument; no copy is made, and changes are visible to the caller. D1, R1
const
Simple words: A promise that something will not be changed, checked by the compiler. Analogy: "Look and taste, but add nothing." Precise: A type qualifier; an object or reference declared const cannot be modified through that name, and the compiler rejects attempts (R3). See also const as first met in KID102. D2, R3
const reference
Simple words: A second name you may only read through. Analogy: Tasting from the pot with a promise not to add anything. Precise: A reference of type const T&; it avoids a copy and forbids modification through it; it can also bind to temporaries. D1, D2
const member function
Simple words: A member function that promises not to change its object. Analogy: The cook's "check the stock" job, which only looks. Precise: A member function declared with const after its parameter list; inside it, the object is treated as const; only const member functions can be called on a const object or through a const reference (R3). D2, R3
Dangling reference
Simple words: A reference to an object that no longer exists. Analogy: A note saying "pot on burner two" after the pot was moved. Precise: A reference whose object's lifetime has ended; using it is undefined behaviour (R5: AddressSanitizer reports heap-use-after-free). D2, R5
Undefined behaviour
Simple words: Something the C++ rules do not allow, so anything may happen, including "seems to work". Analogy: Tasting from an empty burner: maybe nothing, maybe someone else's dish. Precise: Behaviour for which the standard imposes no requirements; SP201 (F2-23) treats it in depth. D2

The idea in pictures

Figure 1 shows what each kind of parameter means for the caller's object. Only "by value" makes a new object; both kinds of reference reach the caller's object directly.

Layer 1 — the kid explanation

When you give a function a value, it usually gets a copy. It can change its copy, but your value stays the same. That is safe, but copying a big thing, like a menu with a thousand dishes, takes time.

A reference is a second name for something that already exists. If a function gets a reference, it works on your thing itself. That is useful when the function's job is to change your thing, like "restock these dishes". It also avoids the copying.

Often you want "no copy" and "no changes" at the same time. Then you use a const reference: the function may look but not touch. The compiler checks the promise for you, so a mistake becomes a compiler error instead of a strange result.

A reference has one danger. It does not keep the thing alive. If the thing goes away, the reference still points where it used to be. Using it then is like tasting from an empty burner.

Layer 2 — the student explanation

A reference is an alias

In Listing 1, int& also_soup = soup; declares a reference. Assigning 15 to also_soup changed soup, and comparing their addresses printed same object: 1. A reference must be initialised when it is declared and always refers to the same object afterwards; there is no "empty" reference and no way to make it refer to something else. R1, D2

Three kinds of parameter

The run shows the three kinds of parameter side by side. discount_copy(int price) changed its own copy, and soup was still 15. discount_ref(int& price) changed the caller's variable: 13. with_tax(const int& price) read the value and returned 14 without changing it. R1

For a class type, passing by value runs the copy constructor (F2-10). Listing 2 counts those copies for a Menu with 1,000 dishes: ten calls by value made 10 copies of all 1,000 dishes; ten calls by const reference made 0 copies. The function that only reads gets nothing from the copy, so it pays for nothing. R2

A practical rule, following the C++ Core Guidelines: pass small, cheap-to-copy types such as int and double by value; pass larger objects you only read by const&; pass by & (non-const) only when the function's job is to change the caller's object, and make that visible in the function's name. D3

const is enforced by the compiler

Listing 3 breaks two const promises. Calling take through a const Stock& gave error: passing 'const Stock' as 'this' argument discards qualifiers, because take is not a const member function; portions(), declared const, was accepted. Assigning to a const int gave assignment of read-only variable 'tables'. Mark every member function that does not change the object as const; otherwise it cannot be used through a const reference at all. R3, D2

When the object goes away first

A reference does not keep its object alive. Two common ways to outlive the object:

  • Returning a reference to a local variable. Listing 4's local string dies at the function's closing brace. GCC caught this one: reference to local variable 'special' returned [-Werror=return-local-addr]. R4
  • Holding a reference into a std::vector while it grows. When push_back needs more room than the vector's capacity, the vector moves its elements to a new, larger block of memory and frees the old one; references to the old elements then dangle. No compiler warning appears; the forensic lab shows what AddressSanitizer reports at run time. D2, R5

Layer 3 — the engineer's depth

const references and temporaries

A const T& parameter can bind to a temporary value, for example with_tax(12) or a function taking const std::string& called with "soup"; a non-const T& cannot, because changing a temporary that is about to disappear would almost always be a mistake. This is part of why const& is the default for read-only parameters. The small listing below tries it with a non-const reference and was refused: D1, D2, R10

const correctness spreads


Once one function takes const Menu&, every member function it calls on the menu must be const. Adding const late to a large codebase therefore cascades through many files; adding it from the start costs nothing. This is called "const correctness". It also documents intent: a reader sees from the signature which functions can change what. D3


Which operations invalidate references


Each standard container documents which operations "invalidate" references, pointers and iterators to its elements. For std::vector, an insertion that exceeds the capacity invalidates all of them; R5 shows the capacity going from 2 to 4 on the third push_back, and the old block being freed. Holding an index instead (Listing 6) survives the move, because the index is re-applied to the new storage. F2-15 extends the same rule to iterators. D2, R5, R6


Not verified — check before relying on this
The growth from capacity 2 to 4 is what this standard library (libstdc++ of GCC 13.3) did in R5. The C++ standard requires that push_back takes amortised constant time, which forces some geometric growth, but it does not fix the factor; another library may grow differently. Check the sequence-container requirements in ISO/IEC 14882 before relying on a particular capacity. R5



How the hardware actually does it


The processor has no "reference" type. When a reference must be stored or passed, the compiler uses the object's memory address. Listing 7 shows the evidence: a struct holding an int printed size 4, a struct holding an int& printed 8, the same as a struct holding an int* pointer, which is an address on this 64-bit machine. Asking sizeof(r) of the reference itself gave 4, the size of the int it names: in the language, the reference simply is the object. R7, D2


This explains both the speed and the danger. Passing a const Menu& passes one address, whatever the size of the menu (R2's 0 copies). And a stored address does not know whether its memory was freed and reused; nothing in the hardware checks it. AddressSanitizer adds that check in software: it marks freed memory as poisoned in a "shadow" map and inserts a check before every memory access of the instrumented program, which is how R5 caught the read. R5, D4



Not verified — check before relying on this
The description of AddressSanitizer's shadow memory and redzones is from the GCC and Clang sanitizer documentation by title only; it was not opened in this build. What is verified is the behaviour in R5: the read was reported with the allocation and free stacks. R5

Where the analogy breaks


    

  • "The pot on burner two" names a place. A C++ reference names an object; when the vector moves its elements, the reference does not follow the order to its new place, and it does not go back to "burner two" either: it is simply invalid (R5). R5
    • 

  • In the kitchen you can see that a burner is empty. In C++ a dangling reference looks exactly like a valid one; without a tool such as AddressSanitizer the read may even return the old value and "work", which is what makes it dangerous. D2, R5
    • 

  • "Look but do not touch" is a polite request between people. const is checked by the compiler on every use (R3), and it applies only through that name: another non-const name for the same object can still change it. R3, D2
    •

Summary


    

  • A reference is a second name for an existing object; it must be initialised and cannot be re-bound.
    • 

  • By value: a copy (costly for big objects). By &: change the caller's object. By const&: read without copying.
    • 

  • const is a compiler-checked promise; read-only member functions must be marked const.
    • 

  • A reference does not keep its object alive; returning a reference to a local, or holding one across a vector's reallocation, dangles.
    • 

  • Under the hood a stored reference is an address; AddressSanitizer checks such accesses at run time.
