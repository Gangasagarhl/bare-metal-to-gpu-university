Story hook

Analogy

Every station in the kitchen has two checklists on the wall. The opening list: switch on the stove, put out a clean board, fill the salt. The closing list: switch off the stove, wash the board, wipe the counter.

Amara, the new cook, follows the opening list perfectly. But on her first evening she leaves through the back door when her shift ends, and nobody does the closing list. The stove stays warm all night.

The head chef, Lucía, changes the rule. "From now on, the closing list is not your job to remember. When a shift ends, however it ends, the closing list runs." In the kitchen that needs a person watching the door. In C++ the compiler does it for you: every object runs its opening list when it starts and its closing list when its scope ends. Those lists are the constructor and the destructor.

What you will be able to do

  • Write constructors with member initialiser lists and default member initialisers, so no member is ever left unset.
  • Predict exactly when constructors and destructors run, including the reverse order of destruction, and check the prediction with a tracing class.
  • Explain why members are initialised in declaration order, and read the -Wreorder error that catches a mismatch.
  • Use explicit, = default and = delete to say which constructors and copies a class allows.
  • Diagnose a "closed twice" bug caused by an implicit copy, from a log.
Jargon box
Destructor
Simple words: The special function that cleans up when an object's life ends. Analogy: The closing checklist of a station, which runs whenever the shift ends. Precise: A member function named ~ClassName(), with no parameters and no return type, called automatically at the end of the object's lifetime; for a local object, when control leaves its block by any path. D1, D2, R1
Lifetime
Simple words: The time from when an object is ready until it is cleaned up. Analogy: A station's shift, from the opening list to the closing list. Precise: The period from the end of the object's initialisation (its constructor finished) to the start of its destruction; a local object's lifetime ends when its enclosing block is left. D2
Scope (block scope)
Simple words: The part of the program between a pair of braces where a name can be used. Analogy: One room of the kitchen: what you set up in the room is cleared when you leave it. Precise: The region of source text in which a declaration is visible; for a local variable, from its declaration to the closing brace of the block. D2
Member initialiser list
Simple words: The list after the colon in a constructor that gives each member its first value. Analogy: Setting each piece of equipment correctly as you put it on the station, instead of putting it wrong and fixing it later. Precise: The : a_(x), b_(y) part of a constructor definition; it initialises members before the constructor body runs. D1, D2
Default member initialiser
Simple words: A starting value written next to the member itself. Analogy: A label on the shelf saying what goes there if nobody says otherwise. Precise: An initialiser in the member's declaration (int portions_ = 1;), used by any constructor that does not initialise that member in its own list. D2, R3
Default constructor
Simple words: The constructor used when you make an object without giving any values. Analogy: The standard opening list when nobody asks for anything special. Precise: A constructor that can be called with no arguments; Order() = default; asks the compiler to generate it. D2
Copy constructor
Simple words: The constructor that makes a new object as a copy of an existing one. Analogy: Photocopying an order ticket. Precise: A constructor taking const T&; if you do not declare one, the compiler generates one that copies each member, which is used, for example, when an object is passed by value. F2-13 treats copying in depth. D2, R5
Deleted function (= delete)
Simple words: A way to say "this operation is forbidden" so the compiler refuses it. Analogy: A sign on the photocopier: "Do not copy tickets." Precise: A function declared with = delete; any use of it is a compile error (R7). D2, R7

Layer 1 — the kid explanation

When you make an object, its opening checklist runs first. That checklist is the constructor. It puts every piece of data in a good starting state, so the object's rule (its invariant from F2-09) is true from the very first moment.

When the object is no longer needed, its closing checklist runs. That is the destructor. You never call it yourself. The object lives inside a pair of braces, and when the program leaves those braces, the destructor runs. It does not matter whether the program reached the closing brace, jumped out early with return, or left because of an error.

If you open several stations in one room, they close in reverse order: the last one opened is the first one closed. Think of a stack of trays. You put tray a down, then b, then c; you take c off first. This order matters when one object uses another: the one that was built later may still need the earlier one while it closes.

Layer 2 — the student explanation

Construction and destruction order

Listing 1 defines a class Tracer whose constructor prints construct and whose destructor prints destroy. The run R1 shows the rules. In the inner block, b was constructed before c, and after "inner block ends" the output says destroy c then destroy b: reverse order, at the closing brace. Object a, declared at the top of main, was destroyed last, after "main ends". R1, D2

A class with members adds one more rule. For Station, the run printed construct board, construct stove, and only then Station constructor body runs. Members are initialised before the constructor body, in the order they are declared in the class. On the way out the order reverses: the destructor body runs first, then stove_, then board_. So inside the constructor body and the destructor body, every member is alive and usable. R1, D2

Initialise members, do not assign them

A constructor's member initialiser list (: board_("board"), stove_("stove")) creates each member directly with its value. Assigning in the body instead would first create the member with a default value and then overwrite it, and it is impossible for members that have no default, such as a Tracer that needs a name. D1, D3

The list does not choose the order: declaration order does. Listing 2 writes the list as capacity_(capacity), free_(capacity_) but declares free_ first, so free_ would be initialised from capacity_ before capacity_ has a value. With the course flags the build failed: 'Shelf::capacity_' will be initialized after [-Werror=reorder], followed by member 'Shelf::capacity_' is used uninitialized [-Werror=uninitialized]. Keep the list in declaration order and never read a member that is declared later. R2, D4

Default member initialisers and several constructors

Listing 3 gives every member of Order a default member initialiser (int table_ = 0;, std::string dish_ = "none yet";, int portions_ = 1;). Then each constructor initialises only what it receives, and the rest takes the default. The run printed table 0, dish 'none yet', portions 1 for Order empty; and table 7, dish 'none yet', portions 1 for Order for_table(7);. No constructor can forget a member. Order() = default; asks the compiler to write the default constructor for you. R3, D2

The constructor Order(int table) is marked explicit. Without it, C++ would let a plain int turn silently into an Order wherever an Order is expected, for example print_order(7). A one-argument constructor should be explicit unless that silent conversion is really wanted. D3, D2

The constructor you did not write

If you do not declare a copy constructor, the compiler generates one that copies every member. It runs, for example, when an object is passed to a function by value. For most classes that is right. For a class whose destructor does something, such as closing a ticket, it means the copy's destructor does it too. The forensic lab shows the result: two closes for one ticket. The cure is either to forbid copying with = delete or to define what a copy means; F2-13 explains both. R5, R6, D3

Layer 3 — the engineer's depth

The special member functions

C++ has six special member functions that the compiler can generate: the default constructor, the destructor, the copy constructor, copy assignment, the move constructor and move assignment. Declaring some of them changes whether the compiler generates the others. The C++ Core Guidelines summarise the safe approaches as the "rule of zero" (declare none and let members such as std::string do the work) and the "rule of five" (if you must declare one of the copy, move or destructor operations, think about all five). F2-13 applies them. D2, D3

A constructor that cannot finish

If a constructor throws (as Stock's did in F2-09), the object never starts its lifetime, so its destructor does not run; but the members that were already fully constructed are destroyed. This is why a class should hold each resource in its own member object that cleans up after itself, the idea of F2-11. D2, D1

Destructors should not fail

A destructor may run while an exception is already travelling up the stack (F2-16). If it throws a second exception then, the program is terminated. Destructors are therefore implicitly noexcept unless declared otherwise, and the guidelines say a destructor must not fail. Report clean-up problems another way, for example through a separate close() function that returns an error. D2, D3

Note

Objects defined outside any function (globals) are constructed before main starts and destroyed after it returns. In a kernel there is no C++ runtime to do this; the curriculum (section 1.2, "Global constructors") explains that your early start-up code must call the compiler's table of initialiser functions itself. You will meet that again in SP301 (F2-48). D5

How the hardware actually does it

The processor has no idea what a destructor is. The compiler turns "end of scope" into ordinary function calls at every place where control leaves the scope. Listing 1 was compiled without sanitizers and its main disassembled; keeping only the calls to Tracer, Station and the unwinder gave the output below (run R4). R4



Lines 1–8 are the normal path and match R1 exactly: three Tracer constructors (a, b, c), two destructors at the end of the inner block (c, b), the Station constructor and destructor, and finally a's destructor. Lines 9–14 are a second copy of destructor calls ending in _Unwind_Resume: this is clean-up code the compiler generated for the case where an exception leaves main part-way, so objects are destroyed on that path too. The objects themselves live in main's stack frame; the constructor and destructor are ordinary functions that receive the object's address as the hidden this argument (F2-09). R4, R1, D1

Where the analogy breaks


    

  • A closing checklist is done by a person who can skip it on a busy night. A destructor is called by code the compiler generated at every exit of the scope (R4); you cannot forget it, but you also cannot delay it: it runs at the closing brace, not "when convenient". R4
    • 

  • In the kitchen, photocopying a ticket does not make the copy "close" anything. In C++ every copy is a full object with its own destructor, so a copied ticket closes too (R5). The analogy hides this, which is exactly the forensic lab's bug. R5
    • 

  • Stations can close in any order the chef likes. Objects in one scope always end in reverse order of construction; you choose the order only by the order of declarations. R1, D2
    •

Transition box

Where you came from: F2-09 wrote classes whose constructor checks the invariant. What carries over: private data, the invariant, checking constructors and tests that print FAIL lines. What changes: you now control the whole life of an object: how it starts (initialiser lists in declaration order, defaults, explicit), when it ends (the closing brace, in reverse order, on every path) and whether it may be copied at all (= delete). R1, R2, R7 What comes next: F2-11 uses the destructor's "runs on every path" guarantee to make files and locks clean up after themselves: RAII.
