Final (F) — ungraded practice paper

Weight: none (ruling B6); marked out of 100 for feedback, and sat before the practical, which it prepares. Covers: all nine chapters, F0-20 to F0-28 (cumulative; level L1). Time: 90 minutes. Allowed: pencil and paper; no calculator, no notes, no computer. Marks: 100 points, 27 questions; the forensic question F27 is worth 12 and is marked with the forensic rubric of guide 11.2 (observation, hypotheses, evidence-based conclusion, fix and verification, prevention). Show your working: write every division ladder, every bit pattern with its place values, and every truth table in full. A right answer with no working gets half marks; a wrong answer with correct working gets most of them. Multiple-choice questions have exactly one right answer. Write binary numbers as eight bits unless the question says otherwise, and hex with the 0x prefix.

Part A — the decoding on paper (40 points)

  1. (6) Bits: write the first two status bytes, 0x5A and 0xE3, as eight bits each, with the bit numbers 7 to 0 written above the bits (F0-22, F0-25).
  2. (10) Fields: decode all five fields of both bytes. For each field, write the shift-and-mask expression you used, in the style (x >> 4) & 0b111, and the value it gives (F0-25). Write LEVEL both as a number and as its word.
  3. (6) Temperatures: read the TEMP bytes 0xF6 and 0x12 as signed bytes. Show the method for 0xF6 (flip and add one, or the "unsigned − 256" rule) and say why 0x12 needs no such step (F0-24).
  4. (6) Encoding: the controller must report ALARM 1, ZONE 2, PUMP 1, LID 0, LEVEL 3. Write that GSTAT byte in binary and in hex, showing each field in its place (F0-22, F0-25).
  5. (6) Masks: write three C++ expressions, one each: turn PUMP on in a byte x without touching the other bits; clear ALARM in x; test whether LID is open. Then apply them: turn PUMP on in 0xE3, clear ALARM in 0xE3, and test LID in 0x0D, giving each result in hex or as yes/no (F0-25).
  6. (6) Units: the controller sends one two-byte packet every 2 seconds. How many packets arrive in one day (86,400 s), how many bytes is that, and what is the size in KiB and in kB? Say which of the two unit names you would put on a memory-card label and why (F0-23).

Course project — 30 %

Goal. A binary-to-hex-to-decimal converter written in C++, with tests, as the course card says. The maths is this course's (F0-21 division ladder and doubling, F0-22 grouping and the base-16 ladder, F0-28 round-trip invariant); the C++ is learned in KID102 (functions, loops, std::string), so the project starts on paper during MA102 and is finished as a program during KID102. The F0-21 and F0-22 mini-projects (secret door code, colour of the week) and the F0-28 transition box are its starters.

Requirements

  • Functional. Three conversions in each direction: decimal → binary, decimal → hex, and text in binary or hex → decimal, each written as its own function. The program reads a number and a base from its input and prints the number in all three forms, with the 0x prefix on hex and uppercase A–F. Input that is not a digit of the stated base (a 2 in binary, a G in hex, empty text) is refused with a message, never guessed (F0-22). Numbers from 0 to at least 65,535 must work.
  • Tests. A test function that (1) checks the worked-example values of the chapters (45 = 101101, 200 = 11001000 = 0xC8, 0x2A = 42, 255 = 0xFF, 12 = 1100) and (2) checks the round-trip invariant of F0-28 for every number from 0 to 65,535: converting to binary and back, and to hex and back, must give the start number. The program prints how many round trips it tested and how many failed; the project is accepted only when that count is 0.
  • Quality. Builds with the course command (-Wall -Wextra -Wpedantic -Werror -fsanitize=address,undefined) with no warnings; one function per conversion; names that say what they hold (bits, placeValue, as in the chapters); a comment above each function stating its invariant or its rule (for example "new bit goes on the LEFT").
  • Honesty. The report shows the real output of the test run, copied, with the date and the compiler's version line; nothing is claimed that was not run (AH-21).

Constraints

No hardware beyond a home computer with the course compiler. About 8 hours of work: 2 hours on paper during MA102 (the conversion tables and the test list), 6 hours in KID102 (the program, run with the course build command or with university/labs/run_lab.sh on the project folder). One source file; no libraries beyond <iostream> and <string>. The reference solution (university/labs/MA102-P/converter_ref.cpp, 105 lines) shows the size expected.

Deliverables

  1. The source file of the converter, with its tests.
  2. A one-page report: the real output of the test run (copied, with date and toolchain), one paragraph per conversion saying which chapter method it uses, and one paragraph on the round-trip invariant: why "there and back gives the start" catches a reversed-bits bug (F0-21 forensic lab) but not every bug.
  3. A check sheet: ten numbers converted by hand (both directions, including one above 255 and one with a leading-zero nibble such as 0x0A) and compared with the program's output.
  4. A five-minute demonstration to a classmate or family member: convert a number they choose, then show the test count. They ask one question; you write down the question and your answer.

Milestones

  1. After F0-22 (during MA102): the conversion tables on paper: ten numbers in all three forms with the ladders shown (the F0-21 and F0-22 mini-project rubrics, 4 points each, are the gate).
  2. After F0-28 (end of MA102): the test list written on paper: the known values, the round-trip invariant stated as a sentence (start, step, conclusion, as in F0-28 Layer 2), and three bad inputs that must be refused.
  3. During KID102 (after its functions chapter, F0-34): the three conversion functions build and the known-value tests pass.
  4. End of KID102: the round-trip test over 0 to 65,535 reports 0 failures; the report, check sheet and demonstration are done.
