Story hook

Analogy

Luca and his grandmother Ines play a game with two jars of marbles: a red jar and a blue jar. On each turn, one of them moves some marbles from one jar to the other. The jars fill and empty, back and forth.

"Here's a riddle," says Ines. "After a hundred turns, how many marbles are there in total?" Luca does not need to watch the hundred turns. "Twenty," he says, "the same as at the start. We only move marbles. We never add or take any away."

Luca has found something that stays true while everything else changes. Engineers call that an invariant. When a program breaks an invariant, you know there is a bug, and the first broken step shows where to look. In this chapter you will learn to state invariants and to use them as bug detectors.

What you will be able to do

  • Explain what an invariant is, with an everyday example.
  • State an invariant for a simple process, such as moving marbles or converting a number to binary.
  • Check that an invariant is true at the start and is kept by every step, and use it to prove a result.
  • Use a parity (odd/even) invariant to show that some goals can never be reached.
  • Diagnose a bug by finding the first step where an invariant breaks (the forensic lab).
Jargon box
Invariant
Simple words: a sentence about a process that stays true at every step. Analogy: "the two jars together hold twenty marbles", whatever moves are made. Precise: a condition (a Boolean expression about the state, F0-27) that holds in the starting state and is preserved by every allowed step, so it holds in every state reached. W1
Loop invariant
Simple words: an invariant for a repeating part of a program. Analogy: the marble total checked after every turn of the game. Precise: a condition that is true before a loop starts and remains true after each pass of the loop body; together with the loop's stopping condition it proves what the loop computes. W1
Parity
Simple words: whether a number is odd or even. Analogy: whether the marbles can be paired off with none left over. Precise: the remainder of a whole number after dividing by 2: 0 (even) or 1 (odd); for a binary number it is the least significant bit (F0-21). W1
Invariant check
Simple words: a line in a program that tests the invariant and complains if it is false. Analogy: counting all the marbles after each turn. Precise: code that evaluates the invariant at chosen points and reports a failure; in larger C++ programs this can be written with assert (introduced in later courses). R1 D2 §19.3

Layer 1 — the kid explanation

Most things in a process change. Marbles move. Numbers get halved. Switches flip. An invariant is something that does not change. You say it as a sentence, and the sentence stays true at every step.

To be sure a sentence is an invariant, you check two things. First: is it true at the start? Second: if it is true before a step, is it still true after the step? If both answers are yes, it stays true forever, however many steps there are. It is like a row of dominoes: the first one falls, and each one knocks over the next.

Invariants are great bug detectors. If a program should keep "twenty marbles in total", let it count after every move. The first time the count is wrong, you know which move has the bug.

Invariants also answer "is this possible?" questions. Suppose you may only flip two switches at a time, and all eight start off. Can you end with exactly one switch on? Each move changes the number of "on" switches by 2, 0 or −2. So the number stays even. One is odd. So it can never happen, and you did not have to try every move.

Layer 2 — the student explanation

An invariant is a Boolean expression about the state of a process (the jars, the variables of a program). Proving that it is an invariant takes two steps. Start: show it is true in the starting state. Step: show that every allowed step, starting from any state where it is true, ends in a state where it is still true. Then it is true in every state the process can reach. W1

For the jars: at the start, red + blue = 12 + 8 = 20. A move of m marbles from red to blue changes red to red − m and blue to blue + m, and (red − m) + (blue + m) = red + blue. A move from blue to red is the same with the roles swapped. So red + blue = 20 is an invariant. W1

A loop invariant does the same job for a loop in a program. Listing 1 converts 45 to binary as in F0-21. Its invariant is: original = rest × placeValue + doneSoFar. Here rest is the part not yet converted, placeValue is the value of the next bit to write, and doneSoFar is the value of the bits already written. R1

  • Start: rest = 45, placeValue = 1, doneSoFar = 0, so 45 × 1 + 0 = 45. True.
  • Step: rest = 2 × (rest ÷ 2) + bit. The loop adds bit × placeValue to doneSoFar, doubles placeValue and halves rest. The new rest × placeValue + doneSoFar equals (rest ÷ 2) × 2 × placeValue + doneSoFar + bit × placeValue = rest × placeValue + doneSoFar, unchanged.
  • End: the loop stops when rest = 0. The invariant then says original = 0 + doneSoFar. So the bits written are worth exactly the original number: the conversion is correct.

The run of Listing 1 checks the invariant at every pass and prints "holds" seven times. W1 R1

Parity invariants are common. If every step changes a count by an even amount, the count's parity (its LSB) never changes. Then any goal with the other parity is impossible. W1

Layer 3 — the engineer's depth

Note

For the curious. The "start plus step" argument is mathematical induction: the Layer 2 proof for Listing 1 is one. A loop invariant, together with the condition that stops the loop, proves what a loop computes, as Layer 2 showed; a similar argument shows that a loop finishes at all (here, rest gets smaller at every pass, and a whole number above 0 cannot shrink for ever). W1 Larger systems state invariants about their data: "this list is always sorted", "this counter equals the number of items", and, in the concurrency courses, "only the thread holding the lock changes the shared data". In C++, invariant checks can be written with the assert macro from <cassert> D2 §19.3; Microsoft's documentation of its implementation says that a false condition prints a message naming the failed expression, the file and the line, and stops the program D4. It is introduced with the tooling in the systems programming courses.

How the hardware actually does it

Parity is used to catch mistakes in stored and sent data too. A group of bits has even parity if it has an even number of 1 bits and odd parity if it has an odd number, and Petzold describes parity as a form of error and consistency checking. D3 ch. 11 The idea: store one extra parity bit with each group of bits, chosen so that the number of 1s is always even (or always odd). If a single bit flips by accident, the count's parity changes and the check fails, so the error is noticed. W1 Whether a particular memory chip or connection uses parity, and how, is in its own documentation; the idea is the parity invariant of this chapter.

Worked example

The two-switch puzzle

Eight switches start off. A move flips exactly two different switches. Can you reach a state with exactly three switches on?

  1. Count the switches that are on: call it n. At the start, n = 0, which is even.
  2. A move flips two switches. Each flip changes n by +1 (off to on) or −1 (on to off). Two flips change n by +2, 0 or −2.
  3. Adding an even number to an even number gives an even number. So "n is even" is an invariant.
  4. Three is odd. So three switches on can never be reached.

Where the analogy breaks


    

  • Real marbles can roll under the sofa; program variables are changed only by the program. If Luca's total drops, a marble may be lost in the room. If a program's invariant breaks, the program itself changed something wrongly (or, much more rarely, the hardware failed). The program's bug is the first thing to look for. R2
    • 

  • Counting marbles is the check; in a program the check is extra code. Luca can see the jars. A program only checks an invariant if someone writes the check, and a check written wrongly can hide a bug. Keep checks simple and close to the definition.
    • 

  • An invariant can be true and still not enough. "Twenty marbles in total" stays true even if all the marbles end up in one jar when they should not. An invariant rules out some mistakes, not all; you choose invariants that capture what matters. W1

Forensic lab answer key


Observation: move 1 (+3) keeps the sum at 20. Move 2 (−2) drops it to 16. Move 3 (+4) keeps it at 16. Move 4 (−1) drops it to 14. Pattern: only negative moves break the invariant, and each loses twice the number of marbles moved. Hypotheses: (1) the starting values are wrong: ruled out, the first line shows 12 + 8 = 20; (2) the negative-move branch is wrong: supported, because every break happens on a negative move. Root cause: Listing 2, line 22, red = red + move;. For a negative move m, blue changes by m (line 21, correct: blue loses |m|), and red also changes by m, so red also loses |m|. Algebra: (red + m) + (blue + m) = red + blue + 2m, not red + blue. The line must be red = red - move;, giving (red − m) + (blue + m) = red + blue.
