Story hook

Analogy

The kitchen's tool wall has a new rule. When you take a tool, you hang a name tag on it: "Lucía has the big knife". When you leave the kitchen, the tool goes back on the wall by itself. If Lucía hands the knife to Omar, she does not copy the tag; she gives him the tag. There is never more than one tag on the knife, so it is always clear who returns it.

The bread recipe binder is different. Several cooks read it all evening. So the binder has a sign-out sheet instead of a tag. Each cook who needs it signs; each cook who is done crosses out their name. When the last name is crossed out, the binder goes back on the shelf. The pastry chef sometimes just looks at the sheet to see whether the binder is still out, without signing; if it has gone back, she knows not to go looking for it.

One night two cooks, Ana and Bo, each sign the other's apron sheet "until my partner leaves". At closing time neither can leave first. They are still in the kitchen in the morning. You will meet them again in this chapter's code.

What you will be able to do

  • Use std::unique_ptr and std::make_unique for single ownership, and transfer ownership with std::move.
  • Use std::shared_ptr, std::make_shared and std::weak_ptr for shared ownership and observation, and explain the reference count.
  • Choose between a value, a unique_ptr, a shared_ptr and a raw pointer or reference for a given relationship.
  • Implement a singly linked list whose nodes are owned through unique_ptr, with an iterative destructor.
  • Diagnose a shared_ptr cycle leak and a recursive-destruction stack overflow from sanitizer reports.
Jargon box
std::unique_ptr
Simple words: a pointer that is the one and only owner of its object. Analogy: a borrowed tool with exactly one name tag. Precise: a class template in <memory> that owns an object through a pointer and deletes it when the unique_ptr is destroyed or reset; it can be moved (transferring ownership) but not copied. D1 D2
std::make_unique
Simple words: "make one on the heap, already owned." Analogy: taking a tool and hanging your tag in one movement. Precise: a function template that constructs a T with new and returns a std::unique_ptr<T> owning it, so no raw new appears in your code. D1 D4
std::shared_ptr
Simple words: a pointer that shares ownership with others; the object goes away when the last one lets go. Analogy: the sign-out sheet on a shared binder. Precise: a class template that shares ownership of an object through a control block holding a use count; copying increments the count, destroying or resetting decrements it, and the object is destroyed when the count reaches zero. D1
Reference count (use count)
Simple words: the number of current owners. Analogy: the number of names not yet crossed out. Precise: the number of shared_ptr instances that share ownership of an object, reported by use_count(); it is kept in the control block and updated atomically so that copies in different threads are safe. D1
std::weak_ptr
Simple words: a pointer that can check whether a shared object still exists, without keeping it alive. Analogy: reading the sign-out sheet without signing it. Precise: a class template that refers to an object managed by shared_ptr without contributing to its use count; lock() returns a shared_ptr that is empty if the object has already been destroyed, and expired() tells whether it has. D1
Ownership cycle
Simple words: two or more objects that keep each other alive, so none is ever freed. Analogy: Ana and Bo, each waiting for the other to leave. Precise: a cycle of shared_ptr references among objects; after the last outside owner is gone, every use count in the cycle stays above zero, so the objects leak. Break it with a weak_ptr on one side. D1 D4
Linked list
Simple words: a chain of nodes where each node knows the next one. Analogy: order tickets clipped together, each clip holding the next ticket. Precise: a sequence container made of separately allocated nodes, each holding an element and a link to the next node (and in a doubly linked list, the previous one); insertion at a known position is constant time, access by index is linear. D3

Layer 1 — the kid explanation

A unique_ptr is a note with an owner's tag. It points to one heap object and promises: "when I go away, I clean it up". There is only ever one owner. You cannot photocopy the tag; you can only hand it over with std::move, and then your hands are empty.D1 R1

A shared_ptr is for things several parts of a program really share. It keeps a count of owners. Copying one adds an owner; when an owner goes away, the count goes down. When it reaches zero, the object is cleaned up.D1 R2

A weak_ptr watches a shared object without being an owner. Before using it, you ask "are you still there?". If two shared objects own each other, the count can never reach zero, and neither is ever cleaned up. A weak pointer on one side breaks that circle.D1 R3

Layer 2 — the student explanation

unique_ptr: single ownership, moved not copied

std::unique_ptr<T> owns at most one object. Its destructor deletes the object; reset(p) deletes the current object and takes p; get() returns the raw pointer without giving up ownership; release() gives up ownership and returns the raw pointer (now you must delete it).D1 Its copy constructor is deleted, so b = a does not compile; GCC's message for unique_copy.cpp says "use of deleted function … unique_ptr(const unique_ptr&)" (mistakes section).R6 Its move operations transfer ownership and leave the source empty, exactly the rules of F2-13.D1 Listing 1 traces this: after b = std::move(a), a tests false; passing std::move(b) into useAndReturn makes the parameter the owner, and the knife is returned when the function ends.R1

Create one with std::make_unique<T>(args): no new in your code, and no window in which a raw pointer exists without an owner.D4 With the default deleter a unique_ptr costs nothing extra in space: it was 8 bytes, the same as a raw pointer, in this build.R1 For arrays, std::unique_ptr<T[]> calls delete[], but std::vector<T> is almost always the better choice.D1 D4

shared_ptr: shared ownership with a count

Copies of a std::shared_ptr<T> share one object and one control block. The control block holds the use count (owners) and a weak count (observers); the object is destroyed when the use count drops to zero, and the control block itself when both counts are zero.D1 Listing 2 prints the count going 1 → 2 → 1, shows that a weak_ptr does not change it, and shows the recipe destroyed by first.reset(), after which the watcher reports "expired".R2 std::make_shared is the preferred way to create one; it can allocate the object and its control block together.D1 D4

Sharing costs more than single ownership: the shared_ptr object was 16 bytes in this build (two pointers), each copy updates the count, and the count's updates are atomic so that copies made in different threads stay correct (SP203).D1 R2 The atomic count makes copying and destroying the pointers thread-safe; it does not make access to the pointed-to object thread-safe.D1

Which owner?

The C++ Core Guidelines' order of preference, applied to this course:D4

  1. A plain value or a container member (no heap object of your own at all). Most objects should be this.
  2. std::unique_ptr when you need a heap object with one clear owner: a polymorphic object, a large object you move around, a node in a structure, an object whose lifetime outlives a scope.
  3. std::shared_ptr only when ownership is genuinely shared and no single owner's lifetime covers all users.
  4. A raw pointer or reference for using an object owned by someone else (function parameters, observers), never for owning.

Cycles and weak_ptr

In Listing 3 two cooks hold shared_ptrs to each other. When ana and bo go out of scope, each object's count drops from 2 to 1, never to 0: neither destructor runs ("goes home" never appears), and LeakSanitizer reports two leaked blocks of 64 bytes, allocated by make_shared at lines 17 and 18.R3 Changing one direction (here both) to std::weak_ptr breaks the cycle; cycle_fixed.cpp prints counts of 1 and both cooks go home.R3 Rule of thumb: in a structure with "parent" and "child" links, the parent owns the child and the child observes the parent.D4

A list built from unique_ptr

In the lab's OrderList, the list owns its first node and every node owns the next through a std::unique_ptr<Node> (Figure 2). pushFront moves the old chain into the new node, then the new node into head_; popFront moves head_->next into head_, which destroys the old head. No line of the list contains delete, and every node is freed exactly once.R4 One trap remains, and it is the forensic lab: the default destructor of such a chain is recursive.

Layer 3 — the engineer's depth

Recursive destruction. Destroying a node destroys its next member, which destroys the next node, which destroys its next member, and so on: the depth of nested destructor calls equals the length of the list.D1 For a long list this overflows the stack exactly like F2-20's recursion; deep_list.cpp survived 1000 nodes and crashed at one million with "stack-overflow", the trace full of Node::~Node() frames.R5 The fix is a destructor that unlinks nodes in a loop, so each node is destroyed with an empty next (Listing 4, lines 49–54); with it, a 200,000-node list was destroyed cleanly under the sanitizer.R4

Custom deleters. std::unique_ptr<T, D> calls D instead of delete, so it can own anything with a "release" function: a C library handle, a memory-mapped region, a block from your own allocator.D1 A stateless deleter type keeps the unique_ptr the size of a raw pointer; a function-pointer deleter makes it larger.

Not verified — check before relying on this

The statement that a unique_ptr with a function-pointer deleter is larger than one pointer comes from the usual implementation technique (storing the deleter alongside the pointer) and was not measured in this build. Measure it with sizeof as an extension of Listing 1, and check the libstdc++ implementation notes for the version in the logs.

Smart pointers in a kernel. The standard library's smart pointers live in a hosted environment; a freestanding kernel (curriculum 1.2) has neither the full standard library nor, by default, exceptions. The idea survives intact: your kernel will have its own small owner types (an owning pointer that calls the kernel heap's free, intrusive reference counts for shared kernel objects), and curriculum B5 requires "containers you write (vector, intrusive lists, hash map) work in the kernel".S1 An intrusive list keeps the link inside the element instead of allocating separate nodes, which is the design kernels prefer.S1

Performance of lists. Every node of a linked list is a separate heap allocation, and walking the list is a chain of dependent loads to unpredictable addresses, which is exactly what F1-32's pointer-chasing benchmark measured as memory latency.D3 For most sequences std::vector is faster; use a list when you need stable element addresses or cheap splicing, and measure (SP302).

How the hardware actually does it

A unique_ptr with the default deleter compiles to the same machine code as careful manual delete: a pointer in a register or stack slot, and a call to the deallocation function at the end of scope; there is no run-time bookkeeping.D2 A shared_ptr copy or destruction performs an atomic read-modify-write on the count in the control block; on a multicore processor such instructions must coordinate cache ownership of that line between cores (HW202, F1-30), so heavily shared pointers copied across threads can become a hot spot.D1 D3 Pass shared_ptr by reference (or pass a raw pointer or reference to the object) when the callee does not need to share ownership.D4

Where the analogy breaks


    

  1. A name tag cannot be in two places; a raw pointer can. get() hands out raw pointers to an object a unique_ptr owns. They are not tags, nobody counts them, and they dangle as soon as the owner deletes the object (F2-23's forensic lab is exactly this).D1
    2. 

  2. Cooks notice a deadlock; counters do not. Ana and Bo would eventually talk. Two shared_ptrs in a cycle wait forever, silently: only a leak checker or a missing destructor message shows the problem.R3
    3. 

  3. Returning a tool is instant; destroying a chain is not. Returning one tagged tool is one action. Destroying an owner may destroy everything it owns, recursively, which can take time and stack (Layer 3).R5
    4.

Summary


    

  • unique_ptr: one owner, move-only, no space overhead with the default deleter; create it with make_unique.
    • 

  • shared_ptr: shared owners counted in a control block; create it with make_shared; costs two pointers and atomic count updates.
    • 

  • weak_ptr: observes without owning; use it through lock(); breaks cycles.
    • 

  • Prefer values, then unique_ptr, then shared_ptr; use raw pointers and references only to observe.
    • 

  • Function signatures express ownership: by-value unique_ptr takes it, references only use.
    • 

  • Chains of owners destroy recursively; long chains need an iterative destructor.

Forensic lab answer key


Observation: both "built a list of … now leaving the block" lines were printed; "done" never was; the report is "AddressSanitizer: stack-overflow" whose frames repeat Node::~Node() deep_list.cpp:5 with std::unique_ptr<Node>::~unique_ptr() between them. So the crash happened while destroying the million-node list at the end of the loop body (line 23). Hypotheses: (H1) heap corruption or a use after free — not supported: no heap error is reported, and there is no raw delete; (H2) recursive destruction exhausts the stack — supported: each ~Node destroys its next, which calls ~Node of the next node, so the nesting depth equals the list length. Why 1000 works: 1000 nested destructor calls fit in the stack (F2-20: 8192 KiB in this container); a million do not, especially with sanitizer frames. Fix: an iterative destructor (Listing 4, lines 49–54), in a list class that owns the head.
