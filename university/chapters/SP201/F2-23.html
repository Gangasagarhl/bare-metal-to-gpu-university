Story hook

Analogy

The kitchen has a thick rule book. It says what happens when an order is changed, cancelled, or sent back. Most cooks never read it, because most evenings everything simply works.

One evening Yusuf, the night cook, keeps a note for shelf 4410: "table 4, noodle soup". Table 4 leaves; the shelf is cleared and handed to someone else for a note about table 7's allergies. Later Yusuf, still holding his old note, walks to shelf 4410 and writes "done" on what he thinks is table 4's order. What happens next? The rule book has no page for "writing on a shelf you no longer have". So anything can happen. Tonight, table 7's allergy note becomes unreadable and the waiter drops a tray an hour later. Tomorrow, with one extra note on the shelves, the trouble appears at closing time instead. The bug is the same; the crash moves.

This chapter is about that missing page: when objects begin and end, and what C++ means when it says a program's behaviour is "undefined".

What you will be able to do

  • Explain when an object's lifetime begins and ends for automatic, dynamic and temporary objects, and in which order members and locals are destroyed.
  • Explain what undefined behaviour is, why compilers may assume it never happens, and why "it worked when I ran it" proves nothing.
  • Recognise common undefined behaviour: use after free, dangling references and views, signed overflow, out-of-bounds access, misaligned and type-punned access.
  • Diagnose a use-after-free whose symptom moves between builds, from an AddressSanitizer report (the course forensic lab "The crash that moves").
  • Use AddressSanitizer, UndefinedBehaviorSanitizer and compiler warnings together, and know what each can and cannot see.
Jargon box
Object lifetime
Simple words: the time during which an object really exists and may be used. Analogy: from stocking a shelf until it is cleared. Precise: a run-time property of an object: for a class type with a non-trivial constructor it begins when initialisation completes, and it ends when the destructor call starts (or when the storage is released or reused); outside its lifetime, an object may not be accessed through its type. D1
Temporary object
Simple words: an unnamed object the compiler creates in the middle of an expression. Analogy: a plate passed through the hatch and taken back at once. Precise: an object created, for example, by a function returning by value; it is destroyed at the end of the full-expression that created it, unless it is bound to a reference that extends its lifetime. D1
Undefined behaviour (UB)
Simple words: something the language rules do not allow, so the result can be anything. Analogy: an order the rule book has no page for. Precise: behaviour for which the C++ standard imposes no requirements; an implementation may do anything, including appearing to work, and compilers may optimise on the assumption that it does not occur. Not the same as unspecified behaviour (one of several allowed results) or implementation-defined behaviour (documented by the implementation). D1
Dangling reference or view
Simple words: a reference, string_view or span that looks at something that no longer exists. Analogy: a window looking onto a cleared shelf. Precise: a reference or non-owning view whose referent's lifetime has ended; any access through it is undefined behaviour. std::string_view and std::span never own the data they view. D1 D4
Signed integer overflow
Simple words: a calculation with signed integers whose true result does not fit in the type. Analogy: a counter on the wall that has no digit left. Precise: an arithmetic result outside the range of a signed integer type; undefined behaviour in C++ (unsigned arithmetic, in contrast, is defined to wrap modulo 2N; MA102). D1
UndefinedBehaviorSanitizer (UBSan)
Simple words: a checker that reports some kinds of undefined behaviour while the program runs. Analogy: an inspector who knows several pages that are missing from the rule book. Precise: compiler instrumentation enabled with -fsanitize=undefined that adds run-time checks for, among others, signed overflow, misaligned access, null member access and out-of-bounds array indexes, and prints "runtime error:" messages; by default it reports and continues. D5 D6
Heisenbug
Simple words: a bug whose symptoms change or disappear when you try to look at it. Analogy: the trouble that moves to closing time when one extra note is added. Precise: informal engineering term for a defect whose observable effect depends on timing, memory layout, optimisation level or instrumentation; memory-safety bugs are a classic source because their effect depends on what else occupies the memory. D3

Layer 1 — the kid explanation

Every object has a beginning and an end. A local variable begins at its line and ends at the closing brace. A heap object begins at new or make_unique and ends when it is deleted. A temporary, like the value a function hands back, ends at the semicolon unless you hold on to it.D1

Using an object after its end is against the rules. So is adding two big ints whose sum does not fit, or reading past the end of an array. The C++ rules call these undefined behaviour. It does not mean "an error message". It means the rules promise nothing at all. The program may crash, may print a wrong number, or may seem fine today and fail tomorrow.D1

That last part is the hard one. A bug that sometimes works is harder to find than a bug that always crashes. So engineers do not trust "it worked". They use tools, the sanitizers, that watch every memory access and every risky calculation and say exactly which line broke the rules.D6

Layer 2 — the student explanation

When lifetimes begin and end

Storage and lifetime are different things: storage is the bytes; lifetime is the period in which an object of a particular type lives in them.D1 Listing 1 makes the rules visible: locals are destroyed at the end of their block in reverse order of construction ("end b" before "end a"); a temporary returned by value is destroyed at the end of the full-expression, after the line has used it; binding a temporary to a const reference extends its lifetime to that of the reference; and members are constructed in declaration order and destroyed in reverse.D1 R1 Look closely at part 2 of the output: "length" is printed, then the temporary begins, then its size is printed, then it ends. Since C++17 the operands of << are evaluated left to right, and the temporary lives exactly until the end of that whole statement.D1 R1

What "undefined" really means

The standard sorts behaviour into three kinds besides "well-defined": implementation-defined (the implementation chooses and documents, like sizeof(long)), unspecified (one of several allowed outcomes, not necessarily documented, like the order in which some function arguments are evaluated), and undefined (no requirements at all).D1 Undefined behaviour is not a run-time event the language detects; it is a promise you make to the compiler that the situation never arises. The compiler may then optimise as if it cannot happen, for example by assuming that x + 1 > x is always true for a signed x.D3 D5 That is why a UB bug can change behaviour between -O0 and -O2, or when an unrelated line is added.

A short catalogue

  • Use after free / after scope: accessing an object after its lifetime (F2-20, F2-21, the forensic lab here).D1
  • Dangling references and views: Listing 3's std::string_view looks at the characters of a temporary std::string that was destroyed at the end of line 14; reading it at line 15 is a heap-use-after-free.R3 GCC 13 caught a similar mistake, a const& bound to the result of std::max of two temporaries, at compile time with -Wdangling-reference (mistakes section).R4
  • Signed overflow: INT_MAX + 1 in Listing 2; UBSan printed "signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'" and then the program continued, printing −2147483648: UBSan reports by default and does not stop.R2 The unsigned version wraps to 0, which is defined.D1
  • Out-of-bounds access: reading or writing outside an array (F2-25).
  • Null dereference (F2-19), uninitialised reads, misaligned or type-punned access (F2-24).

Three tools, three views

Compiler warnings see the source and catch patterns at compile time: -Wuninitialized (F2-19), -Wmismatched-new-delete (F2-21), -Wdangling-reference and, in optimised builds, -Wuse-after-free, which flagged the forensic program's bug in the -O2 build log.D5 R6 AddressSanitizer instruments memory accesses and reports invalid addresses at run time; UndefinedBehaviorSanitizer instruments arithmetic and other operations.D6 Each sees only what its method allows: warnings see only what is visible in the code being compiled, and sanitizers see only the paths your test actually executes. Use all three, and give the sanitizers good tests.

Layer 3 — the engineer's depth

Why UB exists. Leaving behaviour undefined lets the language map operations directly onto hardware without checks (no bounds check on every a[i], no overflow trap on every addition) and lets optimisers reason freely; the cost is that correctness becomes the programmer's proof obligation.D1 D3 Curriculum 1.1 names the cases that bite kernels: strict aliasing, signed overflow, misaligned access, and the lifetime of objects created in raw memory.S1

Strict aliasing. An object may be accessed only through an lvalue of its own type (with some allowances, notably char, unsigned char and std::byte); reading a float's bytes through an int* breaks this rule, and an optimiser may then reorder or delete accesses on the assumption that the two pointers cannot refer to the same object.D1 The defined ways to reinterpret bytes are std::memcpy and std::bit_cast (F2-18, F2-24).

Lifetime in raw memory. Storage obtained from an allocator is just bytes; an object's lifetime starts only when it is created there (by placement new, or implicitly for certain simple types in certain operations), and it ends when it is destroyed or its storage is reused.D1 Casting a void* from an allocator to Order* and using it as if an Order lived there is UB for types with non-trivial construction. Your allocators (F2-25 project) and kernel heap (curriculum B5) must construct objects with placement new and destroy them explicitly.

Not verified — check before relying on this

C++20 added rules under which certain operations (such as std::malloc and std::memcpy) implicitly create objects of "implicit-lifetime" types in the storage they touch, and C++23 added std::start_lifetime_as. The exact list of operations and types was not checked in this build. Check the working draft's clause on the object model (implicit object creation) and the library clause for std::start_lifetime_as before relying on implicit creation in allocator or kernel code.

Why the crash moves. A use-after-free writes into whatever now occupies the freed memory. Which object that is depends on the allocator's reuse policy, on every allocation made in between, and on optimisation. In this build the same source crashed at the line after the stale write in one build and four lines later, in a different object, when one extra allocation was compiled in.R5 AddressSanitizer removes the randomness by delaying reuse of freed blocks (quarantine) and checking every access, so it reports the write, not the later crash.D6 R7 Curriculum B5 asks your kernel allocator to do a lighter version of the same: poison freed memory so that "a deliberate use-after-free in a test build is caught by the poison check".S1

How the hardware actually does it

The processor executes whatever loads, stores and arithmetic the compiler emitted. It has no concept of object lifetime: a store to a freed heap block succeeds if the page is mapped and writable, which is why use-after-free corrupts silently instead of faulting.D3 Signed addition on x86-64 wraps in two's complement and sets the overflow flag (HW102's status flags); C++ calls the overflow undefined anyway, because other processors behave differently and because the optimiser's freedom matters more than the hardware's habit.D3 Faults happen only where the hardware's own checks are violated: an unmapped page (null pointer, F2-19; guard page, F2-20), or on some processors a misaligned access (F2-24).

Where the analogy breaks


    

  1. A rule book with a missing page still leaves people sensible. Faced with an uncovered case, cooks improvise reasonably. A compiler facing UB is not "reasonable": it may assume the case never happens and transform the program accordingly, so the result can be stranger than any plausible mistake.D3 D5
    2. 

  2. Trouble in a kitchen is noticed where it happens. Yusuf would see the wrong note in his hand. In a program, the faulty write leaves no trace at the moment it happens; the crash comes later, elsewhere, or never (the forensic lab).R5
    3. 

  3. Cleared shelves are visibly empty. Freed memory keeps its old bytes, or holds a new object, so a read through a stale pointer often returns something plausible.D3
    4.

Transition box

Where you came from: F2-20 to F2-22 tied lifetimes to scopes and owners; F2-19 met the first undefined behaviour (null dereference). What carries over: RAII and smart pointers still decide when objects end; the sanitizer reports you read in F2-19 to F2-22 have the same structure (kind, access, free, allocation).D6 What changes: you now treat the language rules as a contract with the compiler: breaking one does not produce an error but releases the compiler from every promise, and symptoms can appear far from the cause, differ between builds, or not appear at all.D1 R5 What comes next: F2-24 opens objects up byte by byte: size, alignment and padding, and the misaligned and type-punned accesses that are UB in their own right.

Summary


    

  • Objects live from the end of construction to the start of destruction; locals end in reverse order, members too; temporaries end at the end of the full-expression unless bound to a const reference.
    • 

  • Undefined behaviour means the standard imposes no requirements; compilers may assume it never happens.
    • 

  • "It worked" proves nothing; UB can change with optimisation, layout, or an unrelated line.
    • 

  • Views (string_view, span) and references never own; they must not outlive their data.
    • 

  • Signed overflow is UB; unsigned wrap-around is defined.
    • 

  • Use compiler warnings, UBSan and ASan together; each sees different bugs, and sanitizers see only executed paths.
    • 

  • A use-after-free's crash is a symptom far from the cause; ASan reports the cause.
    •

E4: "heap-use-after-free … WRITE of size 4" in Screen::markDone() moving_crash.cc:16 called from line 36; "located 4 bytes inside of 40-byte region"; freed at line 27; allocated at line 24. Offset 4 is portions (after the 4-byte table) in the 40-byte Order (8 bytes of ints plus a 32-byte std::string, F2-18).


Hypotheses. (H1, Dmitri's) the logging library is broken — refuted: E2 crashes with no logging compiled in at all, and E4 reports an invalid write in markDone, before any log line is printed. (H2) the string printing code is broken — refuted for the same reasons; the strings print correctly until line 36 has run. (H3) screen.showing dangles after line 27 and line 36 writes into freed memory — confirmed by E2's warning and by E4's report, which gives the access, the free and the allocation sites.


Why the symptom moves (inference, see the box below). In the release build, the next allocation after line 27 is note (line 33); the evidence is consistent with the allocator giving note's std::string object the block just freed by order, so the write of 0 at offset 4 overwrites the upper half of the string's internal data pointer, and printing note at line 37 follows a broken pointer: SIGSEGV. In the debug build, log (line 30) is allocated first and receives the freed block; the stale write damages log instead, note prints correctly, and the crash moves to line 41, where log is printed. The bug (line 36) never moved.


Not verified — check before relying on this
That the GNU C library's allocator in this build returns the most recently freed block to the next request of a similar size (which is what makes the order's 40-byte block go to the next 32-byte std::string object) was inferred from the observed crashes, not checked in documentation or by printing addresses. Check the glibc manual and the malloc implementation notes of the installed glibc version (thread-local caches and size classes), or add address printing to moving_crash.cc and rerun.


Fix. Design: the screen must not hold a raw pointer to an object whose lifetime it does not control. Either the screen observes through std::weak_ptr and checks before writing (moving_fixed.cpp, which printed "screen: that order is already closed" and ran clean, R7), or closing an order notifies the screen, or the screen holds an order identifier and looks it up. Prevention: build every configuration with -Werror (the release build's warning named the bug before it shipped); run the tests under AddressSanitizer in CI; include a test that closes an order while it is on the screen. How the evidence was made: run.sh in university/labs/F2-23/ built moving_crash.cc three ways and recorded each run (R5–R7).
