Story hook

Analogy

At the end of each evening, Marta adds up the tips in the jar slots behind the bar. There are four slots, numbered 0 to 3. Her checklist says: "start at slot 0, keep going while the slot number is at most the number of slots". So she counts slot 0, 1, 2, 3, and then slot 4, which is not a tip slot at all; it is the first slot of the coffee shelf next door. Most nights it is empty and the total is right. One night someone parks a box of coffee coins there, and the tips are wrong by a fortune.

The slots have no fence at the end. Nothing stopped Marta from reaching one too far, and on most nights nothing showed she had. This chapter is about the fence that arrays lack, the tools that put one back (std::span, .at(), sanitizers), and how to build a small memory allocator that never reaches past its own counter.

What you will be able to do

  • Compare built-in arrays, std::array and std::vector: where they live, how they know their size, how they are passed.
  • Explain array-to-pointer decay and why a function parameter declared int a[8] is a pointer.
  • Use std::span to pass "a pointer and a length" as one value, and subspan to view part of a sequence.
  • Choose between unchecked operator[], checked .at() and sanitizer builds, and read stack-buffer-overflow and heap-buffer-overflow reports.
  • Diagnose an off-by-one read that gives the right answer by luck (forensic lab).
  • Build a bump allocator and a free-list allocator with tests (course project).
Jargon box
Built-in array
Simple words: a fixed number of same-type values stored next to each other, written int a[4]. Analogy: a run of numbered slots with no fence at the end. Precise: an object of type T[N] holding N contiguous elements; N is part of the type and sizeof gives N * sizeof(T); not assignable or copyable as a whole, and converted to a pointer to its first element in most expressions. D1
Array-to-pointer decay
Simple words: an array turning into a pointer to its first element, losing its length. Analogy: handing over a note with the first slot number but no count. Precise: the standard conversion from an lvalue of type T[N] to a prvalue of type T*; also, a function parameter declared with array type is adjusted to pointer type. D1
std::array
Simple words: a fixed-size array that behaves like a normal value. Analogy: the same slots, sold as a boxed set with the count printed on the lid. Precise: the class template std::array<T, N> from <array>, an aggregate wrapping T[N], copyable and assignable, with size(), iterators, operator[] (unchecked) and at() (checked). D1
std::span
Simple words: a view of a run of elements that knows where it starts and how many there are. Analogy: a note with a first slot number AND a count. Precise: the class template std::span<T, Extent> from <span> (C++20), a non-owning reference to a contiguous sequence, holding a pointer and (for dynamic extent) a size; constructible from built-in arrays, std::array, std::vector and other contiguous ranges. D1 D4
Bounds check
Simple words: a test that an index is inside the array before using it. Analogy: a fence at the last slot. Precise: a run-time comparison of an index against the size, as done by at() (which throws std::out_of_range), by hardened library modes, or by sanitizer instrumentation; built-in subscripting and operator[] of standard containers do not check. D1
Buffer overflow
Simple words: reading or writing past the end (or before the start) of an array. Analogy: counting the coffee shelf's slot as a tip slot. Precise: an access outside the bounds of an array object; undefined behaviour in C++; reported by AddressSanitizer as stack-buffer-overflow, heap-buffer-overflow or global-buffer-overflow according to where the array lives. D6
Off-by-one error
Simple words: a loop or calculation that goes one step too far or stops one step short. Analogy: "while the slot number is at most four". Precise: informal term for a boundary error, typically <= where < was needed, or a size used as a last index. D3
Bump allocator (arena)
Simple words: an allocator that hands out memory from one block by moving a cursor forward, and frees everything at once. Analogy: handing out counter space from left to right and wiping the whole counter at closing. Precise: a region-based allocator whose state is a base, a size and an offset; allocation rounds the offset up to the requested alignment and advances it; individual deallocation is not supported, only reset. D3 S1
Free list
Simple words: a list of the free pieces of a memory region, used to find room for a request and to take pieces back. Analogy: a board listing which counter sections are free right now. Precise: an allocator data structure linking free blocks (often through headers stored inside the blocks themselves); allocation searches it (first fit, best fit), may split a block; freeing returns a block and may coalesce it with free neighbours. D3

Layer 1 — the kid explanation

An array is a row of boxes of the same kind, side by side. You find a box by its number, the index, starting at 0. An array of four boxes has numbers 0, 1, 2 and 3. There is no box 4.D1

The trouble is that the computer does not stop you from asking for box 4. It just goes to where box 4 would be and uses whatever is there. Sometimes that is empty and the answer still looks right. Sometimes it is another variable, and you have just read or changed something that was not yours.D3

So we use helpers that carry the count with the boxes: std::array, std::vector and std::span always know how many boxes there are. .at(4) checks and says "no such box". And the sanitizers put invisible fences around every array so that a reach past the end is caught at once.R3 R4

Layer 2 — the student explanation

Three arrays

A built-in array int cArray[4] has its size in its type: Listing 1 printed sizeof(cArray) = 16 and 4 elements.R1 std::array<int, 3> has the same layout but behaves like a value (copy, assign, compare, return from functions). std::vector<int> chooses its size at run time and keeps its elements in a heap block it owns (F2-20, F2-21).D1 All three store elements contiguously, so element i is at data + i (pointer arithmetic, F2-19).

Decay: where the length gets lost

Pass a built-in array to a function and it decays to a pointer to its first element. Even a parameter written int portions[8] is adjusted to int*; the 8 is ignored.D1 Listing 2 tries to compute the length inside such a function; GCC 13 refused to compile it with the course flags: "'sizeof' on array function parameter 'portions' will return size of 'int*' [-Werror=sizeof-array-argument]".R2 The classic C answer is to pass a pointer and a length as two parameters, and to hope they match.

std::span: pointer and length as one value

std::span<const int> packages both. Listing 1's total(std::span<const int>) accepts the built-in array, the std::array and the vector without copies or templates, and its range-for loop cannot run past the end.R1 A span is small: sizeof(span) = 16 on this build, a pointer and a length, so pass it by value.R1 subspan(1, 3) views elements 1 to 3 of the same storage; Listing 1 checked that &middle[0] == &growing[1].R1 Like string_view (F2-23), a span does not own: it must not outlive its storage, and resizing a vector can move the storage and leave the span dangling.D1 D4

Who checks the bounds?

Nobody, by default: built-in a[i], vector::operator[] and span::operator[] do not check, and an index outside the bounds is undefined behaviour.D1 Three ways to get a check:

  • .at(i) on std::array and std::vector throws std::out_of_range. Listing 3 caught it with the message "array::at: __n (which is 4) >= _Nm (which is 4)".R3 (std::span has no at() in C++20.)
  • Sanitizer builds. For the stack array in Listing 4, UBSan reported "index 4 out of bounds for type 'int [4]'" and ASan "stack-buffer-overflow … WRITE of size 4" at line 10, naming the variable seats declared at line 7.R4 For the vector in the forensic lab, ASan reported a heap-buffer-overflow read "0 bytes after 16-byte region".R5
  • Writing loops that cannot go wrong: range-for, or algorithms over a span, so no index exists to get wrong.

Layer 3 — the engineer's depth

Out-of-bounds is the oldest exploit. A write past a stack array can overwrite neighbouring locals, saved registers and the return address; attackers have used exactly this to redirect execution for decades, which is why modern toolchains add stack canaries, non-executable stacks and address randomisation.D3 These mitigations detect or hamper some overflows after the fact; they do not make out-of-bounds access defined. In Listing 4, the stack layout shown by ASan ("[32, 48) 'seats'") is the sanitizer's own layout with red zones (F2-18), not the layout of a plain build.R4

Not verified — check before relying on this

Whether Ubuntu's GCC 13 enables stack protection (-fstack-protector-strong) and libstdc++ assertions (_GLIBCXX_ASSERTIONS, which make operator[] check bounds) by default, and in which build modes, was not checked in this build. Check with g++ -Q --help=common | grep stack-protector and the distribution's compiler hardening documentation before claiming either for the course machine.

Spans in systems code. Kernel and driver code passes buffers constantly: a DMA region, a received packet, a page. Curriculum 1.2 restricts the language in the kernel (no exceptions), so .at() is unavailable there; std::span survives because it is a pointer and a length with no allocation, and a kernel can add its own checked accessor that panics instead of throwing.S1

Not verified — check before relying on this

That <span> is usable in a freestanding C++ implementation (no hosted library) was not checked: the list of freestanding headers changed between C++20, C++23 and C++26, and libstdc++ follows its own schedule. Check the standard's freestanding clause for the version you compile with and the installed libstdc++ headers before planning kernel code around it (curriculum 1.2).

Allocators are arrays plus bookkeeping. A memory allocator owns one big byte array and hands out pieces. The simplest, a bump allocator, keeps one offset: allocation rounds the offset up to the requested alignment (the same rounding the compiler did for struct members in F2-24) and advances it; nothing is freed individually.D3 Listing 5 implements one over a std::span<std::byte>; requests that do not fit return nullptr instead of overrunning, and the tests show the alignment: a 1-byte piece at offset 0, then an 8-aligned piece at 8, not at 1.R6 A free-list allocator also takes pieces back; that, with splitting and coalescing, is the course project and the CS:APP malloc lab's core (P4).D3 Strictly, objects must still be created in allocator memory with placement new (F2-23); the bump allocator hands out storage, not objects.

How the hardware actually does it

To the processor, a[i] is an address computation, base + i * sizeof(T), often a single instruction with a scaled index addressing mode, followed by a load or store.D3 There is no bounds register and no check: the access fails only if the computed address falls on a page that is not mapped or not writable (F2-19, F2-20). The four tips occupy 16 bytes of a heap block; the byte after them is ordinary mapped memory belonging to the allocator, so a plain build reads it without any fault, as the forensic lab shows (what those bytes are is an inference; see the box in the forensic key).R7 Sanitizers add the missing check in software, by consulting shadow memory before every access (F2-18).D6

Worked example

Trace Listing 5's first three requests on a 64-byte arena whose base address is a multiple of 16 (the alignas(16) on line 39).

  1. allocate(1, 1): offset 0, already a multiple of 1. Piece at 0; offset becomes 1.
  2. allocate(8, 8): offset 1 rounded up to a multiple of 8 is 8; padding 7. Piece at 8; offset becomes 16.
  3. allocate(4, 4): 16 is a multiple of 4. Piece at 16; offset becomes 20.

Prediction: offsets 0, 8, 16 and 20 bytes used. The run printed "a at offset 0", "b at offset 8 (aligned to 8)", "c at offset 16", "used 20 of 64 bytes".R6 Line 20's rounding, (current + align - 1) & ~(align - 1), works because align is a power of two (asserted on line 17): ~(align - 1) clears the low bits (MA102).

Where the analogy breaks


    

  1. Marta could see the coffee shelf. A program reading past an array sees only bytes; nothing tells it they belong to another variable.D3
    2. 

  2. Reaching one slot too far is a small mistake in a kitchen. In a program it is undefined behaviour: the compiler may assume the index is valid and optimise on that assumption (F2-23), so the effect is not limited to "one wrong value".D1
    3. 

  3. A note with a count is still just a note. A span's count is trusted, not checked against the real storage; a span built from a wrong pointer and size, or kept after its vector reallocated, is as dangerous as a raw pointer.D4
    4.

Course project: two allocators with tests


Brief. Over a 4096-byte arena given as std::span<std::byte>, implement (a) the bump allocator of Listing 5, and (b) a free-list allocator with allocate(size, align) and free(pointer). Each block starts with a small header recording its size and whether it is free; free blocks are found by walking the headers (an implicit free list) or by a linked list stored inside the free blocks (an explicit free list). Use first fit; split a free block when the remainder can hold a header plus a minimum payload; coalesce a freed block with free neighbours. Allocation that cannot be satisfied returns nullptr; nothing ever writes outside the arena.D3 S1


Required tests (built and run with the course flags, so the sanitizers watch every test): every returned pointer is aligned and inside the arena; no two live blocks overlap; after freeing everything in any order, one free block covers the whole arena again (coalescing works); a randomised test of at least 10,000 mixed allocate/free steps that checks the invariants after every step; an exact-fit and an out-of-memory case.

Bump allocator correct with boundary tests (4); free-list allocation, splitting and alignment (5); free and coalescing (5); randomised invariant test (4); a one-page design note: header layout with static_asserts (F2-24), worst-case fragmentation example, and what would change in a kernel with no sanitizer (2). Summary


    

  • Built-in arrays know their size only until they decay to a pointer; array parameters are pointers.
    • 

  • std::array is a fixed array with value semantics; std::vector owns a heap block of run-time size.
    • 

  • std::span passes a pointer and a length as one cheap value (16 bytes here); it views and never owns.
    • 

  • operator[] never checks; .at() throws std::out_of_range; sanitizers catch out-of-bounds access at run time.
    • 

  • A right answer from a plain build proves nothing; the off-by-one read returned a harmless value by luck.
    • 

  • Allocators are bounds-checked arrays with alignment rounding: bump (offset only) and free-list (headers, split, coalesce).
    •

Forensic lab answer key


Observation. ASan: "heap-buffer-overflow … READ of size 4" at off_by_one.cpp:11; "located 0 bytes after 16-byte region", the block allocated by the vector at line 8.R5 16 bytes is four ints, so the read is tips[4]. The loop condition i <= tips.size() runs five times. The correct sum is 4 + 9 + 2 + 7 = 22; the release build printed 22 in each of three runs, so its read of tips[4] must have contributed 0 (assuming the read happened at all; under UB the compiler need not even emit it).R7


Hypotheses. (H1, the team lead's) a sanitizer false positive — refuted: the loop on line 10 runs with i = 4, so line 11 reads index 4 of a 4-element vector, exactly what the report says. (H2) a real out-of-bounds read whose value happened to be 0 — confirmed by counting iterations and by the arithmetic above.


Why it was right by luck. The 4 bytes after the vector's block lie in memory the allocator owns (padding or the next chunk's bookkeeping); in these runs they held 0. Different input sizes (more tips give a block of a different size, followed by different bytes), another allocation pattern before the report, a different allocator or library version, or an optimisation change can put a non-zero value there; and because the read is undefined behaviour, a future compiler may transform the loop in ways no one predicted.


Not verified — check before relying on this
What exactly lies after a 16-byte block in glibc's allocator (unused tail of the chunk or the next chunk's size field) was not examined in this build, and neither was the -O2 assembly of the loop. Check by printing the bytes after the block in a plain build, and with objdump -d, before using either as an explanation of why the value was 0.


Fix. for (const int t : tips) sum += t; or std::accumulate(tips.begin(), tips.end(), 0). Policy: run every unit test under ASan and UBSan in CI; treat sanitizer reports as failures; never accept "the output is right" as evidence that memory accesses are right.
