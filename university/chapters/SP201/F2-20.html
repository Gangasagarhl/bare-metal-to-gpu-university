Story hook

Analogy

Watch Kwame at his station during the dinner rush. When an order for soup arrives he puts a fresh tray on his station and lays out what the soup needs. Halfway through, the soup needs a stock, so he puts a second tray on top for the stock. The stock needs chopped onions: a third tray on top. When the onions are done, he clears and removes the top tray, and the stock tray is on top again, exactly where he left it. Trays come off in the reverse order they went on. It is fast, tidy, and needs no paperwork.

But some things must outlive the task that made them. A big pot of sauce made at five o'clock will be used until midnight by several cooks. Kwame cannot keep it on a tray; the tray disappears when his task ends. So he goes to Tomás, the storeroom manager: "I need a shelf for a pot of sauce." Tomás finds a free shelf, writes its number on a note, and lends it. The shelf stays Kwame's until someone tells Tomás "this shelf is free again".

Trays that vanish by themselves; shelves that stay until somebody gives them back. Every program has both, and most memory bugs come from mixing them up.

What you will be able to do

  • Explain the three places objects live (the stack, the heap, static storage) and the lifetime each one gives.
  • Explain what a stack frame holds and why the stack is fast and limited.
  • Measure where your program's frames, heap objects and globals are, and how far apart frames are, on your own machine.
  • Diagnose a stack overflow and a use-after-scope from sanitizer reports.
  • Choose between a stack object and a heap object for a given job.
Jargon box
Storage duration
Simple words: the rule for how long an object's memory is kept. Analogy: tray (until the task ends), lent shelf (until returned), permanent shelf (all evening). Precise: the property of an object that defines the minimum lifetime of its storage: automatic, dynamic, static or thread. D1
Stack (call stack)
Simple words: memory for function calls that is used and freed in strict last-in, first-out order. Analogy: the pile of prep trays at a cook's station. Precise: the region of memory in which an implementation keeps the frames of active function calls; objects with automatic storage duration usually live there. The C++ standard describes automatic storage, not a "stack"; the stack is how the platforms of this course implement it. D1 D3
Stack frame
Simple words: one function call's private space on the stack. Analogy: one tray. Precise: the part of the stack used by one activation of a function: its local variables, saved registers, the return address and outgoing arguments as the ABI requires (HW202 met it at machine level, glossary). D3 D5
Heap (free store)
Simple words: a big pool of memory you ask for while the program runs and give back when you are done. Analogy: shelves the storeroom manager lends on request. Precise: memory for objects with dynamic storage duration, obtained by new (or by containers and smart pointers on your behalf) and released by delete; the C++ standard calls it the free store, and the C library's malloc heap usually provides it. Not the same as the "heap" data structure of algorithms courses. D1 D3
Static storage
Simple words: memory that exists for the whole run of the program. Analogy: shelves labelled and stocked before the restaurant opens. Precise: storage for objects with static storage duration (namespace-scope variables, static locals and members); it lasts from program start (or first use, for static locals) until program end. D1
Stack overflow
Simple words: running out of stack, usually by calling too deep. Analogy: trays piled to the ceiling. Precise: an attempt to grow the stack beyond its reserved size; on Linux this touches an unmapped guard region and the process receives SIGSEGV, which AddressSanitizer reports as "stack-overflow". D3 D6
Use after scope
Simple words: using a local variable after its block has ended. Analogy: reaching for a tray that was already cleared. Precise: accessing an object with automatic storage duration through a pointer or reference after the block that declared it has exited; undefined behaviour, reported by AddressSanitizer as "stack-use-after-scope". D1 D6

Layer 1 — the kid explanation

When a function starts, it gets a fresh tray of memory for its own variables: a stack frame. If it calls another function, that one gets a tray on top. When a function ends, its tray is cleared and taken away at once. Nobody has to remember to clean up, and it is very fast.D3

The catch is that everything on a tray disappears when the function ends. If you need something to last longer, you ask for memory from the heap. Heap memory stays until somebody gives it back. That is powerful, but somebody has to be responsible for giving it back, at the right time, exactly once.D1 F2-21 and F2-22 are about that responsibility.

A few things live for the whole program: global variables. They are ready before main starts and stay until the program ends.D1 And the pile of trays has a limit. Call functions too deep, and the trays hit the ceiling: a stack overflow. You will see one in the forensic lab.

Layer 2 — the student explanation

Three storage durations you will use

C++ gives every object a storage duration.D1 Automatic: local variables and parameters; their storage lasts until the end of the block (the closing brace). Dynamic: objects created with new (directly, or inside std::vector, std::string, std::make_unique…); they last until delete ends them. Static: globals and static variables; they last for the whole program. (A fourth, thread storage duration, arrives with threads in SP203.)D1 On the platforms of this course, automatic objects live on the call stack, dynamic objects in the heap, and static objects in data sections of the program file mapped into memory at start.D3

Frames: push on call, pop on return

Each call reserves a frame for that activation's locals and bookkeeping; each return releases it. Because calls and returns nest, the frames form a last-in, first-out pile, so reserving and releasing is a single adjustment of the stack pointer register: nothing has to be searched or recorded.D3 Recursion creates one frame per active call, each with its own copy of the locals: Listing 1 prints a different address for local at each depth, 64 bytes apart in the plain build.R1 Destructors of automatic objects run when their block ends, in reverse order of construction; this is the mechanism under RAII (F2-11).D1 Listing 3 shows a stack Ticket destroyed as takeOrder returns.R3

The heap: you choose the lifetime

A heap object's lifetime is not tied to any block. It begins when it is created and ends when it is explicitly destroyed, which can be in a different function, much later.D1 That is the only way to create an object whose size is known only at run time (a vector of n orders) or that must outlive the function that made it (Listing 3's heap ticket, returned to main).R3 The price: an allocator must find free space, which takes more work than moving a stack pointer, and someone must end the object exactly once. In modern C++ that "someone" is an owner object: a container, or a smart pointer such as the std::unique_ptr returned by std::make_unique in Listings 1 and 3 (read it for now as "make one object on the heap, with an owner that deletes it"; F2-22 explains it).D4

Handles on the stack, data on the heap

F2-18's lab showed a std::vector object of 24 bytes among the locals and its elements far away. That is the common shape: the small handle (pointer, size, capacity) has automatic storage, the elements are on the heap, and the handle's destructor frees them.D2 R4 You get the speed and automatic clean-up of the stack, and the flexible size of the heap.

Pointers must not outlive their frame

A pointer to a local is valid only until the local's block ends. Listing 2 stores &total in a pointer declared outside the block and reads it after the closing brace; the sanitizer stops it with "stack-use-after-scope" and names the variable and line.R2 Returning the address of a local from a function is the same bug one level up; GCC refused to compile it in SP102 (F2-12's return_local.cpp), but it cannot see every case.

Layer 3 — the engineer's depth

How big is the stack? On Linux the main thread's stack size limit is a per-process resource limit; in this build's container the shell reported 8192 KiB (ulimit -s).R5 Threads created later get stacks whose size is set when the thread is created. A kernel's stacks are much smaller and fixed (your own kernel will choose them in curriculum B9 and B11), which is why kernel code avoids recursion and large local arrays.

Not verified — check before relying on this

The default stack size of threads created with std::thread on Linux (it comes from the C library's thread implementation and the stack limit) was not measured or checked in this build. Check the glibc manual and the Linux manual page for pthread_create for the version installed, or measure it in SP203.

Overflow arithmetic. Listing 4 gives every frame a 1 KiB array. With an 8192 KiB limit, at most 8192 such frames fit even if each frame were nothing but its array; the real frames are larger, and AddressSanitizer adds red zones around locals, so the limit is lower still.D6 1000 calls fit; 100000 calls (about 100 MiB of arrays alone) cannot, and the run ended with "stack-overflow".R6 Never let recursion depth depend on input size without a bound; convert deep recursion to a loop with an explicit std::vector as a stack (F2-22's list destructor is the same lesson).

What a heap allocation costs. A general-purpose allocator keeps data structures describing free blocks (free lists, size classes), may need to ask the operating system for more address space, and must be safe when several threads allocate at once.D3 D7 Listing 1 printed two consecutive 4-byte heap objects 0x20 bytes apart in both builds: each allocation carries hidden bookkeeping and rounding, not just the 4 bytes asked for.R1 The course project builds two allocators so that you can see the trade-offs yourself (F2-25).

The sanitizer changes the picture. In the sanitizer build, the frames' local variables appeared at addresses starting 0x7f… and increasing by 64 per call, while the plain build's were at 0x7ffd… and decreasing.R1 This is consistent with the sanitizer's "fake stack" for detecting use-after-return, which keeps locals in separately allocated memory (F2-18, unverified box there).D6 Measure layouts with a plain build; find bugs with the sanitizer build.

Static initialisation. Globals with constant initialisers are prepared before main starts; globals that need a constructor run it before main, in an order that is defined within one file but not across files. In a freestanding kernel nothing runs those constructors unless your start-up code calls them (curriculum 1.2, the init_array section; SP301's forensic lab).D1 S1

How the hardware actually does it

On x86-64 the stack pointer register rsp holds the address of the top of the stack; a call instruction pushes the return address and jumps, and the function then moves rsp down by its frame size; ret pops the return address back into the instruction pointer.D3 D5 HW202 (F1-31) read that code in compiler output. The stack's memory is ordinary virtual memory; Linux places an unmapped guard region beyond the stack's limit so that running past it causes a page fault and SIGSEGV instead of silently overwriting other data.D3 The heap is also ordinary memory: the C library's allocator obtains large regions from the kernel and carves them up in user space; the processor does not know which bytes are "heap".D3

Worked example

Read Listing 1's plain-build output (in the code walk-through) as an engineer:

  1. The three local addresses differ by −64 each: every call to cook used 64 bytes of stack in that build, and deeper calls are lower.
  2. With an 8192 KiB stack and 64-byte frames, the stack could hold at most 8192 × 1024 ÷ 64 = 131,072 such frames, minus what main and the C library already use. (Arithmetic on two measured numbers; not a guarantee.)
  3. The two heap ints are 0x20 = 32 bytes apart, although each is 4 bytes: 28 bytes of allocator bookkeeping and rounding per allocation in that build.
  4. For Listing 4's frames with a 1 KiB array, the same limit gives fewer than 8192 frames, so 100000 recursive calls must overflow, and 1000 should not. The forensic run agrees.

Where the analogy breaks


    

  1. Cleared trays are not wiped. A cleared kitchen tray is empty. A popped stack frame still contains its old bytes until the next call overwrites them, so a dangling pointer into it may read the "right" value for a while; that is why the bug can hide without a sanitizer.D3 R2
    2. 

  2. The storeroom manager keeps no register of who borrowed what. Tomás would chase a cook who never returns a shelf. The heap allocator does not: memory that is never given back stays taken until the program ends (a leak, F2-21), and memory given back twice corrupts the allocator's own bookkeeping.D3
    3. 

  3. Trays pile upward, frames grew downward. On this build's machine deeper calls had lower addresses. The direction is a property of the platform, not of stacks in general.R1
    4.

Transition box

Where you came from: F2-19 gave you pointers; SP102 (F2-10, F2-11) taught constructors, destructors and RAII without saying where objects live. What carries over: destructors still run at the end of scope, in reverse order; RAII handles such as std::vector and std::string still clean up; the frame you read at machine level in HW202 (F1-31) is the same frame.D1 D3 What changes: you now choose lifetimes yourself: automatic objects end with their block whether or not a pointer still refers to them, and dynamic objects end only when someone ends them; the stack is small and fixed-size, the heap is large but costs work and responsibility.R5 What comes next: F2-21 opens the heap by hand with new and delete, and shows why modern code hands that job to smart pointers.

Summary


    

  • Automatic objects live on the stack and end with their block; dynamic objects live on the heap and end when deleted; static objects live for the whole program.
    • 

  • A stack frame is one call's space; frames are pushed on call and popped on return, last in, first out.
    • 

  • The stack is fast but limited (8192 KiB for the main thread in this build's container); deep recursion overflows it.
    • 

  • The heap gives flexible sizes and lifetimes at the cost of allocator work and the duty to free exactly once.
    • 

  • Handles (vector, string, smart pointers) sit on the stack and own data on the heap.
    • 

  • A pointer to a local must not outlive the local's block; AddressSanitizer reports "stack-use-after-scope".
    • 

  • Measure layouts with plain builds; hunt bugs with sanitizer builds.

Forensic lab answer key


Observation: 10 and 1000 dishes were counted; the output stops at "menu of 100000 dishes:" followed by "AddressSanitizer: stack-overflow", and the trace is the same frame countDishes(int) deep.cpp:12 repeated (the report lists about 250 frames, far fewer than the thousands of calls that must have been active, so the sanitizer printed only part of the stack). Hypotheses: (H1) bad data — ruled out: the "input" is the integer literal 100000 in line 18; there is no file; (H2) recursion depth proportional to the input exhausts the stack — confirmed: each call keeps a 1 KiB array (line 7) plus its frame, so 100,000 calls need more than 100,000 KiB ≈ 98 MiB, far above the 8192 KiB limit; 1000 calls need about 1 MiB and fit. Root cause: unbounded, input-sized recursion with a large local array. Fix: a loop (for counting down), or an explicit heap-allocated work list; the 1 KiB scratch array belongs outside the recursion. Prevention: a test with the largest realistic input (and ten times more); a code-review rule "no recursion whose depth depends on input size" (common in kernel and embedded coding rules, curriculum 1.2). How the evidence was made: deep.cpp run by run_lab.sh with the course flags; run.sh made the trimmed copy and recorded ulimit -s (R5, R6).
