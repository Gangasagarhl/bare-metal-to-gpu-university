Story hook

Analogy

Tomás, the storeroom manager, has a simple system. A cook asks for a shelf, Tomás lends one and hands over a note with its number. When the cook says "shelf 4410 is free", Tomás crosses it off and may lend it to the next cook who asks. He trusts everyone completely. He never checks whether a shelf is really empty, and he keeps no list of who borrowed what.

For a week, things go wrong in three different ways. Ama forgets to return her shelves whenever an order is cancelled; by Friday the storeroom is "full" although half the shelves hold nothing anyone needs. Bruno and his assistant both return the same shelf, and Tomás, crossing it off twice, lends it to two cooks at once. And Chen returns a shelf but keeps using it, so his flour ends up in someone else's soup.

On Saturday the head chef changes one rule: every borrowed shelf gets an owner's tag, and the shelf is returned automatically when its owner leaves the kitchen, on every path, cancelled order or not. The three problems mostly disappear. This chapter is that week, in C++.

What you will be able to do

  • Explain what new and delete do (allocate and construct; destroy and deallocate) and their array forms.
  • Recognise the classic manual-memory bugs: leak, double free, mismatched delete, use after free.
  • Find each of these bugs with AddressSanitizer and LeakSanitizer, and read their reports.
  • Explain why an owner object (RAII, smart pointer) removes these bugs on every path, including early returns and exceptions.
  • Decide when raw new/delete still appear in serious code (allocators, kernels) and how to contain them.
Jargon box
new expression
Simple words: "make me an object on the heap and give me its address." Analogy: asking the storeroom manager for a shelf and stocking it. Precise: an expression that obtains storage by calling an allocation function (operator new) and then constructs an object (or array of objects) in it; it yields a pointer to the object. If allocation fails it throws std::bad_alloc (in the default form). D1
delete expression
Simple words: "destroy this heap object and give its memory back." Analogy: clearing the shelf and handing it back. Precise: an expression that runs the destructor of the object a pointer points to and then calls a deallocation function (operator delete) to release the storage; delete[] does the same for an array created by new[]. Deleting a null pointer does nothing. D1
Memory leak
Simple words: heap memory that is never given back. Analogy: a shelf nobody returns. Precise: dynamically allocated storage that the program no longer references and never deallocates; it stays reserved until the process ends. LeakSanitizer reports it at exit. D3 D6
Double free
Simple words: giving the same memory back twice. Analogy: returning the same shelf twice, so it can be lent to two cooks. Precise: calling delete (or free) a second time on a pointer whose storage was already deallocated; undefined behaviour that can corrupt the allocator's data structures. D1 D3
Use after free
Simple words: using heap memory after giving it back. Analogy: still putting flour on a shelf you returned. Precise: accessing an object through a pointer after the object was deleted; undefined behaviour, a special case of a dangling pointer (F2-19, F2-23). D1
Ownership
Simple words: being the one responsible for giving something back. Analogy: the owner's tag on a borrowed shelf. Precise: the responsibility for ending an object's lifetime and releasing its resources; in modern C++ it is expressed by an owner object (a container, a smart pointer, an RAII handle) rather than by a raw pointer. D4
Smart pointer
Simple words: an object that holds a pointer and deletes the object for you at the right time. Analogy: the shelf with an owner's tag that is returned automatically. Precise: a class template, such as std::unique_ptr or std::shared_ptr, that owns a dynamically allocated object and releases it in its destructor (RAII, F2-11). F2-22 covers them in detail. D1 D2
LeakSanitizer (LSan)
Simple words: a checker that lists, at the end of the run, memory that was never given back. Analogy: a closing-time inspection of the storeroom. Precise: a run-time leak detector that is part of AddressSanitizer on Linux; at process exit it scans memory for heap blocks no longer referenced and prints where each was allocated. D6

The idea in pictures

Figure 1 shows the two steps hidden in each of new and delete, and the four ways the pairing goes wrong.

Layer 1 — the kid explanation

new asks the heap for room and builds an object there. You get back a pointer, a note with the address. delete takes that pointer, tidies the object away, and gives the room back.D1

That sounds easy, and for one object in one straight line of code it is. Trouble starts when a function can leave early, or when two parts of a program both think they must clean up. Forget once and the memory is lost until the program ends: a leak. Clean up twice and the heap's own records get confused: a double free. Clean up and keep using it: a use after free.D3

You already know the cure from SP102: RAII. Put the pointer inside an object whose destructor does the delete. Then leaving the function, by any door, cleans up exactly once. That object is a smart pointer, and from the next chapter on you will almost never write delete yourself.D2 D4

Layer 2 — the student explanation

Two steps each way

A new expression first obtains raw storage by calling an allocation function, operator new(std::size_t), and then constructs the object in it; if the constructor throws, the storage is released again automatically.D1 A delete expression runs the destructor and then calls operator delete to release the storage.D1 Listing 1 shows the pairs: "made soup" appears at new, "destroyed soup" at delete.R1 The separation matters later: allocators (F2-25's project, curriculum B5) provide the raw-storage step, and the kernel track writes its own operator new and operator delete (curriculum 1.2).S1

Arrays: new[] needs delete[]

new T[n] creates an array of n objects and must be released with delete[], which destroys all n elements; releasing it with plain delete (or a single object with delete[]) is undefined behaviour.D1 GCC 13 recognised the mismatch in mismatch.cpp and, with the course's -Werror, refused to compile it (-Wmismatched-new-delete, reproduced in the mistakes section).R4 In real code the simplest rule is: never write new[]; use std::vector.D4

The problem is paths, not syntax

Each new must be matched by exactly one delete on every path the program can take. Listing 2's printBill has two paths out; only one reaches delete, so the zero-total bill leaks: LeakSanitizer reports 16 bytes allocated at leak.cpp:13 and never freed.R2 Exceptions add invisible paths: in Listing 4, cookRaw throws between new and delete, the delete is skipped, and the sanitizer reports a 1-byte leak (the size of an empty Pan); cookOwned, identical except for the owner object, prints "pan returned" during the same exception.R5 Code that looks balanced on the page can be unbalanced at run time.

Ownership: who calls delete?

Listing 3 shows the opposite failure. clearTable deletes the tray it was given, and main deletes it again: a double free, which AddressSanitizer reports with three stack traces (the second free, the first free, and the allocation).R3 Nothing in the type Tray* says who must delete. The C++ Core Guidelines' answer is to make ownership visible in types: a raw pointer T* never owns; an owner is an object whose destructor releases the resource.D4 With std::unique_ptr<Bill> (Listing 2's fixed version) every path frees the bill exactly once, and the sanitizer is silent.R2

Why smart pointers, in one sentence

Because "delete exactly once, on every path, by the right party" is a property a human cannot check reliably in a large program, but a destructor guarantees it by construction (F2-11); smart pointers are the standard library's RAII owners for heap objects.D2 D4

Layer 3 — the engineer's depth

Replaceable allocation functions. operator new and operator delete are ordinary functions that a program may replace with its own definitions, in several overloads: plain, array, sized (the deallocation function receives the object size) and aligned (for over-aligned types).D1 The sanitizer reports in this chapter show the sized form at work: the double free went through operator delete(void*, unsigned long).R3 Your kernel will define all of these on top of its own heap (curriculum B5: "General-purpose kernel allocation with all forms of operator new and delete").S1

Placement new. A form of new takes an address and only constructs (no allocation): new (buffer) T(args). The object must then be destroyed by an explicit destructor call, and the storage released by whoever provided it. Allocators, containers and kernels use it; application code almost never should.D1 Curriculum 1.1 lists "lifetime of objects created in raw memory (placement new, start of lifetime)" as an undefined-behaviour trap for kernels; F2-23 returns to it.S1

Failure. The default new throws std::bad_alloc when it cannot allocate; new (std::nothrow) T returns nullptr instead.D1 On Linux a large allocation may succeed even when physical memory is short, because the kernel can overcommit and fail later.

Not verified — check before relying on this

Linux's overcommit behaviour (when an allocation that succeeded can later lead to the process being killed by the out-of-memory killer) depends on kernel settings that were not checked in this build. Check the Linux kernel documentation on overcommit accounting (the vm.overcommit_memory setting) for the kernel version you use.

How the sanitizer knows. AddressSanitizer replaces the allocator. Freed blocks are not reused at once but kept in a quarantine and marked as poisoned in shadow memory, so a later access or second free is recognised; each block remembers the stack trace of its allocation and its deallocation, which is where the three traces in its reports come from.D6 LeakSanitizer runs at exit and looks for heap blocks that no pointer in memory still refers to.D6 Two consequences: a leak whose pointer still sits somewhere in memory at exit can be missed, and a sanitizer only checks the code it instrumented; reads performed inside an uninstrumented library may not be checked.D6

How the hardware actually does it

The hardware has no idea what new is. A general-purpose allocator such as the C library's obtains large regions of virtual address space from the kernel, then hands out pieces of them, keeping its bookkeeping (block sizes, free lists) in the same memory, often just before each block it returns.D3 D7 That is why a double free or a write past the end of a block can corrupt the allocator itself and crash much later, in an unrelated new (F2-23's forensic lab). The pages behind a heap region are mapped on first touch by the kernel's page-fault handler (curriculum B4); freeing a small block normally returns it to the allocator's lists, not to the kernel.D3

Where the analogy breaks


    

  1. Tomás would notice a returned shelf being used. A human manager might see Chen's flour on a shelf that was handed back. The real allocator does not; only a sanitizer, which deliberately delays reuse and marks freed memory, notices (Layer 3).D6
    2. 

  2. Shelves are returned whole, memory bookkeeping is shared. Returning a shelf twice in the kitchen costs one confused manager. In memory, a double free can corrupt the allocator's own data, so the crash may come later in code that did nothing wrong.D3
    3. 

  3. Leaked shelves come back at closing time. The operating system reclaims all of a process's memory when it ends, so a leak in a short program is invisible; in a server, a robot controller or a kernel that never "closes", leaks accumulate until memory runs out.D3
    4.

Where you came from: F2-20 showed that dynamic objects live until someone ends them; SP102 (F2-11) built RAII wrappers for files and locks. Summary


    

  • new = allocate + construct; delete = destroy + release; arrays need new[]/delete[].
