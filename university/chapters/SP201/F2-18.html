Story hook

Analogy

On her first morning in the restaurant, Nadia is sent to the big pantry down the corridor. She expected a cupboard. Instead she finds one endless shelf, divided into small slots, and every slot has a number painted on its edge: 0, 1, 2, 3, and on and on, far beyond anything she can count.

"Every slot holds exactly one small thing," says Tomás, the storeroom manager. "A jar of salt fits in one slot. A sack of rice needs four slots side by side. When the chef wants the rice, he does not shout 'the rice!'. He writes the number of its first slot on a note, and you walk to that slot."

Nadia looks along the shelf. Nothing on it says "rice" or "salt". There are only numbered slots with something in them. Whether slots 40 to 43 hold one sack of rice or four jars of salt is written on the chef's recipe, not on the shelf. That, it turns out, is exactly how a computer's memory works, and this whole course rests on it.

What you will be able to do

  • Explain memory as a long row of numbered bytes, and what an address is.
  • Measure the size of C++ types with sizeof and the addresses of objects with & on your own machine, and say which results are guaranteed and which belong to your platform.
  • Compute the address of any element of an array from the address of its first element.
  • Explain byte order (endianness) and show it by printing the bytes of a number.
  • Diagnose a value that "came out backwards" after it was copied as raw bytes.
Jargon box
Byte (in C++)
Simple words: the smallest box of memory that has its own number. Analogy: one slot on the pantry shelf. Precise: the fundamental storage unit of the C++ memory model; it is at least 8 bits wide, and every byte has a unique address; sizeof(char) is 1 by definition. On the machines of this course a byte is 8 bits (MA102). D1
Address
Simple words: the number of a memory box. Analogy: the number painted on a slot's edge. Precise: a value that identifies one byte of memory; the address of an object is the address of its first byte. KID101 met the word at L0 (glossary); this chapter makes it exact. D1 D3
Object (in C++)
Simple words: a piece of memory that holds one value of one type. Analogy: a sack of rice that occupies some neighbouring slots. Precise: a region of storage with a type, a size and a lifetime (F2-23); a variable names an object. Not the same word as "object" in "object-oriented": an int is an object too. D1
sizeof
Simple words: asks "how many boxes does this take?". Analogy: how many slots the sack needs. Precise: an operator that yields the number of bytes in the object representation of its operand's type, as a value of type std::size_t, computed at compile time. D1
Object representation
Simple words: the exact bytes an object is made of. Analogy: what you actually see in the slots, with no labels. Precise: the sequence of sizeof(T) unsigned char values taken up by an object of type T; the value the program sees is an interpretation of these bytes by the type. D1
Endianness (byte order)
Simple words: which end of a big number goes into the first box. Analogy: whether the sack's label is written starting at the left slot or the right slot. Precise: the order in which the bytes of a multi-byte scalar are stored at increasing addresses: little-endian stores the least significant byte at the lowest address, big-endian the most significant byte. C++20 lets a program ask with std::endian::native. D1 D3
Address space
Simple words: the whole range of box numbers a program may use. Analogy: the full length of the numbered shelf. Precise: the set of addresses a running program can name; on the Linux systems of this course each process has its own virtual address space, which the operating system and hardware map onto physical memory (F3, curriculum B4). D3

Layer 1 — the kid explanation

Memory is a very long shelf of tiny boxes. Each box holds one byte: eight switches, so a number from 0 to 255 (MA102). Each box has a number, its address. The first box is number 0, the next is 1, and so on.D1 D3

Small things fit in one box. A letter like 'A' is one byte. Bigger things need several boxes next to each other. An int on your computer takes four, a double takes eight. When the program wants a value, it uses the address of its first box and knows from the type how many boxes belong to it.D1 R1

The boxes themselves do not know what they hold. Four bytes could be one whole number, or four letters, or part of a decimal number. The program's types decide. If two parts of a program disagree about what the bytes mean, the program reads nonsense, and nobody warns it. You will see that happen in the forensic lab.

Layer 2 — the student explanation

Bytes and addresses

The C++ standard describes the memory available to a program as one or more sequences of contiguous bytes, each byte with a unique address.D1 A byte must be able to hold any character of the basic character set, so it has at least 8 bits; on every machine this course uses it has exactly 8, and sizeof(char) is 1 by definition.D1 Every object occupies a region of bytes; scalar objects such as an int occupy neighbouring bytes, and the address of the object is the address of its first byte.D1 The operator & (address-of) gives you that address; F2-19 turns it into a pointer.

How big is a type?

sizeof(T) is the number of bytes in an object of type T, known at compile time.D1 The standard fixes very few sizes: sizeof(char) is 1, and the integer types are ordered so that each is at least as wide as the one before it (short ≤ int ≤ long ≤ long long), with minimum widths.D1 Everything else is decided by the platform's application binary interface (ABI). On this build's machine (x86-64 Linux), Listing 1 printed 4 for int, 8 for long and 8 for a pointer.R1 Those values match what the System V AMD64 ABI specifies for that platform, but on 64-bit Windows long is 4 bytes, so a program must never assume them.D5

Not verified — check before relying on this

The claim that 64-bit Windows compilers make long 4 bytes wide (the "LLP64" data model) was not checked against a Microsoft document in this build; no Windows toolchain was available to run Listing 1. Check the Microsoft C++ documentation page on the sizes of fundamental types (Data Type Ranges) and run Listing 1 there.

When you need an exact width, use the fixed-width types from <cstdint>: std::uint8_t, std::int32_t, std::uint64_t and so on (MA102 used them). They are exactly as wide as their names say on every platform that provides them.D1

Arrays: neighbours, no gaps

The elements of an array are stored one after another without gaps, so element k of an array of T starts exactly k × sizeof(T) bytes after element 0.D1 Listing 1 prints the addresses of the four elements of an int array: they differ by 4 bytes each, and sizeof of the whole array is 16.R1 This one rule is the basis of pointer arithmetic (F2-19), of std::vector's fast indexing (SP101) and of spans (F2-25).

Bytes versus values

An int holding 258 is four bytes. Which four? 258 is 0x00000102 in hexadecimal: the bytes 0x00, 0x00, 0x01 and 0x02 from most to least significant. The order in which they lie at increasing addresses is the machine's byte order.D3 On a little-endian machine, which this build's machine reported itself to be, the least significant byte comes first, so memory holds 02 01 00 00.R2 R4 The program normally never notices: it reads and writes whole ints and the hardware handles the order. Byte order becomes visible exactly when bytes leave the program as bytes: written to a file, sent on a network, or copied with std::memcpy into a buffer that another program decodes.D3

C++ lets you look at the bytes of an object without breaking any rule by copying them into an array of unsigned char (or std::byte), either with std::memcpy or with C++20's std::bit_cast.D1 Listing 2 does it with std::bit_cast. F2-24 shows which bytes of a structure are padding, and F2-23 explains why "just cast the pointer" is not a safe way to do the same thing.

Layer 3 — the engineer's depth

Addresses are virtual. The numbers your program prints are addresses in its own virtual address space. The operating system and the processor's memory-management unit translate each one to a physical location in DRAM, page by page; two processes can print the same address and mean different physical bytes.D3 You will build that translation yourself in the kernel track (curriculum B4, paging). Nothing in this course depends on the physical location of a byte.

Addresses printed under a sanitizer look different. Every listing in this course is built with AddressSanitizer (-fsanitize=address), which surrounds objects with unused "red zones" so it can detect overruns (F2-21, F2-25).D6 Look at the lab output: in the sanitizer build, the local variables of main are 0x30 or more bytes apart, while the plain build packs them within a few bytes of each other.R3 The local variables in the sanitizer build also sit at addresses starting 0x7f…, unlike the plain build's 0x7ffe…; this is consistent with the sanitizer placing locals in a separate "fake stack" area, a feature its documentation describes for detecting use of a local after its function returned.D6

Not verified — check before relying on this

Whether the GCC 13 AddressSanitizer runtime of this build uses its fake stack by default (which would explain the 0x7f… addresses of locals in Listings 1 and 3), and which option controls it, was not checked against documentation. Check the AddressSanitizer documentation (the "Use-after-return" section of the Clang AddressSanitizer document and the run-time flags list of the sanitizers project) for the version that ships with the GCC recorded in the logs.

What the standard does not promise. It does not promise that two separate variables are next to each other, in declaration order, or in any particular order; it does not promise that addresses increase or decrease from one call to another; and comparing with < two pointers into different objects does not have a specified result.D1 The lab shows that the plain build placed count right after letter but dish after orders, the reverse of their declaration order.R3 Treat every layout of separate variables as an observation of one build, not a rule.

Converting a pointer to a number. The listings convert addresses to std::uintptr_t with reinterpret_cast so that they can be printed in hexadecimal and subtracted. std::uintptr_t is an optional type that, where it exists, can hold any object pointer converted to an integer and back.D1 Subtracting two such integers gives a byte distance on this platform; the portable way to get an element distance inside one array is pointer subtraction (F2-19). Kernel code does this conversion all the time (curriculum 1.1 asks for strong types for physical and virtual addresses), which is why you meet it here, in a controlled form.S1

How the hardware actually does it

The processor names memory with addresses in its load and store instructions. A load says, in effect, "bring n bytes starting at address a into a register"; the width n is chosen by the instruction, which the compiler picks from the C++ type (HW202, F1-24).D3 On the way, the virtual address is translated, the caches are checked (F1-32, F1-33) and, if needed, a whole cache line is fetched from DRAM. The byte order is a property of the instruction set: x86-64 is little-endian, which is what std::endian::native reported in this build.D3 R2 F2-24 adds the last hardware fact this course needs: many loads work best, or only work, when the address is a multiple of the access width (alignment).

Worked example

An int array a of 100 elements starts at address 0x7ffc1000, and sizeof(int) is 4 (as Listing 1 printed on this machine).

  1. Element 1 starts 1 × 4 = 4 bytes later: 0x7ffc1000 + 4 = 0x7ffc1004.
  2. Element 3: 3 × 4 = 12 = 0xC bytes later: 0x7ffc100c.
  3. Element 9: 9 × 4 = 36 = 0x24 bytes later: 0x7ffc1024. (36 is 2 × 16 + 4, so 0x24.)
  4. The whole array is 100 × 4 = 400 bytes = 0x190. Its last byte is at 0x7ffc1000 + 0x190 − 1 = 0x7ffc118f.
  5. Element 99 starts at 0x7ffc1000 + 99 × 4 = 0x7ffc1000 + 396 = 0x7ffc118c, and its four bytes end at 0x7ffc118f: consistent.

Where the analogy breaks


    

  1. Shelf slots are physical; addresses are not. A pantry slot number names one place in the building. A C++ address is virtual: the same number in two programs names two different physical bytes, and the operating system can move the physical byte without the program noticing (Layer 3).D3
    2. 

  2. An empty slot is visibly empty; a byte never is. A byte always holds some bit pattern. Memory that "holds nothing" in the program's mind still contains old values, which is why reading an uninitialised variable gives a random-looking number instead of "nothing".D1
    3. 

  3. A sack spans slots in one obvious direction. A multi-byte value has a byte order that the shelf picture hides; two machines can store the same number with its bytes in opposite orders (the forensic lab).D3
    4.

Summary


    

  • Memory is a long row of bytes; every byte has a number, its address.
    • 

  • An object occupies sizeof(T) neighbouring bytes; its address is that of its first byte.
    • 

  • Only sizeof(char) == 1 is fixed; other sizes come from the platform ABI. Use fixed-width types when width matters.
    • 

  • Array elements are contiguous: element k starts k × sizeof(T) bytes after element 0.
    • 

  • Byte order decides which byte of a number has the lowest address; it shows up when bytes leave the program.
    • 

  • Look at bytes with std::memcpy or std::bit_cast into unsigned char.
    • 

  • Addresses are virtual, randomised between runs, and laid out differently under sanitizers: observe them, do not rely on them.

Forensic lab answer key


Observation: the writer stored 02 01 00 00; 258 = 0x00000102. Hypotheses: (H1) file corruption — ruled out: the stored bytes are exactly the bytes of 258 in little-endian order, and both sides ran in the same program with no file at all; (H2) byte-order disagreement — confirmed: readHighByteFirst (lines 9–13) treats byte 0 as the most significant, so it computes 0x02 × 224 + 0x01 × 216 = 33,554,432 + 65,536 = 33,619,968, exactly the printed value. Root cause: the writer copies the in-memory representation (little-endian on this machine, line 19) while the reader assumes big-endian. Fix: define the file format's byte order and make the writer produce it with shifts (b[0] = value & 0xFF; b[1] = (value >> 8) & 0xFF; …), and the reader decode the same order; then the program's own byte order no longer matters. Test: a round-trip test with a value whose bytes all differ (0x11223344) and a check of the exact file bytes. How the evidence was made: backwards.cpp run by run_lab.sh in this build (R4).
