Story hook

Analogy

The pantry shelves are numbered slots. Small jars fit anywhere. The big eight-slot crates of flour are different: the shelf frame has supports only at every eighth slot, so a crate must start at slot 0, 8, 16 and so on. Four-slot boxes of rice must start at a multiple of four.

Wei packs an order kit in the order the recipe lists it: one jar of salt, a crate of flour, one jar of chili, a box of rice. The salt goes in slot 0; the flour cannot start at slot 1, so slots 1 to 7 stay empty and the flour takes 8 to 15. Chili in 16, three empty slots, rice in 20 to 23. The kit takes 24 slots and a third of them are air. Ana repacks the same four items, biggest first: flour 0 to 7, rice 8 to 11, salt 12, chili 13, two empty slots to round up. Sixteen slots. Same food, a third less shelf.

The compiler packs every struct exactly like this. This chapter shows you how to read and predict the packing, why it exists, and how it trips up programs that send raw objects to other machines.

What you will be able to do

  • Predict sizeof, alignof and member offsets of a simple struct, and check the prediction with offsetof.
  • Explain what alignment and padding are and why compilers insert padding.
  • Reorder members to reduce padding, and measure the saving.
  • Lock down a layout that other code depends on with static_assert, and check type properties (standard-layout, trivially copyable) with type traits.
  • Read bytes safely with std::memcpy instead of misaligned or type-punned pointers.
  • Diagnose a data-exchange bug caused by sending a struct's raw bytes (forensic lab), and fix it with explicit serialisation.
Jargon box
Alignment
Simple words: the rule that an object of some type must start at an address that is a multiple of a certain number. Analogy: crates may start only at slots that are a multiple of 8. Precise: an implementation-defined power of two, given by alignof(T), such that every object of type T has an address that is a multiple of it; on the x86-64 build used here alignof(int) was 4 and alignof(double) 8. D1 R1
Padding
Simple words: unused bytes the compiler puts inside or at the end of a struct. Analogy: empty slots left so the next crate lines up. Precise: bytes of an object's representation that belong to no member; inserted so that each member meets its alignment and so that the size is a multiple of the struct's alignment (making arrays work); their values are unspecified unless the object was zero-initialised in a way that sets them. D1 D3
alignof
Simple words: the operator that tells you a type's alignment. Analogy: reading the "starts every N slots" label on a crate. Precise: alignof(T) yields a std::size_t constant, the alignment requirement of T; alignas requests a stricter one. D1
offsetof
Simple words: a macro that tells you at which byte a member starts inside its struct. Analogy: "the rice starts at slot 20 of the kit". Precise: offsetof(type, member) from <cstddef>, a constant of type std::size_t; conditionally supported for types that are not standard-layout. D1
Standard-layout type
Simple words: a struct simple enough that its layout follows the C rules. Analogy: a kit packed by the published packing rules, without hidden extras. Precise: a class type with, among other conditions, all non-static data members having the same access control, no virtual functions or virtual base classes, and members that are themselves standard-layout; tested with std::is_standard_layout_v. D1
Trivially copyable type
Simple words: a type whose objects may be copied by copying their bytes. Analogy: a kit you can duplicate by photocopying the shelf. Precise: a type whose copy and move operations and destructor are trivial (or deleted, with at least one eligible); for such types, copying the bytes with std::memcpy into another object of the type gives that object the same value. Tested with std::is_trivially_copyable_v. D1
Strict aliasing
Simple words: the rule that you may read an object only as its own type (or as raw bytes). Analogy: a flour crate must be opened as a flour crate, not as a box of rice. Precise: accessing an object through a glvalue of a type other than its dynamic type, a corresponding signed/unsigned type, or char/unsigned char/std::byte is undefined behaviour. D1
Serialisation
Simple words: turning an object into a sequence of bytes in an agreed format, and back. Analogy: writing the kit's contents onto a delivery slip in an agreed order, instead of shipping the shelf. Precise: encoding of values into a defined external representation (field order, sizes, byte order, no padding) independent of the in-memory object representation; decoding is the reverse. D3

Layer 1 — the kid explanation

Memory is a long row of numbered byte boxes (F2-18). A number like an int takes four boxes in a row, a double takes eight. The computer likes each value to start at a box number that "fits" it: an int at a multiple of 4, a double at a multiple of 8. That rule is called alignment.D1

When you put several values together in a struct, the compiler keeps the rule for each of them. If a double comes right after a one-byte char, it cannot start at box 1, so the compiler leaves boxes 1 to 7 empty. Those empty boxes are padding.D3 Listing 1 measured it: the same four values took 24 boxes in one order and 16 in another.R1

Usually padding is invisible and harmless. It matters when you have millions of objects (wasted memory), and when you send an object's bytes to another program that does not know about the empty boxes.

Layer 2 — the student explanation

The layout rules, as the compiler applied them

For the structs in this chapter the compiler followed three rules, which you can check against every number in Listing 1 and the lab:D3 D7

  1. Members are placed in declaration order (C++ guarantees increasing addresses for members with the same access control).D1
  2. Each member starts at the next offset that is a multiple of its alignment.
  3. The struct's alignment is the largest member alignment, and its size is rounded up to a multiple of that alignment, so that in an array every element's members are aligned too.

Apply them to Loose (char size; double price; char spicy; int table;): size at 0; price needs a multiple of 8, so 8; spicy at 16; table needs a multiple of 4, so 20; it ends at 24, already a multiple of 8. Size 24. Listing 1 printed exactly "offsets: size 0, price 8, spicy 16, table 20" and "sizeof 24, alignof 8".R1 Sorting members from largest alignment to smallest (Tidy) leaves padding only at the end: 16 bytes; 1000 objects took 24000 versus 16000 bytes.R1

Seeing the padding

Listing 2 copies a Loose object's 24 bytes into an unsigned char array with std::memcpy and prints them. The object was value-initialised (Loose order{};), which zero-initialises it including padding, so the padding shows as 00.D1 R2 Without that, the padding bytes have unspecified values, and two objects with equal members can differ byte by byte; that is why comparing structs with memcmp or hashing their raw bytes is unreliable.D1 You can also read price (2.5) in bytes 8 to 15: 00 00 00 00 00 00 04 40, the IEEE 754 encoding 0x4004000000000000 stored little-endian (F2-18, MA102).R2

Locking a layout

When other code depends on a layout (a file format, a device register block in curriculum B3, a message header), do not hope; assert. Listing 3 states static_assert(sizeof(Header) == 8, ...) and static_assert(offsetof(Header, sequence) == 4, ...); if a later edit or a different compiler changes the layout, the build fails with your message.D1 Listing 3 also checks two properties with type traits: Header is standard-layout and trivially copyable (safe to copy as bytes); Named, which holds a std::string, is not trivially copyable, because its bytes include a pointer to heap memory it owns (F2-22).R3

Reading bytes the right way

Data arriving from a file or network is a byte array. Casting packet + 1 to const std::uint32_t* and dereferencing is undefined behaviour twice over: the address is misaligned for uint32_t, and no uint32_t object lives there (strict aliasing).D1 Listing 4 shows UBSan reporting "load of misaligned address … which requires 4 byte alignment" at line 16, while the program still printed 42: on this x86-64 machine the misaligned load happened to work.R4 The std::memcpy version at line 12 is well-defined at any address, and compilers typically turn a small fixed-size memcpy into a single load where the processor allows it.D5

Layer 3 — the engineer's depth

Who decides the layout. The C++ standard fixes only the order of members and leaves sizes and alignments to the implementation; the platform's ABI document (for x86-64 Linux, the System V AMD64 psABI; for AArch64, the procedure call standard; for RISC-V, the RISC-V ELF psABI) pins them down so that separately compiled code agrees.D1 D7 In this build, Listing 1 and the lab program gave identical results when cross-compiled for AArch64 and RISC-V 64 and run under QEMU user-mode emulation; that shows what those compilers chose, not what real hardware does at run time, and no real AArch64 or RISC-V hardware was used.R6





Changing alignment. alignas(64) on a struct raises its alignment, for example to give each thread's counter its own cache line (OS301/HW301's false sharing). The reverse, packing (__attribute__((packed)) or #pragma pack), is a compiler extension, not standard C++; it removes padding but makes members misaligned, so taking a pointer or reference to such a member and using it is a classic source of faults on strict-alignment processors.D5 Prefer explicit serialisation (forensic lab) to packed structs for external formats.


Allocators and alignment. operator new and malloc return memory aligned for any fundamental type (alignof(std::max_align_t), typically 16 on x86-64 Linux); over-aligned types use the aligned forms of new since C++17.D1 Your bump and free-list allocators in F2-25 must therefore take an alignment argument and round addresses up, exactly as the compiler rounds offsets here.


Not verified — check before relying on this
The values alignof(std::max_align_t) == 16 on x86-64 Linux and the statement that some processors (older 32-bit ARM cores, some RISC-V implementations and many microcontrollers) trap or emulate slowly on misaligned loads were not measured in this build. Check by printing alignof(std::max_align_t) with the course command, and in the architecture reference manual of the processor you target (alignment fault behaviour), before relying on either.



How the hardware actually does it


Processors fetch memory in fixed-size, aligned pieces (cache lines of, typically, 64 bytes; HW202). An aligned 8-byte value never straddles two pieces; a misaligned one can, which may cost two accesses or, for an access straddling two pages, two address translations.D3 x86-64 handles ordinary misaligned loads in hardware, which is why Listing 4 printed 42; other architectures and some instructions (for example certain SIMD loads) require alignment and fault otherwise.D3 R4 Alignment rules let compilers emit single, fast instructions without checking addresses; padding is the price.


Not verified — check before relying on this
That the misaligned read in Listing 4 was executed as one ordinary load instruction (rather than split by the compiler) was not checked: the disassembly was not inspected, and the UBSan build adds its own code. Check with objdump -d on a build without sanitizers before using this listing as evidence about the processor.

Where the analogy breaks


    

  1. Shelf supports are physical; alignment is a rule. A crate cannot hang on a missing support. A misaligned value can often be read anyway (x86-64 did, R4); what breaks is the language contract, and the result may be a fault on another processor or a mis-optimisation on any.D1
    2. 

  2. Empty slots look empty. Padding bytes are not "empty"; they hold whatever was there before, unless zeroed, and they are copied and sent along with the object.D1
    3. 

  3. Ana can reorder a kit freely. Reordering members changes every offset; any file, message or device that depended on the old layout breaks. Only reorder types whose layout nothing outside the program sees.
    4.

Transition box

Where you came from: F2-18 showed that objects are bytes in numbered boxes, with an object representation you can copy out; F2-23 showed which accesses the language forbids. What carries over: sizeof, byte order, memcpy as the safe way to look at bytes, and the sanitizers. What changes: you now see that a struct's bytes include padding chosen by the compiler under alignment rules from the platform ABI, so an object's in-memory form is not a data format; anything that crosses a program boundary needs an explicit layout.D1 D7 What comes next: F2-25 turns from single objects to sequences: arrays, spans and the bounds you must not cross, and you will use alignment again in the course project's allocators.

Forensic lab: "The record that would not fit"


Scenario. The cold-room sensors report temperatures to the kitchen dashboard. The format document, agreed by both teams, says each record is 6 bytes: sensor id (1 byte), reading (4 bytes, lowest byte first), flags (1 byte). The sensor team's program sends a SensorRecord struct by copying its bytes. The dashboard shows sensor 3 reporting 3,892,314,112 with every alarm flag set. The sensor team says: "our struct has exactly those three fields, in that order, so the bug is on the dashboard."


Evidence pack. The sender's struct and its encoding, and the receiver's decoding, simulated in one program (header_bug.cpp), and its real output.

Summary


    

  • Every type has a size and an alignment; objects start at multiples of their alignment.
    • 

  • The compiler inserts padding so members are aligned and so arrays work; the struct's size is a multiple of its alignment.
    • 

  • Ordering members by decreasing alignment minimises padding; measured here, 24 bytes became 16.
    • 

  • Padding bytes are part of the object representation and have unspecified values unless zeroed.
    • 

  • Lock layouts that matter with static_assert; check copy-as-bytes safety with std::is_trivially_copyable_v.
    • 

  • Read from byte buffers with memcpy, never through misaligned or type-punned pointers.
    • 

  • An in-memory struct is not a file or wire format: serialise field by field.

Forensic lab answer key


Observation. The sender puts 12 bytes on the wire (sizeof(SensorRecord) = 12); the format promises 6. Byte map: 03 (id) at 0; padding at 1 to 3 (uint32_t needs a multiple of 4); e8 03 00 00 (1000 = 0x3E8, little-endian) at 4 to 7; 01 (flags) at 8; tail padding at 9 to 11 (size rounded to alignment 4). The receiver reads bytes 1 to 4 = 00 00 00 e8 lowest first: 0xE8000000 = 3,892,314,112, exactly the bad value; it reads flags from byte 5 = 03, which is the second byte of the reading.R7


Hypotheses. (H1, the sensor team's) the dashboard decodes wrongly — refuted: the receiver follows the agreed format exactly; with a correct 6-byte input it decodes correctly (see the fix). (H2) a transmission error — refuted: the bytes are deterministic and match the sender's own dump. (H3) the sender's raw struct bytes do not follow the format because of alignment padding — confirmed by the byte map.


Conclusion. The sender's bug. Problem 1 (visible): padding, which the format does not contain. Problem 2 (latent): byte order and type sizes are those of the sender's machine; on a big-endian sender the reading's bytes would be reversed even without padding. The in-memory representation is not a data format.


Fix and prevention. Encode field by field into exactly 6 bytes in the documented order and byte order, and decode the same way (header_fixed.cpp, below). Add a golden test: encoding {3, 1000, 1} must give exactly 03 e8 03 00 00 01. The reference fix printed exactly that and decoded the original values.R7
