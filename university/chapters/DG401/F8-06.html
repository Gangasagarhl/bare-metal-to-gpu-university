Story hook

The teaching campus is trying to perfect one soup recipe. Last month one hall tasted 64 bowls a night and adjusted the recipe a little after each night. Now four halls each taste 16 bowls a night, pool their tasting notes, and every hall adjusts its copy of the recipe in exactly the same way. If they do it right, the four halls together make the very same recipe changes as the one hall did, night after night, only faster.

The first week goes wrong twice. On Monday, nobody handed out the starting recipe; each hall began from its own grandmother's version, and although they pooled their notes faithfully, the four recipes never became the same. On Thursday, each hall wrote "average of my 16 bowls" and then the four averages were added, not averaged: every change was four times too strong. Both mistakes are one line of code. This chapter is about writing that step correctly, first with a ring you built, then with a real communication library.

What you will be able to do

  • Explain a data-parallel training step: shard the batch, compute local gradients, all-reduce them, apply the same update on every replica.
  • Implement it with your own ring all-reduce and with a real library (MPI here; NCCL or RCCL on GPUs), using the correct scaling of the gradient.
  • Verify that N workers reproduce the 1-worker loss curve within a stated tolerance, and that replicas stay identical.
  • Use a GPU collective library's model correctly: communicators, one rank per GPU, collectives on streams, group calls, debug output (from the documentation, checked on your hardware).
  • Diagnose the two classic data-parallel bugs (no initial broadcast; summed instead of averaged gradients) from loss curves and replica differences.
Jargon box
Data-parallel training
Simple words: several workers train the same model, each on a different part of every batch, and combine their results after every step. Analogy: four halls tasting different bowls of the same recipe and pooling notes. Precise: each of N workers holds a full copy of the parameters, computes the gradient of the loss on its shard of the global batch, and an all-reduce combines the gradients so every worker applies the same update. D8 C1
Replica (model)
Simple words: one worker's copy of the model's parameters. Analogy: one hall's copy of the recipe. Precise: the parameters held by one data-parallel worker; correct data parallelism keeps all replicas identical after every step. R1
Global batch and shard
Simple words: all the examples used for one step, and each worker's part of them. Analogy: the 64 bowls of a night, and each hall's 16. Precise: the global batch size B sets the effective batch of the update; with N workers each processes a shard of about B/N examples. R1
Gradient bucketing
Simple words: sending gradients in a few large groups instead of one tensor at a time. Analogy: collecting notes into a few big envelopes before sending them round. Precise: packing many parameter gradients into buckets that are all-reduced as single messages, so the per-message start-up cost α is paid a few times per step, and starting each bucket's all-reduce as soon as its gradients are ready, overlapping it with the rest of the backward pass (as described in the PyTorch DDP paper, title only). D8
Scaling efficiency
Simple words: how much of the ideal N-times speed-up you actually got. Analogy: four halls should do four nights' tasting in one night; did they? Precise: throughput with N workers divided by (N × throughput with 1 worker), for the same global batch per worker (weak scaling) or the same global batch (strong scaling); state which. C1
Group call (NCCL/RCCL)
Simple words: telling the library "these several calls belong together; start them as one". Analogy: one bell for several carts. Precise: NCCL's ncclGroupStart / ncclGroupEnd bracket, used when one thread issues collectives for several GPUs or fuses several operations (from the NCCL documentation; not verified in this build). D1

The idea in pictures

Layer 1 — the kid explanation

If one person tastes 64 bowls and four people taste 16 each, they learn the same thing, as long as they pool their notes properly. Two rules: everyone starts from the same recipe, and the pooled note is the average of all 64 bowls, not the sum of four averages. Then everyone changes their copy in the same way, and the copies stay the same forever.

Layer 2 — the student explanation

Why the sum of shard gradients is the batch gradient

The loss of a step is the mean over the global batch of B samples: L = (1/B) Σi ℓi. Its gradient is (1/B) Σi ∇ℓi (MA302). Split the sum over the workers' shards: worker w computes gw = (1/B) Σi in shard w ∇ℓi, and the all-reduce sum Σw gw is exactly the 1-worker gradient. Every worker receives the same sum and applies the same update, so replicas that start equal stay equal. Dividing each shard by its own size and then summing (the Thursday bug) gives N times the gradient when shards are equal. Dividing by the global B, or summing and then dividing by N, are both correct. R1

The step in code

train.hpp is the whole step: initialise every replica from the same seed (the "broadcast"), and for every step compute each worker's loss sum and gradient on samples [s·64 + w·64/N, s·64 + (w+1)·64/N), divide by 64, put the loss sum in one extra element, run the F8-05 ring all-reduce over the 98 floats, and update. Listing 1 runs it for 1, 2, 4 and 8 workers. R1

What "the same loss curve" means

The 1-worker loss fell from 1.42552 at step 0 to 0.04325 at step 299. With 2, 4 and 8 workers the loss differed from the 1-worker loss at most steps (240 to 255 of 300), but never by more than 2.38·10−7; the final parameters differed by at most 1.79·10−7; and the replicas were identical at every step. R1 The tiny differences are rounding: the sum over 64 samples is added in a different order when it is split into shards and summed by a ring (F8-05). That is why the milestone says "within a stated tolerance": Listing 1 states 10−4 on the loss, and requires bit-identical replicas.

With a real library

Listing 2 does the same with Open MPI: one process per worker, MPI_Bcast of rank 0's parameters, then one in-place MPI_Allreduce per step. With 1, 2 and 4 processes the logged losses agree to six digits (the step 0 loss prints as 1.425524 with one process and 1.425525 with two and four), and no rank's parameters differ from rank 0's. R2 The pattern is the one used with NCCL or RCCL on GPUs; the API names differ.

Layer 3 — the engineer's depth

In one line of analogy: the halls now share one delivery company with its own rules: every hall must book the same deliveries in the same order, and the delivery runs on the hall's own kitchen schedule, not on the head chef's clock.

The rules of a collective library

Every collective library has the rule MPI states for its collectives: all ranks of a communicator call the same collectives in the same order with matching arguments (F8-01). D3 In Listing 2 that is easy: one broadcast, then one all-reduce per step. In a real framework the gradients of many tensors are bucketed, and the order in which buckets become ready may differ between ranks unless the framework fixes it; the PyTorch DDP paper describes this problem and its bucketing design (title only). D8 A rank that calls collectives in a different order hangs or, worse, adds the wrong tensors together.

The NCCL and RCCL model

Not verified — check before relying on this

NCCL and RCCL are not installed in this build, and their documentation was not opened. From the NCCL documentation, as generally described: a communicator is created per GPU, either by one process for all its GPUs (ncclCommInitAll) or by one process or thread per GPU, where rank 0 creates an ncclUniqueId with ncclGetUniqueId, distributes it to all ranks by some other means (for example an MPI_Bcast), and every rank calls ncclCommInitRank(&comm, nranks, id, rank) with its own GPU current. Collectives such as ncclAllReduce(sendbuff, recvbuff, count, ncclFloat, ncclSum, comm, stream) and ncclBroadcast take device pointers and a CUDA stream, return once the operation is enqueued, and complete in stream order, so the optimizer kernel queued after them on the same stream sees the result without a host synchronisation. When one thread issues collectives for several GPUs, or several collectives should be launched together, they are bracketed by ncclGroupStart() / ncclGroupEnd(). Communicators are released with ncclCommDestroy (or aborted with ncclCommAbort on errors). The NCCL_DEBUG environment variable (for example INFO) prints the version, the detected topology and the chosen rings or trees. RCCL keeps the same API names with HIP streams. Every name, signature and behaviour in this box must be checked against the NCCL and RCCL documentation and headers of your installed versions before use.

Translating Listing 2 to that model changes three things. The buffers are on the GPU, so forward, backward, the division by B and the update are kernels (your E6/E7 GEMM kernels from CU302 in the milestone). The all-reduce goes on the stream that produced the gradient, so it starts after the backward kernels without the host waiting. And the communicator needs a bootstrap: MPI is a common way to distribute the unique id. C1

Bucketing and overlap

Listing 1 all-reduces 98 floats per step: 392 bytes, deep in the latency-bound region of F8-03. A real model has millions of parameters in hundreds of tensors. All-reducing each tensor separately pays α hundreds of times; one giant all-reduce at the end of the backward pass waits for the last gradient and hides nothing. Bucketing does both jobs: buckets of a few megabytes each, launched as soon as their last gradient is computed, overlap communication with the rest of the backward pass. D8 Overlap across nodes is milestone F6 in DG402.

Scaling efficiency

Milestone F3 also asks for the scaling efficiency from 1 to N GPUs. C1 Its definition is simple (Jargon box); its measurement needs care: warm-up steps excluded, median step time over many steps, the same global batch or the same per-GPU batch stated, and the communication time per step measured separately so you can tell where efficiency is lost. This build does not report one: Listings 1 and 2 run on four shared CPU cores where a 97-parameter model's step is dominated by thread and process overheads, so a number would mean nothing. The lab does it on GPUs.

How the hardware actually does it

On GPUs, one training step is a long sequence of kernels on a stream: forward layers, backward layers, the all-reduce, and the optimizer. The all-reduce is itself GPU work: a library kernel (or, in your F8-05 ring, copies and reduction kernels) that moves data over the links of F8-04. Because it is queued on a stream, the host thread runs ahead and queues the next step's work while the GPUs are still busy. A second stream lets the all-reduce of one bucket run while backward kernels for earlier layers still compute; then compute units and links are busy at the same time, and the two compete for GPU memory bandwidth. D7 In this build, MPI processes on one CPU take the place of GPUs; Open MPI's all-reduce goes through shared memory between the processes.

Not verified — check before relying on this

That Open MPI 4.1.6 on this container used its shared-memory transport for Listing 2 was not checked (no transport selection was logged). That library collective kernels compete with compute kernels for GPU resources, and by how much, depends on the library, its settings and the GPU, and was not measured.

Worked example

Task. Global batch B = 64, N = 4 workers, learning rate 0.05. (a) What does each worker divide its gradient sum by? (b) If instead each worker divides by its shard size, what effective learning rate results? (c) The loss is reported by the extra element in the same all-reduce: what must each worker put there, and how is the reported loss computed? (d) What is the byte size of each step's all-reduce in Listing 1, and in which region of the alpha-beta model is it?

  1. (a) By 64, the global batch, so that the sum over workers is the mean gradient.
  2. (b) Shards are 16; dividing by 16 and summing four of them gives 4 × the mean gradient, so the update equals one with learning rate 0.2. The forensic run C shows the consequence: its loss falls faster than the 1-worker curve (0.0103 vs 0.0432 at step 299), which is not "the same curve". R3
  3. (c) Its loss sum over its shard (not its mean); the all-reduce gives the global sum, and dividing by 64 gives the global mean loss (train.hpp, lines 45 and 48).
  4. (d) 97 parameters + 1 loss = 98 floats = 392 bytes, far below the half-performance size of F8-03: latency-bound. That is why small models scale badly with data parallelism, and why buckets exist.

Where the analogy breaks


    

  • Notes add up exactly; floats do not. Pooled tasting notes are the same in any order; the summed gradient differs in the last bits with the order (R1), so "the same recipe changes" means "within a tolerance" across worker counts, and "exactly" only across the replicas of one run.
    • 

  • Halls taste in parallel; GPUs also wait. The story has no cost for pooling notes; on real hardware the all-reduce takes time that grows with the model size and shrinks the speed-up (scaling efficiency).
    • 

  • Recipes do not drift on their own. Replicas can: non-deterministic kernels or different library versions on different GPUs can make them differ; check the replica gap.
    • 




Common mistakes and debugging


    

  • Symptom: loss curve with N workers different from the start, replicas never equal. Cause: no initial broadcast. Fix: broadcast parameters (and optimizer state) from rank 0 before step 0.
    • 

  • Symptom: N-worker run diverges or trains "too fast". Cause: gradients summed instead of averaged. Fix: divide by the global batch, or by N after a sum of means.
    • 

  • Symptom: a job hangs at step 0. Cause: one rank calls a collective the others do not (a rank with no data skipping it, F8-01), or calls them in a different order. Fix: every rank calls every collective, in the same order.
    • 

  • Symptom: the optimizer sees half-reduced gradients on GPUs. Cause: the update kernel was queued on a different stream from the all-reduce without an event. Fix: same stream, or an event wait.
    • 

  • Symptom: replicas slowly drift apart. Cause: each rank re-computes a reduced value in a different order, or uses non-deterministic kernels. Fix: reduce once and distribute the bits (all-reduce does); log the replica gap periodically.
    •

Summary


    

  • Data parallelism: same parameters everywhere, different shards, one all-reduce of gradients per step, the same update everywhere.
    • 

  • Divide by the global batch (or average after summing); broadcast the initial state.
    • 

  • Correct runs match the 1-worker loss within rounding (here ≤ 2.38·10−7) and keep replicas bit-identical.
    • 

  • Library rules: same collectives in the same order on every rank; on GPUs, collectives are stream-ordered and need a communicator bootstrap.
    • 

  • Bucketing reduces start-up costs and enables overlap; small models are latency-bound.
    • 

  • Log the loss at step 0 and the replica gap: they catch both classic bugs.
