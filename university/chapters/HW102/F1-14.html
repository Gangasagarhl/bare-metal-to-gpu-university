Story hook

Analogy

The counting boards of F1-13 now stand in a row of four, each with its own cook. Tunde, on the right, adds first and sends his runner left. Each cook waits for the runner from the right before writing a final digit. The token travels down the row, one station at a time.

Next to the row stands Ines's prep station. It has several tools: the counting row, a slicer, a grater, a peeler. A dial on the front, set by the head chef's order ticket, decides which tool's result is placed on the plate. The dial has eight positions, and a small panel of four lamps reports facts about the result: "the plate is empty", "the result is negative", and two more about the counting row.

The row is a ripple-carry adder. Ines's station is an ALU, the arithmetic logic unit at the heart of every processor. In this chapter you build both and test them until you trust them.

What you will be able to do

  • Build an N-bit ripple-carry adder from full adders and explain why it is correct for every input.
  • Subtract with the same adder, using two's complement: a − b = a + NOT b + 1.
  • Design an ALU with eight operations, a result multiplexer and four status flags (zero, negative, carry, overflow), and explain each flag.
  • Test the ALU against a reference model: exhaustively at 4 bits, with edge cases and pseudo-random vectors at 16 bits.
  • Locate a faulty carry connection in a 4-bit adder from its test vectors ("the adder that is wrong for 7 + 1").
Jargon box
Ripple-carry adder
Simple words: a multi-bit adder made by chaining full adders, each passing its carry to the next. Analogy: the row of counting boards, with the runner's token travelling from right to left. Precise: an N-bit adder of N full adders in which the carry out of bit i is the carry in of bit i + 1; the carry may have to pass ("ripple") through every bit. D2 R1
ALU (arithmetic logic unit)
Simple words: the part of a processor that does arithmetic and logic on two numbers, choosing the operation from a code. Analogy: Ines's prep station with its tools and the selector dial. Precise: a combinational circuit with two N-bit operands, an operation code (opcode) and an N-bit result plus status flags; it computes several functions and selects one with a multiplexer. D2 D1
Opcode (operation code)
Simple words: a small binary number that says which operation the ALU should do. Analogy: the dial position on Ines's station. Precise: the select input of the ALU's result multiplexer and of any operation-specific logic; this chapter's ALU uses a 3-bit code with eight operations. W1
Status flags (Z, N, C, V)
Simple words: extra one-bit outputs that report facts about the result: is it zero, is it negative, did the addition carry out, did it overflow? Analogy: the four lamps on the station's panel. Precise: Z = 1 when every result bit is 0; N = the top bit of the result (its sign in two's complement); C = the carry out of the top bit for ADD and SUB; V = 1 when a signed (two's complement) ADD or SUB gives a result outside the range of N bits. D2 R3
Overflow (signed)
Simple words: the true answer is too big or too small to fit, so the bits show a wrong signed number. Analogy: a four-board row asked to show a count that needs five boards, read as a signed count. Precise: in N-bit two's complement, the representable range is −2N−1 to 2N−1 − 1; a signed sum outside that range overflows; this happens exactly when the carry into the top bit differs from the carry out of it. D2 W1 R3
Reference model
Simple words: a second, simpler description of what the answer should be, used to check the circuit. Analogy: the head chef's recipe card that the tasting checks against. Precise: an independent implementation of the specification (here, integer arithmetic in the testbench) whose outputs are compared with the design under test for every applied vector. D1 D2
Pseudo-random test vectors
Simple words: test inputs that look random but come from a formula, so the same list appears every run. Analogy: a tasting list drawn by lottery, but from a lottery whose draw can be repeated exactly. Precise: inputs produced by a deterministic generator from a fixed seed; used when exhaustive testing is too large; the run is repeatable because the seed is fixed. D5 R4

Layer 1 — the kid explanation

You add long numbers one column at a time, starting on the right, and each column may pass a carry to the next. A ripple-carry adder does exactly that with one full adder per column. The carry "ripples" from right to left, like a row of people passing a token.

Subtraction does not need a new machine. In F0-24 you learned two's complement: to make −b, flip all bits of b and add 1. So a − b is a + (flipped b) + 1. The adder adds a and the flipped b, and the extra 1 enters as the first carry. One adder, two jobs.

An ALU puts the adder next to some plain gates (AND, OR, XOR, NOT) and a multiplexer. The opcode picks which answer leaves the ALU. Next to the answer, four flags report facts: is the answer zero, is it negative, did the adder carry out of the top, and did a signed answer overflow?

Layer 2 — the student explanation

The ripple-carry adder and why it is correct

An N-bit ripple-carry adder joins N full adders: bit i adds ai, bi and the carry ci, producing si and ci+1, with c0 = cin. Each full adder guarantees 2·ci+1 + si = ai + bi + ci (F1-13). Multiply that equation for bit i by 2i and add the equations for all bits: every inside carry appears once on each side and cancels. What remains is 2N·cout + s = a + b + cin, where s, a and b are read as N-bit numbers. So the adder is correct for every input, as long as every full adder is. W1 D2

The run of Listing 2 checks this for all 512 input combinations of the 4-bit adder (16 × 16 values of a and b, times 2 values of cin) against plain integer addition, and prints ALL PASS. R1

Subtraction with the same adder

In N-bit two's complement, −b is represented by NOT b + 1. So a − b = a + NOT b + 1. The ALU feeds the adder with b XOR sub on every bit, where sub = 1 for subtraction: XOR with 1 flips a bit and XOR with 0 leaves it (F1-11). The "+ 1" enters as the adder's carry in, also equal to sub. One control wire turns the adder into a subtractor. D2 W1

Four flags

The status flags describe the result. Z (zero) is the NOR of all result bits. N (negative) is the top result bit, which is the sign in two's complement. C (carry) is the carry out of the top bit for ADD and SUB: for unsigned addition, C = 1 means the true sum did not fit in N bits. For subtraction in our ALU, C = 1 means no borrow was needed (a ≥ b as unsigned numbers): 7 − 7 gives C = 1, 5 − 7 gives C = 0, as the run shows. D2 R3

V (overflow) is about signed numbers. Adding two positive numbers must not give a negative result, and adding two negative numbers must not give a positive one. Both failures happen exactly when the carry into the top bit differs from the carry out of it, so V = cout XOR cmsb. In 4 bits, 7 + 1 = 1000, which is −8 as a signed number: the run prints V = 1 and N = 1 for it. The same bits, read as unsigned, are a correct 8 (C = 0). The adder does not know which reading you mean; the flags let the program decide. D2 W1 R3

The ALU

Our ALU has a 3-bit opcode: 000 ADD, 001 SUB, 010 AND, 011 OR, 100 XOR, 101 NOT a, 110 pass a, 111 pass b. All operations are computed at the same time; the result multiplexer keeps one. This is the combinational design of F1-12 at a larger scale: an 8-to-1 multiplexer per result bit. C and V are forced to 0 for the logic operations, so they only report on arithmetic. W1 R3

Testing an ALU

The testbench (Listing 4) contains a reference model: plain integer arithmetic and Verilog's bitwise operators, with no gates. For every vector it computes the expected result and all four flags, and compares. At 4 bits there are 16 × 16 × 8 = 2,048 combinations, so the test is exhaustive. At 16 bits there are 216 × 216 × 8 = 235 = 34,359,738,368 combinations, too many to run here, so the testbench uses 7 hand-picked edge cases and 200,000 pseudo-random test vectors from a fixed seed. A random test can miss a fault; the edge cases target the places where faults hide (all ones + 1, the most negative number − 1). W1 R3 R4

Layer 3 — the engineer's depth

Three design questions turn this teaching ALU into a real one. First, speed: the ripple-carry adder's worst case grows with N, which F1-15 measures; real ALUs use faster adder structures. Second, the operation set: real instruction sets add shifts, comparisons ("set if less than"), and sometimes multiplication in separate units. Third, the flag conventions: which flags exist, what C means after a subtraction, and which instructions update flags at all are defined by each instruction set architecture, not by the adder. D2

Not verified — check before relying on this

Real instruction set architectures differ in their flags: some have no flags register, and some define the carry after subtraction as a borrow (the opposite of our C). This chapter does not state any real architecture's rule. Check the architecture manual named in HW202 (F1-23) before comparing our flags with a real processor.

How the hardware actually does it

In a processor, the ALU sits in the datapath between the register file and the place where results are written back (F1-24 in HW202). The opcode is not chosen by a person: the control unit derives it from the instruction being executed. The flags go to a status register (on architectures that have one), where later conditional branch instructions read them. The adder, the logic gates and the result multiplexer are the same kinds of block you built here, made of CMOS gates (F1-10). Yosys maps the 4-bit ripple-carry adder onto 28 NAND and 20 NOT cells, four copies of the 7 + 5 cells it used for one full adder in F1-13. D2 R5 D6

Worked example

7 + 1 in 4 bits, carry by carry

a = 0111, b = 0001, cin = 0.

Bitaibicarry insicarry out
011c0 = 00c1 = 1
110c1 = 10c2 = 1
210c2 = 10c3 = 1
300c3 = 11cout = 0

Result 1000 = 8, cout = 0. Every carry is 1: 7 + 1 is a carry chain through three bits, which is why it is a good test vector. As unsigned numbers, 8 is correct (C = 0). As signed 4-bit numbers, 7 + 1 should be +8, which does not fit (the range is −8 to +7), and 1000 reads as −8. The carry into bit 3 is 1 and the carry out is 0; they differ, so V = 1. The ALU run prints y=8 Z=0 N=1 C=0 V=1. W1 R3

5 − 7 in 4 bits

  1. NOT 7 = NOT 0111 = 1000. Add 0101 + 1000 + 1 (the carry in).
  2. 0101 + 1000 = 1101; plus 1 = 1110. cout = 0.
  3. 1110 as a signed 4-bit number: −8 + 4 + 2 = −2. And 5 − 7 = −2. N = 1, Z = 0.
  4. C = 0: a borrow was needed (5 < 7 unsigned). V = 0: −2 is in range. The run prints y=e ... N=1 C=0 V=0 (e is hex for 1110). W1 R3

Where the analogy breaks


    

  • Cooks wait politely for the runner; full adders do not wait. Every full adder computes immediately from whatever its carry input currently is, and corrects itself when a new carry arrives. Until the last carry settles, the outputs can be wrong for a moment (F1-15). D2
    • 

  • Ines uses one tool at a time; the ALU uses all of them every time. All operations are computed in parallel and the multiplexer discards all but one. That costs power but no extra time for the choice. D2
    • 

  • The lamp "negative" in a kitchen means the count is below zero; the N flag is only the top bit. For unsigned numbers, N = 1 means "large", not "negative". The flags report bits; the program decides what they mean. W1

Transition box

Where you came from: F1-13 built one full adder; F1-12 built multiplexers; F0-24 taught two's complement. What carries over: full adders, the mux as "choose", exhaustive tests against arithmetic. What changes: circuits are now parameterised by width and built by generate loops; the same bits are read two ways (unsigned and signed), so you need flags; and exhaustive testing stops being possible at 16 bits, so you test with edge cases and pseudo-random vectors against a reference model. What comes next: F1-15 adds time: how long the carry takes to ripple, and what happens if you read the result too early. D2

Method hints


Work from the outputs inward: the wrong bit tells you which full adder's output is wrong; then ask which of its three inputs (a3, b3, carry in) could be wrong. Compare the carry in it should have received with nearby wires.

Summary


    

  • A ripple-carry adder chains N full adders; the carry passes from bit to bit.
    • 

  • It is correct for every input because the full-adder equations sum to 2N·cout + s = a + b + cin.
    • 

  • Subtraction: a − b = a + NOT b + 1; one control signal both flips b and sets the carry in.
    • 

  • Flags: Z (all zero), N (top bit), C (carry out, unsigned), V (carry into top XOR carry out, signed overflow).
    • 

  • An ALU computes all operations and selects one with a multiplexer driven by the opcode.
    • 

  • Test against a reference model: exhaustively when small, with edge cases and seeded random vectors when large.
    • 

  • A fault shows its location in the test vectors: the same wrong bit in every failure points to one full adder's inputs.

Observation: 7 of the 8 named vectors are wrong; only 1 + 1 is right. got − expected is −8 for 7 + 1, 4 + 4, 15 + 1 and 5 + 2 + 1, and +8 for 3 + 1, 4 + 0 and 9 + 6 (in 9 + 6 and 15 + 1 the change in bit 3 also changes the carry out). Every failure is in bit 3 (worth 8), with cout following from it. 384 of 512 combinations fail (R2). Hypotheses: (1) the bit-3 full adder is faulty; (2) its carry in is wrong; (3) its a3/b3 inputs are miswired. For 4 + 0 the true carry into bit 3 is 0 and a3 = b3 = 0, yet s3 = 1: bit 3 is adding a 1 that is not there, so its carry in is wrong (2), not its data inputs (3); and the same bit-3 adder gives correct results whenever c3 and s2 agree, which argues against (1). Pattern: in every failing vector the true c3 differs from s2 (the sum bit of bit 2), and the result is exactly what bit 3 gives if its carry in is s2: for 7 + 1, s2 = 0 while c3 = 1; for 4 + 0, s2 = 1 while c3 = 0. In 1 + 1, s2 = c3 = 0, so it passes. Over all inputs, s2 ≠ c3 in 384 of 512 cases. Root cause: Listing 5, line 8: .cin(s[2]) instead of .cin(c3): the carry into bit 3 is wired to the neighbouring sum wire. Fix: .cin(c3); rerun: ALL PASS (R1). Prevention: include long-carry vectors (7 + 1, 15 + 1) in every adder test, and run the exhaustive test, not only a few hand-picked sums. How the evidence was made: Listing 1 with the carry in of bit 3 changed from c3 to s[2], run with Listing 2 in this build.
