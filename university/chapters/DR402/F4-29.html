Story hook

Mei's RISC-V kernel received exactly one character from the keyboard. The first key she pressed appeared on the screen; after that, nothing, no matter how much she typed. The timer kept ticking, the other harts kept running their tests, nothing crashed. The UART's receive buffer was full of her typing. The interrupt controller had been told about it. But the kernel had never told the interrupt controller that it had finished with the first interrupt, and a RISC-V interrupt controller takes that silence literally.

This chapter completes the RISC-V port's core for milestone D6: device interrupts through the Platform-Level Interrupt Controller (PLIC), a periodic tick through the SBI timer, harts started through SBI's Hart State Management, inter-processor interrupts through SBI, and per-hart data. It then looks at a board: QEMU's sifive_u, a model of a real development board, stands in for the optional milestone D7, and teaches the lesson boards always teach: not every hart in the devicetree is a hart your kernel can run on.

What you will be able to do

  • Find each hart's PLIC context from the devicetree's interrupts-extended, and drive the PLIC: priority, enable, threshold, claim, complete.
  • Run a periodic tick with the SBI TIME extension (and explain where Sstc changes this).
  • Start harts with SBI HSM hart_start, and give each one a stack and per-hart data through tp.
  • Send inter-processor interrupts with SBI send_ipi and handle them as supervisor software interrupts.
  • Choose which harts to use from the devicetree's status and mmu-type, and pick a UART driver by its compatible string.
  • Diagnose a device that interrupts once and never again.
Jargon box
PLIC (Platform-Level Interrupt Controller)
Simple words: RISC-V's standard controller for device interrupts. Analogy: the doorbell panel with a light per door and a "taken" register per teacher. Precise: per-source priority registers, per-context enable bits and priority threshold, and a per-context claim/complete register; reading claim returns the highest-priority pending source and marks it in service; writing its number back completes it. A context is one hart in one privilege mode. D1
Claim and complete
Simple words: "I am taking this interrupt" and "I have finished with it". Analogy: lifting the receiver, and hanging it up. Precise: a read of the context's claim register (claim) and a write of the same source ID to it (complete); until completion, the PLIC does not forward that source again. D1
SBI TIME and Sstc
Simple words: two ways to set a timer alarm from S-mode: ask the firmware, or write a CSR directly. Analogy: asking the caretaker to set the alarm, or having your own alarm clock. Precise: SBI set_timer(stime_value) programs the next timer interrupt and clears the pending one; the Sstc extension adds the stimecmp CSR so S-mode can do this without an ecall. The time CSR counts at the devicetree's timebase-frequency. D2
SBI HSM (Hart State Management)
Simple words: SBI calls to start, stop and query harts. Analogy: asking the caretaker to wake another teacher. Precise: hart_start(hartid, start_addr, opaque) starts a stopped hart in S-mode at start_addr with a0 = hart ID, a1 = opaque and translation off; hart_status returns 0 (started), 1 (stopped) or a transition state. D2
IPI (RISC-V)
Simple words: an interrupt one hart sends to another. Analogy: a note under another teacher's door. Precise: SBI send_ipi(hart_mask, hart_mask_base) raises a supervisor software interrupt (cause 1) on each hart in the mask; the receiver clears sip.SSIP. D2
interrupts-extended
Simple words: a devicetree list that says which interrupt controller and line each output goes to. Analogy: the wiring chart from the panel's outputs to each teacher's room. Precise: pairs of (phandle of a hart's riscv,cpu-intc node, cause number); on the PLIC node, the n-th pair describes context n: cause 11 means M-mode external, 9 S-mode external. D3

Layer 1 — the kid explanation

Analogy

The doorbell panel (PLIC) has a light for every door and, for every teacher, a list of which doors they answer. When a bell rings, the panel lights it and calls a teacher who answers that door. The teacher says "I'm taking door 10", deals with the visitor, and says "door 10 done". Until the teacher says "done", the panel will not call anyone for door 10 again, even if the visitor keeps ringing. The alarm clock is kept by the caretaker: the principal asks "wake me at this time". To wake the other teachers, the principal asks the caretaker too. Some rooms in the building belong to the caretaker's assistant, not to teachers; the building plan says which.

Mapping: doorbell panel = PLIC; a teacher's list = a context's enable bits; "taking door 10" = claim; "door 10 done" = complete; caretaker's alarm = SBI set_timer; waking teachers = SBI HSM and send_ipi; the assistant's room = sifive_u's monitor hart.

Layer 2 — the student explanation

RISC-V separates interrupts by source. Timer and software interrupts belong to each hart and arrive as supervisor timer (cause 5) and supervisor software (cause 1) interrupts, set up through SBI. Device interrupts arrive through the PLIC as supervisor external interrupts (cause 9), and the kernel then asks the PLIC which device it was. F4-28's single trap vector already distinguishes them by scause; F4-29's handler is one function with three branches. D4

The PLIC works per context: one context per hart and privilege mode that can take external interrupts. Each context has enable bits for the sources it wants and a threshold below which it ignores them. Which context belongs to which hart is not a formula: the PLIC's devicetree node lists, in context order, the hart interrupt controller and the cause number each context drives. On QEMU virt with 4 harts the S-mode contexts are 1, 3, 5, 7; on sifive_u, hart 1's S-mode context is 2 (R2, R4). D3 R2

The timer is set through the SBI TIME extension: the kernel asks "interrupt me when time reaches T", and in the handler asks again for T + interval. time counts at the devicetree's timebase-frequency: 10 MHz on virt, 1 MHz on sifive_u (R1, R4). Harts other than the boot hart wait in the firmware until the kernel calls SBI HSM hart_start; they then begin at the address given, in S-mode, with their hart ID in a0 and a value of the kernel's choosing in a1. The lab passes an index used for the stack and per-hart data, which each hart then finds through the tp register. D2

Boards add variation. The lab's UART driver picks between the 16550 of QEMU virt and the SiFive UART of sifive_u by the compatible string. And on sifive_u, hart 0 is a small monitor core without S-mode or an MMU; its devicetree node says so (status = "disabled", no mmu-type), and a kernel that ignores this waits forever for a hart that cannot arrive.

Layer 3 — the engineer's depth

PLIC register model and the context mapping

The PLIC's register block (0xc000000 on both QEMU machines here) has: source priorities at 4 × source; pending bits at 0x1000; per-context enable bits at 0x2000 + 0x80 × context; and per-context threshold at 0x200000 + 0x1000 × context, with the claim/complete register 4 bytes after it. Source 0 does not exist, so a claim returning 0 means "nothing pending". plic::probe builds the context table: it walks the cpu nodes, records the phandle of each one's riscv,cpu-intc child, then reads the PLIC's interrupts-extended as pairs (phandle, cause) and keeps, for each hart, the context whose cause is 9 (S-mode external). D1 D3

Enabling the UART's interrupt takes four steps in two devices: the UART's own interrupt-enable register (receive data available), the source's priority (non-zero: priority 0 means "never"), the context's enable bit and threshold, and finally the hart's sie.SEIE and sstatus.SIE. Any one missing gives silence. R1's PLIC dump after the test shows each: priority 1, pending 0, enable 1, threshold 0. R1

Not verified — check before relying on this

The PLIC register offsets (priority, pending, enable, threshold, claim/complete), the meaning of priority 0 and of a claim value of 0, the claim/complete gateway behaviour and the cause numbers 9 and 11 in interrupts-extended are recalled from the "RISC-V Platform-Level Interrupt Controller Specification" (D1), the privileged specification (D4) and the Linux devicetree binding sifive,plic-1.0.0 / riscv,plic0 (D3), none opened. QEMU 8.2.2's PLIC model delivered interrupts with this code on virt; on sifive_u the UART interrupt was not tested (the console there has no receive test). Vendor PLICs (for example on some SoCs the T-Head variant) differ in details and need their own drivers.

Claim, complete, and why "once" happens

When a source's interrupt line rises, the PLIC's gateway for that source sets its pending bit and then forwards nothing more from that source until the source is completed. A claim returns the highest-priority pending enabled source for the context and clears its pending bit; completion re-opens the gateway. The ns16550a raises its line while received data is waiting. If the handler drains the UART and completes, the next character raises the line and a new interrupt arrives. If the handler drains but never completes, the next character sets the UART's line again and the PLIC sets the pending bit again, but the source stays "in service" and no new interrupt reaches the hart: R6 shows exactly one character and "pending bit 1". D1 R6

Compare F4-25: on the GIC, a missing end-of-interrupt also blocks further interrupts of the same or lower priority, while a missing re-arm of a level source gives a storm. The two controllers differ in detail and agree on the rule: every acknowledge has exactly one completion, and the device's condition must be cleared before completion if it is level-triggered.

The timer: SBI TIME, and Sstc

sbi::set_timer(now() + interval) asks OpenSBI to raise a supervisor timer interrupt when time reaches the value; calling it again moves the deadline and clears the pending interrupt. With timebase-frequency 10000000 Hz, 10 ms is 100000 units; R1 counts 20 ticks in 2029396 units (202 ms of time). On sifive_u the timebase is 1 MHz and the same code gives 20 ticks in 207336 units (207 ms). The handler re-arms on every tick, so the tick keeps running until the kernel clears sie.STIE before its verdict. R1 R4

R1's ISA string lists sstc, and F4-28's OpenSBI banner said "Boot HART ISA Extensions: time,sstc". With Sstc the kernel can write the deadline into stimecmp itself and avoid one ecall (two privilege switches) per tick; OpenSBI, when Sstc is present, implements set_timer with it. The lab uses the SBI call because every SBI 0.2+ firmware offers it; using stimecmp when the devicetree's ISA string lists Sstc is step 3 of the lab. D2

Not verified — check before relying on this

That set_timer clears the pending timer interrupt, that Sstc's stimecmp must also be enabled by M-mode (a bit in menvcfg) before S-mode can use it, and that OpenSBI uses Sstc internally when available, are recalled from the SBI specification (D2), the Sstc extension and OpenSBI's behaviour, not checked. The tick counts above are measured on QEMU under TCG and say nothing about hardware timing.

HSM: starting harts, and the boot hart lottery

hart_start(hartid, secondary_entry, index) returns 0 when the firmware has accepted the request. The hart starts at secondary_entry in S-mode with satp = 0 (no translation), a0 = hart ID, a1 = index. smp.S loads gp, sets a stack 16 KiB × index below the top, installs stvec, and calls secondary_main, which writes the address of its Hart structure into tp, enables Sv39 with the shared root table, initialises its PLIC context, and reports online. hart_status = 0 means started. D2 R2

The boot hart is not always hart 0. OpenSBI on QEMU picks the first hart to reach a certain point (a "lottery"), and R3 shows boot hart 1 with 8 harts; one earlier run in this build had boot hart 7. The kernel therefore uses a0 as the boot hart ID, starts every other usable hart, and builds the IPI mask from hart IDs: R3's mask 0xfd is every hart except hart 1. A kernel that assumes "I am hart 0" works most of the time and fails on the run where it is not. R3

The tp register is the ABI's thread pointer. In the kernel it holds the per-hart pointer; when the kernel runs user programs, it must swap the user's tp with its own on every trap, usually through sscratch (the next chapter's checklist row "syscall/context"). This lab's kernel never enters U-mode, so tp is never disturbed. D5

IPIs

sbi::send_ipi(mask, 0) raises a supervisor software interrupt on each hart whose bit is set in the mask (relative to hart_mask_base). The receiver's handler clears sip.SSIP and counts. R2 and R3: every other hart took exactly one. On hardware with the Ssaia extension or a memory-mapped software-interrupt device, IPIs can be sent without the firmware; through SBI they always work. D2 R3

Which harts to use

find_harts uses a hart only if its node's status is "okay" (or absent) and it has an mmu-type. On sifive_u hart 0's node reads isa rv64imac, no mmu-type, status "disabled": it is the board's monitor core (on the modelled FU540 SoC, an E51 core without S-mode). R4 skips it and passes with one hart. The all_harts build ignores the properties: hart_start(0) returns 0 and hart_status(0) reports 0 (started), but the hart never reaches secondary_main (it cannot run S-mode code), and the kernel reports "only 1 of 2 harts came online" (R7). A successful SBI return means the firmware accepted the request, not that your code runs. R4 R7

Also visible in R1: QEMU virt's harts report mmu-type "riscv,sv57", and the kernel uses Sv39. A hart that supports Sv57 also supports Sv48 and Sv39, so the smaller mode is valid; the property names the largest. D4

How the hardware actually does it

On real SoCs the PLIC is a block of logic between peripherals' interrupt lines and the harts' external-interrupt inputs, with a gateway per source that converts a level or edge into a single request, as described above. The time CSR is usually a read of a memory-mapped counter shared by all harts (on many systems inside the CLINT or ACLINT); M-mode firmware programs its compare registers when S-mode calls set_timer, unless Sstc lets S-mode program a per-hart compare CSR directly. HSM's hart_start on a board releases a hart that the boot ROM or firmware parked, often in a wfi loop. D1 D2

Worked example

Task. For QEMU virt with 8 harts, compute the enable-register and claim-register addresses for the UART (source 10) in the boot hart's S-mode context in R3, and the IPI mask; then check against R3.

Context. R3's boot hart is 1; its S-mode context is 3 (R3's context list: "hart 1 -> 3"). Enable register: 0xc000000 + 0x2000 + 0x80 × 3 + 4 × (10 / 32) = 0xc000000 + 0x2000 + 0x180 + 0 = 0xc002180; bit 10. Threshold: 0xc000000 + 0x200000 + 0x1000 × 3 = 0xc203000; claim/complete: 0xc203004. R3's PLIC dump shows "context 3 enable bit 1, threshold 0". R3

IPI mask. All harts 0–7 except the boot hart 1: 0xff & ~0x02 = 0xfd. R3: "hart mask 0xfd". R3

Lock test. 8 harts × 500 rounds = 4000; R3's locked counter is 4000 and the racy counter 3997: three lost updates. With more rounds the run took minutes, for the reason F4-26 gave (eight vCPUs on four host CPUs with a fair lock); run.sh passes rounds=500 for that reason. R3

Where the analogy breaks


    

  • The panel does not call "a teacher". Every context whose enable bit is set is signalled; if several harts enable the same source, several may trap and race to claim it, and only one gets the source (the others read 0). The analogy's single call hides that race.
    • 

  • The caretaker's alarm can be your own. With Sstc the alarm is a register of the hart itself, not a request to the firmware. The analogy describes SBI TIME only.
    • 

  • The assistant's room is a real processor. The monitor hart is a full CPU running firmware; it is excluded because it lacks S-mode and an MMU, not because it is a different kind of thing.
    • 




Common mistakes and debugging


    

  • Starting every hart in the devicetree. While writing this lab the first version did. On sifive_u, hart_start(0) returned 0 and the status said started, but hart 0 never arrived. Evidence (R7):

    • 

  • Waiting with wfi while no interrupt can come. Also from writing this lab: an early version cleared sie.STIE after the timer test and then waited for UART input with wfi; with no keystroke and no timer, the hart slept for ever and the time-limit check never ran. Fix: keep the tick running (line 228) or poll.
    • 

  • Computing the PLIC context as 2 × hart + 1. Right on virt, wrong on sifive_u (Figure 2). Fix: interrupts-extended.
    • 

  • Priority 0. A source with priority 0 never interrupts. Fix: any non-zero priority above the threshold.
    • 

  • Assuming the boot hart is hart 0. R3's boot hart is 1. Fix: use a0.
    • 

  • Forgetting to clear sip.SSIP in the IPI handler. The software interrupt stays pending: an IPI storm, like F4-25's timer storm.
    • 

  • Ending the run with SRST and assuming it worked. On sifive_u it returned −2. Fix: sbi::shutdown prints the error and halts; CI uses the verdict line.

Transition box

Where you came from: F4-25/F4-26 on AArch64: GICv3 with acknowledge/end-of-interrupt, the generic timer programmed directly, PSCI CPU_ON, SGIs, TPIDR_EL1; OS303 on x86-64: IOAPIC and local APIC, the APIC timer, INIT-SIPI-SIPI, IPIs through the APIC, GS base. What carries over: the shape of the interrupt path (acknowledge, handle, complete); a tick re-armed first; the ticket lock and the online counter; per-CPU data through a register; devicetree-driven discovery; the safety rules for boards from F4-27. What changes: three kinds of interrupt by cause (software, timer, external); a PLIC whose claim/complete pair blocks a source until completion; contexts per hart and mode, mapped by the devicetree; the timer and IPIs through SBI (or Sstc); hart_start with an opaque argument; a random boot hart; harts that exist but cannot run the kernel. What comes next: F4-30 steps back from single ports: the arch-neutrality checklist, the same code on ten CPUs including 32-bit and big-endian ones, and the optional milestones X1 and X2.

Define an interrupt-controller interface (enable source for a CPU, acknowledge, complete, send IPI) and implement it for F4-25's GICv3, this chapter's PLIC plus SBI IPIs, and your OS303 IOAPIC/LAPIC. Summary


    

  • RISC-V interrupts come by cause: software (1), timer (5), external (9); external ones come through the PLIC.
    • 

  • The PLIC works per context; map contexts to harts from interrupts-extended; claim, handle, complete, every time.
    • 

  • The timer is set through SBI TIME (or stimecmp with Sstc) at the devicetree's timebase-frequency; re-arm on every tick.
    • 

  • HSM hart_start starts harts with an opaque argument; per-hart data through tp; the boot hart may be any hart.
    • 

  • Use only harts whose devicetree node is okay and has an mmu-type; an SBI success is not proof the hart runs your code.
    • 

  • D7 on a real board is described, not tested; sifive_u is a model, not a board.
