Story hook

The neutral tests had passed on x86-64, on AArch64 and on RISC-V. The course's code had been called "arch-neutral" for five chapters. Then someone compiled it for a 32-bit Arm CPU. Three of the ten CPUs tried refused to link. Once those were fixed, every 32-bit CPU crashed in the same test, the one that prints a formatted line, and the crash address was different on big-endian CPUs from little-endian ones. Nothing in the failing code mentioned an architecture. It had never been asked to run anywhere that a long is 32 bits wide.

This last chapter of DR402 measures neutrality instead of claiming it. It compiles the course's arch-neutral code, unchanged, for ten CPUs (64-bit and 32-bit, little- and big-endian) and runs it under user-mode emulation. It turns what breaks into the curriculum's arch-neutrality checklist, and it sets up the two optional milestones: X1, a 32-bit port with more memory than the kernel can map, and X2, a big-endian or LoongArch port.

What you will be able to do

  • Apply the arch-neutrality checklist (section 10.2 of the curriculum) to a piece of kernel code and name the risks on each row.
  • Build the same freestanding C++ for many CPUs with one compiler, and run it with qemu-user.
  • Explain why 32-bit ports need compiler helper functions for 64-bit division and atomics, and provide them.
  • Diagnose a variadic-argument mismatch from a crash address, and predict how endianness changes it.
  • Compare architectures on the rows that matter to a kernel: word size, byte order, privilege model, firmware interface, interrupts, memory model, boot protocol.
  • Plan an X1 or X2 port and the log of changes it requires.
Jargon box
Arch-neutral code
Simple words: code that does not depend on which CPU it runs on. Analogy: the school rulebook that applies in every building. Precise: source with no architecture-specific instructions, sizes or orderings; it reaches the hardware only through the arch layer's interfaces, and states every size, byte order and ordering it relies on. D1
Data model (LP64, ILP32)
Simple words: how wide int, long and pointers are. Analogy: the size of the standard paper in each building. Precise: LP64 (64-bit Linux and BSD on x86-64, AArch64, RISC-V 64, LoongArch 64, s390x, ...): int 32, long and pointers 64 bits. ILP32 (32-bit CPUs): int, long and pointers 32 bits; long long is 64 on both. D2
Endianness
Simple words: which byte of a multi-byte number is stored first. Analogy: writing a date day-first or year-first. Precise: little-endian stores the least significant byte at the lowest address (x86, Arm and RISC-V as normally used, LoongArch); big-endian the most significant (s390x, MIPS and PowerPC in the configurations tested here). Data with a defined byte order (devicetree: big-endian; virtio: little-endian) must be read with explicit conversions. D3
Compiler helper functions (libgcc, compiler-rt)
Simple words: small library functions the compiler calls for operations the CPU cannot do in one instruction. Analogy: a calculator the rulebook assumes every building owns. Precise: for example __udivdi3 (64-bit unsigned division on 32-bit CPUs), __aeabi_uldivmod (the Arm EABI equivalent), __atomic_fetch_add_8 (64-bit atomics without hardware support) and AArch64's outline-atomics helpers; normally supplied by libgcc or compiler-rt and libatomic, which freestanding kernels must link or replace. D4
Outline atomics (AArch64)
Simple words: atomic operations compiled as calls to helpers that choose the best instruction at run time. Analogy: asking the building's office how to do a job, instead of doing it the one way you know. Precise: with -moutline-atomics (a default for some AArch64 Linux targets), the compiler emits calls such as __aarch64_ldadd8_relax that test for the LSE atomic instructions; a kernel disables it with -mno-outline-atomics or provides the helpers. D4
qemu-user
Simple words: QEMU running one Linux program for a foreign CPU on your machine. Analogy: a visiting teacher from another building, translated sentence by sentence. Precise: user-mode emulation: QEMU translates the program's instructions and turns its Linux system calls into the host's; no kernel, devices or privileged instructions are emulated. D5

Layer 1 — the kid explanation

Analogy

The school rulebook (arch-neutral code) is supposed to work in every building. A rule that says "write the date in the box" works only if every building's boxes are the same size and everyone writes the date the same way round. In some buildings the box is half the size, and the rest of the date spills into the next box, where someone reads it as a room number. Whether that room number is the year or the day depends on which way round that building writes dates. The fix is not a rule per building; it is a rulebook that says exactly how big the box is.

Mapping: the box = the size of long; the date = a 64-bit number; spilling into the next box = a variadic argument read with the wrong size; which way round = endianness; the rulebook that says how big = explicit types and formats (uint64_t, %llx).

Layer 2 — the student explanation

A kernel can be arch-neutral only where it says what it needs. "A number" is not enough: 32 or 64 bits? Stored in which byte order, if it crosses to a device or a file? Read by other CPUs in which order? Divided by a 64-bit number on a CPU that has no such instruction? The curriculum's section 10.2 lists these questions as a checklist. Two ports (AArch64, RISC-V) are good tests of some rows, but all three of the course's 64-bit architectures are LP64 and little-endian, so they cannot test the rows about word size and byte order. D1

This lab tests those rows without writing five more kernels. The neutral tests and the F3-18 printing code are compiled with clang, which can generate code for many CPUs from one installation, into tiny Linux programs. The only CPU-specific code is ustart.cc: an entry point and two system calls (write and exit) for each CPU. qemu-user then runs each program, translating its instructions and its system calls. No kernel boots; what the lab tests is the neutral code's arithmetic, formatting, byte-order handling, pointer handling, atomics and devicetree parsing on each CPU. D5

The results are in Figure 1. Some CPUs need help to link at all: 32-bit CPUs cannot divide 64-bit numbers in one instruction, and some cannot do 64-bit atomic operations; their compilers call helper functions that a kernel must provide (port32.cc). Once linked, every 64-bit CPU passes, including big-endian s390x. Every 32-bit CPU crashes in the same test, at an address that depends on its byte order. Two lines, in two files that had always been called neutral, were the cause. R3

Round 1: what the compilers need from a kernel

With the kernel's flags and nothing per CPU, four CPUs build (x86-64, RISC-V 64, LoongArch 64, s390x) and six do not (R2). The failures fall in three groups. 64-bit division on 32-bit CPUs: kformat divides by 10 and 16 to print numbers, and the frame allocator divides addresses; on i386 the compiler calls __udivdi3, on 32-bit Arm __aeabi_uldivmod. Outline atomics on AArch64: clang's default for aarch64-linux-gnu turns fetch_add on a 64-bit atomic into a call to __aarch64_ldadd8_relax. The kernel builds of F4-24 use GCC with -mno-outline-atomics, which this round omitted. 8-byte atomics on 32-bit CPUs without them: clang warns that an 8-byte atomic on RISC-V 32, MIPS 32 and PowerPC 32 "may incur significant performance penalty" (it will become a library call), and -Werror turns the warning into an error. i386 and 32-bit Arm passed this point because they have 8-byte atomic instructions (cmpxchg8b, ldrexd/strexd). R2 D4

port32.cc supplies the division helpers (a shift-and-subtract loop: 64 iterations, no division instruction needed) and the 8-byte atomic helpers. The Arm EABI helper returns the quotient in r0:r1 and the remainder in r2:r3, which C cannot express, so a few assembly instructions wrap a C function. The atomic helpers are not atomic: they are plain loads and stores, correct only on one CPU with interrupts masked. A real 32-bit SMP port must take a lock in them or avoid 64-bit atomics in core code. That is a design decision for the port, and the checklist row "atomics" exists for it. D4

Not verified — check before relying on this

The helper names and calling conventions (__udivdi3, __umoddi3, __divdi3, __moddi3, __aeabi_uldivmod returning quotient in r0:r1 and remainder in r2:r3, __atomic_*_8, __aarch64_ldadd8_relax), the statement that i386 and ARMv7-A have 8-byte atomic instructions, and every Linux system-call number and register convention in ustart.cc are recalled from the libgcc and compiler-rt documentation, the Arm "Run-time ABI" (D4) and the Linux system-call tables (D6), not opened. The runs are evidence that each one works with clang 18 and qemu-user 8.2.2 (programs link, print and exit with the right code), not that the descriptions are complete.

Round 2: 64-bit passes, 32-bit crashes

With per-CPU flags (-mno-outline-atomics on AArch64, -Wno-atomic-alignment where the 8-byte atomic becomes a call) and port32.cc, all ten build. The five 64-bit CPUs pass 10 of 10, including s390x, which is big-endian: its log reads "this CPU is big-endian; be32(11 22 33 44) = 0x11223344" and the devicetree tests pass, because fdt.h reads every field with explicit byte-order functions. The five 32-bit CPUs pass the first two tests and die with signal 11 (exit code 139 = 128 + 11) in the third, the formatting test: the forensic lab. R3

The two bugs

The test's literal. F4-23's test passes 0xffffffff80000000ul for %lx. On LP64 that is an unsigned long, 8 bytes, and %lx reads 8 bytes. On ILP32 the value does not fit a 32-bit unsigned long, so the language gives the literal the type unsigned long long: 8 bytes go into the variable-argument list, %lx takes 4 out, and every later argument is read from the wrong place. The formatter. F3-18's kformat sets a flag for any number of ls and then reads a long. So even the correct %llx would read 4 bytes on ILP32. Both are invisible on every LP64 CPU, because there long and long long are both 64 bits. neutral_fix.py writes fixed copies of both files (counting the ls; %llx with ull) without editing the originals, and R4 shows all five 32-bit CPUs passing with them, and x86-64 and s390x unchanged. R1 R4

Why did the compiler not warn? ksnprintf is not declared with a format attribute, so the compiler does not check its arguments against the string. Adding __attribute__((format(printf, 3, 4))) to the declaration would have flagged the mismatch at compile time on ILP32 targets. F3-18's custom formatter accepts a subset of printf's syntax, so the attribute also requires keeping that subset compatible. This is one of the decisions for the course owner: the fix touches OS303's file. D2

X1 and X2: what the two optional milestones add

X1 (32-bit port with high memory). A 32-bit kernel has a 4 GiB virtual address space shared with user programs, so it cannot map all physical memory when there is more than its window (often about 1 GiB of kernel space). Memory above the window ("high memory") must be mapped temporarily when the kernel touches it. Every place in the neutral code that turns a physical address into a pointer by adding a constant is a bug on X1. The acceptance test asks for a log of "every change to arch-neutral code the port required, each classified as a bug fixed or a design change": this chapter's two fixes are the first two entries of that log (both bugs fixed), and the non-atomic 64-bit helpers are the first design decision. D1

X2 (big-endian or LoongArch). The acceptance test requires the FAT32 and ext2 tests to pass "on the same disk images as on x86-64" and the C4 virtio drivers to "work unchanged above the transport layer (virtio's modern interface is little-endian by definition, even on big-endian CPUs)". The devicetree half of the byte-order story is already shown (R3: s390x, mips, ppc). The other half (FAT32 and ext2 are little-endian on disk; virtio's rings are little-endian) needs explicit le16/le32/le64 helpers in every file-system and driver structure access: on a little-endian CPU they compile to nothing, which is why their absence goes unnoticed until a big-endian port. D1 D3

How the hardware actually does it

A 32-bit CPU's arithmetic unit operates on 32-bit registers; a 64-bit division becomes a sequence of instructions or a call. Some 32-bit CPUs provide a 64-bit atomic as a pair of exclusive load and store instructions (ARMv7-A) or a double-width compare-and-swap (i386); others provide none, and a kernel must protect 64-bit values with a lock or by disabling interrupts on a single CPU. Byte order is a property of the CPU's load and store paths: big-endian CPUs place the most significant byte at the lowest address, and some CPUs (Arm, MIPS, PowerPC) can be configured for either order, which is why "the configurations tested here" matters in the jargon box. D3

Untested on hardware

This lab ran under qemu-user only. It tests instruction semantics as QEMU implements them and the Linux system-call interface QEMU translates; it does not test privileged instructions, interrupts, MMUs, caches or memory ordering on any of the ten CPUs, and no physical machine of any of these architectures was used. A user-mode pass is a necessary step towards a kernel port, not a kernel port.

Worked example

Task. Predict, before looking at R3, the output of the formatting test on 32-bit Arm with the original files, and the signal address; then check.

Arguments. After the named ones, the variadic list holds: -42 (int, 4 bytes), 99u (4), 0xbeefu (4), the literal (unsigned long long on ILP32, 8 bytes), "str" (pointer, 4), 'k' (int, 4). The format reads: %5d (4) → −42, %05u (4) → 99, %x (4) → beef, %lx with F3-18's kformat → reads an unsigned long, 4 bytes, %s → the next 4 bytes as a pointer.

Bytes. On little-endian Arm the 8-byte value 0xffffffff80000000 is stored low word first: 0x80000000, then 0xffffffff. So %lx prints 80000000 and %s dereferences 0xffffffff: a fault at 0xffffffff. On big-endian MIPS and PowerPC the order is reversed, so %s dereferences 0x80000000. R5: si_addr=0xffffffff on i386, arm and riscv32; si_addr=0x80000000 on mips and ppc. Prediction confirmed. (The 64-bit value happened to fall on an 8-byte-aligned position in each of these ABIs' argument areas; where an ABI inserts padding before a 64-bit argument, the words read would shift, and the prediction must account for it.) R5

Why x86-64 does not crash. LP64: the literal is an unsigned long, %lx reads 8 bytes, %s reads the next argument, "str". The same is true on s390x, big-endian or not. The bug exists only where long is narrower than the value.

Where the analogy breaks


    

  • The box size is not the only difference. The rulebook picture covers word size and byte order; memory ordering, atomics, alignment and cache coherence differ too, and they do not appear as wrong values in a single-threaded test. The lab's pass on ten CPUs says nothing about those rows.
    • 

  • Not every building gets the rulebook unchanged. The arch layer is supposed to differ; the analogy's "one rulebook" applies to the neutral part only, and the line between the two is a design choice the checklist helps draw.
    • 

  • The visiting teacher is translated, not native. qemu-user runs the programs with QEMU's model of each CPU and the host's Linux; timing, cache effects and kernel interfaces are the host's, not the target's.
    • 




Common mistakes and debugging


    

  • Using the hosted C++ headers for foreign targets. While writing this lab, <cstdint> from libstdc++ pulled in glibc headers that exist only for x86-64 in the build container; every foreign target failed to compile. Fix: freestanding headers (the fsinc shims here, or the toolchain's own).
    • 

  • A quoted include finding the wrong file. F3-18's .cc files say #include "arch.h", which looks in the including file's own folder first, and found F3-18's x86-64 arch.h. Fix: copy the shared files next to the headers they should see (as run.sh does in its scratch folder).
    • 

  • Assuming one mnemonic works everywhere. LoongArch's assembler rejected call; bl is its call. Check each _start on each CPU.
    • 

  • Overlapping segments. The first linker script put .bss on the same 64 KiB page as read-only data on some CPUs; the loader refused. Fix: align .data to a new page of the largest page size in use.
    • 

  • Trusting LP64. %lx with a 64-bit value, long for a physical address, 1ul << 40: all correct on LP64, all wrong on ILP32. Fix: uint64_t and %llx, or a format attribute.
    • 

  • Calling non-atomic helpers atomic. port32.cc's __atomic_*_8 are safe only on one CPU with interrupts masked. On SMP, take a lock or remove 64-bit atomics from core code.
    •

Answers to Check yourself


    

  1. LP64: int 32, long 64, long long 64, pointers 64. ILP32: int 32, long 32, long long 64, pointers 32.
    2. 

  2. They divide 64-bit numbers, which their compilers turn into calls to __udivdi3 (i386) and __aeabi_uldivmod (32-bit Arm EABI) that the freestanding build does not link. They needed those helpers (port32.cc).
    3. 

  3. Clang's default for aarch64-linux-gnu uses outline atomics, so fetch_add became a call to __aarch64_ldadd8_relax. The course's kernels are built with -mno-outline-atomics, so the compiler emits the atomic instructions inline.
    4. 

  4. It is a plain load and a plain store: another CPU (or an interrupt handler) can update the value between them, losing an increment, and a 64-bit store on a 32-bit CPU may even be split into two 32-bit stores that another CPU sees half-done. Fixes: protect every 64-bit atomic with a spinlock (and mask interrupts while holding it), or avoid 64-bit atomics in shared code on 32-bit ports (use 32-bit counters, or per-CPU counters summed under a lock).
    5. 

  5. Every devicetree field is read with fdt::be32/be64, which assemble the value from bytes in a fixed order; no native multi-byte load of devicetree data happens, so the CPU's own byte order never enters.
    6. 

  6. With format(printf, 3, 4) the compiler checks each argument against the format; on ILP32 targets it would warn that %lx expects unsigned long but the argument is unsigned long long (and with -Werror, fail the build), even when built on an x86-64 machine for that target.
    7. 

  7. Wrong on the big-endian X2 targets (big-endian PowerPC and MIPS): FAT32 stores the field little-endian. Fix: le32(p + 32) assembled from bytes. It also violates the alignment row: offset 32 of a buffer may not be 4-byte aligned in general (it is here only if the buffer is), and some CPUs trap on unaligned loads.
    8. 

  8. The literal now has type unsigned long on ILP32 (it fits), so %lx reads exactly it and the later arguments are correct: no crash. The printed field is "80000000", which no longer matches the expected text "ffffffff80000000", so the test fails cleanly instead of crashing. (Run it to confirm.)
    9. 

  9. Memory ordering, atomics on SMP, I/D cache coherence, the MMU model, interrupts and timers, privileged context switching and the boot protocol. qemu-user runs one user process on the host's kernel: no privileged instructions, devices, page tables, caches or second CPU of the target exist in that setting.

Forensic lab answer key


    

  1. 0xffffffff: i386, arm, riscv32. 0x80000000: mips, ppc.
    2. 

  2. Byte order: the first group is little-endian, the second big-endian. The 8-byte argument 0xffffffff80000000 is read as two 4-byte words; the second word becomes the %s pointer: the high half (0xffffffff) on little-endian CPUs, the low half (0x80000000) on big-endian ones.
    3. 

  3. Five independently broken arch layers would not all fail in the same test, at addresses that are the two halves of the same constant; and R3 shows each of these arch layers printing, running constructors and exiting correctly in the tests before it. One neutral line misread on every ILP32 CPU explains all five; R4's pass with only neutral files changed proves it.
    4. 

  4. The test passes a 64-bit value with %lx (a long-sized format) and an ul suffix, which on ILP32 is a 64-bit unsigned long long. kformat treats %llx the same as %lx and reads a long. With only the test fixed, kformat would still read 4 bytes for %llx, and the crash would remain.
    5. 

  5. Both are bugs fixed (neutral code that was wrong on ILP32, corrected without changing the design). The non-atomic 64-bit helpers are a design decision to record separately.
    6. 

  6. Build the neutral code for at least one ILP32 and one big-endian target in CI (this lab's round 2 takes seconds), and declare ksnprintf and kprintf with a format attribute so the compiler checks arguments. Wrong answers: "run the tests on more 64-bit CPUs" (all LP64 CPUs hide it), "use %p" (the value is not a pointer).
