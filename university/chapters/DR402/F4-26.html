Story hook

Ana's block driver had run for months on the x86 test machines. Ported to an Arm server, it passed every test at first. Then, under load, one in a few thousand reads returned the wrong sector's data. Never the same sector twice, never on x86, never with the debugger attached. The driver code was arch-neutral C++: the same lines, compiled for another CPU. What changed was not the code but the rules of the machine underneath it: on x86-64 other observers see a CPU's stores in the order the program made them, and on AArch64 they are not required to.

This chapter does three things on QEMU's virt machine. It asks the firmware to start every other CPU (PSCI CPU_ON), gives each CPU its own data through a system register, and proves a lock with all of them hammering on it at once. It moves the virtio block driver of DR301 from PCI to the virtio-mmio transport the Arm virt machine offers. And it meets Ana's bug: the course forensic, "Works on x86, corrupts on ARM", read from a log of reordered descriptor writes.

What you will be able to do

  • Start secondary CPUs through PSCI CPU_ON and explain what state each one starts in.
  • Give each CPU its own data through TPIDR_EL1, and its own stack, MMU setup and GIC redistributor.
  • Write a lock and a publish step whose ordering is correct on x86-64, AArch64 and RISC-V, and read the instructions each CPU gets.
  • Choose the right barrier for CPU-to-CPU ordering and for CPU-to-device ordering.
  • Drive a virtio-blk device through the virtio-mmio transport, and refuse the legacy transport clearly.
  • Diagnose a missing barrier from a trace of store visibility.
Jargon box
PSCI CPU_ON
Simple words: a firmware call that switches on another CPU and starts it at an address you give. Analogy: asking the caretaker to unlock another classroom and send a teacher to a given page of the plan. Precise: PSCI function 0xC4000003 (64-bit), arguments target MPIDR affinity, entry point address, context ID; the target starts at the entry point with the MMU and caches off and the context ID in x0. D1
MPIDR (multiprocessor affinity register)
Simple words: each CPU's own address, as a set of up to four numbers. Analogy: building, floor, corridor, room. Precise: MPIDR_EL1's Aff3–Aff0 fields; the devicetree's cpu nodes give each CPU's affinity value in reg, and PSCI and the GIC use it to name a CPU. D2
Per-CPU data
Simple words: variables of which every CPU has its own copy. Analogy: each teacher's own register book on their own desk. Precise: a structure per CPU, found through a register only that CPU sees: TPIDR_EL1 on AArch64 (like GS base on x86-64, tp or sscratch on RISC-V). D2
Memory model (weak, TSO)
Simple words: the rules for the order in which other observers see one CPU's memory accesses. Analogy: notes sent by internal post: on one school's post every note arrives in the order written; on another, notes to different rooms may overtake each other. Precise: x86-64 is total store order (stores are seen in program order; only a later load may pass an earlier store); AArch64 and RISC-V are weakly ordered (accesses to different addresses may be observed in any order unless a barrier, acquire or release orders them). D2 D5
Barrier (DMB, DSB)
Simple words: an instruction that stops the CPU from letting some accesses overtake others. Analogy: "post everything above before anything below". Precise: dmb orders memory accesses before it against those after it, for a given domain (ish: inner shareable, osh: outer shareable, sy: full system) and type (ld, st, or both); dsb additionally waits until they complete; acquire loads (ldar) and release stores (stlr) order one access. D2
virtio-mmio
Simple words: virtio devices found at fixed memory addresses instead of on a PCI bus. Analogy: the same delivery truck, parked at a numbered bay instead of booked through the bus office. Precise: a virtio transport with a register block per device (magic "virt", version, device ID, features, queue addresses, notify, status); version 2 is the modern transport, version 1 the legacy one; the devicetree lists each slot with compatible virtio,mmio. D3

Layer 1 — the kid explanation

Analogy

In the morning only one classroom is open. The principal (OS) asks the caretaker (firmware) to unlock the other classrooms one by one and send a teacher in with a page number of the day's plan. Each teacher gets their own register book, so nobody writes in somebody else's. Notes travel by the school's internal post. In the old school every note from one teacher arrived in the order it was written. In the new school, notes to different rooms may overtake each other, unless the teacher writes "deliver everything before this first" on the envelope.

Mapping: unlocking a classroom = PSCI CPU_ON; the page number = the entry address; the teacher's register book = per-CPU data; notes overtaking each other = weak memory ordering; "deliver everything before this first" = a barrier or release store.

Layer 2 — the student explanation

On x86-64 (B11) the boot CPU woke the others by sending INIT and startup interrupts through its local APIC, and each started in 16-bit real mode. On AArch64 machines that follow Arm's conventions, the kernel asks firmware instead: one PSCI call, CPU_ON, with the target CPU's affinity, an entry address and a value for x0. The target starts at that address at the boot CPU's exception level, with the MMU and caches off. QEMU's virt machine implements PSCI itself; on real boards it is usually Arm Trusted Firmware. The devicetree's cpu nodes list each CPU's affinity in reg, and the /psci node says whether to call with HVC or SMC (F4-23's checklist rows 2 and 3). D1

Each new CPU needs its own stack, its own vector-table setting, the MMU switched on with the same tables, a way to find its own data, and its own GIC redistributor. For its own data the kernel stores a pointer in TPIDR_EL1, a register each CPU has privately: this_cpu() reads it. Then the CPU tells the boot CPU it is online.

With several CPUs running, memory ordering matters. The ticket lock from B11 is written with std::atomic and explicit memory orders, so the same source is correct everywhere: the compiler emits each CPU's instructions. But code that shares data through plain variables and relied on x86's order without saying so becomes wrong on Arm. The lab shows both: a lock that keeps an exact count with eight CPUs, and a deliberately racy counter that loses updates.

The disk moves too. On the PC, DR301's virtio-blk driver found its device on PCI. The Arm virt machine also offers 32 virtio-mmio slots at fixed addresses; this chapter adds a virtio-mmio transport and reads a known sector through it. The ordering of the driver's writes to the ring, and to the device's doorbell, is exactly where Ana's bug lives.

Layer 3 — the engineer's depth

PSCI CPU_ON in detail

The boot CPU calls CPU_ON (function ID 0xC4000003, the 64-bit variant) with x1 = the target's MPIDR affinity value from the devicetree, x2 = the physical address of secondary_entry, x3 = a context ID, here the CPU's index. Return 0 means success. The lab also checks two errors: CPU_ON for a CPU that is already on returns −4 (ALREADY_ON), and AFFINITY_INFO for each CPU returns 0 (ON) once all are up (R4). The order in which CPUs report online differs from the order they were started (R4: 1, 3, 2; R5: 1, 2, 3, 7, 6, 5, 4; the order changes from run to run): each is a separate thread on the host and runs when the host schedules it. D1 R4 R5

The entry address must be a physical address, because the new CPU's MMU is off; with this lab's identity map it equals the virtual address. A kernel that runs in the upper half (F4-24's mini-project) must pass the physical address of a small identity-mapped entry stub. The context ID is the only data that reaches the new CPU in a register; everything else must be in memory that the new CPU reads with its MMU and caches off. D1

Not verified — check before relying on this

The PSCI function IDs (0xC4000003 CPU_ON, 0xC4000004 AFFINITY_INFO, 0x84000008 SYSTEM_OFF), the error code −4 meaning ALREADY_ON, AFFINITY_INFO's 0 meaning ON, and the entry state of a CPU started by CPU_ON (MMU and caches off, same EL as the caller, context ID in x0) are recalled from the Arm Power State Coordination Interface specification (D1), not opened in this build. The runs show QEMU's PSCI behaving this way at EL1 (hvc) and EL2 (smc, R3); firmware on real boards was not tested.

Caches off at entry: what the new CPU can see

A CPU that starts with its data cache off reads memory directly. Data the boot CPU wrote may still sit in the boot CPU's cache. On systems where caches are coherent for non-cacheable accesses this is harmless; on others the new CPU may read stale memory. This lab's secondary path reads only values fixed at link time (__stack_top, vector_table) before it enables its MMU and caches, and reads shared data only afterwards: that is why secondary_main calls mmu::enable_this_cpu() first (line 103), with the comment "before touching shared data". F4-27's spin-table boot has to do the opposite as well: the boot CPU cleans the release address to memory (dc civac) because the waiting CPU reads it with its cache off. D2

Per-CPU data and stacks

smp.S gives CPU n the stack __stack_top − n × 16 KiB; the linker script reserves room for eight. cpu_setup writes TPIDR_EL1 = &g_cpu[n]; this_cpu() reads it back. R2–R5 print "TPIDR_EL1 -> g_cpu[n]" from the value read back, and the SGI test increments a counter through this_cpu() in the interrupt handler, which is only correct if each CPU finds its own. TPIDR_EL1 is not accessible at EL0, unlike TPIDR_EL0 which user programs use for thread-local storage; a kernel that saves the user's TPIDR_EL0 on context switch keeps the two apart. D2 R4

The memory model: what changes from x86-64

On x86-64, other CPUs see a CPU's stores in program order, and loads are not reordered with older loads; the only visible reordering is a later load passing an earlier store to a different address (store buffering). That is total store order (TSO). On AArch64 and RISC-V (RVWMO), loads and stores to different addresses may be observed out of order in all four combinations, unless a dependency, a barrier or an acquire/release access orders them. Accesses to the same address are always seen in order by every observer (coherence). D2 D5

C++'s memory orders are the portable way to say what you need. R8 shows the same three publish functions compiled for three CPUs. With plain stores (publish_plain) all three compilers emit plain stores. With a release fence, x86-64 gets no instruction at all (TSO already provides the order; the fence only stops the compiler from moving stores), AArch64 gets dmb ish and RISC-V gets fence rw,w. With a release store of the index, x86-64 again gets a plain mov, AArch64 stlrh and RISC-V fence rw,w before sh. The x86 binary is identical for plain and release: that is exactly why a missing release goes unnoticed on x86 and shows up on Arm. R8

Not verified — check before relying on this

The descriptions of TSO (x86-64), the AArch64 memory model and RVWMO, the barrier domain and type options (ish, osh, sy; ld, st), and the claim that ordering for a device requires the outer-shareable or system domain while CPU-to-CPU ordering needs inner-shareable are recalled from the Arm Architecture Reference Manual (D2), the Intel SDM's memory-ordering chapter (D4), the RISC-V unprivileged specification's RVWMO chapter (D5) and the Linux kernel's memory-barriers document (D6), none opened in this build. The instruction sequences in R8 are measured (GCC 13.3.0, -O2); what they guarantee on hardware is recalled. QEMU's TCG on an x86-64 host did not show reordering in this lab's real-kernel runs, so the barriers in virtio_mmio.cc are argued, not demonstrated on hardware.

CPU-to-CPU versus CPU-to-device ordering

A lock orders memory between CPUs: dmb ish or acquire/release in the inner-shareable domain is enough. A DMA device is a different observer. To make descriptor writes visible to a device before the index, the driver needs a barrier whose domain includes the device; to make all of that complete before the MMIO write that rings the doorbell, it needs a barrier that waits (dsb), because the doorbell is a write to Device memory that can otherwise reach the device first. virtio_mmio.cc lines 52–58 name the three barriers the driver uses: dmb oshst (publish), dsb st (doorbell) and dmb oshld (consume: read the used index before the data). These choices follow the Linux kernel's mapping for its DMA barriers as recalled, and are the most conservative of the arguments in this chapter that the lab cannot test. D6

Under QEMU the "device" is host code that reads guest memory: with TCG on an x86-64 host the guest's stores reach host memory in program order regardless of barriers, so the lab cannot show the device-side bug in the kernel. That is why the forensic lab uses a model, reorder_sim.cpp, labelled as a model in its first line of output. R6

The ticket lock and the racy counter

spinlock.h's ticket lock takes a ticket with a relaxed fetch_add, waits with acquire loads until its number is served, and releases with a release store. The acquire pairs with the release: the next owner sees every write the previous owner made inside the lock. On AArch64 the waiting loop uses wfe, and the unlock sends sev after a dsb ishst (F4-24's arch.h), so waiting CPUs sleep instead of spinning. R5: eight CPUs × 1000 rounds give the locked counter exactly 8000; the racy counter, updated with a separate load and store, ends at 7806: 194 increments lost. R3 and R4 lose 1298 of 400000 and 17008 of 800000. The losses differ on every run; only their presence with more than one CPU is the finding. The lock is correct; the racy counter shows why it is needed. R5 R3 R4

Fairness has a price under emulation. With eight vCPUs on a four-CPU host, the CPU whose ticket is next may not be running, and everyone else waits for it. How much that costs depends on what else the host is doing. R5 (1000 rounds) took 87 ms of wall time in the final run. R9 (4000 rounds) took 278 ms in the final run, while two earlier runs of the same configuration in this build, with other work loading the host, took about 23 seconds and did not finish within 30 seconds. Variation of two orders of magnitude for the same code and input is the signature of a fair lock whose next owner is descheduled: a known problem for ticket locks in virtual machines on overcommitted hosts, not a correctness bug. The numbers are host-dependent and the chapter claims none of them for hardware. R9's racy counter shows no lost updates in the final run (32000): another reminder that a race that does not show proves nothing. R5 R9

virtio-mmio: version 2, and the legacy default

The virtio-mmio register block starts with the magic value 0x74726976 ("virt" read as a little-endian 32-bit word), a version, a device ID (2 = block) and a vendor ID (R2: 0x554d4551, "QEMU"). Initialisation follows the virtio sequence of DR301: reset, ACKNOWLEDGE, DRIVER, feature negotiation (VERSION_1 is feature bit 32, selected through the features-select register), FEATURES_OK, queue setup, DRIVER_OK. The queue's three areas are given to the device as 64-bit addresses split into low and high registers, instead of PCI capability structures. D3 R2

QEMU 8.2.2's virt machine presents version 1 (legacy) virtio-mmio by default. The legacy interface uses a different queue setup (a page-frame number and alignment) and does not use VERSION_1. This driver supports only version 2, so run.sh passes -global virtio-mmio.force-legacy=false; without it the driver says "version 1 (legacy): unsupported, this driver needs version 2" and D3 fails (R10). The same principle as F4-25's GICv2 refusal: detect, say so, stop. D7 R10

Not verified — check before relying on this

The virtio-mmio register offsets in virtio_mmio.cc lines 8–13, the status bits, the virtio-blk request layout and the meaning of version 1 versus 2 are recalled from the OASIS "Virtual I/O Device (VIRTIO)" specification, section "Virtio Over MMIO" (D3), and QEMU's force-legacy property and its default from QEMU's behaviour (D7); none opened. The run reading the known sentence back from sector 0 (R2–R5) checks the offsets against QEMU's implementation, not against the specification.

"Shared, not copied": the transport boundary

Milestone D3 asks that "your C4 virtio-blk driver code is shared, not copied". DR301's virtio code (F4-05) mixes the transport into the device layer: vio::init takes a PCI address, enables bus mastering and walks PCI capabilities. It cannot be reused over virtio-mmio as written. The lab's virtio_mmio.cc is therefore a separate, smaller driver, which the acceptance test does not allow for your own kernel. The fix is a transport interface below the device drivers: read and write device configuration, get and set features, set up queue n at given addresses, notify queue n, read and write status. PCI and MMIO each implement it; virtio-blk and virtio-net use only it. This is recorded as a decision for the course owner (DR301's code would change), and it is the mini-project. D8

How the hardware actually does it

On a real Arm system, PSCI is implemented by firmware running at EL3 (often Trusted Firmware-A). CPU_ON powers up the target core through the SoC's power controller, the core comes out of reset in EL3, and firmware drops it to the requested entry at EL2 or EL1. Between "returns 0" and the core executing your first instruction there can be a power-up delay; the kernel must not assume the new CPU is running when the call returns, which is why the lab waits for the online counter. D1

Weak ordering is not a theoretical permission: out-of-order cores with store buffers and multiple paths to memory make stores visible out of order, and interconnects between cores and devices can reorder further. Coherent DMA on Arm servers makes device reads see CPU caches, but does not order the CPU's stores; non-coherent DMA (common on small SoCs) additionally needs cache cleaning before the device reads and invalidation before the CPU reads what the device wrote. QEMU's virtio devices are coherent by construction. D2 D6

Not verified — check before relying on this

The EL3 firmware path for CPU_ON, the power-up behaviour, and the statements about coherent and non-coherent DMA on real SoCs are recalled. Untested on hardware: no Arm server or board ran this lab. F4-27 starts CPUs on a Raspberry Pi model in QEMU with the spin-table method instead of PSCI, which is what that board's firmware offers.

Worked example

Task. Read R6's first trace events and explain request 1 in terms of Figure 2; then compute how many stores the driver issues for 1000 requests and what fraction of requests were corrupted.

Request 1. At t = 5 the CPU issues desc[1].addr = 0x40201000, desc[1].len = 1024, ring[1] = 1, idx = 2. The model makes one store visible per step: t = 5 len[1], t = 6 ring[1], t = 7 idx = 2. At t = 7 the device sees idx 2, reads ring[1] = 1, then desc[1]: len is 1024 (new), addr is 0x0, the value from before any request used slot 1. The device performs a DMA to address 0 with 1024 bytes: "not what the driver wrote for this request". The addr store becomes visible only at t = 20. R6

Request 2. At t = 8 the idx = 3 store becomes visible first: ring[2] still holds 0 (from the initial memory), so the device uses slot 0 and DMAs to request 0's buffer at 0x40200000. A stale ring entry is as harmful as a stale descriptor.

Totals. Four stores per request, 4000 stores for 1000 requests. The weak model without a fence: 645 of 1000 requests used a stale or wrong descriptor (64.5 %). In-order: 0. Weak with a fence before idx: 0, and the store buffer never held more than 4 stores (one request), against 9 without the fence. The fence costs some overlap and buys correctness. These rates are the model's, under its seeded random choice; a real CPU's rate is unknown and is usually far lower, which is what makes the real bug rare. R6 R7

Where the analogy breaks


    

  • Notes do not overtake each other on their way; the order is decided at the source and in between. The post analogy suggests a delivery race. In hardware the reordering happens in the CPU (store buffers, out-of-order execution) and in the interconnect, and it is a permission the architecture grants, not a race any one note loses.
    • 

  • A single room always sees its own notes in order. The analogy lacks coherence: every observer sees writes to one location in the same order. The model honours it (R6: stores to the same field never pass each other), and so does the ticket lock, which relies on it.
    • 

  • The caretaker does not stay. In the analogy the caretaker could be asked again at any time. PSCI is indeed callable at any time, but on boards without it (F4-27's spin table) the firmware is gone once the kernel runs, and the kernel can never ask again.
    • 




Common mistakes and debugging


    

  • Enabling the device's legacy default by accident. QEMU's virt machine gives legacy virtio-mmio unless told otherwise. Symptom without a version check: queue setup writes go to registers that mean something else, and the first read hangs. Fix: check the version register and refuse clearly (R10).
    • 

  • Reading shared data before the MMU and caches are on. Works on QEMU, can read stale values on hardware. Fix: link-time constants only until enable_this_cpu().
    • 

  • Using a CPU index as an MPIDR. On virt they happen to be equal in Aff0; on many SoCs clusters put CPUs at 0x0, 0x1, 0x100, 0x101. Fix: take reg from the devicetree's cpu nodes (line 143).
    • 

  • Assuming CPU_ON's return means the CPU runs. Fix: wait for the CPU to say so (online counter with release and acquire).
    • 

  • Plain variables shared between CPUs. The racy counter (R3–R5) is the visible symptom; the invisible one is the course forensic. Fix: std::atomic with the order you mean, or the lock.
    • 

  • dmb ish for device ordering. std::atomic_thread_fence(release) gives dmb ish (R8), which orders for other CPUs in the inner-shareable domain, not necessarily for a device. Fix: the driver's own barriers (lines 52–58), named after what they order.
    • 

  • Testing ticket locks with more vCPUs than host CPUs and calling the slowness a hang. R9 and its earlier runs show it can be very slow, not stuck, depending on host load; keep the round count small in CI or use a host with enough CPUs.
    • 




Transition box

Where you came from: OS303 B11 on x86-64: INIT-SIPI-SIPI through the local APIC, a 16-bit trampoline below 1 MiB, per-CPU data through GS base, a ticket lock, IPIs through the APIC; DR301's virtio-blk over PCI. What carries over: the ticket lock source (unchanged, because it uses std::atomic); the per-CPU structure; the virtqueue layout and the virtio initialisation sequence; the boot-CPU-waits-for-online-counter pattern. What changes: one firmware call replaces the APIC sequence and the trampoline; the CPU starts in 64-bit mode at your address; per-CPU data through TPIDR_EL1; IPIs are GIC SGIs; the memory model is weak, so every unstated ordering assumption must become an explicit acquire, release or barrier; the virtio transport is MMIO registers. What comes next: F4-27 takes the kernel to a Raspberry Pi model (milestone D4): a board-specific devicetree, the spin-table boot method instead of PSCI, and a recovery-friendly setup for real hardware.

Summary


    

  • PSCI CPU_ON starts a CPU at a physical entry address with the MMU and caches off and a context ID in x0; the target's affinity comes from the devicetree.
    • 

  • Each CPU needs its own stack, VBAR, MMU enable, redistributor and per-CPU pointer in TPIDR_EL1.
    • 

  • x86-64 is TSO; AArch64 and RISC-V are weakly ordered. Code that relied on TSO without saying so breaks on Arm.
    • 

  • std::atomic orders compile to nothing extra on x86-64 and to dmb, stlr or fence elsewhere; device ordering needs barriers that cover the device and complete before the doorbell.
    • 

  • virtio-mmio version 2 is the modern transport; QEMU's virt default is legacy, which the driver refuses clearly.
    • 

  • "Shared, not copied" needs a transport interface below the virtio device drivers.
    •

Answers to Check yourself


    

  1. Target MPIDR affinity, entry point (physical address), context ID. The target starts at the entry point, at the caller's exception level, with the MMU and caches off and the context ID in x0.
    2. 

  2. With caches off it reads memory directly and may see stale values of data the boot CPU wrote into its cache; with the MMU off, memory is also treated as Device memory, which forbids unaligned accesses. After enable_this_cpu() it uses the same coherent, cacheable view as the others.
    3. 

  3. A pointer to this CPU's PerCpu. TPIDR_EL0 is writable by user programs (thread-local storage), so the kernel cannot trust it; TPIDR_EL1 is accessible only at EL1 and above.
    4. 

  4. Stores become visible to others in program order, and loads are not reordered with older loads or stores, except that a later load may complete before an earlier store to a different address is visible (store buffering). That store-to-load reordering is the one x86-64 allows.
    5. 

  5. On x86-64 a plain store already has release semantics under TSO, so the compiler needs no instruction; on AArch64 it must use stlrh (or a dmb) to order the index after the earlier stores.
    6. 

  6. With several CPUs, two can load the same value and both store value + 1: one increment is lost. With one CPU there is nobody to interleave with.
    7. 

  7. 0x100 as the target (the affinity value itself, not 1). The stack: __stack_top − 4 × 16 KiB: the context ID, not the MPIDR, picks the stack. (Check g_cpu is sized for the index, not the MPIDR.)
    8. 

  8. The slot line says "version 1", the driver prints "version 1 (legacy): unsupported", the sector line disappears and the verdict is D3 FAILED, exit code 0x11 through SYSTEM_OFF, as in R10.
    9. 

  9. The device is QEMU host code; with TCG on an x86-64 host, guest stores reach memory in program order, so the window in which the device could see the index before the descriptor never opens. A model or real weakly ordered hardware is needed.
    10. 



Forensic lab answer key


    

  1. Request 1: addr[1] (visible only at t = 20). Request 2: ring[2], so the device used slot 0 (and slot 2's descriptor stores were also late). Request 3: ring[3] (visible at t = 14) and addr[3]/len[3]. Request 4: addr[0]'s new value (0x40204000, visible at t = 16) and len[0]; ring[0] held the right slot by coincidence (0 from request 0), so the device used request 0's buffer and length. Request 5: addr[1] (request 1's store became visible at t = 20, request 5's at t = 21) and len[1].
    2. 

  2. Under TSO stores become visible in program order: by the time the index store is visible, the descriptor and ring stores are too. R8 shows the compiler emits plain movs for all three variants on x86-64: nothing in the code expressed the ordering, and the x86 hardware provided it anyway.
    3. 

  3. "The device reads late": a late read would see more of the new values, not fewer; the trace shows the device reading right after the idx store becomes visible, with older stores still waiting. "The CPU makes the index visible before the descriptor": every bad request shows idx visible while an older store to the descriptor or ring is not. The second is proven.
    4. 

  4. "weak+fence: 1000 requests, 0 used a stale or wrong descriptor". The ordering point is between the ring store and the index store: publish_fence line 32, or the release store of publish_release line 43.
    5. 

  5. A barrier that orders the descriptor and ring stores before the index store for the device's domain (dmb oshst or stronger), and one that makes everything complete before the MMIO doorbell write (dsb st), plus a read-side barrier after seeing the used index (dmb oshld): virtio_mmio.cc lines 165–171. std::atomic_thread_fence(release) compiles to dmb ish (R8), whose domain is inner shareable: enough for other CPUs and for a hypervisor's device emulated on other CPUs, not guaranteed for a device outside that domain (recalled; unverified box).
    6. 

  6. Write every cross-agent publication with explicit release/acquire or named barriers, never plain stores; review for "flag after data" patterns; test on a weakly ordered machine or with a memory-model checker or model (like reorder_sim); run the same tests on AArch64 hardware in CI. Wrong answers: "add a delay before the doorbell" (hides the window, does not close it), "make the variables volatile" (stops compiler reordering only; R8's plain stores are already in order in the binary, and the CPU reorders them).
    7.
