Story hook

Ms Okafor has been the principal of the same school for years. She knows where every room is, which key opens which door, which bell rings at the end of a lesson and whom to call when the heating fails. Then the school board asks her to open a second school, in a building she has never seen, in another town. Her timetable, her rules for settling quarrels and her lesson plans all still work there: none of them mention a room number. What does not carry over is everything about the building. Where are the classrooms? Where is the doorbell wired to? Who is the caretaker, and what will the caretaker tell her on the first morning?

A sensible principal does not wander around hoping to find out. She sits down with a list of questions that any building must answer, in the same order every time, and she writes the answers down before the first pupil arrives. This chapter gives you that list for computers. You have a kernel that runs on an x86-64 PC (OS303). Over this course you will move it to two other CPU families, 64-bit Arm and RISC-V, without rewriting the parts of it that never mentioned the PC. The first step is not code: it is nine questions, and a small tool that makes the machine answer most of them itself.

What you will be able to do

  • Fill the nine-row platform checklist of the curriculum for an unfamiliar machine, and name for each row the document where the answer lives.
  • Read a flattened devicetree blob (DTB) with your own freestanding parser, and explain its header, tokens, cells and phandles.
  • Extract a machine's memory map, interrupt controller, timer, console, storage and SMP method from the devicetree QEMU hands to a kernel.
  • Separate a kernel into an arch-neutral core and an arch layer, and prove the separation with a test suite that compiles unchanged on every port.
  • Diagnose a kernel that boots on one machine and is silent on another, from an interrupt trace and a symbol lookup.
Jargon box
Platform
Simple words: everything around the CPU that a kernel has to know about: memory, devices, firmware, how the other cores start. Analogy: the school building, as opposed to the principal's rules. Precise: in this course, the answers to the nine rows of the curriculum's checklist (CPU manual, firmware handoff, memory map, interrupt controller, timer, console, storage, SMP start-up, other devices) for one machine. D2
Arch layer
Simple words: the part of a kernel that is written again for every CPU family. Analogy: the notes about one particular building. Precise: the files that use CPU-specific instructions, registers or calling conventions (entry code, exception vectors, page-table format, interrupt-controller and timer drivers, the firmware interface), behind interfaces that the arch-neutral core calls. D2
Arch-neutral code
Simple words: kernel code that compiles and behaves the same on every CPU. Analogy: the timetable rules, which mention no room numbers. Precise: code with no inline assembly, no fixed page or cache-line size, explicit byte order for external data, atomics only through the language's atomic types, and no assumption about pointer width beyond what it states (curriculum 10.2). D2
Devicetree
Simple words: a data structure that firmware hands to the kernel, describing the machine's hardware as a tree of named nodes with properties. Analogy: the plan of the building that the caretaker leaves on the principal's desk (a mapping proposed for the registry in this course's notes). Precise: the format defined by the Devicetree Specification; in memory it is a flattened devicetree blob (DTB) whose address the boot protocol passes in a register. D1
DTB (flattened devicetree blob)
Simple words: the binary form of a devicetree. Analogy: the plan folded into an envelope, with a table of contents on the front. Precise: a header (magic 0xd00dfeed, total size, offsets of the blocks, version), a memory-reservation block, a structure block of 32-bit big-endian tokens (BEGIN_NODE, END_NODE, PROP, NOP, END) and a strings block of property names. D1 R1
Cell (devicetree)
Simple words: one 32-bit number inside a devicetree property. Analogy: one box on a form, always the same size. Precise: a big-endian 32-bit unit; a 64-bit address is two cells, and the parent node's #address-cells and #size-cells say how many cells each entry of a child's reg property uses. D1
compatible (property)
Simple words: the list of names a device answers to, most specific first. Analogy: the language a visitor speaks, written on the visitor's badge, so the school can call the right interpreter. Precise: a string list such as "arm,pl011", "arm,primecell"; a driver binds to a node whose list contains a string it knows. D1
phandle
Simple words: a number that one devicetree node uses to point at another. Analogy: a room number written on a note in another room. Precise: a 32-bit value in a node's phandle property; properties such as interrupt-parent and interrupts-extended refer to nodes by it. D1

Layer 1 — the kid explanation

Analogy

A principal (the operating system) moves to a new school building. The rules for running a school stay the same. The building is new. On the first morning the caretaker (the firmware) has opened the doors, switched on the lights and left a plan of the building on the principal's desk (the devicetree). The plan says where the classrooms are (memory), where the doorbells ring (the interrupt controller), where the school clock hangs (the timer), where the office window is for talking to the outside (the console) and how to wake the other teachers (starting the other CPU cores). The principal reads the plan instead of guessing. Visitors speaking a new language still need their interpreter (a driver).

Mapping: principal = operating system; caretaker = firmware; building plan on the desk = devicetree; doorbells = interrupts; interpreter for a visitor = driver. The building plan is not yet in the university's analogy registry; it is proposed in this course's notes.

Layer 2 — the student explanation

Your OS303 kernel is two kinds of code mixed together. One kind talks about the machine: it writes to I/O port 0x3F8 to print a character, programs the local APIC, loads a GDT, reads the multiboot or UEFI memory map. The other kind talks only about ideas: a formatted print routine, a frame allocator, a scheduler's run queue, a file system's directory lookup. The second kind should not care which CPU runs it. Porting is the act of rewriting the first kind for a new machine while leaving the second kind byte for byte unchanged. When the second kind has to change, the curriculum calls that design feedback: the port has found a hidden assumption, and you record it. D2

To know what the first kind must do on a new machine, you answer nine questions. Row 1 is the CPU itself: privilege levels, how exceptions arrive, how the MMU translates addresses. That answer lives in the architecture manual and changes only when the CPU family changes. Row 2 is the handoff: who starts your kernel, in which CPU mode, and with which information in which register. Rows 3 to 8 are the machine around the CPU: memory ranges, the interrupt controller, the timer, the console UART, storage and how to start the other cores. Row 9 is every other device, and it is the subject of the driver courses. D2

On a PC, rows 3 to 8 come from firmware tables (the UEFI memory map and ACPI tables you met in OS301 and OS302) plus a few addresses that every PC has had for decades. On the Arm and RISC-V machines of this course, rows 3 to 8 come from one structure: the devicetree. QEMU builds it for the machine you asked for and passes its address to your kernel in a register. Your kernel reads it at boot. That is why this chapter's main code is a devicetree parser: it is the first piece of new code, and it is itself arch-neutral, so the same file runs on the host, in the AArch64 kernels and in the RISC-V kernels. D1 D5 D6

The lab runs three QEMU machines and asks each one to describe itself. For AArch64 and RISC-V it uses QEMU's dumpdtb machine option, which writes the devicetree QEMU would give a kernel into a file; the tool then answers the checklist from that file. For the PC, which has no devicetree, it asks the QEMU monitor for the machine's memory map. The answers come out of the machines, not out of anybody's memory, and they are the same answers your kernels will find at boot. R2 R3 R4

Layer 3 — the engineer's depth

The checklist as an engineering artefact

The checklist of curriculum section 9.1 is a table of questions with, for each row, the class of document that answers it. Treat it as the first deliverable of any port, before code: a page that a reviewer can check row by row against the named documents. For each row record (a) the answer for the target, (b) the document and section it came from, (c) whether the kernel reads the answer at boot or compiles it in. Rule of thumb for (c): compile in what the architecture fixes (row 1: the exception-vector layout, the page-table format); read at boot what the machine decides (rows 3 to 8). A compiled-in answer to rows 3 to 8 is a promise that the kernel will only ever run on one machine, and this chapter's forensic lab shows what that promise costs. D2

The handoff contracts (row 2)

For each target the boot contract fixes three things: the CPU state at entry, where the kernel image is loaded, and where the hardware description is. On AArch64, the contract this course uses is the one QEMU implements for a kernel image passed with -kernel, modelled on the Linux arm64 booting document: the image starts with a 64-byte header (a branch instruction, a text offset, the image size, flags and the magic "ARM\x64"), the CPU enters at EL2 or EL1 with the MMU off, and register x0 holds the physical address of the DTB. On RISC-V, OpenSBI runs in machine mode, then jumps to the kernel in supervisor mode with a0 holding the hart ID and a1 the DTB address. On the PC you used UEFI (or Multiboot in some OS303 variants), with ACPI tables describing the machine. Chapters F4-24 and F4-28 print these values from real boots; here they are the row-2 entries of the table, tagged to the documents that define them. D5 D6 D8

The DTB format, as far as a kernel needs it

A DTB begins with a header of ten big-endian 32-bit fields. The parser in this chapter uses six of them: magic (0xd00dfeed), total size, offset of the structure block, offset of the strings block, version, and size of the structure block. The structure block is a sequence of 32-bit tokens. BEGIN_NODE (1) is followed by the node's name as a NUL-terminated string, padded to a 4-byte boundary. PROP (3) is followed by the value's length, an offset into the strings block for the property's name, and the value itself, padded. END_NODE (2) closes a node; NOP (4) is skipped; END (9) ends the block. Nesting is expressed only by BEGIN/END pairs, so a parser walks the block once, keeping a depth counter. D1

Two rules decide whether a parser is correct on every machine. First, every multi-byte number in a DTB is big-endian, whatever the CPU's own byte order: a parser that casts a pointer to uint32_t* reads the wrong numbers on a little-endian CPU, which is every CPU in this course except the big-endian ones of F4-30. Second, the meaning of a reg property depends on the parent node: the parent's #address-cells and #size-cells say how many 32-bit cells form one address and one size. The AArch64 virt root uses two and two, so memory is <0x0 0x40000000 0x0 0x10000000>: base 0x40000000, size 0x10000000 (256 MiB). A node under a bus with one address cell would read the same bytes completely differently. The parser therefore carries the cell counts down the tree as it walks. D1 R2

Three more mechanisms appear in the lab output. /chosen is not a device: it carries the firmware's choices, such as stdout-path (which node is the console) and bootargs (the kernel command line). A compatible property is a list, most specific name first, and a driver matches any entry it knows. A phandle lets one node name another: a device's interrupts belong to the controller whose phandle its interrupt-parent holds. F4-27 adds two more that a real board uses and QEMU's virt machines do not: aliases and address translation through ranges. D1

Arch-neutral by construction

The second artefact of this chapter is a rule and a test. The rule is the curriculum's neutrality list (section 10.2), restated for the code you already have: no inline assembly outside the arch layer; no hard-coded page size (ask the arch layer); explicit byte order for every external format; atomics only through std::atomic with the memory order stated; pointer width only through uintptr_t. The test is neutral_tests.cc: ten checks, written once, compiled unchanged into every kernel of this course, and given only three facts by each port (the CPU's name, the DTB pointer or none, the page size). The files from F3-18 (the formatted print code, the panic routine, the small C++ runtime) are treated the same way: each port compiles the very same files, and every build log records their SHA-256 sums so that a reviewer can see they were not edited. D2 R8

One subtlety makes this work. F3-18's panic.cc contains #include "arch.h". A C++ compiler looks for a quoted include first in the directory of the file that contains it, so compiling panic.cc in place would always pick F3-18's x86-64 arch.h. The course's build helper copies the reused files, byte for byte, into a scratch folder that contains no arch.h; the compiler then finds the port's arch.h on the include path. The file is the same; only the arch layer it is joined to changes. This is a build-system rule worth stating in your own port: the arch layer is chosen by the build, never by editing shared files. R8

When the port changes the core: design feedback

Some changes to shared code are inevitable, and the curriculum asks you to log each one as a bug fixed or a design change. Three examples from this course's own build: (1) DR301's virtio driver (F4-05) and its PCI code call the PC's port I/O directly, so the virtio-blk logic cannot be reused unchanged below a virtio-mmio transport; the honest fix is a transport interface, and F4-26 records that instead of copying the driver. (2) The formatting test of neutral_tests.cc passes a 64-bit constant with the format %lx; on every 64-bit CPU that is correct, and on 32-bit CPUs it is not (F4-30 shows the crash and the fix). (3) Compilers for AArch64 and RISC-V need different flags for freestanding code (outline atomics, a soft-float ABI); those belong in the build's arch section, not in the code. D2

How the hardware actually does it

In this build the "hardware" is QEMU, and the devicetree is produced by QEMU's machine model: when you ask for -M virt -smp 4 -m 256M, QEMU creates the memory, the interrupt controller, the UART and the virtio slots at the addresses its model uses, and writes a DTB that describes exactly those. The AArch64 run shows a 1 MiB blob (1048576 bytes) with 4 CPU nodes, a GICv3 at 0x8000000 and 0x80a0000, a PL011 at 0x9000000, 32 virtio-mmio slots from 0xa000000 and PSCI through hvc. The RISC-V run shows a 5734-byte blob with a PLIC at 0xc000000, a ns16550a at 0x10000000 with interrupt 10, 8 virtio-mmio slots from 0x10008000, a timebase of 10000000 Hz and no enable-method at all (on RISC-V, harts are started through SBI, row 8). R2 R3

On a real board the devicetree comes from the board's firmware or from a file that the boot loader loads next to the kernel; the hardware does not generate it. A wrong or out-of-date devicetree is therefore a real failure mode on boards and almost never one in QEMU. The variants run shows how directly the description follows the machine: asking QEMU for a GICv2 changes the interrupt controller's compatible string to arm,cortex-a15-gic and its second register range, and asking for RISC-V's Advanced Interrupt Architecture replaces the PLIC by APLIC and IMSIC nodes. The kernel's code does not change; what it finds does. R5

Not verified — check before relying on this

That the PC column's sources are the UEFI memory map, the ACPI MADT for interrupt controllers and the HPET table for the timer, and that INIT-SIPI-SIPI is the PC's SMP start-up, comes from OS301–OS303 and the curriculum table, not from documents opened in this build. Check against the UEFI and ACPI Specifications (D8) and the Intel SDM Volume 3 multiprocessor initialisation chapter (D9). The x86 lab run (R4) shows only QEMU's own memory map (RAM, ROM, IOAPIC at 0xfec00000, HPET at 0xfed00000, the APIC/MSI window at 0xfee00000), not the firmware tables.

Worked example

Task. From the AArch64 checklist run (R2), decode the timer's interrupts property and the PL011's, and say which interrupt numbers a kernel would program into the GIC.

Step 1: read the raw values. R2 prints the timer as interrupts <0x1 0xd 0x4 0x1 0xe 0x4 0x1 0xb 0x4 0x1 0xa 0x4> and the UART as <0x0 0x1 0x4>. R2

Step 2: find the format. The meaning of an interrupts value is set by the interrupt controller's binding, through its #interrupt-cells. For the Arm GIC binding the value is three cells per interrupt: type (0 = SPI, shared peripheral interrupt; 1 = PPI, private per-CPU interrupt), number within that type, and flags (trigger type). Twelve cells for the timer are therefore four interrupts. D3

Step 3: convert to GIC interrupt IDs. In the GIC's numbering, SGIs are 0–15, PPIs start at 16 and SPIs at 32. So the timer's four PPIs 0xd, 0xe, 0xb, 0xa are interrupt IDs 16 + 13 = 29, 16 + 14 = 30, 16 + 11 = 27, 16 + 10 = 26. The UART's SPI 1 is interrupt ID 32 + 1 = 33. D3

Step 4: which timer? The order of the four entries in the Arm timer binding is: secure physical, non-secure physical, virtual, hypervisor physical. A kernel running at EL1 that uses the EL1 physical timer takes the second entry: ID 30. F4-25's kernel computes exactly this (16 + the PPI number of entry 1) and the lab run there confirms that its timer ticks arrive on that ID; F4-25 also shows GICv2's flags cell (0x104 instead of 0x4 in R5) carrying a CPU mask. D3 R5

Not verified — check before relying on this

The three-cell GIC interrupt format, the SGI/PPI/SPI ranges 0–15/16–31/32 and up, and the order of the four timer interrupts are recalled from the Linux devicetree bindings for the Arm GIC and the Arm architected timer and from the GIC Architecture Specification, none opened in this build. F4-25's run (timer ticks counted on ID 30, UART receive on ID 33) is consistent with them, which is evidence for the entries used there, not for the whole binding.

Where the analogy breaks


    

  • The plan is not checked by anyone. A caretaker's plan of a building can be compared with the building by walking around it. A kernel cannot walk around: if the devicetree says the UART is at an address where there is none, the kernel finds out only by faulting. The devicetree is a description, and a wrong description is a real class of bugs on boards.
    • 

  • The principal does not change. In the story only the building changes. In a port the CPU itself changes too (row 1): different privilege levels, a different exception model, a different page-table format. That part of the work is not in any plan; it is in the architecture manual and in the arch layer you write.
    • 

  • Some buildings come without a plan. The PC describes itself through ACPI tables and decades of fixed addresses, not a devicetree; some boards in F4-27 may start your kernel with no devicetree at all. The analogy suggests every school has a plan on the desk; machines do not.
    • 




Common mistakes and debugging


    

  • Reading DTB numbers with a pointer cast. *(uint32_t*)p returns byte-swapped values on a little-endian CPU. Symptom: absurd sizes such as 0x00000010 for 256 MiB. Fix: one be32 function used everywhere; the F4-30 big-endian runs prove it.
    • 

  • Decoding reg with fixed cell counts. Assuming two address cells works at the root of virt and fails under a bus node with one (F4-27's Pi devicetree). Symptom: half of an address read as a size. Fix: take the counts from the parent, as Node does.
    • 

  • Hard-coding the console address. The kernel works on the machine where you took the address from and is silent elsewhere. This is the forensic lab below. Fix: /chosen/stdout-path.
    • 

  • Expecting the same answers from the same machine name with different options. -M virt with gic-version=2 or aia=aplic-imsic is a different interrupt controller (R5). Fix: record the full QEMU command line next to every checklist.
    • 

  • Editing shared files "only a little" for a port. Each edit is a fork. Fix: put the difference behind an interface in the arch layer, and if the shared file must change, log it as design feedback and change it for every port at once.
    • 

  • Running QEMU without a time limit. A machine waiting for a kernel that is not there runs forever (an early attempt in this build to dump a PC devicetree booted the PC firmware and never returned). Fix: timeout on every QEMU command, exit code 124 recorded honestly.
    • 




Transition box

Where you came from: OS303's kernel on an x86-64 PC (milestones B1–B11), whose boot information came from UEFI and ACPI (OS301, OS302) and whose drivers you wrote in DR301. What carries over: every piece of code that never mentioned the PC: formatted output, panic, the C++ runtime, allocators, the scheduler's logic, the file systems. In this course they are compiled unchanged, with SHA-256 sums in every log. What changes: the hardware description arrives as a devicetree instead of ACPI tables, and everything in rows 1 to 8 is rewritten per CPU family behind interfaces. What comes next: F4-24 writes the first arch layer: AArch64 on QEMU virt, from the image header to decoded exceptions (milestone D1).

Mini-project


A checklist generator for any QEMU machine. Extend fdt_tool into a script plus tool that takes a QEMU binary and a -M string, dumps the devicetree, and writes the full nine-row checklist as an HTML table with, in each row, the answer, the devicetree node it came from and an empty "checked against (document, section)" column for the reviewer. Handle at least: /aliases in stdout-path, interrupts-extended, several interrupt controllers, CPUs with differing properties (sifive_u's first hart), and machines with no /chosen.


Rubric (10 points): correct answers for the three machines of this chapter and two others of your choice, checked against their dumps (4); aliases and multi-controller interrupts handled, with a test blob for each (2); the tool refuses a damaged blob cleanly (1); output usable as exam P's answer sheet (1); a short note per machine on which rows the devicetree could not answer (2).



Summary


    

  • A port starts with nine questions: CPU, firmware handoff, memory, interrupt controller, timer, console, storage, SMP start-up, other devices. Write the answers and their sources down first.
    • 

  • Compile in what the CPU architecture fixes; read at boot what the machine decides. On AArch64 and RISC-V boards and on QEMU virt, the machine's answers arrive in a devicetree.
    • 

  • A DTB is a header, a reservation block, a token stream and a string table; every number is big-endian; reg is decoded with the parent's cell counts.
    • 

  • QEMU can write the devicetree of any machine it models (dumpdtb), so the checklist can be answered by the machine itself.
    • 

  • Arch-neutral code is compiled unchanged on every port, proven by a shared test suite and recorded SHA-256 sums; every change to it is design feedback.
    • 

  • A constant where the checklist says "read at boot" works on one machine only; the forensic trace shows the cost.
    •

Answers to Check yourself


    

  1. CPU (compile in), firmware handoff (compile in the protocol, read the values it passes), memory map, interrupt controller, timer, console, storage, SMP start-up (all read at boot; the drivers for each controller type are compiled in, their addresses and numbers are not), everything else (drivers compiled in, devices found at boot).
    2. 

  2. The DTB format defines its numbers as big-endian regardless of the CPU. A direct load on a little-endian CPU byte-swaps every value; even if the kernel were only for one CPU, the data is not.
    3. 

  3. When the parent's #address-cells and #size-cells are both 1: address 0x10000000, size 0x100. With 2 and 2 (as at the virt root) the same eight bytes are only half an entry, and the parser must refuse it.
    4. 

  4. 0x10000000, interrupt 10, delivered through the PLIC at 0xc000000 (the console node's interrupt parent).
    5. 

  5. Row 8: there is no enable-method; RISC-V harts are started through the SBI Hart State Management extension, a firmware call (F4-29).
    6. 

  6. A quoted include is searched first in the including file's own folder. Compiled in place, panic.cc would include F3-18's x86-64 arch.h. In a scratch folder with no arch.h, the port's arch.h on the include path is found, and the file itself stays byte for byte the same.
    7. 

  7. Row 4 (compatible arm,cortex-a15-gic, a second register range instead of the redistributor region) and row 5 (the flags cell of the timer's interrupts changes to 0x104). Forensic lab answer key


    

  1. Yes. R7 shows traps from hart 1 with an epc inside the kernel (0x802003cc, above OpenSBI's "Next Address" 0x80200000), and addr2line places it in serial::put. The kernel runs; it cannot print.
    2. 

  2. Cause 5 is a load access fault: the instruction at epc tried to read from tval = 0x10000005 and the access was refused (nothing answers there on this machine). It is the loop in serial::put that waits for the transmitter, reading the line status register.
    3. 

  3. On virt the ns16550a is at 0x10000000 (R3), and register 5 with reg-shift 0 is the line status register (LSR), which put polls before each character. On sifive_u the UART is a sifive,uart0 at 0x10010000 (R5): a different device at a different address.
    4. 

  4. The trap handler reports exceptions by printing through the same serial::put, which faults again at the same address. With no working console the kernel cannot tell anyone; it re-enters the handler (232 traps counted in 3 seconds).
    5. 

  5. The kernel was built with -DFORENSIC_FIXED_UART: console_from_devicetree uses the constant 0x10000000 instead of /chosen/stdout-path. On sifive_u, stdout-path leads to /soc/serial@10010000, compatible sifive,uart0, so a correct kernel would also have needed a second UART driver (F4-29 writes it). How the fault was injected: that compile flag, nothing else.
    6. 

  6. Row 6 of the checklist for the second machine: filling it (R5) shows a different console device and address before any boot. In code: never compile in a row 3–8 answer; a kernel that reads stdout-path and finds no driver for the compatible string can at least fall back to the SBI debug console (F4-28) and say so. Wrong answers: "OpenSBI hung" (its banner ends and R7 shows the kernel executing), "the image was loaded at the wrong address" (addr2line resolves the epc to a valid kernel function).
