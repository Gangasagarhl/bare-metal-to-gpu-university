Story hook

Ravi had followed a well-known tutorial and his RISC-V kernel printed "hello" on QEMU in an afternoon. Then he read the course's milestone: "S-mode entry from OpenSBI". He moved his kernel from the tutorial's world, where it ran in the most privileged mode and owned the whole machine, to the world where a firmware called OpenSBI owns the most privileged mode and the kernel runs one level below. He kept the tutorial's linker script. The new kernel printed nothing at all: OpenSBI's banner, then silence. No crash message, no error, no "hello".

This chapter ports the kernel to its second architecture, 64-bit RISC-V, on QEMU's virt machine: entry in supervisor mode from OpenSBI, a trap vector, the 16550 UART the devicetree names, the Supervisor Binary Interface for what the kernel cannot do itself, and Sv39 paging. The forensic lab is Ravi's silence. After AArch64, much will look familiar; the chapter concentrates on what differs.

What you will be able to do

  • Explain RISC-V's privilege modes (M, S, U) and what OpenSBI leaves for an S-mode kernel.
  • Write an S-mode entry, a trap vector and a trap decoder using stvec, scause, sepc and stval.
  • Call the firmware through SBI: discover the specification version and extensions, and shut down.
  • Enable Sv39 paging with satp and predict page faults.
  • Reuse the arch-neutral code unchanged on a third architecture, with the console from the devicetree.
  • Diagnose a kernel linked at the wrong address from QEMU's interrupt log.
Jargon box
Privilege modes (RISC-V)
Simple words: RISC-V's three levels of permission: machine, supervisor, user. Analogy: the caretaker's level, the principal's level, the classrooms. Precise: M-mode (firmware; always present, full access, controls physical memory protection), S-mode (the OS kernel; virtual memory), U-mode (applications); each has its own trap registers (mcause, scause, ...). D1
SBI (Supervisor Binary Interface)
Simple words: the calls an S-mode kernel makes into M-mode firmware. Analogy: the service hatch in the caretaker's office. Precise: an ecall from S-mode with the extension ID in a7, the function ID in a6 and arguments in a0–a5; the firmware returns an error in a0 and a value in a1; extensions include TIME, IPI, RFENCE, HSM (hart state), SRST (system reset) and DBCN (debug console). D2
OpenSBI
Simple words: the usual open-source firmware that implements SBI. Analogy: the caretaker who stays in the building. Precise: M-mode firmware that initialises the platform, protects its own memory with PMP, and jumps to the next stage in S-mode with a0 = hart ID and a1 = devicetree address; QEMU's riscv64 virt loads a bundled copy by default. D3
Hart
Simple words: RISC-V's word for a hardware thread: one thing that runs instructions. Analogy: one teacher. Precise: a hardware thread with its own registers and program counter; a core may hold several; harts are numbered by hart ID (mhartid, readable only in M-mode, so firmware passes it in a0). D1
Trap CSRs (S-mode)
Simple words: the registers that say where traps go and what happened. Analogy: the doorbell's report card. Precise: stvec (handler address and mode), scause (bit 63 = interrupt; low bits = cause code), sepc (the instruction that trapped), stval (faulting address or instruction bits), sstatus (interrupt enable, previous mode); return with sret. D1
Sv39
Simple words: RISC-V's three-level page tables for 39-bit virtual addresses. Analogy: the locker map, in RISC-V's handwriting. Precise: satp.MODE = 8 selects it; three levels of 512 eight-byte entries; an entry with any of R, W, X set is a leaf (4 KiB, 2 MiB or 1 GiB); the physical page number is in bits 53:10. D1

Layer 1 — the kid explanation

Analogy

In this building the caretaker (firmware) never leaves. The caretaker has the master keys and an office the principal may not enter. When the principal (the kernel) needs something only the caretaker can do, such as setting the school alarm clock or switching the building off, the principal rings at the service hatch and asks. The principal arrives each morning at a door the caretaker chooses and finds the building plan (devicetree) left on the desk. If the principal's own plans assume they will start at a different door, everything they look up is one room off.

Mapping: caretaker = OpenSBI in M-mode; the office the principal may not enter = memory protected by PMP; service hatch = SBI ecall; the door = 0x80200000; the plan on the desk = the devicetree address in a1; "one room off" = a kernel linked for one address and loaded at another.

Layer 2 — the student explanation

RISC-V machines have a machine mode (M) that firmware uses, a supervisor mode (S) for the kernel and a user mode (U) for programs. On QEMU's virt machine, as on most RISC-V boards that run Linux, the firmware is OpenSBI. It initialises the hardware, protects its own memory from the kernel with physical memory protection (PMP), and jumps to the kernel at 0x80200000 in S-mode with the hart ID in a0 and the devicetree's address in a1. R2 shows OpenSBI's banner saying exactly this: "Domain0 Next Address 0x80200000", "Next Arg1 0x8fe00000", "Next Mode S-mode". R2

Things an S-mode kernel cannot do itself, it asks OpenSBI for through the Supervisor Binary Interface: an ecall instruction with an extension and function number in registers. The kernel probes which extensions exist: R2 lists TIME, IPI, RFENCE, HSM, SRST and DBCN, all present on SBI 1.0. At the end of the test it uses SRST (system reset) to shut QEMU down, as F4-24 used PSCI's SYSTEM_OFF. D2 R2

Traps work like AArch64's with different names. One register, stvec, holds the handler's address; every exception and interrupt arrives there. scause says why (bit 63 set for an interrupt), sepc where, and stval gives the faulting address or, for an illegal instruction, the instruction itself. The handler returns with sret. The console is a 16550 UART, the same register model as the PC's COM1 port in DR301, but at a memory address the devicetree gives instead of an I/O port. The arch-neutral tests from F4-23 and the F3-18 printing code compile unchanged and pass (R2: 10 passed).

Paging uses Sv39: three levels of 512 entries, like AArch64 with a 4 KiB granule and 39-bit addresses. A difference: an entry is a leaf as soon as any of its R, W or X bits is set, at any level, and the lab's map uses only the root table: three entries of 1 GiB each. The second gigabyte is left out on purpose, so a load from 0x40000000 gives the page fault the acceptance test asks for.

Layer 3 — the engineer's depth

Entry and the state OpenSBI leaves

boot.S disables S-mode interrupts in sie, keeps a0 and a1, loads the global pointer gp (with linker relaxation off for that one instruction, since gp is not valid yet), sets the stack and stvec, clears .bss, runs the global constructors (F3-18's cxxrt.cc) and calls kmain(hartid, dtb). Every address it loads is computed with la, which with -mcmodel=medany is PC-relative (auipc plus an offset): that detail is central to the forensic lab. D4

R2 shows sstatus = 0x8000000200006000 at entry: UXL = 2 (bits 33:32: U-mode is 64-bit), FS = 3 (bits 14:13: the floating-point unit is on and its state "dirty") and SD (bit 63, summarising FS). OpenSBI left the FPU enabled. This kernel is built for the soft-float ABI lp64 with -march=rv64imac, so the compiler never emits floating-point instructions and the trap handler need not save floating-point registers. After a trap, sstatus reads 0x8000000200006100: bit 8, SPP, says the trap came from S-mode. MIDELEG 0x1666 and MEDELEG 0xf0b509 in OpenSBI's banner say which interrupts and exceptions M-mode delegates to S-mode. R2

The boot convention (S-mode, a0 = hart ID, a1 = devicetree), the CSR names and bit positions (sstatus SIE, SPP, FS, UXL, SD; scause bit 63 and codes 2, 12, 13, 15; stvec modes; satp MODE in bits 63:60 and value 8 for Sv39), the PTE bit layout and the delegation registers' meaning are recalled from "The RISC-V Instruction Set Manual, Volume II: Privileged Architecture" (D1) and the SBI specification (D2), not opened in this build. The runs show QEMU 8.2.2 and OpenSBI v1.3 behaving consistently with them; hardware was not tested.

The trap path

trapvec.S saves all 31 general registers, the interrupted stack pointer, sepc, sstatus, scause and stval into a 288-byte TrapFrame (a static_assert in trap.h keeps the C++ and assembly in step), calls trap_entry, restores sepc and sstatus (the handler may change them) and the registers, and executes sret. There is one entry for everything ("direct mode"); a "vectored" mode sends interrupts to separate entries, which F4-29 does not need. D1

To resume after an expected fault, the handler must step over the faulting instruction, and RISC-V instructions are 2 or 4 bytes long with the C (compressed) extension. The two low bits of the first halfword are 11 only for a 4-byte instruction, so trap.cc reads that halfword at sepc and advances by 4 or 2. In R2, the illegal instruction is csrw cycle, zero: stval holds its bits, 0xc0001073 (a 4-byte instruction: low bits 11; CSR number 0xc00, the read-only cycle counter). The load page fault reports stval = 0x40000000, the address, and the load's destination register keeps whatever it held before (0x80202ea8). R2

SBI calls

sbi::call puts the extension ID in a7, the function ID in a6 and arguments in a0–a2, executes ecall, and returns a0 (error) and a1 (value). Extension IDs are ASCII spelled as numbers: TIME is 0x54494D45, HSM 0x48534D, SRST 0x53525354. Base function 3, probe_extension, returns a non-zero value if an extension exists. R2: specification 1.0, implementation ID 1 (OpenSBI), implementation version 0x10003 (1.3). sbi::shutdown calls SRST with type 0 (shutdown); if the call returns, it prints the error and halts the hart: F4-29's sifive_u run shows that path. D2 R2

The legacy SBI v0.1 calls (for example console putchar, extension 0x01) are still offered by many firmwares and used by tutorials. They are deprecated in favour of named extensions; this kernel uses the UART and, as fallback, could use DBCN (debug console). The console choice is the acceptance test's "UART or SBI debug console". D2

Sv39 with gigapages

sv39::leaf builds an entry: the physical page number (pa >> 12) shifted into bits 53:10, the permission bits, A and D set, and V. Setting A (accessed) and D (dirty) in advance matters: the specification allows hardware either to set them or to raise a page fault when they are clear, and a kernel that leaves them clear may fault on its first access on some implementations. The satp value is MODE 8 in bits 63:60 and the root table's page number: R2 shows 0x8000000000080204 for a root at 0x80204000. sfence.vma before and after the write orders the table writes before the walk and flushes stale translations. D1 R2

This map is deliberately coarse: GiB 2 is readable, writable and executable as one gigapage, so W^X does not hold here as it did in F4-25. A gigapage leaf must also be aligned to 1 GiB in its physical address. The lab's step 4 asks you to replace entry 2 with a level-1 table and 2 MiB pages to restore W^X; your OS303 B3–B5 page-table code should be the code that does it, behind the same interface as on x86-64 and AArch64.

The 16550 over MMIO

uart16550.cc implements F3-18's serial.h interface for the UART the devicetree names: /chosen/stdout-path → /soc/serial@10000000, compatible ns16550a, with an optional reg-shift property that spaces registers 1 << shift bytes apart (0 on QEMU, 2 on many SoCs, which is one of the "vendor variants" F4-29's board section warns about). The register numbers are the PC's: data at 0, interrupt enable at 1, line status at 5. On the PC, DR301 wrote them with outb; here they are bytes in memory. D5 R2

How the hardware actually does it

On RISC-V boards, the boot chain usually has more stages than QEMU's: a boot ROM in the SoC, a first-stage loader (often U-Boot SPL) that sets up DRAM, then OpenSBI in M-mode, then U-Boot proper in S-mode, which loads the kernel and the devicetree and jumps to the kernel in S-mode. Each stage passes the hart ID and the devicetree onwards. PMP is a hardware unit in each hart that checks every S- and U-mode access against address ranges configured by M-mode; it is what makes "S/U: ()" in R2's region list a real restriction rather than a convention. D3 R2

Not verified — check before relying on this

The board boot chain (boot ROM, U-Boot SPL, OpenSBI, U-Boot, kernel) is recalled and varies by board; untested on hardware in this build. Whether a given core sets the A and D bits in hardware or faults when they are clear is implementation-specific (recalled); QEMU 8.2.2 did not fault with them set, and the lab did not test them clear. F4-29 covers the board case (VisionFive 2) as an untested description and uses QEMU's sifive_u as a stand-in.

Worked example

Task. From R2 alone, decode the two trap reports and the satp value, and check that the page-fault address falls into the unmapped entry.

Illegal instruction. scause 0x2: bit 63 clear (an exception), code 2 = illegal instruction. stval 0xc0001073: opcode bits 6:0 = 0x73 (SYSTEM), funct3 bits 14:12 = 1 (CSRRW), rd = 0, rs1 = 0, CSR bits 31:20 = 0xc00 (cycle). Writing a read-only CSR is illegal. sepc 0x80200a28 is inside kmain (which starts at 0x802004c6, R1). R1 R2

Page fault. scause 0xd = 13, load page fault; stval 0x40000000. VPN[2] = 0x40000000 >> 30 = 1; root entry 1 is zero (V clear), so the walk fails at the root and the fault is a page fault, not an access fault (which would come from PMP or a bus error). R2

satp. 0x8000000000080204: bits 63:60 = 8 (Sv39), ASID bits 59:44 = 0, PPN = 0x80204 → root table at 0x80204000, which is inside .bss (R1: .bss at 0x80203780, size 0x1900, so up to 0x80205080), as expected for g_root. R1

Where the analogy breaks


    

  • The caretaker is not a different person. OpenSBI runs on the same harts as the kernel, in a different mode; each ecall is the same hart switching to M-mode and back. There is no separate processor (unlike the Pi's GPU firmware in F4-27).
    • 

  • The hatch is not only for requests. Some traps go to M-mode first even when the kernel caused them (those not delegated), and OpenSBI forwards them to the kernel's stvec. The forensic lab's access faults travel this way.
    • 

  • The locked office is enforced per access. PMP checks every access, including instruction fetches; "the principal may not enter" is a hardware check, not a rule followed by good behaviour.
    • 




Common mistakes and debugging


    

  • Building with the soft-float ABI on a distribution that ships only hard-float headers. While writing this lab the Ubuntu RISC-V cross compiler's C++ headers pulled in glibc's gnu/stubs-lp64.h, which exists only for the hard-float ABI: -mabi=lp64 failed to compile anything that includes <cstdint>. The lab ships an empty include/gnu/stubs-lp64.h (it lists only C-library functions a freestanding kernel never calls). Evidence (R3):

    • 

  • Linking at 0x80000000. The forensic lab. M-mode-only tutorials put the kernel at the start of RAM; with OpenSBI, the kernel is loaded at 0x80200000.
    • 

  • Assuming 4-byte instructions when skipping a fault. With the C extension, sepc + 4 lands in the middle of the next instruction after a 2-byte one. Fix: trap.cc line 88.
    • 

  • Leaving A and D clear in leaf entries. Some implementations fault on first access. Fix: set them, or handle the faults.
    • 

  • Forgetting sfence.vma. Stale translations stay in use. Fix: before and after changing satp, and after changing a valid entry.
    • 

  • Reading mhartid in S-mode. It is an M-mode CSR: illegal instruction. Fix: use the a0 OpenSBI passes, and keep it per hart.
    • 

  • Using the floating-point registers in the kernel by accident. OpenSBI leaves FS on (R2), so floating-point instructions work and silently corrupt user state later. Fix: the soft-float ABI, or clear FS and enable it only around saved regions.
    •

Mini-project


Position-independent RISC-V kernel. Make the D5 kernel run correctly wherever it is loaded: link it as position-independent (-fPIE, -static-pie or equivalent), apply its own relocations at entry before the first absolute address is used, and prove it by loading the same binary at 0x80200000 and 0x80400000 (QEMU's -device loader, with OpenSBI's next address changed through a firmware with that option, or with a small stub).

Summary


    

  • RISC-V has M, S and U modes; OpenSBI stays in M-mode, protects itself with PMP and enters the kernel at 0x80200000 in S-mode with a0 = hart ID and a1 = devicetree.
    • 

  • SBI ecalls (extension in a7, function in a6) give the kernel timer, IPI, hart state, reset and console services; probe before use.
    • 

  • One trap vector; scause, sepc, stval say what happened; skip 2 or 4 bytes after an expected fault.
    • 

  • Sv39: three levels, leaves at any level, A and D bits, satp MODE 8, sfence.vma.
    • 

  • The arch-neutral code ran unchanged on a third architecture.
    • 

  • A kernel linked for one address and loaded at another runs its PC-relative code and fails at its first absolute address.

  6. GiB 2 is one leaf with R, W and X, so code is writable and data executable. Use a level-1 table for that gigabyte (and level-0 tables or 2 MiB leaves) with R-X for text, R-- for read-only data and RW- for the rest, with page-aligned sections as in F4-25.

  7. Registers are 4 bytes apart (1 << 2), and must be accessed as 32-bit words (reg-io-width 4): reg() must use volatile uint32_t accesses at base + (r << 2). The DesignWare UART also has extra registers and a "busy" condition when writing line control (vendor variant; check its documentation).

  8. scause 3 (breakpoint), stval probably 0 or the sepc (implementation choice; run it). The test checks for cause 2, so it reports "NOT seen" for the illegal-instruction test, and D5 fails, unless you change the expected cause. With the C extension the assembler may emit c.ebreak (2 bytes), which the skip logic handles.
    9. 

  9. The firmware's code (0x80000000–0x8003ffff) is readable and executable in M-mode and not accessible at all from S-mode or U-mode: any kernel access there is an access fault enforced by PMP.

Forensic lab answer key


    

  1. Linked at 0x80000000 (the diff and readelf: entry 0x80000000). OpenSBI jumps to 0x80200000 ("Domain0 Next Address"), where QEMU loaded the image. Every link-time absolute address in the kernel is 0x200000 too low.
    2. 

  2. OpenSBI's own, in M-mode during its initialisation (they lie in its region 0x80000000–0x8003ffff and occur before the jump): it probes CSRs and handles the resulting illegal-instruction traps. Not a problem; they appear in every run with -d int. A good investigator recognises and sets them aside.
    3. 

  3. Cause 1, instruction access fault, at 0x80002408, with epc = tval = 0x80002408: the hart jumped to that address. addr2line on the link-time image names _GLOBAL__sub_I__Z17run_neutral_testsRK10NeutralEnv, the static constructor of neutral_tests.cc. run_global_constructors read the pointer from .init_array (__init_array_start 0x80003770), which holds the link-time address; at run time that address is inside OpenSBI's PMP-protected region, so fetching from it faults.
    4. 

  4. The epc 0x80202722 is a run-time address; the code there is the instruction the linker placed at 0x80002722, so subtracting the load offset gives the link-time address addr2line understands: kvformat in kformat.h:100. It is reading tval 0x80002ca8 and 0x80002d08, link-time addresses of format strings in .rodata, again inside the firmware's protected region: load access faults (cause 5). The trap handler's own kprintf faults the same way, so each report causes another fault and nothing is ever printed.
    5. 

  5. boot.S computes every address with la, which under -mcmodel=medany is PC-relative: the stack, stvec, .bss and the call targets are all correct relative to where the code actually is. Only addresses stored as data (the constructor list, pointers to strings, jump tables) are absolute, and the first of those is used when the constructors run.
    6. 

  6. Link at 0x80200000 (or read the load address from the platform and use a position-independent kernel, the mini-project). Check: at entry, compare the run-time address of _start (from auipc) with its link-time value (a stored absolute word) and, if they differ, print through SBI DBCN or the legacy putchar, which need no absolute addresses, and stop. Wrong answers: "OpenSBI is broken" (its banner and region list are normal), "the UART address is wrong" (the console is never reached; the faults come first).
