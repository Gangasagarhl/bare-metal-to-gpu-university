Story hook

On her first morning in the new building, Ms Okafor finds that it is organised differently from the old one. The old school had two kinds of room: student areas and staff-only rooms. The new one has floors. Pupils stay on the ground floor. The principal's office is on the first floor. The second floor belongs to the "real principal above", the person who runs a school inside the school when there is one. On the top floor is the caretaker's office, which stays staffed all day: when Ms Okafor wants the heating switched off at night, she does not touch the boiler herself; she sends a form up to the caretaker.

Some mornings the caretaker lets her in on the second floor instead of the first, because nobody else is using it. Then her first job is to walk down one flight of stairs and settle into her own office, or every visitor who rings will be sent to an empty room. This chapter is that first morning on a 64-bit Arm CPU. You will write the arch layer of milestone D1: the image header that QEMU recognises, the walk down from EL2 to EL1, a stack, a cleared .bss, the C++ constructors, a console found through the devicetree, and a vector table that turns every fault into a decoded report. The arch-neutral code from OS303 will run on it without a single edit.

What you will be able to do

  • Explain AArch64's exception levels EL0–EL3 and which one a kernel uses, and drop from EL2 to EL1 at boot.
  • Build a kernel image with an arm64 Image header, load it with QEMU's -kernel, and read the devicetree address from x0.
  • Write an exception vector table (16 entries of 128 bytes, 2 KiB aligned) that saves a full register frame.
  • Decode ESR_EL1 (exception class, instruction length, syndrome, fault status) and FAR_EL1 into a readable report.
  • Call firmware through PSCI with the conduit the devicetree names, and power the machine off cleanly.
  • Diagnose a kernel that runs but cannot handle its own faults, from QEMU's interrupt log.
Jargon box
Exception level (EL)
Simple words: AArch64's privilege levels, numbered 0 to 3; a higher number has more control. Analogy: the floors of the building: pupils, principal, the real principal above, the caretaker's office. Precise: EL0 runs applications, EL1 an operating-system kernel, EL2 a hypervisor, EL3 the secure monitor (firmware); exceptions are taken to the same or a higher level, and eret returns to the same or a lower one. D1 D2
System register
Simple words: a named CPU control or status register, read with mrs and written with msr. Analogy: a switch or a dial on the wall of a staff room. Precise: registers such as SCTLR_EL1, VBAR_EL1, ESR_EL1, whose suffix names the lowest exception level allowed to access them. D1
Vector table (AArch64)
Simple words: the block of code the CPU jumps into when an exception happens. Analogy: a row of sixteen doorbells, one per kind of caller and situation. Precise: 16 entries of 0x80 bytes at the address in VBAR_ELx, which must be 2 KiB aligned: four groups (current EL with SP_EL0, current EL with SP_ELx, lower EL in AArch64, lower EL in AArch32), each with synchronous, IRQ, FIQ and SError entries. D1
ESR (exception syndrome register)
Simple words: the register that says why an exception happened. Analogy: the note the doorbell system writes: who rang and why. Precise: ESR_EL1: exception class in bits 31:26, instruction length in bit 25, an instruction-specific syndrome in bits 24:0; for aborts the low six bits are a fault status code. FAR_EL1 holds the faulting address and ELR_EL1 the return address. D1
PSCI
Simple words: a standard set of firmware calls for switching CPUs and the whole machine on and off. Analogy: the forms sent up to the caretaker's office. Precise: the Arm Power State Coordination Interface: function IDs such as PSCI_VERSION, CPU_ON, SYSTEM_OFF, invoked with hvc or smc under the SMC Calling Convention; the devicetree's /psci node names the instruction. D6 D7
arm64 Image header
Simple words: 64 bytes at the start of a kernel file that tell a loader how to place it. Analogy: the label on a parcel: which way up, how heavy, where to put it. Precise: a branch instruction, a second code word, text_offset, image_size, flags, reserved words and the magic "ARM\x64" at offset 56, as described by the Linux arm64 booting document. D4
Outline atomics
Simple words: a compiler option that turns atomic operations into calls to helper functions. Analogy: sending every delicate job to a specialist instead of doing it in the room. Precise: GCC's default for AArch64 Linux targets: each atomic becomes a call to a __aarch64_* helper that picks LSE instructions or exclusive load/store pairs at run time; a freestanding kernel has no such helpers and builds with -mno-outline-atomics. D9 R4

Layer 1 — the kid explanation

Analogy

The new building has floors: pupils (EL0), the principal (EL1, our kernel), the real principal above who runs a school inside the school (EL2, a hypervisor), and the caretaker's office at the top (EL3, firmware). The principal works on the first floor. If the caretaker lets her in on the second floor, she walks down first. On her floor she puts up a board of sixteen doorbells, one for each kind of caller and situation, and next to each doorbell a note-taker who writes down who rang and why. When she wants the building switched off at night, she sends a form up to the caretaker's office instead of pulling the main switch herself.

Mapping: floors = exception levels; principal = operating-system kernel at EL1; real principal above = hypervisor at EL2; caretaker = firmware at EL3; doorbell board = vector table; the note = the syndrome register; form to the caretaker = a PSCI call.

Layer 2 — the student explanation

An AArch64 CPU runs at one of four exception levels. Applications run at EL0, an operating-system kernel at EL1, a hypervisor at EL2 and the secure monitor (firmware) at EL3. An exception (a fault, an interrupt, a system call) moves the CPU to the same or a higher level; the eret instruction returns to the same or a lower one, restoring the state saved in SPSR_ELx and jumping to ELR_ELx. Each level has its own copies of the registers it needs: its own stack pointer, its own vector base, its own syndrome register. D1 D2

QEMU's virt machine can start a kernel at EL1 or, with virtualization=on, at EL2. The lab runs both. A kernel that is not a hypervisor should run at EL1: at EL2 its exceptions would go to EL2's vector table, its system registers would be the EL2 ones, and the timer and interrupt set-up of later chapters would differ. So boot.S reads CurrentEL and, if it finds EL2, configures EL2 only as far as needed to let EL1 run in AArch64 with access to the physical timer, and returns into EL1 with eret. The output of both runs says "running at EL1"; the second also says "entered at EL2". R2 R3

The rest of the start-up is the same list as on the PC in F3-18, in a different instruction set: set a stack, clear .bss, run the global constructors (with F3-18's own cxxrt.cc), call kmain. Two things are new. First, QEMU recognises the kernel file as an arm64 Image because of a 64-byte header at its start, and then hands the devicetree's address in x0; boot.S keeps it in a callee-saved register until kmain receives it. Second, before any C++ runs, VBAR_EL1 is pointed at the vector table so that even the earliest fault produces a report instead of a jump into nowhere. D4 R1

kmain then does what F4-23 planned: it parses the devicetree, follows /chosen/stdout-path to the PL011 UART, and from then on F3-18's kprintf works, because the PL011 driver implements the same three-function serial.h interface as the PC's COM1 driver. It prints the entry level, the CPU's identification register, the vector base and the MMU state, asks the firmware for its PSCI version, runs the ten neutral tests, provokes the two faults the milestone asks for, and powers off through PSCI. D8 R2

Layer 3 — the engineer's depth

The Image header and the load address

The first 64 bytes of k_d1.bin are the header of Listing 1. Word 0 is a branch over the header (the build record shows 10 00 00 14, the encoding of b with an offset of 0x10 words, 64 bytes). The 64-bit text_offset is 0x80000; the 64-bit image_size is computed by the linker (0x26000 in R1: the file plus .bss plus the stacks); the flags 0x2 declare a little-endian kernel with 4 KiB pages; the magic at offset 56 reads 41 52 4d 64, "ARMd". QEMU loads the image at RAM base + text_offset. The linker script is therefore based at 0x40080000: the RAM base of virt (F4-23 row 3) plus 0x80000. The kernel runs with the MMU off in this chapter, so it must run at the address it was linked for. D4 R1

Not verified — check before relying on this

The meaning of the header fields (text_offset, image_size, the flag bits for endianness and page size), the requirement that the DTB be passed in x0 with x1–x3 zero, and the requirement that the MMU and data cache be off at entry come from the Linux document "Booting AArch64 Linux" as recalled, not opened in this build. What is verified: QEMU 8.2.2 accepted this header, loaded the image at 0x40080000, and passed 0x48000000 in x0 (R2). A board's firmware or U-Boot may follow the same document; that is untested here (F4-27).

Leaving EL2

Dropping from EL2 to EL1 is an exception return: write the target state into SPSR_EL2, the target address into ELR_EL2, execute eret. Three settings make the target usable. HCR_EL2.RW (bit 31) selects AArch64 for EL1; without it, EL1 would be AArch32. CNTHCTL_EL2 bits 0 and 1 let EL1 read the physical counter and use the physical timer without trapping to EL2 (F4-25 needs both). CNTVOFF_EL2 is cleared so the virtual counter equals the physical one. The SPSR value 0x3c5 means: mode EL1h (EL1 using its own stack pointer, value 0b0101) with D, A, I and F masked (bits 9 to 6). D1

Not verified — check before relying on this

The bit positions of HCR_EL2.RW, CNTHCTL_EL2.EL1PCTEN and EL1PCEN, the SPSR mode encoding 0b0101 for EL1h and the DAIF bit positions are recalled from the Arm Architecture Reference Manual (D1), not opened in this build. The run with virtualization=on (R3) shows the drop working under QEMU (entered at EL2, running at EL1, D1 ok), and F4-25 shows the EL1 physical timer working after it; neither proves that every other EL2 setting a real board's firmware leaves behind is harmless. A production kernel also sets SCTLR_EL1 to a known value before using it.

The vector table and the frame

The CPU does not save general registers on an exception: it saves the return address in ELR_EL1, the processor state in SPSR_EL1, the syndrome in ESR_EL1 and, for aborts, the address in FAR_EL1, then jumps to VBAR_EL1 plus the entry's offset. The offset is chosen by source and kind: a synchronous exception at EL1 while using SP_EL1 enters at 0x200, an IRQ in the same situation at 0x280, a synchronous exception from EL0 (a system call, later) at 0x400. Each entry has 32 instructions of room; vectors.S uses four of them: reserve a 288-byte frame, save x0 and x1, load the entry index, branch to common code. The common code saves x2–x30 and the four system registers, calls the C++ handler with the frame and the index, restores (the handler may change ELR and SPSR), and returns with eret. The frame's layout is shared by assembly and C++ and protected by a static_assert on its size. D1 D2

Decoding the syndrome

ESR_EL1 answers "what happened" in three fields: the exception class (bits 31:26), the instruction length bit (25: 1 for a 32-bit instruction) and the instruction-specific syndrome (24:0). For data and instruction aborts the syndrome's low six bits are the fault status code, and for data aborts bit 6 says whether the access was a write. R2's first fault reads 0x96000010: class 0x25 (data abort at the same EL), length bit 1, syndrome 0x10, status 0x10 (synchronous external abort), a read, at FAR 0x50000000. The second reads 0x2000000: class 0 ("unknown reason", the class the architecture uses for an undefined instruction) with the length bit set. D1 R2

Why an external abort and not a translation fault? The MMU is off. Every address is used as a physical address, and 0x50000000 is the first byte after the 256 MiB of RAM that the devicetree reported. Nothing answers there, so the memory system reports an external abort. In F4-25, with the MMU on, the same kind of mistake becomes a translation fault with a level number, which is more useful; the D1 test asks only for "a data abort on an unmapped address" and a decoded report. D8 R2

The exception-class values in trap.cc (0x00 unknown, 0x15 SVC, 0x16 HVC, 0x17 SMC, 0x20/0x21 instruction abort, 0x24/0x25 data abort, 0x3c BRK, and the others in the table) and the fault-status ranges (0x04–0x07 translation, 0x09–0x0b access flag, 0x0d–0x0f permission, 0x10 synchronous external abort, 0x21 alignment) are recalled from the Arm Architecture Reference Manual's ESR_EL1 description, not opened in this build. The runs confirm the values QEMU produced for the cases exercised in this course: 0x25 with 0x10 (R2), 0x00 for UDF (R2), 0x17 for SMC (R6), and in F4-25 0x25 with 0x05 and 0x0f and 0x21 with 0x0f.

Firmware calls: PSCI and the conduit

PSCI defines firmware functions by 32-bit IDs; the SMC Calling Convention defines how to call them: function ID in x0, arguments in x1–x3, result in x0, and either hvc #0 (handled at EL2) or smc #0 (handled at EL3). Which one is right depends on where the firmware lives, and the devicetree says so in /psci's method. On QEMU virt with the default options it is hvc; with virtualization=on, EL2 belongs to the guest, so QEMU tells the kernel to use smc, and the run's log line changes accordingly. Both times QEMU itself implements PSCI 1.1 and answers SYSTEM_OFF by ending the emulation, which is why every D1 run ends with exit code 0. D6 D7 R2 R3

Not verified — check before relying on this

The function IDs in psci.h (PSCI_VERSION 0x84000000, CPU_ON 0xC4000003 in the 64-bit calling convention, AFFINITY_INFO 0xC4000004, SYSTEM_OFF 0x84000008, SYSTEM_RESET 0x84000009) and the register convention are recalled from the PSCI specification and the SMC Calling Convention (D6, D7). The runs show QEMU accepting PSCI_VERSION and SYSTEM_OFF (this chapter) and CPU_ON and AFFINITY_INFO (F4-26).

The build: what the compiler must be told

The kernel is compiled with the Linux-targeted cross compiler aarch64-linux-gnu-g++ plus freestanding flags. Three AArch64-specific flags matter. -mgeneral-regs-only keeps the compiler away from the floating-point and SIMD registers, which the kernel does not save in its trap frame. -mstrict-align forbids unaligned accesses, which fault on device memory and, with the MMU off, on all memory (all data accesses are treated as device accesses then). -mno-outline-atomics makes the compiler emit atomic instructions inline: without it, the arch-neutral test's std::atomic operations become calls to helper functions such as __aarch64_ldadd8_relax that live in the compiler's runtime library, which a kernel does not link. R4 is that failure, kept as evidence. All three flags live in the build helper, not in the code. D9 R4

Not verified — check before relying on this

That outline atomics are the default for this GCC's AArch64 Linux target, and that all data accesses with the MMU off are treated as Device memory (so unaligned accesses fault), are recalled from the GCC manual and the Arm ARM (D9, D1). R4 proves the first in effect for this build's toolchain. An early test in this build showed that QEMU did not fault on a misaligned load with the MMU off, so the second statement was not demonstrated here; -mstrict-align is kept because real hardware is what matters.

How the hardware actually does it

On QEMU with TCG every instruction of the guest is translated into host code. An exception is QEMU's code updating the emulated ELR, SPSR, ESR and FAR and changing the emulated PC to VBAR plus the offset; the -d int option prints each of these steps, and the forensic lab reads such a log. PSCI is not running as guest firmware at all: QEMU recognises the hvc or smc with a PSCI function ID and performs the action itself ("handled as PSCI call" in R6). The PL011 is QEMU's model of Arm's UART; it needs no baud-rate set-up, which is why serial::init is empty here and F4-27 adds the set-up a real board needs. D10 R6

The CPU model is a Cortex-A57 (-cpu cortex-a57): MIDR_EL1 reads 0x411fd070, implementer 0x41 (Arm) and part number 0xd07. On real hardware that register is how firmware and kernels tell cores apart for errata work; this course's kernels print it and, in F4-27, use it to pick a board description when no devicetree is passed. R2

Not verified — check before relying on this

On real Arm hardware, the exception level at kernel entry depends on the firmware: Trusted Firmware-A, U-Boot and board firmware may start a kernel at EL2 (common, so that a hypervisor can be used) or at EL1. Untested on hardware in this build. The EL2 drop in boot.S was exercised only under QEMU (R3).

Worked example

Task. Decode R2's two exception reports by hand and check the kernel's decoding.

Data abort. ESR = 0x96000010. In binary the top six bits of the 32-bit value 0x96000010 are 1001 01: 0x96 = 1001 0110, so bits 31:26 are 100101 = 0x25 (data abort, same EL). Bit 25 is the next bit, 1: a 32-bit instruction. Bits 24:0 are 0x0000010 = 0x10. The fault status is ISS bits 5:0 = 0x10 (synchronous external abort); bit 6 = 0, a read. FAR = 0x50000000 = 0x40000000 + 0x10000000, the end of RAM from R2's devicetree line ("memory 0x40000000, 256 MiB"). ELR = 0x40082368; the forensic run's addr2line places the same address in kmain, d1_main.cc line 71, which is uint32_t v = *hole;. R2 R6

Undefined instruction. ESR = 0x2000000: bits 31:26 are 0, class 0x00; bit 25 is 1. ELR = 0x400823c4, the udf #0. The handler adds 4 to ELR (every A64 instruction is 4 bytes) and returns to the next instruction; the kernel prints "undefined instruction reported and decoded". R2

The vector offset. Both reports say "vector entry 4, offset 0x200": synchronous (column 0) from the current EL using SP_ELx (row 1), 1 × 0x200 + 0 × 0x80 = 0x200. In the forensic run, the same fault enters at physical address 0x200, which is the clue to that lab. R6

The SPSR. SPSR_EL1 = 0x600003c5: the low bits 0x3c5 are the state the kernel itself set at boot (EL1h, DAIF masked); bits 30 and 29 (0x6 in the top nibble) are the Z and C condition flags of the comparison that ran immediately before the fault. D1

Where the analogy breaks


    

  • Floors are not places. An exception level is a state of the CPU, not a part of memory: the same instructions at the same addresses run at EL1 or EL2, and what changes is which registers and which vector table they use. A building's floors are physically separate.
    • 

  • The caretaker is not always upstairs. In the analogy the caretaker's office is at the top (EL3). On QEMU virt with default options the firmware answers hvc, a call to EL2, and in this build there is no firmware code at all: QEMU performs PSCI itself. Where the firmware lives is a property of the machine, which is why the devicetree names the conduit.
    • 

  • Doorbells do not write notes by themselves. The CPU records the syndrome in ESR, but it saves none of the general registers; the kernel's entry code must save them before using any of them. A doorbell board that kept every visitor's luggage would be a different design.
    • 




Common mistakes and debugging


    

  • Outline atomics. Link errors for __aarch64_ldadd8_relax and __aarch64_cas8_acq_rel (R4, below). Fix: -mno-outline-atomics.

    • 

  • Staying at EL2. Everything prints until the first fault, then silence (the forensic lab). Check: print CurrentEL before and after the drop.
    • 

  • Vector table not 2 KiB aligned. The CPU ignores the low bits of VBAR, so exceptions land in the wrong code. Check: nm shows the table's address; the low 11 bits must be zero.
    • 

  • Forgetting isb after writing VBAR_EL1 or other control registers. The write may not take effect for the instructions already in flight. Fix: isb after each such write that the next instructions depend on.
    • 

  • Linking at the wrong address. With the MMU off, a kernel linked at 0x40000000 but loaded at 0x40080000 reads its own data from the wrong place (F4-28's forensic lab shows the RISC-V version). Fix: base = RAM base + text_offset; check the readelf entry point in the build record.
    • 

  • Hard-coding hvc. Works with default QEMU options; with virtualization=on the call goes to the kernel's own EL2 and is lost. Fix: read /psci's method (R3 shows the change).
    • 

  • Skipping the faulting instruction on an instruction abort. For a failed fetch there is no instruction to skip; adding 4 to ELR jumps further into the bad region. Fix: return to the caller (trap.cc line 108), or treat it as fatal.
    • 




Transition box

Where you came from: F3-18's B1 kernel on x86-64 (multiboot or UEFI entry, GDT, IDT, COM1) and F4-23's checklist and devicetree parser. What carries over: the start-up contract (stack, .bss, constructors, kmain), kprintf, panic, the C++ runtime, the neutral tests, all unchanged (the SHA-256 sums in R1 match those of F4-23 and F4-28); the idea of a trap frame and a decoder from OS302. What changes: privilege is four exception levels instead of rings; there is no GDT and no IDT, only one vector base register and a fixed table layout; the cause of an exception is in one syndrome register instead of a vector number plus an error code; firmware is called through PSCI; the console is found in the devicetree. What comes next: F4-25 turns on the MMU with an identity map and W^X, and adds the GICv3 and the generic timer (milestone D2).

This lab runs only in QEMU. Mini-project


A complete AArch64 trap report. Extend trap.cc into the report your later kernels will rely on: all 31 registers in a compact table, the decoded SPSR (mode, DAIF, condition flags), a symbolic name for ELR from a small symbol table generated at build time (nm output turned into a sorted array), a backtrace by walking frame pointers (the build keeps -fno-omit-frame-pointer), and the instruction word at ELR. Test it with five deliberate faults: data abort, instruction abort (branch to a non-executable address once F4-25's MMU is on), UDF, BRK, and SP alignment fault.


Rubric (10 points): all five faults reported and decoded correctly (4); symbolic ELR and backtrace correct for nested calls (3); report fits on one 80-column screen (1); no change to arch-neutral files (2).



Summary


    

  • AArch64 has four exception levels; a kernel belongs at EL1 and drops there from EL2 with an exception return.
    • 

  • QEMU loads an arm64 Image at RAM base + text_offset and passes the DTB in x0; the linker base must match because the MMU is off.
    • 

  • The vector table has 16 entries of 0x80 bytes; the CPU saves only ELR, SPSR, ESR and FAR, and the entry code saves the rest.
    • 

  • ESR's class, length bit and syndrome (with the fault status for aborts) plus FAR decode every fault of milestone D1.
    • 

  • Firmware is called through PSCI with the conduit the devicetree names; SYSTEM_OFF ends a QEMU run cleanly.
    • 

  • The arch-neutral code ran unchanged; the only build-level surprise was outline atomics.
    •

Answers to Check yourself


    

  1. Applications EL0, kernels EL1, hypervisors EL2, the secure monitor EL3.
    2. 

  2. x0 is an argument and result register under the procedure call standard; any call (here run_global_constructors) may overwrite it. x19 is callee-saved, so it survives.
    3. 

  3. From EL0 in AArch64: the "lower EL, AArch64" group, synchronous: 0x400. IRQ at EL1 with SP_EL1: 0x280.
    4. 

  4. 0x96000046: class 0x25 (data abort, same EL), length bit 1, ISS 0x46: bit 6 set = write, fault status 0x06 = translation fault (level 2 in the encoding's level field, which F4-25 prints).
    5. 

  5. The kernel powers the machine off through PSCI SYSTEM_OFF, and QEMU exits normally with 0 whether the tests passed or not. The pass condition is the line "D1 ok", which run.sh checks.
    6. 

  6. The source is the same for every CPU; how the compiler lowers atomics is a property of the target and the environment (no runtime library in a kernel). Putting the flag in the build's AArch64 section keeps the shared code free of target details and applies the decision to every file at once.
    7. 

  7. boot.S assumes it runs at its link address with the MMU off. With the MMU on, the firmware's mapping decides what addresses mean; the kernel would need to turn the MMU off first (with cache maintenance) or be position-independent, and the Linux booting document's contract (MMU off at entry) would not hold, so it would also be worth reporting as a firmware problem.
    8. 

  8. QEMU loads the image according to its header (RAM base + text_offset), at 0x40080000, but the code expects to be at 0x40000000; absolute addresses (the literal pool's __stack_top, vector_table, string addresses) point 512 KiB too low. A trial run during this build (not kept in the lab folder; repeat it yourself) printed nothing at all and was stopped by a 10-second time limit. The point is the habit: predict, run, compare.
    9. 

  9. "PSCI through hvc: version 1.1" in R2 and "PSCI through smc: version 1.1" in R3. With virtualization=on the guest owns EL2, so the firmware's PSCI must be reached at EL3 through smc, and QEMU's devicetree says so.
    10. 



Forensic lab answer key


    

  1. R5's second line: "D1: entered at EL2, running at EL2". Everything else matches R3 until the first fault.
    2. 

  2. From EL2 to EL2 ("...from EL2 to EL2"), with ESR 0x96000010 and FAR 0x50000000, to PC 0x200. The faulting ELR 0x40082368 is d1_main.cc line 71, the deliberate read.
    3. 

  3. The kernel set VBAR_EL1. An exception taken at EL2 uses VBAR_EL2, which nobody set; it holds 0 here, so the synchronous-current-EL-SP_ELx entry is at 0 + 0x200.
    4. 

  4. Physical address 0 on virt is the start of the flash, empty in this run: the monitor shows the word 0x00000000, which is not a valid A64 instruction. Each attempt raises an undefined-instruction exception, taken again to EL2 at 0x200: an endless loop with no output (R6 shows the repeated entries).
    5. 

  5. Nothing before the fault depended on the exception level: the console, the devicetree, the neutral tests and even PSCI (now through smc, from EL2 to EL3, "handled as PSCI call") work at EL2. Only exception handling needs the right vector base.
    6. 

  6. Restore the EL2-to-EL1 drop (the fault was injected by compiling boot.S with -DFORENSIC_STAY_AT_EL2). Prevention: kmain should refuse to continue if current_el() is not 1 ("running at EL2: unsupported"), and CI should boot both with and without virtualization=on. Wrong answers: "QEMU hangs on reads past RAM" (R3 shows the same read reported correctly at EL1); "the vector table is misaligned" (it is at 0x40080800 and works in R3).
    7.
