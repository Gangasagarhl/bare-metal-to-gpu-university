Story hook

For three chapters the kernel has lived in a school built to a standard plan: QEMU's virt machine, whose caretaker answers PSCI calls, whose doorbell panel is a GICv3, and whose building plan uses the same addresses the CPU uses. Now it moves into a real, older building. The caretaker here is a separate processor that starts first, reads a text file of settings, loads the kernel from an SD card and leaves the other teachers waiting in their rooms, each watching a small mailbox for a page number. The building plan writes every device's address in the language of the building's original architect, and you must translate. And there is no "power off" button that the principal can press: to finish, you set the fire alarm's timer.

This chapter ports the AArch64 kernel to a Raspberry Pi: milestone D4. The build container has no Pi, so the lab runs on QEMU's raspi3b model and marks every board fact that it could not check. The lab also teaches the most important habit of real-hardware work: a setup you can recover from, on hardware you can afford to lose an evening on, never on a machine you depend on.

What you will be able to do

  • Describe the Raspberry Pi boot chain from the GPU's boot ROM to kernel8.img at 0x80000, and what each stage leaves for the kernel.
  • Resolve a console through /aliases and translate a bus address through /soc's ranges.
  • Configure a PL011 from scratch: baud-rate divisors from the reference clock, line control, pin multiplexing.
  • Start secondary cores through a spin table, with the cache maintenance it needs.
  • Prepare a recovery-friendly boot setup for a board and connect a serial console safely.
  • Diagnose a kernel that fails silently because it used an untranslated address.
Jargon box
Bus address and ranges
Simple words: devicetree addresses can be written in a bus's own numbering; ranges says how to turn them into the CPU's addresses. Analogy: room numbers in the original architect's numbering, with a conversion table at the start of each wing. Precise: a node's reg is in its parent bus's address space; the parent's ranges = <child-base parent-base size> triples map it upwards; an empty ranges means identical, a missing one means not translatable. D1
Alias (devicetree)
Simple words: a short name for a node's path. Analogy: "the main office" instead of "building 2, floor 1, room 7". Precise: a property of /aliases whose value is a full path; /chosen/stdout-path may name an alias, optionally followed by ":" and options such as "115200n8". D1
Spin table
Simple words: a way to start the other cores: they wait, watching a memory location, until the kernel writes an address there. Analogy: each waiting teacher watches a mailbox; when a page number appears, they go. Precise: devicetree enable-method = "spin-table" with a cpu-release-addr per CPU; the core waits with wfe, reads the 64-bit slot, and branches to it when it becomes non-zero; the kernel writes the entry, cleans the line to memory, and sends sev. D2
Boot ROM, firmware, config.txt (Raspberry Pi)
Simple words: the chain of programs that run before your kernel on a Pi. Analogy: the building's own caretaker who opens up, reads the instructions pinned to the door and lets you in. Precise: on the Pi 3 and 4 the VideoCore GPU's boot ROM starts first (from the SoC on the Pi 3, via an EEPROM bootloader on the Pi 4), loads the firmware from the SD card's FAT partition, which reads config.txt, loads the devicetree and kernel8.img, and releases the Arm cores. D3
Baud-rate divisor (PL011)
Simple words: the number the UART divides its clock by to get the bit rate. Analogy: how many ticks of the school clock make one beat of the drum. Precise: divisor = UARTCLK / (16 × baud) as a fixed-point number: integer part in IBRD, 6-bit fraction in FBRD; 48 MHz and 115200 give 26.042 → IBRD 26, FBRD 3. D4
Recovery-friendly setup
Simple words: a board arrangement in which a bad kernel can always be undone. Analogy: keeping the old key until the new lock works. Precise: a dedicated SD card for experiments, a known-good card kept aside, the kernel swapped as one file, a serial console that works before the kernel does, and a power switch within reach. D3

Layer 1 — the kid explanation

Analogy

The kernel moves from a model school to a real old building. The building's own caretaker (firmware) arrives first, reads the notes pinned to the door (config.txt), puts the building plan (devicetree) on the principal's desk and lets the principal in. The other teachers wait in their rooms watching their mailboxes. The plan writes room numbers in the original architect's numbering, so the principal converts them with the table at the start of the wing. To leave at the end of the day there is no button to press: the principal sets the fire-alarm timer and the building restarts.

Mapping: caretaker = the Pi's GPU firmware; notes on the door = config.txt; building plan = devicetree (the proposed mapping "building plan on the principal's desk"); mailboxes = spin-table release addresses; architect's numbering = VideoCore bus addresses; conversion table = /soc's ranges; fire-alarm timer = the power-management watchdog.

Layer 2 — the student explanation

The kernel of F4-24 to F4-26 assumed QEMU virt: RAM at 0x40000000, a PL011 at 0x9000000 that QEMU had already set up, PSCI for starting and stopping CPUs, and a GICv3. A Raspberry Pi 3 differs in every one of these. RAM starts at address 0 and the firmware loads the kernel at 0x80000, so the linker script's base changes (R1). The UART must be configured by the kernel: baud-rate divisors, data format and the pins it uses. The other cores are started through a spin table, there is no PSCI to power off, and the interrupt controller is Broadcom's own (this chapter polls the timer; interrupts on the Pi are part of the project). R1

The devicetree a Pi's firmware passes is also written differently. It names the console through an alias: stdout-path = "serial0:115200n8", and /aliases/serial0 holds the full path. Devices sit under a /soc node whose reg values are VideoCore bus addresses (0x7e......); /soc's ranges maps them to the Arm cores' physical addresses (0x3f...... on a Pi 3). F4-23's checklist tool did not follow aliases and reports "no usable stdout-path" on this devicetree (R2, row 6): a limitation you now fix in the kernel.

The kernel also works without a devicetree: QEMU's raspi3b starts it with x0 = 0x100 when no -dtb is given. Then the kernel picks a row of a small board table by the CPU's part number in MIDR_EL1 and says so in its first line (R3). A board table is a fallback, not a design: it knows only the boards someone typed in.

Real hardware adds one more thing: you can lock yourself out. A kernel that writes the wrong register can leave a board unresponsive until power is removed; a card that you overwrite can no longer boot the system you use to fix it. The lab's setup keeps a separate SD card for experiments and a serial console that works before your kernel does.

Layer 3 — the engineer's depth

The boot chain and the image

The Arm64 image header from F4-24 is unchanged: R1 shows the branch instruction, text_offset 0x80000 at byte 8, image size 0x27000 at byte 16, flags 2 (little-endian, 4 KiB pages) and the magic "ARM\x64" at byte 0x38 (0x644d5241 read as a little-endian word). k_d4.bin, 24432 bytes, is what a Pi would load as kernel8.img. The only difference from F4-24's linker script is the base address (R1's diff). Everything else that differs between the boards lives in pi_main.cc, which is the intended shape of a port: one board file, unchanged arch files. R1

The Pi boot chain (GPU boot ROM; on the Pi 4 and 5 an EEPROM bootloader; firmware files on the FAT partition; config.txt; the default load address 0x80000 for kernel8.img; all cores started at EL2 with cores 1–3 in a spin loop on 0xd8, 0xe0, 0xe8, 0xf0; the devicetree address in x0) is recalled from the Raspberry Pi documentation (D3) and from the Linux arm64 booting document (D2), not opened in this build. QEMU's raspi3b reproduces the parts the runs show: load at 0x80000, all cores at EL2 (R3: "entered at EL2"), spin-table slots that start the cores, the devicetree in x0 (R4: at 0x8000000). Every config.txt option in the lab folder is recalled, unverified and untested.

Console: alias, ranges, divisor, pins

resolve_path (lines 58–78) cuts the stdout-path at ":" and, if the result does not start with "/", looks it up in /aliases. translate_soc (lines 82–97) walks /soc's ranges triples (one address cell and one size cell on each side in this devicetree) and maps 0x7e201000 to 0x3f201000. A general implementation walks every parent up to the root and uses each level's #address-cells and #size-cells; one level is enough for this devicetree and the comment says so. D1 R4

pl011_divisor computes 64 × UARTCLK / (16 × baud), rounded: 4 × 48000000 / 115200 = 1666.67 → 1667 = 26 × 64 + 3, so IBRD 26 and FBRD 3 (R3, R4). The real bit rate is 48000000 / (16 × (26 + 3/64)) = 115176 baud, 0.02 % slow, well within what a UART receiver tolerates. pl011_configure disables the UART, waits until it is not busy, writes the divisors, then line control (8 bits, FIFOs on) and finally enables it; line control must be written after the divisors because the PL011 latches them on that write. The reference clock comes from the devicetree's clock-frequency (48 MHz in the lab's devicetree) or the board table. D4 R4

uart_pins selects alternate function 0 for GPIO 14 and 15 in GPFSEL1 (three bits per pin, value 0b100). On a real board, firmware with enable_uart=1 may already have done this; doing it again is harmless and makes the kernel independent of that setting. D5

Not verified — check before relying on this

The BCM2837 addresses (peripherals at 0x3f000000, PL011 at +0x201000, GPIO at +0x200000, power-management watchdog at +0x100000), the GPFSEL1 layout and ALT0 value, the PL011 register offsets and bits, the 48 MHz UART clock and the watchdog password and register values are from QEMU's raspi3b model as exercised here and recalled from "BCM2835 ARM Peripherals" (D5) and the PL011 TRM (D4), not opened. QEMU accepts the PL011 timing registers without modelling them, so the divisor arithmetic is checked only by the arithmetic above. The real UART clock of a Pi 3 depends on firmware settings.

Spin table: the other cores

The devicetree's cpu nodes say enable-method = "spin-table" and give each core a cpu-release-addr. release_core (lines 219–225) writes the entry address to the slot, cleans and invalidates that cache line to memory (dc civac) because the waiting core reads with its caches off, waits for completion (dsb sy) and sends an event (sev) to wake cores sleeping in wfe. A spin-table core receives no argument, so pi_smp.S takes the core number from MPIDR_EL1.Aff0 and continues in F4-26's secondary_entry, which drops to EL1 and sets up the stack and vectors. R3 and R4: three cores report "entered at EL2, running at EL1", and the lock test with four cores counts 80000 of 80000. D2 R3

Two properties of spin tables matter for later work. They cannot be undone: there is no call to stop a core or to restart one, so CPU hot-plug and system suspend are impossible without PSCI. And the release addresses lie in RAM the kernel must not overwrite before the cores are released; a kernel that zeroes low memory early hangs its own secondary cores. Boards whose firmware offers PSCI (through Trusted Firmware-A, which can also be installed on a Pi) avoid both. D2

One observation from building this lab: in one early run of the no-devicetree kernel (while other labs loaded the host), the run stopped after "lock test" never printed; it did not reproduce in 46 later runs. The lab therefore boots each configuration five times and reports how many printed "D4 ok" (R3, R4: 5 of 5). The cause was not found; a missing barrier around the spin-table release on the boot side, a TCG scheduling effect, or the ticket lock's sensitivity to descheduled waiters (F4-26) are hypotheses, not findings. R3

No PSCI: ending the run

Without PSCI there is no SYSTEM_OFF. arch::qemu_exit here writes the power-management watchdog: a time-out of 10 ticks in PM_WDOG and a full-reset request in PM_RSTC, each with the password 0x5a in the top byte. QEMU's model resets, and -no-reboot turns a reset into a QEMU exit with code 0. So exit code 0 means "the kernel asked for a reset", not "the kernel passed": the pass condition is the line "D4 ok". That difference is the root of the forensic lab. R3 R5

The timer and the numbers the acceptance test wants

The acceptance test asks for memory size, CPU count and timer frequency "matching the board's documentation". On QEMU's raspi3b the kernel prints memory 0x0 with 960 MiB (from the devicetree), 4 cores, and CNTFRQ_EL0 62500000 Hz, and a 100 ms poll of the counter takes 6253244 counter ticks. These are QEMU's values. A real Pi 3's counter frequency is set by its firmware and differs (19.2 MHz is the value recalled, unverified); whatever the board prints is the number to compare with its documentation. That is the point of reading CNTFRQ_EL0 rather than assuming it. R3 R4

Pi 4 and Pi 5

The board table holds a Pi 4 row marked "UNVERIFIED VALUES" (peripherals at 0xfe000000), never used in the lab because QEMU 8.2.2 has no Pi 4 model. The Pi 4's BCM2711 adds a GIC-400 (a GICv2), which F4-25's kernel refuses: the mini-project of F4-25 becomes a requirement there. The Pi 5's BCM2712 moves most peripherals, including the UARTs on the GPIO header, into a separate chip (RP1) behind PCI Express, so a console on GPIO 14/15 needs a PCIe and RP1 driver first; the Pi 5 also has a separate debug UART connector. The curriculum's section 9.4 lists "BCM2711 ARM Peripherals" and "RP1 Peripherals" as the documents to read. D6 D7

Not verified — check before relying on this

Everything in the paragraph above about the Pi 4 and Pi 5 (addresses, the GIC-400, RP1 behind PCIe, the debug UART connector, the EEPROM bootloader) is recalled, not checked against D6 or D7, and untested. Before writing a Pi 4 or Pi 5 port, read the board's devicetree as the firmware passes it (dump it with F4-23's tool from your kernel) and the two documents.

How the hardware actually does it

Safety

Real-board work: protect the board, your computer and your data.

  • Use a separate microSD card for experiments. Never the card of a Pi you use for anything else, and never a machine you depend on. Keep a known-good card (the official OS image) in a labelled case for recovery.
  • The Pi's serial pins are 3.3 V logic. Use a 3.3 V USB-to-serial adapter. Never connect 5 V signals or an RS-232 port (which uses higher, negative voltages) to the GPIO pins; they can damage the SoC.
  • Connect only GND, TX and RX (adapter TX to Pi RX on GPIO 15, adapter RX to Pi TX on GPIO 14, GND to GND). Do not connect the adapter's 5 V or 3.3 V power pin to the Pi: power the Pi from its own supply.
  • Wire with the power off. Check each wire against the header's pin diagram before applying power. Use the board's official power supply.
  • When writing the card from your computer, check the device name twice: writing an image to the wrong disk destroys its contents.
  • Keep the Pi on a non-conductive surface; a loose jumper wire across the header can short a supply pin.

The pin numbers and the 3.3 V level are recalled from the Raspberry Pi documentation (D3) and must be checked against the documentation for your model before wiring.

A recovery-friendly setup. Format the experiment card with the Pi firmware files from the official distribution, your config.txt and your kernel8.img. Changing the kernel is then one file copy. Add a second kernel file and switch kernel= to try a new build while keeping the old one on the card. Start the serial terminal (115200 baud, 8N1) before powering on, so the first byte is not missed. A kernel that prints its first line before any other set-up (the lab's does, right after the console) tells you how far it got. With enable_uart=1 the firmware itself can print to the same UART on some models, which tells you whether the cable works before your kernel runs. D3

Untested on hardware

No Raspberry Pi was available for this build. Everything in the lab ran on QEMU 8.2.2's raspi3b model, which emulates a BCM2837 well enough to boot this kernel but does not emulate the firmware, the boot ROM, the SD card's FAT partition, real UART timing, real cache behaviour or power. The acceptance test of D4 requires a real board: "Serial log on real hardware shows memory size, CPU count, timer frequency matching the board's documentation." The lab is a rehearsal for it, not a substitute.

Worked example

Task. Using only the devicetree (R2, R6's dump) find the Arm physical address of the watchdog, and compute the PL011 divisors for 921600 baud at 48 MHz. Then predict what the forensic build reads when it computes the GPIO block's address.

Watchdog. watchdog@7e100000 has reg 0x7e100000. /soc's ranges: child 0x7e000000, parent 0x3f000000, size 0x1000000. 0x7e100000 − 0x7e000000 = 0x100000 < 0x1000000, so the address is 0x3f000000 + 0x100000 = 0x3f100000. R3 and R4 print "watchdog reset at 0x3f100000". R4

921600 baud. 4 × 48000000 / 921600 = 208.33 → 208 = 3 × 64 + 16: IBRD 3, FBRD 16. Actual rate 48000000 / (16 × (3 + 16/64)) = 923077 baud, 0.16 % fast: acceptable, but the error grows as the divisor shrinks, which is why high rates need a suitable reference clock.

Forensic GPIO address. The forensic build stores the untranslated UART address 0x7e201000. kmain derives the peripheral base by clearing the low 24 bits: 0x7e000000. uart_pins then reads 0x7e000000 + 0x200000 + 4 = 0x7e200004. Nothing is mapped there for the Arm cores (RAM ends at 0x3c000000, peripherals are at 0x3f000000), so the read is a data abort with FAR 0x7e200004: exactly R6. R6

Where the analogy breaks


    

  • The caretaker is a different kind of worker. On a Pi the "caretaker" is a separate processor (the VideoCore GPU) with its own firmware, not a privileged mode of the same CPUs like EL3. It keeps running after the kernel starts and owns parts of the hardware (clocks, power) that the kernel reaches only through a mailbox interface.
    • 

  • The architect's numbering is not old, it is another bus. The analogy suggests history; the reality is that the VideoCore and the Arm cores see the same peripherals at different addresses at the same time, and DMA engines use the bus addresses. A driver that programs DMA must translate in the other direction.
    • 

  • The fire-alarm timer resets everything. A watchdog reset is not a polite shutdown: no file system is synced, no device is told. In QEMU it ends the run; on a board it reboots.
    • 




Common mistakes and debugging


    

  • Using reg as a physical address. The forensic lab. Every address under a bus node needs its parents' ranges.
    • 

  • Treating exit code 0 as a pass. On this board 0 means "reset requested". Check the verdict line (run.sh line 45).
    • 

  • Ignoring aliases. F4-23's tool printed "no usable stdout-path" for a valid devicetree (R2). Firmware-provided devicetrees use aliases routinely.
    • 

  • Writing line control before the divisors. The new divisors are latched by the line-control write; the other order leaves the old rate in force until the next format change.
    • 

  • Forgetting the cache clean on release. The waiting core may never see the entry address, and the boot core waits for ever (the lab's wait has a one-second limit and reports "n of 3 other cores came up").
    • 

  • Overwriting low memory. The spin-table slots (0xd8–0xf0) and the firmware's stub live in the first page; clearing it before releasing the cores strands them.
    • 

  • The neutral tests' wording without a devicetree. R3 prints "skip devicetree tests: this platform describes itself another way (ACPI)": F4-23's message assumed the only alternative is ACPI. Here it is a board table. The test logic is right; the message is not (recorded in the course notes).
    • 

  • Wiring TX to TX. Nothing appears; nothing is damaged at 3.3 V. Swap TX and RX.
    •

Mini-project


Interrupts on the Pi 3. The BCM2837 has no GIC: it has the Broadcom interrupt controller for peripherals and a per-core "local" interrupt block that routes the generic timer. Rubric (10 points): tick runs on QEMU raspi3b, 50 ticks counted against the counter (4); both controllers' addresses taken from the devicetree with ranges (2); the same interface as the GIC driver, no Pi checks in kmain (2); an unverified table of every register used, with the document section to check (2).

  • Pi devicetrees name the console through an alias and write bus addresses that /soc's ranges translates.
    • 

  • A real board needs the UART configured: divisors from the reference clock, line control after them, pins.
    • 

  • Spin tables start cores by a release address; clean the line and send an event; they cannot stop a core.
    • 

  • Without PSCI, a watchdog ends the run, and exit code 0 is not a verdict.
    • 

  • Work on real boards with a separate SD card, a 3.3 V serial adapter wired with the power off, and a known-good card for recovery. This build is untested on hardware.
    •
