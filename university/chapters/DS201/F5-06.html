Story hook

Analogy

Lin moves into the new estate at the edge of the river town. On her first morning she has no house number, so nobody can write to her. She shouts in the street, "I am new here! Can anyone give me a number?" The town hall's clerk shouts back, "You may use number 57 for an hour, the post office is at number 1, and the address book is kept at number 1 too." Lin says, "Yes, I take 57," and the clerk says, "Done." Four shouts, and Lin can send and receive mail.

Then Lin wants to write to the copy shop. She knows its name, not its address. She asks the address book: "Where is web?" and gets "number 80, good for five minutes". She asks for "printer" and gets a firm "no such name in this town" — although the printer is in the book, typed by a clerk in a hurry as "pritner".

This chapter is about those two services. Every computer that joins a network asks for an address (DHCP), and every program that connects to a name asks for its address (DNS). You will write a tiny DNS server, watch the system's resolver use it, decode a DHCP exchange byte by byte, and find the typo.

What you will be able to do

  • Explain how a name becomes an IPv4 address: getaddrinfo, the local hosts file, the stub resolver, recursive resolvers and authoritative servers.
  • Read a DNS query and response byte by byte: header, flags, question, answer, TTL, NXDOMAIN, name compression.
  • Write a minimal authoritative DNS server in C++ and test it with the system's own resolver.
  • Describe the four DHCP messages (Discover, Offer, Request, ACK), the lease, and the options that give a host its mask, gateway and DNS server.
  • Diagnose a "name not found" by following the evidence from the program to the wire to the zone data.
Jargon box
DNS (Domain Name System)
Simple words: the internet's address book, turning names into addresses. Analogy: the town's address book. Precise: a distributed, hierarchical database of resource records, queried with a request–response protocol, usually one UDP datagram each way on port 53 (TCP for large answers). D1 R2
Domain name
Simple words: a name like web.lab.example, read from right to left as ever smaller areas. Analogy: "the copy shop, river town, valley country". Precise: a sequence of labels (each at most 63 bytes), written with dots and encoded on the wire as length-prefixed labels ending in a zero byte. D1
Resolver (DNS)
Simple words: the software that asks DNS questions for programs. Analogy: the helper who looks up the book for you. Precise: a stub resolver in the C library sends queries to the servers listed in its configuration (on Linux, /etc/resolv.conf); a recursive resolver answers them by querying authoritative servers from the root down, and caches the answers. D1 D4
Authoritative name server
Simple words: the server that holds the official data for one part of the name space. Analogy: the town hall that keeps its own town's book. Precise: a server loaded with a zone's records; its answers carry the AA (authoritative answer) flag. D1
Resource record (A record)
Simple words: one entry in DNS, for example "this name has this IPv4 address". Analogy: one line in the address book. Precise: name, type, class, TTL and data; type A (1) carries a 4-byte IPv4 address, AAAA an IPv6 address, CNAME an alias, MX a mail server, NS a name server. D1
TTL (DNS time to live)
Simple words: how long an answer may be kept and reused. Analogy: "this entry is good for five minutes; then look again". Precise: a 32-bit count of seconds in every record that bounds how long resolvers may cache it; not the same as the IPv4 header's TTL (F5-03), which counts router hops. D1
NXDOMAIN
Simple words: the DNS answer "this name does not exist". Analogy: "no such name in this town". Precise: response code 3 (Name Error) from an authoritative source; the C library reports it to programs as "Name or service not known" on Linux in this build. D1 R1
DHCP (Dynamic Host Configuration Protocol)
Simple words: how a computer joining a network gets an IP address and settings automatically. Analogy: the town hall that lends a newcomer a house number. Precise: a UDP protocol (client port 68, server port 67) built on BOOTP; a client broadcasts Discover, servers Offer an address, the client Requests one, and the server acknowledges (ACK), with options such as subnet mask, router and DNS servers. D2 R4
Lease (DHCP)
Simple words: the time for which an address is lent. Analogy: "you may use number 57 for an hour". Precise: the duration in option 51; the client renews before it ends and must stop using the address if it cannot. D2

Layer 1 — the kid explanation

Computers find each other by number (the IP address of F5-03), but people remember names. DNS is the address book that turns a name into a number. When you type a name, your computer asks a helper; the helper asks other servers until it finds the one that keeps the official entry, and then it remembers the answer for a while, so next time is faster. D1

But a computer that has just plugged in does not even have its own number yet. It shouts to everyone on its street: "I am new, can I have an address?" A DHCP server answers with an address to borrow, the street's post office (the default gateway) and where the address book is. D2

If the address book has a spelling mistake, the computer gets a clear "no such name", even though the machine is switched on and working. That is the mystery at the end of this chapter.

Layer 2 — the student explanation

From getaddrinfo to the wire

In F5-05 every client called getaddrinfo. On Linux with the GNU C library, that call first consults the configured sources in order, typically the local file /etc/hosts (which defines localhost) and then DNS; numeric addresses such as 192.0.2.7 are converted without any lookup. D4 The build confirms the effect: five names went into Listing 2, and only three DNS queries appeared on the wire — none for localhost and none for the numeric address. R1 R2 For DNS, the stub resolver sends a UDP query to the first server named in /etc/resolv.conf and waits for a response, retrying and trying other servers on time-outs. D4

Not verified — check before relying on this

The exact lookup order (the hosts: line of /etc/nsswitch.conf), the stub resolver's time-out and retry defaults, and whether a local caching service (such as systemd-resolved) sits between programs and the network all vary between distributions and were not checked in this build. Check resolv.conf(5), nsswitch.conf(5) and your distribution's documentation. The build only shows what happened in its private namespace (R1, R2).

A DNS message, byte by byte

A DNS message starts with a 12-byte header: a 16-bit ID chosen by the client (the response repeats it, so the client can match them), 16 bits of flags, and four 16-bit counts: questions, answers, authority records and additional records. D1 Then come the sections. The question is a name, a type (1 = A) and a class (1 = IN, internet). Names are encoded as labels: web.lab.example becomes 03 77 65 62 03 6c 61 62 07 65 78 61 6d 70 6c 65 00 — "3 web 3 lab 7 example 0". D1 You can read exactly those bytes in the captured query of Listing 2's run, starting at offset 0x36. R2

The answer section holds resource records: name, type, class, a 32-bit TTL, a 16-bit data length and the data — for type A, 4 bytes of address. To avoid repeating names, a record may store a compression pointer: two bytes whose top two bits are 1 and whose remaining 14 bits are an offset into the message; C0 0C means "the name at byte 12", which is where the question's name starts. D1 Listing 1 uses that pointer; tshark decoded the result as web.lab.example: type A, class IN, addr 192.0.2.80 with "Time to live: 300". R2

Flags and response codes

The flags carry QR (0 = query, 1 = response), an opcode, AA (authoritative answer), TC (truncated: retry over TCP), RD (recursion desired, set by the client), RA (recursion available, set by a recursive server) and a 4-bit response code: 0 no error, 2 server failure, 3 NXDOMAIN (name error), 5 refused. D1 Listing 1 answers with flags 0x8500: QR, AA and the client's RD copied; RA is 0, which tshark reported as "Server can't do recursive queries" — correct, our server only knows its own zone. R2

Hierarchy and caching

No single server knows every name. The root servers know the servers for each top-level domain; those know the servers for each domain below them, and so on, down to the authoritative server for the zone that holds the record (Figure 1). A recursive resolver follows these referrals for its clients and caches every answer for its TTL, so popular names are answered from memory. D1 D3 The trade-off is set by the zone's administrator: a long TTL means fewer queries and faster answers, a short TTL means changes are seen sooner. A "no such name" answer is cached too, which is why fixing a typo in a zone may take a while to be seen everywhere. D3

DHCP: getting an address in the first place

A new host has a MAC address but no IP address, so it cannot use unicast IP. DHCP solves this with broadcasts on the local network (F5-03). The client sends a Discover from source address 0.0.0.0, port 68, to 255.255.255.255, port 67; each server replies with an Offer of an address ("yiaddr", your address); the client broadcasts a Request naming the chosen offer and server, so other servers can withdraw theirs; the chosen server confirms with an ACK. D2 The transaction ID ties the four messages together. The settings travel as options after a 4-byte "magic cookie" 63 82 53 63: option 53 is the message type, 1 the subnet mask, 3 the router (default gateway), 6 the DNS servers, 51 the lease time, 54 the server identifier, 50 the requested address and 55 the list of options the client wants. D2 D5 tshark decoded all of these in the frames of Listing 3. R4

Leases and renewal

An address is lent, not given. Before the lease ends the client asks the same server to extend it, by unicast; if that fails it asks any server by broadcast; if the lease runs out, it must stop using the address. RFC 2131 describes default renewal times as fractions of the lease (one half and seven eighths). D2 That is why a laptop that sleeps through the end of its lease asks for an address again when it wakes, and why servers usually get fixed addresses or reservations instead of leases.

Layer 3 — the engineer's depth

UDP size and TCP fallback. Classic DNS over UDP limits messages to 512 bytes; larger answers set the TC flag and the client retries over TCP, port 53. The EDNS(0) extension lets the client advertise a larger UDP size in an extra "OPT" record. D1 D6 The captured queries of this build carry no additional records (the count bytes at offsets 0x30–0x35 are zero), so this resolver did not send EDNS here. R2 Listing 1 reads at most 512 bytes and accepts exactly one question; a real server must handle every case in the RFCs.

Trust. Classic DNS and DHCP have no authentication. Anyone on the local network can answer a DHCP Discover (a "rogue DHCP server" can hand out a malicious gateway or DNS server), and a forged DNS response that matches the ID and port will be accepted. Defences include random query IDs and source ports, DNSSEC signatures on records, encrypted transports (DNS over TLS or HTTPS), and switch features that only allow DHCP replies from trusted ports. D3 D6 This chapter only names them; the security courses of F11 (for example SS401 Threat modelling) return to attacks of this kind.

Parsing untrusted input. Listing 1 parses data from anyone who can send it a datagram. It checks every length against the message size before reading (lines 46–48, 108, 111) and refuses compression pointers in questions instead of following them, because a pointer loop is a classic way to make a parser spin forever. D1 Your stack in C9 will parse DHCP replies in kernel mode, where a missing check is a kernel bug.

How the hardware actually does it

A DHCP Discover is an Ethernet frame to the broadcast address ff:ff:ff:ff:ff:ff; every NIC on the segment accepts broadcast frames in hardware and passes them to its host, and switches forward them out of every port of the same network (F5-03). D5 Because the client's IP layer has no address yet, Linux DHCP clients typically send and receive these frames through a raw "packet" socket below IP instead of an ordinary UDP socket. D4 On a home network, the router's small processor usually runs both the DHCP server and a DNS forwarder that relays queries to the internet provider's recursive resolver and caches answers. D3 In your own kernel (C9), the DHCP client is often the first code to send a frame through your NIC driver, because nothing else can work until it succeeds.

Not verified — check before relying on this

That common Linux DHCP clients use packet sockets, and what a typical home router runs, are stated from general knowledge and were not checked in this build. Check the documentation of the DHCP client your distribution uses (for example its manual page) and packet(7).

Worked example

Encode the DNS query for fileserver.lab.example, type A, with ID 0x2132 and recursion desired, then check its size against the capture (the resolver chooses its own random ID, so the captured ID differs).

  1. Header: ID 21 32; flags: QR 0, opcode 0, RD 1 → 01 00; counts: 1 question, 0, 0, 0 → 00 01 00 00 00 00 00 00. 12 bytes.
  2. Name: labels "fileserver" (10 bytes), "lab" (3), "example" (7) → 0a + 10 bytes, 03 + 3 bytes, 07 + 7 bytes, 00: 1 + 10 + 1 + 3 + 1 + 7 + 1 = 24 bytes.
  3. Type A 00 01, class IN 00 01: 4 bytes. DNS message: 12 + 24 + 4 = 40 bytes.
  4. Add headers (F5-02): UDP 8, IPv4 20, and on the loopback capture a 14-byte Ethernet-style header: 40 + 8 + 20 + 14 = 82 bytes.
  5. Check: the capture's line 3 reads DNS 82 Standard query, then the resolver's ID, then A fileserver.lab.example. R2 The prediction matches.
  6. The response repeats the 40 bytes, sets flags 85 00 and the answer count to 1, and adds 2 (pointer) + 2 + 2 + 4 + 2 + 4 = 16 bytes: 98 bytes in the capture, line 4 — also matches.

Where the analogy breaks


    

  1. There is no single address book. The town's book is one object; DNS is millions of servers, each authoritative for a small zone, plus caches that may hold old copies for up to the TTL. Two people can get different answers at the same time. D3
    2. 

  2. Anyone can shout back. Lin trusts the clerk's voice; a DHCP client accepts the first plausible Offer from any machine on the segment, and classic DNS responses are not signed. D6
    3. 

  3. A name can have many addresses and many names one address. A town house has one number; DNS can return several A and AAAA records for one name (F5-05's connectTo tries each in turn), and many names can point at one server. D1
    4.

Transition box

Hardware and software needed


Linux with g++ and tshark (this build: g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0, TShark (Wireshark) 4.2.2). run.sh needs root for the private namespaces; without root, run the server on a high port (for example 5353) and query it with a tool such as dig @127.0.0.1 -p 5353 web.lab.example if you have it, instead of changing your system resolver.

Do not edit your real /etc/resolv.conf for this lab: a wrong DNS server breaks every program on the machine. run.sh changes it only inside a private mount namespace that disappears when the script ends. Summary


    

  • getaddrinfo checks local sources (such as /etc/hosts) and then asks DNS through the stub resolver configured in /etc/resolv.conf.
    • 

  • DNS is a hierarchy of authoritative servers plus caching recursive resolvers; every record has a TTL.
    • 

  • A DNS message is a 12-byte header (ID, flags, counts) and sections; names are length-prefixed labels, compressed with pointers.
    • 

  • NXDOMAIN (rcode 3) means "no such name" from the authoritative source; it is cached too.
    • 

  • DHCP gives a new host its address, mask, gateway and DNS server in four broadcast messages: Discover, Offer, Request, ACK.
    • 

  • Addresses are leased and must be renewed; DHCP and classic DNS have no authentication.
    • 

  • The build ran its own DNS server and resolver in private namespaces; DHCP was shown with decoded simulated frames only.

Forensic lab answer key


Observation: the query for printer.lab.example reached the server (server log line 3; capture line 5) and was answered within a millisecond (capture line 6) with "No such name" (NXDOMAIN, rcode 3). The two other names resolved. Hypotheses: (H1) faulty printer network card — not supported: the failure happens before any packet to the printer is sent; the program never got an address to send to, and the printer's own network was never involved. (H2) caches still updating — not consistent: the answer came from the authoritative server itself (the responses carry the AA flag, as decoded for the first response, and the server's own log shows it produced NXDOMAIN), not from a cache holding old data. (H3) the zone does not contain the name being asked for — confirmed. Root cause: the zone entry was typed as pritner.lab.example (Listing 1, line 27), so the name printer.lab.example really does not exist in the zone. Fix: correct the record's name; then expect resolvers that cached the negative answer to keep it for a while; how long is set by the zone's negative-caching rules (the SOA record's settings, which this tiny server does not send), so check with a query straight to the authoritative server. Lesson: "the machine is up" and "the name exists" are separate facts; check each with its own evidence. How the evidence was made: run.sh ran the server and resolve in private network and mount namespaces with a private resolv.conf and captured port 53 on the loopback interface with tshark.
