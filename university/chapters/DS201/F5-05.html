Story hook

Analogy

Jun runs a small copying service in the river town: people send him pages, he sends back exact copies. His house has a post room with two trays. Outgoing pages wait in the outgoing tray until the van takes them; incoming pages wait in the incoming tray until Jun picks them up. The trays are not infinite.

One day a customer posts a thousand pages and refuses to open any reply until all thousand have been sent. Jun copies the first pages and puts the copies in his outgoing tray; it fills up, because the customer's incoming tray is also full and nobody is emptying it. Jun stops copying — there is nowhere to put copies — so he stops taking pages from his own incoming tray; that fills too, and now the customer cannot send page 600. Both wait for each other, politely, forever.

In this chapter you write Jun's service and its customer in C++, the right way: owning every mailbox properly, never assuming a page arrives in one piece, and never waiting in a way that can wait forever.

What you will be able to do

  • Use the socket API (getaddrinfo, socket, bind, listen, accept, connect, send, recv, shutdown, close) from C++ and check every result.
  • Wrap a socket in a move-only RAII class that reports errors as std::system_error.
  • Handle partial sends and receives, and frame messages on a byte stream.
  • Write a TCP echo server that serves many clients with poll, and a client that verifies 100 MiB with a checksum (the course lab).
  • Diagnose a client that loses data because it assumes one recv returns one message, and a client–server deadlock.
Jargon box
Socket
Simple words: the program's end of a network conversation, used like a file. Analogy: a mailbox slot in your house wall that only your program uses. Precise: a kernel object created by socket() and referred to by a file descriptor; it has a type (stream for TCP, datagram for UDP), local and remote addresses, and kernel send and receive buffers. D1 D2
Listening socket
Simple words: a socket that waits for new TCP connections instead of carrying data. Analogy: the receptionist who greets callers and hands each one to a new desk. Precise: a stream socket on which listen() was called; the kernel completes handshakes and queues connections, and each accept() returns a new, connected socket for one of them. D2 D3
getaddrinfo
Simple words: the library call that turns a host name and a port into addresses you can connect to. Analogy: looking up a friend's address before writing. Precise: the POSIX function that resolves a node name and a service into a linked list of socket addresses (IPv4 and IPv6), freed with freeaddrinfo; errors are reported as its own codes, turned into text by gai_strerror. D2
Partial send and partial receive
Simple words: send and recv may move fewer bytes than you asked for. Analogy: the van takes only the pages that fit; you collect only the pages already in the tray. Precise: on a stream socket, send returns the number of bytes accepted and recv the number of bytes available, each possibly less than requested; correct code loops. D2 R1
Framing
Simple words: marking where each message starts and ends inside a byte stream. Analogy: writing "this letter has 3 pages" on the first page. Precise: an application-level convention, such as a fixed-size length prefix or a delimiter, that lets the receiver split a TCP byte stream back into messages. D4
Event loop (poll)
Simple words: one thread that waits until any of many sockets is ready, then handles only what is ready. Analogy: Jun looks at all his trays at once and works on whichever has something to do. Precise: a loop around poll(), which blocks until at least one of the given file descriptors is readable or writable (or has an error) and reports which; the program then performs operations that will not block. D2 D3
Half-close
Simple words: saying "I will send nothing more" while still listening for the answer. Analogy: "that was my last page; I am still reading yours". Precise: shutdown(fd, SHUT_WR) sends a FIN for one direction (F5-04) while the socket can still receive; the peer's recv then returns 0 after the last byte. D2 D5

Layer 1 — the kid explanation

Your program cannot touch the network card itself. It asks the operating system for a socket, a numbered mailbox slot that belongs to your program, and then calls functions to send bytes into it and receive bytes from it. The operating system does all the TCP work of F5-04 behind the slot. D1

A server first sets up a special socket that waits for visitors, like a receptionist. Each time a client connects, the receptionist gives that client its own new socket, its own desk. A client simply connects to the server's address and port. D2

Two habits make network programs correct. First, a send or receive can move only part of what you asked for, so you keep going until it is all done. Second, never wait for something in a way that can wait forever: Jun's deadlock happens when both sides only send and nobody reads. D1

Layer 2 — the student explanation

The calls and what each one does

getaddrinfo(host, port, hints, &list) resolves a name ("localhost", or a DNS name, F5-06) and a port into a list of socket addresses, IPv4 and IPv6 alike; you try them in order. socket(family, type, protocol) creates the endpoint and returns a file descriptor. A server calls bind (attach to a local address and port), listen (let the kernel accept handshakes) and then accept, which blocks until a connection is queued and returns a new descriptor for it. A client calls connect, which performs the handshake. Both then use send and recv; shutdown closes one direction and close releases the descriptor. D2 D3 Every call returns −1 and sets errno on failure, except getaddrinfo, which returns its own error code. D2

An RAII socket class

A descriptor is a resource: it must be closed exactly once, on every path, including exceptions. Listing 1's Socket owns one descriptor, closes it in its destructor, cannot be copied (two owners would close twice) and can be moved (ownership passes, the source becomes empty), the rule of SP102 F2-11 and F2-13. D4 Errors become exceptions of type std::system_error carrying errno, so no failure is silently ignored and the message names the call. D6 The helpers connectTo and listenOn hide the address boilerplate; sendAll and recvExact hide the loops of the next section.

Partial operations, measured

send returns how many bytes the kernel accepted into the socket's send buffer, which can be fewer than offered; recv returns what has arrived so far, at most the size you asked for. D2 Listing 2 hands 1 MiB to sendAll at once and receives with a 256 KiB buffer: the build's recorded run needed 6 recv calls, and other runs during development needed up to 11, with different sizes each time. R1 Code that assumes "one send, one receive" works in tests with small messages and fails with large ones or under load; that is the forensic lab.

Framing messages

Because TCP is a byte stream (F5-04), an application that exchanges messages must frame them. A common choice is a fixed-size length prefix: send a 4-byte big-endian length, then that many bytes; the receiver uses recvExact for the 4 bytes, checks the length against a maximum (never trust it blindly, F5-01), then recvExact for the body. Delimiters (a newline after each line of text) are the other common choice, and require escaping if the delimiter can appear in a message. D4 The echo protocol of this chapter needs no framing: it returns bytes, not messages.

Serving many clients: poll

A blocking recv on one client would stop a single-threaded server from serving the others. Listing 3 instead asks poll to wait on all sockets at once: the listening socket for new connections, and each client for "readable" and, when it has bytes waiting to be echoed, "writable". When poll returns, the server performs exactly one recv or send per ready socket, which does not block because the socket is ready. D2 D3 Each client has its own pending string of bytes received but not yet sent back; a slow client only makes its own string grow. A thread per client (SP203) is the other classic design: simpler code, more memory and scheduling per client.

A client that cannot deadlock

Listing 4 sends from one thread and receives in another, so receiving never waits for sending to finish, and the kernel buffers keep draining (Figure 2). When the sender is done it calls shutdown(SHUT_WR): the server sees end-of-stream, sends back what it still holds, and closes, so the client's recv returns 0 exactly when the last byte has arrived. D2 Both sides compute a 64-bit FNV-1a hash of the bytes; equal hashes and equal counts mean the echo was exact, with very high probability (a hash can collide; it is a check, not a proof). D7 In the build, 13 bytes, 1 MiB and 100 MiB all passed. R2

Layer 3 — the engineer's depth

Signals and interrupted calls. Writing to a connection the peer has closed raises the SIGPIPE signal on Linux, whose default action ends the process; servers either ignore the signal or, as Listing 1 does, pass MSG_NOSIGNAL to send and get the error EPIPE instead. A blocking call interrupted by a signal handler can fail with EINTR and should simply be retried; both helpers do. D5 D2

Time limits. A program must not wait forever on the network: a peer may vanish without a FIN (power loss, cable pulled). Use a timeout on poll, SO_RCVTIMEO on blocking sockets (F5-04 Listing 3), and application-level deadlines; TCP keepalive exists but its defaults are long. D5 Listing 3 waits with an infinite poll timeout to stay short; the lab asks you to add an idle timeout.

Scaling beyond poll. poll passes the whole list of descriptors on every call and returns after scanning it, so its cost grows with the number of clients; Linux offers epoll, which keeps the interest list in the kernel and reports only ready descriptors. D5 Listing 3's std::string::erase from the front is also linear; a production server would use a ring buffer. Measure before optimising (F5-07).

Not verified — check before relying on this

The default sizes of Linux socket send and receive buffers, their automatic tuning, the default TCP keepalive timings and the exact listen backlog limits were not checked in this build. Check the socket(7), tcp(7) and listen(2) manual pages and the kernel's networking sysctl documentation for the kernel version in the run logs before relying on any number.

How the hardware actually does it

Every socket call is a system call (OS201): the CPU switches to the kernel, which copies your bytes from your buffer into the socket's send buffer (or out of the receive buffer into yours) and returns. The kernel later builds segments from the send buffer and hands them to the NIC driver, whose descriptor rings and DMA (HW205) move them to the wire; arriving packets are written by DMA into kernel memory, processed by the TCP code after an interrupt, and appended to the receive buffer, where your next recv finds them. D1 D8 The copy between your memory and the kernel's costs CPU time per byte and the system call costs time per call, which is why F5-07 finds that tiny sends are slow; "zero-copy" and kernel-bypass interfaces exist to remove both costs (DS401).

Worked example

Design the length-prefix framing for one chat message "hi Lin" (6 bytes) and trace the receiver.

  1. Sender writes the length 6 as a 4-byte big-endian number: 00 00 00 06, then the 6 bytes 68 69 20 4c 69 6e: 10 bytes in total, handed to sendAll.
  2. Suppose the network delivers them as two pieces, 3 bytes and 7 bytes (Listing 2 shows that any split is possible).
  3. Receiver calls recvExact(s, header, 4). The first recv inside it returns 3 bytes; the loop asks for 1 more and gets 06 plus nothing else, because it asked for exactly 1.
  4. Length = 0x00000006 = 6; check 6 ≤ the protocol's maximum (say 4096): accept.
  5. recvExact(s, body, 6) returns the 6 remaining bytes: "hi Lin". The message boundary is restored no matter how TCP cut the stream.
  6. If recvExact returns false in the middle, the peer closed mid-message: report a protocol error, do not process half a message.

Where the analogy breaks


    

  1. The post room's trays have no fixed size. Jun's trays are physical. Kernel socket buffers are sized by the kernel, can grow automatically, and differ between machines; the point at which deadlock.cpp stopped (after 9 or 10 MiB in the build) is a property of that machine and run, not a constant. R4
    2. 

  2. One page can arrive in several pieces. A posted page arrives whole; one send can arrive as several recv results, and several sends as one (Listing 2, F5-04 Listing 1). R1
    3. 

  3. The receptionist works while you sleep. The kernel completes handshakes for a listening socket before your program calls accept; clients can already be "connected" to a server that has not looked at them yet. D3

Summary


    

  • A socket is a kernel object behind a file descriptor; servers bind, listen, accept; clients connect; both send/recv and close.
    • 

  • Own descriptors with a move-only RAII class; turn errno into std::system_error.
    • 

  • send and recv move partial amounts; loop (sendAll, recvExact).
    • 

  • TCP has no message boundaries: frame messages with a length prefix or a delimiter, and validate lengths.
    • 

  • poll lets one thread serve many clients without blocking on any one.
    • 

  • Never send everything before reading: both sides can block forever; send and receive concurrently.

Observation: 5 and 1,000 bytes pass; 100,000 and 300,000 bytes fail, and the received amounts in the build's run were 65,536 and 119,808 bytes (an earlier run gave 128,970 for the second): not a fixed fraction, and different on other runs (R3). Hypotheses: (H1) the server drops data — ruled out: the same server passes 100 MiB with a proper client (Listing 4, R2); (H2) the client reads too little — confirmed by the code: it calls recv exactly once per message. Root cause: the client assumes one recv returns the whole echo. recv returns whatever has arrived, at most the size requested; for small messages that is everything, for large ones only the first piece (Listing 2 shows the same effect). Fix: since the client knows the size it sent, read exactly that much: recvExact(s, reply.data(), size), or in general frame messages. Test that would have caught it: sizes larger than any buffer on the path (1 MiB and more), and a test that splits data artificially (a proxy that forwards one byte at a time). How the evidence was made: truncated.cpp runs a correct echo server in a thread and the colleague's single-recv client against it, built and run by run_lab.sh with the course flags.
