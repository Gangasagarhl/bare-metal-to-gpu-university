Story hook

Analogy

Amara and Rafael argue about the post. "It is fast," says Amara: "my last letter arrived the next morning." "It is slow," says Rafael: "my parcel of four hundred pages took a week." They are both right, because they measured different things. Amara measured how long one letter takes — latency. Rafael measured how many pages per day arrive — throughput.

Then the post office introduces a new rule to save envelopes: a clerk holds back any small note until the receipt for your previous letter has come back. Rafael, who always sends a cover note followed by the main letter, finds that every exchange with Amara now takes days longer. Amara's side, meanwhile, waits to send receipts until it has something else to send. Nobody did anything wrong; two sensible rules met, and every exchange waits for a timer.

In this chapter you measure the network the honest way: many samples, percentiles instead of one average, warm-up, repeated runs, and the machine named next to every number. Then you find the two sensible rules that add forty-odd milliseconds to every request.

What you will be able to do

  • Distinguish latency, round-trip time and throughput, and say which one a user or a benchmark actually cares about.
  • Measure round-trip latency as a distribution (minimum, median, 90th, 99th and 99.9th percentile, maximum) with warm-up and repeated runs.
  • Measure TCP throughput and explain why many small send calls are slower than few large ones.
  • Compute the bandwidth-delay product and use it to size windows and buffers.
  • Diagnose a fixed 40–50 ms delay from a capture, as Nagle's algorithm meeting delayed acknowledgments, and fix it.
Jargon box
Latency (network)
Simple words: how long one message takes to get where it is going. Analogy: how long one letter takes to arrive. Precise: the time from sending a message to its arrival (one-way) or to the arrival of its reply (round trip); it includes processing in both hosts, queueing, transmission and propagation, and varies from message to message. D1
Round-trip time (RTT)
Simple words: the time from sending a message until the answer comes back. Analogy: from posting a letter until the reply is in your mailbox. Precise: measured on one clock (the sender's), so it avoids synchronising two clocks; TCP measures it continuously to set its timers (F5-04). D1 D2
Throughput (network)
Simple words: how much data arrives per second. Analogy: pages per day reaching your friend. Precise: bytes delivered to the receiving application per unit of time over an interval, limited by the slowest of link rate, window per round trip, CPU per byte and per call, and the application itself. D1
Tail latency
Simple words: how slow the slowest few requests are. Analogy: the one letter in a hundred that takes a week. Precise: the high percentiles (99th, 99.9th) of a latency distribution; in systems where one user action waits for many requests, the tail decides what users feel. D3
Warm-up run
Simple words: running the test for a while before you start counting. Analogy: letting the post clerk find the right drawer before you start the stopwatch. Precise: discarding initial iterations dominated by one-time costs (page faults, cache misses, lazy initialisation, CPU frequency changes, TCP slow start) so that the measurement describes the steady state. D4
Bandwidth-delay product
Simple words: how much data must be "on the wire" at once to keep a link busy. Analogy: how many pages must be on the road so your friend never waits for the next one. Precise: link rate × round-trip time; a sender must be allowed (by the receive window and the congestion window) at least this many unacknowledged bytes to reach the link rate. D1 D2
Nagle's algorithm
Simple words: a TCP rule that holds back small pieces of data while earlier data is unacknowledged, to send fewer tiny packets. Analogy: the clerk who holds your small note until the receipt for your last letter returns. Precise: if there is unacknowledged data in flight, a TCP sender buffers new data smaller than a full segment until an ACK arrives or a full segment accumulates; disabled per socket with the TCP_NODELAY option. D5 D6
Delayed acknowledgment
Simple words: a receiver waits a little before sending an ACK, hoping to send it together with reply data. Analogy: Amara waits to send the receipt until she writes back anyway. Precise: TCP receivers may delay a pure ACK for a short time (bounded by the standard) unless a second full segment arrives; combined with Nagle's algorithm on the other side it can stall request–response traffic until the delay timer fires. D5 R4

Layer 1 — the kid explanation

There are two different questions about a network. "How long does one message take?" is latency. "How much can I send per second?" is throughput. A garden hose and a fire hose can both deliver the first drop after one second, but the fire hose fills a bucket far faster. D1

If you time something only once, you might be unlucky. Scientists time it many times and look at the typical result and at the worst results, because the worst ones are what make people complain. D3

Sometimes two sensible rules make each other slow. One computer waits to send a small piece until the other has said "got it"; the other waits to say "got it" until it has something else to say. Both wait, until a timer ends the waiting. Changing one setting fixes it. D5

Layer 2 — the student explanation

What latency is made of

The time for one message is the sum of several parts: processing in the sending host (system calls, copying, protocol code), waiting in queues (in the kernel, the NIC, switches and routers), transmission (putting the bits on the wire: size ÷ link rate), propagation (distance ÷ signal speed in the medium) and processing in the receiving host. D1 On loopback there is no wire at all, so a loopback round trip measures only the host parts: two programs, the kernel's UDP and IP code, and the scheduler waking a thread. That is why loopback numbers say nothing about a real network; they measure your software and your machine. R2

Maths you need here — percentiles

Sort the measurements from smallest to largest. The median (50th percentile) is the value in the middle: half the measurements are smaller. The p-th percentile is the value below which p % of the measurements lie: with 20,000 sorted values, the 99th percentile is about the 19,800th, so 200 measurements are slower. udp_rtt.cpp uses a simple nearest-rank rule: it takes the element at index ⌊p/100 × n⌋ (capped at the last element). Other tools interpolate between neighbours, so small differences between tools are normal.

Why not the average (mean)? One very slow value pulls the mean up, and the mean hides how often slowness happens. In the build's run 1, the mean was 3.8 µs and the median 3.6 µs, but the slowest 0.1 % took more than 24.6 µs. R2 The full treatment is in MA202 (median and percentile).

Throughput and the cost per call

R3 In the build's optimised run the median rose from 93 MiB/s with 64-byte calls to 1,633 MiB/s with 1 KiB calls and about 2,300–2,500 MiB/s with 16 KiB and 256 KiB calls. R3 Rule: batch small messages into larger writes (an application buffer, or writev), and measure before and after.

The bandwidth-delay product

F5-04 showed that a connection can move at most one window per round trip. To fill a link of rate B with round-trip time RTT, the sender must be allowed B × RTT bytes in flight: the bandwidth-delay product. D1 D2 If the receive buffer (F5-04's forensic lab), the congestion window or the application's own window is smaller, throughput is limited to window ÷ RTT, however fast the link. The worked example computes it for a real-world-sized link; the lab measures the loopback case.

Nagle's algorithm and delayed ACKs

Early TCP traffic contained many one-byte packets (each keystroke of a remote terminal), each with 40 bytes of headers. Nagle's algorithm reduces them: while sent data is unacknowledged, small new data waits until the ACK arrives or a full segment is ready. Independently, receivers delay pure ACKs briefly in the hope of sending them with reply data. D5 D6 A client that writes a request as two small pieces (write–write–read) triggers both: the second piece waits for an ACK, and the server, which cannot reply to half a request, delays that ACK. Listing 3 shows the result: a median of 47.963 ms per request with default options and 0.008 ms with TCP_NODELAY on the client. R4 The two fixes are to send each request in one write (best), or to set TCP_NODELAY on latency-sensitive sockets.

Layer 3 — the engineer's depth

Coordinated omission. A load generator that sends the next request only after the previous reply waits during every stall, so it sends fewer requests exactly when the system is slow, and the slow periods are under-represented in its statistics. Tools that measure at a fixed planned rate record the time from the planned send, not the actual one. D3 Listings 1 and 3 are closed-loop (one request at a time) and so describe single-request latency, not latency under load.

Clocks and timer resolution. steady_clock on Linux normally reads a fast, monotonic kernel clock without a system call; its resolution and cost should still be measured on the machine, because a 3 µs measurement with a 1 µs clock is coarse. D7 One-way latency needs synchronised clocks (PTP, or hardware timestamps in the NIC), which is why most tools measure round trips. D1

Little's law. The average number of requests in flight equals throughput × average latency (Little's law, met in HW301); for a network path, that is the bandwidth-delay product again. To get more throughput with the same latency you need more in flight: bigger windows, more connections or pipelined requests. D3

Build flags matter less than you think for system-call-bound code. The course flags (AddressSanitizer, UBSan, no optimisation) slow down computation, but the round trip in Listing 1 is mostly kernel time. The build's sanitizer run had a median of 3.8 µs, inside the 3.6–6.5 µs range of the three optimised runs. R2 For throughput, where user-space code runs per call, the difference was larger: 1 KiB sends gave a median of 1,012 MiB/s with sanitizers and 1,633 MiB/s optimised, with wide ranges in both. R3 Always report the build flags with the number.

How the hardware actually does it

On a real link, transmission time is set by the physical layer: at a link rate of B bits per second, a frame of L bits takes L ÷ B seconds to send, and propagation adds about 5 ns per metre in copper or fibre. D1 NICs also add their own latency trade-offs: interrupt coalescing waits for several packets (or a short time) before interrupting the CPU, which saves CPU at high throughput but adds latency to single packets; segmentation and receive offloads (F5-02) move per-packet work into the NIC. D8 CPU frequency scaling and deep idle states add wake-up time to the first packet after a pause, which is one reason warm-up matters and why latency benchmarks often pin threads to cores. D4 None of these were measurable in the build: the loopback interface has no physical layer, no coalescing and no wire.

Untested on hardware

All measurements in this chapter were made on the loopback interface of a shared cloud build machine (4 logical CPUs, Intel Xeon @ 2.10GHz as reported by the machine, kernel 6.18.44, R1). No physical NIC, cable or switch was involved, so the real-link half of the course lab — latency and throughput between two computers — is untested. It needs two Linux machines on a wired network (or a machine and a single-board computer), the same listings with the server address changed from 127.0.0.1, and the link rate of both NICs recorded. Expect very different numbers: a real link adds transmission, propagation, NIC and switch time.

Worked example

Size a TCP receive buffer for a link with an example rate of 1 Gbit/s and an example round-trip time of 20 ms (both example values chosen for the arithmetic, not measurements).

  1. Rate in bytes per second: 1 Gbit/s = 10⁹ bit/s ÷ 8 = 125,000,000 bytes/s.
  2. Bandwidth-delay product: 125,000,000 bytes/s × 0.020 s = 2,500,000 bytes ≈ 2.4 MiB.
  3. So the receiver must advertise a window of at least about 2.4 MiB for one connection to fill the link. F5-04's forensic logger, with a 4 KiB window, would reach at most 4,096 ÷ 0.020 ≈ 205,000 bytes/s ≈ 0.2 MB/s on this link — 0.16 % of the link.
  4. The 16-bit window field alone allows 65,535 bytes: 65,535 ÷ 0.020 ≈ 3.3 MB/s. Window scaling (F5-04) is what makes fast long links usable.
  5. Now the build's loopback: median round trip 3.6 µs (R2) and about 2,400 MiB/s ≈ 2.5 × 10⁹ bytes/s (R3) give a product of about 2.5 × 10⁹ × 3.6 × 10⁻⁶ ≈ 9,000 bytes: on loopback a small window already suffices, which is why F5-04's run A was fast with a default buffer.

Where the analogy breaks


    

  1. Letters do not compete for the clerk's attention the way packets compete for the CPU. On loopback the "post" is the same CPU that runs both programs; a slow round trip may be a scheduling delay, not anything a network did. R2
    2. 

  2. The post's speed is fixed; TCP's is not. A TCP connection's throughput changes during the transfer (slow start, congestion control, window growth), so a short test measures the start-up, not the steady rate. D2
    3. 

  3. The clerk's rule is per post office; Nagle's is per socket. TCP_NODELAY changes one socket of one program; other programs on the same machine keep the default. D6

  • Latency is time per message; throughput is data per second; round-trip time is measured on one clock.

  • Small writes cost a system call each: batch them.
    • 

  • A connection needs a window of at least the bandwidth-delay product (rate × RTT) to fill a link.

Forensic lab answer key


Observation: in the capture, packets arrive microseconds apart except for two gaps of about 44 ms (before packet 11) and 48 ms (before packet 16). Each gap ends with a pure ACK from the server (length 66, no data), and the client's 80-byte body (length 146) follows at once (packet 12). The timings agree: median 47.963 ms with default options, 0.008 ms with TCP_NODELAY (R4). Hypotheses: (H1) TCP is inherently slow — refuted: the same connection type with one option changed is about 6,000 times faster. (H2) the server is slow — refuted: the server replies microseconds after the body arrives (packet 14). (H3) a TCP timer stalls each request — confirmed. Root cause: the client writes each request as two small sends. The header goes out at once; the body is small and the header is unacknowledged, so Nagle's algorithm holds it. The server has only half a request, so it has no reply to carry an ACK and delays the pure ACK until its delayed-ACK timer fires (about 40–48 ms in this run). Then the body is released, the server replies, and the cycle repeats. Why the first request was fast: the receiver acknowledged at once at the start of the connection (packets 5 and 7 follow within microseconds), consistent with Linux's "quick ACK" behaviour early in a connection (see the unverified box). Fixes: best, build the whole request in a buffer and send it with one call (or writev), so there is never a small second write; alternatively set TCP_NODELAY on the client socket, as the second timing line did. Switching to UDP would trade this for lost-message handling and is not needed. How the evidence was made: small_requests.cpp runs the server in a thread and times 50 requests twice; run.sh built it with -O2 and captured it with tshark in a private network namespace; the course-flags run is small_requests.log.
