Story hook

Analogy

Amara lives in a river town; her friend Rafael lives in a mountain town two valleys away. They plan a weekend together entirely by post. Amara's plan is long, so she writes it on seven numbered cards and drops them in the box on Monday. The cards travel separately: through the sorting office, onto different vans, along different roads.

Rafael's mailbox tells a strange story on Wednesday. Card 6 came before card 5. Card 0 arrived twice, because a sorting clerk thought the first copy was lost and sent another. Card 3 never came at all. And one card has a smudge where "Saturday" should be, so Rafael cannot be sure it says "Saturday" and not "Sunday".

Rafael is not worried, because the friends agreed on rules long ago. Every card carries its number and the total, so he can sort them and see the gap. At the bottom of each card Amara writes how many letters the card holds, so a smudge that changes the count gives itself away. He writes back: "Card 3 missing, please send it again."

Computers that talk across a network are in Rafael's position all the time. This chapter is about the cards: what a packet is, what is written on its outside, and why every byte has a fixed place.

What you will be able to do

  • Explain what a packet is, why networks cut data into packets, and what "best effort" delivery does and does not promise.
  • Lay out a packet header as bytes in network byte order, and read such a header back from a hex dump.
  • Compute and check an Internet-style 16-bit checksum by hand and in C++.
  • Capture a real UDP datagram on the loopback interface and identify its header bytes and its payload.
  • Diagnose a receiver that misreads multi-byte header fields because of byte order.
Jargon box
Packet
Simple words: one small piece of data that travels across a network on its own. Analogy: one numbered card of Amara's plan. Precise: a unit of data sent across a network, made of a header (addresses, lengths, numbers) and a payload; KID101 met the word in F0-09. At the internet layer the unit is called a datagram. D1 D2
Header (packet)
Simple words: the information in front of the data that tells the network and the receiver how to handle it. Analogy: the outside of the envelope and the numbers in the corner. Precise: a sequence of fields of fixed size and position at the start of a packet, defined by a protocol specification; each field has a byte offset, a width and a byte order. D1
Payload
Simple words: the data the packet is carrying for someone. Analogy: the letter inside the envelope. Precise: the bytes of a packet after its header; the protocol that built the header does not interpret them. D1
Best-effort delivery
Simple words: the network tries to deliver each packet, but promises nothing. Analogy: the post usually works, but cards can be late, lost, doubled or overtaken. Precise: a service model in which packets may be lost, duplicated, reordered, delayed or damaged, and the sender is not told; the Internet Protocol provides this service and leaves reliability to higher layers. D2 D1
Network byte order
Simple words: the agreed order of the bytes of a number on the wire: most significant byte first. Analogy: both towns agree to write numbers left to right, biggest digit first. Precise: big-endian order, which the Internet protocol specifications use for multi-byte header fields; a little-endian machine must convert (SP201 F2-18 defined endianness). D2 R1
Checksum
Simple words: a small number computed from the data, sent with it, so the receiver can notice damage. Analogy: the letter count written at the bottom of the card. Precise: a value computed over a block of bytes by a fixed rule; the Internet checksum is the 16-bit ones' complement of the ones' complement sum of the 16-bit words. It detects many, but not all, errors. D3 R1
MTU (maximum transmission unit)
Simple words: the biggest packet one kind of link will carry. Analogy: the largest envelope the post van accepts. Precise: the largest packet, in bytes, that a network interface sends without splitting it; the value depends on the link type and configuration. D1 R5
Loopback interface
Simple words: a pretend network inside one computer: packets sent to it come straight back to the same machine. Analogy: a letter you post to your own house. Precise: a software network interface (named lo on Linux) holding the address 127.0.0.1; packets sent to it are delivered to the same host without leaving it. D1 R4

Layer 1 — the kid explanation

When a computer sends a big message, it does not send one huge lump. It cuts the message into small pieces called packets, as Amara cut her plan into cards. Each packet travels on its own. If one is lost, only that small piece has to be sent again. D1

Every packet has two parts. The header is like the outside of an envelope: who it is for, who sent it, which piece it is, how long it is. The payload is the letter inside. The network reads the header to deliver the packet and does not care what the payload says. D1

The network does its best, but it promises nothing. Packets can be late, lost, doubled or overtaken. So the sender writes enough on each header for the receiver to notice trouble: a number to sort by, and a small check number, the checksum, to spot damage. That is exactly the deal Amara and Rafael made. D2 D3

Both sides must also agree how to write numbers as bytes. If one side writes "biggest part first" and the other reads "smallest part first", 8 becomes 2048. The forensic lab shows this really happening.

Layer 2 — the student explanation

Why packets

A packet-switched network moves independent packets, each carrying enough addressing information to be forwarded on its own; no path is reserved in advance. Links are shared between many conversations, a router can forward packets of different conversations one after another, and a failure affects only the packets that were on the failing part. The price is that every packet carries header bytes, and that nothing about the path or timing is promised. D1

What "best effort" means precisely

The Internet Protocol (IP, RFC 791) delivers datagrams from a source address to a destination address. Its specification does not provide reliability, ordering or flow control: a datagram may be lost, duplicated, delivered out of order or delayed, and the sender is not notified in general. D2 Everything a program needs beyond that is built on top, in a transport protocol (TCP, F5-04) or in the application. Listing 2 simulates such a network so you can see all three effects in one run; the receiver handles them with a sequence number and a total in each header. R2

Headers are bytes at fixed places

A protocol specification defines its header as a list of fields: offset, width in bits and meaning. Nothing in the bytes says where a field starts; both sides know it from the specification. That is why an off-by-one mistake in a hand-written header shifts every later field and garbles the packet. D1 Multi-byte fields are written in network byte order, most significant byte first. D2 The x86-64 machine of this build stores integers in memory least significant byte first (SP201 F2-18), so a program must convert when it writes or reads a header. Listing 1 does it with shifts, which work the same on every machine; Listing 3 uses the POSIX functions htons ("host to network, short") and ntohs. D5 R1

The Internet checksum

Several Internet headers carry a 16-bit checksum computed the same way: treat the bytes as 16-bit big-endian words, add them with "end-around carry" (a carry out of bit 15 is added back at bit 0; this is ones' complement addition), and store the bitwise complement of the sum. D3 The sender computes it with the checksum field set to zero. The receiver adds up everything, checksum included; for an intact packet the complement of that sum is zero. Listing 1 shows both: the intact packet checks "ok", and flipping one bit makes it "DAMAGED". R1 The checksum is cheap, which is why it was chosen, and weak: swapping two 16-bit words, for example, does not change the sum. Links add stronger checks of their own (F5-03). D3

How big can a packet be?

Each link type has a largest packet it will carry, its MTU. Data larger than that must be cut up, either by the sending program or protocol (TCP cuts its byte stream into segments, F5-04) or by IP itself, which can split a datagram into fragments that the destination reassembles. D2 On the loopback interface of this build the kernel reported an MTU of 65536 bytes. R5 A real Ethernet link has a much smaller one; its value is in the unverified box below, not in this paragraph, because it was not checked against the standard in this build.

Layer 3 — the engineer's depth

Header design is a trade-off. Every field costs bytes in every packet, forever, so specifications choose widths carefully and leave room for change: a version field first (so a receiver knows how to parse the rest), a header-length field (so options can be added), and reserved bits that senders must set to zero. D2 When you design a protocol in this course's project, write the header as a table of offsets and widths before writing code, and include a version field.

Robustness principle and parsing. The early Internet specifications ask implementations to be conservative in what they send and liberal in what they accept. D6 Security work since then has shown the cost of "liberal": a parser that trusts a length field without checking it against the bytes actually received reads past the end of its buffer. Always validate every length against the real packet size before using it, as the receiver of the forensic lab does (it rejects, it does not crash). F11 returns to this.

What the checksum does not protect. The IPv4 header checksum covers only the IPv4 header, not the data; UDP and TCP carry their own checksums over their headers, their data and a "pseudo-header" with the addresses. D2 D4 F5-02 builds those headers by hand and lets tshark verify them.

Not verified — check before relying on this

The usual MTU of Ethernet links, the minimum datagram size every IPv4 host must be able to reassemble, and how often real networks lose, duplicate or reorder packets were not checked in this build. Check IEEE 802.3 (frame sizes), RFC 791 (the section on fragmentation and reassembly) and "TCP/IP Illustrated, Volume 1" (D1) before quoting a number. The only size measured here is the loopback MTU (R5).

How the hardware actually does it

A network interface controller (NIC, HW205) does not understand IP or your header. The operating system builds the bytes of a packet in memory, writes a descriptor that points at them into the NIC's transmit ring, and the NIC reads the bytes by DMA and turns them into signals on the wire; on receive it does the reverse and raises an interrupt. D1 Many NICs can also compute some checksums while sending ("checksum offload"), which is why a capture taken on the sending machine can show a checksum the hardware will only fill in later; F5-02 shows this in a real capture. The loopback interface used in this chapter has no hardware at all: the kernel hands the packet from its send path to its receive path in memory. D1 R4

Worked example

Compute the checksum of Listing 1's packet by hand. The header is seq = 2, total = 5, length = 8, checksum = 0 while computing; the payload is the 8 characters Hi Amara.

  1. Write the header as 16-bit big-endian words: 0x0002, 0x0005, 0x0008, 0x0000.
  2. Write the payload as words, two characters each, using their ASCII codes: "Hi" = 0x4869, " A" = 0x2041, "ma" = 0x6d61, "ra" = 0x7261.
  3. Add the payload words: 0x4869 + 0x2041 = 0x68AA; + 0x6D61 = 0xD60B; + 0x7261 = 0x1486C. That has a carry out of 16 bits, so fold it back: 0x486C + 0x1 = 0x486D.
  4. Add the header words: 0x486D + 0x0002 + 0x0005 + 0x0008 = 0x487C.
  5. Complement every bit: 0xFFFF − 0x487C = 0xB783. Listing 1 printed checksum=0xb783. R1
  6. Check as the receiver: the sum of all words including the checksum is 0x487C + 0xB783 = 0xFFFF, whose complement is 0: intact.
  7. Damage: the run flips one bit of byte 9, so "Hi" becomes "Hm" (0x69 to 0x6D). The sum grows by 4: 0x487C + 4 + 0xB783 = 0x10003, folded to 0x0004; its complement 0xFFFB is not 0, and the receiver says "DAMAGED". R1

Second example, read a real header: in the capture of Listing 3 (Figure 2), bytes 16–17 are 00 29. Big-endian, that is 0×256 + 0x29 = 41: the IPv4 total length, 20 bytes of IPv4 header + 8 of UDP header + 13 of payload. Bytes 38–39 are 00 15 = 21: the UDP length, 8 + 13. R4

Where the analogy breaks


    

  1. Networks copy; the post moves. A postcard exists once. A packet is bytes, and a router or a retransmitting sender can create exact copies; a duplicate is not a mistake to apologise for but an everyday event the receiver must handle (Listing 2 received packet 0 twice). D2 R2
    2. 

  2. A smudge is visible; a flipped bit is not. Rafael can see the smudge. A receiver sees a perfectly sharp but wrong byte; only the checksum reveals it, and only for the errors the checksum can detect. Some changes, such as two swapped 16-bit words, leave the Internet checksum unchanged. D3
    3. 

  3. The post office reads nothing but the envelope; routers read more and change it. Routers decrement a hop counter in the IPv4 header and recompute the header checksum at every hop, so the "envelope" is rewritten on the way. D2
    4.

Summary


    

  • Networks move data as packets: a header that the network and the receiver read, and a payload they carry.
    • 

  • IP's service is best effort: packets may be lost, duplicated, reordered, delayed or damaged, silently.
    • 

  • Receivers cope with information the sender put in the header: sequence numbers, totals, lengths, checksums.
    • 

  • Header fields have fixed offsets and widths; multi-byte fields use network byte order (big-endian).
    • 

  • The Internet checksum is a ones' complement sum: cheap, and blind to some errors.
    • 

  • A real 13-byte UDP payload travelled as 55 bytes on loopback: three headers of 14, 20 and 8 bytes.
    • 

  • Never trust a length field before checking it against the bytes really received.

Forensic lab answer key


Observation: the first packet's bytes are 00 01 00 08 then 8 bytes of text: the sender meant seq = 1 and length = 8, which is correct (8 payload bytes). The logger read seq = 256 and length = 2048. Relation: every value read equals the meant value times 256 (0x0001 → 0x0100, 0x0008 → 0x0800, 0x0006 → 0x0600 = 1536, 0x000a → 0x0a00 = 2560): the two bytes of each field were swapped. Hypotheses: (H1) the station writes wrong lengths — ruled out, the bytes show lengths that match the payloads exactly; (H2) the logger reads the fields in the wrong byte order — confirmed by the ×256 relation on all six values. Root cause: std::memcpy(&h.seq, p.data(), 2) and the same for length copy network-order bytes into a little-endian integer without conversion. The compiler cannot warn: the code is valid C++, it just means something else. Fix: assemble each field from its bytes, most significant first (as receiver_fixed.cpp does), or call ntohs on the copied value. The fixed receiver's real run:

How the evidence was made: receiver_log.cpp run by run_lab.sh with the course flags on the x86-64 build machine (R3); on a big-endian machine the bug would be invisible, which is why it survives on some teams for years.
