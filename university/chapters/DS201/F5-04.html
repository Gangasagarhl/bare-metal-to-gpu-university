Story hook

Analogy

Amara and Rafael have two ways to write. For quick news — "it rained here today" — they send postcards. Each card stands alone; if one is lost, the next one carries newer news anyway, so nobody asks for it again.

For their shared story, a long tale they write together page by page, they use a stricter system. Before starting, Amara asks "shall we start a story? my pages start at number 1000", and Rafael replies "yes, and mine start at 5000". Every few pages Rafael sends a receipt: "I have everything up to page 1043; my mailbox has room for four more pages." If a receipt does not come in time, Amara copies the missing page again. And when Rafael's mailbox is full because he has not had time to read, Amara simply waits.

The postcards are UDP. The story is TCP. This chapter watches both at work, byte by byte, and ends with a download that was slow for a reason you can read straight from its packets.

What you will be able to do

  • Compare UDP and TCP: message boundaries, connections, reliability, ordering and what each costs.
  • Read a TCP connection in a capture: the three-way handshake, sequence and acknowledgment numbers, the window, and the close.
  • Explain retransmission, flow control (the receive window) and, in outline, congestion control.
  • Annotate a real capture against the RFCs (the course lab).
  • Diagnose a slow transfer from a capture that shows retransmissions and a small window (the course forensic lab).
Jargon box
UDP (User Datagram Protocol)
Simple words: a transport protocol that sends separate messages with no connection and no guarantees. Analogy: postcards. Precise: a transport protocol that adds ports, a length and an optional checksum to IP; each send is one datagram and each receive returns one whole datagram; no delivery, ordering or duplicate protection. D3 R1
TCP (Transmission Control Protocol)
Simple words: a transport protocol that gives two programs a reliable, ordered stream of bytes. Analogy: the numbered story with receipts. Precise: a connection-oriented transport protocol providing a reliable, in-order, full-duplex byte stream with flow control and congestion control, built on IP datagrams. D2
Segment (TCP)
Simple words: one TCP packet. Analogy: one page of the story. Precise: the TCP data unit: a TCP header (ports, sequence number, acknowledgment number, flags, window, checksum, options) and zero or more bytes of the stream. D2
Sequence and acknowledgment numbers
Simple words: numbers that count bytes, so each side knows exactly which bytes were sent and received. Analogy: page numbers, and the receipt "I have everything before page n". Precise: the sequence number is the stream position of a segment's first byte (SYN and FIN each count as one); the acknowledgment number is the next byte the sender of the ACK expects, which confirms every byte before it. D2 R3
Three-way handshake
Simple words: the three packets that open a TCP connection. Analogy: "shall we start?", "yes, shall we?", "yes". Precise: SYN (client's initial sequence number), SYN-ACK (server's initial sequence number and acknowledgment of the client's), ACK; options such as the maximum segment size and window scaling are agreed here. D2 R3
Receive window (flow control)
Simple words: how many more bytes the receiver can accept right now. Analogy: how many pages still fit in the mailbox. Precise: the window field of each segment advertises the amount of buffer space the receiver has free beyond the acknowledged byte; the sender may not have more unacknowledged data than that in flight. A zero window stops the sender. D2 R6
Retransmission
Simple words: sending data again because it was not acknowledged. Analogy: copying a page again when no receipt came. Precise: TCP resends unacknowledged data when its retransmission timer expires, or earlier when duplicate acknowledgments or selective acknowledgments indicate a loss (fast retransmit). D2 D5
Congestion control
Simple words: the sender slowing itself down so it does not overload the network between the two ends. Analogy: not posting more pages than the post office can carry this week. Precise: algorithms that limit the sender's data in flight by a congestion window, which grows while data is acknowledged and shrinks when loss (or other signals) indicates congestion; the sender uses the smaller of the congestion window and the receive window. D5
ICMP (Internet Control Message Protocol)
Simple words: IP's error-report messages. Analogy: the post office's "addressee unknown" slip. Precise: a protocol carried in IP datagrams that reports errors such as "destination unreachable (port unreachable)" back to the source. D4 R2

Layer 1 — the kid explanation

IP gets packets from one computer to another, but a computer runs many programs. The transport layer adds a port number so the packet reaches the right program, the way a name on an envelope reaches the right person in a house (F5-02). There are two main transport protocols, and they are very different. D1

UDP is like postcards. Each message travels alone. It might be lost, doubled or overtaken, and nobody is told. But it is simple and fast, and every message arrives whole or not at all. D3

TCP is like the numbered story with receipts. First the two programs agree to talk: three packets, the handshake. Then every byte gets a number. The receiver keeps sending receipts, "I have everything up to byte n". Missing bytes are sent again; bytes are put back in order; doubles are thrown away. The receiver also says how much room it has left, so a fast sender cannot flood a slow reader. The programs just see one long, tidy stream of bytes. D2

Layer 2 — the student explanation

UDP: datagrams with ports

A UDP header is 8 bytes: source port, destination port, length, checksum (F5-02 built one). D3 Each sendto produces one datagram and each recv returns exactly one datagram, so message boundaries are kept: Listing 1 sent three messages and the UDP receiver read three messages of 6, 7 and 7 bytes. R1 If no socket is bound to the destination port, the receiving host drops the datagram and may answer with an ICMP "port unreachable" message; the build captured exactly that (Listing 3), and on a connected UDP socket Linux reported it to the program as "Connection refused" on the next call. R2 D4 D6 On an unconnected socket the error is not reported, so a UDP sender usually never learns about losses at all.

TCP: a byte stream, not messages

TCP's service is a stream of bytes in each direction. The boundaries of your send calls are not preserved: Listing 1 sent three messages over TCP and the receiver got all 20 bytes from one recv. R1 D2 If your application has messages, it must mark them itself (a length prefix or a delimiter); F5-05 does this, and its forensic lab shows what happens when a client forgets.

Opening a connection

The client sends a segment with the SYN flag and its initial sequence number; the server answers with SYN and ACK, its own initial sequence number, and an acknowledgment number one higher than the client's (a SYN counts as one byte of sequence space); the client acknowledges that. D2 In the capture, the client's raw initial sequence number was 1491859865 and tshark printed it as relative 0; the server's was a different, unrelated number. R3 Initial sequence numbers are chosen so that they are hard to guess and do not collide with old connections. D2 The SYN segments also carry options: the maximum segment size each side can receive, selective acknowledgment permission, timestamps and a window scale factor. R3 D7

Sequence numbers, acknowledgments, retransmission

Every data byte has a sequence number. Segment 4 carries "hello\n" at relative sequence 1, length 6; the server's acknowledgment in segment 5 is 7, "I have everything before byte 7". R3 Acknowledgments are cumulative, so a receiver that gets bytes 1–6 and 13–18 but not 7–12 can only acknowledge 7, and then keeps doing so (duplicate acknowledgments); with selective acknowledgments it can also report the block it does have. D2 The sender keeps every unacknowledged byte. It retransmits when a timer, set from measured round-trip times, expires, or sooner when duplicate or selective acknowledgments show a gap. D2 D5

Flow control: the receive window

Each segment advertises the receiver's free buffer space in its window field. The 16-bit field alone would limit the window to 65,535 bytes, so a window scale factor agreed in the handshake multiplies it: in the capture, the raw field was 64 and the scale factor 1024, so tshark displayed Win=65536. R3 D7 The sender may have at most one window of unacknowledged data in flight. That gives the most important performance rule of TCP, used in F5-07 and in the forensic lab: one connection can move at most one window per round-trip time. D1

Congestion control in outline

The receive window protects the receiver; the congestion window protects the network. A TCP sender starts with a small congestion window, grows it quickly while acknowledgments arrive ("slow start"), then more cautiously, and cuts it when it detects loss; the amount in flight is limited by the smaller of the two windows. D5 The algorithms are the subject of many papers and of curriculum milestone C9, whose own stack starts with a simple Reno-style controller. S1

Closing, and refusing

Each direction is closed separately with a FIN, which also takes one sequence number; in the capture the client's FIN is at sequence 7 and the server acknowledges 8. R3 D2 A connection request to a port with no listener is answered with a reset (RST): Listing 3's SYN to port 7001 received "RST, ACK" within microseconds, and connect returned "Connection refused". R2 A connect that gets no answer at all — no RST, no SYN-ACK, as when a firewall drops the SYN — instead waits and retries until it times out; telling those two cases apart is a classic first diagnosis.

Choosing

Use TCP when every byte must arrive in order (files, web pages, chat messages, remote procedure calls). Use UDP when the application prefers fresh data to complete data (live audio, sensor streams, game state), when one request and one reply fit in one datagram (DNS, F5-06), or when the application builds its own reliability with different trade-offs. D1

Layer 3 — the engineer's depth

The connection state machine. RFC 9293 defines TCP as a state machine (LISTEN, SYN-SENT, SYN-RECEIVED, ESTABLISHED, FIN-WAIT-1 and -2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT, CLOSED). The side that closes first ends in TIME-WAIT for a while, so that late segments of the old connection are not mistaken for a new one; that is why a server restarted immediately may fail to bind its port unless it sets SO_REUSEADDR, as Listing 2 does. D2 D6

Round-trip time and the timer. A sender measures round-trip times (the timestamp option helps), keeps a smoothed average and a variation estimate, and sets the retransmission timeout from both, with a lower bound; after a timeout it backs off exponentially. D8 On loopback the round trip is microseconds, so the lower bound dominates: a loss that is only repaired by the timer costs far more than the round trip itself. In the forensic lab's capture every retransmission happened within about 3 ms of the original, and most within about 1 ms, which suggests the losses were repaired by acknowledgment signals rather than by a long timer. R6

Not verified — check before relying on this

The minimum retransmission timeout, the initial congestion window and the exact loss-recovery algorithms (fast retransmit and recovery, selective acknowledgment, tail loss probes, RACK) used by the Linux kernel of this build were not checked. Check RFC 6298 ("Computing TCP's Retransmission Timer"), RFC 5681 ("TCP Congestion Control") and the Linux kernel's TCP documentation (the tcp(7) manual page and the networking sysctl documentation) for the version in the run logs before quoting any value.

Head-of-line blocking. Because TCP delivers bytes in order, one lost segment holds back every later byte until it is repaired, even bytes that belong to an independent message. Protocols that multiplex many streams over one connection suffer from this, which is one motivation for designs that run their own reliability over UDP. D1

How the hardware actually does it

TCP and UDP run in the operating system kernel, not in the NIC, on ordinary computers: the kernel keeps the send and receive buffers, the timers and the state of every connection. D1 NICs help with checksums and segmentation offload (F5-02), and on receive with spreading packets of different connections over several queues, each with its own interrupt, so several CPU cores can process traffic in parallel. D1 DS401 studies network hardware that takes over far more of the transport work (RDMA). The size of the receive buffer that a program requests with SO_RCVBUF becomes, through the kernel, the receive window your peer sees: the forensic lab's run asked for 4096 bytes and the kernel reported 8192, and the window on the wire never exceeded 4096. R6 D6

Worked example

Follow the numbers of Figure 1 using the field dump below (R3), as you will in the lab.

  1. Segment 1, SYN: client's raw sequence number 1491859865 = relative 0.
  2. Segment 2, SYN-ACK: ack = 1, so the server confirms "the SYN at 0 is received; next I expect byte 1".
  3. Segment 4: seq = 1 (raw 1491859866 = 1491859865 + 1), length 6. The stream bytes 1–6 are "hello\n".
  4. Segment 5: ack = 7 = 1 + 6. Everything before byte 7 is received.
  5. Segment 6, the server's reply: its own seq = 1 (its SYN used 0), length 6; ack = 7 again, since the client sent nothing new.
  6. Segment 8, client FIN: seq = 7. Segment 9: the server's FIN at its seq 7, with ack = 8 (the client's FIN counted as one). Segment 10: ack = 8 for the server's FIN.
  7. Window: segment 3's raw window field is 64; the client announced window scale 1024 in segment 1; 64 × 1024 = 65,536, the "Win=65536" of the summary. R3

A rate bound for the forensic lab: with at most 4,096 bytes in flight and a round trip of r seconds, a connection moves at most 4096 / r bytes per second, no matter how fast the link is. With r = 1 ms, that is about 4 MB/s; the measured slow runs moved 2 MiB in about 0.64 s. R6

Where the analogy breaks


    

  1. Receipts count bytes, not pages. Rafael's receipts name pages; TCP acknowledges byte positions, and the "pages" (segments) can be cut differently on every retransmission. D2
    2. 

  2. Nobody says "the post office is full". The receive window is the reader's mailbox, but the network's capacity is never announced: TCP infers congestion from losses and delays, and can be wrong. D5
    3. 

  3. Postcards can be refused out loud. A lost postcard is silent; a UDP datagram to a closed port can come back as an ICMP error — but only a connected socket will tell the program (Listing 3). R2
    4.

Summary


    

  • Ports select programs. UDP adds only ports, a length and a checksum: one send, one datagram, no guarantees.
    • 

  • TCP gives a reliable, ordered byte stream: handshake, byte sequence numbers, cumulative acknowledgments, retransmission, close per direction.
    • 

  • TCP does not keep message boundaries; UDP does.
    • 

  • The receive window limits data in flight; at most one window per round-trip time.
    • 

  • Congestion control limits the sender further when the network seems overloaded.
    • 

  • No listener: TCP answers with RST; UDP may get ICMP port unreachable, reported only on connected sockets.
    • 

  • In a slow transfer, measure what retransmissions really cost before blaming the network; a small window can be the whole story.
    •

Forensic lab answer key


Observation: about 1,460 packets in about 0.64 s; 18 retransmissions; 18 zero-window advertisements; the client advertised windows of 4096, 2048 and 0 bytes only; the largest amount of data in flight was 4096 bytes; almost every data segment is marked "TCP Window Full"; every retransmission happened within 3 ms of the original, most within about 1 ms (the exact counts of the recorded run are in the evidence above). R6 Hypotheses: (H1, network team) packet loss causes the slowness; (H2) the receiver's tiny window limits the rate; (H3) the receiving application reads slowly. Testing H1: the "time since the original" of all 18 retransmissions adds up to about 20 ms of the roughly 640 ms: even if the connection had stood still during every repair, loss cannot explain the duration. Testing H2: with at most 4,096 bytes in flight per round trip, 2 MiB needs at least 512 round trips; the window repeatedly reaching zero shows the receiver's buffer, not the network, is full: the sender is waiting for the receiver. Controlled experiment (how the evidence was made, and the decisive test): the same program run four times, with a normal or a tiny receive buffer, with and without packet loss:




With a normal buffer the download takes milliseconds even with the same packet loss (run C); with the tiny buffer it is slow even without any loss (run B). Root cause: the logger sets a 4096-byte receive buffer (SO_RCVBUF, download.cpp with "small") and processes the data in 1 KiB pieces with work between them, so its window stays tiny and often closes; the loss is real but nearly free. Fix: remove the SO_RCVBUF call (let the kernel size and grow the buffer) or set it large enough for the bandwidth-delay product (F5-07); read in larger blocks and do the processing separately. Verification: a new capture shows windows of tens of kilobytes or more, no zero-window events, and a download time near run A's. Reply to the network team: "The capture shows 18 retransmissions, each repaired within 3 ms, about 20 ms in total, which explains at most a few percent of the time. The receiver advertised at most 4 KiB of window and closed it 18 times, so the server spent most of the download waiting for the logger. Please keep the switches; we are fixing the logger's receive buffer." How the evidence was injected: the loss by an iptables rule in a private network namespace (every 40th data packet from port 41000 dropped); the small window by the client's own SO_RCVBUF request (R6).
