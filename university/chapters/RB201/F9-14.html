Story hook

Joon rides in a team of six. They talk over one shared radio channel: only one rider can speak at a time, and when two start together, the one with the more urgent call keeps the channel. For months it works: "car behind", "turn left at the bridge", "slowing". Then a new rider joins with a gadget that reads his heart rate aloud to the channel, ten times a second, and his gadget's calls are marked as more urgent than "turn left".

On the first ride with him, the leader calls the turn. Nobody hears it. The channel is full of heart rates, the leader's call never gets a gap, and the team rides past the bridge. Every message that did go through was correct.

A robot's parts talk over buses in the same way. This chapter is about choosing a bus for each job, working out how full each bus is, giving messages the right priority, and finding out, before the robot drives, whether the important messages will always get through.

What you will be able to do

  • Choose a bus (I2C, SPI, UART, CAN, Ethernet, USB) for each connection of a robot from distance, data rate, number of devices and need for priority.
  • Compute the load of a bus from its message list, including protocol overhead, and check it against a design limit.
  • Assign CAN identifiers so that safety and control messages win arbitration, and explain what lower-priority messages experience when the bus is overloaded.
  • Open a SocketCAN socket on Linux and explain what the program needs from the system.
  • Diagnose starved messages and command timeouts from a CAN bus log after a new node was added.
Jargon box
Bus load
Simple words: how much of the time a bus is busy carrying messages. Analogy: how much of the time somebody is talking on the team radio. Precise: the sum over all message streams of (bits per message, including protocol overhead) × (messages per second), divided by the bus's bit rate; a design keeps it below a chosen limit so that delays stay short and there is room for growth. D2
CAN identifier priority
Simple words: on CAN, the message with the smaller number wins when two start together. Analogy: the more urgent call keeps the radio channel. Precise: during arbitration, nodes send their identifiers bit by bit; a dominant 0 overrides a recessive 1, so the lowest identifier wins without being damaged and the others retry when the bus is next idle (F1-47); identifiers therefore set message priority for the whole bus. D2
Worst-case frame length
Simple words: the longest a single CAN message can take on the wire. Analogy: the longest one call on the radio can last. Precise: for a classical CAN data frame with an 11-bit identifier and n data bytes, the bits of the frame plus the inter-frame space plus the most stuff bits the data could cause; this build's model uses 8n + 47 + ⌊(34 + 8n − 1)/4⌋ bits, 135 bits for 8 bytes (unverified, see the box). D3
Starvation (of a message)
Simple words: a message that never gets a turn because others always win. Analogy: the leader's "turn left" never finding a gap. Precise: on a priority-arbitrated bus that is fully loaded by higher-priority traffic, a lower-priority message waits indefinitely; unlike a slow bus, the delay is unbounded. D3
Command timeout
Simple words: a device stops on its own if commands stop arriving. Analogy: a rider who stops pedalling if he has heard nothing from the leader for too long. Precise: a receiver-side watchdog: if no valid command message has arrived within a stated time, the receiver goes to a safe state (for a motor driver: stop) and reports it; the timeout is longer than the command period by a chosen margin. S1
Bus termination
Simple words: resistors at the ends of a long bus cable that stop signals from bouncing back. Analogy: soft walls at the ends of a tunnel so that echoes do not drown the voice. Precise: resistors matching the cable's characteristic impedance placed at both physical ends of a differential bus such as CAN; their value and placement come from the bus standard and the transceiver's datasheet. D1
SocketCAN
Simple words: the way Linux lets a program send and receive CAN messages like network packets. Analogy: the radio's headset that plugs into the computer. Precise: the Linux CAN subsystem: CAN interfaces appear as network interfaces (for example can0), and a program opens a socket of family PF_CAN, type SOCK_RAW, protocol CAN_RAW, binds it to the interface and reads and writes struct can_frame (declared in linux/can.h). D5

Terms from earlier chapters used here: I2C, SPI, UART, baud rate, CAN, open-drain, logic analyser (F1-47); Ethernet frame (F1-51); utilisation, priority inversion (OS305); watchdog timer (F1-48).

Layer 1 — the kid explanation

The parts of a robot talk to each other through wires called buses. Some buses are for parts sitting close together on one board. Some are for one device talking to the computer. Some run all around the robot and many parts share them.

On a shared bus only one part can talk at a time. If too many parts talk too often, the bus is full, and some messages have to wait. On one kind of bus, called CAN, each message has a number, and the smaller number always goes first. That is good for important messages like "stop!", but it means a message with a big number may never get a turn if the bus is always full.

So engineers add up, before they build, how busy each bus will be, and they give the most important messages the smallest numbers.

Layer 2 — the student explanation

Choosing a bus for each job

Like a team choosing who speaks on which channel, a robot designer matches each connection to a bus by four questions: how far, how fast, how many devices, and does it need priorities (F1-47). D1 I2C (two open-drain wires, addressed devices) and SPI (clock, data and a select line per device) are for short links on one board, such as an IMU next to its microcontroller. A UART links two devices, often a sensor such as a LiDAR to the computer. CAN is a differential, multi-drop bus with priority arbitration, built for nodes spread over a machine in an electrically noisy place, such as motor drivers, battery and emergency-stop board. Ethernet and USB carry large data, such as a camera's images (F9-12). D2 D4

How full is each bus?

The load of a bus is the bits all its streams send per second, divided by its bit rate. The bits per message include the protocol's overhead: a CAN frame with 8 data bytes takes up to 135 bit times in this build's model, so its 64 data bits are less than half the frame; a UART byte in the common 8N1 format takes 10 bit times; an I2C register read takes 9 clocks per byte plus start and stop conditions. D2 D3 Listing 1 adds this up for the course robot's pretend message list: CAN 14.4 %, UART 63.0 %, I2C 41.1 % and Ethernet 77.0 %, which is over the team's 70 % design limit. R1 The limit is a design choice, not a law: it leaves room for retries, bursts and future messages, and on a priority bus it keeps lower-priority messages from waiting long.

Priorities on CAN

On CAN, the lowest identifier wins arbitration (F1-47). D2 So identifiers are a robot-wide priority plan: emergency-stop heartbeat lowest, then control (wheel commands, odometry), then status, then slow housekeeping like the battery. The guarantee is only as good as the load: once higher-priority streams alone need the whole bus, lower ones are starved, not just delayed. The forensic lab shows exactly that. R2 Every receiver of a control message should also have a command timeout, so that a starved command stream stops the motors instead of leaving them running on an old command. S1

CAN from Linux

On the robot computer, Linux's SocketCAN presents a CAN interface as a network interface; a program opens a raw CAN socket and reads and writes frames of type struct can_frame. Listing 2 tries to open such a socket; in the build container the kernel answers that the address family is not supported, which is the real answer of a machine without CAN support. D5 R3

Layer 3 — the engineer's depth

  • Response-time analysis. For CAN, the worst-case time from queuing to reception of each message can be computed from the message set (periods, lengths, identifiers), like the response-time analysis of fixed-priority CPU scheduling (OS305): blocking by one lower-priority frame already on the bus, interference from all higher-priority frames, and the frame's own length. The schedulability paper named in the unverified box gives the analysis and corrects an earlier, too optimistic version. D3
  • Errors and retransmission. CAN controllers detect errors and retransmit automatically, and a node with too many errors goes "bus-off" and stops sending; noise therefore adds load and can silence a node. Error counters are readable through SocketCAN and belong in the robot's health monitoring. D2 D5
  • I2C in practice. I2C has no enumeration: two devices with the same address on one bus cannot both work (F9-15); bus capacitance from long wires and many devices slows the edges and limits speed; a device that holds SDA low after a reset can hang the bus until the master clocks it free. D4
  • Higher layers. Robots often run a higher-layer protocol over CAN (for example CANopen) that fixes identifier ranges, heartbeats and timeouts; on Ethernet, robot middleware (RB303) adds its own overhead and its own QoS settings. Both change the numbers of Listing 1 and are taken from their specifications, not guessed. D2

How the hardware actually does it

A CAN node has a controller (often inside the microcontroller, or a separate chip on SPI) that builds frames, arbitrates, checks the CRC and counts errors, and a transceiver that turns the controller's logic levels into the differential CAN_H/CAN_L pair. During arbitration every transmitter reads the bus back while sending; a node that sends a recessive bit but reads a dominant one has lost and stops sending, which is why the winner's frame is not damaged. D2 On Linux, the controller's driver (for example for an SPI-attached MCP2515 or a built-in M_CAN, named in the curriculum's hardware catalog) registers a network device, and SocketCAN carries the frames between it and the sockets. D5

Worked example

Task. The course robot's CAN bus runs at 500 kbit/s with the base message set (14.4 % load). A new IMU board wants to send four 8-byte frames (accelerometer, gyroscope, magnetometer and temperature, status) at 1000 Hz each. (a) What load would it add? (b) What rate fits under a 70 % limit? (c) Which identifiers should it get?

  1. Frame time. 135 bits / 500,000 bit/s = 270 µs per frame. D3
  2. Added load. 4 × 1000 × 135 = 540,000 bit/s = 108 % of the bus: impossible on its own, before the existing 14.4 %.
  3. Rate that fits. Room under 70 %: 70 − 14.4 = 55.6 % = 278,000 bit/s; per stream 278,000 / (4 × 135) ≈ 514 Hz. At 100 Hz the board adds 10.8 % (total 25.2 %, confirmed by a scratch run of the forensic model: R4); if the robot needs 1 kHz inertial data, it should be processed on the IMU board's own microcontroller or sent over a faster link.
  4. Identifiers. Above the control messages (higher numbers than wheel_cmd's 0x300 and below housekeeping, for example 0x400–0x403), unless the team decides IMU data is more urgent than control, which is rarely right.
  5. Check the worst case. With the new rates, compute (or simulate) the worst latency of wheel_cmd and compare it with its 30 ms command timeout.

Where the analogy breaks


    

  • Riders can talk over each other and still be half heard; CAN nodes cannot. Arbitration is exact: one frame wins whole, the others wait whole. D2
    • 

  • A rider can decide a call is urgent in the moment; a CAN identifier is fixed by design. Priority is set when the identifiers are assigned, for every situation the robot will meet.
    • 

  • Point-to-point buses have no shared channel at all. A UART or SPI link has no arbitration; its limits are rate and distance, not priority.
    • 




Common mistakes and debugging


    

  • Symptom: after adding a node, some messages stop arriving. Cause: bus overloaded by higher-priority traffic. How to find it: bus load per identifier from a log (candump-style tools, or the forensic table). Fix: lower rates, reassign identifiers, or split the bus.
    • 

  • Symptom: CAN errors that come and go, worse with motors running. Cause: missing or extra termination, long stubs, noise. Fix: termination at the two ends only; short stubs; twisted pair; check error counters.
    • 

  • Symptom: an I2C sensor answers sometimes. Cause: two devices with the same address, weak pull-ups, long wires. Fix: address plan (F9-15), pull-ups sized for the bus, shorter wires.
    • 

  • Symptom: the UART LiDAR drops scans. Cause: load near 100 %, or baud rate mismatch. Fix: higher baud rate if both ends support it; check with a logic analyser.
    • 

  • Symptom: motors keep running after the controller crashes. Cause: no command timeout in the driver. Fix: configure and test the timeout; the hardware emergency stop stays the last line (F9-13).
    •

Summary


    

  • Choose buses by distance, data rate, number of devices and need for priority: I2C/SPI on a board, UART point-to-point, CAN across the robot, Ethernet/USB for large data.
    • 

  • Bus load = Σ (bits per message including overhead × rate) / bit rate; keep it under a stated design limit.
    • 

  • An 8-byte classical CAN frame takes up to about 135 bit times in this model (unverified): 270 µs at 500 kbit/s.
    • 

  • On CAN the lowest identifier wins: identifiers are the robot's priority plan.
    • 

  • When higher-priority traffic fills the bus, lower-priority messages starve; command timeouts must turn that into a safe stop.
    • 

  • Linux reaches CAN through SocketCAN; a raw socket is opened with PF_CAN, SOCK_RAW, CAN_RAW.

Forensic lab answer key


How the evidence was made. can_sched.cpp simulates a 500 kbit/s CAN bus with the base message set, then the same set plus four IMU messages at 1000 Hz with identifiers 0x100–0x103, each frame given its worst-case length of 135 bits. The motor drivers' firmware is not modelled at all: the change is only the added traffic. All values pretend.


Root cause. The IMU board alone needs 4 × 1000 × 135 = 540,000 bit/s, 108 % of the bus. Its identifiers are below every control and status message except the emergency-stop heartbeat (0x080), so whenever the bus is free an IMU frame wins; status, odometry, wheel commands and battery are sent 0 times in 2 s; the wheel driver's 30 ms timeout fires 66 times (the motors twitch and stop); the battery display freezes. The heartbeat still gets through because 0x080 wins, and even imu_status (0x103) is sent only 1360 of 2000 times.


Wrong answers. "Driver firmware": the drivers receive no commands at all, which the log shows before any firmware is involved. "Wiring": the IMU frames arrive perfectly. "Broken battery node": it is starved like the others.


Fixes. Reduce the IMU board's rate to what the bus can carry: at 100 Hz the load is 25.2 % and every message is sent with no timeouts (R4); and give the IMU identifiers below the control messages' priority (for example 0x400–0x403), which alone is not enough (R4: still 100 % load, battery starved). If high-rate inertial data is needed, process it on the IMU board or carry it on another bus.


Prevention. Every new node comes with its message list (sizes, rates, identifiers); the bus budget and the model are re-run before connecting it, with the design limit and every timeout checked; the robot's health monitor reports bus load and timeouts per identifier.
