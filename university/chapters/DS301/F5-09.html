Story hook

Bao phones Amara: "Please add my ten books to the club's list." Amara says "Sure, writing it now", and the line goes dead. Did she write it? Bao cannot know. If he phones again and asks again, and she had already written it, the list now says twenty books. If he does not phone again, and the line dropped before she heard him, the books are not on the list at all.

The next time, Bao is smarter. He says: "This is request number 7 from Bao: add my ten books." Amara writes "done: Bao #7" in the margin. When the line drops and Bao calls back with "request number 7 from Bao", Amara looks at the margin, sees it is done, and says "already done". Now calling back is safe.

A phone call that asks a friend to do something is the registered analogy for a remote procedure call. This chapter builds one over TCP, and then meets the dropped line in all its forms.

What you will be able to do

  • Explain what an RPC system does: stubs, marshalling, framing over a byte stream, request ids, and how replies find their requests.
  • Build a small RPC library over TCP in C++ and add a procedure to it, with a defined wire format in network byte order.
  • Explain why an RPC is not a local call: latency, partial failure, no shared memory, and the meaning of a timeout.
  • Choose between at-most-once and at-least-once semantics, and make a non-idempotent operation safe to retry with duplicate detection.
  • Diagnose a duplicated operation from client and server logs and identify which part of the retry design failed.
Jargon box
Remote procedure call (RPC)
Simple words: asking a program on another computer to run a function for you and send back the answer. Analogy: phoning a friend and asking her to do something (registered F5 mapping). Precise: a communication pattern in which a client invokes a named procedure with arguments on a server by sending a request message and waiting for a reply message carrying the result or an error; libraries make it look like a local function call. D2 D1
Stub
Simple words: a small function that looks like the real one but actually sends a message. Analogy: the note Bao reads from when he phones, so every call is asked the same way. Precise: the client-side function (client stub) that marshals arguments into a request, sends it and unmarshals the reply; the server-side counterpart (server stub or skeleton) unmarshals the request and calls the implementation. Often generated from an interface description. D2
Marshalling
Simple words: turning the function's arguments into bytes that can travel, and back. Analogy: spelling a name letter by letter on the phone so it arrives exactly. Precise: encoding typed values into a defined byte representation (field order, sizes, byte order) for a message, and decoding them on the other side; the RPC form of serialisation (SP201). D2 D1
Framing
Simple words: marking where one message ends and the next begins in a stream of bytes. Analogy: saying "end of message" at the end of each request on the phone. Precise: a convention that delimits messages within a byte stream such as a TCP connection, here a 4-byte big-endian length before each message; needed because TCP preserves the order of bytes but not message boundaries (F5-04). D4 R1
Request id
Simple words: a number on every request so its answer and any repeat can be recognised. Analogy: "this is request number 7 from Bao". Precise: an identifier chosen by the client, unique per client, carried in the request and echoed in the reply; the pair (client id, request id) identifies one logical operation across retries. D2
Idempotent operation
Simple words: an operation that has the same effect whether you do it once or several times. Analogy: "set my count to ten books" (safe to repeat) versus "add ten books" (not safe). Precise: an operation f with f(f(state)) = f(state) for the same arguments; repeating it after an unknown outcome cannot change the result. D2 D1
At-least-once and at-most-once
Simple words: either "keep asking until you get an answer, even if it happens twice" or "ask once, even if it may not happen". Analogy: phoning back after a dropped line versus never phoning back. Precise: RPC semantics under failure: at-least-once retries until a reply arrives, so the procedure may execute more than once; at-most-once never executes a request twice, either by not retrying or by detecting duplicates at the server; "exactly-once" effects are obtained by at-least-once delivery plus duplicate detection or idempotence. D2
Timeout (RPC)
Simple words: how long the caller waits for an answer before deciding something went wrong. Analogy: how long Bao listens to silence before hanging up. Precise: a bound after which the client stops waiting for a reply; it tells the client only that no reply arrived in time, not whether the server executed the request. D1 R2

Layer 1 — the kid explanation

Analogy

A remote procedure call is a phone call that asks a friend to do something and waits for her answer. Mapping: the caller = client; the friend = server; the request "please add ten books" = the request message; "done" = the reply; the agreed way to spell names and numbers = marshalling; "this is request number 7 from Bao" = the request id; listening to silence and hanging up = the timeout. The registered warning: if the line drops, you do not know whether she did it.

When you call a function in your own program, it always runs and always returns (or the whole program stops). When you call a function on another computer, three new things can happen: the request can be lost, the answer can be lost, or the other computer can be slow or broken. From the caller's side, all three look the same: silence. Most of this chapter is about what to do with that silence.

Layer 2 — the student explanation

The parts of an RPC system

An RPC system makes a call to another process look like a local function call D2. The pieces, all present in Listing 1 (rpc.hpp):

  • Client stub. A function with the procedure's signature, for example add(client, a, b) in Listing 2. It marshals the arguments, sends the request, waits for the reply and unmarshals the result D2.
  • Marshalling. Writer and Reader encode 8-bit, 32-bit and 64-bit integers and length-prefixed strings in big-endian order ("network byte order"), independent of how the machine stores them in memory (endianness, serialisation, SP201). The request for add(2, 40) is 31 bytes: client id 1, request id 1, the string "add" (length 3, then the bytes 61 64 64), then the two 64-bit integers 2 and 40 (0x28) R1.
  • Framing. TCP delivers a stream of bytes, not messages: one recv may return part of a message or parts of two D4 (F5-04, F5-05). Each message is therefore preceded by its length in 4 bytes, and readFrame reads exactly that many bytes, looping over recv. The 1 MiB argument in Listing 2 arrives in many pieces and the checksum still matches R1.
  • Server stub and dispatch. The server reads a frame, unmarshals the client id, request id and method name, looks up the handler in a table, runs it, and marshals a reply with the same request id, a status byte and the result. An unknown method produces an error reply, not a crash: "no such method: multiply" R1.
  • Matching replies to requests. The client keeps waiting until a reply with its request id arrives; replies with other ids are late answers to abandoned requests and are dropped (stale_ in Client::call).

Why a remote call is not a local call

The library hides the network, but four differences remain, and each must be visible in the calling code D1 D2:

  1. Latency. A local call costs nanoseconds; a remote one costs at least a network round trip (F5-07) plus marshalling. A loop that makes one RPC per item is a design error that a local call would hide.
  2. Partial failure. The call can fail in ways a local call cannot: the server may be down, the connection may break, or no reply may come. The stub must report these as errors that the caller handles.
  3. No shared memory. Arguments are copied into the message. Pointers and references mean nothing on the other machine; a "pass by reference" must become "send the value, and send back the new value".
  4. Independent evolution. Client and server are often built and deployed separately; the message format must be readable by older and newer versions (Layer 3).

What a timeout tells you

A timeout says only one thing: no reply arrived within the time you chose. It does not say whether the request was lost, whether the server executed it and the reply was lost, or whether the server is still working on it D1. Scenario A of Listing 3 shows this: the client gives up after 200 ms and must report "the deposit MAY OR MAY NOT have happened"; in fact it did, and the late reply arrives later and is dropped R2.

At-most-once, at-least-once, and making retries safe

After a timeout the client has two choices D2:

  • Do not retry (at-most-once by giving up): the operation runs zero or one times; the caller must cope with not knowing which.
  • Retry (at-least-once): send the request again until a reply arrives; the operation runs one or more times.

Retrying is harmless if the operation is idempotent: "set the balance to 100" or "read the balance" can run twice with the same effect. "Add 100 to the balance" is not: scenario B retried once and the balance became 200 although one deposit was intended. Worse, the client received a reply saying "balance 100" (the late reply to its first attempt), so the client's view and the server's state now disagree R2.

The remedy is to make each logical operation recognisable: the client sends the same (client id, request id) on every retry, and the server keeps a reply cache from that pair to the reply it already sent. A duplicate is answered from the cache without executing. Scenario C: "duplicate, saved reply sent again, NOT executed", balance 100 R2. At-least-once delivery plus duplicate detection gives the effect of exactly-once execution, as long as the reply cache itself survives as long as retries can arrive. That last condition is what the forensic lab is about.

Layer 3 — the engineer's depth

The reply cache is state, and state has a lifetime

Duplicate detection only works if the server still remembers the request when the duplicate arrives. Three design questions follow D2:

  • Scope. Keyed by what? If the cache is tied to a connection, a client that reconnects before retrying (a common retry policy) gets a fresh, empty cache. Key it by a client identity that outlives connections.
  • Lifetime. How long is an entry kept? Forever is a memory leak. A common rule is that the client promises not to retry requests older than some id or time (for example by sending "I have received all replies up to id n" with each request), and the server discards entries below that.
  • Durability. If the server crashes and restarts, an in-memory cache is gone, and a retry after the restart executes again. If exactly-once effects must survive crashes, the cache entry must be stored atomically with the effect (in the same transaction, or in the same replicated log, DS302).

Choosing timeouts, and retrying without making things worse

A timeout shorter than the server's normal slow case turns slowness into duplicate work; one far longer makes the client wait for a dead server. The value should come from the measured latency distribution of the call (its p99 or p99.9, F5-07, F5-08), not from a guess D1. Retries add load exactly when a server is already slow, so a retry policy needs a limit on attempts, a growing delay between attempts with some randomness (so that many clients do not retry in lock-step), and, ideally, a deadline that travels with the request so that servers can drop work whose caller has already given up. F5-11 returns to timeouts as failure detectors.

Interface definitions and evolving message formats

Our stubs are written by hand and the format is implicit in their code. Production RPC frameworks generate stubs from an interface description written in an interface definition language (IDL), and their encodings tag each field so that a newer server can read an older client's message (ignoring unknown fields, using defaults for missing ones) and the reverse D1 D2. Our format has no version and no field tags: adding a third argument to add would break every deployed client. The lab's extension adds a version field.

Not verified — check before relying on this

This chapter names no production RPC framework, IDL or encoding, and states nothing about their wire formats, generated APIs, timeout defaults or retry behaviour: none of their documentation was opened in this build. If a lab or project uses one, its version and documentation (the framework's own guide and the encoding's specification) must be recorded in the dossier first. The concepts above (stubs, IDL, field tags, schema evolution) are cited to D1 and D2, pending verification.

Design choices in Listing 1, and their limits

  • The server handles one connection at a time (serve). A real server would use one thread per connection, a thread pool (SP203), or poll over many sockets (as F5-05 does). With one thread, a slow procedure blocks every other client: in scenario B the retried request waited behind the slow first one.
  • A frame length above 64 MiB is rejected (readFrame), so a corrupted or hostile length cannot make the server allocate gigabytes.
  • send uses MSG_NOSIGNAL so that writing to a connection the client has closed produces an error instead of the SIGPIPE signal that would terminate the process D4; the server then ends that connection and continues.
  • Errors raised by a handler are caught and sent as error replies: a bad request must not take down the server for everyone.

How the hardware actually does it

In this lab client and server are threads of one process on one machine, talking through the loopback interface: the kernel's TCP implementation moves the bytes from one socket's send buffer to the other's receive buffer without any network card (F5-05). Between machines, the same bytes are cut into segments, wrapped in IP packets and Ethernet frames, and handed to the network interface controller, which moves them by DMA between memory and the link (HW205, F5-03). Marshalling to big-endian exists because processors store multi-byte integers in different orders (endianness); the build machine is x86-64, which is little-endian, so Writer::u32 really does reverse the byte order in memory.

Not verified — check before relying on this

Untested on real hardware: every run in this chapter used the loopback interface of one cloud container; no packet crossed a physical network, and no message was lost by the network (loss and delay were injected by the program). The behaviour of the library across two machines, under real packet loss, and with a peer that disappears without closing the connection (power loss) was not tested. A peer that vanishes silently leaves the client waiting until its own timeout; how long TCP itself waits before reporting a broken connection depends on kernel settings documented in the Linux tcp(7) manual page, which was not opened in this build. To test: two machines or two virtual machines, and a tool that drops packets (DS201 used a private network namespace for this, F5-04).

Worked example

Decode the request bytes printed by Listing 2 by hand, then predict the server's actions for scenario B.

The bytes (after the 4-byte frame length, which is 00 00 00 1f = 31) are R1:

00 00 00 01   client id = 1
00 00 00 01   request id = 1
00 00 00 03   method name length = 3
61 64 64      "a" "d" "d"   (ASCII 0x61 0x64 0x64)
00 00 00 00 00 00 00 02   first argument  = 2
00 00 00 00 00 00 00 28   second argument = 0x28 = 2 × 16 + 8 = 40

4 + 4 + 4 + 3 + 8 + 8 = 31 bytes. The reply is 4 (id) + 1 (status) + 8 (result) = 13 bytes; its result field is 00 … 00 2a = 42.

Scenario B, step by step (timeout 200 ms, injected server delay 300 ms on the first deposit):

  1. t = 0: the client sends deposit(100), id 1. The server executes it (balance 100), then sleeps 300 ms before replying.
  2. t = 200 ms: no reply; the client retries with the same id 1. The bytes wait in the server's receive buffer (the server is single-threaded and still sleeping).
  3. t ≈ 300 ms: the server sends the reply to the first request (balance 100). The client is waiting for id 1, so it accepts it: "attempt 2 -> reply, balance 100".
  4. The server reads the retried request. Without a reply cache it executes again: balance 200, and sends a second reply with id 1.
  5. The client's next call (balance, id 2) first receives that second reply for id 1, drops it as late, then receives id 2: balance 200.

Compare with retry.out: the recorded lines match each step R2. Note step 3: the reply the client accepted was not the reply to the request it had sent last. With identical ids that is harmless for an idempotent call and misleading for this one.

Where the analogy breaks


    

  • On the phone you hear the line drop. A TCP connection to a machine that lost power may look open for a long time; the client learns nothing until its own timeout fires (see the unverified box above).
    • 

  • A friend who heard "request number 7" twice would remember it without a notebook. A server remembers only what the code stores, for as long as the code stores it, and forgets everything in memory when it restarts.
    • 

  • A phone call is between two people. RPC replies can arrive late, after the caller has moved on to another request on the same connection; the request id, not the order of speaking, ties a reply to its request.
    • 

  • Friends share a language. Two versions of a program may not: a newer client may send a message the older server cannot parse (Layer 3).
    •

Summary


    

  • An RPC sends a request message naming a procedure and arguments and waits for a reply; stubs, marshalling and framing make it look like a call.
    • 

  • TCP is a byte stream: frame messages with a length and loop over partial reads and writes.
    • 

  • Define the byte order and layout in the protocol; never send in-memory representations.
    • 

  • A remote call differs from a local one in latency, partial failure, copied arguments and independent versions.
    • 

  • A timeout means "no reply yet", never "it did not happen".
    • 

  • Retries give at-least-once execution; for non-idempotent operations, add a reply cache keyed by a client identity and request id, with a defined scope, lifetime and durability.

Answers to Check yourself


    

  1. Stub marshals client id, request id, method name and arguments; the framing layer prepends the length; the socket sends the bytes; the server's framing layer reads the length and the body; the server stub unmarshals, looks up "add" in its handler table and calls it.
    2. 

  2. TCP delivers bytes in order but not message boundaries: one recv may return half a message or the end of one and the start of the next. Without a length (or another delimiter), the server cannot know where a request ends; large messages would be cut and parsed as garbage.
    3. 

  3. (a) yes; (b) yes; (c) no; (d) no (each repeat appends another line); (e) yes in effect (the second delete finds nothing), although it may return a different status ("not found"), which the client must treat as success. Distractor: (e) looks unsafe because the reply differs; idempotence is about the state, not the reply.
    4. 

  4. A timeout only means no reply arrived in time; the server may have executed the deposit (scenario A shows it did). Better: "no reply within 200 ms: the deposit may or may not have been made; check the balance or retry with the same request id".
    5. 

  5. Each attempt has a new id, so the server's cache sees different requests and executes each: the seat may be booked several times (or the later attempts fail with "already booked", confusing the client). The id must identify the logical operation, so it must stay the same across retries.
    6. 

  6. With 150 ms the first reply arrives before the 200 ms timeout: all three scenarios print one attempt with "reply, balance 100", no dropped late replies, balance 100; the server executes the deposit once in each. (A scratch run made while writing this chapter printed exactly this; it is not one of the recorded lab runs. On a heavily loaded machine the 50 ms margin could be lost.)
    7. 

  7. More than 1 % of calls (all those slower than 50 ms, which is most of the tail and probably much more) time out and are retried, adding load exactly when the server is slow; the slowdown grows, more calls time out, and the server can collapse under retries. Timeouts must be set from the measured distribution, with limited retries and backoff.
    8.

A lifetime (when an entry can be discarded, for example after the client acknowledges later replies) and a scope that outlives connections (client identity, not connection); for crash safety, durability with the effect. Without a lifetime the cache grows forever; without the right scope, reconnecting defeats it; without durability, a restart does.

Forensic lab answer key


Observation. Client: "deposit id=1 attempt=1: timeout; closing connection, reconnecting", then attempt 2 succeeded with "new balance 200". Server: request 7/1 executed on connection 1, connection 1 ended, connection 2 opened, request 7/1 executed again R3.


Hypotheses. (1) The client did not reuse the id: ruled out, both server lines say 7/1. (2) Duplicate detection was not enabled: ruled out by the configuration line, and the server would not have needed a second connection to show it. (3) The reply cache does not survive the end of a connection: consistent with "connection 1 ended" between the two executions and no "duplicate" line on connection 2. (4) The server restarted between the attempts and lost an in-memory cache: ruled out, the log shows no restart, only a new connection.


Root cause. The reply cache is scoped to a connection (Dedup::perConnection in rpc.hpp, line 284: the table is cleared when a new connection is accepted). The client's retry policy opens a new connection before retrying, so the retry meets an empty cache and executes again.


Fix. Server: key the cache by client identity and keep it across connections (Dedup::global), with a lifetime rule. The client could avoid it by retrying on the same connection, but reconnecting after a timeout is a legitimate and common policy (the old connection may be broken), and other clients may do it; the server must not depend on it. If balances must survive server restarts, store the cache entry with the balance change.


Test. An integration test with an injected slow reply and a client that reconnects before retrying, asserting the balance is 100 (lab step 5).


How the evidence was produced. reconnect.cpp: server with Dedup::perConnection and a 300 ms injected delay on the first deposit; client 7 with a 200 ms timeout that closes and reopens the connection before each retry; output unedited.
