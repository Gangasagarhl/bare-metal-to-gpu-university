Story hook

The club grows to forty thousand books. No notebook holds the catalogue any more, so the friends split it: Amara keeps books whose titles start with A–H, Bao I–P, Chidi Q–Z. Each town now holds a third of the catalogue and answers a third of the questions. Then a new member, Dara, joins in a fourth town. How do you give her a share? Moving the letter boundaries is easy on paper and means re-copying thousands of entries.

A year later the club runs a summer reading challenge, and every member asks about the same book, "Pebble and the Sea". All the letters go to Bao's town. Bao is overwhelmed while Amara and Chidi are idle. The friends try splitting the catalogue into more, smaller parts. Bao is still overwhelmed: one book cannot be split by splitting the catalogue.

This chapter is about splitting data over machines (partitioning, or sharding): how to choose which machine holds which key, what moves when machines are added, and why one popular key defeats any number of machines.

What you will be able to do

  • Explain why systems partition data, and how partitioning combines with replication.
  • Compare range partitioning, hash-mod-N partitioning and consistent hashing by data movement, balance and range-query cost, using the lab's recorded numbers.
  • Calculate the fraction of keys that move when N changes, and explain virtual nodes.
  • Diagnose a hot spot from per-shard load and key samples, and choose a remedy that works.
  • Describe what becomes harder across shards: secondary indexes, multi-key transactions and request routing.
Jargon box
Partitioning (sharding)
Simple words: splitting a big dataset into parts that live on different machines. Analogy: each town keeps the part of the catalogue for its own range of letters (proposed). Precise: dividing a dataset so that each record belongs to exactly one partition (shard), and placing partitions on different nodes, so that storage and load are spread; usually combined with replication of each partition. D1
Shard (partition)
Simple words: one of the parts. Analogy: Bao's letters I–P. Precise: a subset of the dataset, defined by a range of keys or a set of hash values, stored and served as a unit and moved as a unit during rebalancing. D1
Range partitioning
Simple words: each part holds keys between two boundaries, like the volumes of an encyclopaedia. Analogy: A–H, I–P, Q–Z. Precise: assigning each partition a contiguous range of sorted keys; range queries touch few partitions, but keys that arrive in order (timestamps, counters) all go to the last partition. D1 R1
Hash partitioning
Simple words: each key goes to the part chosen by a hash of the key, which scatters keys evenly. Analogy: each title is turned into a number by a fixed recipe, and the number decides the town. Precise: assigning a key to a partition by a function of hash(key), for example hash(key) mod N or a position on a hash ring; spreads keys evenly but destroys key order, so range queries must ask every partition. D1 R1
Consistent hashing
Simple words: a way of hashing keys to machines so that adding a machine moves only the keys it takes over. Analogy: towns sit at points around a circle of numbers; each book goes to the next town clockwise from its own number; a new town takes books only from its clockwise neighbour. Precise: keys and nodes are hashed onto the same circular space; a key is owned by the first node point at or after its hash; adding or removing a node moves only the keys in the affected arcs, about 1/N of them. D6 D1 R1
Virtual node
Simple words: letting each machine sit at many places on the circle, so that the shares even out. Analogy: each town gets a hundred small arcs around the circle instead of one big one. Precise: one of V positions on the hash ring assigned to the same physical node; more virtual nodes reduce the variance of each node's share and spread a joining or leaving node's load over many others. D6 R1
Rebalancing
Simple words: moving parts between machines when machines are added, removed or overloaded. Analogy: re-copying catalogue pages to Dara's town when she joins. Precise: changing the assignment of keys or partitions to nodes while the system keeps serving requests, moving as little data as possible and keeping load balanced afterwards. D1
Hot spot (hot key)
Simple words: one key or part that gets far more requests than the rest. Analogy: everyone asking about "Pebble and the Sea". Precise: a partition whose load is disproportionately high because of skew in the workload, often a single popular key; partitioning by key cannot spread the load of one key, since every request for it goes to the same partition. D1 R2
Request routing
Simple words: finding which machine holds the key you want. Analogy: knowing which town to write to for a given title. Precise: the mechanism that sends a request to the node owning its key: any node forwards, a routing tier forwards, or clients know the partition map; all need an up-to-date map, often kept in a coordination service. D1

Layer 1 — the kid explanation

Analogy

When the catalogue is too big for one notebook, the friends split it, and each town answers questions about its own part. Splitting by letters keeps neighbouring titles together, but if all new books start with the same letter, one town gets all the work. Splitting by a number made from each title spreads the books evenly, but then neighbouring titles live in different towns. And if everyone wants the same book, splitting does not help at all: that book still lives in one town. Mapping: catalogue = dataset; one town's part = shard; the letter ranges = range partitioning; the number recipe = hash function; everyone asking about one book = hot key.

Partitioning answers "where does this key live?". Replication (F5-12) answers "how many copies of it are there?". Real systems use both: each shard is replicated.

Layer 2 — the student explanation

Why partition

Replication copies all the data to every replica, so it does not help when the data is too large for one machine or the write load is too high for one primary. Partitioning gives each node a fraction of the data and of the load D1. Two goals compete: spread data and load evenly (no hot spots), and keep the operations that the application needs (range scans, multi-key updates) within as few partitions as possible.

"Imbalance" is the most loaded node's share divided by the average share; 1.00 is perfect. "All to the new node: yes" is the defining property of consistent hashing: no key moves between two old nodes D6.

Hot spots

Hashing balances keys, not requests. If one key receives a large share of the requests, its shard receives that share whatever the number of shards D1. The forensic lab measures exactly this: 35 % of requests for one post kept one shard at 43 % of the load with 8 shards and 39 % with 16 R2. Remedies change the key, not the shard count: split a hot key into k sub-keys on different shards (writes go to a random sub-key, reads combine all k), cache reads of hot keys, or aggregate increments locally before sending them D1.

Layer 3 — the engineer's depth

Rebalancing strategies

Besides consistent hashing, a common scheme creates many more partitions than nodes from the start (a fixed number, for example ten times the expected node count) and assigns whole partitions to nodes; adding a node moves some whole partitions to it, and the key-to-partition mapping never changes D1. Range-partitioned systems instead split a range when it grows too large and move one half. Either way, rebalancing moves data while requests continue, so the system needs a protocol for the hand-over (copy, catch up, switch ownership, redirect clients) and must not lose writes that arrive mid-move. Automatic rebalancing interacts dangerously with failure detection (F5-11): a node that is slow, not dead, can trigger moves that add load to it and its neighbours, making things worse D1.

Request routing

Someone must map a key to a node: the client library, a routing tier, or any node that forwards. All of them need the current partition map, and during rebalancing the map changes. Systems keep the authoritative map in a small, strongly consistent coordination service (built on consensus, DS302) and let routers cache it; a request routed with an old map must be rejected or forwarded by the node that no longer owns the key D1. That is the fencing idea of F5-11 applied to ownership: the map has an epoch number, and nodes reject requests from older epochs.

What becomes harder across shards

  • Secondary indexes. "All books by author X" cannot be answered from the partition key. A local index on each shard means every query asks every shard (scatter-gather, with the tail-latency cost of F5-08); a global index partitioned by the indexed term makes reads cheap and writes touch several shards D1.
  • Multi-key operations. A transfer between two accounts on different shards needs both to commit or neither: an atomic commit protocol, which DS302 builds on consensus.
  • Consistency. Each shard can be linearizable (F5-13) without the system as a whole giving a consistent snapshot across shards; reads that span shards may see one shard's write and not another's.

Choosing the hash

Placement hashes must give the same answer on every machine and in every version of the software; a language's built-in hash for strings may be randomised per process or change between versions. The lab defines its hash by its arithmetic (64-bit FNV-1a with a final mixing step) for that reason. The raw FNV-1a low bits are poorly mixed for keys that differ only in their last characters, which is why the lab adds a mixing step before taking a remainder.

Not verified — check before relying on this

The statements about FNV-1a's weak low bits and about language hash functions being randomised are given from the author's memory; no specification was opened in this build. Which scheme a particular database uses, and how it rebalances, are product facts for its documentation (AH-22). The imbalance numbers of Listing 1 are for this hash, these key names and one seed-free placement: other key sets give different numbers.

How the hardware actually does it

A partition is ultimately bytes on a storage device and work for a CPU and a network card. Moving a shard copies its data over the network, competing with client traffic for the same links and disks; a rebalancing that moves 80 % of the data (hash mod N) can saturate them for a long time, which is the practical reason consistent hashing and fixed partitions exist D1. The same idea appears inside a single machine: memory addresses are interleaved over banks and channels by a function of the address bits (HW205), and a hash table spreads keys over buckets (DS201); in both, a skewed access pattern concentrates load exactly as the hot key does here.

Not verified — check before relying on this

Untested on real hardware: no data was moved between machines and no shard served real requests; shard load in the forensic lab is a count of simulated requests. Rebalancing time, network and disk saturation were not measured.

Worked example

Why does hash mod N move 80.0 % of keys from 4 to 5 nodes, and 91.0 % from 10 to 11?

  1. A key stays if h mod 4 = h mod 5. Both remainders are determined by h mod 20 (the least common multiple).
  2. For h mod 20 = r, h mod 4 = r mod 4 and h mod 5 = r mod 5. They are equal for r = 0, 1, 2, 3 (both equal r) and for no other r below 20 (the next is r = 20).
  3. So 4 of every 20 hash values stay: 20 % stay, 80 % move, if hashes are spread evenly. Recorded: 80.0 % R1.
  4. For 10 → 11: the least common multiple is 110, and h mod 10 = h mod 11 exactly for r = 0, …, 9: 10 of 110 stay, 9.1 %; 90.9 % move. Recorded: 91.0 %, the difference being sampling over 100,000 keys.
  5. In general from N to N + 1, about N/(N(N + 1)) = 1/(N + 1) of keys stay, so nearly all move, while only 1/(N + 1) would need to (the new node's share).

Where the analogy breaks


    

  • Letters of the alphabet are known in advance. Real keys arrive over time, and a range scheme must split ranges as they fill.
    • 

  • Friends can phone each other to ask "who has this book?". Machines need a partition map that is itself replicated and updated consistently.
    • 

  • Moving a few catalogue pages is quick. Moving a shard of a large dataset can take hours and loads the network and disks while the system keeps serving.

Summary


    

  • Partitioning spreads data and load; replication copies each partition.
    • 

  • Ranges keep order (cheap scans) but concentrate time-ordered writes; hashing spreads keys but scatters ranges.
    • 

  • hash mod N moves almost everything when N changes (80.0 % and 91.0 % recorded); consistent hashing moves about 1/(N + 1), all to the new node.
    • 

  • Virtual nodes even out shares (imbalance 1.85 → 1.04 from V = 1 to 1000).
    • 

  • A hot key defeats any number of shards; change the key, cache, or batch.
    • 

  • Routing needs an up-to-date, epoch-numbered partition map; cross-shard indexes and transactions cost extra coordination.
    •

Forensic lab answer key


Observation. Before the change, seven shards carried about 4,800–4,940 requests per minute and shard 2 about 25,850 (43 %); after doubling, the normal shards halved to about 2,400, and shard 2 dropped only to about 23,400–23,700 (39 %) R2.


Cause. The key sample: post:7781203 received 21,144 of the 23,692 requests on shard 2 at 12:06, 35 % of all 60,000 requests; the next keys have 2 each. One key carries 35 % of the load, and every request for it goes to its one shard. The shard's load is 35 % + 65 %/N: 35 + 8.1 = 43 % with 8 shards, 35 + 4.1 = 39 % with 16 shards, matching the log. Hypothesis "uneven hashing" is ruled out by the other shards being equal within a few percent and by the doubling having halved them.


With 64 shards. 35 + 65/64 ≈ 36 %. The limit as N grows is 35 %: no number of shards takes load away from one key.


Fixes. Split the counter for this post into k sub-counters with keys like post:7781203#0 … #k−1 on different shards; increments go to a random sub-counter, reads sum all k (a likes count tolerates a slightly stale sum, F5-13). Or batch increments in the front ends and send one "+n" per second. Monitoring: per-shard load alone shows "where"; a top-keys sample per shard shows "what", and an alert on "one key above x % of a shard's requests" would have pointed to the key at 12:01.


How the evidence was produced. hotshard.cpp: 60,000 requests per minute, each for the hot post with probability 0.35, otherwise for a uniformly random post among 9 million; FNV-1a with mixing, mod 8 for minutes 1–3 and mod 16 for 4–6; key sample on the busiest shard at minute 6. Fixed seed; output unedited.
