Story hook

Analogy

Grandpa Yusuf has made jam. On the kitchen shelf there are 10 spots for jars, numbered 0 to 9 with little stickers. Twelve cousins want to help. Hana organises them in 3 teams of 4, and gives each cousin a ticket with the formula from F0-16: ticket = team × 4 + seat.

"Ticket 0 fills spot 0, ticket 1 fills spot 1, and so on," says Hana. The cousins line up. Tickets 0 to 9 each fill a jar. Then Ravi, holding ticket 10, walks to the end of the shelf. There is no spot 10. His jar would land on the floor.

Hana adds one rule to the ticket: "Before you fill, check: is your ticket less than 10? If not, you have no jar today. Help by cheering." Ravi and the cousin with ticket 11 cheer loudly.

That one line, "is my number inside the allowed range?", is called a bounds check. It protects every list in every program, including the GPU programs at the end of this road.

What you will be able to do

  • Read and write inequalities with <, >, ≤, ≥ and ≠, and draw them on a number line.
  • Describe an allowed range such as 0 ≤ i < 10, and count the whole numbers in it.
  • Solve simple inequalities such as 2x + 1 < 9, like equations, and know the one rule that differs.
  • Apply the full helpers plan: teams = (n + size − 1) ÷ size, ticket = team × size + seat, work only if ticket < n.
  • Diagnose an off-by-one error caused by ≤ where < was needed.
Jargon box
Inequality
Simple words: a statement that one amount is bigger or smaller than another. Analogy: a balance scale that is tipped, not level. Precise: a statement using < (less than), > (greater than), ≤ (less than or equal to), ≥ (greater than or equal to) or ≠ (not equal to), such as x + 3 ≤ 7. D1
Allowed range
Simple words: all the numbers that are permitted, from a lowest to a highest. Analogy: the jar spots that exist on the shelf: 0 to 9. Precise: the set of values satisfying one or more inequalities, for example 0 ≤ i < 10, which for whole numbers is 0, 1, … , 9. D1
Bounds check
Simple words: checking that a number is inside the allowed range before using it. Analogy: "is my ticket less than 10?" before walking to the shelf. Precise: a test such as if (i < n) that guards every use of position i in a list of n items numbered from 0. D1R1
Off-by-one error
Simple words: a mistake that makes a count or a range one too big or one too small. Analogy: letting ticket 10 walk to a shelf that ends at 9. Precise: an error at the edge of a range, for example using ≤ where < is needed (or the reverse), or counting the ends of a range wrongly. D1R3

Layer 1 — the kid explanation

An equation says two amounts balance. An inequality says the scale is tipped: one side is bigger. In F0-11 you met the sign <. Now you meet its whole family.

SignRead it asExample that is true
<is less than3 < 10
>is greater than10 > 3
≤is less than or equal to10 ≤ 10
≥is greater than or equal to4 ≥ 2
≠is not equal to9 ≠ 10

The open side of < and > always faces the bigger number. The extra line under ≤ and ≥ means "or equal". That tiny line decides whether the end number is allowed.

Allowed ranges

Often only some numbers make sense. Grandpa's shelf has spots 0 to 9. A ticket must be at least 0 and less than 10. We write both at once: 0 ≤ i < 10. This is an allowed range.

Figure 1 draws it on a number line. A filled dot at 0 means 0 is allowed. An empty circle at 10 means 10 is not. For whole numbers, the range holds 0, 1, 2, … , 9. That is exactly 10 numbers, one for each jar.

Here is the pattern to remember. A list of n things numbered from 0 uses the range 0 ≤ i < n. The last number is n − 1, and there are exactly n of them. With ≤ instead of <, you would get n + 1 numbers: one too many.

The bounds check

Now the cousins. There are 10 jars and teams of 4. From F0-12 you know to round up: 3 teams, 12 helpers. Two helpers more than jobs. That is normal and fine.

Each helper works out a ticket from F0-16: ticket = team × 4 + seat. Then each helper asks one question: is my ticket less than 10? If yes, fill that spot. If no, do nothing. This question is a bounds check. Figure 2 shows it saving tickets 10 and 11 from the end of the shelf.

Notice the three ideas working together. Rounding up makes sure there are enough helpers. The ticket formula gives every helper a different number. The bounds check stops the extra helpers. Drop any one of them and something breaks.

Solving an inequality

You can solve many inequalities like equations. Do the same thing to both sides. For x + 3 ≤ 7, take 3 from both sides: x ≤ 4. For 2x + 1 < 9, take 1 from both sides, then halve: x < 4. The whole numbers that work are 0, 1, 2 and 3.

There is one surprise. If you multiply or divide both sides by a negative number, the sign flips round. Layer 2 explains why.

Ranges at home

Allowed ranges are everywhere once you look. Mei's home-made card game is for 2 to 8 players: 2 ≤ p ≤ 8. Five players is inside. Nine is outside. Grandma says "at least 2 vegetables on your plate": v ≥ 2.

Layer 2 — the student explanation

Inequalities stay true if you add or subtract the same number on both sides, or multiply or divide both sides by the same positive number. Multiplying or dividing by a negative number reverses the order, because it reflects the number line about 0: 2 < 3, but −2 > −3. So −2x > 6 becomes x < −3 after dividing by −2. Check with whole numbers: x = −4 gives 8 > 6, true; x = −3 gives 6 > 6, false. D1R2

Ranges that include the start but not the end, like 0 ≤ i < n, are called half-open. Their great virtue is that they hold exactly n whole numbers, and two ranges such as 0 ≤ i < 4 and 4 ≤ i < 8 fit together with no gap and no overlap. That is why programmers number from 0 and test with <. D1R2

"How many teams?" is really an inequality. We need the smallest whole number b with b × 256 ≥ 1,000. Try b = 3: 768, too few. b = 4: 1,024, enough. So b = 4, which is exactly (1,000 + 255) ÷ 256 in whole-number division: the rounding-up formula of F0-12 is the solution of this inequality. D1R2

Layer 3 — the engineer's depth

Note

For the curious. Nothing here is needed for the quiz.

This chapter's three steps are the skeleton of the first GPU program in this university. The guide's exemplar chapter F6-01 adds 1,000 elements with blocks of 256 threads: it launches (1,000 + 256 − 1) ÷ 256 = 4 blocks, each thread computes i = blockIdx.x * blockDim.x + threadIdx.x, and it checks i < n before touching memory, so that the 24 extra threads do nothing. Now you can read every part of that sentence. U1R2

In C++, reading or writing a std::vector element with [] at a position outside 0 ≤ i < size is not checked by the language; the program's behaviour is then undefined, which can mean wrong results far away from the mistake. That is why every listing in this university is built with sanitizers that report such errors when they happen, and why the bounds check is written by the programmer. B2U1

How the hardware actually does it

A list in a program sits in memory as items side by side, each at its own address (F0-15). Memory does not end where your list ends: the next addresses belong to other data. So a helper with ticket 10 would not "fall off a shelf"; it would quietly write into somebody else's spot. Nothing in the hardware shouts. The bounds check in the code is what keeps each helper inside its list. B1B2

Worked example

All numbers below are recomputed by checks.cpp (run R2), shown at the end.

Part A — counting a range

  1. 0 ≤ i < 10 with whole numbers: 0 to 9, which is 10 numbers.
  2. 0 ≤ i ≤ 10: 0 to 10, which is 11 numbers: one more.
  3. An egg tray with cups 0 to 11: 11 − 0 + 1 = 12 cups, so 0 ≤ i < 12.

Part B — the jam shelf

  1. Teams: (10 + 4 − 1) ÷ 4 = 13 ÷ 4 = 3 (whole-number division).
  2. Helpers: 3 × 4 = 12. Tickets 0 to 11.
  3. Bounds check ticket < 10: tickets 0 to 9 work, 10 and 11 do nothing. Idle: 12 − 10 = 2.

Part C — the GPU sizes

  1. 1,000 jobs, teams of 256: (1,000 + 255) ÷ 256 = 4 teams, since 3 × 256 = 768 is too few and 4 × 256 = 1,024 is enough.
  2. Helpers 1,024; idle 1,024 − 1,000 = 24.
  3. Edge check: team 3, seat 231 has ticket 3 × 256 + 231 = 999, the last job, so it works. Team 3, seat 232 has ticket 1,000: not less than 1,000, so it does nothing.

Part D — solving

x + 3 ≤ 7 gives x ≤ 4. 2x + 1 < 9 gives 2x < 8, so x < 4: whole numbers 0, 1, 2, 3.

Where the analogy breaks


    

  • A shelf has a visible end; memory does not. A jar past the end of a shelf falls and you see it. A write past the end of a list lands silently on other data. That is why the check must be in the code.
    • 

  • Cousins can think; helpers in a program cannot. Ravi saw there was no spot 10 and stopped. A program helper does whatever its code says. If the code has no check, it does not stop.
    • 

  • A shelf has no spot −1; a calculation can produce −1. A ticket worked out by subtracting can go below zero (F0-14). A full check of 0 ≤ i < n tests both ends; the GPU formula's tickets start at 0, which is why the guide's example tests only i < n.
    •

Goal


Play the helpers-and-jobs game with real cups and tickets, then use the lab program to plan bigger jobs, including the "1,000 jobs, teams of 256" case.


Hardware and software needed


Ten cups or jars (or ten squares drawn on paper) labelled 0 to 9; twelve paper tickets; a pencil; some small objects to put in the cups. Optional: a computer with a C++ compiler; this build used g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0.

None beyond normal care at home. Use unbreakable cups or paper squares, not glass jars.

Forensic lab answer key


    

  1. "helper ticket 10 works on job 10": there is no job 10. The total "jobs done: 11" follows from it.
    2. 

  2. Hypothesis A: the tickets are wrong (for example, two helpers got the same ticket, or a ticket skipped). Hypothesis B: the tickets are right but the bounds check lets one too many through.
    3. 

  3. The tickets run 0 to 11 exactly once each, as in Figure 2, so A is ruled out. The change of behaviour happens between 10 (works) and 11 (no job), so the check's boundary is wrong: B.
    4. 

  4. "ticket ≤ 10" lets 10 through and stops 11. The correct check is "ticket < 10" (in code, ticket < jobs).
    5. 

  5. Writing to position 10 of a 10-item list would land outside the list, on whatever data comes next in memory, without any warning from the hardware. Prevention: always use the half-open pattern 0 ≤ i < n, test the edge cases n − 1 and n, and build with sanitizers.
