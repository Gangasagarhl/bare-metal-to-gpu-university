Story hook

Bao keeps the club's books, Dalia keeps the club's records, and Chidi has the only good printer. In most clubs you would have to learn three different ways of asking: a phone call for books, a form for records, a visit for printing. Bao's town library had a better idea. Everything there is asked for with the same five or six kinds of letter: "find this", "open it", "read me this part", "write this part", "I am finished with it". The library even gives you a numbered bookmark for each thing you are using, so your next letter can say "bookmark 3, read the next page" instead of the whole path again.

Dalia's own club tried something different: instead of a list of members, every member gets a card printed with what it allows ("may read", "may borrow"), and the card has a seal that only the club can make. Whoever holds the card has the rights; nobody needs to check a list.

Two research operating systems of the 1980s and 1990s took these two ideas as far as they would go. Plan 9 made every resource a file and every file reachable with one small protocol, 9P. Amoeba made every resource an object on some server, named and protected by an unforgeable capability. In this chapter your kernel will speak real 9P to a real 9P server, and you will model Amoeba's capabilities and Plan 9's private name spaces, so that you can judge which ideas your own cluster should keep.

What you will be able to do

  • Explain Plan 9's three central ideas (resources as files, one file protocol, per-process name spaces) and Amoeba's (a processor pool, objects on servers, sparse capabilities), and compare each with the single-system image of F5-44.
  • Encode and decode 9P messages byte by byte, and run a complete 9P session (version, attach, walk, open, read, create, write, clunk) from your own kernel over a legacy virtio transport.
  • Read a server-side protocol trace together with the client's log and match every request to its reply by tag.
  • Model capabilities with a check field and show by experiment that rights cannot be widened by editing bits.
  • Diagnose a failed walk from a hex dump and an error reply.
Jargon box
Plan 9 (from Bell Labs)
Simple words: a research operating system in which every resource on every machine is a file, reached with one protocol. Analogy: a town where every service, from books to printing, answers the same kinds of letter. Precise: a distributed operating system built at Bell Labs in which terminals, CPU servers and file servers share resources through the 9P file protocol, and each process assembles its own name space from local and remote file servers. D1
9P
Simple words: Plan 9's small protocol for using files on another machine. Analogy: the library's six kinds of letter: find, open, read, write, stat, finished. Precise: a request–reply file protocol in which each T-message (request) is answered by an R-message (reply) or Rerror with the same tag; messages are size[4] type[1] tag[2] followed by type-specific fields, little-endian; 9P2000 is the classic revision, 9P2000.u and 9P2000.L are Unix and Linux extensions. D3 D9
Fid
Simple words: a small number the client picks to stand for one file it is using on the server. Analogy: a numbered bookmark the library keeps for you. Precise: a 32-bit handle, chosen by the client, that the server associates with a file in the client's session from attach or walk until clunk; most 9P requests name a fid instead of a path. D3
Tag (9P)
Simple words: the number that matches a reply to its request. Analogy: the reference number written on a letter and repeated on the answer. Precise: a 16-bit request identifier chosen by the client, unique among its outstanding requests and copied by the server into the reply, allowing many requests in flight on one connection; NOTAG (0xFFFF) is used only by Tversion. D3
Qid
Simple words: the server's unique identity for a file. Analogy: the library's own shelf number, which stays the same even if the book is renamed. Precise: a 13-byte value of type[1] (directory, append-only and other bits), version[4] (changes when the file changes) and path[8] (unique per file on that server); two files are the same file exactly when their qids' paths are equal. D3
Per-process name space
Simple words: each program has its own private map from path names to files. Analogy: each friend arranges their own shelf of borrowed books, from any library, in their own order. Precise: in Plan 9, a mount table per process (group) built with bind and mount, so that the same path can name different files in different processes; union directories let several directories appear at one path. D2
Amoeba
Simple words: a research distributed operating system in which programs run on a pool of processors and every resource is an object kept by some server. Analogy: a club where any free member does a job and every item has a sealed card instead of a member list. Precise: a distributed operating system from the Vrije Universiteit Amsterdam and CWI, built around a microkernel, a processor pool, RPC between clients and object servers, and capabilities for naming and protection. D4
Capability (sparse)
Simple words: an unforgeable ticket that names an object and says what its holder may do. Analogy: a tamper-proof club card that says "may read". Precise: a bit string containing a server port, an object number, a rights field and a check field derived from a server-held secret with a one-way function, so that holders can pass it on but cannot raise its rights or guess a valid one; "sparse" because valid values are a tiny fraction of the possible ones. D5
Processor pool
Simple words: a set of computers with no owner that the system hands out for running programs. Analogy: whichever friend is free does the next job. Precise: in Amoeba, processors not attached to users' terminals, allocated to processes by the system at run time, so that the user's view is of one large computer rather than of personal machines. D4
Virtqueue (split)
Simple words: the shared memory rings through which a virtual device and its driver pass buffers. Analogy: an in-tray and an out-tray between you and the library clerk. Precise: a descriptor table, an available ring written by the driver and a used ring written by the device, in guest memory; the driver queues chains of descriptors and notifies the device, the device returns finished chains with the number of bytes it wrote. D7

Terms from earlier chapters used here without redefinition: virtio, descriptor (virtio), remote procedure call, idempotent operation, single-system image, transparency.

Layer 1 — the kid explanation

Analogy

Bao's library answers only a few kinds of letter. You write "please find atlas and call it bookmark 1"; the library answers "found, bookmark 1 is the atlas". Then "open bookmark 1 for reading", "read bookmark 1 from page 0, up to 512 words", "I am finished with bookmark 1". Every letter has a reference number, and the answer repeats it, so if you send several letters at once you know which answer is which. Mapping: library = file server; letter = 9P message; bookmark = fid; reference number = tag; "find" = walk; "finished" = clunk; the library's own shelf number = qid.

Because every service in that town answers the same letters, you can borrow anything from anyone the same way: books from Bao, records from Dalia, even the printer from Chidi ("write these pages to the printer"). And every friend can arrange their own shelf from any libraries they like: Amara can put Dalia's records next to her own and see them as one shelf.

Dalia's club does it the other way round. You do not ask by name; you show a card. The card says which item and what you may do, and it carries a seal only the club can make. You can give your card to a friend, but you cannot change "may read" into "may borrow", because the seal would no longer match.

Layer 2 — the student explanation

Plan 9 in three ideas. First, resources are files: the network, the window system, processes and devices appear as file trees that are read and written. Second, every file server speaks one protocol, 9P, whether it is a disk server across a network or a driver inside the kernel. Third, every process has its own name space, built by binding file trees from any servers into its own view of the path tree. D1 D2 Together they give a different kind of single-system image from F5-44's: not one global view for everyone, but a uniform way for each process to assemble the view it needs, from whatever machines provide it.

The 9P session. A client first sends Tversion to agree on a protocol version and the largest message size (msize). Then Tattach makes a fid stand for the root of a served tree. Twalk moves along path names from one fid to a new fid; Topen opens a fid; Tread and Twrite move bytes at an offset; Tclunk tells the server the fid is no longer needed. Each request carries a tag, and the reply carries the same tag. D3 The lab's kernel does exactly this against QEMU's server (Listing 3), and QEMU's trace shows the server's side of each message (R2).

Why the lab uses 9P2000.u. The kernel first offers classic "9P2000"; QEMU's server answers "unknown" (R2). The second offer, "9P2000.u", is accepted. The .u (Unix) extension adds numeric user ids and error numbers to some messages, so the kernel's Tattach carries an extra n_uname field and Rerror carries an errno after the error string. QEMU's server is built for Linux guests, whose 9P client uses 9P2000.u or 9P2000.L. D9 R2

Amoeba in three ideas. First, a processor pool: users' workstations are terminals, and processes run on processors the system picks. Second, objects on servers: files, directories and processes are objects managed by server processes, used through RPC. Third, capabilities: every object is named and protected by a capability, which the holder presents with each request. D4 D5 Amoeba's single-system image is closer to F5-44's: the user sees one computer, and the system decides where things run.

Capabilities without a protected kernel table. In a single machine, capabilities can live in kernel memory where users cannot touch them. Across a network a capability is only bits in a message. Amoeba's answer was to make capabilities sparse: the check field is derived from a secret with a one-way function, so that a holder cannot compute the check for any other rights, and guessing a valid one is hopeless. D5 The lab's model (Listing 4) shows the two properties by experiment: editing the rights bits makes the check fail, and none of a million random check fields is accepted (R5).

What to keep for our cluster. From Plan 9: one small, explicit file protocol with fids and tags (F5-46's DFS copies its shape), and the idea that a name space is a per-process choice, not a global fact. From Amoeba: the processor pool as a scheduling model (F5-47's scheduler places jobs on any node) and capabilities as a way to pass rights around without a central list.

Layer 3 — the engineer's depth

The 9P message format. Every 9P message begins size[4] type[1] tag[2]: size counts the whole message including itself, all integers are little-endian, and strings are a 2-byte length followed by UTF-8 bytes without a terminating zero. D3 The lab's Twalk, from the hex dump in the forensic output, decodes field by field:

BytesFieldValue
1c 00 00 00size[4]28 bytes in total
6etype[1]110 = Twalk

00 00 00 00fid[4]0 (the root, from attach)
01 00 00 00newfid[4]1

09 00 then 9 byteswname[s]"Hello.txt" (forensic run) or "hello.txt" (session)

4 + 1 + 2 + 4 + 4 + 2 + 2 + 9 = 28: the size checks. Rwalk returns one 13-byte qid per element walked; walking zero names clones a fid, which the lab uses to make fid 2 a second handle on the root before Tcreate turns it into the new file (R2). D3

Fids make the server stateful. After a walk the server remembers what fid 1 means for this client. That makes requests short and lets the server keep an open file's state, but it also means a server crash loses every client's fids, and a client crash leaves fids the server must eventually free. F5-46 returns to this choice; NFS's original design went the other way (stateless server, file handles that survive reboots). D6

Tags and flush. Because each request carries a tag, a client may have many outstanding requests on one connection and match replies in any order. Tflush asks the server to abandon a request; the reply to Tflush means the old request will not be answered (or already was). D3 The lab sends one request at a time, but call() still prints the tag of each reply so that you can see they match.

Qid versions and caching. A qid's version changes when the file changes. A client cache can therefore ask "is the version I cached still current?" with a cheap stat request instead of re-reading the data. The lab's qids carry versions such as 1791597927 for hello.txt; QEMU's local back end derives them from the host file's metadata, which is an implementation detail of QEMU, not of 9P (R2). F5-46 uses exactly this idea for its own cache and shows what happens without it.

Not verified — check before relying on this

Historical and design details of Plan 9 and Amoeba in this chapter come from memory of their papers, not from documents opened in this build: Plan 9's origin at Bell Labs and its terminal / CPU server / file server split; the bind and mount operations and union directories; the use of 9P inside the kernel for devices; Amoeba's origin at the Vrije Universiteit and CWI, its Bullet file server and directory server, its FLIP protocol and group communication; the layout of Amoeba capabilities (server port, object number, rights, check) and how restricted capabilities are made with a one-way function. The Source Researcher must check each against D1, D2, D4 and D5 before the chapter is published.

Capabilities, more carefully. The lab model gives each object a random 64-bit secret on the server. The owner capability carries all rights and the secret itself as check. A restricted capability with rights r carries check = f(secret XOR r), with f one-way. The server validates by recomputing; anyone holding a capability can ask the server for a weaker copy, never a stronger one. In the run the reader's capability (rights r--, check 3d0b935add44d570) passes for reading, is refused for writing, and its forged copy with rights rw- and the same check is refused because the check no longer matches (R5). The model's f is a mixing function, not a cryptographic one: it shows the shape of the scheme, not its strength. Three properties follow, and each is a design choice to weigh:

  • Delegation is free. Passing a capability needs no server call, so any process can share access without asking.
  • Revocation is hard. Once a capability is copied, the only way to cancel it is to change the object's secret, which cancels every capability for that object.
  • Secrecy is the protection. A capability seen on the wire can be replayed by anyone; the network must keep capabilities confidential, or they must be bound to their holder.

Plan 9's name spaces, more carefully. The lab's model (Listing 5) builds two processes' name spaces. Both bind a local root, union the file server's /bin after the local one, and bind the server's /usr. Process 2 then binds a gateway's /net over its own. The output shows the effect: /net/tcp names "this terminal's TCP stack" for process 1 and "the gateway's TCP stack" for process 2, while every other path agrees (R6). The cluster lesson: a single global name space is one option, not the only one. Names that differ per process are a feature when they are chosen on purpose, and a debugging trap when they are not (two processes "opening the same file" and getting different ones).

Transport choices. Plan 9 ran 9P over its own network protocols and over pipes; Linux runs it over TCP, over virtio, and over other transports. D9 9P itself assumes a reliable, ordered transport that delivers whole messages. The lab's virtio transport is exactly that (one request, one reply buffer). F5-46 puts a 9P-like protocol over the cluster's raw Ethernet, where frames can be lost, and has to add retries, and with them the question of what a retried request means.

How the hardware actually does it

The lab uses no network card. QEMU's virtio-9p-pci device, with disable-modern=on, appears as a legacy ("transitional") virtio PCI device with vendor 0x1AF4 and device 0x1009, whose registers are I/O ports in BAR0. The kernel's driver (Listing 1) resets the device, acknowledges it, accepts only feature bit 0 (the device has a mount tag), reads the queue size (128 in the run), lays out a split virtqueue in a 4,096-byte-aligned buffer, tells the device the page frame number of that buffer, and sets DRIVER_OK. It then reads the mount tag "ds403share" from the device-specific configuration at offset 0x14 (R2). D7 D8

For each 9P request the driver writes two descriptors: descriptor 0 points at the request and is chained (NEXT) to descriptor 1, which points at the reply buffer and is marked WRITE (the device writes it). It puts descriptor 0's index in the available ring, increments the available index, writes 0 (the queue number) to the notify register, and polls the used ring's index until it changes; the used entry gives the number of bytes the device wrote. There is no interrupt, no second request in flight, and no memory barrier stronger than a compiler barrier, which suffices on one emulated x86 CPU but would not be enough on every real system. D7

Not verified — check before relying on this

The legacy virtio register offsets (host features 0x00, guest features 0x04, queue address 0x08, queue size 0x0C, queue select 0x0E, queue notify 0x10, device status 0x12, device configuration 0x14 without MSI-X), the split-ring layout (16-byte descriptors, available ring after the table, used ring on the next 4,096-byte boundary), the device id 0x1009 for 9P, the feature bit for the mount tag, and the configuration layout (tag length then tag) were written from memory of the OASIS VIRTIO specification's legacy interface and 9P transport sections. They were confirmed only by the driver working with QEMU 8.2.2 (R2). Check them in the specification, and prefer the modern (virtio 1.x) interface for new work.

On the other side, QEMU's 9P server is part of QEMU itself: with -fsdev local,path=export it serves the host directory with the QEMU process's own permissions, and security_model=none passes ownership and mode bits through without mapping. The -trace v9fs_* option enables QEMU's trace events for its 9P server, which print each request and reply as the server sees them. D8

Safety

A 9P export gives the guest read and write access to the exported host directory with the permissions of the user running QEMU. Export only a dedicated, empty directory, as the lab does; never export your home directory or a source tree you have not backed up.

Worked example

Question. Using only the session output, account for every byte of the Rread reply and check its size against QEMU's trace.

Step 1: find the request. The kernel sent Tread tag 4 with fid 1, offset 0 and count 512 (the trace line v9fs_read tag 4 id 116 fid 1 off 0 max_count 512 confirms each field).

Step 2: the reply format. Rread is size[4] type[1] tag[2] count[4] data[count]. D3 The file holds 31 bytes ("hello from the host side of 9P" plus a newline), less than 512, so count = 31.

Step 3: add it up. 4 + 1 + 2 + 4 + 31 = 42 bytes. The kernel printed <- Rread tag 4 (42 bytes), and QEMU's trace says count 31 err 42: in QEMU's trace the last number of a read return is the reply's total size, not an error (R2).

Step 4: where the data is. The data starts at offset 4 + 1 + 2 + 4 = 11, which is why Listing 3 prints rep[11 + i].

Step 5: the same for Rerror. In the forensic run the reply is 38 bytes: 7 header bytes, a 2-byte string length 0x19 = 25, the 25 bytes "No such file or directory", and the 4-byte errno 2 of 9P2000.u: 7 + 2 + 25 + 4 = 38 (R4).

The habit this example trains, adding up every field until the size matches, is the fastest way to find encoding bugs in any protocol you implement.

Where the analogy breaks


    

  • A library remembers bookmarks forever; a 9P server forgets them when it restarts. Fids are server state. After a server reboot every bookmark number is meaningless, and a client that keeps using them gets errors or, worse, another client's new file.
    • 

  • A sealed card cannot be photocopied; a capability can. Paper seals resist copying. A capability is bits: anyone who sees it on the network can use it. Sparse capabilities stop forging, not copying.
    • 

  • Letters are read by people who ask when something is unclear. A 9P server does exactly what the bytes say. A wrong size field or a name with a capital letter is not "nearly right" (the forensic lab).
    • 




Common mistakes and debugging


    

  • No reply at all. Cause: DRIVER_OK not set, wrong queue address (not shifted by 12), or the used ring placed where the device does not expect it. Find it: QEMU's trace prints nothing for the request. Fix: check the layout against the queue size the device reported.
    • 

  • Rversion says "unknown". Not a bug in the encoding: the server does not speak the offered version (R2). Fix: offer one it does; record which one you got.
    • 

  • Fields shifted by a few bytes in every later message. Cause: a string written with a terminating zero, or a .u field missing (n_uname in Tattach, extension in Tcreate). Find it: add up the sizes (worked example) and compare with the trace's field values.
    • 

  • "No such file or directory" for a file you can see. Cause: a different name (case, a trailing newline from a command line, a path with a slash in one wname). Find it: the hex dump of the walk. This is the forensic lab.
    • 

  • Files appear owned by the wrong user on the host. Cause: the security model; with security_model=none the host file belongs to the QEMU user, and the guest's uid is not mapped. Fix: choose the model on purpose; read QEMU's fsdev documentation.
    • 

  • Server state grows forever. Cause: fids never clunked. Fix: clunk on every path, including errors; in a long-lived client keep a table of open fids.
    • 




Transition box

Where you came from: F5-44 built membership and two cluster services over raw Ethernet, and showed that a single-system image leaks under partial failure. What carries over: request ids that match replies (the cps round number is 9P's tag), bounded waits, polled devices with descriptor rings. What changes: most dangerous first: the server now keeps state for each client (fids), so a crash on either side leaves the other with stale state; the transport (virtio) is reliable here, which hides the retry problem F5-46 must face; and names may differ per process. Summary


    

  • Plan 9: resources are files, one protocol (9P) reaches all of them, and each process builds its own name space from local and remote trees.
    • 

  • Amoeba: a processor pool, objects on servers reached by RPC, and sparse capabilities for naming and protection.
    • 

  • A 9P message is size[4] type[1] tag[2] plus fields, little-endian; fids are client-chosen handles to server state; tags match replies to requests; qids identify files and carry versions.
    • 

  • QEMU 8.2.2's 9P server refused "9P2000" and accepted "9P2000.u", which adds numeric ids and errnos.
    • 

  • Capabilities make delegation free, revocation hard, and secrecy of the bits essential.
    • 

  • Per-process name spaces are a powerful alternative to one global name space, and a debugging trap when used by accident.
    • 

  • Adding up a message's fields until the size matches is the quickest check of any protocol encoding.
    •

  5. Making the owner capability needs the secret; going from f(secret XOR r) back to the secret means inverting f, which a one-way function makes infeasible. The lab's f is an invertible mixing function (each step can be undone), so a determined attacker could recover the secret; the model shows the shape only.
    6. 

  6. Capabilities fit "give one node read access to one file for one job": the giver asks for a read-only copy and passes it; no server list changes. Cost: revocation means changing the secret, and the capability must not be seen on the network. Name spaces decide what a process sees, not what it may do, so they help with isolation but not with delegation; using both (a capability to mount, a name space to arrange) is a reasonable design.
