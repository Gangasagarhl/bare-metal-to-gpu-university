Story hook

Amara, Bao, Chidi and Dalia live in four different towns, and together they run one book club. They want the club to feel like a single clubhouse. A caller can phone any of them and ask "which books do we have?" or "please lend me the atlas", and the answer must be the same as if all the shelves stood in one room. So each friend keeps a list of who is "in" the club this week, and they send each other a short letter every day: "still here".

It works well until Chidi's letters stop. Is Chidi ill, on holiday, or is the post slow this week? Nobody can tell from a silent letterbox. A caller asks Amara for the full list of books, and Amara has to decide: wait for Chidi's shelf, or answer without it and say so. The clubhouse that "feels like one room" is really four rooms joined by letters, and the joins show the moment one of them goes quiet.

This chapter is about that clubhouse for computers: the single-system image, the old and attractive idea that many machines can look like one. You will build the first layer of it on top of your own kernel, on three emulated PCs, and you will watch exactly where the illusion breaks.

What you will be able to do

  • Explain the single-system image idea, the kinds of transparency it promises, and the difference between a distributed operating system, a network operating system and middleware.
  • Build a membership service from heartbeats and a suspicion timeout in a freestanding kernel, and read its view changes from logs.
  • Implement two single-system-image services over raw Ethernet (a cluster-wide process list and remote execution) and measure what leaks through the illusion when a node stops.
  • Calculate how the availability of "the whole cluster" depends on whether a design needs every node or only a majority.
  • Diagnose a flapping membership view from three nodes' logs and fix its configuration.
Jargon box
Single-system image (SSI)
Simple words: many computers that look, to their users and programs, like one computer. Analogy: four friends' rooms that callers experience as one clubhouse. Precise: the property of a distributed system that presents one set of names, processes, files and devices, so that users and programs need not know which machine holds what; the degree to which this holds is described by the transparencies it provides. D1
Transparency (distributed systems)
Simple words: hiding a fact about the many machines from the user. Analogy: the caller does not hear which friend's shelf the book came from. Precise: hiding a property of distribution: access (local and remote use look the same), location (names do not say where), migration and relocation (things may move), replication (copies look like one), concurrency (sharing looks private), failure (crashes are masked). Full transparency is neither always possible nor always wise. D1
Distributed operating system
Simple words: one operating system spread over many machines. Analogy: one club rulebook that every friend follows in the same way. Precise: an operating system whose kernels on all machines cooperate to manage the machines' resources as one system, usually with one name space and one process model; contrasted with a network operating system and with middleware. D1
Network operating system
Simple words: separate computers, each with its own operating system, that can use each other's services. Analogy: four separate clubs that lend each other books on request. Precise: independent operating systems on each machine, joined by services such as remote login and remote files that the user invokes explicitly; each machine keeps its own names and processes. D1
Middleware
Simple words: a software layer above ordinary operating systems that makes many machines easier to use together. Analogy: a shared club notebook kept on top of four separate homes. Precise: a layer between applications and the (network) operating systems that provides distribution services such as remote calls, messaging, naming and coordination, without changing the kernels. D1
Membership view
Simple words: one node's current list of which nodes are in the cluster. Analogy: each friend's own list of who is "in" this week. Precise: in this course, the set of node ids a node believes alive, computed from messages received within a suspicion timeout and numbered so that changes are visible; different nodes may hold different views at the same moment. D2 R2
Suspicion timeout
Simple words: how long a node waits without news before it removes another node from its view. Analogy: how many days without a letter before you stop counting a friend in. Precise: the time after the last message from a peer at which a heartbeat failure detector suspects the peer; it must be longer than the heartbeat period plus the expected delay, and every value trades detection speed against false suspicions. D2
Global process identifier
Simple words: a process name that is unique in the whole cluster. Analogy: "Chidi's book number 7" instead of plain "book 7". Precise: a pair (node id, local process id), written node.pid in this course, so that process ids of different kernels never collide; a location-transparent system would hide the node part, ours deliberately shows it. D1
Remote execution
Simple words: running a program on another computer and getting its answer back. Analogy: asking a friend to do a sum for you and post the answer. Precise: placing a unit of work on a chosen node and returning its result to the requester, ideally with the same meaning as a local run; it inherits the failure ambiguity of remote procedure calls (F5-09). D1

Terms from earlier courses used here without redefinition: heartbeat, failure detector, partial failure, remote procedure call, descriptor ring (NIC), EtherType, Multiboot, polling. "Kernel" in this course always means the operating-system kernel, never a GPU kernel.

Layer 1 — the kid explanation

Analogy

The book club is one club, but it lives in four homes. To make it feel like one clubhouse, the friends agree on three things: every book gets a name that says whose shelf it is on ("Chidi's book 7"), every friend keeps a list of who is in the club right now, and any friend can ask another to do a job and send back the answer. Mapping: friend = node; letter = message; "still here" letter = heartbeat; the list of who is in = membership view; "Chidi's book 7" = global process identifier 3.7; asking a friend to do a sum = remote execution; the post office = the network (here, the lab switch).

Callers love the clubhouse because they never need to know which home a book lives in. The friends love it less, because they do all the hidden work: writing letters, keeping lists up to date, and deciding what to do when a letter does not come. That hidden work is what an operating system for many machines has to do.

The hard moment is silence. If Chidi stops writing, the others must decide whether to keep waiting or to carry on without Chidi. If they wait forever, the club stops. If they give up too early, they may drop a friend who was only slow. There is no perfect rule, only a good choice of how long to wait.

Layer 2 — the student explanation

What a single-system image promises. The textbook view of distribution lists a family of transparencies: hide whether a resource is local or remote (access), where it is (location), whether it moved (migration), whether there are copies (replication), whether others use it too (concurrency), and whether parts failed (failure). D1 A single-system image is the strongest form of this promise applied to an operating system: one name space for processes and files, one view of the machines' resources, one place to log in and start work. D1

Three ways to build "many machines as one". A distributed operating system changes the kernels so that they cooperate and present one system. A network operating system leaves each machine its own operating system and adds explicit remote services. Middleware puts the distribution services in a layer above unchanged kernels. D1 This course does something in between, on purpose: the services run inside your own small kernel (so you see every byte), but each kernel is still a separate system with its own memory and clock, and the services are explicit enough that you can see where the illusion is made.

What the illusion needs. Before any process list or remote file can be "the cluster's", every node needs an answer to a simpler question: who is in the cluster right now? The lab answers it with heartbeats: every node broadcasts a small frame every 10 ticks, records when it last heard from each peer, and keeps in its view only peers heard within the last 50 ticks (Listing 3). This is the heartbeat failure detector of F5-11, now inside a kernel. It can be wrong both ways: a slow node can be suspected, and a dead node stays in the view until the timeout expires. D2

Two services on top. The lab kernel offers two single-system-image services. cps (cluster process status) asks every node for its process table and prints one merged list with global names node.pid. rrun (remote run) places a job on the least-loaded other node in the requester's view and prints the answer when it comes back. Both run over raw Ethernet frames with the DS403 header of Listing 1; both wait only a bounded time for answers. In the lab run both work while all three nodes are up, and both show the missing node honestly after node 3 halts: the second process list has 8 entries instead of 12 and says which node is missing, and the third job goes to node 2 because node 3 is no longer in the view (R2, R3).

Partial failure is the price. One computer either runs or does not. Three computers can be "partly up", and every service must decide what to do then. A process list that waits for every node would never finish once a node is gone; one that does not wait may be incomplete. The lab's choice is to wait one second, print what arrived, and name the nodes that are missing. That is the general shape of the answer: bounded waits, explicit partial results, no pretending. D2

Layer 3 — the engineer's depth

Transparency has a cost, and sometimes a price in correctness. Hiding location means a call that looks local may take a network round trip; hiding failure means something must wait, retry or replicate, and a retried operation may run twice. The textbook treatment of transparency is explicit that full distribution transparency is not always achievable and not always desirable, because hiding failures and delays can make a system slower or harder to reason about. D1 The engineering question is therefore not "how much can we hide?" but "which differences does each user need to see?" A scheduler must see where nodes are; a user's shell may not.

Why a merged view is not a snapshot. cps sends one broadcast request; each node answers from its own table when the request arrives; the requester prints answers in arrival order. If a process were created on node 2 between node 2's answer and node 3's answer, the list could show a combination that never existed at any single instant on a global clock, because there is no such clock. A consistent snapshot needs a protocol (the distributed snapshot algorithms that DS301's reading list covers), or acceptance that "a recent view" is enough. For a process list, a recent view is enough; for a lock table it is not, which is why locks wait for F5-47's consensus layer. D1 D2

Membership design choices. The lab's detector has two parameters: heartbeat period h = 10 ticks and suspicion timeout T = 50 ticks. Detection of a stopped node takes between T and T + h after its last heartbeat arrives (the view is recomputed on every loop, so the check itself adds almost nothing). The run agrees: node 3's last heartbeat left at about its tick 590–600, and nodes 1 and 2 removed it at their ticks 651 and 646, on clocks that started at slightly different moments (R2): node 2's 646 is only 46 ticks after node 3's 600, which is possible only because the two counters do not describe the same instant. A false suspicion needs a gap of more than T between two arrivals from a living node, which, with h < T, requires several lost or delayed heartbeats in a row. If T < h, every gap between two heartbeats is longer than the timeout, and every node is suspected once per period: the forensic lab of this chapter. D2

Real membership services add more than the lab does: an incarnation number so that a restarted node is not confused with its old self (the header's term field is reserved for it), gossip so that views converge faster than direct heartbeats in large clusters, indirect probes before suspecting, and, most important for F5-47, a rule that views alone never decide who may write. The lab's views are local opinions; F5-47 shows what happens when a design treats them as truth. D2

Placement and the requester's view. rrun places a job on the least-loaded peer in the requester's view. That is a reasonable local choice, but it is not a cluster decision: two requesters with different views could both pick the same node, or one could pick a node the other already knows is gone. F5-47 moves placement to a single leader whose decisions are written in a replicated log, so that the whole cluster agrees on where each job runs and who restarts it.

Raw Ethernet instead of IP. The lab sends its own EtherType directly in Ethernet frames, broadcast to every port, with a header field saying which node should act (Listing 1). This removes an IP stack from the critical path of a teaching kernel and makes every frame easy to read in the switch log. It also removes routing, fragmentation, checksums beyond the Ethernet CRC, and any protection from other software on the same network. A production design would run the same messages over UDP on the C9 stack. D7 C1

The EtherType value 0x88B5 was chosen because it is remembered as one of the values IEEE 802 sets aside for local experiments. That was not checked against the IEEE 802 or IEEE 802.3 documents or the IEEE EtherType registry in this build. How the hardware actually does it

Each node is an emulated PC (QEMU's pc machine, TCG emulation, 32 MiB). The kernel is a 32-bit Multiboot image that QEMU loads with -kernel; paging stays off and interrupts stay masked, so every device is polled. D5 D6

The network card. The e1000 driver (Listing 6) finds the card by PCI vendor 0x8086 and device 0x100E, maps its registers through BAR0, resets it, reads its MAC address from the EEPROM read register, and sets up two descriptor rings in RAM: 32 receive descriptors, each owning a 2,048-byte buffer, and 16 transmit descriptors. The card writes received frames into the buffers by DMA and sets the "descriptor done" bit; the driver polls that bit, copies the frame, clears the bit and moves the tail register to give the buffer back. Sending is the mirror image. These are the C9 mechanisms; the register offsets come from the Intel 8254x manual and were only confirmed by working on QEMU's model. D3 C1

Not verified — check before relying on this

Every e1000 register offset and bit used in e1000.cc (CTRL, STATUS, EERD, IMC, RCTL, TCTL, TIPG, RDBAL…RDT, TDBAL…TDT, MTA, RAL0, RAH0; RST, SLU, ASDE, EN, BAM, SECRC, PSP, EOP, IFCS, RS, DD; the TIPG value) was written from memory of the Intel "PCI/PCI-X Family of Gigabit Ethernet Controllers Software Developer's Manual (8254x)" and was confirmed only in the sense that the driver works on QEMU 8.2.2's e1000 model. A model may accept settings a real 82540EM would not. Check each against the manual's register chapter before running the driver on a real card.

The clock. With interrupts off, the kernel keeps time by polling the PC's programmable interval timer: channel 0 counts down from a reload value; when a read returns a larger value than the previous one, one period has passed. The reload value 11,932 is meant to give about 10 ms per period. On the build machine, 600 ticks of node 1 (from cps #1 at tick 300 to cps #2 at tick 900) took 9,610 − 3,615 = 5,995 ms on the switch's clock: about 10.0 ms per tick, measured once, in emulation (R2). A polled clock sees at most one wrap of the counter per poll, and its resolution is one tick; the mistakes section shows a run where the resolution matters. D4

Not verified — check before relying on this

The PIT's input frequency (remembered as about 1.193182 MHz, which with a reload of 11,932 would give about 10.0 ms) and the latch command and mode-2 behaviour used in k.cc were not read from the Intel 8254 datasheet in this build. The lab's only evidence is the single measurement above on QEMU's emulated PIT. Read the 8254 datasheet before relying on the period on real hardware.

The wire. QEMU's -netdev dgram backend sends every frame the emulated card transmits as one UDP datagram to a given address and delivers datagrams arriving on another address to the card. labswitch owns one UDP socket per node and forwards each frame to the other nodes (a hub, not a learning switch), optionally dropping frames between two groups of nodes for a time window to simulate a partition. There is no cable, no physical layer and no switch hardware in this course; there is also no real loss except what labswitch causes. D5 R1

Worked example

Question. A "single-system image" that needs every node to work is less available than one node. A design that needs only a majority is more available. By how much, for 1, 3, 5 and 7 nodes, if each node is up with probability p independently?

Step 1: the all-nodes design. All n nodes must be up: P = pn. For p = 0.99 and n = 3: 0.99 × 0.99 × 0.99 = 0.970299. The cluster is down with probability 0.029701, almost three times as often as one node (0.01).

Step 2: the majority design. At least ⌊n/2⌋ + 1 nodes must be up. For n = 3 that is "at least 2": p3 + 3p2(1 − p) = 0.970299 + 3 × 0.9801 × 0.01 = 0.970299 + 0.029403 = 0.999702. Down with probability 0.000298: about 34 times less often than one node.

And "up" is not "reachable": in a partition every node may be up while no majority can talk. D2 R5

Where the analogy breaks


    

  • Friends can tell "no letter" from "the post office is closed"; nodes cannot. A silent node, a dropped frame, a slow emulator and a partition all look the same to member.cc: no message arrived. Friends also phone, ask neighbours, and use common sense; a kernel only has its timeout. D2
    • 

  • Letters arrive in order and once; frames need not. The post rarely duplicates a letter. Networks can duplicate, reorder and drop frames (the lab's switch only drops, during partitions). The round number in cps exists because an answer can arrive after its question is closed.
    • 

  • The friends share one calendar; the nodes do not. "Day 3 of the week" means the same day to every friend. Tick 600 of node 3 and tick 600 of node 1 are different moments, because each counts from its own boot (Figure 2). Comparing tick numbers across logs is a mistake unless you first align the clocks (F5-10).
    • 

  • "One clubhouse" is a feeling for callers only. In the analogy the illusion is harmless. In a cluster, hiding a failure can make a program believe an operation happened when it did not: the remote run that times out is reported as "result unknown", not as a failure, because nobody knows.
    • 




Common mistakes and debugging


    

  • The view flaps every second. Symptom: hundreds of "view" lines; nodes leave and rejoin. Cause: suspicion timeout shorter than (or too close to) the heartbeat period. Find it: count "view" lines per node and look at the gaps between rejoin and leave. Fix: timeout several heartbeat periods long. This is the forensic lab.
    • 

  • Measured times that make no sense. Symptom, from the real run (R2): node 1 reports "remote compute 0 ticks, round trip 0 ticks" for job 1, while the switch log puts node 1's RUN_REQ at 5,110 ms and node 2's RUN_REP at 5,125 ms, 15 ms apart: longer than one tick of about 10 ms. Causes: the tick counters have a resolution of one tick, so a short interval reads as 0 or 1 depending on where the tick boundaries fall; the switch's clock is the host's clock in a separate process, and it also counts the time frames wait in the host's scheduler while three emulators share its processors; and the polled guest clock notices at most one wrap of the PIT counter per call to now(), so a stretch longer than one period without polling loses ticks. Fix: never compare ticks from two nodes or from the guest and the host; measure a round trip only on one node and only when it is many ticks long; use a finer, free-running clock (the TSC with calibration, the HPET) when you need real durations.
    • 

  • A node never appears in any view. Cause: two QEMU nodes with the same MAC, or a node started before the switch. Find it: the switch's "frames forwarded" table shows zero from that node; the kernel's first log line shows its MAC. Fix: unique mac= per node (the lab uses 52:54:00:44:03:0n), start the switch first.
    • 

  • Broadcast frames never arrive. Cause: receive control without "broadcast accept". Find it: the switch forwards frames but the receiver's log shows no views. Fix: BAM in RCTL (Listing 6, line 93).
    • 

  • An old answer shows up in a new list. Cause: replies not matched to their request. Fix: a round number or tag in every request and reply (ssi.cc line 88; the same idea becomes 9P's tag in F5-45).
    • 

  • The whole cluster hangs when one node stops. Cause: a service that waits for every node. Fix: bounded waits and explicit partial results; the worked example shows why "every node" designs are fragile.
    •

Summary


    

  • A single-system image makes many machines look like one; transparency comes in kinds (access, location, migration, replication, concurrency, failure), and full transparency is neither always possible nor always wise.
    • 

  • Distributed operating systems, network operating systems and middleware are three ways to build "many machines as one"; this course builds explicit services inside its own small kernel.
    • 

  • Membership is the first service: heartbeats plus a suspicion timeout give each node a local, numbered, sometimes wrong view.
    • 

  • A suspicion timeout shorter than the heartbeat period makes views flap; detection takes between the timeout and the timeout plus one period.
    • 

  • Cluster-wide services must wait a bounded time and show partial results honestly; a merged list is never a global snapshot.
    • 

  • Designs that need every node are less available than one node; majority designs are more available, under an independence assumption that real clusters may break.
    • 

  • The lab's kernels have separate, polled clocks: never compare tick values across nodes.
    •
