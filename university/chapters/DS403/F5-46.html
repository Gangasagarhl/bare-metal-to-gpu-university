Story hook

A new friend, Emeka, joins the club. He moves into an empty house in a fourth town: no books, no rulebook, not even the club's address. He shouts out of the window "is anyone there who can help a new member?", and the town's post office answers with an address for him and a note: "your rulebook is at the club's post box, ask for n4.ipxe". He asks; the rulebook arrives in small envelopes, one at a time, each acknowledged before the next is sent. Now Emeka knows how to be a member.

Then the real work starts. The club's shared notebook lives at Amara's house. Bao writes a line in it by letter. Chidi adds another. Bao had made a photocopy of the page earlier and reads the photocopy again: it does not show Chidi's line. Later Amara's house is closed for good, and Bao still reads his photocopy as if nothing had happened.

This chapter does both halves on your own kernel: three machines that arrive with nothing and load the kernel over the network, and a remote file service shaped like 9P that they share. Then it breaks the cache on purpose, because the photocopy is where remote file systems get interesting.

What you will be able to do

  • Explain each step of a network boot (DHCP, TFTP, a boot script, a Multiboot kernel) and read it in a packet capture.
  • Boot three QEMU nodes over the network with iPXE and give each its own kernel command line.
  • Implement a remote file service with fids, tags, retries and per-file versions, server and client, over raw Ethernet.
  • Choose and justify a client cache policy, and show by experiment the difference between a validated cache and a naive one.
  • Reason about retries: which file operations are safe to repeat, and what a timeout tells you.
Jargon box
Network boot (PXE)
Simple words: starting a computer with a program it loads over the network instead of from its own disk. Analogy: the new friend is posted the club's rulebook. Precise: a boot in which firmware on the network card (PXE, or a replacement such as iPXE) obtains an address and the name of a boot file by DHCP, downloads the file by TFTP (or another protocol), and runs it. D1
TFTP
Simple words: a very small protocol for downloading a file, one block at a time. Analogy: the rulebook sent in numbered envelopes, each acknowledged before the next. Precise: the Trivial File Transfer Protocol over UDP: a read request names the file; the server sends numbered data blocks, each acknowledged before the next (lock-step); a block shorter than the block size ends the transfer; options such as block size and transfer size can be negotiated. D3
iPXE
Simple words: open-source network boot firmware that can run small boot scripts. Analogy: a helpful neighbour who fetches the rulebook and hands it over. Precise: a network boot program, shipped as option ROMs with QEMU, that performs DHCP, fetches files by TFTP and other protocols, runs scripts that start with #!ipxe, and can load Multiboot kernels with a command line. D4
Boot file
Simple words: the name of the first file a network-booting machine should fetch. Analogy: "ask for n4.ipxe". Precise: the file name a DHCP server gives a client (the "file" field or a boot-file-name option), interpreted relative to the TFTP server. D2
Remote file system
Simple words: files kept on one machine and used from others as if they were local. Analogy: the club notebook at Amara's house, written by letter. Precise: a file service in which clients send file operations to a server by RPC; its design is described by its naming, its state (stateful or stateless server), its caching and the consistency guarantees it gives to concurrent clients. D7
Client cache (file system)
Simple words: a copy of file data kept on the client to save trips to the server. Analogy: a photocopy of a notebook page. Precise: client-side storage of file data or attributes, used instead of a server request; its correctness depends on when the client checks that the copy is still current (revalidation) or on the server telling the client when it is not (callbacks, leases). D7
Revalidation
Simple words: asking the server whether your copy is still the newest before you use it. Analogy: phoning the library: "is page 3 still edition 2?" Precise: a small request (here a stat) that returns the file's current version, compared with the cached version; on a match the cache is used, otherwise the data is fetched again. It costs one round trip per use and fails when the server is unreachable. D7
Close-to-open consistency
Simple words: after one client closes a file it changed, any client that opens the file afterwards sees the change. Analogy: once Bao has posted his page back, anyone who borrows the notebook next sees his writing. Precise: a weaker guarantee than one-copy (UNIX) semantics in which writes are flushed on close and caches are revalidated on open; concurrent readers and writers of an open file may see different data. D7 D10
Stateful server
Simple words: a server that remembers what each client is doing. Analogy: Amara remembers which friend has which bookmark. Precise: a server that keeps per-client state between requests (open files, fids, locks, cache promises); it allows short requests and server-driven cache invalidation, but its state is lost when it crashes and must be rebuilt or invalidated, and clients that crash leave state behind. D7

Terms from earlier chapters used here without redefinition: DHCP, Multiboot, fid, tag (9P), qid, idempotent operation, at-least-once and at-most-once, stale read, remote procedure call, membership view.

Layer 1 — the kid explanation

Analogy

A new friend with an empty house shouts "help, I am new!" (DHCP Discover). The post office answers with an address and the name of a rulebook to ask for (Offer and ACK with a boot file). The rulebook comes in numbered envelopes; each one is acknowledged before the next is sent (TFTP). The rulebook's first page says "now read the big book, and you are member number 2" (the iPXE script with the kernel and its command line).

The club notebook lives at Amara's house (the server). Friends write to it by letter (RPC). A friend may keep a photocopy (cache), but a careful friend phones first: "is the notebook still at edition 1?" (revalidation). A careless friend reads the photocopy forever (naive cache). Mapping: post office = DHCP server; envelopes = TFTP blocks; notebook = file on the server; photocopy = client cache; edition = qid version.

When Amara's house closes for good, the careful friend's phone call fails, so he knows something is wrong. The careless friend never phones, so he never notices. Being careful costs a phone call every time; being careless costs being wrong without knowing it.

Layer 2 — the student explanation

Why network boot. In a cluster you want every node to run the same kernel, and to change it in one place. Network boot gives you that: the nodes' firmware fetches the kernel from a server at every start, so updating the server's copy updates the cluster at the next reboot. It also means a node needs no disk to start. D1

The boot chain in the lab. Each node has two NICs. The first is a virtio-net card on QEMU's user-mode network, whose built-in DHCP and TFTP servers play the role of the boot server; QEMU's iPXE ROM on that card boots it. The DHCP answer names the boot file n2.ipxe (one per node). That file is an iPXE script of three lines: #!ipxe, kernel f546.elf node=2 nodes=3 role=writer server=1 cache=valid life=1500, boot. iPXE fetches f546.elf from the same TFTP server, loads it as a Multiboot image with that command line, and jumps to it. The kernel prints the boot loader's name from the Multiboot information ("iPXE 1.21.1+git-20220113.fbbdc3") and then uses its second NIC, the e1000 on the lab switch, for everything else. D4 D5 R2

The file service. DFS ("DS403 file service") borrows 9P's shape from F5-45: attach, walk, create, open, read, write, stat, clunk; client-chosen fids; tags that match replies to requests; a qid made of a path number that is never reused and a version that grows by one at every change. Unlike 9P it uses a fixed-layout request and reply (Listing 1) that fits in one Ethernet frame, and it carries at most 512 bytes of data per message. One node (node 1) runs the server with a flat directory in RAM; the others are clients.

Retries. On the lab switch frames are not lost unless a partition is configured, but the client is written for a network that loses them: it waits 100 ticks for the reply with its tag, sends again, and gives up after three attempts with "server unreachable". Every retry is the at-least-once behaviour of F5-09: if the first request arrived and only its reply was lost, the server executes it twice. Whether that matters depends on the operation (Layer 3).

The cache. The client keeps up to four small files it has read. Before using a cached copy, the validated client asks the server for the file's current version with a stat; if it equals the cached version the copy is used, otherwise the file is read again. The naive client never asks. The run shows both: at tick 600 the validated node 2 notices that notes went from version 1 to 2 and reads node 3's line; the naive node 2 of the forensic run returns the old 18 bytes, and even after the server has halted it keeps returning them without an error (R2, R5).

Layer 3 — the engineer's depth

Reading the boot capture. The capture (R3) shows two DHCP Discover/Offer pairs about one second apart before the Request at 3.068 s, then two TFTP read requests 56 ms apart. The client asked for a block size of 1,432 bytes and QEMU's server answered with 1,428; the client also asked for the transfer size (tsize=0), and the server filled in 86 for the script and 19,760 for the kernel. With 1,428-byte blocks the kernel needs ⌈19,760 / 1,428⌉ = 14 blocks, the script 1: the 15 data packets counted. The block-size and transfer-size options are extensions to basic TFTP, whose blocks are 512 bytes. D3 R3

Not verified — check before relying on this

Explanations of the capture that go beyond what it shows come from memory, not from documents read in this build: that iPXE repeats DHCP Discover while it waits for possible ProxyDHCP offers before sending its Request; that TFTP's default block size is 512 bytes and that the blksize and tsize options are defined in separate RFCs from the base protocol; that a block shorter than the negotiated size ends a transfer; that QEMU's user-mode network gives guests 10.0.2.15 and itself 10.0.2.2 by default; and that the DHCP "file" field or option 67 carries the boot file name. The Source Researcher must check them against the PXE specification, the DHCP and TFTP RFCs, iPXE's and QEMU's documentation (D1–D5).

What network boot costs and risks. Every node depends on the boot server at start-up: if it is down, nothing boots. TFTP is lock-step, so its time grows with the number of blocks times the round trip (Worked example). Plain TFTP and DHCP have no authentication: anyone on the boot network can answer first and hand your nodes a different kernel. Real clusters therefore isolate the boot network, sign or check boot images (iPXE can verify images; UEFI Secure Boot is another layer), and use faster protocols for large images. D1 D4

Safety

Never run a DHCP or TFTP server on a network you do not own: a second DHCP server can take over other people's machines' addresses and boot settings. The lab uses QEMU's private user-mode network, which no other machine can see.

Design choices of DFS, one by one.

ChoiceDFSAlternativeWhat the choice buys and costs
Server stateStateful: fid table per clientStateless: every request names the file by a durable handle (the original NFS design)Short requests and a place for per-client promises; a server restart loses every fid, and crashed clients leak fids.
Name spaceOne flat directory, one serverPer-process name spaces (F5-45), many serversSimple; one server is a single point of failure, as the run shows.
Cache validationStat on every use of a cached fileTime-based (trust for n seconds), callbacks or leases from the serverAlways current while the server is reachable; one round trip per use; no use at all when the server is gone.
Write policyWrite-through: every write goes to the server at onceWrite-back on close (close-to-open), or delayedNo lost writes in the client; more messages; no batching.
DeliveryAt-least-once: up to three tries, same tagAt-most-once with a server reply cache keyed by (client, tag)Simple; non-idempotent requests may run twice.
TransportOne request per Ethernet frame, 512 data bytes9P over a reliable stream (TCP), large msizeNo fragmentation code; many messages for large files.

Which operations survive a retry? A retry repeats a request whose first copy may have been executed. Read, stat, walk and attach change nothing (or re-establish the same fid) and are safe to repeat. Write at an explicit offset leaves the same bytes in the file, but DFS increments the version twice, so a cache would see one extra change: harmless here, visible in the logs. Create is not safe: if the first create succeeded and its reply was lost, the retry gets "file exists", and the client reports failure for an operation that succeeded. Clunk repeated gets "unknown fid". The fix used by real protocols is a server-side reply cache keyed by client and request id, which turns at-least-once into at-most-once for as long as the cache remembers. D7 D9 The append in this lab is a write at the offset the client saw at walk time (18); two concurrent appenders that both saw 18 would overwrite each other, which is why some protocols have an append mode in which the server picks the offset.

Consistency, in the words of the textbooks. One-copy (UNIX) semantics means every read sees the last write by anyone. Close-to-open semantics, used by NFS clients, revalidates on open and flushes on close. Session semantics (as in AFS) make changes visible to others only after close; the server promises to call back clients whose cached copies it has invalidated. D7 D10 DFS's validated cache gives one-copy semantics for single reads while the server is reachable, because each use asks the server; it pays one round trip per read for it, which is what callbacks and leases exist to avoid.

Not verified — check before relying on this

The characterisations of NFS (stateless server in its original versions, file handles, close-to-open consistency in its clients, a duplicate-request cache in servers) and AFS (whole-file caching, session semantics, callbacks) are from memory. Check them against D7 and D10 before teaching them as facts; later NFS versions are stateful and differ in many details.

Failure handling and membership. In the run node 2 removes node 1 from its view at its tick 961, but its read at tick 1000 still sends three requests over 300 ticks before giving up (R2). The client does not consult membership; it trusts its own timeout. Using the view to fail fast ("server not in view: fail at once") is attractive and dangerous: views can be wrong (F5-44's forensic lab), and a client that fails fast during a false suspicion turns a short delay into an error. The opposite trap is the naive cache: it hides the server's death completely, which in F5-44's terms is failure transparency of the worst kind: the client is wrong and does not know.

How the hardware actually does it

Two NICs per node. Each emulated PC has a virtio-net card with bootindex=1 attached to -netdev user, and an e1000 attached to -netdev dgram with romfile= empty, so that only the virtio card offers a boot ROM. SeaBIOS (QEMU's BIOS) runs the virtio card's option ROM, which is iPXE; iPXE does DHCP and TFTP using the virtio card, loads the kernel, and leaves the card alone. The kernel never touches the virtio-net card; it drives the e1000 exactly as in F5-44. D4 D5 R2

Seeing what the firmware did. iPXE's messages went to the emulated screen, not to the serial port, so the lab cannot log them directly. Two independent pieces of evidence replace them: QEMU's filter-dump object writes every frame of the boot NIC's network to a pcap file, decoded by TShark (R3); and the kernel prints the Multiboot boot-loader name that iPXE filled in (R2). D6

On real hardware. A real cluster would use the NIC's own PXE ROM or iPXE flashed or chain-loaded, a real DHCP server configured with per-machine entries (by MAC address), and a TFTP or HTTP server, on a dedicated boot network. The kernel's e1000 driver would need to match the real card's model and the Intel manual (F5-44). None of this was tested.

Not verified — check before relying on this

Untested on hardware. The boot timings (about 3.2 s from the first Discover to the TFTP requests) are one emulated run on one host and depend on iPXE's DHCP timeouts, not on network speed. Real PXE ROMs, real DHCP servers and real switches (spanning-tree delays on a port that has only now come up are a classic cause of PXE timeouts, from memory) can behave very differently.

Worked example

Question. How long does lock-step TFTP take to deliver the lab's kernel, and a 20 MiB kernel with initial RAM disk, if one block plus its acknowledgement takes one round trip r? And how many DFS messages does it take to read a 1 MiB file?

Step 1: blocks. The lab's kernel: ⌈19,760 / 1,428⌉ = 14 blocks (the capture agrees). A 20 MiB image: 20 × 1,048,576 = 20,971,520 bytes; ⌈20,971,520 / 1,428⌉ = 14,686 blocks. With the basic 512-byte blocks it would be 40,960 blocks.

Step 2: time. Lock-step means one block per round trip: time ≈ blocks × r. For r = 0.5 ms (an illustrative value, not a measurement): 14 blocks take about 7 ms; 14,686 blocks take about 7.3 s; 40,960 blocks of 512 bytes take about 20.5 s. Bandwidth hardly enters: the round trip does. This is why large network boots use protocols with windows (HTTP over TCP, or TFTP's windowsize option where supported). D3

Step 3: DFS message sizes. A request is DfsT: 2 + 1 + 4 + 4 + 4 + 2 + 28 + 512 = 557 bytes; a reply DfsR: 2 + 1 + 1 + 4 + 4 + 4 + 2 + 512 = 530 bytes. With the 12-byte DS403 header and the 14-byte Ethernet header the frames are 583 and 556 bytes, under the 1,514-byte maximum. Every request carries 512 data bytes even when it carries none: an easy optimisation the lab skips for clarity.

Step 4: a 1 MiB read. 1,048,576 / 512 = 2,048 reads, each a round trip, plus walk, open and clunk: 2,051 round trips; with a validated cache, one more stat per cached use. At an illustrative 1 ms per round trip that is about 2 s for one megabyte, against milliseconds for a protocol that streams; this is why DS403's DFS is for small files only and real protocols negotiate large messages (9P's msize) and keep several requests in flight (9P's tags). D8

Where the analogy breaks


    

  • A friend's photocopy is visibly old paper; a cached file looks new. Nothing on the bytes says how old they are. Only a version compared with the server's tells you, and only while you can reach the server.
    • 

  • The post office will not send a rulebook to a stranger who pretends to be Emeka; DHCP and TFTP will. Network boot without signed images trusts whoever answers first.
    • 

  • A letter asking "add this line" is one request; a retried RPC is two. The library notices a duplicate letter; a server without a reply cache does not.
    • 




Common mistakes and debugging


    

  • The node boots the wrong NIC, or none. Cause: both NICs offer a boot ROM, or the boot NIC lacks bootindex. Fix: romfile= empty on the cluster NIC, bootindex=1 on the boot NIC. Check with the boot-loader name the kernel prints.
    • 

  • No boot messages anywhere. Firmware writes to the screen, and the lab has none. Fix: capture the boot network (filter-dump) and decode it; print the Multiboot boot-loader name from the kernel.
    • 

  • iPXE fetches nothing or the wrong file. Cause: a URL in the script that points at a different server, or a typo in the script's first line. Fix: keep the script relative to the TFTP server (kernel f546.elf …) and check the read requests in the capture.
    • 

  • Old data after another node's write. Cause: a cache that never revalidates. Find it: compare the server's version in its log with the client's "from the cache (version …)" line. This is the forensic lab.
    • 

  • "file exists" for a file the client is sure it created once. Cause: a retried create whose first copy succeeded. Fix: a reply cache on the server, or a create that succeeds when the existing file was made by the same client and tag.
    • 

  • Other nodes suspect a client while it waits. Cause: a blocking RPC that stops sending heartbeats. Fix: keep the membership loop running inside waits (Listing 3, line 25).
    • 

  • Appends from two clients overwrite each other. Cause: both write at the offset they last saw. Fix: an append mode where the server picks the offset, or a lock (F5-47).
    • 




Transition box

Where you came from: F5-44 gave the cluster membership and raw-Ethernet messages; F5-45 gave the shape of a file protocol and a real 9P session. What carries over: tags matched to replies, fids as server state, qid versions, bounded waits, keeping heartbeats alive inside waits. What changes: most dangerous first: the service now depends on one server, so its failure is every client's failure; retries make some operations run twice; caches can be wrong silently; and the nodes now load their kernel from the network, so the boot server joins the list of things that must be up and trusted. D7 What comes next: F5-47 removes the single decider: a replicated log decides what the cluster's state is, a leader schedules jobs, and a partition shows why a majority, not a view, must decide.

Mini-project


Leases for DFS. Replace per-read validation with leases: when the server sends file data it also grants a lease of L ticks during which it promises not to change the file without first telling the lease holder (or waiting for the lease to expire). The client uses its cache without asking while its lease is valid. Implement it for writes from other clients, measure the number of DFS messages with and without leases for a read-mostly workload, and write down what happens when the lease holder is partitioned from the server.

Summary


    

  • Network boot: DHCP gives an address and a boot file name, TFTP fetches files in lock-step blocks, iPXE runs a script and loads a Multiboot kernel with its command line.
    • 

  • The lab's capture shows the whole chain; 15 TFTP data blocks carried the 86-byte script and the 19,760-byte kernel.
    • 

  • Network boot makes the boot server a dependency and, without signed images, a trust problem.
    • 

  • DFS borrows 9P's shape: fids, tags, qids with versions; it uses a fixed layout in one Ethernet frame.
    • 

  • Retries give at-least-once delivery: reads and stats are safe to repeat, creates are not; a reply cache gives at-most-once.
    • 

  • A cache validated by version is correct while the server is reachable and costs a round trip per use; a naive cache is fast and silently wrong, even after the server is gone.
    • 

  • Do not trust a remote file service that never reports an error.
    •
