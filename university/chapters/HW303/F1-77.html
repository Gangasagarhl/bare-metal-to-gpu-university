Story hook

The take-away stand has a strange problem: once an hour, a meal goes out wrong, and by the time anyone looks, the cook has moved on. Watching from the street does not help. The health inspector has a better tool: a small hatch in the back wall and a pause button. Press it, and the whole kitchen freezes mid-step. The inspector can read every note on the counter, look into every pot, even change a note, then press "continue". She can also leave instructions: "freeze when the cook opens recipe 15", or "freeze when anyone touches the salt jar".

Every modern microcontroller has that hatch and that pause button built in. The hatch is a debug interface with a few pins, called JTAG or SWD; the device that presses the button from your computer is a debug probe; and the inspector's notebook is a debugger such as GDB. In this chapter you freeze a running program in its reset handler and in an interrupt handler, read its registers and memory, and use a watchpoint to catch the moment a variable changes.

What you will be able to do

  • Explain what a debug probe, JTAG and SWD are, which signals they use, and how the debugger's commands reach the core.
  • Trace the JTAG test-access-port state machine and read an IDCODE and a bypass register by hand, using a model you can run.
  • Attach a debugger to a halted microcontroller (here emulated), set breakpoints in the reset handler and in an interrupt handler, read registers and memory, and set a watchpoint.
  • Interpret what the core's registers say inside an exception: which exception is active, and how it will return.
  • Diagnose an interrupt that "never fires" by combining the symbol table and a debugger session.
Jargon box
Debug probe
Simple words: a small box between your computer's USB port and the chip's debug pins. Analogy: the inspector's hand on the pause button. Precise: an adapter that translates debugger requests (halt, read register, write memory, set breakpoint) from the host into JTAG or SWD transactions on the target's debug port; usually paired with host software that acts as a GDB server. D2 D3
JTAG
Simple words: an old, standard four- or five-wire interface for testing and debugging chips. Analogy: a hatch with a strict door protocol: knock patterns move you from room to room. Precise: the IEEE 1149.1 test access port and boundary-scan architecture: signals TCK (clock), TMS (mode select), TDI (data in), TDO (data out) and optional TRST, a 16-state TAP controller driven by TMS, an instruction register and several data registers shifted serially. D1
TAP (test access port) controller
Simple words: the little state machine behind the JTAG pins. Analogy: the corridor map of the inspection rooms. Precise: a 16-state finite-state machine advanced on each TCK rising edge by the value of TMS, which selects whether an instruction or a data register is captured, shifted between TDI and TDO, and updated. D1 R1
SWD (Serial Wire Debug)
Simple words: Arm's two-wire replacement for JTAG on small chips. Analogy: the same hatch with a smaller door. Precise: a two-pin (SWDIO bidirectional data, SWCLK clock) packet protocol defined by the Arm Debug Interface architecture; each transaction is a request, an acknowledgement and a 32-bit data phase with parity, addressed to debug-port or access-port registers. D2 D3
Debug access port (DP/AP)
Simple words: the doorway inside the chip that turns probe packets into memory reads and writes. Analogy: the inspector's assistant inside the kitchen who fetches what she asks for. Precise: in the Arm Debug Interface, the debug port (JTAG-DP or SW-DP) is the external interface, and access ports behind it, such as a memory access port, perform bus transactions on the chip's memory system, including the core's debug registers. D3
Breakpoint (software, hardware)
Simple words: "stop when the program reaches this instruction". Analogy: "freeze when the cook opens recipe 15". Precise: a software breakpoint replaces an instruction with a breakpoint instruction (bkpt on Arm), which needs writable code memory; a hardware breakpoint is an address comparator in the core's debug logic (on Armv7-M, the Flash Patch and Breakpoint unit), which works on flash but exists in limited number. D4 D2
Watchpoint
Simple words: "stop when this memory location is read or written". Analogy: "freeze when anyone touches the salt jar". Precise: a data-address comparator (on Armv7-M, in the Data Watchpoint and Trace unit) that halts the core after a matching access; the stop is reported at the instruction after the access. D4 R2
GDB remote serial protocol (GDB server)
Simple words: the text protocol a debugger uses to talk to a stub that controls the target. Analogy: the phone line from the inspector's office to her hand on the button. Precise: a packet protocol (read registers, read/write memory, insert breakpoint, continue, stop reply) spoken by GDB and LLDB; probe software and QEMU's -gdb option implement the server side. D5 D6
Weak symbol
Simple words: a default definition that is silently replaced if someone defines the same name. Analogy: a "standard recipe" card that is used unless the cook pins a card with exactly the same title. Precise: a symbol marked weak (GCC/Clang __attribute__((weak))) that the linker uses only if no strong definition of the same name exists; it is how start-up files provide default handlers. D7 R3

Layer 1 — the kid explanation

When a program on a microcontroller goes wrong, you cannot see inside it: there is no screen, and it runs millions of steps per second. So chip makers put a secret door in every chip. A few pins on the chip lead to a tiny helper inside that can stop the processor, look at everything, and start it again.

A debug probe is the box that connects your computer to that door. A debugger is the program on your computer where you type "stop at the start", "show me the registers", "what is in this variable?", "stop when this variable changes". The probe turns those commands into signals on the pins.

In this course we do not have a real chip, so the emulator plays the chip and its secret door at the same time. Your commands are the same as on a real board; only the box in the middle is missing.

Layer 2 — the student explanation

What a debugger can do on a microcontroller

Analogy first: the pause button, the hatch and the notebook. Precisely: the core's debug logic can halt the core, which stops instruction execution while the rest of the chip may keep running (peripherals such as timers often keep counting unless the chip offers a "freeze in debug" setting); while halted, the debugger reads and writes core registers and memory through the debug port; breakpoint and watchpoint units compare addresses and halt the core on a match. D2 D4 Because memory accesses go through the chip's bus, the debugger can also read peripheral registers, which is often the fastest way to check a configuration: read back what the hardware really holds, not what the code meant to write. D2

JTAG and SWD on the wire

JTAG was designed for board testing (boundary scan: shifting values through every pin of every chip on a board to find broken solder joints) and later reused for debug. D1 All of its operations are shifts through registers selected by the TAP state machine: to read a device's identity, the probe resets the TAP, walks to Shift-DR (the identity register is selected after reset) and clocks 32 bits out of TDO. Listing 1 models exactly that, and its output shows the walk:



Three things are visible. First, five clocks with TMS = 1 reset the controller from any state, which is how a probe gets a known starting point without knowing the current state. Second, the identity register's bit 0 is 1, a rule of the standard that lets a probe tell an identity register from a 1-bit bypass register, which captures 0. D1 Third, the bypass register delays data by one clock: the five bits sent come back shifted by one place, with a 0 first. On a board with several chips in one JTAG chain, putting the other chips in bypass reduces each of them to one extra bit. D1 R1 (The device and its IDCODE value 0x0EDC0C01 are invented for the model.)


SWD replaces the four or five JTAG signals with two: a clock and one bidirectional data line. Instead of shifting through a state machine, each SWD transaction is a short packet: an 8-bit request (which register, read or write), a turnaround, a 3-bit acknowledgement (OK, WAIT, FAULT) from the target, and 32 data bits plus a parity bit. D3 Many Cortex-M chips offer both on shared pins and switch with a special sequence; small packages often offer only SWD. D2 Either way, the probe's packets end up as reads and writes in the chip's memory map, performed by an access port. That is why every debugger operation, even "read register r0", becomes a memory access to the core's debug registers. D3 D4

Layer 3 — the engineer's depth


Hardware breakpoints, flash and the emulator


A software breakpoint needs the debugger to write a bkpt instruction into code memory. On a real microcontroller the code is in flash, which cannot be changed by an ordinary write (F1-74), so debuggers use the core's hardware breakpoint comparators there. An Armv7-M core has only a small number of them (the exact number is in the core's technical reference manual), so "too many breakpoints" is a real error on hardware. D4 D2 QEMU's stub implements breakpoints inside the emulator itself, so the session above says nothing about how many comparators a real core has; on a board, check how many breakpoints your probe software reports. D6



What "halted" means for the rest of the chip


Halting stops the core, not the clock tree. Peripherals keep running: a UART finishes its character, a timer keeps counting, and a watchdog may reset the chip while you look at a variable. Many microcontrollers have a debug control register that freezes chosen timers and watchdogs while the core is halted. D2 On a real board you should expect pending interrupts to be waiting when you continue, and a motor driven by PWM to keep turning, which is a safety question, not only a debugging one. The emulator here does not model time realistically while halted, so this effect was not observed in the lab.



Locking the door


The debug port is also a security hole: anyone with a probe can read the whole flash. Production chips therefore offer read-out protection or debug disabling, sometimes permanent. Setting such options on a development board can make it impossible to reprogram, so never change option bytes during these labs. D2 D8

How the hardware actually does it


Inside the chip, the debug port is a small block clocked by the probe's clock (TCK or SWCLK), independent of the core's clock, so a probe can talk to a chip whose core clock is stopped or misconfigured, often even while the core is held in reset. D3 The access port behind it is a bus master on the chip's interconnect, like a second, very slow processor that only makes the accesses the probe asks for. D3 The core's debug logic sits on that bus as memory-mapped registers: a halting control and status register, registers for transferring core-register values, the breakpoint unit's comparators (which watch the instruction fetch address) and the watchpoint unit's comparators (which watch data addresses). When a comparator matches, the core enters debug state at the next instruction boundary. D4 JTAG's TAP controller itself is a 4-bit state register with next-state logic (F1-17) and shift registers between TDI and TDO; Listing 1's kNext table is its next-state logic written as a lookup table. D1



Worked example


Task. Starting from Test-Logic-Reset, how many TCK cycles does Listing 1's probe need to read the 32-bit IDCODE and return to Run-Test/Idle? Check against the run.


    

  1. Reach Shift-DR. TMS = 0 → Run-Test/Idle; 1 → Select-DR-Scan; 0 → Capture-DR (the IDCODE is loaded into the shift register here); 0 → Shift-DR. That is 4 clocks; the run prints the same four states.
    2. 

  2. Shift 32 bits. One bit per clock: 32 clocks. On the last one TMS = 1, which moves to Exit1-DR while shifting that last bit.
    3. 

  3. Return. TMS = 1 → Update-DR; 0 → Run-Test/Idle: 2 clocks.
    4. 

  4. Total. 4 + 32 + 2 = 38 clocks. The run prints "TCK cycles so far: 38". R1
    5. 

  5. Continue. The IR scan then takes 4 (to Shift-IR: 1, 1, 0, 0) + 4 bits + 2 = 10, and the 5-bit bypass scan 3 + 5 + 2 = 10, giving 58, as printed. At a probe clock of, say, 1 MHz, the whole sequence takes 58 µs. R1

Where the analogy breaks


    

  • The inspector's pause freezes the whole kitchen; a debug halt freezes only the cook. Timers, UARTs and watchdogs keep running unless you freeze them explicitly (Layer 3). D2
    • 

  • The inspector looks without touching; a debugger can disturb what it observes. Reading some peripheral registers clears flags (a UART's receive register, for example), so a debugger's memory view can change the program's behaviour. D2
    • 

  • The hatch is one door; JTAG is a chain. Several chips can share one JTAG chain, and the probe addresses them by putting the others in bypass; there is no such thing in the restaurant. D1
    • 




Common mistakes and debugging


    

  • Symptom: the probe cannot connect at all. Cause: wrong wiring, no common ground, target not powered, debug pins reused as GPIO by the firmware, or a too-fast probe clock. Fix: check power and ground, lower the probe clock, connect "under reset" so the firmware cannot reconfigure the pins first.
    • 

  • Symptom: breakpoints are ignored or "cannot be set". Cause: software breakpoints in flash, or more breakpoints than comparators. Fix: use hardware breakpoints; delete unused ones.
    • 

  • Symptom: the source line jumps around and variables show "optimised out". Cause: debugging an -Os or -O2 build. Fix: debug an -O0 or -Og build, or read the disassembly.
    • 

  • Symptom: an interrupt "never fires", and the program ends up in the default handler. Cause: the handler's name does not exactly match the weak symbol in the vector table. How to find it: list symbols and look for two handler names; or break in Default_Handler and read the exception number from xPSR. Fix: rename. (Forensic lab.)
    • 

  • Symptom: the chip resets every few seconds while you are halted. Cause: the watchdog keeps counting. Fix: freeze it in debug, using the chip's debug control register.
    •

Summary


    

  • A debug probe turns debugger commands into JTAG or SWD transactions; inside the chip they become memory accesses to the core's debug registers.
    • 

  • JTAG: four or five signals and a 16-state TAP machine; five TMS = 1 clocks always reset it; IDCODE bit 0 is 1; bypass is a one-bit delay.
    • 

  • SWD: two wires and short request/acknowledge/data packets.
    • 

  • Halting stops the core, not the peripherals.
    • 

  • Hardware breakpoints are needed in flash and are few; watchpoints stop after the access.
    • 

  • Inside a handler, xPSR's low bits name the exception and lr holds an exception-return code.
    • 

  • In emulation, LLDB hit a breakpoint in the reset handler (H1), followed SysTick into its handler, and caught ticks changing.
    • 

  • A misspelt handler name silently falls back to the weak default handler.
    •

Forensic lab answer key


Root cause. The handler was renamed from SysTick_Handler to SysTick_handler. C++ names are case-sensitive, so the new function does not replace the weak alias in startup.cc; the linker keeps the weak SysTick_Handler, which is an alias of Default_Handler. The symbol list shows SysTick_Handler (W) at 0x40, the same address as Default_Handler, and the renamed function as a separate symbol at 0xc4 that nothing calls. The vector-table word at 0x3c (exception 15 × 4) holds 0x41 = Default_Handler + Thumb bit. When SysTick fires, the core enters Default_Handler (xPSR = 0x8100000f, exception 15), which executes bkpt forever; ticks stays 0, so "3 ticks seen" never prints.


Evidence. forensic_nm.out: two handler names, one weak at 0x40. forensic_session.out: breakpoint 2 (Default_Handler) hit, breakpoint 1 never; xpsr 0x8100000f; ticks 0; word at 0x3c = 0x00000041. forensic_uart.out: only the banner. The timer works: an exception 15 did happen.


Fix. Rename back to SysTick_Handler. To make the mistake a build error: drop the weak aliases and declare each handler extern "C" in a shared header that the application must define (an undefined handler then fails to link), or keep the weak defaults but add a link-time check that every vector entry other than reserved ones and Default_Handler resolves to a non-default address.


How the evidence was made. The Lab Engineer wrote app_v2.cc with the one-line rename and ran the steps in run.sh; nothing was edited by hand.


Wrong answers and why. "SysTick is not enabled": exception 15 was taken, so it is. "Missing volatile": ticks is still volatile, and the handler never ran (its breakpoint never hit). Prevention: "Interrupt and exception handler names are fixed by the start-up file and are exempt from naming style; never rename them."
