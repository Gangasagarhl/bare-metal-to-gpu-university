Story hook

Amara has cooked in the big restaurant kitchen for a year: a head chef, shelves near the stove, a pantry down the corridor, a warehouse across town. One summer she helps at a take-away stand at the street market. Everything is in one small room. The cook stands at a single counter. The recipe book is laminated and screwed to the wall, so nobody can spill soup on it. A kitchen timer, a hot plate and the order window are all within arm's reach, each with its own knobs.

On her first morning nothing happens when she switches the lights on. There is no manager to tell her where to start. Then she notices the first page of the recipe book: "Stand here. Start with recipe 1." From that page on, the whole day follows.

A microcontroller is that take-away kitchen: a processor core, its program memory, a little working memory and many small machines called peripherals, all on one chip. When power arrives it reads a "first page" at a fixed place and starts from there. In this chapter you build that first page yourself, and the code that runs right after it, and you watch it run on an emulated microcontroller.

What you will be able to do

  • Name the blocks inside a microcontroller (core, flash, SRAM, bus, peripherals, clock and reset, debug port) and say what each one is for.
  • Explain what a Cortex-M core does at reset with the first two words of its vector table, and why the reset handler must copy .data and clear .bss.
  • Write freestanding start-up code, a vector table and a linker script, build them with a cross toolchain, and report the image size and RAM use (curriculum H1).
  • Boot the image in an emulated board and read its UART banner; compare with the start-up of a RISC-V machine.
  • Diagnose firmware that locks up after main() returns, from the disassembly and the emulator's lockup report.
Jargon box
Microcontroller (MCU)
Simple words: a whole small computer on one chip: processor, program memory, working memory and helpers for the outside world. Analogy: the take-away kitchen in one room. Precise: an integrated circuit that combines one or more processor cores with on-chip non-volatile program memory (usually flash), on-chip SRAM, a bus system and memory-mapped peripherals such as timers, serial ports and general-purpose I/O, designed to run one program directly on the hardware or under a small real-time OS. D2 D3
Peripheral
Simple words: a small machine on the chip that does one job, such as counting time or sending characters. Analogy: the kitchen timer, the hot plate, the order window. Precise: a hardware block on the chip, controlled by reading and writing its registers at fixed addresses (memory-mapped I/O, F1-41). D4 ch. 9 D3
Flash memory (program memory)
Simple words: memory that keeps the program when the power is off. Analogy: the laminated recipe book screwed to the wall. Precise: non-volatile memory on the chip from which the core fetches instructions and constant data; it is read like memory but written only through a special programming procedure. D2 (Flash is the subject of F1-74.)
SRAM
Simple words: the chip's small working memory, which forgets everything when power goes. Analogy: the counter top. Precise: static RAM on the chip holding variables, the stack and any heap; its contents are undefined after power-up unless start-up code writes them. D2 D7 [basic.start.static]
Vector table
Simple words: a list of addresses at a fixed place that tells the core where to start and where to go for each kind of event. Analogy: the first page of the recipe book: "stand here, start with recipe 1, if the doorbell rings go to recipe 5". Precise: on Armv7-M, a table of 32-bit words whose word 0 is the initial main stack pointer value and whose word 1 is the address of the reset handler, followed by the addresses of the handlers of the other exceptions and interrupts. D1 §2.1.3, §2.3.4 R1
Reset handler
Simple words: the first function that runs after power-on or reset. Analogy: recipe 1, the morning routine before any customer arrives. Precise: the code whose address is in vector-table word 1; it prepares memory for the language (copies .data, clears .bss, runs constructors if any) and calls main. D1 §2.1.3 D2
Start-up code
Simple words: the small program, written by you or your vendor, that sets the chip up before main. Analogy: opening the stand: lights, counter wiped, first ingredients out. Precise: the vector table plus the reset handler and default exception handlers, together with the linker-script symbols they rely on. D2 C1
Linker script
Simple words: a text file that tells the linker which memory exists and where each part of the program goes. Analogy: the floor plan saying which shelf holds what. Precise: input to the linker (GNU ld, LLD) with a MEMORY command describing regions and a SECTIONS command placing input sections into output sections at addresses in those regions, and defining symbols. D9 §MEMORY, §SECTIONS
Freestanding
Simple words: C++ with no operating system and almost no library underneath. Analogy: cooking without a manager or a supplier: you bring every tool yourself. Precise: a C++ implementation kind in which only a small set of headers is required and program start-up is implementation-defined; firmware is built this way (here with -ffreestanding -nostdlib -fno-exceptions -fno-rtti). D7 [intro.compliance.general] R1
Bare metal
Simple words: your program runs directly on the chip with nothing else below it. Analogy: the cook is also the manager. Precise: firmware that runs without an operating system or RTOS and owns all of the hardware, from the reset handler on (contrast with an RTOS or Linux in BR-05). D3 C1

Layer 1 — the kid explanation

A laptop is like the big restaurant: many rooms, many helpers, a manager (the operating system) who decides who does what. A microcontroller is the take-away stand. One cook, one room, one small book of recipes, a few appliances. It lives inside washing machines, keyboards, toys, battery chargers and the small controllers inside bigger computers. Nobody opens a menu on it; it just does its one job from the moment it gets power.

Because there is no manager, the chip itself must know how to start. It always looks at the same place first. There it finds two notes: where the stack of plates begins, and where recipe 1 is. Recipe 1 is your start-up code. It sets the counter up and then calls your main recipe.

The appliances are worked by knobs, and each knob has a fixed address. To make the order window show a letter, the program writes the letter into the window's knob. That is all a microcontroller program does all day: read knobs, think a little, turn knobs.

What the core does at reset


On an Armv7-M core, reset is handled by the hardware reading the vector table: it loads the main stack pointer from word 0 and the program counter from word 1, then starts executing. D1 §2.1.3 D2 Cortex-M cores execute only the Thumb instruction set, and the lowest bit of a code address in the table marks Thumb state; that is why the reset-handler entry in this chapter's image is 0x00000041 while the function itself starts at 0x00000040. D1 §2.1.3 R1 The compiler and linker set that bit for you when you put a function's address in the table; you can see it in the raw bytes of the image:




The first line holds four little-endian words. 00000120 read backwards byte by byte is 0x20010000, the initial stack pointer; 41000000 is 0x00000041, the reset handler; 9d000000 is 0x0000009d, Default_Handler with its Thumb bit. Words 7–10 and 13 are zero because those table positions are reserved in this core's exception list. R1 D1 §2.3.2 Table 2-16



Why start-up code exists at all


C++ promises your program that a global uint32_t boot_count = 7; holds 7 when main starts, and that a global uint32_t ticks; holds 0. D7 [basic.start.static] SRAM gives no such promise: after power-up its contents are not defined. D2 So something must write those values before main. On a PC the operating system's program loader and the C runtime do it; on bare metal there is nobody but you. D3 Your reset handler therefore:


    

  1. copies the initial values of the .data section from flash (where the linker stored them) to their place in SRAM;
    2. 

  2. writes zeros over the .bss section;
    3. 

  3. (in larger programs) calls the constructors of global objects;
    4. 

  4. calls main, and makes sure the core never "returns" from reset. D2 C1
    5. 



The linker script tells the reset handler where those sections are, through symbols such as __data_start and __bss_end. Their addresses are the information; there is no variable behind them. D9 §MEMORY, §SECTIONS The symbol list of the lab image shows them next to the real objects:




Notice boot_count at 0x20000000 (in RAM, type D for data) and __data_load at 0x0000034c (in code memory): the 7 is stored at the second address and copied to the first. ticks sits in .bss (type B). R1



Layer 3 — the engineer's depth


The reset contract differs per architecture


The "two words at a fixed place" contract is a property of the Armv7-M architecture that the Cortex-M3 implements, not of a chip vendor. D1 §2.1.3, §2.3.4 That is why the same startup.cc runs unchanged on QEMU's MPS2 board here and on QEMU's STM32F100 model in F1-74: both have a Cortex-M3 core. The vendor decides what comes after the system exceptions (which interrupt number belongs to which peripheral) and where memory is, so the vector table's length and the linker script's MEMORY block change from chip to chip. D2


A RISC-V core works differently: the privileged architecture leaves the reset address to the implementation, and the core starts fetching instructions there; it does not load a stack pointer from a table, so the first instructions must set sp themselves. D8 Trap handling uses a separate trap-vector base register rather than a table read at reset. D8 The lab includes a RISC-V version for QEMU's virt machine so you can compare the two contracts in running code (Listing 4).

Freestanding C++ rules for firmware


The curriculum's rules for kernel code apply to firmware too: no exceptions, no RTTI, no dependence on a C library or heap unless you supply one, typed access to registers, and comments naming the document section for every register you touch. C1 The build flags enforce part of this: -ffreestanding tells the compiler not to assume a hosted library, -nostdlib stops the linker adding start files and libraries, -fno-exceptions -fno-rtti remove the features that need runtime support. R1 One consequence showed up while the lab was being written: the container's cross setup for thumbv7m-none-eabi has no C++ standard library, so <cstdint> was not found and the listings include the compiler's own freestanding <stdint.h> instead. Range-for over a braced list also failed for the same reason (it needs <initializer_list>), which is why F1-76 iterates over a plain array.


Two language details matter in start-up code. First, every access to a peripheral register must be volatile, or the compiler may merge, reorder or remove it, because to the language a store that nobody reads looks useless. D7 [dcl.type.cv] Second, an infinite loop that does nothing observable is not a safe way to "stop" under the C++20 rules this lab compiles with (-std=c++20): the forward-progress clause lets an implementation assume that every thread eventually terminates, performs a volatile access, an atomic or synchronisation operation, or a library I/O call, so a loop that does none of these may be assumed to end. D7 [intro.progress] The current working draft adds "a trivial infinite loop" to that list and notes that such loops "cannot be removed nor reordered"; clang 18 with -std=c++20 does not apply that newer rule, and the forensic lab of this chapter shows exactly what it did with one. D7 [intro.progress] R5

How the hardware actually does it


Inside the chip, "reading the vector table" is two bus reads issued by the core's reset logic before the first instruction fetch; there is no software involved. D1 §2.1.3 On many microcontrollers the address the core reads at reset (address 0 on Armv7-M unless the vector-table offset register is changed later) can be backed by different memories depending on boot pins or option bytes: flash, a system boot ROM, or SRAM. The memory tree of QEMU's STM32F100 model in F1-74 shows such an arrangement, with the same flash visible both at 0 and at 0x08000000. D2 Writing a character to the UART's data register is one bus write; the UART then shifts the bits out on its transmit pin at the configured baud rate, independently of the core, which is why the code polls a "buffer full" status bit before the next write (F1-47). D4 ch. 9 D5 §4.3.1 Table 4-7 wfi ("wait for interrupt") asks the core to stop executing until an interrupt or similar event arrives, which on a real chip lets it enter a lower-power state. D1 §2.5.1


The register layout of the CMSDK APB UART used by Listing 2 is the one in the Cortex-M System Design Kit manual: DATA at offset 0x000, STATE at 0x004 with bit 0 "TX buffer full" (read-only), CTRL at 0x008 with bit 0 "TX enable", and a BAUDDIV register at 0x010 whose value is the peripheral clock divided by the baud rate (minimum 16). Worked example


Task. From the size report, the symbol list and the linker script alone, predict (a) where the initial value of boot_count is stored, (b) how many words the reset handler copies and clears, and (c) the address of the first byte the stack will use. Then check against the run.


    

  1. Where .data is stored. The script places .text first in CODE starting at 0. Its size is 0x34b = 843 bytes (the text column). The next output section, .data, is "> RAM AT > CODE", so its load address follows .text in CODE, rounded up to its 4-byte alignment: 0x34b rounds to 0x34c. Symbol list: __data_load = 0000034c. Correct.
    2. 

  2. Words copied. __data_end − __data_start = 0x20000004 − 0x20000000 = 4 bytes = 1 word. The loop in lines 24–26 of Listing 1 runs once.
    3. 

  3. Words cleared. __bss_end − __bss_start = 0x20000008 − 0x20000004 = 4 bytes = 1 word.
    4. 

  4. Stack. __stack_top = ORIGIN(RAM) + LENGTH(RAM) = 0x20000000 + 64 KiB = 0x20000000 + 0x10000 = 0x20010000. The Armv7-M stack is full-descending: a push first decrements SP by 4 and then stores, so the first word pushed lands at 0x2000FFFC. D1 §2.1.2
    5. 

  5. Check. The boot output prints initial SP 0x20010000, boot_count (expect 7) = 0x00000007 and ticks (expect 0) = 0x00000000, and the symbol list agrees with steps 1–3. To watch SP change push by push, use the debugger of F1-77.
    6.

Where the analogy breaks


    

  • The cook reads the first page; the core does not "read" anything. The core performs two fixed bus reads and loads the results into registers. If word 1 holds garbage, it jumps to garbage without any doubt; the forensic lab of F1-74 shows the result. D1 §2.1.3
    • 

  • A recipe book on the wall cannot be overwritten by accident; on some boards the program memory can. On QEMU's MPS2 board the program sits in RAM (the memory tree says ram), so a wild pointer could overwrite code. On a flash-based chip ordinary stores do not change flash, but the flash controller can erase and rewrite it on purpose. R2 D2
    • 

  • Appliances in a kitchen work on their own; peripherals often do not work at all until enabled. A peripheral may need its clock switched on, its pins assigned and an enable bit set before it responds; F1-75 is about exactly that.
    • 




Common mistakes and debugging


    

  • Symptom: nothing at all after reset; the debugger shows a strange SP and PC. Cause: the vector table is not at the address the core reads. How to find it: look at the first lines of the map file and at word 0/1 of the image. Fix: KEEP the table's section and place it first. (Course forensic lab, F1-74.)
    • 

  • Symptom: initialised globals hold random values; zero-initialised ones are not zero. Cause: the reset handler does not copy .data or clear .bss, or uses the wrong symbols. How to find it: print a known global first thing in main (as Listing 2 does). Fix: the two loops of Listing 1, with symbols from the same linker script. Beware: a missing .bss loop goes unnoticed whenever RAM happens to hold zeros at power-up, which nothing guarantees; test with a non-zero initialised value as Listing 2 does with boot_count.
    • 

  • Symptom: fatal error: 'cstdint' file not found. Cause: no C++ standard library for the bare-metal target. Fix: use the compiler's freestanding headers (<stdint.h>), or install a toolchain that ships a freestanding library.
    • 

  • Symptom: the board runs the banner, then resets or locks up. Cause: main returned into code that was never meant to run. How to find it: disassemble the end of the reset handler. Fix: end it with a loop that has a side effect. (This chapter's forensic lab.)
    • 

  • Symptom: characters missing on the serial line. Cause: writing to the data register without checking the "buffer full" bit. Fix: poll the status bit (Listing 2, lines 24–26) or use interrupts (F1-42).
    • 




Transition box

Where you came from: F1-41 and F1-42 described memory-mapped I/O and interrupts for any computer, and SP201 gave you C++ with an operating system and its runtime underneath. What carries over: registers at addresses, polling status bits, the idea of an interrupt handler, and C++ itself. D4 ch. 9 What changes: nothing runs before your code except the core's two reads of the vector table, so you write what an OS loader and C runtime used to do; there is no standard library, no heap and no exceptions unless you provide them; and a mistake in placement or in start-up code gives silence instead of an error message. Summary


    

  • A microcontroller puts a core, flash, SRAM, a bus and peripherals on one chip; peripherals are registers at fixed addresses.
    • 

  • QEMU's memory tree is real evidence of what an emulated board contains, and of what it does not model.
    • 

  • At reset an Armv7-M core loads SP from vector-table word 0 and PC from word 1 (bit 0 marks Thumb code).
    • 

  • Start-up code copies .data from flash to RAM, clears .bss, calls main and never returns.
    • 

  • The linker script decides every address; the map file and symbol list let you predict and check them.
    • 

  • The size report gives program-memory use (text + data) and static RAM use (data + bss); the stack comes on top.
    • 

  • RISC-V starts by executing code at an implementation-defined address and sets its own stack pointer.
    • 

  • An empty infinite loop is not a safe stop in C++; a loop with a side effect such as wfi is.
    •

Answers to Check yourself


    

  1. (a), (c), (d) are on the chip. (b) is not: storage, if any, is external flash or an SD card. (e) is not hardware at all; many microcontrollers run without one (bare metal), others run a small RTOS.
    2. 

  2. Word 0: the initial value of the main stack pointer. Word 1: the address of the reset handler, which becomes the program counter.
    3. 

  3. Bit 0 of a code address in the vector table marks Thumb state; the core clears it when loading the PC, so execution starts at 0x40. A common wrong answer is "the linker made a mistake": the symbol list shows the function at 0x40 and the table entry at 0x41 by design.
    4. 

  4. Good answers say: the initial values must live in non-volatile memory (flash) because RAM forgets them; at run time the variables must be in writable RAM; somebody has to copy them. On a PC the operating system's loader maps the file's data into memory and the C runtime starts the program, so you never see it.
    5. 

  5. Program memory: text + data = 843 + 4 = 847 bytes. Static RAM: data + bss = 8 bytes. data appears twice because its initial values are stored in program memory and its variables occupy RAM.
    6. 

  6. 0x20000000 + 16 KiB = 0x20000000 + 0x4000 = 0x20004000.
    7. 

  7. Armv7-M loads SP from the vector table in hardware before the first instruction; a RISC-V core just starts executing at its reset address, so the first instruction must set sp before any C++ code runs.

Forensic lab answer key


Root cause. The empty for (;;) {} has no observable side effect, and the C++20 forward-progress rule (the one clang 18 applies with -std=c++20; the current working draft exempts trivial infinite loops) allows the compiler to assume such a loop terminates; clang 18 at -Os therefore treated the end of Reset_Handler as unreachable and emitted nothing after bl main. When main returns to 0x98, that address is the first instruction of Default_Handler (symbol list: 00000098 T Default_Handler), which executes bkpt #0. Without a debugger attached, the breakpoint escalates to a HardFault; the HardFault vector also points to Default_Handler, which executes bkpt again, and QEMU reports a lockup: "can't escalate 3 to HardFault", with R15 (PC) = 0x00000098 and XPSR ending in 3 (exception 3, HardFault, active).


Evidence. The broken disassembly ends at 94: bl 0x9c <_Z4mainv>; the good one continues with 98: wfi and 9a: b 0x98. Symbols: Default_Handler at 0x98 in the broken image. Register dump: R15=00000098, XPSR=61000003.


Fix. Restore a loop with a side effect: for (;;) { asm volatile("wfi"); }. asm volatile is an observable effect the compiler must keep, so the loop is emitted, as the good disassembly shows.


How the fault was made. The Lab Engineer copied Listing 1 to broken_startup.cc and removed only the asm volatile("wfi"); line inside the final loop; the build uses the same flags as Listing 1.


Wrong answers and why. "The stack overflowed": SP (R13 = 0x2000ffd8) is near the top of RAM, far from any limit. "The UART crashed": the whole banner printed. "main must never return": true as a design rule, but here the reset handler was meant to catch the return; the real fault is the removed loop. Prevention: a review rule that every "stop here" loop in firmware contains wfi, a volatile access or asm volatile; an automated check that disassembles Reset_Handler and fails if its last instruction is a call; and keeping the start-up file under test with this lab's boot run.
