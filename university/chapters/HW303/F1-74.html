Story hook

The take-away stand from F1-73 gets a new helper, Ravi. On his first day he asks where things are. Amara draws him a plan of the room on a napkin: "Recipe book on the left wall, from the door to the window. Counter top under the window. The appliances along the back wall, each with a label. And the plates are stacked at the far end of the counter; the stack grows towards you."

Then she adds one more line. "The sauce recipe is in the book, but you cook with a copy on the counter. Every morning, copy it out of the book first." Ravi nods. A week later, a new "cleaned-up" recipe book arrives from head office. Its first page is gone, moved to the back as an appendix. The next morning, nobody knows where to stand or what to start with, and the stand stays dark.

A microcontroller's memory map is that plan of the room, and the linker script is the napkin you draw it on. This chapter reads the map of an emulated chip, follows each part of your program to its address, and uses the linker's own map file to find out why a "cleaned-up" start-up file left a board completely silent.

What you will be able to do

  • Read a microcontroller memory map and locate flash, SRAM, peripheral registers and the core's private region in it.
  • Explain the difference between the load address (LMA) and the run address (VMA) of a section, and which sections live in flash, in RAM, or in both.
  • Write a linker script for a chip from its memory sizes, and check the result with the map file and the size report.
  • Demonstrate with a running program where code, constants, initialised and zeroed variables and the stack really are, and that flash is not written by ordinary stores.
  • Diagnose "nothing happens after reset" from the map file and a debugger's view of the core at reset (the course forensic lab).
Jargon box
Memory map
Simple words: the list of which address ranges hold which memory or device. Analogy: the plan of the room on the napkin. Precise: the assignment of the processor's physical address space to on-chip flash, SRAM, peripheral register blocks, the core's private peripherals and unused (reserved) ranges, as documented by the vendor (for the RP2350 in its datasheet's address map; for an STM32 part in its reference manual and datasheet). D1 B3.1 D10 §2.2
Section
Simple words: a named block of a compiled program, such as "all the code" or "all the zeroed variables". Analogy: the labelled boxes the supplier delivers: recipes, spices, empty jars. Precise: a contiguous part of an object or executable file with a name, flags and alignment; compilers put code in .text, constants in .rodata, initialised variables in .data and zero-initialised variables in .bss (this lab's map file shows each of them). D3 §Basic Script Concepts R2
VMA (run address)
Simple words: the address where a part of the program is when the program runs. Analogy: the sauce recipe's place on the counter. Precise: virtual memory address of an output section: the address the code uses to access it at run time. On a microcontroller without an MMU it is a physical address. D3 §Basic Script Concepts
LMA (load address)
Simple words: the address where that part is stored in the image that gets flashed. Analogy: the sauce recipe's page in the book. Precise: load memory address of an output section: where its contents are placed in the loaded image; it differs from the VMA when start-up code must copy the section, as for .data. D3 §Basic Script Concepts, §Output Section LMA R2
Map file
Simple words: the linker's report of where it put everything. Analogy: the delivery note listing which box went on which shelf. Precise: a text file written by the linker (option -Map) listing each output section, its VMA, LMA, size and alignment, the input sections it contains and the symbols defined in them. D3 §Options (-Map) R2
Memory alias
Simple words: the same memory seen at two different addresses. Analogy: the recipe book has a copy of its first pages hanging by the door. Precise: an address range that decodes to the same physical memory as another range; QEMU's STM32F100 model shows its flash both at 0 and at 0x08000000, and the real MPS2 board with the AN385 image maps either an SSRAM or a block RAM at address 0, selected at boot. R1 D11 §3.1 Table 3-1
Garbage collection of sections
Simple words: the linker throws away parts of the program that nothing uses. Analogy: head office removes pages nobody refers to from the recipe book. Precise: with --gc-sections, the linker removes input sections not reachable from the entry symbol or from sections marked KEEP in the linker script. D3 §Options (--gc-sections), §Input Section and Garbage Collection R4

Layer 1 — the kid explanation

Every byte in a microcontroller has a house number, called its address. Some house numbers belong to the recipe book (flash), some to the counter (RAM), some to the appliances' knobs. The memory map is the street plan that says which numbers are where.

Your program arrives as one long book that is written into flash. But some parts must be changed while cooking, and you cannot write in the book. So, every morning, the first recipe copies those parts onto the counter. The plates (the stack) are kept at the far end of the counter and pile up towards the middle.

If the plan on the napkin is wrong, nothing warns you. The cook goes to a wrong place and stands there. That is why engineers keep the linker's map file: it is the real plan, written by the tool that built the book.

Layer 2 — the student explanation

Reading a memory map

Analogy first: a street plan with house numbers. Precisely: the vendor documents the address range of every on-chip memory and peripheral register block: the RP2350 datasheet has an address-map section, and Arm's AN385 note has memory-map tables for the MPS2 board. D10 §2.2 D11 §3.1, §3.7 For STM32 parts this is the job of the family reference manual and the datasheet of each part (not opened in this pass; box below). ST's own device header for the STM32F100xB carries the main addresses in machine-usable form: flash from 0x08000000 to 0x0801FFFF (128 KiB), SRAM from 0x20000000, peripherals from 0x40000000. D9 FLASH_BASE, FLASH_BANK1_END, SRAM_BASE, PERIPH_BASE For the emulated chip, QEMU itself prints the map it implements:



Three facts in this listing drive the rest of the chapter. First, STM32F100.flash appears twice, at 0x00000000 and 0x08000000, with the same size (0x1ffff + 1 = 131,072 bytes = 128 KiB): that is a memory alias. Second, both are marked rom in QEMU's model, while STM32F100.sram at 0x20000000 (0x1fff + 1 = 8,192 bytes = 8 KiB) is ram. Third, of the peripheral blocks from 0x40000000 upwards only the USARTs and SPI blocks are modelled (prio 0); timers, GPIO ports, the RCC clock controller and others are placeholders (prio -1000). R1 D6 §stm32, §monitor


Why the alias? A Cortex-M3 reads its vector table at address 0 after reset (the Armv7-M architecture lets a chip choose another reset value for the vector-table offset register, but by default it is zero). D8 §2.3.4 D1 B3.2.5 A chip that keeps its flash at 0x08000000 must therefore make some memory appear at 0; on the real STM32F100, which memory appears there is selected at boot (box below). QEMU's model always maps flash there, which is the "boot from main flash" case. R1

Layer 3 — the engineer's depth


Reading the map file


The map file is the linker's statement of fact. ld.lld writes one line per output section, input section and symbol, with columns VMA, LMA, size and alignment. D3 §Options (-Map) R2 The lab's map (debug sections removed from the end):




Read it top-down. .text starts at 0x8000000 with size 0x414. Its first input section is startup.o:(.vectors), size 0x40 = 64 bytes = 16 words: the vector table, at exactly the address the core will see through the alias at 0. The .data line has VMA 20000000 and LMA 8000414: the two addresses of Figure 2. __data_load equals the LMA, and __ram_used is 8 bytes. R2 Every claim in Layer 2 can be checked against this one file, which is why the map file belongs in every firmware build's artefacts.



RAM budget and the stack


The size report (in build.out) and the map give the static RAM use: .data + .bss = 8 bytes. The rest of the 8 KiB is shared by the stack (growing down from 0x20002000) and any heap. R2 The linker cannot know how deep the stack will grow; three techniques close the gap; the last two are also the ones Zephyr's documentation names for its threads (scanning the stack for its unused, still-initialised part, and build-time stack analysis), and the GNU linker provides ASSERT for the first. D14 "Querying stack usage" D3 §Miscellaneous Commands


    

  • Reserve and assert: define a minimum stack size in the linker script and make the link fail (ASSERT) if .data + .bss + stack do not fit.
    • 

  • Measure: fill free RAM with a pattern at reset and later count how much of it was overwritten (a "high-water mark"); the extension of F1-73's lab builds this.
    • 

  • Analyse: let the compiler report each function's stack frame (-fstack-usage in GCC and clang writes a .su file per source file D13 -fstack-usage) and add up the deepest call chain plus the interrupt handlers that can nest on top.
    • 



On a chip with a memory protection unit, a small inaccessible "guard" region below the stack turns a silent overflow into an immediate fault; Zephyr's guard-based stack overflow detection places such a write-protected region immediately before each stack. D1 B3.5 D14 "Thread Stack objects"



Why a missing KEEP is silent


Firmware is usually compiled with each function in its own section and linked with --gc-sections, so unused library code disappears. The linker decides what is "used" by following references from the entry symbol and from KEEP sections. D3 §Options (--gc-sections), §Input Section and Garbage Collection Nothing in a program refers to the vector table: the hardware reads it, but the linker does not know that. A vector table that is not matched by a KEEP pattern in the script is therefore garbage, from the linker's point of view, and is removed without error. The compiler's used attribute does not help here: it stops the compiler discarding the variable, not the linker discarding its section; on ELF targets that needs the retain attribute or a KEEP. D12 used, retain R4 The forensic lab is exactly this case.



Moving the vector table and running from RAM


Armv7-M cores have a vector-table offset register, so software can move the table after reset, for example to SRAM so a bootloader can install the application's handlers, or to an application image that starts after a bootloader in flash. D1 B3.2.5 Code can also be placed in RAM (a section with VMA in RAM and LMA in flash, copied like .data). D3 §Output Section LMA Both are linker-script work of the same kind as this chapter's, and both are used again in the bootloader milestones of Track H (H4). C1



How the hardware actually does it


An address on the bus is decoded by the chip's bus matrix: the upper bits select a target (flash interface, SRAM, a peripheral bridge, the core's private bus) and the lower bits select a location inside it; the RP2350 datasheet describes its version of this as an AHB and APB bus fabric with an address map. D10 §2.1, §2.2 An alias is two decoder entries pointing at the same target. Flash is read through a flash interface, and programming it goes through that interface's control registers (on the STM32F100 the Flash Int block at 0x40022000 in the memory tree, which ST's header calls FLASH_R_BASE). R1 D9 FLASH_R_BASE On the RP2350, a 16 kB cache sits in front of the external flash, and the flash is erased in 4,096-byte sectors and programmed in 256-byte pages: there is always an erase step before writing. D10 §4.4, §5.4.8 SRAM needs no such procedure: an ordinary store writes it, as the lab's store to RAM showed. R3 A bus error on an access becomes a BusFault on Armv7-M, or a HardFault if the BusFault cannot be taken. D1 B1.5.14

Worked example


Task. A colleague adds uint8_t rx_buffer[512]; and const char version[] = "v1.2"; to the lab program. Using the map conventions of this chapter, predict the effect on flash use, on static RAM use, on the address of counter, and on the free space left for the stack.


    

  1. Classify. rx_buffer has no initialiser: .bss, 512 bytes of RAM, 0 bytes of flash. version is const: .rodata, 5 bytes (four characters and the terminating zero) of flash, 0 bytes of RAM.
    2. 

  2. Flash. Before: text 1044 + data 4 = 1048 bytes (build.out). After: about 1048 + 5 = 1053 bytes, plus up to 3 bytes of alignment padding before the next 4-byte-aligned item. Far below 128 KiB.
    3. 

  3. RAM. Before: 8 bytes. After: 8 + 512 = 520 bytes (again up to a few bytes of alignment).
    4. 

  4. Address of counter. Both counter and rx_buffer are in .bss; the order inside the section depends on the compiler's output order, so counter stays at 0x20000004 or moves to 0x20000204. Do not predict it: read it in the new map file.
    5. 

  5. Stack. Free RAM for stack and heap: 8192 − 520 = 7672 bytes, ignoring padding. If the deepest call chain plus interrupts needs more, the stack silently runs into .bss. That is why the reserve-and-assert technique of Layer 3 exists.
    6.

Where the analogy breaks


    

  • A napkin plan can be redrawn any time; the chip's memory map is fixed in silicon. The linker script describes the map, it does not create it. If the script says RAM starts somewhere the chip has none, the linker happily places variables there and the program faults at run time. D3 §MEMORY
    • 

  • Copying a recipe takes a moment; copying .data is not free either, but the analogy hides the real cost of the alias. Through an alias, the "same memory at two addresses" really is one memory; nothing is copied. The copy happens only for sections you mark with different VMA and LMA. R1 R2
    • 

  • Plates stacked at the end of the counter are visible; a stack overflow is not. The stack has no wall in front of it unless you build one (a guard region, a check), and its growth into .bss corrupts variables without any message.
    • 




Common mistakes and debugging


    

  • Symptom: silence after reset; the emulator reports a lockup, or a real board does nothing. Cause: the vector table is not at the start of flash (missing KEEP, section name mismatch, wrong ORIGIN). How to find it: first lines of the map file; the debugger's SP and PC at reset. Fix: match the section name and keep it. (Forensic lab.)
    • 

  • Symptom: globals have wrong initial values only on the real board. Cause: the image was flashed without the .data load segment, or the copy loop uses VMA symbols for the source. How to find it: compare __data_load with the LMA in the map. Fix: use LOADADDR(.data).
    • 

  • Symptom: variables change "by themselves" in a deep call or under heavy interrupt load. Cause: stack overflow into .bss. How to find it: stack fill pattern, high-water mark, or a watchpoint on the last .bss word (F1-77). Fix: reserve and assert a stack size; reduce stack use.
    • 

  • Symptom: link error "will not fit in region". Cause: image larger than LENGTH. Fix: check the size report and the map for unexpected large objects (a printf pulled in, a table not marked const that landed in .data and so costs RAM and flash).
    •

Summary


    

  • A memory map assigns address ranges to flash, SRAM, peripheral blocks and the core's private region; the chip fixes it, the linker script describes it.
    • 

  • QEMU's memory tree showed flash (read-only, aliased at 0), 8 KiB SRAM and which peripherals the model implements.
    • 

  • .text and .rodata live in flash; .data has its LMA in flash and its VMA in RAM; .bss is RAM only; the stack grows down from the end of RAM.
    • 

  • The map file states every placement; the program's own address printout agreed with it.
    • 

  • An ordinary store to flash had no effect on the model; real chips program flash through the flash interface.
    • 

  • The stack is not in any size report: reserve, assert and measure it.
    • 

  • Nothing references the vector table, so without KEEP (or with a mismatched section name) the linker removes it silently and the core starts from garbage.

Forensic lab answer key


Root cause. startup_v2.cc puts the vector table in a section named .isr_vector (a common name in vendor templates), while the linker script keeps *(.vectors). Nothing refers to the table, so --gc-sections removed it ("removing unused section startup_v2.o:(.isr_vector)"); the image is 64 bytes smaller (980 instead of 1044 bytes of text) by exactly the 16-word table. Flash now starts with Reset_Handler's code (new map: 8000000 ... startup_v2.o:(.text)). At reset the core read the first two words of code as if they were table entries: SP = 0x466fb580 (the instruction bytes 80 b5 6f 46: push {r7, lr}; mov r7, sp) and PC = 0x0004f240 (the next code bytes, Thumb bit removed). The first instruction fetch from 0x0004f240 hits an unmapped address, the fault cannot be handled (no table), and QEMU reports "Lockup: can't escalate 3 to HardFault"; its dump shows SP 0x466fb560, which is the garbage SP minus the 32-byte exception frame. On a real chip there is no message: the core just stays locked up.


Evidence. forensic_build.out line 1; forensic_map.out line 3; forensic_reset.out: sp = 0x466fb580, pc = 0x0004f240, memory read at 0x0 showing those same words, and image lookup --address 0x08000000 naming Reset_Handler().


Fix. Either rename the section back to .vectors, or change the script to KEEP(*(.vectors .isr_vector)). The script fix is more robust when you mix files from different templates; keep the name in one documented place.


How the fault was made. The Lab Engineer copied startup.cc to startup_v2.cc and changed only the section name in the attribute (plus the comment); everything else, including the linker script and build flags, is identical.


Wrong answers and why. "The USART is not enabled": the program never reaches main; the debugger shows PC outside any function at reset. "Wrong clock configuration": there is no clock code in this program, and the failure happens before the first instruction. "QEMU is broken": the same QEMU boots the good image. Prevention: a post-link check that reads the first two words of the image and fails unless word 1 points into Reset_Handler (with the Thumb bit) and word 0 lies inside RAM; or a script ASSERT on the address of vector_table; and reading the map file in code review when start-up files change.
