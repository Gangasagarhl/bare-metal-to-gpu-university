Story hook

Analogy

Four kitchen halls stand in a row, joined by a delivery service. Each hall has its own full copy of the same recipe book, and each is trying to improve the same soup. Every morning the head cooks share one big crate of tasting notes: Amara's hall reads the first quarter, Bao's the second, Chidi's the third and Dana's the last. Each hall writes down how it would change the recipe. Before lunch, the four lists travel around the halls on the delivery carts until every hall holds the sum of all four, and every hall makes exactly the same change to its book.

For a week this works beautifully. Then the delivery service gets busy, and the cooks notice something odd: they spend more time waiting for the carts than tasting. Bao suggests sending each page of corrections as soon as it is written instead of waiting for the whole list. Amara warns that a cart for every single line would be worse still. Who is right?

What you will be able to do

  • Explain data parallelism: replicas, shards of the global batch, gradient all-reduce, and why every replica must apply the same update.
  • Prove with a run that N-rank data-parallel training equals one-process training on the same global batch within a stated tolerance, and explain why it is not bit-for-bit equal.
  • Implement gradient buckets that are sent with non-blocking all-reduce while the backward pass continues.
  • Predict the step time of a data-parallel job with the alpha-beta model for different bucket sizes, and choose a bucket size.
  • Diagnose a step-time regression from a communication-stream trace.
  • State the limits of data parallelism (memory per replica, global batch size) that motivate the next three chapters.
Jargon box
Data parallelism
Simple words: every GPU trains a full copy of the model on a different part of the data, and the copies agree after every step. Analogy: every hall has the whole recipe book and reads a different part of the tasting notes. Precise: a training strategy in which N processes each hold a complete replica of the model, each computes the gradient of the loss on its shard of the global batch, the gradients are summed (all-reduce) and averaged, and every replica applies the identical optimizer update, so the replicas stay identical. D1 D2
Model replica
Simple words: one complete copy of the model's parameters, kept by one process. Analogy: one hall's copy of the recipe book. Precise: the full parameter set (and, in plain data parallelism, the full gradient and optimizer state) held by one rank; correctness requires all replicas to hold the same values after each step. D1
Global batch
Simple words: all the training examples used for one update, counted over all GPUs together. Analogy: the whole crate of tasting notes for one morning. Precise: the set of B samples whose mean loss gradient defines one optimizer step; with N ranks each rank processes a shard of B/N samples (the local or per-rank batch). Changing N while keeping the per-rank batch fixed changes B, and with it the optimisation. D1 D6
Gradient bucket
Simple words: a group of gradients that are sent together in one all-reduce. Analogy: one cart loaded with several pages of corrections. Precise: a contiguous group of parameter gradients, filled in the order the backward pass produces them, whose all-reduce is launched as soon as every gradient in it is ready; the bucket size trades the per-message cost (alpha) against how early communication can start. D1
Communication-computation overlap
Simple words: sending the first results while still computing the rest. Analogy: the carts leave with the first pages while the cooks write the next ones. Precise: running the gradient all-reduce of finished buckets concurrently with the backward computation of earlier layers (on a separate stream or with non-blocking collectives), so that only the communication that cannot be hidden ("exposed communication") adds to the step time. D1 D5
Scaling efficiency
Simple words: how close N GPUs come to being N times faster than one. Analogy: four halls finishing the work in a quarter of the time would be 100 %. Precise: for a fixed global batch, efficiency = T1 / (N × TN), where T is the time per step; for a fixed per-rank batch (weak scaling), efficiency = T1 / TN. Always state which one you report (milestone F3 asks for it). M1

Layer 1 — the kid explanation

Training a model means showing it many examples and nudging its numbers a little after each group of examples. With four GPUs, the easiest way to go faster is to give each GPU its own complete copy of the model and a quarter of each group. Each GPU works out which nudge its quarter wants. Then the GPUs add their nudges together, so that each one knows the nudge the whole group wants, and every GPU makes the same nudge. Because they all start the same and always make the same nudge, the copies never drift apart.

Adding the nudges together takes time, because the numbers must travel between GPUs. The trick is to start sending the first nudges while the GPU is still working out the rest.

Layer 2 — the student explanation

The step, precisely

The kitchen picture first: each hall reads a different part of the tasting notes, and the corrections are summed on the carts. Precisely: let the model have parameters p, let the loss of one sample i be ℓi(p), and let one step use a global batch of B samples. Plain gradient descent on one process computes g = Σi ∇ℓi(p) over the batch and updates p ← p − η g / B. Because a sum can be split into parts, rank r of N can compute the partial sum gr over its own B/N samples; an all-reduce with the sum operation gives every rank g = Σr gr, and every rank applies the same update. That is the whole of data parallelism: the mathematics of the step is unchanged, only the work is split. D1 D2

Three conditions keep the replicas identical, and each one is a classic bug when broken: all replicas start from the same parameters (one rank's initial values are broadcast to all); every rank divides by the global batch B, not by its shard size, or every rank averages the summed gradient over N after averaging its own shard; and every rank runs the same optimizer with the same hyperparameters and the same random choices. F8-06's forensic lab shows what happens when the first two are broken. D1

The acceptance test, run with MPI

Milestone F3 states the test for this idea: with fixed seeds, N-GPU training produces the same loss curve as single-GPU training within a stated tolerance, taking the effective batch size into account. M1 Listing 1 runs it with MPI processes in place of GPUs: a two-layer network (4 inputs, 8 hidden units with tanh, 1 output; 49 parameters), a global batch of 32, 60 steps of gradient descent. Rank 0 also trains a reference model on the whole batch alone and prints the largest difference between any parameter of the two after every step. R1 shows the result on 1, 2 and 4 ranks:

  • On 1 rank the difference is exactly 0: the same additions in the same order.
  • On 2 and 4 ranks the difference is not 0 but at most 5.96 × 10−8, inside the stated tolerance of 10−5; the losses agree to the seventh significant digit, with one-digit differences in the last place on some steps.
  • The replica spread (the largest difference of one parameter between any two ranks) is 0 on every printed step.

Why not exactly equal on 2 and 4 ranks? Because the reference adds 32 per-sample gradients in one order, while the data-parallel run adds 8 per rank and then adds the four partial sums in an order chosen by the MPI library. Floating-point addition rounds after every operation, so it is not associative: a different order gives a slightly different sum. That is why the milestone says "within a stated tolerance", and why the replica spread is 0: every rank receives the same all-reduce result, so the replicas agree with each other exactly even though they differ slightly from the reference. D8 R1

Buckets and overlap

In the halls, the carts can leave with the first pages while the cooks write the rest. The backward pass computes gradients from the last layer to the first, so the last layer's gradients are finished long before the first layer's. Instead of waiting for all gradients and launching one big all-reduce, an implementation groups gradients into buckets in the order they become ready and launches each bucket's all-reduce as soon as it is full, on a communication stream (NCCL, RCCL) or as a non-blocking collective (MPI), while the backward pass continues. The PyTorch DDP paper describes this design; milestone F6 asks you to build it. D1 M1

Listing 1 does this on a small scale: the output layer's gradient (8 weights, 1 bias, plus the loss sum: 10 values) is bucket 0 and is sent with MPI_Iallreduce before the hidden layer's gradient (40 values) is computed; then bucket 1 is sent, and MPI_Waitall waits for both. Non-blocking collectives are part of the MPI Standard; the Open MPI 4.1.6 header in the build container declares MPI_Iallreduce and reports MPI version 3.1. D5 L1 On one computer with tiny buckets the overlap saves nothing measurable, and the run does not claim it does; what the run proves is that the bucketed order of operations gives the correct result. The timing question is answered with a model.

Layer 3 — the engineer's depth

A model of the step

The engineer's version of the cart question is a performance model. Let a model have L layers with equal backward time tb and gradient size s bytes each, forward time tf per layer, and buckets of k layers. With the ring all-reduce of F8-02 and the alpha-beta model of F8-03, one bucket of S = k s bytes on N ranks takes

TAR(S) = 2 (N − 1) (α + S / (N β))

where α is the fixed cost per message and β the bandwidth of one link. D7 R2 Bucket j is ready when the backward pass has finished its k layers; it starts when it is ready and the previous bucket has finished (one communication stream); the step ends when both the backward pass and the last all-reduce have finished. Listing 2 computes exactly this.

Two forces pull in opposite directions:

  • Small buckets start early but pay α many times. With L/k buckets, the total α cost is (L/k) × 2 (N − 1) α; for 64 one-layer buckets in R2 that alone is 64 × 14 × 50 µs = 44,800 µs, more than four times the whole computation.
  • Large buckets pay α rarely but start late. With one bucket, nothing overlaps: the whole all-reduce comes after the backward pass.

The best bucket lies between, and its position depends on α, β, N and the compute time per layer. R2's sweep, for invented values chosen to show the effect (64 layers, 0.5 MiB per layer, N = 8, α = 50 µs, β = 25 GB/s), finds the best at 16 layers (8 MiB): a step of 10,887 µs against 9,600 µs of pure computation, with 1,287 µs exposed; one 32 MiB bucket gives 12,649 µs; one-layer buckets give 50,449 µs. R2 These numbers are a property of the invented values, not of any real GPU or network; the method is what carries over.

Note

The model assumes the all-reduce does not slow the computation down. On a real GPU, collective-library kernels run on the same GPU as the training kernels and use some of its resources, and both share memory bandwidth, so overlapped communication can stretch the backward pass. Measure the stretch with a profiler (milestone F6 asks for a timeline); do not assume it is zero.

Not verified — check before relying on this

From memory, not opened in this build: PyTorch DDP's default bucket size is a few tens of MiB and is a constructor argument; DDP builds buckets in reverse parameter order and may rebuild them after the first iteration from the order gradients actually arrived; NCCL kernels occupy a number of GPU multiprocessors that can be limited with environment variables. Check the PyTorch DDP paper (D1, sections on gradient bucketing) and the NCCL and RCCL documentation (D3, D4, environment variables) for the versions you use. None of these names or values is used by this chapter's code.

Strong and weak scaling, and the global batch

There are two ways to use more ranks. With a fixed global batch (strong scaling), each rank gets fewer samples, the computation per rank shrinks as 1/N, but the gradient all-reduce does not shrink: its size is the model's size, and its ring time grows towards 2 S / β as N grows. The communication share therefore rises with N, and overlap hides less and less. With a fixed per-rank batch (weak scaling), the computation per rank stays constant and the global batch grows as N; scaling efficiency looks better, but the optimisation is no longer the same: a larger global batch makes fewer, larger steps per epoch, and the learning rate and schedule must be retuned. The literature on large-batch training studies rules for that retuning; they are hyperparameter recipes, not guarantees, and this chapter does not rely on any of them. D1 D6

When you report scaling (milestone F3 requires it), state which kind, the global batch, and the measured times. A data-parallel speed-up obtained by silently growing the batch is not the same result.

What data parallelism cannot fix

Every replica holds the whole model: parameters, gradients and optimizer state. Data parallelism therefore never lets you train a model that does not fit on one GPU; adding GPUs only adds copies. Three remedies follow in this course: split each layer across GPUs (tensor parallelism, F8-13), split the layers across GPUs (pipeline parallelism, F8-14), and stop replicating the optimizer state, gradients and parameters (sharding, F8-15). Large jobs combine them, for example tensor parallelism inside a node, pipeline stages across nodes and data parallelism over everything else; the Megatron-LM paper describes such a combination. D9

How the hardware actually does it

In the halls, the carts are the links between GPUs and the roads between buildings. On a real system each replica's parameters, gradients and optimizer state live in its GPU's memory. The gradient all-reduce is executed by a collective library (NCCL on NVIDIA GPUs, RCCL on AMD GPUs, or a GPU-aware MPI, DG402) as GPU kernels that move data over the links F8-04 measured: NVLink, xGMI or PCIe inside a node and the network between nodes. The library's operations are enqueued on a GPU stream, so they are asynchronous with respect to the host and can run concurrently with compute kernels on other streams; that is the mechanism behind bucketed overlap. D3 D4 D1

The α and β of the model are properties of the slowest link on the ring and of the library's algorithm; F8-03 and F8-04 showed how to measure them with bus-bandwidth curves. Use your measured values in Listing 2, not the invented ones. No GPU timing of any kind was measured in this build.

Worked example

The question: for the setup of R2 (64 layers, 0.5 MiB of gradient per layer, forward 50 µs and backward 100 µs per layer, N = 8, α = 50 µs, β = 25 GB/s), what is the step time with buckets of 16 layers? The arithmetic uses 1 MiB = 1,048,576 bytes and 25 GB/s = 25,000 bytes per µs.

  1. Bucket size: 16 × 0.5 MiB = 8 MiB = 8,388,608 bytes. Per ring message: S/N = 1,048,576 bytes, which takes 1,048,576 / 25,000 = 41.94 µs, plus α = 50 µs: 91.94 µs.
  2. One all-reduce: 2 (N − 1) = 14 messages on the critical path: 14 × 91.94 = 1,287.2 µs.
  3. Computation: forward 64 × 50 = 3,200 µs; backward 64 × 100 = 6,400 µs, ending at 9,600 µs.
  4. Bucket readiness: every 16 layers of backward = 1,600 µs, so at 4,800, 6,400, 8,000 and 9,600 µs.
  5. Communication stream: bucket 0 runs 4,800–6,087; bucket 1 is ready at 6,400 (the stream is free), runs 6,400–7,687; bucket 2 runs 8,000–9,287; bucket 3 runs 9,600–10,887.
  6. Step time: max(9,600, 10,887) = 10,887 µs; exposed communication 1,287 µs, exactly one bucket: the last bucket can never overlap, because nothing is computed after it.

R2's row for 16 layers prints 10,887 µs and 1,287 µs exposed: the hand calculation and the program agree. R2 The last step suggests a rule worth remembering: with perfect overlap, the exposed time is at least the all-reduce time of the last bucket, which argues for buckets that are not too large at the end of the backward pass.

Where the analogy breaks


    

  • The halls do not really "agree". In the story the cooks compare lists; in data parallelism nobody checks anything: the replicas stay equal only because they start equal and apply bit-identical updates. A replica that starts different stays different forever without any warning (F8-06's forensic lab shows a constant replica gap).
    • 

  • Carts carry pages; all-reduce carries sums. A ring all-reduce does not deliver every hall's list to every hall; it delivers the sum, in chunks, with every link busy at once (F8-02). The total traffic per rank is about twice the gradient size, whatever N is.
    • 

  • One cart per line is not only "busy"; it is slower in a precise way. The analogy suggests congestion; the real cost is the fixed α per message, paid 2 (N − 1) times per all-reduce, which a model can compute before you run anything.
    • 

  • Real halls could taste in any order. The floating-point sums depend on the order of additions, so "the same recipe change" is the same only up to rounding unless the order is fixed.
    • 




Common mistakes and debugging


    

  • Replicas drift apart. Symptom: the replica spread is not 0. Cause: no initial broadcast, or a rank-dependent random choice in the update (for example dropout masks are fine, but a rank-dependent optimizer seed is not). Find it: log a parameter checksum per rank at step 0 and every k steps. Fix: broadcast at start; derive every random choice that affects parameters from shared seeds. (F8-06's forensic lab.)
    • 

  • Loss explodes only with N > 1. Symptom: the N-rank curve leaves the 1-rank curve at once. Cause: gradients summed but divided by the shard size, or not divided at all, so the step is N times too large. Find it: compare the first step's update with the reference. Fix: divide the sum by the global batch exactly once.
    • 

  • Ranks stop in a collective forever. Symptom: no progress, no error. Cause: ranks launched buckets in different orders or different sizes (for example, a parameter unused on one rank so its bucket never fills). Find it: log the bucket sequence per rank; F8-01's forensic lab and F8-16 show the hang. Fix: identical bucket order and sizes on every rank.
    • 

  • Overlap made it slower. Symptom: step time rose after enabling small buckets. Cause: α paid many times (R2: 1-layer buckets). Find it: count the all-reduces per step in a trace. Fix: larger buckets; check with the sweep.
    • 

  • Bit-for-bit comparisons fail. Symptom: N-rank parameters differ from 1-rank in the eighth digit. Cause: summation order (R1). Fix: compare with a tolerance stated in advance; check the replica spread separately, which must be exactly 0.
    • 

  • "Scaling efficiency 98 %" that is not. Cause: the per-rank batch was fixed, so the global batch grew. Fix: report strong and weak scaling separately, with the batch sizes.
    •

Summary


    

  • Data parallelism: every rank holds a full replica, computes the gradient sum of its shard, all-reduces it, and applies the identical update.
    • 

  • The replicas stay identical only if they start identical, divide by the global batch exactly once, and run identical updates.
    • 

  • N-rank results equal 1-rank results within a tolerance, not bit for bit, because floating-point summation order changes (R1: largest difference 5.96 × 10−8, replica spread 0).
    • 

  • Buckets launched while the backward pass continues hide communication; small buckets pay α many times, large buckets start late.
    • 

  • A step-time model with the ring formula predicts the trade-off; in R2's invented setup the best bucket was 8 MiB and one-layer buckets were almost five times slower.
    • 

  • Report scaling with the global batch stated; growing the batch changes the training.
    • 

  • Data parallelism never reduces memory per GPU: the next chapters split layers, split the model into stages, and shard the replicated state.
    •
