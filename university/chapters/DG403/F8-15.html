Story hook

Analogy

Eight halls of the kitchen cook the same menu from the same recipe book. Each hall also keeps a thick notebook next to the book: for every line of every recipe, two running notes on how the line has been changing lately. Every evening, all eight halls agree on the same corrections, and every hall updates every line of its own notebook in exactly the same way. Eight identical notebooks, eight times the same work.

Imani, the head cook, notices that the notebooks now fill more shelves than the food. "Each hall keeps one eighth of the notebook," she says. "Hall 1 keeps the notes for pages 1 to 50, hall 2 for pages 51 to 100. Each hall corrects only its own pages and then reads the corrected recipe lines aloud to the others." The shelves empty. Nobody tastes any difference in the food. But one evening, a hall loses its pages, and the next morning the food from seven halls tastes slightly wrong.

What you will be able to do

  • Count the memory of the model states (parameters, gradients, optimizer state) per GPU for plain data parallelism, with a stated number of bytes per parameter.
  • Explain the three levels of sharding described in the ZeRO paper: optimizer states, gradients, parameters; and what each costs in communication.
  • Show, with an MPI program, that sharding the optimizer state with reduce-scatter and all-gather gives the same weights as plain data parallelism.
  • Recognise the checkpointing consequence: a sharded state must be saved and restored per rank.
  • Use the calculator in a design review: which level of sharding a model needs on a given number of GPUs.
Jargon box
Model states
Simple words: everything training keeps about the model itself: the weights, their gradients and the optimizer's notes. Analogy: the recipe book, tonight's corrections and the notebook of running notes. Precise: the parameters, the gradients and the optimizer state, as distinct from the activations (which depend on the batch) and temporary buffers; the ZeRO paper uses this term for the memory it partitions. D1
Optimizer state
Simple words: the extra numbers an optimizer keeps for every weight between steps. Analogy: the two running notes for every recipe line. Precise: per-parameter tensors an optimizer carries from step to step; Adam keeps a first-moment (moving average of the gradient) and a second-moment (moving average of its square) estimate for every parameter, so two values per parameter, plus, in mixed-precision training, an FP32 master copy of the parameters. D2 D3
Sharded optimizer state
Simple words: each data-parallel GPU keeps the optimizer state for only its own part of the weights. Analogy: each hall keeps only its own pages of the notebook. Precise: the optimizer state of P parameters is partitioned into N disjoint slices of P/N parameters across the N data-parallel ranks; each rank updates only its slice and the updated parameters are then all-gathered; the first of the ZeRO paper's three stages. D1
ZeRO stages
Simple words: three levels of how much is split among the data-parallel GPUs. Analogy: first the notebook, then also tonight's corrections, then also the recipe book itself, read aloud page by page when needed. Precise: in the ZeRO paper's terms, partitioning of the optimizer states (Pos), additionally of the gradients (Pos+g), and additionally of the parameters (Pos+g+p); this course calls them stages 1, 2 and 3, as implementations commonly do. D1
Reduce-scatter
Simple words: add up everyone's arrays and give each rank only its own part of the sum. Analogy: passing bowls around the round table, each cook keeping only the bowl for their own pages. Precise: the collective that reduces N equal-length inputs element-wise and scatters the result in N equal blocks, block r to rank r; in MPI MPI_Reduce_scatter_block; with a ring, each rank sends (N − 1)/N of the data, half of an all-reduce (F8-02). D4 L1

Layer 1 — the kid explanation

When many computers train the same model, each one usually keeps a complete copy of everything: the model, its corrections and the optimizer's notes. The notes are often the biggest part, and every computer works out exactly the same notes. That is wasteful. Instead, each computer can keep the notes for only its own piece of the model, update only that piece, and then tell everyone the new values. The answer is the same; the memory is much smaller; and the amount of talking stays the same. The price: when you save your work, each computer has to save its own piece, and every piece is needed to start again.

Layer 2 — the student explanation

Where the memory goes

The halls' notebooks are the optimizer state. To count it, fix how many bytes each parameter needs. This chapter uses one configuration throughout, from the ZeRO paper's analysis of mixed-precision training with Adam: 2 bytes for the FP16 parameter, 2 bytes for the FP16 gradient, and 12 bytes of optimizer state (an FP32 master copy of the parameter, and Adam's two FP32 moments), 16 bytes per parameter. The calculator below makes the 2 + 2 + 12 split an input, so the arithmetic does not depend on these memories; check D1 (section on model states) before quoting the paper's figures.

With Ψ parameters, plain data parallelism stores 16Ψ bytes on every GPU, however many GPUs there are, because every rank is a full replica (F8-12). For Ψ = 1010, Listing 1 prints 149.01 GiB per GPU, more than the invented 64 GiB budget of the example, and computes that no model larger than 4.29 × 109 parameters fits that budget with plain data parallelism, whatever N is. Stage 1: shard the optimizer state

Every rank computes the same Adam update for every parameter, from the same averaged gradient and the same moments. That work and memory can be divided: rank r keeps the moments (and master weights) of slice r only, P/N parameters. One step becomes:

  1. Each rank computes its local gradient for all P parameters (its shard of the batch, as in F8-12).
  2. Reduce-scatter: rank r receives the sum over all ranks of slice r of the gradient, and nothing else.
  3. Rank r runs Adam on its slice: P/N parameters, with its P/N moments.
  4. All-gather: every rank receives every updated slice, so all ranks again hold the same full parameters for the next forward pass.

Reduce-scatter followed by all-gather is exactly how the ring all-reduce of F8-02 works internally, so the bytes sent per rank are the same as for plain data parallelism: 2 (N − 1)/N times the gradient size. The ZeRO paper makes this point: the first two stages cost no extra communication. D1 Listing 1's "sent per GPU per step" column shows equal values for stages 0, 1 and 2. R1

The same weights

Listing 2 runs both trainers side by side on a linear model with 1,024 parameters and Adam: the plain one (all-reduce, Adam on everything, 8,192 bytes of moments per rank) and the sharded one (reduce-scatter, Adam on 256 parameters, all-gather, 2,048 bytes at N = 4). After 50 steps the largest difference between their weights is 0 on 1 and 2 processes and 7.45 × 10−8 on 4, within the tolerance of 10−5; both reach the same distance to the true weights, 11.5682. R2 The small difference at N = 4 is the floating-point effect of F8-12: Open MPI's reduce-scatter and all-reduce may add the four contributions in different orders. Adam itself is applied element by element, so splitting it into slices changes nothing.

Stages 2 and 3

Each rank, after the reduce-scatter, needs only its own slice of the summed gradient. Stage 2 keeps only that slice, so gradients drop from 2Ψ to 2Ψ/N bytes per rank (in a real implementation, buckets of gradient are reduce-scattered and dropped during the backward pass). Communication is still the same. Stage 3 also shards the parameters: each rank stores only its slice, and before each layer's forward (and again before its backward) the layer's parameters are all-gathered from the ranks that own them, used, and dropped. Memory per rank becomes 16Ψ/N; communication rises to about 1.5 times that of plain data parallelism in the ZeRO paper's analysis, because the parameters are gathered twice per step. D1 Listing 1's example B: 149.01, 39.00, 20.66 and 2.33 GiB per GPU for stages 0 to 3 on 64 GPUs; 36.67 GiB sent per GPU per step for stages 0 to 2 and 55.01 GiB for stage 3. R1

Layer 3 — the engineer's depth

Reading the formula, not the slogan

Per rank, with bp, bg, bo bytes per parameter for parameters, gradients and optimizer state:

StageModel states per rankSent per rank per step (ring)
0 plain(bp + bg + bo) Ψ2 (N − 1)/N · bg Ψ
1 optimizer states(bp + bg) Ψ + bo Ψ/N2 (N − 1)/N · bg Ψ
2 + gradientsbp Ψ + (bg + bo) Ψ/N2 (N − 1)/N · bg Ψ
3 + parameters(bp + bg + bo) Ψ/N3 (N − 1)/N · bg Ψ

These are the formulas of Listing 1, lines 17–30. R1 Two consequences matter in a design review:

  • Stages 1 and 2 have a floor. As N grows, their memory tends to (bp + bg) Ψ and bp Ψ: the replicated part. Doubling the GPUs does not halve it. Stage 3 alone scales as 1/N.
  • The optimizer matters. Listing 1's third case, FP32 weights with plain SGD (4 + 4 + 0 bytes): stage 1 saves nothing, because there is no optimizer state to shard; 74.51 GiB per GPU at stages 0 and 1. R1 Sharding helps exactly where the optimizer state is large, which is why the example uses Adam.

Stage 3 is a different kind of program

Stages 1 and 2 change only the end of the step. Stage 3 changes the inside of the forward and backward passes: a layer cannot run until its parameters have been gathered. Implementations prefetch the next layer's parameters while the current layer computes, in the same spirit as F8-12's gradient buckets overlap the backward pass; when that prefetch is not hidden, the step slows down. The 1.5× communication of Listing 1 is the volume; whether it costs time is a question of overlap, answered by a timeline (F8-12's method), not by the table.

Sharding against the other strategies

Sharding reduces model-state memory without changing the mathematics, like data parallelism; it does not reduce activation memory, and it does not split a single layer's computation. Tensor parallelism (F8-13) splits each layer's weights and computation inside a group, with activation all-reduces in every layer; pipeline parallelism (F8-14) splits the layers and pays a bubble. In a combined plan, sharding is applied across the data-parallel dimension: each data-parallel group shards the states of its (tensor, pipeline) part of the model. D1 D5

Not verified — check before relying on this

From memory, not checked in this build: PyTorch provides sharded data parallelism as "Fully Sharded Data Parallel" (FSDP), with a sharding strategy option whose values include full sharding (comparable to stage 3) and a gradient-and-optimizer sharding mode (comparable to stage 2), and DeepSpeed exposes the ZeRO stages as a configuration value 0–3. Names, defaults and exact behaviour change between versions; read the documentation of the installed version before relying on any of them. This chapter's listings use only MPI calls whose declarations were opened (L1).

Checkpoints of sharded state

With plain data parallelism, any rank's copy of the optimizer state is the whole state; saving rank 0's copy is enough. With sharding, the state is the union of N different slices, and a checkpoint must hold all of them: one file per rank, or a collective write into one file, and a restart that gives each rank back its own slice (or redistributes the slices if N changes). Listing 2 with ckpt=25 saves and reloads one file per rank at step 25 and still matches (R3). The forensic lab is the version that saves only rank 0's file. R3 F8-16 builds the full checkpoint-and-restart machinery.

How the hardware actually does it

The model states live in the GPU's own memory (HBM on data-centre GPUs); sharding decides how much of it each GPU must reserve before the first activation is stored. The reduce-scatter and all-gather run in the collective libraries on GPU streams, over the GPU-to-GPU links inside a machine and the network between machines; NCCL and RCCL provide both collectives directly. D6 Some systems go further and move optimizer state to CPU memory or NVMe storage ("offload"), trading GPU memory for PCIe traffic; the ZeRO line of work includes such variants. This chapter does not quote any GPU memory size: read yours from the device query of CU201 or the vendor's data sheet, and put it in Listing 1 as the budget.

Worked example

Example A of Listing 1: Ψ = 109 parameters, N = 8 GPUs, 2 + 2 + 12 bytes per parameter. All by hand, then compared with R1.

  1. Stage 0: 16 × 109 bytes = 16 × 109 / 230 GiB = 14.90 GiB per GPU.
  2. Stage 1: (2 + 2) × 109 + 12 × 109/8 = 4 × 109 + 1.5 × 109 = 5.5 × 109 bytes = 5.12 GiB.
  3. Stage 2: 2 × 109 + 14 × 109/8 = 3.75 × 109 bytes = 3.49 GiB.
  4. Stage 3: 16 × 109/8 = 2 × 109 bytes = 1.86 GiB.
  5. Communication, stages 0–2: 2 × 7/8 × 2 × 109 = 3.5 × 109 bytes = 3.26 GiB per GPU per step; stage 3: 3 × 7/8 × 2 × 109 = 5.25 × 109 bytes = 4.89 GiB.
  6. Largest model with a 64 GiB budget at stage 1: 64 × 230 / (4 + 12/8) = 1.25 × 1010 parameters.

All six numbers agree with R1's example A. R1 The budget of 64 GiB is an invented teaching value, not the memory of any product.

Where the analogy breaks


    

  • Reading aloud is not free, but it is not extra either. The halls seem to add a new chore; in fact the all-gather replaces the second half of the all-reduce the halls already did, so stages 1 and 2 add no bytes.
    • 

  • Notebook pages are not independent of each other in general. Adam's update is element-wise, so splitting is exact; an optimizer that needs whole-matrix information (for example one that normalises per layer) cannot be cut at arbitrary points, and the slice boundaries must follow its structure.
    • 

  • A lost page in the kitchen is noticed. A lost or wrong optimizer slice is not: training continues and the loss changes only slightly (forensic lab).
    • 




Common mistakes and debugging


    

  • Counting only parameters. "1010 parameters in FP16 = 18.6 GiB, it fits" ignores gradients and optimizer state; Listing 1's example B says 149 GiB per GPU without sharding.
    • 

  • Expecting stage 1 to scale without limit. The replicated parameters and gradients remain; check the floor (Layer 3).
    • 

  • Sharding an optimizer that has no state. Plain SGD: nothing to save (R1, third case).
    • 

  • Saving only one rank's state. Works with plain data parallelism, silently wrong with sharding (forensic lab).
    • 

  • Restarting on a different N without resharding. The slices no longer line up with the ranks; a checkpoint format should record N and the slice boundaries, and the loader should refuse or redistribute.
    • 




Transition box

Where you came from: F8-12 to F8-14 split the batch, the layer and the layer stack; every data-parallel replica still held complete model states. What carries over: the result must equal the unsharded computation within a tolerance; reduce-scatter and all-gather are the two halves of the ring all-reduce (F8-02); count bytes before measuring time. R2 What changes: the state of a training job is now spread over all ranks, so saving and restoring it becomes a collective act: losing one rank loses part of the state. R3 What comes next: F8-16 makes that loss survivable: detect a failed rank, stop the job, and restart from a consistent checkpoint.

Summary


    

  • Plain data parallelism replicates the model states on every GPU: 16 bytes per parameter in this chapter's mixed-precision Adam accounting.
    • 

  • Sharding the optimizer state (stage 1) keeps each rank's slice only; reduce-scatter plus all-gather replaces the all-reduce at the same communication volume.
    • 

  • Stage 2 also shards gradients (same volume); stage 3 also shards parameters (about 1.5 times the volume, memory 1/N).
    • 

  • Listing 2 showed the sharded trainer matches the plain one (largest difference 7.45 × 10−8 on 4 ranks) with a quarter of the optimizer memory.
    • 

  • A sharded state must be checkpointed per rank; saving one rank's slice gives a silent, slowly growing error.
    •
