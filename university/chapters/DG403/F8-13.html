Story hook

Analogy

The festival orders a soup so large that no single kitchen hall can hold its pot. Every bowl must contain the same thirty-two vegetables, chopped and seasoned in a fixed way. Kofi has an idea: the four halls each take eight of the vegetables. Every hall receives the same stock, prepares its eight vegetables for every bowl, and seasons them on its own. At the end, the four partial bowls are poured together into one, and every hall gets the finished soup back for the next course.

Lina points out the catch. The seasoning (a pinch of salt for each vegetable) works on each vegetable alone, so each hall can season its own. But if a hall split the stock instead of the vegetables, it would have to taste the whole soup before seasoning, and the halls would have to pour together twice. Which way you cut the work decides how often the carts must run.

What you will be able to do

  • Explain tensor (intra-layer) parallelism for a two-matrix MLP block: column-parallel then row-parallel, and why this order needs one all-reduce in the forward pass and one in the backward pass.
  • Implement the block with MPI and prove with runs that its outputs and gradients match the single-process block within a tolerance, on 1, 2 and 4 ranks (milestone F7, part 1).
  • Show why splitting the first matrix the other way is wrong without an extra all-reduce before the nonlinearity.
  • Count the communication and memory of tensor parallelism and compare it with data parallelism for the same block.
  • Diagnose a wrong result caused by a dimension that does not divide by the number of ranks.
Jargon box
Tensor parallelism
Simple words: splitting the numbers of one layer over several GPUs, so that each GPU computes part of every result. Analogy: every hall prepares its share of the vegetables for every bowl. Precise: intra-layer model parallelism: the weight matrices of a layer are partitioned across a group of N devices, each device computes the part of the layer's output that its partition determines, and collectives (all-reduce, or reduce-scatter and all-gather) combine the parts where the mathematics requires a sum or the whole tensor. D1
Column-parallel linear layer
Simple words: each GPU holds some columns of the weight matrix and computes the matching columns of the output. Analogy: each hall prepares its own eight vegetables. Precise: for Y = X A with A = [A0 … AN−1] split by columns, device r computes Yr = X Ar; the input X must be present on every device; the output is split by columns, and an element-wise function can be applied to each Yr without communication. D1
Row-parallel linear layer
Simple words: each GPU holds some rows of the weight matrix, multiplies its part of the input, and the GPUs add their results. Analogy: the four partial bowls poured together. Precise: for Z = Y B with B split by rows to match Y split by columns, device r computes the partial product Yr Br, and Z = Σr Yr Br is formed by an all-reduce (or a reduce-scatter if the next operation can work on a split result). D1
Tensor-parallel group
Simple words: the set of GPUs that share the pieces of the same layers. Analogy: the halls that pour into the same bowl. Precise: the communicator over which a tensor-parallel layer's collectives run; in a job that also uses data and pipeline parallelism, every GPU belongs to one tensor-parallel group, one pipeline group and one data-parallel group, each a separate communicator. D1 D2

Layer 1 — the kid explanation

Some models are so big that one layer does not fit on one GPU, or takes too long on one GPU. Then you can cut the layer itself into pieces. Each GPU keeps a piece of the layer's numbers and does its part of every multiplication. At certain points the GPUs must add their parts together, and that costs a trip over the links between them. A clever cut needs only one such trip for each direction through the layer. A careless cut needs more trips, or gives the wrong answer.

Layer 2 — the student explanation

Two matrices, two cuts

The halls slice the vegetables, not the stock. The block in this chapter is the MLP of a transformer layer, simplified: Z = φ(X A) B, with X of size b × h (b tokens, model width h), A of size h × f, B of size f × h, and φ an element-wise nonlinearity (GeLU in the Megatron-LM paper; tanh in Listing 1, which changes nothing about the argument because both act on each element alone). D1

Matrix multiplication can be cut in two natural ways. Cut A by columns, A = [A0 A1 … AN−1]: then X A = [X A0 … X AN−1], so rank r can compute its block of columns of the result from the full X and its own Ar, and apply φ to it, because φ works element by element: φ(X A) = [φ(X A0) … φ(X AN−1)]. No communication so far. Now cut B by rows to match: B = [B0; B1; …], each Br of size (f/N) × h. Then H B = Σr Hr Br: each rank computes its partial product, and one all-reduce adds them. That is the column-parallel then row-parallel arrangement of the Megatron-LM paper, and it is why the paper's MLP needs one all-reduce in the forward pass. D1 R1

The other order fails. Cut A by rows (and X by columns to match): rank r computes Xr Ar, which is a part of every pre-activation sum. φ of a part is not a part of φ: tanh(a) + tanh(b) ≠ tanh(a + b). Applying φ locally and adding afterwards is wrong; R1 measured the error at 0.607 on 2 ranks and 0.836 on 4 ranks, for values whose size is about 1. The correct alternative all-reduces the b × f pre-activation before φ (four times more data than the b × h output with f = 4h) and then still needs a second collective after B. R1

The backward pass

Backpropagation through the block, with the loss gradient dZ the same on every rank (every rank holds the whole Z after the all-reduce):

  • dHr = dZ BrT and dUr = dHr ⊙ φ′(Ur): local, because rank r owns Br and Ur.
  • dBr = HrT dZ and dAr = XT dUr: local, and exactly the slices of the full weight gradients that rank r owns. No communication for the weight gradients inside the group.
  • dX = dU AT = Σr dUr ArT: a sum over ranks, so one all-reduce. It is the mirror image of the forward pass: the "copy X to every rank" at the entrance becomes an all-reduce in backward, and the all-reduce at the exit becomes a copy (identity) in backward.

The Megatron-LM paper names these two operators f (identity forward, all-reduce backward) and g (all-reduce forward, identity backward), and applies the same idea to self-attention by giving each rank a subset of the attention heads, so that a transformer layer needs two all-reduces forward and two backward. Listing 1 implements the MLP only. D1

The acceptance test

Milestone F7 asks you to "split one layer's matrix multiply across GPUs (tensor parallelism)" and accepts when "outputs match the single-GPU model within tolerance". M1 R1 shows, on 1, 2 and 4 ranks: the output Z, the input gradient dX and the weight-gradient slices dAr all match the single-process block with a largest difference of at most 2.86 × 10−6, within the stated tolerance of 10−5; on 1 rank the difference is 0. As in F8-12, the nonzero differences come from the different order of floating-point additions. R1 D7

Layer 3 — the engineer's depth

All-reduce, or reduce-scatter plus all-gather

An all-reduce can be performed as a reduce-scatter followed by an all-gather; the ring algorithm of F8-02 does exactly that. Milestone F7 asks for a version "using all-gather and reduce-scatter". Listing 1 computes the output both ways: MPI_Allreduce, and MPI_Reduce_scatter_block (each rank receives the summed rows for its share of the b tokens) followed by MPI_Allgather. R1 shows identical errors for the two on every run. D2 L1 R1

Why split it? Between the end of one MLP block and the start of the next, a transformer applies operations that work on each token separately (a residual addition, layer normalisation, dropout). If those run on the reduce-scattered result (each rank holding b/N tokens), each rank does 1/N of that work and stores 1/N of those activations; the all-gather then rebuilds the full X for the next column-parallel layer. The bytes moved are the same as one all-reduce. Work by the Megatron-LM authors calls this sequence parallelism.

Not verified — check before relying on this

From memory, not opened in this build: the name "sequence parallelism" and its use of reduce-scatter and all-gather around the token-wise operations of a transformer layer come from V. A. Korthikanti et al., "Reducing Activation Recomputation in Large Transformer Models". Check that paper's sections on sequence parallelism and activation memory before citing it; it is not in the guide's source registry.

What it costs: communication on the critical path

Compare tensor parallelism with data parallelism for the same block (Listing 2 counts it; R2). With width h, a micro-batch of T tokens, v bytes per value and N GPUs:

  • Memory of weights per GPU: data parallelism keeps all 8h2 MLP weights on every GPU; tensor parallelism keeps 8h2/N. That is the point of it.
  • Computation per GPU: 1/N of the block's multiplications, for every token.
  • Communication: one all-reduce of T × h values in forward and one in backward, per micro-batch, in every block. Data parallelism instead all-reduces the block's gradient (8h2 values) once per step.

The decisive difference is not the byte count but the dependency. A data-parallel gradient all-reduce can overlap with the backward pass of earlier layers (F8-12). A tensor-parallel all-reduce cannot overlap with its own block: the next layer needs Z before it can start, and the backward pass needs dX before the previous layer's backward can start. Tensor-parallel communication sits on the critical path of every layer, so it needs the fastest links available. The Megatron-LM paper used tensor parallelism inside a server whose GPUs are joined by fast direct links, and data parallelism across servers. D1 R2 The general rule that follows from the model, not from any vendor claim: put the tensor-parallel group on the fastest, lowest-latency links you have (F8-04's topology matrix tells you which), and keep N small enough that each GPU's share of a GEMM is still large enough to run efficiently.

Divisibility and shapes

The cut requires f (and, for attention, the number of heads) to divide by N. If it does not, a real implementation must either refuse or handle uneven pieces explicitly; silently rounding down drops columns. Listing 1 refuses unless told not to (R4); the forensic lab shows what the unchecked version computes. R4 R3

Groups inside a larger job

In a job that combines strategies, the world of P GPUs is factored, for example P = NTP × NPP × NDP, and each GPU joins three communicators. The tensor-parallel all-reduce runs only inside its group; the data-parallel gradient all-reduce runs across groups, over replicas of the same shard of weights. With MPI, such groups are built with MPI_Comm_split; NCCL and RCCL create one communicator per group. Assigning ranks so that each tensor-parallel group sits inside one server is the job of the launcher and the rank-to-GPU mapping (F8-17). D1 D2 D3

How the hardware actually does it

In the halls, the pour-together happens many times per meal, so the halls must be next door to each other. On a GPU, each rank's share of the block is an ordinary GEMM on its slice of the weights, computed with the tiling of CU302 and, on GPUs that have them, matrix units (Tensor Cores on NVIDIA, Matrix Cores on AMD). Smaller slices mean smaller GEMMs; below some size a GEMM can no longer keep the whole GPU busy, which is one practical limit on N. D6 The all-reduce of activations is executed by the collective library over the GPU-to-GPU links; inside one machine those are the links F8-04 measured, and their latency matters as much as their bandwidth because the messages are moderate in size and on the critical path. D3 D4

Nothing in this build ran on a GPU; no GEMM efficiency or link latency is quoted. Measure both on your hardware before choosing N.

Worked example

A block with h = 1,024, a micro-batch of T = 2,048 tokens per GPU, values of 2 bytes (16-bit), N = 4 GPUs (the "example-1" line of R2; invented sizes).

  1. Weights: A and B together hold 2 × h × 4h = 2 × 1,024 × 4,096 = 8,388,608 values; × 2 bytes = 16,777,216 bytes = 16 MiB. With tensor parallelism each GPU holds 16 / 4 = 4 MiB.
  2. One activation tensor: T × h × 2 bytes = 2,048 × 1,024 × 2 = 4,194,304 bytes = 4 MiB.
  3. Bytes each GPU sends in one ring all-reduce of S bytes: 2 (N − 1)/N × S = 1.5 × 4 MiB = 6 MiB. Forward and backward: 12 MiB per micro-batch, on the critical path.
  4. Data parallelism instead: one all-reduce of the 16 MiB gradient per step; each GPU sends 1.5 × 16 = 24 MiB, which can overlap with the backward pass.
  5. With N = 8 (second line of R2): weights 2 MiB per GPU; tensor-parallel traffic 2 × 1.75 × 4 = 14 MiB per micro-batch; the traffic barely changes with N, while each GPU's computation halves. Communication becomes a larger share as N grows.

R2 prints the same values: 16.00 MiB, 4.00 MiB per GPU, 12.00 MiB per micro-batch, 24.00 MiB per step; and for N = 8, 2.00 MiB and 14.00 MiB. R2 If a step has several micro-batches (F8-14), multiply the tensor-parallel traffic by their number; the data-parallel traffic does not grow.

Where the analogy breaks


    

  • Pouring partial bowls is adding numbers. The "partial bowls" are partial sums of matrix products; nothing in a soup is a sum that must be complete before seasoning, which is the whole reason the column cut must come first. Use the algebra, not the soup, to decide where communication is needed.
    • 

  • The halls receive the same stock for free in the story. In tensor parallelism, giving every rank the full input X is not free: in backward, that copy turns into an all-reduce of dX.
    • 

  • Real halls could prepare an uneven number of vegetables. A tensor-parallel layer with an uneven split needs explicit handling; the simple formulas assume f divides by N.
    • 

  • The halls' pour happens once per meal; the all-reduce happens in every layer for every micro-batch. The frequency, not the volume, is what puts tensor parallelism on the fastest links.
    • 




Common mistakes and debugging


    

  • Wrong output only for some N. Symptom: matches for N = 2, not for N = 4 (forensic lab). Cause: a dimension that does not divide by N, rounded down. Find it: print each rank's slice bounds and check that they cover 0 … f − 1 exactly once. Fix: refuse, or pad and handle uneven slices.
    • 

  • Applying the nonlinearity to partial sums. Symptom: large errors (R1's "wrong split" line). Cause: the first matrix cut by rows. Fix: column-parallel first, row-parallel second.
    • 

  • Gradients of X are 1/N of the truth. Symptom: earlier layers learn too slowly with tensor parallelism. Cause: the backward all-reduce of dX was forgotten (the f operator treated as identity in both directions). Find it: compare dX with the reference, as Listing 1 does.
    • 

  • Weight gradients all-reduced inside the group. Symptom: tensor-parallel weights drift or are N times too large. Cause: treating the tensor-parallel group as a data-parallel group. Fix: weight gradients are all-reduced only across replicas of the same shard (the data-parallel group).
    • 

  • Hangs when combining strategies. Cause: a collective called on the wrong communicator (world instead of the tensor-parallel group) by some ranks. Find it: log the communicator name with every collective. F8-16 shows how to detect the hang.
    • 

  • Different dropout masks across a tensor-parallel group where the computation requires the same values on every rank (for example on the replicated input), or the same mask where independent ones are required. Cause: random-number seeds not organised per group. Fix: seed per data-parallel replica and per tensor-parallel rank deliberately, and document which regions use which seed.
    • 




Transition box

Where you came from: F8-12 kept the whole model on every GPU and communicated gradients once per step, overlapped with the backward pass. What carries over: the same collectives (all-reduce, reduce-scatter, all-gather) and their ring cost; every rank must call them in the same order; results are equal to the single-GPU model within a tolerance. D2 What changes: communication moves from gradients to activations, from once per step to twice per block per micro-batch, and from overlappable to the critical path; correctness now depends on cutting matrices in the right order. D1 What comes next: F8-14 splits the model the other way, by layers, and meets a different cost: GPUs that wait for each other at the start and end of every step.

Summary


    

  • Tensor parallelism splits the weights of each layer across a group of GPUs; each GPU computes part of every output.
    • 

  • For an MLP block, cut the first matrix by columns and the second by rows: one all-reduce forward (on the output), one backward (on the input gradient); weight gradients need no communication inside the group.
    • 

  • Cutting the first matrix by rows puts a nonlinearity between partial sums: wrong unless an extra, larger all-reduce is added (R1: errors up to 0.836).
    • 

  • All-reduce equals reduce-scatter plus all-gather; splitting it lets token-wise operations run on 1/N of the tokens.
    • 

  • Tensor-parallel traffic is per micro-batch and on the critical path, so it belongs on the fastest links; memory per GPU for weights falls as 1/N.
    • 

  • Dimensions must divide by N; a silent round-down produced a wrong block at 4-way (R3).
    •
