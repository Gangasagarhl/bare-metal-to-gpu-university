Story hook

Analogy

The gate guards of F11-01 stop strangers. But the king, far away, has a different question: who actually came into the castle last night? The guards could simply tell him "only friends", but a guard who has been bribed would say the same. So the castle has a notary in a locked tower. Every time someone passes a gate, the notary adds the visitor's name into a tally that can only grow and never be rubbed out, and the gate scribe writes the same name in an open visitors' book.

When the king's messenger arrives, he brings a password nobody has heard before. The notary writes the password and the current tally on a parchment and seals it with a seal that never leaves the tower. The messenger takes the parchment and the visitors' book home. If the book, read from the first page, adds up to the tally on the parchment, the book is complete and true; if the password is the fresh one, the parchment was written today. Then the king can read the book and decide whether he likes who came in.

This chapter does that with a real UEFI firmware. OVMF, the firmware you used in F11-02, measures what it loads into a TPM and writes the visitors' book, the event log. You read the log with a UEFI program, replay it, and compare it with what the TPM holds; you enroll F11-02's keys and rotate them and watch exactly one register change. A model of a TPM, built on OpenSSL, then shows the two things the notary is for: signed reports to a verifier far away (attestation) and secrets that are released only when the tally is right (sealing).

What you will be able to do

  • Explain the difference between verifying a boot (Secure Boot refuses bad code) and measuring it (the TPM records what ran and lets someone else judge).
  • Compute a PCR value by hand from an event log, and say why the order of events matters and why a PCR cannot be set back.
  • Read a real firmware event log: which events go into which PCR, and which PCR changes when the Secure Boot keys change.
  • Describe remote attestation: nonce, quote, attestation key, replay of the log, and the list of known-good values, and say which attack each check stops.
  • Predict when a secret sealed to PCRs will be released, and plan a key rotation so that machines do not lose their sealed disk keys.
  • Diagnose an attestation failure from an event log, a verifier report and a table of PCR values.
Jargon box
Sealing (TPM)
Simple words: locking a secret inside the TPM so that it comes out only if the machine booted in a known way. Analogy: a box the notary opens only while the tally reads exactly what it read when the box was closed. Precise: the TPM binds a data object to a policy over selected PCR values; unsealing succeeds only while those PCRs hold the values in the policy. In this chapter's model: a secret plus the composite digest of the selected PCRs, released when the current composite is equal (observed in measured.out). D2 R1
Nonce (freshness value)
Simple words: a random number used once, so that an old answer cannot be passed off as a new one. Analogy: the messenger's fresh password. Precise: a value chosen by the verifier and included in the data the TPM signs in a quote; a quote over a different nonce is rejected as possibly replayed (scenario 4 of the lab). D2 R1
Attestation key (AK)
Simple words: a signing key that lives inside the TPM and signs only reports about the TPM's own registers. Analogy: the notary's seal, which never leaves the tower. Precise: a restricted signing key created in the TPM whose private part cannot be exported; the verifier trusts its public part through a certificate chain to the TPM maker's endorsement key (not exercised in this build). In the model, a P-256 ECDSA key held by the Tpm object. D2
Reference values (golden measurements)
Simple words: the list of digests a verifier knows to be good. Analogy: the king's list of welcome visitors. Precise: digests of approved firmware, configurations, Secure Boot variables and boot programs, or of whole PCR values from a known-good machine, against which a replayed event log is judged; they must be updated whenever something legitimate changes, such as a key rotation. R1

From earlier chapters, not redefined here: TPM, PCR, extend, event log, attestation and quote and root of trust for measurement (F4-13); measured boot (OS301); chain of trust (F11-01); Authenticode (F3-16).

Layer 1 — the kid explanation

A computer has a tiny, stubborn chip called a TPM. It has a few number boxes. You cannot write a number into a box; you can only "stir in" a new fingerprint, and the box's number changes in a way nobody can undo or aim. While the computer starts, every piece of software stirs in the fingerprint of the next piece before running it. At the end, the boxes say, in a code only a computer can check, exactly what started. The computer also keeps a plain list of what it stirred in. If someone sends the list to a checker far away, the chip signs the box numbers, and the checker stirs the list itself and compares. If they match, the list is honest, and the checker can read it.

Layer 2 — the student explanation

Two kinds of trust: verify, or record

F11-01 and F11-02 built a verified chain: each stage checks the next and refuses what fails. That protects the machine, but nobody outside the machine learns anything: a machine whose firmware was replaced would claim to be fine just as loudly as a healthy one. Measured boot adds a record. Each stage hashes the next and extends the hash into a Platform Configuration Register (PCR) of the TPM before running it, and appends an entry to an event log.S1 Nothing is refused because of a measurement. The value of the measurement is that it cannot be undone: once a stage has been measured, even a malicious stage that runs afterwards cannot make the PCR look as if it had not run.

Extend, and why order matters

A PCR starts at zero when the platform resets. The only way to change it is extend: new value = SHA-256(old value || digest).D2 The model implements exactly that line (tpm_model.h line 63), and Python's hashlib recomputes the same five PCR values from the same strings.R2 Two consequences follow. Order matters: scenario 6 extends the same two digests in both orders and gets 86f38b45… and 6782288f….R1 And there is no way back: to reach a target value you would need a digest whose hash, combined with the current value, gives the target, which is as hard as breaking SHA-256.

A real firmware's log

OVMF with a TPM device measured 26 events in every run of this lab, into PCRs 0, 1, 2, 3, 4, 5, 6 and 7.R4 Reading the fw_enrolled log from the top: PCR 0 receives the firmware's own version string and two firmware blobs; PCR 7 receives the five Secure Boot variables (SecureBoot, PK, KEK, db, dbx) and a separator; PCR 1 receives four events of a type our table does not name and the boot variables (BootOrder, Boot0000, Boot0001); PCR 4 receives an EV_EFI_ACTION event; then every PCR from 0 to 6 receives a separator; then PCR 7 receives the db entry that authorised our program (EV_EFI_VARIABLE_AUTHORITY) and PCR 4 the program itself (EV_EFI_BOOT_SERVICES_APPLICATION).R5 That is the usual division of the PC world, as the TCG firmware profile describes it: PCR 0 firmware code, PCR 1 firmware configuration, PCR 4 boot programs, PCR 7 Secure Boot policy.D1

Not verified — check before relying on this

Written from memory of D1 and D3, which were not opened: the PCR assignment just stated, the event type names and numbers in evlog.cc (lines 36–54), the layout of the TCG2 log (a first entry in the old SHA-1 format holding the "Spec ID Event03" header, then entries with a digest count and one digest per algorithm), the slot order of EFI_TCG2_PROTOCOL and its GUID (lines 9–15). What is verified is narrower: with these assumptions the program parsed the log of OVMF 2024.02 without error, and its replay equals the PCR values the TPM device holds, for all eight PCRs in three different boots.R6 The four PCR 1 events of type 0x0000000a are printed as numbers because the table has no name for them; their meaning was not looked up.D1 D3

Replay: the log checks itself

The event log is ordinary memory: anyone who controls the operating system can edit it. The PCRs cannot be edited. So a log is believed only after a replay: start eight registers at zero, extend each event's digest into its PCR, compare with the TPM. evlog.cc does the replay inside the firmware environment (lines 146–151); the TPM's values come from mock_tpm.py, which records every extend the firmware sent it. For all three boots and all eight PCRs, the replay and the TPM agree.R6 That is the curriculum's C13 acceptance check ("PCR values … equal the values obtained by replaying the firmware event log"), here with a stand-in TPM instead of swtpm, and read through the TPM emulator's record rather than by your own kernel's driver; F4-13 builds that driver side.S1 S2

What measurements are for

A PCR value alone is just a number. It becomes useful in two ways. Attestation: the TPM signs the PCR values together with a verifier's nonce, and the verifier, far away, decides whether it trusts the machine. Sealing: the TPM releases a secret, typically a disk encryption key, only while selected PCRs hold the values they held when the secret was sealed. Both are shown in the model, because the stand-in TPM of the real-firmware lab implements neither (it has no keys at all).S2

Layer 3 — the engineer's depth

PCR 7 is the key-database register

The three firmware boots differ only in the key store: empty (setup mode, unsigned program), F11-02's keys enrolled (program signed with db1), and F11-02's rotation applied (program signed with db2). pcr_compare.out lines them up: PCRs 0 to 6 are identical in all three; only PCR 7 differs, and it differs in every pair.R6 The logs say why. In the empty store the PK, KEK and db events carry 36–38 bytes of data (the variable header with no content) and there is no authority event, because nothing was verified. After enrolment the PK, KEK and db events carry 820, 830 and 828 bytes, and a sixth PCR 7 event records the db entry that authorised the program. After the rotation, db grows to 1,620 bytes and dbx to 830 bytes, and the authority event carries the db2 certificate instead of db1 (digest 20f59096… instead of 28cea840…).R4 R5

Two consequences for design. First, PCR 7 is the right register to seal a disk key to if you want "only while this Secure Boot policy is in force", and the wrong one if you rotate keys often: every legitimate rotation changes it. Second, PCR 4 does not tell you who signed the boot program. The application event's digest 386895b2… is the same for the unsigned copy and both signed copies, and equals the Authenticode hash that sign.py --hash prints for each file.R6 Authenticode leaves the signature out of the hash (F3-16), so re-signing a program with a new key does not change PCR 4. Sealing to PCR 4 survives a re-signing; sealing to PCR 7 does not.

Attestation, check by check

The model's verifier (measured.cc lines 57–78) makes the four checks of Figure 2 and prints each. The scenarios each break one check.

ScenarioWhat happenedFirst check that failsVerdict
1Healthy bootnoneTRUSTED
2Secure Boot off, a patched loader(d) two unknown components, in PCR 7 and PCR 4NOT TRUSTED
3As 2, the operating system edits the log to look healthy(c) replay 3e711f75 ≠ quote 75ad2979NOT TRUSTED
4As 2, the machine resends scenario 1's quote and log(b) nonce is not the one sentNOT TRUSTED
5Legitimate key rotation(d) three new digests, until the verifier learns themNOT TRUSTED, then TRUSTED

All from measured.out.R1 Notice scenario 3: the edited log contains only known-good components, so a verifier that skipped check (c) and only read the log would say TRUSTED. And scenario 4: an old, genuinely signed quote of a healthy boot is perfect evidence of the wrong boot. Without the nonce, a compromised machine would simply keep one good quote and send it forever.

Scenario 5 is the operational lesson. A correct, planned key rotation looks to the verifier exactly like an attack on the Secure Boot policy until the reference values are updated. The rotation procedure of F11-02 therefore needs one more step: publish the new reference values (the new db and dbx contents and the re-signed boot programs) to the attestation service before the machines reboot into the new policy.

Not verified — check before relying on this

The model's quote is a P-256 ECDSA signature over the nonce and a SHA-256 over the selected PCR values. A real TPM 2.0 quote (TPM2_Quote) signs a structure that also carries, among other things, the TPM's clock, a reset counter and the PCR selection, and a real attestation key is certified through the TPM's endorsement key and the maker's certificate. All of that is from memory of D2, not opened, and not exercised: the stand-in TPM implements no keys, quotes, sessions or sealing.S2 Treat the model as the shape of the protocol, not its format.

Sealing and the rotation problem

In scenario 1 the model seals "disk key 7f3a" to PCR 7 and unseals it immediately: released. In scenario 5 the same sealed object is presented after the rotation: REFUSED, because PCR 7 changed; the machine would ask for its recovery key. After resealing under the new PCR 7, the key is released again.R1 The real firmware runs show that a rotation really does change PCR 7 (65caf8dd… → 236e8c98… → ab7e9f6e… across the three boots).R6 Put together: a fleet that seals disk keys to PCR 7 must reseal every disk key to the predicted new PCR 7 value before the machines reboot into the rotated policy, or every machine will ask its user for a recovery key the next morning. Predicting the value is possible precisely because extend is deterministic: the new event data is known in advance.

What measured boot does not do

  • It does not stop anything. Scenario 2's patched loader ran; only the verdict caught it. Combine it with Secure Boot (refuse) for protection and use measurement for evidence.
  • It measures only what the measuring code chooses to measure, and only before it runs. Code that is never measured, or a measured program that is attacked while it runs (TOCTOU, F11-01), is invisible.
  • Its root is the first measuring code (the root of trust for measurement). If that code lies, every PCR value is a lie that still replays perfectly.S2
  • A verifier is only as good as its reference values. Scenario 5's false alarm and the forensic case are both about reference values, not cryptography.

How the hardware actually does it

A TPM is either a separate chip on the board, connected by a low-speed bus, or firmware running in a protected part of the main processor (a "firmware TPM").S1 The operating system and the firmware reach it through one of two register interfaces, FIFO (TIS) or CRB, described by the TCG platform TPM profile; QEMU's tpm-tis device used here offers the FIFO interface at a fixed address, and F4-13 drives it directly.S2 The PCRs reset only when the platform resets, which is what makes "zero at the start of this boot" meaningful; a TPM that could be reset alone, without resetting the processor, would let software start a fresh, clean-looking chain after the real one.

Not verified — check before relying on this

Untested on hardware and with no real TPM. Every firmware run used QEMU 8.2.2's tpm-tis device with its "emulator" backend, answered by mock_tpm.py, a Python script from F4-13 that implements just enough commands (Startup, SelfTest, GetCapability, GetRandom, PCR_Extend, PCR_Read) for OVMF; it has no keys, no sealing and no authorisation checks, and its control protocol was written from memory of swtpm's and is proven only by QEMU accepting it.S2 The bus types, the firmware-TPM implementations named by the curriculum (Intel PTT, AMD fTPM, OP-TEE-based TPMs on Arm) and the reset behaviour stated above are not checked here.

Worked example

Problem. (a) Use the fw_enrolled log to list the events that go into PCR 7, in order. (b) The separator event's digest in every PCR is df3f6198…. What data was hashed, if the event data is 4 bytes? (c) The verifier has the reference value of PCR 7 for the db1 policy. After the rotation it receives a quote whose PCR 7 is ab7e9f6e…. Which events must it look at to decide whether the change is the planned rotation? (d) A disk key sealed to PCRs 4 and 7 on a db1 machine: after the rotation and re-signing, which of the two values changed?

Solution. (a) Events 3–7 (SecureBoot, PK, KEK, db, dbx), event 8 (separator), event 24 (the authority, a db entry).R5 (b) Four bytes; the lab does not print them, but SHA-256 of four zero bytes begins df3f6198 (check with printf '\0\0\0\0' | sha256sum), consistent with a separator value of zero.D1 (c) Replay first; then compare the db event (now 1,620 bytes, digest dbe4a147…), the dbx event (830 bytes, f0421189…) and the authority event (20f59096…) with the published new reference values; every other PCR 7 event is unchanged.R5 (d) Only PCR 7: PCR 4's application digest is the Authenticode hash, which ignores the signature (386895b2… in both runs).R6 So the key will not be released until it is resealed to the new PCR 7.

Where the analogy breaks


    

  1. The notary's tally contains no names. The PCR value is a hash: from it alone nobody can read who passed. That is why the open visitors' book (the event log) exists, and why the book must be checked against the tally before it is read.
    2. 

  2. The notary does not judge. A castle notary might refuse to record a known thief; the TPM records everything it is given, good or bad, and leaves the judgement to the verifier.
    3. 

  3. The notary only records what the guards report. If the first guard (the root of trust for measurement) lies, the tally and the book agree perfectly and both are wrong.
    4. 




Common mistakes and debugging


    

  • Reading the log without replaying it. Symptom: an edited log passes (scenario 3). Fix: replay first, compare with the quoted PCRs, only then read.
    • 

  • Accepting a quote without a fresh nonce. Symptom: an old, valid quote passes (scenario 4). Fix: a new random nonce per request, checked.
    • 

  • Extending EV_NO_ACTION events in a replay. Symptom: the replay of PCR 0 differs from the TPM. Fix: skip them (evlog.cc line 146).
    • 

  • Stepping over digests with a fixed size. Symptom: garbage after the first event on a firmware that logs several algorithms. Fix: take each algorithm's digest size from the header event, as lines 103–106 and 118 do.
    • 

  • Sealing to PCR 7 and rotating keys. Symptom: every machine asks for a recovery key after the rotation (scenario 5). Fix: reseal to the predicted new values before the reboot, or seal to a policy that names a signing authority instead of fixed values (a TPM feature not exercised here).
    • 

  • Expecting PCR 4 to show the signer. Symptom: two programs signed with different keys give the same PCR 4. Cause: Authenticode excludes the signature. Fix: the signer is in PCR 7's authority event.
    •

Safety


Safety
Do not clear, take ownership of or experiment with the TPM of a computer you depend on. Operating systems use it to seal disk-encryption keys; clearing it or changing what is measured can lock you out of your own disk unless you have the recovery key at hand. Everything in this lab runs in QEMU with a copied variable store and a stand-in TPM.

Summary


    

  • Measured boot records; Secure Boot refuses. They answer different questions and are used together.
    • 

  • A PCR can only be extended: new = SHA-256(old || digest). Order matters and nothing can be undone until the next reset.
    • 

  • The event log is untrusted until a replay matches the TPM; in OVMF's real log, all eight PCRs replayed exactly (with a stand-in TPM).
    • 

  • Key changes show up only in PCR 7; the PCR 4 digest of a program is its Authenticode hash and ignores who signed it.
    • 

  • Attestation needs four checks: AK signature, fresh nonce, replay equals quote, every digest known. Each lab scenario fails a different one.
    • 

  • Sealing to PCR 7 breaks at every key rotation unless the keys are resealed first; reference values must be updated before a planned change.

Answers to Check yourself


    

  1. Secure Boot stops unsigned or revoked code from running, but tells nobody outside what ran. Measured boot lets a remote verifier detect, for example, that Secure Boot was switched off (scenario 2), which Secure Boot itself cannot report; Secure Boot stops a malicious loader before it runs, which measurement cannot.
    2. 

  2. Extend is the only operation, and the new value is a hash of the old one with the digest. Reaching a chosen value would require finding a digest that hashes to it, which is breaking SHA-256; and the measurement happened before the measured code ran.
    3. 

  3. The firmware, its configuration and the boot program were the same; only the Secure Boot variables and the authorising db entry changed, and those are measured into PCR 7.
    4. 

  4. The log is ordinary memory that the operating system can edit; the PCRs cannot be edited. Only if replaying the log reproduces the quoted PCRs is the log the one that was measured (scenario 3 shows an edited log of good-looking entries).
    5. 

  5. The nonce check. The signature proves the TPM made the quote, but not when; an old quote of a healthy boot has a valid signature.
    6. 

  6. A firmware update changes PCR 0 (firmware code), so every key sealed to PCR 0 breaks; PCRs 4 and 7 may be unchanged. The process must reseal the keys to the predicted new PCR 0 value (or temporarily to a policy without PCR 0) before rebooting into the new firmware, and keep the recovery keys available.
    7. 

  7. All PCR 7 values change, so the reference values (made by the same changed code) still match: scenario verdicts do not change. The PCR digest numbers printed in the scenarios do change. The order is part of the measurement; the verifier only notices if its references come from a different order.
    8. 

  8. Authenticode's hash excludes the certificate table, so re-signing does not change it. The signer appears in PCR 7 as the EV_EFI_VARIABLE_AUTHORITY event (the db entry used), 28cea840… for db1 and 20f59096… for db2.
    9. 

  9. It has no keys, quotes, sealing, sessions or authorisation, and its control protocol is unverified. Everything about quotes, the attestation key and sealing rests on the model in tpm_model.h; the PCR values, the event log and the PCR 7 behaviour rest on the real firmware runs.
