Story hook

Analogy

A castle has four gates in a row, one inside the other. At the outer gate stands a guard carved into the stone of the wall itself: nobody can replace him, bribe him or teach him new tricks. He holds one thing, a description of the guard of the second gate. When that guard arrives in the morning, the stone guard compares him with the description; if they differ, the gate stays shut and nobody gets in at all. The second guard, once inside, does the same for the third, and the third for the fourth. By noon the innermost hall is full of people, and the lord can say something precise: every person in here was checked by someone who was checked, all the way back to the stone.

The lord's steward finds the weak spots in one afternoon. If one guard is lazy and waves people through, everyone behind him is unchecked, however careful the later guards are. And when the lord wants a new cook in the kitchen, every description at every gate must be rewritten, including the one carved in stone, which cannot be.

This chapter is about that idea, the chain of trust: the structure behind Secure Boot on PCs (F11-02), measured boot (F11-03), signed firmware updates (F11-04), Arm's secure world (F11-05) and the boot of robots and drones (F11-06). You build a small chain on the host, attack it six ways, and find out by experiment why every real chain replaces the fixed "description of the next guard" with a signature check.

What you will be able to do

  • Explain a chain of trust: a root that cannot be changed, and stages that each check the next before running it.
  • Identify the root of trust in a boot chain and explain why it must be immutable and why it must be the first code to run.
  • Predict which modifications a chain detects and which it cannot, and show both with the lab's model.
  • Explain why a chain built from fixed digests cannot be updated, and how signatures and keys solve that.
  • Distinguish verifying (stop what is wrong) from measuring (record what ran), as a preparation for F11-02 and F11-03.
  • Investigate a fleet where some units booted modified software, and find the link that checked nothing.
Jargon box
Chain of trust
Simple words: each piece of start-up software checks the next piece before it lets it run. Analogy: each gate guard checks the badge of the next person before letting them in. Precise: a boot sequence in which a trusted component verifies (or measures) the next component before transferring control to it, so that trust in the last stage reduces to trust in the first one and in every verifier on the way. S1 D1
Root of trust
Simple words: the first piece of the chain, which nobody checks because nothing runs before it. Analogy: the guard carved into the stone of the outer gate. Precise: a component that must be trusted because its misbehaviour cannot be detected by the chain; for a boot chain this is code and key material that run first and cannot be modified in the field (for example a boot ROM and fused key hashes). S1 D2
Hash-locked chain
Simple words: a chain in which every stage stores the exact fingerprint of the next stage. Analogy: each guard holds a portrait of exactly one next guard. Precise: this course's name for a chain in which stage n embeds the SHA-256 digest of stage n+1 and compares it before handing over; it detects every change but forces a new release of all earlier stages for any change later in the chain (lab scenario 6). R1
Trusted computing base (TCB)
Simple words: everything that must work correctly for the protection to hold. Analogy: all guards on the way in, not only the last one. Precise: the set of hardware, firmware and software components whose correct behaviour the security property depends on; in a chain of trust it includes the root and every verifier before the component in question. D5
TOCTOU (time of check to time of use)
Simple words: something is changed after it was checked but before it is used. Analogy: the guard checks a badge, turns round, and a different person walks through. Precise: a race in which the object that was verified is not the object that is executed, for example when a loader verifies an image in flash and then re-reads it from flash to run it, or when a debug probe writes to memory after the check. D5

From earlier chapters: cryptographic hash (SHA-256) and digital signature (F3-41), measured boot and Secure Boot (F3-16), boot ROM and locked (fused) boot chain (DR403).

Layer 1 — the kid explanation

When a computer starts, many programs run one after the other, each one starting the next. If a bad program sneaks in at any point, it could take over everything after it. So each program checks the next one before it lets it run. The very first checker is built into the chip and can never be changed, so a bad program cannot replace it. If every checker does its job, the last program can be trusted, because of a chain of checks that goes back to that first, unchangeable one.

Layer 2 — the student explanation

What a chain of trust guarantees, and what it does not

A boot chain is a sequence of hand-overs. In the PC chain of F3-09 the firmware's phases hand over to a boot loader, which hands over to the kernel; on an Arm board a boot ROM hands over to a first-stage loader, then to further stages and an operating system.S1 S2 A chain of trust adds one rule to every hand-over: before stage n transfers control to stage n+1, it checks stage n+1, and refuses to continue if the check fails.

The guarantee is conditional and worth stating exactly. If (1) the first stage is genuine, (2) every stage that checks does the check correctly, and (3) what was checked is what runs, then every stage that ran was approved by whoever controlled the checks. The chain says nothing about whether the approved software is free of bugs, nor about what happens after the last stage starts.D5 Lab scenario 5 breaks condition (2); the forensic lab is about the same break in a fleet.

The root of trust

Condition (1) cannot be established by the chain itself: nothing runs before the first stage, so nothing can check it. That stage is the root of trust, and the design must make it unchangeable in the field. The curriculum names the PC examples: Intel Boot Guard and AMD Platform Secure Boot "verify the firmware itself", which is why retail PCs do not accept arbitrary firmware.S1 On many SoCs the boot ROM, fixed when the chip is made, checks the first loader against a key hash in one-time-programmable fuses; DR403 called such a chip a locked (fused) boot chain.S2 The lab's model has a ROM that holds the digest of bl1 and is never modified.

Verify or measure

Two different things can be done at each hand-over. Verifying compares the next stage with something trusted and stops the boot on a mismatch: UEFI Secure Boot (F11-02) and signed updates (F11-04) do this. Measuring records a digest of the next stage in a place software cannot rewrite (a TPM's PCR) and continues regardless; someone checks the record later (F11-03).S1 D2 F3-16 introduced both on the PC; this course goes deeper into each, and F11-06 combines them in a robot.

Layer 3 — the engineer's depth

The model and what it shows

The lab's chain_model.h (Listing 1) represents each stage by a string (standing for its code), the 32-byte digest of the next stage that it embeds, and a flag saying whether it performs its check. The digest of a stage covers all three, exactly as a real digest covers all of a stage's bytes, including the digest embedded in it. The release process fills the digests backwards, from the app to bl1, and the factory writes the digest of bl1 into the ROM.R1 Seven scenarios (Listing 2) produced these results:

Why real chains verify signatures, not digests

Scenario 6 is the end of the hash-locked design. A new app changes the app's digest, so the os must be rebuilt to hold it, which changes the os's digest, and so on back to bl1, whose new digest the ROM does not know. All four digests changed between v1 and v2 in the run, and the device refused v2.R1 Real chains therefore store, at each link, not "the digest of the next stage" but "the key that must have signed the next stage". The ROM holds a digest of a public key (fused at the factory); each stage carries a signature; any number of future versions can be accepted without touching earlier stages. The UEFI Specification's Secure Boot works this way with certificates in db (F11-02), and so does MCUboot with a public key built into the boot loader (F11-04).D1 D4

The price is a new kind of root: the private key. Whoever holds it can sign anything the chain will run. The registered analogy says it plainly: badges are cryptographic signatures, and a stolen key breaks everything after it. Key storage (offline keys, hardware security modules), key rotation (F11-02) and revocation are therefore part of the chain's design, not an administrative afterthought.

The rules a chain designer follows

  1. The root runs first and cannot be modified. If anything mutable runs before it, that thing is the real root.
  2. Every mutable stage is checked before it runs, by a stage that was itself checked.
  3. Check what you run. Copy the image into memory the next stage cannot modify, check that copy, and run that copy (TOCTOU). Disable debug access that could write memory after the check (F11-06).
  4. Fail closed, and know what "closed" means for your device. A PC that refuses to boot shows a message; a drone in the air must not reboot to check anything (F11-06).
  5. Keep the TCB small. Every verifier is in the trusted computing base of everything after it; a large boot loader with a network stack and a file-system parser is a large attack surface in the TCB.D5
  6. Plan updates and revocation from day one: which keys, how many, how they are retired (F11-02, F11-04).

How the hardware actually does it

A chain of trust needs three things from the hardware: code that cannot change (a mask ROM, programmed when the chip is manufactured), a small amount of storage that can be written once (one-time-programmable fuses, which hold a key hash, a "secure boot enabled" bit and anti-rollback counters), and a reset that always starts in the ROM.S2 On PCs, the curriculum names hardware roots that verify the firmware itself (Boot Guard, Platform Secure Boot) and independent security processors with their own firmware (Intel CSME, AMD PSP), which run before the main CPU's firmware.S1 A TPM adds a different capability: registers that can only be extended, used for measurement rather than enforcement (F11-03).D3

Not verified — check before relying on this

How a specific chip's boot ROM finds and checks the first loader (which fuses, which signature algorithm, what happens on failure, whether a recovery mode bypasses the check) is chip-specific and was not checked for any chip in this build. Read the chip's reference manual, security chapter, before relying on any of it; F11-06 lists what to look for. The descriptions of Boot Guard, Platform Secure Boot, CSME and PSP are the curriculum's summary (S1), not vendor documents.

Worked example

Problem. A device has the lab's four-stage hash-locked chain. The vendor wants to ship a fix to bl2 only. (a) Which stored values must change, and can the update be installed? (b) The vendor redesigns: the ROM holds the SHA-256 of one public key, and every stage is signed with the matching private key. Repeat (a). (c) In the redesign, an attacker obtains a copy of bl2 v1, which has a known bug, still signed. What stops them from installing it?

Solution. (a) bl2's digest changes, so bl1 must hold the new digest; bl1's digest changes, so the ROM would need the new digest of bl1. The ROM cannot change, so the device refuses the new bl1 (as in scenario 6, where all four digests changed and the ROM refused).R1 No update is possible. (b) Only bl2 changes; it is signed with the same key; bl1 checks the signature with the public key it was given and accepts it; the ROM still checks bl1, unchanged. (c) Nothing in (b) stops it: the old image's signature is valid. The design needs anti-rollback: a security counter in each image, covered by the signature, and a fused minimum that the device raises when a newer image is confirmed. F3-41 introduced it; F11-04 tests it.D4

Where the analogy breaks


    

  1. A real guard can notice something odd; a verifier compares bits. A signed stage with a bug, or one signed by a careless key holder, passes every check. The chain proves origin, not quality.
    2. 

  2. Badges are signatures, and signatures can be copied. A stolen private key lets an attacker make perfect badges for every gate after the one that trusts that key; a castle's guard would at least see a stranger's face. Key protection is part of the chain.
    3. 

  3. A castle gate physically blocks; firmware only declines to jump. Anything that can run code by another path (a debug probe, a DMA-capable device, a second processor that boots first) is a door in the wall that the gate guards never see (F11-06).
    4. 

  4. The stone guard never needs replacing; a ROM sometimes does. A bug in a boot ROM is permanent for that chip. The immutability that makes the root trustworthy also makes its mistakes unfixable.
    5. 




Common mistakes and debugging


    

  • Calling a chain "secure boot" when its first link is mutable. Symptom: the boot loader checks the kernel, but the boot loader itself can be overwritten from the operating system. Cause: the root of trust is in flash. Find it: list every stage and ask "what checks this, and what checks that?". Fix: anchor the first check in ROM or fuses.
    • 

  • A check that is compiled out in some builds. Symptom: modified software runs on some units only (forensic lab). Cause: a configuration option or debug build. Find it: compare build records and flash digests per batch. Fix: make the check unconditional in release builds and test it on every release (feed a modified image and expect a refusal).
    • 

  • Checking one copy and running another (TOCTOU). Symptom: tampering possible with fast external flash or a bus interposer. Find it: read the loader's code path from "verify" to "jump". Fix: load once into protected RAM, verify, run from there.
    • 

  • Fixed digests for components that will be updated. Symptom: every update requires re-releasing earlier stages, eventually impossible (scenario 6). Fix: signatures with keys.
    • 

  • Treating a refused boot as "the chain works". A refusal also has to be handled: a recovery path that is itself verified, and a safe state that suits the device.
    •

Summary


    

  • A chain of trust: an immutable root that runs first, and stages that each check the next before handing over.
    • 

  • The guarantee is conditional: genuine root, every verifier verifies, what was checked is what runs.
    • 

  • Patching a checker changes the checker; a consistent forgery of everything stops at the immutable root (scenarios 3 and 4).
    • 

  • One stage that does not check breaks the chain for everything after it, while the chain still "passes" (scenario 5).
    • 

  • Fixed digests make a chain impossible to update (scenario 6); real chains hold keys and check signatures, which moves trust into the private key.
    • 

  • Verifying stops what is wrong; measuring records what ran. The next two chapters take each one apart.
    •
