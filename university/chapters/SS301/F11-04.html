Story hook

Analogy

The outpost on the hill has no lord of its own. Its orders come by courier from the castle, sealed with the lord's seal, and the outpost's captain opens the gate only to orders whose seal matches the impression carved above his door. Last year an order told the captain to leave the north gate unguarded at night; a later order cancelled it. Since then, every order carries a number, and the captain cuts the highest number he has obeyed as a notch into the gatepost. An order with a lower number is refused, however genuine its seal.

One morning a courier arrives with last year's genuine order. Someone has written "No. 9" on the envelope in large letters, but the sealed letter inside still says No. 2. The new captain reads the envelope.

This chapter builds that outpost: a signed firmware image format with a header, a payload and a trailer of records, a boot loader that checks hash, key and signature, a security counter against rollback, a two-slot update that survives power cuts and reverts an image that does not confirm itself, and a key planned for rotation at manufacture. The curriculum's H4 acceptance tests run against it, and the forensic lab is the captain who read the envelope.

What you will be able to do

  • Design a signed image format and say exactly which bytes the signature must cover and why.
  • Implement image validation in the right order: structure, hash, key, signature, security counter.
  • Show H4's acceptance tests: updates with wrong signatures are refused, and a simulated power cut at any write never leaves the device without a working image.
  • Explain rollback protection, when the device's security counter may be raised, and what goes wrong if it is raised too early or read from the wrong place.
  • Plan signing-key rotation for devices whose trusted keys are fixed at manufacture.
  • Diagnose a downgrade attack from an image dump and a boot loader log.
Jargon box
TLV record (type-length-value)
Simple words: a small labelled box of data: what it is, how long it is, then the data. Analogy: labelled envelopes clipped to the order. Precise: a record of a type code, a length and that many bytes of value; an image trailer of TLVs can carry a hash, a key identifier, a signature and other metadata, and a reader can skip types it does not know. In this chapter's format: 2-byte type, 2-byte length, little-endian (fwimage.h lines 119–126). R1
Unprotected metadata
Simple words: data that travels with a signed image but is not covered by its signature. Analogy: what is written on the envelope rather than inside the sealed letter. Precise: any byte outside the signed region; anyone can change it without breaking the signature, so a boot loader must never take a security decision from it (the forensic lab). R3
Security counter (image)
Simple words: a number inside the signed image that says "this release fixes everything before me". Analogy: the order's number, compared with the notch on the gatepost. Precise: a value in the signed region that the device compares with a counter it stores in memory that can only increase (one-time-programmable fuses or protected storage); an image with a lower value is refused; the device raises its counter only when an image has been accepted for good. R1 S1
Key hash (public key identifier)
Simple words: a short fingerprint that says which key signed an image. Analogy: the seal's maker's mark, so the captain knows which carved impression to compare with. Precise: a hash of the signer's public key carried with the image, used by the boot loader to pick the matching trusted key; it is a hint, not a proof: the signature check with that key is the proof (lab scenario 2, fourth case). R1
Swap with status record
Simple words: exchanging two firmware slots piece by piece while writing down after each piece how far you got. Analogy: moving furniture between two rooms using a hallway, with a note on the door after every item. Precise: a sector-by-sector exchange of the primary and secondary slots through a scratch sector, each write followed by an update of a progress record in flash, so that after a power cut the boot loader repeats the interrupted step and continues. R1

Layer 1 — the kid explanation

A robot's little computer sometimes gets new software. Before it accepts the new software, it checks a stamp on it that only the robot's maker can make. If the stamp is wrong, the new software is thrown away and the old one keeps working. The software also carries a number, and the robot remembers the biggest number it has ever accepted for good, so nobody can sneak in an old version with known holes. And the robot keeps the old software until the new one has shown that it works, so a power cut or a broken update never leaves it unable to start.

Layer 2 — the student explanation

Why sign updates at all

A microcontroller usually has no UEFI, no db, no TPM. Its chain of trust is short: a boot ROM or a first boot loader that cannot be changed, which checks the application image before running it and before accepting an update.S1 F3-41 built the update machinery for H4 and checked integrity; this chapter is about the security half: who may produce an image the device accepts, which old images it must refuse, and what may and may not be trusted inside an image.

An image that describes itself

The lab's format (fwimage.h, Figure 1) has three parts: a fixed 32-byte header with the version and the security counter, the payload, and a trailer of TLV records. The build server hashes header plus payload with SHA-256, signs the same bytes with ECDSA P-256, and appends four records: the hash, the hash of its public key, the signature and an informational copy of the counter.R1 MCUboot's images are built on the same ideas: a header, the payload and a trailer of TLVs with a hash, a key hash and a signature, produced by its imgtool.D1

Not verified — check before relying on this

Everything said in this chapter about MCUboot itself is from memory of its documentation (D1), not opened, and not run: MCUboot and imgtool are not installed in this build. That includes: its header and TLV layout and type numbers, its split of the trailer into a protected part (covered by the signature) and an unprotected part, its security-counter record, its swap modes and status area, and the way an application confirms itself. The lab's own format deliberately does not copy MCUboot's bytes. Check the current MCUboot documentation before you rely on any of it.

Checks in order

validate (lines 214–247) runs five checks, in this order, and stops at the first failure: the image parses with every length inside the image; the SHA-256 of header plus payload equals the hash record; the key-hash record names one of the device's trusted keys; the signature verifies with that key over header plus payload; the security counter in the header is not below the device's counter. The lab's H4 test feeds four bad images and gets four refusals, each from a different check:R1

The independent cross-check confirms the format from outside: OpenSSL's command-line tool verifies a signature made by fwimage.h ("Verified OK") and rejects it when one byte of the signed region is changed ("Verification failure").R2

Rollback

A genuine old image is perfectly signed. If it has a known hole, an attacker who can deliver updates simply installs it. The defence is the security counter: in scenario 3 the device installs 2.0 (counter 2) and then refuses the genuine 1.1, "security counter 1 < device counter 2 (rollback)".R1 The counter only works if two things hold: it is inside the signed region, and the device's own copy can only go up.

Layer 3 — the engineer's depth

H4's power-cut test, every cut point

H4 asks that a simulated power loss during an update leave a working device.S1 The model counts every flash write (the data write and the status update after it) and repeats the update once for every possible cut point: cut before write 0, before write 1, and so on, until an update completes without a cut. Then power returns and the device boots again. Result: "26 cut points: 26 finished the update on the next boot and ran 1.1, 0 ran 1.0, 0 ran nothing".R1 Each step of the swap copies a sector to a place that still holds a valid copy of it (primary to scratch, secondary to primary, scratch to secondary), and the status record moves forward only after the write. Repeating a step after a cut writes the same bytes again, so the resumed swap ends in the same state as an uninterrupted one.

Watch out

H4's wording is "leaves the old image running". In this design a cut during the swap leads, on the next boot, to the new image running in its trial state, with the old image kept in the other slot until the new one confirms. The device is never without a working image, and the old image comes back if the new one fails (scenario 5), but a strict reading of H4 is not what this model does. A design that undoes the swap after a cut instead of finishing it would satisfy the wording literally. Which reading the course means is recorded as a decision for the owner in NOTES.md.

When to raise the counter

The device raises its counter in exactly one place: when a new image in its trial run confirms itself (updates.cc line 118). In scenario 5 the image app 2.0-broken (counter 2) crashes before confirming; on the next boot the loader undoes the swap and runs 1.0, and the device counter is still 1.R1 If the counter had been raised at install time, 1.0 (counter 1) would now be refused, and the device would have no image it may run. F11-06's forensic lab is exactly that mistake on a drone.

A real counter lives in one-time-programmable fuses or in storage only the boot loader can write; fuses can be burned a limited number of times, so products raise the counter only for security releases, not for every version.S1 That is why the lab's 1.0 and 1.1 both carry counter 1: version and security counter are different numbers with different jobs.

Unprotected data must never decide

The trailer of the lab's format is not signed (it cannot be: it contains the signature). Its hash, key-hash and signature records are protected indirectly, because changing them makes a check fail. The info-counter record is protected by nothing: it is a copy for fleet tools that list versions. The forensic lab shows a boot loader that took its rollback decision from that copy. An image with the counter copy changed from 2 to 9 has exactly the same signed region (the hash 1ee6a4ea92be… is equal), so every cryptographic check passes, and the buggy loader installs it over a device at counter 5.R3 The rule generalises: anything that influences a security decision is inside the signed region, or it is checked against something that is.

Key rotation when keys are fixed at manufacture

On many microcontrollers the trusted keys, or their hashes, are written into the boot loader or into fuses at the factory, and there is no db to update.S1 Rotation must therefore be planned before the device ships. The lab's device trusts two keys: vendor A, used every day, and vendor C, kept offline. Scenario 6 installs app 3.0 signed with C and the device accepts it.R1 What the model does not do is revoke A: a device that trusts A and C forever stays open to anyone who stole A's key. Real designs add a revocation step, for example a fuse per key slot that the boot loader burns when told to by an image signed with a later key, or a key-slot counter.

Not verified — check before relying on this

The revocation mechanisms just named are general design patterns described from memory, not features of any specific chip or of MCUboot checked in this build. Whether your microcontroller has key-revocation fuses, how many keys its boot ROM can hold, and how its fuses are programmed are in its reference manual; read that before designing the key plan.

Doing the course lab on real MCUboot

The course lab is "MCUboot signature rejection test (H4)". The shape of the test on a real board, untested here: build MCUboot for the board with signature checking and one of its supported key types; sign an application with imgtool and your key; then (1) sign the same application with a second, untrusted key and upload it to the secondary slot, (2) flip one byte of a correctly signed image, (3) upload an older correctly signed image when the build enables downgrade prevention; after each, reset and check from MCUboot's log that the update was refused and the old image runs. For the power-cut half, cut power at random moments during the swap many times (a relay controlled by a second board, or the debugger halting and resetting) and check that a valid image always runs afterwards.D1 D2 The model's scenarios 2 and 4 are the same tests on the host.

How the hardware actually does it

Flash memory can be erased only in whole sectors, and erased flash reads as all ones (the model fills empty slots with 0xff); a write can fail half-way if power fails.S2 That is why the swap works sector by sector with a status record and why each step is safe to repeat. The boot loader that does all of this must itself be unchangeable or verified by something unchangeable: on many microcontrollers a boot ROM verifies it, or a flash region is locked against writes; otherwise an attacker simply replaces the checker.S1 Signature verification is slow on a small core (an ECDSA P-256 verification takes milliseconds to tens of milliseconds depending on the core and the library); some chips have hardware accelerators for it.

Not verified — check before relying on this

Untested on hardware: the device is a C++ model on a host. The sector size (128 bytes) and the number of sectors (4) are the model's choice, not any chip's. The timing range for ECDSA verification above is an order of magnitude written from general knowledge, not a measurement; measure it on your target. Flash wear limits, fuse programming and accelerators are in your chip's documentation.

Worked example

Problem. (a) app 1.1 is 199 bytes: header 32, payload 7, TLV area 160. Account for the 160 bytes and find the signature's length. (b) In scenario 2, the "forged" image has its key-hash record overwritten at offset kHeaderSize + 12 + 4 + 4 + 32 + 4. Explain each term. (c) The device counter is 5. Which of these is installed: a genuine 1.2 with counter 2; a genuine 1.6 with counter 5; 1.6 with the info-counter copy edited to 1?

Solution. (a) 4 (area header) + (4 + 32) hash + (4 + 32) key hash + (4 + 4) info counter = 84, so the signature record is 160 − 84 = 76 bytes, 4 of them its TLV header: a 72-byte DER-encoded ECDSA signature. DER signatures vary by a byte or two between signings (their integers are encoded without leading zeros), which is why the format stores the length.R1 (b) 32 header bytes, then 12 payload bytes ("app 1.1-evil"), 4 bytes of area header, 4 bytes of the hash record's type and length, its 32-byte value, and 4 bytes of the key-hash record's type and length: the next byte is its value. (c) 1.2: refused (2 < 5). 1.6: installed (5 is not below 5). 1.6 with the copy edited: installed, because the correct loader ignores the copy and reads 5 from the signed header.R3

Where the analogy breaks


    

  1. A copied seal is a perfect seal. A wax seal can be copied badly; a signature made with a stolen private key is indistinguishable from the real thing. Key protection is the whole security of the scheme.
    2. 

  2. The notch on the gatepost can be cut only so many times. Fuses are finite; the counter is raised for security releases only, not for every order.
    3. 

  3. The captain cannot ask the castle. A device often has no network connection at boot; everything it needs to decide must be in the image and in its own fuses.
    4. 




Common mistakes and debugging


    

  • Signing the payload but not the header. Symptom: a version or counter edit goes unnoticed. Fix: the signed region includes the header (scenario 2, second case).
    • 

  • Trusting the key-hash record. Symptom: an attacker's image with a copied key hash reaches the signature check; if the code then skips it, it is accepted. Fix: always verify.
    • 

  • Taking decisions from unprotected metadata. Symptom: a downgrade succeeds with all signatures valid (forensic lab). Fix: read the counter from the signed header.
    • 

  • Raising the counter at install. Symptom: a failed trial cannot revert; the device is left with no image it may run. Fix: raise on confirm.
    • 

  • Parsing before bounds-checking. Symptom: a crafted length crashes the loader or reads outside the image. Fix: check every length against the image size first (parse).
    • 

  • No plan for key loss. Symptom: a leaked signing key with no way to stop trusting it. Fix: a second, offline key and a revocation mechanism decided before manufacture.
    •

Mini-project


Write imgcheck, a command-line tool for the lab's format: it prints every header field and TLV record of an image file, verifies it against a folder of trusted public keys and a given device counter, and labels each record "covered by the signature" or "not covered". Summary


    

  • A signed image is header + payload, signed together, plus a trailer of records that cannot all be signed.
    • 

  • Check in order: structure, hash, key, signature, counter. The key hash picks a key; only the signature proves.
    • 

  • H4 on the model: four wrong-signature updates refused; 26 of 26 power-cut points recovered, the trial image running and the old one kept until confirmation.
    • 

  • The security counter must be in the signed region and raised only when the new image confirms itself.
    • 

  • Unprotected metadata may be displayed, never trusted: the forensic downgrade passed every cryptographic check.
    • 

  • Keys fixed at manufacture need a rotation and revocation plan before the first device ships.
