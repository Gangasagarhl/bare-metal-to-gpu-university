Story hook

Analogy

The castle's gate guard does not decide on his own who may enter. He works from two lists nailed to the gatehouse wall: the guest list of seal-makers whose seals he accepts, and the banned list, which wins over everything. The lists are kept by the stewards; a change is valid only if it carries a steward's seal, and the stewards themselves are appointed by the castle's owner. When the castle is brand new and has no owner yet, anybody may nail anything to the wall. On the day the owner's name goes up, that ends.

One spring the stewards replace the old seal-maker, whose stamp may have been copied, with a new one: they add the new seal-maker to the guest list and put the old one on the banned list. The next morning the castle's own baker is turned away at the gate. Her pass still carries the old seal.

This chapter does all of that for real in the UEFI firmware OVMF: you create the four keys of a platform, enroll them with signed variable updates that you build byte by byte, sign your program, watch the firmware refuse a forged update and a replayed one, rotate the signing key, and then investigate the morning the baker was turned away.

What you will be able to do

  • Explain the roles of PK, KEK, db and dbx, setup mode and user mode, and the order in which keys must be enrolled.
  • Build authenticated variable updates (a time stamp, a PKCS#7 signature and an EFI signature list) and enroll your own keys in OVMF with SetVariable.
  • Sign a UEFI program with your own db key and predict whether the firmware will run a program signed with any given key.
  • Show that the firmware refuses database updates signed with the wrong key and updates replayed with an old time stamp.
  • Rotate a signing key (add the new key to db, revoke the old one in dbx) and explain the order of steps that avoids refused boots.
  • Diagnose a "boot refused" incident from a firmware log, a key database listing and the program's signer.
Jargon box
EFI signature list (ESL)
Simple words: the file format of the key lists: a header saying what kind of entries follow, then the entries. Analogy: one sheet on the gatehouse wall, headed "seal-makers" or "banned passes". Precise: EFI_SIGNATURE_LIST: a signature-type GUID (for example X.509 certificate or SHA-256 hash), the list size, a header size and the size of each entry, followed by entries of a 16-byte owner GUID and the signature data; PK, KEK, db and dbx each hold one or more such lists. D1 R3
Authenticated variable
Simple words: a firmware setting that can be changed only with a signed, dated request. Analogy: a change to the wall lists, accepted only with a steward's seal and a date later than the last change. Precise: a UEFI variable written with the time-based authenticated-write attribute; the data passed to SetVariable starts with an EFI_VARIABLE_AUTHENTICATION_2 descriptor (an EFI_TIME time stamp and a WIN_CERTIFICATE_UEFI_GUID holding a PKCS#7 signature) over the variable name, vendor GUID, attributes, time stamp and new content. D1 R4
Key rotation
Simple words: replacing a signing key with a new one without breaking the machines that trust the old one. Analogy: the stewards appoint a new seal-maker and, later, ban the old one. Precise: a sequence of authenticated updates (add the new certificate to db, re-sign every boot component with the new key, deploy them, then add the old certificate or the hashes it signed to dbx) whose order decides whether machines keep booting. R6
Revocation (dbx)
Simple words: putting a key or a program on the "never run" list. Analogy: the banned list, which wins over the guest list. Precise: adding a certificate, or the hash of an image, to the forbidden signature database dbx; an image matching dbx is refused even if it also matches db (observed in this lab: db still held the old certificate). D1 R6
Replay protection (monotonic time stamp)
Simple words: an old, genuinely signed update cannot be sent again. Analogy: a steward's order dated last winter is not accepted after a spring order. Precise: for time-based authenticated variables the firmware requires the new time stamp to be later than the stored one (except for appends); a validly signed but older update is refused with EFI_SECURITY_VIOLATION (observed). D1 R5

From earlier chapters: Secure Boot (PK, KEK, db, dbx), Authenticode and shim (F3-16); chain of trust and root of trust (F11-01).

Layer 1 — the kid explanation

The firmware keeps lists of who is allowed to sign programs. A program signed by someone on the list may start; anything else is turned away. The lists can be changed only by a note signed by a higher-up, and the notes must carry a newer date than the last one, so an old note cannot be used twice. When a signer is replaced, every program signed by the old signer must be signed again, or it will be turned away.

Layer 2 — the student explanation

Four variables, three levels of authority

Secure Boot's state lives in four non-volatile firmware variables. The Platform Key (PK) identifies the platform owner and authorizes changes to PK and KEK; the Key Exchange Keys (KEK) authorize changes to db and dbx; db lists the certificates and image hashes that may run; dbx lists forbidden ones.S1 D1 F3-16 read these variables on firmware stores prepared by the distribution. Here you create them. Your four keys (keys.out)R1 are RSA-2048 key pairs with self-signed X.509 certificates named "SS301 lab Platform Key", "SS301 lab Key Exchange Key", "SS301 lab signing key 2026" (db1) and "SS301 lab signing key 2027" (db2).

A platform without a PK is in setup mode: no images are verified, and the key variables can be written.D1 The empty OVMF store started that way: sbinfo reported SecureBoot = 0, SetupMode = 1 and all four databases empty, and it ran unsigned.R2 Writing PK ends setup mode. The order therefore matters: setvars wrote db first, then KEK, then PK, and the run shows the switch: SetupMode went from 1 to 0 and SecureBoot from 0 to 1 within the same program, without a reboot.R2

What a signed update contains

Each update is the 16-byte time stamp, a signature header and a PKCS#7 signature, followed by the new value of the variable: an EFI signature list holding one certificate (Figure 2). The signature covers the variable's name, its vendor GUID, the attribute bits, the time stamp and the new value; so an update for db cannot be replayed as an update for dbx, and a change of one attribute bit breaks it.D1 D2 The attribute value 0x27 combines non-volatile (0x01), boot-service access (0x02), runtime access (0x04) and time-based authenticated write (0x20); appends add 0x40, which is why the rotation's updates carry 0x67.D1 R6

The firmware's behaviour is the evidence that OVMF agrees with our encoding: it accepted all three enrolment updates and the rotation, and refused the forged and replayed ones. It does not prove that every detail matches the specification, nor that other firmware accepts the same bytes. Whether OVMF's build of the PKCS#7 verifier requires our options (detached, no signed attributes) or only accepts them was not tested.

Signing your program

The program is signed exactly as in F3-16 (Authenticode, PKCS#7 in the PE certificate table), with sign.py copied from that lab and given your db1 key. After enrolment the unsigned sbinfo was refused ("Access Denied"), the db1-signed one ran and listed the databases, and a copy signed with the distribution's test key, a valid signature from a key that is not in your db, was refused.R2 R3 A signature proves only who signed; db decides whether that signer counts.

Sources for the rows: R2 to R6. Three observations deserve a second look.

The forged update ran as a program but failed as an update. The program setvars itself was signed with db1, a key in db, so the firmware ran it. It then asked the firmware to append to db with an update signed by db1. That key may sign programs, not database updates; only KEK may. The answer was EFI_SECURITY_VIOLATION.R5 This separation is the point of the hierarchy: a compromised program-signing key cannot add more program-signing keys.

The replay was a perfectly signed update. It was byte for byte the db update that the enrolment had applied successfully, KEK signature and all. The firmware refused it because its time stamp (2026-01-01) was not later than the one stored with db.R5 D1 Without this rule, an attacker who once captured an old db update could restore an old db, re-enabling keys that were since removed. In our run the replay came before the rotation; the same refusal after a rotation is what protects the rotation.

dbx won over db. After the rotation, db still contained the db1 certificate (the listing shows both certificates), and dbx contained the same certificate. The db1-signed program was refused.R6 Revocation therefore does not require removing anything from db, which would need the full db to be re-sent; appending to dbx is enough.

Rotation as a procedure

The lab rotated in one step and then booted a program nobody had re-signed: the forensic case. A safe rotation is ordered so that no machine ever holds a dbx entry for a key that still signs something it boots:

  1. Create the new key; protect it as the old one was (offline, ideally in a hardware security module).
  2. Append the new certificate to db (signed by KEK) on every machine. Both keys now work.
  3. Re-sign every boot component (loader, kernel or second-stage loader, option ROMs if your platform verifies them, recovery tools) with the new key and deploy them. Verify on a test machine with the old key already in dbx.
  4. Only when the fleet reports that nothing signed with the old key is still installed, append the old certificate (or the hashes of specific vulnerable images) to dbx.
  5. Keep the recovery path working: a recovery medium signed with the new key, and a documented way to reach setup mode with physical presence.

On PCs with Microsoft's certificates in db, a distribution boots through shim (F3-16), and revocation of vulnerable boot loaders happens through dbx updates published for the whole ecosystem; the curriculum names that structure.S1 The order of steps above is the same; the difference is that many parties sign, and the dbx update reaches machines whose loaders were signed by someone else.

Who owns the PK

On a retail PC the PK belongs to the manufacturer; the KEK and db contain the manufacturer's and Microsoft's certificates.S1 Taking ownership, as this lab did on an empty store, means clearing the keys to reach setup mode (through the firmware's setup screen, with physical presence), then enrolling your own. A machine you own fully is the right target for this; a machine whose operating system was installed under the vendor's keys will refuse that operating system afterwards unless you also enroll the certificates it needs (see the Safety box of the lab).

How the hardware actually does it

Secure Boot is firmware logic, not processor logic: the image loader calls a verification routine, and SetVariable calls an authentication routine before writing to flash. Its strength rests on the variable store being writable only through that routine. On PCs the store is in SPI flash that only System Management Mode code may write; that is why the Secure Boot build of OVMF requires QEMU's smm=on and a secure flash device, as every run's command line shows.R2 S1 If the flash were writable from the operating system, an attacker would not bother forging a KEK signature: they would write db directly. The firmware itself is protected by an earlier root of trust (F11-01).

Not verified — check before relying on this

Untested on hardware: every run used QEMU 8.2.2 with the ovmf package 2024.02-2ubuntu0.10 Secure Boot build. The SMM-protection explanation is from the curriculum and memory, not from a PC's documentation; on a real PC, check the platform's firmware documentation for how its variable store is protected and how setup mode is entered.

Worked example

Problem. (a) sbinfo reported PK as 784 bytes holding one certificate of 740 bytes, and KEK as 792 bytes with a 748-byte certificate. Account for the bytes. (b) The enrolment update of db was 2,004 bytes. How long is its PKCS#7 signature? (c) After the rotation, db is 1,584 bytes. Is that one list with two entries or two lists? (d) Which time stamp must the next KEK-signed replacement of db carry?

Solution. (a) One signature list: a 28-byte header plus one entry of a 16-byte owner GUID and the certificate: 28 + 16 + 740 = 784; 28 + 16 + 748 = 792.R3 (b) 2,004 − 16 (EFI_TIME) − 24 (WIN_CERTIFICATE_UEFI_GUID header) − 792 (the list) = 1,172 bytes, if the layout of Figure 2 is right; the firmware's acceptance is consistent with it.R2 (c) 1,584 = 2 × 792: two complete lists, each with its own 28-byte header. The append added a second list rather than merging the entry into the first; sbinfo walks lists, so it showed both.R6 (d) A time stamp later than the one stored with db. The enrolment used 2026-01-01, the rotation's append 2026-06-01; whether an append updates the stored time stamp was not tested, so a careful tool uses a time stamp later than every update ever sent.

Where the analogy breaks


    

  1. The stewards' seal is not a face. Anyone who copies the KEK private key is, for the firmware, a steward. Castle guards could recognise a stranger; the firmware recognises only mathematics.
    2. 

  2. The banned list in a castle names people; dbx can name a single pass. dbx may hold the hash of one specific image, revoking that program while its signer stays trusted, which a list of people cannot express.
    3. 

  3. A new castle without an owner is rare; a PC in setup mode is a normal, reachable state. Clearing the keys from the setup screen returns the platform to "anybody may nail anything to the wall". Physical access to the machine is part of the trust model.
    4. 




Common mistakes and debugging


    

  • Enrolling PK first. Symptom: the db and KEK updates that follow fail with Security Violation (they are now checked). Cause: PK ends setup mode. Fix: db and KEK first, PK last, or sign every update properly so the order does not matter.
    • 

  • Re-sending an update with the same time stamp. Symptom: Security Violation for a correctly signed update (the replay step). Fix: a new, later time stamp for every non-append update.
    • 

  • Signing a db update with a db key. Symptom: Security Violation (the forged step). Fix: db and dbx updates are signed with a KEK.
    • 

  • Revoking before re-signing. Symptom: "Access Denied" for your own loader after a rotation (forensic lab). Find it: sign.py --signer on the refused file, sbinfo listing of dbx. Fix: follow the order of Layer 3.
    • 

  • The plain OVMF build or no SMM. Symptom: nothing is enforced, or the firmware does not start. Fix: the secboot build with smm=on and secure flash.
    • 

  • Losing the PK or KEK private key. Symptom: no further database updates are possible. Fix: keys backed up offline before enrolment; a recovery plan that uses physical presence.
    • 




Transition box

Where you came from: F11-01 (the chain-of-trust model) and F3-16 (reading Secure Boot state and signing with a key the distribution had enrolled). What carries over: the Authenticode signer, the UEFI programs in C++, the QEMU set-up with SMM, and the rule that only a run decides.R2 What changes: you own the keys now, so you also own the mistakes: the order of enrolment, time stamps, which key signs what, and rotation; the firmware's refusals are now your tests. What comes next: F11-03 leaves enforcement for measurement: the same db and dbx you changed here end up as values in a TPM register, and a remote verifier notices the change.

Safety


Safety
Do this lab only in QEMU with a copy of the variable store. Never enroll keys, clear keys or update dbx on a computer you depend on: a mistake leaves a machine that refuses its own operating system, and on some machines the firmware also verifies the graphics card's option ROM against db, so removing the vendor's certificates can leave no display at all. The keys in keys/ are public test material (their private halves are in the repository): never enroll them on a real machine.

Troubleshooting


    

  • Every signed program is refused after enrolment → the db certificate is not the one you signed with: compare sign.py --signer with the sbinfo listing (boot an unsigned sbinfo on a fresh store copy to read it).

  • The firmware never starts → the Secure Boot code image needs smm=on and -global driver=cfi.pflash01,property=secure,value=on.

  • Results differ between runs → you are not starting from a fresh copy of the store; run.sh copies it at the start.

Summary


    

  • PK authorizes PK and KEK; KEK authorizes db and dbx; db allows signers or hashes; dbx forbids them and wins over db.
    • 

  • Setup mode accepts key writes; writing PK switches to user mode and Secure Boot on at once (observed).
    • 

  • An update is a time stamp, a PKCS#7 signature over name, GUID, attributes, time stamp and data, and an EFI signature list.
    • 

  • The firmware refused an update signed by a program-signing key, and a validly signed update with an old time stamp.
    • 

  • Key rotation is an order of operations: add, re-sign, deploy, then revoke. Revoking first produces "Boot refused".

  1. db: a KEK (in setup mode, anyone). KEK: the PK. PK: the PK itself (in setup mode, the update is checked against the certificate it carries; from memory of D1, not tested separately here).
    2.

    3.

    4. 

  4. Its signer's certificate is in dbx, and a dbx match refuses the image whatever db says (observed in forensic_boot).
