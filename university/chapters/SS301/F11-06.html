Story hook

Analogy

The castle has grown. It now has three towers, each with its own gate and its own guard: the main tower where the captain sits, the tower that steers, and the tower that turns the great wheels. Each guard checks his own tower's orders against the seal impression carved over his own door; the steering tower's seal is not the wheel tower's seal, so a forger who copied one cannot rule the others. Every morning the captain asks each tower: "Did your guard check today's orders? Which orders are you following?" Only if all three answer yes, and the three sets of orders are ones the lord tested together, does the captain lower the drawbridge and let the wheels turn.

One autumn, the steering tower received new orders and, the same day, cut a notch in its gatepost so deep that the old orders could never be accepted again. The new orders turned out not to work with the wheel tower. The next morning the drawbridge stayed up, and stayed up.

This chapter applies everything in SS301 to machines that move: several processors, each with its own chain of trust, keys and update path, joined by a system-level rule that refuses to move the motors unless the whole robot is in a known, tested state. The lab runs the design decisions as scenarios on a model; the forensic lab is the drone whose drawbridge stayed up; the course exam asks you to design such a chain yourself.

What you will be able to do

  • Draw the chains of trust of a robot or drone with several processors and say where each one is rooted.
  • Justify one signing key per processor type, a debug lock per processor, and a system-level check of version combinations.
  • Design a coordinated update of several processors that cannot leave the robot in an untested combination, and that raises anti-rollback counters only at the right moment.
  • Connect security decisions to safety: what the robot does when a check fails, and why "motors stay disabled" is a safe state for a ground robot and is not automatically one for a flying drone.
  • Diagnose a fleet incident caused by an anti-rollback fuse raised too early.
  • Design and defend a chain of trust for a robot (course exam P) and plan the signed boot path of your MP1 or MP6 project.
Jargon box
Per-processor signing key
Simple words: each kind of processor in a machine trusts its own signing key, not one key for everything. Analogy: each tower has its own seal impression over its door. Precise: the boot loader of each processor type holds (or has fused) the hash of a key used only for that processor's firmware; a key stolen from one build pipeline can then sign code for one processor only (lab scenario 4). R1
Signed compatibility manifest
Simple words: a signed list of which firmware versions of the different processors were tested together. Analogy: the lord's list of which towers' orders belong together. Precise: a document, signed by the vendor, listing allowed combinations of the firmware versions of a machine's processors; the system controller compares the versions actually running (each reported after that processor's own verified boot) with the list, and refuses to enter an operational state for an unlisted combination (lab scenarios 3 and 6). R1
Debug lock
Simple words: switching off a processor's debug port for good, so nobody can stop it and change its memory with a debug probe. Analogy: bricking up the tower's back door. Precise: a one-time setting, usually a fuse or a protected option, that disables or restricts the processor's JTAG or SWD debug access; without it, an attacker with a probe can halt the processor after its verified boot and run other code, so the verified boot proves nothing about what runs (lab scenario 5). Mechanisms differ per chip. R1 S2
Provisioning (security)
Simple words: the factory step that gives each new machine its keys, fuses and identity. Analogy: carving the seal impressions over the doors and bricking up the back doors before the castle opens. Precise: the manufacturing process that writes trusted key hashes and initial counters, sets the debug lock and secure-boot enable, creates or injects device keys and records the device's identity, followed by an end-of-line test that checks each of these; a mistake here is usually irreversible. R1

From earlier chapters, not redefined here: chain of trust, root of trust (F11-01); security counter, key hash (F11-04); anti-rollback, test and confirm (F3-41); JTAG, debug probe (HW303); fuse (HW101); safe state; ESC; threat model.

Layer 1 — the kid explanation

A robot is not one computer but a team of small computers: one thinks, one steers, one drives the motors. Each of them checks its own software with its own stamp before starting. Then the thinking computer asks the others: "Did you check yourself? Which version are you?" If anyone failed the check, or if the versions were never tested together, the robot keeps its motors switched off. Being stuck is annoying; a robot arm or a drone motor that moves with the wrong software can hurt someone.

Layer 2 — the student explanation

Many processors, many chains

A typical robot or drone has a main computer running an operating system and the high-level software, one or more real-time controllers (a flight controller on a drone, a motion controller on a ground robot or arm), and small processors in motor drivers, sensors, batteries and radios. Each one runs firmware, and each firmware is a way in. A chain of trust that covers only the main computer leaves the motion controller, which actually commands the motors, unprotected. The lab's robot therefore has three chains, one per processor, each built from F11-04's image format and checks.R1

All from robot.out.R1 Scenario 5 deserves a second look: the output for the unlocked robot is identical to the healthy robot's, up to the probe line. A debug port that is open is not visible to any boot-time check, because the attack happens after boot. It can only be prevented at provisioning and verified at the end of the production line.

Security failure is a safety event

On a PC, a failed signature check means a screen with an error. On a robot, the system must decide what the machine physically does. For a ground robot or an arm, keeping the motors disabled and the brakes applied is usually a safe state. For a flying drone, "switch the motors off" in the air is a crash. A drone's design must therefore separate the decision "may this vehicle take off?", where any failed check means no, from "what happens if something fails in flight?", which belongs to the flight controller's failsafe design and must not depend on a slow or failing security check. The lab's model makes only the first decision.R1

Safety

Never test boot or update behaviour on a robot or drone with propellers fitted, wheels on the ground or an arm within reach. Remove propellers, lift wheels, keep a physical kill switch or arming switch within reach, and keep a clear zone. A firmware that fails its checks may still have left a motor output in an undefined state. LiPo batteries can catch fire if punctured, over-charged, over-discharged or short-circuited; charge them only with a LiPo charger in a fire-resistant bag, never unattended, and follow the battery and charger makers' instructions. Learners at levels L0–L2 work only under adult supervision. Before any outdoor flight, read the current rules of your national aviation authority. This chapter's lab is a model on a computer; none of this was tested on hardware.

Layer 3 — the engineer's depth

Where each chain is rooted

A chain of trust is only as strong as its first link (F11-01). On a robot, the roots differ per processor. A main computer that is a PC or an Arm board can use UEFI Secure Boot (F11-02) or a fused Arm boot chain (F11-05); a microcontroller uses its boot ROM's secure-boot feature, if it has one, or a boot loader in a write-protected flash region; a sensor or a small motor driver may have no secure boot at all. For those, the system must rely on the next level up: the motion controller authenticates the motor driver's messages, or the design accepts the risk and says so in the threat model. A design document that says "the robot has secure boot" without naming the root of each chain is not a design.

Not verified — check before relying on this

Which microcontrollers and SoCs offer boot-ROM signature verification, debug locking and key-revocation fuses, how many keys they hold and how they are provisioned is chip-specific and is not checked here; read the reference manual and the security application notes of the exact part before choosing it. The division of a robot into main computer, motion controller and motor driver is the model's; it is not taken from any product.

Why the manifest is signed, and by whom

Scenario 3 shows a combination that is cryptographically perfect and operationally untested. The compatibility list is how the vendor states, under signature, which combinations it tested; the main computer checks it with a key of its own (the model compares in memory; a product signs the manifest like an image, with its own security counter, so that an old, more permissive list cannot be replayed). The versions it compares must be reported by each processor after its own verified boot; a version claimed in an unverified message is the unprotected metadata of F11-04 at system scale.R1

When to burn the fuses

F11-04 established that a security counter is raised when the new image confirms itself. With several processors, "confirms itself" must mean "the whole new set passed the system test", because a processor can pass its own self-test and still fail with its neighbours. The forensic lab is the opposite policy: the motion controller raised its fuse at install time (robot.cc lines 124–127), the new image then failed the system test, and the old image became illegal on that processor.R2 The recovery path left is a new release built from the old code with the new counter, which only the vendor's signing service can produce. Two policies avoid this: raise counters only after step 4 of Figure 2, and raise them only for releases that fix a security problem. A third, sometimes used, is a counter per "security epoch" that the vendor raises rarely and deliberately.

Keys, pipelines and people

One signing key per processor type limits what a single stolen key can do (scenario 4). It also maps onto how robots are built: different teams, sometimes different companies, build the firmware of different processors. Each key should live in a signing service that logs every signature, with a second, offline key per processor planned for rotation (F11-04). The main computer's manifest key is the most powerful of all, because it decides which combinations may move the machine; it should be the best protected.

The robot software above the boot chain

Secure boot ends where the operating system starts the robot software. From there, measured boot (F11-03) can record what was loaded and let a fleet server attest each robot before it is given work, as in F11-03's forensic lab; TrustZone or a separate secure element (F11-05) can keep the robot's identity key out of reach of a compromised operating system; and the robot middleware's own message security, which is beyond this course, protects commands between processes and machines. Each layer answers a different question; none replaces the others.

How the hardware actually does it

On a microcontroller, the pieces of a chain of trust are physical: a boot ROM that cannot be changed, one-time-programmable fuses for key hashes, counters and the debug lock, flash with sectors that can be write-protected, and often hardware for SHA-256 and public-key arithmetic. On an Arm application processor they are the boot ROM, fuses, TrustZone and its memory protection (F11-05). The links between processors are serial buses such as UART, SPI, I2C or CAN, which by themselves authenticate nothing: a motor driver that obeys any well-formed command on its bus obeys an attacker who is on that bus too.S2

Not verified — check before relying on this

Untested on hardware: the lab is a host model, and no robot, drone, microcontroller, fuse or debug probe was used. Nothing in this chapter states a property of a specific chip, bus or flight-control stack; message authentication on robot buses and the security features of drone flight-control software are not covered by the sources of this build and must be read in their own documentation.

Worked example

Problem. A delivery robot has a main computer, a motion controller and a battery-management processor. The vendor releases a security fix for the motion controller (2.7 → 2.9, counter 1 → 2) that also changes the protocol to the battery processor, which must go from 3.1 to 3.2. Write the update plan: images, manifest, order, when each counter is raised, and what happens if the battery processor's update fails.

Solution. Images: motion controller 2.9 with security counter 2, battery 3.2 with an unchanged counter (not a security fix), each signed with its own processor key; a new manifest listing (main computer's current version, 2.9, 3.2), signed and with a higher manifest counter. Order: stage 3.2 and 2.9 and the manifest with the old images kept; trial-boot both; the main computer verifies the manifest and runs the system self-test with motors disabled; if it passes, confirm on both processors, then raise the motion controller's counter to 2. If the battery update fails at any point before confirmation, both processors revert to (2.7, 3.1), which is still in the old manifest and still allowed, because no counter was raised. The new manifest must keep (…, 2.7, 3.1) listed until the counters are raised, or a failed update would leave a combination that the main computer refuses. This is the plan the lab's scenario 6 follows in miniature, and the forensic lab breaks.R1 R2

Where the analogy breaks


    

  1. The towers talk over a road anyone can walk on. Messages between processors cross buses that authenticate nothing; a castle's towers at least recognise their own messengers.
    2. 

  2. A raised drawbridge is not always safe. For a castle, staying closed is safe; for a drone in the air, "stop the motors" is a fall. The safe state depends on what the machine is doing.
    3. 

  3. A notch can be cut by mistake in every tower of a fleet at once. One wrong update policy, pushed to thousands of machines, grounds them all; a castle's mistakes stay in one castle.
    4. 




Common mistakes and debugging


    

  • Securing only the main computer. Symptom: the motion controller accepts any firmware. Fix: a chain per processor, or a documented reason and compensating control where a processor cannot verify.
    • 

  • One key for all firmware. Symptom: one leaked build-server key can sign motor-driver code. Fix: per-processor keys (scenario 4).
    • 

  • Checking versions one by one. Symptom: every processor is "valid" but the robot misbehaves (scenario 3). Fix: a signed manifest of tested sets.
    • 

  • Debug ports left open. Symptom: none at boot. Fix: lock at provisioning and test at the end of the line (scenario 5).
    • 

  • Burning fuses at install. Symptom: after a failed update, the robot cannot go back (forensic lab). Fix: burn after the system test and confirmation, and only for security releases.
    • 

  • Treating "security check failed" as "stop everything" on a flying vehicle. Fix: security checks decide whether to arm; in-flight failures follow the failsafe design.

Scenario: "Grounded after the update". Inspection drone D-0311 received a motion-controller (flight-controller) update from 2.7 to 2.9, a security release that also changed the protocol to the motor drivers. Mini-project


Course exam P (design) and course project. Design a chain of trust for a robot (for MP6) or for your own operating system on a board (for MP1), and implement its signed boot path. The design document (four to six pages) names every processor and its root of trust, the keys (who holds them, where they are stored, how they rotate and how they are revoked), the image formats and checks, the anti-rollback policy (what is counted, when it is raised), the update procedure in the order of Figure 2, the debug-lock and provisioning steps with their end-of-line checks, the system-level rule that gates motion (with the safe state for your machine) and the threat model's top five threats with the control for each. The implementation, in QEMU first: a boot loader that verifies the next stage with F11-04's checks (MP6: the motion-controller firmware; MP1: your kernel, either through F11-02's Secure Boot or your own loader), with tests that show a refused wrong signature, a refused rollback and a survived power cut. Rubric: every chain has a named root; no security decision uses unprotected data; the fuse policy survives a failed update (show it with a scenario like the forensic lab); the safe state is justified for the machine's type; all tests run from a clean checkout with one command; untested-on-hardware parts are listed honestly.



Summary


    

  • A robot or drone has several processors; each needs its own chain of trust with a named root, or a documented compensating control.
    • 

  • One signing key per processor type limits what a stolen key can sign.
    • 

  • Verified processors are not enough: a signed manifest of tested combinations decides whether the machine may move.
    • 

  • Debug locks and other provisioning steps cannot be seen at boot; the end-of-line test must check them.
    • 

  • Anti-rollback counters are raised only after the whole new set passed its system test, and only for security releases; raising them at install grounded the forensic drone.
    • 

  • Security failures are safety events: "motors disabled" is safe for a parked machine, not for one in the air.

Forensic lab answer key


    

  1. 2.9. The fuse was raised to 2 at install; on the next power-on 2.7 (counter 1) in the primary slot is refused as a rollback, and the boot loader falls back to the image in the other slot, 2.9 (counter 2), which is valid. The "rollback" the technician saw put 2.7 back in the primary slot, but the fuse makes it unbootable.
    2. 

  2. The running set (FC 2.9, MC 4.2, MD 1.3) is not in the signed compatibility list, because 2.9 needs a new motor-driver protocol. Yes: 2.9 already failed its self-test with these motor drivers.
    3. 

  3. Raising the anti-rollback fuse at install time, before the self-test: "anti-rollback fuse raised to 2 at install time" comes before "self-test FAILED, image not confirmed".
    4. 

  4. (a) Release a motor-driver update that speaks 2.9's protocol plus a manifest that lists the new set, and install it as a coordinated update; (b) rebuild 2.7's code as a new release 2.7.1 with security counter 2, signed by the vendor, and install it.
