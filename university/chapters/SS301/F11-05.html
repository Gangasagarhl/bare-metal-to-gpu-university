Story hook

Analogy

The castle's treasure is no longer kept in the great hall, where hundreds of people come and go and any of them might be bribed. It is in the inner keep, a tower inside the castle with its own wall and one door. In the door is a hatch with a guard behind it. People in the outer castle cannot enter; they pass requests through the hatch: "please stamp this letter with the lord's seal". The keep's servants stamp it and pass it back. The seal itself never leaves the keep.

Years ago, a steward asked the servants for a convenience: "if I pass you the number of a shelf, read me what is on it." It saved him trips. Nobody wrote down that the keep's own treasure shelves are numbered too.

This chapter builds that keep on an emulated Arm processor: a secure monitor of about a hundred lines at the processor's most privileged level, holding a key in memory that only the secure world can reach, and a normal-world program that may ask the monitor to use the key but faults when it tries to read it. One bit, the NS bit, is the difference, and a control run proves it. Then comes the steward's convenience, and the key walks out through the hatch. Along the way you place Trusted Firmware-A and OP-TEE, the real software of this layer, on the same map.

What you will be able to do

  • Explain TrustZone's two security states, how the processor's exception levels sit in them, and what the secure monitor at EL3 does.
  • Write a minimal EL3 monitor and a normal-world program that talk through SMC, and show that the normal world cannot read secure memory.
  • Prove with a control experiment which single setting makes the difference.
  • Place TF-A's stages (BL1, BL2, BL31, BL32, BL33) and OP-TEE in the boot chain and say which one runs where.
  • Recognise a confused-deputy service in a secure-world interface and fix it.
  • Say honestly what TrustZone protects against and what it does not.
Jargon box
Secure monitor
Simple words: the small program at the processor's highest privilege that switches between the secure and the normal world. Analogy: the guard behind the hatch of the keep's only door. Precise: code running at EL3 that handles SMC exceptions, saves and restores each world's state and sets the security state of the lower exception levels when it returns; in TF-A this is BL31, the EL3 runtime. The lab's monitor is monitor.cc and el3_entry.S. D1 S1
NS bit (SCR_EL3.NS)
Simple words: the switch that decides whether the levels below EL3 run in the normal or the secure world. Analogy: which side of the keep's wall a person is sent to when the guard lets them go. Precise: bit 0 of the Secure Configuration Register at EL3; with NS = 1 the exception levels below EL3 are non-secure and their memory accesses are non-secure, so secure-only memory is not reachable. In the lab, NS = 1 gave an abort on reading secure RAM and NS = 0 let the same read succeed. D1 R1 R2
TEE (trusted execution environment)
Simple words: a protected place on the same processor where small trusted programs run, out of reach of the main operating system. Analogy: the keep and its servants. Precise: an isolated execution environment, on Arm built on TrustZone's secure world, with its own small OS that runs trusted applications and offers services (keys, secure storage, a firmware TPM) to the normal world through a defined interface. D3 S1
OP-TEE
Simple words: an open-source trusted operating system for the secure world. Analogy: the keep's household, organised. Precise: a trusted OS running in the Arm TrustZone secure world (TF-A's BL32 stage) that implements the GlobalPlatform TEE APIs for trusted applications; it can provide a firmware TPM, secure storage and key handling. S1 D3
Trusted application (TA)
Simple words: one small program that runs inside the TEE and does one secure job. Analogy: one servant of the keep, with one duty. Precise: an application loaded and run by the trusted OS in the secure world, reached from a normal-world client through the TEE's client interface; in OP-TEE, TAs are normally signed and verified before loading (not checked in this build). D3
Confused deputy
Simple words: a privileged helper tricked into using its own power for someone who does not have it. Analogy: the keep's servant who reads any shelf whose number is passed through the hatch. Precise: a component that performs an action with its own authority on a resource named by a less-privileged caller, without checking that the caller may access that resource; in secure-world services, typically a pointer or address from the normal world used without checking that it points into normal-world memory (the forensic lab). R4

From earlier chapters, not redefined here: exception level (EL), EL3 runtime (BL31), SMC, secure and non-secure worlds, Trusted Firmware-A (TF-A), boot chain (Arm) (F4-32 and DR403); trusted computing base and chain of trust (F11-01).

Layer 1 — the kid explanation

Some processors have a secret room inside them. Programs in the normal part of the chip, even the operating system, cannot look into the secret room. Only a tiny guard program can go in and out. If a normal program needs the secret, for example to sign a message, it knocks and asks; the guard does the job inside the room and hands back only the answer. In the lab you build the guard and the secret room yourself, and then find out what happens if the guard is too helpful.

Layer 2 — the student explanation

Why a second world

Every chain of trust so far ends in an operating system. If that operating system is compromised, everything it can read is lost, including keys. TrustZone splits the processor's resources into two security states. The normal world runs the usual software stack; the secure world runs a small, separately verified stack. Memory, and some devices, can be marked secure, and a normal-world access to them is refused by the hardware.D1 The trusted computing base for a key then shrinks from "the whole operating system" to "the monitor and the secure world's code".

Exception levels in two worlds

AArch64 has four exception levels: EL0 for applications, EL1 for an OS kernel, EL2 for a hypervisor, EL3 for the secure monitor (DR403). EL0 and EL1 (and on newer cores EL2) exist in both worlds; EL3 is always secure.D1 Which world the lower levels belong to is decided by EL3, through the NS bit of SCR_EL3, at the moment it returns to them with ERET. The way back up is an exception: the SMC instruction, "secure monitor call", traps to EL3 like a system call traps to a kernel.

The lab in one paragraph

QEMU's virt board with secure=on starts the processor at EL3 in the secure state, at address 0, where the board's secure flash holds our monitor.R1 The monitor writes a 32-byte demo key into secure RAM at 0x0e000000, sets SCR_EL3 to "EL1 is AArch64, non-secure" and returns with ERET to our program in normal RAM at 0x40200000. The program asks for the service version and three keyed digests through SMC, gets the "unknown function" value for an unknown function, and then reads 0x0e000000 directly. The read does not return: the processor takes a synchronous exception, and the program's handler prints ESR_EL1 = 0x96000010 (EC 0x25, DFSC 0x10) with FAR_EL1 = 0x0e000000.R1 The digests are correct: Python recomputes them from the same key and messages.R3

The control run: one bit

Is the abort really TrustZone, or something else about the address? The control run changes a single instruction operand: the monitor sets NS = 0 instead of 1 (el3_entry.S lines 14–18). The program, byte for byte the same, now runs at secure EL1. Its read of 0x0e000000 succeeds and prints 0x948f86b9b0aba2a5, the first eight bytes of the key.R2 (The program still prints "[normal world]", because it is the same program; the monitor's line says what world it really is in.) Only the NS bit differs between the two runs, so the NS bit is what made the key unreachable.

Not verified — check before relying on this

From memory of the Arm Architecture Reference Manual (D1), not opened: the bit positions of SCR_EL3 (NS = bit 0, RW = bit 10) and the SPSR value 0x3c5, the vector offsets (0x400 for a synchronous exception from a lower level in AArch64, 0x200 for the current level with its own stack), the ESR decoding (EC 0x17 = SMC from AArch64; EC 0x25 = data abort at the current level; DFSC 0x10 = synchronous external abort). The runs show that these values produce the described behaviour on QEMU 8.2.2. The memory map (secure flash at 0, secure RAM at 0x0e000000, UART at 0x09000000, RAM at 0x40000000, the device tree at the start of RAM) is QEMU's virt board's, taken from QEMU's documentation and source (pending verification) and confirmed only by the runs. The SMC function-ID bit layout in tz.h follows the SMC Calling Convention from memory (D4).

Layer 3 — the engineer's depth

What a monitor must get right

The lab's monitor shows the irreducible duties: install a vector table (vbar_el3), keep its own stack in secure memory, save the caller's registers on every SMC and restore them afterwards (el3_entry.S lines 42–80), check that the exception really is an SMC (monitor.cc lines 70–77), dispatch on the function ID in x0 and return results in x0, and answer unknown functions with a defined value instead of guessing. A real EL3 runtime also keeps a separate saved context for each world and each core, switches between them, handles power management requests (PSCI: CPU on and off, reset, power off) and other standard services.S1 Every one of those is code at the highest privilege, reachable from the normal world: the attack surface of the secure world is exactly its SMC interface.

TF-A's trusted boot

Trusted Firmware-A names its stages BL1 (a boot ROM-like first stage where TF-A starts first), BL2 (trusted boot loader), BL31 (EL3 runtime), BL32 (secure payload, such as OP-TEE) and BL33 (non-secure firmware, such as U-Boot or EDK II).S1 BL2 loads the later images; in TF-A's trusted-boot configuration each image is verified against a chain of certificates rooted in a key the platform trusts (often a hash in fuses, checked by the boot ROM). That is F11-01's chain on Arm. After boot, BL31 stays resident; BL2 is gone. On a product with a locked boot chain, the boot ROM refuses a BL2 that is not signed by the vendor's key: you cannot replace the secure world, which is good for a product and a limit for a learner (DR403's "locked (fused) boot chain").S2

Not verified — check before relying on this

TF-A was not built or run, and its documentation (D2) was not opened. The description of its trusted-boot mechanism (a certificate chain checked by BL1 and BL2, a root-of-trust public key whose hash is provisioned in the platform) is from memory; its image formats, certificate types, build options and the platforms on which it is enabled must be read in the current TF-A documentation. Stage names and roles are as the curriculum lists them.

OP-TEE and the normal world

The curriculum describes OP-TEE as the optional BL32: a trusted OS in the secure world implementing the GlobalPlatform TEE APIs, which can provide a firmware TPM, secure storage and key handling.S1 Its structure is the lab's structure grown up: instead of one monitor with a switch, a monitor that forwards to a trusted OS, which runs separately loaded trusted applications; the normal world reaches them through a driver in its kernel and a client library; the monitor switches worlds on each request. The lab's keyed-digest service corresponds to what a trusted application for device keys would offer: "use the key", never "give me the key".

Not verified — check before relying on this

OP-TEE was not built or run, and its documentation (D3) was not opened. The description of its normal-world side (a kernel TEE driver, a client library, a helper daemon for storage) and of trusted-application signing is from memory. The curriculum's catalog lists a Linux TPM driver for a TEE-based firmware TPM (tpm_ftpm_tee), which suggests how F11-03's TPM can live in the secure world on Arm; how it is built and provisioned is not checked here.

The confused deputy

The forensic build adds one more service to the monitor, "peek": read eight bytes at an address given in x1 and return them (monitor.cc lines 93–106). It runs at EL3 in the secure state, so it can read secure RAM. A normal-world program asks it to read 0x0e000000, 0x0e000008, 0x0e000010 and 0x0e000018, and prints all 32 bytes of the key; the first word, 0x948f86b9b0aba2a5, is the one the control run read directly.R4 The hardware did exactly its job: the normal world never touched secure memory. The monitor did it on the normal world's behalf. With the address check of lines 98–103 compiled in, the same program gets 0x00000000ffffffff ("unknown function") four times.R5 The general rule for every secure-world service: an address, length or handle that comes from the normal world must be checked to refer to normal-world memory that the caller may use, before the secure side touches it; and checked once, then copied, so that the normal world cannot change it between check and use (TOCTOU, F11-01).

What TrustZone does not protect against

  • Bugs in the secure world itself. Its code runs with full privilege; a parsing bug in a trusted application or the monitor is a hole in the keep (the forensic lab is one).
  • Misuse through legitimate interfaces. Anyone in the normal world can ask the lab's monitor for digests with the key; TrustZone keeps the key secret, not the right to use it. Access control on services is the secure world's job.
  • Physical and side-channel attacks: probing, fault injection, timing and power analysis are outside the architectural model.
  • A secure world that was never verified. Without the trusted boot of Figure 2, whoever controls the flash controls the keep; the lab's monitor is not verified by anything.

How the hardware actually does it

The security state travels with every memory access: a non-secure access carries a marker on the bus, and memory controllers and peripherals that are configured as secure refuse it, which the processor sees as an external abort.D1 That matches the lab: the abort's status code is "synchronous external abort", not a translation or permission fault (the normal world had no MMU enabled at all), so the refusal came from outside the processor core, from QEMU's model of the board.R1 On real SoCs, which memory ranges and devices are secure is set by configurable protection controllers, programmed early in boot by secure firmware, and the same applies to DMA-capable devices, which must not be able to read secure memory on behalf of the normal world.

Not verified — check before relying on this

Untested on hardware: every run was QEMU 8.2.2's virt board with a Cortex-A57 model. The bus-level description above (a security marker on each access, protection controllers set up by secure firmware, DMA protection) is general knowledge written from memory, not read from an SoC manual; the names, registers and defaults of protection controllers differ per SoC and are in its reference manual. Whether a given board's secure world is open to you depends on its boot ROM and fuses (see F4-34 for platform families).

Worked example

Problem. (a) Decode the monitor's function IDs: 0xC3000001 has bit 31 and bit 30 set and 3 in bits 29–24. What does each part mean in tz.h's comment? (b) Decode ESR_EL1 = 0x96000010 into EC, IL and DFSC, using the field positions EC = bits 31–26, IL = bit 25, DFSC = bits 5–0. (c) The normal-world stack is set by the monitor to 0x40300000. Why not 0x0e00f000, and why not 0x40000000?

Solution. (a) Bit 31: a fast call (handled at once, not resumable); bit 30: the SMC64 convention (64-bit arguments); 3 in bits 29–24: the owning-entity range the lab chose, "OEM service"; the low bits 0x0001 select the keyed digest. This follows the SMC Calling Convention from memory (pending verification).D4 (b) 0x96000010 = 1001 0110 0000 … 0001 0000 in binary: bits 31–26 = 100101 = 0x25 (data abort, current EL), bit 25 = 1 (32-bit instruction), DFSC = 010000 = 0x10 (synchronous external abort), as the handler printed.R1 (c) 0x0e00f000 is secure RAM: the first push from the normal world would abort. 0x40000000 is where QEMU places its device tree; the lab moved its program and stack to 0x40200000 and 0x40300000 after an earlier version overwrote the device tree.

Where the analogy breaks


    

  1. The keep has no windows; the processor does. Caches, timing and power use are shared between the worlds, and careful measurement of them can leak information a wall would stop.
    2. 

  2. The guard is not a person who can be persuaded; he is the code. There is no judgement at the hatch beyond what the monitor's switch statement says. Every service is exactly as safe as its code.
    3. 

  3. The keep is built by the same masons as the castle. Secure-world code is written, compiled and updated by the same kind of people and tools; it is smaller, not magically correct.
    4. 




Common mistakes and debugging


    

  • Using a normal-world pointer without checking it. Symptom: secrets leak through a service (forensic lab). Fix: check range and ownership, copy once, then use.
    • 

  • Forgetting to save registers in the SMC handler. Symptom: the normal world crashes some instructions after a successful SMC. Fix: save and restore every register the compiled handler may change (the lab saves x0–x30).
    • 

  • Normal-world stack or image overlapping QEMU's device tree. Symptom: random behaviour or a hang in the normal world at start. Fix: start above the device tree (the lab uses 0x40200000).
    • 

  • Wrong vector offset. Symptom: the SMC goes to the panic handler ("unexpected exception"). Fix: lower-EL AArch64 synchronous is at 0x400 from vbar_el3, as the lab uses.
    • 

  • Concluding "TrustZone works" from one abort. Fix: a control run that changes only the security state, as tz_control does.
    • 

  • Debug services left in a release. Fix: build switches that cannot be on in release builds, and a review of the SMC dispatch table before every release.
    • 




Transition box

Where you came from: F11-04 (a boot loader that verifies images with keys it trusts) and DR403's Arm boot chain. What carries over: exception levels and SMC, the chain of trust (now TF-A's trusted boot), and the habit of proving a claim with a control run.R2 What changes: the question is no longer only "is this code genuine?" but "where can a secret live when the operating system may be hostile?", and the answer is a second world whose whole interface is a list of SMC services. What comes next: F11-06 puts everything together on robots and drones: several processors, each with its own chain, keys and update path, and a system that must fail safe.

Goal


Build the smallest secure monitor that keeps a key out of the normal world's reach, prove the separation with a control run, and find and fix a confused-deputy service. Place TF-A and OP-TEE on the same map.S1


Hardware and software needed


No hardware. clang 18.1.3, ld.lld 18.1.3 and llvm-objcopy for aarch64-none-elf; QEMU 8.2.2 (qemu-system-aarch64); Python 3 for the cross-check. TF-A and OP-TEE are not used; reading their documentation is the extension.


Safety


Safety
Do not try to replace or probe the secure world of a phone, tablet or board you depend on: on locked platforms the boot ROM refuses unsigned secure firmware, and failed attempts can leave a device that does not boot. Work in QEMU, then on a development board whose documentation explicitly supports building and flashing your own TF-A, with its recovery mode tested first.

Summary


    

  • TrustZone splits the processor into a normal and a secure world; EL3, always secure, runs the monitor that switches between them.
    • 

  • The NS bit set by EL3 decides the world of the lower levels; in the lab it alone made the difference between an abort and a successful read of the key.
    • 

  • The normal world reaches the secure world only through SMC services; those services are the secure world's attack surface.
    • 

  • TF-A provides the stages (BL1, BL2, BL31, BL32, BL33) and trusted boot; OP-TEE is a trusted OS at BL32 that runs trusted applications.
    • 

  • A service that uses normal-world addresses without checking them is a confused deputy: the hardware's guarantee is bypassed by the secure world's own code.
    • 

  • None of this was run with TF-A or OP-TEE or on hardware; the mechanism was shown with a 100-line monitor on QEMU.
    •
