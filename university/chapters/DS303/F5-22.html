Story hook

Analogy

Seven friends live in different towns along one railway line. Every weekend the town council gives them chores: paint a fence, sort a library's books, carry a piano up a hill. Some chores need one friend. Sorting the library needs three friends in the same building at the same time, all day. The piano needs four friends with strong arms, and only two of the seven have them.

At first everyone turned up wherever they liked. Two friends painted the same fence while the library waited. So the friends chose an organiser, Lucía. Lucía keeps a notebook: who has which tools, who is busy until when, who is ill this week. Every chore is written on a card and goes into her box. She hands chores out, and she says "not yet" when the people a chore needs are busy, and "never" when nobody in the group can do it.

One Saturday the library chore failed at four in the afternoon because Kenji's train broke down. The other two friends had to start again on Sunday. Lucía wrote in her notebook: the more friends a chore needs at once, the more likely one of them will be missing. That sentence is most of this chapter.

What you will be able to do

  • Explain what a cluster is: nodes, their roles (login, compute, management), the network and the shared storage, and what a cluster scheduler adds on top.
  • Distinguish the two big families of cluster work, batch jobs and long-running services, and say which kind of scheduler each family uses in this course (Slurm in F5-23, Kubernetes in F5-25).
  • Decide, from a node table, whether a resource request can run now, later or never, and write the check as a program.
  • Compute the probability that a job spanning k nodes for T hours finishes, given an assumed per-node failure probability, and explain why large jobs need checkpoints.
  • Run one parallel job as several processes with mpirun, and explain what a launcher does that a single program cannot.
Jargon box
Cluster
Simple words: many computers connected by a network and managed together so that they can share work. Analogy: the seven friends along the railway line, with one organiser. Precise: a set of independent computers (nodes), usually alike and connected by a local network, that is operated as one system: one administrative domain, a common view of users and storage, and a scheduler that decides where work runs. D2 D1
Node (cluster)
Simple words: one computer in a cluster. Analogy: one friend's house, with that friend's own tools. Precise: one machine with its own processors, memory, operating system and network interfaces; it fails independently of the others. Not the same as a circuit node (HW101) or a graph node. D2 D3
Login node and compute node
Simple words: the login node is where people sign in and prepare work; compute nodes are where the work really runs. Analogy: the station where friends meet Lucía, and the houses where the chores happen. Precise: roles a cluster gives its nodes: users connect to a login (front-end) node, submit jobs to the scheduler, and the scheduler starts them on compute nodes; management services (the scheduler's controller, databases, monitoring) often run on separate management nodes. D1
Job (batch)
Simple words: a piece of work you hand to the cluster that starts, runs and ends. Analogy: one chore card in Lucía's box. Precise: a request for resources (nodes, CPUs, memory, GPUs, a time limit) together with the program to run in them; it waits in a queue, is allocated resources, runs to completion or failure, and releases them. D1
Cluster scheduler (resource manager)
Simple words: the program that decides which work runs where and when. Analogy: Lucía, the organiser who assigns chores (registered mapping). Precise: software that tracks the resources of every node, keeps a queue of requests, chooses an allocation for each according to a policy (priorities, fairness, limits), starts the work on the chosen nodes and reclaims the resources when it ends. Not the same as the operating system's CPU scheduler of F3-03, which chooses among threads on one machine. D1 D5
Shared file system (cluster)
Simple words: a disk that every node can see, so a job finds its files on whichever node it lands. Analogy: the library all the towns can borrow from by post. Precise: a network file system mounted at the same path on the login and compute nodes, holding home directories, inputs and outputs; it is itself a distributed system that can be slow or fail (DS402). D1 D3
Tightly coupled job
Simple words: a job whose parts must all keep running and keep talking; if one part stops, the whole job stops. Analogy: the library chore that needs three friends in the room all day. Precise: a parallel job whose processes exchange data during the run (for example with MPI collectives), so that progress needs every process; contrast with independent tasks that can each succeed or fail alone. D4 D3
Rank (MPI)
Simple words: the number of one process in a parallel job, counted from zero. Analogy: the badge number each friend wears for one chore. Precise: the integer identifying a process within an MPI communicator; with N processes in MPI_COMM_WORLD the ranks are 0 to N − 1, returned by MPI_Comm_rank. D4 R3
Checkpoint (job)
Simple words: a saved copy of a job's progress, so that after a failure it can continue instead of starting again. Analogy: writing on the library wall which shelves are already sorted. Precise: application or system state written to stable storage at chosen points, from which a restarted job resumes; the cost of writing it is traded against the work lost per failure. Not the same as a file-system journal checkpoint (OS401). D3

Layer 1 — the kid explanation

A cluster is a team of computers that work as one. Each computer is called a node. People do not choose a node themselves. They write down what their work needs, and a program called the scheduler finds nodes that have it free. When the work ends, the scheduler gives the nodes to someone else.

Some work needs many nodes at once, all talking to each other. That work is fragile: if one node stops, all of it stops. So big jobs save their progress now and then, like a game that saves at checkpoints.

Layer 2 — the student explanation

From one machine to many

On your laptop you are the scheduler. You decide which program runs, you know how much memory there is, and if the machine crashes you notice at once. A cluster replaces you with software, because there are too many machines and too many users to coordinate by hand. DS301's F5-08 gave the two reasons to distribute at all: more capacity than one machine has, and surviving the failure of one machine. A cluster is the place where both reasons meet in practice. D2 D3

The guide's bridge BR-10 lists what changes on that step: many machines fail independently, a scheduler decides where code runs, shared storage and the network become bottlenecks, each server has its own NUMA structure, and observability becomes a requirement because you cannot "go and look". It also names three traps: benchmarking on a noisy shared node, assuming clocks agree, and having no timeouts. This chapter meets the first and the third; DS301 (F5-10) already met the second. C1

The parts

Figure 1 shows the parts that the Slurm overview names and that most clusters share. Login nodes are where people work interactively: edit, compile, look at results, and submit. Compute nodes run jobs and are usually not used interactively; each runs a small agent of the scheduler that starts and watches the work. A controller (on a management node) holds the queue of jobs and the table of node states and makes the decisions. A shared file system is mounted at the same path everywhere, so a job finds its program and inputs on whichever node it lands. The network connects all of them; F5-01 to F5-07 (DS201) taught its Ethernet and IP layers, and DS401 adds the RDMA networks that tightly coupled jobs often need. D1 D2

Nodes are not all alike. A cluster often has partitions or pools of nodes with different hardware: CPU-only nodes, nodes with much memory, nodes with GPUs. A request names what it needs; the scheduler's job is to match requests to nodes that have it. Listing 1 does the simplest version of that match. D1

Two families of work

Cluster work comes in two shapes. A batch job starts, computes and ends: a simulation, a build, a training run. What matters is when it finishes, and it can wait in a queue. A service runs indefinitely and answers requests: a web server, a database, an inference server. What matters is that enough copies are always up. The Borg paper describes one cluster manager that runs both kinds in the same cells, giving services higher priority; F5-27 studies that design. HPC clusters have traditionally run batch schedulers such as Slurm (F5-23); service platforms run orchestrators such as Kubernetes (F5-25). The boundary is blurring, which is why this course teaches both. D5 D1 D6

Three answers a scheduler can give

When a request arrives, the scheduler can say three things: run now (enough suitable nodes are idle), wait (enough suitable nodes exist but some are busy), or never (no set of nodes in the cluster can ever hold it, because the request asks for more per node than any node has, or for more such nodes than exist). The third answer matters because a scheduler that does not give it lets a job wait forever: DS303's forensic lab in F5-23 is exactly that case. Listing 1 computes the three answers for a node table; R1 shows two requests that can never run. R1

Layer 3 — the engineer's depth

Failure arithmetic

Assume each node fails in any given hour with probability p, independently of the others and of earlier hours. A job that needs k nodes for T hours finishes only if none of the k × T node-hours sees a failure, so

P(finish) = (1 − p)k·T

and the expected number of attempts until one finishes, if every failure means starting again from the beginning, is 1 / P(finish). The model's two assumptions are strong: real failures are correlated (a power or network fault takes out many nodes at once) and failure rates change with age and load. DS301's F5-11 showed the second problem every scheduler has: a node that has stopped responding and a node that is merely slow look the same for a while. The formula is still the right first estimate, and its lesson is robust: the success probability falls exponentially in the job's size in node-hours. D3 R2

Two engineering consequences follow. First, a large tightly coupled job must checkpoint: write its state to stable storage periodically, so that a failure costs only the work since the last checkpoint. Checkpointing too often wastes time writing; too rarely wastes time recomputing; the mini-project lets you find the balance numerically. Second, the scheduler must detect failed nodes, stop giving them work, and tell the job's owner; in Slurm the node's state changes and the job ends with a failure state, which F5-23 shows in its simulator and names, as unverified, for Slurm itself. D3 D1

Launching one job on many processes

A parallel job is not one program that "uses many nodes". It is many processes, normally one or more per node, started together and told who they are. MPI defines the contract: every process calls MPI_Init, learns the size of MPI_COMM_WORLD and its own rank, and communicates by messages and collective operations such as MPI_Reduce, which combines one value from every rank into one result at a root rank. Who starts the processes is not part of the program: a launcher (mpirun, or the scheduler's own launcher inside a job allocation) starts N copies on the allocated nodes and gives them the information to find each other. Listing 3 is such a program; R3 shows it run with 1, 2 and 4 processes on one machine. D4 R3

R3 also contains the first lesson of BR-10 in miniature. The time each rank spends computing falls as you add ranks, because each does a smaller share. The wall time of the whole mpirun falls much less, and can even rise, because starting processes and connecting them costs time that does not shrink. On a shared machine the numbers also change from run to run: the build container is shared with other work, so look at the three runs in R3 as measurements on that container only, not as properties of Open MPI or of any processor (AH-23). R3

Note

Why do the ranks of R3 print in order? They did not: run.sh sorts the lines, because processes of one job print independently and their lines can arrive in any order. Never rely on output order between ranks; it is one of the first surprises of parallel jobs.

What "managed together" means

The difference between "a cluster" and "some computers on a network" is operational. A cluster has one list of users and permissions, one software environment (the same compilers and libraries on every node, or containers that bring their own: F5-24), one view of storage, one scheduler with an accounting record of who used what, and one monitoring system. Without those, the scheduler's promise ("your job will see what it asked for") cannot be kept: a job that lands on a node with a different library version fails in ways that depend on where it ran. How the hardware actually does it

A node is a server: one or more processor sockets, each with its memory channels (a NUMA domain, HW203's F1-39), PCI Express devices such as network adapters, local disks and GPUs (HW204's F1-45), and a baseboard management controller that can power it on and off and report sensors over a separate network (DS304's F5-29). The cluster network connects the nodes' network adapters through switches; inside each node, a job's processes on different sockets already see different memory latencies, so "where a process runs" matters at two scales: which node, and which cores of that node. Schedulers expose both scales: the node choice, and options that pin processes to cores and sockets (F5-23). D2 D1

The one machine this build can inspect is its own container: R3's runs report the host name vm for every rank, and the run log records 4 logical CPUs. All four ranks of the 4-process run therefore ran on one node, sharing its cores: this is a one-node "cluster", which is enough to learn the launch contract and not enough to learn the network. A multi-node run is the lab's extension, untested in this build. R3

Worked example

1. Run now, wait, or never (R1). The node table of inventory.in lists seven nodes: four CPU nodes (one of them down) and three GPU nodes with 4 GPUs each. Take request gpu4x3: 3 nodes, each with 32 CPUs, 400 GiB and 4 GPUs. Which nodes can hold that, if free? A CPU node has no GPUs, so none of them. Each GPU node has 32 CPUs, 512 GiB and 4 GPUs, so all three can. Of these, only gpu02 is idle. So "able now" is 1, "ever" is 3, and the request needs 3: it waits. Now gpu8x1: 1 node with 8 GPUs. No node has more than 4 GPUs, so "ever" is 0: never, however long it waits. bigmem asks for 1,024 GiB on one node; the largest node has 512 GiB: never again. R1 prints exactly these verdicts. R1

2. Capacity of the up nodes (R1). The down node cpu04 is not counted. CPUs: 3 × 64 + 3 × 32 = 192 + 96 = 288. Memory: 3 × 256 + 3 × 512 = 768 + 1,536 = 2,304 GiB. GPUs: 3 × 4 = 12. R1's second line prints 288 CPUs, 2304 GiB, 12 GPUs. Notice that the total says nothing about the "never" answers: 12 GPUs exist, but never 8 on one node. R1

3. A 64-node day (R2). With p = 0.0005 per node per hour, k = 64 and T = 24: k·T = 1,536 node-hours, and P(finish) = 0.99951536. Using ln(0.9995) ≈ −0.000500, the exponent is 1,536 × (−0.000500) ≈ −0.768, and e−0.768 ≈ 0.464. R2's formula column prints 0.4639, and the simulation finished 904 of 2,000 attempts (0.452), within sampling noise. Expected attempts: 1 / 0.4639 ≈ 2.16, so about 2.16 × 24 ≈ 52 hours of a 64-node allocation for 24 hours of useful work, if every failure restarts from zero. For 512 nodes, P(finish) = 0.0021 and the expected number of attempts is about 467: the job practically never finishes without checkpoints. R2

QA note: the arithmetic of steps 2 and 3 was checked against R1 and R2, and the logarithm step with Python's math module during authoring (0.46385 for 64 nodes; 466.6 expected attempts for 512).

Where the analogy breaks


    

  • Lucía can phone Kenji and hear that his train broke down. A scheduler cannot tell a dead node from a slow or unreachable one; it only sees missing heartbeats, and must choose a timeout (DS301's F5-11). A node declared dead may in fact still be running the old job.
    • 

  • Friends can share half a chore informally. Nodes cannot: a job gets exactly the resources the scheduler allocated, and two jobs on one node are separated by the operating system (and, in F5-24, by containers), not by good manners.
    • 

  • Lucía sees all of her friends at once in her notebook. A real controller's node table is always slightly out of date, because node states arrive as messages over the network; decisions are made on a picture of the past.
    • 

  • In the story, a failed chore costs one afternoon. In a cluster, a failed tightly coupled job costs every node-hour it used, which grows with its size (Figure 2).
    • 




Common mistakes and debugging


    

  • Reading the total as the answer. Symptom: "the cluster has 12 GPUs free but my 8-GPU job waits". Cause: the request is per node, and no node has 8. How to find it: compare the per-node request with the largest node's capacity (Listing 1, worked example 1). Fix: change the request (two nodes with 4 GPUs each, if the program can use two nodes) or use a partition with bigger nodes.
    • 

  • Running heavy work on the login node. Symptom: the login node is slow for everybody; administrators kill your process. Cause: the login node is shared and not part of the scheduler's allocations. Fix: submit a job, even for a short test (F5-23 shows how to ask for an interactive allocation).
    • 

  • Assuming a failed job means a bad node. Symptom: you exclude node after node and failures continue. Cause: at scale, failures are spread over many nodes by chance (the forensic lab). How to find it: list which nodes failed; if they are all different, the cause is scale, not one node. Fix: checkpoints, shorter jobs.
    • 

  • Benchmarking on a shared node. Symptom: the same run is faster one minute and slower the next (R3's wall times). Cause: other work on the same machine. Fix: ask the scheduler for an exclusive node, repeat runs and report the median (curriculum 13.4's benchmark rules), and record the machine.
    • 

  • Expecting output in rank order. Symptom: interleaved or reordered lines. Cause: ranks print independently. Fix: let rank 0 gather and print, or prefix each line with the rank and sort.
    •

Mini-project


How often to checkpoint? Summary


    

  • A cluster is many independent nodes, a network, shared storage and a scheduler, operated as one system.
    • 

  • Users work on login nodes and submit jobs; the controller keeps a queue and a node table and starts work on compute nodes through an agent on each node.
    • 

  • Cluster work is batch jobs (finish time matters) or services (enough copies up matters); Slurm and Kubernetes are this course's examples of the two.
    • 

  • A request is per node; the scheduler can answer run now, wait, or never, and "never" must be detected or the job waits forever.
    • 

  • With independent failures, P(finish) = (1 − p)k·T falls exponentially with node-hours: large jobs need checkpoints.
    • 

  • A parallel job is many processes started by a launcher; MPI gives each a rank, and collectives need every rank alive.
    • 

  • Measurements on a shared node vary from run to run; record the machine and repeat.
    •
