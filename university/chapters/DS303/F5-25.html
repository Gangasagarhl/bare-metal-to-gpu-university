Story hook

Analogy

The friends now run a lending library that must always be open in three towns at once. Lucía cannot phone everybody every hour, so they try something new. In the town hall there is a noticeboard. On it, someone pins a wish: "the library is open in 3 towns". Below it, the friends pin what is true right now: "open in Amara's town", "open in Kenji's town", "open in Yusuf's town".

Nobody gives orders. Each helper watches one part of the board. Rafael counts the open libraries and compares with the wish; if there are too few, he pins a new card, "a library needs a town". Mei looks only for cards without a town and writes a town on each, choosing the one with the most free shelves. In each town, a caretaker reads the board and opens any library assigned to her town. Every caretaker also pins "still here" every morning.

When Kenji's town floods and his "still here" note stops appearing, Ingrid, who watches those notes, writes "Kenji's town unreachable" and crosses out his library. Rafael sees only two libraries and the wish for three, and pins a new card. Mei finds a town for it. Nobody planned a response to floods. Each helper did its one job again.

What you will be able to do

  • Draw Kubernetes' architecture: the API server and its key-value store, the scheduler and the controllers in the control plane; the node agent, the container runtime and the service proxy on each node; and say what each one reads and writes.
  • Explain declarative desired state and level-triggered reconciliation, and why independent control loops recover from failures nobody programmed for.
  • Trace a node failure through heartbeats, eviction, replacement and scheduling in a simulator log, and compute when and where each pod lands.
  • Explain pods, labels and selectors, deployments and services, and diagnose a service with no endpoints from pod and service listings.
  • Compare Kubernetes with Slurm (F5-23): what each schedules, how each handles failure, and which workloads each fits.
Jargon box
Kubernetes
Simple words: a system that keeps a set of containers running on a group of machines, the way you described you want them. Analogy: the noticeboard and its helpers. Precise: an open-source container orchestration system: users declare objects (desired state) through an API; control loops continuously drive the cluster's actual state toward it, scheduling containers onto nodes, replacing failed ones and routing traffic to them. D1
Control plane
Simple words: the part of the cluster that decides and remembers; the nodes do the work. Analogy: the noticeboard with Rafael, Mei and Ingrid. Precise: the components that hold cluster state and make global decisions: the API server, its backing key-value store, the scheduler and the controller managers; they may run on dedicated machines and are replicated for availability. D1
API server
Simple words: the one front door to the cluster's records; everyone reads and writes through it. Analogy: the noticeboard itself, with its rules about who may pin what. Precise: the component that exposes the Kubernetes API, validates and stores objects in the key-value store, and lets clients watch for changes; the other components communicate through it rather than with each other. D1 D2
etcd
Simple words: the database where the cluster's records are kept safely on several machines. Analogy: the noticeboard's copies, kept identical in several town halls. Precise: a distributed, strongly consistent key-value store that replicates its data with the Raft consensus algorithm (DS302); Kubernetes uses it as the backing store for all cluster data. D1 D6
Pod
Simple words: the smallest thing Kubernetes runs: one or a few containers that always go together. Analogy: one library branch, with its librarian and its book cart, always in the same town. Precise: a group of one or more containers scheduled together onto one node, sharing a network namespace (one IP address) and storage volumes; pods are disposable and are replaced, not repaired. D3
Controller (Kubernetes)
Simple words: a helper that keeps checking one kind of record and fixes any difference between what is wished and what is true. Analogy: Rafael, who only counts libraries. Precise: a control loop that watches objects of some kinds through the API server, compares their desired state (spec) with the observed state (status), and acts through the API to reduce the difference; examples manage replica sets, deployments, nodes and endpoints. D4
Reconciliation (level-triggered)
Simple words: fixing things by looking at how they are now, not by remembering what happened. Analogy: Rafael counts the libraries each time; he does not need to know there was a flood. Precise: a control style in which each loop iteration acts on the current difference between desired and observed state ("level"), not on individual change events ("edges"); a missed or duplicated event therefore does no lasting harm, because the next iteration sees the same difference. D4 R1
kubelet
Simple words: the agent on every node that starts the pods assigned to that node and reports on them. Analogy: the caretaker in each town. Precise: the node agent that watches for pods bound to its node, asks the container runtime to run their containers, reports pod and node status, and renews the node's heartbeat. D1
Deployment and ReplicaSet
Simple words: records that say "keep this many copies of this pod running", and how to change them gradually. Analogy: the wish "open in 3 towns", plus a plan for swapping old books for new ones town by town. Precise: a ReplicaSet keeps a stated number of pods matching a selector; a Deployment manages ReplicaSets to roll out a new pod template gradually and to roll back. D3
Label and selector
Simple words: labels are name tags on objects; a selector is a rule like "everything tagged app=web". Analogy: coloured stickers on the library cards, and "all cards with a green sticker". Precise: labels are key–value pairs attached to objects; an equality-based selector matches an object when every key–value pair of the selector is present in the object's labels; controllers and services find their pods this way. D3 R2
Service (Kubernetes)
Simple words: one stable name and address for a changing group of pods. Analogy: "the library", whichever towns it is open in today. Precise: an object that selects pods by labels and gives them a stable virtual address and name; the set of ready, selected pods' addresses (its endpoints) is kept up to date by a controller, and traffic to the service is spread over them. D5 R2
Resource request and limit (Kubernetes)
Simple words: the request is what a container is promised and what the scheduler counts; the limit is the most it may use. Analogy: "this library needs two shelves" (request) and "may never use more than three" (limit). Precise: per-container amounts of CPU and memory: the scheduler places pods by the sum of requests against a node's allocatable capacity; limits are enforced on the node through control groups (F5-24). D7

Layer 1 — the kid explanation

In Kubernetes you do not say "start this program on that machine". You write down what you want: "three copies of my web server, always". Kubernetes stores your wish. Then many small helper programs keep comparing the wish with what is really running, and fix any difference. If a machine dies, nobody needs a special plan: a helper notices that only two copies run, and starts a third somewhere else.

The programs run in containers (F5-24). Kubernetes groups them in pods and gives each group of pods one stable name, so other programs can find them even while they move around.

Layer 2 — the student explanation

Declarative desired state

Slurm (F5-23) receives commands: "run this job". Kubernetes receives objects: records that describe the state you want, written in a structured format (usually YAML) and sent to the API server. A Deployment object says "keep N pods made from this template"; a Service object says "give the pods with these labels one stable address". Each object has a spec (desired state, written by you) and a status (observed state, written by the system). Everything else in the system is a loop that works on the difference. D1 D3 D4

The components

Figure 1 shows them. The API server is the only door: it authenticates and validates requests, stores objects in etcd, and lets clients watch objects, receiving changes as they happen. etcd is a key-value store replicated with Raft, so the cluster's records survive the loss of a minority of its members (DS302 explains why a majority is needed). The scheduler watches for pods that have no node yet and assigns each to a node. The controller manager runs many controllers, one per kind of object (replica sets, deployments, nodes, endpoints, and more). On each node, the kubelet watches for pods assigned to its node, asks the container runtime (through a defined interface, F5-24) to run their containers, reports their status, and renews the node's heartbeat; a service proxy on each node programs the node's networking so that traffic to a service reaches one of its pods. D1 D2 D6

The components do not call each other. The scheduler does not tell the kubelet to start a pod; it writes the node's name into the pod object, and the kubelet, watching, sees it. This is the noticeboard of the story, and it is why components can restart, be replaced or be replicated independently. D1 D4

Control loops

Listing 1 builds a miniature of this design. A Store plays the API server and etcd. Four loops run every tick and communicate only through the store: node agents (start bound pods, renew heartbeats), a node controller (mark nodes NotReady when their heartbeat is too old, evict their pods), a replica controller (count live pods per app and create or delete pods to match the desired number), and a scheduler (bind each unbound pod to the Ready node with the most free CPU that can hold its request). R1 shows the loops reacting to a scale-up and to a node that loses power without telling anyone. R1

Notice what the replica controller does not know: it never hears about the failure. At t = 9 it only counts three live pods and a wish of five, and creates two. That is level-triggered reconciliation: every iteration acts on the current difference, so a missed event, a crashed controller or a duplicate notification is healed by the next iteration. The Kubernetes documentation describes controllers in exactly these terms, as loops that move the current state toward the desired state. D4 R1

Pods, labels, services

A pod is the unit of scheduling: its containers land on the same node, share one network namespace (one IP address, so they reach each other on localhost) and can share volumes. Pods are cattle, not pets: a failed pod is replaced by a new one with a new name and address, never repaired in place (R1's web-6 and web-7 replace web-2 and web-5). Because addresses change, nothing should depend on a pod's address. Labels on pods and selectors in controllers and services connect objects loosely: a ReplicaSet owns the pods its selector matches; a Service sends traffic to the ready pods its selector matches. Listing 2 implements the selection rule: every key–value pair of the selector must appear in the pod's labels, exactly, and the pod must be ready. D3 D5 R2

Layer 3 — the engineer's depth

Scheduling in two phases

For each unscheduled pod, the Kubernetes scheduler first filters nodes that can run it (enough allocatable CPU and memory for the pod's requests, matching node selectors and affinities, tolerated taints, free ports and volumes), then scores the remaining nodes by plug-in criteria (for example spreading or packing by resource use, affinity preferences) and binds the pod to the best one. If no node passes the filters, the pod stays Pending and the scheduler records why; it may also preempt lower-priority pods to make room (F5-27 studies preemption in Borg, Kubernetes' ancestor). Listing 1's scheduler has one filter (Ready and enough free CPU) and one score (most free CPU); R1's "unschedulable" lines are its version of the recorded reason. D8 R1

Requests, not usage, drive placement. A pod that requests 1.5 CPU occupies 1.5 CPU of the node's schedulable capacity whether it uses it or not; limits, enforced by the node through control groups, cap what it may use. F5-27 shows how Borg exploits the gap between reservation and use, and F5-24 showed what happens at a memory limit. D7

Failure detection: the same problem as DS301

The node controller cannot tell a dead node from an unreachable one. It sees only that the node's heartbeat has not been renewed for longer than a grace period, then marks the node NotReady (in Kubernetes, the node's Ready condition becomes Unknown) and, after a further delay, evicts its pods so that controllers replace them. This is DS301's F5-11 failure detector with a timeout, and it has the same trade-off: short timeouts replace pods quickly but evict healthy pods during network blips; long timeouts leave a service short of replicas for longer. R1's model detects at t = 9 a failure that happened at t = 7. D9 R1

And there is a worse case. If k2 had only lost its network, its kubelet would still be running web-2 and web-5 while the control plane started replacements elsewhere: for a while, more copies run than desired, and two of them cannot be reached by the control plane. For stateless web servers that is harmless; for a pod that must be unique (a database primary), it is the "two leaders" problem of DS301 and DS302, which is why Kubernetes offers separate abstractions with stronger identity guarantees for stateful workloads (check the StatefulSet documentation before relying on its exact semantics). D9 D3

Concurrency control in the store

Many loops write to the same objects. The API server uses optimistic concurrency: each object carries a version; an update must name the version it was based on, and is rejected if the object changed in between, so the writer re-reads and retries. Watches deliver changes in order with those versions, and a client that falls behind lists the objects again and resumes watching. Level-triggered design is what makes this simple: after any conflict or gap, a controller recomputes from the current state. D2 D4

How the hardware actually does it

Kubernetes adds no hardware mechanism; it is a set of user-space programs talking over the network. On each node, the kubelet's work becomes the kernel features of F5-24: a pod's containers share a network namespace, each container gets its control group with the CPU and memory limits from the pod's specification, and its processes run on the node's cores like any others. A service's stable address is implemented in the node's packet-processing rules (the kernel's netfilter tables or similar), programmed by the service proxy, so that a connection to the service's virtual address is rewritten to one pod's real address (DS201's IP layer). etcd's durability rests on each member writing its log to local disk before acknowledging (DS302's persistence rule); slow disks under etcd therefore slow every write in the cluster. D1 D5 D6

Worked example

Following R1 from t = 7 to t = 16. Nodes k1, k2, k3 each have 4,000 m (thousandths of a CPU); every pod requests 1,500 m; grace period 3 ticks.

  1. At t = 5 the records show web-1 and web-4 on k1, web-2 and web-5 on k2, web-3 on k3: free CPU k1 = 4,000 − 3,000 = 1,000 m, k2 = 1,000 m, k3 = 2,500 m.
  2. t = 7: k2 loses power. Its agent stops renewing the heartbeat; the last renewal was at t = 6.
  3. t = 8: 8 − 6 = 2 < 3: still Ready. t = 9: 9 − 6 = 3, not < 3: the node controller marks k2 NotReady and evicts web-2 and web-5 (R1: "no heartbeat since t=6").
  4. Same tick, the replica controller counts 3 live pods, wants 5: creates web-6 and web-7.
  5. The scheduler filters Ready nodes with ≥ 1,500 m free: k1 has 1,000 (no), k3 has 2,500 (yes). web-6 → k3, leaving k3 with 1,000. For web-7 no Ready node has 1,500 free: unschedulable.
  6. Totals hide this again (F5-22): the two Ready nodes have 2,000 m free together, more than 1,500, but no single node does. Two nodes can hold at most 2 × ⌊4,000 / 1,500⌋ = 2 × 2 = 4 pods; the wish is 5.
  7. t = 15: k2 is back; its heartbeat is fresh, the node controller marks it Ready, and the scheduler binds web-7 to k2 (4,000 free, the most). t = 16: k2's agent starts it. Final: 5 pods running, as R1's last line shows.

Every number here is printed in R1; the capacity arithmetic of step 6 is checked by the "unschedulable" lines from t = 9 to t = 14. R1

Where the analogy breaks


    

  • A noticeboard shows everyone the same picture at the same moment. Watchers of the API server receive changes with delays and can fall behind; each loop acts on its own, possibly stale, view and must tolerate conflicts (Layer 3).
    • 

  • In the story, Ingrid's "unreachable" note is a fact. In Kubernetes it is a guess from missing heartbeats: the node may be alive and still running the "evicted" pods (Layer 3's network-partition case).
    • 

  • Rafael's count is instant. The real replica controller's actions go through the API server and etcd, which is a Raft group: if a majority of etcd members is down, nobody can write to the board at all, and the cluster cannot react to anything (DS302).
    • 

  • The libraries in the story keep their names when they move. Pods do not: a replacement is a new pod with a new name and address; only the Service's name is stable.
    • 




Common mistakes and debugging


    

  • A service with no endpoints. Symptom: connections to the service fail although pods are running. Cause: selector and pod labels differ (the forensic lab), or no selected pod is ready. How to find it: list pods with their labels and the service's selector and endpoints (Listing 2's output is the model). Fix: make them match in the workload's pod template.
    • 

  • Pods stuck Pending. Symptom: pods never get a node. Cause: requests larger than any node's free allocatable capacity (R1's web-7), unsatisfiable affinities or untolerated taints. How to find it: the scheduler's recorded reason for the pod. Fix: smaller requests, more capacity, or corrected constraints; never "fix" it by removing requests, which makes placement blind.
    • 

  • Editing a running pod and expecting it to stick. Symptom: your change disappears. Cause: a controller recreated the pod from the template. Fix: change the Deployment's template; the controller rolls the change out.
    • 

  • Assuming a NotReady node's pods are dead. Symptom: two instances of something that must be unique. Cause: a network partition (Layer 3). Fix: workloads that need uniqueness use the abstractions and fencing designed for it, plus application-level leases (DS302).
    • 

  • Treating etcd as an ordinary database. Symptom: the whole cluster is slow to react. Cause: slow disks or too few healthy etcd members. Fix: monitor etcd's health and latency first when the control plane is slow.
    • 




Transition box

Where you came from: F5-24: containers as processes in namespaces with control-group limits; F5-23: a batch scheduler that receives commands and runs jobs to completion; DS301 and DS302: failure detection by timeout, replicated logs and Raft. Summary


    

  • Kubernetes stores desired state as objects in an API server backed by etcd (a Raft-replicated key-value store); every component talks to the API server, never to each other.
    • 

  • The scheduler binds pods to nodes by filtering and scoring, using requests; the kubelet on each node runs bound pods through a container runtime and renews the node's heartbeat.
    • 

  • Controllers are level-triggered loops: they act on the current difference between spec and status, so they repair failures nobody planned for (R1).
    • 

  • Node failure is detected by heartbeat timeout, with DS301's dead-or-unreachable ambiguity; evicted pods are replaced, not repaired.
    • 

  • Pods are disposable groups of containers; labels and selectors connect them to controllers and services; one wrong character empties a service (R2).
    • 

  • Kubernetes places pods one at a time; Slurm places whole multi-node jobs at once: the difference matters for GPU gangs (F5-26).
    •
