Story hook

Analogy

The friends' chores keep failing for silly reasons. Ofelia's recipe for fence paint works in her town and not in Rafael's, because his tin of white is a different brand. Kenji's book-sorting chore assumes the label printer is on the left shelf; in Amara's house it is in the hall.

So the friends invent chore kits. Each kit is a sealed box with the exact tools and the exact paint, and an instruction card. Whoever does the chore takes the kit into a spare room of their house, closes the door, and works only with what is in the box. The room has its own number plate on the door, so letters for the chore go to the right place. And the house owner puts a rule on the door: "this room may use at most two buckets of water". When Rafael's chore tried to use a third bucket, the tap was shut, and the chore stopped.

The kit does not bring its own house. It uses the house's walls, roof and plumbing. That is the difference between a container and a virtual machine, and it is the most important sentence of this chapter.

What you will be able to do

  • Explain what a Linux container is, precisely: ordinary processes placed in their own namespaces, limited by control groups, started on a root file system from an image, all on the host's one kernel.
  • Demonstrate namespaces from C++ (a new host name and a new process-number space) and read the evidence in /proc.
  • Run a real container with an OCI runtime (runc) from a folder you built yourself, and read its generated configuration.
  • Diagnose a process killed for exceeding its memory limit, from its exit status and the control group's counters.
  • Compare containers with virtual machines (F4-38) for isolation, start-up and what each shares with the host.
Jargon box
Container (Linux)
Simple words: a group of ordinary programs that the operating system keeps in their own little world, with their own files and limits. Analogy: a sealed chore kit used in a spare room with its own door, number plate and water rule. Precise: one or more processes running on the host kernel inside a set of namespaces (their own view of process ids, host name, mounts, network and more), confined by control groups (resource limits and accounting) and by privilege restrictions, with a root file system taken from a container image. Not the same as a C++ container such as std::vector (SP101). D1 D3
Namespace (Linux)
Simple words: a separate copy of one thing the system usually shares, such as the list of process numbers or the computer's name. Analogy: the room's own number plate: the same house, a different address inside. Precise: a kernel feature that wraps a global resource so that processes inside the namespace see their own isolated instance of it; Linux has namespaces for mounts, UTS (host and domain name), IPC, PIDs, networks, users, control groups and time. Not the same as an NVMe namespace (DR301) or a C++ namespace. D3 L1
Control group (cgroup)
Simple words: a group of processes that the kernel measures and limits together. Analogy: "this room may use at most two buckets of water". Precise: a kernel mechanism that organises processes in a hierarchy and lets controllers (memory, CPU, PIDs, I/O, devices and others) account for and limit their resource use; Linux has two versions, v1 (one hierarchy per controller) and v2 (one unified hierarchy). D4 R5
Container image
Simple words: the packed contents of a container: its files and the settings to start it. Analogy: the sealed box before anyone opens it. Precise: an immutable bundle of file-system layers plus a configuration (default command, environment, and more), identified by a digest of its content and distributed through registries; the OCI Image Format Specification standardises it. D2
OCI bundle
Simple words: a folder that a container runtime can start: the files, plus a description of how to run them. Analogy: the opened kit laid out on the table with its instruction card. Precise: a directory with a root file system and a config.json describing the process, mounts, namespaces, resources and security settings, as defined by the OCI Runtime Specification; runc spec writes a default one (R3). D1 R3
Container runtime (OCI runtime)
Simple words: the program that actually creates a container from a bundle and starts its first process. Analogy: the friend who opens the kit in the spare room and fits the door rules. Precise: a program implementing the OCI Runtime Specification's operations (create, start, kill, delete, state) by making the system calls that set up namespaces, control groups, mounts and privileges; runc is the reference implementation, and higher-level tools (container engines, Kubernetes' kubelet in F5-25) call such a runtime. D1 R2
OOM kill (cgroup)
Simple words: the kernel stopping a program at once because its group used all the memory it was allowed. Analogy: the tap shut on the third bucket. Precise: when a memory control group reaches its limit and the kernel cannot reclaim enough memory from it, the kernel's out-of-memory handler kills a process in that group with SIGKILL; the parent sees termination by signal 9, which a shell reports as exit status 137 (128 + 9). D4 D5 R5
Capability (Linux)
Simple words: one small piece of the administrator's power that can be given or taken away on its own. Analogy: one key from the house owner's ring, instead of the whole ring. Precise: Linux divides the privileges of the root user into named capabilities (for example CAP_KILL, CAP_NET_BIND_SERVICE) that a process may hold or lack individually; container runtimes drop most of them, so root inside a container is weaker than root on the host. D3 R3

Layer 1 — the kid explanation

A container is not a little computer. It is a normal program that the operating system fools a bit. The program sees its own list of programs, its own computer name, and its own files. It can only use as much memory as it was given. All of this is done by the one real operating system, which is still in charge.

The files come packed in an image, like a kit in a box. Because the kit has everything the program needs, it runs the same way on your laptop and on a cluster node.

Layer 2 — the student explanation

Why clusters want containers

F5-22 said that a cluster must give every job the same software environment, or results depend on which node a job lands on. There are two ways to achieve that: install the same software on every node and change it rarely, or let each job bring its own user-space files. Containers are the second way. The image carries the program with its libraries and tools; the node supplies only the kernel and the hardware. A job that worked on a laptop in a container works on a node in the same container, as long as the kernel features it needs are there. D2 D3

Namespaces: a private view

OS201's F3-02 showed that a process sees the system through the kernel: its process id, the list of other processes, the file tree, the host name. A namespace gives a group of processes a private instance of one of those things. The C library header of this build lists the flags that request a new namespace when creating a process or with the unshare system call: mount (CLONE_NEWNS), control group, UTS, IPC, user, PID, network and time. L1 D3

Listing 1 uses two of them. A helper process calls unshare(CLONE_NEWUTS | CLONE_NEWPID) and then forks. R1 shows the result: the child is process 1 in its new PID namespace and sees its parent as 0 (the parent is outside its namespace), while the helper sees the same child under an ordinary large number; the child sets its host name to box1 and the parent's host name is still vm afterwards; and the namespace identifiers that /proc/self/ns shows are different inside and outside. A new PID namespace takes effect for the children of the caller, not for the caller itself, which is why the program forks after unshare. R1 D3

Control groups: a limited budget

Isolation of the view is not a limit on use. A process in its own namespaces can still use all the memory of the machine. Control groups add the limit: the kernel accounts memory, CPU time, process counts and I/O per group and enforces the limits configured for it. The build container's kernel offers cgroup v1 controllers (memory, cpu, cpuset, pids, blkio, devices, freezer and others) as separate hierarchies under /sys/fs/cgroup, plus a v2 hierarchy, as seen while preparing the lab. R5 creates a v1 memory group by hand, writes a limit of 67,108,864 bytes (64 MiB) to its memory.limit_in_bytes file, moves a process into it, and reads the kernel's counters afterwards. D4 R5

Images and bundles: the files

A container's root file system comes from an image. The OCI Image Format Specification describes an image as a set of file-system layers (each a set of changes on top of the previous one), a configuration, and a manifest that lists them by the digest of their content, so that an image can be fetched from a registry and verified. Before a runtime can start it, a container engine unpacks the layers into a single directory tree and writes a runtime configuration: together they form an OCI bundle. This build has no registry and no internet, so the lab skips the image step and builds a bundle by hand: a rootfs folder containing two statically linked programs, and the config.json that runc spec generates. D2 D1 R3

Layer 3 — the engineer's depth

What runc printed, field by field

R3 is the summary of the configuration that runc 1.5.1 generated. Read it as a specification of the container. ociVersion: 1.3.0 is the version of the runtime specification the file follows, the same "spec" version that runc --version prints. process.args is the command (the default is a shell; the lab replaces it). process.user is uid 0 and gid 0. root.path: rootfs with readonly: True makes the bundle's folder the root directory, read-only. linux.namespaces lists pid, network, ipc, uts and mount: the container gets new instances of those five. The mounts give it its own /proc, /dev (with pts, shm and mqueue), /sys and /sys/fs/cgroup. The bounding set keeps three capabilities, CAP_AUDIT_WRITE, CAP_KILL and CAP_NET_BIND_SERVICE. Finally linux.resources holds a device rule that denies access to all devices by default; the lab adds a memory limit there. R3 D1

Two absences are as important as the entries. There is no user namespace in the list: uid 0 in this container is uid 0 on the host, restrained only by the dropped capabilities, the read-only root and the device rule. Rootless containers, which map the container's root to an unprivileged host user through a user namespace, close that gap; the lab's extension asks you to compare. And there is no cgroup namespace and no time namespace in this default. R3 D3

The same program, two worlds

R4 runs one static program, inside, twice. On the host it is an ordinary process: a large pid, the host name vm, dozens of processes visible in /proc, 27 entries in /, and a memory limit file containing a very large number (the value the kernel shows for a v1 group with no limit set). In the container it is pid 1 with parent 0, host name box1, exactly one process visible (itself), and six entries in /: the four directories made for the bundle and the two programs. With the limit configured (R5's container_limit run), the same file inside the container reads 67108864. Nothing in the program changed; only its namespaces, root directory and control group did. R4 R5

How the runtime does it

A runtime turns the configuration into system calls, in an order that matters: create the control group and write the limits; create the process with the new namespaces (with clone flags or unshare); inside the new mount namespace, mount /proc and the other file systems and switch the root directory to rootfs; drop capabilities and apply security filters; then execute the configured program, which becomes the container's first process. The runtime specification defines the lifecycle operations around that (create, start, kill, delete, and state), and runc's own help lists matching commands, plus extras such as checkpoint, restore, pause, update and events (R2). D1 R2

Not verified — check before relying on this

The order of operations in the paragraph above (control group, namespaces, mounts, pivot_root, capabilities, seccomp, exec) is from memory of the OCI Runtime Specification's "Lifecycle" section and of runc's behaviour; the specification and runc's source code were not opened in this build. The statement that a v1 memory group without a limit reports a very large number in memory.limit_in_bytes is an observation of this kernel (R4), not a documented constant; check the kernel's "Memory Resource Controller" document. The names "rootless containers" and the user-namespace mapping files (uid_map, gid_map) are from memory of the user_namespaces(7) man page.

Containers in clusters

Batch clusters and orchestrators use containers differently. Kubernetes (F5-25) is built around them: its node agent asks a container runtime, through a defined interface, to run the containers of each pod, and the pod's resource requests and limits become control-group settings. HPC batch clusters often run jobs directly on nodes and add containers through runtimes designed for unprivileged users and for MPI and GPU access. Either way, the scheduler's allocation (F5-23) and the container's control group are two views of the same promise: the job gets what it asked for and no more. GPU access in a container needs the device files and the user-space driver libraries of the host, which are not in the image; F5-26 returns to that. D6 D1

Not verified — check before relying on this

The interface between Kubernetes' node agent and the runtime is called the Container Runtime Interface (CRI); common CRI implementations are containerd and CRI-O; HPC-oriented container runtimes include Apptainer (formerly Singularity) and Podman; NVIDIA provides a "container toolkit" that injects GPU devices and driver libraries. All these names are from memory and none of the documents was opened in this build (the container does contain a containerd binary, version 2.3.6, which was not used). Check the Kubernetes documentation ("Container Runtime Interface", "Container Runtimes") and each project's own documentation before relying on them.

Isolation is not a security boundary of the same strength as a VM

Every container on a node shares one kernel. A kernel bug reachable by a system call is reachable from every container, and a container with too many privileges (all capabilities, host devices, the host's PID or network namespace, no user namespace) is close to a process on the host. A virtual machine's attack surface is the hypervisor's much narrower interface (F4-38). Clusters that run untrusted code therefore add layers: user namespaces, system-call filters, mandatory access control, or a lightweight virtual machine per container. F11's courses study these trade-offs. D3 D7

How the hardware actually does it

Nothing new in the hardware: that is the point. A process in a container executes on the same cores, uses the same page tables and memory management unit (F3-04) and enters the same kernel through the same system-call instruction as any other process. Namespaces are tables and pointers inside the kernel; control-group limits are counters the kernel checks when it allocates memory or schedules CPU time. The memory limit in R5 is enforced when the program touches pages: each memset of a new 4 MiB block makes the kernel allocate physical pages, charge them to the group, and, when the charge would pass the limit and nothing can be reclaimed, invoke the out-of-memory handler for that group only. The rest of the machine is not short of memory at all, as the host run of the same program shows. D4 R5

Compare a virtual machine, where the processor's virtualization extensions, nested page tables and virtual devices are involved in every guest memory access and I/O (F4-38). A container costs no hardware mechanism beyond what an ordinary process costs; this chapter does not quote a start-up time or an overhead percentage, because none was measured here.

Worked example

Reading an exit status of 137. R5's container run ended with runc exit status: 137. Shells and runc report a process that ended by a signal as 128 + the signal number. 137 − 128 = 9. In this build's C library header, signal 9 is SIGKILL ("Killed"). So the process did not exit by itself; it was killed, and SIGKILL cannot be caught, which is why the program printed no message of its own. L1 D5 R5

Where did it stop? The program allocates and touches 4 MiB per step and prints every fourth step. The limit is 67,108,864 bytes = 64 × 1,048,576 = 64 MiB. The last printed line is "allocated 48 MiB". The next print would come at 64 MiB of program data, but the process also needs memory for its code, stack and C++ runtime, and the vector of blocks; the group's charge reached the limit before step 16 completed. The hand-made group of the oom_cgroup run confirms it: memory.max_usage_in_bytes equals the limit exactly, memory.failcnt counts the times the limit was hit, and memory.oom_control reports oom_kill 1. On the host, without a limit, the same program reached 256 MiB and printed "done". R5

Units check. 4u << 20 = 4 × 220 = 4,194,304 bytes = 4 MiB; 64 steps × 4 MiB = 256 MiB. The limit argument 67108864 = 226 bytes = 64 MiB. Binary prefixes throughout (guide 13.3).

Where the analogy breaks


    

  • A spare room has walls. A container has no walls of its own: its isolation is a set of kernel rules, and the house's plumbing (the kernel) is shared. A flaw in the plumbing affects every room at once; a flaw in a VM's virtual hardware usually does not reach other VMs.
    • 

  • The kit in the story contains all the tools. A container image contains no kernel and no drivers: a container needing a kernel feature or a GPU driver gets the host's or nothing.
    • 

  • The house owner shuts the tap politely at the third bucket. The kernel's out-of-memory handler kills a process with SIGKILL, without warning and without letting it save anything.
    • 

  • Root in the spare room is not the house owner, in the story. In R3's default configuration, uid 0 inside is uid 0 outside, with fewer capabilities; without a user namespace, the difference is narrower than the analogy suggests.
    • 




Common mistakes and debugging


    

  • "The container works on my laptop but is killed in the cluster." Symptom: exit status 137, no error message from the program (R5). Cause: the cluster sets a memory limit (a pod limit in F5-25, a job's memory request in F5-23) that the laptop does not. How to find it: read the limit from inside (R5's container_limit) and the group's counters (oom_cgroup). Fix: measure peak memory and set the limit with a margin, or reduce memory use.
    • 

  • A program that needs libraries in an empty root. Symptom: "no such file or directory" when running a program that exists. Cause: the program's dynamic loader or libraries are not in the image. Fix: put them in the image, or build statically as this lab does.
    • 

  • Expecting the container to see its own limits through nproc or free. Symptom: a program sizes its thread pool or cache for the whole machine and is throttled or killed. Cause: some tools report the machine's resources, not the control group's. Fix: read the control-group files, or pass the limits to the program explicitly.
    • 

  • Reading the wrong cgroup version. Symptom: the limit file "does not exist". Cause: cgroup v2 uses different file names (for example a single unified hierarchy with memory.max; name from memory, check the kernel's cgroup v2 document). Fix: check which version is mounted (/sys/fs/cgroup) before reading.
    • 

  • Running as root inside without a user namespace. Symptom: none, until something goes wrong. Cause: the default configuration keeps host uid 0. Fix: use rootless containers or user namespaces where possible; never mount host devices or the container runtime's socket into an untrusted container.
    •

Safety
This lab runs commands as root. Use a virtual machine or a machine you can reinstall, never a shared server or a machine you depend on. The memory experiment kills only the process inside its control group, but a typo in a control-group path or a limit written to the wrong group can affect other programs: read every command before running it, and remove the groups you create.

Summary


    

  • A Linux container is ordinary processes in their own namespaces, limited by control groups and privilege restrictions, on a root file system from an image, sharing the host's kernel.
    • 

  • Namespaces isolate views (pids, host name, mounts, network, IPC, users, cgroups, time); /proc/self/ns shows which instance a process is in.
    • 

  • Control groups account and limit resources; at a memory limit the kernel kills a process with SIGKILL, reported as status 137.
    • 

  • An OCI runtime such as runc builds a container from a bundle: rootfs plus config.json; R3 shows a real default configuration.
    • 

  • Without a user namespace, root inside is root outside with fewer capabilities; containers are a weaker boundary than virtual machines.
    • 

  • Clusters use containers to carry the software environment with the job; the scheduler's allocation and the container's limits are the same promise.
    •

Forensic lab answer key


    

  1. Outside a container the program reaches "done: 256 MiB". In the container it prints 16, 32 and 48 MiB and ends with status 137. Its configuration has "memory": {"limit": 67108864}; the probe confirms the limit is visible inside as 67108864.
    2. 

  2. A runtime bug would show up for other programs and other limits, and the same program would fail in a container without the limit. A program crash would usually leave a message, a different signal (for example 11, a segmentation fault, status 139) or fail on the host too. A memory limit predicts SIGKILL at about the limit, a maximum usage equal to the limit and an OOM-kill counter.
    3. 

  3. 137 = 128 + 9: killed by SIGKILL. The limit is 64 MiB; the program needs about 256 MiB plus runtime overhead. The test group shows memory.max_usage_in_bytes equal to the limit, a non-zero memory.failcnt and oom_kill 1: the kernel's out-of-memory handler for that group killed it.
    4. 

  4. Measure the peak memory on the laptop (for example with the control group's maximum-usage counter or a profiler), then request a limit above it with a stated margin; or reduce the program's memory (stream the data in chunks). Verify by rerunning in the container with the new limit and checking that oom_kill stays 0 and the program prints "done".
    5. 

  5. Record each job's memory limit and peak usage; alert on OOM-kill events (runc's own help lists an events command that reports OOM notifications, R2); add a check that rejects images whose measured peak exceeds the requested limit; document that status 137 means "killed by signal 9" in the team's runbook.
