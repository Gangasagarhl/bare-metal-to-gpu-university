Story hook

Lan built a garden shed for herself over three weekends. It stands. The door sticks when it rains, so she lifts it a little as she opens it. The left corner is lower, because her garden slopes, so she keeps the heavy tools on the right. The hinges came from a box in Kofi's garage; he said "take what you need". Nobody else uses the shed, so none of this matters. Lan knows all of it.

Then the neighbours ask her to build a small house for Ines's family. Lan has the same hands, the same saw, the same habit of checking each joint. But now a family will live inside. Ines will not know to lift the door. Her children will lean on the left wall. A second carpenter checks Lan's joints before the plaster goes on. An inspector walks through with a list. Lan writes a handover letter that says what was built and what changed from the drawing, and a snag list: "the back door may stick in wet weather; plane it in spring". She leaves her phone number, because a leak at night is now her problem too. And she asks Kofi what his hinges were for. He says they were for his own repairs, and he would like to be asked before they go into anyone's house.

The shed and the house use the same skills. What changes is that other people depend on the house and cannot read Lan's mind. This bridge is that step for code.

What you will be able to do

  • Explain what carries over from hobby code to production (working code, tests, the habit of reading sources) and what changes when other people depend on it: reviews, CI, versioning, compatibility, documentation, monitoring, security updates, on-call, licences and the cost of being wrong.
  • Reproduce and fix the four traps of this step with real runs: "works on my machine", missing tests for failure paths, undocumented assumptions, and copied code with an unknown licence.
  • Make an earlier project production-grade: a CI script with three builds, failure-path tests that check exit status and message, a version number with one source of truth, release notes, a known-issues list and a licence record.
  • Decide whether a change is a patch, a minor or a major version from its effect on existing callers, and prove a compatibility claim with a test.
  • Estimate the cost of being wrong as an exposure (users × runs × days × fraction affected) and show how monitoring and fast updates shrink it.
Jargon box
Production software
Simple words: code that other people run and rely on, so its mistakes become their problems. Analogy: the house a family lives in, not the shed you built for yourself. Precise: in this university, software whose behaviour other people or programs depend on without reading its source; it therefore needs a stated interface, a version, tests of its failure paths, an automated gate before every change (CI), release notes, a known-issues list, a licence record, a way to notice failures in use (monitoring) and someone who answers when it breaks. The list is this chapter's working definition, assembled from the bridge card (guide 6.2) and discussed as team practice in D1 and D2. D1 D2
Failure path (error path)
Simple words: the way a program goes when something is wrong with its input or its world. Analogy: what the house does when the wind blows, not on a calm day. Precise: every branch of a program that handles invalid input, an unavailable resource or an out-of-range result, including exceptions that are thrown but never caught; a failure path is tested when a test drives the program into it and checks the exact outcome (exit status, message, return value). R1 and R2 show a project whose failure paths had no tests. R1 R2
"Works on my machine"
Simple words: a program that behaves correctly only on the computer where it was written. Analogy: a shed that stands straight only because your own garden is flat. Precise: a defect whose visibility depends on the environment rather than the code alone: compiler and version, flags, installed libraries, current directory, locale, environment variables, file layout; the cure is to make every relevant difference part of the CI matrix or to remove the dependence (R4, R5, R7; F2-26's forensic lab is a third case). R4 R7
Unspecified order of evaluation
Simple words: C++ does not say which argument of a function call is computed first. Analogy: two carpenters told to "fetch a plank each"; the order they come back is not part of the instruction. Precise: the evaluations of the arguments of one function call are indeterminately sequenced with respect to each other, so a program whose result depends on that order may differ between conforming compilers; R4 shows g++ 13.3 and clang 18.1 choosing differently without a warning. D3 R4
Undocumented assumption
Simple words: something the author knew about how the code must be used but never wrote down or checked. Analogy: "lift the door when it rains", known only to Lan. Precise: a condition on inputs, environment or output format that the code relies on and that is neither stated in the interface documentation nor enforced by a check; users discover it by failure. R1 shows four in a 22-line program (prefix parsing, hexadecimal, NaN position, six-digit output). R1
Semantic versioning
Simple words: a three-part version number whose parts tell users whether an update can break them. Analogy: the house's handover letter says "repairs only", "a new room added", or "the doors moved". Precise: MAJOR.MINOR.PATCH, where MAJOR increases for changes incompatible with the documented public interface, MINOR for backward-compatible additions and PATCH for backward-compatible fixes; versions 0.y.z are initial development with no stability promise. Defined in the Semantic Versioning specification (D6, not yet in the source registry). D6
Breaking change
Simple words: a change after which some existing user's code or script stops working or gives different results. Analogy: moving a door the family already walks through in the dark. Precise: a change to observable behaviour that a caller may depend on: function signatures, return types, accepted inputs, output format, exit statuses, error texts that scripts match; R13 shows a "simpler" return type that stops version 0.1's tests from compiling. R13 D6
Source compatibility
Simple words: old code that used your library still compiles and still means the same with the new version. Analogy: the family's furniture still fits through the new doors. Precise: the property that every program that compiled against the old public headers compiles against the new ones with the same meaning; it differs from binary (ABI) compatibility, where already-compiled programs keep working without recompiling (ABI, SP301). Proved here by compiling version 0.1's unchanged tests against 1.0.0 (R12). R12
Changelog (release notes)
Simple words: the list, kept with the code, of what changed in each version and what it means for users. Analogy: the handover letter. Precise: a file with one entry per released version, newest first, stating the version, the date, the compatibility impact, and what was changed, fixed and added; here CHANGELOG.md, whose newest version number a script compares with the build's (R9, R15). R15
Known-issues list
Simple words: a public list of problems the authors already know about, with workarounds. Analogy: the snag list handed over with the keys. Precise: a maintained document with one identified entry per known defect or limitation (here KI-1 … KI-4), each with its effect, who is affected, status and workaround, and where possible a test that pins today's behaviour so that a fix shows up as a changed test result. R9
Software licence
Simple words: the conditions under which you may use, change and pass on someone else's code. Analogy: the conditions written on drawings you borrowed from another builder. Precise: the legal terms granted by the copyright holder; open-source licences differ in what they require when you copy or distribute the code (for example keeping notices, or releasing your changes under the same licence). This chapter teaches the engineering habit (record origin and licence, let the owner decide), not the law; the curriculum notes that copying GPL-licensed code "brings the GPL's obligations into your project". SPDX licence identifier
Simple words: a short standard name for a licence, written in a comment at the top of a file. Analogy: the stamp on each borrowed drawing saying whose it is and on what terms. Precise: a line SPDX-License-Identifier: <id> using an identifier from the SPDX License List (or a LicenseRef- identifier for licences not on it), which tools can read; defined by the SPDX specification (D7, not yet in the source registry). R14 shows a checker reading these lines. D7 R14
Third-party record (code provenance)
Simple words: a list saying where every copied file came from and under which licence. Analogy: Lan's note "hinges from Kofi, his permission asked on this date". Precise: in this lab, THIRD_PARTY.txt: one line per copied file with its path, origin (project, version, path), SPDX licence and SHA-256 of the copy, so that both an unknown origin and a silent local change are detectable (R14). Curriculum rule 19 asks for exactly this habit: "copying code requires checking the licence with the learner and recording the origin". C1 R14
Dependency inventory
Simple words: the list of everything your shipped program needs that you did not write. Analogy: which batch of hinges went into which house, so a recall reaches the right doors. Precise: the libraries linked at build time or loaded at run time (R17: libstdc++.so.6, libgcc_s.so.1, libc.so.6, libm.so.6 and the dynamic loader), the toolchain that built it, and their versions; it is the input to deciding which security updates concern you. R17
Security update
Simple words: a new version released to close a weakness someone could abuse. Analogy: a hinge recall: the old hinge can be forced open. Precise: a release (of your code or of something in your dependency inventory) that fixes a vulnerability; for production code it implies three duties: knowing your dependencies, being able to release quickly (CI green, version and notes ready), and telling users what to update and why. D1 R17
Error-rate alert
Simple words: an automatic message to a person when too many runs fail. Analogy: the damp meter in the basement that beeps before the floor rots. Precise: a monitoring rule that counts outcomes of a program in use (here by exit status and stable error code), computes the fraction of failures over a window and notifies someone when it exceeds a threshold, or when any failure cannot be classified; R18 and R19 run one over a day of invocations. Related: SLO, burn-rate alert (DS402). D2 R19
Exposure (cost of being wrong)
Simple words: how many wrong results a bug produces before everyone has the fix. Analogy: how many nights the family sleeps under the leaking roof before it is mended. Precise: in this chapter, the product users × runs per user per day × days from release until the last user has updated × fraction of runs whose input triggers the bug; detection time and update time are the factors production engineering can shrink (R20). It complements the blast radius (how many are affected) with a time dimension. R20

Layer 1 — the kid explanation

When you write a program for yourself, you are its only user. You know which inputs it likes, which compiler you used, and that it falls over if you type a word instead of a number. You never type a word, so it never falls over.

When other people use your program, all of that changes. They type words. They use another computer. They write scripts that read your program's output every night, and their scripts break if you change one space. They copy your program into their own projects, so they need to know which licence it has. When it goes wrong at night, someone has to answer.

So production code is not cleverer code. It is the same code with promises written down and checked: what it accepts, what it prints, what each failure looks like, which version this is, what changed, what is still broken, where every borrowed piece came from, and who to call. In the lab you take your own SP202 project and add exactly those promises, one file at a time.

Each item below is something the hobby project did not need because its only user was its author. For each, the lab has a concrete artefact.

Reviews. A second person reads every change before it is merged. Review finds defects, but it also spreads knowledge so the project survives its author (the registered analogy's "where it breaks": reviews also share knowledge). Monitoring. You cannot ask every user whether it worked. Licences. Other people will copy your code, and you will copy theirs. Each copied file must have a known origin and a licence the project owner has accepted, and your own files must say under which terms others may use them. The cost of being wrong. A wrong median in your hobby project costs you a minute. The same bug in a library forty teams call fifty times a day keeps producing wrong results until someone notices, a fix is released, and the last user has updated. R20 turns the story numbers into arithmetic: 0.03 expected wrong results for the hobby case, 456 for production with nobody watching, 102 with an error-rate alert and 30 with an alert and fast updates. R20 The same bug, the same code; what changed is who depends on it and how quickly you find out. That is why production work spends effort on tests, monitoring and release speed that look excessive from inside the shed.

Layer 3 — the engineer's depth

What exactly is the interface?

For a library, the interface starts with the declarations in public headers: names, parameter and return types, and the documented meaning of each function, including what happens on bad input. For a command-line tool it is everything a script can observe: accepted arguments, the bytes on standard output, the exit status, the error codes on standard error and anything written to files. Users depend on observable behaviour whether or not you documented it; 0.1's silent acceptance of 3abc was part of its de facto interface (R1, R18). D1 R1 The engineering response is to write the interface down (README "Interface", the header comments), make it machine-checkable (exit-status tests, golden output), and treat any change to it as a version decision. 1.0.0 keeps the output line identical to 0.1 because downstream scripts parse it, and records the six-digit precision as a known issue rather than "fixing" it in a minor release (KI-2).

Version decisions, change by change

Semantic versioning puts a rule on each change, not on the release as a whole: the release takes the largest bump any of its changes needs. D6 Compatible fixes are PATCH (a crash becomes an error with the documented exit status only if the documented interface already promised that status); compatible additions are MINOR (a new option, a new function); anything that can break an existing, documented use is MAJOR (R13). Two subtleties matter in practice. First, a fix can be breaking: once 1.0.0 is out, starting to reject an input that 1.0.0 accepted breaks someone even if the input was nonsense — which is why 1.0.0 made all its strictness changes before the stability promise. Second, source compatibility and binary compatibility differ: adding a member to a struct in a public header can keep every caller compiling while changing the layout that already-compiled callers assume (F2-47, ABIs). This lab's library is built from source by its users, so it promises source compatibility only and says so.

Testing failure paths systematically

The inputs of stats_cli fall into classes, and each class needs at least one test with an exact expected outcome: no arguments (exit 2, E-USAGE); a word (abc); a number with trailing characters (3abc, 249ms, 4,4, 0x10); non-finite text (nan, inf); out of range (1e999); valid inputs whose result overflows (1e308 1e308, exit 4); and the happy path. Listing 3 (parse.cpp) maps std::from_chars's error codes onto these classes. D3 Three details are worth copying into your own projects. (1) A command-line test must check the exit status and the output together, which CTest's regular-expression property alone does not (R3, H1); a ten-line wrapper does (Listing 5). (2) Known issues get tests that pin today's behaviour (known_issue_ki1_…), so fixing one changes a test result and forces the documentation to follow. Designing the CI matrix

A CI matrix is a list of environment differences you choose to make visible. This lab's three columns each catch something the others cannot: sanitizers in Debug catch memory and undefined-behaviour errors on the paths the tests run (F2-29); Release with optimisation catches code that is only correct by accident at -O0; a second compiler catches unspecified behaviour, as in R4, and different warnings. D4 R4 What the matrix does not contain must be written down as well: one operating system, one CPU architecture, no clang sanitizers (R5), and only the compiler versions listed in the changelog (KI-3). CI should also be hermetic in the sense of SE302: it starts from a clean copy and its result does not depend on what was left in a previous build folder. ci.sh configures fresh build folders and the lab runs it on a fresh copy (R9). Operating it: monitoring, on-call and updates

Monitoring a library is indirect: you instrument the programs that use it, or, as here, the command-line tool reports outcomes in a form that the caller's logs can count. Good monitoring signals are those that a person must act on; an alert that fires daily for a known, accepted cause trains people to ignore it. D2 R19's alert is actionable: five of six errors are malformed input from one downstream script, which leads to a conversation with that team (the Forensic lab). The monitor alerts separately on any failure without a known code, because an unclassified failure is the signature of a crash (R18's exit status 134). R18 Service-level objectives and burn-rate alerts (DS402) are the scaled-up form of the same idea. How the hardware actually does it

Two machine-level facts sit under this chapter's bugs. First, a double is an IEEE 754 binary64 value with a largest finite magnitude; arithmetic that exceeds it gives infinity, and operations such as infinity minus infinity give NaN; every ordered comparison involving a NaN is false. D9 That is why 1e308 + 1e308 became inf in R1 and why a NaN broke the sort: the x86-64 SSE compare instructions that implement < follow those rules, and std::sort's algorithm assumes they never apply. std::midpoint avoids the overflow by not forming the sum of two large values. D3 Second, the shipped program is not one file. The Linux dynamic loader (/lib64/ld-linux-x86-64.so.2 in R17) maps libstdc++.so.6, libgcc_s.so.1, libm.so.6 and libc.so.6 into the process at every start, so a security update to those packages changes the behaviour of your unchanged binary the next time it runs — usually what you want, and the reason the dependency inventory lists run-time libraries, not only build-time tools. R17 A statically linked program would carry its copy inside and need a rebuild instead (F2-44 covers dynamic linking in ELF). Order of argument evaluation, by contrast, is not a hardware property at all: both builds in R4 ran on the same CPU; the compilers emitted the calls in different orders.

Worked example

Question. After 1.0.0, five changes are proposed. Decide the version bump for each, then the version of a release containing all five; then estimate, with R20's arithmetic, what a silent bug in such a release would cost with and without monitoring.

  1. Fix KI-1 so that 1e308 1e308 prints mean 1e+308 instead of exit 4. Callers that relied on exit 4 for this input? The README documents exit 4 as "a result does not fit in a double", and the result does fit; KI-1 already calls the current behaviour a defect. PATCH. Update the pinning test and KI-1 in the same commit.
  2. Add --json output. New option, default output unchanged, golden test still green: MINOR.
  3. Accept 249ms by ignoring a unit suffix. A new accepted input class; old callers unaffected (they received exit 3): MINOR, but write the grammar change in the README first — it is a promise you can never take back without a MAJOR.
  4. Print full precision by default (1234567.5 instead of 1.23457e+06). Every script that parses the line may break: MAJOR (this is KI-2's "by design until 2.0.0").
  5. Change median to return double. R13: old callers do not compile: MAJOR.
  6. The release. The largest bump wins: 2.0.0. If changes 4 and 5 are held back, the other three ship as 1.1.0 (MINOR wins over PATCH).
  7. Cost of being wrong. Suppose change 3 has a bug that silently misreads 30 in 10,000 inputs, and 40 users each run the tool 50 times a day: 2,000 runs a day, 0.003 of them wrong, so 6 wrong results per day exposed. With nobody watching, notice after 60 days, fix in 2, last user updated after 14 more: 76 days × 6 = 456. With an error-rate alert the next day: (1 + 2 + 14) × 6 = 102. With an alert and an update in 2 days: (1 + 2 + 2) × 6 = 30. For the hobby case (one user, five runs a day, noticed and fixed in two days): 5 × 2 × 0.003 = 0.03.

Listing 10 (exposure.cpp) computes the same four numbers; its output (R20) agrees: 0.03, 456.00, 102.00, 30.00. R20 The lesson in the numbers: the time to notice dominated the exposure (60 of 76 days), so the cheapest reduction came from monitoring, not from faster coding. And a silent misreading is exactly what an error-rate alert cannot see unless the program rejects what it does not understand — the strictness of 1.0.0 is what makes step 7's middle row possible.

Where the analogy breaks


    

  • A house is handed over once; software is handed over every release. The family gets one set of keys. Users of a library receive a new version every few weeks and must decide whether to take it; versioning and changelogs exist because the handover repeats (R15, Listing 8).
    • 

  • A family can see a crack; a script cannot. Ines notices a sticking door. A script that receives count 2 mean 4.1 for 4,4 4.2 notices nothing (R1, R18): software users often cannot see that a result is wrong, which is why the program must refuse what it does not understand.
    • 

  • Hinges are not copied; code is. Taking a hinge from Kofi's box removes it from his garage, and the house has one hinge. Copying code leaves the original in place and can multiply it into thousands of programs, and the licence's conditions travel with every copy — the opposite of the shed's intuition that something given is yours to use as you like.
    • 

  • Builders' tools rarely change what a wall means; compilers can. Two carpenters with different saws build the same wall. Two conforming compilers built two different programs from one source in R4.

Observation. Evidence 2 (R19): call 8 12.1 11.8 n/a, argument 3, exit 3 E-PARSE … is not a number; call 16 … 249ms, argument 4, exit 3, trailing characters; call 23 0.91 nan 0.92, argument 2, exit 3, not finite; call 30 4.2 4,4, argument 2, exit 3, trailing characters; call 34 1e308 1e308, exit 4 E-RANGE (KI-1); call 39 … 18ms, argument 5, exit 3. (Line numbers are lines of fleet_inputs.txt.) Under 0.1.0 (R18, R1): n/a crashed with std::invalid_argument, exit 134 — the one row that was already empty before Monday; the other five returned exit 0 with numbers: 249ms → 249, 18ms → 18 (prefix parsing, R1's 3abc case), 4,4 → 4 (R1), nan → mean nan and a position-dependent median (R1), 1e308 1e308 → inf (R1).


Hypotheses. (1) Parsing bug in 1.0.0: ruled out — every rejection matches the documented grammar (README, Listing 3) and a test (cli.trailing, cli.nan, cli.overflow); the 34 valid calls give the same output as 0.1.0 (golden test, R8, R9). (2) Bad input that 0.1.0 hid: supported by R1 and R18 — the same inputs produced numbers with exit 0. (3) Locale or environment: ruled out — from_chars is locale-independent (D3) and every rejected argument contains characters that are not part of any decimal number (/, ms, ,) or is NaN/overflow; nothing failed that is a valid number.


Root cause. 1.0.0 is behaving as released and documented (CHANGELOG "Compatibility" and "Changed", KI-4). The benchmark script sends values with units (ms), a decimal comma, a n/a placeholder and a NaN. Before the update, 5 of the 40 summary rows contained wrong or meaningless numbers with no error (and one row was empty after a crash); nobody noticed because a monitor counts failures and 0.1.0 reported none (R18: error rate 2.5 %, one alert for the crash only).


Fix and verification. Benchmark script: strip units before calling, use . as decimal point, skip n/a and nan rows explicitly, handle exit 3 and 4 per row instead of leaving it empty. Verify by replaying the same 40 calls: the monitor should report 0 errors (or only explicitly skipped rows). Stats project: no revert — reverting would restore silent wrong answers. Optionally, if many users send units, consider accepting a unit suffix in a MINOR release (Worked example, change 3) after writing the grammar. KI-1 (the 1e308 row) is a real stats defect, already listed with a workaround.


Prevention and communication. Before Monday: Sipho's team could have read the 1.0.0 changelog's "Compatibility" section (it names exactly these inputs) and replayed a day of their own calls through 1.0.0 in their CI before deploying; the stats project could have announced the strictness one release earlier (a 0.2.0 that printed a warning line for leniently parsed input) so that monitors saw it coming. Reply: "1.0.0 rejects these six inputs on purpose (CHANGELOG 1.0.0, KI-4); five of them were silently producing wrong numbers in 0.1.0, as the attached replay shows. Please fix the inputs listed above; the 1e308 case is our known issue KI-1, workaround attached. We are not reverting, but we are happy to review a patch to your script today."
