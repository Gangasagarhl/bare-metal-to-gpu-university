Story hook

The school porter keeps two records of who came in. One is an ordinary visitors' book: name, time, which room. Anyone with a pen could change it. The other is a sealed tally: each time someone arrives, the porter takes the tally's current number, mixes in the visitor's name by a fixed recipe, and writes down only the new number. Nobody can take a step back; the recipe has no undo.

At the end of the day an inspector arrives. She does not trust the visitors' book. She takes it, starts from zero, applies the recipe to each name in order, and compares her final number with the sealed tally. If they agree, the book is an honest account of who came in. If one name was changed, added or removed, the numbers disagree, and she knows the book lies, though not where.

That is measured boot with a TPM. The firmware and the kernel record what they run in the TPM's sealed tallies (PCRs) and in an ordinary event log; a verifier replays the log and compares. In this chapter you write the driver, read the firmware's log, add your own measurement, and build the inspector.

What you will be able to do

  • Locate a TPM and its firmware event log from the ACPI TPM2 table.
  • Send TPM 2.0 commands through the TIS (FIFO) interface and decode the response codes.
  • Marshal PCR_Read, PCR_Extend and GetRandom by hand, big-endian, field by field.
  • Parse a crypto-agile event log and replay it into software PCRs.
  • Measure data into a PCR and log it so that a verifier can check it.
  • Explain the difference between measured boot and verified boot, and what an attestation does and does not prove.
Jargon box
TPM (Trusted Platform Module)
Simple words: a small security chip that keeps records nobody can roll back and keys nobody can copy out. Analogy: the porter with the sealed tally. Precise: a device implementing the TCG TPM 2.0 Library Specification: PCR banks, hierarchies of keys, a random number generator, sealed storage and signing (quotes), reached through a command/response interface. D1
PCR (Platform Configuration Register)
Simple words: a register you can only add to, never set. Analogy: the sealed tally. Precise: a hash-sized register, one per bank (SHA-256 here), reset to zero at power-on (PCRs 0–15 on PC clients) and changed only by extend: new = H(old ‖ digest). D1
Extend
Simple words: the one way a PCR changes. Analogy: mixing the next name into the tally. Precise: TPM2_PCR_Extend replaces a PCR with the hash of its old value concatenated with a new digest; the order of extends matters and no command undoes one. D1
Event log
Simple words: the list of what was measured, kept in ordinary memory. Analogy: the visitors' book. Precise: a table in memory (its address in the ACPI TPM2 table or from UEFI) with one entry per extend: PCR index, event type, the digest per bank and event data; the TCG PC Client Platform Firmware Profile defines the format. D3
Measured boot
Simple words: each boot stage records what it is about to run. Analogy: every visitor signs in; nobody is turned away. Precise: before passing control to the next stage, each stage hashes it, extends a PCR and logs an event; nothing is checked at boot time. D3
Attestation and quote
Simple words: proving to someone else what your machine booted. Analogy: the inspector's check, with the porter's signature on the tally. Precise: the verifier receives the event log and a quote (PCR values signed by a TPM attestation key it trusts), replays the log and compares. D1
TIS / FIFO interface
Simple words: the register window through which commands go in and responses come out, byte by byte. Analogy: the porter's hatch. Precise: the TPM Interface Specification register set (one 4 KiB page per locality at 0xFED40000 + 0x1000 × locality: ACCESS, STS, DATA_FIFO, DID_VID …), defined in the PC Client Platform TPM Profile; CRB is the alternative, buffer-based interface. D2

Layer 1 — the kid explanation

Analogy

The porter's tally can only go forward. The visitors' book can say anything. The inspector trusts the book only when replaying it gives the porter's number. The porter turns no one away: if a stranger came in, the tally says so, but only the inspector, later, decides whether that is a problem.

A computer starts in stages: first the firmware, then a boot loader, then the operating system. With a TPM, each stage writes down a fingerprint of the next stage before running it. The fingerprints go into a list anyone can read, and also into the TPM's registers, which can only add new fingerprints on top of old ones. Later, another computer can read both, redo the sums from the list, and see whether they agree. If someone changed a program or the list, the sums do not match.

Layer 2 — the student explanation

Finding the TPM

The ACPI TPM2 table says which interface the TPM uses (its start method) and, in newer revisions, where the firmware put its event log. QEMU with -device tpm-tis gives a 76-byte table, revision 4, start method 6 (TIS), and a 65536-byte log area at 0x3ff0000 (R4). D7 R4 The TIS registers are at 0xFED40000; locality 0 is the first 4 KiB page. DID_VID read 0x00011014 (vendor 0x1014, the ID QEMU's model reports), and STS bits 27–26 = 1 said "TPM 2.0" (R4). On a machine without a TPM there is no TPM2 table and DID_VID reads 0 (R8). D2 R8

Sending a command

Every TPM 2.0 command is a byte string: a 10-byte header (tag, total size, command code), handles, an authorization area if the tag says "with sessions", then parameters. Every response starts with a tag, its size and a response code; 0 means success. All fields are big-endian. D1 Through TIS, the driver requests locality 0, sets commandReady, writes the bytes into DATA_FIFO no faster than STS.burstCount allows, checks that the TPM expects no more bytes, writes tpmGo, waits for dataAvail, reads the header to learn the size, reads the rest and sets commandReady again (Figure 2). D2

The firmware's log

SeaBIOS (QEMU's default firmware) measures as it boots: option ROMs, its own actions ("Start Option ROM Scan", "Calling INT 19h") and a separator in each of PCRs 0–7 that marks the end of the firmware's part. It writes a crypto-agile log: a first entry in the old TPM 1.2 format whose data is "Spec ID Event03" and the list of digest algorithms (here one, SHA-256, 32 bytes), then entries with one digest per algorithm. The kernel parsed 13 events (R4). D3 R4

Replay and compare

The kernel starts 24 software PCRs at zero, extends each with the digests of its events in log order, then reads PCRs 0–7 from the TPM with PCR_Read. All eight matched (R4). It then measures its own "command line": hashes the 47 bytes, extends PCR 8 and adds an event to its report. R4

The verifier

verify.cc runs on the host. It reads the report (every event plus the PCR values), checks that events whose data is the measured content (EV_ACTION, EV_IPL) have digest = SHA-256(data), replays all digests and compares. R5: 14 events, 9 PCRs, ACCEPT. R5 In real attestation the PCR values would arrive in a quote signed by the TPM; the mock has no keys, so here they are the kernel's own PCR_Read results. A lying kernel could print anything; a quote is what stops that.

GetRandom

GetRandom(16) returned TPM_RC_SUCCESS and 16 bytes (R4). With the mock those bytes come from the host's os.urandom; they say nothing about a real TPM's generator. R4

Layer 3 — the engineer's depth

What the evidence in this lab proves

The TPM in this lab is mock_tpm.py, written by the same author from the same memory as the driver. Where both sides come from one person's memory, agreement proves little. The lab's evidence splits three ways. D5

  • Independent. The TIS register protocol is QEMU's real tpm-tis model. The event log is written by SeaBIOS, a real implementation; the kernel's parser read all 13 events and the replay matched the PCRs that SeaBIOS's own PCR_Extend commands produced. SHA-256 is checked against the FIPS examples and against Python's hashlib on 2000 messages of every length from 0 to 300 bytes (R1, R2). R1 R2
  • Partly independent. The kernel's PCR_Extend has the layout the mock parses, and the mock parses SeaBIOS's PCR_Extend commands correctly (the PCRs match SeaBIOS's log). So the kernel's command matches SeaBIOS's at least as far as the mock reads it.
  • Circular. PCR_Read and GetRandom response layouts, response codes, and the mock's behaviour before Startup. These pass because the same memory wrote both sides.

The milestone's acceptance test names swtpm, a full software TPM. Rerunning with swtpm, or with a real TPM, is the step that turns the circular items into evidence.

Sessions and authorization

PCR_Extend needs authorization for the PCR. The lab uses the password session (handle 0x40000009) with an empty password: nonce size 0, attributes 0, HMAC size 0, 9 bytes in all, after a 4-byte authorization size (Figure 2). D1 Real TPMs check this; the mock does not. Commands with sessions return a response with a parameter size and a session area, which is why the response tag is 0x8002.

Localities and who may reset what

The TIS interface has five localities (0–4), each a page of the register space. Software normally uses locality 0; higher localities belong to the CPU's dynamic launch (DRTM) and can reset PCRs 17–22, which plain firmware and OS code cannot. D2

Event log details

Event 0 uses the TPM 1.2 layout (PCR, type, a 20-byte SHA-1 field, size, data) so that old parsers can skip it. In the crypto-agile entries that follow, each digest is a 2-byte algorithm ID followed by a digest of that algorithm's size, taken from the Spec ID event; a parser that does not know an algorithm's size cannot continue. EV_NO_ACTION entries are never extended. For EV_ACTION and EV_IPL the data is what was hashed; for many other types (EV_EVENT_TAG, EV_SEPARATOR on some firmware) the data only describes it, and the verifier must trust the digest or know the measured object. D3 R5 shows both kinds. R5

Measured boot versus verified boot

Verified boot (UEFI Secure Boot, for example) checks a signature before running each stage and refuses what fails. Measured boot refuses nothing: it records. The two complement each other: verified boot keeps unsigned code out; measured boot lets a remote party see which signed code ran, and lets the TPM release a sealed secret (a disk key) only when the PCRs have expected values. D3 The lab kernel measures its command line before using it; Linux's IMA and systemd's PCR use extend the same idea to files and boot phases.

Not verified — check before relying on this

The TIS register offsets and bits (tpm.h), the command and response layouts, command codes and response codes, the TPM2 table field offsets, the event log structures and the PCR conventions in this chapter are from the author's memory of D1–D3 and D7, which were not opened in this build. The swtpm control protocol in mock_tpm.py is from memory of swtpm's sources; QEMU 8.2.2 accepted it. The first command the mock saw (code 0x181, before Startup) is probably QEMU's own TPM version probe; this was not checked. Vendor 0x1014 for QEMU's model is from memory. Layer 3 lists which results are circular.

How the hardware actually does it

A discrete TPM is a microcontroller with its own flash, random number generator and hash engine, on the LPC or SPI bus; the chipset decodes 0xFED40000–0xFED44FFF to it and turns MMIO reads and writes into bus cycles, one byte at a time on LPC. Firmware TPMs (Intel PTT, AMD fTPM) run in a security processor inside the chipset or CPU and usually use the CRB interface: a control area and command and response buffers in memory, with a "start" bit instead of a byte FIFO. D2

The PCRs live inside the TPM and are reset only by a platform reset (or, for the DRTM PCRs, by a special locality-4 sequence the CPU performs). That is what makes them trustworthy: software running later cannot return a PCR to an earlier value. The first measurement must come from code that cannot itself have been changed unnoticed, the core root of trust for measurement, often the first block of firmware in boot ROM or a CPU-verified boot block. D3

In the lab, QEMU's tpm-tis model implements the register interface and passes each complete command over a socket to the backend ("emulator" = swtpm's protocol), here played by the mock. D5 TPM commands are slow on real hardware: tens of milliseconds for an extend on some discrete TPMs, seconds for key generation. The lab's 750 ms and 2 s timeouts were chosen without measurements on real devices.

Worked example

Task. Compute PCR 4 from the log by hand, using R4's events: EV_ACTION "Calling INT 19h" (15 bytes) on PCR 4, then the separator on PCR 4.

Step 1. PCR 4 starts as 32 zero bytes.

Step 2. The first event's digest is SHA-256("Calling INT 19h") = 7a19a5a5…df12b; the verifier recomputes this from the data (R5: "digest == SHA-256(data)"). Extend: SHA-256(0³² ‖ 7a19a5a5…) = fa6833d9…5c1e. The mock's log shows the same value after SeaBIOS's extend (R4).

Step 3. The separator's data is ff ff ff ff; its digest SHA-256(ffffffff) = ad95131b…bfd0e. Extend: SHA-256(fa6833d9… ‖ ad95131b…) = 1eb9aa21337cc1fa…57ca.

Step 4. Compare: R4 "pcr 4: TPM 1eb9aa21337cc1fa… = replay". R4

Check. PCR 0, 3, 5, 6 and 7 hold only the separator: SHA-256(0³² ‖ ad95131b…) = e21b703e…ea93, and R4 shows that value five times. The hashes in steps 2 and 3 were computed with Python's hashlib while writing this chapter; R1 checks one extend of the same kind ("extend(0^32, sha256(abc))").

Where the analogy breaks


    

  • The porter is not a judge. A TPM never refuses to boot anything; even the "sealed secret" use only withholds a key.
    • 

  • The tally is many tallies. There are 24 PCRs per bank and several banks (SHA-1, SHA-256, …), each extended separately.
    • 

  • The inspector needs a signature. A tally read out by the very machine under suspicion proves nothing; the quote, signed by a key that never leaves the TPM, is what she trusts.
    • 

  • The book can be incomplete honestly. Many event types record a description rather than the measured bytes; the inspector must know what the digests should be.
    • 




Common mistakes and debugging


    

  • Symptom: every command returns TPM_RC_INITIALIZE (0x100). Cause: no TPM2_Startup since reset. Find it: the response code. Fix: firmware sends Startup on PCs; a kernel on a platform without it must send Startup(CLEAR) itself.
    • 

  • Symptom: the driver hangs after writing the command. Cause: a wrong size field, so the TPM still expects bytes (or stopped expecting them early). Find it: STS.Expect after the last byte. Fix: compute the size last, as Out::finish does.
    • 

  • Symptom: the replay matches no PCR. Cause: digests of the wrong algorithm, EV_NO_ACTION extended, or the log read big-endian. Find it: recompute one PCR by hand (the worked example). Fix: use the Spec ID event's sizes; skip EV_NO_ACTION; read the log little-endian.
    • 

  • Symptom: the replay matches every PCR except the one your code extends. Cause: what you logged is not what you extended. Fix: the forensic lab.
    • 

  • Symptom: PCR_Read returns a value but the wrong PCR. Cause: the selection bitmap built in the wrong byte or bit order. Find it: print the command (the lab's tpm::trace). Fix: PCR n is bit n mod 8 of byte n / 8.
    •

Safety
On a real machine, do not send TPM2_Clear, hierarchy or NV commands while experimenting: they can destroy keys that protect a disk (BitLocker, LUKS with TPM unlock) or lock the TPM after repeated authorization failures. PCR_Read, GetRandom and extends of PCR 8–15 are harmless to other systems, but extending a PCR that sealed a disk key will stop that key from unsealing until the next reboot. Make sure you have your recovery keys before touching a real TPM.

Summary


    

  • A PCR changes only by extend: new = SHA-256(old ‖ digest), with no undo (R1).
    • 

  • The firmware measures into PCRs 0–7 and writes an event log; the log's location comes from the ACPI TPM2 table (R4).
    • 

  • TPM commands are big-endian byte strings; TIS moves them through a FIFO with a five-state handshake.
    • 

  • Replaying the log must reproduce the PCRs; the kernel's replay matched SeaBIOS's PCRs 0–7 (R4).
    • 

  • Measured boot records; verification happens later, by replay plus a signed quote (R5).
    • 

  • Log and extend must describe the same bytes, or every attestation fails (R6, R7). The lab's TPM is a mock: part of its evidence is circular.

Answers to Check yourself


    

  1. The TPM offers no command that writes a PCR, only extend, and SHA-256 cannot be inverted: no input gives back an earlier value except by finding a preimage. Only a platform reset (or a DRTM locality reset for PCRs 17–22) clears them.
    2. 

  2. From the ACPI TPM2 table's log area fields (LAML and LASA), 65536 bytes at 0x3ff0000 (R4). Under UEFI the firmware hands the log over through the EFI TCG2 protocol (and Linux exposes it), and the TPM2 table may not hold the address.
    3. 

  3. 6 is the TIS (FIFO) interface; 7 is CRB (command response buffer). These values are from memory of D7.
    4. 

  4. EV_NO_ACTION events are informational (like the Spec ID header); the firmware never extended them into a PCR, so replaying them would produce a value the TPM never had.
    5. 

  5. Header 10 bytes + count 4 + algorithm 2 + size-of-select 1 + bitmap 3 = 20 bytes (0x14), as in R4's traced command "80 01 00 00 00 14 …".
    6. 

  6. (b). The edited digest changes only the replay of that event's PCR; the others still match.
    7. 

  7. Every circular item of Layer 3 would become evidence: PCR_Read's response layout, GetRandom, response codes and Startup behaviour would then be checked against an implementation of D1 written by someone else. The TIS and event-log results would not change meaning; they are independent already.
    8. 

  8. Verified boot checks signatures and refuses to run what fails; measured boot records and refuses nothing. Verified boot can stop unsigned code before it runs; measured boot can show a remote party exactly which (even signed) code ran and can bind secrets to that state.

Forensic answer key


Observation. R7: PCRs 0–7 match, PCR 8 "replay 553bbb9db1bafdb5 … != TPM 072bdea3beaf0687 …", REJECT. R6: the report's PCR 8 event has digest 946ac9d1… with the 47 bytes of the command line as data; the mock's log shows "PCR_Extend(PCR 8, sha256 578a0344…)". The kernel printed "TPM_RC_SUCCESS" and "F4-13 done".


Root cause. SHA-256 of the 47 bytes is 946ac9d1… (the verifier's data check also says "digest == SHA-256(data)" for event 14). SHA-256 of all 64 bytes of g_cmdline (47 characters and 17 zero bytes) is 578a0344…. f413_main.cc lines 145–146, active with -DF413_SIZEOF_BUG, hash sizeof g_cmdline (the array size, 64) for the TPM while line 144 hashes kstrlen (47) for the log. The log and the TPM describe different bytes.


Why the kernel printed success. TPM_RC_SUCCESS means only that the extend was carried out. The TPM cannot know what the digest was meant to describe, and the kernel never compares its own log with its PCRs.


Injection. Built with -DF413_SIZEOF_BUG.


Fix and verification. Use one digest for both (line 148: extend what was logged); rerun: PCR 8 "553bbb9db1bafdb5 … == TPM", ACCEPT (R4, R5).


Wrong answers. "The attestation server has a bug": it accepts PCRs 0–7 with the same code and rejects only the PCR the new kernel writes. "The TPM is broken": it returned success and its value is exactly SHA-256(0³² ‖ 578a0344…).


Without the mock log. A real verifier sees only the mismatch on PCR 8. The cause can be found by making the kernel replay its own log and compare with PCR_Read before reporting, or by hashing candidate inputs (string length, buffer size, with and without a terminating zero) on the host until one reproduces the TPM's PCR value.


Prevention. Compute the digest once and use the same bytes for the log and the extend; add a self-check that replays the kernel's own events against PCR_Read after measuring.
