Story hook

A school reception desk has eight doors. A visitor walks in, and the receptionist does the same thing every time: points to a chair (a badge number), hands over a form, and reads it. "I am a keyboard. I speak the simple keyboard language. I will send you a short note every time a key changes." Or: "I am a storage box. Give me sealed envelopes with commands; I will answer each with a receipt." Only after reading the form does the receptionist call the right teacher.

The receptionist knows nothing in advance about any visitor. That is the point: the same desk handles a keyboard, a mouse, a memory stick and devices that were not invented when the desk was built. A visitor can also leave at any moment, and the desk must notice and clear the chair.

USB works this way. In this chapter you build the desk (a driver for the xHCI host controller), the badge-and-form procedure (enumeration) and two teachers: a keyboard driver and a storage driver that reads a file from a FAT32 stick.

What you will be able to do

  • Explain USB's host-centred model: devices, configurations, interfaces and endpoints, and the four transfer types.
  • Initialise an xHCI controller's command ring, event ring and device context array, and use doorbells and the cycle bit correctly.
  • Enumerate a device: port reset, Enable Slot, Address Device, descriptor reads, Configure Endpoint and SET_CONFIGURATION.
  • Write a HID boot-protocol keyboard driver and a Bulk-Only Transport driver that sends SCSI READ(10) and WRITE(10).
  • Read and annotate a USB packet capture with Wireshark (tshark), matching each frame to a driver call.
  • Handle hot-plug and removal through port status change events.
Jargon box
Host controller (xHCI)
Simple words: the chip that runs every USB conversation for the computer. Analogy: the reception desk. Precise: a PCI device implementing the eXtensible Host Controller Interface: capability, operational, runtime and doorbell registers plus rings of 16-byte TRBs in memory, covering USB 1.x, 2.0 and 3.x devices. D3
Descriptor
Simple words: a small table a device sends to describe itself. Analogy: the self-description form. Precise: a structure starting with bLength and bDescriptorType; the device descriptor (18 bytes), the configuration descriptor (9 bytes) followed by interface, endpoint and class descriptors, read with GET_DESCRIPTOR. D1 L1
Endpoint
Simple words: one numbered mailbox inside a device, for one direction. Analogy: one of the visitor's in-trays or out-trays. Precise: an address 0–15 with a direction bit (bit 7 = IN, toward the host) and a transfer type: control, bulk, interrupt or isochronous. Endpoint 0 is the bidirectional control endpoint every device has. D1
Enumeration
Simple words: the steps that turn "something is plugged in" into "this is a keyboard on address 2". Analogy: chair, badge, form, teacher. Precise: port reset, address assignment, reading the device and configuration descriptors, selecting a configuration, then binding a class driver to each interface. D1 D3
TRB (transfer request block)
Simple words: one 16-byte work order on a ring. Analogy: one ticket on the desk's spike. Precise: parameter (8 bytes), status (4) and control (4, with the TRB type in bits 15:10 and the cycle bit in bit 0); used for commands, transfers and events. D3
HID boot protocol
Simple words: a fixed, simple keyboard and mouse report format that works without parsing a report descriptor. Analogy: the "short form" every keyboard can fill in. Precise: for a keyboard, an 8-byte report: modifier bits, a reserved byte and up to six key usage codes from the HID Usage Tables; selected with SET_PROTOCOL(0). D4
BOT (Bulk-Only Transport)
Simple words: how a USB stick carries disk commands. Analogy: a sealed command envelope, the goods, then a receipt. Precise: a 31-byte Command Block Wrapper ("USBC") on the bulk OUT endpoint holding a SCSI command, an optional data phase, and a 13-byte Command Status Wrapper ("USBS") on bulk IN with a matching tag and a status. D5

Layer 1 — the kid explanation

Analogy

The reception desk gives each new visitor a chair number, then reads their form. The form says what kind of visitor they are and which trays they have: "one out-tray for key presses, checked every few milliseconds". The desk then calls the matching teacher. Nobody talks directly to a visitor: every message goes through the desk.

When you plug in a USB device, the computer does not know what it is. It asks. The device answers with small tables describing itself. The computer picks a driver from what the tables say: "keyboard", "storage", "mouse". From then on the computer keeps asking: "any keys?", "here is a command, give me block 2050". The device never speaks first; the computer polls it, many times a second.

Layer 2 — the student explanation

Devices, interfaces, endpoints

A USB device has one or more configurations; the one in use has interfaces, and each interface has endpoints. The class of an interface (HID = 3, mass storage = 8, hub = 9) picks the driver. In R2 the keyboard reports one interface of class 3, subclass 1 (boot), protocol 1 (keyboard) with one interrupt IN endpoint 0x81 of 8 bytes; the stick one interface of class 8, subclass 6 (SCSI), protocol 0x50 (Bulk-Only) with bulk endpoints 0x81 IN and 0x02 OUT of 1024 bytes. D1 R2

Four transfer types: control (endpoint 0; setup, optional data, status; for requests like GET_DESCRIPTOR), interrupt (small, polled at a guaranteed interval; keyboards), bulk (large, whenever bandwidth is free; storage) and isochronous (fixed bandwidth, no retry; audio and video, not used here). "Interrupt" is a misleading name: the host still polls; the guarantee is only how often. D1

The xHCI controller

An xHCI controller is a PCI device (class 0C/03/30) with four register areas: capability registers (sizes, offsets), operational registers (run/stop, the device context array pointer, the command ring pointer, one PORTSC register per port), runtime registers (interrupters, each with an event ring) and an array of doorbells. D3 F4-08's xhci_core.cc already resets the controller, builds a command ring and an event ring, and takes MSI-X interrupts. This chapter adds devices. QEMU's controller reports 64 slots, 8 ports and two "Supported Protocol" capabilities: USB 3.00 on ports 1–4 and USB 2.00 on ports 5–8 (R2). The stick appears on port 2 as a super-speed device; the keyboard on port 5 at high speed. R2

Rings and the cycle bit

All work is exchanged through rings of TRBs in memory. The kernel produces commands and transfers; the controller produces events. Neither side has a "count" register for the other to read. Instead each TRB carries a cycle bit: the producer writes it last, and the consumer accepts an entry only when its cycle bit equals the value the consumer expects. At the end of a ring a Link TRB points back to the start and flips the expected value. A doorbell write tells the controller to look at a ring; for the event ring, the kernel writes its dequeue pointer back to ERDP so the controller knows which entries it may overwrite. D3

Enumeration in six steps

Figure 2 lists them. The key xHCI difference from older controllers: the host software never sends SET_ADDRESS. The Address Device command makes the controller choose an address and send the request itself. In R2 the controller gave the stick address 1 and the keyboard address 2. D3 R2 After addressing, the driver reads the first 8 bytes of the device descriptor (enough to learn endpoint 0's maximum packet size), then all 18, then the 9-byte configuration header (for wTotalLength), then the whole configuration (44 bytes for the stick, 34 for the keyboard). D1 R2

Two class drivers

The keyboard driver sends SET_PROTOCOL(boot) and SET_IDLE(0), then keeps one Normal TRB queued on endpoint 0x81. Each completed TRB is an 8-byte report: byte 0 modifier bits, bytes 2–7 the usage codes of the keys held down. A key press appears as a new code; release as its absence. D4 The storage driver wraps SCSI commands in BOT: INQUIRY, TEST UNIT READY, READ CAPACITY(10), then READ(10) for the FAT32 boot sector, the root directory and the file. R2: last LBA 131071 with 512-byte blocks (64 MiB), the volume label DR302STICK, and the file text the host put there. D5 R2

Layer 3 — the engineer's depth

Contexts: the controller's view of a device

For each slot, the device context base address array (DCBAA) holds a pointer to a device context that the controller owns: a slot context (route string, speed, root port, number of context entries, USB address, slot state) followed by 31 endpoint contexts, indexed by the device context index DCI = 2 × endpoint number + direction (IN = 1), with DCI 1 for endpoint 0. D3 Software never writes the device context; it hands the controller an input context: an input control context whose "add" flags say which contexts to take, then copies of the slot and endpoint contexts. Address Device takes the slot context and endpoint 0; Configure Endpoint takes the slot context (with a larger "context entries" field) and the new endpoints. R2 shows the result: "slot state 2" (addressed) after Address Device, endpoint 0x81 at DCI 3 and 0x02 at DCI 4. R2

QEMU's controller reports 32-byte contexts (CSZ = 0, R2); controllers with 64-byte contexts double every offset, which is why usbh.cc computes context addresses from info().context_size instead of a constant. D3

Endpoint context fields that bite

The endpoint type is xHCI's own code, not USB's: 4 control, 2 bulk OUT, 6 bulk IN, 3 interrupt OUT, 7 interrupt IN. The interval is in units of 2n × 125 µs: for high- and super-speed endpoints n = bInterval − 1; for full- and low-speed interrupt endpoints bInterval counts 1 ms frames and must be converted. The keyboard (high speed, bInterval 7) becomes interval field 6: 26 × 125 µs = 8 ms. The max packet size of a USB 3 device's endpoint 0 is given in the device descriptor as an exponent (9 → 512). D1 D2 D3 R2

PORTSC: a register that bites back

PORTSC mixes read-only status, read-write control and write-1-to-clear change bits, and writing 1 to "port enabled" (PED) disables the port. A driver that reads PORTSC, sets one bit and writes it back clears every pending change and may disable the port. The lab masks the dangerous bits first (PORTSC_NEUTRAL_CLEAR, Listing 1 line 12). USB 2 ports need a port reset to become enabled; USB 3 ports train the link by themselves and are enabled after connect. D3

Events can arrive out of order

The event ring carries command completions, transfer events and port status changes in the order the controller produces them. A driver waiting for one command completion will see the keyboard's report or a port change first. The lab keeps a small stash: events that are not the one being waited for are kept and handed to the next caller that wants them (wait_transfer, wait_port_change). The hot-plug code shows why: the two "event for port 2/5 (already enumerated), ignored" lines in R2 are port changes from the first scan, still in the stash when hot-plug waiting began. R2

Hubs

The milestone asks for a hub class driver; the lab has none, so only devices on root ports work. A hub is a USB device (class 9) with an interrupt endpoint reporting port changes; each device behind it gets a route string in its slot context (one 4-bit port number per tier), and full- or low-speed devices behind a high-speed hub also need the hub's slot and port for split transactions. D1 D3

SCSI over BOT

SCSI fields are big-endian. READ(10) is opcode 0x28, a 4-byte logical block address in bytes 2–5 and a 2-byte block count in bytes 7–8. A failed command returns CSW status 1; REQUEST SENSE then gives a sense key and an additional sense code (ASC/ASCQ). D5 The opcodes in bot.h were checked against <scsi/scsi.h> (R1). L2 R1

How the hardware actually does it

On the wire, a USB 2.0 bus is a polled, half-duplex bus: the host sends a token (IN, OUT or SETUP) addressed to a device and endpoint, then data, then a handshake (ACK, NAK or STALL). A keyboard with no new key answers every IN token with NAK; the host retries at the endpoint's interval. A STALL means "this request is not supported" or "this endpoint is halted"; the host must clear the halt before using the endpoint again. D1 USB 3 adds a separate full-duplex super-speed link with its own packets and replaces polling with notifications for asynchronous endpoints. D2

The xHCI controller hides all of this: it schedules transactions from the transfer rings, retries NAKs itself and reports only completions (completion code 1 = success and 13 = short packet in xhci_core.h; 6 = stall from memory of D3). D3 In QEMU there is no wire at all; the device models answer the controller model directly. QEMU can still record a capture of each device's traffic in the Linux "usbmon" format (the pcap= property), at the level of USB requests (URBs), not packets. D6 That is why the capture in R4 shows setup requests and completions but no NAKs and no SET_ADDRESS (the controller model performs the address step internally).

Before the kernel starts, the firmware (SeaBIOS in QEMU) has its own USB driver so that a USB keyboard works in the boot menu. Its traffic is visible in the captures: frames 1–14 of R4 enumerate the keyboard with a sequence the lab kernel does not use (no 18-byte request), and the CBWs with tag 0x3e7 in R7 are not the kernel's (its tags count from 1). R7 That attribution is an inference from the request pattern. A real consequence showed up with the IOMMU on: QEMU reported a DMA read fault at IOVA 0x3fdec60, near the top of the guest's 64 MiB, when translation was switched on and before the kernel had reset the controller (R5). The most likely reading: the controller was still running the firmware's rings. Production kernels take USB controllers from the firmware explicitly (the "BIOS hand-off" in the USB legacy support capability) and reset them before enabling DMA remapping. D3 R5

Worked example

Task. (1) Decode the first five keyboard reports of R2. (2) Annotate frames 15–22 of the keyboard capture (R4) and match each to a line of usbh.cc.

Step 1. HID usage codes for letters start at 0x04 = a; digits at 0x1E = 1; 0x28 = Enter, 0x2C = space. D4 Report 00 00 0b 00 …: no modifiers, key 0x0B = 0x04 + 7 = h. Next, all zeros: release. 00 00 08 = e; release; 00 00 0f = l; release; 00 00 0f = l again. The release report between the two l's is what makes the second one a new key press: the driver compares each report with the previous one (Listing 2 lines 46–50). The full sequence 0b 08 0f 0f 12 2c 18 16 05 2c 21 1f 28 reads "hello usb 42" and Enter, which R2 prints as the typed line.

Step 2. In R4's table, 'S' is a submission and 'C' its completion; type 0x02 is control, 0x01 interrupt.

Where the analogy breaks


    

  • Visitors never speak first. A real visitor walks up to the desk; a USB device only answers when the host asks. Even "interrupt" endpoints are polled.
    • 

  • The desk does not walk anywhere. The analogy's receptionist "calls a teacher"; in xHCI the controller does the bus work, but choosing and loading the class driver is the kernel's job, from the descriptors.
    • 

  • Forms can lie or be wrong. Descriptors come from the device; a malicious device can claim to be a keyboard and type commands ("BadUSB" attacks). The desk in the story trusts every form.
    • 

  • One visitor can be several. A composite device (a keyboard with a built-in touchpad) has several interfaces, each with its own driver; the analogy's "one form, one teacher" hides that.
    • 




Common mistakes and debugging


    

  • Symptom: the controller never processes a ring. Cause: the ring's cycle state (DCS in the endpoint context, RCS in CRCR) does not match the cycle bit in the TRBs, or the doorbell target is wrong (endpoint 0 is target 1, not 0). Find it: dump the TRB and the endpoint context. Fix: initialise both with cycle 1; doorbell target = DCI.
    • 

  • Symptom: a port works once, then never reports changes again. Cause: PORTSC written back with its change bits set (clearing them) or PED set (disabling the port). Find it: print PORTSC before and after each write. Fix: Listing 1 line 24.
    • 

  • Symptom: Configure Endpoint fails with "parameter error". Cause: Context Entries in the slot context smaller than the highest DCI added, or the add flags miss the slot context. Find it: compare the add flags with the DCIs printed. Fix: lines 243–247.
    • 

  • Symptom: the keyboard types each letter twice, or misses repeated letters. Cause: treating every report as key presses, or comparing only with the last non-empty report. Find it: print raw reports as the lab does. Fix: compare with the previous report, including empty ones.
    • 

  • Symptom: the stick answers INQUIRY but every READ(10) fails. Cause: wrong byte order of LBA or count, or a data length in the CBW that differs from blocks × 512. Find it: REQUEST SENSE (ASC 0x21 = LBA out of range, 0x24 = invalid field), and the capture's decoded LBA. Fix: big-endian fields. The forensic lab is this bug.
    • 

  • Symptom: a bulk transfer stalls and every later command times out. Cause: the endpoint halted (STALL) and was not reset. Find it: completion code 6. Fix: Reset Endpoint command, Set TR Dequeue Pointer, CLEAR_FEATURE(ENDPOINT_HALT); for BOT, the reset recovery sequence (not implemented in the lab).
    • 




Transition box

Where you came from: F4-08 gave you MSI-X, the IOMMU and an xHCI core that runs NOOP commands; DR301's NVMe driver (F4-07) taught submission and completion queues with doorbells. What carries over: rings in memory with a producer and a consumer, doorbells, completion entries matched to requests, every address from the mapping API, and OS303's block devices and FAT32. What changes: the devices are discovered at run time, describe themselves, appear and disappear while the system runs, and sit behind a bus protocol with its own requests; there are now two layers of drivers (controller and class). What comes next: F4-10 takes the same ring-and-descriptor pattern to a network card, then builds a protocol stack on top of it.

Summary


    

  • USB is host-driven: devices describe themselves with descriptors; drivers bind to interfaces by class.
    • 

  • xHCI works through rings of 16-byte TRBs with a cycle bit, doorbells and an event ring; contexts describe slots and endpoints.
    • 

  • Enumeration: reset, Enable Slot, Address Device (the controller sends SET_ADDRESS), descriptors, Configure Endpoint, SET_CONFIGURATION (R2, R4).
    • 

  • HID boot keyboards send 8-byte state reports; BOT carries big-endian SCSI commands in CBW/CSW wrappers.
    • 

  • Captures show requests at URB level; IDs-to-name lookups can mislead (R4).
    • 

  • Firmware may leave the controller running; take it over before enabling the IOMMU (R5).
    •

Forensic answer key


Observation. R6: "READ(10) LBA 2050, 1 block(s) → CSW status 1, sense key 0x5 ASC 0x21": ILLEGAL REQUEST, logical block address out of range. R7: frame 69 READ(10) LBA 0 (the boot sector, which succeeded) and frame 75 READ(10) LBA 34078720.


Root cause. 2050 = 0x00000802. Stored little-endian, the CDB bytes are 02 08 00 00; the device reads them big-endian as 0x02080000 = 34078720, beyond the last LBA 131071. bot.cc line 18 (memcpy(p, &lba, 4) under F409_LBA_LE) copies the CPU's byte order into a big-endian SCSI field. LBA 0 reads the same in both orders, so the boot sector worked.


Injection. Built with -DF409_LBA_LE.


Fix and verification. Use put_be32; rerun: the root directory read at LBA 2050 succeeds (R2). A unit test: build the CDB for LBA 0x01020304 and compare the bytes with 01 02 03 04; or read LBA 1 and check it is not the boot sector.


Firmware frames. Tag 0x3e7 (999) on frames 11–37: not the kernel's (its tags start at 1, frame 53); most likely the firmware probing the stick before the kernel ran. They show the device worked before the kernel touched it.


Wrong answers. "The image is corrupt": the host wrote it with mkfs.fat and the boot sector parses. "The FAT arithmetic is wrong": 2050 = 32 reserved + 2 × 1009 FAT sectors, correct for root cluster 2; the capture shows a different number on the wire.
