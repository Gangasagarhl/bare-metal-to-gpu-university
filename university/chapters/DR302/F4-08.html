Story hook

A school's storeroom has one big door. For years every delivery truck backed up to it and unloaded wherever the driver's note said: "shelf 412, 4 boxes". Nobody checked the note. Then one morning a note with a typo sent four boxes of paint onto the shelf where the exam papers were kept. Nobody had done anything malicious; one wrong number was enough.

The school hired a gatekeeper. Now every truck has a list, made by the office, of the shelves it may use. The gatekeeper translates the driver's shelf numbers into real shelves, and a truck whose note names a shelf that is not on its list is stopped at the door. The gatekeeper writes the truck's number, the shelf and the reason into a log book and rings the office.

The same week the school replaced its doorbells. A bell only says "someone is at a door"; the office then had to walk round to find out which one. The new system has visitors push a small written note through the office's mail slot: "class 4B, please". The office knows at once who wants what.

This chapter builds both: message-signalled interrupts (the notes) and an IOMMU (the gatekeeper). Every DR301 driver you wrote used a wired interrupt line and gave devices raw physical addresses. By the end of this chapter, a device that writes to a wrong address leaves a fault record in a log instead of a corrupted page.

What you will be able to do

  • Explain the path of a wired (INTx) interrupt through the IOAPIC and of a message-signalled interrupt (MSI) straight to the local APIC, and say why the handler must acknowledge the device before the end-of-interrupt for a level-triggered line.
  • Program the MSI capability (address, data, enable) and an MSI-X table entry, mask and unmask an entry, and read its pending bit.
  • Parse the ACPI DMAR table, set up a VT-d root table, context entries and a three-level second-level page table, and switch translation on.
  • Write a DMA mapping API that every driver uses, so a device can reach only the buffers it was given.
  • Decode a VT-d fault record (source ID, address, reason) and trace it back to a driver bug.
  • Judge which C7 acceptance tests the lab meets in QEMU and which remain open.
Jargon box
MSI (message-signalled interrupt)
Simple words: a device asks for attention by writing a small value to a special address instead of raising a wire. Analogy: a note pushed through the office's mail slot. Precise: a PCI capability (ID 05h) holding a message address, a message data value and an enable bit; to interrupt, the function performs a posted memory write of the data to the address. On x86 the address selects a local APIC and the data carries the vector. D1 D3 L1
MSI-X
Simple words: MSI with a table of many messages, one per event source. Analogy: a pad of pre-addressed notes, one per class. Precise: a PCI capability (ID 11h) pointing into a BAR at a table of 16-byte entries (address, data, vector control with a mask bit) and a pending bit array (PBA). D2 L1
IOAPIC and GSI
Simple words: the chip that turns interrupt wires into vectors; each of its inputs has a system-wide number. Analogy: the switchboard in the corridor that knows which classroom each bell wire comes from. Precise: an I/O APIC has redirection entries, one per input, holding vector, trigger mode, polarity, mask and destination; ACPI numbers its inputs as global system interrupts (GSIs). D3 D5
IOMMU
Simple words: a translator between the addresses devices use and real memory, which can also say no. Analogy: the storeroom gatekeeper with a list of shelves per truck. Precise: a DMA remapping unit that translates each DMA request's address through page tables selected by the requester's ID, and blocks and reports requests without a valid translation. Intel's version is VT-d. D4
IOVA (I/O virtual address)
Simple words: the address a device is told to use for a buffer. Analogy: the shelf number written on the driver's note. Precise: an address in a DMA domain's address space, translated by the IOMMU to a physical address; without an IOMMU it equals the physical address. D4
DMA domain
Simple words: one set of mappings shared by the devices put in it. Analogy: one list of allowed shelves. Precise: in VT-d, the address space named by a domain ID in a context entry, with its own second-level page tables. D4
Fault record
Simple words: the IOMMU's note about a request it refused. Analogy: the gatekeeper's log book line. Precise: a 128-bit register holding the faulting page address, the requester's source ID, the read/write type and a fault reason code, with a "fault" bit the software clears by writing 1. D4

Layer 1 — the kid explanation

Analogy

A doorbell tells the office "someone, somewhere". A note through the mail slot says who and what. The storeroom gatekeeper holds a list for every truck: "truck 1 may unload on shelves 800 and 802, and nowhere else". A truck that tries shelf 15A is stopped and written into the log book.

Devices interrupt the processor in two ways. Older ones pull a wire to a switchboard, which tells the processor a number. Newer ones send a tiny message, written like any other memory write, that already contains the number. Devices also copy data into memory by themselves. Without a guard they can write anywhere. The IOMMU is the guard: the kernel tells it which pieces of memory each device may use, and it stops and reports everything else.

Layer 2 — the student explanation

Wired interrupts and their limits

In DR301 every driver used a line interrupt. On the q35 machine the 8259 pair is still there but parked and masked; the lab kernel uses the IOAPIC instead. The ACPI MADT names the local APIC (at 0xFEE00000), one IOAPIC (at 0xFEC00000, GSI base 0, 24 entries) and five interrupt source overrides, for example ISA IRQ 0 to GSI 2 and ISA IRQ 9 to GSI 9, level, active high (R1). D5 R1 A PCI function's INTx pin reaches some IOAPIC input; which one, the firmware describes in AML (the subject of F4-11). Lines are shared, they need the routing information, and a level-triggered line stays asserted until the driver clears the cause inside the device.

MSI: the interrupt as a memory write

A function with the MSI capability is given an address and a data value. When it has something to report it writes the data to the address. On x86 the address has the form 0xFEE00000 with the destination APIC ID in bits 19:12, and the data holds the vector in bits 7:0 with fixed delivery and edge trigger when the upper bits are zero. D3 The local APIC picks the write off the bus; no IOAPIC and no routing table are involved. In the lab the edu device's capability read 0x0080 before (64-bit capable, disabled) and 0x0081 after enabling, with address 0xFEE00000 and data 0x0040; five interrupt requests produced five interrupts on vector 0x40 (R1). R1

MSI's limits: one address and one data value, and at most 32 vectors that must be consecutive and aligned (the "multiple message" fields). MSI-X lifts both: a table in device memory with one entry per interrupt source, each with its own address, data and a mask bit, plus a pending bit array that records interrupts that arrived while an entry was masked. D2 QEMU's xHCI controller offers 16 entries in BAR0 at offset 0x3000 with the PBA at 0x3800; with entry 0 masked a command completion set PBA bit 0 and no interrupt arrived; unmasking delivered it (R1). R1

DMA without a guard

Bus-mastering devices read and write memory on their own. In DR301 the kernel handed them physical addresses. The lab's "stray" test tells QEMU's edu device (a teaching device with a DMA engine and an interrupt register) D6 to copy 4096 bytes to the physical address of a canary page that no driver gave it. Without an IOMMU the copy happens: 4080 of 4096 canary bytes changed (R1; 16 bytes happened to be equal). R1

The IOMMU and the mapping API

With VT-d on, each DMA request is translated. The request carries the requester's bus, device and function (the source ID); the IOMMU looks up a root table entry by bus and a context entry by device and function, which names a domain and its page table; the address the device used (the IOVA) walks that page table like a virtual address walks the CPU's. D4 The driver no longer passes physical addresses. It calls dma::map(device, buffer, length, device_writes) and gives the device what comes back. In the lab's IOMMU run the source buffer at physical 0x15c000 became IOVA 0x800000 and the destination at 0x15b000 became 0x802000; the round trip still matched byte for byte, and the stray write now produced a fault record ("source 00:01.0 write at IOVA 0x15a000, reason 5") while 0 canary bytes changed (R2). R2

Layer 3 — the engineer's depth

The MSI capability

The capability's message control word has the enable bit (bit 0), "multiple message capable" (bits 3:1), "multiple message enable" (bits 6:4), "64-bit address" (bit 7) and "per-vector masking" (bit 8). The address low dword follows at offset 4; for a 64-bit capability the high dword is at 8 and the data at 0Ch, otherwise the data is at 8. D1 These offsets and masks were checked in this build against Linux's <linux/pci_regs.h>: 24 of 24 values match (R5). L1 R5 Two rules from the specifications matter for drivers: with MSI or MSI-X enabled the function must not use INTx, and software sets the command register's "interrupt disable" bit to make sure; and the message must be programmed before enable is set. D1

MSI-X: table, PBA and the safe enable order

Message control bits 10:0 hold the table size minus one, bit 14 is "function mask" and bit 15 is "enable"; the table offset/BIR dword says which BAR (bits 2:0) and where (the rest) the table lives, and the PBA dword the same for the pending bits. Each entry has address low, address high, data and vector control, whose bit 0 masks the entry. D2 L1 Entries come out of reset in an undefined or masked state depending on the device, so the driver enables MSI-X with the function mask set, masks every entry, clears the function mask, and unmasks each entry only after programming it. A masked entry that has an event to send sets its PBA bit; unmasking it with the bit set makes the device send the message. D2

The design question MSI-X answers is "one interrupt per what?". NVMe gives one vector per completion queue and pins each queue to a CPU; a NIC gives one per receive and transmit queue; xHCI one per interrupter. The vector then identifies the event source without reading a shared status register, and the destination APIC ID in each entry spreads the work across CPUs. D2

VT-d: the DMAR table and the register set

The ACPI DMAR table lists DMA remapping hardware units (DRHD structures) with their register base and the devices each unit covers: either "all PCI devices of this segment" (the INCLUDE_PCI_ALL flag) or an explicit list of device scopes. QEMU's table in this build had one unit at 0xFED90000 with INCLUDE_PCI_ALL = 0 and seven scopes: the IOAPIC and the endpoints 00.0, 01.0, 02.0, 1f.0, 1f.2 and 1f.3 (R2). D4 R2 A driver must check that every device it attaches is in some unit's scope; a device outside every scope is not translated at all.

The capability register says what the unit supports. In R2: CAP = 0xd2008c22260206 and ECAP = 0xf00f4a, which the kernel decodes as SAGAW 0x2 (only the 39-bit, 3-level table format), MGAW 39, 216 domains, caching mode 0, one fault-recording register at offset 0x220 and the IOTLB registers at 0xf0. R2 The field positions are from memory of D4 (box below). "Caching mode 0" matters: with caching mode 1 (common for virtual IOMMUs) the hardware may cache not-present entries, and software must invalidate after adding a mapping too, not only after removing one. D4

Root, context and second-level tables

The root table is a 4 KiB page of 256 16-byte entries, one per bus; a present root entry points to a context table of 256 entries, one per device and function (index = device × 8 + function). A context entry holds the present bit, the translation type, the second-level page-table pointer, the address width (AW = 1 for 39 bits, three levels) and the domain ID. D4 In R2 the edu device's entry reads 0x0000000000000101_000000000011a001: present, table at 0x11a000, AW 1, domain 1. R2 Second-level entries are 64 bits: bit 0 read, bit 1 write, bits 51:12 the next table or the page. An entry with neither read nor write set is not present; there is no separate present bit. D4 That is why the stray write is reported as reason 5 ("write to a page without write permission") rather than as a separate "not mapped" reason, and why QEMU's own message says "slpte permission error ... slpte=0x0" (R2). R2

Turning translation on, and invalidation

The order in the lab: write the root table address to RTADDR, set SRTP in GCMD and wait for RTPS in GSTS; invalidate the context cache globally (CCMD with ICC); invalidate the IOTLB globally (the IOTLB register at ECAP.IRO + 8); set TE and wait for TES. R2 shows GSTS = 0xc0000000 (TES and RTPS) after the last step. D4 R2 GCMD bits are not "sticky": each write must carry every command bit that should stay on, so the driver writes TE together with whatever is already on. Every unmap must be followed by an IOTLB invalidation before the memory is reused, or the device can still reach the page through the cached translation; the lab's dma::unmap does a global invalidation, which is correct but slow (domain-selective and page-selective invalidations exist for production use). D4

Fault reporting

FSTS bit 1 (PPF) says a fault record is pending; the record holds, in bits 127:64, F (bit 127), the type T (bit 126, 1 = read), the reason in bits 103:96 and the source ID in bits 79:64, and the faulting page in bits 63:12. The software clears F by writing 1 to it. FECTL, FEDATA and FEADDR turn fault events into an MSI. D4 With a single fault-recording register (R2), faults that arrive while the record is still pending are not recorded; QEMU says so on its console ("New fault is not recorded due to compression of faults", R2). Read and clear records promptly, in the fault handler.

Not verified — check before relying on this

The VT-d register offsets (CAP 08h, ECAP 10h, GCMD 18h, GSTS 1Ch, RTADDR 20h, CCMD 28h, FSTS 34h, FECTL 38h, FEDATA 3Ch, FEADDR 40h), the CAP and ECAP field positions, the root, context and second-level entry formats, the fault-record layout and the reason codes in vtd.h and vtd.cc are from the author's memory of D4, which was not opened in this build. They are confirmed only by QEMU 8.2.2's intel-iommu model behaving as expected (translation works, the stray write is refused, the record decodes to the right device and page, R2). The MSI message format (D3) is confirmed the same way (R1). The MSI and MSI-X capability offsets are confirmed by <linux/pci_regs.h> (R5). Nothing here ran on real VT-d hardware.

How the hardware actually does it

An MSI is an ordinary PCI Express memory write transaction; the root complex recognises the 0xFEE address range as interrupt messages and forwards them to the processor's local APICs instead of to DRAM. D2 D3 Because it is a posted write travelling the same path as the device's data writes, PCI ordering rules mean the interrupt cannot overtake the data the device wrote before it: when the handler runs, the DMA data is in memory. A wired interrupt has no such guarantee, which is why drivers using INTx read a device register (a read flushes posted writes) before trusting the data. D2

The IOMMU sits in the root complex on the path from the PCI hierarchy to memory. It sees every inbound request with its requester ID, which the PCI Express link layer attaches to each transaction; this is also its weakness: devices behind a PCI-to-PCI bridge (conventional PCI) may all appear with the bridge's ID and share one context entry. D4 Interrupt messages also pass through the IOMMU; VT-d can remap them too (interrupt remapping, not built in this lab), so that a device cannot inject an arbitrary vector by writing to 0xFEE00000. D4

The IOTLB is to the IOMMU what the TLB is to the CPU: translations cached near the walker. Real units also cache context entries and intermediate page-table entries, and some devices cache translations themselves (ATS); each cache needs its own invalidation. D4

Worked example

Task. (1) Build the MSI message for vector 0x40 to APIC 0, for vector 0x41 to APIC 0 and for vector 0x42 to APIC 3. (2) Split the IOVAs 0x804000, 0x805000 and 0x4c0123456 into the three table indices of a 39-bit domain. (3) Decode the raw fault record R2 printed.

Step 1. Address = 0xFEE00000 | (APIC ID << 12); data = vector. APIC 3 gives 0xFEE00000 | 0x3000 = 0xFEE03000. D3

Step 2. Index L3 = bits 38:30, L2 = bits 29:21, L1 = bits 20:12, offset = bits 11:0. 0x804000 = 8 MiB + 16 KiB: L3 = 0, L2 = 0x804000 >> 21 = 4, L1 = (0x804000 >> 12) & 0x1FF = 0x804 & 0x1FF = 4. For 0x805000, L1 = 5. For 0x4c0123456, write the address as 19 × 230 + 0x123456 (19 × 0x40000000 = 0x4c0000000): L3 = 19; 0x123456 is below 221, so L2 = 0; L1 = 0x123456 >> 12 = 0x123 = 291; offset 0x456.

Step 3. High dword pair 0x80ffff0500000008: bit 127 (top bit of the high quadword) = 1, so the record is valid; bit 126 = 0, a write; bits 103:96 = byte 4 of the high quadword = 0x05, reason 5; bits 79:64 = 0x0008 = bus 0, device 1, function 0 (0x0008 >> 3 = 1). Low quadword 0x15a000: the page. D4

Where the analogy breaks


    

  • The note is not addressed to "the office". An MSI goes to one local APIC, chosen by the address; with several CPUs each entry can name a different one. The single office of the analogy hides the main reason MSI-X exists: spreading interrupts across processors.
    • 

  • The gatekeeper does not read the note's content. The IOMMU checks addresses and permissions, never data. A device allowed to write a buffer can write anything into it, including a malicious network packet or a forged structure; the IOMMU only limits where.
    • 

  • The list is cached, and the cache does not update itself. A gatekeeper who memorised yesterday's list keeps applying it until told to forget. After removing a mapping the kernel must invalidate the IOTLB; the analogy's "the list was changed, so the truck is stopped" is wrong without that step.
    • 

  • Interrupt notes pass the same gate. MSIs are memory writes through the IOMMU; without interrupt remapping a device can write any vector to 0xFEE00000. Notes and deliveries are one mechanism, not two.
    • 




Common mistakes and debugging


    

  • Symptom: MSI enabled, no interrupt ever arrives. Cause: bus mastering off (an MSI is a bus-master write), or the data written at 08h in a 64-bit capability. Find it: print the capability after enabling (Listing 1's msi::print, R1 shows the good state: address 0xfee00000, data 0x0040). Fix: set the command register's master bit; choose the data offset by bit 7.
    • 

  • Symptom: an interrupt storm right after enabling MSI-X. Cause: entries left unmasked with reset contents (address 0, data 0) or programmed after the function was enabled. Find it: dump each entry. Fix: the order in Listing 1 lines 70–72.
    • 

  • Symptom: a level-triggered line interrupts again and again. Cause: the handler did not clear the cause in the device before the EOI. Find it: the vector's count races upward (intr::count). Fix: read and acknowledge the device (edu's IRQ_ACK in edu_irq) before returning.
    • 

  • Symptom: with the IOMMU on, the first DMA faults at address 0x15b000 although the buffer is mapped. Cause: the driver passed the physical address, not the IOVA. Find it: the fault record's address is a physical address, not one of the domain's IOVAs (the lab's IOVAs start at 0x800000). Fix: use the value dma::map returns.
    • 

  • Symptom: after unmap, the device can still write the old buffer (on real hardware or with caching mode 1). Cause: missing IOTLB invalidation. Find it: write a test that unmaps, then asks for DMA to the old IOVA; it must fault. Fix: invalidate after every unmap; with caching mode 1, after every map too.
    • 

  • Symptom: translation enabled, every device faults with "context entry not present". Cause: the context cache was not invalidated after the root table was installed, or the device is outside every DRHD scope. Find it: print the scopes (R2 lists them). Fix: the order in Layer 3; attach only devices in scope.
    • 




Transition box

Where you came from: DR301's drivers used one wired interrupt line per device through the PIC or IOAPIC and gave devices physical addresses (F4-03, F4-07). What carries over: the capability walk of F4-02, the handler-then-EOI rhythm, write-1-to-clear status bits, and the CPU page tables of F3-21: the IOMMU's tables are the same idea for devices. What changes: interrupts become memory writes with a vector inside, there can be one per queue, and every DMA address now comes from a mapping call; a wrong address is a logged fault, not silent corruption. What comes next: every later DR302 driver (xHCI, e1000, HD Audio) uses this chapter's interrupt layer and mapping API, and each lab has a run with the IOMMU on.

Safety
In QEMU nothing can be damaged. On a real machine, a driver that programs a wrong DMA address with the IOMMU off can overwrite any memory, including file-system caches that are later written to disk: test DMA drivers on the spare PC only, with disks you can erase disconnected, as the curriculum's safety box on drivers says. Summary


    

  • MSI turns an interrupt into a memory write of a vector to an APIC address; no IOAPIC, no routing table, no shared line (R1).
    • 

  • MSI-X adds a table of independently masked messages and a pending bit array; enable with the function mask set and unmask entries only after programming them (R1).
    • 

  • Level-triggered lines need the device acknowledged before the EOI; MSIs are edge-like messages.
    • 

  • VT-d translates each DMA by source ID → root entry → context entry (domain) → three-level page table; entries with neither R nor W are not present (R2).
    • 

  • Drivers obtain device addresses only from a mapping API; unmap must be followed by an IOTLB invalidation.
    • 

  • With the IOMMU on, a stray DMA becomes a fault record (source, address, reason) instead of corrupted memory (R1 versus R2).
    • 

  • The register layouts used here are from memory and confirmed only against QEMU; the MSI/MSI-X constants match Linux's header (R5).
    •

Forensic answer key


Observation. Request 1: mapped at IOVA 0x802000 at t = 115 ms; "buffer released" at t = 116 ms; DMAR fault at t = 216 ms for 00:01.0, write, IOVA 0x802000, reason 5; payload fnv1a 0x76efddc5 instead of 0x01fbddc5. Request 2 repeats the pattern at IOVA 0x804000. The raw record high 0x80ffff0500000008 decodes as valid, write, reason 5, source 0x0008 (00:01.0).


Root cause. The driver unmaps the receive buffer immediately after starting the DMA (f408_main.cc, edu_receive_buggy: dma::unmap right after edu::dma_start), so when the device writes, about 100 ms later, the IOVA has no entry and the IOMMU blocks the write. The log alone proves it: the fault's IOVA equals the mapped IOVA, and "released" precedes the fault. Ruled out: "the IOMMU driver is broken" (R2's mapped transfers succeed with the same API); "wrong IOVA passed" (the addresses match exactly).


Injection. Built with -DF408_FREE_TOO_EARLY, which compiles the receive path shown above.


Fix. Unmap only after the completion (IRQ_DMA_DONE) has been observed; verify by rerunning: no fault, payload fnv1a equals the source.


Why it "works" without an IOMMU. Unmap is a no-op in identity mode, so the device writes the buffer, which by then may belong to someone else: silent corruption of reused memory, far worse than a logged fault.


Prevention. The mini-project's dma_debug (refuse to unmap a range owned by an in-flight request; poison on unmap); a test that runs every driver with the IOMMU on.


Wrong answers. "Reason 5 means the mapping was read-only": the mapping existed with write permission while it existed; it was removed. "The IOTLB was stale": a stale IOTLB would let the write through, not block it.
