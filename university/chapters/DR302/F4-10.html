Story hook

The school's post room sends long letters to another school across town. The courier only takes single pages, and sometimes a page falls off the bike. So the post room numbers every page, keeps a copy of each until the other school sends back a receipt ("I have everything up to page 41"), and keeps a kitchen timer running for the oldest page nobody has signed for. If the timer rings, that page goes out again.

One day a new clerk "simplifies" the timer: he stops it whenever a receipt arrives, planning to restart it with the next new page. On a good day nobody notices. On a bad day, the last pages of a letter get lost, no new pages are left to send, and the timer is never restarted. The letter sits half delivered, forever, and nothing in the post room looks wrong.

This chapter builds a network card driver and the post room on top of it: Ethernet, ARP, IPv4, ICMP, UDP, DHCP and TCP. The forensic lab is that clerk's bug, found in a Wireshark capture.

What you will be able to do

  • Drive the Intel 82540EM (QEMU's e1000): reset, MAC address from the EEPROM, receive and transmit descriptor rings, all through the DMA mapping API.
  • Build Ethernet, ARP, IPv4 with the Internet checksum, ICMP echo, UDP and a DHCP client, and check every header layout against the C library.
  • Implement TCP: the three-way handshake, sequence and acknowledgement numbers, the receive window, retransmission with RFC 6298 timers and Karn's rule, fast retransmit and orderly close.
  • Measure correctness end to end: 100 MiB echoed with a checksum, a web page fetched and compared byte for byte, transfers under 5 % loss.
  • Read a capture with Wireshark's TCP analysis and connect each flag to a line of your code.
Jargon box
Descriptor ring (NIC)
Simple words: a circular list in memory where the driver and the card hand packet buffers to each other. Analogy: the post room's pigeonholes with "full" and "empty" flags. Precise: an array of 16-byte descriptors (buffer address, length, status, errors) with a head register advanced by the NIC and a tail register written by the driver; the descriptor-done (DD) bit marks the ones the NIC has finished. D1
ARP
Simple words: asking the local network "who has this IP address?" to learn its hardware address. Analogy: shouting a name in the corridor to find which room someone is in. Precise: the Address Resolution Protocol: a broadcast request and a unicast reply mapping an IPv4 address to an Ethernet MAC address, cached by the requester. D2
Internet checksum
Simple words: a 16-bit sum that lets the receiver notice a damaged header. Analogy: the total written at the bottom of a page. Precise: the one's complement of the one's complement sum of 16-bit big-endian words; IPv4 covers its header, UDP and TCP cover a pseudo-header (addresses, protocol, length) plus their segment. D3
DHCP
Simple words: how a machine gets an IP address when it joins a network. Analogy: asking the office for a desk number on the first day. Precise: a UDP protocol (client port 68, server 67): DISCOVER, OFFER, REQUEST, ACK, with options for mask, router, DNS server and lease time. D5
Sequence and acknowledgement numbers
Simple words: TCP numbers every byte; the receiver says which byte it expects next. Analogy: page numbers and receipts. Precise: 32-bit numbers starting at an initial sequence number chosen per connection; ACK = next expected byte (cumulative); comparisons use modulo-232 arithmetic. D6
RTO (retransmission timeout)
Simple words: how long TCP waits for a receipt before sending again. Analogy: the kitchen timer for the oldest unsigned page. Precise: computed from smoothed round-trip time SRTT and variation RTTVAR (RTO = SRTT + 4 × RTTVAR, at least 1 s per RFC 6298), doubled after each timeout; the timer must run whenever data is unacknowledged. D8
Fast retransmit
Simple words: resending a missing segment as soon as three duplicate receipts show it is missing. Analogy: three receipts in a row saying "still waiting for page 12". Precise: on the third duplicate ACK the sender retransmits the first unacknowledged segment without waiting for the RTO and halves its congestion window (RFC 5681). D7

Layer 1 — the kid explanation

Analogy

The post room cuts every letter into numbered pages and posts them. The other school sends a receipt saying "I have everything before page 42". If a page goes missing, receipts keep saying "still waiting for 42", and after three such receipts the post room resends page 42 at once. If no receipts come at all, a kitchen timer rings and the post room resends the oldest page anyway.

A network card puts packets into memory and takes packets out of memory, by itself. The kernel and the card share a ring of boxes for this. On top of the card, each layer adds a label: the Ethernet label says which card on the wire, the IP label says which computer in the world, the TCP label says which conversation and which byte. TCP turns lossy, unordered packets into a reliable stream of bytes by numbering, acknowledging and resending.

Layer 2 — the student explanation

The NIC

The e1000 is found by PCI ID 8086:100E. The driver resets it (CTRL.RST), sets "link up", reads the MAC address from the first three EEPROM words, programs it into the receive address registers, and builds two rings of 32 descriptors: receive (each with a 2048-byte buffer) and transmit. Receiving: the NIC writes a frame into the buffer of the descriptor at its head, sets DD and advances; the driver copies frames from descriptors with DD set and hands each back by writing the tail register. Transmitting is the mirror image. D1 R2's first lines: MAC 52:54:00:12:34:56, link up, 32/32 descriptors. R2 The lab's driver polls instead of taking interrupts; the interrupt path of the same NIC is tested in F4-11.

The layers

Ethernet frames carry a type: 0x0800 IPv4, 0x0806 ARP. ARP fills a small cache. IPv4 adds addresses, a time-to-live and a header checksum; ICMP echo is ping; UDP adds ports and a length. DHCP runs over UDP broadcasts before the machine has an address. R2: offer and ACK from 10.0.2.2, address 10.0.2.15, mask 255.255.255.0, router 10.0.2.2, DNS 10.0.2.3, lease 86400 s; three pings to the router answered. D2 D3 D4 D5 R2 Every header offset was checked against the C library's <netinet/*.h> (R1). L1 R1

TCP in one page

A connection is opened with SYN, SYN-ACK, ACK and closed with a FIN from each side. Each side numbers its bytes; the other acknowledges the next byte it expects. The sender may have at most min(receiver's window, congestion window) bytes in flight. Lost data is detected two ways: three duplicate ACKs (fast retransmit) or the retransmission timer. D6 D7 D8 The lab's TCP is about 480 lines: no window scaling, no selective acknowledgements, no out-of-order queue (segments after a gap are dropped and acknowledged with a duplicate ACK), no RST for unknown ports.

A hostfwd rule forwards a host port to the guest's echo server; guestfwd rules connect the guest's connections to 10.0.2.100:80 and :9 to programs on the host (a tiny HTTP server and a sink). Layer 3 — the engineer's depth

Sequence arithmetic and state

Sequence numbers wrap at 232, so "a before b" is (int32_t)(a - b) < 0, never a < b (tcp.cc lines 54–55). The sender keeps snd_una (oldest unacknowledged), snd_nxt (next to send) and snd_max (highest sent); after a timeout snd_nxt goes back to snd_una (go-back-N) while snd_max remembers what was already sent once. An ACK is acceptable when snd_una < ack ≤ snd_max. D6

Timers: RFC 6298

The first RTT sample R sets SRTT = R and RTTVAR = R/2; later samples update RTTVAR = ¾ RTTVAR + ¼ |SRTT − R| and SRTT = ⅞ SRTT + ⅛ R; RTO = SRTT + max(G, 4 × RTTVAR), rounded up to 1 s. Karn's rule: never take a sample from a retransmitted segment. On expiry: retransmit the oldest segment, double the RTO, restart the timer. The three rules that matter most: (5.1) when sending data, start the timer if it is not running; (5.2) when everything is acknowledged, stop it; (5.3) when an ACK acknowledges new data but not all, restart it. D8 The lab deviates in one place, marked "LAB:" in the code: the minimum RTO is 200 ms instead of 1 s, so loss runs finish in seconds. In QEMU the measured RTT is 0–1 ms (SRTT 0 or 1 in R2), so every RTO in the run is the minimum, doubled after each timeout (400 ms in R5). R2 R5

Congestion control: RFC 5681

The congestion window starts at two segments and grows by one segment per ACK in slow start (until ssthresh) and by about one segment per round trip afterwards. Three duplicate ACKs: ssthresh = max(flight/2, 2 × MSS), retransmit, cwnd = ssthresh + 3 × MSS, inflate by one MSS per further duplicate, deflate to ssthresh on the next new ACK. A timeout: ssthresh the same way, cwnd = one segment. D7 On a virtual link with 0 ms RTT and no real bottleneck these rules barely matter for speed, but they decide behaviour under loss.

Loss without induced loss: the receive ring

The echo run had no induced loss, yet the kernel's TCP counted 23 segments arriving after a gap, and tshark counted 29 retransmissions and 23 duplicate ACKs on port 7 (R2, R3). The NIC's own statistics registers answer where they went: "missed packets (MPC) 41417, receive-no-buffers events (RNBC) 41417" (R2). QEMU's router sends as fast as the guest's window allows; the polled driver with 32 receive descriptors falls behind; when the ring is full the NIC has nowhere to put a frame. The capture is taken at QEMU's network layer, before the NIC model, which is why tshark sees the segments the kernel never received. D1 R2 R3 How QEMU's model counts (one per lost frame or one per refused delivery attempt) was not established; the two counters are equal, and the IOMMU run with a 64 KiB echo shows 0 (R4). TCP recovered every time, which is the point of the exercise: the layer above must survive the layer below.

Induced loss

The milestone asks for 5 % packet loss "(QEMU network filters)". QEMU 8.2.2's filters, as far as the author knows, dump, buffer, mirror, redirect and rewrite traffic but do not drop a percentage of it (unverified, D10), so the lab induces loss in the kernel itself: net::set_loss drops TCP segments on transmit and on receive by a hash of the sequence number and the retransmission count, which makes runs repeatable (seeded) while giving a retransmission a fresh decision. R2: 13 transmit and 28 receive segments dropped. R2 A drop in the kernel is not the same as a drop on the wire: the sender's own counters see it. Treat this as a substitute, recorded as an open decision.

Not verified — check before relying on this

The e1000 register offsets and bits, the EEPROM read protocol, the legacy descriptor formats and the statistics registers (MPC, RNBC) in e1000.h are from the author's memory of D1, confirmed only by QEMU 8.2.2's e1000 model. The protocol behaviour of net.cc and tcp.cc follows the RFCs (D2–D8) as remembered; the RFCs were not opened. Header layouts are confirmed by glibc's headers (R1), and the wire format by tshark decoding every frame without a malformed packet or bad checksum (R3), which is strong evidence for the formats but none for the timer and congestion rules. The claim that QEMU has no loss filter is unverified.

How the hardware actually does it

The 82540EM has its own receive FIFO in front of the descriptor ring: frames arrive from the PHY at line rate, are filtered by MAC address (exact, multicast hash, broadcast), checked against the Ethernet CRC, and written by DMA into the buffer of the next free descriptor. When the ring has no free descriptor the FIFO fills and frames are counted as missed. D1 Real drivers keep the ring large (256–4096 descriptors), take an interrupt per batch (with interrupt moderation timers so that one interrupt covers many frames) and refill buffers in the handler. Modern NICs add many queues with MSI-X vectors (the pattern of F4-08), checksum and segmentation offload (the NIC computes TCP checksums and cuts large sends into segments), and receive-side scaling that hashes each connection to a queue and a CPU. D1

The minimum Ethernet frame is 64 bytes including the 4-byte CRC; the driver pads shorter frames to 60 bytes before the NIC adds the CRC (e1000.cc lines 112–113; ARP requests are 42 bytes). The NIC appends the CRC itself when the descriptor's IFCS bit is set and, with SECRC in RCTL, strips it from received frames. D1

Worked example

Task. (1) Compute the IPv4 header checksum of the ping packet the kernel sends to the router. (2) Follow the retransmission timer through R2's numbers. (3) Check that the forensic sink's byte count, the sender's snd_una and the capture's last ACK agree.

Step 1. The header is 45 00 | 00 54 | 00 01 | 40 00 | 40 01 | 00 00 | 0a 00 | 02 0f | 0a 00 | 02 02 (version 4, 20-byte header, total length 84, id 1, don't fragment, TTL 64, protocol 1 = ICMP, checksum 0 while computing, 10.0.2.15 → 10.0.2.2). Sum of the ten 16-bit words: 0x4500 + 0x0054 + 0x0001 + 0x4000 + 0x4001 + 0x0000 + 0x0a00 + 0x020f + 0x0a00 + 0x0202 = 0xDD67. No carry to fold. One's complement: 0xFFFF − 0xDD67 = 0x2298. Check: with 0x2298 in place the sum is 0xFFFF, whose complement is 0. R1's last line computed the same header with the kernel's checksum code: "0x2298; re-check … 0x0000 ok". D3 R1

Step 2. A first sample R = 1 ms gives SRTT = 1, RTTVAR = 0 (integer half of 1), RTO = 1 + max(1, 0) = 2 ms, raised to the lab minimum 200 ms. One timeout doubles it to 400 ms (the forensic run, R5: "RTO now 400 ms"); two to 800 ms. With the RFC's 1 s minimum the same run would wait 1 s, 2 s, 4 s. D8 R5

Step 3. The relative sequence number of data byte k is k + 1 (byte 0 is sequence 1, after the SYN). The host sink says it received 34310 bytes: bytes 0 … 34309, sequence 1 … 34310. The next byte expected is sequence 34311. The kernel's snd_una is 34311 and the capture's last ACK from 10.0.2.100 is 34311 (R5, R6). All three agree: the receiver has everything before 34311 and nothing from 34311 on. R5 R6

Where the analogy breaks


    

  • Pages are bytes. TCP numbers bytes, not segments; a retransmission may carry a different split of the same bytes.
    • 

  • Receipts are cumulative only. A receipt cannot say "I have 44 and 45 but not 42" in this lab's TCP (real stacks add selective acknowledgements); the analogy's clerk would naturally list them.
    • 

  • The courier's speed is unknown and changing. The kitchen timer's length is learned from measured round trips and doubles after each ring; a fixed timer is the wrong picture.
    • 

  • Losing pages is also a signal. In TCP, loss means "the network is congested" and makes the sender slow down; the post room only resends.
    • 




Common mistakes and debugging


    

  • Symptom: nothing is received, DHCP times out. Cause: RCTL.EN not set, RAH0.AV missing, broadcast not accepted (BAM), or the receive tail not written. Find it: read RDH after a few seconds; if it never moves, the NIC is not receiving. Fix: lines 73–86.
    • 

  • Symptom: every received IPv4 packet is dropped as "bad checksum". Cause: summing little-endian words, or not folding carries. Find it: run the checksum on a known header (R1). Fix: big-endian words, fold, complement.
    • 

  • Symptom: the TCP handshake completes but the peer resets after the first data. Cause: a wrong pseudo-header (length or byte order), so every data segment fails the peer's checksum. Find it: tshark with checksum validation on (R3's command). Fix: pseudo-header = source, destination, 0, protocol 6, TCP length.
    • 

  • Symptom: a transfer stalls for ever after a loss. Cause: the retransmission timer not running while data is outstanding. Find it: the forensic lab's capture: silence after the last duplicate ACK. Fix: RFC 6298 rules 5.1–5.3.
    • 

  • Symptom: a 100 MiB transfer works, but slowly, with many retransmissions and no induced loss. Cause: the receive ring overflows (R2's MPC). Find it: the NIC's statistics registers. Fix: a larger ring, interrupts instead of polling, a smaller advertised window.
    • 

  • Symptom: the HTTP body has extra bytes at the end. Cause in this lab: the host program wrote log text to stderr, and QEMU's guestfwd … cmd: connects the program's stderr to the guest connection too. Find it: compare the body length with Content-Length. Fix: log to a file (httpd_stdio.py does).
    • 




Transition box

Where you came from: F4-08 (DMA mapping, IOMMU) and F4-09 (rings with ownership bits, completions). What carries over: descriptor rings with head and tail, ownership marked by a status bit, buffers that stay mapped until the device is done, polling or interrupt-driven completion. What changes: the device is the simple part; most of the code is protocol: state machines, timers and arithmetic modulo 232, where bugs show up only under loss and timing you do not control. What comes next: F4-11 leaves the data path for the platform: the ACPI tables that say how this NIC's interrupt is wired and how the machine powers off.

Forensic lab


Scenario. "Packets vanish at 5 % loss." A nightly job uploads 512 KiB from the kernel to a collector over a link that loses about 5 % of segments. Since a colleague "simplified the timer code", the job hangs every night after a few tens of kilobytes; it never errors, it never finishes. The colleague points at the network: "packets vanish".


Evidence pack. The kernel log with TCP tracing on (R5), the collector's log line (end of R5), and the Wireshark (tshark) analysis of the capture (R6).

Forensic answer key


Observation. The sink received 34310 bytes (sequence 1–34310). The capture's last frames: retransmission of 27741 at 1.2133 s, ACK 34311, retransmission of 35771 at 1.2141 s, duplicate ACK 34311 — then nothing. The kernel gave up at about 21 s ("send timed out", "state ESTABLISHED after 20002 ms") with snd_una 34311 < snd_max 37231 and "RTO 400 ms (NOT armed)". Wireshark flags: 4 retransmissions, 2 fast retransmissions, 14 duplicate ACKs, 3 "previous segment not captured".


Root cause. Data outstanding with no retransmission timer: RFC 6298 rule 5.3 broken. Built with -DF410_TIMER_BUG, on_ack stops the timer on every new ACK (tcp.cc line 175) and try_send re-arms it only when sending fresh data (line 120). After the timeout at t = 1204 ms the sender went back to 27741 and resent 27741 and 34311 as retransmissions (not fresh): the ACK for 27741 stopped the timer, the resent 34311 was lost again, then 35771 was resent, which used up the congestion window (2920 bytes, two segments, as the last state line shows), so no new data could be sent; one duplicate ACK is not enough for fast retransmit, and nothing ever re-armed the timer.


Why 34311 was dropped twice. The lab's loss model decides by sequence number and retransmission count; on_ack resets the count when new data is acknowledged, so the go-back resend of 34311 got the same decision as the original. A real network loses retransmissions too; a correct sender survives any number of consecutive losses by backing off and retrying. The double drop exposed the bug; it did not cause it.


Fix and verification. Lines 122 and 177–178: arm when sending if not armed; on a partial ACK restart, on a full ACK stop. The default build's upload under loss completes (R2: "sink replied: received 262144 bytes"). Test without loss: send data to a peer that never acknowledges; assert a retransmission within RTO and back-off to 2 × RTO.


Wrong answers. "The network drops everything after 34311": the capture shows ACKs flowing until the sender went silent. "The receiver's window is zero": every ACK shows window 65535. "Fast retransmit is broken": it worked twice (t = 1003 and 1004 ms); it cannot help when no further segments produce duplicate ACKs.


Prevention. An invariant check in timers(): snd_una != snd_max implies rto_armed; a loss test that drops the same segment several times in a row.
