Story hook

The school has an announcement system. The head teacher's office does not touch the amplifiers. It writes short instructions on numbered slips and puts them in a tray: "desk 0, unit 2: play channel 1", "desk 0, unit 3: switch the speakers on". A technician at the sound desk takes the slips in order and puts a reply slip for each one in a second tray. For the music itself the office prepares a loop of tape cut into eight equal pieces, writes on a card where each piece starts and how long it is, and tells the desk: "play this loop on channel 1, ring the bell at the end of every piece".

The office never hears the music. To know that the right music played at the right speed, someone has to record what came out of the speakers and compare it with the tape.

An HD Audio controller works this way: commands go to the codec through one ring in memory, answers come back through another, and sound flows from a list of buffers by DMA. In this chapter you write the driver, play a two-tone test signal, record it with QEMU and prove on the host that every sample arrived unchanged.

What you will be able to do

  • Reset an HD Audio controller and find its codecs from STATESTS.
  • Send codec verbs through the CORB and read responses from the RIRB.
  • Walk a codec's widget graph and choose an output path from converter to pin.
  • Build a buffer descriptor list and run an output stream with one interrupt per period.
  • Encode a stream format word and set the same format on both sides of the link.
  • Verify audio output by recording it and comparing frequencies and samples with the source.
Jargon box
HD Audio controller
Simple words: the PCI device that moves sound data and commands between memory and the audio chips. Analogy: the cable room between the office and the sound desk. Precise: a PCI function of class 04h subclass 03h whose BAR0 holds global registers, the CORB and RIRB registers and one descriptor per stream; it drives the HD Audio link to up to 15 codecs. D1
Codec
Simple words: the chip that turns numbers into an analog signal (and back). Analogy: the sound desk itself. Precise: a device on the HD Audio link at an address 0–14, described as a tree of nodes: a root node, function groups and widgets, each read with "get parameter" verbs. D1
Verb
Simple words: one command to one part of a codec. Analogy: a numbered slip in the tray. Precise: a 32-bit word: codec address (bits 31–28), node ID (27–20) and a 20-bit verb with payload: either a 12-bit verb and an 8-bit payload or a 4-bit verb and a 16-bit payload. Every verb gets exactly one 32-bit response. D1
CORB and RIRB
Simple words: the two rings in memory for commands out and answers back. Analogy: the note tray and the reply tray. Precise: the Command Outbound Ring Buffer (up to 256 4-byte verbs; software advances the write pointer, the controller the read pointer) and the Response Inbound Ring Buffer (up to 256 8-byte entries: the response and a word with the codec address and a "solicited or not" bit; the controller advances its write pointer). D1
Widget
Simple words: one building block inside a codec. Analogy: one unit on the sound desk: a player, a mixer, a socket. Precise: a node of a function group with a type (audio output converter, audio input, mixer, selector, pin complex, power, volume knob, beep) in its Audio Widget Capabilities parameter, and a connection list naming the widgets that feed it. D1
Buffer descriptor list (BDL)
Simple words: the list of memory pieces a stream plays, in order. Analogy: the card saying where each piece of the tape loop starts and how long it is. Precise: an array of 16-byte entries (64-bit address, 32-bit length, a flags word whose bit 0 is "interrupt on completion"), 128-byte aligned, at least two entries; the stream walks it cyclically up to the last valid index. D1
Stream format
Simple words: the number that says how fast, how many bits and how many channels. Analogy: the tape speed written on the label. Precise: a 16-bit word (base rate 48 or 44.1 kHz, multiply, divide, sample size, channels minus one) written identically to the stream descriptor and to the converter widget (Figure 3). D1

Layer 1 — the kid explanation

Analogy

The office writes slips and gets a reply for every slip. It prepares a tape loop cut into equal pieces and a card listing the pieces. The desk plays the pieces in order and rings a bell after each one, so the office knows which piece it may record over next. If the office writes the wrong tape speed on the label, every note comes out higher, and the whole tape ends sooner.

A computer's sound chip is a small machine of its own. The computer sends it short typed commands ("turn on", "use this speed", "listen to channel 1") and reads its replies. The music is a long list of numbers in memory, one for each tiny moment of time, and the sound hardware fetches those numbers by itself while the computer does something else. A bell (an interrupt) tells the computer each time a piece of the list has been used.

Layer 2 — the student explanation

Finding and resetting the controller

The controller is a PCI function with class 04h, subclass 03h. In the lab it is QEMU's intel-hda at 00:01.0 with BAR0 at 0xfebf8000; GCAP 0x4401 says 4 input streams, 4 output streams, no bidirectional ones and 64-bit addressing (R2). D1 R2 Reset: clear CRST (bit 0 of GCTL), wait until it reads 0, set it, wait until it reads 1, then wait for the codecs to announce themselves. Each codec that answers sets its bit in STATESTS: 0x0001 means one codec, at address 0 (R2). D1

Talking to the codec

The CORB and RIRB are rings in memory. The driver tells the controller where they are and how big (256 entries each here), resets the pointers and sets both to run. To send a verb it writes the 32-bit word into the next CORB slot and moves CORBWP; the controller sends the verb on the link, and when the codec answers, it writes the response into the RIRB and moves RIRBWP. The driver waits until RIRBWP has moved and reads the response. D1 The lab sends about 25 verbs this way, each answered within the 100 ms limit (R2).

Walking the widget graph

The root node (node 0) gives the vendor and device ID and the range of function groups; each function group gives its range of widgets. QEMU's hda-output codec (vendor 0x1af4, device 0x0012) has one audio function group at node 1 with two widgets: widget 2, an audio output converter (the DAC) with an output amplifier, and widget 3, a pin complex whose connection list names widget 2 and whose default configuration says "line out" (R2). D1 R2 The output path is "converter 2 → pin 3". A laptop codec has dozens of widgets, mixers and selectors between converters and pins; the walk is the same, the search is longer.

The stream

Output stream descriptors come after the input ones, so with 4 input streams the first output stream is SD4. The driver resets the stream, fills a BDL with 8 entries of 44160 bytes (about 0.25 s of 44.1 kHz stereo 16-bit each), writes the BDL address, the cyclic buffer length (353280), the last valid index (7) and the format (0x4011), and sets the stream number ("tag") to 1. On the codec side it tells converter 2 to listen to tag 1 with the same format, unmutes its amplifier at 0 dB and enables the pin's output. Then it sets RUN and IOCE. D1

In R2 the stream completed 8 of 8 buffer entries in 1951 ms by the kernel's PIT clock, with 8 interrupts, one MSI per entry and no FIFO error. R2 The nominal length is 2.003 s; both clocks are emulated under TCG, as in F4-11.

Proving it

QEMU's "wav" audio backend writes what the codec outputs into a WAV file. On the host, wavcheck.py finds the strongest frequency in each channel and rebuilds the kernel's samples with the same table and arithmetic. R3: left 440.0 Hz, right 660.0 Hz, and 86753 of 86753 recorded frames identical to the kernel's buffer, starting at frame 0 of the file. R3 The recording ends 1567 frames (36 ms) before the end of the buffer; this changes from run to run (1548 in R5, 1366 and 1611 in earlier runs). R5 The kernel ends QEMU within milliseconds of the last interrupt, and the missing tail is probably still in QEMU's audio buffers at that moment. That explanation was not checked.

Layer 3 — the engineer's depth

Verb encodings

Verbs with a 12-bit ID take an 8-bit payload: Get Parameter (F00h), Get Connection List Entry (F02h), Set Power State (705h), Set Converter Stream/Channel (706h: stream in bits 7–4, lowest channel in bits 3–0), Set Pin Widget Control (707h: bit 6 out enable, bit 5 in enable), Get Configuration Default (F1Ch). Verbs with a 4-bit ID take a 16-bit payload: Set Converter Format (2h), Set Amplifier Gain/Mute (3h), and the matching "get" verbs (Ah, Bh). D1 The amplifier payload has bit 15 "output", bit 14 "input", bit 13 "left", bit 12 "right", bit 7 mute and the gain step in bits 6–0. The Output Amplifier Capabilities parameter (12h) says where 0 dB is (offset, bits 6–0), how many steps there are (bits 14–8) and how big a step is (bits 22–16, in 0.25 dB units minus one). QEMU's DAC reports 0x80034a4a: mute capable, step 1 dB, 0 dB at step 74 (R2). D1 R2

Solicited and unsolicited responses

The second word of each RIRB entry holds the codec address in bits 3–0 and bit 4 "unsolicited". Codecs send unsolicited responses on their own, for example when a headphone is plugged in (jack detection), after the driver enables them with a verb. A driver that assumes "the next RIRB entry answers my last verb" breaks as soon as one arrives; the lab's driver makes that assumption and enables no unsolicited responses. D1

Positions, periods and latency

LPIB (link position in buffer) is the stream's byte offset in the cyclic buffer, updated as data goes to the link. An audio driver uses it, with the completion interrupts, to know which part of the buffer it may refill. The lab plays the buffer once and stops after eight completions; LPIB was 12 at stop (R2; 0 in R4): the stream had wrapped and started the first entry again before RUN was cleared. A player that streams a long file refills each part after its completion interrupt and never stops the stream between parts. Smaller parts lower the delay between "write samples" and "hear them" but cost more interrupts; 0.25 s parts are long for interactive sound and fine for a test. D1 R2

DMA, the IOMMU and caches

The controller reads the CORB, the BDL and the samples and writes the RIRB by DMA. The lab maps each one with the dma::map layer of F4-08. With QEMU's intel-iommu the same kernel ran with all controller DMA translated: CORB at IOVA 0x800300, BDL at 0x85d900, and the recording again identical sample for sample (R4, R5). R4 R5 On x86, PCI DMA is cache-coherent, so the driver needs only compiler barriers between writing a CORB entry and moving CORBWP. Some controllers have a "snoop" control that can turn coherence off for streams; drivers that use it must flush caches themselves. D1

Format conversion

The format word must match on both sides: the stream descriptor packs samples onto the link at its rate, and the converter turns them into sound at its own. The converter's Supported PCM Size, Rates parameter (0Ah) lists what it accepts: QEMU's codec reports 0x000201fc (R2). Read with D1's bit table from memory, that includes 44.1 and 48 kHz and 16-bit samples. A real driver checks this before choosing a format and converts the data in software when the source rate is not supported. D1 R2

Not verified — check before relying on this

The register offsets, bit positions, verb IDs, parameter IDs and payload layouts in hda.h, Figures 1–3 and this chapter are from the author's memory of D1 (High Definition Audio Specification rev. 1.0a), which was not opened in this build. They are confirmed only by QEMU 8.2.2's intel-hda and hda-output models behaving as expected (codecs found, a sensible widget walk, a stream that plays and a recording identical to the source: R2–R5). The decoding of the PCM-rates word 0x000201fc and of the amplifier capability 0x80034a4a was not checked against a second source. The explanation for the missing tail of the recording is an inference.

How the hardware actually does it

The HD Audio link is a serial bus with a 24 MHz bit clock and a 48 kHz frame: every 20.83 µs one frame carries a command slot to the codecs and, from each codec, a response slot, and then the sample data of every running stream, each stream's data packed in a block that starts with its tag. A 44.1 kHz stream cannot fill every 48 kHz frame; the controller leaves some frames without a sample for it, in a fixed pattern. D1 Each stream has a FIFO in the controller; the DMA engine fills it from memory ahead of the link, and a FIFO error means the memory reads fell behind (an underrun for output). D1

In the codec, a converter widget's DAC turns the samples into a voltage at the rate the converter's format says; amplifiers, mixers and selectors route and scale the signal, and a pin complex drives a jack or an internal speaker. The pin's default configuration, written by the board maker into the codec at boot, tells the driver what each pin is wired to: "line out, rear, green" or "internal speaker". Laptop speakers often need an extra "external amplifier power down" (EAPD) bit before any sound comes out. D1

QEMU's model is simpler: it moves samples from the stream to its audio layer, which can play them on the host or, with -audiodev wav, write them to a file. D2 Two details of the model mattered in the lab. A byte write to the stream descriptor's third byte (the stream number) had no effect, so the driver writes SD_CTL as 32 bits with a zero top byte (whose status bits are cleared only by writing 1). And the pin widget has no output amplifier (caps 0x00400101, bit 2 clear), so the driver sets gain only on widgets that report one. R2

Worked example

Task. Build by hand the three 32-bit words the driver sends to point converter 2 of codec 0 at the stream: (1) the stream ID, tag 1, channel 0; (2) the format 0x4011; (3) output amplifier, both channels, 0 dB, unmuted. Then (4) work out how long one BDL entry plays.

Step 1. Codec 0 → bits 31–28 = 0. Node 2 → bits 27–20 = 0x02, which gives 0x00200000. Verb 706h with an 8-bit payload: 0x706 << 8 = 0x70600. Payload: stream 1 in bits 7–4, channel 0 in bits 3–0 = 0x10. Word: 0x00200000 | 0x70600 | 0x10 = 0x00270610.

Step 2. The 4-bit verb 2h takes a 16-bit payload: 0x2 << 16 = 0x20000, plus 0x4011. Word: 0x00200000 | 0x24011 = 0x00224011.

Step 3. Verb 3h: 0x30000. Payload: output (bit 15) 0x8000, left (bit 13) 0x2000, right (bit 12) 0x1000, gain step 74 = 0x4A, mute bit clear: 0xB04A. Word: 0x00200000 | 0x30000 | 0xB04A = 0x0023B04A.

Step 4. One stereo 16-bit frame is 4 bytes. 44160 / 4 = 11040 frames; 11040 / 44100 = 0.2503 s. Eight entries: 2.003 s. 44160 = 345 × 128, so each part is a multiple of 128 bytes.

Check. The converter read back format 0x4011 and amplifier gain 0x4a on both channels (R2); 8 interrupts came in 1951 ms by the kernel's clock, close to 2.003 s. R2 The lab does not print the verb words themselves; add a kprintf in command() to see them (lab step 2).

Where the analogy breaks


    

  • The trays are rings, not stacks. Slips are never removed; the office and the desk each keep a pointer, and old slips are overwritten when the pointer comes round again.
    • 

  • The tape is not cut. The buffer is one area of memory; the "pieces" are entries in a list, and two entries may even point to the same memory.
    • 

  • The desk does not decide anything. A codec does what each verb says and reports facts; choosing the path and the levels is the driver's job.
    • 

  • The bell does not wait. The completion interrupt says a part is used; the stream is already playing the next part, and the driver has until that part ends to refill the old one.
    • 




Common mistakes and debugging


    

  • Symptom: STATESTS is 0 after reset. Cause: CRST never went back to 1, or the driver read STATESTS too soon. Find it: print GCTL after each step. Fix: wait for CRST to read 1, then wait at least the time D1 gives (the lab waits 2 ms).
    • 

  • Symptom: the first verb times out. Cause: CORB or RIRB not running, a wrong ring size, or the CORB read pointer still in reset. Find it: read CORBRP, RIRBWP and both control registers. Fix: follow the reset handshake in lines 163–172.
    • 

  • Symptom: the stream runs (interrupts arrive) but the recording is silent. Cause: the converter listens to a different stream tag, the amplifier is muted, or the pin output is disabled. Find it: read back the stream ID, amplifier and pin control with "get" verbs. Fix: the codec side of lines 294–302.
    • 

  • Symptom: sound plays at the wrong pitch and length. Cause: stream format and actual sample rate disagree. Find it: measure the frequency on the host. Fix: the forensic lab.
    • 

  • Symptom: a FIFO error or crackling. Cause: BDL entries not 128-byte aligned, a buffer not mapped for DMA, or (on hardware) an underrun from refilling too late. Find it: FIFOE in the stream status; with the IOMMU, a DMAR fault record. Fix: align and map; refill earlier or use larger parts.
    • 

  • Symptom: one response seems to belong to the wrong verb. Cause: an unsolicited response in the RIRB. Find it: bit 4 of the RIRB entry's second word. Fix: dispatch unsolicited responses separately.
    • 




Transition box

Where you came from: F4-08 gave you MSI and a DMA mapping layer; F4-09 and F4-10 drove rings of descriptors with ownership handed back and forth; F4-11 read a machine description at run time. What carries over: rings with producer and consumer pointers, write-1-to-clear status, MSI per completion, reading capabilities instead of assuming them. What changes: there are two devices in one: a controller you program through registers and a codec you program only through verbs carried by the controller; and the result must be checked by its timing and content, not by a reply. What comes next: F4-13 drives a device whose whole job is answering commands: the TPM, used to measure what the machine booted.

Safety
On real hardware, a stream started at full gain into headphones can be loud enough to hurt. Start at a low gain step, keep headphones off your ears for the first test, and never unmute an amplifier you have not identified from the pin configuration. On laptops, wrong verbs to vendor-specific widgets can switch internal speaker amplifiers into states the firmware does not expect.

Summary


    

  • An HD Audio controller is reset with CRST; STATESTS shows which codecs answered (R2).
    • 

  • Codecs are programmed only by verbs: the CORB carries them, the RIRB carries one response for each.
    • 

  • The widget graph is read at run time; the output path runs from a converter to a pin (R2).
    • 

  • A stream plays a cyclic buffer described by a BDL and raises an interrupt per completed entry; LPIB tracks the position.
    • 

  • The format word must say the truth on both sides: one wrong bit plays everything 8.8 % fast (R7).
    • 

  • Audio is verified by recording it: frequency for the rate, sample comparison for the data (R3).

Forensic answer key


Observation. R7: 478.9 Hz and 718.4 Hz, both "+8.8 % WRONG"; 478.9 / 440 = 718.4 / 660 = 1.088, the same ratio for both channels. Sound lasts 1.807 s against 1.967 s in R3, and 8 completions took 1805 ms against 1951 ms in R2. R6: "format 0x0011 = 48000 Hz, 16-bit, 2 ch; converter reads back 0x0011", while the PCM line says the buffer holds 44100 Hz samples.


Root cause. 48000 / 44100 = 1.088: the 44.1 kHz samples were played at 48 kHz, so every frequency rises by 8.8 % and 88320 frames take 1.840 s instead of 2.003 s. The format word lost bit 14 (BASE): 0x4011 → 0x0011. hda.cc lines 74–77, active with -DF412_RATE_BUG, set base = 0 for 44100 Hz. Both the stream descriptor and the converter received the same wrong value, so the hardware is consistent and reports no error.


Why no frame matches. The wav backend writes a 44.1 kHz file (R7's header). QEMU converted the 48 kHz stream to the file's rate, so the recorded values are interpolated, not the kernel's samples. That is the conversion, not the cause.


Injection. Built with -DF412_RATE_BUG.


Fix and verification. Remove the block (or build without the flag): format 0x4011, 440.0 / 660.0 Hz and every frame identical (R2, R3).


Wrong answers. "QEMU resamples badly": a resampler error would not produce an exact 48000/44100 ratio in both channels together with a shorter playing time measured by the guest's own clock; the guest's log names 48000 Hz. "A lost interrupt": 8 of 8 arrived.


Prevention. Print the decoded format next to the source's rate and fail when they differ; check the rate against the converter's supported-rates parameter; keep a host test that measures pitch.
