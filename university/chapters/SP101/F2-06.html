Story hook

Analogy

For years the waiters wrote orders on blank paper: "2, soup, 3, 4.0". The cooks had to guess which number was the table and which was the quantity. One night Ines printed order tickets with labelled boxes: Table, Dish, Quantity, Price each. Mistakes dropped at once, because every value now sat next to its name.

A ticket travels as one thing. You hand the whole ticket to the cook, pin it on the spike, and add it up at the end of the evening. Nobody passes four loose numbers around any more.

Then Ines redesigned the ticket and swapped two boxes. The waiters who still wrote "the first number, then the second" without looking at the labels sent soup to the wrong tables. In C++, a labelled ticket is a struct. This chapter shows how to build one, use it, store it in a vector, and avoid Ines's swapped-boxes problem.

What you will be able to do

  • Define a struct with members of different types and default values.
  • Create struct objects with designated initializers, read and change their members, and copy them.
  • Pass structs to functions by const& and &, and return them from functions.
  • Store structs in a std::vector and process them in a loop.
  • Measure a struct's size and member offsets and explain padding.
Jargon box
struct
Simple words: Your own type that groups several named values. Analogy: An order ticket with labelled boxes. Precise: A class type declared with the keyword struct, whose members are public by default; each object of the type contains one object of each data member. D1, D2
Member
Simple words: One named value inside a struct. Analogy: One labelled box on the ticket. Precise: A data member declared inside the struct, accessed with the dot operator, as in order.table (or order.quantity through a reference). D1, R1
Default member initializer
Simple words: A starting value written next to a member. Analogy: A ticket printed with "Quantity: 1" already filled in. Precise: An initializer in a member declaration, such as int quantity = 1;, used whenever an object is created without another value for that member. D2, R1
Aggregate initialization
Simple words: Filling in a struct's members with a list in braces. Analogy: Writing the values into the ticket's boxes from left to right. Precise: Initialization of an aggregate (such as a simple struct) from a braced list; the values go to the members in declaration order, and members without a value get their default member initializer. D2, R4
Designated initializer
Simple words: Naming each member as you fill it in. Analogy: Writing "Table: 2" instead of just "2". Precise: A C++20 form of aggregate initialization, {.table = 2, .dish = "soup"}; the names must follow the declaration order, which g++ checks ("designator order … does not match declaration order"). D2, R3
Padding
Simple words: Unused bytes the compiler puts between or after members. Analogy: Empty space on the ticket so that each box starts on a printed grid line. Precise: Bytes inserted so that each member starts at an offset that is a multiple of its alignment, and so that the struct's size is a multiple of its own alignment; measured with sizeof and offsetof. D3, R2
Alignment
Simple words: The rule "this type must start at an address that is a multiple of N". Analogy: Boxes that may start only on certain grid lines. Precise: The required address multiple of a type, given by alignof; 8 for double in this build. D2, R2

Words you already know: type, std::vector (KID102); const reference and pass by reference (F2-04); sizeof (F2-02).

Layer 1 — the kid explanation

So far your programs had loose variables: table, dish, quantity, price. When you have ten orders, that is forty loose variables, and it is easy to mix them up. A struct ties them together. You invent a new type, Order, with four labelled boxes. Then one variable holds a whole order.

You reach into a box with a dot: soup.table is the table of the soup order. You can copy a whole order, hand it to a function, keep many orders in a std::vector<Order>, and loop over them. R1

The safest way to fill in an order is to name each box: {.table = 2, .dish = "soup"}. Then nobody can confuse the table with the quantity. If you write only the numbers, the computer fills the boxes from left to right. If someone later changes the order of the boxes, your numbers land in the wrong ones, and the computer does not complain. R4

One surprise: a struct can take more bytes than its boxes add up to. The computer likes some values to start at special positions, so it leaves gaps. Figure 1 shows the gaps it left on our machine. R2

Layer 2 — the student explanation

Defining and creating

Listing 1 defines struct Order with four members. Three have default member initializers: table = 0, quantity = 1, price_each = 0.0; the std::string dish starts empty. Note the semicolon after the closing brace of the struct. R1, D1

Order soup{.table = 2, .dish = "soup", .quantity = 3, .price_each = 4.0}; uses designated initializers. In rice, .quantity is left out, so it keeps its default 1; add_one_more later makes it 2. The output confirms "Table 5: 2 x rice". The designators must come in declaration order: Listing 3 put .dish before .table and g++ refused. R1, R3, D2

Structs and functions

Structs follow the parameter rules of F2-04. order_total(const Order&) and print_ticket(const Order&) only read, so they take const&. add_one_more(Order&) changes the caller's order, so it takes &. make_tea_order creates an Order with defaults, fills three members and returns it by value, like an int. R1, D4

Structs in a vector

std::vector<Order> open_orders{soup, rice, make_tea_order(7)}; holds three copies. The range-for visits each by const Order&, prints it and adds its total. In R1 the totals were 3 × 4.0 = 12, 2 × 2.5 = 5 and 1 × 1.5 = 1.5, sum 18.5. R1

Positional initialization and its trap

Without names, Ticket{4, 2, "soup"} fills the members in declaration order: first member 4, second 2. That is aggregate initialization. It is short, but it depends on the order of the members. When two members have the same type (two ints here), swapping them in the struct does not cause any compiler message: the forensic program built cleanly with all course warnings and printed wrong tables. R4, D2

Size, offsets and padding

Listing 2 measures two structs with the same three members. Mixed (char, double, char) took 24 bytes, although its members add up to 10. offsetof showed why: the double starts at offset 8, not 1, and the last char at 16. Reordered (double, char, char) took 16. alignof(double) was 8 on this machine. R2 The compiler places each member at a multiple of its alignment and rounds the struct's size up to a multiple of its largest alignment, so that every element of an array of structs is aligned too. It never reorders members for you: they stay in the order you wrote them. D2, D3

Layer 3 — the engineer's depth

Note

For the curious. A struct and a class are the same kind of type in C++; the only difference is that members of a struct are public by default. SP102 adds member functions, constructors and invariants (F2-09). D1, D2 In systems programming, the layout of a struct sometimes has to match a layout fixed by hardware or a file format. The curriculum asks for "static assertions on structure offsets taken from specs" (curriculum 1.1): static_assert(offsetof(Mixed, price) == 8); would stop the build if the layout ever changed. You meet static_assert in F2-08, and object representation in depth in F2-24. D2

How the hardware actually does it

A struct object is a block of neighbouring bytes, and each member is found at a fixed offset from the start of the block: order.quantity means "start of order plus the offset of quantity". The compiler knows every offset when it translates the program, so reaching a member costs no searching. D3 Alignment exists because processors read memory in fixed-size pieces; a value that sits across the boundary of two pieces can be slower to read, and on some processors it cannot be read with a normal instruction at all. The exact rules come from the platform's ABI document, not from C++. D3, D5

Not verified — check before relying on this

The reasons given for alignment (cost of crossing a boundary; processors that refuse misaligned accesses) are stated from general knowledge and tagged only to title-only sources. Check them in the platform ABI (the System V AMD64 psABI, section on fundamental types and alignment, D5) and in Bryant and O'Hallaron's section on data alignment (D3) before relying on them; the 24 and 16 bytes of R2 are real measurements and do not depend on this box.

Worked example

Predict sizeof(Mixed) by hand from the rules, with the alignments of this build (char 1, double 8):

  1. size_code (char): offset 0, 1 byte. Next free byte: 1.
  2. price (double, alignment 8): the next multiple of 8 at or after 1 is 8. Offset 8, bytes 8–15. Padding: bytes 1–7. Next free byte: 16.
  3. spice_level (char): offset 16. Next free byte: 17.
  4. End: the size must be a multiple of the largest alignment, 8. The next multiple of 8 at or after 17 is 24. Padding: bytes 17–23.

Prediction: 24 bytes, offsets 0, 8, 16. For Reordered: price 0–7, size_code 8, spice_level 9, next free 10, rounded up to 16. Prediction: 16 bytes, offsets 0, 8, 9. The real run R2 printed exactly these values. R2

Where the analogy breaks


    

  • A paper ticket shows the label of every box to anyone reading it. In C++ the labels exist only in the source code; at run time the struct is just bytes at fixed offsets, and nothing checks that a value went into the box its writer intended (forensic lab). D3, R4
    • 

  • On paper you can leave a box blank and fill it later. A struct member always holds some value; members without a default and without an initializer may hold an unpredictable value. Give every member a default. D2
    • 

  • A printed ticket has no hidden space. A struct can contain padding bytes that belong to no member (Figure 1). R2

Summary


    

  • A struct groups named members of different types into one new type.
    • 

  • Members are reached with a dot; give every member a default.
    • 

  • Designated initializers name the members and must follow declaration order.
    • 

  • Positional braces fill members in order; reordering same-type members silently breaks them.
    • 

  • Pass structs by const& to read, & to change; return them by value.
    • 

  • Structs live happily in vectors and range-for loops.
    • 

  • A struct's size can include padding; sizeof, offsetof and alignof measure it.

Forensic lab answer key


    

  • Observation: in every line the table and the quantity are swapped: "Table 4: 2 x soup" should be "Table 2: 4 x soup", and so on. R4
    • 

  • Hypotheses: (1) "wrong data entry" — ruled out: the brace lists contain the right numbers in the old order {quantity, table, dish}. (2) "show prints the members in the wrong order" — ruled out: it prints t.table after "Table". (3) "the values now go into different members" — confirmed.
    • 

  • Root cause: {4, 2, "soup"} is positional aggregate initialization: the first value goes to the first member. In version 1 the first member was quantity; in version 2 it is table. The same unchanged line now means "table 4, quantity 2".
    • 

  • Why no warning: both members are int; the values fit either one, so the code is valid in both versions.
    • 

  • Fix: designated initializers, {.table = 2, .quantity = 4, .dish = "soup"}. They put each value into the named member; if the struct's order changes again, the compiler reports a designator-order error (R3) instead of silently moving data. The fixed program printed the correct tickets: R5
    • 







    

  • Prevention: a project rule "designated initializers for structs"; a test that creates one ticket and checks every member; and when changing a struct, search for every brace list that creates it.

  • How the evidence was made: the two int members of a working struct were swapped while the entry code was kept; the output is the real run R4.
