Story hook

Analogy

The kitchen has grown. The pastry section now works in its own room, and the dining room has a printed menu. The menu lists every dish by name and price, but it does not say how to cook anything. The recipes stay in the kitchen, each in exactly one place.

Waiters take orders from the menu, without knowing the recipes. Cooks cook from the recipes. At the end, the manager checks that every dish on an order exists in some recipe book, and that no dish has two different recipes.

A C++ program with several files works the same way. A header file is the menu: it lists names and types. A source file holds the recipes: the function bodies. The linker is the manager who matches every order to exactly one recipe. When that matching fails, you see "undefined reference" or "multiple definition". This chapter teaches you to read those messages like a detective.

What you will be able to do

  • Split a program into a header (.h), an implementation file (.cpp) and a main.cpp.
  • Explain the difference between a declaration and a definition, and the one-definition rule in simple words.
  • Write an include guard and explain the error it prevents.
  • Build a multi-file program with separate compile and link commands.
  • Decode "undefined reference" and "multiple definition" linker errors using the message, nm and c++filt.
Jargon box
Header file
Simple words: A file of declarations that other files include. Analogy: The printed menu: names and prices, no recipes. Precise: A source file, usually ending in .h or .hpp, whose text is copied into each file that names it in an #include directive. D1, D2
#include
Simple words: "Paste that file here." Analogy: Stapling a copy of the menu to your page. Precise: A preprocessor directive that replaces itself with the contents of the named file; the "units.h" form is looked up first in an implementation-defined way (GCC looks in the including file's directory, which is how R1 found it), and falls back to the <string> form, which searches the implementation's standard places. D3
Definition
Simple words: The full version of a function, with its body. Analogy: The recipe itself. Precise: A declaration that also provides the entity: for a function, the declaration together with its body. D2
One-definition rule (ODR)
Simple words: Many declarations are fine; a normal function may have only one definition in the whole program. Analogy: A dish may appear on many menus, but it has exactly one recipe. Precise: Every non-inline function used in the program must be defined exactly once across all translation units; inline functions may be defined in each unit that uses them, identically. D2, R5
Include guard
Simple words: Three lines that make a header count only once per file. Analogy: A stamp "menu already attached" so you do not staple it twice. Precise: #ifndef NAME / #define NAME … #endif around a header's contents, so that a second inclusion into the same translation unit produces nothing. D3, R4
Multiple definition
Simple words: The linker found the same function body twice. Analogy: Two different recipes for the same dish. Precise: A linker error reported when two object files both define the same non-inline symbol. R5, D4
inline (for functions)
Simple words: A word that allows the same function body in several files. Analogy: A tiny recipe printed on every menu, the same everywhere. Precise: A function specifier that permits a definition in every translation unit that uses it; the linker keeps one copy. D2, R6

Words you already know: declaration (KID102); translation unit, object file, symbol, linker, undefined reference, name mangling (F2-01); overloading (F2-04).

The idea in pictures

Figure 1 shows the unit converter of this chapter: three source files, two separate compilations, one link.

Layer 1 — the kid explanation

A big program in one file is like a cookbook with no chapters. It is hard to find things, and everyone edits the same pages. So you split it. The unit converter has three files. units.cpp knows how to turn grams into kilograms. main.cpp talks to the user. units.h is the menu between them. R1

main.cpp does not need the recipes. It only needs the menu, so it can check that you order convert with the right ingredients. The line #include "units.h" pastes the menu in. D3

Each .cpp file is translated alone. Then the linker joins the pieces, like a manager pinning every order to its recipe. If a recipe is missing, the manager shouts "undefined reference". If there are two recipes for one dish, it shouts "multiple definition". Both are easy to fix once you can read the shout. R3, R5

Layer 2 — the student explanation

What goes where

The header units.h (Listing 1) holds only declarations: double grams_to_kilograms(double grams); and so on, plus convert. Declarations end with a semicolon and have no body. The definitions, with bodies, live in units.cpp (Listing 2). main.cpp (Listing 3) includes the header and calls convert. R1, D1

units.cpp also includes its own header. Then the compiler sees each declaration and its definition in the same unit. Some mistakes, such as a different return type, are then reported at compile time. A different parameter type is not one of them: it simply declares a new overload (forensic lab). D2, R7

Building in steps

R1 compiled each .cpp with -c, then linked the two object files and ran the program on six input lines. Only files that changed need to be compiled again; the link step is repeated. R1, D3 R2 ran nm -C: in units.o, all seven functions are marked T (defined in the text section). main.o defines main and leaves other symbols U, undefined, for the linker to find. R2

Undefined reference

R3 built main.cpp alone. It compiled, because the header promised that convert exists. The linker then reported "undefined reference to `convert(double, …)'", with the file and line of the call: converter/main.cpp:14. The promise was never kept, because no object file defined it. R3

Include guards

In R4, main.cpp included recipe.h and shopping.h, and shopping.h included recipe.h again. The struct Recipe was pasted twice into one unit, and g++ reported "redefinition of 'struct Recipe'". It showed both include chains. R4 An include guard prevents this: the first time, UNITS_H is not defined, so the contents are kept and the name is defined. The second time, #ifndef UNITS_H is false and everything up to #endif is skipped. D3

Bodies in headers

An include guard works inside one translation unit only. In R5, banner.h held a full function body and was included by two .cpp files. Each object file got its own print_banner(), and the linker said "multiple definition of `print_banner()'". R5 Two fixes exist: move the body into one .cpp file and keep only the declaration in the header, or mark the function inline. R6 added inline; the program built and printed the banner twice. R6, D2

Layer 3 — the engineer's depth

Note

For the curious. Many compilers also accept #pragma once at the top of a header instead of an include guard. GCC's preprocessor manual says it "is not recognized by all preprocessors, so you cannot rely on it in a portable program"; that is why this course uses guards. D3 §2.5 The one-definition rule has a dangerous corner. If two units contain different inline definitions of the same function, the program is broken, and the linker is not required to tell you. Keep each inline function in exactly one header. D2 Real projects do not type every g++ command; a build system records which object file depends on which source and header. That comes later, in F2-26 Build systems with CMake. The curriculum's Foundations stage asks you to decode linker errors on purpose (curriculum Foundations).

How the hardware actually does it

Nothing in this chapter happens on the processor while your program runs. All of it happens earlier, in the toolchain. The preprocessor copies text, the compiler turns one unit into machine code with holes for unknown addresses, and the linker fills the holes. D4, D5 The error lines of R3 show this. "(.text+0x19d)" is the place inside main's machine code where the hole for convert's address was. The linker found nothing to fill it with. R3, D4 By the time the processor runs converter, every call is a jump to a fixed place. That is why linking problems never show up at run time. They stop the build instead.

Worked example

Read the first R3 message piece by piece:

converter/main.cpp:14:(.text+0x19d): undefined reference to `convert(double, std::__cxx11::basic_string<char, …> const&, …, double&)'

  1. Who complained? The line starts with /usr/bin/ld, and the run ends with "ld returned 1 exit status". It is the linker, so compiling worked. R3
  2. Where is the use? main.cpp line 14, the call convert(value, from, to, result). The use is not the problem; it is only where the missing thing was needed.
  3. What is missing? The demangled name. std::__cxx11::basic_string<char, …> is the long, real name of std::string, so the missing function is convert(double, const std::string&, const std::string&, double&). R3, D1
  4. Which object file should define it? units.o. R2 shows it there as T, but the command of R3 never mentioned units.cpp. R2
  5. Fix: add units.cpp (or units.o) to the command, as in R1.

Where the analogy breaks


    

  • A waiter can glance at the menu and walk to the kitchen to ask. The compiler cannot: when it translates main.cpp, it sees only that file plus what was pasted in. It never looks at units.cpp. D4
    • 

  • A real menu is one shared sheet. #include makes a separate text copy of the header in every file that includes it. That is why a body in a header becomes two bodies (R5). R5
    • 

  • A manager would notice that "grams_to_kilogram" is almost "grams_to_kilograms". The linker matches exact symbol names only; there is no "did you mean" (forensic lab). R7, R8

Summary


    

  • Headers hold declarations and struct definitions; .cpp files hold function bodies.
    • 

  • #include pastes a copy of the header into each file that includes it.
    • 

  • Each .cpp file is compiled alone; the linker matches every used symbol (U) to exactly one definition (T).
    • 

  • "Undefined reference": no definition with that exact name and parameter types.
    • 

  • "Multiple definition": two definitions; usually a non-inline body in a header.
    • 

  • Include guards stop a header being pasted twice into one unit.
    • 

  • nm -C and c++filt turn linker errors into evidence.
