Story hook

Analogy

The restaurant on the corner has a new head chef, Mrs Okafor. She reads only one language: the language of the kitchen. The cooks write their recipe cards in everyday words, so every card goes to a translator first.

Two cooks share the work. Tomás writes the card "Serve table 4". It says: "look up the price of soup on the price list". Lin writes the price list on a separate card. Tomás does not need to know the prices. He only needs to know that a price list exists.

After translation, the kitchen manager, Mr Haddad, binds all the cards into one book. He finds every note that says "look this up on another card" and writes the real page number next to it. If the price list card is missing, he cannot finish the book. He walks into the kitchen and says: "Someone told me to look up a price, but nobody gave me a price list."

A C++ program is built the same way. Today you will watch every step, and you will learn to read the manager's complaints.

What you will be able to do

  • Name the four steps that turn C++ source files into a program: preprocessing, compiling, assembling and linking.
  • Run each step on its own with g++ -E, -S and -c, and look at the files they produce.
  • Build one program from two source files, both in one command and step by step.
  • Use nm to see which names an object file defines and which ones it needs.
  • Tell a compiler error from a linker error, and explain an "undefined reference".
Jargon box
Build
Simple words: All the steps that turn your source files into a program you can run. Analogy: Translating every recipe card and binding them into one cookbook. Precise: The sequence preprocess, compile, assemble, link; g++ runs all four when you give it .cpp files and -o name. D3, R1
Preprocessor
Simple words: The first step: it handles the lines that start with #, such as #include. Analogy: A copy clerk who pastes shared pages into a recipe card before it goes to the translator. Precise: The phase of translation that executes directives such as #include (which inserts the text of a header) and produces one long text; g++ -E stops after it. D2, D3, R1
Translation unit
Simple words: One .cpp file together with everything it includes. Analogy: One recipe card after the clerk has pasted in all the shared pages. Precise: A source file plus all headers and source files included through #include, minus lines skipped by conditional directives; each one is compiled separately. D2, D1
Assembly code
Simple words: The processor's instructions written as short words you can read. Analogy: The recipe in the head chef's own kitchen language, still on paper. Precise: A text form of machine instructions (here x86-64, in the AT&T style that GCC writes); g++ -S stops after producing it. D3, D5, R1
Object file
Simple words: The machine-code version of one source file. It is not a program yet. Analogy: A translated card with blank spaces where page numbers of other cards must go. Precise: The output of compiling and assembling one translation unit (g++ -c, a .o file; on this machine an "ELF 64-bit LSB relocatable" file) holding machine code, a symbol table and notes for the linker. D3, D4, R1
Symbol
Simple words: A name that an object file offers to others, or asks others for. Analogy: A page title ("Price list") or a note "see the price list". Precise: An entry in an object file's symbol table that names a function or variable; nm marks a symbol defined in the code section with T and an undefined one with U. D4, D6, R1
Linker
Simple words: The program that joins object files into one program and connects each use of a name to its definition. Analogy: The kitchen manager who binds the cards and writes in every page number. Precise: A tool (here ld, started by g++ through collect2) that combines object files and libraries, resolves every undefined symbol to exactly one definition, and writes an executable. D4, D5, R2
Undefined reference
Simple words: The linker's message when code uses a name but no object file defines it. Analogy: "I was told to look up the price list, but nobody gave me one." Precise: A link error reported by ld as undefined reference to `name', listing the function and object file that used the name. R2, D4
Name mangling
Simple words: The way C++ writes a function's parameter types into its symbol name. Analogy: Writing "price list (by dish number)" as the page title, not only "price list". Precise: The encoding of a C++ name and its parameter types into one symbol, for example _Z10dish_pricei for dish_price(int) in this build; nm -C turns it back into readable form. R1, D7, D6

Words you already know from KID102: compiler, source code, executable, declaration, function.

Layer 1 — the kid explanation

In KID102 you typed one command, and a program appeared. That one command hides four helpers working in a row. Knowing them helps you understand error messages, because each helper complains in its own way.

The first helper is the copy clerk, called the preprocessor. It looks for lines that start with #. When it sees #include <iostream>, it pastes in a large page of shared text. Our 12-line file became more than 43,000 lines after this step. R1

The second helper is the translator, the compiler. It reads the long text and writes the same steps in the processor's own language. The third helper, the assembler, packs those words into numbers the machine can use. The result is an object file: one translated card.

The fourth helper is the kitchen manager, the linker. It takes all the translated cards and binds them into one program. Some cards say "see the price list". The manager finds the card that really contains the price list and connects the two. If no card has it, the manager stops and reports an "undefined reference". R2

Why split a program into several files at all? Two cooks can write two cards at the same time. A small change to one card means only that card is translated again. Big programs have thousands of files, so this matters a lot.

Layer 2 — the student explanation

The four steps, one command each

You can stop g++ after any step. -E stops after preprocessing and writes the expanded text; -S stops after compiling and writes assembly code; -c stops after assembling and writes an object file. Without these options, g++ also links. D3, R1

The transcript R1 shows each step on Listings 1 and 2. wc -l counted 12 lines in main.cpp and 43,178 lines in main.ii. The declaration of dish_price sits near the very end of the expanded text, after everything <iostream> brought in. R1

One file at a time

The compiler works on one translation unit at a time: one .cpp file plus everything it includes. While it compiles main.cpp, it never looks at prices.cpp. That is why main.cpp needs the line int dish_price(int dish_number);. This declaration tells the compiler the name, the parameter type and the return type. That is enough to check the call and to translate it. D1, D2, R4

Without the declaration the compiler refuses: Listing 3 calls dish_price above its definition and gets "'dish_price' was not declared in this scope". That is a compiler error. It names a file, a line and a column, because the compiler is reading source text. R4

Symbols: what a file offers and what it needs

An object file contains a symbol table. The tool nm prints it. In R1, nm -C prices.o printed T dish_price(int): the file defines this function in its code. nm -C main.o printed U dish_price(int), U std::cout and T main: it defines main and needs the others from somewhere else. R1, D6

Without -C, nm printed the raw symbol _Z10dish_pricei. C++ writes the parameter types into the symbol name; this is called name mangling. The final i stands for the int parameter in this encoding. Because of mangling, dish_price(int) and a dish_price(double) would be two different symbols. R1, D7

Linking

The linker reads all object files and matches every U with exactly one definition. Names such as std::cout are found in the C++ standard library, which g++ passes to the linker for you. When R2 linked main.o alone, dish_price(int) had no definition, and the linker printed "undefined reference to `dish_price(int)'" twice: once for each call in main. R2, D4, D5

A linker error looks different from a compiler error. It comes from /usr/bin/ld, it names an object file and a function ("in function `main'"), and it ends with "collect2: error: ld returned 1 exit status". When you see ld, think "a missing or doubled definition", not "a typo in my syntax". R2

Layer 3 — the engineer's depth

Note

For the curious. The C++ standard describes translation in eight numbered phases. Phases 1 to 4 are the preprocessor's work (phase 4 is where "preprocessing directives are executed", including #include); phase 7 translates the tokens and instantiates templates; phase 8 is linking, where "translated translation units are combined, and all external entity references are resolved". Compilers group the phases into the tools you saw. D2 §5.2 Object files on Linux use the ELF format: file called them "ELF 64-bit LSB relocatable". "Relocatable" means the addresses inside are not final yet; the linker fixes them when it decides where each piece goes. R1, D4, D5 The curriculum's Foundations section goes much deeper: sections, relocations and linker scripts (curriculum 1.1), taught in SP301.

The program does not start at main. The forensic lab shows a startup file, Scrt1.o, whose function _start refers to main. The toolchain links this file into every normal program. R5, D5

How the hardware actually does it

The processor understands only machine instructions: numbers that select an operation such as "compare", "jump" or "move". R1 shows them in readable form. dish_price became a short list of instructions: compare the argument with 1 (cmpl $1), jump if not equal (jne), put 7 into the result register (movl $7, %eax) and return (ret). Your two if statements turned into compares and jumps. R1, D5 When you run ./kitchen, the operating system copies the executable into memory and the processor starts fetching these instructions one after another. How the processor fetches and executes them is the subject of HW202; this chapter needs only one idea: the linker's job is to make every jump and every call point to the right place. D5

Worked example

Predict, step by step, what the build of Listings 1 and 2 produces, then compare with the real transcript R1.

  1. Preprocess main.cpp. The #include <iostream> line is replaced by the text of the header and everything it includes. Prediction: main.ii is much longer than 12 lines, and our own lines appear at its end. Real: 43,178 lines; dish_price appears on lines 43,171 and 43,175. R1
  2. Compile prices.cpp. Two if statements and three returns. Prediction: two compares with jumps, and the values 7, 12 and 0 moved into a register. Real: cmpl $1, cmpl $2, movl $7, movl $12, movl $0. R1
  3. Assemble both. Prediction for nm: prices.o defines dish_price(int); main.o defines main and needs dish_price(int) and std::cout. Real: exactly these, plus some standard-library names (those starting with std::). R1
  4. Link. Every U in main.o has a T in prices.o or in the standard library. Prediction: no error. Then the program computes 7 + 2 × 12 = 31. Real: "Table 4: one soup and two noodles cost 31 coins." R1, R3
  5. Leave out prices.o. Prediction: the linker cannot find dish_price(int). It is called twice in main, so expect two messages. Real: two "undefined reference" lines, then "ld returned 1 exit status". R2

Where the analogy breaks


    

  • A kitchen manager reads the cards and could guess what a cook meant. The linker reads only symbol names. If the declaration says dish_price(int) and the definition says dish_price(double), these are two different names to it (name mangling), and it will not guess. R1, D7
    • 

  • A copy clerk pastes a page once. The preprocessor pastes whatever #include names, as often as it is asked, and it does not understand C++ at all. Protecting headers from double pasting is the topic of F2-07. D2
    • 

  • In the story, translation and binding happen once. In real work you rebuild many times a day, and only the changed files are compiled again; the linker runs every time. D4

Summary


    

  • A build has four steps: preprocess (-E), compile (-S), assemble (-c), link.
    • 

  • #include pastes text; one .cpp file plus its includes is one translation unit.
    • 

  • The compiler sees one translation unit at a time, so each file declares what it uses.
    • 

  • Object files list symbols: T for "defined here", U for "needed from elsewhere".
    • 

  • C++ symbol names include parameter types (name mangling); nm -C shows them readably.
    • 

  • The linker matches every U with one definition; a missing one is an "undefined reference".
    • 

  • Compiler errors name a source line; linker errors come from ld and name symbols.
