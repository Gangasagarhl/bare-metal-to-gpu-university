Story hook

Analogy

Between the stove and the dining room there is a counter called the pass. Every plate stops there. The head chef looks at it: is it the right dish? Is it hot? Is the sauce on? If anything is wrong, she stops the plate at once and the cook redoes it. A wrong plate never reaches a guest.

One busy Friday, the owner said: "Skip the checks tonight, we are too slow." Plates flew out faster. Three of them were wrong, and nobody noticed until the guests complained.

In C++, the check at the pass is assert. A test program is the head chef tasting every dish before the restaurant opens. This chapter shows how to write those checks, what a failed check looks like, and what happens when someone turns the checks off.

What you will be able to do

  • Write assert checks for preconditions and expected results, and read the message of a failed one.
  • Write static_assert checks that run during compilation.
  • Build a separate test program for the unit converter that shares units.cpp with the real program.
  • Choose test cases: normal values, edge cases, round trips, and known reference points.
  • Explain what -DNDEBUG does to assert, and why a test must never be built that way.
Jargon box
Assertion
Simple words: A line that says "this must be true here", and stops the program if it is not. Analogy: The head chef's check at the pass. Precise: The macro assert(expression) from <cassert>; if the expression is false, it prints the file, line, function and expression, then calls std::abort. D1, R3
static_assert
Simple words: A check that the compiler does, before the program exists. Analogy: Checking the recipe card before anyone starts cooking. Precise: A declaration static_assert(constant-expression, "message");; if the expression is false, compilation fails with the message. D2, R2
Unit test
Simple words: A small check of one function, with an input and the answer you expect. Analogy: Tasting one sauce on its own. Precise: Code that calls a unit (here: one function) with chosen inputs and compares the results with expected values computed independently. D3, R1
Test program
Simple words: A second program whose only job is to run the tests. Analogy: A tasting session before opening. Precise: An executable built from the code under test plus a test file with its own main; exit code 0 means all tests passed. R1
Precondition
Simple words: What must be true before a function may be called. Analogy: "Only plates with a ticket go on the pass." Precise: A condition on the arguments or state at entry; checking it with assert documents it and catches wrong callers during testing. D3, D4
Edge case
Simple words: An input at the border: zero, empty, the smallest or largest value. Analogy: An order for zero guests. Precise: A test input at the boundary of a function's valid range or of a branch condition, where off-by-one and missing-case errors show up. D3
NDEBUG
Simple words: A switch that turns every assert into nothing. Analogy: "Skip the checks tonight." Precise: A macro name; when it is defined (for example with -DNDEBUG) before <cassert> is included, assert(e) expands to nothing and e is not evaluated. D1, R4
Floating-point tolerance
Simple words: How close two decimal numbers must be to count as equal. Analogy: "Hot enough" is a range, not one exact degree. Precise: A bound eps such that |got - expected| < eps is accepted; needed because double results carry rounding (F2-02). D5

Words you already know: undefined behaviour (F2-02); header file, linker (F2-07); return value (KID102).

The idea in pictures

Layer 1 — the kid explanation

When you finish a function, how do you know it works? You could run the program and look at the output. But looking is slow, and you forget to look again after every change. A test does the looking for you. D3

You write a line like assert(cups_needed(4) == 9);. It means: "four guests need nine cups, and if that is not true, stop right now". If the answer is right, nothing happens. If it is wrong, the program stops and tells you the file and the line. R2, R3

You collect many such lines in a test program. You run it after every change. If it prints "All unit tests passed.", you know that every check is still true. R1

Be careful with one switch, -DNDEBUG. It deletes every assert from the program. The tests then cannot fail, which also means they cannot help you. R4

Layer 2 — the student explanation

assert and static_assert

Listing 1 shows both kinds of check. static_assert(cups_per_guest > 0, "...") on line 5 is checked by the compiler. The value is a constexpr constant, so the compiler can compute it. In R5, a constant set to 0 stopped the build with "static assertion failed: a portion must weigh something". R2, R5

assert runs while the program runs. Line 9 checks a precondition, guests >= 0. Lines 15–17 check results, including the edge case of zero guests. In R3, a wrong cups_needed failed its first check. The program printed assert_fail.cpp:12: int main(): Assertion `cups_needed(0) == 1' failed. and ended with exit code 134. R2, R3 The message names the file, line, function and the exact expression. Exit code 134 is how this Linux shell reports a program stopped by the abort signal. R3, D6

A test program for the converter

Listing 2, test_units.cpp, is a fourth file for the F2-07 converter. It has its own main, so it is built with units.cpp but without main.cpp. One program can have only one main. R1 The tests are grouped into functions, one per area: mass, volume, temperature and convert. Each function contains several asserts. When all of them pass, main prints one line and returns 0. That exit code lets a script or build system know that the tests passed. R1, D3

Choosing the cases

Good tests use expected values that do not come from the code itself. The listing uses four kinds of case. Hand-worked values: 250 g = 0.25 kg. Edge cases: 0 g, and an unknown unit pair that must return false. Known reference points: water freezes at 0 °C = 32 °F and boils at 100 °C = 212 °F, and the scales meet at −40. Round trips: converting there and back must return the start value. R1, D3

Comparing doubles

F2-02 printed 0.1 + 0.2 as 0.30000000000000004, so == on computed doubles is risky. close_enough accepts a difference below 10−9. That is far smaller than any kitchen measurement, and far larger than the rounding error of these few operations. D5, R1

NDEBUG

Release builds often add -DNDEBUG, and then every assert vanishes. R4 built the failing program of R3 with -DNDEBUG. It printed "all checks passed", which was false. R4 R6 shows a second trap. When the call is inside the assert, assert(send_order_to_kitchen());, the call itself disappears too: "orders sent: 1" became "orders sent: 0". So never put work that must happen inside an assert. R6, D1

Layer 3 — the engineer's depth

Note

For the curious. assert is a tool for finding programmer mistakes, not for handling bad input from users. The converter answers "Sorry, I cannot convert" to an unknown unit; it does not assert. D4, R8 Larger projects use a test framework. It runs every test even after one fails, names each test, and counts the results. The idea underneath is the same: a call, an expected value, and a comparison. The curriculum's first milestone, P1, makes this a requirement. One of its acceptance tests reads: "The host unit-test target builds and runs a trivial passing test." (curriculum 1.6). Your test_units program is exactly such a target, on a small scale. Build systems that run tests come in F2-26.

How the hardware actually does it

An assert costs one comparison and one conditional jump when it passes. When it fails, the C library prints the message to standard error and calls abort. abort raises the signal SIGABRT. The operating system then ends the process, and nothing after the failed line runs. D1, D6 The shell reports a process ended by signal number n as exit code 128 + n. That is how R3's 134 arises, with 6 being SIGABRT on Linux. R3, D6 A static_assert costs nothing at run time. It is evaluated inside the compiler and leaves no machine code at all. D2

Not verified — check before relying on this

The chain "abort → SIGABRT number 6 → exit code 128 + 6 = 134" is stated from general knowledge. Only the final 134 was observed (R3). Confirm the signal number in the Linux signal manual page and the 128 + n rule in the bash manual (D6) before teaching it as fact. The temperature formula and the reference points used in the worked example (0 °C = 32 °F, 100 °C = 212 °F, −40 °C = −40 °F) are also from general knowledge; see the matching box in F2-07. The tests only show that the code agrees with them.

Worked example

Design the tests for celsius_to_fahrenheit before looking at its code. Work out each expected value by hand from °F = °C × 9/5 + 32:

  1. 0 °C → 0 × 9/5 + 32 = 32. This is an edge case (zero), and a known reference point: water freezes.
  2. 100 °C → 100 × 9/5 + 32 = 180 + 32 = 212. A second reference point: water boils.
  3. −40 °C → −40 × 9/5 + 32 = −72 + 32 = −40. A negative input, and the one point where both scales agree.
  4. Round trip: fahrenheit_to_celsius(celsius_to_fahrenheit(37.5)) must give 37.5 again. This checks that the two functions are inverses, without a hand-worked value.

Why several cases? A wrong formula such as °C × 5/9 + 32 still passes case 1, because 0 × anything + 32 = 32. It fails case 2. A single test proves very little. Lines 31–35 of Listing 2 contain these four checks plus the reverse reference point, and all passed in R1. R1

Where the analogy breaks


    

  • The head chef checks every plate, every evening. An assert checks only the cases that actually run. A test checks only the inputs you wrote down. Untested inputs can still be wrong. D3
    • 

  • A chef who skips checks still cooks the same food. With -DNDEBUG, code inside an assert is removed as well, so the program itself behaves differently (R6). R6
    • 

  • A stopped plate can be fixed and sent again. A failed assert ends the whole program at once (R3). R3
