Story hook

The great kitchen hall has grown. There are now four levels of planning: the head cook splits the evening's work into big trays, one per table; each table splits its tray among its rows of helpers; each row feeds the tray machine of F6-26 in small squares; and on the shelf, the jars are not stored in plain rows any more but in a pattern chosen so that a row of helpers never queues for the same shelf section.

Sizwe, the new planner, keeps all of this in his head and in scribbled sums: "row 5 of the tray is row 1 of the second square, so its jar is at 1 × 4 + 1 × 32…". When he is ill, nobody can follow the sums. His replacement, Amara, tries a different approach. She writes every arrangement as a seating chart: a short rule of two lists of numbers that says, for any row and seat, which place number it gets. Trays, rows of helpers, squares and shelves all get charts of the same kind, and the sums become something you can check by writing the chart out.

That is what NVIDIA's CUTLASS library does for GEMM: a fixed hierarchy of tiles, and, in its newer part called CuTe, one small algebra of "layouts" that describes them all. This chapter does not install CUTLASS. It builds the two ideas from scratch, checks them by brute force, and prepares you to read the real library's documentation and code.

What you will be able to do

  • Describe the GEMM hierarchy of block, warp and instruction tiles, and place F6-21 to F6-26's kernels in it.
  • Compute, for a proposed hierarchy, the warps per block, instruction tiles per warp, shared-memory bytes per stage and FLOP per byte at the warp and block levels, before writing code.
  • Write a layout as shape and stride, including nested (tiled) shapes, and evaluate it to the index table it describes.
  • Check whether a layout is a bijection onto its range, and explain what goes wrong when it is not.
  • Explain a swizzled shared-memory layout and compare it with padding using a bank-conflict count.
Jargon box
CUTLASS
Simple words: NVIDIA's open-source C++ template library for writing fast matrix multiplies and related kernels. Analogy: the hall's book of planning rules. Precise: a header library of CUDA C++ templates that organises GEMM as a hierarchy of tiles (threadblock, warp, instruction), named in the curriculum and in NVIDIA's "Efficient GEMM in CUDA" documentation; not installed or compiled in this build. C1 D1
CuTe
Simple words: the part of CUTLASS that describes how data and threads are arranged, with one kind of object called a layout. Analogy: the seating charts. Precise: CUTLASS's layout algebra (curriculum: "its CuTe layout algebra"): layouts built from shapes and strides, composed and partitioned to describe tensors and thread-to-data mappings. API names are not given here (unverified box). C1 D2
Layout
Simple words: a rule that turns a coordinate, such as (row, column), into a position in memory. Analogy: the seating chart: "row 2, seat 3 → place 19". Precise: a function from coordinates to integer offsets given by a shape (the extent of each mode) and a stride (the offset step of each mode): index = Σ coordinated × strided. Row-major 4 × 8 is shape (4, 8) with stride (8, 1). R1
Hierarchical (nested) layout
Simple words: a layout in which one dimension is itself split, for example "row inside tile" and "which tile". Analogy: "table 2, row 1, seat 3". Precise: a mode whose shape and stride are tuples, such as rows of shape (4, 2) with stride (4, 32): row r maps to (r mod 4) × 4 + (r div 4) × 32. R1
Thread–value layout
Simple words: a rule that says which thread owns which elements of a tile, and in what order. Analogy: the chart that says which helper holds which part of the tray. Precise: a layout from (thread, value) coordinates to positions in the tile; WMMA fragments (F6-26) have such a layout that the API hides; library code makes it explicit. R1
Swizzle
Simple words: shuffling the positions inside each row of a shared-memory tile so that a column read touches different banks. Analogy: storing each row's jars in a shifted order so that a column of helpers reaches different shelf sections. Precise: a bijective remapping of addresses, here column → column XOR row on a 32 × 32 float tile, which removes the 32-way bank conflict of a column read without the extra words that padding costs, under the bank model of F6-11. R1 D3
Warp tile / instruction tile
Simple words: the part of a block's output tile one warp computes, and the part one matrix instruction computes. Analogy: a row's share of the tray, and one square for the tray machine. Precise: the middle and lowest levels of the GEMM hierarchy: F6-26's kernel has a 32 × 32 warp tile made of 16 × 16 × 16 instruction tiles. R2 C1

Terms from earlier chapters: tile, bank conflict, register tiling, fragment, arithmetic intensity.

Layer 1 — the kid explanation

Analogy

Block tile = a table's tray; warp tile = one row of helpers' share; instruction tile = one square for the tray machine; layout = a seating chart, written as "how many" and "how far apart" for each direction; swizzle = storing each shelf row in a shifted order.

A big job is easier if it is cut into pieces, and the pieces into smaller pieces. The hall cuts the work three times: for each table, for each row of helpers, and for each pull of the machine's lever.

At every level somebody must know where things are. Instead of remembering sums, you write a seating chart: "four rows, eight seats; each new row adds eight, each new seat adds one". With the same kind of chart you can describe squares inside a tray, or helpers inside a row.

A chart is good if every seat gets its own place and no place is left empty. A bad chart puts two people on one chair. You can check that by writing the chart out — which a computer does in a blink.

Layer 2 — the student explanation

The hierarchy you already built

The curriculum names "the CUTLASS hierarchy (threadblock, warp, instruction-level tiles)". C1 You have built every level. F6-22 introduced the block tile staged in shared memory. F6-23's thread tiles are an instruction level of 1 × 1 × 1 (one FFMA); its warps implicitly own a band of rows of the block tile. F6-24 pipelined the block level. F6-26 made the warp tile explicit (32 × 32) and used a 16 × 16 × 16 instruction tile, but skipped shared memory. Listing 2 puts all of them in one table and adds an example that combines the best of each. R2

Each level answers three questions: what is the tile's shape, where does its data live, and how many times is each loaded value used. With block tile BM × BN × BK, warp tile WM × WN and instruction tile IM × IN × IK, a K step of the block does 2·BM·BN·BK floating-point operations. The block brings (BM + BN)·BK elements in from global memory; its warps together read (number of warps)·(WM + WN)·BK elements from shared memory (or, without a shared stage, from global memory and the L1 cache). The ratios are the FLOP per byte that each level must sustain. Listing 2 prints them.

Layouts

A layout is a function from coordinates to indices, given by a shape and a stride. Row-major 4 × 8 is (4, 8):(8, 1) and column-major is (4, 8):(1, 4) — same shape, different strides, different tables (Listing 1, parts 1a and 1b). The power comes from nesting. Write row r of an 8 × 8 matrix as the pair (r mod 4, r div 4) — "row inside the tile, which tile" — and give each part its own stride: shape (4, 2), stride (4, 32). Do the same for columns with stride (1, 16). The resulting layout stores the matrix tile after tile, row-major inside each tile (Figure 2; Listing 1, part 2). Nothing in the code that uses the layout changes: it still asks for element (r, c).

The same tool describes threads. Part 3 of Listing 1 assigns an 8 × 16 tile to 32 threads, four contiguous values each: thread t owns row t div 4, columns 4·(t mod 4) to 4·(t mod 4) + 3. This is a thread–value layout. It is the explicit form of what F6-23 wrote as index arithmetic, and of what WMMA hides inside its fragments.

Swizzling

F6-11 and F6-22 padded shared-memory tiles with one extra column to avoid bank conflicts. Part 4 of Listing 1 compares three layouts of a 32 × 32 float tile read by columns, one thread per row, under the model "32 banks, bank = word address mod 32": plain row-major puts all 32 threads on one bank; padding (row stride 33) spreads them over 32 banks at a cost of 32 extra words; the XOR swizzle — column c of row r stored at r × 32 + (c XOR r) — also gives 1 thread per bank and costs nothing, because XOR with r permutes each row. R1 Writing and reading must use the same swizzle; the layout makes that one function instead of two copies of a formula.

Layer 3 — the engineer's depth

Reading Listing 2's table

The four configurations of Listing 2 tell the story of the course in two columns. R2

  • F6-24's double-buffered 64 × 64 FP32 kernel: 16 FLOP per byte from global memory, 3.6 per byte read from shared memory by its warps. That second number is low because in F6-23 and F6-24 each warp's tile is a band of 2 thread rows × 16 thread columns covering the whole BN (Listing 2's last line); the register tile, not the warp tile, provided the reuse.
  • F6-23's 128 × 128 kernel: 32 FLOP per byte from global memory, 7.1 at the warp level.
  • F6-26's WMMA kernel: 32 per byte at the block level and 16 at the warp level, with no shared stage: every warp's loads go to global memory and the L1 cache, as sass_loop.out showed with its 16 LD.E per 8 HMMA.
  • The example: a 128 × 128 × 32 block tile with four 64 × 64 warp tiles, 16 × 8 × 16 instructions and three stages — 64 FLOP per byte from global memory, 32 per byte from shared memory, 64 instructions per warp per BK step, and 49,152 bytes of shared memory.

The arithmetic decides the design before any code exists. Doubling the block tile doubles the block-level intensity and the shared-memory size per stage. Larger warp tiles raise warp-level reuse but cost accumulator registers (64 × 64 FP32 accumulators per warp is 4,096 values, 128 per thread). More stages hide more latency (F6-24's pipeline model) but multiply shared memory, which lowers occupancy (F6-20 and F6-23's calculator). CUTLASS's template parameters are, in essence, these numbers; the library's value is that the code for each level is written once and checked, and the numbers are chosen per GPU. Whether the 16 × 8 × 16 instruction of the example exists for your target is answered by the PTX ISA (D4): F6-26's SASS mnemonic HMMA.16816 suggests such a shape on sm_80, which is an inference, not a verified fact.

Why an algebra

Layouts compose. If a tile layout maps (row, column) to a shared-memory index and a thread–value layout maps (thread, value) to (row, column), their composition maps (thread, value) directly to the shared-memory index: which address each thread touches for each of its values. Checks become mechanical. Two threads write the same address if and only if the composed layout is not injective. A column read conflicts on banks if the composed layout, taken mod 32, repeats within a warp. Listing 1 and the forensic program check such properties by evaluating the layout everywhere — brute force that is cheap for tile-sized layouts. CuTe's documentation describes a richer algebra (composition, complement, division into tiles, partitioning among threads) that does this at compile time; read it with these small examples as a guide (D2).

How the hardware actually does it

Each level of the hierarchy corresponds to a level of the memory and execution hardware. The block tile lives in an SM's shared memory, which is why its size is bounded by shared memory per SM and per block (F6-20, F6-23); its loads are the asynchronous copies of F6-24. The warp tile lives in the warp's registers: accumulators plus the current A and B fragments; it is bounded by registers per thread and spills (F6-23's forensic). The instruction tile is what one tensor-core instruction consumes from registers (F6-26). The layouts tie them together: the shared-memory layout decides bank conflicts (32 banks of 4 bytes is the model used in this course, F6-11; check your GPU's guide, D3); the thread–value layout of the copy decides coalescing and vector width (F6-23's float4 loads); and the fragment layout of the instruction decides which registers must hold which elements. None of these is visible in a naive kernel, and all of them appear as named parameters in a library kernel. That is the step from "a kernel that works" to "a kernel generator that works for many shapes and GPUs".

Worked example

Task. A colleague proposes a block tile of 256 × 128 × 32 with eight warps of 64 × 64 warp tiles, FP16 inputs, 16 × 8 × 16 instructions and four stages. Compute the warps, instruction tiles per warp per BK step, shared memory and both intensities. Use Listing 2's formulas.

  1. Warps: (256 ÷ 64) × (128 ÷ 64) = 4 × 2 = 8. ✓ matches the proposal.
  2. Instruction tiles per warp per BK step: (64 ÷ 16) × (64 ÷ 8) × (32 ÷ 16) = 4 × 8 × 2 = 64.
  3. Shared memory: stages × (BM + BN) × BK × 2 B = 4 × 384 × 32 × 2 = 98,304 B. On F6-20's example device (102,400 B per SM with 1,024 B reserved per block) that fits one block per SM.
  4. FLOP per K step: 2 × 256 × 128 × 32 = 2,097,152.
  5. Block level: global bytes per step = 384 × 32 × 2 = 24,576; intensity 2,097,152 ÷ 24,576 = 85.3 FLOP per byte.
  6. Warp level: 8 warps × (64 + 64) × 32 × 2 = 65,536 bytes read from shared memory; 2,097,152 ÷ 65,536 = 32 FLOP per byte — the same as the example of Listing 2, because the warp tile did not change.
  7. Conclusion: the larger block tile raises global-memory intensity from 64 to 85.3 but costs twice the shared memory, leaving one block per SM on the example device. Whether that trade wins depends on the GPU's memory bandwidth, its latency, and how well one block hides latency (F6-20): a measurement question.

Where the analogy breaks


    

  • A seating chart in the story is a printed table. A layout is a formula, and its table is never stored; that is the point — the index is computed when needed, often at compile time.
    • 

  • In the story every seat has a person. Real layouts can deliberately map several coordinates to the same index (a stride of 0 broadcasts one value) or leave gaps (padding). Whether a layout must be a bijection depends on its use; for storing a matrix it must be.
    • 

  • The story's levels of planning are people. In a kernel the levels are loops and template parameters of one program; nothing negotiates at run time.
    • 




Common mistakes and debugging


    

  • Mixing strides from two layouts. Symptom: wrong results for some tiles only. Cause: an inner stride taken from the untiled matrix (8 instead of 4, forensic lab). Find it: evaluate the layout at every coordinate and check it is a bijection.
    • 

  • Swizzled write, plain read. Symptom: elements permuted within rows. Cause: the swizzle written as a formula in two places. Fix: one layout function used by both.
    • 

  • Choosing tiles that do not divide. Symptom: a compile error in a library, or silently uncovered elements in your own code. Fix: check every quotient in Listing 2 is an integer, and handle the edges (F6-22).
    • 

  • Ignoring the register cost of the warp tile. Symptom: spills (F6-23's forensic). Fix: accumulator values per thread = WM × WN ÷ 32; add the fragments.
    • 

  • Treating library configurations as universal. Symptom: a configuration that was fast on one GPU is slow on another. Fix: recompute the table with the new GPU's limits and measure.
    •

Summary


    

  • A GEMM is a hierarchy: block tiles in shared memory, warp tiles in registers, instruction tiles on the tensor cores; each level has its own reuse factor.
    • 

  • Listing 2's table computes warps, instructions, shared memory and FLOP per byte per level before any code is written; the example configuration reaches 64 FLOP per byte from global memory and 32 from shared memory.

  • A layout is a function from coordinates to indices given by shape and stride; nested shapes describe tiled storage and thread–value ownership with the same object.
    • 

  • An XOR swizzle removes the column-read bank conflict of a 32 × 32 float tile without the 32 extra words that padding costs (course bank model).
    •
