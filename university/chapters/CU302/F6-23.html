Story hook

After F6-22, Amara's table group carries each jar from the pantry only once. Now the table is the crowded place: for every single multiplication, each helper reaches to the table twice, once for an amount and once for a weight. Hands are moving between table and stove all evening.

Kwame, a new helper, holds four amounts in one hand and four weights in the other. With those eight jars in his hands he can make sixteen dishes — every amount with every weight — before he reaches to the table again. His neighbour does the same with the next four weights. The table traffic drops by a factor of eight.

The catch is that hands are limited. If every helper holds sixty-four bowls of results and sixteen jars, fewer helpers fit in the hall, because the hall has only so many hands in total. And if a helper is told to hold more than his hands can carry, he puts some bowls on the floor behind him and picks them up again later — which is slow, and which nobody sees unless they look at the floor. This chapter is about holding the right number of jars, carrying four at a time, and checking the floor.

What you will be able to do

  • Explain register tiling as an outer product per k, and compute shared-memory loads per multiply-add for a TM × TN thread tile.
  • Write 1-D and 2-D register-tiled SGEMM kernels with 16-byte vectorised loads that stay correct on shapes that are not multiples of 4.
  • Read the compiler report and SASS for registers, LDS.128, LDG.E.128 and spills, and connect them to occupancy.
  • Diagnose register spills caused by __launch_bounds__ from a ptxas report and a SASS listing.
  • Argue from counted evidence why a kernel with 25 % theoretical occupancy can be the best step so far.
Jargon box
Register tiling
Simple words: each thread computes a small block of outputs and keeps them in its registers. Analogy: Kwame's sixteen dishes made from eight jars in his hands. Precise: each thread owns a TM × TN sub-tile of the block's C tile in an accumulator array that the compiler maps to registers; per k it loads TM values of A and TN values of B and performs TM·TN multiply-adds, an outer product. D2 D5
Thread tile (TM × TN)
Simple words: the outputs one thread is responsible for. Analogy: the bowls one helper fills. Precise: the TM rows × TN columns of C computed by one thread; 1-D register tiling has TN = 1, 2-D has both above 1. D5
Outer product
Simple words: multiplying every value of one short list with every value of another. Analogy: every amount in one hand with every weight in the other. Precise: for column vector a (TM) and row vector b (TN), the TM × TN matrix a·b with elements aibj; GEMM is a sum over k of outer products of a column of A and a row of B (MA201). D2
Vectorised load
Simple words: one instruction that loads several neighbouring numbers at once. Analogy: carrying four jars in one trip. Precise: a load of a 16-byte aligned float4, compiled to LDG.E.128 (global) or LDS.128 (shared) in this build; the address must be a multiple of 16 bytes. D1 R4
Register spill
Simple words: values that do not fit in registers are stored in slow memory and loaded back. Analogy: bowls put on the floor behind the helper. Precise: when the register allocator cannot keep all live values in the available registers, it stores some to local memory (per-thread memory in device DRAM, cached) with STL and reloads them with LDL; ptxas -v reports "spill stores" and "spill loads" in bytes. D1 R5
Launch bounds
Simple words: a promise to the compiler about block size, and a request for how many blocks should fit. Analogy: telling the hall manager in advance how big your table group is and how many groups you want seated. Precise: __launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor); the second argument makes the compiler limit registers per thread so that that many blocks can be resident, spilling if necessary. D1 R5

Terms from earlier chapters: occupancy and instruction-level parallelism (F6-20); spill (local memory), first met in F6-20; local memory here is GPU per-thread memory, unrelated to "local" variables in the C++ sense.

The idea in pictures

Figure 1 shows the three levels now in play. The block tile (BM × BN) lives in shared memory as BK-wide strips of A and B; each thread owns a TM × TN thread tile of C in registers; at each k a thread reads a column piece of TM values of A and a row piece of TN values of B and updates all TM·TN accumulators.

Layer 1 — the kid explanation

Analogy

Registers = each helper's hands; thread tile = the bowls one helper fills; outer product = every amount in one hand with every weight in the other; vectorised load = four neighbouring jars in one trip; spill = bowls put on the floor.

In F6-22 each helper made one dish and reached to the table twice for every step. Now each helper makes a small square of dishes. With four amounts and four weights in hand, she can make sixteen dishes before reaching to the table again.

Holding more is faster, up to a point. The hall has a fixed number of hands. If each helper holds a lot, fewer helpers fit. That is fine as long as each helper always has work ready: a helper with sixteen independent dishes rarely stands idle.

If you force more helpers into the hall than their bowls allow, they put bowls on the floor. Picking them up again is slow. The compiler tells you exactly how many bowls went to the floor, and this chapter shows you where to read it.

Layer 2 — the student explanation

From dot products to outer products

C = AB can be written as C = Σk A[:, k] B[k, :], a sum over k of outer products of a column of A and a row of B. D2 A thread that owns the TM × TN sub-tile of C at rows r…r+TM−1 and columns c…c+TN−1 needs, at each k, only A[r…r+TM−1, k] and B[k, c…c+TN−1]: TM + TN values for TM·TN multiply-adds. For 4 × 4 that is 16 multiply-adds per 8 shared-memory values; for 8 × 8, 64 per 16. In F6-22 it was one multiply-add per 2 values.

Listing 1 implements this with templates: BM × BN is the block tile, BK the depth of one shared-memory step, TM × TN the thread tile. A block has (BM ÷ TM)·(BN ÷ TN) threads: 256 for 64 × 64 with 4 × 4 and for 128 × 128 with 8 × 8. Thread tid owns thread-tile row tRow = tid / (BN/TN) and column tCol = tid % (BN/TN). Loading the BM × BK and BK × BN strips is done cooperatively by all threads in a strided loop, since there are now more elements than threads.

Why A is stored transposed

Per k, a thread reads TM consecutive rows of A at one k. In a row-major As[m][k] those are BK floats apart; in a transposed As[k][m] they are contiguous, so a thread can fetch four of them with one 16-byte shared load. The price is paid once per tile, at the store: the kernel writes A into As[k][m] element by element. B needs no transpose: its TN values per k are already contiguous in Bs[k][n]. D5

Vectorised global loads

With VEC = true, each thread reads four consecutive floats of A (along k) or of B (along n) with one float4 load. A warp's 32 float4 loads cover 512 consecutive bytes for B, so they stay coalesced (F6-08) while issuing a quarter of the instructions. D3 A float4 access must be 16-byte aligned. D1 Row starts are aligned only if the row length (K for A, N for B) is a multiple of 4, given that cudaMalloc returns suitably aligned base pointers (unverified box in Layer 3). The launcher in launchers.cuh therefore checks K % 4 and N % 4 and falls back to the scalar kernel otherwise; within a row, column offsets are multiples of 4, so with N a multiple of 4 a float4 is either wholly inside the row or wholly outside, and the zero-fill test needs only its first element.

What it costs in registers

The accumulators alone are TM·TN floats: 16 for 4 × 4, 64 for 8 × 8, plus TM + TN operand values, addresses and loop counters. The compiler report for sm_80: 75 registers for 64 × 64 / 4 × 4 scalar, 78 with float4, 77 for the 1-D kernel (8 × 1), 121 and 124 for 128 × 128 / 8 × 8 scalar and vector, all with 0 bytes of spills. R3 Listing 4 feeds these numbers to NVIDIA's occupancy calculator header with F6-20's example device: 37.5 % for the 64 × 64 kernels, 25 % for 128 × 128, against 100 % for the naive and tiled kernels. R6

Layer 3 — the engineer's depth

Lower occupancy, more work in flight

F6-20 established, with Little's law and Volkov's argument, that latency is hidden by independent work in flight, which can come from more warps (thread-level parallelism) or from more independent instructions per warp (instruction-level parallelism). D4 A thread with an 8 × 8 tile issues 64 independent FFMAs per k: the scheduler can issue one after another from the same warp without waiting for any of them, because none depends on another. A thread with one output issues one FFMA per k, and the next one depends on it through the accumulator. So 25 % occupancy with 64 independent accumulators per thread offers far more independent arithmetic than 100 % occupancy with one. What it does not offer is many warps to cover global-memory latency during the tile loads; that is what F6-24 fixes by overlapping the loads with computation.

The SASS confirms the counts

For one BK = 8 step, the 2-D 64 × 64 / 4 × 4 kernel contains 128 FFMA (4·4·8) and 16 LDS.128: per k, one 16-byte load for the four A values and one for the four B values. That is 0.125 shared-memory load instructions per FFMA, ten times fewer than sgemmTiled's 1.25. The 128 × 128 / 8 × 8 kernel has 512 FFMA and 32 LDS.128: 0.0625. R4 Note that even the "scalar" 2-D kernel uses LDS.128: the compiler vectorised the shared loads itself because the transposed layout made them contiguous and the array is declared 16-byte aligned. What VEC changes is the global side: 14 LDG.E become 14 LDG.E.128, each moving four times the data, and the B tile is stored with STS.128. R4 D6

Banks again

Two shared-memory patterns deserve a check in F6-11's model. The reads are fine: in a warp of the 64 × 64 / 4 × 4 kernel, 16 threads share a tRow and 16 consecutive tCol; their B reads Bs[k][4·tCol] as 16-byte loads cover 64 consecutive words, and their A reads are two distinct addresses, each broadcast. The transposed stores are not perfect: in the vector path, thread i stores four values to As[k..k+3][m] with m = i/2 and k ∈ {0, 4}, so in one store instruction the threads with k = 0 and k = 4 hit word addresses m and 256 + m, which are the same bank: a two-way conflict, once per tile. D3 It costs far less than the inner loop gains; a profiler will show it, and swizzled layouts (F6-27) remove it.

Launch bounds and spills

__launch_bounds__(256, MINB) tells the compiler the block size and asks for at least MINB resident blocks per SM. D1 With MINB = 1, ptxas used 124 registers for the 128 × 128 kernel; with MINB = 4 it limited itself to 64 registers, which needs 408 bytes of stack and produces 1,336 bytes of spill stores and 1,204 bytes of spill loads per thread. R5 The SASS counts confirm it: 0 LDL / 0 STL without the bound, 301 LDL / 334 STL with it, around the same 512 FFMA. Local memory is per-thread memory in device memory, cached in L1 and L2; every LDL in the inner loop adds a load with cache or DRAM latency in front of an FFMA that needs its value. D1 Listing 4 shows what the bound bought: 50 % theoretical occupancy instead of 25 %. Whether that trade wins is a measurement, and the course forensic lab below asks you to predict it from evidence. Volkov's talk is the classic warning against chasing occupancy at the cost of registers. D4

Not verified — check before relying on this

Three platform facts used above were not read in a document during this build: (1) the alignment that cudaMalloc guarantees for returned pointers (the kernels need 16 bytes; check the CUDA Runtime API reference for cudaMalloc and the Programming Guide's device-memory section); (2) whether local memory is cached in L1 on your GPU generation (check the Programming Guide's "Local Memory" section and the tuning guide for your architecture); (3) the size of the register file per SM of your GPU (read regsPerMultiprocessor from cudaGetDeviceProperties). The register and spill numbers in this chapter are the compiler's own reports for sm_80 and are not affected.

How the hardware actually does it

Registers are the fastest storage on the GPU; each thread's registers are allocated from the SM's register file when its block becomes resident, for the block's lifetime. D1 An FFMA reads its three operands from registers; an LDS.128 moves 16 bytes from shared memory into four consecutive registers in one instruction, and LDG.E.128 does the same from global memory. D6 Fewer, wider load instructions mean fewer issue slots spent on loads, which matters once the FMA pipeline is the target. The register file is shared by all resident warps, which is the exact mechanism behind "using more per helper means fewer helpers fit in the hall": the occupancy calculator in Listing 4 divides the register file by registers per warp, rounded to the allocation unit that the header uses for compute capability 8.x (F6-20). R6 When the compiler is told to use fewer registers than the code needs, the overflow goes to local memory, which lives in device memory and is reached through the caches like any other load. D1

Worked example

Task. For the 128 × 128 / 8 × 8 kernel with BK = 8 at n = 4,096: count FFMAs and shared-memory loads per thread per BK step, the global intensity, the minimum registers for the data alone, and the theoretical occupancy on the example device.

  1. Threads per block: (128 ÷ 8)·(128 ÷ 8) = 256. Per BK step per thread: 8 × 8 × 8 = 512 FFMA. Shared loads: per k, 8 A values (two LDS.128) and 8 B values (two LDS.128) = 4 instructions, × 8 = 32 LDS.128. Ratio 32 ÷ 512 = 0.0625, as the SASS shows. R4
  2. Global intensity: the 128 × 128 block tile of F6-21's Listing 4: 31.5 FLOP/byte at n = 4,096 (it does not depend on the thread tile). R2
  3. Registers for data: 64 accumulators + 8 + 8 operand values = 80. The compiler used 124: the rest holds addresses, indices and loop state. R3
  4. Registers per block: 124 × 256 = 31,744. With the example device's 65,536 registers per SM, two blocks fit (63,488) and a third does not: 2 × 8 warps = 16 of 64 warps = 25 %, as Listing 4 prints. R6
  5. To fit four blocks, a thread may use at most 65,536 ÷ (4 × 256) = 64 registers (Listing 4's sweep agrees: 64): exactly the 64 that ptxas chose for MINB = 4, at the price of the spills. R5 R6

Where the analogy breaks


    

  • Helpers' hands in the story hold any number of jars a little less comfortably. Registers are all-or-nothing per block: one register more per thread can drop a whole block from the SM (Listing 4: 124 registers allow two blocks, 128 would still allow two, but the allocation is rounded per warp, so the steps are discrete).
    • 

  • A helper who puts bowls on the floor knows where they are and picks them up herself. Spilled values go to local memory, which is device memory behind the caches: the "floor" is shared with every other thread's traffic and may be far away.
    • 

  • In the story, more helpers always keep the hall busier. On a GPU, independent instructions inside one warp hide latency as well as more warps do, so fewer helpers with more independent dishes each can be faster (F6-20).
    • 




Common mistakes and debugging


    

  • Accumulator array in local memory without any bound. Symptom: ptxas -v shows a stack frame and LDL/STL in the SASS even with MINB = 1. Cause: an index into acc that is not a compile-time constant after unrolling (a loop without #pragma unroll or with a runtime trip count). Fix: constant trip counts and full unrolling; check the report after every change.
    • 

  • float4 on unaligned rows. Symptom: works for 64³, fails with a misaligned-address error (GPU) or wrong values for K = 65. Fix: the launcher's fallback, or pad rows to a multiple of 4.
    • 

  • Forgetting the transposed store. Symptom: the emulator reports most elements outside the bound. Cause: As[m][k] written, As[k][m] read. Find it: the emulator on 17 × 13 × 9 fails immediately.
    • 

  • Using MINB to "fix" low occupancy. Symptom: occupancy up, time worse (to be measured). Evidence: spill bytes in the report. Fix: remove the bound, or reduce the thread tile and compare in the step table.
    • 

  • Too few threads to load the strips. Symptom: wrong results for some configurations. Cause: assuming one element per thread when BM·BK exceeds THREADS. Fix: the strided loading loops of lines 27 and 49.
    •

Summary


    

  • Register tiling makes each thread compute a TM × TN outer product per k: TM·TN multiply-adds for TM + TN shared values.
    • 

  • The SASS shows 0.125 shared loads per FFMA for 4 × 4 and 0.0625 for 8 × 8, against 1.25 for the shared-memory-tiled kernel.
    • 

  • Storing A transposed in shared memory makes a thread's A values contiguous, so they load as LDS.128.
    • 

  • float4 global loads need 16-byte alignment; the launcher falls back to scalar loads when K or N is not a multiple of 4.
    • 

  • Registers rise to 75–124 per thread and theoretical occupancy falls to 25–37.5 % on the example device; the independent FMAs per thread hide latency instead.
    • 

  • __launch_bounds__(256, 4) forces 64 registers and produces 1,336 bytes of spill stores and 301 LDL: read the compiler report before trusting an occupancy "fix".
