Story hook

A new machine arrives in the great kitchen hall. You load it with a small square tray of amounts and a small square tray of weights, press one lever, and it adds every amount-times-weight combination into a third tray at once. One row of helpers operates it together: every helper of the row holds part of each tray, and the machine only starts when the whole row pulls the lever at the same moment.

Esperanza, who runs the evening's table, is delighted, until she reads the label. The machine takes trays of exactly sixteen by sixteen. It accepts only the light measuring cups of F6-25 for the inputs, and it keeps its totals in the finely marked bowl. Which helper holds which part of the tray is "the machine's business": the manual says not to rely on it.

And there is a warning sticker on the back: "In halls built before a certain year, this lever does nothing." Esperanza's colleague later finds out what that means the hard way — by bringing a recipe written for an old hall into a new one. This chapter puts the machine to work through NVIDIA's WMMA interface, proves from the compiler's output that it is really being used, and shows how a build flag can quietly take it away.

What you will be able to do

  • Write a mixed-precision GEMM (FP16 or BF16 inputs, FP32 accumulation) with nvcuda::wmma fragments, load_matrix_sync, mma_sync and store_matrix_sync.
  • Explain the warp-level contract of WMMA: all 32 threads participate, fragment contents are opaque, shapes and types are restricted.
  • Prove from PTX and SASS that the kernel uses tensor-core instructions in its inner loop, as milestone E7 requires.
  • Test the kernel with the tolerance derived in F6-25 and check its index arithmetic without a GPU.
  • Diagnose a build that contains no tensor-core instructions from cuobjdump evidence.
Jargon box
Tensor core
Simple words: a unit in the GPU that multiplies small matrices in one operation. Analogy: the tray machine. Precise: NVIDIA's name for the matrix-multiply-accumulate units of its GPUs, which compute D = A·B + C on small fixed-size tiles for specific input and accumulator types; reached from CUDA C++ through the WMMA API, PTX wmma/mma instructions or libraries. AMD calls its equivalent matrix cores (F7). D1 D2
WMMA
Simple words: NVIDIA's C++ interface for warp-wide matrix multiplies. Analogy: the lever and the instructions for the tray machine. Precise: warp matrix multiply-accumulate: the nvcuda::wmma namespace of mma.h, with class template fragment and the functions fill_fragment, load_matrix_sync, mma_sync and store_matrix_sync (all present in the CUDA 12.0 header read in this build). H1 D1
Fragment
Simple words: a piece of a small matrix spread over the registers of the 32 threads of a warp. Analogy: the part of each tray that each helper of the row holds. Precise: wmma::fragment<Use, m, n, k, T, Layout>, where Use is matrix_a, matrix_b or accumulator; each thread holds num_elements values whose mapping to matrix positions is not specified by the API. H1 D1
Leading dimension (ldm)
Simple words: how far apart, in elements, two consecutive rows (or columns) are in memory. Analogy: how many jars to skip on the shelf to get to the next row of the tray. Precise: the stride passed to load_matrix_sync and store_matrix_sync: for a row-major M × K matrix A, the leading dimension is K. D1
HMMA
Simple words: the machine instruction that runs a half-precision-input matrix multiply on the tensor cores. Analogy: one pull of the lever. Precise: the SASS mnemonic seen in this build for sm_80 and sm_90: HMMA.16816.F32 (FP16 inputs, FP32 accumulate) and HMMA.16816.F32.BF16; each 16 × 16 × 16 wmma.mma.sync became two of them. R3 D3
Compute capability / -arch
Simple words: the version number of a GPU's feature set, and the compiler option that chooses which one to build for. Analogy: the year the hall was built, and which hall the recipe is written for. Precise: sm_XY names the target; __CUDA_ARCH__ is defined in device code to the target's value (800 for sm_80); a binary carries machine code (cubin) for the targets it was built for and PTX that the driver can compile later. D1 R5

Terms from earlier chapters: mixed precision, tolerance (F6-25); register tiling (F6-23). "Warp" here is the NVIDIA term for 32 threads that execute together; AMD's wavefront is the similar group (F7).

The idea in pictures

Figure 1 shows how Listing 1 divides C. A block of four warps computes a 64 × 64 tile; each warp computes a 32 × 32 tile, held as 2 × 2 accumulator fragments of 16 × 16; along K the warp loads two A fragments and two B fragments per step of 16 and issues four mma_sync.

Figure 2 shows what a fragment is, using Listing 4's survey of the header: the 32 threads of a warp jointly hold a 16 × 16 tile, but how many values each holds — and which ones — is the library's business.

Layer 1 — the kid explanation

Analogy

Tensor core = the tray machine; fragment = the part of a tray each helper of the row holds; mma_sync = the whole row pulling the lever together; load_matrix_sync / store_matrix_sync = filling and emptying the trays in the machine's own order; -arch = which hall the recipe is written for.

Until now, every helper multiplied numbers one pair at a time. The tray machine multiplies a whole small square of pairs and adds them all up in one go. It is much faster, but it is picky: exact tray sizes, light cups only for the inputs, a fine bowl for the totals.

A whole row works the machine together. If one helper of the row is missing, the machine does not work properly, so the recipe must make sure the whole row is there.

The trays are filled by the machine's own loading tool. Nobody needs to know which helper holds which number, and nobody should rely on it.

Layer 2 — the student explanation

The four calls

The WMMA API declares, in mma.h: a class template fragment<Use, m, n, k, T, Layout>; fill_fragment(frag, value); load_matrix_sync(frag, pointer, ldm) for A and B fragments (and an overload with a layout argument for accumulators); mma_sync(d, a, b, c), computing d = a·b + c; and store_matrix_sync(pointer, frag, ldm, layout). H1 For 16-bit inputs the CUDA 12.0 header defines the shapes m × n × k = 16 × 16 × 16, 32 × 8 × 16 and 8 × 32 × 16, for both __half and __nv_bfloat16 (the BF16 ones, and TF32 with 16 × 16 × 8, only when __CUDA_ARCH__ >= 800 or in host code), with row_major or col_major layouts for A and B. H1 The suffix _sync means that all threads of the warp must call the function together with the same arguments; the functions are collective over the warp. D1

The kernel

Listing 1 is the "WMMA version first" of E7. C1 Warp w = threadIdx.x / warpSize of a 128-thread block takes the 32 × 32 sub-tile at row (w / 2)·32, column (w % 2)·32 of the block's 64 × 64 tile. It zero-fills four FP32 accumulator fragments, then for each k in steps of 16 loads two A fragments (rows r and r + 16, row-major with leading dimension K) and two B fragments (columns c and c + 16, row-major with leading dimension N), and performs four mma_sync. At the end it stores the four accumulators to C as row-major with leading dimension N. All conditions in the kernel depend only on warp-uniform values (warpRow, warpCol, k), so either the whole warp calls a WMMA function or none of it does.

The kernel requires M, N and K to be multiples of 16; the launcher refuses other shapes. Real libraries pad or use predicated loads for the edges; padding is the lab extension. Pointer arithmetic such as A + r * K + k with r, k and K multiples of 16 keeps every fragment pointer a multiple of 16 elements (32 bytes) from the base; the alignment rules for load_matrix_sync are stated in the Programming Guide (unverified box below).

The test

Listing 2 rounds random FP32 values in [−1, 1] to the input type on the host, keeps the FP32 originals for the FP64 reference, and judges each element of C against F6-25's bound [(2uin + uin2)(1 + γK) + γK]Σ|ab|, with uin = 2−11 for FP16 and 2−8 for BF16 and FP32 accumulation. R1 It then times the kernel at n = 1,024, 2,048 and 4,096 against cublasGemmEx with the same input type, FP32 output and FP32 compute, using F6-21's row-major trick. On this build it stops at the first runtime call, so the correctness of the index walk is checked separately by Listing 3 on the CPU: for six shapes, every element of C is written exactly once, no fragment load reaches outside A or B, and the number of mma_sync calls is M·N·K ÷ 4,096. R2

Layer 3 — the engineer's depth

From mma_sync to HMMA

The PTX for sm_80 contains wmma.mma.sync.aligned.row.row.m16n16k16.f32.f32 in the FP16 kernel and wmma.mma.sync.aligned.row.row.m16n16k16.f32.bf16.bf16.f32 in the BF16 kernel: the instruction name carries the layouts (row, row), the shape and the types. R3 D2 The FP16 kernel's PTX has 12 of them and the BF16 kernel's 4: the compiler unrolled the K loop differently for the two types (these are static counts in the code, not executed counts). In the SASS for both sm_80 and sm_90, each became two instructions: 24 HMMA.16816.F32 and 8 HMMA.16816.F32.BF16. R3 The "16816" reads naturally as an m16 n8 k16 operation, so one 16 × 16 × 16 product is two halves of 8 columns; that reading of the mnemonic is an inference, to be confirmed in the SASS reference (D3).

E7 asks that "the disassembly shows the matrix instructions in the inner loop". C1 The sass_loop step finds the main loop of the BF16 kernel (the backward branch @P5 BRA 0x590 at 0x0ac0) and lists its loads and tensor-core instructions: 8 HMMA.16816.F32.BF16 per iteration, preceded by 16 LD.E loads of 4 bytes each. R4 That is the evidence E7 wants — and it also shows this first version's weakness.

Why this first version is slow by design

Three things in the SASS loop deserve attention. The loads are LD.E, generic loads, not LDG: the compiler did not prove that the pointers point to global memory. They are 4 bytes each: two 16-bit elements per load, so a warp issues 16 load instructions per step of 16 in K for its four fragments. And they come straight from global memory: each A fragment is re-read by every warp and block that needs it, with no shared-memory reuse beyond what the warp tile gives (16 FLOP per byte read at the warp level, 32 per byte for the block, in F6-27's Listing 2). R4 R7 Everything F6-22 to F6-24 taught applies again: stage A and B tiles through shared memory with asynchronous copies, give each warp a larger tile of fragments, load fragments from shared memory with wide loads. Library kernels do all of this and more; F6-27 reads how CUTLASS organises it. The lab's measurements against cuBLAS will show how much this matters on your GPU.

The architecture guard

BF16 fragments exist in mma.h only for __CUDA_ARCH__ >= 800. H1 Listing 1 therefore compiles its body only for those targets and otherwise executes __trap(), so that a wrong build fails loudly instead of writing nothing (the harness would then find NaN everywhere, because C is poisoned). The forensic lab shows why this guard matters: a build without -arch produced machine code for sm_52 and PTX for sm_52 only, and both contain the trap path. R5 If the driver compiles that PTX for a newer GPU at load time, it compiles the code as written for sm_52 — with __CUDA_ARCH__ already fixed at 520 — so the trap remains. D1

How the hardware actually does it

A tensor-core instruction is issued by one warp and computes a small matrix product whose operands are spread over the registers of the warp's 32 threads; the hardware gathers them, multiplies, accumulates and scatters the result back into registers. D1 D2 In the SASS line HMMA.16816.F32.BF16 R8, R44.reuse, R54, R8, R8 is both the accumulator input and output, R44 holds A-fragment data and R54 B-fragment data, each naming the first of a group of consecutive registers; .reuse is an operand-reuse hint seen in this SASS. R4 D3 One HMMA replaces many FFMA: a 16 × 8 × 16 product is 2,048 multiply-adds, so if the reading of "16816" above is right, one instruction does the work that F6-23's kernel needed 2,048 FFMA instructions spread over a warp for (64 per thread). The arithmetic has moved from the FMA units to the tensor cores; the data movement has not changed, which is why staging through shared memory matters even more here than for SGEMM. Throughput per SM and per format is a product fact: your GPU's whitepaper.

Worked example

Task. For M = 112, N = 208, K = 96 (one of the test shapes), compute the grid, the number of warps that do work, the number of mma_sync calls, and the number of HMMA instructions executed on sm_80; then the bound for a BF16 element with Σ|ab| = 24.

  1. Grid: ⌈208 ÷ 64⌉ × ⌈112 ÷ 64⌉ = 4 × 2 = 8 blocks, 32 warps.
  2. Warps with work: warp rows start at 0, 32, 64, 96 (all < 112); warp columns at 0, 32, …, 224 — 224 ≥ 208, so the last column of warps returns. 4 × 7 = 28 warps work.
  3. mma_sync calls: 112 × 208 × 96 ÷ (16 × 16 × 16) = 2,236,416 ÷ 4,096 = 546, as Listing 3 prints. R2 (The warps on row 96 and column 192 have only one fragment row or column inside C, which is why the count is not 28 × 4 × 6.)
  4. HMMA executed: 2 per mma_sync on sm_80 (R3): 1,092.
  5. Bound factor for BF16, K = 96: 2uin + uin2 = 0.0078278; γ96 = 96 × 2−24 ÷ (1 − 96 × 2−24) = 5.722 × 10−6; factor ≈ 0.0078278 × 1.0000057 + 0.0000057 = 0.0078336. Tolerance for Σ|ab| = 24: 0.188.

Where the analogy breaks


    

  • The tray machine in the story is one machine shared by the hall. Tensor cores are part of every SM, and each warp issues its own instructions to them; there is no queue for "the" machine.
    • 

  • Helpers in the story load the trays by hand. Fragments live in the warp's registers; "loading the tray" is an ordinary load instruction (here 16 LD.E per step), so the machine is only as fast as the loads that feed it.
    • 

  • The story's warning "in old halls the lever does nothing" suggests a harmless no-op. In Listing 1's default build the kernel traps; without the guard, a WMMA kernel for an unsupported target would not compile at all (the fragment types do not exist there), which is the better outcome.
    • 




Common mistakes and debugging


    

  • No -arch. Symptom: the kernel traps (with Listing 1's guard) or fails to compile (without it). Find it: cuobjdump -lelf and -lptx on the binary, and a grep HMMA on its SASS (forensic lab). Fix: -arch=sm_XY for your GPU, or a -gencode list.
    • 

  • Divergent WMMA calls. Symptom: wrong results or a hang. Cause: a per-thread condition around load_matrix_sync or mma_sync. Fix: conditions on warp-uniform values only.
    • 

  • Wrong layout tag. Symptom: results look like A·BT or a transposed C. Cause: col_major fragment for row-major memory, or the wrong mem_*_major in the store. Find it: a non-symmetric test (M ≠ N, identity-like B).
    • 

  • Wrong leading dimension. Symptom: correct for square shapes only. Cause: ldm = M instead of K for A. Fix: ldm is the distance between consecutive rows of the stored matrix.
    • 

  • Element-wise code that assumes a fragment order. Symptom: works for FP16, wrong for BF16 (Listing 4 shows why). Fix: only position-independent operations on frag.x[i] (scaling, activation), or go through shared memory.
    • 

  • Comparing FP16 results with the FP32 tolerance. Symptom: "failures" everywhere. Fix: F6-25's bound with uin.
    •

Summary


    

  • WMMA exposes tensor cores as warp-wide operations on fragments: fill_fragment, load_matrix_sync, mma_sync, store_matrix_sync.
    • 

  • Fragments are opaque: the header gives 16 values per thread for an FP16 A fragment and 8 for BF16; never depend on their order.
    • 

  • In this build each 16 × 16 × 16 mma_sync became two HMMA.16816 instructions on sm_80 and sm_90; the BF16 main loop holds 8 HMMA fed by 16 LD.E.
    • 

  • The test uses F6-25's bound; the index walk is verified on the CPU (every element once; M·N·K ÷ 4,096 mma_sync).
    • 

  • A build without -arch contained only sm_52 code and PTX with 0 HMMA and the trap; the driver's later compilation cannot add what the PTX does not contain.
    • 

  • This first version loads fragments straight from global memory; staging and pipelining (F6-22 to F6-24, F6-27) are what libraries add.
