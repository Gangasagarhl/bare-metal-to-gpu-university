Story hook

Every evening the great kitchen hall makes a table of results: for every guest (a row) and every dish (a column), a score made by combining one long list of ingredient amounts with one long list of ingredient weights. Ingrid, a new helper, gets one cell of the table. She walks to the far pantry for the first amount, walks back, walks again for the first weight, multiplies, adds, and starts over for the second ingredient.

Next to her, a thousand other helpers do the same for their own cells. Most of them fetch exactly the jars that their neighbours fetched a minute ago: everyone on Ingrid's row needs the same amounts, and everyone in her column needs the same weights. The road to the pantry is jammed, and the stoves are mostly cold.

The recipe is right. Every cell will be correct. But for each multiplication, two trips to the pantry are made, and the pantry road, not the stove, decides when dinner is served. This chapter measures how bad that is, with arithmetic rather than opinion, and sets up the table on which the rest of the course will record every improvement.

What you will be able to do

  • Write a naive SGEMM kernel with correct indexing, bounds checks and coalesced access to B and C.
  • Test any GEMM kernel against an FP64 reference on awkward shapes with an error bound derived from the arithmetic, both on the GPU and on the university's CPU emulator.
  • Compute the arithmetic intensity of a GEMM for naive access, for block tiles of a given size, and for compulsory traffic, and place each on a roofline.
  • Use the E6 harness: correctness on a shape matrix, registers and occupancy, and median time against cuBLAS at three sizes.
  • Read the naive kernel's PTX and SASS and count loads per multiply-add.
Jargon box
SGEMM
Simple words: the single-precision matrix multiply. Analogy: the whole evening's table of guest-by-dish scores. Precise: single-precision general matrix multiply, C = αAB + βC in the BLAS interface; here α = 1, β = 0, row-major, M × K times K × N, 2MNK floating-point operations (as defined in F2-56). D3
Naive GEMM
Simple words: the first, simplest GPU version: one thread per result, reading everything from global memory. Analogy: Ingrid walking to the pantry twice for every multiplication. Precise: a kernel in which thread (i, j) computes Cij = Σk AikBkj by loading each operand from global memory; it requests 2K loads per output for 2K floating-point operations. D2 R3
Arithmetic intensity
Simple words: how much arithmetic a program does for each byte it moves. Analogy: how many dishes a cook prepares per jar carried from the pantry. Precise: the ratio of floating-point operations to bytes of memory traffic, in FLOP/byte; which traffic is counted (DRAM, a cache level; compulsory only or measured) must be stated (as in F2-56). D4
Compulsory traffic
Simple words: the bytes you must move even with a perfect cache: every input read once, every output written once. Analogy: every jar carried exactly once, no matter how many dishes use it. Precise: for SGEMM, 4(MK + KN + MN) bytes; it gives the highest intensity any implementation can reach for that traffic level. D4 R2
Roofline model
Simple words: a drawing that says the best speed a kernel can reach is set either by arithmetic or by memory, whichever is lower. Analogy: the stove's limit versus the pantry delivery limit. Precise: attainable performance = min(peak FLOP/s, arithmetic intensity × peak bandwidth), drawn on log–log axes (as in F2-56). D4
cuBLAS
Simple words: NVIDIA's library of tuned linear-algebra routines for its GPUs. Analogy: the master chef's recipe book, against which you time your own cooking. Precise: NVIDIA's GPU implementation of the BLAS interface (plus extensions), column-major; its cublasSgemm is E6's reference for both correctness at large sizes and speed. D5
Speed table (E6)
Simple words: one line per version of the kernel, with its speed and the evidence explaining it. Analogy: the kitchen's logbook of every change to the recipe and how long dinner took. Precise: the log that milestone E6 requires: per step, correctness on the shape matrix, registers and occupancy, median time and GFLOP/s at three sizes, percentage of cuBLAS, and the profiler evidence for the change. The idea in pictures

Figure 1 shows what one thread of the naive kernel reads: a whole row of A and a whole column of B, to produce one element of C. Its neighbours in the same warp (same row of C, next columns) read the same row of A again and neighbouring columns of B. The only reuse is whatever the caches happen to keep.

Figure 2 places the intensities that Listing 4 computes on a roofline with symbolic roofs: the slanted memory roof is bandwidth × intensity, the flat roof is peak arithmetic. Your GPU's two roofs come from its datasheet and your own E2 bandwidth measurement; this chapter does not draw them with numbers.

Layer 1 — the kid explanation

Analogy

Thread = one helper; one element of C = one cell of the score table; a row of A and a column of B = the two lists of jars that cell needs; global memory = the big pantry far away; arithmetic intensity = dishes per jar carried; roofline = the stove's limit versus the pantry delivery limit.

Each cell of the table needs a whole row of amounts and a whole column of weights. If every helper fetches their own jars, the same jars are carried again and again: everybody in a row needs the same amounts.

The kitchen has two limits. The stoves can only cook so fast, and the road can only carry so many jars per minute. If you cook very little per jar, the road decides your speed and the stoves wait. If you cook a lot per jar, the stoves decide.

The naive recipe cooks one multiply-and-add per two jars. That is about the worst ratio possible. The rest of this course is about carrying each jar once and using it many times.

Layer 2 — the student explanation

The kernel

Listing 1 launches a 2-D grid of 16 × 16 blocks; thread (threadIdx.x, threadIdx.y) of block (blockIdx.x, blockIdx.y) computes column col and row row of C (F6-02). D1 All three matrices are row-major: element (i, k) of A is at A[i * K + k]. Neighbouring threads in x are neighbouring columns, so a warp's loads of B[k * N + col] touch 32 consecutive floats (coalesced, F6-08), and its loads of A[row * K + k] all touch one address. D2 The bounds check row < M && col < N lets the grid be larger than C.

The indices are int. The largest index used is below M·K, K·N or M·N, so the kernel is correct while those stay below 231; at 4,096 × 4,096 they are 224. A library kernel would use 64-bit offsets (13.4 code rules).

Counting operations and bytes

SGEMM does M·N·K multiply-adds; counting each as two floating-point operations gives 2MNK FLOP. D3 Each naive thread requests 2K floats (8K bytes) and writes 4 bytes, so for square n the requested traffic is 8n3 + 4n2 bytes and the intensity of requests is just under 0.25 FLOP/byte. R2 Compulsory traffic is 12n2 bytes (three matrices once), giving n/6 FLOP/byte: 170.7 at n = 1,024 and 682.7 at 4,096. R2 The gap between 0.25 and 683 is the reuse that a GEMM kernel can win.

A block that computes a BM × BN tile of C must bring in a BM × K strip of A and a K × BN strip of B. Its intensity against global memory is 2·BM·BN·K ÷ (4·K·(BM + BN)) = BM·BN ÷ (2(BM + BN)): 4 for 16 × 16, 8 for 32 × 32, 16 for 64 × 64, 32 for 128 × 128, plus the small effect of writing C. Listing 4 prints exactly these, with C included. R2

The roofline

The roofline model bounds attainable performance by min(peak, intensity × bandwidth). D4 The ridge point, peak ÷ bandwidth, is where the two roofs meet. A kernel whose intensity is below the ridge cannot exceed intensity × bandwidth, however good its arithmetic. You built the CPU version in F2-56; on a GPU the bandwidth is the E2 measurement from F6-09 and the peak comes from the GPU's documented specifications (with FMA counted as two operations), recorded in your dossier.

Not verified — check before relying on this

Peak FP32 throughput and DRAM bandwidth of a real GPU are product facts (AH-21). Take them from the NVIDIA datasheet or architecture whitepaper for your exact GPU, record the document and section in the dossier, and use your own E2 measurement as the practical memory roof. This chapter deliberately draws the roofs without numbers.

Layer 3 — the engineer's depth

Requested bytes are not DRAM bytes

The 0.25 FLOP/byte counts bytes requested by load instructions. DRAM traffic is smaller, because caches serve repeated requests: the 32 threads of a warp ask for the same A element (one request), and the 16 rows of threads in a block re-read the same B columns. D2 On a GPU, Nsight Compute reports bytes moved at each level (L1, L2, DRAM), so you can place the naive kernel on a roofline per level; the "hierarchical roofline" view in the profiler does this. D6 The honest statement is: the naive kernel relies on caches for its reuse, and how much the caches give depends on the GPU's cache sizes and on the order in which blocks run. Measure it.

What the compiler did

The PTX of sgemmNaive for sm_80 has 10 ld.global.f32 and 5 fma.rn.f32 in the whole kernel: the compiler unrolled the k loop by four plus one remainder iteration, still two loads per multiply-add. R4 The SASS has 58 LDG.E and 29 FFMA: ptxas unrolled further, and the ratio is still exactly 2 loads per FMA. R5 Note the multiply-add: acc += a * b in source became a fused multiply-add because nvcc contracts by default (F6-04). The CPU reference must not assume that every product was rounded separately; the error bound below covers both. D1 D7

A correctness bound you can defend

A K-term dot product computed in floating point, in any order, with or without FMA, satisfies |ĉ − c| ≤ γK Σ|akbk|, where γK = Ku ÷ (1 − Ku) and u = 2−24 for FP32. D8 The harness tests every element against its own bound with an FP64 reference, which is far more precise than FP32, so the reference's own error is negligible. A test with a single absolute tolerance would either fail large-magnitude outputs or pass real bugs; F6-25 returns to this with reduced precision. The bound is a worst case; on the emulator the largest error seen was 0.042–0.997 of it, the high end for K = 1, where it is tight. R1

The shape matrix

E6 asks for correctness on square, tall-skinny, short-wide and non-tile-multiple shapes. C1 The harness uses 1 × 1 × 1, 17 × 13 × 9, 64³, 127 × 129 × 65, 256 × 32 × 300, 33 × 512 × 64, 1,000 × 7 × 513 and 128 × 128 × 1 on the GPU; the emulator uses a smaller set that includes 130 × 7 × 33 and 96 × 132 × 36 (the latter has K and N divisible by 4 so that F6-23's vectorised path is exercised). Every later kernel must pass all of them before it may enter the speed table. The output buffer is filled with NaN before each test, so an element the kernel forgets to write fails.

Comparing with cuBLAS

cuBLAS is column-major. D5 A row-major M × N matrix in memory is the column-major N × M transpose, so the harness asks cuBLAS for CT = BTAT by passing B first, with leading dimensions N, K and N; no copies are needed. The cuBLAS call is compiled only with -DUSE_CUBLAS and linked with -lcublas, which this build did for sm_80. Whether cuBLAS's default math mode for SGEMM may use reduced-precision tensor-core paths depends on the library version and environment settings: the harness sets CUBLAS_DEFAULT_MATH explicitly, and you must check the cuBLAS documentation for your version (unverified box below).

Not verified — check before relying on this

The harness's cuBLAS calls (cublasCreate, cublasSetMathMode with CUBLAS_DEFAULT_MATH, cublasSgemm, cublasDestroy) compiled and linked against the cuBLAS of CUDA 12.0 in this build, so the names and argument types exist; their semantics (column-major convention, whether any SGEMM path may use TF32, and the effect of environment variables on that) were not read from the cuBLAS documentation here (D5). How the hardware actually does it

A warp executing LDG sends one request per instruction to the memory system; the load/store unit groups the 32 addresses into as few memory transactions as the addresses allow (F6-08). D2 For the B operand the 32 addresses are consecutive floats; for the A operand they are one address, which the hardware serves once and broadcasts. Requests that hit in L1 or L2 do not reach DRAM. D2 Each FFMA needs both operands in registers, so a warp stalls at the first FFMA whose loads have not returned; with 2 loads per FMA, the kernel is a memory-latency and memory-bandwidth problem before it is an arithmetic one (F6-20). The sizes of the caches and the bandwidths are product facts for the dossier.

Where the analogy breaks


    

  • In the kitchen, two helpers fetching the same jar make two trips. On a GPU, the 32 threads of a warp asking for the same A element make one request, and caches may serve later requests: the naive kernel is less wasteful than the story suggests, by an amount only a profiler can tell.
    • 

  • The road to the pantry has one speed in the story. Real memory has several levels (L1, L2, DRAM) with different bandwidths, so there is a roofline per level, and a kernel can be bound by L2 while far from the DRAM roof.
    • 

  • Cooking speed in the story is one number. A GPU's arithmetic peak depends on the instruction (FP32 FMA, tensor-core instructions in F6-26), so "the stove's limit" changes with the recipe's number format.
    • 




Common mistakes and debugging


    

  • Swapping x and y. Symptom: correct results, very slow. Cause: row from threadIdx.x makes B and C accesses strided. Find it: the profiler's memory transactions per request; or read the index lines. Fix: x → column for row-major C.
    • 

  • Missing bounds check. Symptom: passes 64³, corrupts memory on 17 × 13 × 9. Find it: Compute Sanitizer memcheck, or the emulator under AddressSanitizer. Fix: the check on both indices.
    • 

  • One fixed tolerance. Symptom: "fails" at K = 4,096 with large values, "passes" a kernel that drops one term. Cause: tolerance not scaled by K and Σ|ab|. Fix: the per-element bound.
    • 

  • Calling cuBLAS as if it were row-major. Symptom: cuBLAS "disagrees" with your correct kernel on non-square shapes, agrees on square symmetric data. Fix: the transpose trick, and test with M ≠ N ≠ K.
    • 

  • Timing without a warm-up. Symptom: the first size looks slow. Cause: one-time initialisation (context, library handles, module loading) in the first timed run. Fix: the harness's warm-up.
    •
