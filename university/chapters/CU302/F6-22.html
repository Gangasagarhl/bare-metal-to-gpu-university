Story hook

In F6-21, every helper in the great kitchen hall walked to the far pantry for every single jar, even though the helper next to her needed the same jar a moment later. Today the head of one table group, Amara, tries something else.

She sends each of the 256 helpers at her table on exactly one trip. Each brings back one jar from a small square of the amounts shelf and one jar from a small square of the weights shelf, and puts it on the shared table. When every jar is on the table, everybody stops and checks: "Is the table full?" Then every helper works through one row of amounts and one column of weights, using jars that sixteen other helpers also use. Only when everyone has finished does the table get cleared for the next squares.

Two trips instead of thirty-two for the same cooking. But there is a rule that must never be broken: everybody waits at the "table full?" check, and everybody waits at the "finished?" check. One helper who leaves early, thinking "my cell is off the edge of the table, I have nothing to do", can leave the whole group waiting forever. This chapter builds Amara's method, measures how much it saves, and shows that waiting forever with real evidence.

What you will be able to do

  • Explain how a shared-memory tile lets each value loaded from global memory be used TILE times, and compute the resulting arithmetic intensity.
  • Write a tiled SGEMM kernel with correct barriers and zero-filled edges that passes the E6 shape matrix.
  • Count global loads, shared-memory loads and multiply-adds in the SASS, and say which resource now limits the kernel.
  • Choose a tile size from its effect on reuse, shared memory, threads per block and occupancy (F6-20).
  • Diagnose a barrier placed in divergent code from a hang and a partial test log.
Jargon box
Tile
Simple words: a small square piece of a big matrix that is worked on as a unit. Analogy: the small square of jars brought from one shelf to the table. Precise: a contiguous sub-matrix (here TILE × TILE elements) of A, B or C that a block (or warp, or thread) loads, computes or stores together; the tile sizes of a GEMM kernel decide its data reuse. D2
Shared-memory tiling
Simple words: copy a tile once into the block's fast shared memory, then let every thread of the block use it many times. Analogy: each jar is fetched once, put on the table, and used by a whole row or column of helpers. Precise: a loop over K in steps of TILE in which a block cooperatively loads one tile of A and one of B into __shared__ arrays, synchronises, accumulates TILE multiply-adds per thread from shared memory, and synchronises again before the next load. D1 D2
Phase (K-step)
Simple words: one round of "load the tiles, wait, compute, wait". Analogy: one filling and clearing of the table. Precise: one iteration of the outer k0 loop; a tiled kernel runs ⌈K ÷ TILE⌉ phases. D2
Reuse factor
Simple words: how many times a value loaded from global memory is used. Analogy: how many helpers cook with one jar before it leaves the table. Precise: the number of multiply-adds performed per operand element loaded from global memory; TILE for this kernel, versus 1 for the naive kernel (ignoring caches). R2
Zero-fill (edge padding)
Simple words: threads whose tile position lies outside the matrix put a zero on the table instead of reading memory. Analogy: an empty bowl placed where a jar would be, so the recipe still works. Precise: loading 0.0f into shared memory for tile elements with row ≥ M, column ≥ N or k ≥ K, so that the inner loop needs no bounds checks and the padded terms add exactly zero. R1
Divergent barrier
Simple words: a __syncthreads() that some threads of the block never reach. Analogy: one helper leaves before the "table full?" check, and the others wait for her forever. Precise: a block-wide barrier inside a condition that is not uniform across the block; the CUDA Programming Guide allows __syncthreads() in conditional code only if the condition evaluates identically across the whole block, and otherwise the behaviour is not defined (a hang or wrong results). D1

Terms from earlier chapters used here: shared memory (GPU), which is not the shared memory between processes of an operating system (F2 and F3 courses); the GPU kernel, which is not the operating-system kernel of F3; bank conflict (F6-11); occupancy (F6-20); arithmetic intensity (F6-21).

The idea in pictures

Figure 1 is the picture every GEMM kernel in this course refines: tiles travel from global memory into shared memory once per phase, and from shared memory into registers, where the multiply-adds happen. The block owns one TILE × TILE tile of C. In each phase it moves along the K dimension: one tile of A from its block row, one tile of B from its block column.

Figure 2 shows one phase in time for one block. The two barriers split it into three parts; the second barrier is the one that people forget, and the first is the one that people place in an if.

Layer 1 — the kid explanation

Analogy

Block = a group of rows sharing one table; shared memory = the table; a tile = a small square of jars; one phase = filling the table, cooking, clearing it; __syncthreads() = "everybody stop and check" — first "is the table full?", then "has everybody finished?"

The naive kitchen carried each jar many times. Now each table group carries a square of jars once, puts it on the table, and everybody at the table uses it. A square of 16 by 16 jars is used by 16 helpers each, so the long walks drop by a factor of 16.

Two stops keep the table honest. Nobody may start cooking before every jar is on the table, or she would cook with an empty bowl. Nobody may bring the next square before everyone has finished with this one, or she would take a jar out from under someone's hands.

At the edges of the shelves, some places in the square have no jar. The helper for that place puts down an empty bowl (a zero). Then everybody follows the same recipe, and the empty bowls add nothing.

Layer 2 — the student explanation

The algorithm

A block of TILE × TILE threads computes a TILE × TILE tile of C. Thread (tx, ty) owns C[row][col] with row = blockIdx.y·TILE + ty and col = blockIdx.x·TILE + tx, exactly as in the naive kernel. D1 The dot product over K is split into phases of TILE terms. In phase p (starting at k0 = p·TILE), thread (tx, ty) copies A[row][k0 + tx] into As[ty][tx] and B[k0 + ty][col] into Bs[ty][tx]. After a barrier, every thread adds Σk As[ty][k]·Bs[k][tx] for k = 0 … TILE − 1 to its accumulator. A second barrier protects the tiles from being overwritten by the next phase while slower warps still read them. D2

The accumulator acc lives in a register for the whole kernel; C is written once at the end. The order of additions changes compared with the naive kernel (phase by phase rather than one long sum), but each output is still a K-term dot product, so the error bound of F6-21 applies unchanged. D5

Counting the reuse

Per phase, each thread issues 2 global loads and does TILE multiply-adds. The naive kernel did 2 global loads per multiply-add; the tiled one does 2 ÷ TILE. In bytes: TILE multiply-adds are 2·TILE FLOP for 8 bytes, so the intensity against global memory is TILE ÷ 4 FLOP/byte: 4 for TILE = 16 and 8 for TILE = 32. F6-21's Listing 4 printed 3.992 and 7.969 at n = 4,096, the small difference being the bytes of C. R2

The loads did not disappear; they moved. Each multiply-add now needs two operands from shared memory: As[ty][k] and Bs[k][tx]. Shared memory is far faster than global memory, but it is not free: one shared-memory load instruction per multiply-add means the load/store pipeline is as busy as the FMA pipeline. You will see that ratio in the SASS below, and F6-23 attacks it with register tiling.

Edges by zero-fill

Shapes such as 17 × 13 × 9 do not fill whole tiles. Listing 1 handles them in one place: a thread whose A element is outside (row ≥ M or k ≥ K) stores 0.0f into As, and likewise for Bs. For a valid output element every padded term is 0 × 0 or 0 × (a real value) and adds exactly zero. Threads outside C still load and still reach both barriers; only the final store is guarded. This is the pattern that keeps barriers safe, and the forensic lab shows what happens without it.

Bank conflicts

In the bank model of F6-11 (successive 4-byte words in successive banks), check the three shared-memory accesses of one warp. D3 With TILE = 32, a warp is one row of threads: one ty, 32 consecutive tx. The store As[ty][tx] and the read Bs[k][tx] touch 32 consecutive words: conflict-free. The read As[ty][k] is one address for the whole warp: a broadcast. With TILE = 16, a warp covers two rows ty and ty + 1: As[ty][k] and As[ty+1][k] are two addresses 16 words apart, in different banks, each broadcast to 16 threads. No padding is needed for this kernel. (It was needed in F6-19's transpose, which read a column.)

Layer 3 — the engineer's depth

Why two barriers, precisely

__syncthreads() waits until all threads of the block have reached it, and makes the shared- and global-memory accesses made by those threads before the barrier visible to all threads of the block after it. D1 Barrier 1 orders a write (the tile store) before reads by other threads: a read-after-write dependency across threads. Barrier 2 orders reads (the inner loop) before the next phase's writes to the same addresses: a write-after-read dependency. Remove barrier 1 and a fast warp may multiply stale or half-written tiles; remove barrier 2 and a fast warp may overwrite As while a slow warp is still reading it. Both are data races with no compiler error. On a GPU they may pass a test for months; on the university's emulator, which runs every thread as a real std::thread with a real std::barrier, they race for real, and the barrier that some threads skip really hangs. R1 R5

Why not one barrier with two tile buffers? That is double buffering, the subject of F6-24; it trades shared memory for one barrier per phase and, more importantly, lets loads overlap computation.

Choosing TILE

A larger tile raises reuse but costs: TILE = 32 needs 1,024 threads per block and 8,192 bytes of shared memory; TILE = 16 needs 256 threads and 2,048 bytes. The compiler report for sm_80 gives 32 registers per thread for both. R3 Residency is decided per block (F6-20): with 1,024-thread blocks, an SM whose thread limit is 2,048 holds at most two blocks, and when both blocks wait at barriers nothing else can issue. Smaller blocks give the scheduler more independent blocks to switch between. Which effect wins is a measurement for your GPU; E6 asks you to record registers and occupancy per step precisely so that you can explain the result. C1 The limits of your GPU (threads, blocks and shared memory per SM) are product facts: take them from cudaGetDeviceProperties on your machine and the vendor documentation (unverified box below).

Not verified — check before relying on this

The per-SM limits used in this course's examples (2,048 threads per SM is F6-20's example device, not a product) and the maximum shared memory per block (the static limit without opting in to a larger dynamic allocation) differ between GPU generations. Read them from your GPU with cudaGetDeviceProperties (maxThreadsPerMultiProcessor, sharedMemPerBlock, sharedMemPerMultiprocessor), and check the "Compute Capabilities" table of the CUDA C++ Programming Guide for your toolkit version (D1).

What the compiler made of it

The SASS for sm_80 shows, for sgemmTiled<16>: 2 LDG.E, 2 STS, 2 BAR.SYNC, 16 FFMA, 16 LDS and 4 LDS.128; for sgemmTiled<32> the same with 32 FFMA, 32 LDS and 8 LDS.128. R4 Read it as: the inner loop over k was fully unrolled; the row As[ty][0..TILE-1] is the same for all k of one thread and contiguous, so ptxas fetched it four floats at a time with 128-bit LDS.128; the column Bs[k][tx] is strided by TILE words and needed one scalar LDS per k. That is 1.25 shared-memory load instructions per FFMA, against 2 global loads per FFMA before. The 16-byte shared loads are visible in the excerpt: LDS.128 R12, [R0] followed by LDS.128 R8, [R0+0x10] (16 bytes further), while the scalar loads step by 0x80 = 128 bytes = 32 floats, one row of Bs. R4 D4

The next limit is therefore instruction issue and shared-memory bandwidth, not DRAM. On a roofline drawn against shared-memory traffic, this kernel's intensity is about 2 FLOP per 4-byte shared load: far below anything the FMA units could use. The cure is to make each value loaded from shared memory feed several multiply-adds, which needs each thread to own several outputs: register tiling.

How the hardware actually does it

Shared memory is on-chip storage in each SM, allocated per block for the block's lifetime and accessed with its own instructions (STS, LDS), separate from global loads (LDG). D1 D4 It is divided into banks; a warp's request is served in one pass when its addresses fall into different banks or share an address (broadcast), and in several passes otherwise (F6-11). D3 BAR.SYNC is the SASS instruction behind __syncthreads() in this build: a warp that reaches it stops being eligible to issue until all warps of its block have arrived. R4 Because the scheduler issues only eligible warps (F6-20), the time a block spends at barriers must be covered by other blocks on the same SM — one reason why occupancy still matters for this kernel, even though the next chapters will show it is not the whole story.

Worked example

Task. For n = 4,096 and TILE = 32, compute the number of blocks, phases per block, bytes each block loads from global memory, total global bytes, and the intensity; then the same for TILE = 16; and compare shared-memory load instructions per FFMA from the SASS.

  1. Blocks: (4,096 ÷ 32)² = 128² = 16,384. Phases per block: 4,096 ÷ 32 = 128.
  2. Per phase a block loads 2 × 32 × 32 floats = 2,048 floats = 8,192 bytes; per block 128 × 8,192 = 1,048,576 bytes = 1 MiB.
  3. Total: 16,384 MiB = 16 GiB = 17,179,869,184 bytes, plus C written once: 4,096² × 4 = 67,108,864 bytes. Sum 17,246,978,048 ≈ 1.725 × 1010 bytes, exactly the "block tile 32 × 32" row of F6-21's Listing 4. R2
  4. Intensity: 1.374 × 1011 FLOP ÷ 1.725 × 1010 bytes = 7.97 FLOP/byte (Listing 4: 7.969).
  5. TILE = 16: 65,536 blocks × 256 phases × 2,048 bytes = 34,359,738,368, plus C: 3.443 × 1010 bytes; intensity 3.99 (Listing 4: 3.992). Halving the tile doubles the global traffic.
  6. Shared-memory loads per FFMA from the SASS: (16 + 4) ÷ 16 = 1.25 for TILE = 16 and (32 + 8) ÷ 32 = 1.25 for TILE = 32. The tile size changes global reuse, not shared-memory reuse. R4

Where the analogy breaks


    

  • In the kitchen, the table is a visible place and helpers can see whether a jar is there. On a GPU nothing tells a thread that a shared-memory element is "not yet written": it reads whatever bits are there. Only the barrier makes the order safe; there is no error message when it is missing.
    • 

  • The story's "everybody waits" sounds as if the whole hall stops. Only the warps of one block wait at its barrier; warps of other blocks on the same SM keep issuing, which is how barrier time is hidden (F6-20).
    • 

  • Helpers at a table can pass jars hand to hand freely. Shared memory has banks: some access patterns are served in one pass and others take several (F6-11), and the table has a fixed size per SM that limits how many groups can sit down at once.
    • 




Common mistakes and debugging


    

  • Early return before the barriers. Symptom: hang, or wrong results only for shapes that are not tile multiples (see the forensic lab: 64³ passes, 127 × 129 × 65 never finishes on the emulator). Cause: if (row >= M || col >= N) return; before the loop. Find it: emulator hang or Compute Sanitizer's synccheck tool on a GPU (check its documentation, D6). Fix: zero-fill and guard only the final store.
    • 

  • Missing second barrier. Symptom: rare wrong results that change with block scheduling. Find it: the emulator (threads really race) or racecheck on a GPU (D6). Fix: barrier after the inner loop.
    • 

  • Bounds check on only one index of the tile load. Symptom: passes square shapes, fails 17 × 13 × 9 or reads out of bounds. Find it: the emulator under AddressSanitizer reports the bad read with the line. Fix: check row and k for A, k and column for B.
    • 

  • Transposed thread mapping. Symptom: correct, slower than naive. Cause: tx used for rows, so neither tile load is coalesced. Fix: x is the column, as in F6-21.
    • 

  • TILE = 32 with extra shared arrays. Symptom: launch fails with a resource error. Cause: threads × registers or shared memory per block above the device limits. Find it: the error check after the launch; the compiler report. Fix: smaller tile or fewer registers.
    •

Summary


    

  • A block loads one TILE × TILE tile of A and one of B per phase into shared memory; each value is then used TILE times.
    • 

  • Global intensity rises from 0.25 to TILE ÷ 4 FLOP per byte: 4 for TILE = 16, 8 for TILE = 32 (F6-21's Listing 4: 3.992 and 7.969 at n = 4,096).
    • 

  • Two barriers per phase: after the load (read after write) and after the compute (write after read).
    • 

  • Edges are handled by zero-fill so every thread reaches every barrier; only the final store is guarded.
    • 

  • An early return before a barrier hangs the emulator on non-multiple shapes; on a GPU it is undefined behaviour.
    • 

  • The SASS shows 1.25 shared-memory loads per FFMA: shared memory and issue, not DRAM, are the next limit.

Answers to Check yourself


    

  1. TILE: each element of an A tile is used by the TILE threads of its row of the block, each B element by the TILE threads of its column. Intensity 2·TILE FLOP per 8 bytes = TILE ÷ 4 FLOP/byte.
    2. 

  2. Barrier 1 (after the loads) makes sure every tile element is written before anyone reads it: read after write. Barrier 2 (after the inner loop) makes sure everyone has finished reading before the next phase overwrites the tiles: write after read.
    3. 

  3. (b). (a) is false: rows beyond M and columns beyond N also need it. (c) is false: it adds a comparison per load; its purpose is correctness. (d) is false: that is exactly the forensic bug.
    4. 

  4. (32 + 8) ÷ 32 = 1.25. The row As[ty][0..31] is contiguous and the same for all k of a thread, so ptxas loads it four floats per LDS.128; the column of Bs is strided and needs scalar loads.
    5. 

  5. 32 × 64 = 2,048 threads per block. Compare that with maxThreadsPerBlock of your GPU (Layer 3 unverified box): the harness's tiled32 step already uses 1,024, and a block above the limit fails to launch with an error that the launch check prints. Intensity against global memory: BM·BN ÷ (2(BM + BN)) = 2,048 ÷ 192 ≈ 10.7 FLOP/byte (F6-21's formula).
