Story hook

The great kitchen hall has room for a fixed number of rows of helpers. Tonight the head cook, Amara, is making a soup that needs one ingredient from the far pantry for every bowl. A runner takes a long time to come back from the pantry. While a row waits for its runner, it can do nothing for that bowl.

Amara's first idea is to fill the hall: as many rows as fit, each sending one runner at a time. While one row waits, another row cooks. Her assistant, Tomás, tries something different. He seats only a quarter of the rows, but every helper in his rows sends four runners at once, for four different bowls, and starts on whichever ingredient comes back first. Tomás's half-empty hall finishes first.

How can fewer rows be faster? The hall's job is not to be full. Its job is to keep enough runners on the road that the pantry is always busy and the cooks never stand idle. Rows in the hall are one way to get runners on the road; more runners per helper is another. This chapter is about counting both.

What you will be able to do

  • Compute the theoretical occupancy of a kernel from its registers per thread, shared memory per block and block size, name the limiting resource, and check the result against the CUDA Toolkit's own occupancy calculator.
  • Explain latency hiding with Little's law: how many independent memory operations must be in flight, and how warps (thread-level parallelism) and independent instructions per warp (instruction-level parallelism) both supply them.
  • Read a compiler report (ptxas -v) and a SASS listing to find a kernel's register count and how many loads it issues before the first use.
  • Diagnose a case where lower occupancy is faster, from compiler and model evidence, and explain it with instruction-level parallelism.
  • Record registers and occupancy for every step of the E6 speed table, as the milestone asks.
Jargon box
Occupancy
Simple words: how full the hall is: the warps that are resident on a multiprocessor, compared with the most it can hold. Analogy: how many rows of helpers sit in the hall, out of the rows it has chairs for. Precise: resident warps per SM ÷ maximum resident warps per SM; limited by registers, shared memory, the warp limit and the block limit, whichever allows fewest blocks (as defined in F1-60). D1 D2
Theoretical occupancy
Simple words: the occupancy the resource limits allow, worked out before the kernel runs. Analogy: how many rows the hall could seat, given how many hands and how much table each row needs. Precise: active blocks per SM computed from the kernel's resource use and the device's per-SM limits, times warps per block, divided by the maximum warps per SM; the value the occupancy API and calculator return. D1 R1
Achieved occupancy
Simple words: how full the hall really was, on average, while the kernel ran. Analogy: the rows actually seated, counted every minute; at the end of the evening the hall empties. Precise: the average number of resident warps per SM over the kernel's run, measured by a profiler; it is lower than the theoretical value when the grid is too small, when blocks finish unevenly (the "tail"), or when launches are short. D3
Register allocation unit
Simple words: registers are handed out in fixed-size bundles per warp, not one at a time. Analogy: hands are given to rows in packs, so asking for one more hand can cost a whole pack. Precise: the granularity in which the register file is allocated to warps; the toolkit's calculator (cuda_occupancy.h, CUDA 12.0) uses 256 registers per warp for compute capability 8.x, which is why occupancy falls in steps. R1 D4
__launch_bounds__
Simple words: a note on a kernel that tells the compiler the largest block size you will use, and optionally how many blocks you want to fit on one SM. Analogy: telling the hall manager in advance "rows of at most 256, and I want four tables' worth in the hall", so hands are budgeted to match. Precise: a CUDA C++ function qualifier with a maximum threads-per-block argument and an optional minimum-blocks-per-multiprocessor argument; the compiler limits registers per thread to satisfy it, spilling if necessary. D1
Latency hiding
Simple words: keeping the GPU busy while some operations wait, by having other independent work ready. Analogy: while one row waits for the pantry, another row cooks. Precise: overlapping the latency of operations with the issue of independent instructions from the same warp (ILP) or other warps (TLP), so that issue slots stay busy (as defined in F1-60). D2 D5
Instruction-level parallelism (ILP)
Simple words: independent instructions inside one thread, which can be in progress at the same time. Analogy: one helper sending four runners for four bowls instead of one. Precise: the degree to which instructions of one instruction stream do not depend on each other's results; on a GPU, for example, several independent loads issued before the first use. D5
Occupancy calculator
Simple words: a program or function that does the occupancy arithmetic for you. Analogy: the seating chart of the hall. Precise: NVIDIA ships a host-side calculator in the header cuda_occupancy.h (functions such as cudaOccMaxActiveBlocksPerMultiprocessor, found in the CUDA 12.0 header in this build) and a runtime API (cudaOccupancyMaxActiveBlocksPerMultiprocessor) that asks the driver for a real device. R1 D1

A reminder from the faculty's rules: the word kernel here means a GPU function launched on many threads (kernel (GPU)), not the operating-system kernel of F3 (kernel (operating system)).

The idea in pictures

Figure 1 is the warp-execution timeline that guide 9.2 requires for this chapter. It shows one warp scheduler over time, in two situations of the model of Listing 3. On the left, four warps each issue one load and wait for it: the scheduler is idle most of the time. On the right, the same four warps each issue four independent loads before waiting: four times as many loads are in flight, and the idle gaps shrink. Nothing about the hall's size changed.

Figure 2 shows the other half of the story: where occupancy comes from. Each block asks for registers (warps × registers per warp, rounded up), shared memory and warp slots. The SM grants whole blocks. Whichever resource runs out first sets the number of blocks, and therefore the number of warps that can hide latency.

Layer 1 — the kid explanation

Analogy

Hall = one SM; row of helpers = warp; a helper's hands = registers; the table in the middle of a row group = shared memory; runner to the pantry = a load from global memory; "while one row waits for the pantry, another row cooks" = latency hiding; seats filled = occupancy; one helper sending several runners at once = instruction-level parallelism.

The pantry is far away. Every trip takes a long time, and nothing can shorten it. What you can change is how many trips are under way at once. If many runners are on the road, ingredients arrive one after another, and the cooks always have something to work on.

There are two ways to have many runners on the road. You can seat more rows, each sending one runner. Or each helper can send several runners for different bowls before waiting. Both count. A hall full of rows that each send one runner can be slower than a half-full hall where each helper sends four.

Seats are limited by what each row needs. If each helper needs many hands (registers), fewer rows fit. If each row group needs a big table (shared memory), fewer groups fit. So a kernel that does more per helper usually means fewer rows, and the art is to find the balance that keeps the pantry busiest.

Layer 2 — the student explanation

Four limits, one minimum

A multiprocessor (SM) holds resident blocks. Each resident block keeps its registers and shared memory for its whole life, which is why switching between warps costs nothing: the state never leaves the chip. D1 D2 The number of resident blocks of one kernel is the minimum of four numbers D1 R1:

  1. Registers. Registers per thread × 32, rounded up to the allocation unit, gives registers per warp; the register file per SM divided by that gives warps, and warps divided by warps per block gives blocks. The CUDA 12.0 calculator additionally divides the register file among four sub-partitions for compute capability 8.x and rounds warps per block up to a multiple of four when it checks the per-block limit. R1
  2. Shared memory. Static plus dynamic shared memory per block, plus a per-block amount reserved by the system, rounded up to the allocation granularity; the shared memory per SM divided by that gives blocks. R1 D1
  3. Warp slots. Maximum threads per SM ÷ 32 gives warp slots; divided by warps per block gives blocks. D1
  4. Block slots. A per-SM maximum number of resident blocks. D1

Theoretical occupancy is active blocks × warps per block ÷ maximum warps per SM. All per-SM limits are properties of your GPU: deviceQuery and cudaGetDeviceProperties report them (F6-07), and the CUDA Programming Guide tabulates them per compute capability. This chapter never quotes them for a real product. D1

Little's law: how much must be in flight

Little's law says that in a steady state, the average number of items in a system equals their arrival rate times their average time in the system: L = λW. D6 Applied to memory: if each load takes W cycles and you want the memory system to accept λ loads per cycle, you need L = λW loads in flight at every moment. With fewer, the memory system idles; more than that does not help, because the roof is reached. D5 D6

Loads in flight per SM = resident warps × independent loads each warp has outstanding. Occupancy controls the first factor; the code controls the second. Vasily Volkov's talk "Better Performance at Lower Occupancy" is the course card's source for this point: it argues, with measurements on the GPUs of its time, that raising ILP can reach the same throughput with fewer warps. D5 No number from that talk is used here.

How code supplies ILP

A thread has ILP when it issues several operations that do not depend on each other before it needs their results. In Listing 2, each thread of scaleIlp<4> loads four elements, blockDim.x apart so that every load of a warp stays coalesced (F6-08), and only then multiplies. The compiler keeps that order in the machine code: the SASS for sm_80 shows four LDG instructions before the first FMUL. R4 The price is registers: the four values must sit in registers while they are in flight. ptxas reports 8 registers for ILP 1, 14 for ILP 2, 22 for ILP 4 and 29 for ILP 8. R5

Layer 3 — the engineer's depth

The calculator in the toolkit, read and cross-checked

The CUDA Toolkit ships its occupancy calculator as a header, cuda_occupancy.h, that compiles as ordinary host C++. In CUDA 12.0 it describes a device with a cudaOccDeviceProp structure (compute capability, threads, registers and shared memory per SM and per block, reserved shared memory) and a kernel with cudaOccFuncAttributes (registers per thread, static shared memory), and cudaOccMaxActiveBlocksPerMultiprocessor returns active blocks plus a bit mask of limiting factors. R1 Reading its source shows the rules that Layer 2 lists: per-architecture tables for the register allocation unit, the maximum registers per thread, the number of sub-partitions, the shared-memory granularity, the maximum blocks per SM, and the shared-memory carveout sizes that the hardware can configure. R1

Listing 1 implements the four limits in about thirty lines and compares its answer with the header's for 64,000 combinations of block size, registers and shared memory on the example device: all 64,000 agree. R1 That agreement is evidence that the simple model is the model, for this toolkit and this architecture family; it is not evidence about any particular GPU's numbers, which are inputs.

Cliffs and steps

Because registers are granted per warp in units, occupancy is a step function of registers per thread. In Listing 1's table, 64 registers allow 4 blocks of 256 threads (50 %), 72 registers allow 3 (37.5 %), and 128 allow 2 (25 %). For 1,024-thread blocks, 64 registers fit one block and 65 registers fit none: the launch would fail with a "too many resources" error. R1 Shared memory produces steps the same way: 8,192 bytes per 128-thread block allow 11 blocks, 16,384 bytes per 256-thread block allow 5. R1

Two tools move a kernel across a step. __launch_bounds__(maxThreads, minBlocks) tells the compiler to fit minBlocks blocks of maxThreads on one SM, and the compiler caps registers accordingly; -maxrregcount caps registers for a whole compilation unit. Both can force spills to local memory, which F6-23's forensic lab shows in SASS. D1 D2

When more occupancy helps, and when it does not

The Best Practices Guide's position, which this chapter adopts, is that occupancy is a means, not a goal: low occupancy can starve the scheduler, but beyond the point where latency is hidden, more warps add nothing, and the resources they cost (registers per thread, shared memory per block) may be what makes each thread efficient. D2 The model of Listing 3 shows both halves with invented latencies: with ILP 1, throughput rises in proportion to warps (1, 4, 8, 16 warps give 0.25, 0.99, 1.98, 3.95 elements per 100 cycles); with 4 warps, raising ILP from 1 to 8 raises it from 0.99 to 7.27. Holding warps × ILP at 16 gives nearly the same throughput for every split (3.95, 3.90, 3.81, 3.64). R3 In the model, what matters is loads in flight, and the "loads in flight" column tracks throughput.

GEMM, the subject of the rest of this course, lives on the "fewer, fatter threads" side: F6-23's register-tiled kernels use 75 to 124 registers per thread, which means low theoretical occupancy, and they are designed that way because each thread then does many multiply-adds per value loaded. R6 E6 asks you to record registers and occupancy for every step for exactly this reason: so that the speed table can show whether occupancy explained a change or not. C1

Theoretical is not achieved

The calculator gives an upper bound. A profiler measures achieved occupancy, which can be lower: a grid with fewer blocks than SMs × active blocks never fills the GPU; blocks of uneven length leave a tail where few warps remain; very short kernels are dominated by launch and ramp-up. D3 When a profile shows low achieved occupancy, first compare it with the theoretical number: if they agree, a resource limits you; if achieved is much lower, look at the grid and the tail.

How the hardware actually does it

Each SM has a register file and on-chip shared memory that are partitioned among resident blocks when they start, and warp schedulers that each pick, every cycle, an eligible warp from those assigned to them. A warp is eligible when its next instruction's operands are ready; a warp whose next instruction needs a load still in flight is stalled. D1 F1-60 D3 There is no saving and restoring of registers when the scheduler moves between warps; this is why a GPU can switch every cycle and why the register file must hold every resident warp's registers at once. D1 The hardware tracks dependences per instruction, so a warp can have several loads outstanding and stall only at the first instruction that uses one of them; the order of LDG and FMUL in the SASS of Listing 2 is what the hardware will follow. R4 D7 How many warp schedulers an SM has, its register-file size and its memory latency are product facts: read them in the architecture whitepaper of your GPU (named in the dossier), never from this chapter.

Worked example

Task. A kernel uses 256 threads per block, 72 registers per thread and no shared memory. On the example device of Listing 1 (65,536 registers, 2,048 threads, 32 blocks per SM; allocation unit 256 registers per warp; 4 sub-partitions), what is its theoretical occupancy, and how many registers per thread would raise it by one block?

  1. Registers per warp: 72 × 32 = 2,304, already a multiple of 256, so 2,304. R1
  2. Per sub-partition: 65,536 ÷ 4 = 16,384 registers, which hold ⌊16,384 ÷ 2,304⌋ = 7 warps; × 4 = 28 warps per SM.
  3. Warps per block: 256 ÷ 32 = 8. Blocks by registers: ⌊28 ÷ 8⌋ = 3.
  4. Blocks by warp slots: ⌊(2,048 ÷ 32) ÷ 8⌋ = ⌊64 ÷ 8⌋ = 8. Blocks by block slots: 32. Shared memory: no limit.
  5. Active blocks = min(3, 8, 32) = 3; warps = 24; occupancy = 24 ÷ 64 = 37.5 %. Listing 1 prints the same row. R1
  6. For 4 blocks you need 32 warps, so 8 warps per sub-partition: 16,384 ÷ 8 = 2,048 registers per warp, so at most 64 registers per thread. Listing 1's row for 64 registers shows 4 blocks and 50 %.

Second task: in flight. In Listing 3's model, one load takes 400 cycles and the memory system accepts at most one load every 4 cycles. Little's law: to reach that roof, 400 × ¼ = 100 loads must be in flight. Version A of the forensic lab (16 warps, ILP 1) keeps about 16 in flight and reaches 3.95 elements per 100 cycles; version B (4 warps, ILP 8) keeps about 29 in flight and reaches 7.27. Neither is near the roof of 25: both would profit from more of either kind of parallelism. R3 R2

Where the analogy breaks


    

  • A runner is a person who can be sent at any time. A load is an instruction that occupies an issue slot, registers for its result, and space in the memory system's queues; "send more runners" eventually stops working because those queues fill, which the analogy hides.
    • 

  • In the hall, empty chairs cost nothing. On an SM, resources are claimed per block for the block's whole life: a block that waits at a barrier still holds its registers and shared memory, so its seats are not free for others.
    • 

  • The hall seats rows one at a time. An SM admits whole blocks: a 1,024-thread block needs room for all its 32 warps at once, which is why one register too many can drop occupancy from 50 % to zero (Listing 1, last row).
    • 

  • Helpers in the story choose to send four runners. A GPU thread has ILP only if the compiler keeps the loads independent and early; reading the SASS is the only way to know (Listing 2).
    • 




Common mistakes and debugging


    

  • Chasing 100 % occupancy. Symptom: a change raises occupancy and the kernel gets slower. Cause: the change cut registers per thread (spills) or work per thread (less ILP). Find it: compare ptxas -v before and after and the SASS for LDL/STL. Fix: optimise loads in flight, not occupancy.
    • 

  • Quoting another GPU's limits. Symptom: your occupancy table disagrees with the runtime API. Cause: limits copied from a different compute capability. Fix: take them from cudaGetDeviceProperties on the lab GPU and cross-check with cudaOccupancyMaxActiveBlocksPerMultiprocessor.
    • 

  • Forgetting dynamic shared memory. Symptom: the calculator says 4 blocks, the profiler shows 2. Cause: the third launch parameter adds shared memory that ptxas -v does not report. Fix: pass the same dynamic size to the occupancy API.
    • 

  • "Too many resources requested for launch". Symptom: a launch error after raising the block size. Cause: registers × threads exceed the per-block register limit (Listing 1's 1,024 × 65 row). Fix: smaller blocks, __launch_bounds__, or fewer registers.
    • 

  • Grid too small. Symptom: high theoretical, low achieved occupancy. Cause: fewer blocks than the GPU can hold. Fix: more, smaller blocks, or more work per launch.
    •

  • ILP costs registers (8 → 29 registers from ILP 1 to 8 in this build) and shows in SASS as several loads before the first use.
    • 

  • Lower occupancy can be faster when each warp keeps more loads in flight; achieved occupancy can be lower than theoretical for grid-size and tail reasons.
