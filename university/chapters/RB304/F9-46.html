Story hook

The school band has one drum and two drummers who share it. Amara plays the quick pattern: two strokes in every bar of four counts. Jun plays the slow pattern: three strokes in every bar of six counts. Each pattern must be finished before its next bar starts. The band leader tries a simple rule: "Amara's pattern comes back more often, so Amara always goes first." It sounds fair. At count six Jun is still one stroke short, and the song stumbles.

Then the leader tries another rule: "whoever's bar ends sooner plays now." Nobody gets a fixed rank; the rank changes with every bar. With that rule both patterns fit, every time, although the drum is never silent. The two rules have names, rate-monotonic and earliest-deadline-first, and engineers can predict, before anyone plays, which task sets each rule can handle. That prediction is this chapter.

What you will be able to do

  • Explain fixed-priority (rate-monotonic) and dynamic-priority (earliest-deadline-first) scheduling, and when each is optimal.
  • Apply the utilisation tests (Liu–Layland, hyperbolic, EDF's U ≤ 1) and say which are sufficient and which are exact.
  • Compute worst-case response times with response-time analysis including a blocking term and release jitter, and EDF's processor-demand test for deadlines shorter than periods.
  • Compare the behaviour of the two policies under overload from a simulation.
  • Use Linux's SCHED_DEADLINE policy, observe its admission control and throttling, and diagnose an admission failure.
Jargon box
Schedulability test
Simple words: a calculation that says, before running, whether every deadline will be met. Analogy: checking on paper that both drum patterns fit into the bars. Precise: a test on a task set's parameters (T, C, D, and possibly B, J) under a given policy; it is sufficient if "yes" guarantees schedulability, necessary if "no" guarantees a miss, and exact if both. D1 D2
Earliest deadline first (EDF)
Simple words: always run the job whose deadline comes soonest. Analogy: whoever's bar ends sooner plays now. Precise: a dynamic-priority preemptive policy: at every instant the ready job with the earliest absolute deadline runs. On one processor, for independent preemptible jobs, EDF meets all deadlines whenever any algorithm can (it is optimal); for periodic tasks with deadlines equal to periods, the set is EDF-schedulable if and only if U ≤ 1. D1 D3
Hyperbolic bound
Simple words: a better quick test for rate-monotonic priorities than the classic bound. Analogy: a stricter but fairer check of the band's bar plan. Precise: a set of n periodic tasks with D = T is schedulable under rate-monotonic priorities if Π(Ui + 1) ≤ 2; sufficient, not necessary, and never more pessimistic than the Liu–Layland bound. D4
Blocking term (B)
Simple words: time a task waits for a less urgent task that holds something it needs. Analogy: Amara must wait while Jun finishes tightening the drum skin he started on. Precise: in response-time analysis, the longest time a job can be delayed by lower-priority jobs, for example a critical section on a shared lock; with priority inheritance or a priority-ceiling protocol it is bounded by the length of critical sections (F3-40 covered priority inversion). D2 D1
Release jitter (J) in analysis
Simple words: the most a task's release can be late compared with when it was due. Analogy: the beat that sometimes reaches Amara a little after the conductor's hand moved. Precise: the maximum delay between a job's nominal arrival and its actual release (for example a timer's lateness, F9-45); a higher-priority task with jitter Jj can interfere as if its period were shortened, so RTA uses ⌈(w + Jj)/Tj⌉, and the task's own response time is Ri = wi + Ji. D2
Demand bound function (dbf)
Simple words: the most work that must be finished inside any window of a given length. Analogy: how many strokes must fit inside any stretch of counts. Precise: for synchronous periodic tasks, dbf(L) = Σ max(0, ⌊(L − Di)/Ti⌋ + 1)·Ci; EDF meets all deadlines on one processor if and only if dbf(L) ≤ L for every L (the processor-demand criterion), and it is enough to check the absolute deadlines up to a bound such as the hyperperiod plus the largest D. D5 D1
Hyperperiod
Simple words: the time after which the whole pattern of releases repeats. Analogy: the number of counts after which both drummers start a bar together again. Precise: the least common multiple of the periods; for synchronous tasks the schedule repeats every hyperperiod if U ≤ 1. D1
Domino effect
Simple words: under overload, one late job makes the next ones late too, in every task. Analogy: one drummer running late pushes everyone after her off the beat. Precise: the behaviour of EDF when U > 1: because priorities follow deadlines, late jobs keep early deadlines and delay jobs of all tasks, so misses spread across the set, whereas fixed priorities confine misses to the lowest-priority tasks. D1 R1
SCHED_DEADLINE
Simple words: Linux's EDF policy, where each task books a share of a processor. Analogy: each drummer reserves so many strokes per bar, and the leader refuses a booking that would not fit. Precise: a scheduling policy (value 6 in the installed <linux/sched.h>) set with the sched_setattr system call and a struct sched_attr whose fields include sched_runtime, sched_deadline and sched_period (installed <linux/sched/types.h>); the kernel schedules such tasks by earliest deadline, limits each to its runtime per period, and refuses new reservations that exceed its admission limit. H1 D6 R3

Terms from earlier chapters: rate-monotonic priority assignment, response-time analysis, utilisation, fixed-priority preemptive scheduling, priority inversion, priority inheritance (OS305); jitter and relative and absolute deadline (F9-45).

The idea in pictures

Layer 1 — the kid explanation

When several jobs share one processor, a rule must say who runs now. Two rules are famous. The first gives every job a fixed rank: jobs that repeat more often get a higher rank. The second has no fixed ranks: at every moment, the job whose deadline is closest runs.

The first rule is simple and very common. But it can fail even when there is enough time in total, as the drummers found. The second rule uses every free moment, so it works whenever the total work fits, but the computer must know every deadline and keep re-sorting.

The best part: you do not need to try. Short formulas tell you in advance whether all the beats will fit. Engineers write those formulas down before they build a robot, and then they measure to check.

Layer 2 — the student explanation

Fixed priorities, from F3-39

In F3-39 you assigned priorities by period (rate-monotonic, RM), checked the Liu–Layland bound U ≤ n(21/n − 1), and computed exact worst-case response times with RTA: Ri = Ci + Σj∈hp(i) ⌈Ri/Tj⌉·Cj. D3 D2 RM is optimal among fixed-priority assignments when D = T (if any fixed assignment works, RM works); when D < T, deadline-monotonic order (shorter D, higher priority) takes that role. D1 The bound is sufficient only: above it, RTA decides.

Earliest deadline first

EDF assigns priority to jobs, not tasks: the ready job with the earliest absolute deadline runs, and a newly released job preempts the running one if its deadline is earlier. For independent preemptible periodic tasks with D = T on one processor, EDF is schedulable if and only if U ≤ 1. Layer 3 — the engineer's depth


RTA with blocking and jitter


The general recurrence for task i (in priority order) is wi = Ci + Bi + Σj∈hp(i) ⌈(wi + Jj)/Tj⌉·Cj, iterated from w = Ci + Bi to a fixed point, then Ri = wi + Ji. D2 Three remarks. (1) Bi is the longest single critical section of a lower-priority task on a resource that task i (or a higher one) also uses, if the lock implements priority inheritance or a ceiling protocol; with a plain mutex and no inheritance, B is unbounded (the priority-inversion story of F3-40). D1 (2) Jj of a higher-priority task makes its jobs arrive "bunched", which is why it appears inside the ceiling: in Listing 2 the estimator's first iteration counted ⌈(1,150 + 100)/1,000⌉ = 2 control jobs, not 1. R2 (3) The analysis holds for the model: independent jobs except for the stated locks, no self-suspension, C as a true upper bound, and a known overhead. Context-switch time and the kernel's own interrupt work must be added as extra terms (F3-39 showed a whole preemption appearing from a tiny overhead).



EDF with constrained deadlines: processor demand


When D < T, U ≤ 1 is necessary but no longer sufficient. The exact test asks, for every interval length L, whether the work whose release and deadline both fall inside the interval fits in it: dbf(L) ≤ L. D5 Sets X and Y in Listing 2 both have U = 0.875; X passes at every deadline, Y fails at L = 4, where P's first job (2 units by time 3) and Q's (3 units by time 4) need 5 units in 4 (Figure 2). R2 The program checks every integer L up to H + max D; for synchronous tasks this bound is enough, and smaller bounds exist when U < 1 (unverified detail below).



Overload: who misses?


Set 2 in Listing 1 has U = 1.1, more work than time. Under RM, A and B never miss and C misses all 6 of its deadlines in 120 units: the overload is absorbed by the lowest priority. Under EDF, A misses 10, B 7 and C 6: misses spread to every task (the domino effect). R1 For a robot this matters more than the 0.12 of extra utilisation EDF can use: when an execution time is underestimated, RM degrades predictably (the planner is late, the control loop is not), while plain EDF can make the control loop late. EDF-based systems therefore add budget enforcement: each task gets a reservation (runtime per period) and is throttled when it exceeds it, so an overrunning task harms only itself. D1 D6 That is exactly what Linux's SCHED_DEADLINE does.

More than one processor


All tests in this chapter are for one processor. On several processors there are two families: partitioned scheduling (each task is pinned to one processor; each processor is analysed with the one-processor tests, and the hard part is the bin-packing of tasks to processors) and global scheduling (one queue for all processors; the one-processor optimality results do not carry over, and a set with low total utilisation can still miss deadlines). D1 For robots the practical advice is partitioning: pin the hard real-time tasks to chosen processors (often isolated ones, F9-48) and analyse each processor separately.

How the hardware actually does it


The theory assumes that C is a fixed upper bound and that switching is free. Hardware breaks both. A job's execution time depends on the state of the caches, the branch predictors and the translation buffers it finds; a preemption by another task evicts some of that state, so the preempted job runs longer after it resumes (a cache-related preemption delay). D1 Every preemption also costs the kernel's switch path and, on a timer-driven kernel, the tick handler's work. EDF can preempt less than RM on the same set (in Figure 1, RM preempts B at 4 and at 8, EDF only at 8, where equal deadlines are broken in A's favour), but it must compare deadlines at every release. In practice C is measured on the target under realistic interference, inflated by a margin, and the margin is recorded in the analysis (F3-39's 0.8-tick surprise is the reason).

Where the analogy breaks


    

  • Drummers can see each other; a scheduler can only see what tasks declare. EDF needs every deadline and SCHED_DEADLINE needs every runtime and period in advance; a task that lies about its runtime is throttled, which no band leader could do to a drummer.
    • 

  • Handing the drum over is instant in the story; a context switch costs time and disturbs caches. The analysis must add those costs; the story's "always fits at U = 1" is only true in the zero-overhead model.
    • 

  • A bar is a fixed length for both drummers; deadlines need not equal periods. Set Y has U = 0.875 and still fails because deadlines are short, which has no counterpart in a song where every pattern has to end with its bar.
    • 




Common mistakes and debugging


    

  • Symptom: "U is below 1, so all deadlines are met", then misses. Cause: U ≤ 1 is exact only for EDF with D = T. Fix: for fixed priorities use RTA; for EDF with D < T use processor demand.
    • 

  • Symptom: "above the Liu–Layland bound, so not schedulable". Cause: treating a sufficient test as necessary. Fix: run RTA (the robot set at U = 0.88 passes).
    • 

  • Symptom: RTA promises 450 µs, measurement shows 4 ms. Cause: the model omits something real: the timer's jitter (J), blocking on an unprotected lock (B unbounded), a self-suspending task, kernel overhead, or another real-time thread not in the model. Find it: trace the worst case (F9-48, F9-49). Fix: add the missing term or remove the interference.
    • 

  • Symptom: sched_setattr fails with EBUSY. Cause: admission control: the requested bandwidth does not fit. Fix: forensic lab below.
    • 

  • Symptom: sched_setattr fails with EPERM. Cause: the process may not use real-time policies. Fix: run with the needed privilege or capability, as your system's documentation describes; never run a robot's whole software as root to work around it.
    • 

  • Symptom: a SCHED_DEADLINE task's work takes many periods. Cause: its runtime is smaller than its real execution time (part B). Fix: measure the execution time first, then reserve it with a margin.
    •

Summary


    

  • Rate-monotonic gives fixed priorities by period; EDF runs the job with the earliest absolute deadline.
    • 

  • EDF with D = T is schedulable on one processor if and only if U ≤ 1; RM can fail at U = 1 (set 1: RB = 7 > 6).
    • 

  • Quick tests (Liu–Layland, hyperbolic) are sufficient only; RTA with B and J is the exact fixed-priority test; processor demand is EDF's exact test for D < T.
    • 

  • Under overload RM confines misses to low priorities; plain EDF spreads them (domino), so EDF systems enforce budgets.
    • 

  • Linux SCHED_DEADLINE: EDF with per-task runtime/deadline/period; the run showed admission refused with EBUSY beyond the limit and an overrunning task throttled to its share.
    • 

  • One-processor results need partitioning to carry over to multi-processor robots.

Answers to Check yourself


    

  1. Run the ready job with the earliest absolute deadline. For D = T on one processor: schedulable if and only if U ≤ 1. Fixed priorities cannot always use the whole processor: a task can be forced to wait for a higher-priority job whose deadline is later than its own (set 1 at time 4), so some sets with U ≤ 1 fail.
    2. 

  2. Bound for n = 2: 0.8284; U = 0.4 + 0.4286 = 0.8286 is slightly above it: inconclusive. RTA: R = 3 → 3 + ⌈3/5⌉·2 = 5 → 3 + ⌈5/5⌉·2 = 5. R = 5 ≤ 7: schedulable.
    3. 

  3. B is the time a job waits for a lower-priority job inside a critical section on a shared resource. Without inheritance, a medium-priority job can preempt the lock holder while the high-priority job waits, and that can repeat, so the wait has no bound; inheritance or a ceiling lets the holder run at high priority until it releases the lock, which bounds the wait by one critical section.
    4. 

  4. With jitter, two consecutive jobs of task j can arrive closer than Tj apart (the first late, the second on time), so within a window of length w one more job can interfere; counting arrivals in a window of length w + Jj covers that worst case.
    5. 

  5. dbf(5) = 3 + 3 = 6 > 5: not schedulable, although U = 0.6. Both jobs must finish 6 units of work in the first 5 units of time. (The distractor "U < 1, so yes" applies only when D = T.)
    6. 

  6. RM: the balance controller has the shortest period, so it has the highest priority and never misses even under overload; the misses fall on C. EDF becomes acceptable with budget enforcement (reservations such as SCHED_DEADLINE's runtime per period), which throttles an overrunning task instead of letting it delay the others.
    7. 

  7. Six requests × 0.7 = 4.2 > 3.8 available; five requests = 3.5 fit. Expect 5 accepted and the sixth refused with EBUSY (if no other deadline tasks are present). Your run decides.
    8. 

  8. (c). The hyperbolic test guarantees RM schedulability with D = T, and any set schedulable by RM on one processor has U ≤ 1, hence is EDF-schedulable. (a) alone is true but incomplete; (d) is wrong because the test is sufficient.
    9. 

  9. Under EDF, B (deadline 6) was not interrupted at time 4 by A's second job (deadline 8), so B ran 2–5 in one piece; under RM, A preempted B at 4. Fewer preemptions mean fewer context switches and less cache disturbance, i.e. smaller real execution times.

Forensic lab answer key


Observation. Requests 1–4 accepted, 5 and 6 refused with "Device or resource busy" (EBUSY); requested 6 × 0.9 = 5.4 processors on a 4-processor machine. R3


Hypotheses. (a) A kernel bug would not refuse exactly at the arithmetic limit, and four identical requests succeeded. (c) Missing permission gives "Operation not permitted" (EPERM) and would refuse the first request too. (b) Admission control fits the error and the count.


Root cause. Limit ratio 950,000/1,000,000 = 0.95 per processor; 4 × 0.95 = 3.8. Four reservations use 3.6 and fit; a fifth would bring 4.5 > 3.8. The team reserved 90 % of a processor per controller "to be safe", which made the set unschedulable by construction. R4 (The exact kernel rule is in the chapter's unverified box; the numbers here are consistent with it.)


Fix. Measure each controller's execution time under load (F9-48), reserve that plus a stated margin (for example C = 200 µs per 1 ms would be bandwidth 0.2 + margin), and check the sum against the limit before deployment. Part B shows the opposite risk: a reservation below the real execution time throttles the task to its share (3 ms of work took about 30 ms), which for a controller means missed periods.


Prevention. Treat a refused reservation as a start-up failure: the robot stays in its safe state (motors disabled) and reports which service failed, instead of starting with some joints uncontrolled; include the bandwidth sum in a pre-deployment check.
