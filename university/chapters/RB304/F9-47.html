Story hook

Tomás is riding home and thinking about his homework. Suddenly the bicycle wobbles. A good rider drops the thought at once, steers, and only then goes back to the homework. Now imagine a rider who has promised himself: "once I start a thought, I finish it before I do anything else". Most of his thoughts are short, so he rides well most of the time. But now and then he starts a long one, and if the wobble comes during that thought, he falls.

A general-purpose operating system kernel is a little like that second rider. Most of its work can be interrupted, but some sections, once started, run to the end before anything else may run, however urgent. Usually they are short. The worst case is set by the longest one that happens to be running when your robot's control task wakes up. PREEMPT_RT is a way of building the Linux kernel so that almost all of its work can be dropped at once when something more urgent appears. This chapter shows what it changes, how to see which kind of kernel you have, and how to compare the two honestly.

What you will be able to do

  • Explain what keeps a ready high-priority task from running on Linux (non-preemptible sections, interrupt handlers, deferred work) and how PREEMPT_RT shrinks each.
  • Inspect a running kernel's preemption model, timer configuration, interrupt threads and real-time limits from its own files.
  • Predict from a model how the preemption model and the task's priority relative to interrupt threads shape the latency histogram.
  • Configure a real-time process correctly on a PREEMPT_RT system: policy, priority relative to interrupt threads, locked memory, priority-inheritance locks.
  • Plan the "with and without PREEMPT_RT on the same machine" measurement so that its result means something.
Jargon box
Kernel preemption model
Simple words: the rule that says when the kernel may stop what it is doing to run a more urgent task. Analogy: the rider's promise about finishing thoughts. Precise: a build-time (and on some kernels boot-time) choice of how often kernel code checks for and allows rescheduling: never inside the kernel except at explicit points ("none"), at additional voluntary points, almost anywhere outside sections that disable preemption ("full"), or, with PREEMPT_RT, almost anywhere at all. The build container's kernel shows CONFIG_PREEMPT_NONE=y and CONFIG_PREEMPT_DYNAMIC=y. D1 R1
PREEMPT_RT
Simple words: a way to build Linux so that nearly all kernel work can be interrupted by a more urgent task. Analogy: the rider who drops any thought the moment the bicycle wobbles. Precise: the Linux real-time preemption model: interrupt handlers run in kernel threads, most kernel spinning locks become sleeping locks with priority inheritance, and the remaining non-preemptible regions are kept short, so that the wake-up latency of the highest-priority task is bounded by small, analysable sections. Its configuration option was not present in the build container's kernel configuration. D1 R1
Non-preemptible section
Simple words: a stretch of kernel code that nothing else may interrupt to run another task. Analogy: a thought the second rider must finish. Precise: code that runs with preemption disabled (explicitly, while holding a spinning lock, or in interrupt context) or with local interrupts disabled; a task that becomes ready meanwhile cannot run on that processor until the section ends (OS303 introduced the preemption count). D1 D2
Threaded interrupt handler
Simple words: an interrupt handler that runs as a normal kernel task with a priority, instead of immediately. Analogy: a message passed to a helper, who deals with it when the rider's more urgent steering is done. Precise: a handler split into a minimal part in hard-interrupt context, which acknowledges the device and wakes a kernel thread, and the main part, which runs in that thread under a scheduling policy and priority; such threads are named irq/<number>-<name>, and the two on the build container ran as SCHED_FIFO priority 50. D1 R2
Wake-up latency (scheduling latency)
Simple words: the time from "this task should run now" to "it is running". Analogy: from the wobble to the first steering movement. Precise: for a timer-driven task, the time from the programmed expiry to the moment the task executes its first instruction after the wake-up; it includes timer interrupt latency, the time until the scheduler may run, the scheduling decision and the context switch. D1 D3
Real-time throttling
Simple words: a safety limit that keeps real-time tasks from taking every last moment of a processor. Analogy: the rule that the drummer must leave a short pause each minute for others. Precise: the kernel's limit on processor time for real-time tasks, configured by /proc/sys/kernel/sched_rt_runtime_us per sched_rt_period_us; the build container read 950,000 per 1,000,000 µs (F9-46). D4 R3

Terms from earlier chapters: preemption count, IRQ-safe lock (OS303); priority inheritance, priority inversion (OS305); interrupt latency (HW204); tickless timer (OS302); SCHED_DEADLINE (F9-46).

The idea in pictures

Layer 1 — the kid explanation

A computer's operating system does a lot of housework: it moves data to and from disks and networks, answers devices, and tidies memory. Some of that housework, once started, cannot be paused. If your robot's balance program wakes up during such a piece, it has to wait until the piece is finished.

Usually the wait is tiny. But a robot must be safe in the worst moment, not the usual one. PREEMPT_RT rebuilds the housework so that almost every piece can be paused. The urgent program goes first; the housework finishes afterwards.

The housework does not get faster. Sometimes it even gets a little slower. What improves is the worst wait of the most urgent job, and that is what a robot needs.

Layer 2 — the student explanation

What delays a woken task

When your control task's timer expires, the following must happen before its first instruction runs: the timer hardware interrupts a processor; the interrupt is taken when interrupts are enabled; the timer code marks the task runnable; the scheduler decides it should run; a context switch happens at the next point where the kernel allows preemption. D1 D3 On a general-purpose kernel the longest of these waits is usually the last: the processor may be inside kernel code that has disabled preemption (holding a spinning lock, for example), inside an interrupt handler, or processing deferred interrupt work ("softirqs"), and the task waits until that code reaches a point where preemption is allowed. D1 Your own program's priority does not shorten such sections; they belong to the kernel.

What PREEMPT_RT changes

The Linux kernel documentation's "Real-Time Preemption" pages describe the approach; the main points are: D1

  • Interrupt handlers become threads. Only a minimal part runs in hard-interrupt context; the rest runs in a kernel thread with a real-time priority, which a higher-priority task can preempt.
  • Most spinning locks become sleeping locks with priority inheritance. Code holding them can be preempted; a high-priority task that needs a lock held by a low-priority one raises that holder's priority instead of waiting for an unbounded time.
  • Deferred interrupt work runs in task context, where it can be scheduled and preempted.
  • What remains non-preemptible is kept short: a small set of "raw" locks and sections in core code.

The result is not a faster kernel. It is a kernel whose worst-case wake-up latency for the highest-priority task is bounded by short sections, at some cost in throughput. D1 The exact list of what stays non-preemptible depends on the kernel version and its drivers, which is why every real-time system is measured (F9-48).

Layer 3 — the engineer's depth


Priorities on a PREEMPT_RT system


Once handlers are threads, they compete with your tasks by priority. If the control task's priority is below the handler threads, every handler that runs when it wakes is added to its latency; this is the forensic lab of this chapter. The usual design places: (1) the hard control task(s) above the handler threads, (2) the handler threads of devices the control path depends on (the motor bus, the IMU's interface) raised above the control task or directly below it, as the data path requires, (3) everything else below. D1 D5 Raising a handler thread above your task is right when your task waits for that device's data: otherwise the task would run, find no data, and wait anyway. Priorities of handler threads can be changed with chrt on the thread's process id; the build container has chrt and taskset installed (used while preparing this chapter to read the handler threads' policy).


Two further rules: never give a task SCHED_FIFO 99 without a reason (the kernel's own per-processor helper threads ran at 99 on the build container when inspected with chrt -p during preparation; a user task there competes with them) and never let a SCHED_FIFO task spin: on its processor nothing of lower priority runs while it spins, except for the throttling margin. D4

Locks in user space


PREEMPT_RT bounds priority inversion inside the kernel. Your program must do the same for its own locks: a POSIX mutex shared between the control thread and a lower-priority thread should use the priority-inheritance protocol (pthread_mutexattr_setprotocol with PTHREAD_PRIO_INHERIT), and better still, the control thread should not share locks at all, but exchange data through lock-free single-producer single-consumer buffers (F9-49, F2-42). D5 D6 The protocol names are those of POSIX; check that your C library implements them on your kernel (unverified box in Common mistakes).



The rest of the system


The kernel is one source of latency. Others are below it and around it: firmware that takes the processor away without the operating system knowing (system management interrupts on PCs), power management (deep idle states take time to leave; frequency changes), devices and drivers whose handlers or locks are long, and virtualisation (a virtual processor may not be running at all when its timer expires). The kernel documentation's hardware considerations for real-time lists such topics. D1 A robot computer is therefore chosen and configured as a whole: the kernel model, the boot options that isolate processors and move interrupts away from them, the BIOS or firmware settings, and the drivers in use. RB403 (F9-66, F9-67) builds such an image; this chapter's lab measures one.

What it costs


Sleeping locks, more context switches (handlers are threads) and priority inheritance add work. A PREEMPT_RT kernel may therefore show lower throughput for the same workload, and the median latency may not improve at all. D1 Judge it by the requirement: the course's requirement is a bound on the control loop's worst lateness, not the build time of a large program. Measure both if both matter.



Linux with PREEMPT_RT, an RTOS, or both


The bridge BR-05 listed the trade: an RTOS on a microcontroller gives small, analysable timing for small programs; Linux gives drivers, networking, ROS 2 and large memory, with real-time behaviour only after configuration and care. Many robots use both: the fastest loops (motor current, sometimes joint position) on a microcontroller (F9-51), the coordinating loops at hundreds of hertz to a few kilohertz on Linux with PREEMPT_RT, and planning and perception as soft tasks. How the hardware actually does it


Interrupts reach a processor through the interrupt controller (an APIC on x86 PCs, a GIC on most Arm systems, DR402); the processor takes one only when its interrupt-enable state allows it, which is why "interrupts disabled" sections add directly to latency. D2 Threaded handlers move the long part of the handler out of that state, but the device itself may still need a fast response: its first-level acknowledge remains in the hard handler. The interrupt lines of the build container are virtual (virtio devices, a serial port, ACPI event lines in /proc/interrupts), and the timer interrupt of a virtual machine is itself delivered by the host; a measurement there includes the host's scheduling (F9-48 sees it). On a real robot computer, the chipset's power management and firmware handlers are the hardware-level causes left after the kernel is fixed, and they are found by measuring with everything else quiet.

Where the analogy breaks


    

  • The rider decides himself what to drop; the kernel's preemptibility is fixed by how the code was written and built. No setting at run time turns a non-RT kernel's long non-preemptible section into a preemptible one.
    • 

  • Dropping a thought costs the rider nothing; preempting the kernel costs time and throughput. Locks that sleep, extra switches and inheritance are real work.
    • 

  • The rider has one body; a robot computer has several processors. A long section on one processor does not delay a task on another, which is why isolating processors (F9-48) helps even without PREEMPT_RT, and why the model's single processor is a simplification.
    • 




Common mistakes and debugging


    

  • Symptom: PREEMPT_RT installed, latency no better. Cause: the task is not real-time (SCHED_OTHER) or is below the handler threads (forensic lab), or the machine was not rebooted into the RT kernel. Check: Listing 1 and chrt -p on your task. Fix: SCHED_FIFO above the relevant handler threads.
    • 

  • Symptom: the whole machine becomes unresponsive when the control program has a bug. Cause: a SCHED_FIFO thread that spins. Fix: every real-time thread must block; keep real-time throttling on during development; test new real-time code in a simulator first.
    • 

  • Symptom: rare latency spikes on an RT kernel, all on one processor. Cause: a device's handler or deferred work bound to that processor, or firmware activity. Find it: F9-48's per-processor measurement and the kernel's tracing tools. Fix: move interrupts away, isolate the processor.
    • 

  • Symptom: priority inversion in user space despite PREEMPT_RT. Cause: a plain mutex shared with a low-priority thread. Fix: priority-inheritance mutexes or no shared locks.
    •

Transition box

Where you came from: F9-46 analysed task sets assuming the operating system lets the highest-priority ready task run at once; OS303 built a kernel with a preemption count and IRQ-safe locks; F3-40 showed priority inheritance on an RTOS. What carries over: priority-driven scheduling, the blocking term B of RTA (now including kernel sections), priority inheritance, and the habit of reading what the system really is instead of assuming. What changes: the "operating system overhead" term is no longer small and fixed: on Linux it is set by the kernel's preemption model, its drivers and the hardware; interrupt handlers become tasks with priorities you must place; and a real-time kernel trades throughput for a bounded tail. What comes next: F9-48 measures latency for real on Linux, with histograms, load, priorities, locked memory and page faults, so that the numbers in your analysis come from evidence.

Summary


    

  • A woken task waits for timer handling, the scheduler, and above all the end of whatever non-preemptible work is running.
    • 

  • PREEMPT_RT threads interrupt handlers, turns most kernel spinning locks into priority-inheriting sleeping locks and keeps the rest short; it bounds the tail, not the median.

Forensic lab answer key


Observation. All six worst wake-ups (741–850 µs) happened while "storage handler" was running; the 99th percentile is 489 µs against 8 µs in the "rt" run with the same background. R5 R4


Hypotheses. (a) RT not active: in the model the long kernel sections no longer appear in the cause list (they did in the stock run), so the RT behaviour is active. (b) Firmware stalls would not correlate with one handler. (c) Priority: every worst case is a handler, i.e. work that runs at priority 50, above the task at 40.


Root cause. On a PREEMPT_RT kernel, handlers are threads at SCHED_FIFO 50 (Figure 1, and the probe's two threads); a control task at 40 waits for each of them. The team's "polite" priority put the robot's most urgent work below the disk and network handlers.


Fix. Run the control thread above the handler threads (for example 80), after checking no other thread of the system uses that range; if the control loop waits for a specific device (the motor bus), raise that device's handler thread directly above or below the control task as the data flow requires. Re-measure: the model's "rt" configuration is the expected shape (maximum 12 µs under its assumptions).


Prevention. A start-up check that reads the control thread's policy and priority and the handler threads' priorities and refuses to enable the motors if the control thread is below a configured threshold; record the priority map in the design document.
