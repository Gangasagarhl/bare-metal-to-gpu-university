Story hook

A drummer's teacher says: "Play along with the click for one minute." The student is perfect for fifty-nine seconds and a bit late once. "Fine," says the student. The teacher answers: "In the concert you play for two hours. How late is the worst beat going to be? And does it get worse when the stage lights are hot and the audience is loud?"

That is the question of this chapter. A control loop must be on time in its worst cycle, under the load the robot really has, for as long as the robot runs. You will build a small tool that measures exactly that, and you will see four results that every robot engineer should have seen once with their own eyes: an average that hides the problem, load that multiplies the tail, a real-time priority that fixes most of it, and a page fault that hides in a line of code that looks harmless.

What you will be able to do

  • Build a wake-up latency tester that uses absolute release times and records every cycle.
  • Report latency as a histogram with percentiles, maximum, sample count and the exact conditions.
  • Measure the effect of load, scheduling policy, locked memory and per-cycle allocation, and explain each result.
  • Find page faults inside a real-time loop from evidence, and remove them.
  • Judge what a measurement can and cannot prove about the worst case.
Jargon box
Percentile
Simple words: the value below which a given share of the measurements falls. Analogy: the 99th percentile of beats is the lateness that only 1 beat in 100 exceeds. Precise: for n sorted samples, the pth percentile is the sample at a chosen index near p/100·n; Listing 1 uses index ⌊p/100·n⌋, so its "p99.9" of 5,000 samples is the fifth-largest sample. Always state n with a percentile. D4
Latency histogram
Simple words: a count of how many cycles had each amount of lateness. Analogy: a chart of all the drummer's beats, sorted by how late they were. Precise: counts per lateness bin; for latency the bins are best spaced roughly logarithmically, because the interesting part is the long, sparse tail and not the dense median. D3
Tail latency
Simple words: the rare, large latencies at the end of the histogram. Analogy: the few beats that went badly wrong in two hours. Precise: the high percentiles and the maximum of a latency distribution; for hard deadlines the maximum observed is the evidence, and even it is only a lower bound of the true worst case.
Page fault
Simple words: the processor finding that a memory page is not ready and asking the kernel to prepare it. Analogy: the drummer reaching for a stick that is still in the bag. Precise: an exception taken when a virtual address has no valid mapping or the access is not allowed; a minor fault is resolved without reading from storage (for example a new zero-filled page), a major fault needs storage I/O. Both run kernel code inside the faulting thread. D2
Locked memory (mlockall)
Simple words: telling the kernel to keep all of the program's memory in RAM and ready. Analogy: laying every stick and brush out before the concert. Precise: mlockall(MCL_CURRENT | MCL_FUTURE) asks the kernel to keep all current mappings and future ones in RAM, so they are not paged out; it does not stop a program from creating new mappings inside its loop. D2
Background load
Simple words: other work the computer does during the measurement. Analogy: the hot lights and loud audience. Precise: a defined, repeatable set of competing activity (processor, memory, input/output, interrupts) under which the latency is measured; a latency number without its load is not a result.

Terms from earlier chapters: start latency, jitter (F9-45); wake-up latency, PREEMPT_RT (F9-47); virtual memory (OS301).

The idea in pictures

Layer 1 — the kid explanation

To find out whether a clock-driven program is always on time, you let it set an alarm many thousands of times and write down, every time, how late it woke up. Then you count: how many times was it a little late, how many times very late, and what was the latest of all.

You do it while the computer is busy, because a robot's computer is busy. You do it for a long time, because rare problems are rare. And you write down exactly how you did it, so somebody else can do it again and check.

Layer 2 — the student explanation

The tool

Listing 1 is a small tester in the style of the classic "cyclic test": one measuring thread sleeps until absolute release times with clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, …), reads the clock on waking, and stores the difference. It can run the thread under SCHED_OTHER or SCHED_FIFO, lock memory, start load threads, and do per-cycle work that touches either freshly allocated or prepared memory. D2 D3 Three rules make its numbers trustworthy:

  1. Absolute release times (F9-45): a late cycle does not move the following releases, so every sample is measured against the true schedule.
  2. Nothing allocated in the loop except what the experiment wants: the result arrays are created and touched before the loop starts, and printing happens after it.
  3. Every sample kept, then sorted for percentiles and binned for the histogram, with the sample count printed.
Not verified — check before relying on this

Check the rt-tests documentation before using it, and compare its numbers with Listing 1 on your machine.

  • Load hurts the tail far more than the median. SCHED_OTHER's median moved from 98.3 to 113.4 µs; its 99th percentile from 238.1 to 5,818.6 µs; its maximum from 2.1 to 15.5 ms. 55 cycles were 5 ms or more late, five whole periods. R2 R3
    • 

  • Real-time priority removes most of the load's effect. With SCHED_FIFO 80 under the same load: median 42.0, p99 141.5, maximum 3,100.4 µs. The load threads are SCHED_OTHER, so they never run before the measuring thread when it is ready. R4
    • 

  • Not all of it. 3 cycles of 5,000 were still 2–5 ms late. On this machine a woken SCHED_FIFO thread can still wait for non-preemptible kernel work (the kernel is PREEMPT_NONE, F9-47) and for the host, which may not be running the virtual processor at all. This measurement cannot tell the two apart; a tracer could tell the first (Layer 3), and only bare hardware removes the second.
    • 

  • The median is lower for SCHED_FIFO even without contention (42 against 98 µs). A likely cause is timer slack, the kernel's permission to delay ordinary threads' timer expiry slightly to group wake-ups; it does not apply to real-time threads (unverified box below). The minimum of about 22–25 µs for SCHED_FIFO is this virtual machine's floor; bare hardware is usually lower.

Not verified — check before relying on this
That ordinary threads have a default timer slack of 50 µs and real-time threads none, and that it can be read and changed per thread (prctl with PR_SET_TIMERSLACK, /proc/<pid>/timerslack_ns), is from the author's memory and was not tested in this build. Check the man pages prctl(2) and proc(5), then test: if true, setting the slack of the SCHED_OTHER measuring thread to 1 ns should move its median close to the SCHED_FIFO median.



How to report a measurement


A latency result is a sentence with all of these parts: what was measured (wake-up latency of a periodic thread, 1,000 µs period), how many samples (5,000, i.e. 5 seconds), the distribution (histogram, p50, p99, p99.9, maximum), the conditions (machine, kernel and its preemption model, policy and priority, locked memory, load, processor placement) and the tool and its version. The .log next to every output in this course records them (BR-08). Five seconds is far too short for a robot; it was chosen to keep the build fast. Real qualification runs last hours, with the robot's real load. D3



Layer 3 — the engineer's depth


Page faults in the loop


Locking memory with mlockall keeps every page that exists, and (with MCL_FUTURE) every page of mappings created later, in RAM. It does not stop the loop from creating new mappings. Listing 1's --work fresh allocates a 256 KiB vector every cycle; with glibc's threshold for using a separate mapping fixed at 128 KiB (line 129), each such allocation becomes a new mapping that the kernel must create, populate and later remove. --work reuse touches a vector prepared before the loop. Both under SCHED_FIFO 80 with locked memory and no load: R5 R6






195,033 minor faults in 3,000 cycles is 65 per cycle: one for each of the 64 pages of 4 KiB in 256 KiB, plus one. The median work time is 79.8 µs against 1.2 µs: the loop's real work (touching 64 bytes) is the same, and 98 % of the time went into the kernel's page handling. The wake-up latency tail is also worse with fresh memory (p99.9 2,065.0 against 620.0 µs) — a plausible cause is the extra kernel work for mapping and unmapping, but these two short runs on a shared virtual machine do not prove it. R5 R6


The rules that follow (F9-49 applies them to a ROS 2-style node): allocate everything before the loop; reserve container capacity; touch stack and heap you will need (pre-fault); lock memory; check with a fault counter like line 44 that the loop's count is zero. D1 D2


Not verified — check before relying on this
That glibc adapts its mapping threshold at run time by default (the reason line 129 fixes it), and the exact meaning of M_MMAP_THRESHOLD, are from the author's memory; check the man page mallopt(3). What was verified: with the threshold fixed at 128 KiB the fresh work faulted 65 times per cycle, and with prepared memory zero times.



Processors, interrupts and isolation


On a machine with several processors, the next step after priority is placement: run the control thread on a processor that runs nothing else and receives as few interrupts as possible. The Linux mechanisms are processor affinity (sched_setaffinity, the taskset tool), interrupt affinity (per interrupt line), and boot-time isolation of processors from the general scheduler (F9-47's unverified box). D1 Measure per processor: a latency problem caused by one device often appears only on the processor that receives its interrupts. F9-50's lab pins its controller to a processor and reports the effect on this machine.



From "how late" to "why late"


A histogram tells you how late; a trace tells you why. The Linux kernel's tracing system can record scheduling events, interrupt entry and exit, and how long preemption or interrupts were disabled, and can stop when a latency threshold is exceeded so that the last events before the bad cycle are kept. D1 F9-49 uses a small trace of its own (which callback ran when) to find a cause inside the program; the kernel tracer does the same for causes inside the kernel.


Not verified — check before relying on this
Kernel tracing names from memory, not used in this build: the "ftrace" framework under the tracing file system, tracers that record the longest interrupts-off and preemption-off sections and the wake-up latency of the highest-priority task, and a break-on-threshold option in cyclictest that stops the trace. The build container's kernel has CONFIG_PREEMPT_TRACER not set (F9-47's config.out), so the preemption-off tracer is not available there. Check the kernel's tracing documentation for your version.



What a measurement proves


A measured maximum is a lower bound on the true worst case: the true worst is at least that bad. No number of samples turns it into an upper bound. Engineers combine three things: analysis of what can happen (F9-46, F9-47's model), measurement under the worst realistic load for long periods, and margin: a requirement that the measured maximum, with the conditions recorded, stays well under the deadline. How much margin and how long a run are project decisions; write them down with the result. D4



How the hardware actually does it


The clock that Listing 1 reads (CLOCK_MONOTONIC) is backed by a hardware counter; on the build container the kernel's clock source was tsc, the processor's time-stamp counter (F9-47's config.out). R1 Reading it is fast and does not enter the kernel on most systems, so the measurement disturbs the result little. The wake-up itself starts from a timer interrupt programmed for the release time; its accuracy depends on the timer hardware and, on a virtual machine, on the host delivering it. A page fault is an exception raised by the memory management unit when a translation is missing (OS301): the processor stops the instruction, runs the kernel's handler, which finds or zero-fills a physical page and writes the page table, and then retries the instruction. 64 of those per cycle are what the fresh-work run shows.

Where the analogy breaks


    

  • A drummer's late beat is heard at once; a late control cycle may have no visible effect until the rare unlucky combination. That is why the measurement must be long and the analysis must exist.
    • 

  • Recording a drummer does not change the playing; measuring a computer does a little. Reading the clock and storing the sample take time, and a heavy tracer can change the timing it records.
    • 

  • A concert has one stage; the robot's computer has the load of all its own software. The right "background load" is the robot's software itself, not an artificial one alone.
    • 




Common mistakes and debugging


    

  • Symptom: a beautiful histogram in the lab, failures on the robot. Cause: measured idle, or for one minute. Fix: measure under the robot's load for hours; report the conditions.
    • 

  • Symptom: only averages reported. Fix: histogram, percentiles, maximum and sample count; Figure 2 is the reason.
    • 

  • Symptom: the tool's own latency explodes after a few minutes. Cause: the tool grows a vector or prints inside the loop. Fix: preallocate, print afterwards.
    • 

  • Symptom: SCHED_FIFO "has no effect". Cause: the call failed silently (no permission; RLIMIT_RTPRIO 0 for a normal user, F9-47), or it was set on the wrong thread. Fix: check the return value and print the applied policy, as lines 149–152 do.
    • 

  • Symptom: rare spikes even with SCHED_FIFO and locked memory. Check: the fault counter of the loop; the kernel's preemption model; interrupts on that processor; virtualisation or firmware. Find: a kernel trace stopped at the spike.
    •

Lab


Goal. Measure your machine's wake-up latency under controlled conditions, find the effect of load, policy and in-loop allocation, and write a report another engineer can repeat.


Hardware and software needed. A Linux computer, g++ 13.3.0 (as in the logs) or similar, permission for real-time priorities (a user with an RLIMIT_RTPRIO above 80, or root on a test machine). Run university/labs/run_lab.sh university/labs/F9-48.


Safety
A SCHED_FIFO thread that never sleeps can freeze a processor. Listing 1's measuring thread always sleeps; if you change it, keep real-time throttling enabled (F9-47) and test on a machine you can reset. Do not run load tests on a robot's computer while it drives motors. See the course safety rules.

Troubleshooting.


    

  • "SCHED_FIFO refused: Operation not permitted" → raise the user's real-time limit (your distribution's limits configuration) or use a test machine as root.

Forensic lab answer key


Observation. Fresh: work p50 79.8 µs, maximum 2,464.6 µs, 195,033 minor faults (65 per cycle). Reuse: work p50 1.2 µs, maximum 1,482.3 µs, 0 faults. R5 R6


Hypotheses. (a) Slower computation would not produce faults. (b) Sharing the processor would show in wake-up latency more than in work time and would not produce faults in this thread (the counter is per thread). (c) Faults per cycle equal to the page count of the buffer: confirmed.


Root cause. A 256 KiB buffer above the allocator's mapping threshold is a new mapping each cycle; its 64 pages are provided by the kernel each time and returned at the end. mlockall keeps existing pages resident; it does not make new ones free.


Fix. Make the buffer a member created and touched at start-up (the "reuse" branch, lines 73–74), and keep the step function free of allocation.


Prevention. A test that runs the controller for N cycles and asserts that the loop's minor-fault count (line 44's counter) and an allocation counter (F9-49) are zero; run it in continuous integration.


How the evidence was made. The same program with --work fresh and --work reuse, both SCHED_FIFO 80, locked memory, no load, 3,000 cycles, back to back.
