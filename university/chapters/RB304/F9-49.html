Story hook

A small band has only one musician. She plays the drums, and every ten bars she also has to turn the page of the sheet music for the whole band, which takes her a few seconds because the pages stick. Every time she turns a page, the beat stops. Nobody would build a band that way. Yet a ROS 2 node can be built exactly that way without anybody noticing: the 1 kHz control callback and a "harmless" 10 Hz logging callback share one thread, and every time the logger runs, the control loop waits.

This chapter takes a node like that, measures it, finds the cause in a trace, and rebuilds it so that the control path has its own thread with a real-time priority, no memory allocation, and a lock-free hand-over to everything else. Then the same rules are mapped onto ROS 2's own concepts, which the build container could not run, so they come with honest boxes.

What you will be able to do

  • Explain how an executor turns callbacks into work on threads, and what a callback group guarantees.
  • Diagnose a late control callback from a callback trace: which callback ran instead, and why it could.
  • Design the thread and group structure of a node with a hard control path and soft side tasks.
  • Remove allocation, locks and blocking calls from a control path and prove it with counters.
  • Hand data from the real-time thread to non-real-time threads through a preallocated lock-free ring, and account for drops.
Jargon box
Executor
Simple words: the part of a robot program that decides which waiting piece of work runs next, and on which thread. Analogy: the musician who plays the parts given to her, one at a time. Precise: a loop that waits for events (timer expiry, arriving messages, service requests), then calls the callbacks registered for them on the thread or threads it owns; ROS 2 provides executors of this kind (RB303). Listing 1 is a miniature with one thread that serves timers only. D1
Callback group
Simple words: a set of callbacks with one rule about whether they may run at the same time. Analogy: the parts written for one player. Precise: in ROS 2, a grouping of callbacks that the executor serves under the group's rule (callbacks of a "mutually exclusive" group never run concurrently); a group is added to one executor, so groups are how a node's callbacks are split between threads. Listing 1's groups are mutually exclusive by construction. D1
Real-time path (control path)
Simple words: the chain of code that must finish before the deadline every cycle. Analogy: the drumbeat. Precise: the callbacks and functions between reading the sensor and writing the command in each control cycle, including everything they call; every operation on it must have a bounded, known duration. D2
Lock-free ring buffer
Simple words: a fixed circle of slots where one thread writes and another reads, without waiting for each other. Analogy: a rack of sheet-music pages: the drummer drops each page in; the page-turner takes them out. Precise: a single-producer single-consumer queue of fixed capacity, with head and tail indices updated with atomic release and acquire operations, so neither side ever blocks; when it is full, the producer drops the item and counts it (F2-42). D3
Allocation-free loop
Simple words: a loop that never asks for new memory while it runs. Analogy: every stick laid out before the concert. Precise: a code path that performs no heap allocation or deallocation after initialisation (no new, no growing containers, no string building); verified by counting allocations per thread, as Listing 2 does by replacing the global operator new. D2

Terms from earlier chapters: jitter (F9-45); blocking term (B) (F9-46); page fault, locked memory, tail latency (F9-48); priority inversion (OS305).

The idea in pictures

Layer 1 — the kid explanation

A robot program has many little jobs: steer the motors, read the camera, write a diary of what happened. Something has to decide which job runs when; that something is called the executor. If one worker does all jobs one after another, a slow job (writing the diary) makes the fast, important job (steering) wait.

So you give the steering job its own worker, who is allowed to go first and never stops to do anything slow. The steering worker drops short notes into a box; the diary worker picks them up later and writes them down at his own pace.

Layer 2 — the student explanation

Executors and groups, in miniature

ROS 2 programs hand their callbacks to an executor, which waits for events and runs the callbacks on its threads (RB303). D1 ROS 2 is not installed in the build container, so Listing 1 implements the idea in about 120 lines: a CallbackGroup holds periodic timers; an Executor owns one thread, sleeps until the earliest timer is due, then runs every due callback of its groups in order, and records each run (release, start, end) in a trace allocated before spinning. It is not ROS 2's executor; it has the two properties that matter here: one thread runs one callback at a time, and a callback cannot be interrupted by another callback of the same executor.

Listing 2 is a node with a 1 kHz control callback (a PI controller driving a simulated motor) and a 10 Hz logging callback that formats the recent samples and writes them (to /dev/null, a real system call). It runs in two configurations.

The fixed configuration


Four changes, each one rule from F9-47 and F9-48: (1) control in its own group on its own executor thread, (2) that thread at SCHED_FIFO 80, (3) memory locked and the control callback free of allocation, (4) records handed to the logger through a 512-slot lock-free ring (Figure 2). D2 Result: R3




    

  • Misses 74 → 3; p99 start lateness 2,185.3 → 224.4 µs; maximum 4,653.0 → 1,919.4 µs.
    • 

  • 0 allocations in the control path, 0 records dropped; the logger did the same work (2,944,320 bytes in both runs) on its own thread, and its own lateness (up to 2,040.5 µs) no longer matters to the controller.
    • 

  • The trace around the worst control start contains only control callbacks: nothing in this program delayed it. The remaining tail comes from outside the program, as in F9-48 (non-RT kernel, virtual machine).
    • 

  • The final speed is the same in both runs (0.558): the controller's arithmetic depends on the cycle count, not on the timing, because this simulated motor advances by exactly 1 ms per call. On a real motor, late cycles change the physics (Layer 3).

Layer 3 — the engineer's depth


Mapping to ROS 2


The structure of the fixed configuration is the one recommended for ROS 2 real-time nodes in its documentation and talks: real-time callbacks in their own callback group, that group in an executor whose thread has a real-time policy and priority, everything else in other groups and executors, memory prepared and locked before the loop, and no allocation, blocking or unbounded work on the real-time path. D1 D2


Not verified — check before relying on this
ROS 2 names from the author's memory, none compiled in this build (ROS 2 is not installed in the build container): the rclcpp executors SingleThreadedExecutor, MultiThreadedExecutor, StaticSingleThreadedExecutor and the newer EventsExecutor (availability depends on the ROS 2 distribution); callback group types MutuallyExclusive and Reentrant created with create_callback_group, and passed to timers and subscriptions in their options; adding a group to a specific executor with add_callback_group instead of adding the whole node; that a multi-threaded executor runs callbacks of different groups in parallel but gives no priorities; that the executor thread's priority is set by the program, for example with pthread_setschedparam before spinning, because ROS 2 does not set it. Check the ROS 2 documentation for your distribution ("Executors", "About callback groups", real-time guidance) and test a node with a trace before relying on any of this.


Memory on the real-time path


Everything F9-48 measured applies inside ROS 2, with additions: messages are objects whose fields (strings, unbounded sequences) may allocate when filled or copied; publishing and receiving go through middleware layers that may allocate or lock internally. D2 The practical approach: prove the path allocation-free with a counter like Listing 2's (lines 27–35); keep messages on the real-time path of fixed size; and do not publish from the real-time thread directly, but hand data through a ring to a non-real-time thread that publishes.


Not verified — check before relying on this
From memory, not tested in this build: the realtime_tools package's real-time-safe publisher and buffer classes (which hand messages to a non-real-time thread internally); the "ros2_tracing" tools, which record executor and callback events with the kernel's tracer and can produce traces like Listing 2's for a real node; allocator options for messages and publishers; that the default DDS middleware may allocate during publish. Check each package's documentation for your distribution.



The ring and its failure mode


The ring (lines 40–63) is the same algorithm as F2-42's and F9-51's: the producer writes the slot, then publishes the new head with a release store; the consumer reads the head with an acquire load before reading the slot. D3 When the ring is full, push returns false and the control callback counts a drop instead of waiting. Size it from the rates: control produces 100 records per logging period, so 512 slots allow the logger to be up to about five periods late before drops start. Waiting would move the logger's lateness into the control loop, which is what the fix removed. A drop counter must be reported (line 220) so that losing data is visible, not silent; F9-51's forensic lab is what happens when it is not watched.



When late cycles change the physics


Listing 2's motor advances exactly 1 ms per control call, so its final speed is the same in both runs. A real motor keeps moving while the callback waits; a PI controller that assumes dt = 1 ms when 5 ms passed computes the wrong integral and acts on old data. Measure dt each cycle and use it, or better, keep the cycles on time; and treat repeated misses as a fault (F9-50 turns misses into a requirement with a test).



How the hardware actually does it


Two executor threads become two kernel threads, which the scheduler places on processors; the build container has 4. While the logger formats text on one processor, the control thread can run on another; with one shared thread, the second processor sits unused and the control callback waits. The ring's indices live in memory shared between processors; the release and acquire operations make sure that the processor running the logger sees the slot's contents before it sees the new head index (how much a processor reorders memory accesses on its own differs between architectures; the C++ atomics give the same guarantee on all of them, by limiting both the compiler and, where needed, the processor). D3 Locked memory keeps the control thread's pages resident, so it takes no page faults (F9-48).

Where the analogy breaks


    

  • A musician can tell when she is falling behind; an executor runs its callbacks blindly. Nothing in the executor knows about deadlines; only your measurement does.
    • 

  • Two musicians share one beat by listening; two threads share data only through memory. The ring's memory ordering rules are what listening is for threads.
    • 

  • Adding players to a band costs salaries; adding threads costs context switches and memory, and more threads at real-time priority make the system harder to analyse. One real-time thread per rate or per independent path, not one per callback.
    • 




Common mistakes and debugging


    

  • Symptom: control misses deadlines periodically, at the rate of another callback. Cause: both in one group or one single-threaded executor. Find: a callback trace (Listing 2's, or the ROS 2 tracing tools). Fix: separate groups on separate executors.
    • 

  • Symptom: separate groups, still late. Cause: the executor thread is SCHED_OTHER (nobody set its priority) or competes with other real-time threads. Check: chrt -p on the thread; print the policy as Listing 1 does.
    • 

  • Symptom: rare long cycles that correlate with nothing. Cause: allocation (a log message, a growing container, a message with an unbounded field) or a lock shared with a slow thread. Find: allocation counter and page-fault counter on the control thread. Fix: preallocate; ring instead of lock.
    • 

  • Symptom: after the fix, log records are missing. Cause: the ring was too small for the logger's worst lateness. Fix: size from rates, report drops, and decide whether drops are acceptable for that data.
    • 

  • Symptom: "printf debugging" makes the loop late. Cause: console output is a system call that may block. Fix: log through the ring.
    • 




Transition box

Where you came from: RB303 wrote ROS 2 nodes with callbacks and an executor; F9-48 measured latency and found page faults; F9-47 set thread priorities against the kernel's own threads. What carries over: absolute release times, real-time priority for the control thread only, locked and preallocated memory, histograms and traces as evidence. What changes: the unit of scheduling you design with is no longer a thread you wrote but a callback that a framework calls; the structure of executors and groups decides what can delay what, and the hand-over between threads becomes a data structure you must size. What comes next: F9-50 looks at ros2_control, where the framework itself fixes the real-time loop (read, update, write) and your code becomes a controller and a hardware interface inside it.

Summary


    

  • An executor runs one callback at a time per thread; a long callback delays every other callback on that thread.

  • No allocation, locks or blocking calls on the control path; count allocations to prove it.

Forensic lab answer key


Observation. Between the control callback ending at −881.6 µs and the worst control start at +4,653.0 µs, the logging callback ran from −881.5 to +4,604.4 µs. Logging runs take 3,020.9 µs at the median. R2


Hypotheses. (a) The control callback's median duration is 3.0 µs: it is not slow. (b) The kernel or machine may add some delay, but the worst case follows a logging run exactly. (c) Confirmed by the trace. (d) 6,024 allocations in 2,999 runs: present, a source of rare long cycles (maximum duration 174.1 µs) and a risk, but not the cause of the 4.6 ms gaps.


Root cause. The logging callback shares the control callback's single executor thread; each 10 Hz logging run blocks the control loop for 3–5.5 ms, which produces several missed cycles in a row ten times a second: the wobble's rhythm. The allocations are a second, smaller defect.


Fix. Control in its own group on its own executor thread at a real-time priority, logging elsewhere; history and messages replaced by a push into a preallocated ring; memory locked. Evidence to require: the fixed run's trace contains no other callback before the worst start, the allocation counter is 0, drops are 0 (as in node_fixed.out). R3


Prevention. A test that runs the node for a few seconds and asserts zero allocations on the control thread and no deadline misses caused by own callbacks (a trace check); a review rule that new callbacks go into an explicitly named group, never the default one.
