Story hook

A rider's brain does not know which muscle fibre pulls on the handlebar; it sends "turn a little left" down the nerves, and the nerves report back "the bar has turned this far". If you swapped the bicycle for a scooter, the brain's steering skill would mostly still work, because the nerves give it the same kind of messages.

ros2_control is built on that idea. A controller (the brain's skill) reads named states and writes named commands. A hardware interface (the nerves) turns those names into a real motor driver's registers, or a simulator's variables. A controller manager runs the loop: read the hardware, let the controllers decide, write the hardware, every cycle, on time. Swap the simulated robot for the real one, and the controllers stay the same. This chapter builds that structure in miniature, runs it in simulated time and on the clock, and finds a bug that only a name-to-value mapping can make: a robot that drives too fast on one side, while its controller reports that everything is fine.

What you will be able to do

  • Explain the roles of hardware interfaces, controllers and the controller manager, and the read → update → write cycle.
  • Write a hardware interface that exports state and command interfaces, with all allocation and failure before the loop.
  • Write a controller that claims interfaces by name and updates without allocating or blocking.
  • Run the loop at 1 kHz on a real-time thread and check it against a written jitter requirement.
  • Diagnose a wrong interface mapping by comparing what the controller sees with an independent measurement.
Jargon box
Hardware interface
Simple words: the code that connects the control software to one robot's real (or simulated) motors and sensors. Analogy: the nerves between brain and muscles. Precise: in ros2_control, a component that is initialised and activated by the framework, exports named state and command interfaces backed by values it owns, and implements a read step (device → state values) and a write step (command values → device) called every cycle. Listing 2 is a miniature with the same shape. D1
State interface and command interface
Simple words: a named number the controller may read (state) or write (command). Analogy: one nerve fibre, carrying one kind of message. Precise: a pair of a name, conventionally "joint/quantity" such as left_wheel/velocity or left_wheel/effort, and a reference to a value owned by the hardware interface; controllers exchange values through these references, without copying or allocating in the loop. D1
Controller (ros2_control)
Simple words: the piece of code that turns targets and measurements into commands each cycle. Analogy: the brain's steering skill. Precise: a component that declares the interfaces it needs, is configured once with references to them, and implements an update function called every cycle by the controller manager; the update must be real-time safe (no allocation, no blocking, bounded time). D1
Controller manager
Simple words: the part that loads controllers, connects them to the hardware, and runs the loop. Analogy: the rhythm of looking, deciding and steering. Precise: the component that owns the hardware interfaces and controllers, assigns interfaces to controllers (refusing a command interface claimed twice), and runs the cycle read → update → write at a configured rate on its own thread. D1
Jitter requirement
Simple words: a written rule for how regular the loop's timing must be. Analogy: "every beat within a tenth of a beat of the click, and never a missed beat". Precise: measurable limits on the loop's period and execution time, with the share of cycles that must meet them and the conditions of the measurement; this chapter's: R1 period within 1,000 ± 100 µs for at least 99.9 % of cycles, R2 no period above 2,000 µs, R3 read + update + write under 200 µs in every cycle. C1

Terms from earlier chapters: control loop, jitter (F9-45); real-time path, allocation-free loop (F9-49); tail latency (F9-48).

The idea in pictures

Layer 1 — the kid explanation

Think of a remote-controlled car. The person with the remote control decides; the car's little computer turns "go faster" into electricity for the motor and reports back "I am going this fast". If you get a new car, you can use the same skills with the remote, as long as the new car understands the same buttons.

A robot's control software is built like that. The part that decides (the controller) only talks in named buttons and readings: "left wheel speed", "left wheel push". The part that knows the real motors (the hardware interface) translates. A third part makes them take turns, a thousand times a second: read the readings, decide, push the buttons.

Layer 2 — the student explanation

The shape of ros2_control, in miniature

ros2_control is the ROS 2 framework for this structure: hardware interfaces, controllers, and a controller manager that connects them and runs the loop. D1 It is not installed in the build container, so Listings 1–3 build a framework of about 150 lines with the same shape and our own names:

  • Listing 1, uctl.h: a StateInterface and a CommandInterface are a name and a pointer to a value; Hardware has init, activate, exportStates, exportCommands, read, write; Controller has wantedStates, wantedCommands, configure, update; ControllerManager connects them by name in configure and runs cycle.
  • Listing 2, sim_hw.h: two simulated wheels, each a first-order motor model (gain 20 and 18 rad/s at full command, time constants 50 and 60 ms) with an encoder of 4,096 counts per revolution; the velocity state is the difference of two encoder readings, lightly filtered.
  • Listing 3, controllers.h: a PI controller per wheel with anti-windup, whose targets can be set from another thread through atomics.

The rule that makes this real-time safe: everything that can fail or allocate happens in configure (looking up names, building vectors, refusing a command claimed twice); the loop only follows pointers. That is the same rule as F9-49's, built into the framework's structure.

Layer 3 — the engineer's depth


The real framework


In ros2_control the same parts exist with more machinery: hardware components are described in the robot's description file and loaded as plugins; they have a lifecycle (initialised, configured, activated, deactivated); controllers are loaded and started at run time by name; the controller manager runs the loop on its own thread at a configured update rate; and several controllers can be chained. Writing a real hardware interface


For the course robot, the hardware interface talks to the motor controller (over a serial bus, CAN or USB, RB201/RB202) and to the encoders. The real-time rules become concrete:


    

  • Open, allocate and configure in the setup steps, never in read or write; fail there, loudly, if the device is absent.
    • 

  • read and write must have bounded time. A blocking serial read that waits for a reply can take a whole period or more when a byte is lost. Use non-blocking input with a timeout shorter than the budget, or a separate input/output thread that exchanges data with the loop through rings (F9-49), and report stale data as a state.
    • 

  • Safe activation and deactivation: commands zeroed on activation (Listing 2 line 22) and on deactivation; a stop path that does not depend on the loop (a hardware stop and the motor controller's own watchdog).
    • 

  • Units and signs at the boundary: convert counts to radians and commands to the driver's units in the hardware interface only, and test the conversion with the wheels off the ground.
    • 




Where the fastest loop lives


Many motor controllers run their own current and velocity loops at tens of kilohertz; the Linux loop then sends velocity or position targets at 100–1,000 Hz. The faster and harder the loop, the more it belongs on a microcontroller (F9-51), and the hardware interface becomes a translator for a command stream. Choosing that split is part of the course project and of F9-66.



Proving a jitter requirement


The course exam asks you to meet a jitter requirement and prove it with measurements. A proof package contains: the requirement (as in the Jargon box, with the measurement method); the configuration (kernel and its preemption model, priorities, pinning, locked memory, load); the program's own timing record (Listing 5's per-cycle start and execution times); the histogram and percentiles from a long run (hours) under the robot's worst realistic load; and an argument for why the measured worst case, with margin, covers what was not measured (F9-48 Layer 3). Listing 5's output is the skeleton of such a report: on the build container it records an honest FAIL. R2



How the hardware actually does it


An incremental encoder produces two square waves a quarter period apart; a counter in the motor controller or microcontroller counts their edges up or down (RB201). The computer sees only the count at the moment it reads it, so velocity is a difference of counts divided by time: at 1 kHz and 4,096 counts per revolution, one count per millisecond is 1.53 rad/s, which is why Listing 2's velocity alternates and is filtered. The command travels the other way: a value in the hardware interface becomes bytes on a bus, then a PWM duty cycle in the motor driver (HW204), which sets the average voltage on the motor. Every link adds delay, and the loop's real timing is the sum: the controller manager's period jitter is one term; the bus transfer and the driver's own loop are others.

Where the analogy breaks


    

  • Nerves carry many signals at once, continuously; the framework exchanges a few numbers once per cycle. Anything that happens between two reads is invisible to the controller.
    • 

  • A body learns its nerves; the framework trusts names. If a name points to the wrong value, nothing complains: the forensic lab.
    • 

  • The brain adapts to a new body slowly; swapping hardware interfaces is instant, but controller tuning (gains) belongs to the robot. "Same controller, new robot" is true for the code, not for its parameters.
    • 




Common mistakes and debugging


    

  • Symptom: the loop is late whenever the motor bus has an error. Cause: a blocking read with a long timeout in read. Fix: bounded, non-blocking input; staleness as a state.
    • 

  • Symptom: one wheel runs at full speed and the controller's error stays large. Cause: a wrong interface mapping or sign. Find: compare the state with an independent measurement (positions over time, the forensic lab). Fix: correct the mapping; add a start-up self-test.
    • 

  • Symptom: after a long saturation (robot held against a wall), the robot jumps forward when released. Cause: integrator windup. Fix: anti-windup (Listing 3 line 35).
    • 

  • Symptom: controller start fails with a message about an interface claimed twice. Cause: two controllers want the same command. Fix: one owner per command; stop one controller before starting the other.
    • 

  • Symptom: jitter requirement fails although the code is fast. Cause: the platform (Layer 2). Fix: PREEMPT_RT, priorities, pinning, isolation, bare hardware; re-measure.
    • 




Transition box

Where you came from: F9-49 structured a node so that its control path has its own thread, no allocation and a lock-free hand-over; RB302 tuned PID controllers and computed odometry from encoders. What carries over: the real-time rules (setup before the loop, nothing unbounded inside it), the PI controller, the measurement of periods and execution times. What changes: the framework owns the loop and its thread; your code becomes two plug-ins with fixed roles, a hardware interface and a controller, joined by named interfaces; and a requirement is now checked by the program itself. What comes next: F9-51 moves the fastest part of the loop off Linux onto a microcontroller with an RTOS, and connects it to ROS 2 through micro-ROS, so the hardware interface may end up talking to a microcontroller rather than to a motor.

Answers to Check yourself


    

  1. Read (the hardware interface fills the states), update (each controller computes commands), write (the hardware interface sends commands); the controller manager calls all three in order.
    2. 

  2. Looking up names compares strings and may throw; it has no bounded time worth trusting and can fail. Done once in configure, failures appear at start-up, and the loop follows pointers in constant time.
    3. 

  3. At 4,096 counts per revolution (4,096 / 2π ≈ 651.9 counts per radian) and 10 rad/s, a wheel turns about 6.5 counts per millisecond; one count per millisecond is 1.53 rad/s, so raw velocity alternates between about 9.2 and 10.7 rad/s; the filter (0.2 per cycle) reduces that to the observed ripple of about ±0.15.
    4. 

  4. R3 (code time) is the software author's: it passes. R1 and R2 (period jitter) belong to the platform: the integrator of the robot computer must change the kernel, priorities and placement, and re-measure.
    5. 

  5. Releases are absolute: the late cycle starts late (long period before it), and the next one starts on time (short period after it).
    6. 

  6. Never wait for the reply in read: an input/output thread sends commands and receives replies; write puts the newest command into a ring, read takes the newest reply from another ring and marks the data stale if it is older than, say, 3 ms. The loop runs at 1 kHz; the data is up to about 2 ms old, which the controller design must tolerate.
    7. 

  7. configure throws "command interface claimed twice", before the loop starts. Two writers to one command would fight, and the result would depend on the order of updates; refusing is the only safe answer.
    8. 

  8. u = 10 / 9 = 1.11, above the clamp: during the 10 rad/s phase the command saturates at 1.0 and the right wheel settles near 9 rad/s, below the target; anti-windup keeps the integral from growing. From 1.0 s the target is 5 rad/s and u = 5 / 9 ≈ 0.56 is reachable, so the final check of the last 0.1 s should still print PASS: a test that only looks at the end misses the earlier failure. Run it to confirm.

Forensic lab answer key


Observation. From 0.20 s on, the right wheel's vel_state equals its command u (both 1.000), and the right speed_from_pos rises to about 18.0 rad/s, while the left wheel holds 10.0. The right wheel is the faster one; a robot whose right wheel is faster curves to the left. R4


Hypotheses. (a) A weak motor would give a right speed_from_pos below 10, not 18. (b) A broken encoder would give positions that do not change; the right positions change faster than the left ones. (c) A wrong mapping predicts a state that copies another value: the right vel_state equals u exactly, in every row, including 0.210 at 0.10 s.


Root cause. hw_diff.out: line 27 of the robot's hardware interface maps right_wheel/velocity to &effortCmd_[1], the command, instead of &vel_[1]. R5 The controller reads back its own command (at most 1.0), sees an error of about 9 rad/s, and saturates the command at 1.0 permanently; the motor then runs at its full speed of about 18 rad/s (gain 18 × 1.0).


Fix. Map the name to &vel_[1] (the reference sim_hw.h); re-run: cm_demo.out is the expected behaviour (both wheels near 10, PASS). Cancel the motor order.


Prevention. A start-up self-test that commands each wheel briefly and checks that its velocity state follows the change in its position state (and not its command); a unit test that every exported state interface points to a value written by read; and in review, a rule that interface tables are compared against a list generated from the robot description.


How the evidence was made. cm_forensic.cpp is cm_demo.cpp built with sim_hw_v2.h, printing positions and a speed computed from positions 0.1 s apart (lines 73–74), which does not depend on the velocity mapping.
