Story hook

The restaurant's office has two boards on the wall. On the first, the order board, the cooks write numbered requests for the warehouse in the next free row: "row 3: fetch box 5". When they have written a few, they ring a bell that is wired to the warehouse's counter, and the bell's display shows the row number after the last new request. The warehouse clerk comes, reads the new rows, and goes to work. When a request is done, the clerk writes a line on the second board, the done board: "request 7 finished, all good". The cooks glance at the done board whenever they have a moment, and ring a second bell to say how far they have read, so the clerk knows which rows may be reused.

There is one clever trick. The boards are circular: after the last row, writing continues at the top. How can a cook tell a fresh "done" line from yesterday's old line in the same row? The clerk changes ink colour every time round: blue on the first pass, red on the second, blue again on the third. The cook remembers which colour is "new" this time round. That is exactly how an NVMe solid-state drive and its driver talk, and in this chapter you will read a real recording of that conversation.

What you will be able to do

  • Explain the NVMe model: submission and completion queues in host memory, doorbell registers in the controller, DMA of commands and data, and completion signalling.
  • Simulate a queue pair with head and tail indices, the "queue full" rule and the phase tag, and predict every value.
  • Read a real NVMe trace from QEMU line by line: controller reset and enable, admin queue set-up, Identify, creating an I/O queue pair, one Read.
  • Inspect an emulated NVMe controller in QEMU (PCI IDs, class code, BAR) and match it to the pci.ids database.
  • Diagnose a driver that stops seeing completions after the completion queue wraps.
Jargon box
NVMe (NVM Express)
Simple words: the language a computer uses to talk to fast SSDs over PCI Express. Analogy: the restaurant's order board and done board system with the warehouse. Precise: a family of specifications by NVM Express, Inc. defining a register interface, queue-based command submission and completion, an admin command set and I/O command sets for non-volatile memory controllers. D1 D3
Submission queue (SQ)
Simple words: a ring of command slots in the computer's memory, filled by the driver. Analogy: the circular order board. Precise: a circular buffer of fixed-size command entries in host memory; the host writes entries at the tail, the controller fetches them from the head. D1
Completion queue (CQ)
Simple words: a ring of "done" slots in the computer's memory, filled by the device. Analogy: the circular done board. Precise: a circular buffer in host memory into which the controller posts completion entries (command identifier, status, SQ head pointer, phase tag); one CQ may serve several SQs. D1
Doorbell register
Simple words: a device register the driver writes to say "there is new work" or "I have read up to here". Analogy: the bell wired to the warehouse counter, with a number display. Not the same as the faculty's "doorbell" analogy for interrupts, which ring the other way (device to CPU, F1-42). Precise: a memory-mapped controller register holding a queue's new SQ tail or CQ head index. D1 D2 R3
Phase tag
Simple words: one bit in each completion that flips every time the device goes round the ring. Analogy: the clerk's ink colour, changed each lap of the board. Precise: a bit the controller writes in each completion entry, inverted on each pass through the CQ, so the host can tell new entries from stale ones without clearing memory. D1 R1
Admin queue and I/O queues
Simple words: one special queue pair for managing the drive, and other queue pairs for reading and writing data. Analogy: the manager's board and the cooks' boards. Precise: queue pair 0 carries admin commands (Identify, Create I/O Completion Queue, Create I/O Submission Queue…); I/O queue pairs, created through the admin queue, carry I/O commands such as Read and Write. D1 R3
Namespace
Simple words: one numbered "disk" inside the NVMe drive. Analogy: one named storage area of the warehouse. Precise: a quantity of non-volatile memory addressed by logical blocks, identified by a namespace ID (nsid); I/O commands name the nsid they act on. D1 D3
PRP (physical region page) entry
Simple words: the memory address inside a command that tells the drive where to put or take the data. Analogy: the shelf number written on the order. Precise: a pointer to a host physical memory page used to describe a command's data buffer; QEMU's trace prints it as prp1 and prp2. D1 R3
Command identifier (cid)
Simple words: the number the driver gives each command so it can match the answer. Analogy: the request number on the order. Precise: a value chosen by the host in each submission entry and returned in the matching completion entry. D1 R3

Layer 1 — the kid explanation

An SSD can do many jobs at once, so the computer does not ask one question and wait. It writes a list of jobs in its own memory and rings a bell on the drive. The drive fetches the list, does the jobs, and writes "done" notes into a second list, also in the computer's memory. The computer reads the done notes when it can.

Both lists are circles: after the last place, you start again at the first. To tell new notes from old ones, the drive flips a little marker each time it goes round. The computer just remembers which marker means "new" this lap.

Layer 2 — the student explanation

The model: rings in host memory, doorbells in the device

An NVMe controller is a PCI Express function (F1-45) whose registers are memory-mapped through a BAR. QEMU's emulated controller in the lab appears as PCI device 1b36:0010 with one 64-bit memory BAR, and the pci.ids database names it "QEMU NVM Express Controller"; its class code 0x0108 with programming interface 0x02 is listed there as "Non-Volatile memory controller / NVM Express". R2 (QEMU's info pci prints the class as 0264, its decimal form; info qtree prints 0108.) R2

Work is exchanged through queue pairs. The host allocates each submission queue and completion queue as a ring of fixed-size entries in its own memory. To submit, the driver writes a command entry at the SQ tail, advances the tail (wrapping to 0 after the last slot) and writes the new tail value to that SQ's tail doorbell register. The controller fetches entries between its head and the new tail by DMA, executes them, transfers data by DMA to or from the buffers the commands describe, and writes a completion entry at the CQ tail. The driver consumes completions from the CQ head and writes the new head to the CQ's head doorbell, which tells the controller those slots may be reused. D1 D2 Each completion carries the command identifier, a status and the controller's current SQ head, which is how the host learns that SQ slots are free again. D1

A ring with head and tail indices cannot use all its slots: if the tail were allowed to catch up with the head, "full" and "empty" would look the same (head = tail). So a ring of n slots holds at most n − 1 outstanding entries. D1 Listing 1 shows it: with 4 slots, the fourth command is refused ("SQ full, cid 4 must wait"). R1

The phase tag

The host must know which CQ entries are new. Clearing each entry after reading it would cost a memory write and invite races. Instead, the controller writes a phase tag bit in every completion, and inverts the value it writes each time it wraps around the CQ. The host starts expecting the value that the first pass writes, consumes entries while their phase matches, and inverts its expectation each time its own head wraps. D1 In Listing 1 (Figure 2), the first pass writes phase 1 into zeroed memory, the second pass writes phase 0, and after the second batch the host stops correctly at slot 2, whose stale entry still has phase 1. R1

Admin queue first, I/O queues next

Only the admin queue pair is configured through registers: the driver writes its sizes and the physical addresses of the admin SQ and CQ, then enables the controller. Every I/O queue pair is created afterwards with admin commands, completion queue first because a submission queue names the CQ it reports to. D1 The real trace in the lab shows exactly this order (Create CQ with cqid 1, then Create SQ with sqid 1 and cqid 1). R3 Drivers that care about performance create several I/O queue pairs, often one per CPU, each with its own interrupt vector, so that CPUs never share a queue lock (curriculum milestone C6: "one I/O queue per CPU"). D1 D5 QEMU's model lists its own limits as properties: max_ioqpairs = 64 and msix_qsize = 65 in the lab's run. R2

Layer 3 — the engineer's depth

Analogy first, briefly: the order board, the bell, the done board and the ink colours map to SQ, doorbell, CQ and phase tag. Now the trace. The lab boots QEMU's firmware (SeaBIOS 1.16.3, as it printed itself) with one NVMe disk whose LBA 0 holds a 512-byte boot sector. SeaBIOS's NVMe driver initialises the controller and reads LBA 0; QEMU's pci_nvme_* trace events record every register access and command. D4 R3 Reading it line by line is HW205's practical exam skill.

Controller reset and enable

  1. pci_nvme_mmio_read addr 0x8, 0x0, 0x4: the driver reads registers at the start of the BAR. QEMU does not name them in these lines; the unverified box gives their names to check.
  2. mmio_write addr 0x14 data 0x0, which QEMU labels "config controller config=0x0": the driver writes 0 to the controller configuration register, disabling the controller before setting it up. Then it reads offset 0x1c (the status register, according to the unverified box below), as a driver does when it waits for the controller to report that it has stopped. R3 D1
  3. addr 0x24 data 0xff003f, labelled "admin queue attributes": two size fields, 0x3f = 63 in the low part and 0xff = 255 in the high part. R3
  4. addr 0x28 / 0x2c: the admin submission queue address 0x7fdd000 (low and high halves); 0x30 / 0x34: the admin completion queue address 0x7fde000. Both end in 000 hexadecimal: page-aligned buffers. R3
  5. addr 0x14 data 0x460001, then "setting controller enable bit succeeded": bit 0 (the final 1) enables the controller; the 0x46 in the upper bits sets entry sizes (see the unverified box). R3

Are the size fields "number of slots minus one"? The trace answers it without any document. Listing 2 found that the admin SQ tail wrapped from 63 to 0 (so it has 64 slots) and the admin CQ head wrapped from 255 to 0 (256 slots): the register held 63 and 255, one less than the slot counts. R4 The NVMe documents call such values "0's based"; that term must be confirmed in D1.

The first admin command



In the excerpt above, after enabling: mmio_write addr 0x1000 data 0x1 = "doorbell_sq sqid 0 new_tail 1". The driver had written one command into admin SQ slot 0 and told the controller the tail is now 1. The controller immediately fetched it: admin_cmd cid 0 sqid 0 opc 0x6 'NVME_ADM_CMD_IDENTIFY' with cns 0x1, which QEMU decodes as "identify controller". The data buffer is described by prp1 0x6fdd000, 4096 bytes, and QEMU writes the Identify data there by DMA (map_addr). Then enqueue_req_completion cid 0 cqid 0 ... status 0x0: a completion with status 0 (success) was posted to CQ 0; irq_pin pulsing IRQ pin: QEMU signalled a legacy pin interrupt. Finally the driver wrote 0x1004 = "doorbell_cq cqid 0 new_head 1": it consumed one completion. R3


The doorbell offsets in this trace are 0x1000 (SQ 0 tail), 0x1004 (CQ 0 head), 0x1008 (SQ 1 tail) and 0x100c (CQ 1 head): a 4-byte step, SQ then CQ, per queue number. R3 The general rule, including a stride the controller advertises, is in D1 and D2 (unverified box).



Creating an I/O queue pair and reading LBA 0


opc 0x5 'NVME_ADM_CMD_CREATE_CQ' creates CQ 1 at 0x7fdc000 with qsize=255, vector=0 and ien=0: interrupts disabled for this queue, so the driver will poll. Then opc 0x1 'NVME_ADM_CMD_CREATE_SQ' creates SQ 1 at 0x7fd8000, bound to cqid=1. R3 Next, SeaBIOS sends Identify Namespace (cns 0x0) for namespace IDs 1 to 256: that is the long trimmed middle of the trace (257 Identify commands in total, Listing 2), and it is what made the 64-slot admin SQ wrap four times. R4


The I/O path is the last thirteen lines. 0x1008 = "doorbell_sq sqid 1 new_tail 1"; io_cmd cid 0 nsid 0x1 sqid 1 opc 0x2 'NVME_NVM_CMD_READ'; pci_nvme_read ... nlb 1 count 512 lba 0x0: one 512-byte block from LBA 0 of namespace 1; map_prp ... prp1 0x7c00: the destination is physical address 0x7c00, where PC firmware loads boot sectors; rw_cb/rw_complete_cb: QEMU's back end read the disk image; enqueue_req_completion cid 0 cqid 1 ... status 0x0; irq_masked IRQ is masked: no interrupt this time; 0x100c = "doorbell_cq cqid 1 new_head 1". R3 The proof that the 512 bytes really arrived: the boot sector they contain ran and printed "boot sector arrived from NVMe LBA 0 and is running" on QEMU's debug console, then made QEMU exit with status 33. Register names and fields written from memory, to be checked in the NVM Express Base Specification (controller registers section) and the NVMe PCIe Transport Specification (doorbell registers) of the version recorded in the dossier: offset 0x0 = CAP (controller capabilities, including the doorbell stride DSTRD and the maximum queue size MQES), 0x8 = VS (version), 0x14 = CC (controller configuration; EN in bit 0; I/O SQ and CQ entry sizes in fields IOSQES and IOCQES, so 0x46 would mean 26 = 64-byte submission entries and 24 = 16-byte completion entries), 0x1c = CSTS (controller status; RDY), 0x24 = AQA, 0x28 = ASQ, 0x30 = ACQ; SQ y tail doorbell at 0x1000 + (2y × (4 << DSTRD)) and CQ y head doorbell at 0x1000 + ((2y + 1) × (4 << DSTRD)). How the hardware actually does it


A doorbell write is a posted memory write from the CPU, carried as a PCI Express transaction to the controller's BAR; the CPU does not wait for it (F1-45). D2 Everything else is the controller acting as a bus master: it reads submission entries and writes data and completion entries in host memory by DMA (F1-44), which is why queue memory must be physically contiguous or page-described, and why a driver on a system with an IOMMU must map these buffers for the device (curriculum milestone C7). D1 D5 Ordering matters: the driver must make sure the command entry is visible in memory before the doorbell write reaches the device; on weakly ordered CPUs that needs a write barrier (F1-37). D5 Completion signalling is either an interrupt (legacy pin, MSI or MSI-X, one vector per CQ) or polling; the trace shows both a pulsed pin for the admin CQ and a masked interrupt for the polled I/O CQ. R3 Inside a real SSD, the controller turns each Read into flash page reads through its FTL (F1-49); QEMU's model instead reads a disk image file, so nothing here measures a real drive's speed. R3


Watch out
Untested on hardware: every observation in this chapter comes from QEMU's emulated controller (QEMU 8.2.2) driven by SeaBIOS. A physical controller follows the same specification but adds timing, errata and firmware behaviour that this build could not observe. Worked example


Task. A driver uses an SQ and a CQ of 8 slots each, both starting at index 0, and the CQ memory starts zeroed. It submits 7 commands and rings once. The controller completes all 7. The driver consumes them. Then it submits 5 more and rings; all 5 complete. Give every doorbell value, and the phase the driver expects after each batch.


    

  1. Batch 1: SQ slots 0–6 filled; tail = 7. Doorbell SQ tail = 7. (An 8th command would have to wait: 7 + 1 = 8 → 0 = head.)
    2. 

  2. The controller posts completions in CQ slots 0–6 with phase 1. The driver consumes 7 entries; its head is 7; it writes CQ head doorbell = 7; it still expects phase 1 (no wrap yet). The completions report SQ head 7.
    3. 

  3. Batch 2: SQ slots 7, 0, 1, 2, 3; tail = 4. Doorbell SQ tail = 4.
    4. 

  4. Completions go to CQ slot 7 (phase 1), then the controller wraps and writes slots 0, 1, 2, 3 with phase 0.
    5. 

  5. The driver reads slot 7 (phase 1, matches), its head wraps to 0 and it now expects phase 0; it reads slots 0–3 (phase 0), stops at slot 4 (stale phase 1 from batch 1). CQ head doorbell = 4.
    6.

Where the analogy breaks


    

  • The warehouse clerk walks to the office; the controller reaches into host memory. The queues are in the host's memory, and the device reads and writes them by DMA without the CPU's help. A clerk in the story would never write directly on the restaurant's board while the cooks are busy; the controller does exactly that. D1
    • 

  • One bell, one board, in the story; many queue pairs in reality. A controller can serve many queue pairs at once, and it may complete commands in a different order from submission; the command identifier, not the slot order, matches a completion to its command. D1
    • 

  • Ink colours are seen; the phase is a single bit inside a binary entry. And it only works if the host flips its expectation at exactly the wrap; a story reader would notice the colour change, a driver that forgets does not (forensic lab). R5
    • 

  • "Doorbell" means two things in this faculty. The registered F1 analogy uses the doorbell for interrupts (device to CPU); NVMe's doorbell registers ring the other way (CPU to device).
    • 




Common mistakes and debugging


    

  • Symptom: the first few commands complete, then the driver waits for ever. Cause: the expected phase is not flipped on CQ wrap. How to find it: dump the CQ memory: entries with the "other" phase are sitting there. Fix: flip on wrap (Listing 1, line 88 of the header).
    • 

  • Symptom: the controller never starts executing. Cause: doorbell written with the wrong value (the slot index of the last command instead of the index after it), or to the wrong offset. How to find it: QEMU's doorbell_sq ... new_tail trace line. Fix: write the new tail (one past the last command).
    • 

  • Symptom: commands seem to vanish or the controller reports an error after many commands. Cause: the host overwrote SQ slots the controller had not consumed (ignored the SQ head reported in completions). How to find it: count outstanding commands; never exceed n − 1. Fix: track the SQ head from completions.
    • 

  • Symptom: stale or garbage data in a read buffer on some machines only. Cause: missing barrier or cache maintenance between filling an entry and ringing the doorbell, or reading the buffer before the completion. How to find it: reproduce on a weakly ordered architecture; review barriers. Fix: barrier before the doorbell; read data only after its completion.
    • 

  • Symptom: I/O queue creation fails. Cause: SQ created before its CQ, or sizes beyond the controller's limit. How to find it: the completion status of the Create command. Fix: create the CQ first; respect the limit in the capabilities register.
    • 




Transition box

Where you came from: F1-49 (what is inside an SSD) and HW204 (MMIO, interrupts, DMA, PCI Express). What carries over: the device is a PCI Express function with BARs; it moves data by DMA and may interrupt; the block interface is an array of LBAs. D1 What changes: instead of programming a few device registers per transfer, the driver and device share rings in host memory and use registers only as doorbells; many commands are in flight at once and may complete out of order; correctness depends on index arithmetic, the phase tag and memory ordering, not on timing. D1 D5 What comes next: F1-51 leaves storage for networking, starting at the wire: the Ethernet MAC and PHY. The ring idea returns in F1-52 as NIC descriptor rings.

Summary


    

  • NVMe exchanges work through rings in host memory: submission queues written by the driver, completion queues written by the controller.
    • 

  • Doorbell registers carry only indices: the new SQ tail, the new CQ head.
    • 

  • A ring of n slots holds n − 1 entries; completions report the SQ head so the host can reuse slots.
    • 

  • The phase tag flips each pass, so new completions are recognised without clearing memory.
    • 

  • The admin queue pair is set up by registers; I/O queue pairs by admin commands, CQ before SQ.
    • 

  • The real QEMU trace showed reset, enable, Identify, Create CQ/SQ and one Read of LBA 0 into 0x7c00, whose boot sector then ran.
    • 

  • The trace proved the admin queue sizes (64 and 256 slots) from doorbell wraps alone.

Forensic lab answer key


Observation. The device ran all six commands: cid 1–3 into CQ slots 0–2 with phase 1, cid 4 into slot 3 with phase 1, then (after wrapping) cid 5 and 6 into slots 0 and 1 with phase 0. The driver consumed cid 1–4 and then, at slot 0, printed "has phase 0, expected 1 → nothing new" three times and reported a timeout of 2 commands. The final dump 0:5/0 1:6/0 2:3/1 3:4/1 shows both missing completions sitting in memory.


Root cause. The driver does not invert its expected phase when its CQ head wraps from 3 to 0 (built with flipPhaseOnWrap = false). The device correctly writes phase 0 on its second pass; the driver keeps waiting for phase 1, which will only come back on the third pass. It shows only after the first wrap, i.e. after as many completions as the CQ has slots, which is why "the first few reads always work".


Ruling out the alternatives. "The device lost commands": the device lines show cid 5 and 6 executed and the dump holds their completions. "Wrong doorbell": the doorbell value 2 is exactly one past slot 1, where cid 6 was placed, and the device ran both commands.


Fix. Flip the expected phase on wrap: line 88 of nvme_model.h (if (cqHead_ == 0 && flip_) expectedPhase_ ^= 1; with flip_ true), as in Listing 1, whose run consumes cid 5 and 6.


Prevention. A unit test that submits at least two full rings of commands (more than 2 × n completions) and checks that every command completes; and a driver assertion that counts outstanding commands against the SQ head reported in completions.
