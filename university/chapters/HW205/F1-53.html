Story hook

The restaurant now works closely with a partner kitchen across town. At first every delivery went the ordinary way: the partner's driver rang the bell, a cook stopped cooking, signed the papers, carried the crate inside and put each item on the right shelf. On busy nights the cooks spent more time receiving than cooking.

So the two kitchens agreed on something unusual. The restaurant marked one cold-room shelf with a numbered seal and gave the partner a matching card: "shelf 7, top half, deliveries allowed, taking things out not allowed, card number 1100". The partner's driver now walks in through a service door, shows the card to the door guard, puts the crate on exactly that half-shelf and leaves. No cook looks up. The guard turns away anyone whose card does not match a seal, asks for a shelf that is not on the card, or wants to take something out. And the driver gets a receipt for his own records — the restaurant gets none, unless it asked for one.

That service door is an RDMA-capable NIC, the sealed shelf is a registered memory region, the card is its remote key, and the guard's checks are what the NIC does in hardware before it writes into another computer's memory. This chapter is a preview: it explains the idea and its rules with a toy model, and leaves programming real hardware to DS401.

What you will be able to do

  • Explain what RDMA adds to the NIC of F1-52: transfers placed directly in application memory, without the target CPU running code for each transfer.
  • Distinguish one-sided operations (RDMA WRITE, RDMA READ) from two-sided ones (SEND with a posted RECEIVE), and predict who gets a completion.
  • Apply the three checks of a remote request — key, permission, bounds — and predict the result of a request.
  • Name the main transports (InfiniBand, RoCE v2) and the role of RDMA for GPU clusters (GPUDirect RDMA), as a map for Track F.
  • Diagnose "remote access error" after a memory region was re-registered.
Jargon box
RDMA (remote direct memory access)
Simple words: one computer's network card reading or writing another computer's memory directly. Analogy: the partner's driver using the service door and the sealed shelf. Precise: network transfers executed by the NICs between registered memory regions of two hosts, with the data placed by DMA directly in application buffers, without copies through the operating system and, for one-sided operations, without target-CPU involvement per transfer. D1 D3 D5
Memory region and registration
Simple words: a piece of a program's memory that the program has announced to its NIC, with rules about who may use it. Analogy: the sealed shelf with its rules. Precise: an address range pinned in physical memory and entered in the NIC's translation and protection tables, with access flags (for example local write, remote write, remote read); registration returns a local key and a remote key. D1 D2
Remote key (rkey)
Simple words: the number another computer must quote to use a registered region. Analogy: the card number 1100. Precise: a key the target's NIC checks on each incoming one-sided request, together with the requested address range and operation; a request that fails a check completes with a remote access error. D1 R1
Queue pair (QP)
Simple words: a send queue and a receive queue that a program uses to give the NIC work for one connection. Analogy: the driver's order book and the restaurant's list of free crates. Precise: a send queue and a receive queue of work requests in memory shared with the NIC, connected to a queue pair on the remote host (for the reliable connected transport); the program posts work requests and rings a doorbell, as with the rings of F1-50 and F1-52. D1 D3
Completion queue (CQ, RDMA)
Simple words: where the NIC reports finished work. Analogy: the driver's receipt book. Precise: a queue of completion entries that the NIC writes when work requests finish, polled by the program; one-sided operations produce completions only on the requesting side. D1 R1
One-sided and two-sided operations
Simple words: one-sided: only the requester takes part; two-sided: both sides take part. Analogy: the driver putting a crate on the sealed shelf versus a cook signing for a delivery. Precise: RDMA WRITE and RDMA READ name a remote address and key and complete without action by the target program; SEND consumes a receive buffer the target program posted in advance and produces a completion at both ends. D1 R1
InfiniBand and RoCE
Simple words: two kinds of networks that carry RDMA. Analogy: a private road built for the service vans, and the same vans on the public road. Precise: InfiniBand is a network architecture with its own links, switches and transport defined by the InfiniBand Trade Association; RoCE v2 (RDMA over Converged Ethernet) carries the InfiniBand transport inside UDP/IP over Ethernet. D1 D6
GPUDirect RDMA
Simple words: an RDMA NIC reading or writing a GPU's memory directly. Analogy: the service door opening straight into the pastry room instead of the cold room. Precise: a mechanism with which a PCIe NIC performs DMA to and from GPU device memory, avoiding a copy through host memory; named in curriculum Track F. D4 D6

Layer 1 — the kid explanation

Normally, when a message arrives from the network, the computer's processor has to stop what it is doing, look at the message and copy it to where the program wants it. If thousands of messages arrive, the processor is busy with post instead of with real work.

Some network cards can do something special. A program can tell its card: "this part of my memory may be written by my partner computer, and here is a secret number for it". The partner's card can then put data straight into that part of memory. The processor does not even notice. The card checks the secret number, checks that the partner is allowed to write and that the data fits, and refuses anything else. This is called RDMA. Big computers that train AI models on many machines use it to move data quickly between them.

Layer 2 — the student explanation

What problem RDMA solves

With the NIC of F1-52, a received frame lands in a kernel buffer, the CPU takes an interrupt, the kernel's network stack processes the headers, and the data is copied into the application's buffer when the application asks for it. D5 Each of those steps costs CPU time and adds delay. RDMA moves the transport protocol into the NIC and lets the NIC place data directly in application memory that was prepared for it, so the kernel is not on the data path for each transfer ("kernel bypass") and no copy is made ("zero copy"); these two terms are the titles of DS401's last chapter, F5-38. D1 D3

Distributed GPU training is a main user today: the curriculum's Track F lists InfiniBand, RoCE v2, verbs, queue pairs and memory registration under "Inter-node networks", and GPUDirect RDMA — a NIC reading and writing GPU memory directly — as its own topic. D6

One-sided and two-sided

Listing 1 is the university's toy model (not a real API). Host A registers bytes 0 to 63 of its memory with "local write" and "remote write" access and gets key 0x1100; the key is given to host B beforehand. R1 Four experiments follow:

  1. RDMA WRITE. B writes "hello from B" to A's address 16 with key 0x1100: success. A's memory now holds the text, but A posted nothing, and A's completion queue is empty; only B gets a completion. R1
  2. RDMA READ of the same region: "remote access error", because the region allows remote writes but not remote reads. R1
  3. WRITE past the end (address 60, 12 bytes, but the region ends at 64): "remote access error". R1
  4. SEND. Without a receive buffer posted by A: "receiver not ready". After A posts a receive at address 200, the SEND succeeds, and both sides get completions: B "SEND success", A "RECEIVE success". R1

In real RDMA the same distinctions hold: one-sided operations need the target's address and key; two-sided operations need the target to post receive buffers in advance, like the receive ring of F1-52. D1 D3

Not verified — check before relying on this

The toy's "receiver not ready" is a simplification. On a real reliable connection, the sending NIC retries a SEND that finds no receive buffer for a configurable number of times before reporting an error; the error name and retry settings were not checked. Check the InfiniBand Architecture Specification (transport chapter: receiver-not-ready handling) and the RDMA Aware Networks Programming User Manual.

The three checks

Every one-sided request is checked by the target's NIC before any byte is written: the key must belong to a valid region, the region's access flags must include the operation, and the whole range must lie inside the region. Listing 1's allowed function (lines 60–69 of rdma_model.h) is exactly these three tests. R1 Registration is therefore a security decision: whoever holds the key and can reach the NIC may perform the allowed operations on that range, with no further action of the target program. D1 D2

Layer 3 — the engineer's depth

What registration does in hardware

Analogy first: sealing the shelf is not only writing down its number; the restaurant also promises not to move the shelf while the card is valid. The NIC addresses memory with physical (or IOMMU) addresses, as in F1-52, but programs use virtual addresses. Registration therefore pins the pages (the operating system may not move or swap them while registered) and loads the virtual-to-physical translations and the access rights into the NIC's own tables; a remote request quotes a virtual address and key, and the NIC translates it itself. D1 D2 This is why registration is slow compared with a transfer and why programs register large buffers once and reuse them — and why deregistering and registering again, as in the forensic lab, produces a different key that the peer must learn. D3 R2

Queues: the same pattern for the third time

Analogy first: the order book and receipt book are the NVMe order board and done board of F1-50, now kept by a program instead of the kernel. A program posts work requests (descriptors naming local buffers, and for one-sided operations a remote address and key) on a queue pair's send queue and rings a doorbell register of the NIC that is mapped into its own address space; the NIC executes them and writes completion entries into a completion queue, which the program polls. D1 D2 Submission and completion queues, a doorbell write and polling are the pattern of F1-50 and F1-52; what is new is that a user program, not a kernel driver, writes the descriptors and the doorbell, once the kernel has set up the queues and the protection. D2 D3

Not verified — check before relying on this

Names of the real programming interface ("verbs", library libibverbs from the rdma-core project), written from memory and not checked: ibv_open_device, ibv_alloc_pd (protection domain), ibv_reg_mr (register memory region, returning lkey and rkey), access flags IBV_ACCESS_LOCAL_WRITE, IBV_ACCESS_REMOTE_WRITE, IBV_ACCESS_REMOTE_READ, ibv_create_cq, ibv_create_qp, ibv_post_send with opcodes IBV_WR_RDMA_WRITE, IBV_WR_RDMA_READ, IBV_WR_SEND, ibv_post_recv, ibv_poll_cq, the completion status IBV_WC_REM_ACCESS_ERR, and the connection manager library (librdmacm). Check the rdma-core documentation and manual pages before using any of them; DS401 (F5-36) teaches them with real runs.

Transports: InfiniBand, RoCE, and why lossless matters

Analogy first: the vans can use a private road with its own traffic rules, or the public road if the public road is made to behave. InfiniBand defines its own physical links, switches, addressing (managed by a subnet manager) and transport; RoCE v2 keeps the InfiniBand transport and carries it in UDP/IP packets over Ethernet, so it runs through ordinary Ethernet switches and routers. D1 D6 Because the NIC's transport recovers lost packets much less gracefully than TCP does, RoCE deployments configure the Ethernet network to avoid drops (flow control and congestion signalling); DS401's forensic lab, "RDMA slower than TCP", is about exactly such a missing lossless setting or a wrong MTU. D3 D6 A software implementation of RoCE in the Linux kernel ("Soft-RoCE") lets a learner use the verbs API on an ordinary NIC; DS401 names it as one lab option. D6

Not verified — check before relying on this

Not checked in this build: that RoCE v2 uses UDP destination port 4791; the names of the Ethernet mechanisms used for lossless RoCE (priority flow control, PFC, and explicit congestion notification, ECN, with DCQCN as a congestion control scheme); the kernel module name of Soft-RoCE (rdma_rxe) and the command that creates a Soft-RoCE device. Check the RoCE v2 annex of the InfiniBand Architecture Specification and the rdma-core documentation. Bandwidth and latency numbers for any RDMA hardware must come from your own perftest runs (DS401, F5-37).

GPUDirect RDMA

Analogy first: a door into the pastry room saves carrying every tray through the cold room. In a GPU cluster the data to exchange lives in GPU memory. Without GPUDirect RDMA it is copied from GPU memory to host memory, sent by the NIC, and copied into GPU memory on the other side; with it, the NIC registers GPU memory and does its DMA to and from the GPU across PCIe directly. D4 D6 Whether this works, and how fast, depends on the PCIe topology between NIC and GPU (for example, both behind the same PCIe switch) — the topology question that HW204's PCIe chapters prepare and Track F's F1 milestone measures. D6 Communication libraries such as NCCL and RCCL use it when available (Track F, DG402). D6

How the hardware actually does it

An RDMA-capable NIC is the NIC of F1-52 with three additions: a transport engine that implements the reliable transport in hardware (sequence numbers, acknowledgements, retransmission), a memory translation and protection unit holding the registered regions and their keys, and many queue pairs with doorbells that user programs can write. D1 D2 On the Linux side, devices appear under /sys/class/infiniband (also for RoCE NICs), and the rdma-core project provides the libraries and tools. D2 This build ran the check honestly: the build machine has no /sys/class/infiniband folder and none of the tools ibv_devinfo, ibv_devices or rdma, so nothing in this chapter was tested on RDMA hardware. R3

Where the analogy breaks


    

  • A door guard can be bribed or tired; a NIC's checks are mechanical. But the security model is weaker than it sounds: anyone who learns a key and can reach the NIC is allowed in. Keys are protection against mistakes and are not a substitute for network isolation. D1
    • 

  • The driver walks; data does not move by itself. The requester's NIC sends packets, the target's NIC acknowledges them; there is a full transport protocol under the "direct" write. D1
    • 

  • The restaurant notices a full shelf sooner or later; a program does not. After an RDMA WRITE the target program learns about new data only through a separate signal (a SEND, a flag it polls, or a write with immediate data). D1 D3
    • 

  • A shelf stays put; memory pages may move. Registration pins pages; that is a cost in memory, not just a label. D2
    • 




Common mistakes and debugging


    

  • Symptom: remote access errors after a restart, resize or reconnect. Cause: stale key or address. How to find it: compare the key the requester uses with the target's current registrations (forensic lab). Fix: announce new keys whenever a region is registered again.
    • 

  • Symptom: RDMA READ fails, WRITE works. Cause: region registered without remote read. Fix: register with the flags the peer needs (and no more).
    • 

  • Symptom: SEND errors or long stalls. Cause: the receiver did not post enough receive buffers. Fix: keep the receive queue filled, as with the receive ring of F1-52.
    • 

  • Symptom: the target reads half-written data. Cause: it polled the buffer before the WRITE completed and no signal was used. Fix: signal completion with a SEND or write the "ready" flag last (DS401).
    • 

  • Symptom: RDMA slower than TCP on Ethernet. Cause: network not configured for RoCE (MTU, lossless settings). Fix: DS401's forensic lab.
    •

Forensic lab answer key


Observation. Write 1 with key 0x1600 succeeds at t = 0.1. At t = 5.0 the server deregisters key 0x1600 and registers the same range again with key 0x1601, without announcing it. Writes 2–4 still use 0x1600 and fail with remote access errors; the result buffer still holds "result-0001".


Ruling out. Network failure: the requests are answered with an error, so they reach the server's NIC. Permissions: the new registration has the same flags (remote write). Bounds: same range 64..127, same 11 bytes at 64. Only the key differs.


Root cause. The client uses a stale remote key. The server's NIC no longer has a valid region with key 0x1600, so the key check fails.


Fix. Server side: announce the new key to every client whenever a region is registered again (and stop clients from writing while the buffer is resized). Client side: on a remote access error, ask the server for its current key once before retrying, instead of retrying with the cached one.


Prevention. Treat (address, length, key) as one value that changes with every registration; never deregister memory a peer may still write; test resizing under load.
