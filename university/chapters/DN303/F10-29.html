Story hook

Kofi moves to a new restaurant. His carrying skills are the same, but nothing else is: the bar is on the left, the kitchen hatch is up three steps, table 12 is behind a pillar. On his first evening the manager hands him a floor plan. With it, he is a good waiter on day one. Without it, or with a plan that has two tables swapped, he spills drinks on strangers.

A flight controller board is a new restaurant for ArduPilot. The vehicle code and the libraries are the carrying skills. What changes from board to board is which pin does what, which bus each sensor hangs on, how the sensor is rotated on the board, where the flash memory is divided. All of that is written in one text file per board, and a generator turns it into code. This chapter is about that floor plan: how to write one, check it, and find the mistake when a board misbehaves.

What you will be able to do

  • Explain why ArduPilot describes each ChibiOS board in a text file and generates code from it, and what the file must contain.
  • Build a board description from a schematic and the MCU's pin and DMA tables, and check it with a generator before any firmware is built.
  • Plan a flash layout (bootloader, parameter storage, application) that respects the MCU's erase sectors.
  • Diagnose a board revision that lost DMA on a serial port, from the generator's output alone.
  • Plan the bring-up order of a new board port, with a recovery path.
Jargon box
Board description (hwdef)
Simple words: a text file that says what every pin of a flight controller's chip is used for and which sensors are on the board. Analogy: the floor plan of a new restaurant. Precise: a per-board configuration file read at build time by a generator script, which checks it against the microcontroller's tables and produces headers and linker settings for the HAL backend; ArduPilot documents such "hwdef" files for its ChibiOS boards. D2
Alternate function (pin mux)
Simple words: one of the jobs a chip's pin can be switched to. Analogy: a doorway that can be the way to the kitchen or the way to the bar, but not both at once. Precise: a peripheral signal (UART transmit, SPI clock, timer channel) that a pin can be routed to by the GPIO configuration; the possible functions of each pin are listed in the MCU's datasheet, and a pin carries one function at a time. D6
DMA stream (DMA channel)
Simple words: a helper in the chip that moves data between a peripheral and memory without the processor. Analogy: a trolley that carries glasses between bar and tables while the waiter does other things. Precise: one of a fixed number of DMA engine channels; each peripheral request can be served only by certain streams (a table in the reference manual), and a stream serves one request at a time unless the software shares it. D6 O2
DMA allocation
Simple words: deciding which peripheral gets which DMA helper. Analogy: sharing out a few trolleys between many jobs. Precise: the assignment of streams to peripheral requests at build time, under the constraint that each request may use only its listed streams; when streams run out, some requests run without DMA or share a stream. D2 R1
Board ID
Simple words: a number that says which board a firmware file was built for. Analogy: the restaurant's name on the floor plan. Precise: an identifier compiled into both the bootloader and the application image; the bootloader and the upload tools compare them so that firmware for one board is not flashed onto another. D2
Bootloader (flight controller)
Simple words: a small program at the start of the chip's flash that can load new firmware over USB. Analogy: the restaurant's back door, through which the new floor plan is delivered. Precise: a separate image in the first flash sector(s) that runs after reset, waits briefly for an upload over USB or serial, checks the image, and then jumps to the application at a fixed offset. D2 D6
Sensor orientation (rotation)
Simple words: how a sensor chip is turned on the board compared with the board's forward direction. Analogy: a sign on the plan saying "this table faces the window". Precise: a fixed rotation applied in software to a sensor's axes so that its readings are expressed in the board frame; a wrong rotation makes the estimator see rolls as pitches or the wrong sign. D2

The idea in pictures

Layer 1 — the kid explanation

A flight controller is a little computer chip with many legs (pins). Each leg can do a few different jobs: talk to a radio, read a sensor, drive a motor. The board maker decides which leg does which job and solders the parts to them.

ArduPilot cannot guess what the maker decided. So each board gets a list: "leg 9 talks to radio one, leg 5 is the clock for the sensor bus, the sensor is turned a quarter turn". A helper program reads the list, checks that each leg really can do that job, and writes code for the board. If the list has a mistake, the helper says no, before anything is flashed.

The chip also has a few helpers that move data on their own. There are not enough for every job, and some jobs can use only one particular helper. Deciding who gets which helper is a puzzle the helper program solves, and sometimes solves badly.

Layer 2 — the student explanation

What a board description contains

The floor plan lists what is where; Kofi's skills stay the same. The ArduPilot porting documentation describes a board for the ChibiOS backend as a directory with a text definition file (and one for the bootloader), from which a script generates the board's headers at build time. D2 The file names the microcontroller; sets clocks and flash size; gives each used pin its function and a label; lists the devices on SPI and I2C buses with their chip selects and the sensor drivers with their orientation; sets the order in which UARTs become the flight stack's serial ports; sets default parameters; and gives the board ID. D2 D4 The generator then emits pin configuration, peripheral settings and DMA assignments for ChibiOS/HAL, so that no board-specific C code is written for a board that uses known parts. D2

Flash layout, bootloader and board ID

The flash of a microcontroller is erased only in whole sectors, often of unequal sizes. D6 ArduPilot's documentation describes a bootloader at the start of flash, a reserved area for parameter storage on boards without a separate storage chip, and the application linked to start after them; the bootloader and the application carry the same board ID, and the upload tools refuse a mismatch. D2 Listing 3 plans this for U-MCU1 (four 16 KiB sectors, one 64 KiB, seven 128 KiB): bootloader in sector 0, storage in sectors 1–2, and the application from 48 KiB (0xC000) with 126 KiB spare. R4 Two sectors for storage allow one to be written while the other still holds a valid copy, so a power loss during a parameter save does not lose all parameters; whether a given flight stack does this, and how, is in its documentation. D2

Layer 3 — the engineer's depth

DMA allocation is a matching problem

  • Greedy in a fixed order can fail where a solution exists. Listing 1 gives each request the first free stream in the order of the wanted list. In rev B, SPI2_RX takes D1S1 although D1S3 would do; UART3_RX, which can use only D1S1, is left without DMA. R3 Assigning the most constrained requests first, or solving the bipartite matching exactly, finds the assignment with both on DMA. O2
  • Sharing is the other way out. A stream can serve two peripherals if the driver releases it between transfers; this costs latency and a lock, and is risky for a receiver that must be ready at all times (a UART receiving telemetry) and harmless for bursty, driver-initiated transfers (an SPI read the driver starts). ArduPilot's documentation describes DMA sharing and settings that forbid it for particular peripherals. D2
  • Without DMA, every byte is an interrupt. A UART at high bit rate without receive DMA asks the CPU for every byte; with a cooperative main loop (F10-28) and other high-priority interrupts, a late interrupt means an overwritten receive register and a lost byte. A MAVLink frame with one lost byte fails its checksum and is discarded whole (F10-30). The lab shows the allocation, not the loss: the loss rate depends on the bit rate, the interrupt load and the hardware's receive buffer, which this build did not measure.

What a generator can and cannot check

A generator can check everything that follows from the tables: pin functions, double use, completeness, DMA reachability, flash sizes. It cannot check that the tables are right (a typo in the MCU table makes every board wrong), that the schematic matches the board file, or anything electrical: pull-ups on I2C, the voltage of a GPIO, a swapped TX/RX on the connector. Those need the bench: a continuity check, an oscilloscope, a loop-back test per port. R2 S1

Sensor orientation

The rotation of each IMU and compass is a board fact, not a user setting. A wrong rotation is a dangerous error: the estimator receives consistent but wrongly labelled data, the attitude estimate may look plausible on the bench, and a controller acting on a sign error diverges in the first second of flight (the instability of F10-17 with the gain sign reversed). Verify each sensor's axes by tilting the board by hand in each direction and comparing the ground station's attitude display, before any motor is connected. D2 S1

Bring-up order

  1. Recovery path first: SWD probe or the MCU's ROM DFU mode, tested once.
  2. Bootloader: build, flash, see the USB device appear.
  3. Application with a minimal board file: USB console, LEDs, one UART.
  4. One bus and one sensor at a time; rotation check per sensor.
  5. Serial ports with loop-back tests at the highest bit rate in use; DMA report.
  6. Motor outputs with an oscilloscope, no ESCs; then ESCs without propellers (DN202).
  7. Logging and storage: power-cycle during a parameter save.

Each step adds one unknown; when something fails, only the newest step is suspect. This is the bring-up discipline of BR-05 applied to a flight stack. D2

How the hardware actually does it

At reset the MCU runs the bootloader from the start of flash. The bootloader sets up clocks and USB, waits a short time for an upload, checks that a valid application is present, and jumps to it: it sets the vector table offset register to the application's start (0xC000 in Listing 3's plan) and loads the stack pointer and reset vector from there. D6 D2 The application's startup code (ChibiOS's, configured from the generated header) then programs the GPIO mode and alternate-function registers of every pin, enables peripheral clocks, and configures the DMA streams that the generator assigned; from then on, the HAL drivers of F10-27 use them. D1 If the application was linked for the wrong offset, the jump lands in the middle of code and the board appears dead with a working bootloader, the classic symptom of a flash-layout mismatch.

Worked example

Task. Rev B adds a second IMU on SPI2. Show by hand why UART3_RX loses DMA under Listing 1's greedy rule, and find an allocation that keeps everything on DMA.

  1. The wanted list, in order: SPI1_RX, SPI1_TX, SPI2_RX, SPI2_TX, UART1_RX, UART3_RX, UART2_RX, TIM1_UP. R3
  2. Greedy pass: SPI1_RX → D2S0; SPI1_TX → D2S3; SPI2_RX → D1S1 (first of D1S1, D1S3); SPI2_TX → D1S4 (only option); UART1_RX → D2S2 (first of D2S2, D2S5); UART3_RX → options D1S1 only, taken → none; UART2_RX → D1S5; TIM1_UP → D2S5 (only option). The generator prints exactly this. R3
  3. Most-constrained first: requests with one option: SPI2_TX (D1S4), UART1_TX (not wanted), UART2_RX (D1S5), UART3_RX (D1S1), TIM1_UP (D2S5). Assign them. Then two-option requests: SPI1_RX → D2S0; SPI1_TX → D2S3; SPI2_RX → D1S3 (D1S1 is taken); UART1_RX → D2S2 (D2S5 taken). All eight are served.
  4. Check: every stream is used at most once: D2S0, D2S3, D1S3, D1S4, D2S2, D1S1, D1S5, D2S5. Yes.
  5. Lesson: the board file was correct; the allocation algorithm was too simple. Either improve the generator (lab step 3) or order the wanted list with constrained requests first.

Where the analogy breaks


    

  • Kofi notices when a floor plan is plainly wrong; firmware follows its board file exactly. A wrong rotation or a swapped pin is obeyed without complaint unless a check was written for it. R2
    • 

  • Trolleys can be shared by asking; DMA streams can be reached only by the requests the silicon wires to them. No board file can give UART3_RX a stream outside its row of the table. D6
    • 

  • A restaurant floor plan describes one building; a board file can describe a wrong chip. If the MCU line names the wrong part, every check passes against the wrong tables.
    • 




Common mistakes and debugging


    

  • Symptom: board dead after flashing, bootloader still works. Cause: application linked for another offset or with another board ID. How to find it: compare the linker's start address with the flash layout; read the image's board ID. Fix: one source of truth for the layout.
    • 

  • Symptom: a sensor is "not found". Cause: wrong chip select, wrong bus, missing pull-up, wrong driver. How to find it: the boot messages, then an oscilloscope on CS and SCK. Fix: correct the board file; check the schematic.
    • 

  • Symptom: attitude on the ground station moves the wrong way when tilting the board. Cause: wrong sensor rotation. How to find it: tilt test per axis. Fix: correct the rotation in the board file. Never fly before this test passes.
    • 

  • Symptom: one telemetry port loses packets at high bit rate, others do not. Cause: no receive DMA on that port. How to find it: the generator's DMA report (forensic lab). Fix: reorder or improve the allocation; forbid sharing for that port.
    • 

  • Symptom: serial ports numbered differently from the board's labels. Cause: serial order in the board file does not follow the documentation's convention. How to find it: loop-back test per port. Fix: correct the order; document it for users.

Forensic lab answer key


How the evidence was made. run.sh ran the generator on uboard_revb.txt and built board_use.cc against the resulting header. The loss rate in the scenario is invented for the story; the lab shows the allocation that would cause it.


Observation. Rev B: UART3_RX → none, with the warning "no free DMA stream for UART3_RX (its streams: D1S1 by SPI2_RX)"; the boot report says SERIAL2 (TELEM2) receives by interrupt per byte, self-check WARN. Rev A: UART3_RX → D1S1, PASS. R3 R1


Root cause. Adding IMU2 put SPI2_RX before UART3_RX in the DMA wanted list; the greedy allocator gave SPI2_RX its first option D1S1, the only stream UART3_RX can use. TELEM2 then receives one interrupt per byte; under flight load some interrupts are served after the next byte arrives, a byte is lost, and the frame fails its checksum. Wrong hypotheses: radio or cable (TELEM1 is fine, rev A is fine with the same firmware); firmware bug (same firmware on both revisions).


Fix and verification. Give SPI2_RX stream D1S3 (move UART3_RX earlier in the wanted list, or make the allocator most-constrained-first); expected: all eight requests on DMA, self-check PASS; then a loop-back test on TELEM2 at the highest bit rate under flight-like load, on the bench.


Prevention. Make "telemetry port without receive DMA" a build error, not a warning, and run the generator on every board revision in CI.
