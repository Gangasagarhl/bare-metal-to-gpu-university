Story hook

Nadia has carried trays of drinks in three different halls this week: a school canteen with a tiled floor, a wedding tent with grass under the boards, and her family's long kitchen. Her way of carrying never changes: feel the tilt, correct with the wrist, keep walking. What changes is the floor under her feet, where the doors are, and how fast she must go. She does not relearn carrying for each hall; she learns each hall's floor once.

ArduPilot does the same. The code that keeps a multirotor level, flies a mission and talks to a ground station is written once. Underneath it sits a thin layer that knows the "floor": which processor, which real-time operating system, which serial ports and sensors. On most of its flight controllers that floor is ChibiOS; on a laptop running a simulation it is Linux. This chapter looks at that layer, builds a small one of our own, and runs the same vehicle code on a PC and on an emulated microcontroller.

What you will be able to do

  • Explain what ChibiOS provides to a flight stack (a real-time kernel and a hardware abstraction layer with driver objects) and how its parts relate, using the vocabulary of its documentation.
  • Explain the idea of ArduPilot's HAL: abstract driver interfaces, one backend per platform, one HAL object that vehicle code holds, and why this makes software-in-the-loop (SITL) simulation possible.
  • Build a two-backend HAL of your own and show, with a byte-for-byte comparison, that the same vehicle code produces the same results on a PC and on an emulated Cortex-M3.
  • Measure per-thread stack use by painting stacks, and diagnose a stack overflow that the high-water mark alone hides.
  • Reason about the driver life cycle of a HAL (init, start, use, stop) and catch calls made in the wrong state.
Jargon box
ChibiOS
Simple words: a small operating system for microcontrollers that many flight controllers run under ArduPilot. Analogy: Nadia's reflexes, which decide in a split second which job gets her attention first. Precise: an open-source embedded software project made of a real-time kernel (ChibiOS/RT, threads with fixed priorities and kernel objects) and a hardware abstraction layer (ChibiOS/HAL, device drivers with a common model), joined by an operating-system abstraction layer; ArduPilot's porting documentation describes new boards as STM32-based boards running ChibiOS. D1 D2 C1
HAL (hardware abstraction layer)
Simple words: a set of "plugs" through which the main program uses hardware, without knowing which chip is behind them. Analogy: Nadia's way of carrying, which works on every floor. Precise: a software layer that defines interfaces (serial ports, timers, buses, storage, scheduling) and hides each platform's implementation behind them; the word names two different layers in this chapter: ChibiOS/HAL (drivers for one microcontroller family) and ArduPilot's HAL (interfaces that the vehicle code uses, implemented once per platform). D1 D2
HAL backend
Simple words: the part that makes the plugs work on one kind of computer. Analogy: learning one hall's floor. Precise: a concrete implementation of every HAL interface for one platform; ArduPilot documents backends for ChibiOS boards, for Linux boards and for SITL on a desktop computer. D2 D4
OSAL (operating-system abstraction layer)
Simple words: a thin adapter that lets the driver code run on top of a kernel. Analogy: the few words of a hall's language that Nadia needs to ask for a door to be opened. Precise: the interface through which ChibiOS/HAL drivers use kernel services (locking, waiting, waking a thread from an interrupt), so that the HAL can be used with ChibiOS/RT or with another kernel. D1
Driver state machine (HAL driver)
Simple words: the rule that a driver must be switched on before you use it, and in which order its functions may be called. Analogy: picking up the tray before walking, putting it down before letting go. Precise: the documented set of states of a HAL driver object (for example uninitialised, stopped, ready, active) and the calls allowed in each; ChibiOS/HAL drivers are started with a configuration structure and stopped to release the peripheral, and calls in the wrong state are caught by checks in debug builds. D1
Stack painting (high-water mark)
Simple words: filling a thread's stack with a known pattern before it runs, then counting how much of the pattern was overwritten. Analogy: chalk lines on the floor that show how far the waiter ever walked. Precise: a measurement of the maximum stack depth a thread has written, obtained by filling its stack area with a fill value at creation and scanning from the far end for the first overwritten word; it can be fooled when a frame reaches past the end of the stack, because writes that land outside the painted area are not seen (Layer 3). D1 R5
Stack guard (guard region)
Simple words: a strip of memory below a stack that nobody should ever write. Analogy: a "do not step here" strip at the edge of the stage. Precise: memory placed beyond the end of a stack and painted or protected (by a memory protection unit where one exists), so that an overflow is detected instead of silently corrupting a neighbour. D1 R5

Layer 1 — the kid explanation

A flight controller runs many jobs at once: keep level, read the GPS, talk to the ground, write the diary. A small operating system decides which job runs now. ChibiOS is one such system. It is like Nadia's reflexes: when the tray tips, everything else waits.

The flying program should not care which chip it runs on. So it talks to the hardware through plugs with fixed shapes: "send these letters", "give me the gyro", "run this every millisecond". Behind each plug, a small piece of code knows the real chip. To move to a new board, you rewrite the pieces behind the plugs, not the flying program.

The same trick lets you fly on a laptop. Put a pretend drone behind the plugs, and the real flying program cannot tell the difference. That is how engineers test before they ever spin a propeller.

Layer 2 — the student explanation

What ChibiOS gives a flight stack

Nadia's reflexes rank her jobs: the tray first, the conversation later. ChibiOS/RT does the same for threads. Its documentation describes a preemptive kernel in which each thread has a priority, the highest-priority ready thread runs, and kernel objects let threads wait for each other and for interrupts: semaphores, mutexes (with priority inheritance, the cure for the priority inversion of F3-39), event flags, message queues and mailboxes, and virtual timers that call a function after a delay. D1 Threads are normally created with statically allocated working areas (their stack plus their control block) rather than from a heap, which keeps memory use known at build time. D1 All of this is the same kind of kernel as the uRTOS you wrote in OS305; ChibiOS adds many more objects, a tested port for each processor family, and debug options. D1 O1

ChibiOS/HAL is the second half. It gives each kind of peripheral (serial port, SPI, I2C, PWM, timers, ADC, USB, CAN and others) a driver object with a common pattern: you initialise the driver system once, start a driver with a configuration structure, use it, and stop it to release the peripheral. D1 Each driver is split into a portable upper part and a low-level part for one microcontroller family, and the HAL reaches the kernel only through the OSAL, so the same driver code can run over ChibiOS/RT or another kernel. D1 Listing 5 models one driver's life cycle and shows a call in the wrong state being caught. R6

What ArduPilot's HAL adds

ArduPilot puts its own abstraction above the operating system. Its documentation describes a set of abstract classes (serial ports, SPI and I2C devices, a scheduler, storage, GPIO, RC input and output, analog inputs, utility functions) and one implementation of all of them for each platform: a ChibiOS backend for microcontroller boards, a Linux backend for boards that run Linux, and a SITL backend in which the "hardware" is a simulator on a desktop computer. D2 D4 Vehicle code and libraries reach the hardware only through one HAL object. D2 That rule is what makes SITL honest: the code that flies in simulation is the same code that flies on the board, compiled for a different backend. Our lab proves the principle on a small scale: the five lines that vehicle.h prints are identical on the PC backend and on the emulated microcontroller. R3

Why two abstraction layers?

They solve different problems. ChibiOS/HAL hides the differences between microcontroller families from driver users; it stops at the edge of one microcontroller world. ArduPilot's HAL hides the difference between whole platforms, including ones with no ChibiOS at all (Linux, SITL). D1 D2 On a ChibiOS board the ArduPilot backend is written in terms of ChibiOS threads and drivers; on SITL the same interfaces are written in terms of Linux sockets, files and a simulated clock. Figure 1 shows both stacks side by side.

Layer 3 — the engineer's depth

Designing a HAL interface

  • Abstract classes and one object. Listing 1 uses C++ abstract classes with pure virtual functions and a Hal struct of references. The cost is one indirect call per HAL call. For a 1 kHz loop that makes a handful of calls, the cost is small next to the control computation; for a driver that moves one byte per call it matters, which is why serial interfaces in real HALs move buffers, not bytes. D2 On the firmware side, abstract classes without a C++ run-time library need one function, __cxa_pure_virtual, which Listing 4 provides; without it the link fails. R2
  • What belongs in the interface. Everything the vehicle code may need from a platform, and nothing it must not know: no register addresses, no RTOS calls, no file paths. The test is mechanical: vehicle.h includes only hal.h and <stdint.h>; if it ever needs board.h or urtos.h, the abstraction has leaked. R3
  • Time is part of the HAL. The scheduler interface hides whether time is a hardware timer (SysTick in uRTOS) or a counter that a simulator advances. Our host backend advances time only when every due task has run, so a slow PC cannot make the simulated vehicle miss deadlines; that is a strength for repeatable tests and a limit, because timing bugs are invisible there. R1 ArduPilot's SITL documentation describes a similar control of simulated time, including running faster than real time. D2
  • Determinism makes comparison possible. The airframe model in sim_airframe.h uses integer arithmetic only, so the PC (x86-64, g++) and the emulated Cortex-M3 (Armv7-M, clang, no floating-point unit) compute bit-identical results. With floating point the two could differ in the last bits, and a byte-for-byte comparison would need a tolerance instead. R3

From scheduler interface to RTOS threads

The firmware backend turns each addPeriodic call into a uRTOS thread with its own 1 KiB stack, created from a template so that each thread knows its slot without arguments (uRTOS task functions take none). R2 The fast loop has priority 3 and the telemetry thread priority 1, so at tick 10, when both are released, the fast loop runs first, and the telemetry line printed at tick 10 reports fast_runs=11, the eleventh fast loop (ticks 0 to 10). The host backend reproduces the same order by sorting its table by priority; that is why the lines match. R1 R2 With ChibiOS the same backend would use static working areas and the kernel's sleep-until-a-time call, which avoids the drift of a "sleep for a period" loop. D1

Stacks: how big, and how do you know?

Each thread's stack must hold its deepest call chain, its local variables, and the frames that interrupts push onto it. On Armv7-M with a process stack per thread, as in uRTOS, an exception taken while a thread runs stacks eight registers on that thread's stack, and the context switch adds eight more; that is part of what the high-water mark measures. O1 Three ways to know the size: static analysis of the call graph (compilers can report per-function frame sizes, which the dossier must cite for the toolchain used), measurement by painting (this lab), and hardware protection (a memory protection unit region below each stack that faults on the first stray write). D1 Painting has a blind spot, and the forensic lab is built on it. A function that reserves a large local array but writes only part of it moves the stack pointer far down without disturbing the paint inside the array. While the calls made below the array still land inside the stack, the scan finds them and the mark is honest: the sweep R7 reads 676 bytes for a 600-byte buffer and 1,020 bytes for 948. Once the frame reaches past the end of the stack, those deeper writes land in the guard, the scan from the bottom meets only the unwritten array, and the mark collapses: 1,024 bytes and 11 guard words at 1,000, but only 72 bytes with 21 guard words at 1,400. R7 R5 A high-water mark that suddenly drops after a change is therefore a warning sign, and a guard region (or an MPU region) catches what the mark misses.

Trade-offs a porting engineer weighs

  • Static versus dynamic memory. Static working areas make RAM use visible in the linker map (areas is 6,144 bytes in R4) and remove allocation failures in flight; the price is RAM reserved for the worst case of every thread. R4 D1
  • Tick versus tickless. A periodic tick (uRTOS) is simple; ChibiOS also documents a tickless mode in which a hardware timer is programmed for the next deadline, saving power and wake-ups at the cost of more delicate timer code. D1
  • Where to draw the HAL line. A very thin HAL (bytes and pins) pushes device knowledge into vehicle libraries; a very thick one (whole sensor drivers per platform) duplicates them. ArduPilot's documentation describes sensor drivers as libraries that talk to buses through HAL device interfaces, which keeps one IMU driver for all platforms. D2

How the hardware actually does it

On a ChibiOS flight controller the kernel's timing comes from a hardware timer, and its context switches use the processor's exception mechanism, the same PendSV-and-process-stack technique uRTOS uses on Armv7-M (F3-39). D1 O1 HAL drivers program the microcontroller's peripherals, usually with DMA so that a whole SPI transfer or serial buffer moves without the CPU (F1-44); a driver thread sleeps on a kernel object and the transfer-complete interrupt wakes it through the OSAL. D1 Which peripherals, DMA streams and pins a given board uses is a board description, not code: that is the hwdef file of F10-29. D2

In this build, the "hardware" is QEMU's model of an Arm MPS2 board with a Cortex-M3 (mps2-an385), run with -icount shift=0,sleep=off so that virtual time advances by a fixed amount per instruction. The image is 3,844 bytes of code, 24 bytes of initialised data and 9,244 bytes of zeroed data, of which the four stack areas take 6,144 bytes (R4). These are facts about our image in an emulator, not about any flight controller. R4

Worked example

Task. The telemetry thread of Listing 4 has a 1,024-byte stack. Its high-water mark with a 64-byte line buffer is 140 bytes (R2). How large can LOG_LINE_BYTES be before the thread overflows, and why does the forensic run's 1,400 bytes overflow by about the amount the guard shows?

  1. Split the measured 140 bytes. They include the 64-byte buffer (written only partly, but it lies between written words, so the paint below it was reached by deeper calls). The rest, 140 − 64 = 76 bytes, is the thread's other frames plus what print and an interrupt push below the buffer. R2
  2. Budget. Stack available: 1,024 bytes. Needed: B + 76 bytes, where B is the buffer size (rounded up to 8 for alignment). So B ≤ 948 bytes keeps the thread inside its stack, with zero margin.
  3. Check with the sweep. R7 builds the firmware for several buffer sizes. At 948 bytes the mark is 1,020 of 1,024 bytes and the guard is clean, exactly the predicted 948 + 76 = 1,024 minus 4 bytes of rounding; at 1,000 bytes the stack is full and 11 guard words are written. The estimate holds. R7
  4. Check the forensic run. With B = 1,400 the need is about 1,476 bytes, 452 bytes more than the stack. The guard is 512 bytes, so the overflow should stay inside it, and it did: 21 guard words (84 bytes) written. Only 84 of the 452 bytes are written; the rest is the unwritten part of the buffer, which painting cannot see, and because the written words are all in the guard, the mark for the stack itself drops to 72 bytes. R5
  5. Engineering answer. Do not run near 948. Keep a margin (this chapter's rule of thumb for the lab: at most half the stack, so B ≤ 436), and better still, do not put large buffers on thread stacks: format telemetry into a static buffer owned by the thread. Then repeat the measurement, because the 76-byte figure is a measurement of this build and changes with the compiler and options.

Where the analogy breaks


    

  • Nadia adapts to a new floor without being told; a HAL backend adapts to nothing it was not written for. If a board's serial port, timer or sensor differs from what the backend expects, the vehicle code fails, often silently. A new board needs a new board description and sometimes new driver code (F10-29). D2
    • 

  • Carrying feels the same in every hall; simulated time does not feel like real time. Our host backend never misses a deadline, because it waits for every task. A SITL run can therefore pass while the board build overruns. Timing must be measured on the target (F10-07). R1
    • 

  • Reflexes are one system; ChibiOS is two (kernel and HAL), and ArduPilot adds a third layer. The single word "HAL" names both ChibiOS/HAL and ArduPilot's HAL; mixing them up leads to looking for a function in the wrong layer. D1 D2
    • 




Common mistakes and debugging


    

  • Symptom: the firmware link fails with an undefined reference to __cxa_pure_virtual. Cause: abstract classes in a build without a C++ run-time library. How to find it: the linker names the symbol. Fix: provide the function (Listing 4, lines 12–16) or avoid pure virtual functions.
    • 

  • Symptom: a non-void function does not return a value error for main in the firmware build, although the same main is fine on the PC. Cause: with -ffreestanding, main is an ordinary function and gets no implicit return 0. This happened in the first build of this lab. Fix: return explicitly after the call that never comes back (Listing 4, line 157). R2
    • 

  • Symptom: PC and board outputs differ in the last digit. Cause: floating-point arithmetic evaluated differently on the two targets. How to find it: compare with a tolerance and look at which operations differ. Fix: integer models for comparison tests, or a documented tolerance.
    • 

  • Symptom: random crashes after adding a feature, high-water marks look fine. Cause: a large, partly written local buffer jumped past the paint (forensic lab). How to find it: guard regions or an MPU region below each stack; per-function stack sizes from the compiler. Fix: move large buffers out of thread stacks; enlarge the stack with a margin.
    • 

  • Symptom: a driver call does nothing or asserts in a debug build. Cause: the driver was not started, or was started with a configuration for another peripheral. How to find it: the driver's state field in the debugger. Fix: follow the life cycle of Listing 5.
    •

Summary


    

  • ChibiOS has two halves: a preemptive real-time kernel (ChibiOS/RT) and a hardware abstraction layer with driver objects (ChibiOS/HAL), joined by an OSAL.
    • 

  • ArduPilot adds its own HAL above the platform: abstract interfaces, one backend per platform (ChibiOS, Linux, SITL), one HAL object in the vehicle code.
    • 

  • The lab's teaching HAL ran the same vehicle code on a PC and on an emulated Cortex-M3; the five vehicle lines were byte-for-byte identical.
    • 

  • Simulated time makes runs repeatable but hides timing problems; timing is measured on the target.
    • 

  • Stack painting measures the deepest written word; a large unwritten buffer can hide an overflow, which a guard region catches (high-water mark 72 bytes, 21 guard words written).
    • 

  • HAL drivers have a life cycle (init, start, use, stop); calls in the wrong state are bugs that debug checks catch.
    •

Forensic lab answer key


How the evidence was made. run.sh step 4 builds the same sources with -DLOG_LINE_BYTES=1400 and runs them in QEMU (R5). Nothing else differs from the healthy run (R2).


Observation. The five V lines and the fast loop's figures are unchanged (40 runs, high-water 72 bytes, guard clean). The telemetry thread's high-water mark fell from 140 to 72 bytes, its guard has 21 words written, and the check reports FAIL. R5


Root cause. char buffer[LOG_LINE_BYTES]; in telemetry() (vehicle.h, line 68). With 1,400 bytes the frame reaches below the 1,024-byte stack (the sweep R7 shows the mark is honest up to 948 bytes and fails from 1,000). Only the first few dozen bytes of the buffer are written (the line is short), so the paint inside the rest of the buffer survives; the scan from the bottom finds intact paint up to the top part of the stack and reports 72 bytes. Below the buffer, the calls to Line::text, Line::number and print, and the exception frames pushed by SysTick and PendSV, write into the guard: 21 words. On a board without a guard those words belong to the neighbouring memory, which explains resets that depend on timing. Wrong hypotheses: "the thread uses less stack now" (contradicted by the guard), "an interrupt handler is broken" (the fast loop's figures are unchanged and its guard is clean).


Fix and verification. Make the buffer static (one per thread, not on the stack) or limit it to what the stack can hold with margin (worked example). Expected report: telemetry high-water around the healthy 140 bytes or less, guard words written 0, stack check: PASS.


Prevention. Build time: ask the compiler for per-function stack usage and fail the build if a thread's worst call chain exceeds its stack minus a margin (the dossier must cite the toolchain option). Run time: guard regions or an MPU region below each thread stack, checked in the stack report that the vehicle sends (the lab extension), plus a rule in code review that large buffers do not live on thread stacks.
