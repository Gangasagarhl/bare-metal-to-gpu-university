Story hook

In a loud restaurant the waiters and the head waiter talk over walkie-talkies. They do not chat; they use short code words that everyone learned on the first day: "table 4, two still", "kitchen, hold 6", "copy". Each message starts with who is speaking and who it is for. If the head waiter hears only half a code word through the noise, she does not guess; she asks again.

One week the kitchen prints a new code card with "hold" meaning something slightly different, and nobody tells the waiters. Every message still sounds right; the kitchen and the floor misunderstand each other all evening. MAVLink is the walkie-talkie code of drones, and this chapter teaches the code words, the conversations built from them, and what happens when two sides learned different cards.

What you will be able to do

  • Explain how a MAVLink-style frame is built: start marker, length, sequence, system and component IDs, message ID, payload, checksum with a per-message extra byte.
  • Generate code from a message definition file, and explain wire order, payload truncation and extension fields.
  • Decode a frame by hand from its bytes.
  • Implement a microservice (a mission upload) as two state machines with timeouts and retries, and show that it survives lost frames.
  • Diagnose a dialect mismatch from link statistics.
Jargon box
MAVLink
Simple words: the message language drones, ground stations and companion computers use to talk to each other. Analogy: the walkie-talkie code words of the waiters. Precise: a lightweight, binary, message-based protocol in which each message type is defined in an XML file and code for packing and parsing is generated from it; the MAVLink Developer Guide describes two wire versions, MAVLink 1 and MAVLink 2. D3
Frame (packet)
Simple words: one message as bytes on the wire, with a beginning marker and a check at the end. Analogy: one complete radio call: "who, to whom, what, over". Precise: a start byte, a header (length, flags, sequence number, system ID, component ID, message ID), the payload, and a 16-bit checksum; MAVLink 2 adds optional signature bytes. D3
System ID and component ID
Simple words: two numbers saying which vehicle (or ground station) sent a message and which part of it. Analogy: "this is restaurant 1, waiter Kofi". Precise: the system ID identifies a vehicle or ground station on the network; the component ID identifies a part of that system (the autopilot, a camera, a companion computer); targeted messages carry a target system and target component in their payload. D3
Dialect
Simple words: one particular list of message types that two programs agree on. Analogy: the code card printed for one restaurant. Precise: an XML definition file (which may include others) listing enums and messages with IDs and fields; MAVLink has a common set and additional dialects maintained by flight-stack projects. Both ends must be generated from compatible definitions. D3
CRC extra (seed byte)
Simple words: a secret-looking extra byte, computed from a message's definition, that is mixed into its checksum. Analogy: each code card has a watermark; a message checked against the wrong card fails. Precise: a byte derived from the message's name and its fields' types and names; sender and receiver mix it into the frame checksum, so a frame whose definition differs between the two sides is rejected instead of misread. D3
Microservice (MAVLink)
Simple words: a small conversation made of several messages, used for one job, such as uploading a mission. Analogy: the fixed sequence of calls to take an order: "table 4 ready" — "go ahead" — "two still" — "copy". Precise: a protocol on top of messages with defined roles, sequences, timeouts and retries; the MAVLink guide documents microservices such as heartbeat and connection, mission, parameter and command protocols. D3
Heartbeat
Simple words: a short message each system sends regularly to say "I am here, and this is my state". Analogy: each waiter clicking the walkie-talkie once a second. Precise: a periodic message announcing the sender's type, flight stack, mode and status; receivers use heartbeats to discover systems and to detect a lost link. D3

The idea in pictures

Layer 1 — the kid explanation

A drone and the computer on the ground talk with numbered messages. Every message starts with a special first byte, then says how long it is, who sent it, which kind of message it is, then the message itself, and at the end a check number. If the check number does not match, the message was damaged, and it is thrown away.

Both sides need the same list of message kinds. The list lives in a file, and a program turns it into code for both sides. If one side uses an older list, the check numbers stop matching for the messages that changed.

Bigger jobs, like sending a whole flight plan, are little conversations: "I have 3 points" — "send point 0" — "here is point 0" — and so on, until "got them all". If a message gets lost, the side that is waiting asks again.

Layer 2 — the student explanation

Messages are defined, not written

The code card comes first; the radios only carry it. The MAVLink Developer Guide describes message sets as XML files: each message has a numeric ID, a name, a description and typed fields; enums give names to numbers; a file may include another. A code generator produces packing and parsing code in many languages from these files. D3 Listing 1 is our own teaching dialect, U-link, in the same file structure; Listing 2 is our generator. For each message it sorts the fields by type size (largest first, which keeps every field naturally aligned in the payload), computes the payload length, and computes a CRC extra byte from the name and the fields. R1 Our generator's CRC routine prints 0x6F91 for the ASCII string "123456789"; CRC catalogues publish a check value for this input for every CRC variant, and comparing with it is the standard self-test of a CRC routine (the catalogued value is in the unverified box). R1

U-link uses none of these IDs or names; its messages are numbered from 1.

Who is talking: systems and components

Each call starts with who is speaking. Every frame carries the sender's system ID and component ID; messages meant for one receiver carry a target system and target component in their payload, and messages without a target (such as heartbeats and telemetry) are broadcast. D3 Each system sends a heartbeat about once per second, announcing its type, flight stack and state; a ground station learns which vehicles exist from heartbeats, and both sides detect a lost link when heartbeats stop (F10-31). D3 Each sender also numbers its frames with an 8-bit sequence number; a receiver that sees a jump from 1 to 4 knows two frames were lost, which is how link-quality figures are computed. D3 R2

Microservices

Taking an order is a fixed sequence of calls. The MAVLink guide documents protocols built from messages: the mission protocol (upload, download, clear, with the receiver requesting items one by one), the parameter protocol (read all, read one, set, with the value echoed back), the command protocol (a command with up to seven parameters, acknowledged with a result, and resent with a confirmation counter when no answer comes), and others for files, cameras and more. D3 Listing 5 implements a mission upload in that shape: the vehicle drives the transfer, re-requests after 250 ms, gives up after five retries, and acknowledges at the end; the ground station repeats its last message when it hears nothing. Run A transfers three items in 320 ms of simulated time; run B, losing one item on the way up and the acknowledgement on the way down, completes at 820 ms with the same three items stored. R3

Dialects

Each restaurant can add its own code words to the common card. The MAVLink project maintains a common message set and accepts dialects that add messages for one flight stack or one company; a dialect includes the common file and adds its own messages with IDs reserved for it. D3 ArduPilot's documentation describes the flight stack as speaking the common set plus its own dialect, and ground stations as needing that dialect to show some ArduPilot-specific data. D2 A program that does not know a message ID skips the frame (it cannot even check the checksum, because it does not know the CRC extra); a program that knows the ID but with different fields rejects it through the CRC extra, as the forensic lab shows. R4

Layer 3 — the engineer's depth

Evolving a message without breaking anyone

  • Extension fields. A field added after the <extensions/> marker is appended to the payload in declared order and left out of the CRC extra. Old receivers see a longer payload and ignore the tail; new receivers given a short payload from old senders read zeros. U_POSITION's quality works this way: length 21, minimum 20, and the same CRC extra (11) with or without it. R1 Zero must therefore mean "not provided" for every extension field.
  • Changing a field's type or name breaks the CRC extra. The ground-station dialect of the forensic lab changes z from float to int32_t; its CRC extra becomes 64 instead of 58, and every item frame fails its check at the vehicle. R4 This is the intended behaviour: a frame that would be misread (an integer read as a float) is dropped. The cost is that the failure looks like noise on the link unless you read the statistics.
  • Truncation is not compression. Dropping trailing zeros saves bytes only for messages whose last fields are often zero (status text: 17 of 51 bytes sent). R2 Field order (by size) is fixed by the generator, so the designer cannot move a rarely used field to the end unless it is an extension.

Robust parsing

A byte-stream parser must resynchronise after noise: Listing 3 skips bytes until a start marker, reads the length, waits for the whole frame and checks it. A corrupted length byte can make it swallow the next real frame; real parsers limit this by restarting the search at the byte after a failed start marker. Our parser does not, which the lab's extension asks you to fix. R2 On a UART with a 16-bit checksum, a damaged frame passes the check with a probability of about one in 65,536 for random damage; MAVLink 2 signing, which the guide documents, protects against deliberate forgery, which a checksum cannot. D3

Timeouts, retries and idempotence

The mission protocol survives loss because every step is safe to repeat: a repeated request gets the same item again, and a repeated last item gets the acknowledgement again (run B, 740–780 ms). R3 Timeouts must exceed the round-trip time with margin: with 40 ms each way here, 250 ms leaves room; on a long-range radio with large buffers the round trip can be seconds, and a too-short timeout produces duplicate requests that load the link further. Commands that change state (arm, take off) are not naturally idempotent; the command protocol's confirmation counter lets the receiver tell a retry from a new command. D3

Link budget

At 57,600 bit/s with 10 bits per byte on the UART, a link carries 5,760 bytes per second; a 20-byte heartbeat costs 0.35 % of that, and a stream of 40-byte frames at 50 Hz takes 2,000 bytes, about 35 %. Flight stacks therefore let the ground station choose per-stream rates, and a mission upload competes with telemetry for the same bytes. Plan the budget before raising rates.

How the hardware actually does it

MAVLink rides on whatever carries bytes: a UART to a telemetry radio (F10-29's TELEM ports), USB, UDP over Wi-Fi or Ethernet, or a simulator's TCP socket. D3 On the flight controller, receive DMA or the UART's FIFO collects bytes, a thread hands them to the parser, and complete messages are dispatched to the library that owns them (missions, parameters, commands); outgoing streams are scheduled as tasks of the main loop (F10-28) at configured rates. D2 A telemetry radio adds its own framing, error correction and buffering; its buffering adds latency that the protocol's timeouts must tolerate, and its air data rate, not the UART rate, sets the real link budget. D2

Worked example

Task. Decode the first frame of Listing 4's output by hand and check its length: FD 08 00 00 00 01 01 01 00 00 05 00 00 00 02 03 80 02 1D 97.

  1. Header. FD: start marker. 08: payload length 8. 00 00: no flags. 00: sequence 0. 01: system 1. 01: component 1. 01 00 00: message ID 1 (little-endian, 24 bits) = U_HEARTBEAT. R2
  2. Payload in wire order (from the generator's table: custom_mode type autopilot base_mode system_status, R1): 05 00 00 00 → custom_mode = 5; 02 → type 2; 03 → autopilot 3; 80 → base_mode 0x80, bit 7 set: armed; 02 → status 2 (active).
  3. Checksum. 1D 97 → 0x971D, computed over the 17 bytes from the length byte to the end of the payload, then the CRC extra 252. Only a receiver that knows message 1's CRC extra can verify it.
  4. Length check. 10 header bytes + 8 payload + 2 checksum = 20 bytes, as printed.
  5. Status text. The same rule gives 10 + 17 + 2 = 29 bytes for "Mission accepted": severity (1 byte) and 16 characters; the remaining 34 zero bytes of the 50-character field are not sent. R2

Where the analogy breaks


    

  • A waiter who hears half a code word can guess the rest; a receiver must not. A frame that fails its checksum is dropped whole, even if only one bit was wrong. R2
    • 

  • Waiters with different code cards notice the confusion; MAVLink programs with different dialects see only "noise". The vehicle in the forensic lab counts CRC errors and nothing else; no message says "dialect mismatch". R4
    • 

  • Walkie-talkie talk is heard by whoever listens; MAVLink by default too. Without signing, anyone on the link can send a command that the vehicle accepts. A checksum is not security. D3
    • 




Common mistakes and debugging


    

  • Symptom: some messages never arrive, others do. Cause: the receiver's dialect lacks those IDs, or defines them differently. How to find it: the parser's unknown-ID and CRC-error counts per message ID. Fix: generate both ends from the same definition files and record their version.
    • 

  • Symptom: a command is executed twice. Cause: a retry after a lost ACK treated as a new command. How to find it: the confirmation field in the log. Fix: handle retries as the command protocol documents.
    • 

  • Symptom: mission uploads fail only over the long-range radio. Cause: timeouts shorter than the radio's round trip. How to find it: timestamps of request and answer. Fix: measure the round trip; raise the timeout.
    • 

  • Symptom: values arrive scaled wrongly (altitudes a hundred times too large). Cause: unit confusion in a field (cm vs m, degrees × 10⁷). How to find it: the field's description in the definition file. Fix: convert at one place, with a test.
    • 

  • Symptom: two vehicles "fight" in the ground station. Cause: both use the same system ID. How to find it: heartbeats from one ID with two sequences. Fix: unique system IDs per vehicle.
    •

Summary


    

  • MAVLink messages are defined in XML dialect files; code for both ends is generated from them.
    • 

  • A frame carries start marker, length, flags, sequence, system and component IDs, message ID, payload and a checksum.
    • 

  • The CRC extra mixes the message definition into the checksum, so mismatched definitions are rejected, not misread.
    • 

  • Fields are ordered by size; extension fields are appended and excluded from the CRC extra; trailing zeros are not sent.
    • 

  • Microservices (mission, parameter, command) are small protocols with timeouts and retries; repeats must be safe.
    • 

  • Sequence numbers measure loss; heartbeats announce systems and reveal lost links.
    • 

  • A checksum is not security; signing exists for that.

Forensic lab answer key


How the evidence was made. forensic_mission.cc runs the upload of Listing 6 with no losses, but the ground-station side is built from udialect_gcs.xml, in which U_MISSION_ITEM.z is int32_t (centimetres) instead of float; the vehicle side is built from udialect.xml. R4


Observation. The vehicle receives the COUNT (frames ok 1) and requests item 0 six times; it records 6 CRC errors, the last on message ID 12 (the item); it gives up at 1,540 ms and sends ACK error. The ground station receives all 7 of the vehicle's frames correctly. Six ITEM frames sent, six CRC errors: every item and nothing else fails. R4

Wrong hypotheses: noise (would hit all message types at random, and the ground station's side has zero errors); a vehicle bug (the same vehicle accepts items from the old ground station, run A of Listing 6).


Fix and verification. Build both from the same definition; if the team wants centimetres, add a new message or an extension, and update the vehicle. Expected: run A's output, three items stored.


Prevention. Record the dialect file's hash in both builds and compare at connection; a CI test that uploads a mission between the newest ground station and the deployed vehicle firmware; a link analyser alarm when CRC errors concentrate on one message ID.
