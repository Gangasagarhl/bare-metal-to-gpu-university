Story hook

During a busy evening, Kofi carries drinks and has a list of other jobs: glance at table 4 every minute, take empty glasses back now and then, check the kitchen hatch every ten seconds, tell the head waiter when a table wants the bill. Keeping the tray level always comes first; nobody has to remind him. The other jobs are done in the order on his list, as long as there is time before his next step.

One evening the manager adds a new job near the top of the list: "count the guests at every table". It takes long, and suddenly Kofi never reaches the bottom of his list. The kitchen hatch is checked less, the head waiter hears from him rarely. Nothing is broken; the list no longer fits. ArduPilot's vehicle code is organised like Kofi's evening, and this chapter shows how, and what happens when the list stops fitting.

What you will be able to do

  • Describe ArduPilot's code structure: vehicle directories, shared libraries, the HAL, and where control, estimation, navigation, logging and the ground-station link live.
  • Explain the main loop: a fast loop for the time-critical path and a task table run in order when time remains, with a rate and a declared time budget per task.
  • Predict and measure how a new task changes which other tasks run, using a scheduler model and its per-task statistics.
  • Explain how flight modes, mode-change checks and parameters are organised, and implement modes as classes that refuse to start without what they need.
  • Diagnose a starved task from once-per-second performance data.
Jargon box
Vehicle code (ArduPilot)
Simple words: the part of ArduPilot that makes one kind of vehicle behave like that vehicle: a multirotor, a plane, a rover or a submarine. Analogy: the habits of a waiter in one particular restaurant. Precise: a top-level program per vehicle type that owns the main loop, the task table, the flight modes and the failsafe logic, and uses the shared libraries through their interfaces; the ArduPilot documentation lists Copter, Plane, Rover and Sub among the vehicles built from one source tree. D2 D4
Library (ArduPilot)
Simple words: a piece of ArduPilot that every vehicle can use, such as the IMU code or the logger. Analogy: skills every waiter has, whatever the restaurant. Precise: a directory of C++ classes for one function (a sensor family, the estimator, attitude control, motors, navigation, missions, logging, parameters, the MAVLink link, the scheduler), shared by all vehicles and reaching hardware only through the HAL. D2 D4
Fast loop
Simple words: the work the flight controller does every single loop, before anything else. Analogy: keeping the tray level at every step. Precise: the time-critical path run once per main-loop period: read the inertial sensors, update attitude estimation, run the rate and attitude controllers and send motor outputs; other work is scheduled around it. D2
Scheduler table (task table)
Simple words: the list of jobs the flight controller does now and then, each with how often and how long it may take. Analogy: Kofi's list of other jobs. Precise: a static table of entries (function, desired rate in hertz, declared maximum run time, and in recent releases a priority) that the scheduler walks after the fast loop, running each due task whose budget fits into the time left in the period. D2 D4
Task budget (declared maximum time)
Simple words: the longest time a job promises to take. Analogy: "this will take me at most ten seconds". Precise: the per-task time in the table that the scheduler compares with the time remaining before starting the task; it is a promise made by the developer, not enforced by preemption, so a task that exceeds it delays everything after it. D2 R1
Flight mode (as a class)
Simple words: one way of flying, such as "hold position" or "come home", written as its own piece of code. Analogy: different ways of walking: carrying, clearing tables, standing by the bar. Precise: a class derived from a common mode base, with functions to enter the mode (which may refuse), run it every loop and report what it needs (for example a position estimate); the vehicle switches modes through one call that records the reason. D2 D4
Parameter (flight stack)
Simple words: a named setting stored on the flight controller, such as a gain or a failsafe action. Analogy: the restaurant's house rules, written on a card. Precise: a named, typed value with a default, kept in the board's persistent storage and exposed to ground stations over MAVLink; ArduPilot organises parameters in groups that belong to libraries and vehicle objects. D2 D3
SITL (software in the loop)
Simple words: running the real flight software on a computer, flying a simulated vehicle. Analogy: practising the evening's walk in an empty hall with pretend trays. Precise: a build of the flight stack for a desktop HAL backend whose sensors and actuators are connected to a physics simulator, so that the same vehicle code can be tested without hardware; ArduPilot documents its SITL and the simulators it can connect to. D2

Layer 1 — the kid explanation

ArduPilot is one big program that can fly many kinds of vehicles. Each vehicle has its own "boss" part that knows how that vehicle behaves. All the bosses share the same toolbox: code for sensors, for working out where the vehicle is, for steering, for writing the diary, for talking to the ground.

Many times a second, the boss does the most important job first: keep the vehicle steady. Then it walks down a list of other jobs. A job runs only if there is still time before the next steady-keeping step. If someone adds a slow job near the top, the jobs at the bottom wait, and some never get a turn.

The vehicle also has modes, like "hold still here" or "fly home". A mode checks first whether it can work. "Fly home" needs to know where the vehicle is; without that, it says no.

Layer 2 — the student explanation

One source tree, many vehicles

Kofi's skills are the same in every restaurant; only the house habits change. The ArduPilot documentation describes one source tree from which each vehicle type is built: a directory per vehicle (Copter, Plane, Rover, Sub and others) containing the vehicle's main loop, its task table, its flight modes and its failsafe logic, and a large set of shared libraries used by all vehicles. D2 D4 Libraries cover sensors (inertial sensors, compasses, barometers, GNSS receivers), the estimator, attitude and position control, motor output and mixing, navigation, missions, arming checks, logging, parameters, the scheduler and the MAVLink connection to ground stations. They reach hardware only through the HAL of F10-27. D2 A fix in a library therefore reaches every vehicle, and a bug does too.

The main loop and the task table

The tray comes first. The documentation describes the vehicle code as running a main loop at a fixed rate; each period starts with the fast loop (inertial sensors, attitude estimation, the rate and attitude controllers, motor outputs), and the remaining time goes to the scheduler, which walks a static task table. D2 Each table entry names a function, the rate at which it wants to run, and the maximum time it is expected to take; the scheduler runs a task when it is due and when its declared time fits into what is left of the period, and records statistics when tasks overrun or are delayed. D2 D4 This is cooperative scheduling inside one thread: a running task is not interrupted by the next one, so a task that takes longer than it promised delays all the tasks after it in that period. D2 Slow input and output (serial ports, buses, storage, the log) is handled in other threads of the HAL backend, so the main loop does not wait for a slow device. D2 D4

Listing 1 is the university's model of that rule: a 400 Hz loop (2,500 µs), a 1,100 µs fast loop, and nine table tasks with exercise rates, budgets and costs. In the healthy design every task reaches its rate over ten simulated seconds (battery: 100 runs, one skip). Insert one new 400 Hz task with a 1,000 µs budget after the RC input, and telemetry falls to 166 of 500 runs, logging to 649 of 1,000, with gaps of 230 ms and 52.5 ms, while no loop overruns. R1 The model exaggerates nothing: it is the arithmetic of a fixed time budget shared in table order.

Flight modes

Kofi walks differently when carrying, clearing or waiting. The documentation describes each flight mode of a vehicle as a class derived from a common base: it has an entry function that may refuse (for example when the mode needs a position estimate and there is none), a function run every loop, and properties that say what it needs. D2 D4 Mode changes go through one function that records why the change happened (pilot switch, ground station, failsafe, mission end), and failsafes are mode changes with a reason. D2 Listing 2 implements that pattern: a request for LOITER without a position estimate is refused and the vehicle stays in STABILIZE; after a GPS glitch in LOITER the vehicle falls back to LAND; a request for RTL without position is refused. R2 The mode names in the listing are exercise choices that echo common multirotor modes; the real list and each mode's requirements are in the vehicle's documentation. D2

Parameters

House rules are written once and read by everyone. ArduPilot's documentation describes a parameter system in which libraries and vehicle objects declare their settings with names, types and defaults in tables, grouped by owner; values live in the board's persistent storage, are loaded at boot, and are read and changed by ground stations through the MAVLink parameter protocol of F10-30. D2 D3 Two engineering consequences follow. A parameter's name is an interface: renaming one breaks ground-station scripts and saved parameter files unless the flight stack converts old values, which ArduPilot documents doing for some renamed parameters. D2 And defaults matter: a failsafe parameter left at its default may not suit your field (in the F10 analogy the failsafe is "go back to the meeting point"; a meeting point chosen for another hall can be the wrong place).

Layer 3 — the engineer's depth

The task budget is a contract

  • Two separate failure modes. A task whose budget is too large rarely fits: it starves itself (telemetry in design B of Listing 1). A task whose budget is too small fits everywhere but overruns it: it starves the tasks after it, and if it runs long enough, the next fast loop starts late. The forensic evidence of this chapter shows the second kind: object_avoid declares 300 µs and takes about 900 µs after its feature is switched on, so it is over budget 400 times per second and telemetry drops from 50 to 0 runs per second. R3
  • Order is priority. In written-order scheduling the table's order is the priority. A task added near the top takes time from everything below. Putting a new heavy task at the bottom protects the existing ones but may starve the new one; neither is a substitute for measuring. R1
  • Load is not the measure. In design B the worst loop used 2,461 of 2,500 µs and no loop overran, yet telemetry missed two thirds of its runs. As in F10-07, an average or a peak load does not tell you whether each task meets its rate; per-task run counts and maximum gaps do. R1
  • Why cooperative? One thread with a table has no locking between tasks, a fixed order that is easy to reason about, and stack use that is known; preemptive threads give isolation in time at the cost of shared-data locking and per-thread stacks (F10-27). ArduPilot's documented design combines both: a cooperative main thread for vehicle logic, separate threads for I/O and slow devices. D2 D5

How fast must the fast loop be?

The loop period bounds the controller's sampling time and adds up to one period of delay between a gyro sample and a motor command. From DN301 you know that delay erodes phase margin in the rate loop (F10-17, F10-19): a higher loop rate permits higher gains. The cost is CPU time: at 400 Hz in the model the fast loop's 1,100 µs is 44 % of the period; at 800 Hz the same work would take 88 % and leave almost nothing for the table. The fast loop's cost is therefore the first number to measure when porting to a slower processor. R1 D5

Mode logic as state machines

A mode is a state of the vehicle's top-level state machine, and the transitions have guards (requirements) and actions (initialise the controller from the current state, so the vehicle does not jump). Three design rules from Listing 2 transfer directly: refuse rather than half-enter (the vehicle stays in its old mode and reports why); re-check requirements every loop, not only at entry (position can be lost after entry); and make fallbacks explicit chains (LAND, and if LAND were refused, ALT_HOLD), so that a failsafe never leaves the vehicle without a mode. R2 ArduPilot's documentation describes failsafe actions as configurable through parameters, with fallbacks when the preferred action is impossible; which fallback applies in which case is documented per vehicle. D2

SITL as the development loop

Because vehicle code and libraries are platform-free, a change can be built for the SITL backend and flown against a physics model on a laptop, logged with the same logger and analysed with the same tools as a real flight (F10-32). The ArduPilot documentation describes SITL, launching it with a ground station, and connecting it to external simulators. D2 What SITL cannot show is the board's timing (F10-27): a task-table change must also be measured on the board, from the scheduler's own performance records.

How the hardware actually does it

On a ChibiOS board the main loop is woken by the inertial sensor: new IMU samples (from a data-ready line or the sensor's FIFO read by a bus thread) mark the start of a period, so the loop's timing follows the sensor's sample clock rather than a separate timer. D2 D4 Motor outputs are produced by timer peripherals (and DMA for digital ESC protocols, F10-10), so the fast loop only writes new values. The table's time budgets assume the processor of the board; the same table on a slower microcontroller needs a lower loop rate or fewer features, which is why the documentation lists board classes with different feature sets. D2

Worked example

Task. In design B of Listing 1, why does telemetry (budget 500 µs, 50 Hz) run only about one time in three, while compass (budget 100 µs, 100 Hz) keeps its full rate?

  1. Time before the table. Fast loop 1,100 µs plus up to 50 µs of jitter. RC input costs about 40–50 µs. object_avoid costs 800 µs plus up to 200 µs of jitter (a quarter of its cost). Before any other task, a loop has used between 1,940 and 2,200 µs. R1
  2. Time left. 2,500 − 1,940 = 560 µs in the best case, 300 µs in the worst. Every task that runs before telemetry in the same loop reduces it further.
  3. Telemetry's chance. It needs 500 µs free. That happens only in loops where the jitter was low and no other task (GPS 200, navigation 300, compass 100, baro 150) ran first. Such loops exist, but not in every 20 ms window: 166 of 500 runs, longest gap 230 ms. R1
  4. Compass's chance. It needs 100 µs, which almost every loop has: 1,000 of 1,000 runs. Small budgets squeeze in; large ones starve.
  5. Engineering answer. Either give the new task less of every period (split its work across loops, run it at a lower rate), or move it below telemetry and accept that it may starve, or raise the loop's capacity (a faster processor, a cheaper fast loop). Each choice must then be checked with run counts and gaps, not with load.

Where the analogy breaks


    

  • Kofi notices that his list no longer fits; the scheduler does not complain unless it is asked. In design B nothing overran and no error was raised; only per-task statistics showed the starvation. A flight stack reports this only through its performance records, which someone must read. R1
    • 

  • A waiter can stop a long job halfway to save the tray; a cooperative task cannot be stopped. Once a table task starts, it runs to its end, however long it takes; only the next period's fast loop is protected by the budget check, and only if budgets are honest (forensic lab). R3
    • 

  • House rules are read by people who use judgement; parameters are read by code that does not. A parameter with a wrong value is obeyed exactly, including a failsafe action that does not suit the field. D2
    • 




Common mistakes and debugging


    

  • Symptom: a task's effect is "sluggish" (telemetry rate low, a sensor's data old) after a feature was added. Cause: table starvation. How to find it: per-task run counts and maximum gaps from the scheduler's performance records. Fix: rebalance budgets and order; split heavy work across loops.
    • 

  • Symptom: attitude control gets worse when a feature is enabled. Cause: a task over its budget pushes the next fast loop late. How to find it: loop-time statistics (worst loop time, overruns) in the logs. Fix: measure the task's real worst case and declare it; move slow work to a thread.
    • 

  • Symptom: a mode switch from the transmitter "does nothing". Cause: the mode refused to start (requirement not met), and the message went to the ground station only. How to find it: the ground station's message list and the log's mode records (F10-32). Fix: meet the requirement (wait for a position estimate) or choose a mode that does not need it.
    • 

  • Symptom: a saved parameter file loads with "unknown parameter" warnings after an upgrade. Cause: parameters renamed between releases. How to find it: the release notes. Fix: use the documented conversion or re-enter the values; never assume a file from an old release is complete.
    • 

  • Symptom: a change works in SITL and fails on the board. Cause: timing (SITL's processor is faster) or a hardware difference. How to find it: the board's performance records. Fix: budget for the board, not for the laptop.
    •

Summary


    

  • ArduPilot builds every vehicle from one source tree: vehicle programs on top, shared libraries in the middle, the HAL at the bottom.
    • 

  • The vehicle's main loop runs the fast loop first and then a task table in which each task has a rate and a declared time budget.
    • 

  • Table scheduling is cooperative: a task runs only if its budget fits, and once started it is not interrupted.
    • 

  • Large budgets starve themselves; dishonest small budgets starve the tasks after them; neither shows up as load or as an error.
    • 

  • In the model, one new task cut telemetry from 500 to 166 runs in ten seconds with no loop overrun.
    • 

  • Flight modes are classes that check their requirements at entry and every loop; mode changes carry a reason; failsafes are mode changes.
    • 

  • Parameters are named, stored settings; names and defaults are part of the interface.
    •

Forensic lab answer key


How the evidence was made. perf_log.cpp runs the model of Listing 1a for 17 s with design A plus object_avoid (400 Hz, declared budget 300 µs) after rc_input; its cost is 100 µs until t = 8 s and 900 µs (plus jitter) after. Each line summarises the second before it.


Observation. Up to second 8: RC input 400, telemetry 50, logging 100, battery 10 runs per second, no over-budget runs, worst loop about 2,230–2,280 µs. From second 9: telemetry 0, logging 14–20, battery 10, RC input 400; object_avoid over budget 400 times per second; worst loop up to 2,475 µs; still no loop overrun. R3


Root cause. object_avoid's declared budget (300 µs) is far below its real cost once the feature is on (about 900–1,125 µs). The scheduler starts it every loop because 300 µs fits, then has too little time left for tasks with larger budgets: telemetry (500 µs) never fits, logging (400 µs) rarely. Small-budget tasks (battery 120 µs) still fit. The ground station hears nothing because the vehicle stopped sending, not because the radio failed. Wrong hypotheses: a radio fault (would not change the vehicle's own telemetry run count, and would not touch logging); CPU overload in general (no loop overran, battery and RC kept their rates).


Fix and verification. Declare the real worst-case cost and restructure the task (split across loops, lower rate, or a separate thread); expected records: telemetry back to 50 and logging to 100 per second with the feature on, avoid_over 0.


Prevention. A SITL test that enables every feature and fails if any task's run count falls below 95 % of its rate or any task runs over budget; repeated on the bench board, because SITL's timing is not the board's.
