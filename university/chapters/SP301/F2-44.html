Story hook

Mr Haddad's bound recipe book (F2-43) leaves the kitchen in a van every morning for the restaurant's second branch. The book has two lists at the front. The first, for cooks, says where each recipe and each list of ingredients starts: "soups, page 12; desserts, page 40". The second, for the van driver, is much shorter: "load pages 1 to 30 on the shelf marked read only; load pages 31 to 35 on the shelf marked may write on; leave five blank pages after them for notes". The driver never reads the cooks' list. At the other branch, the head cook opens the book at the page marked "start here".

One morning Amira hands the driver a book written for the other branch's oven, a different model, and nothing happens: the branch refuses it at the door. The first line of the book said which oven it was for. In this chapter you will read those two lists and that first line, byte by byte, in real files, and build a reader that agrees with readelf on every line and survives an hour of random damage.

What you will be able to do

  • Explain every field of the 64-byte ELF64 header from a raw hex dump.
  • Distinguish the linking view (sections, section headers) from the execution view (segments, program headers), and map one to the other.
  • Read section headers, program headers, string tables and symbol tables with readelf, and say what each column is.
  • Build a bounds-checked ELF reader (milestone P2) whose output matches readelf on six real files, with unit tests and a fuzzing run.
  • Diagnose "Exec format error" and similar loader refusals from the header alone.
Jargon box
ELF
Simple words: the file format of programs, libraries and object files on Linux and many other systems. Analogy: the standard layout of the bound recipe book. Precise: Executable and Linking Format, defined by the System V generic ABI (gABI) with a processor supplement per architecture; one format for relocatable files, executables, shared objects and core dumps. D1
ELF header
Simple words: the fixed-size block at the start of the file that says what the file is and where everything else is. Analogy: the book's first page: for which oven, start page, where the two lists are. Precise: 64 bytes in ELF64: identification bytes (magic, class, byte order, version, OS ABI), type, machine, version, entry point, offsets of the program and section header tables, flags, and the sizes and counts of their entries. D1 R4
Section header
Simple words: one entry in the table that describes a named part of the file for the linker and tools. Analogy: one line of the cooks' table of contents. Precise: a 64-byte ELF64 record (name offset, type, flags, address, file offset, size, link, info, alignment, entry size); the table may be absent or stripped of meaning in an executable, because the loader does not use it. D1 R2
Program header (segment)
Simple words: one entry in the table that tells the loader what to put in memory. Analogy: one line of the van driver's list. Precise: a 56-byte ELF64 record (type, flags, file offset, virtual address, physical address, file size, memory size, alignment); PT_LOAD entries describe ranges of the file to map with given permissions, others give the interpreter path, dynamic linking table, stack permissions and so on. D1 R4
String table
Simple words: a block of names, one after another, each ended by a zero byte. Analogy: the index of titles; a line elsewhere says "title starts at character 27 of the index". Precise: a section of type SHT_STRTAB; other structures store names as byte offsets into it; e_shstrndx names the one holding section names. D1
Entry point
Simple words: the address of the first instruction to run. Analogy: "start here". Precise: e_entry; for a dynamically linked program the kernel first runs the interpreter named in PT_INTERP, which later jumps to it. D1 D3
Fuzzing
Simple words: testing a program by feeding it huge numbers of random or damaged inputs and watching for crashes. Analogy: handing the reader thousands of books with torn and scribbled pages. Precise: automated generation of inputs (here by mutating valid seed files) run against a target built with sanitizers, so that any memory error or undefined behaviour is detected and the input saved. D7 R5

Layer 1 — the kid explanation

A program file starts with a short label: "this is an ELF file, for this kind of processor, start here, and the two lists are there". One list tells the computer which parts of the file to copy into memory and whether they may be changed or run. The other list names every part of the file for the tools that build and inspect programs. A careful reader checks every number before it believes it, because a broken or hostile file can say anything.

Sections: the linker's view


Each section header gives a name (an offset into the section-name string table), a type (PROGBITS for bytes from the program, NOBITS for zero-filled space, SYMTAB, STRTAB, RELA, DYNAMIC …), flags (A allocated in memory at run time, W writable, X executable, M/S mergeable strings, I "info link" for relocation sections), an address (0 in an object file), a file offset and size, and two generic numbers, link and info, whose meaning depends on the type. D1 For a symbol table, link is the index of its string table and info is one more than the index of the last local symbol; in hello.o, .symtab has link 13 (.strtab) and info 7, and indeed symbols 0–6 are LOCAL and 7–10 GLOBAL. R3 For a relocation section, link is the symbol table and info the section it patches: .rela.text has 12 and 1. R3



Segments: the loader's view


A relocatable file has no program headers (hello.o: 0 segments); executables and shared libraries have them (hello: 13). R2 The loader cares mainly about PT_LOAD: "map file bytes [offset, offset + filesz) at address vaddr, with these permissions, and if memsz is larger, fill the rest with zeros". The fourth LOAD of hello has filesz 0x258 and memsz 0x260: the extra 8 bytes are .bss (including greetings), which occupy no space in the file. R4 D1 readelf -l also prints the section-to-segment mapping: segment 03, the only executable one (R E), holds .init .plt .plt.got .plt.sec .text .fini. R4 Other types: PT_INTERP (the path of the dynamic loader), PT_DYNAMIC (the table the dynamic loader reads), PT_GNU_STACK (whether the stack may be executable: here RW, not executable), PT_GNU_RELRO (a range to make read-only after relocation). Layer 3 — the engineer's depth


In the kitchen's words: the van driver's list must be right or the branch cannot cook at all; the cooks' table of contents can be torn out (stripping) and the branch still cooks. Now the precise version, and what it costs to read a file you do not trust.


An ELF file is untrusted input


Every number in an ELF file is a claim. e_shoff may point past the end of the file; e_shnum × e_shentsize may overflow; a name offset may point outside its string table, or into a table that has no terminating zero; a section's offset plus size may wrap around 264. Tools that read ELF files from strangers (debuggers, package scanners, firmware loaders, your own kernel in milestone B13) have had real vulnerabilities from trusting such fields, which is why the curriculum's P2 demands a fuzzing run. D7 The reader in Listing 1 follows three rules: (1) copy fixed-size records out of the byte array with memcpy rather than casting pointers, so alignment and aliasing rules are respected D8; (2) check every range with an overflow-safe test, off <= size && len <= size - off, never off + len <= size, which can wrap; (3) return an error code from every accessor, with no exceptions and no allocation, so the same parser can later run freestanding (F2-48).



Extended numbering and the corner cases


The header's counts are 16-bit. The gABI provides an escape for files with 65,280 sections or more: e_shnum is 0 and the real count is in the sh_size field of section header 0; if the section-name table's index does not fit, e_shstrndx holds SHN_XINDEX (0xffff) and the real index is in section 0's sh_link. D1 Listing 1 implements this (lines 110–123) but none of the six sample files uses it, so that path is tested only by the fuzzer's random values, not by a real file. Symbol section indices have reserved values too: 0 = undefined (UND), 0xfff1 = absolute (ABS), 0xfff2 = common (COM), which the reader prints like readelf. D1 R2

What the kernel and the dynamic loader do with it


When you run ./hello, the Linux kernel reads the ELF header and program headers, checks class, byte order and machine, maps each PT_LOAD with its permissions (choosing a random base for a DYN file), maps the interpreter named in PT_INTERP (/lib64/ld-linux-x86-64.so.2 here), and starts the interpreter; the interpreter loads shared libraries, applies the dynamic relocations of F2-43, runs initialisers, and jumps to e_entry plus the base. D3 D2 The section header table is not used for any of this, which is why strip can remove .symtab and the program still runs. D1 R2 In milestone A3 your own bootloader will do the kernel's part for your kernel: read the header, check it, copy each PT_LOAD, zero the memsz − filesz tail, jump to the entry. Listing 1 is written so that it can be reused there.

How the hardware actually does it


The processor never sees an ELF file. It sees memory pages, set up by the kernel with the permissions from p_flags: on x86-64 the page tables carry a writable bit and a no-execute bit per page, which is why PT_LOAD segments are aligned to 0x1000, the page size, and why the four LOADs of hello start on separate pages (0x0, 0x1000, 0x2000, 0x3db8 in a page of its own) — read-only, executable, read-only, writable. D4 R4 A segment's file offset and virtual address must agree modulo the alignment (0x2db8 and 0x3db8 both end in 0xdb8), so that the kernel can map file pages directly. D1 R4 And e_machine exists because instruction encodings differ: the bytes of hello-arm64's .text are AArch64 instructions, which an x86-64 processor would decode as something else entirely. D5 R7

Where the analogy breaks


    

  • A van driver can see the pages; the loader trusts numbers. If the header says the list is on page 500 of a 30-page book, a careless reader walks off the end of memory. Nothing in the format stops a file from lying. R6
    • 

  • The two lists overlap freely. A section belongs to at most one LOAD segment, but non-LOAD segments (GNU_RELRO, DYNAMIC) overlap LOAD segments and each other; one byte of the file can be in several segments. R4
    • 

  • "Blank pages" are not in the book at all. .bss has a size but no bytes; a book would print blank pages. R4
    • 




Common mistakes and debugging


    

  • Symptom: "cannot execute binary file: Exec format error". Cause: wrong e_machine or class for this computer (forensic lab), or a file that is not ELF at all. How to find it: readelf -h or file. Fix: build for the right target, or run under an emulator.
    • 

  • Symptom: "No such file or directory" for a file that exists. Cause: the interpreter named in PT_INTERP is missing (for example an AArch64 loader path on an x86 machine, or a different libc). How to find it: readelf -l FILE | grep interpreter. Fix: install that loader or link statically. (Observed behaviour in many systems; not reproduced in this lab — try it as an extension.)
    • 

  • Symptom: your reader crashes on a damaged file. Cause: an unchecked offset, a size check written as off + len <= size (wraps), or a string read without looking for its zero byte. How to find it: build with -fsanitize=address,undefined and fuzz. Fix: the patterns of Listing 1.
    • 

  • Symptom: your section names are all wrong. Cause: you looked up names in .strtab (symbol names) instead of the table at e_shstrndx. Fix: section names use e_shstrndx; symbol names use the symbol table's sh_link.
    • 

  • Symptom: your symbol counts differ from readelf on stripped files. Cause: only .symtab is read; stripped files keep only .dynsym. Fix: read both (R2: hello-stripped has 7 symbols, all dynamic).
    •

Summary


    

  • An ELF file starts with a 64-byte header (ELF64): identification, type, machine, entry, and the positions, sizes and counts of the program and section header tables.
    • 

  • Sections are the linker's view; segments (program headers) are the loader's view; the loader needs only the header and the program headers.
    • 

  • PT_LOAD maps a file range with permissions; memsz beyond filesz is zero-filled (.bss).
    • 

  • Names are offsets into string tables: e_shstrndx for sections, sh_link for symbols.
    • 

  • An ELF file is untrusted input: check every range without overflow, every string for its terminator.
    • 

  • The lab's reader matched readelf on six files, passed 15 targeted unit tests, and survived fuzzing under sanitizers.
    • 

  • "Exec format error" is usually a header mismatch: read e_machine and class first.
    •

Forensic lab answer key


Observation. Both files: type=3 (DYN), ELF64, little-endian, phoff=64, ehsize=64. They differ in machine: AArch64 versus Advanced Micro Devices X86-64 (and naturally in entry, counts and sizes).


Hypotheses. (b) is ruled out by ls -l (-rwxr-xr-x) and by the error text (a permission problem gives "Permission denied"). (a) is ruled out because elfread parses the whole file without error and QEMU runs it correctly ("ELF lab: hello, reader"). (c) is confirmed by e_machine.


Root cause. The file was compiled for AArch64 (Leila's laptop is an Arm machine, or she used an Arm cross compiler). The x86-64 kernel will not execute AArch64 code. The INTERP line confirms it: it requests /lib/ld-linux-aarch64.so.1, the AArch64 dynamic loader.


Fix. Build on the server or with an x86-64 target (g++ there, or a cross compiler for x86-64 on the laptop); or run it under user-mode emulation (qemu-aarch64 -L /usr/aarch64-linux-gnu), slower and only for testing.


Prevention. In the deployment script, check readelf -h's Machine (or file) against the target before copying, and fail with a clear message; name build outputs by target triple.


How the evidence was made. The lab builds hello-arm64 with aarch64-linux-gnu-g++ from the same source and runs it on the x86-64 build container (step forensic_exec).
