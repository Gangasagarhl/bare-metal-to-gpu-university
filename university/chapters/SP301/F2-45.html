Story hook

The restaurant opens a branch inside a hotel, and the hotel kitchen has its own rules. Recipe books must follow the hotel's binding: a small old-style cover page that hotels of the last century needed, then a stamped label, then a page of facts, then the table of contents. And one rule matters more than the others: the hotel decides on which shelf a book goes. The book may say "I would like shelf 140", but if shelf 140 is full or does not exist, the hotel puts it on shelf 6 and corrects every page number written inside — but only if the book contains a list of every place where a page number was written. A book without that list either gets its favourite shelf or is turned away at the door.

In this chapter you will read that format, PE/COFF, byte by byte, compare your own reader with LLVM's, and watch real UEFI firmware put a program on a shelf it did not ask for and fix its page numbers — and refuse the same program when the list is missing.

What you will be able to do

  • Explain the layout of a PE32+ image: MS-DOS header, PE signature, COFF file header, optional header, data directories, section table.
  • Distinguish a COFF object file from a PE image, and RVAs from file offsets and virtual addresses.
  • Compare COFF relocations with ELF relocations for the same source code.
  • Read the base relocation table and explain how a loader uses it when it cannot load an image at its preferred base.
  • Build a freestanding PE32+ UEFI application with Clang and LLD and boot it in QEMU with OVMF.
Jargon box
PE/COFF
Simple words: the program file format of Windows and of UEFI firmware. Analogy: the hotel's book binding. Precise: Portable Executable images built on the Common Object File Format; COFF is also the object-file format; PE32+ is the 64-bit variant (optional-header magic 0x20b). D1 R3
RVA (relative virtual address)
Simple words: a distance from where the image starts in memory. Analogy: "page 12 of this book", whichever shelf the book is on. Precise: an address relative to the image's load base; the address at run time is base + RVA. Not a file offset: sections are aligned differently in the file (FileAlignment) and in memory (SectionAlignment). D1 R3
ImageBase
Simple words: where the image would like to be loaded. Analogy: "I would like shelf 140". Precise: the preferred virtual address recorded in the optional header; absolute addresses in the image were computed for it (0x140000000 in the lab). D1 R3
Base relocation
Simple words: an entry saying "an absolute address is stored here; adjust it if the image moves". Analogy: the list of places where a page number was written. Precise: entries in the .reloc table (data directory 5), grouped in blocks per 4 KiB page, each a 16-bit value with a 4-bit type (10 = DIR64 for a 64-bit address) and a 12-bit offset; the loader adds (actual base − ImageBase) to each location. D1 R4
Data directory
Simple words: a fixed list in the header that points to special tables. Analogy: "imports on page …, fix-up list on page …". Precise: an array of (RVA, size) pairs at the end of the optional header; entries include exports, imports, exceptions and the base relocation table (index 5). D1
UEFI application
Simple words: a program the firmware itself can load and start before any operating system. Analogy: a book the hotel's own staff can cook from. Precise: a PE32+ image with subsystem EFI_APPLICATION (10), entered as efi_main(ImageHandle, SystemTable) using the Microsoft x64 calling convention. D2 R3

Layer 1 — the kid explanation

Windows and the PC's start-up firmware use a different kind of program file from Linux. It starts with an old cover page, then a label "PE", then facts about the program, then a list of its parts. The program says where it would like to live in memory, but the firmware may put it elsewhere. If that happens, the firmware fixes every stored address using a list of where those addresses are. No list, and the program can only live at its favourite place.

RVA, file offset and virtual address


Three kinds of position meet in PE files. A file offset is where bytes are in the file (.data at 0x800). An RVA is where they are relative to the image base in memory (.data at 0x3000). A virtual address is base + RVA. To convert an RVA to a file offset, find the section whose [VirtualAddress, VirtualAddress + VirtualSize) contains it, then offset = PointerToRawData + (RVA − VirtualAddress). pe_read does exactly that to find the base relocation table: RVA 0x4000 is in .reloc (VirtualAddress 0x4000, PointerToRawData 0xa00), so the table is at file offset 0xa00 (Listing 1, lines 146–147). D1 R3



COFF objects and their relocations


A COFF object starts directly with the COFF file header: no MZ, no signature, no optional header (SizeOfOptionalHeader 0). D1 Its sections carry relocation lists, like ELF's .rela sections, but each COFF relocation is 10 bytes (offset, symbol index, type) without an explicit addend: the addend is whatever bytes are already at the place. D1 The lab's object has four in .text (IMAGE_REL_AMD64_REL32, PC-relative, like ELF's PC32) and two in .data (IMAGE_REL_AMD64_ADDR64, a full 64-bit address, like ELF's R_X86_64_64). Layer 3 — the engineer's depth


In the hotel picture, the list of corrected page numbers is what lets the hotel choose the shelf. Here is what that means precisely, and why the lab's ELF and COFF objects differ so much for one source file.


Base relocations


Code that refers to its own data with RIP-relative addressing does not care where the image is loaded (F2-43). Absolute addresses stored in data do: g_lines holds two 64-bit pointers to strings, which the linker computed as ImageBase + RVA of each string. If the loader places the image elsewhere, those values are wrong by delta = actual base − ImageBase. The base relocation table is the list of such places. It is divided into blocks: each block starts with an 8-byte header (page RVA, block size), followed by 2-byte entries whose high 4 bits are the type and low 12 bits the offset within that 4 KiB page. D1 The lab's table is one block of 12 bytes: page 0x3000, size 0xc, two entries of type 10 (DIR64) at offsets 0x000 and 0x008 — the two pointers in .data. R3 R4 A block's size must be a multiple of 4 in the specification (padding entries of type 0 are allowed), which is why pe_read skips type 0 (line 157). D1


Now the run. OVMF, the open-source UEFI firmware for QEMU, loaded app.efi and started it; the application printed that efi_main was running at 0x000000000676e000. R5 Its RVA is 0x1000, so the image base was 0x676d000, not 0x140000000. Both strings reached through g_lines printed correctly, so the firmware must have added delta to both pointers: without that, they would point to 0x1400020xx, far beyond the emulated machine's memory. The COFF object has 6 relocations; the ELF object has 36 (34 in .rela.text, 2 in .rela.data). R4 The difference is not the format but the code model the compiler assumed for each target. For the Windows target, Clang addressed g_lines RIP-relatively (REL32) and computed &efi_main with one lea. For x86_64-unknown-none-elf, which by default is not position-independent, it used 32-bit absolute addresses (R_X86_64_32 for efi_main, R_X86_64_32S for the hex-digit string) — and, with -O2, it unrolled the 16-digit loop of sayHex, so every iteration carries its own pair of relocations. R4 Those absolute 32-bit relocations would only work if the program were linked below 2 GiB; that is a target default observed in this run, not a rule of ELF. Both objects agree on the data: two 64-bit absolute pointers (ADDR64 versus R_X86_64_64). R4



The UEFI calling convention


UEFI uses the Microsoft x64 calling convention: the first four integer arguments in RCX, RDX, R8, R9, with 32 bytes of "shadow space" reserved by the caller on the stack. D2 That is why the lab compiles for a Windows target: efi_main(void*, void*) then receives the image handle and system table where the firmware puts them. The lab's application deliberately uses neither argument; it writes to two QEMU devices instead, so its run does not depend on UEFI table layouts that could not be checked in this build. F2-47 compares the two x86-64 conventions in detail, and milestone A1 uses the system table properly.


Not verified — check before relying on this
From memory of the UEFI specification, not checked in this build: that UEFI images use the Microsoft x64 calling convention; that subsystem 10 means EFI application; that firmware loads removable-media boot files from the default path \EFI\BOOT\BOOTX64.EFI on x86-64 (the lab relies on it, and the boot worked, R5, which supports but does not prove the rule for other firmware); and that a UEFI loader may place an image at an address other than ImageBase and must then apply base relocations. Check the UEFI specification's chapters on image loading, boot manager (removable media boot behaviour) and calling conventions.



How the hardware actually does it


When a PC with UEFI firmware starts, the firmware itself runs in 64-bit long mode with paging set up so that virtual addresses equal physical addresses (identity mapping). D2 "Loading an image at 0x676d000" therefore means putting it at that physical address in RAM; the lab does not set a memory size for QEMU, and its default (128 MiB, recalled from QEMU's documentation, D7) is far below 0x140000000 (5 GiB), which would explain why the firmware did not honour ImageBase; the run shows only that it did not. R5 The application then talks to devices with x86 I/O instructions: outb to port 0xe9 (QEMU's debug console, written to debug.txt) and to port 0xf4 (QEMU's isa-debug-exit device, which ends the emulator with exit status (value << 1) | 1, so 0x21 gives 67). D6 D7 R5 On a real PC neither device exists; a real UEFI application writes text through the firmware's console protocol instead.


Watch out
Untested on hardware. Every boot in this chapter ran in QEMU 8.2.2 with OVMF from /usr/share/OVMF/OVMF_CODE_4M.fd, logged in R5 and R6. No physical UEFI PC was used. Real firmware may choose different load addresses, may refuse unsigned images when Secure Boot is enabled, and has no port-0xe9 console or debug-exit device; the lab application would hang silently in its hlt loop there. The QEMU device semantics (0xe9 console, isa-debug-exit formula) are from QEMU's documentation, recalled from memory (D7); the exit status 67 in R5 is consistent with that formula.



Worked example


Task. The first pointer in g_lines points to the string "PE32+ app: started by the firmware". Suppose its RVA is 0x2000 (the start of .rdata). What value does the linker store at RVA 0x3000, and what must the firmware write there after loading the image at 0x676d000?


    

  1. Linker's value: ImageBase + RVA = 0x140000000 + 0x2000 = 0x140002000.
    2. 

  2. delta = 0x676d000 − 0x140000000. As a signed number that is −(0x140000000 − 0x676d000) = −0x139893000.
    3. 

  3. Patched value: 0x140002000 + delta = 0x140002000 − 0x139893000 = 0x676f000 = 0x676d000 + 0x2000. ✓ The pointer now holds base + RVA.
    4. 

  4. Arithmetic note: the loader adds delta modulo 264, so it never needs a separate "subtract" case.
    5. 



The string RVA 0x2000 is an assumption made for this exercise (the run printed only efi_main's address); the method, not the number, is what the run supports: the strings printed correctly at a base other than ImageBase. R5

Where the analogy breaks


    

  • The hotel reads the whole book; the firmware does not check what the code does. It checks headers (and signatures under Secure Boot), not whether the program is correct.
    • 

  • Correcting page numbers is not the only way to move a book. Position-independent code needs no corrections at all; only absolute addresses stored in the image do. R4
    • 

  • The old cover page is not decoration. The MS-DOS header and stub are a real, tiny DOS program in Windows executables; in the lab's EFI file LLD kept only the header fields (the "stub" is minimal). R3
    • 




Common mistakes and debugging


    

  • Symptom: firmware says "Not Found" or "Unsupported" for your .efi and falls back to the next boot option. Cause: wrong subsystem, wrong machine, no base relocations while ImageBase cannot be honoured (forensic lab), or the file is not at the default path. How to find it: read the headers with llvm-readobj --file-headers or Listing 2; read the firmware's serial log. Fix: /subsystem:efi_application, no /fixed, the right path.
    • 

  • Symptom: your PE reader prints garbage for a field. Cause: confusing an RVA with a file offset. How to find it: convert explicitly through the section table. Fix: one helper function rvaToOffset, used everywhere.
    • 

  • Symptom: UEFI calls your entry point and the arguments are nonsense. Cause: compiled with the System V convention (an ELF target) and converted. How to find it: disassemble the entry and check which registers it reads. Fix: compile for a Windows target, or mark the entry __attribute__((ms_abi)) (F2-47).
    • 

  • Symptom: lld-link complains about missing __chkstk or C runtime symbols. Cause: large stack frames or library calls in freestanding code. How to find it: the undefined symbol's name. Fix: /nodefaultlib, small frames, and your own memcpy/memset (F2-48).
    •

Observation. fixed.efi has 3 sections instead of 4 (no .reloc); Characteristics 0x23 instead of 0x22 (an extra bit, 0x1, "relocations stripped"); DllCharacteristics 0x8120 instead of 0x8160 (bit 0x40, "dynamic base", cleared); BaseRelocationTableRVA and Size 0. ImageBase is the same, 0x140000000.


Hypotheses. (a) is ruled out: the firmware found and tried to load Boot0001 from the same disk ("loading Boot0001"), as with the good image. (c) is ruled out: debug.txt is empty, so the first say never ran; the log says "failed to load … Not Found", before starting. (b) is confirmed.


Root cause. The good image ran at 0x676d000, which shows that the firmware did not (or could not) use 0x140000000 in this machine. An image without base relocations can run only at its ImageBase, so the loader had to refuse it. (The exact reason OVMF reports "Not Found" rather than another status was not investigated; the observation is the refusal and the fallback to "EFI Internal Shell".)


Fix and verification. Remove /fixed; step boot shows the same object, linked without it, loaded and run (exit 67).


Prevention. A build check that fails when an .efi has no base relocation directory (Listing 2 prints BaseRelocationTableSize); a boot test in the emulator in continuous integration; read what a linker option does in the linker's documentation before using it to save space.
