Story hook

In F2-01 you met Mr Haddad, the kitchen manager who binds everyone's translated recipe cards into one book. Today Amira, the new apprentice, watches him closely. Every card arrives with a small slip clipped to it. One slip says: "line 3 of this card: write here how far it is from this line to the page called Price list". Another says: "line 9: write here where the page Order counter starts". Some slips are about pages on the same card; most are about pages that other cooks wrote.

Mr Haddad never reads the recipes themselves. He lays out all the pages, decides on which page of the book each card will start, and only then goes through the slips one by one, doing a little subtraction for each and writing the number into the blank. If a slip names a page that no card provides, he stops. If two cards both claim to be the Price list, he stops too. And if one card says "use my Alarm page only if nobody else has one", he quietly uses it whenever nobody else does, which, as you will see in the forensic lab, can switch off an oven's safety alarm without a single warning.

Those slips are called relocations, and in this chapter you will read them, do the subtraction yourself, and check your number against the bytes the real linker wrote.

What you will be able to do

  • Explain what a relocatable object file contains: sections, a symbol table, a string table and relocation entries.
  • Read symbol tables with nm and readelf -s: name, value, size, type, binding (local, global, weak) and section index, including C++ mangled names.
  • Read relocation entries with readelf -r and objdump -dr, and say which instruction bytes each one patches.
  • Compute a PC-relative relocation by hand (S + A − P) and verify it against the linked executable.
  • Diagnose link-time surprises: undefined and duplicate symbols, a relocation that does not fit, and a weak default that silently wins.
Jargon box
Relocatable object file
Simple words: the machine-code output of compiling one source file, with blanks still to be filled in. Analogy: a translated recipe card with slips clipped to it. Precise: an ELF file of type REL (on this machine) holding sections of code and data, a symbol table and relocation entries; it is input to a linker, not something you can run. D2 R1
Section
Simple words: one named part of an object file, such as the code or the initialised data. Analogy: the parts of a card: the steps, the ingredient list, the empty boxes to fill in later. Precise: a named, typed range of an ELF file described by a section header; common ones are .text (code), .data (initialised writable data), .bss (zero-initialised data, no bytes in the file), .rodata (read-only data). D2 D4
Symbol table
Simple words: the list of names an object file defines or needs. Analogy: the page titles on a card, and its "see page X" notes. Precise: an array of entries (in ELF64, 24 bytes each) giving each symbol's name (as an offset into a string table), value, size, type, binding, visibility and the index of the section it is defined in, or "undefined". D2 R1
Symbol binding
Simple words: who may see a name and how strongly it is defined. Analogy: a private note on one card (local), a page title the whole book may use (global), or a "use mine only if nobody else has one" page (weak). Precise: LOCAL symbols are visible only inside their object file; GLOBAL symbols resolve references from other files; WEAK symbols are global but give way to a GLOBAL definition of the same name and may stay undefined without an error. D2 D1
Relocation
Simple words: an instruction to the linker: "when you know the addresses, put this value at this place". Analogy: the slip clipped to a card. Precise: an entry (in ELF64 with explicit addend, a RELA entry) giving the offset of the field to patch, a relocation type that says how to compute the value, the symbol it refers to, and an addend. D2 D3
Addend
Simple words: a constant added to the symbol's address in the calculation. Analogy: "minus 4" written on the slip. Precise: the A in the relocation formula; for x86-64 PC-relative fields that end an instruction it is −4, because the processor measures the distance from the end of the 4-byte field. D3 R2
PC-relative relocation
Simple words: a blank that must hold a distance, not an address. Analogy: "write how many pages from here to the Price list". Precise: a relocation whose value is computed as S + A − P (symbol address plus addend minus the address of the field), such as R_X86_64_PC32; the result must fit the field, here a signed 32-bit integer. D3 R2
Map file
Simple words: the linker's report of where it put everything. Analogy: Mr Haddad's table of contents, with the card each page came from. Precise: a text file written on request (GNU ld: -Map=file) listing each output section, the input sections placed in it with their addresses, sizes and object files, and symbol addresses. D5 R3

The idea in pictures

Figure 2 zooms into one relocated field: the four bytes after the call opcode e8. In main.o they are zero; in the executable they hold 0x38, the distance from the end of the field to the called function.

Layer 1 — the kid explanation

When a program is made of several files, the compiler translates each file alone. It cannot know where the other files' functions and variables will end up, so it leaves blanks and writes a note for each blank: which name it needs, and how to compute the number. The linker reads all the translated files, decides where everything goes, and fills in every blank using those notes. If a name has no owner, or two owners, it complains.

Layer 2 — the student explanation

What is inside an object file

Compile the lab's counter.cpp with g++ -c and ask file what it is: "ELF 64-bit LSB relocatable, x86-64". R1 ELF (Executable and Linking Format) is the object and executable format of Linux and many other systems; F2-44 reads its headers byte by byte. A relocatable file is organised in sections, each with a header that gives its name, type, flags, size and position in the file. D2 readelf -S counter.o listed thirteen sections, among them .text (flags AX: allocated and executable), .data (WA: writable, allocated), .bss of type NOBITS (it occupies memory but no bytes in the file), .rela.text of type RELA, and .symtab and .strtab. R1 All their addresses are 0: nothing has been placed yet. R1

Symbols: name, value, type, binding, section

The symbol table of counter.o (Listing 1's output) has eight entries. The interesting ones are _Z13next_order_idv (FUNC, GLOBAL, section 1 = .text, value 0, size 27), _Z12calls_so_farv (FUNC, GLOBAL, value 0x1b), g_orders (OBJECT, GLOBAL, section 3 = .data, size 4) and _ZL7s_calls (OBJECT, LOCAL, section 4 = .bss). R1 In an object file a symbol's value is its offset inside its section; after linking it becomes an address. D2

  • Binding follows linkage. static int s_calls has internal linkage in C++, so the compiler emits it as a LOCAL symbol: no other file can refer to it, and two files may each have their own s_calls. D7 R1
  • Names are mangled. C++ functions carry their parameter types in their symbol names (F2-01): next_order_id() becomes _Z13next_order_idv, where 13 is the length of the name and v stands for an empty (void) parameter list; nm -C shows the readable form. The rules are those of the Itanium C++ ABI, which F2-47 returns to. D8 R1 Variables such as g_orders are not mangled here, and neither their type nor a function's return type is encoded: the linker cannot catch a declaration that lies about them (Common mistakes).
  • Undefined symbols. In main.o, nm prints U for _Z13next_order_idv, _Z12calls_so_farv, g_orders and printf: they are used but defined elsewhere. R1 In the ELF symbol table this is a symbol whose section index is the special value "undefined" (UND in readelf). D2
  • nm's letters. T = defined in a text (code) section, D = initialised data, b/B = BSS, r = read-only data, W = weak, U = undefined; lower case means local. D5 R1

Relocations: the slips

readelf -r main.o shows six entries in .rela.text. Each has an offset (where in .text the field to patch starts), a type, a symbol and an addend. D2 R1 Three calls use R_X86_64_PLT32; the load of g_orders and the address of the format string use R_X86_64_PC32; every addend is −4. R1 objdump -dr prints each relocation under the instruction it patches: a: call f <main+0xf> with b: R_X86_64_PLT32 _Z13next_order_idv-0x4 underneath. The call's four displacement bytes are zero in the object file, which is why objdump shows the "target" as the next instruction. R1

Not every name needs a relocation in every place: a call between two functions of the same section could be resolved by the compiler. GCC still emitted relocations for calls to next_order_id because it is a global symbol that another file could, in principle, replace (interposition in shared libraries); this is an implementation choice, which we only observe here. D1 R1

Resolution: exactly one definition

The linker's second job is symbol resolution: every undefined reference must be matched with exactly one GLOBAL definition among the inputs (or a library). D1 D4 No definition gives "undefined reference" (F2-01); two GLOBAL definitions give "multiple definition" (F2-07). A WEAK definition is the exception: it is used only when no GLOBAL definition exists, and a GLOBAL definition silently replaces it. D2 R4 That is useful for default hooks (a library provides a default, the application may override it) and dangerous when the override is accidentally left out of the link (the forensic lab).

Layer 3 — the engineer's depth

Analogy first, briefly: placing the pages, matching the "see page" notes, and doing the subtraction on each slip are the linker's three passes. Now the specification level.

The relocation formulas of the x86-64 psABI

The ELF specification defines the relocation entry; each processor supplement defines the types and how each value is computed. For x86-64, the System V AMD64 psABI uses the symbols S (the value of the symbol), A (the addend), P (the place: the address of the storage unit being relocated), L (the place of the symbol's PLT entry), and defines, among many others: R_X86_64_64 = S + A (a 64-bit field), R_X86_64_PC32 = S + A − P (a 32-bit field), R_X86_64_PLT32 = L + A − P (32-bit), R_X86_64_32 and R_X86_64_32S = S + A (32-bit, zero- or sign-extended). D3 These names and formulas are written from memory and must be checked in the psABI's relocation chapter (see the unverified box); what this build verified is narrower and solid: for the four PC32/PLT32 relocations of main that refer to symbols defined in the executable, S + A − P computed from nm addresses equals, byte for byte, what ld wrote (Listing 3, R2). R2

For R_X86_64_PLT32 the formula names L, the PLT entry. When the called function is defined in the same executable, the linker does not need a PLT entry and uses the function's own address: the lab's calls go straight to 0x1190 and 0x11ab. R2 The call to printf, defined in the shared C library, does go through the PLT: the linked main calls printf@plt at 0x1050, and the executable keeps a dynamic relocation R_X86_64_JUMP_SLOT against printf@GLIBC_2.2.5 in .rela.plt, which the dynamic loader resolves at run time. R2 D1 (The lab's command adds -U_FORTIFY_SOURCE so that the call keeps the plain name printf; with Ubuntu's default fortification, an optimised build may call a checking variant instead. That is a distribution setting, checked here only by keeping it out of the way.)

Not verified — check before relying on this

The relocation type names, their numeric values (PC32 = 2, PLT32 = 4 in the Info column of the run, R1) and the formulas S + A, S + A − P, L + A − P are written from memory of the System V AMD64 psABI. Check them in "System V Application Binary Interface, AMD64 Architecture Processor Supplement", chapter on relocation (relocation types table), for the version recorded in the dossier. The lab proves only that S + A − P reproduces the four fields shown.

Range: why 32 bits is a design decision

A 32-bit signed field can hold distances from −231 to 231 − 1 bytes, that is up to 2 GiB either way. Code generated with the default "small" code model assumes all code and data of the program lie within that range, so most references can be 4-byte RIP-relative fields. D3 If the linker cannot honour that assumption, it must stop. The lab forces it: with .data placed at 0x200000000 (8 GiB), GNU ld reports "relocation truncated to fit: R_X86_64_PC32 against symbol `g_orders' defined in .data section in counter.o" for main.cpp:(.text+0x22), exactly the offset of the g_orders relocation, and refuses to write the executable. R5 A kernel that runs at the top of the 64-bit address space uses a different code model for the same reason (milestone B1's linker script, F2-46).

Position-independent executables and what remains for the loader

The executable built in the lab is a PIE ("pie executable" in file's words): its addresses start near 0 and the loader may place it anywhere. R2 PC-relative references survive that move unchanged, because code and data move together; absolute addresses stored in data would not, so they become dynamic relocations (.rela.dyn, 8 entries in this run) applied by the loader. R2 D1 The same idea appears in PE/COFF as base relocations, which you will watch UEFI firmware apply in F2-45.

Linking order, archives and COMDAT

Two more resolution rules matter in practice. First, a static library (.a) is an archive of object files, and GNU ld extracts a member only when it defines a symbol that is undefined at the moment the archive is scanned, scanning the command line left to right; a library placed before the objects that need it therefore contributes nothing. D5 D4 Second, C++ inline functions and templates are emitted in every object file that uses them, in "group" sections (COMDAT) so that the linker keeps one copy and discards the rest; F2-47's lab shows such groups (flag G) for a class's vtable and member functions. D2 D8

How the hardware actually does it

The relocations exist because of how the processor encodes addresses. An x86-64 near call with opcode e8 carries a signed 32-bit displacement; the processor adds it to the address of the instruction that follows the call (the value the instruction pointer has after fetching the call) to get the target. D6 That is why the addend is −4 when the field is the last four bytes of the instruction: P + 4 is the next instruction's address, so S + (−4) − P = S − (P + 4). R2 In 64-bit mode, data can be addressed the same way, relative to the instruction pointer (RIP-relative addressing): mov 0x2ea1(%rip),%ecx in the linked main loads g_orders without any absolute address in the code. D6 R2 Bytes are stored little-endian, least significant first, which is why the field 0x00000038 appears as 38 00 00 00. R2 Other instruction sets split addresses differently (AArch64, for example, builds a PC-relative address from a page part and an offset part in two instructions), so they have different relocation types for the same idea; their psABIs define them. D9

Worked example

Task. In main.o, the relocation at offset 0x22 is R_X86_64_PC32 g_orders − 4. In the executable, nm says main is at 0x1149 and g_orders at 0x4010. Compute the four bytes the linker must write, and check that the processor will then load from 0x4010.

  1. P = address of the field = 0x1149 + 0x22 = 0x116b.
  2. S + A − P = 0x4010 − 4 − 0x116b. First 0x4010 − 0x116b = 0x2ea5 (check: 0x116b + 0x2ea5 = 0x4010). Then 0x2ea5 − 4 = 0x2ea1.
  3. 0x2ea1 = 11,937 in decimal: positive and far below 231, so it fits a signed 32-bit field.
  4. Little-endian bytes: a1 2e 00 00.
  5. The processor: the instruction is 8b 0d plus the 4-byte field, starting at 0x1169 and ending at 0x116f, so the next instruction is at 0x116f; 0x116f + 0x2ea1 = 0x4010. ✓

Listing 3 did the same computation for all four locally resolved relocations and compared with the bytes in the file: "S + A − P = 11937 (0x2ea1 …) linker wrote 11937 (bytes a1 2e 00 00) … match: YES". R2 objdump agrees independently: it prints mov 0x2ea1(%rip),%ecx # 4010 <g_orders>. R2

Where the analogy breaks


    

  • Mr Haddad reads the recipes; the linker does not. The linker never checks that a declaration matches its definition. If one file says extern long g_orders; and another defines int g_orders, it links: the variable's name carries no type. Functions are protected only partly, by C++ name mangling of the parameter list; return types are not encoded for ordinary functions. D8 D7
    • 

  • Page numbers in a book are absolute; most slips here hold distances. A PC-relative field holds S − (P + 4), not S. That is what lets the same code run at any address, which a printed page number never could. D3 R2
    • 

  • Not all slips are handled by the manager. Some relocations are deliberately left in the output for the dynamic loader (the JUMP_SLOT for printf), and the processor itself never sees any relocation at all, only the patched bytes. R2
    • 

  • A "default page" in a kitchen would be noticed. A weak definition is replaced, or kept, with no message in either case. R3 R4

Common mistakes and debugging


    

  • Symptom: undefined reference to `next_order_id()'. Cause: the defining object or library is not on the link line, or is declared with a different signature (different mangled name), or with extern "C" on one side only. How to find it: nm -C on every input: is there a T for exactly that name? Compare mangled names with nm (without -C). Fix: add the object, or make the declarations identical (one shared header, F2-07).
    • 

  • Symptom: multiple definition of `g_orders'. Cause: a non-inline variable or function defined in a header included twice. How to find it: the message names both objects. Fix: declare in the header, define in one .cpp, or use inline variables (C++17). D7
    • 

  • Symptom: a variable "changes by itself" or reads garbage in the upper half. Cause: two declarations with different types (long versus int); the linker cannot see it. How to find it: readelf -s shows the definition's size (4 bytes for g_orders, R1); compare with the type every user believes. Fix: one declaration in one header.
    • 

  • Symptom: "relocation truncated to fit: R_X86_64_PC32 against symbol …". Cause: code compiled for the small code model, but the linker placed the target more than 2 GiB away (R5). How to find it: the message gives the object, section and offset; readelf -r shows the relocation there. Fix: fix the layout (linker script, F2-46) or compile with a code model that matches it.
    • 

  • Symptom: a library function is "undefined" although the library is on the command line. Cause: the library came before the objects that use it. How to find it: move it to the end; GNU ld's --trace-symbol=NAME (-y) reports where a symbol is defined and referenced (check the option in the ld manual, D5). Fix: objects first, libraries after, in dependency order.
    • 

  • Symptom: the program runs but a hook or interrupt handler does nothing. Cause: a weak default won because the strong definition was not linked (forensic lab). How to find it: nm shows W for the symbol in the final program; the map file shows which object supplied it. Fix: link the right object; make the build fail when an override is required (for example no weak default for safety-critical hooks).
    •

Summary


    

  • The compiler turns one translation unit into a relocatable object file: sections, a symbol table, a string table and relocation entries.
    • 

  • Symbols have a value (an offset until linking), size, type, binding (LOCAL, GLOBAL, WEAK) and a section index or "undefined"; C++ names are mangled.
    • 

  • The linker places sections, resolves each undefined symbol to exactly one definition, then patches each relocated field.
    • 

  • A PC-relative field holds S + A − P; on x86-64 the addend −4 accounts for the processor measuring from the next instruction.
    • 

  • Four relocated fields of the lab were recomputed and matched byte for byte; a layout beyond ±2 GiB was refused with "relocation truncated to fit".
    • 

  • Relocations against shared-library symbols are left for the dynamic loader (JUMP_SLOT).
    • 

  • Weak symbols, type-mismatched declarations and library order fail silently or confusingly: read nm and the map file, not only the error messages.

Forensic lab answer key


Observation. The run printed "default on_overheat(97): nothing to do". nm -C sensor.o shows W on_overheat(int) and nm -C oven shows the same W at 0x1165, inside sensor.o's .text (the map file puts sensor.o's code at 0x1165). The map lists only main.o and sensor.o among the project's objects, and although ls shows board.cpp in the folder, make never compiles it.


Hypotheses. "The temperature check is wrong": ruled out, the default hook was called with 97, so the comparison worked. "The board hook was not called": true but incomplete. "The board hook was not linked": proven by the map file and the absence of board.o.


Root cause. OBJS = main.o sensor.o $(wildcard board_v1.o): after the rename, the wildcard matches nothing, so board.o is neither a prerequisite nor on the link line. Because sensor.cpp provides a weak default, the reference to on_overheat is satisfied, and a weak definition used alone is not an error. No message is produced.


Fix and verification. List board.o explicitly in the prerequisites and in OBJS. Step forensic_fixed shows the result: "board on_overheat(97): HEATER OFF" and nm now prints T on_overheat(int) (strong, GLOBAL).


Prevention. Remove the weak default for safety-critical hooks, so a missing board file becomes "undefined reference"; or add a link-time check (for example a test that runs nm on the final binary and fails on W on_overheat); never build object lists with wildcard for required files.


How the evidence was made. The Makefile in the evidence folder was written with the renamed file left out; run.sh step forensic_build runs it unchanged.
