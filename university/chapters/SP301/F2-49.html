Story hook

Mr Haddad's kitchen has a few tools that no recipe language describes: the blowtorch, the liquid-nitrogen flask, the old oven's secret reset lever. The cooks may use them, but only through a laminated handling card fixed to each tool: "takes: one dish; gives back: one dish, browned; may splash: the counter to your left". Cooks who follow the card can plan around the tool. A cook who uses the blowtorch without telling anyone what it splashed leaves the next cook working on a counter he believes is clean.

Amira's colleague Lars writes a card for a new "ready" stamp: "takes: the address of the order slip". He forgets to write "changes: the order slip itself". The head cook, who just read that slip, keeps working from what he remembers it said — zero — and the order is never served. You will reproduce that bug with one line of inline assembly and see the compiler do exactly what the card allowed.

What you will be able to do

  • Write GCC/Clang extended inline assembly with correct outputs, inputs, clobbers and constraints.
  • Wrap each special instruction (CPUID, RDTSC, BSR, CR0, CLI, IN/OUT) in a tiny typed C++ function.
  • Explain what volatile and the "memory" and "cc" clobbers tell the compiler, and predict what it may do without them.
  • Recognise privileged instructions and what happens when user code tries them.
  • Diagnose a wrong result caused by an incomplete asm statement, from disassembly.
Jargon box
Extended asm
Simple words: a way to put a few machine instructions inside C++ and tell the compiler what they read and write. Analogy: the specialist tool plus its handling card. Precise: the GCC/Clang statement asm [volatile] ("template" : outputs : inputs : clobbers); the compiler treats the template as an opaque block, allocates registers for the operands according to their constraints, and relies only on the declared effects. D1 D2
Constraint
Simple words: a letter that says where an operand must be. Analogy: "put the dish on the left tray". Precise: a string such as "r" (any general register), "m" (memory), "a"/"b"/"c"/"d" (the specific x86 register), "N" (an 8-bit unsigned constant for I/O instructions); "=" marks a write-only output. D1
Clobber
Simple words: something the assembly changes that is not an output. Analogy: "may splash the counter to your left". Precise: an entry in the fourth list: a register name, "cc" (condition flags) or "memory" (memory may be read or written in ways the operands do not show: the compiler must not cache memory values in registers across the statement or move memory accesses across it). D1 R7
Privileged instruction
Simple words: an instruction only the operating system's kernel may run. Analogy: the oven's reset lever, for the head cook only. Precise: on x86, instructions such as mov to or from control registers, cli, hlt or lgdt that require current privilege level 0 (some, like I/O instructions, depend on IOPL and the I/O permission bitmap); otherwise the processor raises a general-protection exception. D3 R3

Layer 1 — the kid explanation

Some things a processor can do have no word in C++: "tell me your brand name", "how many ticks since power-on?", "stop listening to interruptions". To use them, we write the one machine instruction ourselves and wrap it in a small C++ function. Around it we tell the compiler exactly what goes in, what comes out and what else changes, because the compiler cannot read the instruction and believes only what we tell it.

Layer 2 — the student explanation

The rules of a good wrapper

  1. One instruction (or a tiny fixed sequence) per wrapper, with a C++ name and C++ types: cpu::rdtsc() returns uint64_t. The rest of the code never sees assembly.
  2. Every value in or out is an operand with a constraint; never assume a value "happens to be" in a register.
  3. Every other effect is a clobber: registers written but not outputs, "cc" if flags change, "memory" if memory is touched behind the compiler's back or ordering matters.
  4. volatile when the instruction has effects beyond its outputs or can give different results for the same inputs (reading a counter, port I/O, control registers).
  5. Test it against plain C++ where an equivalent exists.

Listing 1 follows these rules for CPUID, RDTSC, BSR and a compiler barrier. The demo ran under AddressSanitizer and UBSan: CPUID leaf 0 reported the highest standard leaf (32) and the vendor string "GenuineIntel" from EBX, EDX, ECX in that order; two RDTSC readings increased; and the BSR wrapper agreed with std::bit_width(v) − 1 on every tested value (0 mismatches). R1 Those numbers describe the build container's (virtualised) processor and are not a property of x86 in general.




Reading the constraints


In asm("bsrq %1, %0" : "=r"(index) : "rm"(value) : "cc"), %0 and %1 are operand numbers counted across outputs then inputs. "=r" lets the compiler pick any register for the result; "rm" lets it pass value in a register or straight from memory; "cc" declares that BSR changes the flags. D1 The disassembly shows the compiler's choices, bsr %rbx,%rax and bsr %rbx,%rdx: two inlined copies with different output registers. R1 For I/O, "Nd"(port) means "an 8-bit constant if possible, otherwise DX", which matches the two encodings of the x86 in/out instructions; the kernel's inb(0xf4) became in $0xf4,%al. D3 R4



What volatile on asm means


Without volatile, an asm statement with outputs is treated like a pure function of its inputs: if its outputs are unused, it may be deleted; if two have the same inputs, they may be merged. D1 Listing 2 has an RDTSC wrapper without volatile. At -O0 the program contains one rdtsc (in the non-inlined wrapper, called twice) and the two readings differ. At -O2 the program contains no rdtsc at all and says the readings are identical: the compiler merged the two statements (same inputs: none), concluded t2 == t1, and then removed the now-unneeded asm entirely. R2 That is not a compiler bug: the statement claimed to have no side effects.





Layer 3 — the engineer's depth


The handling card is a contract that the compiler enforces against you: it will move, merge or delete the tool's use whenever the card permits. Three parts of the contract cause most bugs.


The "memory" clobber and hidden memory operands


An asm statement that writes memory through a pointer it receives as a register input has not told the compiler that memory changed. In the forensic lab, asm volatile("movl $1, (%0)" : : "r"(&b->ready)) stores to b->ready, but the compiler only knows "the asm reads a pointer value". In publish, compiled with -O2, it had just stored 0 to b->ready, so for the following return b->ready it returned the 0 it remembered: xor %eax,%eax. R7 It even merged the two earlier stores into one 8-byte store from a constant (mov 0xe79(%rip),%rax; mov %rax,(%rdi)). R7 Two correct fixes: declare the memory as an output operand, asm volatile("movl $1, %0" : "=m"(b->ready)), which tells the compiler precisely what changed; or add a "memory" clobber, which tells it "any memory may have changed" and costs more optimisation. D1 volatile alone does not help: it keeps the statement, not the compiler's knowledge of memory. R6


The "memory" clobber with an empty template (compilerBarrier() in Listing 1) is a compiler barrier: it stops the compiler from moving memory accesses across it, but emits no instruction, so it does not order accesses between processor cores. D1 Ordering between cores needs atomic operations or fence instructions, covered with concurrency in later courses.



Privileged instructions: user mode versus ring 0


Reading CR0 from a Linux program compiles fine; running it ends the process with exit status 139 (signal 11, SIGSEGV) right after "about to read CR0 from user mode". R3 The processor refused a privileged instruction at privilege level 3 with a general-protection exception, and Linux turned that into a signal. D3 In the lab's ring-0 kernel (booted by QEMU's Multiboot loader, as in F2-46), the same kind of wrapper works: CR0 = 0x00000011, with bit 0 = 1 (protected mode on) and bit 31 = 0 (paging off), which is exactly the state Multiboot promises; after cli, EFLAGS = 0x00000002, so the interrupt flag (bit 9) is clear. R4

When not to use inline assembly


Prefer, in order: plain C++ (std::bit_width instead of BSR); a compiler builtin or intrinsic (__builtin_ia32_rdtsc, <x86intrin.h> functions), which the compiler understands fully; inline assembly in a one-instruction wrapper; and only then a separate .S file for whole routines such as context switches or interrupt entry, where you control every register yourself (F2-47's rules apply in full). D1 Inline assembly is also not standard C++: the asm declaration is "conditionally-supported" with implementation-defined meaning; the extended syntax here is a GCC extension that Clang implements. D4 D2 MSVC does not support inline assembly for x64 at all, which matters only if you build UEFI code with Microsoft's compiler.



How the hardware actually does it


Each wrapper is one instruction with a fixed hardware contract. CPUID takes a leaf number in EAX (and sometimes a subleaf in ECX) and overwrites EAX, EBX, ECX and EDX — all four, which is why all four are outputs. RDTSC writes the 64-bit time-stamp counter into EDX:EAX, the high half in EDX. BSR writes the index of the highest set bit and sets flags (its result is undefined for zero input, so the wrapper's comment says "non-zero"). in/out address the separate 64 KiB I/O space with the port in an 8-bit immediate or DX and data in AL/AX/EAX. D3 The privilege check happens inside the processor at execution time, using the current privilege level held in the code segment selector: the compiler and linker never know whether code will run in ring 0 or ring 3. D3 R3


Watch out
Untested on hardware. The ring-0 kernel ran only in QEMU 8.2.2 with TCG, which emulates the processor in software (R4); CR0 and EFLAGS values on a physical PC after a real bootloader can differ. The host programs ran on the build container's virtualised x86-64 processor (R1–R3), so the CPUID values are those the hypervisor presents.

Where the analogy breaks


    

  • A cook would notice the splash. The compiler cannot: whatever is missing from the card simply does not exist for it (R7).
    • 

  • Handling cards don't change how the kitchen works. Declaring operands changes the generated code around the statement: register choices, deleted or merged statements (R1, R2).
    • 

  • Anyone can pick up a blowtorch. Privilege is enforced by the processor at run time, not by who wrote the code (R3).
    • 




Safety
On a real machine, a ring-0 wrapper with a wrong clobber or a wrong control-register write can hang the computer or corrupt data on disk. Develop privileged wrappers in QEMU first, and test each one alone before using it in a driver.



Common mistakes and debugging


    

  • Symptom: a value read after an asm store is stale, only at -O2. Cause: memory written through a register operand, without "=m" or "memory" (forensic lab). How to find it: disassemble; look for the reload that is missing. Fix: a memory output operand, or the clobber.
    • 

  • Symptom: timing code always measures 0, or an I/O read happens once instead of in a loop. Cause: missing volatile (R2). Fix: asm volatile.
    • 

  • Symptom: a variable unrelated to the asm changes value. Cause: the template writes a register that is neither an output nor a clobber. How to find it: list every register the instruction writes (from the SDM) and compare with the operand lists. Fix: add outputs or clobbers.
    • 

  • Symptom: "impossible constraint in asm" or "invalid operand". Cause: a constraint that cannot be met (for example, "N" with a non-constant and no d alternative), or the wrong operand size suffix. Fix: correct the constraint; use explicit size suffixes (outb, movl).
    • 

  • Symptom: segmentation fault on a "harmless" read in a user program. Cause: a privileged instruction (R3). Fix: move it into the kernel.
    •

Summary


    

  • Extended asm: template, outputs, inputs, clobbers; the compiler trusts the lists and never reads the template.
    • 

  • Wrap one instruction per C++ function with real types; test against plain C++ where possible.
    • 

  • volatile keeps a statement that has effects or varying results; without it, the compiler merged and deleted RDTSC.
    • 

  • Memory written by asm must be an "=m" operand or covered by a "memory" clobber; otherwise the compiler uses stale values.
    • 

  • Privileged instructions work only in ring 0: CR0 read gave SIGSEGV in user mode and 0x00000011 in the QEMU kernel.

Forensic lab answer key


Observation. At -O2, "publish() saw ready = 0; memory now holds ready = 1", exit 1. The return value comes from xor %eax,%eax — a constant 0, no load.


Hypotheses. (a) is ruled out: movl $0x1,(%rdi) is in the disassembly, and memory holds 1 afterwards. (c) is ruled out: single-threaded code on one core sees its own stores in order; the processor is not involved. (b) is confirmed: the compiler returned the value it had last stored itself.


Root cause. The asm statement declares only a register input (the address), no memory output and no "memory" clobber. The compiler is therefore allowed to believe b->ready still holds 0 after the asm.


The first two instructions. The compiler combined b->ready = 0; b->length = 64; into a single 8-byte store of the constant 0x0000004000000000 (loaded from read-only data with mov 0xe79(%rip),%rax), written with mov %rax,(%rdi).


Fix. asm volatile("movl $1, %0" : "=m"(b->ready)); (precise), or add : "memory" (broad). Either way the compiler reloads or knows the new value; -O2 then returns 1.


Prevention. Review rule: any asm that touches memory names it as an operand or clobbers "memory"; test drivers at the optimisation level you ship; prefer a volatile store in C++ (F2-50) when a single store is all you need — the compiler emits one 32-bit mov for an aligned volatile uint32_t write in practice, though the language does not promise it.


How the evidence was made. run.sh builds ready.cpp at -O0 and -O2, runs both, and disassembles publish.
