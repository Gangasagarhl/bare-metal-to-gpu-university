Story hook

Until now Mr Haddad bound the book his own way, and nobody minded where the soups ended and the desserts began. Then the restaurant built a cold room with fixed shelves: the hotel's inspector must find the kitchen's licence on the first shelf, the recipes go on shelf 2, anything the cooks may write on goes on shelf 4, and shelf 5 must be empty boxes, counted but never filled until the morning. For that, Mr Haddad needs a written plan: what goes on which shelf, in which order, starting where, and where to write down "soups start here" so the cooks can find them.

A new cook, Joon, rewrote the plan to look tidier: "price lists first, then recipes". Everything was still in the book. But the inspector looked only at the first few shelves for the licence, did not find it, and closed the kitchen. In this chapter you write that plan for a real kernel — a linker script — and investigate exactly that inspection failure.

What you will be able to do

  • Write a linker script that places a kernel at a fixed address with page-aligned sections and exported boundary symbols.
  • Explain the location counter, input versus output sections, KEEP, /DISCARD/, ALIGN and ENTRY.
  • Distinguish VMA (run address) from LMA (load address) and link a higher-half kernel with AT().
  • Use boundary symbols from C++ correctly (zeroing .bss, measuring the kernel).
  • Read a map file to find where every input section went, and diagnose a layout that a loader rejects.
Jargon box
Linker script
Simple words: a text file that tells the linker where to put each part of the program. Analogy: Mr Haddad's shelving plan. Precise: a program in the GNU ld command language (also accepted, with differences, by LLD) whose SECTIONS command maps input sections to output sections, assigns addresses through the location counter, and defines symbols. D1 D2
Location counter
Simple words: the linker's "current address" while it lays things out. Analogy: the shelf position Mr Haddad's hand is at. Precise: the symbol . inside SECTIONS; assigning to it moves the layout forward; each output section starts at its current value (possibly aligned). D1
Input and output sections
Simple words: the parts in the object files, and the bigger parts they are combined into. Analogy: cards from each cook, and the shelf they are filed on. Precise: an output section statement such as .text : { *(.text .text.*) } collects input sections matching the patterns from all input files, in command-line order, into one output section. D1 R1
VMA and LMA
Simple words: the address where code will run, and the address where it is first loaded. Analogy: the shelf where a box will be used, and the loading bay where the van drops it. Precise: virtual memory address (used to compute every address in the code) and load memory address (the ELF program header's physical address, p_paddr); they differ when AT(...) is used, as in a kernel that is loaded low and runs high after paging is enabled. D1 R3
Boundary symbol
Simple words: a name the linker script defines to mark a position, such as "end of the kernel". Analogy: the tag "soups start here". Precise: a symbol assigned in the script (__bss_start = .;); it has an address but no storage, so C++ must use only its address. D1 R2
Map file
Simple words: the linker's report of where it put everything. Analogy: the finished shelving list, with the cook who wrote each card. Precise: written with -Map=file; LLD's map lists VMA, LMA, size and alignment of each output section, each input section with its object file, and each symbol. D2 R1

Layer 1 — the kid explanation

A normal program lets the linker decide where its pieces go in memory. A kernel cannot: it must sit exactly where the computer's loader expects it, with its parts in a certain order. So we give the linker a written plan, a linker script: "start at 1 MiB, code first, then read-only data, then data, then the empty space, each starting on a new page, and write down where each one starts". The kernel reads those notes to find its own pieces.

Layer 2 — the student explanation

Reading the lab's script

Listing 1 is the whole script. Read it as a program that runs once, top to bottom, inside the linker.

  • ENTRY(_start) sets the ELF header's entry point to the address of _start; readelf shows 0x10000c. D1 R1
  • . = 1M; sets the location counter to 0x100000. The first output section will start there. R1
  • .text ALIGN(4K) : { … } creates the output section .text at the next 4 KiB boundary and fills it with, in order, the .multiboot input sections (from boot.o, 12 bytes), then every .text and .text.* input section. The map file shows exactly that order: boot.o:(.multiboot) at 0x100000, boot.o:(.text) at 0x10000c, kmain.o:(.text) at 0x100030, then the three inline functions in their own .text._Z… sections. R1
  • KEEP(...) protects input sections from garbage collection (--gc-sections), which would otherwise drop a section nothing refers to; nothing calls the Multiboot header, so without KEEP it could disappear in builds that enable collection. D1
  • __text_start = .; inside a section defines a symbol at the current position. D1
  • .bss collects .bss, .bss.* and COMMON; its type is NOBITS, so it takes 0x4004 bytes of memory and none of the file. R1
  • /DISCARD/ throws away matching input sections: comments, notes and unwind tables (.eh_frame), which a kernel without exceptions does not need (F2-48). D1

What came out

The result has three PT_LOAD segments, one per permission set: R E for .text, R for .rodata, RW for .data plus .bss (file size 4, memory size 0x5004). R1 Booted by QEMU's built-in Multiboot loader, the kernel printed its own boundary symbols — __text_start 0x00100000, __rodata_start 0x00101000, __data_start 0x00102000, __bss_start 0x00103000, __bss_end 0x00107004, __kernel_end 0x00108000 — confirmed that the section starts are 4 KiB aligned, measured itself as 32,768 bytes in memory, and found g_initialised = 1234 (from the file) and g_zeroed = 0 (zeroed by boot.S). R2




Using boundary symbols from C++


A symbol defined in the script has an address and nothing else: there is no variable at __bss_start. Declare it as an array, extern "C" char __bss_start[];, so that the name itself is the address and no load from memory happens; declaring extern char __bss_start; and then reading __bss_start would read the first byte of .bss, a classic mistake. D1 Subtracting two such addresses gives a size (__kernel_end − __kernel_start = 32,768). Strictly, C++ does not define comparing or subtracting pointers into different objects; kernels do it anyway and convert to integers first, as Listing 2 does with uintptr_t. D6 R2



Layer 3 — the engineer's depth


The shelving plan has to satisfy three readers at once: the linker (which computes every address from it), the loader (which reads only program headers), and the kernel itself (which reads the boundary tags). The details below are where those readers disagree.


VMA, LMA and a higher-half kernel


Many kernels run at high virtual addresses (on 32-bit x86, often from 0xC0000000) so that user programs can have the low addresses. The bootloader, however, runs before paging and can load only to physical addresses. The solution is to link the code for the high address (VMA) and tell the loader to put it low (LMA): .text ALIGN(4K) : AT(ADDR(.text) - KERNEL_VMA) { … }. D1 The lab links the same objects with higher.ld: the entry point becomes 0xc010000c, every program header has VirtAddr 0xc01xxxxx and PhysAddr 0x001xxxxx, and nm shows kmain at 0xc0100030. R3 That kernel would crash if started as is: its first absolute jump or data access would use a 0xC… address with no memory behind it. Its entry code must first enable paging with a mapping from 0xC0100000 to 0x00100000 (and, briefly, an identity mapping of the code that switches it on); that is track B's work, so the lab only links and reads it. Two further observations: with AT(), LLD put .bss in its own LOAD segment (file size 0), where the plain layout merged it with .data; and the entry address in the ELF header is a VMA, which a loader that ignores paging must translate itself. R1 R3





The loader's view: why order matters


QEMU's -kernel option can boot a Multiboot (version 1) kernel. Multiboot requires a 12-byte header — magic 0x1BADB002, flags, checksum (the three add to 0 modulo 232) — 4-byte aligned within the first 8,192 bytes of the file. D3 That is why link.ld puts KEEP(*(.multiboot)) first in the first output section: the header lands at file offset 4096 (the first section starts at file offset 0x1000 because of 4 KiB alignment), inside the first 8 KiB. R5 Nothing in the linker knows about this requirement; it is a contract between your script and the loader.


Not verified — check before relying on this
The Multiboot header values (magic 0x1BADB002, flags 0, checksum = −(magic + flags)), the 8,192-byte search window and the 4-byte alignment are written from memory of the Multiboot Specification version 0.6.96, which was not opened in this build. The lab shows only that QEMU 8.2.2 accepted the header at file offset 4096 (R2, R5) and did not find it at 24576 (R4). That QEMU then falls back to looking for a "PVH ELF Note" is inferred from its error message, not from its documentation. Check the specification's "OS image format" section before relying on the numbers.



Section ordering, patterns and alignment rules


Within an output section, input sections are placed in the order the patterns are written; for one pattern, in the order of the input files on the command line. D1 An output section's address is the location counter aligned to the strictest alignment of its inputs, or to an explicit ALIGN; the gap is padding. D1 Page alignment between sections of different permissions lets a kernel later map .text read-only and executable, .rodata read-only and not executable, and .data/.bss writable and not executable, each with its own page-table entries; with the sections sharing a page, one of those protections would be impossible. D5 In ELF files, offsets and addresses of each LOAD segment agree modulo the page size (F2-44), which is why the file grows when you align sections in memory: kernel.elf's sections begin at file offsets 0x1000, 0x2000, 0x3000. R1


GNU ld versus LLD


The lab uses LLD (ld.lld -m elf_i386). LLD accepts most of the GNU linker-script language, but not all of it, and its map-file format is different (the lab's map has columns VMA, LMA, Size, Align, Out, In, Symbol). D2 R1 If you write scripts that must work with both, test with both; this lab tested only with LLD 18.1.3.



How the hardware actually does it


When QEMU's Multiboot loader starts the kernel, the processor is in 32-bit protected mode with paging off: every address the code uses is a physical address, which is why link.ld makes VMA = LMA. D3 D5 The loader copies each PT_LOAD segment's file bytes to its physical address and, per Multiboot, may or may not zero .bss; boot.S zeroes it itself with rep stosb from __bss_start to __bss_end, so the kernel does not depend on that. R2 The 1 MiB start address avoids the first megabyte of a PC's physical address space, which holds legacy areas such as video memory and the BIOS. D5 On a real PC with a different loader (GRUB, for example) the same Multiboot rules would apply, but this build did not try one.


Watch out
Untested on hardware. All boots ran in QEMU 8.2.2 (TCG) with its built-in Multiboot loader (R2, R5). No physical PC and no other bootloader was used. The output devices (port 0xe9 console, isa-debug-exit) exist only in QEMU; on a real machine this kernel would run but print nothing.

Where the analogy breaks


    

  • A shelving plan is followed by people who think. The linker follows the script literally: if a pattern does not match an input section, that section is placed by default rules (as an "orphan" section) without complaint, possibly somewhere you did not expect. D1
    • 

  • A box is in one place; a section can have two addresses. VMA and LMA have no kitchen equivalent. R3
    • 

  • Empty boxes would take shelf space; .bss takes none in the file. R1
    • 




Common mistakes and debugging


    

  • Symptom: the loader refuses the kernel or reports no header. Cause: the header section is not first or is collected away (forensic lab). How to find it: search the file for the magic bytes and check the offset; read the map. Fix: KEEP(*(.multiboot)) first in the first output section.
    • 

  • Symptom: a global variable has garbage at boot. Cause: .bss not zeroed, or the script does not include COMMON or .bss.*, so some variables fall outside __bss_start…__bss_end. How to find it: nm -n: are all B/b symbols between the two boundaries? Fix: complete patterns; zero the range in the entry code.
    • 

  • Symptom: the kernel reads strange values from a boundary symbol. Cause: declared as extern char __bss_start; and read as a value. Fix: declare as an array and use only its address.
    • 

  • Symptom: the higher-half kernel triple-faults at its first instruction. Cause: started without paging, or the entry code uses VMA addresses before paging is on. How to find it: QEMU -d int,cpu_reset and the faulting address. Fix: write the early entry code to use physical addresses (subtract the offset) until paging is enabled.
    • 

  • Symptom: a new section appears in an odd place in the map. Cause: an orphan section (for example .init_array, see F2-48) not matched by any pattern. Fix: add an explicit output section for it, or --orphan-handling=error to make the linker report orphans (an LLD/GNU ld option; check its exact behaviour in your linker's manual).
    •

Forensic lab answer key


Observation. In new.elf the magic is at file offset 24,576 (0x6000); in the fixed (original-order) kernel with the same table it is at 4,096. QEMU says "Error loading uncompressed kernel without PVH ELF Note".


Hypotheses. (a) is ruled out: fixed.elf contains the same 16 KiB table and boots. (b) is ruled out: the magic bytes are intact, just elsewhere. (c) is confirmed.


Root cause. link_new.ld puts .rodata first: the map shows .rodata at 0x100000 with size 0x416c (the 0x4000-byte table from tables.o plus 0x16c), so .text, which begins with boot.o:(.multiboot), moves to 0x105000, file offset 0x6000 = 24,576. That is outside the first 8,192 bytes where the Multiboot loader searches, so QEMU did not recognise the kernel as Multiboot. Before the table was added, .rodata was only 0x16c bytes, and the header would still have been in the first 8 KiB in the new order: the bug was latent until the table grew .rodata.


Fix. (1) Return to link.ld (step forensic_fixed: magic at 4096, the kernel boots). (2) Keep .rodata first but add a tiny first output section just for the header, .multiboot : { KEEP(*(.multiboot)) }, before .rodata.


Prevention. A build step that searches the first 8 KiB for the magic at a 4-byte-aligned offset and fails otherwise (the mini-project), and a boot test in the emulator for every change to the linker script.


How the evidence was made. run.sh step forensic_new links the unchanged kernel objects plus tables.o with link_new.ld.
