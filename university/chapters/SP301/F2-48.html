Story hook

The restaurant runs a pop-up stall at a festival. There is no supplier, no cleaning crew, no manager who lights the ovens at six. Mr Haddad's recipes assume all of that: "take a clean bowl" (who washed it?), "from the warm oven" (who lit it?). Amira goes through the recipes and writes a list of everything the stall must provide itself: bowls, knives, someone who lights the ovens before service. Some recipes she simply crosses out: the flambé needs a fire licence the stall will never have.

On the first evening, everything works except the soup: cold, as if the oven had never been lit. It hadn't. The list said "light all ovens on the oven list before service", and the stall's plan copied from an older festival kept the oven list on a different board, so the person lighting the ovens read an empty list and went home satisfied. That is this chapter's forensic case, "the global that was never constructed", and you will solve it from a map file and ten lines of disassembly.

What you will be able to do

  • Set up milestone P1: a cross build for x86_64-unknown-none-elf with separate host and target configurations, from a clean clone, and prove with readelf that the object has no host C library dependency.
  • Explain what "freestanding" means for C++: which language features need runtime support, and which compiler flags remove them.
  • Provide the minimal runtime a freestanding C++ kernel needs: memcpy, memset, operator new/delete, __cxa_pure_virtual, __cxa_atexit.
  • Run global constructors yourself from .init_array, with the linker script that collects it.
  • Diagnose a global that was never constructed from the map file and disassembly.
Jargon box
Freestanding implementation
Simple words: C++ without an operating system or its library underneath. Analogy: the pop-up stall with no supplier. Precise: a C++ implementation in which programs may run without an operating system; only a subset of the standard library (the freestanding headers) is required, and program start-up and termination are implementation-defined. -ffreestanding tells the compiler not to assume a hosted library. D1 D4
Cross compiler / target triple
Simple words: a compiler that builds code for a different system than the one it runs on. Analogy: cooking in the main kitchen for the stall's equipment. Precise: a compiler configured for a target named by a triple such as x86_64-unknown-none-elf (architecture, vendor, operating system, object format); Clang selects the target with --target=, GCC needs a separately built compiler. D5 R1
init_array
Simple words: a list of functions to run before the program's main code, to build global objects. Analogy: the list of ovens to light before service. Precise: an ELF section (SHT_INIT_ARRAY) of function pointers; compilers put a pointer to each translation unit's static-initialisation function there; in a hosted program the C runtime calls them, in a freestanding kernel the kernel must. D3 R6
Guard variable
Simple words: a hidden flag that remembers whether a function's static object has been built yet. Analogy: a "lit" tag on an oven that is lit only the first time someone needs it. Precise: for a function-local static with dynamic initialisation, the Itanium C++ ABI uses a guard object and, for thread-safe statics, calls __cxa_guard_acquire/__cxa_guard_release, which a freestanding environment must provide or disable. D2 R4
RTTI
Simple words: type information kept in the program so it can ask "what type is this object really?" at run time. Analogy: a label on each dish naming its recipe. Precise: run-time type information used by dynamic_cast, typeid and exception matching; implemented with typeinfo objects that need the C++ runtime library; disabled with -fno-rtti. D2 R3

Layer 1 — the kid explanation

Normal C++ programs get help before main starts: someone sets up memory, builds global objects, and provides library functions. A kernel runs before any of that exists. So kernel C++ switches off the features that need a big helper library (exceptions, run-time type checks), writes the few small helpers itself, and does the set-up steps itself — including building the global objects, which nobody else will do.

The flags, and what each removes


    

  • -ffreestanding: the compiler must not assume the hosted library (for example, that main is special or that library functions behave as specified). D4
    • 

  • -fno-exceptions: no throw, try or catch; no unwind tables needed for them. Both compilers reject throw outright: Clang says "cannot use 'throw' with exceptions disabled", GCC "exception handling disabled, use '-fexceptions' to enable". R3
    • 

  • -fno-rtti: no dynamic_cast or typeid; Clang says "use of dynamic_cast requires -frtti". R3
    • 

  • -nostdlib (at link time): no C runtime start files and no standard libraries. The lab's kernels link with ld.lld directly, which links nothing it is not given. D4
    • 

  • -mno-red-zone for x86-64 kernel code (F2-47).
    • 



The headers are a separate problem. The freestanding target in this container has the compiler's own C headers (stdint.h, stddef.h) but no C++ standard library at all: #include <cstdint> fails with "'cstdint' file not found". R3 The C++ standard lists headers a freestanding implementation must provide, but a bare compiler without a library does not implement them; the lab's kernels therefore use <stdint.h> and avoid std::initializer_list (a braced list in a range-for needs it). D1





What the compiler still calls


Even with those flags, ordinary C++ code makes the compiler emit calls to functions it expects someone to provide. The lab compiles the kernel without its runtime file and asks nm and the linker what is missing: operator new(unsigned int), operator delete(void*), __cxa_atexit, __dso_handle, plus the kernel's own variable g_atexit_registrations; LLD reported four of them as undefined. R5 (LLD did not report __dso_handle; it appears to define that symbol itself, an observation not checked in its documentation.) Listing 2 supplies:


    

  • memcpy and memset: compilers may turn struct copies and zeroing into calls to them, even in freestanding mode. D4
    • 

  • operator new/delete: here a 4 KiB bump allocator that never frees, enough for one new Uart; a real kernel heap is milestone B5.
    • 

  • __cxa_pure_virtual: placed in vtables for pure virtual functions; called only by a bug. D2
    • 

  • __cxa_atexit and __dso_handle: a global with a non-trivial destructor registers it at construction; a kernel never exits, so the lab counts registrations and ignores them. D2 R6

Layer 3 — the engineer's depth


In the stall's terms: the recipes still say "from the warm oven", and you must decide who lights it, when, and from which list. Here is the precise mechanism, and two more traps.


Global constructors and .init_array


C++ promises that a global object like Log g_log; is constructed before main (more precisely, dynamic initialisation of non-local variables happens before their first use, and in practice before main). D1 When a constructor cannot run at compile time — Log() prints, so it cannot — the compiler emits a per-file function (_GLOBAL__sub_I_kmain.cpp) that constructs every such global of that file and registers destructors, and it puts a pointer to that function in an .init_array input section. R6 In a hosted Linux program, the C runtime start-up code and the dynamic loader walk .init_array (found through DT_INIT_ARRAY or linker-defined symbols) before main. D3 In a kernel, nobody does — unless the kernel does.


So the kernel's linker script (Listing 3) collects all .init_array.* sections sorted by priority, then plain .init_array, between two boundary symbols, and kmain calls each pointer before using any global (Listing 4, lines 38–43). D6 The run shows the chain working: the map places kmain.o:(.init_array) (4 bytes) at 0x10108c between __init_array_start 0x10108c and __init_array_end 0x101090; readelf -x shows its contents 60041000, which read little-endian is 0x00100460, the address nm gives for _GLOBAL__sub_I_kmain.cpp; the kernel prints "init_array entries: 1", "[init] Log constructor ran", "g_log.lines = 1 (constructed)" and one __cxa_atexit registration. R6




Older toolchains used a section named .ctors for the same purpose, with a different order and sometimes sentinel values; linker scripts copied from old projects often still collect only .ctors. D3 Clang 18 emitted .init_array here (R6). A script that does not mention .init_array does not make the linker fail: the section becomes an orphan, placed by default rules — and is never called. That is the forensic lab.


Not verified — check before relying on this
From memory, not checked in this build: the exact C++ rules for when dynamic initialisation of non-local variables happens (the standard's "Dynamic initialization of non-block variables"); the list of headers the standard requires of a freestanding implementation; the Itanium C++ ABI signatures and meanings of __cxa_atexit(void (*)(void*), void*, void*), __dso_handle, __cxa_pure_virtual and the guard functions; and the history and ordering differences between .ctors and .init_array. The lab shows only what these two compilers emitted and what the linker reported (R3–R7). Check the C++ working draft (clauses on program start-up and freestanding implementations), the Itanium C++ ABI ("DSO object destruction", "Guard variables") and the gABI ("Initialization and termination functions").



Function-local statics and guards


A function-local static whose initial value is a constant (static int counter = 100;) needs no code: it sits in .data. One with a dynamic initialiser (static Calibration c;, whose constructor calls readSensor()) is constructed the first time control passes through it, and C++ requires that to be safe if two threads arrive at once. D1 Clang implemented that with a guard variable and calls to __cxa_guard_acquire and __cxa_guard_release; with -fno-threadsafe-statics the guard remains but the calls disappear. R4 A single-core kernel during early boot can use -fno-threadsafe-statics; a multi-core kernel must either provide guard functions built on its own locks or avoid such statics. Choose deliberately and write the choice in the design notes.





What remains usable


Freestanding C++ keeps most of the language: classes, templates, constexpr, lambdas, references, namespaces, virtual functions (the lab's Uart virtual call works), RAII for locks and resources, and static_assert for layouts. R6 What goes: exceptions (use error codes, as the F2-44 reader does), RTTI, the hosted library (std::vector, std::string, iostreams), and anything that silently allocates. Some header-only parts of the library can be brought back later with a freestanding-capable library build; this course does not depend on that.



How the hardware actually does it


None of this is visible to the processor: a constructor is a function call, new is a function call, a vtable is data. What the hardware provides at the start is a state set by the loader — for QEMU's Multiboot loader, 32-bit protected mode with paging off — and the kernel's first instructions (boot.S) must create the rest of the C++ environment from it: a stack (RSP/ESP pointing into a reserved .bss area), zeroed .bss (C++ promises zero for statics without initialisers), then kmain, which calls the constructors. D7 R6 On x86-64 under UEFI (milestone A1), the firmware provides a stack and 64-bit mode, but still no C++ runtime; the same .init_array loop is needed in the loader.


Watch out
Untested on hardware. The kernels in this chapter ran only in QEMU 8.2.2 (TCG) with its Multiboot loader (R6, R7). The P1 build ran in the cloud build container; "the second machine" of P1 was a second folder on the same machine (R1), which proves a clean clone builds but not that a different installation does. Where the analogy breaks


    

  • A cold oven is obvious. An unconstructed global is not: it is zero (it lives in .bss) and many zeros look plausible. The forensic kernel did everything else correctly. R7
    • 

  • Crossing out a recipe is visible. Turning off exceptions changes behaviour at a distance: library code written for exceptions may call abort-like paths instead of throwing.
    • 

  • The stall can buy bowls on the way. A kernel cannot link a library function "just this once" — every symbol must be in its own image (R5).
    • 




Common mistakes and debugging


    

  • Symptom: a global object has zero fields; its constructor's side effects never happen. Cause: .init_array not collected between the boundaries, or the loop not called (forensic lab). How to find it: map file: where is .init_array? nm: are the boundaries equal? Fix: collect .init_array.* and .init_array; call the loop first in kmain.
    • 

  • Symptom: "undefined symbol: memcpy" in a kernel that never calls memcpy. Cause: the compiler generated the call for a struct copy. Fix: provide it (Listing 2).
    • 

  • Symptom: "undefined symbol: __cxa_guard_acquire". Cause: a function-local static with a dynamic initialiser. Fix: provide guard functions or -fno-threadsafe-statics (single core), or make the initialiser constexpr (R4).
    • 

  • Symptom: "'cstdint' file not found". Cause: no C++ library for the freestanding target. Fix: <stdint.h> and friends, or install a freestanding C++ library.
    • 

  • Symptom: unexplained triple fault early in boot. Cause: a constructor ran before the stack or .bss was ready, or used a device not yet initialised. Fix: constructors that only set fields; explicit init() calls for anything that touches hardware.
    •

Observation. "init_array entries: 0", "g_log.lines = 0 (NOT constructed)", no "[init]" line, exit 35. nm: __init_array_start = __init_array_end = 0x00101090. _GLOBAL__sub_I_kmain.cpp still exists at 0x00100460.


Map. kmain.o:(.init_array) (4 bytes) is in an output section .init_array at 0x10108c that link_old.ld never created — an orphan placed by the linker's default rules right after .rodata. The script's own output section .ctors at 0x101090 is empty, and the boundary symbols are inside it. The pointer exists, but outside [start, end).


Disassembly. mov $0x101090,%esi loads __init_array_start; cmp $0x101090,%esi compares with __init_array_end; they are equal, so je skips straight to the return. The call *(%esi) at 0x100060 is never reached.


Root cause. The copied script collects only .ctors, while this compiler emits constructor pointers in .init_array; the boundary symbols therefore enclose an empty range, and the kernel's loop calls nothing.


Fix and verification. Collect .init_array.* (sorted by priority) and .init_array between the boundaries, as Listing 3 does (keeping .ctors too if old objects are linked). Step kernel: entries 1, constructor ran, exit 33.


Prevention. (1) A build check that fails when __init_array_end − __init_array_start is 0 while any input object has an .init_array section (or simply when the kernel has globals with constructors). (2) --orphan-handling=error (or warn) so that any section the script does not place stops the link. (3) An early boot self-test like the lab's exit code.


How the evidence was made. run.sh links the same three objects with forensic/link_old.ld and boots the result.
