Story hook

Above the pass hangs the order board. When a cook writes "10" in the box labelled FACTORIAL, a helper behind the wall takes the number, works on it, and writes the answer back into the same box. A small lamp labelled BUSY glows while the helper works. The board is not a notebook: writing to it starts something, and reading it can give a different answer every time.

Joon, in a hurry, stops looking at the board. He writes 10, glances once at the lamp, and then reads the answer from his own memory of what he just wrote: 10. The kitchen serves "factorial of 10 is 10". In this chapter you will see the compiler do exactly what Joon did — on a real (emulated) PCI device — and why one keyword, volatile, makes it look at the board every time.

What you will be able to do

  • Explain memory-mapped I/O: device registers that appear at physical addresses and have side effects.
  • State what volatile guarantees (each access happens, in program order, as written) and what it does not (atomicity, ordering against other cores or devices, caching).
  • Write a typed register wrapper with a fixed width, offset and access direction, checked at compile time.
  • Find a PCI device and its memory BAR, and drive its registers from a freestanding kernel.
  • Diagnose a driver that "works at -O0 only" from its disassembly.
Jargon box
Memory-mapped I/O (MMIO)
Simple words: talking to a device by reading and writing special memory addresses. Analogy: the order board on the wall. Precise: a device decodes a range of physical addresses; loads and stores to that range become device register reads and writes instead of RAM accesses. D3 R2
Device register
Simple words: a small storage place inside a device that software reads or writes to control it. Analogy: one box on the board. Precise: a location at a fixed offset from the device's base address, with a defined width, access type (read-only, write-only, read-write) and meaning per bit, given by the device's documentation. D4
Side effect (of a register access)
Simple words: something that happens in the device just because you read or wrote a register. Analogy: writing a number in the box makes the helper start working. Precise: a state change caused by the access itself — starting an operation, clearing a status bit on read, popping a FIFO — which is why such accesses must not be removed, merged, duplicated or reordered. D1 R4
volatile (C++)
Simple words: a keyword that tells the compiler "every access to this object matters, do each one exactly as written". Analogy: the rule "always look at the board, never at your own memory of it". Precise: accesses through volatile glvalues are side effects in the abstract machine; the compiler must perform them, and in program order relative to each other, but volatile gives no atomicity and no ordering with respect to other threads, cores or bus masters. D1 R3
BAR (base address register)
Simple words: a field in a PCI device's configuration that says where its registers are. Analogy: the note telling you where on which wall the board hangs. Precise: one of up to six 32-bit configuration registers (from offset 0x10) holding the base of a memory or I/O region; the low bits describe the region type and are masked off to obtain the address. D2 R1

Layer 1 — the kid explanation

Some memory addresses are not memory at all: they are switches and displays inside a device. Writing there tells the device to do something; reading there asks it what is happening now. A compiler normally assumes memory only changes when the program changes it, so it skips "pointless" reads and writes. For device addresses that is wrong, so we mark them volatile: "do every read and write I wrote, exactly as written".

Layer 2 — the student explanation

What the compiler may do with ordinary memory

C++ compilers optimise under the "as-if" rule: they may change the program in any way that does not change its observable behaviour, and ordinary memory accesses are not observable behaviour by themselves. D1 The lab compiles a few tiny functions and shows what that means. writeTwicePlain (*r = 1; *r = 2;) became a single movl $0x2,(%rdi): the first store was dead. pollPlain (while (*status & 1) {} return *status;) became one load and a return: a loop that reads unchanging memory either never runs or never ends, and the compiler may assume a loop without side effects terminates, so it deleted it. R3 With volatile, writeTwiceVolatile keeps both stores and pollVolatile keeps a real loop: load, test bit 0, jump back. R3




A typed register wrapper


Scattering *(volatile uint32_t*)(base + 0x20) through a driver invites three mistakes: the wrong width, the wrong offset, and writing a read-only register. Listing 1, Reg<T, Offset, Access>, puts all three into the type: the width is T (1, 2 or 4 bytes only), the offset is a template constant that must be naturally aligned, and read/write refuse to compile for write-only/read-only registers. Every access goes through a volatile pointer of exactly that width. Listing 2 names the edu registers with it, so the driver reads edu::Status::read(base) instead of a magic number.



Finding the device


The lab starts QEMU with -device edu, a small PCI device QEMU provides for teaching. QEMU's own monitor reports it at bus 0, device 4, function 0, as "PCI device 1234:11e8", with "BAR0: 32 bit memory at 0xfea00000". R1 The kernel finds the same thing itself: it reads configuration dword 0 of each device on bus 0 through I/O ports 0xCF8 (address) and 0xCFC (data) until it sees 0x11e81234 (device ID in the high half, vendor ID in the low half), then reads BAR0 at configuration offset 0x10: 0xfea00000. R2 Since the kernel runs with paging off (F2-46), that physical address can be used directly as a pointer.

Layer 3 — the engineer's depth


Back at the board: volatile is the rule "always look", but it says nothing about how fast the helper is, whether two cooks look at once, or whether a waiter's copy of the board is up to date. Each of those needs something else.


What volatile guarantees, precisely


In C++, reading or modifying an object through a volatile glvalue is a side effect, and the observable behaviour of a program includes accesses to volatile objects, which are evaluated strictly according to the rules of the abstract machine. D1 In practice that gives a driver four properties: no access is removed, none is added, volatile accesses are not reordered with respect to each other, and the access uses the type's width when the hardware can do so in one instruction (the standard does not literally promise a single instruction; compilers for x86 and Arm do this for aligned 8-, 16- and 32-bit types, as R3 shows). R3 It does not give: atomicity of read-modify-write sequences (reg |= 1 is a read and a separate write), ordering of non-volatile accesses around it, ordering as seen by other cores or by DMA-capable devices, or any control over processor caches and write buffers. D1 D5


Ordering beyond the compiler


Two layers can still reorder accesses after the compiler has emitted them correctly: the processor and the memory system. On x86, MMIO ranges are normally mapped uncacheable (by firmware-set memory-type registers and page attributes), and uncached accesses are performed in program order; on Arm, device memory types give similar guarantees for accesses to the same device, but ordering between normal memory (a DMA buffer) and a device register needs explicit barriers (dmb/dsb). D3 D5 Linux drivers therefore never use raw volatile pointers: they use accessor functions (readl, writel and relaxed variants) that combine a volatile access with the barriers each architecture needs. D6 This lab's kernel runs on one emulated core, with no DMA and paging off, so volatile alone is enough here — and the header says so in its first comment.

Bit-fields and read-modify-write


Registers are often described as bit-fields, and C++ bit-fields look like a natural fit. The lab compares c->mode = 5 on a volatile bit-field struct with an explicit mask: GCC produced identical x86 code for both — one 32-bit load, and $0xfffffff1, or $0xa, one 32-bit store — and for AArch64 a 32-bit ldr, a bfi bit-field insert and a 32-bit str. R3 But the layout of bit-fields (bit order, which unit is accessed) is implementation-defined, and some compilers on some targets access a smaller unit than the register's width, which devices may reject. D1 The safe rule for drivers: read the whole register into an integer, change bits with masks, write the whole register back — as setModeMask does — and remember that this sequence is not atomic: if an interrupt handler also modifies the register, protect the sequence with a lock or with interrupts disabled (F2-49's cli).



Polling and timing


The driver writes 10 to the factorial register and then polls the status register while bit 0 ("computing") is set. In the recorded run the loop body ran zero times — "status polls while computing: none (already done)" — because QEMU completed the computation before the first status read; on another run, another machine or real hardware the count can differ, which is why the kernel prints only "at least one" or "none", not a number. R2 A real driver also needs a timeout on every poll loop, so that a dead device produces an error message instead of a hang.





How the hardware actually does it


On a PC, the processor's physical address space is shared between RAM and devices. The chipset routes each physical address: ordinary addresses go to the memory controller, and addresses inside a PCI device's BAR window are sent over PCI (or PCI Express) to that device, which answers loads and accepts stores as register accesses. D2 D3 Firmware assigns those windows at boot by writing BARs; 0xfea00000, just below 4 GiB, is where QEMU's firmware put edu's 1 MiB window in this machine ([0xfeafffff] is its last address). R1 Because the device itself decides what a read returns, two reads of the same address can legitimately differ (status bits), a write can be invisible to a later read (write-only command registers), and a read can change state (clear-on-read flags). D4 x86 also has the separate I/O-port space used for PCI configuration here; MMIO is the normal path for modern devices.


Watch out
Untested on hardware. Every run in this chapter used QEMU 8.2.2's emulated edu device, which exists only in QEMU (R1, R2, R4, R5). On a physical PC there is no edu device, the BAR addresses differ, and caches, write buffers and real bus timing come into play; the polling observation in particular is timing-dependent.

Where the analogy breaks


    

  • A cook knows the board is special. Nothing in an address tells the compiler it is a device; only the type (volatile) does (R3).
    • 

  • Looking at the board is instant. A device read can be slow, can have its own side effects, and can be reordered by the processor relative to normal memory unless the mapping or barriers prevent it (D5).
    • 

  • "Always look" is not "look together". volatile does not coordinate two cooks (cores) reading and writing the same box; that needs locks or atomics.
    • 




Safety
On real hardware, a wrong MMIO write can reconfigure a device that controls storage, power or displays. Read the device's documentation for every register you write; never write to unknown offsets "to see what happens"; and test drivers first against emulated devices, as this lab does.



Common mistakes and debugging


    

  • Symptom: a driver works at -O0 and returns stale values or hangs at -O2. Cause: plain pointers to device registers (forensic lab). How to find it: disassemble; count the loads and stores to the register block. Fix: volatile accessors for every register.
    • 

  • Symptom: a register "ignores" writes or a device reports an error after a bit-field assignment. Cause: the compiler accessed a narrower unit than the register. Fix: whole-register reads and writes with masks.
    • 

  • Symptom: the device sees the "go" command before the buffer contents (on Arm, or with write-combining). Cause: volatile does not order normal memory against MMIO in hardware. Fix: the architecture's barrier between them.
    • 

  • Symptom: rare lost updates to a control register. Cause: a read-modify-write interrupted by a handler that changes the same register. Fix: lock or disable interrupts around it.
    • 

  • Symptom: the kernel hangs forever in a poll. Cause: dead device or wrong bit. Fix: a timeout and an error message.
    • 

  • Symptom: page fault or garbage reading a BAR address in a paging kernel. Cause: the physical MMIO range is not mapped, or mapped cacheable. Fix: map it uncacheable in the page tables (track B).
    •

Summary


    

  • MMIO registers are physical addresses decoded by a device; accesses have side effects and values can change on their own.
    • 

  • Without volatile, the compiler removed a dead store, deleted a poll loop and printed the value it had written instead of the device's result.
    • 

  • volatile keeps every access, in order, at its width; it does not make read-modify-write atomic or order accesses against other cores, DMA or caches.
    • 

  • Wrap registers in types that fix width, offset and direction; use masks instead of bit-fields.
    • 

  • The lab's kernel found edu by PCI configuration reads and computed factorial(10) = 3628800 through volatile accesses.

Forensic lab answer key


Observation. The only device access in the excerpt is movl $0xa,0x8(%eax) (store 10 to the factorial register). The printed value comes from push $0xa before call printDec: a constant.


Hypotheses. (a) is ruled out: the same device, same QEMU, gives 3628800 at -O0 and through the volatile wrappers. (b) is ruled out: a slow device would make a correct poll wait, not produce 10. (c) is confirmed: there is no load from the register block after the store.


Root cause. With a plain uint32_t*, the compiler may assume memory changes only through the program. It concluded that regs[2] still holds the 10 it just stored, and that the status loop reads memory nothing modifies — a side-effect-free loop it may assume terminates, so it removed it (the same transformation as pollPlain, R3). The missing property is volatile's "every access is performed".


Why -O0 worked. Without optimisation the compiler emits every load and store as written, so the program accidentally behaved as if the pointer were volatile.


Fix. volatile uint32_t*, or better, the Reg<> wrappers of Listing 1 (the main kernel, R2).


Prevention. Never form plain pointers to MMIO; make the register types the only way to reach a device; test drivers at the shipped optimisation level; a code-review rule or a static check that flags reinterpret_cast of BAR values to non-volatile pointers.


How the evidence was made. run.sh builds kmain_fast.cpp at -O2 and -O0 with the same boot code and runs both in QEMU with -device edu.
