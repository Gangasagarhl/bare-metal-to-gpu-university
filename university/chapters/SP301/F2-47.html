Story hook

In Mr Haddad's kitchen, cooks hand work to each other across the pass. The rules are written on the wall: the first ingredient goes in tray 1, the second in tray 2, up to six trays; anything more goes on the shelf below, in order. The finished dish comes back in tray A. Some knives belong to the cook who asks for help — the helper may use them but must put them back exactly as found. Others are shared — the helper may leave them anywhere, so a cook who needs his knife after asking for help must put it away safely first.

A visiting chef, used to the hotel's rules, sets his ingredients out in trays 3 to 6 and on the shelf at a different height. Nothing works, though both kitchens make the same dishes. And a new helper, Rafael, borrows the head cook's favourite knife for a quick job and does not put it back; for weeks nothing happens, because the head cook happened not to use that knife after asking for help — until the week he did. That last story is this chapter's forensic lab, and it ends with a crash at address 1.

What you will be able to do

  • State where arguments, return values and the return address go in the System V AMD64, Microsoft x64 and AArch64 (AAPCS64) conventions, and check it in disassembly.
  • Explain caller-saved versus callee-saved registers, stack alignment at calls, shadow space and the red zone.
  • Predict how a struct is passed or returned (registers or hidden pointer) and why the answer depends on the data model.
  • Write an assembly function that C++ can call, and find an ABI violation from a crash and the disassembly.
  • Recognise the C++ ABI's parts in object files: mangled names, vtables, typeinfo, COMDAT groups.
Jargon box
ABI (application binary interface)
Simple words: the rules that let separately compiled machine code work together. Analogy: the rules written on the kitchen wall. Precise: data type sizes and alignment, calling convention, stack layout, object file format details, and for C++ also name mangling, class layout, vtables and exception handling; defined per platform (for example the System V AMD64 psABI with the Itanium C++ ABI on Linux). D2 D5
Calling convention (ABI)
Simple words: the part of the ABI about calls: where arguments go, where the result comes back, who saves which registers. Analogy: which tray holds which ingredient. Precise: the agreement between caller and callee on argument registers and stack slots, return registers, preserved registers, stack alignment and cleanup. D2 R1
Callee-saved register
Simple words: a register a called function must give back unchanged. Analogy: the knife you must put back. Precise: a register the convention requires to have the same value on return as on entry; a callee that uses it saves and restores it (for System V AMD64: RBX, RBP, R12–R15, plus RSP). Others are caller-saved (volatile): the caller must assume a call destroys them. D2 R8
Stack frame
Simple words: the part of the stack a function uses while it runs. Analogy: the cook's own corner of the shelf. Precise: the region holding a function's return address, saved registers, locals and outgoing stack arguments; delimited by the stack pointer (and optionally a frame pointer). D2
Red zone
Simple words: space just below the stack pointer that a function may use without moving the stack pointer. Analogy: the shelf space right under your hand that nobody else touches while you work. Precise: in the System V AMD64 ABI, 128 bytes below RSP that signal and interrupt handlers must not modify; leaf functions use it for locals. Kernels compile with -mno-red-zone because hardware interrupts push onto the current stack. D2 R4
Shadow space
Simple words: 32 empty bytes a Windows caller leaves on the stack for the callee. Analogy: four empty spots on the shelf reserved for the helper to put tray contents down. Precise: in the Microsoft x64 convention, the caller allocates 32 bytes above the return address where the callee may spill RCX, RDX, R8, R9; stack arguments start after it. D3 R2
Vtable
Simple words: a table of function addresses that makes virtual calls work. Analogy: a card on each dish saying which cook prepares its sauce. Precise: in the Itanium C++ ABI, a per-class array (in read-only-after-relocation data) with an offset-to-top, a typeinfo pointer and then virtual function pointers; each object with virtual functions starts with a pointer into it. D5 R6

Layer 1 — the kid explanation

When one piece of code calls another, they must agree where to put the inputs and where to find the answer. Computers have a few fast boxes called registers, and a stack in memory. A calling convention is the written agreement: "first input in this box, second in that one, extra ones on the stack, answer in this box; these boxes you must give back unchanged". Different systems wrote different agreements, so code built for one cannot simply call code built for another.

Layer 2 — the student explanation

System V AMD64, read from the disassembly

The lab compiles five small functions with g++ -O2 and prints their disassembly (R1). Read each one as evidence for one rule:

  • Integer arguments. sum8 adds %rsi, %rdx, %rcx, %r8, %r9 into %rdi, then adds 0x8(%rsp) and 0x10(%rsp): arguments 1–6 arrive in RDI, RSI, RDX, RCX, R8, R9; 7 and 8 on the stack just above the return address. The result is in RAX. R1 D2
  • Small structs. pairSum(Pair p) with Pair = two longs (16 bytes) compiles to lea (%rdi,%rsi,1),%rax: the struct was split into two registers. R1
  • Large structs returned. makeBig(long) returns a 32-byte struct: the code stores four values at (%rdi)…0x18(%rdi) and returns %rdi in RAX, while seed arrives in %rsi. The caller passed a hidden pointer to the result as an invisible first argument. R1 D2
  • Floating point. mix(int a, double b, int c, double d) reads a from %edi, c from %esi, b from %xmm0 and d from %xmm1: integer and floating-point arguments are numbered separately. The result returns in XMM0. R1
  • Stack alignment. callsOut does sub $0x8,%rsp before its call and adds it back after. On entry RSP is 8 bytes past a 16-byte boundary (the call pushed the return address); subtracting 8 restores the 16-byte alignment that the convention requires at every call instruction. R1 D2



Microsoft x64: same source, different rules


Compiled with clang++ --target=x86_64-pc-windows-msvc, the same functions look different (R2). sum8 uses RCX, RDX, R8, R9 for the first four arguments and reads the other four at 0x28, 0x30, 0x38, 0x40 from RSP: 8 bytes of return address plus 32 bytes of shadow space come first. callsOut subtracts 0x28: 32 bytes of shadow space for its callee plus 8 for alignment. R2 D3


The bigger surprise is the data model. On 64-bit Windows, long is 32 bits (the LLP64 model), while on Linux it is 64 bits (LP64). D3 The disassembly shows it: addl on 32-bit registers in sum8; Pair becomes 8 bytes and travels in one register (pairSum splits RCX with a shift by 32); Big becomes 16 bytes, yet is still returned through a hidden pointer in RCX, with seed in EDX. R2 If you share a struct between a UEFI application and a Linux tool, use fixed-width types (int64_t), never long.





AArch64 (AAPCS64)


On AArch64 the eight arguments of sum8 arrive in X0–X7 and the result returns in X0; makeBig's hidden result pointer is in the dedicated register X8 (stp x0, x3, [x8]) rather than in the first argument register; and the non-leaf callsOut saves the frame pointer X29 and the link register X30 (which holds the return address, because bl does not push anything) with stp x29, x30, [sp, #-16]!. R3 D4





Layer 3 — the engineer's depth


The kitchen's wall rules are a contract with two sides, and every violation looks like someone else's bug. Below, the parts of the contract that systems code touches most.


Who saves what


A convention divides registers into two sets. Caller-saved registers (System V: RAX, RCX, RDX, RSI, RDI, R8–R11, and all XMM registers) may be destroyed by any call, so a caller that needs a value across a call keeps it in a callee-saved register or on its stack. Callee-saved registers (System V: RBX, RBP, R12–R15) must be preserved by any function that uses them. D2 Microsoft x64 also counts RDI, RSI and XMM6–XMM15 as callee-saved; AAPCS64 makes X19–X28 callee-saved. D3 D4 The forensic lab shows the sharpest consequence: total, compiled with -O2, keeps its array pointer in RBX across calls to scale, because RBX is callee-saved. A hand-written scale overwrites RBX. At -O0 the compiler kept everything on the stack, so the bug hid (R7); at -O2 it crashed (R8).


Not verified — check before relying on this
The complete caller-saved and callee-saved register lists for System V AMD64, Microsoft x64 and AAPCS64, the 16-byte stack alignment rule at calls, the 128-byte red zone size, and the Windows rule that structs of 1, 2, 4 or 8 bytes travel in a register while others go by reference are written from memory of the three ABI documents. The lab's disassembly confirms the argument registers, the stack-argument offsets, the hidden result pointers, the shadow space and alignment adjustments shown above (R1–R3), and that RBX must be preserved (R8, R9) — not the full lists. Check each list in the System V AMD64 psABI ("Registers" table), Microsoft's "x64 calling convention" pages and the AAPCS64 ("General-purpose registers").



The red zone and why kernels turn it off


A leaf function (one that calls nothing) in System V may keep locals below RSP without moving RSP. The lab's leafWithArray does exactly that: its eight-element array is written at -0x28(%rsp,%rdx,4), below the stack pointer, with no sub at all. With -mno-red-zone the same function starts with sub $0x28,%rsp and uses positive offsets. R4 In user programs this is safe because the operating system delivers signals on a stack location below the red zone. In a kernel, an interrupt arriving while that leaf runs makes the processor push its interrupt frame at RSP — right over the red zone — corrupting the locals without any visible cause. D1 D2 That is why every x86-64 kernel in this curriculum, and the UEFI application of F2-45, is compiled with -mno-red-zone.

Declared in C++ as extern "C" long sum6(long, long, long, long, long, long); (no mangling), it is called normally and returns 654,321 — under AddressSanitizer and UBSan. R5 Assembly is where the convention stops being the compiler's job and becomes yours; F2-49 shows how inline assembly lets the compiler keep that job.





The C++ part of the ABI


Calling conventions are not enough for C++. Linux compilers follow the Itanium C++ ABI for name mangling, class layout, vtables, typeinfo and exception handling. D5 The lab's vtable.cpp defines a class Thermometer with virtual functions; its object file contains: _ZTV11Thermometer (the vtable, nm type V, a weak object), _ZTI…/_ZTS… (typeinfo and its name string, used by RTTI and exceptions), three destructor symbols (D0, D1 and D2: in the Itanium ABI the deleting, complete-object and base-object destructors), and undefined references to the C++ runtime's __cxxabiv1::__class_type_info vtables and to operator new/delete (_Znwm, _ZdlPvm). R6 The vtable lives in its own COMDAT group section (flag G) and has five 64-bit relocations: typeinfo, the two destructors, read, unit — at offset 8, so the vtable begins with a 0 offset-to-top, and objects point 16 bytes in (the + c addend in makeThermometer's PC32 relocation is 0x10 − 4). R6 D5 The same class compiled for Windows has different names entirely (?read@Thermometer@@UEBAHXZ): C++ object files from MSVC-ABI and Itanium-ABI compilers cannot be linked together. R6 These runtime references are exactly what a freestanding kernel must provide or avoid (F2-48).





How the hardware actually does it


The processor knows almost nothing of all this. On x86-64, call pushes the return address and jumps; ret pops and jumps; push/pop move RSP by 8. D1 Which register holds which argument is purely a software agreement. There are two places where the hardware does care. First, some SSE instructions that access memory require 16-byte-aligned addresses (for example movaps); compilers use them for stack data because the ABI promises alignment, so a misaligned stack can turn into a general-protection fault far from its cause. D1 Second, on an interrupt or exception the processor itself pushes a frame onto the stack (in 64-bit mode: SS, RSP, RFLAGS, CS, RIP, and sometimes an error code), which is what destroys a red zone in kernel code. D1 On AArch64, bl writes the return address into X30 instead of memory, which is why non-leaf functions save X30 themselves (R3). D4

Where the analogy breaks


    

  • Cooks would notice a missing knife at once. A clobbered callee-saved register is noticed only when the caller next uses it, possibly much later and in another function, and only in some builds (R7 versus R8).
    • 

  • The kitchen has one set of rules. One machine can run several conventions at once: Linux and UEFI code on the same x86-64 processor, or __attribute__((ms_abi)) functions inside a Linux program. D7
    • 

  • Trays have fixed sizes; types do not. long changes size between Linux and Windows on the same processor (R2).
    • 




Common mistakes and debugging


    

  • Symptom: crash only at -O2, in the caller of an assembly function, at a strange address. Cause: the assembly clobbers a callee-saved register (forensic lab). How to find it: gdb: which register holds the bad address? Is it callee-saved? Read the assembly for writes to it. Fix: save/restore, or use caller-saved registers.
    • 

  • Symptom: a movaps general-protection fault, or crashes inside printf called from your assembly. Cause: RSP not 16-byte aligned at the call. How to find it: check RSP modulo 16 before each call in your code. Fix: adjust by 8 as compilers do.
    • 

  • Symptom: UEFI calls your function and it receives garbage. Cause: compiled with System V for an ELF target. Fix: a Windows target (F2-45) or __attribute__((ms_abi)) on the entry point.
    • 

  • Symptom: rare corruption of locals in kernel leaf functions, only under interrupts. Cause: red zone. Fix: -mno-red-zone for all kernel code.
    • 

  • Symptom: structs shared between a Windows-built tool and a Linux-built tool disagree. Cause: long and alignment differ. Fix: fixed-width types and static_assert(sizeof …) on both sides.
    •

Summary


    

  • A calling convention fixes argument and return registers, stack argument slots, preserved registers and stack alignment.
    • 

  • System V AMD64: RDI, RSI, RDX, RCX, R8, R9, then the stack; XMM0–7 for floating point; result in RAX/XMM0; 16-byte alignment at calls; 128-byte red zone.
    • 

  • Microsoft x64 (Windows, UEFI): RCX, RDX, R8, R9; 32 bytes of shadow space; long is 32 bits.
    • 

  • AAPCS64: X0–X7, hidden result pointer in X8, return address in X30.
    • 

  • Callee-saved registers must be restored; violating that crashes the caller, often only in optimised builds.
    • 

  • Kernels compile with -mno-red-zone; C++ classes bring vtables, typeinfo and runtime references defined by the Itanium C++ ABI.

Forensic lab answer key


Observation. SIGSEGV at total+24, the instruction mov (%rbx),%rdi; RBX = 1.


Hypotheses. (a) is ruled out: the same total works with the fixed scale and at -O0. (b) cannot cause a load through RBX; a wrong return value would give a wrong total, not a crash. (c) is confirmed. In total, RBX is the pointer into v: the loop is mov (%rbx),%rdi (load v[i]), add $0x8,%rbx, call scale, add %rax,%rbp, cmp %r12,%rbx, jne back to the load, and RBX is never reloaded after the call because the compiler may assume a callee-saved register survives it. scale begins with mov %rdi,%rbx, so after the first call RBX = v[0] = 1; 1 is not equal to the end pointer in R12, so the loop continues and loads from address 1. gdb confirms RBX = 1 at that load.


Root cause. scale.S line 7 writes RBX, which is callee-saved in the System V AMD64 convention, without saving and restoring it.


Why -O0 passed. See answer 5: no value lived in RBX across the call.


Fix and verification. scale_fixed.S pushes and pops RBX (or better, uses RCX). Step forensic_fixed: total = 116, also under ASan/UBSan.


Prevention. Test assembly functions in optimised builds; write a test harness that fills all callee-saved registers with known values, calls the function and checks them afterwards; prefer small inline-assembly wrappers (F2-49), where the compiler handles register saving.
