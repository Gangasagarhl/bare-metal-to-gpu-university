Story hook

Analogy

Chef Amara's restaurant has a counting job: a sack with millions of beans of 256 kinds, and the question "how many of each kind?". In her own kitchen she solves it with four cooks. Each cook takes a quarter of the sack and keeps a personal tally sheet; at the end Amara adds the four sheets. When she once tried a single shared tally board with one key, the cooks spent the evening queuing for the key.

Today Amara visits the great kitchen hall. Thousands of helpers stand in rows, and each row moves together, step by step, following one recipe card. Amara gives the hall her kitchen's instructions word for word: "take the key, write on the board, give the key back". The first helper of a row gets the key and stops to wait for her row, because a row only moves on together. The rest of the row keeps reaching for a key that never comes back. The row stands there forever.

The hall's head of service smiles and changes three things: each table of rows gets its own tally sheet, neighbouring helpers take neighbouring beans, and nobody holds a key while waiting for their row. Same job, same counting rules, a different way to organise the workers. This chapter is about those three changes, and about everything Amara does not have to change.

What you will be able to do

  • Explain which concurrency ideas from SP203 carry over unchanged to GPU code (data races, synchronization, atomics, a memory model, Amdahl's reasoning about serial parts) and show each one in a real run.
  • Contrast CPU threads (few, heavy, scheduled by the operating system) with GPU threads (many, light, created by the launch and scheduled by hardware in warps of 32 or wavefronts of 64), using measured costs from this build.
  • Write the same histogram with std::thread and with CUDA, choosing the partition (chunked or interleaved) and the synchronization that fit each world.
  • Predict the cost of divergence and of a group's memory access pattern with a small model, and read the machine code that implements divergence and reconvergence.
  • Diagnose the three bridge traps: a CPU-style spin lock inside a warp, a single GPU thread expected to be fast, and ignored divergence.
Jargon box
Thread (CPU) and thread (GPU)
Simple words: two different things with the same name: a CPU thread is a flow of work the operating system manages; a GPU thread is one of thousands of tiny workers a kernel launch creates. Analogy: one of the few cooks in Amara's kitchen versus one helper in the great hall. Precise: a CPU thread has its own registers, program counter and stack in its process's address space and is scheduled onto cores by the OS (F2-34) D8; a GPU thread runs the kernel's code with its own built-in indices, is created by the launch and executed as a lane of a warp or wavefront (F6-01, F1-57). D1
Warp / wavefront
Simple words: a fixed-size group of GPU threads that share one stream of instructions. Analogy: a row of helpers that move together, step by step. Precise: the group the hardware schedules and executes together: 32 threads in an NVIDIA warp; 64 work-items in an AMD wavefront on CDNA (RDNA supports 32 and 64). Vendor terms: NVIDIA says warp, AMD says wavefront. D1 D3 X1
Divergence
Simple words: some lanes of a group need one path of an if and others need the other path, so the group walks both. Analogy: if some helpers in a row must do something different, the others in the row wait. Precise: lanes of one warp or wavefront evaluate a branch differently; the paths execute one after the other with complementary masks and the lanes reconverge afterwards (F1-57). D1 D4
Reconvergence point
Simple words: the place in the program where the lanes that split at an if or a loop wait for each other and continue together. Analogy: the spot where a row lines up again before its next step. Precise: a program point after a divergent branch at which the hardware resumes executing the group with the combined mask; in the SASS of this build it is set by SSY (target sm_60) or BSSY (sm_80) and reached at SYNC or BSYNC. R9 R11 D11
Independent thread scheduling
Simple words: newer NVIDIA GPUs can let the lanes of one warp make progress on different paths in turn, instead of strictly as one row. Analogy: helpers of a row may now take separate small steps, although the row still prefers to move together. Precise: NVIDIA's execution model since the Volta generation, in which each thread keeps its own program counter and call stack, so divergent paths of one warp may interleave; it is why warp intrinsics take an explicit participation mask (_sync suffix). D1 (unverified box in Layer 3)
Forward-progress guarantee
Simple words: a promise that a waiting thread will eventually let the thread it waits for run. Analogy: the OS will sooner or later give the cook with the key a turn at the stove. Precise: a property of a scheduler or execution model stating which threads are guaranteed to keep executing while others wait; a lock is safe only if the lock holder is guaranteed to progress while waiters spin. D1 D7
SIMT deadlock (spin lock in a warp)
Simple words: a warp hangs because the lane holding a lock waits for its own warp, and the rest of the warp waits for the lock. Analogy: the helper with the key waits for her row; the row waits for the key. Precise: a deadlock between lanes of one group under lock-step execution: the lock owner has left the spin loop and waits at the reconvergence point, which lies before the unlock, while the other lanes keep spinning; shown by this chapter's model R10 and by the reconvergence instructions in the SASS R9. R9 R10
Chunked and interleaved partitioning
Simple words: two ways to share a long list among workers: each takes one solid block, or each takes every T-th item. Analogy: each cook takes a quarter of the sack, versus helpers standing side by side taking neighbouring beans. Precise: chunked: worker t of T processes indices [n·t/T, n·(t+1)/T); interleaved: indices t, t + T, t + 2T, … On a GPU the interleaved form makes the lanes of a group touch neighbouring addresses in one instruction (coalescing, F6-08); on a CPU the chunked form gives each core one contiguous stream. D2 R12
Context switch and zero-cost switching
Simple words: how a CPU swaps one thread for another (save its registers, load another's), versus how a GPU picks another ready group without saving anything. Analogy: a cook leaves the stove and writes down where she was; in the hall, the next row simply starts its step because every row keeps its own hands. Precise: a context switch is the OS operation that saves the running thread's registers and restores another's (F3-03) D8; on a GPU every resident warp keeps its registers in the register file, so the warp scheduler can issue from a different warp in the next cycle (F1-60). D1

Layer 1 — the kid explanation

In Amara's kitchen there are only a few cooks. Each cook is clever and quick, and each one works alone at her own pace. A manager decides who stands at the stove; when one cook has to stop, the manager writes down exactly where she was, so she can carry on later. That writing down takes a little time, but with few cooks it does not matter.

The great kitchen hall is different. There are thousands of helpers, and they arrive all at once when the order comes in. They stand in rows. A whole row does the same step at the same moment, like a line of dancers. Nobody writes anything down when a row pauses: every helper simply keeps everything in her hands, and another row takes its step while this one waits for ingredients from the far pantry.

Some things do not change at all. If two workers write on the same tally sheet at once, a count gets lost, in the kitchen and in the hall. A tally counter that clicks in one movement fixes that in both places. And the slowest part of the job, the part only one person can do, still decides how fast the whole job can be.

Three habits from the kitchen must stay at the door of the hall. First, never let a helper hold a key while she waits for her row: her row may wait for the key. Second, one helper alone is slow; the hall is fast only when many helpers work. Third, if half a row does something different, the other half stands still and waits. You will see each of these happen in a real program in this chapter.

Layer 2 — the student explanation

This layer goes through the bridge card of guide 6.2 line by line: first what carries over from SP203, then what changes, then the three traps. The running example is one job, a 256-bin histogram of bytes, written twice: with std::thread (Listing 1) and with CUDA (Listing 2). A histogram is the right test because it needs everything at once: many workers, one shared result, and a choice between sharing and privatizing. D4

What carries over

Data races. A data race is two conflicting accesses to one memory location, at least one a write, not ordered by synchronization; in C++ it is undefined behaviour (F2-35). D5 Listing 3 is the CPU version: four threads run ++bins[in[i]] on one plain table. Five runs lost between 380,436 and 695,856 of 4,194,304 increments R3, and ThreadSanitizer named the line, hist_racy.cc:22 R4. Listing 2's histRacy is the same line in a kernel: a load, an add and a store that two GPU threads can interleave exactly as two cooks can. D1 The bug does not change; only the number of threads does.

The need for synchronization. In both worlds you need something that orders one thread's writes before another thread's reads. On the CPU it was join(), a mutex, or an atomic with release and acquire (F2-39). Listing 1 relies on join(): line 92 orders every private table write before the merge. D5 In Listing 2 the same role is played by __syncthreads() between the zeroing, counting and merging phases of histShared, and by the end of the kernel before the host reads the result. D1

Atomics. std::atomic<unsigned long>::fetch_add (Listing 1, line 66) and atomicAdd (Listing 2, lines 33, 39, 49, 53) are the same idea: a read-modify-write that nobody can cut into, the tally counter that clicks in one movement. D5 D1 The same cost lesson carries over too: many clicks on one counter form a queue. Listing 1's sharedAtomic took 100.0 ms with one thread and 372.9 ms with two, against 8.0 ms for the plain serial loop, on uniform input R2. Every thread clicking one shared table is correct and slow in both worlds; privatization (privateMerge, histShared) is the cure in both. D4

The idea of a memory model. SP203 taught that "what another thread sees, and when" is defined by the language's memory model, through happens-before (F2-39). D5 CUDA has a memory model as well: PTX defines a memory consistency model with scopes (a block, the device, the whole system), and CUDA's atomics come in matching scopes (atomicAdd_block, atomicAdd, atomicAdd_system, F6-13). D10 D1 The habit carries over unchanged: reason with ordering rules, never with "it worked when I ran it". Only the vocabulary grows by one word, scope.

Amdahl's reasoning about serial parts. If a fraction p of the time can be spread over N workers, the speedup is at most 1 / ((1 − p) + p/N) (F2-34), whether the workers are cooks or helpers. Listing 1's serial parts are starting the threads and adding the private tables; Listing 2's include copying the bytes to the GPU. The Worked example applies the formula to this build's numbers.

What changes

Few, heavy, OS-scheduled threads become many, light, hardware-scheduled threads. In this build one std::thread start and join cost 63.3 µs on average, and every new thread reserves 8192 KiB of stack by default R2. The operating system decides which thread runs on which core and may pause any thread at any instruction. D8 With 8 threads on 4 CPUs, five runs of privateMerge caused 15 voluntary and 18 involuntary context switches R2. A GPU program does not start threads one by one: the launch histGlobal<<<65536, 256>>> creates 16,777,216 threads in one statement. D1 If starting one cost what a CPU thread costs here, creating them would take 16,777,216 × 63.3 µs ≈ 1,062 s; the GPU model is built so that it does not.

Groups: warps of 32, wavefronts of 64. The hardware executes GPU threads in fixed groups with one instruction stream: warps of 32 threads on NVIDIA GPUs, wavefronts of 64 work-items on AMD CDNA GPUs (RDNA runs wave32 and wave64); consecutive threads of a block form consecutive groups. D1 D3 D9 This build's compilers agree: __AMDGCN_WAVEFRONT_SIZE is 64 for gfx90a and gfx942 and 32 for gfx1030 and gfx1100, and the sm_80 SASS uses 0x20 = 32 for warpSize (F1-57, X1). A CPU thread has no such group: it is its own instruction stream.

Divergence inside a group costs time. When lanes of one group disagree at a branch, the group executes both paths, each with part of the lanes switched off, and reconverges afterwards. D1 D4 A CPU thread only ever pays for its own path. Listing 6 has a typical branch: bytes ≥ 200 need extra work. Listing 7 models its cost: on the scrambled input, 21.9 % of the bytes need the extra path, every group of 32 or 64 contains at least one of them, and the group pays 40.00 model instructions per byte for 13.44 of useful work, a SIMD efficiency of 33.6 %. Sorted input makes every group uniform and the efficiency 100.0 % R12. The machine code of Listing 6 shows the mechanism: BSSY B0, 0x410 before the branch, @P0 BRA 0x400 to skip the expensive path, and BSYNC B0 at 0x400 where the lanes meet again R11.

No OS context switch per GPU thread. Every resident warp keeps its registers in the SM's register file, so when one warp waits for memory, the warp scheduler issues an instruction from another ready warp in the next cycle; nothing is saved or restored (F1-60). D1 The price is fixed: the registers a kernel uses per thread limit how many warps fit (occupancy). The compiler reports it: 10 registers per thread for histGlobal, 12 for histShared, 20 for histChunked and histOneThread R6.

Synchronization is cheap inside a block and expensive or unavailable across the grid. __syncthreads() waits for the threads of one block, all on one SM. D1 There is no mutex, no condition variable and no plain barrier across all blocks of a grid: blocks are not guaranteed to run at the same time, so a home-made grid barrier can deadlock; a grid-wide barrier exists only for cooperative launches (F6-12). D1 The usual "barrier across everyone" is the end of the kernel. This is why histShared merges with atomics instead of waiting for all blocks and letting one thread add the tables, as Listing 1's main thread does.

The memory access pattern of the whole group matters. A CPU core streams through its own contiguous slice. A GPU group issues one load instruction for all its lanes, and the memory system combines neighbouring addresses into few transactions (coalescing, F6-08). D1 D2 So the best partition flips (Figure 2). With the 32-byte segment of the TG-1 teaching model, Listing 7 counts the segments one load touches: interleaved, 1 for a warp of 32 and 2 for a wavefront of 64; chunked with 64 bytes per thread (histChunked), 32 and 64 R12. On the CPU, this build measured no clear winner between the two splits R2; on the GPU the model predicts a large one, still to be measured.

The three traps

Trap 1: a mutex-like spin lock across threads of the same warp. On the CPU, F2-38's spin lock worked: four threads counted 400000 of 400000 X2, because the operating system eventually runs the thread that holds the lock. Listing 4 carries the same lock to the GPU: spin on atomicCAS until the lock is ours, increment, unlock. The machine code shows why that can hang a warp. For target sm_60, the compiler sets a reconvergence point with SSY 0x78, loops on ATOM.E.CAS and @P0 BRA 0x40, and places SYNC at 0x70: the lanes that leave the loop wait there for the rest of their warp. The unlock, ATOM.E.EXCH, is at 0xb8, after that point R9. Listing 5 models exactly this structure: with lock-step execution, one lane wins the lock and waits at the reconvergence point; the other 31 keep spinning; after 10,000 rounds there is no progress R10. Figure 3 draws it.

The model also shows the fix and the subtlety. Program B puts the increment and the unlock inside the loop, done by the lane that won; under lock-step execution it finishes in 32 rounds with 496 failed CAS attempts R10. Program A finishes under a scheduler that gives every lane its own program counter (65 rounds, 992 failed CAS); NVIDIA documents such independent thread scheduling for GPUs since the Volta generation, which is why Listing 4 "may" hang rather than "will" (unverified box in Layer 3). D1 Either way it is slow, and the best fix is no lock at all: countAtomic, one atomicAdd per thread, or a privatized table.

Trap 2: expecting one GPU thread to be fast. Listing 2's histOneThread<<<1, 1>>> is Listing 1's serial loop moved into a kernel: correct, and running in one lane of one warp on one SM while every other lane and SM idles. A GPU is designed for throughput, not for the latency of one thread; it hides memory latency by switching between many warps, and with one warp there is nothing to switch to (F1-55, F1-60). D1 D4 The CPU reference is real, 8.0 ms for 16,777,216 bytes R2; the one GPU thread's time is the first number to measure in the Lab.

Trap 3: ignoring divergence. On a CPU, "22 % of the bytes take the slow path" adds 22 % of the slow path. On a GPU it can make every group take it (100.0 % of groups mixed, 33.6 % SIMD efficiency, R12). Fixes: make the groups agree (sort or bin the work first, if that is cheaper than the waste), or make the paths short. And read the machine code first: the compiler may already predicate a short branch (F1-57).

Layer 3 — the engineer's depth

One analogy sentence first: the hall's rows are a promise the hardware makes about instruction issue, not a promise about which helper finishes first, and the specification sections below say exactly what is promised.

Execution model. The CUDA Programming Guide's "SIMT Architecture" and "Hardware Multithreading" sections define the warp, how threads are assigned to warps, divergence, and the on-chip execution context of each resident warp. D1 Since Volta, independent thread scheduling gives each thread its own program counter; the guide states that code which assumed implicit warp-synchronous execution must use the _sync intrinsics with a mask, and it discusses starvation-free algorithms such as locks. D1 The SASS in this build is consistent with a change of mechanism: sm_60 uses SSY/SYNC; sm_80 uses BSSY B0/BSYNC B0 with a YIELD inside the spin loop R9.

Memory model and scopes. The PTX ISA's memory consistency model defines scopes (CTA, GPU, system), strong and weak operations, and release/acquire semantics, in the same spirit as the C++ model of F2-39. D10 CUDA C++ exposes it through scoped atomics and through cuda::atomic_ref with a thread scope in the libcu++ library. D1 The sm_80 SASS of Listing 4 makes scopes visible: ATOMG.E.CAS.STRONG.GPU for the lock (device scope) and MEMBAR.SC.GPU for __threadfence() R9. A scope that is too narrow (block scope for data shared across blocks) is a GPU-only bug class with no SP203 counterpart.

Grid-wide synchronization. A grid barrier requires all blocks to be resident at once; CUDA provides it through cooperative groups (this_grid().sync()) for kernels started with a cooperative launch, and the launch fails if the grid cannot be co-resident (F6-12). D1 Splitting the work into two kernel launches is the portable alternative; its cost is a launch and a pass over memory.

Profilers replace intuition on both sides. On the CPU, getrusage already shows the OS at work R2; perf did not run in this container (SP302, F2-55). On the GPU, Nsight Systems shows the copy and kernel timeline, and Nsight Compute reports per-kernel metrics for branch efficiency, sectors per request and atomic throughput (F6-32, F6-33). How the hardware actually does it

CPU. Each core has one set of architectural registers per hardware thread. To run a different software thread, the OS kernel saves the running thread's registers (program counter, stack pointer, general registers) into the thread's kernel record and loads another's: a context switch, triggered by a timer interrupt, a blocking call or a wake-up (F3-03). D8 That is why a waiting cook costs nothing but a switch does: R2 counted 18 involuntary switches when 8 threads competed for 4 CPUs. Atomic read-modify-writes are performed on a cache line the core holds exclusively; when many cores click one counter, the line travels between them (F2-38, F1-36), which is the measured slowdown of sharedAtomic. D7

GPU. An SM holds the registers of all its resident warps in one large register file and the shared memory of its resident blocks (F6-03, F1-58). Each cycle a warp scheduler picks a warp whose next instruction is ready and issues it for all active lanes; a warp waiting for memory simply is not picked (F1-60). D1 Divergence is implemented with masks: on AMD the 64-bit EXEC register, on NVIDIA predicates and convergence instructions such as the BSSY/BSYNC pair visible in R11 (F1-57). D9 D11 Global atomics are carried out by the memory system outside the SM; Listing 6's histogram update compiles to RED.E.ADD.STRONG.GPU, the form used when the old value is not needed (R11, F6-13). Shared-memory atomics stay on the SM, which is the hardware reason privatization into shared memory pays (F6-17). D4

Worked example

Task. Listing 1 and Listing 2 histogram the same 16,777,216 bytes. (a) How many workers does each create, and in how many hardware groups? (b) What does Amdahl's law predict for Listing 1 with 4 threads, and how does the prediction compare with the measurement? (c) What bounds the GPU version before any kernel is written? (d) Check Listing 7's divergence numbers by hand.

(a) Workers and groups. CPU: 4 threads (one per CPU visible), 16,777,216 / 4 = 4,194,304 bytes each. GPU, histGlobal: one thread per byte, blocks of 256, so 16,777,216 / 256 = 65,536 blocks. Each block holds 256 / 32 = 8 warps on NVIDIA, or 256 / 64 = 4 wavefronts on CDNA: 65,536 × 8 = 524,288 warps, or 65,536 × 4 = 262,144 wavefronts. Creating that many CPU threads at this build's 63.3 µs each would take 16,777,216 × 63.3 µs ≈ 1,062 s R2: a GPU thread is not a cheap CPU thread, it is a different thing.

(b) Amdahl for the CPU version. Skewed input: the serial loop took 30.6 ms R2. The serial part of privateMerge is starting and joining the threads plus a merge of T × 256 additions; estimate it by the thread cost alone, 4 × 0.0633 ms = 0.253 ms. If the rest spreads perfectly: t(4) = 0.253 + 30.6 / 4 = 7.90 ms, a predicted speedup of 30.6 / 7.90 = 3.87. Measured: 16.3 ms for chunked privateMerge with 4 threads, a speedup of 1.88 R2. The serial part does not explain the gap; other limits do (four CPUs of a shared virtual machine, the memory system the cores share, and one counter updated again and again on skewed input: the serial loop needs 30.6 ms there against 8.0 ms on uniform input). Amdahl gives a ceiling; a profiler finds the rest.

(c) Amdahl for the GPU version. The 16 MiB must be copied to the GPU before any kernel can count them, and the copy is serial with respect to the kernel. If it takes c ms (measure it with events, F6-06), even an infinitely fast kernel cannot beat the CPU's 8.0 ms by more than 8.0 / c. The GPU wins clearly when the data already lives there or one copy serves many operations. This build has no GPU, so c is the first number in your lab record.

(d) Divergence by hand. Of the 256 byte values, 56 are ≥ 200, and the scrambled input contains each value equally often in 65,536 bytes (256 each), so the fraction is 56 / 256 = 0.21875: 14,336 bytes, as Listing 7 printed. Useful work per byte: 6 + 34 × 0.21875 = 13.4375 model instructions. A group of 32 avoids the slow path only if all 32 bytes are below 200: 0.7812532 ≈ 0.00037, so almost every group pays 6 + 34 = 40 per byte. Efficiency 13.4375 / 40 = 0.336, the 33.6 % of R12. For a wavefront of 64 the chance of a fast group is 0.7812564 ≈ 1.4 × 10−7; the answer is the same 33.6 %.

Where the analogy breaks


    

  • Rows are not lines of people who can see each other. Lanes of a warp do not "notice" that a neighbour holds the key; the hang in Figure 3 comes from where the compiler placed the reconvergence point R9, not from politeness. Change the code layout (Program B) and the same lanes finish.
    • 

  • "The row moves together" is the model, not the whole truth on newer NVIDIA GPUs. With independent thread scheduling the lanes of a warp may make progress separately, so a row can sometimes behave like independent cooks; it still pays for divergence and still prefers to move together (unverified box in Layer 3). D1
    • 

  • Nobody "keeps everything in her hands" for free. The registers that let a warp pause without saving anything are a fixed budget per SM: more registers per thread means fewer warps in the hall (occupancy, F1-58). The analogy hides this trade-off.
    • 

  • A CPU cook is not one person either. A CPU core also executes several operations at once (pipelining, SIMD, F2-53); "few, clever cooks" means few instruction streams, not one operation at a time.
    • 

  • Thousands of helpers "arriving at once" is a simplification. The launch creates the whole grid logically, but blocks are placed on SMs as resources free up; a large grid is never all in the hall at once (guide 8.1, "Grid"). D1
    •

Summary


    

  • Data races, synchronization, atomics, the idea of a memory model and Amdahl's ceiling carry over unchanged; Listing 3 lost increments on the CPU exactly as histRacy can on the GPU.
    • 

  • CPU threads are few and heavy (63.3 µs per start and join, 8192 KiB of stack each, here) and scheduled by the OS with context switches; GPU threads are created by the launch by the million and scheduled by hardware in warps of 32 or wavefronts of 64.
    • 

  • A warp switch saves nothing, because every resident warp keeps its registers; the price is that registers per thread limit how many warps fit.
    • 

  • Divergence makes a whole group pay for every path any lane takes; a rare slow path can make almost every group slow (33.6 % SIMD efficiency in the model).
    • 

  • Synchronization is cheap inside a block (__syncthreads()) and missing or expensive across the grid; merge with atomics or a second kernel.
    • 

  • The access pattern of the whole group decides memory efficiency: the CPU's chunked split becomes the GPU's worst case; interleave instead.
    • 

  • Trap 1: a CPU-style spin lock can hang a warp, because the unlock lies after the reconvergence point; Trap 2: one GPU thread is slow; Trap 3: ignored divergence wastes most of each group.
    • 

  • Measure both sides; Amdahl gives the ceiling, the profiler explains the rest.
    •

Forensic lab answer key


Observation. sm_60: SSY 0x78 at 0x0018 sets the reconvergence point; the loop is ATOM.E.CAS at 0x0050 and @P0 BRA 0x40 at 0x0068; lanes that leave it reach SYNC at 0x0070; the critical section is 0x0090–0x00a8; the unlock ATOM.E.EXCH is at 0x00b8. sm_80: the same structure with BSSY B0, 0xe0, BSYNC B0 at 0x00d0, a YIELD at 0x0090 inside the loop, and scoped instructions (ATOMG.E.CAS.STRONG.GPU, MEMBAR.SC.GPU) R9.


Hypotheses. (a) The lock is never released (supported: the unlock follows the reconvergence point; Listing 5 reproduces the hang under lock-step execution, R10). (b) The kernel is just very slow (weakened: the same program finishes on a newer GPU, and the model shows a finite cost under an independent scheduler, 65 rounds for 32 lanes). (c) A launch error that is never checked (ruled out for this code: every call in Listing 4's host code is checked, and an error would end the program instead of hanging it).


Root cause of the hang. A CPU spin lock used between lanes of one warp: the winning lane waits at the reconvergence point before its unlock, and the losing lanes spin; under lock-step execution nobody progresses. On GPUs with independent thread scheduling the lanes can progress separately, which matches the team's report that the newer GPU finishes (to be verified: Layer 3 unverified box).


Root cause of the slowness. histChunked ports the CPU's chunked split: lane l reads byte 64·l, so one load instruction of a warp touches 32 segments instead of 1 (R12; Figure 2). On the CPU, the same split gave each core one contiguous stream, which is why it was a sensible choice there (R2 shows chunked and interleaved close). A second, smaller cost: every update is a global atomic on 256 shared bins. R6 also shows 20 registers per thread against 10 for histGlobal.


Fix and verification. Replace the lock with atomicAdd (no lock), or keep a lock only in the Program B form; replace chunked slices with an interleaved grid-stride loop and privatize per block (histShared). Verify on a GPU: all counts equal the CPU reference; timeout 20 ./spin_warp finishes on every GPU in the lab; Nsight Compute shows fewer sectors per request for the interleaved kernel; the event-timed median drops.


Prevention. Review rule: no spin locks in device code without a written forward-progress argument; a port changes the partition on purpose, never "line by line". Automatic check: a CI job that runs every kernel test under timeout, plus a profiler-metric gate on sectors per request for the histogram kernel. How the evidence was produced: real compiler outputs and model runs of this build (CUDA 12.0, g++ 13.3.0); the two symptoms in the scenario are part of the story and were not observed, because this build has no GPU.
