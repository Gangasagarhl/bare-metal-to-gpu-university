Story hook

After the banquet, a thousand numbered plates must go back to the shelf in order, plate 0 first. Luis cannot compare plates two by two with a thousand helpers: who would compare with whom? Lucía has a different plan. "First, sort only by the last digit. Every table counts how many of its plates end in 0, in 1, … in 9. We add up the counts so every table knows where its plates ending in 0 go, where its plates ending in 1 go, and so on. Everyone puts their plates in place at once. Then we do it again for the middle digit, and then for the first."

"But the second round will mess up the first," says Luis. "Only if you are careless," says Lucía. "When two plates have the same middle digit, keep them in the order they arrived. Then the last digit's order survives inside every group." Three rounds, no comparisons, every helper busy. That is radix sort, and its middle step, "add up the counts so everyone knows where to go", is the scan of F6-16.

What you will be able to do

  • Explain why least-significant-digit (LSD) radix sort is correct only if every pass is stable.
  • Trace one pass by hand: per-tile digit counts, the digit-major exclusive scan, and the scatter.
  • Build a radix sort for 32-bit keys and key-value pairs from a histogram and a scan, and test it on milestone E4's sizes and inputs.
  • Map signed integers and floats to unsigned keys whose order matches, and back.
  • Choose the digit width by trading passes against counters per tile, and compare your sort with CUB's DeviceRadixSort.
  • Diagnose a radix sort whose every pass is right but whose result is not sorted (the forensic lab).
Jargon box
Radix sort
Simple words: sorting by looking at one digit at a time instead of comparing whole keys. Analogy: putting plates in order by the last digit, then the middle, then the first. Precise: a non-comparison sort that treats a key as a sequence of d-bit digits and distributes keys by one digit per pass; for b-bit keys it needs ⌈b/d⌉ passes, each linear in n. D3 D4
LSD (least significant digit first)
Simple words: sort by the lowest digit first, the highest last. Analogy: last digit of the plate number first. Precise: after pass p, keys are sorted by their lowest p digits, provided every pass is stable; the last pass leaves them fully sorted. D4 R2
Stable sort
Simple words: equal keys keep their original order. Analogy: plates with the same middle digit stay in the order they arrived. Precise: if ki = kj and i < j in the input, the item from i comes first in the output; std::stable_sort guarantees it; the installed CUB header states "DeviceRadixSort is stable". D4 R6
Digit (radix digit)
Simple words: a small group of bits of the key looked at in one pass. Analogy: one digit of the plate number. Precise: (key >> shift) & (2d − 1); with d = 4 a digit has 16 values, with d = 8, 256. R2
Split (1-bit partition)
Simple words: one pass of radix sort with a one-bit digit: all keys with a 0 go first, then all with a 1, each group in its old order. Analogy: plates with an even number to the left, odd to the right, keeping the order. Precise: destination = exclusive scan of the 0-flags for 0-keys, and (number of 0-keys) + (number of 1-keys before me) for 1-keys. D3 R1
Scatter
Simple words: writing each item to a computed position, not the next one. Analogy: each helper carries a plate to the shelf spot it was given. Precise: out[dst[i]] = in[i] with dst a permutation; on a GPU its store pattern decides how well writes coalesce (F6-08). D3
Key transformation (order-preserving)
Simple words: changing the bits of signed numbers or floats so that sorting them as unsigned numbers gives the right order. Analogy: relabelling plates so the shelf order is right. Precise: the installed CUB header lists them: unsigned keys "used directly"; signed: "the sign bit is inverted"; positive floats: "the sign bit is inverted"; negative floats: "the full key is inverted". R6

The idea in pictures

Figure 1 is one pass of the sort, with the numbers of the worked example: two tiles of four keys and 2-bit digits (so the digit is the whole key, 0 to 3).

Layer 1 — the kid explanation

To sort numbers without comparing them, look at one digit at a time. Start with the last digit: put every number in the group for its last digit, keeping the order inside each group. Then do the same with the next digit. After the last round the numbers are in order. Every helper can work at the same time, because each one only needs to know where its group starts, and adding up the group sizes tells everyone that.

Layer 2 — the student explanation

The smallest case: a 1-bit split

With a 1-bit digit, a pass is a split. Listing 1 traces it on 5 2 7 0 3 6 1 4. For bit 0, the flags "bit is 0" are 0 1 0 1 0 1 0 1; their exclusive scan 0 0 1 1 2 2 3 3 gives each 0-key its place; there are 4 zeros, so a 1-key at index i goes to 4 + (i − scan[i]). The destinations are 4 0 5 1 6 2 7 3 and the result is 2 0 6 4 5 7 3 1. After bits 1 and 2 the keys are 0 1 2 3 4 5 6 7. R1 The whole pass is one scan and one scatter; no thread compares two keys.

Why LSD works, and why stability is the condition

Suppose after some passes the keys are sorted by their lowest p digits. The next pass sorts by digit p + 1. Two keys with different digits p + 1 end up in the right order by that digit. Two keys with the same digit p + 1 keep their previous order, if the pass is stable, and that order was right by the lower digits. By induction, after all passes the keys are sorted. D4 Without stability the argument fails at the second pass; the forensic lab measures how badly.

A pass with d-bit digits

Listing 2 uses 4-bit digits (16 values) and tiles of 256 keys, the way a GPU kernel would assign one block per tile (lines 18–41). Each pass has three steps:

  1. Count (lines 25–29): every tile builds a 16-bin histogram of its digits, as in F6-17.
  2. Scan (line 30): one exclusive scan over all counts, laid out digit-major: all tiles' counts for digit 0, then all tiles' counts for digit 1, and so on. The scanned value at [d][t] is the first output position for digit d of tile t: after all smaller digits, and after the same digit of earlier tiles.
  3. Scatter (lines 31–37): every key goes to that position plus its rank among equal digits inside the tile, in input order.

The digit-major layout is what makes the scan do the work of two: it orders digits globally and tiles within a digit, which is exactly stability across tiles. D3 Key-value pairs cost nothing extra in the logic: the value moves with its key (lines 35–36).

E4's acceptance cases

Listing 2 sorts sizes 1, 2, 255, 257, 65,535, 65,537 and 1,000,003, each random, sorted, reverse-sorted and all-equal, as keys and as pairs. Every case passes, and the pairs equal those of std::stable_sort, which checks stability directly: the values are the original positions, so any unstable step would show. R2 These are E4's words: "results identical to a CPU reference for random, sorted, reverse-sorted and all-equal inputs, including sizes 1, 2^k−1, 2^k+1". C1

Signed and float keys

Radix sort orders bit patterns as unsigned numbers. Two's-complement negatives have the top bit set, so they would sort after the positives; inverting the sign bit fixes it (Listing 2, line 43). IEEE 754 floats are sign and magnitude: for positives, inverting the sign bit is enough; for negatives, a larger magnitude must come first, so all bits are inverted (lines 44–49). The run sorts −2147483648 −3 −1 0 3 5 2147483647 and −7.25 −0.5 −1e-09 0 2.5 3 1e+09 correctly. R2 These are the transformations the CUB 2.0.1 header lists, quoted in the jargon box. R6 One difference: CUB's header says that "-0.0 and +0.0 are considered equal and appear in the result in the same order as they appear in the input", while Listing 2's mapping gives −0.0 a smaller key than +0.0. H1 NaNs are, in CUB's words, "sorted according to their bit representations after any transformations". H1

Layer 3 — the engineer's depth

Lucía's plan hides one cost: every round moves every plate. The engineering is about how many rounds, and how each move is made.

Digit width: passes against counters

For 32-bit keys, 1-bit digits need 32 passes (Listing 3), 4-bit digits 8 passes (Listing 2), 8-bit digits 4 passes. Each pass reads every key at least once and writes it once, so fewer passes means less memory traffic. Wider digits cost more counters per tile (2, 16, 256) and a bigger scan (2d × tiles entries: for 2^26 keys in tiles of 256 with 4-bit digits, 16 × 262,144 = 4,194,304). D3 CUB's tuning policy for compute capability 8.0, read in this build, sets ONESWEEP_RADIX_BITS = 8 and ONESWEEP = sizeof(KeyT) >= sizeof(uint32_t), and PRIMARY_RADIX_BITS 7 for keys wider than one byte: CUB chooses wide digits. R7

Counting the traffic

Listing 2's pass reads the keys twice (count, then scatter) and writes them once: about 3 key accesses per key per pass, plus the counts. A sort that keeps a whole tile in shared memory during the pass reads each key once, counts and ranks it on chip, and writes it once. A further step removes the separate counting kernel: compute the histograms of all digits in one upfront pass, then do each digit pass as a single sweep, with tile offsets passed between blocks by decoupled look-back (F6-16). The compiled CUB code in Listing 3's binary contains kernels named DeviceRadixSortHistogramKernel, DeviceRadixSortOnesweepKernel and, for other policies, DeviceRadixSortUpsweepKernel, RadixSortScanBinsKernel and DeviceRadixSortDownsweepKernel. R8

Ranking inside a tile

The scatter needs, for each key, its rank among keys with the same digit in its tile, in input order. On a CPU, Listing 2 gets it for free by walking the tile in order (offset[...]++, line 33). On a GPU, threads run concurrently, and the obvious shortcut, a shared-memory atomicAdd on the digit's counter, gives each key a unique place but in the order the atomics happened (the forensic lab). Stable ranking uses a scan: a 1-bit split per bit of the digit inside the tile (as Listing 3 does with blockExclusiveScan), or a scan of per-digit flags, or warp-level match operations that count equal digits among lower lanes (F6-15). D3

Listing 3: correct and simple, not fast

Listing 3 is the 1-bit split on the GPU. countZeros counts the 0-keys per block with __syncthreads_count, a barrier that also counts how many threads passed a true predicate (line 33). D1 CUB's DeviceScan::ExclusiveSum turns the per-block counts into per-block starting positions (line 88). scatter ranks each key in its tile with a Hillis–Steele block scan (lines 14–27) and writes it (lines 44–51). Thirty-two passes of three kernels: a teaching baseline whose distance from CUB your E4 table will show. It sorts keys only; pairs are the lab's step 6.

How the hardware actually does it

A block-wide count is cheap because the barrier hardware can count: the SASS of countZeros contains a single BAR.RED.POPC between the load (LDG) and the store (STG), which, as its name suggests, combines the barrier with a population count of the predicate. R9 The expensive part of a pass is the scatter. Keys of one digit from one tile go to consecutive addresses, but neighbouring threads usually hold different digits, so one warp's 32 stores land in up to 2d separate runs and need many memory transactions (F6-08). D3 Production sorts therefore first reorder the tile in shared memory by digit, so that consecutive threads write consecutive addresses within each run; the shared-memory step costs barriers and bank traffic but turns scattered stores into near-coalesced ones. D3 CUB's onesweep kernel, compiled into Listing 3's binary, contains 21 ATOMS.POPC.INC.32 and 21 ATOMS.ADD shared-memory atomics, the same increment instruction as the histogram of F6-17, and a single global ATOMG.E.ADD, which would fit a dynamic tile counter like the one of F6-16 (an interpretation, not traced in the source). R10

Worked example

Task. One pass with 2-bit digits over two tiles of four keys: tile 0 = 3 1 2 1, tile 1 = 0 3 1 2 (Figure 1).

  1. Count. Tile 0: digit 0: 0, digit 1: 2, digit 2: 1, digit 3: 1. Tile 1: 1, 1, 1, 1. Check: each tile's counts add up to 4.
  2. Lay out digit-major. d0t0, d0t1, d1t0, d1t1, d2t0, d2t1, d3t0, d3t1 = 0 1 2 1 1 1 1 1.
  3. Exclusive scan. 0 0 1 3 4 5 6 7. So tile 0's 1-keys start at 1, tile 1's 1-keys at 3; tile 0's 3-key at 6, tile 1's at 7.
  4. Scatter tile 0 in input order: 3 → 6; 1 → 1 (then the 1-offset becomes 2); 2 → 4; 1 → 2.
  5. Scatter tile 1: 0 → 0; 3 → 7; 1 → 3; 2 → 5.
  6. Result. 0 1 1 1 2 2 3 3. The three 1-keys are, in order, tile 0's first, tile 0's second, tile 1's: input order is kept, so the pass is stable.

Listing 2 performs exactly these steps, with 16 digit values, 256 keys per tile and eight passes.

Where the analogy breaks


    

  • Plates do not need relabelling. Plate numbers are non-negative decimal numbers. Real keys can be negative or floating point, whose bit patterns do not sort correctly as unsigned numbers without the transformations of Layer 2.
    • 

  • Helpers putting plates on the shelf do not get in each other's way. On a GPU, where the keys go matters: scattered stores from one warp need many memory transactions, and the "putting in place" step is the expensive one.
    • 

  • "Keep the order they arrived" is not free. Helpers in the hall naturally line up; GPU threads do not. Stability must be built with a scan or a ranking step; an atomic counter gives places in a random order.
    • 




Common mistakes and debugging


    

  • Symptom: each pass looks right, the final result is not sorted. Cause: an unstable pass (atomic ranking). How to find it: sort key-value pairs whose values are the original positions and compare with std::stable_sort. Fix: rank with a scan.
    • 

  • Symptom: negative numbers come after positive ones. Cause: signed keys sorted as unsigned. Fix: invert the sign bit before and after.
    • 

  • Symptom: negative floats in reverse order. Cause: only the sign bit flipped for negatives. Fix: invert all bits of negative floats.
    • 

  • Symptom: wrong only when n is not a multiple of the tile. Cause: threads past the end counted as 0-keys, or skipped barriers. Fix: count only i < n (Listing 3, line 32) but let every thread reach every barrier.
    • 

  • Symptom: result is in the wrong buffer after an odd number of passes. Cause: ping-pong buffers. Fix: track which buffer holds the result (Listing 3 swaps pointers each pass; 32 is even).
    • 

  • Symptom: pairs sorted, values scrambled. Cause: the value scattered with a different index from its key. Fix: compute dst once and use it for both.
    • 




Transition box

Where you came from: F6-16 (exclusive scans, decoupled look-back), F6-17 (histograms with privatization), SP203 (comparison sorts and std::stable_sort). What carries over: a histogram counts digits; an exclusive scan of counts gives starting positions; stability is the property you already know from std::stable_sort. D4 What changes: no comparisons at all: the sort is a fixed number of linear passes, and the cost is memory traffic per pass, not O(n log n) comparisons; stability, free in a sequential loop, must be engineered on a GPU. D3 What comes next: F6-19 returns to shared memory for its classic use: making both the reads and the writes of a matrix transpose coalesced, without bank conflicts.

Forensic lab

Their test sorts 8-bit keys with 4-bit digits and checks after each pass that the keys are sorted by that pass's digit: it passes. With 16-bit keys, the final output is not sorted. Summary


    

  • LSD radix sort: one stable pass per digit, lowest digit first; correct by induction only if every pass is stable.
    • 

  • A pass is a histogram per tile, one exclusive scan of digit-major counts, and a scatter.
    • 

  • The 1-bit split is the simplest pass: a scan of the 0-flags.
    • 

  • Signed and float keys sort as unsigned after order-preserving bit transformations.
    • 

  • Wider digits: fewer passes, more counters; CUB's sm_80 policy uses 8-bit digits for its onesweep path.
    • 

  • On a GPU, stability must be built (scan-based ranking); atomics give unique but unordered places.
    • 

  • The scatter dominates; local reordering in shared memory makes its stores coalesce.

Forensic lab answer key


Observation. Stable version: 0 and 0 in every pass; the final keys start 1 2 4 4 4 5 6 6. Atomic version: 0 out of order by each pass's own digit, but 680, 10,227 and 42,436 out of order by all digits so far after passes 1, 2 and 3; the final keys start 8 4 6 7 5 4 8 4 (R4).


Hypotheses. The first column is 0 everywhere, so the count, scan and grouping of every pass are right; the last copy cannot explain an error that already exists after pass 1. The second column grows from pass 1: the passes destroy each other's order.


Root cause. The atomic ranking (replayed by the shuffle at line 24) makes each pass unstable. Keys with the same current digit end up in arbitrary order, so the order by lower digits is lost; LSD's induction step fails.


Why the 8-bit test passed. Its check after each pass only looked at that pass's digit, which is always right; and with two passes, only the second one could break the first (the team's check never compared full keys).


Fix. Rank with a stable method: a scan per digit or per bit inside the tile, as in Listing 3's blockExclusiveScan. Prevention: test pairs with original positions as values against std::stable_sort (Listing 2), and always check the final full-key order, not a per-pass property.


How the evidence was produced: unstable.cpp, a CPU replay where a seeded shuffle stands in for the order in which atomics happen; no GPU was used. That real atomics produce a different order every run is the scenario's assumption, not a measurement.
