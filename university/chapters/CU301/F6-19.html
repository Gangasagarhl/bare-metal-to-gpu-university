Story hook

The pantry's jars stand in long shelves, row after row. Tonight's job is to move them to a second pantry, but turned: what was a row must become a column. Neighbouring helpers can fetch neighbouring jars from a shelf in one trip. Reading a row is easy. Putting the jars down along a column is not: each helper walks to a different shelf.

Mei's idea: each row group fetches a square block of jars, row by row, and sets it on the table in the middle of the row. Then they pick the jars up from the table column by column and carry each column to the new pantry, where it is now a row. Both trips to the pantries are neighbour-to-neighbour. The only awkward moment is at the table: picking up a column means every helper reaches into the same drawer. Mei shifts each row on the table by one place, and the queue at the drawer disappears. Rahim has another trick: instead of shifting, he shuffles where each jar is put on the table by a simple rule, so no drawer is visited twice, and the table needs no extra space.

This chapter is milestone E5: naive, tiled, padded and swizzled transposes.

Jargon box
Transpose
Simple words: turning a matrix so that rows become columns. Analogy: moving jars so each shelf row becomes a column in the new pantry. Precise: for an input of h rows and w columns in row-major order, out[c * h + r] = in[r * w + c]; the output has w rows of h elements. R2
Tiled transpose
Simple words: a transpose that goes through a small square in shared memory so that both global reads and global writes are along rows. Analogy: a square of jars set on the table and picked up by columns. Precise: a block loads a TILE × TILE tile with row-wise (coalesced) reads, synchronises, and writes the tile's columns as rows of the output tile at the swapped block coordinates. D2 D3
Padding
Simple words: making each tile row one element longer than needed so columns fall into different banks. Analogy: shifting each row on the table by one place. Precise: tile[32][33]: element (r, c) is word 33r + c, bank (r + c) mod 32 in a 32-bank model; costs one unused word per row (F6-11). D2 R2
Swizzling (XOR)
Simple words: storing each element at a column computed with a simple bit rule, so no column read hits one bank twice, without extra space. Analogy: Rahim's rule for where each jar goes on the table. Precise: store logical (r, c) at physical column c XOR r in a tile[32][32]; for fixed c, r ↦ c ⊕ r is a permutation of 0…31, so a column read touches every bank once; so does a row write. R2
Coalesced write
Simple words: neighbouring threads storing to neighbouring addresses, so the stores combine into few memory transactions. Analogy: putting neighbouring jars on one shelf in one trip. Precise: the store counterpart of coalescing (F6-08); in the 32-byte-segment model of Listing 2, a warp storing 32 consecutive floats touches 4 segments, 32 floats one row apart touch 32. R2
Copy bandwidth (reference)
Simple words: how fast the GPU can just copy the matrix, the ceiling a transpose is measured against. Analogy: moving the jars without turning them. Precise: E5's target is "X % of your E2 copy bandwidth"; Listing 1's copyTile uses the same tiles and threads without transposing and reports each kernel's time as a percentage of it. C1

Layer 1 — the kid explanation

Turning a big table of numbers on its side means reading along rows and writing along columns. Helpers are fast when they work on neighbours, so one of the two directions is always slow. The fix is to carry a small square to the shared table, then pick it up the other way round. On the table, a column must not all sit in one drawer; shift each row by one place, or use a rule that spreads the column over all drawers.

Layer 2 — the student explanation

The naive kernel and its strided write

Listing 1's naive (lines 27–34) gives each thread an element and writes out[x * height + (y + j)] = in[(y + j) * width + x] (line 32). For one warp, x runs over 32 neighbours: the reads are consecutive, the writes are height floats apart. Listing 2 counts it for a 4,096 × 4,096 matrix: the load touches 4 segments of 32 bytes, the store 32. R2 Swapping the roles only moves the problem: then the reads are strided. Whichever way you index, one side of a direct transpose is uncoalesced. D2

The tiled kernel

The template tiled<MODE> (lines 37–56) has three phases (Figure 1):

  1. Load (lines 43–47): thread (tx, ty) reads rows ty, ty + 8, ty + 16, ty + 24 of the input tile; along tx the addresses are consecutive (4 segments per warp). It stores into tile[r][c] with r = ty + j, c = tx: a row of the tile, one pass.
  2. Barrier (line 48): no thread reads the tile before all of it has been written (F6-12).
  3. Store (lines 49–55): the block coordinates are swapped (lines 49–50); thread (tx, ty) reads tile[tx][ty + j], a column of the tile, and writes it to consecutive addresses of the output row: 4 segments per warp. R2

Both global accesses are now coalesced; the price is one shared-memory round trip and one barrier. The column read in phase 3 is where the banks matter.

The banks of a column read

In the 32-bank, 4-byte model of F6-11, word k is in bank k mod 32. D1 For tile[32][32], lane r of the column read takes word 32r + c, bank c for every lane: 32 distinct words in one bank, 32 passes. Listing 2 prints exactly that for tiledNoPad: shared write 1 pass, shared read 32. R2 Two fixes:

  • Padding (MODE == 1, line 40: tile[32][33]): word 33r + c, bank (r + c) mod 32, all different for r = 0…31: 1 pass. Cost: 4,224 bytes of shared memory instead of 4,096 (ptxas, R4).
  • Swizzling (MODE == 2, lines 45 and 53): logical (r, c) is stored at physical column c ⊕ r. A column read (fixed c, lane r) takes banks c ⊕ 0, c ⊕ 1, …, c ⊕ 31: a permutation of 0…31, 1 pass. A row write (fixed r, lane c) takes c ⊕ r for all c: also a permutation, 1 pass. Shared memory stays at 4,096 bytes (R4). R2 R4

Listing 2 confirms 1 pass for both reads and writes of tiledPad and tiledSwizzle. R2

Non-square and non-multiple shapes

E5 requires "correct for non-square and non-tile-multiple shapes". C1 Two rules make the tiled kernel safe. The grid covers the input, rounded up: ⌈w/32⌉ × ⌈h/32⌉ blocks (line 74). Each global access has its own bounds check with the right dimensions: the load checks x < width && y + j < height (line 46); after the swap, the store checks x < height && y + j < width and writes with row length height (line 54). The barrier is outside every condition, so every thread reaches it. Listing 2 replays every block of every kernel for 1,000 × 700, 33 × 65, 1 × 77 and 64 × 64: 0 errors for all four transposes. R2

Layer 3 — the engineer's depth

Mei's shift and Rahim's rule both work on the table; the engineer's questions are what each costs, when each one fails, and what the profiler will show.

Padding or swizzling?

Padding is one character in the source and trivially correct, but it wastes a column per row and breaks alignment: a padded row of 33 floats starts at 132-byte steps, so vector loads of 16 bytes from shared memory no longer line up for every row. Swizzling keeps the tile dense and aligned, which matters when tiles are large, when they are filled by asynchronous or vectorised copies, or when shared memory per block limits occupancy (F6-10). Its cost is an XOR per index (cheap) and an index rule every reader and writer must agree on. D2 D3 CU302's GEMM tiles and CUTLASS's layouts use swizzles of this family; the XOR here is the simplest member.

Other element sizes

The bank arithmetic above assumes 4-byte elements. With 8-byte doubles, each element spans two 4-byte words, and with 1- or 2-byte elements several share a word. Pitch 33 and c ⊕ r are then not automatically conflict-free; redo the arithmetic with words, and check against the profiler.

Not verified — check before relying on this

The 32-bank, 4-byte-wide model is the one the CUDA documentation describes for recent compute capabilities according to the authors' memory, but it was not checked against the CUDA C++ Programming Guide's compute-capability appendix in this build; how 8-byte accesses are served (possibly in two half-warp phases) was not checked either. For AMD GPUs, E5 asks you to read "the vendor's description of LDS banks in the AMD ISA guide for your architecture"; the LDS bank count and width were not checked here. Check: D1 (shared memory section, compute-capability appendix) and the AMD ISA reference guide for your GPU.

What the profiler should show

E5 accepts when the "profiler shows zero (or near-zero) shared-memory bank conflicts for the final version". C1 Expected, from the model: for tiledNoPad, the shared loads need 32 times as many wavefronts (passes) as requests; for tiledPad and tiledSwizzle, one per request. The forensic lab of F6-11 shows the same transpose from the profiler's side. Only an Nsight Compute run on a GPU can confirm this; none was possible in this build.

How fast can it be?

A transpose does no arithmetic: it reads and writes every element once, so its time is bounded below by the copy time. Listing 1 therefore reports each kernel as a percentage of copyTile, which uses the same grid, block shape and bounds checks, and prints "GB/s" as 2 × elements × 4 bytes / time (line 123). R1 E5 measures against "your E2 copy bandwidth" (F6-09); copyTile is a convenient stand-in, but use the E2 number in your report. The integer index (y + j) * width + x overflows for matrices with more than 2^31 elements; use 64-bit indices before going there (F6-14).

How the hardware actually does it

The compiler output shows the three designs as numbers. ptxas reports 4,096 bytes of shared memory for tiledNoPad and tiledSwizzle and 4,224 for tiledPad; naive and copyTile use none. R4 In the SASS of tiledSwizzle, the four stores to the tile are STS [R14.X4], [R14.X4+0x400], [R7.X4+0x800], [R21.X4+0xc00]: rows 8 apart, 8 × 32 × 4 = 1,024 = 0x400 bytes, the unpadded pitch (padding would give 0x420, as F6-11 showed). The swizzle itself appears as only four LOP3.LUT … 0x3c instructions, before the stores, BAR.SYNC 0x0 and the LDS loads of the column read: one per j, because the writer's threadIdx.x ^ r and the reader's (threadIdx.y + j) ^ threadIdx.x are the same value, and the compiler computes it once for both phases. R5 LOP3 computes any function of three inputs from an 8-bit truth table; with the usual operand masks 0xF0, 0xCC and 0xAA, XOR of the first two inputs is 0xF0 ⊕ 0xCC = 0x3C, which matches. R5

Not verified — check before relying on this

The LOP3 truth-table convention (operand masks 0xF0, 0xCC, 0xAA) is from memory; NVIDIA's instruction-set reference was not opened. The consistency of four LOP3 instructions, one per j, with the four distinct XOR values of the source is the evidence used here. Check: the CUDA binary utilities documentation for your architecture.

Worked example

Task. In the swizzled tile, lane r = 0…3 of a warp reads logical column c = 5. Give the physical columns and banks, then check two lanes of a padded read.

  1. Physical column = c ⊕ r: 5 ⊕ 0 = 5, 5 ⊕ 1 = 4, 5 ⊕ 2 = 7, 5 ⊕ 3 = 6 (binary 101 with the last two bits flipped as r says).
  2. Word = 32r + physical column: 5, 36, 71, 102. Bank = word mod 32: 5, 4, 7, 6. All different.
  3. For all 32 lanes, r ↦ 5 ⊕ r takes every value 0…31 once (XOR with a constant is its own inverse), so all 32 banks are used once: 1 pass.
  4. Padded tile, lanes 0 and 31 reading column 5: words 5 and 33 × 31 + 5 = 1,028; banks 5 and 1,028 mod 32 = 4. Different, as (r + c) mod 32 predicts: (31 + 5) mod 32 = 4.
  5. Unpadded tile, same lanes: words 5 and 32 × 31 + 5 = 997; banks 5 and 997 mod 32 = 5. The same bank: this is the conflict.

Where the analogy breaks


    

  • Shifting a row on a real table takes space; on the GPU so does padding, but swizzling does not. The kitchen has no equivalent of storing jars at XOR-ed places: it is a pure index rule, invisible until you read the code.
    • 

  • The pantry trips are not equal. In the hall, a column trip is "slower"; on a GPU the cost is the number of memory transactions (32 segments instead of 4 in the model), and caches can partly hide it; the real ratio must be measured.
    • 

  • Drawers are not furniture. Banks are an addressing rule (word mod 32 in the model), so the same tile can be conflict-free for one access pattern and 32-way conflicted for another; nothing physical moves.
    • 




Common mistakes and debugging


    

  • Symptom: correct for square matrices, wrong or crashing for 1,000 × 700. Cause: the output index uses width as its row length (the forensic lab). How to find it: test a non-square shape in both orientations; Compute Sanitizer memcheck reports the out-of-bounds writes. Fix: output rows have length height.
    • 

  • Symptom: garbage in some output elements, varying between runs. Cause: barrier missing, or placed inside the bounds check so edge threads skip it. Fix: one __syncthreads() between the phases, reached by all threads.
    • 

  • Symptom: padded kernel no faster than unpadded. Cause: padding applied to the wrong dimension (tile[33][32]). Fix: pad the row length, the second index.
    • 

  • Symptom: swizzled kernel wrong. Cause: the reader uses a different XOR rule from the writer (for example, XOR with threadIdx.y instead of the logical row). Fix: one helper function for the physical column, used by both.
    • 

  • Symptom: slow edges on small matrices. Cause: partial tiles do little work. Fix: none needed for large matrices; for small ones, measure before tuning.
    •

Summary


    

  • A direct transpose has one uncoalesced side: 32 segments per warp instead of 4 in the model.
    • 

  • A shared-memory tile makes both global sides coalesced: read rows, barrier, read columns, write rows at swapped block coordinates.
    • 

  • The column read of a [32][32] tile hits one bank 32 times.
    • 

  • Padding ([32][33]) fixes it with 128 extra bytes; the XOR swizzle fixes it with none.
    • 

  • Bounds checks must use the right dimension on each side; the barrier must be reached by all threads.
    • 

  • A transpose is judged against copy bandwidth; only a GPU run can give the percentage.

Answers to Check yourself


    

  1. A warp's 32 neighbouring threads touch either 32 neighbours in one row of the input (and then 32 elements of one column of the output, far apart) or the reverse; a direct mapping cannot make both sides consecutive.
    2. 

  2. 32: neighbouring lanes write 4,096 floats apart, so every store falls into its own 32-byte segment (R2). A distractor is "4, as for the load": that holds only for the load.
    3. 

  3. Pitch 32: bank c for every lane (32 passes). Pitch 33: bank (r + c) mod 32, different for every lane (1 pass).
    4. 

  4. Element (r, c) is in bank c ⊕ r (word 32r + (c ⊕ r), mod 32). Row write: r fixed, c = 0…31, and c ↦ c ⊕ r is a bijection on 0…31. Column read: c fixed, r = 0…31, and r ↦ c ⊕ r is a bijection. One word per bank in both cases: 1 pass.
    5. 

  5. Cost: one XOR per index (four LOP3 in the SASS, R5) and an index rule to keep consistent. Saving: 128 bytes of shared memory per block (4,096 instead of 4,224, R4) and aligned rows.
    6. 

  6. ⌈40/32⌉ × ⌈100/32⌉ = 2 × 4 = 8 blocks. Input block (1, 3) covers columns 32–39 and rows 96–99; after the swap it writes output rows 32–63 (only 32–39 exist, since the output has 40 rows) and columns 96–127 (only 96–99 exist). The store check x < height (here x is an output column, < 100) and y + j < width (output row < 40) stops the rest.

  7. Threads outside the matrix would skip it, while the others wait at it; a barrier that not all threads of the block reach is undefined behaviour (F6-12).

Forensic lab answer key


Observation. Square shapes: 0 wrong, 0 unwritten, 0 outside. 1,000 × 700: 699,300 wrong, 210,000 never written, 210,000 writes outside the buffer. 700 × 1,000: 699,000 wrong, 209,700 never written, 0 outside. The fixed kernel: 0 everywhere (R3).


Hypotheses. A bank-conflict layout or a missing barrier would not depend on whether the matrix is square, and could not write outside the buffer: the tile is read and written with in-range indices. A wrong row length in the store fits: it only matters when width ≠ height.


Why square shapes hide it. When width == height, the buggy and correct row lengths are equal; the same code is correct.


Outside or not. The output has width rows of height elements. With the bug, a row index up to width − 1 is multiplied by width. For 1,000 × 700: largest index 999 × 1,000 + 699 = 999,699 ≥ 700,000 = buffer size, so writes land outside (on a GPU, in other allocations, hence the later illegal address). For 700 × 1,000: 699 × 700 + 999 = 490,299 < 700,000, inside the buffer but in the wrong places, overwriting some elements twice and leaving others unwritten.


Fix. out[(y + j) * height + x] (Listing 1, line 54). Prevention: E5's own acceptance test, non-square shapes in both orientations; Compute Sanitizer memcheck on every new kernel; name the dimensions of the output explicitly (outRows, outCols).


How the evidence was produced: nonsquare.cpp replays every block and thread of the kernel on the CPU and counts instead of writing outside the buffer; no GPU was used.
