Story hook

The plates for tonight's banquet are numbered, and each table must know where its plates start in the long serving line. Table 0 has 3 plates, table 1 has 1, table 2 has 7, and so on. Table 5 starts after all the plates of tables 0 to 4. That number, "how many came before me", is a prefix sum, and every helper in the hall needs one.

Inside one row it is easy: helpers pass running totals hand to hand. For the whole hall, Sofia first had every table count its plates, then the head of the hall added up the table counts, then every table placed its plates. Three trips. Then she tried something bolder: each table, as soon as it knows its own count, writes it on a board by the door, and looks at the board for the tables before it, walking back until it finds one whose full "start" number is already written. One trip. But it only works because every table that a helper waits for has already started work: otherwise they would wait forever, as in F6-12.

This chapter builds both: the block-level scan, the three-pass device-wide scan, and the single-pass decoupled look-back that CUB uses.

What you will be able to do

  • Explain decoupled look-back: tile status words, the look-back loop, and why tile numbers must be assigned in start order.
  • Diagnose an in-place scan that is right for one warp and wrong for a block.
Jargon box
Scan (prefix sum)
Simple words: for every position, the total of everything up to it. Analogy: each table's starting plate number. Precise: for input x and associative ⊕, output yi = x0 ⊕ … ⊕ xi (inclusive). D3
Inclusive scan
Simple words: each output includes its own element. Analogy: "plates up to and including mine". Precise: yi = ⊕j ≤ i xj; std::inclusive_scan. D3
Exclusive scan
Simple words: each output is the total of the elements before it; the first is the identity. Analogy: "where my plates start". Precise: y0 = identity, yi = ⊕j < i xj; exclusive = inclusive shifted right by one. D3
Hillis–Steele scan
Simple words: in step k, every element adds the element 2k places before it. Analogy: everybody looks 1, then 2, then 4 places back and adds. Precise: log₂ n steps, about n log₂ n additions; not work-efficient but short; needs two buffers or a barrier between read and write. D3 R1
Blelloch scan
Simple words: a reduction tree up, then a tree down that hands each subtree its starting value. Analogy: collect counts up to the head of the hall, then hand starting numbers back down. Precise: up-sweep and down-sweep, 2 log₂ n steps, about 2n additions (work-efficient); exclusive result. D3 R1
Reduce-then-scan
Simple words: a device-wide scan in three passes: tile sums, a scan of those, then each tile with its offset. Analogy: count per table, the head adds the counts, tables number their plates. Precise: needs about 3n memory accesses (read, read, write) plus the small middle pass; the kernel boundaries are the grid-wide barriers (F6-12). D3
Decoupled look-back
Simple words: a one-pass device scan where each tile publishes its total and looks back at earlier tiles' published values. Analogy: the board by the door. Precise: Merrill and Garland's method: per-tile status words (not ready, aggregate available, inclusive prefix available); a tile sums predecessors' aggregates until it meets an inclusive prefix; about 2n memory accesses; implemented in CUB's DeviceScan. S2 H2

The idea in pictures

Layer 1 — the kid explanation

Everyone wants to know "how many came before me?" In a short line you can just count. In a huge hall, each table counts its own plates first. Then each table asks the tables before it: "how many did you have?" It does not need to ask all of them: as soon as one table says "I already know how many came before me, and here is the total including mine", you can stop asking and add up.

Layer 2 — the student explanation

Inclusive and exclusive

For the input 3 1 7 0 4 1 6 3, the inclusive scan is 3 4 11 11 15 16 22 25 and the exclusive scan is 0 3 4 11 11 15 16 22. R1 The exclusive form answers "where does my output start?", which is what compaction, radix sort (F6-18) and allocation need. One converts to the other by shifting, or by subtracting the element.

Hillis–Steele

Listing 1 traces it: in step d = 1, 2, 4, every element i ≥ d adds element i − d of the previous array. After three steps the 8 elements hold the inclusive scan. R1 It is short (log₂ n steps) but does more additions than necessary: 17 for n = 8, 1,793 for 256, 9,217 for 1,024, against 7, 255 and 1,023 for a sequential loop. R1 Inside a warp, where all lanes work anyway, that does not matter; that is why F6-15's warp scan uses it.

Blelloch

The up-sweep is a reduction tree that leaves partial sums in place (after it, the last element is 25, the total). The root is set to 0, and the down-sweep passes starting values down: at each node, the left child receives the node's value and the right child receives the node's value plus the left child's old sum. The result is the exclusive scan, 0 3 4 11 11 15 16 22, with 14 additions for 8 elements, 510 for 256, 2,046 for 1,024: about 2n. R1 It takes twice as many steps as Hillis–Steele, each with a barrier when done in shared memory.

A practical block scan

Listing 3's blockInclusiveScan (lines 13–34) combines the two worlds: each warp scans its 32 values with shuffles (Hillis–Steele in registers); lane 31 of each warp writes the warp total to shared memory; after a barrier, warp 0 scans the warp totals; after another barrier, each warp adds the total of the warps before it. Two barriers per block, no bank conflicts, no second buffer. H1

Device-wide: reduce-then-scan

One block can only scan its tile. For the whole array, Listing 3's deviceScan (lines 58–75) does what Listing 2's reduceThenScan does on the CPU: scanTiles scans each tile and writes its total; the totals are scanned (recursively, by the same function); addOffsets adds to each tile the scanned total of the tiles before it. R2 The kernel boundaries order the passes; no block waits for another.

Layer 3 — the engineer's depth

The board-by-the-door story has one hidden condition, residency; the precise version follows.

Why a single pass

A scan does very little arithmetic per element; its speed is set by memory traffic (F6-09). Reduce-then-scan reads the input twice and writes the output once (the variant here: read, write, read and write again in addOffsets), plus the small middle pass. A single pass can read once and write once. Merrill and Garland's decoupled look-back achieves that while avoiding the serial chain of an older single-pass scheme, in which each tile waited for its predecessor's full prefix. S2 The CUB 2.0.1 header device_scan.cuh, read in this build, states that DeviceScan implements it and cites "Single-pass Parallel Prefix Scan with Decoupled Look-back", NVIDIA Technical Report NVR-2016-002, 2016. H2

The algorithm

Listing 2's lookback (lines 37–75) implements it with CPU threads standing in for blocks:

  1. A block takes the next tile number from an atomic counter (line 46), so tile t − 1 was taken before tile t.
  2. It reduces its tile and publishes status A with its aggregate (line 54; tile 0 publishes P directly).
  3. It looks back over tiles t − 1, t − 2, …: while a status is X it waits; it adds each value; it stops at the first P (lines 56–64).
  4. It publishes P with exclusive + aggregate (line 65), then writes its tile's outputs.

Status and value are packed into one 64-bit word (lines 16–20), so a reader never sees a status from one write and a value from another; the stores use release and the loads acquire ordering (F2-39). The threaded version passes every E4 size (1, 2, 255, 256, 257, 2^16 − 1, 2^16 + 1, 1,000,000) and input (random, sorted, reverse, all-equal) with 0 failures, as does reduce-then-scan. R2 CUB's version, read in this build, has the same three states plus an out-of-bounds state (SCAN_TILE_INVALID = 99, SCAN_TILE_PARTIAL, SCAN_TILE_INCLUSIVE) and waits with a warp vote, WARP_ANY(tile_descriptor.status == SCAN_TILE_INVALID, …) (R5): a whole warp inspects 32 predecessors at once. R5

Why it does not deadlock

A tile waits only for tiles with smaller numbers. If tile numbers were simply blockIdx.x, block 1,000 could be resident and spinning while block 999 has not been scheduled, and if all slots were filled with such waiters, nothing would progress (F6-12). Taking tile numbers from an atomic counter at the start of each block guarantees that every tile one waits for belongs to a block that has already started, and a started block runs to completion. S2 That forward-progress argument is the heart of the method.

Not verified — check before relying on this

Whether CUB 2.0.1 obtains tile numbers from an atomic counter or relies on another guarantee was not traced in its source during this build; Listing 2 uses a counter because it makes the argument above explicit. Also not checked: the memory-ordering primitives CUB uses on the GPU, and whether a started block is guaranteed to keep making progress while other blocks spin (the argument above assumes it). Check: cub/agent/agent_scan.cuh and single_pass_scan_operators.cuh in your CUB version, and S2.

Determinism

For integers, any correct scan gives identical results. For floats, the CUB 2.0.1 header states that results "are not deterministic for pseudo-associative operators (e.g., addition of floating-point types)" and "may vary from run to run", because the look-back may combine different groupings of predecessors. H2 E4 asks for results "identical to a CPU reference": that is achievable for integer keys and counts, and needs a tolerance for floats.

How the hardware actually does it

A block scan maps to hardware as in the previous chapters: shuffles inside warps (SHFL.UP), shared memory and BAR.SYNC between warps (F6-15). A device-wide scan adds two hardware facts. The tile status words live in global memory and are communicated through the L2 cache, the one level all SMs share, with fences ordering the payload before the status. D1 And the look-back relies on blocks that have started being able to finish: once resident, a block keeps its SM resources until it exits (F6-12). D1

Worked example

Task. Run Blelloch's down-sweep on the up-swept array 3 4 7 11 4 5 6 25 by hand.

  1. Clear the root: 3 4 7 11 4 5 6 0.
  2. d = 4: node 7 (value 0), left child 3 (value 11). Left gets 0; right gets 0 + 11 = 11: 3 4 7 0 4 5 6 11 (Listing 1 prints the same line). R1
  3. d = 2: pairs (1, 3) and (5, 7). Element 1 gets 0, element 3 gets 0 + 4 = 4; element 5 gets 11, element 7 gets 11 + 5 = 16: 3 0 7 4 4 11 6 16.
  4. d = 1: pairs (0,1), (2,3), (4,5), (6,7): 0 3 4 11 11 15 16 22, the exclusive scan.

Where the analogy breaks


    

  • Tables do not take numbers at the door. In the hall, table numbers are fixed; in a correct look-back, tile numbers are handed out in the order blocks start. The analogy hides the condition that prevents deadlock.
    • 

  • The board by the door is not instantly up to date. Writes to global memory become visible to other SMs only with the right ordering; a status could be seen before its value without fences or a single packed word.
    • 

  • Counting plates is integer arithmetic. A float scan's result depends on the grouping and can change between runs; plates cannot.
    • 




Common mistakes and debugging


    

  • Symptom: a block scan is right for 32 threads and wrong from index 32 for larger blocks (the forensic lab). Cause: Hillis–Steele in place, one buffer. Fix: two buffers, or a barrier between the read and the write of each step, or warp shuffles.
    • 

  • Symptom: off by one element everywhere. Cause: inclusive and exclusive confused. Fix: test the first and last output against std::inclusive_scan/std::exclusive_scan.
    • 

  • Symptom: wrong only for sizes that are not a multiple of the tile. Cause: threads past the end read garbage or skip barriers. Fix: load the identity past the end; test E4's 2^k ± 1 sizes.
    • 

  • Symptom: a hand-written single-pass scan hangs on large inputs. Cause: tiles numbered by blockIdx.x waiting for unscheduled blocks. Fix: dynamic tile numbers from an atomic counter.
    • 

  • Symptom: overflow in the totals. Cause: 32-bit sums of many elements. Fix: a wider output type.
    •

Summary


    

  • Inclusive includes the element; exclusive starts at the identity.
    • 

  • Hillis–Steele: log₂ n steps, ~n log₂ n additions; Blelloch: 2 log₂ n steps, ~2n additions.
    • 

  • Practical block scan: warp shuffles plus a scan of warp totals.
    • 

  • Device-wide: reduce-then-scan (three passes), or single-pass decoupled look-back (CUB).
    • 

  • Look-back waits only for tiles that started earlier: dynamic tile numbers make that true.
    • 

  • Integer scans are deterministic; float scans may vary run to run.

Forensic lab answer key


Observation. Warp 0 first: 223 of 256 wrong, first at index 32. Warp 7 first: 0 wrong. Shuffled orders: 214, 219, 204, 216 wrong, first always 32 (R4).


Hypotheses. The barrier between steps is present in the replay and the errors remain. Overflow is impossible with values up to 256. A race inside a step fits: the result depends on warp order.


Root cause. At d = 1, lane 0 of warp 1 (index 32) reads a[31], which lane 31 of warp 0 writes in the same step. If warp 0 runs first, index 32 adds the already updated value: a read-after-write within one step with no barrier between the read and the write. Inside one warp it cannot happen in the replay (all lanes read before any write), which is why 32-thread blocks passed.


Why warp 7 first works. Higher warps read before lower warps write, by luck of order. The hardware does not promise any order between warps, so a test that passes on one GPU proves nothing.


Fix. Two buffers (Listing 1, lines 12–18), or read into a register, __syncthreads(), then write, then __syncthreads(); or the warp-shuffle block scan of Listing 3. Prevention: test with the production block size; Compute Sanitizer racecheck; the rule of F6-12: every shared write that others read needs a barrier between.


How the evidence was produced: inplace_race.cpp (a CPU replay with a seeded warp order); no GPU was used. The within-warp "all lanes read before any lane writes" rule is a modelling assumption.
