Story hook

In the great kitchen hall, each group of rows works around one table. Today the group bakes a long line of flatbreads, and every flatbread gets a topping made from seven neighbouring bowls of spice paste: its own bowl and the three bowls on each side. Amira, the newest helper, walks to the far pantry seven times for every flatbread she tops. So does everyone else. The path to the pantry is jammed.

Then Kofi has an idea. Each helper fetches one bowl from the pantry and puts it on the group's table. A few helpers at the ends fetch the extra bowls just past the edges of the group's stretch. They all wait until the table is full. Now everyone reads their seven bowls from the table, which is right in front of them. The pantry path is quiet again, and the flatbreads come out faster.

The table is shared memory: a small, fast store that the threads of one block fill together, wait on together, and then read many times. This chapter teaches you to use it on purpose.

What you will be able to do

  • Explain what shared memory is, who can see it, how long it lives, and why a block uses it to turn many global reads into one.
  • Write a kernel that stages a tile with a halo in shared memory, with both a static and a dynamic shared array, and launch it correctly.
  • Compute the global reads saved by staging, and the shared memory a block needs, for a given block size and stencil radius.
  • Read a kernel's shared-memory use from the ptxas report and its LDS/STS/BAR.SYNC instructions from SASS.
  • Diagnose a stencil whose answers are wrong only at block edges.
Jargon box
Shared memory (GPU)
Simple words: a small, fast memory that the threads of one block share and fill themselves. Analogy: the table in the middle of a row group. Precise: on-chip memory allocated per thread block, declared with __shared__, visible to all threads of that block and only for the lifetime of the block; the kernel itself writes it, synchronises and reads it. Not the same as shared memory between processes (OS304). D1 D3
Tile
Simple words: the piece of a big array that one block copies to its table and works on. Analogy: the stretch of bowls one group puts on its table. Precise: a contiguous sub-block of the data, sized by the programmer, that a thread block stages in shared memory to reuse it (MA201 uses "tile" for a sub-block of a matrix). D3
Halo (ghost cells)
Simple words: the few extra values just outside a tile that the threads at its edges also need. Analogy: the extra bowls just past the ends of the group's stretch. Precise: the elements outside a block's output range that its computation reads; for a 1-D stencil of radius R, R elements on each side. D3
Stencil
Simple words: a calculation where every output uses a fixed pattern of nearby inputs. Analogy: every flatbread's topping uses the seven nearest bowls. Precise: out[i] = f(in[i−R], …, in[i+R]) for a fixed radius R; here f is a sum. D3
Static and dynamic shared memory
Simple words: a shared array whose size is fixed when you compile, or one whose size you choose when you launch. Analogy: a table built to one size, or a folding table opened to the size you ask for. Precise: a __shared__ array with a compile-time size, or an extern __shared__ array whose size in bytes is the third parameter of the execution configuration <<<grid, block, bytes>>>. D1
Barrier (__syncthreads)
Simple words: a "wait here until everyone in the block arrives" point. Analogy: nobody starts reading the table until every bowl is on it. Precise: a block-wide barrier: no thread of the block continues past it until all threads of the block have reached it, and shared-memory writes made before it are visible to the block after it. Full treatment in F6-12. D1

Layer 1 — the kid explanation

A group of helpers who all need the same ingredients should not each walk to the pantry. One trip per bowl is enough, if the bowl goes on the table where everyone can reach it. The only rule is patience: nobody may take from the table until everyone has put their bowl down. And the table is small, so each group only brings the bowls it needs right now.

Layer 2 — the student explanation

What shared memory is

Shared memory is memory declared with __shared__ inside a kernel. Every thread block gets its own copy; all threads of that block can read and write it; threads of other blocks cannot see it; and it disappears when the block finishes. D1 It is on-chip, unlike global memory, which lives in the GPU's device memory and is reached through caches (F1-58). D1 D3 Nothing moves into shared memory by itself: it is a scratchpad that the kernel manages, not a cache. D3

The pattern: load, barrier, compute

Almost every use of shared memory follows the same three steps. (1) Each thread copies a part of the data from global memory into the shared array. (2) The block waits at __syncthreads(), so that every part is written. (3) Each thread reads what it needs from the shared array, often many values, often values that other threads loaded. D1 Listing 1 does this for a 1-D stencil of radius 3: out[i] is the sum of in[i−3] to in[i+3]. Without shared memory, each output needs 7 global reads; neighbouring outputs read almost the same 7 values.

How many reads does staging save?

For a block of B threads and radius R, the direct version requests B(2R+1) global elements; the staged version requests B+2R. Listing 2 prints the ratio: for B = 256 and R = 3, 1,792 requests become 262, a factor of 6.84; for R = 32 it is 52.00. R2 The shared array costs (B+2R) × 4 bytes for ints: 1,048 bytes for B = 256, R = 3. R2

Watch out

"Requests" is not "trips to device memory". The GPU's caches may already serve many of the repeated reads of the direct version, so the real gain is smaller than the ratio and must be measured on your GPU (the lab's extension). What staging guarantees is that the reuse no longer depends on the cache's luck. D2

Static and dynamic shared arrays

A static array has its size in the source (__shared__ int tile[BLOCK + 2 * RADIUS];). A dynamic array is declared extern __shared__ int dtile[]; without a size, and the launch supplies the size in bytes as the third execution-configuration parameter: stencilDynamic<<<blocks, BLOCK, smem>>>(…). D1 Use dynamic shared memory when the size depends on a runtime value, here the radius. The ptxas report makes the difference visible: for sm_80, stencilStatic reports 1056 bytes smem, and stencilDynamic reports no static shared memory at all, because its size is only known at launch. R3

Not verified — check before relying on this

The array is 262 × 4 = 1,048 bytes, but ptxas reported 1,056. In check runs of modified copies (Lab Engineer's check run in scratch space; not in the recorded output), 258 ints (1,032 bytes) were reported as 1,040, while 264 ints (1,056 bytes) and 136 ints (544 bytes) were reported exactly. That pattern fits a rounding of the allocation up to a multiple of 16 bytes, but this build found no document that says so. Check: the ptxas and nvcc documentation for the toolkit in the lab log.

Layer 3 — the engineer's depth

In one line of analogy: the table is fast but small, and every group that sits in the hall needs its own table, so the size of your table decides how many groups fit.

Limits you must query, not assume

The amount of shared memory a block may use, and the amount an SM has in total, are properties of the device. The CUDA 12.0 headers read in this build describe them as sharedMemPerBlock ("Shared memory available per block in bytes"), sharedMemPerMultiprocessor ("Shared memory available per multiprocessor in bytes"), sharedMemPerBlockOptin ("the per device maximum shared memory per block usable by special opt in") and reservedSharedMemPerBlock ("the shared memory reserved by CUDA driver per block in bytes"). H1 A kernel that wants more dynamic shared memory than the default per-block amount must opt in through the function attribute cudaFuncAttributeMaxDynamicSharedMemorySize ("Maximum dynamic shared memory size"). H1 D1 This chapter quotes no values: read them for your GPU with the device query of F6-07.

Shared memory and occupancy

A block can become resident on an SM only if its shared memory fits beside the shared memory of the blocks already there; so shared memory per block is one of the limits on resident blocks, next to registers and thread slots (F1-58 computed this for the invented teaching GPU TG-1). D1 D3 A tile of 1 KiB rarely limits anything; a GEMM tile of tens of KiB often does (F6-22). The trade-off is reuse per block against blocks per SM.

Edges: the part that goes wrong

Three edges need code. (1) The halo: the first R threads load R extra elements on each side (Listing 1, lines 18–23). (2) The array ends: halo elements before index 0 or past n−1 are replaced by 0, the boundary rule chosen for this stencil. (3) The last block: when n is not a multiple of the block size, threads with g ≥ n still take part in the load and the barrier (they store 0) but write no output. A thread must never skip the barrier because it has no output: every thread of the block has to reach __syncthreads() (F6-12). D1

When shared memory is the wrong tool

Data read only once per block gains nothing from staging: the copy into shared memory is pure overhead. Data that every thread of the block reads at the same address may be better served by constant memory or a broadcast. And when the reuse is between neighbouring threads of one warp only, register shuffles (F6-15) avoid shared memory altogether. D2 D3

How the hardware actually does it

Shared memory is an SRAM inside each SM; it has its own address space and its own load and store instructions, separate from global memory. D1 The SASS of stencilStatic for sm_80 shows the whole pattern in machine code: LDG.E (global load), STS (store to shared), BAR.SYNC 0x0 (the barrier), seven LDS (loads from shared) and one STG.E (global store). R4 The immediate offsets match the source: STS [R9.X4+0xc] writes tile[s] with s = threadIdx.x + 3, so 3 × 4 = 12 = 0xc bytes past the thread's base; the right-halo store is at +0x40c = (256 + 3) × 4 = 1,036 bytes; the seven LDS read offsets 0x0 to 0x18, the seven neighbours 4 bytes apart; the right-halo global load reads +0x400 = 256 × 4 bytes past the thread's own element and the left one -0xc. R4 Shared memory is split into banks so that one warp's access can complete in one pass when the addresses spread over the banks; that is the subject of F6-11. D1

Worked example

Task. A stencil of radius R = 8 runs with 512 threads per block on int data. (a) How many global elements does one block request without and with staging? (b) How many bytes of dynamic shared memory must the launch pass? (c) On TG-1, the invented teaching GPU of F1-58 (32 KiB of shared memory per SM, at most 4 blocks per SM), does shared memory limit the resident blocks?

  1. Without staging: 512 × (2 × 8 + 1) = 512 × 17 = 8,704 requests.
  2. With staging: 512 + 2 × 8 = 528 requests. Ratio 8,704 / 528 = 16.48.
  3. Shared memory: 528 × 4 = 2,112 bytes, so the launch passes (512 + 2 * 8) * sizeof(int) = 2,112.
  4. TG-1: 32,768 / 2,112 = 15.5, so 15 blocks would fit by shared memory; the block limit of 4 is reached first. Shared memory does not limit this kernel there.

Steps 1–3 are the row 512 8 of Listing 2's output (8,704; 528; 16.48; 2,112). R2 TG-1 is invented; redo step 4 with your GPU's device-query values.

Where the analogy breaks


    

  • The table is wiped when the group leaves. Shared memory lives only as long as the block; the next block on the same SM cannot read what the last one left, and must not rely on what it finds there (the forensic lab of F6-17). D1
    • 

  • The table has drawers. Real shared memory is divided into banks; helpers reaching into the same drawer for different items wait in line. The kitchen story has no reason for this; F6-11 uses a picture instead.
    • 

  • Nobody "walks" to the pantry. A global load is an instruction that returns later while the warp does other work; repeated loads may also be served by caches. The story's "jammed path" exaggerates the saving; the real gain must be measured.
    • 




Common mistakes and debugging


    

  • Symptom: wrong outputs only near block boundaries (positions 0–2 and 253–255 of each block for R = 3). Cause: halo not loaded. How to find it: print the wrong indices modulo the block size (the forensic lab). Fix: load the halo; test with n spanning several blocks.
    • 

  • Symptom: results wrong sometimes, different from run to run. Cause: missing __syncthreads() between the load and the compute phase. How to find it: Compute Sanitizer's racecheck tool (F6-05). Fix: a barrier that every thread reaches.
    • 

  • Symptom: the program hangs, or the results are garbage, only in the last block. Cause: threads with g ≥ n return early, before the barrier. How to find it: look for return before __syncthreads(). Fix: let them load a neutral value and skip only the output write.
    • 

  • Symptom: a launch error, or out-of-bounds shared accesses. Cause: the dynamic size passed at launch is smaller than the kernel uses (for example forgetting the halo), or larger than the device allows without opting in. How to find it: check the launch error; compare with sharedMemPerBlock. Fix: compute the size from the same formula the kernel uses.
    •

Summary


    

  • Shared memory is per block, visible to all its threads, and lives as long as the block.
    • 

  • The pattern is load, barrier, compute: one global read serves many threads.
    • 

  • A 1-D stencil block of B threads and radius R requests B+2R elements instead of B(2R+1).
    • 

  • Static arrays have a compile-time size; dynamic ones get theirs from the third launch parameter.
    • 

  • Every thread must reach the barrier, including threads with no output.
    • 

  • The ptxas report and SASS (STS, BAR.SYNC, LDS) show what the compiler made of it, without a GPU.

Forensic lab answer key


Observation. Only thread positions 0, 1, 2, 253, 254 and 255 are wrong: 3,906 times each for 0, 1, 254, 255 and 3,551 times for 2 and 253, 22,726 outputs in total; the first wrong indices are 253–258, at the boundary between blocks 0 and 1.


Root cause. With R = 3, thread t reads tile cells t .. t+6. Threads 0–2 read the left-halo cells 0–2 and threads 253–255 read the right-halo cells 259–261; nobody wrote those cells, so they hold stale values. The replay shows stale values from the previous block; on a GPU the content is undefined.


Why the small test passed. 100 elements fit in one block. Its left halo lies before index 0, where the boundary rule wants 0, and in the replay the tile starts zero-filled, which happens to match; its last real outputs (97–99) read tile cells written by threads 100–102, which store 0 because they are past the end. On a GPU the unwritten left-halo cells hold undefined values, so even that pass was luck. Edge bugs need tests that span several blocks.


Wrong answers and why. "A missing barrier": a race gives different wrong values from run to run and at varying positions, not always the same six positions. "Grid too small": would leave the end of the array unwritten, not regular clusters.


Fix. Restore lines 18–23. Prevention: tests with n spanning many blocks and not a multiple of the block size; a check that prints wrong indices modulo the block size. How the evidence was produced: edges.cpp, both versions, same input as Listing 1.
