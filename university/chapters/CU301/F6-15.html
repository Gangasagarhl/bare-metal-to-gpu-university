Story hook

Every row in the hall has a habit the head of the hall never planned. When a helper needs a value from the helper beside them, they do not walk to the table, put it down, wait for the bell and pick it up again. They just hold out a hand, and the neighbour passes it over. When the row needs to know "is anyone still peeling?", nobody writes on the table: they all raise or lower a hand at once, and everyone sees the hands.

It works beautifully in Ravi's hall, where every row has 32 helpers. Then a team from the hall across the street, where rows have 64 helpers, borrows Ravi's recipe card. The card says "pass to the helper 16 places along, then 8, 4, 2, 1". In their long rows that adds up only half of the row. Nothing crashes, the total is just wrong.

Passing hand to hand is a shuffle; raising hands is a vote. This chapter teaches both, the rules of who gets which value, and how to write them so that they work on 32-lane NVIDIA warps and 64-lane AMD wavefronts alike.

What you will be able to do

  • Use the four shuffles (index, up, down, xor) and predict, lane by lane, what each returns, including at the edges of the warp.
  • Build warp reduce, warp all-reduce, warp inclusive scan and warp compaction from shuffles and votes.
  • Explain the mask argument of the _sync functions and why warp-synchronous code without it is unsafe.
  • Write warp-size independent code that runs correctly on 64-lane wavefronts, with 64-bit ballot masks.
  • Recognise shuffles and votes in PTX, SASS and AMD assembly.
Jargon box
Warp / wavefront
Simple words: the group of threads that the hardware runs together, 32 on NVIDIA, 32 or 64 on AMD. Analogy: a row of helpers. Precise: as defined in HW301 (F1-57); the width is warpSize, which in HIP 5.7 is a compile-time constant __AMDGCN_WAVEFRONT_SIZE. H3
Lane
Simple words: a thread's position in its warp, 0 to width − 1. Analogy: a helper's seat number in the row. Precise: threadIdx.x % warpSize for one-dimensional blocks. D1
Warp shuffle
Simple words: every lane reads a register value of another lane, all at once. Analogy: passing a value hand to hand along the row. Precise: __shfl_sync (from a given lane), __shfl_up_sync (from self − delta), __shfl_down_sync (from self + delta), __shfl_xor_sync (from self XOR mask), each with an optional width that splits the warp into independent segments. H1 D1
Warp vote (ballot)
Simple words: every lane gives a yes or no; the result tells every lane who said yes. Analogy: raising hands. Precise: __ballot_sync(mask, p) returns a bit mask with bit k set when lane k is in mask and its predicate is true; __all_sync and __any_sync reduce it to one bit. The same term as in HW301. H1
Participation mask
Simple words: the list of lanes that promise to take part in a warp operation. Analogy: the helpers who agreed to pass hands this round. Precise: the first argument of every _sync warp function; each named lane must execute the same call (with the same mask) before any of them gets the result; __activemask() returns the lanes currently executing, which is not the same as the lanes that should take part. D1 H1
Butterfly (XOR) shuffle
Simple words: lanes swap values with a partner whose number differs in one bit. Analogy: helpers swap with the helper opposite in their group of 2, 4, 8, … Precise: __shfl_xor_sync(m, v, k) pairs lane i with lane i XOR k; log₂ width steps give every lane the full reduction (all-reduce). R1
Warp-synchronous programming
Simple words: code that assumes the lanes of a warp move in lockstep. Analogy: assuming the whole row always moves in step, without anyone saying "now". Precise: an old practice (implicit synchronisation through shared memory inside a warp) that is unsafe since independent thread scheduling (compute capability 7.0); replace with _sync primitives or __syncwarp(). D1

The idea in pictures

Layer 1 — the kid explanation

Helpers in a row can hand things to each other without using the table. "Everyone, take what the person two seats to your right is holding." The two at the end have nobody there, so they keep what they have. And to ask a question of the whole row, everyone raises or lowers a hand at once. The only danger: if your recipe card assumes 32 seats and your row has 64, half the row is left out.

Layer 2 — the student explanation

Shuffle down: a warp reduction

Listing 1 is a simulator of one warp. Its first experiment fills 32 lanes with 1 to 32 and repeats v += shfl_down(v, off) for off = 16, 8, 4, 2, 1. Lane 0 ends with 528 = 32 × 33 / 2. The other lanes hold partial or meaningless values (lane 31 ends with 1,024, its own value doubled five times, because it never had a source). R1 That is fine: only lane 0's result is used, as in warpReduce of Listing 2 (lines 11–15).

Shuffle xor: everyone gets the answer

With shfl_xor and masks 16, 8, 4, 2, 1, every lane pairs with a partner and both add; after five steps all 32 lanes hold 528. R1 Use it when every lane needs the result (normalising by a warp's sum, for example); it costs the same five steps.

Shuffle up: an inclusive scan

For a prefix sum each lane adds the value d lanes below it, for d = 1, 2, 4, 8, 16, but only if such a lane exists (lane >= d). With every lane holding 1, lane i ends with i + 1 (R1, experiment 3). This is the Hillis–Steele scan of F6-16, done in registers. R1

Votes: ballot and population count

Experiment 4 keeps lanes whose value (100 + lane) is a multiple of 3. The ballot is 0x24924924: bits 2, 5, 8, …, 29, ten of them. Each kept lane finds its output slot by counting the kept lanes below it, popc(mask & ((1 << lane) − 1)), and the ten values land in slots 0 to 9 without gaps. R1 That is stream compaction inside a warp with no shared memory and no atomics; F6-13 used the same ballot to aggregate atomics.

The width argument

All shuffles take an optional width (a power of two up to the warp size) that splits the warp into independent segments. Experiment 5 uses width 16: lane 0 ends with 136 (the sum of 1..16) and lane 16 with 392 (17..32), two reductions in one instruction stream. R1

Layer 3 — the engineer's depth

In hall terms: who must hold out a hand, and how long the row really is. Both have precise rules.

The mask and independent thread scheduling

The CUDA 12.0 header sm_30_intrinsics.h, read in this build, declares the shuffles as __shfl_down_sync(unsigned mask, T var, unsigned int delta, int width=warpSize) and similar, the votes __ballot_sync(unsigned mask, int pred), __all_sync, __any_sync, plus __activemask() and __syncwarp(unsigned mask=0xFFFFFFFF). H1 Since compute capability 7.0, lanes of a warp may be scheduled independently, so the programming guide requires that every lane named in mask executes the same _sync call; the call then acts as a synchronisation point for those lanes. D1 Two consequences:

  • A shuffle inside an if that only some lanes enter, with the full mask, is undefined. Shuffle unconditionally, then use the result conditionally (Listing 2, lines 27–28).
  • Old code that passed values through shared memory inside a warp without any barrier, relying on lockstep execution, is broken; insert __syncwarp() or use shuffles.

__activemask() only reports which lanes happen to be executing together now; using it as the mask of a shuffle does not make a divergent shuffle meaningful. D1

Edge rules

Listing 1's lane selection is copied from the HIP 5.7 header amd_warp_functions.h, read in this build: __shfl_down keeps its own value when (self & (width−1)) + delta >= width; __shfl_up when self − delta lies below the start of the segment; __shfl_xor when the partner lies beyond the segment. H3 CUDA's guide describes the same behaviour for up and down ("does not wrap around"), and wrapping modulo width for __shfl_sync with an out-of-range source lane. D1

Not verified — check before relying on this

That CUDA's edge behaviour matches the HIP header rules simulated here was taken from the programming guide's description (D1, title only), not tested on an NVIDIA GPU; Listing 2's checks avoid the edge cases by using lane 0's result only. Also not checked: what happens on a GPU when a lane named in the mask does not reach the call (undefined behaviour; it may hang or return garbage). Check: run Listing 2 on a GPU, and the "Warp Shuffle Functions" and "Warp Vote Functions" sections of D1 for your toolkit.

64-lane wavefronts: what breaks

Many AMD GPUs run 64-lane wavefronts; the gfx90a target used in this build reports .wavefront_size: 64 (R5). R5 D5 Experiment 6 of Listing 1 runs CUDA-style code on 64 lanes: R1

  • a reduction loop starting at offset 16 (hard-coded) gives lane 0 = 32 instead of 64: the upper half of the wavefront is never added;
  • starting at warpSize / 2 gives 64;
  • a ballot of 64 true lanes copied into a 32-bit variable has a population count of 32 instead of 64.

In HIP 5.7, __ballot returns unsigned long long and __popcll counts it; there are no _sync variants and no mask argument in that header. H3 Listing 3 is the HIP version: warpSize / 2 in the loop, a 64-bit mask, and the host asks the device for its wavefront size (line 43) instead of assuming. Hidden 32s also hide in lane = tid & 31, warp = tid >> 5, 0xffffffff masks, and shared arrays sized BLOCK / 32. E3's last criterion, "no hidden 32-lane assumption", is about exactly these lines.

Not verified — check before relying on this

Untested on hardware. Listing 3 was built for gfx90a and its assembly read (R5), but it was not run: the run stopped at hipGetDevice with hipErrorInvalidDevice (R4). Which AMD families use wave32 or wave64 by default was not checked in this build. Check: the AMD ISA guide for your architecture and prop.warpSize on your device.

A reduction instruction

__reduce_add_sync(mask, value), declared for compute capability 8.0 in crt/sm_80_rt.h, reduces 32 integer lanes in one call; Listing 2's hardwareReduce (lines 52–61) uses it, and the PTX and SASS show redux.sync.add.s32 / REDUX.SUM.S. H1 R2 It exists for integer types only (in this header), and only on NVIDIA.

How the hardware actually does it

On NVIDIA (sm_80), each kind of shuffle is one SASS instruction: SHFL.DOWN, SHFL.UP, SHFL.BFLY (xor; "butterfly"), and the full-index form SHFL.IDX; votes are VOTE.ANY (which, despite the name, also delivers the ballot), and the count is POPC (R3). R3 On AMD (gfx90a), HIP 5.7 builds the shuffles on __builtin_amdgcn_ds_bpermute, which compiles to ds_bpermute_b32, a cross-lane permute that goes through the LDS hardware without allocating LDS: six of them appear in waveTests, one per reduction step for 64 lanes. The ballot is a vector compare that writes a 64-bit scalar mask, and s_bcnt1_i32_b64 counts its bits; the kernel metadata says .wavefront_size: 64 (R5). H3 R5 So a shuffle costs one instruction on NVIDIA, a permute through the LDS crossbar on AMD; both avoid shared-memory allocation and barriers.

Worked example

Task. Compute, for a warp of 32 lanes holding 1..32, what lanes 0 and 31 hold after the step with offset 16 of a shfl_down reduction, and after all five steps.

  1. Offset 16: lane 0 reads lane 16 (value 17): 1 + 17 = 18. Lane 31 reads lane 47, outside the warp, so it keeps its own: 32 + 32 = 64. Listing 1 prints 18 and 64. R1
  2. Offset 8: lane 0 reads lane 8, which after step 1 holds 9 + 25 = 34: 18 + 34 = 52 (printed). Lane 31 doubles again: 128.
  3. After all five: lane 0 = 528, the sum; lane 31 = 32 × 2^5 = 1,024, meaningless.
  4. Lesson: only lane 0 is valid. For an all-reduce use xor; for a value in every lane after a down-reduction, broadcast it: __shfl_sync(FULL, v, 0).

Where the analogy breaks


    

  • Everyone passes at once, and everyone must. In the hall a helper can pass a bowl while the neighbour is busy. A shuffle is one instruction for the whole warp: all lanes named in the mask take part, or the result is undefined.
    • 

  • Hands do not reach further than the row, but they reach any seat. A shuffle can read any lane of the warp (or of the segment), not only neighbours; it cannot reach another warp at all.
    • 

  • Raising hands produces a number. A ballot is not a visual impression but an exact bit mask that every lane receives, and that can be counted and indexed.
    • 




Common mistakes and debugging


    

  • Symptom: a warp sum is right in lane 0 but code reads it in another lane. Cause: down-reduction leaves only lane 0 valid. Fix: xor-reduction, or broadcast with __shfl_sync(mask, v, 0).
    • 

  • Symptom: hang or garbage after adding a condition around a shuffle. Cause: lanes in the mask did not reach the call. Fix: shuffle unconditionally; use the value conditionally.
    • 

  • Symptom: correct on NVIDIA, half the answer on AMD. Cause: loop from 16, & 31, >> 5, or a 32-bit ballot variable. Fix: warpSize, 64-bit masks; test on wave64.
    • 

  • Symptom: old reduction code gives wrong results on newer GPUs. Cause: implicit warp-synchronous shared-memory steps without volatile or __syncwarp. Fix: shuffles, or __syncwarp() between steps.
    • 

  • Symptom: wrong scan values in the first lanes. Cause: adding the shuffled value without the lane >= d test. Fix: as Listing 2, line 28.
    •

Summary


    

  • Shuffles read another lane's register: index, up, down, xor; lanes without a source keep their own value.
    • 

  • Down-reduction: result in lane 0; xor-reduction: in every lane; up: inclusive scan.
    • 

  • Ballot + popc: counting and compaction inside a warp.
    • 

  • Every lane in the mask must execute the _sync call; lockstep is not guaranteed.
    • 

  • Write warpSize, not 32; ballots are 64-bit on wave64.
    • 

  • NVIDIA: SHFL.*, VOTE, REDUX; AMD: ds_bpermute_b32, 64-bit scalar masks.
    •

Forensic lab answer key


Observation. Hard-coded loop: lane 0 = 32 (expected 64). Width-derived loop: 64. Population count: 64 for the 64-bit mask, 32 for the 32-bit copy (R1).


Hypotheses. hipify translates names, not literals, so it is not the translation itself. Integer sums and counts have no rounding, so it is not floating point. The "exactly half" pattern on a 64-wide device (R5) points to a 32-lane assumption.


Root cause. (1) for (int off = 16; …): the reduction never adds the upper 32 lanes into lane 0. (2) unsigned mask = __ballot(…): HIP's __ballot returns unsigned long long (H3), and the conversion to 32 bits drops lanes 32–63.


Fix. for (int off = warpSize / 2; off > 0; off /= 2) and unsigned long long mask = __ballot(p); … __popcll(mask) (Listing 3, lines 11 and 22). Prevention: run the simulator (or CI) at width 64; grep for literal 16, 31, 32, 0xffffffff and >> 5 in device code; review rule "lane masks have a platform-defined type".


How the evidence was produced: warp_sim.cpp (CPU simulation with the HIP header's rules) and run.sh (AMD assembly); no AMD GPU was used.
