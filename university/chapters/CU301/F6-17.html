Story hook

The hall is sorting a delivery of 60 crates of fruit by kind: apples, pears, plums, and so on, 256 kinds in all. On the wall by the door hangs one tally board with a counter for every kind. Amara's first plan: every helper opens a crate, takes one fruit, walks to the wall and clicks the counter for its kind. It is correct, and it is slow. The walk is long, and when a crate is full of apples, every helper queues at the same apple counter.

Kenji suggests a change. Each table gets its own small tally sheet, lying on the table in the middle of the row. Helpers click the counters on their table's sheet, a few steps away. When a table has finished all its crates, one helper per kind carries the table's count to the wall and adds it in one click. The wall now sees one click per table and kind, not one per fruit.

That is privatization, and it is the whole idea of this chapter. The details are where it goes wrong: a sheet that was not wiped before use, a table that only had one crate to count, and a wall counter that still gets a queue when all the fruit is apples.

What you will be able to do

  • Write a 256-bin byte histogram three ways: global atomics, shared-memory privatized bins per block, and privatized bins with a grid-stride loop.
  • Count how many global atomic operations each version issues and how many land on the busiest address, for uniform, skewed and constant inputs, and explain the difference.
  • Explain why the three steps of a privatized histogram (zero, count, merge) each need a barrier between them.
  • Test a histogram on milestone E4's sizes and input kinds and compare it with CUB's DeviceHistogram.
  • Diagnose a privatized histogram whose totals grow with the input size (the forensic lab).
Jargon box
Histogram
Simple words: a count of how many items fall into each category. Analogy: the tally board by the door, one counter per kind of fruit. Precise: for input values xi and a bin function b(x) with B possible results, the array h[k] = |{ i : b(xi) = k }|, k = 0 … B − 1; the bins add up to the number of items. D3
Bin
Simple words: one category of a histogram and its counter. Analogy: the counter for "plums". Precise: one element h[k]; in CUB's HistogramEven, bins are equal-width ranges between a lower and an upper level, and "the number of histogram bins is (num_levels - 1)" (quoted from the installed header). H2
Privatization
Simple words: each group keeps its own private copy of the counters and adds it to the shared result once at the end. Analogy: a tally sheet on each table, carried to the wall when the table is done. Precise: replicate the output (here the B bins) per block (or per warp or thread), update the copies with low contention, then merge them into the global result; correct for any associative and commutative update. D3
Merge (of private bins)
Simple words: adding a private copy into the global counters. Analogy: one helper per kind walks the table's count to the wall. Precise: after a barrier, threads of the block each take some bins and do atomicAdd(&global[b], local[b]), skipping zeros; at most B global atomics per block. R1
Contention (in a histogram)
Simple words: many updates aimed at the same bin at the same time. Analogy: the queue at the apple counter when every crate is apples. Precise: atomic updates to one address are serialised (F6-13); its cost depends on the input's distribution, so a histogram's speed depends on its data. D1 D3
Skewed input
Simple words: input where a few values are far more common than the rest. Analogy: a delivery that is nine-tenths apples. Precise: in this chapter, a test input where 9 of every 10 bytes are 0 and the rest are spread over all 256 values (Listing 2's sample, kind 1). R2

Layer 1 — the kid explanation

Counting things is easy for one person. When many helpers count at once, they all want the same counters. If they all walk to one board, they queue. If every table keeps its own small sheet, the queues are short and close by. At the end, each table adds its sheet to the board once. Two rules keep the count right: wipe the sheet before you start, and do not carry it to the board until everyone at the table has finished counting.

Layer 2 — the student explanation

Version 1: one global atomic per element

The simplest GPU histogram gives one thread to each byte and does atomicAdd(&bins[in[i]], 1u) on the global bins (Listing 1, lines 17–21). It is correct, because an atomic read-modify-write cannot lose an update (F6-13). D1 For 2^26 bytes it issues 67,108,864 global atomics, one per byte, whatever the data. R2 What changes with the data is how many land on the same address. For the uniform input, the busiest bin receives 262,148; for the skewed input (90 % zeros), bin 0 receives 60,424,194; for an input of one repeated byte, all 67,108,864 go to one bin. R2 Updates to one address are serialised, so the same kernel can be fast on one input and slow on another. D3

Version 2: privatized bins in shared memory

Listing 1's histShared (lines 23–34) gives every block 256 counters in shared memory. Step 1 zeroes them (line 26); a barrier (line 27) makes sure no thread counts into a bin that another thread has not yet zeroed; step 2 counts with shared-memory atomics (line 29); a second barrier (line 30) makes sure all counting is done; step 3 merges, each thread taking bins threadIdx.x, threadIdx.x + blockDim.x, … and skipping empty bins (lines 31–33). R1 The ptxas report confirms the cost: 1,024 bytes of shared memory per block (256 four-byte counters) for the two privatized kernels, none for histGlobal. R4

Does it help? Listing 2 counts exactly. With one byte per thread and 256 threads per block, each block sees only 256 bytes. For uniform data most of those are different, so a block has many non-empty bins and merges almost all of them: 58,025,860 global atomics, barely fewer than the 67,108,864 of version 1. For skewed data the merges drop to 6,347,595 and the busiest global address falls from 60,424,194 to 262,144 operations (one per block). R2 Privatization helps exactly when a block's private copy absorbs many updates per bin, and that needs many elements per block.

Version 3: privatized bins and a grid-stride loop

histStride (lines 36–49) launches a fixed number of blocks (four per SM in Listing 1, line 96) and lets each thread walk the input with the grid-stride loop of F6-14 (lines 41–44). Each block now counts thousands of bytes before it merges. Listing 2 models 320 blocks: the merges fall to 81,920 for every input (320 blocks × 256 bins at most), and the busiest global address receives at most 320. R2 The global traffic of the merge becomes negligible next to reading 2^26 input bytes. What remains is the contention inside each block: for skewed data, the busiest shared bin in a block of 256 bytes receives 233 updates; for constant data, 256, meaning every thread of the block queues on one shared counter. R2

Correctness first: E4's cases

Milestone E4 asks for "results identical to a CPU reference for random, sorted, reverse-sorted and all-equal inputs, including sizes 1, 2^k−1, 2^k+1". C1 For integer counts, "identical" is the right standard: integer addition is associative and commutative, so the order of the atomics cannot change the result. Listing 3 replays histStride block by block with an odd grid of 7 blocks and checks 9 sizes, including 1,791 and 1,793 on either side of 7 × 256, against a plain count: 36 cases, 0 failures. R3

Layer 3 — the engineer's depth

The tally-sheet story says nothing about how big a sheet may be or who wipes it; the engineering is in those questions.

Levels of privatization

Private copies can live at several levels: per block in shared memory (this chapter), per warp (several copies in shared memory, more space, less contention), per thread in registers (only for a handful of bins), or per block in global memory when the bins do not fit in shared memory. D3 CUB's histogram agent makes the same choice explicit: its policy has a parameter described in the installed header as "Whether to prefer privatized shared-memory bins (versus privatized global-memory bins)", and PRIVATIZED_SMEM_BINS, where "Zero indicates privatized counters to be maintained in device-accessible memory". H2 Its shared array is declared histograms[NUM_ACTIVE_CHANNELS][PRIVATIZED_SMEM_BINS + 1] "(with 1 word of padding)": the bank-conflict padding of F6-11 in a production library. R6

The shared-memory budget

256 four-byte counters cost 1,024 bytes per block (R4). A 4,096-bin histogram per block costs 16 KiB, per warp 16 KiB times the warps per block; at some point the private copies limit how many blocks fit on an SM (F6-10), and smaller counters (16-bit, flushed before they overflow) or global privatization become the better trade. The point where that happens depends on your GPU's shared-memory size; measure it rather than assume it.

Contention inside the block

For constant input, every thread of a block hits one shared bin. Two remedies come from earlier chapters. Warp aggregation (F6-13, F6-15): lanes with the same value elect a leader with __match_any_sync and the leader adds the count of its group in one atomic. Per-warp copies: each warp counts in its own sub-histogram, so contention is at most 32 lanes. The compiler already does something on its own: the SASS of histShared shows the shared-memory counting step as ATOMS.POPC.INC.32, not a plain add. R5

Not verified — check before relying on this

The meaning of the .POPC.INC suffix of ATOMS was not looked up in this build. The name suggests that the compiler counted, with a population count, how many active lanes increment by 1, and that lanes with equal addresses are combined, but NVIDIA's SASS instruction list was not opened. Do not rely on the compiler to aggregate for you until you have measured it. Check: the CUDA binary utilities documentation (instruction set reference for your architecture), and a GPU timing of Listing 1 on constant input with and without explicit warp aggregation.

Thread coarsening and input loading

The grid-stride loop is a form of thread coarsening: each thread does more work so that the fixed per-block costs (zeroing and merging 256 bins, two barriers) are paid less often. D3 The loads are bytes; one byte per thread per iteration gives a warp 32 consecutive bytes, coalesced but small. Loading four bytes as one 32-bit word (or sixteen as a vector) and counting them in registers reduces load instructions, at the cost of tail handling. That is a tuning step for your E4 report, not a correctness step.

How the hardware actually does it

Shared-memory atomics are carried out by the SM on its own shared memory; global atomics are carried out at the memory side, in the L2 cache, which is why they are coherent across SMs and why many of them to one address serialise there (F6-13). D3 The compiled kernels show the two kinds side by side: histGlobal uses RED.E.ADD.STRONG.GPU (a global reduction with no returned value, at GPU scope), while histShared counts with ATOMS.POPC.INC.32 on shared memory between two BAR.SYNC barriers, and its merge again uses RED.E.ADD.STRONG.GPU. R5 The global bins are only 1 KiB in total, small enough that they are likely to stay in the L2 cache; if so, the cost of version 1 is not DRAM traffic for the bins but the serialisation of updates to the same few cache lines. (Not measured in this build: a profiler on a GPU can confirm it.)

Worked example

Task. 16 values with 4 bins, 2 blocks of 8 threads. Block 0 sees 0 1 1 3 0 0 2 1; block 1 sees 3 3 3 3 0 3 3 1. Count the global atomics and the busiest global address for the global and the privatized versions, and the busiest shared bin.

  1. Global version. 16 global atomics, one per value. Bin 3 receives 1 + 6 = 7 of them: the busiest address.
  2. Block 0's local bins. bin 0: 3, bin 1: 3, bin 2: 1, bin 3: 1. All four non-empty: 4 merges.
  3. Block 1's local bins. bin 0: 1, bin 1: 1, bin 2: 0, bin 3: 6. Three non-empty: 3 merges (bin 2 is skipped).
  4. Privatized totals. 4 + 3 = 7 global atomics instead of 16; bins 0, 1 and 3 each receive 2 merges, bin 2 receives 1: the busiest address now sees 2 operations instead of 7.
  5. Busiest shared bin. Block 1's bin 3 receives 6 of its 8 updates: the queue has moved from the wall to the table, and it is shorter.
  6. Check. Global bins: 4, 4, 1, 7; sum 16, the number of values.

Where the analogy breaks


    

  • The tally sheet is not wiped by anyone. In the hall, a new table starts with a clean sheet. On a GPU, shared memory is not cleared between blocks; a block that skips step 1 starts with whatever is there (the forensic lab).
    • 

  • The walk to the wall is not the main cost. The global bins are small and are likely to stay in the L2 cache; what costs time is many updates on the same few addresses, not distance.
    • 

  • Helpers at one table do not really click one at a time. A warp issues one atomic instruction for 32 lanes, and the hardware or compiler may combine lanes with equal addresses (R5, unverified); the queue is per instruction and per address, not per helper.
    • 




Common mistakes and debugging


    

  • Symptom: totals larger than the number of elements, growing with the input size. Cause: private bins not zeroed. How to find it: check that the bins sum to n, on a size with more blocks than the GPU can hold at once. Fix: step 1 and a barrier.
    • 

  • Symptom: counts slightly too small, varying between runs. Cause: the barrier between counting and merging is missing, so some threads merge bins others are still counting. How to find it: Compute Sanitizer racecheck (F6-12). Fix: __syncthreads() before the merge.
    • 

  • Symptom: correct, but no faster than the global version. Cause: one element per thread; blocks are too small to absorb updates (Listing 2, uniform input). Fix: a grid-stride loop with a fixed grid.
    • 

  • Symptom: fast on random data, slow on real data. Cause: skew; contention on one bin. Fix: per-warp copies or warp aggregation; always test the all-equal input.
    • 

  • Symptom: bins wrong only for some values. Cause: signed char input used as an index (negative indices). Fix: unsigned char, as Listing 1.
    • 

  • Symptom: occupancy drops after increasing the number of bins. Cause: shared memory per block. Fix: read the ptxas report; consider 16-bit counters or global privatization.
    •

Forensic lab answer key


Observation. Sizes 256 (1 block) and 1,024 (4 blocks) are right. From 4,096 on, totals are too large: 10,240 instead of 4,096; 2,129,920 instead of 65,536; 537,395,200 instead of 1,048,576 (R7). The error grows much faster than n.


Hypotheses. A missing barrier would lose or duplicate a few counts at random, not inflate totals by hundreds of times. Overflow would make totals smaller or wrap, not grow. Unzeroed bins fit: each block adds its predecessors' leftovers again.


Why small sizes pass. With at most 4 blocks, each SM runs one block, which finds the zeroed memory the replay starts with. From 16 blocks, each SM runs 4 blocks in turn and every block starts with the previous block's counts, which it merges again: the leftovers are counted over and over, so the error grows roughly with the square of the number of blocks per SM.


On a real GPU. The initial content of shared memory is undefined: it may be zeros the first time, leftovers of another block or of another kernel. The error pattern would differ between runs and GPUs, which makes the bug look random.


Fix. Zero the private bins (Listing 1, line 26) and put a barrier after it (line 27). Prevention: test sizes with many more blocks than SMs; assert that the bins sum to n; check in the Compute Sanitizer documentation whether its initcheck tool covers uninitialised shared memory in your version (not verified in this build).


How the evidence was produced: stale_bins.cpp, a CPU replay with a deterministic choice of "previous block's leftovers"; no GPU was used. That a real GPU leaves leftovers in exactly this pattern is a modelling assumption.
