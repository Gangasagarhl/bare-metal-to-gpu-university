Story hook

At Ravi's table the helpers work in rounds: each puts a bowl on the table, then takes the bowl of the helper to their left. The table has one rule, a bell. When you have put your bowl down, you wait at the bell; when the last helper of the table arrives, everyone continues. Without the bell, a quick helper sometimes grabs an empty spot, or yesterday's bowl.

One day the head of the hall wants every table in the hall to finish round one before anyone starts round two. "Easy," says Ravi, "a bell for the whole hall." But the hall is full. Some tables are still waiting outside the door for a free place, and they will only get one when a table inside finishes. The tables inside wait at the hall bell for the tables outside; the tables outside wait for the tables inside to leave. Nobody moves again.

The table bell is __syncthreads(). The hall bell that freezes everything is a home-made grid-wide barrier. This chapter shows why the first is cheap and safe, why the second is dangerous, and what CUDA offers instead.

What you will be able to do

  • State exactly what __syncthreads() guarantees: every thread of the block arrives, and shared-memory writes before it are visible after it.
  • Place barriers correctly in multi-phase kernels, including the second barrier before a shared buffer is reused.
  • Explain with a residency argument why a spinning barrier across all blocks can hang, and name the two safe alternatives.
  • Use a cooperative launch with cooperative_groups::this_grid().sync(), sized by the occupancy calculator.
  • Diagnose a kernel that hangs only when the grid is larger than the GPU can hold at once.
Jargon box
Barrier (__syncthreads)
Simple words: a "wait here until everyone in the block arrives" point. Analogy: the table's bell. Precise: a block-wide barrier: no thread of the block continues until all threads of the block have reached it, and global and shared memory accesses made by the block's threads before it are visible to all of the block's threads after it. It must be reached by every thread of the block. D1
Race (data race, GPU)
Simple words: two threads touch the same memory, at least one writes, and nothing fixes their order. Analogy: grabbing a neighbour's bowl without waiting for the bell. Precise: conflicting accesses not ordered by synchronization; the result depends on scheduling. The same idea as in SP203 (F2-35), now between GPU threads. D1 D3
Residency
Simple words: a block is resident when it has a place on an SM and can run. Analogy: a table that is inside the hall, not waiting outside. Precise: a block occupies an SM's registers, shared memory and thread slots from its start until it finishes; blocks beyond what all SMs can hold wait until resident blocks finish, and the programming model does not let you assume any order or co-residency between blocks. D1
Grid-wide barrier
Simple words: a point that all threads of all blocks must reach before any continues. Analogy: a bell for the whole hall. Precise: safe only when every block of the grid is resident at the same time; CUDA provides it through cooperative groups (this_grid().sync()) for kernels started with a cooperative launch. D1 H1
Cooperative launch
Simple words: a special way to start a kernel that promises all its blocks run at once. Analogy: asking for the whole hall, and only being let in if every table fits. Precise: cudaLaunchCooperativeKernel; the device must report the cooperative-launch attribute, and the number of blocks may not exceed the occupancy calculator's blocks per SM times the number of SMs. H1
Memory fence (__threadfence)
Simple words: an instruction that orders a thread's own memory writes as others see them, without waiting for anybody. Analogy: putting the bowl down firmly before raising your hand, so whoever sees the hand also sees the bowl. Precise: orders the calling thread's memory accesses before and after it as observed by other threads (block, device or system scope for the three variants); unlike a barrier it waits for no other thread. Compare the C++ fences of F2-39. D1 H1

The idea in pictures

Layer 1 — the kid explanation

A bell works when everyone who must ring it is in the room. At one table, everyone is always in the room, so the table's bell is safe. The whole hall is different: if not all tables fit inside at once, a bell for the whole hall can trap everyone forever. So you either ask for a hall where every table fits, or you end the shift: when one job is completely finished, the next job starts, and that end is the hall-wide bell.

Layer 2 — the student explanation

What __syncthreads() guarantees

Two things. Execution: no thread of the block passes the barrier until every thread of the block has reached it. Memory: the global and shared memory accesses that the block's threads made before the barrier are visible to all threads of the block after it. D1 Both matter. The first stops a fast warp from reading a tile that a slow warp has not filled; the second ensures that what was written is what is read. The compiler turns it into bar.sync 0 in PTX and BAR.SYNC 0x0 in SASS (R4, and the listings of F6-10). R4

Where barriers go: count the phases

Listing 1 is an exhaustive check on a tiny "block" of four threads. Each thread writes s[t] and reads its neighbour's s[(t + 1) % 4]; the explorer tries every possible interleaving of the steps and counts wrong answers. R1

  • No barrier (WR): 1,432 of 2,520 orders are wrong.
  • Barrier between write and read (WBR): 0 of 576 wrong.
  • Two rounds reusing s, a barrier only after each write (WBRWBR): 824,832 of 1,451,520 wrong, because a fast thread overwrites s[t] for round 2 while its neighbour still needs the round-1 value.
  • Two rounds with a barrier after the write and after the read (WBRBWBR): 0 of 331,776 wrong.

The rule that follows: a shared buffer that is written, read, and written again needs a barrier after each write (read-after-write) and one after the last read before the next write (write-after-read). Loops over tiles, as in GEMM (F6-22), need both. D3

Every thread must arrive

A barrier inside a branch that only some threads of the block take is not allowed: the programming guide requires __syncthreads() in conditional code only when the condition evaluates identically across the whole block. D1 Otherwise the kernel may hang or behave unpredictably. The usual offender is an early return for threads past the end of the data, placed before a barrier (F6-10's mistakes). Compute Sanitizer has a tool that checks barrier use (synccheck) and one that finds shared-memory races (racecheck) (F6-05). D4

Barrier variants

The CUDA 12.0 headers read in this build declare __syncthreads_count(int), __syncthreads_and(int) and __syncthreads_or(int), which are barriers that also combine one predicate per thread over the block (count, all, any), and __syncwarp(unsigned mask=0xFFFFFFFF), a barrier for the lanes of one warp named in the mask. H1 D1 F6-18 uses __syncthreads_count to count the keys of a block in one step.

Layer 3 — the engineer's depth

In one line of analogy: the table bell is free because the table is in the room by construction; the hall bell is only safe if you are guaranteed that all tables are in the room together.

Why there is no simple grid barrier

Blocks of one grid are independent by design: the hardware may run them in any order, concurrently or one after another, which is what lets the same kernel run on GPUs of any size. D1 A barrier across blocks breaks that assumption. If the grid has more blocks than the device can hold at once, resident blocks that spin at the barrier keep their slots, and the waiting blocks can never start. Listing 2 simulates it on TG-1 (invented: 2 SMs × 4 resident blocks = 8 slots): grids of 4 and 8 blocks finish; grids of 9, 16 and 64 blocks hang with 8 blocks spinning and 1, 8 and 56 blocks never resident. R2 Even a grid that fits is not safe with a home-made barrier unless all of its blocks are guaranteed to be resident together (another kernel or process may hold slots), and the barrier also needs correct memory ordering (fences). D1

The two safe answers

1. End the kernel. Kernels launched into the same stream run in order, so the end of one kernel is a barrier for the whole grid, with all its memory writes visible to the next kernel. D1 Listing 3, variant A, splits a sum into phase1 (per-block partial sums) and phase2. It costs a launch, and shared memory and registers do not survive the boundary. Most multi-pass algorithms in this course (reduce-then-scan in F6-16, radix sort in F6-18) use this answer.

2. A cooperative launch with a grid group. The CUDA 12.0 header comment of cudaLaunchCooperativeKernel, read in this build, describes it as a launch "where thread blocks can cooperate and synchronize as they execute"; the device must have a non-zero cudaDevAttrCooperativeLaunch, and "the total number of blocks launched cannot exceed the maximum number of blocks per multiprocessor as returned by cudaOccupancyMaxActiveBlocksPerMultiprocessor … times the number of multiprocessors"; a launch that is too large returns cudaErrorCooperativeLaunchTooLarge. H1 Inside, cooperative_groups::this_grid().sync() is the grid barrier. D1 Listing 3, variant B, sizes the grid exactly by that rule and uses a grid-stride loop (F6-14) so that a grid of any size covers the input. This is the residency argument of Figure 1, turned into an API contract.

What a grid barrier costs

The SASS of bothPhases (Evidence R3) shows what this_grid().sync() compiles to in CUDA 12.0 for sm_80: a block barrier (BAR.SYNC), a device-scope fence (MEMBAR.ALL.GPU), one atomic add per block on a counter (ATOM.E.ADD.STRONG.GPU, issued by one lane), a polling loop of strong loads (LD.E.STRONG.GPU) with YIELD and a branch back, and a final block barrier. Before it there is a BPT.TRAP on a path guarded by a check of a launch parameter. R3 In other words, it is the "counter and spin" barrier of the story, made safe by the launch-size rule, plus fences.

Not verified — check before relying on this

That the BPT.TRAP path fires when the kernel was not launched cooperatively is an interpretation of the SASS, not a documented fact checked in this build. Also not checked: the exact memory-ordering guarantees of grid.sync(), and whether a separate compiler option is needed for grid groups in other toolkit versions (CUDA 12.0 compiled Listing 3 without one, R5). Check: the CUDA C++ Programming Guide, "Cooperative Groups" (grid synchronization and its requirements), for your toolkit version.

Fences are not barriers

__threadfence_block(), __threadfence() and __threadfence_system() order the calling thread's own writes as seen by others at block, device and system scope; they do not wait for any other thread. D1 H1 They are the building block for "publish, then flag" protocols between blocks, such as the last-block-done reduction and the decoupled look-back of F6-16, where one block waits only for blocks that are guaranteed to have started before it.

How the hardware actually does it

A block lives on one SM for its whole life, so a block barrier is a local affair: the SM counts the warps of the block that have arrived at barrier 0 and releases them when all have; waiting warps simply are not scheduled, which costs no other warp anything (F1-60). D1 D3 There is no such counter across SMs; a grid barrier must be built from memory operations on the device's L2 or memory: atomics, fences and polling (R3). R3 That is the hardware reason for the asymmetry BR-03 announced: synchronization is cheap inside a block and expensive across the grid.

Worked example

Task. A kernel tiles a long array into chunks of 256 elements and loops over them with one shared buffer: for each chunk, load into s, then each thread reads s[(t + 1) % 256]. Where do barriers go, and how many per chunk?

  1. Write s[t]; then other threads read it: a read-after-write dependency between threads → barrier B1 after the load.
  2. Read s[(t + 1) % 256]; then, in the next chunk, thread t+1 overwrites s[t+1]: a write-after-read dependency → barrier B2 after the read, before the next load.
  3. Two barriers per chunk. Listing 1's WBRBWBR row is this pattern on four threads: 0 wrong of 331,776 orders; without B2 (WBRWBR), 824,832 of 1,451,520 are wrong. R1
  4. Alternative: two buffers used alternately (double buffering, F6-24) remove B2 at the cost of twice the shared memory.

Where the analogy breaks


    

  • The bell also delivers the bowls. A real bell only says "everyone is here"; __syncthreads() also makes memory writes visible. A barrier that only waited would not be enough. D1
    • 

  • Tables outside the hall are not "slow"; they do not exist yet. A non-resident block has not started at all; it has no registers, no shared memory and no program counter. The story's "waiting outside the door" suggests they are ready to go.
    • 

  • The hall's size is not visible from inside. A helper cannot look around and count tables; a kernel has no reliable way to know how many blocks are resident. That is why the launch, not the kernel, has to guarantee co-residency.
    • 




Common mistakes and debugging


    

  • Symptom: results correct most of the time, wrong sometimes, different on another GPU. Cause: a missing barrier (read-after-write or write-after-read). How to find it: Compute Sanitizer racecheck; count phases as in the worked example. Fix: add the missing barrier, or double-buffer.
    • 

  • Symptom: the kernel hangs or gives garbage when n is not a multiple of the block size. Cause: a barrier inside a branch or after an early return. How to find it: Compute Sanitizer synccheck. Fix: hoist the barrier out of the branch; let inactive threads do neutral work.
    • 

  • Symptom: a kernel with a counter-and-spin barrier works on a big GPU and hangs on a small one (the forensic lab). Cause: grid larger than resident capacity. Fix: split into kernels, or use a cooperative launch sized by the occupancy calculator.
    • 

  • Symptom: cudaLaunchCooperativeKernel returns cudaErrorCooperativeLaunchTooLarge. Cause: the grid exceeds blocks per SM × SMs. H1 Fix: compute the grid as Listing 3 does and use a grid-stride loop.
    •

Forensic lab answer key


Observation. Grids of 4 and 8 blocks finish; 9, 16 and 64 hang, always with 8 blocks spinning (= the number of slots) and the rest never resident; arrived = 8 in every hanging case.


Hypotheses. An infinite work loop would leave blocks "working", not "spinning"; the evidence shows all resident blocks reached the barrier. A lost counter update would show arrived < resident; it equals the resident count. Insufficient capacity fits every line: hangs exactly when grid > slots.


Root cause. Resident blocks wait for non-resident blocks to arrive; non-resident blocks wait for a slot, which only a finishing block frees; no block can finish: a cycle (deadlock). The developer's larger GPU held the whole test grid at once; CI's smaller GPU with the production size did not.


Fix. (1) Split the kernel at the barrier into two launches. (2) A cooperative launch with this_grid().sync(), grid = cudaOccupancyMaxActiveBlocksPerMultiprocessor × SM count, a grid-stride loop for the data, and the cudaDevAttrCooperativeLaunch check. Prevention: test with a grid larger than the device can hold (or on the smallest supported GPU), always under a timeout; ban hand-written grid barriers in code review.


How the evidence was produced: grid_barrier_sim.cpp (simulation, TG-1 invented) and run.sh (SASS). No GPU was used; the CI story is the scenario.
