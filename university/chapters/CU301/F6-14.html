Story hook

At closing time every helper in the hall has a small pile of coins, the tips of the evening, and the head of the hall wants one number. The first idea is a queue: everyone walks to the cashier, who adds one pile at a time. That is a loop on one core, and in this hall of thousands it takes all night.

Then Ravi's row tries pairs. Helper 0 adds helper 1's coins to his own, helper 2 adds helper 3's, and so on. Half the helpers are done after one round. In the next round the survivors pair up again. After eight rounds a row of 256 has one pile. But Ravi's way of choosing who adds (only helpers whose number is divisible by 2, then by 4, then by 8) leaves gaps everywhere in the row, and helpers keep reaching into the same drawer. Mira changes who adds, then who reads from where, then lets helpers pass coins hand to hand along the row without the table at all. Same total, a fraction of the time.

This chapter follows Mira, step by step, through the six versions of a parallel reduction that milestone E3 asks for, measures what each step changes, and then finds the bug that only bites when the pile of coins is larger than two billion.

  • Predict for each version how many warp-steps and bank passes its shared-memory phase needs, and check the prediction with a model.

  • Find a 32-bit index overflow that only appears above 2^31 elements, from PTX and a replay.
Jargon box
Reduction
Simple words: combining many values into one, such as a sum, maximum or count. Analogy: turning everyone's pile of coins into one total. Precise: applying an associative binary operator ⊕ to n values; a tree evaluation takes n − 1 operations in ⌈log₂ n⌉ steps; the result equals the sequential one exactly only when ⊕ is truly associative (integer addition), not for floating-point addition. D3
Tree reduction
Simple words: add in pairs, then pairs of pairs. Analogy: rounds of pairing up in the row. Precise: step k combines elements 2k apart; in shared memory each step needs a barrier (F6-12). D3
Warp shuffle
Simple words: a lane reads a register of another lane in its warp directly. Analogy: passing coins hand to hand along the row, no table needed. Precise: __shfl_down_sync(mask, v, delta) returns v of lane self + delta; no shared memory and no block barrier; see F6-15. H1
Grid-stride loop
Simple words: each thread handles element i, then i + (all threads of the grid), and so on. Analogy: each helper takes every N-th plate from the long counter. Precise: for (i = global id; i < n; i += gridDim.x * blockDim.x); decouples the grid size from n, so a fixed, occupancy-sized grid covers any input. D2
Pairwise summation
Simple words: summing in a tree instead of a line, which keeps rounding errors small. Analogy: adding small piles to small piles, never a coin to a mountain. Precise: the error bound grows with log₂ n instead of n; a GPU tree reduction is a pairwise sum in a particular order. Compare Kahan's compensated sum (F0-75). R4
Index overflow
Simple words: an index that does not fit in its integer type wraps around. Analogy: a plate numbering that goes from 2,147,483,647 back to a negative number. Precise: blockIdx.x * blockDim.x + threadIdx.x is computed in 32-bit unsigned arithmetic and wraps at 2^32; stored in an int, it is negative from 2^31 on. R7

The idea in pictures

Layer 1 — the kid explanation

To add up everyone's coins quickly, pair up: each pair makes one pile, then pairs of piles make one pile, and so on. With a thousand helpers that is only ten rounds. The tricks are about who works in each round (keep the workers next to each other, so whole groups can rest) and where they put the coins (do not all reach into the same drawer). The fastest helpers do not even use the table: they pass the coins straight from hand to hand.

Layer 2 — the student explanation

The shape of a GPU reduction

Each block reduces its part of the input to one value; that leaves one partial per block, which is reduced again, by another launch or by an atomic. D3 Inside a block, each thread first puts one value in shared memory, then a loop halves the number of active threads per step, with a barrier between steps (F6-12). Listing 1 contains six versions; versions 1–5 are finished by repeated launches until one value is left (the host loop of lines 149–161), version 6 finishes in one launch.

v1 → v2: remove divergence

v1 (lines 13–27) picks the active threads with tid % (2 * stride) == 0. In step 1 every even thread works: every warp has some lanes working and some idle, so every warp is divergent (F1-57) and must issue the step. Listing 3 counts, for one block of 256 threads: in v1, all 8 warps issue each of the first five steps, and every warp that issues is divergent; 47 warp-steps in total. R3 v2 (lines 29–44) keeps the same pairs but lets consecutive threads do the work: thread t handles index 2 * stride * t. Now the active threads are the first ones, warps are either fully active or fully idle until fewer than 32 threads remain, and the count falls to 12 warp-steps. R3

v2 → v3: remove bank conflicts

v2's index 2 * stride * t makes lanes of one warp read words 2, 4, 8, … apart: the bank model of F6-11 gives 2, 4, 8, 8, 8, 4, 2, 1 passes in the eight steps. v3 (lines 46–60) reverses the loop: the stride starts at half the block and halves; thread t adds s[t + stride]. Consecutive lanes read consecutive words: 1 pass in every step, still 12 warp-steps. R3 This is "sequential addressing" (Figure 1).

v3 → v4: first add during the load

In v3 half the threads are idle from the first step. v4 (lines 62–78) lets each thread load two elements and add them before writing to shared memory; each block covers 2 × 256 elements, and half as many blocks are launched. S1

v4 → v5: shuffles

The last five steps of v3 and v4 involve at most one warp and still pay a barrier each. v5 (lines 104–113) uses warpSum (lines 80–87): five __shfl_down_sync steps reduce a warp's 32 values in registers, with no shared memory and no block barrier. blockSum (lines 89–102) reduces each warp, writes one value per warp to shared memory, one barrier, and lets warp 0 reduce those. H1 The loop counts from warpSize / 2, not 16, so the same source is correct on 64-wide wavefronts (F6-15), as E3 requires.

v5 → v6: one launch

v6 (lines 115–127) launches a fixed grid (here 8 blocks per SM, line 221, a starting point to tune) and lets each thread accumulate many elements in a grid-stride loop before blockSum; thread 0 of each block then does one atomicAdd on the total (F6-13). One launch, and almost all of the work is sequential adds in registers. The price: float atomics add the block results in an order that can change between runs.

The E3 list also mentions "unrolling". In v5/v6 the warp step is already a five-iteration loop; the classic unrolled last-warp trick of the Harris slides relied on implicit warp-synchronous execution, which is no longer safe without __syncwarp (F6-15). S1 D1

Layer 3 — the engineer's depth

In the hall: the row's coins are added in a different order than the cashier would, so a float total can differ in the last coins. The precise version follows.

Why float sums need a tolerance

Floating-point addition is not associative; different orders give different roundings. Listing 4 sums E3's input, 2^28 floats with values in thousandths from 0 to 0.999, four ways on the CPU, against an exact integer total of 134,083,486.704: R4

  • a plain float loop gives 16,777,216.000, a relative error of 0.875: once the running sum reaches 2^24, adding a value below 1 no longer changes it;
  • a pairwise (tree) float sum gives 134,083,488.000, relative error 9.666 × 10⁻⁹;
  • Kahan's compensated float sum gives the same value;
  • a double loop gives 134,083,486.707, relative error 2.395 × 10⁻¹¹.

So the GPU's tree is more accurate than the naive CPU loop, and comparing against that loop would reject a correct kernel. E3 asks for a Kahan-summed CPU reference and a stated tolerance; Listing 1 computes the reference in double with Kahan's correction (lines 196–209) and the tolerance as (elements per thread + 2 log₂ n) × ε × Σ|x| (lines 222–224), a bound for sums of non-negative data whose derivation is in MA302 (F0-75). Integer sums must be exact.

Measuring against CUB, honestly

Listing 2 calls cub::DeviceReduce::Sum twice, the first time with a null temporary buffer to learn its size, as CUB requires; it times the median of 20 calls. Its documentation states that it "provides 'run-to-run' determinism for pseudo-associative reduction (e.g., addition of floating point types) on the same GPU device", but results "may be inconsistent" between devices of different compute capability. Large inputs and 32-bit indices

blockIdx.x * blockDim.x + threadIdx.x has type unsigned int and wraps at 2^32; assigned to an int, it is negative from 2^31. Inputs above 2^31 elements are now ordinary (2 GiB of bytes). v4–v6 compute their index in size_t (line 68). The forensic lab is about a kernel that does not.

How the hardware actually does it

The shuffle step is a register-to-register exchange inside the SM; in Evidence R8 it is SHFL.DOWN PT, R9, R0, R7, 0x1f followed by FADD, with no shared-memory instruction and no BAR.SYNC between the steps; one STS, one BAR.SYNC and one LDS connect the two warp-level phases of blockSum. R8 Newer GPUs also have a warp-wide integer reduction instruction (REDUX.SUM, exposed as __reduce_add_sync for compute capability 8.0 in the CUDA 12.0 header crt/sm_80_rt.h); the SASS of F6-13 and F6-15 shows it. H1 It covers integers only; floats still use shuffles.

Worked example

Task. For 2^28 elements and blocks of 256, how many launches does v3 need, and how many does v4? How many elements does each thread of v6 add on a GPU with 100 SMs (an invented number)?

  1. v3: each launch divides the count by 256 (rounded up): 2^28 → 2^20 → 2^12 → 2^4 → 1: four launches.
  2. v4: each launch divides by 512: 2^28 → 2^19 → 2^10 → 2 → 1: four launches, the first with half as many blocks.
  3. v6: grid = 100 × 8 = 800 blocks of 256 = 204,800 threads. 2^28 / 204,800 = 1,310.72, so each thread adds 1,310 or 1,311 elements in its loop.
  4. Tolerance for v6 (lines 222–224): (1,311 + 2 × 28) × 1.19 × 10⁻⁷ × Σ|x|, with Σ|x| ≈ 1.34 × 10⁸: about 2.2 × 10⁴, a relative tolerance of about 1.6 × 10⁻⁴. The pairwise result of R4 is far inside it.

Where the analogy breaks


    

  • Coins are exact; floats are not. Adding coins in any order gives the same total; adding floats does not (Listing 4). The analogy hides the most important correctness issue of this chapter.
    • 

  • Idle helpers in a busy row still cost. In the hall, an idle helper is free. On the GPU, a warp with one active lane issues the whole instruction; that is why v1 is slow even though it does no more additions than v3.
    • 

  • Passing hand to hand is limited to one row. Shuffles only work inside a warp; across warps the table (shared memory) and a barrier are still needed.
    • 




Common mistakes and debugging


    

  • Symptom: float sum "wrong" compared with a CPU loop. Cause: the CPU loop is the inaccurate one (R4). Fix: compare with a Kahan or double reference and a stated tolerance.
    • 

  • Symptom: correct for powers of two, wrong otherwise. Cause: threads past the end load garbage, or skip the barrier. Fix: load the identity (0 for sums) past the end; keep all threads in the loop.
    • 

  • Symptom: wrong on AMD, correct on NVIDIA. Cause: a hard-coded 32 (offset 16, mask 0xffffffff, lane = tid & 31). Fix: warpSize everywhere (F6-15).
    • 

  • Symptom: wrong only above 2^31 elements (the forensic lab). Cause: a 32-bit index. Fix: compute indices in size_t.
    • 

  • Symptom: the last-warp unrolled code from an old tutorial gives wrong sums on new GPUs. Cause: it assumes lanes run in lockstep without __syncwarp. Fix: shuffles, or __syncwarp() between steps (F6-15).
    •

Forensic lab answer key


Observation. Correct up to and including n = 2^31; at 2^31 + 512, 256 bytes are missing; at 3 × 2^30, 536,870,912 (= 2^29) are missing, total 2,684,354,560 as reported. The first wrong block is 4,194,304 = 2^31 / 512 (R9).


Hypotheses. The total is accumulated in unsigned long long with atomicAdd, and per-block sums are at most 512: no accumulator overflow. The kernel uses atomics, so no lost update; and the loss is exactly reproducible. The index overflow matches: everything from element 2^31 on is affected, and exactly half of it is missing.


Root cause. int i = blockIdx.x * (blockDim.x * 2) + threadIdx.x: the PTX computes it with mad.lo.s32 and sign-extends it with cvt.s64.s32 before the unsigned compare setp.ge.u64 (R7). From block 4,194,304 on, i is negative, the extended value is huge, and the first load is skipped. The second index, i + blockDim.x, is computed in unsigned arithmetic (int + unsigned), wraps back to the right value, and still loads. Half of each block's bytes are lost.


Fix. size_t i = static_cast<size_t>(blockIdx.x) * (blockDim.x * 2) + threadIdx.x; (sumBytes64); the PTX shows mul.wide.u32, a 32 × 32 → 64-bit multiply (R7). Prevention: test sizes just below and above 2^31 and 2^32 elements (of bytes, cheap); compile with -Wconversion or a linter for narrowing assignments; a review rule "indices into arrays that can exceed 2^31 elements are 64-bit".


How the evidence was produced: overflow_emu.cpp replays the kernel's arithmetic on the CPU (no data stored); run.sh produced the PTX. The kernel itself was built but not run (no GPU).
