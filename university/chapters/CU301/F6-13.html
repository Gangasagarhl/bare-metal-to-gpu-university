Story hook

At the end of the evening the head of the hall wants to know how many plates were served. On the wall hangs one tally counter: press the button, and the number goes up by one. Mira has a faster idea. She reads the number on the counter, adds one in her head, and writes the new number on a sticky note over the display. When only Mira does this, it works. When the whole hall does it, two helpers read 41 at the same moment, both write 42, and a plate disappears from the count. By the end of the night the wall says 1,472 where 32,000 plates were served.

The real tally counter does the reading, adding and writing in one press that nobody can interrupt. That is an atomic operation. It is correct, but there is one counter, and a long queue forms in front of it. So the smarter helpers count on their own row first, and only one of them walks to the wall with the row's total. This chapter is about both halves of that story: why "read, add, write" loses updates, and how to keep atomics from becoming a queue.

What you will be able to do

  • Explain why (*counter)++ by many threads loses updates, using the three machine steps it compiles to.
  • Use atomicAdd, atomicCAS and their scoped variants correctly, and build an atomic operation the hardware lacks from a compare-and-swap loop.
  • Reduce contention with warp aggregation (ballot plus population count) and block aggregation (shared-memory atomics), and count how many global atomics each version issues.
  • Read PTX and SASS to see whether an update is atomic and whether the compiler already aggregated it.
  • Diagnose a counter that is too small and different on every run.
Jargon box
Atomic operation (GPU)
Simple words: a read, change and write of one memory word that no other thread can cut into. Analogy: pressing the tally counter's button. Precise: a read-modify-write on a 32-, 64- (or for some operations 16- or 128-) bit word in global or shared memory, guaranteed to be performed without interference from other threads in its scope; CUDA exposes it as atomicAdd, atomicSub, atomicExch, atomicMin, atomicMax, atomicInc, atomicDec, atomicCAS, atomicAnd, atomicOr, atomicXor. D1
Read-modify-write
Simple words: read a value, change it, write it back. Analogy: reading the counter, adding in your head, writing a sticky note. Precise: three steps (a load, an arithmetic operation, a store); when not atomic, another thread's store can fall between them. D3
Lost update
Simple words: an increment that disappears because another thread overwrote it. Analogy: two sticky notes that both say 42. Precise: the outcome of a data race on a read-modify-write; the final value is smaller than the number of increments, and different between runs. R2
Contention
Simple words: many threads wanting the same address at the same time. Analogy: the queue in front of the one counter. Precise: atomics on one address are performed one after another, so their throughput falls as more of them target it; the cost per operation depends on the GPU. D2 D3
Warp aggregation
Simple words: the lanes of a warp combine their updates, and one lane makes a single atomic for all. Analogy: the row counts its plates, one helper walks to the wall. Precise: use a warp vote (__ballot_sync, F6-15) and __popc to count passing lanes, elect a leader with __ffs, and issue one atomic with the total. H1
Compare-and-swap (CAS)
Simple words: "write my new value only if the old value is still what I saw." Analogy: replacing the sticky note only if it still shows the number you read. Precise: atomicCAS(addr, compare, val) reads old, stores val if old == compare, and returns old; any atomic read-modify-write can be built from it with a retry loop. D1
Atomic scope
Simple words: which threads the "cannot be cut into" promise covers. Analogy: a counter for one table, one for the hall, one for the whole restaurant chain. Precise: atomicAdd_block is atomic with respect to the threads of the block, atomicAdd of the device, atomicAdd_system also of the host and other devices; available from compute capability 6.0. D1 H1

The idea in pictures

Layer 1 — the kid explanation

If everyone writes the new total on a note, two people can write the same number and one plate is forgotten. If everyone presses the counter's button, nothing is forgotten, but everyone waits in line. So each row counts its own plates first, and one person per row presses the button once with the row's number. Same total, much shorter line.

Layer 2 — the student explanation

What (*counter)++ really is

Listing 1's countPlain counts elements divisible by 3 with (*counter)++. The PTX the compiler made of it, in Evidence R4, is three instructions: ld.global.u32, add.s32 … 1, st.global.u32; the SASS shows LDG.E and STG.E on the same address (R5). R4 R5 Between the load and the store, any other thread may store too. That is a data race (F6-12), and its result is a lost update.

How many are lost?

Listing 2 replays it without a GPU: K model threads each increment a counter 1,000 times; a seeded scheduler interleaves their load, add and store steps. With 1 thread nothing is lost. With 2, the non-atomic result is 1,137 instead of 2,000; with 4, 1,188 of 4,000; with 32, 1,472 of 32,000; with 256, 1,547 of 256,000. The same 32 threads under five different schedules give 1,503, 1,481, 1,463, 1,509 and 1,463. The atomic version is exact every time. R2 A real GPU's interleaving is different from this model's, so the exact numbers will differ (see the unverified box); the two signatures, "too small" and "different every run", are the point.

The fix: one indivisible step

atomicAdd(counter, 1) performs the read, add and write as one operation, and returns the old value. D1 In PTX it is atom.global.add.u32 (R4). Atomics exist for global and shared memory, for int, unsigned, unsigned long long, float and (on newer GPUs) double addition and several other operations; check the programming guide for which type and operation your target supports. D1

Atomics give no order

An atomic makes one update safe; it does not say in which order updates happen. Integer addition does not care. Floating-point addition does: atomicAdd on float sums in an order that can change between runs, so the result can differ in the last bits (F6-14). And an atomic on one word does not make other memory visible to other threads; for that you need a fence or a barrier (F6-12). D1

Layer 3 — the engineer's depth

In the kitchen: the counter is a queue, so you count locally and send a delegate. The rest of this layer is the precise version.

Contention: atomics on one address serialise

Atomics on different addresses can proceed in parallel; atomics on the same address are performed one after another. D3 D2 So the useful number is not "how many atomics" but "how many on the busiest address". Listing 3 counts them for Listing 1's data (2^24 elements, about a third pass): countAtomic, one per passing thread, sends 5,592,417 atomics to the one counter; countWarpAgg, one per warp, 524,288; countBlockAgg, one per block of 256, 65,536. Within one warp instruction, 32 lanes on one address is 32 operations; 32 lanes on 32 addresses is 1 per address; 32 lanes on 4 bins is 8 on the busiest. R3 These are counts. How much time each costs depends on the GPU and is not stated here.

Warp aggregation, by hand

countWarpAgg (Listing 1, lines 31–40): every lane computes its predicate; __ballot_sync(0xffffffff, p) returns a 32-bit mask with bit k set when lane k passes; the lowest set bit, found by __ffs(mask) - 1, elects a leader; the leader adds __popc(mask). All lanes must execute the ballot with the full mask, so it sits outside the if. H1 D1

The compiler already does some of this

A surprise in Evidence R5. The SASS of the plain countAtomic for sm_80 is not one atomic per thread: it contains VOTEU.ANY, POPC and a single RED.E.ADD.STRONG.GPU, which means ptxas turned the per-thread atomicAdd(counter, 1) on a uniform address into a warp-aggregated one. RED is the form used when the returned old value is not needed. The hand-written countWarpAgg becomes VOTE.ANY, POPC, REDUX.SUM and one RED; countBlockAgg's shared-memory atomic becomes ATOMS.POPC.INC.32. R5 Two lessons: read the machine code before optimising, and do not depend on this rewrite, which applies only when the compiler can prove the address and the added value are the same for all lanes.

Not verified — check before relying on this

The reading of VOTEU.ANY + POPC + RED as automatic warp aggregation is an interpretation of the SASS of one toolkit (CUDA 12.0, sm_80); this build did not find documentation of when ptxas does it, and did not time it. Listing 3's counts therefore describe the source code, not necessarily what the hardware executes for countAtomic. Also unverified: the relative cost of global atomics, shared atomics and RED on any GPU. Check: the CUDA C++ Best Practices Guide and the Nsight Compute memory workload analysis on your GPU.

Building a missing atomic from CAS

There is no atomicMax for float in the list of built-in functions. atomicMaxFloat (lines 55–65) builds it: read the word; while the stored value is smaller than ours, try atomicCAS with the value we last saw; if another thread changed the word in between, CAS returns the new value and we retry. D1 It is lock-free: some thread always succeeds. It is slow under contention, because failed attempts repeat. Do not build a spin lock from CAS on a GPU without great care: lanes of one warp spinning on a lock that another lane of the same warp holds were a classic deadlock before independent thread scheduling, and are still slow (F6-15). D1

Scope

scopes (lines 73–79) compiles to atom.global.cta.add.u32 for atomicAdd_block and atom.global.sys.add.u32 for atomicAdd_system (R4). R4 A narrower scope can be cheaper but is only correct if no thread outside it touches the word. The CUDA 12.0 header sm_60_atomic_functions.h, read in this build, declares these variants. H1

How the hardware actually does it

Global atomics are carried out near the memory side, in the L2 cache, rather than by the SM that issued them; that is why atomics from different SMs to one address are coherent, and why they serialise there. Shared-memory atomics are performed by the SM on its own shared memory. D3 In SASS the forms are visible: ATOM (returns the old value), RED (no return; "reduction to memory") and ATOMS (shared memory), as in Evidence R5. R5

Not verified — check before relying on this

Where exactly a given GPU executes global atomics, and how many per clock it can sustain on one address or on many, was not checked in this build; the statement above is from the textbook's general description (D3, title only). Check: the GPU's architecture whitepaper or tuning guide, and a measurement with Listing 1 extended to time each version.

Worked example

Task. 2^24 elements, 65,536 blocks of 256. A third of the elements pass. How many global atomics does each version send to the counter, and what is the worst-case number from one warp instruction?

  1. Per thread: one per passing element: about 2^24 / 3 ≈ 5.59 million; Listing 3 counts exactly 5,592,417 for this data. R3
  2. Per warp: one per warp with at least one passing lane. 2^24 / 32 = 524,288 warps; every warp has at least one pass here, so 524,288.
  3. Per block: one per block, 2^24 / 256 = 65,536, plus up to 256 shared-memory atomics inside each block on the block's own counter.
  4. Worst from one warp instruction in the per-thread version: the busiest warp has 14 passing lanes (R3), so 14 operations on one address, unless the compiler aggregates (R5).

Result: aggregation cuts the global operations on one address by about 10× (warp) and 85× (block), at the cost of a vote, a population count, or a shared-memory phase and two barriers.

Where the analogy breaks


    

  • The queue is invisible and has no fairness you can rely on. In the hall you can see who is next; on the GPU you cannot tell, and the order of atomics is unspecified.
    • 

  • A tally counter only adds one. GPU atomics add any value, take minimum and maximum, swap, and compare-and-swap; the analogy covers only atomicAdd(…, 1).
    • 

  • Sticky notes would be noticed. A lost update leaves no trace at all: no error, no warning, only a wrong number.
    • 

  • The walking delegate is not free in the hall but nearly free on a GPU. Combining a row's count costs a vote and a population count, a few instructions, not a walk.
    • 




Common mistakes and debugging


    

  • Symptom: a count or sum that is too small and changes between runs. Cause: a non-atomic read-modify-write. How to find it: look for ++, += on shared or global locations used by many threads; read the PTX for ld/st instead of atom/red; Compute Sanitizer racecheck for shared memory. Fix: an atomic, or a reduction (F6-14).
    • 

  • Symptom: correct but slow. Cause: every thread hits one address. Fix: warp or block aggregation; privatised copies (F6-17).
    • 

  • Symptom: countBlockAgg wrong on the first block only, or randomly. Cause: missing barrier after zeroing the shared counter, or before reading it. Fix: both barriers of lines 46 and 51.
    • 

  • Symptom: a float total differs in the last digits between runs. Cause: atomic float addition in a varying order. Fix: accept a tolerance (F6-14), or reduce in a fixed order.
    • 

  • Symptom: the warp-aggregated kernel hangs or gives wrong counts in a block whose size is not a multiple of 32. Cause: the full mask 0xffffffff names lanes that do not exist. Fix: block sizes that are multiples of 32, or __activemask() with care (F6-15).
    •

Summary


    

  • x++ by many threads is load, add, store, and loses updates silently.
    • 

  • Atomics make a read-modify-write indivisible; they do not order updates or publish other memory.
    • 

  • Atomics on one address serialise: count operations on the busiest address.
    • 

  • Aggregate first: warp (ballot + popc + leader), block (shared atomics), then one global atomic.
    • 

  • CAS loops build any atomic; scope (block, device, system) is part of correctness.
    • 

  • Read the SASS: the compiler may already aggregate.

Forensic lab answer key


Observation. Every run gives a different number in a narrow band (about 1,500), and all are far below the true count (over 30,000), like R2's 1,503, 1,481, 1,463, 1,509, 1,463 against 32,000.


Hypotheses. A wrong predicate would give the same wrong number every run. An overflow of a 32-bit counter at 30,000 is impossible and would wrap, not shrink. A lost-update race explains "too small" and "different every run"; the PTX shows a non-atomic load, add, store.


Root cause. (*counter)++ compiles to ld.global.u32 / add.s32 / st.global.u32 (R4) and LDG / STG (R5); stores of other threads between the load and the store are overwritten.


Fix. Minimal: atomicAdd(counter, 1), one global atomic per passing record in the source (5,592,417 for 2^24 records with a third passing, R3). Better: warp-aggregated (524,288) or block-aggregated (65,536). Prevention: review rule "no plain ++ or += on memory shared between threads"; a test that compares GPU and CPU counts on every run.


How the evidence was produced: lost.cpp (a seeded model, not a GPU), and run.sh (PTX and SASS). The scenario's numbers were chosen to match the model; a GPU would give its own.
