Story hook

The table in the middle of the row has a long line of drawers, numbered 0 to 31, and then the numbering starts again: drawer 0, drawer 1, … drawer 31, drawer 0, drawer 1… Each drawer can hand out one thing at a time. When the 32 helpers of a row each reach into a different drawer, everyone gets what they need at once.

One afternoon Mei's row is told to take the first spice of every recipe card on the table. The cards are laid out so that the first spice of each card sits in drawer 0. Thirty-two hands reach into drawer 0. The drawer hands out one spice, then the next, then the next: thirty-two turns for what should have been one. Nobody did anything wrong; the cards were simply laid out badly. Mei slides every card along by one drawer, and the queue disappears.

The drawers are banks, the queue is a bank conflict, and sliding the cards along by one is padding. This chapter teaches you to predict the queue before it forms.

What you will be able to do

  • Compute, in the bank model, the bank of any shared-memory word and the number of passes a warp's access needs.
  • Predict the conflict degree of strided accesses (it is gcd(stride, 32) in the model) and recognise broadcasts.
  • Remove conflicts by padding a 2-D array or by XOR swizzling, and explain the cost of each.
  • Read address arithmetic in SASS to see which pitch a kernel really uses.
  • Diagnose a slow transpose from evidence and prove the padding fix.
Jargon box
Bank (shared memory)
Simple words: one of the equal slices of shared memory that can each serve one word at a time. Analogy: one drawer of the table. Precise: shared memory is divided into banks that can be accessed simultaneously; successive 32-bit words are assigned to successive banks. Not a DRAM bank (HW203). D1 D2
Bank conflict
Simple words: several threads of one warp want different words from the same bank, so they are served one after another. Analogy: two helpers reaching into the same drawer for different things. Precise: the access is split into as many conflict-free passes as the largest number of distinct words requested from one bank (the conflict degree). D1
Broadcast
Simple words: many threads read the very same word, and one read serves them all. Analogy: one helper lifts the spice out and everyone looks at it. Precise: threads that read the same 32-bit word do not conflict; the word is delivered to all of them. D1
Pitch (row stride)
Simple words: how many elements one row of a 2-D array really takes in memory. Analogy: how many drawers one recipe card covers, including empty ones. Precise: the distance, in elements, between the starts of consecutive rows; for float t[32][33] the pitch is 33. D3
Padding
Simple words: adding unused elements at the end of each row so that rows start in different banks. Analogy: sliding each card along by one drawer. Precise: choosing a pitch that is not a multiple of the bank count (for example 33 instead of 32) so that a column of the array spreads over all banks. D2
Swizzling (XOR)
Simple words: shuffling where each element of a row is stored, in a way you can undo, so that columns spread over the banks without wasting space. Analogy: each card's spices are put in its drawers in a different, fixed order. Precise: storing element (r, c) at column c XOR r (within a row of 32) instead of c; reading and writing use the same mapping. D3

The idea in pictures

Layer 1 — the kid explanation

The table is fast because it has many drawers that work at the same time. That only helps if the helpers reach into different drawers. If many of them need different things from one drawer, they queue, and the fast table becomes slow. You fix it by deciding where things go on the table, so that the things a row needs together sit in different drawers.

Layer 2 — the student explanation

The bank model used in this course

Shared memory is divided into banks; consecutive 32-bit words go to consecutive banks, and the banks can serve one word each in the same cycle. D1 If the threads of a warp ask for different words in the same bank, the request is split into conflict-free passes. Threads asking for the same word get it together (a broadcast). D1 This course computes with the model "32 banks of 4 bytes, bank = word mod 32, passes = the largest number of distinct words in one bank", which is the model the course's sources describe for NVIDIA GPUs; Listing 1 takes the bank count and width as parameters because they are not verified for every product (unverified box below).

Strides

When lane k reads word k·s, the words fall into banks k·s mod 32. Lanes k and k′ collide exactly when (k − k′)·s is a multiple of 32, and a little modular arithmetic (MA102) shows that each used bank then receives gcd(s, 32) distinct words. Listing 1 confirms it: stride 1, 3, 5, 17 and 33 need 1 pass; stride 2 needs 2, 4 needs 4, 8 needs 8, 16 needs 16, 32 needs 32. R1 Odd strides never conflict in this model, because an odd number shares no factor with 32.

Broadcasts and sub-word data

Every lane reading a[0] needs 1 pass, and pairs of lanes sharing a word (a[lane / 2]) need 1 pass: equal words do not count twice. R1 A char array read with c[lane] puts four lanes in each word, so 32 lanes touch 8 words in 8 banks: 1 pass. R1 Any permutation of the 32 words of one row (a[(lane * 7) % 32]) is conflict-free too: what matters is the set of banks, not the order of the lanes. R1

The 2-D tile: rows are fine, columns are not

In float tile[32][32], element (r, c) is word 32r + c, bank c. A warp reading a row (fixed r, lane = c) touches 32 banks: 1 pass. A warp reading a column (fixed c, lane = r) touches bank c 32 times: 32 passes, the worst case. With a pitch of 33, element (r, c) is word 33r + c, bank (r + c) mod 32: a column now covers every bank once. R1 D2 The cost is one unused word per row: 4,224 bytes instead of 4,096 for a 32 × 32 float tile (the ptxas report in the forensic lab). R4

Layer 3 — the engineer's depth

In one line of analogy: you cannot change the drawers, only where you put things; padding wastes a drawer per card, swizzling wastes none but needs a rule everybody follows.

XOR swizzling

Instead of moving rows apart, a swizzle changes where each element sits inside its row: element (r, c) is stored at column c XOR r (for 32 columns, using the low 5 bits of r). For a fixed column c, the 32 rows store it at 32 different columns, because r ↦ c XOR r is a bijection on 0..31; so a column read hits every bank once. For a fixed row r, c ↦ c XOR r is also a bijection, so row accesses stay conflict-free. Listing 1 prints 1 pass for both. R1 The tile keeps its 4,096 bytes (F6-19 shows ptxas confirming it), and both the writer and the reader must apply the same XOR. CUTLASS's layouts use swizzles of this family at larger scale (F6-27). D3

Padding or swizzle?

  • Padding is one character in the declaration and easy to review; it costs shared memory (3 % for 32 × 33) and breaks the alignment of rows, which matters if a later step wants vector loads (float4) from a row.
  • Swizzling costs no memory and keeps rows aligned, but costs an XOR per index, and every access to the array must use the mapping; a single forgotten access silently reads the wrong element (the compiler will not warn).

Both should be proved twice: once with arithmetic or a model, once with the profiler's shared-memory conflict counters on the real GPU.

How the hardware actually does it

A shared-memory instruction carries one address per lane; the hardware groups the lanes by bank, serves one distinct word per bank per pass, and repeats until every lane has its data, so a conflicting instruction takes several passes while the instruction stream of that warp waits. D1 D3 The compiler cannot fix this for you, because the bank of an access depends on run-time indices, but you can see the addressing it chose. In the forensic kernels, the SASS computes the tile address of the column read as IMAD R0, R3, 0x20, R0 in the unpadded kernel and IMAD R0, R3, 0x21, R0 in the padded one: a multiply by 32 or by 33, consistent with pitch × threadIdx.x + threadIdx.y. R5 The four stores of each thread are 8 rows apart, which appears as immediate offsets +0x400, +0x800, +0xc00 (8 × 32 × 4 = 1,024 bytes) versus +0x420, +0x840, +0xc60 (8 × 33 × 4 = 1,056 bytes). R5 One number in the source, one constant in the machine code, and a factor of 32 in passes.

Worked example

Task. A kernel stores a struct of three floats per thread in shared memory, struct P { float x, y, z; }; __shared__ P p[256];, and lane k reads p[k].x. How many passes in the model? What if the struct had four floats?

  1. Three floats: p[k].x is word 3k, a stride of 3. gcd(3, 32) = 1: 1 pass.
  2. Four floats (for example with an extra w): word 4k, stride 4, gcd(4, 32) = 4: 4 passes. Lanes 0, 8, 16, 24 all hit bank 0.
  3. Check with Listing 1's table: stride 3 gives 1, stride 4 gives 4. R1
  4. Fix for the four-float case: store the fields as separate arrays (structure of arrays: x[256], y[256], …), so lane k reads x[k], stride 1.

The surprising lesson: a "neater" power-of-two struct can be slower in shared memory than an odd-sized one.

Where the analogy breaks


    

  • Drawers do not wrap around. In a kitchen, drawer 32 would be a new drawer; in shared memory, word 32 is in bank 0 again. The modulo is the whole story of bank conflicts, and the analogy hides it.
    • 

  • Looking at the same spice is free only for words. Two threads reading the same 32-bit word share one read; two threads reading different bytes of the same word also share it. A kitchen drawer has no notion of "the same word".
    • 

  • The queue is per instruction, not per afternoon. Passes are counted for one warp's one instruction; another warp's access at the same time is a separate instruction. "Helpers queueing all afternoon" suggests a lasting jam that does not exist.
    • 




Common mistakes and debugging


    

  • Symptom: a shared-memory kernel is several times slower than its arithmetic suggests. Cause: column access of a tile whose pitch is a multiple of 32. How to find it: compute bank = word mod 32 for one warp (Listing 1); confirm with the profiler's conflict counters. Fix: pad to 33 or swizzle.
    • 

  • Symptom: padding added, but conflicts remain. Cause: the pitch was changed in the declaration but an index computes r * 32 + c by hand. How to find it: the multiplier in SASS (0x20 instead of 0x21). Fix: always index as tile[r][c].
    • 

  • Symptom: after swizzling, wrong results but no crash. Cause: the writer or the reader forgot the XOR. How to find it: replay the kernel on the CPU (as in F6-19's audit). Fix: one helper function for the mapping, used everywhere.
    • 

  • Symptom: a power-of-two struct in shared memory is slow. Cause: stride 4 or 8 words between lanes (worked example). Fix: structure of arrays.
    •

Forensic lab answer key


Observation. In the replay, the four row stores need 1 pass each and the four column loads 32 passes each: 132 passes for 8 requests per warp, 124 extra; over the 4096 × 4096 transpose, 16,252,928 extra passes. The padded kernel needs 8 passes for 8 requests. ptxas: 4,096 versus 4,224 bytes of shared memory, 24 registers each.


Hypotheses ruled out. Global accesses: both kernels index global memory identically (in[(y + j) * width + x], out[(y + j) * height + x]), with consecutive lanes at consecutive addresses. Occupancy: the two kernels use the same registers and almost the same shared memory, so they cannot differ much in occupancy. The barrier: one BAR.SYNC in both.


Root cause. The column read uses word index 32 × threadIdx.x + threadIdx.y + j; for one warp only threadIdx.x varies, so the bank (32 × threadIdx.x + const) mod 32 is the same for all 32 lanes. The SASS shows the multiplier 0x20. With pitch 33 the index is 33 × threadIdx.x + const, bank (threadIdx.x + const) mod 32, different for every lane; the SASS multiplier is 0x21 and the store offsets grow from 0x400 to 0x420 per 8 rows.


Fix. tile[TILE][TILE + 1]. Proof: the replay's 0 extra passes, and on a GPU the profiler's conflict counters near zero (the E5 acceptance test) with time close to the copy. Prevention: the mini-project's linter in the test suite, and an E5-style acceptance test with the profiler. How the evidence was produced: run.sh (ptxas and cuobjdump) and replay.cpp; no GPU was used.
