Story hook

The school hall has a projector, and the visiting theatre company owns it. Teachers may not touch the projector. Instead, the stage manager keeps a store of slides in the company's own room, and teachers work through the order board at the stage door, as with every other request. A teacher who wants to show a picture first asks for a blank slide of the right size and gets a number for it. Then she tells the company where in the school her drawing is, and asks for the slide to be loaded onto the projector. Each time she changes her drawing, she pins two orders: "copy this part of my drawing onto slide 1" and "show that part on the screen". A new teacher once pinned only the second order. The audience kept seeing the old picture, although her drawing had changed. Nobody had told the company to copy it.

QEMU's virtio-gpu works exactly like this. Your driver draws into its own memory; the device keeps its own copy of every image (a resource); two commands copy and show. This chapter writes that driver, on top of the virtio transport from F4-05, and checks it the way milestone G2 asks: QEMU's screen dump against a reference image.

What you will be able to do

  • Write a virtio-gpu 2D driver for your own kernel: control and cursor queues, display information, EDID, resources, backing memory, scan-out, transfers and flushes.
  • Explain why virtio-gpu has two copies of every image and which command moves pixels from one to the other.
  • Compute a damage rectangle and the transfer offset that goes with it.
  • Verify a display driver automatically by comparing a QEMU screen dump with a CPU-rendered reference image, pixel by pixel.
  • Use QEMU's trace events to see which commands the device received, as evidence independent of your driver's own log.
  • Diagnose a screen that shows stale content after an update, from a screen-dump comparison and a device trace.
Jargon box
virtio-gpu
Simple words: a pretend graphics card that virtual machines use, described in an open standard. Analogy: the company's projector, which teachers reach only through orders on the board. Precise: the virtio device type 16; its 2D command set creates host-side resources, attaches guest memory as backing, copies rectangles into resources and assigns resources to scan-outs; optional features add EDID, 3D (virgl) and blob resources. D1 D2
Resource (virtio-gpu)
Simple words: an image the device keeps on its side. Analogy: a numbered slide in the company's slide store. Precise: a device-side object with an id chosen by the driver, a format and a size, created with RESOURCE_CREATE_2D; it is the device's copy of the pixels, separate from the guest's backing memory. D1 D2
Backing memory
Simple words: the guest's own memory where the driver draws the pixels. Analogy: the teacher's drawing in her classroom. Precise: a list of guest-physical memory ranges attached to a resource with RESOURCE_ATTACH_BACKING; TRANSFER_TO_HOST_2D copies a rectangle from it into the resource. D1 D2
Scan-out
Simple words: one output of a graphics card, like one monitor connector. Analogy: the projector. Precise: a display output of the device (virtio-gpu reports up to 16); SET_SCANOUT selects which resource, and which rectangle of it, the output shows. In real hardware the term also means the act of reading a framebuffer out to the display, line by line (F4-46). D2
Damage rectangle
Simple words: the part of the screen that changed. Analogy: the bit of the drawing the teacher re-did, so only that part is copied onto the slide. Precise: a rectangle (or set of rectangles) bounding all pixels that differ between two frames; a driver or compositor sends and shows only that region to save copying. R2
EDID
Simple words: a small block of data in which a monitor describes itself. Analogy: the projector's label: maker, model, and the picture sizes it can show. Precise: Extended Display Identification Data, a 128-byte base block (plus 128-byte extension blocks) with a fixed header, manufacturer and product ids, supported timings and detailed timing descriptors; read over DDC on real hardware and with GET_EDID on virtio-gpu. F4-46 parses it. D2 D4
Screen dump
Simple words: a picture file of what a virtual monitor shows right now. Analogy: a photograph of the hall's screen taken from the back row. Precise: QEMU's monitor command screendump, which writes the current contents of the guest display, here as a binary PPM file; it is the evidence for G2's acceptance test. D3 R3

Layer 1 — the kid explanation

A virtual computer has a pretend screen. To put a picture on it, your program draws the picture in its own memory. Then it asks the pretend graphics card for a blank picture of the same size, tells the card where its drawing is, and connects that picture to the screen. Each time the drawing changes, the program sends two messages: "copy this part of my drawing" and "show this part". If it forgets to copy, the screen keeps showing the old picture, even though the drawing in memory is new.

Layer 2 — the student explanation

virtio-gpu is a virtio device like the block and network devices of F4-05, so the transport is not new: find the PCI function (vendor 0x1AF4, device 0x1040 + 16 = 0x1050 for the modern interface), negotiate features, set up virtqueues, tell the device DRIVER_OK. Queue 0 is the control queue and queue 1 the cursor queue. On the control queue every command is a request structure that the device reads, followed by a response structure that the device writes, both starting with the same 24-byte control header whose first field is a type: a command code going in, a response code coming out. D1 D2 R1

A minimal 2D driver needs eight commands, in this order:

  1. GET_DISPLAY_INFO: which scan-outs are enabled and what size each one is. The response has 16 entries; the driver takes scan-out 0's width and height.
  2. GET_EDID (only if the device offered feature bit 1, VIRTIO_GPU_F_EDID): the monitor description for a scan-out.
  3. RESOURCE_CREATE_2D: a new resource with an id the driver picks (not 0), a format, a width and a height.
  4. RESOURCE_ATTACH_BACKING: a list of guest memory ranges that hold the pixels.
  5. SET_SCANOUT: show this resource on this scan-out.
  6. TRANSFER_TO_HOST_2D: copy a rectangle from the backing memory into the resource.
  7. RESOURCE_FLUSH: update the display from a rectangle of the resource.
  8. On the cursor queue, UPDATE_CURSOR (set the cursor image and position) and MOVE_CURSOR (position only).

Steps 6 and 7 repeat for every frame, with the damaged rectangle. D1 D2

The format matters because "a pixel" is four bytes in some order. B8G8R8X8_UNORM (value 2) means the bytes in memory are blue, green, red, unused. On a little-endian CPU a 32-bit value 0x00RRGGBB stored in memory is exactly those bytes, so the lab draws with ordinary integers. The cursor uses B8G8R8A8_UNORM (value 1), with alpha, so that the area around the arrow is transparent. D2 R1

How do you know the picture is right? Not by looking: the build container has no screen, and a learner's eyes are not a test. Milestone G2's acceptance test says "QEMU screen dump matches a reference image". The lab draws its frames with one file of plain integer code, scene.h, compiled twice: into the kernel and into a host program that renders the same frame in ordinary memory. The run script asks QEMU for a screen dump of each frame and the host program compares the two, pixel by pixel. Any bug in the driver (wrong format, wrong stride, wrong offset, missing transfer) shows up as pixels that differ, together with the rectangle they lie in. D5 R3

Layer 3 — the engineer's depth

Writing the protocol from the header

The lab does not include Linux's <linux/virtio_gpu.h> in the kernel: a freestanding kernel should not depend on a host's headers, and the point is to understand every byte. vgpu_proto.h declares only what the driver uses, written after reading the Linux UAPI header, and vgpu_check.cpp is a host program that includes both and compares 39 constants, sizes and offsets. R1 reports zero differences. This is the same pattern as F4-05's virtio_check: a hand-written protocol is allowed, an unchecked one is not. D2 R1

Not verified — check before relying on this

The normative description of virtio-gpu is the OASIS VIRTIO specification, section "GPU Device" (D1), which was not opened in this build. Everything about the protocol here is from Linux's UAPI header (D2, opened) and from what QEMU 8.2.2 did in the lab runs. Not verified against D1: that resource id 0 is reserved; the exact rule for offset in TRANSFER_TO_HOST_2D (the lab uses y × stride + x × 4, which QEMU accepted and which the pixel comparison confirms for QEMU only); whether a device may complete control commands out of order (the driver has one command in flight, so it does not depend on it); the meaning of the fence flag in the control header (unused here).

One command, two descriptors

command() (Listing 2, lines 21–41) is the whole control-queue protocol. It copies the request into a static buffer, clears the response buffer, takes a chain of two descriptors from the F4-05 allocator, points the first at the request and the second at the response with the WRITE flag (the device writes into it), publishes the chain in the available ring, notifies the device and polls the used ring. The response's type field is the result. Polling with a spin limit is a choice for a first driver; DR302's interrupt-driven completion (F4-08) is the next step, and the extension asks for it. D2 R2

The cursor queue is different: its commands have no response, so cursor_command() uses a single read-only descriptor and waits only until the device has consumed it. The cursor image is a separate 64 × 64 resource; UPDATE_CURSOR names it and a position; MOVE_CURSOR changes the position only, with resource id 0. R4 shows QEMU's own trace of both: update, res 0x2 at (100, 100), then move, res 0x0 at (300, 250). R4

Backing memory and physical addresses

RESOURCE_ATTACH_BACKING takes a list of {address, length} entries in guest-physical memory. The lab kernel runs with paging off, so the framebuffer's address in the program is its physical address and one entry covers it. A kernel with paging must translate each page and send one entry per physically contiguous run; a 640 × 480 framebuffer is 1,228,800 bytes, 300 pages of 4 KiB, which could be 300 entries in the worst case. The backing memory must stay where it is for as long as it is attached: if your memory manager ever moves or frees it, the device copies from whatever is there next. D2 R2

Transfers, flushes and damage

TRANSFER_TO_HOST_2D carries a rectangle in resource coordinates and an offset into the backing memory where the rectangle's first pixel lies. For a framebuffer with stride w × 4 bytes, the pixel (x, y) is at y × stride + x × 4. RESOURCE_FLUSH carries only a rectangle. The driver could send the whole screen every time; sending the damage instead saves copying. In the lab, frame 2's damage is the union of window A, B's old position and B's new position, x = 40, y = 40, w = 560, h = 390, so the transfer copies 218,400 of 307,200 pixels (R2). A real compositor keeps a list of rectangles instead of one bounding box. R2

Notice what is not in the protocol: vertical blank. QEMU's virtio-gpu takes the flushed rectangle and updates the host's display whenever its display backend next renders; the guest neither waits for nor learns about the host's refresh. Tearing is the host's problem here. On real hardware it is the driver's (F4-46). D2

Not verified — check before relying on this

That QEMU's virtio-gpu has no vertical-blank event visible to a 2D guest is the author's reading of the UAPI header (D2 defines no such command or event; the only config event bit is VIRTIO_GPU_EVENT_DISPLAY) and of the trace events in trace-events-all (D3); it was not confirmed in QEMU's source or in D1.

Display changes

The device's configuration space has events_read and events_clear. When the host changes the display (a resized window, a new resolution), the device sets VIRTIO_GPU_EVENT_DISPLAY in events_read and raises a configuration-change interrupt; the driver writes the bit to events_clear, calls GET_DISPLAY_INFO again, and recreates its resource and scan-out at the new size. G2's acceptance test asks for exactly this. The lab driver reads events_read at start and end (both 0 in R2) but does not handle the event: with -display none there is no host window to resize, and the build had no way to trigger it. What the lab does show is the driver adapting to a different size at start: R5 runs the same kernel on a device configured for 800 × 600, and both frames match their references. D2 R5

Untested in this build

Two parts of milestone G2's acceptance test were not run: "changing the virtual display resolution from QEMU is handled through a display-change event" (no event was triggered; the handler is the second lab extension) and "cursor moves with the C8 USB mouse" (the cursor commands were checked through QEMU's trace, R4, without a USB mouse driver and without a screen dump of the cursor, which QEMU draws in its user interface and not in the guest's resource). The screen-dump part of the test passed at 640 × 480 and 800 × 600 (R3, R5). Nothing was run on a physical GPU; virtio-gpu has no physical form.

How the hardware actually does it

There is no hardware: virtio-gpu is QEMU code. That is its value for the course. On a real GPU, the job "show these pixels" means programming a display engine to read a framebuffer from VRAM or system memory at the pixel clock's rhythm (F4-46), and the job "draw these pixels" means rendering with the GPU's engines (F4-42). virtio-gpu 2D replaces both with copies done by the host CPU: TRANSFER_TO_HOST_2D is a memory copy inside QEMU from guest RAM to a host image, and RESOURCE_FLUSH tells QEMU's display layer to repaint a region. The guest's commands travel the virtqueue path of F4-05: descriptors in guest RAM, a notification write to the device's notify region in a PCI BAR, and QEMU's device code reading the guest's memory directly. D2 D3

R2's first lines show the transport facts for this device in QEMU 8.2.2: it offered features 0x10130000002, the driver accepted 0x100000002 (bit 1, EDID, plus bit 32, VIRTIO_F_VERSION_1 from F4-05); the control queue has 64 entries and the cursor queue 16; there is one scan-out. R2

Worked example

The frame-2 transfer, by hand. Screen 640 × 480, format B8G8R8X8, stride 640 × 4 = 2560 bytes.

  1. Windows. A = (x 40, y 40, w 300, h 200), so its box is x 40–340, y 40–240. B in frame 1 = (200, 150, 320, 220): x 200–520, y 150–370. B in frame 2 = (280, 210, 320, 220): x 280–600, y 210–430.
  2. Union. x from min(40, 200, 280) = 40 to max(340, 520, 600) = 600; y from min(40, 150, 210) = 40 to max(240, 370, 430) = 430. Damage = (40, 40, 560, 390), inside the 640 × 480 screen, so clipping changes nothing.
  3. Pixels. 560 × 390 = 218,400 of 640 × 480 = 307,200 (71 %). R2 prints the same numbers.
  4. Offset. 40 × 2560 + 40 × 4 = 102,400 + 160 = 102,560 bytes into the backing memory.
  5. Check against the forensic run. If the transfer is skipped, the device's copy keeps frame 1 inside the damage; the pixels that differ between frame 1 and frame 2 are where B was and where B now is and where A now covers B. R6 reports the differing pixels inside x 200–599, y 150–429: B's old left and top edges (200, 150) and B's new right and bottom edges (599 = 280 + 320 − 1, 429 = 210 + 220 − 1). Window A's region outside B's two positions is identical in both frames, so it does not appear.

Where the analogy breaks


    

  • The "slide store" is in the same building. The device's resource is host memory inside the QEMU process, and the "copy" is a memcpy on the same machine. On a real GPU the analogous copy crosses PCIe or does not happen at all, because the display engine reads the framebuffer directly (F4-46).
    • 

  • There is no dark moment between showings. The analogy's projector changes slides at a fixed rhythm. virtio-gpu has no vertical blank the guest can see; the host updates its window when it likes.
    • 

  • Orders are not read by a person. The device reads the guest's memory directly, including the backing memory, at any time after ATTACH_BACKING. A teacher's drawing in her classroom is private; the guest's backing memory is not.
    • 




Common mistakes and debugging


    

  • Flush without transfer. Symptom: the screen does not change, or changes only where an earlier transfer happened. Find: the device trace shows res_flush with no res_xfer_toh_2d before it (forensic lab). Fix: always transfer the same rectangle you flush.
    • 

  • Wrong offset. Symptom: the updated area shows the right shapes in the wrong place, or a sheared copy. Find: the bounding box of differing pixels equals the damage rectangle. Fix: offset = y × stride + x × bytes per pixel.
    • 

  • Red and blue swapped. Symptom: blue windows are orange. Cause: the format says BGRX but the drawing code assumes RGBX bytes. Find: compare one known pixel in the dump. Fix: pick the format that matches your pixel layout.
    • 

  • Response descriptor without WRITE. Symptom: the response stays zero or the device reports an error (not tried in this build). Fix: mark the response descriptor device-writable (Listing 2 line 33).
    • 

  • Resource id 0. Symptom: an error response. Cause: id 0 used as "no resource" (as MOVE_CURSOR does). Fix: start ids at 1 (unverified rule, see the box in Layer 3).
    • 

  • Unchecked response types. Symptom: a black screen and no clue. Fix: check every response against the expected type and stop with its name, as expect() does.
    • 




Transition box

Where you came from: F4-05, where virtqueues carried block and network requests; F4-42, where a GPU driver's jobs were mapped. What carries over: the virtio transport unchanged, two-descriptor request/response chains, feature negotiation, and the habit of checking a hand-written protocol against the real header D2 R1. What changes: the payload is pixels, the result is something you see, so you need a verification method that is not your eyes (the screen dump and the reference renderer); and pixels now live twice, so "the data is in memory" no longer means "the device has it". What comes next: F4-44 leaves the virtual device behind and looks at a real GPU's PCI identity and video ROM, read-only, without the help of a friendly open protocol.

Summary


    

  • virtio-gpu 2D keeps two copies of every image: the guest's backing memory and the device's resource.
    • 

  • Set-up: display info, EDID, create resource, attach backing, set scan-out. Every frame: transfer the damage, then flush it.
    • 

  • A control command is a two-descriptor chain, request then device-writable response; cursor commands use a separate queue and one descriptor.
    • 

  • A hand-written protocol header is fine if a host program checks it against the real one (0 differences, R1).
    • 

  • Display drivers are verified by comparing screen dumps with a reference renderer; a device trace is independent evidence of what was received.
    • 

  • A successful flush response does not mean the new pixels are on screen: only a transfer moves them to the device.
