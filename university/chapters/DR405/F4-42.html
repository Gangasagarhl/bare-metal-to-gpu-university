Story hook

Twice a week a visiting theatre company performs in the school hall. It is not one visitor but a whole crew: dozens of performers, stage hands who move scenery, lighting and sound technicians, and three or four stage managers who run everything behind the curtain. None of them speaks the school's language. The school gives the company one interpreter, and the interpreter's job turns out to be much bigger than translating.

Before the first show the interpreter books the hall, finds storage space for the scenery, and gives the stage managers their scripts (the company insists on its own signed scripts; nobody else's will do). During the season, teachers who want a performance do not walk backstage. They write a running order, pin it to the order board at the stage door and ring the little bell on the board. The stage managers take orders from the board in turn, the crew performs, and a stamp on the order says "done". When a show goes wrong, the interpreter is the one who stops the stage, resets the crew and tells the teacher what happened. And every evening someone has to change the slides on the big screen in the hall, at exactly the moment the screen goes dark between two showings, or the audience sees half of one slide and half of the next.

A GPU kernel driver is that interpreter. This chapter maps what it does, using the open Linux drivers as the reference, and follows one real request, a HIP kernel launch, from your program down to the GPU's command processor.

What you will be able to do

  • List the jobs of a GPU kernel driver (bring-up, firmware, memory management, command submission, synchronisation and recovery, display, the compute interface) and say which part of the Linux stack does each one.
  • Explain the path of a compute dispatch from a HIP call to the GPU's command processor, step by step, naming the user-space component, the device file, the ioctls used for set-up and the memory writes used for each dispatch (course exam P).
  • Explain the path of a page flip from a compositor to the display engine and why it waits for vertical blank.
  • Build an AQL kernel-dispatch packet with the real ROCm header, publish it correctly in a ring, and explain the publication order.
  • Read AMD GPU code generated by hipcc and find where the kernel reads its own dispatch packet and its arguments.
  • Diagnose a dispatch that ran with the numbers of an older dispatch, from a queue log.
Jargon box
GPU kernel driver
Simple words: the operating-system part that owns a GPU and lets programs use it safely. Analogy: the interpreter assigned to the visiting theatre company. Precise: kernel code that brings the GPU up (PCI, power, clocks), loads the firmware of its microcontrollers, manages GPU memory and GPU page tables, accepts and schedules command submissions, tracks their completion with fences, recovers from hangs, drives the display engine, and exposes all of this to user-space drivers through device files and ioctls. Not the same thing as a GPU kernel, the function a GPU runs (HW301). D1 D10
DRM (Direct Rendering Manager)
Simple words: Linux's common framework for graphics drivers. Analogy: the school's standard booking rules that every visiting company's interpreter follows. Precise: the Linux kernel subsystem that GPU drivers plug into; it provides device nodes (a primary "card" node and "render" nodes), buffer-object management (GEM, TTM), a GPU scheduler, fences, and the kernel mode-setting (KMS) interface for displays. D1 D6
KMS (kernel mode setting)
Simple words: the part of a graphics driver that controls what the screen shows. Analogy: the projector operator in the hall. Precise: the DRM interface and driver code that program the display engine: framebuffers, planes, CRTCs (scanout timing generators), encoders and connectors, mode changes and page flips, optionally as one atomic commit. D1 D6
Command processor
Simple words: a small processor inside the GPU that reads the work lists and starts the work. Analogy: the stage manager who takes running orders from the board. Precise: a microcontroller block of the GPU, running vendor firmware, that fetches command packets (PM4 packets on AMD's graphics and compute rings; AQL packets from user-mode queues) and programs the GPU's engines to execute them. D2 D10
User-mode queue (GPU)
Simple words: a list of jobs in memory that a program fills directly, without asking the kernel each time. Analogy: the order board at the stage door, which teachers may pin orders to themselves once they have a pass. Precise: a ring buffer of fixed-size packets in memory mapped both into the process and into the GPU's address space, with a write index, a read index and a doorbell; the kernel driver creates it (on AMD, AMDKFD_IOC_CREATE_QUEUE) and the hardware consumes it. D6 D7
AQL packet
Simple words: one fixed-size job description for the GPU. Analogy: one running order on the board, written on a standard form. Precise: a 64-byte packet of the HSA Architected Queuing Language; the kernel dispatch packet holds a header (packet type, barrier bit, fence scopes), the work-group and grid sizes in work-items, segment sizes, the kernel object, the kernel-argument address and a completion signal. D7 R2
Fence (GPU)
Simple words: a marker that says "the GPU has finished up to here". Analogy: the stage manager's "done" stamp on a running order. Precise: a synchronisation object signalled when a submitted job completes; Linux represents it as a dma-fence, which other drivers and user space can wait on; a fence that never signals is how a hang is detected (with a timeout). D1
Buffer object
Simple words: a piece of memory the GPU driver manages for a program. Analogy: a numbered storage crate in the theatre's store room. Precise: a driver-managed allocation (GEM object) that may live in VRAM or in system memory, can be mapped into a process and into a GPU address space, and can be moved (evicted) by the driver's memory manager. D1 D6
amdkfd
Simple words: the part of AMD's Linux driver that serves ROCm compute programs. Analogy: a second door to the same interpreter, reserved for one kind of visitor. Precise: the Linux kernel driver behind /dev/kfd, part of the amdgpu module, that gives the ROCm runtime GPU memory, user-mode compute queues, events and debugging support. D2 D6 R3

Layer 1 — the kid explanation

A graphics card is a computer inside your computer. It has its own memory, its own tiny managers and thousands of workers. Your program cannot talk to it directly. The operating system has a special program for it, the GPU driver. The driver gets the card ready, gives its managers their instructions, finds memory for your pictures and numbers, and makes sure two programs do not mix up their work.

When your program wants work done, it writes a job card and puts it in a queue that the card reads, then rings a bell. The card's manager takes the job, the workers do it, and a stamp says it is done. When a picture should appear on the screen, the driver swaps pictures only in the short dark moment between two screen refreshes, so you never see half of one picture and half of another.

Layer 2 — the student explanation

Curriculum section 15.1 lists eight jobs for a GPU kernel driver, and the open Linux drivers give each of them a home. Device bring-up: PCI probing, reading the video BIOS, sequencing power and clocks. Firmware loading: a modern GPU contains several microcontrollers (on AMD: a security processor, a power-management controller, the command processors, the DMA engines and the video engines) that each need a signed firmware image. Memory management: VRAM and system memory, one GPU address space per process with its own GPU page tables, and moving buffers when VRAM is full. Command submission: getting the work that user space prepared onto the hardware. Synchronisation and recovery: fences, a scheduler, time-outs and GPU reset. Display: mode setting, link training, reading the monitor's EDID. The compute interface: on AMD, amdkfd for ROCm. And user-space drivers, outside the kernel, that compile shaders and build the command buffers. D10 D1 D2

The split between kernel and user space is the key design fact. The kernel driver owns the hardware and enforces isolation: it decides which memory a process may make the GPU touch, and it can stop a job that runs too long. It does not understand shaders or graphics APIs. The user-space driver (Mesa's radeonsi or RADV for OpenGL and Vulkan on AMD; the ROCm runtime for HIP) compiles programs for the GPU's instruction set and writes command packets. Between them sits a set of ioctls on device files, and you can read them in the Linux UAPI headers. D1 D3 D6

Listing 1 prints those ioctls for three paths from the headers installed in the build container (R1). The compute path uses /dev/kfd: check the version, attach to the GPU's address space through a DRM render node (AMDKFD_IOC_ACQUIRE_VM takes a DRM file descriptor), allocate memory with flags for VRAM or GTT (system memory the GPU reaches through its translation table), map it to the GPU, create a queue, create and wait for events. The graphics path of Mesa uses the render node: create a context and buffer objects, then submit command buffers with DRM_IOCTL_AMDGPU_CS, whose chunks name a GPU virtual address, a size, a hardware IP type (GFX, COMPUTE, DMA) and a ring. The display path uses the card node: list the display resources, wrap a buffer object as a framebuffer, and ask for a page flip. D6 R1

Two submission models follow. In the kernel-mediated model (amdgpu's command submission, i915's execbuffer, every open SoC driver of F4-45), each submission is an ioctl: the kernel checks the buffers, pins them in memory, adds a fence, and puts the job on a hardware ring that the kernel driver alone writes. In the user-mode queue model (amdkfd for ROCm), the kernel creates the queue once and maps its ring and its doorbell into the process; from then on the process writes packets and rings the doorbell itself, and the kernel is not involved per dispatch. The first model is simpler to make safe; the second removes a system call from every launch. D1 D2 D6

The packets in AMD's user-mode compute queues are AQL packets, defined by the HSA standard and declared in ROCm's hsa.h. A kernel dispatch packet is 64 bytes (Figure 3; Listing 2 prints the offsets). Its grid size is given in work-items, not in blocks: the HIP launch vecAdd<<<4096, 256>>> becomes grid_size_x = 1,048,576 and workgroup_size_x = 256. A slot whose header says INVALID must not be processed, which is what makes the publication order matter (Layer 3). D7 R2

Layer 3 — the engineer's depth

The compute dispatch, step by step

Here is the path that course exam P asks for, with the evidence for each step and its status in this build.

  1. The first HIP call opens the driver. R3 is a real trace of vecadd starting in the build container: the runtime opens /dev/kfd read-write, gets "No such file or directory" (there is no GPU and no amdkfd here), and hipGetDeviceCount returns "no ROCm-capable device is detected". On a machine with an AMD GPU the same open succeeds and the runtime goes on to read the GPU topology the driver publishes. R3 R5
  2. Set-up ioctls. The runtime checks the interface version, attaches to the GPU address space, allocates memory for the queue's ring, for kernel arguments and for hipMalloc buffers, maps them to the GPU, and creates an AQL queue. The create-queue arguments (88 bytes in this header version) carry the ring's address and size, the queue type (KFD_IOC_QUEUE_TYPE_COMPUTE_AQL = 2) and buffers for the hardware's context save and end-of-pipe events; the driver returns the addresses of the write and read pointers and a doorbell offset that the runtime maps into its address space. D6 R1
  3. The launch writes a packet. For vecAdd<<<grid, block>>>, the runtime copies the four arguments into a kernel-argument buffer (R4 shows the kernel expects 28 bytes: three 8-byte pointers and a 4-byte int), reserves the next slot by incrementing the write index, fills the packet body (sizes, kernel_object pointing at the kernel descriptor in the loaded code object, kernarg_address, a completion signal) and stores the header last. D7 R4
  4. The doorbell. The runtime writes the packet id to the queue's doorbell. The doorbell is a page of the GPU's register space (MMIO), mapped into the process by the driver, so the write goes over PCIe straight to the GPU. hsa.h describes the doorbell as a signal "used by the application to indicate the ID of a packet that is ready to be processed". D7 D6
  5. The command processor. Firmware running on the GPU's command processor notices the doorbell, reads packets from the read index up to the doorbell value, skips nothing and processes nothing whose header is INVALID, and launches the work-groups described by the packet on the compute units, with the kernel descriptor telling the hardware how many registers to allocate and which values to preload. D7 D9
  6. The kernel runs. Each wavefront starts with preloaded registers. R4 shows vecAdd's descriptor asking for the dispatch pointer and the kernel-argument pointer as user SGPRs and for the work-group id in s8; the first instruction, s_load_dword s0, s[4:5], 0x4, reads bytes 4–7 of the dispatch packet, and the next s_and_b32 s0, s0, 0xffff keeps workgroup_size_x: blockDim.x is read from the packet in Figure 3. R4 D9
  7. Completion. When all work-groups have finished, the packet processor makes the packet's memory effects visible at the release fence scope, decrements the completion signal (which can wake a waiting host thread through an event, AMDKFD_IOC_WAIT_EVENTS), resets the slot to INVALID and advances the read index. D7 D6

Why the header goes last

The packet processor and the host run at the same time. A slot is published the moment its header changes from INVALID to a valid type. If the producer writes the header first and the body afterwards, a packet processor that is already reading the queue can see a valid header with the body of whatever packet occupied the slot one lap of the ring earlier. Two things make that window real. A queue may have several producers (hsa.h distinguishes single- and multi-producer queue types, and for the multi-producer type allows the doorbell to be written "with any value"), so another thread's doorbell can wake the processor while your packet is half written. And CPUs and compilers reorder ordinary stores unless told not to, so even "body then header" in the source needs a release store to stay in that order in memory. The forensic lab is a deterministic replay of exactly this. D7 D8 R6

Memory management

A GPU driver's memory manager is a second virtual-memory system. Each process gets GPU virtual address spaces with GPU page tables that the kernel driver writes; buffers live in VRAM or in system memory reached through the GPU's own translation (the GART on AMD); and when VRAM is full the driver evicts buffers to system memory and moves them back, which requires knowing which buffers each pending job uses. Linux provides two helpers for this, GEM (handles and lifetime) and TTM (placement and eviction across memory types); amdgpu uses both. amdkfd adds a twist: compute buffers must stay mapped while user-mode queues may use them at any time, so the driver cannot wait for "the job that uses this buffer" to finish before evicting it, and must preempt the process's queues instead. D1 D2

Synchronisation, scheduling and recovery

Every kernel-mediated submission gets a dma-fence. The DRM GPU scheduler holds jobs until their dependencies' fences have signalled, pushes them to the hardware ring, and arms a time-out; if the job's fence does not signal in time, the driver declares a hang, resets the engine or the whole GPU, and signals the affected fences with an error. A user-mode queue escapes this per-job tracking, so the driver protects itself differently: it can preempt or destroy the queue and evict the process's memory. Recovery is where a hobby driver is weakest, and F4-47's feasibility studies ask for it explicitly. D1 D2

The page flip

A compositor that wants to show a new frame wraps the buffer as a framebuffer (DRM_IOCTL_MODE_ADDFB2) and calls DRM_IOCTL_MODE_PAGE_FLIP (or an atomic commit that changes a plane's framebuffer). The UAPI header's own comment states the contract: the kernel schedules the flip, "the crtc will be reprogrammed to display that fb after the next vertical refresh", the ioctl returns at once, and with DRM_MODE_PAGE_FLIP_EVENT the kernel sends an event when the flip is done; a flip requested while one is pending gets EBUSY. The flag DRM_MODE_PAGE_FLIP_ASYNC asks for the flip "as soon as possible", and the comment warns: "This may cause tearing on the screen." Inside the driver, the KMS code writes the new surface address into the display engine's double-buffered registers, which the hardware latches at the start of vertical blank, and a vertical-blank interrupt completes the event. F4-46 builds this on Intel hardware and its forensic lab is the course's "Tearing" case. D6 D1

The same jobs in other drivers

NVIDIA's open kernel modules and nouveau do the same jobs with a different split: on recent NVIDIA GPUs much of the work that amdgpu does on the CPU runs inside the GSP firmware on the GPU, and the kernel module mostly talks to that firmware (the container holds two such GSP images, F4-45 R1). Windows splits the same responsibilities between the DirectX graphics kernel (dxgkrnl), a vendor kernel-mode driver and vendor user-mode drivers (WDDM); the project's boot-trace analysis (DRIVERS.html) lists the DirectX graphics kernel dxgkrnl.sys and two parts of AMD's kernel-mode driver, amdkmdap ("display part") and amdkmdag ("GPU engine part", which "loads firmware into the GPU at start"). How the hardware actually does it

Everything in Figure 2 crosses the PCI Express link in one of two directions. CPU-to-GPU traffic is memory-mapped I/O into the GPU's BARs (F4-02, F1-62): register writes from the kernel driver and the doorbell writes from user space, which land in a doorbell aperture that the driver maps page by page into processes. GPU-to-memory traffic is DMA: the command processor reads the ring and the packets from system memory or VRAM, the compute units read and write buffers, and the completion signal is a memory write the host can poll. Interrupts (MSI, F4-08) tell the kernel driver about fences, faults and vertical blanks. D2 D6

The GPU's internal engines are separate hardware blocks with their own queues: the graphics and compute command processors, asynchronous compute engines, SDMA copy engines, video encode and decode, and the display engine. That is why a submission names an IP type and a ring, and why one GPU can copy, compute and scan out at the same time. The display engine is the most independent: it reads a framebuffer from memory at a fixed rhythm set by the mode's pixel clock, whether or not anything else on the GPU is busy. D6 D10

Worked example

The vecAdd launch as a packet and as registers. vecadd.hip adds two vectors of n = 1 << 20 = 1,048,576 floats with block = 256, so grid = (1,048,576 + 255) / 256 = 4096 blocks.

  1. Packet sizes. workgroup_size_x = 256, grid_size_x = 4096 × 256 = 1,048,576 work-items; y and z are 1; setup = 1 (one dimension, field at bit 0). The toy packet processor of Listing 2 recomputes the number of work-groups as (1,048,576 + 255) / 256 = 4096, which is the line "grid=1048576 block=256 -> 4096 workgroups" of R2.
  2. Header. Type KERNEL_DISPATCH = 2 at bits 0–7; barrier = 1 at bit 8; acquire scope SYSTEM = 2 at bits 9–10; release scope SYSTEM = 2 at bits 11–12. 2 + (1 << 8) + (2 << 9) + (2 << 11) = 2 + 256 + 1024 + 4096 = 5378 = 0x1502, the value R2 prints.
  3. Kernel arguments. R4's descriptor says .amdhsa_kernarg_size 28. The code loads s_load_dwordx4 s[0:3], s[6:7], 0x0 (bytes 0–15: a and b), s_load_dwordx2 s[4:5], s[6:7], 0x10 (bytes 16–23: c) and s_load_dword s1, s[6:7], 0x18 (bytes 24–27: n). 8 + 8 + 8 + 4 = 28.
  4. Global index. s_mul_i32 s8, s8, s0 multiplies the work-group id by the work-group size read from the packet; v_add_u32 v0, s8, v0 adds the work-item id in the group: blockIdx.x * blockDim.x + threadIdx.x, exactly the source line. v_cmp_gt_i32 vcc, s1, v0 and s_and_saveexec_b64 implement if (i < n) by switching off the lanes that fail. R4

So the packet is not only a message to the command processor: the running kernel reads fields of it. A wrong workgroup_size_x in the packet would not only start the wrong number of groups; every thread would compute wrong indices.

Where the analogy breaks


    

  • The order board is shared memory, not a board someone walks past. The GPU reads the ring by DMA, possibly at the very moment the host is writing it. A teacher can pin an order and walk away; a program must make the order's body visible before its header (Layer 3), something the analogy never has to think about.
    • 

  • The bell carries a number. The doorbell write says "packets up to this id are ready", not "one more". Ringing it twice with the same id is not two orders.
    • 

  • The interpreter is not in the room during the show. With user-mode queues the kernel driver is not involved per dispatch at all; a real interpreter would at least watch. The driver's control is indirect: it decided which memory the queue can reach, and it can stop the queue.
    • 

  • The stage managers' scripts are not optional reading. GPU firmware is code that runs the command processor and power management. Without it the GPU does nothing, and on some GPUs most of the driver's logic lives in it (F4-45).
    • 

  • The same word, two meanings. "Kernel" here is the operating-system kernel and its GPU kernel driver; HIP's vecAdd is a GPU kernel (HW301). The analogy does not help with that; the qualifiers do.
    • 




Common mistakes and debugging


    

  • Publishing the header first. Symptom: a dispatch runs with another dispatch's grid, kernel or arguments, rarely and under load (R6). Cause: a valid header became visible before the body. Find: log requested versus launched parameters per packet id. Fix: header last, with a release store; never reuse a slot until it is INVALID again.
    • 

  • Ringing the doorbell before publishing. Symptom: the queue appears to stall until the next launch "pushes" it. Cause: the processor read an INVALID header and stopped (Listing 2 line 44 of aql_sim.h models this). Fix: publish, then ring.
    • 

  • Treating "no device" as "no work". Symptom: zeros in the output and no error. Cause: unchecked HIP calls. Find: the CHECK macro; R5 shows what a checked failure looks like. Fix: check every call (AH-27).
    • 

  • Grid in blocks instead of work-items. Symptom: only 1/256 of the data processed. Cause: a hand-built AQL packet with grid_size_x = 4096. Find: compare with the worked example. Fix: grid_size_x = blocks × block size.
    • 

  • Mixing up the device files. Symptom: ENOTTY or EINVAL from ioctls. Cause: KMS ioctls on a render node, or amdkfd ioctls on a DRM node. Find: R1 lists which file each belongs to. Fix: open the right node.
    • 

  • Reading a version's header as the truth for all versions. Symptom: structure sizes disagree with a newer driver. Cause: UAPI headers grow (R1 shows interface version 1.14 for this header). Fix: record the header version in the dossier, as AH-8 asks.
    • 




Transition box

Where you came from: DR301 and DR302, where your kernel drove devices with rings of descriptors, doorbells and interrupts (virtio in F4-05, NVMe in F4-07, MSI in F4-08); HW301, where the GPU was hardware: compute units, wavefronts, memories (F1-55 to F1-62). What carries over: rings with producer and consumer indices, doorbells as MMIO writes, DMA, the ordering rule "make the data visible before you publish it", and fences as the GPU form of a completion queue D6 D7. What changes: the device runs firmware you must load and cannot read; user space may write queues the hardware reads, without the kernel in between; memory management becomes a second virtual-memory system; there is a separate display engine with its own timing; and recovery from a hung device is part of the design, not an afterthought. What comes next: F4-43 writes a complete driver for a GPU that has none of the hard parts: QEMU's virtio-gpu, where every command and every response is in an open specification.

Summary


    

  • A GPU kernel driver brings the GPU up, loads its firmware, manages its memory and page tables, accepts submissions, tracks them with fences, recovers from hangs, drives the display and serves compute runtimes.
    • 

  • User-space drivers (Mesa, the ROCm runtime) compile programs and write command packets; the kernel driver enforces isolation and owns the hardware.
    • 

  • Kernel-mediated submission costs an ioctl per job; user-mode queues cost ioctls only at set-up, then a packet write and a doorbell write per dispatch.
    • 

  • An AQL kernel dispatch packet is 64 bytes; its grid is in work-items; a slot is published when its header becomes valid, so the header goes last.
    • 

  • The running GPU kernel reads its own packet (blockDim.x) and its argument buffer, as the generated code shows.
    • 

  • A page flip is scheduled for the next vertical blank; an asynchronous flip may tear, as the UAPI header itself warns.
    •
