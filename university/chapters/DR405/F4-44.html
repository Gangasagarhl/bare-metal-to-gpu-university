Story hook

A new theatre company arrives for the season, and the school wants to know what it has brought before anyone signs anything. The caretaker is allowed to read the labels on the crates, count them, read the company's registration papers and look at the instruction booklet that comes taped to the first crate. He is not allowed to open a crate, switch on a light rig or press any button: some of the equipment does something the moment you touch it, and some of it cannot be put back the way it was.

On his first day the caretaker finds the booklet's pages blank. On his second day they are full of text. The only difference: on the second day he remembered to switch on the little reading lamp on the crate before looking. This chapter is that caretaker's job on a real GPU: identify it, read its labels and its video BIOS, and write nothing that changes its state, except one switch that he puts back exactly as he found it.

What you will be able to do

  • Identify every display-class PCI function and decode its IDs, BARs and capabilities without sizing BARs or touching device registers.
  • Read a PCI expansion ROM through the ROM BAR, with the only configuration writes counted and restored.
  • Parse a ROM image's header and PCI data structure and verify its checksum.
  • Explain the difference between a device's ROM, the firmware's shadow copy at 0xC0000 and the ROM file a virtual machine is given.
  • Plan the ATOM BIOS part of milestone G3 on a real AMD GPU, with the safety rules for a spare machine.
  • Diagnose a ROM read that returns zeros.
Jargon box
Expansion ROM
Simple words: a small memory chip on a card that holds code and data for the computer's firmware. Analogy: the instruction booklet taped to the first crate. Precise: a read-only image on a PCI device, mapped into memory through the ROM BAR, made of one or more images, each starting with the signature 0x55 0xAA and containing a PCI data structure that names the device and the code type (x86 legacy, UEFI, …). D1 D2
ROM BAR
Simple words: the setting that decides where the card's ROM appears in memory, and whether it appears at all. Analogy: the reading lamp on the crate. Precise: the configuration register at offset 0x30 of a type 0 header (PCI_ROM_ADDRESS); bits 31–11 hold the address, bit 0 (PCI_ROM_ADDRESS_ENABLE) enables decoding; the device answers reads in the ROM window only while the bit and memory decoding in the command register are both set. D2 R2
PCI data structure (PCIR)
Simple words: a label inside the ROM that says which card it is for. Analogy: the booklet's title page: company name, model, edition. Precise: a structure inside an expansion-ROM image, found through the 16-bit pointer at offset 0x18, starting with the ASCII signature "PCIR" and holding the vendor and device IDs, class code, image length in 512-byte units, code type and the last-image flag. D1 R1
Video BIOS (VBIOS)
Simple words: the graphics card's own start-up program and settings table. Analogy: the booklet, which on some companies' crates also lists every setting of the rig. Precise: the expansion ROM of a display device; its legacy x86 image sets up a text or VESA mode at boot; on AMD GPUs it also holds the ATOM BIOS command and data tables that the amdgpu driver reads. D3 D5
ATOM BIOS
Simple words: AMD's format for the tables and little scripts inside its graphics BIOS. Analogy: the booklet's appendix of settings, written in the company's own shorthand. Precise: AMD's VBIOS table format: a ROM header points to a master command table and a master data table, each a list of offsets to individual tables (clock information, display objects, power tables, …); the amdgpu driver parses the data tables and interprets the command tables. D3
Shadow copy (VGA BIOS)
Simple words: a copy of the graphics card's start-up program that the PC firmware puts in ordinary memory. Analogy: the caretaker's photocopy of the booklet, possibly with notes in the margin. Precise: the legacy VGA option ROM image that the system BIOS copies to memory at 0xC0000 and runs; it can differ from the device's ROM because the code may modify its own copy during initialisation. D4 R2

Layer 1 — the kid explanation

A graphics card is like a sealed box with a label on the outside and a little booklet inside. You can read the label any time: it says who made the card and what kind it is. To read the booklet, you have to switch on a small light first. Then you read the first page, which says how long the booklet is, and you add up all its numbers to check that no page is missing. When you are done, you switch the light off again, so the card is exactly as you found it. You never press any other button on the card.

Layer 2 — the student explanation

Everything F4-02 taught about PCI applies unchanged. A display controller has base class 0x03 (0x030000 for a VGA-compatible controller, 0x038000 for "other display controller"). Its configuration space gives vendor and device IDs, a subsystem ID (the board maker's identity), the command and status registers, up to six BARs and a capability list. The lab kernel walks all PCI functions and inspects each one of class 0x03 (Listing 3). D2 R2

"Read-only" sounds simple, but two ordinary PCI habits break it. Sizing a BAR means writing all ones to it, reading back which bits stuck, and restoring it; while the BAR holds all ones the device decodes the wrong addresses. The probe therefore prints each BAR's current address, type and prefetch bit, and states that the size was not measured. Reading device registers through a memory BAR can itself change state on some hardware (a read that clears a status bit, a FIFO that pops on read). The probe reads no BAR-mapped register at all. D2 R2

The expansion ROM needs exactly two configuration writes. The ROM BAR at 0x30 holds an address assigned by the firmware and an enable bit, which is normally clear after boot. The probe reads the register, sets bit 0, reads the ROM window, and writes the original value back. If the firmware assigned no address (the virtio-gpu function in R2), the probe stops: assigning an address is a resource decision that belongs to the firmware or the operating system, not to an inspection tool. D2 R2

The parser (Listing 1) checks the signature 0x55 0xAA, follows the pointer at 0x18 to the "PCIR" structure, reads the IDs, class, image length and code type, and adds all bytes of the image: the sum must be 0 modulo 256. The lab tests the parser twice: on the host with the four ROM files that QEMU's display devices use (R1), and in the kernel with the same images read through each device's ROM BAR (R2). When the two hashes agree, both the read path and the parser are confirmed on these images (R4). R1 R4

Layer 3 — the engineer's depth

Three copies of the same booklet

The lab finds three versions of each VGA BIOS, and they are not all the same.

  1. The file. QEMU loads a ROM file for each display device from /usr/share/seabios/ (SeaBIOS's VGA BIOS builds). R1 parses them on the host: standard VGA and the virtio image are 39,424 bytes, bochs-display 28,672 bytes; all have valid checksums. R1
  2. The device's ROM. Read through the ROM BAR in the guest. For standard VGA and bochs-display the hash equals the file's (R4: SAME). For ati-vga it does not: the file's PCI data structure says device 0x5159, but the ROM the guest reads says 0x5046, which is the device ID of the ati-vga function in R3; the hash differs and the checksum is still valid. The likely explanation is that QEMU patches the IDs in the image it exposes and fixes the checksum; this is an inference from R1, R3 and R4, not checked in QEMU's source. R3 R4
  3. The shadow copy. SeaBIOS copies the primary VGA's legacy image to 0xC0000 and runs it there. R2 finds a valid image there with the standard VGA's IDs and a valid checksum, but a different hash (0xa13d1b81 versus the ROM's 0x9bb077c7). The ROM code may write into its shadow copy during initialisation and recompute the checksum, which would explain both facts; this too is an inference, not verified. R2

The lesson for real hardware: the bytes at 0xC0000 are not a reliable copy of the card's ROM, and a ROM file shipped by a vendor or extracted by another tool may differ from what the card exposes. Milestone G3 asks for the ROM image read from the device, and for its checksum. D4 D6

R2 shows one more detail worth noticing: bochs-display's configuration space says class 0x038000 ("other display controller"), while the PCI data structure in its ROM says 0x030000. The parser reports what each says and does not hide the difference; the probe checks only the IDs. R1 R2

The ATOM BIOS part of G3

On an AMD GPU, milestone G3 continues past the PCI data structure: "parse the top-level ATOM BIOS tables" and print a table list that "matches what Linux's amdgpu debug output reports for the same card". The format is defined by AMD's headers in the Linux source (atombios.h and the newer atomfirmware.h in the amdgpu tree) and parsed by amdgpu's atom.c and amdgpu_atombios.c. D3

Not verified — check before relying on this

Untested on hardware and unverified in every detail: this build had no AMD GPU and no AMD VBIOS image, and the amdgpu source was not opened. From the author's memory: a 16-bit pointer near the start of the image (offset 0x48) leads to an ATOM ROM header containing the signature "ATOM", and that header holds offsets of a master command table and a master data table, each beginning with a common table header (structure size, format and content revision) followed by one 16-bit offset per table. Confirm every offset and name in atombios.h / atomfirmware.h (D3) at the kernel version you compare with, and find which amdgpu debug output lists the tables (a kernel log line at a raised debug level, or a debugfs file; D3, D5). The comparison is the milestone's acceptance test and cannot be passed from this chapter alone.

The approach that works without trusting memory: implement the parser on the host first, against a ROM image you extracted on your spare machine under Linux, compare its table list with the Linux output from the same machine, and only then move it into your kernel, where it reads the same bytes through the ROM BAR. The F4-44 lab has the same shape: romparse.h is shared by the host program and the kernel. R4

Safety

The real-hardware part of this lab runs only on a spare PC whose data you do not need, after the QEMU part passes (curriculum safety box: "Do GPU experiments on a machine whose data you do not need; driver crashes, hangs and forced resets are normal while learning"). Boot your kernel from a USB stick or a separate disk. Read-only means: no BAR sizing, no command-register changes, no MMIO register reads or writes, no attempt to flash or modify the ROM. Never write to the ROM BAR with a different address; restore exactly the value you read. If your kernel shares the machine with a running GPU driver (it should not), the ROM BAR change can disturb that driver.

Capabilities that matter for a GPU

The capability list (R2) is short in QEMU: virtio-gpu-pci has MSI-X and five vendor-specific capabilities (the virtio structures of F4-05), bochs-display a PCI Express capability. A real discrete GPU will show power management, PCI Express, MSI or MSI-X and, in the extended configuration space beyond 256 bytes, capabilities such as resizable BAR, which decides whether the CPU can map all of VRAM at once. Reading extended space needs the ECAM mapping of F4-02; the lab reads only the first 256 bytes. D2 R2

How the hardware actually does it

On a real card, the ROM is a small flash chip (or a region of a larger one) behind the GPU's own PCI interface. The GPU decodes reads in the ROM window only while the ROM BAR's enable bit is set and memory decoding is on; on many devices the ROM and other BARs share address decoders, which is why the enable bit is off in normal operation. With the bit clear, reads to the window return whatever the bus returns for an unclaimed address or the device returns for its other function; in QEMU they returned zeros (R5). D2 R5

The system firmware runs the legacy x86 image of the primary display's ROM at boot, so that text output and VESA modes work before any driver loads; a UEFI firmware runs the UEFI image (the GOP driver) instead. amdgpu, once loaded, can fetch the VBIOS in several ways (through the ROM BAR, from ACPI tables on laptops, from a shadow copy), which is why the milestone compares your output with what amdgpu reports. D3 D4

Not verified — check before relying on this

The statements about shared address decoders, the GOP driver in the UEFI image, and amdgpu's alternative VBIOS sources are from the author's memory (D3, D4, D6 not opened). Only the QEMU behaviour (zeros with the enable bit clear, R5) was observed.

Worked example

Checking the standard VGA ROM by hand. From R1 and Figure 1.

  1. Bytes 0–1 are 0x55 0xAA: an expansion-ROM image starts here.
  2. Byte 2 is 0x4D = 77, so the initialisation size is 77 × 512 = 39,424 bytes.
  3. Bytes 0x18–0x19 are 0x5C 0x98, little-endian 0x985C: the PCI data structure is at offset 39,004, near the end of the image.
  4. At 0x985C: "PCIR", vendor 0x1234, device 0x1111, class bytes at +0x0D..+0x0F = 00 00 03, read as 0x030000; image length 0x004D × 512 = 39,424 bytes; code type 0 (x86); indicator 0x80 (last image).
  5. The sum of all 39,424 bytes is 0x00 modulo 256: valid. The ROM BAR read in R2 gives the same fnv1a hash as the file (0x9bb077c7), so the device exposed the file unchanged.
  6. The device's own IDs in configuration space are 1234:1111: they match the PCIR IDs. A mismatch here would mean the ROM is for a different device, or someone patched one side (the ati-vga case, Layer 3).

Where the analogy breaks


    

  • Reading can change things. Reading a crate's label never changes the crate. Reading a device register can (a read-to-clear status register), which is why the probe reads configuration space and the ROM window only.
    • 

  • The lamp is shared. On real cards the ROM's decoder may be shared with another BAR, so "switching on the lamp" briefly changes what other addresses do. A caretaker's lamp affects nothing else.
    • 

  • The photocopy can be edited by the booklet itself. The shadow copy at 0xC0000 is code that runs and may rewrite its own bytes; no paper booklet does that.
    • 




Common mistakes and debugging


    

  • Reading the ROM without enabling it. Symptom: zeros or 0xFF, "55AA NO". Find: print the ROM BAR's raw value and the enable bit. Fix: set bit 0, read, restore (forensic lab).
    • 

  • Sizing BARs in a "read-only" tool. Symptom: none on QEMU, possible hangs on hardware with an active driver. Fix: print the current values only.
    • 

  • Trusting 0xC0000. Symptom: a valid-looking image whose hash matches no file. Fix: read the device's ROM through its ROM BAR (Layer 3).
    • 

  • Using byte 2 as the image length. Symptom: wrong checksum on images where the run-time size differs. Fix: use the PCIR length for the checksum (Listing 1 line 38).
    • 

  • Forgetting the restore on an error path. Symptom: the ROM stays enabled. Fix: compute everything between the two writes and return only after the restore, as Listing 2 does.
    • 

  • Assigning a ROM address. Symptom: a "fixed" probe that now conflicts with another device's BAR. Fix: if the firmware assigned none, report it and stop.
    •
