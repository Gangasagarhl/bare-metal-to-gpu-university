Story hook

The drama club has learned to run the hall's projector by itself (F4-46). Now it wants more: to run one piece of the theatre company's stage machinery, say the scenery lift, without the company's crew. Before anyone touches the lift, the club's teacher asks for a written report: what powers the lift, which levers and which switches, where the instructions are, which parts nobody has written down, what can go wrong and how to stop it safely, and how the club will know it worked. The teacher adds one more line: "If the report shows we cannot do it safely, the report is the result, and that is fine."

That report is a feasibility study. Milestones G4 and G6 ask for one, and both accept stopping after it. This chapter teaches how to write a study that a reviewer can check, builds the reference renderer that G6's acceptance test needs, and shows why "the documented rasterisation rules" is not a detail.

What you will be able to do

  • Write a feasibility study for one GPU engine: firmware, register blocks, documents, gaps, risks, a stop criterion, a verification method, each item with a source or an UNVERIFIED mark.
  • Check a study draft mechanically against the acceptance test of G4 and G6.
  • Explain what a fill rule is and why a pixel-exact reference needs the hardware's documented rule.
  • Build a CPU reference renderer with integer edge functions and a top-left rule.
  • Diagnose a pixel comparison that fails along shared edges.
Jargon box
Feasibility study
Simple words: a careful written check of whether a project can be done, before doing it. Analogy: the drama club's report on the scenery lift. Precise: in Track G, a document that "lists every firmware blob, register block and documentation gap needed" (G4) for one engine and one job, with risks, a stop criterion and a verification method; an acceptable outcome on its own for G4 and G6. D4
Stop criterion
Simple words: a rule, written in advance, for when to stop. Analogy: "if we cannot find out how the lift's brake works, we do not touch the lift". Precise: a condition in a study (for example, "the power-up sequence cannot be documented from the guide or the open driver") that ends the project after the study, decided before effort or hope can bias it. R2
Rasterisation
Simple words: working out which pixels a shape covers. Analogy: deciding which floor tiles of the stage a painted triangle touches. Precise: converting a primitive (here a triangle in screen coordinates) into the set of pixel samples it covers, usually by testing each pixel centre against the triangle's three edge functions. R1
Edge function
Simple words: a calculation that says on which side of a line a point is. Analogy: standing on a chalk line and asking "am I to its left or right?". Precise: for an edge from a to b and a point p, (b.x − a.x)(p.y − a.y) − (b.y − a.y)(p.x − a.x); its sign tells the side, zero means on the line; for a consistently wound triangle, a point is inside when all three are non-negative (subject to the fill rule). R1
Fill rule (top-left rule)
Simple words: the tie-break for pixels exactly on the edge of a shape. Analogy: a tile on the line between two painted triangles belongs to exactly one of them, by an agreed rule. Precise: a convention that includes a pixel whose centre lies exactly on an edge only if that edge is a "top" or "left" edge, so that triangles sharing an edge cover each pixel exactly once; which rule a given GPU applies is defined by its documentation. R1 D1
Control list (VideoCore IV)
Simple words: the list of instructions the Raspberry Pi's 3D core reads to draw. Analogy: the running order for one show. Precise: a sequence of packets in memory that the VideoCore IV 3D core's binner and renderer execute (state, primitives, tile operations), named in curriculum G6 and defined in Broadcom's architecture guide. D1 D4

Layer 1 — the kid explanation

Before you try to run a big machine you have never used, you write down what you know and what you do not know: what makes it go, where its instructions are, what could break, and how you would stop. Sometimes the list shows that you should not try yet. That is a good result, because you found out without breaking anything.

And when you test your drawing of a triangle against a "correct" picture, both pictures must follow the same rule for pixels exactly on the line. Otherwise the test complains about pixels that are not wrong at all.

Layer 2 — the student explanation

What G4 and G6 ask

G4 is "One real engine, under Linux first": prototype a small, well-documented piece on real hardware, for example a DMA copy with the SDMA engine of an older AMD GPU through the existing amdgpu interfaces, then study what it would take from your own kernel. G6 is "A 3D job on Broadcom VideoCore IV": on a Raspberry Pi 3 or 2, from your own kernel, clear a render target and draw one triangle with a fixed shader, then read back the result. Both build "a written feasibility study, then the prototype if it is feasible", and both accept stopping after the study. D4

The study's contents follow from G4's acceptance test: "every firmware blob, register block and documentation gap needed". The course adds three items that make a study reviewable: risks (what can go wrong, and how it is recovered), a stop criterion, and a verification method for the prototype. And every item names its source or says UNVERIFIED, the same discipline these chapters follow. D4 R2

Checking a study mechanically

Listing 2 reads studies in a one-item-per-line format and checks two rules: all six required kinds are present (firmware, register, doc, gap, stop, verify), and no item lacks a source. R2 runs it on two drafts. The G4 draft for an SDMA copy has six items but no firmware item and no stop item: not acceptable yet. That is a real omission, not a formality: on AMD GPUs the copy engines run microcode loaded by the driver (curriculum 16.1 lists command-processor and other microcode for every generation), so a study that does not name it has missed the first thing a cold GPU needs. The G6 draft for VideoCore IV has all six kinds, three items marked UNVERIFIED: complete enough to review. A checker cannot judge whether an item is true; it makes sure nothing is missing or unsourced, so a reviewer's time goes to the content. R2 D4

The reference renderer

G6's acceptance test compares "the rendered buffer, read back ... pixel by pixel" with "a CPU-rendered reference of the same triangle within the documented rasterisation rules". Listing 1 is such a reference. It works in integer coordinates of 1/16 pixel, evaluates the three edge functions at every pixel centre, and includes a pixel when all three are non-negative, with a top-left fill rule deciding pixels exactly on an edge. R1's last image is a single triangle with 87 covered pixels and a hash (fnv1a 0xa0c16850) that a test can compare. R1

Layer 3 — the engineer's depth

Why the fill rule matters

Listing 1's first test is the hard case: a square whose corners lie on pixel centres, split along its diagonal into two triangles, so that every edge passes through a row or column of pixel centres. With the top-left rule, the square covers 8 × 8 = 64 pixels, each exactly once (R1). With an inclusive rule (count every centre with all three edge values ≥ 0), it covers 81 pixels: 72 once and the 9 on the diagonal twice; the right column and bottom row are drawn although they lie on the square's far edges. The two renderers differ in 25 pixels. R1

Both renderers are "correct" in the sense that they draw the triangles; they differ only in a convention. A pixel-exact test is only meaningful when the reference uses the same convention as the hardware, which is why G6 says "within the documented rasterisation rules": the oracle must come from the hardware's documentation, not from the learner's preference. Double coverage also matters beyond tests: with blending, a pixel drawn twice on a shared edge shows as a visible seam. R1 D4

Not verified — check before relying on this

Which fill rule VideoCore IV applies, the subpixel precision of its rasteriser, and whether its sample point is the pixel centre are not verified: Broadcom's "VideoCore IV 3D Architecture Reference Guide" (D1) was not opened. Listing 1's top-left rule is the convention described in common graphics literature, written from the author's memory; it is the reference only after D1 confirms it. If D1 specifies another rule or precision, change top_left and SUB and re-run.

What a G6 prototype involves

Curriculum G6's Build line names the pieces: a memory allocator for GPU-visible buffers, binning and rendering control lists built by your kernel, a precompiled fixed shader, job submission and completion interrupt handling. The study draft in study_check.in adds the questions that decide feasibility: how the 3D block is powered and clocked (from the guide, the vc4 driver, or a firmware mailbox call), and how a hung binner is recovered, because the acceptance test also requires that "a malformed control list produces a reported GPU error and the GPU recovers for the next job". Recovery is half the test. D4 D2

Untested in this build

No G4 or G6 prototype was built or run: the build container has no AMD GPU and no Raspberry Pi. What ran is the reference renderer (R1) and the study checker (R2). The G4 and G6 study drafts in study_check.in are teaching examples written by the author; their items marked UNVERIFIED are exactly that, and items with a named source were not checked against that source in this build.

Safety

G4: spare PC only, data you do not need (curriculum safety box); prototype through amdgpu from Linux first, where the driver can reset a hung engine; never load firmware from an unknown source. G6: a Raspberry Pi dedicated to the experiment, with its SD card backed up; power the board from its specified supply; a hung GPU may need a power cycle.

Linux first

G4's title contains the method: "under Linux first". Before your kernel touches an engine, make the same job work through the existing driver (for G4, through amdgpu's interfaces; for G6, the vc4 kernel driver and Mesa's control-list code are the open references). You then have a known-good trace to compare with, a driver that can recover from your mistakes, and a working job whose every step you can move into your kernel one at a time. D4 D2 D3

How the hardware actually does it

A hardware rasteriser does what Listing 1 does, but incrementally and in parallel: it sets up the three edge functions once per triangle in fixed-point, steps them by constant increments from pixel to pixel and from tile to tile, and tests many samples per clock. VideoCore IV is a tile-based design: a binner first sorts primitives into screen tiles, then a renderer processes each tile in on-chip memory and writes it out, which is why G6 speaks of binning and rendering control lists. D4

Not verified — check before relying on this

The description of incremental edge-function evaluation in hardware and of VideoCore IV's tiling is from the author's memory and curriculum G6's wording (D4); it was not checked in D1.

Worked example

One pixel on the diagonal, by hand. Units of 1/16 pixel. Square corners a = (72, 40), b = (200, 40), c = (200, 168), d = (72, 168). Pixel (5, 3) has centre p = (88, 56).

  1. Triangle a, b, c: edge(a, b, c) = (128)(128) − 0 = 16,384 > 0, clockwise in y-down space, no swap.
  2. The diagonal is the edge c → a of this triangle (edge w1 in Listing 1 tests v2 → v0). edge(c, a, p) = (72 − 200)(56 − 168) − (40 − 168)(88 − 200) = (−128)(−112) − (−128)(−112) = 0: p lies exactly on the diagonal.
  3. Is c → a top-left? It is not horizontal, and it goes from y = 168 to y = 40, upwards (b.y < a.y): a left edge. Bias 0; 0 ≥ 0, so with the other two edges positive, triangle a, b, c includes (5, 3).
  4. Triangle a, c, d contains the same diagonal as a → c, going downwards: not top-left, bias −1; 0 − 1 < 0, so this triangle excludes (5, 3). Exactly one triangle draws it.
  5. With the inclusive rule both include it: one of the nine "2" pixels in R1.

Where the analogy breaks


    

  • The lift's manual exists somewhere. For many GPU engines, no manual exists at all, and the gap list is the main result of the study.
    • 

  • Stopping costs nothing on stage; it costs effort here. A study that ends in "stop" may represent weeks of reading. The curriculum counts it as a result so that the effort is not wasted.
    • 

  • Tiles on a stage floor have no "exactly on the line". Pixel centres can lie exactly on an edge, and only an agreed rule decides; the analogy hides why a rule is needed at all.
    • 




Common mistakes and debugging


    

  • A study without firmware. Symptom: the prototype does nothing on a cold GPU. Fix: start the inventory with what must be loaded (R2's G4 draft).
    • 

  • No stop criterion. Symptom: the project runs on long after the evidence says stop. Fix: write the criterion first.
    • 

  • Reference with the wrong fill rule. Symptom: mismatches only along edges (forensic lab). Fix: confirm the rule in the documentation.
    • 

  • Floating-point reference. Symptom: different results on different machines or compilers along edges. Fix: integer edge functions with documented subpixel precision.
    • 

  • Skipping recovery. Symptom: the first malformed control list needs a power cycle. Fix: test the error path before the happy path is perfect; G6 requires it.
    •

Forensic lab


Scenario. A learner's G6 prototype draws the square of Listing 1 as two triangles on a Raspberry Pi, reads the buffer back and compares it with their reference. The comparison reports 25 pixels different, all on the diagonal and along the right and bottom edges. They conclude the GPU is "slightly broken". To show what the two possible pictures look like, the evidence pack uses Listing 1's two renderers (no hardware was involved).


Evidence pack: R1 (above): the top-left picture, the inclusive picture, and "pixels that differ between the two renderers: 25".


Questions.


    

  1. Observation: where are the 25 differing pixels, and how many of them are drawn twice in one picture?
    2. 

  2. Hypotheses: (a) the GPU is faulty; (b) the reference and the GPU use different fill rules; (c) the vertex coordinates were converted differently. What pattern would each produce?
    3. 

  3. Root cause: what does the pattern in R1 point to, and what can you not decide from it alone?
    4. 

  4. Fix: what must the learner read, and what do they change?
    5. 

  5. Prevention: which test case should every reference renderer include, and why?
    6. 



Method hints. A faulty GPU rarely fails only on edges; a rule difference only ever does. Count: 9 diagonal pixels plus 8 + 8 on the far edges.

Summary


    

  • A feasibility study inventories firmware, registers, documents, gaps and risks, and defines a stop criterion and a verification method; every item is sourced or marked UNVERIFIED.
