Story hook

Kofi sends an order into the great kitchen hall: "square every number on this list, 65,536 of them". He wants it fast, so he writes on the order slip: "use tables of 2,048 helpers each". The hall has no tables that big. The door-keeper reads the slip, writes "refused: impossible table size" in the hall's logbook, and does not send a single helper to work. Kofi does not read the logbook. He waits a moment, collects the results tray (empty, as it was when he left it) and reports: "every square is zero".

Nobody lied to Kofi. The hall wrote the reason down in the place where it always writes reasons. Kofi's program never looked. This chapter is about looking every time: after every call, after every launch, and, for the mistakes that happen deep inside the work itself, with an inspector who watches every helper's every step.

What you will be able to do

  • Check every CUDA runtime call and every launch with a small helper that reports the error name, the call text, the file and the line.
  • Explain the two moments at which a launch can fail (when it is made, and while the kernel runs) and where each error becomes visible.
  • Distinguish cudaGetLastError from cudaPeekAtLastError, and an ordinary error from one that ruins the whole process.
  • Run Compute Sanitizer's memcheck tool on a kernel and read what it should report for an out-of-bounds write.
  • Diagnose "the kernel that silently did nothing" from its evidence.
Jargon box
Error code (cudaError_t)
Simple words: the number every CUDA runtime function returns to say "it worked" or what went wrong. Analogy: the line the door-keeper writes in the logbook. Precise: an enumeration in driver_types.h; cudaSuccess means no error; each other value has a name (cudaGetErrorName) and a description (cudaGetErrorString). H1
Launch error
Simple words: a launch refused before any thread runs, for example because the block is too big. Analogy: the door-keeper refusing an impossible table size. Precise: such as cudaErrorInvalidConfiguration, which the header describes as "a kernel launch is requesting resources that can never be satisfied by the current device"; the launch syntax returns no value, so it is read with cudaGetLastError. H1
Asynchronous error
Simple words: an error that happens while the kernel runs and is reported by a later call. Analogy: a helper dropping a jar in the far pantry; you hear about it the next time you talk to the hall. Precise: because a launch returns before the kernel ends, errors inside the kernel (such as cudaErrorIllegalAddress) are returned by a later synchronizing or other runtime call. D1
Sticky error
Simple words: an error after which the GPU cannot be used again in this process. Analogy: the hall is closed for the rest of the day; every new order comes back with the same note. Precise: the header for cudaErrorIllegalAddress: "This leaves the process in an inconsistent state and any further CUDA work will return the same error. To continue using CUDA, the process must be terminated and relaunched." H1
Compute Sanitizer
Simple words: a tool that runs your program and watches every memory access and synchronisation of every GPU thread. Analogy: an inspector who follows every helper and notes each reach into the wrong shelf. Precise: NVIDIA's correctness tool compute-sanitizer with sub-tools memcheck (memory access checking, the default), racecheck, synccheck and initcheck, as listed by its own help. R5

Layer 1 — the kid explanation

When you ask the hall to do something, the hall always answers with a little note: "done" or "not done, because…". If you never read the notes, you will not know when something went wrong, and you may carry home an empty tray and think it is the answer. So you read the note after every request.

Some problems happen at the door: you asked for something impossible, and the hall refuses at once. Other problems happen inside, while the helpers are working: one of them reaches for a shelf that does not exist. You do not hear about that straight away, because you were not waiting at the door; you hear about it the next time you ask the hall anything. And some mistakes are so bad that the hall closes for the day: every later request gets the same "closed" note. For the mistakes that leave no note at all (a helper writing on the wrong shelf without being caught), you invite an inspector who follows every helper and writes down each wrong move.

Layer 2 — the student explanation

Every call returns an error code

Nearly every CUDA runtime function returns a cudaError_t. cudaSuccess means it worked; anything else has a name such as cudaErrorNoDevice and a one-line description you can print with cudaGetErrorName and cudaGetErrorString. H1 Ignoring the returned value is legal C++, and the compiler does not warn, which is exactly why unchecked programs are common. The fix is mechanical: wrap every call. Listing 1 is the helper this course uses from here on. The macro CUDA_CHECK(call) passes the call's result, the call's own text (#call), the file and the line to a function that prints all four and stops the program. A failed run then says precisely where it failed: in this build, Listing 2 printed scale.cu:19: cudaMalloc(&d, n * sizeof(float)) failed: cudaErrorNoDevice (no CUDA-capable device is detected). R2 Compare that with "the answer is zero".

A launch has no return value

kernel<<<blocks, threads>>>(args) is not a function call that returns an error code. The runtime records a launch failure as the "last error", which you read with cudaGetLastError() immediately after the launch. H1 A launch that asks for more threads per block than the device allows, or more shared memory, fails this way with cudaErrorInvalidConfiguration, and the kernel does not run at all. H1 Kofi's 2,048 threads per block is such a request on every NVIDIA GPU this author knows of, whose limit is 1,024; check maxThreadsPerBlock in your device report (F6-07). On TG-1, the university's teaching GPU, the limit is 512. cudaGetLastError also resets the last error to success; cudaPeekAtLastError returns it without resetting. H1 Listing 3's part 3 shows the difference on the TG-1 model: peek, peek, get all report the error; the second get reports success. R3

Errors inside a kernel arrive later

The launch returns as soon as the work is queued (F6-01). If a thread then writes to an address that does not belong to the program, the GPU detects it while the host is already doing something else. The host learns about it from the next call that waits for the GPU or otherwise talks to it, for example cudaDeviceSynchronize or the next cudaMemcpy, and the error is reported there, not at the launch. D1 The header describes two such errors, cudaErrorIllegalAddress ("The device encountered a load or store instruction on an invalid memory address") and cudaErrorLaunchFailure ("An exception occurred on the device while executing a kernel"), and adds for both: "any further CUDA work will return the same error. To continue using CUDA, the process must be terminated and relaunched." H1 So the line number in the error message points at the call that noticed the error, not at the kernel that caused it. In a debug build, Listing 1's CUDA_CHECK_LAUNCH() with CU201_DEBUG_SYNC defined synchronizes after every launch, so the error is noticed right after the guilty kernel. That costs speed (the host waits every time), which is why it is a debug option and not the default.

When no error code appears: Compute Sanitizer

Not every bug produces an error code. A thread that writes one element past the end of an array often lands in memory the program owns anyway (another allocation, padding), so nothing is detected and some other value is silently overwritten. Compute Sanitizer runs the program under supervision and checks every access. Its help lists four tools: memcheck ("Memory access checking", the default), racecheck ("Shared memory hazard checking"), synccheck ("Synchronization checking") and initcheck ("Global memory initialization checking"). R5 Listing 4 is a kernel without its bounds check: 1,024 threads write into 1,000 elements. Under compute-sanitizer --tool memcheck the expected report is an invalid write for each of the 24 extra threads, naming the kernel and, because the program was built with -lineinfo, the source line. In this build the tool could not run: it printed Unable to find injection library libsanitizer-collection.so and exited with status 13. R4 E1 requires that the sanitizer "reports no errors" on your E1 programs; that has to be checked on the lab GPU. C1

Errors at compile time

Some mistakes never reach the GPU. A kernel may call only functions compiled for the device. Listing 5 calls an ordinary function from a kernel; nvcc refuses with calling a __host__ function("twice(int)") from a __global__ function("useTwice") is not allowed. R6 Marking the function __host__ __device__ compiles it for both sides. Compile errors are the cheapest errors; this course compiles with -Werror all-warnings so that warnings are treated the same way.

Layer 3 — the engineer's depth

One analogy sentence: the logbook has one "last line" per helper thread of yours, and some entries close the hall for good. The engineering consequences:

  • Last error is per host thread. The header: cudaGetLastError "Returns the last error that has been produced by any of the runtime calls in the same instance of the CUDA Runtime library in the host thread". A launch error in one host thread is not seen by another thread's check; and a library that links its own copy of the runtime statically has its own last error ("Multiple instances of the CUDA Runtime library can be present"). H1
  • Sticky errors end the process. After cudaErrorIllegalAddress or cudaErrorLaunchFailure, the only recovery is to restart the process (H1). A test harness that runs many kernels should therefore run each risky test in its own process, or stop at the first sticky error and say so.
  • Exiting from the check is a choice. Listing 1 calls std::exit. That is right for labs and tools. A library must instead return or throw the error to its caller (F2-16); the harness of F6-06 keeps the exit for simplicity and says so.
  • The sanitizer slows the program and changes its timing, so never time under it. It also cannot see bugs on code paths your test does not execute: run it on the same sizes as your correctness tests, including the odd ones.
  • Debuggers. cuda-gdb lets you stop inside a kernel and inspect one thread's variables. It is outside CU201's labs; this build did not try it.
  • HIP follows the same pattern with hipError_t, hipGetLastError and hipGetErrorName, declared in the HIP 5.7 header read in this build (H2); F6-06's HIP slot uses them.

How the hardware actually does it

A launch passes through two checks. On the host, the runtime and driver compare the execution configuration with the device's limits (threads per block, shared memory per block, grid size) before anything is sent; a request that "can never be satisfied by the current device" is refused there (H1). This is why a configuration error appears at cudaGetLastError right after the launch. If it passes, the launch is queued for the GPU and the host continues.

On the GPU, every load and store goes through address translation: device memory, like host memory, is accessed through page tables. An address that maps to nothing raises a fault, which stops the kernel; the driver records it and reports it to the next runtime call that checks the GPU's state. D3 An address that is wrong but still maps to memory the program owns (the next allocation, or padding after an array) raises nothing; only a tool that knows the size of every allocation, like memcheck, can call it an error. That is the reason the sanitizer exists: hardware protection works at page granularity, not at array granularity.

Note

The page-table explanation above is a model consistent with the header's description of cudaErrorIllegalAddress and with how host virtual memory works (HW203); this build did not open a source that describes the GPU's memory management unit, and the details differ by GPU generation (D3).

Worked example

Task. Using the TG-1 model (Listing 3), predict and then confirm what each call returns in this sequence: a kernel without bounds check is launched with 4 blocks of 256 threads for an array of 1,000 elements; then cudaGetLastError; then cudaDeviceSynchronize; then a copy; then another launch.

  1. Launch. 256 threads per block is within TG-1's 512, and no shared memory is requested, so the configuration is valid: cudaSuccess.
  2. Get last error. The launch was accepted, and the kernel's fault has not been reported yet: cudaSuccess. (A check here is not enough.)
  3. Synchronize. 4 × 256 = 1,024 threads; threads 1,000 to 1,023 write out of range; the fault is reported now: cudaErrorIllegalAddress.
  4. Copy and next launch. The error is sticky: both return cudaErrorIllegalAddress.
  5. Confirm. Listing 3's part 4 prints exactly this sequence. R3 On a real GPU, as the model's comment says, an out-of-range write can also land in memory the program owns and raise nothing; the model always faults, which is the case the header describes.

Where the analogy breaks


    

  • A door-keeper would shout; the runtime only writes. Nothing interrupts your program when a launch is refused; the error waits until you ask (Layer 2).
    • 

  • A real kitchen's "closed for the day" ends at midnight; a sticky CUDA error ends only with the process. No call reopens the hall (H1).
    • 

  • An inspector in a kitchen does not slow the cooks much; Compute Sanitizer slows the program a lot and must never be used while timing.
    • 

  • A wrong shelf in the kitchen is always noticed by someone; on the GPU an out-of-bounds write to memory the program owns is noticed by nobody unless a tool checks every access.

Hypotheses. (a) The kernel computes wrong values: ruled out by reading line 11 (squares are not zero for non-zero inputs). (b) The input was not copied: possible, unchecked. (c) The kernel did not run: possible, unchecked. (d) The result was not copied back: possible, unchecked. Every hypothesis except (a) involves an unchecked call.


Root cause. Line 25: 2,048 threads per block exceeds the device's limit, the launch on line 26 is refused with cudaErrorInvalidConfiguration (shown by the model with the check, R3; meaning from H1), no thread runs, and line 27 copies back dOut's unwritten content. Zero, not random, is consistent with fresh device memory reading as zero, but CUDA does not promise that: never rely on it.

Two different causes give the same symptom; only checks tell them apart. With CUDA_CHECK on every call, this build would stop at line 22 with cudaErrorNoDevice, and the lab GPU would stop after line 26 with cudaErrorInvalidConfiguration.


Fix and prevention. Use 256 threads per block (or any size within maxThreadsPerBlock); check every call and every launch (Listing 1); make the program verify at least one known output and return a non-zero status otherwise. How the evidence was produced: the real program was compiled and run in this build (no GPU); the launch refusal is reproduced on the TG-1 model; the GPU behaviour is predicted from the header, not measured.
