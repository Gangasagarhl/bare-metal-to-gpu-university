Story hook

A new cook, Nadia, joins a chain of kitchen halls. Before she plans a single order she walks through her hall with a notebook: how many rows of helpers are there, how many helpers in a row, how big is the pantry, what generation of equipment is this hall (the new ovens or the old ones)? Then she does something most new cooks skip: she compares her notebook with the chain's official sheet for that hall. Her pantry, she wrote, holds "8192"; the sheet says "8 GB". Same pantry, different units; but a computer comparing the two would say "mismatch", and it would be right to ask.

Later the same week a recipe that worked perfectly in the hall across town fails in hers with a note on the door: "no recipe card for this kind of hall". The cards had been printed only for the newer hall. This chapter is about knowing your GPU exactly, writing it down in a form a program can check, and making sure the code you ship has a version your GPU can run.

What you will be able to do

  • Print a device report from cudaGetDeviceProperties with the facts every benchmark table needs.
  • Explain each field in the header's own words, and what compute capability, SM count and warp size mean for your code.
  • Compare your report with a vendor tool's numbers key by key, with units, and pass the E1 device-report test.
  • Read runtime and driver version numbers and explain what each one means.
  • Choose code-generation targets so that your program contains machine code or PTX your GPU can use, and diagnose "no kernel image is available".
Jargon box
Device query
Simple words: asking the runtime what GPU you have and what its limits are. Analogy: Nadia's walk through the hall with a notebook. Precise: cudaGetDeviceCount and cudaGetDeviceProperties, which fill a cudaDeviceProp structure; NVIDIA's deviceQuery sample prints the same structure. H1 D2
Compute capability
Simple words: the generation-and-version number of an NVIDIA GPU's design, like 8.0 or 9.0. Analogy: which generation of equipment the hall has. Precise: major and minor in cudaDeviceProp ("Major compute capability", "Minor compute capability"); nvcc names real targets after it (sm_80 for 8.0). H1 R3
Driver version and runtime version
Simple words: two numbers: the newest CUDA the installed driver supports, and the CUDA version your program was built with. Analogy: what the hall's door-keeper understands, and which edition of the recipe book you wrote from. Precise: both "(1000 × major + 10 × minor)"; the runtime version is, as of CUDA 12.0, "a compile-time constant stating the CUDA Toolkit version". H1
Fatbinary
Simple words: the GPU part of your program, which can hold several versions of each kernel for different GPUs. Analogy: a folder of recipe cards printed for different kinds of hall. Precise: a container embedded in the executable holding machine code (cubin ELF) for real targets (sm_XX) and/or PTX for virtual targets (compute_XX); cuobjdump --list-elf and --list-ptx list them. R4 D3
Vendor tool
Simple words: the GPU maker's own program that reports the same facts, used as the reference. Analogy: the chain's official sheet for the hall. Precise: for E1, NVIDIA's deviceQuery sample or AMD's rocminfo; nvidia-smi also reports memory and driver. C1

The idea in pictures

Figure 1 shows the two checks of this chapter: the report compared with the vendor's numbers, and the fatbinary compared with the GPU's compute capability.

Layer 1 — the kid explanation

Before you plan work for a hall, you count: how many rows, how many helpers per row, how big the pantry is, what kind of equipment it has. A program can ask the GPU these questions and get exact answers. You write the answers down, one per line, so that another program can read them.

Then you check your notes against the maker's official sheet, because a note with the wrong unit ("8192" instead of "8 GB") is wrong even if the pantry is the same. And you make sure that the recipe cards you bring are printed for this kind of hall; a card for a newer kind of hall is useless here, and the hall will say so instead of cooking.

Layer 2 — the student explanation

The device report

cudaGetDeviceProperties(&p, d) fills a cudaDeviceProp for device d. The installed CUDA 12.0 header describes every field in one line; the ones the course harness prints are shown in the "header_fields" tool run below, for example multiProcessorCount: "Number of multiprocessors on device", warpSize: "Warp size in threads", totalGlobalMem: "Global memory available on device in bytes", maxThreadsPerBlock: "Maximum number of threads per block", memoryBusWidth: "Global memory bus width in bits". H1 Listing 1 prints them as key=value lines. That plain format is deliberate: a person can read it, a program (Listing 2) can compare it, and the harness can put it on top of every result table, so that every measurement carries the name of the GPU it was made on.

What the fields mean for your code: sm_count and the per-SM limits decide how many blocks run at once (F1-58); warp_size is the width of the row of helpers that act together (F6-02); max_threads_per_block is the limit that Kofi's launch broke in F6-05; memory_bus_width_bits enters the peak-bandwidth formula of F6-09; async_engine_count says how many copies can overlap with kernels (CU303).

Two version numbers

The report starts with two numbers. cudaDriverGetVersion returns "the latest version of CUDA supported by the driver … as (1000 × major + 10 × minor)", or 0 "If no driver is installed". cudaRuntimeGetVersion returns the runtime's version in the same format; "As of CUDA 12.0, this function no longer initializes CUDA. The purpose of this API is solely to return a compile-time constant stating the CUDA Toolkit version". H1 In this build the report printed runtime_version=12000 (toolkit 12.0) and driver_version=13000 (a driver library supporting CUDA 13.0 is present in the container, but no GPU). R1 If the driver's number is lower than the runtime's, the program may fail with cudaErrorInsufficientDriver: "the installed NVIDIA CUDA driver is older than the CUDA runtime library". H1

A lesson in the output itself

Look at this build's output of Listing 1 (below): the error message from line 15 appears before the two version lines, although the program printed the versions first. R1 The versions go to stdout, which is buffered when it goes to a file; the error goes to stderr, which is not; the buffer is written out only when the program exits. When you read a log, the order of lines from the two streams is not the order of events. This is why Listing 1 of F6-05 writes errors to stderr: they appear even if the program dies before flushing.

Comparing with the vendor's numbers

E1's acceptance test is precise: "Your device report matches deviceQuery / rocminfo for SM or CU count, memory size, warp/wavefront size and compute capability or gfx target." C1 Matching means "same value in the same unit". Listing 2 reads lines ours key=value and vendor key=value and compares the four required keys. Its input in this build is invented (TG-1 values, no GPU), with one planted error: our memory in bytes, 8,589,934,592, and the vendor's in MiB, 8,192. The program says MISMATCH and FAIL, correctly, although 8,192 MiB × 1,048,576 = 8,589,934,592 bytes is the same pantry. R2 The fix is to convert to one unit before comparing, and to write the unit in the key name (memory_bytes), not to loosen the comparison.

Does my program contain code for my GPU?

nvcc compiles kernels for targets. A real target such as sm_80 produces machine code (SASS in a cubin) for compute capability 8.0; a virtual target such as compute_90 produces PTX, which the driver can compile for the GPU when the program starts. This build's nvcc can generate machine code for 14 real targets from sm_50 to sm_90 (nvcc --list-gpu-code). R3 Building SAXPY with only -gencode arch=compute_90,code=sm_90 gives a fatbinary with one ELF (sm_90.cubin) and no PTX at all: cuobjdump says "No PTX file found". R4 On a GPU of capability 8.0, nothing in that file is usable, and the launch fails with cudaErrorNoKernelImageForDevice: "there is no kernel image available that is suitable for the device. This can occur when a user specifies code generation options for a particular CUDA source file that do not include the corresponding device configuration." H1 The fixed build lists sm_80 and sm_90 machine code plus compute_90 PTX. R5

The vendor's documentation

The device report gives limits; the vendor's documents explain them. For NVIDIA: the CUDA C++ Programming Guide's table of features and technical specifications per compute capability, the architecture tuning guide for your generation, and the GPU's datasheet or whitepaper for memory type and clock. D1 For the course's numbers, the rule is: values your program reads from the device beat values from a document; documented values beat values from memory; and a datasheet's peak numbers are "context, not the target" (C1, 13.4).

Layer 3 — the engineer's depth

One analogy sentence: the hall's equipment generation decides which recipe cards it can read, and a card written in the general recipe language can be translated on the spot, but only for halls at least as new as the card. The engineering consequences:

  • Choosing targets. Ship machine code for each capability you test on, plus PTX for the newest virtual target, so that newer GPUs can compile it at start-up. The cost is a larger binary and, for the PTX path, a start-up compile (part of the first-run cost of F6-06).
  • Compatibility direction. Machine code for sm_80 runs on GPUs of capability 8.x with x ≥ 0 within the same major version; PTX for compute_90 can be compiled for capability 9.0 and later, never for older GPUs. Hence the fixed build of R5 needs its own sm_80 code for an 8.0 GPU.
  • Several GPUs. device_count may be more than one; the harness must say which device each row was measured on (Listing 1 prints a section per device and the PCI bus id).
  • What the report does not contain. Clock frequencies and power limits are not in this report in a form the course relies on; record them from the vendor's management tool, with the setting of the protocol's "fixed clocks" (C1).
  • AMD. HIP has hipGetDeviceProperties with a similar structure; the "warp" is a wavefront, whose size is 64 on many AMD GPUs and 32 on others; the compute-capability equivalent is the gfx target (for example gfx90a, the target this build's HIP code was compiled for). The F7 courses cover it.
Not verified — check before relying on this

The compatibility rules in the second bullet (machine code runs within the same major capability on equal or newer minor versions; PTX is compiled only for equal or newer capabilities), the statement that the driver compiles PTX at program start, and the wavefront sizes in the last bullet are from memory. Check the CUDA C++ Programming Guide sections on compute capability and application compatibility and the nvcc documentation on -gencode (D1, D3), and test on the lab GPU (lab step 4). This build observed only the fatbinary contents (R4, R5) and the header's description of the error (H1).

How the hardware actually does it

Most of the report is not measured: the driver knows the GPU's model from its PCI identity and reads its configuration, then answers from tables and from registers of the chip. totalGlobalMem is the memory the driver makes available, which can be slightly less than the memory on the board; pciBusID is the GPU's address on the PCI Express bus, the same number lspci shows on Linux (F1-62). H1 Compute capability names the SM's instruction set and features: SASS for one capability is a different machine language from SASS for another, which is why a cubin for sm_90 cannot run on an 8.0 GPU and the driver refuses with cudaErrorNoKernelImageForDevice. PTX is the stable intermediate language (F6-01) from which the driver's own compiler can produce SASS for the GPU in front of it.

Note

"Answers from tables and registers" and "slightly less than the board memory" describe the usual behaviour and are consistent with the header's field descriptions; they are not documented in a source opened in this build. Compare your report's memory_bytes with the board's specification in the lab.

Worked example

Task. TG-1's datasheet (the university's invented teaching GPU) says: 4 SMs, warps of 32, 8 GiB of memory, "teaching capability TG.1". A student's report prints sm_count=4, warp_size=32, memory_bytes=8589934592, compute_capability=TG.1, and the vendor tool prints memory as "8192 MiB". Decide whether E1's device-report test passes.

  1. SM count. 4 = 4: ok.
  2. Warp size. 32 = 32: ok.
  3. Capability. TG.1 = TG.1: ok.
  4. Memory. Convert the vendor's value: 8,192 MiB × 220 bytes/MiB = 8,192 × 1,048,576 = 8,589,934,592 bytes. Equal to ours. (And 8 GiB = 8 × 230 = 8,589,934,592 bytes: the datasheet agrees too.)
  5. Verdict. The test passes after converting the vendor's number to bytes; written as raw strings, Listing 2 correctly reports a mismatch (R2). The record of the test must show the conversion.
  6. Careful with GB. If a datasheet said "8 GB" meaning 8 × 109 bytes, that is 589,934,592 bytes less than 8 GiB. Always find out which one is meant.

Where the analogy breaks


    

  • A cook can count helpers by looking; a program can only believe what the driver says. If the driver is wrong or old, so is the report: that is why E1 compares with a second tool.
    • 

  • A recipe card for an older hall usually works in a newer one; GPU machine code does not cross major generations (unverified box in Layer 3). Only PTX travels forward.
    • 

  • The official sheet of a kitchen chain is one document; a GPU's facts are spread over several (programming guide, tuning guide, datasheet), and some numbers in them are peaks, not what you will get.

Forensic lab answer key


Observation. One ELF for sm_90; no PTX ("No PTX file found") (R4).


Hypotheses. (a) An old driver gives cudaErrorInsufficientDriver, a different error (H1); the version numbers in the device report would show it. (b) Supported by the fatbinary listing and by the header's words "code generation options … that do not include the corresponding device configuration" (H1). (c) A kernel bug would let the launch start and produce a different error or wrong values, not "no kernel image".


Root cause. The program contains machine code only for capability 9.0 and no PTX; an 8.0 GPU cannot run sm_90 code and there is nothing to compile, so the runtime finds no suitable image and the launch fails; unchecked, the program copied back unwritten memory.


Fix. The 8.0 GPU uses the sm_80 ELF (R5). The compute_90 PTX can be compiled only for capability 9.0 and newer (from memory, see the unverified box), so it does not help an 8.0 GPU; it is there for future GPUs.


Prevention. Print the device report and the compiled-in targets at start-up and stop with a clear message when the device's capability is not covered (mini-project); check every launch (F6-05). How the evidence was produced: real nvcc and cuobjdump runs in this build; Lena's GPU failure is the scenario, its error predicted from the header, not observed.
