Story hook

The hall of helpers has a new order: brighten every square of a giant mosaic, a picture made of 600 rows of 1,000 tiles each. Yusuf, who runs the hall, does not hand out tickets numbered 0 to 599,999. That would be like reading a street address as one huge number. Instead, he lays the mosaic out on the floor and puts the tables in a grid over it: table (0, 0) in the top-left corner, table (1, 0) to its right, table (0, 1) below it. Each table has 16 rows of 16 seats, and the helper in seat (3, 5) of table (2, 1) knows exactly which tile is hers: count across, count down.

The mosaic is 1,000 tiles wide, and 1,000 does not divide by 16. So Yusuf rounds up and puts out a few extra tables along the right and bottom edges. Some helpers at those tables find no tile under their seat. They are told one rule: "If there is no tile under you, do nothing." Last year a new manager rounded down instead, to save tables. The right edge and the bottom of the mosaic stayed dark, and nobody noticed until the picture was hung on the wall. That is this chapter's forensic lab.

What you will be able to do

  • Describe the thread hierarchy (thread, block, grid) in one, two and three dimensions, with the built-in variables that name each level.
  • Compute a two-dimensional launch for an image of any size, and the pixel each thread handles, including the threads that must do nothing.
  • Write a kernel with a two-dimensional bounds check and a grid-stride loop.
  • Explain how the threads of a block are numbered into warps and why block sizes are usually multiples of 32.
  • Diagnose missing edges in an image from a coverage map.
Jargon box
Thread index (threadIdx)
Simple words: a thread's seat number at its table, with an x, y and z part. Analogy: seat (3, 5) at a table. Precise: a built-in variable of type uint3 holding the thread's coordinates within its block. D1 H1
Block index (blockIdx) and block size (blockDim)
Simple words: which table you sit at, and how many seats each table has in each direction. Analogy: table (2, 1); tables of 16 × 16 seats. Precise: built-in variables holding the block's coordinates within the grid and the block's dimensions in threads; all blocks of one launch have the same dimensions. D1
Grid size (gridDim)
Simple words: how many tables there are in each direction. Analogy: 63 tables across, 38 down. Precise: a built-in variable holding the grid's dimensions in blocks, set by the first value of the execution configuration. D1
dim3
Simple words: a small box of three numbers (x, y, z) used to give the size of a grid or a block. Analogy: "63 across, 38 down, 1 high" written on the order slip. Precise: a CUDA struct with members x, y, z; the installed header's constructor gives every missing value the default 1, so dim3 block(16, 16) means 16 × 16 × 1. H1
Row-major order
Simple words: storing a picture one whole row after another in a single long list. Analogy: reading the mosaic like a book, left to right, then the next row. Precise: element (x, y) of a width-wide array is stored at position y * width + x. D3 (Defined in MA201; used here unchanged.)
Grid-stride loop
Simple words: each thread does element i, then jumps ahead by the total number of threads and does another, until the data runs out. Analogy: each helper takes every 8th tile when there are 8 helpers. Precise: a loop for (i = global index; i < n; i += blockDim.x * gridDim.x), which makes a kernel correct for any grid size. D2
Linear thread id (in a block)
Simple words: one number for a seat, counting across a table row first, then the next row. Analogy: seat numbers painted on the chairs, row by row. Precise: for a block of size (Dx, Dy), thread (x, y) has id x + y·Dx (and + z·Dx·Dy in 3-D); consecutive ids, in groups of 32, form the block's warps. D1

Layer 1 — the kid explanation

A big job is split into teams, and each team sits at a table. All the tables together are the whole order. Every helper knows two things: which table they are at, and which seat they are in. From those two numbers, and the size of a table, each helper works out which piece of the job is theirs. Nobody needs a manager to tell them.

For a list, one number per helper is enough. For a picture, it is easier to count across and down, so tables and seats get two numbers each, like squares on a map. For a stack of pictures, you can even use three numbers: across, down and which picture.

The job is rarely an exact number of tables. So you put out enough tables to cover everything, round up, and you give every helper the same rule: "if there is no piece of work under your seat, do nothing". If you round down instead, the edges of the job are never done, and nobody complains, because nobody is there to notice.

Layer 2 — the student explanation

Three levels, up to three dimensions

A launch kernel<<<grid, block>>>(…) creates grid.x × grid.y × grid.z blocks, each with block.x × block.y × block.z threads. D1 The two values may be plain integers, as in F6-01, or dim3 values. The installed CUDA header defines dim3 as three unsigned int members with a constructor whose parameters default to 1, which is why dim3 block(16, 16) is a 16 × 16 × 1 block and a plain 256 behaves like dim3(256, 1, 1). H1 Inside the kernel, the built-ins threadIdx, blockIdx, blockDim and gridDim each have .x, .y and .z. D1 Dimensions are a convenience for you: the hardware does not care whether you think of your data as a line or a picture, but your index arithmetic becomes simpler and less error-prone when the launch has the same shape as the data.

Two-dimensional indexing

For an image of width × height pixels stored in row-major order, Listing 1 computes

int x = blockIdx.x * blockDim.x + threadIdx.x;   // column
int y = blockIdx.y * blockDim.y + threadIdx.y;   // row
if (x < width && y < height) { int i = y * width + x; … }

Each line is the one-dimensional formula of F6-01, once per direction. The bounds check now has two parts, and both are needed: the grid is rounded up in x and in y. The real PTX of Listing 1 shows the structure directly: two mad.lo.s32 instructions (one using %ctaid.x, %ntid.x, %tid.x, the other the .y registers), two compares combined by or.pred into one branch, and a third mad.lo.s32 for y * width + x. R3

Limits you must query, not remember

There is a maximum number of threads per block, a maximum size of each block dimension and a maximum size of each grid dimension. The installed header names them in the device-properties structure: maxThreadsPerBlock ("Maximum number of threads per block"), maxThreadsDim[3] ("Maximum size of each dimension of a block") and maxGridSize[3] ("Maximum size of each dimension of a grid"). H1 Their values depend on the GPU and are printed by your own device report in F6-07; this chapter does not quote them (guide AH-21). Asking for more than a limit makes the launch fail with cudaErrorInvalidConfiguration, which the header describes as "requesting too many threads or blocks" (F6-05 shows what that looks like when nobody checks). For the course's invented teaching GPU, TG-1 (F1-55), a block cannot have more than 512 threads, because a block must fit on one SM and a TG-1 SM holds 16 warps of 32 threads; the model of F6-05 uses that limit.

From threads to warps

Inside a block, threads are numbered with x changing fastest, then y, then z, giving the linear id x + y·Dx + z·Dx·Dy; the hardware forms warps from consecutive ids: ids 0–31 are the first warp, 32–63 the second, and so on. D1 In a 16 × 16 block, the first warp is therefore rows y = 0 and y = 1 of the block, 16 threads each. Two practical rules follow. A block whose thread count is not a multiple of 32 has a last warp that is partly empty, and those empty lanes still occupy a warp's place; and the threads of one warp should touch neighbouring data, which is easiest when x, the fastest-changing index, runs along a row of a row-major array (F6-08). Listing 2 prints, for a chosen pixel, its linear id and warp within the block. R2

Blocks are independent

Blocks of one grid may run in any order, at the same time or one after another; the programming model promises nothing about their order. D1 A kernel must therefore not depend on block 7 finishing before block 8 starts. Within a block, threads can cooperate (shared memory and the barrier __syncthreads(), F6-03); between blocks of the same launch, use a second launch. This independence is what lets the same program run on a GPU with few SMs and on one with many (F1-56).

The grid-stride loop

Sometimes you do not want one thread per element: the data may be larger than the grid you want to launch, or you want to reuse one launch configuration for many sizes. A grid-stride loop lets each thread handle elements i, i + stride, i + 2·stride, …, where stride = blockDim.x * gridDim.x is the total number of threads. D2 Listing 3 prints the elements each thread handles for a grid of 2 blocks of 4 threads and 21 elements: thread 0 of block 0 does 0, 8 and 16; thread 1 of block 1 does 5 and 13. R4 Notice that neighbouring threads still handle neighbouring elements at every step, which keeps the warp's accesses together (F6-08).

Layer 3 — the engineer's depth

One analogy sentence: the seat and table numbers are painted on the furniture before the helpers sit down. In hardware terms, the block and thread indices are special registers that the GPU initialises for every thread at launch; in the SASS of F6-01-style kernels you see them read with S2R … SR_CTAID.X and S2R … SR_TID.X (F1-56 reproduces such a listing). blockDim and gridDim are launch parameters, the same for every thread, and the compiler reads them from the constant bank (c[0x0][0x0] in the SASS of F6-04). D4

  • Integer width. All the built-ins are 32-bit unsigned values, and the index formulas above use int. For an array of more than about two thousand million elements (231 − 1 is the largest int), blockIdx.x * blockDim.x overflows. Use a 64-bit index (long long or std::size_t) when n can be that large; F6-08's strided copy does exactly that for i * stride. CU301's forensic lab "the reduction that is wrong only for large inputs" is this bug.
  • Signed and unsigned. blockIdx.x * blockDim.x is computed in unsigned arithmetic and then converted to int. With the sizes of this course that is harmless, but comparing an unsigned index with a negative int is a classic C++ trap (F2-02).
  • Choosing a block shape. For images, 16 × 16 (256 threads) or 32 × 8 are common starting points because x runs along rows and the thread count is a multiple of 32; the right shape for your kernel is measured, not guessed (F6-06, CU302's occupancy chapter). D2
  • Too few blocks. A grid with fewer blocks than the GPU can hold leaves SMs idle; F1-56 computes the "waves" of a launch. The grid-stride loop is often launched with a grid sized from the SM count (queried, F6-07) rather than from n.
Not verified — check before relying on this

The warp-formation rule (x fastest, consecutive ids form warps), the absence of any promised block order, and the advice on block shapes are written from memory of the CUDA C++ Programming Guide (thread hierarchy and SIMT architecture sections) and the CUDA C++ Best Practices Guide (execution configuration section). Neither document was opened in this build. Check both, for the toolkit version you use, before relying on these statements.

How the hardware actually does it

At launch, the GPU's block scheduler hands whole blocks to SMs as resources allow; a block stays on its SM until all its threads finish, and the SM sets up each thread's index registers and splits the block into warps as described above. D1 D3 Because blocks never migrate and never share an SM's shared memory, the block is the unit of cooperation and the grid is only a list of independent blocks. The dimensions of grid and block are bookkeeping for the indices; the hardware schedules warps, not "rows of the picture". F1-56 and F1-57 describe the SM and the warp in detail.

Worked example

Listing 1 brightens a 1,000 × 600 image with 16 × 16 blocks.

  1. Grid in x. (1000 + 16 − 1) / 16 = 1015 / 16 = 63 (integer division; 63 × 16 = 1008 ≥ 1000).
  2. Grid in y. (600 + 15) / 16 = 615 / 16 = 38 (38 × 16 = 608 ≥ 600).
  3. Threads. 63 × 38 blocks × 256 threads = 2,394 × 256 = 612,864 threads for 600,000 pixels.
  4. Idle threads. 612,864 − 600,000 = 12,864: columns 1000–1007 of every row and the eight rows 600–607.
  5. Who does pixel (999, 599)? x: 999 = 62 × 16 + 7, so block x = 62, thread x = 7. y: 599 = 37 × 16 + 7, so block y = 37, thread y = 7. Linear id in the block: 7 + 7 × 16 = 119; warp 119 / 32 = 3 (the fourth warp of its block).
  6. Row-major position. 599 × 1000 + 999 = 599,999, the last pixel of the image.

Where the analogy breaks


    

  • Tables in a hall are all there at once; blocks are not. A large grid does not fit on the GPU at the same time: some blocks run, finish, and only then do others start, in an order nobody promises. D1
    • 

  • Seats are arranged in a square; warps are not. A 16 × 16 table "looks" square, but the hardware groups its threads by linear id: the first warp is two rows of 16, not a 4 × 8 patch. The 2-D shape exists only in your index arithmetic.
    • 

  • A helper at an empty seat could help a neighbour; an idle thread cannot. Threads outside the data skip the work; they cannot take over someone else's pixel unless you write that logic (the grid-stride loop is one such logic).
    •

Summary


    

  • A launch creates a grid of blocks of threads; each level can have x, y and z dimensions given by dim3 (missing values default to 1).
    • 

  • threadIdx, blockIdx, blockDim and gridDim give each thread its coordinates.
    • 

  • In 2-D: x = blockIdx.x·blockDim.x + threadIdx.x, y likewise; check both against the data; i = y·width + x.
    • 

  • Round the grid up in every dimension; idle threads are normal and harmless with a bounds check.
    • 

  • Warps are formed from consecutive linear thread ids (x fastest); block sizes are usually multiples of 32.
    • 

  • Blocks are independent and unordered; limits on block and grid size are device properties you query.
    • 

  • A grid-stride loop makes a kernel correct for any grid size.
    •

Observation. Grid 2 × 1 (rounded down), 32 threads launched for 60 pixels, 0 idle, 28 pixels missed: columns 8–9 of rows 0–3 and all of rows 4–5 (the dots in R5).


Hypotheses. A too-strict bounds check would leave idle threads and could not launch fewer threads than pixels; swapped x and y would scramble the letters rather than leave a clean right and bottom margin. "threads launched 32" for 60 pixels proves the grid itself is too small.


Root cause. width / 4 = 10 / 4 = 2 and height / 4 = 6 / 4 = 1 with integer division. For 8 × 8 images, 8 / 4 = 2 exactly, so rounding down and rounding up agree and every test passed.


Fix. dim3 grid((width + 3) / 4, (height + 3) / 4) → 3 × 2 blocks, 96 threads, 36 idle, 0 missed: exactly the correct run of Listing 2 (R2).


Prevention. Test sizes that are not multiples of the block in each direction separately (for example 10 × 8, 8 × 6 and 10 × 6), plus 1 × 1, and assert in the host code that grid.x * block.x >= width and the same for y.
