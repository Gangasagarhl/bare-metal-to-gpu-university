Story hook

In the great kitchen hall, a row of 32 helpers needs one jar each from the big far pantry. The pantry has a rule: a runner fetches whole shelf sections, never single jars. One section holds eight jars standing side by side. If the 32 helpers need jars 0, 1, 2, … 31, the runner fetches four sections in four quick grabs and every jar carried is used. Neighbouring jars, one trip.

Now the recipe changes: helper 0 needs jar 0, helper 1 needs jar 8, helper 2 needs jar 16, and so on. Each helper's jar sits in a different section. The runner must fetch 32 sections, 256 jars, to deliver 32 of them; seven of every eight jars carried are put straight back. The row waits eight times as long for the same work. Nobody in the row did anything wrong; the recipe asked for jars that are far apart. This chapter is about writing recipes whose rows ask for neighbouring jars.

What you will be able to do

  • Explain coalescing: how the addresses of one warp's load become a number of memory segments, and why that number sets the kernel's speed.
  • Compute with a model the segments and efficiency of strided, offset, array-of-structures and vector accesses.
  • Write and time strided and offset copy kernels for E2 and predict their bandwidth from the model.
  • Restructure data (structure of arrays) and index mapping so that consecutive threads read consecutive addresses.
  • Diagnose "slow by stride" with the profiler's memory metrics.
Jargon box
Coalesced access
Simple words: the threads of a warp reading neighbouring addresses, so the hardware can serve them with few, full memory transfers. Analogy: the row needs neighbouring jars, fetched in one trip per section. Precise: the device combines the global loads or stores of a warp's threads into as few memory transactions as their addresses allow (paraphrase; the exact rules are in D1); efficiency is the ratio of bytes requested to bytes moved. D1
Memory segment (sector)
Simple words: the smallest aligned block of bytes the memory system moves at a time. Analogy: a shelf section of eight jars, always fetched whole. Precise: in this course's TG-1 model, an aligned 32-byte unit; NVIDIA calls 32-byte units "sectors" and caches in 128-byte lines on many generations (from memory; check D1, D2). D2
Stride
Simple words: the distance, in elements, between what thread t and thread t+1 read. Analogy: helper 1's jar is 8 jars along from helper 0's. Precise: thread t reads element offset + t × stride; stride 1 is the coalesced case. (Defined in HW203.)
Memory efficiency
Simple words: what fraction of the bytes moved were actually wanted. Analogy: jars used ÷ jars carried. Precise: bytes requested by the warp ÷ (segments touched × segment size); Listing 1's last column. A profiler reports related ratios from hardware counters.
Structure of arrays (SoA)
Simple words: storing each field in its own array (all x together, all y together) instead of one array of records. Analogy: one shelf of all the salt, one of all the pepper, instead of a box per dish holding one of each. Precise: the layout struct { float x[N], y[N], z[N]; } versus array of structures (AoS) struct { float x, y, z; } p[N]; with SoA, thread t reading x[t] is stride 1. D3

Layer 1 — the kid explanation

The pantry never hands out single jars: it hands out whole shelf sections. So the question for a row of helpers is not "how many jars do we need?" but "how many sections do our jars sit in?". If the 32 helpers need 32 jars standing next to each other, that is a few sections and every jar carried is used. If their jars are spread out, every helper's jar needs its own section, and the runner carries many jars nobody wanted.

So you arrange two things: the shelves (put the things that are used together next to each other) and the recipe (helper number t takes jar number t, not jar number 8t). Then each trip is full.

Layer 2 — the student explanation

One instruction, 32 addresses

A warp executes a load instruction for its 32 threads together (F6-02). The SASS of both copy kernels in this chapter contains exactly one global load, LDG.E, and one store, STG.E, per thread, whatever the stride or offset. R3 The instructions are the same; what differs is the 32 addresses they produce. The memory system serves those addresses in units larger than 4 bytes: it moves whole aligned segments. D1 So the cost of one warp load is set by how many distinct segments the 32 addresses fall into, not by how many bytes the threads want.

The model

Listing 1 is the university's teaching model for TG-1: thread t reads element offset + t × stride of an array that starts at a segment boundary; the model counts the distinct 32-byte segments touched and computes efficiency = requested ÷ moved. R1 Its real output:

  • Stride. 4-byte floats: stride 1 → 4 segments, 100 %; stride 2 → 8, 50 %; stride 4 → 16, 25 %; stride 8 → 32, 12.5 %; stride 32 → still 32, 12.5 %. Once each thread's element lies in its own segment (stride ≥ 8 here), it cannot get worse in this model: 32 segments per warp load.
  • Offset. Starting one element late (offset 1) spreads the 128 bytes over 5 segments: 80 %. Offset 8 (exactly one segment) is aligned again: 100 %.
  • Records. Reading only x from an array of {x, y, z} records (AoS) is stride 3: 12 segments, 33.3 %; the same field from its own array (SoA) is 100 %.
  • Vectors. Each thread reading a 16-byte float4 at stride 1 touches 16 segments for 512 bytes: 100 %, with four times the bytes per instruction (F6-09).
  • Bigger units. If the unit moved were 128 bytes instead of 32, stride 1 would still be 100 %, but stride 32 would fall to 3.1 % (4,096 bytes moved for 128). The segment size decides how bad scattered access is.

From efficiency to speed

For a kernel limited by memory bandwidth (a copy, SAXPY), time is roughly bytes moved ÷ bandwidth. If the moved bytes grow by 8× for the same useful work, the useful bandwidth falls to about one eighth. The model's prediction for Listing 2: the strided copy's effective bandwidth (counted from requested bytes, as the harness does) falls roughly as 100 %, 50 %, 25 %, 12.5 % of the stride-1 value for strides 1, 2, 4, 8, and stays near 12.5 % beyond; offset 1 costs about 20 % on the reads. Two cautions: the copy also writes 4 bytes per thread with stride 1, which stays at 100 %, so the total falls less than the reads alone; and caches can serve some of the "wasted" bytes later to a neighbouring warp, which the model ignores. Measure (E2) and compare. C1

How to get coalesced access

  • Map consecutive threads to consecutive addresses: threadIdx.x to the fastest-changing index of a row-major array (F6-02).
  • Use structures of arrays for data that kernels read field by field.
  • Keep arrays aligned: cudaMalloc returns well-aligned pointers (at least 256 bytes on current GPUs, from memory, D1); offsets you add yourself can break alignment.
  • When an algorithm must read columns (transposes, some stencils), read a tile coalesced into shared memory and read the column from there (CU301's tiled transpose).

Layer 3 — the engineer's depth

One analogy sentence: the pantry also keeps a small counter near the hall where recently fetched sections wait for a while, so the second row asking for the same section may not need a trip. The engineering consequences:

  • Caches. Global loads pass through the L2 cache and usually the SM's L1 (F6-03). A stride-2 warp leaves the other half of each segment in cache, and the neighbouring warp that needs it may hit; that is why measured stride curves are often better than the model at small strides.
  • Sectors and lines. On many NVIDIA generations the L1 and L2 cache in lines of 128 bytes made of four 32-byte sectors, and DRAM is accessed in sectors. The TG-1 model's 32-byte segment follows that structure in simplified form (unverified box below).
  • Stores. Writes coalesce the same way; partial writes of a segment can cost extra work in some memory systems. Measure strided stores separately in the extension.
  • Profiler metrics. Nsight Compute reports, per kernel, how many requests the global loads made and how many sectors they moved, plus the bytes transferred from DRAM; sectors per request near 4 for 4-byte loads means coalesced, near 32 means one sector per thread. These are the "memory-transaction metrics" E2 asks for (C1). Look up the exact metric names for your Nsight Compute version.
  • Index width. i * stride for large n and stride exceeds int: Listing 2 computes the index in 64 bits (line 11).

How the hardware actually does it

When a warp executes LDG.E, the SM's load/store unit has 32 addresses. It groups them by the aligned units of the memory system, looks those units up in L1, sends misses to L2 and from there to DRAM, and waits until all the data for the warp has arrived before the warp can use it. D2 DRAM moves data in bursts: a whole run of consecutive bytes is transferred per access (F1-59, F1-33), so a scattered warp keeps the DRAM busy transferring bytes nobody uses. The SASS confirms that nothing in the instruction stream changes with the pattern: copyStrided computes its address with IMAD.WIDE and LEA/LEA.HI.X (a 64-bit index scaled by 4) and issues one LDG.E; copyOffset adds the offset with IADD3 and issues one LDG.E. R3 The difference in speed comes entirely from the memory system below the instruction.

Worked example

Task. A kernel reads an array of 3-D points stored as records {float x, y, z} (12 bytes each); thread t reads p[t].x. Compute with the TG-1 model the segments per warp and the efficiency; then do the same if the points are stored as three arrays.

  1. Addresses. p[t].x is at byte 12t: element stride 3 floats.
  2. Span. Thread 31 reads bytes 372–375, so the warp touches bytes 0 to 375.
  3. Segments. Bytes 0–375 lie in segments 0 to ⌊375 ÷ 32⌋ = 11: 12 segments. Is every one touched? Consecutive addresses are 12 bytes apart, less than 32, so yes: 12 segments, 384 bytes moved.
  4. Efficiency. 128 ÷ 384 = 33.3 %, matching Listing 1's aos_x_of_xyz line (R1).
  5. SoA. With x[t] in its own array: stride 1, 4 segments, 100 % (soa_x, R1).
  6. Caveat. If the kernel reads x, y and z of each point, the AoS layout's three loads touch the same 12 segments, so after caching the total may be close to SoA; the model per instruction is the worst case. Measure.

Where the analogy breaks


    

  • A runner can see which jars are wanted and grab only those; the memory system cannot move less than a segment. The waste is not laziness; it is the unit of transfer.
    • 

  • Jars put back go back to the shelf; wasted bytes may stay in a cache and be used by another warp. The kitchen picture has no counter near the hall unless you add one (Layer 3).
    • 

  • In the kitchen a row of 32 helpers could split up and fetch separately; a warp's load is one instruction and waits for all its segments.

Transition box

Where you came from: F1-33: caches and cache lines; F2-33: profiling; CPU loops that walk arrays in row-major order. What carries over: memory moves in blocks larger than one value; sequential access uses every byte of a block; layout (row-major, AoS versus SoA) decides the pattern. What changes: on the CPU, one thread's successive accesses should be neighbours; on the GPU, the 32 threads' simultaneous accesses should be neighbours: the loop index of the CPU becomes the thread index, and "walk along the row" becomes "spread the threads along the row" (R1). A CPU hides some bad patterns with prefetching; a warp waits for every segment its one instruction touched. What comes next: F6-09 asks how fast the best pattern can go: the memory roof, vector loads, and copies between host and device.

Forensic lab answer key


Observation. Tomás's "column sums": at each step the 32 threads read row r, columns t = 0…31: consecutive addresses, 4 segments, 100 % (row_read). The colleague's "row sums": the 32 threads read column c of 32 different rows: addresses 1,024 floats apart, 32 segments, 12.5 % (column_read_w1024; 3.1 % with 128-byte units) (R1).


Hypotheses. (a) Instructions: ruled out by the SASS, one LDG.E per load in both. (b) Uncoalesced loads: supported by the model and by the invented profiler summary (about 32 sectors per request instead of about 4). (c) Cache effects: part of the story for (d) below.


Root cause. Coalescing is about the 32 threads' simultaneous addresses. The colleague's threads each walk along their own row, but at any moment they are 4 KiB apart, so every warp load touches 32 segments.


DRAM bytes. Each segment fetched for one element also contains the next 7 elements of that row, which the same thread needs in its next 7 loop steps; if the segment has been evicted from the caches by then (the warp's working set is 32 rows), it is fetched again. Repeated fetches make DRAM traffic exceed the matrix size.


Fix. Assign a warp (or block) to each row and let the threads take consecutive columns (thread t reads columns t, t + 32, …), then combine the partial sums (a reduction, CU301); or keep one thread per row but stage tiles through shared memory. How the evidence was produced: the model output and SASS are real runs in this build; the profiler summary is invented for the scenario and labelled so.
