Story hook

Kwame runs the quality desk of the great kitchen hall. Every order that leaves the hall is checked against the head chef's own version of the dish. One day the hall makes a sauce: "take a spoon of base, multiply it by 1.7, add a spoon of stock". The head chef measures the 1.7 spoons, levels the spoon, writes the amount on a card, then adds the stock and levels again. The hall's helpers have a special measuring cup that does "multiply and add" in one pour and levels only once at the end.

Both sauces taste right. But Kwame's scale is very precise, and for about three pots in ten the weights differ in the very last digit. Is the hall cheating? Is the chef? Neither: they rounded a different number of times. Before Kwame can sign off a single order, he has to decide what "the same" means and make sure his reference is measured the way the hall measures. That is what "bit-exact against a CPU reference" asks of you in this chapter.

What you will be able to do

  • Port a CPU loop to a CUDA kernel step by step, keeping a working program at every step.
  • Write vector add and SAXPY kernels with launch, bounds check, copies and checks, and explain every line.
  • Test a kernel against a CPU reference bit for bit, for sizes from 1 to 100 million, including sizes that are not multiples of the block size.
  • Explain why a * x + y can give two different correctly rounded answers, and show which one the GPU code computes by reading its SASS.
  • Diagnose a "not bit-exact" failure caused by fused multiply-add contraction.
Jargon box
SAXPY
Simple words: "times a, plus y": each element of y becomes a times the element of x, plus itself. Analogy: every helper multiplies a spoon of base by 1.7 and adds a spoon of stock. Precise: Single-precision A·X Plus Y, y[i] = a * x[i] + y[i] for float vectors x, y and scalar a; one of the classic BLAS level-1 operations. D3
CPU reference
Simple words: a plain CPU version of the computation whose answers you trust and compare against. Analogy: the head chef's own version of the dish at the quality desk. Precise: an independent implementation (often the obvious loop) used as the test oracle; curriculum 13.4: "compare against a CPU reference or the vendor library with a tolerance justified by the precision". C1
Bit-exact
Simple words: not merely close, but the very same bits in every result. Analogy: Kwame's scale shows identical weights to the last digit. Precise: two floating-point results are bit-exact when their encodings are identical (compared as 32-bit integers, as Listing 2 does); stronger than "within a tolerance". C1
FMA (fused multiply-add)
Simple words: multiply and add in one step, rounding only once at the end. Analogy: the helpers' cup that pours "multiply and add" together and levels once. Precise: computes a·x + y with a single rounding of the exact result; C++ exposes it as std::fma; nvcc may contract a * x + y into an FMA instruction (FFMA in SASS), controlled by --fmad, "Default value: true". D4 R5
Contraction
Simple words: the compiler merging a multiply and an add written separately into one FMA. Analogy: the hall replacing "measure, level, add, level" by its one-pour cup without asking. Precise: nvcc's help: --fmad "enables (disables) the contraction of floating-point multiplies and adds/subtracts into floating-point multiply-add operations (FMAD, FFMA, or DFMA)". R5
ULP (unit in the last place)
Simple words: the gap between a floating-point number and the next one. Analogy: the smallest step on Kwame's scale at that weight. Precise: the spacing of representable numbers at a value; for float values between 512 and 1024 it is 2−14. (Defined in MA302, F0-73.) D5

The idea in pictures

Layer 1 — the kid explanation

A GPU program is a CPU program with one loop handed to the hall. So you start with a CPU program that works, and you change it a little at a time. First you make sure each turn of the loop can be done on its own. Then you turn the loop's body into the recipe card. Then you add the carrying: to the hall, and back. After every change, you run it and compare.

Comparing sounds easy: "is the GPU's answer the same as the CPU's?" With whole numbers it is. With numbers that have decimals, a computer keeps only a fixed number of digits and must round. If the CPU rounds twice and the GPU rounds once, they may disagree in the very last digit, and both are doing arithmetic correctly. So a good tester first asks "how exactly does each side compute?", then makes the reference compute the same way, and only then demands "the same, to the last bit".

Layer 2 — the student explanation

Porting a loop

The CPU loop of Listing 1 does c[i] = a[i] + b[i] for each i. A loop can become a grid when every iteration is independent: iteration i reads only element i of the inputs and writes only element i of the output, so the iterations may run in any order or all at once. D3 Then the body becomes the kernel, the loop variable becomes the global index, the loop condition becomes the bounds check, and the host does the allocation, the copies and the launch (F6-01, Listing 1 of that chapter is the finished vector add). BR-01 asks you to do this port by hand and break it three ways; this chapter does it for SAXPY and then asks the harder question of what "correct" means.

SAXPY

SAXPY, y[i] = a * x[i] + y[i], has the same shape as vector add with one multiplication more and one input fewer: it reads x[i] and y[i], writes y[i] in place. Each thread does one multiply, one add, two 4-byte loads and one 4-byte store. Like vector add it is limited by memory, not arithmetic (F6-09 builds on that). The curriculum's milestone E1 makes it the first acceptance test of the course: "SAXPY is bit-exact against a CPU reference for 1 to 100 million elements, including non-multiple-of-block sizes." C1 Listing 2 does exactly that, for nine sizes from 1 to 100,000,000, including 7, 255, 257 and 1,000,003, which are not multiples of 256.

Two correct answers

A float keeps 24 significant bits; after each operation the exact result is rounded to the nearest representable float (F0-73). D5 The expression a * x + y can be evaluated in two ways: round the product, then round the sum (two roundings), or compute the exact a·x + y and round once (a fused multiply-add). The second is closer to the exact result or equal to it, but the two can differ. Listing 3 measures how often, on this chapter's test data: for 1,048,576 elements, 308,538 results differ in their bits, almost three in ten. R4 Every difference it found is the kind shown in Figure 2: the fused result is the nearest float to the exact value; the plain one is its neighbour.

What the GPU code computes

Which one does the kernel compute? Not a question to answer from memory: read the machine code. Compiled for target sm_80 with the default options, the SAXPY kernel's arithmetic is a single instruction, FFMA R7, R2, c[0x0][0x164], R7: a fused multiply-add of x[i] (in R2), the constant a (read from the constant bank) and y[i] (in R7). R3 Compiled with --fmad=false, the same source becomes FMUL R0, R2, c[0x0][0x164] followed by FADD R7, R0, R7: two roundings. R3 nvcc's own help explains the switch: --fmad "enables (disables) the contraction of floating-point multiplies and adds/subtracts into floating-point multiply-add operations (FMAD, FFMA, or DFMA)" with "Default value: true". R5 The host compiler made the opposite choice for Listing 3's product + y: with this build's flags (-std=c++20, x86-64 default target) it kept two roundings, as the difference count proves. R4

So a CPU reference written as y[i] = a * x[i] + y[i] and a GPU kernel written the same way are not computing the same function in this build's configuration. Listing 2 resolves it the honest way: the reference is written with std::fma, which rounds once, matching the FFMA that the SASS shows. If the GPU's FFMA rounds once to nearest, as an IEEE 754 fused multiply-add must, the two agree bit for bit. D5 Whether that holds on your GPU is exactly what running Listing 2 tests; this build could not run it.

Bit-exact or tolerance?

Bit-exactness is possible here because each output depends on one operation sequence that both sides can reproduce. It is the right demand for SAXPY. For a sum of many numbers (CU301's reductions), the GPU adds in a different order than a CPU loop, and rounding makes the order matter; there the curriculum asks for "a tolerance justified by the precision" instead. C1 Never loosen a test to a tolerance to hide a difference you have not explained: first explain it (as above), then decide.

Layer 3 — the engineer's depth

One analogy sentence: a recipe is only "the same" if the measuring tools are the same. The engineering consequences:

  • Reproducibility across builds. Contraction is a compiler decision. The same source compiled with --fmad=false, or with a different host compiler or target, can change results in the last bit. Record the compile options with every result (the harness logs do, F6-06), and pin --fmad explicitly in builds whose results must be reproducible.
  • Fast-math options. nvcc's help notes that --use_fast_math implies --fmad=true (R5). Other effects of fast-math options (approximate division and transcendental functions, flushing of tiny values) change results more than one ULP; they are outside CU201 and must be checked in the nvcc documentation before use.
  • Subnormal numbers. This chapter's data has no tiny values, so the treatment of subnormal (denormal) floats does not matter here. A test suite should include them once you use options that may flush them to zero.
  • Integer index width. At n = 100,000,000 the largest index is below 231 − 1, so int is enough; Listing 2's byte count uses std::size_t because 4 × 100,000,000 = 400,000,000 bytes is close to int's limit and the next size would exceed it.
  • Memory. At the largest size the program needs 2 × 400,000,000 bytes on the GPU and three vectors of that size on the host; check that your GPU's memory_bytes (F6-07) allows it.
Not verified — check before relying on this

That the GPU's FFMA computes the IEEE 754 fused multiply-add with round-to-nearest-even (and therefore matches std::fma bit for bit, including for subnormal inputs and outputs under default compile options) is stated here from memory. Check: the CUDA C++ Programming Guide (floating-point standard and mathematical functions appendix), NVIDIA's "Floating Point and IEEE 754 Compliance for NVIDIA GPUs" whitepaper, and the nvcc documentation for --fmad, --ftz, --prec-div and --use_fast_math; then run Listing 2 on the lab GPU. This build observed only the SASS (R3) and the CPU side (R4).

How the hardware actually does it

The SASS of the SAXPY kernel (R3) is short enough to read completely. S2R R4, SR_CTAID.X and S2R R3, SR_TID.X read the block and thread index from special registers; IMAD R4, R4, c[0x0][0x0], R3 computes the global index with blockDim.x read straight from the constant bank; ISETP.GE.AND and @P0 EXIT are the bounds check (threads past n exit at once). IMAD.WIDE turns the index into two 64-bit addresses (the HFMA2.MMA R5, -RZ, RZ, 0, 2.384185791015625e-07 before it only loads the constant 4, the size of a float, into R5: the disassembler prints the two 16-bit halves of the bit pattern as half-precision numbers, and 2−22 = 2.384185791015625 × 10−7 is how the bit pattern 4 reads in that format). Then LDG.E twice (global loads), one FFMA, one STG.E (global store), EXIT. R3 D2 Every thread executes this same short sequence; a warp executes it for 32 threads at once. Three of the thirteen instructions listed touch memory, which is why the kernel's speed is set by memory (F6-09), and why F6-08 looks at the addresses of those LDGs.

Worked example

Task. Element 1 of the test data has x = 876.177002 and y = −572.510986 (as stored in float), and a = 1.7f, which is stored as 1.70000005. Show why the plain and fused results differ, using the real numbers of R4.

  1. Exact value. Computed in double (the product of two floats is exact in a double): a·x + y = 916.989958772. R4
  2. Spacing. 916.99 lies between 29 = 512 and 210 = 1024, so neighbouring floats are 29−23 = 2−14 = 0.00006103515625 apart.
  3. Neighbours. The two floats around the exact value are 916.989929… (bits 0x44653f5b) and 916.989990… (bits 0x44653f5c); they differ by 1 in the last bit, one ULP.
  4. Fused. One rounding of 916.989958772 goes to the nearer neighbour. The distances are about 0.0000296 to the lower one and 0.0000315 to the upper one, so the fused result is 916.989929 (0x44653f5b), as R4 prints.
  5. Plain. First a·x is rounded to 1489.50098; the small error of that rounding moves the subsequent sum barely past the midpoint, and the second rounding picks 916.98999 (0x44653f5c), as R4 prints.
  6. Conclusion. Both are one ULP apart. A reference that rounds twice and a kernel that rounds once will disagree on such elements, here 308,538 of 1,048,576 (29.4 %).

Where the analogy breaks


    

  • A cook can taste whether two sauces are "the same"; a computer compares bits. There is no "close enough" unless you write one, with a tolerance you can justify (MA302).
    • 

  • The one-pour cup in the story is the helpers' own tool; the FMA choice is the compiler's. The kernel source looks identical either way; only the compile options and the SASS reveal the difference (R3).
    • 

  • Every helper does exactly the same steps; the hall's real "order" of operations can still differ. For SAXPY each element is independent, so the order between threads does not matter; for sums across threads it will (CU301).

Forensic lab answer key


Observation. Default: one FFMA R7, R2, c[0x0][0x164], R7. With --fmad=false: FMUL then FADD (R3). nvcc's help: contraction is on by default (R5).


Hypotheses and evidence. "Not IEEE": not supported; both CPU computations in Listing 3 are IEEE operations and still differ by one ULP in 29.4 % of elements (R4). "Rounded a different number of times": supported by the SASS (one rounding on the GPU) and by Kwame's reference (two roundings on the CPU). "Bad copy": would give large or random differences, not exactly one ULP.


Root cause. nvcc contracted a * x[i] + y[i] into an FMA; Kwame's CPU reference rounds after the multiply and after the add. On this data about 29.4 % of elements are expected to differ, each by one ULP (R4).


Fixes. (a) Reference with std::fma (Listing 2): tests the kernel exactly as it will run, the preferred choice for a benchmark because it keeps the faster default code. (b) Compile the kernel with --fmad=false: matches the plain reference but changes (usually slows) the code being benchmarked. A tolerance would hide the explanation; it is not a fix here.


Prevention. Log the full compile command (including --fmad) and the toolkit version with every result; keep a CPU-side test like Listing 3 that documents which rounding the reference uses. How the evidence was produced: real compiler and CPU runs in this build; Kwame's GPU failure is the scenario, and its expected size is predicted from R4, not measured.
