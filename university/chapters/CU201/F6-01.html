Story hook

Imagine a school kitchen that must make one million sandwiches before lunch. The head chef, Amara, is brilliant. She can cook anything, and she can change plans in a second when something goes wrong. But she has only two hands. One sandwich at a time, she would still be working next week.

Next door is a huge hall full of kitchen helpers. Each helper is not a great chef. Each one can only follow a simple recipe card: "take your bread, add your filling, put it on your plate". But there are thousands of them, and if every helper makes a few sandwiches at the same time, the million sandwiches are done before the bell rings.

There is a catch. The helpers work in the hall, and the ingredients are in Amara's kitchen. Someone has to carry the bread to the hall's own pantry before the helpers can start, and carry the sandwiches back afterwards. And if Amara sends the order and walks away without checking, she may come back to an empty tray and never learn why.

A computer with a graphics card has both: the CPU is the head chef, the GPU is the hall of helpers. This chapter is about the hall, the recipe card, the carrying, and the checking.

What you will be able to do

  • Explain, with the kitchen analogy and with precise words, why a GPU can finish some jobs much faster than a CPU and why it is no help for others.
  • Name the parts of the CUDA thread hierarchy (thread, block, grid) and say what a warp is.
  • Compute how many blocks a launch needs, how many threads do nothing, and which element a given thread handles.
  • Read, build and run a complete CUDA C++ vector-add program and explain every line, including the error checks.
  • Read the PTX that the compiler produces for that kernel and find the index formula in it.
  • Diagnose a GPU program whose results are all zeros, from its output alone.
Jargon box
Host and device
Simple words: the host is the CPU side of your program; the device is the GPU. Analogy: Amara's kitchen (host) and the hall of helpers (device), each with its own pantry. Precise: in CUDA the host is the CPU and its memory, which runs ordinary C++ and starts work on the device; the device is the GPU and its own memory, which runs kernels. D1 D3
Kernel (GPU)
Simple words: the instructions every GPU worker follows. Analogy: the recipe card handed to every helper. Precise: a function marked __global__ that the host launches and that many GPU threads execute in parallel. D1 Not the same as the operating-system kernel of OS201 and F3: same word, different thing.
Thread (GPU)
Simple words: one worker on the GPU doing one small part of the job. Analogy: one kitchen helper. Precise: the smallest unit of execution in CUDA; each thread runs the kernel's code with its own built-in index variables such as threadIdx. D1 Not an operating-system thread like the std::thread of F2-34: you do not create GPU threads one by one, a launch creates them all.
Block (thread block)
Simple words: a team of GPU workers that can share a table and wait for each other. Analogy: the helpers around one table. Precise: a group of threads, identified by blockIdx and containing blockDim threads, that can cooperate through shared memory and synchronisation. D1
Grid
Simple words: all the teams working on one job. Analogy: every table in the hall for this order. Precise: the set of all thread blocks created by one kernel launch. D1
Warp
Simple words: a small group of GPU workers that always do the same step together. Analogy: a row of helpers who move in step. Precise: a group of 32 threads that NVIDIA GPUs schedule and execute together. D1 AMD's similar group is the wavefront (64 threads on CDNA GPUs; see F1-57 and BR-02).
Launch (execution configuration)
Simple words: the moment the CPU tells the GPU "run this recipe with this many teams of this size". Analogy: Amara handing the order slip to the hall. Precise: a kernel call written kernel<<<blocks, threadsPerBlock>>>(arguments); the values between the triple angle brackets are the execution configuration. D1 Launches are asynchronous with respect to the host. H1
PTX
Simple words: the GPU program written in an in-between language that the compiler produces before real machine code. Analogy: the recipe written in a general cookbook language, before it is rewritten for one particular hall. Precise: NVIDIA's virtual instruction set (Parallel Thread Execution); nvcc -ptx writes it as text. D4 R5

The idea in pictures

Figure 1 puts the two kinds of processor side by side. On the left, a CPU with a few strong cores, the head chefs. On the right, a GPU made of many identical units (NVIDIA calls them SMs, streaming multiprocessors, as F1-56 explains), each running rows of simple helpers. The two sides have separate memories joined by a link, and that link is the corridor between the two pantries.

Figure 2 is the order of work in every program of this course: allocate in the hall's pantry, carry the ingredients over, hand out the recipe card, carry the results back, check them.

Layer 1 — the kid explanation

Some jobs are made of many small, similar pieces. Adding two long lists of numbers is like that. Each pair of numbers can be added on its own. Nobody has to wait for anybody else.

The CPU is great at hard, twisty jobs where each step depends on the one before. The GPU is great at jobs with many similar pieces. So we give the GPU the long lists. We hand every helper the same recipe card: "take your number from list A, take your number from list B, add them, write the answer in list C".

How does a helper know which number is "theirs"? Every helper has a seat number at their table, and every table has a number too. A helper works out a ticket number from the two: table number times the size of a table, plus seat number. Ticket 515 means "the 515th number of each list". You will do that calculation yourself in the Worked example.

Two more rules keep the hall honest. First, the helpers can only use food that is already in the hall's pantry, so we carry the lists over before they start and carry the answers back afterwards. Second, the hall does not shout when something goes wrong. We must ask, after every step, "did that work?". A program that never asks can come back with a tray of zeros and no idea why: that is this chapter's forensic lab.

Layer 2 — the student explanation

Kernels, threads, blocks and the grid

The analogy first: one recipe card, many helpers, helpers grouped at tables, all tables of one order forming the job. In CUDA, the function every GPU thread runs is a kernel, marked with __global__. D1 When the host launches a kernel it says how many blocks to create and how many threads each block has; together the blocks form the grid. D1 Inside the kernel, each thread can read built-in variables: threadIdx.x (its position inside its block), blockIdx.x (its block's position in the grid) and blockDim.x (the number of threads per block). D1 Combining them gives every thread a unique global index:

int i = blockIdx.x * blockDim.x + threadIdx.x;

The CUDA Programming Guide's own vector-add example computes this index and then checks it against the vector length before touching memory, because the grid may contain more threads than there are elements. D1 That check, if (i < n), is called the bounds check; forgetting it is the most common first bug in GPU code (F6-05).

Warps

The hardware does not run the threads of a block one by one. It runs them in groups of 32 called warps: one instruction is issued for the whole warp, and the 32 threads execute it on their own data. D1 You never write "warp" in Listing 1; the hardware forms the warps from consecutive threads of each block. It still matters for you, for two reasons that later chapters develop: when threads of one warp take different branches they have to wait for each other (divergence, F1-57), and the memory addresses of one warp's 32 loads decide how many memory trips are needed (coalescing, F6-08).

Two memories, explicit copies

In this model the GPU and the CPU have separate memories. A kernel can only use pointers to device memory, so the host allocates device buffers with cudaMalloc, copies inputs in with cudaMemcpy, launches the kernel, and copies results out. D1 D2 The installed CUDA header says that cudaMalloc returns memory that "is not cleared" (H1): what is in a fresh device buffer is whatever was there before. Later courses meet other arrangements, such as managed memory (CU303); in CU201 every copy is written by you, so you can see it and time it.

A launch does not wait

The installed CUDA 12.0 runtime header states it in one line: "Kernel launches are asynchronous with respect to the host." H1 The launch statement returns as soon as the work is queued, and the host's next line runs while the GPU may still be busy. The same header lists when a copy waits: "For transfers from device to either pageable or pinned host memory, the function returns only once the copy has completed." H1 Because the copy is queued behind the kernel, the device-to-host copy in Listing 1 returns only after the kernel has finished and the result has arrived. This one fact explains two habits of the course: you read results only after such a waiting call, and you time kernels with GPU events, not a host clock (F6-06).

Errors are return codes

Every runtime call returns a cudaError_t. A launch has no return value, so its error is fetched afterwards with cudaGetLastError, which the header describes as returning "the last error that has been produced by any of the runtime calls in the same instance of the CUDA Runtime library in the host thread" and resetting it. H1 If you ignore the codes, a failed program usually does not crash. It runs to the end and prints whatever was in its host buffers. You will see exactly that, from a real run, in the forensic lab.

Layer 3 — the engineer's depth

One analogy sentence: the recipe card is written once in a general cookbook language and then rewritten for each hall. nvcc splits a .cu file into host code, which it passes to the host C++ compiler, and device code, which it compiles to PTX and then, by the PTX assembler ptxas, to SASS, the machine code of one GPU generation. D4 R5 You can stop the compiler at PTX with -ptx ("Compile all .cu input files to device-only .ptx files", in nvcc's own help text, R5) and read the kernel. This build did that for vecAdd with -arch=sm_80, a compiler target name (which products have that target is in NVIDIA's documentation, not here):



Read it from the top. The four ld.param lines load the kernel's arguments. The three mov.u32 lines read the special registers %ctaid.x, %ntid.x and %tid.x, which are PTX's names for blockIdx.x, blockDim.x and threadIdx.x; mad.lo.s32 multiplies and adds them: that is the index formula, in one instruction. setp.ge.s32 and the predicated branch @%p1 bra are the bounds check. Then come two ld.global.f32, one add.f32 and one st.global.f32: two loads from global memory, one addition, one store. R3 D4 Three things stand out. There is no loop: the "loop" of the CPU version became the grid. Each thread does one addition and three memory accesses, so this kernel will be limited by memory traffic, not by arithmetic (F6-09). And mul.wide.s32 %rd5, %r1, 4 turns the element index into a byte offset (4 bytes per float): the address arithmetic you did by hand in F2-19.

How the hardware actually does it


The blocks of a grid are distributed over the GPU's streaming multiprocessors; each SM holds several blocks at once, runs their warps, and switches between warps that are ready, which hides the waiting time of memory accesses. D1 D3 F1-56 (SMs and how blocks are placed on them) and F1-60 (latency hiding) explain this in depth, and F1-55 explains why a design with many simple threads beats a few strong cores for throughput but not for latency. How many SMs your GPU has is printed by the device-query lab (F6-07) and stated in the vendor documentation for your exact product; this chapter does not quote a "typical" number (guide AH-22). The copies of step 2 and step 4 cross the link between host and GPU memory; on a PCIe card that is the PCIe bus, whose cost F1-62 models and F6-09 measures.



Worked example


You want to add two arrays of n = 1000 numbers with 256 threads per block.


    

  1. Blocks needed. We round up, so that no element is left out: (1000 + 256 − 1) / 256 = 1255 / 256, which is 4 in integer division (1255 / 256 = 4.90…, and integer division drops the fraction). So 4 blocks.
    2. 

  2. Threads created. 4 × 256 = 1024. That is 24 more than the 1000 elements.
    3. 

  3. Thread 3 of block 2 computes i = 2 × 256 + 3 = 515, so it adds element 515.
    4. 

  4. Thread 255 of block 3 computes i = 3 × 256 + 255 = 1023. Since 1023 is not less than 1000, the bounds check stops it: it does nothing. Without the check, it would write past the end of the arrays.
    5. 

  5. Listing 1's size. n = 220 = 1,048,576 with 256 threads per block gives exactly 4096 blocks and no idle thread, because 220 is a multiple of 256. The bounds check is still there: the next person to change n will thank you.
    6.

Where the analogy breaks


    

  • Helpers can each do something different; threads of a warp cannot, cheaply. Threads in a warp execute one instruction together, so if some must take a different branch, the others wait (divergence, F1-57, F6-14). D1
    • 

  • Helpers can talk to the whole hall; threads cannot. Threads cooperate quickly only within their block (shared memory and barriers), not across the whole grid in a simple way (F6-03, F6-12). D1
    • 

  • Carrying food next door is quick; copying data is not. For a job as small as one addition per element, the two copies can cost more time than the kernel itself; F6-09 measures it and F1-62 models it.
    • 

  • A helper with nothing to do goes home; a thread does not. The 24 extra threads of the Worked example are created and run the kernel; they only skip the work because of the bounds check you wrote.
    •

Summary


    

  • A CPU is a few strong workers; a GPU is many simple workers grouped in warps inside SMs.
    • 

  • A kernel (__global__) is run by many threads; threads form blocks; blocks form the grid.
    • 

  • Each thread computes blockIdx.x * blockDim.x + threadIdx.x and checks it against n.
    • 

  • Threads run in warps of 32 on NVIDIA GPUs.
    • 

  • Host and device have separate memories: allocate, copy in, launch, copy out, check, free.
    • 

  • Launches are asynchronous; a device-to-host copy waits for the kernel.
    • 

  • Every call returns an error code; a launch's error comes from cudaGetLastError. Unchecked failures look like zeros.
    • 

  • The PTX shows the whole kernel: the index formula is one mad.lo.s32, the bounds check a compare and a branch.
    •

Forensic lab answer key


Observation. Every printed C[i] is 0.0 although the expected values are 0, 3, 6, 9, 12; only C[0] is right, by accident, because 0 + 0 = 0. The program prints "finished normally" and exits 0 (R4).


Hypotheses. The kernel computed zeros (for example, wrong pointers); the kernel never ran; the copy back never happened; the inputs were zero. The last is ruled out by the source: hA and hB are filled on the host.


Evidence-based conclusion. The checked program on the same machine fails at its very first runtime call: cudaMalloc A failed: cudaErrorNoDevice (no CUDA-capable device is detected) (R1). So there was no device: every allocation, copy and launch in Tomás's program failed too, and nothing ran on a GPU at all. hC still holds the zeros it received when the std::vector<float> was constructed (value-initialised elements), which is why the "results" are zeros. The GPU is not broken; it is absent or invisible to this machine.


Wrong answers and why. "The kernel has a bug": the same kernel is in Listing 1, and the evidence shows the program never got as far as running it. "The copy back failed": true but not the root cause; the first failure is earlier.


Fix and verification. Check every call and the launch (Listing 1, or the macro of F6-05), then set up the driver or use a GPU machine. On a machine without a GPU the fixed program must stop at the first call with a clear message and a non-zero exit status, which this build's real run shows (R1).


Prevention. A review rule "no unchecked runtime call, no unchecked launch", and a test that runs the program on a machine without a GPU and expects a non-zero exit status. How the evidence was produced: real runs of vec_add_unchecked.cu and vec_add.cu in this build's container, which has no GPU; nothing was injected.
