Story hook

The great kitchen hall's big pantry has one wide corridor to the hall. However clever the recipes, no more jars can arrive per minute than the corridor carries: that number is the hall's memory roof. Rosa, the hall's new manager, wants to know how close her helpers come to it. She counts the jars of one order, times the order, divides, and finds 168 % of the corridor's capacity. She is about to announce a record when Kwame from the quality desk asks one question: "did the order actually come out complete?"

Deliveries from the town are a second story. The trucks can unload only at the hall's own loading dock. Goods that arrive in an ordinary warehouse must first be carried by hand to the dock, then loaded; goods kept on the dock already are loaded straight away. This chapter measures both corridors, explains why one result can never exceed 100 %, and finishes the course project: the harness that every later GPU lab uses.

What you will be able to do

  • Compute a GPU's peak memory bandwidth (the memory roof) from bus width and data rate, and a kernel's effective bandwidth and percentage of the roof.
  • Measure device copy bandwidth with scalar and vector loads and compare it with the vendor's bandwidth test (E2).
  • Explain pinned (page-locked) and pageable host memory and measure the ratio of their copy speeds (E2).
  • Model host–device copies as a fixed cost plus bytes ÷ link bandwidth and predict when small copies are slow.
  • Diagnose an impossible bandwidth result, and complete the course's benchmark harness.
Jargon box
Peak bandwidth (memory roof)
Simple words: the most bytes per second the GPU's memory can ever deliver. Analogy: the jars per minute the pantry corridor carries when full. Precise: bus width in bytes × transfers per second; for TG-1, 256 bits ÷ 8 × 8 × 109 = 256 GB/s (F1-59). R1
Effective bandwidth
Simple words: bytes your kernel had to read and write, divided by its time. Analogy: jars an order needed ÷ how long it took. Precise: (bytes read + bytes written) ÷ median time (F6-06); never above the roof for data that really comes from memory.
Pinned (page-locked) memory
Simple words: host memory the operating system promises not to move or swap out, so the GPU can copy it directly. Analogy: goods kept on the loading dock. Precise: allocated with cudaMallocHost: "host memory that is page-locked and accessible to the device … it can be read or written with much higher bandwidth than pageable memory". H1
Pageable memory
Simple words: ordinary host memory (malloc, new, std::vector), which the OS may move. Analogy: goods in the ordinary warehouse, carried to the dock first. Precise: for a cudaMemcpy from it to the device, the header says the function "will return once the pageable buffer has been copied to the staging memory for DMA transfer". H1
Vector load
Simple words: one instruction that loads several values at once, for example four floats. Analogy: a helper carrying a crate of four jars instead of one jar. Precise: a float4 load compiles to LDG.E.128, a 16-byte load, instead of LDG.E (4 bytes). R4

The idea in pictures

Layer 1 — the kid explanation

A corridor can carry only so many jars per minute. If you count the jars an order needed and divide by the time it took, you get how fast your helpers used the corridor. That number can come close to the corridor's limit, but never go over it. If your sum says you went over, you counted wrong, or the order did not do all its work.

Deliveries from outside come through a narrower door. Each delivery costs a fixed amount of time for opening the door and signing papers, so tiny deliveries are slow per jar; big deliveries are fast per jar. And goods that are not already waiting at the loading dock must first be carried there by hand, which adds a step.

Layer 2 — the student explanation

The memory roof

Peak memory bandwidth is bus width × data rate: each transfer moves the bus's width in bits, and the memory performs a fixed number of transfers per second (F1-59). For TG-1: 256 bits ÷ 8 = 32 bytes per transfer, × 8 × 109 transfers per second = 256 × 109 bytes per second, 256 GB/s. R1 For a real GPU, memory_bus_width_bits comes from your device report (F6-07) and the data rate from the vendor's documentation. The curriculum treats such numbers as "context, not the target" (C1, 13.4); E2's reference is a measured number: "the bandwidth measured by bandwidthTest or rocm-bandwidth-test on the same GPU". C1

Effective bandwidth and percentage of the roof

A copy kernel of n floats reads 4n and writes 4n bytes; SAXPY reads 8n and writes 4n. Divide by the median time. Listing 1 does this for two example timings (invented inputs, to practise the arithmetic): SAXPY on 224 floats in 1.0 ms is 201,326,592 bytes ÷ 1.0 ms = 201.3 GB/s, 78.6 % of TG-1's roof; the roof itself would allow 0.7864 ms. A copy of 226 floats in 2.5 ms is 214.7 GB/s, 83.9 %. R1 Note the units: the same copy is 200.0 GiB/s, because 1 GiB = 230 bytes; this course uses GB = 109 bytes, like bench::gbPerS (F6-06). Real kernels stay below the roof, because DRAM needs time for refresh and for switching between reads and writes; the curriculum suggests that "80–95 % of measured copy bandwidth" is a sensible first target for memory-bound kernels, with X written down before you start. C1

Why "memory-bound"

SAXPY performs 2 floating-point operations per 12 bytes: an arithmetic intensity of 1/6 flop per byte. At 256 GB/s, that is at most about 43 × 109 flop/s, far below what the SMs can compute. The kernel's speed is therefore set by bytes, not by arithmetic: it sits under the sloped part of the roofline (F2-56). That is why this course reports GB/s for SAXPY and copies; CU301's matrix multiply will report flop/s.

Vector loads

Listing 2 copies the same array twice: one float per thread (copyScalar) and one float4 per thread (copyVector, a quarter of the threads). The SASS shows the difference: LDG.E/STG.E versus LDG.E.128/STG.E.128. R4 Both are fully coalesced (F6-08: float4_stride1, 100 %); the vector version issues a quarter of the memory instructions for the same bytes, which can help a kernel get closer to the roof. Vector loads need 16-byte-aligned addresses and a size divisible by 4 (or a scalar tail for the rest); Listing 2 chooses n = 226, a multiple of 4.

Host–device copies: pinned and pageable

The GPU copies host memory with a DMA engine (F1-62), which needs physical pages that will not move during the transfer. Ordinary pageable memory gives no such promise, so the runtime first copies it into a pinned staging buffer: "The function will return once the pageable buffer has been copied to the staging memory for DMA transfer to device memory, but the DMA to final destination may not have completed." H1 Memory from cudaMallocHost is page-locked from the start; the header says "it can be read or written with much higher bandwidth than pageable memory obtained with functions such as ::malloc()", and warns that "Allocating excessive amounts of memory with ::cudaMallocHost() may degrade system performance" because it "reduces the amount of memory available to the system for paging". H1 Listing 2's part 2 times both directions from both kinds of memory and prints the ratio; E2 asks that "Pinned host transfers beat pageable transfers, and the measured ratio is recorded". C1 Listing 3 measures the extra step's cost on the host alone: a 64 MiB memcpy on this build's CPU took on the order of 10 ms per run (on the order of 10 GB/s; the value varies between runs, and the build's sanitizer flags add overhead). R3

Small copies

Every copy pays a fixed cost before bytes flow. With TG-1's model, time = 10 µs + bytes ÷ 16 GB/s; Listing 1 prints effective rates of 0.40 GB/s at 4 KB, 4.65 at 64 KB, 13.88 at 1 MB, 15.85 at 16 MB and 15.99 GB/s at 256 MB (Figure 2). R1 Half the link rate is reached where the fixed time equals the transfer time: 10 µs × 16 GB/s = 160 KB. Many small copies are slow; batch them into one.

Layer 3 — the engineer's depth

One analogy sentence: the corridor's capacity printed on the door is a promise for perfect traffic, and real traffic always loses some of it. The engineering consequences:

  • Why not 100 %. DRAM spends time on refresh, on opening rows and on turning the bus around between reads and writes; a copy (half reads, half writes) pays the turnarounds. Measured copy bandwidth is therefore the honest reference, which is why E2 compares with the vendor's bandwidth test, not with the datasheet.
  • Caches can fake bandwidth. If the data fits in the L2 cache, repeated runs read it from L2, faster than DRAM. Use arrays much larger than l2_cache_bytes (F6-07) when measuring DRAM bandwidth; Listing 2 uses 256 MiB arrays.
  • Copy timing and pageable memory. For a pageable host-to-device copy, cudaMemcpy may return before the DMA completes (H1); event timing in the same stream still waits for it, because the stop event is processed after the copy. A host clock around the call would not.
  • Pinned memory is a resource. Pin buffers you reuse (staging areas), not everything; the header's warning above is about the whole system.
  • Asynchronous copies. cudaMemcpyAsync from pinned memory can overlap with kernels on different streams; that is CU303's topic. From pageable memory the header says the staging "will be handled asynchronously with a worker thread" (H1), which still costs CPU work.
  • Link details. The real link's rate depends on PCI Express generation and lane count (F1-62); read them from the system (for example lspci -vv on Linux) and record them with the measurement.
Not verified — check before relying on this

The causes of the gap to 100 % (refresh, row activation, bus turnaround), the claim that vector loads help a copy approach the roof, and the event-ordering argument for pageable copies are stated from memory and from the header's description, not measured. This build has no GPU: no bandwidth, pinned/pageable ratio or vendor-tool number appears in this chapter. Check with the lab (steps 2–4) and with the CUDA C++ Best Practices Guide's sections on bandwidth and on pinned memory (D1).

How the hardware actually does it

Device memory (GDDR or HBM, F1-59) is connected to the GPU by several independent channels; the bus width in the device report is their total. The memory controllers keep many requests in flight from all SMs and schedule them to keep every channel busy; a kernel reaches the roof only when enough warps have loads outstanding to fill all channels at once (latency hiding, F1-60). D2 Host copies go through the copy engines (the device report's async_engine_count), DMA units that read host memory over PCI Express using physical addresses; that is why the pages must be locked while the engine works, and why pageable memory needs the staging copy described in the header (H1).

Note

The description of channels, controllers and copy engines is the model taught in HW301 (F1-59, F1-62); vendor-specific details for your GPU are in its architecture documentation (D2), not opened in this build.

Worked example

Task. On TG-1 (16 GB/s link, 10 µs per copy), estimate the pinned and pageable host-to-device times for 64 MiB, if the pageable path first copies the data on the CPU at an assumed 8 GB/s (an assumption for the example; Listing 3 shows how to measure your own) and the two steps do not overlap. Then give the ratio.

  1. Bytes. 64 MiB = 67,108,864 bytes.
  2. Pinned. 10 µs + 67,108,864 ÷ (16 × 109) s = 0.010 ms + 4.194 ms = 4.204 ms; 15.96 GB/s.
  3. Staging. 67,108,864 ÷ (8 × 109) s = 8.389 ms.
  4. Pageable, no overlap. 8.389 + 4.204 = 12.593 ms; 5.33 GB/s.
  5. Ratio. 12.593 ÷ 4.204 = 3.0: pinned is three times faster in this model.
  6. With full overlap (staging in chunks while the DMA runs), the slower step decides: about 8.4 ms, ratio 2.0. A real measurement lands somewhere between, which is why E2 asks you to measure and record the ratio.

Where the analogy breaks


    

  • A corridor's capacity is the same for carrying in and out; DRAM pays to switch direction, so a pure read stream can be faster than a copy.
    • 

  • Goods on the loading dock take dock space only; pinned memory takes physical memory away from every other program on the machine (H1).
    • 

  • Kitchen "deliveries" happen one at a time; real copy engines can work while kernels run (with pinned memory and streams, CU303).

Forensic lab answer key


Observation. 429.5 GB/s is 167.8 % of TG-1's 256 GB/s roof (R1, rosa_reported): impossible for data read from and written to DRAM.


Hypotheses. (a) Byte count: line 40 counts 2 × 4 × 226 bytes, correct for a full copy. (b) Less work: testable from the source, see below. (c) Cache: arrays of 256 MiB are far larger than any L2; unlikely.


Root cause. Line 29 computes the grid for float4 elements (n/4), but line 32 launches the scalar kernel with that grid: only n/4 threads run, each copying one float, so a quarter of the array is copied. With no correctness check in the timing runs, nothing noticed.


True bandwidth. A quarter of the bytes in 1.25 ms: 2 × 4 × 224 = 134,217,728 bytes ÷ 1.25 ms = 107.4 GB/s, 41.9 % of the roof. Evidence (3) shows the effect of the byte count on the same time: halving the bytes (copy_reads_only) gives 83.9 %; the correct count for a quarter of the copy halves that again to 41.9 % (not printed: compute it, or add the line kernel rosa_actual 16777216 4 4 1.25).


Fix and prevention. Launch copyVector with the n/4 grid (Listing 2, lines 54–59), or keep the scalar kernel with the n grid. Harness rule: check the result of every timed kernel against the reference after the timed runs, and refuse to print a GB/s above the roof (or above the reference) without a FAIL flag. How the evidence was produced: the program and the model are real runs in this build; Rosa's 1.25 ms is invented for the scenario.
