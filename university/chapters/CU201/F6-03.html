Story hook

Watch one helper, Mei, during a busy shift in the great kitchen hall. The thing she is working on right now is in her hands: nothing is faster to reach. In the middle of her row's table lies a tray of ingredients the whole table shares; she can reach it in a moment, but only the helpers at her table can, and the tray is cleared when the table's order is done. On the wall hangs the menu board: the same few numbers for everyone ("40 grams of cheese, 2 slices of tomato"), easy to read from anywhere, and nobody writes on it during service. Far away is the big pantry. Everything is there, every helper in the hall can fetch from it, and things stay there between orders; but every trip is a long walk.

And then there is Mei's private shelf in the big pantry. When her hands are full and the recipe says "keep the eight spice amounts for later", she has to park them somewhere. Her shelf is hers alone, but it is in the far pantry, so parking and fetching cost the same long walk as any pantry trip. A helper who keeps walking to her private shelf looks busy and gets little done. Knowing which of these places a value lives in is half of making a GPU program fast.

What you will be able to do

  • Name the five memory spaces of a CUDA kernel (registers, shared, global, constant, local) and say for each who can see it, how long it lives, and how you declare it.
  • Write a kernel that uses shared memory with a barrier, and constant memory set from the host.
  • Read the compiler's resource report (-Xptxas -v) and the PTX state spaces to find where each variable really lives.
  • Explain why a small per-thread array may end up in slow local memory, and show it with the compiler's own output.
  • Diagnose a kernel slowed by local memory from a resource report and its SASS.
Jargon box
Memory space (state space)
Simple words: one of the different places a GPU value can live, each with its own rules. Analogy: hands, table, menu board, pantry, private shelf. Precise: a class of memory with its own scope (which threads see it), lifetime and access instructions; PTX calls them state spaces and names them in its instructions (.reg, .shared, .global, .const, .local, .param). D1 D4 R1
Registers (GPU)
Simple words: each thread's own fastest storage for the values it is using right now. Analogy: each helper's hands. Precise: per-thread storage allocated by the compiler from the SM's register file for the thread's lifetime; ordinary local scalar variables live there; ptxas -v reports the count per thread. D1 R2
Shared memory
Simple words: a small, fast memory that the threads of one block share and manage themselves. Analogy: the table in the middle of a row group. Precise: on-chip memory declared __shared__, allocated per block for the block's lifetime and visible to all its threads; written and read explicitly, with a barrier (__syncthreads()) between writes and reads by other threads. D1 Not the shared memory between operating-system processes (OS304).
Global memory
Simple words: the GPU's big main memory that every thread and the host (by copies) can reach. Analogy: the big pantry far away. Precise: device memory allocated with cudaMalloc (or declared __device__), visible to all threads of all launches and kept between launches until freed; accessed with ld.global/st.global in PTX. D1 R1
Constant memory
Simple words: a small read-only area for values that are the same for every thread. Analogy: the menu board on the wall. Precise: device memory declared __constant__, read-only for kernels, written from the host with cudaMemcpyToSymbol, accessed through a cache; its total size is the device property totalConstMem. D1 H1
Local memory
Simple words: private storage of one thread that is kept in the slow main memory, used when registers are not enough or cannot be used. Analogy: a helper's private shelf in the far pantry. Precise: per-thread memory whose scope is private but which resides in device memory (cached); the compiler uses it for arrays it cannot keep in registers (for example indexed with a run-time value) and for register spills; SASS accesses it with LDL/STL, and ptxas reports it as "stack frame" and "spill" bytes. D1 R4
Barrier (__syncthreads)
Simple words: a "wait here until everyone in the block arrives" point. Analogy: the table waits until all ingredients are on the tray before anyone takes from it. Precise: a block-wide barrier: no thread of the block continues until all have reached it, and shared-memory writes before it are visible to the block's threads after it; bar.sync in PTX. D1 R1

Layer 1 — the kid explanation

A GPU helper can keep things in five places. In its hands: super fast, but only a few things fit. On its team's table: fast, shared with its team, cleared when the team is done. On the menu board: everyone reads it, nobody writes on it during the job. In the big pantry: everything fits and everybody can reach it, but it is far away. And on its own shelf in the big pantry: private, but equally far away.

Good GPU programs fetch each thing from the far pantry once, keep it in hands or on the table while working, and write the answer back once. Sharing a table needs one rule. If you put something on the table for your teammates, they must wait until everyone has put their part down before taking. That waiting point is called a barrier.

Sometimes the computer decides for you. If you ask a helper to keep a little list and pick an item "chosen later", the list may not fit in hands, so it goes to the private shelf. You did not ask for a pantry trip, but you got one. The compiler can tell you when that happens, and in this chapter you will read its report.

Layer 2 — the student explanation

One kernel, every space

Listing 1 is a kernel written to touch every space once. It computes out[i] = c0·in[i] + c1·(right neighbour of in[i] within the block) + c2·(an entry of a small private table). The constants c0, c1, c2 are in constant memory, set once by the host. Each thread reads its input from global memory, puts it into a shared tile, waits at the barrier, and reads its neighbour's value from the tile. The private table is an array of eight floats, and the entry used is chosen by a kernel argument, a value known only at run time.

What the PTX says

The compiler's PTX for Listing 1 (R1) names the space of every load and store. In order: .const declares coeff[12] (12 bytes: three floats); .shared declares the 1,024-byte tile (256 floats); a .local "depot" of 32 bytes holds the eight-float table; four ld.param load the kernel arguments; ld.global.f32 reads in[i]; st.shared.f32 writes the tile; bar.sync 0 is __syncthreads(); st.local.v4.f32 twice writes the table; ld.shared.f32 reads the neighbour; ld.local.f32 reads the chosen table entry; three ld.const.f32 read the coefficients; and st.global.f32 writes the result. R1 The source and the PTX agree line by line with the table above.

What ptxas says: PTX is not the end

PTX is not the final code: ptxas translates it to SASS and optimises on the way. Asked for its report with -Xptxas -v ("Specify options directly to ptxas", nvcc's help, R5 of F6-01), it says for Listing 1: 10 registers per thread, 1,024 bytes of shared memory, 12 bytes in constant bank 3 (our coeff), 376 bytes in constant bank 0, and "0 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads". R2 And the SASS of the kernel contains no local-memory instruction at all (R3). So the .local table of the PTX did not survive: ptxas found a way to keep the eight values in registers and select the right one. The lesson is about evidence, not about this kernel: the PTX shows what the front end asked for, the ptxas report and SASS show what the machine will do. When you want to know whether a kernel uses local memory, read the report, not the source.

Shared memory and the barrier

Shared memory is allocated when a block starts and released when it finishes; its contents are not kept between blocks or launches. D1 Because threads of a block run in warps that progress at different times, thread 5 cannot assume thread 6 has already written tile[6]. __syncthreads() makes every thread of the block wait until all have arrived, and makes the shared-memory writes before it visible to the block after it. D1 Two rules follow: every thread of the block must reach the same __syncthreads() (never put it inside an if that only some threads take), and there is no such barrier across blocks (F6-02). Listing 1 is careful about the first rule: threads with i ≥ n still write a 0 into the tile and reach the barrier; only the global store is guarded.

Constant memory

A __constant__ variable is written by the host before the launch with cudaMemcpyToSymbol and read by every thread; kernels cannot write it. D1 It is the natural home of small parameters that every thread reads, such as filter coefficients. Its total size per device is the property totalConstMem ("Constant memory available on device in bytes", H1); read your value from F6-07's report. Kernel arguments are a second way to pass the same kind of value; in this build's SASS, arguments and launch sizes are read from constant bank 0 (c[0x0][…] operands, F6-04), which is consistent with ptxas reporting bank 0 usage for every kernel.

Local memory

Local memory is private to a thread in scope but stored in device memory, so its accesses cost like global accesses (with caching). D1 The compiler uses it when a value cannot stay in registers: an array indexed with a value the compiler cannot resolve, a structure too large, or register spills when the kernel needs more registers than it may use (F1-58 forces spills with a register cap and reads the report). Listing 2 shows the first case in a form the compiler could not rescue: a per-thread histogram of 32 bins indexed by a value read from memory. Its report says "128 bytes stack frame" (32 floats × 4 bytes) and its SASS has 18 LDL/STL instructions; the rewritten version, which touches every bin with a compile-time index, has 0 bytes of stack frame and no local-memory instructions, at the price of 48 registers instead of 38 and more arithmetic per element. R4 R6 Which version is faster on a real GPU is a measurement, not a guess; this build could not make it.

Layer 3 — the engineer's depth

One analogy sentence: the hall's tables, hands and menu board are limited furniture, and how much each helper takes decides how many helpers fit in the hall at once. That is occupancy, the topic of CU302 and of F1-58: registers per thread × threads, and shared memory per block × blocks, must fit in one SM's register file and shared memory. Listing 1's 10 registers and 1 KiB per block are small; Listing 2's 48 registers in the fixed version are a real cost to weigh.

  • Sizes are properties. sharedMemPerBlock, regsPerBlock, totalConstMem, sharedMemPerMultiprocessor are fields of cudaDeviceProp; the header describes each (H1). Read them for your GPU in F6-07.
  • Dynamic shared memory. A kernel can declare extern __shared__ float buf[]; and receive its size as the third value of the execution configuration. D1 CU301 uses it.
  • Caches. Global and local accesses go through the L1 and L2 caches (F1-58); on some generations L1 and shared memory share the same on-chip storage. Which, and how they are split, is generation-specific.
  • Constant access pattern. Constant memory is designed for many threads reading the same address; if the threads of a warp read different constant addresses, the accesses are serialised. D2 For per-thread different read-only data, global memory with the right access pattern (F6-08) is the usual choice.
  • Other spaces. Texture and surface memory exist and are read through dedicated hardware; they are outside CU201.

The statements about caches in front of local and global memory, the shared L1/shared-memory storage on some generations, the serialisation of divergent constant-memory reads, and the meaning of ptxas's constant bank numbers (cmem[0], cmem[3]) are written from memory. Check: the CUDA C++ Programming Guide (device memory spaces; variable memory space specifiers; the compute-capability appendix for your GPU), the CUDA C++ Best Practices Guide (memory optimizations: constant memory, local memory), and the CUDA Binary Utilities document for SASS operands. The numbers in this chapter (10 and 38/48 registers, 1,024, 12, 376 and 128 bytes) are real compiler output for target sm_80 (R2, R4); other targets and toolkit versions can differ.

How the hardware actually does it

Registers are entries of the SM's register file, allocated to each resident thread for its lifetime; shared memory is a block of on-chip storage on the same SM, carved into per-block regions when blocks start (F1-58). D3 Global, local and constant data all live in the GPU's device memory (GDDR or HBM, F1-59), behind the L2 and per-SM caches; what differs is how the program may address them and which cache path the hardware uses. The SASS makes this concrete: LDG/STG for global (F6-04), LDL/STL for local (Listing 2's report), constant operands written c[bank][offset] directly inside arithmetic instructions (IMAD R4, R4, c[0x0][0x0], R3 in F6-04's SASS reads blockDim.x that way), and LDS/STS for shared. D4 R3 The far-pantry cost of a local access is therefore the same kind of cost as a global access: that is why a kernel full of LDL/STL is suspicious.

Worked example

Task. For Listing 1 launched with n = 65,536 and 256 threads per block, how much of each space is used in total, and how many global-memory bytes does one run move?

  1. Blocks. 65,536 / 256 = 256 blocks (exact).
  2. Registers. 10 per thread (R2) × 65,536 threads = 655,360 registers over the whole grid; but only the resident blocks hold registers at any moment, so the limit that matters is per SM (F1-58).
  3. Shared memory. 1,024 bytes per block (R2) = 256 floats × 4 bytes; it exists only while the block runs.
  4. Constant memory. 12 bytes for the whole program (three floats), written once by the host.
  5. Global traffic per run. Each thread reads one float and writes one float: 65,536 × (4 + 4) = 524,288 bytes = 512 KiB. The neighbour value comes from shared memory, not from a second global read: without the tile, each thread would read two floats from global memory and the reads would be 1.5 times as many bytes in total (65,536 × 12 instead of 65,536 × 8 bytes, if nothing is cached).
  6. Listing 2's local memory. 32 bins × 4 bytes = 128 bytes per thread, which is exactly the stack frame ptxas reports (R4); for the launch's 1,024 threads, 128 KiB of local memory traffic area, every byte of it in the far pantry.

Where the analogy breaks


    

  • A private shelf sounds fast because it is private; local memory is not. "Local" describes who may see it, not where it is: it lives in device memory. D1 The kitchen word "local" would suggest "near"; the GPU meaning is the opposite.
    • 

  • You choose where to put your things; the compiler chooses for registers and local memory. You cannot declare a variable "in registers"; you write a scalar and the compiler decides, as Listing 1's table shows (R1–R3).
    • 

  • The far pantry has shelves near the hall. Global and local data go through caches, so a repeated trip can be short. The analogy's "every trip is long" is the worst case, not a rule (F1-58).
    • 

  • Helpers glance at the table whenever they like; threads must wait at the barrier. Without __syncthreads(), reading a neighbour's slot is a data race, as in F2-35.
    •

Summary


    

  • Registers: per thread, fastest, chosen by the compiler; count reported by ptxas -v.
    • 

  • Shared memory: per block, on chip, __shared__, lives for the block; use __syncthreads() between writes and others' reads, reached by all threads.
    • 

  • Global memory: all threads and launches, cudaMalloc, kept until freed, off-chip.
    • 

  • Constant memory: __constant__, read-only in kernels, written with cudaMemcpyToSymbol.
    • 

  • Local memory: private in scope but off-chip; caused by run-time-indexed arrays and spills; shows as stack frame or spill bytes and LDL/STL.
    • 

  • PTX shows the requested spaces; ptxas and SASS show what the machine really does.
    •

Forensic lab answer key


Observation. binsSlow: 128 bytes stack frame, 0 spill stores and loads, 38 registers; 18 LDL/STL instructions, starting with four STL.128 [R1…], RZ that zero the bins. binsFixed: 0 bytes stack frame, 48 registers, 0 local-memory instructions (R4, R6).


Hypotheses. Input reads (each element once: keys and vals), output writes (32 per thread, once), or local-memory traffic for the bins (a load and a store per input element). The stack frame of exactly 32 × 4 bytes and the LDL/STL instructions support the third: every input element causes an extra read-modify-write in device memory.


Root cause. Line 18, bins[keys[j] & (kBins - 1)] += vals[j]: the index comes from memory at run time. Registers are named inside the instruction (R5, R6, …), so a register cannot be chosen by a run-time number; the compiler therefore places the array in local memory, addressed like memory. This is not a spill (spill bytes are 0): it is the array's home.


Fix and cost. binsFixed uses only compile-time indices (fully unrolled loops over k), so each bin is its own register. Costs: 10 more registers per thread (48 versus 38, which can lower occupancy) and 32 conditional additions per input element instead of one. Whether it is faster must be measured on the lab GPU (Lab step 5); in this build it was not.


Wrong answers. "Register spills": the report says 0 spill bytes. "The input reads are uncoalesced": the grid-stride loop reads neighbouring elements in neighbouring threads (F6-08).


Prevention. Build with -Xptxas -v in CI and fail (or warn) when a kernel's stack frame or spill bytes are non-zero unless an allow-list says so; review rule: no run-time-indexed private arrays in hot loops. How the evidence was produced: real compiler runs in this build (nvcc 12.0, target sm_80); no fault was injected, the slow version is written that way on purpose.
