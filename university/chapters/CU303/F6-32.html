Story hook

The great kitchen hall is slow on Fridays, and everyone has a theory. The cooks blame the porters. The porters blame the head chef's order slips. The head chef blames the oven. Each theory sounds right, and each person is sure.

Zainab, the new hall manager, stops the arguments. She hangs a long sheet of paper on the wall with one row for each station: the head chef's desk, the pass, the porters coming in, the porters going out, the cooks. Every few seconds an assistant marks on each row what that station is doing. After one Friday, the sheet tells the story. The cooks' row is mostly empty. The porters' rows have long bars, but never at the same time as the cooks. And on the head chef's row there is a pattern: every time a pot goes out, she stands at the door and waits until the porter is back, before she writes the next slip.

"Nobody was lazy," Zainab says. "The order of things was wrong, and the chart shows exactly where."

In CUDA, Zainab's wall chart is a timeline profile, the rows are the host threads, the API calls, the copy engines and the kernels, and Nsight Systems is the tool that draws it. This chapter teaches you to read one, to make your own program's phases show up on it, and to reduce it to numbers you can compare with your plan.

What you will be able to do

  • Explain what a whole-program (system-level) timeline shows, which rows it has, and which questions it answers that a kernel profiler cannot.
  • Instrument a program with NVTX ranges so that its own phases appear on the timeline, at close to zero cost when no tool is attached.
  • Reduce a timeline export to three numbers (lane busy fractions, compute idle time, copy–kernel overlap) with a small program, and compare them with the plan of F6-29.
  • Verify milestone E8's overlap acceptance test from a timeline: overlap is visible, and the end-to-end gain is within 20 % of the prediction.
  • Diagnose "no overlap" from an exported timeline: pageable host memory turning every device-to-host copy into a host wait.
Jargon box
System-level profiler (timeline profiler)
Simple words: a tool that records what every part of the program did over time and draws it as rows. Analogy: Zainab's wall chart with one row per station. Precise: a profiler that traces host threads, runtime and driver API calls, memory copies and kernel executions (and optionally operating-system and library activity) with timestamps on a common time axis; NVIDIA's tool for this is Nsight Systems. D1 Contrast with a kernel profiler (F6-33), which looks inside one kernel.
Trace and sampling
Simple words: a trace writes down every event; sampling looks every so often. Analogy: writing down every slip the chef writes, versus glancing at each station every few seconds. Precise: tracing records each instrumented event (an API call, a copy, a kernel) with start and end times; sampling records the state (for example the CPU's program counter) at intervals and estimates where time goes. Timelines of GPU work are traces. D1 D5
NVTX range and marker
Simple words: labels your program puts on the timeline: "from here to here I was doing X", or "X happened now". Analogy: the head chef writing "Friday specials" on her own row of the chart. Precise: calls of the NVIDIA Tools Extension library such as nvtxRangePushA/nvtxRangePop (a nested range on the calling thread) and nvtxMarkA (an instantaneous marker); the installed header says the library "introduces close to zero overhead if no tool is attached". H2
Lane (timeline row)
Simple words: one row of the chart, for one thing that can be busy. Analogy: the porters-in row. Precise: a horizontal track for one execution resource or source of events: a host thread, the CUDA API calls of that thread, a stream, a copy direction, kernels on a device. Bars in one lane of an engine do not overlap; overlap appears between lanes (F6-28).
Busy fraction and idle gap
Simple words: how much of the time a row is doing something, and the empty stretches in between. Analogy: how much of the evening the cooks were actually cooking. Precise: the sum of bar lengths in a lane divided by the timeline's total time; an idle gap is an interval with no bar in that lane. Listing 3 computes both from an export.
Copy–kernel overlap
Simple words: the time during which a copy and a kernel ran at the same moment. Analogy: the time when porters and cooks were both busy. Precise: the measure of the union of intervals where at least one copy-lane bar and at least one compute-lane bar are active; zero overlap with streams in the code means something serialised them.
Host synchronisation point
Simple words: a call where the CPU stops and waits for the GPU. Analogy: the head chef standing at the door until the porter is back. Precise: a runtime call that returns only after GPU work completes, for example cudaStreamSynchronize, cudaEventSynchronize, and copies documented as synchronous, such as any device-to-host copy into pageable memory, which "will return only once the copy has completed". H1

Layer 1 — the kid explanation

A fast program is a team where everyone is busy at the right time. When it is slow, guessing who is to blame does not work. You need to see what each part did, and when.

A timeline profiler draws that picture. It gives each part of the computer its own row. The CPU's work is one row. Copies into the GPU are another. The GPU's calculations are another. Each job is a bar.

Your program can write its own labels on the picture, like "loading" or "checking". Then you can see which part of your code caused which bars.

Then you look for empty space. An empty row means a worker was waiting. Bars that never sit above each other mean nothing happened at the same time. The picture shows where to look; your plan says what it should have looked like.

Layer 2 — the student explanation

What a whole-program profiler records

Analogy first: one row per station, one bar per job. Nsight Systems is NVIDIA's system-wide performance analysis tool; its documentation describes tracing of CUDA API calls, memory copies and kernels, NVTX annotations, operating-system runtime calls and CPU sampling, all on one time axis, and exporting the collected report for later analysis. D1 The value of the whole-program view is that it shows relations: the host call that caused a kernel, the copy that a kernel waited for, the host thread that sat in a synchronisation call while the GPU was idle. A kernel profiler (F6-33) cannot show any of that, because it looks at one kernel at a time.

Putting your program's phases on the timeline: NVTX

The profiler sees API calls and GPU work, but not your program's meaning: it cannot know that a loop is "fill input" or that a block of calls is "pipeline". The NVIDIA Tools Extension (NVTX) lets the program say so. The installed header describes NVTX as "a set of functions that a developer can use to provide additional information to tools", and distinguishes markers, which "describe events at a specific time", from ranges, which describe "a time span". H2 Listing 1 brackets its phases with nvtxRangePushA and nvtxRangePop; ranges nest per thread. The header documents the return values: push returns "the 0 based level of range being started", pop returns "the level of the range being ended", and both return a negative value if an error occurs. H2

Two properties make NVTX safe to leave in production code. The header says the library "introduces close to zero overhead if no tool is attached to the application" and that the overhead with a tool attached "is specific to the tool". H2 And with this toolkit's nvtx3 headers, Listing 2 needed no extra library to build and run in this container: it compiled with g++ alone, ran, and showed that with no tool attached nvtxRangePop returned a negative value (R2), the documented error signal, while the program's own work was unaffected.



Reading a timeline: three questions in order


    

  1. Is the compute row full? The GPU's kernels should cover most of the time of the phase you care about. Long idle gaps in the compute row are the first thing to explain.
    2. 

  2. Do copies sit under kernels? In a pipeline (F6-29), the copy rows should have bars at the same times as the compute row. If copies and kernels alternate like a zip, something serialises them.
    3. 

  3. Where does the host wait? Look at the CUDA API row of each host thread: a long bar in a synchronisation call, or in a copy call, means the host was blocked. If the host is blocked, it cannot issue the next work, and the GPU will starve after it.
    4. 



The answers become numbers with Listing 3: busy fraction per lane, total and longest idle gap in the compute lane, and the time during which at least one copy and at least one kernel ran together.


Why pageable memory serialises: the documented host behaviour


The runtime header has a section, "API synchronization behavior", that every profile reader should know. For the asynchronous copy functions it says: "For transfers from device memory to pageable host memory, the function will return only once the copy has completed", while "for all other transfers, the function is fully asynchronous. If pageable memory must first be staged to pinned memory, this will be handled asynchronously with a worker thread". For the synchronous forms, "for transfers from pageable host memory to device memory, a stream sync is performed before the copy is initiated". H1 So in a loop that issues copy in, kernel and copy out for each chunk, a copy out into pageable memory holds the host thread until that chunk is completely done, and the next chunk is not even issued until then. The streams in the code are correct; the host simply never gets far enough ahead to give the GPU two chunks at once. That is the forensic lab of this course, predicted by the documentation before any profiler is opened.



Layer 3 — the engineer's depth


One analogy sentence: the wall chart is only as good as the questions you bring to it and the plan you compare it with.


Method: plan, record, reduce, compare


Milestone E8's first acceptance test is: "Timeline (Nsight Systems or ROCm Systems Profiler) shows overlapping copies and kernels; end-to-end time improves over the single-stream version by the amount predicted in your plan, within 20 %." C1 It has three parts, and each needs its own evidence:


    

  1. Plan. A prediction made before running: the model of F6-29 with your measured copy and kernel times, giving the expected pipeline time and the expected gain over one stream.
    2. 

  2. Record. A report of the single-stream run and of the pipeline run, with NVTX ranges around the measured phase so that set-up and checking are excluded the same way in both.
    3. 

  3. Reduce and compare. From the reports: the duration of the measured range, the overlap, the busy fractions. The verdict is |measured gain − predicted gain| ≤ 20 % of the predicted gain, and a visible overlap.
    4. 



Write the plan's numbers and the measured numbers in the same table. When they disagree by more than the tolerance, that is not failure; it is the start of a forensic investigation, and the timeline is the evidence.


The observer effect


Tracing is not free. Every traced API call and every GPU activity record costs some time, and the tool's documentation discusses its own overhead and how to reduce it (fewer traced APIs, shorter collection). D1 Two rules follow. Take durations from the profiler but cross-check the end-to-end time with events or a host clock in an untraced run (F6-06). And never take timing from a run under an instrumentation tool built for correctness, such as Compute Sanitizer; F6-31's forensic lab showed the same effect on the CPU with AddressSanitizer.

How the hardware actually does it


A timeline is assembled from timestamps taken in two places. On the host, the tool intercepts runtime and driver calls (and NVTX calls, through the injection mechanism the NVTX header's initialisation section describes) and stamps them with a host clock. H2 On the GPU, start and end times of copies and kernels are recorded by the device and collected by the tool through NVIDIA's profiling interfaces; the tool then places both on one axis. D1 D2 This is why a launch call (host row) and its kernel (GPU row) appear at different times: the call only queues work (F6-28). The copy lanes correspond to the DMA copy engines (F1-44, F1-62); counting the copy lanes that are busy at the same moment is a direct reading of asyncEngineCount in action.


Not verified — check before relying on this
How GPU timestamps are generated and correlated with host time, the timestamp resolution, and how much tracing perturbs short kernels were not available in any document opened in this build. Read the Nsight Systems User Guide (D1) and the CUPTI documentation (D2) for your versions, and report profiler durations as "measured with Nsight Systems version …".



Worked example


Reduce a timeline by hand, then check with Listing 3. The timeline is F6-28's two-stream scenario (Figure 1 there), written as six export rows in timeline_stats.in: A-in 0–30 and B-in 30–60 on the copy-in lane; A-kernel 30–70 and B-kernel 70–110 on the compute lane; A-out 70–100 and B-out 110–140 on the copy-out lane.


    

  1. Total. From the earliest start (0) to the latest end (140): 140.
    2. 

  2. Busy fractions. Compute: 40 + 40 = 80, so 80 / 140 = 57.1 %. Copy in: 60 / 140 = 42.9 %. Copy out: 60 / 140 = 42.9 %.
    3. 

  3. Compute idle. Before the first kernel: 30. Between kernels: 70 − 70 = 0. Total 30, longest gap 30.
    4. 

  4. Overlap. Cut the axis at every start and end: 0, 30, 60, 70, 100, 110, 140. In 0–30 only a copy runs; in 30–60 B-in and A-kernel (30); 60–70 only A-kernel; 70–100 B-kernel and A-out (30); 100–110 only B-kernel; 110–140 only B-out. Overlap = 60, which is 42.9 % of 140.
    5. 

  5. Interpretation. Without overlap the same work would take 200 (one stream). The overlap of 60 is exactly the time saved: 200 − 140. That identity holds whenever each lane is a single in-order engine and the lanes' busy times are fixed.
    6.

Where the analogy breaks


    

  • Zainab's assistant does not slow the cooks; a profiler slows the program. Tracing has overhead (Layer 3), so a profile is a slightly different run than the one you ship.
    • 

  • The wall chart shows every station; a timeline shows what was traced. Work the tool did not trace (an untraced library, another process on the GPU) leaves empty space that looks like idleness.
    • 

  • A bar on the chart means a person was working. A bar on the CUDA API row may mean the host was waiting inside a call (a synchronisation, a pageable copy). Busy on the host row is not useful work.
    • 

  • The chart's rows are fixed stations. GPU rows group work by stream, by device or by engine, depending on how the tool is configured; the same run can look different in two views.
    •

Summary


    

  • A whole-program timeline puts host threads, API calls, copies and kernels on one time axis; it shows relations between them that no kernel profiler can.
    • 

  • NVTX ranges and markers put your program's own phases on the timeline at close to zero cost when no tool is attached; the calls return negative values when they cannot do anything.
    • 

  • Read a timeline with three questions: is the compute row full, do copies sit under kernels, where does the host wait. Reduce it to busy fractions, idle gaps and overlap.
    • 

  • A device-to-host asynchronous copy into pageable memory returns only once the copy has completed; in a per-chunk loop it serialises the whole pipeline regardless of streams.
    • 

  • Profilers perturb what they measure: take structure from the profile and end-to-end times from untraced runs.
    • 

  • Milestone E8's overlap test needs a plan made in advance, a timeline that shows overlap, and a measured gain within 20 % of the plan.

Forensic lab answer key


Observation. Timeline A (pinned): total 100.0, each lane busy 80.0 %, compute idle 10.0, overlap 80.0 (R7). Timeline B (pageable): total 240.0, each lane 33.3 %, compute idle 150.0 with gaps of 20.0 between every pair of kernels, overlap 0.0 (R8). In B, chunk 1's copy in (in1, stream 2) starts at 30.0, exactly when chunk 0's copy out (out0) ends.


Hypotheses. (a) Legacy default stream; (b) one copy engine; (c) over-synchronisation in the loop; (d) pageable host memory blocking the host; (e) kernels too long to overlap. The source rules out (a) (non-blocking streams, lines 45–48, no launch without a stream) and (c) (one cudaDeviceSynchronize, after the loop, line 67). (b) cannot explain B: even with one engine, chunk 1's copy in could run during chunk 0's kernel. (e) is ruled out by A, which overlaps with the same kernels.


Evidence-based conclusion. "For transfers from device memory to pageable host memory, the function will return only once the copy has completed" (H1). Line 65 issues chunk 0's copy out and the host waits there until it ends at 30.0; only then does the loop issue chunk 1. The host never has two chunks in flight, so the timeline is serial, and the single difference between A and B in the model's input is exactly that rule. The 2.4× difference (240.0 against 100.0) matches Wei's "more than twice as fast".


Fixes. (1) Stage through pinned buffers: allocate a few pinned chunk-sized buffers once, copy the result chunk from pinned to the vector on the host after an event says the chunk is done (cost: pinned memory and one host memcpy per chunk, which can overlap with GPU work of later chunks). (2) Register the vector's memory with cudaHostRegister once, which page-locks existing memory (H1 of F6-29; cost: registration time, and the vector must not reallocate while registered). Reordering the loop breadth-first helps the copies in but still blocks at each copy out.


Verification and prevention. Record a new timeline: the "pipeline" range should show copies under kernels and a total close to the plan; check 0 errors. Prevent: a rule that every buffer passed to cudaMemcpyAsync is pinned or registered, enforced by a small wrapper that checks cudaPointerGetAttributes in debug builds; and the E8 timeline test in the team's performance checks. How the evidence was produced: two runs of the F6-28 model on inputs whose operation order is copied from Listing 1, with the documented pageable rule enabled only in B; summaries by Listing 3. No GPU and no profiler were involved, and the pack says so.
