Story hook

The great kitchen hall has two stores. The head chef keeps a larder next to her office; the hall has its own pantry beside the cooks. Until now, Amara wrote a delivery order every time something had to go from her larder to the pantry or back. It works, but she must remember every crate.

Ravi, the new store manager, proposes a different system. "Every crate gets one number, valid in both stores. Nobody writes delivery orders. If a cook reaches for crate 812 and it is in the larder, a runner fetches it, and the cook waits a moment. If you want the cooks never to wait, tell the runners in advance which crates will be needed, and they bring them over before the cooks start."

It feels like magic at first. Then the evening of the tasting comes. After every single course, Amara walks to the pantry and tastes from every crate. The runners carry the crates to her larder, then back to the pantry for the next course, then back again. The kitchen spends the evening carrying crates.

In CUDA, the shared crate number is a managed pointer, the runners are page migration, the advance notice is prefetching, and Amara's tasting is the most common way to make managed memory slow.

What you will be able to do

  • Explain what managed memory is, what one pointer valid on both processors means, and what the device attributes managedMemory, concurrentManagedAccess and pageableMemoryAccess tell you.
  • Connect GPU page migration to the demand paging you know from the CPU, using a real fault count measured in this build.
  • Write a managed-memory program with cudaMallocManaged, cudaMemPrefetchAsync and cudaMemAdvise, synchronising correctly before the CPU touches the data.
  • Predict with a cost model when on-demand migration is close to explicit copies and when it is many times slower (fault granularity, ping-pong access).
  • Diagnose a measurement whose fault count does not match the plan, separating the program's own page faults from those of a tool.
Jargon box
Managed memory (unified memory)
Simple words: memory with one address that both the CPU and the GPU can use; the system moves the data to whoever uses it. Analogy: crates with one number valid in both stores, moved by runners. Precise: memory allocated with cudaMallocManaged or declared __managed__; the header says the pointer "is valid on the CPU and on all GPUs in the system that support managed memory" and "all accesses to this pointer must obey the Unified Memory programming model". It is released with cudaFree. H1 D1
Page migration
Simple words: moving a page of data to the memory of the processor that uses it. Analogy: a runner carrying a crate from one store to the other. Precise: on systems where devices report concurrentManagedAccess, "managed memory can migrate to any processor's memory at any time", and "the Unified Memory driver will employ heuristics to maintain data locality and prevent excessive page faults". H1
Page fault (GPU, managed memory)
Simple words: the moment a processor reaches for data that is not where it can use it, and must wait for it. Analogy: the cook reaches for crate 812, it is not there, and the cook waits for the runner. Precise: an access to a virtual page that has no valid mapping for the accessing processor, resolved by the operating system (CPU, F1-38, F3-21) or by the Unified Memory driver (GPU) before the access is retried. D1 D4
Prefetch (managed memory)
Simple words: moving data to where it will be needed before anyone asks for it. Analogy: telling the runners in advance which crates to bring. Precise: cudaMemPrefetchAsync(ptr, bytes, dstDevice, stream) migrates a managed range to a GPU or, with cudaCpuDeviceId, to host memory, as an operation in a stream; the header calls it "not required for functionality" and says it "only serves to improve performance". H1
Memory advice
Simple words: hints that tell the system how you will use a range of memory. Analogy: notes on a crate: "mostly for tasting", "keep in the pantry", "the larder will look at this too". Precise: cudaMemAdvise with cudaMemAdviseSetReadMostly, cudaMemAdviseSetPreferredLocation or cudaMemAdviseSetAccessedBy (and their unset forms), each with documented effects on duplication, migration and mapping. H1
Thrashing (ping-pong migration)
Simple words: data moving back and forth between two processors again and again. Analogy: crates carried to the larder after every course and back again. Precise: repeated migration of the same pages because two processors take turns accessing them; the header mentions the driver's "page thrash detection and resolution logic", which may eventually pin a constantly thrashing page to host memory. H1
Minor page fault
Simple words: a page fault the operating system fixes without reading the disk. Analogy: the crate is in the building; it only needs to be put on the right shelf. Precise: the count Linux reports in ru_minflt of getrusage; Listing 2 uses it to count first-touch faults on the CPU. D5 R2

Layer 1 — the kid explanation

The CPU and the GPU each have their own memory. Until now you copied data from one to the other yourself. With managed memory, you get one address that works on both. You stop writing copies.

The data still has to travel. When the GPU touches data that is in the CPU's memory, it stops and waits. The system carries a piece of memory, a page, across. Then the GPU goes on. This waiting is called a page fault.

If you know which data the GPU will need, you can say so first. That is a prefetch. The pages travel in one big trip before the work starts, and nobody waits.

The worst case is two processors taking turns. The CPU looks at the data, then the GPU, then the CPU again. Each turn, the pages travel. Managed memory makes that easy to write and slow to run.

Layer 2 — the student explanation

Allocating and using managed memory

Analogy first: one crate number, valid in both stores. cudaMallocManaged(&p, bytes) returns a pointer that "is valid on the CPU and on all GPUs in the system that support managed memory". The memory "is not cleared"; a size of 0 returns cudaErrorInvalidValue; if the device does not support managed memory the call returns cudaErrorNotSupported, and support "can be queried using the device attribute cudaDevAttrManagedMemory". The memory is released with cudaFree. H1 The optional flags argument sets the default stream association (cudaMemAttachGlobal, the default, or cudaMemAttachHost). H1

Three device attributes decide what you may do with it. Their one-line descriptions in this build's driver_types.h are: cudaDevAttrManagedMemory, "Device can allocate managed memory on this system"; cudaDevAttrConcurrentManagedAccess, "Device can coherently access managed memory concurrently with the CPU"; cudaDevAttrPageableMemoryAccess, "Device supports coherently accessing pageable memory without calling cudaHostRegister on it". H2 Listing 1 prints the first two before doing anything else. Record them in your device report (F6-07): the rest of this chapter depends on them.

The one rule you must not break: synchronise before the CPU touches it

A managed pointer does not make the GPU's work synchronous. The kernel launch still returns before the kernel finishes (F6-28). If the CPU reads the data while the kernel is still writing it, it reads a mix of old and new values, or worse. On a device whose concurrentManagedAccess is 0, the rules are stricter: the header's description of cudaStreamAttachMemAsync speaks of "exclusive ownership of the managed memory region by an active GPU", by default for "whole-GPU activity", and describes how attaching memory to a single stream lets the CPU access it "so long as all operations in stream have completed, regardless of whether other streams are active". H1 Either way, the safe program waits (stream, event or device synchronisation) before the CPU touches managed data that the GPU may be using. Listing 1 waits with cudaEventSynchronize(stop) at line 39 and says so in a comment.

Do not test it on a machine you depend on; read D1 for your toolkit and record the answer in your dossier.

Prefetching

cudaMemPrefetchAsync(p, bytes, dst, stream) enqueues a migration in a stream. The header's description is the specification you need: the range "must refer to managed memory"; passing cudaCpuDeviceId as destination "will prefetch the data to host memory"; to prefetch to a GPU, cudaDevAttrConcurrentManagedAccess "must be non-zero"; the range is rounded to CPU page size; "if no physical memory has been allocated for this region, then this memory region will be populated and mapped on the destination device"; by default "any mappings to the previous location of the migrated pages are removed"; and the call "is asynchronous with respect to the host and all work on other devices". H1 Because it is a stream operation, a prefetch before a kernel in the same stream is ordered before it; a prefetch back to the CPU after the kernel is ordered after it. That is exactly the pattern of Listing 1, lines 31–36.

Note the two promises the header makes: prefetching "is not required for functionality", and "memory accesses to this range are always coherent and are allowed even when the data is actively being migrated". H1 A wrong prefetch costs time, never correctness. That makes managed memory a good way to start a port: get it correct with no copies at all, then add prefetches where the profiler shows faults (F6-32).

Advice

cudaMemAdvise(p, bytes, advice, device) attaches a usage hint to a range. The header documents three hints and their unset forms: H1

Layer 3 — the engineer's depth

One analogy sentence: runners are free to hire but each trip has a fixed cost, so the questions are how many trips, how big, and whether anyone has to wait for them.

Demand paging, measured on the CPU

The GPU side of managed memory could not be measured in this build. The idea underneath it can: an operating system that maps memory lazily and fills a page only when it is first touched. Listing 2 maps 256 MiB of anonymous memory, touches one byte per 4096-byte page, and counts minor page faults with getrusage. Its run without sanitizers (R4) is the clean measurement:



Read it like a profile. The mapping has 65,536 pages. Pass 1 faults on (almost) every one of them: that is demand paging, one fault per first touch. Pass 2 touches the same pages and faults on none. The MAP_POPULATE mapping pays for all its pages during mmap itself, and pass 3 then runs without faults. The fault counts are the operating system's own numbers; the times were measured in this cloud container and vary from run to run, so treat them as an order of magnitude for this machine only (AH-23). R4 D5


Two transferable lessons: the cost of the first touch is per page, so it scales with the number of pages, not with how much of each page you use; and paying it in advance (populate, prefetch) moves the cost, it does not remove it. A prefetch moves it to a place where it can overlap with other work or happen as one bulk transfer.


A cost model for managed memory


Listing 3 models four strategies for a kernel that touches every byte of a buffer of B bytes, N times. Bulk transfers cost α + B/β (TG-1's link: α = 10 µs, β = 16 GB/s, F1-62). On-demand migration is modelled as B/s fault groups of size s, each paying a fault cost φ, plus the same B/β of transfer. All of α, β, s and φ are invented teaching values; the point is the structure, not the numbers:


    

  • explicit copies and prefetch: 2(α + B/β) + N·k;
    • 

  • on-demand: 2((B/s)·φ + B/β) + N·k;
    • 

  • ping-pong (the CPU reads after every pass): N · 2((B/s)·φ + B/β) + N·k.
    • 



The structure says three things a measurement must then confirm. The fault term grows with the number of groups, so larger groups (or prefetching, which is one bulk operation) shrink it. Ping-pong multiplies the transfer term by N: no fault granularity can fix an algorithm that moves the data every pass. And when the kernel is long compared with the transfers, all strategies converge. R3


Where the data lives: what the header says about multi-GPU systems and Windows


The documentation of cudaMallocManaged is unusually explicit about placement. On systems where all GPUs report concurrentManagedAccess, managed memory "may not be populated when this API returns and instead may be populated on access", and can migrate at any time. Where all GPUs report 0 for that attribute but support peer-to-peer access, "the physical storage for managed memory is created on the GPU which is active at the time cudaMallocManaged is called", other GPUs reach it "at reduced bandwidth via peer mappings over the PCIe bus", and "the Unified Memory driver does not migrate memory among such GPUs". In the remaining mixed case the location is "system-dependent", and the header adds that on Windows in that case "the physical storage is always created in 'zero-copy' or host memory". H1 Practical consequence: the same managed-memory program can behave very differently on two machines. Record the attributes of every GPU in the dossier before interpreting any timing.


Oversubscription and eviction


On GPUs with a non-zero concurrentManagedAccess, the header says that "device memory oversubscription is possible": managed memory "may be evicted from device memory to host memory at any time by the Unified Memory driver in order to make room for other allocations". Memory from cudaMalloc is not evicted by prefetching. H1 That allows data sets larger than GPU memory, at the price of migrations you did not plan. When a working set does not fit, chunked explicit copies (F6-29) give you control over every byte that moves; managed memory gives you convenience and lets the driver decide.


When to use which


Use managed memory to get a port correct quickly, for data structures with pointers that both processors follow (a linked structure would need deep copies otherwise), and for working sets that may exceed GPU memory. Add prefetches and advice where the profiler shows faults. Use explicit device memory and pinned staging buffers when you need predictable transfer times and overlap that you plan chunk by chunk, as in the E8 pipeline. Never decide by belief: write both, profile both (F6-32).



How the hardware actually does it


Both processors translate virtual addresses through page tables (F1-38, F3-21). A managed range has a virtual address that is the same for the CPU and the GPU; what changes is which page table holds a valid entry, and which physical memory that entry points to. Migration is therefore three things: unmapping in one page table, a DMA copy over the link (F1-44, F1-62), and mapping in the other page table. A GPU that can take page faults lets a warp stop on an unmapped page and resume after the driver has done those three steps; prefetch does them before any warp asks. D1 D4 TLBs on both sides cache translations, so unmapping a page also means invalidating cached translations, one more fixed cost per migration (F1-38).

Worked example


A buffer of 256 MiB = 268,435,456 bytes; a kernel that takes 2 ms per pass; TG-1's link: α = 0.010 ms, β = 16 GB/s = 16,000,000 bytes per ms; on-demand fault groups of 64 KiB with φ = 20 µs each (invented).


    

  1. Transfer time, one direction. B/β = 268,435,456 / 16,000,000 = 16.777 ms. Bulk: 16.787 ms with α.
    2. 

  2. Explicit copies, one pass. In and out: 2 × 16.787 = 33.574 ms, plus 2 ms of kernel: 35.574 ms.
    3. 

  3. On-demand, one pass. Number of groups: 268,435,456 / 65,536 = 4096. Fault cost: 4096 × 0.020 = 81.92 ms per direction, plus 16.777 ms of transfer = 98.697 ms. Both directions plus kernel: 2 × 98.697 + 2 = 199.394 ms, 5.6 times the explicit version.
    4. 

  4. Ten passes, data stays on the GPU. The transfers do not repeat: explicit 33.574 + 20 = 53.574 ms; on-demand 197.394 + 20 = 217.394 ms.
    5. 

  5. Ten passes with the CPU reading after each (ping-pong). 10 × 197.394 + 20 = 1993.94 ms: 37 times the explicit version.
    6. 

  6. Larger groups (2 MiB). 128 groups, fault cost 2.56 ms per direction: on-demand 2 × 19.337 + 20 = 58.674 ms, only 10 % worse than explicit. Ping-pong still costs 406.744 ms.
    7.

Where the analogy breaks


    

  • A crate is either here or there; a page can be in both. With cudaMemAdviseSetReadMostly, reads create read-only copies in several memories at once (H1). There is no "duplicate crate" in the story.
    • 

  • Runners carry whole crates, not the one onion you asked for. That part maps well; but the size of the "crate" (the migration granularity) is not something you choose, and it is not documented in the sources of this build.
    • 

  • A cook can reach into the other store. With cudaMemAdviseSetAccessedBy or on systems without migration, a processor can map and read memory in place over the link without moving it (H1); the story has no long-armed cooks.
    • 

  • Waiting cooks do not stop the hall. In the kitchen, other cooks keep working while one waits. On a GPU, other warps may keep the SMs busy while one warp waits for a fault, but how much work can continue during fault handling is not documented here (unverified box).

Transition box

Where you came from: F6-29, where you copied every byte explicitly through pinned buffers, and F1-38 and F3-21, where the CPU's page tables and page faults made virtual memory work. What carries over: asynchronous execution and the duty to synchronise before the CPU reads (F6-28); the α–β cost of moving bytes over the link (F1-62); the page-fault mechanism itself, now between two processors. H1 D1 What changes: most dangerous first: the code no longer shows when data moves, so a single CPU access inside a loop can move the whole buffer every iteration; behaviour depends on device attributes and the operating system (H1, H2); prefetching and advice are optional for correctness but decide performance. What comes next: F6-32 makes the invisible visible: a whole-program timeline with copies, kernels, launches and, on a GPU, unified-memory activity.

Summary


    

  • Managed memory gives one pointer valid on the CPU and on GPUs that support it; it is allocated with cudaMallocManaged, freed with cudaFree, and not cleared.
    • 

  • Data still moves: pages migrate on demand when a processor touches them, at the price of page faults, or in bulk when you prefetch.
    • 

  • The device attributes managedMemory, concurrentManagedAccess and pageableMemoryAccess decide what is allowed and how data is placed; record them before interpreting any timing.
    • 

  • Always synchronise before the CPU touches managed data that the GPU may be using.
    • 

  • cudaMemPrefetchAsync and cudaMemAdvise never change results; they change where data is and how often it moves.
    • 

  • Ping-pong access (CPU and GPU taking turns on the same data) multiplies transfers; only a change of algorithm fixes it.
    • 

  • Demand paging on the CPU, measured in this build, shows the same structure: one fault per first-touched page, none afterwards, and populate-in-advance moving the cost rather than removing it.
    •

Forensic lab answer key


Observation. In Nadia's sanitizer build (R2), pass 1 shows 8,192 or 8,193 faults more than the 65,536 pages, and pass 3 shows 8,192 faults on populated memory. In the clean build (R4), pass 1 shows the page count plus at most a couple, and pass 3 shows 0. (Check the exact numbers in your copy of the outputs; the build copies the latest run.)


Hypotheses. (a) MAP_POPULATE is ignored in containers; (b) transparent huge pages change the count; (c) the instrumentation's own memory faults are counted in the same process; (d) a helper thread touches memory. (a) is ruled out by R4: same container, same source, pass 3 has 0 faults. (b) would reduce, not increase, the count, and the program asks for ordinary pages. (d) does not fit an exact multiple.


Evidence-based conclusion. The extra count is 8,192 pages × 4096 bytes = 32 MiB = 256 MiB / 8. AddressSanitizer keeps shadow memory that records the state of the application's memory at a ratio of one shadow byte per eight application bytes (D6, pending verification); writing to 256 MiB of new memory makes the tool touch 32 MiB of new shadow memory, which faults page by page in the same process. Populating b populated the application pages, not their shadow, so pass 3 still faults on the shadow. The comparison run is the proof; the shadow ratio explains the exact number.


Is Nadia right? No. MAP_POPULATE worked: the clean build shows the faults moved into the mmap call and none in pass 3.


Fix and prevention. Measure performance in a build without instrumentation, and keep sanitizer builds for correctness. State in every measurement which build it came from. On the GPU the same rule applies: tools that instrument kernels (Compute Sanitizer, a profiler's kernel replay, F6-33) change what they measure; never take timing from a sanitizer run. How the evidence was produced: both runs are real, in this build, of the same unmodified source; the only difference is the compiler flags, recorded in the two logs. Nothing was injected.
