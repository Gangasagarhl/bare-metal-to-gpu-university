Story hook

Every evening the great kitchen hall serves the same tasting menu: one hundred small courses, each a tiny step that takes the cooks only a moment. Amara, the head chef, has been writing one order slip per course and carrying it to the pass herself. Writing a slip takes her longer than the cooks need to cook the course. So the cooks finish, look up, and wait for the next slip. The hall is quick; the head chef is the bottleneck.

Joseph, who runs the pass, has an idea. "Write the whole menu once, on one laminated card. Draw arrows where a course must wait for another. Hand me the card, and every evening you only say serve the card." The first evening costs Amara some extra time to prepare the card. After that, one word starts all hundred courses, and the cooks go from one to the next without waiting for her.

Two weeks later a guest asks for less salt, and nothing changes: the card still says "two pinches". Joseph shrugs. "The card is laminated. If you want something different, you have to update the card."

In CUDA, the laminated card is a graph, preparing it is instantiation, "serve the card" is a graph launch, and the guest's salt is the lesson of this chapter's forensic lab.

What you will be able to do

  • Explain what a CUDA graph is (nodes, dependency edges, the graph and its executable form) and why replaying an executable graph can cost less host time than issuing the same operations one by one.
  • Write a graph by stream capture, including a fork and a join across two streams, instantiate it once, launch it many times, and check every call.
  • Predict with the course's launch model when a graph helps (many short kernels, host-bound issue) and when it hardly helps (long kernels), before measuring.
  • Measure the per-launch saving of a 100-kernel sequence as curriculum milestone E8 asks, and state what the measured interval contains.
  • Diagnose a graph that keeps using stale argument values, and fix it with an executable-graph update or with arguments read through device memory.
Jargon box
CUDA graph
Simple words: a recorded plan of GPU work, with arrows that say what must wait for what. Analogy: the laminated menu card with arrows between courses. Precise: an object of type cudaGraph_t made of nodes (kernel launches, copies, memsets, event operations, host functions, child graphs) and dependency edges; it describes work but does not run it. D1 H1
Node and edge (graph)
Simple words: a node is one job; an edge is a "wait for" arrow between two jobs. Analogy: one course on the card; an arrow from the sauce to the dessert. Precise: a node is created with a call such as cudaGraphAddKernelNode (with a list of dependencies) or by stream capture; an edge from node A to node B means B may start only after A completes. H1 Not the edges of a road map in MA102, although the mathematics (a directed acyclic graph) is the same.
Executable graph (instantiation)
Simple words: the ready-to-run version of a graph, checked and prepared once. Analogy: the card after Joseph has laminated it. Precise: a cudaGraphExec_t made by cudaGraphInstantiate, which validates "any structural constraints or intra-node constraints which were not previously validated"; it is launched with cudaGraphLaunch and destroyed with cudaGraphExecDestroy. H1
Stream capture
Simple words: recording the jobs you put into a stream instead of running them. Analogy: Joseph copies each slip onto the card instead of sending it to the cooks. Precise: between cudaStreamBeginCapture(s, mode) and cudaStreamEndCapture(s, &graph), "all operations pushed into the stream will not be executed, but will instead be captured into a graph". H1
Graph launch
Simple words: one call that starts all the jobs of an executable graph. Analogy: "serve the card". Precise: cudaGraphLaunch(exec, stream) executes the graph in a stream; "each launch is ordered behind both any previous work in stream and any previous launches of graphExec", and only one instance of an executable graph may execute at a time. H1
Launch overhead
Simple words: the time spent starting a kernel, not running it. Analogy: the time Amara spends writing and carrying a slip. Precise: the host time of a launch call plus any gap on the GPU between the end of one kernel and the start of the next; this course's launch model (Listing 3) treats both as parameters, because no values could be measured in this build (AH-23).
Executable-graph update
Simple words: changing the values inside a prepared graph without preparing it again. Analogy: updating the card's salt line without writing a new card. Precise: cudaGraphExecKernelNodeSetParams changes one kernel node's parameters for future launches; cudaGraphExecUpdate copies the node parameters of a "topologically identical graph" into the executable graph, or fails with a reason. H1

Layer 1 — the kid explanation

Starting a GPU job costs a little time on the CPU. For a big job, nobody notices. For a tiny job, starting it can take longer than doing it. Then the GPU spends its evening waiting for the CPU.

A CUDA graph is a recorded plan. You write down all the jobs once, with arrows for "this one waits for that one". The computer checks the plan and prepares it. After that, one short call starts the whole plan.

The easiest way to write the plan is to record it. You tell a stream "record, don't run". Then you issue your jobs as usual. When you stop recording, you get the plan.

A recorded plan remembers the numbers you gave it. If a number must change every time, you have to update the plan, or let the jobs read the number from GPU memory.

Layer 2 — the student explanation

Three steps: define, instantiate, launch

Analogy first: write the card, laminate it, serve it many times. The CUDA Programming Guide describes work submission with graphs as three separate stages: definition, where the program creates the description of the operations and their dependencies; instantiation, which validates the graph and does much of the setup work once; and execution, where the executable graph is launched into a stream as often as needed. Stream capture is the easy road


Capture lets you reuse code you already have. In Listing 1, the function issueSequence launches 100 kernels into a stream. Called normally, it runs them. Called between cudaStreamBeginCapture and cudaStreamEndCapture, the same function records 100 kernel nodes, each depending on the previous one because in-stream order becomes a chain of edges. D1 H1 Nothing runs during capture: if your code reads a result back between two captured kernels, the result is not there.


The mode argument decides which other API calls are allowed while a capture is in progress. The header explains why such a rule is needed: some calls, such as cudaMalloc, are "not enqueued asynchronously to a stream" and are "not observed by stream capture", so a captured sequence that depended on them would be invalid when replayed. With cudaStreamCaptureModeGlobal, the default, a thread is "prohibited from potentially unsafe API calls" while it, or any other thread in global mode, is capturing; cudaStreamCaptureModeThreadLocal only looks at the thread's own capture; cudaStreamCaptureModeRelaxed lifts the prohibition. H1 Use global mode unless you know why not. Allocate everything before capturing.


Forks and joins: events become edges


Capture can follow work into other streams. In Listing 2, the main stream records forkEv; the side stream waits on it, and from that moment the side stream is part of the same capture. Work issued to both streams is recorded; the event wait at the end (joinEv) brings the side branch back. The result is the graph of Figure 2: two kernels with no dependency between them, and a sum that depends on both. D1 If the side stream is not joined back, the header's error list has the name for it: cudaErrorStreamCaptureUnjoined. Other capture errors are just as specific: cudaErrorStreamCaptureImplicit ("a disallowed implicit dependency on a current capture sequence from cudaStreamLegacy"), cudaErrorStreamCaptureIsolation, cudaErrorStreamCaptureInvalidated. H2 The legacy default stream of F6-28 causes trouble here too: the header says that while a blocking stream is capturing, "the legacy stream is in an unusable state until the blocking stream capture is terminated". H1 One more reason for non-blocking streams.


What a graph remembers


A graph records the work as it was issued. For a node added by hand, the header states that the kernel's argument values are copied when the node is created. H1 A pointer argument is an address, so the graph will read whatever is stored at that address when it runs; a value argument such as a float gain is frozen. That difference is the whole story of the forensic lab.

Layer 3 — the engineer's depth


One analogy sentence: the card saves Amara's writing time, not the cooks' cooking time, so the card pays off only when the writing was the slow part.


When does a graph pay off? A model


Listing 3 models one sequence of K kernels, each taking k µs on the GPU. Issued one by one, the host needs h µs per launch call, and the GPU needs a gap of g µs between one kernel's end and the next one's start. Issued as a graph, the host needs G µs once, and the GPU needs a gap of g′ between nodes. All five numbers are inputs; this build measured none of them. With individual launches, kernel i starts at max((i + 1)·h, end of kernel i − 1 + g). For large K the total tends to K · max(h, k + g): either the host is the bottleneck or the GPU is. With a graph, the total is G + K·k + (K − 1)·g′.


Two conclusions follow from the algebra, whatever the real values are. First, the saving per kernel is bounded by max(h, k + g) − (k + g′): when kernels are long, k dominates both terms and the relative gain goes to zero. Second, when the host is the bottleneck (h > k + g), the graph removes the host term from the critical path entirely, which is the largest gain the model can show. The real output (Worked example) shows both. R3


The cost of instantiation, and amortisation


Instantiation does validation and setup once (H1, D1); it is not free. A graph launched once has paid for instantiation and saved nothing, as the model's short-1 line shows with its invented numbers (a speed-up below 1). The engineering rule: build and instantiate the graph outside the loop, launch it inside the loop, and measure the break-even count on your machine. Milestone E8 asks for exactly the per-launch saving: "Graph version of a 100-kernel sequence reduces total time versus individual launches; the measured per-launch saving is logged." C1 Listing 1 logs that number on a GPU; it excludes instantiation from the timed interval and says so.


Changing a graph without rebuilding it


Real programs rarely replay exactly the same work: a frame number, a pointer to the next buffer or a gain changes every time. There are three honest options, from cheapest to most general:


    

  1. Indirection. Pass a pointer to device memory and update the value there with an ordinary copy before each launch. The graph never changes; the kernel reads the current value. (Version 3 of the forensic model.)
    2. 

  2. Set one node's parameters. cudaGraphExecKernelNodeSetParams changes a kernel node in the executable graph; "the modifications only affect future launches", and "already enqueued or running launches … are not affected". You need the node handle, which you get from a graph you built by hand, or by querying the captured graph's nodes. H1
    3. 

  3. Capture again, then update. Capture the new work into a new graph and call cudaGraphExecUpdate(exec, newGraph, &info). It succeeds when the new graph is "topologically identical" and the changes are within its documented limits; otherwise it returns cudaErrorGraphExecUpdateFailure and info.result names the reason, for example cudaGraphExecUpdateErrorTopologyChanged. The header adds: "The API may add further restrictions in future releases. The return code should always be checked." H1 Listing 4 does this and falls back to a fresh instantiation.
    4.

The header documents graph instantiation flags for graphs with memory allocation nodes (cudaGraphInstantiateFlagAutoFreeOnLaunch), for graphs launched from the device (cudaGraphInstantiateFlagDeviceLaunch) and for per-node priorities (cudaGraphInstantiateFlagUseNodePriority), and a call cudaGraphUpload that uploads an executable graph "to the device in hStream without executing it". H1 cudaGraphDebugDotPrint writes "a DOT formatted description of the graph" (Listing 2 uses it). H1 Device-side launch, conditional nodes and memory nodes are beyond this course; read the Programming Guide's graphs section (D1) for the toolkit you use before using them. HIP offers graphs with hip names (HP301); check the HIP API reference before assuming any one-to-one mapping.



How the hardware actually does it


A kernel launch is a message from the host to the GPU: the driver writes a command describing the kernel, its launch configuration and its argument values into memory that the GPU reads, and tells the GPU there is new work, in the way a host hands work to any device that reads its commands from memory (F1-44). D3 The host side of that (checking arguments, building the command, writing it) is what a graph launch can do once for many nodes instead of once per kernel; that is the gain the Programming Guide attributes to graphs, by moving work from launch time to instantiation time. D1 On the GPU side, a kernel still occupies the streaming multiprocessors in exactly the same way; a graph does not make any kernel itself faster.

Worked example


Use the launch model with invented parameters: host time per launch call h = 4 µs, GPU gap between individually launched kernels g = 2 µs, one graph launch G = 6 µs, gap between graph nodes g′ = 1 µs. These are teaching numbers, not properties of any GPU.


    

  1. 100 kernels of 3 µs, individually. The GPU needs k + g = 5 µs per kernel, the host 4 µs per launch, so the GPU is the bottleneck after the first kernel. Kernel 0 starts when the first launch call is done, at 4, and ends at 7. Each further kernel adds 5: 7 + 99 × 5 = 502 µs.
    2. 

  2. The same as a graph. First node starts at G = 6, ends at 9; each further node adds g′ + k = 4: 9 + 99 × 4 = 405 µs. Speed-up 502 / 405 ≈ 1.24; saving per kernel (502 − 405) / 100 = 0.97 µs.
    3. 

  3. One kernel. Individually: 4 + 3 = 7 µs. As a graph: 6 + 3 = 9 µs. The graph is slower (0.78×) because nothing is amortised.
    4. 

  4. 100 kernels of 500 µs. Both totals are about 50 ms; the saving is still about 1 µs per kernel, but the speed-up is 1.00×: invisible.
    5. 

  5. Host-bound: h = 8 µs. Individually the host is the bottleneck: kernel 99 ends at 100 × 8 + 3 = 803 µs. The graph does not depend on h: 405 µs again. Speed-up 1.98×, saving 3.98 µs per kernel.
    6.

Where the analogy breaks


    

  • The card does not make the cooking faster. A graph removes launch work; each kernel's own time is unchanged. If the kernels are the slow part, the card helps nothing (Worked example step 4).
    • 

  • A laminated card is truly fixed; a graph is fixed only in what it copied. Value arguments are frozen at definition, but pointer arguments are addresses: the graph reads whatever memory holds when it runs. The "salt" can change through a pointer without any update (version 3 of the forensic model).
    • 

  • Only one card can be served at a time. In the kitchen, two copies of a card can be served in parallel by two teams. An executable graph cannot execute twice at the same time; a second launch waits behind the first. To run two at once, instantiate twice (H1).
    • 

  • Joseph reads the card; there is no Joseph on the GPU. The analogy suggests a person walking the card. The real mechanism of graph execution is not documented in the sources read for this chapter (unverified box above).
    •

Summary


    

  • A CUDA graph describes work as nodes and dependency edges; it is defined, instantiated once and launched many times.
    • 

  • Stream capture records the operations issued to a stream (and to streams that join it through events) without running them; it must end on the stream where it began, and forked streams must be joined back.
    • 

  • A graph saves launch work, not kernel time: it helps most when kernels are short or the host is the bottleneck, and can lose when launched only once.
    • 

  • Instantiation has a cost; keep it out of loops and measure it separately.
    • 

  • Value arguments are frozen in a graph; pointer arguments are read at run time. Change values with cudaGraphExecKernelNodeSetParams, cudaGraphExecUpdate (always check its result), or indirection through device memory.
    • 

  • Milestone E8 asks for the measured per-launch saving of a 100-kernel sequence; plan it with the model, measure it on a GPU, log it with the machine and versions.
    •

Forensic lab answer key


Observation. In version 1 (R6) the node gain is 1.0 in every frame while the host gain is 1.0, 2.0, 4.0, 0.5; the pixel is always 10.0. Frame 0 is correct by coincidence (the gain at capture time was 1.0); frames 1–3 are wrong.


Hypotheses. (a) The gain never reaches the GPU because the value was frozen when the graph was recorded; (b) the result is not copied back; (c) the operator interface does not pass the gain; (d) the kernel ignores the gain. The host log rules out (c). Frame 0 is correct and every frame has a fresh result of 10.0, which rules out (b) and (d) (the kernel computes, with gain 1.0). The node's stored gain of 1.0 against the host's changing value proves (a).


Evidence-based conclusion. The graph was defined once with gain passed by value; a recorded kernel node holds a copy of its argument values (H1 for hand-built nodes; the unverified box for capture), so every launch reuses 1.0. Kenji's change of the host variable cannot reach a node that holds its own copy.


The two fixes. Version 2 models cudaGraphExecKernelNodeSetParams or capture-and-cudaGraphExecUpdate (Listing 4): one update call per frame, cheaper than instantiating again when the update succeeds. Version 3 models indirection: the kernel reads the gain through a pointer to device memory, and the host copies the new gain there before each launch (one small copy per frame, which can itself be part of the graph as a copy node from a pinned slot). Both give correct pixels in R6.


Fix, verification, prevention. Ship version 3 if the gain is the only thing that changes (the graph never changes), or Listing 4's update if several values change. Verify on a GPU with a test that sets four different gains and checks four different pixel values (Listing 4's output), under Compute Sanitizer. Prevent: a code-review rule that every argument of a captured kernel is listed as "fixed" or "changes per launch", and a test that changes every "per launch" argument. How the evidence was produced: a real run in this build of a host-only model; no fault was injected beyond writing Kenji's version as described; the model's node behaviour follows the header's statement for kernel nodes, and its application to capture is the chapter's unverified assumption.
