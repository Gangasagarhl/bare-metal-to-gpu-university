Story hook

The great kitchen hall has to turn two hundred crates of vegetables into soup. The first plan is simple: the porters carry all two hundred crates in, the cooks chop and boil everything, then the porters carry all the pots out. The porters wait while the cooks cook, and the cooks wait while the porters carry. Most of the evening, half the hall stands still.

Mei Ling, the shift leader, splits the job into batches of twenty-five crates. While the cooks work on batch one, the porters bring in batch two; while the cooks work on batch two, another porter carries batch one's pots out. After the first batch, everybody is busy at the same time.

There is one catch. The porters may only take crates from the loading dock, where crates stay put. The crates in the big storeroom get moved around all evening by the storeroom staff, so before a porter can take one, somebody has to carry it to the dock first, and while that happens the porter just waits. Mei Ling's batches only flow if the crates are on the dock to begin with.

In CUDA, the batches are chunks, the porters are copy engines, the loading dock is pinned memory, and the storeroom is ordinary pageable memory. This chapter plans, builds and checks Mei Ling's pipeline.

What you will be able to do

  • Derive the time of a chunked copy-in / compute / copy-out pipeline from the three stage times and the number of chunks, and say when the formula stops being true.
  • Plan a pipeline with the course's model: chunk count, number of copy engines, fixed cost per copy and the order in which the host issues work.
  • Explain, from the runtime's own documentation, why overlapping copies need page-locked host memory, and what pinning costs.
  • Write a chunked pipeline over several streams that is correct by construction (checked bit for bit against a one-stream run) and that measures its own prediction error (milestone E8).
  • Diagnose a pipeline that misses its plan because the machine has one copy engine and the work is issued depth-first.
Jargon box
Pageable memory
Simple words: ordinary memory from new, malloc or std::vector, which the operating system may move or swap. Analogy: crates in the storeroom, which the storeroom staff rearrange. Precise: host memory whose pages the operating system may relocate or page out (F1-38); for copies from it the CUDA driver first copies the data into "staging memory for DMA transfer". H1
Pinned (page-locked) memory
Simple words: host memory the operating system promises not to move, so the GPU can read it directly. Analogy: crates on the loading dock. Precise: host memory allocated with cudaMallocHost or cudaHostAlloc, or registered with cudaHostRegister, that is "page-locked and accessible to the device" and "can be read or written with much higher bandwidth than pageable memory". H1 Already defined in F1-62; this chapter adds its role in overlap.
Chunk (pipeline chunk)
Simple words: one piece of a big job, copied and processed on its own. Analogy: one batch of twenty-five crates. Precise: a contiguous slice of the input whose copy in, kernel and copy out form one in-order sequence in one stream, so that different slices can be in different stages at the same time.
Software pipeline (copy–compute pipeline)
Simple words: doing different steps for different pieces at the same time. Analogy: porters carrying batch two in while cooks cook batch one and another porter carries batch zero out. Precise: a schedule in which chunk k+1's copy in, chunk k's kernel and chunk k−1's copy out run concurrently on different engines; with C equal chunks its time is about serial / C + (C − 1) / C × (slowest stage), plus per-chunk costs (this chapter's derivation).
Issue order (depth-first, breadth-first)
Simple words: the order in which the CPU hands the GPU its jobs. Analogy: pinning all of batch one's slips, then batch two's (depth-first), or all "carry in" slips first, then all "cook" slips (breadth-first). Precise: depth-first issues copy in, kernel, copy out per chunk; breadth-first issues all copies in, then all kernels, then all copies out. Results are the same; on hardware whose engines take work in issue order, the timelines can differ (Listing 2's model).
Overlap efficiency
Simple words: how close the real pipeline came to the plan. Analogy: the evening's actual finish time against the shift plan. Precise: measured pipeline time divided by predicted time, the quantity milestone E8 bounds ("within 20 %"). C1

The idea in pictures

Figure 1 shows Mei Ling's plan as a timeline: one job split into four chunks, three engines (copy in, compute, copy out). The first chunk's copy in and the last chunk's copy out overlap with nothing; in between, all three engines are busy. That shape gives the formula of the Worked example.

Figure 2 is the reason for the loading dock. A copy engine reads host memory by direct memory access; from pageable memory the driver must first copy the data into a pinned staging buffer, and only then can the engine move it.

Layer 1 — the kid explanation

A big job has three steps: carry in, cook, carry out. If you do all of one step before the next, two kinds of workers always wait. Cut the job into pieces. Then, while piece two is carried in, piece one is cooked. While piece two is cooked, piece one is carried out. After a short start, every worker is busy.

How long does it take? The first piece has to go through all three steps. After that, one piece comes out every time the slowest step finishes a piece. More pieces make the start shorter. But every piece also has a small fixed cost, like a porter walking to the dock. Too many tiny pieces and those walks add up.

The carriers can only take data that stays put. Normal memory may be moved around by the operating system. So the computer first copies it to a safe place, and the carriers wait. Memory that is "pinned" never moves. The carriers can take from it straight away.

Layer 2 — the student explanation

The pipeline in code

The analogy first: one batch, one spike; batches on different spikes. In code, chunk c goes to stream c % nStreams, and in that stream it is copied in with cudaMemcpyAsync, processed by a kernel, and copied out with cudaMemcpyAsync. Within the chunk the stream orders the three steps; across chunks the streams allow overlap (F6-28). D1 H1 Each chunk uses its own slice of the device buffers, so no two streams write the same bytes: the pipeline is race-free by construction, and Listing 1 checks it bit for bit against a one-stream run.

Why the host memory must be pinned

The installed CUDA 12.0 header contains a section titled "API synchronization behavior". For the synchronous cudaMemcpy it says: "For transfers from pageable host memory to device memory, a stream sync is performed before the copy is initiated. The function will return once the pageable buffer has been copied to the staging memory for DMA transfer to device memory, but the DMA to final destination may not have completed." And: "For transfers from device to either pageable or pinned host memory, the function returns only once the copy has completed." H1

For the asynchronous forms (the "Async" suffix, which the header itself calls "a misnomer as each function may exhibit synchronous or asynchronous behavior depending on the arguments") it lists: "For transfers from device memory to pageable host memory, the function will return only once the copy has completed", and "for all other transfers, the function is fully asynchronous. If pageable memory must first be staged to pinned memory, this will be handled asynchronously with a worker thread." H1

Three consequences follow, each from those sentences:

  1. A device-to-host cudaMemcpyAsync into pageable memory blocks the host thread until the copy is done. While it is blocked, the host cannot issue the next chunk's work into any stream. A pipeline whose results go to a std::vector therefore issues one chunk at a time; F6-32's forensic lab shows the resulting timeline.
  2. Pageable data passes through a staging copy made by the CPU (or a driver worker thread) before the DMA. That costs CPU time and memory bandwidth, and it is a step the copy engine waits for.
  3. Pinned memory is what the copy engine reads directly. The header says pinned memory "can be read or written with much higher bandwidth than pageable memory obtained with functions such as malloc()". H1 The Programming Guide makes page-locked host memory a condition for overlapping copies with kernel execution. D1

Measure the bandwidth difference on your machine: F6-09's lab prints the pinned/pageable ratio. No number for it is given here (AH-22).

Predicting the time

Let a, k and b be the times of copy in, kernel and copy out for the whole array, measured alone. Split into C equal chunks, each stage of each chunk takes a third of that per chunk: a/C, k/C, b/C. With an engine per stage (two copy engines and the compute engine), the first chunk needs (a + k + b)/C to pass through all three stages, and after it one chunk finishes every max(a, k, b)/C. So

T(C) = (a + k + b) / C + (C − 1) / C × max(a, k, b).

As C grows, T approaches max(a, k, b): the pipeline can never beat its slowest stage. This is the classic pipeline argument of F1-24 (stages and throughput), applied to copies; it is arithmetic, and Listing 2 checks it against a simulation. The formula ignores two things that the model adds: a fixed cost per copy (the α of F1-62's α–β model) and the number of copy engines.

Layer 3 — the engineer's depth

One analogy sentence: a good shift plan counts the porters, the walk to the dock for every batch, and the order in which slips are pinned, not only the cooking time.

How many chunks

Each copy has a fixed cost (TG-1, the course's invented teaching GPU: 10 µs per copy, F1-62) besides its size-proportional part. With C chunks there are 2C copies, so the fixed part grows linearly with C while the fill time shrinks as 1/C. The model output in the Worked example shows the consequence on TG-1: the speed-up rises from 1.00× (1 chunk) to its best value around 16–64 chunks and then falls, below 1× at 1024 chunks. The real optimum on your GPU depends on its fixed costs, which you measure (F6-09 measures copy time against size). A kernel launch per chunk also costs time; F6-30 discusses how graphs reduce it.

Copy engines and issue order

The header defines asyncEngineCount = 1 as "can concurrently copy memory between host and device while executing a kernel" and 2 as "can concurrently copy memory between host and device in both directions and execute a kernel at the same time". H1 With one engine, copies in and copies out share it, and the best possible time is bounded by a + b instead of max(a, k, b). The model also shows a second effect: if that engine takes copies in the order the host issued them, a depth-first issue order puts chunk 0's copy out (which must wait for chunk 0's kernel) in front of chunk 1's copy in, and the engine idles. Issuing breadth-first avoids that. Whether a given GPU behaves like the model's in-order engine is not documented in the sources read for this build; the forensic lab treats it as a hypothesis to test on your hardware.

Not verified — check before relying on this

The claim that issue order (depth-first versus breadth-first) changes the achieved overlap on GPUs with one copy engine comes from this course's model and from NVIDIA material on overlapping transfers that was not opened in this build (CUDA C++ Best Practices Guide, D2; NVIDIA technical blog articles on overlapping data transfers, tier 5). Whether and how it applies to your GPU generation must be checked in those documents for your toolkit version and confirmed with an Nsight Systems timeline (F6-32).

Reusing pinned staging buffers safely

Because pinning is costly, real pipelines copy data from pageable application memory into a small ring of pinned staging buffers and stream from those. The hazard: the host must not refill staging buffer j while the asynchronous copy that last read it is still running, because cudaMemcpyAsync "may return before the copy is complete". H1 Record an event after each copy that reads a staging buffer and call cudaEventSynchronize on it before the host writes into that buffer again. The same rule applies on the way out: the host may read a pinned result buffer only after the event recorded after its copy out has completed. These are host–device races; Compute Sanitizer cannot see host writes, so they must be prevented by design.

Zero-copy, briefly

cudaHostAllocMapped maps pinned host memory into the device's address space; a kernel can then read host memory directly through the pointer from cudaHostGetDevicePointer, without an explicit copy. H1 Every access then crosses the link, so this suits data that is touched once and sparsely; for the streaming pipeline of this chapter, explicit chunked copies keep the kernel reading device memory at device bandwidth. Unified memory (F6-31) is a third option with its own costs.

How the hardware actually does it

The copy engines are DMA engines on the GPU: they issue memory read or write transactions over PCIe (or another link) to host physical addresses, without the CPU moving the bytes (F1-44, F1-45). D4 A DMA engine works with physical pages; if the operating system could move or page out a page during the transfer, the engine would read the wrong memory. Page-locking removes that possibility, which is why a direct DMA needs pinned memory and why pageable data is first staged into a pinned buffer by the driver (H1). H1 On the device side the kernels run on the SMs and read device memory at device bandwidth (F1-59), so a well-overlapped pipeline is limited by whichever is slower: the link or the kernel. The link's speed comes from the PCIe generation and width of your slot and is measured in F6-09; this chapter quotes none.

Worked example

TG-1 (invented, glossary): host link 16 GB/s with 10 µs fixed cost per copy, two copy engines. The job copies 64 MiB in and 64 MiB out; the kernel takes 4.0 ms on the whole array (an invented value chosen to make the stages nearly equal).

  1. Stage times. 64 MiB = 64 × 1,048,576 = 67,108,864 bytes. At 16 × 109 bytes/s that is 67,108,864 / 16,000,000,000 s = 4.194 ms, plus 0.010 ms fixed: a = b = 4.204 ms. Serial: 4.204 + 4.000 + 4.204 = 12.409 ms (rounded).
  2. Formula for C = 8. 12.409 / 8 + 7/8 × 4.204 = 1.551 + 3.679 = 5.230 ms.
  3. Model for C = 8. Each of the 16 copies now carries its own 10 µs, and the first chunk's three stages cannot overlap: 5.309 ms, speed-up 12.409 / 5.309 = 2.34×. The formula was 1.5 % optimistic.
  4. Too many chunks. At C = 1024, each copy moves only 64 KiB, about 4.1 µs of transfer, and still pays 10 µs fixed: the model gives 14.452 ms, slower than serial.
  5. Kernel-bound job. With a 20 ms kernel, the best the pipeline can do is approach 20 ms: 1.41× at 64 chunks. Overlap hides copies; it cannot shorten the kernel.

Where the analogy breaks


    

  • The storeroom is not slower to walk to; it is unsafe to grab from. Pageable memory is the same DRAM as pinned memory. The difference is that its virtual-to-physical mapping may change, so a DMA engine cannot be pointed at it; the cost is the extra staging copy and the host blocking, not distance (H1, F1-38).
    • 

  • A bigger loading dock is not free. Pinning takes physical memory away from the operating system's paging, and the header warns it "may degrade system performance". The analogy's dock costs nothing; real pinned memory does (H1).
    • 

  • Porters are not interchangeable. With asyncEngineCount = 2 the two copy engines serve different directions in the model; you cannot use both for copies in (H1 defines the property only in terms of directions).
    • 

  • Batches do not cost the same as crates. In the story, smaller batches only help; real chunks each pay a fixed cost per copy and per launch, so there is an optimum chunk count (Worked example, step 4).
    •

Summary


    

  • A chunked pipeline overlaps chunk k+1's copy in, chunk k's kernel and chunk k−1's copy out; with C equal chunks its time is about serial/C + (C−1)/C × slowest stage.
    • 

  • The pipeline cannot beat its slowest stage; fixed per-copy and per-launch costs make too many chunks slower.

  • Overlap needs pinned host memory: copies from pageable memory are staged by the driver, and a device-to-host copy into pageable memory blocks the host (installed header).

Forensic lab answer key


Observation. At 8 chunks the formula column is the same, 5.230 ms, for all three configurations: it knows nothing about engines or issue order. The model gives 5.309 ms (plan, two engines), 12.549 ms (one engine, depth-first: speed-up 0.99×) and 8.549 ms (one engine, breadth-first: 1.45×) (R3).


Hypotheses. Pageable memory; one copy engine; fixed costs from too many chunks; a kernel much longer than planned; a default-stream operation (F6-28). Jonas's code uses pinned memory, 8 chunks are few, and his stage times match the plan, which leaves the engine count, supported by the device report.


Evidence-based conclusion. With asyncEngineCount = 1 the device can copy in only one direction while a kernel runs (H1): copies in and copies out share one engine. In depth-first order, chunk 0's copy out is queued on that engine before chunk 1's copy in; in the model's in-order engine, chunk 1 cannot be copied in until chunk 0's kernel and copy out are done, so the pipeline degenerates to serial (12.549 ms against 12.409 ms serial: slightly worse, because of the extra fixed costs). Breadth-first order lets all copies in go first, so the kernels overlap them: 8.549 ms.


Best possible on this machine. All bytes must cross the single engine: a + b = 4.204 + 4.204 = 8.408 ms, plus fixed costs. Breadth-first at 8 chunks (8.549 ms) is within 2 % of that bound. The plan's 2.34× was never possible.


Fix and prevention. Code: issue breadth-first (all copies in, then kernels, then copies out), or interleave so that no copy out sits in front of a needed copy in; verify with a timeline. Planning: read asyncEngineCount before planning and plan with the model for that engine count; add the device report to the plan file. Treat the issue-order effect as a hypothesis to confirm on the real GPU (unverified box in Layer 3). How the evidence was produced: real runs of Listing 2 on forensic.in in this build; the machine and its numbers are invented (TG-1-class), and the one-engine behaviour is the model's documented assumption.
