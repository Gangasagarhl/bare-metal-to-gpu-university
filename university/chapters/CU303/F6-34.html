Story hook

Every recipe card in the great kitchen hall is written twice. The head chef writes the first version in the hall's general recipe language: "stir until smooth, add the sauce". It works in any of the guild's kitchens. Before the evening starts, the kitchen's own steward rewrites the card for this particular hall: which shelf, which ladle, which of the hall's four stoves, and in what exact order the helpers' hands move.

Most cooks never read the steward's version. Ahmed does. When a dish is slow, he reads it line by line, and he finds things the head chef never wrote: a helper who puts a bowl down on the far shelf and walks back for it later, because her hands were full; a step that fetches one carrot at a time where a whole tray could have been carried.

"The general card says what we want," Ahmed says. "The steward's card says what we actually do."

The general recipe language is PTX, the steward is the assembler ptxas, the hall-specific card is SASS, and the bowl on the far shelf is a register spill. This chapter teaches you to read both cards.

What you will be able to do

  • Explain the path from CUDA C++ to PTX to SASS, what the executable carries, and why both levels exist.
  • Produce PTX and SASS for your own kernels with nvcc, cuobjdump and nvdisasm, including source-line annotations, without a GPU.
  • Read a kernel's SASS: find the index computation, the bounds check, global loads and their width, shared-memory accesses, barriers, FMAs, and local-memory spills.
  • Predict the effect of one source or build change from a SASS reading (milestone E10), and say how to confirm it in a profiler.
  • Diagnose a kernel that became slower after a build change by comparing two SASS listings and the compiler's resource reports.
Jargon box
PTX (Parallel Thread Execution)
Simple words: NVIDIA's portable GPU assembly language, one level below CUDA C++. Analogy: the recipe in the guild's general recipe language. Precise: a virtual instruction set with unlimited typed virtual registers (%r, %rd, %f, %p) and explicit state spaces (.param, .global, .shared, .local), specified by the "PTX ISA" document; nvcc emits it with -ptx. D1 R1 Already met in F1-57.
SASS
Simple words: the real machine code one GPU generation executes. Analogy: the steward's card for this hall. Precise: the native instruction set of an sm_XY architecture, produced from PTX by ptxas and shown by cuobjdump -sass or nvdisasm; its instructions use physical registers (R0…, predicates P0…, uniform registers UR…) and differ between architectures. D2 R2
Virtual and real architecture (compute_XY, sm_XY)
Simple words: the PTX level a program targets, and the actual GPU generation its machine code is for. Analogy: the edition of the general recipe language, and the hall the steward writes for. Precise: nvcc's help text, recorded in this build, says that --gpu-architecture=sm_50 "is equivalent to" --gpu-architecture=compute_50 --gpu-code=sm_50,compute_50: SASS for the real architecture plus PTX for the virtual one. R8
Fatbinary
Simple words: the bundle of GPU code images stored inside your executable. Analogy: a folder holding the general card and the steward's cards for several halls. Precise: the container nvcc embeds in the host executable with SASS (ELF cubin) images and PTX images; cuobjdump --list-elf --list-ptx lists them (R9). D2 Defined in CU201's glossary.
Predicate (guard)
Simple words: a true/false flag that decides whether an instruction does anything. Analogy: "only the helpers whose bowl is empty do this step". Precise: in PTX, a .pred register set by setp; in SASS, P0–P6 and the constant-true PT, written @P0 or @!P0 before an instruction (R2). D1
Register spill
Simple words: a value the compiler had to park in memory because the thread ran out of registers. Analogy: the bowl put down on the far shelf and fetched back later. Precise: a store to and load from per-thread local memory (SASS STL/LDL), reported by ptxas -v as "spill stores" and "spill loads" in bytes; local memory is private in scope but resides in device memory (F1-58). D3 R10
Line information (-lineinfo)
Simple words: notes in the binary that say which source line each machine instruction came from. Analogy: the steward writing the head chef's line number next to each of his steps. Precise: nvcc's -lineinfo keeps source-line correlation in the cubin; nvdisasm -g prints it as //## File "...", line N comments (R3), and profilers use it to attribute metrics to source lines. D2

Layer 1 — the kid explanation

You write a kernel in C++. The GPU cannot run C++. The compiler translates it twice. First into PTX, a GPU language that works for many GPU generations. Then into SASS, the exact instructions for one generation.

You do not need a GPU to look at either one. The compiler and two small tools print them for you.

Reading SASS shows what really happens. You can count the loads and stores. You can see how many bytes each load fetches. You can see whether the compiler had to park values in slow memory because it ran out of registers.

Then you can make a prediction: "if I change this line, these three instructions will disappear". You make the change, read the SASS again, and measure. That is how engineers find speed without guessing.

Producing the listings

Analogy first: ask the steward for both cards. Every listing in this chapter was produced in this build with three commands, recorded in run.sh and its logs:

Reading PTX


PTX is typed, in SSA-like style with fresh virtual registers, and names its memory state space in every load and store. The real PTX of the two axpy kernels, filtered to the instructions that do the work (R1):




Line by line: ld.param reads the four kernel parameters; %ctaid.x, %ntid.x and %tid.x are blockIdx.x, blockDim.x and threadIdx.x, combined by mad.lo.s32 into i; setp.ge.s32 sets the predicate for the bounds check; cvta.to.global converts the generic pointers to global addresses; mul.wide.s32 … 4 computes the byte offset; then two loads, one fma.rn.f32 (round-to-nearest fused multiply-add) and one store. D1 The only difference between the two kernels is one load: ld.global.f32 for plain x, ld.global.nc.f32 when x is const __restrict__. The PTX ISA defines .nc as a load through the non-coherent (read-only) path, allowed only when the data is read-only during the kernel, which is what __restrict__ lets the compiler assume. D1 D3

A build flag in the SASS: contraction


By default nvcc contracts a * x + y into one fused multiply-add. Built with --fmad=false, the same line becomes FMUL then FADD (R6):




That is one more instruction and, numerically, two roundings instead of one: results can differ in the last bit (MA302; CU201's glossary entry "Contraction (FMA contraction)"). The SASS is the place to check which you got; the source cannot tell you.

What SASS does not promise


SASS is generated for one architecture by one version of ptxas. A new toolkit can reorder, combine or replace instructions; a new architecture has another instruction set. The PTX ISA is the stable contract between versions; SASS is evidence about one build. D1 D2 Record the toolkit version and the architecture next to every SASS listing you keep, as this chapter's run logs do.



How the hardware actually does it


Each SASS instruction is issued for a whole warp (F1-57): an LDG.E asks for one 4-byte word per active lane, which the memory system combines into sector-sized transactions when the addresses are neighbours (F6-08); an LDG.E.128 asks for 16 bytes per lane, so a warp moves the same data with a quarter of the load instructions. D3 Registers are allocated per thread from the SM's register file; the more registers each thread uses, the fewer warps fit (F6-20), which is why a build may cap them, and why a cap that is too tight produces spills to local memory: per-thread memory that lives in device memory and is cached (F1-58). D3 A barrier (BAR.SYNC) makes every warp of the block wait until all have arrived, so its cost depends on the slowest warp. The .CONSTANT loads use the read-only path the PTX .nc qualifier names. D1

Where the analogy breaks


    

  • The steward rewrites once; ptxas may rewrite at run time. When the executable carries no SASS for the GPU it runs on, the driver compiles the PTX when the program loads (D3, unverified here). The "hall-specific card" can then come from a compiler you did not run yourself.
    • 

  • One card per hall, but one instruction per warp. The steward's card describes one helper's hands; a SASS instruction is executed by a whole warp at once, under a predicate mask. Reading SASS as one thread's program is right for meaning and wrong for cost.
    • 

  • The far shelf is not far. Local memory is cached (F1-58); a spill can cost little or a lot depending on cache behaviour. The analogy makes every spill sound slow; only measurement says how slow.
    • 

  • The general recipe language is not a recipe. PTX is closer to SASS than to C++: it already fixes the algorithm, the types and the memory spaces. Many optimisations happen in ptxas, so PTX alone does not show register use or spills.
    •

  5. Propose a fix, a prediction of what the SASS and the profiler will show after it, and a way to stop this from returning.
    6. 



Method hints. Diff the two resource reports first; then count local-memory instructions between the loop's start and its backward branch. A "compiler update" story is a hypothesis like any other: look for the evidence. Hypothesis → evidence → conclusion.

Summary


    

  • CUDA C++ becomes PTX (a virtual ISA with typed virtual registers and explicit state spaces) and then SASS (one architecture's machine code); an executable built with -arch=sm_XY carries SASS for sm_XY and PTX for compute_XY.
    • 

  • No GPU is needed to read either: nvcc -ptx, nvcc -cubin, cuobjdump -sass and nvdisasm -g (with -lineinfo) produce them.
    • 

  • Read SASS by lining it up with PTX and source; mark inferred meanings as inferred and check them in NVIDIA's instruction set reference.
    • 

  • The E10 signatures: LDG/STG and their width, LDS/STS, BAR.SYNC, FFMA (or FMUL+FADD without contraction), STL/LDL for spills.
    • 

  • Predict a change with a number, check it in the SASS first, then confirm it in a profiler and with a timed run.
    • 

  • Build settings change machine code: a register cap creates spills; --fmad=false splits FMAs and changes results in the last bit. Keep the toolkit and architecture with every listing.
    •

Limits: meanings of suffixes, special registers and constant-bank offsets are inferred, may be wrong, and change between architectures; ptxas may merge or split operations so that no one-to-one match exists. Inferred meanings must be checked in D2.

Three 4-byte LDG.E per thread at addresses 12 bytes apart: neighbouring threads' requests interleave, and no 64- or 128-bit load is possible because 12-byte elements are not 8- or 16-byte aligned. Changing to a structure of arrays (three arrays) gives coalesced 4-byte loads per array; padding to float4 allows LDG.E.128 at the cost of 4 extra bytes per element.

Forensic lab answer key


Observation. Before (R10): 31 registers, 0-byte stack frame, 0 spill bytes; opcodes 16 LDG.E.CONSTANT, 16 FMUL, 16 FFMA, 16 FADD, 1 STG.E, 4 BRA; the loop (from 0x240 to the backward branch at 0x5a0) contains 16 global loads and nothing else in memory. After (R11): a ptxas warning, 24 registers, a 24-byte stack frame, 68 bytes of spill stores and 48 bytes of spill loads; new opcodes 17 STL and 12 LDL.LU; inside the loop (0x220 to the backward branch at 0x680): 6 LDL.LU and 6 STL next to the 16 global loads. (Re-check the counts in your copy of the outputs; the build copies the latest run.)


Hypotheses. (a) A new compiler version schedules worse; (b) a register cap was added to the build; (c) the source changed; (d) a different target architecture. (c) is ruled out by the scenario and by identical FP and global-load counts. (d) is ruled out: both reports say sm_80. (a) and (b) both fit "after the update", which is why the scenario's own explanation must be tested.


Evidence-based conclusion. The first line of the "after" report names the cause: "ptxas warning : For profile sm_80 adjusting per thread register count of 16 to lower bound of 24". A per-thread register limit was requested by the build (-maxrregcount=16, recorded in forensic_after.log), ptxas raised it to the architecture's lower bound of 24, and with 24 registers instead of the 31 the kernel needs, it spills part of the 16 accumulators to local memory. The compiler is the same in both builds (same toolchain line in both logs): the "compiler update" was a build-configuration change.


Traffic estimate. Per loop iteration per thread: 16 global loads × 4 bytes = 64 bytes; 6 local loads + 6 local stores × 4 bytes = 48 bytes of local-memory traffic, 75 % on top of the useful traffic, plus 12 more memory instructions to issue. Whether the local traffic reaches DRAM depends on caching (unverified box), but the instructions are issued in any case.


Fix and prediction. Remove the cap for this kernel (or give it its own __launch_bounds__ that allows enough registers). Prediction: the SASS returns to R10: 0 spill bytes, no STL/LDL, 31 registers; on a GPU, the profiler shows no local-memory traffic and the kernel time returns to its earlier value, unless the lower occupancy from 31 registers costs more, which you would see as fewer active warps (F6-20). Prevention: keep -Xptxas -v output for every build in CI and fail the build when spill bytes of any kernel rise; avoid global register caps, prefer per-kernel launch bounds. How the evidence was produced: the same source compiled twice in this build with the same toolkit, the second time with -maxrregcount=16 (the injected fault); outputs filtered by run.sh as recorded in the logs. Wrong answers to avoid: "the new compiler is worse" (same compiler) and "more registers is always better" (occupancy can matter).
