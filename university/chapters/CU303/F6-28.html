Story hook

It is the busiest evening of the year in the great kitchen hall. At the pass, the counter where orders come in, Priya has been putting every order slip on one single spike. The rule of the spike is simple: the helpers take the slips from the bottom, one at a time, and a slip is started only when the one below it is completely finished, plated and carried out. Nobody ever gets confused. But the porters who carry crates in from the store stand idle while the cooks cook, and the cooks stand idle while the porters carry.

Tunde, the hall manager, puts up three more spikes. "Orders on the same spike still go in order," he says. "Orders on different spikes don't wait for each other. While table four's food is cooking, the porters can already bring in the crates for table seven." The hall gets faster at once.

Then one order needs another: the dessert for table seven may only start when table four's sauce is ready, because they share the pot. Tunde gives Priya a small brass token. "Drop this on spike one right after the sauce slip. Pin a note on spike two: wait until the token is reached." And one last warning: "There is also the old spike by the door. Anything you put on it makes every other spike stop and wait. Use it for nothing that should run alongside."

In CUDA, the spikes are streams, the token is an event, and the old spike by the door is the legacy default stream. This chapter is about all three.

What you will be able to do

  • Explain the ordering rules of CUDA streams: what is guaranteed inside one stream, what is allowed between streams, and what the legacy default stream does to both.
  • Write host code that creates non-blocking streams, issues copies and kernels into them, records events and makes one stream wait for another with cudaStreamWaitEvent, with every call checked.
  • Predict the timeline of a set of streams on a GPU with a given number of copy engines, using the course's timeline model, before running anything.
  • Measure elapsed time across two streams with events and state what the measured interval really contains.
  • Diagnose a program whose streams do not overlap because one launch went to the legacy default stream, from the timeline and the source, and fix it without introducing a race.
Jargon box
Stream (CUDA)
Simple words: a queue of GPU jobs that are done in the order you put them in. Analogy: one order spike at the pass. Precise: a sequence of operations (copies, kernels, event records, waits) that execute in issue order; operations in different streams may run concurrently. The runtime creates one with cudaStreamCreate or cudaStreamCreateWithFlags. D1 H1 Not a C++ I/O stream (std::ostream) and not the HD Audio stream of DR302.
Legacy default stream (stream 0, the NULL stream)
Simple words: the queue your work goes to when you name no stream. Analogy: the old spike by the door that makes every other spike wait. Precise: the per-context implicit stream used when no stream argument is given; nvcc's help text describes it as "per context, implicitly synchronizes with other streams", and nvcc uses it by default. R4 D1
Non-blocking stream
Simple words: a queue that never waits for the old default queue. Analogy: a spike that ignores the old spike by the door. Precise: a stream created with the flag cudaStreamNonBlocking, which the header documents as: work in it "may run concurrently with work in stream 0 (the NULL stream)" and the stream "should perform no implicit synchronization with stream 0". H1
Per-thread default stream
Simple words: each CPU thread gets its own ordinary default queue. Analogy: each waiter gets a private spike instead of sharing the old one. Precise: selected with nvcc's --default-stream per-thread; nvcc describes it as "a normal CUDA stream (per thread, does not implicitly synchronize with other streams)". R4 The handle cudaStreamPerThread names it explicitly. H1
Event (CUDA)
Simple words: a marker you drop into a queue to know when the queue gets that far. Analogy: the brass token dropped on a spike. Precise: an object that cudaEventRecord fills with "the contents of stream at the time of this call"; cudaEventQuery, cudaEventSynchronize and cudaStreamWaitEvent then examine or wait for completion of that captured work, and two completed events give an elapsed time. H1 Not the same as a probability event (MA202) or a Windows event object (OS304).
Cross-stream dependency
Simple words: a rule that one queue must wait for a point in another queue. Analogy: the note "wait until the token is reached" pinned on spike two. Precise: cudaStreamWaitEvent(stream, event, 0) "makes all future work submitted to stream wait for all work captured in event"; the wait is performed on the device when applicable, so the host does not block. H1
Asynchronous (with respect to the host)
Simple words: the call returns before the GPU has done the job. Analogy: Priya pins the slip and walks away; she does not stand and watch it cook. Precise: a call that may return before the operation completes, for example kernel launches and cudaMemcpyAsync in most directions; the header's section "API synchronization behavior" lists the exceptions. H1
Timeline
Simple words: a picture of what each worker did over time. Analogy: a wall chart with one row per station and a bar for every job. Precise: a time axis with one lane per execution resource (copy engine, compute, host thread) and one bar per operation; profilers such as Nsight Systems record them (F6-32), and this chapter's model computes them.

Layer 1 — the kid explanation

A GPU has more than one kind of worker. Some workers carry data in. Some carry data out. Many workers compute. If you put every job in one line, each kind of worker waits for the others. That wastes time.

A stream is a line of jobs. Jobs in the same line go in order. Jobs in different lines may happen at the same time. So you give each independent job its own line. Then the carriers can carry for one job while the cooks cook for another.

Sometimes a job in one line needs a result from another line. Then you drop a marker, an event, in the first line, and tell the second line to wait for it. Only that one point waits; everything else keeps moving.

Be careful with the oldest line, the default stream. Work you send without naming a line goes there. In its old mode it makes every ordinary line wait. One small job sent there by accident can make all your lines take turns again.

Layer 2 — the student explanation

The two rules

Analogy first: one spike keeps its slips in order; different spikes do not wait for each other. The CUDA Programming Guide states the stream model in these terms: a stream is a sequence of commands that execute in order, and different streams may execute their commands out of order with respect to one another or concurrently. D1 The installed runtime header says the same thing about copies at the level of a single call: cudaMemcpyAsync "is asynchronous with respect to the host", and "if kind is cudaMemcpyHostToDevice or cudaMemcpyDeviceToHost and the stream is non-zero, the copy may overlap with operations in other streams". H1 Notice the word may. Streams give the GPU permission to overlap; whether it does depends on the hardware's engines (Layer 3), on the kind of host memory (F6-29), and on what else you issued.

So the first rule is a guarantee and the second is only a possibility:

  1. Inside one stream, order is guaranteed. A kernel issued after a copy in the same stream sees the copied data. You need no extra synchronisation for that.
  2. Between streams, nothing is ordered unless you order it. If stream 2 reads what stream 1 writes, you must add a dependency (an event wait) or a host synchronisation. Without one, the program has a race, and it may pass a test today and fail on another GPU.

Creating streams and issuing work into them

A stream is created with cudaStreamCreate(&s) or with cudaStreamCreateWithFlags(&s, flags), where the flags are cudaStreamDefault or cudaStreamNonBlocking. H1 Work goes into a stream through the stream argument: the fourth value of the launch configuration (kernel<<<blocks, threads, sharedBytes, s>>>(...)) and the last argument of cudaMemcpyAsync, cudaMemsetAsync and cudaEventRecord. D1 H1 A stream is destroyed with cudaStreamDestroy; if the device is still working on it, the header says the call "will return immediately and the resources associated with stream will be released automatically once the device has completed all work in stream". H1

The default stream: the old spike by the door

Every launch and copy without an explicit stream goes to the default stream. Its behaviour depends on a compiler choice. nvcc's own help text, recorded in this build, lists the choices: legacy, "the CUDA legacy stream (per context, implicitly synchronizes with other streams)", which is the default value, and per-thread, "a normal CUDA stream (per thread, does not implicitly synchronize with other streams)". R4



"Implicitly synchronizes with other streams" is the dangerous part. The Programming Guide describes it as follows: work issued to the legacy default stream waits until previously issued work in all blocking streams of the context has finished, and work issued afterwards to blocking streams waits until the default-stream work has finished. D1 A "blocking" stream here simply means one created without cudaStreamNonBlocking. The non-blocking flag removes that implicit synchronisation for the stream that carries it. H1 The CU201 programs you wrote put everything in the default stream; that was correct then, because everything was meant to run in order.


Events: record, wait, query, time


The header's documentation of cudaEventRecord is precise enough to quote: it "captures in event the contents of stream at the time of this call", "uses of stream after this call do not modify event", it "can be called multiple times on the same event and will overwrite the previously captured state", and "before the first call to cudaEventRecord(), an event represents an empty set of work, so for example cudaEventQuery() would return cudaSuccess". H1 Four operations use what an event captured:

The ways the host can wait


From the widest to the narrowest: cudaDeviceSynchronize() waits for all work on the device; cudaStreamSynchronize(s) "blocks until stream has completed all operations"; cudaEventSynchronize(e) waits only for the work the event captured; cudaStreamQuery and cudaEventQuery ask without waiting. H1 Use the narrowest wait that is correct. A cudaDeviceSynchronize inside a loop of streamed work turns every iteration into "everything waits for everything", the single spike again.



Layer 3 — the engineer's depth


One analogy sentence: the spikes are a promise about order, not a promise about speed; how many porters and cooks the hall has decides what can really happen at once.


What the API promises, and what it does not


The runtime documentation is careful to promise ordering and to describe concurrency only as possible. Three statements from the installed header define the limits:


    

  • Copies between host and device in non-zero streams "may overlap with operations in other streams" (cudaMemcpyAsync). H1
    • 

  • concurrentKernels "is 1 if the device supports executing multiple kernels within the same context simultaneously", but "it is not guaranteed that multiple kernels will be resident on the device concurrently so this feature should not be relied upon for correctness". H1 A program whose kernels must run at the same moment to make progress (one spinning until another writes a flag) is wrong, even if it passes on your GPU.
    • 

  • asyncEngineCount "is 1 when the device can concurrently copy memory between host and device while executing a kernel. It is 2 when the device can concurrently copy memory between host and device in both directions and execute a kernel at the same time. It is 0 if neither of these is supported." H1 Your device report from F6-07 prints it. Plan with that number, not with a picture from a slide.
    • 



A model you can check by hand


Because the guarantees are about order and the speed depends on engines, a small model is enough to predict a timeline. Listing 2 implements one. Its rules come from the documents: in-stream order (D1), event waits (H1), legacy default-stream synchronisation with blocking streams (D1, R4), the absence of that synchronisation for non-blocking streams (H1), and host blocking for calls documented as synchronous (H1). Two rules are assumptions of the model and are labelled as such in the source: each engine runs one operation at a time in the order the host issued work to it, and only one kernel runs at a time. The second is pessimistic when kernels are small (concurrentKernels above); the first is a simplification of hardware whose real queue structure this build could not verify (see the unverified box in "How the hardware actually does it").


Timing across streams


Listing 1 records start in stream A and stop in stream B. That is legal, and it measures something meaningful only because stream B waits for an event recorded in stream A after start, so stop cannot complete before start. The header warns about the general case: "If either event was last recorded in a non-NULL stream, the resulting time may be greater than expected (even if both used the same stream handle)", because "any number of other different stream operations could execute in between the two measured events". H1 State in your lab notes what the interval contains: here, from the moment stream A reaches start until stream B has copied the result out, including the time B spent waiting for A.


Priorities, host functions and per-thread streams


cudaStreamCreateWithPriority creates a stream whose kernels may preempt work in lower-priority streams; lower numbers mean higher priority, the meaningful range comes from cudaDeviceGetStreamPriorityRange, and the header adds that "only compute kernels launched in priority streams are affected by the stream's priority. Stream priorities have no effect on host-to-device and device-to-host memory operations." H1 cudaLaunchHostFunc enqueues a CPU function into a stream; it "will be called after currently enqueued work and will block work added after it", and it "must not make any CUDA API calls". H1 Finally, multi-threaded host programs should know about --default-stream per-thread (R4): with it, two CPU threads that both launch "without a stream" no longer share, and no longer serialise on, one legacy stream. Prefer explicit streams anyway; nvcc can warn about every launch without a stream argument (-Wdefault-stream-launch, recorded in the forensic lab, R5).

How the hardware actually does it


A discrete GPU moves data between host memory and its own memory with direct-memory-access engines, the copy engines of F1-44 and F1-62, while its streaming multiprocessors run kernels. That is why a copy and a kernel can happen at the same time at all, and why asyncEngineCount counts them (H1). The copies themselves are bus transactions on PCIe or another link (F1-45); a copy engine reads host memory directly, which is only possible when the host pages cannot move: the reason pinned memory appears in every overlap recipe (F6-29). H1 D4 Kernels from different streams can share the SMs when resources allow (the occupancy rules of F6-20), which is what concurrentKernels reports.

Worked example


Two independent jobs, A and B. Each copies its input in (30 units), runs a kernel (40 units) and copies its result out (30 units). Units are model time units, invented for the arithmetic. The GPU has two copy engines (asyncEngineCount = 2 in the model) and runs one kernel at a time.


    

  1. One stream. Everything is in order: 30 + 40 + 30 + 30 + 40 + 30 = 200 units.
    2. 

  2. Two streams, by hand. A-in occupies the copy-in engine from 0 to 30. B-in can use the same engine only after A-in: 30 to 60. A-kernel starts when A-in is done: 30 to 70. B-kernel needs both B-in (done at 60) and the compute engine (free at 70): 70 to 110. A-out: 70 to 100 on the copy-out engine. B-out: after B-kernel, 110 to 140. Total: 140 units.
    3. 

  3. Speed-up. 200 / 140 ≈ 1.43. It is not 2, because the second job's kernel still waits for the first job's kernel, and the first copy in and the last copy out overlap with nothing.
    4. 

  4. A dependency. Now job C writes its result into A's output buffer, so C's kernel must not start before A's result has been copied out (event recorded after A-out, at 100). C-in can still run from 30 to 60, but C-kernel waits until 100: 100 to 140, then C-out 140 to 170. The event costs 30 units here, and it is the price of correctness.
    5. 

  5. The legacy stream. Add a 5-unit kernel to stream 0 between the two jobs. It must wait for everything A issued (until 100), and B's work must wait for it: B-in 105–135, B-kernel 135–175, B-out 175–205. Total 205 units: slower than one stream.
    6.

Where the analogy breaks


    

  • A spike is a physical queue; a stream is a promise about order. Two slips on different spikes are not guaranteed to be worked on at the same time, and the hall may even serve them in any order. The GPU "may" overlap streams; it never must (H1). Correctness must not depend on overlap.
    • 

  • The token is not passed to the other spike. An event does not move any data and does not copy anything; it only orders. Data written by stream A is visible to stream B after the wait because both use the same device memory, not because the event carried it.
    • 

  • More spikes do not mean more porters. Creating eight streams does not create eight copy engines. With asyncEngineCount = 1, copies in both directions share one engine whatever the number of streams (H1); F6-29's forensic lab is about exactly that.
    • 

  • The old spike by the door is not always old. With --default-stream per-thread the default stream of each host thread is an ordinary stream (R4). The analogy describes the legacy mode only.
    •

Transition box

Where you came from: CU201–CU302, where every copy and kernel went into the default stream and ran in order, and F2-34, where CPU threads ran concurrently and needed locks. What carries over: the error checks after every call and launch; event timing from F6-06; the data-race thinking of F2-35: two writers, or a writer and a reader, without an ordering are a bug. H1 What changes: most dangerous first: work in different streams is unordered unless you order it, so a missing event wait is a race that may stay hidden; the legacy default stream silently serialises blocking streams (R4, D1); calls return before the work is done, so every host read needs a matching wait (H1); and overlap is a possibility the hardware may not deliver (asyncEngineCount, concurrentKernels, H1). What comes next: F6-29 splits one large job into chunks across streams so that copies and compute overlap, and shows why the host memory must be pinned.

Summary


    

  • A stream is a queue: operations in one stream run in issue order; operations in different streams may overlap but are not ordered.
    • 

  • Overlap is a permission, not a promise; asyncEngineCount and concurrentKernels say what the device can do, and correctness must never depend on it.
    • 

  • Events capture a stream's work at the moment of recording; cudaStreamWaitEvent orders another stream behind it on the device; cudaEventSynchronize makes the host wait.
    • 

  • Marker events use cudaEventDisableTiming; timing events must be complete before cudaEventElapsedTime, and you must state what the interval contains.
    • 

  • The legacy default stream, nvcc's default, synchronises with blocking streams; one launch without a stream can serialise everything. Use explicit, non-blocking streams; let nvcc warn about launches without a stream.
    • 

  • A small timeline model built from the documented rules predicts what to expect; the profiler (F6-32) tells you what really happened.
    •

Answers to Check yourself


    

  1. Inside one stream, operations run in issue order: a guarantee. Operations in different streams may run concurrently: a possibility, which depends on engines, memory and other work (D1, H1).
    2. 

  2. (b), quoted from the header (H1). (a) is false: different streams "may" overlap. (c) is false: the wait is on the device; the host continues. (d) is false: cudaEventElapsedTime returns cudaErrorInvalidResourceHandle for such events (H1).
    3. 

  3. fill does not depend on stream A, so it should be free to run while A copies and scales. If the wait came first, fill would also wait for xReady and the two streams would barely overlap; the result would still be correct.
    4. 

  4. With one shared copy engine and the issue order of the input (A-in, A-kernel, A-out, B-in, B-kernel, B-out), the engine runs copies in issue order, so B-in must wait behind A-out, which itself waits for A-kernel: A-in 0–30, A-kernel 30–70, A-out 70–100, B-in 100–130, B-kernel 130–170, B-out 170–200; total 200, no better than one stream. If the host issues breadth-first (A-in, B-in, A-kernel, B-kernel, A-out, B-out), B-in runs 30–60, B-kernel 70–110, A-out 70–100, B-out 110–140: total 140 again. The model gives both results (run it). With one copy engine, issue order matters; F6-29 develops this.
    5. 

  5. Yes. cudaMemset without a stream argument is issued to the default stream; in legacy mode it waits for earlier work in blocking streams and later blocking-stream work waits for it (D1, R4). Non-blocking streams are not affected (H1).
    6. 

  6. Stream B waits for xReady, which was recorded in stream A after start; so stop completes after start. The interval includes stream A's copy and kernel, stream B's fill (overlapping), the wait, combine and the copy out; it is "time to result" for this small graph of work, not the time of any single operation (H1's warning).
    7. 

  7. One possible design: N streams (for example 3), frame k in stream k mod N; in each stream copy in, denoise, detect, copy out, all in order, so no events are needed inside a frame. Expected overlap: frame k+1's copy in with frame k's kernels, and frame k's small copy out with frame k+1's kernels, subject to asyncEngineCount. An event is needed only if frames share a buffer (for example a reused pinned staging buffer: the host must wait for the copy that last used it before refilling it).

Forensic lab answer key


Observation. In timeline 1 (R3), resetCounter on stream 0 starts at 100.0, when stream 1's copy out ends; stream 2's copy in starts at 105.0, when the reset ends. Nothing of stream 2 overlaps stream 1. Total 205.0, against 200.0 for one stream and 140.0 for two streams without the reset (R2): "no faster, sometimes a bit worse" is exactly what Rosa saw.


Hypotheses. One copy engine; pageable host memory; a default-stream operation; kernels long enough that overlap gains little. The source rules out pageable memory (lines 30–31 use cudaMallocHost) and shows one launch without a stream argument at line 52, which nvcc flags with -Wdefault-stream-launch (R5). The streams are created with cudaStreamCreate, so they are blocking streams.


Evidence-based conclusion. The legacy default stream "implicitly synchronizes with other streams" (R4): the reset waits for all of stream 1's earlier work, and stream 2's later work waits for the reset (D1). The model with only that rule reproduces the serialisation (timeline 1); making the streams non-blocking removes it (timeline 3, total 145.0). One copy engine is not needed to explain the evidence, and the model with two engines already shows the effect.


Is timeline 2 a correct fix? No. Moving the reset into stream 2 restores some overlap (175.0), but now nothing orders the reset after stream 1's work kernel, which also increments dCounter (line 11). On a GPU that runs the two kernels concurrently, the reset can happen in the middle of stream 1's increments, or stream 2's increments can be added to stream 1's count: a race. Rosa's program was "correct by accident" because the legacy stream ordered it. Timeline 3 has the same race.


Correct fix. Give each job its own counter (two allocations, each reset with cudaMemsetAsync in its own stream before its kernel), and use non-blocking streams. Then the two jobs share nothing and the plan is the two-streams scenario (140.0). If one counter is truly needed, record an event after stream 1's kernel, make stream 2 wait for it, and only then reset in stream 2, accepting less overlap.


Verification and prevention. On a GPU: both counts correct over many runs and under Compute Sanitizer; a timeline showing stream 2's copy in during stream 1's kernel (F6-32). Prevention: build with -Wdefault-stream-launch as an error (nvcc's help lists default-stream-launch among the allowed values of its -Werror option, R4); review rule "one shared buffer, one documented ordering". How the evidence was produced: real compile and run of the program in this build (no GPU); real nvcc warning; the model of Listing 2 on forensic.in, whose operation order is copied from the source. Nothing was injected; the fault is in the source as written.
