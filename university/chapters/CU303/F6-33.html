Story hook

The wall chart of the last chapter told Zainab that on Fridays the cooks' station is busy all evening. Nobody waits for porters any more. Still, the soup takes too long. Is the station slow because the cooks cannot chop faster, or because they keep walking to the pantry for one onion at a time?

Zainab invites an inspector, Dr. Okafor, who studies one station only. She brings two numbers from the hall's plans: the most vegetables the cooks could possibly chop in an hour if they never stopped, and the most crates the pantry door can let through in an hour. Then she watches one batch of soup closely and counts: how much chopping per crate does this recipe need?

"Your soup needs very little chopping per crate," she says. "So the door is your limit, not the knives. Sharpening the knives will change nothing. Bring the crates in faster, or find a recipe that does more with each crate."

The two limits are the roofs, the chopping per crate is arithmetic intensity, and the inspector is Nsight Compute. This chapter teaches you to place a kernel under its roofs, from counts you can read yourself in the machine code, before any profiler confirms it.

What you will be able to do

  • Explain the roofline model for a GPU kernel: the two roofs, arithmetic intensity, the ridge point, and what "memory-bound" and "compute-bound" do and do not mean.
  • Count a kernel's floating-point operations and global-memory bytes per element from its real SASS, and see where the compiler's code differs from the source's arithmetic.
  • Predict each kernel's attainable performance and time on a stated machine (the course's invented TG-1, then your own GPU from its datasheet).
  • Use a kernel profiler's view of one kernel (throughput relative to peak, memory traffic, instruction mix) to test the prediction, and explain the remaining gap.
  • Diagnose a kernel that became compute-heavy because a division compiles to a reciprocal, a refinement and a slow path, and choose a fix with its numerical cost stated.
Jargon box
Kernel profiler
Simple words: a tool that looks inside one GPU kernel and reports how busy each part of the GPU was while it ran. Analogy: the inspector who studies one station. Precise: a profiler that collects hardware performance counters for individual kernel launches and derives metrics such as achieved memory throughput and compute throughput relative to the device's peak; NVIDIA's tool for this is Nsight Compute. D1 Not the whole-program view of F6-32.
Roofline model
Simple words: a picture that says the fastest a kernel can possibly go, given how much arithmetic it does per byte it moves. Analogy: the inspector's two limits, knives and pantry door. Precise: attainable performance = min(peak FLOP/s, arithmetic intensity × peak memory bandwidth), drawn on log–log axes as a slanted memory roof meeting a flat compute roof. D3 Already defined for CPUs in F2-56.
Arithmetic intensity (AI)
Simple words: how much calculating a kernel does for each byte it reads or writes. Analogy: chopping per crate. Precise: floating-point operations divided by bytes of memory traffic, in FLOP/byte; the chapter counts DRAM-level traffic as the bytes the kernel's global loads and stores request (a lower bound when caches help, an upper bound when accesses are uncoalesced). D3 Defined for GEMM in F6-21.
Ridge point
Simple words: the intensity at which a kernel stops being limited by memory and starts being limited by arithmetic. Analogy: the recipe at which the knives and the door are equally busy. Precise: peak FLOP/s divided by peak bandwidth, in FLOP/byte. D3
Speed of light (SOL) throughput
Simple words: how close a kernel came to the hardware's maximum for one kind of work. Analogy: "the door was in use 85 % of the evening". Precise: a kernel profiler's summary metric of achieved throughput as a percentage of the theoretical peak, reported separately for compute and memory units; the curriculum's topic list names "speed-of-light and memory charts" as what to read. C1 D1 Exact metric names: unverified box in Layer 2.
Kernel replay
Simple words: running the same kernel several times so that a profiler can collect more counters than it can read at once. Analogy: the inspector asking for the same batch of soup three times, counting different things each time. Precise: a kernel profiler technique in which the kernel launch is repeated, with memory saved and restored between passes, to collect metric groups that do not fit in one pass; it makes profiled durations differ from unprofiled ones. D1
Slow path (of an instruction sequence)
Simple words: a longer piece of code that runs only for rare, difficult inputs. Analogy: the special procedure for a frozen crate. Precise: in the SASS of an IEEE-rounded single-precision division in this build, a check instruction (FCHK) decides whether the fast reciprocal-based result can be used; otherwise the code calls a subroutine (CALL.REL.NOINC) (R5).

Layer 1 — the kid explanation

Every kernel has two possible limits. It can be limited by how fast the GPU can calculate. Or it can be limited by how fast the GPU can bring data from memory. A kernel cannot beat either limit.

Which limit matters depends on the kernel. Count how many calculations it does for each byte it moves. Few calculations per byte means memory is the limit. Many calculations per byte means the calculators are the limit.

The roofline picture shows both limits as a roof. You put a dot for your kernel under the roof. If the dot is far below the roof, something is wasting time, and you go looking for it.

To count calculations honestly, read the machine code. The compiler sometimes removes work you wrote, and sometimes adds work you did not see. One division, for example, becomes many instructions.

Layer 2 — the student explanation

The roofline for a GPU kernel

Analogy first: knives and the pantry door. The roofline model bounds a kernel's performance P (FLOP/s) by two ceilings: the peak floating-point rate π of the processor, and the product of the kernel's arithmetic intensity I (FLOP/byte) and the peak memory bandwidth β (byte/s): P ≤ min(π, I · β). D3 On log–log axes, I · β is a straight line of slope 1, the memory roof; π is horizontal, the compute roof; they meet at the ridge point I = π / β. You met the model on a CPU in F2-56; nothing in the model changes for a GPU, but three things in its use do:

  • π depends on the instruction and the number format. A GPU's FP32 FMA rate, its FP64 rate and its tensor-core rates are different roofs. Use the roof of the instructions your kernel actually executes; read them from your GPU's datasheet or architecture whitepaper (D4), never from memory (AH-21).
  • β depends on the level you count. DRAM, L2 and shared memory each have their own roof. The chapter counts global-memory bytes requested by the kernel's loads and stores; a kernel profiler measures the bytes actually moved at each level.
  • The prediction is a ceiling. "Memory-bound" means the memory roof is the lower one at this intensity. It does not mean the kernel reaches it; the distance to the roof is what you must explain. The curriculum's rule for every performance milestone is to end with "a profiler-backed explanation of the remaining gap (memory throughput, issue stalls, occupancy, instruction mix)". C1

What a kernel profiler adds


The counts above are what the kernel asks for. A kernel profiler measures what the hardware did: achieved DRAM throughput and bytes, cache hit rates, how busy the arithmetic pipelines were, how many instructions of each kind were issued, and why warps were stalled. Nsight Compute's documentation describes collecting such metrics per kernel launch, grouping them into sections, comparing a kernel against a baseline, and plotting it on a roofline chart built from the device's peaks. D1 Two of its properties change how you read its numbers: metrics that need several passes are collected by replaying the kernel, and kernels are usually serialised while being profiled, so the durations it reports are not those of a normal run. Special functions and what they cost


The roofline counts FLOPs as if every arithmetic instruction were an FMA on the FP32 pipeline. Some source operations are not: the forensic program's single division becomes, on sm_80, a special-function reciprocal (MUFU.RCP), two FFMA that refine it, a check (FCHK), three more FFMA for the quotient and its correction, and a conditional call into a slow-path subroutine (R5). That sequence implements IEEE round-to-nearest division, which is what nvcc's default --prec-div=true promises; nvcc's own help text says --prec-div=false "enables the fast approximation mode" and that --use_fast_math implies it (R7). Built that way, the same source line becomes range checks, MUFU.RCP and one FMUL, with no FCHK and no call (R8):




Precision is the price: x / 3 and x * (1/3) are different floating-point computations. Listing 4 checks the forensic program's 1000 input values on the host: about a third of them give a result one unit in the last place different (R9). Whether that matters is a numerical decision (MA302), not a performance one, and it must be written down.





How the hardware actually does it


An SM issues warp instructions to several kinds of execution units: FP32 pipelines that execute FFMA, FADD and FMUL, integer pipelines for address arithmetic, special-function units for MUFU operations such as reciprocals, and load/store units that send memory requests through the L1 and L2 caches to DRAM (F1-57, F1-58, F1-59). D4 D5 Each unit type has its own peak rate per SM per clock; the "compute roof" of a roofline is the peak of one of them, usually the FP32 FMA rate. Performance counters in the SM and the memory system count issued instructions, active cycles and bytes per level; a kernel profiler reads them per launch and divides by the elapsed cycles to get throughput percentages. D1

Worked example


Place poly<4> on TG-1's roofline, first from the source, then from the SASS, for n = 224 = 16,777,216 elements.


    

  1. TG-1's roofs. Memory: 256 bit × 8 GT/s / 8 bit per byte = 256 GB/s. Compute: 4 × 32 × 2 × 1 GHz = 256 GFLOP/s. Ridge: 256 / 256 = 1 FLOP/byte.
    2. 

  2. Source counts. Four multiply-adds: 8 FLOP; one float read and one written: 8 bytes. I = 1.0 FLOP/byte, exactly at the ridge. Attainable: 256 GFLOP/s; time max(8n/π, 8n/β) = 8 × 16,777,216 / 256 × 109 s = 524.3 µs, with both roofs equal.
    3. 

  3. SASS counts. 3 FFMA + 1 FADD = 7 FLOP; bytes unchanged. I = 0.875: just left of the ridge, memory-bound. Attainable 0.875 × 256 = 224 GFLOP/s; time still 524.3 µs (the memory term).
    4. 

  4. What a measurement would mean. On a real GPU you would compute the achieved FLOP/s as 7n / measured time and the achieved bandwidth as 8n / measured time, and compare each with its roof. For a memory-bound kernel the bandwidth percentage is the one that matters.
    5. 

  5. The other kernels. Listing 3's output for the source counts (R10) next to the SASS-count output above shows the same pattern: poly<1>'s intensity halves (2 to 1 FLOP), poly<16> loses 1 FLOP of 32; all predicted times of memory-bound kernels are unchanged.
    6. 





The lesson: an error in the FLOP count moves a kernel left or right, and near the ridge it can change the verdict "memory-bound" or "compute-bound". Count from the machine code.

Where the analogy breaks


    

  • The kitchen has one kind of knife. A GPU has several roofs: FP32, FP64, special functions, tensor cores, and one bandwidth roof per memory level. A kernel can be under the wrong roof in the picture and still be "correctly" placed by the formula.
    • 

  • The inspector counts what the cooks did. Intensity counted from source or SASS is what the kernel asks for; the memory system may move more (wasted sectors) or less (cache hits). Only a profiler measures what was moved.
    • 

  • The inspector does not change the soup. A kernel profiler replays and serialises kernels; durations under the profiler are not those of a normal run (D1).
    • 

  • Walking to the pantry is the only waiting in the story. On a GPU, warps also wait for arithmetic results and for each other (F1-60); a kernel can be below both roofs with neither unit busy, which the two-limit story cannot express.
    •

Build the roofline of your lab GPU from its datasheet (FP32 and FP64 compute roofs, DRAM bandwidth), then measure your own "practical" roofs: the best bandwidth of a copy kernel (F6-09) and the best FP32 rate of poly<256> with enough threads. Plot both rooflines (by hand or with numpy and a plotting tool of your choice) with the six kernels on them, and write one paragraph on the difference between the datasheet and the measured roofs.


Rubric. Roofs sourced to named documents, measured roofs with machine, versions and dates (4). Correct placement of all kernels with SASS-based counts (3). An honest discussion of the gaps (3).



Summary


    

  • The roofline bounds a kernel by min(π, Iβ); the ridge π/β separates memory-bound from compute-bound kernels.
    • 

  • Count FLOPs and bytes from the SASS: the compiler removed a multiply in poly and turned one division into seven arithmetic and check instructions plus a slow path.
    • 

  • Below the ridge, extra arithmetic is free in time; past it, time grows with FLOPs.
    • 

  • A kernel profiler measures what the hardware did (bytes per level, throughput percentages, instruction mix, stalls) and explains the gap to the roof; it replays and serialises kernels, so take times from normal runs.
    • 

  • Machines with different ridge points can disagree about whether a change matters; never generalise a speed-up from one GPU to another without the roofs.
    • 

  • Precision flags (--prec-div) and algebraic rewrites change both speed and results; state the numerical cost of every such change.
    •

Forensic lab answer key


Observation. multiplyInverse: one FMUL between load and store (R5). divideEach: MUFU.RCP, five FFMA and FCHK on the fast path; if FCHK sets P0, the code does not take the branch at 0x130 and instead executes CALL.REL.NOINC to a subroutine (the slow path), then rejoins at BSYNC.


Hypotheses. (a) More arithmetic per element moved the kernel past the ridge of a machine with low arithmetic throughput; (b) a memory effect (different access pattern); (c) a compiler difference between machines; (d) the slow path being taken often. (b) is ruled out: both kernels have the same load and store (one LDG.E.CONSTANT, one STG.E, same addresses). (c) is not supported: the evidence comes from one compiler for one target. (d) is unlikely for these inputs (moderate values, divisor 3), but must be checked on the board with the profiler's branch or instruction counts.


Evidence-based conclusion. Counted per element, the fast path moves from 1 FLOP to 10 FLOP-equivalents plus a special-function instruction, with the same 8 bytes: intensity from 0.125 to 1.25 FLOP/byte (R12). On TG-1, whose ridge is 1 FLOP/byte, that crosses the ridge: multiplyInverse is memory-bound at 524.3 µs, divideEach compute-bound at 655.4 µs. A GPU with a much higher ridge (much more arithmetic per byte of bandwidth) keeps both kernels memory-bound and shows no difference. The explanation needs only the two ridges as variables, not any real product's numbers.


Fixes. (1) Go back to multiplication by a host-computed inverse: fastest, but about a third of the results differ by one unit in the last place from the correctly rounded quotient (R9); acceptable only if the reviewer's "exact" requirement is relaxed in writing. (2) --prec-div=false or __fdividef-style fast division: similar speed, approximate results, and the flag affects every division in the file (R7, R8). (3) Keep exact division and accept the cost on the board, documenting it. (4) Fuse the normalisation into a neighbouring kernel so that the extra arithmetic hides under that kernel's memory traffic (CU401).


Verification and prevention. On the board, profile both kernels: compute-pipeline throughput high and memory throughput below its peak for divideEach, the reverse for multiplyInverse; executed instruction counts consistent with R5. Prevent: a performance test on the slowest supported GPU; review rule "every change to arithmetic in a kernel is reviewed with its SASS and its numerical effect". How the evidence was produced: real compiles and SASS dumps in this build, real host rounding check, and the TG-1 model with counts read from the SASS; the "development board" is TG-1 and the server GPU is described only by its ridge being higher.
