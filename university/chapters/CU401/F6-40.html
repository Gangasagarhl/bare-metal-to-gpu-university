Story hook

For a whole course, Rahul has written recipe cards for single helpers: "you are helper number i; fetch jar i; if i is past the end, do nothing; after this step wait for your table". He knows exactly what every helper does, and his dishes are fast. But each new dish takes him a week.

A visiting cook shows him a different kind of card. It does not talk to single helpers at all. It talks to a whole table: "take this tray of jars; where the tray runs past the shelf, fill the empty places with this; find the largest jar on the tray; divide the whole tray by it". Who fetches which jar, where the tray waits on the table, how the helpers share the work: the head of the hall decides that, from the card. Rahul writes his softmax card in an afternoon.

Is it as fast? Is it always correct? What did he give up? This chapter answers those questions honestly, including one evening when the tray's empty places were filled with the wrong thing.

What you will be able to do

  • Explain the block-program model of Triton (a program per tile, operations on whole tiles, masked loads with a fill value) and how it differs from CUDA's thread-level SIMT model.
  • Read and write a reduction, a row softmax and a tiled matrix multiply in Triton, after checking every API name against the documentation of your installed version.
  • Model the block-program style on the CPU, and test the kernels' logic (masks, fill values, odd sizes) without a GPU.
  • Compare Triton and CUDA kernels on correctness, performance and development effort with a fair protocol (milestone E11), and say what each measure does and does not show.
  • Diagnose a softmax that is wrong only for some row lengths and some input ranges, from the fill value of a masked load.
Jargon box
Triton
Simple words: a way to write GPU kernels in Python where you describe what happens to whole blocks of data, and a compiler works out what each GPU thread does. Analogy: a recipe card written for a whole table instead of for one helper. Precise: a Python-embedded language and compiler for tile-based GPU programs, introduced by Tillet, Kung and Cox ("Triton: An Intermediate Language and Compiler for Tiled Neural Network Computations"); functions decorated as Triton kernels are compiled just in time for the GPU. D2 D1
Block program (program instance)
Simple words: one running copy of a Triton kernel, which handles one tile of the work. Analogy: one table following the table-level card. Precise: a Triton kernel is launched over a grid of program instances; each instance obtains its index with tl.program_id(axis) and operates on tiles (blocks of values) created with tl.arange; how the instance is mapped onto warps and threads is chosen by the compiler. D1 D2
Tile (in Triton)
Simple words: a small block of values that the program treats as one thing. Analogy: a tray of jars. Precise: a block-shaped value (1-D or 2-D) whose shape is a compile-time constant (a tl.constexpr parameter, usually a power of two); arithmetic, comparisons, reductions (tl.sum, tl.max) and matrix products (tl.dot) apply to whole tiles. D1
Masked load and fill value
Simple words: loading a tile where some places are "outside the data", and saying what to put there instead. Analogy: where the tray runs past the shelf, fill the empty places with something that cannot change the dish. Precise: tl.load(ptrs, mask=m, other=v) reads only where m is true and returns v elsewhere; tl.store(ptrs, x, mask=m) writes only where m is true. The fill value must be the identity of what follows: 0 for a sum, −∞ for a maximum (and therefore for softmax). D1 R3
Just-in-time (JIT) compilation
Simple words: compiling the kernel when the program first runs it, not before. Analogy: the head of the hall reads the card the first time the dish is ordered and plans the table then. Precise: a Triton kernel is compiled when first launched with a given set of constant parameters and argument types, and cached; the first call therefore includes compile time, which a benchmark must exclude by warming up (F6-06). D1
Productivity (of a kernel language)
Simple words: how much useful, correct, fast code you get for your effort. Analogy: how many good dishes per week of card writing. Precise: in this chapter, a set of measures reported together, never one number: development time (logged), lines of code (Listing 3), defects found by tests, performance as a percentage of a reference, and portability across GPUs; each measure is labelled with how it was taken. D3
Kernel (GPU)
As in F6-01; a Triton kernel is also a kernel in this sense once compiled. Not the operating-system kernel of OS301.

Layer 1 — the kid explanation

A CUDA recipe card talks to one helper: "you are number i, do this to jar i". A Triton card talks to a whole table: "take this tray, do this to the whole tray". The head of the hall then decides which helper does which jar, and where the tray rests on the table.

Table cards are shorter and quicker to write. But you can no longer tell a single helper to do something clever on their own. And you must be careful with the empty places at the edge of the tray. If you fill them with the wrong thing, the dish comes out wrong, and only for some trays.

Layer 2 — the student explanation

The block-program model

One analogy sentence: you stop programming helpers and start programming trays. A Triton kernel is a Python function marked as a Triton kernel; a launch runs a grid of program instances, and each instance asks for its index with tl.program_id, builds index tiles with tl.arange, loads tiles with tl.load, computes on whole tiles and writes with tl.store. D1 D2 Tile shapes are compile-time constants (tl.constexpr), which is why the softmax launcher rounds the row length up to a power of two and masks the rest (Listing 1, lines 24–26 and 56). How the instance's tile is spread over warps and threads, whether it passes through shared memory, and which instructions implement tl.dot are decisions of the compiler (Figure 2). D2

Because none of this could run in the build container, Listing 2 implements the model itself in NumPy: a tiny tl stand-in with arange, a masked load with a fill value and a masked store, and the three kernels written in the same shape as Listing 1, launched by a Python loop that plays the grid. It is the university's teaching model, not Triton; it checks the logic of the kernels (indices, masks, fill values, odd sizes), not their speed. Its run (R3):



Read the three results. The sum of 100,003 values by 98 programs of 1,024 differs from a float64 sum by 1.86 × 10−5: FP32 partial sums, as in F6-14. The softmax with 1,000 columns (tile 1,024, 24 masked places) has the same tiny error as the one with exactly 1,024 columns: the −∞ fill makes the masked places vanish. The 300 × 100 × 200 matmul with 64 × 64 output tiles and K-steps of 32 (none of the sizes a multiple of the tiles) agrees with a float64 product to 1.02 × 10−5, because masked loads fill A and B with 0 outside the matrices, and 0 is the identity of the sum inside a dot product.



The three kernels


    

  • Reduction (Listing 1, lines 12–18): one program per 1,024 elements; masked load with fill 0; tl.sum of the tile; one partial per program. The second level (summing the partials) is a second launch or a host sum, as in your F6-14 version. There is no shuffle, no shared memory and no barrier in the source: the compiler produces the block reduction.
    • 

  • Softmax (lines 21–30, 53–57): one program per row; the whole row in one tile; fill −∞; safe softmax in four tile statements. This is the three-pass algorithm of F6-38 in one read, possible because the row stays in the tile between the passes. Rows longer than the largest practical tile need a loop over tiles with the online normaliser: the same algorithm as F6-38's kernel, written per tile.
    • 

  • Matmul (lines 33–50, 60–67): a 2-D grid of programs, each owning a BM × BN tile of C; a loop over K in steps of BK with masked 2-D loads; tl.dot accumulates in an FP32 tile. Compare with your F6-22–F6-24 kernels: the tiling structure is the same, but shared-memory staging, double buffering and the use of tensor cores are left to the compiler. D2
    •

Layer 3 — the engineer's depth


One analogy sentence: a table-level card is only as good as the head of the hall who turns it into helper-level work, so an engineer reads what the head decided. This section covers what to inspect, where the model's limits are, and how to decide between the two languages.


Inspecting what the compiler did


A Triton kernel compiles to the same kind of machine code as a CUDA kernel (PTX and SASS on NVIDIA GPUs), so every tool from CU303 applies: Nsight Systems shows its launches, Nsight Compute shows its registers, shared memory, occupancy and roofline position, and the SASS can be read like your own (F6-34). D1 For the matmul, check that the inner loop contains the tensor-core instructions you saw in F6-26 when the input types allow them; for the softmax, check the number of global loads per element. If the profile disagrees with Figure 2's promise, the profile wins.

Where the block-program model fits, and where it does not


    

  • Fits: dense, regular tiles: element-wise chains (fusion is natural: several statements on one tile before one store), row-wise reductions and normalisations, GEMM-like kernels, attention forward passes (the published Triton tutorials include a fused attention; F6-39's algorithm is tile-shaped). D1
    • 

  • Fits less well: irregular, data-dependent control per element (graph traversals, sparse formats with per-thread work lists), algorithms built on warp-level primitives (shuffle-based scans, warp-aggregated atomics, F6-15, F6-17), cross-block protocols such as decoupled look-back (F6-16) or grid barriers (F6-36), and multi-GPU peer access patterns (F6-37). For these, CUDA C++ (or a library) remains the tool.
    • 

  • Tile shapes are compile-time. Each new BLOCK value is a new compilation; a softmax launcher that passes the next power of two of the row length compiles one kernel per distinct rounded length. Autotuning over tile sizes is common practice and costs compile time too. D1
    • 

  • Edges are masks. Every edge case becomes a mask and a fill value. That is concise and easy to get wrong in exactly one way: a fill value that is not the identity of the following operation (forensic lab).
    • 



A decision procedure


    

  1. Is there a library routine (F6-35)? Use it, and use it as the reference.
    2. 

  2. Is the kernel tile-shaped and mostly dense? Write it in Triton first; it is the fastest way to a correct fused kernel and a performance baseline.
    3. 

  3. Measure against the library and against the roofline bound. If Triton reaches your target, stop: the maintenance cost of the shorter code is lower.
    4. 

  4. If not, profile; if the gap comes from something the block model cannot express (a warp-level trick, a cross-block protocol, a precise shared-memory layout), write that kernel in CUDA C++ and record why.
    5. 

  5. Re-run the comparison when the GPU, the Triton version or the CUDA toolkit changes: compiler improvements can move the answer in either direction.
    6. 




How the hardware actually does it


The GPU does not know which language a kernel came from. A Triton program instance becomes a thread block (a CTA) of some number of warps chosen at compile time; its tiles become registers spread across the lanes of those warps, with shared memory used where the compiler needs to change a tile's layout or to stage operands for matrix instructions; masks become predicated loads and stores (F1-57, F6-03). D2 Everything you learned about coalescing, occupancy, bank conflicts and tensor cores therefore still decides the speed; the difference is who chose the mapping. A performance gap between a Triton kernel and a hand-written one is explained with the same evidence as always: registers and occupancy from the compiler report, memory traffic and stalls from the profiler, instructions from the SASS.

Worked example


Trace Listing 2's softmax program for one row of n_cols = 5 with BLOCK = 8, values x = (1, 3, 2, 0, 4), to see exactly what the mask and fill do.


    

  1. Indices. cols = arange(0, 8) = 0 … 7; mask = cols < 5 = (T, T, T, T, T, F, F, F).
    2. 

  2. Masked load with fill −∞. v = (1, 3, 2, 0, 4, −∞, −∞, −∞).
    3. 

  3. Subtract the maximum. max(v) = 4 (the fill cannot win a maximum); v − 4 = (−3, −1, −2, −4, 0, −∞, −∞, −∞).
    4. 

  4. Exponentiate. ev = (0.049787, 0.367879, 0.135335, 0.018316, 1, 0, 0, 0). The masked places become exactly 0.
    5. 

  5. Sum. den = 1.571317: only the five real values contribute.
    6. 

  6. Divide and masked store. y = (0.031685, 0.234122, 0.086129, 0.011656, 0.636409), written to places 0–4 only; the sum is 1.
    7. 

  7. With fill 0 instead (the forensic bug): v = (1, 3, 2, 0, 4, 0, 0, 0); the maximum is still 4, but the three fill places contribute 3 × e0−4 = 0.054947 to den, which becomes 1.626264, and every stored output is 3.4 % too small; the stored values now sum to 0.966. If all real values were below 0, the fill 0 would even become the maximum.
    8.

Where the analogy breaks


    

  • The "head of the hall" is a compiler, not a manager at run time. The mapping from tiles to threads is decided once, at compile time, for each set of constant parameters; nothing adapts while the kernel runs. A tile size that was good for one input shape is used for all shapes that compile to the same kernel.
    • 

  • Helpers still exist. The table card hides individual helpers, but they are still there with their registers, their warps and their divergence; a Triton kernel can have low occupancy, bank conflicts or spills like any CUDA kernel, and the profiler will show them.
    • 

  • The tray has no physical size limit in the story. In reality a tile larger than what fits in registers spills or fails to compile efficiently; "load the whole row as one tile" works only up to a size you must find by measurement.
    •

Forensic lab


Scenario. Chen ported the team's softmax to the block-program style and, to avoid "infinities in the code", filled masked lanes with 0.0. The unit tests use rows of 1,024 columns and pass. In production, models with 1,000-wide rows report slightly low probabilities, and one model whose scores are strongly negative (log-probabilities around −30 and below) produces near-zero outputs for every row. The evidence is a real run of the team's model of the kernel (Listing 2, --forensic) with fill 0.0 on four configurations; each line gives the row length, the value range, the tile size, the largest error against a float64 reference and the smallest row sum.

Summary


    

  • Triton programs tiles, not threads: a grid of program instances, each loading, computing on and storing whole tiles.
    • 

  • The compiler, not you, maps tiles onto warps, threads, registers and shared memory, and chooses matrix instructions for tl.dot.
    • 

  • Edges are masked loads with fill values; the fill must be the identity of the next operation (0 for sums and products in a dot, −∞ for max and softmax).
    • 

  • The block model fits dense, tile-shaped kernels and fusion; warp-level tricks and cross-block protocols stay in CUDA C++.
    • 

  • Productivity is several measures together: correctness, logged development time, lines of code, performance against a reference; JIT compile time is excluded from timing by warm-up.
    • 

  • In this build only the logic was run (a NumPy model); every Triton name and every claim about its compiler must be checked against the installed version's documentation.

Forensic lab answer key


Observation. 1,024 columns: error 2.09 × 10−7, row sums 1 (correct). 1,000 columns around 0: error 2.24 × 10−4, worst row sum 0.999. Around −30: error 0.863, row sum 9.95 × 10−11. Around −120: error 0.979, row sum 0. The error appears only when BLOCK (1,024) is larger than the row (1,000), and grows as the values fall below 0.


Hypotheses. With 1,024 columns there are no masked places and the result is correct, so the arithmetic of the kernel is fine; the problem is in the masked places. An inflated denominator explains the values-around-0 line (row sum slightly below 1). A wrong maximum explains the negative lines (the fill 0 becomes the maximum). Underflow alone would also affect the 1,024-column case if values were negative; it did not occur there because the values were around 0.


Root cause. Around 0 (spread 3), the row maximum m is several units above 0, so each of the 24 filled places adds e0−m to the denominator: a small amount, but not zero. Dividing by a denominator that is too large makes the outputs add up to less than 1; the evidence's worst row sum of 0.999 says the filled places made up about 10−3 of that row's denominator. Around −30 and −120, the fill 0 is the largest value in the tile, so max = 0, every real ex−0 is tiny (about e−30) or underflows to 0 (e−120 in FP32), and the denominator is about 24 (the filled places): outputs ≈ ex/24, row sums near 0.


Fix and verification. Fill with −∞ (other=-float("inf") in Listing 1, fill = -np.inf in the model). Verified by R3: the 1,000-column softmax has error 1.61 × 10−7.


Prevention. Tests with row lengths that are not powers of two (and lengths just above a power of two), values far below 0 and far above 0; an assertion that every row sums to 1 within n·ε. How the evidence was produced: real runs of Listing 2 with fill 0.0 on random rows (NumPy generator seed 11); no GPU or Triton involved.
