Story hook

The restaurant has grown. There are now four kitchen halls in one building, each with its own helpers and its own big pantry. Some dishes need ingredients from another hall's pantry, so there is a delivery service. Kofi, who plans the deliveries, assumed that a delivery between any two halls takes the same time. It does not. Halls 0 and 1 share a corridor; so do halls 2 and 3; but a delivery from hall 1 to hall 2 goes down the corridor, through the central lobby and up the other corridor.

Two more surprises followed. A hall can only take things from another hall's pantry directly if both managers have agreed to it, and the agreement is one-way: hall 0 may take from hall 1 without hall 1 being allowed to take from hall 0. And when two separate catering companies share the building, one company can lend the other a key to one of its shelves, but only by handing over a written key card, and it must not empty the shelf while the other company is still using it.

This chapter is about measuring the delivery roads, getting the agreements right, and lending shelves safely.

What you will be able to do

  • Query peer capability and link rank for every ordered pair of GPUs, and enable peer access correctly (direction, flags, "already enabled").
  • Measure a peer bandwidth and latency matrix, unidirectional and bidirectional, with events and the median of 20 runs (milestone F1).
  • Predict the matrix of a machine from its topology with the alpha–beta model, and explain every difference between prediction and measurement.
  • Share a device allocation between two processes with CUDA IPC handles, with correct lifetime rules.
  • Diagnose a slow row in a peer matrix from the matrix and the topology.
Jargon box
Node (machine)
Simple words: one computer, possibly with several GPUs. Analogy: one building with several kitchen halls. Precise: a single machine (one operating-system instance) whose GPUs share its CPU sockets, memory and PCIe hierarchy; "multi-node" means several machines connected by a network (DG401). D4 (Not the circuit node of F1-04.)
Peer-to-peer (P2P) access
Simple words, analogy: as in F1-62: one GPU reading or writing another GPU's memory directly, without a stop in host memory; taking from another hall's pantry by the corridor. Precise: after cudaDeviceEnablePeerAccess(peerDevice, 0) succeeds, "all allocations from peerDevice will immediately be accessible by the current device"; the access "is unidirectional", so the other direction needs "a separate symmetric call". H1
Peer capability and performance rank
Simple words: whether two GPUs can use direct access at all, and how good their connection is compared with the others. Analogy: whether a corridor exists, and whether it is the short or the long one. Precise: cudaDeviceCanAccessPeer(&can, device, peerDevice) returns 1 "if device device is capable of directly accessing memory from peerDevice"; cudaDeviceGetP2PAttribute with cudaDevP2PAttrPerformanceRank returns "A relative value … Lower value means better performance (0 being the value used for most performant link)". H1
Topology
Simple words: the map of how the GPUs, the CPU and the switches between them are wired. Analogy: the building plan: corridors, lobby, which halls share a corridor. Precise: the graph of links (PCIe switches, CPU root complexes, inter-socket links, NVLink or NVSwitch, xGMI on AMD) between devices; it decides the path, and therefore the latency and bandwidth, of every peer copy. D4 D3
Staged copy
Simple words: a GPU-to-GPU copy that stops in the computer's main memory on the way. Analogy: a delivery that goes to the building's central store and is picked up from there. Precise: without peer access, a device-to-device copy between GPUs is performed through host memory, two transfers over the host links; it is correct but slower (the model of Listing 3 charges two host-link copies). D1
CUDA IPC handle
Simple words: a small block of bytes that lets another program on the same computer use your GPU memory. Analogy: the written key card one catering company hands to another for one shelf. Precise: cudaIpcGetMemHandle(&handle, devPtr) "exports" an allocation made with cudaMalloc into a cudaIpcMemHandle_t; another process passes it to cudaIpcOpenMemHandle(&ptr, handle, cudaIpcMemLazyEnablePeerAccess) and later cudaIpcCloseMemHandle(ptr); IPC "is restricted to devices with support for unified addressing on Linux and Windows operating systems". H1
Bidirectional bandwidth
Simple words: how many bytes per second move when two GPUs copy to each other at the same time. Analogy: deliveries going both ways down the corridor at once. Precise: total bytes moved in both directions divided by the elapsed time of both concurrent copies; on a full-duplex link it can approach twice the unidirectional figure, on a shared path it may not; only measurement tells (Listing 1). D3

Layer 1 — the kid explanation

Four kitchen halls in one building share ingredients. Some halls are next to each other and some are far apart, so a delivery's time depends on the road. Before you plan the menu, you walk every road and time it. That table of times is your most important map.

A hall may take directly from another hall's pantry only if it has permission, and permission goes one way. Without permission, deliveries still happen, but they go through the central store, which is slower. And when two different catering companies share the building, one can lend the other a key card to a shelf. The lender must wait until the borrower says "done" before clearing the shelf.

Layer 2 — the student explanation

Several devices, one process

One analogy sentence: each hall has its own manager, and you talk to one manager at a time. A CUDA process sees every visible GPU as a device number from 0 to cudaGetDeviceCount − 1; cudaSetDevice(d) makes device d current for the calling host thread, and allocations, streams, events and kernel launches then belong to that device (F6-07). D1 Listing 1 sets the device before every call that creates something, and creates each stream on the device that will use it.

Peer access: capability, permission, direction

The installed runtime header defines the three steps precisely. H1

  1. Capability. cudaDeviceCanAccessPeer(&can, device, peerDevice) answers whether device can access memory that lives on peerDevice. It is a question about an ordered pair; ask it for both orders.
  2. Permission. With the current device set to the one that will access, cudaDeviceEnablePeerAccess(peerDevice, 0) makes all of the peer's allocations accessible. The header says the access "is unidirectional", flags is "Reserved for future use and must be set to 0", and a second call returns cudaErrorPeerAccessAlreadyEnabled. Listing 1 treats that error as harmless (line 92) and then clears it with cudaGetLastError() (line 95), because otherwise the sticky "last error" would be reported by the next check (F6-05).
  3. Use. A kernel on the accessing device may dereference pointers into the peer's memory, and cudaMemcpyPeerAsync(dst, dstDevice, src, srcDevice, count, stream) copies between devices; the header calls it "asynchronous with respect to the host and all work on other devices". H1

The header also gives you a free hint about topology: cudaDeviceGetP2PAttribute with cudaDevP2PAttrPerformanceRank returns a relative rank, lower is better, 0 for the most performant link; other attributes report whether peer access is enabled and whether native atomics work over the link. H1 Listing 1 prints the access matrix with the rank in brackets before it measures anything: a measured matrix that disagrees with the ranks needs an explanation. The declarations and enum values below are read from the installed headers (R4), not typed from memory.

Sharing memory between processes: CUDA IPC


Multi-GPU programs are often one process per GPU (curriculum F2: "One process per GPU (or one thread per GPU)"). D6 Processes do not share an address space, so a device pointer means nothing in another process. CUDA IPC exports an allocation as a handle that another process can open. The installed header documents the rules Listing 2 follows: H1


    

  • cudaIpcGetMemHandle takes "a pointer to the base of an existing device memory allocation created with cudaMalloc" and is "a lightweight operation"; the handle is plain bytes you may send through any channel (Listing 2 uses a pipe).
    • 

  • cudaIpcOpenMemHandle's flags "Must be specified as cudaIpcMemLazyEnablePeerAccess" (the value 0x01 in R4), and "No guarantees are made about the address returned": two processes may see the same memory at different addresses. Never send raw pointers between processes; send handles and offsets.
    • 

  • "Calling cudaFree on an exported memory region before calling cudaIpcCloseMemHandle in the importing context will result in undefined behavior." Listing 2's parent therefore waits for the child's acknowledgement byte and for waitpid before cudaFree.
    • 

  • Handles from each device "may only be opened by one context per device per other process", and opening the same handle again in the same context increments a reference count; cudaIpcCloseMemHandle decrements it.
    • 

  • IPC "is restricted to devices with support for unified addressing on Linux and Windows operating systems", and "on Windows is restricted to GPUs in TCC mode"; test with cudaDeviceGetAttribute and cudaDevAttrIpcEventSupport.
    • 



Listing 2 also forks before its first CUDA call, so each process creates its own CUDA context, and it handles failure in the parent by closing the pipe, so the child sees end-of-file instead of waiting forever. In this build the parent's first call failed with cudaErrorNoDevice, the parent closed the pipe and waited, and the child printed "no handle received" and exited (R2): the error path, at least, is tested.

Layer 3 — the engineer's depth


One analogy sentence: the building plan is the first thing a delivery planner asks for, and the second is a stopwatch. This section is about reading topology, designing the measurement, and choosing between peer copies, peer loads and IPC.


Reading topology


    

  • Ask the tools, then verify. The curriculum's F1 reading list names "the topology views of nvidia-smi and amd-smi / rocm-smi". D6 They print a matrix of link types between GPUs (and NICs); the CUDA attribute rank (H1) gives a second opinion; your measured matrix gives the third. The acceptance test asks you to explain every link type you see.
    • 

  • Path types. Through one PCIe switch, through a CPU's root complex, across CPU sockets (an inter-socket link in the path), and over GPU-to-GPU links (NVLink, possibly through NVSwitch; xGMI on AMD Instinct). D3 D4 Each has its own α and β, and a path's β is limited by its slowest hop and by other traffic sharing that hop.
    • 

  • Capability is not performance. Two GPUs on different sockets may report peer capability and still be slower than a staged copy on some platforms; two GPUs may report no capability (some systems disable it) and fall back to staging. cudaDeviceEnablePeerAccess's header notes "both device-wide and system-wide limitations per system configuration". H1 Measure both with and without peer access when in doubt.
    •

Designing the measurement


    

  • Sizes. At least one latency size and one bandwidth size; better a sweep (4 B to 1 GiB, as F2 requires for all-reduce) so you can fit α and β per pair and compare with Listing 3's model.
    • 

  • Directions. The matrix need not be symmetric: links, switches and DMA engines can behave differently in each direction. Measure every ordered pair.
    • 

  • Concurrency. Bidirectional runs both copies at once. A further test runs all pairs of a ring at once (each GPU sending to its right neighbour): that is the traffic pattern of F8-02's ring all-reduce, and it can expose a shared switch uplink that single-pair tests hide.
    • 

  • Agreement. F1 accepts your matrix when it "agrees with p2pBandwidthLatencyTest (cuda-samples) or the ROCm bandwidth test within 10 %". D6 Disagreement usually means a different method (sizes, copy engine versus kernel, timing interval), not a broken machine: find out which.
    • 



Note
Listing 1's bidirectional timing records the start event on the source's stream and makes that stream wait for an event recorded after the reverse copy. Read lines 41–52 with F6-28 open: it is the cross-device version of the "fork–join with events" pattern. Check the result against the sum of two unidirectional runs: bidirectional time must lie between the larger of the two and their sum.


Peer copies, peer loads, or IPC?


    

  • Peer copies (cudaMemcpyPeerAsync) move bulk data with the copy engines and overlap with kernels on other streams (F6-29). They are the building block of F2's chunked ring.
    • 

  • Peer loads and stores in a kernel (after enabling access) read or write the peer's memory element by element. They suit irregular, fine-grained access and fused "compute while fetching" kernels, but every access crosses the link, so coalescing matters even more than locally (F6-08). Atomics over the link need cudaDevP2PAttrNativeAtomicSupported. H1
    • 

  • IPC is needed whenever the GPUs are driven by different processes; after opening, the imported pointer is used with the same peer copies or loads. Events can be shared too (cudaIpcGetEventHandle appears in the header's "see also" list) so that one process can wait for another's work. H1
    • 

  • Libraries: for collectives (all-reduce, all-gather) the course moves to NCCL and RCCL in DG401; this chapter's tools are what such libraries are built from, and what you need to understand their topology logs.
    • 




How the hardware actually does it


Each GPU sits on the PCIe hierarchy of the machine as an endpoint with its memory exposed through address windows (BARs, F1-62, F4-01). A peer copy or a peer load is a PCIe (or NVLink) transaction from one GPU to an address that the other GPU decodes as its own memory; when the path stays below one PCIe switch, the switch forwards it without involving the CPU, and when it crosses the root complex, the CPU's PCIe controller forwards it, which some platforms support well and some poorly. D3 D4 Bulk copies are executed by each GPU's copy engines (DMA, F1-44), so they can overlap with kernels. A staged copy is two DMA transfers through pinned host memory and uses the host links twice. GPU-to-GPU links such as NVLink bypass PCIe entirely, with their own bandwidth per link, which is why the topology view, not the GPU model alone, predicts your matrix. Unified virtual addressing (one address space across host and all GPUs of a process) is what lets a single pointer value identify which device's memory it points to; IPC requires it (H1). H1 D1

Worked example


Predict TN-4's matrix by hand with the alpha–beta model, then check against Listing 3 (R3). The invented link parameters are: same switch α = 6 µs, β = 12 GB/s; through the root complex α = 9 µs, β = 9 GB/s; host link α = 10 µs, β = 16 GB/s (the same TG-1 host link as F6-29). 1 GB/s = 103 bytes per µs.


    

  1. Latency, 4,096 B, GPU 0 → GPU 1 (same switch): 6 + 4096/12,000 = 6 + 0.341 = 6.34 µs. R3 prints 6.3.
    2. 

  2. Latency, GPU 1 → GPU 2 (root complex): 9 + 4096/9,000 = 9.455 µs. R3 prints 9.5. At this size, α is over 90 % of the time: buying a faster link would hardly help small messages.
    3. 

  3. Bandwidth, 256 MiB = 268,435,456 B, same switch: 6 + 268,435,456/12,000 = 6 + 22,369.6 = 22,375.6 µs; 268,435,456 B / 22,375.6 µs = 11,997 B/µs ≈ 12.00 GB/s. The fixed cost is invisible at this size.
    4. 

  4. Staged (peer access off): two host-link copies, 2 × (10 + 268,435,456/16,000) = 2 × 16,787.2 = 33,574.4 µs → 8.00 GB/s. In this invented machine a staged copy is only a little slower than a root-complex peer copy; in a real machine the relation can go either way, which is exactly why the F1 matrix is measured with and without peer access.
    5. 

  5. Use the matrix. A ring 0 → 1 → 2 → 3 → 0 uses two fast hops (0→1, 2→3) and two slow ones (1→2, 3→0); every ring on TN-4 must cross the root complex twice. The ring's speed is set by its slowest hop: plan for 9 GB/s, not 12.
    6.

Where the analogy breaks


    

  • "Permission" is not a person's decision. In the kitchen a manager could refuse for a reason; on the GPU, cudaDeviceCanAccessPeer reports what the hardware, driver and platform allow, and cudaDeviceEnablePeerAccess is your program's choice, nothing more. A "no" is a property of the system, not a negotiation.
    • 

  • Deliveries are not single trips. A large copy is split into many packets that are in flight at the same time; that is why bandwidth, not "trip time", dominates large copies, and why two directions can sometimes run at full speed together.
    • 

  • A key card is not a copy of the shelf. The IPC handle does not move data; both processes access the same physical memory. Writes by one are seen by the other, with the same ordering questions as any shared memory (OS201, F6-36).
    •

Transition box

Where you came from: one GPU: streams and copies (F6-28, F6-29), groups up to the whole grid (F6-36), and the interconnect chapter F1-62. Forensic lab


Scenario. Lucía maintains the nightly peer-matrix job on the team's TN-4 test node. Summary


    

  • Every GPU is a device number; objects belong to the device current when they are created.
    • 

  • Peer access is a capability per ordered pair, enabled one way at a time with flags 0; "already enabled" must be tolerated and cleared.
    • 

  • Without peer access, GPU-to-GPU copies are staged through host memory.
    • 

  • Topology decides each pair's latency and bandwidth: measure an ordered-pair matrix, unidirectional and bidirectional, and explain it with the alpha–beta model.
    • 

  • CUDA IPC shares a cudaMalloc allocation between processes through a handle; addresses may differ, and the exporter frees only after every importer has closed.
    • 

  • The matrix of milestone F1 is the input to the ring all-reduce of F2 and to every later multi-GPU design.

Forensic lab answer key


Observation. Row 3 (copies from GPU 3) shows 8.00 GB/s with an asterisk for all three destinations; the prediction was 12.00 (3 → 2, same switch) and 9.00 (3 → 0, 3 → 1). All other entries, including column 3 (copies to GPU 3), match the prediction. The asterisk means "staged through host memory (no peer access)".


Hypotheses. A degraded link would affect copies to GPU 3 too, and would slow different paths differently; it does not. Another job on GPU 3 would slow both directions and fluctuate. A missing peer enable for copies from GPU 3 gives one identical value for every destination: the evidence shows exactly that.


Root cause. A staged copy is two host-link copies regardless of the destination: 2 × (10 + 268,435,456/16,000) µs = 33,574.4 µs → 8.00 GB/s for every entry of the row. The refactored loop runs a only up to count − 2, so device 3 never calls cudaDeviceEnablePeerAccess for any peer; the self-pair is already excluded by a != b, so the "fix" it was meant to provide was not needed.


Fix and verification. for (int a = 0; a < count; ++a) for (int b = 0; b < count; ++b) if (a != b && can(a, b)) enable…; the verification is the clean prediction (R3) on the model and, on the real node, a matrix without asterisks and an access matrix of "yes" in row 3.


Prevention. Before timing, query cudaDevP2PAttrAccessSupported for every ordered pair that reports capability and fail loudly if any is 0; keep the access matrix in the nightly log. How the evidence was produced: real runs of Listing 3 with peer access marked off for 3 → 0, 3 → 1, 3 → 2 (invented numbers); no GPU involved. The question of which device's enable a peer copy depends on is simplified here; check the Programming Guide's peer-to-peer section (D1) for the exact rule.
