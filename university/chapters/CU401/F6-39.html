Story hook

Every evening the great kitchen hall prepares a tasting menu: each guest's plate is a blend of every dish on the buffet, weighted by how well each dish matches that guest's taste. The old method was thorough and slow. First the helpers wrote a giant chart: every guest against every dish, a matching score in each square. Then they turned each row of the chart into shares. Then, from the chart, they blended each plate. With a thousand guests and a thousand dishes, the chart had a million squares, and carrying it to and from the big pantry took most of the evening.

Ayşe, who had learned Kenji's running-tally trick from the softmax station, asked a simple question: why write the chart at all? Each helper could take one tray of dishes at a time to the table, score them for her guests, fold them into a running blend, and forget the scores. When a better-matching dish appeared, she would scale down the blend so far, exactly as Kenji scaled his tally. At the end she divides once. The chart never exists.

The new method worked beautifully, until the night a group of guests arrived who matched nothing on the first tray at all.

What you will be able to do

  • Explain the attention forward pass O = softmax(QKT/√d)·V and why the unfused version is dominated by the N × N score and probability matrices.
  • Derive the tiled algorithm: a running maximum m, normaliser l and unnormalised output per query row, updated once per key/value tile, and prove it equals the unfused result.
  • Implement a simple tiled attention kernel with K and V tiles staged in shared memory, and read its register, shared-memory and SASS reports.
  • Count global-memory traffic for both versions and predict how it scales with N, d and the tile sizes.
  • Diagnose silently zeroed output rows caused by fully masked tiles, and fix them with an empty-state guard.
Jargon box
Attention (scaled dot-product)
Simple words: each output row is a weighted average of value rows, with weights from how well a query matches each key. Analogy: each guest's plate is a blend of all dishes, weighted by matching score. Precise: for Q, K, V of size N × d, O = softmax(QKT/√d)·V, with the softmax taken over each row of the N × N score matrix S = QKT/√d. D2
Query, key, value
Simple words: three tables of numbers: what each position is looking for, what each position offers, and what it contributes if chosen. Analogy: the guest's taste, the dish's label, the dish itself. Precise: rows qi, kj, vj ∈ ℝd; score sij = qi·kj/√d; output oi = Σj pijvj with pij the row softmax of si·. D2
Head dimension (d)
Simple words: how many numbers describe one query, key or value. Analogy: how many flavours a taste card lists. Precise: the length of qi, kj, vj for one attention head; Listing 2 fixes d = 64 at compile time so that a query row and an output row fit in registers. D2
Masking (causal, padding)
Simple words: hiding some keys from some queries. Analogy: some dishes are not offered to some guests. Precise: setting sij = −∞ for hidden pairs so that pij = 0; causal masking hides j > i, padding masking hides positions that hold no real data (Listing 1 hides j < pad, a left-padded sequence). D2 D3
Tiled (flash-style) attention
Simple words: computing attention one block of keys at a time, keeping only a running summary per query row, so the big score chart is never stored. Analogy: Ayşe's tray-by-tray blend. Precise: for each tile of Br query rows, iterate over tiles of Bc key/value rows; keep per row the running maximum m, normaliser l and unnormalised output a; per tile, m′ = max(m, maxj sij), α = em−m′, a ← αa + Σj esij−m′vj, l ← αl + Σj esij−m′; finally o = a/l. This is the structure of FlashAttention's forward pass. D3 D4
IO-aware algorithm
Simple words: an algorithm designed around how many bytes it moves, not only how many sums it does. Analogy: planning the evening around pantry trips. Precise: the FlashAttention paper's term for algorithms that minimise reads and writes between the GPU's large, slow memory and its small, fast on-chip memory. D3
Kernel (GPU)
As in F6-01; not the operating-system kernel of OS301.

Layer 1 — the kid explanation

For each guest you want a blend of all dishes, weighted by how well each dish matches the guest. The slow way writes a huge chart of every guest against every dish and carries it back and forth. The fast way never writes the chart: a helper takes one tray of dishes at a time, scores them for her guest, adds them to a running blend, and forgets the scores.

The trick that makes this exact is the one from the softmax station. When a better-matching dish appears, the helper scales down her blend so far, then carries on. At the very end, she divides once by the running total. One last rule: if a whole tray has nothing her guest may eat, she must not "scale" by a nonsense number. She simply skips that tray.

Layer 2 — the student explanation

The computation and its cost

One analogy sentence: the tasting menu is three matrix steps, and the chart is the expensive part. Scaled dot-product attention, for one head, computes S = QKT/√d (N × N), P = row-softmax(S) and O = PV (N × d). D2 Written as three kernels (two GEMMs from F6-35 and the softmax of F6-38), the intermediate S and P each have N2 elements. Listing 1's naive() counts the floats each kernel moves, assuming ideal reuse inside each kernel:

  • kernel 1 reads Q and K (2Nd) and writes S (N2);
  • kernel 2 reads S and writes P (N2 each);
  • kernel 3 reads P and V (N2 + Nd) and writes O (Nd).

Total: 2N2 + 3Nd reads and 2N2 + Nd writes. For N = 512 and d = 64 that is 622,592 + 557,056 floats, exactly what R1 prints for the case long. Since d is fixed by the model (here 64) and N is the sequence length, the N2 terms dominate as sequences grow, and so does the N2 memory needed just to hold S. D3

The tiled algorithm

The FlashAttention paper's forward pass avoids storing S and P by combining two ideas you already have: tiling (F6-22) and the online softmax (F6-38). D3 D4 For each query row i, keep three things: the running maximum m, the running normaliser l = Σ esij−m over the keys seen so far, and the running unnormalised output a = Σ esij−mvj. Process the keys in tiles. For a new tile with scores sij:

m'  = max(m, max_j s_ij)
alpha = exp(m - m')
l   = alpha * l + sum_j exp(s_ij - m')
a   = alpha * a + sum_j exp(s_ij - m') * v_j
m   = m'
... after the last tile:  o_i = a / l

Why it is exact. This is F6-38's invariant extended by one vector. Before the update, l and a are sums of terms relative to m; multiplying by α = em−m′ re-expresses every old term relative to m′ (es−m·em−m′ = es−m′), and the new tile's terms are added relative to m′. After the last tile, l is the softmax denominator of the row and a is Σj esij−mvj, so a/l = Σj pijvj = oi. The division happens once per output element instead of once per probability. Listing 1 compares tiled() with naive() on five cases, including sizes that are not multiples of the tiles, causal masking and padding: the largest difference is 1.79 × 10−7, at the level of FP32 rounding of values of order 1 (R1).




Traffic of the tiled version


Per tile of Br query rows, tiled() reads the Q tile once (Br·d) and every K and V tile once (2Nd in total), and writes the O tile once. Over N/Br query tiles: reads Nd + (N/Br)·2Nd = Nd(1 + 2N/Br), writes Nd. For N = 512, d = 64, Br = 64: 32,768 × 17 = 557,056 reads and 32,768 writes (R1). Three conclusions follow, each worth more than a single speed-up number:


    

  • Writes drop from O(N2) to O(Nd). Nothing quadratic is ever stored; memory use is linear in N. D3
    • 

  • Reads are still quadratic, but divided by Br/d. The ratio of the dominant terms, unfused 4N2 against tiled 2N2d/Br, is 2Br/d. With Br = d = 64 that is 2; doubling Br doubles it. Larger query tiles mean more reuse of every K and V tile, limited by registers and shared memory (Layer 3).
    • 

  • The work is the same. Both versions compute every score and every exponential; the tiled one does a little more (the rescaling by α). Attention becomes cheaper because it moves fewer bytes, not because it does less arithmetic: the IO-aware argument of the paper. D3
    • 




Masking and the empty state


Masked scores are −∞, so their probabilities are e−∞ = 0, which is what masking means. D2 The danger is a tile in which every score of a row is masked. Then maxj sij = −∞; if the row's m is still −∞ (no visible key yet), m′ = −∞ and α = e−∞−(−∞) = eNaN = NaN, and the NaN poisons l and a for the rest of the row. This is the same trap as the empty-state merge of F6-38. Listing 1's guard flag skips the update when m′ = −∞ (line 104); every case in R1 runs with the guard. The forensic lab shows what happens without it.



Layer 3 — the engineer's depth


One analogy sentence: a helper who keeps a whole guest's blend in her hands can serve fewer guests at once, so the tile sizes are a trade between reuse and how many helpers fit in the hall. Listing 2 is a teaching kernel: correct structure, deliberately simple, and far from a tuned FlashAttention implementation. Its reports show exactly where it is expensive.


What the compiler reports




    

  • 168 registers per thread on sm_80 (R3). One thread owns a whole query row: qr[64] and acc[64] alone are 128 values. With 32 threads per block, a block needs 5,376 registers; how many blocks fit on an SM follows from your GPU's register file size (device report, F6-07) and the occupancy calculation of F6-20. Write the number in your lab record; it will be low.
    • 

  • 16,384 bytes of shared memory: kTile and vTile, 2 × 32 × 64 × 4 bytes. This is the reuse buffer: every K and V element loaded is used by all 32 query rows of the block.
    • 

  • A 128-byte stack frame, no spills: 128 bytes is exactly float s[BC] with Bc = 32. The score loop's trip count cols is not a compile-time constant, so the compiler keeps s in local memory (F6-03); the SASS has one STL and one LDL (R4). Making cols constant for full tiles (and handling the last tile separately) would let it live in registers.
    • 



From the teaching kernel to a fast one


The published FlashAttention kernels differ from Listing 2 in ways that each address one of the reports above. D3 D7


    

  • Several threads per query row. Splitting d across lanes (or using a warp per few rows) cuts registers per thread and allows larger Br, which Layer 2 showed is what reduces K/V traffic.
    • 

  • Tensor cores for both matrix products. QKT for a tile and PV for a tile are small GEMMs; with FP16 or BF16 inputs and FP32 accumulation they map onto the MMA units of F6-26. Listing 2 does them with scalar FFMAs (458 FFMA instructions in the SASS, R4).
    • 

  • Asynchronous copies and double buffering (F6-24): load the next K/V tile while computing on the current one, instead of the two __syncthreads() per tile of Listing 2.
    • 

  • Loop order and work partitioning. FlashAttention-2 reorganises which loop is outer and how work is split between warps to reduce non-matrix work and shared-memory traffic. D7
    • 

  • Masking that skips work. With causal masking, whole tiles above the diagonal are fully masked; a production kernel does not load them at all, which removes almost half the work for long sequences.
    •

Precision and tolerances


Listing 2 keeps everything in FP32 and uses __expf, which the installed header documents as an approximation (F6-38, H1). H1 Its CPU check uses double precision on sampled rows. Production kernels use FP16 or BF16 inputs with FP32 statistics and accumulators, and the tolerance of your E12 acceptance test must be justified from those input formats (F6-25). Note that tiling changes the order of additions in l and a: tiled and unfused results agree to rounding, not bit for bit (R1: up to 1.79 × 10−7).



How the hardware actually does it


Each block of 32 threads is one warp (F1-57). The tile load spreads Bc × d = 2,048 floats per matrix over the 32 threads, consecutive threads loading consecutive floats, so the global loads are coalesced (F6-08). In the score loop all 32 threads read the same kTile[c][x] at the same time: a shared-memory broadcast, which does not cause bank conflicts (F6-11). The compiler turned these reads into 128-bit vector loads, LDS.128 (32 of them in R4), four floats per instruction. The two exponentials per tile and row (α and each p) become MUFU.EX2, the special-function unit's base-2 exponential that F6-38 saw as ex2.approx.f32 in PTX; the dot products and accumulations are FFMA fused multiply–adds; the two barriers per tile are BAR.SYNC. Worked example


One query row, d = 1, two key tiles of two keys each, to see the rescaling by hand. Scores (already scaled) s = (1, 2 | 4, 3); values v = (10, 20 | 30, 40).


    

  1. Start. m = −∞, l = 0, a = 0.
    2. 

  2. Tile 1 (s = 1, 2). m′ = 2; α = e−∞ = 0. Terms: e1−2 = 0.367879, e0 = 1. l = 0 + 1.367879 = 1.367879. a = 0 + 0.367879 × 10 + 1 × 20 = 23.678794. m = 2.
    3. 

  3. Tile 2 (s = 4, 3). m′ = 4; α = e2−4 = 0.135335. Terms: e0 = 1, e−1 = 0.367879. l = 0.135335 × 1.367879 + 1.367879 = 0.185122 + 1.367879 = 1.553001. a = 0.135335 × 23.678794 + 30 + 0.367879 × 40 = 3.204577 + 30 + 14.715178 = 47.919755.
    4. 

  4. Divide. o = 47.919755 / 1.553001 = 30.856.
    5. 

  5. Check against the unfused formula. Relative to the maximum 4: weights e−3, e−2, 1, e−1 = 0.049787, 0.135335, 1, 0.367879; sum 1.553001 (the same l). Weighted sum 0.49787 + 2.70671 + 30 + 14.71518 = 47.91976; o = 30.856. Same result, as the proof promised.
    6. 



Traffic, for the lab's size. N = 4,096, d = 64, Br = 32 (Listing 2): unfused reads 2N2 + 3Nd = 33,554,432 + 786,432 = 34,340,864 floats and writes 2N2 + Nd = 33,816,576 floats; tiled reads Nd(1 + 2N/Br) = 262,144 × 257 = 67,371,008 floats and writes 262,144. With Br = 32 = d/2, the tiled kernel reads more than the unfused chain (ratio 2Br/d = 1) but writes 129 times less, and needs no N × N buffer. Where the analogy breaks


    

  • Helpers do not each carry a whole tray. In Listing 2 a block of 32 threads shares each tray (tile) through shared memory; in faster kernels several threads share one guest. "One helper, one guest" is the teaching kernel, not the design.
    • 

  • Forgetting the scores is not free. In the kitchen, forgetting costs nothing; on the GPU, the backward pass of training needs the probabilities, so a training implementation must either store some statistics (m and l per row) or recompute scores. The forward pass in this chapter is only half of the story.
    • 

  • The trays are not read once. The story suggests every dish is carried to the table once; in fact every K and V tile is read once per query tile (Figure 2). Caches may help; the formula does not assume they do.
    •

Summary


    

  • Attention is two matrix products around a row softmax; unfused, it stores two N × N matrices.
    • 

  • The tiled forward pass keeps m, l and an unnormalised output row per query, rescales them by α = em−m′ per key tile, and divides once at the end; it is exact up to rounding.
    • 

  • Writes drop from O(N2) to O(Nd); reads remain quadratic but shrink by 2Br/d; the arithmetic is the same.
    • 

  • Fully masked tiles make α = e−∞−(−∞) = NaN unless the empty state is guarded; a l > 0 test then hides it as zeros.
    • 

  • One thread per query row is simple and register-hungry (168 registers, R3); fast kernels split rows across threads and use tensor cores.
    •

Forensic lab answer key


Observation. padded_prod (pad 40, guard 0) has 128 rows with non-finite l, 128 all-zero output rows, and a maximum difference of 0.0599 from the reference (the size of the correct outputs). NaN outputs: 0, because line 126 writes 0 whenever l > 0 is false, and comparisons with NaN are false. padded_test (pad 10) and padded_prod_fixed (pad 40, guard 1) agree with the reference to about 3 × 10−8.


Hypotheses. Overflow would depend on the input values, which are the same in all three runs; it would not depend on pad. An invalid rescale from an empty tile depends exactly on whether pad ≥ Bc, and the guard flag alone switches the failure off.


Root cause. Keys 0–31 form the first tile and all are padding (pad = 40): every score is −∞, tileMax = −∞, m′ = max(−∞, −∞) = −∞, α = e−∞−(−∞) = eNaN = NaN, and each p = e−∞−(−∞) = NaN, so l = 0·NaN + NaN = NaN and acc becomes NaN. In the next tile α = e−∞−m′ = 0, but NaN × 0 = NaN, so l and acc stay NaN for the rest of the row. Every row has the same padding, so all 128 rows fail.


Why the test passed. With pad = 10 < Bc = 32, every row sees visible keys in its first tile, so m′ is finite from the start and the empty state never meets the update.


Fix and verification. Re-enable line 104: skip the tile while m′ = −∞. Verified by padded_prod_fixed: 0 bad rows, difference 3.73 × 10−8.


Prevention. Tests with pad = 0, Bc − 1, Bc, Bc + 1 and N (fully masked rows, with a defined output); a debug counter of rows with non-finite l, reported instead of being hidden by the l > 0 test. How the evidence was produced: real runs of Listing 1 with guard 0 and 1; no GPU involved.
