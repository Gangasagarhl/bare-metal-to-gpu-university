Story hook

In the great kitchen hall, helpers have always known two kinds of "wait for each other". The row of helpers moves together step by step, so a row never needs to wait. And the helpers at one table can call "everyone stop until the whole table is done", the table barrier you met in F6-12. Nothing else existed: no word for "the four helpers at the end of the row", and certainly no way to say "the whole hall, stop".

Sofia, the new head of the morning shift, wants both. Some of her dishes need groups of four helpers; one dish needs every table in the hall to finish its sauce before anyone starts the next step. The second wish has a catch that she discovers the hard way: on a busy morning, not every table group is in the hall at once. Some wait outside for a free table. If the groups inside wait for the groups outside, and the groups outside wait for a free table, nobody ever moves again.

This chapter gives names to every group, from a few helpers to the whole hall, and shows when the whole-hall stop is safe.

What you will be able to do

  • Use the cooperative groups API: this_thread_block, tiled_partition, thread_block_tile, cg::reduce, this_grid and grid.sync().
  • Write a device-wide sum in one launch with a grid barrier, launched with cudaLaunchCooperativeKernel and a grid sized from the occupancy query.
  • Explain why a grid-wide barrier requires every block to be resident at once, and predict the hang of a hand-made barrier from a residency model.
  • Read what grid.sync() becomes in SASS and connect each instruction to the barrier algorithm in the installed header.
  • Diagnose a kernel that hangs only after an unrelated change raised its register count.
Jargon box
Cooperative groups
Simple words: a way to name a set of GPU threads and let only that set share data and wait for each other. Analogy: naming "these four helpers", "this table", "the whole hall" and giving each name its own "stop until we are all done". Precise: a CUDA C++ device API (header cooperative_groups.h, namespace cooperative_groups) whose group objects expose size(), thread_rank() and sync(), with group types for a thread block, statically sized tiles of a block, coalesced (active) threads and the whole grid. D1 H1
Thread block tile
Simple words: a fixed-size slice of a block (2, 4, …, 32 threads) that can exchange values directly. Analogy: a few neighbouring helpers in one row who pass things hand to hand. Precise: thread_block_tile<Size>, made by tiled_partition<Size>(block); the installed header allows single-warp sizes "1/2/4/8/16/32" (and, separately, 64/128/256/512 for multi-warp tiles); meta_group_rank() is the tile's index in the block, computed as the parent's thread rank divided by Size. H1
Grid group and grid barrier
Simple words: all the threads of one kernel launch, and a stop that waits for all of them. Analogy: "the whole hall, stop until every table is done". Precise: cg::grid_group from this_grid(); the header states its threads "are guaranteed to be co-resident on the same device", that the kernel "must have been launched with cuLaunchCooperativeKernel (or the CUDA Runtime equivalent)", and its sync() calls _CG_ABORT() if the group is not valid. H1
Cooperative launch
Simple words: a kernel launch that promises every block is running at the same time, or fails. Analogy: the hall manager admits the dish only if all its table groups fit at once. Precise: cudaLaunchCooperativeKernel(func, gridDim, blockDim, args, sharedMem, stream); the device must report a non-zero cudaDevAttrCooperativeLaunch, and the number of blocks "cannot exceed" the occupancy result times the SM count, otherwise the launch returns cudaErrorCooperativeLaunchTooLarge. H2 H3
Resident (block)
Simple words, analogy, precise: as in F1-56 and F6-20: a block that has been given an SM and its registers and shared memory, and stays there until it finishes. How many blocks can be resident per SM depends on the kernel's resources; cudaOccupancyMaxActiveBlocksPerMultiprocessor returns that number. H2
Deadlock (of a barrier)
Simple words: everyone waits for someone who can never arrive. Analogy: the tables inside wait for the groups outside; the groups outside wait for a free table. Precise: a state where every resident block spins at a barrier that counts blocks not yet scheduled, while the scheduler can only start them when a resident block exits; the kernel never finishes (Listing 2 shows it in a model). D2 R2
Kernel (GPU)
As in F6-01: the function every GPU thread of a launch runs; not the operating-system kernel of OS301.

Layer 1 — the kid explanation

Helpers in the hall work in groups of different sizes. A few helpers side by side can pass a spoon hand to hand. A whole row moves step by step together. A table can call "stop until the whole table is ready". Cooperative groups give every one of these groups a name, so a recipe can say exactly which group should wait.

The biggest group is the whole hall. A "whole hall, stop" only works if every table group of the dish is inside the hall at the same time. If some are still waiting at the door for a free table, the groups inside wait for them forever, and they never get a table. So the manager has a rule: a dish with a whole-hall stop is accepted only if all its groups fit inside at once.

Layer 2 — the student explanation

Groups as objects

One analogy sentence: before, the recipe could only say "my table" (__syncthreads) or rely on the row moving together; now it can name any group and hand that name to a function. Cooperative groups represent a set of threads as a C++ object with three basic members: size(), thread_rank() (my number inside the group) and sync(). D1 Listing 1 uses three of them:

  • cg::thread_block block = cg::this_thread_block(); — the block; block.sync() is the block barrier of F6-12. In the compiled SASS, the tileSum kernel's one block.sync() is its single BAR.SYNC (R4).
  • cg::thread_block_tile<32> tile = cg::tiled_partition<32>(block); — the block cut into tiles of 32. Each tile knows its index in the block, meta_group_rank(), which the installed header computes as the parent's thread_rank() / Size, and how many tiles there are, meta_group_size(). H1 Listing 3 prints the mapping for a block of 64 cut into tiles of 16: block thread 26 is in tile 1 with rank 10 (R3).
  • cg::reduce(tile, v, cg::plus<float>()) — a reduction over the tile, written once for any tile size and operator. In SASS it is five SHFL.BFLY instructions for a tile of 32 (R4): the butterfly pattern of F6-15, after which every lane holds the sum.


The value of naming groups is composability. A function that takes a thread_block_tile<16> parameter documents in its signature which threads must call it together, and the compiler knows the size. Writing __shfl_down_sync(0xffffffff, …) by hand inside a helper function instead hides an assumption ("all 32 lanes of my warp call this") that breaks as soon as someone calls the helper from divergent code or from a 16-thread sub-group. The header restricts statically sized single-warp tiles to sizes "1/2/4/8/16/32" with a static_assert, so a wrong size is a compile error, not a wrong answer. H1



The grid group and the grid barrier


F6-12 explained why an ordinary kernel cannot have a grid-wide barrier: blocks may run in any order and need not all be in the hall at once. That is the reason reductions so far needed two launches (a kernel per level) or atomics. Cooperative groups add a grid barrier, under a contract the header states explicitly: threads of a grid_group "are guaranteed to be co-resident on the same device within the same launched kernel", and to use it "the kernel must have been launched with cuLaunchCooperativeKernel (or the CUDA Runtime equivalent), and the device must support it". H1


The runtime side of the contract is in cuda_runtime_api.h: the device "must have a non-zero value for the device attribute cudaDevAttrCooperativeLaunch", and "The total number of blocks launched cannot exceed the maximum number of blocks per multiprocessor as returned by cudaOccupancyMaxActiveBlocksPerMultiprocessor … times the number of multiprocessors". H2 If you ask for more, the launch fails with cudaErrorCooperativeLaunchTooLarge (value 720 in the installed driver_types.h). H3 Listing 1's main follows the contract line by line: it reads the attribute, the SM count and the occupancy for gridSum with 256 threads, multiplies, and launches exactly that many blocks. The kernel then uses a grid-stride loop (F6-04) so that any number of elements fits any number of blocks.


What happens if you break the contract? Two different things, both bad:


    

  • An ordinary launch of a kernel that calls grid.sync(). In the installed header, grid_group::sync() begins with if (!is_valid()) { _CG_ABORT(); }, and _CG_ABORT() is defined as __trap() in device code (or assert(0)). H1 The SASS of gridSum contains the matching BPT.TRAP (R4). The kernel aborts with an error instead of hanging.
    • 

  • A hand-made grid barrier (an atomic counter plus a spin loop, written without cooperative groups) launched with too many blocks. Nothing checks anything: the blocks that are resident spin forever, waiting for blocks that can only start when a resident block exits. Listing 2 models it. With 16 slots and 20 blocks, round 1 starts 16 blocks that all wait, round 2 starts nobody, and the model reports the hang (R2). The forensic lab is this bug in a real-looking team.
    • 






When to use which group


    

  • Tiles smaller than a warp for short rows: a row of 16 values handled by a thread_block_tile<16>, two rows per warp. F6-38 uses this for short softmax rows.
    • 

  • Tiles of 32 instead of hand-written shuffles, for clarity and for the size check.
    • 

  • The block exactly as before; block.sync() and __syncthreads() are interchangeable.
    • 

  • The grid when a kernel has phases that each need all results of the previous phase, and launching one kernel per phase costs too much: iterative solvers, a reduction followed by a normalisation in one kernel, persistent kernels. Measure against the multi-launch version (with CUDA Graphs, F6-30) before choosing it: the grid size is now limited by residency, so the kernel may have fewer threads than the data would like.
    • 




Layer 3 — the engineer's depth


One analogy sentence: a whole-hall stop is a messenger who counts the tables as they report in, and every table pays for the walk. Here is what the installed toolkit actually does, and what follows for design.


How grid.sync() is implemented in this toolkit


The header cooperative_groups/details/sync.h of CUDA 12.0 contains the barrier algorithm, sync_grids. H1 Paraphrased:


    

  1. Every block first runs a block barrier (__barrier_sync(0)), so all its threads have arrived.
    2. 

  2. One thread per block (the "cta master", thread (0, 0, 0)) atomically adds to a counter in global memory: 1 for most blocks, and for block 0 the value 0x80000000 - (expected - 1). When every block has added, the sum has changed the counter's top bit.
    3. 

  3. For compute capability 7.0 and newer, the add is a PTX atom.add.release.gpu.u32 and the waiting is a loop of ld.acquire.gpu.u32 until the top bit has flipped (bar_has_flipped); older architectures use __threadfence(), atomicAdd and volatile polling.
    4. 

  4. A second block barrier releases the other threads of each block.
    5. 



The header lines quoted in this chapter, extracted by the lab's header_quotes step so that anyone can reproduce them (R7):




The SASS of gridSum for sm_80 (R4) contains each of these pieces: the extra BAR.SYNC instructions, one ATOM.E.ADD.STRONG.GPU (the release add), one LD.E.STRONG.GPU (the acquire poll), a MEMBAR.ALL.GPU and a CCTL.IVALL around them, and the BPT.TRAP of the validity check. Flipping a bit rather than resetting the counter lets the same counter serve the next barrier without a reset race.




Not verified — check before relying on this
The roles of MEMBAR.ALL.GPU and CCTL.IVALL (a memory fence and a cache invalidation that implement the release/acquire semantics in SASS) are inferred from the instruction names and the PTX in the header; NVIDIA does not document SASS semantics in detail. Check the CUDA Binary Utilities instruction-set overview and the PTX ISA memory-consistency chapter (release and acquire at .gpu scope).


Costs and consequences


    

  • Latency of one barrier. One atomic per block on a single counter, then every block polls the same address: the barrier time grows with the number of blocks and with the latency of global atomics (F6-13). It is not free, and it is not obviously cheaper than ending a kernel and launching the next one in a graph. Only a measurement on your GPU decides (Lab step 5).
    • 

  • Grid size is capped by occupancy. gridSum must be launched with SMs × resident-blocks-per-SM blocks at most. Raising the kernel's register or shared-memory use lowers the cap (R5 shows 29 registers for gridSum and 28 for tileSum on sm_80). Code that hard-codes a grid size computed once will break when the kernel changes; always query.
    • 

  • Memory visibility. After grid.sync(), writes made by any block before the barrier are visible to all blocks after it; that is what the release/acquire pair is for. Without the barrier (for example, block 0 reading partials written by others with only a flag) you need explicit fences (F6-16's decoupled look-back does exactly that). H1 D3
    • 

  • Other users of the GPU. The co-residency guarantee is about this kernel's blocks. Other kernels running concurrently (other streams, other processes, F6-37's IPC peers) reduce the free slots; the cooperative launch accounts for this by refusing or waiting, a hand-made barrier does not.
    • 

  • Multi-device groups. The header also declares a multi_grid_group, marked _CG_DEPRECATED in this toolkit. H1 Do not start new designs on it; F6-37 shows the multi-GPU tools to use instead.
    • 



Groups you have not used yet


The header also provides coalesced_threads(), the group of currently active threads of a warp (useful inside divergent branches, for example for warp-aggregated atomics in F6-17), and cluster groups for GPUs that support thread block clusters. H1 D1 Their semantics, and the compute capabilities that support clusters, are in the Programming Guide's cooperative groups chapter; this chapter's listings do not use them.



How the hardware actually does it


Every group in Figure 1 maps to a hardware mechanism you have met. Tiles up to 32 threads live inside one warp; their data exchange is the warp shuffle network that moves register values between lanes (SHFL.BFLY, SHFL.IDX in R4), and their synchronisation is a warp-level operation (WARPSYNC). The block's barrier is the SM's hardware barrier (BAR.SYNC), which is cheap because all the block's warps are on one SM (F1-57, F1-60). The grid has no hardware barrier of its own in this toolkit's implementation: it is built from global-memory atomics, memory-ordering instructions and polling (Layer 3), so it runs at the speed of the memory system and L2, not of an SM. H1 D2 Residency is decided by the block scheduler using each kernel's registers and shared memory against each SM's limits (F6-20); the occupancy API performs that calculation for you, which is why the cooperative launch rule is phrased in its terms. H2





Worked example


Size a cooperative launch and check it with the model. Suppose your GPU's device report (F6-07) gives S SMs and the occupancy query for gridSum at 256 threads returns b. Use TG-1's invented S = 4 for the arithmetic.


    

  1. Build A: the occupancy query returns b = 4. Maximum cooperative grid = 4 × 4 = 16 blocks. A grid of 16 is accepted; R2's case fits shows all 16 finishing in one round.
    2. 

  2. Fewer blocks are always fine: case small_grid (8 blocks) also finishes; the grid-stride loop gives each thread more elements.
    3. 

  3. Build B raises register use so that b = 3. The maximum becomes 12. A cooperative launch of 16 blocks now fails with cudaErrorCooperativeLaunchTooLarge (H3); Listing 1 never asks for 16, because it recomputes S × b at run time.
    4. 

  4. Elements per thread. Listing 1 sums n = 10,000,000 floats. With 16 blocks of 256 threads (4,096 threads), each thread adds ⌈10,000,000 / 4,096⌉ = 2,442 or 2,441 elements in its grid-stride loop; with 12 blocks (3,072 threads), 3,256 or 3,255. The work per thread grows as the grid shrinks; correctness does not change.
    5. 

  5. The tile reduction by hand: values 3, 1, 4, 1, 5, 9, 2, 6 in a tile of 8. Offset 4: lane 0 gets 3 + 5 = 8, lane 1 gets 1 + 9 = 10, lane 2 gets 4 + 2 = 6, lane 3 gets 1 + 6 = 7. Offset 2: lane 0 gets 8 + 6 = 14, lane 1 gets 10 + 7 = 17. Offset 1: lane 0 gets 14 + 17 = 31. R3 prints the same rows; the sum is 31.
    6.

Where the analogy breaks


    

  • There is no messenger. "The whole hall stops" suggests a person who sees all tables. In reality each block's thread 0 adds to a counter in memory and then repeatedly reads it (Layer 3); nobody watches, and if a block never arrives, nobody notices. A hang has no error message.
    • 

  • Waiting at the door is not visible. In the kitchen you could see the queue at the door. On the GPU, blocks that are not yet resident do not exist anywhere you can inspect from the kernel; the only way to know the limit is the occupancy query before launch.
    • 

  • Helpers passing things hand to hand do not pay attention to who is listening. A shuffle in a tile requires every named lane to execute it; in the kitchen, a helper can hand a spoon to a neighbour who is busy. On the GPU, a lane that is not participating makes the result undefined (F6-15).
    •

Summary


    

  • Cooperative groups name sets of threads as objects with size(), thread_rank() and sync().
    • 

  • Tiles of 1–32 threads use shuffles; cg::reduce on a tile of 32 compiles to five butterfly shuffles.
    • 

  • block.sync() is the familiar block barrier.
    • 

  • grid.sync() requires a cooperative launch and a grid no larger than SMs × resident blocks per SM; otherwise the launch fails or the kernel traps.
    • 

  • A hand-made grid barrier with too many blocks deadlocks silently.
    • 

  • In CUDA 12.0 the grid barrier is a global atomic with release/acquire ordering and polling, so it has a cost to measure.
    • 

  • Always compute the cooperative grid at run time from the occupancy query.
    •

Forensic lab answer key


Observation. Build A: 4 resident blocks per SM, 16 slots; grids of 12 and 16 finish in one round. Build B: 3 per SM, 12 slots; with a grid of 16, round 1 starts 12 blocks, all 12 wait at the barrier, 4 never start, and round 2 starts nobody. The grid size (16) and SM count (4) did not change; only the per-SM residency did.


Hypotheses. An infinite loop in the solver would also appear in build A or in the test configuration (it does not). A lock deadlock would not depend on the number of resident blocks. A barrier that cannot open is exactly what the model shows for build B, grid 16, and only there.


Root cause. The extra local variables raised register use, so fewer blocks fit per SM (4 → 3), and the slots fell from 16 to 12, below the hard-coded grid of 16. The hand-made barrier counts 16 arrivals; at most 12 blocks can ever be resident while the others wait for a slot that no waiting block will release.


Why no error. An ordinary launch has no co-residency check, and a spin loop on a counter is legal code; nothing in the runtime knows it is a barrier. (A cooperative launch would have returned cudaErrorCooperativeLaunchTooLarge, H2.)


Fix. (1) Use cg::this_grid().sync() with cudaLaunchCooperativeKernel and a grid computed from the occupancy query at run time (Listing 1). (2) Remove the grid barrier: one kernel per iteration phase, launched in sequence or captured in a CUDA Graph.


Prevention. At launch: assert grid ≤ SMs × occupancy result (or let the cooperative launch do it). In CI: attach the ptxas register report per build and a test that runs the production grid size with a timeout. How the evidence was produced: real runs of Listing 2 with the occupancy numbers of the scenario (TG-1's invented 4 SMs); no GPU was involved.
