Story hook

The old school library has a strange way of storing long reports. The shelves are numbered, and every shelf holds exactly one page-sized folder. A long report is spread over many shelves, wherever there was room. On the librarian's desk lies one big ledger with one line per shelf. Line 7 says "continued on shelf 12", line 12 says "continued on shelf 13", line 13 says "end". The catalogue card for the report names only the first shelf.

When the library was built, catalogue cards had room for eight letters and a three-letter kind. Later, students wanted long titles such as "Quarterly Report Draft". The librarian did not want to throw away the old cards, so long titles are written on extra cards placed directly in front of the old card, each one marked with a small check number that proves it belongs to the card behind it.

That ledger is the file allocation table, the cards are directory entries, and the extra cards are long-name entries. In this chapter you write a driver for the FAT32 format and prove it correct with the host's own tools, as curriculum milestone B15 asks.

What you will be able to do

  • Read a FAT32 boot sector and compute where the FATs, the data area and every cluster are, by hand and in code.
  • Follow and build cluster chains in the FAT, keeping both FAT copies and the FSInfo free count consistent.
  • Decode and write 32-byte directory entries, including long-name entries with their checksum, the 8.3 short name with a numeric tail, and packed dates and times.
  • Order the writes of create, replace and delete so that an interruption leaves only lost clusters, and verify the result with fsck.fat after 10,000 random operations.
  • Diagnose a driver whose long names are invisible to every other system, from a hex dump and an fsck.fat report.
Jargon box
FAT32
Simple words: a simple, old and very widely understood way of storing files on a disk, with a big table that links the pieces of each file. Analogy: the old library with its ledger of "continued on shelf n" lines. Precise: the 32-bit-entry variant of Microsoft's File Allocation Table file system: a boot sector with a BIOS parameter block, reserved sectors including FSInfo, one or more copies of the FAT, and a data area of clusters, where directories are ordinary cluster chains of 32-byte entries. D1
Sector and cluster
Simple words: a sector is the smallest piece the disk reads; a cluster is the piece of space the file system hands out, one or more sectors. Analogy: a page, and the folder of pages that fits one shelf. Precise: the sector is the device's addressing unit (512 bytes on the lab volume); a cluster is a run of 2n consecutive sectors in the data area, numbered from 2; file space is allocated in whole clusters. D1
BIOS parameter block (BPB)
Simple words: numbers at the start of the volume that describe its shape. Analogy: the plan of the library pinned at the entrance. Precise: fields in the boot sector (sector 0) giving bytes per sector, sectors per cluster, reserved sector count, number of FATs, total sectors, FAT size, the root directory's first cluster and the FSInfo sector, stored little-endian. D1
File allocation table (FAT)
Simple words: a table with one number per cluster saying which cluster comes next in the file, or that the cluster is free or the last one. Analogy: the ledger with one "continued on shelf n" line per shelf. Precise: an array indexed by cluster number; entry value 0 means free, a value ≥ 0x0FFFFFF8 means end of chain, other values give the next cluster; in FAT32 the top 4 bits of each 32-bit entry are reserved and must be preserved. D1
Cluster chain
Simple words: the list of clusters one file uses, linked through the FAT. Analogy: following "continued on" lines from the first shelf to "end". Precise: a linked list starting at the first cluster recorded in the directory entry and continuing through FAT entries until an end-of-chain mark. D1
Directory entry (8.3 short name)
Simple words: a 32-byte record holding a file's short name, kind, dates, first cluster and size. Analogy: the old catalogue card with eight letters and a three-letter kind. Precise: a 32-byte structure in a directory's clusters: 11 bytes of name (8 base, 3 extension, space-padded, upper case), an attribute byte, timestamps, the high and low 16 bits of the first cluster, and a 32-bit size; first byte 0xE5 marks a deleted entry and 0x00 the end of the directory. D1
Long file name (LFN) entry
Simple words: extra 32-byte records directly in front of a short-name entry that hold the real, long name. Analogy: the extra title cards in front of the old card, each with a check number. Precise: a directory entry with attribute 0x0F holding 13 UCS-2 characters, a sequence number (0x40 set on the last part, which is stored first) and a checksum of the 11-byte short name it belongs to. D1
Numeric tail
Simple words: the "~1" in a short name like README~1.TXT, added so a long name gets a unique short form. Analogy: numbering two cards that would otherwise look the same. Precise: the suffix "~n" written into the last characters of the 8-character base of a generated short name, with the smallest n that makes the name unique in its directory. D1
FSInfo sector
Simple words: a note on the volume that remembers how many clusters are free, so nobody has to count. Analogy: the "free shelves: 80,376" board at the entrance. Precise: a reserved sector, located by the BPB, with three signatures, a free-cluster count and a next-free hint; both values are hints that a driver may recompute (0xFFFFFFFF means unknown). D1
Lost cluster
Simple words: space marked as used in the FAT that no file points to. Analogy: a shelf the ledger says is taken, but no card leads to it. Precise: a cluster (or chain) whose FAT entry is non-zero but which is not reachable from any directory entry; a checker such as fsck.fat reports it and can free it or save it as a file. D3

Layer 1 — the kid explanation

A disk is a long row of numbered boxes. FAT32 groups the boxes into "clusters" and keeps a big table with one line per cluster. A line says where the file goes next, or "end", or "free". To read a file, you look up its first cluster on its card, read that cluster, then ask the table "what comes next?" until it says "end".

Directories are files too: their contents are cards. Each card has room for an old-style name of eight letters plus three. Long names are written on extra cards in front of the old one. Every extra card carries a check number made from the old card's name, so a reader can tell whether the extra cards really belong to it.

When you save a file, the order of work matters. Write the pages first, then the card, and only then throw away the old pages. If the power fails in the middle, the worst case is a few shelves that are marked "taken" but belong to no card, and a checker can find and free them.

Layer 2 — the student explanation

From the boot sector to a cluster

The boot sector holds the BPB at fixed byte offsets, little-endian. Listing 2, lines 45–52, reads the fields our driver needs: bytes per sector (offset 11), sectors per cluster (13), reserved sectors (14), number of FATs (16), total sectors (19, or 32 when the 16-bit field is 0), FAT size (22, or 36 for FAT32), the root directory cluster (44) and the FSInfo sector (48). The last two bytes of the sector must be 0x55, 0xAA. D1 From those fields everything else is arithmetic (Figure 1). Because the driver and fsck.fat -v print the same numbers for the same image, the offsets in Listing 2 agree with what mkfs.fat wrote. R3 R6



Which FAT type a volume has is decided by its cluster count, not by a name in the boot sector: the specification gives thresholds below which a volume is FAT12 or FAT16. The driver refuses volumes with fewer than 65525 clusters (line 56). D1 That is why the lab uses a 40 MiB image with one sector per cluster: a smaller image would be FAT16 by definition.

The FAT and its copies


FAT entry c lives at byte 4c of the FAT, so in sector reserved + 4c / 512 at offset 4c mod 512 (Listing 2, lines 78–83). Only the low 28 bits are a cluster number; a driver must keep the top 4 bits when it writes (line 92). Entries 0 and 1 are reserved, which is why cluster numbering starts at 2. D1 The driver writes every change to all FAT copies (line 88) so that fsck.fat, which compares them, stays quiet.


The FSInfo sector keeps a free-cluster count and a "next free" hint. Both are hints: a driver may not trust them blindly, and the specification allows 0xFFFFFFFF for "unknown" (line 61 recounts in that case). Our driver keeps them up to date after every operation (lines 382–389), and the 10,000-operation test ends with fsck.fat agreeing. D1 R8


Directory entries


A directory is a cluster chain of 32-byte entries. The first byte has two special values: 0x00 means "this and every following entry are unused" and 0xE5 means "deleted". Byte 11 is the attribute: 0x10 directory, 0x20 archive, 0x08 volume label, and the combination 0x0F marks a long-name entry. The first cluster is split into a high half at offset 20 and a low half at offset 26 (FAT32 added the high half to an older format). The size is at offset 28. D1 Listing 2, lines 121–169, decodes all of this.


Dates and times are packed into 16 bits each. The date holds year − 1980 in bits 15–9, the month in bits 8–5 and the day in bits 4–0; the time holds hours in 15–11, minutes in 10–5 and seconds divided by two in 4–0. D1 The worked example decodes one entry byte by byte and checks the result against what mdir displays.


Long names


Each long-name entry carries 13 characters in three pieces (5 + 6 + 2 UCS-2 characters, at offsets 1, 14 and 28), a sequence number in byte 0, the attribute 0x0F, and in byte 13 a checksum of the short name. The parts are stored in reverse: the entry with the highest number comes first and has 0x40 added to its sequence byte. The name ends with a 0x0000 character, and unused characters after it are 0xFFFF. D1


The checksum is a rotate-right-and-add over the 11 bytes of the stored short name (Listing 1, line 16). The run of lfn.cpp computes it step by step for README~1TXT and gets 0x6B, the same byte that mtools stored in both long-name entries of "Read me first.txt" (Figure 2). That agreement between our code and an independent implementation is the test. R1 R5




The short name is generated from the long one: upper case, characters that 8.3 names do not allow become "_", spaces and all but the last period are dropped, the base is cut to 8 and the extension to 3 characters, and when anything was lost a "~n" tail makes it unique. D1 Our driver writes long-name entries whenever the long name differs from the short one, including a difference only of case (readme.txt).


Not verified — check before relying on this
Windows and mtools store a name that differs from its short form only by lower case (such as numbers.txt) without long-name entries, using two "lower case" flag bits in byte 12 of the short entry; mdir showed numbers txt in lower case with no long name, which fits that explanation. Our driver ignores byte 12 (it lists the file as NUMBERS.TXT) and writes a long name instead. The meaning of those bits is not in the Microsoft specification as the author remembers it and was not checked; the full short-name generation rules (which characters are allowed, how a tail longer than "~9" shortens the base, what happens after "~999999") were also written from memory. Check: Microsoft FAT32 specification, sections on short-name generation; mtools documentation or source for the case bits.



Layer 3 — the engineer's depth


Write ordering without a journal


FAT32 has no journal. A create touches at least three places: data clusters, the FAT (in two copies), and the directory sector; a replace also frees an old chain; FSInfo changes as well. A crash can stop the sequence after any sector write. The only defence is the order of writes, chosen so that every prefix of the sequence leaves a volume whose damage is harmless and repairable. D2


Listing 2's rule (comment at lines 292–293): first write the data and link the new chain in the FAT, then write the directory entry that makes the file visible, last free the old chain. Check each crash point. Before the entry is written, the new chain is a lost chain: space leaks, but no name points at garbage. After the entry, before the free, the old chain is lost. The name never points at clusters that are unwritten or already given to another file, which would be the dangerous case. remove uses the mirror order: hide the name first (line 368), then free the chain. The same reasoning, with a stricter checker, is the whole subject of F3-33.


Two weaknesses remain. A long name is several entries; if a crash happens after some long-name entries but before the short entry, the directory holds orphan long-name entries, which readers ignore because no short entry follows with the right checksum. And FSInfo may be stale after a crash, which is why it is only a hint. The FAT copies can also disagree if the crash falls between the two FAT writes of line 88; fsck.fat checks the copies against each other. D3


Warning
Write ordering only works if the layers below keep the order. A write-back block cache (F3-31) that flushes dirty blocks in block-number order will write the directory sector (sector 1292 and up) after FAT sectors (32–1291) whatever order the driver used. Your kernel needs either a write-through path for these metadata writes or an explicit "flush this block now" call at each ordering point.


What the driver costs


The driver has no cache of its own, so the device counters show its raw access pattern. Reading the 23893-byte numbers.txt (47 one-sector clusters) took 98 sector reads, because every step along the chain reads a FAT sector again (line 81), though 128 consecutive entries share one FAT sector. Creating a 23 KiB file took 244 reads and 238 writes, because every fat_set reads and writes one sector per FAT copy. The stress test made 595423 sector reads and 235842 sector writes for 10000 operations. R4 R7 Put the B14 block cache under this driver and nearly all FAT reads become hits; with write-back, the FAT writes of one file collapse into a few sector writes. The ordering warning above is the price.




Allocation and fragmentation


alloc_cluster (lines 97–109) starts searching at the FSInfo "next free" hint and wraps around. This "next fit" spreads new files forward across the disk and keeps one file's clusters mostly consecutive while free space is plentiful. After many deletes the free space is scattered and new files become fragmented chains, which costs seeks on a spinning disk and extra FAT lookups everywhere. Real drivers also keep a free-cluster bitmap in memory, built at mount time, instead of scanning the FAT for every allocation. D2


Names, case and character sets


FAT names are compared without regard to case (line 190), and long names are stored as UCS-2, which our driver handles only for ASCII (line 143 turns other characters into ?). A complete driver needs a character-set conversion, a case-folding rule for non-ASCII names, and a decision on what a short name may contain on systems with different code pages. Those rules are where FAT implementations most often disagree. D1


Two more FAT32 limits matter for a modern kernel: a file's size is a 32-bit field, so a file is at most 4 GiB − 1 bytes, and there are no owners or permission bits, only a few attribute flags. A Unix-like kernel mounting FAT32 has to invent owners and modes at mount time; the VFS of F3-31 makes that a property of the vnode the driver returns. D1



How the hardware actually does it


Every structure in this chapter lives in 512-byte sectors, and the driver's BlockDev reads and writes whole sectors (lines 26–38). On a real disk the same interface is provided by a storage driver (AHCI or NVMe, Track C) through the block cache of F3-31. Two facts of real devices matter to a FAT driver. First, a sector write is the unit a device is expected to complete or not at all; a write that spans several sectors may be cut in the middle by a power failure. Second, devices and their caches may reorder writes unless the driver issues a flush or a forced-unit-access write. D2


Not verified — check before relying on this
Whether a given disk guarantees that a single 512-byte sector write is atomic, what its physical sector size is (many disks use 4096-byte physical sectors behind 512-byte logical ones), and which flush command it honours are properties of the device and were not tested in this build. Check: the disk's datasheet; the ATA command set (ACS) and NVM Express base specifications for the flush and force-unit-access commands. On a USB stick, also check how its controller handles power loss: this build did not test any physical medium.


Flash media (USB sticks, SD cards) are where FAT32 lives today. Their controllers translate logical sectors to flash pages internally and erase in large blocks; a FAT driver sees none of that, but frequent rewrites of the same FAT and FSInfo sectors are exactly the pattern those controllers must spread out. D2

Where the analogy breaks


    

  • A library ledger is one book; the FAT is stored twice and can disagree. The second copy exists so that a damaged first copy can be repaired, but nothing keeps the copies equal except the driver writing both. A ledger has no such failure mode.
    • 

  • Extra title cards are tied to their card by position and a check number, not by being stapled. A long-name entry is a separate record. If the short entry is changed without updating the long-name entries, or the checksum is computed differently, every reader silently drops the long name. The analogy suggests a sturdier link than exists.
    • 

  • Shelves in a library are fixed; clusters have no owner field. A cluster does not say which file it belongs to. Only by walking every chain from every directory entry can a checker tell a lost cluster from a used one, which is why fsck.fat reads the whole tree.
    • 




Common mistakes and debugging


    

  • Symptom: files written by your driver show only short names on other systems. Cause: wrong checksum, wrong part order (the 0x40 part must come first), or characters at the wrong offsets. How to find it: dump the directory sector and compare with entries mtools wrote for a similar name; run fsck.fat -n. Fix: compare your checksum with the step table of lfn.cpp.
    • 

  • Symptom: fsck.fat reports differences between the FATs. Cause: only FAT 1 updated. Fix: write every copy (line 88).
    • 

  • Symptom: large files read back with garbage after 64 KiB of clusters. Cause: the high 16 bits of the first cluster (offset 20) ignored, a FAT16 habit. Fix: combine both halves (line 155).
    • 

  • Symptom: a chain loop makes cat hang. Cause: a corrupt FAT where an entry points back into its own chain. How to find it: bound the walk by the file size in clusters, as line 216 does with data.size() < e->size. Fix: report corruption instead of looping.
    • 

  • Symptom: after many creates, new names land in garbage entries. Cause: a newly allocated directory cluster was not zeroed. Fix: zero it before linking it (lines 257–259).
    • 

  • Symptom: fsck.fat reports a "free cluster summary wrong". Cause: FSInfo not updated after an allocation or free. Fix: write FSInfo at the end of every operation, or set it to 0xFFFFFFFF ("unknown") while the volume is mounted and correct it at unmount.
    •

Summary


    

  • A FAT32 volume is reserved sectors (boot sector with BPB, FSInfo), two FAT copies and a data area of clusters numbered from 2; every position follows from the BPB by arithmetic.
    • 

  • The FAT is an array of 28-bit "next cluster" values; a file is a chain starting at the cluster in its directory entry.
    • 

  • Directory entries are 32 bytes: an 8.3 name, attributes, packed dates and times, the first cluster in two halves, and the size.
    • 

  • Long names are stored backwards in extra entries tied to the short entry only by a checksum; a wrong checksum hides every long name.
    • 

  • Without a journal, write order is the only crash protection: data, then entry, then free the old chain.
    • 

  • The host's mtools and fsck.fat are the acceptance judges; the driver passed 10,000 random operations with fsck.fat clean.
    • 

  • An uncached driver re-reads FAT sectors constantly; the B14 cache fixes the cost but must respect the write order.
    •

The fix is a flush of the data and FAT blocks before the directory write.

Forensic lab answer key


Root cause. The cleanup changed line 16 of fat_names.h from a rotate-right-and-add to sum = static_cast<std::uint8_t>((sum << 1) + c);, a shift left. The checksum is used in both directions: when writing long-name entries and when attaching read long-name entries to a short entry. Every other implementation computes the rotation.


Evidence. Kernel side: its own two files show long names, the host-made "Read me first.txt" does not. Host side: the host-made file shows its long name, the two kernel-made files do not. That symmetry rules out a writing-only bug. The dump shows checksum byte 0x5C in both long-name entries of "Quarterly Report Draft.txt" (bytes 128 and 160, offset 13), while lfn.cpp computes 0x6E for QUARTE~1TXT; the host-made entries for "Read me first.txt" (bytes 32 and 64) carry 0x6B, which the changed driver rejects. fsck.fat names the problem exactly: "Wrong checksum for long file name".


Wrong hypotheses. Reversed part order: the dump shows the 0x42 part first, then 0x01, which is correct, and it would not explain why the kernel cannot read the host's names. Wrong character offsets: the dump shows the characters at offsets 1, 3, 5 … and the checker could read the full long name (it prints it). Case-only names: all three names are lossy and need long names anyway.


Fix and prevention. Restore the rotation. Prevention: a test vector from an independent implementation (the 0x6B that mtools wrote for README~1TXT) in the unit tests, and a round-trip test through the host tools on every commit, which is acceptance test 1 of B15. How the fault was made: the lab script applies the one-line change with sed to a copy of fat_names.h, builds the tool with the same flags and runs it on a fresh image.
