Story hook

The school office has a window, and only requests on the office's own forms are accepted there. Pupils rarely fill in those forms themselves. They talk to the receptionist in the hall: "copy this list, sort it, and give the first two names to Class 5B." The receptionist knows which forms to fill in, in which order, which pupil does each step, and how to pass the papers from one helper to the next. When the job is done she writes on the board whether it worked.

A new school across town wants to use the same helpers and the same requests, but its office window takes different forms. Nobody rewrites the helpers. The new school only prints its own version of the forms with the same headings, so that a request written for one office works at the other.

The receptionist is the shell. The forms with the same headings everywhere are the C library, and the part that differs from office to office is its system-call layer. This chapter builds both and tests them the way curriculum milestone B18 and the course's practical exam ask: a scripted session over the serial line must match a reference transcript, and one C program must print the same output on different C libraries.

What you will be able to do

  • Implement a shell that runs pipelines and redirections with fork, execvp, pipe, dup2, open, close and waitpid, and explain why cd and exit must be built in.
  • Structure a C library into a portable part, a system-call layer and start-up code, and port it by replacing only the system-call layer, shown for Linux on x86-64 and on AArch64.
  • Measure what a C library does underneath a program with a system-call trace, and explain output buffering.
  • Run a scripted serial session against a reference transcript, and avoid the timing trap of feeding input before the prompt.
  • Diagnose a pipeline that never ends from process states and open descriptors.
Jargon box
Userland (user space)
Simple words: all the programs that run outside the kernel: shells, tools, libraries. Analogy: the pupils and helpers in the hall, outside the office. Precise: code running in the processor's unprivileged mode in process address spaces, reaching the kernel only through system calls. D1
Shell
Simple words: a program that reads commands you type and runs other programs for you. Analogy: the receptionist who turns spoken requests into forms and helpers. Precise: a command interpreter that parses command lines, creates processes for commands, connects their standard input and output to files and pipes, and reports exit statuses; the POSIX shell language defines its grammar. D2
Pipeline (shell)
Simple words: several commands joined by |, each one's output feeding the next one's input. Analogy: helpers passing papers along a row. Precise: a sequence of commands run as concurrent processes, where the standard output of each is connected by a pipe to the standard input of the next; its exit status is the last command's. D2
Redirection
Simple words: making a program read from or write to a file instead of the keyboard or screen. Analogy: telling a helper "take your papers from this folder". Precise: shell syntax (<, >, >>) that opens a file and installs it as descriptor 0 or 1 of the command with dup2 before exec. D2
Built-in command
Simple words: a command the shell does itself instead of starting a program. Analogy: the receptionist moving her own desk. Precise: a command executed inside the shell process, required when it must change the shell's own state (current directory, exit, variables). D2
Exit status
Simple words: the number a program gives back when it ends: 0 for success, other values for problems. Analogy: the tick or cross on the board. Precise: the value passed to exit, collected by the parent with waitpid; the shell stores the last one in $?, uses 127 for "command not found" and 128 + n for death by signal n. D2
C library (libc)
Simple words: the standard set of functions every C program can call, like printf and strlen, plus the code that talks to the kernel for them. Analogy: the school's standard forms. Precise: the implementation of the ISO C standard library (and usually POSIX interfaces), consisting of portable code, a system-call layer for one kernel and architecture, start-up code that calls main, and headers. D3 D2
System-call layer (sysdeps)
Simple words: the small part of a C library that knows how to ask one particular kernel for things. Analogy: the office-specific version of the forms. Precise: the functions that load system-call numbers and arguments into the registers a kernel and architecture expect, execute the trap instruction and convert results and errors; porting a library to a new OS means writing this layer. D4
Start-up code (crt0, _start)
Simple words: the first code that runs in a program, before main. Analogy: the receptionist opening the folder and handing out the first page. Precise: the entry point the kernel jumps to; it reads the argument count, argument and environment pointers from the initial stack as the ABI defines, initialises the library and calls exit(main(argc, argv)). D5
Output buffering
Simple words: collecting output in memory and writing it in bigger pieces. Analogy: collecting slips and taking them to the office in one trip. Precise: the C library's stdio buffer for each stream, flushed when full, at a newline (line-buffered, the usual mode for terminals), or only when full or at exit (fully buffered, the usual mode for files and pipes). D3
Reference transcript
Simple words: a saved, known-correct record of a session that a new run must match exactly. Analogy: the answer sheet for the practical exam. Precise: an expected output file, produced independently of the system under test, compared byte for byte with the captured output of a scripted session. C1

Layer 1 — the kid explanation

When you type sort fruit.txt | head -n 2, the shell does not sort anything itself. It makes a tube (a pipe), makes two copies of itself, and turns one copy into sort with its output going into the tube, the other into head with its input coming from the tube. Then it waits for both to finish and remembers whether the last one worked.

Some commands cannot be done by a copy. If a copy changed its folder with cd, only the copy would move, and it ends at once. So the shell does cd itself.

Every program the shell runs uses the C library: printf to print, strlen to count letters. Most of the library does not care which kernel it runs on. Only a small corner knows the kernel's "forms": which number means "write" and which instruction knocks on the kernel's door. To move all your programs to your own kernel, you rewrite that corner and keep the rest.

Layer 2 — the student explanation

The shell's loop

A shell repeats four steps: read a line, split it into words and operators (Listing 1), group the words into pipelines of commands, and run each pipeline (Listing 2, lines 49–80). For each command it calls fork; the child sets up its descriptors and calls execvp, which searches the directories of PATH for the program and replaces the child's image with it; the parent records the child's process id. When every command of the pipeline has been started, the parent waits for all of them and keeps the last one's status as $?. D2 D1

The shell needs only nine C library calls (comment at the top of Listing 2), which is why the curriculum makes a shell the first real user program on a new kernel: if your C library port provides those nine and your kernel implements the system calls under them, every external command works.

Wiring a pipeline

For each command except the last, the shell creates a pipe before the fork. In the child, dup2(prev_read, 0) makes the previous pipe's read end the standard input and dup2(fds[1], 1) makes the new pipe's write end the standard output; then the child closes the original descriptors, because the copies on 0 and 1 are all it needs (lines 61–62). In the parent, the write end is closed immediately and the read end is kept only until the next command has been forked (lines 71–72). dup2 works because, as F3-31 showed, it makes a second descriptor for the same open-file description. D2

Redirection uses the same tool: open the file, dup2 it onto 0 or 1, close the original (lines 18–32). The order inside the child matters: pipe wiring first, then redirections, so that cmd > file | next sends cmd's output to the file, as in POSIX shells.

Built-ins and statuses

cd must run in the shell process: a child's chdir would change only the child's current directory, which disappears when the child exits. The same holds for exit and for setting variables. Listing 2 implements cd and exit (lines 34–47). D2 If execvp returns at all, it failed; the child prints a message and exits with 127, the status shells use for "command not found". A child killed by a signal gets status 128 + the signal number (line 78). D2

What a C library is made of


A C library has four parts. Headers declare the standard interface. Portable code implements most functions in plain C: string functions, formatting, the stdio buffers, sorting, character classes, much of the maths library. The system-call layer turns operations such as "write these bytes to descriptor 1" into a trap into a particular kernel on a particular processor. Start-up code receives control from the kernel, finds argc and argv where the ABI says they are, initialises the library and calls main. D3 D4 Real libraries meant for porting (the curriculum names mlibc, newlib and musl) collect the system-call layer into a documented set of functions; mlibc calls them sysdeps. C1


tlibc, the teaching library of this chapter, has exactly that shape in about 300 lines: four headers, tlibc.cc (Listing 3) and one system-call file per port (Listings 4 and 5), each with two functions and the _start code. Layer 3 — the engineer's depth


The system-call ABI is a contract


Listings 4 and 5 each make two system calls, and every detail is fixed by the kernel's ABI for that processor. On Linux x86-64 the number goes in rax, arguments in rdi, rsi, rdx (then r10, r8, r9), the instruction is syscall, the result comes back in rax, and the instruction itself overwrites rcx and r11, so the inline assembly must declare them clobbered. On Linux AArch64 the number goes in x8, arguments in x0–x5, the instruction is svc #0, the result is in x0. The numbers differ: write is 1 on x86-64 and 64 on AArch64. Errors come back as small negative numbers (−4095 to −1), which a full library turns into −1 and errno. D4 D5


Not verified — check before relying on this
The register conventions, the system-call numbers and the error range were written from memory. In this build they are confirmed only for the two calls used, by the programs producing the right output and exit status R4 R5 and by strace naming the calls R6. The AArch64 build ran under QEMU's user-mode emulation, not on Arm hardware. Check: the Linux kernel's system-call tables for x86-64 and arm64, the System V AMD64 psABI and the AAPCS64, and the syscall(2) manual page.


Your kernel's ABI is your decision (F3-29, and OS402 chapter F3-50 discusses the choice in depth). Whatever you choose, write it down once and generate both the kernel's dispatch table and the library's system-call layer from that one description, so they cannot drift apart.


Start-up: what the kernel must hand over


The System V ABI defines the initial process stack: at the stack pointer, argc; above it the argv pointers ending with a null pointer, then the environment pointers ending with a null pointer, then the auxiliary vector (pairs of type and value, for example where the program headers are), and above all that the strings themselves. D5 The _start code of Listings 4 and 5 passes the initial stack pointer to tlibc_start, which reads argc and argv from it (Listing 3, lines 142–147). On x86-64 it also aligns the stack to 16 bytes before the call, because the ABI requires that alignment at every call and compilers rely on it for vector instructions.


So your kernel's exec (B13, F3-30) must build exactly this layout if you want to use an existing libc without changing its start-up code. The ctest: argc = 1 line of the test program checks the simplest part of the contract on every port.


Buffering: the same output, different system calls


The outputs of glibc and tlibc are identical, but the work underneath is not. The lab traces both programs with output redirected to a file:




glibc made one write for nine lines, because standard output to a file is fully buffered and is flushed once at exit; tlibc made nine, because it flushes at every newline (Listing 3, line 33). glibc also made about 20 kinds of calls before main (memory mapping of itself, thread-local storage setup, security features); tlibc made none. R6 D3


Buffering is invisible until processes are involved. A shell that calls fork with unflushed data in its stdout buffer gives the child a copy of that buffer, and both may write it: the output appears twice. Listing 2 calls fflush(stdout) before every fork (line 58) for that reason. The same applies to your kernel: a C library that keeps a buffer must flush it before fork, or document that the program must.

How the hardware actually does it


Every line of the scripted session crosses the serial port twice: the harness's bytes go into the UART's receive register (or FIFO) and the kernel reads them by polling the line status register; the kernel's output goes out the transmit register one byte at a time. On the PC this is the 16550-compatible UART at COM1 that the kernel has used since OS302; QEMU emulates it and connects it to its standard input and output with -serial stdio. R7 On a spare PC the same session runs over a real serial cable or a USB serial adapter to the computer that runs the harness, with both sides set to the same speed and format.


For the C library, the hardware contract is the trap instruction and the registers it uses. syscall on x86-64 jumps to the kernel entry point stored in a model-specific register and switches privilege; svc #0 on AArch64 raises a synchronous exception to EL1 that the kernel's vector table handles. F3-29 set this up for x86-64 in your kernel; the library only has to execute the instruction with the registers the kernel expects. D6 D4


Not verified — check before relying on this
Untested on hardware. No serial session ran over a real cable in this build, and the AArch64 library ran only under qemu-aarch64. Where the analogy breaks


    

  • A receptionist hands work to helpers; a shell copies itself. fork makes a complete copy of the shell, open descriptors and buffers included, and only then does exec turn the copy into the helper. Everything the copy inherited and did not close stays with the helper, which is the cause of this chapter's forensic bug and the duplicated-output bug of Layer 3.
    • 

  • Forms with the same headings are all a program needs; a library port needs more than the same function names. The ABI below the names also has to match: the start-up stack layout, structure layouts in headers, error codes and the meaning of each system call. Two "forms" can look the same and still mean different things.
    • 

  • A request slip goes to the office once; a printf may not reach the kernel at all yet. Output waits in the library's buffer until a newline, a full buffer or exit, and a crash before that loses it.
    • 




Common mistakes and debugging


    

  • Symptom: a pipeline never finishes. Cause: a write end still open in the shell or in a later child. How to find it: while it hangs, list each process's descriptors and their access modes. Fix: close every pipe end you do not use, in parent and child (Listing 2, lines 62 and 71–72).
    • 

  • Symptom: output printed before a command appears twice. Cause: unflushed stdio buffer copied by fork. Fix: flush before fork (line 58); use _exit in a child that fails to exec.
    • 

  • Symptom: cd has no effect. Cause: run as an external command or in a child. Fix: a built-in (lines 34–47).
    • 

  • Symptom: a ported program crashes before main on your kernel. Cause: the initial stack does not match the ABI (missing null pointers, no auxiliary vector, wrong alignment). How to find it: dump the first 32 words at the initial stack pointer from the kernel. Fix: build the System V layout in exec.
    • 

  • Symptom: scripted serial transcript differs in the first command only (elp instead of help). Cause: input sent before the kernel was ready R9. Fix: wait for the prompt before each line, as serial_session.py does.
    • 

  • Symptom: transcripts differ only by carriage returns. Cause: the serial console sends CR LF. Fix: normalise line ends in the harness, never in the reference.
    •

Summary


    

  • A shell reads a line, parses it, and for each command forks, wires descriptors with pipe, dup2 and close, and execs; it waits for all and keeps the last status.
    • 

  • cd and exit must be built in, because they change the shell process itself.
    • 

  • End of file in a pipeline needs every copy of the write end closed, in the shell and in every child.
    • 

  • A C library is headers, portable code, a system-call layer and start-up code; a port replaces only the system-call layer (and start-up code if the ABI differs).
    • 

  • The system-call ABI (numbers, registers, trap instruction, initial stack) is a contract between your kernel and every program.
    • 

  • Buffering changes how many system calls a program makes and must be flushed before fork.
    • 

  • Scripted serial sessions must wait for the prompt; references must be generated independently of the system under test.
    •

Forensic lab answer key


Root cause. The refactor changed line 72 of Listing 2 from if (!last) { close(fds[1]); prev_read = fds[0]; } to if (!last) { prev_read = fds[0]; }. The shell never closes its copy of the pipe's write end.


Evidence. The snapshot shows the shell and wc, both asleep (S); cat has already finished and been reaped (the shell waits for its children in order). The transcript has only "start": wc printed nothing because it is still reading. In the descriptor lists, the pipe that is wc's standard input (0->pipe:[N](read)) has two write ends open: descriptor 4 in minish and descriptor 4 in wc itself, both (write). With writers ≥ 1, wc's read blocks instead of returning end of file, and the shell blocks in waitpid for wc: neither can make progress, and "end" is never printed.


Why wc holds a write end. Because the parent kept descriptor 4 open, the second fork copied it into wc's child, and the child code (line 61) only rewires descriptor 0 and closes prev_read; it has no reason to know about descriptor 4. So closing the write end only in the shell after both forks would not be enough: wc would still hold its own copy. The parent must close it before the next fork, as the original line did.


Wrong hypotheses. "cat is stuck": it does not appear in the process list; it finished. "The file is empty or missing": cat would then exit at once and wc would still need end of file; the hang does not depend on the file. "A pipe buffer is full": three short lines cannot fill a pipe, and the blocked side is the reader, not a writer.


Fix and prevention. Restore close(fds[1]) in the parent before the next fork. Prevention: a test that runs pipelines of 2, 3 and 8 stages under a short time limit, and a debug mode in which every child prints its open descriptors before exec and the test fails on any descriptor above 2. How the fault was made: run.sh applies the one-line change to a copy of minish.cc with sed, builds it with the same flags, runs it in the background on the three lines, and takes the snapshot from ps and /proc/<pid>/fd and fdinfo after two seconds.
