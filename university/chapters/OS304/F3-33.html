Story hook

The new library building has several floors, and every floor is organised the same way. Near the stairs hangs a chart with one square per shelf on that floor: shaded means taken, white means free. Next to it is a second chart for the drawer of record cards. Each record card describes one book: who may borrow it, how many pages it has, and the shelf numbers where its pages are. Very long books have so many shelves that the card only names a "list shelf", where a sheet of further shelf numbers is kept.

The catalogue at the entrance is separate from the cards. It maps titles to card numbers and nothing else. Two titles may even lead to the same card.

One evening the lights went out while Kenji, the library assistant, was putting away a new report. The next morning nobody checked the charts, and a second report was shelved. A week later the head librarian found two record cards that both claimed the same shelves. In this chapter you build the system of charts and cards, called ext2, and then you find out what Kenji did in the wrong order.

What you will be able to do

  • Locate any inode, bitmap and data block of an ext2 volume from its superblock and group descriptors, and check the result against dumpe2fs and debugfs.
  • Map a file offset to a disk block through direct, single-indirect and double-indirect pointers, and compute how many metadata blocks a file needs.
  • Implement create, replace, unlink and mkdir in an order that leaves only leaks after a power cut, and prove it with a simulated power cut and e2fsck.
  • Diagnose a multiply-claimed-blocks report from e2fsck back to the order of bitmap and inode updates (the course's forensic lab "fsck is angry").
  • Compare ext2's design with NTFS's master file table and journal, from reading.
Jargon box
ext2
Simple words: the "second extended file system", the classic Linux disk format, built from inodes, bitmaps and block groups. Analogy: the many-floored library with charts and record cards. Precise: a block-based file system whose volume is divided into block groups, each with a block bitmap, an inode bitmap and an inode table; files are inodes with block pointers, and directories map names to inode numbers. D1 D2
Superblock
Simple words: the block that describes the whole volume: its size, block size and how many things are free. Analogy: the plan at the entrance of the building. Precise: a 1024-byte structure at byte offset 1024 of the volume (with backup copies in some groups) holding counts, sizes, the magic number 0xEF53, feature flags and state. D1
Block group and group descriptor
Simple words: a slice of the disk with its own maps and its own inodes, and the small record that says where those maps are. Analogy: one floor, with its own charts and drawer, and the floor directory at the entrance. Precise: a run of blocks_per_group consecutive blocks; the group descriptor table, in the block(s) after the superblock, gives each group's block-bitmap, inode-bitmap and inode-table locations and its free counts. D1
Inode
Simple words: the record of one file: its type, permissions, size, times and where its blocks are, but not its name. Analogy: the record card in the drawer. Precise: a fixed-size entry in an inode table, addressed by inode number (counting from 1), with mode, owner, size, timestamps, link count and an array of 15 block pointers: 12 direct, one single-, one double- and one triple-indirect. D1 D3
Indirect block
Simple words: a block that holds block numbers instead of file data, for files too large for the inode's own list. Analogy: the "list shelf" with a sheet of further shelf numbers. Precise: a block of 32-bit block numbers (block size / 4 of them); a single-indirect block maps data blocks, a double-indirect block maps single-indirect blocks, and so on. D1
Bitmap (block bitmap, inode bitmap)
Simple words: a row of bits, one per block or inode, saying used (1) or free (0). Analogy: the shaded-square charts by the stairs. Precise: one block per group whose bit i records whether block (or inode) i of that group is allocated; the allocator searches them and the free counts in the group descriptor and superblock summarise them. D1
Directory entry (ext2)
Simple words: a record in a directory that links a name to an inode number. Analogy: a line in the catalogue: title → card number. Precise: a variable-length record with inode number, record length, name length, file type (with the filetype feature) and the name; record lengths chain the entries through each directory block, and deleting merges a record into its predecessor. D1
Hard link and link count
Simple words: a second name for the same file, and the counter of how many names a file has. Analogy: two catalogue lines leading to one card. Precise: any directory entry naming an inode; the inode's i_links_count counts them (a directory counts its name, its own "." and every child's ".."), and the inode and its blocks are freed only when the count reaches 0 and no process has it open. D3 D2
fsck (e2fsck)
Simple words: a program that reads the whole file system and checks that all its records agree. Analogy: the head librarian comparing every card with the charts. Precise: the ext2/3/4 checker of e2fsprogs; in passes it checks inodes and their blocks, directory structure, connectivity, reference counts and group summaries against each other, and repairs or (with -n) only reports differences. D4
Crash consistency
Simple words: making sure that a power cut in the middle of an update leaves the disk in a state that is still safe to use or easy to repair. Analogy: shelving in an order that leaves at worst a shaded square with no book, never two cards for one shelf. Precise: the property that every prefix of a file system's write sequence leaves a state from which the invariants can be restored without losing or exposing data, achieved by write ordering, journaling or copy-on-write. D2

Layer 1 — the kid explanation

ext2 splits the disk into floors called block groups. Each floor has two charts and a drawer. One chart says which blocks are taken, the other which record cards are taken, and the drawer holds the cards, called inodes. An inode knows everything about a file except its name: size, owner, permissions and the list of blocks. A directory is a file whose contents are lines of "name → inode number".

Saving a file means changing several things: the block chart, the blocks themselves, the card chart, the card, and the directory line. If the power fails halfway, some changes are on the disk and some are not. The trick is to choose an order where the half-done state is never dangerous. Mark the blocks as taken first. If the power fails then, you have wasted some blocks, and the checker can give them back. If you write the name first and the chart last, a power cut can leave a file whose blocks look free, and the next file will be written over it.

Layer 2 — the student explanation

Superblock and group descriptors

The superblock is always at byte 1024 of the volume, whatever the block size (Listing 2, line 42). Its magic number at offset 56 is 0xEF53. It holds the inode and block counts (offsets 0 and 4), the free counts (12, 16), the first data block (20), the block size as a shift of 1024 (24), blocks and inodes per group (32, 40), and in revision 1 the first usable inode (84), the inode size (88) and three sets of feature flags (92, 96, 100). D1 Our driver prints what it read, and the numbers agree with dumpe2fs (Figure 1):



Feature flags come in three classes. A compatible feature can be ignored safely. An incompatible feature changes the format so that a driver that does not know it must refuse to mount. A read-only compatible feature may be ignored for reading but not for writing. D1 Listing 2, line 57, accepts only the incompatible feature filetype and the read-only-compatible features sparse_super and large_file, the set that mke2fs -t ext2 produced here. Our driver writes, so it must refuse anything else; that is why it refuses ext4 volumes, which use extents instead of block pointers.


The group descriptor table starts in the block after the one holding the superblock, one 32-byte descriptor per group with the locations of the group's two bitmaps and inode table and its free counts (lines 61–65). D1


Finding an inode


Inodes are numbered from 1. Inode n is in group (n − 1) / inodes_per_group, at index (n − 1) mod inodes_per_group in that group's table (line 99). Inodes 1 to 10 are reserved; inode 2 is the root directory, and the first ordinary inode (here 11) is usually lost+found. D1 The listing above shows exactly that: / is inode 2 and lost+found inode 11. The worked example finds an inode on the disk by hand.


The inode's 15 block pointers (offset 40) map file block i: blocks 0 to 11 directly, the next block size / 4 blocks through the single-indirect block, then the double-indirect, then the triple-indirect (lines 132–153). With 1 KiB blocks one indirect block holds 256 numbers, so a file larger than 12 + 256 = 268 KiB needs the double-indirect block. The stress test writes files of 270000 to 299999 bytes in 5 % of its writes for that reason. D1 Note the unit trap: the inode's i_blocks field counts 512-byte units, not file-system blocks (line 127), which is why debugfs showed "Blockcount: 42" for a file of 21 blocks.


Directories


A directory's blocks hold variable-length records: inode number (4 bytes), record length (2), name length (1), file type (1) and the name, padded to a multiple of 4 (Listing 2, lines 378–420). The record lengths of one block always add up to the block size, so a reader steps from record to record by rec_len. To delete, the driver adds the record's length to its predecessor's, which makes it invisible; a record at the start of a block instead gets inode 0 (lines 435–436). To insert, it looks for a record whose rec_len is larger than it needs and splits it (lines 397–400). D1 Names are compared byte for byte; ext2 is case-sensitive, unlike FAT (line 212).


Allocation


Allocating a block means finding a 0 bit in a block bitmap, setting it, and decrementing the free counts in the group descriptor and the superblock (lines 317–334). Allocating an inode does the same with the inode bitmap (lines 265–285). Our driver searches from the start of group 0. Real ext2 tries to place a file's blocks in the same group as its inode, and a new directory in a group with many free inodes, so that related data stays close together, an idea from the BSD Fast File System's cylinder groups. Layer 3 — the engineer's depth


The invariants e2fsck checks


A file system is a set of redundant records that must agree. For ext2 the main invariants are: (1) a block is marked in the block bitmap if and only if exactly one inode refers to it, as data or as an indirect block; (2) an inode is marked in the inode bitmap if and only if it is in use (non-zero links or mode, no deletion time); (3) an inode's link count equals the number of directory entries naming it; (4) the free counts in each group descriptor and in the superblock equal the counts of 0 bits; (5) every directory is reachable from the root, with consistent "." and "..". e2fsck's five passes check these in turn: inodes and their blocks, directory structure, connectivity, reference counts, group summaries. D4 D2


Violations of these invariants are not equally bad. A block marked used that no inode uses is a leak: space is lost, no data is wrong. An inode that uses a block marked free is a time bomb: the next allocation hands the block to another file, and two files then share it; whichever writes last wins, and the other file's contents are silently replaced. D2 The whole design question of crash consistency is how to make every crash produce only the first kind.


Ordering rules for ext2 without a journal


Classic ext2 had no ordering guarantee at all: it wrote metadata through the buffer cache in whatever order the cache flushed it and relied on e2fsck after every unclean shutdown. D2 A driver can do better with three rules, which the BSD "soft updates" work stated generally: never point to a structure before it has been initialised; never reuse a resource before every pointer to it has been removed; never remove the old pointer to a live resource before the new pointer is set. D5 Applied to a file create (Listing 2, lines 461–478):


    

  1. Mark the blocks used in the bitmap (and update the counts). A cut here leaks blocks.
    2. 

  2. Write data and indirect blocks. A cut here leaks blocks.
    3. 

  3. Allocate the inode in the inode bitmap, then write the inode. A cut here leaks blocks and an inode.
    4. 

  4. Add the directory entry. Only now is the file visible, and everything it points to is initialised and marked.
    5. 



A replace (lines 469–473) writes the new blocks, switches the inode to them, and only then frees the old blocks: a cut leaves the old file intact or the new one complete, plus leaks. Unlink runs the other way (lines 517–523): remove the name, mark the inode deleted, then free its blocks and the inode. D5 The lab's power-cut harness tests rule 1 directly; the forensic lab shows what happens without it.


Warning
The order of a driver's writes reaches the disk only if nothing below reorders them. The write-back cache of F3-31 does reorder (it flushes in block-number order), and so may a disk's own write cache. In your kernel, the ordering points above need a cache flush of the earlier blocks and, on real hardware, a device flush command, or the order is fiction. D2


From ordering to journaling


Ordering has two costs: many synchronous writes, and a full e2fsck after a crash to reclaim leaks, which reads every inode and grows with the size of the disk. ext3 added a journal to ext2's format: each update is first written as a transaction to a log, followed by a commit record, and only then to its home locations; after a crash the log is replayed, so recovery time depends on the log's size, not the disk's. In ordered mode, data blocks are written before the metadata transaction that refers to them commits, which gives the same guarantee as rule 1 without leaks. D2 Journaling is the subject of OS401; this chapter's harness, which logs every write and cuts at any point, is the tool you will reuse there.


Reading: NTFS


NTFS, the default Windows file system, makes different choices for the same problems. Everything on an NTFS volume is a file, including its own metadata: the master file table (MFT) is a file of fixed-size records, one or more per file, and the bitmap of clusters, the log and the volume information are files with reserved MFT records. A file's record holds a list of attributes: its names, standard information (times, flags), security, and its data. A small file's data can be stored inside the MFT record itself (a resident attribute); a large file's data is described by runs (start cluster, length), similar to extents, instead of per-block pointers. Directories are B+ trees of names, not linear lists. Metadata changes are journaled in a log file, so a crash is repaired by replaying the log. D6 D7 D3


Compare with ext2: the inode table and bitmaps are fixed regions created by mke2fs, while NTFS's MFT and bitmap are files that can grow; ext2 maps each block, NTFS maps runs; ext2 relies on ordering and e2fsck, NTFS on a journal. ext4 later moved ext2's descendants towards NTFS's choices on two of these points (extents and a journal). D3 D2

How the hardware actually does it


ext2's block size (1 KiB here, set by mke2fs -b 1024) is a file-system choice; the device still transfers sectors. A 1 KiB block is two 512-byte sectors, so even one block write is a multi-sector write that a power cut could, in principle, split. ext2 has no checksum to detect a torn block; ext4 added metadata checksums partly for such cases. D2 Larger blocks (4 KiB is the usual choice on large volumes) mean fewer indirect blocks and smaller bitmaps relative to the volume, at the cost of wasted space at the end of small files.


Block groups were designed for spinning disks, where keeping a file's inode, its blocks and its directory close together reduces head movement. On flash storage the physical placement is decided by the device's translation layer, and the groups matter mainly for keeping each bitmap to one block and allowing parallel allocation. D2 D3

Problem 3: largest file with double indirection. 12 + 256 + 256 × 256 = 12 + 256 + 65536 = 65804 blocks of 1 KiB, a little over 64 MiB, plus 1 + 1 + 256 = 258 metadata blocks in the worst case. Where the analogy breaks


    

  • A shaded square and a book on a shelf are one physical fact; a bitmap bit and a block's use are two separate records. In a library you can look at the shelf to see if it is taken. On a disk, "this block belongs to inode 15" is written only in inode 15's pointers; the bitmap is a second copy of that fact, and the two can disagree after a crash.
    • 

  • Two catalogue lines to one card is unusual in a library; in ext2 it is normal. Hard links make names and files many-to-one, and every directory has at least two names (its entry and its "."), so "the file's name" is not a property of the file at all.
    • 

  • Floors of a library are fixed; block groups are a performance hint. Nothing in the format forces a file's blocks to be in its inode's group. The analogy suggests a rule where there is only a placement preference.
    • 




Common mistakes and debugging


    

  • Symptom: e2fsck pass 1 reports a wrong i_blocks value for your files. Cause: i_blocks filled in file-system blocks instead of 512-byte units. Fix: multiply by block size / 512 (line 374).
    • 

  • Symptom: "Free blocks count wrong for group #0". Cause: bitmap changed but descriptor or superblock count not, or the other way round. Fix: change all three together (lines 329–333).
    • 

  • Symptom: large files read back wrong from 268 KiB on. Cause: double-indirect index arithmetic (i / p versus i % p). How to find it: write a file of exactly 12 + 256 + 1 blocks and compare debugfs stat with your map. Fix: lines 144–150 and 357–361.
    • 

  • Symptom: after deleting a file, a directory listing loops or shows garbage. Cause: the record was zeroed instead of merged, or rec_len became 0. Fix: merge into the predecessor (line 435); readers must stop on rec_len < 8.
    • 

  • Symptom: e2fsck reports "Multiply-claimed blocks" after a crash test. Cause: the block bitmap is written after the inode or directory entry (the forensic lab). Fix: the order of Layer 3.
    • 

  • Symptom: after mkdir, e2fsck pass 4 reports a wrong link count for the parent directory. Cause: the parent's link count not incremented for the child's "..". Fix: lines 503–505.
    • 




Transition box

Where you came from: F3-32 wrote FAT32, where a file is a chain in one table and names live in the same entry as the size and first cluster. What carries over: the block-device and cache interfaces, write ordering as the only crash defence, the host's checker as the judge, and the reference-model stress test. What changes: names and files are separated (directory entries point to inodes, and several names may share one), allocation state is kept twice (in pointers and in bitmaps, plus counts), and the checker is strict enough to tell a harmless leak from a dangerous double claim, so the order of the bitmap update becomes visible. C1 What comes next: F3-34 leaves storage for communication between processes: pipes, shared memory and events, where the same question "what may the other side see, and when?" returns as synchronisation.

Summary


    

  • ext2 divides a volume into block groups, each with a block bitmap, an inode bitmap and an inode table; the superblock at byte 1024 and the group descriptors locate them.
    • 

  • An inode holds everything about a file except its name, and maps file blocks through 12 direct, one single-, one double- and one triple-indirect pointer.
    • 

  • Directories are variable-length records of (inode, record length, name length, type, name); names point to inodes, and several names can point to one.
    • 

  • Allocation state is redundant: pointers, bitmaps and counts must agree, and e2fsck checks that they do.
    • 

  • A leak (marked but unused) is harmless; a block used but marked free will be given out again and silently shared.
    • 

  • Safe order without a journal: mark, write, point; and when freeing, unpoint before unmarking. Caches below must keep that order.
    • 

  • NTFS (reading) chooses differently: metadata as files in the MFT, run lists, B+ tree directories and a journal.
    •

  1. Group = (20000 − 1) / 8192 = 2 (integer division: 19999 / 8192 = 2.44). Index = 19999 − 2 × 8192 = 3615. Inode table: 8192 × 256 / 4096 = 512 blocks per group.
    2. 

  2. 4096 / 4 = 1024 pointers per indirect block, so 12 + 1024 = 1036 blocks of 4 KiB = 4243456 bytes (about 4 MiB) before the double-indirect block is needed.
    3. 

  3. Only (b). (a) and (c) are leaks: space or an inode is lost until e2fsck reclaims it, but no data is wrong. In (b) the allocator will give the block to another file, and two files will share it.
    4. 

  4. Good answers say: finding a free block from the inodes alone would mean reading every inode and every indirect block on each allocation; the bitmap is a summary that makes allocation a search of one block per group. The price is redundancy that must be kept consistent.
    5. 

  5. Add the new entry in /b first (and increase the link count while both names exist), then remove the entry in /a. A crash between them leaves the file with two names, which e2fsck sees as a link-count mismatch at worst; the opposite order could leave the file with no name, an orphan that ends in lost+found.
    6. 

  6. 20 data blocks (20480 / 1024) plus 1 indirect block (12 direct, 8 through the indirect) = 21 file-system blocks of 1024 bytes = 42 units of 512 bytes. A common wrong answer is "42 blocks": the field counts sectors.
    7. 

  7. A read-only-compatible feature changes structures that writes must maintain (for example a checksum or an index); a driver that writes without knowing it leaves them stale and corrupts the volume for drivers that do know it. Reading does not change them, so ignoring the feature is safe for a reader.
    8. 

  8. With cut = 3, writes 1–3 reach the disk: the block bitmap, the group descriptor and the superblock. Everything else is lost. Prediction: e2fsck reports "Block bitmap differences: −(282--302)" and wrong free-block counts, a leak only. Run it and compare; your output is the answer.
    9. 

  9. A journal makes a group of writes atomic: after a crash it is replayed or discarded as a whole, so there are no leaks and no full scan; recovery time depends on the journal size. The cost is writing metadata (and in some modes data) twice, and the journal's own space and commit ordering.

Forensic lab answer key


Root cause. The cleanup moved step 1 of write_file, mark_blocks(blocks, true), from before the data to after add_entry (and, for replaces, after the inode write). The bitmap update became the last write of the operation instead of the first.


Evidence. In the harness log, writes 1–21 are the data and indirect blocks, 22–24 the inode bitmap with its descriptor and superblock, 25 the inode table block 69 (inode 15), 26 the directory block 100. The cut fell after 26, so the block bitmap (66), its descriptor and the superblock were lost. Run 2 read a bitmap in which 282–302 were free, picked them again for report-b, and overwrote report-a's data: "0 of them still 'A'". debugfs shows inodes 15 and 16 with identical block maps, and e2fsck Pass 1B reports the 21 blocks as multiply claimed by inodes 15 and 16.


Wrong hypotheses. (a) The harness: with Listing 2's driver, the same harness and the same cut give only a leak (below), so the harness is not the cause. (b) The team's driver differs from Listing 2 only in the position of three lines; without a cut it marks exactly the same blocks, only later, so a plain allocator bug is not the explanation (the 10,000-operation stress test passed with Listing 2's allocator). (c) is the cause.


The team's objection. Before the cleanup, the same harness with Listing 2's order lost the superblock, the inode and the directory entry R12, and e2fsck reported R13:






"−(282--302)" means "marked in the bitmap, used by no inode": a leak, which e2fsck repairs by clearing the bits; the same holds for inode 15 and the count. Both reports have exit code 4 with -n, but only the new one describes lost data.


Fix and prevention. Restore the order: bitmap and counts first, data, inode, name last; for replaces, free the old blocks only after the inode points to the new ones. Prevention: run the harness for every cut point in the per-commit suite and fail on any e2fsck report other than bitmap differences and counts (Extension 1). How the fault was made: run.sh copies ext2.cc and moves three lines with a short Python script (the moved lines are the ones with the comments "1) block bitmap and counts" and "4) the name"), then builds it with the same flags.
