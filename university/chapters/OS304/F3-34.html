Story hook

Each class in Amara's school has its own room, and nobody may walk into another class's room. That keeps lessons calm, but sometimes classes must work together. Class 4A writes questions, 4B checks them and 4C prints the quiz.

The caretaker installs a message tube between neighbouring rooms. 4A pushes paper slips in at one end, 4B takes them out at the other, in the same order. The tube holds only so many slips: when it is full, 4A has to wait; when it is empty, 4B waits. For bigger jobs, the caretaker mounts one whiteboard in the wall between two rooms, visible from both sides. Both classes can write on it, so they agree on a signal: 4A rings a bell when the board is ready, and 4B rings another bell when it has copied the board and 4A may wipe it.

One week the caretaker "optimised" the bells: he rang only when the tube had been empty. On Thursday, two pupils in 4B were waiting at the tube, only one heard the bell, and the whole school stood still. This chapter builds the tube (pipe), the shared board (shared memory) and the bells (events), and then finds the caretaker's mistake.

What you will be able to do

  • Implement a kernel pipe object: a ring buffer with a lock and two wait queues, blocking and non-blocking modes, end of file and broken-pipe errors, and reference-counted ends.
  • Map one set of physical frames into two processes and coordinate them with events, without lost or reordered data.
  • Build a wait-for-multiple primitive and compare it with poll.
  • Reason about lost wake-ups with the rule "every waiter that might proceed must be woken", and diagnose one from a watchdog report and a diff.
  • Write a short design for signals or an alternative, as milestone B17 requires.
Jargon box
Inter-process communication (IPC)
Simple words: any way for separate programs to pass data or signals to each other. Analogy: the tubes, boards and bells between closed classrooms. Precise: the kernel mechanisms that let processes with separate address spaces exchange data or synchronise: pipes, shared memory, message queues, sockets, events and signals. D1
Pipe
Simple words: a one-way channel of bytes: one program writes at one end, another reads at the other. Analogy: the message tube between two classrooms. Precise: a kernel object holding a bounded byte buffer, with a read end and a write end exposed as file descriptors; reads block while it is empty and writes block while it is full, and closing all write ends gives readers end of file. D2 D1
Wait queue
Simple words: the list of threads sleeping until something happens to an object. Analogy: pupils waiting at the tube for the bell. Precise: a kernel list of blocked threads attached to an object and a condition; the code that changes the condition wakes some or all of them, and each woken thread re-checks the condition under the object's lock. D1
Shared memory (between processes)
Simple words: memory that two programs can both see, so a value one writes the other can read. Analogy: the whiteboard in the wall between two rooms. Precise: physical frames mapped into the page tables of two or more processes (possibly at different virtual addresses), created anonymously and inherited across fork, or named and opened by each process. D2 D1
Event (synchronisation object)
Simple words: a kernel flag that one thread sets and another waits for. Analogy: the bell. Precise: a waitable object with a signalled state; with auto-reset, one waiting thread is released and the event is cleared; with manual reset, all waiters are released and it stays signalled until reset. D3
Semaphore
Simple words: a counter you can wait on: waiting takes one unit or sleeps until there is one; posting adds one. Analogy: a bowl of tokens by the door. Precise: a non-negative integer with atomic wait (decrement, blocking at zero) and post (increment, waking a waiter); a semaphore with values 0 and 1 used across processes behaves as an auto-reset event. D1 D2
Wait for multiple objects
Simple words: one call that sleeps until any one of several things is ready. Analogy: a teacher waiting for whichever of three bells rings first. Precise: a primitive that blocks a thread on a set of waitable objects and returns which became signalled (Windows WaitForMultipleObjects; on POSIX, poll or select over file descriptors). D3 D2
Lost wake-up
Simple words: a bug where a thread sleeps forever because the signal that should have woken it went to someone else or came before it slept. Analogy: only one of two waiting pupils hears the bell. Precise: a synchronisation failure in which a state change that allows a blocked thread to proceed does not wake it, because the wake-up was skipped, delivered to another thread, or raced with the decision to sleep. D1
Signal (POSIX)
Simple words: a small numbered notice the kernel delivers to a process, interrupting what it is doing. Analogy: a knock on the classroom door during a lesson. Precise: an asynchronous notification identified by a number (for example SIGPIPE, SIGINT), delivered by running a registered handler, ignoring it or taking a default action such as terminating the process. D2

Layer 1 — the kid explanation

Programs are kept apart on purpose: each has its own memory, so one program's mistake cannot spoil another's work. When they must cooperate, the kernel offers safe doors between them.

A pipe is a tube for bytes. One program pushes bytes in, another takes them out, in the same order. The tube has a fixed size. If it is full, the writer sleeps until there is room. If it is empty, the reader sleeps until something arrives. When the writer closes its end and the tube is empty, the reader learns "that's all".

Shared memory is faster: the kernel lets two programs see the same piece of memory. Nothing is copied, but now both can write at the same time, so they need a way to take turns. An event is that way: a bell. One program rings it when it has finished writing; the other sleeps until it rings.

The hardest part is the sleeping and waking. A program that sleeps must be woken by whoever makes its wish come true. If the waking is skipped even once, it can sleep forever.

Layer 2 — the student explanation

Pipe semantics

POSIX fixes what programs may rely on. A read from a pipe returns the bytes available, up to the amount asked for, and blocks only when the pipe is empty. When the pipe is empty and no process holds a write end open, read returns 0, which is end of file. A blocking write waits until all its bytes are in the pipe. A write when no read end is open fails with EPIPE, and the process also receives the signal SIGPIPE, whose default action ends it. With O_NONBLOCK, calls that would block fail with EAGAIN instead (or a write returns the part it managed). D2

Two of these rules surprise people. First, a reader asking for 32 bytes gets 11 if 11 are there; programs must loop (write_all in Listing 2 does the same for writes). Second, end of file depends on every write end being closed, including the copies a fork made. A process that forgets to close its copy of the write end keeps the reader waiting forever, which is the forensic lab of F3-35.

The pipe as a kernel object


In your kernel a pipe is a VFS object (F3-31): pipe() allocates one pipe object and two open-file descriptions, one with read access and one with write access, and installs them in the two lowest free descriptors. Each description holds a reference to the pipe and the pipe counts how many descriptions of each kind exist. dup and fork add descriptor references to an existing description, so the pipe's counts change only when a description's last descriptor closes (Listing 2 of F3-31, line 153). That is the moment to decrement writers and wake the readers so they can see end of file (Listing 1, line 62). D1 D2


Shared memory


Shared memory reuses paging from OS302: the kernel allocates frames for a shared-memory object and enters them in the page tables of every process that maps it. Anonymous shared mappings created with MAP_SHARED survive fork as shared (unlike private mappings, which become copy-on-write), which is how Listings 2 and 3 give four and two processes one result record and one slot. Named objects (shm_open on POSIX, section objects on Windows) let unrelated processes find the same frames. The object is freed when the last mapping and the last handle are gone, so it needs a reference count like the pipe. D2 D3


Shared memory transfers nothing by itself: there is no "data arrived" notification and no ordering. That is why it always comes with a synchronisation object. In Listing 3 the objects are two POSIX semaphores placed inside the shared page itself with sem_init(…, 1, …), where 1 means "shared between processes". D2


Events and waiting for many


Windows offers events as kernel objects: an auto-reset event releases one waiter and clears itself; a manual-reset event releases every waiter and stays set until reset. Any waitable object (events, processes, threads, semaphores, mutexes) can be passed to WaitForMultipleObjects, which returns when one (or all) of them is signalled. D3 POSIX has no general event object; a semaphore with values 0 and 1 behaves like an auto-reset event, and waiting for many is done on file descriptors with poll. Linux adds file-descriptor-based events (eventfd) so that they too can be passed to poll. D2

Layer 3 — the engineer's depth


The wake-up rule


Every blocking kernel object follows one pattern: take the object's lock; while the condition does not hold, sleep on a wait queue (which releases the lock atomically with going to sleep); when woken, take the lock again and re-check. The code that changes the state must wake the queue. Listing 1, lines 24–30 and 45–50, is this pattern with std::condition_variable standing for a kernel wait queue. D1


Two mistakes break it. The first is checking the condition outside the lock, or releasing the lock before going to sleep: a wake-up that happens in the gap is lost, because the thread was not yet on the queue. Kernels avoid this by putting the thread on the queue and marking it "about to sleep" before releasing the lock, so a wake-up in the gap turns the sleep into a no-op. The second mistake is waking too few. The precise rule: after a state change, every waiter that might now be able to proceed must be woken, or some other mechanism must guarantee it will be. Waking everyone (notify_all) is always correct and costs extra context switches; waking one is correct only if any one waiter can consume the whole change and will pass the wake-up on if it does not. D1


The forensic lab is a real-looking "optimisation" that violates the second rule. Its symptom is typical of lost wake-ups: no crash and no error, only a system where the work stops and every thread is asleep or finished.


Shared memory on real CPUs


Listing 3 writes the slot in one process and reads it in another without any lock around the slot. It is correct because the semaphore operations do more than count: a post and the wait it releases form a synchronisation point, and the memory model guarantees that writes made before the post are visible after the wait. On x86 the hardware already keeps stores in order relative to each other, but the compiler does not; on ARM even the hardware may reorder. The semaphore implementation contains the barriers that make both behave. D4 D1 If you build your own events in shared memory, use atomic operations with acquire and release ordering, not plain variables.


Speed is the reason to use shared memory. The B17 handoff test passes one 8-byte number per round trip, so the time is almost all synchronisation: two semaphore operations and, whenever a side must sleep, a system call and a context switch. Inside a wait for multiple


A wait for several objects cannot use one wait queue, because the waiting thread must be on every object's queue at once and must be removed from all of them when any one fires. Windows' design, which Listing 4 copies, is a wait block per (thread, object) pair, linked into the object's list, plus one global "dispatcher" lock that protects every object's state and every wait block. D3 set walks the object's wait blocks, wakes the first thread that has not fired yet, and for an auto-reset event stops there; if nobody is waiting, the event stays signalled for the next waiter (lines 27–37). wait_any checks for an already signalled object first, then hooks wait blocks into all objects, sleeps, and unhooks from all of them before returning (lines 46–63).


The single lock makes the design simple and correct at the cost of contention on many CPUs; modern kernels split such locks. poll in Linux takes another approach: each file's poll operation adds the caller to that file's own wait queue and reports readiness, and the caller sleeps until any queue wakes it, then asks every file again. D2 The model ran 60,000 wake-ups through three auto-reset events with every one counted, which checks that no signal was lost or delivered twice.


Signals as a topic (a design to write)


Milestone B17 asks for a written design for signals "or an alternative". POSIX signals interrupt a thread at an arbitrary point to run a handler on its stack, which forces the kernel to build a signal frame on the user stack, restore the interrupted state with a special return call, decide which thread of a process receives a signal, define which system calls restart after a handler, and restrict what a handler may call. D2 An alternative used by some systems is to turn asynchronous notifications into messages: an exception or notification port that a thread reads like any other IPC object, so no code ever runs at an unexpected point. A design document for your kernel should state which events need delivery (child exit, broken pipe, keyboard interrupt, faults), how each reaches the process, and what happens to a blocked system call. C1



How the hardware actually does it


Three pieces of hardware make IPC work. Paging makes shared memory possible: two page-table entries in two address spaces point to one frame. Atomic instructions (on x86, instructions with the lock prefix such as compare-and-exchange) make the counter of a semaphore and the state of an event update correctly when two CPUs touch them at once. Cache coherence makes a store by one CPU eventually visible to the others without software flushing caches; the memory-ordering rules of the architecture say in which order. D4


On a single CPU, as in the early kernel of OS302, "atomic" can be had by disabling interrupts around the update; with SMP (OS303) the kernel needs spinlocks around each object, and the waiting itself must go through the scheduler: a sleeping thread is removed from the run queue and put on the object's wait queue, and waking it means putting it back and perhaps sending an inter-processor interrupt to the CPU that should run it. D1

Where the analogy breaks


    

  • A tube between rooms has one sender and one receiver; a pipe end can be held by many processes. After fork, parent and child both hold both ends. The tube picture hides the most common pipe bug: an end that stays open in a process nobody thought about.
    • 

  • A bell is heard by everyone in earshot; a kernel wake-up goes exactly where the code sends it. If the code wakes one waiter, the others hear nothing. "Ring the bell" sounds like a broadcast, and the forensic lab's bug is the gap between the two.
    • 

  • A whiteboard shows what is written as soon as it is written; shared memory does not promise that order. Without the barriers inside the synchronisation objects, another CPU may see writes late or in a different order. The board in the wall is more orderly than real memory.
    • 




Common mistakes and debugging


    

  • Symptom: a pipeline never finishes; the last stage waits for end of file. Cause: a write end still open in some process (often the parent or a sibling). How to find it: list each process's open descriptors (/proc/<pid>/fd on Linux, your kernel's ps extension) and look for the pipe's write end. Fix: every process closes every end it does not use, right after fork.
    • 

  • Symptom: threads asleep, data in the buffer, no progress. Cause: a lost wake-up. How to find it: a watchdog that prints each object's count and sleepers (Listing 1, lines 66–71 and 95–111). Fix: wake every waiter that might proceed; re-check conditions in a loop.
    • 

  • Symptom: data arrives corrupted or interleaved when several processes write to one pipe. Cause: large writes from different writers are not atomic. Fix: keep each message at most PIPE_BUF bytes, or use one writer per pipe.
    • 

  • Symptom: shared-memory consumer occasionally reads an old value. Cause: a hand-made flag in shared memory without atomic operations or barriers. Fix: use the kernel's semaphores or events, or atomics with release (writer) and acquire (reader) ordering.
    • 

  • Symptom: a process dies silently when the reader of its output exits. Cause: SIGPIPE's default action. Fix: handle or ignore SIGPIPE and treat EPIPE as an error, if the process should continue.
    • 

  • Symptom: after many test runs the system runs out of memory. Cause: shared-memory objects or pipes never freed because a reference count never reached zero. Fix: count descriptions and mappings; test with the B13 "memory statistics return to baseline" method.
    •

Summary


    

  • A pipe is a kernel object with a bounded ring buffer, a lock, two wait queues and counts of open ends; its ends are ordinary file descriptions.
    • 

  • Reads return what is available; end of file needs every write end closed; writing with no reader gives EPIPE and SIGPIPE.
    • 

  • Shared memory maps one set of frames into several page tables; it moves data without copies but needs synchronisation for both notification and ordering.
    • 

  • Events release one (auto-reset) or all (manual reset) waiters; a wait for multiple needs one wait block per object and a lock covering them all.
    • 

  • The wake-up rule: after a state change, wake every waiter that might proceed, and always re-check the condition after waking.
    • 

  • Lost wake-ups do not crash; they stop progress. A watchdog that prints object states turns them into diagnosable failures.
    • 

  • Signals are a design topic: asynchronous delivery is costly to get right, and message-based alternatives exist.
    •

Answers to Check yourself


    

  1. 10: a read returns what is there, up to the amount asked. With an empty pipe and no writers, 0 (end of file). A common wrong answer is "it blocks until 100 bytes arrive".
    2. 

  2. Readers asleep on an empty pipe are waiting for data or end of file; closing the last write end creates end of file, a state change they must see. Without the wake-up they sleep forever.
    3. 

  3. Good answers mention: another thread may have taken the data between the wake-up and the moment this thread got the lock; some wake-ups are spurious; with notify_all several threads wake for one change. The condition, not the wake-up, says whether to proceed.

  4. With empty = 0 and full = 0, both processes wait forever at their first sem_wait: deadlock. With both at 1, the consumer runs first and reads slot 0 before any write, so the check of line 34 counts a lost or out-of-order number (and the two can overlap on the slot).

Forensic lab answer key


Root cause. The second change: readable_.notify_all() after every chunk became if (was_empty) readable_.notify_one(). With two readers asleep on an empty pipe, the writer's first chunk wakes only one of them. Before that reader runs, the writer adds more chunks; the pipe is no longer empty, so nobody else is woken. The other reader stays asleep although data is waiting. One worker then does all the reading until it has its 100000 records and returns; it never closes its end, so readers stays 2. The writer fills the pipe and sleeps; the second worker is still asleep from long ago. Nobody will ever wake either of them.


Evidence. The watchdog report: "8192 of 8192 bytes used, readers 2 (asleep 1), writers 1 (asleep 1)": a full pipe with a sleeping reader is impossible if every write wakes the readers. The moved bytes (12706944 in the run shown, varying by run) are more than one worker's 6400000 and less than the 12800000 total: one worker finished, the other stopped early.


The other two changes. if (sleeping_writers_ > 0) writable_.notify_all() is harmless here: sleeping_writers_ is read under the same lock that writers hold while incrementing it before they sleep, so no writer can be about to sleep unseen. Pipe jobs(8192) only changes timing. To answer the colleague, apply each change alone and run the test. The lab script does exactly that, three runs per change R7:




Only change 1 hangs, in every run; the buffer size alone passes every run. A larger buffer lets the writer add more chunks between wake-ups, which may make the hang show sooner, but it is not the cause.


Why other tests passed. The semantics tests are single-threaded, and the pipeline has exactly one reader per pipe: with one reader, "wake one when it was empty" happens to satisfy the rule.


Fix and prevention. Restore notify_all after each chunk (or keep "only when it was empty" but wake all readers then, and make a reader that leaves data behind wake the next one). Prevention: keep the multi-reader test with the watchdog in the per-commit suite, and review wake-up changes against the written rule.
