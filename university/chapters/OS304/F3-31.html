Story hook

Rosa's school has more than one library. The main library is upstairs, the science room keeps its own shelf of lab manuals, and on the first day of term a box of books arrives with the new principal before any shelf is built. Students should not need to know where a book lives. They write the title on one request slip and hand it to the front desk. The desk knows that anything starting with "science/" goes to the science room and everything else to the main library.

The librarian at the desk also keeps a trolley of books that were asked for recently. Most requests are for the same few books, so most requests are answered from the trolley without walking to the shelves. Notes that students add to a book are written into the copy on the trolley; the shelves are updated later, in one trip.

That desk is the virtual file system, the box of first-day books is the initial RAM disk, and the trolley is the block cache. In this chapter you build all three in a small kernel and test them the way curriculum milestone B14 asks.

What you will be able to do

  • Explain the layers between a read system call and a disk block: descriptor, open-file description, vnode, file system, block cache, block device.
  • Implement a VFS with a mount table, path lookup that crosses mount points and handles .., and per-process file descriptors with dup.
  • Parse a USTAR archive given to the kernel as a Multiboot module and serve it as a read-only file system.
  • Build and test a block cache with LRU replacement and write-back against a reference model, and compare write-back with write-through by counting disk writes.
  • Diagnose a block cache that loses data from the history of one block.
Jargon box
Virtual file system (VFS)
Simple words: the part of the kernel that offers one set of file operations and passes each request to the right file system. Analogy: the front desk that sends each request slip to the right library. Precise: a kernel layer that defines file-system-independent objects (mounted file systems, vnodes or inodes, directory-entry caches, open files) and an operations interface each concrete file system implements; system calls such as open and read are written once against it. D3 D1
Vnode
Simple words: the kernel's record for one file or directory, the same shape whatever file system it lives on. Analogy: the desk's index card for a book, which names the library that holds it. Precise: an in-memory object representing one file-system object, holding its type, size, permissions and a pointer to an operations table supplied by its file system (Linux calls the equivalent object an inode; the name vnode comes from the BSD and SunOS tradition). D3 D2
Mount, mount point
Simple words: attaching one file system into the tree of another, at a directory. Analogy: a door from the main library into the science room's shelf. Precise: an entry in the kernel's mount table binding the root of a file system to a directory (the mount point) of an already mounted one; path lookup that reaches the mount point continues in the mounted root. D3 D1
File descriptor and open-file description
Simple words: the small number a program uses for an open file, and the kernel record behind it that remembers the current position. Analogy: a numbered ticket in your hand, and the desk's note of how far you have read. Precise: a per-process index into a descriptor table; each entry points to an open-file description holding the offset and access mode; dup and fork create descriptors that share one description and therefore one offset. D4 D1
Initial RAM disk (initrd)
Simple words: a packed set of files that the boot loader puts into memory next to the kernel, so the kernel has files before it has disk drivers. Analogy: the box of books that arrives with the principal on the first day. Precise: an archive or file-system image loaded into memory by the boot loader (here as a Multiboot module) and mounted by the kernel, usually as its first root file system. D5 C1
USTAR
Simple words: a standard way of packing files one after another, each with a 512-byte label in front. Analogy: books packed in the box, each with a label card on top. Precise: the "ustar" interchange format of the POSIX pax utility: a sequence of 512-byte header blocks, each followed by the file's data padded to whole 512-byte blocks, ended by blocks of zeros. D4
Block device
Simple words: a device you read and write in fixed-size pieces by number, like a disk. Analogy: the shelves, where books sit at numbered places. Precise: a device whose interface transfers whole blocks addressed by block number, with no notion of files; file systems are built on top of it. D1
Block cache (buffer cache)
Simple words: copies of recently used disk blocks kept in memory, so most reads and writes do not touch the disk. Analogy: the librarian's trolley of recently used books. Precise: a kernel cache of block-device blocks indexed by (device, block number), with a replacement policy such as least recently used and a write policy (write-through or write-back with a sync operation). D2 D1
Write-back and write-through
Simple words: write-back saves a change to the disk later; write-through saves it at once. Analogy: notes added to the trolley copy now and taken to the shelves on the next trip, or carried to the shelves immediately. Precise: in write-through every write to a cached block is also written to the device before the operation completes; in write-back the cached block is marked dirty and written when it is evicted or when a sync is requested. D2 D1
LRU (least recently used)
Simple words: when the cache is full, throw out the block nobody has used for the longest time. Analogy: the book at the bottom of the trolley pile goes back to the shelf first. Precise: a replacement policy that evicts the entry whose last access is oldest, commonly kept as a list ordered by access time. D1

The idea in pictures

Figure 1 is the map of this chapter: one read call travels down through five layers. The top two belong to the process; the middle one is the VFS; the bottom two belong to a file system that keeps its data on a block device. A RAM-disk file system such as the initrd skips the bottom layers, because its data is already in memory.

Figure 2 shows the one piece of the VFS that surprises most people: path lookup walks a stack of directories, and a mount point is a directory whose contents are hidden by the root of another file system. The path /sys/../etc/hostname goes into the infofs and back out again.

Layer 1 — the kid explanation

A program wants a file. It does not know whether the file is on a disk, inside the box that came with the kernel, or made up on the spot. So it asks the kernel's front desk with a name such as /etc/motd. The desk reads the name piece by piece. At each piece it asks the library that owns that part of the tree: "do you have something called etc?" When the answer is a door to another library, the desk walks through the door.

When the file is found, the program gets a ticket number. Every later request uses the ticket, not the name. The desk remembers how far along the file each ticket has read. Two tickets can share one bookmark, which is how a shell later passes an open file to a program.

Libraries that keep books on far-away shelves are slow. So the librarian keeps a trolley of recently used shelf pieces next to the desk. Changes go into the trolley copy first. A full trolley sends its oldest piece back to the shelf. If that piece had changes, they must be carried back; if the librarian forgets, the changes are lost. The forensic lab of this chapter is about exactly that.

Layer 2 — the student explanation

Four kinds of object

A VFS separates what all file systems share from what each one does differently. The shared part is a small set of objects. Mounted file systems are recorded in a mount table. Each file or directory that is in use has a vnode (Linux: inode) with its type, size and mode and a pointer to an operations table. Each open creates an open-file description holding the vnode and the current offset. Each process has a descriptor table whose entries point to open-file descriptions. D3 D1 D2

Linux adds a fifth object, the directory entry (dentry), which caches the result of looking up one name in one directory, including negative results ("no such name"), so that repeated lookups of the same path do not ask the file system again. The kernel of this chapter has no dentry cache; every lookup calls the file system. D3

The operations interface

Listing 1 (vfs.h) is the whole contract between the VFS and a file system in this kernel: three functions. lookup finds a name in a directory and returns its vnode, read copies bytes from an offset, and readdir returns the n-th entry of a directory. Real VFS interfaces have dozens of operations (create, unlink, rename, truncate, permissions, extended attributes, memory mapping); the principle is the same. D3 The two file systems of the kernel, tarfs and infofs, fill in the table differently: tarfs returns slices of the archive, infofs builds text when the file is read. The VFS code never tests which one it is talking to.

Descriptors, descriptions and dup

POSIX distinguishes the file descriptor (a small integer, per process) from the open-file description (the kernel object with the offset and status flags). dup makes a new descriptor that refers to the same description; reading through either descriptor advances the shared offset. D4 The boot run shows it: five bytes through descriptor 0 give "Welco", five bytes through its duplicate, descriptor 1, give "me to". The shell of F3-35 depends on this sharing for redirection, and fork creates the same kind of sharing between parent and child. R2



The run also shows the error contract the VFS gives to system calls: -ENOENT for a missing name, -ENOTDIR when a file is used as a directory, -EISDIR for read on a directory, -EBADF for a closed descriptor and -EMFILE when the table is full after 16 descriptors. The names are the POSIX error names; the numbers are this kernel's own (kbase.h), since a kernel chooses its own error numbering and the C library translates (F3-35). D4 R2


The initial RAM disk


A kernel needs files before it has disk drivers: the first user program, configuration, perhaps the drivers themselves. The boot loader solves this by loading a file next to the kernel. With the Multiboot protocol, the loader passes such files as modules: the information structure has a flag bit saying the module fields are valid, a module count and the address of an array whose entries give each module's start and end address. D5 QEMU's built-in Multiboot loader, started with -kernel, loads the file named by -initrd as such a module. D6 The boot run prints what the kernel received: initrd: 20480 bytes at 0x116000. R2


The content of the module is a USTAR archive, the format the curriculum names for B14. C1 Each member starts with a 512-byte header holding its name, mode, size and type as ASCII fields (numbers in octal), followed by its data rounded up to whole 512-byte blocks; the archive ends with blocks of zeros. D4 Because the data sits in memory already, tarfs never copies a file: a vnode's data pointer points into the archive.




The block cache


Disk file systems read and write whole blocks. A block cache keeps recently used blocks in memory, looked up by block number. Bach's description of the UNIX buffer cache is the classic one: a hash table finds a buffer by (device, block), a free list ordered by use chooses the victim, and a "delayed write" flag marks buffers whose contents must reach the disk before the buffer is reused. D2 Listing 5 is that design in about 100 lines of host C++: an unordered_map for the hash table, a std::list as the LRU list, a dirty flag per buffer and a sync that writes all dirty buffers in block order.


Write-through is simpler: every write goes straight to the device, so a crash loses nothing that was written. Write-back is faster when the same block is written several times before it is evicted, and it lets the cache sort and merge writes. Its price is that the cache, not the disk, holds the truth for a while; F3-32 and F3-33 show what that means when the power fails in the middle of an update. D1 D2



Layer 3 — the engineer's depth


Path lookup in detail


Path lookup is the hottest code in most VFS implementations, and the source of many security bugs. Listing 2 does it in four rules. (1) Every path in this kernel is absolute; a real kernel also starts from the process's current directory for relative paths and from its root directory (which chroot can change) for absolute ones. (2) Components are separated by any number of slashes. (3) . is skipped; .. pops one level, never above the root. (4) After every successful lookup the result passes through cross_mounts, which follows the mounted pointer of a directory to the root of the file system mounted on it. D3


Rule 3 is subtle at mount points. If .. asked the file system for its parent, the root of infofs would answer "myself", because infofs knows nothing of where it is mounted. Linux handles this by recording, for each mount, the mount point it covers, and stepping across it when .. is applied at a mounted root. D3 Listing 2 gets the same effect with less code: the walked directories are on a stack, so .. returns to wherever the walk came from (Figure 2). The price: a path that names a file and then .., such as /etc/motd/.., succeeds here, while POSIX requires an error because motd is not a directory. That simplification is listed under Common mistakes.


Two more things a production lookup must handle are symbolic links (with a limit on how many are followed, to stop loops) and concurrency: another thread may rename or remove a directory while a lookup walks through it. The usual answer is reference counts on the objects held in the walk plus fine-grained locks or read-copy-update in the dentry cache. D3 The kernel of this chapter has one CPU active and no writers, so it has neither problem yet; F3-33's writable ext2 is where they begin.


Note
A stat of a mount point reports the mounted root, not the covered directory. The archive stores sys/ with mode 0755, but the boot run lists d 0555 /sys, because /sys resolves to the infofs root. That is why the comparison script leaves the /sys lines out of the "host view" comparison. R3


The USTAR header


The header fields used by tarfs, after the POSIX description of the ustar format: name (100 bytes), mode (8, octal), size (12, octal), chksum (8, octal), typeflag (1: '0' or NUL for a regular file, '5' for a directory), magic ("ustar"), and prefix (155). A member's path is prefix + "/" + name when the prefix is not empty; that is how USTAR stores paths longer than 100 bytes. The checksum is the sum of all 512 header bytes taken as unsigned values, with the checksum field itself counted as eight spaces. D4 The worked example below takes one real header apart.

Cache design choices


Four decisions define a block cache. Indexing: by (device, block number); Listing 5 has one device so the block number alone is the key. Replacement: LRU is easy and good for repeated access, but one large sequential scan pushes every useful block out; real caches add a second list or a "used twice" rule for this reason. D1 Write policy: write-back with a sync call, plus periodic flushing of old dirty blocks so a crash loses only a bounded window of work. Locking: in a kernel every buffer has a lock or a "busy" state, because one thread may be reading a block from disk while another asks for it; Bach's getblk algorithm spends most of its text on these cases (sleeping until the buffer is free, rechecking after waking). D2 Listing 5 is single-threaded; the kernel version needs that state machine.


Modern kernels mostly cache files rather than disk blocks: Linux's page cache holds pages of file contents indexed by (inode, offset), and keeps a block-level cache mainly for file-system metadata. D3 For a hobby kernel the block cache comes first, because FAT32 and ext2 metadata (FAT sectors, bitmaps, inode tables) are blocks, and because mmap of files is not yet a goal.


Not verified — check before relying on this
The statement that the Windows cache manager caches views of files (virtual-address based) rather than disk blocks, and how it interacts with the memory manager, is from the author's memory of "Windows Internals". Check: Windows Internals, 7th edition, Part 2, chapter on caching and file systems, before using it in a comparison.



How the hardware actually does it


For the initrd there is no device at all: the boot loader copied the archive into RAM, and every "read" is a memory copy. QEMU placed it at 0x116000, above the kernel image, page aligned because bit 0 of the Multiboot header flags asks for page-aligned modules. D5 R2 The kernel must not overwrite that memory: its physical memory manager has to mark the module's frames as used before handing out pages. In OS302's kernel that means reading the module range before the frame allocator starts (F3-20).


For a disk, the block device driver turns "read block n" into a command to a controller (AHCI, NVMe or virtio-blk in DR301) that moves the data by DMA into a buffer the cache supplies. The cache's buffers must therefore be in memory the device can reach, and the driver must wait for completion before the cache marks the buffer valid. Those details belong to Track C; the block cache is written so that the RAM-disk device of the lab can later be replaced by a real driver without changing anything above it. C1


The serial port the kernel prints on is the emulated 16550 UART at the COM1 I/O ports, polled for "transmit holding register empty" before each byte (Listing in kbase.cc), the same driver as OS302's console. R1


Not verified — check before relying on this
The 16550 register offsets and bits used in kbase.cc (divisor latch, line control 0x03, FIFO control 0xC7, line status bit 5 "transmit holding register empty" and bit 0 "data ready") were written from memory and confirmed only by QEMU's model behaving as expected. Problem 3: predict the hit rate of the cache. The test of Listing 5 accesses 640 blocks uniformly at random through a 64-block cache. In steady state the cache holds 64 of the 640 blocks, so the chance that a random block is cached is 64 / 640 = 10 %, whatever the replacement policy. The run reports 9989 hits in 100000 operations: 9.99 %. When 80 % of the accesses go to 32 "hot" blocks, all of which fit in the cache, the hit rate should be a little above 80 %, because some of the other 20 % also hit; the run reports 80987 hits, 81.0 %. R4




Now compare disk writes. Write-through writes once per write operation: about half the operations are writes, and the runs show 49864 and 49925 device writes. Write-back writes once per eviction of a dirty block plus the dirty blocks left at sync: 47254 (only 5 % fewer) for the uniform workload, where nearly every written block is evicted before it is written again, but 10194 (80 % fewer) with locality, where hot blocks absorb many writes before each write-back. Write-back pays off exactly when the workload has locality. R4

Where the analogy breaks


    

  • A front desk can ask a library "where is the shelf?"; a VFS cannot ask a file system for its mount point. A mounted file system has no idea where it is attached. The VFS must keep that knowledge itself, which is why .. at a mounted root needs special handling (Layer 3, Figure 2).
    • 

  • A trolley copy and the shelf copy are both real books; a cache buffer and its disk block can disagree. After a write-back, the cache holds the only correct copy until it is written. If the machine stops, the "shelf" is out of date; there is no second book. This is the root of crash consistency (F3-33, OS401).
    • 

  • The first-day box is unpacked into shelves; the initrd is not unpacked at all. tarfs serves files directly from the archive bytes in memory. Linux's initramfs instead unpacks its archive into an in-memory file system; this kernel avoids the copy because its tarfs is read-only.
    • 




Common mistakes and debugging


    

  • Symptom: reads return data from the wrong file or run past the archive. Cause: trusting the header's size: a corrupt or hostile archive can claim a size larger than what follows (Listing 3, line 128, does not check). How to find it: a fuzzer feeding truncated archives, as B13 did for ELF files. Fix: reject a member whose pos + 512 + size exceeds the module length; the mini-project asks for it.
    • 

  • Symptom: ls /sys shows the covered directory's contents, or .. inside a mount loops. Cause: forgetting cross_mounts after a lookup, or asking the mounted file system for its parent. How to find it: test /mountpoint/.. and /mountpoint/../x explicitly, as the boot run does. Fix: Listing 2, lines 21 and 45.
    • 

  • Symptom: after dup, two descriptors read the same bytes. Cause: the offset was stored in the descriptor slot, not in a shared description. Fix: two tables (descriptors point to descriptions), as in Listing 2.
    • 

  • Symptom: the kernel crashes some time after boot, only when the initrd is large. Cause: the frame allocator handed out the module's frames. How to find it: print module start and end at boot (the boot run does) and compare with the first frames allocated. Fix: reserve the module range before starting the allocator.
    • 

  • Symptom: /etc/motd/.. resolves to /etc. Cause: the stack-based .. of Listing 2 pops without checking that the previous component was a directory. Fix: on .., check stack[depth-1]->type first and return -ENOTDIR; POSIX requires a directory before each slash. D4
    • 

  • Symptom: after a run of the cache test, the disk differs from the model but every read during the run matched. Cause: dirty buffers still in the cache: sync was not called before the comparison, or did not visit every buffer. Fix: call sync; count its writes (the run prints "by sync").
    • 




Transition box

Where you came from: in F3-30 (milestone B13) init started programs that the kernel found in an initial RAM disk, and F3-29 gave you system calls that validate user pointers. C1 What carries over: system calls as the only door into the kernel, negative error returns, the process structure (which now gains a descriptor table) and the serial-log-plus-exit-code test style. What changes: files become a kernel subsystem with its own objects and lifetimes: descriptors are per process but descriptions can be shared, a name is resolved through several file systems, and with a write-back cache the kernel's memory, not the disk, holds the current data, so forgetting a dirty bit or a sync loses data silently. D2 D4 What comes next: F3-32 puts the first real disk format, FAT32, on top of the block-device and cache interfaces and checks its writes with the host's own tools.

Summary


    

  • A VFS gives every file system one interface: mounted file systems, vnodes with operations tables, open-file descriptions and per-process descriptors.
    • 

  • Path lookup asks one file system per component and crosses mount points; .. at a mounted root must return to the covered directory.
    • 

  • Descriptors created by dup share one description and therefore one offset; the shell and fork depend on it.
    • 

  • An initial RAM disk arrives as a Multiboot module; a USTAR archive is headers plus data in 512-byte blocks and can be served in place.
    • 

  • A block cache indexes blocks by number, evicts by LRU and, with write-back, marks written blocks dirty and writes them on eviction or sync.
    • 

  • Uniform access gives a hit rate near cache size divided by working set; write-back helps when the same blocks are written repeatedly.
    • 

  • A missing dirty bit loses data silently; per-block event histories make such bugs visible.
    •

Forensic lab answer key


Root cause. Tomás changed line 45 of Listing 5 from buf.dirty = true; to if (last_was_miss_) buf.dirty = true;. A write that hits a block already in the cache (loaded earlier by a read) no longer marks it dirty. When that buffer is evicted it is dropped as clean, and the next load reads the old disk contents.


Evidence. Block 92: load from disk (op 163), write (op 185), evict (clean: dropped) (op 251), load from disk (op 573), then the mismatch at op 573. There is no load between 163 and 185, so the write at op 185 was a hit; a written block evicted as "clean" proves the dirty bit was not set. Block 13 shows the same pattern with three hit writes (ops 31, 57, 113). The write-through runs pass because they write every change to the disk immediately and never depend on the dirty bit.


Wrong hypotheses and why. "The eviction wrote the wrong buffer": the history would say "dirty: written back", and other blocks would show foreign data; here the eviction wrote nothing. "The disk lost a write": the RAM disk never received one (no write-back event). "A race between threads": the test is single-threaded and deterministic (fixed seed; the same op numbers every run).


Fix. Restore buf.dirty = true; for every write. Prevention: a unit test "read block, write it, force eviction, reread" (four calls), and keeping the random reference-model test in the per-commit suite rather than only nightly. How the fault was made: the lab script applies that one-line change with sed to a copy of bcache.cpp and builds it with the same flags.
