Story hook

Sione is riding his bicycle to his grandmother's house. He knows the way: "Ride along the river. When you see the blue gate, stop."

So he rides. Look: is that the blue gate? No. Keep pedalling. Look again: blue gate? No. Pedal. Look. Pedal. Look. He does not think about it much. His brain keeps going round the same small plan.

Then, there it is. Blue gate! He brakes and stops.

But one day the gate has been painted green. Sione rides and rides. He looks for blue and never finds it. After a long time he thinks, "I have gone much too far. Something is wrong." He stops and calls home.

Sione's plan had two ways to end: "I found the gate" and "I have gone much too far". A good robot brain needs both, too.

What you will be able to do

  • Explain a robot's brain as a program that runs a loop: sense, think, act, again.
  • Trace a robot loop by hand, round by round, in a table.
  • Write a loop's stopping rule, including a safety limit.
  • Read a robot's log to see what it did in each round.
  • Diagnose a robot that loops forever, from its log.
Jargon box
Program
Simple words: exact steps that a computer follows, one after another. Analogy: Sione's plan for the ride. Precise: a sequence of instructions that a computer executes exactly as written; a robot's program turns sensor readings into motor commands. D5 §5.1.1 D5 §5.1.4
Loop
Simple words: a part of a program that repeats. Analogy: look, pedal, look, pedal. Precise: a control structure that executes its body repeatedly; a while loop in C++ repeats as long as its condition is true. D6 §8.6.2 R1
Condition
Simple words: a question with the answer yes or no. Analogy: "Is that the blue gate?" Precise: an expression that evaluates to true or false and decides whether an if branch runs or a loop goes round again. D6 §8.5.2 D6 §8.6.2
Safety limit (step limit)
Simple words: a rule that stops the robot after too many rounds, even if the job is not done. Analogy: "I have gone much too far, I will stop and call home." Precise: a maximum number of loop iterations (or a maximum time) after which the program stops on purpose, so that a wrong rule cannot make the robot run forever. R2
Log (trace)
Simple words: the lines a program prints about what it did, one after another. Analogy: a diary of the ride. Precise: a time-ordered record of a program's actions and values, used to understand and debug its behaviour. R1

Layer 1 — the kid explanation

A robot's brain is a computer. The computer follows a program: exact steps, one after another. You met programs as recipes in F0-01.

A robot program has a special shape. Most of it is a loop: steps that repeat. Inside the loop are the three jobs. Sense. Think. Act. Then back to the top.

Why a loop? Because the robot can never be sure it is done. It moved, so the world looks different now. It must look again, like Sione looking for the gate.

Every loop needs a way to end. The robot asks a yes/no question each round, called a condition. "Am I on the flag?" If yes, stop. If no, keep going.

But what if the flag is missing? Or the rule is wrong? Then the answer is "no" forever, and the robot never stops. That can be dangerous with a real robot. So good robot programs add a second way out: a safety limit. "If I have gone round 20 times, stop anyway."

How do you know what the robot's brain did? You make it write a diary. Each round, it prints one line. This is the robot's log. Reading logs is a robot engineer's daily job.

The loop also goes round very quickly in a real robot, many times every second. You cannot watch each round. That is another reason the log matters.

Layer 2 — the student explanation

In C++, a while loop repeats its body as long as its condition is true. Listing 1's condition is !atGoal && step < maxSteps: "not at the goal, and fewer rounds than the limit". The loop ends as soon as either part becomes false. D6 §8.6.2 D6 §7.6.2.2 D6 §7.6.14 R1

Inside the body the program senses (atGoal = (position == goal)), thinks (if (atGoal)) and acts (moves or stops). This repeating read–decide–command structure is the skeleton of a computer control program: control textbooks describe a main loop that reads the sensor, computes the control output and sends it to the actuator, once every round. D1 §11.5

Notice an important detail in the run: the robot reaches square 6 in loop 6, but only knows it in loop 7. A robot learns about its world only when it senses, and it senses at the start of each round. R1 (The corridor with its flag is the course's own tiny simulation; later courses use a full robot simulator such as Gazebo. D14)

The safety limit (maxSteps) makes the program end even when the goal condition never becomes true. A program that waits forever for a condition that cannot happen is a common bug; the step limit turns it into a visible, safe stop. R2

Layer 3 — the engineer's depth

Note

For the curious. Real robot controllers often run their loop at a fixed rate: "sense, think, act" once every sampling period, started by a clock. Being on time matters: delays in a control loop can make it oscillate, so engineers keep the time between reading and acting short. D1 §11.5 D1 §10.1 That idea is called real-time, and it is taught in RB304. Later courses also meet the "watchdog": a timer outside the main program that resets the computer when the program gets stuck, for example in a loop that never ends. D7 Watchdog Our step limit is a tiny cousin of that idea.

How the hardware actually does it

The robot's computer runs the loop's instructions one after another, very fast. Each round it reads its input pins (the sensors), calculates, and writes to its output pins (the motor driver). D5 §5.1.4 D5 §5.1.6 How many rounds per second a real robot can do depends on its computer and program; you would measure it, not guess it (AH-22).

Where the analogy breaks


    

  • Sione notices surprises; the program does not. Sione realised "I have gone much too far" by common sense. A program only stops for reasons someone wrote into it. Without line 7's limit, the robot would never "feel" that something is wrong. R2
    • 

  • A loop runs in separate rounds. Sione watches the road the whole time. The program looks only at the start of each round, so it learns about the flag one round late (round 7, not round 6). R1 D1 §11.5
    • 

  • The program does exactly the same thing every time. Sione might take a shortcut today. Given the same start, our program prints the same log every run. That is good for testing: you can repeat a bug and study it.
    • 




Common mistakes and debugging


    

  • Symptom: the robot keeps going until the safety limit, never reaching the goal. Cause: the rule can never make the goal condition true. How to find it: read the log and look for repeating lines (the same squares again and again). Fix: change the rule, not only the limit. The forensic lab is a real example. R2
    • 

  • Symptom: the program never ends and prints nothing new. Cause: the round counter is never increased (line 13 deleted), so the safety limit is never reached. How to find it: the loop runs on forever; stop it with Ctrl+C. Fix: make sure the counter goes up every round. (F0-33 has a whole forensic lab on this.)
    • 

  • Symptom: the robot stops immediately, in round 1. Cause: the condition is the wrong way round, for example while (atGoal …) without the !. How to find it: the log has no lines from the loop. Fix: read the condition aloud: "while not at the goal".
    • 

  • Symptom: you think the loop ran 6 times but the log says 7. Cause: forgetting the extra round needed to sense the goal. How to find it: trace it in a table like the worked example. Fix: remember: arriving and knowing are two different rounds.
    •

Scenario. Tomasz built a robot for an empty room with a flag in the middle. Its only rule is: "if a wall is ahead, turn right; otherwise go forward". He pressed start and the robot "went on and on" until its safety limit stopped it. He saved the log.

Mini-project


Be the robot brain. With a friend, play "robot and brain". The brain writes a loop on a card: what to sense, what to decide, how to act, and two ways to stop. The robot follows it exactly across a room (slowly, clear floor, an adult nearby). Write a log of every round on paper.

Summary


    

  • A robot's brain is a program; most of it is a loop of sense, think, act.
    • 

  • The loop repeats because the world changes after every action.
    • 

  • A condition (yes/no question) decides when the loop ends.
    • 

  • A safety limit gives a second way out, so a wrong rule cannot run forever.
    • 

  • A robot only knows what it sensed at the start of a round.
    • 

  • Logs show what happened in each round; repeating lines mean the robot is stuck in a cycle.

Forensic lab answer key


Observation. Steps 21–24 repeat steps 1–4 exactly (column 1 to 4 along row 0, facing east). Step 20 turned the robot back to east at column 0, row 0, which is where it started. The path is a square around the edge of the room.


Root cause. The rule "wall ahead → turn right, else forward" only ever turns at walls, so the robot follows the walls forever. The flag at column 2, row 2 is not next to a wall, so the path never touches it. A bigger safety limit would only make the log longer.


Evidence. The repeat starting at step 21, and the fact that no logged square is column 2, row 2; the last line says "safety limit: stopped after 24 steps, flag not reached".


How the fault was made. The Lab Engineer wrote the wall-following rule for an empty room with the flag in the middle, and a safety limit of 24 steps, then ran it.


Fix. For example: "go forward 2 squares, turn right, go forward 2 squares" for this room; or a rule that senses the flag's direction. Test it in the simulator and check the log ends with "reached the flag".


Wrong answers and why. "The limit of 24 is too small": the path repeats from step 21 on, so no limit will help. "The robot is broken": every line is exactly what the rule says. Prevention: always keep a safety limit, and watch logs for repeats.
