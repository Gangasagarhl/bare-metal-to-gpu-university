Story hook

Kofi, Amara and Mei have kept their shared notebook in three towns for a year now. They have voted on pizzas, survived phone lines going down, and argued about who writes the order. Now they want more: the notebook should also hand out chores, notice when somebody falls ill, and give the chore to someone else. And they want to know, every week, whether the club kept its promise to answer letters quickly.

That is this project. In DS302 you built Raft inside a simulator and learned to break it on purpose. In DS402 you instrumented a service and ran a game day. In DS403 your own kernel ran on three emulated machines and elected a leader over raw Ethernet. MP2 asks you to join these pieces into one system you could hand to someone else: a consensus library you can prove is safe under faults, a replicated key-value service whose members can change, a job scheduler that restarts work when a node dies, all running on three or more machines, observed well enough that you can run a deliberate incident and write it up honestly.

What you will be able to do

  • Write a protocol specification for a replicated service precise enough that a reviewer can find a bug in it before you write code (gate R1).
  • Build a Raft library behind clean transport and storage interfaces, and prove its safety with deterministic fault injection, Raft's invariants and a linearizability check, including a planted-bug table with honest catch rates.
  • Build a replicated key-value service with client sessions, linearizable reads and membership changes by joint consensus.
  • Add cluster membership and a job scheduler (submit, place, restart on failure) whose re-placement cannot run a job twice in a way that matters, using fencing tokens or idempotent jobs.
  • Run the whole layer on three or more nodes of your own OS from MP1, or on Linux virtual machines as a documented fallback, and replay the simulator's fault schedules there.
  • Instrument it with metrics, structured logs and traces; define an SLO with an error budget and alerts; run a game day with stop conditions and write a blameless post-mortem.
  • Defend every claim with evidence a reviewer can rerun from a clean checkout.
Jargon box
Fault schedule (scenario)
Simple words: a list of "at this time, break this" lines that a test follows exactly. Analogy: a fire-drill plan that says which door is locked at which minute. Precise: a data file (here suite.in) of timed fault steps — crash, restart, isolate, partition, heal — with targets resolved at run time ("the current leader"), plus network settings and a seed; together with the seed it determines the run completely in the simulator. R1
Catch rate (planted-bug table)
Simple words: how often your tests notice a bug you put in on purpose. Analogy: hiding a few known mistakes in an exam to see whether the marker finds them. Precise: for each deliberately broken variant of the system (a mutant), the fraction of test runs in which at least one check fails; a variant that is never caught "survives" and is either a gap in the tests or provably harmless under the options used. R2
Run fingerprint
Simple words: one number that summarises everything that happened in a test run. Analogy: a photograph of the finished notebook pages, to compare two runs at a glance. Precise: a hash (FNV-1a in the lab) over the client history and every server's final term, commit index and log; equal fingerprints for two runs of the same seed are the harness's evidence that it is deterministic. R1
Liveness probe (after the faults stop)
Simple words: a test write sent once everything is repaired, to check the system works again. Analogy: after the storm, posting one letter to see whether the mail runs. Precise: from the settle time on, every 100 simulated ms, a put to the current leader until one is answered; the run fails the liveness check if none is answered before the end, and the time to the first answer is reported as recovery time. R1
Election storm
Simple words: servers keep starting elections although nothing is broken. Analogy: friends who keep calling a new vote because the organiser's weekly postcard arrives a day after they expect it. Precise: repeated leader elections in a cluster without faults, caused by timing settings (heartbeat interval not well below the election timeout) or by disruptive servers; safety holds, availability falls. R4 D1
Protocol specification (written)
Simple words: the rules of your system, written down before the code. Analogy: the club's rulebook that every friend can check a decision against. Precise: a document giving the state of each role, every message and its fields, every handler as preconditions and effects, the persistence points, the client contract, and the invariants the tests check; reviewed at gate R1. D6
Client session (duplicate detection)
Simple words: the service remembers each client's last request number so a retry is not done twice. Analogy: numbering your letters so the friend can throw away a copy that arrives twice. Precise: per-client state in the replicated state machine (last applied request number and its reply) that makes retried commands apply at most once, so a client may retry after an unknown outcome. D1
Zombie worker
Simple words: a worker that was given up for dead but is still running the job. Analogy: a friend cut off by a storm who keeps doing a chore that was already given to someone else. Precise: a scheduler worker that was partitioned, not crashed, so the job it holds is re-placed and runs twice; the defences are idempotent jobs or a fencing token checked by the resource the job writes to. D2

Layer 1 — the kid explanation

Three friends keep one notebook in three towns. Every new line goes in only when most of them have copied it, so even if one friend is ill, the notebook is never wrong. In this project the notebook does more: it remembers who has which chore, and when a friend stops answering, the chore goes to someone else. You also build a "bad postman" who loses and delays letters on purpose, and a referee who checks after every game that nobody's answers ever contradicted each other. Then you move the friends from a pretend world into real computers, put meters on the wall that show how fast letters are answered, and hold a fire drill to see what happens when things go wrong.

Layer 2 — the student explanation

What you build

A service layer: the shared services that turn several machines running your operating system into one cluster. It has four parts, one on top of the other (Figure 1).

  1. A Raft library that replicates a log of commands between servers and commits a command once a majority stores it. Your DS302 library is the starting point; the course lab's version, unchanged, is what the starter lab of this handbook runs. D1 F5-18 to F5-21
  2. A replicated key-value store on top of the log: put, get, compare-and-set and delete on many keys, client sessions so that retries apply once, linearizable reads, and membership changes so that servers can be added and removed while the store keeps working. D1 D2 F5-20, F5-40
  3. Cluster membership and a job scheduler on top of the store: which nodes are alive, where a submitted job runs, and what happens when its node dies. DS403's lab layer (F5-47) is the sketch; this milestone makes it safe against zombie workers and restarts. D5
  4. Observability: metrics, structured logs and traces, an SLO and alerts, and a game day (F5-41 to F5-43). D3

All of this runs on three or more nodes: preferably your own kernel from MP1 on three QEMU machines, as in F5-44; otherwise three Linux virtual machines, a fallback the card allows if you document it. D6

Why simulation comes first

Consensus bugs live in rare orders of events: a crash between a write and its flush, a partition just as a vote is granted. On real machines such orders happen once and are gone. In a deterministic simulator, the network, the clocks and the disks are objects inside one process, driven by a seed, so a failing run is a bug report you can replay byte for byte. DS302 built that simulator; F5-21 showed that it finds real bugs and, just as important, which bugs it did not find. MP2 keeps that discipline for the whole project: every new feature first passes the simulator's checks, and only then runs on real nodes. F5-21 R1

The four checks of the starter harness

Every run of the starter suite is judged four ways, and fails if any one fails R1:

  • Safety, checked inside the run by DS302's cluster.h: Election Safety, Leader Completeness, State Machine Safety and Log Matching. D1
  • Linearizability of the clients' history, checked after the run by DS302's linearizability.h. D2
  • Liveness after the faults stop: at the settle time the harness heals the network and restarts every crashed server; a probe write must then be answered before the end.
  • Determinism: every run is executed twice and the two run fingerprints must match.

The first two say "nothing bad happened"; the third says "something good happens again"; the fourth says the harness itself can be trusted to replay what it found.

Layer 3 — the engineer's depth

Interfaces decide whether the simulator stays useful

The single design decision that matters most in this project is where you cut the library from the world. DS302's raft::Env already shows the shape: the server sees only now(), send(), a random generator and callbacks. Extend it with a storage interface whose contract includes the crash model: a write is durable only after an explicit flush, and a crash loses everything not flushed. The simulator implements it in memory and can lose unflushed writes (the lazyPersist bug of DS302 is exactly a broken flush); your MP1 kernel implements it on its block driver; a Linux virtual machine implements it on a file and the file system's flush call. If the real implementations sit behind the same interface, every simulator test also tests the protocol code that runs on the real nodes. D1 F5-19

Not verified — check before relying on this

What a "flush" really guarantees on a given disk, virtual disk or file system (write caches, the file system's ordering of data and metadata, what a hypervisor does with a guest's flush) was not checked in this build and differs between systems. Before milestone 4 claims durability, the learner must read the storage documentation of the target (the NVMe specification's flush command for an MP1 driver; the POSIX definition of fsync and the file system's documentation on Linux) and test it with a crash-injection run on a disposable disk image. DS302 recorded the same open question (F5-15).

Reads, sessions and membership

Three features of milestone 2 are where student implementations usually break safety, and the starter's planted bugs show two of them. A leader that answers reads from its own state without confirming it is still leader returns stale values once it is partitioned (the readFromLocalState bug; Listing 5's replay shows one). The safe options are to send reads through the log, as the DS302 lab does, or to confirm leadership with a round of heartbeats before answering. D1 Retried commands must be deduplicated by client sessions, or an "outcome unknown" followed by a retry applies a command twice. D1 Membership changes must never allow two disjoint majorities; DS302 taught joint consensus and implemented it in raft_membership.h. D1 F5-20

Not verified — check before relying on this

Several refinements you may want are described in Diego Ongaro's PhD dissertation rather than in the Raft paper, as far as the author recalls: the "read index" and lease-based reads, pre-vote, check-quorum, single-server membership changes (and a published correction to them), and adding new servers as non-voting members first. The dissertation is not in the university's source registry, and none of these was implemented or tested in this build. Use them only after reading the primary text, and add each one to your protocol specification and to the planted-bug table.

The scheduler's real problem

Placing a job is easy; re-placing it safely is the project. When the membership view loses a node, the scheduler cannot tell a crashed node from a partitioned one (F5-11). If it re-places the job and the old node was only cut off, the job runs twice. F5-47 named both defences: make the job idempotent, or give every assignment a fencing token (the log index of the assignment entry) that the job must present to whatever it writes, which rejects tokens lower than one it has seen. D2 Your scheduler's invariants become checks in the harness: a job has at most one assignment whose token is accepted; every accepted job eventually completes or is reported failed; a job is never placed on a node outside the current configuration.

Safety never depends on time; availability always does

Raft's safety holds whatever the clocks and delays do; its liveness needs the heartbeat interval and message delays to be well below the election timeout, which in turn must be well below the time between failures. D1 This is not an academic point. In the forensic lab, one changed option leaves every safety check green while the SLO is missed, and the starter suite does not notice it at all (the last row of Listing 4's output). Milestone 5 is where you learn to see what safety checks cannot.

Not verified — check before relying on this

The timing requirement is stated from memory of the Raft paper's section on timing and availability ("broadcast time ≪ election timeout ≪ mean time between failures"); the exact wording, the section number and any example ranges the paper gives must be checked by the Source Researcher. The forensic run of this handbook demonstrates the effect in the simulator; it does not establish safe margins for real networks.

Risks and safety

Safety

Read the university's safety section first. This project has no moving parts and no batteries, but its fault injection is real on milestone 4 and 5: crash, partition and storage faults can cut you off from your own machines and destroy data. Run the cluster only on disposable QEMU instances or virtual machines, or on spare physical machines the owner has approved, on a network that carries nothing else; never inject faults on a shared or home network, on a machine you depend on, or on a disk that holds anything you need. Keep a console path to every node that does not go through the network under test (DS402's F5-43 has a safety box on the same risk). Any step on real hardware follows the owner's supervision rules, and the R3 safety items must be signed before the game day. No mains-voltage work is involved or allowed.

How the hardware actually does it

In the simulator, a message takes a number of milliseconds drawn from a range, a crash is a function call and a disk write is a struct copy. On real nodes each of these becomes hardware with its own behaviour, and milestone 4 exists to meet it.

  • Network. On your own OS, a message is an Ethernet frame through your e1000 driver and your TCP/IP stack (F4-10), and in QEMU it passes through the emulator's network back end and, in the DS403 setup, the lab's own switch program (F5-44). Real partitions are rarely clean: one direction may work while the other drops, and a slow link is harder for a failure detector than a dead one. Write such cases as fault schedules before you meet them.
  • Clocks. Each node counts time from its own timer. Raft uses clocks only for timeouts measured on one node, never to compare two nodes' times, which is why it stays safe when clocks drift. Your logs, however, will carry different clocks; merge them by term and index, not by timestamp (F5-10). D1
  • Storage. The persistence step (term, vote and log entries written and flushed before a reply leaves) is where real latency and real data loss come from. DS403's lab kernel kept them in RAM; your milestone 4 must not (F5-47). D1
  • CPU and scheduling. A node that pauses (a long garbage collection in another language, a stalled emulator thread, a host that is overloaded) looks to the others like a node that died, and then comes back with old beliefs. The simulator's crash-and-restart and "isolate then heal" steps model this only roughly.

No number about any of this appears in this handbook. The latencies printed by the starter lab are simulated milliseconds from a delay range written in the code; they say how the protocol reacts to delay, not how fast any machine is. Milestone 4's performance table is the first place where measurements belong, labelled with the machine they were measured on.

Not verified — check before relying on this

Untested on hardware: nothing in this handbook ran on more than one machine, on a real network or on a real disk. The DS403 three-node QEMU runs (F5-44 to F5-47) are the closest evidence in this university, and they too are emulated.

Where the analogy breaks


    

  • Friends in towns notice when a letter is missing and ask again; Raft servers act only on messages that arrive and on their own timers. Nothing "notices" a lost message except a timeout.
    • 

  • A friend who was cut off knows it when the phone line comes back. A partitioned Raft leader does not know it has been deposed until it hears a higher term; meanwhile, as the replay shows, it may still answer clients.
    • 

  • A fire drill in a building cannot accidentally lock everyone out of the building. A game day on your cluster can cut you off from the very machines you need to stop it, which is why R3 checks for an independent console path.
    • 

  • The friends' chores are done by people who stop when told; a zombie worker keeps running a job no one thinks it has, until its write is refused by a fencing token.
    •

With the heartbeat (200 ms) longer than the shortest election timeout (150 ms), any follower that draws a timeout below the heartbeat interval starts an election in a healthy cluster: an election storm. Raft's timing requirement — heartbeats well below the election timeout — is violated. D1
