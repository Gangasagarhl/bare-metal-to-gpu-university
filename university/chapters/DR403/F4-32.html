Story hook

At six in the morning the school is dark. The first person to arrive is old Mr Pike at the gate. He has done the same thing every morning for forty years and will never change: he looks at the board by the gate that says which entrance to use today, walks to that entrance, picks up the envelope left there, checks that the seal is intact, and hands it to whoever the envelope names. He knows nothing else about the school.

The envelope names Ms Ruiz, the facilities manager. She switches on the heating, the boilers and the water, checks two more envelopes, and hands them on: one to the caretaker who will live in the office all day, one to the teacher who will open the classrooms. The caretaker settles into the office and stays there. From then on, whenever a teacher needs something only the caretaker may do (turn off the building's power, open the locked wing), the teacher passes a note through the office hatch and waits for the answer.

Your kernel is the teacher. By the time it runs, three people have been through the building before it, each one deciding something it cannot change: which entrance, which rooms are heated, which wing is locked. When the kernel does not start, the evidence is in what those three left behind. This chapter builds all four stages in QEMU, small enough to read in one sitting, and then breaks the hand-over between the last two.

What you will be able to do

  • Describe the common Arm boot chain of curriculum 11.2: boot ROM, first stage (U-Boot SPL or TPL, or TF-A BL2, or a vendor loader), TF-A BL31, optional BL32 (OP-TEE), BL33 (U-Boot proper or EDK II), your kernel; and state the job, exception level and lifetime of each.
  • Build a four-stage chain in QEMU (-M virt,secure=on) in which a "ROM" at EL3 loads and checks a second stage, the second stage loads a resident EL3 monitor and a kernel, and the monitor drops to EL1 with the DTB address in x0.
  • Program the EL3 hand-over registers (SCR_EL3, SPSR_EL3, ELR_EL3, VBAR_EL3) and explain each bit you set.
  • Implement two PSCI calls in the monitor and call them from the kernel through the SMC instruction, following the SMC Calling Convention.
  • Diagnose a failed hand-over from the monitor's exception report and QEMU's exception log.
Jargon box
Boot chain (Arm)
Simple words: the list of programs that run one after another from power-on until your kernel starts. Analogy: the people who open the school in the morning, each handing an envelope to the next. Precise: on Arm SoCs, a boot ROM, a first stage that initialises DRAM, an EL3 runtime (TF-A BL31), an optional secure-world OS (BL32), a normal-world loader (BL33) and the OS, each loaded and optionally verified by the one before. C1 D1
Trusted Firmware-A (TF-A)
Simple words: the open reference firmware for the secure parts of booting an Arm 64-bit chip. Analogy: the caretaker's rule book, used by many schools. Precise: the Trusted Firmware project's implementation of the Arm boot stages BL1 (ROM-like first stage), BL2 (trusted boot loader), BL31 (EL3 runtime with PSCI and the SMC dispatcher), with interfaces to BL32 (secure payload) and BL33 (non-secure firmware). D1
EL3 runtime (BL31)
Simple words: firmware that stays in memory after the kernel starts, in the most privileged mode, to do the few things the kernel may not do itself. Analogy: the caretaker who lives in the office all day. Precise: the TF-A stage resident at exception level 3 in secure memory; it owns VBAR_EL3, handles SMC exceptions from lower levels (PSCI, SMCCC services, sometimes SCMI or vendor services) and switches between the secure and non-secure worlds. D1 R3
SMC (Secure Monitor Call)
Simple words: the instruction a kernel uses to ask the EL3 firmware for a service. Analogy: a note passed through the office hatch to the caretaker. Precise: an AArch64 instruction that, when permitted by SCR_EL3, takes a synchronous exception to EL3 with exception class 0x17; the SMC Calling Convention defines the function ID in w0, arguments in x1 onwards and results in x0 to x3. D3 R4
PSCI (Power State Coordination Interface)
Simple words: the standard list of power requests an OS can send to firmware: start a CPU, stop a CPU, power off, reset. Analogy: the printed form the teacher fills in for the caretaker. Precise: an Arm specification of firmware functions (PSCI_VERSION, CPU_ON, CPU_OFF, SYSTEM_OFF, SYSTEM_RESET and others) called through SMC or HVC with fixed function IDs, advertised to the OS by a /psci devicetree node or ACPI. D2
SPL and TPL (U-Boot)
Simple words: small first versions of U-Boot that fit in the chip's on-chip memory and start the DRAM. Analogy: the facilities manager who switches on the heating before anyone else can work. Precise: U-Boot's Secondary and Tertiary Program Loaders: reduced builds that run from on-chip SRAM, initialise clocks and DRAM, and load the next stages (TF-A BL31, OP-TEE, U-Boot proper) into DRAM. D5 C1
Secure and non-secure worlds
Simple words: two separate sets of privileges inside one chip; the normal OS runs in one, trusted firmware in the other. Analogy: the locked wing of the school that teachers cannot enter. Precise: Arm's TrustZone security states; SCR_EL3.NS selects the state of the levels below EL3, and memory and devices can be made accessible only to the secure state. D4
Recovery mode (boot ROM)
Simple words: a way to load a program into a board over USB when nothing on its storage works. Analogy: the side gate the old caretaker opens when no envelope is waiting. Precise: a boot ROM function, selected by pins, fuses or the absence of a valid image, that receives code over USB or serial (Allwinner FEL, NXP serial download, Rockchip mask-ROM mode). C1 D9

Layer 1 — the kid explanation

When a small computer board switches on, it does not start your program straight away. First a tiny program that was built into the chip in the factory wakes up. It knows only one thing: where to find the next program. That one wakes up the memory and finds two more: a guard who stays awake all the time in a locked room, and your program. Your program can ask the guard for help, for example "please switch everything off", by passing a note. If any of these helpers makes a mistake, your program never starts, and you have to work out which helper it was.

Layer 2 — the student explanation

An Arm SoC starts executing in a boot ROM inside the chip. The ROM reads boot-mode pins or fuses to pick a boot medium (SD, eMMC, SPI flash, UFS, NAND or USB), loads the first stage from that medium into on-chip SRAM, because DRAM does not work yet, optionally verifies its signature, and jumps to it. Many ROMs also offer a USB recovery mode when no valid image is found. C1

The first stage (U-Boot SPL or TPL, TF-A BL2, or a vendor's loader) initialises clocks and DRAM, then loads the rest into DRAM: TF-A's BL31, optionally OP-TEE as BL32, and the normal-world loader as BL33, which is U-Boot proper or EDK II. BL31 stays resident at EL3. BL33 runs in the non-secure world, loads your kernel, a devicetree and perhaps an initial RAM disk, and starts the kernel with the DTB address in x0, or runs it as a UEFI application (F4-33). C1 D1 D5

After the kernel is running, BL31 is still there. The kernel cannot switch CPUs on and off, reset or power off the system by itself on most Arm platforms, because those controls are reserved for the secure world. It asks BL31 through the smc instruction, using function numbers defined by the PSCI specification. The /psci node of the devicetree tells the kernel that PSCI exists and whether to use smc or hvc. D2 D3

The lab builds a miniature of this chain: four programs on a 64 MiB flash image in QEMU's virt machine with its EL3 extension switched on. The "ROM" checks BL2 with a CRC-32 and copies it to secure RAM; BL2 loads BL31 and the kernel; BL31 programs the EL3 registers and drops to EL1; the kernel calls PSCI_VERSION and SYSTEM_OFF. Breaking one bit of the kernel image stops the chain in BL2; breaking one bit of a register value in BL31 stops it at the very first instruction of the kernel, which is the forensic lab. R3 R6 R8

Layer 3 — the engineer's depth

The stages, their levels and their lifetimes

The TF-A documentation names five image slots. BL1 is a ROM-like first stage for platforms where TF-A itself provides the first code (on most SoCs the vendor's mask ROM fills this role, and TF-A starts at BL2 or BL31). BL2 is the trusted boot loader: it runs at EL3 or S-EL1, loads the other images, and on platforms with trusted boot verifies them against a chain of certificates. BL31 is the EL3 runtime and stays resident. BL32 is a secure payload at S-EL1, OP-TEE being the common open one D6. BL33 is the non-secure firmware: U-Boot proper or EDK II. D1 C1

What a boot ROM does, and what this lab's ROM leaves out


A real boot ROM decides the boot medium from pins or fuses, initialises enough of that medium's controller to read from it, parses a vendor-specific header (offsets, sizes, load addresses, sometimes several copies for redundancy), loads the image into on-chip SRAM, verifies a signature against a key hash fused into the SoC if secure boot is enabled, and jumps. If none of that works, it may fall back to a USB recovery protocol. Each vendor documents its own format, or does not; U-Boot's tools generate the formats of many vendors. C1 D9


The lab's ROM reads a fixed offset (0x10000) of one fixed medium (QEMU's first flash device, mapped at 0), checks a 32-byte header of the course's own format ("DR4I", load address, size, CRC-32, name), copies the payload to the load address and jumps. A CRC-32 detects accidental damage. It does not detect tampering: anyone who can write the flash can recompute it. Real secure boot replaces it with a signature check against a key the attacker cannot change, which is the subject of F11-01's chain of trust. R2




The damaged-image test flips one bit in the middle of the kernel's payload after its CRC-32 was computed. BL2 finds the mismatch and stops with exit code 6, before anything is copied over the kernel's load address. That is the behaviour you want from every stage: refuse loudly, early, and with the offset of the bad image. R5 R6







DRAM initialisation: the step this lab cannot show


BL2 prints "DRAM init would happen here". On real hardware this step is the biggest piece of the first stage: programming the memory controller and the DRAM PHY with the timings of the chips soldered on the board, then running training sequences that tune delays per data line. It runs from on-chip SRAM because DRAM is not usable until it finishes. Whether it is open code or a vendor binary decides whether a fully open boot chain exists for a board: curriculum 11.4 records open DRAM initialisation for RK3399 and many Allwinner parts, a Rockchip binary for RK3588, and a DDR PHY training firmware blob on i.MX8M. F4-34 uses those facts to choose boards. C1

The EL3 hand-over: three registers and an ERET


Leaving EL3 for the kernel is one instruction, eret, which restores the processor state from SPSR_EL3 and jumps to ELR_EL3. What the lower level will be, and in which execution state, is decided by those two registers and by SCR_EL3. The lab's enter_bl33 writes all three and puts the DTB address in x0, so the kernel sees exactly the arm64 boot contract of F4-31. D4 D8

And EL2 is skipped: the kernel is entered at EL1. SMC, the calling convention and PSCI


The SMC Calling Convention (SMCCC) gives every firmware service a 32-bit function ID in w0: bit 31 says "fast call", bit 30 says "SMC64" (64-bit arguments) or "SMC32", bits 29:24 name the owning service range (standard secure services include PSCI), and the low bits number the function. Arguments go in x1 to x7 (or w1..), results come back in x0 to x3, and the callee preserves the other registers. An unknown function returns −1, NOT_SUPPORTED. D3


The lab's kernel calls two PSCI functions: PSCI_VERSION (0x84000000) and SYSTEM_OFF (0x84000008). The smc #0 traps to EL3 with exception class 0x17 (the log shows ESR 0x17/0x5e000000), through the vector at VBAR_EL3 + 0x400 ("synchronous exception from a lower level using AArch64"): 0xe101000 + 0x400 = 0xe101400, the address in the log. The handler saves the registers C++ may clobber, calls smc_dispatch, restores them and returns with eret; ELR_EL3 already points at the instruction after the SMC. R4 D3 D4


PSCI_VERSION returns 0x10000, major 1 minor 0, because our BL31 says so. On QEMU's virt machine without secure=on, QEMU itself implements PSCI behind hvc, and F4-37's kernel reads "1.1" from it. The number is a property of the firmware, not of the chip. R3 R10

One observation from the run needs explaining: the kernel reports "devicetree has a /psci node: no". When QEMU is given firmware with -bios and secure=on, it does not emulate PSCI itself and leaves the /psci node out, expecting the firmware to provide both. A real chain does: TF-A implements PSCI, and U-Boot or the board's devicetree source adds the node with method = "smc". Our chain adds nothing, so a Linux kernel booted by it would not know PSCI exists and could not start secondary CPUs. Adding the node is one of the lab steps. R3 D7



The secure world leaves marks in the devicetree


QEMU's virt machine with secure=on has a second PL011, reserved for the secure world, at 0x9040000. Its devicetree node is present with status = "disabled" and a secure-status = "okay" property, so that secure firmware may use it and the normal world must not. A kernel that takes "the first PL011" without checking status picks it. The normal-world access to secure-only hardware is refused with a data abort (fault address 0x9040018, the flag register), the exception handler tries to print through the same UART and faults again, and the run never produces a byte of output. The run shows the first abort and the count of exceptions QEMU logged before the 8-second timeout. R7




The exact path from the first abort to the long run of "Undefined Instruction" exceptions was not investigated; what matters is the first line and its fault address. Two lessons follow. status is not a hint; it is the board's statement of ownership. And an exception handler whose only output is the device that has faulted reports nothing.

Standard boot, UEFI and where your kernel fits


In the real chain, BL33 is a full loader. U-Boot proper reads a boot script or its "standard boot" configuration, loads the kernel, the devicetree and an initial RAM disk from a partition or the network, applies devicetree fix-ups (memory size, MAC addresses, /chosen with the command line, the /psci node), and starts the kernel with booti (the arm64 contract) or as a UEFI application through its UEFI implementation. EDK II provides UEFI on platforms that use it. Curriculum 11.3 explains why the UEFI path matters: it is the one that lets a single image boot on many boards (F4-33), and it is the path milestone D10 asks for. D5 C1



How the hardware actually does it


At reset an Armv8-A core starts at its highest implemented exception level, at an address given by a reset-vector configuration (an implementation-defined input or register, RVBAR_EL3), with the MMU and caches off. On an SoC that address points into the mask ROM. The other cores are held in reset or parked by the ROM until firmware releases them; on QEMU virt all cores start at the same entry, which is why every stage checks MPIDR_EL1 and parks the others. D4


TrustZone is implemented by the interconnect and by security controllers in front of memories and peripherals: every bus transaction carries a non-secure bit taken from the issuing world, and a controller configured by secure firmware rejects non-secure accesses to secure regions. That rejection is what the normal-world kernel saw as a data abort on the secure UART in QEMU. D4 R7


Boot-medium selection is electrical. Boot-mode pins (straps) are sampled at reset, sometimes with fuses that override them; boards wire some straps to buttons ("hold this button to enter recovery mode"), which is how you reach a ROM's USB recovery protocol on a board whose storage holds a broken image. C1

Safety
Replacing boot stages on a real board can make it unbootable. Before writing any boot medium, know the board's recovery path (a removable SD card, USB recovery mode through the ROM, an external SPI programmer with a backup image) and test it once while the board still works. Never write fuses: secure-boot and boot-mode fuses are one-time programmable, and a wrong value is permanent. Never flash firmware on a machine you depend on. Develop in QEMU first, as this lab does. See the university safety rules.



Worked example


Question. Using only the boot trace, show that the kernel's two SMCs went to the right vector, and work out which instruction issued each one.


Step 1: the vector. BL31 printed VBAR_EL3 = 0xe101000. The AArch64 vector table has four groups of four 128-byte entries: current level with SP_EL0 (offset 0x000), current level with SP_ELx (0x200), lower level in AArch64 (0x400), lower level in AArch32 (0x600); within each group, synchronous is the first entry. An SMC from EL1 in AArch64 is a synchronous exception from a lower level in AArch64: 0xe101000 + 0x400 = 0xe101400. The log says "to EL3 PC 0xe101400". R3 R4


Step 2: the syndrome. ESR 0x17/0x5e000000: QEMU prints the exception class and then the full register. 0x5e000000 = 0b0101_1110_0000…; bits 31:26 = 0b010111 = 0x17, "SMC instruction executed in AArch64 state". Bit 25 (IL) = 1, a 32-bit instruction; the low 16 bits hold the SMC's immediate, 0. D4


Step 3: the callers. The first SMC has ELR 0x400820a8, the second 0x400820d8. For an SMC, ELR_EL3 holds the address of the next instruction, so the SMCs are at 0x400820a4 and 0x400820d4. Subtract the load address 0x40080000: offsets 0x20a4 and 0x20d4 in the image, which is linked at 0. Running aarch64-linux-gnu-addr2line -f -i -e bl33.elf 0x20a4 on the lab's build points into the inlined smc() helper called from kmain, the first for PSCI_VERSION and the second for SYSTEM_OFF (this step was not recorded as a run; do it in the lab).


Step 4: the return. After the first SMC the log shows "Exception return from AArch64 EL3 to AArch64 EL1 PC 0x400820a8": the instruction after the SMC, as expected. After the second there is no return: BL31 ended the run with semihosting (the log's "Semihosting call ... from EL3 to EL3"). R4


Step 5: cross-check with the serial log. Between the two SMCs the kernel printed "PSCI_VERSION returned 0x10000 (major 1, minor 0)", and BL31 printed its two "SMC ... from the normal world" lines in the same order. Two independent records (the serial output of our code and QEMU's own log) agree on the sequence. R3

Where the analogy breaks


    

  • Mr Pike at the gate can be replaced when he retires. A mask ROM cannot be changed after manufacture; its bugs are permanent, and a vulnerable ROM stays vulnerable on every chip made with it.
    • 

  • A caretaker who lives in the office is a person you can see. BL31 is invisible to the kernel: it occupies memory the kernel must not touch (the devicetree's reserved-memory or memory reservation map should say where), and it can run at any SMC, interrupt or power event, taking time the kernel cannot account for.
    • 

  • Passing a note through the hatch is voluntary. On real platforms some events go to EL3 without the kernel asking: secure interrupts routed to EL3, and on some platforms errors that firmware handles first.
    • 

  • In the school, every envelope is checked by a person who can notice an odd seal. A boot stage checks exactly what its code checks: a CRC detects damage, not forgery; a signature check with a leaked key accepts forgeries.
    • 




Common mistakes and debugging


    

  • Ignoring status and picking a secure-world device. The kernel aborts on its first access and its own exception report faults on the same UART: no output at all. Debug with QEMU's -d int log, which does not depend on your console. R7
    • 

  • Missing RW in SCR_EL3. The exception return is illegal and the first instruction of the kernel raises an Illegal Execution State exception at EL3. This is the forensic lab.
    • 

  • Not installing VBAR_EL3 before the first SMC. The SMC lands at an address left over from reset. Symptom: a hang or a random crash at the first PSCI call, never at boot.
    • 

  • Expecting a /psci node that your firmware never added. A Linux kernel then runs on one CPU and cannot power off. Check the tree the kernel actually received (dump it from the kernel or with QEMU's dumpdtb), not the source file.
    • 

  • Overlapping images. A BL33 load address inside BL31's memory overwrites the monitor; the symptom appears at the first SMC. A good BL2 checks load ranges against each other (a lab step).
    • 

  • Debugging with the console only. Before the console works, use the exit code (this course's semihosting exit), QEMU's -d int,guest_errors log, or a debugger attached to QEMU's gdb stub (-s -S); on hardware, a JTAG probe.
    •

Summary


    

  • An Arm SoC boots through a boot ROM, a first stage that brings up DRAM (SPL, TPL, BL2 or a vendor loader), a resident EL3 runtime (BL31), an optional secure OS (BL32) and a normal-world loader (BL33) before your kernel.
    • 

  • Each stage should check the next before copying it and refuse loudly; a CRC detects damage, only a signature detects tampering.
    • 

  • Leaving EL3 is SCR_EL3 (security state, AArch64 or AArch32 below), SPSR_EL3 (target level, masks), ELR_EL3 (entry), then ERET; the kernel gets the DTB in x0.
    • 

  • After boot the kernel asks BL31 for power and CPU control with SMC and PSCI function IDs under the SMC Calling Convention; the /psci node says that, and how, PSCI is available.
    • 

  • The secure world's ownership shows in the devicetree as status = "disabled"; ignoring it crashes the kernel without a word.
    • 

  • When the console is silent, QEMU's exception log and exit codes are your evidence.
    •

Forensic lab answer key


    

  1. The only difference before the failure is BL31's line "SCR_EL3 = 0x31" (failing) versus "SCR_EL3 = 0x431" (good). After the ERET, the failing run is still at EL3: QEMU's log shows an exception "from EL3 to EL3" with ELR 0x40080000, the kernel's entry, and the target "EL3 PC 0xe101200".
    2. 

  2. Bits 31:26 of 0x3a000000 are 0b001110 = 0x0E: Illegal Execution State. The exception return was illegal (it asked for an AArch64 EL1 while SCR_EL3 declared the lower levels AArch32), so the ERET did not change the level: it set PSTATE.IL and branched to ELR_EL3. The first instruction at 0x40080000 then raised the exception at EL3, through the "current level, SP_ELx, synchronous" vector: VBAR_EL3 + 0x200 = 0xe101200, vector number 4 in BL31's report. QEMU names the exception "Undefined Instruction" in its log while the syndrome says 0x0E.
    3. 

  3. Damaged kernel: ruled out, BL2 checked its CRC-32 ("CRC-32 ok") and the image was unchanged. Wrong entry: ruled out, ELR is 0x40080000 as in the good run. Bad SPSR_EL3: not printed, but the code path is unchanged and the value is a constant; possible, ruled out by the source diff. Bad SCR_EL3: supported, it is the only printed difference.
    4. 

  4. 0x431 − 0x31 = 0x400: bit 10, RW. With RW = 0 the levels below EL3 are AArch32, so an exception return to an AArch64 EL1 is illegal. The engineer's field list included NS and the RES1 bits but forgot RW.
    5. 

  5. Fix: set bit 10 (build with the default SCR_VALUE, 0x431). Prevention: define each field by name and add a static_assert that RW is set whenever the BL33 entry state is AArch64; in BL31, read SCR_EL3 back before the ERET and refuse to continue if RW does not match the requested SPSR mode; keep the good boot log as a reference and diff each new build's log against it in CI. How the fault was injected: run.sh builds BL31 with -DSCR_VALUE=0x31.
    6.
