Story hook

A travelling teacher works at two schools. The first school is a modern building with a printed floor plan at the entrance: the office is on the ground floor, the bell is in the hall. The second is an old building with different corridors, a bell in another place, and a floor plan the teacher has to bring herself, which the caretaker corrects at the door ("the top floor is closed; we use it for storage").

She does not carry a different lesson book for each school. She carries one book, and at each door she reads the plan: where is the office, where is the bell, how many classrooms. The same book works in both buildings because it never assumes where anything is.

One day a substitute takes her place with a shortcut written into the book: "the office is the first door on the left". In the modern school, that is true and everything works. In the old school, the first door on the left is a storeroom. The substitute talks into an empty room all day, hears nothing back, and goes home. The classes were taught (the pupils' notebooks prove it), but the office never heard a word.

This chapter boots one kernel file, byte for byte, on two QEMU machines with different SoC layouts, and then looks at the substitute's shortcut.

What you will be able to do

  • Build one AArch64 kernel image that runs on two platforms without a compile-time board choice, and prove it with a hash and a log check.
  • List every platform difference between QEMU's virt and raspi3b machines that the kernel must discover at run time: load address, exception level, memory, CPUs, interrupt controller, console, power-off.
  • Explain how a position-independent image relocates itself, and diagnose a relocation table that is too short.
  • Compare the devicetree a loader hands over with the one you gave it, and the bus and CPU views of an SoC's address map.
  • State what milestone D10 requires beyond this build: TF-A, U-Boot's UEFI, a board from a second SoC family, and the B9/B10 tests on all cores.
  • Diagnose a kernel that is silent on one platform but ran, using evidence that does not depend on its console.
Jargon box
Generic kernel image
Simple words: one kernel file that runs on many boards, because it finds out what board it is on while it boots. Analogy: the teacher's one lesson book. Precise: a kernel binary with no compile-time board selection: load address, exception level, memory, CPUs, devices and firmware services are discovered from the boot protocol and from firmware tables (devicetree or ACPI), and devices are handled by drivers matched at run time. D1 C1
Position-independent image
Simple words: a program that works wherever in memory it is loaded, because it fixes its own addresses first. Analogy: a book whose page references say "three pages on" instead of "page 47". Precise: code built with -fpie and linked with -pie: instructions address relative to the program counter, and every absolute pointer in data has an R_AARCH64_RELATIVE dynamic relocation that start-up code applies by adding the load address. D5 R1
Dynamic relocation (R_AARCH64_RELATIVE)
Simple words: a note in the file saying "this word must be increased by wherever the file ends up". Analogy: a sticky note on page 12: "add the room number to this". Precise: an Elf64_Rela entry (offset, info, addend; 24 bytes) of type 1027, meaning: store load address + addend at load address + offset. D5
Bus address and CPU address
Simple words: the same register can have one number seen from the SoC's internal bus and another seen from the processor. Analogy: a room called "B12" by the building plan and "the third door upstairs" by the staff. Precise: on SoCs whose peripherals hang on a bus with its own address map, the devicetree describes nodes in bus addresses and gives the translation in the parent's ranges; on QEMU's raspi3b, bus 0x7e000000 is CPU 0x3f000000. D4 R6

Layer 1 — the kid explanation

Some programs are made for one computer only, like a key cut for one lock. This chapter's program is more like a person who walks into any house, reads the note by the door ("the kitchen is here, there are four bedrooms, the light switch is there") and then gets to work. The same person works in two very different houses because they read the note first and never guess. If they guess, they may talk to a cupboard.

Layer 2 — the student explanation

On PCs, one operating system image boots on thousands of different machines, because firmware describes each machine in a standard way (UEFI and ACPI, OS301). On Arm SoC boards the tradition was the opposite: one kernel build per board, with addresses compiled in. Arm's SystemReady and EBBR programmes (F4-33) push SoC boards towards the PC model: firmware (TF-A, then U-Boot) hands a kernel a devicetree and UEFI services, and one generic image boots everywhere. Milestone D10 asks you to do this with your own kernel. D2 D3 C1

This chapter's version uses two QEMU machines with very different layouts. QEMU's virt machine is a modern design: RAM from 1 GiB, a GIC interrupt controller, PSCI for power, a devicetree generated by QEMU. QEMU's raspi3b imitates the Broadcom BCM2837 of a Raspberry Pi 3: RAM from 0, peripherals on a bus seen through an address window, Broadcom's own interrupt controllers, no PSCI, and a devicetree that we supply. D6

The kernel of F4-35 and F4-36 is built once. The build prints the file's SHA-256; each run computes it again; a checker requires them to match and requires each log to show the right memory size, CPU count and timer frequency. Both pass. The kernel binds 9 devices on virt and 4 on raspi3b, through the same driver table. R4

Three things made this possible. The image fixes its own pointers wherever it is loaded (position independence). It reads everything about the platform from the devicetree, including where its console is. And it treats every difference as data: the exception level it was entered at, whether there is a PSCI node, which compatible strings are present. The chapter then shows a short relocation table breaking the first, and a hard-coded console address breaking the second. R7 R9

Layer 3 — the engineer's depth

One build, one hash

The build compiles the F4-35 and F4-36 sources with -fpie, links them with -pie at address 0 with F4-31's linker script, and converts the result to a flat binary with an arm64 image header. There is no board option: the build script has no variable that could select one. R1



Eleven drivers are linked in; the driver core of F4-35 walks the table they form and matches each devicetree node's compatible strings against it. Nothing in the image says which machine it is for. R1



Where it lands, and at which level


The image header (F4-31) carries a text offset of 0x80000 and a flag saying the image may be placed anywhere in RAM. QEMU's loader puts it at the start of RAM plus the offset: 0x40080000 on virt (RAM starts at 1 GiB) and 0x80000 on raspi3b (RAM starts at 0). The loader passes the devicetree's address in x0: 0x48000000 on virt, 0x8000000 on raspi3b. D1 R2 R3


The virt machine without virtualization=on starts the kernel at EL1; raspi3b starts it at EL2. F4-31's start.S reads CurrentEL, and at EL2 sets HCR_EL2.RW, gives EL1 the physical counter, and drops to EL1 with an exception return (lines 27–41). After that, both runs execute identical code. The arm64 booting document allows entry at EL2 or EL1 and recommends EL2 when the kernel may want to run virtual machines; this kernel does not. D1



Fixing its own pointers


Code compiled with -fpie reaches functions and data with PC-relative instructions (adr, adrp), which work at any address. Data that holds absolute pointers does not: the driver table's pointers to compatible strings and probe functions, virtual-function tables, string tables. The linker records each such word as an R_AARCH64_RELATIVE entry in .rela.dyn, with the value it would have at link address 0 as its addend. start.S lines 54–67 walk the table: for each entry of type 1027, store load address + addend at load address + offset. The image has 177 of them. D5 R1


The table's bounds come from the linker script. F4-31's kernel.ld defines them outside the section, from its final address and size (lines 12–15), with a comment explaining why: the linker sizes dynamic relocations late. An earlier draft defined them inside the section's braces. That draft links without a warning, and the start code applies only 144 of the 177 relocations, so 33 pointers keep their link-time values near 0. The kernel still prints (the early console code uses PC-relative addresses), but every compatible string pointer in the driver table is wrong, and the driver core matches nothing: 49 nodes, 0 bound. R7

The tree each loader handed over


On virt, QEMU generates the whole devicetree from its configuration: -m 512M and -smp 2 become a memory node and two CPU nodes. On raspi3b, we pass F4-36's tree with -dtb, and QEMU's loader edits it before handing it over. Asking QEMU to dump the tree it would pass shows the edit: our memory node said 0x3f000000 bytes; the kernel received 0x3c000000 (960 MiB). The handed-over blob is also much larger than ours (23440 bytes against 1720): the loader added content of its own. The kernel printed 960 MiB, which is the tree it received, and that is what the D10 checker compares against. R5




This is normal on real boards too: firmware (the Raspberry Pi's own boot firmware, or U-Boot) fixes up the tree it passes on, with memory size, MAC addresses, command line, reserved memory for itself. A kernel must trust the tree it is given, not the source you wrote. D8

Why QEMU's raspi3b loader reduced the memory to 960 MiB, and what the extra 21720 bytes contain, were not investigated: the dump was filtered to the memory and /chosen nodes. The author's guess, that the top 64 MiB are set aside for the VideoCore GPU as on the real board's firmware, is unverified. The statement that real Raspberry Pi firmware and U-Boot fix up the tree is from the author's memory of their documentation, not opened in this build.



Two views of one SoC


QEMU's memory tree for raspi3b shows the peripherals twice: in the address space of the VideoCore bus (the GPU's view, where the devicetree's 0x7e20xxxx addresses come from) and in the CPU's address space at 0x3f20xxxx. The ranges property of the tree's /soc node (F4-31) is exactly this translation. The kernel's driver core applies it, so the PL011 driver receives 0x3f201000 although the node says 0x7e201000. R6 D4




The CPU view also shows RAM from 0 to 0x3f002fff, and the BCM2836 control block at 0x40000000, outside the /soc window, which is why the tree's local_intc node sits at the root with a CPU address. Note that 0x09000000, virt's UART, is ordinary RAM on this machine. The forensic lab depends on that.

Two lines in the virt log need a word. "Bound 9, failed 31": QEMU's virt machine always creates 32 virtio-mmio transports; the one with the RNG device answers with device ID 4, and the 31 empty ones are reported as failed probes, which is correct. Each is a missing driver or a missing tree property, not a board option: that is the line D10 draws.



From two QEMU machines to D10


D10's real test differs in three ways. The second platform is a real board from a second SoC family. The kernel is not loaded by QEMU's direct kernel boot but by firmware: TF-A (F4-32), then U-Boot, whose UEFI implementation runs your A3 loader as a UEFI application (F4-33), which loads the kernel and hands it the firmware's devicetree. And "on all cores" means the B9/B10 tests (OS30x: SMP start-up and per-CPU structures) run on every CPU, which this kernel does not start. C1 D8

How the hardware actually does it


On a real board from a second family (the curriculum names, for example, RK3399, i.MX8M, AM62x, A64 or H6), the boot ROM loads a first stage (TF-A's BL2 or U-Boot SPL) from SD or eMMC, which initialises DRAM, loads BL31 (EL3 runtime, PSCI) and U-Boot proper, which in turn finds an EFI system partition and runs a UEFI application. The devicetree comes from U-Boot (built in, or loaded and fixed up). Every one of these stages is a place where the kernel's assumptions can fail: memory reserved by BL31 must appear as reserved in the tree, the UART's clock must be on, and the exception level at entry depends on firmware configuration. C1 D8


The cache and MMU state at entry matters on hardware in a way QEMU does not show: the booting protocol requires the MMU off and the kernel image cleaned to the point of coherency, and a kernel that writes its relocations with caches off and then turns caches on must not find stale lines. QEMU does not model caches, so this build cannot test it. D1


Not verified — check before relying on this

Safety
D10's board work installs firmware. Develop in QEMU first; never flash firmware on a machine you depend on; keep a recovery path (a second SD card with known-good firmware, the SoC's USB recovery mode, or a debug probe) and practise it before you need it. Use a 3.3 V USB-serial adapter for the console, never 5 V. See the university safety rules.



Worked example


Question. The PL011 driver's probe function lives in the image at offset f from _start, and the driver table holds a pointer to it. What value does that pointer hold in the file, what does it hold after start-up on each machine, and what would it hold if its relocation were among the 33 not applied?


In the file. The image is linked at 0, so the pointer's link-time value is f. Because it is a RELA relocation, the addend f is also stored in the relocation entry; the start code uses only the entry's addend and overwrites the word with addend + load address. (What ld leaves in the word itself was not inspected in this build.) D5


After start-up. virt: 0x40080000 + f. raspi3b: 0x80000 + f. Both are computed from adr x3, _start, the address the code is running at, not from the header's text offset; the kernel would also work if a loader placed it elsewhere in RAM. R2 R3


Not applied. The pointer stays f, a small number. On virt, address f is in the flash region below 0x40000000; on raspi3b it is in RAM below the kernel. The driver table's compatible-string pointers suffer the same, so the core compares node strings against bytes at small addresses and never matches. That is why the short-table run binds nothing instead of crashing on a call. R7


Check with the evidence. 177 − 144 = 33 relocations missed; all 49 nodes "no driver". A kernel that reports "no driver" for a node whose driver you know is linked in (the PL011 here) points at the driver table, not at the tree.

Where the analogy breaks


    

  • A teacher who walks into the wrong room notices. A kernel writing to a wrong address that happens to be RAM gets no error at all; nothing tells it the "room" is empty.
    • 

  • The floor plan in the story is read once at the door. A kernel reads its devicetree once at boot, but on some platforms the tree changes later (overlays, hot-plug) and the kernel must handle that.
    • 

  • The teacher's book has page numbers that stay correct. A kernel image must first rewrite its own internal references before it can read its "book" at all; the teacher never has to fix her book on arrival.
    • 

  • The caretaker's corrections in the story are announced. A loader's changes to the tree are silent; only a dump shows them.
    • 




Common mistakes and debugging


    

  • Relocation bounds inside the section. A short table and no warning. Compare readelf -r's count with (end − start) / 24 in every build (step 5).
    • 

  • Hard-coded console address. Works on the first board, silent on the second (forensic lab). Find the console through /chosen/stdout-path, and keep a second channel (semihosting, a debugger, an LED) for "is it running?".
    • 

  • Trusting your tree source instead of the handed-over tree. Firmware edits trees. Read the tree at the address in x0.
    • 

  • Forgetting ranges. Using bus addresses as CPU addresses on raspi3b writes 0x7e201000, which is not a device. Always translate through every parent.
    • 

  • Assuming the entry level. virt enters at EL1, raspi3b at EL2, a board through TF-A and U-Boot often at EL2. Read CurrentEL.
    • 

  • Compile-time board selection creeping back. An #ifdef for "the board with the odd UART" defeats D10. Write a driver with a compatible string instead.
    • 

  • Comparing builds instead of files. "Same source, same flags" is not "same file": compare SHA-256 of the file you booted.
    •
