Story hook

Mr Haddad has been principal of a large old school for ten years. On his first morning there, long ago, he walked the corridors and knocked on every door: "Who is in here, and what do you teach?" Every room answered with a card on the door that named the subject and the number of seats. He never needed a plan of the building, because the building told him.

This year he takes over a second school, newly built. He knocks on the first door. Nothing. He knocks on the second: a bang from inside and an alarm goes off, because that door leads to the boiler room and nobody is allowed to open it. The caretaker hurries over and hands him a folded sheet: the building plan. It lists every room, what is in it, which key opens it, which light switch has to be on before anybody can work there, and which rooms are closed this year. "Here," says the caretaker, "nobody answers knocks. You read the plan."

A PC is the old school. A system on a chip (SoC) board is the new one. Your kernel, written against a PC, knocks on doors: it scans the PCI bus and reads ACPI tables, and the hardware answers. On an SoC board most devices do not answer a knock, some knocks set off an alarm, and the only reliable description of the machine is a plan written by somebody else: the devicetree. This chapter is about what is different, why, and how a kernel learns to read the plan first.

What you will be able to do

  • Compare a PC and an SoC board across the ten aspects of curriculum section 11.1 (discovery, first code, DRAM set-up, clocks and resets, interrupts and timers, DMA coherency, storage and display, security, documentation, reused IP blocks) and state the consequence of each for your kernel.
  • Read a flattened devicetree blob (DTB) by hand and with your own parser: the header, the structure tokens, #address-cells and #size-cells, reg, ranges, compatible, status, phandle and /chosen.
  • Translate a device's bus address into the CPU physical address by walking ranges properties, and verify the result against an independent view of the machine (QEMU's memory tree).
  • Build an AArch64 kernel image that QEMU's direct-boot path accepts, enters with the DTB address in x0, and that finds its console, memory, CPU count and timer frequency only from the devicetree.
  • Diagnose a crash caused by probing an address nothing decodes, from the exception syndrome, the fault address and addr2line.
Jargon box
System on a chip (SoC)
Simple words: one chip that holds the processor cores and most of the devices a computer needs. Analogy: a whole school in one building, with the boiler room, the library and the classrooms under one roof. Precise: an integrated circuit containing CPU cores, an interconnect, memory controllers, on-chip SRAM and ROM, and many peripheral blocks (UARTs, timers, storage and network controllers), with fixed physical addresses decided by the chip vendor and documented, if at all, in its technical reference manual. C1
Devicetree
Simple words: a data file that describes the hardware of one machine: what is there, at which address, and how the parts are connected. Analogy: the building plan the caretaker hands to a new principal. Precise: a tree of nodes with named properties, defined by the Devicetree Specification, passed to the OS in the flattened binary form (DTB) so that the OS can discover devices that cannot be enumerated. D1
Flattened devicetree blob (DTB)
Simple words: the devicetree packed into one block of bytes that a loader can put in memory. Analogy: the plan folded into an envelope. Precise: a big-endian binary with a 40-byte header (magic 0xd00dfeed, total size, offsets of the structure block, strings block and memory reservation map, version), a structure block of tokens (BEGIN_NODE 1, END_NODE 2, PROP 3, NOP 4, END 9) and a strings block for property names. D1 R2
Compatible string
Simple words: the name in a devicetree node that says what kind of device it is, so the right driver can be chosen. Analogy: the subject written on the door in the building plan, so the principal sends the right interpreter. Precise: the compatible property, a list of strings of the form "vendor,model", most specific first; a driver binds to a node when one of its strings appears in the list. D1
Address translation through ranges
Simple words: working out which CPU address a device really has when the plan writes its address in the local numbering of a bus. Analogy: room "2.14" in the east wing is "E2.14" from the main entrance. Precise: a reg address is in the address space of the node's parent bus; each ranges entry (child address, parent address, length) maps a window of the child space into the parent space; an empty ranges means identity; a missing ranges means the child space is not memory-mapped from the parent. D1
Phandle
Simple words: a number that one node uses to point at another node. Analogy: "see room 8000" written on a door. Precise: a 32-bit value stored in a node's phandle property and quoted in other nodes' properties (clocks, interrupt-parent, resets, pin control) to reference it. D1 R2
Boot ROM (mask ROM)
Simple words: the first program an SoC runs, burned into the chip when it is made. Analogy: the fixed first caretaker at the gate, who never changes and only knows where to find the next person. Precise: read-only code inside the SoC that runs at reset, reads boot-mode pins or fuses, loads the next stage from a boot medium into on-chip SRAM in a vendor-specific format, optionally verifies its signature, and often offers a USB recovery mode. C1
Technical reference manual (TRM)
Simple words: the big book from a chip vendor that describes every register of every block on the chip. Analogy: the architect's full drawings, not the summary plan. Precise: the vendor's programming documentation for one SoC (address map, clock and reset trees, pin multiplexing, each peripheral's registers), whose public availability ranges from complete to none, depending on the vendor. C1
Image header (AArch64)
Simple words: 64 bytes at the very start of an Arm 64-bit kernel file that tell a loader how to place it. Analogy: the label on a delivery box that says "this side up, put it in room 0x80000". Precise: a header with a branch instruction, the text offset, the image size, flags (endianness, page size, placement) and the magic "ARM\x64" at offset 0x38, after the Linux arm64 booting document; QEMU's direct kernel boot recognises it. D2 R7

The idea in pictures

Figure 1 puts the two worlds side by side. On the left, a PC's kernel asks: the PCI bus answers with vendor and device IDs and the size of every register window, and ACPI tables describe the rest. On the right, an SoC kernel is told: the devicetree, prepared before the kernel runs, lists every device with its address and its dependencies, and nothing answers if you do not already know where to look.

Figure 2 follows one question through the tree: "where is my console?" The kernel starts at the DTB address it was handed, goes to /chosen, reads stdout-path, finds that node, checks its compatible, decodes reg with the cell sizes of the parent, translates through any ranges, and only then touches the hardware. The same walk, with different nodes, finds memory, CPUs, the interrupt controller and every other device.

Layer 1 — the kid explanation

A normal PC is a friendly building: you can knock on each door and the room tells you what it is. A small board, like the ones inside phones, robots and routers, is a building where the rooms stay silent. To find anything, the computer needs a plan that somebody wrote down in advance, and it has to switch on the lights and unlock the doors itself before a room can be used. If it guesses and opens the wrong door, an alarm may go off. So the first thing the new computer does is read the plan.

Layer 2 — the student explanation

On a PC, two standards do most of the discovery work. PCI enumeration lets the kernel read a configuration space for each bus, device and function number; every device stores its vendor ID, device ID, class and the sizes of its register windows (BARs) there, so the kernel can find it without knowing in advance that it exists. ACPI tables, handed over by the firmware, describe the parts that are not on PCI: interrupt controllers, timers, power management. Before the kernel runs, firmware has already started the memory, set the clocks and powered the devices. D6 C1

On an SoC board, most devices are blocks inside the chip connected to an internal bus at fixed addresses chosen by the chip designer. These blocks have no configuration space. If you do not know that a UART lives at a certain address, nothing tells you. The description comes from a devicetree: a tree of nodes, one per device, each with a compatible string that names the device type, a reg property with its address and size, and references to the clocks, resets, interrupts and pins it depends on. The boot firmware loads the devicetree into memory and passes its address to the kernel in register x0. D1 D2

The lab shows both worlds on the same build machine. QEMU's PC machine (q35) answers "info pci" with device IDs and BARs that nobody wrote down in advance R6. QEMU's Arm machine (virt) has no such answer for its UART, real-time clock or GPIO: QEMU generates a devicetree for it D5, and our kernel reads that tree to find everything R8. A small scanning program that pokes addresses instead of reading the tree crashes on the fourth address it tries R9. That crash is the forensic lab.

Other differences follow from the same fact that the SoC exposes more and standardises less. The first code is a boot ROM inside the chip, not firmware in a flash chip. Clocks, resets and pins of each block are often left for the OS to set. Many devices are not cache-coherent. Documentation is a technical reference manual per chip, and some vendors do not publish one. Layer 3 goes through all ten aspects.

Why a PC can ask and an SoC cannot

PCI enumeration works because the bus defines a second address space, configuration space, that every device must implement at a location derived from its bus, device and function number. A read of the vendor ID of a slot where no device sits returns all ones, a defined "nobody here" answer, not a fault. The OS then reads each BAR, writes all ones to it, and reads it back to learn the size of the window the device needs; it then assigns an address. The device does not have an address until software gives it one. D6

The q35 run shows the "before" state of that process. QEMU was started with -S, so no firmware has run, and the monitor's info pci lists a host bridge, a virtio device and an e1000 network card with their IDs and BAR sizes, and every BAR address is still the unassigned value 0xffffffffffffffff. The devices are known by asking, before anybody has placed them. R6



An SoC's internal blocks are wired to the interconnect at addresses fixed in silicon. The interconnect decodes an address range per block; there is no second address space and no "nobody here" convention. An access to an address that no block decodes is an error on the interconnect. What the CPU sees then depends on the interconnect: on QEMU's virt machine in this build, a synchronous external abort (the forensic lab); on real chips, an abort, a value of zero, a hung bus, or something else that only the TRM, if it says, can tell you. R9 D3

The devicetree in detail


The devicetree is a tree of nodes. Each node has a name, which by convention is name@unit-address where the unit address is the first address in its reg, and a set of properties: a name and a byte string. The Devicetree Specification defines the standard properties and how to read them; bindings (per device type) define the rest. D1


In memory, the tree is a DTB. Its header is ten big-endian 32-bit words: magic 0xd00dfeed, total size, offset of the structure block, offset of the strings block, offset of the memory reservation map, version, last compatible version, physical ID of the boot CPU, size of the strings block, size of the structure block. The structure block is a stream of 32-bit tokens: BEGIN_NODE (1) followed by the node name as a NUL-terminated string padded to 4 bytes; PROP (3) followed by the value length, an offset into the strings block for the property name, and the value padded to 4 bytes; END_NODE (2); NOP (4); and END (9) at the very end. Property names are stored once in the strings block. D1


The DTB QEMU generated for its virt machine in this build is version 17, total size 1048576 bytes, with a structure block of 6992 bytes and a strings block of 454 bytes; the rest of the 1 MiB is free space that a loader can use to add properties. R2

Four properties deserve rules of their own, because getting them wrong produces bugs that look like hardware faults.


#address-cells and #size-cells belong to the parent. The cell counts used to read a node's reg are the ones declared in its parent, not in the node itself. The default when a parent declares none is 2 and 1. The fdt.h reader encodes this in reg(), which looks up the parent first. D1


reg is a bus address; the CPU may see something else. A node's reg is in the address space of its parent bus. To get the CPU physical address, walk upward: at each bus, find the ranges entry whose child window contains the address and add the offset to its parent address. An empty ranges means the bus is mapped one-to-one. A missing ranges means the child addresses are not memory addresses at all; the CPU nodes, whose reg is the MPIDR affinity value, are the common example, and our device table marks /cpus/cpu@0 as "not translatable" for that reason. D1 R3


status decides whether a node is in use. Absent, "okay" or "ok" mean in use; "disabled" means present but not to be used, which often means "the pins go to something else on this board" or "reserved for the secure world". A kernel that ignores status will drive hardware it does not own; F4-32 shows that crash. D1


compatible is a list, most specific first. The PL011 node lists "arm,pl011" and then "arm,primecell". A driver for the specific block matches the first; a generic driver could match the second. Vendors add a string for their own integration ahead of the generic IP name when the integration has quirks, so a driver can match the quirk without losing the generic fallback. D1



Checking a parser against an independent view


Our DTB reader is our own code, so its output is a claim, not a fact. The lab checks it against a second, independent description of the same machine: QEMU's memory tree, printed by the monitor command info mtree -f, which lists the address ranges QEMU actually routes to each device model. Every address that fdtdump --devices decoded must be the start of a region in QEMU's map. In this build, 41 of 41 were. That does not prove the reader correct on every tree, only that it agrees with QEMU on this one, which is the claim the lab makes. R3 R4 R5








Notice two things in the device table. The PCIe host's first reg entry is at 0x4010000000, above 4 GiB: its configuration window (ECAM). So even on an Arm machine, PCI enumeration exists behind a host bridge that the devicetree describes; the devicetree tells you where the bus is, and then the bus answers questions as it does on a PC. And the GIC's v2m frame is a child node of the interrupt controller, with its address translated through the controller's ranges.



How the kernel receives the tree


The Linux arm64 booting document defines a contract that QEMU's direct kernel boot and U-Boot's booti both follow, and that our kernel adopts: the image starts with a 64-byte header; the loader places it at a 2 MiB-aligned base plus text_offset (or anywhere, if a flag says so); it enters at the first byte with the MMU off, data cache off, interrupts masked, at EL2 or EL1; and x0 holds the physical address of the DTB. x1 to x3 are zero. D2

Three properties of the image matter for the rest of the course. It is position independent: linked at address 0, it applies its own R_AARCH64_RELATIVE relocations at start-up, so the same bytes run at 0x40080000 on virt and at 0x80000 on the Raspberry Pi model of F4-37. It runs with the MMU off, where Device memory rules apply to all accesses and unaligned loads fault, so the compiler is told -mstrict-align and the DTB reader assembles every multi-byte value from bytes. And it knows no addresses: everything after the header comes from the tree. D7 D3

Reused IP blocks: why one driver serves many chips


The UART on QEMU's virt machine is an Arm PL011, and so is the UART on the Raspberry Pi model of F4-36 and F4-37, at a different address with a different clock. The same is true of many blocks across vendors: SoC designers license IP blocks and wrap them in their own glue (address, clocks, resets, interrupts, sometimes extra registers). The compatible string reveals the IP, so the driver for "arm,pl011" is written once, and each board's devicetree tells it where the block is and which clock feeds it. C1 D4


PrimeCell blocks also carry identification registers at the top of their 4 KiB window (offsets 0xFE0 to 0xFFC): a part number and a fixed "cell ID" value. The forensic lab's scanner reads the cell ID at 0x08000000 and gets 0xb105f00d. That looks like a discovery mechanism, and it is one only inside a known window: it says "the block at this address, if one is there, is a PrimeCell". It cannot tell you where the windows are. D4 R9

How the hardware actually does it


Inside an SoC, the CPU cluster issues a physical address onto an interconnect (on Arm-based chips, an AMBA fabric of AXI, AHB and APB buses with bridges between them). Each slave port of the interconnect has an address decoder: a range of addresses routed to one peripheral's registers or one memory controller. Slow peripherals such as UARTs sit behind a bridge on a narrow peripheral bus, which is why the PL011's register clock is called apb_pclk: the clock of the APB bus interface. The functional clock (uartclk) is a separate input that sets the baud-rate generator. The devicetree lists both because both must be running for the device to work, and they may come from different places in the SoC's clock tree. D4 R2


An access to an address that no decoder claims ends at a default slave that answers with an error, and the error travels back to the core as an external abort. In Arm's exception model, a data access that aborts is reported in ESR_ELx with exception class 0x25 ("data abort taken without a change in exception level") and a fault status code; 0x10 is "synchronous external abort, not on a translation table walk". FAR_ELx holds the faulting address and ELR_ELx the address of the instruction. The forensic run shows all three. D3 R9


Many blocks also need their clock running and their reset released before their registers respond. Whether a gated block's registers read as zero, return stale data, or stall the bus is a design decision of the chip, and the TRM is the only place to learn it. F4-35's simulated SoC models the "reads as zero" choice, because it is the one that produces the course's forensic case.

Safety
On a real board, use a 3.3 V USB-to-serial adapter on the debug UART pins (never 5 V, which can damage the SoC), and check the board's documentation for the voltage of its UART pins before connecting anything. Do not run address-scanning code on real hardware: an access to the wrong address can do more than abort, for example start a write to a flash controller or change a power regulator. Keep a recovery path (an SD card you can rewrite, a USB recovery mode) before writing anything to on-board storage. See the university safety rules.



Worked example


Question. Using only the dump above, find the CPU physical address and size of the UART, its clock rate, and the amount of RAM. Then translate a second address through a ranges window, by hand.


Step 1: cell sizes. The UART node is a child of the root. The root says #address-cells = <0x2> and #size-cells = <0x2>. So each reg entry of the UART is four cells: two for the address, two for the size. R2


Step 2: decode reg. reg = <0x0 0x9000000 0x0 0x1000>. Address = (0x0 << 32) | 0x9000000 = 0x9000000. Size = (0x0 << 32) | 0x1000 = 4 KiB.


Step 3: translate. The parent is the root, the top of the tree: there is no bus above to translate through, so the CPU address is 0x9000000. QEMU's memory tree has a region pl011 at 0000000009000000-0000000009000fff, which agrees in both start and size. R4


Step 4: the clock. clocks = <0x8000 0x8000> with clock-names = "uartclk", "apb_pclk". The provider with phandle = <0x8000> is apb-pclk, whose #clock-cells is 0, so each entry is one cell, the phandle alone: two entries, both the same clock. Its clock-frequency is 0x16e3600 = 1×166 + 6×165 + 14×164 + 3×163 + 6×162 = 16777216 + 6291456 + 917504 + 12288 + 1536 = 24000000 Hz. F4-35's driver model prints the same number from the same tree. R2


Step 5: memory. memory@40000000: reg = <0x0 0x40000000 0x0 0x10000000>: 0x10000000 bytes = 256 MiB at 0x40000000. The kernel's own report agrees. R8


Step 6: a ranges window. Take platform-bus@c000000: #address-cells = 1, #size-cells = 1, and ranges = <0x0 0x0 0xc000000 0x2000000>. Each entry has child-address cells (1, the bus's own), parent-address cells (2, the root's) and size cells (1, the bus's own): 4 cells, one entry. It maps child addresses 0 to 0x1ffffff to parent addresses 0x0c000000 to 0x0dffffff. A hypothetical child with reg = <0x10000 0x1000> would be at 0x10000 − 0 + 0x0c000000 = 0x0c010000 for the CPU. (QEMU's platform bus has no children here; it is used for dynamically added devices.)


Step 7: the same rule on another machine. In F4-36's Raspberry Pi description, the soc bus has ranges = <0x7e000000 0x3f000000 0x01000000>, and the UART's reg starts at 0x7e201000. Inside the window (0x7e201000 − 0x7e000000 = 0x201000 < 0x01000000), so the CPU address is 0x3f000000 + 0x201000 = 0x3f201000. QEMU's raspi3b memory tree shows the UART at 0x7e201000 in the peripheral bus view and at 0x3f201000 in the CPU view. A kernel that uses reg without translating writes to 0x7e201000 and nothing appears on the serial line. R11


Now run the kernel and compare: it reports the same console, memory and clock from the same tree, plus the CPU count from /cpus and the counter frequency from the CPU's own register. R8




The counter frequency, 62500000 Hz, comes from CNTFRQ_EL0, which firmware sets on real hardware and QEMU sets on its virt machine. The devicetree's timer node may also carry a clock-frequency property, used when firmware failed to program the register; this tree has none.

Where the analogy breaks


    

  • A building plan is drawn once for a building. A devicetree is often written per board and edited by every loader on the way: QEMU and U-Boot add /chosen properties, fix the memory size, or remove nodes. F4-37 shows QEMU's loader rewriting the memory node of our Raspberry Pi tree. The plan in the kernel's hand may differ from the plan in the source repository.
    • 

  • A wrong room number on a plan sends the principal to the wrong door, and he notices. A wrong address in a devicetree can produce silence (a write to nothing that does not abort), zeros, or a crash minutes later, with nothing pointing at the tree.
    • 

  • In a school, every room exists whether or not it is on the plan. In a devicetree, status = "disabled" marks rooms that exist but belong to someone else this year (another processor, the secure world), and entering them is not only useless but harmful.
    • 

  • A PC is not entirely a "knock on doors" building either: its firmware also hands over a description (ACPI) for everything PCI cannot enumerate, and an Arm server may use the same ACPI. The difference is of degree: how much is described rather than discovered.
    • 




Common mistakes and debugging


    

  • Using a node's own #address-cells to read its reg. The cell counts come from the parent. Symptom: addresses that look shifted by 32 bits or sizes of zero. Check: print the parent's two properties next to the decoded value.
    • 

  • Skipping translation. Symptom: the console works on QEMU virt (whose devices sit under the root) and is silent on a board whose devices sit under a soc bus with ranges. Check: compare reg with the address the TRM gives for the CPU view.
    • 

  • Ignoring status. Symptom: the kernel picks the first PL011 and it is a secure-world UART; the first access aborts. F4-32's lab shows this exact crash.
    • 

  • Hard-coding "only for now". One fixed UART address for early debugging tends to survive into the release. F4-37's forensic lab is a kernel that works on one platform and is silent on the other for this reason. Keep early debug addresses in a separately named path that the build disables, or read them from the tree from the first day.
    • 

  • Scanning for devices. Reading addresses that the tree does not name, to "see what answers", aborts on QEMU and may do worse on silicon (this chapter's forensic lab).
    • 

  • Unaligned loads with the MMU off. With the MMU off, all data accesses are treated as Device memory and an unaligned load faults. The compiler may merge byte loads into a word load unless told -mstrict-align. Symptom: an alignment fault inside the DTB parser on the first odd-length property name.
    • 

  • Trusting your parser. Check it against a second view: QEMU's info mtree, the dtc decompiler on another machine, or the kernel log of a known-good Linux boot on the board.
    •

Summary


    

  • A PC's hardware largely describes itself (PCI enumeration, ACPI) and its firmware sets it up; an SoC's blocks sit at fixed addresses that only a description, the devicetree, tells you, and many need clocks, resets and pins set by the OS.
    • 

  • The DTB is a header, a token stream and a strings block; properties are untyped bytes whose meaning comes from the specification and the bindings.
    • 

  • reg is decoded with the parent's #address-cells and #size-cells and translated to a CPU address through every ranges above it; status decides whether you may use a node; compatible is a list, most specific first.
    • 

  • The arm64 boot contract hands the kernel the DTB address in x0; a position-independent image runs wherever a loader places it.
    • 

  • Check your parser against an independent view of the machine; in this build, 41 of 41 decoded addresses matched QEMU's map.
    • 

  • Never scan for devices on an SoC: an address nothing decodes aborts on QEMU and may hang or do worse on silicon.
    •

Forensic lab answer key


    

  1. ESR_EL1 = 0x96000010: exception class 0x25 (bits 31:26 = 0b100101), a data abort at the current exception level; fault status 0x10, synchronous external abort not on a table walk. FAR_EL1 = 0x8030ff0, the first ID word of the window at 0x08030000. ELR_EL1 0x400817c0 minus the load address 0x40080000 is offset 0x17c0, which addr2line places in k::rd32 inlined into kmain at blindprobe.cc:24, the ID read.
    2. 

  2. 0x08000000 is the GIC distributor (region gic_dist), whose model implements the ID registers. 0x08010000 is gic_cpu (0x08010000–0x08011fff) and 0x08020000 is gicv2m: both decode the address but do not implement offset 0xff0, and read as zero. 0x08030000 lies in no region: nothing decodes it, and QEMU's virt machine reports an external abort.
    3. 

  3. Hypothesis A, "QEMU is broken": ruled out, because the fault address is exactly the first address outside all regions of the map and the three earlier reads behave as the map predicts. Hypothesis B, "an alignment or MMU fault in our code": ruled out by the fault status (0x10, external abort, not an alignment fault 0x21 or translation fault). Hypothesis C, "the scan range is wrong": correct, the routine reads addresses the machine never promised.
    4. 

  4. It proves that something decodes 0x08010000 + 0xff0 and returns zero. It does not prove that no device is there (the GIC CPU interface is) or that the device is off. On a real SoC a gated block may also read as zero (F4-35).
    5. 

  5. Fix: delete the scan; find devices from the devicetree passed in x0, as Listing 5 does. Test: run the kernel on QEMU with a second machine configuration (another -M option or a different GIC version) and require that the boot completes and that every printed address is a region start in that machine's info mtree (Listing 3).
    6. 

  6. On silicon, an access to an undecoded or unclocked address may hang the interconnect (no abort, no way to report), and an access to a decoded but wrong address may have side effects: reading a FIFO pops data, reading some status registers clears them, and neighbouring windows may belong to flash, power or security controllers. The emulator gave a clean abort; a board may give nothing at all.
    7.
