Story hook

A supply teacher works in a different school every week. In the first year of the job, every school was a new puzzle: one kept the registers in the head's office, one in a cupboard by the gym, one gave them out at the gate; one had the fire assembly point on the field, one in the car park. Every Monday morning was spent finding things.

Then the county introduced an inspection checklist. A school that passes it keeps the registers in the staff room, in a drawer labelled "registers", and the fire plan on the inside of each classroom door. The schools are as different as before, with different buildings, different heating, different caretakers, but the few things a visitor needs on the first morning are always in the same place, under the same label. The supply teacher now walks into a school she has never seen and starts teaching at nine.

An operating system image for Arm boards faces the same Monday morning on every board. Arm SystemReady is the checklist; EBBR is the version of it for boards that run U-Boot. This chapter runs a small UEFI program of your own on QEMU's Arm firmware and looks in the labelled drawer: the UEFI configuration table, where the firmware leaves either ACPI tables or a devicetree.

What you will be able to do

  • Explain the problem SystemReady and EBBR solve, and distinguish the hardware requirements (BSA, SBSA), the firmware requirements (BBR, EBBR) and the compliance tests (ACS), as described in curriculum 11.3.
  • Build an AArch64 UEFI application (PE32+, machine 0xAA64) with clang and LLD, without EDK II headers, and run it from the UEFI Shell of QEMU's firmware.
  • Read the UEFI configuration table, recognise ACPI, devicetree and SMBIOS entries by GUID and by content, and list the ACPI tables an Arm server-style platform provides.
  • Explain why, under UEFI, the memory map comes from GetMemoryMap and not from the devicetree's memory node.
  • Diagnose a loader that cannot find a devicetree that is present.
Jargon box
Arm SystemReady
Simple words: Arm's certification that a computer will boot ordinary, unmodified operating-system images. Analogy: the county's school inspection checklist. Precise: Arm's compliance programme combining hardware requirements (BSA, SBSA), firmware requirements (BBR, which includes EBBR for devicetree systems) and test suites (ACS); a certified system boots generic OS images through UEFI. Arm has reorganised its bands over time; read the current requirements document for today's names. C1 D3
EBBR (Embedded Base Boot Requirements)
Simple words: the rules a small Arm or RISC-V board's firmware follows so that a standard OS can boot on it. Analogy: the short version of the inspection checklist for small schools. Precise: an open specification maintained by Arm and the community that defines the subset of UEFI that embedded firmware (U-Boot or EDK II) must provide and where the devicetree comes from (the UEFI configuration table). C1 D2
BSA and SBSA
Simple words: the minimum hardware an Arm system must have for a generic OS: a standard interrupt controller, timer, UART and so on. Analogy: the part of the checklist about the building itself: fire doors, a staff room. Precise: Arm's Base System Architecture and Server Base System Architecture specifications: required GIC version and behaviour, generic timer, watchdog, UART, PCIe behaviour and more. C1 D4
Configuration table (UEFI)
Simple words: a list, kept by the firmware, of the extra tables it is handing to the OS, each with an identifying number. Analogy: the drawer labelled "registers". Precise: an array of (GUID, pointer) pairs referenced from the EFI System Table; well-known GUIDs identify ACPI 2.0+ tables, SMBIOS 3 entry points and the devicetree blob. D1 R3
GUID
Simple words: a 128-bit number used as a name that nobody else will pick by accident. Analogy: a label printed by the county, not handwritten by each school. Precise: a globally unique identifier stored by UEFI as a 32-bit, two 16-bit and eight 8-bit fields; the first three are little-endian in memory and printed most significant digit first, the last eight are bytes in order. D1
RSDP and XSDT (ACPI)
Simple words: the starting point of ACPI and the list of all other ACPI tables. Analogy: the index card that says where the folders are, and the list of folders. Precise: the Root System Description Pointer (signature "RSD PTR ", revision 2 or later for ACPI 2.0+) holds the 64-bit address of the Extended System Description Table, whose body is an array of 64-bit pointers to tables, each beginning with a four-character signature. D5 R2
Generic OS image
Simple words: one operating-system file set that boots on many different boards without being rebuilt. Analogy: the supply teacher who starts at nine in any school. Precise: an OS installation medium with a UEFI loader at the removable-media default path and no board-specific code selected at build time; hardware is learned at run time from ACPI or a devicetree passed through UEFI. C1

The idea in pictures

Figure 1 shows the contract. Below the line, every board is different: its boot ROM, its BL2, its DRAM, its devices. Above the line, the OS image sees one interface: UEFI boot services, a memory map, and a configuration table that holds a hardware description. SystemReady and EBBR are the rules for that line.

Figure 2 zooms into the labelled drawer: how a loader goes from the EFI System Table, which it receives as an argument, to the hardware description.

Layer 1 — the kid explanation

Every small computer board is built differently, so for a long time every board needed its own special copy of the operating system. Some companies agreed on a rule: whatever is different inside, the board's first program must leave a few important things in the same place, with the same labels, before it starts the operating system. Then one copy of the operating system can start on all the boards that follow the rule, because it knows where to look.

Layer 2 — the student explanation

Without a standard, every Arm board needs a board-specific kernel image and board-specific boot instructions: which address to load the kernel at, which devicetree file to pass, which boot command to type. Curriculum 11.3 states the fix in one sentence: a system that follows Arm's SystemReady rules boots generic, unmodified operating-system images through UEFI. C1

UEFI is the same firmware interface you used on PCs in OS301: the firmware loads a PE32+ application from a FAT partition, passes it a pointer to the EFI System Table, and offers boot services (memory allocation, file access, the memory map) until the OS calls ExitBootServices. On Arm, the application's machine type is AArch64 (0xAA64), and the calling convention is the normal Arm one. D1 D8

The hardware description travels in the configuration table, an array of (GUID, pointer) pairs referenced from the System Table. Servers put ACPI tables there, like PCs. Embedded boards that follow EBBR put a devicetree there, under its own GUID. The OS loader looks up the GUID and finds everything else from that one table. D1 D2

The lab builds a UEFI application, ebbrprobe.efi, and runs it twice on QEMU's virt machine with the EDK II firmware: once with ACPI enabled, once without. In the first run the configuration table holds an ACPI RSDP and the probe lists eight ACPI tables; in the second it holds a devicetree, the same kind of tree as in F4-31, and the probe reads it with the same fdt.h. Same firmware, same application, two hardware descriptions. R2 R3

Layer 3 — the engineer's depth

The pieces of SystemReady

Curriculum 11.3 describes SystemReady as a programme built from separate documents, which is the useful way to think about it even as Arm renames the bands. C1

  • Hardware: BSA and SBSA. The Base System Architecture defines the minimum hardware for a generic OS (GIC, generic timer, watchdog, a UART, PCIe behaviour); the Server Base System Architecture adds server requirements. A board that lacks, for example, a standard interrupt controller cannot be served by a generic image, whatever its firmware does. D4
  • Firmware: BBR and EBBR. The Base Boot Requirements define the firmware side: which UEFI services, which ACPI tables or which devicetree rules. EBBR is the subset for devicetree-based embedded systems, written so that U-Boot can implement it. D3 D2
  • Tests: the Architecture Compliance Suites (ACS). Arm's test suites check both the hardware and the firmware against the requirements. C1
  • Bands. Historically SR (servers: SBSA hardware, UEFI and ACPI per BBR), ES (embedded servers: BSA, UEFI and ACPI) and IR (IoT: UEFI as defined by EBBR, in practice from U-Boot, with a devicetree). Arm has since reorganised the bands; the curriculum tells you to read the current requirements document for today's names, and so does this chapter. C1
Not verified — check before relying on this

The division of SystemReady into BSA/SBSA, BBR/EBBR and ACS, and the historical band names, are taken from curriculum 11.3; the documents themselves (Arm "SystemReady Requirements", "Base Boot Requirements", "Base System Architecture", "Server Base System Architecture", the EBBR specification) were not opened in this build. What each requires in detail, and the current band names, must be read from their current releases. RISC-V's analogues (the Boot and Runtime Services specification, the RVA23 profile) are named in the curriculum D9; check their ratification status when you start.

A UEFI application for AArch64 without EDK II

The build container has no EDK II headers or build system, so the lab writes the few declarations it needs (efi_a64.h) and builds with clang for the aarch64-unknown-windows target, which produces Microsoft-style object files, then links with lld-link as an EFI application. The result is a PE32+ file: optional-header magic 0x20B, machine 0xAA64, subsystem 10 (EFI application), entry point at 0x1000. R1 D8



Two consequences of the Windows-style target are worth knowing. Its data model is LLP64: long is 32 bits, so 64-bit values must be printed as unsigned long long with %llu and %llx (the course's printf and the probe do this; the first build attempt failed on it). And on AArch64, unlike x86-64, UEFI uses the standard Arm procedure-call standard, so function pointers in the UEFI tables need no special calling-convention attribute. The same fdt.h and kbase.cc as the bare-metal kernel compile unchanged, because they include only <stddef.h>, <stdint.h> and <stdarg.h>. D1 R1

The runs prove only that this firmware accepted code built on them: the probe printed sensible values for every field it read. A layout error in a slot the probe does not use would not show.

A kernel that wants to be generic on Arm servers must parse these ACPI tables, and the interesting parts of ACPI on Arm are tables, not AML bytecode: interrupt routing comes from the MADT and GTDT, not from methods. That is a smaller job than ACPI on PCs, but still a second description language beside the devicetree. This course's kernel stays with the devicetree; the decision is recorded for the owner in NOTES.md.



What the firmware hands over with a devicetree


With acpi=off, the same firmware publishes a devicetree instead of the RSDP. The probe identifies it by its magic, reads it with the course's fdt.h, and finds the same machine as F4-31: root compatible "linux,dummy-virt", one CPU node, /chosen with the PL011 as console. The blob is 1052672 bytes, 4096 more than the tree QEMU handed directly to the kernel in F4-31; the firmware hands over its own copy, and this build did not investigate what it changed. R3




The devicetree's GUID in this firmware is b1b621d5-f19c-41a5-830b-d9152c69aae0. The probe looks it up by that value and finds it; on the ACPI run the same lookup finds nothing. This is the lookup a real loader makes: by GUID, not by scanning every table for a magic number. The probe scans by content as well only because it is a teaching tool that wants to name tables it does not know. R3 R2


Not verified — check before relying on this
The GUID value in the probe was copied from this build's own run, not from a specification. Likewise, the ACPI 2.0 GUID shown at entry [7] of the ACPI run (8868e871-e4f1-11d3-bc22-0080c73c8881) and the SMBIOS 3 GUID at entry [5] were observed, not looked up. Under UEFI, the memory map is the UEFI memory map


Both runs report 471 MiB of conventional (free) memory in 32 or 33 descriptors, lowest at 0x40000000, out of the 512 MiB given to QEMU. The rest is firmware code and data, boot services data that the OS may reclaim after ExitBootServices, runtime services memory it must never touch, and reserved regions. The devicetree's memory node still says "all 512 MiB at 0x40000000": it describes the hardware, not who is using it. R3 D1


That is why the probe prints "UEFI's memory map is the one to use". A kernel booted through UEFI that takes its free memory from the devicetree's memory node will hand out pages that hold UEFI runtime services or firmware-reserved tables. The fix is the A3-style loader of the curriculum, rebuilt for AArch64: it calls GetMemoryMap last, calls ExitBootServices with that map's key, and passes the map (or a summary) to the kernel along with the devicetree. C1


Not verified — check before relying on this
That EBBR (and the Linux EFI stub's practice) requires the OS to take memory from the UEFI memory map and treat the devicetree's memory nodes as superseded is the author's memory, not checked in the EBBR specification in this build. What the run shows is the difference between the two descriptions on this firmware.



What EBBR asks of a U-Boot board, in outline


EBBR's job is to make U-Boot-based boards look, at the UEFI interface, enough like servers that the same distribution image boots. In outline, and subject to the box below: UEFI boot services must work; runtime services may be limited (for example, setting variables at run time may be unsupported, since the variable store may be on the same eMMC the OS owns); the devicetree, if used, goes in the configuration table and must describe the hardware, not a particular OS's view; firmware must reserve its own memory in the UEFI memory map; PSCI is the way to start CPUs on AArch64; and a removable medium with a loader at the default path (on AArch64, \EFI\BOOT\BOOTAA64.EFI) must boot without configuration. U-Boot implements this through its UEFI subsystem and "standard boot". D2 D10


Not verified — check before relying on this
Every requirement in the previous paragraph is from the author's memory of the EBBR specification and U-Boot's documentation; neither was opened in this build, U-Boot was not available, and requirements change between EBBR releases. The default removable-media file name BOOTAA64.EFI is from memory of the UEFI Specification's boot manager chapter and was not tested here (the lab started the probe from startup.nsh in the UEFI Shell instead). Read the current EBBR release before claiming that a board or a loader complies.



How the hardware actually does it


Nothing in this chapter is hardware in the narrow sense: UEFI and ACPI are software interfaces. What makes them work on real Arm hardware is the part below the line in Figure 1. The firmware (EDK II for servers and some boards, U-Boot with its UEFI layer for most embedded boards) is built per board, with drivers for that board's storage, console and clocks, and it presents the standard interface above. The BSA/SBSA rules constrain the hardware itself so that a generic OS can drive what remains after firmware hands over: a GIC of a known architecture version, the generic timer, a UART a generic kernel can drive (the SPCR table or stdout-path says which), and PCIe that behaves as PCIe should. C1 D4


On the boards in curriculum 11.4, the status varies: some have SystemReady-certified firmware, many have mainline U-Boot whose UEFI support makes them EBBR-like in practice, and some (for example vendor-locked phones) offer only the vendor's chain. F4-34 turns that into a selection procedure. C1


Not verified — check before relying on this
Untested on hardware. The probe ran only on QEMU 8.2.2 with the EDK II build shipped in the Ubuntu package qemu-efi-aarch64 2024.02-2ubuntu0.10. It was not run on any SystemReady-certified system or on U-Boot's UEFI implementation. Which boards are certified, and for which band, must be checked on Arm's current list.


Safety
Running a UEFI application from a USB stick or SD card does not change the board. Changing firmware settings, UEFI variables or the boot order on a board you depend on can make it fail to boot; changing Secure Boot keys can lock you out of your own installation. Experiment on QEMU first, then on a spare board with a known recovery path. See the university safety rules.



Worked example


Question. The probe printed [6] b1b621d5-f19c-41a5-830b-d9152c69aae0. What 16 bytes does the firmware store for this GUID, and what must a loader's constant look like to match them?


Step 1: the fields. UEFI stores a GUID as a 32-bit value, two 16-bit values and eight bytes (efi_a64.h, struct Guid). The printed form shows them as a-b-c-d0d1-d2…d7: a = 0xb1b621d5, b = 0xf19c, c = 0x41a5, d = 83 0b d9 15 2c 69 aa e0. D1


Step 2: the bytes. On a little-endian CPU, a is stored d5 21 b6 b1, b as 9c f1, c as a5 41, and d in order: d5 21 b6 b1 9c f1 a5 41 83 0b d9 15 2c 69 aa e0.


Step 3: the constant. A C++ initialiser with the same field split, {0xb1b621d5, 0xf19c, 0x41a5, {0x83, 0x0b, 0xd9, 0x15, 0x2c, 0x69, 0xaa, 0xe0}}, produces exactly those bytes, because the compiler stores each field in the CPU's byte order. That is the probe's kDtbGuid. Copying the printed string into a byte array in printed order would give b1 b6 21 d5 … and never match.


Step 4: the comparison. The probe's same() compares all 16 bytes. One wrong digit anywhere makes the lookup fail silently: there is no "near miss". The run with ACPI shows the expected "not found" (no devicetree at all); the forensic lab shows an unexpected one. R2 R4


Step 5: free memory. The probe sums NumberOfPages of every descriptor of type 7 (conventional memory) and multiplies by 4096: 471 MiB in this run. Every descriptor is DescriptorSize bytes apart (48 here), which can be larger than the structure the loader knows (40 bytes in efi_a64.h); the loop steps by the firmware's size, not by sizeof. R3

Watch out
The probe trusts the firmware's pointers: it reads the XSDT and every table header without checking lengths or checksums. A loader for real use validates the RSDP checksum and the XSDT length before following pointers, and handles an RSDP revision below 2 (no XSDT) without crashing.


The run script feeds the firmware's serial output through uefi_clean.py, which turns the firmware's screen-control escape sequences into line breaks and trims the shell's countdown, so the recorded output is readable text; the trimming is marked "[...]" in the output.



Where the analogy breaks


    

  • A school inspection is done by an inspector. SystemReady certification uses Arm's test suites, but the OS still meets firmware bugs that the tests did not cover; "certified" reduces Monday-morning surprises, it does not remove them.
    • 

  • The supply teacher only needs the registers and the fire plan. A real OS needs drivers for everything beyond the minimum the standard guarantees: the standard gets you a console, interrupts, timers and storage to boot from, not the board's camera or GPU.
    • 

  • In the county, every school has the same kind of register. On Arm, the drawer may hold two different languages, ACPI or devicetree, and a generic OS must read both, as the lab shows with one firmware.
    • 

  • A checklist is static. Firmware is software that keeps running: UEFI runtime services and BL31 remain in memory beside the OS, and a bug in them is a bug in your system.
    • 




Common mistakes and debugging


    

  • Writing a GUID constant in printed byte order. The first three fields are little-endian in memory. Symptom: lookup "not found" for a table you can see. Check: print the 16 bytes of both GUIDs.
    • 

  • Using sizeof(MemoryDescriptor) to step through the memory map. The firmware's descriptor size (48 bytes here) can be larger than the structure you know. Symptom: garbage types after the first few entries.
    • 

  • Taking free memory from the devicetree under UEFI. Symptom: crashes after ExitBootServices when the kernel overwrites runtime services or reserved tables. Use the UEFI memory map.
    • 

  • Printing 64-bit values with %lu in a UEFI build. The Windows-style target is LLP64: long is 32 bits. With -Wformat and -Werror the build fails, which is the good outcome.
    • 

  • Assuming one description. A generic loader must handle a configuration table with ACPI only, devicetree only, or both (the probe reports "devicetree AND ACPI" for the last case), and decide which the kernel uses.
    • 

  • Debugging blind. The UEFI Shell can show configuration tables and memory maps with its own commands (for example memmap, dmem); compare your probe's output with the shell's. These commands were not run in this build; check their names in your shell.
    •

Lab


Goal. Build an AArch64 UEFI application, run it on QEMU's EDK II firmware with ACPI and with a devicetree, and read the hardware description from the configuration table. This lab prepares the UEFI path of milestone D10, whose build step is "Your A3 loader built for AArch64 and launched by U-Boot's UEFI; board support expressed only as drivers matched by compatible strings, never as compile-time board selection", and whose first acceptance test is: "One kernel file, byte-identical, boots on QEMU virt and on the board; on both, the serial log shows memory size, CPU count and timer frequency matching the platform, and the B9/B10 tests pass on all cores." C1


Hardware and software needed. No hardware. The build used Ubuntu clang version 18.1.3 (1ubuntu1), Ubuntu LLD 18.1.3, QEMU emulator version 8.2.2 (Debian 1:8.2.2+ds-0ubuntu1.18) and the firmware /usr/share/qemu-efi-aarch64/QEMU_EFI.fd from the Ubuntu package qemu-efi-aarch64 2024.02-2ubuntu0.10, as printed in the logs. Run university/labs/run_lab.sh university/labs/F4-33 from the repository root; each QEMU run takes up to 90 seconds.


Safety. None beyond normal computer use; see the safety box above before changing firmware settings on a real board.

Forensic lab


Scenario. A team ports its AArch64 OS loader from an ACPI server to an EBBR-style board. On the board the loader prints "no devicetree; trying ACPI", finds no ACPI either, and refuses to boot. The firmware engineer insists the devicetree is there. To settle it, the team runs the loader's diagnostic build on QEMU with a devicetree (acpi=off), where the reference probe of this chapter finds the tree.

Mini-project


An AArch64 UEFI loader for the course kernel. Turn the probe into the curriculum's A3-style loader for AArch64: read kernel.bin (the F4-37 image) from the same FAT volume with the Simple File System protocol, allocate memory for it at a 2 MiB-aligned address plus its header's text_offset, find the devicetree by GUID (and refuse to boot without one), get the memory map, call ExitBootServices with the map key (retrying if the key changed), and jump to the kernel with x0 = DTB. Pass the UEFI memory map to the kernel by adding a /chosen property that points to a copy of it, and make the kernel prefer it to the memory node. This is D10's build step for QEMU. C1


Rubric. The F4-37 kernel boots through the loader on QEMU virt with acpi=off and prints the platform's memory, CPU count and timer frequency (3). ExitBootServices is handled correctly, including the retry when the map key changes, shown by a test that forces a change (2). The kernel's free memory comes from the UEFI map, and the log shows the difference from the memory node (2). The loader refuses, with a clear message naming the GUID it searched for, when started with acpi=on (1). Every UEFI structure the loader adds to efi_a64.h is checked against the specification and the check is recorded (2).



Summary


    

  • SystemReady makes generic OS images boot on certified Arm systems by fixing the firmware interface (UEFI, ACPI or devicetree) and the hardware minimum (BSA, SBSA), checked by the ACS; EBBR is the firmware subset for U-Boot-style devicetree boards.
    • 

  • Under UEFI, the hardware description is found through the configuration table: ACPI (RSDP, then XSDT and its tables) or a devicetree, each under a GUID.
    • 

  • GUIDs are stored with their first three fields little-endian; a loader's constant must use the same field split, and one wrong digit means "not found".
    • 

  • The UEFI memory map, not the devicetree's memory node, says which memory the OS may use.
    • 

  • One firmware can provide either description: on QEMU's EDK II, acpi=on gave ACPI only and acpi=off gave a devicetree only.
    • 

  • AArch64 UEFI applications are PE32+ (machine 0xAA64); built with a Windows-style target they are LLP64.
    •
