Story hook

The new principal of F4-31 now has the building plan in hand. On Monday morning he sends interpreters to the rooms the plan lists: the French interpreter to room 12, where the plan says a French-speaking visitor waits; the sign-language interpreter to the hall. At room 12 the interpreter finds the door locked, the lights off and the chairs stacked. She sits in the dark corridor, waits, hears nothing, and writes in her report: "Visitor said nothing." The report is filed. Nobody questions it, because it is a report, and reports are trusted.

Room 12 was not empty. Its visitor was sitting in the dark behind a locked door, unable to hear the knock. The plan said, in small print, "needs the east-wing lights (switch 2) and the east door (key 2)". Someone had switched on the lights in the west wing (switch 3) instead.

On an SoC, many devices behave like room 12. Before their registers answer, their clock must run, their reset line must be released, and their pins must be connected to the right function. If any of that is wrong, many devices do not raise an error. They read as zero, and a driver that does not check turns zero into a plausible-looking result: a temperature of 0.000 °C, an empty status, a silent UART. This chapter builds the driver model that does the switching on, in the right order, from the devicetree, and then works through the course's forensic case, "Device reads all zeros".

What you will be able to do

  • Build a driver model that creates a device for every devicetree node with a compatible, matches drivers by compatible string from a table the linker assembles, and probes them in passes.
  • Implement providers for clocks, interrupt controllers, pins and (in the simulated SoC) resets, resolve consumers' clocks, resets and pin properties through phandles and #…-cells, and defer a probe until its providers exist.
  • Show on QEMU's virt machine that every supported node is bound by the generic mechanism and that probing works when consumers are listed before providers: the QEMU acceptance tests of milestone D8.
  • Verify in a probe that a device really answers (identification registers, a counter that moves) before reporting it bound.
  • Diagnose a device that reads all zeros from the devicetree and a register dump: a clock left gated because the tree names the wrong clock.
Jargon box
Driver model
Simple words: the part of the kernel that decides which driver handles which device, and in what order they start. Analogy: the office that sends each interpreter to the right room at the right time. Precise: the kernel's set of device records, driver descriptors, the matching rule (here: compatible strings) and the probe sequence, including retries for devices whose dependencies are not ready. C1
Deferred probe
Simple words: putting off a device's start-up until the things it depends on are ready, and trying again later. Analogy: the timetable postpones a lesson until the room is ready. Precise: a probe result meaning "a provider I need (clock, reset, interrupt controller, pin controller, regulator) has not been probed yet"; the driver model keeps the device waiting and retries after other probes succeed, stopping when a full pass makes no progress. D3 R2
Clock provider and consumer
Simple words: a clock controller hands out clocks; a device that needs one says which, in the devicetree. Analogy: the light switches of a wing, and the note on a room's door saying which switch it needs. Precise: a provider node has #clock-cells; a consumer's clocks property is a list of (phandle, n specifier cells) entries, with n taken from the provider, optionally named by clock-names. D1 D2
Clock gating
Simple words: switching a block's clock off to save power, which also stops the block from working. Analogy: the lights in a wing switched off. Precise: a gate in the SoC's clock tree, controlled by a register bit, that stops the clock to one block; what a gated block does on a register access is a property of the chip (reads as zero, stale data, bus error or a hang), documented in its TRM if at all. D5
Reset controller
Simple words: the block that holds other blocks in their starting state until software lets them go. Analogy: the locked door of a room. Precise: a provider with #reset-cells whose lines hold blocks in reset; a consumer's resets property names the line to release (and optionally reset-names). D2
Pin multiplexing (pin control)
Simple words: choosing which of several jobs a chip's pin does, for example GPIO, UART or SD card. Analogy: arranging the furniture of a room for this lesson, not the last one. Precise: per-pin function-select registers in a pin controller, set by the OS (or firmware) according to pin configuration properties referenced from the consumer's node; Linux uses pinctrl-0 and pinctrl-names with vendor-specific child nodes. D2 D6
Linker-section driver table
Simple words: a list of drivers that the build tools assemble automatically from every driver file. Analogy: each interpreter signs a sheet on arrival; the office reads the sheet. Precise: each driver places a descriptor in a named section with __attribute__((used, section(...))); the linker script collects the section and defines start and end symbols, so the driver core needs no central list. D4 R1

Layer 1 — the kid explanation

A computer chip has many small helpers inside it, and most of them are asleep when it starts. To wake one up, the computer has to do three things in order: give it a heartbeat (a clock), let go of its "stay still" button (a reset), and plug its wires into the right sockets (the pins). The building plan says which heartbeat, which button and which sockets each helper needs. If the computer wakes up the wrong heartbeat, the helper stays asleep and every answer it gives is "nothing", which can look like a real answer if nobody checks.

Layer 2 — the student explanation

In DR301 you built a driver model for PCI: enumerate the bus, read each function's vendor and device ID, call the driver that claims that pair. On an SoC, the list of devices comes from the devicetree instead, and the matching key is the compatible string. The shape is the same: a list of devices, a list of drivers, a rule that matches them, and a probe function per driver that checks the device and sets it up. C1

What is new is dependencies. A PCI device's clocks and power were set by firmware. An SoC device's node names its providers: the clock controller and clock number (clocks), the reset controller and line (resets), the pin controller and pin configuration, the interrupt controller (interrupt-parent). Those providers have drivers too, and they must be probed first. The devicetree does not list nodes in dependency order; on QEMU's virt machine, for example, the UART, RTC and GPIO nodes come before the interrupt controller and the clock they use. D1 R2

The solution is deferred probing: a probe that finds a provider missing returns "defer", and the driver model tries again in the next pass, after other drivers (including the providers) have probed. Passes continue until every device is bound or failed, or a pass makes no progress. The lab's kernel binds nine devices on QEMU virt; four of them, the UART, RTC, GPIO controller and the one populated virtio transport, after a deferral. A small Python script checks the log against D8's acceptance tests. R2 R3

QEMU's virt machine has a fixed clock and no reset or pin controllers, so the lab adds a small simulated SoC on the host, described by its own devicetree, with a clock controller, a reset controller, a pin multiplexer and a temperature sensor wired to clock 2, reset line 2 and pin 4. In this model, a sensor whose clock is gated reads as zero. With the right tree it reads 41.250 °C; with a tree that names clock 3, it reads 0.000 °C and the driver reports success. That is the forensic lab. R6 R7

Layer 3 — the engineer's depth

Devices, drivers, matching

The kernel's dm::init walks the tree once and creates a device record for every node that has a compatible property: its node offset, its first reg entry translated to a CPU address (F4-31), and a state. A node with status other than "okay" becomes disabled; a node no driver claims becomes no driver; the rest are waiting. The QEMU virt tree with one virtio device attached gives 48 such nodes. R2

Drivers are not listed anywhere in the core. Each driver file ends with one DR403_DRIVER(...) line, which places a constant descriptor (name, compatible list, probe function) in the linker section dr403_drivers. The linker script collects that section between __drivers_start and __drivers_end, and match walks it. The build record lists the ten descriptors the linker found. R1 D4



Matching walks the driver table and, for each driver, its compatible list, and asks whether the node's compatible list contains that string anywhere. This kernel takes the first driver that matches. Linux's rule is more careful: it prefers the driver that matches the node's earliest (most specific) compatible entry. With one driver per IP block, as here, the two rules agree; with a vendor-specific driver and a generic one both present, they do not, and the mini-project asks you to implement the specific-first rule. D3


Watch out
The driver table contains pointers (to names, compatible lists and probe functions). In a position-independent image these are absolute addresses fixed at start-up by the relocation loop of start.S. If the relocation table is cut short, the driver table keeps link-time addresses (near 0) and no driver ever matches. F4-37 shows that failure: "bound 0", with every node "no driver".



Probing in passes


dm::probe_all repeats passes over the waiting devices. Each probe returns one of three results: kOk (the device answered and is set up: bound), kFail (it is not the device the tree promised, or a required property is missing: failed, never retried), or kDefer (a provider is missing: stay waiting). The loop stops when a pass leaves nothing waiting, or when a pass makes no progress, which means the remaining devices wait for providers that will never come (a missing driver, or a cycle). Those remain waiting in the report, which is itself a finding. R2


On QEMU virt, pass 1 binds the five devices with no unmet dependencies (PSCI, fw-cfg, the GIC, the timer and the fixed clock) and defers 35: the 32 virtio transports and the UART, RTC and GPIO controller. Their nodes come earlier in the tree than the GIC and the clock. Pass 2 finishes all 35: four bound, 31 failed because their virtio transports are empty (device ID 0: nothing plugged in). Nothing is left waiting. R2




Deferral in passes is simple and costs repeated work: each pass calls every waiting probe again. With hundreds of devices and deep dependency chains this becomes slow; Linux retries deferred probes when any driver binds, and newer kernels also read the dependency properties ahead of time to order probes ("device links" from firmware). For a teaching kernel with tens of devices, passes are clear and enough. D3

"Bound" must mean "answered"


A probe that only records a base address proves nothing about the hardware. Every probe in drivers.cc checks something the device can only get right if it is really there and running: the PrimeCell part number for the PL011 (0x011), PL031 (0x031) and PL061 (0x061); the virtio magic "virt" and a non-zero device ID D7; the GIC distributor's type register; the timer counter advancing over a 10 ms wait; the fw-cfg signature "QEMU"; the RTC's seconds register increasing over 1.1 s of counter time. The log prints each value. R2


Two of those values decode into facts about the machine. GICD_TYPER = 0x8: its low five bits, ITLinesNumber, are 8, and the distributor supports 32 × (8 + 1) = 288 interrupt lines. The timer's 10 ms wait advanced the counter by about 628 thousand ticks at 62.5 MHz, which is 10 ms plus the time the probe itself took under emulation (the exact count differs per run and per machine). R2 D5

Providers: clocks, interrupt parents, pins, resets


Clocks. A clock consumer's clocks property is a list of entries, each a phandle followed by as many cells as the provider's #clock-cells says. To find entry i, clock_enable walks the list from the start, looking up each phandle's provider to learn how many cells to skip, since entries can have different lengths when different providers are used. The QEMU PL011's clocks = <0x8000 0x8000> is two entries of length one (the fixed clock has #clock-cells = 0), and the PL011 driver picks the entry named "uartclk" through clock-names. If the provider has not registered yet, the result is "defer". D2 R2


Interrupt parents. A device's interrupt controller is named by the nearest interrupt-parent on the node or an ancestor (the root of QEMU's tree sets it for everyone). irq_parent_ready defers until that controller's driver has registered. This is what deferred the virtio transports, RTC and GPIO controller on virt. D1


Pins. Linux's pin-control binding uses pinctrl-0 and pinctrl-names pointing to configuration nodes inside the pin controller, whose content is vendor-specific. This course uses a simpler, own format for its own trees: a property <&provider first count function>. F4-36 uses it on the Raspberry Pi model (dr403,sd-pins) and the simulated SoC uses it (pins). The binding is the course's, not a standard; the NOTES record it as a decision. D6


Resets. QEMU's virt machine has no reset controller, so the kernel's driver model has no reset framework yet; the simulated SoC has one, with #reset-cells = 1 and a register in which bit n = 1 holds line n in reset. Adding a reset provider to the kernel, following the clock provider's pattern, is lab step 3. D8's build step asks for "minimal clock, reset, pinctrl and GPIO frameworks"; this build has clocks, interrupt parents and pins in the kernel, and resets only in the host model. C1

What order the hardware needs


For a block on an SoC the safe order is usually: supply power (regulator, power domain), enable the clocks, release the reset, configure the pins, then touch the block's registers. Releasing a reset while the clock is off may leave the block half-initialised on some chips, because its reset logic needs clock edges; muxing pins to a block that is still in reset may glitch the lines. The TRM's chapter on the block, or the reset controller chapter, says what the chip requires; the Linux driver for the block often encodes the order and any delays. D5


The simulated sensor follows this order: clock on, reset off, pin function, start conversions, read. Its probe also shows the trap of trusting an unchecked read. It writes "start conversions" to the control register and reads the data register once, and does not read the identification register first. In this model a gated sensor ignores the write and reads zero, so the probe prints a temperature of 0.000 °C and returns "OK". R6 R7






The good run shows deferral in the simulated SoC too: the sensor is listed first in soc.dts, defers in pass 1 ("clock provider not probed yet"), and binds in pass 2 after the three providers. The register dump confirms each step: GATES = 0x4 (bit 2, clock 2 running), ASSERT = 0xfffffffb (bit 2 clear, line 2 released), pin 4 at function 3, the sensor's ID register "TSN1" (0x54534e31), conversions enabled, and data 0xa122 = 41250 m°C. R6



How the hardware actually does it


An SoC's clock tree starts at oscillators and PLLs, passes through multiplexers that choose a parent and dividers that set a rate, and ends in gates, one or more per block: often a separate gate for the bus interface clock and for the functional clock, as the PL011's apb_pclk and uartclk. Gating saves power by stopping the clock; it also stops the block's logic. A register access to a block whose bus interface clock is gated cannot be answered by the block; the interconnect or a wrapper decides what the CPU sees. D5


Reset controllers hold blocks in reset until software releases them. Many SoCs come out of power-on with most blocks held in reset and gated, and the boot firmware enables only what it uses (the boot medium, a UART, DRAM). That is why curriculum 11.5 says to trust firmware-enabled clocks at first and add clock and reset drivers only when a device needs a clock or reset the firmware left off. C1


Pin controllers connect each package pin to one of several internal signals. On the BCM2835 family, which the F4-36 lab uses, each GPIO pin has a 3-bit function field in a GPFSEL register: ten pins per register, at bit 3 × (pin mod 10) of register pin ÷ 10. The kernel's bcm2835-gpio driver implements exactly that as a pin provider. D6


Not verified — check before relying on this

The behaviour of the simulated SoC (gated block reads as zero, writes lost; reset bits active-high; one gate bit per clock) is this course's model, chosen to reproduce the forensic case; real chips may instead raise an external abort, return stale values, or stall the bus forever. The clock-tree description and the BCM2835 GPFSEL layout are from the author's memory of general SoC documentation and of "BCM2835 ARM Peripherals", not opened in this build; F4-36's run shows QEMU's model of GPFSEL behaving that way, not the silicon. Which behaviour your SoC has, and what order its blocks need, is in its TRM.


Safety
Clock, reset and pin drivers can do physical harm on a real board: muxing a pin that drives a regulator enable or a motor driver to the wrong function can switch power rails or actuators; changing a PLL or a CPU clock divider beyond its rated range can crash or overheat the chip. Start with the clocks and pins firmware already set, change only what a device needs, check every value against the TRM and the schematic, and test on a spare board. See the university safety rules.



Worked example


Question. Trace the PL011's probe on QEMU virt through both passes, from its devicetree node to "bound (after deferral)".


Step 1: the record. dm::init finds /pl011@9000000, compatible "arm,pl011", translated base 0x9000000, status absent (okay); match finds the descriptor pl011_driver whose list contains "arm,pl011". State: waiting. R2


Step 2: pass 1. pl011_probe looks up "uartclk" in clock-names = "uartclk", "apb_pclk": index 0. clock_enable(dev, 0, rate) reads clocks = <0x8000 0x8000>, finds the node with phandle 0x8000 (/apb-pclk), reads its #clock-cells = 0, so entry 0 is the single cell 0x8000. It searches the registered clock providers. The /apb-pclk node comes after the PL011 in the tree, so its driver has not run: "clock provider not probed yet", kDefer.


Step 3: still pass 1. Later in the same pass, fixed_clock_probe runs for /apb-pclk, registers fixed_rate as the provider and prints "fixed-clock /apb-pclk: 24000000 Hz". The log shows "probe pass 1: 5 finished, 35 still waiting".


Step 4: pass 2. pl011_probe runs again. This time clock_enable finds the provider and calls fixed_rate, which reads clock-frequency = 24000000. The probe reads the PrimeCell part number: 0xfe0 low byte 0x11 and 0xfe4 low nibble 0x0 give 0x011. It prints "part 0x011, uartclk 24000000 Hz" and returns kOk. With defers = 1, the report marks it "(after deferral)".


Step 5: the acceptance check. d8check.py reads the report: every node whose compatible is in its supported list is "bound" (the 31 empty virtio transports are reported as a count, which is correct behaviour: nothing is plugged in), and at least one device was bound after a deferral. Both D8 QEMU tests pass. R3

Where the analogy breaks


    

  • A dark room still has a visitor who can shout. A gated block cannot say anything; in the model, and on some chips, it returns zeros that look like data. On others, the CPU waits forever for an answer that never comes: no report at all.
    • 

  • Switching on the wrong lights in the school wastes electricity. Enabling the wrong clock on an SoC can also power a block that interferes with another, or change the rate of a clock another running device shares.
    • 

  • Postponing a lesson costs a period. Deferring a probe costs a pass over all waiting devices, and a probe that defers for a provider that will never appear waits forever unless the model detects "no progress".
    • 

  • In the school, the plan's small print is read by a person who can notice "switch 3 is the west wing". The kernel reads cell values and cannot tell that clock 3 is not the sensor's clock; only the device's behaviour (and an ID check) can reveal that.
    • 




Common mistakes and debugging


    

  • Probes that do not check the device. A probe that returns OK after writing registers it never reads back will "bind" a gated, absent or wrong device. Read an ID or status register that only a working device can produce. (Forensic lab.)
    • 

  • Skipping clocks entries by a fixed size. Different providers have different #clock-cells; walk entry by entry.
    • 

  • Treating "waiting" as "failed" (or the reverse). A device still waiting at the end names a missing provider driver or a cycle; a failed one names a device that did not answer. Print the reason for both.
    • 

  • Probing forever. Without "stop when a pass makes no progress", a missing provider hangs the boot. The kernel prints the stuck devices instead.
    • 

  • Assuming tree order is dependency order. QEMU's virt tree lists the UART before its clock and interrupt controller; board trees do the same.
    • 

  • Losing the driver table. Without used and KEEP, the compiler or the linker's garbage collection removes descriptors nothing references; with a broken relocation table, their pointers are wrong (F4-37). Check the image: the lab lists the descriptors with nm.
    • 

  • Debugging zeros. When a device reads all zeros, dump the clock gate, reset and pin registers next to the device's registers, and compare the devicetree's provider numbers with the TRM's clock and reset tables.
    • 




Transition box

Where you came from: F4-02 built a PCI driver model (enumerate, match IDs, probe); F4-31 read devicetrees; F4-34 chose a board by its documentation. What changes: the device list comes from the tree, the matching key is a compatible string, drivers come from a linker-assembled table, and probes have dependencies on providers (clocks, resets, pins, interrupt controllers) that must be satisfied, in order, with deferral. Forensic lab


Scenario. "Device reads all zeros." A temperature sensor worked on revision A of a board. On revision B, which the hardware team says changed "only the power supply layout", the kernel boots normally and its log says the sensor driver probed successfully, but every reading is 0.000 °C, in a warm room. The software is the same binary. The board support package for revision B came with its own devicetree.

Summary


    

  • A devicetree driver model creates devices from nodes with compatible, matches drivers by compatible string, and probes them; here the driver table is assembled by the linker from a named section.
    • 

  • SoC devices depend on providers (clocks, resets, pins, interrupt controllers) named by phandles with provider-defined cell counts; probes defer until providers exist, in passes that stop when nothing progresses.
    • 

  • On QEMU virt, 9 nodes bound, 4 after a deferral, and D8's two QEMU tests passed; the board test is untested in this build.
    • 

  • "Bound" must mean "answered": check an ID or a behaviour, not only a base address.
    • 

  • The safe order is power, clock, reset release, pins, then registers; the TRM decides the details.
    • 

  • A device that reads all zeros is often not running: compare the tree's provider numbers with the TRM, and dump the gate, reset and pin registers beside the device's.
    •

Answers to Check yourself


    

  1. Good answers say: on PCI, firmware has already powered and clocked every device and the bus enumerates them in an order that has no dependencies between functions, so any order works. On an SoC, devices depend on other devices (clock, reset, pin and interrupt providers) that have their own drivers, and the tree does not list them in dependency order, so a probe may run before its provider and must be retried.
    2. 

  2. Three entries: (&ccu 5), (&fixed), (&ccu 9). Entry 2 is the phandle of ccu followed by the cell 9. Skipping by a fixed two cells would land in the middle of the list after entry 1.
    3. 

  3. (b). The device waits for a provider; when a pass makes no progress, the model stops and the report shows it "waiting" with the reason, pointing to the missing driver. (a) would claim the device works without its interrupt controller. (c) would hide the real cause (the device may be fine). (d) is wrong: the result depends on the provider's state, not on the pass number.
    4. 

  4. Yes. Probes run in the order of the device records, which follow the tree; the PL011 node comes before /apb-pclk, so its probe runs first in pass 1 and defers, whatever the order of the driver table.
    5. 

  5. An empty transport (device ID 0) is a definite answer: nothing is plugged in and nothing ever will be during this boot. Deferring would mean "try again later", which can never succeed and would keep the loop running.
    6. 

  6. No deferral is needed if the providers' drivers probe first; it will be probed in pass 1. It can still read zeros if the tree's clock or reset numbers are wrong for this board (the forensic case), if a power domain or regulator is off and the model has no driver for it, or if the pins are muxed to another function.
    7. 

  7. Read the ID register after enabling the clock and releasing the reset, and fail if it is not the expected value. And read the control register back after writing "start" and fail if the bit did not stick (a gated block loses writes).

Forensic lab answer key


    

  1. Registers: GATES 0x00000008 (A: 0x00000004); TSENS ID 0x00000000 (A: 0x54534e31); TSENS CTRL 0x00000000 (A: 0x00000001); TSENS DATA 0x00000000 (A: 0x0000a122). Unchanged: ASSERT 0xfffffffb, PINMUX PIN4 0x3. Log: "clock 3 on" (A: "clock 2 on") and "temperature 0.000 C" (A: 41.250 C).
    2. 

  2. GATES = 0x8: only bit 3 set, so clock 3 runs and clock 2, the sensor's clock, is gated. ASSERT = 0xfffffffb: bit 2 clear, line 2 released (met). PINMUX PIN4 = 3: function 3 (met). Only the clock requirement fails.
    3. 

  3. Sensor broken: possible in general, but the ID register reads 0, and a broken sensor with a running clock would still return its ID; ruled out by the next point. Held in reset: ruled out, line 2 is released. Pins wrong: ruled out, pin 4 is at function 3 (and in the model wrong pins give 0x7fffffff, not 0). Clock not running: supported, bit 2 of GATES is 0 and every sensor register, including ID and the CTRL bit the driver wrote, reads 0, the documented behaviour of a gated block. Driver bug: the driver enabled exactly what the tree said; its bug is that it did not check the ID.
    4. 

  4. From the revision-B devicetree: line 20, clocks = <&ccu 3>, where revision A has <&ccu 2>. The driver did what the tree said, wrote "start" (lost), read DATA (0) and returned OK because it never checked that the device answered. How the fault was injected: run.sh generates board_rev_b.dts from soc.dts with sed, changing the clock number from 2 to 3.
    5. 

  5. Fix: clocks = <&ccu 2> in the revision-B tree. Loud failures: the sensor probe checks the ID register after enabling clock and reset (lab step 5); and a board test in CI reads the sensor and fails on a value outside a plausible range (for example 0.000 °C at room temperature). A binding check that compares clock numbers with the TRM's table (or the vendor's binding header) would catch it before boot.
    6. 

  6. Ask whether any clock or power wiring changed (a different clock output for the sensor, a new power domain), and for the revision-B schematic. In the board support package, find the commit that created the revision-B tree and diff it against revision A: an unexplained provider-number change in a "power layout" revision is the lead. Here the hardware did not change; the tree did.
    7.
