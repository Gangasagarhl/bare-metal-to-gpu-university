Story hook

Analogy

Mr Haddad teaches maths to three classes this morning, but there is only one of him. Class A has a long test that needs eight periods, class B needs four, class C needs two. If he stays with A until the test is done, C waits all morning for a two-period lesson. If he gives every class a short turn in rotation, everyone sees him early, but A finishes last of all. If he always goes to the class with the least work left, the small classes are happy, and A may wait a long time.

Inside each room the students work together on one project. They share the books on the shelves and the board, but each student has a private notebook. When the teacher leaves, he leaves a bookmark in the class register so that he can continue exactly where he stopped.

The timetable, the bookmarks and the shared shelves are this chapter: scheduling, context switches and threads.

What you will be able to do

  • Explain what a thread is, what threads of one process share and what each has privately, and how that differs from two processes.
  • Explain a context switch, and measure how often the kernel switched your process off the CPU.
  • Compute turnaround and response times for FIFO, shortest-job-first, shortest-time-to-completion-first and round-robin schedules, by hand and with the university's simulator.
  • Choose a scheduling policy for a stated goal and explain its trade-off.
  • Diagnose starvation from a scheduling trace and propose aging as a fix.
Jargon box
Thread
Simple words: one line of work inside a running program; a program can have several. Analogy: a student working in the class's room. Precise: an independent flow of control with its own registers, program counter and stack, sharing the address space and open files of its process; the OS schedules threads onto cores (the HW202 definition, glossary). A CPU thread is not a GPU thread (F6). D1 D3
Context switch
Simple words: the kernel stops one thread, saves where it was, and starts another. Analogy: the teacher leaves a bookmark in the register, packs up and goes to the next room. Precise: the kernel operation that saves the registers (including the program counter and stack pointer) of the running thread into its kernel record, restores another thread's saved registers and, if the new thread belongs to another process, switches to that process's page tables. D1 D2
Scheduler
Simple words: the part of the kernel that decides which thread runs next, and for how long. Analogy: the timetable. Precise: the kernel component that selects, from the ready threads, the next one to run on each CPU, according to a scheduling policy, whenever a thread blocks, exits, or is preempted. D1
Preemption
Simple words: taking the CPU away from a thread that has not finished. Analogy: the bell rings and the teacher must go, even mid-sentence. Precise: the scheduler's ability to stop a running thread, normally on a timer interrupt, and make it ready again so that another thread can run; a policy that never does this is non-preemptive. D1
Time slice (quantum)
Simple words: how long a thread may run before the scheduler may take the CPU away. Analogy: the length of one lesson period. Precise: the maximum interval a thread runs before a round-robin scheduler preempts it and moves it to the back of the ready queue. D1
Turnaround time
Simple words: how long a job takes from arriving to finishing. Analogy: from the moment a class asks for the teacher until its lesson is done. Precise: Tturnaround = Tcompletion − Tarrival. D1
Response time
Simple words: how long a job waits before it first gets the CPU. Analogy: how long a class waits before the teacher first walks in. Precise: Tresponse = Tfirst run − Tarrival. D1
Starvation
Simple words: a job that never gets the CPU because others are always chosen first. Analogy: a class always moved down the timetable because more urgent classes keep arriving. Precise: indefinite postponement of a ready thread by a scheduling policy, for example strict priority with a steady supply of higher-priority work. D7
Aging
Simple words: letting a job become more urgent the longer it waits. Analogy: the longer a class has waited, the higher it moves on the timetable. Precise: a technique that gradually raises the effective priority of threads that have waited a long time, bounding how long any ready thread can be postponed. D7

Layer 1 — the kid explanation

A computer has a few cores, and each core can run one thing at a time, like a teacher with one class.D1 But you can have hundreds of programs running. The kernel makes that work by switching: a program runs for a short while, then the kernel saves exactly where it was and lets another program run. Switching happens so often that every program seems to run all the time.

Who goes next is decided by the scheduler, the computer's timetable. Different timetables are good for different things. "First come, first served" is simple, but a short job can be stuck behind a long one. "Shortest job first" finishes small jobs quickly. "Everyone gets a short turn in rotation" makes sure every program reacts quickly, which matters when a person is waiting for an answer.D1

One program can also do several things at once. Each line of work is a thread, like several students working on one project in the same room. They share the room's books (the program's memory), so they can help each other, but they can also get in each other's way. Each has a private notebook (its own stack).D1

Layer 2 — the student explanation

Threads share an address space

A process starts with one thread. Creating another (with std::thread in C++) gives the process a second flow of control that runs the same code, sees the same global variables and heap, and has its own stack and registers.D1 D8 Listing 1 checks each part of Figure 1 on this build's machine: both threads report the same process ID but different kernel thread IDs; both see the counter at the same address; their local variables have different addresses; and 2 × 1000 atomic increments give exactly 2000.R1 Compare F3-02: after fork, parent and child had separate copies of every variable. Threads are cheaper to create and communicate through plain memory, which is their strength and their danger: two threads changing the same non-atomic variable without synchronization is a data race, undefined behaviour in C++ (F1-30).D8

Context switches

Each core runs one thread at a time. When the running thread blocks (it asked to sleep or to read data that is not there yet), exits, or uses up its time slice and is preempted by the timer interrupt, the kernel performs a context switch: it saves the thread's registers into the thread's kernel record and restores another ready thread's registers; if the new thread belongs to another process, it also switches the page-table root (F3-04).D1 D2 Linux counts switches per process and reports them through getrusage: voluntary ones, when the thread blocked, and involuntary ones, when it was preempted.D4 Listing 2 slept 50 times for 1 ms each; the kernel reported 50 voluntary switches.R2

What a scheduler optimises

The textbook measures a schedule with two numbers per job. Turnaround time is completion minus arrival: how long the job took in total. Response time is first run minus arrival: how long it waited before it first got the CPU.D1 Batch work cares about turnaround; anything a person is waiting on cares about response. Fairness (does every job get its share?) and overhead (how much time goes into switching itself) matter too.

Four classic policies

FIFO (first in, first out) runs jobs to completion in arrival order. A long job that arrives first makes everyone wait: in Figure 2, C needs 2 ticks but waits 10 before it starts.D1 R3 SJF (shortest job first) picks the shortest waiting job whenever the CPU is free, but still never interrupts; because A was alone at tick 0, SJF could not help B and C here (average turnaround 9.67 instead of 10.33). STCF (shortest time-to-completion first) is SJF with preemption: when a job arrives with less work left than the running one, it takes over. It gives the best average turnaround of the four (7.33) and here every job started the moment it arrived.R3 Both SJF and STCF need to know how long each job will run, which a real OS does not know.D1 Round robin (RR) needs no knowledge: it runs each ready job for one time slice, then moves it to the back of the queue. Its average response time was 1.00 tick, but A, the long job, finished last at tick 14.R3

Priorities and starvation

Real systems also give jobs priorities: an interactive editor should run before a nightly report. A strict priority scheduler always runs the most urgent ready job. If urgent work never stops arriving, a less urgent job never runs: starvation. A common cure is aging: a job's effective priority improves the longer it waits.D7 The forensic lab shows both behaviours in the simulator.

Layer 3 — the engineer's depth

Learning instead of knowing. Because the OS cannot know job lengths, practical schedulers observe behaviour. The multi-level feedback queue (MLFQ) described in the textbook keeps several queues of different priority; a job that uses its whole time slice is moved down (it looks like long-running batch work), a job that blocks early stays up (it looks interactive), and periodically all jobs are boosted to the top so that none starves.D1 Other designs aim at proportional shares of the CPU (lottery and stride scheduling in the same textbook).D1 The mini-project adds MLFQ to the simulator.

The time slice is a trade-off. A shorter slice improves response time, but each switch costs time: saving and restoring registers is cheap; refilling caches and the TLB that the new thread needs is not (HW203, F1-33 and F1-38). A slice must be long compared with the switch cost.D1 This build did not measure the cost of a switch, and this chapter quotes no number for it (AH-22): Listing 2 counts switches, it does not time them.

More than one core. With several cores the scheduler must also decide where a thread runs. Keeping a thread on the same core preserves its cached data (affinity); per-core run queues avoid one shared, locked queue, at the price of balancing load between queues.D1 The build machine reported 4 online CPUs (F3-01, R1 there).

Kernel threads and user threads. On Linux each std::thread is a separate kernel-scheduled thread with its own kernel thread ID, which is why Listing 1 sees different IDs from the gettid system call.D4 R1 Other systems and libraries have mapped many user-level threads onto fewer kernel threads; the textbook compares the models.D7

Not verified — check before relying on this

The scheduling policy of the Linux kernel used in this build (the default policy for ordinary threads has changed between kernel versions) and the default time slice of any real system were not checked and are deliberately not described. Check the scheduler documentation in the Linux kernel source tree (Documentation/scheduler/) for the exact kernel release you use; the release of this build's kernel is printed in F3-01's lab run.

How the hardware actually does it

Two hardware features make scheduling possible. First, a timer that the kernel can program to raise an interrupt after a chosen interval; when it fires, the core stops the running thread, enters kernel mode and runs the kernel's handler, which can call the scheduler (F3-01 Layer 3).D1 Second, a register-saving mechanism: on a trap the hardware records where the thread was (on RISC-V, in the mepc or sepc register), and the kernel's entry code stores the remaining registers in memory, exactly as F3-07's trap.S does for the university's kernel.D5 A context switch is then ordinary code: store this thread's callee-saved registers and stack pointer, load another thread's, return. In xv6 that code is a short assembly routine called swtch.D2 On a multicore chip (F1-30) each core does this independently, so the kernel's shared scheduling data must be protected by locks: that is F3-05.

Worked example

Jobs: A arrives at 0 and needs 8 ticks; B arrives at 1 and needs 4; C arrives at 2 and needs 2. Compute FIFO and RR (slice 2) by hand, then compare with the simulator.

  1. FIFO. A runs 0–8, B 8–12, C 12–14. Turnaround: A 8 − 0 = 8, B 12 − 1 = 11, C 14 − 2 = 12; average 31 ÷ 3 = 10.33. Response: A 0, B 8 − 1 = 7, C 12 − 2 = 10; average 17 ÷ 3 = 5.67.
  2. RR, slice 2. Rule used by the simulator: new arrivals join the back of the queue before the job whose slice has ended. t = 0–2: A (B arrived at 1, C at 2; queue B, C, then A goes back). t = 2–4: B. t = 4–6: C (C finishes at 6). t = 6–8: A. t = 8–10: B (B finishes at 10). t = 10–14: A alone (finishes at 14).
  3. RR turnaround: A 14, B 10 − 1 = 9, C 6 − 2 = 4; average 27 ÷ 3 = 9.00. Response: A 0, B 2 − 1 = 1, C 4 − 2 = 2; average 3 ÷ 3 = 1.00.
  4. The simulator prints the same numbers (R3, in the code walk-through), and its timelines are the rows of Figure 2.R3
  5. Reading the result: RR cut the average response from 5.67 to 1.00 ticks, and cost A six extra ticks of turnaround (8 → 14). Which is "better" depends on whether a person is waiting for B and C.

Where the analogy breaks


    

  1. The timetable is not printed in advance. A school timetable is fixed for the term; the scheduler decides continuously, many times per second, from what threads did a moment ago (the registered note for this mapping).S2
    2. 

  2. Students in one room cannot be interrupted mid-word; threads can. The kernel may stop a thread between any two instructions, even in the middle of updating a shared variable. That is why shared data needs atomics or locks (F3-05), and why the registered map says "the OS can pause a cook at any instant, mid-step".S2
    3. 

  3. A teacher's bookmark is free; a context switch is not. Changing rooms costs a teacher a minute. A context switch costs time to save and restore state and, more, to refill caches and the TLB for the new thread; very short time slices waste the CPU (Layer 3).D1
    4.

Summary


    

  • A thread is a flow of control with its own stack and registers; threads of one process share code, globals, heap and files.
    • 

  • A context switch saves one thread's registers and restores another's (and switches page tables between processes); Linux counts them per process.
    • 

  • Turnaround = completion − arrival; response = first run − arrival.
    • 

  • FIFO is simple; SJF and STCF minimise turnaround but need job lengths; round robin gives good response at the cost of turnaround.
    • 

  • Strict priority can starve low-priority jobs; aging bounds the wait.
    • 

  • Real schedulers learn from behaviour (MLFQ) and balance work across cores.
    •
