Story hook

Analogy

Every class in Amara's school has lockers numbered 1 to 40. Class 7B's locker 12 holds Amara's football boots; class 8A's locker 12 holds somebody's violin. Nobody is confused, because the number on the door is not where the cupboard really is. The school keeps a map for each class: "7B locker 12 is cupboard 318 in the east corridor; 8A locker 12 is cupboard 77 by the gym". A student only ever uses locker numbers. The office keeps the maps.

When a new student arrives, the office does not fill forty cupboards in advance. It writes "no cupboard yet" on the map and assigns a real cupboard the first time the student opens that locker. And when a student asks for locker 900, which no map lists, the office does not guess: it stops the student and reports the mistake.

The locker numbers are virtual addresses, the maps are page tables, and the moment the office steps in is a page fault. This chapter is how the operating system runs that office.

What you will be able to do

  • Explain why two processes can use the same address for different data, and show it with a program.
  • Translate a virtual address by hand through a three-level RISC-V Sv39 page table, and check your answer with the university's walk simulator.
  • Explain what the kernel does on a page fault, and measure the page faults of your own program.
  • Read a process's memory map in /proc/self/maps and place code, globals, heap and stack in it.
  • Diagnose a crash at a small address as a null-pointer access, using the fault address and the structure layout.
Jargon box
Virtual memory
Simple words: each program uses its own made-up addresses, and the hardware and OS map them to real memory. Analogy: locker numbers instead of real cupboards. Precise: the HW203 definition (glossary); this chapter adds the operating system's side: who builds the tables, when, and what happens when a mapping is missing. D1
Address space
Simple words: all the addresses one program can use. Analogy: one class's locker numbers. Precise: the set of virtual addresses a process may use, with what is mapped at each (glossary). D1
Page table
Simple words: the table that says where each page really is. Analogy: the map of lockers: locker number to real cupboard (registered). Precise: a per-address-space data structure in memory that maps virtual page numbers to physical page numbers plus permission bits (glossary). D1
Physical frame
Simple words: one page-sized piece of real memory. Analogy: one real cupboard. Precise: a page-aligned block of physical memory, of the page size, that the kernel can map at one or more virtual pages; identified by its physical page number (PPN). D1
Page fault
Simple words: the hardware finds no valid mapping and asks the OS what to do. Analogy: the map has no cupboard for that locker; the office steps in. Precise: the exception raised when translation finds a missing or forbidden mapping (glossary); the kernel either installs a mapping and restarts the instruction, or reports an error to the process. D1
Demand paging
Simple words: giving a program real memory only when it first touches it. Analogy: "no cupboard yet" until the locker is first opened. Precise: a policy in which the kernel records that a virtual range is valid but maps no frame until the first access faults; the fault handler then allocates (or reads in) the page and maps it. D1
Copy-on-write (COW)
Simple words: after fork, parent and child share the same memory until one of them writes, and only then is a private copy made. Analogy: two classes share one cupboard for reading; the first class to put something in gets its own cupboard. Precise: a technique in which pages are mapped read-only into several address spaces; a write causes a page fault, and the handler copies the page, maps the copy writable for the writer, and restarts the write. D1 D3
Segmentation fault (SIGSEGV)
Simple words: the OS stops a program that touched memory it may not touch. Analogy: the office reports the student who opened a locker that does not exist. Precise: on Linux, the signal the kernel sends when a page fault cannot be resolved because the address is unmapped or the access is not permitted (glossary). D4
Sv39
Simple words: the RISC-V rule book for 39-bit virtual addresses. Analogy: the school's rule for writing locker maps as a three-level index. Precise: the RISC-V paged virtual-memory mode with 39-bit virtual addresses, 4 KiB pages and three levels of 512-entry page tables; the mode xv6 uses. D5 D2

Layer 1 — the kid explanation

Every program on a computer thinks it has the whole memory to itself. It uses addresses, numbers that say where a piece of data lives, and it can use the same numbers as every other program. That works because the addresses a program sees are not the real places in the memory chips. They are like locker numbers: each class has its own map that turns a locker number into a real cupboard.D1

The operating system writes those maps, and the processor reads them every time a program touches memory. If a program asks for an address that its map does not list, the processor stops and calls the operating system. Sometimes that is planned: the OS hands out real memory only when a program first uses it, the way a school assigns a cupboard only when a student first opens the locker. Sometimes it is a mistake in the program, and the OS stops the program with an error.D1

Because each program has its own map, one program cannot read or scribble over another program's memory, and a broken program crashes alone instead of taking the whole computer with it.

Layer 2 — the student explanation

Why the OS wants virtual memory

HW203 (F1-38) explained virtual memory from the processor's side: pages, page tables, the TLB and the cost of a walk. Here we take the operating system's side. The OS uses translation for three jobs.D1

  • Isolation. Each process gets its own page table. An address that is not in a process's table does not exist for that process, so it cannot reach another process's memory or the kernel's.
  • A simple picture for programs. Every program can be linked to run at the same addresses, with code low, a heap above it and a stack near the top, no matter where in physical memory its pages land.
  • Efficiency. The kernel can hand out memory only when it is touched, share one copy of read-only pages between processes, and make fork cheap by sharing pages until someone writes.

Listing 1 shows isolation directly. A program has a global variable seat. It forks; the child sets seat = 42; both print the address and the value. Both printed the same address (the exact number changes from run to run; see Layer 3); the child saw 42 and the parent still saw 1.R1 The same number reached two different pieces of memory, as in Figure 2.

Pages, frames and the address split

Memory is managed in pages. On the build machine a page is 4096 bytes (the run in Listing 3 printed it).R3 Because 4096 = 212, the low 12 bits of an address are the offset inside a page and stay the same in translation. The bits above are the virtual page number (VPN), which the page table replaces with a physical page number (PPN). The physical address is the PPN followed by the same offset.D1

A single flat table with one entry per virtual page would be enormous, and most of it empty, because a program uses a few small regions of a huge address space. So the table is a tree. In RISC-V's Sv39 mode, which xv6 uses, a virtual address has 39 significant bits: three 9-bit indexes and the 12-bit offset. Each table is one 4 KiB page of 512 entries (29), each entry eight bytes. The top-level table's address is in a control register, satp.D5 D2

The walk

To translate, the hardware takes VPN[2] and reads that entry of the root table. If the entry is valid and points to another table, it takes VPN[1] and reads that table, then VPN[0] in the last table. The last entry, a leaf, holds the PPN and the permission bits: readable (R), writable (W), executable (X), and user-accessible (U). Figure 1 is exactly this for address 0x1234: indexes 0, 0, 1, offset 0x234, result 0x80200234.R2

The walk fails in three ways, and the simulator shows all three. An entry without the valid bit: "not valid ⇒ PAGE FAULT" for 0x5000. A valid leaf without the needed permission: a write to the code page at 0x1234, which is R-X. A page without U, touched from user mode: 0x3fc0001010 is a kernel page, so the same address that the kernel reads successfully faults for a user program.R2 That last rule is what keeps user programs out of the kernel's memory even though the kernel is mapped in the same table.D5

Three reads per memory access would make every program several times slower, so the processor keeps recent translations in the TLB, the principal's sticky note of recently looked-up lockers (F1-38 measured its effect).D1 The OS must keep the TLB honest: when it changes a mapping, it must flush the stale entries (on RISC-V, with the sfence.vma instruction).D5

Page faults are the OS's tool

A page fault is a trap, like a system call or an interrupt (F3-01): the processor stops the instruction, switches to kernel mode and runs the kernel's handler, telling it the faulting address and the kind of access.D5 The handler looks up what the process should have at that address. The kernel keeps that list separately from the page table: on Linux it is the list of regions printed in /proc/self/maps (Listing 4).D4 Then there are two cases.D1

  • Legal, not yet present. The address is in a region the process asked for (heap, stack, a mapped file), but no frame is there yet, or the page is shared copy-on-write. The kernel allocates a frame, fills it (zeros, a copy, or file data), installs the entry, and restarts the instruction. The program never notices, apart from the time it took.
  • Illegal. The address is in no region, or the access breaks the region's permissions. On Linux the kernel sends the process the signal SIGSEGV, the "segmentation fault" every C++ programmer meets.D4

Listing 3 measures the first case. It asks the kernel for 4096 pages with mmap, then writes one byte into each page twice. The kernel counted exactly 4096 minor page faults during the first pass and 0 during the second (the build without sanitizers).R4 mmap only recorded a region; each page got a frame on its first touch. That is demand paging. A minor fault is one served without reading the disk; a major fault needs a disk read, for example a page of a file not yet in memory.D4

Copy-on-write explains why fork in F3-02 is cheap and why Listing 1 still works: after fork both processes map the same frames read-only; the child's write to seat faults, the kernel copies that one page, and from then on the two tables point to different frames.D1 D3 The output of Listing 1 is consistent with copy-on-write but does not prove it: an eager copy would print the same lines. Listing 1 shows the effect, not the method.

Layer 3 — the engineer's depth

The kernel lives in every address space. In Linux on most architectures, the kernel's own mappings are present in (or reachable from) each process's page table but marked without the user bit, so a system call or fault does not need to switch tables to reach kernel data.D1 xv6 instead gives the kernel its own page table and switches on every trap, through a small "trampoline" page mapped at the same address in both; the xv6 book explains why.D2 Either way the permission bits, not secrecy of addresses, do the protecting.

Large pages. A leaf entry may sit at level 1 or 2 instead of level 0, mapping 2 MiB or 1 GiB at once in Sv39 (a megapage or gigapage); fewer TLB entries then cover more memory, the huge pages of F1-38.D5

When memory runs out. If the kernel needs a frame and none is free, it must take one from some page: write it to disk if it is dirty (swapping) or drop it if a copy exists in a file, and clear its entry so the next access faults and reads it back. Choosing which page to take is a replacement policy (LRU approximations such as the clock algorithm).D1 xv6 has no swapping at all; a process that asks for too much memory gets an error.D2

Address-space layout randomisation. Compare the address of seat in Listing 1's output with the address of global in Listing 4's: both are globals of small programs built the same way, yet they sit at different places, and a rerun of either program moves them again (this build's reruns did). Linux places the program, libraries, heap and stack at randomised addresses on each run, which makes attacks that need a known address harder.D4 R5 Never hard-code or compare raw addresses between runs; compare offsets inside a region, as the forensic lab does.

Not verified — check before relying on this

The Sv39 details in this chapter were written from the author's memory and not checked against the RISC-V privileged specification in this build: the 39-bit address with bits 63 to 39 equal to bit 38, the entry format (PPN above ten flag bits V, R, W, X, U, G, A, D), the megapage and gigapage sizes, satp and sfence.vma. The university's simulator (Listing 2) models only the parts it states in its header comment. Also unverified: the xv6 details (separate kernel page table, the trampoline page, no swapping, and the names of xv6's page-table functions, which F3-08 treats as unconfirmed), and that Linux refuses to map the lowest pages of the address space (the setting vm.mmap_min_addr). Check each against D5, D2 and the Linux documentation for your kernel release.

How the hardware actually does it

On every load, store and instruction fetch, the memory-management unit (MMU) in the core looks the VPN up in the TLB. On a hit, it checks the permission bits from the cached entry and forms the physical address. On a miss, RISC-V and x86-64 cores walk the page tables in hardware, reading one entry per level from memory (and from the caches, which hold recently used table entries like any other data); some other architectures leave the walk to a software handler.D1 D5 If the walk finds an invalid entry or a permission violation, the core raises a page-fault exception: on RISC-V it records the cause in scause (or mcause), the faulting instruction's address in sepc and the faulting address in stval, and jumps to the trap handler.D5 F3-07 shows those registers in a real QEMU run, where the university's kernel prints mcause and mtval for a protection fault. The OS writes the tables as ordinary memory and tells the core where the root is by writing satp; switching processes means writing a different root and flushing stale TLB entries, which is part of the cost of a context switch (F3-03).D5 Real multicore systems must also flush the TLBs of other cores when a shared mapping changes, a "TLB shootdown", using an inter-processor interrupt; that is the "where it breaks" of the registered TLB analogy.S2 D1

Worked example

Translate the virtual address 0x2abc for a user-mode write, using the tables of Listing 2's input (the page at 0x2000 is mapped to 0x80201000 with RWU).

  1. Offset. The low 12 bits: 0x2abc AND 0xfff = 0xabc.
  2. VPN. Shift right by 12: 0x2abc ≫ 12 = 0x2. Split into 9-bit fields from the bottom: VPN[0] = 2, VPN[1] = 0, VPN[2] = 0.
  3. Level 2. Root table (page 0x80001), entry 0: valid, points to the table at page 0x80010 (created when the first page was mapped).
  4. Level 1. Table 0x80010, entry 0: valid, points to page 0x80011.
  5. Level 0. Table 0x80011, entry 2: leaf, PPN 0x80201, flags RW-U.
  6. Checks. The access is a write and W is set; the mode is user and U is set. Allowed.
  7. Physical address. PPN followed by the offset: (0x80201 ≪ 12) | 0xabc = 0x80201abc.
  8. Compare with the second block of the simulator's output: same indexes, same tables, same result.R2

A second check: how many table pages do the three mappings need? Pages 0x1000 and 0x2000 share VPN[2] = 0 and VPN[1] = 0, so they share the level-1 and level-0 tables: root + 2. Page 0x3fc0001000 has VPN[2] = 255 (0x3fc0001000 ≫ 30 = 255), so it needs its own level-1 and level-0 tables: + 2. Total 5, which is the simulator's last line.R2 Five pages (20 KiB) of tables describe three pages of data here; in a real process the ratio is far better because thousands of pages share each level-0 table.

Where the analogy breaks


    

  1. The map is a tree, not a list. A school locker map is one list per class; a page table is a three- or four-level tree, its entries carry permission bits, and its answers are cached in the TLB (the registered "where it breaks" for page tables).S2
    2. 

  2. The sticky note must be torn up. When the office changes a class's map, a sticky note with the old cupboard is wrong. A TLB must be flushed when mappings change, on every core that may hold the entry (TLB shootdown).S2
    3. 

  3. Two classes can share one cupboard on purpose. In a school that would be an error in the map. In an OS it is common and deliberate: shared libraries, copy-on-write after fork, and shared memory between processes that ask for it (the registered note "processes can share memory if they ask").S2
    4. 

  4. The office is not a separate person. The "office" that handles a page fault is kernel code running on the same core that faulted, in the middle of the faulting program's instruction.
    5.

Summary


    

  • Each process has its own page table, so the same virtual address can name different memory in different processes (Listing 1).
    • 

  • An address is a page number plus an offset; the page table replaces the page number and keeps the offset.
    • 

  • Sv39 uses three levels of 512-entry tables; the walk reads one entry per level, and the TLB caches results.
    • 

  • Leaf entries carry R, W, X and U bits; violations and missing entries cause page faults.
    • 

  • The kernel uses page faults on purpose: demand paging (one fault per first touch, Listing 3) and copy-on-write.
    • 

  • Faults outside any region end the program with SIGSEGV; a small fault address usually means a null pointer plus an offset.
