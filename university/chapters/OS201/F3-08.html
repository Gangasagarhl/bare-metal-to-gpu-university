Story hook

Analogy

On her first day at a new school, Mei is handed a building plan with forty rooms on it, and she is lost by the second corridor. The next morning an older student, Kwame, gives her a different kind of tour. "Forget the plan for now. Follow one visitor. They come through the gate, sign in at the office window, wait in the hall, get sent to room 12, and leave by the side door. Now you know five rooms and the corridors between them. Tomorrow we follow a delivery van."

By Friday Mei knows the building better than the plan does, because she knows why each room is where it is.

xv6 is a small, real teaching operating system of a few thousand lines, and MIT's course 6.1810 builds its labs on it. This chapter gives you Kwame's kind of tour: first through the university's own even smaller kernel, which this build could run, and then through the map of xv6, room by room.

What you will be able to do

  • Navigate a small kernel by following paths: boot, a system call, a fault, and find each function with a symbol table.
  • Map the parts of uni-rv to their counterparts in xv6, and say which xv6 file to open for each topic of F3-01 to F3-07.
  • Add a system call to a kernel: number, handler, table entry, user-side call, test.
  • Diagnose a system-call table that disagrees with its numbers, from a kernel log.
  • Prepare the xv6 "util" and "syscall" labs and the practical exam (add a system call to xv6).
Jargon box
xv6
Simple words: a small Unix-like teaching operating system. Analogy: a model school built so pupils can see every room. Precise: a re-implementation of Sixth Edition Unix's ideas in C for multicore RISC-V (and earlier x86), written at MIT for teaching operating systems, with a book that explains its source; it runs in QEMU. D2 D9
Symbol table
Simple words: the list of function and variable names in a program file, with their addresses. Analogy: the building plan's room list. Precise: the section of an ELF file that maps names to addresses and kinds (code, data); printed by nm, used by debuggers and addr2line to turn addresses into names and source lines. D3
System-call table
Simple words: the list that turns a system-call number into the kernel function that handles it. Analogy: the binder at the office window: form number to procedure. Precise: an array of handler pointers indexed by system-call number, used by the kernel's dispatcher after a bounds check; its order must match the numbers that user programs are built with. D2
User-space stub
Simple words: the tiny function a program calls, which puts the number in a register and traps. Analogy: the pre-printed form with the form number already filled in. Precise: a library function (in xv6, generated from a script; in uni-rv, the inline ecall wrapper) that loads the system-call number and arguments into the convention's registers and executes the trap instruction. D2
Grading script
Simple words: a program that runs your lab solution and says pass or fail. Analogy: the exam marker's checklist. Precise: in 6.1810, per-lab scripts run by the Makefile that boot xv6 in QEMU, run test programs, and compare their output with expected patterns; the curriculum's P4 acceptance is that they pass. Layer 1 — the kid explanation

An operating system is a big program, and nobody reads a big program from the first line to the last. You read it like you explore a new school: pick one thing that happens, and follow it from start to finish.D2

Good first walks are: "what happens when the computer is switched on", "what happens when a program asks the kernel to print something", and "what happens when a program does something forbidden". Each walk visits only a few rooms of the program. After three walks you know where the important rooms are and how they connect.

xv6 is an operating system made small on purpose, so that students can take these walks. It has everything this course talked about: processes, a scheduler, virtual memory, locks, files and system calls, in a few thousand lines.D2

Layer 2 — the student explanation

How to read a kernel: follow paths

You have already read one whole kernel: uni-rv, in F3-05 and F3-07. Its four files have 345 lines in total (the sizes run): entry.S 15, trap.S 82, kernel.ld 18, kernel.cc 230.R2 The method that works for it works for xv6 and, later, for Linux.

  1. Find the entry. The linker script says where execution starts (ENTRY(_start), placed at 0x80000000); the symbol table confirms it: _start at 0x80000000.R1
  2. Follow boot to the first user instruction. _start sets a stack per hart and calls kmain; kmain sets the PMP, mtvec and mscratch, then calls enter_user, whose mret lands at user_main (0x80020000).
  3. Follow one system call (F3-07, Figure 1): ecall → trap_entry → handle_trap → the table → sys_write → back.
  4. Follow one fault: the hartid_direct run below takes the other branch of handle_trap.
  5. Use the tools. nm -n lists every function in address order (R1); addr2line turns an address from a log into a source line (F3-05 did this for the frozen machine); objdump -d shows the instructions (F3-07).

Adding a system call

Adding a system call is the course card's practical exam and the core of the 6.1810 "syscall" lab, and it is the same four edits in any kernel. Figure 2 shows them for count, which returns how many system calls the process has made, this one included. The tour run logged "syscall 4 (count) -> 5": the user's fifth call, and the total of 7 at exit.R3 The worked example goes through the edits line by line.

Why make it a system call at all, rather than let the program read the kernel's counter? Because user mode cannot reach kernel data, and must not. The lab's experiment shows the hardware enforcing that for a register: the hartid_direct build makes the user program read the machine-mode register mhartid with csrr; the hart raised an illegal-instruction exception, and the kernel logged mcause=2 with mtval=0x00000000f14027f3, the instruction's own encoding, and killed the process (exit code 1).R4 D5 The lab then adds a system call hartid so that the kernel, which may read the register, returns it.

Layer 3 — the engineer's depth

Numbers are an ABI. Once user programs are built with a system-call number, the kernel can never reuse it for something else, or old programs call the wrong function. That is why Linux numbers only grow, why removed calls leave holes that return ENOSYS, and why numbers differ between architectures (F3-07's write = 1 on x86-64 is a fact about that architecture's table).D4 L1 The forensic lab is what happens when the table and the numbers drift apart.

Generating both sides from one list. Because the number appears in the kernel's table and in every user stub, kernels generate them from one source. xv6 generates its user stubs from a script; Linux generates its tables from per-architecture table files.D2 uni-rv uses one enum shared by both sides, and its table relies on the order of the rows, which the forensic lab breaks. Designated array indices ([SYS_count] = …) remove that risk in C; C++20 does not allow array designators, so a C++ kernel can instead build the table with a constexpr function and static_assert that each row's position equals its number.

Arguments and safety. xv6 fetches integer and pointer arguments from the saved trap frame with helper functions, and copies strings and buffers with checked copy functions, the copyin family; a new system call that takes a pointer must use them.D2 F3-07's forensic lab is the reason.

Tracing as a lab. A classic first kernel extension is a per-process trace mask: a system call that sets it, and a line in the dispatcher that prints each traced call with its result. uni-rv's dispatcher prints every call already (lines 145–153 of the F3-08 kernel); making it conditional on a mask is the mini-project.

From reading to building. Track B of the curriculum continues from here: real boot on PC hardware, a kernel of your own in C++. The paths you follow in xv6 (boot, trap, scheduler, page fault, file read) are the chapters of that kernel.S1

How the hardware actually does it

QEMU's virt machine with -bios none starts every hart at 0x80000000 in machine mode, which is why _start must be there (R1) and why entry.S first reads mhartid to give each hart its own stack.R1 D5 uni-rv keeps the extra harts asleep with wfi; xv6 starts them all and gives each a scheduler loop.D2 The illegal-instruction trap in the lab is pure hardware: each CSR has its privilege level encoded in its address, and a csrr of a machine-level CSR from user mode never reaches the register; the hart raises cause 2 and, on this QEMU version, put the faulting instruction's bits into mtval (0xf14027f3: 0xf14 is mhartid's CSR number in the top 12 bits).R4 D5 On a real board, a firmware layer usually runs first in machine mode and starts the kernel in supervisor mode; the board's documentation, not this chapter, says how.

Untested on hardware

No RISC-V board was used. The CSR-address privilege encoding and whether mtval holds the instruction bits on illegal-instruction traps (implementations may write 0 instead) come from memory of D5 and were not checked; the run shows what QEMU did.

Worked example

Add the system call count to F3-07's uni-rv. The F3-08 kernel in the lab folder is the result; compare it with F3-07's file (diff) as you go.

  1. Choose the number. The next free one: SYS_count = 4, added to the enum (line 58). Both the kernel and the user program use this enum, so they cannot disagree about the number.
  2. Write the handler. long sys_count(Frame&) { return current.syscalls; } (line 80). It takes the trap frame like every handler, ignores it (no arguments), and reads kernel data the user cannot see.
  3. Add the table row at index 4: {"count", sys_count} (lines 103–104). The dispatcher needs no change: nsyscalls is computed from the table's size (line 113), so its bounds check grows with it.
  4. Call it from user mode: ecall(SYS_count, 0, 0); (line 200), then one more write so the run shows the program continuing (line 201).
  5. Predict the log. Calls before count: write, getpid, refused write, write of the refusal message = 4; handle_trap increments the counter before calling the handler, so count returns 5. Then write (6) and exit (7).
  6. Run and compare: "syscall 4 (count) -> 5", "user: all done, exiting", "7 system calls in total", exit code 0.R3

The same five steps in xv6 touch more files, because the number, the stub, the prototype and the table live in different places (Figure 2's grey row); the exam asks for them, plus a user test program.

Where the analogy breaks


    

  1. A school's rooms are all there at once; a kernel's "rooms" are code paths. Following a visitor in a building is following a path in space. Following a system call is following a path in time, across files, through function pointers and assembly; the symbol table and a debugger are your plan.
    2. 

  2. A tour shows one building; the map in this chapter mixes two. uni-rv and xv6 solve the same problems differently (M-mode with PMP versus S-mode with page tables). A mapping table helps you find the room; it does not say the rooms are built the same way.
    3. 

  3. The office binder can be rearranged; a system-call table cannot. Renumbering forms confuses only staff. Renumbering system calls breaks every program built before (Layer 3).
    4.
