Story hook

Analogy

Two students in the library each need two books for their homework: the atlas and the dictionary. Ravi picks up the atlas first. At the same moment, on the other side of the room, Lina picks up the dictionary. Ravi now waits for the dictionary; Lina waits for the atlas. Each politely holds what they have until the other is finished. The library closes, and both are still standing there.

Nobody did anything wrong on their own. Each student followed a sensible plan. The trouble is the combination: two people, two books, two different orders. The fix is a rule that costs nothing: "always take the atlas before the dictionary". Then whoever gets the atlas first gets both, and the other waits a minute.

An operating system kernel runs on several cores at once, and its shared tables are the library's books. This chapter is about the keys that protect them, and about the frozen machine you get when two cores take the keys in different orders.

What you will be able to do

  • Explain why kernel code that runs on several cores needs locks, and what a critical section is.
  • Explain how a spinlock works with one atomic instruction, and when a kernel uses a sleeping lock instead.
  • Name the four conditions for deadlock and show them in a real trace.
  • Diagnose a frozen machine from its serial log and the program counters of its CPUs, and prove a deadlock with a wait-for graph.
  • Fix a lock-order deadlock with a global lock order, and in C++ with std::scoped_lock.
Jargon box
Critical section
Simple words: a piece of code that must not run on two cores at the same time over the same data. Analogy: the moments when a student has the shared cupboard open. Precise: a code region that accesses shared data and must execute with mutual exclusion with respect to other critical sections on that data, so that their steps never interleave. D1
Lock
Simple words: a variable that says "somebody is using this data; wait". Analogy: the one key to a shared cupboard. Precise: a synchronization object with acquire and release operations that guarantees that at most one thread holds it at a time; code holding the lock forms a critical section. Also called a mutual-exclusion lock. D1
Spinlock
Simple words: a lock you wait for by trying again and again in a loop. Analogy: standing at the cupboard and trying the handle again and again. Precise: a lock whose acquire operation repeatedly executes an atomic read-modify-write (such as an atomic swap) until it observes the lock free; the waiting core stays busy. Used for short critical sections, and where the waiter cannot sleep, as in interrupt handlers. D1 D2
Sleeping lock
Simple words: a lock whose waiters give up the CPU until it is free. Analogy: writing your name on the list and sitting down until you are called. Precise: a lock whose acquire operation, when the lock is taken, blocks the calling thread (the scheduler runs something else) and wakes it when the lock is released; suited to long critical sections. std::mutex is the C++ interface to one. D1 D8
Deadlock
Simple words: threads that wait for each other forever. Analogy: two students each holding a book the other needs (registered). Precise: a state in which each thread of a set waits for a resource held by another thread of the same set, so none can proceed; it requires mutual exclusion, hold-and-wait, no preemption and circular wait. D7 S2
Lock ordering
Simple words: a rule that says in which order locks may be taken. Analogy: keys are always collected in alphabetical order. Precise: a global partial order on locks such that every thread acquires locks only in increasing order; it makes circular wait, and so deadlock between those locks, impossible. D1 D7
Wait-for graph
Simple words: a drawing of who waits for whom. Analogy: arrows from each waiting student to the student holding their book. Precise: a directed graph with one node per thread and an edge from T to U when T waits for a resource held by U; with single-instance resources such as locks, a cycle means deadlock. D7
Hart
Simple words: RISC-V's word for one CPU that runs instructions. Analogy: one teacher. Precise: a RISC-V hardware thread: a context that fetches and executes its own instruction stream with its own registers; each has a number readable from the mhartid register. D6 D5

Layer 1 — the kid explanation

A computer has several cores, and all of them can run parts of the operating system at the same time. They share the operating system's lists: which programs exist, which files are open, which memory is free. If two cores change the same list at the same moment, the list can end up broken, like two people writing on the same line of a notebook at once.D1

So the operating system uses locks. A lock is like the one key to a cupboard: only the person holding the key may open it, and everyone else waits until the key is returned. That keeps the lists tidy.D1

Locks bring a new danger. If one core holds key A and waits for key B, while another core holds key B and waits for key A, both wait forever. The computer freezes. This is called a deadlock. The cure is a rule: everyone takes the keys in the same order.D7

Layer 2 — the student explanation

Why the kernel needs locks

F3-01 to F3-04 described the kernel as if one CPU ran it. On a multicore machine every core enters the kernel on its own: one core handles a system call from one process while another handles a page fault for a second and a third takes a timer interrupt.D2 They all touch shared kernel data: the process table, the list of free frames, the scheduler's queue, the directory blocks of a file system. HW202 (F1-30) showed that two threads incrementing one plain counter lose updates, because "read, add, write" is three steps and the steps interleave.D1 In the kernel the consequences are worse than a wrong count: two cores could take the same free frame for two processes, or link a half-built entry into a list. Code that must not interleave with other code on the same data is a critical section, and a lock makes it one.

Even on one core the kernel has the same problem in miniature: an interrupt can arrive in the middle of kernel code, and the interrupt handler may touch the same data. That is why xv6's spinlocks also turn interrupts off on the core that holds them.D2

How a spinlock works

A lock is a word in memory: 0 means free, 1 means taken. Acquiring it cannot be "read the word; if it is 0, write 1", because two cores could both read 0 before either writes. The processor must do the read and the write as one indivisible step: an atomic operation. The university's kernel uses an atomic swap: write 1 and get the old value back, in one step. If the old value was 0, this core took the lock; if it was 1, somebody else has it, so try again.D1 Listing 1, line 69, is exactly that loop, and the compiler turned it into the RISC-V instruction amoswap.w.aq (R6, in "How the hardware actually does it").R6 Release is a single atomic store of 0.

The __ATOMIC_ACQUIRE and __ATOMIC_RELEASE words in the listing are memory-ordering constraints (HW203, F1-37): the processor and compiler may not move the critical section's loads and stores out past the lock operations, so the next holder sees all the previous holder's writes.D8

A spinning core does no useful work. That is acceptable when critical sections are short (a few list operations) and when the waiter could not sleep anyway, such as inside an interrupt handler. When a holder may wait for something slow, such as a disk read, the kernel uses a sleeping lock: a waiter asks the scheduler to block it, and the release wakes it. xv6 has both kinds; the file system's per-file locks are sleeping locks, because they are held across disk operations.D2 In user programs, std::mutex plays the sleeping-lock role.D8

Deadlock

Operations that touch two objects need two locks. A file system's rename changes a directory and an inode; unlink changes the same two. If rename takes the directory lock first and unlink takes the inode lock first, and both run at once on two cores, each can end up holding one lock and spinning for the other. That is the frozen machine of Figure 1, and it is a real run: the university's kernel on two emulated RISC-V CPUs in QEMU printed its last lines and then nothing, until the 6-second limit stopped QEMU with exit code 124.R1

The textbook lists four conditions that must all hold for a deadlock:D7

  1. Mutual exclusion: a lock has one holder at a time.
  2. Hold and wait: a thread holds one lock while waiting for another.
  3. No preemption: nobody can take a lock away from its holder.
  4. Circular wait: a cycle of threads, each waiting for a lock held by the next.

Break any one and deadlock is impossible. In practice kernels break the fourth: they fix a lock order, and every code path takes locks in that order. With one order, the thread that gets the first lock can always get the rest, so no cycle can form.D1 D7 The fixed kernel (-DSAME_ORDER) makes unlink take the directory first as rename does; the same interleaving now completes and powers the machine off with exit code 0.R3

In user-space C++ there is a second way when you need several mutexes at once: std::scoped_lock with all of them. It acquires them with a deadlock-avoidance algorithm whatever order the callers name them in.D8 Listing 3 moves books between two shelves in opposite directions in two threads, 100,000 times each, and finishes with the total intact.R5

Layer 3 — the engineer's depth

Lock order must be written down. A kernel with hundreds of locks needs a documented order (for example "directory before the inodes in it; parent before child; the process-table lock before any single process's lock"), and every new code path must respect it. xv6's book describes its own ordering rules for the file system and the process locks.D2 When an operation cannot know the order in advance (two inodes found during a path walk), a common rule is to order by a stable key, such as the inode number or the lock's address. That is the idea behind std::scoped_lock's deadlock avoidance, done with retries instead of a fixed order.D8

Tools find the cycle before the machine freezes. A lock validator records, at run time, every pair "lock B taken while holding lock A" and reports the first time a path takes them in the opposite order, even if that run did not deadlock. The Linux kernel has one (lockdep).D1 Listing 4 is a much smaller relative: it rebuilds the wait-for graph after the fact from a log. ThreadSanitizer reports lock-order inversions in user programs too.

Spinlocks and interrupts. If a core holds a spinlock and an interrupt handler on the same core tries to take it, the handler spins forever: the holder cannot run until the handler returns. A deadlock with one CPU. That is why kernels disable interrupts while holding a lock that handlers also use (xv6 does this for every spinlock).D2

Sleep and wakeup. Sleeping locks, pipes and wait all need "block until a condition changes". The danger is a lost wake-up: the condition changes after a thread checked it but before it went to sleep. The fix is to hold a lock while checking and to release it atomically with going to sleep; condition variables (std::condition_variable, the xv6 sleep and wakeup pair) are built for that pattern.D1 D2

Other failures. Livelock (threads keep reacting to each other and make no progress), priority inversion (a low-priority holder blocks a high-priority waiter while medium-priority work runs), and lock contention (correct but slow, because all cores wait for one lock) are the other faces of locking; the textbook covers them with deadlock.D1 D7 Lock-free data structures avoid locks with atomic instructions alone; they are a later topic.

Not verified — check before relying on this

The statements about xv6 in this chapter (spinlocks that disable interrupts; sleeping locks for inodes; its documented lock-ordering rules; the sleep and wakeup names) and about Linux's lockdep come from the author's memory and were not checked against the xv6 source or book or the Linux documentation in this build; xv6's source is not in the build container. Also unverified: that amoswap.w.aq is defined with acquire semantics exactly as C++'s __ATOMIC_ACQUIRE requires (the compiler chose it, R6; the mapping is in the RISC-V specification, D6, not opened). The deadlock in the forensic lab is real, but its interleaving is forced by the kernel's step flags so that it happens on every run; in a real kernel the same bug strikes rarely and at random.

How the hardware actually does it

The disassembly of the frozen kernel's acquire shows the spin loop the two stuck CPUs were executing:



The address 0x800001f4, where QEMU found both program counters (R2), is the top of this loop. amoswap.w.aq a5,a5,(a4) swaps the 32-bit word at the lock's address (a4 = lock + 8, the locked field) with 1 and returns the old value in a5; bnez loops while it was not 0. The .aq suffix marks acquire ordering. The beq s0,s4 instruction compares the spin counter with 2,000,000 (s4 was loaded with 0x1e8480), the watchdog of line 70.R6 D6 On real hardware an atomic instruction gets exclusive ownership of the cache line holding the lock through the coherence protocol of HW203 (F1-36): while two cores spin with swaps, that line moves back and forth between their caches on every attempt, which slows both and the memory system around them. Production spinlocks therefore spin on a plain load until the lock looks free and only then try the atomic, or use queue-based designs.D1 RISC-V also offers the load-reserved / store-conditional pair (lr.w, sc.w) from which any atomic update can be built.D6

Worked example

  1. Order of events. cpu0 (pid 3) logs "holds 'dir /home'". Then cpu1 (pid 4) logs "holds 'inode notes.txt'". Then cpu1 asks for 'dir /home' and cpu0 asks for 'inode notes.txt'. Neither ever logs "holds" again.
    2. 

  2. Mutual exclusion. The watchdog lines say "still spinning on 'dir /home' held by cpu0" and "… 'inode notes.txt' held by cpu1": each lock has exactly one holder, and the other CPU is excluded.
    3. 

  3. Hold and wait. cpu0 holds 'dir /home' and waits for 'inode notes.txt'; cpu1 holds 'inode notes.txt' and waits for 'dir /home'. No "release" line appears for either lock.
    4.

    5. 

  5. Circular wait. cpu0 → (waits for a lock held by) cpu1 → cpu0. Listing 4 finds the same cycle mechanically.R4

Where the analogy breaks


    

  1. Students notice; CPUs do not. Two students would soon talk and one would put a book down. A spinning core has no idea it is in a cycle; it tries the same instruction forever (Figure 2). Only a design rule (lock order) or a tool notices.
    2. 

  2. A key is a thing; a lock is a convention. A cupboard without the key stays shut. A lock protects data only if every piece of code that touches the data takes the lock first; nothing stops a careless function from writing without it.D1
    3. 

  3. Trying the handle costs others too. A student rattling a handle disturbs nobody else much. Spinning cores fight over one cache line and slow the memory system for everyone (How the hardware actually does it).
    4. 

  4. The registered deadlock picture has two students. Real cycles can be long (A waits for B, B for C, C for A) and can involve other resources besides locks; the four conditions still apply.D7
    5.

Transition box

Where you came from: HW202 (F1-30) showed data races and atomics between threads; HW203 (F1-36, F1-37) explained coherence and memory ordering; F3-03 made threads and preemption the normal case. What carries over: every rule about data races and atomics; the scheduler can stop a thread anywhere.D8 What changes: now the shared data is the kernel's own, the code that races is the kernel running on several cores (and its interrupt handlers), and a mistake freezes the whole machine instead of one program. Locks fix races and bring a new failure, deadlock, which you prevent by design.D1 What comes next: F3-06 builds files and directories, the very structures that rename and unlink lock, and asks what happens when the power fails in the middle of changing them.

Method hints. "acquire" without a matching "holds" means waiting. Two CPUs at one PC can wait for different locks: look at the register that holds the lock's address, or at the watchdog lines. A frozen machine is a cycle, a crash or an infinite loop; the evidence tells them apart.

Summary


    

  • Kernel code runs on several cores and in interrupt handlers at once; shared kernel data needs critical sections.
    • 

  • A spinlock is an atomic swap in a loop (amoswap.w.aq on RISC-V); a sleeping lock blocks the waiter.
    • 

  • Deadlock needs mutual exclusion, hold and wait, no preemption and circular wait; kernels break circular wait with a lock order.
    • 

  • A frozen machine is diagnosed from evidence: the log's last lines, every CPU's PC, and the wait-for graph.
    • 

  • In C++, std::scoped_lock takes several mutexes without deadlock.
