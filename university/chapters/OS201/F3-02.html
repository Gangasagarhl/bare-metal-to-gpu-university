Story hook

Analogy

On sports day, class 7B is too big for one coach, so the principal does something unusual: she splits it. A second room is opened, and everything in 7B's room is copied into it: the desks, the posters, every half-finished drawing. The new group even gets a copy of 7B's register, with one difference written at the top: "you are the new class". From that moment the two groups live separate lives. If someone in the new room rubs out a drawing, the drawing in the old room is untouched.

Sometimes the new class does not want to keep 7B's work at all. It keeps its new room and its register number, but empties the shelves and brings in the books for a completely different subject.

And when a class finishes its day and goes home, it leaves its attendance sheet on the principal's desk. Somebody, usually the class that asked for the split, must come and sign it. Until then the sheet stays, and if nobody ever signs, the desk slowly disappears under paper.

Those three moments are the three most important system calls about processes: fork, exec and wait.

What you will be able to do

  • Explain what a process is and what the kernel keeps about it, with the school analogy and precise terms.
  • Draw the life of a process as states (ready, running, blocked, zombie) and name what moves it between them.
  • Write C++ programs that create processes with fork, run another program with exec, and collect exit status with waitpid, checking every return value.
  • Predict how many processes a sequence of fork calls creates, and check the prediction with a program.
  • Diagnose a process leak (zombies) from the kernel's process information.
Jargon box
Process
Simple words: a program while it is running. Analogy: a class with its own room. Precise: the OS abstraction of a running program: a private address space, one or more threads, and kernel-held state (open files, current directory, credentials, parent, exit status), identified by a PID (F3-01). D1 D3
Process identifier (PID)
Simple words: the number the kernel gives each process. Analogy: the class's register number. Precise: a positive integer that names a process in system calls such as waitpid and kill; getpid returns the caller's, getppid its parent's. D4
Process control block (PCB)
Simple words: the kernel's record card for one process. Analogy: the class's file in the principal's cabinet. Precise: the kernel data structure holding a process's state, saved registers (when it is not running), memory map, open files, PID, parent and exit status; xv6 calls it struct proc. D1 D2
fork
Simple words: the call that makes a copy of the running process. Analogy: splitting a class into two identical classes in two rooms. Precise: a POSIX system call that creates a child process whose address space and open files are copies of the caller's; it returns twice: 0 in the child and the child's PID in the parent (−1 on failure, with no child). D3 D4
exec
Simple words: the call that replaces the running program with a different one, in the same process. Analogy: the class keeps its room and number but swaps every book for a new subject. Precise: the execve system call (and its C library front ends such as execv) loads a new program image into the calling process, keeping its PID and (by default) its open files; on success it does not return. D3 D4
wait / waitpid
Simple words: the call a parent uses to wait for a child to finish and hear how it ended. Analogy: signing the attendance sheet. Precise: system calls that block the caller until a child changes state (by default, terminates), return the child's PID and store a status word decoded with WIFEXITED and WEXITSTATUS; collecting it lets the kernel free the child's remaining record. D4
Exit status
Simple words: the small number a program hands back when it ends: 0 for success. Analogy: the mark written on the attendance sheet. Precise: the value passed to exit or returned from main, of which the parent receives the low 8 bits through wait; by convention 0 means success. D3 D4
Zombie process
Simple words: a process that has finished but whose parent has not yet collected its exit status. Analogy: an unsigned attendance sheet on the principal's desk. Precise: a terminated process whose kernel record (PID, exit status, resource usage) is kept until its parent waits for it; it uses no CPU or user memory, but its process-table entry and PID stay taken. D3 R4
Process state
Simple words: what a process is doing right now: running, ready to run, waiting, or finished. Analogy: a class being taught, waiting for a teacher, waiting for the library, or gone home. Precise: the kernel's classification of a process for scheduling: running (on a CPU), ready (runnable, waiting for a CPU), blocked (waiting for an event such as I/O), plus states for creation and termination such as zombie. D1

Layer 1 — the kid explanation

A program on the disk is like a lesson plan in a drawer: nothing happens. A process is the lesson actually taking place: a class in a room, with its own things on the desks and a register number. Run the same program twice and you get two processes, two classes following the same plan in two rooms.D1

New processes are made by copying. A process calls fork, and the kernel makes a second process that is a copy of the first, down to the values of the variables. The copy is the child; the original is the parent. Both carry on from the same line of the program. The only way to tell them apart is the answer fork gave: 0 in the child, the child's number in the parent.D3

Often the child does not want to run the same program. It calls exec and becomes a different program, keeping its number. That is how a shell starts every command you type: fork, then exec in the child.D1 When the child ends, it leaves an exit status behind, and the parent collects it with wait. If the parent never collects it, the finished child stays in the kernel's list as a zombie.D3

Layer 2 — the student explanation

What the kernel keeps per process

For each process the kernel keeps a record, the process control block: the process's state, its PID and its parent, its memory map, its table of open files, and, whenever the process is not on a CPU, a copy of its registers so that it can be resumed exactly where it stopped.D1 All the records together form the kernel's process list. A process cannot read or change its own record; it can only ask about it (getpid) or change parts of it through system calls (chdir, open).D4

States

At any moment a process is running on a CPU, ready to run but waiting for a CPU, or blocked until some event happens (data from a disk or network, a child exiting, a timer).D1 The scheduler moves processes between ready and running (F3-03); system calls such as read and waitpid move a process to blocked; the kernel moves it back to ready when the event occurs. After exit, a process is a zombie until its parent waits for it (Figure 1).D3

fork: one call, two returns

Listing 1 tells the whole story in about 25 lines. The variable marks is 10 before the call. After fork, the child sets its copy to 99 and returns 7 from main; the parent waits, learns the status 7, and prints its own marks, still 10.R1 Child and parent have separate address spaces, so a change in one is invisible to the other.D3 F3-04 shows that the two copies even use the same virtual address for marks. The child also confirms that getppid() names the process that called fork.R1

Every call can fail. fork returns −1 and creates no child when the system cannot make another process; Listing 1 checks for that before testing for 0.D4

exec: same process, new program

In Listing 2 the child calls execv("/bin/echo", argv). The kernel discards the child's program image, loads /bin/echo into the same process and starts it at its beginning, with the argument list the child supplied.D3 If that succeeds, nothing after execv in the child's code ever runs: that code is gone. The two lines after it (perror, _exit(127)) are reached only if exec failed, for example because the file does not exist.D4 The run shows echo's output between the parent's two lines, and the parent receiving exit status 0.R2

Why two calls instead of one "start a program" call? Because between fork and exec the child can change its own situation (redirect its output to a file, close descriptors, change directory), and the new program inherits it. That is how a shell implements > file and pipes.D1

wait: collecting the result

waitpid(child, &status, 0) blocks the parent until that child terminates, then returns its PID and fills status. WIFEXITED(status) says whether the child ended normally, and WEXITSTATUS(status) extracts the number it returned.D4 Until a parent waits, the kernel must keep the child's exit status somewhere; that leftover record is the zombie. If the parent itself exits first, the orphaned children are adopted by another process, traditionally init, which waits for them.D3

Layer 3 — the engineer's depth

Copying cheaply. Copying a whole address space on every fork would be slow, and wasted when the child calls exec at once. Implementations therefore share the parent's physical pages with the child and mark them read-only; the first write by either process causes a page fault, and only then does the kernel copy that one page (copy-on-write, F3-04's mechanism).D3 To the program, the effect is the same as a full copy, which is what Listing 1 shows; the speed difference is invisible in its output.

Buffers are in the process's memory. printf collects output in a buffer inside the process before calling write (F3-01). A buffer that still holds text at the moment of fork is copied too, and both processes will eventually write it: the text appears twice. That is why every listing here calls std::fflush(stdout) immediately before fork, and why a child that must not run the parent's clean-up ends with _exit, which skips the C library's flushing and exit handlers.D3 D4

Inherited descriptors. The child's table of open files is a copy of the parent's, pointing at the same open files. Listing 3 relies on that: all eight processes write into one pipe created before the first fork, and the original reads until end-of-file, which arrives only when every process has closed its copy of the writing end.D4 R3

Where the state is visible on Linux. Linux shows each process as a directory /proc/<pid>; the third field of /proc/<pid>/stat is a one-letter state.D4 Listing 4 read it for three children that had exited but had not been waited for: each showed Z; after waitpid, their directories were gone.R4

Not verified — check before relying on this

The other state letters Linux uses in /proc/<pid>/stat (for example R for running or runnable, S for interruptible sleep, D for uninterruptible sleep, T for stopped) and the names of xv6's process states in struct proc (believed to include UNUSED, SLEEPING, RUNNABLE, RUNNING and ZOMBIE) were written from memory; only Z was observed in this build. Check proc(5) in the Linux man-pages project and the xv6 book's scheduling chapter (and kernel/proc.h in the xv6 source) for the versions you use.

How the hardware actually does it

The CPU has no idea what a process is. It has one set of registers per core and a register that points at the current page-table root (F1-38 in HW203 showed translation).D3 A process exists only because the kernel saves one process's registers into its record, loads another's, and switches the page-table root: that switch is the context switch of F3-03. fork works the same way at the hardware level: the kernel builds a new page-table tree for the child (sharing pages copy-on-write), copies the parent's saved registers into the child's record with the return-value register set to 0, and marks the child ready; the parent's copy of that register gets the child's PID.D2 D3 That is why fork "returns twice": two saved register sets, two different values in the return register.

Worked example

Question: how many processes exist after this loop, and who creates whom? for (int i = 0; i < 3; ++i) { fork(); }

  1. Before the loop: 1 process, P.
  2. i = 0: every existing process (only P) forks once. Now 2: P and its child A. Both continue the loop with i = 0 finished.
  3. i = 1: both P and A fork. Now 4: P, A, B (child of P), C (child of A).
  4. i = 2: all four fork. Now 8.
  5. In general, n calls in a row give 2n processes, because each call doubles the number of processes that execute the rest of the code. For n = 3: 2 × 2 × 2 = 8.
  6. Check with a program: Listing 3 makes every process write one byte into a shared pipe; the original counts the bytes. It printed 8.R3
  7. Who must wait for whom? P waits for its direct children (A, B and the child it made at i = 2). A waits for its own children, and so on. In Listing 3 the copies exit with _exit without waiting; their own children are adopted and collected by another process (Layer 2), so nothing leaks for long. A long-running parent cannot rely on that.

Where the analogy breaks


    

  1. Copies are not made at once. Splitting a class means carrying furniture. fork on real systems shares the pages and copies a page only when someone writes to it (Layer 3); a fork followed by exec copies almost nothing.D3
    2. 

  2. Processes can share on purpose. Two classes in two rooms share nothing. Processes can ask for shared memory or share open files and pipes, as Listing 3 does; the registered map already notes this ("processes can share memory if they ask").S2
    3. 

  3. A zombie costs almost nothing, until there are many. An unsigned sheet is only paper. A zombie holds a PID and a process-table entry; both are limited, so a parent that never waits can eventually prevent new processes from being created (the forensic lab).D3
    4.

Summary


    

  • A process is a running program: a private address space, threads, and a kernel record (PID, parent, open files, state, saved registers).
    • 

  • States: ready, running, blocked, and zombie after exit until the parent waits.
    • 

  • fork copies the caller and returns twice: 0 in the child, the child's PID in the parent, −1 on failure.
    • 

  • exec replaces the program in the same process and returns only on failure.
    • 

  • waitpid blocks until a child ends, returns its status (decode with the macros) and frees the zombie.
    • 

  • n forks in a row make 2n processes; flush output before forking.
    •
