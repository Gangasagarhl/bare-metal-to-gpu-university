Story hook

Analogy

Students may not walk into the school office. When Tomás needs a copy of his timetable, he fills in form 1 ("please print page …") at the office window, writes the page number, and slides it through. The clerk reads the form number, finds the right procedure in the binder, prints the page, and slides the result back. Tomás never touches the printer.

One day Tomás writes on the form a page number from the staff cupboard: the page with next week's exam answers. A careful clerk checks "is this page one of the student's own?" and hands the form back stamped "refused". A careless clerk who only checks "is the page number below the end of the student pages?" prints the exam.

The window is the system call, the form number is the system-call number, and the clerk's check is the line of kernel code that decides whether a user program can read the kernel's secrets. In this chapter you write both clerks and watch what each does.

What you will be able to do

  • Explain step by step what happens from a write call in a program to the kernel's code and back, on RISC-V and in outline on x86-64 Linux.
  • Read a trap handler: the trap frame, the cause register, the dispatch table and the return.
  • Call Linux system calls three ways (library, wrapper, raw number) and interpret errno values such as EFAULT and ENOSYS.
  • Explain why the kernel must check every pointer a program passes, and write a correct range check.
  • Diagnose a kernel information leak from a serial log and a symbol table.
Jargon box
System call
Simple words: a program's request for the kernel to do something it may not do itself. Analogy: asking at the office window with a form (registered). Precise: the F3-01 definition (glossary); in this chapter, the exact sequence: arguments in registers, a trap instruction, the kernel's dispatch on a number, checks, the work, and a return value in a register. D1
Trap
Simple words: the processor stops the program and jumps into the kernel. Analogy: the window opens and the clerk takes over. Precise: a synchronous or asynchronous transfer of control to a privileged handler, caused by a trap instruction (system call), an exception (fault) or an interrupt; the hardware records the cause and the interrupted program counter and raises the privilege level. D1 D5
Trap frame
Simple words: the saved copy of the program's registers while the kernel works. Analogy: the clerk copies everything on the student's desk onto a tray, and puts it back afterwards. Precise: a memory area, written by the kernel's trap entry code, that holds the interrupted program's general-purpose registers, so that the handler can read the arguments, write the result and restore the program exactly. D2
ecall
Simple words: the RISC-V instruction that asks the next privilege level for service. Analogy: sliding the form through the window. Precise: the RISC-V environment-call instruction; executed in user mode, it raises an exception with cause 8 ("environment call from U-mode") into the handler of a higher privilege level. D6 D5
Machine mode
Simple words: the RISC-V processor's most powerful mode, which can touch everything. Analogy: the principal's keys. Precise: the highest RISC-V privilege level (M), in which a hart starts after reset; below it are supervisor mode (S, where xv6 and Linux run) and user mode (U); the university's kernel uses only M and U. D5
PMP (physical memory protection)
Simple words: RISC-V hardware that says which physical addresses lower modes may use. Analogy: a fence around the student area of the building. Precise: a set of machine-mode registers (address and configuration pairs) that grant read, write and execute permission on physical address ranges to S and U mode; an access by those modes that no entry allows raises an access-fault exception. D5
errno
Simple words: the number that says why a system call failed. Analogy: the reason stamped on a refused form. Precise: a thread-local variable that the C library sets from the error code a failing Linux system call returns (the call itself returns −1); for example EFAULT (14, "Bad address") and ENOSYS (38, "Function not implemented") on the build machine. D4 R1

Layer 1 — the kid explanation

Programs are not allowed to touch the computer's hardware directly: not the screen, not the disk, not the network, not the memory of other programs. Only the operating system's kernel may. That is what keeps one broken or nasty program from wrecking everything.D1

So when a program wants something done, such as "write these letters on the screen", it asks the kernel. Asking is a special instruction that stops the program and wakes up the kernel, like sliding a form through the office window. The form says which service is wanted (a number) and the details (where the letters are, how many). The kernel checks the form, does the job, writes the answer back, and the program carries on.D1

The checking matters. If a program hands over the address of some secret kernel data and says "please print this", a careless kernel would print it. A careful kernel first checks that the address belongs to the program.D2

Layer 2 — the student explanation

The path of one system call

F3-01 showed system calls from outside, with strace. Now follow one through the university's kernel, uni-rv, which runs in QEMU's RISC-V virt machine (Listings 2 to 4). It is small enough to read entirely: one process, three system calls, one trap handler.

  1. The program prepares the form. By uni-rv's convention (the same one xv6 uses on RISC-V), the system-call number goes in register a7 and the arguments in a0, a1, …D2 The disassembly of user_main shows it: li a1,27, li a7,1, ecall.R5
  2. The hardware traps. ecall in user mode raises an exception. The hart saves the address of the ecall in mepc, writes the cause 8 into mcause, switches to machine mode, and jumps to the address in mtvec.D5
  3. Entry code saves the program. trap_entry (Listing 3) swaps the stack pointer with mscratch, which holds the kernel's stack, and stores 31 registers into a 256-byte trap frame, each at offset 8 × its register number. Nothing of the user program's state is lost.
  4. The handler dispatches. handle_trap reads mcause; 8 means system call. It takes the number from the frame's a7 (register 17), checks that it is in the table, and calls the function, here sys_write.
  5. The system call checks and works. sys_write reads the pointer and length from the frame's a0 and a1, checks that the whole range lies in the user's region, and prints it to the serial port, which only the kernel can touch.
  6. The result goes back. The handler stores the result in the frame's a0 and adds 4 to mepc, so that the program continues after the ecall instead of repeating it.
  7. Return. trap_entry restores all registers (now with the new a0), swaps the stack back and executes mret, which returns to user mode at mepc.D5

The syscalls run logs each step's result: write → 27 (bytes), getpid → 1, the refused write → −1, and the exit after 5 system calls, with QEMU's exit code 0.R2

What stops a program from cheating

Three hardware rules make the window the only way in.D5 D1

  • The entry point is fixed. A trap always jumps to mtvec, which only machine mode can set. A program cannot jump into the middle of the kernel with higher privilege.
  • Privileged instructions fault in user mode. Reading or writing mtvec, mstatus or the PMP registers from user mode raises an illegal-instruction exception (F3-08's experiment shows one).
  • Memory is fenced. uni-rv has no page tables; it uses RISC-V's PMP: one entry allows user mode to read, write and execute 0x80020000 to 0x80028000 and nothing else. In the device_fault build the user program stores a byte to the serial port at 0x10000000; the hart raised a store access fault, the kernel printed mcause=7 and mtval=0x0000000010000000, killed the process and powered off with exit code 1.R4 On a kernel with virtual memory, page-table permissions (the U bit of F3-04) do this job.

The fourth rule is software: the kernel must check every argument. The hardware fences stop the program from reading kernel memory; they do not stop the program from asking the kernel to read it on its behalf, because the kernel runs in machine mode and may read everything. In the syscalls run the user passes the address of the kernel's secret kernel_note to write; user_range_ok sees the address is outside the user region and returns −1.R2 The forensic lab shows a kernel whose check has one missing condition.

The same thing on Linux

Listing 1 reaches Linux's write three ways: printf (the C library buffers, then calls write), the write wrapper, and syscall(SYS_write, …) with the number chosen by hand. strace sees three identical write(1, …) calls.R6 The build machine's header defines SYS_write as 1 and SYS_getpid as 39, and the program printed the same numbers.L1 R1

Linux reports failure by returning a negative error code; the C library wrapper turns it into the return value −1 and stores the code in errno.D4 Listing 1 shows two refusals. A write from address 1, which the process does not own, returned −1 with errno 14, "Bad address" (EFAULT), and the process carried on: Linux checked the pointer as uni-rv does. System call number 99999 returned −1 with errno 38, "Function not implemented" (ENOSYS): the table lookup failed, as uni-rv's bounds check does.R1

Layer 3 — the engineer's depth

When is a pointer checked? The two strace runs of Listing 1 differ in one line. With standard output going to a file, write(1, 0x1, 5) returned EFAULT. With standard output going to /dev/null, the same call returned 5.R6 R7 The interpretation, consistent with both runs but not tested further in this build: Linux does not check a buffer when the call starts; it checks each access when the kernel actually copies from user memory, and /dev/null's write never reads the buffer. Kernels do this with special copy functions (copy_from_user in Linux, copyin in xv6) that validate the address and turn a fault during the copy into an error code instead of a kernel crash.D2 uni-rv instead checks the whole range up front, which is simpler and enough because it has one fixed user region.

Time of check to time of use. If the kernel checks a value in user memory and later reads it again, another thread of the same process can change it in between. Kernels copy arguments into kernel memory once and use only the copy.D1

Writing the check without overflow. The obvious check addr >= lo && addr + len <= hi has a trap of its own: with a huge len, addr + len wraps around past zero and the check passes. uni-rv's line 67 is written so that no expression can overflow: first len <= hi - lo, then addr <= hi - len.

Faster system calls. Some calls are made so often (reading the time) that Linux maps a small kernel-provided code page, the vDSO, into every process; the C library calls into it and no trap happens. You saw [vdso] in F3-04's memory map.D4 On x86-64, Linux system calls use the syscall instruction with the number in rax and arguments in rdi, rsi, rdx, r10, r8, r9.D4

Real kernels use supervisor mode. xv6 and Linux on RISC-V run in S-mode with page tables; a small firmware (OpenSBI, for example) stays in M-mode. The trap path is the same with s registers: stvec, sepc, scause, stval, sscratch, sret. In xv6, user traps enter through the trampoline page, save registers into a per-process trap frame page, and dispatch in a C function called syscall through a table indexed by a7; arguments are fetched with helper functions.D2 uni-rv uses machine mode only to stay small; F3-08 maps each of its parts to xv6's.

How the hardware actually does it

QEMU's own report of the machine (info mtree, through its QMP control socket, before the first instruction) gives the physical memory map uni-rv is written against:



The serial port is 8 bytes at 0x10000000; writing a byte there prints a character (memory-mapped I/O, HW204). The test device at 0x100000 stops QEMU: uni-rv writes 0x5555 for exit code 0 and (code << 16) | 0x3333 for an error code, which is how the runs report success or failure to the lab runner.R3 RAM starts at 0x80000000, where QEMU (with -bios none) starts every hart, and where entry.S is linked.R2 On a trap the hart itself does a small, fixed amount of work: it records mepc, mcause and mtval (the faulting address for an access fault, as the device_fault run showed), saves the previous privilege mode and interrupt-enable bit in mstatus, and jumps to mtvec. Saving registers is software's job, which is why trap.S exists. mret reverses the hardware part: the privilege mode comes back from mstatus.MPP and the program counter from mepc.D5 enter_user uses exactly that to start the user program the first time: it sets mepc to user_main, sets MPP to user mode, and executes mret as if returning from a trap that never happened.

Where the analogy breaks


    

  1. It is not a polite request. A form at a window waits until the clerk has time. A system call is the processor switching privilege level at once, in the middle of the program's instruction stream (the registered "where it breaks").S2
    2. 

  2. The clerk is the student's own teacher. No separate person serves the window: the same hart that ran the program runs the kernel's handler, on a different stack, then goes back to the program.
    3. 

  3. Staff-only rooms are enforced by hardware. A sign on a door can be ignored; a PMP fence or a page-table permission cannot (the registered note for user and kernel mode).S2 But the kernel's own checks are software, and they can have bugs, as the forensic lab shows.
    4.

Summary


    

  • A system call puts a number and arguments in registers and executes a trap instruction (ecall; syscall on x86-64).
    • 

  • The hardware records the cause and return address, raises privilege and jumps to a fixed entry; software saves the registers in a trap frame.
    • 

  • The kernel dispatches through a table, checks every argument, writes the result into the frame and returns past the trap instruction.
    • 

  • Hardware fences (PMP, page permissions) stop user code from touching kernel memory; only software checks stop the kernel from doing it on the user's behalf.
    • 

  • Linux reports failures as −1 plus errno: EFAULT for bad pointers, ENOSYS for unknown numbers.
