Story hook

Analogy

The school library has thousands of books, and nobody finds one by walking along the shelves. You look up the title in the catalogue. The catalogue gives you a card number; the card says how long the book is and on which shelves its parts are. Two titles can lead to the same card: "Maths 7" and "Mr Haddad's textbook" are one book.

One evening the librarian, Ms Wanjiru, is shelving a new book when the power fails. She had already written the new card, but had not yet put the pages on the shelf. Next morning the card points to a shelf that still holds the pages of a book that was thrown away last week, and the first student to borrow the "new" book reads someone else's old exam marks.

The catalogue, the cards and the shelves are a file system. The order in which the librarian updates them, so that a power cut never leaves a lie behind, is crash consistency. Both are in this chapter.

What you will be able to do

  • Explain the difference between a file's name, its inode and an open file descriptor, and show it with system calls.
  • Trace a path lookup through directories to an inode and its data blocks, by hand and with a toy file system.
  • Predict what link, rename and unlink do to names and link counts, and why an unlinked file can still be read.
  • Explain why the order of disk updates matters when power can fail, and what a consistency checker can and cannot find.
  • Diagnose a crash that exposed old data, from a replay of the update order.
Jargon box
File system
Simple words: the part of the OS that keeps named files on a storage device. Analogy: the library catalogue and shelves (registered). Precise: an on-disk data layout (allocation maps, inodes, directories, data blocks) together with the kernel code that implements files and names on top of a block device and keeps the layout consistent. D1 S2
Inode
Simple words: the record that describes one file, without its name. Analogy: a catalogue card: size and the shelves that hold the pages. Precise: an on-disk structure, identified by an inode number, holding a file's type, size, permissions, link count, timestamps and the addresses of its data blocks (directly or through indirect blocks). D1 D2
Directory (file system)
Simple words: a special file that lists names and the inodes they belong to. Analogy: a list of titles, each with a card number. Precise: a file whose content is a set of entries (name, inode number); path lookup reads directories one component at a time, starting at the root directory's inode. D1
Hard link
Simple words: one more name for a file that already exists. Analogy: two titles pointing to the same card. Precise: a directory entry; every name of a file is a hard link to its inode, the inode's link count records how many there are, and the file's storage is freed only when the count is 0 and no process has it open. D1 D4
File descriptor
Simple words: the small number a program uses for a file it has opened. Analogy: a borrowing slip. Precise: the SP102 definition (glossary); here: an index into the process's table of open files, each pointing to a kernel open-file object that refers to the inode, not to the name. D1
Crash consistency
Simple words: making sure a power cut never leaves the file system in a state that lies. Analogy: shelving in an order that survives a power cut mid-way. Precise: the property that the on-disk structures, after a crash at any point of an update that touches several blocks, are either consistent or can be made consistent, without exposing other files' data; achieved by careful write ordering, journaling (logging) or copy-on-write. D1
fsck
Simple words: a tool that checks a file system's records against each other after a crash. Analogy: the librarian checks that every shelf marked "in use" belongs to some card. Precise: a file-system consistency checker that scans allocation maps, inodes and directories, and repairs disagreements (leaked blocks, wrong link counts, blocks used twice); it cannot tell whether a block holds the right data. D1
Journaling
Simple words: writing a note of what you are about to change before changing it. Analogy: the librarian writes "card 2 → shelf 0, shelf 0 = new pages" in a notebook first, then shelves; after a power cut she redoes what the notebook says. Precise: a technique in which the blocks of an update are first written to a log on disk and committed with a final record; after a crash, committed transactions are replayed and uncommitted ones ignored, so the update is all-or-nothing. D1 D2

Layer 1 — the kid explanation

A computer keeps your drawings, games and homework in files. A file has a name, like holiday.png, and it lives inside folders (computer people say directories), which can live inside other folders. The disk itself knows nothing about names or folders: it is a long row of numbered boxes, each holding a few thousand bytes.D1

The operating system's file system is the library catalogue that turns names into box numbers. For each file it keeps a card that says how big the file is and which boxes hold it. A folder is a list of names with card numbers.D1

Saving one file changes several things: the list of free boxes, the card and the boxes themselves. If the power goes off in the middle, some of those changes happened and some did not. A good file system does the changes in a careful order, or writes a note first, so that a power cut never leaves a card pointing at the wrong box.D1

Layer 2 — the student explanation

Names, inodes and open files are three different things

Listing 1 creates a file, gives it a second name, renames it, deletes both names while the file is open, and reads it anyway.R1 Each step separates two ideas that everyday language mixes up.

  • The file is the inode. stat reports an inode number; after link and after rename it is the same number ("same inode: yes"). The data, the size and the permissions belong to the inode.D4
  • Names are directory entries. link added a second entry for the same inode, and the link count went from 1 to 2. rename changed an entry and left the inode alone. unlink removes an entry; there is no system call that "deletes a file" directly.D1 D4
  • An open file refers to the inode. After both names were removed, the link count was 0, yet read through the open descriptor returned all 15 bytes. The kernel frees the inode and its blocks only when the link count is 0 and no open file refers to it; after close, the name does not exist.R1 D1

The strace run of the same program (Listing 1's second output) shows that each library call is one system call: openat, write, link, rename, unlink, read, and an access that fails with ENOENT, "No such file or directory".R2 The descriptor is 3 both times because 0, 1 and 2 are taken by standard input, output and error, and the kernel hands out the lowest free number (SP102; F3-01).D4

How a file system lays out a disk

A storage device is a block device: it reads and writes whole blocks by number (HW205, F1-49 and F1-50).D1 A simple Unix-style file system, like xv6's, divides the device into regions: a superblock describing the layout, a log (for crash safety, later), the inodes, a bitmap with one bit per data block saying "in use", and the data blocks.D2 An inode lists its data blocks: a few direct block numbers, then an indirect block that holds more block numbers for larger files.D1 D2

The university's toy file system (Listing 2) keeps the same parts in memory, at a scale you can print: 16 blocks of 16 bytes, 8 inodes with 4 direct blocks each, a bitmap, and directories. One simplification: its directories are kept in a separate list instead of in data blocks; a real file system stores directory entries in the directory's data blocks, like any file's content.

Path lookup

To open /home/notes.txt, the kernel starts at the root directory, whose inode number is fixed (0 in the toy; 1 in xv6).D2 It reads the root's entries and finds home → inode 1, reads inode 1's entries and finds notes.txt → inode 2. The toy printed exactly this walk, and Figure 1 draws it.R3 Each step also checks permissions (may this process search this directory?), and every step reads disk unless the blocks are cached, which is why the kernel caches directory entries and inodes in memory.D1 Once found, open creates an open-file object pointing to the inode, with the current offset, and returns a descriptor for it; later read and write calls never look at the name again.

One write is several updates

Appending one block to a file changes three things on disk: the bitmap (block taken), the data block (the new bytes), and the inode (new block pointer, new size). A disk writes blocks one at a time, so a crash can land between any two. Look at what each partial state means.D1

  • Only the bitmap: a block is marked used but nobody points to it. It is lost space, a leak, harmless and easy to find. The toy's first run crashed exactly there, and its fsck found "block 1 marked used but no inode points to it (leaked)", while the file kept its old content.R3
  • Bitmap and data, not the inode: the same leak; the new data is lost, but nothing lies.
  • Bitmap and inode, not the data: the inode points to a block whose content is whatever was there before, possibly a deleted file's data. Nothing disagrees: the bitmap says used, the inode uses it. A checker finds no problem, and the user reads garbage or someone else's secrets.

The rule that follows: write the thing that is pointed to before the pointer, and allocate before you point. With that order, a crash leaves at worst a leak, which a checker can repair. The forensic lab replays both orders.R4 R5

Layer 3 — the engineer's depth

Careful ordering is not enough on its own. Some operations cannot be ordered safely. rename between directories must remove one entry and add another; with any order, a crash in between leaves the file with two names or none. Ordering also needs the disk to keep the order, and devices with write caches may reorder writes unless the kernel asks for a flush or a forced-unit-access write.D1

Journaling makes updates atomic. The file system first writes all the blocks of an operation (bitmap, inode, directory, and in some modes data) to a log region, then a commit record, waits for them to reach the device, and only then writes the blocks to their home locations. After a crash, recovery replays every committed transaction from the log and ignores an uncommitted one. An operation therefore happens completely or not at all.D1 xv6 has such a log: its file-system system calls wrap their updates in a transaction, and its recovery runs at boot.D2 Many journaling file systems log only metadata by default and write data blocks before committing the metadata that points to them, the same "pointee before pointer" rule.D1

Copy-on-write file systems never overwrite a live block: they write new versions elsewhere and switch one root pointer at the end, so the switch is the atomic step.D1

The page cache and fsync. write returns when the data is in the kernel's memory cache, not when it is on the device. The kernel writes it back later. A program that must survive a crash (a database, a log of a robot's flight) calls fsync on the file, and for a new file also on its directory, so that the name is durable too.D1 D4 A common safe-update pattern: write a temporary file, fsync it, rename it over the old name (rename is atomic for the name on POSIX file systems), then fsync the directory.D4

Locks again. Directory and inode updates from two processes race exactly like F3-05's: the kernel locks inodes during changes, and operations that touch two (such as rename) need an order. F3-05's frozen machine was this situation.

How the hardware actually does it

The kernel's block layer turns file-system requests into commands to the device driver: "read 8 sectors at logical block address N into this memory". An NVMe SSD (F1-50) receives such commands through submission queues in memory, moves the data by DMA, and reports completion through a completion queue and an interrupt.D1 The device's unit of atomic write is a sector (512 bytes or 4 KiB, see sector and LBA); a write of several sectors may be cut part-way by power loss unless the device guarantees more.D1 Flash devices do not overwrite in place at all: their controller writes new data to fresh pages and remaps them, which is one more layer of translation below the file system (F1-49).D1 To make ordering real, the kernel sends a cache-flush command or marks a write as forced-unit-access, and waits for its completion before writing the blocks that depend on it.D1

Untested on hardware

No storage device was tested in this build: the Linux runs used whatever file system the cloud build container provides (not identified), and the crash runs are a model. This chapter gives no device timings and makes no claim about the power-loss behaviour of any real SSD or disk.

Worked example

In the toy file system, after tinyfs.in's first three commands, where are the bytes of /home/notes.txt, and what happens to the counts if we also run crashwrite /home/notes.txt Room-14:art data-first 1?

  1. mkdir /home: the root (inode 0) gets the entry home; the first free inode is 1. Output "directory inode 1".
  2. create /home/notes.txt: lookup of /home gives inode 1; the next free inode is 2; inode 1 gets the entry notes.txt → 2.
  3. write with the default order (data first, all three steps): block 0 is the first free block; the data goes into block 0; inode 2 gets block[0] = 0 and size 13 ("Room-12:maths" has 13 characters).
  4. Lookup /home/notes.txt: inode 0 → home → inode 1 → notes.txt → inode 2 (Figure 1). The bytes are in block 0.
  5. crashwrite … data-first 1: step 1 marks block 1 used; the crash comes before the data and before the inode change.
  6. Prediction for fsck: block 1 is used, no inode refers to it: one leak. Prediction for cat: inode 2 is unchanged, so the file still reads "Room-12:maths" (13 bytes).
  7. Compare with the run: both predictions match the output.R3

Where the analogy breaks


    

  1. A power cut does not stop a librarian's hands. A person who loses the light still remembers what she was doing. A computer loses everything in memory; only what reached the device survives, and the device may have written blocks in a different order from the one requested (the registered "where it breaks": a file system must survive a power cut in the middle of shelving).S2
    2. 

  2. Thrown-away books leave the shelf. A deleted file's blocks keep their contents until they are reused; the file system only marks them free. That is why stale data can reappear (forensic lab).
    3. 

  3. The catalogue is itself on the shelves. Inodes, directories and bitmaps are blocks on the same device, read and written like data, and cached in memory like data.D1
    4. 

  4. A borrowing slip keeps a book alive without a title. In a library a book with no catalogue entry is lost; a file with no name lives as long as a process has it open (Listing 1).
    5.

  3. Three: the root (to find a), a (to find b), b (to find c); then c's inode is read. More if blocks are not cached or directories span several blocks.
