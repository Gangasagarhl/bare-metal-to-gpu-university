Story hook

Analogy

It is eight o'clock and the school is filling up. Thirty classes need rooms, but there are only twelve rooms with a board. Four teachers can each teach only one class at a time. The science lab, the library and the one printer are wanted by everybody at once. And yet, by nine, every class is somewhere sensible, every teacher knows where to go, and nobody is fighting over the printer.

That calm is not luck. Mrs Okafor, the principal, and her timetable decide who gets which room and when. Students may not walk into the staff room or open the printer's back panel; when they need something, they ask at the office window with a form, and the office does it for them. When two classes want the same room, the office settles it.

A computer has the same problem: many programs, a few processor cores, one memory, one disk, a handful of devices. The program that plays principal is the operating system. This course is about how it keeps the peace.

What you will be able to do

  • Explain what an operating system does, with the school analogy and with the precise terms kernel, process, user mode, kernel mode and system call.
  • Name the three big jobs of an operating system (sharing the processor and memory, coordinating things that happen at the same time, keeping data safe on storage) and the course chapter that treats each.
  • Observe a real program's system calls with strace and sort them into "setting up the process" and "doing the program's work".
  • Diagnose a program that seems frozen by finding the system call it is blocked in.
  • Say where the school analogy stops being true.
Jargon box
Operating system (OS)
Simple words: the program that shares the computer fairly between all the other programs and does the risky jobs for them. Analogy: the school principal and the timetable. Precise: the software that manages a computer's hardware resources (processor time, memory, storage, devices) and provides programs with abstractions of them (processes, address spaces, files) and a controlled interface to them (system calls). D1 D2
Kernel (operating system)
Simple words: the part of the operating system that runs with full power over the machine. Analogy: the principal's office and its staff. Precise: the part of the OS that executes in the processor's privileged mode, handles every system call, exception and interrupt, and owns the page tables, the scheduler and the device drivers. Not the same as a GPU kernel (the function every GPU thread runs, F6). D2 D3
User mode and kernel mode
Simple words: two levels of permission the processor itself enforces: ordinary programs run with few permissions, the kernel with all of them. Analogy: student areas and staff-only rooms. Precise: processor privilege levels; code in user mode cannot execute privileged instructions or touch memory and devices it has not been granted, and enters the kernel only through traps (system calls, exceptions, interrupts). The names differ by architecture (x86 rings, RISC-V U/S/M modes, Arm exception levels). D1 D5
Process
Simple words: a program while it is running, with its own memory and its own number. Analogy: a class with its own room. Precise: the OS's abstraction of a running program: an address space, one or more threads of execution, and kernel-held state such as open files and a process identifier (PID). F3-02 treats it in depth. D1 D3
System call
Simple words: a request from a program to the kernel, such as "write these bytes" or "give me more memory". Analogy: asking at the office window with a form. Precise: a controlled entry into the kernel: the program places a call number and arguments in agreed registers and executes a trap instruction; the kernel checks the request, performs it in kernel mode and returns a result (or an error number) to user mode. F3-07 treats it in depth. D1 D3
strace
Simple words: a tool that prints every system call a program makes. Analogy: a notebook kept at the office window, listing every form handed in and the answer given. Precise: a Linux diagnostic utility that uses the kernel's process-tracing interface to stop a traced process at each system-call entry and exit and print the call, its decoded arguments and its return value (or error name). D6 R2

Layer 1 — the kid explanation

A computer has a few processor cores, one memory, one disk and some devices. Dozens of programs want them at the same moment. Without a referee, a program could take the processor forever, scribble over another program's memory, or send half a picture to the printer while another program sends half a letter.

The operating system is the referee and the helper at once. It runs each program as a process, a class with its own room: the process gets its own memory, and it gets the processor for a while, then another process gets a turn, like classes taking turns with a teacher. The timetable is changed so quickly that every class feels it has a teacher all the time.D1

Programs are not allowed to touch the hardware themselves. The processor has two kinds of rooms: student areas, where programs run, and staff-only rooms, where the operating system's kernel runs. When a program wants something done (print a line, read a file, get more memory), it hands a form through the office window: a system call. The kernel checks the form, does the job, and hands back the answer.D1 D2

In this chapter's lab you will read the office window's notebook for a real program. Printing one line of text takes the program one form. Getting ready to run took it about thirty more.

Layer 2 — the student explanation

Three jobs

The textbook this course follows organises an operating system around three ideas.D1 Virtualization: the OS turns one processor into the illusion of many (each process seems to have its own CPU) and one physical memory into many private address spaces. Concurrency: many things happen at once (several cores, interrupts from devices, several threads in one program), and the OS must coordinate them without corrupting its own data. Persistence: data must survive the program and the power being switched off, which is the job of the file system. OS201 follows that order: F3-02 to F3-04 are virtualization, F3-05 is concurrency, F3-06 is persistence, and F3-07 and F3-08 look at the interface and at a whole small kernel.

The kernel and the rest

The kernel is the part of the OS that runs in the processor's privileged mode. It is the only code allowed to change page tables, program devices, mask interrupts or switch from one process to another.D2 Everything else (the shell, the C library, the compiler, your programs) runs in user mode. An operating system as a product is more than its kernel, but in this course "the OS" mostly means the kernel.

How much belongs inside the kernel is a design decision. A monolithic kernel keeps the file system, drivers and scheduler in kernel mode together; a microkernel keeps only a small core there and runs services such as file systems as user-mode processes that talk by messages. xv6, the teaching kernel this course's labs are built around, is monolithic.D2 D7

A program asks; it does not take

Listing 1 (ask_os.cpp, in the code walk-through) asks the OS five questions: its own process identifier, its parent's, how many CPUs are online, the page size, and the kernel's name and release. On this build's machine the answers were 4 CPUs, 4096-byte pages and a Linux kernel whose release string is 6.18.44-fc-v80.R1 The program could not have found any of this by looking at the hardware: it can see only its own memory. Each answer came from the kernel, through a system call or through data the kernel placed in the process for the C library to read.D3 D4

Watching the office window

strace runs a program and prints each system call as it happens: name, arguments, and the result after the =.D6 The trace of the one-line hello.cpp (Listing 2, plain build) starts with execve, the call that replaced the shell's child process with this program; then come calls that open and map the C library into memory (openat, read, mmap, close), a few that prepare the process (arch_prctl, set_tid_address, mprotect, brk), and only near the end the program's own work: write(1, "Hello from a process!\n", 22) = 22. The last call is exit_group(0), which never returns.R2 Loading shared libraries before main runs is the dynamic loader's job (SP301 treats it); the kernel provides the calls it uses.D3

Two of those calls failed, and that is normal. access("/etc/ld.so.preload", R_OK) = -1 ENOENT means "that file does not exist", which the loader was only checking; ioctl(1, TCGETS, …) = -1 ENOTTY means "standard output is not a terminal", which the C library uses to choose how to buffer output.R2 A system call that returns an error is an answer, not a crash. The program decides what the answer means.

Waiting is a system call too

Some requests cannot be answered at once. A read from the keyboard, from a pipe or from the network may have nothing to return yet. The kernel then blocks the process: it stops running it, gives the CPU to another process, and wakes it when data arrives.D1 To the user, a blocked program looks frozen. The forensic lab of this chapter is exactly that case, and strace shows which call the process is waiting in.

Layer 3 — the engineer's depth

Limited direct execution. The OS wants programs to run at full speed on the real CPU, not inside an interpreter, but without losing control. The textbook's name for the solution is limited direct execution: the kernel starts the program directly on the CPU in user mode, and gets control back in exactly three ways: the program makes a system call (a trap it asked for), the program causes an exception (a divide by zero, a page fault, an illegal instruction), or a device raises an interrupt, in particular a timer interrupt that the kernel programmed before handing over the CPU.D1 The timer is what makes the principal's timetable enforceable: even a program stuck in an endless loop is interrupted, and the scheduler may run something else (F3-03).D1

The system-call interface is the OS's contract. On Linux, programs reach it through the C library, which wraps each call in a function (write, getpid), puts the call number and arguments in the registers the architecture's convention specifies, and executes the trap instruction.D4 On this build's x86-64 machine the installed kernel header gives write the number 1 and getpid the number 39.L1 Numbers and conventions differ between architectures and kernels; the idea does not. F3-07 performs the whole sequence by hand, and in F3-07 and F3-08 you will see the kernel's side in the university's own small RISC-V kernel running in QEMU.

Abstractions the OS provides. Hardware offers cores, physical memory, disk blocks and device registers. The OS turns them into processes and threads (F3-02, F3-03), address spaces (F3-04), files and directories (F3-06), and pipes and sockets. Each abstraction hides details, adds protection (one process cannot read another's memory or a file it has no permission for) and lets the OS share the resource.D1 D3 The cost of the abstraction is the boundary crossing: every system call is a trip from user mode to kernel mode and back, which is why the C library buffers output and why the hello program printed its line with one write.

Not verified — check before relying on this

That glibc's sysconf(_SC_NPROCESSORS_ONLN) obtains its answer by reading a file under /sys or /proc, and that getpid is not cached by the C library on this version, were not checked in the glibc sources or manual (Listing 1's trace was not recorded; F3-07's trace shows two getpid calls for two calls in the program, which is consistent with "not cached"). Check the GNU C Library manual and source for the installed version before teaching either detail.

How the hardware actually does it

The two modes are a property of the processor, not a rule the OS asks programs to obey. The processor keeps the current privilege level in a register that user-mode code cannot change; privileged instructions executed in user mode raise an exception instead of running; and the memory-management unit checks every access against permissions that only kernel-mode code can set.D5 On RISC-V, the processor of this course's QEMU labs, the levels are called machine mode (M), supervisor mode (S) and user mode (U); a trap instruction named ecall moves from user mode into a more privileged mode at an address the kernel registered earlier.D5 On x86-64 (this build's host), the same roles are played by privilege rings and the syscall instruction, documented in the Intel and AMD manuals that Track B reads.S1 HW202 (F1-23) introduced instruction sets; F3-07 and F3-08 run the RISC-V mechanism for real.

Worked example

Question: how much of the hello program's conversation with the kernel was about printing the line? Read the summary that strace -c printed (lab run R3, in the lab section) together with the full trace (R2).

  1. The summary's last line counts 35 calls that returned, with 2 errors. The full trace has one more line: exit_group(0) = ?, which never returns and so is not in the table.R2 R3
  2. The program's own source has one output statement (std::puts), and the trace has exactly one write, of 22 bytes: the 21 characters of the message plus the newline that puts adds.R2
  3. So 1 of 36 calls did the program's visible work, 1 ended it, and 34 prepared the process (loading and protecting libraries, setting up the heap and thread data). The proportion depends on what the program does: a program that prints a million lines will spend most calls on write.
  4. Check: execve appears once, at the top, and returned 0. That is the moment the shell's child process became this program (F3-02 explains the pair fork and execve).

Where the analogy breaks


    

  1. The principal is not a separate person. The OS is software, and it runs on the same CPU cores it manages. When a process runs, the kernel is not running at all on that core; it gets control back only through a trap, an exception or an interrupt (Layer 3). A principal can walk into any room at any time; the kernel cannot "watch" a running program.D1
    2. 

  2. The office window is not a polite request. A student can ignore the rule and open the staff-room door. A process cannot: the CPU switches privilege level only through the trap instruction, and any attempt to use a privileged instruction or a protected address raises an exception that the kernel handles (often by ending the process). F3-07's lab shows the uni-rv kernel killing a program that touched a device directly.D5
    3. 

  3. The timetable is not fixed in advance. A school timetable is printed for the term; the scheduler decides continuously, many times per second, using what processes did a moment ago (F3-03).S2
    4.

Transition box

Where you came from: SP201 showed a program's memory as numbered boxes, with a stack and a heap (F2-18 to F2-20); HW202 showed the instructions a core executes and that a chip has several cores (F1-23, F1-30). What carries over: everything a program does is still instructions on a core and loads and stores to memory; the stack, heap and pointers of SP201 are exactly what a process's address space contains.D3 What changes: the program is no longer alone: the addresses it uses are private to it and not physical, it may be stopped at any moment and resumed later, and anything outside its memory (output, files, time, other programs) is reached only by asking the kernel through system calls, which can fail or block.D1 What comes next: F3-02 looks at the process itself: how the kernel creates one with fork, gives it a new program with exec, and collects its exit status with wait.

Summary


    

  • An operating system shares the processor, memory, storage and devices between programs, and gives them abstractions: processes, address spaces, files.
    • 

  • Its three big jobs in this course: virtualization (F3-02 to F3-04), concurrency (F3-05) and persistence (F3-06).
    • 

  • The kernel runs in the processor's privileged mode; programs run in user mode and enter the kernel only through system calls, exceptions and interrupts.
    • 

  • A timer interrupt lets the kernel take the CPU back from any program.
    • 

  • strace shows every system call: the hello program made one write for its line and about thirty calls to get started.
    • 

  • A system call can fail (an error number) or block (the process waits); a blocked process looks frozen.
