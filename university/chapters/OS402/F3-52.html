Story hook

A small school cannot employ a teacher for every subject. The music teacher visits on Tuesdays, and the same music teacher visits four other schools in the week. When she arrives, the school must give her a room, tell her which classes she has, and show her where things are in this building. She brings her own lesson plans; the school brings the rooms. One rule surprises new staff: if this school already has its own choir leader, the school's choir leader takes the choir, even when the visiting music teacher's plan says "choir: me".

Each pupil also has a personal pencil case, the same model for everyone, but each one's own. When the visiting teacher hands out her worksheets, every pupil must get a separate copy, even if forty pupils arrive at the same moment.

Shared libraries are visiting teachers, the dynamic linker is the secretary who settles them in, and thread-local storage is the personal pencil case. This chapter makes your OS able to host visitors.

What you will be able to do

  • Explain what the kernel does for a dynamically linked program (PT_INTERP, the auxiliary vector) and what the dynamic linker does after that.
  • Read the dynamic section, symbol table and program headers of an executable and a shared object with readelf and nm.
  • Predict which definition a symbol reference binds to, including interposition by the executable, and control it with visibility.
  • Describe how thread-local variables are found through the thread pointer, in the executable and in a dlopened library, and what your kernel must save per thread.
  • Run the three U2 acceptance tests on the host and design them for your OS.
Jargon box
Shared object
Simple words: a library file that many programs use at the same time, loaded when they run. Analogy: the visiting teacher. Precise: an ELF file of type ET_DYN with a dynamic section, built from position-independent code, mapped into each process that needs it by the dynamic linker. D1
Dynamic linker
Simple words: the program that loads a program's libraries and connects the names. Analogy: the school secretary who settles a visitor in. Precise: the interpreter named in the executable's PT_INTERP program header; the kernel maps it with the program and starts it first; it maps the needed shared objects, applies relocations, runs initialisers and jumps to the program's entry. D1 R2
PT_INTERP
Simple words: a line in the program file that says "start this helper first". Analogy: "report to the secretary" written on the visitor's badge. Precise: a program header holding the path of the program interpreter; this build's executables request /lib64/ld-linux-x86-64.so.2. D1 R2
Auxiliary vector
Simple words: a short list of facts the kernel hands to a new program. Analogy: the note the office gives a visitor: room numbers, timetable, where the staff room is. Precise: key–value pairs placed by exec on the initial stack after the environment, such as AT_PHDR, AT_PHNUM, AT_ENTRY, AT_BASE, AT_PAGESZ, AT_RANDOM. D2 R1
Relocation
Simple words: a note "fill in this address once you know it". Analogy: blank spaces in the visitor's plan: "room ___". Precise: an entry telling the linker or dynamic linker to patch a location with a value computed from a symbol's address or the load address; the types are defined per architecture in the psABI. D2
GOT and PLT
Simple words: a table of addresses and a set of jump stubs, so code itself never needs patching. Analogy: a notice board in the corridor; plans say "see board, line 7". Precise: the global offset table holds addresses filled in by the dynamic linker; procedure linkage table stubs jump through it to functions in other objects, possibly resolving them on first call (lazy binding). D1 D2
Symbol interposition
Simple words: when two files define the same name, the earlier one in the search order wins everywhere. Analogy: the school's own choir leader takes the choir. Precise: the default rule of the System V gABI's symbol lookup: a reference to a default-visibility global symbol binds to the first definition in the lookup scope, which begins with the executable. D1 R2
Symbol visibility
Simple words: a label saying whether a name may be used from outside its library. Analogy: "staff only" on a lesson plan. Precise: the ELF st_other field (default, protected, hidden, internal); hidden symbols are not exported into the dynamic symbol table and cannot be interposed. D1 D3
Thread-local storage (TLS)
Simple words: a variable with a separate copy for every thread. Analogy: each pupil's own pencil case. Precise: variables declared thread_local (C++) or _Thread_local (C), placed in an ELF PT_TLS template that the runtime copies into a block for each thread, reached through the thread pointer. D3 R4
Thread pointer
Simple words: a register that points at the current thread's own data. Analogy: the pupil's name tag that says where her pencil case is. Precise: FS base on x86-64, TPIDR_EL0 on AArch64, tp on RISC-V (as the curriculum lists); set by the kernel or by the thread library through the kernel for every thread. C1 D3
TLS access model
Simple words: the recipe the compiler uses to find a thread-local variable. Analogy: "third shelf in your own case" versus "ask the secretary where the visitor's worksheets are". Precise: four models (general dynamic, local dynamic, initial exec, local exec) trading generality for speed; R4 shows local exec in the executable (a fixed offset from FS) and general dynamic in the shared object (a call to __tls_get_addr). D3 R4
dlopen
Simple words: loading a library while the program is already running. Analogy: calling in a substitute teacher in the middle of the day. Precise: the POSIX interfaces dlopen, dlsym, dlclose and dlerror; the object is mapped, relocated and initialised on demand and may be unloaded. D4

Layer 1 — the kid explanation

Analogy

A shared library is a visiting teacher; the dynamic linker is the secretary who gives her rooms and a class list each morning. If the school has its own teacher with the same job, the school's own teacher is used: that is interposition. Thread-local storage is each pupil's own pencil case: the same model for everybody, with separate contents. Mapping: visiting teacher = shared object; secretary = dynamic linker; the note on the visitor's badge = PT_INTERP; the office's welcome note = auxiliary vector; the school's own choir leader winning = interposition; "staff only" = hidden visibility; pencil case = TLS block; name tag = thread pointer.

The kernel only opens the school gate and hands over the welcome note. Settling in the visitors is the secretary's job, and the secretary is a normal program.

Layer 2 — the student explanation

U2's goal is short: "Position-independent executables and shared libraries load through a dynamic linker; TLS works in executables and libraries; dlopen works." C1 You have two choices for the dynamic linker: the one that comes with your C library (the curriculum notes that musl and mlibc include one) or your own, as a learning exercise. C1 Either way, the kernel's part is smaller than you might expect, and the user-space part larger.

What the kernel does

The curriculum lists four kernel duties: file-backed mmap and mprotect; exec honouring PT_INTERP; an auxiliary vector with the program-header address, entry point, interpreter base, page size and random bytes; and per-thread TLS registers. C1 Listing 1 asks the host kernel for exactly those auxiliary-vector entries and checks them against what the dynamic linker reports: the program headers, the entry point (the address of _start) and the interpreter's load address all match. R1 Those three checks are a good first test for your own exec.

What the dynamic linker does

Listing 2 builds the U2 library chain: main_ab needs libb.so, which needs liba.so. The program prints 42 (40 from liba.so plus 2 in libb.so). R2 readelf shows how the dynamic linker knew what to do: the executable asks for the interpreter /lib64/ld-linux-x86-64.so.2; its dynamic section lists NEEDED libb.so and NEEDED libc.so.6 and a RUNPATH of $ORIGIN (search next to the executable); libb.so lists NEEDED liba.so. R2 The executable does not mention liba.so in its dynamic section even though the link command named it: -la was not needed by the executable directly, and this toolchain dropped it (the observed list has two entries).

Interposition

Both liba.so and the executable define who(). When libb.so calls who(), it reaches the executable's version: "libb.so's call to who() reached: the executable". R2 The dynamic linker's own debug trace confirms the three bindings: answer from the program to libb.so, base_value from libb.so to liba.so, and who from libb.so to main_ab. R2 This is the gABI rule U2 asks you to reproduce: "a symbol defined in the executable wins". C1 D1

Thread-local storage

Listing 3 gives both the executable and a dlopened plugin a thread_local variable. Eight threads each write their own values (100+t and 200+t), sleep so the others can write too, and read back: every thread sees its own values, and the main thread, which never wrote, sees 0 in both. R3 Then the program loads and unloads the plugin 50,000 times in five batches and watches the C library's heap statistics: after the first batch they stay exactly flat. R3 Those are U2's second and third acceptance tests in host form.

Layer 3 — the engineer's depth

exec with an interpreter

For a static program your exec maps the PT_LOAD segments and jumps to e_entry (B13). With PT_INTERP present, it also opens the named file, maps that file's PT_LOAD segments at an address of its choosing, and starts the interpreter at the interpreter's entry point; the program's own entry is passed in AT_ENTRY. D1 D2 For a position-independent executable (type ET_DYN, "Flags: NOW PIE" in R2) the kernel also chooses the program's base, so AT_PHDR is the only way the dynamic linker learns where the program's headers are. R2 R1 shows different addresses every run on the host (address-space layout randomisation) but the "matches" lines are always "yes": a test that compares relations rather than values is the right shape for your OS too. R1

The initial-stack layout (argument count, argument pointers, a null, environment pointers, a null, auxiliary-vector pairs ending in AT_NULL) is part of the psABI's process-initialisation section, and therefore part of the ABI you fixed in F3-50. D2 If you took the Linux-compatible path, keeping the same keys and layout lets an unmodified dynamic linker start; on your own path, your C library's start-up code reads whatever you defined.

The exact rules for where a kernel places a PIE program and its interpreter, and which auxiliary-vector entries beyond the five that U2 names are needed by glibc's or musl's dynamic linker (for example hardware-capability or system-information entries), were not checked in this build. Read the psABI's process-initialisation section (D2) and your C library's start-up and dynamic-linker sources before freezing your list.

Mapping a shared object

The dynamic linker maps each object by calling mmap on the file once per PT_LOAD segment, with the segment's permissions, and uses anonymous memory for the part of a writable segment beyond the file's contents (the zero-filled .bss). D1 After relocation it may call mprotect to make the relocated part read-only again ("RELRO"). Your kernel therefore needs file-backed private mappings with copy-on-write (one physical copy of a library's code shared by all processes, private copies of the pages a process writes), and mprotect that changes permissions on part of a mapping. C1 If your VM in OS303 only supports anonymous memory, this is the first piece of U2 to build.

Relocations, GOT and PLT

Position-independent code reaches its own data relative to the instruction pointer and reaches other objects' data and functions through the GOT. The dynamic linker fills GOT entries using relocation records whose types the psABI defines (on x86-64, for example, relative relocations for addresses inside the same object, and GOT and jump-slot relocations for symbols). D2 Function calls to other objects go through PLT stubs. With lazy binding, the first call through a stub enters the dynamic linker to resolve the symbol; with immediate binding, everything is resolved before _start. R2's executable carries FLAGS BIND_NOW and FLAGS_1 NOW PIE, so this toolchain asked for immediate binding by default. R2 For a first dynamic linker of your own, immediate binding is the simpler design: no resolver trampoline, and every missing symbol is reported at start-up.

Not verified — check before relying on this

Relocation type names and numbers (for example R_X86_64_RELATIVE, R_X86_64_GLOB_DAT, R_X86_64_JUMP_SLOT and their AArch64 and RISC-V counterparts) were not read from the psABIs in this build. Take them from the psABI documents (D2) or from /usr/include/elf.h of your build host, not from this chapter.

Symbol lookup and why interposition exists

The gABI's default lookup searches the "global scope": the executable first, then its needed objects in breadth-first load order. D1 A reference from inside a library to a default-visibility global function therefore goes through the GOT too, so that a definition earlier in the scope can take over. That makes things like replacing malloc with a debugging allocator possible, and it is why R2 shows libb.so reaching the executable's who. R2 For the executable's who to be found at all, it must be in the executable's dynamic symbol table: R2's readelf --dyn-syms lists it, because the link exported it for the library that references it. R2

The cost of interposition is that every library-internal name is public by default. Drepper's "How To Write Shared Libraries" recommends hiding everything that is not API: smaller dynamic symbol tables, faster start-up, no surprise interposition. D3 The forensic lab of this chapter is a real case of that surprise; its fix, -fvisibility=hidden with the API marked as default, takes a library's dynamic symbol list from three names to two in R5. R5

How TLS is laid out

Each object with thread-local variables has a PT_TLS program header describing a template: initialised data and a size. R4 shows memsz 0x000004 for both the plugin and main_tls: one int each. R4 For every thread, the runtime allocates a block for each module's template and copies the initial values in. Drepper's paper defines two layouts: in "variant II", used on x86-64, the static TLS blocks lie just below the address held in the thread pointer and the thread control block starts at it. D3 R4's disassembly is consistent with that: every access to exe_slot in main_tls is a single instruction on %fs:0xfffffffffffffffc, that is, 4 bytes below the thread pointer. R4 AArch64 and RISC-V use the other layout ("variant I"), with the blocks above the thread pointer. D3

The executable's variables can use such fixed offsets because the executable's block is placed at link time (the local-exec model). A library loaded by dlopen cannot: its block is created later and can be anywhere. So the compiler emits the general-dynamic sequence: R4 shows plugin_get computing an argument from the GOT and calling __tls_get_addr, which uses the per-thread dynamic thread vector (DTV) to find or allocate the plugin's block for the calling thread. R4 D3 Between the two sit initial exec (libraries loaded at start-up, offset taken from the GOT) and local dynamic (several variables of one module, one call). D3

Note

The data16 and rex.W prefixes in R4's plugin_get are padding that makes the general-dynamic sequence a fixed length, so the linker can rewrite it into a faster model when it can prove that is allowed. D3 (Drepper's TLS paper describes these "linker relaxations"; pending verification.)

The thread pointer is kernel state

Whatever layout, everything hangs off one register per thread. On x86-64 user code cannot set FS base with an ordinary instruction in every configuration, so the kernel provides a call (on Linux, arch_prctl; with the FSGSBASE feature enabled, user code may also write it directly). D5 On AArch64, TPIDR_EL0 is writable from user mode; on RISC-V, tp is an ordinary register. C1 In all three cases, the kernel must save and restore it on every context switch, and the thread-creation call must let the new thread start with its own value (on Linux, a TLS argument to clone). D5 Forgetting to save FS base on a switch produces exactly the bug U2's eight-thread test is designed to catch: threads see each other's values.

Not verified — check before relying on this

The Linux interfaces named here (arch_prctl(ARCH_SET_FS), the CLONE_SETTLS flag of clone, and when user-mode WRFSBASE is allowed) were not checked in this build, and no man pages are installed. Check arch_prctl(2) and clone(2) (D5) and the Intel manual's FSGSBASE description before relying on them.

dlopen, dlclose and the 10,000-cycle test

dlopen runs the same machinery as start-up, but later: map, relocate (now also against already-loaded objects), allocate TLS (lazily, per thread, through the DTV) and run initialisers. dlclose reverses it when the reference count drops to zero: run finalisers, unmap, free the DTV slot and the per-thread blocks. D4 Every missed free shows up in U2's third test, "dlopen, dlsym and dlclose of a plugin library work 10,000 times in a loop with memory statistics returning to baseline". C1

"Returning to baseline" needs care. During development of Listing 3, a plain before-and-after comparison failed on glibc: the heap grew by a few kilobytes during the first cycles and then never again. A second attempt then reported a small leak that was caused by the test itself: the vector holding the measurements reallocated while it grew. The final design reserves the vector first, measures after each batch of 10,000 cycles, and passes when the last three batches leave the heap exactly where it was. R3 In R3 the heap grew once during batch 1 and then stayed flat for 40,000 cycles. Write down this definition of "baseline" in your U2 report: a one-time growth (caches, a first DTV allocation) is not a leak, a steady growth per cycle is.

Writing your own dynamic linker

If you write one, the smallest useful version: relocate yourself without calling any function that needs relocation; read AT_PHDR and AT_BASE; map DT_NEEDED objects breadth first; build one symbol lookup over the global scope (start with a linear search, then the ELF hash tables); apply relative, GOT and jump-slot relocations with immediate binding; set up the initial thread's static TLS and the thread pointer; run DT_INIT_ARRAY functions in dependency order; jump to AT_ENTRY. Then add dlopen and the DTV. D1 D3 F3-53 adds one more duty: the interface that lets the unwinder find each loaded object's unwind tables.

How the hardware actually does it

Three hardware features carry this chapter. First, the MMU's per-page permissions and the page tables your VM builds: shared code is the same physical pages mapped into many processes, read-only and executable; writable data pages are private copies created on the first write (copy-on-write, OS303). C1 Second, PC-relative addressing: x86-64's RIP-relative operands, as in R4's lea 0x2e78(%rip), let code reach its GOT without any absolute address, which is what makes the code pages shareable. R4 Third, the thread-pointer register: on x86-64 a segment base (FS) added to an offset by the address-generation hardware, so %fs:-4 costs no more than an ordinary memory access; on AArch64 a system register read into a general register first; on RISC-V the general register tp. D3 C1

Not verified — check before relying on this

Untested on hardware in this build: the TLS code sequences were inspected on x86-64 only; AArch64 and RISC-V sequences and the variant I layout were not compiled or run here. Check them with the cross compilers (aarch64-linux-gnu-g++ -S, riscv64-linux-gnu-g++ -S) and the psABIs (D2) when you port U2 to those architectures.

Where the analogy breaks


    

  • One visitor, many schools at the same instant. A teacher is in one school at a time; a shared library's code pages are in every process at once, and only its writable pages are copied. D1
    • 

  • The choir rule is applied by name only. A school would notice that "choir" means something different to its own teacher; the dynamic linker binds by name and nothing else, which is how R5's library got the wrong validate. R5
    • 

  • Pencil cases are created lazily. Pupils get their case on the first day; a dlopened library's TLS block for a thread may be allocated only when that thread first touches it. D3
    • 

  • The secretary is herself a visitor. The dynamic linker is an ordinary shared object that has to relocate itself before it can do anything, which no school secretary must do.
    •

Forensic lab answer key


Observation. Total 3 = 1 + 1 + 1, which is what the application's own validate returns for three non-zero fields. Both libstats.so and app_stats export validate (forensic_syms).


Root cause. libstats.so's internal helper validate has default visibility, so it is exported and its call from stats_add goes through the dynamic linker. Lookup starts with the executable, which also exports a function named validate (a form-field check, returning 1 or 0). The library's call binds to the executable's function: symbol interposition, exactly as the gABI rule in this chapter and in R2 describes.


Why the unit tests pass. The library's tests link no other validate, so the library's own definition is the only one in scope.


How the evidence was produced. Both files built by run.sh lines 55–59 with default options; no fault was injected beyond the name clash in the sources.


Fix and verification. Build the library with -fvisibility=hidden (the API is already marked with STATS_API), or make validate static. Verification, from R5's fixed build: "stats_total() … = 12 (expected 12)" and the library exports only stats_add and stats_total.


Wrong answers and why. "Integer overflow": the values are tiny. "The dynamic linker is broken": glibc's linker follows the documented rule; the same happens with any conforming dynamic linker. "Rename the application's function": it works here but leaves every other internal name of the library open to the same accident.
