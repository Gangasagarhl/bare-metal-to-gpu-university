Story hook

Every school office has a window where students hand in forms: a form to borrow a laptop, a form to change a timetable, a form to report a lost key. The students may not enter the office; they push a form through the window and wait for the slip that comes back. The forms are numbered, every box on them has a fixed meaning, and the reply slip says either "done, here is your laptop number" or "refused, reason 9".

Now the principal is opening a new school. She can print her own catalogue of forms, with her own numbers and her own boxes. Or she can copy the catalogue of the big school across town, so that the thousands of students who already know those forms can move in tomorrow and use the window without learning anything new. Her own catalogue lets her design every form properly. The copied one brings students. Once the first students fill in a form, she can never quietly change what box 3 means.

Your operating system is at the same moment. It has processes, system calls and a small C library from OS304. Before it grows a real C library, shared libraries, a C++ runtime and a compiler, you must decide what its window looks like: the system-call ABI. This chapter is about making that decision on purpose, writing it down, and testing it.

What you will be able to do

  • List everything a system-call ABI fixes: the entry instruction and registers, the numbers, the argument and structure layouts, the error convention and the process-start contract.
  • Make a system call three ways (C-library wrapper, syscall(), the bare instruction) and explain the two error conventions you observe.
  • Compare the conventions of x86-64, AArch64 and RISC-V from real binaries and real runs.
  • Evaluate the two legitimate paths (your own system calls with a C-library port, or a Linux-compatible layer) for your OS, and record the decision in a design note.
  • Diagnose a compatibility layer that reports errors with the wrong sign, from a log and a kernel trace.
Jargon box
ABI (application binary interface)
Simple words: the rules that let two pieces of already-compiled code work together. Analogy: the exact layout of every form at the office window. Precise: the machine-level contract between separately compiled components: calling convention, data type sizes and alignment, structure layouts, object-file format and, for an operating system, how programs request kernel services and how processes start. D2 D6
System-call ABI
Simple words: the exact way a program asks the kernel for something. Analogy: the office's form catalogue: form numbers, boxes, reply slips. Precise: the instruction used to enter the kernel, the register that carries the call number, the registers that carry arguments and the result, the numbering of calls, the layout of structures passed through memory, and the error convention. D6 R2
System-call number
Simple words: the number that says which service you want. Analogy: the form number. Precise: an integer placed in an agreed register before the trap instruction; the kernel uses it to index its dispatch table. On Linux the numbers differ per architecture (write is 1 on x86-64 and 64 on AArch64 and RISC-V in this build's headers). L1 L2
Trap instruction
Simple words: the special instruction that hands control to the kernel. Analogy: pushing the form through the window. Precise: syscall on x86-64, svc on AArch64, ecall on RISC-V; each raises the privilege level and jumps to an entry point the kernel configured. D3 D4 D5 R2
errno
Simple words: the C library's variable that holds the reason for the last failure. Analogy: the refusal reason written on the reply slip, copied into your notebook. Precise: an integer lvalue defined by the C standard and POSIX; functions that fail set it to a positive error number such as EBADF; it is per thread in POSIX. D1
Error convention
Simple words: how a kernel says "no" and why. Analogy: the refusal slip's format. Precise: the rule for encoding failure in the result; Linux returns minus the error number in the result register, which the C library turns into −1 and errno (observed in R1). R1 L3
ENOSYS
Simple words: the answer "there is no such service". Analogy: "we do not have a form with that number". Precise: the error a Linux kernel returns, as −ENOSYS, for a system-call number it does not implement; the header comment asks real system calls not to return it, so callers can tell "missing" from "failed". L3 R1
Compatibility layer
Simple words: code in your kernel that understands another system's requests. Analogy: accepting the other school's forms at your window. Precise: a second dispatch path that accepts another operating system's call numbers, arguments and conventions and maps them onto the kernel's own services. C1
vDSO
Simple words: a little piece of kernel-provided code that runs inside your program, so some questions need no trip to the kernel. Analogy: a clock on the corridor wall: you read it without going to the window. Precise: on Linux, a small shared object the kernel maps into every process, used by the C library for calls such as clock_gettime without a trap (R5 counted zero traps for 1,000 calls). D6 R5
Design note (decision record)
Simple words: a short document that says what you decided and why. Analogy: the principal's letter explaining which form catalogue the school uses. Precise: in this university, a dated note with the decision, the context, the options considered, the consequences and the conditions under which it should be revisited; the curriculum asks for one on the system-call ABI before U1. Layer 1 — the kid explanation

Analogy

The office window (the system call) only works because everybody agrees on the forms. Form numbers are system-call numbers; the boxes on a form are the registers; the reply slip is the result. A refusal slip says "no" plus a reason number, and your notebook where you copy the reason is errno. Copying another school's catalogue is the Linux-compatible path; printing your own is path 1. Mapping: window = trap instruction; form number = call number; boxes = argument registers; reply slip = result register; refusal reason = error number.

A program never walks into the kernel. It fills in the boxes and pushes the form through. If the school ever changes what box 3 means, every student who learned the old form gets the wrong laptop. That is why this decision is made early, written down, and then kept.

Layer 2 — the student explanation

In OS303 you added system calls to your kernel (B12), and in OS304 a small C library called them (B18). C1 Those calls already form an ABI, perhaps an accidental one. This chapter makes it deliberate. A system-call ABI fixes six things.

  1. Entry. Which instruction enters the kernel and which registers carry the number, the arguments and the result. On Linux x86-64, the program puts the number in rax and the first arguments in rdi, rsi, rdx and r10, executes syscall, and reads the result from rax; Listing 1 does exactly this and it works. R1 D2 AArch64 uses x8 and svc #0; RISC-V uses a7 and ecall (Figure 2). R2
  2. Numbers. Which number means which service. The numbers are part of the binary contract: they are compiled into every program. L1
  3. Argument types and structures. The size of each argument, and the exact layout of every structure passed through memory (a stat result, a signal action, a time value). Changing a field's size breaks every program compiled against the old layout. D2
  4. Errors. How failure is reported. Linux returns minus the error number in the result register; the run of Listing 1 shows -9 for a closed descriptor and -38 for an unknown call number, while the C library's write() and syscall() return −1 and set errno to 9 and 38. R1 POSIX defines only the second form: the library function returns −1 and sets errno. D1
  5. Process start. What the stack holds when a program begins (argument count, argument pointers, environment, auxiliary vector) and which registers are set. Listing 2 reads argc from the first word of the initial stack on three architectures. R2 D2 F3-52 adds the auxiliary vector.
  6. Signals and threads. How a signal handler is entered and returns, and how a new thread gets its stack and thread pointer. F3-51 and F3-52 return to these.

The C library sits on top of all six. It hides the trap instruction inside small wrapper functions, converts the error convention into errno, and offers the portable interface that POSIX describes. D1 That is why a C library port has a well-defined "system-dependent layer": everything below it is your ABI, everything above it is portable. C1 D7

The two legitimate paths

The curriculum states the choice plainly: (1) your own system calls, with a C library port (it names mlibc and newlib as designed for this); (2) a Linux-compatible system-call layer, so that musl and even unmodified static Linux binaries run on your OS. Path 2 gives a large software base quickly but ties your design to Linux semantics; a middle road is possible. C1 The library statements are the curriculum's and must be confirmed in each library's own porting documentation. D7

Listing 3 models both paths inside one ordinary program, so you can watch the conversion happen. The model kernel answers with a pair {value, error}; path 2 converts that pair into Linux's single minus-errno value; a C-library wrapper converts that into −1 and errno. R6

Layer 3 — the engineer's depth

The analogy for this layer is the principal's letter: before the first student arrives, she writes down which forms exist, what every box means, and what she promises never to change. Here is what goes into that letter for an operating system, and the trade-offs behind each line.

Numbering: stable, never reused, extendable

A call number is compiled into every binary that uses it, so it must never change meaning. Two consequences follow. First, a retired call keeps its number and returns the "no such call" error forever, so that old programs fail cleanly. Second, a new behaviour gets a new number rather than a changed old one. The Linux headers in this build show the result of that policy: the x86-64 table still has open (2) and fork (57), while the newer generic table used by AArch64 and RISC-V has neither and offers only openat (56) and clone (220). L1 L2 A Linux-compatible layer therefore needs one table per architecture, and the dynamic C library on x86-64 already uses openat, not open, as the strace in R3 shows. R3

The header that defines the error numbers states the rule for the "missing" answer in so many words: "arch syscall entry code will return -ENOSYS if users try to call a syscall that doesn't exist", and real system calls "should refrain from returning -ENOSYS". L3 That rule makes probing possible. R4 makes the kernel's answer to clone3 look like ENOSYS; the C library then calls the older clone and the program's thread still runs. R4 Your kernel should give unimplemented calls exactly this answer, so that a ported C library can fall back the same way.

The error convention

A single result register can carry both value and error only if the two ranges cannot overlap. Linux's minus-errno convention relies on the fact that legitimate results of most calls are non-negative or are addresses outside a small negative range; the C library treats a specific range of negative values as errors. D6 Your own ABI may choose differently, for example a second result register or a flag, at the price of every library wrapper knowing it. Whatever you choose, document it in the design note and test it at both ends: the kernel's raw answer and the library's errno.

Not verified — check before relying on this

The exact range of negative return values that Linux C libraries treat as errors (and therefore the largest error number the kernel may return) is not stated in any document opened in this build. Check the syscall(2) and errno(3) manual pages and the C library's own system-call wrapper source for the version you port, and record the range in your design note.

Types and structures

Arguments travel in registers, but many calls pass pointers to structures. Their layout is part of the ABI: field order, sizes, padding, alignment, and the width of types such as time_t and off_t. D2 On path 2 you must reproduce Linux's layouts for each architecture exactly; on path 1 you define them once in a kernel header that the C library port includes. Choose 64-bit file offsets and 64-bit time from the start; widening them later means new call numbers and new structure versions.

Entry and exit: what the instruction costs you

The trap instruction defines which registers the kernel may destroy. Listing 1 must tell the compiler that syscall overwrites rcx and r11 (line 22); the reason is that the instruction saves the return address and the flags in those two registers. D3 On AArch64 and RISC-V the hardware saves this state in system registers instead, so Listing 2 lists no extra clobbers there and still runs correctly under QEMU. R2 D4 D5 Your kernel's entry code must save and restore everything else, and must check every pointer argument before using it (B12). C1

Calls that do not trap

Some services are asked for so often that a trap per request is wasteful. Linux maps a small shared object, the vDSO, into every process; the C library calls clock_gettime through it. R5 asked for the time 1,000 times and strace saw zero clock_gettime system calls. R5 D6 On path 2 a statically linked Linux program will still work without a vDSO if its C library falls back to the real system call; whether it does is a property of that library and version, so test it. A vDSO is an optimisation for later, not part of the first ABI.

Making the decision

Weigh the paths against your goals, not against fashion.

A middle road is common in practice: an own native ABI plus a compatibility layer added later for a set of programs. C1 If you take it, give the two paths separate entry points or separate number ranges, so that the kernel never has to guess which catalogue a form came from.

How the hardware actually does it

The trap instruction is a controlled jump to a higher privilege level. On x86-64, syscall loads the instruction pointer from a model-specific register that your kernel programmed in B12 and switches to ring 0; it saves the old instruction pointer in rcx and the flags in r11, which is why Listing 1 declares both as clobbered. D3 On AArch64, svc raises a synchronous exception taken to EL1; the exception syndrome register records that it was a supervisor call, and the return address is saved in an exception link register. D4 On RISC-V, ecall raises an environment-call exception that, with delegation set up, is taken in supervisor mode; the return address goes to sepc. D5 In all three, no register is changed by the hardware except those the documents name, so the choice of argument and result registers is a software convention: it is your ABI, and Figure 2 shows the one Linux chose on each architecture. R2

Note

The RISC-V start code in Listing 2 also loads the global pointer register gp, because the linker may turn some addresses into offsets from it. That is part of the process-start contract for RISC-V programs, not of the system call. D5 R2

Where the analogy breaks


    

  • The window is not polite. A form at a school window is a request a person reads. A trap instruction switches the CPU's privilege level and jumps to code the kernel chose; nothing "reads" the form except your entry code, which must check every box, especially pointers, because a malicious program fills them in on purpose. D3 C1
    • 

  • A form has one catalogue; an ABI has one per architecture. The same Linux call has different numbers on x86-64 and AArch64, and some calls exist on one and not the other (open and fork exist only in the x86-64 table opened here). L1 L2
    • 

  • Not every question goes through the window. The vDSO lets a program answer some questions without trapping at all (R5), which no form system has. R5
    • 

  • The reply slip has two formats. The kernel's reply (minus the error number) and the library's reply (−1 and errno) are different conventions for the same answer; the analogy has only one slip. R1

Summary


    

  • A system-call ABI fixes entry instruction and registers, numbers, argument and structure layouts, errors, process start, and signal and thread entry.
    • 

  • Linux returns minus the error number; the C library turns that into −1 and errno (R1).
    • 

  • Conventions differ per architecture: syscall/rax, svc #0/x8, ecall/a7, and different numbers (R2, L1, L2).
    • 

  • Numbers are never reused; unknown numbers answer −ENOSYS, which lets libraries probe and fall back (L3, R4).
    • 

  • Path 1 (own ABI and a ported library) buys design freedom; path 2 (Linux-compatible) buys software; a middle road is possible (C1).
    • 

  • Record the decision in a design note before U1 and test both ends of every convention.
    •

Forensic lab answer key


Observation. The kernel trace shows every write failed: {value 0, error 9} (EBADF, descriptor 5 not open). The logger reports "short write, 9 of 8 bytes" and similar; 9 is larger than the request, which is impossible for a correct write. No byte reached any file.


Root cause. The compat-v2 layer returns the error number with the wrong sign: return r.error != 0 ? r.error : r.value; instead of minus the error (compare Listing 3 line 59). The wrapper treats only negative results as errors, so +9 looked like 9 bytes written and errno was never set.


How the fault was injected. forensic_logger.cpp contains the layer with the sign removed; nothing else differs from Listing 3's logic.


Fix and verification. Return -static_cast<long>(r.error); rerun: the logger prints "write failed: Bad file descriptor" three times. Test: a conformance probe (the mini-project) that writes to a closed descriptor and checks both the raw result (−9) and the library result (−1, errno 9).


Wrong answers and why. "The logger opened the wrong descriptor": true but secondary; the bug is that the failure was reported as success. "The kernel's write is broken": the trace shows the kernel answered correctly. "Short writes are normal": a write can return fewer bytes than asked, never more.
