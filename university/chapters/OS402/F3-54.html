Story hook

For years the school used textbooks printed for another school: the maps showed the wrong town, the timetable examples used the other school's bell times, and teachers corrected every copy by hand. This year the school orders its own edition. The printer needs three things: the school's name on the order form (the printer's form has a list of known schools, and this one is not on it yet), the school's own pictures and timetables to print from, and a list of books in the right order, because the workbook refers to pages of the reader, which must be printed first.

Two weeks later a teacher compares two copies of the same workbook from the two print runs. They differ. Not in the lessons, but in a line on the first page that nobody looks at.

That is this chapter: a toolchain that knows your OS by name, a sysroot to build against, a ports tree that builds programs in the right order, and the discipline that makes two builds of the same thing identical.

What you will be able to do

  • Explain what a target triple is and which parts of GCC, Binutils, LLVM and build systems must learn your OS's name.
  • Build a sysroot and a compiler wrapper that produce programs for your OS with no host headers or libraries leaking in, and prove the absence of leaks.
  • Recognise the "driver trap": a compiler that accepts an unknown triple but falls back to host behaviour at link time.
  • Design a ports tree: recipes, dependencies, build order in waves, error reporting for missing dependencies and cycles.
  • Make packages reproducible and diagnose a non-reproducible one.
Jargon box
Target triple
Simple words: a short name that says "this CPU, this vendor, this operating system". Analogy: the school's name on the printer's order form. Precise: a string such as x86_64-pc-linux-gnu (architecture, vendor, OS, optionally environment); GNU config's config.sub turns short forms into canonical ones, and LLVM parses triples into fields. D1 R1
OS-specific toolchain
Simple words: a compiler, assembler and linker that know your OS by name. Analogy: the printer who has your school on its list. Precise: GCC with Binutils, or Clang with LLD, patched so the triple <arch>-<yourOS> selects your start files, libraries, search paths, predefined macros and defaults. C1 D2
Sysroot
Simple words: a folder that looks like the root of your OS, holding its headers and libraries. Analogy: the school's own pictures and timetables, sent to the printer. Precise: a directory tree the compiler and linker treat as the target's root for header and library search (usr/include, usr/lib), so nothing from the build host is used. C1 R3
Compiler driver
Simple words: the gcc or clang command itself, which runs the compiler, assembler and linker for you. Analogy: the print-shop clerk who sends the order to each machine. Precise: the program that turns one command line into a sequence of tool invocations, choosing start files, libraries and linker options per target; in Clang, chosen through per-OS "toolchain" classes. D2 R2
Ports tree
Simple words: a collection of recipes, one per program, that say how to build it for your OS. Analogy: the print room's order list with "print after" notes. Precise: per package: source location and checksum, patches, dependencies, configure/build/install steps into a staging folder, and packaging; examples named by the curriculum are SerenityOS's Ports, managarm's bootstrap recipes driven by xbstrap, and NetBSD's pkgsrc. C1
Build order (topological order)
Simple words: an order in which every recipe comes after the recipes it needs. Analogy: print the reader before the workbook. Precise: a topological sort of the dependency graph; grouping into "waves" of recipes whose dependencies are all in earlier waves shows what may build in parallel; a cycle makes an order impossible. R4
Reproducible build
Simple words: building the same sources twice gives exactly the same bytes. Analogy: two print runs of the same workbook are indistinguishable. Precise: byte-identical outputs from the same sources, toolchain and recipe, independent of time, user, folder and machine; U4 asks for byte-identical packages on a second machine "or the differences are explained". C1 R5
SOURCE_DATE_EPOCH
Simple words: an agreed "build time" that tools use instead of the clock. Analogy: the edition date printed in the book instead of the day it went through the press. Precise: an environment variable holding a Unix time; in this build Clang used it for __DATE__ and __TIME__ (R6). R6 D5

Analogy

The school orders its own textbooks. If the printer does not know your school, it prints the other school's maps by default. That mistake is quiet: the books look fine until a pupil follows a map.

Layer 2 — the student explanation

U4's goal: "Your OS has its own target triple (for example x86_64 followed by your OS's name); a ports system builds third-party software for it from recipes." C1 Until now you built programs for your OS with a generic cross compiler and long command lines (B-track and F3-51 to F3-53). That works for your own code. It does not work for the thousands of programs whose build systems ask "what system am I building for?" and expect a real answer.

The triple, and who reads it

R1 shows the first wall. GNU config.sub, the script almost every autotools package ships, canonicalises x86_64-linux-gnu, aarch64-linux and riscv64-elf, but rejects x86_64-myos: "Invalid configuration `x86_64-myos': OS `myos' not recognized". R1 Adding myos* to the list of known operating systems in a copy (one line, the same list that already holds other systems) makes it return x86_64-pc-myos, aarch64-unknown-myos and riscv64-unknown-myos. R1 Every autotools package you port carries its own copy of config.sub, so your ports tree must either patch each copy or replace it with your patched one; the long-term fix is to get the name accepted by the GNU config project. D1

Clang is more permissive: it accepts x86_64-unknown-myos unchanged. R2 But accepting is not knowing: for the myos triple Clang predefines 375 macros against 389 for Linux, and the only OS-related one left is __ELF__. __linux__, __unix__ and __gnu_linux__ are gone, and nothing says "myos". R2 A real port adds the OS to LLVM's triple parser and a predefined macro to Clang; the lab's wrapper adds -D__myos__=1 by hand. D2

The driver trap

The quieter problem is the link step. Asked to compile and link hello_myos.c for x86_64-unknown-myos, Clang's driver plans to link by calling /usr/bin/gcc -m64: the host's GCC, with the host's start files and C library. R2 For an OS it has no toolchain class for, the driver falls back to a generic one that delegates linking to GCC. Nothing fails; you get a program linked against the wrong system. This is the "printer prints the other school's maps by default" of the hook, and the reason the curriculum lists "Clang's driver toolchain classes" among the documents for this component. C1

Not verified — check before relying on this

The explanation of why Clang delegates to gcc (a generic GCC-based toolchain chosen for unknown operating systems) is inferred from the observed command line, not read from Clang's sources or documentation in this build. Check Clang's driver documentation and the toolchain classes in its source (D2) before writing your own.

A sysroot and a wrapper

R3 The first program it builds checks for contamination itself: it prints "built for myos: __myos__ is defined" and "__linux__ is not defined: no host contamination". R3 It runs on the Linux build host because this teaching port took F3-50's path 2: its C library uses the Linux-compatible system-call numbers (1 for write, 60 for exit). On your OS with its own ABI, the same program runs only inside your OS.

Layer 3 — the engineer's depth

Teaching GCC and Binutils your OS

The curriculum points to the OSDev wiki pages "OS Specific Toolchain" and "Hosted GCC Cross-Compiler", the GCC Internals manual (target configuration and the config.gcc mechanism), the Binutils documentation (BFD targets and linker emulations) and GNU config. C1 The shape of the work, as those documents describe it: config.sub accepts the name; Binutils' configure maps your triple to an existing object format (ELF for your architecture) and a linker emulation with your default linker script and library paths; GCC's config.gcc maps the triple to target header fragments that define your OS's predefined macros, start files (crt0.o, crti.o, crtbegin.o and their end counterparts), default libraries and specs; libgcc and libstdc++ get configured for the target. D3 D4 The result is a x86_64-myos-gcc that needs no wrapper and passes the right options to every tool by itself.

Not verified — check before relying on this

No GCC or Binutils was patched or built in this build; the file names (config.gcc, target header fragments), start-file names and configure options above are given from the documents' titles and general knowledge, not from opened sources. Follow the OSDev wiki pages and the GCC Internals manual (D3, D4) for the exact files and macros; check every name against the GCC and Binutils versions you port.

Teaching LLVM your OS

For Clang the work is similar in structure: add the OS to the triple's operating-system field, predefine your macro, and write a driver toolchain class that names the linker (LLD), the start files, the library search paths under the sysroot and the default libraries. D2 R2's "/usr/bin/gcc" line is what you are replacing. Clang can already take --sysroot and target options, so one compiler binary can serve the host and every target; GCC is built once per target.

What belongs in the sysroot

The sysroot holds what a program for your OS links against: the C library's headers and the kernel's user-visible headers (system-call numbers, ioctl structures, the ABI of F3-50), start files, the C library (static and shared), the dynamic linker (F3-52), libgcc or compiler-rt, the C++ runtime (F3-53). Your ports tree installs each package into a staging folder and then into the sysroot, so later recipes find earlier ones. R3's tree is the minimum: usr/include/{stddef,stdio,stdlib,string,unistd}.h, usr/lib/crt0.o, usr/lib/libc.a. R3 Note that its program's ELF header says "OS/ABI: UNIX - System V", like most Linux programs: ELF files usually do not name their OS, so your kernel recognises its programs by convention (and by the interpreter path and ABI notes if you use them), not by that byte. R3

Proving the absence of host contamination

Host leaks are the most common toolchain bug: a header from /usr/include found before your sysroot's, or a host library linked in. Defences: compile with -nostdinc and the sysroot only; link with explicit paths; put a canary in every test program (R3's #if defined(__linux__) line); and inspect the result (readelf -d shows no host NEEDED; readelf -l shows only expected program headers: R3 lists PHDR LOAD LOAD GNU_STACK, a static program). R3 In a ports tree, run the canary check after every recipe, not once.

What a recipe contains

A recipe needs: name and version; source location and a checksum of the downloaded archive; patches (your config.sub, OS-specific code); dependencies, split into build-time tools that run on the host and target libraries that link into the package; configure, build and install commands with the triple, sysroot and a staging prefix; and the test command that U4's second acceptance test asks for. C1 Build systems need their own adapters: autotools through --host=<triple> and your config.sub, CMake through a toolchain file (and a platform file for your OS name), Meson through a cross file. C1 The Linux From Scratch book is the curriculum's model of building a whole system in order. D6

Not verified — check before relying on this

The recipe formats and commands of SerenityOS's Ports, xbstrap and pkgsrc, and the exact CMake and Meson cross-file syntax, were not read in this build. Read each project's documentation (D6) before copying a format.

Build order, errors and parallelism

Listing 3 does three things a real ports system must also do. It refuses missing dependencies instead of building around them (a recipe that silently skips a dependency builds a different package). It propagates "blocked" to everything that depends on a broken recipe. And it detects cycles: if a round finds no recipe whose dependencies are all built, the remaining ones form or depend on a cycle. R4 Its waves are a topological order with parallelism made visible: wave 3 has five independent recipes that could build at once. Real trees break cycles by splitting a package into a minimal "stage 1" build and a full one; you will meet the same idea in F3-55's compiler stages.

Reproducibility

U4's first acceptance test asks for "byte-identical package contents" from a clean checkout on a second machine, "or the differences are explained". C1 R5 shows what stands in the way, even on one machine. Two builds, two seconds apart, with plain tar: both packages differ. With deterministic archive options (sorted names, owner and group 0, a fixed modification time) the hello package becomes identical; the banner package still differs. R5 The archive was one source of variation (timestamps and owners in the tar headers); the program itself is the other, which the forensic lab investigates. The general sources of non-reproducibility are a short list: time (file dates, embedded dates), ordering (directory order, hash-table order), paths (build folders embedded in debug information or strings), users and hosts, locale, and randomness. D5 Each has a standard countermeasure, and your recipes should apply them by default: SOURCE_DATE_EPOCH, sorted inputs, path-prefix mapping options, fixed owners, a fixed locale.

Note

The hashes in R5 and the forensic evidence differ on every run of the lab (they contain the build time); the identical/different verdicts do not. Read the verdicts, not the digits.

How the hardware actually does it

A toolchain is pure software, but it encodes hardware facts that must match your kernel exactly: the instruction set and its optional extensions (a compiler targeting x86-64 with AVX2 by default produces programs your kernel must enable the extension for, and that fault on CPUs without it); the calling convention and stack alignment of the psABI (F3-50); the page size assumed by the linker's segment alignment (R3's program places .rodata at 0x200120 and .text at 0x201160, on different 4 KiB pages, so they can have different permissions); and the code model (how far code and data may be apart). R3 D7 Choose these defaults in your target description deliberately, write them in the design note, and keep the kernel's view (which extensions it enables, which page size it uses) in step.

Not verified — check before relying on this

Untested on hardware: no program built by the myos toolchain ran inside a myos kernel or on real hardware in this build; hello_myos ran on the Linux build host through the Linux-compatible ABI. The default instruction-set level and page-size handling of GCC and LLD for a new triple were not checked (D3, D7).

Worked example

Task. A recipe for a small autotools program fails on myos. Walk through the four places it can fail and what R1–R3 tell you about each.

  1. configure stops with "OS `myos' not recognized". The package's own config.sub is unpatched (R1). Fix in the recipe: replace it with your patched copy before running configure. R1
  2. configure runs, but detects "Linux" features. Host headers leaked in, or a test program was run on the host. Check that the compiler sees only the sysroot (R3's canary) and that configure knows it is cross-compiling (--host given). R3
  3. Compilation fails in an #ifdef __linux__ … #else #error unsupported OS block. The package needs a port: add a __myos__ branch (your predefined macro, R2) or use its POSIX branch if it has one. R2
  4. The link succeeds, the program crashes at start on myos. The driver linked host start files and libraries: the driver trap (R2). Check the link command with -v or -###; fix the driver or use your wrapper. R2

Check. Each failure is caught by a different check: configure output, the canary, the compiler error, and the link command. A ports system that runs all four checks for every recipe finds these problems at build time, not on the target.

Where the analogy breaks


    

  • The printer rejects an unknown school; the compiler may not. config.sub refuses myos loudly, but Clang accepts it and quietly links for the host (R2). Loud failures are the easy ones. R1 R2
    • 

  • A book does not print its own print date unless told to. Programs embed build dates through ordinary language features (__DATE__), so a build tool cannot fix every case from outside. R6
    • 

  • "Print after" lists are short; dependency graphs are not. Real trees have hundreds of recipes, optional dependencies and build-time tools that run on the host, which a school's print list never has.

Transition box

Where you came from: F3-51 to F3-53 gave you a C library, a dynamic linker and a C++ runtime, built by hand with a generic cross compiler. What carries over: every library becomes a sysroot component and a recipe; the system-call ABI becomes the sysroot's kernel headers. What changes: your OS gets a name that tools recognise; builds are driven by recipes, in an order, from a clean checkout; outputs must be reproducible. R1 R5 What comes next: F3-55 moves the toolchain itself into your OS: the compiler, built by this toolchain, runs inside your OS and rebuilds the system (U5).

Summary


    

  • Your OS needs a name in the triple; config.sub rejects unknown names (R1), Clang accepts them but knows nothing about them (R2).

  • A sysroot plus a canary program proves that no host headers or libraries leaked in (R3).

  • A ports tree is a dependency graph: report missing dependencies and cycles, build in waves (R4).

Forensic lab answer key


Observation. The tar listings are identical (same size, owner, date: the deterministic options worked). cmp reports a few dozen differing bytes, all within a short range of offsets; with the section table, they lie in .rodata (file offset 0x120, size 0x37) and, in the run shown, also in .text (starting at 0x160). The strings diff shows the only differing text: two different "build: … " lines, with times two seconds apart. (Byte counts and offsets vary between runs of the lab; the conclusion does not.)


Root cause. banner.c line 7 embeds __DATE__ and __TIME__, the time of compilation, into the program. Each build compiles at a different time, so the strings differ, and so does every byte that depends on their position or contents. The archive tool is not to blame.


How the evidence was produced. run.sh built both packages twice, two seconds apart, with deterministic tar options (lines 75–79), and collected the evidence (lines 84–97). No fault was injected; the macro use is as upstream wrote it.


Fix and verification. Set SOURCE_DATE_EPOCH for every recipe; Clang used it for __DATE__ and __TIME__ in this build. Verification (R6): both packages identical, and the banner prints "build: Nov 14 2023 22:13:20", the fixed epoch 1700000000. Alternative: patch the recipe to use the package version instead of a time.




Wrong answers and why. "tar is non-deterministic": the listings are identical and hello-1.0.tar is identical. "The compiler is non-deterministic": hello is byte-identical from the same compiler. "Build both on the same second": the second machine in U4 runs at another time; a one-machine test that passes by luck hides the problem (question 5).
