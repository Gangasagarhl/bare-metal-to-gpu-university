Story hook

For its first years, every teacher at the new school was trained somewhere else. The school could teach pupils, but it could not make teachers. The day it becomes a real school is the day one of its own former pupils, trained in its own teacher course, teaches a class there. The day it becomes an independent school is later: when the teachers it trained run the teacher course itself, and the teachers trained that way teach exactly as well as the ones trained before.

The inspector has a neat test for that last step. She takes a teacher trained by the outside college and a teacher trained by the school's own graduates, gives both the same lesson plan, and compares the lessons word for word. If they match, the school's course reproduces itself faithfully.

An operating system is self-hosting when its own compiler, running inside it, can rebuild it. This chapter is about getting there, and about how the comparison test proves you did.

What you will be able to do

  • Name the five levels of self-hosting and what each one tests in your kernel.
  • Explain build, host and target for a compiler, and the difference between a cross compiler, a native compiler and a "Canadian cross".
  • Explain a three-stage bootstrap with stage comparison and why the comparison is meaningful.
  • Measure what a compile asks of an operating system: processes, system calls, files, memory, time.
  • Diagnose a compiler failure inside your OS that is really a missing system call.
Jargon box
Self-hosting
Simple words: a system that can rebuild itself with tools running on itself. Analogy: a school that trains its own teachers. Precise: in the curriculum, U5: "The compiler runs inside your OS and the system can rebuild itself", graded in five levels from a native "hello" to a compiler that rebuilds itself. C1
Build, host and target
Simple words: where a compiler is built, where it runs, and what it makes programs for. Analogy: where the teacher was trained, where she teaches, and which pupils she teaches. Precise: the three system types of GNU configure: --build (the machine doing the build), --host (the machine the result runs on), --target (for compilers: the machine the result generates code for). D1 R3
Native compiler
Simple words: a compiler that makes programs for the same system it runs on. Analogy: a teacher teaching at the school where she now works. Precise: host equals target; in U5, host and target are your OS. D1
Canadian cross
Simple words: building, on one machine, a compiler that will run on a second machine. Analogy: the outside college preparing a teacher who will work at your school. Precise: a build where build, host and target are not all equal and build differs from host; the usual way to produce the first native compiler for a new OS: build = Linux, host = target = your OS. D1
Bootstrap (three-stage)
Simple words: building a compiler with itself, twice, and checking the two results are the same. Analogy: the inspector's word-for-word lesson comparison. Precise: GCC's native bootstrap: stage 1 built by the existing compiler, stage 2 built by stage 1, stage 3 built by stage 2; the object files of stages 2 and 3 are compared ("stage comparison"); the curriculum lists it as U5's stretch goal. D1 C1
Stage comparison
Simple words: comparing two builds of the compiler byte for byte. Analogy: comparing two teachers' lessons word for word. Precise: a check that two compiler binaries built from the same sources by functionally equivalent compilers are identical; a difference points to a miscompilation, non-determinism or an environment leak. D1 R1
Compiler driver and passes
Simple words: the g++ command starts several programs one after another. Analogy: the timetable that sends a class from room to room. Precise: in this build, g++ started cc1plus (the C++ compiler proper) and as (the assembler) for one -c compile, communicating through a temporary assembly file. R2

Layer 1 — the kid explanation

Analogy

A self-hosting OS is a school that trains its own teachers. First an outside college trains one teacher who will work at your school (the Canadian cross). She teaches a simple class (level 1), then a hard one (level 2), then re-teaches the school's own staff (levels 3 and 4). Finally she runs the teacher course, and the inspector compares a lesson by a teacher she trained with a lesson by a teacher they trained (stage comparison). Mapping: teacher = compiler; outside college = cross toolchain on Linux; class = program; teacher course = the compiler's own source; word-for-word lesson comparison = comparing stage 2 and stage 3.

The comparison is clever because it does not need a reference answer: if two different generations of teachers give the same lesson, the course transmits itself faithfully.

Layer 2 — the student explanation

U5's goal: "The compiler runs inside your OS and the system can rebuild itself." C1 Its build list: "Native builds of Binutils (or LLD), GCC (or Clang), Make and the utilities; a disk large enough; your kernel's build scripts runnable inside the OS." C1 The curriculum splits the way there into five levels (Figure 2). The course project of OS402 is level 2, with an exact test: "the U3 test program is compiled by the native compiler inside your OS and its output matches the host's". C1

Build, host, target

Every GCC records how it was configured. On this build machine, the native gcc has build, host and target all x86_64-linux-gnu; the two cross compilers have build and host x86_64-linux-gnu and targets aarch64-linux-gnu and riscv64-linux-gnu. R3 F3-54's compiler for your OS is of the second kind. The native compiler you need for U5 is a third kind: build x86_64-linux-gnu, host and target your OS, built on Linux by your cross toolchain. GNU configure supports this three-way case, usually called a Canadian cross. D1 Its output is a set of programs (driver, compiler proper, assembler, linker) that only run inside your OS; you copy them into your disk image with their libraries.

What a compile asks of your OS

R2 traced one ordinary compile on the Linux host: g++ -std=c++20 -O2 -c of the U3 test program from F3-53. The driver started two more programs, cc1plus and as. In total there were about 8,600 system calls of 33 different kinds; more than half were readlink; there were over a thousand openat calls, of which about two thirds failed. R2 The 33 names are a useful checklist for level 2: they include vfork, execve, wait4, pipe2, mmap, mprotect, brk, lseek, pread64, unlink, getcwd, getrusage, prlimit64 and sysinfo. R2 On your OS with your own ABI the names differ, but each one is a service the C library will ask your kernel for.

Listing 2 measures the same compile: about two seconds of wall-clock time, and a peak resident memory of about 185 MiB in the largest process, on this build container. R4 That one translation unit already needs more memory than many early hobby kernels can give a single process. The curriculum's kernel column for self-hosting names exactly this: "Robust memory management under load (a compiler is a stress test), large files, many processes, pipes, timestamps, enough disk space". C1

Levels 3 and 4

Level 3 rebuilds your C library, shell and utilities inside the OS, and the acceptance test asks that "the rebuilt versions pass the U1 tests". C1 This needs Make and a shell that run build scripts unchanged, and correct file timestamps: Make decides what to rebuild by comparing modification times, so a kernel that stores times in seconds and a fast build that writes several files in one second can make Make skip or repeat work. Level 4 rebuilds the kernel inside the OS, installs it to the boot partition, and "the next boot passes the B-track regression suite". C1 Keep the previous kernel bootable: a broken self-built kernel must not leave you without a way back.

Layer 3 — the engineer's depth

Why the three-stage comparison works

GCC's documentation describes a native bootstrap in three stages, with a comparison of stages 2 and 3. D1 Stage 1 is built by whatever compiler you had; it is a new compiler but compiled by an old one, so its machine code reflects the old compiler. Stage 2 is the new compiler compiled by the new compiler (stage 1). Stage 3 is the new compiler compiled by stage 2. If the new compiler is correct and deterministic, stages 1 and 2 are different programs that implement the same translation, so stage 2 and stage 3 are produced by the same translation of the same source: they must be identical. A difference means one of: the new compiler miscompiles itself (stage 1 and stage 2 behave differently), the compiler's output depends on something other than its input (time, addresses, uninitialised memory), or the environment leaked in. D1

Listing 1 shows the core of that reasoning in a few hundred lines. minicc is a tiny compiler from a toy language to x86-64 assembly. Built twice by g++, it gives byte-identical binaries (A and A2): the build is deterministic. Built by clang++ instead, it gives a different binary (B): two different compilers translate the same source differently. Yet A and B, given the same toy program, produce identical 108-line assembly outputs, and that output, assembled and linked with no C library, prints 42, −13, 16 and −4. R1 Different binaries, same translation: that is what stages 1 and 2 are, and why stage 2 and stage 3 must match. (A real bootstrap compares compilers compiled by those compilers; minicc cannot compile itself, so the lab compares their outputs on a test program instead.)

Note

The comparison also guards against a subtler problem: a compiler binary that inserts something into the programs it compiles, including future compilers, without it being in the source. Reasoning about that class of attack, and the "diverse double-compiling" defence that compares builds made by independent compilers, goes beyond this course; the stage comparison is its everyday cousin.

Reading the compile trace

Three things in R2 deserve a closer look before you run a compiler on your OS. R2

  • Failures are normal. About 660 failed openat calls are the compiler searching the include path: each #include is tried in several folders until it is found. Thousands of readlink calls returned EINVAL (not a symbolic link) or ENOENT. Your kernel must return those errors quickly and correctly; a kernel that returns the wrong error (for example EACCES instead of ENOENT) can stop the search early. The forensic lab shows why the kind of error matters.
  • Processes and waiting. The driver used vfork, execve and wait4 to run cc1plus and as, and pipe2. A vfork that behaves like fork is correct but slower; a vfork whose child corrupts the parent's stack is not. (F3-50 discussed fork and vfork in the ABI decision.)
  • Queries about the machine. sysinfo, prlimit64 and getrusage appear: the compiler and driver ask about memory and limits. If your kernel returns zeros or nonsense, a compiler may size its caches or garbage-collection thresholds wrongly.
Not verified — check before relying on this

Why cc1plus calls readlink thousands of times (most likely path canonicalisation of include files) and why GCC calls sysinfo (most likely to size its memory heuristics) are inferences from the trace, not checked in GCC's sources in this build. Check the GCC sources (D1) if your OS's implementation of these calls is slow or incomplete.

Memory under load

A compiler allocates and frees large amounts of memory quickly, maps files, and runs alongside other compilers when Make runs jobs in parallel. Level 2 needs at least: demand paging that does not fail under hundreds of MiB per process; brk and mmap allocators that release memory; reclaiming page cache when memory is tight; and, ideally, a clear "out of memory" outcome (the process gets an error or is ended with a message) rather than a kernel hang. R4's ~185 MiB for one translation unit is a measurement from this machine, not a property of GCC: compile larger files or at higher optimisation and it grows; run Make with several jobs and it multiplies. R4 Size your QEMU guest and your kernel's limits from your own measurements inside your OS.

Files, timestamps and disk

A GCC source tree and build tree hold tens of thousands of files; object files and archives are written with seeks and partial writes (the assembler writes sections at computed offsets, as the forensic lab shows). Your file system needs large files, many directory entries, fast lookup of failed names, correct modification times with enough resolution for Make, rename for atomic replacement, and space. Check the free space before a long build and write the build log to a file you can read after a crash.

Native builds of the toolchain

The native compiler is built first as a Canadian cross on Linux (Figure 1). Later, with your OS self-hosting at level 3, you can build it again natively inside your OS from your ports tree: the same recipes, with build, host and target all your OS. The Linux From Scratch book is the curriculum's model of that ordering: a temporary toolchain, then the final system built with it. D3 C1

How the hardware actually does it

Self-hosting is where hardware limits you notice nowhere else become visible. A compiler is CPU-bound for seconds to hours: timer interrupts and the scheduler (OS304) decide whether your shell stays responsive during a build. It is memory-bound: TLB reach and page-fault cost decide how much time the kernel spends on its behalf (OS303). It writes many files: the block driver and its interrupts (DR301) carry the traffic, and in QEMU, the virtual disk's caching mode decides whether a crash loses the build. On the spare PC, you meet real disk latency and real memory sizes for the first time. C1

Worked example

Task. Plan the course project (level 2) as a sequence of checks, each failing for one identifiable reason.

  1. The native compiler starts. Run the driver with --version inside your OS. Fails on: missing shared libraries (F3-52), a wrong interpreter path, missing system calls at start-up.
  2. Level 1: C hello. Compile and run a C "hello". Fails on: vfork/exec/wait, temporary files in /tmp, the assembler's seeks and writes (see the forensic lab), the linker finding the sysroot's start files (F3-54).
  3. Compile the U3 test program (F3-53, Listing 1) and libthrower.so with the native compiler. Fails on: memory (R4 measured ~185 MiB on the host for this file), the C++ headers in the native sysroot, time limits.
  4. Run it and compare. Copy the output out and cmp it with the host's u3_x86.out (419 bytes). Fails on: the runtime (F3-53), threads (futex), filesystem calls. R2

Check. Each step has one new dependency, so a failure points at one part of your system. That is the same design principle as the curriculum's five levels: never let a level-5 failure be the first sign of a level-1 bug.

Where the analogy breaks


    

  • Teachers differ; compilers must not. Two well-trained teachers never give word-identical lessons; two correct, deterministic compiler stages must give byte-identical output. The comparison is far stricter than any school inspection. D1
    • 

  • Different teachers, same lesson; different binaries, same output. R1's A and B differ as binaries but translate identically. A school has no word for "two different people who are the same teacher". R1
    • 

  • A school does not need its building to train teachers. A compiler inside your OS depends on every part of the OS at once; a kernel bug can look like a compiler bug, as the forensic lab shows.

Forensic lab answer key


Observation. The messages come from the assembler (/tmp/cc<random>.s: Assembler messages, "as: BFD … assertion fail"). The compiler proper finished: it produced the temporary assembly file. The trace shows the same three programs as the good run. Among the failed calls, ENOENT, EINVAL and ENOTTY also appear in a normal compile (include search, readlink on ordinary files, terminal checks on non-terminals). The only ENOSYS failures are two lseek calls in as.


Root cause. The kernel does not implement lseek and answers ENOSYS (F3-50's convention for a missing call). The assembler (through the BFD library) positions the file before writing a section's contents; the failed seek makes the write of the .text section fail, and BFD reports it with the error text of ENOSYS, "Function not implemented". (That BFD seeks before each section write is inferred from the trace and the message, not read in the Binutils sources.) The assertion failures and "No such file or directory" are consequences (the half-written object file was abandoned).


Why -S hid it. With -S the assembler never runs; the compiler proper writes its output sequentially and needs no seek.


How the evidence was produced. On the Linux host, the compile ran under strace -f -e inject=lseek:error=ENOSYS, which makes every lseek fail as it would on a kernel without the call (run.sh line 55). Nothing else was changed.


Fix and verification. Implement lseek (including SEEK_SET, SEEK_CUR, SEEK_END, and seeking beyond the end followed by a write). Verify: the compile produces an object file, the U3 program links and runs. To make the next case easier, the kernel should log every unknown system-call number once with the calling program's name, as F3-50 recommended: this failure would have been one log line.


Wrong answers and why. "Rebuild the compiler with other options": the compiler proper worked; the assembler failed because of the kernel. "The thousands of openat/readlink failures are the problem": they appear identically in the successful run (compile_trace). "Disk full": that would be ENOSPC, not ENOSYS.
