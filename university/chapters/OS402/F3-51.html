Story hook

Amira changes schools in the middle of the year. On her first morning she already knows how to borrow a book, how to report that she is ill, and what happens when the fire bell rings. Nobody taught her the new school's rules: every school in the region follows the same rulebook, and each school prints a small handbook that tells students how to do those things in this building, which window to go to, which form to use.

The rulebook is what makes moving possible. But a rulebook is only useful if each school really follows it. So once a year an inspector comes with a checklist: "A student rings the fire bell while another is waiting at the library desk. Does the librarian stop and does the student get a clear 'interrupted' answer?" A school either passes each check or writes down why it does not offer that service yet.

Programs move between operating systems the same way. The rulebook is POSIX and the C standard; the handbook is your C library; the inspector's checklist is a test suite. In this chapter your library stops being "enough for my shell" and becomes a library that can prove which rules it follows.

What you will be able to do

  • Explain which parts of a C library depend on the kernel and which do not, and where a port's system-dependent layer sits.
  • Write a "supported interfaces" list and a test harness that checks the behaviour POSIX requires of each claimed interface.
  • Run the U1 signal acceptance test (SIGINT from a terminal interrupts a blocked read) and explain EINTR and SA_RESTART.
  • Name the kernel services U1 needs: signals, poll, terminal control, directories, clocks, process creation and waiting.
  • Diagnose duplicated output after fork from a log and explain it with stdio buffering.
Jargon box
POSIX
Simple words: a shared rulebook for Unix-like operating systems. Analogy: the regional rulebook every school follows. Precise: IEEE Std 1003.1, also published as The Open Group Base Specifications; its volumes are Base Definitions, System Interfaces, Shell and Utilities, and Rationale; it specifies the behaviour of C interfaces such as open, read, fork and sigaction. D1 C1
Conforming C library
Simple words: a C library that really does what the rules say, for the parts it claims. Analogy: a school that passes the inspector's checklist. Precise: in this course (milestone U1), a library whose claimed subset of the C standard and POSIX passes recognised test suites, with every excluded test listed with an approved reason. C1
System-dependent layer
Simple words: the small part of a C library that talks to one particular kernel. Analogy: the handbook page that says which window and which form this school uses. Precise: the code a port supplies so the portable library can run on a new kernel: system-call wrappers, start-up code, thread and TLS set-up, and type definitions that follow the system-call ABI. D4 C1
Supported interfaces list
Simple words: the written list of functions your library promises to get right. Analogy: the services the school says it offers. Precise: a document naming each claimed interface, its test coverage and its known deviations; U1 asks for it explicitly. C1
Signal
Simple words: a notice the kernel delivers to a process, interrupting what it is doing. Analogy: the fire bell. Precise: an asynchronous notification identified by a number (for example SIGINT, SIGPIPE); the process may ignore it, take the default action, or run a handler installed with sigaction. D1
EINTR and SA_RESTART
Simple words: "your waiting was interrupted", and the option to keep waiting instead. Analogy: the librarian stops serving you when the bell rings; you can ask her to continue afterwards. Precise: a blocking call interrupted by a caught signal fails with EINTR; if the handler was installed with SA_RESTART, certain calls are restarted instead. The run in this chapter shows both. D1 R2
Controlling terminal
Simple words: the terminal whose Ctrl-C reaches your program. Analogy: the bell wired to your classroom. Precise: a terminal associated with a session; the terminal driver sends signals such as SIGINT, generated from special input characters, to the session's foreground process group. D1 D6
Pseudo-terminal
Simple words: a terminal made of software, with two ends. Analogy: a practice bell that a teacher rings from the staff room. Precise: a pair of devices, master and slave; what is written to the master appears as terminal input on the slave, passing through the same line discipline (including signal characters) as a real terminal. D1 D6
stdio buffering
Simple words: the C library collects output and writes it in larger pieces. Analogy: collecting letters in a tray and taking them to the office once. Precise: a stream is unbuffered, line buffered or fully buffered; standard output is fully buffered when it does not refer to an interactive device, and buffers are flushed by fflush, by exit and when full. D2 R3
Test suite (libc-test, Open POSIX Test Suite)
Simple words: ready-made programs that check a C library. Analogy: the inspector's checklist. Precise: the curriculum names libc-test (associated with musl) and the Open POSIX Test Suite (distributed with the Linux Test Project) as U1's judges. D3 C1

Layer 1 — the kid explanation

Analogy

The rulebook (POSIX and the C standard) says what must happen; the handbook (your C library) says how this school does it; the inspector (the test suite) checks that it really happens. Mapping: rulebook = POSIX and ISO C; handbook = the C library; the handbook page about "which window, which form" = the system-dependent layer; inspector's checklist = libc-test and the Open POSIX Test Suite; the fire bell = a signal; the librarian stopping = EINTR.

A school that says "we follow the rulebook" without an inspection is only hoping. A school that lists what it offers, passes the checks for those things, and writes down honestly what it does not offer yet, can be trusted. That is the difference between "my shell runs" and "my C library conforms to this list".

Layer 2 — the student explanation

B18 ported a C library far enough to run a shell and a few utilities. C1 U1 grows it into a library that passes recognised test suites for the parts you claim. The milestone's build list names the missing system calls you will need: signals, poll, termios, directory operations and time; plus a written supported-interfaces list and the test suites cross-compiled and run under your harness. C1

What "the C library" contains

Two documents define it. The C standard (ISO/IEC 9899) specifies the library every C implementation provides: string handling, formatted I/O through streams, memory allocation, numeric conversion, and a few process functions such as exit. D2 POSIX adds the operating-system interfaces: file descriptors, processes, signals, terminals, directories, threads, clocks. D1 Some functions are pure computation and port unchanged (Figure 1, left). Others are thin wrappers around system calls, and some, like stdio, add a large user-space layer on top of a few calls. C1

The port

The curriculum names four candidate libraries: newlib (ported by implementing a short list of system stubs), musl (complete, but written for the Linux system-call ABI), mlibc (designed for hobby and research systems, with a per-OS "sysdeps" layer) and picolibc; or your own minimal library. C1 Which one fits depends on the path you chose in F3-50. Each library's porting notes are the authority for what its layer must provide. D4

Choosing and writing down the subset

No hobby OS starts with all of POSIX. The honest unit of progress is a written list: interface, source of truth (the POSIX page or C standard clause), tests that cover it, status. The U1 acceptance rule makes the list binding: the chosen test-suite subsets pass, and "every excluded test is listed with a reason the learner approved". C1 Listing 1 is a miniature of that discipline: twelve behaviours, each tied to a rule, and an excluded list with reasons. On the host it passes all twelve. R1

The signal test

The second U1 acceptance test is specific: "SIGINT from the TTY interrupts a blocked read in a child process, the handler runs, and the read returns the interruption error." C1 Listing 2 runs exactly that on the host, using a pseudo-terminal as the TTY: the parent writes the Ctrl-C byte to the master side; the child, blocked in read on the slave side, sees its handler run and read return −1 with errno 4 (EINTR). With SA_RESTART the same Ctrl-C runs the handler but the read keeps waiting, and returns the three bytes typed afterwards. R2 Figure 2 lists the kernel duties behind each line of that output.

Layer 3 — the engineer's depth

The inspector does not check that the school has a handbook; she checks what happens in awkward moments. The same is true of conformance: the hard parts are the interactions between features. This section goes through the ones that U1 exposes.

errno is per thread

POSIX requires errno to be thread-local: each thread sees its own value. D1 In a library this means errno is a macro that expands to something like a function call or a thread-local variable, and therefore your port needs working thread-local storage before it has working threads. F3-52 builds TLS; until then, a single-threaded library may use a plain variable, and the supported-interfaces list says "single-threaded only".

stdio and fork

The C standard lets standard output be fully buffered when it does not refer to an interactive device, and requires exit to flush open streams. D2 POSIX's fork creates a child whose memory is a copy of the parent's, including any data sitting in a stdio buffer, while _exit ends a process without flushing. D1 Put together, a buffered line written before fork can be written twice: once by the child's exit, once by the parent's. The forensic lab of this chapter is a real run of exactly that; R3 shows the same program printing four lines on a terminal and six when its output goes to a file. R3 Your library must reproduce this behaviour, not "fix" it: programs and test suites depend on the documented rules.

Signals: what a handler may do

A handler can run between any two instructions of the interrupted code, so it may only call functions that POSIX lists as async-signal-safe. D1 Listing 2's handler only sets a volatile sig_atomic_t flag, the pattern the C standard allows. D2 In your library this has a consequence: internal locks taken by functions such as malloc or stdio must never be needed by the functions you mark async-signal-safe. Check your list against the POSIX list before you claim it.

Interrupted and restarted calls

When a caught signal interrupts a blocking call, POSIX gives two outcomes: the call fails with EINTR, or, for handlers installed with SA_RESTART, certain calls are restarted. D1 R2 shows both outcomes for read on a terminal. R2 Which calls restart, and which return EINTR regardless, is listed per system; POSIX leaves some of it to the implementation. Your kernel needs one mechanism for both: mark the sleeping call as interruptible, wake it when a signal is pending, run the handler on the way to user mode, and either return EINTR or rewind the user instruction pointer to repeat the trap.

Not verified — check before relying on this

The list of system calls that Linux restarts after an SA_RESTART handler, and those that always fail with EINTR (for example certain timed waits), was not read in this build. Check signal(7) in the Linux man-pages (D6) and the POSIX page for sigaction (D1) before you write your kernel's restart rules, and test each call you claim.

Terminals and sessions

For Ctrl-C to become SIGINT, your kernel needs more than a serial driver. It needs a line discipline that knows the special characters (VINTR among them), a notion of session and controlling terminal, and process groups so that the signal reaches the foreground job. D1 Listing 2's child calls setsid and then opens the slave without O_NOCTTY; on the host that makes the slave its controlling terminal, and the printed settings show ISIG on and VINTR equal to 3 (Ctrl-C). R2 The curriculum's terminal row adds pseudo-terminals (for a terminal emulator and remote shells) and job control as the next steps, and ECMA-48 for the control functions a terminal emulator interprets. Running real test suites under your OS

The U1 build step is "the test suites cross-compiled and run under your harness". C1 In practice that is four pieces of engineering: cross-compiling each test against your sysroot (F3-54 makes this routine); putting the binaries into your OS's file system image; a runner inside the OS that executes each test with a time limit and records its exit status; and a host-side script that copies the results out and compares them with the expected list. Plan the time limit carefully: a test that hangs because a wake-up is missing in your kernel must count as a failure, not stop the whole run.

Read each suite's own documentation (D3) before designing your harness; the curriculum names the suites but is not a source for their details.

How the hardware actually does it

Two hardware mechanisms sit under this chapter. The first is the interrupt that brings a key press in: on a serial console, the UART raises a receive interrupt, your driver reads the byte, and the line discipline decides whether it is data or a special character (DR301's UART chapter and OS304's TTY work). C1 The second is the return to user mode. A signal handler runs because the kernel, before returning from the interrupted system call, rewrites the saved user state: it pushes a signal frame on the user stack holding the interrupted registers, points the instruction pointer at the handler, and arranges for the handler's return to enter the kernel again (a "sigreturn" call), which restores the frame. D6 The layout of that frame is part of your ABI (F3-50): a C library's signal code and a debugger's unwinder both read it.

Note

The pseudo-terminal in R2 has no hardware at all: the parent's write to the master end enters the same line-discipline code path that a UART byte would. That is why it is a faithful test of the kernel logic and an unfaithful test of the serial driver.

Worked example

Task. Read R2's first block line by line and name, for each line, the kernel duty it proves (or would expose as missing on your OS).

  1. child: ISIG is on, VINTR is 3 (Ctrl-C), blocking in read — the terminal has a line discipline with default settings; tcgetattr works on the slave. Missing in your kernel: tcgetattr fails, or ISIG is off by default. R2
  2. parent: typing Ctrl-C (byte 0x03) on the master side — the master accepts writes. Missing: pseudo-terminals.
  3. child: read returned -1, errno 4 (Interrupted system call), handler ran: yes — four duties at once: the byte was recognised as VINTR; SIGINT went to the right process group (the child's new session); the sleeping read was woken; the handler ran before read returned; EINTR (4 in this build's headers) was returned. L1
  4. child exit status 0 -> acceptance test PASS — _exit status reached the parent through waitpid.

Second block, with SA_RESTART: the handler ran, but read returned 3 (the bytes ok and newline typed afterwards). This proves the kernel did not return EINTR but repeated the call. If your kernel ignores SA_RESTART, this block shows −1 and EINTR instead, and the listing exits with a failure.

Check. Count the duties: a terminal with a line discipline, pseudo-terminals, sessions and process groups, interruptible sleep, handler entry and sigreturn, the EINTR versus restart decision, exit status. That is the "signals and terminals" row of the checklist above, and why U1 puts this test next to the test suites.

Where the analogy breaks


    

  • The rulebook leaves gaps on purpose. A school rulebook tries to settle everything; POSIX explicitly leaves some behaviour "implementation-defined" or "unspecified" (for example parts of which calls restart). D1 Conformance means following the rules and documenting your choices in the gaps.
    • 

  • The inspector checks behaviour, not intention. A test suite can pass for the wrong reason (a test that never blocks cannot detect a missing wake-up), and a failure may be the test's fault. Each exclusion needs a reason, not a shrug. C1
    • 

  • The fire bell can ring between two words. A school bell interrupts a lesson at a sentence boundary; a signal can interrupt a program between any two instructions, which is why handlers are restricted to async-signal-safe functions. D1
    • 

  • Copying a pupil copies her notebook. Nothing in a school duplicates a student with her unfinished notes; fork does exactly that with unflushed stdio buffers (R3). R3
    •

Forensic lab answer key


Observation. The file holds six lines, the terminal run four (forensic_compare). Each extra "starting worker pool" is directly followed by a worker's "ready" line; "all workers finished" appears once, so the service started once.


Root cause. Standard output to a file is fully buffered (C standard). "starting worker pool" was still in the buffer when fork copied the process (POSIX). Each child called std::exit, which flushed the copied buffer plus its own line. The parent flushed its own copy at its end. On a terminal the stream is line buffered, so the line had already been written.


How the evidence was produced. forensic_workers.cpp as shown, run once by run_lab.sh with output to a file and once by run.sh under script; no fault was injected: this is the documented behaviour.


Fix and verification. Call std::fflush(stdout) (or fflush(nullptr)) before fork, and end children with _exit unless they own the streams they flush. Verify: the file run shows four lines.


Wrong answers and why. "The service restarts": then "all workers finished" would also repeat. "The C library port is broken": the reference glibc run shows the same, and the behaviour follows the standards. "Make stdout unbuffered": hides the symptom at a performance cost and leaves other buffered streams duplicated.
