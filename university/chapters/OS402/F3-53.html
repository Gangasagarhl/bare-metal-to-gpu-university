Story hook

During a fire drill, a pupil in the chemistry room on the second floor must find her way out. She does not know the whole building. She does not need to: every room has an evacuation plan on the wall that says "from here, go to this corridor", and every corridor has one that says "from here, go to these stairs". Step by step she reaches someone who can take charge of her, a teacher waiting at the assembly point.

Now the drill is held while a visiting teacher is using a room in the new wing, opened last week. The pupils in the old rooms get out. The pupils in the new wing stand still: nobody put plans in those rooms, and the office's list of "rooms with plans" was printed before the wing opened. In the report the headline reads "drill failed in new wing only".

A C++ exception finds its way out of nested function calls the same way, room by room, reading a plan for each function. This chapter is about building that system for your OS, and about the list that tells the pupil which plans exist.

What you will be able to do

  • Name the pieces of a hosted C++ runtime (standard library, ABI support library, unwinder) and which of them depend on your OS.
  • Explain two-phase exception handling: the unwinder, personality routines, call-frame information and the language-specific data.
  • Trace how an unwinder finds the unwind tables of the object that contains a code address, through dl_iterate_phdr or a faster lookup service, PT_GNU_EH_FRAME and .eh_frame_hdr.
  • Run the U3 test program on three architectures and compare outputs byte for byte.
  • Diagnose exceptions that crash only when thrown from a dlopened library.
Jargon box
Hosted C++ runtime
Simple words: everything a normal C++ program needs from the system beyond the compiler. Analogy: the school's full equipment, not just the classroom. Precise: the standard library (libstdc++ or libc++), the language support library (libsupc++ or libc++abi: new, RTTI, exception objects) and an unwinder, built for a hosted environment that has a C library and threads; in the kernel you stay freestanding. C1 D4
Unwinder
Simple words: the code that walks back through the chain of calls when an exception is thrown. Analogy: the pupil reading one evacuation plan after another. Precise: a library (libgcc's unwinder or LLVM's libunwind) implementing the Itanium base ABI's _Unwind_* functions: it finds each frame's caller from call-frame information and runs cleanup and handler code. D1 C1
Call-frame information (CFI)
Simple words: a description, for every instruction of a function, of how to find the caller's registers. Analogy: the evacuation plan on the wall of one room. Precise: DWARF call-frame information, stored in the .eh_frame section as common information entries (CIEs) and frame description entries (FDEs), one FDE per function or code range. D2 D3
.eh_frame_hdr and PT_GNU_EH_FRAME
Simple words: an index of the plans, sorted by address, and a pointer to it. Analogy: the floor's list of rooms and where their plans are. Precise: a section holding a pointer to .eh_frame and a sorted table of (start address, FDE) pairs for binary search, located through the PT_GNU_EH_FRAME program header. D3 R3
Object lookup service
Simple words: the dynamic linker's answer to "which loaded file contains this code address?". Analogy: the office list of rooms that have plans. Precise: dl_iterate_phdr (iterate over loaded objects and their program headers; named by the curriculum for U3) or, in glibc 2.35 and later, _dl_find_object, which the unwinders of this build call instead. C1 R3 L1
Personality routine
Simple words: a language's own helper that reads a function's catch and cleanup table. Analogy: the teacher who knows which pupils are hers. Precise: a function named by the CIE (for C++, __gxx_personality_v0) that the unwinder calls for each frame; it reads the language-specific data area and answers "handler here", "cleanup here" or "continue". D1
LSDA
Simple words: the table, per function, of which code ranges have catch blocks or destructors to run. Analogy: the note saying "a teacher waits by this door for her class". Precise: the language-specific data area, in GCC's output the .gcc_except_table section; referenced from the FDE. D1
Two-phase unwinding
Simple words: first look for a catch without changing anything, then go back and actually unwind. Analogy: check that the assembly point is open before leading the class out. Precise: the Itanium base ABI's search phase (find a handler; if none, terminate without unwinding) followed by the cleanup phase (run destructors frame by frame and transfer control to the handler). D1
std::terminate
Simple words: the standard way a C++ program gives up. Analogy: the drill is abandoned and the headteacher is called. Precise: called when no handler is found (among other cases); the default handler calls abort, which raises SIGABRT; libstdc++'s default verbose handler first prints the exception's type and what(), as in R2. D5 R2

Layer 1 — the kid explanation

Analogy

A thrown exception is a pupil leaving during a drill. Each room (function) has a plan on the wall (its call-frame information) saying how to get to the room it was entered from; some doors have a teacher waiting (a catch block); some rooms must be tidied on the way out (destructors). The pupil first checks that some teacher is waiting somewhere (phase 1), then walks out, tidying as she goes (phase 2). If no teacher is waiting, the drill is abandoned (std::terminate). Mapping: room = function frame; wall plan = FDE; floor's list of plans = .eh_frame_hdr; the office list of rooms with plans = the dynamic linker's object lookup; waiting teacher = handler; tidying = cleanup.

The school's office list is the weak point: a wing opened after the list was printed is invisible, and the drill fails only there.

Layer 2 — the student explanation

U3's goal: "C++ programs written for a normal OS build and run on yours: the standard library, exceptions, RTTI, threads, iostreams, filesystem." C1 Its build list has three entries: the C++ library and unwinder built for your OS; the dl_iterate_phdr interface; std::thread mapped onto your POSIX threads. C1

The three libraries

The curriculum names two families: libstdc++ with libsupc++ (GCC) or libc++ with libc++abi (LLVM), and as unwinder either LLVM's libunwind or libgcc's unwinder. C1 The standard library holds containers, strings, streams, threads and filesystem; it calls the C library for almost everything that touches the OS. The support library implements the Itanium C++ ABI's runtime parts: operator new, RTTI type-info comparison, __cxa_throw and __cxa_begin_catch, and the personality routine. The unwinder walks frames. D1 D4

Of the three, only the unwinder talks to something OS-specific apart from the C library: the dynamic linker, to find unwind tables. That is why the curriculum lists "a way for the unwinder to find each loaded object's unwind tables" in the kernel-and-system column of the C++ row. C1

Layer 3 — the engineer's depth

Two phases, and why

The Itanium base ABI defines a language-independent unwinder interface (_Unwind_RaiseException, _Unwind_Resume, context accessors) and a C++ layer on top. D1 throw compiles to a call to __cxa_allocate_exception and __cxa_throw; __cxa_throw calls _Unwind_RaiseException. The unwinder then performs the search phase: starting from the thrower, for each frame it finds the frame's FDE, calls the personality routine named in the CIE with "search", and computes the caller's registers from the CFI. Nothing is changed. If a personality routine reports a handler, the cleanup phase walks the same frames again, this time letting each personality routine install a landing pad that runs destructors and then calls _Unwind_Resume; at the handler's frame, control is transferred to the catch block. D1

The design has a visible consequence: when no handler exists, the search phase fails and std::terminate is called before any destructor runs, with the whole stack still intact. A debugger attached at that moment sees the frame that threw, which is why a core dump of an uncaught exception is useful. D1 It has a second consequence, which the forensic lab exploits: if the unwinder cannot find the CFI of one frame, the search ends there, and the result looks exactly like "no handler".

Call-frame information

DWARF CFI describes, for each instruction address in a function, how to compute the canonical frame address (CFA, usually the stack pointer value at the call) and where each callee-saved register and the return address were saved, as offsets from the CFA. D2 The compiler emits it as a compact program of "CFA = rsp + 16", "rbp saved at CFA − 16" rules, grouped into FDEs (one per function) that share CIEs (common parameters, including the personality routine and pointer encodings). The .eh_frame section uses this format with small differences from .debug_frame that the LSB specification describes; it is loaded at run time, unlike debug information. D3

Listing 3 shows that this data really is reachable at run time. For every loaded object it reads the program headers through dl_iterate_phdr, finds PT_GNU_EH_FRAME, and decodes the first bytes of .eh_frame_hdr: version 1, the pointer encodings, and the number of entries in the binary-search table. R3 As a cross-check, run.sh builds the same program without sanitizers and counts FDE records with readelf --debug-dump=frames: both report 6 for the program itself. R3 The C library alone has 3,788 entries in this build, the C++ library 5,127: an unwinder without a sorted index would search linearly through thousands of records per frame. R3

Not verified — check before relying on this

The cross-check against readelf (6 = 6) agrees for one program only. Confirm against the LSB Core Specification's exception-frames section (D3) before reusing the decoder.

Finding the tables: dl_iterate_phdr and _dl_find_object

Given a return address, the unwinder must first find which loaded object contains it. The classic interface is dl_iterate_phdr: the dynamic linker calls a callback for every loaded object with its load address and program headers; the unwinder checks which object's PT_LOAD segments contain the address and then uses that object's PT_GNU_EH_FRAME. D3 C1 The curriculum names this interface for U3. C1

This build shows that current GNU systems have moved on: the shared unwinder libgcc_s.so.1 for all three architectures, and the static unwinder libgcc_eh.a, import _dl_find_object (versioned GLIBC_2.35) and not dl_iterate_phdr. R3 Its declaration in <dlfcn.h> says: "If ADDRESS is found in an object, fill in *RESULT and return 0. Otherwise, return -1." L1 It answers the same question in one call, without a callback over every object. For your OS the lesson is the interface, not the name: whichever your unwinder calls, your dynamic linker must answer correctly for every loaded object, including those loaded and unloaded by dlopen and dlclose at any time, and safely while other threads load libraries.

Not verified — check before relying on this

Which lookup interface LLVM's libunwind uses on each system, and whether libgcc's unwinder falls back to dl_iterate_phdr when _dl_find_object is absent (as it must have before glibc 2.35), were not checked in this build. Read the unwinder's sources and build configuration (D4) for the library you port; on a musl- or mlibc-based port, expect dl_iterate_phdr.

Personality routines and the LSDA

Each function that has catch blocks or objects with destructors gets an LSDA: a table of call-site ranges, each with a landing pad and an action (catch which types, or cleanup only). D1 The C++ personality routine looks up the current call site, and in the search phase compares the thrown type against the catch clauses using RTTI: catch (const std::runtime_error&) must match an exception of that class or a derived class, which needs type-info objects and their comparison to work across shared-library boundaries. D1 Line 7 of R1 shows the derived-class rule (std::out_of_range caught as std::logic_error); line 8 shows the cross-library case. R1

std::thread on your threads

libstdc++ implements std::thread, std::mutex and std::condition_variable on POSIX threads ("gthreads"), so U3's thread requirement becomes a requirement on your C library's pthreads, which in turn need the curriculum's kernel list for the Threads row: thread creation with a given stack and TLS pointer, futex-like wait and wake, thread exit and join. C1 D4 Section 5 of Listing 1 is a producer–consumer with four consumers waiting on a condition variable: a missed wake-up in your futex leaves a consumer asleep for ever and the test hangs, a lost update shows as a sum different from 500500. R1 Exceptions and threads meet in one more place: the support library keeps per-thread exception state (the caught-exception stack), which needs the TLS of F3-52.

filesystem, iostreams and locale

std::filesystem rests on opendir/readdir, stat and friends from F3-51's list; R1's line 4 checks iteration, creation, size and removal. R1 iostreams depend on locale support; the curriculum allows "locale can be minimal": a library that supports only the "C" locale is enough for U3, provided the standard streams format numbers as on the host. Building the runtime for your OS

libstdc++ is built as part of GCC for a target triple; libc++ and libc++abi with CMake against a sysroot. Both have "hosted" and "freestanding" configurations, and the kernel stays freestanding. C1 D4 In practice the order is: C library installed in the sysroot (F3-51, F3-52) → compiler and unwinder for your triple (F3-54) → C++ library configured against the sysroot → the U3 program. Failures in the third step are almost always missing C library functions or headers, which go onto your F3-51 list.

Not verified — check before relying on this

No C++ runtime was built for a new OS in this build (no libc++ is installed, and building libstdc++ for a new triple was out of scope). The configuration names, CMake options and GCC configure options for hosted builds must be taken from the libstdc++ and libc++ build documentation (D4); none are given here.

How the hardware actually does it

Unwinding uses no special hardware: it is a software interpretation of the stack that the calling convention of each architecture leaves behind. What differs per architecture is where the return address lives: x86-64's call pushes it on the stack; AArch64's bl and RISC-V's jal put it in a link register (x30, ra), which a non-leaf function then saves. D6 The CFI records which of these happened at each instruction, so the same unwinder code works on all three, as R1's identical outputs under QEMU illustrate. R1 Two hardware-related details do concern your kernel: signal frames (the kernel's signal-frame layout from F3-51 must be describable to the unwinder if you want exceptions or backtraces through signal handlers) and the stack alignment the psABI requires at a call, which landing pads assume. D6

Not verified — check before relying on this

Untested on hardware: the AArch64 and RISC-V runs of R1 used QEMU user mode on an x86-64 host with the cross toolchains' Linux libraries, not real Arm or RISC-V machines and not your OS. The return-address register names are from the psABIs and architecture manuals (D6), not opened in this build.

Worked example

Task. Follow throw_from_library(7) in R1 through the unwinder, and name each point where your OS could break it.

  1. throw in libthrower.so allocates the exception object (__cxa_allocate_exception: the C library's allocator) and calls __cxa_throw in the support library. D1 Breaks if malloc fails or the support library is not linked.
  2. _Unwind_RaiseException starts the search at the throwing frame. It needs the frame's object: the lookup service answers "libthrower.so". Breaks if the dynamic linker does not know objects loaded later (the forensic fault). R4
  3. From PT_GNU_EH_FRAME, binary search in .eh_frame_hdr gives the FDE; the CFI gives the caller's registers. Breaks if the object was built without unwind tables or the header is missing.
  4. The next frame is main (the call at line 142 of Listing 1). Lookup now answers "the program"; its LSDA has a catch for std::runtime_error; the personality routine compares type-info objects: match. Breaks if type-info comparison fails across libraries.
  5. Cleanup phase: frames are unwound again; the string temporary from libthrower.cc's line 8 is destroyed on the way; control enters the catch block, which prints line 8 of R1. R1

Check. R1's line 8 on all three architectures reads "8 exception across the library boundary: thrown inside libthrower.so, code 7". In the forensic run, step 2 fails, the search phase finds no handler, and the process ends in std::terminate with exit code 134. R4

Where the analogy breaks


    

  • The pupil checks the whole route before moving. Real evacuations do not have a "search phase"; two-phase unwinding does, and that is why an uncaught exception leaves the stack untouched. D1
    • 

  • Plans are exact to the instruction. A room has one plan; a function's CFI changes from instruction to instruction as registers are saved and the stack moves. D2
    • 

  • A missing plan looks like a missing teacher. In a school, a pupil without a plan would shout for help; an unwinder that cannot find CFI simply reports "end of stack", which ends in std::terminate with a message about an uncaught exception, pointing the wrong way. R4

  • A hosted C++ runtime is a standard library, an ABI support library and an unwinder; only the unwinder needs something OS-specific beyond the C library: the dynamic linker's object lookup.

Forensic lab answer key


Observation. The exception thrown in the program is caught. After dlopen, the debug dump lists libthrower.so with "in the port's table: no"; every other object says yes. The exception from libthrower.so ends in "terminate called after throwing an instance of 'std::runtime_error'", exit code 134, and "end of main" is never printed.


Root cause. The port's lookup service (port_ldso.cc) builds its table of objects once, in a constructor at start-up (lines 35–38), and never updates it. Its _dl_find_object (lines 55–62) returns "not found" (line 59) for any object not in the table. The unwinder asks for the throwing frame's object, gets "not found", cannot find its CFI, and ends the search phase without a handler: std::terminate. Objects present at start-up are all in the table, which is why other exceptions work.


How the evidence was produced. The real host dynamic linker loaded everything; port_ldso.cc interposes the lookup service the host's unwinder calls (_dl_find_object, R3) with the port's logic. The card's wording, "the unwinder cannot find the .eh_frame of a shared object; find the missing dl_iterate_phdr support", describes the same defect for an unwinder that uses dl_iterate_phdr: there, the port's dl_iterate_phdr would iterate a list that dlopen does not extend. The diagnosis does not change (question 5).


Fix and verification. The object list must follow dlopen and dlclose. A real dynamic linker updates it inside those calls (under a lock); port_ldso_fixed.cc rebuilds the table on a miss (lines 58–69). Verification: the fixed run prints "caught: thrown inside libthrower.so, code 7" and "end of main", exit code 0. Its debug dump still shows "no" for libthrower.so, because the dump is printed before the first lookup refreshes the table.




Wrong answers and why. "The plugin was built without -fexceptions": C++ code has unwind tables by default, and the same library works with the fixed loader. "Type-info mismatch across libraries": that would fail the match in the personality routine, not the lookup, and the fixed run shows the same types matching. "A kernel bug": nothing in the evidence involves the kernel; the process ended by abort as designed.
