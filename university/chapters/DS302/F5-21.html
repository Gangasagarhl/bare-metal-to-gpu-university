Story hook

The friends' system has worked for months. Then Kofi asks Amara "what pizza did we order last?", and she answers "margherita" — although Kofi himself had changed the order to "funghi" an hour ago and got a "done". Nothing crashed. Amara simply had not heard that she was no longer the order-writer: the phone line to her town had been down, the others had picked a new writer, and she answered from her own copy of the notebook.

Bugs like this one never show up while everything works. They need a partition at the right moment, a request to the wrong server, and somebody who compares the answers with what happened in real time. This chapter is about building that somebody: a test harness that injects faults on purpose, checks every safety property while the system runs, and decides whether the answers clients received could have come from one single copy. Then we turn it on the four bugs of this course and measure, honestly, which ones it finds.

What you will be able to do

  • Explain why consensus code needs fault-injection testing and why deterministic simulation makes failures replayable.
  • Write runtime checkers for Raft's safety properties.
  • Define linearizability and decide by hand whether a small history is linearizable.
  • Implement and use a linearizability checker for a single register.
  • Measure how often randomized testing finds a given bug, and design a targeted nemesis for a rare one.
  • Diagnose a stale read from a client history and fix it.
Jargon box
Deterministic simulation
Simple words: running the whole distributed system inside one program where time, the network and randomness are fake and controlled. Analogy: replaying the friends' week from a diary, letter by letter. Precise: executing all nodes, the network and the clock in a single process driven by a seeded pseudo-random generator, so that the same seed always produces the same execution. (Definition from this course's lab; no registry source.)
Nemesis (fault injector)
Simple words: the part of a test that breaks things on purpose. Analogy: a deliberately bad mail service that loses, delays and duplicates letters and sometimes knocks a friend out. Precise: a component that schedules crashes, restarts, partitions, message loss, delay and duplication during a test run, either at random or targeting specific nodes such as the current leader. (Term as used in this course's lab; no registry source.)
History
Simple words: the list of every client request with when it started, when it ended, and what came back. Analogy: each friend's list of questions asked and answers heard, with times. Precise: a record of operation invocations and responses as observed by clients; an operation without a response has an unknown outcome.
Linearizability
Simple words: the system behaves as if there were one copy of the data and each operation happened at one instant between its start and its end. Analogy: every answer fits one single notebook read in one order, consistent with the clock. Precise: a history is linearizable if there is a total order of its operations that respects the sequential specification of the object and in which an operation that completed before another began is ordered first. D4
Stale read
Simple words: a read that returns an old value after a newer value was confirmed. Analogy: Amara saying "margherita" after Kofi's "funghi" got its "done". Precise: a read whose result could only be explained by ordering it before a write that completed before the read began; a violation of linearizability. D4

Layer 1 — the kid explanation

To test a plan for agreeing, you hire a terrible mail service on purpose: it loses letters, delays them, delivers some twice, and sometimes cuts a town off. You let the friends run their plan through this mail service thousands of times, each time with a different dice roll, and you write down every question and every answer with the time. Then a checker asks: "could all these answers have come from one notebook, read one line at a time, never going back in time?" If not, there is a bug — and because you wrote down the dice roll, you can replay the exact same bad week as often as you like to find it.

Layer 2 — the student explanation

Why ordinary tests are not enough

Every bug of this course needed a specific combination of events: a crash between a vote and its disk write (F5-18), a partition that left a follower behind (F5-19), four leader changes in a particular order (F5-20). Unit tests check what the author thought of. Consensus bugs live in the interleavings the author did not think of, so we generate interleavings automatically and check properties rather than expected outputs.

Three ingredients make this work:

  1. Deterministic simulation. All servers, the network and the clock run in one process driven by one seeded random generator (sim.h, cluster.h). A failing seed is a complete bug report: run it again and the same thing happens, as often as needed, with any amount of tracing.
  2. A nemesis. A fault schedule derived from the seed: crashes, restarts, partitions, healing, plus a network that delays (1–20 ms), drops (2%), duplicates (1%) and therefore reorders messages (fuzzOne).
  3. Checkers. Properties that must hold in every execution: Raft's own safety properties, checked inside the simulation where one can see every server (F5-20), and linearizability of what clients saw, checked from the outside.

Linearizability

A key-value service built on Raft promises clients that it behaves like a single copy: once a write has completed, every read that begins afterwards sees it (or something newer). Formally, the history must be explainable by one total order of operations, each taking effect at an instant between its invocation and response. D4 Listing 2 checks four small histories:



H1: the get overlaps the put, so it may take effect before it: linearizable. H2: the get starts after the put ended and still returns 0: no valid order. H3 and H4 contain a put that never got a reply: its outcome is unknown, so it may have taken effect at any time after it was called, or never. In H4 that freedom explains everything ("get 0, then put 1, then get 1"); in H3 one reader saw 1 and a later reader saw 0, which no single order can explain. R1



The correct implementation under fire




100 seeds, each 4,000 simulated ms with five servers and a random nemesis acting every 150 ms for the first 3,000 ms: no safety violation and no non-linearizable history. 4,994 client operations were started and 3,434 answered (the others timed out during faults, which is allowed); the runs elected 315 leaders in total. A bug that needs a crash in a short window (lazy persistence) or a partition plus a read at the wrong server (stale reads) shows up in a few percent — enough, if you run thousands of seeds. Two lessons: a tester's power depends on its fault schedule, and you should measure that power by planting known bugs (mutation testing) before trusting a clean result.



Layer 3 — the engineer's depth


How the linearizability checker works


Listing 2's checker searches for a valid order in the style of Wing and Gong: repeatedly choose an operation that may take effect next — one that is not yet placed and that began before every unplaced operation's response — apply it to a model register, and backtrack when a get returns the wrong value. It remembers visited (set of placed operations, register value) pairs, so no state is explored twice. Two simplifications keep it small: gets without a reply are dropped (they constrain nothing), and so are unanswered puts whose value no get returned (they can always be explained as "never took effect", because each put writes a distinct value). The checker handles at most 63 operations (a 64-bit set) and is exponential in the worst case. That is fine for 50-operation runs; real checkers split histories by key and use smarter search.


Not verified — check before relying on this
The attribution of this search to Wing and Gong, and the original definition of linearizability by Herlihy and Wing, are recalled from memory; neither paper is in the F5 source registry. Industrial tools that test real databases with a nemesis and a linearizability checker (for example the Jepsen project) and the formal TLA+ specification of Raft are also outside the registry. The complexity claim (checking linearizability is NP-complete in general) is likewise unverified here. Add sources before publication (dossier gate G1).



Linearizable reads in Raft


The forensic lab's bug is the classic one: a leader answering reads from its local state. A leader that has been partitioned away may not know that a newer leader exists and that newer writes have been committed. The Raft paper's remedy: a leader must have the latest committed entries (it commits a no-op at the start of its term) and must check that it has not been deposed before answering a read, by exchanging heartbeats with a majority; alternatively, it can rely on the heartbeat to grant a lease, which depends on bounded clock drift. D1 The lab takes the simplest correct route: reads go through the log like writes, so a get is answered only after it is committed in the leader's term.



What the harness cannot find


    

  • Bugs outside the model. The simulated disk is perfect and instantaneous; a real file system can reorder, tear or lose writes that were not flushed. The network simulator does not corrupt messages.
    • 

  • Bugs in code not simulated. If production uses real sockets, threads and timers, the simulation tests a model of it; keeping the two in step needs the same code compiled against two environments (the lab's Env interface is that seam).
    • 

  • Liveness. The checkers test safety; a run in which nothing ever commits passes. Add progress checks: "after healing, a put completes within T ms".
    • 

  • Rare schedules. As the table shows, a clean result after 100 seeds says little about bugs that need five coordinated events.
    • 




How the hardware actually does it


Deterministic simulation tests logic, not machines. The physical failure modes that matter for consensus — a disk that acknowledges a flush it has not made durable, a process paused by the operating system or the virtual machine host, a clock that jumps, a network card that drops packets under load, a partition that is asymmetric (A hears B, B does not hear A) — must be tested on real hardware too: by killing processes and cutting power, by pausing processes with signals, by adjusting clocks, by dropping packets with firewall rules. The simulator can model some (the lab's block makes one-way partitions); the disk and clock behaviours depend on the actual devices and must be measured there. This build ran no such hardware tests.



Worked example


Task. Is this history on register x (initially 0) linearizable? A: put x=1 [0, 50]. B: get x → 1 [10, 20]. C: get x → 0 [30, 40]. If yes, give an order.


    

  1. Real-time constraints: B ended (20) before C began (30), so B precedes C. A overlaps both.
    2. 

  2. B returned 1, so A must precede B: A, B, then C. But C returns 0 after A wrote 1, and there is no other put. Contradiction.
    3. 

  3. Try A after B: then B would read 0, not 1. Contradiction.
    4. 

  4. Not linearizable — the same shape as H3 in Listing 2, with the put answered this time. A system that produces this has let one reader see a write and a later reader miss it.
    5. 

  5. Variation: if C had been [15, 40] instead, C overlaps B, and the order C(0), A(1), B(1) works: linearizable.

Where the analogy breaks


    

  • A bad mail service is random. The most valuable fault schedules are not random but adversarial: the leader hunter found what random faults never did.
    • 

  • Replaying a diary needs a perfect diary. Determinism holds only if every source of randomness and time goes through the simulator; one call to the real clock or one hash-ordered container iteration in the wrong place breaks replay.
    • 

  • "One notebook read in order" is about clients. Linearizability says nothing about the servers' internal notebooks; a system can have perfect logs and still give stale answers, as in the forensic lab.
    • 




Common mistakes and debugging


    

  • Symptom: a failing seed does not fail again. Cause: non-determinism (real time, threads, unordered iteration, uninitialized memory). How to find it: run the same seed twice and diff the traces; the first difference points at it. Fix: route all time and randomness through the simulator.
    • 

  • Symptom: the linearizability checker never finishes. Cause: many concurrent operations with unknown outcomes. Fix: fewer clients per key, shorter runs, memoization, dropping unobserved puts.
    • 

  • Symptom: everything passes, always. Cause: a weak nemesis or a checker that checks nothing. Fix: plant known bugs and measure the catch rate (bug_hunt).
    • 

  • Symptom: client timeouts are recorded as failures. Cause: treating "no reply" as "did not happen". Fix: record an unknown outcome; the checker must allow both.
    •

Summary


    

  • Consensus bugs live in rare interleavings; test with generated fault schedules and property checks, not expected outputs.
    • 

  • Deterministic simulation turns every failing seed into a replayable bug report.
    • 

  • Check Raft's safety properties inside the simulation and linearizability of client histories from outside.
    • 

  • Linearizable: one order of operations, consistent with each answer and with real time; unknown outcomes may be placed anywhere after their call, or omitted.
    • 

  • Measure the tester: in this build the random nemesis caught skipPrevLogCheck in 94 of 100 seeds but commitOldTermByCount in 0 of 100; a leader hunter caught it in 2 of 150.
    • 

  • Leaders must not answer reads from local state without confirming leadership; the lab sends reads through the log.

Forensic lab answer key


Observation. n1 led term 1 from 110 ms; the partition {1,2} | {3,4,5} at 300 ms cut it off from the majority; n3 won term 2 at 570 ms. put x=2 was committed by n3 (term 2) at 715 ms. The get at 800 ms went to n1, which answered 1 at 810 ms, still believing it was leader of term 1. n1 learned about term 2 only at 1,010 ms, after healing ("n1 term 2 LEADER -> follower").


Linearizable? No (Figure 2): put x=2 completed at 720 ms, before the get began at 800 ms, so the get must follow it and return 2. The checker agrees: "NOT linearizable".


Why the Raft checker is green. The logs and state machines are all consistent: n1 never applied anything wrong; it answered from a correct but old state. The Raft properties concern logs; linearizability concerns what clients observed. You need both checkers.


Hypotheses. (a) ruled out: "715 ms n3 commits up to entry 4 (t2 put x=2)" with n4 and n5. (c) ruled out: the times come from the simulator's single clock. (b) confirmed: n1's get reply has no corresponding log entry; it was answered 10 ms after the request, the time of one round trip from the client, with no message to the other servers.


Root cause and fix. The leader answered a read-only request without first checking that it had not been deposed. The deployed code ran with readFromLocalState (raft_replication.h lines 170–175). Correct options: send reads through the log (the lab's default: the fixed run shows n1 appending "t1 get x" and never committing it, so that client gets no reply, which is allowed, while the get at n3 returns 2); or record the commit index, exchange heartbeats with a majority to confirm leadership, then answer once that index is applied; or leases, which depend on bounded clock drift. D1




How the evidence was made. stale_read_story.h fixes the timeouts, partitions {1,2} from the rest at 300 ms, sends put x=2 to n3 at 700 ms, get x to n1 at 800 ms and to n3 at 900 ms, heals at 1,000 ms, and checks the history; stale_read.cpp runs it with the fault, stale_read_fixed.cpp without.
