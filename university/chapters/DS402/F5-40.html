Story hook

The club's address book has become too big for one person, so the friends split it. Their first rule was simple: count the letters of a name, divide by the number of friends, and the remainder says who keeps that entry. It worked until Yara joined as the fifth keeper. Overnight, four out of five entries had to move to someone else's book, and for a week nobody could find anything.

So they drew a wheel. Each friend owns the stretch of the wheel just before her own mark, and each name lands somewhere on it. When Yara joined, she put her mark on the wheel and took over only the names just before it; everyone else's entries stayed put. To survive a lost notebook, each entry is also written in the books of the next two friends round the wheel.

Then Leila and Hiro both updated the club's packing list for a trip on the same afternoon, while the phone line between their towns was down. Both changes were accepted. When the line came back, the list had two versions, and the club had to decide what the "real" list was. The way they decided brought back an item that Leila had crossed out. This chapter builds the wheel, the copies and the version tracking, and then finds out exactly why the item came back.

What you will be able to do

  • Explain how a distributed key-value store partitions keys with consistent hashing and virtual nodes, and measure how many keys move when a node joins.
  • Configure replication with N, R and W, predict when a read can miss the latest write, and verify the prediction with the lab's simulation.
  • Explain sloppy quorums, hinted handoff, vector clocks and siblings, and the trade-off between availability and consistency they encode.
  • Compare a leaderless Dynamo-style store with the leader-based Raft key-value service of DS302, and say which to choose for a given requirement.
  • Diagnose a resurrected deleted item from replica logs with vector clocks, and propose a merge that does not lose deletes.
Jargon box
Key-value store
Simple words: a storage service where you save a value under a name (the key) and get it back by that name. Analogy: the club's address book: look up a name, read the entry. Precise: a data store whose interface is essentially get(key) and put(key, value) on opaque values, without queries across keys; distributed key-value stores partition the key space across nodes and replicate each key. D1 D4
Consistent hashing
Simple words: put both keys and computers on a circle of numbers; each key belongs to the next computer round the circle. Analogy: the wheel of letters, each friend owning the stretch before her mark. Precise: a partitioning scheme in which a hash function maps keys and nodes onto the same circular space and each key is assigned to the first node clockwise from its position, so that adding or removing a node moves only the keys of the neighbouring range. D7 D4
Virtual node (token)
Simple words: each computer puts many marks on the circle instead of one. Analogy: Yara draws many small marks round the wheel, so she takes a few names from everyone. Precise: one of several positions on the ring assigned to the same physical node, which evens out the load and spreads the work of a joining or leaving node over many others. D4
Preference list
Simple words: the computers that should keep copies of a key, in order. Analogy: the owner of the stretch and the next two friends round the wheel. Precise: in Dynamo, the list of nodes responsible for a key: the first N distinct physical nodes found walking clockwise from the key's position, skipping further virtual nodes of a node already listed. D4
Quorum (N, R, W)
Simple words: keep N copies; wait for W of them on a write and ask R of them on a read. Analogy: write the entry in three books, wait until two friends confirm; when reading, ask two friends and trust the newer entry. Precise: a replication configuration in which a write succeeds after W of the N replicas acknowledge and a read returns after R replicas reply; if R + W > N, every read set intersects every write set, so a read sees at least one replica with the latest successful write (absent sloppy quorums and concurrent writes). D1 D4
Sloppy quorum and hinted handoff
Simple words: if the usual keepers are unreachable, a stand-in keeps the copy and hands it back later. Analogy: Kofi keeps Mei's copy of an entry, with a note "belongs to Mei", while her line is down. Precise: a quorum counted over the first N reachable nodes of the extended preference list rather than over the N home nodes; a stand-in node stores the write with a hint naming the intended node and forwards it when that node is reachable again. D4 D1
Vector clock
Simple words: a small list of counters, one per writer, that shows which versions came before which. Analogy: each friend numbers her own changes; a version carries the latest number it has seen from each friend. Precise: a map from node identifiers to counters attached to a version; version a descends from version b if every counter of a is greater than or equal to the matching counter of b; if neither descends from the other, the versions are concurrent. D4 D6
Siblings
Simple words: two versions of the same entry that were written without knowing about each other. Analogy: Leila's packing list and Hiro's packing list from the afternoon the line was down. Precise: concurrent versions of one key that the store keeps side by side and returns together on a read, leaving reconciliation to the application. D4
Tombstone
Simple words: a note that says "this was deleted", kept instead of just erasing. Analogy: crossing out the stove and writing "removed by Leila" instead of tearing out the line. Precise: a marker stored in place of a deleted item or value so that the deletion can be merged with concurrent versions and propagated to replicas instead of being undone by them. D1 D8

Layer 1 — the kid explanation

Analogy

The club's address book is split among friends by a wheel. Mapping: the wheel = the hash ring; a friend's mark = a token; many small marks per friend = virtual nodes; the owner and the next two friends round the wheel = the preference list (N = 3); "wait for two friends to say 'written'" = W = 2; "ask two friends and trust the newer entry" = R = 2; a friend keeping an entry for someone whose line is down, with a note = hinted handoff; each friend numbering her own changes = a vector clock; two lists written while the line was down = siblings.

The wheel makes joining cheap: a new friend takes a little from her neighbours on the wheel, and nobody else moves anything. Copies on the next friends round the wheel mean a lost notebook loses nothing. Waiting for some, but not all, friends makes writing fast even when one friend is slow.

The price is that friends can disagree. If you ask the wrong friends, you may read an old entry. If two people change the same entry while the phone lines are down, both changes are kept, and someone has to combine them later. Combining is easy for additions and surprisingly hard for removals: if you combine two lists by keeping everything on either list, anything one person crossed out comes back.

Layer 2 — the student explanation

Partitioning keys: modulo hashing versus a ring

A store that spreads keys over nodes needs a rule from key to node. Hashing the key and taking the remainder modulo the number of nodes spreads keys evenly, but when the number of nodes changes, most keys change node: a key stays only if its hash gives the same remainder for both node counts D1. Listing 1 measures it: going from four to five nodes moves 7,995 of 10,000 keys (80.0 %), although an even share for the new node would be 2,000 R1. The worked example derives the 80 % by arithmetic.

Consistent hashing places nodes and keys on the same circular hash space and gives each key to the first node clockwise D7. A joining node takes over only the range just before its own position, so only those keys move D7. With one position per node, the lab moves 2,398 keys (24.0 %), but the load is uneven: node D owns 965 keys and A owns 3,396, and after E joins B is left with 147 R1. Random positions make ranges of random length.

Dynamo's remedy is virtual nodes: each physical node takes many positions (tokens) on the ring D4. Many ranges per node average out, and a joining node takes small ranges from all others instead of one large range from one neighbour. With 64 tokens per node, the lab's maximum load falls to 1.26 times the mean with four nodes, and 1,933 keys (19.3 %) move when E joins; with 256 tokens the maximum is 1.05 times the mean R1. More tokens cost more metadata (every node must know the ring) and more, smaller ranges to move and repair; Kleppmann discusses these trade-offs and alternatives such as a fixed number of partitions assigned to nodes D1.

Replication along the ring

Each key is stored on N nodes: the owner and the next distinct nodes clockwise, the key's preference list D4. "Distinct" matters with virtual nodes: walking clockwise you may meet a second token of a node already chosen, which must be skipped, or two of the N copies would sit on one machine. preferenceList in Listing 1 does this (lines 46–59), and the lab prints the list of key-42 before and after E joins: C B D, then C B E R1. Dynamo also lists more than N nodes, so that unreachable ones can be skipped, and places replicas on nodes in different data centres D4.

Any node can coordinate a request for any key: it finds the preference list, sends the write or read to the N nodes, and waits for W acknowledgements or R replies D4. There is no leader per key: this is leaderless replication, the third architecture of F5-12 D1.

Quorums: R + W > N, measured

If R + W > N, any R replicas and any W replicas of the same N share at least one replica, so a read that follows a successful write reaches at least one replica that has the write D1. The reader must then choose the newest of the versions it received, which requires versions that can be compared. Part 1 of Listing 2 tests this with N = 3: each new version reaches each replica after a random delay, mostly short and sometimes long; a write is acknowledged after W replicas have it; a read right after the acknowledgement asks R random replicas R2.

Sloppy quorums and hinted handoff

A strict quorum stops accepting writes for a key when fewer than W of its N home nodes are reachable. Dynamo chose to stay writable: it counts the quorum over the first N healthy nodes of the extended preference list, and a stand-in node stores the write with a hint naming the home node it was meant for, then hands it over when that node is back D4. The cost is that R + W > N no longer guarantees intersection, because the write and the read may count different nodes D1. Part 2 of Listing 2 is the smallest example: the write is acknowledged by A and stand-in D; the reader can reach only B and C; both hold the old version, and the read returns it R2. Sloppy quorums improve write availability; they are not a consistency mechanism.

Versions: vector clocks and siblings

Without a leader, two clients can write the same key concurrently through different coordinators, especially during a partition. Dynamo attaches a vector clock to every version: a list of (node, counter) pairs D4. When a coordinator writes a new version, it starts from the clock of the version the client read and increases its own counter. A replica that receives a version whose clock descends from (is greater than or equal to, in every entry) the clock it holds replaces the old one; if neither descends from the other, the two are concurrent and the replica keeps both as siblings D4. A read returns all siblings, and the client reconciles them and writes back a version whose clock descends from all of them D4. This is the version-vector idea of F5-10 used to detect conflicts rather than to order events.

The forensic lab's evidence pack is produced by this logic. descends in resurrect.cpp is the definition above, and the replica logs show A holding [A:5] and [A:4 C:1] side by side after the partition heals R3. Reconciliation is application logic, and the forensic lab is about what happens when that logic is wrong.

Layer 3 — the engineer's depth

Dynamo's design as a set of choices

The Dynamo paper summarises its techniques against the problems they address: consistent hashing for partitioning, vector clocks with reconciliation during reads for high write availability, sloppy quorums and hinted handoff for temporary failures, anti-entropy with Merkle trees for permanent failures, and gossip-based membership and failure detection D4. The common thread is that the system is designed to accept writes even during failures and partitions, pushing conflict resolution to reads and to the application D4. Read this as a choice in the sense of F5-13: during a partition, a replica either refuses some requests or accepts writes that may conflict; Dynamo accepts and reconciles.

Anti-entropy with Merkle trees deserves a sentence of mechanism. Each node keeps, per key range, a hash tree whose leaves hash individual keys' values and whose inner nodes hash their children; two replicas compare roots, and only if they differ descend into the children, so they find the differing keys while exchanging data proportional to the differences, not to the range D4. Hinted handoff repairs short absences; anti-entropy repairs whatever hinted handoff missed (for example when the stand-in node itself failed). You built the simplest anti-entropy in F5-12 with the G-counter; this is the scalable version.

Many systems combine both: a Raft group stores the cluster's membership and the ring, while data uses leaderless or per-partition leader replication. The course project's MP2 uses the Raft side; its observability (F5-41 onwards) is the same either way.

Reconciliation that does not lose deletes

The Dynamo paper describes a shopping cart whose siblings are merged by taking the union of their items, so that an added item is never lost, and reports that deleted items can resurface as a consequence D4. A union cannot tell "Hiro never had the stove" from "Leila removed the stove": both look like absence. The fix is to make the removal a piece of data. Two standard designs: tombstones (remember removed items with the clock of the removal, and let the merge drop an item if its removal is newer than the add it removes) and the observed-remove set from the CRDT literature, in which every add carries a unique tag and a remove deletes only the tags it has observed, so a concurrent re-add with a new tag survives while the observed one does not D8. Both need garbage collection of tombstones or tags once every replica has seen them, which in turn needs to know that every replica has seen them: a membership question.

Last-writer-wins and clock size

Some stores resolve concurrent versions by timestamp, keeping the newest and discarding the rest; this silently loses concurrent writes, and with skewed clocks may keep the older one (F5-10) D1. Vector clocks avoid that but grow with the number of coordinators that wrote a key; Dynamo bounds their size by truncating the oldest entries beyond a threshold, accepting that truncation can make descendant versions look concurrent D4.

Not verified — check before relying on this

The Dynamo paper reports configuration values from production (a common (N, R, W) setting recalled as (3, 2, 2)), latency percentiles, the clock-truncation threshold and its partitioning strategies with numbers of tokens; none is used in this chapter because none could be checked in this build. Take them from D4, sections on partitioning, replication, versioning and experiences, before quoting. Products that describe themselves as Dynamo-inspired implement different subsets (some use last-writer-wins instead of siblings); their behaviour must come from their own documentation for a recorded version. The hash constants in Listing 1 are those of FNV-1a and the SplitMix64 finaliser written from memory; the experiment's conclusions do not depend on them, but the constants should not be copied as verified.

How the hardware actually does it

Each node of a key-value store is a server with memory, local storage and a network interface; a put that a replica "acknowledges" has reached its memory, its write-ahead log, or its disk, depending on the store's configuration, with the same durability questions as in F5-12. The waits in Listing 2 are an abstraction of where time really goes: the network round trip to each replica, the replica's queue, and its storage write; waiting for the second-fastest of three replicas instead of the slowest is exactly why quorum systems cut tail latency, a point the Dynamo paper makes when it discusses its latency percentiles D4. Placing the replicas of a key in different racks or data centres protects against correlated failures but puts a wide-area round trip into every W > 1 write whose quorum must span sites.

Not verified — check before relying on this

Untested on real hardware: all nodes and replicas in this chapter are objects in one process and all delays are numbers drawn from an exercise distribution. No network latency, no disk latency and no throughput was measured. A measurement of a real store needs at least three machines (or virtual machines) with a recorded network setup, which the build container does not have.

Worked example

Why does modulo hashing move 80 % of the keys when going from 4 to 5 nodes?

  1. A key with hash h is on node h mod 4 before and on node h mod 5 after; it stays on the same node index only if h mod 4 = h mod 5. (Listing 1 compares node names, and the four old names keep their indices 0–3.)
  2. The pair (h mod 4, h mod 5) repeats every lcm(4, 5) = 20 values of h. Check h = 0 to 19: the remainders are equal for h = 0, 1, 2, 3 (both give h) and for no other h (for h = 4 to 19 they differ: for example h = 4 gives 0 and 4; h = 20 starts the cycle again).
  3. So 4 of every 20 hash values stay: 20 % stay and 80 % move. With a well-mixed hash, the lab's 10,000 keys should show about 8,000 moves; the run shows 7,995 (80.0 %) R1.
  4. In general, from n to n + 1 nodes, keys with h mod n = h mod (n + 1) stay: exactly the values h < n in each cycle of length n(n + 1), a fraction n / (n(n + 1)) = 1/(n + 1). From 4 to 5 that is 1/5 = 20 % staying; from 99 to 100 only 1 % stay.
  5. Consistent hashing moves only the keys the new node takes over: about 1/(n + 1) of them with enough tokens (19.3 % and 19.6 % in the lab with 64 and 256 tokens) R1. Modulo hashing moves almost everything; the ring moves almost the minimum.

Where the analogy breaks


    

  • Friends on a wheel see where everyone's marks are. Real nodes learn the ring through gossip, and for a while two nodes can disagree about who owns a range, so two coordinators may send the same key to different replicas.
    • 

  • A friend's paper address book keeps the newer entry because the friend can read the date. Replicas cannot read "newer" from wall clocks safely; they need version numbers or vector clocks, and some versions are neither newer nor older.
    • 

  • Combining two packing lists is something people do with judgement ("Leila crossed this out on purpose"). A merge function has no judgement: whatever it does to absence is what happens to every delete.
    • 

  • The wheel suggests that nodes are equal. Real nodes have different capacities; the number of tokens per node is how a store gives a bigger node a bigger share.
    •

Transition box

Where you came from: F5-39 built a file system with one master that knows where everything is, and DS302 built a key-value service in which a Raft leader orders every write. What carries over: replication factor, quorums and majorities (a Raft majority is the special case R = W = majority), version numbers that expose stale replicas, and partitioning from F5-14 D1. What changes: most dangerous first: without a leader, concurrent writes are normal and the application must merge them, and a careless merge loses deletes or updates; R + W > N gives intersection only for strict quorums; and there is no central catalogue: placement is computed from the ring by every node D4 R2. What comes next: F5-41 asks how you would even know that a read was stale or slow in production, and instruments a service with logs, metrics and traces.

Summary


    

  • Modulo hashing moves most keys when nodes change (80 % from 4 to 5 nodes); consistent hashing moves about the new node's share.
    • 

  • Virtual nodes even out the load (max/mean 1.36 with one token, 1.05 with 256 in the lab) and spread the work of membership changes.
    • 

  • A key's N replicas are the first N distinct nodes clockwise; any node can coordinate.
    • 

  • With strict quorums, R + W > N makes reads see the latest acknowledged write; the lab measured zero stale reads for every such configuration and many without it.
    • 

  • Sloppy quorums and hinted handoff keep the store writable during failures but break the intersection guarantee.
    • 

  • Vector clocks detect concurrent writes; the store keeps siblings and the application merges them.

Answers to Check yourself


    

  1. Modulo: a key stays only if h mod 9 = h mod 10, which holds for 9 of every 90 hash values (1/10), so 90 % move. Consistent hashing with many tokens: about the new node's share, 1/10 of the keys.
    2. 

  2. With one random position per node, the ranges between positions have random lengths, so some nodes own much more of the circle (lab: D 965 keys, A 3,396). Many tokens per node average many random ranges, so each node's total is close to the mean (64 tokens: max/mean 1.26; 256: 1.05), and a joining node takes small pieces from every node instead of one big piece from one neighbour.
    3. 

  3. Good answers say: the write is on W of the N replicas and the read asks R of the same N; if R + W > N, the two sets cannot be disjoint (pigeonhole), so at least one reply has the write, and choosing the newest version returns it. It fails with sloppy quorums (the sets are drawn from different nodes), when the read overlaps a write still in progress, and when a replica holding the write fails and is restored from an older copy before repair.
    4. 

  4. R + W = 6: (1, 5), (2, 4), (3, 3), (4, 2), (5, 1). Fast writes: small W, so (5, 1) (every read asks all five).
    5. 

  5. Neither descends: A:2 > A:1 but B:1 < B:2. They are concurrent; the store keeps both as siblings and returns both on a read.
    6. 

  6. The union keeps the item: the laptop's sibling still contains it (with the new text), and the phone's sibling simply lacks it, which the union cannot distinguish from "never had it". The user sees the ticked-off item back, edited. An observed-remove set would also keep it, correctly: the edit is a concurrent new add the remover did not observe; the right design decision is a product question, and the merge must make it explicit.
    7. 

  7. The waits change most: with no slow deliveries, waiting for the slowest of three is no longer expensive, and the R = 3 and W = 3 waits fall from about 59 ticks to about 4. The stale-read counts barely move (for (1, 1) from 58.59 % to about 56 %), because the read happens at the moment of acknowledgement, when the replicas outside the write quorum have usually not received the write yet, however short the delays are; rows with R + W > N stay at zero. Staleness without intersection is structural, not a matter of slow networks. (A scratch run with all deliveries 1–5 ticks during the build printed 55.91 % stale for (1, 1) and waits of 4.2 ticks for R = 3 and W = 3; it is not in the lab logs.)
    8. 

  8. When you need a single order of writes or an invariant that spans concurrent writers: unique usernames, a lock, compare-and-set, a counter that must not exceed a limit, configuration that all nodes must agree on. Leaderless stores cannot refuse the second of two concurrent conflicting writes; Raft can.

Forensic lab answer key


Observation. Leila's 18:01:10 write [A:5] {map,tent} (stove removed) and Omar's 18:02:30 write [A:4 C:1] {map,rope,stove,tent} both descend from [A:4] and not from each other: A:5 > A:4 but C:0 < C:1 R3. After the partition healed, replica A holds both as siblings (18:20:05). At 18:30:00 the application read two versions and its mergeSiblings produced {map,rope,stove,tent}, written back as [A:6 C:1], which descends from both and replaced them on every replica.


Why the lamp stayed removed. The 17:50 removal had no concurrent write: its clock [A:4] descends from [A:3], so replicas replaced the old version and no sibling with the lamp ever existed. Removal works with any merge when nothing is concurrent; the merge matters only for siblings.


Hypotheses. (1) "A replica lost Leila's write": ruled out, replica A logged [A:5] {map,tent} at 18:01:10, and replica C received it at 18:20:05 as a sibling. (2) "Omar re-added the stove": ruled out, Omar's version was derived from [A:4], which already contained the stove; he added only the rope. (3) "The merge function": confirmed: union cannot represent removal, so the stove, present in Omar's sibling, survives. The store's statement is true: the stove-bearing version was written by the application's merge at 18:30:01, and the store faithfully stored it.


A correct merge. Record removals: with an observed-remove set, Leila's removal carries the tag of the stove's add (the add made under [A:3]); Omar's sibling has the same stove tag and no new one; the merge keeps rope (new tag), map and tent, and drops the stove (its only tag was removed). Result {map,rope,tent}. A tombstone design gives the same answer: "stove removed at [A:5]" dominates "stove added at [A:3]".


How the evidence was produced. resurrect.cpp runs the store logic (vector-clock comparison, sibling keeping, union merge) on a scripted sequence of writes and a scripted partition from 18:00 to 18:20; the logs are what it printed. The fault is the application's mergeSiblings (union), described in the configuration excerpt; nothing else was injected.
