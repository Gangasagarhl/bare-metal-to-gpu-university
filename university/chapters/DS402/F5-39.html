Story hook

The book club from DS301 has grown. Its library no longer fits on one shelf, so the books live on the shelves of five friends in five towns. Long books are split into volumes, and every volume has three copies on three different shelves, because shelves get flooded and friends go on holiday. Ines keeps the catalogue: a small card box that says which volumes make up each book and whose shelf holds each copy. Nobody sends books through Ines. You ask her where volume 3 is, she answers "Kofi, Mei or Ravi", and you fetch it from whichever of them lives closest.

One week Mei is away and misses the corrections the club makes to volume 3. When she returns, her copy looks perfectly fine, but it is out of date. Ines notices, because every card in her box carries the number of the latest edition, and Mei's copy has an older number. Yet a friend who had written down "Mei has volume 3" a week earlier, and did not ask Ines again, borrows Mei's copy and reads last week's text.

This chapter is about building exactly this library out of computers: one metadata server that knows where everything is, many storage servers that hold the bytes, copies that must stay in step, and the ways readers still manage to read the wrong thing.

What you will be able to do

  • Explain the architecture of a GFS-style distributed file system: a single master holding metadata, chunk servers holding replicated chunks, and clients that send control to the master and data to the chunk servers.
  • Trace a write and a record append through leases, version numbers, the primary's ordering and the secondaries, and say which failures leave duplicates or padding in the file.
  • Explain how the master detects dead chunk servers, re-replicates chunks and rejects stale replicas, and simulate each of these in the lab.
  • Explain the MapReduce programming model and how it uses the file system's replica locations for data locality and re-execution for fault tolerance.
  • Diagnose a stale read from the logs of the master, the chunk servers and the clients.
Jargon box
Distributed file system
Simple words: one big file system whose files are spread over many computers. Analogy: the club's library spread over five friends' shelves, with one catalogue. Precise: a file system whose namespace and data are stored on multiple networked machines and accessed by clients through a protocol, usually with data replicated across machines so that files survive machine failures. D1 D2
Master (metadata server)
Simple words: the computer that knows where every piece of every file is. Analogy: Ines and her catalogue card box. Precise: in GFS, the single server that holds the file and chunk namespace, the mapping from files to chunks and the current locations of each chunk's replicas, grants leases and directs re-replication; file data never passes through it. D2
Chunk and chunk server
Simple words: a file is cut into pieces of equal size; the computers that store the pieces are chunk servers. Analogy: volumes of a long book; a friend's bookshelf. Precise: GFS divides each file into fixed-size chunks, each identified by a chunk handle assigned by the master; chunk servers store chunks as files on their local disks and serve reads and writes of byte ranges. D2
Lease (GFS)
Simple words: a time-limited permission for one copy to decide the order of changes. Analogy: Ines tells Kofi "for the next hour, you decide the order of corrections to volume 3". Precise: a grant from the master to one replica of a chunk, the primary, for a limited time; the primary assigns a serial order to all mutations of the chunk, and the secondaries apply them in that order. D2
Chunk version number
Simple words: an edition number for each piece, raised whenever writing starts again. Analogy: the edition number on each catalogue card. Precise: a counter kept by the master for each chunk and recorded by its replicas; the master increases it when it grants a new lease, so a replica that was unavailable during that grant keeps an older number and is recognised as stale. D2
Stale replica
Simple words: a copy that missed some changes. Analogy: Mei's volume 3 after her week away. Precise: a replica whose version is older than the master's current version for that chunk; the master excludes it from the locations it gives to clients and removes it later. D2
Record append
Simple words: "add this record at the end, wherever the end is", done safely by many writers at once. Analogy: several friends posting new reviews to be glued in at the back of the volume, in whatever order they arrive. Precise: a GFS operation in which the client supplies only the data; the primary chooses the offset, and the record is written atomically at least once, so retries after failures may leave duplicate records or padding that readers must skip. D2
Re-replication
Simple words: making a new copy when one copy is lost. Analogy: Ines asks Ravi to photocopy volume 3 for Tomas when Mei's house floods. Precise: the master's action of copying a chunk from a live replica to another chunk server when the number of available replicas falls below the replication target. D2
MapReduce
Simple words: a way to run one calculation over a huge data set on many computers by writing just two small functions. Analogy: every friend counts the words in the volumes on her own shelf (map), then the counts are sorted by first letter and added up by one friend per letter (reduce). Precise: a programming model and runtime in which a user-supplied map function turns input records into intermediate key/value pairs and a reduce function merges all values of each key; the runtime partitions the work, schedules it on a cluster, and handles failures by re-executing tasks. D3
Data locality
Simple words: run the work where the data already is. Analogy: the friend with the volume on her shelf counts its words; nobody posts the book. Precise: scheduling a task on (or near) a machine that stores a replica of its input, so the input is read from a local disk instead of over the network. D3

Layer 1 — the kid explanation

Analogy

A library too big for one shelf is spread over many friends' shelves. Mapping: the catalogue keeper (Ines) = the master; a friend's shelf = a chunk server; a volume of a long book = a chunk; the three copies of each volume = replicas; "for the next hour you decide the order of corrections" = a lease; the edition number on the card = the chunk version number; photocopying a volume when a shelf is lost = re-replication. You ask the catalogue keeper where things are, and fetch the books yourself.

Splitting the library this way lets the club keep far more books than one shelf could hold, and lets many friends read at once without all queueing at one house. Keeping three copies means a flooded shelf loses nothing. The catalogue keeper stays fast because she never carries books, only answers "where".

The hard parts are the moments of change. When several friends add pages to the same volume, someone must decide the order, or the three copies end up different. When a friend is away and misses changes, her copy must be recognised as old. And when a friend gets an error halfway through adding a page, she tries again, so the page may end up glued in twice. Good file systems do not pretend these things never happen; they say exactly what a reader may find, and give readers a way to cope.

Layer 2 — the student explanation

Why a distributed file system, and why this design

A file system on one machine is limited by that machine's disks, its network interface and its failures. A distributed file system spreads files over many machines so that capacity and throughput grow with the number of machines, and replicates data so that the loss of machines does not lose files D1 D6. The Google File System paper describes a design driven by its workload: component failures are treated as the normal case rather than the exception; files are large; most files are mutated by appending rather than overwriting; and high sustained bandwidth matters more than low latency for single operations D2. Every design decision below follows from those assumptions, and the chapter returns to them in Layer 3, because a different workload (many small files, random overwrites, low-latency access) leads to different decisions.

Master, chunk servers, clients

A GFS cluster has one master and many chunk servers, accessed by many clients D2. Files are divided into fixed-size chunks; each chunk has a handle assigned by the master and is stored on several chunk servers (three by default in the paper) as an ordinary local file D2. The master keeps all metadata: the namespace, the mapping from files to chunks, and the locations of each chunk's replicas D2. A client that wants to read byte range [o, o + n) of a file computes the chunk index from the offset and the fixed chunk size, asks the master for that chunk's handle and replica locations, caches the answer, and then reads directly from one of the replicas, usually the closest D2. The master is therefore on the path of every open, but not of the data: Figure 1's thin and thick arrows.

Listing 1 is a toy of exactly this structure. Its master is three C++ containers (the namespace files, the chunk table chunks, the lease state inside each ChunkInfo), its five chunk servers are ChunkServer objects with a map of chunk handle to bytes and version, and its client is a handful of functions. The chunk size is 36 bytes and records are 8 bytes, so that you can see every byte in the output; real chunk sizes are discussed in the unverified box of Layer 3.

Where the metadata lives

The master keeps metadata in memory, which makes its operations fast and lets it scan the whole chunk table in the background (for re-replication, garbage collection and balancing) D2. Changes to the namespace and the file-to-chunk mapping are recorded in an operation log that is written to disk and replicated to other machines before the master answers the client, with periodic checkpoints so that recovery replays only a short log D2. Chunk locations are deliberately not persisted: the master asks the chunk servers at startup and keeps the information current from heartbeats, because the chunk server has the final word on what is on its own disks D2. You met the operation log idea in DS302 as the replicated log; the master's log is the place where consensus (F5-19) can make the master itself fault-tolerant.

Writes: leases and the primary

Mutations of a chunk (writes and appends) must be applied to all replicas in the same order. The master grants a lease on the chunk to one replica, the primary; the primary picks a serial order for all mutations it receives, applies them in that order, and forwards them to the secondaries, which apply them in the same order D2. The lease has a timeout and can be extended while mutations continue; if the master loses contact with the primary, it can grant a new lease to another replica after the old one has expired, which prevents two primaries from ordering mutations at the same time D2. This is the fencing idea of F5-11 implemented with time, and it has the same dependency on clocks running at roughly the same rate.

The data and the control are separated: the client pushes the data to all replicas first (in the paper along a chain of chunk servers chosen by network distance, so that each machine's outbound link carries the data once), the replicas buffer it, and only then does the client send the small write request to the primary D2. Listing 1 does the forwarding in a loop over the replicas (lines 123–136) rather than as a chain.

Record append and what readers may see

With a normal write, the client chooses the offset; concurrent writers to the same region leave a mixture of their fragments. With record append, the client supplies only the data, and the primary chooses the offset (the current end of the chunk) and tells the secondaries to write at exactly that offset D2. If the record does not fit in the remaining space, the primary pads the chunk to its end on all replicas and the client retries on the next chunk D2. If any replica fails, the client retries the whole append; the replicas that succeeded the first time keep the record, so the file can contain the record more than once, and the replica that failed holds whatever was there before at that offset D2. The guarantee is that the record is written at least once as an atomic unit at an offset the system chose, not that replicas are byte-for-byte identical D2.

Step 2 of Listing 1 shows this in four lines of output. The forward of r3 to cs2 fails, the client retries, and the dump of chunk 100 afterwards shows r3 twice on cs0 and cs1 and padding followed by r3 on cs2 R1. The reader at the end of step 2 still prints each record once and reports "duplicates skipped: 1", because each record carries an identifier (r1, r2, …) and the reader skips padding and identifiers it has already seen. This is the application-side half of the contract: the paper describes writers that include checksums and unique identifiers in records so that readers can discard padding, fragments and duplicates D2.

Failures: heartbeats, re-replication, stale replicas

The master exchanges heartbeat messages with every chunk server, giving instructions and collecting state D2. When a chunk server stops answering, the master treats its replicas as unavailable, and every chunk whose number of available replicas has fallen below the target is re-replicated by instructing a chunk server to copy it from a live replica; the paper describes prioritising chunks that have lost more replicas D2. Step 3 of Listing 1 kills cs0, and after 3,020 simulated milliseconds without heartbeats the master removes it and copies chunk 100 from cs1 to cs3 and chunk 101 from cs3 to cs1 R1.

A chunk server that comes back may hold old data. Because the master increases a chunk's version number whenever it grants a new lease, and live replicas record the new number, a replica that was down during the grant reports an older version, and the master treats it as stale: it is not handed to clients and is garbage-collected D2. In step 4, cs0 returns with chunk 101 at version 1 while the master's version is 2 (granted when the old lease expired and r6 was appended), and the master deletes it; its copy of chunk 100 is current but surplus, because re-replication already restored three copies R1.

MapReduce on top of the file system

MapReduce lets a programmer express a computation over a large data set as two functions: map, applied to every input record, emits intermediate key/value pairs; reduce, applied to each intermediate key with all its values, produces the output D3. The runtime splits the input into M pieces (in practice aligned with file-system chunks) and the intermediate key space into R partitions using a partitioning function, by default a hash of the key modulo R D3. A master assigns map tasks and reduce tasks to workers. Map workers write their intermediate output to their own local disks, partitioned into R regions; reduce workers read their partition from every map worker, sort by key and call reduce D3.

Two design points connect it to the file system. First, the master schedules a map task on a machine that holds a replica of its input chunk if it can, using the replica locations that the file system's master knows, so that most input is read from local disks D3. Second, failures are handled by re-execution: a worker that stops answering the master's pings is marked failed; its in-progress tasks are rescheduled, and so are its completed map tasks, because their output lived on the failed machine's local disk; completed reduce tasks need not be re-run, because their output is in the global file system D3. Listing 2 shows both: all eight map runs read locally, and the two map tasks that worker 2 had completed are run again on worker 0 after it dies R2.

Layer 3 — the engineer's depth

The consistency model, precisely

GFS describes the state of a file region after a mutation with two words D2. A region is consistent if all clients see the same data regardless of the replica they read. It is defined after a mutation if it is consistent and clients see what that mutation wrote in its entirety. A successful mutation without concurrent writers leaves the region defined. Concurrent successful writes leave it consistent but undefined: all replicas agree, but the content may be fragments of several writes. A failed mutation leaves it inconsistent: different replicas may hold different data. Successful record appends leave defined regions interspersed with inconsistent ones (the padding and the failed attempt) D2. Compare this with the consistency models of F5-13: a GFS file is not linearizable, and the paper says so; it moves part of the work to the application (self-identifying, checksummed records; writing a file completely and then atomically renaming it) in exchange for simpler, faster servers.

The lab's chunk 100 is a concrete example of all three states at once: bytes 0–15 are defined (r1, r2 identical on all replicas), bytes 16–23 are inconsistent (r3 on two replicas, padding on the third), bytes 24–31 are defined (the successful retry), bytes 32–35 are padding on all replicas.

One master: bottleneck and single point of failure

A single master simplifies placement, re-replication and lease decisions, because one process sees everything D2. Its costs are equally clear. All metadata must fit in one machine's memory, so the number of chunks (and hence the chunk size) is bounded by it; very large chunks keep the metadata small but make small files expensive and turn popular small files into hot spots on the few chunk servers that hold them, which the paper reports and mitigates with a higher replication factor for such files D2. Every open goes through the master, so client-side caching of locations and batching of requests are essential. The master's state is protected by its replicated operation log and checkpoints; the paper also describes read-only "shadow" masters that may lag slightly D2. If you design such a system today you would replicate the master's log with a consensus protocol (DS302) and consider partitioning the metadata itself across several servers once one machine is not enough; both moves trade simplicity for scale, and both bring back the problems of F5-14.

Data integrity and garbage collection

Chunk servers verify the integrity of their own data with checksums over small blocks of each chunk, checked on every read, so that a corrupted replica is detected locally and replaced from another replica rather than returned to a client D2. Replication across machines does not protect against corruption by itself: a replica that is "present" can still be wrong. Deletion is lazy: a deleted file is renamed to a hidden name and reclaimed later by the master's background scan, and orphaned chunks (no longer referenced by any file, or stale) are deleted when chunk servers report them in heartbeats D2. The lab's step 4 shows the heartbeat-driven half: cs0's stale chunk is deleted because of what cs0 reported.

Replica placement and re-replication priority

Where replicas go decides what a failure takes away. Spreading the replicas of a chunk across racks protects against the loss of a rack (switch, power) at the cost of cross-rack write traffic; the master also balances disk utilisation and limits how many new chunks it places on one server at once D2. Listing 1's placement rule (least-loaded servers first, line 74) knows nothing about racks; the mini-project adds them. Re-replication competes with client traffic for disk and network bandwidth, so it is rate-limited and prioritised: a chunk with one remaining replica first, and chunks blocking client progress first D2. The engineering question in every incident review is the same as in F5-08: how long is the window during which a second (or third) failure loses data, and what shortens it.

Not verified — check before relying on this

The GFS paper gives concrete values that this chapter deliberately does not use: the chunk size (recalled as 64 MB), the checksum block size (recalled as 64 KB), the initial lease timeout (recalled as 60 seconds) and the default number of replicas (recalled as three). They are written here from memory and must be checked in D2 (sections on chunk size, data integrity and leases) before being quoted. The lab uses 36-byte chunks, a 10-second lease and a 3-second dead-server limit as exercise values. The design of current production systems that descend from GFS (for example the Hadoop Distributed File System, whose documentation is a tier-2 source not opened in this build) differs in names and details and must be taken from their own documentation for a recorded version.

MapReduce: stragglers, combiners and the shuffle

The total time of a MapReduce job is set by its slowest task. The paper describes "backup tasks": near the end of a phase, the master schedules duplicate executions of the remaining in-progress tasks and takes whichever finishes first, which works because map and reduce are deterministic functions of their input D3. A combiner function, run on the map worker, partially merges values with the same key before they are written (Listing 2's mapFn sums counts locally, line 43), which reduces the volume of the shuffle D3. The shuffle itself is an all-to-all exchange: every reduce partition reads a piece from every map task, M × R transfers in all. Re-execution makes the model fault-tolerant without any replication of intermediate data, at the price of recomputation; it is correct only if tasks are deterministic and their output is committed atomically (a reduce task writes a temporary file and renames it when done, which relies on the file system's atomic rename) D3.

Kleppmann places MapReduce in a family of batch-processing systems that read immutable input from a distributed file system and write new output files, comparing it with the Unix philosophy of small tools connected by files and pipes and with later dataflow engines that keep intermediate state in memory D1. The idea that survives every generation is the one in this chapter: immutable inputs, deterministic tasks, and recomputation instead of replication of intermediate state.

How the hardware actually does it

A chunk server is an ordinary machine with local disks and a network interface. Each chunk is a file in its local file system (OS304), so a "write to a chunk" is a write system call, the page cache, and eventually the disk, with exactly the durability questions of F5-12: when the primary says "applied", is the data in memory, in the page cache, or on the platter or flash? The paper's design of separate data and control flow exists because each machine's network link and disk bandwidth are finite: pushing data along a chain uses each machine's outbound link once, instead of making the client's link carry every copy D2. Data locality in MapReduce exists for the same reason: reading from the local disk avoids the network, which the paper describes as a scarce resource in its environment D3. In storage hardware terms (HW205), large sequential appends and large sequential reads are the access patterns that disks and SSDs serve best, which is another reason the design favours appends and big chunks.

Not verified — check before relying on this

Untested on real hardware: every chunk server in this chapter is an object in one process; no byte reached a disk and no message crossed a network. Real throughput, the effect of rack placement, and the time to re-replicate a failed disk depend on the disks, the network and the software version, and none was measured in this build. Any number for them must come from a named product's documentation (AH-21) or from your own measurement, labelled with the machine and the date (AH-23).

Worked example

Predict the bytes of chunk 100 on each replica after step 2 of Listing 1, then check them against the output.

  1. Records are 8 bytes each (r1:t=21;: two characters of identifier, a colon, four characters of payload, a semicolon). The chunk size is 36 bytes.
  2. r1 goes to offset 0 and r2 to offset 8 on all three replicas cs0, cs1, cs2 (all forwards succeed).
  3. First attempt of r3: the primary cs0 picks offset 16 (its current length). cs0 writes at 16; cs1 writes at 16; the forward to cs2 fails, so cs2 still has 16 bytes. The client is told "error".
  4. Retry: the primary's length is now 24, so it picks offset 24. cs0 and cs1 write at 24. cs2 is 16 bytes long, shorter than the offset, so it pads bytes 16–23 with . (line 133) and writes at 24. All three are now 32 bytes long.
  5. r4 needs 8 bytes but only 36 − 32 = 4 remain: the primary pads all replicas to 36 bytes and the append moves to a new chunk, 101.
  6. Prediction: cs0 and cs1 hold r1 r2 r3 r3 ...., cs2 holds r1 r2 ........ r3 ..... The output's chunk 100 lines match exactly R1.
  7. Space used: 3 records of useful data (24 bytes) occupy 36 bytes on each replica, so 12 of 36 bytes (one third) are duplicates or padding. With 8-byte records and 36-byte chunks the padding per chunk is at most 36 mod 8 = 4 bytes when nothing fails; the duplicate came from the failure. This is why the paper bounds record size relative to the chunk size, to keep padding waste small D2.

Where the analogy breaks


    

  • A friend who is away is plainly away. A chunk server cut off from the master may still be reachable by clients and keep serving reads (the forensic lab), so "away from the catalogue keeper" and "away from readers" are different things.
    • 

  • A photocopy of a volume is identical page for page. GFS replicas of the same chunk are not guaranteed to be byte-identical after record appends: they agree on the defined regions only (Layer 3).
    • 

  • Ines can remember a few hundred cards. The master's memory is a hard limit on the number of chunks, and that limit, not convenience, drives the large chunk size.
    • 

  • A friend asked to count words in her volume reads her own book. A MapReduce map task that is re-executed reads the input again from any replica, and its earlier output is thrown away even if the first run finished: computation is cheap to repeat, but only because it is deterministic.
    •

Transition box

Where you came from: DS302 (F5-15 to F5-21) built a replicated log with Raft, and DS301 built primary-backup replication (F5-12) and partitioning (F5-14). What carries over: a single orderer per piece of data (Raft's leader, here the lease holder), version or term numbers that expose stale participants, timeouts as failure detectors, and the replicated log, which protects the master's metadata D2. What changes: most dangerous first: the data path no longer gives every read the latest value (stale replicas, at-least-once appends, padding), so correctness depends on the application reading defensively; metadata and data are separated, so a failure can hit one without the other; and the unit of replication is a large chunk, not a log entry D2 R1. What comes next: F5-40 replaces the central master with a decentralised key-value store, where every node can find any key without asking a single catalogue keeper.

Summary


    

  • A GFS-style file system separates metadata (one master, in memory, protected by a replicated operation log) from data (chunks replicated on chunk servers).
    • 

  • Clients ask the master where chunks are and then move data directly to and from chunk servers; control and data flows are separate.
    • 

  • A lease makes one replica the primary that orders mutations; the version number raised at each lease grant exposes stale replicas.
    • 

  • Record append is atomic and at least once: retries leave duplicates and padding, and readers must skip them using record ids and checksums.
    • 

  • The master detects dead chunk servers by missed heartbeats and re-replicates chunks below the target; returning stale replicas are deleted.
    • 

  • MapReduce expresses batch computations as map and reduce; it schedules for data locality and tolerates failures by re-executing deterministic tasks.
    • 

  • Every simplification (one master, relaxed consistency, big chunks) is a deliberate trade made for one workload; a different workload deserves a different design.
    •

Answers to Check yourself


    

  1. One master (metadata), many chunk servers (data), many clients. File data passes only between clients and chunk servers (and between chunk servers during pushes and re-replication), never through the master.
    2. 

  2. Chunk locations change whenever a chunk server fails, returns or loses a disk, and the chunk server is the authority on what it actually stores; keeping a persistent copy at the master would create a second, often wrong, copy of that truth. The file-to-chunk mapping exists nowhere else, so it must be persisted (operation log and checkpoints) and replicated.
    3. 

  3. Good answers say: the primary chooses the offset and the client retries the whole append when any replica fails; replicas that succeeded on the failed attempt keep the record, so after a successful retry the record is present at two offsets on those replicas. The reader must recognise records by a unique id (and validity by a checksum) and skip duplicates and padding, or process records idempotently.
    4. 

  4. The returning replica reports a version lower than the master's current version, because it missed the lease grant at which the version was raised; the master excludes and deletes it. Raising at every write would be costly (a metadata update per write) and would not by itself help: a replica that misses one write within a lease is handled differently: the write fails, the client retries, and the primary forwards the retry to all replicas; the version guards against replicas that were absent while a whole new lease (and possibly many mutations) happened.
    5. 

  5. Bytes 0–15 defined (r1, r2 on every replica); bytes 16–23 inconsistent (cs2 holds padding where cs0 and cs1 hold r3); bytes 24–31 defined (the successful retry, identical on all); bytes 32–35 padding, consistent on all.

Forensic lab answer key


Observation. At 10:15:05.001 the report builder used its location cache (age 63 s, TTL 120 s) and read chunk 7731 from cs5 "same rack"; cs5 served version v4 at 10:15:05.003; the report was built with total=1712 R3. The master had marked cs5 dead at 10:14:41, re-replicated to cs8, and granted a new lease with version 4 → 5 at 10:14:50 to cs2, cs7, cs8; the writer's append succeeded on all three at 10:14:50.031.


Hypotheses. (1) "The writer's append was lost": ruled out, cs2, cs7 and cs8 all logged the append at v5 and the writer got "ok". (2) "The master gave out a wrong location": ruled out, the client did not ask the master at 10:15:05 (cache hit), and the master's log shows cs5 removed. (3) "cs5 was cut off from the master but not from its own rack, kept serving, and the client's cache sent it there": confirmed by cs5's heartbeat failures from 10:14:30 to 10:15:40 alongside a successful read at 10:15:05.003, and by the master deleting cs5's v4 copy as stale at 10:15:40.502.


Root cause. A stale replica on a server partitioned from the master but not from clients, reached through a client location cache that outlived the version change. The two settings: client_location_cache_ttl_s = 120 (longer than the time the master needs to detect a dead server and change versions) and chunkserver_check_lease_before_read = false (cs5 kept serving although it had not heard from the master for 35 seconds).


Fixes. Chunk server: stop serving a chunk if it has not exchanged a heartbeat with the master within a bound (self-fencing, F5-11), or include the chunk version in every read and let the client compare it with the master's version when it next talks to the master. Cost: reads fail during master-connectivity problems even when data is current. Client: shorter cache lifetime for location data, and on any suspicious read (record ids going backwards, version lower than seen before), re-ask the master. Cost: more load on the master. The application can also protect itself: the report job could record the highest record id it has seen and refuse to publish a report built from fewer records. The storage team's statement was true and irrelevant: detection and re-replication were fast, but the stale replica was still reachable.


How the evidence was produced. stale.cpp prints a scripted timeline (no random numbers): cs5's heartbeats stop reaching the master at 10:14:30 while its reads continue; the master detects it after 11 s and re-replicates; the writer appends at v5; the report builder reads through its cache at 10:15:05; cs5's link to the master is repaired at 10:15:40.
