Story hook

Analogy

Amara bakes for a school fair: 4,096 small batches, each "a scoop of this times a scoop of that". Her good measuring set has 24 marks on every scoop (F0-73). Today she has to use the camping set, whose scoops have only 11 marks, or the toy set with 4. Two separate things go wrong. Each scoop is measured coarsely: that error is fixed the moment she scoops. And the running total of all batches, if she keeps it on the same coarse scoops, loses small additions entirely once the total is large. Her trick: measure with whatever scoops she has, but write the running total in her notebook with every digit. The first error stays; the second almost disappears.

That trick is mixed precision, the way GPUs run most of today's arithmetic: inputs in FP16, BF16 or FP8, sums in FP32. This chapter measures both errors, turns them into test tolerances that can be defended line by line (the curriculum asks for exactly that in E3 and E7), and investigates a test that has passed every day for months while the kernel it checks was dropping data.

What you will be able to do

  • Compare FP32, FP16, BF16 and the two FP8 formats by precision, range and special values, and predict which values each can represent.
  • Separate the error of a reduced-precision computation into input rounding and accumulation, and bound each.
  • Derive the tolerance for a GPU reduction test against a Kahan-summed reference, and for a mixed-precision dot product against an FP64 reference (curriculum E3, E7).
  • Design a numerical test that can fail: exact integer cases, sizes that hit edge cases, and planted bugs as negative controls (the MA302 course lab).
  • Diagnose a test whose tolerance was widened until it could no longer detect a bug (this chapter's forensic lab).
Jargon box
FP8 (E4M3 and E5M2)
Simple words: 8-bit floating-point formats, with either more precision (E4M3) or more range (E5M2). Analogy: the toy scoop set: a handful of marks per scoop. Precise: 1 sign bit, then 4 exponent and 3 fraction bits (E4M3) or 5 and 2 (E5M2); unit roundoff 2−4 and 2−3. The exact special values and largest number are set by the format's specification, not by IEEE 754 (Hardware section). S2S3
Accumulator precision
Simple words: the precision in which a sum or dot product keeps its running total. Analogy: whether Amara's running total is written on a coarse scoop or in her notebook. Precise: the format of the partial sums si = si−1 + aibi; with k terms, its contribution to the error is bounded by γk(uacc) Σ|aibi| (F0-75), and the bound says nothing once k uacc ≥ 1. B1D1
Input rounding error
Simple words: the error made by storing the data in a short format before any arithmetic. Analogy: the coarse scoop itself. Precise: replacing ai, bi by fl(ai), fl(bi) with relative errors ≤ uin changes each product by at most (2uin + uin2)|aibi|; no accumulator can remove it. D1
Error budget
Simple words: a list of every source of error with a bound for each, added up into a tolerance. Analogy: "scoops: at most this much; adding up: at most that much; the reference itself: a crumb". Precise: tolerance = Σ (bound of each independent error source), each term derived from u of the format involved, the problem's size and conditioning (Σ|x|), and the reference's own error. D1U1
Negative control (in a numerical test)
Simple words: a deliberately broken version that the test must reject. Analogy: before trusting the kitchen scale, put a known weight on it. Precise: a planted fault (an off-by-one, a dropped tail) run through the same test; if the test still passes, its tolerance or its inputs are too weak to detect faults of that size. D1

Layer 1 — the kid explanation

Computers can store numbers with lots of digits or with very few. Few digits are faster and take less memory, which is why AI chips love 16-bit and even 8-bit numbers. But a number with three significant bits cannot tell 0.1 from 0.09375.

There are two places where precision can be lost. Storing the inputs short loses a little on every input. Keeping the running total short is worse: once the total is big, small additions fall off the end and are never counted. So the usual trick is short inputs, long total.

When you test such a program, you cannot ask for the exact answer. You must say how far off is acceptable, and you must be able to explain that number. If you make the allowed error bigger every time a test fails, one day it is so big that the test cannot catch anything at all.

Layer 2 — the student explanation

The formats

Listing 1 prints each format's unit roundoff u = 2−p, range and the value each stores for six inputs (run R1). Points to notice: R1

  • FP16 has u = 2−11 ≈ 4.9 × 10−4 (about 3 decimal digits) but a maximum of 65,504: 70,000 overflows to infinity.
  • BF16 has the same exponent range as FP32 (70,000 is stored as 70,144) but only u = 2−8 ≈ 3.9 × 10−3: 1000.3 is stored as 1000.
  • FP8 is coarser still: π becomes 3 (E5M2) or 3.25 (E4M3 model), and 10−5 underflows to 0 in the E4M3 model.

The model in lowp.hpp rounds to nearest, ties to even, with subnormals and overflow to infinity. Run R7 checks it against GCC's std::float16_t and std::bfloat16_t (C++23) on 200,000 values spread over many binades: zero differences. The FP8 rows rest on the model alone (see the unverified box). R7B2

Two errors, two bounds

For a dot product s = Σaibi computed from rounded inputs with an accumulator of unit roundoff uacc: D1B1

|ŝ − s| ≤ (2uin + uin2) Σ|aibi| + γk(uacc) Σ|fl(ai)fl(bi)|

The first term is the input rounding error; the second is the accumulation error with the recursive-summation bound of F0-75 (Σ of the rounded products, which differs from Σ|aibi| by a factor 1 + O(uin)). Run R2 measures both parts separately for k = 4,096: R2

  • FP16 inputs, FP32 accumulator: total 4.2 × 10−3, of which 4.1 × 10−3 is input rounding and 3.4 × 10−5 accumulation. The accumulator is irrelevant; the inputs set the accuracy.
  • FP16 inputs, FP16 accumulator: total 0.10, now dominated by accumulation (0.106). The bound is useless here: k uacc = 4096 × 2−11 = 2 ≥ 1.
  • BF16 inputs, BF16 accumulator: 1.86, more than half the true result 3.20.
  • FP8 inputs, FP32 accumulator: 0.090 (E4M3 model) and 2.89 (E5M2), all from input rounding.

The measured errors are far below the bounds (input part: 4.1 × 10−3 against a bound of 1.0 for FP16), because rounding errors of random data partly cancel. A bound is what a test can rely on; a typical value is not. R2B1

Tolerances that can be defended

The curriculum's acceptance tests say what is required, verbatim: for E3, "Sum of 2^28 floats matches a Kahan-summed CPU reference within your stated tolerance; integer sums are exact."; for E7, "Error versus an FP64 reference within a tolerance justified from FP16/BF16 input rounding." A tolerance meets that only if each term in it can be traced to a format, a size and a bound. U1

For a reduction kernel of depth d (the longest chain of roundings, F0-75) against a Kahan reference in double: tol = γd(ufloat) Σ|xi| + 4udouble Σ|xi|. The first term is the kernel's worst case; the second is a generous margin for the reference's own error. For E7, the input term above with uin of FP16 or BF16, plus the FP32 accumulation term, plus the FP64 reference's error. D1B1

A test must be able to fail

Listing 4 (the MA302 course lab) tests a reduction three ways and proves each way with negative controls: two planted bugs, one that drops the last n mod 256 elements and one that drops the last element. Run R4: R4

  • The correct kernel passes everything; its largest error is 3.2 % of the tolerance.
  • The tolerance test alone misses the "drops tail" bug at n = 220 + 3: three missing values in [0, 1) are only 24 % of a tolerance of 5.2. The exact integer test (values i mod 7, every partial sum an integer below 224, so float addition is exact in any order) catches it.
  • No test can catch "drops tail" at n = 256 or 65,536: those sizes have no tail. Only sizes that are not multiples of the block size exercise that code.
  • The exact test misses "drops last" at n = 1,000,000, because the dropped value is 999,999 mod 7 = 0. Two kinds of data and several sizes are needed.

Layer 3 — the engineer's depth

Probabilistic bounds. The γk bound grows like ku, but for rounding errors that behave like independent random variables the error grows like √k u with high probability. Such bounds explain why measured errors sit orders of magnitude below worst case (run R2) and allow tighter tolerances when a small, quantified chance of a false failure is acceptable. A test tolerance based on them must state that probability. B4B1

Scaling. FP16's narrow range and FP8's tiny one make overflow and underflow a design problem: values are multiplied by a scale factor before conversion and divided after, per tensor or per block, so that they land in the format's best range. In the formats table, 70,000 overflows FP16 and 10−5 underflows the E4M3 model; scaled by 2−4 or 210 they would not. R1S3

Mixed-precision solvers. Iterative refinement (F0-77) can factor a matrix in FP16 or FP32 and refine in FP64, recovering FP64 accuracy when κ(A) ulow is well below 1 (F0-78). The condition number decides whether the cheap precision is usable. B4

Contraction. A compiler may fuse a × x + b into one FMA with a single rounding. That changes results (usually for the better) and therefore changes what "bitwise equal to the CPU" means. Run R8 shows nvcc generating fma.rn.f32 for a * x[i] + b by default and mul.rn.f32 plus add.rn.f32 with --fmad=false; nvcc's own help text says the option enables contraction and that --use_fast_math implies it. R8






How the hardware actually does it


GPUs store and move FP16, BF16 and FP8 data at half or a quarter of FP32's bytes, and their matrix units multiply small tiles of such inputs and add the products into wider accumulators (HW301). Listing 3 is a plain FP32 reduction kernel: its PTX (run R9) contains only add.f32 instructions, one for the grid-stride loop and one for the tree, so its addition order is exactly the one modelled by reduce_model.hpp, with no contraction to account for. Not verified — check before relying on this

FP8 details. This course's E4M3 model is IEEE-like (largest value 240, top exponent reserved for infinity and NaN). The 8-bit floating-point specification published through the Open Compute Project (OFP8) is reported to define E4M3 differently: no infinities, a single NaN pattern per sign, and a largest finite value of 448; and conversions may saturate instead of overflowing. None of this was checked in this build. Read OFP8 (S2) and the FP8 paper (S3) for the version in your dossier and correct kE4M3 in lowp.hpp before using its numbers.


Other formats and units. TF32 (a format with FP32's exponent and a 10-bit fraction used by NVIDIA matrix units), the BF16 definition in Intel's BFLOAT16 white paper S4, which input and accumulator precisions each GPU's matrix instructions support, and whether those units round their internal sums exactly as an FP32 add does, were not checked. Read the CUDA C++ Programming Guide (warp matrix functions), the PTX ISA and the AMD ISA guides named in curriculum E7 for the versions in your dossier.

Where the analogy breaks


    

  • A coarse scoop is coarse everywhere; a float is coarse relative to its size. FP16 represents 0.001 to about 3 digits and 60,000 to about 3 digits, but not 70,000 at all: range limits have no equivalent on a scoop. R1
    • 

  • Amara's notebook is exact; the FP32 accumulator is not. It is only 213 times finer than FP16, so for very long sums or catastrophic cancellation it matters again (FP16 inputs with FP32 accumulation still have an accumulation part of 3.4 × 10−5). R2
    • 

  • Scoop errors are visible; tolerance errors are silent. A tolerance that is too loose produces no symptom at all until something else fails (forensic lab). R5
    • 

  • Real ingredients do not come with known totals. Tests can choose data with exactly known sums (integers); real workloads cannot, which is why both kinds of test are needed. R4
    •

Expected observations


Your bug is caught by at least one test at some size; if it is not, the sizes or data are too narrow. With more blocks the depth is dominated by the 1,023 in-order partial additions, so the tolerance gets looser, which is a reason to reduce the partials with a tree too. Every case of Listing 2 passes its derived tolerance with a large margin; skipping one term of size about 0.25 fails cases whose tolerance is below that. On a GPU, the bitwise comparison is the prediction this chapter could not check.

Summary


    

  • FP16 trades range for precision against BF16 (u = 2−11 against 2−8); FP8 has u of 2−4 or 2−3.
    • 

  • Reduced-precision error = input rounding + accumulation; a wide accumulator removes only the second (run R2).
    • 

  • A tolerance is an error budget: γdepthΣ|x| for the kernel plus the reference's error (E3); input rounding from uin plus accumulation (E7).
    • 

  • A test must be shown to fail: exact integer sums, sizes with and without tails, planted bugs (run R4).
    • 

  • A tolerance widened to stop failures can hide a lost tail of 64 values in a million (run R5).
