Story hook

Analogy

The street's bake sale ends and three friends count the coins. Hana counts them one by one into a single big jar, reading the jar's scale after each coin. Jamal makes small piles of ten, then piles of piles. Amara counts like Hana, but on a notepad she writes the little bits the jar's coarse scale could not show and adds them back as she goes. They get three slightly different totals. Nobody stole anything. The totals differ because the order of adding, and what each method throws away, differ.

A sum of a million floats behaves exactly like this, and a GPU always counts like Jamal. This chapter measures how much each order loses, derives a bound for each, and turns the bound into a test tolerance, so that a test comparing a GPU sum with a CPU sum fails only when there is a bug. Its forensic lab is a test that fails every Tuesday although nothing is broken.

What you will be able to do

  • Measure the error of summing 220 floats in different orders against a reference (the MA302 lab).
  • Bound the error of any summation order by its depth: |error| ≤ γdepth Σ|xi|.
  • Implement Kahan (compensated) summation and explain why compiler flags can silently remove it.
  • Choose and justify a test tolerance for a sum computed in a different order, such as a GPU reduction, against a Kahan-summed reference (curriculum E3).
  • Diagnose a flaky test that compares two correct sums with an unjustified tolerance (this chapter's forensic lab).
Jargon box
Recursive summation
Simple words: adding numbers one after another into one running total. Analogy: Hana's single jar. Precise: s0 = 0, sk = fl(sk−1 + xk); the first input passes through n − 1 roundings, so |error| ≤ γn−1 Σ|xi|. B1
Pairwise summation
Simple words: adding neighbours in pairs, then pairs of pairs, until one number is left. Analogy: Jamal's piles of piles. Precise: a balanced binary tree of additions with depth ⌈log2 n⌉, so |error| ≤ γ⌈log2 n⌉ Σ|xi|. B1
Depth (of a summation order)
Simple words: the largest number of additions any one input goes through. Analogy: how many times the first coin was re-counted on its way to the total. Precise: the length of the longest path from an input to the result in the tree of additions; every order satisfies |error| ≤ γdepth Σ|xi| (this course's working rule, from the bound per input in B1). B1D1
Kahan summation (compensated summation)
Simple words: a running sum that also keeps track of what each addition rounded away and puts it back. Analogy: Amara's notepad of crumbs. Precise: keeps a correction c: y = xk − c; t = s + y; c = (t − s) − y; s = t. Its error is bounded by (2u + O(nu2)) Σ|xi|, nearly independent of n. B1S2
Condition number of a sum
Simple words: how much a sum magnifies small relative changes in its terms. Analogy: counting the coins of two people who owe each other almost the same amount: a tiny counting slip is a big part of the small difference. Precise: κ = Σ|xi| / |Σxi|; relative errors of order u in the terms can produce a relative error of order κu in the sum. κ = 1 for terms of one sign. B1
Test tolerance (justified)
Simple words: the largest difference from the reference that a test accepts, with a reason for its size. Analogy: "the count may be off by at most the crumbs of 166 scoops", not "off by a bit". Precise: a bound tol(n, data) derived from the computation's error analysis (for example γdepth Σ|xi| plus the reference's own error), such that a correct implementation can never exceed it and a wrong one usually does. The SP101 entry "Floating-point tolerance" is the general idea; this chapter makes its size derivable. B1U1

Layer 1 — the kid explanation

When you add numbers on paper, the order does not matter: 1 + 2 + 3 is 3 + 2 + 1. On a computer it can matter, because every addition rounds (F0-74), and the roundings depend on what is being added at that moment. So two correct programs that add the same million numbers in different orders can print slightly different totals.

Some orders are better than others. Adding into one running total, like Hana, means the first coins are counted again and again inside a growing total, and each time a little is lost. Making piles, like Jamal, keeps the totals small for longer and loses less. Writing down the crumbs, like Amara, loses almost nothing.

This matters most when a test compares two programs. If a GPU adds in piles and the CPU adds one by one, their answers differ a little even when both are right. The test must allow for that difference, and the allowance must be worked out, not guessed.

Layer 2 — the student explanation

Bounds for three orders

From the standard model (F0-74), every input of a summation tree is multiplied by one factor (1 + δ) per addition it passes through. With the γ notation this gives, for any order, |ŝ − s| ≤ γdepth Σ|xi|. B1D1

How Kahan's correction works

In t = s + y with |y| ≤ |s|, the low bits of y fall off the end of t. Then t − s is exact (the two are close; Sterbenz's lemma from F0-74), so (t − s) − y is exactly the negative of what was lost. The next iteration subtracts it from the next input. Listing 2 makes the effect obvious: one 1.0 followed by a million copies of 10−8. In float, 1 + 10−8 rounds back to 1 (10−8 is less than half of ulp(1) = 1.19 × 10−7), so the forward loop returns exactly 1, losing the whole 0.01; pairwise and Kahan return 1.00999999 (run R2). B1R2

From a bound to a tolerance

To test a sum computed in order A against a reference, accept the result if

|ŝ_A − ŝ_ref| ≤ γ_depth(A) · Σ|x_i| + err_ref

where err_ref bounds the reference's own error. With a Kahan-summed double reference, err_ref is about 2udoubleΣ|x| ≈ 2.2 × 10−16Σ|x|, negligible next to float errors. Three rules follow. (1) The reference must be more accurate than the thing tested, or the test measures the reference's error; a plain float loop is a bad reference (the forensic lab). (2) The tolerance scales with Σ|x|, so it is relative to the data, not a constant. (3) A correct implementation can never fail, because the bound is a theorem; how often a wrong one fails is a separate question, answered by negative tests in F0-80. B1D1U1

Layer 3 — the engineer's depth

The bound per input. The exact statement behind the depth rule is that ŝ = Σ xi(1 + θi) with |θi| ≤ γdi, where di is the number of additions on input i's path. Bounding every di by the maximum gives the depth rule; keeping the di gives a sharper bound when inputs of very different size sit at different depths. This is why the order of a plain loop matters: the first inputs sit at depth n − 1, the last at depth 1. B1

Kahan's limits. The compensated bound is (2u + O(nu2)) Σ|xi|: excellent, but still proportional to Σ|xi|, so an ill-conditioned sum (κ large) is still inaccurate relative to its result. Variants (Kahan–Babuška/Neumaier) also handle |y| > |s|; doubly compensated and exactly rounded summation algorithms exist when even that is not enough. For test references, Kahan in double, as the curriculum's E3 asks, is far more accurate than any float order under test. B1U1

Reproducibility versus accuracy. A GPU sum's order depends on the launch configuration. If the grid size is derived from the device (for example from its number of multiprocessors), the same program sums in a different order on a different GPU and prints different last digits. Sums that use atomic additions in arbitrary order differ even between runs on the same GPU. Both are correct within the bound. Bit-reproducible results need a fixed order (fixed grid, fixed tree) or special reproducible-summation algorithms; they are a design requirement to state, not a default to expect. B1B4

Not verified — check before relying on this

The statements that floating-point atomic additions on GPUs complete in an unspecified order (so that repeated runs can differ) and the names of library routines that offer deterministic or reproducible reductions (for example in CUB or rocPRIM) were not checked in this build. Read the CUDA Programming Guide (atomic functions) and the CUB and rocPRIM documentation for the versions in your dossier.

Compilers and order. In ISO C++ mode the compiler must keep the written order of floating-point additions. Options such as GCC's -ffast-math allow reassociation, which is how a vectorised loop gets several partial sums (SP302 F2-53), and which can also delete Kahan's correction entirely, because in exact arithmetic (t − s) − y is zero. The run below shows exactly that on this machine: with -O2 Kahan returns 1.00999999; with -O2 -ffast-math it returns 1, as bad as the plain loop (run R5). B3R5




How the hardware actually does it


The hardware adds two numbers at a time; "the order of a sum" is decided entirely by software. On a CPU, a scalar loop adds in sequence with one addss per element (F0-73), while a vectorised loop keeps one partial sum per SIMD lane and combines them at the end, which is a different order (SP302). On a GPU, thousands of threads each keep a partial sum and the block combines them through shared memory in a tree, as in Figure 2; F0-80 compiles such a kernel with nvcc and shows the add.f32 instructions it generates. B4U1

Worked example


Set the tolerance for a GPU sum of n = 220 floats in [0, 1), 128 blocks of 256 threads.


    

  1. Depth: each thread handles n / (128 × 256) = 32 elements, a chain of 31 additions after the first; the block tree has log2 256 = 8 levels; the 128 block results are added in a chain of 127. Depth = 31 + 8 + 127 = 166.
    2. 

  2. Factor: γ166 = 166u / (1 − 166u) with u = 2−24: 166 × 5.96 × 10−8 ≈ 9.89 × 10−6; the denominator changes it only in the 6th digit.
    3. 

  3. Scale: all terms are positive, so Σ|xi| = Σxi ≈ 524,290 (about n/2).
    4. 

  4. Tolerance: 9.89 × 10−6 × 524,290 ≈ 5.19. Add the reference's error, about 2 × 1.1 × 10−16 × 524,290 ≈ 10−10: negligible.
    5. 

  5. Compare: the kernel's measured error (run R1, 128 blocks) is 1.66 × 10−7 × 524,291 ≈ 0.087, about 60 times below the tolerance. A correct kernel passes with a wide margin; the forensic lab shows what a wrong tolerance does instead.
    6.

Where the analogy breaks


    

  • Coins are whole; floats are not. Counting coins one by one is exact; only the jar's coarse scale in the story makes it lossy. Real integer sums are exact in any order (F0-80 uses that for an exact test); float sums are not. D1
    • 

  • Jamal's piles are always better; pairwise is not always the most accurate. Pairwise has the smallest bound of the tree orders, but a particular data set can come out better in another order (run R1, mixed data: the GPU model with depth 166 was three times more accurate than pairwise with depth 20). Bounds rank worst cases, not every case. R1
    • 

  • Amara's notepad is never thrown away; Kahan's can be. An optimising compiler that is allowed to reassociate removes the correction, because in exact arithmetic it is zero (run R5). R5
    • 

  • Nobody at the bake sale counts in parallel by accident. A GPU's order is set by its launch configuration, which can change with the device; the kitchen has no such hidden dependence. D1
    •

Method hints


Do not argue from the CPU number as if it were the truth: compute an accurate reference first (Kahan in double over the same data). Then compare each result's error with the bound for its own depth. A bug would produce errors far beyond the bound, or errors that do not grow like the bound.

Summary


    

  • A float sum's result depends on the order of additions; correct programs can disagree in the last digits.
    • 

  • Any order obeys |error| ≤ γdepth Σ|xi|: depth n − 1 for a loop, log2 n for pairwise, 166 for the GPU-style order with n = 220 and 128 blocks.
    • 

  • Kahan summation's bound is about 2u Σ|xi|, independent of n; fast-math flags can delete it.
    • 

  • Ill-conditioned sums (Σ|x| ≫ |Σx|) lose digits in every order.
    • 

  • Test a sum against a Kahan-in-double reference with a tolerance derived from depth and Σ|x|; never against a plain float loop with a guessed constant.
