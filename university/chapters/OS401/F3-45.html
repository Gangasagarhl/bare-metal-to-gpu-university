Story hook

After term's tests, the library's safe order works, but every morning after a power cut someone still has to walk the shelves and fix the free-place chart. Ms Okafor wants mornings without that walk. She starts a day book at the desk. Before she touches a shelf, a card or the chart, she copies the new card and the new chart page into the day book, and when the entry is complete she draws a tick under it. Only then does she go and change the real card and chart.

After a power cut, the rule is simple. Open the day book. Every entry with a tick is copied out again onto the cards and the chart, whether or not that had been done before. Every entry without a tick is ignored. The walk around the shelves is no longer needed.

One evening the porter, in a hurry, carries the tick to the desk before the pages it belongs to. The power goes. In the morning, the day book shows a ticked entry, but the pages above the tick are last week's. Following the rule, the librarian copies last week's pages onto this week's cards. This chapter builds the day book (a journal that Linux's tools can read), and its forensic lab is that hurried evening.

What you will be able to do

  • Describe the JBD2 on-disk format: journal superblock, descriptor blocks with tags, logged block copies with escaping, commit blocks, revoke blocks, sequence numbers and the circular log.
  • Implement replay at mount (scan, collect committed transactions, apply revokes, write in place, mark the log empty) and check it against e2fsck's replay of a journal written by e2fsprogs.
  • Implement ordered-mode transactions with the correct flush order (data and log, flush, commit, flush, checkpoint, flush, log reset) under the F3-44 writer.
  • Pass the FS2 acceptance test: the FS1 harness with zero repairs in 500 runs, with both e2fsck and your own recovery as the replayer.
  • Diagnose a lost-after-power-cut report from a write-stream recording, by finding the missing flush before the commit block.
Jargon box
JBD2
Simple words: the journal format and code that ext3 and ext4 use on Linux. Analogy: the day book's standard layout, so any librarian can read it. Precise: Journaling Block Device version 2, Linux's generic block-level journal layer; its on-disk format (inside an ext3/ext4 file system, usually in inode 8) is shared by the kernel and by e2fsprogs. D1
Journal superblock
Simple words: the first block of the journal, saying how big it is and where the log currently starts. Analogy: the day book's cover page with a bookmark. Precise: a block with the JBD2 magic number, block type 3 or 4 (v1/v2), journal block size and length, the first usable log block, the sequence number expected next (s_sequence) and the log start (s_start, 0 meaning the log is empty), plus feature flags and a UUID. D1
Descriptor block
Simple words: a journal block that lists which file-system blocks the following log blocks are copies of. Analogy: the line in the day book that says "next pages: card 12, chart page 3". Precise: a block of type 1 with the transaction's sequence number, followed by tags; each tag holds a target block number and flags (escaped, same UUID, last tag), and the first tag carries a 16-byte UUID. D1
Commit block
Simple words: the block that says "this transaction is complete". Analogy: the tick under a finished entry. Precise: a block of type 2 with the transaction's sequence number (and optionally a checksum and a time stamp); recovery replays a transaction only if its commit block is found. D1
Revoke block
Simple words: a note in the journal that says "do not replay older copies of these blocks". Analogy: "ignore earlier entries about card 12: that card was thrown away and the slot reused". Precise: a block of type 5 listing block numbers; during replay, a logged copy of a listed block from a transaction with a sequence number not later than the revoke's is skipped, so a block freed and reused for data is not overwritten by stale metadata. D1
Escaping
Simple words: hiding a data block that happens to look like a journal block, so recovery does not mistake it. Analogy: crossing out a tick that appears by accident on a copied page. Precise: if a logged block begins with the JBD2 magic number, its first four bytes are written as zero and its tag gets the escape flag; replay restores the magic number. D1
Checkpoint
Simple words: writing the journaled blocks to their real places, after which their space in the journal can be reused. Analogy: copying the day book's pages onto the real cards and then turning the page. Precise: writing a committed transaction's blocks in place, making them durable, and then advancing s_start (or setting it to 0) in the journal superblock so that recovery no longer needs that part of the log. D2
Replay (recovery)
Simple words: after a crash, redoing every complete transaction from the journal. Analogy: copying every ticked entry onto the cards again. Precise: scanning the log from s_start for blocks with the expected sequence numbers, collecting transactions that end in a commit block, applying revokes, writing the logged copies to their targets, flushing, and marking the log empty; it is idempotent. D1
needs_recovery
Simple words: a flag in the file system's superblock that says "the journal may hold work that has not been replayed". Analogy: a sign on the desk: "read the day book before opening". Precise: the ext3/ext4 incompatible feature flag (0x4) set while the file system is mounted with a journal and cleared after a clean unmount or a replay; tools that cannot replay must refuse to mount. D1

Layer 1 — the kid explanation

A day book makes a big job safe. First write everything you are going to change into the book. Then draw a tick. Then do the real changes. If the lights go out, read the book: do every ticked job again, skip every job without a tick.

The tick must be the last thing written. If the tick gets into the book before the pages above it, a power cut can leave a tick under old pages, and the rule then copies old pages over new cards. That is why the librarian waits until the pages are really in the book before drawing the tick.

Layer 2 — the student explanation

ext3 is ext2 plus a journal: an area of the disk (in the lab, the 1 MiB file of inode 8) where changes are written first. A transaction groups the metadata blocks of one or more operations. To commit it, the file system writes a descriptor block listing the targets, the new copies of those blocks, and finally a commit block. Once the commit block is on the medium, the transaction is durable, and the blocks can be written to their real places (the checkpoint) at leisure. D1 D2

After a crash, recovery reads the journal superblock, starts at s_start, and walks the log while it finds journal blocks with the expected sequence number. Each transaction with a commit block is replayed: its copies are written over their targets. Transactions without a commit block are ignored. Then the log is marked empty. Replay is idempotent: doing it twice gives the same disk, so a crash during recovery is harmless. D1

Ordered mode adds one rule for file data: data blocks that a transaction's metadata makes reachable are written in place before the commit block. The F3-44 writer already separates data writes from metadata writes, so the journal only has to send data straight to the disk and keep metadata in the transaction. D1

The flush order is: data blocks and log blocks, flush, commit block, flush, checkpoint, flush, then mark the log empty. FS2 asks that, with this journal under the writer, the FS1 harness finds a clean file system after replay in all 500 runs, and that journals are interchangeable with Linux: theirs replayed by you, yours replayed by them. In this build "them" is e2fsprogs: debugfs writes a journal and e2fsck replays ours. C1 R3

Layer 3 — the engineer's depth

The format, field by field

Every JBD2 metadata block begins with a 12-byte header: magic 0xC03B3998, block type, sequence number, each a big-endian 32-bit value. The journal superblock (type 4 for version 2) continues with the journal's block size, total length in blocks and first log block, then s_sequence (the first sequence number expected in the log) and s_start (the log block where it begins; 0 = empty). After an errno field come three feature words (compatible, incompatible, read-only compatible) at offsets 36, 40 and 44, and the journal's UUID at 48. The lab's listing accepts only the incompatible "revoke" feature for reading and writes none, which matches the journal that mke2fs 1.47.0 made in this build ("Journal features: (none)"). D1 R2

A descriptor block (type 1) is followed by tags. Without the 64-bit and checksum features, a tag is 8 bytes: a 32-bit target block number, a 16-bit checksum field (unused here) and 16-bit flags: 1 = escaped, 2 = same UUID as the previous tag, 8 = last tag in this descriptor. A tag without "same UUID" is followed by 16 bytes of UUID, which in practice means the first tag. Each tag corresponds, in order, to the next log block after the descriptor. A transaction larger than one descriptor's capacity uses several descriptors before its commit block. D1

A commit block (type 2) can carry a checksum type and checksum of the transaction, and a commit time; the lab writes the time only. A revoke block (type 5) holds, after the header, the number of bytes used and a list of 32-bit block numbers. During replay, a logged copy is skipped if its target was revoked by a transaction with a sequence number at least as large as the copy's. D1

The offsets, type numbers and tag flags above were written from the author's memory of the Linux kernel documentation "ext4 Data Structures and Algorithms" (journal section), which was not opened in this build. They are confirmed here only for the subset the lab exercises: a journal written by debugfs 1.47.0 (two transactions with a revoke) is read by our recovery code exactly as e2fsck replays it R3, and journals written by our code are accepted and replayed by e2fsck and listed by debugfs logdump R4 R6. Not exercised at all: 64-bit block numbers in tags, the checksum features (v2, v3, commit-block checksums), asynchronous commit, fast commits, multiple descriptors per transaction, a log that wraps around, and the escape path with real data. Read the document before adding any of them.

Recovery, as Listing 1 does it

Recovery reads the superblock; refuses features it does not know; and if s_start is 0, clears needs_recovery and stops. Otherwise it walks from s_start with the expected sequence number s_sequence. A block that lacks the magic number or carries a different sequence number ends the log; this is what makes old leftovers in the circular log harmless, as long as sequence numbers keep increasing. Descriptor tags are collected as "pending"; revokes as "pending revokes"; a commit block moves both into the committed set and increments the expected sequence number. Then every committed copy is written to its target, oldest transaction first, unless revoked by a later or equal sequence; the escape flag restores the magic number. Finally the superblock's s_sequence is set past the last replayed transaction, s_start to 0, and needs_recovery is cleared, with a flush before and after. D1

The real JBD2 recovery runs three passes (scan, revoke, replay); Listing 1 folds them into one scan and one replay loop over a small journal. The order matters: if revokes were applied while scanning without remembering their sequence numbers, a copy logged by a later transaction after the block was reused as metadata again would be wrongly skipped. D1

Writing transactions

JournalStore implements F3-44's Store. A metadata write is kept in memory in the current transaction (a later write of the same block replaces the copy); a data write goes straight to the device; order() does nothing, because the whole transaction becomes durable at once; sync() commits. The workload calls a commit after every operation, so each operation is one transaction. commit() then does, in this order: write the journal superblock with s_start = first log block and the new sequence; write the descriptor and the copies (escaping any copy that begins with the magic number); flush; write the commit block; flush; checkpoint every block in place; flush; write the journal superblock with s_start = 0 and the next sequence; flush. R5

The first flush covers both the data blocks (written earlier by the operation) and the log blocks: that is ordered mode. The second makes the commit durable before any checkpoint write, so a checkpoint never lands for a transaction that recovery would ignore. The third and fourth make the checkpoint durable before the log is declared empty and reused. In exchange, the in-place writes need no ordering among themselves at all: a crash in the middle of a checkpoint is repaired by replay. D2

This design is deliberately simpler than Linux's. Linux batches many operations into one transaction, commits on a timer or on fsync, lets several committed but not yet checkpointed transactions share the circular log, and checkpoints lazily. Two consequences matter for your kernel. First, with lazy checkpoints, revoke records become necessary: if a metadata block is freed and reused for file data while an older transaction that logged it is still in the log, replay would overwrite the data, unless the block is revoked. The lab's journal never needs revokes because it empties the log after every transaction. Second, a transaction must never be larger than the free log space; the lab simply refuses. D1 D2

Note

Notice the cost difference with F3-44. The same 300-operation workload issued 18,456 block writes and 596 flushes with careful ordering, and 7,853 block writes and 1,202 flushes with the journal (4 flushes per transaction, one transaction per operation) R5 R4. Fewer writes, because the careful writer flushes and rewrites shared blocks such as the superblock and group descriptor many times per operation; more flushes, because of one-transaction-per-operation. Batching operations into one transaction, as Linux does, is what makes journaling cheap.

What the tests show

The lab runs the F3-44 harness with two recoveries per crash image. Path A: e2fsck -fy replays the journal (it prints "recovering journal") and would repair anything else, then e2fsck -fn must be clean. Path B: our recover, then e2fsck -fn must be clean and every promised file must have its bytes. FS2's acceptance asks for "no repairs needed in all 500 runs". With random cut points, our recovery replayed a committed transaction in 120 runs (in the others, the cut fell where the log was empty or the transaction uncommitted); because random cuts rarely hit the critical window right after a commit, the lab adds 200 cuts placed right after a commit-block write, of which 99 replayed. Both sets: zero repairs, zero unclean checks, zero lost files. R7 R8

The cross-check with e2fsprogs covers FS2's interchange clause as far as this container allows. debugfs 1.47.0 can open a journal, write blocks into it and commit (jo, jw, jc), including a revoke; logdump lists what it wrote. Image A is replayed by e2fsck, image B by our code; blocks 300 to 302 agree, block 301 keeps its old contents in both because the second transaction revoked it, and our recovery reports "2 transaction(s) replayed, 2 block(s) written, 1 revoked". R3

How the hardware actually does it

JBD2's commit is where the device's flush semantics meet the file system. Linux traditionally issues the commit block as a write with "preflush" and FUA semantics: flush the cache before writing it (covering data and log blocks) and make the commit block itself durable before completion, which removes one round trip compared with write, flush, write, flush. With the asynchronous-commit option and a commit checksum, the first flush is dropped: a commit block that lands without its log blocks fails the checksum and is ignored. F3-43's model showed the limit of that trade: the checksum covers the log, not ordered-mode data. D1 D3 R1

Not verified — check before relying on this

Untested on hardware. The description of Linux's preflush/FUA commit and of the asynchronous-commit option is from memory and was not checked against the kernel source or documentation in this build. Check the Linux kernel's block-layer documentation on cache flushes and FUA ("writeback cache control") and the jbd2 commit code of the kernel version you compare with. Whether your device honours FUA or emulates it with a flush is a property of the device and driver.

Safety

A journal replay writes blocks wherever the log says. A bug in recovery (wrong target numbers, a wrong sequence check) can destroy a file system in one pass. Test on image copies in QEMU, never on a disk you need, and keep the image from before the replay so you can compare.

Worked example

Follow one transaction through the stream, using showj, which names each write by its role (the journal is located through inode 8 of the image) R6:



Read it as the commit sequence of Layer 3. Records 122–125 are the end of transaction 6's copies, 126 the flush, 127 the commit block of sequence 6, 128 the flush, 129–132 the checkpoint of blocks 66, 2, 1 and 69, 133 the flush, 134 the journal superblock with s_start 0 and the next sequence 7, 135 the flush. Then operation 7 begins: records 136–142 write file data in place (blocks 1253–1260, except 1256, which is a directory block and therefore metadata), 143 sets s_start 1 for the new transaction, 144–149 the descriptor and five copies, 150 the flush, 151 the commit block of sequence 7, 152 the flush.


Now place cuts. A cut after record 143 with the superblock landed: recovery starts at block 1, finds transaction 6's old descriptor with sequence 6, but expects 7, so the log ends immediately: nothing is replayed, and the data blocks written in place are simply not referenced by anything durable (leaks are impossible too, since no bitmap changed in place). A cut after record 151 with the commit landed: the flush at 150 guarantees blocks 144–149 are on the medium, so replay writes exactly transaction 7. A cut after 152: the same, durably.

Where the analogy breaks


    

  • A librarian reading the day book can see that a page is from last week. Replay cannot: it trusts the descriptor's list and copies whatever bytes sit in the slots. Only sequence numbers in headers, flush order and (optionally) checksums protect it.
    • 

  • The day book in the story has a fresh page for every entry. The journal is a ring of a fixed number of blocks, constantly overwritten; old entries are always lying around, which is exactly what makes the missing flush dangerous.
    • 

  • Copying an entry twice does no harm to a card. That is true of replay too (it is idempotent), but only because JBD2 logs whole block images; a journal of operations ("add 1 to the free count") would not be idempotent without extra care.
    • 




Common mistakes and debugging


    

  • Little-endian journal fields. ext2 is little-endian, JBD2 big-endian. A recovery that reads s_start little-endian sees a huge number and either crashes or reads garbage. debugfs logdump on your image is the quickest check.
    • 

  • Forgetting the UUID after the first tag. The next tag is then read 16 bytes too early; recovery replays copies onto random block numbers.
    • 

  • Not escaping. A file data block that begins with 0xC03B3998 (rare, but test it) ends the scan early or is parsed as a descriptor.
    • 

  • Reusing log space before the checkpoint is durable. If s_start is advanced (or set to 0) before the in-place writes are flushed, a crash loses the transaction both in place and in the log.
    • 

  • Leaving needs_recovery set or clearing it too early. Set it at mount before the first transaction; clear it only after the log is empty and flushed. e2fsck will replay (or complain) if it is left set.
    • 

  • Testing only random cuts. The lab's 500 random cuts replayed a transaction in only 120 runs; the bug of the forensic lab shows up mostly in cuts right after a commit block. Add targeted cut points.
    •

Summary


    

  • JBD2: a journal superblock (sequence, start), descriptor blocks with tags, logged copies (escaped if needed), commit blocks and revoke blocks, all with big-endian headers.
    • 

  • Recovery replays transactions that end in a commit block, in sequence order, skips revoked copies, then empties the log and clears needs_recovery; it is idempotent.
    • 

  • Commit order: data and log, flush, commit, flush, checkpoint, flush, empty the log, flush.
    • 

  • With the journal, the FS1 harness found no repairs in 500 random and 200 commit-point cuts, with both e2fsck and our code as replayers.
    • 

  • Without the flush before the commit, replay copied a stale journal slot (an old commit block) over an inode table block: fsynced files lost.
    • 

  • Interchange was checked against e2fsprogs only; the Linux-kernel test remains to be done.

  1. Transaction 9 (3 copies) is replayed. Transaction 10 has a descriptor and copies but no commit block: ignored. The scan stops at the block with sequence 8 because it expects 10 (after replaying 9's commit, the expected sequence is 10; the descriptor of 10 matched, then the next header block found has 8): an old leftover from an earlier pass around the ring, which ends the log.
    2. 

  2. Until the checkpoint writes are durable, the log is the only durable copy of the transaction. If s_start = 0 lands first and the power goes, recovery sees an empty log and the in-place writes may be missing: the transaction is lost although it was committed.
    3. 

  3. Good answers say: a logged copy that happens to start with the journal's magic number would look like a journal block to the scanner; escaping zeroes those four bytes in the log and sets a flag in the tag, and replay writes the magic number back before copying the block to its target.
    4. 

  4. Replay would write the old directory block's image over block 5000, destroying the file data now stored there. A revoke record for 5000, written when the block was freed, tells replay to skip older copies. The lab's journal empties the log after every transaction, so no older transaction is ever replayed after a block is reused.
    5. 

  5. Because all metadata of a transaction becomes durable atomically at the commit: there is no intermediate on-disk state between the steps of one operation that could be seen after a crash, so the order within the transaction does not matter. In F3-44 every step reached the disk in place, so each "before" needed a flush.
    6. 

  6. The commit block can reach the medium before some log blocks (and before the data blocks). A crash then leaves a valid-looking commit with stale slots (replay writes old contents or even old journal blocks over metadata), or committed metadata pointing to unwritten data (stale bytes in files). Exactly strategy 4 of F3-43 and this forensic lab.
    7. 

  7. Many cuts fell while no transaction was open or between commits (log empty or transaction not committed), where there is nothing to replay; and the window between commit block and log reset is short compared with a whole stream. Targeted cuts put the power failure exactly in the window where replay must run and stale slots could matter.
    8. 

  8. Replay writes full block images to fixed targets; writing the same image twice gives the same result. If the power fails during recovery, the log is still there (it is emptied only at the end, after a flush), so the next recovery simply replays again.
    9. 

  9. It proves that our recovery reads the subset of the format that e2fsprogs writes (v2 superblock, 32-bit tags, revoke) and that e2fsprogs replays our journals. It does not prove compatibility with the kernel's jbd2, which may use features (checksums, 64-bit tags, other commit-block fields) that debugfs did not use here, and it does not test a journal left by a kernel that was stopped abruptly.
    10.

  1. Transaction 6 has no FLUSH between its last copy (record 120) and its commit block (121) either; that is this build's bug throughout. Comparing with the correct build in the worked example, the FLUSH between the copies and the commit (record 126 there) is missing; only the flush after the commit remains (record 122 here). Transaction 7's records 137–144 end at the cut with no flush at all.
    2. 

  2. Durable: everything before the last flush before the cut, record 129 (109 block writes). Cached: the 15 writes of records 130–144 (seven data blocks in place, the journal superblock, the descriptor, five copies, the commit block), of which 6 landed.
    3. 

  3. Transaction 7: its descriptor (journal block 1, sequence 7) and commit block (journal block 7, sequence 7) both landed, so recovery replayed it and wrote the five targets 66, 2, 1, 1256 and 69 from journal blocks 2–6, whatever they contained.
    4. 

  4. Block 69 holds inodes 9 to 16 ((9 − 1) × 128 / 1024 = 1, so block 68 + 1; eight inodes per block). Inode 9 is a reserved inode that now has garbage as its mode; inodes 11 (lost+found), 12 (r4) and 13 (p5) are zeroed or garbage, so their directory entries point to unused inodes; the bitmaps and counters then disagree.
    5. 

  5. Journal block 6 held transaction 6's commit block (sequence 6, Figure 2). Transaction 7's copy of block 69 should have replaced it, but did not land. Replay wrote a commit block's bytes over the inode table block, wiping eight inodes: committed files (/p5, fsynced) are destroyed, not merely missing their last update.
    6. 

  6. The flush between the last log copy and the commit block (if (flushBeforeCommit_) dev_.flush();, left out by the nobarrier build). A commit-block checksum over the transaction's log blocks would have failed (the slots do not match the descriptor's copies), so recovery would have ignored transaction 7 and kept the file system intact. It would not protect ordered-mode data blocks, which the checksum does not cover (F3-43, strategy 5).
    7. 

  7. Random cuts rarely land in the short window between a commit block and the next flush, so 500 random cuts can pass by luck. The suite must include cuts right after each commit block (as harness.py ... commits does) and the known-bad build as a test that must fail.
