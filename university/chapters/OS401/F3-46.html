Story hook

The library has grown. The old catalogue card for a long encyclopedia listed every volume's shelf place, one per line, and needed extra cards stapled on for the long series. The new cards say "shelf 12, places 4 to 40", and a very long series gets a small index card that points to a few such ranges. The drawer of cards for the biggest section has also been reorganised: instead of reading every card to find a name, you turn a name into a number with a fixed rule and go straight to the right drawer.

And each drawer now carries a seal, a short code computed from everything inside it. If a card has been bent, smudged or swapped, the code no longer matches, and the librarian knows not to trust that drawer before she reads a single wrong card.

That is ext4 compared with ext2: extents instead of block lists, hashed directories instead of linear ones, and checksums on every piece of metadata. This chapter reads all three, on an image made by the host's mkfs.ext4, and refuses politely when it meets something it does not understand.

What you will be able to do

  • Decide from the superblock's feature flags whether a reader may mount an image, and refuse with a message naming the feature.
  • Read 64-bit group descriptors with flexible block groups and find any inode.
  • Walk an extent tree (header, index entries, leaf extents, uninitialised extents, holes) and read a file's bytes.
  • Find a name in a hashed-tree directory with the half-MD4 hash, and check the hash against debugfs.
  • Verify CRC32C metadata checksums (superblock, group descriptors, inodes, extent blocks, directory blocks) and report a corrupted block before using it.
Jargon box
Feature flags (compat, incompat, ro_compat)
Simple words: three sets of switches in the superblock that say which extensions the file system uses. Analogy: notes on the library door: "you may ignore this", "you must understand this to read", "you may read but not write". Precise: bit masks at fixed superblock offsets; an unknown incompatible bit forbids mounting, an unknown read-only compatible bit forbids writing, an unknown compatible bit may be ignored. D1
Extent
Simple words: one entry saying "these many consecutive blocks of the file are stored at these consecutive places on the disk". Analogy: "shelf 12, places 4 to 40" on one card. Precise: a 12-byte leaf entry: first logical block (32 bits), length (16 bits, above 32,768 meaning uninitialised), physical start (48 bits). D1
Extent tree
Simple words: the small tree of extents that maps a whole file; tiny files keep it inside the inode. Analogy: the index card that points to a few range cards. Precise: a B-tree whose root (a 12-byte header and up to four entries) occupies the inode's 60-byte i_block; index entries point to tree blocks, each with a header, entries and (with metadata checksums) a 4-byte tail checksum. D1
Uninitialised extent
Simple words: space reserved for a file but never written; it must read as zeros. Analogy: shelf places reserved for a series that has not arrived. Precise: an extent whose length field exceeds 32,768 (the length is the value minus 32,768); used by preallocation, read as zeros until converted. D1
Flexible block groups (flex_bg)
Simple words: the bitmaps and inode tables of several block groups are placed together. Analogy: the charts of several floors kept on one desk. Precise: an incompatible feature that lets a group's metadata live outside the group, so readers must take every location from the group descriptor, never compute it. D1
64-bit mode
Simple words: block numbers get 48 or 64 bits, and group descriptors grow to hold them. Analogy: longer shelf numbers for a bigger library. Precise: the 64bit incompatible feature: group descriptors of s_desc_size bytes (64 in this build) with high halves of each block field, and a 64-bit block count. D1
Hashed-tree directory (htree, dir_index)
Simple words: a large directory with an index that sends each name, by a number computed from it, to one block. Analogy: the rule that turns a name into a drawer number. Precise: a directory whose first block holds a dx_root (disguised as entries for . and ..) with sorted (hash, block) pairs, optional dx_node levels, and ordinary leaf blocks; the hash (here half-MD4 with a seed from the superblock) selects the leaf. D1
CRC32C (metadata_csum)
Simple words: a 32-bit check code computed over each metadata structure. Analogy: the seal on each drawer. Precise: the Castagnoli CRC-32 used by ext4's metadata_csum feature, seeded per file system from the UUID (or a stored seed) and per object from numbers such as the inode number and generation; stored in the superblock, descriptors (16 bits), inodes, extent and directory block tails. D1
Inline data
Simple words: a very small file stored inside its inode instead of in a block. Analogy: a short note written on the catalogue card itself. Precise: the inline_data incompatible feature: file (or directory) contents in i_block and an extended attribute; FS3's goal lists it, and this chapter's reader refuses it. D1

Layer 1 — the kid explanation

The new library writes ranges instead of single places: "shelf 12, places 4 to 40" is one line, not 37. A huge directory has a rule that turns a name into a number, and the number tells you which drawer to open, so you never search the whole cabinet.

Every drawer has a seal made from its contents. Before you trust a drawer, you make the seal again yourself and compare. If the two seals differ, someone or something has changed the drawer, and you stop.

And the door has notes: "if you do not understand this note, do not come in". A careful reader who meets a note it does not know stays outside and says which note it was.

Layer 2 — the student explanation

ext4 keeps ext2's skeleton (superblock, block groups, inodes, directories) and changes how blocks are found, how directories scale, and how corruption is detected. A reader for ext4 created "with default options" has to handle five things: the feature flags, 64-bit group descriptors with flexible block groups, extent trees, hashed directories, and metadata checksums. FS3 adds inline data to the goal; the default options of the mkfs.ext4 in this build did not enable it. C1 R1

Feature flags come first. The superblock has three masks. An incompatible feature changes the format so that a reader that ignores it would misread the disk (extents, 64-bit, inline data); a read-only-compatible feature can be ignored when reading but not when writing (metadata checksums, huge files); a compatible feature can be ignored (the journal, from a reader's point of view, once it is clean). A correct reader knows a list of incompatible features it supports and refuses everything else, naming it. D1

Extents replace ext2's block pointers. An inode with the extents flag has, in place of its 15 pointers, a tree: a header and up to four entries inside the inode, and further tree blocks if more are needed. Leaf entries are extents (logical start, length, physical start); index entries point to the next level. Logical blocks that no extent covers are holes. D1

Hashed directories keep ext2's entry format in their leaf blocks, so an old reader can still list them linearly; the index sits in the first block, hidden behind fake . and .. entries. Checksums use CRC32C: each structure stores a checksum computed with a seed from the file system's UUID and, for per-file structures, the inode number and generation. A reader computes the checksum before using a structure and reports a mismatch instead of following a corrupted pointer. D1

Layer 3 — the engineer's depth

Superblock, features, descriptors

The superblock is at byte 1024 whatever the block size; magic 0xEF53 at offset 0x38; block size 1024 shifted left by s_log_block_size. The three feature words are at 0x5C (compatible), 0x60 (incompatible) and 0x64 (read-only compatible). The lab's image, made by mkfs.ext4 1.47.0 with no options except a fixed UUID and hash seed, shows the incompatible set filetype extent 64bit flex_bg (plus the journal, a compatible feature) and the read-only set including metadata_csum R1 R2. The reader's table names every incompatible bit it knows and accepts only filetype, extent, 64bit, flex_bg and metadata_csum_seed; unknown bits beyond the table are refused too. D1

With 64bit, the descriptor size is s_desc_size (64 here), the block count gains a high half (offset 0x150), and every block address in a descriptor has a high 32-bit half in the second 32 bytes. With flex_bg, never compute where a group's inode table is: read it from the descriptor. In the lab, groups 1 and 2 have their inode tables at blocks 1645 and 3245, inside group 0's area, which an ext2-style computation would get wrong R2. An inode is found as in ext2: group (n − 1) / s_inodes_per_group, index (n − 1) mod the same, at inode_table × block_size + index × s_inode_size. Inodes are 256 bytes here; the second half holds i_extra_isize, the high checksum half and nanosecond times. D1

Checksums

The superblock checksum is CRC32C over its first 1020 bytes, stored in its last 4. The per-filesystem seed is CRC32C of the 16-byte UUID (or s_checksum_seed if the metadata_csum_seed feature is set, so the UUID can change without rewriting every checksum). A group descriptor's 16-bit checksum is the low half of CRC32C over the seed, the group number (little-endian 32 bits) and the descriptor with its checksum field zeroed. An inode's checksum continues the seed with the inode number and i_generation, then runs over the whole on-disk inode with both checksum fields zeroed; the low 16 bits are at 0x7C, the high 16 at 0x82 when i_extra_isize covers them. Extent tree blocks carry a CRC32C of the block up to the end of the header's maximum entry count, with the inode's seed; directory leaf blocks a 12-byte tail entry (inode 0, record length 12, a 0xDE marker) with a CRC32C of everything before it. In ext4's usage the CRC32C is computed without the final inversion. D1

These details are easy to get almost right, and "almost" fails every check. In this build they are confirmed the strongest way possible short of reading the document: on the lab image, the reader's computed values matched the stored ones for 1 superblock, 3 group descriptors, 4,025 inodes, 2 extent tree blocks and 17 directory leaf blocks with zero mismatches R3. And a single changed byte in one inode was reported by the reader and by e2fsck alike R8.

The structure offsets and checksum rules in this section were written from the author's memory of the Linux kernel documentation "ext4 Data Structures and Algorithms" (not opened). Agreement with the values mke2fs and e2fsck 1.47.0 wrote and checked is strong evidence for the cases exercised, but not for: the checksums of dx_root/dx_node index blocks (the reader does not verify them), block and inode bitmaps (not read), the journal, extended-attribute blocks, the metadata_csum_seed path (the lab image does not use it), 128-byte inodes with only a 16-bit checksum, and big-endian hosts. Check the document's checksum section before extending the reader.

Extent trees

The extent header is 12 bytes: magic 0xF30A, number of entries, maximum entries, depth, generation. In the inode, the header plus four 12-byte entries fill i_block's 60 bytes. At depth 0 the entries are leaves: 32-bit logical block, 16-bit length, 48-bit physical start (high 16 bits first in the entry, then low 32). A length above 32,768 marks an uninitialised extent of (length − 32,768) blocks, which must read as zeros. At depth > 0 the entries are index entries: 32-bit logical block (the first logical block covered by the child), 48-bit child block number (low 32 first, then high 16). Entries are sorted by logical block, so lookup at each level picks the last entry whose logical start is not greater than the target. D1

The reader collects all leaf extents of a file and copies each block to logical × block_size in an output buffer of the file's size, initialised to zeros: holes and uninitialised extents stay zero by construction. That one line, the destination computed from the extent's logical start, is where the forensic lab's colleague went wrong. Note also the 48-bit physical field: a reader that keeps only the low 32 bits works on every small test image and fails on disks larger than 16 TiB with 4 KiB blocks. D1

Hashed directories

A directory with the index flag (0x1000) has a dx_root in its first block: an entry for . (record length 12), an entry for .. whose record length covers the rest of the block (so linear readers skip the index), then at offset 0x18 the root info (reserved, hash version, info length 8, indirect levels, flags), then at 0x20 the limit and count fields followed by (hash, block) pairs, the first pair's hash slot holding the block of hashes from 0. For lookup: compute the name's hash with the directory's hash version (half-MD4 by default, using the superblock's 16-byte hash seed), pick the last pair whose hash ≤ the name's hash, descend through dx_node blocks if indirect levels > 0, and search the chosen leaf block linearly. The lowest bit of an index hash has a special meaning for names whose hashes collide across a block boundary; this reader ignores that case. D1

The lab's /many has 2,000 entries and one index level with 13 leaves. The reader's half-MD4 gives 0x17433198 for file1999.txt and 0x0df37f34 for file0042.txt; debugfs's dx_hash command with the same seed prints the same values. The superblock flag signed_directory_hash says whether name bytes above 0x7F are treated as signed in the hash; the lab's names are ASCII, so that branch is untested. R6

Note

Why did the lab run e2fsck -fyD after mkfs.ext4 -d? Building an image from a host directory with -d is not guaranteed to produce indexed directories, so the lab runs e2fsck -D, which optimises (indexes) directories, to make sure /many is indexed. The debugfs stat line in the mkfs output shows /many with flags 0x81000: extents (0x80000) and the index flag (0x1000) R1. On a mounted file system, the kernel converts a directory to an indexed one when it outgrows one block.

What the reader leaves out

The reader is read-only by construction (it opens the image with "rb"), ignores the journal (a reader must refuse or replay if needs_recovery is set; this one refuses through the feature table), and does not handle inline data, encryption, case folding, meta_bg, large directories (3-level htrees) or extended attributes. FS3 lists inline data in its goal: to complete the milestone, implement it (the data lives in i_block and the system.data extended attribute) and use another feature, such as encrypt or casefold, for the refusal test. C1

How the hardware actually does it

CRC32C is not just any CRC: the Castagnoli polynomial has a dedicated instruction on x86 (SSE4.2 crc32) and on Armv8 (the CRC32C instructions of the CRC extension), which is one reason ext4, btrfs, iSCSI and others chose it. The lab uses the bit-by-bit table-free loop, which is slow but obviously correct; a kernel uses the instruction or a slicing table. Metadata checksums catch corruption the disk did not report (a misdirected write, a bug in a driver, a flipped bit in RAM before the write); they are not a substitute for the device's own error correction, which protects the medium. D1 D3

Not verified — check before relying on this

Untested on hardware. No hardware CRC instruction was used or timed in this build. Check the Intel SDM (instruction CRC32, which computes CRC-32C) and the Arm Architecture Reference Manual (CRC32C* instructions) before writing an accelerated version, and test it against the bitwise version on the lab image.

Safety

Read real Linux disks only as images or through a read-only path, never with a driver under development that can write. Make an image copy of the partition first and work on the copy.

Worked example

Read the extent tree of /big/sparse.bin by hand, then check it against the reader and debugfs. The file was written by mktree.py as twelve islands of 5,000 bytes, island k starting at byte 300,000 × k; its size is 11 × 300,000 + 5,000 = 3,305,000 bytes.

  • Island 1 starts at byte 300,000; 300,000 / 4,096 = 73.24, so it begins in logical block 73 and ends at byte 304,999, in block 74: two blocks, 73–74.
  • Island 4 starts at byte 1,200,000 = block 292.97; it ends at 1,204,999 = block 294.18: blocks 292–294, three blocks. mke2fs stored them as two extents (292 alone at 5629, then 293–294 at 5631); block 5630 between them is the extent tree block.
  • Island 11 starts at 3,300,000 = block 805.66 and ends in block 806: blocks 805–806, the last extent.


The reader and debugfs agree on every extent, including the tree block (ETB0 5630) R5. Reading the file then means: a zeroed buffer of 3,305,000 bytes, and for each extent, its blocks copied to logical block × 4,096. Everything not copied is a hole and stays zero.

Where the analogy breaks


    

  • A seal on a drawer shows that the drawer changed; it does not say whether the change was a smudge or a forgery. CRC32C detects accidental corruption well but offers no protection against deliberate changes: anyone can recompute it.
    • 

  • "Shelf 12, places 4 to 40" suggests the range is on one shelf in a building. An extent's physical blocks are consecutive block numbers; on a RAID, a thin-provisioned volume or flash, consecutive numbers need not be physically next to each other.
    • 

  • The hash rule sends every name to one drawer; with many names that hash alike, a "drawer" can overflow into the next leaf block, which the collision bit in the index records. The library's rule has no such case.
    • 




Common mistakes and debugging


    

  • Computing group metadata locations. With flex_bg, inode tables are not in their own group. Always use the descriptor.
    • 

  • Reading only the low 32 bits. 64-bit descriptors and 48-bit extent starts have high halves; tests on small images will not notice.
    • 

  • Getting the CRC32C conventions slightly wrong. Initial value, inversion, which fields are zeroed, whether the inode number goes in before the generation: each mistake fails every check. Debug with one known structure (the superblock first, it has no per-object seed).
    • 

  • Copying extents sequentially. Placing each extent's blocks after the previous one instead of at logical × block size drops the holes: the size is right and the contents are wrong (the forensic lab).
    • 

  • Treating an unknown feature as harmless. Mounting an image with, for example, inline data or encryption and reading i_block as extents produces garbage, not an error. Refuse by default.
    • 

  • Following the index blindly. A corrupt dx_root can send lookups to the wrong block; a linear scan of all blocks is the fallback that e2fsck and the reader's tree command use.
    • 




Transition box

Where you came from: F3-45 wrote and replayed the journal that ext3 added to ext2; F3-33 read ext2's inodes and directories. What carries over: superblock, groups, inodes, linear directory blocks, and e2fsprogs as the independent judge. What changes: you read a format you did not write, made by someone else's tool with options you did not choose, so the reader must check everything (checksums) and refuse what it does not know (features). C1 What comes next: F3-47 leaves the ext family for exFAT, the format of camera cards and large USB sticks, where the reference implementation is not in the container and the only independent judge is a probe.

Summary


    

  • Feature flags decide: unknown incompatible means refuse, by name; unknown read-only compatible means do not write.
    • 

  • 64-bit descriptors and flex_bg: take every location from the descriptor and read both halves.
    • 

  • Extent trees: a header and four entries in the inode, tree blocks below; leaves map ranges; holes and uninitialised extents read as zeros; place blocks at logical × block size.
    • 

  • Hashed directories: half-MD4 with the superblock seed selects one leaf through dx_root; leaves stay linear and readable.
    • 

  • CRC32C everywhere: verified for 4,025 inodes and every other structure read, and a one-byte change detected exactly as e2fsck reports it.
    • 

  • The lab's listing of 2,012 entries matched the host; inline data and multi-level indexes remain to be done for FS3.

  2. A reader that ignores checksums still reads the structures correctly (the layout does not change), so reading is safe; a writer that ignores them would write structures with stale checksums that checksum-aware readers then reject, so writing is not.
    3. 

  3. Good answers say: a hole is a range of logical blocks that no extent covers; nothing is stored for it on disk. A reader starts with a buffer of zeros of the file's size and copies only the blocks that extents map, each to its logical position; whatever is left over is the hole and reads as zeros.
    4. 

  4. 32,770 − 32,768 = 2 blocks, uninitialised: allocated but never written, so the reader must return zeros for them, not the stale contents of the physical blocks.

  1. /big/sparse.bin: the size (3,305,000) is the same, the CRC-32 differs (02b26193 instead of 06c6b4f0). Everything else in the listing is identical.
    2. 

  2. Their extents are contiguous from logical block 0 (no holes), so "each extent follows the previous one" happens to equal "each block at logical × block size".
    3. 

  3. After the first extent's two blocks: at logical block 2 (byte 8,192). It belongs at logical block 73 (byte 299,008).
    4. 

  4. All the data is packed at the start: the 13 extents' 26 blocks fill bytes 0 to 106,495, in order; everything from there to 3,305,000 is zeros. The islands are no longer at multiples of 300,000.
    5. 

  5. In read, the destination at: the colleague used a running position (at = pos; pos += bs_, the FORENSIC_NO_HOLES branch). Correct: at = (e.logical + i) × bs_.
    6.
