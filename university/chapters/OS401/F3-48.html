Story hook

Once a year the library prints its catalogue as a bound book and sends copies to the other schools. Nobody can change a printed book, so its format is simple: every list is written once, in a fixed order, with page numbers. The old printing rules allow only short names in capital letters, so the printer adds notes in the margin: one set for readers who want the long names with their accents, another for readers who also want to know who may borrow what.

The book has one more page, at the front: "if you are the caretaker restarting the computer room, start the machines with the program on page 73". The caretaker's machines do not read the catalogue; they read only that page. If the page number is written in the wrong unit, the caretaker goes to page 292, finds a blank page, and waits forever.

This chapter writes and reads that book: ISO 9660, the file system of CDs, DVDs and installer images, with its two extensions and its boot catalogue. The firmware itself is the judge in the lab.

What you will be able to do

  • Describe an ISO 9660 image: the system area, the volume descriptor set, path tables, directory records and file extents, and why numbers are stored in both byte orders.
  • Read the same image three ways: plain ISO 9660 names, Joliet (UCS-2 names in a second tree) and Rock Ridge (POSIX names, modes and symbolic links in System Use fields).
  • Write an image with all three, and check each view against the host tree.
  • Decode an El Torito boot catalog, extract its BIOS and UEFI images, and boot the BIOS entry under SeaBIOS.
  • Diagnose a boot failure caused by mixing the catalog's two units (512-byte virtual sectors and 2,048-byte CD sectors).
Jargon box
ISO 9660
Simple words: the file system of CDs, DVDs and ".iso" files. Analogy: the printed and bound catalogue. Precise: the file structure standardised as ECMA-119 / ISO 9660: 2,048-byte logical sectors, a volume descriptor set from sector 16, directories as lists of variable-length records, each file as one contiguous extent (in the basic levels). D1
Volume descriptor
Simple words: a 2,048-byte sector that describes one view of the disc. Analogy: the title page. Precise: a sector starting with a type byte and "CD001": type 1 primary, 2 supplementary (Joliet), 0 boot record (El Torito), 255 set terminator. D1
Path table
Simple words: a list of every directory and its parent, so that a reader can find a deep directory without walking. Analogy: the book's table of contents. Precise: a table of directory identifiers, extents and parent numbers in breadth-first order, stored once little-endian (L) and once big-endian (M). D1
Both-byte order
Simple words: a number written twice, once for each kind of computer. Analogy: a page number printed in two scripts. Precise: ISO 9660's 16- and 32-bit fields stored little-endian then big-endian, so either kind of machine reads its half directly. D1
Rock Ridge (SUSP, RRIP)
Simple words: notes added to each directory record giving the POSIX name, permissions and link target. Analogy: margin notes for readers who want the full details. Precise: the System Use Sharing Protocol defines tagged entries in a record's System Use area (SP, CE, ER, ...); the Rock Ridge Interchange Protocol defines PX (mode, links, uid, gid), NM (name), SL (symbolic link), TF (times) and others. D3
Joliet
Simple words: a second directory tree with Unicode names, for Windows. Analogy: a translated index. Precise: a supplementary volume descriptor with an escape sequence (%/@, %/C or %/E for UCS-2 levels 1–3) whose root leads to a separate tree of records with UCS-2 big-endian identifiers, pointing at the same file extents. D2
El Torito
Simple words: the rules for making a CD bootable. Analogy: the caretaker's "start here" page. Precise: a boot record volume descriptor pointing at a boot catalog: a validation entry with a checksum, a default entry, and optional section headers and entries for other platforms (0xEF for UEFI). D4
No-emulation boot
Simple words: the BIOS loads a small program from the CD and runs it, without pretending the CD is a floppy or hard disk. Analogy: "run the program on page 73 as it is". Precise: media type 0 in a catalog entry: the BIOS loads sector count 512-byte virtual sectors from the given 2,048-byte load RBA to the load segment (default 0x7C0) and jumps to it with DL = the drive number. D4

Layer 1 — the kid explanation

A CD is like a printed book: you write it once and then only read it. So its catalogue can be very simple: each list of names is printed in one place, and each file is printed in one piece. The old rules allow only short capital names, so the book also has margin notes with the real names, and a second, translated index for Windows.

At the very front there is a page for the computer that is starting up. It says "the start-up program is on page 73". The computer reads that page, copies the program and runs it. Write the wrong page number and the computer runs a blank page, and nothing happens.

Layer 2 — the student explanation

An ISO 9660 image starts with 16 sectors (32 KiB) that the standard leaves to the system; hybrid images put an MBR and partition table there so the same file boots from a USB stick. From sector 16 come volume descriptors, one per sector, until a terminator. The primary descriptor gives the volume size, the path tables and the root directory record. Directories are extents full of variable-length records; a record never crosses a sector boundary, so a reader can start at any sector. Each file in the basic levels is one contiguous extent: perfect for a medium written once from start to finish. D1

Plain ISO 9660 names are restrictive (level 1: upper-case letters, digits and underscore, 8.3, with a version ";1"), and there are no POSIX permissions or links. Two extensions fill the gap, in different ways. Rock Ridge adds tagged entries to the System Use area at the end of each record in the same tree: a Linux reader takes the name from NM, the mode from PX and a link's target from SL. Joliet adds a whole second directory tree, reachable from a supplementary volume descriptor, whose identifiers are UCS-2; Windows reads that tree. Both point at the same file data. D2 D3

Booting is a separate path. A boot record descriptor (type 0, "EL TORITO SPECIFICATION") gives the sector of the boot catalog. The catalog's validation entry carries a checksum; the default entry describes the BIOS boot image; further sections can describe images for other platforms, such as UEFI, whose image is a FAT file system containing EFI/BOOT/BOOTX64.EFI. The BIOS never reads the directory tree at all. D4

FS5's acceptance test compares an image built by xorriso and a real installer image with the host. Neither was available here; the lab builds its own image, reads it with a separate reader that shares no code with the writer, and uses libblkid, file, mtools and SeaBIOS as independent judges. C1

Layer 3 — the engineer's depth

Descriptors, both-byte fields and path tables

The primary volume descriptor's fields the lab uses: type (0), "CD001" (1–5), version (6), system identifier (8, 32 bytes), volume identifier (40, 32 bytes), volume space size (80, both-byte 32-bit), Joliet escape sequence (88, supplementary only), set size, sequence number and logical block size (120, 124, 128, both-byte 16-bit), path table size (132), L path table location (140, little-endian), M path table location (148, big-endian), the root directory record (156, 34 bytes), identifier strings from 190, dates from 813 as 16 ASCII digits plus a time-zone byte, and file structure version (881). D1

Each path-table entry is identifier length, extended attribute length, extent (4 bytes, in the table's byte order), parent directory number (2 bytes), the identifier and a pad byte to an even length. Directory numbers start at 1 for the root, in breadth-first order, sorted by parent then by identifier. The lab's table for 5 directories is 60 bytes: root 10, BOOT 12, DOCS 12, EMPTY 14, GRUB 12. libblkid read the primary descriptor and found the volume label, the Joliet escape and the boot record. R3 R4

Directory records and the three views

A record (Figure 2) has its length at byte 0, the extent at 2 and the data length at 10 (both-byte), a 7-byte date at 18 (years since 1900, month, day, hour, minute, second, offset in 15-minute units), flags at 25 (bit 1 = directory), the volume sequence number at 28, the identifier length at 32 and the identifier from 33, then a pad byte if the identifier length is even, then the System Use area. The first two records of every directory are "." (identifier byte 0) and ".." (byte 1). D1

The real listing shows what each view gives R3: the Rock Ridge view has /Read me first.txt with mode 100644, /docs/big.bin with 100600, the symbolic link link-to-readme -> ../Read me first.txt and the Greek and German name; the Joliet view has the same names but no modes and no link (Joliet cannot express one, so mkiso leaves it out); the plain view shows READ_ME_.TXT, __BERSIC.TXT (the two UTF-8 bytes of Ü each became an underscore) and the link as an empty file LINK_TO_.. The Rock Ridge and Joliet views were compared with a listing made from the host tree by a separate Python script: identical.

Rock Ridge is announced by an SP entry ("indicator" BE EF) in the root's "." record and an ER entry naming the extension; readers look for SP before trusting any other entry. mkiso writes PX, NM and SL only. Things it does not do that real images need: CE continuation areas when the System Use area does not fit in the record (long names, long link targets), TF time stamps, and the CL/PL/RE relocation of directories deeper than 8 levels. isoread correspondingly does not follow CE. A name longer than roughly 170 bytes therefore fails with "directory record too long" rather than producing a broken image. D3

Not verified — check before relying on this

The SUSP and RRIP entry formats (SP, ER, PX with 36 bytes in RRIP 1.12 versus 44 with an inode number in later versions, NM flags, SL component flags 0x02 current, 0x04 parent, 0x08 root) and the Joliet escape sequences are from memory. Our writer and reader were written separately but by the same author, so a shared misreading would not show. libblkid read only the Joliet volume identifier. Linux's own isofs driver and xorriso were not used: mounting the image needs privileges this build did not have. That comparison is the first thing to do with the image.

The boot catalog

The catalog is 32-byte entries R5. The validation entry: header ID 0x01, platform (0 = 80x86), an ID string ("OS401 MKISO"), a checksum word at offset 28, and the key bytes 55 AA at 30–31; the sixteen 16-bit little-endian words of the entry must sum to zero modulo 216 (here the checksum word is 0x1311). The default entry: boot indicator 0x88, media type 0 (no emulation), load segment 0 (meaning the traditional 0x7C0), system type, sector count in 512-byte virtual sectors (4 for our 2,048-byte image), and load RBA in 2,048-byte CD sectors (73). A section header (0x91 = last section, platform 0xEF = UEFI, 1 entry) is followed by an entry for the UEFI image at sector 74. D4

The UEFI entry's sector count is a 16-bit field; for a 1.44 MB FAT image it is 2,880. For a larger EFI system partition image the count does not fit, and firmware is commonly said to use the FAT image's own size instead, with tools writing 0 or 1. The lab extracted the 2,880 × 512 bytes, compared them with the input image (identical) and listed EFI/BOOT with mtools. FS5 asks for this image to mount with your own FAT driver (B15); mtools stands in here. R5 C1

The BIOS side was tested for real, in emulation: SeaBIOS in QEMU read the catalog, loaded the image, and jumped to it; the image printed on the serial port and wrote to QEMU's isa-debug-exit port, so QEMU exited with code 33 = (0x10 << 1) | 1. The drive number this SeaBIOS passed in DL was 0xE0; do not hard-code it, use whatever DL holds. R6

Watch out

An observation, not a rule: with the validation entry's checksum set to zero (words summing to 0xECEF), this SeaBIOS still booted the image. R7 Do not conclude that the checksum does not matter. Other firmware, and tools like our isoread, reject the catalog; a mastering tool must always write a valid checksum. One emulator tolerating an error says nothing about the machine in the school's computer room.

How the hardware actually does it

A CD-ROM data sector (Mode 1) carries 2,048 user bytes within a 2,352-byte physical sector, with a sync pattern, header and error-correcting codes the drive checks before handing the data over. DVDs and Blu-ray discs use 2,048-byte sectors natively. The drive is reached by SCSI/MMC commands (over ATAPI, USB or SATA), with READ(10) taking 2,048-byte block addresses; the BIOS's El Torito support uses those commands and then presents the no-emulation image through INT 13h extensions with 2,048-byte sectors. Installer ".iso" files that also boot from USB sticks are hybrid: they put an MBR (and often a GPT) in the system area, so the stick's firmware sees a disk while a CD drive sees ISO 9660. D4 D5

Not verified — check before relying on this

Untested on hardware. No optical drive, disc or USB stick was used; the only boot was the SeaBIOS bundled with QEMU 8.2.2 under TCG emulation. The statements about Mode 1 sectors, MMC commands, INT 13h behaviour and hybrid images are from memory: check the ECMA-130 and MMC documents and the El Torito specification before relying on them. UEFI booting of the 0xEF entry was not tried (no OVMF in this build, and the FAT image contains a placeholder, not an EFI program).

Safety

When you write an image to a USB stick with dd, the target is a whole disk: check the device name twice (lsblk), unmount it first, and never point it at the disk your system runs from.

Worked example

Recompute the validation entry's checksum by hand. The entry's 32 bytes, as mkiso writes them: byte 0 = 01, byte 1 = 00 (platform), bytes 4–14 = "OS401 MKISO", bytes 28–29 = the checksum, bytes 30–31 = 55 AA, all others 0. As 16-bit little-endian words:

  • Word 0: bytes 01 00 → 0x0001. Word 1: 00 00 → 0.
  • Words 2–7 hold bytes 4–15: "OS" → 0x534F, "40" → 0x3034, "1 " → 0x2031, "MK" → 0x4B4D, "IS" → 0x5349, "O" and 0 → 0x004F.
  • Word 15: 55 AA → 0xAA55.
  • Sum without the checksum: 0x0001 + 0x534F + 0x3034 + 0x2031 + 0x4B4D + 0x5349 + 0x004F + 0xAA55 = 0x1ECEF; modulo 216 that is 0xECEF. This is exactly the "words sum to 0xecef" that isoread printed when the checksum was zeroed. R7
  • Checksum = 0x10000 − 0xECEF = 0x1311, which is what the lab's catalog holds. R5

Now the units. The boot image is 2,048 bytes and sits at CD sector 73. The default entry's sector count is in 512-byte units: 2,048 / 512 = 4. Its load RBA is in CD sectors: 73, byte offset 73 × 2,048 = 149,504. A writer that converts the RBA to 512-byte units as well writes 292, which is byte offset 598,016: inside the UEFI FAT image (which starts at sector 74, byte 151,552), where the bytes are zeros.

Where the analogy breaks


    

  • A printed catalogue is read by people who can guess. A plain ISO 9660 reader cannot: it shows __BERSIC.TXT and never knows the real name.
    • 

  • Margin notes are on the same page as the entry. Joliet is not a note at all: it is a second, separate set of directories, and the two can disagree (the link exists in one and not the other).
    • 

  • The caretaker's page is in the book, but the computer starting up never opens the rest of the book. The boot path and the file system share only the image's sectors; a correct directory tree says nothing about whether the disc boots.
    • 




Common mistakes and debugging


    

  • Mixing the catalog's units. Sector count is in 512-byte units; load RBA in 2,048-byte units. The forensic lab.
    • 

  • Records crossing a sector. Readers stop at a zero length byte and move to the next sector; a record split across the boundary is lost.
    • 

  • Writing only one half of a both-byte field. Little-endian readers work, big-endian readers (and some checkers) read nonsense.
    • 

  • Forgetting the pad byte after an even-length identifier, which shifts the System Use area by one and makes every Rock Ridge entry unreadable.
    • 

  • Unsorted records or a path table in the wrong order. Some readers binary-search; parent numbers depend on the order.
    • 

  • Trusting one firmware. SeaBIOS booted with a bad checksum; real machines may not. Test on several, and on hardware.
    • 

  • Debugging a silent boot. Use SeaBIOS's debug port (-device isa-debugcon,iobase=0x402): "Booting from 0000:7c00" means the BIOS jumped, so the problem is what it loaded.
    •

Summary


    

  • ISO 9660: 2,048-byte sectors, descriptors from 16 to a terminator, path tables in both byte orders, directory records that never cross a sector, single-extent files.
    • 

  • Rock Ridge adds POSIX names, modes and links in each record's System Use area; Joliet adds a second tree with UCS-2 names; both share the file data.
    • 

  • El Torito: boot record → catalog → validation entry (words sum to zero), default BIOS entry, sections for UEFI. Sector count in 512-byte units, load RBA in 2,048-byte units.
    • 

  • The lab's image passed our separate reader, a host comparison, libblkid, file, mtools and a SeaBIOS boot; it was not checked by xorriso, Linux's isofs or real hardware.
    • 

  • One emulator's tolerance is an observation, not a specification.
