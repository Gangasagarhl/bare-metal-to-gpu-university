Story hook

The school library has a new rule after last term's power cut. Every move of a book now follows the same order: book on the shelf, then the free-place chart, then the card. And every evening, the porter hands in a list of everything he carried that day, in the order he carried it, with a line drawn each time he had the head librarian sign that the trolley was empty.

Ms Okafor wants to know whether the rule works. She cannot wait for the next power cut, so she uses the porter's list. She takes a photograph of the library from the morning, replays the list on it up to some random point, and, for the moves after the last signed line, flips a coin for each one: carried, or still on the trolley. Then she asks the strictest librarian in the district to inspect the result. She does this five hundred times.

This chapter does the same with ext2. We complete the write side of the driver from OS304, record every block write and flush it makes, and replay the recording five hundred times to the disk a power cut could have left, with e2fsck as the strict inspector.

What you will be able to do

  • Implement the ext2 write paths that FS1 names (create, write with direct, single and double indirect blocks, sparse files, truncate, unlink, rename, hard and symbolic links, mkdir) and order their block writes so that a crash leaves only leaks.
  • Record a write stream from your block layer and build crash images from it under the device model of F3-43.
  • Run the FS1 acceptance test: 500 power cuts, e2fsck findings classified against a list written in advance, and every fsynced file compared byte for byte.
  • Read an e2fsck report line by line and explain which lost write caused each line (practical exam P).
  • Show that the harness can fail: run it against a deliberately careless build and see it report damage.
Jargon box
Write stream
Simple words: a recording of every block a file system wrote and every flush it asked for, in order. Analogy: the porter's list of everything he carried, with the signed lines. Precise: a log of (block number, block contents) write records and flush records taken at the block-device interface; together with the starting image it determines every crash state. D5
Power-cut harness
Simple words: a test program that fakes many power failures and checks the disk after each one. Analogy: replaying the porter's list to a random point, 500 times, with an inspector after each replay. Precise: a test that builds crash images (by replaying a write stream with unflushed writes randomly dropped, or by killing an emulator), runs recovery and an independent checker, and verifies the application-level promises. D5 C1
Indirect block
Simple words: a block that holds no file data, only a list of block numbers of the file. Analogy: an index card that lists more shelf places for a very long book series. Precise: in ext2, inode pointers 12, 13 and 14 point to single, double and triple indirect blocks, each holding block-size/4 32-bit block numbers. D1
Sparse file (hole)
Simple words: a file with ranges that were never written and take no disk space; they read as zeros. Analogy: a numbered series with empty places that are not reserved on any shelf. Precise: logical blocks whose pointer is 0; reads return zeros, and i_blocks counts only allocated blocks (including indirect blocks), in 512-byte units. D1
Hard link
Simple words: a second name for the same file. Analogy: two catalogue cards for one book. Precise: a directory entry pointing to an existing inode; the inode's i_links_count counts its names, and the inode is freed when the count reaches 0 (and no process holds it open). D1
Fast symbolic link
Simple words: a small file whose content is a path to another file, stored inside the inode itself. Analogy: a card that says "see the card for the atlas". Precise: an ext2 symlink whose target (under 60 bytes) is stored in the inode's block-pointer area instead of a data block, with i_blocks = 0. D1
Orphan inode
Simple words: a file that exists on disk but has no name in any directory. Analogy: a book on a shelf with no card anywhere. Precise: an inode with a non-zero link count and no directory entry; e2fsck reports it as "Unattached inode" and offers to connect it to lost+found. D2
Acceptable damage list
Simple words: the kinds of checker complaints your design allows after a crash, written down before testing. Analogy: "a free place marked taken is fine; a card pointing to the wrong book is not". Precise: the categories, declared in the FS1 plan, of e2fsck findings that do not lose, mix or expose data: leaked blocks and inodes, counters, link counts and i_blocks too high. C1
Promise (fsync record)
Simple words: a note in the recording that says "the program was told this file is safe". Analogy: the librarian's signature under one move. Precise: a record appended to the write stream after an fsync returned, naming the file and its expected contents; the harness checks every promise issued before the cut. R6

The idea in pictures

Figure 1 is the harness. The workload runs once, on an in-memory image, and its block layer records the write stream. Every power cut is then a replay of that stream onto the starting image, cut at a random record, with a coin toss for each write after the last flush. Two independent judges look at the result: e2fsck in read-only mode for the structure, and debugfs for the bytes of every file whose fsync had returned.

Figure 2 is the order of writes for creating a file, in the careful build and in the careless build that the forensic lab uses. The careful build makes the inode complete and durable before any directory names it; the careless one writes the name first and does not flush at all.

Layer 1 — the kid explanation

To keep the library honest, always do the moves in the same safe order: the book on the shelf first, the card last. Taking a book away goes the other way round: the card first, the book last. Then a power cut can only leave a book without a card, never a card without its book.

To check the rule, you do not need a real power cut. Keep a list of every move in order, and replay the list to a random point, pretending some of the last moves never happened. Then let a strict inspector walk the shelves. If you do this many times and the inspector only ever finds books without cards, the rule works.

Layer 2 — the student explanation

OS304's ext2 driver could create and write files. FS1 asks for every common write operation and for proof of what a power cut does. The operations are: creating files and directories, writing (including files large enough to need indirect blocks, and sparse files with holes), truncating, unlinking, renaming, hard links and symbolic links. Each one changes several blocks: bitmaps, the group descriptor and superblock counters, inode table blocks, directory blocks and indirect blocks. C1 D1

F3-43 gave the rules for ordering. Applied to ext2 they become: allocate (bitmap bit set) before pointing; write a new block's contents before the pointer to it; write a new inode before the directory entry that names it; remove a name before decrementing the link count; clear a pointer before freeing the block. Each "before" is a flush, because only a flush orders writes on a device with a write cache. D3

With those rules, a crash can leave only a few kinds of finding: a free-space or directory counter that is wrong, a block or inode marked used that nothing uses, an inode with no name, a link count that is too high, and an i_blocks count that is too high. Those are the lab's acceptable damage list. Everything else, such as a name pointing to an unused inode, a block used by two files, or a link count that is too low, is damage. D2 R7

The harness runs a random workload once and records the write stream. For each of 500 seeds it builds a crash image from the stream, runs e2fsck -fn (force a full check, change nothing) and classifies every line it prints, then dumps every file whose fsync had returned before the cut and compares its bytes. Run against the careful build, it found no damage and no lost file. Run against a careless build, it found damage in 65 of 100 runs. Both numbers matter: the second shows the harness can see what it claims to look for. R7 R8

Layer 3 — the engineer's depth

One seam for every block

All block traffic of the writer goes through a small interface, Store, with five operations: read a block, write a metadata block, write a data block, order(), and sync(). order() means "everything written so far must be on the medium before anything written later"; in this chapter's DirectStore it is a cache flush, in F3-45's JournalStore it becomes something cheaper. Separating metadata from data writes costs nothing here and is exactly what ordered-mode journaling needs next. The block device itself (BlockDev) holds the image in memory and appends every write and flush to the write stream, which is the role a recording layer in your kernel's block cache plays when the harness runs your OS. R4

The write paths and their order

Create (and mkdir, symlinks): allocate the inode (inode bitmap, group descriptor, superblock), write the complete inode (and for a directory its first block with . and ..), flush, then add the directory entry. For mkdir, the parent's link count (for the child's ..) is raised and flushed before the name appears, so a crash can leave the count too high (acceptable) but never too low. Fast symlinks store targets under 60 bytes in the inode's pointer area and need no data block. D1

Write: map each logical block, allocating data blocks and any new indirect blocks; write the data and the new indirect blocks; flush; write the inode (size, i_blocks, direct pointers); then, after another flush, rewrite any existing indirect block that gained a pointer. New indirect blocks are written before anything points to them; an existing one is updated only after the new data it points to is durable. With 1 KiB blocks, 12 direct pointers cover 12 KiB, the single indirect block 256 more blocks (to 268 KiB), the double indirect block 65,536 more (to about 64 MiB). The workload's large files are 270,000 to 320,000 bytes, so they always use the double indirect block. A write at an offset beyond the end leaves pointers at 0: a hole. D1 R4

Truncate: zero the tail of the new last block, clear pointers in kept indirect blocks, flush, write the inode with the new size and pointers, flush, and only then free the blocks in the bitmap. Freeing first would let a crash leave a block that is both free and still pointed to; the next allocation would give it to a second file. Unlink: remove the name, flush, decrement the link count (and, at zero, set the deletion time), flush, then free the blocks and the inode. D3

Link: raise the link count, flush, add the name. Rename within or across directories: raise the link count, flush, add the new name, flush, remove the old name, flush, lower the count. At every cut the file has at least one name and a link count at least as high as its number of names. ext2 itself does not raise the count during a rename; this writer does so on purpose so that the in-between state (two names) is a valid ext2 state with a correct count. D3

Note

What this writer does not do, so you know what your own driver must add: triple indirect blocks (the curriculum's "files above 4 GiB" need them, and the large-file feature for sizes over 2 GiB); renaming over an existing name (POSIX rename replaces the target atomically); renaming and removing directories; long symlinks in a data block; hashed directory indexes (the writer clears the index flag it does not maintain). The image is 16 MiB with 1 KiB blocks, chosen so 500 checks run in about two minutes.

The harness, precisely

The crash tool applies the F3-43 model to a recorded stream. For a seed it draws a cut point uniformly among the stream's records, finds the last flush before the cut, applies every write before that flush, and applies each write after it with probability one half. It also prints every promise recorded before the cut: a promise is written by the workload right after an fsync of a newly written file returned, and names the file and the expected bytes. To keep the check simple, promised files are never modified, renamed or removed afterwards. R6

The judge for structure is e2fsck -fn: it reads everything and changes nothing, so its report describes the crash state, not a half-repaired one. The harness compares every line with regular expressions for the declared categories; "count too high" lines are accepted only if the stored number is larger than the counted one. Any other line is damage. The judge for contents is debugfs, which reads the image with e2fsprogs' own library and dumps each promised file. Neither judge shares code with the writer. D2 R7

The careful run's statistics also tell you what the design costs. The 300-operation workload issued 18,456 block writes and 596 flushes. In 484 of 500 crash images, e2fsck found acceptable leftovers (free counters in 425, leaked blocks or inodes in 467, orphan inodes in 166); in 16 it found nothing. A real system would reclaim those leaks with a background scan or at the next check. A journal (F3-45) removes even those, because replay makes every multi-block update atomic. R5 R7

How this differs from the milestone as written

FS1's harness "runs a random workload in your OS, cuts QEMU off at a random moment, then runs e2fsck on the image". This build ran the writer as a host program on an in-memory image and replayed its recorded write stream instead of killing QEMU. The replay is stricter in one way (the cache is assumed to reorder anything between flushes, which QEMU's default cache modes may not do) and weaker in another (it tests the writer, not your block driver's flush path). When you port the writer into your kernel, keep the recording layer in your block cache and run both: replay for reproducible failures, a real QEMU kill for the flush path. C1

Not verified — check before relying on this

Untested on hardware, and not run inside a kernel. No QEMU instance was killed and no disk lost power in this build. The FS1 acceptance clause "Files above 4 GiB and sparse files read back identically on the Linux host" is only half done: sparse files of this writer are read back by debugfs (no mount was possible in the container), and files above 4 GiB were not attempted. To complete it: add triple indirect blocks and the large-file feature, make a larger image, and mount it read-only on a Linux host.

How the hardware actually does it

The writer's order() becomes, in your kernel, "flush the block cache's dirty blocks written so far, then send the device's flush command and wait for it to complete". With virtio-blk (DR301, milestone C4) that is a request of the flush type, issued after the earlier write requests have completed. With AHCI it is the ATA FLUSH CACHE EXT command; with NVMe, the Flush command. Two details catch people: the block cache must not reorder writes across an order() (a cache that writes dirty blocks back in block-number order breaks every rule above), and the driver must wait for the earlier writes to complete before issuing the flush, because a flush covers completed writes. D4 C1

Not verified — check before relying on this

Untested on hardware. The statement that a flush covers only writes that completed before it is the author's reading from memory of the NVMe and VIRTIO specifications (not opened). Check the "Flush" command description in the NVMe Base Specification and the block device section of the VIRTIO specification, and the AHCI and ATA documents for FLUSH CACHE EXT, for the device you drive.

Safety

A bug in a write path or in the flush path corrupts the disk it runs on. Run your kernel's version in QEMU on an image file first; on real hardware, only on a disk whose contents you may lose, with every other disk disconnected.

Where the analogy breaks


    

  • The porter's list in the story is written by the porter. The write stream is written by the file system's own block layer; if that layer has a bug (writes missing from the recording, or a flush recorded but never sent), the replay tests a different file system from the one that runs. In your kernel, record as close to the driver as you can.
    • 

  • A librarian inspecting a library notices that a card is "wrong" only by comparing it with the shelf. e2fsck can only compare structures with each other; a file whose data blocks are all present but hold the wrong bytes passes the check. That is why the harness has a second judge for contents.
    • 

  • Coin tosses for "carried or not" treat every unflushed write alike. Real devices drain caches with patterns (by position on a disk, by flash page), so some states are far more likely than others; the replay covers them evenly, including rare ones.
    • 




Common mistakes and debugging


    

  • A block cache that writes back in its own order. Sorting dirty blocks by number before writing them is a common optimisation; across an order() it destroys the design. Keep a barrier: everything dirtied before order() is written and flushed first.
    • 

  • Freeing before unlinking pointers. The most damaging single mistake: a crash leaves a block free and pointed to, and the next allocation shares it between two files. e2fsck reports "multiply-claimed blocks" much later.
    • 

  • Forgetting the indirect blocks in i_blocks. e2fsck reports "i_blocks is X, should be Y". Count every allocated block of the file, data and indirect, in 512-byte units.
    • 

  • Running e2fsck without -f. A file system marked clean is not checked at all; the harness then reports success for every image.
    • 

  • Running e2fsck -y or -p in the harness. The report then mixes findings with repairs and the image is changed; use -n on a copy.
    • 

  • A harness that cannot fail. If the careless build passes too, the harness is broken (wrong image, wrong exit code handling, flushes ignored). Always keep a known-bad build in the test suite.
    • 

  • Accepting "ref count is 1, should be 2". A link count that is too low is damage: the file will be freed while a name still points to it. The harness accepts only counts that are too high.
    •

Summary


    

  • Every ext2 write path has a safe order: allocate and write before pointing; unpoint before freeing; add the new name before removing the old; keep link counts at least the number of names.
    • 

  • Each "before" is a flush on a device with a write cache; a block cache must not reorder across it.
    • 

  • With that order, a crash leaves only leaks, wrong counters, orphans and counts that are too high: the acceptable list.
    • 

  • A write stream plus the F3-43 model gives reproducible crash images; e2fsck -fn judges structure and debugfs judges the bytes of fsynced files.
    • 

  • The careful build passed 500 cuts with no damage and 9,787 promise checks; the careless build failed 65 of 100.
    • 

  • Reading an e2fsck report means mapping each line to a lost or landed write.
    •
