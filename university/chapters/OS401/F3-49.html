Story hook

The neighbouring school runs its library differently. Everything, even the catalogue itself, is a numbered form in one big register: form 0 describes the register, form 5 is the main hall, and every book has its own form listing its title, its owner and where its pages are kept. The neighbours never published their rules. What we know comes from people who studied the register for years and wrote down what they found.

The forms are two pages long. To catch a form whose second page was swapped for an older one, the clerk writes the form's current serial number at the foot of every page, and keeps the words that were there in a box on page one. A reader checks that every foot carries the same number, then puts the original words back.

Our library may borrow from the neighbours, but must never write in their register: we do not know all their rules, and a wrong entry would damage a library we cannot repair. This chapter reads NTFS and never writes it. Its forensic lab is a reader that checked the numbers at the foot of each page but forgot to put the original words back.

What you will be able to do

  • Find the Master File Table from the boot sector, read MFT records through their update sequence (fixups), and fall back to $MFTMirr when record 0 is damaged.
  • Parse attributes, resident and non-resident, and decode run lists with signed offsets and sparse runs.
  • Walk a directory's $I30 B-tree in order and look up a name by descending it, with NTFS's case-insensitive collation.
  • Refuse what is unsafe or unknown: torn records, compressed or encrypted data, attribute lists, and any request to write; warn on a dirty volume.
  • Judge the evidence for a reader built without a specification, and plan the acceptance test on a Windows-made volume.
Jargon box
NTFS
Simple words: Windows's main file system. Analogy: the neighbouring school's library, rules unpublished. Precise: the New Technology File System, in which all metadata, including the allocation bitmap and the MFT itself, is stored as files described by MFT records; Microsoft has not published an on-disk specification, and the structures used here come from reverse-engineering documentation. D1 D2
Master File Table (MFT)
Simple words: a table with one fixed-size record per file and directory. Analogy: the master register. Precise: the file $MFT (record 0), whose records (commonly 1 KiB) start with "FILE"; records 0–15 are system files ($MFT, $MFTMirr, $LogFile, $Volume, $AttrDef, the root "." at 5, $Bitmap, $Boot, ...). D1
Attribute (resident, non-resident)
Simple words: one piece of a file's description, such as its name or its contents, stored in the record or out on the disk. Analogy: a section of the form; a short one is written on the form, a long one says which shelves hold it. Precise: a typed, optionally named record part (0x10 standard information, 0x30 file name, 0x80 data, 0x90 index root, 0xA0 index allocation, 0xB0 bitmap, ...); a resident attribute holds its value in the record; a non-resident one holds a run list and sizes. D1
Run list (data runs)
Simple words: a compact list of "this many clusters, starting there". Analogy: shelf ranges written as "3 places from shelf 62, then 3 from three shelves back". Precise: mapping pairs: a header byte whose low nibble is the length field's size and high nibble the offset field's size; the offset is signed and relative to the previous run; an offset size of 0 is a sparse run; a 0 header ends the list. D1
Update sequence (fixups)
Simple words: a check that every 512-byte piece of a record was written at the same time. Analogy: the form number at the foot of every page. Precise: before writing, the last two bytes of each 512-byte stride of a record or index block are saved in the update sequence array and replaced by the update sequence number; a reader verifies all strides carry the number, then restores the saved bytes. D1
$I30 index
Simple words: a directory's sorted list of names, as a B-tree. Analogy: the hall's card index, with guide cards that tell you which drawer to open. Precise: the index named $I30 on file names: the root node in $INDEX_ROOT (in the record), further nodes in "INDX" blocks of $INDEX_ALLOCATION, with a $BITMAP of used blocks; entries carry a file reference and a copy of the $FILE_NAME value, and a subnode VCN when they have a child. D1
$MFTMirr
Simple words: a spare copy of the first records of the MFT. Analogy: a copy of the register's first forms kept in another room. Precise: the file at record 1 holding copies of at least records 0–3, at a cluster given in the boot sector, used when record 0 cannot be read. D1
Dirty volume
Simple words: a volume that Windows did not finish closing. Analogy: a register left open on the desk with a half-written form. Precise: bit 0x0001 of the volume flags in $Volume's $VOLUME_INFORMATION; metadata may be mid-change, and $LogFile may hold transactions only Windows (or a full log implementation) can replay. D1 D3

Layer 1 — the kid explanation

In this library, everything is a form in one big register, even the list of free shelves. To find a book, you open the register at form 5 (the main hall), look the name up in the hall's card index, which tells you a form number, and that form tells you where the pages of the book are.

Each form is two pages. The clerk writes the same number at the bottom of both pages, so you can tell if one page is from an older version. If the numbers disagree, you put the form aside and say so. And you never write in this register: it is not ours.

Layer 2 — the student explanation

NTFS puts all metadata in files. The boot sector gives the geometry and the cluster of the MFT; MFT record 0 describes the MFT itself (its $DATA run list says where every other record is); record 5 is the root directory; record 6, $Bitmap, is the cluster allocation bitmap; record 3, $Volume, holds the name, the version and the flags. A file's record holds attributes: standard information (times, flags), one or more file names (each with the parent directory's reference), and data. Small data is resident in the record; larger data is non-resident, described by a run list. D1 D2

Directories are B-trees of file names, sorted by the upper-cased UTF-16 name using the volume's $UpCase table. Small directories fit in $INDEX_ROOT; larger ones keep the root in the record and the other nodes in 4 KiB INDX blocks. Records and INDX blocks are protected by the update sequence, so a reader can tell when the sectors of one were written at different times. D1

There is no official specification. The structures are known from the Linux-NTFS project's documentation, Carrier's forensic analysis book and Windows Internals; the curriculum says so plainly: "Honest: no official specification exists; expect gaps." This build had no Windows and no ntfs-3g or mkntfs, so the lab writes its own test volume with a generator and reads it with a separate reader. libblkid's NTFS probe and file are the independent checks, and they read only the boot sector and a little of the MFT. C1

Write support is out of scope by rule. FS6's acceptance test includes "the driver refuses to mount for writing". The lab's reader opens the image read-only and contains no code that writes; a kernel driver should return a read-only error for any write mount, and a dirty volume should be read with a warning, never "fixed". C1

Layer 3 — the engineer's depth

Boot sector and record headers

The fields the reader uses: OEM ID "NTFS " at 3, bytes per sector at 0x0B, sectors per cluster at 0x0D, total sectors at 0x28 (64-bit), MFT cluster at 0x30, mirror cluster at 0x38, clusters per MFT record at 0x40 and per index block at 0x44, serial number at 0x48, signature 55 AA at 510. The two size bytes are signed: a positive value counts clusters, a negative one n means 2−n bytes. Our generator writes 0xF6 = −10 for 1,024-byte records and 1 for 4,096-byte index blocks (one cluster). file printed "bytes/RecordSegment 2^(-1*246)": it read the byte as unsigned, so even the independent tool's interpretation needs checking. libblkid accepted the boot sector and found the label in $Volume, which it can only do by following the MFT location and parsing a record. R2

An MFT record header: "FILE", update sequence offset (4) and count (6), log sequence number (8), sequence number (0x10), hard link count (0x12), first attribute offset (0x14), flags (0x16: 1 in use, 2 directory), bytes used (0x18), bytes allocated (0x1C), base record reference (0x20), next attribute instance (0x28), record number (0x2C). An attribute header: type (0), length (4), non-resident flag (8), name length and offset (9, 0x0A), flags (0x0C: 0x0001 compressed, 0x4000 encrypted, 0x8000 sparse), instance (0x0E); then for resident attributes value length (0x10) and offset (0x14), and for non-resident ones the VCN range (0x10, 0x18), the run list offset (0x20), and allocated, data and initialised sizes (0x28, 0x30, 0x38). The real dump of $MFT's own record shows the result R5: a non-resident $DATA of 187,392 bytes (183 records) in two runs, 6 clusters at 4 and 40 at 1,536. D1

Not verified — check before relying on this

Every NTFS offset and rule in this chapter is from the author's memory of the Linux-NTFS documentation and Carrier (neither opened in this build), and both the test image and the reader were written by the same author from the same memory: a misreading shared by both would pass every test in the lab. Confirmed independently: the boot sector fields libblkid and file print (OEM ID, geometry, MFT and mirror clusters, record size byte, serial) and enough of $MFT and $Volume for libblkid to find the label (R2). Not confirmed by anything independent: the attribute header layouts, the $FILE_NAME and $STANDARD_INFORMATION values, the index entry and INDX block layouts, the collation, the $Bitmap semantics, and the run list encoding. A Windows-made image (FS6's acceptance test) is the only real check; until then, read this chapter as a hypothesis with a test harness.

Run lists: fragmented and sparse

The generator places fragmented.bin (10 clusters) in three runs, the second before the first on disk, so the second offset is negative. The reader decoded: 3 clusters at LCN 62 (offset +62), 3 at LCN 59 (offset −3), 4 at LCN 65 (offset +6). sparse.vhd (1 MiB, 256 clusters) has data only in clusters 0 and 128: 1 cluster at 82, 127 sparse, 1 at 83 (offset +1, relative to the last real run, not to the sparse one), 127 sparse; its attribute flags are 0x8000. Reading it returns the full 1 MiB with zeros for the sparse runs, identical to the host file. R4 R5

Two rules in data() matter for real volumes. Bytes past the initialised size read as zeros even if clusters are allocated (Windows preallocates). And compressed or encrypted attributes are refused rather than returned raw: compressed data on disk is LZNT1 in 16-cluster units, and returning it as if it were the file would be silent corruption. The same refusal applies to records with an $ATTRIBUTE_LIST (0x20), which a large or very fragmented file needs when its attributes no longer fit one record; FS6 lists attribute lists in its build list, and this reader does not have them yet. Both refusals were added for honesty and are untested: no image in this build contains either. C1

The $I30 B-tree

An index node starts with a header: offset of the first entry, bytes used, bytes allocated, flags (1 = has children). Each entry: file reference (8 bytes: record number in the low 48 bits, sequence number in the high 16), entry length, key length, flags (1 = has a subnode, 2 = last entry), the key (a copy of the $FILE_NAME value: parent reference, times, sizes, flags, name length at 0x40, namespace at 0x41, name from 0x42), and if it has a subnode, the child's VCN in the entry's last 8 bytes. The last entry has no key and may still have a subnode, for names greater than every key. D1

The lab's Photos directory has 150 entries: the root in record 26 holds separators, and the leaves are in INDX blocks in a 5-cluster $INDEX_ALLOCATION at LCN 85. The lookup of IMG_0100.JPG compares with the root's keys, takes the subnode of the first key greater than the name, reads INDX VCN 2, and finds record 128. Here a VCN counts clusters because the index block size equals the cluster size; for blocks smaller than a cluster the unit is said to be 512 bytes, which the reader implements but no image tested. The in-order walk also checks that every key lies between its bracketing keys: that check is what produced the forensic lab's warnings. R4 R5

Names: Windows can give a file a second, DOS 8.3 name (namespace 2) as another $FILE_NAME and another index entry; the reader skips namespace 2 entries so files are not listed twice. The generator writes only Win32 names (namespace 1). The collation upper-cases through the volume's $UpCase; both tools use a built-in table (ASCII, Latin-1, Greek) that the generator also writes as $UpCase, so a real volume's ordering of other scripts was not exercised. R3

Torn records, the mirror, and the dirty flag

The lab damaged a copy of the volume in two places R6: the end of stride 2 of notes.txt's record (28) got 02 00 instead of 01 00, as if its second sector came from a later write; and the end of stride 1 of record 0 got 07 00. The reader listed everything except notes.txt, which it reported as refused with "update sequence mismatch in stride 2 (torn or damaged write)", and exited 3. It read record 0 from $MFTMirr and said so. The check reported both as problems and exited 4. Nothing was guessed and nothing was repaired.

A volume with the dirty flag set (the generator's --dirty option) is read with a warning, and the image's SHA-256 is unchanged afterwards. R7 On real Windows systems the flag is also set by a hibernated "Fast Startup" shutdown, in which case the on-disk state may be stale relative to what Windows will resume with; reading is still safe, but what you read may not be what the user last saw. D3

Not verified — check before relying on this

The Fast Startup and hibernation behaviour, the meaning of other volume flag bits, and whether Windows itself refuses a record with a fixup mismatch or tries $LogFile first, are from memory and were not tested. $LogFile was not parsed at all (the generator writes zeros there). Check Windows Internals' file-system chapter and the Linux-NTFS documentation, and test with a volume made dirty by a real Windows VM (power off the VM while it writes).

How the hardware actually does it

The update sequence exists because a 1 KiB record spans two 512-byte sectors and a disk guarantees at most that a single sector is written whole: power can fail between the two (F3-43's torn write). The stride stays 512 bytes even on disks with 4,096-byte sectors, where both strides of a record may fall in one physical sector and the check then rarely fires. INDX blocks of 4 KiB have eight strides. A write cache that reorders sectors (F3-43) can produce exactly the lab's damage: a new second sector with an old first. D1 D2

Not verified — check before relying on this

Untested on hardware. No disk, and no Windows-made volume, was used; damage was simulated by changing two bytes in an image. The 512-byte stride on 4Kn disks and the atomicity statements are from memory: check them in the documentation and with a 4Kn virtual disk in a VM.

Safety

Work on a copy of the volume, never on a disk Windows uses. Attach images read-only (a read-only loop device or a VM disk with read-only set). Never try to "fix" a dirty or torn NTFS volume with your own code; that is what Windows's chkdsk is for, on a backup.

Worked example

Encode and decode the run lists of the two odd files by hand, with the rules from the jargon box.

  • fragmented.bin, runs (3 @ 62), (3 @ 59), (4 @ 65). First run: length 3 needs 1 byte, offset +62 = 0x3E fits a signed byte: header 0x11, then 03 3E. Second: offset 59 − 62 = −3 = 0xFD: 11 03 FD. Third: 65 − 59 = +6: 11 04 06. End: 00. Total 10 bytes for 10 clusters.
  • Decode 11 03 FD back: low nibble 1 (length size), high nibble 1 (offset size); length 3; offset byte 0xFD has its top bit set, so it is negative: 0xFD − 0x100 = −3; LCN 62 − 3 = 59. This is the "(offset -3)" in R5.
  • sparse.vhd, runs (1 @ 82), (127 sparse), (1 @ 83), (127 sparse): 11 01 52, 01 7F (offset size 0 = sparse), 11 01 01 (83 − 82: the sparse run does not move the reference), 01 7F, 00.
  • A trap: offset +200 does not fit a signed byte (top bit set would mean negative), so it needs two bytes, C8 00, and the header becomes 0x21.

These byte sequences come from the rules as implemented in encodeRuns (ntfs.h, lines 74–95); the lab did not dump the raw bytes, but the decoded runs in R5 are what the reader got back from them.



Then the fixup on notes.txt's record. $STANDARD_INFORMATION starts at 0x38 and is 96 bytes long; $FILE_NAME for a 9-character name is 112 bytes; so $DATA's header is at 264 and its resident value at 264 + 24 = 288. Stride 1 ends at record offset 510, which is file offset 510 − 288 = 222. Those two bytes of the text were saved in the update sequence array, and the disk holds 01 00 in their place. Keep that number for the forensic lab.

Where the analogy breaks


    

  • A clerk writes the form number on each page deliberately. On disk, the number replaces two real bytes of content: a reader that checks but does not restore reads wrong data with no error (the forensic lab).
    • 

  • The neighbours' register is just unpublished, not secret; but a register you have never seen a real copy of is worse than unpublished. The lab's "register" was made by us, so agreeing with it proves little.
    • 

  • "Never write in their register" is a policy in the story. In a driver it must be enforced in code: no write path at all, and a mount for writing refused.
    • 




Common mistakes and debugging


    

  • Checking fixups but not restoring them (or restoring without checking). Both must happen, in that order, before any field of the record is used.
    • 

  • Treating the run offset as unsigned or as absolute. It is signed and relative to the previous non-sparse run.
    • 

  • Using the full 64-bit reference as a record number. Mask off the sequence number (high 16 bits).
    • 

  • Returning compressed or encrypted data raw. Refuse until implemented.
    • 

  • Listing DOS names as extra files. Skip namespace 2 entries, or show them as aliases.
    • 

  • Ignoring the initialised size. Bytes past it are zeros, whatever the clusters hold.
    • 

  • Trusting the generator. If reader and generator agree, look for a third opinion: libblkid, ntfsinfo from ntfs-3g, or a Windows-made image.
    • 




Transition box

Where you came from: F3-48 read a write-once format whose rules are public, and let firmware judge the boot path. What carries over: independent probes as evidence, UTF-16 names and case folding, B-tree directories (as in ext4's htree, F3-46), torn-write detection (F3-43), and refusing what you cannot read correctly. Summary


    

  • NTFS stores everything, including the MFT and the bitmap, as files described by MFT records found through record 0.
    • 

  • Records and INDX blocks carry an update sequence: check every stride, then restore the saved bytes; refuse on mismatch, and use $MFTMirr for record 0.
    • 

  • Attributes are resident or non-resident; run lists use signed relative offsets and sparse runs.
    • 

  • Directories are $I30 B-trees in case-insensitive collation; lookups descend one node per level.
    • 

  • Read-only means no write path at all; dirty volumes are read with a warning; unknown features are refused.
    • 

  • In this build, the generator and reader agree and libblkid accepts the boot sector and label; nothing else is independent, and FS6's Windows test was not run.

Answers to Check yourself


    

  1. 0xF6 as a signed byte is −10, so records are 210 = 1,024 bytes. 0x02 is positive: 2 clusters per record (8 KiB with 4 KiB clusters).
    2. 

  2. 21 10 00 01: length size 1, offset size 2; length 0x10 = 16 clusters; offset 0x0100 = +256: LCN 256. 11 08 F0: length 8, offset 0xF0 = −16: LCN 240. 00: end. So 16 clusters at 256, then 8 at 240.
    3. 

  3. Checking tells you all strides were written together; restoring puts back the two real bytes per stride that the number replaced. Skip the check and torn records are used as if whole; skip the restore and every record and index block has two wrong bytes per 512, silently.
    4. 

  4. Whether all index entries (each a copy of a $FILE_NAME, about 80–100 bytes for short names) fit in the space left in the directory's MFT record for $INDEX_ROOT. 150 entries cannot fit in 1 KiB; 5 can.
    5. 

  5. Exit 1 means the reader failed (could not run); 3 means it ran and produced a listing, but some entries were refused. A script copying files must distinguish "nothing read" from "all but these read".

Forensic lab answer key


    

  1. IMG_0063, IMG_0027, IMG_0099 and IMG_0135 appear as IMG_00^A3, IMG_00^A7, IMG_00^A9 and IMG_01^A5 (the CRC-32 values match the missing names'); one character of each name became U+0001. In each case the odd character is the one that falls on the last two bytes of a 512-byte stride of an INDX block.
    2. 

  2. From the update sequence number: the generator writes 1, and the reader checked that every stride ends in 0x0001 but did not put the saved bytes back.
    3. 

  3. The resident value starts at record offset 288, and stride 1 ends at 510: file offset 222, the 223rd byte (cmp counts from 1). The disk holds 01 00 there; the restored bytes are the original text, "he" of "the" (from "line 04: the quick...", where od shows "t" followed by 01 00).
    4. 

  4. The order check in walk found keys out of order (a name with U+0001 sorts before the names around it) and warned on standard error, but warnings do not refuse anything, so the exit code stays 0. A reader should treat index disorder as a reason to look harder.
    5. 

  5. The check verifies that strides carry the right number, which they do; the damage is introduced by the reader's own missing restore, after the check, and the mirror comparison compares two copies read with the same mistake.
    6. 

  6. ntfs.h line 48: the FORENSIC_SKIP_RESTORE build removes the restore loop in unprotect. Its effect appears only where content happens to cross a stride end (some names, some resident files), so it looks like scattered bit rot rather than a systematic bug. The give-away is the position: always the last two bytes of a 512-byte stride, always the value of the update sequence number.
