Story hook

In the school library, Ms Okafor is moving a new atlas onto shelf 12. Three things must change: the atlas must stand on the shelf, the catalogue card must say "shelf 12", and the shelf chart at the desk must mark one more place on shelf 12 as taken. She writes the card first, because the card box is next to her. Then the lights go out. The power cut lasts all night.

In the morning a pupil looks up the atlas. The card says "shelf 12". On shelf 12, in the place the card names, stands an old dictionary that was thrown out last year and never removed. The shelf chart says the place is free, so the next librarian will put another book there. Nothing is broken in a way anyone can see, and yet the catalogue now lies twice.

Ms Okafor's mistake was not slowness. It was the order of her three steps, and the fact that she could not know which of her steps were really finished when the lights went out. A computer's file system has exactly her problem, made worse: the disk has its own helpers who carry the writes to the shelves in whatever order suits them. This chapter is about the rules that keep the catalogue truthful whenever the power goes.

What you will be able to do

  • Enumerate every disk state a power cut can leave behind for a given sequence of writes and flushes on a device with a volatile write cache, and classify each state as consistent, repairable, or damaged.
  • Explain the five strategies of curriculum section 7.2 (checker after the crash, careful ordering and soft updates, journaling, copy-on-write, log-structured) and where each puts its single atomic step.
  • Name the device commands that give ordering and durability (cache flush, Force Unit Access) for NVMe, ATA, SCSI and virtio-blk, and state what the file system can and cannot assume about atomic writes.
  • Write an application update that survives a crash (write a temporary file, fsync, rename, fsync the directory), and verify its system calls with strace.
  • Design a crash test: record a write stream, cut it at every point or at random points, let the cache drop unflushed writes, then check the image and the files whose fsync had returned.
Jargon box
Crash consistency
Simple words: the file system is still correct, or can be made correct, whenever the power is cut. Analogy: the catalogue never sends a pupil to the wrong book, even after a power cut in the middle of shelving. Precise: the property that every on-disk state reachable by a crash at any point (with any subset of unflushed writes lost) satisfies the file system's invariants after the defined recovery step, and that every operation acknowledged as durable is preserved. D1
Volatile write cache
Simple words: memory inside the disk that holds writes for a while before they reach the medium; it forgets everything when the power goes. Analogy: the porter's trolley in the corridor: books on it are not yet on any shelf. Precise: a device-side buffer that may acknowledge a write before the data is on non-volatile media and may write cached blocks to the media in any order. D7
Cache flush
Simple words: a command that tells the disk "put everything you are holding onto the medium, and tell me when it is done". Analogy: the porter's signed delivery note: everything on the trolley is now on a shelf. Precise: a device command (NVMe Flush, ATA FLUSH CACHE EXT, SCSI SYNCHRONIZE CACHE, virtio-blk flush request) that completes only after all previously completed writes are on non-volatile media. D7 D8 D9
Force Unit Access (FUA)
Simple words: a flag on one write that says "do not finish this until it is on the medium". Analogy: carrying one book to the shelf yourself instead of putting it on the trolley. Precise: a per-command attribute of a write that makes its completion imply that this command's data is on non-volatile media; it says nothing about other writes still in the cache. D7 D8
Crash state
Simple words: one possible picture of the disk after a power cut. Analogy: which books happened to reach their shelves when the lights went out. Precise: the media contents given a cut after operation k: every write before the last completed flush is present, and any subset of the writes issued after it may be present. R1
File system checker (fsck)
Simple words: a program that reads the whole file system after a crash and repairs what it can. Analogy: a librarian who walks every shelf with the catalogue and fixes the cards. Precise: an offline tool that verifies cross-structure invariants (bitmaps against pointers, link counts against directory entries) and repairs violations; its run time grows with the size of the file system, and it cannot know which of two contradicting versions the user meant. D1
Journaling (write-ahead logging)
Simple words: first write down what you are about to change in a separate log, mark it complete, and only then change the real places. Analogy: the librarian's day book: "atlas to shelf 12, card updated, chart updated", ticked off before she starts. Precise: recording a transaction's new block images (physical journaling) or operations (logical journaling) in a log, followed by a commit record; after a crash, committed transactions are replayed and uncommitted ones ignored. D1 D2
Ordered mode
Simple words: only metadata goes into the journal, but file data is written to its final place before the metadata that points to it is committed. Analogy: the atlas is on the shelf before the day book's entry about its card is ticked. Precise: the ext3/ext4 default journaling mode: data blocks of a transaction are forced to disk before its commit record, so committed metadata never points to unwritten data. D11
Soft updates
Simple words: keep the disk consistent by tracking which writes depend on which, and writing them in a safe order. Analogy: the atlas first, then the chart, then the card, every time. Precise: a technique that records dependencies between cached metadata blocks and orders (and if needed rolls back) updates so that the on-disk image only ever contains leaks, never dangling pointers. D3
Copy-on-write (COW)
Simple words: never change a block in place; write a new copy and switch one pointer at the end. Analogy: write a whole new catalogue drawer, then swap the label on the cabinet. Precise: an update discipline in which modified blocks are written to free space and the tree of pointers above them is rewritten up to a root, which is updated with a single atomic write after a flush. D1
fsync
Simple words: the system call a program uses to ask "make this file safe on disk now". Analogy: asking the librarian to confirm that this one book, card and chart are done. Precise: a POSIX call that returns after the file's data and the metadata needed to retrieve it have been transferred to the storage device; whether the directory entry naming the file is included is not guaranteed by POSIX, hence the separate directory fsync. D10
Torn write
Simple words: a write that was cut in half by a power failure, leaving part old and part new. Analogy: half of a catalogue card rewritten. Precise: a multi-sector write of which only some sectors reached the media; devices guarantee atomicity only up to a documented unit, often one logical block. D7

The idea in pictures

Figure 1 shows where the uncertainty comes from. The file system sends writes to the device; the device may keep them in a volatile cache and move them to the medium in any order. Only a completed flush draws a line: everything before it is on the medium. Between two flushes, any subset of the writes may have landed when the power goes.

Figure 2 shows the same append done with a journal in ordered mode, with its two flushes as solid bars. A crash anywhere left of the first bar finds no commit block: recovery ignores the log and the old file is intact. A crash after the second bar finds a complete committed transaction: recovery replays it and the new file is intact. There is no third outcome, and the lab counts all 26 crash states to prove it.

Layer 1 — the kid explanation

A library is only useful if the cards tell the truth. When a librarian moves a book, three things change: the shelf, the card and the chart of free places. If the lights go out halfway, some of those changes are done and some are not.

The trick is to choose an order where a half-finished job is harmless. Put the book on the shelf before you write the card. Then a power cut can only leave a book with no card (annoying, but nobody is misled), never a card that points to the wrong book.

A second trick is a notebook. Before touching anything, write in the notebook what you are going to do, and put a big tick under it when the note is complete. After a power cut, read the notebook: a ticked note is done again from the start; an unticked note is crossed out. Either way, the library is right.

Layer 2 — the student explanation

A file system keeps several structures that must agree with each other: the data blocks, the inodes that point to them, the bitmaps that say which blocks and inodes are in use, and the directory entries that give names to inodes. One user operation, such as appending a block to a file, changes several of them: a data block D, the file's inode I (new size, new block pointer) and a bitmap block B (one more block in use). D1

The disk writes one block at a time, so between the first and the last of those writes there is a window in which a power cut leaves only some of them on the medium. There are two kinds of damage. A leak (B updated, I not) wastes a block but misleads nobody. A dangling pointer (I updated, D or B not) is worse: the file shows another file's old bytes, or the block is marked free and will later be given to a second file, so two files share it. D1

Disks make it harder because of their write cache. A write that the device has acknowledged may still be in volatile memory, and the device may write cached blocks to the medium in a different order than they arrived. The only tool the file system has is the cache flush: when a flush completes, every write that completed before it is on the medium. Order therefore exists only across flushes. D7 D9

Curriculum section 7.2 names five answers. Check after the crash (FAT, ext2): let anything happen, then run fsck, which reads every structure and repairs; it is slow on large disks and has to guess. Careful ordering (soft updates in FreeBSD's UFS): order writes so that only leaks are possible. Journaling (ext3, ext4, NTFS, XFS): write the changes to a log first, with a commit record, then in place. Copy-on-write (ZFS, btrfs, APFS): never overwrite live blocks; build the new version elsewhere and switch one root pointer. Log-structured (Sprite LFS, F2FS): the whole disk is a log. C1 D3 D4

Applications have their own share of the job. A program that wants its file to survive must call fsync, and a program that wants to replace a file atomically writes a new file, syncs it, renames it over the old one and syncs the directory. Many real programs get this wrong; one study traced popular applications and found such bugs widely. D5 D10

Layer 3 — the engineer's depth

A model you can count

Treat the device as follows. Each write, once issued, may land on the medium at any time until the next flush completes; a flush completes only when all writes issued before it have landed; a crash at any moment loses every write that has not landed. A crash after the k-th operation therefore leaves all writes before the last flush, plus any subset of the m writes issued since: 2m states for that cut. Summing over every cut point gives the full state space of a write sequence, small enough to enumerate for one operation and the basis of every crash-testing tool. D6 R1

Two refinements matter in practice. First, this model assumes each block write is atomic. Devices document an atomic write unit (for NVMe, in the namespace's atomic-write fields), and it may be a single logical block; a 4 KiB file-system block on a device with 512-byte sectors could tear. Second, the model ignores reads: recovery code sees the crash state and must not trust anything it has not validated. File systems defend against torn and stale blocks with checksums (ext4 metadata checksums, the JBD2 commit checksum, NTFS's update sequence arrays in F3-49). C1 D7

The device semantics in this section (that a completed flush covers all previously completed writes, that FUA covers only its own command, that atomicity is guaranteed only up to a reported unit, and that write caches may reorder) are the author's summary from memory of the NVMe Base Specification (Flush command; Force Unit Access; Atomic Write Unit Normal and Power Fail fields), the ATA/ATAPI Command Set (FLUSH CACHE EXT; WRITE DMA FUA EXT), SCSI Block Commands (SYNCHRONIZE CACHE) and the VIRTIO specification (block device, flush request and the VIRTIO_BLK_F_FLUSH feature). None was opened in this build. The lab's model is deliberately the most pessimistic reading; check each specification for the device you use, including whether its write cache is enabled at all.

Strategy 1: let it happen, then check

ext2 and FAT write in whatever order the block cache flushes, and recovery is a full check: e2fsck reads every inode, follows every block pointer, rebuilds the bitmaps it expects and compares; walks every directory and counts links. This catches everything that breaks a cross-structure invariant, so it is the ground truth the FS1 harness uses. Its two weaknesses are cost (work proportional to the size of the file system, not to the size of the last change) and ambiguity: if the inode points to block 700 and the bitmap says 700 is free, the checker can mark it used, but it cannot know whether block 700 holds the new data or another file's old bytes. It repairs the structure, not the contents. D1

Strategy 2: careful ordering and soft updates

The ordering rules of soft updates can be stated as three rules about pointers: never point to a structure before it has been initialised (write D and B before I); never reuse a resource before every pointer to it has been removed (clear the inode's pointer before freeing the block in the bitmap); and never reset the last pointer to a live resource before the new pointer has been set (for a rename, write the new name before removing the old one). Followed strictly, a crash can only leave leaks: blocks or inodes marked used that nothing references, and link counts that are too high. Those are harmless and can be reclaimed lazily in the background. D3

The naive way to follow the rules is to flush between the steps, which makes every metadata update synchronous. Soft updates instead keep per-block dependency records in the cache and write blocks in dependency order, rolling back not-yet-safe changes in a block's image when it must be written early. That machinery is notoriously intricate; F3-44 follows the rules with plain flushes, which is slow but easy to verify. D3

Strategy 3: journaling

A journal turns many writes into one atomic step: the commit record. A transaction writes the new images of every metadata block it changes into a log area, then a commit block; once the commit block is durable, the transaction is durable, and the in-place writes (the checkpoint) can happen lazily. Recovery scans the log, replays every transaction that has a valid commit block, and ignores the rest. Log space is reused only after the checkpoint is durable, which is recorded by advancing the start of the log in the journal superblock. D2

What goes into the log decides the mode. In data journaling, data blocks are logged too (everything is written twice). In ordered mode, only metadata is logged, and the data blocks a transaction makes reachable are written in place before the commit block, so committed metadata never points at garbage. In writeback mode, data and metadata are not ordered against each other: the file system stays consistent, but a file can show stale bytes after a crash. ext3 and ext4 default to ordered mode. D11

The flushes are the whole point. The commit block must not reach the medium before the log blocks it describes (and, in ordered mode, before the data blocks): otherwise the device may land the commit block first, the power goes, and recovery replays log slots that still hold an older transaction's contents onto live metadata. Hence the classic sequence: write data and log blocks, flush, write commit, flush, checkpoint. JBD2 adds an option to put a checksum of the transaction into the commit block so that a commit without its log blocks is detected and ignored, which allows dropping the first flush; the lab shows exactly what that does and does not protect. D2 D11 R1

The output of Listing 1 for strategies 3 to 5 is the most useful table in this course. With both flushes (strategy 3), all 26 crash states are "old" or "new". Without the first flush (strategy 4), 6 of 39 states replay stale journal slots over metadata ("CORRUPT") and 1 state shows a deleted file's bytes in the new file ("BAD"). The commit checksum (strategy 5) removes the 6 corrupt states, because recovery now refuses a commit whose log blocks are not the ones it describes, but the stale-data state remains: the checksum covers the log, not the data block D that ordered mode promised to write first. R1

Watch out

A checksum in the commit block is not a replacement for the data flush in ordered mode. It protects the log against itself. If you drop the flush before the commit, you must find another way to make sure the transaction's data blocks are durable before the commit can be, or accept writeback-mode semantics and say so.

Strategies 4 and 5: copy-on-write and log-structured

Copy-on-write file systems never overwrite a live block. An update writes new copies of the changed blocks, then new copies of every block on the path up to the root of the tree, flushes, and finally writes a new root (an "uberblock" or superblock with a higher generation number), flushes again. A crash before the root write leaves the old tree intact; after it, the new tree. There is no replay, and the price moves to allocation (free space fragments) and to write amplification on the path to the root. Checksums stored in parent pointers, as ZFS and btrfs do, make every read verifiable. D1

A log-structured file system takes the idea to its end: the whole disk is an append-only log of segments, inodes included, located through an inode map that is itself written to the log, with periodic checkpoints of where the map is. Recovery reads the last checkpoint and rolls forward through the log written after it. The cost is the cleaner that compacts partially dead segments; the benefit is large sequential writes, which is why the idea returned for flash in F2FS. D4

What applications are promised

None of this helps a program that does not ask. POSIX write returns when the data is in the page cache; only fsync (or fdatasync, which may skip metadata not needed to read the data back) asks for durability. rename is atomic with respect to other processes (an observer sees the old file or the new one), and on Linux file systems with journaling it is also atomic across a crash as a metadata operation. But the rename's durability needs an fsync of the directory, and a rename of a file whose data was never synced can leave a correctly named empty file after a crash, because the metadata transaction committed before the data was written. D5 D10

The robust pattern, Listing 2's replaceSafely, is therefore: create a temporary file in the same directory, write, fsync it, rename it over the target, open the directory and fsync it. Each step closes a specific window: the first fsync guarantees the new bytes exist before any name points to them (the soft-updates "initialise before pointing" rule, applied by the application); rename switches the name in one step; the directory fsync makes the switch durable before the program reports success. R3

Testing crash consistency

The tests in this course follow one recipe, used by research tools such as CrashMonkey and by Linux's dm-log-writes target: record every write and flush the file system sends to the device (a write stream); pick a cut point; build the image the device could hold at that point (everything before the last flush, plus a chosen subset of later writes); run recovery and a checker on it; and check every file whose fsync had returned. Choosing subsets randomly gives a fast random test (F3-44, F3-45); choosing them all gives an exhaustive test for small workloads (Listing 1). A real emulator power cut (killing QEMU with a cache mode that drops unflushed writes) tests the same thing less reproducibly. D6 D11 D12

Not verified — check before relying on this

QEMU's block cache modes (for example cache=unsafe, which ignores guest flushes, and cache=writeback, which honours them) and the exact behaviour of a killed QEMU process with each were not tested in this build: the harnesses of F3-44 and F3-45 replay recorded write streams instead. Check the QEMU documentation on block device cache modes before building a kill-based harness, and note that a host page cache sits between QEMU and the image file.

How the hardware actually does it

A drive's write cache is DRAM (or SRAM) on the controller board; hard disks use it to reorder writes by head position, and flash devices use it to gather writes into full flash pages. When the cache is enabled, the drive acknowledges a write as soon as the data is in that memory. The device interfaces give the host three tools: a flush command per device class (NVMe Flush; ATA FLUSH CACHE EXT; SCSI SYNCHRONIZE CACHE; a virtio-blk request of type flush if the device offers the flush feature); a FUA bit on individual writes; and a way to disable the write cache altogether. Enterprise flash devices commonly carry capacitors that let them write their cache out after the power fails ("power-loss protection"); when the device reports a non-volatile cache, flushes become cheap or unnecessary. D7 D8 D9

Your DR301 virtio-blk driver (milestone C4) already speaks the flush request if you implemented it; FS1 asks for "a flush call down to the block driver", which means your block cache must be able to say "flush now and wait", and your driver must turn that into the device command and wait for its completion before reporting success. A driver that completes flushes immediately without sending them makes every file system above it unsafe, silently. C1

Not verified — check before relying on this

Untested on hardware. No device with a real write cache was used in this build, and no power was cut. Whether a particular drive honours flushes, reports a volatile write cache, or has power-loss protection is a fact about that product: take it from the product's datasheet and from the identify data it returns (NVMe Identify Controller, the Volatile Write Cache field; ATA IDENTIFY DEVICE, write-cache support and enable bits), never from this chapter.

Safety

Crash tests belong in an emulator first. On real hardware, use only a disk whose contents you may lose, disconnect disks you care about, and never "test" by pulling the power of a machine whose file systems you need: a cut during a firmware update or on a device without power-loss protection can do more than lose the last write.

Where the analogy breaks


    

  • A librarian remembers what she was doing; a computer after a power cut remembers nothing that was only in memory. Recovery code sees only the disk, and must decide from the disk alone.
    • 

  • Books on the porter's trolley arrive in the order they were stacked, or at least one by one. A disk's cache may land the third write before the first, and may land half of a large write. The analogy hides reordering and tearing, which are the hard parts.
    • 

  • The day book is read by a person who can spot a smudged entry. A journal is read by code that replays bytes; without a checksum it cannot tell an old entry from a new one (strategy 4's "CORRUPT" states).
    • 

  • In a library, one card per book is natural. In a file system the same block can be pointed to by two inodes after a bad crash, and a checker must choose which one keeps it.
    • 




Common mistakes and debugging


    

  • Treating "the write returned" as "the data is safe". A completed write may be in the page cache or the device cache. Durability is a flush (device) or an fsync (application), and only after it returns.
    • 

  • Forgetting the directory. A new file's name lives in its directory. fsync on the file alone may not persist the name; sync the directory after creat, rename, link and unlink when it matters.
    • 

  • Testing on a fresh, zeroed disk. Stale bytes are what make dangling pointers visible. Listing 1 starts with a deleted file's data in D and an old transaction in the log for that reason; F3-44's harness reuses blocks.
    • 

  • Flushes that do nothing. A block driver that completes a flush without sending it, an emulator configured to ignore flushes, or a mount option that disables barriers all turn a correct file system into an unsafe one. Test the flush path itself: count flush commands in the write stream.
    • 

  • Running the checker in repair mode first. e2fsck -y changes the evidence. Always copy the image, run the checker read-only (-n), keep its report, and only then repair a copy.
    • 

  • Declaring acceptable damage after the test. FS1 asks for the acceptable categories "in the plan". Write them before the first run, as Listing 1's classify does, or every new failure will look acceptable.
    • 




Transition box

Where you came from: OS304 gave you a VFS with a block cache (F3-31), FAT32 with a careful update order (F3-32) and ext2 read and write checked by e2fsck (F3-33); DR301 gave you a virtio-blk driver (milestone C4). What carries over: the on-disk structures and the habit of letting an independent checker judge your images. What changes: correctness is no longer "the image is valid after a clean unmount" but "every image a power cut could leave is valid after recovery, and every fsync that returned is honoured". You reason about sets of possible disks, not one disk. Mini-project


A crash-state explorer for your own kernel. Add to your kernel's block layer (from OS304 and DR301) a recording mode: every write (block number and contents) and every flush is appended to a log on a second virtual disk or sent over the serial port. Write a host program that reads such a log, applies a cut and a random subset of the unflushed writes to a copy of the starting image, and runs e2fsck -fn on the result. Use it on a short workload of your OS304 ext2 driver (create, append, unlink) and report the categories you find.


Rubric. Recording is complete (every write and flush, in order, with contents) and tested with a known workload (3). The replay tool builds images exactly per the model of Layer 3, with an exhaustive mode for short logs (3). A written plan lists the acceptable categories before the first run (1). Results for at least 100 cuts with the real e2fsck report counts per category (2). One state of each category is explained by naming the writes that were lost (1).



Summary


    

  • One file operation changes several blocks; a power cut can leave any prefix of the issued writes plus any subset of the writes since the last completed flush.
    • 

  • A flush is the only ordering tool a device gives; FUA makes one write durable; atomicity is guaranteed only up to the device's documented unit.
    • 

  • Leaks are acceptable damage; dangling pointers and stale data are not. Decide the acceptable list before testing.
    • 

  • Careful ordering keeps damage to leaks; journaling makes the commit record the single atomic step; copy-on-write makes the root pointer that step; log-structured designs make the whole disk a log.
    • 

  • Ordered-mode journaling needs data and log blocks durable before the commit block; a commit checksum protects the log but not the data.
    • 

  • Applications must fsync, write new files under a temporary name, rename, and fsync the directory.
    • 

  • Crash testing records the write stream, cuts it, drops unflushed writes, recovers, and checks with an independent checker and the fsynced files.
    •

Answers to Check yourself


    

  1. After the fifth operation: A, B, C are durable and D is open: 2 states. Over all cuts: 1 (none) + 2 (A) + 4 (A, B) + 8 (A, B, C) + 1 (flush) + 2 (D) = 18.
    2. 

  2. Good answers say: a leak is space marked used that nobody points to; every pointer still leads to the right thing, so no reader is misled and the space can be reclaimed later. A dangling pointer leads a reader to something that is not what it claims (stale bytes, a block about to be given to another file), so data is wrong or two files end up sharing a block.
    3. 

  3. It removes the 6 "CORRUPT" states: a commit block whose log blocks are not the ones it describes fails the checksum and is ignored. The 1 "BAD: stale data" state remains: the commit and the log landed, the data block D did not, and the checksum does not cover D. Ordered mode needs D durable before the commit; only a flush (or FUA writes of D completed before the commit is issued) gives that.
    4. 

  4. (a) Initialise (here: allocate) before pointing: the bitmap must say "used" before an inode points at the block. (b) Never reuse before nullifying: clear the pointer first, then free. (c) Never reset the last pointer before the new one is set: write the new name first.
    5. 

  5. Without it, the rename (a metadata change) can be committed and become durable before the new file's data is written, because data writes may be delayed and allocated late. After a crash, settings.conf names the new inode, which has no data yet: an empty or zero-filled file, and the old contents are gone. The fsync forces the data out before the name points at it.
    6. 

  6. For the commit block alone, a FUA write (or a write followed by a flush) is enough, since the log blocks are already durable. FUA alone is not enough for the log blocks before the commit, because FUA on the commit says nothing about other writes still in the cache: the commit could be durable while log blocks are still cached. The log blocks need a flush (or each its own FUA write, completed) before the commit is issued.
    7. 

  7. With one flush at the end, the device may land the new root before the new leaves and interior blocks; a crash then leaves a root pointing at blocks that hold old or random contents. A flush must separate "all new blocks of the tree" from "the new root", and a second flush after the root makes the update durable.
    8. 

  8. Nothing about crash consistency on a real device: with flushes ignored, the test cannot distinguish a correct flush order from no flushes at all. (It may even be that every write landed in order.) The test must use a device model that drops unflushed writes.
    9. 

  9. fsck reads every inode and follows every pointer and directory, so its work grows with the number of files and blocks. Replay reads only the part of the log written since the last checkpoint, which depends on recent activity and the journal size, not on the disk size.
    10. 



Forensic lab answer key


    

  1. openat with O_TRUNC (size becomes 0: the old settings are gone from the file at this call), write of 21 bytes (into the page cache), close. There is no fsync.
    2. 

  2. Metadata: the inode's size set to 0 and its blocks freed (truncate), later the size set to 21 and a block allocated; data: the 21 bytes. The truncate is a metadata change that a journal can commit on its own, early; the data and the allocation can follow much later (delayed allocation), in another transaction.
    3. 

  3. The truncate is committed (the periodic journal commit, or another program's fsync pulling it in), the new data is still in memory, the power goes. Recovery restores a consistent file system in which settings.conf has size 0.
    4. 

  4. Old settings: yes, if the power goes before the truncate is committed. Half of the new ones: not for a 21-byte file in one block, but a larger file written in several blocks could be found partly written.
    5. 

  5. A different name for the new bytes (the old file is untouched while the new one is written: rules out "empty or half file" under the real name); fsync of the new file before rename (rules out a name pointing to unwritten data); rename plus fsync of the directory (rules out success being reported while the old name could come back).
    6. 

  6. Record the write stream of a save on a test disk, cut it at every point (or randomly, many times) with unflushed writes dropped, mount or check each image and assert that settings.conf holds either the complete old or the complete new contents. The unsafe version fails on the states where the truncate landed and the data did not.
