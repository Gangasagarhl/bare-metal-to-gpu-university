Story hook

The school photography club brings its camera card to the library computer. The card is large, so it is not FAT32; the camera formatted it as exFAT. The library's own system can read FAT32 (it has done since OS304), but this card shows nothing.

exFAT is FAT's younger relative. It keeps the idea of a table of "next place" numbers, but adds a free-place chart, lets a long file say "all my pieces stand side by side, no need to follow the table", and protects each catalogue card with a small check number. The club's movie files are large and usually written in one piece, so the camera mostly uses the side-by-side shortcut.

The shortcut has a price. When the card is nearly full and the free places are scattered, a new file cannot stand in one row. If a writer still claims "side by side" in that case, every reader will believe it, and the movie will end with someone else's photograph. This chapter writes and reads exFAT, and its forensic lab is that movie.

What you will be able to do

  • Describe the exFAT layout: boot region with its checksum sector and backup, FAT, cluster heap, allocation bitmap, up-case table and root directory.
  • Read and write directory entry sets (File, Stream Extension, File Name entries) with their set checksum and name hash, including names outside ASCII.
  • Choose between contiguous allocation with the NoFatChain flag and a FAT chain, and read both correctly.
  • Check a volume: boot checksums, entry-set checksums, and the allocation bitmap against the clusters the tree really uses.
  • Explain what can and cannot be verified without the reference implementations, and plan the milestone's acceptance test with Windows and exfatprogs.
Jargon box
exFAT
Simple words: the file system on large SD cards, camera cards and USB sticks. Analogy: a newer catalogue for big collections, related to the old FAT catalogue. Precise: Microsoft's Extended File Allocation Table file system, with a 32-bit FAT, an allocation bitmap, 64-bit file sizes, directory entry sets with checksums and an up-case table; its specification was published by Microsoft. D1
Boot region
Simple words: the first twelve sectors, describing the volume, followed by an identical backup. Analogy: the library's front door notice, with a copy at the back door. Precise: the main boot sector, eight extended boot sectors, an OEM parameters sector, a reserved sector and a boot checksum sector (a 32-bit checksum of sectors 0–10 repeated to fill sector 11); sectors 12–23 hold the backup. D1
Cluster heap
Simple words: the part of the volume where file contents and directories live, in clusters. Analogy: the shelves. Precise: the region starting at ClusterHeapOffset, divided into ClusterCount clusters numbered from 2. D1
Allocation bitmap
Simple words: one bit per cluster: used or free. Analogy: the free-place chart. Precise: a file in the cluster heap, described by a root-directory entry of type 0x81, whose bit n − 2 says whether cluster n is allocated; in exFAT it, not the FAT, is the authority on free space. D1
Up-case table
Simple words: a table that says what each character looks like in capitals, so that names can be compared without case. Analogy: the rule that "atlas" and "ATLAS" are the same card. Precise: a file (root entry type 0x82, with a checksum of its contents) mapping UTF-16 code units to their upper-case forms; used for case-insensitive name comparison and for the name hash. D1
Directory entry set
Simple words: the group of 32-byte entries that together describe one file. Analogy: one catalogue card made of several slips stapled together, with a check number on the first slip. Precise: a File entry (0x85: secondary count, set checksum, attributes, times), a Stream Extension entry (0xC0: flags, name length, name hash, valid data length, first cluster, data length) and 1–17 File Name entries (0xC1: 15 UTF-16 code units each). D1
NoFatChain
Simple words: a flag that says "this file's clusters are all next to each other; do not look in the FAT". Analogy: "all volumes stand side by side from place 5". Precise: bit 1 of the Stream Extension's general secondary flags; when set, the clusters are FirstCluster to FirstCluster + ⌈DataLength / cluster size⌉ − 1 and the FAT entries are undefined and must not be used. D1
Valid data length
Simple words: how much of a file has really been written; the rest reads as zeros. Analogy: reserved shelf places that are still empty. Precise: the Stream Extension's ValidDataLength, at most DataLength; bytes beyond it are undefined on disk and must read as zero. D1

Layer 1 — the kid explanation

The camera card keeps a chart of free shelf places, one tick per place. A file's card says where its first piece is and how long it is. If all its pieces stand in a row, the card says so, and you just walk along the shelf. If they are scattered, you follow the "next place" table, as in the old FAT library.

Each card also has a check number made from its contents. If the card is damaged, the number no longer fits. The only rule you must never break: never write "they stand in a row" when they do not.

Layer 2 — the student explanation

FAT32 (F3-32) has two weaknesses for large media: file sizes are limited to 4 GiB by a 32-bit size field, and finding free space means scanning the FAT. exFAT keeps the FAT for chains, but moves free-space tracking to an allocation bitmap and makes sizes 64-bit. It also lets a file skip the FAT completely: when a file's clusters are contiguous, its Stream Extension entry sets the NoFatChain flag, and readers compute the clusters from the first cluster and the length. Cameras writing large videos to a freshly formatted card get contiguous files almost always. D1

Directories hold 32-byte entries, but a file is described by a set of entries: a File entry with attributes and times, a Stream Extension entry with the flags, first cluster and lengths, and one File Name entry per 15 UTF-16 characters. The File entry stores a checksum over the whole set, and the Stream Extension a hash of the up-cased name, so lookups can skip non-matching names quickly. The root directory also contains entries for the volume label, the bitmap and the up-case table. D1

The boot region is protected by a checksum too: sector 11 is filled with a 32-bit checksum of sectors 0–10 (excluding the fields that change during use: the volume flags and the percent-in-use byte), and the whole region has a backup copy right after it. A reader that finds a wrong checksum must not mount the volume. D1

FS4's acceptance test needs Windows and exfatprogs, neither of which exists in this build. The lab therefore writes volumes with its own tool and checks them with the only independent exFAT code available, libblkid's probe, plus the tool's own checker. That is weaker evidence, and the chapter says exactly where. C1

Layer 3 — the engineer's depth

The boot sector and its checksum

The main boot sector starts with a jump (EB 76 90) and the name "EXFAT ", followed by 53 bytes that must be zero (where FAT's BIOS parameter block was, so that FAT drivers do not misread the volume). The fields this lab writes: VolumeLength (64-bit, at 72), FatOffset and FatLength (80, 84), ClusterHeapOffset and ClusterCount (88, 92), FirstClusterOfRootDirectory (96), VolumeSerialNumber (100), FileSystemRevision 1.00 (104), VolumeFlags (106), BytesPerSectorShift and SectorsPerClusterShift (108, 109), NumberOfFats (110), DriveSelect (111), PercentInUse (112), and the signature AA55 at 510. Extended boot sectors end with the signature AA550000. D1

The boot checksum is a rotate-right-and-add over every byte of sectors 0–10, skipping bytes 106, 107 and 112: c = ((c & 1) ? 0x80000000 : 0) + (c >> 1) + byte. The same rotate-and-add, on 16 bits, gives the entry-set checksum (skipping the checksum field's own two bytes), and on 32 bits over a table's bytes, the up-case table checksum. The name hash applies the 16-bit form to the up-cased name's UTF-16 code units, low byte then high byte. D1

Here the lab found its one piece of independent evidence. libblkid's exFAT probe reports TYPE=exfat with the right label and serial for the tool's volume; after one byte of boot code (byte 200) was changed without updating the checksum sector, the probe no longer recognised exFAT at all (it reported only a DOS partition table signature). So libblkid computes the boot checksum, and ours agrees with it. libblkid also found the label, which it can only do by locating the root directory through ClusterHeapOffset, SectorsPerClusterShift and FirstClusterOfRootDirectory and parsing the 0x83 entry. Independently confirmed here only: the boot sector fields libblkid needs, the boot checksum, and the root directory's volume label entry (R1, R4). Not independently confirmed: the entry-set checksum, the name hash, the Stream Extension field offsets, the bitmap and up-case entry layouts, the FAT entry values, the time-stamp format, the up-case table format, and the rules for ValidDataLength. Our checker agrees with our writer, which proves consistency, not correctness: both could share the same misreading. Before relying on any of it, read the specification's sections on the main boot sector, boot checksum, allocation bitmap, up-case table, File, Stream Extension and File Name directory entries, and run fsck.exfat (exfatprogs) and Windows on volumes your code wrote, as FS4 requires.

Entry sets in practice

The real dump of the lab volume's root directory shows the structure R2: slot 0 is the label (0x83, length 6, "CAMERA" in UTF-16); slot 1 the bitmap (0x81, first cluster 2, length 0x7FC = 2,044 bytes for 16,352 clusters); slot 2 the up-case table (0x82, checksum, cluster 3, length 0x100 = 256 bytes: 128 entries of 2 bytes); slots 3–5 the directory DCIM (File with secondary count 2 and attributes 0x10, Stream with flags 0x03 and length 4,096, one name entry); slots 6–9 the file Grüße aus Köln.bin (secondary count 3: one stream and two name entries for an 18-character name). The type byte's top bit means "in use": deleting a file clears it in every entry of the set, which turns 0x85 into 0x05, and so on. D1

Names are stored as written and compared after up-casing. The lab's tool reads /GRüßE AUS KöLN.BIN back as the file it wrote as /Grüße aus Köln.bin: the ASCII letters were up-cased by the table, while ü, ß and ö are the same in both spellings. A real up-case table maps ü to Ü too; the lab's table is deliberately minimal (ASCII only), which is allowed for a writer as far as the author recalls, but makes the volume's case-insensitivity weaker than Windows expects for non-ASCII names. R2

Allocation: bitmap, FAT and NoFatChain

The lab's allocator looks for one free run of the needed length in the bitmap. If it finds one, it marks the bits, writes no FAT entries, and sets NoFatChain in the stream flags (0x03 = AllocationPossible | NoFatChain). If not, it takes free clusters in order, marks the bits, and links them in the FAT with an end-of-chain marker, leaving NoFatChain clear (flags 0x01). The fragmentation test makes this happen on purpose: fill a 2 MiB card with 49 photos, delete every other one, then write a 15-cluster movie. The first free run long enough does not exist, so the movie gets clusters 5–14 and 25–29 with FAT[14] = 25, flags 0x01, and reads back identical. R6

Two consistency rules follow, and the checker tests both. First, the bitmap must equal the set of clusters reachable from the directory tree (through chains or NoFatChain ranges), plus the system files. Second, no cluster may belong to two files. A reader cannot detect a wrong NoFatChain flag from the entry alone; only the checker's cross-check of every file's clusters against every other file and against the bitmap can. R8

Two exFAT details the lab handles only partly. ValidDataLength can be smaller than DataLength (preallocated files); the tool always writes them equal and its reader does not zero the tail. And a FAT entry for a NoFatChain file is undefined, so a writer that converts a contiguous file into a fragmented one (appending when the next cluster is taken) must first write the FAT chain for the existing clusters, then clear the flag. D1

Crash consistency in exFAT

exFAT has no journal. The specification defines a VolumeFlags bit "volume dirty" that a driver sets before modifying metadata and clears when the volume is consistent again; a driver that mounts a volume with the bit set should run a check. The entry-set checksum turns a torn update of a set into a detectable error rather than a silent mixture of old and new fields. Ordering between bitmap, FAT and directory writes follows the F3-44 rules (allocate before pointing, unpoint before freeing); the lab's tool writes the whole image at once and does not order anything, so it says nothing about crash behaviour. D1

How the hardware actually does it

SD cards and USB sticks contain a flash translation layer: the controller maps logical sectors to flash pages and erases blocks behind the scenes. Their performance depends on writing in large aligned units, which is one reason formatting tools align the FAT and the cluster heap to the card's erase-block size and choose large clusters. The SD Association's specifications tie exFAT to the SDXC capacity class. For the file system, the card is a block device that may also have a volatile cache and may lose the most recent writes on power loss, like any disk in F3-43. D2 C1

Safety

Test on a card or stick whose contents you may lose, in a reader connected to a test machine or passed through to a VM. Never test a writer on the camera's only copy of the club's photos: copy the card to an image first, and work on images until the acceptance test passes.

Where the analogy breaks


    

  • A card saying "all volumes stand side by side" can be checked by looking at the shelf. A reader of exFAT cannot check NoFatChain: the clusters it reads are just bytes, and the photograph's bytes look as valid as the movie's.
    • 

  • The check number on a catalogue card protects the card. exFAT's set checksum protects only the directory entries, not the file contents; a wrong cluster read produces no checksum error at all.
    • 

  • The library has one free-place chart. exFAT has two structures that could describe allocation (bitmap and FAT), and only the bitmap is authoritative for free space; a FAT entry of 0 does not mean "free" for a NoFatChain file's clusters.
    • 




Common mistakes and debugging


    

  • Following the FAT for a NoFatChain file. Its FAT entries are undefined (often 0); following them ends the file after one cluster or wanders into garbage.
    • 

  • Setting NoFatChain on a fragmented file. The forensic lab. Set it only when the allocator returned one run, and clear it (after writing the chain) when a file stops being contiguous.
    • 

  • Computing the checksum over the wrong bytes. The boot checksum skips three bytes; the set checksum skips its own field; both run over every byte of the region including unused ones.
    • 

  • Name hash on the wrong form of the name. The hash is over the up-cased name, as UTF-16 code units, low byte first. A name that hashes differently from the entry is skipped by readers that compare hashes first.
    • 

  • Forgetting the backup boot region. Change both copies, or a later checker may "repair" the main region from a stale backup.
    • 

  • Treating our checker as fsck.exfat. It checks the rules as we understood them; the milestone needs the reference checker and Windows.
    •

Summary


    

  • exFAT: boot region with checksum sector and backup, FAT, cluster heap; bitmap, up-case table and root directory in the heap.
    • 

  • A file is an entry set: File (checksum, attributes, times), Stream Extension (flags, hash, lengths, first cluster), File Name entries.
    • 

  • NoFatChain means "contiguous, ignore the FAT"; set it only for a single run, and readers will believe it.
    • 

  • Free space is the bitmap's business; a checker must compare the bitmap with every file's clusters and look for clusters claimed twice.
    • 

  • In this build only libblkid confirmed anything (boot checksum, label); everything else is our code agreeing with itself, and FS4's real test needs exfatprogs and Windows.
