Story hook

Analogy

Diego is a new cook. On his first day the head chef shows him the wall of the service corridor. It looks like more pantry shelves, each with a number. "Shelf 2000 is not a shelf," she says. "It is a hatch into the dish-washing room. Put a note there and the machine starts. Shelf 2004 is a little window: when a light is on behind it, a clean tray is waiting."

In the old part of the building there is something else: a panel of numbered intercom buttons, separate from the shelves. Only the head chef and the manager may press them.

By lunchtime Diego has learned two lessons. Some "shelves" change by themselves, so looking once is not enough: he must look again each time. And putting something on a hatch shelf is not storing it; it is pressing a button. This chapter is about those hatches (memory-mapped I/O) and that intercom panel (port I/O).

What you will be able to do

  • Explain memory-mapped I/O (MMIO) and port I/O, and read a real machine's two address maps.
  • Describe register semantics: read-only, write-only, read/write, write-1-to-clear, reserved bits, side effects of reads.
  • Write typed register accessors in C++ with volatile, and keep bits you do not own with read-modify-write.
  • Read disassembly to check that every register access the source asks for is really performed.
  • Diagnose a polling loop that the optimiser removed (the forensic lab).
Jargon box
Device register
Simple words: a small storage place inside a device that software reads or writes to control it or to ask its state. Analogy: a hatch or a little window in the corridor wall. Precise: a location in a device, with a fixed width and documented bit fields, accessed by the CPU through bus transactions; reads and writes may have side effects (F1-40 showed how the address reaches the device). D1
Memory-mapped I/O (MMIO)
Simple words: device registers placed in the same address space as memory, used with ordinary load and store instructions. Analogy: hatches that look like pantry shelves. Precise: an I/O method in which device registers occupy physical address ranges of the memory address space, so the CPU's normal load/store instructions access them; the address decoder routes those addresses to the device. D1 D2
Port I/O (x86)
Simple words: on x86 PCs, a second, separate set of addresses only for devices, used with special instructions. Analogy: the intercom panel with its own button numbers. Precise: an x86 I/O address space separate from memory, accessed only by the in and out instruction family; the CPU controls which privilege levels may use them. D4 R4
Side effect (of a register access)
Simple words: something that happens in the device because you read or wrote a register. Analogy: taking the tray from the window turns the light off. Precise: a state change caused by the access itself, for example reading a receive-data register removing the byte from the device's buffer, or writing 1 to a status bit clearing it. D1 D7
Write-1-to-clear (W1C)
Simple words: a status bit you clear by writing a 1 to it. Analogy: pressing the "seen it" button next to the light. Precise: a register-bit convention in which writing 1 clears the bit and writing 0 leaves it unchanged, so software can acknowledge one event without disturbing others. C1
Read-modify-write (RMW)
Simple words: read the register, change only your bits, write it back. Analogy: moving only your own jar on a shared shelf. Precise: an update sequence that preserves bits the software does not own (including reserved bits whose value must be preserved); it is not atomic unless the hardware or a lock makes it so. C1
volatile (C++)
Simple words: a C++ word that tells the compiler "this value can change behind your back; really read and write it every time". Analogy: the rule "look again each time" for the hatch windows. Precise: a type qualifier; accesses through a volatile glvalue are observable behaviour, so the compiler must perform each one, in program order relative to other volatile accesses; it does not make accesses atomic and is not a CPU memory barrier. D5 [intro.abstract] R2
Address space
Simple words: one complete numbering of places that addresses can name. Analogy: one set of shelf numbers; the intercom panel has its own set. Precise: a range of addresses with its own decoding; an x86 PC has (at least) a memory address space and a separate I/O port address space, which QEMU's info mtree prints separately. Q1 R5

Layer 1 — the kid explanation

A device is a machine in another room: a keyboard, a timer, a network card. The CPU controls it by leaving notes and reading little windows. Those notes and windows are the device's registers.

On most computers, the windows are mixed in with the pantry shelves. They have shelf numbers like everything else. That is memory-mapped I/O. The CPU uses the same "put" and "take" it uses for food. But a window is not a shelf. Its light can change by itself. Taking something from it can change what is behind it. So the cook must look again every time.

Older PCs also have a separate intercom panel with its own numbers. That is port I/O. Only special instructions press those buttons, and only trusted programs may use them. You will see in this chapter that a normal program that tries is stopped at once.

Layer 2 — the student explanation

Memory-mapped I/O

With memory-mapped I/O, the address decoder of F1-40 routes some physical addresses to device registers instead of memory, and the CPU uses ordinary load and store instructions on them D1 D2. QEMU's PC model shows this for real: the I/O APIC's registers at 0xfec00000–0xfec00fff and the HPET timer's at 0xfed00000–0xfed003ff sit in the same address space as RAM (run R5). All architectures this university uses rely on MMIO: QEMU's RISC-V and Arm boards put their UARTs and interrupt controllers in the memory address space too (runs in F1-43).

Port I/O on x86

x86 processors also have a separate I/O port address space, reached only by the in and out instructions D4. QEMU's PC places the classic devices there: the interrupt controllers (pic) at 0x20 and 0xa0, the timer (pit) at 0x40–0x43, the keyboard controller at 0x60 and 0x64, the real-time clock at 0x70, the serial port at 0x3f8–0x3ff, and the PCI configuration index and data ports at 0xcf8 and 0xcfc (run R5). Listing 3 compiles in and out from C++ with GCC's inline assembly; the disassembly shows the instructions in al,dx and out 0x80,al (run R4) D6 Extended Asm.

The CPU decides which programs may use port I/O D4. When Listing 3 runs as a normal Linux program, the very first in is refused and the program is killed with signal 11 (SIGSEGV); it never prints the value (run R4). An operating system kernel runs at a privilege level that is allowed to use the ports; that is why port I/O belongs to drivers, not applications.

Registers are not memory

Memory is boring in a useful way: you read what you wrote, and reading changes nothing. Device registers break both rules D1:

  • A status register changes by itself when the device's state changes (STATUS bit 0 in Listing 1 becomes 1 on ticks 3, 6 and 9, run R1).
  • A data register may return a different value on every read, and the read itself may remove the value from the device's buffer.
  • Some bits are write-1-to-clear: writing 1 acknowledges an event; writing 0 does nothing C1.
  • Some bits are reserved: the documentation says to preserve their value. Listing 1's CTRL bit 31 was set by "firmware"; the driver enables bit 0 with a read-modify-write and the run shows CTRL = 0x80000001, bit 31 kept (run R1) C1.
  • Width matters: a 32-bit register must be read with one 32-bit access; two 16-bit reads are two different bus transactions that the device may treat differently C1.

What the compiler is allowed to do

A C++ compiler optimises your program as if memory were boring. If a loop reads the same plain variable again and again and nothing in the loop can change it, the compiler may read it once, or remove the loop D5. Listing 2 shows it for real. At -O0, both versions of the waiting loop load the status word each time round (run R2). At -O2, wait_ready_plain became a single ret: the loop is gone. wait_ready_volatile still loads the status word (mov eax,DWORD PTR [rdi]) and tests bit 0 on every iteration (run R2). The C++ standard treats volatile accesses as observable behaviour that must be performed, and its forward-progress rules let a compiler assume that a loop with no observable behaviour ends D5 [intro.abstract]. That is why every register accessor uses a volatile pointer (Listing 1, lines 20 and 26).

Watch out

volatile makes the compiler perform each access. It does not make an access atomic, it does not stop the CPU or the bus from reordering accesses relative to normal memory, and it does not make memory shared between threads safe D5. Drivers combine typed volatile accessors with the memory-barrier and mapping rules of their platform (Layer 3).

Layer 3 — the engineer's depth

Analogy first: the hatches in the wall must not be treated like shelves by anyone: not by the cook (the compiler), not by the shelf assistant who keeps copies nearby (the cache), not by the porter who reorders deliveries (the CPU and the bus).

Caches and mapping types. If MMIO addresses were cached like memory, a read could return an old copy and a write could sit in the cache instead of reaching the device. Operating systems therefore map device registers with a memory type that is not cached; the curriculum's method says "map MMIO BARs uncached in your page tables" C1. On x86 this involves the page attribute and memory-type mechanisms of the Intel SDM; on Arm, the "Device" memory types of the architecture manual D4.

Not verified — check before relying on this

The names and exact rules of the memory types used for device registers (on x86: the PAT/MTRR memory types; on Arm: the Device-nGnRnE family and its ordering guarantees; on RISC-V: the physical memory attributes of I/O regions) were not checked in this build, and the verification pass could open only the Intel manual set's download page, not its chapters. Check the Intel SDM Volume 3A chapter on memory cache control, the Arm Architecture Reference Manual section on memory types, and the RISC-V privileged specification's physical memory attributes before writing page-table code for MMIO.

Ordering. A driver often writes a buffer address to one register and then writes "go" to another. The device must see them in that order. Volatile accesses keep their program order in the compiler, but the hardware may still reorder or post writes on some platforms; drivers use the barrier or ordered-accessor primitives of their kernel, which the curriculum's method calls "a small typed accessor with the right width and ordering" C1. F1-40 mentioned posted writes and reading back to flush them.

Port I/O and the UART. The serial port that QEMU places at port 0x3f8 is compatible with the classic 16550 UART D7. The Linux header serial_reg.h, opened in this build, numbers its registers as offsets from the base: UART_RX and UART_TX at 0, UART_IER at 1, UART_LSR (line status) at 5, with UART_LSR_DR = 0x01 meaning "receiver data ready" and UART_LSR_OE = 0x02 "overrun error" L1. So port 0x3f8 + 5 = 0x3fd, the port Listing 3 tried to read, is the line status register on that machine. Curriculum milestone C2 drives this UART with interrupts; F1-42 builds the model.

PCI configuration through ports. The two port windows pci-conf-idx (0xcf8) and pci-conf-data (0xcfc) in run R5 are the legacy way to reach PCI configuration space: write an address to the index port, then read or write the data port. The memory window pcie-mmcfg-mmio at 0xb0000000 is the newer memory-mapped way (ECAM). The curriculum's C1 milestone uses ECAM "with the legacy configuration I/O ports as a fallback" C1; F1-45 reads configuration space for real.

How the hardware actually does it

A store to an MMIO address leaves the core like any other store and travels the interconnect to the address decoder, which selects the device instead of a memory controller D2. Inside the device, the register is a group of flip-flops (F1-16) whose outputs drive the device's logic, or a status signal sampled at read time. A W1C bit is a flip-flop with a set input from the device's event and a clear input from "write strobe AND data bit = 1" D1. An in or out instruction on x86 produces a transaction marked as I/O space, so the decoders route it to the port space, which is why port 0x3f8 and memory address 0x3f8 are different places D4. QEMU models both: its info mtree lists an address-space: memory and an address-space: I/O (run R5).

Worked example

Enable a device without breaking its reserved bit

CTRL holds 0x80000000 (bit 31 set by firmware). You want to set bit 0.

  1. Wrong: reg_write(kCtrl, 0x1) writes 0x00000001 and clears bit 31.
  2. Right: read 0x80000000; OR with 0x00000001; write 0x80000001.
  3. Clearing bit 0 later: read, AND with ~0x1 = 0xFFFFFFFE, write: 0x80000001 AND 0xFFFFFFFE = 0x80000000.

Run R1 printed CTRL after enable = 0x80000001 R1.

Which port is the UART's line status register?

Base 0x3f8 (run R5) plus offset UART_LSR = 5 (L1): 0x3f8 + 0x5 = 0x3fd. To test "data ready", read port 0x3fd and AND with UART_LSR_DR = 0x01. That is the read Listing 3 attempts, which user mode is not allowed to perform (run R4) L1 R4.

Where the analogy breaks


    

  • A hatch looks different from a shelf if you look closely; an MMIO address does not. Nothing in the instruction or the pointer says "device". Only the memory map, the page-table memory type and your volatile make the difference C1.
    • 

  • The intercom panel is not a second building. Port I/O is an x86 feature; the RISC-V and Arm machines of this course have no port space at all, only MMIO (runs in F1-43) D4.
    • 

  • A cook who forgets to look again sees an old tray; a compiler may delete the looking entirely. Run R2 and the forensic lab show the loop vanishing, which no cook would do R2.
    • 




Common mistakes and debugging


    

  • Symptom: works at -O0, hangs or reads garbage at -O2. Cause: register accessed through a non-volatile pointer. Find it: disassemble the function and look for the load inside the loop (R2). Fix: all register access through typed volatile accessors.
    • 

  • Symptom: after enabling one feature, another stops working. Cause: a plain write that cleared other bits. Find it: read the register before and after; compare with the documented reset value. Fix: read-modify-write, or write the full documented value.
    • 

  • Symptom: an interrupt or event fires again and again. Cause: a W1C bit "cleared" by writing 0, or by writing back the value read (which writes 1 to every pending bit). Find it: compare your write with the register's documented semantics. Fix: write 1 only to the bit you handled.
    • 

  • Symptom: "Segmentation fault" at an in or out instruction in a user program (R4). Cause: user mode may not use the ports. Fix: do port I/O in kernel code (or, on Linux, through the operating system's interfaces for that device).
    • 

  • Symptom: a 32-bit register reads half right. Cause: two 16-bit (or four 8-bit) accesses, for example from memcpy or a byte-wise struct copy. Fix: one access of the documented width.
    •

Goal

No hardware. Linux with g++ and objdump, Python 3 and QEMU. The Lab Engineer used g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0, GNU objdump from the same system, and QEMU emulator version 8.2.2 (Debian 1:8.2.2+ds-0ubuntu1.18); the exact lines are in the .log files.

None beyond normal computer use. Do not run port-I/O code as root on your own machine to "see what happens": writes to real ports can reset or confuse real hardware. Use QEMU.

  • Devices are controlled through registers; MMIO puts them in the memory address space, port I/O (x86 only) in a separate one.

Forensic lab answer key


Observation: -O0: 0x41 after about 50 ms; -O2: 0x00 after about 0 ms (R3). Hypotheses: (1) the device is slower or broken in the release setup; (2) the compiler changed the wait loop. Deciding evidence: the device is identical in both runs (same harness, only the flag differs); Listing 2's -O2 disassembly shows a plain-pointer wait loop compiled to a bare ret (R2), which matches "instantly" and "reads the initial value 0x00". Root cause: read_byte reads STATUS and DATA through const std::uint32_t* (not volatile); at -O2 the compiler removed the loop. Fix: const volatile std::uint32_t* status, const volatile std::uint32_t* data (or the typed accessors of Listing 1); verify by rebuilding at -O2, checking the disassembly for a load inside the loop, and rerunning: 0x41 after about 50 ms. Prevention: a rule "all device registers through reg.h accessors" plus a CI step that builds and runs the hardware-in-the-loop test at the release optimisation level. How the evidence was made: the harness above, built twice, flags as in driver_bug_O0.log and driver_bug_O2.log. Wrong answers: "a race in the device thread" (the device thread writes long after the driver has already returned); "the -O2 build is too fast for the device" (a correct wait loop would still wait for the bit).
