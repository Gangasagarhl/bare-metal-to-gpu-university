Story hook

Analogy

The food hall has a front counter where customers' gadgets are checked in: a keyboard, a mouse, a drawing tablet, a foot pedal. There is one rule at this counter: the gadgets never speak first. A waiter, the host, walks past each one on a fixed round and asks "anything for me?". Only then may the gadget answer.

When a new gadget arrives, the waiter first asks it a set of standard questions: "what are you, who made you, how do you like to be asked?". The gadget answers from a little card of descriptors, and the waiter writes down how often to come back.

One gadget, a foot pedal for a music app, has a strange fault: quick taps sometimes do nothing, slow presses always work. The pedal is fine, the cable is fine, and the waiter is never late. This chapter explains why.

What you will be able to do

  • Describe USB's structure: host controller, root hub, hubs, devices, ports, and the rule that the host starts every transfer.
  • Name the four transfer types and choose the right one for a device.
  • Read a USB capture of enumeration and decode SETUP packets and descriptors byte by byte.
  • Explain how interrupt endpoints work by polling, and what that means for short events (the forensic lab).
  • Find USB devices and their speeds in QEMU's monitor.
Jargon box
USB host and host controller
Simple words: the computer side of USB, which runs the bus and asks every device in turn. Analogy: the waiter and the waiter's station. Precise: the host schedules all transfers on a USB bus; the host controller (for example xHCI, a PCI device, F1-45) carries out the schedule and contains the root hub with the first ports. D1 R1
Hub
Simple words: a box that turns one USB port into several. Analogy: a side table where several gadgets sit together. Precise: a USB device class that repeats traffic between an upstream port and several downstream ports and reports attach and detach events; devices behind it get port paths such as 2.1. D1 R1
Endpoint
Simple words: one numbered "mailbox" inside a device, for data in one direction. Analogy: the in-tray and out-tray on a gadget. Precise: an addressable source or sink of data in a device, identified by number and direction (IN = device to host, OUT = host to device); endpoint 0 is the bidirectional control endpoint every device has. D1 L1
Transfer types
Simple words: four ways to move data: control (setup questions), bulk (lots of data, whenever there is time), interrupt (small, regular checks), isochronous (steady streams like audio). Analogy: forms at check-in, parcels, a regular "anything for me?", a conveyor belt. Precise: control transfers carry a SETUP stage, optional data and a status stage; bulk transfers use spare bandwidth with error retry; interrupt transfers are polled at a bounded interval; isochronous transfers get reserved bandwidth without retry (USB_ENDPOINT_XFER_CONTROL 0, ISOC 1, BULK 2, INT 3 in ch9.h). L1 D1
Descriptor
Simple words: a small record a device sends to describe itself. Analogy: the gadget's ID card. Precise: a byte structure beginning with its length and type: the device descriptor (type 1), configuration (2), interface (4), endpoint (5), and class-specific descriptors; the host reads them with GET_DESCRIPTOR requests. L1 R3
Enumeration (USB)
Simple words: what happens when you plug a device in: the host gives it an address, reads its descriptors and switches it on. Analogy: the standard questions at check-in. Precise: the host detects attachment on a port, resets it, assigns a device address, reads the device and configuration descriptors, selects a configuration (SET_CONFIGURATION) and loads a class or vendor driver. D1 R2
Device class (USB)
Simple words: a standard type of device, so one driver can serve devices from many makers. Analogy: "all keyboards answer the same questions the same way". Precise: a class code in the device or interface descriptor (for example 3 = HID, human interface device, USB_CLASS_HID) with a class specification defining requests, descriptors and data formats. L1 D2
SETUP packet
Simple words: the 8-byte question that starts a control transfer. Analogy: the form the waiter hands over. Precise: eight bytes: bmRequestType (direction, type, recipient), bRequest, wValue, wIndex, wLength (the number of data bytes the host wants); the Linux header defines it as struct usb_ctrlrequest. L1 R3

Layer 1 — the kid explanation

USB is how most small gadgets connect to a computer. The computer is the boss of the cable: a device never speaks first, it only answers when the computer asks. When you plug something in, the computer asks it standard questions: "what are you?", "who made you?", "how should I talk to you?". The answers come as little cards called descriptors. Then the computer picks a driver and starts asking regularly, for example "any keys pressed?" many times a second.

Hubs let one port feed many devices, so USB makes a tree, like the PCI tree of F1-45.

Layer 2 — the student explanation

Host-driven, tiered, hot-pluggable

USB has one host per bus, and the host schedules every transaction D1. On a PC the host controller is a PCI device; QEMU's qemu-xhci appears in F1-45's listing as USB controller: PCI device 1b36:000d. Its root hub has ports; hubs add more, so devices are named by a port path. QEMU printed the lab machine's tree (run R1): the keyboard on port 1 at 480 Mb/s, a hub on port 2 at 12 Mb/s, and behind the hub a tablet on port 2.1 and a mouse on port 2.2, both at 12 Mb/s R1. Devices of different speeds share one tree.

Not verified — check before relying on this

The USB speed names and rates (low speed, full speed 12 Mb/s, high speed 480 Mb/s, SuperSpeed and later) and the frame and microframe periods were not checked in a specification in this build or in the verification pass (the USB 2.0 specification could not be opened: lookup budget); only the two rates QEMU printed (12 and 480 Mb/s) are evidence here. Use the USB 2.0 and USB 3.x specifications for rates, frame timing and cable limits.

Endpoints and the four transfer types

Inside a device, data goes to or from numbered endpoints. Endpoint 0 is the control endpoint every device has; others are declared in descriptors D1. Each endpoint has one transfer type L1:

Typech9.h valueUsed forGuarantee
Control0setup, configuration, class requestsdelivered, with a status stage
Isochronous1audio, video streamsbandwidth reserved; no retry
Bulk2storage, printersdelivered; uses leftover bandwidth
Interrupt3keyboards, mice, sensorspolled within a bounded interval; delivered

The guarantees column follows the USB specification as summarised in the textbooks (D1, D3), not checked against it in this build or in the verification pass, in which D1 could not be opened D1 D3. "Interrupt" transfers are not interrupts in F1-42's sense: the device cannot signal the host; the host polls the endpoint on a schedule, and the device answers with data or "nothing new" D1. The host controller then raises a real interrupt to the CPU when a transfer completes.

Enumeration in a real capture

QEMU can record a USB device's traffic to a capture file, which Wireshark's command-line tool tshark decodes. The lab recorded the keyboard while the firmware (SeaBIOS) enumerated it (run R2) R2. The sequence is: GET DESCRIPTOR (device); GET DESCRIPTOR (configuration) twice; SET CONFIGURATION; two HID class requests, SET_PROTOCOL and SET_IDLE; then repeated URB_INTERRUPT in polls on endpoint 1 (the address column changes from 0.1.0 to 0.1.1, device 1, endpoint 0 then 1).

Listing 1 decodes the actual bytes (run R3) R3. The first SETUP packet was 80 06 00 01 00 00 08 00: bmRequestType 0x80 (device-to-host, USB_DIR_IN), bRequest 6 (USB_REQ_GET_DESCRIPTOR), wValue 0x0100 (descriptor type 1, device, index 0), wIndex 0, wLength 8 L1. The firmware asked for only 8 bytes of the 18-byte device descriptor: enough to learn bMaxPacketSize0 = 64, the largest packet endpoint 0 accepts. It then asked for 9 bytes of the configuration descriptor (enough to read its total length, 34) and then all 34. The 34 bytes hold four descriptors in a row: configuration, interface (class 0x03 HID, subclass 0x01, protocol 0x01), a class-specific HID descriptor (type 0x21), and an endpoint (number 1, IN, interrupt, max packet 8, bInterval 7).

No SET_ADDRESS request appears in the capture, although classic enumeration assigns the device address with that request (USB_REQ_SET_ADDRESS = 0x05 in ch9.h) L1. One explanation: with xHCI the address is assigned by a command to the host controller, which sends the request itself, so software and QEMU's per-device capture never see it.

Not verified — check before relying on this

That xHCI performs SET_ADDRESS through its "Address Device" command, and that QEMU's per-device pcap therefore omits it, is an explanation from memory, not checked against the xHCI specification or QEMU's source in this build or in the verification pass (neither could be opened). Check the xHCI specification (device slot and Address Device command) and QEMU's hw/usb code.

Device classes

The interface descriptor's class 0x03 (USB_CLASS_HID = 3 in ch9.h) says "human interface device" L1. Any HID keyboard works with the operating system's one HID driver; subclass 1 and protocol 1 mark it as a "boot" keyboard, which simple firmware can use without parsing the full report descriptor D2 §4.2, §4.3. That is why the firmware sent SET_PROTOCOL (request 0x0B, value 0 = boot protocol): to select the simple boot protocol; SET_IDLE (0x0A) limits how often the keyboard repeats an unchanged report D2 §7.2.4, §7.2.6. Other classes include mass storage, audio, communications (serial adapters) and hubs; a device with no fitting class uses a vendor class and needs its own driver.

Layer 3 — the engineer's depth

Analogy first: the waiter's round is printed in advance: how often each gadget is visited, and how much each may say per visit.

Scheduling. The host divides time into frames (and, at high speed, microframes) and builds a schedule: isochronous and interrupt endpoints get reserved slots according to their intervals and packet sizes; control and bulk use what is left D1. An interrupt endpoint's bInterval sets its maximum polling period; how it is encoded depends on the speed.

Not verified — check before relying on this

The encoding of bInterval was not checked in this build or in the verification pass (the USB 2.0 specification could not be opened). The usual statement is that for full- and low-speed interrupt endpoints it is a period in 1 ms frames, and for high-speed endpoints the period is 2bInterval−1 microframes of 125 µs; for the keyboard's bInterval 7 at 480 Mb/s that would be 64 microframes = 8 ms. Confirm in the USB 2.0 specification (endpoint descriptor) before relying on it. The polls in run R2 are further apart than 8 ms; firmware may poll less often than the endpoint allows.

Host controller interfaces. xHCI, like the network card of F1-44, works with rings in memory: software places transfer descriptors on per-endpoint transfer rings and rings a doorbell register; the controller completes them by DMA and posts events on an event ring, then interrupts the CPU D4. The curriculum's device rows place xHCI next to NVMe and virtio as ring-based devices C1.

Device side. A microcontroller with a USB peripheral implements the other side: it answers SETUP packets from its descriptor tables and fills endpoint buffers; its USB peripheral raises interrupts to the firmware when the host has read or written a buffer D3. If the firmware has nothing new when the host polls, the device replies "nothing" (a NAK), and the host tries again at the next interval.

Power and electrical. The configuration descriptor in run R3 contains bmAttributes = 0xa0 and bMaxPower = 0x32. In ch9.h, bit 7 is USB_CONFIG_ATT_ONE ("must be set") and bit 5 is USB_CONFIG_ATT_WAKEUP ("can wakeup") L1, so the keyboard declares remote wake-up. The units of bMaxPower (current drawn from the bus) were not checked here or in the verification pass (D1 not opened).

How the hardware actually does it

At USB 2.0 speeds, data travels on one twisted pair as a differential signal, half-duplex: the host and the device take turns, which is one reason the host must run the schedule D1. Each transaction is a short exchange of packets: a token from the host (which device, which endpoint, which direction), a data packet, and a handshake (acknowledged, not ready, or stalled) D1. The host controller turns the software's transfer descriptors into these transactions, frame by frame, and writes completion events back to memory by DMA. A device's USB peripheral contains endpoint buffers and a small state machine that answers tokens addressed to it; the firmware sees only "buffer filled" and "buffer emptied" events.

Worked example

Decode the endpoint descriptor by hand

From run R3's bytes, the last descriptor is 07 05 81 03 08 00 07.

  1. 07: bLength, 7 bytes.
  2. 05: bDescriptorType 5, endpoint (USB_DT_ENDPOINT) L1.
  3. 81: bEndpointAddress: bit 7 = 1, IN (0x80 = USB_DIR_IN); low bits 1: endpoint 1.
  4. 03: bmAttributes: transfer type 3, interrupt.
  5. 08 00: wMaxPacketSize, little-endian: 0x0008 = 8 bytes per report.
  6. 07: bInterval 7 (meaning in the unverified box of Layer 3).

Listing 1 printed the same: ENDPOINT number 1 IN, type interrupt, max packet 8, bInterval 7 R3 W1.

Decode the second SETUP packet

80 06 00 02 00 00 22 00: device-to-host; GET_DESCRIPTOR; wValue 0x0200: descriptor type 2 (configuration), index 0; wIndex 0; wLength 0x0022 = 34. The firmware asks for the full configuration set, whose length it learned from the previous 9-byte read.

Where the analogy breaks


    

  • A gadget at a counter could wave; a USB device cannot. Even "interrupt" endpoints wait to be asked. That is the point of the forensic lab D1.
    • 

  • One waiter walks at one speed; USB mixes speeds in one tree. Hubs translate between them (R1 shows 480 and 12 Mb/s devices together) R1.
    • 

  • Check-in questions are asked once; USB enumeration repeats on every reset, plug and resume. A device must answer its descriptors correctly every time.
    • 




Common mistakes and debugging


    

  • Symptom: a home-made device is not recognised. Cause: wrong descriptor lengths or total length, or wrong bMaxPacketSize0. Find it: capture enumeration (usbmon on Linux, or QEMU's pcap) and check every length byte. Fix: make wTotalLength equal the sum of the descriptors.
    • 

  • Symptom: short events lost (forensic lab). Cause: device reports only the current state, and polls are further apart than the event. Fix: latch events in the device until reported; shorten bInterval.
    • 

  • Symptom: a device works on one port and not behind a hub. Cause: power budget or speed translation. Find it: the kernel log and the hub's port status. Fix: powered hub; check bMaxPower.
    • 

  • Symptom: treating "interrupt endpoint" as "the device can interrupt". Cause: the name. Fix: remember that the host polls.
    • 




Transition box

Where you came from: F1-45 enumerated PCI devices from configuration space. What carries over: enumeration from self-describing records, IDs and class codes, a tree of hubs like PCI bridges, and a host controller that works with rings and DMA (F1-44) D1. What changes: most dangerous first: the device cannot interrupt; anything it does not hold until it is polled can be lost; descriptors arrive in pieces over control transfers, not as registers you read at will; one host schedules a shared, half-duplex cable D1. What comes next: F1-47 goes down to the simple serial buses inside boards: I2C, SPI, UART and CAN, where you can watch every bit with a logic analyser.

Summary


    

  • USB is host-driven: one host schedules every transfer; devices only answer.
    • 

  • Host controller (xHCI on PCs) with a root hub; hubs build a tree; devices of different speeds share it.
    • 

  • Endpoints carry one of four transfer types: control, bulk, interrupt (polled), isochronous.
    • 

  • Enumeration reads descriptors with GET_DESCRIPTOR over control transfers, then SET_CONFIGURATION.
    • 

  • Descriptors: device, configuration, interface (class), endpoint, class-specific; all little-endian and self-sized.
    • 

  • Interrupt endpoints are polled: a device must hold short events until the host reads them.

Forensic lab answer key


Observation: every missed tap ended before the next poll: 401 + 5 = 406 < 416; 498 + 3 = 501 < 512; 692 + 7 = 699 < 704; 789 + 4 = 793 < 800; 886 + 10 = 896, ended exactly when the poll came, so the poll saw "released" (R4). Reported taps were still held at a poll. Hypotheses: (1) electrical or cable fault: it would not depend on the tap's timing relative to polls, and would not change with the polling interval; (2) the device reports only the current state and the host polls every 16 ms: fits exactly. Proof: the replay with other intervals: 1, 2 and 4 ms report 10 of 10; 8 ms 8; 16 ms 5; 32 ms 1. Why long presses work: any press longer than the interval always contains a poll. Fixes: (a) shorter bInterval: reduces but never removes the problem (8 ms still misses the 5 ms tap at 401 ms and the 3 ms tap at 498 ms, which fall between polls), and costs bus time; (b) robust: latch each tap in the firmware ("pressed since last report") and clear it only after the report has been read by the host, or send press and release events in a queue. Prevention: rule for polled devices: never report only a state if the user cares about events shorter than the poll interval. How the evidence was made: usb_poll.cpp, a model with exercise taps. Wrong answers: "the host is late" (polls are on time in the log); "the switch bounces" (bounce adds events, it does not remove long ones only when short).
