Story hook

Analogy

Amara runs the evening shift in a busy restaurant building. The head chef works on the ground floor; the pantry, the cold room, the dish-washing room and the till are spread around the building. Everything moves through one service corridor with a lift at the end.

Every trolley that enters the corridor carries a label with a room number: "pantry, shelf 16" or "till, drawer 2". The doorkeeper at each door reads the label and opens only if the number belongs to their room. If two trolleys try to enter the corridor at the same time, Amara lets one in and makes the other wait.

One evening a new cold-room door is fitted, and its sign says it owns rooms 3000 to 30FF. The till's door, further along, still says 3080 to 3087. That night, some deliveries to the till arrive half-frozen. Nobody broke anything on purpose. Two doors answered the same label. This chapter is about corridors like that one, the labels, the doorkeepers, and what goes wrong when two of them disagree.

What you will be able to do

  • Explain what an address bus, a data bus and control signals carry, and why one shared bus allows only one transfer at a time.
  • Read a memory map and decode, by hand and in code, which device answers a given address.
  • Compute the peak transfer rate of a bus from its width and its transfer rate, and say why the real rate is lower.
  • Explain bus masters, arbitration and why a second master (a DMA engine) makes the CPU wait.
  • Diagnose an address-decoding overlap from a decoder table and a read log (the forensic lab).
Jargon box
Bus
Simple words: the paths that carry information between the parts of a computer (defined first in F0-05; this chapter adds detail). Analogy: the service corridor and its lift. Precise: a set of connections that carries addresses, data and control signals between the processor, memory and devices; on a shared bus only one sender may drive the data lines at a time. D1 D2
Address bus
Simple words: the wires that say where a value should go or come from. Analogy: the room-and-shelf label on a trolley. Precise: the group of signals that carries the address of a transfer; with n address lines, 2n distinct addresses can be named. D1 W1
Data bus
Simple words: the wires that carry the value itself. Analogy: the trolley's load. Precise: the group of signals that carries the data of a transfer; its width (for example 8, 32 or 64 bits) is how many bits move in one transfer. D1
Control signals
Simple words: the extra wires that say what kind of transfer this is and when it is valid. Analogy: the "deliver" or "collect" stamp on the trolley, and the bell that says "now". Precise: signals such as read/write, a clock or strobe that marks valid data, and handshake or error signals; the exact set belongs to each bus's specification. D2
Address decoder
Simple words: the circuit that checks an address and wakes up the one device it belongs to. Analogy: the doorkeeper who reads the label. Precise: combinational logic that compares (part of) the address with each device's window and asserts that device's select (chip-select) signal. D1
Memory map
Simple words: the table that says which address range belongs to which device. Analogy: the building's floor plan with room numbers. Precise: the assignment of address ranges (windows) to memories and device registers in an address space; addresses outside every window are holes. D1
Bus master and arbitration
Simple words: a master is a part that may start transfers; arbitration decides which master goes next. Analogy: Amara deciding which trolley enters the corridor first. Precise: a bus master (in newer documents: an initiator or requester) drives addresses and starts transactions; an arbiter grants the bus to one requesting master at a time by a policy such as fixed priority or round-robin. D2
Bus contention
Simple words: two senders talking on the same wires at once. Analogy: two doors answering the same label. Precise: two drivers enabled on the same line at the same time; with push-pull outputs it can damage parts, with open-drain lines the result is the AND of the senders; either way the value is wrong. D1
Bandwidth (of a bus)
Simple words: how many bytes the bus can move each second at most. Analogy: how many trolleys per minute the corridor can take, times their load. Precise: peak bandwidth = width in bytes × transfers per second; the sustained rate is lower because of arbitration, address phases, wait states and protocol overhead. D2 W1

Layer 1 — the kid explanation

A computer is a building full of rooms. The CPU is the head chef. Memory is the pantry. The screen, the keyboard and the timer are other rooms. They all need to pass things to each other, and they do it through the same corridor: the bus.

Every delivery has two parts. The label says where it goes: that is the address. The trolley's load is the value: that is the data. A third stamp says "deliver" (write) or "collect" (read). At each door a doorkeeper, the address decoder, reads the label and opens only for its own rooms.

The corridor is narrow. Only one trolley fits at a time. If two cooks want to send something at the same moment, someone has to decide who goes first. That someone is the arbiter. Later in this course you will meet faster buildings with many private corridors, one per room. The labels and the doorkeepers stay the same.

Layer 2 — the student explanation

Three groups of signals

A classic parallel bus has three groups of signals D1 D2. The address bus carries the address of the transfer. The data bus carries the value. The control signals say whether this is a read or a write and mark the moment when address and data are valid (a clock edge, or a strobe on asynchronous buses). With n address lines, 2n addresses can be named: 16 lines give 216 = 65,536 addresses, 32 lines give 232 = 4,294,967,296 W1.

A transaction is one complete transfer. For a write, the master puts the address, the data and "write" on the bus, and the selected device stores the data. For a read, the master puts the address and "read" on the bus, and the selected device puts its data on the data lines for the master to latch D1. The bus itself does not know whether the address belongs to memory or to a device. That is the job of the decoder.

Address decoding and the memory map

The address decoder compares the address with each device's window and asserts that device's select line D1. The list of windows is the memory map. In Listing 1 the map is RAM at 0x0000–0x0FFF, an LED register at 0x2000–0x2003 and a timer at 0x3000–0x300F. A write to 0x0010 lands in RAM. A write to 0x2000, issued by exactly the same kind of instruction, lands in the LED register. A read of 0x1800 finds no window and ends as a bus error (run R1, cycle 6). This is the root of memory-mapped I/O, the subject of F1-41: to the CPU, a device register is "only an address".

Real decoders rarely compare every bit. A window whose size is a power of two and whose base is a multiple of that size can be decoded from the high address bits alone: the window 0x3000–0x300F is "the top twelve bits of a 16-bit address equal 0x300" W1. Cheap decoders that ignore some bits make the same device appear at several addresses (aliases). That is legal, but a driver writer must know it D1.

One sender at a time

Many devices are connected to the same data lines, so they must not all drive them. Devices that are not selected leave the lines alone: their outputs are tri-state (disconnected) or open-drain (only able to pull low) D1. If two devices drive the lines at once, that is bus contention. With push-pull outputs, one pulls up while the other pulls down, which is an electrical fault; with open-drain lines the result is the AND of the two values. Either way the value read is wrong D1. The forensic lab shows the AND case.

Masters and arbitration

A bus master may start transactions. The CPU is one. A DMA engine (F1-44) is another: it moves data between a device and memory without the CPU D2. When two masters want the shared bus in the same cycle, an arbiter grants it to one, using a policy such as fixed priority or round-robin D2. Listing 2 models round-robin: with the CPU wanting 6 transfers and the DMA engine 4, the bus is busy for 10 cycles, and each master waits 4 cycles (run R2). Nothing is lost, but the two masters' work is serialised.

How fast is a bus?

The peak bandwidth of a bus is its width in bytes times the number of transfers per second D2. An exercise bus that is 32 bits (4 bytes) wide and makes one transfer per clock at 100 MHz peaks at 4 × 100,000,000 = 400,000,000 bytes per second W1. The sustained rate is lower: an address phase may cost a cycle, a slow device may add wait states, and arbitration costs time D2. These are exercise numbers, not the specification of any real bus.

Layer 3 — the engineer's depth

Analogy first: the single corridor became a road network with junctions, toll gates and private lanes. The labels on the trolleys did not change.

Hierarchies of buses. Real systems do not hang every device on one bus. A fast connection joins the CPU cores, their caches and the memory controllers; bridges connect slower I/O buses below it D2. A bridge forwards a transaction from one side to the other when the address belongs to a window behind it, so the decoder of Figure 1 becomes a tree of decoders. You will see one such tree in QEMU's PCI listing in F1-45, where a PCI bridge owns a "memory range" and forwards it to bus 1.

From shared parallel buses to point-to-point links. Many wide parallel wires switching together are hard to run fast: they must all arrive within the same time window (skew), and every extra device adds electrical load. Modern external connections such as PCI Express use point-to-point serial lanes with the clock embedded in the data stream, and send transactions as packets with headers instead of using separate address wires D3 D2. The ideas of this chapter survive the change: there is still an address, a decoder (routing), a read/write distinction, and the possibility of a transaction no one claims.

Split and posted transactions. A simple bus holds the bus for the whole read, from address to data. Faster buses split a read into a request and a later completion, so the bus can carry other traffic in between; writes may be posted, meaning the master does not wait for the target to finish D3. Posted writes are one reason why device drivers sometimes read a register back after writing it: the read cannot complete until earlier writes on the same path have arrived. The details belong to each bus's ordering rules, which F1-45 names.

Not verified — check before relying on this

The exact ordering rules for posted writes, reads and completions (which may pass which) are defined in the PCI Express Base Specification's chapter on transaction ordering, and differently for on-chip interconnects such as the Arm AMBA protocols. Neither document could be opened in this build or in the verification pass (PCI-SIG's site refuses automated access; the Arm documentation site returned no content). Check the ordering section of the specification for the bus you are using before relying on "a read flushes earlier writes" in a driver.

On-chip interconnects. Inside a system-on-chip, CPU cores, GPUs, DMA engines and peripherals meet on an on-chip interconnect, often with several independent channels for addresses, write data, read data and responses, so that reads and writes can be in flight at once. The memory map of such a chip lives in its technical reference manual (TRM), and a Linux or devicetree description repeats it. Chapter F1-41 prints the real memory maps of three QEMU machines.

How the hardware actually does it

At the electrical level a bus line is a wire with a voltage: high for 1, low for 0 (F1-08). A master changes its address and data outputs, and the control signals mark when receivers should sample them, often on a clock edge (F1-18) D1. The decoder is ordinary combinational logic built from the gates of HW102: comparators feeding AND gates, one output per device D1. Shared lines need outputs that can let go: a tri-state buffer has an extra enable input and, when disabled, neither pulls up nor down D1. An open-drain output can only pull down; a pull-up resistor makes the line high when nobody pulls, which is why two senders produce the AND of their bits. You will meet open-drain lines again in I2C (F1-47), where this "AND" is used on purpose.

Worked example

Decode four addresses with the toy map

Map: RAM 0x0000–0x0FFF (size 0x1000), LEDS 0x2000–0x2003 (size 4), TIMER 0x3000–0x300F (size 0x10).

  1. 0x0010: 0x0010 ≥ 0x0000 and 0x0010 − 0x0000 = 0x0010 < 0x1000, so RAM, offset 0x010.
  2. 0x2000: RAM fails (0x2000 − 0 is not < 0x1000). LEDS: 0x2000 − 0x2000 = 0 < 4, so LEDS, offset 0.
  3. 0x3004: TIMER: 0x3004 − 0x3000 = 4 < 0x10, so TIMER, offset 4.
  4. 0x1800: not in any window, so a bus error.

Run R1 printed exactly these four results (cycles 1, 3, 4 and 6) R1.

Bandwidth with overhead

Exercise bus: 4 bytes wide, 100 million cycles per second. If every transfer needs one address cycle and one data cycle, only half the cycles move data: 4 × 50,000,000 = 200,000,000 bytes per second, half the peak. If the CPU and a DMA engine share the bus and the DMA engine uses 4 of every 10 cycles (as in run R2), the CPU is left with 60 % of whatever the bus delivers W1.

Where the analogy breaks


    

  • A corridor can hold a queue; a simple shared bus holds one transfer. In the restaurant, trolleys can line up inside the corridor. On a simple shared bus, a waiting master holds its request outside; nothing is "in the corridor" except the current transfer. Split-transaction and packet-based links (Layer 3) do keep several transfers in flight D3.
    • 

  • Doorkeepers do not take time to think; decoders do. The analogy hides that decoding and driving long wires take time, which limits how fast a shared parallel bus can run. This is one reason modern links are point-to-point (Layer 3) D2.
    • 

  • Two trolleys collide; two bus drivers combine. When two doors answer at once, the restaurant gets two deliveries. On open-drain lines you get one value, the AND of both, and nothing tells you it happened unless the hardware detects it (run R3) R3.
    • 




Common mistakes and debugging


    

  • Symptom: a read returns a value that is the AND (or a mix) of two expected values. Cause: overlapping windows, so two devices answer. Find it: list every window with its last address (base + size − 1) and sort by base; any window that starts before the previous one ends is an overlap (forensic lab). Fix: correct the size or the base in the decoder table.
    • 

  • Symptom: a device appears at several addresses. Cause: partial decoding (some address bits ignored). Find it: write a value at one address and read it back at others. Fix: usually none needed, but never place another device in the alias range.
    • 

  • Symptom: off-by-one window: the last register of a device is unreachable, or one byte beyond it answers. Cause: confusing size with last address (0x10 bytes from 0x3000 end at 0x300F, not 0x3010). Find it: test the first and last address of every window and the first address after it. Fix: store base and size, compute last = base + size − 1 in one place.
    • 

  • Symptom: "bandwidth is lower than the bus width times the clock". Cause: that number is the peak; address phases, wait states and other masters take cycles. Find it: count cycles per useful transfer, as in the worked example. Fix: none; quote sustained rates from measurements, labelled as such.
    • 




Transition box

Where you came from: F1-24 and F1-30 showed the CPU's datapath and its cores, and F0-05 drew the computer as a kitchen map with "corridors" between the parts. What carries over: binary addresses, hexadecimal, combinational logic (a decoder is a comparator plus gates), and the clock that marks when signals are valid D1. What changes: the CPU is no longer alone: other masters share the bus and make it wait; addresses can belong to devices instead of memory; and a wrong address no longer means "a wrong value" but possibly "the wrong device" D2. What comes next: F1-41 uses the memory map to talk to devices: registers that look like memory but do not behave like it.

Summary


    

  • A bus carries addresses (where), data (what) and control signals (read or write, and when).
    • 

  • n address lines name 2n addresses; the memory map assigns windows of them to memories and devices.
    • 

  • The address decoder selects exactly one device per transfer; addresses in no window are holes and end as bus errors.
    • 

  • Only one sender may drive shared data lines; two at once is contention, and the value read is wrong.
    • 

  • Masters start transfers; an arbiter grants the shared bus to one master at a time, so masters wait for each other.
    • 

  • Peak bandwidth = width × transfers per second; sustained bandwidth is lower.
    • 

  • Modern links are point-to-point and packet-based, but addresses, routing and "nobody answered" remain.

Forensic lab answer key


Observation: reads of 0x3080 and 0x3081 select TIMER+UART and return 0x40; reads of 0x2000, 0x3004 and 0x30F0 are normal (R3). Bits: 0x64 = 0110 0100, 0x41 = 0100 0001; AND = 0100 0000 = 0x40, so the value is the open-drain AND of both devices. Hypotheses: (1) a faulty UART: ruled out, because reads that select only the UART would be needed to show that, and the only UART reads are the contended ones; the chip also works on another board. (2) A decoding overlap: confirmed, the TIMER window is 0x3000–0x30FF (size 0x100) and contains the UART window 0x3080–0x3087. Root cause: the TIMER line of the decoder table has size 0x0100; the board notes say 0x3000–0x300F, so the size must be 0x0010. Fix: set the size to 0x0010; rerun: 0x3080 then selects UART alone and returns 0x41, and 0x30F0 becomes a hole. Prevention: the overlap check from the lab, run on every decoder table at build time. Why it worked elsewhere: the other board's map had no device inside the oversized timer window. How the evidence was made: Listing 1's map with a UART added and the timer's size deliberately set to 0x100. Wrong answers: "the UART sends the wrong bit 0" (it is never read alone); "the timer is broken" (0x3004 reads correctly).
