Story hook

Analogy

The restaurant has become a food hall. Suppliers rent stalls on every floor, and they change every month. The building manager cannot print one fixed floor plan any more. Instead, every stall has a card holder at its door with a standard card: who the supplier is, what they sell, and how much storage space they need.

Each morning the manager walks every corridor, reads every card, and hands out storage space: "you get rooms 400 to 403". Corridors branch at junctions, and each junction has its own card saying which corridors lie behind it.

A new manager, on her first morning, gives a supplier three rooms when he asked for four. The supplier's stock spills into the stall next door. This chapter is about the cards, the morning walk, and that small mistake.

What you will be able to do

  • Describe PCI Express as a tree of point-to-point links: root complex, root ports, switches, bridges, endpoints.
  • Name PCI functions by bus, device and function number, and find them in QEMU's monitor and with lspci.
  • Read the standard configuration header: vendor and device ID, command, status, class code, header type, BARs, capability pointer.
  • Size a BAR with the write-all-ones method, including I/O, 64-bit and prefetchable BARs.
  • Walk a capability list and find MSI-X; explain enumeration and the ECAM configuration window.
  • Diagnose a wrong BAR size from an enumerator's log (the forensic lab).
Jargon box
PCI Express (PCIe)
Simple words: the main expansion bus of PCs and servers: fast serial links between the processor and cards such as GPUs, network cards and drives. Analogy: the food hall's corridors, one private corridor per stall. Precise: a point-to-point, packet-based serial interconnect that keeps the software model of PCI (configuration space, BARs, memory and I/O transactions) while carrying them as transaction-layer packets over one or more lanes per link. D3 C1
Bus, device, function (BDF)
Simple words: the three-part address of one PCI device or part of a device. Analogy: floor, stall, counter. Precise: a PCI function is addressed by its bus number, device number on that bus and function number within the device, written for example 00:1f.2; one physical device can have several functions. D3 R1
Configuration space
Simple words: a small block of registers every PCI function has, describing what it is and how to set it up. Analogy: the standard card at the stall door. Precise: a per-function register space, separate from memory and I/O space, with a standard 64-byte header (identification, command, status, class code, base address registers, capability pointer) followed by capability structures; 256 bytes in PCI and 4096 bytes in PCI Express. L1 D3
Base address register (BAR)
Simple words: a register in which software tells the device where in the address map its registers or memory should appear. Analogy: the space on the card where the manager writes "rooms 400 to 403". Precise: a configuration register that describes a memory or I/O window the function decodes: its low bits say the type (I/O or memory, 32- or 64-bit, prefetchable) and are read-only; software discovers the size by writing all ones and reading back, then programs the base address. L1 R4
Enumeration
Simple words: the start-up walk that finds every PCI device and gives each its addresses. Analogy: the manager's morning walk. Precise: the process (in firmware, the OS or both) of probing each bus, device and function for a valid vendor ID, numbering the buses behind bridges, sizing and assigning BARs, and enabling decoding and bus mastering in the command register. D3 C1
Capability list
Simple words: a chain of optional feature blocks in configuration space. Analogy: extra pages stapled to the card, each pointing to the next. Precise: a linked list starting at the offset in the capability pointer register (0x34), each entry beginning with an ID byte and a next-pointer byte; IDs include power management, MSI, MSI-X, PCI Express and vendor-specific. L1 R2
Root complex, root port, switch, endpoint
Simple words: the parts of the PCIe tree: the processor's side, its sockets, branching boxes, and the devices at the ends. Analogy: the building's core, its corridor exits, junctions, and the stalls. Precise: the root complex connects the CPU and memory to the PCIe hierarchy through root ports; a switch fans one upstream link out to several downstream ports (each appearing to software as a PCI-to-PCI bridge); endpoints are the devices that issue and receive transactions. D3 R1
Link, lane, TLP
Simple words: a link is a connection between two PCIe ports; it has 1 or more lanes (pairs of wires each way); data travels in packets. Analogy: a corridor, its number of walking lanes, and the parcels carried. Precise: a PCIe link aggregates lanes, each a differential pair in each direction; reads, writes, completions and messages travel as transaction-layer packets (TLPs), protected and retried by the data-link layer. D3 D5

Layer 1 — the kid explanation

A computer's maker does not know which cards you will plug in. So every PCI device carries a small set of standard registers, like an ID card: who made it, what kind of device it is, and how much address space it needs. When the computer starts, the firmware walks through every possible slot, reads every card, and gives each device its own addresses. After that, the device's registers appear in the memory map, and the driver can use them as in F1-41.

PCI Express is the fast modern form of PCI: instead of one shared set of wires, each device has its own private link, and data travels in small packets.

Layer 2 — the student explanation

A tree of links

Old PCI was a shared parallel bus like F1-40's. PCI Express replaced the wires with point-to-point serial links, but kept the software view D3. The topology is a tree (Figure 1): the root complex joins the CPUs and memory to the hierarchy; root ports and switches appear to software as PCI-to-PCI bridges, each opening a new bus number; endpoints are the devices D3. QEMU printed this structure for the lab machine (run R1) R1: the root port at bus 0, device 4 shows secondary bus 1. and subordinate bus 1., and the virtio RNG appears as Bus 1, device 0.

Each function is named by bus, device and function. In the lab machine, device 31 (0x1f) on bus 0 has three functions: the ISA bridge (31.0), the SATA controller (31.2) and the SMBus controller (31.3) (run R1). lspci writes the same addresses as 00:1f.2.

Configuration space

Every function has a configuration space. Figure 2 shows its standard header with the offsets defined in the Linux header pci_regs.h: vendor ID at 0x00, device ID at 0x02, command at 0x04, status at 0x06, class code at 0x09–0x0b, header type at 0x0e, BARs from 0x10, capability pointer at 0x34, interrupt line at 0x3c L1. The same header defines 256 bytes as the size of PCI configuration space and 4096 bytes for PCI Express (PCI_CFG_SPACE_SIZE, PCI_CFG_SPACE_EXP_SIZE) L1.

Listing 1 reads this header for every function of the build machine, through the files Linux provides under /sys/bus/pci/devices (run R2) R2. The build machine is itself a virtual machine. Its host bridge is 8086:0d57 and its other functions are virtio devices with vendor ID 1af4. lspci, using its ID database, names them, for example Red Hat, Inc. Virtio 1.0 network device with class 02/00 "Ethernet controller" (run R3) R3. The vendor ID is how a driver finds its device: the OS matches vendor, device and class against the drivers it has.

The command register

Listing 1 printed cmd 0x0406 for every virtio function. Using pci_regs.h: 0x0002 is PCI_COMMAND_MEMORY (respond to memory accesses), 0x0004 is PCI_COMMAND_MASTER (may start DMA, F1-44), 0x0400 is PCI_COMMAND_INTX_DISABLE (the legacy interrupt wire is off) L1. So these devices decode memory BARs, may do DMA, and use message-signalled interrupts. The host bridge shows cmd 0x0000. A device whose memory bit is 0 ignores accesses to its BARs; this is the first thing to check when a driver reads all ones.

BARs: asking how much space a device needs

A device does not choose its addresses. Each BAR has read-only low bits that give its type, and address bits of which only those above the window size are writable D3. Software writes all ones, reads back, clears the type bits (PCI_BASE_ADDRESS_MEM_MASK = ~0x0f for memory, PCI_BASE_ADDRESS_IO_MASK = ~0x03 for I/O), and computes size = ~value + 1 (Figure 2) L1. Bit 0 says I/O (1) or memory (0); for memory, bit 2 set (PCI_BASE_ADDRESS_MEM_TYPE_64) means the BAR is 64-bit and uses the next BAR slot for the high half; bit 3 (PCI_BASE_ADDRESS_MEM_PREFETCH) means prefetchable L1.

Listing 2 applies this rule to read-back values that correspond to the windows QEMU assigned (run R4). The e1000's BAR0 gives 0x20000 = 128 KiB, which matches QEMU's BAR0: 32 bit memory at 0xfea80000 [0xfea9ffff]; its I/O BAR1 gives 64 bytes, matching I/O at 0xc000 [0xc03f]; the xHCI's 64-bit BAR0 and the virtio RNG's 64-bit prefetchable BAR4 give 16 KiB each, matching their QEMU windows (runs R1 and R4) R1 R4. The read-back values themselves were derived from QEMU's windows by the rule, not read from a device; the lab's extension reads real ones.

Capabilities and MSI-X

If status bit 0x10 (PCI_STATUS_CAP_LIST) is set, the byte at 0x34 points to the first capability; each capability starts with an ID and a pointer to the next L1. Listing 1 walks the chain: every virtio function has five vendor-specific capabilities (ID 0x09) at 0x40, 0x50, 0x60, 0x70, 0x84, then MSI-X (ID 0x11) at 0x98 (run R2). lspci -v decodes the same chain, naming the virtio blocks CommonCfg, ISR, DeviceCfg, Notify, and printing MSI-X: Enable+ Count=3 (run R3) R3: the network device has three MSI-X vectors, and they are enabled (F1-43).

None of the build machine's functions has a PCI Express capability (ID 0x10): its virtual bus presents them as conventional PCI functions. On real PCIe hardware, that capability holds the link's capabilities and status (PCI_EXP_LNKCAP at offset 0x0c and PCI_EXP_LNKSTA at 0x12 within it, per pci_regs.h) L1; lspci -vv decodes them as link speed and width.

Layer 3 — the engineer's depth

Analogy first: the manager reads the cards through a special window at the back of the building: every stall's card has a fixed place in that window, worked out from its floor, stall and counter.

How software reaches configuration space. Old PCs used two I/O ports: write an address to 0xCF8, then read or write data at 0xCFC. QEMU's PC still has them, as pci-conf-idx and pci-conf-data (F1-41, run R5 there). PCI Express adds a memory-mapped window, the Enhanced Configuration Access Mechanism (ECAM): 4 KiB per function, placed by bus, device and function. In QEMU's PC that window is pcie-mmcfg-mmio at 0xb0000000–0xbfffffff (F1-41, run R5 there) C1. The size fits the layout: 256 buses × 32 devices × 8 functions × 4096 bytes = 268,435,456 bytes = 256 MiB = 0x10000000 W1. Firmware tells the OS where the window is (ACPI's MCFG table on PCs; a devicetree node elsewhere).

Not verified — check before relying on this

The ECAM address formula (function's offset = bus × 220 + device × 215 + function × 212 + register) and the 0xCF8 address format (enable bit 31, bus in bits 23–16, device in bits 15–11, function in bits 10–8, register in bits 7–2) are written from memory and only checked here for consistency with the 256 MiB window. Confirm them in the PCI Express Base Specification (configuration mechanisms) and the PCI Local Bus Specification before writing an enumerator.

Enumeration. Software probes each device number on bus 0; a vendor ID of 0xFFFF means "nothing here". For each function it reads the header type: type 0 is an endpoint (PCI_HEADER_TYPE_NORMAL), type 1 a bridge (PCI_HEADER_TYPE_BRIDGE) L1. For a bridge it assigns the primary, secondary and subordinate bus numbers (offsets 0x18, 0x19, 0x1a) and recurses. It then sizes all BARs, assigns non-overlapping, naturally aligned windows, programs each bridge's forwarding ranges to cover the windows behind it, and sets the command bits D3 L1. QEMU's listing shows the result for the root port: memory range [0xfe800000, 0xfe9fffff] holds the RNG's BAR1 at 0xfe800000, and prefetchable memory range [0xfe000000, 0xfe1fffff] holds its prefetchable BAR4 at 0xfe000000 (run R1). Its I/O range is printed as [0xc000, 0xbfff], base above limit: the firmware gave the bridge no I/O window because nothing behind it needs one.

Transactions. On the link, a CPU load from a BAR becomes a memory read request TLP routed down the tree by address; the device answers with a completion TLP carrying the data. A store becomes a posted write: no completion comes back D3 D5. Device DMA (F1-44) and MSIs (F1-43) travel upstream as memory write requests. This is why an MMIO read is slow (it waits for a round trip) and an MMIO write is fast but may arrive later.

Not verified — check before relying on this

Link speeds per generation (transfer rates per lane, encodings), the maximum link widths, payload sizes and the ordering rules between posted and non-posted requests were not checked in this build, and no number for them is given here. Use the PCI Express Base Specification, or lspci -vv on a real machine, which prints the link capability and the negotiated speed and width.

Errors and extended capabilities. PCI Express configuration space beyond 256 bytes holds extended capabilities, such as advanced error reporting, SR-IOV (one device appearing as many functions for virtual machines) and resizable BARs; pci_regs.h lists their IDs L1. Listing 1 reads only the first 256 bytes' chain.

How the hardware actually does it

A BAR is a register in which the low address bits are wired to zero (F1-17). Writing all ones sets only the bits that exist; the zero bits that read back are exactly the bits inside the window, which is why ~value + 1 gives the size and why windows are powers of two and naturally aligned D3. The device's address decoder compares the high bits of each incoming address with the BAR (F1-40's decoder). On the link side, each lane is a differential pair in each direction with an embedded clock; a physical layer serialises bytes onto the lanes, a data-link layer adds sequence numbers and checksums and retransmits on error, and a transaction layer builds the request and completion packets D5. Software sees none of this except through link status registers.

Decode one line of Listing 1

Run R2 printed: 0000:00:08.0 1af4:1041 class 02/00/00 header type 0x00 cmd 0x0406.

  1. 0000:00:08.0: PCI domain 0, bus 0, device 8, function 0.
  2. 1af4:1041: vendor 0x1af4, device 0x1041; lspci names it "Red Hat, Inc. Virtio 1.0 network device" (R3).
  3. Class 02/00/00: base class 0x02, subclass 0x00, programming interface 0x00; lspci calls it "Ethernet controller" (R3).
  4. Header type 0x00: an endpoint, not a bridge.
  5. Command 0x0406 = 0x0400 + 0x0004 + 0x0002: INTx disabled, bus master, memory decoding L1 W1.

Size a 64-bit BAR by hand

The xHCI's BAR0 reads back 0xFFFFC004 with high half 0xFFFFFFFF. Flags 0x4: memory, 64-bit, not prefetchable. Low half masked: 0xFFFFC000. Combined: 0xFFFFFFFF_FFFFC000. Invert: 0x00000000_00003FFF. Add one: 0x4000 = 16,384 bytes = 16 KiB, matching QEMU's 64 bit memory at 0xfeab0000 [0xfeab3fff] (R1, R4).

Where the analogy breaks


    

  • The card is not paper: reading or writing it can change the device. Writing a BAR moves the device in the address map; writing the command register turns decoding and DMA on or off L1.
    • 

  • Corridors carry people both ways at once; PCIe links carry packets with ordering rules. Posted writes, read requests and completions follow rules that no corridor has (Layer 3).
    • 

  • Room numbers are fixed; BAR windows are powers of two and aligned to their size. A device asking for 3 rooms gets 4 D3.
    • 




Common mistakes and debugging


    

  • Symptom: reads of a device's registers return all ones (0xFFFFFFFF). Cause: memory decoding off, wrong BAR address, device absent or powered down. Find it: lspci -vv: the command register and BAR addresses. Fix: enable the device (on Linux, the driver's enable call).
    • 

  • Symptom: BAR sizes slightly smaller than a power of two, overlapping windows (forensic lab). Cause: flag bits not masked before inverting. Fix: mask with the header's masks.
    • 

  • Symptom: a 64-bit device placed at a wrong address. Cause: high half not written, or the next BAR slot treated as a separate BAR. Fix: handle bit 2 of the BAR.
    • 

  • Symptom: devices behind a bridge are invisible. Cause: enumerator does not recurse into type 1 headers or does not set the bus numbers. Fix: assign secondary and subordinate bus numbers before probing behind the bridge.
    • 

  • Symptom: a driver works in QEMU but not on real hardware, with garbage reads. Cause: configuration space read with the wrong width or alignment. Fix: use aligned 8-, 16- or 32-bit accesses as defined for each field.
    • 




Transition box

Where you came from: F1-44 let devices master the bus for DMA; F1-41 placed device registers in the address map. What carries over: MMIO registers with side effects, address decoding, bus mastering, MSIs as memory writes L1. What changes: most dangerous first: addresses are no longer fixed by the board, so a driver must read them from configuration space and must never hard-code them; a wrong BAR size makes devices overlap silently; the bus is a tree of packet links, so reads are round trips and writes are posted D3. What comes next: F1-46 looks at USB, which also enumerates its devices from descriptors, but through one host controller and a polled protocol.

Hardware and software needed


No hardware. Linux with g++, the Linux UAPI headers (package linux-libc-dev on Debian and Ubuntu), lspci (pciutils) and qemu-system-x86_64. The Lab Engineer used g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0, lspci version 3.10.0 and QEMU emulator version 8.2.2 (Debian 1:8.2.2+ds-0ubuntu1.18).


Safety


Reading configuration space is safe. Do not write to configuration space of real devices (setpci, or writing the config files as root): a wrong write can hang the machine or disable a disk controller. All writes in this lab happen inside QEMU.

Summary


    

  • PCI Express is a tree of point-to-point links with the PCI software model: root complex, root ports and switches (bridges), endpoints.
    • 

  • Functions are addressed by bus, device, function; each has a configuration space (256 bytes PCI, 4096 PCIe).
    • 

  • The header holds IDs, class, command, status, header type, BARs and a capability pointer.
    • 

  • BAR size = ~(read-back with flag bits cleared) + 1; windows are powers of two; 64-bit BARs use two slots.
    • 

  • Enumeration probes, numbers buses, sizes and assigns BARs, sets bridge ranges and command bits.
    • 

  • Configuration space is reached through ports 0xCF8/0xCFC or the ECAM window (0xb0000000 in QEMU's q35).
    • 

  • Loads become read requests answered by completions; stores, DMA and MSIs are posted writes.

Observation: e1000 BAR0 0x20000 correct; e1000 BAR1 0x3F instead of 0x40; xHCI BAR0 0x3FFC instead of 0x4000; RNG BAR4 0x3FF4 instead of 0x4000 (R4, compared with R1's windows). Hypotheses: (1) the devices report odd sizes: impossible, a BAR size is a power of two; (2) the flag bits were not masked before inverting: the error equals exactly the flag bits (0x1, 0x4, 0xC), which fits. Proof: the code computes ~lo + 1 (line 16) without masking; for 0xFFFFFFC1 that gives 0x3F (the I/O flag bit 0x1 is missing from the size); for 0xFFFFC00C it gives 0x3FF4 (0xC missing). The e1000's BAR0 is right only because its flag bits are all zero (32-bit, non-prefetchable memory). Also, the 64-bit high half is read but ignored (line 13), which happens to be harmless here because the high half is all ones. Effect: windows assigned back to back with sizes like 0x3FFC are not aligned; the next window starts inside the address range the device really decodes (it decodes 0x4000 bytes), so two devices answer the same addresses, the contention of F1-40. Fix: mask with PCI_BASE_ADDRESS_MEM_MASK or PCI_BASE_ADDRESS_IO_MASK by type, combine 64-bit halves, then invert and add one; align each window to its size. Test: assert that every size is a power of two and every base is a multiple of its size; compare with QEMU's listing. How the evidence was made: bar_size_bug.cpp on the same input as Listing 2. Wrong answers: "QEMU is buggy" (QEMU's own listing shows power-of-two windows); "the network card is fine so the code is fine" (it is fine only by luck of its flag bits).
