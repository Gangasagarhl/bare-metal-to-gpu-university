Story hook

Analogy

The restaurant has grown. There are doorbells at the back door, the side door, the delivery lift, the cold room alarm and the oven timer. Wiring all of them into the kitchen would be chaos, so the owner hangs a panel by the pass. Each bell has its own light on the panel, a switch to silence it, and a number that says how urgent it is.

When a bell rings, its light comes on. The panel buzzes the head chef only for the most urgent unsilenced bell, and only if the chef is not already dealing with something at least as urgent. When the chef is done, she presses "done" on the panel, and the panel can buzz again.

One week a new assistant handles the side door and forgets to press "done". From then on the side door, the cold room and the lift are never answered again, while the oven timer still works perfectly. This chapter explains that strange pattern, and shows the real panels inside three emulated computers.

What you will be able to do

  • Explain what an interrupt controller does: collect, mask, prioritise, deliver a vector, track "in service", accept end-of-interrupt.
  • Read pending, mask and in-service registers and predict which interrupt is delivered next.
  • Explain edge- and level-triggered requests and message-signalled interrupts (MSI).
  • Name the controllers of x86 PCs (8259 PIC, I/O APIC, local APIC), Arm (GIC) and RISC-V (PLIC, ACLINT), and find them in QEMU's own output.
  • Diagnose a missing end-of-interrupt from per-line counters (the forensic lab).
Jargon box
Interrupt controller
Simple words: the part that collects the interrupt requests of many devices and passes them to the CPU one at a time, most urgent first. Analogy: the panel of bell lights by the pass. Precise: a hardware block between devices and processors that latches requests, applies per-source masks and priorities, selects the target CPU, delivers an interrupt with a vector or identifier, and tracks active interrupts until software signals completion. D2 C1
Pending, masked, in service
Simple words: three states of a request: waiting, silenced, being handled. Analogy: the bell's light is on; its switch is off; the chef is at that door now. Precise: a request is pending after the source asserts it and before the CPU accepts it (the classic PC controller calls this register IRR); masked when software disabled the source (IMR); in service after acceptance and before end-of-interrupt (ISR). D6 R3
End-of-interrupt (EOI)
Simple words: the handler's "I am done" message to the controller. Analogy: pressing "done" on the panel. Precise: a write by software to the controller (a command register, or the GIC's end-of-interrupt register, or the PLIC's claim/complete register) that ends the in-service state, so the controller may deliver that source and lower-priority ones again. D2 C1
Edge-triggered and level-triggered
Simple words: edge: "a ring happened"; level: "someone is still at the door". Analogy: a bell that rings once when pressed, versus a light that stays on while a visitor waits. Precise: an edge-triggered input records a transition of the request signal; a level-triggered input sees the request as long as the signal is asserted, so the source must be cleared before EOI or the interrupt is delivered again. D2
Message-signalled interrupt (MSI)
Simple words: instead of a wire, the device sends a small memory write that means "interrupt". Analogy: a note pushed through a slot in the panel instead of a bell wire. Precise: an interrupt delivered as a memory write of a programmed data value to a programmed address that the interrupt controller decodes; PCI devices announce MSI and MSI-X in their capability lists. D7 L1
APIC (local APIC, I/O APIC)
Simple words: the x86 interrupt controllers of today: one I/O APIC collects device lines; each CPU core has its own local APIC. Analogy: a panel per floor (I/O APIC) and a pager on each chef's belt (local APIC). Precise: the Advanced Programmable Interrupt Controller architecture: an I/O APIC with a redirection table entry per input pin (vector, destination, trigger mode, mask), and a local APIC per logical CPU that accepts interrupts, holds in-service state and receives EOI. D4 D5 R3
GIC
Simple words: the standard interrupt controller of Arm application processors. Analogy: the same panel, built by a different firm. Precise: the Arm Generic Interrupt Controller; in version 3 a distributor, one redistributor per CPU, CPU interfaces, and an optional ITS that turns device messages into interrupts. D8 R5
PLIC and ACLINT
Simple words: RISC-V's controller for device interrupts, and its block for timer and software interrupts. Analogy: the panel, and a separate kitchen timer and intercom per chef. Precise: the Platform-Level Interrupt Controller routes external interrupts with priorities and per-context claim/complete; the ACLINT provides machine-level timer (MTIMER) and software (MSWI/SSWI) interrupts per hart. D9 R4

Layer 1 — the kid explanation

A computer has many devices that can ring a doorbell, but a CPU core has room for very few bells. So the bells go to a panel first: the interrupt controller. The panel remembers which bells rang (pending), which bells are switched off (masked), and which bell the CPU is answering right now (in service).

The panel passes on the most urgent bell, with a number that tells the CPU which handler to run. When the handler is finished, it must tell the panel "done": the end-of-interrupt. If it forgets, the panel thinks the CPU is still busy with that bell. It then holds back that bell and every less urgent one, for ever.

Layer 2 — the student explanation

The five jobs of a controller

  1. Collect: latch each source's request in a pending register D2.
  2. Mask: ignore sources that software disabled, without losing their pending state D2.
  3. Prioritise: choose the most urgent pending, unmasked source; deliver it only if nothing of equal or higher priority is in service D6.
  4. Deliver: signal the CPU (or choose which CPU) and provide a vector or an interrupt identifier D2.
  5. Track: mark the delivered source in service until software writes end-of-interrupt D6.

Listing 1 runs these jobs on a scripted scenario (run R1). The UART (line 4) is taken at t = 0 with vector 36 (base 32 + line 4). At t = 2 the timer (line 0, more urgent) arrives and is taken at once: the timer handler nests inside the UART handler. At t = 3 the disk (line 6) and the masked audio (line 5) arrive; the disk waits because line 4 is still in service; audio waits because it is masked. After the UART's EOI at t = 5, the disk is taken at t = 6. Audio stays pending (IRR=00100000) until the driver unmasks it, and is then delivered at once. Note that masking did not lose the request.

Edge, level and why EOI order matters

An edge-triggered input records that the request signal changed; a level-triggered input sees the request for as long as the device holds it D2. With level triggering, a handler must clear the cause in the device (F1-41's W1C acknowledge) before it sends EOI, or the controller sees the still-asserted line and delivers the interrupt again. With edge triggering, a request that arrives while the line is already pending merges with it: the pending register has one bit per line, not a counter. The forensic run shows it: in build A every request was served, but in build B the UART raised its line 10 times and was served once (run R2), because later requests merged into one pending bit that was never delivered.

The x86 PC: two generations side by side

QEMU's PC still contains the classic pair of 8259 programmable interrupt controllers, at I/O ports 0x20 and 0xa0 (F1-41, run R5 there). Its monitor command info pic prints each one's request (irr), mask (imr) and in-service (isr) registers and its vector base: after the firmware ran, pic0 had irq_base=08 and pic1 had irq_base=70 (run R3) R3. The two are cascaded: the second controller's output enters an input of the first D6, and run R3's interrupt statistics show it, with the same count on 8259 line 2 and line 8 (the clock line of the second controller).

The same info pic prints the I/O APIC: 24 input pins in QEMU's model, each with a redirection entry showing destination, vector, polarity (active-hi), trigger mode (edge), mask state and delivery mode (run R3). With only firmware running, every pin is masked with vector 0: it is the operating system that programs these entries, which is curriculum milestone B7 ("route external interrupts through the IOAPIC to the local APIC"; "disable the 8259 PIC") C1. The build machine's Linux shows the result of that programming: its serial port ttyS0 is on IO-APIC 4-edge, and most of its devices use PCI-MSIX (run R6) R6.

Message-signalled interrupts

A PCI Express device has no interrupt wire to the CPU's controller. It signals an interrupt by writing a value to an address that the interrupt controller decodes D7. In QEMU's PC that address window is the region named apic-msi at 0xfee00000–0xfeefffff (F1-41, run R5 there). The Linux header pci_regs.h defines the capability IDs a device uses to announce this: PCI_CAP_ID_MSI = 0x05 and PCI_CAP_ID_MSIX = 0x11 L1; F1-45 finds MSI-X capabilities in real configuration space. MSI-X lets one device have many vectors, for example one per queue, which is why the build machine's network device appears on several lines (F1-42, run R3 there).

Arm and RISC-V

QEMU's Arm board with a version-3 GIC maps its parts at separate addresses: gicv3_dist (distributor) at 0x08000000, gicv3_its at 0x08080000, and gicv3_redist_region[0] at 0x080a0000 (run R5). QEMU's RISC-V board maps riscv.sifive.plic at 0x0c000000 and the ACLINT's software-interrupt (riscv.aclint.swi) and timer (riscv.aclint.mtimer) blocks at 0x02000000 and 0x02004000 (run R4). The names differ but the jobs are the five above: the GIC's distributor prioritises and routes, its CPU interface delivers and receives end-of-interrupt D8; the PLIC has a priority per source and a claim/complete register per target, where reading claims an interrupt and writing the same ID back completes it D9. Small Arm microcontrollers use the NVIC, built into the Cortex-M core (curriculum H2) D10.

Layer 3 — the engineer's depth

Analogy first: in a large restaurant, the panel also decides which chef gets the buzz, and some notes come through the mail slot rather than a bell wire.

Routing to CPUs. On multiprocessors the controller chooses a destination: the I/O APIC entry's destination field, the GIC's routing per interrupt, the PLIC's per-context enables D4 D8 D9. Operating systems spread device interrupts over CPUs (on Linux this is "IRQ affinity"); run R6's per-CPU columns show the build machine's interrupts landing on different CPUs. CPUs also interrupt each other (inter-processor interrupts, IPIs) through the same controllers; the "Rescheduling", "Function call" and "TLB shootdowns" rows of F1-42's run R3 are IPIs.

Spurious interrupts. A controller can signal the CPU and then find, when the CPU asks for the vector, that the request has gone (a glitch, or a level request withdrawn). It then delivers a special "spurious" vector, which must not be answered with a normal EOI on some controllers. The curriculum's catalog row warns: "Mask the 8259 PICs even if you never use them; spurious IRQ 7 and 15 are a classic surprise" C1; Linux keeps a counter (the SPU row of run R6).

Not verified — check before relying on this

The exact EOI procedures were not checked in this build: for the 8259A, the OCW2 non-specific and specific EOI commands (Intel 8259A datasheet); for the local APIC, the EOI register and the rules for x2APIC mode (Intel SDM Volume 3, APIC chapter); for GICv3, the split between priority drop and deactivation (Arm GIC Architecture Specification); for the PLIC, the claim/complete register layout per context (RISC-V PLIC Specification). Each also defines how a spurious interrupt is reported. Read the section for your controller before writing a handler epilogue.

Interrupt remapping and MSIs. Because an MSI is a memory write, a device could in principle write any vector to any CPU. IOMMUs add interrupt remapping, which checks and translates these writes; the curriculum notes that "Interrupt remapping (part of VT-d and AMD-Vi) is needed for more than 255 CPUs in x2APIC mode" C1. On Arm the ITS plays this role for MSIs D8. F1-44 introduces the IOMMU for DMA.

Where firmware tells the OS about controllers. On PCs, ACPI's MADT table lists the local APICs, I/O APICs and interrupt source overrides (curriculum B7); on Arm and RISC-V boards a devicetree describes the GIC or PLIC and each device's interrupt specifier C1. Driver code never hard-codes the addresses of Figure 2; it reads them from these tables.

How the hardware actually does it

A classic controller is a small sequential circuit (F1-17, F1-19): flip-flops for the pending, mask and in-service bits; a priority encoder that turns "the lowest-numbered set bit of (pending AND NOT mask)" into a line number; a comparator against the highest in-service bit; and a register that adds the vector base D1 D6. Listing 1's best() function is that priority encoder written as a loop. Modern controllers keep the same idea but add per-source priority registers, many CPUs, and a memory-mapped register interface instead of I/O ports (Figure 2). A GIC or PLIC has many sources, each with its own priority and enable bits in MMIO registers D8 D9; reading a "claim" or "acknowledge" register is a read with a side effect: it returns the winning interrupt and marks it active (F1-41).

Worked example

Which line is delivered next?

State: IRR = 0110 1000 (lines 3, 5, 6 pending), IMR = 0010 0000 (line 5 masked), ISR = 0001 0000 (line 4 in service). Line 0 is the highest priority.

  1. Pending and not masked: 0110 1000 AND 1101 1111 = 0100 1000: lines 3 and 6.
  2. The best of these is line 3.
  3. Is anything of equal or higher priority in service? The highest in-service line is 4, which is lower priority than 3. So line 3 is delivered, nested inside line 4's handler, with vector 32 + 3 = 35.
  4. Line 6 must wait for both EOIs; line 5 waits for its unmask.

Read QEMU's mask register

Run R3 printed pic0: … imr=b8. 0xb8 = 1011 1000: bits 3, 4, 5 and 7 are 1 (masked); bits 0, 1, 2 and 6 are 0 (unmasked). So the firmware left lines 0, 1, 2 and 6 of the first 8259 enabled; line 2 is the cascade input from the second controller R3 W1.

Where the analogy breaks


    

  • A panel light is on or off; a request can be an edge or a level. The analogy hides the difference between "rang once" and "still waiting", which decides whether a missing acknowledge causes silence or an endless storm D2.
    • 

  • Bells are wires; many modern "bells" are memory writes. MSIs travel the same path as data, so they are ordered with the device's data writes and can be remapped by an IOMMU; no panel light works that way D7.
    • 

  • A panel serves one chef; a controller routes to many CPUs and CPUs interrupt each other. Routing and IPIs have no counterpart in one kitchen pass (Layer 3).
    • 




Common mistakes and debugging


    

  • Symptom: one device and all lower-priority devices go silent after their first interrupt; higher-priority ones keep working (R2). Cause: missing EOI. Find it: per-line counters; the controller's in-service register stuck non-zero. Fix: EOI on every path out of the handler, including error paths.
    • 

  • Symptom: an interrupt storm: the handler runs again and again. Cause: level-triggered line, cause not cleared in the device before EOI. Fix: acknowledge the device first, then EOI.
    • 

  • Symptom: a device never interrupts. Cause: masked in the controller, wrong vector or destination, or the device's own interrupt-enable bit is off. Find it: check every gate on the path of F1-42 Figure 1: device enable, controller mask, CPU interrupt flag. Fix: enable at each level.
    • 

  • Symptom: an unexpected interrupt on a vector nobody registered. Cause: a spurious interrupt, or the legacy 8259s left unmasked and delivering on vectors that overlap CPU exceptions. Fix: mask the 8259s (curriculum catalog note) and install a spurious handler.
    • 




Transition box

Where you came from: F1-42 followed one interrupt from one device to one handler. What carries over: the flow device → controller → CPU → handler → acknowledge; short handlers; acknowledging the cause; registers with side effects from F1-41 D2. What changes: most dangerous first: a forgotten EOI now silences other devices, not only your own; priorities let one handler interrupt another, so handlers can nest; the controller differs by architecture (APIC, GIC, PLIC) and is found through firmware tables, not fixed addresses C1. What comes next: F1-44 lets devices move data into memory by themselves (DMA), and uses an interrupt only to say "done".

  • info pic prints nothing on RISC-V or Arm: that is what QEMU 8.2.2 did in this build for those boards; use info mtree and info qtree instead.

Method hints


Line 0 is the highest priority. A hypothesis that is local to the UART (a broken UART, a masked UART line) cannot explain why the disk stopped. Look for a single cause that blocks a line and everything below it.

Summary


    

  • An interrupt controller collects, masks, prioritises, delivers with a vector, and tracks in-service state until EOI.
    • 

  • Masked requests stay pending; repeated requests on one line merge into one pending bit.
    • 

  • A forgotten EOI blocks that line and every lower-priority line; higher-priority lines keep working.
    • 

  • Level-triggered lines need the device's cause cleared before EOI, or they storm.
    • 

  • x86 PCs: legacy 8259 pair (still present, masked by the OS), I/O APIC with redirection entries, local APIC per CPU, MSI window at 0xfee00000 in QEMU.
    • 

  • Arm: GIC (distributor, redistributors, ITS). RISC-V: PLIC for devices, ACLINT for timer and software interrupts.
    • 

  • Firmware tables (ACPI MADT, devicetree) tell the OS where the controllers are.

Forensic lab answer key


Observation: build A serves everything (TIMER 12/12, NET 9/9, UART 10/10, DISK 7/7). Build B: TIMER 12/12 and NET 9/9 (lines 0 and 3, higher priority) still served; UART 1/10 and DISK 0/7 (lines 4 and 6) silent (R2). Hypotheses: (1) the UART is broken or its line masked: explains the UART only, not the disk; (2) the UART handler leaves line 4 in service (missing EOI): blocks line 4 and every lower-priority line, explaining both. Proof: final ISR of build B = 0001 0000: line 4 in service forever although no UART handler runs; final IRR = 0101 0000: lines 4 and 6 pending and never delivered. Root cause: the UART handler returns without EOI (the model's forget_eoi_line = 4, standing for a driver path that skips the EOI). Fix: send EOI on every exit path of the UART handler; verify by rerunning the workload: counts equal build A's. Why 10 raised, 1 served: after the first delivery, every new UART request only set the already-set pending bit; pending is one bit per line. Prevention: a test that runs a mixed interrupt workload and checks per-line counters, and a code review rule "every handler ends through one epilogue that sends EOI". How the evidence was made: pic_noeoi.cpp, same model with and without the missing EOI. Wrong answers: "the disk is broken too" (two independent faults appearing together after one driver update is unlikely, and ISR proves the shared cause); "the timer is too frequent" (the timer is served normally in both builds).
