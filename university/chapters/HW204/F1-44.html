Story hook

Analogy

Every morning two hundred and fifty-six crates of vegetables arrive. For a while the head chef carried each crate from the back door to the pantry herself. Nothing got cooked until the last crate was in.

Then the restaurant hired a delivery truck with its own driver. The chef writes a delivery note ("from the farm, to pantry shelf 100, 256 crates"), hands it over, and goes back to cooking. When the truck is unloaded, the driver rings the doorbell once: done.

A week later the soup tastes of yesterday. The chef had kept a few vegetables on her own worktable, and she used those instead of the fresh ones the driver had put on the shelf. The truck was fast, the note was right, and still the food was old. This chapter is about the truck, the note, the gatekeeper at the loading bay, and that worktable.

What you will be able to do

  • Explain direct memory access (DMA) and compare its CPU cost with programmed I/O from a measured model.
  • Describe a DMA descriptor and a descriptor ring, and the role of the completion interrupt.
  • Explain why a driver on a non-coherent system must clean caches before a device reads and invalidate before the CPU reads what a device wrote, and show it in a cache model.
  • Explain what an IOMMU does and find the per-device DMA address spaces in QEMU's own memory tree.
  • Diagnose a stale-data DMA bug from packet logs (the forensic lab).
Jargon box
Direct memory access (DMA)
Simple words: a device copies data to or from memory by itself, while the CPU does other work. Analogy: the delivery truck that unloads straight into the pantry. Precise: a transfer in which a device (or a DMA engine) acts as bus master and issues memory reads or writes without the CPU executing a load or store per item; the CPU sets up the transfer and is told of completion, usually by an interrupt. D2 R1
Programmed I/O (PIO)
Simple words: the CPU moves every piece of data itself with its own loads and stores. Analogy: the chef carrying each crate. Precise: data transfer in which the processor executes an instruction for every unit moved between a device register and memory. D2
DMA descriptor
Simple words: a small record in memory that tells the device what to copy, from where, to where, how much. Analogy: the delivery note. Precise: a data structure in memory, in a format defined by the device, holding at least a buffer address and a length plus control and status bits; the device reads descriptors and writes back status. D7 R1
Descriptor ring
Simple words: a circular list of descriptors shared by the driver and the device. Analogy: a clipboard of delivery notes that goes round and round. Precise: a ring buffer of descriptors in memory with a producer index and a consumer index, one owned by the driver and one by the device; the driver tells the device about new entries by writing a "doorbell" register. D7
Scatter-gather
Simple words: one transfer made of several pieces of memory in different places. Analogy: one delivery note listing several shelves. Precise: DMA driven by a list of (address, length) pairs, so a buffer need not be contiguous in physical memory. D7
Cache coherence (for DMA)
Simple words: making sure the CPU's cached copy and memory agree when a device reads or writes memory. Analogy: the chef's worktable and the pantry shelf holding the same vegetables. Precise: a system is DMA-coherent if device accesses to memory see the latest CPU writes in caches and invalidate or update cached copies; on a non-coherent system software must clean (write back) and invalidate cache lines around each transfer. D2 R2
Clean and invalidate (cache maintenance)
Simple words: clean: copy changed cached data to memory; invalidate: throw the cached copy away so the next read goes to memory. Analogy: putting worktable vegetables back on the shelf; clearing the worktable. Precise: cache maintenance operations on a range of addresses: clean writes dirty lines back to memory; invalidate marks lines not valid. D2 R2
IOMMU
Simple words: a translator and guard between devices and memory: devices use their own addresses, and may only reach memory they were given. Analogy: the gatekeeper at the loading bay, with a list of shelves each truck may use. Precise: an input–output memory management unit that translates device-issued addresses (I/O virtual addresses) to physical addresses through per-device page tables and blocks accesses without a mapping; many also remap interrupts. D8 R4 C1
Bounce buffer
Simple words: a spare buffer the device can reach, used when it cannot reach the real one; data is copied between them. Analogy: a trolley at the gate when the truck may not enter the building. Precise: a buffer in device-addressable memory used for DMA when the real buffer is outside the device's address range or not suitable, at the cost of a CPU copy. D9

Layer 1 — the kid explanation

Moving a lot of data is boring work. If the CPU does it, it does nothing else. So many devices can copy data into memory, or out of memory, by themselves. That is DMA. The CPU writes a short note in memory saying where the data should go and how much there is, tells the device "go", and gets on with its work. When the copying is finished, the device rings the doorbell from F1-42.

There are two traps. The CPU keeps copies of memory in its cache, its worktable; if the device puts new data in memory, the CPU might still look at its old copy. And a device that can write anywhere in memory could break everything, so many computers have a gatekeeper, the IOMMU, that only lets each device write where it was allowed.

Layer 2 — the student explanation

Why DMA: the CPU's time

In programmed I/O the CPU executes a load from the device and a store to memory for every word D2. Listing 1 counts it: moving 256 words kept the CPU busy for 256 ticks. With DMA the CPU wrote a descriptor (5 ticks), the engine moved the 256 words, and the completion handler took 3 ticks: 8 busy ticks and 256 free ticks, with identical memory contents (run R1) R1. The tick costs are invented for the exercise; the shape of the result is the point: DMA's CPU cost is a fixed setup and completion, not a cost per word. For very small transfers that fixed cost can exceed the PIO cost, which is why drivers sometimes copy tiny messages by hand.

The device becomes a bus master

In F1-40 the bus had more than one master and an arbiter. A DMA-capable device is such a master: it puts addresses on the bus itself D2. Two forms exist. A DMA controller is a separate engine, shared by simple devices, that the CPU programs with source, destination and count; microcontrollers have them. A bus-mastering device (a network card, an NVMe drive, a GPU) has its own DMA engine and reads its instructions from memory D7. On PCI the command register has a "Bus Master" enable bit, PCI_COMMAND_MASTER = 0x4 in the Linux header; a device may not start DMA until software sets it L1 (F1-45).

Descriptors, rings and the doorbell

A device that does many transfers does not want a register write per transfer. The driver instead fills a descriptor ring in memory: each entry holds a buffer address, a length and status bits. The driver writes the index of the newest entry to a device register, the doorbell; the device reads the descriptors by DMA, moves the data, writes status back into the descriptors, and raises an interrupt D7 D9. It is the ring buffer of F1-42, now shared between the CPU and a device. The order matters: the descriptor must be complete in memory before the doorbell write reaches the device, and drivers use write barriers for that (Layer 3).

The worktable problem: caches and DMA

The CPU reads and writes through its caches (F1-33). A write-back cache holds new data that memory does not have yet (F1-35). F1-36 kept several CPUs' caches coherent; a device is one more party that touches memory. On a system where the device's memory accesses do not look into the CPU's caches, two things go wrong D2:

  • Transmit (CPU writes, device reads): the device reads memory, which still holds the old data. Listing 2 shows it: the CPU wrote A0..BF; without a cache clean, the device sent 32 zero bytes. After a clean, it sent A0..BF (run R2) R2.
  • Receive (device writes, CPU reads): the device writes memory, but the CPU still has the old lines cached. Without an invalidate, the CPU read 32 zeros; after an invalidate, it read 50..6F, the device's data (run R2) R2.

Systems whose interconnect makes device accesses snoop the caches are called coherent for DMA, and then these steps are not needed for correctness D2. Portable drivers do not decide this themselves: operating systems provide a DMA API that performs the right maintenance for the platform. In Linux, a driver "maps" a buffer for a direction before giving it to the device and "syncs" it before the CPU looks at it D9.

Not verified — check before relying on this

Which platforms are DMA-coherent was not checked in this build. The usual statements, that PCI Express devices on x86 PCs are cache-coherent by default, while many Arm and RISC-V systems on a chip have devices that are not, and that some interconnects offer both, depend on the platform and on device configuration (for example PCIe's "No Snoop" attribute). Check the platform's documentation and the Linux DMA API documentation (Documentation/core-api/dma-api.rst and dma-api-howto.rst in the kernel source) before writing a driver.

The gatekeeper: IOMMU

Without an IOMMU, the address in a descriptor is a physical address, and a buggy or malicious device can write anywhere in memory. An IOMMU sits between the devices and memory. Each device (on PCI, identified by its bus, device and function numbers) gets its own translation tables: the device uses an I/O virtual address, the IOMMU translates it to a physical address, and blocks any access without a mapping D8. This gives three things: protection (a device reaches only its buffers), contiguity (scattered physical pages can look contiguous to the device), and safe device assignment to virtual machines. The curriculum's catalog lists the IOMMU among the components of a platform, and notes that its interrupt remapping is needed for more than 255 CPUs in x2APIC mode (F1-43) C1.

QEMU's PC can include a model of Intel's IOMMU (VT-d). Its memory tree shows the idea directly (run R4) R4. The CPU's view is the address space "memory"; each PCI device has its own "vtd-root" address space, one per device (vtd-00.0, vtd-01.0, vtd-1f.2 and so on, named by device and function). The IOMMU's own registers appear at 0xfed90000 (intel_iommu). With only firmware running, nobody has turned translation on, so the devices' view is a pass-through region named vtd-nodmar ("no DMA remapping") that contains the same RAM as the CPU's view. One difference already shows: in the devices' view, the MSI window at 0xfee00000 is vtd-ir, the IOMMU's interrupt-remapping region, instead of the CPU-side apic-msi.

Layer 3 — the engineer's depth

Analogy first: the delivery note must be finished before the driver is called; the gatekeeper's list must be updated before a truck arrives and must be torn up after it leaves.

Ordering. A driver writes a descriptor (ordinary memory) and then the doorbell (an MMIO register, F1-41). If the CPU or the interconnect can reorder these writes, the device may read a half-written descriptor. Drivers put a write barrier between them, and read the descriptor's status bit before its other fields with a read barrier D9. Ownership is explicit: a descriptor belongs to the device from the doorbell until the device sets its "done" bit; the driver must not touch the buffer in between.

Not verified — check before relying on this

The barrier rules depend on the architecture's memory model and on the OS. In Linux, wmb(), dma_wmb() and the ordering guarantees of writel() differ in subtle ways; this build did not check them. Read Documentation/memory-barriers.txt in the kernel source and the device's datasheet. F1-37 covers the theory of memory ordering.

Cache-line granularity. Cache maintenance works on whole lines. If a receive buffer shares a cache line with unrelated data, invalidating the line throws away the CPU's recent writes to that data, and cleaning it can overwrite the device's data. DMA buffers are therefore aligned and sized to cache lines D9. The forensic lab shows the other half of the problem: invalidating too little.

Address limits and bounce buffers. Some devices can only generate addresses below a limit (old devices used 24- or 32-bit addresses). Without an IOMMU, a buffer above the limit must be copied through a bounce buffer below it, which costs a CPU copy and defeats part of the purpose of DMA; with an IOMMU, the buffer can be mapped to a low I/O virtual address instead D9.

Mapping cost. IOMMU maps and unmaps are not free: page-table updates and invalidations of the IOMMU's translation cache. High-speed drivers keep long-lived mappings for their rings and recycle buffers, trading some protection for speed D8. This trade-off returns with GPUs, which do large amounts of DMA (the GPU courses).

Peer-to-peer. In run R4 the devices' view also contains another device's registers (e1000e-mmio): in principle one device can DMA into another device's memory-mapped space. GPUs and NVMe drives use this for direct transfers; IOMMUs and PCIe switches can allow or block it D7 R4.

How the hardware actually does it

A DMA engine is a small state machine (F1-19) with address and count registers (F1-17): it requests the bus, puts its address on it, transfers a word or a burst, adds the transfer size to the address, decrements the count, and when the count reaches zero sets a status bit and raises its interrupt line D1 D2. Listing 1's loop on lines 42–49 is that state machine. A descriptor-based engine adds a second address register, the pointer to the next descriptor, and fetches descriptors with the same bus machinery. On PCI Express, the device's DMA becomes memory read and write requests on its link; the root complex forwards them into the memory system, passing through the IOMMU when one is enabled D7 D8. The IOMMU itself is a page-table walker with a translation cache, much like the CPU's MMU and TLB (F1-38), placed on the device side.

Worked example

When is DMA worth it?

Use Listing 1's exercise costs: PIO costs 1 CPU tick per word; DMA costs 5 + 3 = 8 CPU ticks per transfer. For a transfer of n words, DMA saves CPU time when 8 < n, so from 9 words up W1. For 256 words it saves 248 ticks, 97% of the PIO cost: (256 − 8) / 256 = 0.969. Real costs are different and include the interrupt's latency and cache maintenance, but the method (fixed cost versus cost per word) carries over.

Which cache lines does a buffer cover?

In the cache model lines are 16 bytes. A 32-byte buffer at address 0 covers lines 0 (bytes 0–15) and 1 (bytes 16–31). The maintenance range must cover both: invalidate(0, 32) computes the first line as 0 / 16 = 0 and the last as (0 + 32 − 1) / 16 = 1 (Listing 2's model, lines 43–46 of cache_model.h). A buffer at address 8 of length 32 would touch lines 0, 1 and 2: (8 + 31) / 16 = 2, and lines 0 and 2 would also hold other data, which is why DMA buffers are line-aligned.

Where the analogy breaks


    

  • A truck carries crates; DMA writes can tear. A device writes in bursts; if the CPU reads a buffer during the transfer it can see half old and half new data. Real deliveries do not leave half a crate on the shelf D9.
    • 

  • The chef's worktable is visible; the cache is not. In a kitchen anyone can see old vegetables on the table. Cache contents are invisible to the program, which is why stale-data bugs look like "the device sent the wrong data" (the forensic lab).
    • 

  • The gatekeeper checks shelves; the IOMMU checks pages. Protection has page granularity: a buffer that shares a page with secret data exposes that data to the device D8.
    • 




Common mistakes and debugging


    

  • Symptom: the device sends zeros or old data. Cause: no cache clean before the device reads (non-coherent system), or the DMA API's map step skipped. Find it: compare the buffer as the CPU sees it with a hardware trace or with the device's view. Fix: map for "to device" before starting the transfer.
    • 

  • Symptom: received data repeats or is partly stale (forensic lab). Cause: no invalidate, or an invalidate that does not cover the whole buffer, or the CPU read the buffer before the device finished. Fix: sync the whole buffer for the CPU after completion and before any read.
    • 

  • Symptom: random memory corruption far from the driver. Cause: a device DMAs to a buffer after the driver freed it (no IOMMU), or a wrong length. Find it: enable the IOMMU; its fault log names the device and the address. Fix: stop the device before freeing its buffers.
    • 

  • Symptom: the device works once, then reads garbage descriptors. Cause: doorbell written before the descriptor was complete (missing write barrier). Fix: barrier between descriptor and doorbell.
    • 

  • Symptom: no DMA at all on a PCI device. Cause: bus master enable not set in the command register. Fix: set it (on Linux, the driver's enable call does) L1.
    • 




Transition box

What carries over: the completion interrupt and its acknowledge; arbitration between masters; ring buffers from F1-42; MMIO doorbells from F1-41 D2. Summary


    

  • DMA lets a device move data to or from memory as a bus master; the CPU pays a fixed setup and completion cost instead of a cost per word.
    • 

  • Descriptors in memory tell a device what to move; rings and doorbells let it work through many.
    • 

  • On non-coherent systems: clean before the device reads, invalidate before the CPU reads what the device wrote, on whole cache lines.
    • 

  • Use the OS's DMA API; it performs the maintenance the platform needs.
    • 

  • An IOMMU gives each device its own address space: protection, contiguity, device assignment; QEMU shows one vtd-root space per PCI device.
    • 

  • Order the descriptor before the doorbell; free buffers only after the device has stopped.

Forensic lab answer key


Observation: in packets 2–4 the second half (bytes 16–31: 20.., 30.., 40..) is correct; the first half, including the header, is always packet 1's (01 01 12 13 …) (R3). Hypotheses: (1) the device writes only the second half of the buffer after the first packet: possible, but the device's design writes whole packets, and the header byte is read by the CPU, not shown by the device; (2) the CPU reads a stale cached copy of the first cache line: the first half is exactly one 16-byte line, which fits. Proof: the driver's peek (cpu_read(0), line 19 of dma_forensic.cpp) happens before the invalidate and caches line 0; the invalidate covers only bytes 16–31 (invalidate(16, 16), line 20), so line 0 is never refreshed. Why the header always says 1: line 0 was cached during packet 1's peek and every later peek hits that cached line. Fix: invalidate the whole buffer (0, 32) before any CPU read, including the peek; in Linux terms, sync the full buffer for the CPU first thing in the handler. Order matters because a read before the invalidate re-caches the old line. Verify: rerun; each packet's header must equal its number. Prevention: a test that sends packets with different contents through one buffer and checks every byte; never "optimise" cache maintenance to less than the buffer. How the evidence was made: dma_forensic.cpp on the cache model. Wrong answers: "the device is broken" (the second half proves the device writes new data every time); "add a delay" (time does not refresh a valid cache line).
