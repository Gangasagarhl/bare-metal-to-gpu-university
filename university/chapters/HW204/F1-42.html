Story hook

Analogy

Kofi is cooking alone tonight, and deliveries arrive at the back door. In the first hour he walks to the door every few minutes to check. Most trips are wasted: nobody is there. Worse, when the pans need him, he stays at the stove a little longer, and a courier who finds the door closed leaves the box on the step, where the next courier's box knocks it into the rain.

At eight o'clock the owner fits a doorbell and a small shelf beside the door. Now Kofi cooks without walking anywhere. When the bell rings he finishes the stir he is doing, puts the box on the shelf, says "got it" to the courier, and goes back to exactly the pan he left. He unpacks the shelf when the cooking allows.

That doorbell is an interrupt. The shelf is a ring buffer. This chapter shows, with a simulation you can run, why the boxes in the rain were not the courier's fault.

What you will be able to do

  • Explain polling and interrupts and when each one is the better choice.
  • Trace the interrupt path from device to handler and back: request, controller, CPU entry, handler, acknowledge, return.
  • State the rules for interrupt handlers: short, no blocking, acknowledge the device, share data safely.
  • Size a ring buffer from the arrival rate and the longest time the main program is busy.
  • Diagnose lost UART bytes from bench evidence, and fix them with an interrupt and a ring buffer (the course forensic lab, "The missing bytes").
Jargon box
Polling
Simple words: the program asks the device again and again "anything for me?". Analogy: walking to the back door every few minutes. Precise: software repeatedly reads a device status register and acts when a condition is true; simple and predictable, but it costs CPU time when nothing happens and reacts no faster than the polling period. D2
Interrupt
Simple words: a signal from a device that makes the CPU stop what it is doing for a moment, run a special function, and then continue. Analogy: the doorbell. Precise: an asynchronous event, raised by hardware outside the instruction stream, that causes the processor to finish or abandon the current instruction, save enough state to resume, and transfer control to a handler; after the handler, the interrupted code resumes. D3 D2
Interrupt request (IRQ)
Simple words: the device's "please ring" signal. Analogy: the courier pressing the bell button. Precise: the signal (a wire level or edge, or a message on newer buses) that a device uses to request an interrupt; "IRQ number" also names the input line or interrupt number in an operating system. D2 R3
Interrupt handler (ISR)
Simple words: the small function that runs when the doorbell rings. Analogy: taking the box, saying "got it", going back to the pan. Precise: an interrupt service routine: code entered through the CPU's vector mechanism for one interrupt; it services the device (reads data, acknowledges the cause) and returns with a special return sequence that restores the interrupted state. D3 D4
Interrupt vector
Simple words: the number that says which handler to run. Analogy: the bell's room number on the panel in the kitchen. Precise: an index into a table of handler addresses (on x86 the IDT, on Cortex-M the vector table); the CPU reads the entry for the vector and jumps to it. D4 D5
Acknowledge (an interrupt)
Simple words: telling the device (and the controller) "I have seen it". Analogy: saying "got it" so the courier stops ringing. Precise: the handler's actions that remove the cause in the device (for example reading the data register, or writing a W1C status bit, F1-41) and signal end-of-interrupt to the interrupt controller (F1-43). D2
Overrun
Simple words: a new byte arrived before software took the previous one, so a byte was lost. Analogy: the box knocked off the step into the rain. Precise: a receiver error: a received character could not be stored because the holding register or FIFO was full; UARTs report it in a status bit (the Linux header names the 16550's UART_LSR_OE). D6 L1
Ring buffer
Simple words: a fixed row of slots used in a circle: the writer adds at the head, the reader takes from the tail. Analogy: the shelf beside the door. Precise: a circular FIFO queue in an array with head and tail indices that wrap modulo its size; with one producer (the handler) and one consumer (the main program) it decouples arrival from processing. D8 R2
Interrupt latency
Simple words: how long it takes from the doorbell ringing to the handler starting. Analogy: finishing the stir before walking to the door. Precise: the time from the assertion of an interrupt request to the first instruction of its handler; it grows when interrupts are masked or a higher-priority handler is running. D2

Layer 1 — the kid explanation

A computer must notice when something happens outside: a key is pressed, a byte arrives on a cable, a timer runs out. It can notice in two ways.

The first way is polling. The program keeps asking the device "anything new?". It is easy to write. But most answers are "no", and while the program is busy with something else, it is not asking at all. If two bytes arrive while nobody asks, the device can keep only one. The other is lost.

The second way is an interrupt. The device rings a doorbell. The CPU finishes the instruction it is on, remembers exactly where it was, and runs a tiny function called the handler. The handler takes the byte, puts it on a shelf called a ring buffer, and says "got it". Then the CPU goes back to its work as if nothing happened. Later the program takes the bytes from the shelf when it has time.

Layer 2 — the student explanation

Polling and its two costs

A polling loop reads a status register and acts when a bit is set (Listing 1 of F1-41). Polling has two costs D2. First, wasted work: in Listing 1 of this chapter, with a main loop that polls every 4 ticks and a byte every 10 ticks, 98,303 polls found nothing (run R1). Second, a reaction time no better than the polling period: if the program is busy for longer than the device can buffer, data is lost. With a one-byte receiver and a byte every 10 ticks, polling every 4, 9 or 10 ticks passes the 64 KiB test; polling every 11 ticks loses 5,957 bytes and every 25 ticks loses 39,321 (run R1). The threshold is exactly the byte interval, because the receiver holds one byte.

What happens on an interrupt

An interrupt is an asynchronous event: it is not caused by the instruction being executed D3. Figure 1 shows the path. The device raises its interrupt request. The interrupt controller decides whether to forward it and with which vector (F1-43). The CPU, between instructions, saves the state needed to resume (at least the program counter and status flags), looks up the handler address for that vector and jumps there D3 D4 D5. The handler services the device and acknowledges it, then returns with the architecture's interrupt-return sequence, and the interrupted code continues as if nothing had happened D3. The CPU usually blocks further interrupts of the same or lower priority while a handler runs, which is one reason handlers must be short D2.

Rules for handlers

  • Short. Do the minimum: move the data, acknowledge, return. Long work goes to the main program D8.
  • Never block. No waiting for other devices, no locks the main program might hold, no memory allocation in time-critical code. A handler that waits can wait forever, because the code it waits for cannot run until the handler returns D8.
  • Acknowledge the cause. If the device's request is not cleared, a level-triggered line still asks, and the handler runs again at once, forever (F1-43 shows a missing EOI) D2.
  • Share data carefully. Data shared with the main program needs a design that tolerates the handler running between any two instructions of the main program: a single-producer single-consumer ring buffer with correctly ordered index updates, or short sections with interrupts disabled D8.

The ring buffer

Listing 2 lets the handler move each byte from the UART into a ring buffer of 64 slots, and the main loop drains the buffer between its other jobs. With the same "field" workload that loses 28,911 bytes when polling (run R4), the interrupt version receives all 65,536 bytes with the right checksum; the buffer never held more than 4 bytes (high water 4, run R2). The buffer must be big enough: with only 2 slots, the same workload drops 19,274 bytes (run R2). The sizing rule is arrival rate × longest busy time, plus a margin: one byte per 10 ticks × 40 ticks = 4 bytes, which is exactly the high-water mark the run measured W1 R2.

Layer 3 — the engineer's depth

Analogy first: a real kitchen has several doorbells with different tones, a rule about which one may interrupt which, and a "do not disturb" switch.

Masking and critical sections. Every CPU can globally disable interrupt delivery for a short time (x86 clears the interrupt flag; Cortex-M sets a priority mask), and controllers can mask individual lines D4 D5. Main-program code that must not be interrupted half-way (updating a shared index that is not a single atomic store, for example) runs with interrupts briefly disabled. Every such section adds to the worst-case interrupt latency, so they must be as short as the handlers.

Entry and exit differ by architecture. On x86 the vector indexes the interrupt descriptor table (IDT), and the handler ends with iretq in 64-bit mode; on Arm Cortex-M the hardware itself stacks a set of registers on entry, so a handler can be an ordinary C or C++ function listed in the vector table D4 D5. The curriculum's B3 and H1/H2 milestones build these paths.

Not verified — check before relying on this

The exact set of registers saved automatically on interrupt entry, the stack used, and the return instruction are architecture details that this build could not check: for x86-64, the Intel SDM Volume 3 chapter "Interrupt and Exception Handling"; for Cortex-M, the Armv7-M or Armv8-M Architecture Reference Manual sections on exception entry and return; for RISC-V, the privileged specification's trap handling (mepc, mcause, mret). Read the section for your target before writing an entry stub.

Top half and bottom half. Operating systems split interrupt work: a minimal handler that runs with the line blocked, and deferred work that runs later with interrupts enabled (Linux has several mechanisms for this) D9. The ring buffer of this chapter is the bare-metal form of the same idea: the handler only moves bytes; the main loop does the echo, the checksum and the log flush.

When polling wins. Polling is not wrong. When events arrive faster than the cost of an interrupt entry and exit, or when the CPU has nothing else to do, a tight polling loop has lower latency and overhead; high-rate network and storage drivers switch between interrupts and polling under load D2. The UART FIFO is a middle way: a 16550-compatible UART can collect several bytes and interrupt once per group D6; the Linux header defines UART_FCR_ENABLE_FIFO for that and UART_IER_RDI ("enable receiver data interrupt") for the receive interrupt L1.

How the hardware actually does it

The interrupt request is a wire from the device to the interrupt controller (or, for PCI Express devices, a memory write of a special value to a special address, F1-45) D2. Inside the CPU, the pipeline of F1-26 checks for pending, unmasked interrupts at instruction boundaries; when it takes one, it lets older instructions complete, discards younger ones, and redirects fetch to the handler D2. That is why an interrupt never splits one instruction in half from the program's point of view, and why the saved program counter points at the next instruction to execute. In the UART, a received byte sets "data ready"; if the receive interrupt is enabled, the same condition drives the interrupt request output, and reading the receive register clears it D6. Listing 2 models exactly that: deliver() sets data-ready and the handler empties the receiver.

Worked example

Will polling keep up?

Byte interval: 10 ticks. Receiver capacity: 1 byte. A byte is lost when two bytes arrive between two polls, which happens when the gap between polls is longer than 10 ticks.

  • Poll every 10 ticks: at most one byte between polls: no loss (R1: PASS).
  • Poll every 11 ticks: sometimes two bytes arrive between polls: loss (R1: 5,957 lost).
  • Field workload: passes of 4 ticks with a 40-tick pass every 8th time. In the 40-tick gap, 4 bytes arrive; the receiver keeps 1, so 3 are lost per long pass (Figure 2: 40, 50, 60) R4.

Size the ring buffer

Longest busy time of the main loop: 40 ticks. Bytes arriving meanwhile: 40 / 10 = 4. Plus one arriving at the boundary in the worst case: 5. A 64-slot buffer is far above this; a 2-slot buffer is below it, and run R2 confirms both: high water 4 with 64 slots, 19,274 drops with 2 W1.

Watch out
This model is single-threaded, so the handler can never interrupt pop() half-way. On real hardware it can. A real ring buffer shared between a handler and the main program must make the producer update only head and the consumer only tail (no shared count), with each index update a single, correctly ordered store, or protect the update by briefly disabling the interrupt D8. The mini-project asks you to rewrite Ring that way.

Where the analogy breaks


    

  • A doorbell can wait while you finish the sauce; an unmasked interrupt cannot. The CPU takes it at the next instruction boundary unless software masked it in advance D2.
    • 

  • Kofi remembers where he was; the CPU must save it. The "where I was" is a set of registers that hardware and the handler's entry code save and restore exactly; forgetting one corrupts the interrupted program in ways that look random D3.
    • 

  • A doorbell rings once; a level-triggered request keeps ringing. If the handler does not remove the cause, the CPU re-enters the handler immediately, and the main program never runs again (F1-43) D2.
    • 




Common mistakes and debugging


    

  • Symptom: bytes lost under load only (R4). Cause: polling period longer than the device can buffer. Find it: measure the main loop's longest pass and compare with byte interval × receiver depth; look for overrun flags. Fix: receive interrupt plus a ring buffer sized from the longest busy time.
    • 

  • Symptom: the system freezes as soon as the interrupt is enabled. Cause: the handler does not clear the device's request (or the controller's EOI), so it is re-entered forever. Find it: count handler entries; a counter that climbs while the main loop counter stands still. Fix: acknowledge in the device and the controller.
    • 

  • Symptom: rare corruption of data shared with a handler. Cause: a non-atomic update in the main program interrupted half-way. Find it: list every variable written by both sides. Fix: one writer per variable, or a short critical section with the interrupt masked.
    • 

  • Symptom: interrupts work, but other interrupts are now late. Cause: a long handler (printing, waiting) blocks lower-priority lines. Fix: move the work out of the handler.
    • 

  • Symptom: drops counted in the ring buffer (R2 with 2 slots). Cause: buffer smaller than arrival rate × longest busy time. Fix: size it from the measured worst case, and keep the drop counter visible.
    • 




Transition box

Where you came from: F1-41 controlled devices through registers and waited for them by polling; F1-25 and F1-26 showed how the CPU's control unit and pipeline fetch the next instruction. What carries over: status and data registers, W1C acknowledges, volatile accessors; the idea of the program counter D2. What changes: most dangerous first: your code can now be entered between any two instructions of the main program, so shared data needs a design; handlers must be short and must never block; control flow is no longer only what your source shows D3 D8. What comes next: F1-43 opens the interrupt controller: many devices, one CPU, priorities, masks and the end-of-interrupt that a handler must not forget.

Summary


    

  • Polling is simple but wastes CPU time and reacts no faster than its period; data is lost when the period exceeds what the device can buffer.
    • 

  • An interrupt makes the CPU save its state, run a handler through a vector, and return as if nothing happened.
    • 

  • The flow is device → controller → CPU → handler → acknowledge → return.
    • 

  • Handlers are short, never block, acknowledge the cause, and share data through a carefully designed structure.
    • 

  • A ring buffer sized from arrival rate × longest busy time decouples arrival from processing: 0 bytes lost in R2.
    • 

  • Real machines take hundreds of interrupts per second; Linux shows them in /proc/interrupts (R3).
