Story hook

A restaurant group is choosing a new kitchen hall. The builder sends a glossy brochure: photographs, a floor plan, and a page of large numbers. "Up to 400 covers an hour." "Peak capacity." "Industry-leading." Priya, who will run the hall, takes a pencil and goes through it line by line. For each number she writes one of three marks: this is a design fact I can check on the plan, this is a best case under conditions they do not state, or this is advertising. Then she visits a working hall of the same design and times a real service.

Her final page for the group has two columns: what the brochure says, with the page it says it on, and what she measured, with the date and the conditions. Nothing on her page comes from memory, from a forum, or from a colleague's guess.

The brochure is a GPU vendor's architecture whitepaper. Priya's page is the hardware passport, the project of this course. This chapter teaches the reading method, shows which facts this build could establish from toolchain evidence alone, and checks a passport automatically.

What you will be able to do

  • Classify each claim in a whitepaper as an architectural fact, a peak (theoretical) figure, or a marketing statement.
  • Locate every course concept (SM/CU, warp/wavefront, registers, shared memory/LDS, caches, memory, matrix units, links) in a whitepaper, and record the section.
  • Cross-check documented facts against toolchain evidence and measurements.
  • Build a hardware passport in which every number is tagged to a document section, a tool output or a measurement.
  • Map a kernel's threads onto a named GPU's hardware using only its documentation.
Jargon box
Architecture whitepaper
Simple words: the vendor's long document describing how a GPU generation is built. Analogy: the builder's brochure with the floor plan. Precise: a vendor publication describing a GPU architecture or product: block diagrams, unit counts, memory system, new features, and peak performance tables; a primary source for architecture, but written by the vendor, so peak numbers are stated under the vendor's own conditions. C1
Peak (theoretical) figure
Simple words: the biggest number the hardware could reach if everything went perfectly. Analogy: "up to 400 covers an hour". Precise: a figure computed from unit counts, clocks and widths (F1-59's formula is one), not measured; it is an upper bound. Guide rule AH-23 forbids presenting a measurement as a peak or a peak as a measurement. C1
Hardware passport
Simple words: a one-page card listing a GPU's important numbers, each with where it came from. Analogy: Priya's two-column page. Precise: this course's project: a table of fields (target, warp/wavefront size, units, storage, memory, matrix units, links), each value tagged DOC: (document and section), TOOL: (tool output and run record) or MEAS: (measurement run record), or left TBD. R1
Provenance tag
Simple words: a short note saying where a number came from. Analogy: the page number next to each copied figure. Precise: the tag in the passport's third column; Listing 1 checks that every filled-in value has one, that document tags name a section, and that peaks and measurements are not confused. R1
Toolchain evidence
Simple words: facts about a GPU that you can read from what the compiler produces, without the GPU. Analogy: learning the size of the hall's trays from the order form for trays. Precise: compiler outputs such as metadata (.wavefront_size: 64), constants substituted for built-ins (MOV R5, 0x20), accepted or rejected instructions (MFMA on gfx90a, not on gfx1030), and resource reports; they describe the target the compiler was built for, not a particular board. R2

The idea in pictures

Layer 1 — the kid explanation

When a company makes a new GPU, it writes a long description of it, full of pictures and big numbers. Some sentences explain how the GPU is built. Some numbers say how fast it could go if everything were perfect. Some sentences are only there to make it sound good.

A careful reader sorts them out. For every number, she writes down exactly where it came from. Then she checks what she can: she asks the compiler, she runs small programs, and she writes down what she saw and when. In the end she has one page where every number has a label: "the company says, on page so-and-so", or "I measured, on this day".

Layer 2 — the student explanation

What a whitepaper contains

Architecture whitepapers usually have the same parts: an overview with a full-chip block diagram (how many SMs or CUs, how they are grouped, F1-56); a diagram of one SM or CU (schedulers, arithmetic units, matrix units, register file, shared memory/LDS, L1, F1-57 to F1-61); the memory system (L2, memory type and interface, F1-58, F1-59); interconnects (F1-62); and tables of peak throughput per number format. W1 W2 Read in that order, every section maps onto a chapter of this course.

Three kinds of statement

Architectural facts ("each CU contains four SIMD units" — an illustrative wording, not a quotation) can be checked against other documents (ISA guides, programming guides) and partly against tools. Peak figures ("up to N TFLOPS in FP16") are products of unit counts, clocks and widths under the vendor's conditions (often a boost clock, sparsity or a particular format); they are upper bounds, never measurements. Marketing statements ("industry-leading", "up to N× faster than the previous generation") are comparisons whose conditions are rarely stated; they do not belong in a passport. C1 Guide rule AH-23 keeps peaks and measurements apart; Listing 1 enforces it mechanically. R1

What the toolchain proves without a GPU

Some passport fields can be established from compiler output alone, and this build did so. For gfx90a, the HIP compiler stored the constant 64 for warpSize (v_mov_b32_e32 v1, 64) and wrote .wavefront_size: 64 in the kernel metadata; for sm_80, the PTX keeps the symbol (mov.u32 %r1, WARP_SZ;) and the SASS stores 32 (MOV R5, 0x20). R2 F1-61 showed that MFMA instructions exist for gfx90a and gfx942 but are rejected for gfx1030 and gfx1100 (needs target feature mai-insts). R6 Such evidence describes the compiler target; whether a particular board is that target is a device-query fact (gcnArchName, "AMD GCN Arch Name", in HIP's header). H2

Layer 3 — the engineer's depth

The analogy in one line: the brochure, the plan, the order forms and the timed service are four witnesses; the passport records what each one says and never lets one speak for another.

Read the conditions of every peak

A peak figure is a formula. Reconstruct it: units × operations per unit per clock × clock, or width × data rate (F1-59). If the reconstruction does not match, find the condition you missed (a boost clock, a sparsity feature that counts skipped operations, a different number format, or a count per package instead of per die). C1 Record the formula in the passport next to the peak, so a reader can see what it assumes. A peak that cannot be reconstructed stays in the passport with its DOC tag and a note "formula unknown".

Cross-check across documents

A whitepaper is a summary; the ISA guide, the programming guide and the runtime headers are more precise. A wavefront size in the whitepaper should agree with the ISA guide, with the compiler metadata and with the device query; a shared-memory size should agree with the programming guide's limits and with sharedMemPerBlock/maxSharedMemoryPerMultiProcessor from the device query (F1-58). H1 H2 Where they disagree, the more specific and more recent document usually wins, but the passport records both and marks the field open until resolved.

The whitepaper opened for this chapter, W1, has the sections "Introduction", "AMD CDNA 2 Architecture Overview", "Scaling the Memory Hierarchy", "Communication and Scaling", "AMD CDNA 2 Architecture Shader Array", "AMD CDNA 2 Matrix Core Technology", "AMD CDNA 2 Packed FP32", "AMD ROCm Open Software Platform Enables AMD CDNA 2", "AMD Instinct MI200 Series Product Offering" and "Conclusion": the overview and block diagrams first, then the compute unit, then the product table. The product table shows the two habits this chapter warns about. Counts are per package for a two-die product: the MI250X is listed with 220 compute units in two graphics compute dies of 110 each, the MI250 with 208 (104 per die), while each die physically has 112; and the peak figures rest on a footnoted "peak boost engine clock" of 1,700 MHz. The whitepaper describes each compute unit as "4x 16-wide SIMD" (the origin of the illustrative wording above) and uses 64-work-item wavefronts, in agreement with the ISA guide's definition (D6, section 1.1). Mapping a kernel onto the hardware (exam P)

To map a kernel's threads onto a named GPU using only its documentation, you need: the warp/wavefront size; the number of SMs/CUs; per-SM limits (resident threads, warps, blocks, registers, shared memory); and the kernel's resource use from the compiler. Then: threads per block → warps per block (F1-57); resource use → blocks per SM and occupancy (F1-58); grid size ÷ (blocks per SM × SM count) → waves (F1-56). Every input number gets a tag. The worked example does it for TG-1, whose "documentation" is the invented table of this course.

How the hardware actually does it

A whitepaper describes the hardware at the level of this course's chapters: SMs or CUs (F1-56), each with schedulers that issue warp or wavefront instructions (F1-57, F1-60) to arithmetic units and matrix units (F1-61), reading a register file and a shared memory or LDS (F1-58), backed by caches, an L2 and HBM or GDDR (F1-59), with a host link and possibly GPU-to-GPU links (F1-62). W1 W2 The compiler encodes the parts of that design that software must obey: the wavefront size (metadata and constants, R2), the available instructions (accepted or rejected builtins, R6), and resource limits checked at compile and launch time. R2 R6 The device query reports what the driver knows about the installed board (H1, H2). Measurements report what the hardware does under one workload. Each of these sees the same machine from a different side; the passport puts them next to each other.

Worked example

Task (exam P style, on TG-1). TG-1's "documentation" (invented): 4 SMs; warp of 32; per SM 16 resident warps, 4 resident blocks, 16,384 registers, 32 KiB shared memory. A kernel launches 10,000 threads in blocks of 256; the compiler reports 24 registers per thread and 4,224 bytes of shared memory per block. Map it onto the hardware.

  1. Warps per block: 256 / 32 = 8 [DOC: TG-1 table, warp size].
  2. Blocks: ⌈10,000 / 256⌉ = 40; the last block has 10,000 − 39 × 256 = 16 active threads (one warp with 16 active lanes and 7 empty warps).
  3. Blocks per SM: registers 16,384 / (24 × 256) = 2; shared memory 32,768 / 4,224 = 7; warps 16 / 8 = 2; block limit 4 → 2 blocks per SM, 16 warps, occupancy 100 % [DOC: TG-1 limits; TOOL: compiler report].
  4. Waves: 4 SMs × 2 blocks = 8 blocks at a time; 40 / 8 = 5 full waves.
  5. Each warp is 32 lanes executing in lock step (F1-57); the 16-thread tail warp runs at 50 % SIMD efficiency for its instructions.

Check steps 1–3 with F1-58's Listing 4 (input line examP 24 4224 256). For the named product, replace each [DOC] input by the whitepaper or programming-guide value with its section, and each [TOOL] input by your compile of the kernel for that target.

Where the analogy breaks


    

  • A brochure cannot be tested against the building's own order forms. A GPU can: the compiler, the driver and small probes give independent evidence that a restaurant brochure never has (R2). R2
    • 

  • Advertising is not always wrong. Peak figures are usually correct under their conditions; the problem is using them as if they were measurements.
    • 

  • One timed service is not "the" performance. A measurement describes one workload on one system; the passport's MEAS entries must name both.
    • 




Common mistakes and debugging


    

  • Symptom: a passport number nobody can trace. Cause: copied from memory, a forum or a slide. How to find it: Listing 1 reports a missing or invalid tag. Fix: find the document and section, or mark it TBD.
    • 

  • Symptom: "our measured bandwidth is 95 % of peak" is quoted as the peak. Cause: peak and measurement swapped. Fix: two fields, two tags (AH-23).
    • 

  • Symptom: a passport of the right product family but the wrong variant. Cause: whitepapers often cover several products; the lab board is one of them. How to find it: the device query's product name and target. Fix: record the exact variant and the document's table row.
    • 

  • Symptom: the passport says wavefront 32 for a CDNA GPU. Cause: confusion with RDNA defaults or with NVIDIA. How to find it: compiler metadata for the target (R2). Fix: tag the field to the TOOL evidence.
    •

Course project


The hardware passport. One page for the lab GPU, as the course card requires: every number tagged to the vendor document (with section) or to a measurement or tool run (with its run record). Minimum fields: product and variant; compiler target; warp/wavefront size; SM/CU count; per-SM/CU limits (threads, warps, blocks, registers, shared memory/LDS); L2 size; memory type, interface width, data rate, peak bandwidth (with formula) and measured bandwidth; matrix-unit formats; host link and GPU-to-GPU links; device-query excerpt. Include the checker's final report.


Rubric. Every value tagged and checkable (4). Peaks and measurements separated, with the peak's formula (2). At least three cross-checks between independent sources, disagreements recorded (2). Clear one-page layout readable by a non-specialist (2).
