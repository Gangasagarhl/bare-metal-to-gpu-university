Story hook

The banquet hall is a fast kitchen, but every ingredient comes from the restaurant's main building, through one corridor, on trolleys. One night the kitchen's manager sees something odd on the activity board: the cooks stand idle almost all evening. The kitchen is not slow; there is nothing on their benches.

She walks the corridor. Each order is sent in its own trolley, fully loaded before it leaves; the cooks finish it in moments; then the empty trolley is sent back full of plates, and only then does the next trolley leave. The corridor is busy, the cooks are not. On top of that, the trolleys are loaded from the main building's ordinary shelves, which are not allowed to be wheeled out directly, so every crate is first repacked onto a loading dock.

The corridor is PCIe, the bus between the CPU's memory and the GPU. The kitchens next door, wired to each other by private passages, are GPUs linked by NVLink or xGMI. And the activity board is the profiler's timeline in this course's forensic case: "Why is my GPU idle?"

What you will be able to do

  • Model a transfer as a fixed cost plus bytes ÷ bandwidth, and compute when transfers dominate a job.
  • Explain what PCIe, NVLink/NVSwitch and Infinity Fabric/xGMI connect, and why GPU-to-GPU links exist.
  • Explain page-locked (pinned) host memory and why asynchronous, overlapped copies depend on it, from the CUDA headers.
  • Read a copy/compute timeline and diagnose an idle GPU from it.
  • Find a machine's PCI devices and a GPU's link-related properties.
Jargon box
PCIe
Simple words: the standard connection between a computer's processor and plug-in cards like GPUs. Analogy: the corridor from the main building to the hall. Precise: PCI Express, a point-to-point serial interconnect organised as a tree of links from the root complex through switches to endpoints; each link has a number of lanes and a generation that sets the per-lane rate. On Linux, lspci -tv prints the tree. S1 R3
NVLink / NVSwitch
Simple words: NVIDIA's private, faster connections between GPUs, and a switch chip that connects many GPUs that way. Analogy: private passages between neighbouring kitchens, and a hub where many passages meet. Precise: NVIDIA's GPU-to-GPU (and on some systems CPU-to-GPU) interconnect, and the switch that lets every GPU in a node reach every other over it. S2
Infinity Fabric / xGMI
Simple words: AMD's connections inside and between its chips; xGMI is the version that links GPUs (and CPUs) to each other. Analogy: AMD's private passages. Precise: AMD's coherent interconnect family; its inter-socket/inter-GPU links are called xGMI. S3
Alpha–beta model
Simple words: a transfer costs a fixed start-up time plus a time per byte. Analogy: every trolley trip costs the walk, plus the time to roll each crate. Precise: T(n) = α + n/β, where α is the latency per transfer and β the bandwidth; small transfers are dominated by α, large ones by n/β. D2 R1
Pinned (page-locked) memory
Simple words: host memory the operating system promises not to move, so the GPU can read it directly. Analogy: crates already on the loading dock. Precise: host memory locked in physical memory and accessible to the device; the CUDA header says it "can be read or written with much higher bandwidth than pageable memory", and that copies from pageable memory go through "staging memory for DMA transfer". H1
Copy engine / DMA
Simple words: a helper on the GPU that moves data over the link by itself while the GPU computes. Analogy: the trolley porters, who work while the cooks cook. Precise: a direct-memory-access engine; the CUDA property asyncEngineCount is "1 when the device can concurrently copy memory between host and device while executing a kernel", and 2 when it can copy in both directions and execute a kernel at the same time. H1
Peer-to-peer (P2P)
Simple words: one GPU reading or writing another GPU's memory directly, without going through the CPU's memory. Analogy: passing a crate through the passage to the next kitchen. Precise: direct device-to-device access over PCIe or NVLink/xGMI when the platform allows it; CUDA reports it with cudaDeviceCanAccessPeer. D3

The idea in pictures

Layer 1 — the kid explanation

A GPU is a separate machine plugged into the computer. Its own memory is fast, but the data first have to travel from the computer's memory to the GPU, through a cable-like connection called PCIe, and the results have to travel back.

That trip is much slower than the GPU's own memory. So if you send a little data, do a little work, and send it back, the GPU spends most of its time waiting for deliveries. The trick is to send data while the GPU is already working on the previous piece, and best of all, to keep the data on the GPU and do lots of work on it before sending anything back.

Big computers with many GPUs also have special fast passages between the GPUs, so they can share data without going through the main computer.

Layer 2 — the student explanation

Cost of a copy

Model every copy as T = α + bytes/β. With the TG-1 invented host link (β = 16 GB/s, α = 10 µs), copying 256 MB takes 0.01 + 16.0 = 16.01 ms; copying it in, running a 4 ms kernel and copying 256 MB back takes 36.02 ms, and the GPU is busy 11.1 % of that time (R1). R1 D2 The fixed cost α matters for small copies: 64 copies of 8 MB pay α 64 times. The more fundamental issue is the ratio of work to bytes: a kernel that spends 4 ms on 256 MB cannot hide a 16 ms copy.

Overlapping copies and kernels

Copies are done by DMA engines, so they can run while kernels run, if the hardware has the engines and the program lets them: asyncEngineCount reports 1 when the device "can concurrently copy memory between host and device while executing a kernel" and 2 when it can copy in both directions while executing a kernel. H1 The program splits the work into chunks and issues copies and kernels with the asynchronous API into several streams. Listing 1's overlap mode models three engines (in, compute, out), each in order: with 8 chunks the same job takes 18.59 ms instead of 36.02 ms (R1). R1

Overlap requires pinned host memory. The installed CUDA header's "API synchronization behavior" section says that for transfers from pageable host memory "the function will return once the pageable buffer has been copied to the staging memory for DMA transfer", and that for asynchronous copies "if pageable memory must first be staged to pinned memory, this will be handled asynchronously with a worker thread"; cudaMallocHost's comment says page-locked memory "can be read or written with much higher bandwidth than pageable memory" and warns that allocating too much of it "may degrade system performance". H1

Keep data where the work is

The largest gain does not come from faster copies but from fewer: copy once, run many kernels on data in GPU memory, copy the results once. In Listing 1's resident case, ten 4 ms kernels between one copy in and one copy out keep the GPU busy 55.5 % of the time (R1). R1 This is why GPU applications move whole pipelines to the GPU instead of single functions.

Layer 3 — the engineer's depth

The analogy in one line: the corridor's width is fixed when the building is built (link generation and lanes), but how often you send trolleys and how full they are is your program.

PCIe as a tree

PCIe connects devices in a tree under the CPU's root complex; switches fan one upstream link out to several downstream ones. S1 Two GPUs under one switch can exchange data without crossing the root; two GPUs under different branches share the links above them. On the build container, lspci -tv shows a flat virtual bus with virtio devices and no GPU (R3): any statement about this course's PCIe topology must come from the lab machine. R3 The CUDA properties pciBusID, pciDeviceID and pciDomainID identify where each GPU sits, so you can match the runtime's device numbers to the lspci tree (H1; Listing 2). H1

Why GPU-to-GPU links exist

Training and simulation across several GPUs exchange large volumes between GPUs (gradients, halos, layer activations). Over PCIe, these exchanges share the host links and the root. Dedicated links (NVLink, possibly through NVSwitch; AMD's xGMI) connect GPUs directly with more bandwidth than the host link, so collective operations such as all-reduce run without the CPU's memory. S2 S3 D1 Communication libraries (NCCL, RCCL) choose routes according to the topology they detect; their algorithms are the subject of SP303.

Fitting α and β

The alpha–beta model's two parameters are measured, not assumed: time copies of sizes from a few bytes to hundreds of megabytes, fit a line to time against size; the intercept is α, the inverse slope β. Pageable and pinned memory give different lines. The F6 labs do this on the lab GPU; here the TG-1 values are invented for arithmetic, and Listing 2 of F1-59 shows the method for a host-only copy. D2

How the hardware actually does it

A host-to-device copy is executed by a DMA engine on the GPU: it reads host physical memory over PCIe and writes device memory, without the CPU moving the bytes. D3 To read host memory directly, the pages must stay at known physical addresses, which is what page-locking guarantees; pageable memory is first copied by the driver into a pinned staging buffer, then DMA'd, which is the "staging memory for DMA transfer" in the header (H1). H1 The PCIe link moves data in packets with headers and acknowledgements, so the payload rate is below the raw signalling rate. S1 GPUs with more than one copy engine can move data in both directions while kernels run (asyncEngineCount 2, H1). H1 GPU-to-GPU links carry loads, stores and atomics from one GPU's memory system to another's, so a kernel on one GPU can address a peer's memory directly when peer access is enabled (cudaDeviceCanAccessPeer, cudaDeviceEnablePeerAccess). D3

Worked example

Task. A job processes 1 GB of input into 1 GB of output with a kernel that needs 20 ms for the whole gigabyte. The host link (TG-1, invented) has β = 16 GB/s and α = 10 µs. (a) Serial time and GPU busy fraction with one copy each way. (b) The best possible time if copies and the kernel overlap perfectly (both directions concurrently). (c) How much kernel work per gigabyte would make the link no longer the limit?

  1. (a) Copy in: 0.01 + 1,000 MB / 16 GB/s = 0.01 + 62.5 = 62.51 ms; same out. Total 62.51 + 20 + 62.51 = 145.02 ms; busy 20 / 145.02 = 13.8 %.
  2. (b) With in, compute and out overlapped on separate engines, the time approaches the slowest stage: about 62.5 ms (plus the first chunk's fill and the last chunk's drain). The GPU is still busy at most 20 / 62.5 = 32 %.
  3. (c) The kernel must take at least as long as one direction's copy: ≥ 62.5 ms per gigabyte, more than three times the current work. Otherwise only keeping data resident or sending fewer bytes (compression, reduced precision, filtering on the host) helps.

Check (a) with Listing 1: worked serial 1 1000 1000 20 16 10 (R1's model; your run). Check (b) with worked_b overlap 32 31.25 31.25 0.625 16 10; the model gives 65.41 ms with 32 chunks: the 62.5 ms of one direction plus fill and drain. R1

Where the analogy breaks


    

  • Trolleys can pass each other. A PCIe link carries traffic in both directions at once; the corridor in the story is one-way per trip. S1
    • 

  • Repacking is not done by the cooks. Staging pageable memory costs CPU time and host memory bandwidth, not GPU time; the GPU only sees a slower, later copy. H1
    • 

  • Private passages are not always private. Whether GPUs can address each other directly depends on the platform and its settings (the unverified box), not only on the links.
    • 




Common mistakes and debugging


    

  • Symptom: cudaMemcpyAsync does not overlap with kernels. Cause: pageable host memory, or all work in the default stream. How to find it: the timeline shows copies and kernels never side by side. Fix: pinned buffers and separate streams.
    • 

  • Symptom: the GPU is idle most of the time in a profile. Cause: transfers dominate (the forensic case). Fix: fewer, larger, overlapped transfers; keep data resident.
    • 

  • Symptom: the machine becomes sluggish after a "pin everything" change. Cause: too much page-locked memory (H1's warning). Fix: pin a few staging buffers and reuse them.
    • 

  • Symptom: multi-GPU scaling stalls at two GPUs. Cause: traffic routed over PCIe through the CPU instead of over GPU links. How to find it: topology commands and the communication library's debug output. Fix: place processes on GPUs that share a link; enable peer access.
    •

Summary


    

  • A copy costs α + bytes/β; the host link is far slower than device memory.
    • 

  • DMA engines let copies overlap kernels (asyncEngineCount 1 or 2), but only with pinned host memory and asynchronous calls in separate streams.
    • 

  • Pageable memory is staged through a pinned buffer; pinned memory is faster but limited (H1).
    • 

  • The biggest gain is fewer transfers: keep data on the GPU across kernels.
    • 

  • NVLink/NVSwitch and xGMI connect GPUs directly for multi-GPU work; PCIe connects them to the host.
    • 

  • An idle GPU in a timeline full of copies is a data-movement problem, not a GPU-speed problem.

Forensic lab answer key


Observation. Total 178.35 ms; GPU busy 6.40 ms = 3.6 %. Each 8 MB copy costs 0.01 + 1.33 ms; 128 copies take about 172 ms. The kernels take 0.1 ms per batch.


Root cause. The job is limited by the host link and by how it uses it. (1) Every copy is synchronous and the next step waits for it: copies, kernels and copies never overlap. (2) The 6 GB/s rate is consistent with pageable memory being staged through a pinned buffer by the driver (H1's "staging memory for DMA transfer"); the profile alone does not prove this, so check by repeating with cudaMallocHost buffers. (3) The work per byte is tiny: 0.1 ms of kernel per 8 MB, while one 8 MB copy takes more than 1.3 ms, so even perfect overlap leaves the GPU mostly idle. A bigger GPU would shorten the 6.4 ms of kernel time and change almost nothing.


Fix, in order of expected gain. (a) Keep data on the GPU: fuse more of the pipeline into GPU kernels so that each byte crosses the link once and gets more work. (b) Pinned buffers (the header's "much higher bandwidth than pageable memory"), with a few reused staging buffers. (c) Asynchronous copies in several streams so copies in, kernels and copies out overlap. The Lab Engineer's check runs of Listing 1 (not in the recorded output): overlap alone at 6 GB/s gives 87.42 ms; overlap with a 16 GB/s link (TG-1, invented) gives 33.25 ms; GPU busy stays below 20 % until (a) is done.


Wrong answers and why. "Buy a bigger GPU": the GPU is busy 3.6 % of the time; a faster GPU only shortens that part.


How the evidence was produced. The Lab Engineer ran Listing 1 on forensic.in, whose values reproduce the scenario's profile (invented; no GPU was profiled). Prevention: before moving a step to the GPU, compute bytes moved per iteration ÷ link bandwidth and compare it with the expected kernel time; require pinned staging buffers in the coding guidelines.
