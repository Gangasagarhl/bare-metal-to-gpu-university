Story hook

The banquet hall gets its ingredients from a warehouse across the yard. A delivery road connects them. Two warehouse companies offer contracts. The first has a narrow road with a few lanes, but its carts run very fast. The second builds the warehouse right against the hall's back wall, with a very wide doorway and hundreds of slow, short carts going through side by side.

Omar, who orders for the hall, asks the only question that matters for a big banquet: "How many crates per second reach the kitchen?" For the first company that is lanes × cart speed. For the second it is also lanes × cart speed: far more lanes, far slower carts. He writes both products down and compares them. A colleague, in a hurry, takes the second company's "engine speed" from the brochure instead of the speed at which crates actually pass, and gets a number eight times too small.

The two companies are GDDR (graphics DRAM chips on the board, around the GPU) and HBM (stacks of DRAM dies right next to the GPU, connected by a very wide interface). The question is the peak bandwidth, and the colleague's mistake is the most common one in this topic.

What you will be able to do

  • Compute the peak bandwidth of a memory interface from its width and data rate, and say which units the answer is in.
  • Distinguish clock frequency from data rate, and decimal GB/s from binary GiB/s.
  • Compare the design choices of HBM and GDDR (wide-and-slower versus narrow-and-faster) without quoting product numbers you cannot source.
  • Bound the run time of a memory-bound kernel from the bytes it must move.
  • Find the memory-system fields of a GPU in the device-query structures of CUDA and HIP.
Jargon box
DRAM
Simple words: the main memory chips: large, cheap per byte, and slow to start answering. Analogy: the warehouse. Precise: dynamic random-access memory, storing bits as charge in capacitors organised in banks, rows and columns; reads open a row and then stream columns. GPU device memory is DRAM. D2
HBM
Simple words: DRAM chips stacked on top of each other and placed right next to the GPU, connected by a very wide set of wires. Analogy: the warehouse against the back wall with a huge doorway. Precise: High Bandwidth Memory, a JEDEC-standardised stacked DRAM with a very wide interface per stack, connected to the processor through a silicon interposer or similar package technology. J1 D1
GDDR
Simple words: separate memory chips on the graphics board, around the GPU, each connected by fewer, much faster wires. Analogy: the narrow road with fast carts. Precise: Graphics Double Data Rate SDRAM, a JEDEC family of DRAM devices with narrow, high-data-rate interfaces, placed on the circuit board. J2
Bus width
Simple words: how many wires carry data at the same time. Analogy: the number of lanes on the road. Precise: the total number of data bits transferred in parallel by the whole memory interface; the CUDA runtime reports memoryBusWidth, "Global memory bus width in bits". H1
Data rate (GT/s)
Simple words: how many times per second each wire sends a new bit. Analogy: how many carts per second pass on one lane. Precise: transfers per second per data pin; one transfer moves one bit per pin. It can be a multiple of a clock frequency (double data rate moves data on both clock edges), which is why a clock in MHz is not a data rate. D2
Peak bandwidth
Simple words: the most bytes per second the memory could ever deliver. Analogy: lanes × carts per lane per second. Precise: (bus width in bits ÷ 8) × data rate; a theoretical upper bound that real kernels approach but do not reach (F6-11 measures how close). D1 R1
GB/s versus GiB/s
Simple words: two different sizes of "gigabyte": a thousand-million bytes or 230 bytes. Analogy: crates counted in tens or in dozens. Precise: 1 GB = 109 bytes; 1 GiB = 230 = 1,073,741,824 bytes; bandwidths in datasheets are normally decimal, memory sizes often binary. Always state which (guide 13.4). C1
ECC
Simple words: extra bits that let the memory detect and fix small errors. Analogy: a checksum on each crate's label. Precise: error-correcting codes stored with the data; on some memories they use extra pins or capacity and reduce usable bandwidth or size. The CUDA runtime reports ECCEnabled. H1 D2

The idea in pictures

Layer 1 — the kid explanation

A GPU does a lot of work, and nearly all of it needs data from its big memory. The memory is like a warehouse, and the data travels along many wires, like crates on a road with many lanes.

There are two ways to make the road carry more: more lanes, or faster carts. GDDR memory uses few lanes with very fast carts. HBM memory puts the warehouse right next to the GPU and uses a huge number of lanes with slower carts. To know which is better, multiply lanes by speed: that product is how much arrives each second.

And be careful with the brochure: "how fast the engine turns" is not "how many carts pass per second". Use the number that counts carts.

Layer 2 — the student explanation

The peak formula

A memory interface of W data bits that makes R transfers per second on each pin can move at most W/8 × R bytes per second. D1 D2 Listing 1 computes it for TG-1's invented interface: 256 bits = 32 bytes per transfer, × 8 × 109 transfers per second = 256 × 109 bytes per second = 256 GB/s, which is 238.4 GiB/s (divide by 230 instead of 109). A wide-but-slower invented interface of 4,096 bits at 1 GT/s gives 512 GB/s: twice as much, at one eighth of the rate per pin (R1). R1 A real example, read in the verification pass from AMD's CDNA 2 whitepaper: the product table lists the Instinct MI250X with 128 GB of HBM2e on an 8,192-bit interface and a peak of 3.2 TB/s, and the MI210 with 64 GB on 4,096 bits at 1.6 TB/s. Running the formula backwards, 3.2 × 1012 bytes per second over 1,024 bytes per transfer is about 3.1 GT/s per pin: wide and comparatively slow, as the next section explains. W1

A lower bound on time

A memory-bound kernel cannot finish faster than the bytes it must move divided by the peak bandwidth. SAXPY (y = a·x + y) on n single-precision elements reads x and y and writes y: 12n bytes. For n = 226 that is 805.306 MB, and at 256 GB/s at least 3,145.728 µs (R1). A real run is slower; how much slower is a measurement (F6-11), and comparing the two is the start of a roofline analysis (F6-09). R1 For tiny inputs the bound is meaningless: 1,024 elements need 0.048 µs at peak, far below the time it takes to launch a kernel. R1

What the runtime reports

The installed CUDA header defines memoryBusWidth ("Global memory bus width in bits") and memoryClockRate ("Deprecated, Peak memory clock frequency in kilohertz"); HIP's header defines the same names ("Global memory bus width in bits." and "Max global memory clock frequency in khz."). H1 H2 Note the words: the runtime reports a clock frequency, not a data rate. Turning one into the other needs the number of transfers per clock of that memory type, which the header does not give. Listing 3 prints these fields; in this build it printed the runtime's "no device" error. R4

Not verified — check before relying on this

The number of data transfers per reported clock differs between memory types and between how each vendor's runtime defines the reported clock; it is commonly said that the CUDA bandwidthTest-style calculation multiplies the reported memory clock by 2. This could not be checked: the CUDA Runtime API reference page for cudaDeviceProp and the HIP API reference could not be opened in the verification pass (the shared web-fetch budget ran out), and the installed headers (H1, H2) give only the field comments quoted above. Do not convert memoryClockRate into bandwidth without the vendor's definition for your GPU. Check: the CUDA Runtime API reference for memoryClockRate, the HIP API reference for hipDeviceProp_t, and the memory standard (J1 or J2) for the data rate per pin.

Layer 3 — the engineer's depth

The analogy in one line: lanes are wires, and wires cost area, power and package technology; carts are signalling speed, and speed costs power and signal integrity.

Why two designs

Every off-chip wire needs a pin, a driver and a receiver. GDDR keeps the number of wires moderate and pushes the data rate per pin high, which needs careful board design and spends energy on each fast transfer. HBM moves the DRAM into the package, beside the processor, where thousands of short connections are possible; it then runs each pin at a lower rate. D1 J1 J2 The trade-offs (cost, capacity, energy per bit, packaging) are reasons why data-centre accelerators and consumer graphics cards have often made different choices. D1

Not verified — check before relying on this

Details written from memory and not checked here: that an HBM stack's interface is organised as many independent channels (and pseudo-channels in later generations); that HBM connects through an interposer with through-silicon vias inside the stack; that GDDR6 devices have two independent channels per chip; which data rates each generation allows. This chapter deliberately gives no per-generation numbers. The JEDEC standards are behind JEDEC's registration wall and were not opened in the verification pass; by ruling C2 they are cited by their catalogue entries (J1, J2) and every claim about their content stays here. Check: the JEDEC HBM and GDDR6 standards (J1, J2) and the vendor page of the reference kit's GPUs (F1-63).

Why the peak is not reached

DRAM moves data fastest when it streams columns from an open row. Opening a new row, refreshing, switching between reads and writes, and uneven use of channels all spend time without transferring data. D2 The GPU side adds its own limits: requests must be grouped into large, aligned accesses (coalescing, F6-12) or each transfer carries bytes nobody asked for. The difference between peak and achieved is why F6-11 measures bandwidth and why the passport of F1-63 tags peak numbers to a document and achieved numbers to a measurement.

Units, again

Write the units in every step. A "bit" versus "byte" slip is a factor of 8; GB/s versus GiB/s is about 7 % (256 GB/s = 238.4 GiB/s, R1); a clock versus a data rate is a factor that depends on the memory type. Guide 13.4 requires the unit to be named every time. C1 R1

A measurement you can make here

The build container has no GPU, but it has DRAM. Listing 2 copies 64 MiB with memcpy eleven times and reports the slowest, median and fastest rate, counting read plus write. It measures this machine's host memory system under one particular workload, not any GPU; its value is in the method: name the bytes counted, repeat, report a spread, state the machine (R2). R2

How the hardware actually does it

Each SM's memory requests that miss in its L1 go to the L2 (F1-58); the L2 is divided into slices, each in front of one or more memory controllers, and addresses are spread across them so that a streaming access uses all channels at once. D1 D2 A memory controller turns requests into DRAM commands (activate a row, read or write columns, precharge, refresh) and schedules them to keep its channel busy. D2 On the wires, data moves in bursts: several transfers per command, each moving one bit per data pin. The physical interface (PHY) on the GPU die drives and samples those pins at the data rate; for HBM it connects to the stack through the package, for GDDR through traces on the board. J1 J2 The peak formula counts only the data pins at full rate; command, address and refresh time, and ECC where it uses data capacity, are what keep real throughput below it.

Worked example

Task. An invented GPU has a 384-bit GDDR interface at 14 GT/s per pin. (a) Compute its peak bandwidth in GB/s and GiB/s. (b) A kernel adds two vectors of 108 doubles into a third. Find its minimum time. (c) A measured run takes 2.0 ms. What fraction of peak did it achieve?

  1. (a) 384 / 8 = 48 bytes per transfer. 48 × 14 × 109 = 672 × 109 B/s = 672 GB/s. In GiB/s: 672 × 109 / 1,073,741,824 ≈ 625.8 GiB/s.
  2. (b) Bytes moved: read 2 × 8 × 108, write 8 × 108 = 24 × 108 B = 2.4 GB. Minimum time = 2.4 × 109 / 672 × 109 ≈ 3.57 ms.
  3. (c) A run of 2.0 ms would be faster than the bound: impossible for a kernel that really moves 2.4 GB. Check the measurement: maybe the timer missed part of the kernel (no synchronisation), or the vectors were smaller than assumed, or a cache held part of the data. A bound is a tool for catching wrong measurements as much as slow kernels.

Check (a) and (b) with Listing 1: add the line worked 384 14 100000000 to peak_bw.in. Listing 1 assumes 12 bytes per element (SAXPY with floats), so for (b) multiply its element count by 2 (24 bytes per element): worked_b 384 14 200000000 prints the 3,571.429 µs bound. R1

Where the analogy breaks


    

  • Carts carry crates of any size; transfers carry one bit per wire. Bandwidth is always (bits per transfer) × (transfers per second); there is no "bigger cart".
    • 

  • The road is not the whole story. The warehouse needs time to find each shelf (row activation); a road at full speed delivers less when the warehouse keeps switching shelves. D2
    • 

  • Moving the warehouse is not free. HBM's closeness comes from package technology with its own cost and capacity limits, which the story leaves out. D1

Common mistakes and debugging


    

  • Symptom: computed bandwidth is a small fraction of the datasheet's. Cause: a clock frequency used as the data rate. How to find it: check the unit: MHz or kHz is a clock; GT/s or Gb/s per pin is a data rate. Fix: use the data rate, or the vendor's conversion (the forensic lab).
    • 

  • Symptom: a result off by exactly 8. Cause: bits and bytes mixed. Fix: carry units through every line of the calculation.
    • 

  • Symptom: a result about 7 % off a published number. Cause: GB versus GiB. Fix: state the unit; datasheet bandwidths are normally decimal.
    • 

  • Symptom: a measured bandwidth above the peak. Cause: the data fit in a cache, the timer missed work, or the byte count is wrong. How to find it: grow the buffer; synchronise before stopping the timer; recount the bytes. Fix: correct the measurement before believing it (F6-11).
    •

Summary


    

  • Peak bandwidth = (width in bits ÷ 8) × data rate per pin; it is an upper bound.
    • 

  • HBM: very wide, slower per pin, in the package. GDDR: narrower, faster per pin, on the board.
    • 

  • A clock frequency is not a data rate; the runtime reports a clock.
    • 

  • GB = 109 bytes, GiB = 230 bytes; say which.
    • 

  • Bytes moved ÷ peak bandwidth gives a minimum time; a measurement faster than that is a broken measurement.
    • 

  • Real throughput is lower than peak because of DRAM commands, refresh, access patterns and ECC.

Forensic lab answer key


Observation. Colleague's inputs: 32.0 GB/s, SAXPY bound 25,165.824 µs. Datasheet inputs: 256.0 GB/s, bound 3,145.728 µs. The factor is 8.


Root cause. The footnote's "1.0 GHz" is a clock (the header calls the field "Peak memory clock frequency"); the datasheet's 8 GT/s is the data rate per pin. Feeding a clock into a formula that needs transfers per second undercounts by the number of transfers per clock, here 8 (an invented ratio for TG-1; real ratios depend on the memory type, see the unverified box).


Wrong answers and why. "The device query is wrong": it reported a clock correctly; it was misread. "The datasheet is wrong": nothing in the evidence contradicts it; check it, but the unit mismatch explains the factor exactly.


Fix. "Peak memory bandwidth 256 GB/s (238.4 GiB/s), computed from 256-bit interface × 8 GT/s per pin (vendor datasheet, section …); not measured."


How the evidence was produced. The Lab Engineer ran Listing 1 on the two input lines of forensic.in. The accelerator, its clock and datasheet are invented (TG-1). Prevention: a planning template that asks for "data rate per pin (GT/s)" and its source, separately from any clock, and requires a unit next to every number.
