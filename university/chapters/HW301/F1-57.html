Story hook

In each section of the banquet hall, helpers stand in rows. A row does not get one recipe card per helper; it gets one supervisor who calls out one step at a time, and every helper in the row does that step on their own bowl. "Ladle the soup." Thirty-two ladles move. "Add the herbs." Thirty-two pinches of herbs. One voice, thirty-two pairs of hands: the supervisor's voice is cheap, and the hands do the work.

Then a card says: "If the guest ordered it spicy, add chili; otherwise add cream." Kofi's row has a problem. Nine bowls are spicy, twenty-three are not. The supervisor cannot call two steps at once. So she calls "chili" and the nine spicy helpers act while the other twenty-three wait with their hands still; then she calls "cream", and the twenty-three act while the nine wait. Both groups are back together for the next step, "serve". The row took two steps of time for one step of work.

In AMD's building next door, the rows are sixty-four helpers long. The voice is shared even more widely, and a single spicy bowl now keeps sixty-three helpers waiting instead of thirty-one. This chapter is about these rows, which NVIDIA calls warps and AMD calls wavefronts, and about what the hardware does when the bowls disagree.

What you will be able to do

  • Explain SIMT execution: one instruction stream driving a warp or wavefront of lanes, with an active mask.
  • Predict the cost of a divergent branch from the lanes' data, and compute SIMD efficiency.
  • Read divergence and vote instructions in real PTX, SASS and AMD assembly, and find the warp or wavefront width in compiler output.
  • Write warp-width-independent code, and explain why lane masks are 32-bit on NVIDIA and 64-bit on wave64 AMD targets.
  • Diagnose a reduction that is correct on 32-wide warps and wrong on 64-wide wavefronts.
Jargon box
Warp / wavefront
Simple words: a group of GPU threads that always do the same step at the same time. Analogy: a row of helpers who follow one supervisor's voice. Precise: the group of threads that the hardware schedules and executes together with one instruction stream; NVIDIA calls it a warp (32 threads on the targets compiled in this build: the sm_80 SASS replaces warpSize by 0x20), AMD a wavefront (64 lanes on gfx90a and gfx942, 32 by default on the RDNA targets gfx1030 and gfx1100 in this build's compiler). D3 R4 R6
Lane
Simple words: one position in a warp; one thread's slot. Analogy: one helper's place in the row. Precise: the index of a thread within its warp or wavefront (0 to width − 1); lane-indexed bits form the masks used by votes and by the hardware's active mask. D3 D6
SIMT
Simple words: "single instruction, multiple threads": you write code for one thread, the hardware runs it for a whole row at once. Analogy: one recipe card read aloud to a row. Precise: NVIDIA's name for its execution model, in which threads are programmed as independent scalar threads but executed in warps that share instruction issue; divergent threads are handled by masking. D3 D1
Active mask / EXEC
Simple words: a row of on/off switches saying which threads of the warp take part in the current step. Analogy: which helpers in the row have their hands up. Precise: a bit mask with one bit per lane; disabled lanes do not write results. On AMD GCN/CDNA it is the architectural 64-bit register EXEC, manipulated by instructions such as s_and_saveexec_b64; on NVIDIA it is maintained by the hardware and the compiler (predicates and convergence barriers). D6 R5
Divergence
Simple words: when threads of one warp need different steps, so they take turns. Analogy: the spicy bowls and the creamy bowls in one row. Precise: the situation in which lanes of a warp or wavefront evaluate a branch condition differently; the paths are executed one after the other with complementary masks, and the lanes reconverge afterwards. D3 D1
Predication
Simple words: doing both little steps for everybody, but each thread only keeps the result of the step meant for it. Analogy: the supervisor calls both short steps, and each helper's card says which one to really do. Precise: guarding individual instructions with a per-lane predicate instead of branching; NVIDIA SASS writes it as @P0 / @!P0. Compilers use it for short divergent paths. D5 R3
Warp vote (ballot)
Simple words: every thread in the warp says yes or no, and everybody gets the whole list of answers. Analogy: a show of hands in the row, written down as a row of ticks. Precise: an intrinsic that returns a mask with bit l set if lane l's predicate is true: __ballot_sync(mask, p) returns a 32-bit unsigned in CUDA; HIP's __ballot(p) returns a 64-bit value on wave64 targets. D3 D8 R1
SIMD efficiency
Simple words: how many of the lanes did useful work, on average, per step. Analogy: the share of helpers in the row whose hands moved. Precise: useful lane-slots ÷ (instructions issued × width); 100 % without divergence, lower with it. Profilers report related metrics under vendor-specific names. D1 R2

Layer 1 — the kid explanation

A GPU does not give every thread its own supervisor. That would cost far too much. Instead, threads stand in rows, and one supervisor reads each step to the whole row. On NVIDIA GPUs a row has 32 threads; on many AMD GPUs it has 64.

When everybody in the row needs the same step, this is wonderful: one call, many hands. When the row disagrees, for example at an "if", the supervisor reads the "yes" steps while the "no" threads wait, and then the "no" steps while the "yes" threads wait. Nobody gets a wrong answer. But the row spends time on both sides.

So the rule of thumb is: inside one row, try to make threads take the same path. Across different rows, it does not matter, because each row has its own supervisor.

Layer 2 — the student explanation

The SIMT model

In CUDA and HIP you write a kernel as the code of one thread. The hardware groups consecutive threads of a block into warps (NVIDIA) or wavefronts (AMD) and executes each group with one instruction stream: one fetch and decode, many lanes. D3 D1 Which threads form a warp is defined by the programming guide in terms of the thread index within the block: consecutive threads (by threadIdx.x first) form consecutive warps. D3 The width is not a language constant. CUDA exposes it as the built-in variable warpSize; this build's compiler leaves it symbolic in PTX (mov.u32 %r16, WARP_SZ;) and replaces it by 0x20 = 32 in the SASS for sm_80 (IADD3 R5, R4, 0x20, R5). R3 D4 HIP defines warpSize as the compiler macro __AMDGCN_WAVEFRONT_SIZE (in the installed header amd_warp_functions.h), which this build's compiler sets to 64 for gfx90a and gfx942 and to 32 for gfx1030 and gfx1100 unless -mwavefrontsize64 is given; the gfx90a assembly adds the constant 64 where the source says warpSize (v_add3_u32 v2, v2, s0, 64). H2 R5 R6

Divergence and its cost

When the lanes of a warp evaluate a branch differently, the hardware executes each path with only the lanes that took it enabled, and the lanes reconverge where the paths join. D3 D1 Correctness is preserved; time is not. Listing 1 models it: for the branch of Figure 1, a warp whose lanes all agree issues 2 instructions (one path plus the store), while a warp whose lanes alternate issues 4 (both paths plus the store), and SIMD efficiency falls to 62.5 % (R2). The cost depends only on whether any lane takes each path: a single odd lane forces the whole warp through path A ("only lane 0 odd": 50.8 % at width 32, 50.4 % at width 64). R2

The width matters. The pattern "lanes 0–31 even, lanes 32–63 odd" is perfectly uniform inside each 32-wide NVIDIA warp (100 %), but the same data inside one 64-wide wavefront diverges (62.5 %). Code tuned so that warps never diverge on NVIDIA can diverge on wave64 AMD targets. R2

Masks you can see: votes

Warp-level intrinsics expose the lane structure to the programmer. __ballot_sync(0xffffffff, p) returns a 32-bit mask with one bit per lane of the warp whose predicate is true; its first argument names the lanes that take part. D3 In this build's PTX it is vote.sync.ballot.b32, in the SASS VOTE.ANY R4, PT, P0 followed by POPC (population count) for __popc. R3 HIP's __ballot(p) returns a 64-bit value (Listing 3 stores it in unsigned long long); on gfx90a the compiler counts its bits with s_bcnt1_i32_b64 s0, vcc, a scalar instruction on a 64-bit register pair, because the comparison result is already a 64-lane mask in vcc. R5 D6

Layer 3 — the engineer's depth

The analogy in one line: the supervisor's job is now done partly by the compiler and partly by the hardware, and the two vendors split it differently.

AMD: the mask is a register you can read

On GCN and CDNA, the 64-bit EXEC register is the active mask; every vector instruction only affects lanes whose bit is set. D6 The compiler lowers an if/else into explicit mask arithmetic, which this build's gfx90a assembly of Listing 3 shows line by line: v_cmp_eq_u32_e32 vcc, 1, v2 writes the per-lane condition into the 64-bit vcc; s_and_saveexec_b64 s[0:1], vcc saves the old EXEC and keeps only the "then" lanes; s_xor_b64 s[0:1], exec, s[0:1] computes the "else" lanes; the "then" path runs (v_mad_u64_u32 … 3, 1); s_andn2_saveexec_b64 switches EXEC to the "else" lanes; the "else" path runs (the shift sequence for v / 2); and s_or_b64 exec, exec, s[0:1] restores the full mask at the reconvergence point. R5 Earlier, the bounds check if (i >= n) return; became s_and_saveexec_b64 plus s_cbranch_execz: if no lane remains active, the scalar unit jumps over the body entirely. That is the hardware's way of skipping a path no lane takes, the "skipped" line in Listing 1's drawing. R5 R2

NVIDIA: predicates and convergence

For the same short branch, the CUDA compiler did not branch at all: the SASS computes the predicate once (ISETP.NE.U32.AND P0, PT, R4, 0x1, PT) and executes both arms as predicated instructions (@!P0 IMAD R5, R2, R5, 0x1 for 3v + 1 and @P0 SHF.R.S32.HI R5, RZ, 0x1, R4 for the halving). R3 The cost is the same as in the model: both arms are issued for the warp. For longer divergent regions the compiler emits real branches, and the hardware tracks which lanes are on which path; since the Volta generation NVIDIA documents "independent thread scheduling", in which each thread has its own program counter and divergent paths may interleave, which is why warp-level intrinsics carry the _sync suffix and an explicit participation mask. D3

Confirmed in the verification pass: the CUDA Programming Guide says "The SIMT model allows each thread to maintain its own state and control flow" (2.3.1), that "consecutive values of threadIdx.x indicate consecutive threads" (2.3.2) and that "the size of a warp is 32 threads" (2.3.4.2.1), that each SM "executes threads in groups of 32 parallel threads called warps" (3.2.2.1) and, for independent thread scheduling, that from compute capability 7.0 "the GPU maintains execution state per thread, including a program counter and call stack" (3.2.2.1.1); the PTX ISA defines WARP_SZ as "the number of threads per warp for the target platform" (4.5.1), 32 on every target to date; and the ISA guide defines EXEC as a 64-bit mask, "1 = execute, 0 = do not execute" (3.3), with VCC set by vector comparisons, "1=pass, 0=fail" (3.9). D3 D4 D6

Portability rules that follow

  • Never hard-code 32 as the warp size in portable code; use warpSize or a compile-time constant derived from the target (guide 13.4; bridge BR-02). C1
  • Lane masks must be 64-bit where the wavefront is 64 wide: unsigned long long for HIP ballots on wave64. A 32-bit variable silently drops lanes 32–63. R1
  • Shuffle-based reductions start from warpSize / 2, not from 16 (the forensic lab).
  • Block sizes should be multiples of the width, or the last warp of every block runs partly empty: a block of 100 threads uses 4 warps of 32 (28 idle lanes) or 2 wavefronts of 64 (28 idle lanes).

How the hardware actually does it

One instruction fetched and decoded per warp drives many lanes; the lanes are physical arithmetic units, sometimes fewer than the width, in which case one warp instruction takes several cycles to pass through them (a design detail that differs by generation, see the unverified box in F1-56). D1 D2 The active mask gates the write of results: a masked-off lane computes nothing useful and writes nothing, so its time slot is lost. On AMD the mask is the EXEC register set by scalar instructions, exactly as the assembly in Layer 3 shows; the scalar unit also evaluates uniform branches (s_cbranch_execz) so that a path no lane needs costs only the test. D6 R5 On NVIDIA the predicate registers (P0 to P6, PT = always true) gate individual instructions, and the hardware maintains the warp's active threads across real branches. D5 R3 Votes are cheap because the per-lane predicate bits already sit side by side in the hardware: VOTE.ANY R4, PT, P0 gathers them into one register, and AMD's comparison writes them directly into the 64-bit vcc. R3 R5

Worked example

Task. A kernel processes particles; each thread runs if (p.alive) { 10 instructions } else { 2 instructions }, then 4 common instructions. Compute the instructions issued and the SIMD efficiency for one warp of 32 and one wavefront of 64 when (a) all particles are alive, (b) exactly one particle per group is dead, (c) particles are sorted so that the first 40 of every 64 are alive.

  1. (a) All alive. Only the "alive" path runs: 10 + 4 = 14 instructions, all lanes active: efficiency 100 % for both widths.
  2. (b) One dead per group. Both paths run: 10 + 2 + 4 = 16 instructions. Width 32: useful lane-slots = 31 × 10 + 1 × 2 + 32 × 4 = 310 + 2 + 128 = 440 of 16 × 32 = 512: 85.9 %. Width 64: 63 × 10 + 2 + 64 × 4 = 630 + 2 + 256 = 888 of 16 × 64 = 1,024: 86.7 %. The cost per group is the same 16 instructions; one dead particle costs a whole extra path.
  3. (c) Sorted, 40 alive of every 64. Width 64: every wavefront has 40 alive and 24 dead: 16 instructions, useful = 40 × 10 + 24 × 2 + 64 × 4 = 400 + 48 + 256 = 704 of 1,024 = 68.8 %. Width 32: lanes 0–31 of each 64 are all alive (14 instructions, 100 %); lanes 32–63 hold 8 alive and 24 dead (16 instructions, useful 80 + 48 + 128 = 256 of 512 = 50 %). Two warps issue 30 instructions for the same 64 particles that one wavefront handles in 16, but 30 warp-instructions of 32 lanes are 960 lane-slots, fewer than the wavefront's 1,024.

The arithmetic follows the model of Listing 1 (each path issued once if any lane takes it; useful = instructions × active lanes). Sorting work so that groups agree is a standard optimisation; how much it helps depends on the width of the target. D1

Where the analogy breaks


    

  • Waiting helpers could chat; masked lanes do nothing. In the hall, a waiting helper might prepare the next bowl. A masked-off lane's slot is lost for that instruction; the SM fills time with other warps, not with the waiting lanes (F1-60). D1
    • 

  • The supervisor sometimes reads both steps to everybody. With predication the hardware issues both arms to all lanes and each lane keeps one result (R3); there is no "waiting" at all, only wasted slots. R3
    • 

  • Rows are not fixed by the room. AMD's RDNA targets can compile for wave32 or wave64 (R6): the row length is chosen by the compiler for the target, not by the building. R6
    • 




Common mistakes and debugging


    

  • Symptom: a reduction returns half the expected sum on an AMD GPU. Cause: shuffle offsets start at 16 (a hard-coded 32-wide warp). How to find it: test with all inputs equal to 1 and compare with the width (the forensic lab). Fix: start at warpSize / 2.
    • 

  • Symptom: a ballot shows no votes from lanes 32–63. Cause: the result was stored in a 32-bit variable. How to find it: compile with warnings for narrowing; print the mask in hex. Fix: unsigned long long (Listing 3).
    • 

  • Symptom: a kernel is slower than expected with "rare" special cases. Cause: one lane per warp takes the rare path, so every warp runs it. How to find it: the profiler's branch-efficiency metrics; or count with Listing 1's model. Fix: sort or bin the work so that groups agree; move rare work to a second kernel.
    • 

  • Symptom: a CUDA warp intrinsic hangs or gives wrong results after a refactor. Cause: not all lanes named in the mask reach the call (it is inside a divergent branch). How to find it: Compute Sanitizer's synchronisation checks (F6-05). Fix: call it where all named lanes are converged, or pass the correct mask (see the unverified box above).
    • 




Transition box

Where you came from: F1-56 (SMs and CUs) and HW202's single-thread datapath, where one instruction worked on one set of operands; SP203's CPU threads, each with its own program counter.   • SIMT: you write one thread's code; the hardware runs it for a warp (NVIDIA) or wavefront (AMD) with one instruction stream.

  • AMD exposes the mask as the 64-bit EXEC register; NVIDIA uses predicates and hardware-tracked convergence.

  • Votes return one bit per lane: 32-bit masks in CUDA, 64-bit on wave64 HIP targets.
    • 

  • Portable code never hard-codes 32: use warpSize, 64-bit masks and width-derived loop bounds.

Root cause. Line 11 starts the tree at offset 16, which is correct only for a 32-lane group. With offsets 16, 8, 4, 2, 1, lane 0 accumulates lanes 0–31 only: the largest distance a value can travel is 16 + 8 + 4 + 2 + 1 = 31 lanes. On gfx90a the wavefront is 64 lanes wide (.wavefront_size: 64, __AMDGCN_WAVEFRONT_SIZE 64), so half the values are never added. HIP's shuffles are not broken; the model shows the same result with no GPU at all.


Wrong answers and why. "HIP shuffles are broken": the model reproduces the error without any library. "A race": the model is sequential and deterministic, and the sum is exactly 32 every time.
