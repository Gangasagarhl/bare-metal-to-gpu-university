Story hook

Most of the banquet hall's work is one recipe: take a tray of sauce bowls and a tray of spice bowls, and for every pair, mix and add to a running pot. Each helper can do one mix-and-add per step. Then the hall buys a machine: a press that takes a whole tray of sauces and a whole tray of spices at once and mixes every pair in a single stroke, adding the results into a tray of pots. One stroke does the work of hundreds of helper-steps.

The press has rules. It only accepts trays of certain shapes. It is fastest with small, light bowls (short number formats), though it keeps the running pots in large ones. And it does nothing at all if you hand it single bowls one at a time: the helper who keeps mixing by hand, however hard he works, never touches the press.

NVIDIA calls these presses tensor cores, AMD matrix cores. This chapter finds them in real machine code (HMMA, v_mfma), explains why they multiply in short formats and add in long ones, and shows what happens when a matrix multiply never reaches them.

What you will be able to do

  • Describe what a matrix unit computes (D = A × B + C on small tiles) and how a warp or wavefront cooperates to feed it.
  • Recognise matrix instructions in PTX, SASS and AMD assembly, and count the multiply-adds per instruction from its shape.
  • Explain mixed precision: short input formats, long accumulators, and what goes wrong with short accumulators.
  • Check whether a given kernel uses the matrix units, from its machine code alone.
  • Name which targets have the units, using compiler evidence rather than memory.
Jargon box
Tensor Core / Matrix Core
Simple words: a special part of the GPU that multiplies small blocks of numbers in one go. Analogy: the press that mixes a whole tray in one stroke. Precise: a functional unit in the SM (NVIDIA: tensor core) or CU (AMD CDNA: matrix core) that executes a matrix multiply-accumulate on small tiles as one warp- or wavefront-wide instruction. Available only on some targets: the AMD compiler refused the MFMA builtin for gfx1030 and gfx1100 ("needs target feature mai-insts"). D3 D6 R6
MMA (matrix multiply-accumulate)
Simple words: "multiply two blocks and add to a third". Analogy: one stroke of the press. Precise: D = A × B + C where A is m × k, B is k × n, and C and D are m × n; the shape is written mMnNkK (PTX) or MxNxK (AMD). One MMA performs M·N·K multiply-adds. D4 D6
MFMA / WMMA
Simple words: the names of the matrix instructions and programming interfaces. Analogy: the press's operating handles. Precise: WMMA ("warp matrix multiply-accumulate") is the CUDA C++ API in mma.h (namespace nvcuda::wmma) and the PTX instruction family wmma.*; MFMA ("matrix fused multiply-add") is the AMD CDNA instruction family (v_mfma_*), reachable from HIP through compiler builtins. (AMD RDNA 3 also has instructions named WMMA, not used here.) H1 R2 R5
Fragment
Simple words: the piece of a matrix tile that one thread holds in its registers. Analogy: the bowls each helper carries to the press. Precise: in WMMA, an opaque per-thread object holding part of a tile; its layout across the warp's lanes is unspecified by the API, so it must be loaded and stored with the *_sync functions. D3
Mixed precision
Simple words: multiplying with short numbers but adding up with long ones. Analogy: light bowls in, large pots for the running total. Precise: inputs in a short format (FP16, BF16, or shorter), products and sums accumulated in a longer format (FP32), as in the WMMA fragment types of Listing 1 (half inputs, float accumulator) and the PTX .f32.f32 suffix. D3 R2
FP16 / BF16
Simple words: two 16-bit number formats: FP16 keeps more digits, BF16 a wider range. Analogy: two kinds of small bowl: one with finer markings, one that holds more extreme amounts. Precise: IEEE 754 binary16 has an 11-bit significand (10 stored) and 5 exponent bits; bfloat16 has an 8-bit significand (7 stored) and FP32's 8 exponent bits. D7 D1

The idea in pictures

Layer 1 — the kid explanation

Many of the most important GPU programs, especially in machine learning, spend most of their time multiplying big tables of numbers. Multiplying tables means doing "multiply two numbers and add to a total" again and again, millions of times.

So GPU makers added a special machine that does a whole small block of those steps at once. It is like a cookie cutter that cuts a whole tray instead of one cookie at a time. You only get the speed if you hand it whole trays in the right shape; one cookie at a time, it is not used at all.

The machine works with small, short numbers to go fast, but keeps the running totals in big, careful numbers, so that adding millions of small things does not go wrong.

Layer 2 — the student explanation

What a matrix instruction does

A matrix multiply C = A × B of large matrices splits into many tile products. A matrix unit computes one tile product plus accumulation, D = A × B + C, as a single instruction issued for a whole warp or wavefront. D3 D6 In Listing 1, one warp calls wmma::load_matrix_sync for A and B, wmma::mma_sync, and wmma::store_matrix_sync; all 32 lanes take part, each holding part of each tile (a fragment). In PTX this is wmma.mma.sync.aligned.row.col.m16n16k16.f32.f32; in sm_80 SASS it became 8 loads (LDG.E, two tiles' worth of fragments) and two HMMA.16816.F32 instructions. R2 R3

Counting the work

A 16 × 16 × 16 tile product is 4,096 multiply-adds. The same kernel compiled for older targets used more, smaller instructions: 16 HMMA.884 on sm_70 (8 × 8 × 4 = 256 each), 4 HMMA.1688 on sm_75 (16 × 8 × 8 = 1,024 each), and 2 HMMA.16816 on sm_80, sm_86 and sm_90 (2,048 each): every row multiplies out to 4,096 (Figure 2, R4). R4 For comparison, an ordinary FP32 fused multiply-add (FFMA) does one multiply-add per lane, 32 per warp instruction (F1-57). D5

On AMD, Listing 2 calls __builtin_amdgcn_mfma_f32_16x16x4f32; for gfx90a the compiler emitted v_mfma_f32_16x16x4f32 v[2:5], v2, v3, 0: each of the 64 lanes supplies one element of A and one of B (64 = 16 × 4 each) and receives 4 results in v[2:5] (64 × 4 = 256 = 16 × 16), for 16 × 16 × 4 = 1,024 multiply-adds in one instruction. R5 For gfx942 the same builtin produced v_mfma_f32_16x16x4_f32 (a renamed mnemonic); for gfx1030 and gfx1100 the compiler refused it: "needs target feature mai-insts". R6

Why short inputs and long accumulators

Short formats move fewer bytes and need smaller multipliers, which is where matrix units get their throughput. D1 But sums of many products need precision. Listing 3 models rounding: adding 4,096 ones in FP16 gives 2,048.0, because above 2,048 the spacing of FP16 numbers is 2 and adding 1 rounds back down; in FP32 it gives 4,096.0. For 4,096 random products, accumulating in FP16 gives a relative error of 7.00e-02; accumulating the same FP16 inputs in FP32 gives 4.21e-08; BF16 inputs with FP32 accumulation give 7.77e-05, because BF16 keeps fewer significand bits (R1). R1 That is why the WMMA fragment in Listing 1 is half for A and B but float for the accumulator.

Layer 3 — the engineer's depth

The analogy in one line: the press is only useful if trays arrive at its pace, and keeping it fed is a memory and scheduling problem (F1-58 to F1-60), not an arithmetic one.

Feeding the units

Each HMMA.16816.F32 in Listing 1 reads its A and B fragments from registers, here loaded directly from global memory (LDG.E, R3). A real matrix multiply loads tiles into shared memory or LDS once and reuses each element many times (F1-58), keeps several tiles in flight (F1-60), and arranges the data so that fragment loads avoid bank conflicts. D1 The higher a unit's arithmetic rate, the more reuse is needed to avoid being limited by memory bandwidth (F1-59); this is the arithmetic-intensity argument of the roofline model (F6-09). Libraries (cuBLAS, rocBLAS, CUTLASS, Composable Kernel) exist because this staging is hard to get right.

AMD specifics in the evidence

The gfx90a code shows two details. First, after v_mfma_f32_16x16x4f32 the compiler inserted s_nop 7 and s_nop 2 before the store reads the result registers: the instruction's result is not available in the next cycle, and in this case the compiler, not hardware interlocks, enforced the wait. Second, the kernel descriptor has .amdhsa_accum_offset 8, a field about accumulation registers (AGPRs) that gfx90a provides for matrix results. R5 D6 D8

Not verified — check before relying on this

From memory, not checked in this build: that s_nop N waits N + 1 cycles and that MFMA results require a documented number of wait states; that gfx90a has a unified register file split between architectural VGPRs and accumulation registers at accum_offset; that SASS HMMA.884 on sm_70 operates per pairs of quads of a warp in four steps; the exact shapes behind the SASS names (the m×n×k reading in this chapter is an interpretation that makes the counts consistent); the input and accumulator formats supported per generation (TF32, FP8 and others). Check: the AMD Instinct MI200 ISA reference guide (MFMA and dependency/wait-state sections), the LLVM AMDGPU backend user guide (kernel descriptor), the PTX ISA (warp-level matrix instructions), and the named product's whitepaper.

The compiler does not find matrix units for you

A loop of scalar multiply-adds is compiled to scalar FMA instructions. In the forensic evidence, a plain FP32 matrix multiply compiled for sm_80 contains 29 FFMA and no HMMA; Listing 1's kernel contains 2 HMMA.16816.F32 (R7). Matrix units are reached through explicit interfaces (WMMA or the PTX mma family, AMD builtins, or libraries). R7 D3 Whether a library uses matrix units for FP32 inputs (for example through a reduced-precision mode) is a library setting; check its documentation and its effect on accuracy.

How the hardware actually does it

A matrix unit is a block of many multipliers and adders arranged so that one instruction's operands, read from the register files of a warp's lanes, are combined in a fixed dataflow and the results written back to the lanes' registers. D1 D2 The warp scheduler issues the matrix instruction like any other (F1-60); the instruction occupies the unit for several cycles, and dependent instructions must wait for its result, either by hardware tracking or, as the gfx90a code shows, by compiler-inserted waits (R5). R5 Because the fragment layout spreads each tile across all lanes, matrix instructions require the whole warp or wavefront to participate (the .sync.aligned qualifiers in PTX). R2 D4 Short-format multipliers are much smaller than FP32 or FP64 ones, so more of them fit in the same area and energy budget, which is the design reason for mixed precision. D1

Worked example

Task. A layer of a neural network multiplies a 4,096 × 4,096 matrix by a 4,096 × 4,096 matrix. (a) How many multiply-adds? (b) How many HMMA.16816 instructions (m16n8k16) would cover them, and how many warp-level FFMA instructions instead? (c) How many v_mfma_f32_16x16x4f32?

  1. (a) M·N·K = 4,0963 = 236 = 68,719,476,736 multiply-adds.
  2. (b) Each HMMA.16816 does 16 × 8 × 16 = 2,048 = 211: 236 / 211 = 225 = 33,554,432 instructions. Each warp-level FFMA does 32 = 25: 231 = 2,147,483,648 instructions, 64 times as many issue slots.
  3. (c) Each does 16 × 16 × 4 = 1,024 = 210: 226 = 67,108,864 instructions.

Instruction counts are not times: how many cycles each instruction occupies its unit, and how many units an SM or CU has, are product facts from the vendor's documentation, which this chapter does not quote (F1-63). The counts show why issue bandwidth alone would make scalar FMAs the bottleneck. R4 R5

Where the analogy breaks


    

  • The press does not sit beside the helpers. The matrix unit reads the warp's registers directly; there is no "carrying the tray over" step beyond loading the fragments into registers. R3
    • 

  • Light bowls differ in more than weight. Short formats also have smaller ranges and coarser steps; the analogy hides the numerical risk that Listing 3 shows. R1
    • 

  • One press per section is a simplification. How many matrix units an SM or CU has, and how they are shared among warps, is product-specific (F1-63).
    • 




Common mistakes and debugging


    

  • Symptom: a "tensor-core" kernel is no faster than before. Cause: the code never reaches the matrix units (plain loops; wrong types; library mode off). How to find it: look for HMMA/v_mfma in the machine code (forensic lab) or the profiler's tensor-pipe utilisation. Fix: use WMMA, MMA instructions, builtins or a library configured for them.
    • 

  • Symptom: a WMMA kernel traps or fails to compile. Cause: built for a target without tensor cores (the runner's default target in this build). How to find it: check -arch. Fix: build for the GPU's target.
    • 

  • Symptom: large sums lose accuracy or saturate. Cause: FP16 accumulation. How to find it: compare with an FP32 or FP64 reference (Listing 3). Fix: FP32 accumulator fragments.
    • 

  • Symptom: wrong results with hand-indexed fragments. Cause: assuming a lane-to-element layout. Fix: use the load/store functions, or the documented layout of the exact instruction.
    • 




Transition box

Where you came from: F1-57, where every lane executed its own scalar instruction, and F1-60's scheduler. What carries over: warps and wavefronts, registers, issue slots, and the need to keep units fed. What changes: one instruction now spans the whole warp's data as a matrix: lanes cooperate on one result instead of computing independent ones (2 HMMA.16816 for a 16 × 16 × 16 tile, R3; one v_mfma for 1,024 multiply-adds, R5), and numerical format becomes a design choice.
