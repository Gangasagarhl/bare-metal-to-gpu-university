Story hook

Every helper in the banquet hall has a small tray on the bench in front of them: the tray holds what that helper is working on right now, and nobody else can reach it. Each section of the hall also has one shared side table, where the helpers of one team can put ingredients for each other. Further away is the hall's pantry, and much further away, across the yard, the warehouse.

Lena's team chops vegetables. One evening the head chef says: "Use smaller trays, then I can fit more helpers in the section." The trays get smaller. Each helper can no longer keep all the pieces they need in front of them, so they walk to the pantry shelf to park pieces and walk back to fetch them, again and again. There are more helpers in the section, and the vegetables come out slower.

The trays are the registers, the side table is shared memory (NVIDIA) or the LDS (AMD), the pantry shelves are the caches, and the warehouse is the GPU's main memory. This chapter is about how big each one is, who can reach it, and why making one smaller can make the whole kitchen slower.

What you will be able to do

  • Describe the on-chip storage of an SM or CU: register file, shared memory or LDS, L1 and constant caches, and the L2 behind them, with the scope (thread, block, device) of each.
  • Read a kernel's resource use from compiler output: registers, shared memory, spills (ptxas) and the AMD kernel metadata.
  • Compute occupancy from the per-SM limits and a kernel's resource use, and name the limiting resource.
  • Predict shared-memory bank conflicts for an access pattern and remove them by padding.
  • Diagnose a slowdown caused by register spills.
Jargon box
Register file
Simple words: the fastest storage on the GPU, split up so each thread gets its own few boxes. Analogy: each helper's tray. Precise: the per-SM (per-CU) array of 32-bit registers, divided among resident threads; a kernel's register count per thread is fixed at compile time and multiplied by the threads resident. The CUDA runtime reports it as regsPerMultiprocessor ("32-bit registers available per multiprocessor"). H1 D1
Shared memory / LDS
Simple words: a small, fast memory that the threads of one block share and manage themselves. Analogy: the team's side table. Precise: on-chip memory allocated per block, declared __shared__ in CUDA and HIP; AMD calls it the local data share (LDS). Its size per block appears as "smem" in the ptxas report and as .group_segment_fixed_size in AMD metadata. D3 D7 R2 R4
Bank conflict
Simple words: when several threads want different words from the same part of shared memory at once, so they must wait in line. Analogy: two helpers reaching into the same drawer of the side table for different things. Precise: shared memory is divided into banks that each serve one word per cycle; when the threads of a warp access different words in one bank, the access is split into as many passes as the largest number of distinct words in any bank (the conflict degree). D3 D1
Occupancy
Simple words: how full the SM is with warps, compared with how many it could hold. Analogy: how many helpers are in the section, out of the places available. Precise: resident warps per SM ÷ maximum resident warps per SM; limited by registers, shared memory, the warp limit and the block limit, whichever allows the fewest blocks. D1 D3
Spill / local memory
Simple words: when a thread runs out of registers, the compiler parks values in memory and fetches them back later. Analogy: walking to the pantry shelf to park pieces that do not fit on the tray. Precise: per-thread "local" memory is private in scope but lives in device memory, cached on the way; ptxas reports "spill stores" and "spill loads" in bytes, and SASS uses STL/LDL. D3 R5
L1 / L2 cache
Simple words: automatic copies of recently used memory, near the SM (L1) and shared by the whole GPU (L2). Analogy: the pantry shelves of one section, and the hall's central pantry. Precise: hardware-managed caches between the SMs and device memory; the L1 is per SM (on many NVIDIA designs it shares storage with shared memory), the L2 is shared by all SMs; the CUDA runtime reports l2CacheSize ("Size of L2 cache in bytes"). H1 D2
Barrier (__syncthreads)
Simple words: a "wait here until everyone in the block arrives" point. Analogy: the team waits until all ingredients are on the side table. Precise: a block-wide execution and memory barrier; BAR.SYNC in SASS and s_barrier on AMD (R3, R4). R3 R4

The idea in pictures

Layer 1 — the kid explanation

A GPU has several kinds of storage, like a kitchen has several kinds of places to put food. Each thread has its own tiny tray: very fast, but nobody else can see it. Each team of threads has a shared table: fast, and the team can pass things to each other there. Then there are shelves that fill themselves with things used recently. And far away is the big warehouse, which holds everything but takes a long walk.

The trays and tables are in the section, and the section has only so much room. If every helper wants a big tray, fewer helpers fit. If a team wants a big table, fewer teams fit. Choosing sizes is a balance between "more helpers" and "enough room for each helper".

Layer 2 — the student explanation

Registers: private and fixed per kernel

The compiler decides how many registers each thread of a kernel uses, and the whole kernel launch uses that number. For the transpose of Listing 1, ptxas reported Used 12 registers, 4224 bytes smem for sm_80; the gfx90a compiler reported .vgpr_count: 6 and .sgpr_count: 16 for the HIP version (AMD splits registers into per-lane vector registers and per-wavefront scalar registers, F1-56). R2 R4 Registers come from a fixed per-SM pool; every resident thread takes its count from that pool. H1 D1

Shared memory and LDS: a scratchpad you manage

Shared memory is allocated per block and is visible to all threads of that block, for the lifetime of the block. D3 Unlike a cache, nothing moves into it by itself: the kernel writes it, synchronises, and reads it. Listing 1 shows the standard use: each thread reads one element of a row of the input (neighbouring threads, neighbouring addresses, F1-59's coalescing), stores it in the tile, waits at __syncthreads(), and then reads a column of the tile so that the write to the output is again along a row. The tile is float tile[32][33]: 32 × 33 × 4 = 4,224 bytes, exactly the "4224 bytes smem" of ptxas and the .group_segment_fixed_size: 4224 of the AMD metadata. R2 R4

Banks

Shared memory serves many threads per cycle by being split into banks; successive 4-byte words go to successive banks. D3 In the model of Listing 3 (32 banks of 4 bytes), reading a row of the tile is conflict-free for any pitch, but reading a column with a pitch of 32 words puts every thread's word in the same bank: degree 32. A pitch of 33 shifts each row by one bank, and the column read becomes conflict-free (degree 1); the same holds for 64 versus 65 (R6). That is the reason for the "+ 1". R6

Occupancy

An SM can keep a block resident only if all of its resources fit at once: registers (registers per thread × threads), shared memory, a warp slot for each warp and a block slot. D1 D3 Listing 4 does the arithmetic for TG-1, the invented teaching GPU of this course (16,384 registers, 32 KiB shared memory, 16 warps and 4 blocks per SM). A kernel with 64 registers per thread and 128-thread blocks: 64 × 128 = 8,192 registers per block, so 2 blocks fit, 8 warps of 16: occupancy 50 %, limited by registers. A kernel with 16 KiB of shared memory per block: 2 blocks, 50 %, limited by shared memory (R7). On a real GPU the same computation uses the numbers from the device query and the vendor's occupancy rules (allocation granularity, reserved shared memory per block, see reservedSharedMemPerBlock in the CUDA header). R7 H1

Note

TG-1 is invented. Its limits are chosen for easy arithmetic and are not the numbers of any real GPU. Replace them with your lab GPU's device-query values before drawing conclusions about it.

Layer 3 — the engineer's depth

The analogy in one line: tray size, side-table size and number of helpers are traded against each other by the head chef, who here is the compiler plus your launch configuration.

The register trade-off

More registers per thread let the compiler keep more values live (unrolled loops, many independent loads in flight, F1-55's instruction-level parallelism). Fewer registers per thread allow more resident warps (thread-level parallelism, F1-60). Both hide latency; neither is free. A cap set with -maxrregcount or __launch_bounds__ forces the compiler to fit, and when the live values do not fit it spills them to local memory. D3 In the forensic evidence, the same kernel compiled without a cap uses 40 registers and no spills; with -maxrregcount=16, ptxas reports 24 registers, a 352-byte stack frame, 416 bytes of spill stores and 572 bytes of spill loads per thread, and the SASS gains 245 local-memory instructions (LDL/STL) where it had none. R5

"Local" memory is not local

Per-thread local memory is private in scope, but it is stored in device memory and reaches the SM through the caches (the CUDA header even has a property localL1CacheSupported, "Device supports caching locals in L1"). H1 D3 Spills therefore cost memory bandwidth and latency when they miss in the cache. Dynamic indexing of a private array (acc[(k + r) % 32] where the compiler cannot resolve the index) can also force an array into local memory even without a register cap; full unrolling, as in pressure.cu, lets the compiler resolve the indices.

Barriers and the order of shared-memory accesses

The generated code makes the protocol visible. SASS for sm_80: @!P0 LDG.E (guarded global load), @!P0 STS (store to shared), BAR.SYNC 0x0, LDS (load from shared), STG.E (global store). R3 gfx90a: global_load_dword, ds_write_b32, s_barrier, ds_read_b32, global_store_dword; the ds_ prefix marks LDS instructions ("data share"). R4 D6 Without the barrier, a thread could read a tile element before the thread responsible for it has written it: a race that produces wrong answers only sometimes.

Shared memory and L1 sharing storage

On several NVIDIA generations the L1 cache and shared memory use one on-chip array whose split can be configured (the "carveout"), and kernels can opt in to more shared memory per block than the default (the header lists sharedMemPerBlockOptin, "Per device maximum shared memory per block usable by special opt in"). H1 D3

Not verified — check before relying on this

Hardware details stated from memory and not checked in this build: that NVIDIA shared memory has 32 banks of 4 bytes on current generations; that AMD's LDS on CDNA has 32 banks of 4 bytes; that the L1/shared array is unified and configurable on Volta and later; and the size of the AMD LDS per workgroup on gfx90a. The bank model of Listing 3 takes the bank count and width as parameters for this reason. Check: CUDA C++ Programming Guide, "Shared Memory" sections of the compute-capability appendix; the AMD Instinct MI200 ISA reference guide, chapter on the data share operations.

How the hardware actually does it

The register file is a large, banked SRAM inside each SM or CU, read every cycle by the arithmetic units; each resident warp owns a fixed range of it for its whole life, which is why switching between resident warps costs nothing (F1-60): nothing is saved or restored. D1 D2 Shared memory or LDS is a separate SRAM, split into banks so that one warp-wide access can complete in one pass when the addresses spread over the banks; a conflicting access is split into several passes. D3 The instructions that touch it are distinct from global-memory instructions (LDS/STS versus LDG/STG; ds_read/ds_write versus global_load/global_store), because the address spaces are different (R3, R4). R3 R4 The L1 caches global and local accesses per SM, and the L2, shared by all SMs, sits in front of the memory controllers (F1-59). D2 At launch, the block scheduler places a block on an SM only if all its registers, shared memory and warp slots are free there: the occupancy arithmetic of Listing 4 is the arithmetic of that check. D1

Worked example

Task. On TG-1 (invented: 16,384 registers, 32 KiB shared memory, 16 warps, 4 blocks per SM), a kernel uses 40 registers per thread, 6 KiB of shared memory per block and 128 threads per block. Find the resident blocks, the occupancy and the limiter. Then find the largest register count that reaches 100 % occupancy with this block size.

  1. Warps per block: 128 / 32 = 4.
  2. Registers: 40 × 128 = 5,120 per block; 16,384 / 5,120 = 3.2, so 3 blocks.
  3. Shared memory: 32,768 / 6,144 = 5.33, so 5 blocks.
  4. Warps: 16 / 4 = 4 blocks. Block limit: 4.
  5. Resident blocks = min(3, 5, 4, 4) = 3: 12 warps of 16, occupancy 75 %, limited by registers.
  6. 100 % needs 4 blocks = 512 threads: 16,384 / 512 = 32 registers per thread at most.

Check with the tool: add the line worked 40 6144 128 to occupancy.in and run Listing 4; it should print 3 blocks, 75.0 %, "regs". Whether 32 registers is faster than 40 depends on whether it causes spills (Layer 3), which only the compiler report and a measurement can tell. R7

Where the analogy breaks


    

  • A tray's size is decided before service. The register count is fixed at compile time for every thread of the kernel; a helper cannot borrow a bigger tray for one hard dish. D1
    • 

  • The side table has drawers. Banks have no kitchen equivalent that explains the "same drawer, different item" rule well; use Figure 2, not the analogy, to reason about conflicts.
    • 

  • The pantry shelf is in the warehouse. Spilled values go to "local" memory, which lives in device memory and is only cached nearby; the walk can be much longer than the story suggests. H1
    • 




Common mistakes and debugging


    

  • Symptom: a kernel gets slower after -maxrregcount or __launch_bounds__ raised its occupancy. Cause: spills. How to find it: -Xptxas -v spill bytes; LDL/STL in SASS; on AMD, scratch use in the kernel metadata. Fix: remove the cap, or reduce live values in the code.
    • 

  • Symptom: a shared-memory transpose is much slower than a copy. Cause: column reads with a pitch that is a multiple of the bank count. How to find it: the profiler's shared-memory bank-conflict counters, or Listing 3. Fix: pad by one element.
    • 

  • Symptom: results wrong only sometimes. Cause: a missing __syncthreads() between writing and reading shared memory, or a barrier inside a branch that not all threads reach. How to find it: Compute Sanitizer racecheck and synccheck (F6-05). Fix: a barrier on every path, outside divergent code.
    • 

  • Symptom: a launch fails with "too many resources requested". Cause: registers × threads per block exceed what one SM provides for a block. How to find it: compare with regsPerBlock from the device query. Fix: smaller blocks, or fewer registers.
    • 




Transition box

Where you came from: HW203's CPU memory hierarchy, where caches were automatic and registers were few and named in the ISA; F1-57's warps. What carries over: locality, the latency gap between levels, and the idea that the fastest storage is the smallest. What changes: GPU registers are a large shared pool divided among thousands of threads, so their count per thread limits how many threads run; shared memory/LDS is a cache-sized scratchpad that you fill and synchronise; and the compiler reports the price of each kernel (12 registers and 4,224 bytes for the transpose, R2). Summary


    

  • Registers are private and fast; their count per thread is fixed at compile time and limits how many threads fit.
    • 

  • Shared memory/LDS is a per-block scratchpad that the kernel fills, synchronises and reads; it is split into banks.
    • 

  • Column reads of a tile with pitch equal to the bank count conflict; padding by one word removes the conflict (in the 32 × 4-byte model).
    • 

  • Occupancy = resident warps ÷ maximum; the scarcest of registers, shared memory, warp and block slots decides it.
    • 

  • A register cap can cause spills to "local" memory, which lives in device memory: more occupancy, more traffic, possibly slower.
    • 

  • ptxas -v, SASS and the AMD metadata tell you a kernel's real resource use without a GPU.
    •

Forensic lab answer key


Observation. Build A: 40 registers, 0-byte stack frame, no spills, 0 local-memory instructions. Build B: 24 registers (above the cap of 16, see the unverified box), 352-byte stack frame, 416 bytes of spill stores and 572 bytes of spill loads per thread, 245 local-memory instructions.


Root cause. Lines 13–17 load 32 values into acc, and lines 19–25 read all of them repeatedly, so about 32 values plus s and the indices must be alive at once. Under the cap they cannot all be registers, so the compiler parks them in local memory, which is in device memory: that is the extra memory traffic. The higher occupancy does not compensate, because every warp now waits on more memory operations.


Wrong answers and why. "The inputs changed": the kernel and its launch are identical between builds; only the flag differs. "Cache thrashing from more warps": possible as a secondary effect, but the evidence shows a direct cause (spill instructions) that must be removed first.


Fix. Build: remove the cap, or set it no lower than the spill-free count (40 here). Code: reduce live values, for example by evaluating the polynomial in a loop that loads coefficients from shared memory instead of keeping 32 in registers.


How the evidence was produced. The Lab Engineer compiled pressure.cu twice with ptxas reporting enabled and counted LDL/STL in the SASS (commands in run.sh). The slowdown itself is part of the scenario and was not measured (no GPU). Prevention: a CI step that fails when ptxas reports non-zero spill bytes for kernels marked as performance-critical.
