Story hook

The banquet hall from F1-55 is not one big room. When Wei, the new floor manager, walks through it for the first time, she counts identical sections. Each section has its own long table, its own racks of bowls and its own supervisor who calls out the next step of the recipe card to the rows of helpers standing there. The sections do not share tables. A section can host a few groups of guests' orders at a time, and when one group's order is done, the next waiting order is sent to whichever section has room.

"How many sections are there?" Wei asks. Nobody on the floor knows for sure; one helper thinks forty, another says "more than last year's hall". Wei goes to the office, takes the building plan out of the drawer and counts. Then, to be safe, she asks the front desk, which keeps a list of every section that is open today. The two numbers agree, and she writes both sources next to the number in her notebook.

The sections are what NVIDIA calls streaming multiprocessors and AMD calls compute units. This chapter is about what is inside one, how the work of a launch is spread over them, and how to ask a real GPU how many it has, with a source for every number.

What you will be able to do

  • Explain what an SM (NVIDIA) and a CU (AMD) contain and why GPUs are built from many copies of them.
  • Describe how the blocks (workgroups) of one launch are assigned to SMs and stay there until they finish.
  • Compute the number of waves of a launch and the share of the GPU left idle in the last wave.
  • Query a GPU's SM or CU count and related limits with the CUDA runtime, the HIP runtime and rocminfo, and record where each number came from.
  • Diagnose a launch that leaves SMs idle because it has too few blocks.
Jargon box
SM (streaming multiprocessor)
Simple words: one of the identical building blocks of an NVIDIA GPU that runs threads. Analogy: one section of the banquet hall with its own table, racks and supervisor. Precise: NVIDIA's replicated processor unit; thread blocks are scheduled onto SMs, and each SM holds the registers, on-chip memory and schedulers for the warps resident on it. The CUDA runtime reports the count as multiProcessorCount, "Number of multiprocessors on device". D3 H1
Compute Unit (CU)
Simple words: AMD's name for the same kind of building block. Analogy: a section of the hall in AMD's building. Precise: AMD's replicated processor unit, which runs the wavefronts of the workgroups assigned to it, with vector and scalar execution resources, a register file and the LDS; HIP reports the count as multiProcessorCount, which the HIP header describes as "Number of multi-processors (compute units)". D6 H2
Thread block / workgroup
Simple words: a team of GPU threads that always runs together on one SM or CU. Analogy: one group of guests' orders handled at one section. Precise: the group of threads of a launch that is scheduled as a unit onto one SM (CUDA "thread block") or CU (AMD "workgroup"), can share on-chip memory and synchronise at barriers, and stays on that unit until all its threads finish. D3 D8
Resident
Simple words: already sitting on an SM with everything it needs, ready to run. Analogy: an order whose helpers are standing at the section's table. Precise: a block or warp whose registers and on-chip memory are allocated on an SM, so the SM's schedulers can issue its instructions without any switching cost; limits are reported as, for example, maxBlocksPerMultiProcessor and maxThreadsPerMultiProcessor. D3 H1
Wave (of a launch)
Simple words: one round in which every free place on every SM gets a block. Analogy: one round of seating, when every section's table is filled once. Precise: the set of blocks that can be resident at the same time across the whole GPU (number of SMs × resident blocks per SM); a launch with more blocks runs in several waves, and a partly filled last wave is the "tail". Not to be confused with an AMD wavefront. D1
Compute capability / gfx target
Simple words: the name of a GPU's generation that compilers use. Analogy: the edition number printed on the building plan. Precise: NVIDIA identifies a GPU's feature set by a compute capability (major.minor, reported by cudaDeviceProp::major and minor; compiler targets sm_XY and compute_XY); AMD identifies the instruction set by a gfx target name such as gfx90a, reported in gcnArchName. H1 H2 R4
Scalar and vector registers (AMD)
Simple words: AMD keeps values that are the same for a whole wavefront in one place and per-thread values in another. Analogy: one note on the section's board for the whole row, versus each helper's own hands. Precise: on AMD GCN/CDNA targets, scalar registers (SGPRs) hold one value per wavefront and are used by scalar (s_) instructions; vector registers (VGPRs) hold one value per lane and are used by vector (v_) instructions; kernel metadata reports .sgpr_count and .vgpr_count. D6 D7 R5

Layer 1 — the kid explanation

A GPU is made of many copies of one small machine. NVIDIA calls the small machine an SM; AMD calls it a CU. Each copy has its own table (fast memory), its own racks (registers) and its own supervisors (schedulers). Building a GPU this way is like building a big hall out of identical sections: to make a bigger GPU, you add sections.

When a program starts work on the GPU, the work is cut into teams called blocks. Each team goes to one section and stays there until it is done. A section can host only a few teams at once. If there are more teams than places, the rest wait at the door and go in as soon as a team leaves.

If a program sends fewer teams than there are sections, some sections stand empty. The hall is big, but most of it does nothing. That is the mistake in this chapter's forensic lab.

Layer 2 — the student explanation

Inside one SM or CU

The analogy first: a section has helpers, a supervisor who reads the card aloud, private racks for each helper, and a shared table. In hardware terms, an SM or CU contains: an instruction cache and fetch logic; one or more schedulers that each cycle choose a warp (or wavefront) whose next instruction can issue; a large register file holding the private registers of every resident thread; arithmetic lanes for integer and floating-point work, special-function units, and on recent generations matrix units; load/store units; and an on-chip memory used as shared memory (NVIDIA) or LDS (AMD) and, in some generations, also as L1 cache. D1 D3 D6 Everything outside the SM, the L2 cache and the GPU memory, is shared by all SMs (F1-58, F1-59).

The same structure appears in AMD's real machine code. The gfx90a assembly of F1-57's kernel (reproduced in the Worked example below, R5) has two families of instructions: s_ instructions such as s_load_dword and s_mul_i32, which compute one value for the whole wavefront in scalar registers, and v_ instructions such as v_add_u32_e32, which compute one value per lane in vector registers. The kernel's metadata reports how many of each it uses (.sgpr_count: 13, .vgpr_count: 4). R5 D7 The block index, which is the same for every lane, is computed with scalar instructions; the thread index, which differs per lane, with vector instructions.

How a launch is spread over SMs

A kernel launch creates a grid of blocks. The hardware assigns whole blocks to SMs; all threads of a block run on the same SM, and a block stays there until all its threads have finished; it never migrates. D3 D1 An SM can hold several blocks at once, as many as its resources allow: registers, shared memory, a maximum number of resident threads and a maximum number of resident blocks (the arithmetic is in F1-58). Blocks that do not fit wait and are assigned as earlier blocks finish. The programming model promises no order and no co-residency between blocks: your code must not assume block 7 runs after block 3, or at the same time as it. D3

This is why a GPU program scales across products: the same launch runs on a GPU with few SMs in many waves and on a GPU with many SMs in fewer waves. It is also why a launch with too few blocks wastes a large GPU: blocks are the unit of distribution, so a grid of four blocks can occupy at most four SMs, however many the GPU has. D1

Asking the GPU

The CUDA runtime fills a cudaDeviceProp structure for each device. The installed CUDA 12.0 header documents its fields; among them multiProcessorCount ("Number of multiprocessors on device"), warpSize ("Warp size in threads"), maxThreadsPerMultiProcessor, maxBlocksPerMultiProcessor, regsPerMultiprocessor ("32-bit registers available per multiprocessor"), sharedMemPerMultiprocessor, l2CacheSize, totalGlobalMem and memoryBusWidth. H1 HIP's hipDeviceProp_t uses many of the same names and adds gcnArchName ("AMD GCN Arch Name"). H2 AMD's command-line tool rocminfo prints a report of every agent (CPU and GPU) the ROCm runtime sees. Listings 1 and 2 are our own small device queries; the curriculum's milestone E1 asks that your own report match the vendor tools. C1

In this build there was no GPU, so every query ended at its first call, and the recorded outputs are the tools' own error messages (R1, R2, R4). That is still useful: it shows you exactly what "no device" looks like, so that you never mistake it for a zero.

Layer 3 — the engineer's depth

One analogy sentence: the hall's sections are grouped into wings, and wings into the building. Then the details, each to be confirmed in the named product's documentation.

  • Groupings above the SM. Vendor documents describe SMs grouped into larger clusters (NVIDIA whitepapers describe graphics processing clusters; AMD documents describe shader engines, and on RDNA, workgroup processors that pair two CUs). C1 These groupings matter for features such as thread-block clusters and for how the L2 cache is partitioned, but the programming model of this course only sees SMs and blocks.
  • Partitions inside the SM. Recent NVIDIA SMs are described as divided into several processing blocks, each with its own scheduler, register file slice and lanes; AMD's GCN and CDNA CUs as several SIMD units, each executing a wavefront over several cycles. D1 D6 The counts are generation-specific and belong in an unverified box until read in the documents (see below).
  • Scalar unit. AMD's CU has a scalar unit that executes instructions once per wavefront (uniform values, branch conditions, loads of kernel arguments); NVIDIA SASS has uniform registers and instructions with a similar role on recent generations (the ULDC instruction in this build's sm_80 SASS loads into uniform registers UR4). R5 R6 D5
  • Generation names. The compiler names generations, not products: nvcc --list-gpu-arch in this build listed the virtual architectures compute_50 to compute_90 (R4), and the AMD compiler takes gfx target names such as gfx90a. Which product has which compute capability or gfx target is stated in the vendor's documentation, not in the compiler. R4 D7
  • What the query cannot tell you. The runtime reports counts and limits; it does not report the number of lanes per SM, the scheduler count, the matrix-unit generation or peak throughput. Those come from the architecture whitepaper and tuning guide of the named product (F1-63), and the device query becomes the cross-check that you are reading the right document for the GPU in front of you.
Not verified — check before relying on this

The internal partitioning described above (the number of processing blocks and schedulers per NVIDIA SM; four SIMD units per GCN/CDNA CU, each running a 64-lane wavefront over several cycles; two CUs per RDNA workgroup processor) was written from memory and could not be checked in this build. Check: the CUDA Programming Guide section on hardware implementation and the architecture whitepaper of the named NVIDIA GPU; the "AMD Instinct MI200" ISA reference guide and CDNA 2 whitepaper (chapter on the compute unit); the RDNA ISA guide for Radeon products. How the hardware actually does it

A hardware block scheduler (the documents give it different names) keeps a list of the launch's blocks that have not started. When an SM has enough free registers, shared memory, thread slots and block slots for one more block, the scheduler assigns the next block there: the SM allocates the block's registers and shared memory, initialises the built-in index registers of each thread (the S2R R0, SR_CTAID.X and S2R R3, SR_TID.X instructions in this build's sm_80 SASS read the block index and thread index from special registers), and its warps become eligible for issue. D1 D3 R6 On AMD hardware the workgroup id arrives in a scalar register and the lane's work-item id in a vector register; the kernel descriptor tells the hardware which ones to set up (.amdhsa_system_sgpr_workgroup_id_x 1, .amdhsa_system_vgpr_workitem_id 0 in the assembly this build produced). R5 D7 When the last warp of the block exits, the resources are freed and the next block can start. There is no preemption in this simple picture and no migration; the SM count you query is the number of such independent engines working on your grid.

Worked example

Task 1 (waves). TG-1 (invented) has 4 SMs and a kernel of which 2 blocks fit on one SM. How many waves do launches of 8, 9, 16, 100 and 1,000 blocks need, and how busy is the GPU if every block takes the same time?

  1. Slots = 4 × 2 = 8 blocks at once.
  2. 8 blocks: ceil(8/8) = 1 wave, 8 of 8 slot-rounds used: 100 %.
  3. 9 blocks: ceil(9/8) = 2 waves; the second wave runs 1 block on 1 slot while 7 slots idle; 9 of 16 slot-rounds: 56.2 %.
  4. 100 blocks: ceil(100/8) = 13 waves; the last holds 100 − 12 × 8 = 4 blocks; 100 of 104 slot-rounds: 96.2 %.
  5. 1,000 blocks: 125 waves exactly: 100 %.

Listing 3 computes the same table (output below, R3). The lesson: the tail matters most when the number of waves is small; launches with many blocks per slot make it negligible.

Task 2 (reading the AMD split). In the gfx90a assembly that this build produced for F1-57's kernel, the first instructions are s_load_dword s0, s[4:5], 0x4, s_mul_i32 s8, s8, s0 and v_add_u32_e32 v0, s8, v0. Reading them with the jargon box: the scalar unit loads the block size from the dispatch packet and multiplies it by the workgroup id held in a scalar register (one value for the whole wavefront); then a vector instruction adds the per-lane work-item id held in v0, producing each lane's own global index, the familiar blockIdx.x * blockDim.x + threadIdx.x. R5 The exact meaning of the registers s[4:5] and s8 at kernel entry is defined in the "User Guide for AMDGPU Backend" (kernel descriptor and initial register state), which must be checked before you rely on this reading. Where the analogy breaks


    

  • A section's supervisor does not choose which order comes in. In a restaurant the floor manager could send a big order to an empty section on purpose. The block scheduler's policy is the hardware's and is not documented as a fixed order; programs must not depend on which SM runs which block. D3
    • 

  • Sections can lend each other a table; SMs cannot. Shared memory and registers belong to one SM; a block cannot use another SM's shared memory in the programming model of this course (cluster features on recent NVIDIA GPUs relax this and are outside HW301). D3
    • 

  • A guest group may be split across sections; a block never is. All threads of a block are on one SM for their whole life. D3
    • 




Common mistakes and debugging


    

  • Symptom: a device query prints 0 devices and the program "works" with zeros. Cause: no GPU or no driver, unchecked. How to find it: check the return codes (Listings 1 and 2 print cudaErrorNoDevice / hipErrorNoDevice in this build). Fix: install the driver, check device visibility, and never ignore an error code.
    • 

  • Symptom: a large GPU is no faster than a small one. Cause: the grid has fewer blocks than the large GPU has slots. How to find it: compute waves with Listing 3 using your queried SM count. Fix: more, smaller blocks, or several independent problems per launch.
    • 

  • Symptom: a passport or report quotes an SM count that differs from the device query. Cause: a number from a different product variant, or from memory. How to find it: compare name and multiProcessorCount with the document's product name. Fix: tag every number with its document and section or with the query run (F1-63).
    • 

  • Symptom: code that assumes blocks run in order hangs or gives wrong results on another GPU. Cause: inter-block dependence. How to find it: look for a block waiting on a flag set by another block. Fix: split into two launches or use the documented grid-wide synchronisation features (F6).
    •

Summary


    

  • A GPU is built from many identical units: SMs (NVIDIA) or CUs (AMD).
    • 

  • Each contains schedulers, a large register file, arithmetic lanes, special-function and (on recent generations) matrix units, load/store units and shared memory/LDS with L1.
    • 

  • Whole blocks (workgroups) are assigned to SMs and stay until they finish; no order between blocks is promised.
    • 

  • A launch runs in waves of (SMs × resident blocks per SM); too few blocks leave SMs idle.
    • 

  • Query the counts with cudaGetDeviceProperties, hipGetDeviceProperties and rocminfo; tag every number with its source.
    • 

  • AMD code shows the CU's scalar/vector split directly: s_ instructions and SGPRs per wavefront, v_ instructions and VGPRs per lane.

Forensic lab answer key


Observation. 8 slots (4 SMs × 2). The night run has 4 blocks: 1 wave, 4 of 8 slots used, busy 50 % for the whole run; the day run has 32 blocks: 4 full waves, 100 %.


Root cause. Blocks are the unit of distribution. With 4 blocks, at most 4 of the 8 block slots ever hold work, so each SM holds one block instead of two: half the resident warps it could switch between, so it hides memory latency worse (F1-55, F1-60), and if the scheduler places them two to an SM, two SMs are entirely idle. In both cases the GPU does the same work with fewer warps in flight. Launch overhead is paid once per launch, not per block, so fewer blocks did not reduce it.


Wrong answers and why. "Bigger blocks are slower per row": the model shows the effect without any change in per-row cost; the evidence points at slots, not at per-row work. "Launch overhead": both versions use one launch.


Fix. Use at least as many blocks as slots, and preferably several waves: the day configuration (32 blocks, 4 waves) or smaller blocks still. On a GPU with 100 SMs, even 32 blocks would leave most SMs idle; derive the grid from the queried SM count (Listing 1) or make blocks small enough that the grid is large for any GPU.


How the evidence was produced. Real runs of Listing 3 on forensic.in; the machine is TG-1, the course's invented GPU, so the evidence is a model, not a profiler trace. Prevention: a review rule "grid size ≥ 4 × slots of the target GPU", or an assertion in the host code using the queried SM count.
