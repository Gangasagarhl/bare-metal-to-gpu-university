Story hook

A supervisor in the banquet hall runs four rows of helpers, and she has one voice: each moment she can call one step to one row. Row 0 asks the warehouse for flour; the flour will take a long time to arrive. A careless supervisor would stand and wait for row 0's flour. Ours turns to row 1 and calls its next step, then row 2, then row 3. When row 0's flour arrives, she goes back to row 0. As long as some row has a step it can do, her voice is never idle.

One week the hall's manager "simplifies" the work: instead of sixteen rows each doing sixteen dishes, four rows do sixty-four dishes each. The same number of dishes, the same supervisor. Service takes more than twice as long. Nobody is lazy; the supervisor runs out of rows to turn to while flour is on its way.

The supervisor is the warp scheduler, and turning to another row is latency hiding by switching warps. This chapter measures it in a model, shows the compiler's part of the job in real machine code, and explains the manager's mistake.

What you will be able to do

  • Explain how a warp scheduler hides latency by issuing from another ready warp, and why switching costs nothing.
  • Draw and read a warp execution timeline: issuing, stalling and switching.
  • Estimate with Little's law how much independent work must be in flight to cover a latency.
  • Distinguish the two sources of independent work: more warps (thread-level) and more independent instructions per warp (instruction-level, prefetching).
  • Find the compiler's waits for memory in real AMD and NVIDIA machine code.
Jargon box
Warp scheduler
Simple words: the part of an SM that picks, every cycle, which warp gets to do its next step. Analogy: the supervisor choosing a row. Precise: the issue logic that selects, among the resident warps assigned to it, one whose next instruction has its operands and resources ready, and issues it; an SM has one or more schedulers. D1 D3
Latency hiding
Simple words: doing other useful work while waiting, so the waiting does not cost time. Analogy: calling another row while the flour is on its way. Precise: overlapping the latency of an operation with the issue of independent instructions, from the same warp (ILP) or from other warps (TLP), so that the issue slots stay busy. D1 D2
Stall
Simple words: a warp that cannot take its next step yet. Analogy: a row whose next step needs flour that has not arrived. Precise: a warp is stalled when its next instruction depends on a result that is not ready (memory or arithmetic latency), or waits at a barrier or for a busy unit; profilers classify stall reasons. D3
Zero-cost switching
Simple words: moving from one warp to another takes no extra time. Analogy: each row keeps its own bowls on its own bench; nothing has to be packed away. Precise: every resident warp keeps its registers in the register file (F1-58), so the scheduler can issue from a different warp in the next cycle without saving or restoring state, unlike a CPU context switch. D1 D2
Little's law (for latency hiding)
Simple words: work in flight = rate × waiting time. Analogy: to serve one dish per minute when each needs ten minutes of waiting, ten dishes must be under way. Precise: L = λW; to sustain a throughput λ against a latency W, about λW independent operations must be in flight (F1-55). D4
s_waitcnt
Simple words: an AMD instruction that says "wait until at most N of my memory requests are still outstanding". Analogy: "wait until the flour is here before mixing". Precise: a scalar instruction on GCN/CDNA that stalls the wavefront until counters of outstanding operations (vmcnt for vector memory, lgkmcnt for scalar memory, LDS and others) fall to the given value; the compiler places it before the first use of loaded data. D6 R4

Layer 1 — the kid explanation

Fetching data from the GPU's big memory takes a long time, like waiting for a delivery. A GPU does not sit and wait. It keeps many groups of threads ready, and when one group is waiting for a delivery, it lets another group work.

If there are enough groups with work to do, the GPU is always busy, and the waiting does not slow anything down: it is hidden. If there are too few groups, there are moments when everybody is waiting, and the GPU sits idle.

There is a second trick: a single group can order several deliveries at once, before it needs the first one. Then, while it uses the first delivery, the next ones are already on their way.

Layer 2 — the student explanation

What the scheduler does each cycle

Each SM holds many resident warps (F1-58 computed how many). Every cycle, a scheduler looks at its warps, finds those whose next instruction can issue (its inputs are ready and its unit is free), picks one, and issues it. A warp whose next instruction needs data still on its way from memory is stalled; the scheduler skips it. D1 D3 Because each warp's registers stay in the register file, issuing from warp 3 right after warp 2 costs nothing extra. D2

Listing 1 models one scheduler: one instruction per cycle, warps picked round robin among the ready ones, loads that take mem cycles and dependent compute steps 4 cycles apart (an invented model latency). In Figure 1, the first four cycles issue one load from each warp; then all four are stalled on memory and the issue slot is empty until the data arrive; then the four warps' compute steps interleave perfectly, because each warp's 4-cycle compute latency is filled by the other three. R1

How many warps are enough? Little's law

To keep one instruction issuing every cycle, there must always be a warp with an instruction ready. If each load takes W cycles and each warp has c instructions of independent work per load, a rough estimate is that about W / c warps are needed to cover the wait, plus the issue time of the work itself. With W = 100 and c = 9 (one load, eight compute steps), that is more than 11 warps. D4 The model shows more: 16 warps reach only 63.2 % and 24 warps 74.0 % (R1). The reason is visible in the timelines: with round-robin issue, warps that start together stay together, so they all load at once, all wait at once and all compute at once. The waiting phases of different warps overlap instead of interleaving. Real schedulers and real programs break such convoys partly (different start times, different data); the model is a worst case, and a warning that "number of warps" alone is not the whole story. R1

The other source: loads in flight per warp

A warp can issue its next load before it uses the previous one, if the loads are independent. With ahead = 3, each warp in the model keeps up to four loads in flight; four such warps reach 87.3 % busy, more than twenty-four warps that load one at a time (74.0 %). R1 Compilers do this on their own when the code allows: in Listing 2's SASS the three loads (LDG.E at 00a0, 00c0, 00d0) are issued back to back and the multiply-add (FFMA at 00f0) comes after them; in Listing 3's gfx90a code the three global_load_dword instructions come first and a single s_waitcnt vmcnt(0) waits for all of them before v_fmac_f32. One wait covers three latencies. R3 R4

Note

The model's numbers are invented. Memory latency 100 cycles and compute latency 4 cycles are TG-1 model values chosen for readable arithmetic. They are not the latencies of any GPU; measuring real ones is the subject of microbenchmarks in F6-11.

Layer 3 — the engineer's depth

The analogy in one line: the supervisor (hardware) chooses which row goes next, but the order of steps inside each row's recipe (the compiler) decides how early each row can ask for flour.

Who tracks dependences

On AMD GCN and CDNA, dependence on memory is explicit in the instruction stream: memory instructions increment per-wavefront counters, and s_waitcnt stalls until a counter falls to a given value. D6 Listing 3's assembly shows two kinds: s_waitcnt lgkmcnt(0) after the scalar loads of the kernel arguments (s_load_dword, s_load_dwordx8), and s_waitcnt vmcnt(0) after the three vector loads. R4 A wavefront stalled at an s_waitcnt is exactly the "m" state of the model; the hardware then issues from other wavefronts. On NVIDIA, the SASS printed by cuobjdump shows no explicit wait instruction between the loads and the FFMA (R3); the dependence is tracked by scheduling information encoded with each instruction and by the hardware.

Read in the verification pass: the ISA guide's Table 2 defines the two counters seen in the assembly. VMCNT counts vector-memory instructions that have been issued but not completed; LGKMCNT counts LDS, GDS, constant-fetch and message instructions that have been issued but not completed (section 3.1). The CUDA Programming Guide says that the execution context of each warp "is maintained on-chip throughout the warp’s lifetime" so that "switching between warps incurs no cost" (3.2.2.2), and of the scheduler's choice only that "no ordering guarantees are made by the scheduler" (2.3.7). D6 D3

The occupancy–ILP trade-off

Loading ahead needs registers: every load in flight needs a destination register that stays allocated until the data are used. Registers per thread limit warps per SM (F1-58). So the two sources of independent work compete for the same register file: many warps with few registers each, or fewer warps with more registers and more loads in flight each. D1 Neither "maximise occupancy" nor "maximise ILP" is a rule; the requirement is enough independent work in flight, by Little's law, from either source. The forensic lab shows the consequence of reducing one source without adding the other.

Other stalls

Not every stall is memory. A warp waits at __syncthreads until its whole block arrives (F1-58); a long chain of dependent arithmetic stalls on arithmetic latency (the "a" state, F1-55's single chain); a busy special-function or memory unit stalls issue. Profilers report the fraction of each reason; the method is the same as here: find what the warps wait for, then supply more independent work of the right kind. D3

How the hardware actually does it

Each SM or CU is divided among one or more schedulers, each owning a set of resident warps. D1 Every cycle a scheduler checks, for each of its warps, whether the next instruction's source registers are ready and its execution unit can accept it; among eligible warps it selects one by a policy the vendor does not fully document, and sends the instruction to the unit with the warp's register-file addresses. D2 Loads leave the SM for the cache hierarchy and memory (F1-58, F1-59); the destination registers are marked pending until the data return. D2 On AMD the pending state is visible to software through the counters that s_waitcnt tests (R4). D6 R4 Since all resident warps' registers are on-chip all the time, "switching" means choosing a different warp's instruction in the next cycle; this is fine-grained multithreading, the design described for GPUs in D2. D2

Worked example

Task. In the model (1 issue per cycle, memory latency 100 cycles, compute latency 4), a kernel's warps each do 16 iterations of one load and 8 dependent compute steps. (a) How many cycles does one iteration take for a single warp? (b) What busy fraction does one warp reach? (c) Using Little's law, how many loads must be in flight to keep the issue slot full?

  1. (a) Load issues at cycle 0; data at 100; first compute at 100; the other 7 compute steps 4 cycles apart: the last at 128; the next load at 129. One iteration ≈ 129 cycles. Check: the model reports 2,064 cycles for 16 iterations = 129 each (R1).
  2. (b) 9 instructions per 129 cycles ≈ 7.0 % (R1 prints 7.0 %).
  3. (c) The slot must issue 1 instruction per cycle; each load supports 9 instructions (itself and its 8 compute steps), so loads must start at 1/9 per cycle; each stays in flight 100 cycles: L = λW = (1/9) × 100 ≈ 11 loads in flight at all times. From one load per warp (ahead 0) that needs at least 11–12 warps that do not all wait at once; from loading 3 ahead, 3–4 warps can do it, which is what the 87.3 % of w4_ahead3 reflects (the remainder is the start-up and drain). D4 R1

Where the analogy breaks


    

  • The supervisor does not decide by fairness or by urgency. The scheduler's policy is a hardware rule; vendors document it only partly. The model's round robin is one simple choice. D2
    • 

  • Rows cannot leave and come back. Resident warps stay resident until they finish; the scheduler can only choose among the warps already on the SM, not bring in new ones to fill a gap.
    • 

  • Flour does not get slower when everyone orders. Real memory latency grows when many requests compete for bandwidth (F1-59); the model's fixed 100 cycles ignores this.
    • 




Common mistakes and debugging


    

  • Symptom: a kernel slows down when work per thread is increased and the grid is shrunk. Cause: fewer resident warps and no extra independent loads per warp. How to find it: compare achieved occupancy and stall reasons before and after; or run the model (forensic lab). Fix: keep enough warps, or restructure the loop to issue several loads ahead.
    • 

  • Symptom: high occupancy, low throughput. Cause: all warps wait on the same thing (a barrier, a long dependent chain, or saturated bandwidth). How to find it: stall reasons in the profiler. Fix: depends on the reason: more ILP, fewer barriers, or fewer bytes.
    • 

  • Symptom: unrolling a loop made the kernel slower. Cause: more registers per thread reduced occupancy, or caused spills (F1-58). How to find it: -Xptxas -v, or the AMD metadata's .vgpr_count. Fix: a smaller unroll factor.
    • 

  • Symptom: a timing that ignores the first launch varies wildly. Cause: not a scheduler issue: launch and warm-up costs. Fix: warm up, repeat, report a spread (F6-11).
    •

Summary


    

  • The warp scheduler issues, each cycle, from any resident warp that is ready; switching costs nothing because registers stay on-chip.
    • 

  • Latency is hidden when enough independent work is in flight: Little's law, L = λW.
    • 

  • Independent work comes from more warps (TLP) and from more loads in flight per warp (ILP); they compete for registers.
    • 

  • In the model, 4 warps with 3 loads ahead (87.3 %) beat 24 warps with none (74.0 %).
    • 

  • Compilers issue independent loads before the first use: three LDG before FFMA; one s_waitcnt vmcnt(0) for three global_loads.
    • 

  • Fewer warps with more work each can be slower, unless each warp keeps more loads in flight.
    •

Forensic lab answer key


Observation. All three cases issue 2,304 instructions: the work is identical. Before: 3,648 cycles, 63.2 % busy, 1,344 idle cycles on memory. After: 8,448 cycles, 27.3 %, 6,144 idle on memory. Fixed: 2,388 cycles, 96.5 %, 84 idle.


Root cause. Latency is hidden by work in flight. Before, 16 warps each had one load in flight; after, only 4. With the same 100-cycle latency and the same work per load, Little's law needs about 11 loads in flight; 4 is far too few, so the issue slot sits idle on memory for most cycles (6,144 of 8,448). The number of instructions did not change, so "more work" is ruled out; launch overhead is not in the model at all, yet the model reproduces the slowdown.


Fix. Keep the 4 warps but restructure each warp's loop to issue loads 3 iterations ahead (prefetch into registers, or let the compiler do it by unrolling the loop with independent loads). Each warp then keeps 4 loads in flight: 16 in total, enough to cover the latency, which is why it beats the original 16 warps × 1 load in this model.
