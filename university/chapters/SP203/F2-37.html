Story hook

Analogy

Between the kitchen and the dining room there is the pass: a shelf where the chef puts finished plates and the waiters pick them up. It holds four plates. When it is empty, a waiter has nothing to carry; when it is full, the chef has nowhere to put the next plate.

At first the waiters walked to the pass every few seconds to look. They wore out the floor and still arrived late. So the restaurant installed a bell. When the chef puts a plate down, she rings it; waiters who were waiting nearby wake up and come. When a waiter takes a plate from a full pass, he rings a second bell for the chef.

The bell has two quirks you will meet in this chapter. A ring that nobody hears is gone: a waiter who arrives a moment later hears nothing, and must look at the pass to know there is a plate. And sometimes two waiters wake for one plate; one of them will find the pass empty again. Both quirks have the same cure: after the bell, look.

What you will be able to do

  • Make a thread wait until a condition about shared data is true, with std::condition_variable and a predicate.
  • Explain lost wake-ups and spurious wake-ups, and why a predicate loop handles both.
  • Build a bounded producer/consumer queue with shutdown, and pass the curriculum B10 acceptance test under ThreadSanitizer.
  • Measure throughput and waiting for different buffer sizes and thread counts.
  • Diagnose an if that should have been a while, from a log.
Jargon box
Condition variable
Simple words: something a thread can sleep on until another thread says "something changed". Analogy: the bell at the pass. Precise: a synchronisation object (std::condition_variable, header <condition_variable>) with wait, which atomically unlocks a std::unique_lock<std::mutex> and blocks, and relocks before returning; and notify_one/notify_all, which unblock waiting threads. It carries no state of its own. D1
Predicate (of a wait)
Simple words: the yes/no question the waiting thread really cares about, such as "is there a plate?". Analogy: looking at the pass after the bell. Precise: a callable returning bool, evaluated with the mutex held; cv.wait(lock, pred) is equivalent to while (!pred()) cv.wait(lock);. D1
Spurious wake-up
Simple words: a wait that returns although nobody notified, or although the condition is false again. Analogy: you hear a bell, but the plate is gone or there never was one. Precise: the standard allows wait to return without a corresponding notification; and between a notification and the waiter's relock, another thread may change the state. Both are handled by re-checking the predicate. D1
Lost wake-up
Simple words: a notification sent when nobody was waiting, so nobody gets it. Analogy: the bell rang before the waiter arrived. Precise: because a condition variable has no memory, a notify with no waiting thread has no effect; a thread that waits afterwards without first checking the state may block for ever. D2
Producer/consumer (bounded buffer)
Simple words: some threads make items, others use them, and a fixed-size shelf sits between them. Analogy: the chef, the pass with four places, the waiters. Precise: a pattern in which producers insert into and consumers remove from a shared buffer of fixed capacity; producers block when it is full, consumers when it is empty. The block on "full" gives back-pressure: fast producers are slowed to the consumers' pace. D7
Back-pressure
Simple words: when the next stage is too slow, the earlier stage is made to wait instead of piling up work. Analogy: when the pass is full, the chef stops plating. Precise: flow control in a pipeline in which a bounded buffer blocks or rejects producers, keeping memory use bounded. D3
Ring buffer
Simple words: an array used in a circle: after the last slot comes the first again. Analogy: four places on the pass, filled left to right and then from the left again. Precise: a fixed array with a head index and a count (or head and tail indices); slot indices are taken modulo the capacity. D7

Layer 1 — the kid explanation

A mutex (F2-36) answers "one at a time". Threads also need a second answer: "wait until something is ready". A waiter should not keep walking to an empty pass; he should sit down until the chef rings the bell. A condition variable is that bell.D1

The bell does not carry the plate and does not remember that it rang. So the rule is: the real information is the pass (the shared data, protected by a mutex); the bell only says "go and look". After every ring, a waiter looks at the pass, and if there is nothing, he waits again.D2 If he arrives after the bell, he looks first and sees the plate, so the missed ring does not matter.R1

With a shelf of fixed size between makers and users, you get the most common pattern in concurrent programs: producer/consumer. Makers wait when the shelf is full, users wait when it is empty.D7

Layer 2 — the student explanation

The interface

A std::condition_variable is always used together with a std::mutex and some shared state that the mutex protects. A waiting thread does this:D1

  1. lock the mutex with std::unique_lock (not lock_guard: wait must be able to unlock and relock it);
  2. call cv.wait(lock, predicate), which returns only when the predicate is true, with the mutex held;
  3. use the state, still under the lock.

A notifying thread changes the state under the same mutex, and then calls cv.notify_one() (wake one waiter) or cv.notify_all() (wake all). The waiting functions also come with timeouts: wait_for(lock, duration, pred) and wait_until(lock, time_point, pred) return the predicate's value when they give up.D1 std::condition_variable_any works with any lock type, at some cost.

Why the predicate is not optional

Listing 1 shows a lost wake-up. The main thread sets soupReady = true and notifies while nobody waits. A thread that then waits with no predicate sleeps until its 300 ms timeout: the notification is gone. A thread that waits with the predicate [] { return soupReady; } checks the state first and returns at once.R1 The predicate also handles the other problem: wait may return when nobody notified (spurious wake-up), and when it returns because of a notify, another thread may have changed the state before this one got the mutex back. The forensic lab shows that second case with real output. The C++ Core Guidelines rule is short: never wait without a condition.D6

The state must also be changed under the mutex, even if it is an atomic. Otherwise this can happen: the waiter checks the predicate (false), the notifier changes the state and notifies, and only then the waiter goes to sleep: the notification fell into the gap between check and sleep. Holding the mutex while changing the state closes the gap, because the waiter holds the mutex from its check until wait atomically releases it.D2

A bounded blocking queue

Listing 2, BoundedQueue<T>, is the course lab's data structure (Figure 1). Its state is a ring buffer (slots_, head_, count_) and a closed_ flag, all protected by one mutex. Its invariant: 0 ≤ count_ ≤ capacity, and the items are in slots_[head_], slots_[head_+1], … modulo the capacity.

  • push waits on notFull_ until there is a free slot or the queue is closed; stores the item; unlocks; notifies notEmpty_.
  • pop waits on notEmpty_ until there is an item or the queue is closed; returns std::nullopt when closed and empty; otherwise removes the item, unlocks and notifies notFull_.
  • close sets the flag and wakes everybody with notify_all, so no thread stays blocked at shutdown.

Two separate condition variables mean a producer's notification wakes a consumer, never another producer, which would only go back to sleep.D2 Shutdown is part of the design, not an afterthought: without close, consumers waiting on an empty queue at the end of the program would wait for ever, and their join would never return (F2-34).

The acceptance test

The curriculum's B10 milestone states the test exactly: "Producer/consumer test with bounded buffer: 10 million items, no loss, no duplicates".S1 Listing 3 runs it in user space: two producers send the numbers 0 to 9,999,999 (even and odd) through a queue of capacity 1,024; two consumers record what they receive in their own vectors; after close and join, the program counts how often each number arrived. Both the course build and a ThreadSanitizer build print PASS, and ThreadSanitizer reports nothing.R2 R3 Note what makes the test strong: it checks every single item, it runs long enough for millions of full and empty transitions (the wait counters show hundreds of thousands of producer waits), and it is run under the race detector.

Note

A passing test under ThreadSanitizer means no data race happened in the executions observed. It does not prove the queue correct for every interleaving. That is why the design also gets a written invariant and an argument (Layer 3), and why curriculum B10 also asks for a lock-order checker (F2-40).

Layer 3 — the engineer's depth

Correctness argument for BoundedQueue. (1) Every access to the state is made with the mutex held, so there is no data race. (2) Each push stores into slot (head_ + count_) % capacity only after its predicate saw count_ < capacity under the same lock hold, so it never overwrites an unread item; each pop reads slots_[head_] only after seeing count_ > 0. (3) No lost wake-up: every change that can make a predicate true (an increment of count_, a decrement, closed_ = true) is followed by a notify on the matching condition variable, and waiters check before sleeping. (4) Termination: after close, notify_all wakes every waiter; producers return false; consumers drain the remaining items and then receive std::nullopt.D2 D7

Notify inside or outside the lock? Both are correct, as long as the state change was made under the lock. Notifying after unlock (lines 30–31 and 49–50) can save the woken thread from waking only to block on the mutex the notifier still holds. Notifying under the lock is sometimes required: when the waiter may destroy the condition variable as soon as it sees the state (for example a one-shot object on the waiter's stack).D2

notify_one or notify_all? notify_one is enough when any one waiter can make progress with the change and every waiter waits for the same kind of change. Use notify_all when the change may allow several waiters to proceed (shutdown) or when waiters on the same condition variable wait for different conditions. Waking all costs a "thundering herd" of threads competing for the mutex.D3

How the hardware actually does it


There is no condition-variable instruction. On Linux, glibc's pthread_cond_wait (used by libstdc++'s std::condition_variable) keeps a sequence counter in memory, and a waiting thread sleeps in the kernel with the futex system call on that counter; notify changes the counter and calls futex to wake one or all sleepers.D9 The "atomic unlock and sleep" of Figure 2 is achieved because the kernel's futex wait checks that the counter still has the value the thread saw, and refuses to sleep if it changed. A woken thread then has to be scheduled on a CPU and must reacquire the mutex: this is why each hand-over at capacity 1 costs several microseconds while an item in a mostly full buffer costs much less (pc_bench).R5 In your own kernel (curriculum B10), the same idea is a wait queue attached to the object, with "check, then sleep" made atomic by holding the object's spinlock while adding yourself to the queue.S1


Not verified — check before relying on this
The description of glibc's condition-variable algorithm (sequence counter, futex wait with value check) is from memory; the algorithm was rewritten in glibc 2.25 and the details here were not checked against the glibc sources or the futex(2) manual page. No trace of a waiting thread's system calls was taken in this build; to see them, run Listing 3 with a small item count under strace -f -e trace=futex.

Where the analogy breaks


    

  1. A bell rings in the room; a notify does not reach everyone. notify_one wakes one waiter, chosen by the system, not the one who waited longest; and a waiter who has not yet started waiting gets nothing (Listing 1).R1
    2. 

  2. A bell does not ring by itself. A wait may return when nobody notified (spurious wake-up).D1
    3. 

  3. Hearing the bell does not get you to the pass first. A woken thread must reacquire the mutex; another thread can get there first and take the item (forensic lab). This is why the predicate is checked again after waking.R6

Transition box

Where you came from: F2-36 gave you mutual exclusion with RAII locks; F2-34 taught that every thread must be joined. What carries over: the mutex still protects all shared state, and the invariant is still what you reason about; a condition variable adds waiting on top of the mutex, never instead of it.D1 What changes: most dangerous first: a missed notification can stop a thread for ever without any error message; a wake-up is only a hint, so the condition must be re-checked; and shutdown must now be designed, because blocked threads do not stop by themselves.R1 R6 What comes next: F2-38 goes one level below mutexes, to the atomic operations that mutexes and condition variables are built from.

Summary


    

  • A condition variable lets a thread sleep until another thread says the shared state changed; the state itself lives under a mutex.
    • 

  • Always wait with a predicate: cv.wait(lock, pred) handles lost and spurious wake-ups and stolen items.
    • 

  • Change the state under the mutex, then notify (after unlocking is fine).
    • 

  • A bounded buffer uses one mutex and two condition variables, and needs a designed shutdown.
    • 

  • The B10 test passed: 10 million items, no loss, no duplicates, ThreadSanitizer clean.
    • 

  • Small capacity means a sleep and wake-up per item; one mutex limits scaling.

Forensic lab answer key


Observation: one plate, two waiters returned from take; one served noodles, the other printed "took a plate from an EMPTY pass" and served "(nothing)" (which waiter it is changes from run to run). Explanation: both waiters wait at line 33. put pushes one plate and calls notify_all (line 25): both wake, and both need m_. The first to reacquire it finds the plate and takes it (lines 40–41). The second reacquires it afterwards; its if was checked once, before waiting, so it falls through to line 36 and finds the pass empty. Ruled out: notify_one alone is not a fix: a spurious wake-up, or a third waiter arriving between the notify and the relock, produce the same symptom.
