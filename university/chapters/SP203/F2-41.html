Story hook

Analogy

In the first week, the restaurant hired a new cook for every order and sent the cook home after one dish. Hiring took longer than cooking. So the owner changed the system: four cooks stay all evening; orders are clipped to a rail as tickets; whichever cook is free takes the next ticket. The guest who ordered gets a numbered receipt and can wait for the dish at the counter, or do something else and come back.

That is a thread pool: a fixed team of worker threads, a queue of tasks, and a future — the receipt — for each result. It is the most common way real programs use threads.

One Saturday, though, the four cooks stopped working while tickets were still on the rail. Each cook was in the middle of a dish that needed a sauce, and each had clipped a "make sauce" ticket to the same rail and was waiting for it. No cook was free to make any sauce. The forensic lab of this chapter is that evening.

What you will be able to do

  • Use std::future, std::promise, std::packaged_task and std::async to return values and exceptions from other threads.
  • Build a fixed-size thread pool with a task queue, futures and orderly shutdown, and test it under ThreadSanitizer.
  • Measure when a pool is faster than serial code and than one thread per task, and model the overhead.
  • Choose a pool size for CPU-bound and for blocking work.
  • Diagnose pool starvation: tasks that wait for tasks queued behind them.
Jargon box
Future
Simple words: an object that will hold a result that is not ready yet. Analogy: the numbered receipt the guest holds. Precise: std::future<T> (header <future>) is the reading end of a shared state; get() blocks until the value (or an exception) is stored, then returns it (or throws it); it can be called once. wait_for waits with a time limit. D1
Promise
Simple words: the writing end that a thread uses to deliver a future's value. Analogy: the cook's copy of the receipt, handed in with the dish. Precise: std::promise<T> owns a shared state; get_future() returns the matching future; set_value/set_exception make it ready; setting it synchronises with the future's get. D1
std::packaged_task
Simple words: a function wrapped so that calling it fills a future. Analogy: a ticket with its receipt stub attached. Precise: a move-only callable wrapper whose call operator invokes the stored function and stores the result or the thrown exception in its shared state. D1
Thread pool
Simple words: a fixed group of threads that take tasks from a queue and run them, one after another. Analogy: four cooks who stay all evening and take tickets from the rail. Precise: a set of long-lived worker threads and a shared task queue; submitting a task enqueues it and returns a handle (here a future); workers block on a condition variable while the queue is empty. D2
Task granularity
Simple words: how much work each task does. Analogy: a ticket for "one grain of rice" versus "a pot of rice". Precise: the ratio of a task's useful work to the per-task overhead (queueing, synchronisation, wake-ups); too fine and overhead dominates, too coarse and load is unbalanced. D3
Pool starvation (thread-pool deadlock)
Simple words: all workers wait for tasks that are queued behind them, so nothing runs. Analogy: every cook waits for a sauce ticket that no free cook can pick up. Precise: a deadlock in which every worker of a bounded pool is blocked waiting for the result of a task that is still in the same pool's queue. D2
Oversubscription
Simple words: more busy threads than CPU cores. Analogy: eight cooks for four stoves. Precise: running more runnable threads than hardware threads, so the operating system time-slices them; adds context switches and cache disruption without adding throughput for CPU-bound work. D3

Layer 1 — the kid explanation

Starting a thread costs time (F2-34 measured tens of microseconds). If a program has thousands of small jobs, starting a thread for each is like hiring a cook for each dish. A thread pool starts a few threads once and keeps them; jobs go into a queue, and free threads take them.D2

When you give a job to the pool, you get a future back: a receipt for the result. Later you call get() on it. If the job is done, you get the answer at once; if not, you wait. If the job failed with an exception, get() throws that exception in your thread, as if you had called the function yourself.D1 R1

A pool is only faster when each job is big enough. If a job takes less time than putting it in the queue and taking it out, the pool makes the program slower.R5

Layer 2 — the student explanation

Futures, promises, tasks

Listing 1 shows the three ways the standard library fills a future:D1

  • std::async(std::launch::async, f, args…) runs f on a new thread and returns its future. Without std::launch::async, the implementation may defer the call until get(), in the calling thread; always say which policy you want.
  • std::promise<T> is filled by hand with set_value or set_exception by whatever code produces the value.
  • std::packaged_task<R(Args…)> wraps a function; calling the task runs the function and stores its result or exception. This is what a pool queues.

The fourth part of Listing 1 throws std::domain_error inside an async task; the exception is stored and re-thrown by get() in main.R1 Making the shared state ready synchronises with the get() that returns it, so everything the task wrote before finishing is visible to the thread that called get(): futures are also a happens-before edge (F2-39).D1 One trap: the destructor of a future returned by std::async blocks until the task finishes, so std::async(std::launch::async, f); with the result ignored runs f synchronously.D2

A pool in 80 lines

Listing 2, ThreadPool, combines the pieces of this course:

  • a std::deque<std::function<void()>> of jobs, protected by one mutex, with one condition variable wake_ (F2-36, F2-37);
  • submit(f, args…) wraps the call in a std::packaged_task held by a std::shared_ptr (because std::function needs a copyable target and a packaged task is move-only), queues a small lambda that runs it, and returns the future;
  • each worker loops: wait until there is work or the pool is stopping; if stopping and the queue is empty, return; otherwise take a job and run it outside the lock;
  • the destructor sets stopping_, wakes everybody and joins the workers, so every queued job runs before the pool is gone (RAII for threads, F2-34).

The member order matters: workers_ is declared last, so the mutex, condition variable and queue already exist when the constructor starts threads that use them, and are destroyed only after the destructor's body has joined the threads.D1

Testing a pool

Listing 3 tests six properties: all of 1,000 tasks run and their results arrive; an exception reaches the caller; the destructor drains the queue; four client threads may submit at the same time; tasks run on pool threads only, never on the caller; a pool of zero workers is refused. All six pass with AddressSanitizer and UndefinedBehaviorSanitizer, and again with ThreadSanitizer.R2 R3 Notice what the tests do not do: they never sleep to "give the pool time"; every check waits on futures or on the destructor, so the tests are deterministic.

How many workers?

For CPU-bound tasks, one worker per hardware thread (std::thread::hardware_concurrency()) is the starting point: more workers only time-share the same cores (oversubscription).D3 For tasks that block (disk, network, locks), more workers can help, because a blocked worker uses no core. A common rule of thumb is cores × (1 + wait time / compute time), to be checked by measurement.D2 Never let a pool's tasks block on other tasks of the same pool (forensic lab).

Layer 3 — the engineer's depth

Overhead, measured. pool_bench.cc runs 20,000 tasks of three sizes serially, on pools of 1, 2, 4 and 8 workers, and with one std::async thread per task (for the two smaller sizes):R5



Two results held in every run of this build, and agree with the model in the worked example. (1) For tiny tasks, every pool was slower than the serial loop: queueing, waking and the future cost more than the work. (2) A thread per task was slower than any pool by more than an order of magnitude, because each task paid a thread start.R5 The third expected result, that the largest tasks run nearly four times faster on 4 workers, depended on the load from other jobs on this shared machine: one run had 4 workers more than twice as fast as serial, another run no faster at all, and 8 workers were never clearly faster than 4. Read the large-task row as a measurement of the machine's free capacity at that moment, and repeat it on an idle machine.


One queue is a contention point. Every submit and every take locks the same mutex. With many workers and short tasks, that lock becomes the bottleneck (F2-36's lock ceiling). Production pools use one queue per worker plus work stealing: a worker takes from its own queue's front and, when empty, steals from the back of another's. Tasks submitted from inside a task go to the local queue, which also improves cache locality.D2 D3


Avoiding starvation. Three remedies, from best to worst: (a) do not wait inside a task; structure work as continuations (submit the follow-up when the sub-task finishes) or do the sub-work inline; (b) "help while waiting": a worker that waits for a future runs other queued tasks meanwhile (Williams's pool does this); (c) separate pools for tasks that wait and tasks that are waited for. Making the pool bigger only moves the threshold: with N workers, N simultaneous outer tasks still starve.D2


Cancellation and shutdown policy. This pool's destructor drains the queue. Other policies are possible: discard queued tasks (their futures then report std::future_errc::broken_promise when the packaged_task is destroyed unrun), or cooperative cancellation with std::stop_token (F2-34's std::jthread). Document which one your pool implements; Listing 3's test 3 pins this one down.D1

How the hardware actually does it


A pool saves three hardware costs compared with a thread per task. Thread creation: a clone system call, a new stack mapping, scheduler bookkeeping; F2-34 measured tens of microseconds per start and join in this container.R7 Cold caches: a new thread starts on whatever core the scheduler picks, with none of the task's data in that core's caches, while a long-lived worker keeps its stack and often its data warm. And scheduler load: 20,000 short-lived threads are 20,000 entries for the kernel to create, schedule and reap.D7 What a pool still pays per task is the queue's lock (an atomic RMW and a possible cache-line transfer, F2-38), the condition variable's wake-up when a worker sleeps (a futex system call, F2-37), and the shared state of the future (a heap allocation and another synchronisation). Those are the "overhead per task" that the worked example models; for work of a microsecond or less they dominate.R5


Not verified — check before relying on this
The breakdown of thread-creation cost (system call, stack mapping, scheduler) and the claim that a std::future's shared state is heap-allocated in libstdc++ are from memory and were not traced or profiled in this build. Check with strace -c on pool_bench's async-per-task section and with perf record; the per-task overhead of 5 µs in the worked example is a round number for the model, not a measurement.



Worked example


A model: N = 10,000 tasks, P = 4 workers, each task does t µs of work and costs o = 5 µs of pool overhead (queueing, wake-up, future). Assume perfect balance and no other limit.


    

  1. Serial time = N × t.
    2. 

  2. Pool time ≈ N × (t + o) / P, because each worker handles N/P tasks and pays t + o for each.
    3. 

  3. Speedup = serial / pool = P × t / (t + o). Efficiency (useful fraction of each worker's time) = t / (t + o).
    4. 

  4. For t = 1 µs: speedup = 4 × 1/6 ≈ 0.67: the pool is slower than serial. For t = 10: 2.67. For t = 100: 3.81. For t = 1,000: 3.98.
    5. 

  5. Rule: to get within 5 % of the ideal speedup, a task must do about 20 times the per-task overhead. If your tasks are smaller, batch them (one task processes a range of items).
    6.

Where the analogy breaks


    

  1. A cook can see that everyone is waiting for sauce and go and make it. A worker blocked in get() cannot do anything else unless the pool was designed to "help while waiting"; the forensic lab's pool was not.R6
    2. 

  2. A receipt can be shown many times. std::future::get() can be called once; after that the future is empty. std::shared_future allows many readers.D1
    3. 

  3. More cooks at more stoves cook more. More workers than cores do not run more CPU work at once; in the benchmark 8 workers on 4 CPUs were never clearly faster than 4 (a limit of this chapter's use of the analogy, not the registered one: the cooks picture hides that threads need cores to run on).R5

Summary


    

  • A future is a receipt for a result; get() waits, returns the value or re-throws the exception, and synchronises.
    • 

  • std::async (with launch::async), std::promise and std::packaged_task fill futures.
    • 

  • A thread pool is a producer/consumer queue of tasks plus long-lived workers, joined in its destructor.
    • 

  • Pools pay off only when tasks are large compared with per-task overhead; batch small work.
    • 

  • For CPU-bound work, use about one worker per core; oversubscription does not help.
    • 

  • Never let tasks block on tasks of the same pool: that is a deadlock with no mutex.
    •

Forensic lab answer key


Observation: both reports gave up after 500 ms with 2 tasks queued: the two sub-tasks. Workers: worker A runs report 1 and is blocked in part.wait_for (in the real service, get()); worker B runs report 2, likewise. Graph: report 1 waits for sub-task 1, which waits for a free worker; the only workers are held by reports 1 and 2, which wait for their sub-tasks: a cycle through the resource "worker". Quiet days: with one report, one worker waits and the other runs the sub-task. A pool of N workers hangs when N reports are in progress at once. Bigger pool: no; 16 workers hang with 16 simultaneous reports; the bug only moves to busier days. Fixes: (1) keep the sub-task but help while waiting (the worker runs queued tasks until its future is ready), or submit sub-tasks to a separate pool; (2) remove the wait: compute the part inline in the report task, or make the report a continuation submitted when the sub-task finishes. Detection: a thread dump shows every worker inside std::future::get (or wait) under a task, while queued() is non-zero. How the evidence was made: starvation.cpp, run by run_lab.sh in this build (R6); the 500 ms limit replaces the real service's unbounded get() only so that the program ends.
