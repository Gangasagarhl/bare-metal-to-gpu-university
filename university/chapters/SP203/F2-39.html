Story hook

Analogy

The chef finishes a plate of dumplings, writes "table 7" on its ticket, and raises a little flag on the pass that means "ready". The waiter sees the flag and takes the plate. Surely the plate was on the pass before the flag went up. Or was it?

Suppose the kitchen were run by an over-eager assistant who reorders jobs to save steps. "The flag is right here, the plate is still on the stove; let me raise the flag now and put the plate down in a moment." Nothing is wrong from the chef's point of view: both jobs get done. But the waiter, who sees the flag first, reaches for an empty spot or for a ticket that still says "table 0".

Compilers and processors are that assistant. They reorder memory operations whenever a single thread cannot tell the difference. This chapter is the contract that says when they may not: you mark the flag as a release ("everything before me goes down first") and the waiter's look as an acquire ("nothing after me happens before I look").

What you will be able to do

  • Define sequenced-before, synchronises-with and happens-before, and use them to decide whether a program has a data race.
  • Choose among memory_order_relaxed, acquire, release, acq_rel and seq_cst, with a reason for each choice.
  • Publish data from one thread to another safely with a release store and an acquire load.
  • Read the instructions that each order becomes on x86-64 and on AArch64, and explain why a bug can hide on one and appear on the other.
  • Investigate a publication bug with ThreadSanitizer and compiler output when the target hardware is not at hand.
Jargon box
Memory model
Simple words: the rules that say which values a read in one thread may see from writes in other threads. Analogy: the kitchen's written rules about what the assistant may reorder. Precise: for C++, the part of the standard ([intro.multithread], [atomics.order]) that defines data races, happens-before and the values atomic loads may return; for hardware, the memory consistency model of the ISA (F1-37). D1
Happens-before
Simple words: "this action is guaranteed to be finished and visible before that one". Analogy: the plate was down before the waiter looked, and the waiter knows it. Precise: a partial order on actions built from sequenced-before (program order in one thread) and synchronises-with (between threads), closed under transitivity. If a write happens-before a read of the same location, with no other write in between, the read sees that write. D1
Synchronises-with
Simple words: the link between two threads that creates happens-before. Analogy: the waiter seeing the flag the chef raised. Precise: a release operation on an atomic object synchronises with an acquire operation on the same object that reads the value written by the release (or by a later write in its release sequence); unlock/lock of a mutex and thread start/join also synchronise. D1
Acquire and release
Simple words: a release write publishes everything written before it; an acquire read that sees it receives all of that. Analogy: put the plate down, then raise the flag (release); see the flag, then take the plate (acquire). Precise: HW203 term (F1-37); in C++, memory_order_release on stores and memory_order_acquire on loads (and acq_rel on read-modify-writes) create synchronises-with edges; writes sequenced before the release cannot be moved after it, reads sequenced after the acquire cannot be moved before it. D1
Relaxed atomic
Simple words: an atomic operation that is indivisible but orders nothing else. Analogy: the tally counter clicks correctly, but nobody may conclude anything about the plates from its number. Precise: memory_order_relaxed: the operation is atomic and respects the object's modification order, but creates no synchronises-with edge. D1
Sequential consistency
Simple words: the program behaves as if all threads' steps were interleaved into one list. Analogy: one long order book in which every cook's action appears in their own order. Precise: HW203 term (F1-37); in C++, memory_order_seq_cst (the default) adds a single total order over all seq_cst operations; and a program with no data races, using only seq_cst atomics, behaves sequentially consistently ("DRF-SC"). D1 D11
Memory fence
Simple words: an instruction or statement that stops memory operations moving across it. Analogy: a rule "finish everything on the counter before you go on". Precise: HW203 term (F1-37); in C++, std::atomic_thread_fence(order), which combined with atomic operations creates synchronisation without a particular atomic object carrying it. D1

Layer 1 — the kid explanation

When you write two lines of code, you expect them to happen in that order. Inside one thread they appear to. But the compiler and the processor are allowed to swap them whenever your thread alone could not notice the difference. Another thread can notice.D1 D4

So when one thread prepares some data and then says "ready" with an atomic flag, it must tell the machine: "everything I wrote before this flag must be visible before the flag". That is a release. The thread that reads the flag must say: "once I see the flag, show me everything that came before it". That is an acquire.D1 Together they make a handshake. Without the handshake, the reader might see "ready" and still get old data.R3

If you do not choose an order, C++ uses the safest one, called sequentially consistent. Use it unless you have measured a reason to do otherwise and can explain why the weaker order is enough.D6

Layer 2 — the student explanation

The rules in one page

The C++ memory model decides everything with one relation, happens-before:D1

  1. In one thread, an action that comes earlier in program order is sequenced before a later one, and so happens-before it.
  2. Between threads, happens-before comes only from synchronises-with edges: a release on an atomic and an acquire that reads its value; a mutex unlock and the next lock; the start of a std::thread and its function; a thread's end and the return of join().
  3. Happens-before is transitive: A before B and B before C gives A before C.
  4. Two conflicting accesses (same location, at least one write), not both atomic, and not ordered by happens-before, are a data race: undefined behaviour (F2-35).
  5. If a write W happens-before a read R of the same location, R cannot see a value older than W.

F2-35 used rule 4 to define data races; F2-36's mutex and F2-34's join were examples of rule 2. This chapter adds the edges you can make yourself with atomics.

Warning
Weaker orders are an optimisation with a real risk: a mistake may be invisible in testing on x86-64 and appear only on Arm or after a compiler upgrade. Start with the default; weaken only with a measured benefit, a written happens-before argument, and a ThreadSanitizer run (which understands release/acquire). The C++ Core Guidelines say to use seq_cst unless you are an expert.D6



Layer 3 — the engineer's depth


Why seq_cst is different from acquire/release. F1-37's store-buffering test has two threads: one stores x = 1 then loads y; the other stores y = 1 then loads x. With release stores and acquire loads, both loads may return 0, because acquire/release only constrain a load against later operations and a store against earlier ones: a store followed by a load to a different location may still be reordered. With seq_cst on all four operations, there is a single total order of them, and in any such order one of the stores comes before the other thread's load, so at least one load returns 1.D1 D4 On x86-64 this is exactly the one reordering the hardware does (the store buffer, F1-37), and exactly why g++ makes the seq_cst store an xchg: a locked instruction drains the store buffer.R6 D8


DRF-SC. The central guarantee of the model: a program without data races whose atomics all use seq_cst behaves as if executed by interleaving the threads' steps in program order. You can reason about such programs as F2-35's interleavings, and forget about reordering.D11 Weaker orders give up that guarantee; reasoning then needs happens-before diagrams like Figure 1.


Release sequences and RMWs. An acquire load that reads a value written by an RMW (for example fetch_add) that came after a release store on the same object still synchronises with that release: the RMW chain forms a "release sequence". This is why reference counts can use relaxed increments and an acq_rel (or release plus an acquire fence) decrement.D1 D2


Fences. std::atomic_thread_fence(memory_order_release) before a relaxed store, paired with a relaxed load followed by atomic_thread_fence(memory_order_acquire), synchronises like a release store and an acquire load. Fences let one barrier cover several atomics; they are the C++ form of the hardware fences of F1-37 (dmb ish on Arm, mfence or a locked instruction on x86).D1 R6 R7


The compiler counts as much as the hardware. Reordering is not only a processor matter. In the forensic lab's AArch64 build, g++ merged the two int stores of the configuration into one 8-byte store and placed it before the pointer store; with relaxed order it would have been equally entitled to place it after.R8 F2-35's hoisted flag was the same rule applied to loads.

AArch64:R7




On x86-64, every load already has acquire semantics and every store release semantics under TSO, so acquire and release compile to plain mov; only seq_cst stores need xchg, and the fence is a locked no-op on the stack (lock orq $0,(%rsp)), which g++ prefers to mfence.R6 D8 AArch64 has a weaker model in which ordinary loads and stores to different addresses may become visible out of order, so release stores become stlr (store-release), acquire loads ldar (load-acquire), and the seq_cst fence dmb ish (data memory barrier, inner shareable domain).R7 D10 Note that seq_cst stores and loads use the same stlr/ldar as release/acquire there: on Armv8, ldar may not be reordered before an earlier stlr, which is enough for seq_cst.

Where the analogy breaks


    

  1. An assistant reorders by choice; reordering in machines has many sources. The compiler reorders and merges instructions, the processor executes out of order, and the store buffer delays writes (F1-37). The rules of this chapter cover all of them together; the analogy suggests a single culprit.D4
    2. 

  2. A plate is in one place; memory has copies. Each core's caches and store buffer can hold a different view for a while, so two waiters can disagree about the order in which two flags went up (the store-buffering result of Layer 3).D4
    3. 

  3. The data race in the analogy is a wrong plate; in C++ it is undefined behaviour. The registered picture of a data race — two cooks writing on the same order slip (guide 8.1) — suggests a garbled slip; the language gives no guarantee at all once a race happens (F2-35).D1
    4.

Transition box

Where you came from: F1-37 (HW203) showed hardware reordering with litmus tests and introduced TSO, fences and acquire/release at the instruction level; F2-38 used atomics with the default order. What carries over: the litmus tests and the store buffer explain why C++ needs memory orders; the hardware vocabulary (fence, acquire, release) is the same.D4 What changes: most dangerous first: you now reason about the language's model, which is weaker than any one processor's, so a test on your own machine proves less than before; correctness is a property of a happens-before argument, not of observed output; and the compiler is as much a source of reordering as the hardware.R3 R8 What comes next: F2-40 returns to locks, and to the bug locks bring with them: deadlock.

Forensic lab


Scenario: "Works on the laptop, garbage on the board". The restaurant's new smart oven has a small Arm controller board. A settings thread writes a new configuration and publishes a pointer to it; the control loop picks up the pointer and applies the settings. On the developer's x86-64 laptop, thousands of test runs were fine. On the oven, a technician once saw the control loop log "speed limit 0, max temperature 0" for a configuration that had been written as 30 and 85. The team cannot reproduce it on the laptop.

Mini-project


Write a double-buffered configuration class for the oven: the settings thread fills an inactive buffer and publishes it with one atomic pointer; the control loop reads the current buffer. Address the problem of reuse: when can the settings thread overwrite the buffer the control loop may still be reading? Solve it with a generation counter or by never reusing (allocate a new configuration and keep old ones until shutdown), and justify every memory order in a comment. Summary


    

  • Happens-before decides everything: program order inside a thread, synchronises-with between threads, transitivity.
    • 

  • A release store and an acquire load that reads it synchronise; both sides are needed.
    • 

  • Relaxed atomics are exact but publish nothing.
    • 

  • seq_cst (the default) adds one total order; with no data races it gives sequential consistency (DRF-SC).
    • 

  • x86-64 compiles acquire/release to plain moves; AArch64 needs stlr/ldar. Bugs can hide on x86-64.
    • 

  • Prove correctness with a happens-before argument and ThreadSanitizer, not with passing output.
    •

Forensic lab answer key


Observation: ThreadSanitizer reports a data race on the global storage: read at line 29 in controlLoop, previous write at line 19 in settingsThread. Diagnosis: the pointer is published with a relaxed store (line 21) and read with a relaxed load (line 27): no synchronises-with, so the configuration writes do not happen-before the reads. This is a data race, so undefined behaviour on every machine. AArch64 code: the two int settings were merged by the compiler into one 8-byte str d0, followed by str x0 for the pointer; there is no stlr and no dmb between them, so nothing stops the Arm memory system from making the pointer visible to another core first. Why the laptop passed: on x86-64 the same relaxed code is two plain mov stores, and TSO keeps stores in order, so the reordering that would expose the bug does not happen in the hardware there (Figure 2); the compiler could still reorder them, but did not in this build. QEMU: proves the Arm binary runs and computes the right values in at least one execution; it does not reproduce the Arm memory system (see the untested-on-hardware box). Fix: current.store(&storage, std::memory_order_release) at line 21 and current.load(std::memory_order_acquire) at line 27 (or leave both at the default seq_cst). AArch64 then uses stlr for the pointer store and ldar for the load (check with -S). Chain: writes (19–20) →sb release store (21) →sw acquire load (27) →sb reads (29). Prevention: any relaxed atomic that guards other data is a review finding; run ThreadSanitizer in CI on x86-64, which catches the race even though the hardware hides it. How the evidence was made: publish_config.cc, built and run by the lab's run.sh in this build (R8); the oven, the technician and the logged zeros are an illustrative scenario, not an observation.
