Story hook

Analogy

At the end of a busy night the restaurant counts how many meals it served. There is one order slip on the wall with a number on it. Every time a cook sends out a plate, she reads the number, adds one in her head, rubs the old number out and writes the new one.

Ana and Rafael send out plates at the same moment. Both read "41". Both think "42". Both write "42". Two plates went out, but the slip only went up by one. Nobody did anything silly: each of them followed the rule exactly. The problem is that the rule has three steps, and the two cooks' steps got mixed together.

Worse things can happen with slips. If Ana writes while Rafael is reading, he may read half of her new number and half of the old one. In C++ the situation is even stranger: the language says that a program in which this happens has no meaning at all, and the compiler is allowed to assume it never happens. This chapter shows what that means in practice, and introduces the tool that catches it: ThreadSanitizer.

What you will be able to do

  • Define a data race exactly as C++ does, and decide for a given piece of code whether it has one.
  • Explain why a data race is undefined behaviour, not merely a "wrong number", using a real compiler output.
  • Enumerate the interleavings of a read–modify–write and count how many lose an update.
  • Use ThreadSanitizer to find a data race and read its report: the two accesses, the location, the threads.
  • Distinguish a data race from a race condition (a timing-dependent bug that may have no data race).
Jargon box
Memory location (C++)
Simple words: one variable's worth of memory that the rules about threads talk about. Analogy: one order slip on the wall. Precise: an object of scalar type (an int, a pointer, a bool…) or a maximal sequence of adjacent non-zero-width bit-fields; two threads may update different memory locations without interfering, even if they are neighbours in memory. D1
Conflicting accesses
Simple words: two uses of the same variable where at least one changes it. Analogy: one cook reads the slip while another rewrites it. Precise: two expression evaluations conflict if one of them modifies a memory location and the other reads or modifies the same memory location. D1
Data race
Simple words: two threads touching the same memory at the same time, at least one writing, with nothing to keep them in order. Analogy: two cooks writing on the same order slip at once. Precise: in C++, two conflicting accesses to the same memory location from different threads, at least one a write, not ordered by synchronisation (neither happens-before the other) and not both atomic; a program with a data race has undefined behaviour. D1
Lost update
Simple words: one thread's change is overwritten as if it never happened. Analogy: two plates out, the slip went up by one. Precise: the outcome of interleaved read–modify–write sequences in which a thread stores a value computed from a stale read, erasing another thread's store. D3 D7
Interleaving
Simple words: one possible order in which the steps of several threads are mixed together. Analogy: the order in which Ana's and Rafael's steps actually happened. Precise: a total order of the threads' operations that keeps each thread's own order; the model F1-30 used. Real hardware and compilers can produce results that no interleaving explains (F1-37, F2-39). D7 D4
Race condition
Simple words: a bug where the result depends on which thread gets there first. Analogy: two cooks both see "one portion left" and both promise it to a table. Precise: a correctness bug that occurs only under some timings of concurrent operations; it may involve a data race, or happen with every access properly synchronised (a check-then-act on an atomic, F2-38). D2 D3
ThreadSanitizer (TSan)
Simple words: a compiler option that adds checks to your program so that it reports data races while it runs. Analogy: a supervisor who watches every slip and writes down every time two cooks touch one without taking turns. Precise: a dynamic data-race detector in GCC and Clang, enabled with -fsanitize=thread; it instruments memory accesses and synchronisation and reports pairs of conflicting accesses that were not ordered by happens-before in the execution that ran. D5

Layer 1 — the kid explanation

Two threads can use the same variable. Reading it together is fine: looking at a slip does not change it. The trouble starts when at least one of them writes. If nothing makes them take turns, their steps can mix in any order. That is a data race.D1

Adding one to a number looks like one step, but the computer does three: read the number, add one, write it back. Two threads doing that at once can both read the same old number. Then one of the two additions disappears. You will see a program that should count to two million and counts to about one million instead.R1

There is a second, stranger danger. The compiler is allowed to assume that no data race happens. So it may change your program in ways that are perfectly fine for one thread but break the second one. You will see a loop that never stops, because the compiler decided it only needs to look at a variable once.R3 The good news: a tool called ThreadSanitizer can watch a running program and tell you exactly where two threads touched the same variable without taking turns.D5

Layer 2 — the student explanation

The definition, piece by piece

C++ defines a data race in its description of multi-threaded executions.D1 Two evaluations conflict if one modifies a memory location and the other reads or modifies the same location. A program's execution contains a data race if it contains two conflicting actions in different threads, at least one of which is not atomic, and neither happens-before the other. Any such data race results in undefined behaviour.D1 Figure 2 is the same sentence as a checklist.

The definition is about memory locations, not bytes or variables in general. Two different int elements of an array are different memory locations, so two threads may write partial[0] and partial[1] at the same time with no data race, which is why F2-34's Listing 1 is correct.D1 (They may still slow each other down if they share a cache line; F2-38 measures that "false sharing", which is a performance problem, not a correctness one.) Adjacent bit-fields, on the other hand, form one memory location: two threads writing two neighbouring bit-fields do race.D1

Happens-before is the relation that synchronisation creates. You have met one source of it: everything a thread did happens-before the return of join() on it (F2-34). Unlocking a mutex happens-before the next lock of that mutex (F2-36), and a release store happens-before an acquire load that reads it (F2-39).D1 If you can draw a chain of these between two conflicting accesses, they do not race.

Why "undefined behaviour" and not "a wrong value"?

Because the language makes data-race-free programs behave as if each thread's operations happened in some interleaving (for programs that use only plain accesses, locks and default atomics), and compilers and processors rely on that promise to optimise.D1 D4 A compiler optimising one thread's code may keep a variable in a register, merge two reads into one, or move a store, because no other thread is allowed to look in between without synchronisation.D2 If another thread does look, the result is not "the old value or the new value": it is whatever the transformed code does.

Listing 2 shows this with a real compiler. A worker spins on a plain bool stopRequested; main sets it to true after 100 ms. Built with -O0, the worker stopped. Built with -O2, it never stopped: the run was ended by the 3-second time limit (exit code 124).R3 The assembly g++ produced for worker() at -O2 explains it: the flag is tested once (cmpb $0, stopRequested(%rip)), and if it was false, the code enters .L6: jmp .L6, a loop that never reads memory again. The ++spins is gone too, because nobody could legally observe it.R3 The compiler did nothing wrong: in a program without data races, no other thread can change stopRequested while the loop runs without synchronising, so reading it once is a valid optimisation.D1 Making the flag std::atomic<bool> removes the race and the hang.

ThreadSanitizer

ThreadSanitizer is enabled by compiling and linking with -fsanitize=thread (GCC and Clang; use -g for line numbers and some optimisation such as -O1).D5 It cannot be combined with AddressSanitizer in the same build, so this course runs it as a second build of the same source (the lab's run.sh does it).D5 The instrumented program records, for every memory access, which thread made it and what that thread had synchronised with; when two conflicting accesses are not ordered by happens-before, it prints a report.D5

Read the report of Listing 1 (below, lost_update_tsan) from the top:R2

  • WARNING: ThreadSanitizer: data race — the kind of problem.
  • Read of size 8 … by thread T2 with a stack ending in sell(int) lost_update.cc:10 — the current access. (At -O1 the report attributes the increment to the loop line 10; the ++sold is on line 11. Optimisation can shift line numbers by a line; read the function and the variable, then the line.)
  • Previous write of size 8 … by thread T1 — the other access, at the same place in the other thread.
  • Location is global 'sold' — the variable. For a heap or stack object the report says so instead.
  • Thread T2 … created by main thread at: … main lost_update.cc:18 — where each thread was started.

Two details matter. First, under ThreadSanitizer the same program printed sold = 2000000: the instrumentation changed the timing so much that no update was lost in that run, yet the race was reported.R2 A race detector does not need the bug to show; it needs the two unsynchronised accesses to happen. Second, a reported race causes the program to exit with code 66 here even though main returned 0; that is how a test script notices the report.R2

Removing the race

There are two families of fix: make the accesses take turns (a mutex, F2-36), or make the operation indivisible (an atomic, F2-38). Listing 3 changes one line, long sold to std::atomic<long> sold{0}; ++sold then becomes one atomic read–modify–write. Its ThreadSanitizer build printed only the correct total and exited with 0.R5 The fix you choose depends on what must be protected: one counter (an atomic), or several variables that must change together (a mutex).

Layer 3 — the engineer's depth

"SC for data-race-free programs". The C++ memory model is designed so that a program without data races, using only locks and the default (seq_cst) atomics, behaves as if all threads' operations were interleaved in one total order consistent with each thread's program order: sequential consistency (F1-37).D1 D4 This is the deal: you remove every data race; the compiler and hardware keep every optimisation that a single thread cannot notice; together, you get interleaving semantics back. Weaker atomic orders (F2-39) give up part of the deal for speed, explicitly.

What compilers may do to racy code. Beyond reading once (Listing 2), a compiler may: invent a read (load a variable twice where the source loads it once, and get two different values); split a wide store into two narrower ones; or write a value speculatively and restore it later.D2 D3 Each is invisible to a single-threaded program and fatal to a racy one. The standard does forbid compilers from inventing writes to memory locations the program would not have written, because that could create a data race in a correct program.D1

Not verified — check before relying on this

The list of specific transformations (invented loads, store splitting, speculative writes) and the rule against invented stores are recalled from the concurrency literature (Williams; McKenney; the C++ memory-model papers by Boehm and Adve) and from the C++ draft, none of which were opened in this build. Only the "read once" transformation was observed here (Listing 2's assembly). Check D1 ([intro.races]) and D3's chapter on compiler optimisations of shared variables before quoting this list.

"Benign" races do not exist in C++. Programmers sometimes argue that a race on a flag or a statistics counter is harmless ("a slightly wrong count is fine"). In C++ the behaviour is undefined, so there is no "slightly": Listing 2 is exactly such a flag. If an approximate, unsynchronised count is acceptable, the correct tool is an atomic with memory_order_relaxed (F2-39), which costs little and is defined.D1 D6

What ThreadSanitizer can and cannot tell you. It reports races that occurred in the execution it watched; code paths the test did not run are not checked, so its silence is evidence about one run, not a proof.D5 It understands the synchronisation of the standard library and POSIX threads (mutexes, condition variables, atomics, thread start and join); hand-written synchronisation through inline assembly or memory it cannot see is invisible to it.D5 It slows programs down and uses more memory: F2-37's 10-million-item queue test needed tens of seconds under ThreadSanitizer on this machine (its run record notes the wall time), so stress tests under it are kept smaller or run less often.D5 R6 And it reports other bugs too, such as lock-order inversions (F2-40).

Not verified — check before relying on this

The statements that ThreadSanitizer cannot be combined with AddressSanitizer, that exit code 66 is its default exit code after a report, and that it tracks a bounded history of accesses (so very old accesses can be missed) come from memory of the sanitizer documentation, which was not opened. The build only observed exit code 66 after reports (R2, R8). Check the Clang "ThreadSanitizer" documentation and the GCC manual's "Instrumentation Options" for the versions in the run records.

How the hardware actually does it

On x86-64, ++sold on a plain long compiles to a load into a register, an add, and a store (or an add instruction with a memory operand, which still performs a separate read and write without a lock prefix).D8 Between the read and the write, another core can obtain the cache line in the Modified state, write its own value, and lose it again when this core writes back (F1-36).D4 Cache coherence keeps each location's writes in one order that all cores agree on; it does not make a read followed by a write indivisible.D4 That indivisibility needs a locked read–modify–write instruction: F2-38 shows g++ emitting lock addq and lock xaddq for std::atomic increments.R7

Worked example

Two threads A and B each run r = x; r = r + 1; x = r; once, starting from x = 0. How many interleavings are there, and how many end with x == 2?

  1. Each thread has 3 steps in a fixed order. An interleaving chooses which 3 of the 6 time slots belong to A: C(6, 3) = 6·5·4 / (3·2·1) = 20 interleavings.
  2. The result is 2 only if one thread's load comes after the other's store. A's store is its last step, so B's load (B's first step) must come after all of A: the order AAABBB. Symmetrically BBBAAA.
  3. So exactly 2 interleavings are correct, and 18 end with x == 1: in every other order, both loads happen before the second store's thread has finished, so both compute 1.

Real runs lose far fewer than 90 % of the increments because a thread usually executes many loop iterations without interruption; the losses come in bursts when both threads run at the same time. That is why the totals in Listing 1's runs are "about half" rather than "about a tenth".R1

Where the analogy breaks


    

  1. A garbled slip is the worst a kitchen can get; a C++ data race is worse. With two cooks, the slip shows some mix of the two numbers. In C++ a data race is undefined behaviour: the program may hang (Listing 2), crash, or do something no ordering of the two cooks could explain (registered limit, guide 8.1).D1 R3
    2. 

  2. Cooks see each other; threads are invisible to each other. Ana would notice Rafael reaching for the same slip. Threads have no such awareness: nothing in the hardware or language warns either thread, which is why a tool like ThreadSanitizer is needed.D5
    3. 

  3. The kitchen has one slip; the program may have copies. A compiler can keep a variable in a register (each cook's private memory of the number) for a long time, so "reading the slip" may not read memory at all.R3
    4.

Transition box

Where you came from: F2-34 started threads and avoided sharing by giving each thread its own slot; F1-30 met interleavings and saw ThreadSanitizer once; SP101 and F2-23 defined undefined behaviour for one thread. What carries over: the undefined-behaviour mindset (a program that breaks a rule has no meaning, and the optimiser exploits that), and the sanitizer habit: every concurrent listing now gets a second build with -fsanitize=thread.D1 D5 What changes: most dangerous first: a data race is undefined behaviour even when "only a counter" is involved; a result that looks right proves nothing (TSan reported a race in a run with the correct total); and correctness now depends on happens-before relations you create explicitly, not on the order of lines in the source.R2 What comes next: F2-36 introduces the main tool for creating happens-before around several variables at once: the mutex.

Summary


    

  • A data race: two accesses to the same memory location, in different threads, at least one a write, not both atomic, neither happening-before the other.
    • 

  • A data race is undefined behaviour; the optimiser assumes there is none (Listing 2's loop that never stops).
    • 

  • ++x on a plain variable is a load, an add and a store; interleaving loses updates (18 of 20 orders for two threads).
    • 

  • Different memory locations (two array elements) do not race, even if they are neighbours.
    • 

  • ThreadSanitizer (-fsanitize=thread) reports races that happened in the run, even when the output looks right; silence covers only what ran.
    • 

  • Fix with an atomic for a single variable, a mutex for several; volatile is not a fix.
    • 

  • A race condition is a timing-dependent logic bug; it can exist without any data race.
    •

Forensic lab answer key


Observation: ThreadSanitizer reports data races in KitchenStats::recordOrder(long) at stats.cc:16: a read (and writes) of size 8 by different till threads (T1, T2, T3…), called from the lambda at line 39; the plain -O2 runs always show orders = 400000, while the revenue is short in some runs and exact in others (which runs are short changes every time the lab runs; on a busy machine the threads overlap less and fewer updates are lost). Why one is right: ++orders_ (line 14) is inside the block that holds guard (lines 12–15); revenueCents_ += priceCents (line 16) is after the block's closing brace, where the lock has already been released. "Stack of main": stats is a local variable of main (line 34), and its members live inside it; the tills reach it through the lambda's reference capture. Hypotheses: (H1) a rounding error in cents arithmetic — ruled out: all values are integer cents, and the deficit is not a constant; (H2) lost updates on revenueCents_ — confirmed by the ThreadSanitizer report on exactly that line, which appears in every ThreadSanitizer run whether or not any revenue was lost, and by the varying deficit. Fix: move line 16 inside the locked block (or protect both members with the same lock in every member function, including any getters). Proof: rebuild with -O1 -g -fsanitize=thread: no warning, exit code 0; plain runs show exactly 1000000.0. Prevention: document "mutex_ protects orders_ and revenueCents_" next to the members (F2-36), and run the statistics test under ThreadSanitizer in CI. How the evidence was made: stats.cc built and run by the lab's run.sh (R8).
