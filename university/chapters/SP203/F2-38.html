Story hook

Analogy

At the door of the restaurant, two greeters count guests. In F2-35 they kept the count on a slip of paper: read the number, add one in your head, write the new number. When two greeters did it at once, guests vanished from the count.

Now each door has a metal tally counter: you press it, and it clicks from 41 to 42 in one movement. There is no moment where a number is "in your head". Two greeters pressing the same counter at the same instant still get 43: the clicks happen one after the other inside the counter.

On Friday the theatre next door uses the same kind of counter to sell its last seats, and still sells more seats than it has. The counter itself never lost a click. So what went wrong? That question is this chapter's forensic lab, and the lesson of the whole chapter: one click is indivisible; two clicks in a row are not.

What you will be able to do

  • Use std::atomic<T>: load, store, exchange, fetch_add and compare_exchange_weak/_strong.
  • Write a compare-and-swap retry loop and explain why it is correct when other threads interfere.
  • Check whether an atomic type is lock-free on your platform, and know what the answer means.
  • Build a spinlock from std::atomic_flag and say when a spinlock is a bad idea.
  • Recognise an atomicity violation (check-then-act on atomics), which ThreadSanitizer cannot report, and fix it.
  • Measure the cost of atomic operations, contention and false sharing.
Jargon box
Atomic operation
Simple words: an operation that other threads see either completely done or not started. Analogy: a tally counter that clicks in one movement. Precise: an operation on an atomic object; in C++, operations on std::atomic<T> are indivisible and never form a data race with each other, even when they conflict. D1
Read-modify-write (RMW)
Simple words: reading a value, changing it and writing it back as one atomic step. Analogy: the click itself: read 41, write 42, nothing in between. Precise: an atomic operation such as fetch_add, exchange or compare_exchange that always reads the latest value in the object's modification order and writes the new value with no other write in between. D1
Compare-and-swap (CAS)
Simple words: "change this to X, but only if it is still Y". Analogy: you set the counter to 50 only if it still shows the 42 you saw. Precise: an RMW that compares an atomic object with an expected value and, if equal, stores a desired value; otherwise it loads the current value into the expected variable. In C++: compare_exchange_strong and compare_exchange_weak (which may fail spuriously). D1
Lock-free (atomic type)
Simple words: the atomic is done with special processor instructions, not with a hidden lock. Analogy: the counter is a real mechanical counter, not a clerk behind a door. Precise: std::atomic<T>::is_always_lock_free (compile time) and is_lock_free() (run time) report whether operations on the type never use a lock in the implementation; large types may be implemented with a lock. D1
Spinlock
Simple words: a lock where a waiting thread keeps trying in a loop instead of sleeping. Analogy: a cook who stands at the cabinet trying the handle again and again. Precise: a mutual-exclusion lock built from an atomic flag; acquisition busy-waits on the flag; cheap for very short critical sections when the owner is running on another core, wasteful otherwise. D3
Atomicity violation
Simple words: a sequence of steps that must happen together but can be interrupted between steps. Analogy: look at the seat counter, see 999, turn away, then click: someone else clicked in between. Precise: a race condition (F2-35) in which a code region assumed to be indivisible is interleaved with conflicting operations of another thread; it can occur with atomic variables only, so it is not a data race and race detectors do not report it. D5
False sharing
Simple words: threads slow each other down by writing different variables that sit in the same cache line. Analogy: two cooks writing on different lines of the same notepad keep grabbing the pad from each other. Precise: HW203 term (F1-36): the coherence protocol moves cache lines, not variables, so independent writes to one line make it move between cores. D4

Layer 1 — the kid explanation

A mutex (F2-36) makes other threads wait while one thread does several steps. For a single number there is a cheaper way. The processor has special instructions that read a number, change it and write it back in one go, so that no other core can sneak in between. C++ gives you these instructions through std::atomic.D1

An atomic counter is like the tally counter at the door: every click counts, even when two people click together.R1 But each click is separate. If you look at the counter, think, and then click, someone else may click while you think. Atomics protect one step, not a plan made of several steps.R8

There is also a clever atomic step called compare-and-swap: "change the number to 50, but only if it still says 42". If someone changed it in the meantime, nothing happens and you are told the new number, so you can think again and retry.D1

Layer 2 — the student explanation

The basic operations

std::atomic<T> (header <atomic>) wraps a value of a type T that can be copied byte by byte (the standard states the exact requirement). Accesses through it are atomic, and conflicting atomic accesses are never a data race.D1 Listing 1 uses each basic operation once and then lets four threads click one counter 250,000 times each:

OperationDoesReturns
x.load()readsthe value
x.store(v)writes vnothing
x.exchange(v)writes v (RMW)the value before
x.fetch_add(n), fetch_sub, fetch_and, fetch_or, fetch_xorRMW arithmetic (integers; fetch_add/fetch_sub also for pointers and, since C++20, floating point)the value before
x.compare_exchange_strong(expected, desired)if x == expected, writes desired; else copies x into expectedtrue if it wrote
x.wait(old), notify_one(), notify_all()C++20: block until the value is no longer oldnothing

The operators are shortcuts: ++x is x.fetch_add(1) + 1, x = 0 is x.store(0), and using x as a value is x.load().D1 The danger of the shortcuts: x = x + 1 compiles, but it is a load followed by a separate store, not one RMW, so it loses updates exactly like F2-35's plain counter. Every operation also takes an optional memory order argument (std::memory_order_relaxed, acquire, release, …); without it the order is seq_cst, the strongest one. This chapter uses the default except in the spinlock; F2-39 explains the orders.D1

The output shows the arithmetic of the single-thread part (store 5, fetch_add(3) returns 5, exchange(100) returns 8) and a final count of exactly 1,000,000; the ThreadSanitizer build reports nothing.R1 R2

Compare-and-swap

Not every update is an addition. To keep a running maximum, you must read the value, decide, and write only if your decision is still valid. That is what compare_exchange is for. Listing 2 first shows one success and one failure: with the value at 20, a CAS that expects 10 fails, leaves the value alone and overwrites expected with 20.R3 Then updateMax wraps the CAS in the loop of Figure 2: if another thread raised the maximum in between, the CAS fails, current now holds the newer value, and the condition candidate > current is re-evaluated. Four threads offering all scores from 0 to 99,999 end with 99,999.R3

compare_exchange_weak may fail even when the values are equal (a "spurious failure"); on some processors it maps to a cheaper instruction sequence. Use weak inside a loop, which retries anyway, and strong for a single attempt.D1 D2 A CAS compares the object representation, the bytes; padding bytes inside a struct and floating-point values such as -0.0 and +0.0 can make "equal" values compare unequal, or unequal ones equal.D1

Lock-free or not

The standard allows std::atomic<T> for any byte-copyable T, but the hardware only has atomic instructions up to a certain size. Larger atomics may be implemented with a hidden lock. Listing 3 asks the compiler: bool, int, long and double are always lock-free on this x86-64 build; a 16-byte struct and a 24-byte struct are not.R4 Asking at run time with is_lock_free() needs a function from GCC's support library libatomic: Listing 5 does not link with the course's standard command ("undefined reference to __atomic_is_lock_free"), and with -latomic it reports false for the 16-byte struct.R5 R6 The only type guaranteed lock-free everywhere is std::atomic_flag, which has test_and_set(), clear() and, since C++20, test(); since C++20 it also starts clear when default-constructed.D1

Note

Lock-free atomics (this section) are not the same as lock-free algorithms (F2-42). A lock-free atomic type means a single operation needs no lock; a lock-free algorithm is a whole data structure whose progress does not depend on any one thread.

A spinlock from an atomic flag

Listing 4 builds a lock: lock() sets the flag with test_and_set and loops while the flag was already set; unlock() clears it. Because it has lock() and unlock(), std::lock_guard works with it. Four threads increment a plain long 100,000 times each under it, the result is exactly 400,000, and ThreadSanitizer is silent.R7 The inner loop at line 14 waits by reading the flag, not by writing it: a read can be served from the waiting core's own cache, while a failed test_and_set is a write that pulls the cache line away from everyone (F1-36).D3 D4

A spinlock is the right tool only when critical sections are very short and the lock holder is guaranteed to be running. In user space neither is guaranteed: if the holder is preempted by the operating system, the waiters burn whole time slices spinning. Prefer std::mutex, whose waiters sleep; spinlocks belong in kernels, where interrupts can be disabled while one is held (curriculum B10).D3 S1

One step is atomic; two steps are not

The forensic lab's program uses only atomic operations, so ThreadSanitizer correctly reports no data race. It still sells more seats than exist: the check sold.load() < kSeats and the purchase sold.fetch_add(1) are two separate atomic steps.R8 R9 This is an atomicity violation. The fixes: make the decision and the update one RMW (a CAS loop, or fetch_add first and undo if over the limit), or protect the whole sequence with a mutex. If an invariant involves two or more variables, a mutex is almost always the right answer: atomics cannot update two variables in one step.D2

Layer 3 — the engineer's depth

Modification order. Every atomic object has a single total order of all writes to it, the modification order, which all threads agree on. An RMW always reads the last value before its own write in that order; that rule is what makes fetch_add lose nothing, even with memory_order_relaxed.D1 Agreement on one object's order does not mean agreement on the order between different objects: that is what memory orders control (F2-39).

Two results held in every run of this build: an uncontended atomic increment cost several nanoseconds against well under one for a plain register increment; and four threads on one counter cost each thread several times more again, because the counter's cache line must move to each core for every increment.R10 The false-sharing rows were less clear: with four threads, counters packed side by side were slower than the same counters 64 bytes apart in each run, but the size of the gap changed a lot between runs (from more than two times to about 20 %), and with two threads there was no difference.R10 std::hardware_destructive_interference_size (C++17, header <new>) is the compiler's suggested minimum distance to avoid false sharing; it printed 64 bytes.D1


Not verified — check before relying on this
The false-sharing part of this measurement is not a clean demonstration and was not explained in this build: the 2-thread packed and padded runs took the same time; per-thread times for private padded counters rose with the number of threads, although those threads share nothing; and in one run four threads with private padded counters were slower than four threads sharing one counter. Possible causes are that the container's 4 virtual CPUs are shared with other jobs, may be hyper-threads of fewer physical cores, or that threads were moved between CPUs during a run; none of these was checked. Repeat the measurement with threads pinned to CPUs (taskset or pthread_setaffinity_np) on a dedicated machine before drawing conclusions; F1-36 (HW203) gives the expected effect.


Contention collapse and the ABA problem. A CAS loop under heavy contention can retry many times; total throughput may fall as threads are added, and no thread is guaranteed to finish in a bounded number of tries (lock-free, not wait-free; F2-42).D3 And a CAS only checks that the value is equal to what you saw, not that it was never changed: if it went from A to B and back to A, the CAS succeeds. For counters this is harmless; for pointers it is the ABA problem of F2-42.D2


volatile is not atomic. In C++, volatile means "every access is a visible side effect" (for memory-mapped device registers, SP101/B-milestones); it gives neither atomicity nor ordering between threads, and a volatile counter shared by threads is still a data race.D1 D6


Atomic references and waiting. C++20 adds std::atomic_ref<T>, which performs atomic operations on an ordinary object for a period during which all accesses go through atomic_ref, and wait/notify on atomics, a lighter alternative to a condition variable for "wait until this value changes".D1



How the hardware actually does it


On x86-64, g++ turned Listing 1's operations into the instructions below (counted from the compiler's assembly output; loads are ordinary mov instructions and are not counted):R11




fetch_add whose result is unused became lock addq; the one whose result is printed became lock xaddq (exchange-and-add, returns the old value); exchange and the default sequentially consistent stores became xchgq (on x86, xchg with memory is locked even without a prefix).R11 D8 A compare-and-swap uses lock cmpxchg. The LOCK prefix makes the read and write of the instruction one indivisible operation; on modern processors this is done by holding the cache line in the Modified state for the whole instruction (a "cache lock") rather than locking the memory bus, which is why contention on one line is what costs time.D8 D4 Arm processors use a load-exclusive/store-exclusive pair that retries if another core touched the line, or, since Armv8.1, single atomic instructions such as LDADD and CAS.D10


Not verified — check before relying on this
The statements about cache locking versus bus locking, and about xchg being implicitly locked, come from memory of the Intel SDM (Volume 3, "Locked atomic operations", and the XCHG instruction entry); the Arm statements come from memory of the Arm Architecture Reference Manual. Neither document was opened, and no Arm atomic code was compiled for this chapter (F2-39 compiles loads and stores for AArch64). Check both manuals; to see the Arm instructions, compile Listing 1 with aarch64-linux-gnu-g++ -O2 -S, with and without -march=armv8.1-a.



Worked example


Trace updateMax (Listing 2) when two threads interfere. The maximum best is 70. Thread A offers 90, thread B offers 80.


    

  1. A: current = best.load() → 70. 90 > 70, so A will try a CAS.
    2. 

  2. B: current = best.load() → 70. 80 > 70. B's CAS(70 → 80) runs first and succeeds: best is 80.
    3. 

  3. A: CAS(70 → 90) fails, because best is 80, not 70. The CAS writes 80 into A's current.
    4. 

  4. A: loop condition: 90 > 80 is true, so A tries CAS(80 → 90). It succeeds: best is 90.
    5. 

  5. If instead A had offered 75: after step 3, 75 > 80 is false, the loop ends, and best stays 80. Correct, because 80 is the larger.
    6. 



Count the RMWs: three CAS attempts, one failed. A version that did if (candidate > best.load()) best.store(candidate); would, in the same interleaving with A offering 75, overwrite 80 with 75: an atomicity violation like the forensic lab's. Where the analogy breaks


    

  1. A tally counter only adds one. Atomics also exchange, compare-and-swap, and work on pointers and flags; and their memory order controls what other data becomes visible with them (F2-39). The counter picture covers only the indivisibility (registered limit, guide 8.1: memory orders add rules about what others see before and after the click).D1
    2. 

  2. Two people pressing one counter do not slow each other down. Two cores updating one atomic do: the cache line must travel between them on every update, and the measured cost per increment grew several times with four threads.R10
    3. 

  3. A tally counter is always "lock-free". An std::atomic<T> of a large type may hide a lock (Listing 3).R4
    4.

Summary


    

  • std::atomic<T> operations are indivisible and never form data races with each other.
    • 

  • RMW operations (fetch_add, exchange, compare_exchange) read and write in one step; x = x + 1 is two steps.
    • 

  • A CAS loop updates from a snapshot and retries with fresh data on failure.
    • 

  • Small atomics are lock-free; large ones may hide a lock and need libatomic; check with is_always_lock_free.
    • 

  • Atomics protect one step on one variable. Check-then-act on atomics is an atomicity violation that ThreadSanitizer cannot see.
    • 

  • Atomic operations cost more than plain ones, and much more under contention or false sharing.
    • 

  • Spinlocks suit kernels with very short critical sections; in user space prefer std::mutex.
    •

Forensic lab answer key


Observation: the optimised runs issued a few tickets over 1,000 (the exact counts are in the output and change from run to run), and the ThreadSanitizer run printed no warning (whether that run also oversold changes from run to run); in every run the counter equals the number of tickets, so no increment was lost: the counter works. Data race: none; all accesses to sold are atomic. Interleaving: sold is 999; booth 1 loads 999 (line 13), 999 < 1000, then yields (line 14); booth 2 loads 999, passes the check, yields; booth 1 fetch_add → 1,000; booth 2 fetch_add → 1,001. Bound: at most 1,000 + 7: each of the other seven booths can be between check and add when the last seat goes, because each booth has one call in progress at a time. Fix 1: int n = sold.load(); while (n < kSeats) { if (sold.compare_exchange_weak(n, n + 1)) return true; } return false;. Fix 2: a std::mutex around the check and the add (with a plain int). For this single counter the CAS loop is short and lock-free; once the booking also writes the seat's name to a table, the invariant spans two pieces of data and the mutex is the right choice. Prevention: in review, flag every load() of an atomic whose result decides a later write. How the evidence was made: oversell.cc, built and run by the lab's run.sh in this build (R8, R9); the yield() stands in for the log line and makes the window between check and add wide enough to show in a few runs.
