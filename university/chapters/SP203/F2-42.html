Story hook

Analogy

The pass between kitchen and dining room has a peculiar rule on Friday nights. The chef has a chalk mark showing where she will put the next plate; the waiter has a chalk mark showing where he will take the next one. The chef only ever moves her mark, after the plate is down. The waiter only ever moves his, after the plate is gone. Nobody needs a key, nobody waits for anybody to hand one over, and the pass flows faster than it ever did with the bell and the key.

It works because there are exactly two people and each owns one mark. Add a second waiter, and the two waiters could reach for the same plate. Then they need another trick: "I take it only if it is still the plate I saw" — compare-and-swap.

And that trick has a trap. On Friday, a waiter saw plate X on top of the stack, turned to pick up a tray, and came back. Plate X was still on top, so he took it and pointed the stack at the plate he remembered under X. But in those seconds, X had been taken, the plate under it reused for a different table, and X put back. The forensic lab of this chapter is that plate.

What you will be able to do

  • Define blocking, obstruction-free, lock-free and wait-free progress, and classify a given algorithm.
  • Read and justify a single-producer/single-consumer ring buffer with acquire/release counters.
  • Read a Treiber stack and explain each compare-and-swap and memory order.
  • Explain the ABA problem and the memory-reclamation problem, and name the standard remedies.
  • Decide, with a measurement, whether a lock-free structure is worth its complexity in a given case.
Jargon box
Lock-free (algorithm)
Simple words: some thread always makes progress, even if others are paused at any moment. Analogy: if one waiter freezes mid-reach, the others can still take plates. Precise: a progress guarantee: in any execution, if threads keep taking steps, some operation completes in a finite number of steps; no thread's suspension can block the others (unlike a lock, whose holder can be descheduled). D15
Wait-free
Simple words: every thread finishes its operation in a bounded number of its own steps. Analogy: each cook has their own mark and never retries. Precise: a stronger progress guarantee than lock-free: every operation completes in a bounded number of steps of the calling thread, whatever the others do. D15
Obstruction-free
Simple words: a thread finishes if it is left to run alone for long enough. Analogy: a waiter gets his plate if nobody else reaches at the same time. Precise: every operation completes if its thread eventually runs in isolation; weaker than lock-free (contending threads may keep undoing each other: livelock). D15
SPSC ring buffer
Simple words: a circular buffer for exactly one writer thread and one reader thread, without locks. Analogy: the pass with the chef's mark and the waiter's mark. Precise: a bounded queue in which the producer alone writes the tail index and the consumer alone writes the head index; each publishes progress with a release store and reads the other's with an acquire load. D2
Treiber stack
Simple words: a linked-list stack where push and pop change the top pointer with compare-and-swap. Analogy: "I take the top plate only if it is still the one I saw". Precise: the lock-free LIFO stack published by R. K. Treiber (1986); push and pop retry a CAS on the head pointer. D16
ABA problem
Simple words: a value changes from A to B and back to A, and a compare-and-swap cannot tell. Analogy: plate X is on top, gone, and back on top; the waiter thinks nothing happened. Precise: a CAS succeeds because the location holds the expected value, although the state it stood for has changed in between (for example because a node was freed or reused and its address appears again). D2
Safe memory reclamation
Simple words: deciding when a removed node can be freed, given that another thread may still be reading it. Analogy: you may wash a plate only when no waiter is still looking at it. Precise: schemes such as hazard pointers, epoch-based reclamation and read-copy-update (RCU) that defer freeing until no thread can hold a reference; without one, lock-free structures with removal must leak or risk use-after-free and ABA. D3 D17

Layer 1 — the kid explanation

With a lock, if the thread holding it is paused (the operating system can pause a thread at any moment), everyone who needs the lock waits too. Lock-free code avoids that: threads never wait for each other; they use atomic operations (F2-38) and retry if someone else got there first.D15

The easiest case is one writer and one reader. Each keeps its own counter and only reads the other's, like two chalk marks on the pass. This can be very fast.R4 With more threads, you need compare-and-swap loops, and two hard problems appear: the ABA problem (something changed and changed back, and you cannot tell) and the question of when it is safe to throw away a piece of memory that another thread might still be looking at.D2

Lock-free code is hard to get right and hard to test. Use a tested library when you can, and a mutex when you are not sure.D6

"Lock-free" in this sense is about the algorithm, not about F2-38's is_lock_free (which says only that one atomic operation needs no hidden lock).D15 Lock-free does not mean faster: a CAS loop under heavy contention can retry many times, and a mutex that puts waiters to sleep can give higher throughput. The guarantee is about progress when threads are delayed, which matters in kernels, real-time systems and signal handlers.D3

The SPSC ring buffer

Listing 1's SpscRing is safe for exactly one producer thread and one consumer thread. The counters head_ and tail_ only grow; a slot index is the counter modulo the capacity (a power of two, so & mask_), and the number of stored items is tail − head (see the worked example).D2 The memory orders follow F2-39's message-passing pattern twice:

  • producer: write the slot (line 22), then tail_.store(…, release) (line 23); consumer: tail_.load(acquire) (line 30), then read the slot (line 34). So the slot's contents happen-before the consumer's read.
  • consumer: read the slot, then head_.store(…, release) (line 35); producer: head_.load(acquire) (line 18) before overwriting that slot. So the consumer's read happens-before the producer's next write of the same slot.
  • Each thread reads its own counter with relaxed (lines 17 and 29): only it writes that variable, so it always sees its own last write.

The two counters are 64 bytes apart (alignas(64), lines 42–43), so the producer's writes to tail_ do not falsely share a cache line with the consumer's writes to head_ (F2-38). The test moves 1,000,000 numbers and checks that all arrive in order; it passes in the course build and under ThreadSanitizer, which understands acquire/release.R1 R2

The Treiber stack

With several threads on each side, no variable has a single writer, so updates need CAS (F2-38's Figure 2). Listing 2's push sets the new node's next to the current top and tries CAS(top: next → node); on failure, compare_exchange_weak has loaded the new top into n->next, so the loop retries with fresh data. pop reads the top and tries CAS(top: old → old->next). The push CAS uses release on success so that the node's contents are published with the pointer; the pop uses acquire so that the popped node's contents are visible.D2 Four threads pushing 50,000 nodes each and popping after every second push end with every node popped exactly once (count and checksum), under ThreadSanitizer as well.R3

Listing 2 is honest about the hard part it skips: it never frees a popped node while threads run (all nodes are owned by a vector and freed at the end). In a real stack, a thread in pop may have read old and be about to read old->next when another thread pops old and deletes it: a use-after-free. And if the memory is reused for a new node pushed at the same address, the first thread's CAS can succeed wrongly: the ABA problem of the forensic lab.D2 R5

Remedies for ABA and reclamation

  • Tagged pointers: pair the pointer with a counter that increments on every change, and CAS both together (a double-width CAS, or spare pointer bits). ABA then needs the counter to wrap around. F2-38's lock-free query showed that a 16-byte atomic is not lock-free with this build's default flags.D2 R6
  • Hazard pointers: each thread publishes the pointers it is about to dereference; a node is freed only when no hazard pointer refers to it.D17
  • Epoch-based reclamation and RCU: readers announce that they are in a read section; removed nodes are freed after every reader that might have seen them has left. RCU is used heavily in the Linux kernel.D3
  • Reference counting (std::atomic<std::shared_ptr<T>> in C++20), at a cost in speed; libstdc++'s implementation may itself use a lock.D1

Is it worth it? Measure. ring_bench.cc moves 5,000,000 integers from one producer to one consumer through SpscRing and through F2-37's BoundedQueue, both with 1,024 slots (median of five runs):R4



In every run of this build the lock-free ring was faster than the mutex queue, by a factor that varied between about two and more than ten from run to run on this shared machine. Note what the comparison does and does not show: the ring's threads spin when full or empty, burning a core each, while the queue's threads sleep; the ring supports exactly one producer and one consumer; and the numbers come from a shared machine. For a pipeline stage with one producer, one consumer and both threads otherwise busy, the ring is a good choice; for a general work queue, it is not even applicable.R4


Linearisability. The usual correctness condition for concurrent objects: each operation appears to take effect at one instant between its call and its return, its linearisation point, and the resulting order is a legal sequential history. For the Treiber stack, the linearisation point of a successful push or pop is its successful CAS; for an empty pop, the load that saw nullptr.D15 Arguing correctness means naming those points and showing the state invariant holds before and after each.


Testing is weaker here. ThreadSanitizer checks the executions it sees for data races; it does not check for ABA or for lost nodes, and the dangerous interleavings may be rare. Lock-free code needs (a) a written argument with linearisation points and happens-before edges, (b) stress tests with checksums like Listing 2's, (c) deterministic replays of known-bad interleavings like the forensic program, and ideally (d) model checking (for example with CDSChecker or GenMC, or TLA+ for the algorithm), which this course does not cover.D3

How the hardware actually does it


Lock-free algorithms rest on the hardware's atomic read-modify-write instructions (F2-38): on x86-64, lock cmpxchg for CAS (and lock cmpxchg16b for 16-byte CAS, on processors that have it); on AArch64, load-exclusive/store-exclusive loops or, since Armv8.1, the CAS instruction.D8 D10 Their cost is the cost of getting the cache line in the Modified state: under contention every CAS on the stack's top moves that line between cores, which is why a lock-free stack does not scale better than a well-designed locked one under heavy contention.D3 The SPSC ring avoids RMW entirely: it uses only loads and stores with acquire/release (plain mov on x86-64, ldar/stlr on AArch64, F2-39) and keeps the two counters on separate cache lines. Its remaining cost is each side reading the other's counter, which moves one cache line per check; production rings cache the other side's counter locally and re-read it only when the ring seems full or empty.D2 On load-exclusive/store-exclusive machines, a store-exclusive fails if the line was touched in between, even if the value came back: such machines are not vulnerable to ABA on a single word in the same way, which is one reason ABA behaviour can differ between architectures.D10


Not verified — check before relying on this
The instruction details (cmpxchg16b availability, Armv8.1 CAS, exclusive-monitor behaviour) are from memory of the Intel SDM and the Arm ARM, not opened in this build, and no lock-free code was compiled for AArch64 in this chapter. The claim about exclusive monitors and ABA applies to algorithms written directly with load-linked/store-conditional; C++ compare-exchange on Arm still compares values, so C++ code has the ABA problem on every architecture. Worked example


The SPSC ring's counters never reset. What happens when an unsigned 32-bit counter wraps around from 4,294,967,295 to 0? Take capacity 8, mask 7.


    

  1. head 0, tail 3: items = 3 − 0 = 3; next read slot 0 & 7 = 0; next write slot 3.
    2. 

  2. head 5, tail 13: items = 8 = capacity, so the ring is full; the next write slot 13 & 7 = 5 is the slot the consumer reads next, exactly the slot that must not be overwritten.
    3. 

  3. head 4,294,967,294, tail 4,294,967,295: items = 1; slots 6 and 7.
    4. 

  4. head 4,294,967,294, tail 2 (tail has wrapped): unsigned subtraction is modulo 232, so items = 2 − 4,294,967,294 + 232 = 4. The slots also stay consistent because 232 is a multiple of the capacity: 4,294,967,294 & 7 = 6, and the four items occupy slots 6, 7, 0, 1; the next write slot is 2.
    5. 

  5. Conclusion: the design is correct across wrap-around as long as the capacity is a power of two (so it divides 232 or 264) and the counters are unsigned (signed overflow would be undefined behaviour). SpscRing uses std::size_t, 64 bits here, so wrap-around takes centuries; the 32-bit check shows the argument holds anyway.

Where the analogy breaks


    

  1. Chalk marks are seen at once; counters are not. The waiter sees the chef's mark move the moment she moves it. A counter's new value reaches the other core later, and without release/acquire the slot's contents may arrive after the counter (F2-39).D1
    2. 

  2. A waiter who looks away can still see that the plate changed. A CAS sees only the bits of one word; if the same address comes back, it cannot tell (ABA).R5
    3. 

  3. Plates do not vanish while you look at them. Memory can: another thread may free a node you are reading. The analogy has no counterpart for reclamation, which is the hardest part of real lock-free code.D17
    4.

Summary


    

  • Lock-free means some thread always makes progress; wait-free means every thread does. Neither means "faster".
    • 

  • A single-producer/single-consumer ring needs only release/acquire loads and stores: each side owns one counter.
    • 

  • Multi-writer structures need CAS loops, like the Treiber stack.
    • 

  • CAS cannot see ABA; node reuse and freeing make it real.
    • 

  • Safe memory reclamation (hazard pointers, epochs, RCU) is the hard part of lock-free code.
    • 

  • Verify with a written argument, stress tests with checksums and deterministic replays; measure against a locked baseline.

Forensic lab answer key


A's view: A read top = X and X->next = Y (lines 36–37) and planned CAS(top: X → Y). B's operations: pop X → [Y, Z]; pop Y and reuse the node as "bread, table 9" with next = nullptr → [Z]; push X again (X's next is now Z) → [X, Z]. CAS: compares the pointer value in top with A's expected: both are the address of X, so it succeeds and stores A's stale next, the address of Y. Damage: the stack is now [Y reused: bread, table 9]; Z (tea) is lost from the stack, and table 9's bread node is now also on the order stack, so it can be served twice or freed while still in use. The correct result after A's pop was [Z tea]. Why recycling matters: without reuse, X could not come back to the top after being popped, so a CAS that sees X really means "nothing changed"; recycling made the same address stand for different states. Fix: a tag that increments on every successful CAS of top (A's expected tag is older than the current one, so its CAS fails and it retries with fresh data), or hazard pointers / epochs that forbid recycling X and Y while A may still hold them. Why nobody could reproduce it: A must be paused between line 37 and its CAS long enough for B to do three operations; that window is a few instructions wide. How the evidence was made: aba_replay.cpp, run by run_lab.sh in this build (R5); "thread A" and "thread B" are the two halves of one thread's code, so the interleaving is the same in every run. The weekly lost order is the scenario, not an observation.
