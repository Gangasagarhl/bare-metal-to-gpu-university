Story hook

Analogy

The restaurant's saffron is precious, so it lives in a cabinet with one key. The rule is simple: you may open the cabinet only while you hold the key; when you are done you hang the key back on its hook. If the key is not on the hook, you wait.

Inside the cabinet there is also a little stock list. When Joon takes saffron, he crosses out one jar and writes the new count. For a moment, while he is between "take the jar" and "fix the list", the cabinet and the list disagree. That is fine, because nobody else can look: Joon has the key. By the time he hangs it back, the list is right again.

One night Joon is called away in a hurry and takes the key home in his pocket. The next morning nobody can open the cabinet, all day. Nothing is broken; everyone is waiting for a key that will never come back. Keep both halves of this story in mind: the key makes sharing safe, and a key that is not returned stops the kitchen.

What you will be able to do

  • Protect shared data with std::mutex and RAII lock objects (std::lock_guard, std::unique_lock, std::scoped_lock), and say exactly which data each mutex protects.
  • Explain why a mutex removes data races (happens-before from unlock to the next lock) and how it preserves an invariant.
  • Use std::shared_mutex for many readers and rare writers, and know when it does not help.
  • Measure lock contention and reduce it by shrinking critical sections or by local accumulation.
  • Diagnose a mutex that was never unlocked, from the program's own log.
Jargon box
Mutex
Simple words: a lock that only one thread can hold at a time. Analogy: the single key to the spice cabinet. Precise: a mutual-exclusion object; lock() blocks until the calling thread owns it, unlock() releases it; an unlock of a mutex synchronises with the next successful lock of the same mutex, so it creates happens-before (F2-35). std::mutex is in <mutex>. D1
Critical section
Simple words: the piece of code that runs while the lock is held. Analogy: the time between taking the key and hanging it back. Precise: a region of code that accesses shared data and must not be executed by more than one thread at a time; a mutex enforces this by being held for the whole region. D7
Invariant (of shared data)
Simple words: a fact about the data that is true whenever nobody holds the lock. Analogy: "the stock list matches the jars" whenever the key is on its hook. Precise: a condition (MA102, F2-09) that may be broken temporarily inside a critical section but must hold at every lock and unlock; it is what the mutex really protects. D2
std::lock_guard
Simple words: an object that locks a mutex when created and unlocks it when it goes away. Analogy: a key on a spring that flies back to its hook when you leave the room. Precise: an RAII class template whose constructor calls lock() and whose destructor calls unlock(), also when the scope is left by return or by an exception. D1
std::unique_lock
Simple words: a more flexible lock holder that can unlock early, relock, or be moved. Analogy: a key you may hang back early and take again. Precise: an RAII lock owner that may or may not own its mutex at a given moment; supports deferred locking, try_lock, timed locking, unlock()/lock() and move; required by std::condition_variable (F2-37). D1
std::scoped_lock
Simple words: a lock holder that can take several mutexes at once without deadlocking. Analogy: taking the spice key and the fridge key together, in a way that never leaves two cooks each holding one. Precise: a C++17 RAII class template that locks zero or more mutexes using the deadlock-avoidance algorithm of std::lock and unlocks them in its destructor (F2-40). D1
Shared mutex (reader–writer lock)
Simple words: a lock that many readers may hold together, but a writer only alone. Analogy: anyone may read the menu board at once; changing it needs everyone to step back. Precise: std::shared_mutex (<shared_mutex>) has exclusive ownership (lock, used through std::unique_lock) and shared ownership (lock_shared, used through std::shared_lock); shared owners exclude exclusive ones. D1
Lock contention
Simple words: threads waiting for the same lock instead of working. Analogy: a queue of cooks in front of the key hook. Precise: the situation in which several threads try to acquire the same lock at the same time; contended acquisitions cost far more than uncontended ones and serialise the critical sections. D3

Layer 1 — the kid explanation

In F2-35 two threads changed the same number and lost updates. The fix is a rule: only one thread at a time may touch that number. A mutex is how a program writes down that rule. It works like the single key to the spice cabinet.D1

Before touching the shared data, a thread locks the mutex: it takes the key. If another thread already has it, this thread waits. When it is done, it unlocks: it hangs the key back. The code in between is called the critical section.D7

Two habits make mutexes safe. First, never take the key by hand if you can avoid it: let an object called a lock guard take it for you. The guard hangs the key back automatically when it goes away, even if something goes wrong.D1 Second, keep the critical section short. While one cook holds the key, every other cook who needs it stands still.R6

Layer 2 — the student explanation

What a mutex guarantees

A std::mutex has two states, unlocked and owned by one thread. lock() blocks until the calling thread becomes the owner; unlock(), called by the owner, releases it; try_lock() tries once without blocking and returns whether it succeeded.D1 Two guarantees make it useful:

  • Mutual exclusion: at most one thread owns the mutex at a time, so critical sections protected by the same mutex never overlap (Figure 1).
  • Ordering: an unlock() synchronises with the next lock() that obtains the mutex, so everything the previous owner wrote before unlocking happens-before everything the next owner does after locking.D1 That is exactly the happens-before edge that F2-35's definition asks for: accesses to shared data made only while holding the same mutex never form a data race.

Rules that the standard leaves as undefined behaviour: unlocking a mutex you do not own, locking a std::mutex you already own (it is not recursive), and destroying a mutex that is still locked.D1 std::recursive_mutex allows the same thread to lock again, but needing it usually signals a design in which a function does not know whether its caller already holds the lock.D2

A mutex protects data, not code

The mutex itself knows nothing about the variables it protects. The association exists only in your head, so write it down next to the members, as Listing 1 does (std::mutex mutex_; // protects balance_), and make every access to those members hold it.D6 F2-35's forensic lab showed what happens when one access forgets. The safest structure is a class whose private data can only be reached through member functions that lock: users of the class cannot forget.D2 The danger that remains is returning a pointer or reference to the protected data out of the critical section: then callers touch it without the lock.

What the mutex really protects is an invariant. In Listing 1 the invariant is "the sum of all balances is 8,000". Inside transfer, between lines 16 and 17, the invariant is false (money has left one account and not arrived in the other). No other thread can observe that moment, because every function that reads balances also takes the lock. The run prints the same total before and after 400,000 concurrent transfers, and the ThreadSanitizer build is clean.R1 R2

Lock objects: RAII for locks

Calling lock() and unlock() by hand has the same problem as new and delete: every path out of the function must unlock, including return statements and exceptions. Listing 2 throws an exception inside a critical section twice: once with manual locking (the mutex stays locked, as another thread's try_lock() confirms) and once with std::lock_guard (the destructor unlocked it during stack unwinding).R3 Use the lock classes:

ClassUse it whenNotes
std::lock_guard<M>one mutex, locked for the whole scopesimplest; cannot unlock early
std::scoped_lock<M…>one or several mutexes for the whole scopeC++17; locks several without deadlock (F2-40); the default choice in new code
std::unique_lock<M>you must unlock early, relock, lock later, try or time out, or hand the lock to a condition variablemovable; slightly larger (tracks ownership)
std::shared_lock<M>shared (reader) ownership of a std::shared_mutexListing 3

All of them are in <mutex> except std::shared_lock and std::shared_mutex, which are in <shared_mutex>.D1 A classic mistake with all of them is forgetting the variable name: std::lock_guard<std::mutex>(m); does not create a guard for the scope; depending on the context it declares a new variable called m or creates a temporary that unlocks at the end of the statement. Always write a name: std::lock_guard<std::mutex> guard(m);.D2

Many readers, few writers

A std::shared_mutex lets any number of threads hold it in shared mode, or one thread in exclusive mode.D1 Listing 3 keeps a price list that four waiter threads read 200,000 times while one manager thread changes a price 1,000 times: the readers use std::shared_lock, the writer std::unique_lock, and the ThreadSanitizer build is clean.R4 A reader–writer lock is not automatically faster than a plain mutex: shared locking still writes to the lock's internal state, so very short read sections can be slower than with a plain mutex. Measure before choosing it.D3

Contention and how to reduce it

An uncontended lock and unlock is cheap; a contended one is expensive, because a waiting thread may be put to sleep and woken by the operating system, and because the cache line holding the mutex moves between cores (F1-36).D3 D4 The measurement program contention.cc increments one counter under one shared mutex, with 1, 2 and 4 threads, and compares it with counting in a local variable and adding to the shared total once under the lock:R6



The time shown is wall-clock time divided by the total number of increments, so if more threads helped, it would fall as threads are added. With one shared lock it did not fall in any run of this build: it stayed at tens of nanoseconds, or got worse, with 2 and 4 threads, because the increments are serialised by the lock. Counting locally and merging once stayed below one nanosecond per increment, around a hundred times cheaper; the exact ratio changed from run to run on this shared machine.R6 The techniques, from most to least effective: do the work outside the lock and hold it only to publish the result; give each thread its own data and merge (as here); split one lock into several (one per account, one per hash bucket), accepting the deadlock risks of F2-40; and only then consider lock-free structures (F2-42).D3



Layer 3 — the engineer's depth


Lock granularity. One lock for a whole data structure ("coarse-grained") is easy to get right and serialises everything; one lock per element ("fine-grained") allows parallelism but multiplies lock acquisitions and creates ordering problems when an operation needs two elements (transfers between two accounts, F2-40).D3 McKenney's design rule is to partition the data so that most operations need only one partition's lock; the curriculum's per-CPU data (B11) is the kernel version of the same idea.D3 S1


Amdahl's law for locks. The time spent inside a single lock is a serial part of the program. If each request holds the lock for c seconds, the lock can serve at most 1/c requests per second, no matter how many threads you add (Figure 2, the worked example).D3 Contention also lengthens c itself, because the lock's cache line has to move to each new owner, so real curves bend down before the ideal ceiling (compare the measured 2-thread and 4-thread rows above with the model).


Fairness and starvation. The standard does not promise that a waiting thread eventually gets the mutex in any particular order; a thread could in principle lose every race for the lock (starvation).D1 Ticket locks (curriculum B10 lists them) give first-come, first-served order at some cost. With std::shared_mutex, whether a steady stream of readers can starve a writer depends on the implementation.


Not verified — check before relying on this
Whether libstdc++'s std::shared_mutex (on top of the POSIX read–write lock) prefers readers or writers, and the exact fairness guarantees of pthread_mutex_lock on Linux, were not checked against documentation or measured in this build. Check the GNU C Library manual and the POSIX specification of pthread_rwlock_rdlock (writer-preference options), and measure with your own lab variant before relying on either.


Timed and try locks. std::timed_mutex adds try_lock_for and try_lock_until.D1 They are useful for diagnostics (the forensic lab's screen reports that it could not get the lock) and for back-off strategies, but a timeout is not a fix: if a lock is held for ever, waiting less only fails faster.


Lock-based design checklist (after the C++ Core Guidelines and Williams):D6 D2 name what each mutex protects; keep the mutex and its data in one class; never call unknown code (callbacks, virtual functions of user types) while holding a lock, because it may try to take the same or another lock; never return references to protected data; prefer std::scoped_lock; document lock order whenever two locks can be held together (F2-40).



How the hardware actually does it


A mutex is built from an atomic variable in memory. On Linux, glibc's mutex tries to change that word from "unlocked" to "locked" with one atomic read–modify–write instruction (F2-38); if that succeeds there is no system call at all. If it fails, the thread asks the kernel to sleep with the futex system call until the owner, on unlocking, wakes it.D9 F2-40's thread dump shows this path in real stacks: std::mutex::lock → ___pthread_mutex_lock → __GI___lll_lock_wait → futex_wait.R7 That is why an uncontended mutex costs about as much as an atomic operation, while a contended one costs a trip through the kernel scheduler. The atomic instruction itself must own the mutex's cache line in the Modified state (F1-36); when several cores fight for a lock, that line moves between them on every acquisition.D4 In your own kernel (curriculum B10) the same idea appears as a spinlock for short sections and a mutex with a wait queue for long ones.S1


Not verified — check before relying on this
The description of glibc's fast path (one atomic compare-and-swap, no system call when uncontended) and of the futex wait/wake protocol is given from memory of the futex(2) manual page and Drepper's paper "Futexes Are Tricky"; neither was opened. Only the function names in F2-40's real stack trace were observed. Check the Linux man-pages futex(2) and the glibc sources for the version in this build (Ubuntu 24.04) before relying on the details.



Worked example


A service handles requests with several threads. Each request spends 800 ns doing work that needs no lock, then 200 ns updating a shared table under one mutex. What is the best possible throughput for 1 to 8 threads?


    

  1. Without any lock, one thread finishes one request per 800 + 200 = 1,000 ns, that is 1 million requests per second; T threads could do T million per second (if there are T cores).
    2. 

  2. The lock is held 200 ns per request, and only by one thread at a time. So the lock can be "passed through" at most 1 / 200 ns = 5 million times per second.
    3. 

  3. The bound is the smaller of the two: T million for T ≤ 5, then 5 million for every larger T. Threads 6, 7 and 8 add only waiting.
    4. 

  4. To raise the ceiling, shrink the 200 ns (move work out of the critical section) or split the table into several independently locked parts.

Where the analogy breaks


    

  1. A key on a hook is visible; a forgotten unlock is not. A cook can see that the key is missing and ask who took it. A program has no "who holds this mutex" display; you need a debugger or the program's own diagnostics (forensic lab, F2-40's thread dump) to find the owner (registered limit, guide 8.1: forgetting to return the key blocks everyone forever).
    2. 

  2. The cabinet's walls protect the spices; a mutex has no walls. Any thread can read or write the "protected" data without taking the mutex: nothing stops it. The protection exists only if every access in the code follows the rule (F2-35's forensic lab).D1
    3. 

  3. Handing over a key is instant; handing over a mutex is not. When a contended mutex changes owner, the waiting thread may have to be woken by the operating system and the mutex's cache line must move between cores: the hand-over itself costs time (contention measurement).D4 R6
    4.

Summary


    

  • A mutex gives mutual exclusion and ordering: unlock happens-before the next lock of the same mutex.
    • 

  • It protects data only if every access holds it; write down which data each mutex protects and keep both private in one class.
    • 

  • What a mutex really protects is an invariant that may be broken only inside the critical section.
    • 

  • Always lock with RAII objects: std::scoped_lock or std::lock_guard; std::unique_lock when you need flexibility.
    • 

  • std::shared_mutex allows many readers or one writer; measure before assuming it is faster.
    • 

  • Time inside a lock is serial: it caps throughput. Shorten critical sections, use per-thread data, split locks.
    • 

  • A lock that is never released stops every thread that needs it; timed locks help diagnose, not fix.
    •

Forensic lab answer key


Observation: the last event before the failures is [till] rejected order: tea x0; the first failure is [screen] refresh 1: could not get ticketMutex within 200 ms, then all refreshes fail. Before that, all three refreshes of the first screen session succeeded. Owner: takeOrder locks at line 14; for quantity <= 0 it prints (line 16) and returns at line 17 without reaching unlock() (line 20). So the thread that called it — main, the till — still owns the mutex. Hypotheses: (H1) the till holds the lock for a long, slow operation — ruled out: each of the three tries waits 200 ms and they are 250 ms apart, so the lock was unavailable for at least 0.75 s while the till was doing nothing but waiting in join(); (H2) the lock was never released — confirmed by the code path. Why the till froze too: the next takeOrder on the same thread calls lock() on a std::timed_mutex it already owns: undefined behaviour, in practice a self-deadlock. Fix: replace lines 14 and 20 by std::lock_guard<std::timed_mutex> guard(ticketMutex); (or std::unique_lock if the print should happen outside the lock), so every return path unlocks. Test: call takeOrder with quantity 0, then check from another thread that try_lock_for succeeds; run under ThreadSanitizer. Prevention: forbid manual lock()/unlock() in code review (C++ Core Guidelines CP rule on RAII locks). How the evidence was made: forgot_unlock.cpp, run by run_lab.sh in this build (R8); the last line of main releases the mutex only so that the evidence program can end cleanly.
