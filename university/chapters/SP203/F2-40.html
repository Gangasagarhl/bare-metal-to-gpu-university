Story hook

Analogy

The restaurant now has two locked cabinets: spices and the wine fridge, each with one key. Joon is making a wine sauce. He takes the spice key first, measures pepper, then goes for the fridge key. Meanwhile Andrés, making mulled wine, took the fridge key first and now goes for the spice key.

Joon holds spices and waits for the fridge. Andrés holds the fridge and waits for spices. Each is waiting politely for the other to finish, and neither will ever finish. No one is doing anything wrong by their own rules; the kitchen has arranged its rules in a circle.

The fix is not a better cook. It is a kitchen rule: "if you need both keys, always take the spice key first". With that rule a circle cannot form. This chapter turns that rule, and the tools that check it, into code.

What you will be able to do

  • State the four conditions for deadlock and use them to argue that a design cannot deadlock.
  • Prevent lock-order deadlocks with a global lock order, std::scoped_lock or a lock hierarchy.
  • Build a lock-order checker that reports an inverted pair in a test build (curriculum B10).
  • Detect potential deadlocks with ThreadSanitizer before they happen.
  • Diagnose a real deadlock from a thread dump taken with GDB, by building the wait-for graph.
Jargon box
Deadlock
Simple words: threads waiting for each other in a circle, so none can ever continue. Analogy: two cooks, each holding one key and waiting for the other's. Precise: a state in which every thread of a set is blocked waiting for a resource held by another thread of the same set; with mutexes, a cycle in the wait-for graph. D7
Coffman conditions
Simple words: four things that must all be true for a deadlock to happen. Analogy: keys are exclusive; cooks keep one key while waiting; nobody snatches keys; and the waiting forms a circle. Precise: mutual exclusion, hold-and-wait, no preemption and circular wait (Coffman, Elphick, Shoshani, 1971); breaking any one prevents deadlock. D7 D12
Lock ordering
Simple words: a rule saying in which order locks must be taken when you need more than one. Analogy: "spice key before fridge key, always". Precise: a total (or partial) order on locks such that every thread acquires locks only in increasing order; it makes circular wait impossible. D2
Lock-order inversion
Simple words: one piece of code takes A then B, another takes B then A. Analogy: Joon takes spices then fridge; Andrés fridge then spices. Precise: two acquisition paths that take the same pair of locks in opposite orders; a potential deadlock even if it has never occurred, because a suitable interleaving produces a cycle. D5
Wait-for graph
Simple words: a drawing with an arrow from each waiting thread to the thread it waits for. Analogy: "Joon waits for Andrés, Andrés waits for Joon": a circle on paper. Precise: a directed graph whose vertices are threads and with an edge T → U when T is blocked on a resource held by U; a deadlock is a cycle in it. D7
Thread dump
Simple words: a snapshot of where every thread of a running program is, function by function. Analogy: a photo of the kitchen showing who is standing where and holding what. Precise: the call stack of every thread of a process, here taken with GDB by attaching to the process (gdb -p) and running thread apply all bt. D13
Livelock
Simple words: threads keep reacting to each other and so never get anything done, though none is blocked. Analogy: two cooks in a narrow corridor stepping aside the same way again and again. Precise: a state in which threads change state repeatedly in response to each other without making progress, for example when each releases its locks and retries in lock step. D3

Layer 1 — the kid explanation

A deadlock is when two or more threads wait for each other in a circle. Thread 1 has lock A and wants lock B; thread 2 has lock B and wants lock A. Neither lets go, so both wait for ever. The program does not crash and prints no error; it stops.R5

The simplest way to make deadlocks impossible is a rule about order: give every lock a number and always take locks in increasing order. Then nobody can hold a "big" lock and wait for a "small" one, so the circle can never close.D2 C++ also has a helper, std::scoped_lock, that takes several locks for you in a way that cannot deadlock.D1

And because people forget rules, you can make the computer check them. A small checker can remember which lock was taken before which, and shout when someone does it the other way round, even in a test where the deadlock did not happen.R2

Layer 2 — the student explanation

The four conditions

A deadlock needs all four Coffman conditions at once:D7 D12

ConditionMeaning with mutexesHow to break it
Mutual exclusiona mutex has one ownerrarely possible: use data that needs no lock (immutable, per-thread)
Hold and waita thread holds one lock while waiting for anothertake all locks at once (std::scoped_lock), or never hold a lock while acquiring another
No preemptionnobody can take a lock away from its ownertry_lock: on failure, release what you hold and retry (risk: livelock)
Circular waita cycle in the wait-for grapha global lock order; lock hierarchies

In practice, two remedies cover most code: a global lock order, and taking all needed locks in one step.

Fix 1: a global lock order

Give each lock a rank and acquire in increasing rank only. Listing 1's transferOrdered uses the account id: whichever account has the smaller id is locked first, regardless of the direction of the transfer. Two threads making 100,000 transfers each in opposite directions finish, the balances are unchanged, and ThreadSanitizer reports nothing.R1 The order must be total over everything that can be held together, and it must be documented: a rank only works if every path follows it. When two objects have no natural id, compare addresses (std::less<Account*>), which is a total order on pointers.D2

Fix 2: lock all at once

std::scoped_lock both(from.m, to.m); (C++17) locks several mutexes using the deadlock-avoidance algorithm of std::lock: it may lock, try, back off and retry internally, but it never ends in deadlock with other calls that use it for the same mutexes, in any argument order.D1 It is the simplest fix when all locks are known at one point, and Listing 1's second version shows it working in both directions.R1 It does not help when locks are taken in different functions at different times: then you need an order.

Making the order checkable

An order that lives only in documentation will be broken. Curriculum milestone B10 asks for "a debug mode that records lock acquisition order and detects inversions", with the acceptance test "The lock-order checker reports a deliberately inverted pair in a test build."S1 lock_order_checker.hpp implements this in user space:

  • each CheckedMutex has a name; each thread keeps a thread_local list of the checked mutexes it holds;
  • before locking mutex W while holding H, the registry records the edge H → W; if the edge W → H was recorded earlier (by any thread), it reports an inversion.

Listing 2 is the acceptance test: cook 1 takes pantry then fridge; after cook 1 has finished, cook 2 takes fridge then pantry. Because the threads run one after the other, no deadlock can happen in this run, yet the checker reports the inverted pair and the test prints PASS.R2 That is the whole point: the checker finds the possibility of deadlock in a run where none occurred. The Linux kernel's lockdep validator works on the same principle, with lock classes instead of individual locks.D14

ThreadSanitizer's deadlock detector

ThreadSanitizer keeps the same kind of lock-order graph for every mutex. On Listing 3 (the same inversion with plain std::mutex) it reports "lock-order-inversion (potential deadlock)", naming both acquisition sites, lines 14 and 19, and the program's own message confirms that no deadlock happened in the run.R3 Run under ThreadSanitizer, Listing 2 is reported twice: by our checker and by ThreadSanitizer, which sees the inner std::mutex of each CheckedMutex.R4




Layer 3 — the engineer's depth


Lock hierarchies. In large programs, locks are grouped into levels (for example: request lock, then table lock, then logging lock), and a thread may acquire only a lock of a lower level than any it holds. Williams shows a hierarchical_mutex that checks this at run time with a thread_local "current level", the same mechanism as our checker but with ranks declared in advance.D2 A hierarchy also tells you where callbacks are allowed: never call code of an unknown level while holding a lock (F2-36's checklist), because the callee may take a lock of a higher level.


Deadlocks without two mutexes. Circular waiting can involve any blocking operation:D2 D3


    

  • locking a non-recursive mutex twice in one thread (F2-36);
    • 

  • joining a thread while holding a lock that the thread needs to finish;
    • 

  • waiting on a condition variable for a state that only a thread blocked on your lock can produce;
    • 

  • a thread pool task waiting for another task that is queued behind it on a full pool (F2-41's forensic lab);
    • 

  • two processes each waiting for the other to read from a pipe.
    • 



Detection and recovery. Databases detect cycles in the wait-for graph and abort one transaction. General programs cannot roll back, so they use prevention; timed locks (try_lock_for) are a last-resort diagnostic, and back-off-and-retry can turn deadlock into livelock if all threads retry in lock step (add randomised back-off).D3 D7


Cost of the checker. Our checker takes a global mutex and searches a set on every acquisition, which serialises all locking; it is a test-build tool. Production-grade checkers (lockdep) use per-class hashing and check each new dependency once.D14 Our version also only detects inversions between pairs; a cycle of three locks (A→B, B→C, C→A) needs a search for paths in the graph, which is one of the lab's steps.

How the hardware actually does it


A deadlocked program is not busy: the threads in the forensic dump are asleep in the kernel. The stacks show the path from the C++ call to the system: std::lock_guard → std::mutex::lock → __gthread_mutex_lock → ___pthread_mutex_lock → __GI___lll_lock_wait → futex_wait, with expected=2 (in glibc's lock word, 2 means "locked, with waiters").R6 The kernel keeps each waiting thread on a queue keyed by the address of the lock word (the futex_word=0x… value in frame #0), and wakes it only when the owner unlocks. Because nobody will unlock, the threads use no CPU at all: a deadlock shows up as 0 % CPU and a frozen program, unlike a livelock or a spin, which shows 100 %.D9 That observation (CPU idle, requests not answered) is often the first clue in production.


Not verified — check before relying on this
The meaning of the value 2 in glibc's low-level lock word ("locked, possibly with waiters") is from memory of glibc's lowlevellock code and Drepper's "Futexes Are Tricky", neither opened in this build. The CPU usage of the deadlocked process was not measured. Check the glibc source for the version in Ubuntu 24.04, and observe with top -H -p <pid> while the forensic program is stuck.

Where the analogy breaks


    

  1. Cooks would talk; threads do not. Two people in a key standoff notice and negotiate. Threads have no idea they are waiting on each other; nothing in the program notices, so you need external tools (thread dumps, checkers).R6
    2. 

  2. Two keys, two cooks. Real deadlocks can involve many threads and resources of different kinds (mutexes, joins, full queues), and the cycle can be long (Figure 2).D7
    3. 

  3. The kitchen deadlock happens every time the two cooks meet. A program's deadlock needs a precise timing; the same inversion can run for months without a hang (the checker test never hangs). That is why the inversion, not the hang, is what you hunt.R2
    4.

Summary


    

  • A deadlock is a cycle of threads each waiting for a resource another holds; all four Coffman conditions are needed.
    • 

  • Prevent it with a global lock order, or with std::scoped_lock when all locks are taken in one place.
    • 

  • Check orders, do not wait for hangs: a lock-order checker or ThreadSanitizer reports inversions in runs that do not deadlock.
    • 

  • The B10 acceptance test passed: the checker reports a deliberately inverted pair in a test build.
    • 

  • Diagnose a hang with a thread dump: match waited-for lock addresses to holders, draw the wait-for graph, find the cycle.
    • 

  • Deadlocks also arise from joins, condition waits and full queues, not only from two mutexes.
    •

Forensic lab answer key


Threads: three: ledger (the main thread) in std::thread::join from main at line 46; payroll and refunds, both in futex_wait under transfer at line 28 (the second lock_guard). Locks (the addresses change in every run; match them within one dump): payroll's from is "savings" ($1) and it holds &from.m ($3); the futex_word in its frame #0 is its &to.m ($7), the kitchen mutex. Refunds' from is "kitchen" ($2) and it holds &from.m ($4); it waits on its &to.m ($8), the savings mutex. In the dump, $3 equals $8 and $4 equals $7: each thread waits for exactly the mutex the other holds. Graph: payroll → refunds (it waits for the kitchen mutex, held by refunds), refunds → payroll (it waits for the savings mutex, held by payroll): a cycle of two. The main thread waits for payroll to finish (join): a victim, not part of the cycle. Why most nights work: if one job reaches line 28 before the other reaches line 26, it takes both locks and finishes; the deadlock needs both threads to be between lines 26 and 28 at the same time. Test: use CheckedMutex for the account mutexes in a test build, or run the nightly-jobs test under ThreadSanitizer: both report the inversion in a run that does not hang (R3, R4). How the evidence was made: ledger.cc was built with -O0 -g, started by run.sh, left for 2 s, then GDB attached and printed the stacks and locals (R5, R6); the 03:00 and 07:00 times are the scenario, not a measurement.
