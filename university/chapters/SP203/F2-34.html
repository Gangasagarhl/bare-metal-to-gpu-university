Story hook

Analogy

The restaurant has one huge order tonight: a wedding wants a thousand dumplings. Chef Amara could fold them all herself, one after another, and finish long after the guests have gone home. Instead she calls three more cooks into the same kitchen. Each cook gets a tray and a clear share: "Kwame, you fold the first quarter; Lin, the second; Sofía, the third; I take the last."

They all use the same kitchen: the same flour bin, the same fridge, the same counting board on the wall. Each cook also has a personal cutting board and a personal note of how far they have got. When a cook finishes, she puts her tray on the pass and waits. Amara does not carry the dumplings out until every tray is on the pass.

That is the whole of this chapter in one picture: one program (the kitchen), several threads (the cooks), shared memory (the bins and the board), private stacks (the cutting boards), and "join" (waiting until every tray is on the pass). The rest of this course is about what goes wrong when cooks share things carelessly.

What you will be able to do

  • Start threads with std::thread and std::jthread, pass them arguments correctly (copy, reference, move) and join them.
  • Explain what a thread shares with the other threads of its process and what it owns alone.
  • Predict what happens when a std::thread is destroyed without join() or detach(), and why detaching is dangerous.
  • Split a computation into slices for several threads and measure the speedup on your own machine, including when it is disappointing.
  • Diagnose a thread that used an object after its lifetime ended, from an AddressSanitizer report.
Jargon box
Thread
Simple words: one running sequence of instructions inside a program; a program can have several. Analogy: one cook in the shared kitchen. Precise: an independent flow of control with its own registers, program counter and stack, sharing the address space of its process; the operating system schedules threads onto cores. F1-30 introduced the word; this chapter starts threads from C++. D1 D7
std::thread
Simple words: the C++ object that starts a thread and lets you wait for it. Analogy: the name card of one cook, which the head chef keeps until that cook is done. Precise: a class in <thread> whose constructor starts a new thread of execution running a callable with copies of the given arguments; the object represents that thread until it is joined or detached. D1 D2
Join (a thread)
Simple words: wait until a thread has finished. Analogy: waiting until a cook's tray is on the pass. Precise: join() blocks the calling thread until the thread represented by the object has completed; everything the finished thread did happens-before the return from join() (F2-39), so its results can be read safely afterwards. D1
Detach (a thread)
Simple words: let a thread run on its own; nobody will wait for it. Analogy: sending a cook off without asking for the tray back. Precise: detach() separates the thread of execution from the std::thread object; the thread keeps running and its resources are released when it ends; nothing in the program can wait for it any more. D1
Joinable
Simple words: "still has a thread that somebody must wait for or let go". Analogy: the head chef still holds the cook's name card. Precise: a std::thread is joinable if it represents a thread of execution (it was started and neither joined nor detached); destroying a joinable std::thread calls std::terminate(). D1
std::jthread
Simple words: a thread object that joins itself when it goes away and can be asked politely to stop. Analogy: a cook who, at closing time, is told "please stop" and is then waited for automatically. Precise: a C++20 class in <thread> like std::thread, whose destructor calls request_stop() and then join(); it owns a stop source and passes a std::stop_token to a callable that accepts one. D1
Concurrency and parallelism
Simple words: concurrency means several jobs are in progress at once; parallelism means several jobs are being worked on at the same instant. Analogy: one cook switching between three pots is concurrency; three cooks each stirring a pot is parallelism. Precise: concurrency is a property of the program's structure (several threads whose executions overlap in time); parallelism needs hardware that runs them simultaneously (several cores, F1-30). D3 D7
Speedup
Simple words: how many times faster the job got. Analogy: the wedding order took a quarter of the time with four cooks: speedup 4. Precise: the time of the best one-thread version divided by the time of the parallel version, measured on the same machine; Amdahl's law (F1-30) bounds it. D3
Load imbalance
Simple words: some threads get much more work than others, so everyone waits for the slowest. Analogy: one cook gets all the difficult dumplings. Precise: the situation where the work assigned to threads is unequal, so the parallel time is set by the most loaded thread rather than by the average. D3

The idea in pictures

Figure 1 shows what a thread shares and what it owns. All threads of one process see the same global variables and the same heap; each has its own stack and its own registers (including its own program counter). This one picture explains most of the course: everything in the shared part can be touched by two threads at once.

Figure 2 is the shape of almost every program in this chapter: fork (start workers), work in parallel, join (wait for all), then use the results.

Layer 1 — the kid explanation

A program you wrote until now did one thing at a time: one cook following one recipe. A thread is one cook. A program can start several threads, and they all work in the same kitchen at the same time. If your computer has four cores, four threads can really work at the same instant, like four cooks at four stoves.D7 R1

Starting a cook is easy: you tell them which recipe to follow and which ingredients to use. Waiting for a cook is called joining: you stand at the pass until their tray arrives. If you forget to wait and close the kitchen, the program is stopped on the spot (Listing 4 shows it).D1 R4

The cooks share the bins and the board on the wall. That is useful, because they need the same flour. It is also dangerous: if two cooks write on the same board at once, the writing gets mixed up. The safe trick in this chapter is to give every cook their own place to write their result, and to read the results only after everyone has finished. The next chapters teach what to do when cooks must share.

Layer 2 — the student explanation

Starting and joining

A std::thread is constructed from a callable (a function, a lambda, an object with operator()) and its arguments; the constructor starts a new thread of execution that calls it.D1 The constructor returns as soon as the thread has been started, not when it finishes. To wait for it, call join(). Listing 1 starts four workers with workers.emplace_back(sumSlice, …), which constructs each std::thread in place inside a vector, then joins them in a loop. Joining in order 0, 1, 2, 3 does not mean they finish in that order; it only means main passes the loop when all four have finished.D1 R1

Joining does more than wait. The language guarantees that everything the finished thread did happens-before the return from join().D1 That is why main may read partial[t] after the loop without any further protection. The term "happens-before" is the backbone of F2-39; for now, remember the rule: results written by a thread may be read after joining it.

How arguments reach the thread

The arguments you pass to the std::thread constructor are copied (or moved) into storage that belongs to the new thread, even if the function's parameter is a reference.D1 D2 Listing 2 shows the three cases you need:

  • By value (addOne(int)): the thread works on its own copy; the caller's counter stays 10.
  • By reference, on purpose: wrap the argument in std::ref (or std::cref for read-only), as Listing 1 does for the big vector. Now the thread refers to the caller's object, and the caller must keep that object alive until the thread is done.D1
  • By move: a move-only owner such as std::unique_ptr is moved into the thread with std::move; afterwards the caller's pointer is empty (F2-13, F2-22).R2

A lambda that captures by reference ([&counter]) is the same as passing std::ref: convenient, and with the same lifetime duty.

How a thread object must end

Every std::thread that started a thread must be either joined or detached before it is destroyed. If the destructor runs while the object is still joinable, the program calls std::terminate().D1 Listing 4 does exactly that; the run printed terminate called without an active exception and ended with exit code 134, which on Linux means the process was killed by the abort signal.R4 This rule exists because both alternatives would be worse: silently joining could hang the program, silently detaching could leave a thread using objects that are about to disappear.D2

std::jthread (C++20) applies RAII (F2-11) to threads: its destructor asks the thread to stop and then joins it.D1 If the callable's first parameter is a std::stop_token, the jthread passes one in; the thread checks stop_requested() and finishes by itself. Stopping is cooperative: nothing forcibly interrupts a thread in C++; the thread must look at the token (Listing 3).D1 R3 Prefer std::jthread in new code; this course still shows std::thread because most existing code uses it.D6

Why detach is a trap

detach() lets the thread run on with nobody responsible for it. Nothing can wait for a detached thread, so nothing can know when it has stopped using the objects it refers to.D1 If it still holds a reference to a local variable of a function that has returned, it reads dead memory. That is undefined behaviour (SP101, F2-23), and the forensic lab shows AddressSanitizer catching it.R6 The C++ Core Guidelines advise against detaching for this reason.D6

How many threads?

std::thread::hardware_concurrency() returns a hint: the number of hardware threads the implementation reports, or 0 if it cannot tell.D1 On this build's container it printed 4.R1 More threads than that cannot all run at the same instant: the operating system then time-slices them, so extra threads add overhead, not speed, for work that only computes (F2-41 calls this oversubscription).D7

Layer 3 — the engineer's depth

What the standard promises and what it leaves open. The standard specifies the behaviour of threads in terms of an abstract machine: each thread executes its own sequence of evaluations, and their interaction through memory is governed by the rules of [intro.multithread] (F2-35 to F2-39).D1 It says nothing about cores, scheduling policy, priorities or stack sizes. Those belong to the platform: on Linux with GCC, std::thread is built on POSIX threads, as the thread dump in F2-40 shows (pthread_create, pthread_mutex_lock frames).R6 Platform facilities such as thread names or CPU affinity are reached through native_handle() and the platform API, outside portable C++.D1

Forward progress. The standard only gives limited guarantees that a thread which is not blocked will eventually make progress; it encourages, but does not require, implementations to give every unblocked thread a chance to run.D1 On a general-purpose operating system the scheduler preempts threads, so a thread stuck in a loop does not stop the others (curriculum B9 asks your own kernel to provide the same). Code that assumes another thread "will surely run soon" is relying on the scheduler, not on C++.

Not verified — check before relying on this

The exact wording of the forward-progress clauses (which the standard calls "should" recommendations versus requirements, and the names of the progress guarantee classes) was written from memory of the C++20 draft and was not opened in this build. Check ISO/IEC 14882 (the C++20 working draft), clause [intro.progress], before quoting it.

Exceptions inside a thread. If the function a thread runs lets an exception escape, std::terminate() is called; the exception does not travel to the thread that called join().D1 To carry results or errors back, use a shared slot read after join() (Listing 1), or a std::future (F2-41), which transports exceptions.

Cost of a thread. Starting a thread is a system call plus a stack allocation; it is far more expensive than a function call. This build measured a mean of tens of microseconds to start and join an empty thread on the container (lab output, speedup), against well under a nanosecond for one loop iteration of plain arithmetic in F2-38's measurement.R5 That is why long-running programs reuse threads in a pool (F2-41) instead of starting one per small job.

Splitting work. Listing 1 gives thread t of T the index range [n·t/T, n·(t+1)/T). This formula covers every index exactly once, with slices that differ in size by at most one element, for any n and T (the worked example checks a small case).R7 Equal sizes are not equal work, though: the speedup measurement below shows a split that looked fair and was not.

How the hardware actually does it

A core runs one thread at a time (or a few, with simultaneous multithreading). The operating system keeps, for every thread, a saved copy of its registers and program counter. When it switches a core from one thread to another (a context switch), it saves the registers of the old thread and loads those of the new one; the memory stays where it is, because all threads of a process share one address space and one set of page tables (F1-38).D7 Threads on different cores really run at the same time, each with its own L1 and L2 caches; the coherence protocol of F1-36 keeps their views of shared memory consistent, at the cost of traffic when they write to the same cache lines (F2-38 measures that).D4 The kernel track builds all of this yourself: curriculum B9 (threads and scheduling) and B11 (starting the other cores).S1

Not verified — check before relying on this

The container reported 4 CPUs (hardware_concurrency() and nproc), but it is a virtual machine shared with other jobs: whether these are 4 dedicated physical cores was not checked, and other build jobs were running during the measurements. Treat every time in this course as "measured on a busy shared virtual machine" (AH-23) and measure on your own computer.

Worked example

Split n = 10 elements, holding the values 1 to 10, among T = 4 threads with Listing 1's formula, and predict each thread's sum.

  1. Thread 0: begin = 10·0/4 = 0, end = 10·1/4 = 2 (integer division drops the .5). Indices 0, 1 hold 1 + 2 = 3.
  2. Thread 1: begin = 2, end = 20/4 = 5. Indices 2–4 hold 3 + 4 + 5 = 12.
  3. Thread 2: begin = 5, end = 30/4 = 7. Indices 5, 6 hold 6 + 7 = 13.
  4. Thread 3: begin = 7, end = 40/4 = 10. Indices 7–9 hold 8 + 9 + 10 = 27.
  5. Check: 3 + 12 + 13 + 27 = 55 = 10·11/2. Every index was used once; the slices have 2 or 3 elements.

Read the numbers before reading on. In every run of this build, two threads took about as long as one: no speedup at all. The 4- and 8-thread rows varied a lot between runs on this shared machine (from about half the one-thread time to almost no gain), but never came near a speedup of 4.R5 The comment in countPrimes promised that "every thread gets small and large numbers", and that is true; but with two threads, thread 0 gets 2, 4, 6, 8, …: all even numbers, which isPrime rejects after one division. Thread 1 gets all the odd numbers and nearly all of the work. That is load imbalance. With four threads, two of them get only even numbers, so again only two do real work. Where the analogy breaks


    

  1. Cooks are never frozen mid-movement; threads are. The operating system can pause a thread between any two machine instructions, for as long as it likes, and run another one (registered limit of this analogy, guide 8.1). A cook who is "folding dumpling 312" finishes the fold; a thread may stop half-way through updating a variable.D7
    2. 

  2. Four cooks need four stoves; threads do not. You can start a hundred threads on a four-core machine. They do not run at the same instant: the scheduler takes turns. In the kitchen, a hundred cooks would at least all be standing there working.D7 R5
    3. 

  3. A cook's cutting board is physically private; a stack is not. Any thread that has the address of another thread's local variable can read and write it. The privacy of the stack is a convention you keep by not handing out addresses, not a wall (forensic lab).R6
    4.

Transition box

Where you came from: SP201 (F2-18 to F2-25) taught memory as numbered bytes, pointers, lifetimes and undefined behaviour in a program with one flow of control; F1-30 showed that a multicore processor runs several threads at once. What carries over: everything about objects, lifetimes, references and RAII still holds; AddressSanitizer still finds lifetime bugs, now with "thread T1" in the report.D1 R6 What changes: most dangerous first: two flows of control can now touch the same object at once, and a reference handed to a thread extends your lifetime duty to that thread's whole run; the order of events between threads is no longer fixed by the text of the program; and a forgotten join() ends the program.D1 What comes next: F2-35 shows what happens when two threads write the same variable: a data race, which C++ treats as undefined behaviour, and the tool that finds it, ThreadSanitizer.

Lab


Goal


Parallelise a computation with std::thread, measure the speedup on your machine, find the load imbalance in speedup.cc and fix it.

A Linux computer (or WSL) with at least two cores and g++ with C++20 support. The build used g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0 on an x86-64 container with 4 CPUs visible. No special hardware.

None beyond normal computer use.

    2.

Expected observations


Before the fix, this build's run showed little or no gain from 1 to 2 threads and roughly a halving of the time at 4 threads; the prime count was 216,816 in every configuration.R5 After a balanced split you should see the time drop clearly at 2 threads and continue to fall up to the number of cores; beyond that, little or nothing. Your absolute times will differ; a shared or virtual machine also adds noise, which is why the program reports the median of five runs.


Verification


(1) The prime count is identical for every thread count. (2) The per-thread division counts after your fix differ by less than 10 % from their mean (your own measurement). (3) The program builds with the course flags plus -fsanitize=thread (F2-35) and ThreadSanitizer prints no warning.


Troubleshooting


    

  • Speedup is exactly 1.0 for every thread count → the threads run one after another because you call join() right after each start, inside the creation loop → start all, then join all.
    • 

  • Results change between runs → two threads write the same variable → give each thread its own slot (Listing 1, line 15).
    • 

  • Times vary wildly → other programs are running, or the machine changes its clock speed → close other programs, take the median of more runs, and report the spread.
    •

Summary


    

  • A thread is an independent flow of control; all threads of a process share code, globals and heap, and each has its own stack and registers.
    • 

  • std::thread starts a thread from a callable; arguments are copied or moved into the thread; use std::ref/std::cref to share on purpose.
    • 

  • Every started std::thread must be joined or detached; destroying a joinable one calls std::terminate().
    • 

  • join() waits and makes the thread's writes visible to the joiner; reading results after joining is safe.
    • 

  • std::jthread joins automatically and supports cooperative stopping with std::stop_token.
    • 

  • Detaching hands away your only way to know when a thread stops using your objects: avoid it.
    • 

  • Speedup needs balanced work and no more busy threads than cores; measure, do not assume.
    •

Forensic lab answer key


Observation: AddressSanitizer reports stack-use-after-return, a READ of size 8 in thread T1, in printLater at dangling.cpp:11 (tables.front()). The memory "is located in stack of thread T0" in the frame of startPrinter(), inside the variable tables (line 16). T1 was created in startPrinter() at line 17. Story: T0 starts the printer with a reference to its local tables, detaches it, and returns; tables is destroyed at line 19; 50 ms later T1 wakes up and reads through the dangling reference. Hypotheses for "works on my laptop": (H1) without the sanitizer the dead stack memory still held the old bytes for a while, so the read returned plausible values — test by building without sanitizers and adding more calls after startPrinter() that reuse the stack; (H2) on the laptop the printer thread happened to run before the function returned — test by changing the sleep. Both are possible; neither makes the program correct: the access is undefined behaviour whatever the timing. Fix: give the printer its own copy (pass tables by value, or move it into the thread), or keep one long-lived printer thread fed through a queue and joined at shutdown; do not detach. Proof: the same AddressSanitizer build runs clean, and a ThreadSanitizer build (F2-35) reports nothing. How the evidence was made: dangling.cpp run by run_lab.sh in this build (R6); the 50 ms sleep makes the late read happen on every run.
