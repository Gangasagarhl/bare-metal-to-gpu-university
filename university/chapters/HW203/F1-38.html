Story hook

Analogy

The cooks never say "pantry shelf 7, box 3". They say "the tomatoes". A thick index binder by the pantry door turns each name into a shelf and box; looking it up means walking to the door and leafing through four tabbed sections. So each cook keeps a few sticky notes at the station with the last lookups: "tomatoes: shelf 7, box 3". With the notes, finding an ingredient is quick. Without them, every ingredient costs a trip to the binder before the trip to the shelf.

One day a new cook starts with an empty pantry corner. The first time she asks for each of a thousand boxes, the manager must first fetch and clear an empty box and write it into the binder. Her first evening is slow; her second is not.

What you will be able to do

  • Split an x86-64 virtual address into four table indices and a page offset, by hand and with code.
  • Trace a page-table walk and a TLB in front of it, including a page fault.
  • Explain why the first touch of fresh memory is slow, and measure it with the kernel's page-fault count.
  • Estimate TLB reach and measure the effect of 4 KiB versus 2 MiB pages.
  • Diagnose a "first run is slow" report from timings and fault counts.
Jargon box
Virtual memory
Simple words: each program uses its own made-up addresses, and the hardware and operating system map them to real memory. Analogy: ingredient names instead of shelf numbers. Precise: a mechanism in which a program's addresses (virtual addresses) are translated, page by page, to physical addresses through tables maintained by the operating system, giving each process its own address space, protection and the ability to map pages on demand. D1 D2
Page (memory)
Simple words: a fixed-size block of memory, the unit of mapping. Analogy: a pantry box. Precise: an aligned, power-of-two-sized block of virtual address space (4096 bytes on the build container) mapped as a unit onto a physical frame of the same size. D1 R5
Page table
Simple words: the table that says where each page really is. Analogy: the index binder. Precise: an in-memory data structure, per address space, mapping virtual page numbers to physical frame numbers plus permission and status bits; on x86-64 a tree of 512-entry tables. D1 D7
Page-table walk
Simple words: following the tables from the top to find one page's location. Analogy: leafing through the binder's four tabbed sections. Precise: the sequence of memory reads, one per table level, that the hardware (or software) performs to translate a virtual page number when the TLB has no entry for it. D1 D3
TLB
Simple words: a tiny cache of recent address translations. Analogy: the sticky notes at the station. Precise: the translation lookaside buffer: a small, associative cache of page-table entries indexed by virtual page number, checked on every memory access; a miss starts a page-table walk. D1 D2
Page fault
Simple words: the hardware finds no valid mapping and asks the operating system to fix it. Analogy: the binder has no entry yet; the manager fetches a box. Precise: an exception raised when translation finds a missing or forbidden mapping; the kernel either maps a page (a minor fault when no disk read is needed, a major fault when it is) and restarts the instruction, or signals an error. D1 D8
Huge page
Simple words: a much larger page, so one translation covers more memory. Analogy: one sticky note for a whole shelf instead of one box. Precise: a page larger than the base size (2 MiB on x86-64, mapped by a level-2 entry), which reduces TLB misses and walk depth; Linux offers them through transparent huge pages and explicit huge-page pools. D7 D8
TLB reach
Simple words: how much memory the TLB can cover at once. Analogy: number of sticky notes times what each note covers. Precise: number of TLB entries × page size; a working set larger than the reach causes TLB misses even if its data fits in the caches. D3 D1

Layer 1 — the kid explanation

A program does not use real memory addresses. It uses its own "pretend" addresses, and every time it reads or writes, the computer translates the pretend address into a real one, in blocks called pages.D1

The translation is written in a big table in memory, the page table. Reading that table every time would be slow, so the processor remembers recent translations in a tiny, very fast list called the TLB.D1

When a program touches a page for the first time, there is often no real memory behind it yet. The operating system then picks a free piece of memory, clears it and writes it into the table. That is a page fault, and you will count them.D1 R3

Layer 2 — the student explanation

Why virtual addresses

Translation gives each process a private address space (it cannot name another process's memory), per-page permissions (read, write, execute, user/kernel), and a way to map memory lazily: a page gets physical memory only when first touched, or comes from a file on demand.D1 D2

Splitting the address

With 4 KiB pages the low 12 bits of an address are the offset inside the page; the rest is the virtual page number (VPN). Translation replaces the VPN with a physical frame number and keeps the offset.D1 On x86-64 with 4-level paging, 48 address bits are used, and the 36-bit VPN is split into four 9-bit indices, one per table level; each table has 29 = 512 entries of 8 bytes, which fills one 4 KiB page.D7 Listing 1 does the split.

The walk and the TLB

A walk reads one entry per level: four dependent reads for one translation. Each read can hit or miss in the data caches like any other load.D1 D3 The TLB caches finished translations; like a data cache it has a size, an associativity and a replacement policy (F1-33), and processors have several levels of TLB.D3 Listing 2 models a 2-entry fully associative TLB with LRU in front of a page table.

Page faults and first touch

When the walk finds no valid entry, the processor raises a page fault. For memory a program allocated but never touched, Linux maps a fresh zero-filled page and restarts the instruction: a minor fault.D1 D8 Listing 4 fills a 256 MiB buffer three times and reads the process's minor-fault count with getrusage around each pass.D8

TLB reach and huge pages

If a TLB holds E entries of 4 KiB, it covers 4 KiB × E. A loop touching one line in each of more pages than that misses in the TLB even when all its lines fit in the cache. A 2 MiB page covers 512 times as much with one entry, and its walk ends one level earlier.D3 D7 Linux applies transparent huge pages to memory marked with madvise(MADV_HUGEPAGE) when the system is configured in "madvise" mode, as the build container was.D8 R4

Layer 3 — the engineer's depth

Caches and translation together. L1 caches are commonly virtually indexed and physically tagged: the set index comes from the page-offset bits, which translation does not change, so the TLB lookup and the cache set lookup can run in parallel.D1 D3 That limits the L1 size to page size × ways; the build container's reported L1d (48 KiB, 12 ways, 64-byte lines) has exactly 48 KiB / 12 = 4 KiB per way, consistent with this design.R5

Context switches. Each process has its own page tables; switching processes changes the root (CR3 on x86). TLB entries can be tagged with an address-space identifier so they need not all be flushed.D7 D3

Huge pages cost something too. A 2 MiB page must be backed by 2 MiB of contiguous physical memory, zeroed on first touch, and wastes memory when only a part is used.D8 A less obvious cost appears in Listing 3: with 4 KiB pages, address bits 12 and above are scrambled by translation, so data a program places at 4 KiB strides lands in physical frames that spread over many cache sets. With 2 MiB pages, physical bits 12–20 equal the virtual ones, so the program's own stride pattern decides the cache sets.D1 Listing 3's "spread" pattern puts block b at byte b × 4096 + (b mod 64) × 64; with the reported L2 geometry (2048 sets, index from bits 6–16), this gives only 64 distinct L2 sets when virtual = physical in those bits. This is a derivation from the layout and the reported geometry, not a counter measurement.

How the hardware actually does it

On every load and store the core looks up the virtual page number in the first-level data TLB at the same time as the L1 set; a hit supplies the frame number for the tag compare. On a miss, a second-level TLB is tried; on a miss there, a hardware page walker reads the page-table entries — through the data caches — starting from the root register, and fills the TLBs.D3 D7 If an entry is not present or the access is not permitted, the walker raises a page-fault exception with the faulting address; the kernel's handler fixes the mapping and returns to the same instruction.D1 D7 When the kernel changes a mapping, it must also invalidate stale TLB entries, on every core that may hold them ("TLB shootdown").D3

Where the analogy breaks


    

  1. One binder per process. The kitchen has one binder; a computer has one set of page tables per process, so the same "name" (virtual address) means different shelves in different processes.D1
    2. 

  2. The binder lives in the pantry. Page tables are themselves in memory and are cached like data, so a walk can hit in the caches; the binder by the door has no such shortcut.D3
    3. 

  3. Sticky notes can lie. A cook may forget to update a note when a box moves. Hardware does not track this either: the kernel must invalidate stale TLB entries itself when it changes a mapping.D3
    4.

Transition box

Where you came from: F1-33 and F1-34 treated addresses as if they went straight to the caches. What carries over: address splitting into fields, associativity and LRU, working set and locality — now applied to translations.D1 What changes: every access first needs a translation, the TLB is a second cache with its own reach, and the operating system takes part in memory accesses (page faults).D2 What comes next: F1-39 goes below the caches and the page tables to DRAM itself, its banks, rows, channels and NUMA nodes.

Summary


    

  • Programs use virtual addresses; pages (4 KiB on the build container) are mapped to physical frames by page tables.
    • 

  • x86-64 4-level paging: 9 + 9 + 9 + 9 index bits and a 12-bit offset; a walk is up to four dependent reads.
    • 

  • The TLB caches translations; reach = entries × page size.
    • 

  • First touch of allocated memory causes minor page faults: 65,539 faults cost about 160 ms in pass 1 on the build container.
    • 

  • Huge pages extend TLB reach; on the build container they halved the spread time at 16,384 blocks, but also change which cache sets data uses.
    • 

  • Without counters, interpret timing steps carefully: one step in Listing 3 remained unexplained.

Forensic lab answer key


Observation: pass 1: 201.2 ms, 65,539 minor faults; passes 2 and 3: 37.2 and 36.2 ms, 0 faults (R3). The buffer is 65,536 pages of 4 KiB, so pass 1 faulted once per page (the three extra are other memory the process touched in that interval). Cost per fault: (201.2 − 37.2) ms / 65,539 ≈ 2.5 µs per fault, which includes the kernel's zeroing of a 4 KiB page and updating the page table — measured on the build container, one session. Hypotheses: (H1) "cold CPU / caches": a 256 MiB fill does not fit in any cache (the reported L2 is 2 MiB; the L3 is shared and its usable share in a VM unknown), so passes 2 and 3 run from DRAM as well and do not benefit from warm caches; H1 cannot explain a 5× difference. (H2) page faults: the only thing pass 1 does that later passes do not is fault, and the fault count matches the page count exactly. Allocation: make_unique_for_overwrite asks for memory without initialising it; the kernel only reserves virtual addresses, and physical pages are assigned on first write. Fix: a sleep does nothing; pre-touch the buffer (one write per page) before timing, reuse buffers across iterations, or report first-touch time as a separate number because real users may pay it. 2 MiB pages: about 128 faults (256 MiB / 2 MiB), each more expensive (zeroing 2 MiB); the total time would need measuring. Prevention: benchmark harnesses report per-phase fault counts. How the evidence was made: run.sh in university/labs/F1-38/.
