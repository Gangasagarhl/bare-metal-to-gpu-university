Story hook

Analogy

Two cooks share a notice board. Yuki writes "I am using the big pot" on a note, drops it in her outbox tray to pin up later, and looks at the board: no note from Ahmed, so she takes the pot. At the same moment Ahmed writes "I am using the big pot", drops it in his tray, looks at the board, sees nothing from Yuki, and takes the pot too. Each cook did things in the right order — write first, then look — and each still missed the other's note, because notes wait in the trays for a moment before they reach the board.

The kitchen's fix is a rule: for this kind of note, you must pin it up yourself and wait until it is on the board before you look. Slower, but the pot is safe.

  • Diagnose a broken lock from lost updates and from the instructions the compiler generated.
Jargon box
Memory consistency model
Simple words: the rules for which values loads may return when several cores read and write memory. Analogy: the kitchen's rules for when a note counts as "on the board". Precise: a specification of the allowed behaviours of a multithreaded program's loads and stores, across all memory locations, as defined for a hardware architecture or a programming language. D4
Sequential consistency
Simple words: the result is as if all threads took turns, one memory operation at a time, each in program order. Analogy: one pen on a chain at the board; every cook writes and reads only with it. Precise: a model in which the result of any execution equals some single total order of all memory operations that respects each thread's program order (SC). D4 D3
Store buffer
Simple words: a small queue in each core where finished stores wait before they are written to the cache. Analogy: each cook's outbox tray. Precise: a per-core FIFO of committed stores not yet written to the coherent cache; the core's own loads check it first (forwarding), while other cores cannot see its contents. D4
Total store order
Simple words: a model like SC except that a load may be done before an earlier store to another address. Analogy: notes may wait in the outbox while the cook already reads the board. Precise: TSO relaxes only the store→load order of SC (for different addresses), as a FIFO store buffer does; stores from all cores still appear in one total order. D4
Litmus test
Simple words: a tiny multi-thread program used to ask "can this outcome happen?" Analogy: the two-cooks-one-pot story, written down exactly. Precise: a short program with a few threads and an outcome of interest; a model either allows or forbids the outcome. D4
Memory fence
Simple words: an instruction that stops later memory operations from overtaking earlier ones. Analogy: "pin it up and wait before you look". Precise: an instruction (or language construct) that orders memory operations before it with those after it; on a TSO machine, a full fence drains the store buffer before later loads execute. D4 D7
Acquire and release
Simple words: one-way orderings: a release store keeps earlier work before it, an acquire load keeps later work after it. Analogy: "finish the dish, then flip the ready sign" / "see the sign, then pick up the dish". Precise: in C++, a release store that is read by an acquire load synchronises with it, so writes before the release happen-before reads after the acquire; it does not order a release store with a later acquire load to a different variable. D6

Layer 1 — the kid explanation

When two threads share memory, you might expect the computer to behave as if the threads took turns, one step at a time. That expectation has a name: sequential consistency.D4

Real processors break it a little, for speed. A core puts its writes in a small waiting line (the store buffer) and keeps going. Its next read can happen before the earlier write reaches the others, so two threads can each miss the other's write.D4

Programming languages give you tools — atomics with a chosen memory order, and fences — to say "here the order matters". You will see the surprising outcome happen hundreds of times on a real machine, and disappear with the right choice.D6 R1

Layer 2 — the student explanation

Sequential consistency

SC requires that every execution looks like some interleaving of the threads' memory operations in which each thread's operations keep their program order.D4 D3 In the store-buffering (SB) litmus test, thread A runs x = 1; r1 = y; and thread B runs y = 1; r2 = x;, with x and y initially 0. In every interleaving, one of the stores comes first, so whichever thread loads last sees a 1: under SC, r1 = 0 and r2 = 0 together is impossible. Listing 1 checks this by trying every ordering (20 orderings, no 0/0).R3

Store buffers and TSO

A store that misses in the cache needs ownership of the line (F1-36), which can take many cycles. Instead of waiting, the core places the store in its store buffer and continues; a later load to a different address can complete from the cache before the store drains.D4 To the other core this looks like the load moved ahead of the store. The model that allows exactly this relaxation — store followed by load to another address — and keeps the others is called total store order (TSO).D4 When the course model adds store buffers, 0/0 appears in 18 of 80 allowed orderings.R3

The C++ view

C++ programs do not target one hardware model. The standard defines atomics with memory orders, and the compiler emits whatever instructions make the chosen order hold on the target.D6

  • memory_order_relaxed: the operation is atomic, but orders nothing else.
  • memory_order_release (stores) / memory_order_acquire (loads): if an acquire load reads the value of a release store, everything written before the release is visible after the acquire. This is enough for "publish data, then set a flag". It does not forbid the SB outcome: a release store followed by an acquire load of a different variable may still be reordered.D6
  • memory_order_seq_cst (the default): additionally, all seq_cst operations appear in one total order consistent with each thread's program order, so the SB outcome is forbidden.D6

A program without data races that uses only seq_cst atomics behaves as if sequentially consistent ("SC for data-race-free programs").D4 D6

Fences

A fence orders operations across it. On a TSO machine the only reordering to prevent is store→load, and a full fence (or an atomic read-modify-write instruction, which also drains the store buffer) between the store and the load prevents it.D4 D7 In C++, std::atomic_thread_fence(std::memory_order_seq_cst) is the portable form.D6

Layer 3 — the engineer's depth

Why hardware relaxes. Store buffers hide store-miss latency; out-of-order cores (F1-29) also want to execute loads early. A strict SC implementation must either wait or speculate and roll back when another core's write could expose the reordering.D4 D3 TSO keeps the store buffer and forbids the rest; weaker models (several RISC architectures) also allow store→store and load→load/store reordering and rely on fences or acquire/release instructions.D4

Not verified — check before relying on this

That the x86-64 memory-ordering rules in the processor vendor's manual are equivalent to TSO, and which exact orderings Arm and RISC-V allow, are stated here from the Primer's general description, not from the vendor manuals, which were not opened. Only x86-64 was tested in this build: the counts in this chapter say nothing about Arm or RISC-V machines. Check the vendors' architecture manuals (memory-ordering chapters) before relying on these mappings.

What the compiler emitted. On the build container, g++ compiled the release stores of Listing 2 to plain mov instructions and the seq_cst stores to xchg; all loads, acquire or seq_cst, were plain mov (outputs in the forensic lab).R4 xchg with a memory operand is a locked read-modify-write on x86, which the vendor manual describes as ordering it with earlier and later loads and stores — that is what removes the store→load reordering.D7 Another compiler might use mov followed by mfence for the same purpose; the choice is the compiler's, the guarantee is the language's.

Observation is not proof. The SB test produced 0/0 in about 0.4% of rounds with relaxed and acq/rel, and never with seq_cst in one session.R1 Zero observations do not prove an outcome impossible: the proof comes from the language rules (and their mapping to the hardware), which is why litmus tools enumerate the model's outcomes, as Listing 1 does, instead of only running tests.D4

Coherence still holds. TSO does not break coherence: each location still has one order of writes that all cores agree on. The surprise is only about the relative order of a store and a later load to different locations (F1-36).D4

How the hardware actually does it

A store retires from the out-of-order core into the store buffer; the buffer writes stores to the L1 data cache in program order once the line is held in M or E state (F1-36). Every load searches the store buffer for a matching address and, if found, takes the newest value from there (store-to-load forwarding); otherwise it reads the cache.D4 A full fence or a locked instruction waits until the buffer is empty. Out-of-order cores also issue loads early and check, before they retire, that no other core invalidated the line in the meantime; if one did, the load and everything after it is replayed — this keeps load→load order visible as in TSO while still executing out of order.D4 D3 The store buffer size and the replay mechanism of the build container's processor were not checked.

Worked example

Count the orderings of the SB test in the store-buffer model by hand, at least partly. Events: A0 (x = 1 into A's buffer), A1 (r1 = y), Af (x drains to memory), and B0, B1, Bf for thread B.

  1. Constraints: A0 before A1 and before Af; B0 before B1 and before Bf. Without the SC rule, Af may come after A1.
  2. Number of orderings of 6 events with these constraints: each thread's three events have A0 first and A1, Af in either order: 2 of the 6 orders of three events, so 1/3. For two threads: 720 × (1/3) × (1/3) = 80.
  3. Under SC, add Af before A1 and Bf before B1: each thread's order is fixed (A0, Af, A1), so 720 / 6 / 6 = 20.
  4. For 0/0 we need A1 before Bf and B1 before Af. Example ordering: A0, B0, A1, B1, Af, Bf. A1 reads memory y = 0, B1 reads x = 0: r1 = 0, r2 = 0.
  5. Listing 1 confirms: SC 20 orderings, no 0/0; store-buffer model 80 orderings, 0/0 in 18.R3

Where the analogy breaks


    

  1. Your own notes. A cook might forget a note in her own tray. A core never does: its own loads see its own buffered stores (forwarding).D4
    2. 

  2. Order of the tray. In TSO the tray empties strictly in order; in weaker models the analogy would need a tray that pins notes up in any order, which no kitchen would accept.D4
    3. 

  3. The compiler is a second actor. In the kitchen only cooks reorder. In a program the compiler may also reorder or remove memory operations on non-atomic variables; memory orders constrain both the compiler and the hardware.D6

Summary


    

  • A memory consistency model says which values loads may return across locations and threads.
    • 

  • SC: some single interleaving that keeps program order; the SB outcome 0/0 is forbidden.
    • 

  • Store buffers let a later load overtake an earlier store to another address; TSO allows exactly this.
    • 

  • C++ relaxed and acquire/release allow the SB outcome; seq_cst forbids it. Release/acquire is enough for publishing data through a flag.
    • 

  • On the build container, seq_cst stores became xchg; release stores were plain mov.
    • 

  • Locks built from loads and stores (Peterson) need store→load order: seq_cst or a full fence.
    • 

  • Tests can show an outcome is possible, never that it is impossible; models and the standard do that.

Forensic lab answer key


Observation: release/acquire lost 718 additions of 2,000,000; seq_cst lost none (R2). Assembly: in the release/acquire loop, lock() is mov BYTE PTR [rdx],0x1 (wants[0] = true), mov DWORD PTR [rax],0x1 (turn = 1), then movzx ecx,BYTE PTR [rdx+0x1] (load wants[1]) — plain stores followed by a plain load. In the seq_cst loop the two stores are xchg instructions; the loads are unchanged (R4). Litmus mapping: thread 0 stores wants[0] then loads wants[1]; thread 1 stores wants[1] then loads wants[0]: this is the SB test with x = wants[0], y = wants[1]. If both loads read false (0/0), both threads pass the while condition and enter together; the critical section's separate load and store then lose an addition. (The turn variable does not save them: each thread's check of turn is skipped when wants[other] reads false.) Hypotheses: (H1) the counter update itself is racy — it is, but only when two threads are inside, which the lock should prevent; the seq_cst version with the identical counter code lost nothing, so the lock is what failed. (H2) store→load reordering in lock() — supported by the litmus mapping, by the SB test showing 0/0 with release/acquire on the same machine (R1), and by the only code difference being mov versus xchg. Fix: seq_cst for the stores and loads of lock() (the default), or a std::atomic_thread_fence(std::memory_order_seq_cst) after the stores — or use std::mutex. Prevention: keep the stress test with a lost-update check in CI, add a comment linking the lock to the SB litmus test, and do not weaken memory orders without a model argument. How the evidence was made: run.sh in university/labs/F1-37/.
