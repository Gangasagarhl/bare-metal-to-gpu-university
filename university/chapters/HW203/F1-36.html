Story hook

Analogy

The restaurant now has four cooks, each at a station with a small shelf of their own. The house recipe for the soup lives in the pantry, and each cook keeps a photocopy on their shelf. One evening Yuki changes the salt in the recipe on her copy. Ahmed, at the next station, still cooks from his old copy, and two different soups leave the kitchen.

The kitchen adopts a rule. Anyone may hold a read-only copy. Before you change a recipe, you call out "tear up your copies of the soup recipe!", and only then do you write on yours. Anyone who wants to read it afterwards must ask you for the new version. The rule costs some shouting across the kitchen, and it has one surprise: when two cooks keep editing two different recipes printed on the same sheet of paper, they shout at each other all evening although they never share a recipe.

What you will be able to do

  • State what cache coherence guarantees, using the single-writer–multiple-reader rule.
  • Trace the MESI states of one line in several caches through a sequence of reads and writes, and check the trace with the course's MESI model.
  • Compare snooping and directory protocols.
  • Measure false sharing on your machine and fix it with alignment.
  • Diagnose "four threads slower than one" from timings, a type layout and a race-detector run.
Jargon box
Cache coherence
Simple words: making sure all cores see one agreed value for each memory location, even though each has its own cache. Analogy: the kitchen rule about recipe copies. Precise: the property that, for each memory location, at any time either one core may write it or any number of cores may read it (single-writer–multiple-reader), and every read returns the value of the most recent write to that location. D4 §2.4 D3 ch. 5 D11 §11.6
MESI protocol
Simple words: a set of four labels each cache keeps for each line, and rules for changing them. Analogy: each cook's copy is marked "mine and changed", "mine only", "shared" or "torn up". Precise: an invalidation-based coherence protocol with line states Modified (only copy, dirty), Exclusive (only copy, clean), Shared (clean, possibly in other caches) and Invalid. D4 §6.4.1 D2 ch. 5 D11 §11.6
Snooping
Simple words: every cache listens to every other cache's requests. Analogy: every cook hears every call across the kitchen. Precise: a family of coherence protocols in which coherence requests are broadcast to all caches (over a bus or another ordered interconnect) and each cache controller reacts to the requests that concern lines it holds. D4 §6.4.3 D3 ch. 5 D11 §11.6
Directory (coherence)
Simple words: a record that says which caches have a copy of which line. Analogy: a list on the pantry door of who holds a copy of each recipe. Precise: a structure, usually distributed with memory, that tracks the state and the sharers of each line, so coherence requests can be sent only to the caches involved instead of broadcast. D4 §6.4.3, §8.1–8.2 D3 ch. 5
Invalidation
Simple words: telling other caches their copy is no longer valid. Analogy: "tear up your copies!" Precise: a coherence action that changes other caches' copies of a line to Invalid, so that a core can obtain write permission (single writer). D4 §6.4.3
False sharing
Simple words: two threads slow each other down by writing different variables that happen to share one cache line. Analogy: two recipes printed on one sheet. Precise: coherence traffic caused by independent data items located in the same line; because coherence works per line, writes to either item invalidate the other core's copy of the whole line. D1 ch. 12 D3 ch. 5 D11 §14.5

Layer 1 — the kid explanation

Each core has its own fast cache, so the same memory location can be copied into several caches. If one core changes its copy, the others must not keep using the old one. Keeping all copies in agreement is called coherence.D4 §2.4 D11 §11.6

The common rule is simple to say: many cores may read a line at the same time, but only one may write it, and before it writes, everybody else's copy is thrown away (invalidated).D4 §2.4, §6.4.3

Because the rule works on whole lines, two cores writing two different variables in the same line still take turns, as if they shared one variable. That slowdown is called false sharing, and you will measure it.D1 ch. 12 D11 §14.5

Layer 2 — the student explanation

The problem

With write-back caches (F1-35), a core's store may live only in its own cache. Another core reading the same address from its own cache or from memory would see an old value. A coherence protocol prevents this.D4 §2.2 D2 ch. 5 D11 §14.5 The Primer defines coherence with two invariants: single-writer–multiple-reader (for any location, at any time, either one core may write it or any number may read it) and the data-value invariant (the value at the start of an epoch equals the value at the end of the last read-write epoch).D4 §2.4

MESI states

Each cache keeps a state per line. Modified: this cache has the only valid copy and it is dirty. Exclusive: the only copy, clean. Shared: a clean copy that other caches may also hold. Invalid: no usable copy.D4 §6.4.1 D2 ch. 5 Reading is allowed in M, E and S; writing only in M (and in E after a silent change to M, because no other copy exists: the Primer describes E as "valid, exclusive, and clean" and counts it as an ownership state).D4 §6.4.1

Transitions

A read miss broadcasts a read request (BusRd in the course model). If another cache holds the line in M, it supplies or writes back the data and drops to S; caches in E also drop to S; the requester enters S if anyone else had a copy and E otherwise.D4 §6.4.2, ch. 7 D11 §11.6 A write in I broadcasts a read-for-ownership (BusRdX): all other copies become I (an M copy is written back or forwarded first) and the requester enters M. A write in S needs only permission, not data (BusUpgr): other copies become I and the requester enters M (the Primer's GetM and Upg transactions; Upg "does not require data to be sent to the requestor").D4 §6.4.2 The E state exists to make the common pattern "read, then write a private line" cost one bus request instead of two.D4 ch. 7 §7.3 "Adding the Exclusive State" (title only) D3 ch. 5

Snooping and directories

In a snooping protocol every request is seen by every cache, which needs a broadcast medium that orders requests; it is simple ("logically simple" in the Primer's words) but the broadcast traffic grows with the number of cores.D4 §6.4.3 D3 ch. 5 In a directory protocol a directory records, per line, its state and which caches hold it; requests go to the directory, which forwards them only to the caches involved. This scales to more cores at the cost of directory storage and an extra step of indirection. In the Primer's words, "This additional level of indirection increases the latency of some coherence transactions", and the full sharer list "requires a significant amount of storage", which coarse vectors, limited pointers and directory caches reduce.D4 §8.1, §8.5, §8.6 D3 ch. 5 D11 §11.6

False sharing

Coherence states are kept per line. If thread 0 writes variable a and thread 1 writes variable b, and a and b are in the same line, every write by one thread must invalidate the other's copy and take the line over, although the threads share no data.D1 ch. 12 D3 ch. 5 D11 §14.5 The MESI model shows this as "ping-pong" (one bus transaction per write); placing each variable in its own line removes it. In C++, alignas(64) on the type places each object at a 64-byte boundary (an "extended alignment", greater than alignof(std::max_align_t), which makes the type over-aligned) and makes its size a multiple of 64.D6 §6.8.3 Dive Into Systems shows the same fix as padding the array, and prefers per-thread local counters merged once at the end.D11 §14.5

Layer 3 — the engineer's depth

Variants. Real protocols extend MESI: an Owned state (MOESI) lets a dirty line be shared without first writing it back, and a Forward state designates which sharer answers requests.D4 §6.4.1 (Owned state) D3 ch. 5 Which variant a particular processor uses is a vendor detail.

Not verified — check before relying on this

The coherence protocol variant, the interconnect (ring, mesh) and whether a directory or snoop filter is used in the build container's processor were not checked; the model of this chapter is a teaching protocol on an ideal bus. Check the vendor's documentation for the exact processor model in the .log files (for example its optimisation reference manual or uncore documentation) before stating any of these. To test it you need a physical machine with a documented processor model and, for counting coherence events, its performance-counter event list; the verifier's container was another virtual machine and could not test it either.

Atomics need ownership. An atomic read-modify-write (such as fetch_add) must read and write the line without another core writing in between, so the core obtains the line in M (or E) for the duration of the operation.D4 §6.4.1–6.4.2 That is why the false-sharing program uses fetch_add: every increment needs exclusive ownership, which makes the coherence cost visible in every iteration. (A plain store loop can be absorbed by a core's store buffer for a while, F1-37, which hides part of the cost.)

Coherence is not consistency. Coherence talks about one location at a time. It says nothing about the order in which a core's writes to different locations become visible to others; that is the memory consistency model, F1-37.D4 §1.1–1.2, §3.3 A coherent system can still let another core see a later write before an earlier one to a different address.

Detecting false sharing. The evidence pattern is: more threads, more time, even though threads share no data; the time drops when the data is padded. A race detector (ThreadSanitizer) confirms that there is no data race, which separates false sharing from a real sharing bug.D10 On machines with hardware counters, coherence events (such as snoop hits on modified lines) can be counted; the event names are processor-specific and were not available in this build.

How the hardware actually does it

Each cache controller is a state machine per line, with the coherence state stored next to the tag. In a bus-based snooping design every controller watches the bus; a controller that holds a line in M and sees another core's read request supplies the data (or writes it back) and changes the line's state; tag lookups for snooping must not starve the core's own lookups, which is one reason designs duplicate tags or use snoop filters (the Primer describes inclusive directory caches built from duplicate L1 tags).D4 §6.4.3, §8.6.2 D3 ch. 5 With many cores the bus is replaced by a network (F1-30) and a directory or a filter in the shared cache tracks which cores may hold each line.D3 ch. 5 The build container is a virtual machine with four virtual CPUs; how they map onto physical cores of the host was not visible to it.

Worked example

Three cores; all lines start in I. Trace (core, op, line): 0 R 40; 1 R 40; 0 W 40; 1 R 40; 2 W 40; 2 W 40; 0 R 80; 0 W 80; 1 W 80.

  1. 0 R 40: miss, no other copy → BusRd, core 0 = E. States (0, 1, 2): E I I.
  2. 1 R 40: BusRd; core 0 has E → drops to S; core 1 = S. S S I.
  3. 0 W 40: core 0 in S → BusUpgr; core 1 invalidated. M I I.
  4. 1 R 40: BusRd; core 0 has M → writes back, drops to S; core 1 = S. S S I.
  5. 2 W 40: core 2 in I → BusRdX; cores 0 and 1 invalidated. I I M.
  6. 2 W 40: hit in M, no bus traffic. I I M.
  7. 0 R 80: new line, no other copy → E. 0 W 80: E → M silently.
  8. 1 W 80: BusRdX; core 0's M copy written back and invalidated; core 1 = M.
  9. Bus transactions: steps 1, 2, 3, 4, 5, 7 and 9 = 7.

Where the analogy breaks


    

  1. No one waits to hear the shout. A cook can keep cooking from a torn-up copy for a moment by mistake; a coherent cache never returns a value from an invalid line: the core waits until it has a valid copy.D4 §6.4.1
    2. 

  2. Sheets are fixed by the hardware. In the kitchen you could print each recipe on its own sheet whenever you like. In a computer, the "sheet" is the 64-byte line chosen by the address; only the program's data layout decides which variables share it.D1 ch. 12
    3. 

  3. Coherence is not about order between recipes. The kitchen rule might suggest that everyone sees all changes in the same order. Coherence only orders writes to the same location; the order of changes to different locations is a separate question (F1-37).D4 §3.3
    4.

Summary


    

  • Coherence: for each location, one writer or many readers, and reads see the latest write.
    • 

  • MESI keeps a state per line per cache: Modified, Exclusive, Shared, Invalid.
    • 

  • Writes need ownership: other copies are invalidated (BusRdX / BusUpgr in the course model).
    • 

  • E allows a silent upgrade to M for private data.
    • 

  • Snooping broadcasts requests; directories track sharers and scale further.
    • 

  • Coherence works per line, so independent variables in one line cause false sharing; pad per-thread data.
    • 

  • Coherence is per location; ordering across locations is consistency (F1-37).

Observation: packed: 125.8 ms (1 thread), 1109.4 ms (2), 2489.6 ms (4); padded: 124.0, 121.5, 283.7 ms (R3). With four threads the packed layout was about nine times slower than the padded one in this run. No race: ThreadSanitizer reported nothing and every counter reached its target (the program prints "unexpected count" otherwise); each thread writes only its own atomic (R4). So the results are correct and the problem is speed only. Layout: sizeof(Packed) = 8, so eight counters fit in one 64-byte line: all four threads' counters share one line. Hypotheses: (H1) data race / lock contention — ruled out by evidence 3 and by the code (no shared variable, no lock); (H2) the machine is overloaded — not enough: the padded layout with the same thread count is fast; (H3) false sharing — supported: only the layout differs between the two columns. Model: two cores writing one line need one bus transaction (BusRdX with write-back) per write; writing two lines needs two transactions in total (R2). Every fetch_add on the packed layout must win the line from another core. Fix: struct alignas(64) for the per-thread slot (the Padded version), or local counters merged once. The remaining rise of the padded time at 4 threads on the shared VM is small in comparison and was not investigated further. Prevention: a scaling test (1, 2, 4 threads) in CI that fails if the 4-thread time exceeds the 1-thread time by a set factor. How the evidence was made: run.sh in university/labs/F1-36/.
