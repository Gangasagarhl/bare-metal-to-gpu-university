Story hook

Analogy

Three helpers prepare the same forty dishes. Lina keeps going back to the same few jars all evening: salt, oil, pepper. Once they are on the shelf by the stove, she never walks to the pantry again. Kofi needs every jar on a tray, left to right; one trip brings eight jars, and he uses all eight. Tomás needs one jar from each tray, then the next jar from each tray, and so on: each trip brings a whole tray, he uses one jar, and by the time he wants the second jar of that tray the shelf has filled up and the tray has gone back.

All three cook the same dishes with the same number of steps. Lina and Kofi are fast; Tomás is slow. The difference is not what they fetch but the order in which they fetch it. That order has a name: locality.

What you will be able to do

  • Explain temporal and spatial locality and the three kinds of misses (compulsory, capacity, conflict).
  • Predict the number of misses of a loop nest in a small cache, then check the prediction with the course simulator (the course's practical exam task).
  • Measure the stride benchmark ("memory mountain") of your own CPU and read its ridges and slopes.
  • Diagnose "same work, ten times slower" from timings and cache counts, and say honestly which counts are simulated and which are hardware counters.
  • Fix a cache-unfriendly loop by changing its traversal order.
Jargon box
Temporal locality
Simple words: if you used something a moment ago, you will probably use it again soon. Analogy: Lina's salt, oil and pepper. Precise: the tendency of a program to access the same memory location again within a short time; caches exploit it by keeping recently used lines. D1 ch. 6 D2 ch. 5 D11 §11.3
Spatial locality
Simple words: if you used something, you will probably use its neighbours soon. Analogy: Kofi using every jar on the tray. Precise: the tendency of a program to access locations near recently accessed ones; caches exploit it by moving whole lines. D1 ch. 6 D2 ch. 5 D11 §11.3
Stride
Simple words: how far apart, in elements, two accesses in a row are. Analogy: Tomás taking one jar from each tray. Precise: in a stride-k reference pattern a program accesses every k-th element of a sequence; stride 1 is sequential access. D1 ch. 6
Compulsory miss
Simple words: the miss you cannot avoid the first time you touch a line. Analogy: the first trip for a tray that was never on the shelf. Precise: a miss on the first access to a line (a cold miss); it occurs even in an infinitely large cache. D1 ch. 6 D3 ch. 2, App. B D11 §11.4.2
Capacity miss
Simple words: a miss because the cache is too small for what you are using. Analogy: the shelf is full, so a tray you will need again goes back. Precise: a miss that would occur even in a fully associative cache of the same size, because the working set is larger than the cache. D1 ch. 6 D3 ch. 2, App. B D11 §11.4.2
Memory mountain
Simple words: a table or 3-D chart of read speed for many sizes and strides. Analogy: a map of how fast each helper can work for every size of order and every way of picking jars. Precise: the read throughput of a stride benchmark as a function of working-set size and stride; its ridges show the cache levels, its slopes show spatial locality. D1 ch. 6
Row-major order
Simple words: a table stored row by row: first all of row 0, then all of row 1. Analogy: trays lined up row after row in the pantry. Precise: the layout in which element [i][j] of an n-column array is stored at position i × n + j; C and C++ arrays use it. D1 ch. 6 D6 §23.3.13.1 D11 §11.3

The idea in pictures

Figure 1 shows a small matrix stored in row-major order and the two ways of walking it. Walking along rows uses every element of each line before moving on. Walking down columns uses one element per line and jumps a whole row each step.

Figure 2 shows why stride costs bandwidth: memory moves whole 64-byte lines, so a stride-k walk over 8-byte elements uses 8 ÷ k of each line for k ≤ 8, and one element per line for k ≥ 8.

Layer 1 — the kid explanation

A cache helps only if you come back to things. Coming back to the same thing soon is temporal locality. Using the neighbours of something you used a moment ago is spatial locality.D1 ch. 6 D11 §11.3

Because the cache always fetches a whole line, reading neighbours is almost free: they arrived with the first one. Jumping far each time wastes most of every line you fetch.D1 ch. 6

So two loops that do exactly the same additions can run at very different speeds. One walks through memory in order; the other jumps around. You will measure a difference of about nine times on this build's machine.R2

Layer 2 — the student explanation

Locality in code

Programs show locality because of how they are written: loops execute the same instructions repeatedly (temporal locality of instructions), loop variables and accumulators are reused (temporal locality of data), and arrays are walked element after element (spatial locality).D1 ch. 6 D2 ch. 5 In for (i) sum += a[i]; the variable sum has excellent temporal locality and a has stride-1 spatial locality.D1 ch. 6 D11 §11.3

Stride and miss rate

For 8-byte elements, 64-byte lines and data not yet in the cache, a stride-1 walk misses once per 8 accesses (12.5 %), stride 2 once per 4 (25 %), stride 4 once per 2 (50 %), and stride 8 or more on every access (100 %).D1 ch. 6 This is Figure 2 as arithmetic. The stride benchmark (Listing 1) measures the consequence: read throughput falls as the stride grows, until every access is a miss.

Three kinds of misses

Misses are classified as compulsory (first touch of a line), capacity (the working set does not fit even if lines could go anywhere) and conflict (lines that would fit compete for the same set, F1-33).D1 ch. 6 D3 ch. 2, App. B D11 §11.4.2 The classification tells you which fix can work: compulsory misses need fewer distinct lines or prefetching; capacity misses need a smaller working set (for example by processing data in blocks that fit); conflict misses need a different layout (padding) or more associativity.D3 ch. 2, App. B

Loop order on a row-major array

C++ stores a 2-D array (or a std::vector indexed as i * n + j) row by row.D6 §23.3.13.1 A loop nest whose inner loop runs over j walks with stride 1; one whose inner loop runs over i walks with stride n.D1 ch. 6 D11 §11.3 If n × 8 bytes is at least a line, the column walk misses on every access unless the lines it touched in one column survive until the next column; with n rows that means n lines must stay in the cache, which fails once n lines exceed the cache, or earlier if they conflict.D1 ch. 6 Swapping the two loops ("loop interchange") changes nothing in the result for a sum and turns the stride-n walk into stride 1.D3 ch. 2, App. B (For floating-point sums the order of additions can change the last bits of the result; for the all-ones matrix of Listing 2 it does not.)

Reading the memory mountain

The stride benchmark varies two things: working-set size (rows of Listing 1's table) and stride (columns). Moving down a column (larger sizes) you cross from one cache level into the next: those are the ridges. Moving right along a row (larger stride) spatial locality decreases: those are the slopes. Hardware prefetching keeps small-stride throughput high even for large working sets.D1 ch. 6

Layer 3 — the engineer's depth

Blocking (tiling). When a loop nest touches a large data set more than once, reorganise it to work on blocks small enough to stay in a cache level, finishing all the work on one block before moving on.D1 ch. 6 D3 ch. 2, App. B Blocked matrix multiplication and blocked transpose are the classic examples; the same idea, applied to GPU shared memory, is the tiling of F6-22.

Column walks also cost translation. In Listing 2 with n = 4096, consecutive reads of the column walk are 4096 × 8 = 32 KiB apart, so every read is in a different 4 KiB page. The TLB (F1-38) covers only a limited number of pages, so the column walk also pays for page-table walks; part of its slowdown is translation, not caching.D1 ch. 6 Distinguishing the two needs hardware counters for TLB misses.

Simulated counts versus hardware counts. Cachegrind (part of Valgrind) runs the program on a synthetic CPU and simulates a first-level cache and a last-level cache with a geometry you give it (options --I1, --D1 and --LL, each as size, associativity and line size; without them it reads the host's cache description through the CPUID instruction).D9 ch. 5 D11 §11.5 Its counts are exact for the model but are not what the processor did: real hardware has more levels, prefetchers, different replacement and a TLB; the manual itself says the simulation "is not a true representation of what's happening in the cache", that it works with virtual addresses, and that it does not model TLB misses or speculative execution.D9 ch. 5 Hardware counters (read with perf stat on Linux) count the processor's own events, but their event names and meanings are processor-specific; the manual page says that PERF_COUNT_HW_CACHE_MISSES counts cache misses "usually" of the last-level cache, and that glibc has no wrapper for the call, so Listing 4 uses syscall.D8 perf_event_open(2) On the build container neither the perf tool nor hardware events were available (evidence in the forensic lab), so this chapter's counts are simulated and labelled so.

Not verified — check before relying on this

The exact perf event names for L1, last-level cache and TLB misses on your processor (for example whether generic events such as cache-misses map to last-level misses) were not checked in this build. Check the "perf-list" manual page and the vendor's performance-monitoring event documentation for your processor model, and record the event list perf list prints on your machine. To test it you need a physical machine (or a virtual machine type that exposes the performance-monitoring unit) with a perf build that matches its kernel; neither the build container nor the verifier's container had one.

How the hardware actually does it

Spatial locality pays off because a miss brings a whole line (F1-33) and because hardware prefetchers notice sequential or constant-stride streams and request the next lines before the program asks.D1 ch. 6 D3 ch. 2, App. B Temporal locality pays off because a recently used line is the last one LRU-like policies evict.D1 ch. 6 Large strides defeat both: each access needs a new line, and once the stride crosses page boundaries each access may also need a new translation (F1-38).D1 ch. 6

Worked example

Predict first. Cache: 8 sets × 2 ways × 64-byte lines (1 KiB, 16 lines, LRU). Matrix: n × n doubles at address 0, row-major. Count misses for row order and column order.

  1. n = 8 (512 bytes = 8 lines, everything fits): each line is fetched once in either order. Rows: 8 misses. Columns: 8 misses. All compulsory.
  2. n = 16, rows: 256 accesses, 8 per line → 256 ÷ 8 = 32 misses, all compulsory.
  3. n = 16, columns: a row is 128 bytes = 2 lines. Column j (j < 8) touches line 2i of each row i: lines 0, 2, 4, …, 30, sixteen lines. Line L goes to set L mod 8, so these sixteen lines use only sets 0, 2, 4 and 6: four lines per 2-way set. With LRU, each set's two slots are overwritten before the next column comes back, so every one of the 256 accesses misses. A fully associative 16-line cache would hold all sixteen lines and miss only 32 times: these are conflict misses.
  4. n = 64, rows: 4096 ÷ 8 = 512 misses (compulsory). Columns: each column touches 64 lines, four times the cache's 16 lines: every access misses, 4096 misses. Even a fully associative cache could not keep 64 lines: capacity misses.

Then check: Listing 3 runs these six cases through the F1-33 model; its table shows 8/8, 32/256 and 512/4096.R3

Where the analogy breaks


    

  1. Helpers can be told the order; caches only see it. Amina could tell Tomás to take all eight jars of a tray at once. A cache cannot reorder a program's accesses; only the programmer or the compiler can (loop interchange, blocking).D3 ch. 2, App. B
    2. 

  2. The pantry's trays have fixed boundaries. A kitchen tray could be packed with whatever jars are convenient. A cache line always holds the aligned 64 bytes around an address, so an array that starts in the middle of a line, or a record that straddles two lines, costs extra misses that no helper would suffer.D1 ch. 6
    3. 

  3. "Coming back soon" is measured in other accesses, not minutes. Lina's salt stays on the shelf because she uses it often in time; a cache line survives only if fewer than a set's worth of other lines mapped to its set are touched in between.D1 ch. 6
    4.

Summary


    

  • Temporal locality: reuse the same data soon. Spatial locality: use neighbours of data you used.
    • 

  • Caches fetch whole lines, so stride-1 access uses every fetched byte and large strides waste most of them.
    • 

  • Misses are compulsory, capacity or conflict; each has a different cure.
    • 

  • Loop order on a row-major array decides the stride: the last index should change fastest.
    • 

  • The memory mountain shows ridges (cache levels) and slopes (stride) of your own machine.
    • 

  • Cachegrind counts are simulated; hardware counters need a working perf and a machine that exposes them — the build container had neither.

Forensic lab answer key


Observation: 217.2 ms versus 24.8 ms, a ratio of about 8.8 on the build container (R2); both compute the same sum with the same 16.8 million additions. No counters: the perf command is a wrapper that found no perf binary for the running kernel (evidence 3), and the kernel refuses hardware events with "No such file or directory" while software events work (evidence 4): the virtual machine exposes no hardware performance-monitoring unit to this guest; therefore all counts are from a simulator (R4). Simulated reads: about 4.71 million data reads in each run (4.19 million matrix elements plus other reads). Row order misses D1 on 536,800 reads, about 1 in 8: one miss per 64-byte line of eight doubles. Column order misses on 4,206,815 reads, about 89 % of all reads and essentially every matrix element: consecutive reads are 16 KiB apart, so each is a new line, and the 2048 lines of one column do not survive until the next column needs them (R5). Writes: the 4.19 million writes are the initialisation std::vector<double> m(n * n, 1.0); 526,502 write misses ≈ one per line of 8 doubles; identical in both runs because initialisation does not depend on the summing order. Last-level misses: each row is 2048 × 8 = 16,384 bytes. The simulated 2 MiB, 16-way, 64-byte-line LL has 2048 sets, so sets × line = 131,072 bytes; addresses 16 KiB apart therefore use only every eighth set (131,072 ÷ 16,384 = 8 distinct set positions per column), and the 2048 lines of a column compete for 8 sets × 16 ways = 128 slots: conflict misses. With the 256 MiB control LL the column's lines spread over many more sets and its LL read misses drop from 4.2 million to about 7,600 (evidence 6). Root cause: the inner loop of sumCols runs over the row index, giving a stride of n × 8 bytes; the refactoring swapped the loops. Fix: make j the inner loop (as sumRows). Verification on a machine with counters: perf stat with the processor's L1-data and last-level miss events (names from perf list, unverified here) for both versions, plus the timing ratio. Prevention: a benchmark in CI and a code-review rule "last index innermost". How the evidence was made: run.sh in university/labs/F1-34/ (all runs in this build).
