Story hook

Tomás has fitted a new, wider window frame in the kitchen. Before the glass goes in, Kofi comes to check it. That is the team's rule: a second carpenter checks every joint. Kofi could look only at the new frame, see that its corners are square and its joints tight, and say "good work". The frame is good work.

Instead Kofi steps back and looks at what the frame touches. Above it is the lintel, the beam that carries the wall over the opening. Nobody changed the lintel. It was made for the old, narrower window, and now it rests on less than a hand's width of brick at one end. "The frame is lovely," Kofi says. "What is the lintel resting on now? I think it was sized for the old opening. Could we check before the glass goes in?" Tomás measures. Kofi is right; a longer lintel goes in the same afternoon.

Kofi's comment was kind and precise: it praised what was good, pointed at an exact place, asked a question instead of accusing, and gave a reason. And it was about the part of the work that was not in the change. This chapter is about giving review like that.

What you will be able to do

  • Explain what code review is for: finding defects, checking the design against its document, sharing knowledge, and keeping a codebase consistent.
  • Read a change in a useful order (description, tests, interfaces, implementation) and then read the code the change depends on but does not show.
  • Ask the reviewer's standard questions: boundaries, error paths, lifetimes, context, units, changed tests, and sources for hardware facts.
  • Write comments that are precise (location, label, reason, proposal) and kind (about the code, not the person), and check them mechanically.
  • Review real university project code and decide between approving and requesting changes.
  • Diagnose a merged change that caused an incident, and name the review question that would have caught it.
Jargon box
Code review
Simple words: someone other than the author reads a change before it is accepted, and writes down what they find. Analogy: a second carpenter checks your joints (registered F12 mapping). Precise: a written examination of a proposed change (code, tests, documents) by one or more reviewers against the design document, the codebase's rules and their own experience, ending in a recorded decision (approve, or request changes) and a thread of comments the author answers; besides finding defects it spreads knowledge of the code, a purpose the registered analogy's "where it breaks" note names D3. D1 describes code review as practised in one large company D1.
Change (patch)
Simple words: one proposed set of edits to the code, sent for review as a unit. Analogy: the new window frame, as one piece of work. Precise: a set of modifications to files, with a description of what and why, reviewed and accepted or rejected as a whole; in git, one or more commits on a branch; a good change does one thing, so its review has one question to answer.
Unified diff
Simple words: a printout of a change that shows removed lines with a minus, added lines with a plus, and a few unchanged lines around them. Analogy: a photo of the new frame with a little of the wall around it, but not the lintel. Precise: the output format of diff -u and of git diff: file headers (---, +++), then hunks headed @@ -l,s +l,s @@ giving the start line and length in the old and new file, with three lines of context by default; context shows only lines near a change, so code a change depends on may be invisible D4 R3.
Comment label (review)
Simple words: a word at the start of a review comment that says how much it matters. Analogy: "must fix before the glass goes in" versus "nicer finish if you have time". Precise: in this course, one of blocking (must be resolved before approval), suggestion (author decides), question (reviewer needs an answer to judge), nit (small style point, optional) and praise (specific good practice, so it is kept and copied); labels let the author sort the thread and stop small points from being read as demands.
Blocking comment
Simple words: a comment that says "this must change before I can approve". Analogy: "the lintel may not hold; we check before the glass goes in". Precise: a review comment whose resolution is a condition of approval; in this course it must state the reason (the defect, risk or rule) and propose a change or ask the question that would settle it, and it is resolved only by a change or by the reviewer's recorded agreement (F12-05).
Review checklist
Simple words: a short list of questions a reviewer asks of every change. Analogy: the carpenter's habit of always looking at what a frame rests on. Precise: a written, short, project-specific list of questions applied to every change (boundaries, error paths, resource lifetimes, calling context and concurrency, units and interfaces, changed or deleted tests, untrusted inputs, sources for hardware facts), kept next to the code and extended after each incident whose cause a question would have caught.

Terms from earlier courses used here: commit (SP202, F2-31); AddressSanitizer, buffer overflow (SP201, SP202); bounded wait and surprise removal (DR401); continuous integration (CI); from this course interface contract and failure mode.

Layer 1 — the kid explanation

Analogy

Mapping (F12; registered: code review = a second carpenter checks your joints; the rest proposed in NOTES.md): the new frame = the change; the photo of the frame with a little wall around it = the diff; the lintel nobody changed = code the change depends on but does not show; "the frame is lovely" = a praise comment; "what is the lintel resting on now?" = a question comment with a reason; "we check before the glass goes in" = a blocking comment. The registered warning holds: reviews also share knowledge, not only find defects.

When you review, you are helping a teammate, not grading them. You read their change carefully, you look at what it touches, and you write down what you find so they can use it. Every comment says where, what, why, and what could be done.

Kind does not mean vague. "Looks fine" is not kind if the lintel is about to crack. Kind means you talk about the work, not the person, you ask when you are not sure, and you say what is good as specifically as what is wrong.

Layer 2 — the student explanation

What review is for

A review has four purposes, and a good reviewer keeps all four in mind:

  • Defects. Find mistakes before users do: wrong boundaries, unhandled errors, leaked resources, races.
  • Design. Check the change against its design document (F12-02): does it do what the goals say, handle the failure modes listed, keep the interface contract?
  • Knowledge. After the review, at least two people understand the code. The registered analogy says it: reviews also share knowledge, not only find bugs D3.
  • Consistency. The codebase keeps one style of error handling, naming and testing, so the next reader is not surprised.

D1 discusses the purposes and costs of code review in one large company D1; this course's rules below are its own and are justified by the labs you run.

Not verified — check before relying on this

This chapter makes no claim about how effective code review is in general (how many defects it finds, the best size of a change, how fast reviewers read). Such numbers exist in the literature, but no study was opened in this build. The Source Researcher should look for a peer-reviewed study (tier 5) or D1's own statements, and record them in the dossier before any such number is added.

Reading a change in order

  1. The description. What does the change claim to do, and why? If you cannot tell, that is your first comment. Find the design document it implements.
  2. The tests. Read them before the implementation: they say what the author thinks the code must do. Look especially at tests that were changed or deleted: a changed expectation is a changed requirement, and it needs a reason.
  3. The interfaces. New or changed functions, types, constants, file formats. Apply the seven contract questions of F12-02.
  4. The implementation. Now read the code, with the tests and the contract in mind.
  5. The code around the diff. For every changed name or value, search the file and the project for the other places that use or duplicate it. The diff shows three lines of context D4; the code a change depends on may be anywhere.

Reviewers may also run things. Two runs are cheap and powerful: the change's tests under sanitizers (CI should already do this), and the old tests against the new code. The forensic lab shows the second one finding the bug that the change's own tests could not.

Writing a comment

Every comment has four parts: where (file and line), what you see, why it matters (the consequence, the rule, the evidence), and what could be done (a proposal or a question). A label in front says how much it matters. Compare two comments on the same line of real university code (worked example):

  • "Why didn't you add a timeout? Infinite loops in a driver are obviously wrong." No location, no label, judges the person, and "obviously" hides the reason. The author learns that the reviewer is annoyed, not what to do.
  • "rtc.cc:47 [blocking] This wait, the one on line 50 and the for(;;) on line 49 have no bound. If the status register ever keeps bit 7 set (a chip that is absent or broken), the caller hangs here without a message, because the loop has no exit. Our design table asks for a timeout on every wait (curriculum 5.4, row "Error handling"). Could read_raw() give up after a fixed number of polls and return a failure the caller can report?"

The second is longer and much kinder: it gives the author everything needed to act, and it leaves room for the author to know something the reviewer does not. Listing 1 checks the mechanical part of these rules: location, label, a reason and a proposal in blocking comments, and a list of words that judge the person or pretend the point is self-evident. A clean run means "no known problem", not "kind": tone is ultimately read by people.

Layer 3 — the engineer's depth

Approve or request changes

An approval says: "I read all of it, I understood it, and I am willing to share responsibility for it." It does not say "I believe it has no bugs". Approve when no blocking comment is open; suggestions, questions already answered and nits do not hold a change back. Request changes when a blocking comment is open, and say which ones. If you cannot judge part of a change (an unfamiliar subsystem, a hardware detail you cannot check), say so in a comment and name who should review that part; an approval that silently skips part of a change is the most dangerous kind, because the author and everyone after believe that part was reviewed.

What is blocking

Block for: a defect or a likely defect (with the scenario); a violated goal, failure mode or interface contract from the design document; a missing test for a new behaviour or a boundary; a changed test without a reason; a safety or security risk; a hardware fact without a source in driver code. Do not block for: a different but equivalent style; a design you would have chosen differently when the chosen one meets the document (write a suggestion, or argue in the design review next time); improvements outside the change's scope (suggest a follow-up). Blocking for taste teaches authors to ignore labels.

Size and focus

Review works on changes a reviewer can hold in their head. A change that renames a module, fixes a bug and adds a feature has three questions mixed together; ask the author to split it, kindly and early. Within a change, spend attention where the risk is: interfaces, boundaries, error paths, concurrency and anything that touches hardware or data on disk. Mechanical points (formatting, simple style) belong to tools (a formatter, warnings as errors, sanitizers in CI: SP202) so that review time goes to what tools cannot see. The unverified box in Layer 2 applies here too: this chapter gives no number for a "good" change size.

Kindness as precision

Several habits make comments both kinder and more useful, and none of them makes them vaguer:

  • About the code, never the person. "This loop has no bound", not "you forgot the bound". "We" for shared rules: "our design table asks…".
  • Questions when you are not sure. "Is the C header on purpose for the freestanding build?" lets the author teach you; a wrong assertion costs trust.
  • Reasons, always. A comment without a reason is an order; with a reason it is engineering, and the author can disagree with the reason.
  • Specific praise. "The comment explains the torn-read problem with a concrete example" tells the author what to keep doing and the team what to copy. "Nice!" tells nobody anything.
  • No hidden reasons. Words such as "obviously", "just", "simply", "clearly" imply that the point needs no explanation; if it is obvious, the reason is short, so write it.
  • One round, complete. Write all your comments in one pass where possible, so the author is not surprised by a new blocker in round three that was visible in round one.

When you are the only reviewer

In small learner teams, one reviewer is common. Then the checklist matters more, and two cheap habits help: run the old tests against the new code, and write down in the approval what you did not review ("did not check the register offsets against the datasheet; Mei will"). The mega projects' design-review gates need written approval by reviewers and name who signs D3; code review inside a project follows the same idea at a smaller scale.

How the hardware actually does it

Reviewing driver code adds questions the hardware forces, and the curriculum's design table 5.4 is the reviewer's checklist for them D2. Waits: a device may never become ready, and a removed device reads as all ones ("surprise removal (reads return all ones)" in the error-handling row), so a status bit that means "busy" can look set forever; every wait needs a bound (the worked example's blocking comment). Trust: lengths, indices and descriptor contents come from the device and are treated as untrusted (the "Trust" row); the forensic lab's length byte is such a value. Register model: access widths, write-1-to-clear bits, posted writes that need a read-back, ordering barriers; each register used must name its document and section (runbook) D2. Context: what runs in the interrupt handler and what is deferred ("Interrupts" row).

There is one more hardware fact a reviewer must keep in mind: in a kernel, there is usually no AddressSanitizer watching. The forensic lab's overflow was caught because the team replayed the recorded frames through a sanitizer build on the host; in the robot's firmware, the same write would silently overwrite whatever lies after the array on the stack, and the symptom would appear somewhere else, later. That is why the reviewer's boundary question is worth more in low-level code than anywhere else: the review may be the last place the bug can be seen before it becomes an incident R5.

Where the analogy breaks


    

  • Reviews also share knowledge. A second carpenter checks a joint and walks away; a code reviewer becomes the second person who understands the code, which matters on the day the author is away and the code breaks (the registered note) D3.
    • 

  • The reviewer can run the work. A carpenter cannot load the lintel to see whether it fails; a reviewer can run the old tests on the new code in seconds. The analogy makes review look like inspection only.
    • 

  • Code has no visible "around". Kofi saw the lintel by stepping back. In a diff, the code a change depends on is not in view at all, sometimes in another file; it has to be searched for on purpose.
    • 

  • The work is copied. A bad joint stays in one house; a pattern approved in review gets copied into the next ten changes. Praise and blocking comments shape the codebase far beyond the change.

Forensic lab answer key


How the evidence was produced. frame_v1.cpp declares the payload array with a literal 16 while the length check uses kMaxPayload; frame_v2.cpp is the same file with only kMaxPayload raised to 32; frame_v2.in replaces the 17-byte over-length test by a 40-byte one. run.sh produced the diff (R3), and ran version 2 on the recorded frames (R5) and on the version 1 tests (R4) R3 R4 R5.


Observation. The report: "stack-buffer-overflow … WRITE of size 1 … in frame::parse … frame_v2.cpp:40", object "'f' (line 35)", "Memory access at offset 64 overflows this variable", after case 1 passed: the second frame (24-byte payload) is written past the end of Frame f. Line 40 is f.payload[i] = in[3 + i];; line 22 declares payload as std::array<std::uint8_t, 16>.


Why CI passed. Only test 6 used a length above 16; the change moved it from 17 to 40, and 40 is rejected by the length check before any byte is copied. No test had a length from 17 to 32.


Why the line was not in the diff. The diff shows three lines of context around line 16; line 22 is outside it (Figure 2). The constant and the array size encode the same limit in two places, and only one was changed.


Prediction for question 4, and the run. The old test file's case 6 (len 17, expected reject) now passes the length check and copies 17 bytes into 16: AddressSanitizer stops it at the same line. The run confirms it: cases 1–5 pass, then the same report at frame_v2.cpp:40 R4:




The old test was the one that would have caught the bug; the change edited it away. Running the old tests against the new code during review would have found it in seconds.


The comment that would have caught it. "frame.cpp:16 [blocking] kMaxPayload now allows 32 bytes, but is the same limit encoded anywhere else? Frame::payload on line 22 is still std::array<std::uint8_t, 16>, so a 17–32-byte frame would be written past it, because the copy loop on line 40 runs to len. Could the array use kMaxPayload, and could we keep a test at 17 and add tests at 32 and 33?" It comes from two checklist questions: "for every changed constant, where else is the old value encoded?" and "for every changed test, why, and does the old test still pass?"


Alternative explanations to rule out. "The sensor firmware sends malformed frames": the 24-byte frame is valid (correct start byte, length and checksum) and expected "ok". "The checksum code is wrong": the report is a write to payload, not a checksum mismatch. "Sanitizers caused the crash": the sanitizer detected an out-of-bounds write that happens in every build; without it the write corrupts the stack silently, which matches the garbage telemetry before the crash.


Fix and prevention. One constant: std::array<std::uint8_t, kMaxPayload>, a static_assert tying the constant to the one-byte length field, and boundary tests at 16, 17, 31, 32, 33 and 255, plus the recorded frames as a regression test. F12-05 shows that fix going through review (frame_v3.cpp). Process: add both questions to the team's review checklist; let CI also run the previous version's tests and fail on any test the change deleted or edited without a recorded reason.
