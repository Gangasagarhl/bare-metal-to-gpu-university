Story hook

Ayasha, Tomás and Mei are building a small house together. On the first morning Tomás is eager: the bricks are there, the mortar is mixed, so he starts the kitchen wall. By lunch it is waist-high and straight. Then Mei arrives with the water pipe. Where should it go through the wall? Nobody decided. Tomás knocks out six bricks, the pipe goes in, the wall is patched. In the afternoon Ayasha asks where the window is. The wall comes down to the second row.

The next morning they sit at the table before anyone touches a brick. They draw the kitchen: where the pipe enters, where the window goes, what happens if it rains before the roof is on. Drawing takes an hour; erasing a line takes a second. Everyone signs the drawing, and every builder knows which line their work must match. When the inspector comes, she checks the house against the drawing, line by line.

The drawing is a design document. Each line on it is a decision someone can check. This chapter is about drawing before building: the curriculum's rule to write the plan before the code, and why a plan whose lines turn into tests is the cheapest bug-finder you will ever own.

What you will be able to do

  • Explain the curriculum's rule 10, "write the plan before the code", and the four things it asks a plan to cover: data structures, hardware sequence, failure modes, and how the acceptance tests will observe success.
  • Write a one-page plan for a small driver component in which every decision has an identifier that a test can name.
  • Turn each plan line into an acceptance test, so that a failing test points back to a written decision.
  • Decide how much plan a change deserves, from how hard it is to undo and how many people it affects.
  • Diagnose a defect that exists because a decision was never made, and name the plan line that would have forced it.
Jargon box
Design document (design doc)
Simple words: a written plan for a piece of software, made before the code, that says what will be built, how, and how we will know it works. Analogy: the house blueprint that every builder signs before the first brick. Precise: in this university, a dated, reviewed document that records the context, goals and non-goals, the design and its interfaces, the alternatives considered, the failure modes, the test plan and the open questions of a change; the driver-specific design note of DR401 (one row per aspect of curriculum table 5.4) is one section of it. The curriculum's runbook asks for "a short design note" before code D2; design documents as a team practice are discussed in D1 D1.
Acceptance test
Simple words: a test, agreed in advance, that decides whether the work is done. Analogy: the inspector's checklist, written before building, that the house must pass. Precise: an executable check (a host test, an emulator scenario with expected serial output, a measurement against a target) that is written down in the plan before the implementation and is not weakened afterwards without the approver's agreement; the curriculum's milestones list theirs and its definition of done requires all of them to pass from a clean build D2.
Failure mode
Simple words: one specific way a thing can go wrong. Analogy: "what if it rains before the roof is on?" Precise: a named condition under which a component cannot do its normal job (input arrives too fast, a device stops answering, a counter reaches its largest value, a caller passes a value out of range) together with the component's chosen behaviour in that condition. Curriculum rule 10 lists failure modes as one of the four things a plan must cover D2.
Traceability (plan to test)
Simple words: every decision in the plan has a test, and every test says which decision it checks. Analogy: the inspector's checklist refers to numbered lines on the blueprint. Precise: a two-way mapping between identifiers in the plan (here D1–D3, F1–F3) and acceptance tests (here P1–P5), kept in the test names and the plan, so that a test failure leads to a decision and a decision without a test is visible. This is the course's convention; the lab in this chapter uses it.

Terms from earlier courses used here: design note and test plan (DR401, F4-17, F4-18); ring buffer (SPSC) and interrupt handler (DR301, F4-03); unsigned wrap-around; unit test and regression test (SP202).

The idea in pictures

Figure 1 puts the two mornings of the story side by side, as software. On the top row, code comes first: each decision is made silently, inside the code, at the moment the author meets it, and is discovered by others only when something breaks. On the bottom row, the plan comes first: decisions are made on paper, a reviewer sees them while they cost a sentence, and each one becomes a test.

Figure 2 is the decision that the forensic lab of this chapter is about. A ring of eight slots can be "empty" or "full", and both look the same if all you keep is two positions inside the array. Writing the plan forces you to say how the code will tell them apart.

Layer 1 — the kid explanation

Analogy

Mapping (F12, registered: design doc = the house blueprint; the rest proposed in NOTES.md): the blueprint = the design document; a numbered line on the blueprint = a plan line such as D2 or F2; "what if it rains before the roof is on?" = a failure mode; the inspector's checklist = the acceptance tests; the builders signing the drawing = the plan's approval; knocking out bricks to fit the pipe = changing code after a decision was made silently. The registered warning holds: software blueprints change more often than house blueprints, so they must be kept alive.

A plan is a list of decisions you write down before you build. Writing a decision takes a minute. Finding out later that two people made different decisions takes much longer, because by then the decisions are buried in code and nobody remembers making them.

A good plan has numbered lines. Each line says one thing that will be true when the work is done: "when the ring is full, the new byte is dropped and counted". Then each line gets a test with the same number. If a test fails, you know which decision was broken. If a line has no test, you know which decision nobody is checking.

Layer 2 — the student explanation

What the curriculum asks for

The curriculum's runbook for every milestone contains this rule: "Write the plan before the code: a short design note covering data structures, hardware sequence, failure modes, and exactly how the acceptance tests will observe success. The learner approves the plan." D2 The next rule asks for tests first where possible: host unit tests for pure logic before the implementation, and the emulator scenario with its expected serial output before hardware-facing code D2. The definition of done then requires that every listed acceptance test passes from a clean checkout and that the design note is updated D2.

Read the four parts as four questions the plan must answer:

  1. Data structures. What state exists, who owns it, and what is always true about it (its invariant)? For the receive ring: eight bytes, two counters, "held = head − tail".
  2. Hardware sequence. In which order is the device touched, and what may happen between two steps? For the ring: the interrupt handler writes, the console task reads, and the handler may run between any two instructions of the task.
  3. Failure modes. What can go wrong, and what does the code do in each case? Nothing arrived; bytes arrive faster than they are read; a counter reaches its largest value.
  4. How the acceptance tests observe success. For each line above, what will a test look at, and what must it see?

The fourth part is the one learners skip, and it is the one that makes the plan useful. "The ring handles overflow" cannot be checked. "After nine pushes into an empty ring, eight bytes are held, one is counted as dropped, and the eight read back are the first eight" can be checked by a program, and the plan of this chapter says exactly that (line P3 of plan.txt).

Why the plan comes first

Three reasons, each of which you can check against your own experience rather than take on trust.

  • Every program contains decisions, written or not. The no-plan ring of the forensic lab also "decided" what happens when eight bytes arrive: it treats a full ring as empty and loses all of them (R2) R2. Nobody chose that; it fell out of the code. A plan does not add decisions; it makes the existing ones visible and deliberate.
  • A plan can be reviewed by someone who cannot read your code yet. A peer who has never seen the ring can read "F2: when full, overwrite the oldest byte" and say "that loses the start of a command; drop the newest instead". The same peer would need much longer to find that choice in thirty lines of index arithmetic. Reviewing plans is the subject of F12-02; reviewing code is F12-04.
  • The plan is where the acceptance tests come from. Tests written after the code tend to test what the code does. Tests written from the plan test what the code was supposed to do. The difference is exactly the class of bugs that "pass all tests".

Design documents as a practice in large teams (who writes them, who reviews them, when they are worth their cost) are discussed in D1 D1; this course uses its own small format, introduced fully in F12-02, so that the claims in these chapters rest on things you can run and check.

Traceability: the cheapest bug-finder

Give every plan line an identifier (D for data, F for failure, and so on) and give every acceptance test an identifier that names the lines it checks. Listing 1 does this literally: its output lines start with P1–P5, and plan.txt says which plan lines each P checks R1. Two kinds of gap become visible at once: a plan line no test names (an unchecked decision), and a test no plan line explains (a test that checks an accident of the code, which will break when the code is improved).

Layer 3 — the engineer's depth

How much plan does a change deserve?

Rule 10 says "a short design note" D2. Short is right for a milestone, but changes vary from a one-line fix to a new subsystem. This course sizes the plan by two questions, each answered before writing anything:

Easy to undo (one file, no interface, no data written to disk or device)Hard to undo (an interface others call, an on-disk or on-wire format, a hardware sequence that can leave a device in a bad state)
Affects only youA sentence in the commit message: what and why.A short plan: the four parts of rule 10, one page.
Affects others (callers, reviewers, operators)A short plan, shared before the code.A full design document (F12-02) with alternatives (F12-03), reviewed by at least two people before the code.

This table is this course's rule, not a fact about the industry. Its logic is the logic of the story: the more expensive it is to knock out the bricks, the more the drawing is worth. The receive ring of this chapter sits in the top-right cell when you write it for your own kernel (only you call it, but a wrong overflow policy loses user input silently), and moves to the bottom-right cell when a second learner's shell starts calling rx_pop.

Write invariants, not intentions

A plan line is useful when it states something that is always true, or always true at a named moment, in terms a test can evaluate. Compare:

  • "The ring is circular and handles wrap-around." (An intention: what does "handles" mean?)
  • "D2: held = head − tail; empty when held is 0, full when held is 8." (An invariant: a test can compute it after any sequence of operations.)
  • "F3: the counters pass the largest value of their type; head − tail is still correct." (A failure mode with its behaviour.) This line relies on a property of the C++ language: arithmetic on unsigned integers is performed modulo 2n, where n is the number of bits of the type, so the difference of two counters is still the number of bytes held after either one wraps D4. P5 checks it by starting both counters three below their largest value R1.

The habit carries far beyond rings. A page-frame allocator's plan states "free + used = total frames"; a scheduler's plan states "every runnable task is on exactly one run queue"; a network driver's plan states "every descriptor is owned by exactly one of driver or device". Each is a test waiting to be written.

What the host test does not check

Plans also record what their tests cannot observe. Listing 1 runs on the host, in one thread. The real receive ring is filled by an interrupt handler while the console task reads it, and its correctness then also depends on the order in which the two sides' memory writes become visible: the ring of F4-03 uses volatile counters and a compiler barrier between storing a byte and publishing the counter, and is written for one CPU D5. A complete plan for that ring adds a line such as "H1: the producer stores the byte before it publishes head; tested in QEMU by a paste test (F4-03's lab), not by Listing 1". Writing down where each line is tested is part of the plan; it stops a green host test from being read as proof of something it never ran.

How plans fail

  • The plan is theatre. It is written after the code to satisfy a rule. Symptom: no line in it was ever changed by a reviewer, and no test names its lines.
  • The plan is stale. The code changed and the plan did not. The registered analogy warning says it: software blueprints change more often; keep them alive D3. The curriculum's definition of done includes "design note updated" for this reason D2.
  • The plan is the code in prose. It lists every variable and every loop, so nobody reads it. Plan decisions, invariants and tests; leave the mechanics to the code.
  • The plan has no failure modes. It describes the day everything works. The forensic lab of this chapter is that plan's consequence.

Who approves, and what approval means

Rule 10 ends with "The learner approves the plan" D2: in the curriculum, an agent writes the plan and the learner approves it. In SE301 you write the plan and a peer approves it. Approval means "I read every line, I understand what each test will check, and I accept the failure-mode decisions"; it does not mean "I believe the code will be correct". The mega projects' design-review gates (R1 design review onwards) use the same meaning, with written reviewer approval D3.

How the hardware actually does it

Hardware is why the "hardware sequence" and "failure modes" parts of rule 10 exist. A device does not wait for your code. The UART of F4-03 raises an interrupt for received bytes whether or not the console task is ready, and the interrupt handler must not block, because the code it interrupted cannot run until it returns; blocking calls inside interrupt handlers are listed among the traps of bridge BR-05 D3. So the ring's "full" case cannot be handled by waiting: the plan must choose between dropping the new byte, overwriting an old one, or a bigger ring, and must say how the loss is made visible. Software that only talks to other software can sometimes push back on its caller; software that talks to hardware usually has to decide, in advance, what to throw away.

The same applies to every device you met in DR301 and DR401: a disk completes requests in its own time, a network card fills receive descriptors as packets arrive, a removed device reads as all ones (the curriculum's "surprise removal" row) D2. Each of these is a failure mode a driver plan must name. The curriculum's design table 5.4 (bus binding, resources, initialization sequence, register model, interrupts, DMA, power, error handling, hot-plug, upper interface, trust, observability) is the hardware-facing checklist for a driver's plan, and F12-02 places it inside a design document D2.

Worked example

Task. Plan the receive ring of the serial console before writing it, so that the console task of the OS302 kernel can read typed characters. Here is the plan the lab uses, written in the order you would write it:

Listing 2 — plan.txt: the plan, written before Listing 1.



Step 1 — data structures. Eight slots, a power of two so that "slot = counter % 8" is cheap and wraps cleanly (D1, D3). Then the decision that matters: how to tell full from empty. Positions kept inside the array (0–7) cannot tell them apart, because eight writes bring the write position back to the read position (Figure 2). Free-running counters can: held = head − tail (D2).


Step 2 — failure modes. Ask "what if" for each input. What if the task reads when nothing arrived? Return "no byte" at once; the task decides whether to sleep (F1). What if bytes arrive faster than they are read? The handler cannot wait (see the hardware section), so something must be dropped. Two choices: drop the new byte, or overwrite the oldest. For a command line, overwriting the oldest loses the start of the command ("make run" becomes "ake run!"), which is worse than losing its end; the plan records the rejected alternative and its reason (F2). What if the counters reach their largest value? Unsigned arithmetic wraps, and the difference stays right (F3, D4).


Step 3 — how the tests observe success. One test per line, each stated as an observation: P1 for F1, P2 for D1 and D3 (order kept across the end of the array: push 5, pop 5, push 5 more, which crosses slot 7), P3 for D2 and F2 (nine pushes: 8 held, 1 dropped, and the first 8 kept), P4 for D2 (exactly 8 pushes: size is 8, not 0), P5 for F3 (start both counters 3 below the maximum, push and pop 8).


Step 4 — check the arithmetic of P2 and P5 by hand. P2: after "abcde" is pushed and popped, head = tail = 5; pushing "fghij" writes slots 5, 6, 7, 0, 1 (5 % 8 to 9 % 8), so it does cross the end. P5: with 64-bit std::size_t (as on the build machine), the start is 264 − 3; after 8 pushes head has wrapped to 5 while tail is still 264 − 3; head − tail modulo 264 is 5 − (264 − 3) + 264 = 8. The run confirms both R1.


Step 5 — approval. A peer reads the plan. In the lab's version of the story the first draft said "F2: overwrite the oldest byte"; the reviewer asked what a user sees when a pasted command is cut at the front, and the line changed. That is the cheapest bug fix in this course: one sentence, before any code existed.

Where the analogy breaks


    

  • Building software is cheap; deciding is not. In a house, the bricks are the expensive part and the blueprint protects them. In software, "building" (compiling) costs seconds; the expensive part is discovering, agreeing and re-checking decisions, and changing code that others already depend on. The plan protects decisions, not bricks.
    • 

  • Software blueprints change. A house blueprint is usually finished before building starts. A software plan is revised when the code teaches you something; that is normal, provided the plan is updated with the code (the registered "where it breaks" note of the F12 map) D3.
    • 

  • Tests can be run again; inspectors visit once. An acceptance test is executable and is run on every change, forever. The inspector's checklist is an image for "decided in advance", not for "checked once".
    • 

  • Hardware does not read the blueprint. A device behaves as it behaves, documented or not. A plan's hardware lines are claims to be checked against the datasheet and the emulator, with sources, not wishes (DR401, F4-17).

Summary


    

  • Curriculum rule 10: write the plan before the code, covering data structures, hardware sequence, failure modes and how the acceptance tests will observe success; the plan is approved before code.
    • 

  • Every program contains decisions; a plan makes them visible and reviewable while they cost a sentence.
    • 

  • Give plan lines identifiers and name them in tests: traceability shows unchecked decisions and unexplained tests.
    • 

  • State invariants and failure-mode behaviours, not intentions; "held = head − tail" is checkable, "handles overflow" is not.
    • 

  • Size the plan by how hard the change is to undo and how many people it affects.
    • 

  • Plans say where each line is tested and what the tests cannot observe (here: the interrupt-time interleaving).
    • 

  • Hardware forces failure-mode decisions in advance: an interrupt handler cannot wait for the reader.
    • 

  • A plan is kept alive: updated in the same change as the code.

Forensic lab answer key


How the evidence was produced. rx_ring_noplan.cpp was written to reproduce a ring built without a full/empty decision: positions modulo 8, no full test, no drop counter. It was run by run_lab.sh with the five pastes of rx_ring_noplan.in R2.


Observation. Sent → received: 7 → 7, 8 → 0, 9 → 1 ("x"), 6 → 6, 13 → 5 ("s.txt"). The drop counter is 0 every time.


Rule. Received = sent modulo 8, and what is received is the last (sent mod 8) bytes. Each push advances the write position modulo 8 with no check; after k pushes from equal positions, the write position is k mod 8 slots ahead, the reader sees only that many bytes, and every earlier byte has been overwritten or lies "behind" the read position.


Paste 2 and 3. Before paste 2, both positions are 7 (after paste 1's 7 bytes were read). Eight pushes write slots 7, 0, …, 6 and move the write position back to 7: equal positions, "empty", 0 bytes. Paste 3 (9 bytes) moves it to 7 + 9 = 16 → 0 modulo 8 one slot ahead of the read position at 7, which holds the last byte, "x".


Why the counter says 0. dropped() always returns 0: the code has no notion of a loss, so nothing tells users or developers that input was discarded. The bug is silent, which is why it lasted a week.


Plan line and test. D2 ("full and empty can never be confused") and F2 ("when full, the new byte is dropped and counted") would have forced the decision. P3 (9 pushes) and P4 (exactly 8 pushes) both fail on this code. Wrong answer to rule out: "the ring is too small, use 64 slots" — a larger ring only moves the failure to 64-byte pastes and keeps it silent.


Fix and verification. Free-running counters with a full test and a drop counter (Listing 1), verified by P1–P5 (R1). As a second check, replay the same five pastes through Listing 1's class; by the plan's rules the prediction is: received 7, 8 ("make run"), 8 ("ls -la /"), 6, 8 ("cat note") bytes, with drops 0, 0, 1, 0, 5. This replay was not run in the build: running it is part of the verification.


Prevention. Make "every plan line has a test, every failure mode has a chosen behaviour" part of review (F12-02's checker does the first mechanically). And make losses observable: a counter that a test, a log line or a statistic can see.
