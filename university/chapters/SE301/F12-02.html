Story hook

The kitchen drawing from the last chapter is on the table, and now more people need it. Kwame, the plumber, looks for the pipe and finds an arrow labelled "water, 30". Thirty what? He assumes centimetres from the floor. Lin, the electrician, reads the same 30 as the distance from the corner. Both are careful; both are wrong about the other. When the wall is opened, the pipe and the cable cross.

Ayasha redraws the blueprint. This time it has a legend: every length in centimetres, measured from the floor or from the left corner, as marked. It has a short list at the top, "this house will not have a basement", so nobody digs. It has a box called "not decided yet: which way the back door opens", so nobody guesses. And every room has a line saying how the inspector will check it.

A design document is that blueprint for software. It is read by people with different jobs, who each look for their part. This chapter is about writing one that each of them can read without guessing.

What you will be able to do

  • Write a design document with the course's nine sections, for a driver or another component, that two peers can review.
  • State goals that a test can check, and non-goals that stop work nobody asked for.
  • Specify an interface completely: units, ranges, ownership, calling context, errors and timeouts, and move the unit into the type where the language allows it.
  • Use a mechanical checker on a design document, and say what it cannot find.
  • Diagnose a failure caused by an ambiguous interface line, from a log and the document.
Jargon box
Non-goal
Simple words: something the design deliberately does not try to do. Analogy: "this house will not have a basement", written on the blueprint so nobody digs. Precise: an explicit statement in a design document that a plausible requirement is out of scope for this change, so that reviewers do not judge the design against it and implementers do not build it; a non-goal may become a goal of a later document. This is the course's definition; D1 discusses goals and non-goals of design documents D1.
Interface contract
Simple words: the exact promise a function or module makes to whoever calls it, and what it expects in return. Analogy: the legend of the blueprint: what every symbol and every number means. Precise: for each operation: parameters with types, units and allowed ranges (preconditions); results and side effects (postconditions); who owns memory before and after; from which context it may be called (task, interrupt, any CPU); how errors and timeouts are reported. The course's checklist; the C++ Core Guidelines discuss expressing interfaces precisely and in the type system D4.
Measurable requirement
Simple words: a goal written so that a test or a measurement can say yes or no. Analogy: "the window is as wide as the table" instead of "a big window". Precise: a requirement stated as an observable condition with a method of observation (a test, an emulator scenario, a measurement procedure with its target); words like "fast" or "robust" are replaced by the observation that would show them. Curriculum rule 10's "exactly how the acceptance tests will observe success" asks for this D2.
Open question (design document)
Simple words: a decision that is not made yet, written down so nobody guesses. Analogy: the box "not decided yet: which way the back door opens". Precise: a numbered item in a design document that names an undecided point, who will decide it, by when or before which step, and what depends on it; the review's job includes deciding which open questions must be closed before code starts.
Living document
Simple words: a document that is changed whenever the thing it describes changes. Analogy: the blueprint on site gets the corrections, not a drawer copy. Precise: a design document kept in version control next to the code, with a status line (draft, in review, approved, implemented, superseded) and updated in the same change as the code it describes; the curriculum's definition of done includes "design note updated" D2; the F12 analogy row warns that software blueprints change more often D3.

Terms from earlier chapters used here: design document, acceptance test, failure mode and traceability (F12-01); design note and test plan (DR401); bounded wait (DR401); steady (monotonic) clock (SP302).

Layer 1 — the kid explanation

Analogy

Mapping (F12; registered: design doc = the house blueprint; the rest proposed in NOTES.md): the legend that says "all lengths in centimetres, from the floor" = the interface section with units and reference points; "no basement" = a non-goal; the box "not decided yet" = an open question; "how the inspector checks each room" = the test plan; the plumber and the electrician = readers with different jobs (implementer, tester, operator).

A design document is written once and read many times, by different people, often when you are not in the room. Each reader looks for their part: the reviewer asks "is this the right problem?", the implementer asks "what exactly do I build?", the tester asks "how will I know it works?". If your document makes any of them guess, two of them will guess differently.

So you write for the reader who knows least. Every number has its unit. Every goal says how it will be checked. Everything you decided not to do is written down, and so is everything you have not decided yet.

Layer 2 — the student explanation

This course uses one format, with the headings that Listing 1 checks. Each section answers one question; the order is the reading order of a reviewer.

Status values in this course: draft (author still writing), in review, approved (reviewers signed; code may start), implemented, superseded by (with a link). The document lives in the repository next to the code, so that it is changed in the same commit as the code it describes: a living document D2 D3.

Goals a test can check

Rewrite every goal until you can name the test that would fail if the goal were not met. Compare the two drafts of the lab's document (Listings 2 and 3):

  • Draft 1, G2: "The receive path is fast and robust." Which test fails if it is slow? None can, because "fast" has no threshold.
  • Draft 2, G2: "The interrupt handler never waits and never takes a lock." Test T2 is a review of the handler's code against a three-item list: no loop, no lock, no call that can sleep. Not every check is a program; a check must still be specific enough that two reviewers agree on the result.
  • Draft 1, G3: "A paste of a long line does not crash the kernel." Draft 2, G3: "A paste longer than the ring loses only the bytes that do not fit, and counts them", checked by T3: "push 9 bytes: 8 held, 1 dropped, rx_dropped() returns 1". The second version also says what should happen, not only what should not.

Where a goal is a performance target, the number comes from a measurement or from a requirement someone stated, with its source, never from a feeling. The curriculum's performance milestones work this way: the learner writes the target X in the plan before starting, and the agent never lowers it after the fact without approval D2.

What a checker can and cannot find

Listing 1 is a small checker for this format. It finds missing sections, goals with no test naming them, a list of vague words, and numbers without a unit in the Interfaces and Failure modes sections. On draft 1 it reports nine findings (R1) R1; on draft 2, none (R2) R2. Read R1 closely and you will see what it missed:

  • Line 22 of draft 1, bool rx_wait(int timeout), has no unit, but contains no digit, so the number rule does not see it. This exact line is the forensic lab of this chapter.
  • T2, "run the shell for a while and check nothing breaks", names G2, so the traceability rule is satisfied, but the test is as vague as the goal. "A while" is not in the word list.
  • Nothing in R1 says whether dropping the new byte or the oldest is the right choice. Judging the design is the reviewers' job.

A clean checker run means "no known mechanical problem", not "a good document". Use the checker so that human reviewers spend their attention on the things only humans can see.

Layer 3 — the engineer's depth

Interface contracts

The Interfaces section is where most cross-team defects start, because it is the only section two teams implement from opposite sides. For each operation, answer these seven questions in the document. The checklist is this course's; each item is a question the forensic labs of SE301 turn into a failure.

  1. Types and units. Every quantity has a unit: time (ns, us, ms, s), size (bytes, slots, entries), rate. If the language can carry the unit in the type, the document says which type.
  2. Ranges and preconditions. Allowed values, including the edges: is 0 allowed? the maximum? what about a length the device reported?
  3. Results and postconditions. What is true after success, after failure, after a timeout. "Returns false" is incomplete without "and has not consumed a byte".
  4. Ownership. Who owns each buffer before, during and after the call; whether the callee may keep a pointer.
  5. Calling context. Task only, interrupt-safe, any CPU, with or without a given lock held. For drivers this is part of the "Interrupts" row of table 5.4 ("what runs in the handler and what is deferred") D2.
  6. Errors and timeouts. How each error is reported; every wait has a bound, and the bound's unit and clock are stated (the "Error handling" row of 5.4: "timeouts on every wait") D2.
  7. Compatibility. What callers may rely on in the future; what may change.

Move the unit into the type

Prose is read by people; types are read by the compiler, every time. Where the language allows it, the interface section names a type that carries the unit. In C++, std::chrono::duration types such as std::chrono::microseconds carry a time unit, convert exactly between units where no precision is lost (5 ms to 5000 us), and are not constructed implicitly from a plain integer D5. The forensic lab's answer key shows the compiler refusing a bare number for such a parameter, as a real build run (R4) R4. The same idea applies to other quantities: a Bytes or Slots wrapper type, an enumeration instead of a bool parameter whose meaning is invisible at the call site (F12-04 meets one in real university code). The C++ Core Guidelines discuss making interfaces precise and strongly typed D4.

For code that cannot use such types (C interfaces, kernel code following the curriculum's freestanding rules, register layouts), put the unit in the name: timeout_us, len_bytes, and say so in the document.

A design document for a driver

For a driver, the Design section embeds the twelve rows of curriculum table 5.4, each with its answer and where the answer was found, and the Test plan follows the parts of 5.5 D2. You wrote such a note in DR401 (F4-17; its lab file is a full example). What the design document adds around it:

  • Context and goals that say why this driver, for which milestone, and what "working" means for its users (the shell, the file system), not only for the device.
  • Interfaces upward and downward. The upper interface (block device, network interface, character device) with the seven contract questions; the register-level interface with every register's document and section title (curriculum runbook rule on explaining every register with its source) D2.
  • Alternatives: polling versus interrupts versus DMA, one queue versus several, a class driver versus a device-specific one (F12-03 shows how to compare them).
  • Open questions that belong to the dossier: every hardware fact that could not be confirmed in a document goes here and into the dossier's "not found" list, not into the design as if known (AH-10, AH-18) D3.

Length, audience and lifecycle

Write the shortest document that lets every reader do their job without asking you. For the receive path, draft 2 is 46 lines (R2) R2; for a block-device driver with DMA, a few pages including table 5.4 is normal for this course. If a section grows long, it is often hiding a second design that deserves its own document.

The lifecycle matters as much as the content. A design document that is approved and then never updated becomes a trap: the next engineer trusts it. Keep it in the repository; change the status when the code lands; add a short "as built" note when the implementation differs, with the reason; mark it superseded when a new design replaces it.

How the hardware actually does it

The hardware is the part of a driver's design document that you do not get to decide, so the document must say where each hardware fact comes from. The curriculum's rules are strict here: each register used gets its source document and section title, unknown registers are not touched, and quirks are recorded with evidence D2. In a design document this becomes a discipline: the Design section states hardware behaviour only with a citation; the Failure modes section covers what the hardware can do that the happy path ignores (a device that never becomes ready, a removed device that reads as all ones, interrupts that arrive before initialization completes, from the error-handling and fault-injection rows of 5.4 and 5.5) D2; and the Open questions section holds every hardware fact you could not find written down. Time is a hardware fact too: a timeout counted in polling iterations depends on how fast the CPU polls, which is why the forensic lab's fix states its deadline in microseconds of a named clock rather than in loop counts.

Where the analogy breaks


    

  • A blueprint is drawn to scale; a design document is not. A drawing shows sizes by itself; a document says nothing unless it is written. That is why units, ranges and reference points must be stated in words or types.
    • 

  • Builders can see the wall; programmers cannot see the other team's code. The plumber eventually sees the cable. Two software modules can disagree for months without anyone seeing it, until an unusual input (no modem attached) exposes it. The Interfaces section carries more weight than any line on a house drawing.
    • 

  • The compiler is a reader too. No inspector reads a blueprint thousands of times a day. A type that carries a unit is checked on every build, by a reader that never gets tired; the analogy has nothing like it.
    • 

  • Software blueprints change more often; keep them alive (the registered note) D3.
    •

Mini-project


The interface audit. Take one interface between two components in your current or a past project (a driver and the kernel, a ROS 2 node and its topic consumers, a kernel and a user program). Write its Interfaces section with all seven contract questions answered. Then read both sides' code and list every place where the code disagrees with your section or where one side depends on something your section does not promise. Fix one disagreement, moving a unit or a range into a type if the language allows. Rubric: completeness of the contract (30 %); disagreements found with file and line (30 %); the fix and its test (25 %); clarity (15 %).

Forensic lab answer key


How the evidence was produced. timeout_units.cpp keeps the driver team's arithmetic (deadline = now + timeout * 1000L in microseconds, polling every 100 us) and the console team's call (rx_wait(5000), meaning 5 ms) side by side, with a simulated clock and a 2-second boot watchdog that belongs only to this simulation. It was run on three boots R3.


Observation. The console expected to give up after 5 ms. The driver computes a deadline of 5,000 × 1,000 us = 5,000,000 us, that is 5 s. Boot 1 (no modem): no return before the watchdog at 2,000,000 us; the board resets. Boot 2 (answer at 3,000 us): returns true at 3,000 us, as both teams expect. Boot 3 (answer at 40,000 us): returns true at 40,000 us, while the console expected to have given up at 5,000 us and disabled the radio: "console expected false: modem state now wrong" R3.


Hypotheses. (1) The modem's absence breaks the serial driver: ruled out, the driver loop runs and polls normally; it simply has a much later deadline. (2) The watchdog is too short: ruled out as a root cause, the boot was supposed to spend at most 5 ms here; lengthening the watchdog would hide the bug and make every modem-less boot take 5 s. (3) The two sides disagree on the unit of timeout: confirmed by the factor of 1,000 between the console's expectation and the driver's deadline, and by the boot 3 mismatch.


Why no test caught it. Every test ran with a modem that answered within 5 ms (like boot 2), where both readings give the same result. The contract questions "unit?" and "what is true after a timeout?" were never answered, so no test of the timeout path existed. Boot 3 also shows that the bug is not only "hang when absent": a late answer is accepted when the caller has already given up.


Fix. In the document: bool rx_wait(std::chrono::microseconds deadline), "measured on the monotonic clock; returns false if no byte arrived within deadline; a deadline of 0 us returns at once", plus a test with no byte ever arriving (T4 of Listing 3). In the code: the same type. With it, the console team's old call does not compile, which is exactly what you want: a real build of that call failed with the message below R4.
