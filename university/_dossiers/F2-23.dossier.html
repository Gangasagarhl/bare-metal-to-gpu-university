Notes and quotes (paraphrased unless quoted)

  • N4861 7.6.7 paragraph 4: "The expression E1 is sequenced before the expression E2." (shift operators, so the operands of a << chain are evaluated left to right).
  • N4861 6.8.1 note: "Unsigned arithmetic does not overflow. Overflow for signed arithmetic yields undefined behavior (7.1)."
  • N4861 6.7.2 paragraph 13: "Any implicit or explicit invocation of a function named operator new or operator new[] implicitly creates objects in the returned region of storage"; library functions memcpy, memmove, malloc also implicitly create objects.
  • N4950 20.2.6: template<class T> T* start_lifetime_as(void* p) noexcept; Mandates: T is an implicit-lifetime type.
  • GCC 13.3 manual 3.8, -Wstrict-overflow: an optimisation that assumes signed overflow does not occur may simplify x + 1 > x to 1.
  • GCC 13.3 manual 3.12: "The runtime library defaults to halt_on_error=0 for ThreadSanitizer and UndefinedBehaviorSanitizer, while default value for AddressSanitizer is halt_on_error=1."
  • Clang UBSan page (opened at https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html): by default a failed check prints a verbose report and execution continues; -fno-sanitize-recover makes it exit.

Fact list (keyed to the chapter's claim tags, in chapter order)

  1. F1 (able) Precise: a run-time property of an object: for a class type with a non-trivial constructor it begins when initialisation completes, and it ends when the destructor call starts (or when the storage is released or reused); outside its lifetime, an object may not be accessed through its type. — source: D1 §6.7.3 (opened, checked)
  2. F2 (able) Precise: an object created, for example, by a function returning by value; it is destroyed at the end of the full-expression that created it, unless it is bound to a reference that extends its lifetime. — source: D1 §6.7.7 (opened, checked)
  3. F3 (able) Not the same as unspecified behaviour (one of several allowed results) or implementation-defined behaviour (documented by the implementation). — source: D1 §3.13, §3.30, §3.31 (opened, checked)
  4. F4 (able) Precise: a reference or non-owning view whose referent's lifetime has ended; any access through it is undefined behaviour. std::string_view and std::span never own the data they view. — source: D1 §6.7.3, §21.4.2, §22.7.3.1 (opened, checked); D4 SL.str.2, F.24 (opened, checked)
  5. F5 (able) Precise: an arithmetic result outside the range of a signed integer type; undefined behaviour in C++ (unsigned arithmetic, in contrast, is defined to wrap modulo 2 N ; MA102). — source: D1 §7.1, §6.8.1 (opened, checked)
  6. F6 (able) Precise: compiler instrumentation enabled with -fsanitize=undefined that adds run-time checks for, among others, signed overflow, misaligned access, null member access and out-of-bounds array indexes, and prints "runtime error:" messages; by default it reports and continues. — source: D5 §3.12 (opened, checked); D6 UBSan (opened, checked)
  7. F7 (able) Precise: informal engineering term for a defect whose observable effect depends on timing, memory layout, optimisation level or instrumentation; memory-safety bugs are a classic source because their effect depends on what else occupies the memory. — source: R5 (local lab run record)
  8. F8 (layer1) A temporary, like the value a function hands back, ends at the semicolon unless you hold on to it. — source: D1 §6.7.3, §6.7.7 (opened, checked)
  9. F9 (layer1) The program may crash, may print a wrong number, or may seem fine today and fail tomorrow. — source: D1 §3.30 (opened, checked)
  10. F10 (layer1) They use tools, the sanitizers, that watch every memory access and every risky calculation and say exactly which line broke the rules. — source: D6 §3 (opened, checked)
  11. F11 (l2-life) Layer 2 — the student explanation When lifetimes begin and end Storage and lifetime are different things: storage is the bytes; lifetime is the period in which an object of a particular type lives in them. — source: D1 §6.7.3 (opened, checked)
  12. F12 (l2-life) … ck in reverse order of construction ("end b" before "end a"); a temporary returned by value is destroyed at the end of the full-expression, after the line has used it; binding a temporary to a const reference extends its lifetime to that of the reference; and members are constructed in declaration order and destroyed in reverse. — source: D1 §6.7.7, §8.7, §11.4.6 (opened, checked); R1 (local lab run record)
  13. F13 (l2-life) Since C++17 the operands of << are evaluated left to right, and the temporary lives exactly until the end of that whole statement. — source: D1 §7.6.7, §6.7.7 (opened, checked); R1 (local lab run record)
  14. F14 (l2-ub) … standard sorts behaviour into three kinds besides "well-defined": implementation-defined (the implementation chooses and documents, like sizeof(long) ), unspecified (one of several allowed outcomes, not necessarily documented, like the order in which some function arguments are evaluated), and undefined (no requirements at all). — source: D1 §3.13, §3.31, §3.30 (opened, checked)
  15. F15 (l2-ub) The compiler may then optimise as if it cannot happen, for example by assuming that x + 1 > x is always true for a signed x . — source: D5 §3.8 (opened, checked)
  16. F16 (l2-catalogue) A short catalogue Use after free / after scope : accessing an object after its lifetime (F2-20, F2-21, the forensic lab here). — source: D1 §6.7.3 (opened, checked)
  17. F17 (l2-catalogue) Listing 3's std::string_view looks at the characters of a temporary std::string that was destroyed at the end of line 14; reading it at line 15 is a heap-use-after-free. — source: R3 (local lab run record)
  18. F18 (l2-catalogue) GCC 13 caught a similar mistake, a const& bound to the result of std::max of two temporaries, at compile time with -Wdangling-reference (mistakes section). — source: R4 (local lab run record)
  19. F19 (l2-catalogue) UBSan reports by default and does not stop. — source: R2 (local lab run record)
  20. F20 (l2-catalogue) The unsigned version wraps to 0, which is defined. — source: D1 §6.8.1 (opened, checked)
  21. F21 (l2-tools) … three views Compiler warnings see the source and catch patterns at compile time: -Wuninitialized (F2-19), -Wmismatched-new-delete (F2-21), -Wdangling-reference and -Wuse-after-free (enabled by -Wall ; GCC's manual warns that its results can differ with optimisation), which flagged the forensic program's bug in the -O2 build log. — source: D5 §3.5, §3.8 (opened, checked); R6 (local lab run record)
  22. F22 (l2-tools) AddressSanitizer instruments memory accesses and reports invalid addresses at run time; UndefinedBehaviorSanitizer instruments arithmetic and other operations. — source: D6 §3.1 (opened, checked); D6 UBSan (opened, checked)
  23. F23 (layer3) Leaving behaviour undefined lets the language map operations directly onto hardware without checks (no bounds check on every a[i] , no overflow trap on every addition) and lets optimisers reason freely; the cost is that correctness becomes the programmer's proof obligation. — source: D1 §3.30 (opened, checked); D3 §2.3 (table of contents only; text not opened)
  24. F24 (layer3) Curriculum 1.1 names the cases that bite kernels: strict aliasing, signed overflow, misaligned access, and the lifetime of objects created in raw memory. — source: S1 (local curriculum file)
  25. F25 (layer3) An object may be accessed only through an lvalue of its own type (with some allowances, notably char , unsigned char and std::byte ); reading a float 's bytes through an int* breaks this rule, and an optimiser may then reorder or delete accesses on the assumption that the two pointers cannot refer to the same object. — source: D1 §7.2.1 (opened, checked)
  26. F26 (layer3) Storage obtained from an allocator is just bytes; an object's lifetime starts only when it is created there (by placement new , or implicitly for certain simple types in certain operations), and it ends when it is destroyed or its storage is reused. — source: D1 §6.7.2, §6.7.3 (opened, checked)
  27. F27 (layer3) Among those operations are every call of an operator new , the start of the lifetime of an array of unsigned char or std::byte , and the library functions std::malloc and std::memcpy . — source: D1 §6.7.2 (opened, checked)
  28. F28 (layer3) C++23 added std::start_lifetime_as<T>(p) , which does the same explicitly for one implicit-lifetime type T . — source: D7 §20.2.6 (opened, checked)
  29. F29 (layer3) In this build the same source crashed at the line after the stale write in one build and four lines later, in a different object, when one extra allocation was compiled in. — source: R5 (local lab run record)
  30. F30 (layer3) AddressSanitizer removes the randomness by delaying reuse of freed blocks (quarantine) and checking every access, so it reports the write , not the later crash. — source: D6 §3.3 (opened, checked); R7 (local lab run record)
  31. F31 (layer3) Curriculum B5 asks your kernel allocator to do a lighter version of the same: poison freed memory so that "a deliberate use-after-free in a test build is caught by the poison check". — source: S1 (local curriculum file)
  32. F32 (hardware) It has no concept of object lifetime: a store to a freed heap block succeeds if the page is mapped and writable, which is why use-after-free corrupts silently instead of faulting. — source: D3 §9.11.9 (table of contents only; text not opened)
  33. F33 (hardware) Signed addition on x86-64 wraps in two's complement and sets the overflow flag (HW102's status flags); C++ calls the overflow undefined anyway, because other processors behave differently and because the optimiser's freedom matters more than the hardware's habit. — source: D3 §2.3.2 (table of contents only; text not opened)
  34. F34 (worked) The real output (code walk-through) matches all three predictions. — source: R1 (local lab run record)
  35. F35 (breaks) A compiler facing UB is not "reasonable": it may assume the case never happens and transform the program accordingly, so the result can be stranger than any plausible mistake. — source: D5 §3.8 (opened, checked)
  36. F36 (breaks) In a program, the faulty write leaves no trace at the moment it happens; the crash comes later, elsewhere, or never (the forensic lab). — source: R5 (local lab run record)
  37. F37 (breaks) Freed memory keeps its old bytes, or holds a new object, so a read through a stale pointer often returns something plausible. — source: D3 §9.11.9 (table of contents only; text not opened)
  38. F38 (mistakes) RAII and smart pointers still decide when objects end; the sanitizer reports you read in F2-19 to F2-22 have the same structure (kind, access, free, allocation). — source: D6 §3.3 (opened, checked)
  39. F39 (mistakes) What changes: you now treat the language rules as a contract with the compiler: breaking one does not produce an error but releases the compiler from every promise, and symptoms can appear far from the cause, differ between builds, or not appear at all. — source: D1 §3.30 (opened, checked); R5 (local lab run record)
