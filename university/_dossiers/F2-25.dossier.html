Notes and quotes (paraphrased unless quoted)

  • N4861 16.5.1.3 Table 24 and N4950 16.4.2.5 Table 27 list the headers a freestanding implementation must provide; <span> is in neither.
  • N4861 9.3.3.5: a parameter of type "array of T" is adjusted to "pointer to T".
  • N4861 22.7.3.1: span holds (exposition only) a pointer data_ and, for dynamic extent, a size size_; C++20 span has no at().
  • OSTEP 17.2: allocators split free chunks to satisfy smaller requests, coalesce adjacent free chunks, and keep a header (size, magic number) just before each allocated region; 17.3 describes best, worst, first and next fit.
  • Ubuntu "ToolChain/CompilerFlags" wiki page: not opened (HTTP 404 on two attempts, curl and WebFetch).

Fact list (keyed to the chapter's claim tags, in chapter order)

  1. F1 (able) Precise: an object of type T[N] holding N contiguous elements; N is part of the type and sizeof gives N * sizeof(T) ; not assignable or copyable as a whole, and converted to a pointer to its first element in most expressions. — source: D1 §9.3.3.4, §7.3.2 (opened, checked)
  2. F2 (able) Precise: the standard conversion from an lvalue of type T[N] to a prvalue of type T* ; also, a function parameter declared with array type is adjusted to pointer type. — source: D1 §7.3.2, §9.3.3.5 (opened, checked)
  3. F3 (able) Precise: the class template std::array<T, N> from <array> , an aggregate wrapping T[N] , copyable and assignable, with size() , iterators, operator[] (unchecked) and at() (checked). — source: D1 §22.3.7.1, §22.2.3 (opened, checked)
  4. F4 (able) Precise: the class template std::span<T, Extent> from <span> (C++20), a non-owning reference to a contiguous sequence, holding a pointer and (for dynamic extent) a size; constructible from built-in arrays, std::array , std::vector and other contiguous ranges. — source: D1 §22.7.3.1 (opened, checked); D4 F.24, I.13 (opened, checked)
  5. F5 (able) Precise: a run-time comparison of an index against the size, as done by at() (which throws std::out_of_range ), by hardened library modes, or by sanitizer instrumentation; built-in subscripting and operator[] of standard containers do not check. — source: D1 §22.2.3, §19.2.6 (opened, checked)
  6. F6 (able) Precise: an access outside the bounds of an array object; undefined behaviour in C++; reported by AddressSanitizer as stack-buffer-overflow, heap-buffer-overflow or global-buffer-overflow according to where the array lives. — source: D6 Clang intro (opened, checked)
  7. F7 (able) Precise: informal term for a boundary error, typically <= where < was needed, or a size used as a last index. — source: D3 §9.11.5 (table of contents only; text not opened)
  8. F8 (able) Precise: a region-based allocator whose state is a base, a size and an offset; allocation rounds the offset up to the requested alignment and advances it; individual deallocation is not supported, only reset. — source: R6 (local lab run record); S1 (local curriculum file)
  9. F9 (able) Precise: an allocator data structure linking free blocks (often through headers stored inside the blocks themselves); allocation searches it (first fit, best fit), may split a block; freeing returns a block and may coalesce it with free neighbours. — source: D3 §9.9.6, §9.9.13 (table of contents only; text not opened); D7 §17.2, §17.3 (opened, checked)
  10. F10 (layer1) An array of four boxes has numbers 0, 1, 2 and 3. There is no box 4. — source: D1 §9.3.3.4 (opened, checked)
  11. F11 (layer1) Sometimes it is another variable, and you have just read or changed something that was not yours. — source: D3 §3.10.3 (table of contents only; text not opened)
  12. F12 (layer1) And the sanitizers put invisible fences around every array so that a reach past the end is caught at once. — source: R3 (local lab run record); R4 (local lab run record)

  15. F15 (l2-decay) Even a parameter written int portions[8] is adjusted to int* ; the 8 is ignored. — source: D1 §7.3.2, §9.3.3.5 (opened, checked)

  20. F20 (l2-span) Like string_view (F2-23), a span does not own: it must not outlive its storage, and resizing a vector can move the storage and leave the span dangling. — source: D1 §22.7.3.1, §22.3.11.5 (opened, checked); D4 F.24, R.14 (opened, checked)
  21. F21 (l2-bounds) Nobody, by default: built-in a[i] , vector::operator[] and span::operator[] do not check, and an index outside the bounds is undefined behaviour. — source: D1 §7.6.1.1, §7.6.6, §22.2.3 (opened, checked)

  24. F24 (l2-bounds) For the vector in the forensic lab, ASan reported a heap-buffer-overflow read "0 bytes after 16-byte region". — source: R5 (local lab run record)
  25. F25 (layer3) A write past a stack array can overwrite neighbouring locals, saved registers and the return address; attackers have used exactly this to redirect execution for decades, which is why modern toolchains add stack canaries, non-executable stacks and address randomisation. — source: D3 §3.10.4 (table of contents only; text not opened)
  26. F26 (layer3) In Listing 4, the stack layout shown by ASan ("[32, 48) 'seats'") is the sanitizer's own layout with red zones (F2-18), not the layout of a plain build. — source: R4 (local lab run record)
  27. F27 (layer3) Curriculum 1.2 restricts the language in the kernel (no exceptions), so .at() is unavailable there; the idea of std::span survives because it is just a pointer and a length with no allocation, and a kernel can add its own checked accessor that panics instead of throwing. — source: S1 (local curriculum file)
  28. F28 (layer3) The header <span> itself is not in the list of headers that the C++20 or the C++23 standard requires a freestanding implementation to provide, so a kernel may have to write its own small span type. — source: D1 §16.5.1.3 (opened, checked); D2 §16.4.2.5 (opened, checked)
  29. F29 (layer3) The simplest, a bump allocator, keeps one offset: allocation rounds the offset up to the requested alignment (the same rounding the compiler did for struct members in F2-24) and advances it; nothing is freed individually. — source: R6 (local lab run record)
  30. F30 (layer3) Listing 5 implements one over a std::span<std::byte> ; requests that do not fit return nullptr instead of overrunning, and the tests show the alignment: a 1-byte piece at offset 0, then an 8-aligned piece at 8, not at 1. — source: R6 (local lab run record)
  31. F31 (layer3) A free-list allocator also takes pieces back; that, with splitting and coalescing, is the course project and the CS:APP malloc lab's core (P4). — source: D3 §9.9.6–§9.9.14 (table of contents only; text not opened); D7 §17.2 (opened, checked)
  32. F32 (hardware) How the hardware actually does it To the processor, a[i] is an address computation, base + i * sizeof(T) , often a single instruction with a scaled index addressing mode, followed by a load or store. — source: D3 §3.8 (table of contents only; text not opened)
  33. F33 (hardware) The four tips occupy 16 bytes of a heap block; the byte after them is ordinary mapped memory belonging to the allocator, so a plain build reads it without any fault, as the forensic lab shows (what those bytes are is an inference; see the box in the forensic key). — source: R7 (local lab run record)
  34. F34 (hardware) Sanitizers add the missing check in software, by consulting shadow memory before every access (F2-18). — source: D6 §3.1 (opened, checked)
  35. F35 (worked) The run printed "a at offset 0", "b at offset 8 (aligned to 8)", "c at offset 16", "used 20 of 64 bytes". — source: R6 (local lab run record)
  36. F36 (code) The parameter on line 4 is int* , so line 6 would compute 8 / 4 = 2 on this 64-bit machine instead of 8; the compiler's warning, an error under -Werror , stops it. — source: R2 (local lab run record)

  38. F38 (breaks) A program reading past an array sees only bytes; nothing tells it they belong to another variable. — source: D3 §3.10.3 (table of contents only; text not opened)
  39. F39 (breaks) In a program it is undefined behaviour: the compiler may assume the index is valid and optimise on that assumption (F2-23), so the effect is not limited to "one wrong value". — source: D1 §3.30 (opened, checked)
  40. F40 (breaks) A span's count is trusted, not checked against the real storage; a span built from a wrong pointer and size, or kept after its vector reallocated, is as dangerous as a raw pointer. — source: D4 F.24 (opened, checked)
  41. F41 (mistakes) What changes: you stop passing bare pointers and start passing sizes with them ( std::span ), and you build the thing that hands out memory instead of only using it. — source: D1 §22.7.3.1 (opened, checked)
