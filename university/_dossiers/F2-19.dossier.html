Notes and quotes (paraphrased unless quoted)

  • N4861 7.3.11: a null pointer constant converts to the null pointer value of a pointer type, "distinguishable from every other value of object pointer or function pointer type".
  • N4861 7.6.1.1: "The expression E1[E2] is identical (by definition) to *((E1)+(E2))". 7.6.1.4: "E1->E2 is converted to the equivalent form (*(E1)).E2".
  • N4861 7.6.1.2 paragraph 7: when a function is called, each parameter is initialised with its corresponding argument (pass by value).
  • Core Guidelines F.60: "Prefer T* over T& when “no argument” is a valid option"; ES.20 "Always initialize an object"; R.3 "A raw pointer (a T*) is non-owning".
  • x86-64 psABI 3.1.2: "A null pointer (for all types) has the value zero."

Fact list (keyed to the chapter's claim tags, in chapter order)

  1. F1 (able) Precise: an object of type T* whose value is the address of an object of type T , the address one past the end of an array of T , or the null pointer value. — source: D1 §6.8.2 (opened, checked); D2 §1.7 (table of contents only; text not opened)
  2. F2 (able) Not the same symbol use as the reference declarator T& (F2-12). — source: D1 §7.6.2.1 (opened, checked)
  3. F3 (able) Dereferencing a pointer that does not point to a live object is undefined behaviour. — source: D1 §7.6.2.1, §7.6.1.4, §6.7.3 (opened, checked)
  4. F4 (able) Dereferencing it is undefined behaviour. — source: D1 §5.13.7, §7.3.11, §9.3.3.2 (opened, checked)
  5. F5 (able) Precise: adding an integer n to a pointer into an array gives a pointer n elements further; subtracting two pointers into the same array gives the number of elements between them (type std::ptrdiff_t ); results outside the array, except one past its end, are undefined. — source: D1 §7.6.6 (opened, checked)
  6. F6 (able) Standard iterators' end() follows the same rule (F2-15). — source: D1 §6.8.2, §7.6.6 (opened, checked)
  7. F7 (able) Precise: a pointer whose value was the address of an object whose lifetime has ended; using it to access memory is undefined behaviour (F2-23). — source: D1 §6.7.3, §6.7.5 (opened, checked)
  8. F8 (layer1) It is a note that says "the thing you want is in box 4410". — source: D2 §1.7 (table of contents only; text not opened)
  9. F9 (layer1) Two little symbols do all the work. &portions asks "where is portions ?" and gives you the note. *p says "go to the box on note p ", and there you can read or change what is inside. — source: D1 §7.6.2.1 (opened, checked)
  10. F10 (layer1) If you change *p , you change portions itself, because they are the same box. — source: R1 (local lab run record)
  11. F11 (l2-make) Storing it in a variable, T* p = &x; , gives you an object (8 bytes on this build's machine) whose value is x 's address. — source: D1 §7.6.2.1 (opened, checked); R1 (local lab run record)
  12. F12 (l2-make) For a pointer to a structure, p->member is short for (*p).member . — source: D1 §7.6.2.1, §7.6.1.4 (opened, checked)
  13. F13 (l2-params) Pointers as parameters C++ passes arguments by value: a function receives copies. — source: D1 §7.6.1.2 (opened, checked)
  14. F14 (l2-params) Listing 2's swapCopies swaps its own copies and the caller sees nothing. swapThrough receives two addresses and swaps the objects they point to, so the caller's variables change. — source: R2 (local lab run record)
  15. F15 (l2-params) Prefer a reference ( int& ) when the argument must always refer to an object; use a pointer when "no object" ( nullptr ) is a meaningful value, or when the function must walk through memory. — source: D4 F.60 (opened, checked)
  16. F16 (l2-params) The C++ Core Guidelines state exactly this preference. — source: D4 F.60, F.16, F.17 (opened, checked)
  17. F17 (l2-null) The null pointer nullptr converts to the null pointer value of any pointer type; it compares unequal to the address of every object. — source: D1 §7.3.11 (opened, checked)
  18. F18 (l2-null) Dereferencing the null pointer is undefined behaviour: the standard says nothing about what happens next (F2-23). — source: D1 §7.6.2.1, §9.3.3.2, §3.30 (opened, checked)
  19. F19 (l2-null) On this build's machine, the sanitizer build reported the bad member access and the program was then stopped by a segmentation fault. — source: R3 (local lab run record)
  20. F20 (l2-arith) Pointer arithmetic Inside an array, p + n points n elements further, not n bytes: the compiler multiplies by sizeof(T) for you. q - p for two pointers into the same array is the number of elements between them. — source: D1 §7.6.6 (opened, checked)
  21. F21 (l2-arith) Listing 1 prints "2 elements, 8 bytes" for q = &shelf[0] + 2 on an int array. — source: R1 (local lab run record)
  22. F22 (l2-arith) Array indexing is defined in terms of this arithmetic: a[i] means *(a + i) . — source: D1 §7.6.1.1 (opened, checked)
  23. F23 (l2-arith) A pointer may legally point at any element or one past the last element ; computing anything outside that range is already undefined, even if you never dereference it. — source: D1 §7.6.6 (opened, checked)
  24. F24 (l2-const) Read the declaration from right to left: "p is a const pointer to int". — source: D1 §9.3.3.1 (opened, checked); D2 §1.6, §1.7 (table of contents only; text not opened)
  25. F25 (layer3) Two pointers can hold the same address and still not be interchangeable in the language's eyes: pointer arithmetic is defined only within one array object, and the compiler may assume a pointer derived from one object does not reach another. — source: D1 §7.6.6 (opened, checked)
  26. F26 (layer3) Optimisers use that assumption; it is one reason why "it is just an address, I can compute it" leads to undefined behaviour in C++ and why kernels that really need address arithmetic do it on std::uintptr_t values and convert back at well-defined points (curriculum 1.1, strong types for addresses). — source: S1 (local curriculum file)
  27. F27 (layer3) On the platforms of this course it is all-zero bits, which is why the sanitizer says "address points to the zero page" and why the faulting address 0x10 in the forensic evidence is a small number: a null pointer plus a small offset into the object. — source: D1 §7.3.11 (opened, checked); D5 §3.1.2 (opened, checked); R3 (local lab run record)
  28. F28 (layer3) A kernel can map memory at address zero; in your own operating system (track B) a null dereference does not crash unless you deliberately leave the first page unmapped, which is exactly what operating systems do to catch these bugs. — source: D3 §9.5 (table of contents only; text not opened)
  29. F29 (layer3) A local int* p; without an initialiser has an indeterminate value; using it is undefined behaviour. — source: D1 §6.7.4 (opened, checked)
  30. F30 (layer3) GCC, with the course's warnings turned into errors, refused to compile wild.cpp , which writes through such a pointer; the compiler's message is in the mistakes section. — source: R5 (local lab run record)
  31. F31 (layer3) The compiler cannot catch every case (a pointer set on some paths only, or stored in a structure), so the habit is: initialise every pointer, to an object or to nullptr . — source: D4 ES.20 (opened, checked)
  32. F32 (layer3) In modern C++ a raw T* is used as a non-owning observer, while ownership is expressed with containers and smart pointers (F2-21, F2-22). — source: D4 R.3, I.11 (opened, checked)
  33. F33 (hardware) How the hardware actually does it At the machine level a pointer is an address in a 64-bit register, and dereferencing is a load or store instruction whose address operand is that register (plus a constant offset for p->member , plus an index times a scale for p[i] ). — source: D3 §3.4, §3.8 (table of contents only; text not opened)
  34. F34 (hardware) It only checks, through the page tables, whether the page is mapped with the right permissions; if not, it raises a page fault, which Linux turns into the SIGSEGV signal that ended Listing 3's run. — source: D3 §8.1, §9.3.4, §9.5 (table of contents only; text not opened); R3 (local lab run record)
  35. F35 (worked) The lab program ptr_lab.cpp computes steps 3 and 4; its output (Listing 4, in the lab) prints "largest tip 9 at index 1" and then "largest tip 9 at index 3". — source: R4 (local lab run record)
  36. F36 (worked) The lab's reference solution continues from step 4. — source: R6 (local lab run record)
  37. F37 (breaks) A program never notices: a dangling pointer into memory that was reused reads or writes the new contents silently (the registered "where it breaks" of this mapping, guide 8.1). — source: D1 §6.7.3 (opened, checked)
  38. F38 (breaks) In C++, arithmetic that leaves the array is undefined even if the resulting number looks fine, and the compiler may optimise on that assumption (Layer 3). — source: D1 §7.6.6 (opened, checked)
  39. F39 (breaks) Following nullptr is not a polite "nothing there": it is undefined behaviour, which on this build ended in a crash. — source: R3 (local lab run record)
  40. F40 (mistakes) What carries over: a reference and a pointer both let code reach an object it does not own; const still means "you may not change it through this name"; the byte arithmetic of F2-18 is exactly what pointer arithmetic does for you. — source: D1 §9.3.3.1 (opened, checked)
  41. F41 (mistakes) What changes: a pointer is a separate object that can be null, can be re-pointed, can be moved with arithmetic, and can outlive what it points to, and the language checks none of this at run time; you, the compiler's warnings and the sanitizers must. — source: D1 §3.30 (opened, checked); R3 (local lab run record)
