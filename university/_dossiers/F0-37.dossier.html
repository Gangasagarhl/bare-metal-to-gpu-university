C. Fact list

One entry per tagged claim in the chapter (the claim text as it stands after the verification pass, the tag that supports it, and the chapter section). Every document section named in a tag was opened and the fact was found there; R-ids are this build's lab runs.

  1. F1 Simple words: A program that runs your program one step at a time, so you can look inside. Analogy: A pause button for the kitchen: everything freezes and you can look into every jar. Precise: A tool (here GNU gdb 15.1) that starts or attaches to a program, stops it at chosen places and shows the values of its variables (R3, R5). source: R3, R5, D2 §5.1.1, §8.2; used in: F0-37-jargon
  2. F2 Simple words: A place in your program where the debugger will pause. Analogy: A sticky note on step 9: "stop here and check". Precise: A location set with the gdb command break (help text: "Set breakpoint at specified location.", R5); the program stops each time it reaches that line (R4). source: R4, R5, D2 §5.1.1; used in: F0-37-jargon
  3. F3 Simple words: Running exactly one more line of the program, then pausing again. Analogy: Doing one recipe step and freezing again. Precise: gdb's next runs one line and treats a function call as one line ("proceeding through subroutine calls"); step goes into the called function (R3, R5). source: R3, R5, D2 §5.2; used in: F0-37-jargon
  4. F4 The debugger in this build is GNU gdb, version line "GNU gdb (Ubuntu 15.1-1ubuntu1~24.04.1) 15.1". It needs the program to be built with -g, which keeps the line numbers and variable names in the executable; the course flags already include -g (F0-29). source: R3, R5, D2 §4.1, D4 §3.10; used in: F0-37-layer2
  5. F5 … ession ended with "LeakSanitizer has encountered a fatal error" and the hint "LeakSanitizer does not work under ptrace (strace, gdb, etc)". The program's own output was lost. We switched leak checking off inside gdb only, with set environment ASAN_OPTIONS=detect_leaks=0, and the session worked. The runs without gdb keep every check. When a tool tells you how it fails, believe it and write it down. source: R9, D6; used in: F0-37-layer3
  6. F6 A debugger shows you a frozen moment, but it can also change it: gdb can assign a new value to a variable while the program is paused, or stop only when a condition is true (break 9 if i == 3, a form described in gdb's help for break: "[if CONDITION]"). You will use these in later courses. source: R5, D2 §17.1, §5.1.1; used in: F0-37-layer3
  7. F7 … SIGABRT, Aborted." and showed a library file that is not installed on the build machine ("No such file or directory"). That is normal: the stop happened inside library code, not yours. The command backtrace lists the chain of calls that led there, so you can walk back to your own line; its help text was not saved in this build, so this last point rests on the GDB manual (section 8.2, Backtraces). source: R4, D2 §8.2; used in: F0-37-layer3
  8. F8 … h can then read your program's memory: that is how it finds the value of i. The -g information is the map from machine code back to your line numbers and variable names. The word "ptrace" in the LeakSanitizer hint above names the Linux facility for this kind of control. Its manual page says it lets one process "observe and control" another. It is "primarily used to implement breakpoint debugging". source: R9, D2 §5.1.1, §4.1, D5; used in: F0-37-hardware
  9. F9 … instruction that hands control back to the debugger. When the program stops, gdb puts the original instructions back. A second command, hbreak, asks for a breakpoint built into the processor itself. That needs hardware support, which not every computer has. gdb can also choose between the two kinds by itself. Our recorded sessions used break only, and which kind gdb picked inside was not recorded. source: R3, D2 §5.1.1; used in: F0-37-hardware

D. Not found / conflicting

  • N1 Which kind of breakpoint (software or hardware) gdb 15.1 chose in the recorded sessions was not recorded; the manual (D2 §5.1.1) says ordinary breakpoints are software breakpoints and that gdb can choose automatically. The chapter now says this instead of the former "Not verified" box.
  • N2 The manual of exactly gdb 15.1 was not opened; the current online manual (version 19.0.50) was used. Every command the chapter uses is also confirmed by gdb 15.1's own help text (R5), except backtrace, which rests on D2 §8.2.
  • N3 Why LeakSanitizer "does not work under ptrace": no opened document explains it; the chapter reports only the tool's own hint (R9) and the documented switch detect_leaks=0 (D6).
