Notes and quotes (paraphrased unless quoted)

  • N4861 20.11.3 paragraph 5: "For purposes of determining the presence of a data race, member functions shall access and modify only the shared_ptr and weak_ptr objects themselves and not objects they refer to." The standard does not use the words "control block" or "atomic" for the count; those come from the GCC library source (D7).
  • N4861 20.11.3.6: make_shared "Implementations should perform no more than one memory allocation."
  • N4861 20.11.1.2: unique_ptr(const unique_ptr&) = delete. 20.11.4.5: lock() returns expired() ? shared_ptr<T>() : shared_ptr<T>(*this), executed atomically.
  • libstdc++ 13.3 shared_ptr_base.h: _M_add_ref_copy() uses __gnu_cxx::__atomic_add_dispatch on _M_use_count (the _S_single policy uses a plain increment); unique_ptr.h stores tuple<pointer, _Dp>.
  • Core Guidelines R.24: "Use std::weak_ptr to break cycles of shared_ptrs"; R.21: "Prefer unique_ptr over shared_ptr unless you need to share ownership".

Fact list (keyed to the chapter's claim tags, in chapter order)

  1. F1 (able) Precise: a class template in <memory> that owns an object through a pointer and deletes it when the unique_ptr is destroyed or reset; it can be moved (transferring ownership) but not copied. — source: D1 §20.11.1, §20.11.1.2 (opened, checked); D2 §15.2 (table of contents only; text not opened)
  2. F2 (able) Precise: a function template that constructs a T with new and returns a std::unique_ptr<T> owning it, so no raw new appears in your code. — source: D1 §20.11.1.4 (opened, checked); D4 R.23, C.150 (opened, checked)
  3. F3 (able) Precise: a class template that shares ownership of an object through a control block holding a use count; copying increments the count, destroying or resetting decrements it, and the object is destroyed when the count reaches zero. — source: D1 §20.11.3, §20.11.3.2 (opened, checked)
  4. F4 (able) Precise: the number of shared_ptr instances that share ownership of an object, reported by use_count() ; it is kept in a separately allocated control block, and copies of shared_ptr made or destroyed in different threads must not cause a data race on it (GCC's library updates it with atomic operations). — source: D1 §20.11.3 (opened, checked); D7 (opened, checked)
  5. F5 (able) Precise: a class template that refers to an object managed by shared_ptr without contributing to its use count; lock() returns a shared_ptr that is empty if the object has already been destroyed, and expired() tells whether it has. — source: D1 §20.11.4, §20.11.4.5 (opened, checked)
  6. F6 (able) Precise: a cycle of shared_ptr references among objects; after the last outside owner is gone, every use count in the cycle stays above zero, so the objects leak. Break it with a weak_ptr on one side. — source: D1 §20.11.3.2 (opened, checked); D4 R.24 (opened, checked)
  7. F7 (able) Precise: a sequence container made of separately allocated nodes, each holding an element and a link to the next node (and in a doubly linked list, the previous one); insertion at a known position is constant time, access by index is linear. — source: D1 §22.3.9.1 (opened, checked)
  8. F8 (layer1) You cannot photocopy the tag; you can only hand it over with std::move , and then your hands are empty. — source: D1 §20.11.1.2 (opened, checked); R1 (local lab run record)
  9. F9 (layer1) When it reaches zero, the object is cleaned up. — source: D1 §20.11.3, §20.11.3.2 (opened, checked); R2 (local lab run record)

  11.   12. F12 (l2-unique) Its copy constructor is deleted, so b = a does not compile; GCC's message for unique_copy.cpp says "use of deleted function … unique_ptr(const unique_ptr&)" (mistakes section). — source: R6 (local lab run record)
  13. F13 (l2-unique) Its move operations transfer ownership and leave the source empty, exactly the rules of F2-13. — source: D1 §20.11.1.2 (opened, checked)
  14. F14 (l2-unique) Listing 1 traces this: after b = std::move(a) , a tests false; passing std::move(b) into useAndReturn makes the parameter the owner, and the knife is returned when the function ends. — source: R1 (local lab run record)
  15. F15 (l2-unique) Create one with std::make_unique<T>(args) : no new in your code, and no window in which a raw pointer exists without an owner. — source: D4 R.23, C.150 (opened, checked)

  17. F17 (l2-unique) For arrays, std::unique_ptr<T[]> calls delete[] , but std::vector<T> is almost always the better choice. — source: D1 §20.11.1.3 (opened, checked); D4 SL.con.2 (opened, checked)
  18. F18 (l2-shared) The control block holds the use count (owners) and a weak count (observers); the object is destroyed when the use count drops to zero, and the control block itself when both counts are zero. — source: D1 §20.11.3.2 (opened, checked); D7 (opened, checked)

  22. F22 (l2-shared) That guarantee covers copying and destroying the pointers ; it does not make access to the pointed-to object thread-safe. — source: D1 §20.11.3 (opened, checked)
  23. F23 (l2-choose) The C++ Core Guidelines' order of preference, applied to this course: — source: D4 R.5, R.20, R.21, F.7 (opened, checked)
  24. F24 (l2-cycles) When ana and bo go out of scope, each object's count drops from 2 to 1, never to 0: neither destructor runs ("goes home" never appears), and LeakSanitizer reports two leaked blocks of 64 bytes, allocated by make_shared at lines 17 and 18. — source: R3 (local lab run record)
  25. F25 (l2-cycles) Changing one direction (here both) to std::weak_ptr breaks the cycle; cycle_fixed.cpp prints counts of 1 and both cooks go home. — source: R3 (local lab run record)
  26. F26 (l2-cycles) Rule of thumb: in a structure with "parent" and "child" links, the parent owns the child and the child observes the parent. — source: D4 R.24 (opened, checked)
  27. F27 (l2-list) No line of the list contains delete , and every node is freed exactly once. — source: R4 (local lab run record)
  28. F28 (layer3) Destroying a node destroys its next member, which destroys the next node, which destroys its next member, and so on: the depth of nested destructor calls equals the length of the list. — source: D1 §11.4.6 (opened, checked)
  29. F29 (layer3) For a long list this overflows the stack exactly like F2-20's recursion; deep_list.cpp survived 1000 nodes and crashed at one million with "stack-overflow", the trace full of Node::~Node() frames. — source: R5 (local lab run record)
  30. F30 (layer3) The fix is a destructor that unlinks nodes in a loop, so each node is destroyed with an empty next (Listing 4, lines 49–54); with it, a 200,000-node list was destroyed cleanly under the sanitizer. — source: R4 (local lab run record)
  31. F31 (layer3) Custom deleters. std::unique_ptr<T, D> calls D instead of delete , so it can own anything with a "release" function: a C library handle, a memory-mapped region, a block from your own allocator. — source: D1 §20.11.1.1, §20.11.1.2 (opened, checked)
  32. F32 (layer3) GCC's library stores the deleter next to the pointer, so a stateless deleter type keeps the unique_ptr the size of a raw pointer, while a function-pointer deleter adds a second pointer-sized member. — source: D7 (opened, checked)
  33. F33 (layer3) The idea survives intact: your kernel will have its own small owner types (an owning pointer that calls the kernel heap's free, intrusive reference counts for shared kernel objects), and curriculum B5 requires "containers you write (vector, intrusive lists, hash map) work in the kernel". — source: S1 (local curriculum file)
  34. F34 (layer3) An intrusive list keeps the link inside the element instead of allocating separate nodes, which is the design kernels prefer. — source: S1 (local curriculum file)
  35. F35 (layer3) Every node of a linked list is a separate heap allocation, and walking the list is a chain of dependent loads to unpredictable addresses, which is exactly what F1-32's pointer-chasing benchmark measured as memory latency. — source: D3 §6.2 (table of contents only; text not opened)
  36. F36 (hardware) … e_ptr with the default deleter holds only the pointer (the default deleter is an empty class), and its destructor simply deletes the object it owns: a pointer in a register or stack slot, and a call to the deallocation function at the end of scope, with no run-time bookkeeping (Listing 1 measured the same size as a raw pointer). — source: D2 §15.2 (table of contents only; text not opened); D7 (opened, checked)
  37. F37 (hardware) … ibrary, a shared_ptr copy or destruction in a multi-threaded program performs an atomic read-modify-write on the count in the control block; on a multicore processor such instructions must coordinate cache ownership of that line between cores (HW202, F1-30), so heavily shared pointers copied across threads can become a hot spot. — source: D7 (opened, checked); D3 §6.4 (table of contents only; text not opened)
  38. F38 (hardware) Pass shared_ptr by reference (or pass a raw pointer or reference to the object) when the callee does not need to share ownership. — source: D4 R.30, R.36, F.7 (opened, checked)
  39. F39 (worked) The real output in the code walk-through matches: 1, 2, 1, 1, the destruction message, then "yes". — source: R2 (local lab run record)
  40. F40 (breaks) They are not tags, nobody counts them, and they dangle as soon as the owner deletes the object (F2-23's forensic lab is exactly this). — source: D1 §20.11.1.2.4 (opened, checked)
  41. F41 (breaks) Two shared_ptr s in a cycle wait forever, silently: only a leak checker or a missing destructor message shows the problem. — source: R3 (local lab run record)
  42. F42 (breaks) Destroying an owner may destroy everything it owns, recursively, which can take time and stack (Layer 3). — source: R5 (local lab run record)
  43. F43 (mistakes) RAII and the move rules apply unchanged: unique_ptr is a move-only RAII class, like the file wrapper you wrote in SP102. — source: D1 §20.11.1.2 (opened, checked)
  44. F44 (mistakes) What changes: ownership becomes part of the type : a function signature now says whether it takes ownership ( unique_ptr by value), shares it ( shared_ptr ) or only uses the object ( T& , T* ); and shared ownership brings two new failure modes, cycles and recursive destruction. — source: D4 R.30, R.32, R.34, F.7 (opened, checked); R3 (local lab run record); R5 (local lab run record)
