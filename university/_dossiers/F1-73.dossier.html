F15On an Armv7-M core, reset is handled by the hardware reading the vector table: it loads the main stack pointer from word 0 and the program counter from word 1, then starts executing.D1 §2.1.3; D13 B1.5.5l2-reset
F16The Cortex-M3 executes only Thumb instructions, and the lowest bit of a code address in the table marks Thumb state; that is why the reset-handler entry in this chapter's image is 0x00000041 while the function itself starts at 0x00000040.D1 §2.1.3l2-reset
F17Words 7–10 and 13 are zero because those table positions are reserved in this core's exception list.D1 §2.3.2 Table 2-16l2-reset

F19The hardware gives no such promise: the core's reset sequence sets up registers (it loads SP and PC from the vector table and leaves the general-purpose registers UNKNOWN) and writes nothing to memory.D13 B1.5.5l2-startup
F20The GNU linker manual describes the classic case of a ROM-based system: the initial values are stored in ROM and copied into RAM when the program starts up.D9 §Basic Script Conceptsl2-startup
F21calls main, and makes sure the core never "returns" from reset.D16 startup_<Device>.cl2-startup
F22Their addresses are the information; there is no variable behind them.D9 §Source Code Referencel2-startup
F23The "two words at a fixed place" contract is a property of the Armv7-M architecture that the Cortex-M3 implements, not of a chip vendor.D1 §2.1.3, §2.3.4l3-contract
F24The vendor decides what comes after the system exceptions (which interrupt number belongs to which peripheral) and where memory is, so the vector table's length and the linker script's MEMORY block change from chip to chip.D1 §2.3.4; D11 §3.1, §5l3-contract
F25A RISC-V core works differently: the privileged architecture leaves the reset address to the implementation, and the core starts fetching instructions there; it does not load a stack pointer from a table, so the first instructions must set sp themselves.D8 §2.1.4l3-contract
F26Trap handling uses a separate trap-vector base register, mtvec, rather than a table read at reset.D8 §2.1.1.7l3-contract
F27… vector is 0x1000; the virt board writes a ten-word reset program there that loads a start address and jumps to it with jr t0; with -bios none and no flash image, that start address is the base of RAM, 0x80000000, where -kernel placed the lab's ELF image.D12 hw/riscv/boot.c, hw/riscv/virt.c, target/riscv/cpu_bits.hl3-contract
F28First, every access to a peripheral register must be volatile, or the compiler may merge, reorder or remove it, because to the language a store that nobody reads looks useless.D7 [dcl.type.cv]l3-freestanding
F29… =c++20): the forward-progress clause lets an implementation assume that every thread eventually terminates, performs a volatile access, an atomic or synchronisation operation, or a library I/O call, so a loop that does none of these may be assumed to end.D14 [intro.progress]l3-freestanding
F30The current working draft adds "a trivial infinite loop" to that list and notes that such loops "cannot be removed nor reordered"; clang 18 with -std=c++20 does not apply that newer rule, and the forensic lab of this chapter shows exactly what it did with one.D7 [intro.progress]l3-freestanding
F31Inside the chip, "reading the vector table" is two bus reads issued by the core's reset logic before the first instruction fetch; there is no software involved.D1 §2.1.3hardware
F32… he core reads at reset (address 0 on the Cortex-M3, which fixes the vector table there at reset; the Armv7-M architecture lets a chip choose the reset value of the vector-table offset register, which is otherwise zero) can be backed by different memories.D1 §2.3.4; D13 B3.2.5hardware
F33QEMU does not implement this remapping and always maps SSRAM 1 there.D11 §3.1 Table 3-1; D6 §mps2hardware
F34The CMSDK manual shows exactly this structure: a write buffer in front of a shift register, so software can write the next character while the current one is being sent.D5 §4.3 Figure 4-5, §4.3.1 Table 4-7hardware
F35wfi ("wait for interrupt") asks the core to stop executing until an interrupt or similar event arrives, which on a real chip lets it enter a lower-power state.D1 §2.5.1hardware
F36DATA at offset 0x000, STATE at 0x004 with bit 0 "TX buffer full" (read-only), CTRL at 0x008 with bit 0 "TX enable", and a BAUDDIV register at 0x010 whose value is the peripheral clock divided by the baud rate (minimum 16).D5 §4.3.1 Table 4-7hardware
F37The note also gives the board's main system clock, SYSCLK, as 25 MHz.D11 §3.7 Table 3-4, §4; D12 hw/arm/mps2.chardware
F38The Armv7-M stack is full-descending: a push first decrements SP by 4 and then stores, so the first word pushed lands at 0x2000FFFC.D1 §2.1.2worked
F39Lesson: the map of your memory is fully determined by three inputs you control (the linker script, the section attributes in your code, and the sizes the compiler produced), and you can predict every address before running.D9 §MEMORY, §SECTIONSworked

C. Not found (kept only inside "unverified" boxes, or dropped)

  • Definition clause 'designed to run one program directly on the hardware or under a small real-time OS' (formerly tagged to Yiu and White, not opened): dropped from the jargon box.
  • 'SRAM contents are not defined after power-up' as a general statement: not found in an opened document; replaced by the Armv7-M TakeReset() pseudocode (registers set, memory not written) and the C++ static-initialisation rule.
  • How a real MPS2 board (not QEMU) remaps the lowest 16 KiB at boot is described in AN385 Table 3-1 but was not observed: QEMU does not implement it (QEMU MPS2 page).
  • Anything about a real Cortex-M board (flash, SRAM, UART of the kit boards): untested on hardware; the chapter's 'untested on hardware' box names what is needed.
