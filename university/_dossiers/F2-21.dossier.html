Notes and quotes (paraphrased unless quoted)

  • N4861 7.6.2.8 paragraph 2: the operand of a single-object delete must be null or come from a non-array new-expression, of an array delete from an array new-expression; "If not, the behavior is undefined."
  • N4861 7.6.2.7 paragraph 25: if object initialisation throws and a suitable deallocation function can be found, it is called to free the storage.
  • N4861 17.6.2.1: default operator delete: "If ptr is null, does nothing."
  • ASan paper 3.3: the run-time library replaces malloc and free, poisons red zones, keeps freed memory in a FIFO quarantine and records allocation and free call stacks.
  • LSan design document: blocks reachable from the root set (globals, stacks, registers, TLS) are live; unreachable blocks are reported with their allocation stacks; directly and indirectly leaked blocks are distinguished.
  • Kernel "Overcommit Accounting": mode 0 heuristic (default) refuses obvious overcommits; mode 2 means "in most situations ... a process will not be killed while accessing pages but will receive errors on memory allocation".

Fact list (keyed to the chapter's claim tags, in chapter order)

  1. F1 (able) If allocation fails it throws std::bad_alloc (in the default form). — source: D1 §7.6.2.7, §17.6.3.1 (opened, checked)
  2. F2 (able) Precise: an expression that runs the destructor of the object a pointer points to and then calls a deallocation function ( operator delete ) to release the storage; delete[] does the same for an array created by new[] . Deleting a null pointer does nothing. — source: D1 §7.6.2.8 (opened, checked)
  3. F3 (able) Precise: dynamically allocated storage that the program no longer references and never deallocates; it stays reserved until the process ends. LeakSanitizer reports it at exit. — source: D3 §9.11.10 (table of contents only; text not opened); D7 §14.4 (opened, checked); D8 (opened, checked)
  4. F4 (able) Precise: calling delete (or free ) a second time on a pointer whose storage was already deallocated; undefined behaviour that can corrupt the allocator's data structures. — source: D1 §6.7.5.4.2 (opened, checked); D3 §9.11 (table of contents only; text not opened); D7 §14.4 (opened, checked)
  5. F5 (able) Precise: accessing an object through a pointer after the object was deleted; undefined behaviour, a special case of a dangling pointer (F2-19, F2-23). — source: D1 §6.7.3 (opened, checked)
  6. F6 (able) Precise: the responsibility for ending an object's lifetime and releasing its resources; in modern C++ it is expressed by an owner object (a container, a smart pointer, an RAII handle) rather than by a raw pointer. — source: D4 R.20, R.3 (opened, checked)
  7. F7 (able) Precise: a class template, such as std::unique_ptr or std::shared_ptr , that owns a dynamically allocated object and releases it in its destructor (RAII, F2-11). F2-22 covers them in detail. — source: D1 §20.11.1, §20.11.3 (opened, checked); D2 §6.3, §15.2 (table of contents only; text not opened)
  8. F8 (able) Precise: a run-time leak detector that is part of AddressSanitizer on Linux; at process exit it scans memory for heap blocks no longer referenced and prints where each was allocated. — source: D6 leak detection (opened, checked); D8 (opened, checked)
  9. F9 (layer1) You get back a pointer, a note with the address. delete takes that pointer, tidies the object away, and gives the room back. — source: D1 §7.6.2.7, §7.6.2.8 (opened, checked)
  10. F10 (layer1) Clean up and keep using it: a use after free . — source: D3 §9.11 (table of contents only; text not opened); D7 §14.4 (opened, checked)
  11. F11 (layer1) That object is a smart pointer , and from the next chapter on you will almost never write delete yourself. — source: D2 §6.3 (table of contents only; text not opened); D4 R.11, R.20 (opened, checked)
  12. F12 (l2-two) Layer 2 — the student explanation Two steps each way A new expression first obtains raw storage by calling an allocation function, operator new(std::size_t) , and then constructs the object in it; if the constructor throws, the storage is released again automatically. — source: D1 §7.6.2.7 (opened, checked)
  13. F13 (l2-two) A delete expression runs the destructor and then calls operator delete to release the storage. — source: D1 §7.6.2.8 (opened, checked)
  14. F14 (l2-two) "made soup" appears at new , "destroyed soup" at delete . — source: R1 (local lab run record)
  15. F15 (l2-two) The separation matters later: allocators (F2-25's project, curriculum B5) provide the raw-storage step, and the kernel track writes its own operator new and operator delete (curriculum 1.2). — source: S1 (local curriculum file)
  16. F16 (l2-arrays) Arrays: new[] needs delete[] new T[n] creates an array of n objects and must be released with delete[] , which destroys all n elements; releasing it with plain delete (or a single object with delete[] ) is undefined behaviour. — source: D1 §7.6.2.8 (opened, checked)
  17. F17 (l2-arrays) GCC 13 recognised the mismatch in mismatch.cpp and, with the course's -Werror , refused to compile it ( -Wmismatched-new-delete , reproduced in the mistakes section). — source: R4 (local lab run record)
  18. F18 (l2-arrays) In real code the simplest rule is: never write new[] ; use std::vector . — source: D4 R.11, SL.con.1 (opened, checked)
  19. F19 (l2-paths) LeakSanitizer reports 16 bytes allocated at leak.cpp:13 and never freed. — source: R2 (local lab run record)
  20. F20 (l2-paths) Exceptions add invisible paths: in Listing 4, cookRaw throws between new and delete , the delete is skipped, and the sanitizer reports a 1-byte leak (the size of an empty Pan ); cookOwned , identical except for the owner object, prints "pan returned" during the same exception. — source: R5 (local lab run record)
  21. F21 (l2-owner) Listing 3 shows the opposite failure. clearTable deletes the tray it was given, and main deletes it again: a double free, which AddressSanitizer reports with three stack traces (the second free, the first free, and the allocation). — source: R3 (local lab run record)
  22. F22 (l2-owner) The C++ Core Guidelines' answer is to make ownership visible in types: a raw pointer T* never owns; an owner is an object whose destructor releases the resource. — source: D4 R.3, R.1 (opened, checked)
  23. F23 (l2-owner) With std::unique_ptr<Bill> (Listing 2's fixed version) every path frees the bill exactly once, and the sanitizer is silent. — source: R2 (local lab run record)
  24. F24 (l2-why) Why smart pointers, in one sentence Because "delete exactly once, on every path, by the right party" is a property a human cannot check reliably in a large program, but a destructor guarantees it by construction (F2-11); smart pointers are the standard library's RAII owners for heap objects. — source: D2 §6.3, §15.2 (table of contents only; text not opened); D4 R.1, R.20 (opened, checked)
  25. F25 (layer3) Layer 3 — the engineer's depth Replaceable allocation functions. operator new and operator delete are ordinary functions that a program may replace with its own definitions, in several overloads: plain, array, sized (the deallocation function receives the object size) and aligned (for over-aligned types). — source: D1 §17.6.2, §6.7.5.4 (opened, checked)
  26. F26 (layer3) The sanitizer reports in this chapter show the sized form at work: the double free went through operator delete(void*, unsigned long) . — source: R3 (local lab run record)
  27. F27 (layer3) "General-purpose kernel allocation with all forms of operator new and delete"). — source: S1 (local curriculum file)
  28. F28 (layer3) Allocators, containers and kernels use it; application code almost never should. — source: D1 §17.6.2.3, §7.6.2.7 (opened, checked)
  29. F29 (layer3) Curriculum 1.1 lists "lifetime of objects created in raw memory (placement new, start of lifetime)" as an undefined-behaviour trap for kernels; F2-23 returns to it. — source: S1 (local curriculum file)
  30. F30 (layer3) The default new throws std::bad_alloc when it cannot allocate; new (std::nothrow) T returns nullptr instead. — source: D1 §17.6.2.1, §17.6.3.1 (opened, checked)
  31. F31 (layer3) Only the "don't overcommit" mode ( vm.overcommit_memory set to 2) promises that, in most situations, a process gets an allocation error instead of being killed later while it uses its pages. — source: D10 (opened, checked)
  32. F32 (layer3) Freed blocks are not reused at once but kept in a quarantine and marked as poisoned in shadow memory, so a later access or second free is recognised; each block remembers the stack trace of its allocation and its deallocation, which is where the three traces in its reports come from. — source: D6 §3.3 (opened, checked)
  33. F33 (layer3) LeakSanitizer runs at exit and looks for heap blocks that no pointer in memory still refers to. — source: D8 (opened, checked)
  34. F34 (layer3) Two consequences: a leak whose pointer still sits somewhere in memory at exit can be missed, and a sanitizer only checks the code it instrumented; reads performed inside an uninstrumented library may not be checked. — source: D6 §3.5 (opened, checked)
  35. F35 (hardware) A general-purpose allocator such as the C library's obtains large regions of virtual address space from the kernel, then hands out pieces of them, keeping its bookkeeping (block sizes, free lists) in the same memory, often just before each block it returns. — source: D3 §9.9.5, §9.9.6 (table of contents only; text not opened); D9 (opened, checked); D7 §17.2 (opened, checked)
  36. F36 (hardware) The pages behind a heap region are mapped on first touch by the kernel's page-fault handler (curriculum B4); freeing a small block normally returns it to the allocator's lists, not to the kernel. — source: D3 §9.3.4 (table of contents only; text not opened); D9 (opened, checked)
  37. F37 (worked) The real report (code walk-through) says "Direct leak of 16 byte(s) in 1 object(s)", frames printBill(int, double) leak.cpp:13 and main leak.cpp:28 . — source: R2 (local lab run record)
  38. F38 (breaks) The real allocator does not; only a sanitizer, which deliberately delays reuse and marks freed memory, notices (Layer 3). — source: D6 §3.3 (opened, checked)
  39. F39 (breaks) In memory, a double free can corrupt the allocator's own data, so the crash may come later in code that did nothing wrong. — source: D3 §9.11 (table of contents only; text not opened); D7 §14.4 (opened, checked)
  40. F40 (breaks) The operating system reclaims all of a process's memory when it ends, so a leak in a short program is invisible; in a server, a robot controller or a kernel that never "closes", leaks accumulate until memory runs out. — source: D3 §9.11.10 (table of contents only; text not opened); D7 §14.4 (opened, checked)
  41. F41 (mistakes) RAII is exactly the answer here; a destructor runs on every path out of a scope, including exceptions (F2-16), so an owner object that deletes in its destructor deletes exactly once. — source: D1 §8.7, §14.3 (opened, checked); R5 (local lab run record)
  42. F42 (mistakes) What changes: heap memory is a resource like a file, but the raw pointer that names it carries no ownership information, so the compiler cannot help you balance new and delete beyond simple cases; the sanitizers become part of every build. — source: D4 R.3, I.11 (opened, checked); R4 (local lab run record)
  43. F43 (lab-expect) The plain build may print a plausible seat number or garbage; that difference is the lesson. — source: R6 (local lab run record)
