Notes and quotes (paraphrased unless quoted)

  • N4861 8.7 paragraph 2: "On exit from a scope (however accomplished), objects with automatic storage duration ... are destroyed in the reverse order of their construction."
  • x86-64 psABI 3.2.2: "each function has a frame on the run-time stack. This stack grows downwards from high addresses."
  • OSTEP 14.1: stack memory is allocated and freed implicitly by the compiler ("automatic memory"); heap memory is allocated and freed explicitly by the programmer.
  • glibc MallocInternals: several arenas, each with a mutex, reduce contention between threads; free chunks are kept in bins.
  • pthread_create(3), NOTES: under NPTL the RLIMIT_STACK soft limit at program start (if not unlimited) is the default stack size of new threads; otherwise 2 MB on most architectures.

Fact list (keyed to the chapter's claim tags, in chapter order)

  1. F1 (able) Precise: the property of an object that defines the minimum lifetime of its storage: automatic, dynamic, static or thread. — source: D1 §6.7.5 (opened, checked)
  2. F2 (able) The C++ standard describes automatic storage, not a "stack"; the stack is how the platforms of this course implement it. — source: D1 §6.7.5.3 (opened, checked); D3 §3.7.1 (table of contents only; text not opened); D7 §14.1 (opened, checked)
  3. F3 (able) Precise: the part of the stack used by one activation of a function: its local variables, saved registers, the return address and outgoing arguments as the ABI requires (HW202 met it at machine level, glossary ). — source: D3 §3.7.1, §3.7.4 (table of contents only; text not opened); D5 §3.2.2 (opened, checked)
  4. F4 (able) Not the same as the "heap" data structure of algorithms courses. — source: D1 §6.7.5.4, §7.6.2.7 (opened, checked); D3 §9.9 (table of contents only; text not opened); D7 §14.1 (opened, checked)
  5. F5 (able) Precise: storage for objects with static storage duration (namespace-scope variables, static locals and members); it lasts from program start (or first use, for static locals) until program end. — source: D1 §6.7.5.1 (opened, checked)
  6. F6 (able) Precise: an attempt to grow the stack beyond its reserved size; on Linux this touches an unmapped guard region and the process receives SIGSEGV, which AddressSanitizer reports as "stack-overflow". — source: D3 §9.7.2 (table of contents only; text not opened); R6 (local lab run record)
  7. F7 (able) Precise: accessing an object with automatic storage duration through a pointer or reference after the block that declared it has exited; undefined behaviour, reported by AddressSanitizer as "stack-use-after-scope". — source: D1 §6.7.5.3, §6.7.3 (opened, checked); D6 Clang intro (opened, checked)
  8. F8 (layer1) Nobody has to remember to clean up, and it is very fast. — source: D3 §3.7.1 (table of contents only; text not opened); D7 §14.1 (opened, checked)
  9. F9 (layer1) That is powerful, but somebody has to be responsible for giving it back, at the right time, exactly once. — source: D1 §6.7.5.4, §7.6.2.8 (opened, checked)
  10. F10 (layer1) They are ready before main starts and stay until the program ends. — source: D1 §6.7.5.1, §6.9.3.2 (opened, checked)
  11. F11 (l2-durations) Layer 2 — the student explanation Three storage durations you will use C++ gives every object a storage duration . — source: D1 §6.7.5 (opened, checked)

F14 (l2-frames) Because calls and returns nest, the frames form a last-in, first-out pile, so reserving and releasing is a single adjustment of the stack pointer register: nothing has to be searched or recorded. — source: D3 §3.7.1 (table of contents only; text not opened); D5 §3.2.2 (opened, checked)

  16. F16 (l2-frames) Destructors of automatic objects run when their block ends, in reverse order of construction; this is the mechanism under RAII (F2-11). — source: D1 §8.7 (opened, checked)
  17. F17 (l2-frames) Listing 3 shows a stack Ticket destroyed as takeOrder returns. — source: R3 (local lab run record)
  18. F18 (l2-heap) It begins when it is created and ends when it is explicitly destroyed, which can be in a different function, much later. — source: D1 §6.7.5.4, §7.6.2.8 (opened, checked)
  19. F19 (l2-heap) That is the only way to create an object whose size is known only at run time (a vector of n orders) or that must outlive the function that made it (Listing 3's heap ticket, returned to main ). — source: R3 (local lab run record)
  20. F20 (l2-heap) In modern C++ that "someone" is an owner object: a container, or a smart pointer such as the std::unique_ptr returned by std::make_unique in Listings 1 and 3 (read it for now as "make one object on the heap, with an owner that deletes it"; F2-22 explains it). — source: D4 R.1, R.20 (opened, checked)
  21. F21 (l2-handles) That is the common shape: the small handle (pointer, size, capacity) has automatic storage, the elements are on the heap, and the handle's destructor frees them. — source: D2 §5.2, §6.3 (table of contents only; text not opened); R4 (local lab run record)

  23. F23 (layer3) On Linux the main thread's stack size limit is a per-process resource limit; in this build's container the shell reported 8192 KiB ( ulimit -s ). — source: R5 (local lab run record)
  24. F24 (layer3) Not verified — check before relying on this Checked in the verification pass: the Linux manual page for pthread_create — source: D10 (opened, checked)
  25. F25 (layer3) With an 8192 KiB limit, at most 8192 such frames fit even if each frame were nothing but its array; the real frames are larger, and AddressSanitizer adds red zones around locals, so the limit is lower still. — source: D6 §3.4 (opened, checked)
  26. F26 (layer3) With an 8192 KiB limit, at most 8192 such frames fit even if each frame were nothing but its array; the real frames are larger, and AddressSanitizer adds red zones around locals, so the limit is lower still. 1000 calls fit; 100000 calls (about 100 MiB of arrays alone) cannot, and the run ended with "stack-overflow". — source: R6 (local lab run record)
  27. F27 (layer3) A general-purpose allocator keeps data structures describing free blocks (free lists, size classes), may need to ask the operating system for more address space, and must be safe when several threads allocate at once. — source: D3 §9.9.3 (table of contents only; text not opened); D8 (opened, checked); D7 §17.2, §17.3 (opened, checked)
  28. F28 (layer3) Listing 1 printed two consecutive 4-byte heap objects 0x20 bytes apart in both builds: each allocation carries hidden bookkeeping and rounding, not just the 4 bytes asked for. — source: R1 (local lab run record)
  29. F29 (layer3) In the sanitizer build, the frames' local variables appeared at addresses starting 0x7f… and increasing by 64 per call, while the plain build's were at 0x7ffe… and decreasing. — source: R1 (local lab run record)
  30. F30 (layer3) This is the sanitizer's "fake stack" for detecting use-after-return, which keeps locals in separately allocated memory; the runtime of this build's GCC turns it on by default on Linux (F2-18, Layer 3). — source: D6 UAR (opened, checked); D9 (opened, checked)
  31. F31 (layer3) In a freestanding kernel nothing runs those constructors unless your start-up code calls them (curriculum 1.2, the init_array section; SP301's forensic lab). — source: D1 §6.9.3.2, §6.9.3.3 (opened, checked); S1 (local curriculum file)
  32. F32 (hardware) How the hardware actually does it On x86-64 the stack pointer register rsp holds the address of the top of the stack; a call instruction pushes the return address and jumps, and the function then moves rsp down by its frame size; ret pops the return address back into the instruction pointer. — source: D3 §3.7.2 (table of contents only; text not opened); D5 §3.2.2 (opened, checked)
  33. F33 (hardware) The stack's memory is ordinary virtual memory; Linux places an unmapped guard region beyond the stack's limit so that running past it causes a page fault and SIGSEGV instead of silently overwriting other data. — source: D3 §9.7.2 (table of contents only; text not opened)
  34. F34 (hardware) The heap is also ordinary memory: the C library's allocator obtains large regions from the kernel and carves them up in user space; the processor does not know which bytes are "heap". — source: D3 §9.9 (table of contents only; text not opened); D8 (opened, checked)
  35. F35 (code) The "shadow bytes" map shows how the sanitizer knows: f8 marks memory of a variable whose scope has ended. — source: D6 §3.1 (opened, checked); R2 (local lab run record)
  36. F36 (breaks) A popped stack frame still contains its old bytes until the next call overwrites them, so a dangling pointer into it may read the "right" value for a while; that is why the bug can hide without a sanitizer. — source: D3 §9.11.8 (table of contents only; text not opened); R2 (local lab run record)
  37. F37 (breaks) The heap allocator does not: memory that is never given back stays taken until the program ends (a leak, F2-21), and memory given back twice corrupts the allocator's own bookkeeping. — source: D3 §9.11.10 (table of contents only; text not opened); D7 §14.4 (opened, checked)
  38. F38 (breaks) The direction is a property of the platform, not of stacks in general. — source: R1 (local lab run record)
  39. F39 (mistakes) What carries over: destructors still run at the end of scope, in reverse order; RAII handles such as std::vector and std::string still clean up; the frame you read at machine level in HW202 (F1-31) is the same frame. — source: D1 §8.7 (opened, checked); D3 §3.7.1 (table of contents only; text not opened)
  40. F40 (mistakes) What changes: you now choose lifetimes yourself: automatic objects end with their block whether or not a pointer still refers to them, and dynamic objects end only when someone ends them; the stack is small and fixed-size, the heap is large but costs work and responsibility. — source: R5 (local lab run record)

F41 (lab-expect) Expected observations This build's numbers: stack limit below, and frames 64 bytes apart in both builds of the unmodified Listing 1 (decreasing in the plain build, increasing on the sanitizer's fake stack), as shown in the code walk-through. — source: R1 (local lab run record); R5 (local lab run record)
