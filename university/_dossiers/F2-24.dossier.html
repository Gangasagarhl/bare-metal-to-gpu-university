Notes and quotes (paraphrased unless quoted)

  • N4861 9.4.4 paragraph 3.4: for an aggregate, list-initialisation (including an empty {}) is aggregate initialisation; only 3.5 (no elements and a class with a default constructor, not an aggregate) is value-initialisation. N4861 9.4 paragraph 6.2: zero-initialisation of a class sets its padding bits to zero bits. So Loose order{} sets the members to zero but the standard does not promise zero padding.
  • N4861 11.4 paragraph 19 (note): non-static data members with the same access control are allocated so that later members have higher addresses.
  • N4861 17.2.4: use of offsetof with a type other than a standard-layout class is conditionally-supported.
  • x86-64 psABI 3.1.2: "Structures and unions assume the alignment of their most strictly aligned component. Each member is assigned to the lowest available offset with the appropriate alignment. The size of any object is always a multiple of the object‘s alignment." "The value of _Alignof(max_align_t) is 16." Misaligned accesses "are slower than aligned accesses but otherwise behave identically", except __m128, __m256, __m512.
  • AAPCS64 Aggregates and RISC-V "C/C++ Type Sizes and Alignments": the same alignment and size rules for aggregates; RISC-V: "The alignment of max_align_t is 16."
  • Intel SDM Vol. 1 4.1.1: unaligned word/doubleword/quadword access allowed but needs two memory accesses; some double-quadword instructions raise #GP on unaligned operands.

Fact list (keyed to the chapter's claim tags, in chapter order)

  1. F1 (able) Precise: an implementation-defined power of two, given by alignof(T) , such that every object of type T has an address that is a multiple of it; on the x86-64 build used here alignof(int) was 4 and alignof(double) 8. — source: D1 §6.7.6, §7.6.2.5 (opened, checked); R1 (local lab run record)
  2. F2 (able) Precise: bytes of an object's representation that belong to no member; inserted so that each member meets its alignment and so that the size is a multiple of the struct's alignment (making arrays work); their values are unspecified unless the object was zero-initialised in a way that sets them. — source: D1 §6.8, §9.4 (opened, checked); D7 §3.1.2 (opened, checked)
  3. F3 (able) Precise: alignof(T) yields a std::size_t constant, the alignment requirement of T ; alignas requests a stricter one. — source: D1 §7.6.2.5, §9.12.2 (opened, checked)
  4. F4 (able) Precise: offsetof(type, member) from <cstddef> , a constant of type std::size_t ; conditionally supported for types that are not standard-layout. — source: D1 §17.2.4 (opened, checked)
  5. F5 (able) Precise: a class type with, among other conditions, all non-static data members having the same access control, no virtual functions or virtual base classes, and members that are themselves standard-layout; tested with std::is_standard_layout_v . — source: D1 §11.2 (opened, checked)
  6. F6 (able) Tested with std::is_trivially_copyable_v . — source: D1 §6.8, §11.2 (opened, checked)
  7. F7 (able) Precise: accessing an object through a glvalue of a type other than its dynamic type, a corresponding signed/unsigned type, or char / unsigned char / std::byte is undefined behaviour. — source: D1 §7.2.1 (opened, checked)
  8. F8 (able) Precise: encoding of values into a defined external representation (field order, sizes, byte order, no padding) independent of the in-memory object representation; decoding is the reverse. — source: D3 §2.1.3 (table of contents only; text not opened)
  9. F9 (layer1) The computer likes each value to start at a box number that "fits" it: an int at a multiple of 4, a double at a multiple of 8. That rule is called alignment . — source: D1 §6.7.6 (opened, checked); D7 §3.1.2 (opened, checked)
  10. F10 (layer1) If a double comes right after a one-byte char , it cannot start at box 1, so the compiler leaves boxes 1 to 7 empty. Those empty boxes are padding . — source: D3 §3.9.3 (table of contents only; text not opened)
  11. F11 (layer1) Listing 1 measured it: the same four values took 24 boxes in one order and 16 in another. — source: R1 (local lab run record)

F24 (layer3) The C++ standard fixes only the order of members and leaves sizes and alignments to the implementation; the platform's ABI document (for x86-64 Linux, the System V AMD64 psABI; for AArch64, the procedure call standard; for RISC-V, the RISC-V ELF psABI) pins them down so that separately compiled code agrees. — source: D1 §6.7.6, §11.4 (opened, checked); D7 §3.1.2 (opened, checked); D8 §Aggregates (opened, checked); D9 §C/C++ Type Sizes and Alignments (opened, checked)

  26. F26 (layer3) Taking the address of such a member "usually results in an unaligned pointer value", which is why GCC warns about it by default; using that pointer on a processor that requires aligned accesses can fault. — source: D5 §6.35.1, §6.62.10, §3.8 (opened, checked)
  27. F27 (layer3) Allocators and alignment. operator new and malloc return memory aligned for any fundamental type ( alignof(std::max_align_t) , which the x86-64 ABI fixes at 16); over-aligned types use the aligned forms of new since C++17. — source: D1 §6.7.5.4.1, §7.6.2.7 (opened, checked); D7 §3.1.2 (opened, checked)
  28. F28 (hardware) An aligned 8-byte value never straddles two pieces; a misaligned one can, and Intel's manual says such an unaligned access needs two memory accesses instead of one. — source: D10 §4.1.1 (opened, checked)
  29. F29 (hardware) … ligned access needs two memory accesses instead of one. x86-64 handles ordinary misaligned loads in hardware, which is why Listing 4 printed 42; some of its own instructions (certain 16-byte SIMD loads) require alignment and raise a general-protection exception otherwise, and other architectures may be stricter (box in Layer 3). — source: D10 §4.1.1 (opened, checked); R4 (local lab run record)
  30. F30 (worked) Prediction: sizeof 24 , alignof 8 . The lab run printed "E 24 (align 8)". — source: R5 (local lab run record)
  31. F31 (code) Row 3: 01 (spicy), three padding bytes, then 7 (table) little-endian. — source: R2 (local lab run record)
  32. F32 (breaks) A misaligned value can often be read anyway (x86-64 did, R4); what breaks is the language contract, and the result may be a fault on another processor or a mis-optimisation on any. — source: D1 §3.30, §6.7.6 (opened, checked)
  33. F33 (breaks) Padding bytes are not "empty"; they hold whatever was there before, unless zeroed, and they are copied and sent along with the object. — source: D1 §6.8 (opened, checked)
  34. F34 (mistakes) What changes: you now see that a struct's bytes include padding chosen by the compiler under alignment rules from the platform ABI, so an object's in-memory form is not a data format; anything that crosses a program boundary needs an explicit layout. — source: D1 §6.7.6 (opened, checked); D7 §3.1.2 (opened, checked)
