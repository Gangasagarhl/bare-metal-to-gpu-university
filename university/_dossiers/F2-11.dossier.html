F1… borrows from the system and must give back. Analogy: A tool from the tool wall. Precise: Anything that must be acquired and later released: memory, open files, locks, network connections, GPU memory; if not released, it stays taken until the process ends.D3 R (introduction), R.1F2-11-jargonconfirmed
F2… when you leave the room. Precise: The technique of acquiring a resource in a constructor and releasing it in the destructor of an owning object, so that the release happens on every path out of the owner's scope, including early returns and exceptions.D3 R.1, E.6F2-11-jargonconfirmed
F3… file it has open. Analogy: The number on the tag of a borrowed tool. Precise: On Linux and other POSIX systems, a non-negative integer returned by open() that indexes the process's table of open files; it stays valid until close() or the end of the process.D4 open(2), close(2)F2-11-jargonconfirmed
F4… key to the spice cabinet. Precise: Here: a lock taken with Linux's flock() on an open file; it is held through that open file and released by flock(fd, LOCK_UN) or when the file is closed; "advisory" means only programs that also ask for the lock are stopped.D4 flock(2)F2-11-jargonconfirmed
F5… back. Analogy: The name written on the borrowing card. Precise: The object whose destructor releases the resource; with RAII each resource has exactly one owner at a time, which is why the wrapper forbids copying (F2-13 adds transfer of ownership by moving).D3 R (introduction), C.31F2-11-jargonconfirmed
F6… entry is one file descriptor. The function open_file_count() in the listings counts those entries (the listing itself uses one descriptor while it reads the folder, which is why the count starts at 4: standard input, output, error, and the folder being read).D4 proc_pid_fd(5), stdin(3)F2-11-layer2confirmed
F7… 5 lowers its own limit to 32 open files and then opens without closing. The run printed open failed after 29 leaked files: Too many open files. A leak is a slow failure: the program works for a while, then a completely unrelated open somewhere else fails.D4 open(2), getrlimit(2)F2-11-layer2confirmed
F8… if it fails, so a File object always owns an open file (its invariant). The destructor calls close. Copying is deleted, because two objects closing the same descriptor would be the "closed twice" bug of F2-10. And a member function, write_line, does the work.D3 R.1, C.21, C.42F2-11-layer2confirmed
F9… succeeded, so the lock had been released at the closing brace. When a standard RAII type exists for your resource, use it; write your own wrapper only for resources the library does not cover, such as raw descriptors, device handles or, later, GPU memory.D2 §22.2.1, §29.9.2.1, §32.5.4.1, D3 R.1F2-11-layer2confirmed
F10… second acquisition throws, the destructor of the half-built object does not run (F2-10), and the first resource leaks. Give each resource its own small wrapper and make them members; already-constructed members are destroyed even when the constructor throws.D2 §14.3, D3 C.31, R.1F2-11-layer3confirmed
F11… must not fail loudly. close can report an error, but a destructor must not throw (F2-10). If a caller needs to know whether data reached the disk, offer an explicit close() or flush() member that returns an error, and let the destructor be the safety net.D3 C.36, C.37, D4 close(2)F2-11-layer3confirmed
F12Copy is forbidden; move comes next. A File cannot yet be returned by name from a function (return f;) or stored in a std::vector. F2-13 adds move operations that transfer ownership.D2 §11.10.5, §22.2.3F2-11-layer3corrected: "returned by name (return f;)"; a prvalue return is allowed by guaranteed elision (D2 §11.10.5)
F13… through a special instruction, to add or remove an entry. The kernel only frees the entry when the program asks, or when the whole process ends. That is why a leak is invisible to the program itself: the table lives in the kernel, not in your variables.D4 open(2), syscalls(2), syscall(2), _exit(2)F2-11-hardwareconfirmed
F14… What the forensic evidence shows: descriptor 3 still refers to menu.lock, which still holds the exclusive lock, although the variable that held the number is long gone. Table contents from run R4; lock semantics as described in the Linux flock(2) manual page.D4 flock(2)F2-11-hardwareconfirmed
F15… is released by LOCK_UN or when every descriptor referring to that open file description has been closed. If one process opens the same file twice, the two descriptors are treated independently, so a lock held through one can refuse a lock through the other.D4 flock(2)F2-11-hardwareconfirmed
F16A forgotten key can be found and brought back. A leaked descriptor cannot be recovered by the program: the variable holding the number is gone, and only the end of the process frees the entry (R4).D4 _exit(2)F2-11-breaksconfirmed
F17Resource Acquisition Is Initialisation: acquire the resource in a constructor, release it in the destructor of the same object.D3 R.1F2-11-answersconfirmed
