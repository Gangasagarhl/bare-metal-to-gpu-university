Forensic question — "The helper that stood still" — answer key

How the evidence was made. The Lab Engineer took the practical's reference solution (beans.in) and changed only its last line from GO BACK TO STEP 1 to GO BACK TO STEP 2, then ran it with the unchanged helper (forensic_beans.cpp, situation 1). The fixed file forensic_beans_fixed.in is byte-identical to beans.in; its run ends like this (forensic_beans_fixed.out, exit code 0):

What happened at the end:
  beans in the left cup:         5
  beans in the right cup:        5
  bean still in the hand:        no
  the helper reached STOP:       yes
  steps the helper did:          19
  steps it did not understand:   0
  steps where nothing happened:  0
  task passed:                   yes
  1. Observation (3). 1 bean ended in the right cup; 5 should have. The first "nothing happened" is the fifth trace line, the second run of step 2: "step 2: PUT THE BEAN IN THE RIGHT CUP -> nothing happened: the hand is empty". The summary confirms it: "beans in the right cup: 1", "steps where nothing happened: 9". (1 for 1 and 5, 1 for the line, 1 for the reason "the hand is empty".)
  2. Guesses (3). Any two different, sensible guesses, for example: the loop goes back to the wrong step; the hand (or the PUT step) is broken; the STOP check asks for the wrong number; a PICK UP step is missing from the loop. (3 for two guesses written before the conclusion; 1 for one guess.)
  3. Root cause (4). Step 4, "GO BACK TO STEP 2", is wrong: it should go back to step 1. Proof from the trace: the first time round, step 1 picks up a bean ("hand: one bean") and step 2 puts it down ("right cup 1, hand: empty"). Step 4 then says "going to step 2", so step 1 never runs again; nobody picks up a new bean, the hand stays empty, and every later step 2 says "nothing happened: the hand is empty". The right cup therefore stays at 1 and the check "IF THE RIGHT CUP HAS 5 BEANS" always answers "no, the right cup has 1". (2 for naming step 4, 2 for the proof that step 1 is skipped.)
  4. Judge the guesses (4). "The hand is broken" is wrong: the hand worked at the first step 1 and step 2 (left cup 9, right cup 1), so PICK UP and PUT both work when they are given the chance; the same helper passed the reference run. "The loop goes back to the wrong step" is right (above). The helper gave up because nothing inside the loop (steps 2, 3, 4) ever changes the number the check looks at, so "IF THE RIGHT CUP HAS 5 BEANS" can never say yes: an infinite loop, exactly as in F0-07 ("the cup that never fills"); the 30-step limit is what stopped it ("gave up after 30 steps: yes"). (2 for ruling out the broken hand with evidence, 2 for the infinite-loop reason.)
  5. Fix and prevention (3). Fixed steps: 1. PICK UP ONE BEAN FROM THE LEFT CUP. 2. PUT THE BEAN IN THE RIGHT CUP. 3. IF THE RIGHT CUP HAS 5 BEANS, STOP. 4. GO BACK TO STEP 1. The run with these steps passes (above: 19 steps, right cup 5, "task passed: yes"). Prevention, any one of: for every "GO BACK", point at the step that gives the hand a new bean and check it is inside the loop; act the steps out with real cups for two rounds before running; for every loop, name the line that moves it towards the end (F0-07). (2 for the four steps, 1 for a prevention.)

Wrong answers and why. "The STOP check is wrong (5 is too many)": the check is right; with step 4 fixed the same check stops the helper at 5. "The helper is too slow": it did 30 steps; the trouble is that 27 of them changed nothing. "Step 2 is the bug": step 2 is correct; it only fails because step 1 is never reached again.

Other correct answers. Marking points (50; see the table in the paper):

  • Situation 1 (12): "task passed: yes", "steps it did not understand: 0", "steps where nothing happened: 0". Deduct 4 if a step was not understood (a typing slip in a step shape) but the task still passed; 0 if "task passed: no".
  • Situation 2 with the same file (14): "task passed: yes". 0 otherwise.
  • Says when to stop (6): STOP or IF … STOP reached in both runs ("the helper reached STOP: yes"); 0 if either run says "gave up after 30 steps" or "ran out of steps before STOP".
  • Debugging record (8): one line per failed run with the trace clue, the step changed and why; 8 if every failed run has a line; 4 if lines are missing; 8 also when the first run passed and the learner wrote why.

Course project — reference notes

Feasibility. The Lab Engineer's reference for the rule card is F0-07 Listing 2, university/labs/F0-07/add_rules.cpp, which follows the card's four rules column by column for every pair of four-switch numbers; its recorded run printed 0101 + 0011 = 01000 and checked 256 sums, 0 wrong (exit code 0). So the rules on the card are complete: every sum from 0 + 0 to 15 + 15 fits on the five-switch answer board (the biggest, 15 + 15 = 30 = 11110).

Sums for the marker to set (all worked by the same rules; the two with traces are printed by real runs): 5 + 3 = 01000 (8; F0-07 worked example and add_rules.out); 6 + 7 = 01101 (13; F0-07 Check yourself 4); 11 + 6 = 10001 (17; key_checks.out, column trace above in the final's Q14); 15 + 15 = 11110 (30; the F0-07 lab check); 0 + 0 = 00000 (0).

Where the machine stops working (for the report): a number of 16 or more does not fit on a four-switch board, and a sum over 31 would not fit on the answer board; the fix is more switches, which is the "ninth box" extension of F0-02.

Marking notes. Correctness (35 %): run the marker's five sums; one wrong sum that the learner finds and corrects on the record sheet still earns the points, because finding it is the F0-08 milestone. Engineering quality (20 %): hand the rule card to someone who has not seen the course; if they ask a question, note which rule was unclear. Evidence (20 %): the record sheet must keep crosses, not only ticks. Documentation (15 %): the three parts of the report. Presentation (10 %): the demo sum is chosen by the stranger, not the learner.
