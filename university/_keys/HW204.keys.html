Midterm — model answers and marking points (60 points)

  1. M1 (3). Address bus: where (the address of the transfer); data bus: what (the value); control signals: the kind of transfer (read or write) and when the signals are valid (clock or strobe), plus handshakes. Bus contention: two drivers enabled on the same line at the same time; with push-pull outputs they fight electrically, with open-drain lines the result is the AND of both; either way the value read is wrong. Marking: three groups 2 (all three needed for 2, two for 1), contention 1.
  2. M2 (5). (a) 224 = 16,777,216 addresses. (b) 0x0FFF → RAM, offset 0xFFF (its last byte); 0x2004 → bus error (LEDS ends at 0x2003); 0x401F → DMA, offset 0x1F (its last byte); 0x4020 → bus error (DMA ends at 0x401F). Marking: (a) 1, (b) 1 each. The classic error is treating size as the last address (0x4020 "DMA offset 0x20"): 0 for that item.
  3. M3 (5). (a) 4 bytes × 125,000,000 = 500,000,000 bytes per second. (b) Half the cycles move data: 250,000,000 bytes per second. (c) 70 % of that: 175,000,000 bytes per second. (d) Any two of: wait states added by slow devices; arbitration time; protocol overhead beyond the address phase; other masters; the figures are peaks, a measurement is sustained. Marking: 1, 1, 1, 2.
  4. M4 (4, rubric). MMIO: device registers occupy addresses of the memory address space and are reached with ordinary loads and stores; port I/O: a separate x86 I/O address space reached only by in/out. The CPU checks the privilege level (and the I/O permissions the OS sets) before port I/O; a user program lacks it, the CPU faults and Linux delivers SIGSEGV (F1-41 run R4, exit code 139); a kernel runs with the privilege that allows it. The RISC-V and Arm virt boards use MMIO only (no port space in their maps). Full marks need all three parts.
  5. M5 (5). (a) Write 0x08 (1 only to bit 3). Writing back 0x0B would write 1 to bits 0 and 1 as well and clear two events that have not been handled. (b) 0x40000010 OR 0x4 = 0x40000014; then 0x40000014 AND NOT 0x10 = 0x40000004 (bit 30 kept both times). (c) 0x3e8 + 5 = 0x3ED; bit UART_LSR_DR = 0x01. Marking: (a) 2 (1 value, 1 consequence), (b) 2, (c) 1.
  6. M6 (6). (a) wait_b waits: at 18 it loads the status word (mov eax,DWORD PTR [rdi]), at 1a tests bit 0, and at 1c jumps back to 18 while the bit is 0, so one load per iteration. (b) wait_a is one load and ret: the loop is gone. Through a plain pointer nothing in the loop can change *status as far as C++ is concerned and the loop has no observable behaviour, so the compiler may assume it ends; it keeps only the load of the return value. Volatile accesses are observable behaviour and must be performed ([intro.abstract], F1-41 Layer 2), which is why wait_b keeps its loop. (c) Any two of: the access is not atomic; it is not a barrier (the CPU or the bus may still reorder or post it relative to normal memory accesses); it does not make the location uncached (the mapping's memory type does); it does not make sharing between threads safe. Marking: (a) 2, (b) 2, (c) 2. Accept the note that the recorded disassembly is from g++ 13.3; g++ 15.2 pads wait_b with a longer nop but emits the same loop (README of HW204-P).
  7. M7 (6). (a) 20 ticks: the receiver holds one byte, so at most one byte may arrive between polls. (b) 180 / 20 = 9 arrivals; the receiver keeps 1, so 8 are lost per long pass. (c) 9 bytes, plus 1 at the boundary = 10; choose 16 slots. (d) 65,536 × 2 = 131,072 ticks. Marking: 1, 2, 2, 1.
  8. M8 (4, rubric). (a) While the handler runs, the main program cannot run (and often lower-priority interrupts are blocked), so whatever the handler waits for can never happen: deadlock or missed deadlines. (b) In the model the handler can never interrupt pop() half-way, because the program is single-threaded; on real hardware it can interrupt between any two instructions, and a count written by both sides can be corrupted. F1-42 says: the producer updates only the head and the consumer only the tail, each index update a single correctly ordered store (no shared count), or the update is protected by briefly disabling the interrupt. 2 points each part.
  9. M9 (6). (a) IRR = 1010 0100: lines 2, 5, 7 pending; IMR = 0000 0100: line 2 masked; ISR = 0100 0000: line 6 in service. (b) Pending and not masked: 0xA0 (lines 5 and 7); the best is line 5; the highest in-service line is 6, of lower priority than 5, so line 5 is delivered with vector 32 + 5 = 37, nested inside line 6's handler. (c) Line 7 waits for the EOIs of lines 5 and 6 (it is below both); line 2 waits for its unmask. (d) 0x3A = 0011 1010: lines 1, 3, 4 and 5 masked (line 2 is now unmasked and, being above 5 and 6, would be delivered next). Marking: (a) 1, (b) 2, (c) 2, (d) 1. Source: exam_checks.out M9.
  10. M10 (4). (a) One delivery: the pending register has one bit per line, so requests that arrive while the bit is already set merge (F1-43's forensic run: the UART raised its line 10 times and was served once). (b) Lines 0, 1 and 2 are still served; lines 3, 4, 5, 6 and 7 are blocked for ever, because line 3 stays in service and blocks itself and every lower-priority line. Marking: 2 and 2.
  11. M11 (6). (a) 6 words: PIO 6 ticks, DMA 8, saving −2 ticks (−33.3 %): DMA costs 2 more. 8 words: 8 and 8, saving 0 (0.0 %). 1,024 words: 1,024 and 8, saving 1,016 ticks (99.2 %). (b) From 9 words on. (c) First line 24 / 16 = 1, last (24 + 40 − 1) / 16 = 3: lines 1, 2, 3. Line 1 covers bytes 16–31 and also holds bytes 16–23 of other data; lines 2 (32–47) and 3 (48–63) are the buffer's only. Invalidating line 1 throws away the CPU's recent writes to bytes 16–23, and cleaning it can overwrite the device's data: DMA buffers are aligned and sized to cache lines. Marking: (a) 2, (b) 1, (c) 3. Source: exam_checks.out M11 and Addendum.
  12. M12 (6, Evaluate). Three rules are broken. (1) Receive: the header is read before the invalidate; the read re-caches line 0, and on the next packet the CPU sees the previous packet's first line, a stale header (F1-44's forensic lab). Fix: invalidate (sync for the CPU) the whole buffer first, then read anything. (2) Transmit: the doorbell is written right after the descriptor with no write barrier; the CPU or interconnect may reorder them and the device can read a half-written descriptor ("works once, then garbage descriptors"). Fix: descriptor, write barrier (the Linux guide's wmb()), doorbell. (3) Transmit: no cache clean of the data buffer before the doorbell on a non-coherent system: the device reads memory that does not yet hold the CPU's data (F1-44 run R2: 32 zero bytes). Fix: clean (map for the device) before the doorbell. An IOMMU would confine the device to its mapped buffers (a DMA to a freed or wrong address faults instead of corrupting memory) but fixes none of the three bugs: stale lines and reordering happen inside the mapping. Marking: (1) 2, (2) 1, (3) 1, IOMMU 2.

Part C — forensic key: "The FIFO that was not enough" (18 points)

How the evidence was made. uart_fifo_forensic.cpp runs F1-42's uart_model.h unchanged with the receiver depth set to 4 (kFifoDepth) and a new workload: a main-loop pass takes 4 ticks, but every 16th pass takes 60 (board2_work: display refresh plus log flush). The bench part is the same as F1-42's: 65,536 bytes, one per 10 ticks, order-sensitive checksum. Nothing was edited by hand.

  1. Observation (4). BENCH 1: 54,614 of 65,536 bytes received, checksum 0xDB8341F4 instead of 0x52668772: FAIL; 10,922 bytes lost. BENCH 2: the overrun flag was seen 10,922 times, equal to the loss; first overruns at t = 110, 120, 230, 240, 350, 360 (in pairs, 120 ticks apart); FIFO high-water mark 4 bytes: the FIFO was full, so it works. BENCH 3: passes of 4 ticks (81,923) and of 60 ticks (5,461); 87,384 passes in all, so one pass in 16 is long; 5,461 long passes × 2 = 10,922, exactly the loss. Marking: loss and checksum 1; OE count equals loss 1; pass lengths and frequency 1; 5,461 × 2 = 10,922 cross-check 1.
  2. Hypotheses (3). (1) Wrong baud rate: ruled out, it corrupts bytes rather than dropping whole ones while the rest stay in order, and it would not produce overrun flags in pairs at fixed times. (2) Sender fault: ruled out, an overrun is the receiver's report that a byte arrived and could not be stored. (3) The 4-byte FIFO is still too small for the longest gap between polls: confirmed below. Also acceptable: "the FIFO is broken": ruled out by the high-water mark of 4. Marking: at least two hypotheses with the evidence that decides each, 3.
  3. Conclusion (5). BENCH 4: polls at 32, 36, …, 60, then nothing until 120. Bytes arrive at 70, 80, 90, 100, 110 and 120 (the byte at 60 was taken by the poll at 60). The FIFO keeps 70, 80, 90 and 100; the bytes at 110 and 120 find it full and are lost (overruns at t = 110 and 120 in BENCH 2; in the model the arrival at 120 is handled before the poll at 120). So 6 arrivals per 60-tick gap, 4 slots, 2 lost per long pass. A FIFO of depth d at one byte per 10 ticks tolerates d × 10 ticks between polls: 40 ticks for d = 4, less than the 60-tick pass. The FIFO moved the threshold from 10 to 40 ticks; it did not remove it. Marking: arrivals and polls listed 2; kept and lost bytes 1; 40-tick threshold against 60 ticks 2. Source: uart_fifo_forensic.out; exam_checks.out F22 and Addendum.
  4. Fix and verification (4). Enable the receive interrupt and move bytes into a ring buffer in the handler (F1-42 Listing 2). Size: 60 / 10 = 6 bytes per long pass, plus 1 at the boundary = 7, so 8 slots or more. Verification, run under the same workload (uart_fifo_fixed.out, shown below): interrupt + ring of 8 slots: 65,536 echoed, high-water mark 6, checksum 0x52668772, PASS; ring of 4 slots: FAIL with 10,922 bytes dropped in the ring (too small); even the old one-byte receiver with a 64-slot ring passes. The alternative "8-byte FIFO and keep polling" passes this bench (polling with a FIFO of 6, 7 or 8 bytes: PASS, high-water mark 6), but its margin is 2 bytes: any pass longer than 8 × 10 = 80 ticks loses bytes again, and the next feature that lengthens a pass brings the failure back; the interrupt decouples arrival from the main loop's longest pass. Marking: fix 1, size 1, verification with numbers 1, evaluation of the deeper FIFO 1.
  5. Prevention (2). Keep the curriculum C2 test ("Pasting 64 KiB through the serial port loses no bytes (checksum).") in the release checklist, run with the display and the logging enabled; expose the overrun and ring-drop counters in the firmware's status output; measure the main loop's longest pass and alarm when it approaches depth × byte interval. Marking: test 1, monitoring 1.

Practical (P) — reference solution and marking

The capture was generated by make_capture.cpp on the course's I2C model (i2c_exam_model.h): one sensor at 7-bit address 0x5A with registers 0x6B, 0x00, 0x2C, 0x8F; the driver under test probes 7-bit address 0x1E (nothing there), writes 0x80 into register 0x01, and reads two bytes from register 0x02. Explanation (20 points) and habits (10 points)

Model answer. Transaction 1 is a probe of 7-bit address 0x1E: the address byte 0x3C was not acknowledged, so no device answers at 0x1E, and the controller ends with STOP. Transaction 2 writes register 0x01 of the sensor at 0x5A with the value 0x80: address 0x5A write ACK, register pointer 0x01 ACK, data 0x80 ACK, STOP. Transaction 3 reads two bytes starting at register 0x02: address 0x5A write, pointer 0x02, repeated START, address 0x5A read (0xB5), then the sensor sends 0x2C (ACKed by the controller) and 0x8F (NACKed). The final NACK is the controller saying "that was the last byte" before the STOP, not an error (F1-47 run R1). "B4h/B5h" is the 8-bit form (address and R/W bit together): the 7-bit address is 0xB4 >> 1 = 0x5A. A driver configured with 0xB4 as a 7-bit address would shift it: 0xB4 << 1 = 0x168, so the byte on the wire is 0x68 = 7-bit 0x34, write, answered by NACK, as in F1-47's forensic lab (exam_checks.out Practical and Addendum). The capture is 349 samples = 87.25 bit times at four samples per bit; it has three STARTs plus one repeated START, three STOPs and 9 bytes (81 clocks). Marking as in the paper's table; the habits points need "7-bit" or "8-bit" next to every address and "exercise value" or "model capture" next to the values.
