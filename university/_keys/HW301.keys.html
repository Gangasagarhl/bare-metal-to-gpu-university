Final — model answers and marking points

Part A (41 points)

  1. F1 (2). Latency: the time from the start of one operation to its result. Throughput: how many operations complete per unit of time. Little's law L = λ × W: L the average number of operations in progress, λ the completion (arrival) rate, W the average time each spends in the system (F1-55). Marking: 1 for the two definitions, 1 for the law with its three quantities named.
  2. F2 (4). (a) Each must wait for the one before: 200 × 8 = 1,600 cycles. (b) One issued per cycle: 200 cycles of issue, plus the last one's remaining latency, about 207 cycles. (c) λ = 1/3 access per cycle, W = 300 cycles: L = 100 accesses in flight. (Recomputed: exam_checks.out lines "F2".) Marking: 1, 2 (1 for 200, 1 for saying what the last operation adds), 1.
  3. F3 (4). (a) Every FFMA writes R5 and reads R5 (and R4, the constant): each needs the result of the one before, a true (read-after-write) dependence; the FFMAs form one chain. (b) The launch has one warp in the whole GPU, so the scheduler has no other warp to switch to while it waits (F1-60), and inside the warp the next FFMA cannot issue before the previous result exists (F1-55's chain). Unrolling sixteen FFMAs per trip only removes loop overhead (one IADD3 and one branch per sixteen steps); it does not make the steps independent, so the chain's latency still sets the time. (c) One block of one thread: one SM holds one warp with one active lane out of 32; every other lane and every other SM is idle for the whole kernel. Marking: 1, 2, 1. Full marks need "dependence" and "no other warp" both in (b).
  4. F4 (3). (a) False: a block is assigned whole to one SM and never migrates. (b) False: no order between blocks is promised. (c) True: blocks are the unit of distribution, so 6 blocks can occupy at most 6 SMs. Marking: 1 each, the reason is required.
  5. F5 (3). Slots = 60 × 3 = 180. (a) 700 blocks: 4 waves; last wave 160 of 180 slots; share used 700 ÷ 720 = 97.2 %. (b) 150 blocks: 1 wave; 83.3 %; 30 slots idle. (exam_checks.out lines "F5".) Marking: 2 for (a), 1 for (b).
  6. F6 (3). (a) s8, s0, s1 and the pair s[0:1] are scalar registers, one value per wavefront; v0 is a vector register, one value per lane; vcc is a 64-bit scalar register pair that holds one bit per lane (the comparison result). The prefix of the instruction and the register name tell: s_/s scalar, v_/v vector (F1-56). (b) s8 = blockIdx.x × blockDim.x (workgroup id times workgroup size, one value for the whole wavefront), then v0 = s8 + threadIdx.x: the global index i of each lane. (c) s_and_saveexec_b64 sets EXEC to the lanes with i < n; if none is left, s_cbranch_execz jumps over the body to .LBB0_2 (the end). It is cheap because one scalar test and branch decide for the whole wavefront: no vector instruction of the skipped path is issued (F1-57). Marking: 1 each.
  7. F7 (4). (a) 17 instructions issued, 544 of 544 lane-slots useful: 100.0 %. (b) Both paths run: 20 issued; useful = 30 × 12 + 2 × 3 + 32 × 5 = 526 of 640: 82.2 %. (c) 20 issued; useful = 62 × 12 + 2 × 3 + 64 × 5 = 1,070 of 1,280: 83.6 %. (exam_checks.out lines "F7".) Marking: 1, 1.5, 1.5; the formula must be shown.
  8. F8 (4). (a) Both lines are wrong on the three wave64 settings (gfx90a, gfx942, gfx1100 with -mwavefrontsize64) and correct on gfx1030 and gfx1100 (wave32). The ballot returns a 64-bit mask on wave64; storing it in a 32-bit unsigned drops the votes of lanes 32–63, so n counts at most the lower half. The loop with offsets 16, 8, 4, 2, 1 moves a value at most 31 lanes, so lane 0 sums only lanes 0–31: about half the total when all lanes contribute. (b) unsigned long long votes = __ballot(v > 10); int n = __popcll(votes); and for (int offset = warpSize / 2; offset > 0; offset /= 2). The installed HIP 5.7 header amd_detail/amd_warp_functions.h defines warpSize = __AMDGCN_WAVEFRONT_SIZE, the macro shown in the evidence, so the loop bound follows the target setting. Marking: 2 for (a) (targets 1, what is lost 1), 2 for (b) (two correct lines 1, the header definition 1). A rewrite that hard-codes 64 scores 0 for that line.
  9. F9 (3). From compute capability 7.0 "the GPU maintains execution state per thread, including a program counter and call stack" (CUDA Programming Guide 3.2.2.1.1, as F1-57 quotes it): the lanes of a divergent warp may interleave, so the hardware can no longer assume that all lanes are together at a warp-level operation. The intrinsic therefore names the lanes that take part (the mask) and synchronises them (_sync). The rule F1-57 states: every lane named in the mask must execute the intrinsic, so inside divergent code the mask must contain only the lanes that reach that call. Honest status: F1-57 lists this rule as "still not checked" (the warp vote functions page could not be opened in its verification pass); the per-thread program counter is confirmed. Marking: 1 for the cc 7.0 change, 1 for the rule, 1 for stating its unverified status. An answer that presents the rule as confirmed loses that last point.
  10. F10 (4). (a) 192 threads = 6 warps per block. Registers 32 × 192 = 6,144 per block: 16,384 ÷ 6,144 = 2 blocks; shared memory 32 KiB ÷ 8 KiB = 4; warps 16 ÷ 6 = 2; block limit 4. Resident 2 blocks = 12 warps, occupancy 75.0 %, limited by registers and warps. (b) 128 threads = 4 warps: registers 16,384 ÷ 4,096 = 4, shared 4, warps 4, blocks 4: 4 blocks, 16 warps, 100.0 % (all four limits equal). (c) Occupancy is not speed: check with a measurement (or at least the latency-hiding argument of F1-60, the shared-memory traffic and the waves of the real grid) before calling it faster. (exam_checks.out lines "F10".) Marking: 2, 1, 1.
  11. F11 (4). (a) The tile is 32 × 33 floats (a 32 × 32 tile padded by one word per row against bank conflicts): 32 × 33 × 4 = 4,224 bytes (4,096 without the padding). The occupancy inputs are "Used 12 registers" (per thread) and "4224 bytes smem" (per block), with the threads per block from the launch. (b) Build A uses 40 registers with no stack frame and no spills; build B, capped at 16, reports 24 registers, a 352-byte stack frame, 416 bytes of spill stores and 572 bytes of spill loads, and 245 LDL/STL instructions instead of 0. Spilled values live in local memory: private to each thread but physically in device memory (through the caches). Every spill store and reload is extra memory traffic, so traffic rose although inputs and outputs did not change. (c) Report the number exactly as printed, say that it exceeds the cap, and say that the output does not explain it (F1-58 leaves the reason in a "Not verified" box: a minimum allocation or ABI registers are guesses). Do not invent a cause. Marking: 1.5, 1.5, 1.
  12. F12 (3). Pitch 32: degree 32. Pitch 33: degree 1. Pitch 48: degree 16, because bank = (48 × t) mod 32 = (16 × t) mod 32, which is only bank 0 (even t) or bank 16 (odd t): 16 threads in each of two banks. Choose 33 (padding by one word): consecutive rows then start in consecutive banks and a column read hits 32 different banks. (exam_checks.out lines "F12".) Marking: 1 for the three degrees, 1 for the pitch-48 arithmetic, 1 for the choice and reason.

Part C — forensic key: "The bigger GPU that changed nothing" (18 points)

How the evidence was produced. The scenario is invented (TG-1-class GPUs). The Lab Engineer fed its numbers to the course's own models: forensic_occupancy.in to F1-58's occupancy.cpp, forensic_waves.in to F1-56's waves.cpp, forensic_copy.in to F1-62's copy_model.cpp (run.sh in labs/HW301-P/). The "fault" is built into the job: a grid of 8 blocks, sized for GPU-A's 4 SMs × 2 resident blocks, and two serial 512 MB copies from pageable memory around an 8 ms kernel.

  1. C1 Observation (3). Occupancy: 24 × 256 = 6,144 registers per block, 16,384 ÷ 6,144 = 2 blocks; 16 ÷ 8 = 2 by warps: 2 blocks per SM, 100.0 %, limited by registers and warps. Waves: GPU-A 8 slots, 8 blocks, 1 wave, 100.0 %; GPU-B 32 slots, 8 blocks, 1 wave, 25.0 % (8 of 32 slots). Copy model: 72.02 ms on both, GPU busy 8.00 ms = 11.1 %. Composition: each copy is 10 µs + 512 × 106 B ÷ 16 GB/s = 32.01 ms; 32.01 + 8.00 + 32.01 = 72.02 ms; the copies are 64.02 ms (89 %). Marking: 1 per output.
  2. C2 Hypotheses (3). "GPU-B defective or ignored": tested by the waves output and the profile; the kernel did run (8 ms in the kernel lane) and 8 blocks only fill 8 slots on either GPU, so nothing points to a defect. "Grid too small for GPU-B": waves output, 25 % of slots used. "Copies dominate": copy model, 64.02 of 72.02 ms. "Pageable memory slows the copies": the evidence does not test it; the malloc buffer says pageable, and repeating the copy with cudaMallocHost would measure the difference. Marking: 1 per hypothesis with its test, up to 3; at least two before the conclusion.
  3. C3 Root cause (5). (a) Blocks are the unit of distribution: each block runs whole on one SM and the same block does the same work at the same speed on either GPU. The 8 blocks fill all 8 slots of GPU-A but only 8 of GPU-B's 32; the other slots get no work, so the single wave takes the same 8 ms. Occupancy is per SM and says nothing about how many SMs get work. (b) A kernel four times faster (2 ms) gives 66.02 ms (forensic_fix.out, first case): 8 % less. The job is limited by the host link (two serial 32.01 ms copies), and a bigger GPU changes neither the link nor the copies. Marking: 3 for (a) (slots versus blocks 2, occupancy is per SM 1), 2 for (b).
  4. C4 Fixes (4). Model estimates (forensic_fix.out, forensic_fix_waves.out), each on GPU-B with the grid fix included:
    1. Keep the data resident if consecutive jobs work on the same data: copy in once, run 10 kernels, copy out once: 84.02 ms for 10 jobs, 8.40 ms per job instead of 72.02. This is a job-structure change, with no change in the kernel; it only applies if the data really can stay on the GPU between jobs.
    2. Overlap: 16 chunks of 32 MB in streams with asynchronous copies: 34.29 ms. This needs page-locked (pinned) host memory and two copy engines (asyncEngineCount 2); the copies are still the floor (about 32 ms in each direction, overlapped).
    3. Fill GPU-B: launch at least 32 blocks (one full wave, 100 %) or 128 (4 waves, 100 %), with each block doing a quarter (or a sixteenth) of the work: kernel about 2 ms if the work divides evenly (an assumption), job 66.02 ms. This changes only the launch line if the kernel indexes by global thread id or uses a grid-stride loop. Derive the grid from multiProcessorCount.
    Order for this job: resident (where allowed) > overlap > grid. Pinned memory may also raise β, but the evidence gives no number for it, so it is not estimated. Marking: three fixes with estimates 3, correct order and the pinned/copy-engine attribution 1.
  5. C5 Prevention (3). (1) Data movement: before moving or re-running a job, compute 2 × (α + bytes ÷ β) and compare it with the kernel time; if the copies are longer, a bigger GPU will not help. Check asyncEngineCount before planning overlap, and use measured α and β. (2) Grid size: require grid blocks ≥ multiProcessorCount × resident blocks per SM (from the occupancy calculation with regsPerMultiprocessor, maxBlocksPerMultiProcessor and so on), better several waves; compute the grid from these properties at run time, never as a constant. Marking: 1.5 each; a check that cannot be computed before the run ("profile it") scores half.

Wrong answers and why. "GPU-B is defective": the kernel ran and took exactly what 8 blocks need. "The driver ignores GPU-B": same evidence. "Occupancy is too low": 100 % per SM on both. "The kernel is slow": 8 of 72.02 ms; even a four-times-faster kernel saves 8 %. "Buy a faster GPU again": the link sets the floor. Rubric mapping (guide 11.2): C1 observation 3 (17 %), C2 hypotheses 3 (17 %), C3 evidence-based conclusion 5 (28 %), C4 fix and verification 4 (22 %), C5 prevention and communication 3 (17 %).

  • Limiter and change per kernel (8). stencil: registers and warps, 100 %, 96.9 % of slot-rounds; the kernel is memory-bound in the model (166.667 µs minimum), and the 12.808 ms host copy is about 77 times longer: keep the data on the GPU or overlap the copy. histogram: shared memory (8 blocks, 66.7 %); with 4,096 bytes per block the reference gives 12 blocks, 100.0 %, limited by warps, still 67.9 % of slot-rounds in 2 waves (kernel_map_variants.out), so more occupancy does not fix the small grid. tiny: the block limit (16 blocks of 2 warps, 66.7 %).
  • bigblock (4). 72 × 1,024 = 73,728 registers per block exceed the SM's 65,536, so not even one block fits ("cannot launch"). Two fixes from kernel_map_variants.out: cap registers at 64 (exactly 65,536 per block: 1 block, 66.7 %), at the risk of spills to local memory (F1-58's forensic lab); or smaller blocks: 512 threads give 1 block, 33.3 %; 256 threads give 3 blocks, 50.0 %, at the risk of breaking code that assumes the block size (shared tiles, barriers) and of more per-block overhead.
  • tiny (2). 64 blocks fill 64 of 384 slots: one wave at 16.7 %; most of the 24 SMs get no work. Smaller blocks (32 threads: 128 blocks) only reach 33.3 % (kernel_map_variants.out). The real fix is more work per launch (batch it with other work) or leaving it on the CPU.
  • Model limits (2), any three: memory-access patterns, coalescing and caches; bank conflicts; latency hiding and the dependence structure inside the kernel (F1-60); register and shared-memory allocation granularity and reserved shared memory; launch overhead; clocks and power limits; how the block scheduler really distributes blocks; copy and kernel overlap.
