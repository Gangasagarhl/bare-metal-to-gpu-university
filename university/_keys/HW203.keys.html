Midterm — model answers and marking points

  1. M1. (a) Latency: the time from issuing a memory request until its data can be used, in ns (or clock cycles). Bandwidth: the rate of data transfer once requests flow, in bytes per second; this course's GB/s is 109 bytes per second. (b) Compulsory (cold): the first access to a line; capacity: the working set is larger than the cache, so lines are evicted before reuse; conflict: more lines map to one set than it has ways, although the cache as a whole could hold them. Marking: 1 per definition with unit (2); the three kinds with causes (2; 1 for names only).
  2. M2. (a) 16 GB/s = 16 bytes per ns; 16 × 120 = 1,920 bytes in flight. (b) 1,920 ÷ 64 = 30.0 blocks. (c) 64 bytes ÷ 120 ns = 0.533 GB/s. (d) Pointer chasing (a linked list or tree walk): each load's address comes from the previous load, so only one request is outstanding and every step pays the full latency. Marking: 2, 1, 1, 2 (exam_checks.out, line "M2").
  3. M3. (a) Plateau of about 1.9 ns from 4 to 32 KiB; step between 32 and 64 KiB, where the working set passes the reported 48 KiB L1d; second plateau of 5.4–6.2 ns from 64 to 512 KiB (7.93 ns at 1024 KiB); step between 1 MiB and 2 MiB (38.19 ns), where the chain plus other data no longer fits the reported 2 MiB L2; then a steady climb at every doubling up to 263.64 ns at 256 MiB, with no plateau below the reported 260 MiB L3. F1-32's unverified box lists possible reasons (an L3 shared with other virtual machines, TLB misses growing with the working set, a reported size that describes the host); none was verified. (b) 263.64 ÷ 1.92 = 137: a load at the largest working set (DRAM plus translation cost) took 137 times as long as one served by L1, on this machine in this run. 38.19 ÷ 7.93 = 4.8: the size of the step when the working set passes the L2 size. (c) The visiting order is shuffled with a fixed seed, so hardware prefetchers cannot predict the next block; each node fills its own 64-byte block, so every load needs a different line; and the loads are dependent (p = nodes[p].next), so they cannot overlap. Marking: 3 (one per correct step/plateau statement, including the missing L3 plateau), 3 (1.5 per ratio with meaning), 2.

Part A

  1. F1. Bytes in flight = bandwidth × latency (in a steady system, items inside = arrival rate × time inside). Memory-level parallelism: the number of memory accesses outstanding at the same time; it needs independent addresses. Marking: 1 + 1.

(c) S × B = 64 × 64 = 4,096 bytes: addresses that differ by a multiple of 4,096 have the same bits 6–11, the index. Marking: 2, 2, 1 (exam_checks.out, lines "F3").
  4. F4. All k lines fall into set 0. k = 12: 12 misses (first pass) and 24 hits; k = 13: 0 hits, 39 misses; k = 16: 0 hits, 48 misses (exam_checks.out; k = 16 is also F1-33's sameset.out). (b) i × 0x8000: channel 0 for all four; banks 0, 2, 0, 2; rows 0, 0, 1, 1; column 0: one channel and two of the four banks do all the work (bit 15 changes, bits 6 and 14 never do). (c) i × 0x8040: channels 0, 1, 0, 1; banks 0, 2, 0, 2; rows 0, 0, 1, 1; columns 0, 0, 1, 1: the extra 64 bytes flip bit 6 on every other access, so both channels share the stream (the padding fix of F1-39's forensic lab). Marking: 2, 1, 1 (exam_checks.out, lines "DRAM model").
  12. F19. (a) 263.6 ns × 7.53 bytes/ns = 1,985 bytes = 31.0 blocks of 64 bytes in flight for one thread. (b) 23.17 ÷ 7.53 = 3.08. One core can keep only a limited number of misses outstanding (its non-blocking caches track a fixed number), which by Little's law caps its bandwidth; four cores keep about four times as many misses in flight, and the memory system had spare capacity. The limit's value for this CPU was not verified (F1-32 unverified box). Marking: 2, 2 (exam_checks.out, lines "F19").

Part C — forensic answer: "The energy sum that read eight times more"

Root cause. The array-of-structures layout makes the mass loop read one 8-byte field from every 64-byte struct Particle: each mass read brings a whole line of which one eighth is used, so the loop moves eight times as many lines as the mass array did; once the structs no longer fit a cache level, every pass pays for all of them again. The extra lines cost little while the data stays in L1 or L2 and a great deal when it comes from DRAM, which is why the tests saw almost nothing and the production run slowed down.

Evidence that proves it. E1 (university/labs/HW203-P/forensic_layout.out), L1d geometry: 512 particles, AoS 512 misses in pass 1 and 0 in pass 2, SoA 64 and 0; 4,096 particles, AoS 4,096 and 4,096, SoA 512 and 0. Pass-1 ratio AoS ÷ SoA = 4,096 ÷ 512 = 8 (and 512 ÷ 64 = 8): one miss per struct against one miss per 8 masses. Pass 2: 4,096 structs are 256 KiB, 5.33 times the 48 KiB L1d of E2, so nothing survives until the second pass; the SoA masses are 32 KiB and fit, as do the 512 structs (32 KiB). The fully associative rows of E1 give exactly the same counts, so these are capacity misses, not conflict misses. E3 (F1-34's stride.out): stride 1 ÷ stride 8 is 16.71 ÷ 15.68 = 1.07 in the 16 KiB row (data in L1, the nearest row to the unit test's 32 KiB), 18.47 ÷ 18.66 = 0.99 in the 256 KiB row (the medium test's size: no measurable penalty while the data sits in L2), and 6.26 ÷ 1.42 = 4.4 in the 262144 KiB row, the size of 4,194,304 structs (256 MiB): from DRAM, reading one double per line delivered 4.4 times fewer requested bytes per second. (exam_checks.out, lines "F20".)

Wrong answers and why. "Conflict misses from the power-of-two struct size": ruled out, the fully associative cache of the same capacity gives identical counts, and 64-byte strides walk through consecutive sets. "TLB pressure is the cause": the AoS data spans eight times as many pages (256 MiB against 32 MiB in production), so it may contribute, but the course model has no TLB and the evidence cannot apportion it; it is a secondary hypothesis, not the proven cause. "Eight times more misses means eight times slower": not supported, the measured stride table shows almost no penalty in L1 and L2 and 4.4 in DRAM; model counts are not times. "The 4,096-particle test proves the layout harmless": it only shows that a 256 KiB working set hides the cost on this machine. Also wrong: treating E1's counts as hardware counter readings (they come from the course model) or E3's GB/s as measurements of the particle program (they were measured on F1-34's stride benchmark, on the build container).

Fix and verification. Keep the masses (the hot field of this loop) in their own array: structure of arrays for fields that are read alone, or a hot/cold split (a small struct of the fields used together in the hot loops, the rest elsewhere). Trade-off: AoS is the better layout when a loop uses most fields of each particle together (all eight doubles of a line are then useful). Verify without counters: rerun the model trace (pass-1 misses back to one per 8 masses, pass 2 at 0 while the masses fit the reported L1d), and time the diagnostics step at the production size, median of several runs, machine named, against the old layout.

Prevention. A continuous-integration test that runs the diagnostics loop's access pattern through the course model for the production layout and fails when the misses per mass read exceed 1/8 (one line per eight masses), plus a timing benchmark at a DRAM-sized particle count that fails when the step exceeds the SoA baseline by a set factor; a code-review note that the unit test's 512 particles fit in L1 and cannot show layout regressions.

How the evidence was made. forensic_layout.cpp traces 2 passes over 512 and 4,096 particles through cache.hpp (F1-33's model) with a 64-byte stride and offset 48 (AoS) or an 8-byte stride (SoA), in the reported L1d geometry and in a fully associative cache of the same capacity; run by run_lab.sh with the course sanitizer flags, exit code 0. E2 and E3 are F1-33's and F1-34's recorded runs. The "fault" is the layout itself; no timing of the particle program exists, and none is claimed.

Marking (20). F20a (3): the eight counts and the ratio 8. F20b (3): 64-byte struct, mass at offset 48, 8 useful bytes per 64-byte line against 64. F20c (3): 256 KiB against 48 KiB (5.33); 32 KiB fits; the fully associative rows rule out conflicts: capacity. F20d (3): 1.07, 0.99 and 4.4, with the conclusion that the penalty appears only for DRAM-sized data. F20e (4, Evaluate): at least three hypotheses with evidence for and against, and the limits (model counts, a different program's measurement, no counters). F20f (4: 2 Evaluate, 2 Create): the fix with its trade-off and a verification (2), and a concrete automatic test (2). The forensic rubric of guide 11.2 applies to the write-up as a whole.

Prediction sheet (30 points)

  • Rows and columns (15). Sum by rows = number of lines of the matrix (n² × 8 ÷ 64): 8, 8, 32, 512, 32,768. Sum by columns: cases 1 and 2: 8 (the whole 512-byte matrix is 8 lines in 8 different sets); case 3: 256 (a row is 2 lines; a column's 16 lines fall into 4 sets, 4 lines per 2-way set); case 4: 4,096 (a row is 8 lines = sets × line, so a column's 64 lines share one set); case 5: 262,144 (a row is 4,096 bytes = 64 sets × 64 bytes, so a column's 512 lines share one 12-way set). 1.5 per case and order; reasoning required for full marks.
  • Case 1 naive transpose exact (5). 16: a occupies 8 lines in sets 0–7 and b the next 8 lines in sets 0–7; 16 lines in 8 sets × 2 ways all fit, so only compulsory misses remain.
  • Blocking (7). Case 3: blocked misses less (reference 288 → 108, a factor of 2.67). Case 4: no gain (4,608 both): with tile 8, the 8 lines of a tile column of b (and the 8 lines of a tile of a at fixed jj) all map to one set, 8 lines in 2 ways; a candidate who says "tile 8 needs 16 lines in one or two sets, so it thrashes" gets full marks.   • Case 2 (3). More than 16 (reference 37), because a's line k and b's line k map to the same direct-mapped set and evict each other; blocking with tile 4 does not help (reference 49, worse): blocking reduces capacity misses, not conflicts between two arrays in a 1-way cache.
