Quizzes (Q)

Each chapter's "Check yourself" is its quiz: seven or eight questions per chapter, each with an "explain in your own words", an "apply to a new case" and, as the L2 rule of guide 11.3 requires, a "predict, then run" question whose answer was checked by a real run (the chapter's NOTES.md lists these check runs). Learners answer in writing after reading the chapter and before the lab, then mark themselves against the chapter's answers; a mentor checks the "in your own words" and "predict, then run" answers against the generic rubric of guide 11.4. The six required quizzes are worth 1⅔ % each (10 % in all).

  • Quiz 1 — F1-16 Check yourself (feedback and memory; SR latch cases; latch versus flip-flop on a timing diagram; output reg is not always a flip-flop).
  • Quiz 2 — F1-17 Check yourself (wrap-around; reset before load; synchronous versus ripple counting; shift register trace; the wrap output; a decade counter).
  • Quiz 3 — F1-18 Check yourself (period and frequency; the timing budget and slack; setup versus hold; a clock enable every 1 µs; which periods work for the slow-adder counter).
  • Quiz 4 — F1-19 Check yourself (the three parts of an FSM; encodings; Moore or Mealy; tracing the 101 detector; overlapping patterns; a two-coin machine).
  • Quiz 5 — F1-20 Check yourself (SRAM versus DRAM; destructive reads; address bits and words; drive strengths; refresh gaps).
  • Quiz 6 — F1-21 Check yourself (which reg becomes what; blocking and non-blocking; testbench-only constructs; what a lint warning did and did not say).
  • Quiz 7 (optional chapter) — F1-22 Check yourself (LUT configurations; FPGA resources; reading a LUT netlist; an 8-bit counter's resource count).

// Forensic evidence for the HW201 final: Mira's detector for the bit pattern 0, 1, 0.
// Specification: found = 1 in the cycle after the last three sampled bits were 0, 1, 0;
// overlapping occurrences count (01010 contains the pattern twice).
`timescale 1ns/1ns
module seq010_bug (
    input  wire clk,
    input  wire reset,
    input  wire in,
    output wire found
);
    localparam S0   = 2'd0,    // nothing useful seen yet
               SA   = 2'd1,    // last bit was 0
               S01  = 2'd2,    // last two bits were 0, 1
               S010 = 2'd3;    // last three bits were 0, 1, 0

    reg [1:0] state;
    reg [1:0] next;

    always @(*) begin
        case (state)
            S0:      next = in ? S0  : SA;
            SA:      next = in ? S01 : SA;
            S01:     next = in ? S0  : S010;
            default: next = S0;                 // S010: pattern reported, start again
        endcase
    end

    always @(posedge clk) begin
        if (reset)
            state <= S0;
        else
            state <= next;
    end

    assign found = (state == S010);
endmodule

The task: the dishwasher controller

The restaurant's dishwasher has a controller on one clock; all inputs are sampled at the rising edge. Inputs: reset, start, door_open. Outputs (lamps on the panel): wash, rinse, dry, done, plus a 3-bit state output for your own debugging (the testbench prints it but does not check it). All phase lengths are exercise values in clock cycles.

  1. After reset the machine is IDLE: all lamps off.
  2. In IDLE, when start = 1 and door_open = 0 are sampled, a programme begins: WASH for exactly 6 cycles (wash = 1), then RINSE for exactly 4 cycles (rinse = 1), then DRY for exactly 3 cycles (dry = 1), then DONE (done = 1).
  3. DONE lasts until door_open = 1 is sampled; the machine then returns to IDLE. start is ignored in DONE.
  4. If door_open = 1 is sampled during WASH, RINSE or DRY, the programme pauses: all lamps are off while the door is open. When door_open = 0 is sampled again, the interrupted phase continues, and the cycles already spent in it still count: every programme, interrupted or not, has exactly 6 wash, 4 rinse and 3 dry lamp cycles.
  5. In IDLE with door_open = 1, start is ignored.
  6. At most one lamp is on at any time. The lamps depend on the state only (Moore machine).

Timing convention (the one every testbench of the course uses): inputs change half a period before the edge; the outputs that follow from the inputs sampled at edge k are observed one time unit after that edge and belong to "cycle k". So when start is sampled at edge 3, the wash lamp is on in cycles 3 to 8.

What you hand in

  1. Design on paper (about 35 minutes): inputs and outputs with their timing; the states, each named by what it remembers; the state table or diagram with an arrow for every input in every state; the encoding and the widths of the state register and of any timer; and a sentence on how you return from the pause to the right phase (one PAUSE state plus a "resume" register, or one pause state per phase: both are acceptable).
  2. Verilog (about 50 minutes): complete dishwasher.v in the three blocks of the course (next-state logic with a default, state register with reset, output logic), keeping the module name and ports. Build with iverilog -g2005 -Wall -o dishwasher.vvp dishwasher_tb.v dishwasher.v && vvp -n dishwasher.vvp until the testbench prints RESULT: PASS with no compiler warning.
  3. Tools and reading (about 20 minutes): run verilator --lint-only -Wall dishwasher.v and fix every warning; run yosys -q -p 'read_verilog dishwasher.v; synth -top dishwasher; tee -q -o /dev/stdout stat' and write three sentences that account for every flip-flop in the report from your declarations.
  4. Log (throughout, about 15 minutes in all): a short written record of what failed, what the testbench said and what you changed, plus one extra test scenario you would add and why.

Course project — a memory unit and program counter for the HW202 CPU

Weight 20 %. Brief per guide 11.5. The project is built in the steps that the chapters' mini-projects already define and the owner approved (ruling B3 and the NOTES.md of HW201): the program counter in F1-17, the memory unit in F1-20, the review with relative jump in F1-21, and the resource budget in F1-22. Widths stay 8-bit addresses and 8-bit words; widening to HW202's 16-bit CPU is HW202's integration step (WIDTH parameter on the counter; the RAM's word width is the one change HW202 must make).

Goal

Deliver two tested, lint-clean, synthesised Verilog modules that HW202 can drop into its CPU: a program counter with reset, absolute jump, relative jump and increment, and a 256 × 8 memory unit with synchronous write and write enable; prove with a self-checking testbench that the counter can fetch consecutive words from the memory.

Requirements

  • Functional: pc_branch #(WIDTH = 8) with ports clk, reset, load, branch, inc, jump_to[WIDTH-1:0], offset[WIDTH-1:0], pc[WIDTH-1:0]; priority reset, then load (pc = jump_to), then branch (pc = pc + offset, offset in two's complement, so negative offsets jump backwards), then inc, else hold; all arithmetic wraps modulo 2WIDTH. ram256x8 with ports clk, we, addr[7:0], din[7:0], dout[7:0]: write at the rising edge when we = 1, read at any time (asynchronous read, as F1-20's Listing 3; a registered read is an accepted extension if the testbench is adjusted and the one-cycle delay is documented).
  • Tests: self-checking testbenches that print RESULT: PASS or FAIL: every address written with a pattern that differs for every address and read back; an edge with we = 0 that must not write; 16 consecutive fetches through the counter; a forward branch, a backward branch and a branch that wraps; all priority cases, including every control active at once.
  • Quality: verilator --lint-only -Wall clean for both modules; <= in clocked blocks only; no testbench constructs in the design files; a synthesis report for each module with a written reading of every cell group.

Constraints

Hardware: none; everything runs in Icarus Verilog, Verilator and Yosys (the course toolchain). Time: about eight hours in all, spread over F1-17 to F1-22. Language: Verilog as compiled with -g2005, the course flags. The design files may not include delays, initial blocks or $display.

Deliverables

  1. pc_branch.v and ram256x8.v, with a header comment stating the priority order and the widths.
  2. The testbenches and their unedited outputs, with the build commands and the tool versions as printed by the tools.
  3. The lint output (no warnings) and the synthesis reports of both modules, with a one-page reading: which cells are storage, which are logic, and why the counts are what they are (F1-21); for the memory, the report with the memory kept as one cell and the report with it mapped to flip-flops and LUTs, and what the difference means for an FPGA (F1-22 mini-project; done with Yosys alone, so it does not require the optional board chapter).
  4. A short design note (one page): the interface HW202 will see, what must change for 16-bit words, and one limitation you know of.
  5. A five-minute demo: run the combined fetch test and explain one line of its output and one line of a synthesis report.
