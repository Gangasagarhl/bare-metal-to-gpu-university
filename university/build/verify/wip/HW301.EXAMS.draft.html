Part C — forensic question: "The bigger GPU that changed nothing" (18 points)

Scenario. A team runs a nightly batch job on GPU-A, a TG-1-class machine (invented: 4 SMs; per SM 16,384 registers, 32 KiB shared memory, 16 resident warps, 4 resident blocks; host link 16 GB/s with 10 µs per copy). Course project — a one-page hardware passport of the lab GPU

Weight 20 % (guide 11.4). The course card's project: "a one-page hardware passport of the lab GPU, every number tagged to the vendor document or to a measurement". The brief follows guide 11.5; the passport format and the checker are those of F1-63 (Listing 1, passport_check.cpp).

Goal

Produce a one-page passport of the GPU in front of you (a reference-kit GPU, ruling D1, or any GPU you can run the device query on; if you have none, the compiler target gfx90a or sm_80 with the lab staff's recorded device query) in which every number is tagged DOC (document and section), TOOL (tool output and run record) or MEAS (measurement run record), or is left TBD, and which the course's checker accepts with 0 problems.

Requirements

  • Functional. At least the fields F1-63's "Course project" section names: product and variant; compiler target; warp or wavefront size; SM or CU count; per-SM limits (threads, warps, blocks, registers, shared memory or LDS); L2 size; memory type, interface width, data rate, peak bandwidth with its formula, and measured bandwidth; matrix-unit formats or "none"; host link and GPU-to-GPU links; a device-query excerpt. The checker's report is attached and shows 0 problems.
  • Quality. Peaks and measurements in separate fields with separate tags (AH-23); every peak carries the formula that reproduces it, or the note "formula unknown"; at least three fields are cross-checked against a second independent source (ISA or programming guide, header comment, compiler metadata, device query), with disagreements recorded rather than resolved by guessing; every DOC section can be opened by the marker; no number from memory, a forum or a slide.

Constraints

Hardware: the device query and the measured fields need the lab GPU (or the staff's recorded output; then the measured fields stay TBD and say so). Toolchain: the course's compilers for the TOOL rows (the build used CUDA 12.0 and HIP 5.7; the kit names CUDA 13.4 Update 1 and ROCm 7.14.0). Length: one page for the passport, plus an appendix with the checker report, the device-query record and the source list. Time: about ten hours spread over the course, following the milestones. Honesty: fields that cannot be sourced stay TBD; "untested on hardware" is written wherever it is true.

Deliverables

  1. The passport as a text file in the checker's format (field | value | tag), one page when printed.
  2. The checker's report on it (passport_check output, with the run record).
  3. The device-query record (your run of F1-56's Listing 1 or 2 and of the vendor tool, with date, machine, driver and toolkit versions), or the staff's recorded output with its provenance.
  4. A short design note (one page): the three cross-checks, the peak formulas, every disagreement found, and what would be needed to close each TBD.
  5. A five-minute walk-through for a non-specialist: what the GPU is, what its numbers mean for a kernel, and where each number came from.

Milestones

  1. After F1-56: the device query recorded; passport started with the TOOL rows (target, SM/CU count, warp size, per-SM limits) and the matching E1 table.

  3. After F1-59: memory type, width, data rate and peak bandwidth with its formula (DOC), and the first measured bandwidth (MEAS) or TBD.
  4. After F1-61: matrix-unit rows from compiler evidence (accepted or rejected instructions) and the document.
  5. After F1-62: host link and GPU-to-GPU link rows; fitted α and β (MEAS) or TBD.
  6. After F1-63: the complete passport with 0 checker problems, the design note and the walk-through.
