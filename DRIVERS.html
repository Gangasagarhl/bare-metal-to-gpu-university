Windows drivers: what loads at boot, what has firmware, and where drivers sit in the OS

A driver is the code that lets Windows use a piece of hardware, or adds a feature inside the kernel. This page shows where drivers sit, how they are loaded at boot, which ones have firmware behind them, and two real lists.

1 · Where drivers sit

Read from the bottom up. Each layer uses the one below it.

ApplicationsPrograms you run. They ask Windows for files, network and screen; they never touch hardware.
Sessions: smss, csrss, wininit, winlogon, LogonUIThe first user-mode processes. They build the session, start the service manager and show the logon screen.
Services (services.exe)Background programs started by the service manager; it also starts drivers marked "Auto".
Drivers (kernel mode)Code loaded into the kernel. It runs with full rights, so one slow or broken driver slows or stops the whole machine.
Boot-start loaded by winload before the kernel runs
System-start started by the kernel early
PnP on demand loaded when matching hardware is found
Filter drivers stacked on top of other drivers
HAL + kernel (ntoskrnl.exe)The kernel manages memory, threads, interrupts and I/O. The HAL hides small differences between motherboards.
FirmwareCode that is not part of Windows.
Firmware on the device inside the GPU, Wi-Fi, SSD, touchpad
UEFI / BIOS starts the PC and loads Windows
ACPI tables + Embedded Controller describe and run the board (power, battery, lid, fans)
CPU microcode fixes inside the processor
HardwareThe chips themselves: CPU, memory, chipset, disks, GPU, network, USB, input devices.

How drivers are loaded at boot

  1. winload (the Windows boot loader) reads the registry and loads every Boot-start driver into memory, before the kernel runs. These are the drivers needed to read the disk: ACPI, PCI, storage, file system.
  2. The kernel starts and initialises the Boot-start drivers, then loads and starts the System-start drivers.
  3. The Plug-and-Play manager walks the hardware tree. For each device it finds, it loads the matching Manual (demand-start) driver. This is why most drivers are "Manual": they load only if the hardware is present.
  4. The service manager (services.exe) starts the Auto drivers, together with the auto-start services.
  5. Disabled drivers never load.
How this maps to the tool's phases. kernel_to_smss holds the Boot-start and System-start drivers and the early PnP drivers (the trace's milestones "PnP boot-start drivers" and "PnP system-start drivers" are in this phase). smss_to_wininit holds more PnP drivers (graphics, audio, Wi-Fi, Ethernet, USB, input). Drivers in the XML with no ETL event in the four pre-logon phases are shown as after logon: they started later, mostly through the service manager or on demand.

2 · Driver kinds and firmware

hardware

Hardware device drivers

Drive one device: GPU, Wi-Fi, Ethernet, disk, USB device, touchpad. The device runs its own firmware. Some drivers also upload a firmware file into the chip each time they start (Wi-Fi, Bluetooth, some GPUs).

If slow: check the driver version, then the device firmware version, then the device itself (a failing disk or a device that does not answer).

platform

Platform drivers

Talk to the motherboard: ACPI, PCI, processor power, battery, SMBIOS. The firmware behind them is the UEFI/BIOS, the ACPI tables, the Embedded Controller and CPU microcode.

If slow: check the BIOS/UEFI version and its settings first; ACPI methods and the Embedded Controller run firmware code, not Windows code.

software-only

Software-only drivers

No hardware and no firmware: file systems, filters, network protocol stacks, crypto, volume managers, security products.

If slow: check the driver version and what else is stacked with it. A file system is often slowed by filter drivers stacked on it (antivirus, cloud sync, encryption).

In the tables below, chipset controllers (USB host, SATA, HD Audio, PS/2) are marked hardware with firmware yes-platform: the UEFI firmware sets them up and they are part of the motherboard. Class drivers that only translate data (for example kbdclass, mouhid) are marked software-only: the hardware and its firmware sit below them.

5 · From this list to building a kernel

These lists are a map of a running Windows. They are not a recipe for a kernel. Most of the drivers above exist because Windows supports thousands of devices and features. A kernel does not start with drivers.

What a kernel needs first

  • Boot, and switch the CPU into its modes (real mode → protected/long mode).
  • Paging and memory: physical page allocator, virtual memory.
  • Interrupts and exceptions.
  • A scheduler: threads and context switches.
  • System calls: the door from user programs into the kernel.
  • Locking: so two CPUs do not break the same data.

A hobby kernel starts with about 5 drivers

  • Screen (text mode or a frame buffer)
  • Keyboard (PS/2)
  • Timer (for the scheduler)
  • Disk (ATA or virtio in an emulator)
  • Serial port (for debug output)

A learning path

  1. Operating Systems: Three Easy Pieces (Arpaci-Dusseau; free online): the concepts.
  2. xv6 with the MIT course 6.1810: a small real Unix-like kernel you read and change.
  3. The OSDev wiki and Philipp Oppermann's Writing an OS in Rust: build your own from boot.
  4. Windows Internals (Russinovich, Solomon, Ionescu, Yosifovich): how Windows does all of the above, including drivers and boot.

6 · Glossary

Driver
Code loaded into the kernel that controls a device or adds a kernel feature (file system, filter, protocol).
Firmware
Software stored in or loaded into a chip, which runs on that chip, not on the main CPU under Windows.
UEFI / BIOS
The motherboard firmware. It tests and sets up the hardware, then loads the Windows boot manager. UEFI is the modern form; BIOS the old one.
ACPI
Advanced Configuration and Power Interface: tables and small programs in the firmware that describe the board's devices and how to power them.
Embedded Controller (EC)
A small microcontroller on laptop boards. It runs its own firmware for the battery, charger, lid, keyboard matrix, fans and power buttons.
HAL
Hardware Abstraction Layer: the part of the kernel that hides differences in interrupt controllers and timers between boards.
PnP (Plug and Play)
The kernel manager that finds devices, picks a driver for each and loads it.
Boot-start / system-start / demand-start
Start types. Boot = loaded by winload before the kernel runs. System = started by the kernel during its start-up. Demand (shown as "Manual") = loaded by PnP or on request. Auto = started by the service manager. Disabled = never.
Filter driver
A driver stacked above or below another driver to watch or change its requests (antivirus on a file system, a firewall on a network adapter).
Device instance id
The name of one device in the device tree: bus\vendor&device\instance.
Microcode
Low-level code inside the CPU. Updates come from the UEFI firmware or from Windows at boot and fix CPU bugs.
